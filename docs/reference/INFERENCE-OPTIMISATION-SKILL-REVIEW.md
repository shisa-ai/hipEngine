# Inference optimisation skill review

Reviewed 2026-11-20 against hipEngine `826c3a24f` and Sybil Solutions' [`inference-optimisation` skill at `fda968e7fc19`](https://github.com/sybil-solutions/inference-optimisation-skill/tree/fda968e7fc1996aa23c67139c755fe541c9d4be0/skills/inference-optimisation). This is a source review, not a benchmark, policy change, or decision to integrate. “Not found” means no common mechanism was identified in the reviewed paths, not that no campaign has done it.

**Finding:** The skill is a useful checklist for tuning an unfamiliar serving stack. hipEngine already has workload-specific rooflines, bracketed comparisons, and long-context soaks. The additions worth considering are more consistent host checks, a startup comparison protocol, and a way to prove that a rebuilt deployment recipe matches the tuned winner. Keep `/multiloop` and native hipEngine harnesses rather than running a second optimization system.

## Integration options to revisit

1. **Host preflight and postflight for expensive serving comparisons.** The exploration rules already call for one GPU benchmark owner, the [microbenchmark tooling](../../benchmarks/micro/collect_env.py) captures power, clocks, and temperature, and some [gfx1151 harnesses](../../scripts/qwen4exp_active_task_checks.py) share a lock. The opportunity is consistent enforcement across entry points: reserve the selected physical device, record power source/profile and competing work before and after, and reject a performance comparison if conditions materially changed. Do not change power settings implicitly. On unified memory, keep allocator accounting, HIP samples, and whole-device GTT figures distinct. Per-container driver residency may be an additional view for external engines, not a replacement.
2. **A startup comparison protocol.** The [server](../../hipengine/server/api.py) already reports engine creation, resident preparation, warmup, probes, and total startup. Compare labeled fresh-process starts with controlled file/JIT cache state, warm restarts, and first-request TTFT. A warm restart is not evidence for a cold start, and process-to-ready is not request TTFT. Use this protocol when startup is the objective, not on every iteration.
3. **A deployable-recipe verification packet.** Pin model and build inputs, mechanically compare the rendered launch to the winning configuration, and run comparable workloads against the rebuilt artifact and the tuned winner. Check readiness and chat, plus reasoning, tools, vision, or concurrent retrieval at depth when the recipe advertises them. Keep this separate from package CI and feature enablement.
4. **A lightweight external-server comparison.** Use the upstream checklist when only an OpenAI-compatible endpoint is available and the question is basic startup, TTFT, prefill, or decode triage. Prefer our existing replay and matched comparator harnesses for retained claims. The external vLLM, SGLang, Intel XPU, and ExLlama notes can inform surveys; recheck them on the pinned stack.

The smallest first step, if any of these are adopted, is a serving-run template in the existing benchmark playbook: name the harness, target shape and metric, cache state and physical device, host evidence, applicable controls, and any depth or recipe check. Add shared verifier code only for checks that repeatedly need manual work.

## Why not adopt the upstream helpers as verifiers?

- **`bench.py`** can leave `ok=true` after missed retrieval or flagged looping, and its CLI does not turn an unsuccessful result into a nonzero exit. Long context is one approximate-length request with substring matching, not a measured full-depth concurrent soak. Its concurrent rate includes prefill and total request wall time; it is neither decode-only throughput nor proof of device overlap. It uses server usage counts, but measures decode through stream completion rather than the last content delta.
- **`queue.sh`** serializes callers that share its lock, not arbitrary GPU users or hipEngine harnesses on a different lock. It prints completion messages without enforcing benchmark verdicts. The run order is useful; the script is not a keep/revert guard.
- **`mem.sh` and the watchdog** provide a container-oriented sampled diagnostic. Missing or unreadable measurements can be treated as zero or skipped; a trip invokes the optional configured stop command, not a guaranteed cancel/drain/stop sequence. Do not treat this as a fail-closed memory cap or as equivalent to native AMD memory accounting.
- **`ceiling.py`** is a useful worksheet, not a validated multi-user roofline. Its aggregate decode expression divides traffic by `accept * n` and then multiplies the resulting rate by `n` again. If `accept` is emitted tokens per stream per step and the modeled bytes are already per group step, the second factor counts concurrency twice. Validate the units and calibrate against measured traffic before using the estimate.

The distinction to preserve: **reuse the checklist and external hypotheses; retain hipEngine's evidence, correctness, and promotion rules.**
