# Inkling 2 Mini: match Loom on Strix Halo

**Goal:** Match or beat Loom on the same Strix Halo host, using the exact same Inkling 2 Mini checkpoint and workload. Start with ordinary text generation. Measure drafting separately, and do not count it as a speedup unless it preserves the declared output contract. There is no same-weight hipEngine result yet: the first deliverable is packed GGUF generation on `gfx1151`, not a faster result on another GPU or quantization.

## What we know

- **Local Loom:** fixed backing works with `hrx-loom` 0.2.0; elastic backing failed the compiler's KV pool range check. At 575 input / 128 output tokens, three warm ordinary requests had a median of **0.524 s to first streamed text** and **3.749 s end to end**, with no prompt reuse. Depth one was quicker but changed streamed reasoning in four of six pairs across the 47- and 575-token workloads. Repeating a prompt at each length in reverse mode order reproduced the same text within a mode and the same difference across modes. This is evidence for an ordinary reference, not evidence that spec always diverges. The [published card][loom-card] reports a passing spec gate on its own inputs and setup, uses depth one for its one-stream rows, and turns drafting off on both sides for four streams. Reproduce these as separate lanes, not as one blended result.
- **hipEngine on W7900:** text prefill already batches causal short convolution, K/V preparation and attention, and expert routing. Routed expert projections share weights across four prompt rows and production uses blocks up to 256 tokens. The [warm width confirmation][w7900-prefill] measured 6.262 s to first token at 512 input / 128 output with exact first-token logits and output IDs against the narrower control. Decode stayed near 15 tok/s. The [existing dense matrix-instruction pilot][dense-pilot] changed arithmetic without a consistent latency win. Do not repeat either trial unchanged. [The earlier same-W7900 llama.cpp comparison][w7900-gguf] used a different checkpoint and predates the new prefill work.
- **GGUF bring-up:** the [CPU NVFP4 decoder][nvfp4] matches the pinned llama.cpp block decoder on synthetic and sampled mainline rows. This does not validate whole-model inference or per-expert scales. The Loom file declares 48 visits, stores 24 physical layers, and has global loop residual query banks. It contains NVFP4 expert weights with external scales and Q8_0 experts in the final four physical layers; the scanned mainline artifact also has Q5_K expert banks and different loop tensors. Support each layout by its declared metadata and tensors, not by filename or hash. In particular, [llama.cpp #32704][scale-pr] documents a bug where repeated visits lost the physical layer's expert scale vectors.
- **Packed GGUF prefill:** the W7900 `fast` path reads prompts in 64-token blocks and takes 5.1 to 5.4 s for 575 tokens in-process. Its grouped expert kernels are limited by FP32 dot-product throughput, not weight reads: the NVFP4 tile kernel runs at 5.12 TFLOP/s and does not speed up with 256-row blocks, which re-read the weights three times fewer ([width trace](../../worklog/entries/20261123T234541.751229Z-lhl-inkling2-mini-2f4ab7.md)). The host leaves the GPU idle for about two thirds of the window under the profiler. A matrix-core grouped expert kernel and device-resident per-visit work are the two prerequisites for Stage 3.

## External optimization leads

**Vulkan fork.** The author's [pinned `INKLING.md`][vk-notes] documents batch-one `llama-bench tg64` on an RX 7900 XT with legacy root `UD-Q4_K_M`: **25 → 66.5 tok/s** when strided gate/up halves stayed on GPU, then gains from fused routing, depth mixing, loop gates, convolution and relative attention, and finally **108.9 tok/s** with a dedicated NVFP4 matvec and fused expert scales among other changes. The early rows use F16 KV; the last two use Q8_0 keys and Q4_0 values, with a bridge measurement at the 84 tok/s stage. The notes report 2,075 tok/s at `pp512` and give distinct long-context and server results. These are author measurements, not reproduced here. [Upstream Vulkan PR #32735][stride-pr] independently demonstrates the non-contiguous `SCALE` fallback on a different card and checkpoint. Check hipEngine traces for analogous host crossings; do not port a Vulkan scheduling fix into HIP without finding an equivalent problem. Test direct NVFP4 decode, outer-scale fusion, on-device loop ops, and streamed relative bias as separate changes. The [LocalLLM thread][vk-thread] also includes a Radeon 780M follow-up that changes artifacts and reports a DSpark slowdown; use it as a lead, not a matched result.

**Gufo HIP extension.** The [v0.1.0 architecture][gufo-arch] describes aligned planar packed weights, grouped matrix-instruction prefill for routed experts, table-based flash attention, fused single-token operators, and HIP graph replay. Its [progress log][gufo-results] reports roughly **29–30 tok/s ordinary decode**, **650 tok/s prefill**, and **56 tok/s aggregate across four requests** on its Strix Halo with mainline `UD-Q4_K_M`, with byte-identical batched versus serial output in the reported check. Its DSpark run was slower than ordinary decode; the authors cite weak acceptance, increased expert traffic during verification, and an unoptimized draft head. These are author measurements, not results on `strixhalo`. The [StrixHalo thread][gufo-thread] discusses the launch-limited diagnosis; verify it locally before choosing graph replay over memory-traffic work. The [tagged validation notes][gufo-readme] use teacher-forced expert routes for layer comparisons, which is useful for isolating arithmetic differences but does not replace an independent router check.

**Loom source audit.** The [local audit][loom-audit] identified batched convolution with separate history commit, staged current K/V followed by causal attention and ring commit, fused normalization and row preparation, and tiled loop, router, and matrix prefill work. hipEngine already adopted the first two scheduling ideas on the original-checkpoint path. Transfer their state ordering to GGUF; profile the remaining fusion and projection differences rather than restarting those ports.

**Maya Inkling engine.** The [guide][maya-guide] of [alesha-pro/maya-inkling-mini][maya-repo] documents a CUDA engine for the same Unsloth `UD-Q4_K_XL` file as the Loom lane. On one RTX 3090 it reports **128 tok/s plain decode** and **2,742 tok/s prefill at 4,096 tokens**, with `llama.cpp` at 57 and 1,052 on the same card. A token replays as one CUDA graph of 781 launches with routing and every expert on the device, and prompts are read in 2,048-token chunks through FP16 GEMMs, with a grouped expert path for prompts up to 96 tokens. Its matrix-core kernels are `mma.sync` and do not run on AMD, so what transfers is the structure and the order of work; the [local review](../../worklog/entries/20261123T233607.588698Z-lhl-inkling2-mini-826f0a.md) maps it to hipEngine and lists what the author reports did not help. These are author measurements, not reproduced here.

## Execution order

| Stage | Work | Advance when |
| --- | --- | --- |
| **1. Packed reference and public bring-up** | Build an `inkling2` adapter for the pinned Loom file and a separate `inkling2_loop` mapping for the mainline lane. Map physical weight layers, repeated visits, and per-visit KV and convolution state explicitly. Validate vocabulary, loop queries and controller tensors, Q8_0 dense weights, expert scale application at every visit, and NVFP4/Q8_0 expert projections; cover Q5_K where the mainline layout requests it. Keep banks packed on device, with a slice-decoded CPU oracle. | Public `LLM.generate()` and served text run on the pinned Loom file on `gfx1151` without a reference fallback. Record layer/visit and token evidence; test the mainline mapping independently against llama.cpp with the repeated-slot scale fix. |
| **2. Profile and remove decode boundaries** | Trace one ordinary request at short and warm long context. Attribute complete token time to host/device transfers, synchronization, launch gaps, routing and experts, attention, and vocabulary projection/sampling. Keep activations, routing, and sampling on device where the trace warrants; fuse depth mix, loop controller, short convolution and residual, clip/norm and KV store where adjacent. Try graph replay once argument and state ownership are stable; measure fusion and replay separately. | Public traces prove the intended route ran with fewer transfers or launches and lower wall time or an attributable phase win. No removal of per-request state, masking, or cancellation checks. |
| **3. Raise prefill and long-context throughput** | Bring the existing block schedule and four-row weight reuse to the packed route. Profile dense and expert projections before testing aligned tile reuse and grouped matrix-instruction prefill. Test table-driven relative-bias evaluation inside tiled causal attention rather than materializing a full query-by-history bias tensor. Preserve old-ring/staged-new-KV ordering and sink semantics. Measure prompt ingestion and prepared-depth decode separately. | Validate logits and state across chunk boundaries, sliding-window wrap, and local/global slots. Establish the limit with an allocation probe before running a full long-context workload. Arithmetic-changing variants pass their profile gate before default promotion. |
| **4. Improve packed expert and vocabulary bandwidth** | If profiling identifies these as limiting, compare direct packed NVFP4 decode with widened scales, apply each expert's external scale in the projection, and measure Q8_0/Q5_K paths separately. Compare weight bandwidth and gathered expert bytes, not just kernel time. Profile the vocabulary head and full-vocabulary sampling separately; keep user sampling semantics fixed. | Measured wins survive the complete request, correctness, and peak memory checks; include load costs for any repack or scale expansion. |
| **5. Four streams, then DSpark** | Bring up independent requests with packed device execution and exact continuation ownership. Compare four concurrent streams with speculation off first. Measure DSpark depth one against true ordinary decoding, then test broader proposal depths only if the economics warrant it. Record proposals, accepted tokens, unique experts per verifier block, and draft/verify/rollback time plus bytes. | Four-stream outputs satisfy the declared isolation contract under refill, cancellation, and wrap. Speculative results are separate until verified against their own ordinary route and the full prompt and held-out suite; do not infer a win from acceptance alone. |

Stages 2–4 may move in priority based on the first complete profile. Reuse existing registry, generation, and request-state ownership. Preserve original-checkpoint text and image behavior; Loom has no image comparator. Do not make a capability depend on a measured artifact allowlist. Source-derived code needs license review, file and commit lineage, and the same tests as in-tree kernels.

## Measurement and completion

1. **Freeze the protocol before tuning.** On `strixhalo`, pin target and tokenizer hashes, runtime revisions, clocks/power settings, context and KV types, and prompt IDs after rendering. Use the same inputs, output limit, sampling parameters, warmup, and localhost streaming timer; verify no prompt reuse unless testing a prepared context. Match KV storage for the isolation comparison, or label the run as a complete-stack comparison and disclose the difference. Record both the release configurations and any normalized configuration needed to isolate a change.
2. **Run matched cells, not headline ratios.** Start with the local 47/128 and 575/128 cells. Add fresh prefill around 1K, 2K, 8K, and 32K, a prompt that crosses the rolling window and is not aligned to a chunk, prepared-context ordinary decode near 2K and 32K, and four simultaneous ordinary streams. Use varied natural prompts for the completion matrix. For each arm record prefill time, first streamed text, steady decode, end-to-end time, peak memory, and warm/cold status as applicable. For four streams report per-request latency and aggregate cohort throughput; do not sum isolated request rates. Keep the W7900 development lane separate.
3. **Establish correctness before interpreting speed.** Check known answers and identical rendered IDs; capture generated IDs where available, streamed text, finish state, and actual token counts. If free-running results diverge, localize the first difference with teacher-forced logits and routing, and distinguish near-ties from errors in scales, cache ownership, token selection, or rendering. Compare routed values on fixed expert IDs and compare independently selected top-eight experts and scores. Test strict fixtures, production numerical gates where arithmetic changes, cache wrap, request isolation, and provisional rollback. Label output drift or timing-boundary differences instead of treating those cells as output-preserving wins.
4. **Declare match per metric.** Use at least five warmed paired samples per cell, repeated in reverse engine order, with an idle GPU. For decode/prefill throughput and four-stream aggregate throughput, a match is at least 97% of Loom's median; for time to first streamed text and end-to-end latency it is at most 103%. A beat is a greater-than-3% improvement in both orders for the named metric. Require the match bound in both orders for the campaign's ordinary workloads; if baseline noise exceeds the band, mark the cell inconclusive and collect more evidence before calling it. Publish regressions alongside wins and do not roll a diagnostic into the scoreboard.

Record exact commands, profiles and manifests, correctness checks, samples, and rejected alternatives in immutable worklog entries. Follow [Optimization and Evidence Rules](../OPTIMIZATION.md), [Execution Profiles](../EXECUTION-PROFILES.md), and [Benchmark Protocol](../BENCHMARK.md) for implementation, promotion, and any benchmark publication.
