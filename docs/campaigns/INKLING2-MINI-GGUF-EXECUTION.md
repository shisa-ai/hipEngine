# Inkling 2 Mini: GGUF optimization implementation plan

**First assignment: lock in the matched comparison, then retest the public block.** A CPU check showed that the full-block prototype and the host trace exposed *different tensors* at two loop restarts and at model exit, so the reported differences there did not localize an attention bug. A [matched 48-visit dump][matched] now agrees within 1.6e-4 (maximum absolute difference) across the block, host and NumPy paths on one 64-token W7900 prompt. With the comparison sound, the highest-priority changes are to keep activations and routing on the GPU across visits, and to speed up expert projections at the group sizes real prompts produce. These target different costs: host waits during generation and GPU arithmetic during prompt processing. Loom's decode already streams weights at about three quarters of Strix Halo's practical bandwidth, so a match also needs whole-token submission and near-bandwidth kernels; see the [decode budget](#decode-budget-what-looms-rate-requires). Prompt processing is the wider gap at 575 tokens and about half of that cell's end-to-end gap; see the [prompt budget](#prompt-budget-what-looms-prefill-requires). Loom ships with depth-one drafting on, so the speculative window in step 7 is part of matching its shipped decode, not an optional extra.

This is the implementation companion to [Match Loom on Strix Halo](INKLING2-MINI-LOOM-OPTIMIZATION.md), which owns the target, checkpoint locks, workload matrix and definition of a match. Code audited: `inkling2-mini` at `10d814df5`, including the pinned-upload repair; diagnostics through [the November 24 boundary sweep](../../worklog/entries/20261124T131703.985686Z-lhl-inkling2-mini-34e569.md). Before taking a task, check `git status -sb`, the latest Inkling worklog entries and the actual callers. If another worker owns the resident-block repair or the GPU, use their result; work on the CPU oracle or comparison harness instead of running a competing benchmark.

## Decode budget: what Loom's rate requires

A decode token reads each weight it touches once. Every visit reads its physical layer's dense tensors and eight of 128 routed experts. The second and third core passes add the loop controllers, and the head is read once. Byte counts below come from each file's tensor table, from the [Loom program's tensor views][loom-step] for the root file and from `scan_gguf` for the mainline file. They are computed, not measured:

| File | Routed experts | Dense, mostly Q8_0 | Loop controllers | Q8_0 head | Per token |
| --- | ---: | ---: | ---: | ---: | ---: |
| Root `UD-Q4_K_XL` (Loom lane) | 1.85 GB | 1.44 GB | 0.23 GB | 0.49 GB | 4.0 GB |
| Mainline `UD-Q4_K_M` | 1.78 GB | 1.44 GB | 0.23 GB | 0.49 GB | 3.95 GB |

- **Strix Halo.** At the [~221 GB/s local read reference][rdna3-roofs], streaming 4.0 GB takes 18 ms, a ceiling near 55 tok/s. Loom's 39–43 tok/s (23–26 ms per token) means it already streams at roughly 155–175 GB/s and spends only 5–8 ms on everything else. The November 22 hipEngine rows (70–93 ms per token) are overhead, not bandwidth.
- **W7900.** At 750–820 GB/s the floor is about 5 ms (~200 tok/s); the measured ~18 tok/s is ~55 ms. A kernel trace puts 19.7 ms of that step in 1,618 kernels after 1,717 prompt tokens (17.4 ms after 47) and the rest in host work between them: rocBLAS GEMV 5.0 ms, the Q8_0 dense GEMV 4.0 ms, the NVFP4 experts 3.3 ms, attention scores and values 3.5 ms, the Q8_0 head 1.8 ms.

**Loom does not issue fewer kernels.** Its [single-token branch][loom-visit] launches about 26 kernels per sliding-window visit. That comes to roughly 1,300–1,400 per token with controllers and head; hipEngine's [four-row trace][four-row] recorded about 1,230 dispatches per row. What differs is that the whole step is one recorded device command: routing and token selection run inside it, only token IDs come back, and nothing waits on the host. Each normalized activation is quantized to Q8 once and feeds every integer-dot matrix–vector product that consumes it. Gufo's pinned source [replays decode-sized steps as one HIP graph][gufo-graph] by default, with routing on device, ~1,900 launches and full logits returned to the host sampler. Its log reports 29–30 tok/s on Strix Halo, so capturing today's launch count is unlikely to be enough on its own.

**What a match leaves for overhead.** 41 tok/s is 24.4 ms per token. If weight streaming reaches 85–95% of 221 GB/s (19–21 ms), attention, sampling, host work and every gap between dependent kernels must fit in about 3–5 ms: 2–4 µs per kernel at Loom's count. A Python `ctypes` launch costs [about 15 µs][kernels] on the host. At today's count that is ~18 ms per token, the entire Strix floor and over three times W7900's. Therefore:

1. Whole-token submission (step 4) is a prerequisite for the match, not an optional last step.
2. The node count a token can afford follows from the measured cost per dependent node (step 0): roughly (24.4 ms − streaming − attention) ÷ that cost. Fuse to that count, not further.
3. Every weight-streaming kernel needs its own GB/s figure. The eight-route expert chain [took 231.67 µs on Strix][graph-loss] for about 35.8 MB of weights, ~155 GB/s including its packing and mix kernels. Maya's first matrix-core expert kernel beat its scalar kernel only after eight warps shared each 16-row group on separate K strides with one step of lookahead. It then ran at 745 of 936 GB/s: bytes in flight set matrix–vector speed. The step 0 probe has since measured the same chain on W7900 at ~237 GB/s and the Q8_0 head at ~307 GB/s: 27–36% of the [864 GB/s roof][roof-w7900], not the 576 GB/s that [its entry][w7900-ceiling] names.

**Rows and drafts change the bytes, not the floor.** Dense projections, loop controllers and the head (2.16 GB) serve every row of a step; experts do not. With independent routing, four rows touch on average 128 × (1 − (120/128)⁴) ≈ 29 experts per visit, 3.6 times one row's. Reading the shared set once cuts per-token bytes by about 40%; grouping experts across four independent streams saves only about 7% more. A depth-one verifier window (anchor plus one draft) touches about 1.9 times one token's experts with independent routing, 2.0 at most. A bandwidth-bound depth-one step therefore costs up to about 1.45 ordinary steps of weight bytes before any drafting. Consecutive tokens of one stream route more alike: [Maya's five-token window][maya-how] read 2.7 times one token's experts, not the 4.4 expected from independent routing. Compute break-even acceptance from unique-expert counts measured on captured routes, not from these bounds.

## Prompt budget: what Loom's prefill requires

Prompt processing is the wider gap and, at 575 tokens, as large a share of the request as decoding. Times are the two run-order medians of the [paired run][pairs]; bytes and FLOP counts come from the root file's tensor table. They are computed, not measured:

| 128-output request | hipEngine `fast` | Loom | Ratio |
| --- | ---: | ---: | ---: |
| 47 input: time to first text | 0.952–0.971 s | 0.215–0.230 s | 4.3× |
| 575 input: time to first text | 10.145–10.595 s | 0.529–0.540 s | 19× |
| First-text cost per prompt token (slope between those lengths) | 17.8 ms | 0.59 ms | 30× |
| First-text cost that slope leaves unexplained | 0.12 s | 0.20 s | 0.6× |
| 575 input: split of the 18.4 s end-to-end gap | 9.8 s before first text, 8.6 s after | | 53% / 47% |
| 47 input: split of the 6.8 s end-to-end gap | 0.7 s before first text, 6.1 s after | | 11% / 89% |

Request setup is not the problem. The prompt-side work is:

- **Cost is per block-visit.** 575 tokens are nine 64-row blocks through 48 visits: 432 block-visits at about 24 ms each in the November 22 Strix run. In the November 23 profile the [kernel sum][strix-trace] was 11.9 ms per block-visit: grouped NVFP4 6.5 ms, packed dense projections 1.4 ms, block attention 1.4 ms, other 2.6 ms. The rest of the November 22 wall is host work between launches, with six stream waits per block-visit (2,593 per prompt in the November 22 trace). The same prompt took 6.9 ms per block-visit on W7900 once controllers and the attention half ran on the device. A 47-token prompt pays 48 block-visits at about 20 ms each, so its 0.96 s is nearly all per-visit cost.
- **Block width is a bandwidth requirement on Strix Halo.** Each 64-row block spreads 512 expert picks over 128 experts and touches about 98% of every bank. For a 575-token prompt:

  | Rows per block | Blocks | Expert bytes re-read | All weights | At 221 GB/s |
  | --- | ---: | ---: | ---: | ---: |
  | 64 (today) | 9 | 261 GB | 277 GB | 1.26 s |
  | 128 | 5 | 148 GB | 157 GB | 0.71 s |
  | 256 | 3 | 89 GB | 94 GB | 0.43 s |
  | 512 | 2 | 59 GB | 63 GB | 0.28 s |
  | 575 (whole prompt) | 1 | 30 GB | 31 GB | 0.14 s |

  At today's width the re-reads alone take 1.2 s, more than twice Loom's whole prefill, so no kernel change makes a 64-row block match. The same 277 GB take 0.32 s on W7900, which is why width alone showed no kernel gain there. At 8K tokens, 64-row blocks re-read 3.9 TB (17.8 s) and 1,024-row blocks 0.25 TB (1.1 s).
- **Compute sets the floor.** Tensor shapes give about 9.8 GFLOP per prompt token, 5.2 TFLOP for 575 tokens. At the [27–33 TFLOP/s FP16 WMMA class measured on Strix Halo][rdna3-strix] that is 0.16–0.19 s, and 0.09 s at the 59.4 TFLOP/s specification (2.8–3.4 s at 8K). A match therefore needs one block for a prompt of this size, expert kernels at half or more of the measured WMMA class, and host work under about 0.1 s.
- **Today's kernels are far from either limit.** Grouped NVFP4 took 2.82 s for 3.22 TFLOP: 1.1 TFLOP/s and 79 GB/s, which is 8% of the 14.85 TFLOP/s FP32 rate without VOPD and 36% of the read reference. Packed dense projections took 603 ms; the dense projections and controllers are 1.57 TFLOP, so no more than 2.6 TFLOP/s. Block attention took 595 ms for 0.1 TFLOP. Each is about 12% of kernel time now and becomes the largest cost once experts are fixed.
- **Where a win over Loom is possible.** The [published card][loom-card] reports Loom at 1,179–1,282 tok/s on 1K–8K prompts, 12–14% of prefill ceilings near 9,000–9,600 tok/s, and at 42.7 tok/s in decode, 38% of a 112.7 tok/s ceiling that counts drafting (98.5 without). Its undrafted decode ceiling is 228 GB/s ÷ 98.5, about 2.3 GB per token, which is the expert and head bytes alone; its prefill ceiling implies 4.6 GFLOP per token. Counting every visited tensor (about 9.8 GFLOP and 4.0 GB per token), one Strix decode pass has room for about 55 tok/s and Loom uses about three quarters of it, so ordinary decode can beat Loom by at most about 1.3–1.4×. Prompt processing keeps roughly 3–4× above Loom at 44 TFLOP/s. Prefill is where to invest for a beat; the decode work is what makes hipEngine match.

## Work queue, ordered by expected impact

Priorities are hypotheses tied to measured work, not promised speedups. **Start with step 1's CPU comparison.** Step 0's driver and schema tests can run in parallel without the GPU, and its ceiling measurement needs an idle assigned GPU but no model; finish step 0 before claiming a new public timing. Step 3 can use captured routes independently of whole-block integration. Steps 4 and 7 depend on a stable ordinary token path. Build that path for one to eight rows, because the verifier window is the same kernels with more rows. Take one independently testable change per commit. Re-rank the remaining work if a new public trace changes which phase dominates.

### 0. Make the baseline and comparison reproducible

- **Deliverable:** check in a small ordinary-pairs driver and CPU tests for its timing/aggregation. The [paired HTTP worklog][pairs] describes an off-tree driver; a fresh checkout must not depend on it or its logs. Reuse [the decode marker script][trace] for attribution, [the decode bench][decode-bench] for the decode-rate control and [the known-answer check][tasks] for output sanity. Record the effective profile/manifest, actual variants and call counts, not just requested settings. The packed public route reports `execution_path=inkling2_gguf_packed_hip`; that distinguishes packed execution but does **not** identify a full resident block.
- For each request record input-token digest, generated IDs **when exposed**, first selected ID/time if available, first/last nonempty text (including reasoning), stream close, actual output count, finish reason, prefix-cache hits, draft state and request ID. A first text delta may represent more than one token. Report prompt-only throughput when a real prompt timer exists; otherwise label `input tokens / first-text latency` a proxy. Keep unprofiled wall measurements separate from marked kernel, copy and host timings.
- Freeze matched inputs, engine versions, quant, tokenizer, capacity, KV types, clock/power and sampling. Run one engine at a time. Check host memory, swap/I/O pressure **and** GPU ownership; no other GPU process is not sufficient. Preserve timeouts and missing reverse runs as inconclusive. If the host is occupied, finish fixtures and schema tests off GPU. Do not silence a timeout, change the output cap, or switch hosts to complete a pair.
- **Measure the dispatch and bandwidth ceilings** on each assigned GPU before choosing between fusion and replay; no model is needed. Time a chain of N dependent minimal kernels (N = 48, 1,300 and 2,000) launched from Python, from a captured HIP graph, and through the `aql` and `pm4` [submission transports](../../hipengine/core/pm4/transport.py). Record `HIP_FORCE_DEV_KERNARG` and try both values. Time one event record plus synchronize under default scheduling and under `hipDeviceScheduleSpin`. Then time each weight-streaming decode kernel alone at real shapes (Q8_0 at 2,304 and 3,072 wide, eight-route NVFP4 gate/up and down, the Q8_0 head) and report GB/s against the ~221 and 750–820 GB/s references. These numbers convert dispatch counts and bytes into the [decode budget](#decode-budget-what-looms-rate-requires); they are not model timings.

### 1. Correct the block oracle, then finish device-resident prefill

**Why first:** the [resident attention run][attention-run] removed a measured part of request time; completing the traversal is the shortest path to testing the remaining host visits. The [pinned upload race][upload-fix] was real and fixed. The [previous public block attempt][block-reject] failed repeat/quality checks **before** that fix. Neither establishes the result after it.

1. **Make a CPU RED test for observation points.** The scratch sweep used `prefill_block(..., capture=...)` and subtracted `trace[k]` from `_resident_block(..., limit=k)[0]`. In [`_traverse`/`_forward`][traversal], `capture(k, h)` is *entry* to visit `k`, **after** a prelude restore. At 18 and 30 that is not the preceding visit's exit. At 48 the callback gets `_output_hidden(h, blocks)`, not raw `h`. The [reported spikes][sweep] land on precisely these three boundaries. The [CPU-only reproduction][capture-repro] uses `TinyWeights` from [the existing fixture][tiny]. Turn its assertions into a unit test in `tests/test_unit_inkling2_reference.py` before editing a kernel. It invalidates this subtraction, **not** the earlier failed public test or the possibility of a real device error. The [matched dump][matched] confirms that reading for one prompt; it does not replace this unit test or the public retest in item 3.
2. Name and copy the same point on both arms: `(request, position, row, visit index, weight layer, state slot, phase)`. Use raw post-MLP hidden vs raw post-MLP hidden **before** the next restore; compare restored entry separately. At exit compare raw to raw, or apply the same final depth mix, norm, unpadded head and softcap to both. Snapshot before a mutable list grows or an arena is reused. Prove host-vs-host zero on the same schedule and inject a known wrong row to prove the checker detects it. Do not add fences to the timed path.
3. Re-run the isolated and **public** candidate on both layouts, same inputs in repeat and fresh sessions. Assert the *full-block* call count is positive for eligible blocks (not the sum of attention-half and full-block calls). Compare 32/64 rows, 63/64/65 tokens, 151, 257, 511, 575 and 1,031; include a multi-block prompt with final scalar tail, ring wrap, final logits and subsequent forced decode steps. Check the upload pool with overlapping payloads, late event completion, no-pinning fallback, growth and close. Preserve exact positions and independent visit histories.
4. If aligned outputs disagree, stop at the **first same-stage mismatch**. Capture inputs and output together: residual read → normalized Q/K/V or message blend → projected dynamic/static convolution → attention branch → residual add → expert inputs, outputs and post-convolution. Cross-check independently chosen routes *and* fixed-route outputs before attributing an error to routing. If only the old checker failed, retire it; do not change kernel math to reproduce it.
5. Only after the applicable gate, use the full traversal for eligible committed blocks. Keep scalar/tail, capture, provisional verifier and strict routes correct. `project_experts_mixed_rows(device=...)` currently requires a usable shared tile set: test zero reuse/small tails before handing it arbitrary blocks, provide the existing supported route **before any state mutation**, never replay a half-committed visit. Prove `LLM.generate()` and serving selected the intended path. Measure time through first token, per-visit downloads, bytes, waits and peak scratch versus attention-half `fast`.

### 2. Remove scalar decode round trips: router, experts, then the next visit

**Why:** the [W7900 suffix trace][waits] counted 2,088 stream waits across eight steps at both short and wrapped depth; the [host profile][host-profile] attributed more self time to synchronization than to any other single call. These are not 2,088 removable kernel durations. Start with `project_from_device` → `_select_routes` → `_plan_expert_chain`; the full-block prototype still downloads logits and constructs route metadata on the host. Even its `device=` expert arm builds `packed`, uploads a staging copy with the hidden region zeroed, then copies resident hidden into it. “Device output” does not mean “no transfer.”

- First separate immutable per-physical-layer gate/up and down scale tables from per-row IDs, mixture weights and tile records. Keep all per-request inputs in device buffers; have the consumer take pointers rather than upload an empty activation payload. Reuse the [fixed-route scale check][scale-replay] and the [guarded router experiment][router-trial], not a new standalone top-k demo. Count bytes and synchronizing reads per visit in addition to launches.
- Implement and test the [router contract][router]: sigmoid scores; optional correction bias **for ranking only**; lower ID breaks ties; sort winners by ID; normalize the **unbiased** scores with the model scale, then mix in order. Cover near-ties, identical logits, ignored padding, gate/up and down scales, with/without scales, and repeated physical layers. The [legacy layout check][coverage] covers 44 NVFP4 visits plus four Q8_0 visits; mainline also has Q5_K. Counts describe these artifacts, not admission rules.
- If a guarded path uses host resolution near a cutoff, a rejected arm must not publish speculative output or advance state owned by its fallback. Commit the selected expert convolution **once**; do not replay already committed attention or KV. Force accept, reject, alternating and mixed rows. Test device routing independently of forced-ID arithmetic; compare logits through subsequent steps, not just winner sets. The previous accepted arm changed logit bits; use the numerical gate, not a bitwise rejection or a claim of exact arithmetic.
- **Small F32 and BF16 matrices.** Every dense tensor that is not Q8_0 (router, loop controllers and the other F32/BF16 projections) is decoded to FP32 and projected through rocBLAS `sgemv`/`sgemm` ([`_launch_projection`](../../hipengine/loading/inkling2_device_dense.py)), about 400 calls per decode row. In the [four-row trace][four-row] they were the largest device bucket: 1,600 calls and 14.1 of 50.0 ms of kernel time per tick. Loom uses [dedicated row-tiled F32 kernels][loom-f32] for the 2,304-wide router and the 4,608-wide controllers, in single-row and four-row variants. Register a matrix–vector family that reads each matrix once for all rows of a step, then fuse the router with its top-k. Treat a reduction order different from rocBLAS as changed arithmetic for the router: cover near-ties and use the numerical gate.
- **Attention inputs.** The scalar decode step ([`Inkling2DeviceAttention.step`](../../hipengine/runtime/inkling2_device_attention.py)) copies host-built query, key, value, sink and an FP32 `heads × extent` relative bias into device scratch every visit. The bias accounts for most of that exchange's growth from [14.5 to 50.4 MB per eight steps][waits] between 47 and 2,057 input: 24 heads × 1,024 lags × 4 bytes is 96 KiB per visit once the lag extent fills. Project the relative query on device (Loom: one 384-output `attn_rel` product, then `qr_prep`) and evaluate the bias from the resident lag table inside the decode kernel, as the block path already does. Preserve sink, clipping, global log scale, masking and wrapped extents.
- **Token selection.** The [resident runner](../../hipengine/generation/inkling2_gguf_resident.py) downloads full logits and calls host `select_token`. For greedy rows, have the head write per-chunk (value, lowest ID) partials and finish on device, as Loom's [`g_head_mv_q8`][loom-head] and [`g_head_select`][loom-select] do. Tanh capping can merge nearly equal logits, so prove that the device choice matches the host's capped tie order over the unpadded vocabulary on the same rows. For sampled rows, use the existing [native sampler](../../hipengine/runtime/native_sampler.py) wherever `supports_native_gpu_sampling` admits the request. Keep the host sampler for the rest, and full logits wherever penalties, logprobs or verifier scoring need them. Do not copy Loom's 64-candidate sampling cap, which also applies when `top_k=0`; it changes the distribution. Gate on exact sampler, stop and streamed output contracts.
- Extend residency **one boundary at a time** on the scalar route: residual/controller → grouped Q/K/V and gated attention → experts/post-convolution → next visit. Keep eager launches first. Advance when counters fall and an unprofiled suffix or its isolated public phase improves in both orders.

### 3. Speed up grouped expert *prefill*, then widen prompt blocks

**Why:** [the pinned Strix trace][strix-trace] attributes 2,821 of 5,158 ms of summed kernel time to grouped NVFP4 at 575 tokens (not wall time). On W7900, [wider blocks alone][width] reduced re-reads but did **not** reduce NVFP4 kernel time. On Strix Halo the re-reads themselves rule out 64-row blocks, and every block-visit also carries its host cost ([prompt budget](#prompt-budget-what-looms-prefill-requires)). Do not start by copying Maya's chunk size; take the width and the kernel from the measurements below.

1. Capture per-expert `(count, token row, rank)` histograms separately for gate/up and down on real short, long, code, Japanese and mixed prompts; include sparse, skewed and uneven tails. Reuse [`build_expert_route_tiles`](../../hipengine/loading/inkling2_device_experts.py) and the existing [NVFP4 kernels](../../hipengine/kernels/hip_gfx1100/quant/gguf_nvfp4_gemv.hip) as controls. Keep the current small-group path. Bucket populated pairs on device; compare *useful* rows per tile, not nominal matrix throughput.
2. Compare one change at a time: raw packed weights vs Gufo-style aligned code/scale planes; selected four-route FP32 vs a dense-enough AMD wave matrix multiply-accumulate (WMMA) group; gate/up vs down; one FP16 activation vs high plus residual FP16 parts with FP32 accumulation. Check input conversion, true outer scales, capped gate/up activation and route reduction order against CPU and strict. Include conversion, group construction, partially filled tiles and recombination in the timed interval; record cold repack time, peak and resident bytes. No permanently expanded full expert bank without a memory and latency comparison.
3. **Fill the tile before judging it.** With eight routes over 128 experts, a step of T tokens gives about T/16 rows per expert: 4 at today's 64-token block, about 36 at 575 and 128 at 2,048. The [16-route FP16 screen][wmma-loss] lost where tiles were mostly padding. [Width alone][width] cannot speed an FP32-bound kernel, so neither result tests the combination. Loom's RDNA3 program shows one working recipe. Below 64 tokens per step its quantized projections use integer dot. From 64, [its experts run 64×64 FP16 WMMA tiles][loom-wmma] over expert-sorted rows: NVFP4 is decoded to FP16 in LDS, the activation is one FP16 value under a power-of-two row scale, accumulation is FP32, and the SITU activation and outer scale are fused. One step [admits up to 8,192 tokens][loom-step]. Test the matrix kernel and the wider block in the **same** experiment, at widths that fill the tile (256 through 2,048 plus unrelated lengths), and keep the current four-route path for small groups and tails.
4. Two negative controls matter: [16-route FP16 tiles lost on Strix][wmma-loss] at the tested densities, and [grouped Q8 prefill exceeded the KL ceiling][q8-loss] with the same top token. That KL was measured against `fast`, not the `strict` teacher that the [production gate](../EXECUTION-PROFILES.md#6-production-numerical-gate) uses. Replay the row against `strict` before treating integer-dot prefill as rejected; Loom uses that arithmetic below 64 tokens. Require a changed occupancy, layout or arithmetic hypothesis and replay the failing cell. Screen on both GPUs; re-profile the secondary Q5_K/Q8_0 banks and dense projections only if they become limiting.
5. With the projection result in hand, set **both** model block width and scheduler budget for the public route, independently and together. Log actual dispatched widths. Test the widths the kernel needs, tails and unrelated lengths; use larger blocks only where measured useful work warrants them. Measure first token, mixed-load decode starvation, memory and split-schedule quality. Do not generalize a session-only result to `serve`.
6. **Dense projections and controllers.** Packed dense projections took 603 ms on Strix and 209 ms on W7900 for 575 tokens. From 256 rows these are ordinary GEMM shapes (2,304 in, 1,024 to 3,072 out). First try the existing dense Q8_0 prefill WMMA owner, [`gguf_q8_0_t16_prefill.hip`](../../hipengine/kernels/hip_gfx1100/quant/gguf_q8_0_t16_prefill.hip), at these shapes. The alternative decodes each visit's Q8_0 matrices to FP16 in a bounded scratch and calls [`Rocblas`](../../hipengine/core/rocblas.py), which is how Maya handles experts. It adds about 0.6 ms of bytes per visit on Strix, so keep it only where it beats the fused kernel. Q8_0 values are not exact in FP16, so gate it as changed arithmetic. Do not do this for the expert bank: a 2 GB FP16 copy per visit costs about 21 ms of writes and reads on Strix, 1.0 s per 575-token prompt. Decode experts inside the kernel.
7. **Block attention.** It took 595 ms on Strix and 182 ms on W7900 for a 0.1-TFLOP prompt. [`inkling2_target_attention_tiled`](../../hipengine/kernels/hip_gfx1100/attention/inkling2_target_attention.hip) gives one 128-thread block to each (query head, row). The block walks the live context 16 keys at a time with three barriers per step, one thread doing the softmax bookkeeping and a serial dependent sum in every thread. Rework it so a wave owns one (row, KV head) with its three query heads, reads 128-dimensional keys and values as 16-byte vectors, keeps the running softmax in registers and reads each K/V row once. The number of (row, key, head) scores does not change with block width, so this does not depend on items 3 and 5. Keep the current kernel as the strict control and gate the new reduction order as production arithmetic.

### 4. Capture the whole token, then fuse to the measured budget

At Loom's kernel count a token has a few microseconds per dispatch, less than one Python launch costs on the host ([decode budget](#decode-budget-what-looms-rate-requires)). Whole-token submission is therefore required for the match. After step 2, trace a warmed eager token and keep it as the control. Then capture the token, or its longest stable visit chain, through the [existing HIP graph API](../../hipengine/core/hip.py). Follow the in-tree whole-step owners rather than writing a new one: [`gguf_packed_decode_graph.py`](../../hipengine/runtime/gguf_packed_decode_graph.py) for state-bound packed GGUF replay, and [`gemma4_decode_graph.py`](../../hipengine/runtime/gemma4_decode_graph.py) for context buckets and sliding-window rebasing over a ~780-kernel step. On the same graph, A/B the `aql` and `pm4` [submission transports](../../hipengine/core/pm4/transport.py) (`HIPENGINE_SUBMISSION_TRANSPORT`). A chain that must stay host-dispatched can use a native function table such as [`moe_c1_dispatch.hip`](../../hipengine/kernels/hip_gfx1100/dispatch/moe_c1_dispatch.hip). A [six-node expert graph][graph-loss] already lost on both GPUs; repeating it is not this experiment.

Keep inputs, request/slot mapping, positions, route records and sampler state mutable **data** at stable addresses; prewarm weights, kernels and scratch. No allocation, host route decisions, dangling staging buffers or borrowed output in capture. Key graphs by executable shape, storage and output requirements, not prompt identity. On a bucket miss execute eager for that step; test wrap, shape transitions, cancellation, slot reuse and teardown while another request survives. Report capture cost, memory, hits/misses, replays, host dispatch time and warm *wall* per token.

Fuse only as far as step 0's per-node cost requires, longest dependent chains first, each against its eager control. Fusions used by the reference engines:

- Quantize each normalized activation to Q8 once for all of its consumers. Loom feeds the query, gate, key, value and relative projections from one quantization.
- Paired or grouped matrix–vector products: Loom's `pair` variants, Maya's single q/k/v launch, Gufo's `k_multi_gemv`.
- Short convolution fused with its residual add or with clip/norm and KV store (Loom's `sconv1_stat_add` and `sconv1_swa_kv_prep_store`), or run inside the preceding product (Maya's `mv_q8p_conv`).
- The depth mix as one kernel per block count (Loom's `mix2`–`mix5`; Vulkan: one op instead of ~9, 72.5 → 77.1 tok/s).
- The loop controller as one kernel (Vulkan: 80.8 → 84.0 tok/s), and all twelve core layers' loop messages in one launch per pass (Maya).
- Router top-k fused with weight normalization (Vulkan's `TOPK_MOE`).

Folding the short-convolution residual into the convolution taps at load time (Vulkan: 77.1 → 80.8 tok/s) changes rounding; treat it as a production arithmetic candidate. Keep a fusion only if its own comparison passes; do not ship replay on node count alone.

### 5. Attack prepared-depth attention and KV traffic separately

**Attention is already a cost in the matched 575-token cell.** A token takes 71–72 ms after 47 input tokens and 93 ms after 575, 30% more. Loom's token goes from 23.0–24.3 ms to 24.4–25.6 ms, 6%. The K/V that step reads is 226 MB in FP32, about 1.0 ms at the read reference. At 2,057 tokens the [prepared Strix trace][depth-trace] put 51.8 ms of each token into split value (37.5 ms) and score (14.2 ms) kernels against a 2.1 ms K/V bound: about 9 GB/s.

The cause is kernel shape, not bytes. [`split_scores`](../../hipengine/kernels/hip_gfx1100/attention/inkling2_split_attention.hip) gives one wave to each (query head, key) and loads the key once per query head. `split_values` gives one 128-thread block to each query head; `split_chunk_values`, which `fast` selects from 513 live tokens, gives one to each 64-key chunk. Both walk their keys in a loop of dependent FMAs with one scalar load per thread per key. Rebuild the decode kernel around workgroups that each own a context range for one KV head and its three query heads, read keys and values as 16-byte vectors, keep several independent accumulators and merge partials in slot order. Hold FP32 storage fixed so the comparison is the kernel alone, and gate the new reduction order as production arithmetic; the current kernels keep the strict order.

`fast` **already has** chunk-parallel split values and table-based resident block attention. Re-trace before selecting a candidate. Instrument [`Inkling2DeviceAttention`](../../hipengine/runtime/inkling2_device_attention.py): local vs global slots, bias bytes, K/V bytes, scratch, split score/value durations and host work. Exercise sink-only and masked scores, lag-table extent, multiple heads, wrap and partial tiles; stage new K/V before the old ring is overwritten and preserve `KVLiveSpans`.

K/V read per step is 226 MB at 575 tokens, 470 MB at 2K, 872 MB at 8K and 2.5 GB at 32K: the 40 sliding-window visits stop at 1,024 keys and the 8 global visits do not. FP16 halves that. It is worth about 2% of a Loom-level token at 575 tokens, 7% at 8K and 19% at 32K, so measure it where it can matter.

Treat physical FP16 KV as a **separate storage experiment** against FP32, not a prerequisite for running or a fix for all output drift: [rounding K/V alone did not explain the Loom divergence][kv-trial]. Measure quality, capacity, bytes and prepared decode before considering FP8 or a different key/value quant. Run the allocation probe below first on the intended host, then one full unaligned prompt per required depth with finite logits, actual local/global live counts and cleanup. A W7900 allocation or 32K completion is not evidence for Strix.

### 6. Serve four ordinary streams

Extend the [existing resident cohort implementation][cohort], not a parallel server. Use the trace to choose between reducing row-serial prompt ingestion and filling grouped expert/attention/head work during decode. Share before grouping: dense projections, loop controllers, step 2's small F32 matrices and the head are read once for all rows of a step, and Loom specializes its products for 1, 4, 8 and 16 rows. Grouping experts across independent streams saves far less ([decode budget](#decode-budget-what-looms-rate-requires)). Preserve per-request KV, convolution, sampler and stop state. Test two, three and four rows with zero/partial/full expert overlap, unequal prompts, mixed finish times, refill, disconnect, deadline and slot reuse. Verify each row against its declared serial/control contract, then use a barrier to submit four actual HTTP streams. Report both steady aggregate during the common decode window and total output/cohort wall time including prefill, plus per-request first text and inter-token latency. [Prior pressured cohorts][cohort-pair] are not a parity result.

### 7. Speculative decoding: make the window cheaper than the tokens it saves

**Why it belongs.** Ordinary decode can beat Loom by at most about 1.3–1.4× ([prompt budget](#prompt-budget-what-looms-prefill-requires)), and Loom ships with depth-one drafting on: 44–47 tok/s in the local run and 42.7 on its card, against 39–43 undrafted. A verified window reads the shared weights once for several tokens, which is the one decode lever that goes further. hipEngine's drafter accepts 87% of depth-one proposals (198 of 227 across the 18 greedy prompts of the [W7900 suite][dspark-suite]). Loom accepts 56% on its prompts and still gains 13–14% in the [local run][loom-local]. Maya's five-token window gains 4% on prose and 19–71% on code and edits ([its table][maya-how]). [Gufo's log][gufo-results] (10–30% acceptance, 17.6 against 30 tok/s) and the [Vulkan fork's notes][vk-notes] (38–48 tok/s) both measured drafting slower than plain decoding.

**Why it is not one today.** GGUF verifies with ordinary scalar steps (`serial_target`). The packed block changed one token on 1 of 18 prompts: block and scalar `fast` arithmetic differ by about 1e-6 at the first visit, later routing amplified that, and a 0.013 margin flipped ([localized][verify-fail], [traced][verify-trace]). With the packed verifier still on, a two-token window took 116 ms against about 55 ms for one token, each proposal 7.0 ms, and drafting finished at 0.85× end to end ([same suite][dspark-suite]). In `strict` the block kept every routed expert and moved logits by less than 2.5e-5.

**The arithmetic.** Speedup is tokens committed per window divided by window cost plus drafting cost, both in ordinary tokens:

| Case | Tokens per window | Break-even cost | Cost for 1.3× |
| --- | ---: | ---: | ---: |
| Depth one at hipEngine's 87% acceptance | 1.87 | 1.87 | 1.44 |
| Depth one at Loom's 56% | 1.56 | 1.56 | 1.20 |
| Four drafts, Maya on prose | 2.63 | 2.63 | 2.02 |
| Four drafts, Maya on edits | 4.36 | 4.36 | 3.35 |

Bytes set the floor for both terms:

- **Window.** Two rows share 2.16 GB and touch about 1.9 times one token's experts, 1.41 times a token's bytes. Five rows cost 1.78 times at the 2.7× expert overlap Maya measured and 2.53 times with independent routing.
- **Drafter.** [`propose`](../../hipengine/runtime/inkling2_mini_dspark.py) runs the anchor and the draft rows through three 93 MB blocks once, projects the full vocabulary for them, then projects it again for each draft token's Markov correction. That is 1.27 GB per depth-one proposal: 5.7 ms on Strix Halo at the read reference, 0.23 of a 24.4 ms token. Four drafts cost 0.51. The two full-vocabulary projections are 1.0 GB of the 1.27.

At the byte floor depth one is about 1.14×, or 1.22× if consecutive tokens share more experts. Four drafts range from 1.15× on prose to 1.9× on edits. These are bounds to measure against, not expectations.

**Units, in order:**

1. **Build the token path for one to eight rows.** This is a constraint on steps 2–4, not extra work. The window is the same kernels with more rows, and the whole-token graph is keyed by row count, as Maya keeps one graph per window size. A verifier written later against scalar-only kernels would share neither arithmetic nor submission with ordinary decoding.
2. **One window pass.** Run anchor and drafts as rows of one traversal. Dense projections, controllers and the head are read once, which is the sharing step 6 needs. Expert picks are grouped on the device so an expert is read once for every row that chose it. Each key is read once for all window queries, and K/V rows are staged, then committed or dropped. Each visit's four convolution histories are recorded and rebuilt in one launch for rejected rows. The taps stay on the device. The original-checkpoint path already owns this commit and rollback: its `packed_target` verification over provisional blocks matched ordinary decoding token for token ([bring-up][packed-orig]). Port that ownership rather than writing a second rollback. For scale, Maya's five-token window cost 15.6 ms against 7.8 ms for one token on this path and 40.8 ms through its general prompt path ([how it works][maya-how]); Loom's [verifier][loom-verify] is one device command with acceptance on device and convolution replay in one launch.
3. **Exact greedy acceptance.** With row-shared kernels the window's arithmetic is the ordinary token's, so a draft is accepted exactly when it equals the target's argmax at that position. A stage that still reduces differently from the scalar path is the changed-arithmetic case that flipped the token: restore the scalar order there, or pass the production gate before the window is public. Keep `serial_target` as the control and the fallback.
4. **Drafter on the device.** `propose` is a NumPy loop with a host argmax per draft token. Capture the taps at visits 5, 23, 41 and the final hidden on the device, run the blocks and the Markov steps as one launch chain per window, and let the verifier read proposal IDs from device memory. Then cut the head: score the Markov correction on a shortlist of each row's first-pass candidates instead of all 201k rows. Maya's shortlist cost acceptance without saving time on a 3090; on Strix Halo each full projection is 2.2 ms, so measure time and acceptance together.
5. **Accept and commit on the device.** For greedy rows a small kernel compares draft IDs with the target argmax row by row and returns the accepted prefix length; commit keeps that many K/V rows and convolution states. Sampled rows keep the exact accept-or-resample rule with step 2's native sampler. The in-tree MTP route has a device accept and commit ([`qwen35_gguf_mtp2.py`](../../hipengine/generation/qwen35_gguf_mtp2.py)); reuse its contract if it fits. One result comes back per window: the committed count and the next token.
6. **Depth from measurement.** Record acceptance at depths 1, 2 and 4 on [all four prompt categories](../../benchmarks/prompts/mtpbench-code-general-ja.jsonl) and the disjoint held-outs. Choose depth from a running acceptance estimate or measured cost tables, never from prompt identity. Verify a short prefix first and continue only when all of it is accepted, so a long block spends its bytes only when they are used.

**Gates and ledgers.** Compare true draft-off with explicit depth one on the same target. Before enabling packed verification, pin the known [mixed-language divergence][verify-fail] and compare successive windows against ordinary logits on the same history, including the first token with taps. Test rejection at every offset, full rejection, partial acceptance, wrap, close and rollback of KV, convolution and draft features. Count distinct experts and bytes alongside time in draft, verify and restore, and report the tuning guide's [three ledgers][spec-ledgers]: proposals, accepted and committed tokens; same-session ordinary against speculative tok/s; and the share of steps that fell back to ordinary decoding. Keep the window only if verified tokens per unit wall time improve by more than 3% in both orders with output identical to ordinary decoding. A high acceptance fraction alone is not acceleration.

Loom's own depth-one run changed streamed reasoning on four of six paired prompts ([local run][loom-local]), so racing Loom with drafting on is a complete-stack timing, not an output match. Speculation and four streams compete for the same shared reads: Loom disables drafting for four streams, and vendor rows in the [Qwen3.8 specdec campaign][spec-campaign] show block drafters losing at high concurrency. Report them as separate lanes. The general method is in [`SPECULATIVE-DECODE.md`](../reference/SPECULATIVE-DECODE.md), and the [Qwen3.8 specdec campaign](QWEN38-27B-SPECDEC-OPTIMIZATION-CAMPAIGN.md) lists in-tree pieces to reuse.

### 8. Make the qualified plan the default

`fast` is opt-in. `ExecutionProfile.FAST` is documented as never a shipped default, and with no profile requested [`LLM`](../../hipengine/llm.py) resolves `None` for a combination that lacks a registered `strict` and `production` pair. `hipengine serve --model …` therefore builds the generator without the device-resident plan. When steps 1–4 pass the production gate on both layouts, register that plan as `production` for both backends, keep `strict` registered, and confirm that an unset profile selects it. Rerun the smoke below without `--execution-profile`, record which variants ran, and add the `docs/REFACTOR.md` entry for any switch that remains. A result that needs `--execution-profile fast` is not shipped.
