# Dense GGUF serving defaults: INT8 KV, fp32 scales, one slot

## Summary

A zero-flag `hipengine serve --model <gguf>` now reaches the context the recent
INT8 KV work makes available, instead of sizing against the most conservative
configuration the server can be in. Three coupled defaults changed on the dense
GGUF route:

| Knob | Was | Now | Rollback |
| --- | --- | --- | --- |
| `--kv-storage` | `auto` (resolved to BF16) | `int8_per_token_head` | `--kv-storage bf16` |
| `--kv-scale-dtype` | `fp16` | `fp32` | `--kv-scale-dtype fp16` |
| resident slots | 4 | 1 | `--max-active-requests N` |

Measured on the W7900 (48 GiB), one short chat request per run, no sizing or KV
flags, target artifact `Qwen3.8-27B-Q4_K_M.gguf` (SHA-256 `7b2aec3b...c89f1b`,
verified against the frozen lane identity):

| KV storage | Slots | Selected context | Bytes/token | Whole-card use |
| --- | ---: | ---: | ---: | ---: |
| INT8, fp32 scales | 1 | **176,128** | 142,944 B | 32.5 GiB |
| BF16 | 1 | 121,344 | 207,456 B | 34.4 GiB |
| BF16 | 4 | 40,960 | 600,963 B | 40.7 GiB |

**4.30x the context at 3.2 GiB less memory.** The previous defaults were the
subject of `20260912T134710.640315Z` and `20260912T152128.835655Z`; this entry
supersedes their selected-context rows.

## Changes

- `hipengine/server/__main__.py`: `--kv-storage` defaults to
  `int8_per_token_head`; `--kv-scale-dtype` defaults to `fp32`.
- `hipengine/generation/qwen35_gguf.py`: `_GGUF_RESIDENT_MODEL_LOOP_DEFAULT_CAPACITY`
  4 -> 1, with the slot-count reasoning recorded at the constant. Each slot
  reserves a full-context KV plane and the packed-workspace lease and union
  geometry follow the same capacity, so the slot count is the dominant
  multiplier on KV memory.
- `hipengine/server/api.py`: the request/response KV policy comparison resolves
  the **effective** storage from the engine's capability provenance instead of
  re-resolving `config.kv_storage`. Without this, an artifact that failed closed
  to BF16 would reject an explicit BF16 request, because the comparison still
  believed the server was on INT8. That mismatch predates this change; the new
  default merely made it reachable.
- `tests/test_unit_qwen35_gguf_capacity.py`: 33 tests. Adds the slot default and
  its override, the CLI defaults with both rollbacks, and
  `test_server_defaults_match_the_qualified_int8_contract`, which asserts the CLI
  defaults key a registered `qualified` contract for the target artifact.
- `docs/API.md`, `docs/REFACTOR.md`, `benchmarks/README.md`,
  `benchmarks/CHANGELOG.md`: the new defaults, the fallback contract, and the
  measured rows.

## The `scale_dtype` coupling

This is the load-bearing detail and the reason the first attempt at this change
did not work. Qualification is keyed on the exact artifact SHA-256, size,
backend, target architecture, weight quant, storage layout, **and scale dtype**.
The retained evidence for the supported dense artifacts is keyed on
`scale_dtype="fp32"` (`_QWEN38_GGUF_KV_CAPABILITY_EVIDENCE` in
`hipengine/models/qwen35.py`), and the server defaulted to `fp16`.

So the first run of this change requested INT8, built a key matching no evidence
row, and **failed closed to BF16 silently**. The evidence that it had happened
was an internally inconsistent report, not an error:

```
KVCache: storage=bf16 ... bytes_per_token=207456    # allocated BF16
/ready: kv_capacity.storage = "int8_per_token_head"  # requested INT8
/ready: kv_capacity.estimate.kv_storage_dtype = "bf16"
```

A fallback is a normal outcome by design, so it is not logged as a warning. The
new test asserts the CLI defaults key a registered `qualified` contract, so a
future artifact whose evidence is keyed on a different scale dtype fails a test
rather than silently shrinking the context.

`admission_gated_int8` in `hipengine/kvcache/policy.py` is the mechanism that was
*intended* for "`auto` means INT8 when qualified" — it makes `auto` resolve to
INT8 with `int8_admission=True`. It has no callers, and it is not used here: the
INT8 capability gate lives only in `qwen35_gguf.py`, while the PARO route has
eight `resolve_kv_policy` call sites and no gate, so routing `auto` through the
admission flag would give PARO unqualified INT8 — and the gfx1151 artifact is a
retained INT8 rejection. The server reaches INT8 through an explicit storage
request instead, which keeps the gate on the only route that has one. Recorded in
`docs/REFACTOR.md` as a trap to resolve one way or the other.

## Validation

**Identity.** The target artifact's SHA-256 is `7b2aec3b...c89f1b`, matching the
frozen lane identity in `docs/CONCURRENCY2-GFX1100-MTP-CN-PROMOTION.md`. The DMS
sidecar at `/models/dms/qwen38-27b-q4km-dms-w8192-local/dms_metadata.json` carries
the same fingerprint, though DMS is not enabled by this change.

**Selection.** Each row above is a real server run with one chat request. The
INT8 row's own report: `storage=int8_per_token_head scale=fp32 slots=1
max_context_tokens=176128 ... bytes_per_token=142944 usable=24.62 GiB
reserve=3.00 GiB`.

**Full depth.** A 171,985-token prompt at the auto-selected 176,128 context
completed with `finish_reason=length` after 824 s of prefill. Whole-card use rose
from 32.5 GiB at rest to a **37.46 GiB peak** as the BF16 prefill oracle
materialized (the INT8 route reads its transient through a BF16 oracle), then
returned to 32.6 GiB. **7.5 GiB of headroom at peak** against a 45.00 GiB card.

**Why the reserve matters here.** The 3 GiB reserve from
`20260912T152128.835655Z` is what makes this safe. The transient is priced at
65,536 B/token for the oracle plus ~10 KiB/token of hidden owners, i.e. 10.75 GiB
at 176,128 tokens, against roughly 5 GiB measured — so the model is still
conservative, and the measured peak lands 7.5 GiB inside the card. The INT8 row
would not have been safe under the old 512 MiB reserve.

`pytest tests/ -k "unit and (gguf or server or kv or capacity or context)"` —
2836 passed, 1 failed:
`test_unit_grammar_masks.py::test_server_schema_does_not_use_json_tool_prefix_for_xml_engine`,
a pre-existing `ModuleNotFoundError: No module named 'llguidance'` environment gap.

## Next

- **The quality basis is a retained artifact, not a re-measurement.** The INT8
  qualification for this exact file is the 2026-08-16 quality run (complete 512/8
  and 4K/16, bounded 129,024/16 at mean/max KL `0.0000104/0.0001354`, top-1 100%,
  no BF16 mirror). This change did not re-run it. Making INT8 the default raises
  the stakes on that evidence, so a fresh same-suite gate at the new 176,128
  context would be the right follow-up. Pure INT8 graph capture still fails
  closed.
- **Concurrency is now one slot by default.** Four concurrent requests used to be
  served in parallel; they now serialize, and each additional slot costs roughly a
  quarter of the context. This is a serving-behavior change that deserves a
  documented concurrency row rather than only a CLI note.
- **DMS remains available and off.** `load_dms_retrofit_config` requires a
  packaged `dms_metadata.json` and refuses to infer DMS from an ordinary model, so
  DMS can only ever be opt-in per artifact. The 24 GB XTX ladder reaches 232,448
  tokens with DMS; that figure carries no serving or quality claim because DMS
  discards history.
- The layer_outer route still fails closed on the 48 GB W7900 (documented in
  `docs/QWEN38-27B-GFX1100-24GB-CAPACITY.md`), which blocks the W7900 no-evict
  reference arm of the DMS quality ladder.
