# Measure gemma4's registry dispatch trace as the input to profile-plan selections

## Summary

Piece (A) of the gate build needs `selections` that honestly describe which
registry variant each scope resolves to today. Gemma 4's MoE route picks
among `_WMMA_*`, `_MMQ32_*` and `_GROUPED_*` variants conditionally per call
(`gemma4_experts.py` `:768`, `:837`, `:969`, `:1255`, `:1338`, `:1401`), so
those selections cannot be read off the source -- they have to be observed.
This entry records the observation: a spy on `hipengine.kernels.registry.resolve`
wrapped around one real `LLM.generate` on the shipped artifact.

Two runs, because the first was too small to be representative.

## Changes

- This entry only; the probe ran from `/tmp` and wrote
  `/tmp/gemma4_dispatch_trace{,_1024}.json`. No script was added to the tree:

wrapper, then run `LLM(model=...UD-Q4_K_XL.gguf)` and generate.

Findings that constrain (A):

- **Migration path confirmed empirically**: `llm.resolved_execution_profile`
  is `None` on this artifact, exactly as `resolve_default_execution_profile`
  predicts with zero plans registered.
- **`llm.resolved_quant` is `gguf_q4_k_m`**, not `gguf_ud_q4_k_xl`. That is the
  quant string `_resolve_quant` supplies to `resolve_runtime_profile`, so it is
  the quant half of (A)'s registration key -- it is *not* the artifact filename
  and not the string §2.1 uses for qwen4exp.
- **The first run proves prompt size gates the routes.** `moe_linear` needs
  `lanes >= 16 * num_experts` (the P3 row's WMMA plan gate), so a 4-token
  prompt never reaches it. Any probe intended to enumerate routes must prefill
  at production width, or it will silently under-report.
- **Four quant families are in play under `linear` and `moe_linear`**:
  `gguf_q4_k` (gate_up), `gguf_q5_1` (down), `gguf_q5_k` (layer-29 experts),
  `gguf_q8_0` (qkv/o and lm_head). `moe_linear` splits by quant -- q4_k and
  q5_k take the mmq32 dual route while q5_1 and q8_0 take grouped WMMA -- so a
  single `selected_variant` per `(layer, scope)` cannot describe gemma4 unless
  the scope axis or `registry_quant` carries that split. `VariantSelection`
  keys on `(layer, scope)` while carrying `registry_quant` as a field, so the
  design question for (A) is how to name those scopes.
- **Attention, norm, rotary, router and lm_head never appear.** They are called
  directly by `runtime/gemma4.py` / `gemma4_layer.py` rather than through
  `resolve()`, so they are not registry-routed and belong to no
  `VariantSelection`. Only `embedding`, `linear` and `moe_linear` are
  registry-resolved for this model -- the selection set is therefore three
  layers, not the 13-layer native key list enumerated earlier, which described
  what is *registered* rather than what is *dispatched through the registry*.
- Call counts hint at the phase split (29 layers x 4 decode steps = 116 for
  q4_k and q5_1) but do not label it; `pack8_gemv_bf16_f32_out` at exactly 2
  calls is almost certainly the lm_head's greedy path.
