# Restore ParoQuant gfx1151 quality oracle

## Summary

Restored an independent exact-checkpoint ParoQuant/Transformers oracle on the ZBook's gfx1151 GPU. The earlier `invalid device function` was not a rotation-math defect: ParoQuant defaulted both JIT extensions to `gfx1100`. After selecting the visible `gfx1151` target, the rotation kernel passed its numerical oracle and the AWQ dequant/GEMV extension also passed. The next failure was Transformers' MIOpen grouped-`conv1d` fallback, which had no suitable depthwise algorithm on this ROCm stack. The quality harness now installs an algebraically equivalent unfold/reduce causal-convolution fallback on gfx1151 and records the compatibility route in its cache manifest.

The clean no-architecture-env capture loaded all 94,596 checkpoint tensors and completed all 90 logits. Versus the BF16 portable teacher it measured mean/p95/max KL `0.029687/0.166413/0.320969` and `91.111%` top-1, independently corroborating the checkpoint's canonical KL `0.027939` / top-1 `92.856%`. hipEngine versus this same-format oracle remains 0/90 top-1 with KL `12.075839`, so the packed hipEngine implementation blocker is confirmed rather than weakened.

## Changes

- Made `capture-transformers-paro` derive the visible ROCm GCN architecture before importing ParoQuant, so its rotation and AWQ JIT extensions compile for gfx1151 without manual `PAROQUANT_HIP_ARCH` / `PYTORCH_ROCM_ARCH` settings.
- Added a gfx1151 quality-oracle fallback for Qwen3.5 depthwise causal convolution because MIOpen rejected the grouped `conv1d` shape. `HIPENGINE_QUANT_QUALITY_MIOPEN_DEPTHWISE=1` preserves the original MIOpen path for diagnosis.
- Added the selected architecture and convolution route to the large-cache manifest and a Torch-optional numerical regression test. No hipEngine production dispatch or external `/home/lhl/paroquant` source changed.
