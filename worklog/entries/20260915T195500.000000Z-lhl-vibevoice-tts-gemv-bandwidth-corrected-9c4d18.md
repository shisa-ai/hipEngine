# Second correction: the dual GEMV thread-count win is ~1.23x, not 3.8x and not zero

## Summary

The entry `20260915T194207.764379Z-lhl-vibevoice-tts-l2-artifact-correction-7b362b`
retracted an earlier "3.8x" claim for running `dense_dual_gemv_out_bf16` at
`threads=64` and replaced it with the conclusion that the thread count is
irrelevant under DRAM streaming (~37 GB/s for every setting). **That retraction
overshot and is itself corrected here.** The 37 GB/s figure came from a flush that
was never drained before timing, so a 256 MB `memset` was still draining and
competing with the kernel for bandwidth.

Measured correctly -- flush written, **synchronized**, then the kernel timed,
median of 12:

| threads | flushed+synced | GB/s | warm (no flush) | GB/s |
| --- | ---: | ---: | ---: | ---: |
| 64 | 324.8 us | **169.5** | 98.4 us | 559.5 |
| 128 | 339.8 us | 162.0 | 123.8 us | 444.7 |
| 256 | 398.5 us | 138.1 | 235.1 us | 234.2 |

So there is a real **~1.23x**, and 169.5 GB/s is a plausible fraction of this GPU's
~200 GB/s. The end-to-end cross-check agrees: applying `threads=64` took the LM
stage from 1.450 s to 1.266 s, which is a ~1.2x effect on this kernel and not a
3.8x one.

The rejection is unaffected and still correct: 5 of 17920 outputs move by one ulp,
`chain_exact` stays true, the correctness suite stays green at 126 passed, and the
ten-seed generated-audio suite still goes from 58/60 to 57/60 with a new
`single-numbers` failure at WER 0.1667.

## What the benchmark did wrong

Two traps, in sequence, both of which produced confident wrong answers:

1. **Reusing one input buffer measures L2.** The first benchmark ran 30 iterations
   against a single 55 MB weight buffer, so the weights stayed cached and
   `threads=64` reported 74.8 us -- an impossible 736 GB/s on this hardware.
   `threads=256` showed no cold/warm difference at all, which was the tell.
2. **An unsynchronized flush steals bandwidth.** Fixing (1) by writing a 256 MB
   flush buffer between calls, but *not* synchronizing it before starting the
   timer, made every thread count measure ~1420-1478 us (~37 GB/s). The flush was
   still draining into the same memory system the kernel needed.

The lesson is that the end-to-end stage delta is the arbiter. 1.450 -> 1.266 s was
in the record the whole time and is consistent with ~1.2x, not with either 3.8x or
with no effect; that cross-check would have caught both errors immediately.

## Validation

- `uv run python /tmp/l2_flush2.py` -> 324.8 / 339.8 / 398.5 us with the flush
  synchronized before timing (169.5 / 162.0 / 138.1 GB/s), against 98.4 / 123.8 /
  235.1 us warm.
- End-to-end cross-check: `uv run python scripts/vibevoice_tts_session_bench.py`
  with the change applied gave `lm_total_seconds` 1.450 -> 1.266.
- `uv run pytest tests/ -k vibevoice` -> 126 passed, 11 skipped with the change
  applied (green, and it does not see the quality defect).

## Next

The ~1.23x is worth having if it can arrive without moving the summation order.
That means a variant that preserves the exact per-thread element sets and the
same tree pairing -- for example staging the row through shared memory so the
global loads vectorise while each thread still sums the same elements in the same
order. A bare thread-count change is not safe however well it measures.

For anything else in this kernel family: flush AND synchronize, then cross-check
against the end-to-end stage delta before believing an isolated number.
