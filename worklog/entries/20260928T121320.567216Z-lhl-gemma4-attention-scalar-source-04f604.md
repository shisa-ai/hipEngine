# strength-reducing the row pointers is inert: LLVM already does it, so the scalar stream comes from somewhere else

## Summary

The scalar-bound diagnosis in `20260928T121300.000000Z-lhl-gemma4-attention-scalar-bound-7f2b1a.md`
named its own fix: hoist the K and V row pointers out of their loops so each key
costs one add instead of a 64-bit multiply-add chain. Both were done, both are
bit-exact, and **both are inert.**

### Pass 1's K row pointer

`const scalar_t* k_row = key + (j * num_kv_heads + kv_head) * head_dim;` inside the
key loop, replaced by a pointer hoisted before the loop and advanced by
`8 * num_kv_heads * head_dim` in the loop's increment.

Static SASS, strict prefill kernel body:

| | total | VALU | scalar ALU |
| --- | ---: | ---: | ---: |
| before | 32630 | 6811 | 16216 |
| after | 32636 | 6813 | 16218 |

Six instructions of difference in 32,630. The bench at 2048 tokens:
46.71 / 77.93 / 131.06 ms and 1823.1 ms for the 30 layers, against 45.95 / 77.67 /
131.70 and 1807.2 ms -- inside the noise, in both directions.

### Pass 3's V row pointer

This one looked much more promising, because pass 3's loop runs **once per key per
output dimension** rather than once per key:

```cpp
for (int64_t d = threadIdx.x; d < head_dim; d += blockDim.x)
  for (int64_t j = first_kept; j < walk_end; ++j) {
    const float weight = logits_s[j];
    if (weight == 0.0f) continue;
    const scalar_t* v_row = value + (j * num_kv_heads + kv_head) * head_dim;  // rebuilt per key
    acc += weight * gemma4_attn_to_float(v_row[d]);
  }
```

Hoisted to a pointer advanced by `value_stride` per key. The wall clock moved 0.6
to 0.7 percent better on all three cases in one session -- 1794.8 ms against
1807.2 ms for the 30 layers -- which looked like a result.

**It is not one.** The dynamic instruction counts are unchanged:

| counter | swa 256d w=1024 | swa 256d w=0 | full 512d w=0 |
| --- | ---: | ---: | ---: |
| `SQ_INSTS_SALU` before | 1,939,590,784 | 4,708,794,368 | 6,891,159,552 |
| `SQ_INSTS_SALU` after | 1,939,852,928 | 4,709,056,512 | 6,891,421,696 |
| delta | +0.01% | +0.01% | +0.00% |
| `SQ_INSTS_VALU` delta | 0.00% | 0.00% | 0.00% |

An address computation the compiler was already eliminating cannot be the thing
that costs 82 percent of the runtime, and a 0.7 percent wall-clock difference with
identical instruction counts is noise. Both changes were reverted.

### What this leaves

**LLVM strength-reduces source-level index arithmetic.** `(j * a + b) * c` with
loop-invariant `a`, `b`, `c` becomes an induction variable without help, and it
does so at `-O3` on this target with no prompting. So the 6.89e9 scalar
instructions in the full-512d launch are not coming from the multiply chains that
are visible in the source, and rewriting more of those is not the lever.

The scalar work must be coming from something the source does not show as
arithmetic. The candidates, none of them yet measured:

- the `logits_s[j]` shared-memory index, which is a 32-bit address computation per
  key visit and happens four times per key across the three passes;
- the `mask_row[j]` byte load and compare in pass 1;
- the `weight == 0.0f` test and its branch in pass 3;
- the 64-bit loop induction and its bound comparisons;
- `__syncthreads` in the fallback path.

Static counts cannot separate these -- the body is 32,630 instructions because
everything is unrolled, and the two edits above moved the static count by six
while moving nothing at all. **The next measurement has to be dynamic and
per-loop**, not another static count or another source-level rewrite.

## Next

- **Get a per-loop dynamic attribution before changing the kernel again.** The
  two inert edits above are the second and third time this session that a
  plausible source-level change moved the instruction count by nothing, and the
  scalar-bound finding deserves a measurement that can name the loop rather than
  a fourth guess. `rocprofv3`'s `--pc-sampling` with the ISA dump maps samples to
  instructions; that is the tool for this, and it should be pointed at the
  full-512d launch first because it has the largest scalar stream at 6.89e9.
- Only after that, the candidates in the order the profile names them. The
  `logits_s` shared-memory round trip is the leading one on the source's own
  account: the tiled variant's header comment counts four LDS accesses per key
  visit in the strict kernel, and the scalar address computation for a shared
  index is not something LLVM can hoist across the loop's `__syncthreads`.
- The scalar-bound finding itself stands and is unaffected: SALU is 77 to 89
  percent of VALU and the scalar stream is 62 to 95 percent of the runtime. What
  this entry corrects is only the guess about which source construct emits it.
