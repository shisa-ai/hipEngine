# R0203 device-side greedy-chain EOS bound removes the pre-accept readback

## Summary

The default dense MTP2 physical route no longer copies candidate and target IDs to the host
before accept for EOS-active requests. A new device kernel,
`hipengine_dflash_greedy_chain_eos_limit_i32`, applies the greedy-chain EOS bound
(`greedy_chain_eos_limit` semantics) to the uploaded accept budget in place, after the target IDs
are chained in and before the accept kernel runs. The host helper `_limit_target_batch_eos` now
runs only inside the opt-in `device_chain_qualification_oracle`, where it also cross-checks the
device bound. Closes R0203.

## Changes

- `hipengine/kernels/hip_gfx1100/speculative/dflash_accept.{hip,py}`: added the EOS-limit kernel
  and its wrapper. Its metadata is three int32 runs: first-candidate row, candidate count, and EOS id
  (-1 for none).
- `hipengine/generation/qwen35_gguf_mtp2.py`: added the `eos_limit_meta` workspace tensor,
  `_enqueue_target_batch_accept(eos_token_ids=...)`, a cycle that passes per-request EOS ids
  (`None` for `ignore_eos`), and an oracle that derives the host bound.
- Tests:
  - `tests/test_gpu_dflash_greedy_chain_eos_limit.py`: named boundaries plus six random seeds
    against the host reference, including padding rows.
  - Seam and accept-staging expectations updated for the new tensor.
  - The staging cleanup test no longer expects the retired ngram owner, which an earlier commit
    had left stale.
- `docs/KERNELS.md`: updated the row; `docs/REFACTOR.md`: removed R0203.

  plus the new GPU test: all pass (rc 0).
- Public `LLM.generate_detailed(speculative_mtp=True)` on `Qwen3.8-27B-UD-Q4_K_M.gguf`, greedy:
  12 chat-templated short-answer prompts with EOS active (reason `eos`, id 248046, confirmed),
  `max_tokens` 64/7/3 (remaining-decode bound below, at and above the EOS position), widths 1/2/4.
  - The default route made 0 `_limit_target_batch_eos` D2H calls at every width. Pre-change HEAD made
    192 at width 4 / max 64 on the same prompts.
  - With the oracle on, every cycle compared GPU and CPU accept using the host-derived EOS bound:
    31/33/10/6/6/3 cycles at the width-2/4 cells, with no mismatch.
  - MTP equals AR on 12/12 in every cell except width 4 / max 64, which is 11/12 (prompt 8). Pre-change HEAD
    shows the same prompt-8 difference, so it is the existing batch-composition difference, not this change.
  - Tracked allocations after close: 0.
- Cancellation is not separately exercised. The cancel check runs before the EOS bound and returns
  before accept, and that ordering is unchanged.
- Not run on gfx1100. The kernel is backend-neutral HIP in the shared tree.
