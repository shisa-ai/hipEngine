# d8 step 2: enqueue the staging and token uploads, drop 7 blocking hipMemcpy per decode step

## Summary

- Screen first (`scratch/d8_async_h2d_screen.py`, artifact
  `benchmarks/results/2026-09-30-gemma4-d8-async-h2d-screen.json`): ROCm's
  `hipMemcpyAsync` from **pageable** memory does not drain the stream — 11.2 us
  host with a deep queue where the sync `hipMemcpy` costs 18022 us for the same
  KB-scale upload, landed bytes verified, pinned no faster (11.0 us). The CUDA
  documentation warning about pageable-async performing a stream sync first does
  not apply to this ROCm, so the fix needs no pinned slots, double-buffering, or
  source-lifetime machinery.
- The six `_stage_upload` copies are **not hoistable**: cos/sin tables depend on
  this block's positions and masks on the block range, so all six rebuild every
  decode step (they are already deduplicated per block — 6/step instead of the
  old 30 — but cannot move across steps).
- Wired: new `enqueue_host_to_device` in `hipengine/core/memory.py`, used by
  `_stage_upload` and the token-ids upload in `hipengine/runtime/gemma4.py` on
  the same default stream (0) every gemma4 wrapper uses. Stream order delivers
  the data to readers; the next step's upload of a reused staging buffer lands
  behind this block's readers.
- The logits D2H at `gemma4.py:1137` (3.36–3.93 ms/step) is the sampler's
  inherent dependency — it is the last thing the device produces and the host
  cannot act without it. Screen verdict: **not wired**; async would move the
  wait, not remove it, on a single sequence.
- Measured (same probe, `scratch/d8_host_attribution_probe.py`): the 7 blocking
  hipMemcpy per step are gone — the post-change caller table names only the
  logits D2H. Probe wall 16.04–16.60 ms pre (5 runs) vs 15.67–15.95 ms post
  (3 runs), non-overlapping; HIP host 7.13–7.70 → 6.67–7.26 ms/step.
