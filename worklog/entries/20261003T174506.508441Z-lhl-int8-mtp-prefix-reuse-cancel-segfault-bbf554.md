# Diagnose INT8 MTP prefix-reuse cancellation segfault as a gfx1151/gfx1100 arch mismatch

## Summary

The live/slow run aborted at 54% with a host segmentation fault in the first
case of `tests/test_live_int8_mtp_prefix_reuse_cancel.py`. The node reproduces
the crash in isolation, so ordering is not involved. The crash is a backend/device
architecture mismatch, established by a hardware-free minimal reproduction, not a
lifecycle defect in prefix reuse or cancellation.

Mechanism: the module pins `BACKEND = "hip_gfx1151"`. The generator's
`target_arch` is `gfx1151`, and the engine wraps its build and launch calls in
`hip_target_arch_environment("gfx1151")` (`hipengine/generation/qwen35_gguf.py`),
so `build_hip` compiles every JIT kernel with `--offload-arch=gfx1151`. A gfx1100
device cannot execute a gfx1151 code object, and HIP 7.2 aborts the host process
with SIGSEGV at the first kernel launch instead of returning a named error. The
first launch in that path is the raw Q4_K token embedding
(`gguf_q4_k_embedding_bf16_out` -> `_launch_embedding` line 209).

Minimal reproduction, no model and no engine: forcing the embedding test's build
to gfx1151 on this gfx1100 host segfaults the same way.

```
env ... HIPENGINE_HIP_ARCH=gfx1151 .venv/bin/python -m pytest -o addopts='' \
  tests/test_live_gguf_q6_k_embedding.py::test_gguf_q4_k_embedding_hip_matches_cpu_reference_synthetic
# Fatal Python error: Segmentation fault, gguf_q6_k_embedding.py:209, exit 134
env ... .venv/bin/python -m pytest -o addopts='' \
```

## Second finding: the runnable gfx1100 backend cannot satisfy the arms

The parent's constraint prefers a runnable backend over a backend gate for
generic lifecycle coverage, so the module was replayed on the host backend
(`BACKEND = "hip_gfx1100"`) before deciding. It no longer crashes, but the reuse
assertion fails: `hit=False`, `matched_tokens=0`, `cache_resident_entries=0`,
`fallback_reason="miss"`.

Instrumenting the resident runner on the gfx1100 host shows why. The seed
prefill is chunked by the scheduler into 256/256/67 tokens, but for a prompt
that fits one prefill round the INT8 direct route declines the resumable
layer-outer executor (`resumable_int8_prefill_declined`), falls back to
`int8_direct_full_prompt_prefill`, and prefills the whole 579-token prompt in one
call. That route refreshes the prefix cache only at the final position (579, not
256-aligned), so no boundary snapshot is ever captured. The gfx1151 route engages
the resumable layer-outer prefill, which captures the aligned boundary
mid-prefill. Confirming the diagnosis, a 256-aligned prompt (768 tokens) does
capture on gfx1100 (`[refresh] tokens=768 -> captured`, `cache_resident_entries=1`).

This is a separate, broader engine gap: the native-greedy full-prompt prefill
route never captures the deepest 256-aligned prompt boundary, so prefix reuse is
unavailable for any prompt that fits one prefill round. It is out of scope here.
Fixing it means either extending the full-prompt route to prefill the aligned
prefix and tail separately (the processed-argmax route already does this) or
making the gfx1100 INT8 executor accept the single-round shape. Both are shared
prefill-routing changes, so this unit stops and reports rather than making them.
