# Promote 1024-row linear/MoE prefill chunks for the H2048-MoE geometry (bit-exact, +1.4% at 4K)

## Summary

The 512-row linear/MoE prefill chunk override for the Qwen3.6-35B-A3B
(H2048-MoE) geometry on gfx1151 is not the fastest value and has been replaced
by 1024. The replacement is **bit-exact** against the value it replaces, so it
carries no arithmetic risk. It is the third and last chunk item from the
2026-10-03 ranked list; the earlier two are the single-owner resolver and the
`target_arch` wiring, both already committed.

The 512 override came from a 2026-08-20 measurement whose protocol passed an
explicit `PrefillConfig`. Under the manual-chunk contract an explicit config
leaves `full_attn_query_chunk_size` at 0, so that sweep left full attention
unchunked in every arm and could not see the interaction. Re-measuring with the
production config shape on one host state gives 1024 the win at every short
shape.

## Changes

- `hipengine/kernels/hip_gfx1151/__init__.py`:
  `GGUF_PREFILL_CHUNK_SIZES_BY_GEOMETRY[(QWEN35_MOE_H2048_E256_GEOMETRY,
  "MOSTLY_Q4_K_M")]` 512/512 -> **1024/1024**, with the per-shape table and the
  bit-exactness result recorded in the comment.
- `scripts/gguf_prefill_chunk_boundary_gate.py` (new): generalizes the ad-hoc
  `pn3_chunk_correctness.py` probe into a reusable gate. Compares last-token
  logits across any set of linear/MoE chunk sizes, **plus same-config repeats**
  so the run-noise floor is measured rather than assumed, and reports KL, top-1
  agreement, max absolute logit difference and a bit-exact flag per pair.

The geometry entry stays even though 1024 equals the documented default, because
it is load-bearing as a shield: the gfx1151 arch profile carries (256, 256),
which measures as the worst value for this geometry (1363.7 tok/s at 4K).

## Validation

### Numerical gate (required: a chunk size is an arithmetic change)

`scripts/gguf_prefill_chunk_boundary_gate.py --chunks 512,1024,4096 --length 4096
--repeats 1` on `Qwen3.6-35B-A3B-UD-Q4_K_M.gguf`, gfx1151, one session per arm:

| pair | KL | max abs logit | top-1 |
| --- | --- | --- | --- |
| 512 vs 512 (repeat) | 0.00000000 | 0.00000000 | identical |
| 1024 vs 1024 (repeat) | 0.00000000 | 0.00000000 | identical |
| 4096 vs 4096 (repeat) | 0.00000000 | 0.00000000 | identical |
| **512 vs 1024** | **0.00000000** | **0.00000000** | identical |
| 512 vs 4096 | 0.00000031 | 1.27896905 | identical |
| 1024 vs 4096 | 0.00000031 | 1.27896905 | identical |

Same-config repeats are bit-identical, so the run-noise floor on this path is
exactly zero rather than the 0.034 quoted by the 2026-08-20 note. 512 vs 1024 is
therefore **bit-exact**, which is the expected result: row chunking partitions
tokens, not reductions, so changing the row-chunk size cannot change any single
token's arithmetic. 4096 is not bit-exact, which means it selects a different
kernel/tile rather than merely regrouping; its KL is 3.1e-07, far below the 0.05
outer floor, but it is recorded and not promoted.

### Performance (one host state, one session per point, 4 reps, 4 s settle)

`SWEEP_SIZES=512,1024,4096 SWEEP_SHAPES=1024,16384,65536`, shipping AR route,
tok/s:

| shape | 512 | 1024 | 4096 |
| --- | --- | --- | --- |
| 1K | 1454.8 | 1486.4 (+2.17%) | 1488.2 (+2.29%) |
| 4K | 1459.3 | 1487.7 (+1.95%) | 1503.9 (+3.06%) |
| 16K | 1358.5 | 1358.5 (0.00%) | 1358.3 (-0.01%) |
| 64K | 969.9 | 969.5 (-0.04%) | 969.2 (-0.07%) |

The lever is confined to short prompts and vanishes at 16K, where all three
values land inside 0.02%. 4096 is faster at 1K/4K but costs more at 64K with
non-overlapping samples, so the long-context penalty is real if tiny and grows
with context; 1024 was chosen because it is bit-exact, keeps that penalty at
noise level, and still takes the short-prompt win.

### Production rows after promotion

`scripts/qwen35_gguf_bench.py --public-ar-profile --measured-runs 3`, confirmed
`chunks=1024/1024 reason=geometry_prefill_chunk_policy` in the tuning record:

| shape | prefill tok/s | vs 512-chunk | decode tok/s |
| --- | --- | --- | --- |
| 512 | 1401.89 | +0.84% | 56.551 |
| 4K | 1479.75 | +1.39% | 56.163 |
| 32K | 1197.59 | -0.17% | 45.067 |
| 64K | 969.08 | -0.02% | 38.241 |

Prefill moves exactly where the sweep predicted; decode is unchanged by the
chunk, as expected. The decode column is measured on the 2026-10-03 host state
and is not comparable to the published rows - see the artifact note below.

### Tests

`207 passed, 1 skipped` for the new precedence suite plus the row-cap and batch
layout suites. No test pinned the old 512 value. `py_compile` clean on all three
touched modules, and a resolver probe confirms 35B at 4352 max sequence length
resolves to 1024/1024 via `geometry_prefill_chunk_policy`.

## Next

- **The published table was not replaced.** Its decode column is measured on the
  2026-08-20 host state and the new prefill column is +2.4% to +4.6% partly from
  the accelerator-performance profile, so swapping rows would mix protocols. The
  artifact and the `benchmarks/README.md` note carry the new rows instead. A
  clean same-session re-measurement of all four shapes is the condition for
  replacing the table.
- Long-context decode is still below the published rows by 2.9% (32K) and 4.8%
  (64K) and remains unexplained; long-context decode also varies ~1% between
  sessions, so this needs a dedicated host-state investigation rather than more
  chunk work.
- The gfx1151 arch chunk profile is geometry-blind. Its (256, 256) is right for
  H5120 dense (398.6 vs 387.7 at 1024) and wrong for H2048-MoE (1363.7, worst of
  five). It should be keyed by geometry, and the PARO 35B-A3B lane - same
  H2048-MoE geometry - is likely running 256 and should be measured on its own
  path before that change.
- 128K prefill and decode remain blocked by the long-sequence lifecycle stall.
