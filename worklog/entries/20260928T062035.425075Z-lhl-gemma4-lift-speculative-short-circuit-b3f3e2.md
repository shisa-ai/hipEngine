# the generator no longer declares a speculative capability miss so the staged route is reachable

## Summary

`Gemma4GGUFGenerator` carried `supports_speculative_mtp = False` as a class
attribute. It has been **removed**, which unblocks the staged speculative route
the engine already supports.

The attribute was accurate about the *legacy* protocol -- this generator does not
implement `generate_speculative_mtp_detailed` -- but it was not a statement about
the artifact, and `engine_loop` reads it *first*:

```python
supports = getattr(self._inner, "supports_speculative_mtp", None)
if supports is not None and not bool(supports):
    return False
if self._supports_staged_speculative_mtp:
    return True
```

So a class-level falsy value made the property return `False` **before** it ever
consulted the runner's staged hooks. With the attribute present, a runner
implementing `speculative_capability` plus `execute_target_frontier` could never
be reached, and any such hooks would have been dead code.

The engine's own comment names the intent: *"Staged hooks describe runner
mechanics, not the loaded artifact's tensors. Respect an explicit model
capability miss before routing."* An explicit miss should mean the artifact
cannot do it, not that one of the two protocols is unimplemented.

## Why removal is safe and not a claim

Absence is read as "no legacy method", not as "capable":

| attribute | legacy path | staged path |
| --- | --- | --- |
| `False` (before) | blocked | **blocked** |
| absent (now) | blocked (`None` is falsy) | decided by the runner |

So the generator still does not claim the legacy protocol, and
`supports_speculative_mtp` still reports `False` today because `Gemma4Runner`
does not yet expose the staged hooks. Nothing claims a capability it lacks.

This is also the "Ship it on" rule applied correctly: the old flag was a
capability-miss declaration with no named cause and no clearing command, and the
drafter it was suppressing demonstrably works.

## What is still required

Removing the short-circuit does not by itself make MTP available. The remaining
work is the adapter and the runner hooks:

1. A Gemma4 speculative adapter wrapping the existing `Gemma4MtpDrafter`
   (`hipengine/runtime/gemma4_assistant.py`, 752 lines, already exercised by
   `tests/test_gpu_gemma4_assistant_forward.py` and four unit tests).
2. `speculative_capability()` and `execute_target_frontier()` on `Gemma4Runner`,
   resolving that adapter and returning `None`/`False` conservatively when it is
   absent -- the shape `qwen35_gguf.py` uses.

The bit-exactness requirement for the verify is answered: force both MMQ routes
to one setting via `HIPENGINE_GEMMA4_MOE_GATE_UP_MMQ` and
`HIPENGINE_GEMMA4_MOE_DOWN_MMQ` (entry `20260928T061522`).

## Changes

- `hipengine/generation/gemma4_gguf.py`: the `supports_speculative_mtp = False`
  class attribute replaced by a comment recording why the attribute is absent and
  what would go wrong if it returned.
- `tests/test_unit_gemma4_speculative_wiring.py` (new): pins the routing rather
  than the drafter.

## Validation

- `uv run pytest tests/test_unit_gemma4_speculative_wiring.py`: **3 passed**.
  - the class does not declare `supports_speculative_mtp`;
  - with no staged runner, `supports_speculative_mtp` is `False` (absence is not
    read as capable);
  - with a runner exposing `speculative_capability` and
    `execute_target_frontier`, it is `True` -- the case the removed attribute was
    blocking, asserted through the engine's own routing rather than a copy of it.
- `uv run pytest --suite unit -k "gemma4 or engine_loop or speculative"`:
  the only failure is `test_unit_gemma4_runner.py::test_incremental_decode_matches_a_dense_prefill`,
  which is the pre-existing route-selection blocker from `20260928T061522` and
  not a regression -- this change only removes a class attribute that affects
  capability routing, and that test is about numerics.
