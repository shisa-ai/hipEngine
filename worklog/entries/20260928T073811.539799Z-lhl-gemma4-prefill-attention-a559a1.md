# tiling fixes occupancy at long context but occupancy is not what limits the measured 2048 token point

## Summary

`20260928T073739` measured the prefill kernel at 1.6% of compute peak and attributed it to the
three-pass LDS latency chain. The obvious additional hypothesis is occupancy: the resident
logit array is large, so few blocks fit per CU. The arithmetic says that is true **at long
context but not at the length actually measured**, and separating the two matters because it
decides what the tiled kernel is expected to fix.

## The LDS footprint

`shared_bytes = (head_dim + keys + threads) * 4`, with `head_dim = 256` and `threads = 256`,
against 64 KiB of LDS per CU on this part:

| keys | shared bytes | blocks per CU |
|---|---|---|
| 1024 | 6.0 KiB | 10 |
| **2048** | **10.0 KiB** | **6** |
| 8192 | 34.0 KiB | **1** |
| 15872 | 64.0 KiB | **1** |

The grid is `tokens x num_heads` = 2048 x 16 = **32768 blocks** at 256 threads, so there is no
shortage of blocks -- the limit is how many fit per CU.

## The separation that matters

**At 2048 tokens -- the length the 414-528 GFLOP/s figures were measured at -- the footprint
is 10.0 KiB and six blocks fit per CU, about 1536 resident threads.** That is not obviously
starved. **So the 1.6%-of-compute-peak figure at that length is not explained by occupancy**,
and the three-pass LDS dependency remains the standing explanation for it.

**Above roughly 8192 keys the footprint reaches 34 KiB and occupancy collapses to one block
per CU.** That is a real and separate defect, and it is the one that bites the long-context
case -- the same regime the 15872 ceiling caps.

## What tiling fixes, stated separately

| T | shared bytes | blocks per CU |
|---|---|---|
| 512 | 4.0 KiB | 16 |
| 1024 | 6.0 KiB | 10 |
| 2048 | 10.0 KiB | 6 |
| 4096 | 18.0 KiB | 3 |

Tiling makes the footprint **independent of context**, so:

1. **Long context**: occupancy stops collapsing. At T=2048 the footprint is 10 KiB at *any*
   context length, so 8192 keys keeps six blocks per CU instead of one. **This is the effect
   the 15872 ceiling is a symptom of**, and it should be large.
2. **Short context**: fewer LDS round trips per key, because the weight stays in a register
   rather than being written back and re-read. **This is the effect that should show up at the
   2048-token measurement point.**

**Two different payoffs at two different lengths, and the tiled kernel should be measured at
both.** Measuring only at 2048 would miss the occupancy effect entirely; measuring only at
long context would miss the register effect.
