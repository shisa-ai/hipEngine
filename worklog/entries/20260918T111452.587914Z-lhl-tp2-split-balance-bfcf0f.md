# TP2 split balance: the even shard split makes the slower card the pacer

## Summary

The TP2 route splits every sharded tensor evenly, but the two cards are not
equal: on this host the RX 7900 XTX runs the same streaming kernels 15-21%
faster than the W7900. The even split therefore gives the *slower* card the
pacer role and leaves the faster card idle inside the exchange spin. The
inventory now quantifies that idle at **4.182 ms/step** on rank 1, and a
manifest-derived balance model - which reproduces the measured pacer work time
exactly - puts an uneven MLP split at **1.752 ms/step**, about 7.3% of the
24.025 ms/token wall. This entry records the measurement and the plan; no
split has been changed.

## Changes

- `scripts/tp2_split_balance_plan.py` (new): reads the shard manifest and the
  decode kernel inventory, splits each rank's per-step time into streaming,
  fixed and spin components, solves for the byte fraction that equalizes the
  two ranks, and emits block-aligned per-tensor counts. The two decision
  functions (`balance_fractions`, `derive_rank_costs`) are pure and tested;
  the script is a dry run and never touches weights or the manifest.
- `tests/test_unit_scripts_tp2_split_balance_plan.py` (new): 21 tests over
  tensor eligibility (a head-structured tensor must never be selected), block
  arithmetic (totals preserved, largest remainder, minimum one block per rank),
  the balance solve, the inventory accounting (spin excluded, narrow pair
  routes counted as streaming), and the committed artifact's consistency with
  the inventory it cites.
- `benchmarks/results/2026-09-18-w7900-tp2-split-balance-plan.json` (new) plus
  the `benchmarks/README.md` evidence link and a `benchmarks/CHANGELOG.md`
  entry marked as a plan with no performance claim.
- `docs/QWEN38-27B-GFX1100-TP2.md`: new "the split is even; the two cards are
  not" subsection with the per-kernel table, the validated model, the plan, and
  the two constraints that bound its scope.

## Validation

- `python3 -m pytest tests/test_unit_scripts_tp2_split_balance_plan.py` - 21
  passed.
- **The model reproduces the measurement it is derived from.** Predicted
  even-split pacer work is 19.689 ms/step; the measured value is the rank-0
  kernel time 19.949 ms/step minus its 0.260 ms/step spin = 19.689. Fixed work
  comes out nearly equal across ranks (2.347 vs 2.092 ms/step), which is what
  replicated kernels should show, and is an independent check on the split.
- Derived streaming rates (432.0 vs 526.6 GiB/s, ratio 0.821) agree with the
  isolated projection audit's ratio (577 vs 730 GB/s on `ffn_gate`/`ffn_up`)
  and with the resident TP1 controls (31.753 vs 26.329 ms/token).
- Plan output: fractions 0.417 / 0.583 of the 9.65 GiB MLP pool; predicted
  17.937 ms/step against 19.689 even; rank 1 gains 0.851 GiB resident weights
  (7.009 to 7.860 GiB) and rank 0 loses the same (8.646 to 7.795 GiB).

## Next

- Implement the uneven split. Surface: `partition_groups` /
  `_row_split_bounds` / `build_shard_manifest` (a per-rank block-count vector,
  with the existing refusal for head-structured tensors preserved),
  `shard_weights.py` (`per_rank_ffn` becomes per-rank, and the fused
  pair+SiLU variant is resolved per rank because the shapes differ),
  `tp2_generate.py` (per-rank shard shapes), and the tests that assert equal
  splits today.
- `ffn_gate`/`ffn_up` move independent output rows, so that part is bit-exact.
  `ffn_down` moves a summation grouping, so the change needs the full
  production numerical gate (KL / top-1 on the multi-prompt suite) rather than
  an exactness argument.
- Re-measure the capacity ladder afterwards: rank 1 carries 0.851 GiB more
  weights, which trades against maximum context.
- The head is a second, independent instance of the same imbalance: its
  vocabulary rows are split evenly in `head_shard.py` while rank 1 is the
  faster card. It is deliberately left out of this plan's movable pool so the
  first change is contained to the MLP path.
