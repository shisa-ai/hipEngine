# VibeVoice-ASR Q4_K_M end-to-end RTF 0.354, with stage attribution

## Summary

First end-to-end real-time factor measurement for the VibeVoice-ASR Q4_K_M lane,
plus a stage breakdown that says where the time goes. RTF is **0.354** pooled
(131.5 s of inference over 371.4 s of audio, 40 LibriSpeech test-clean
utterances), and **0.360** on an independent 20-clip run instrumented per stage.

Decode is the whole story: **81.3%** of end-to-end time, against 9.9% batched
prefill, 8.8% front-end and 0.0% prompt assembly. Decode is 46.64 ms/token
(21.4 tok/s). Excluding decode the pipeline is about 19% of end-to-end time, so
remaining RTF work is decode work.

## Changes

- `scripts/vibevoice_q4_e2e_stage_breakdown.py` (new): replays the production Q4
  path on matched requests, timing front-end, prompt assembly, batched prefill
  and decode separately, and reporting pooled and per-clip RTF. Each stage is
  bracketed by device synchronizes so a stage is execution wall time rather than
  enqueue time.
- `benchmarks/results/2026-09-14-gfx1151-vibevoice-q4-e2e-rtf.json` (new
  artifact).
- `benchmarks/README.md` and the exported root `README.md`: the VibeVoice row now
  carries RTF 0.35 and decode 21.4 tok/s.
- `benchmarks/CHANGELOG.md`: dated entry for the measurement.

## Validation

- `python3 scripts/vibevoice_q4_e2e_stage_breakdown.py --num-clips 20`:
  pooled RTF 0.3602, per-clip median RTF 0.2393, decode 81.3% / prefill 9.9% /
  front-end 8.8% / assembly 0.0%, decode 46.64 ms/token.
- `python3 scripts/vibevoice_asr_wer_q4.py --num-clips 40 --cache-dir
  /tmp/librispeech-clean-spread --gguf /tmp/vibevoice-asr-q4km.gguf`:
  131.48 s over 371.4 s audio, mean 3.287 s/clip, WER 1.37%.
- The two runs agree (0.354 with no stage timers, 0.360 with per-stage
  synchronizes), which is the cross-check that the instrumented run did not
  perturb the pipeline.
- `python3 scripts/sync_benchmark_readme.py --check`: synchronized.

## Notes

- RTF is token-bound rather than duration-bound. The 20-clip stage run pools to
  0.360 but its per-clip median is 0.239, because most clips reach EOS in about
  30 tokens while one 22.6 s clip hit the 256-token cap at RTF 0.625. Both are
  reported rather than quoting only the flattering one.
- Decode is a bandwidth-bound GEMV: 5.012 GB of Q4_K_M weights streamed per
  token against 14.15 GB for dense bf16, which is where the 1.55x decode ratio
  comes from.
- The on-disk request cache under `/tmp/librispeech-requests` is **not** usable:
  all 40 cached requests fail the `_read_request` array-hash check, including a
  single-scalar array, so the hashes and the arrays were not written from the
  same values. The stage-breakdown script therefore regenerates each request
  through the bench's prepare lane, the same matched-request protocol the WER
  gate uses. Worth fixing or deleting the cache before someone trusts it.
- For context only: the same host recorded 3.477 s/clip (RTF 0.399) on the
  200-clip run before the decode-scratch and prefill-arena changes landed. The
  clip sets and durations differ, so this is not a same-suite delta and is not
  claimed as one.
- The public README prose budget is at 2794/2800 characters, so fitting RTF in
  required dropping the bf16 WER figure (2.10%) from that paragraph. It remains
  in the artifact, the changelog and this entry. A future addition there will
  need to remove something else first.
