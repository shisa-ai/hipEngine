# Gemma 4 decode attention kernel (G3): bit-exact barrier batching

## Summary

Landed the G3 decode-attention candidate: `gemma4_attention.hip` now exports a
decode kernel selected by the public wrappers at `tokens == 1`
(`attention_symbol`), bit-exact with the original block kernel. The campaign
metric improved from the G0 baseline 16.09 to 20.48 decode tok/s at
1024p/128o (+27.4%) with prefill unchanged and public-path token-id parity
still exact.

The design took three measured iterations; the earlier two are on record
because both plausible-sounding hypotheses were wrong:

- **v2, warp-32 (refuted).** Distribute keys across a single 32-lane wave and
  replicate every reduction in registers + `__shfl`. No per-key barriers at
  all, but 1.256 ms/launch vs the block kernel's 0.459 at the same shape
  (keys=544, heads=32, kv=8, head_dim=256): one wave has no latency hiding,
  so serial per-lane chain work costs more than the barriers it removes.
- **v3, block shape with a cheaper tree (small win).** Same 256-lane shape as
  the parent, but cross-wave strides >= 32 through shared partials, strides < 32
  through `__shfl_down`, and pass 2 stores `expf(logit - row_max)` over its
  logit so pass 3 reads weights instead of recomputing `expf` per (element,
  key). 0.428 ms/launch; ablation showed the per-key tree (5 barriers x 544
  keys, ~200 cycles per barrier) was 50% of kernel time and pass 3 was free.
- **v4, barrier batching across keys (landed).** Same tree, but a tile of
  kTile keys shares one write/3-stride/broadcast barrier sequence (5 barriers
  per kTile keys), each key in its own `partial[kb]` row. Tile sweep at the
  microbenchmark shape: 1 -> 0.406, 2 -> 0.320, 4 -> 0.281, 8 -> 0.263,
  16 -> 0.559 ms/launch (16 over-serializes the dot phase). Launcher caps at
  tile 8 and shrinks it when the LDS budget is tight, so `kTile = 1` always
  fits whatever the caller's shared-bytes check admitted.

gfx1100 gotcha found along the way: a `__shfl_down` whose *source* lane sits
in an inactive branch returns 0, silently dropping terms — the shuffle must
execute unconditionally with only the accumulate guarded. The first parity
failures were exactly this (denominator missing every lane but lane 0's).

Exactness argument, all covered by the parity suite: products are elementwise;
each key's tree uses the parent's (t, t + stride) pairs in descending order
(shared rounds for >= 32, shuffles for < 32); the pass-2 partition is
`j == lane mod blockDim` with the same serial order; the stored weight is
`expf` of the same arguments on the same device, so pass 3 reads the same bits
the parent recomputes; `running_max` walks the same ascending-j `fmaxf` chain.
