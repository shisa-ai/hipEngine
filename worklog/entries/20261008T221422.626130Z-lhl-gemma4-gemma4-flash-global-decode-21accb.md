# Promote the flash decode route for the long global step on the fixed tree

## Summary

`gemma4_flash` is the production decode variant for the one-token global step
again, on a tree without the Q5_1 staged prefill overrun. The earlier rejection
was measured on the defective tree, so its evidence and the timing rows published
with it are withdrawn and replaced here.

**Gate** -- 527 teacher-forced rows, keys 15,857-16,383, `kl(baseline || candidate)`
against the frozen staged chain captured on this same commit, with the candidate
arm unforced (the new default) and the route observed on all 15,790 decode
launches:

| check | limit | measured |
| --- | --- | --- |
| mean KL | <= 1e-3 | **2.90e-6** |
| p95 KL | <= 5e-3 | **1.50e-6** |
| p99 KL | <= 2e-2 | **2.29e-5** |
| max KL | <= 5e-2 | **5.38e-4** |
| top-1 | >= 99% | **100%**, 0 flips |

Every numeric bar passes, the mean by 345x and the max by 93x. The defective
tree's reading for the same route was mean 1.11e-2 with 7 flips.

**Decode step time** (median of 5, fixed teacher token and KV prefix, rewind each
replay, so prefill is outside every row; all three arms report their own resolved
route):

| keys | strict plain | staged | flash | flash vs staged |
| --- | --- | --- | --- | --- |
| 32,769 | 60.25 ms | 25.21 ms | 16.11 ms | **1.57x** |
| 65,537 | 108.73 ms | 38.89 ms | 21.15 ms | **1.84x** |
| 131,073 | 209.38 ms | 69.01 ms | 35.02 ms | **1.97x** |

The argmax is identical in all three arms at every length (24,744 / 236,751 /
973), so the product-visible output is unchanged on these rows, and staged and
plain carry bit-identical logits as documented.

The earlier published rows (1.51x/1.76x/2.44x) came from the defective tree and
are withdrawn: the overrun corrupted prefill values, which changed the decode
work itself, so neither those absolute times nor their ratios were a valid
measurement of this route.

## Next

- **`scripts/gemma4_public_route_probe.py` cannot observe the decode scope.** It
  wraps the layer's native launcher functions, so a registered variant (staged,
  flash) never appears in its counts; at 16,384 prompt tokens it reports only
  prefill launches and no singleton ones at all. For a decode-scope change the
  route has to be read from the gate's launch counts or the layer's own route
  reporter. Wrapping the registry-invoked variants would make this probe answer
  the question it looks like it answers.
- **One gate check still reads false, and it is not a numeric bar.** The
  evaluator's `require_wmma_full_split` appends `no_wmma_full_launches_observed`
  whenever the run planned no full-layer walk, which is the case for any
  unforced decode-scope arm, and it then sets `passed` from that list. So this
  artifact and every other decode-scope gate carry `passed: false` regardless of
  the numbers. Clearing it means forcing `--wmma-full-slices`, which changes the
  arithmetic of a scope this unit does not touch, so it was not forced here. If
  the evaluator should report scope coverage separately from the numeric verdict,
  that is a small change to `scripts/gemma4_teacher_forced_gate.py` and a
  decision about the verdict's meaning, not a measurement.
- The short-context flash route above its entry band (task 53) is still unmeasured
  at keys 2,048-15,856.
- The 8-column Q5_1 prefill tile is a legitimate candidate once the launcher sizes
  `out_tile`, `staged_bytes` and the grid for it.
