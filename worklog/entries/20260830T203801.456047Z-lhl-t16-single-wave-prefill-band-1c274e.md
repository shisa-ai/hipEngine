# single-wave owns the 5120x17408 prefill band rows 2-128

## Summary

The prefill-owner trace named a 140 ms kernel but not why it was slow. This entry closes that: the shipping
dense-prefill leaf is launched on a 256-row tile, so a 35-row prompt pays almost the full 256-row cost, and a
registered, production-qualified sibling already fixes it. `gguf_q4_k_t16_wmma_prefill_bf16_bf16_out` is
**bit-identical** to `gguf_q4_k_t16_wmma_prefill_shared_b_bf16_bf16_out` at every row from 2 to 128 and
**1.43x-1.04x faster** there, so the change is an ownership change, not an arithmetic change. The same-build
A/B on a real 35-row AR first-token request moved **253.0 ms to 233.4 ms (-7.75%)**.

This is the first measured prefill win since the campaign stopped treating dispatch declarations as the
lever, and it came from the method the previous entry demanded: profile the owner, then microbenchmark that
kernel's cost curve, not the source tree.

## Changes

- `hipengine/kernels/hip_gfx1100/__init__.py`: new capability constant
  `GGUF_Q4_T16_PHYSICAL_SINGLE_WAVE_MAX_ROWS = 128`, exported in `__all__`, with the measured band and the
  crossover recorded at the declaration site.
- `hipengine/kernels/hip_gfx1100/quant/gguf_k_t16_selected_prefill.py`:
  `gguf_q4_k_t16_physical_c1_rowtile_gfx1100_bf16_bf16_out` now selects the single-wave leaf for shapes in
  `GGUF_Q4_T16_PHYSICAL_SINGLE_WAVE_SHAPES` at rows 2..128 instead of falling through to shared-B, which was
  the unconditional fallback for every row other than 6. Shared-B stays registered as the strict sibling and
  the fallback; no registry key, ABI, or kernel body changed.
- Same module: `_single_wave_max_rows()` plus `HIPENGINE_GGUF_Q4_T16_SINGLE_WAVE_MAX_ROWS` as a resolved-once
  bisection switch (`0` restores the old route on the same build). Removal condition is stated in the
  docstring: delete it once shared-B has survived one release cycle as the strict sibling. No
  `if backend ==` or `if quant ==` branch was added anywhere; the selection lives in the gfx1100 backend
  module behind a declared capability constant.
- `scripts/gguf_t16_prefill_row_sweep.py` (new): row-sweep harness for the T16 dense leaves on
  `(rows, 5120, 17408)`. Consumes only `repack_gguf_q4_k_tile16` output over a valid Q4_K block image, times
  every arm twice, reports best-of-two medians, per-row cost, effective GB/s, finiteness, and the BF16 ULP
  distance of each candidate against the shipping owner, and captures host/git identity. Ratios are
  always owner/candidate so `> 1.0` means faster.
- `tests/test_gguf_q4_k_t16_dense.py`: the selection contract now pins the new band (rows 35 and 128 select
  single-wave at the single-wave shape, row 129 and the transposed 17408x5120 shape still select shared-B,
  row-6 routes are untouched) and covers the bisection switch returning every non-row-6 call to shared-B.

  The owner's cost is flat to row 256 (0.630 ms at 6 rows to 1.081 ms at 256 rows, i.e. 1.7x for 43x the
  work) and jumps at row 257, which is the `Q4_DENSE_TILE_ROWS = 4*4*16 = 256` tile boundary. That confirms
  the mechanism the backend comment already described for ragged verify cycles ("ride the shared-B 256-row
  padded tile at a measured ~5.1x cycle cost"). `rows6_rowtile` measured neutral throughout (1.00x-1.06x),
  and `smallm` rejects rows > 16 by contract.
- Same-build, same-host, same-prompt A/B through the public `LLM` API, production profile, one 35-row prompt,
  `max_tokens=1`, third iteration steady state: **253.49 / 252.56 ms with the switch at 0** versus
  **233.47 / 233.29 ms with the new default**, i.e. **-7.75% and ~19.6 ms per first-token request**, matching
  the predicted 140.3 ms x (1 - 1/1.22) = ~25 ms of owner-kernel wall.
- No numerics gate was required beyond bit-exactness for the changed leaf, because the promoted path is
  bit-identical to the strict sibling at every row in the declared band. The production profile's KL/top-1
  task gates stay with the packet below, not with this claim.
