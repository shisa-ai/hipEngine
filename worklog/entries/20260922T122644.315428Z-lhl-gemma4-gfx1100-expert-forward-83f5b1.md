# Gemma 4 gfx1100 expert forward assembled and matched to the reference

## Summary

The routed-expert FFN now runs end to end on gfx1100 and matches the reference
`gemma4_experts_forward` to **0.8% of scale** (max abs diff 0.042 against a
reference magnitude of 5.10), which is the expected bf16 rounding through three
chained projections.

`hipengine/kernels/hip_gfx1100/gemma4/gemma4_experts.py` composes kernels that
are each tested on their own:

| Stage | Kernel |
| --- | --- |
| lane counts per expert | `qwen35_moe_group_count` |
| compact prefix + active experts | `qwen35_moe_group_prefix_active` |
| compact lanes into expert order | `qwen35_moe_group_compact_active` |
| gather hidden rows into compact order | `qwen35_moe_gather_packed_hidden_lowp` |
| per-expert fused gate_up | `dense_gemv_out_bf16` |
| GeGLU | `gemma4_gelu_tanh_mul_bf16` |
| per-expert down | `dense_gemv_out_bf16` |
| routing-weighted accumulate | `gemma4_moe_weighted_accumulate_bf16` |

Compaction makes each expert's rows contiguous, so the projections are **one
launch per non-empty expert** with a pointer offset into the stacked weights —
not one launch per token-lane. With 128 experts and 8 selected per token, that is
the difference between 8 launches and 1024 per layer.

`Gemma4ExpertScratch` sizes the twelve device buffers once from
`(tokens, top_k, hidden_size, intermediate, num_experts)` and reuses them across
layers and decode steps.

**One host synchronisation is unavoidable here and is documented at the
function.** The per-expert row counts live in `expert_start` on the device and
the launch count depends on them, so the whole prefix is read back in one copy
(`num_experts + 1` int64 values) rather than per expert. A device-resident
dispatch would remove the sync; that is a separate optimisation, and this path is
correctness-first.

## The ABI mismatch this unit had to fix

The first run **segfaulted** in the group-scatter chain. The cause was buffer
widths, not logic: I had sized `active_experts`, `active_count`, `sorted_lanes`,
and `sorted_experts` as int32 and passed `selected_experts` as int32, but the
group-scatter ABI is **int64** for all of those (only `counts` is int32 and
`sorted_weights` is float). A kernel reading int64 from an int32 buffer reads
twice as far as the buffer extends, so the gather kernel walked off the end of
`sorted_lanes`.

`gemma4_moe_lane_to_row_i32` was changed to take `const int64_t* sorted_lanes`
for the same reason; it still writes int32 row indices, which is what the
accumulate kernel consumes.

This is worth recording because the widths are inconsistent *within* one ABI —
`counts` is int32 while `active_count` is int64 — so a reader cannot infer one
from the other. The widths are now stated explicitly in `_size_of` with a comment
naming the whole set, and the module docstring marks `selected_experts` as int64
"the group-scatter ABI, not a choice".

## Validation

- `pytest tests/test_unit_gemma4_gpu_kernels.py` — **38 passed** (34 prior + 4 new):
  - `test_experts_forward_matches_the_reference` — the whole chain against
    `gemma4_experts_forward`; 6 tokens, top_k 4, 8 experts, distinct experts per
    lane.
  - `test_experts_forward_weights_each_lane_by_its_route` — zeroing one lane's
    route weight must remove exactly that lane's expert and leave the other
    tokens bit-identical. Catches a plain-sum accumulate and a compact-order /
    lane mix-up.
  - `test_experts_forward_handles_an_unused_expert` — 16 experts where only 2 are
    ever selected; an expert with no lanes must be skipped, not launched with
    `rows=0`.
  - `test_expert_scratch_rejects_nonpositive_shapes`.
- Measured agreement, printed directly rather than only asserted:
  max abs diff **0.042**, mean **0.0071**, reference scale **5.10** → 0.8%
  relative. A structural error (wrong expert, dropped lane, gate/up swapped,
  unweighted accumulate) is orders of magnitude larger than this.
- `ruff check` on the changed files: clean.
- `python3 audit/audit.py check`: exit 0.
