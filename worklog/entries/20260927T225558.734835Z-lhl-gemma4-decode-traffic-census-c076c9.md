# the decode step moves 3.22 GB in 825 launches at 29 percent of peak bandwidth

## Summary

A per-decode-step census of every launch funnel, plus a host-floor measurement
with the launches removed, replaces the route ablation's shares with a budget
that adds up:

| component | ms/token | note |
| --- | --- | --- |
| dense Q8_0 GEMV | 13.78 | 218.7 launches, 1866.7 MB |
| expert GEMV (Q4_K gate/up + Q5_1 down) | 14.04 | 62 launches, 1348.1 MB |
| host floor (launches removed) | 8.12 | measured, and hidden under the GPU |
| norm + rotary | 2.24 | 416 launches |
| MoE elementwise | 1.09 | |
| router | 0.93 | |
| attention | 0.14 | |
| measurement slack | 3.54 | |
| **total** | **43.88** | 22.79 tok/s |

One decode step issues **825.6 kernel launches** and moves **3219.6 MB** of
weight traffic. At the 256 GB/s this host reaches on a pack8 Q8_0 GEMV in
isolation, that traffic is 12.6 ms, so the step runs at **29% of achievable
bandwidth**.

The same-host llama.cpp reference is 41.92 tok/s, which is 135 GB/s on the same
traffic -- **53% of peak, not peak**. So the 1.84x that remains is a gap in
achieved bandwidth between two implementations that are both short of peak, and
the lever is not "reach peak".

## Changes

- `scripts/gemma4_decode_traffic_census.py` (new): hooks
  `launch_gguf_linear`, the four `gemma4_project_experts_*` entry points and the
  layer's elementwise/norm/attention/router functions, and prints launches, weight
  plus activation bytes and output bytes per family per decode step. GGUF block
  bytes per element are keyed by quant.
- `scripts/gemma4_decode_host_floor.py` (new): stubs every launch funnel and
  times the decode loop with no device work issued, at two output lengths so the
  per-token figure is a pure steady-state measurement.
- `scripts/gemma4_decode_route_ablation.py`: the `no_all_gemv` wildcard arm
  hooked only `gguf_k_gemv._launch`, so it silently excluded the Q4_K selected
  family, which lives in `gguf_q4_k_gemv` and is this artifact's expert gate/up
  and (through Q5_1) its down projection. That is why the arm measured 30.8% when
  `no_experts` alone measured 32.0% -- skipping a superset cannot save less than
  skipping a subset. It now hooks `gguf_q4_k_gemv._launch_selected` as well. A
  `no_norm_rope` arm was added for the normalization and rotary chain.

## Validation

```
env -u HIP_VISIBLE_DEVICES ROCR_VISIBLE_DEVICES=0 PYTHONPATH=. \
  python3 scripts/gemma4_decode_traffic_census.py --prompt 8 --output 16
```

Per step, over 15 decode forwards: dense `gguf_q8_0` 218.67 launches and
1866.7 MB; `expert-selected gguf_q4_k` 30.93 and 793.4 MB; `expert-selected
gguf_q5_1` 30.93 and 528.9 MB; `expert-selected gguf_q8_0` 1.07 and 25.8 MB;
total 3219.6 MB and 825.6 launches. Dense shapes resolve to seven projections per
layer: `2816->2112` twice, `2112->2816`, `2816->2048`, `2816->4096`,
`4096->2816`, plus a `2816->8192`/`8192->2816` pair and a `2816->1024` on five
of the thirty layers.

```
env -u HIP_VISIBLE_DEVICES ROCR_VISIBLE_DEVICES=0 PYTHONPATH=. \
  python3 scripts/gemma4_decode_host_floor.py
# host floor, no launches issued: 8.12 ms/token (123.1 tok/s)
# short_s=[0.0649, 0.066, 0.065]  long_s=[0.3201, 0.326, 0.3286]
```

The host floor is 18.5% of the step, and it is hidden: the host spends 9.8 us per
launch against 53 us of device time per launch, so the queue stays full and the
GPU is the bottleneck. Removing the host cost is worth at most the 3.5 ms of
measurement slack, not the 8.12 ms.

## Next

Two facts bound the decode work. First, the lm_head -- one Q8_0 GEMV of 784 MB
issued once per token -- runs at **195 GB/s**, while the 218.7 per-layer dense
GEMVs run at **135 GB/s** on the same kernel family. The difference between them
is launch count, and the per-launch cost is about 30 us of device-side latency
that a 6.3 MB GEMV cannot amortize. Second, 416 of the 825 launches are
normalization and rotary kernels costing 2.24 ms in total, so they are cheap per
launch and not the problem.

That points at fewer, larger dense launches rather than a faster kernel: the
dense MLP gate and up (`2816->2112` twice, 379 MB/step) share one input and are
two launches, and the attention projections are three more. MTP is the larger
lever and is now the next unit: the head artifact is at
`/models/gguf/gemma-4-26B-A4B-it-GGUF/mtp-gemma-4-26B-A4B-it-Q8_0.gguf`, the
loader contract landed in b42a56c20, and the forward, the draft/verify loop and
the registry adapter do not exist yet.
