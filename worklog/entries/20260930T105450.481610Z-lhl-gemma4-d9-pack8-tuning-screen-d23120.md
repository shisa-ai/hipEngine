# D9 pack8 tuning screen: registered-variant timings and association-parity rates

## Summary

D9's open clause ("tune the pack8 GEMV for the 2112 / 4096 / 8192-row
shapes") got its two instruments and a decisive answer.

`scratch/d10_q8_dense_gemv_screen.py` times every registered rows==1
`gguf_q8_0` bf16 candidate at the five production decode shapes (raw GGUF
bytes for the pack8 family, byte-neutral Q8T16 repack for the t16 family,
touch-check on every launch, f32 dequant oracle rounded bf16-RNE, legacy
parent-parity column; 3 runs, medians). One five-launch set:

- legacy `pack8_gemv` (production): 156.0 us
- `pack8_gemv_decode` (P9.B3, rejected at the gate): 85.4 us (-45%)
- `t16_gemv_decode`: 94.9 us (-39%)
- gate+up pair: two legacy singles 44.2 us -> `rowvec8_dual_split t=64` 12.1 us

Per-shape winners (median us): gate/up 2112 = 14.1 (pack8_decode), q 4096 =
18.6 (t16), fused qkv 8192 = 21.2 (t16), o 2816 = 16.0 (pack8_decode), down
2816 = 12.8 (pack8_decode).

The timing screen's legacy-comparison column read 0 bit diffs for every
candidate, which is underpowered: the known divergence rate of the rejected
rewrite is ~1e-4, so a handful of one-row samples expect fewer than one diff.
`scratch/d10_association_parity_screen.py` is the parity instrument: 200
random trials per shape, element-level bf16 bit rate vs legacy, with the
rejected `pack8_gemv_decode` as a mandatory nonzero control.

- Control: 8.8e-5 .. 9.7e-5 on all five shapes -- reproduces the pinned
  `tests/test_gpu_gguf_q8_0_pack8_gemv_decode_parity.py` rate, instrument
  validated.
- `t16_gemv_decode` and `t16_gemv_decode_rowtile4`: 0 differing bits out of
  422400 / 819200 / 1638400 / 563200 / 563200 (95% upper bounds < 7.1e-6).

So the takeable D9 win is the t16 route: ~39% faster per five-launch set with
no observed association drift, while `pack8_gemv_decode` stays rejected (its
8-consecutive-k walk reassociates the f32 sum; the 2026-09-24 production-gate
rejection, kl_max 2.447, still describes the shipped code).
