# the growing KV is handled by bucketing, and gemma4's length is already device-side

## Summary

`20260929T233000` named "is gemma4's decode step capture-compatible?" as the precondition before
extending graph capture to it, and called the growing KV length the classic blocker. **Reading the
existing path answers it: the length is bucketed, not baked, and gemma4's attention already reads
it from a device buffer.**

## How the existing path solves the growing KV

```python
replay_context_limit = int(position + max_replay_steps if attention_max_context_len is None
                           else attention_max_context_len)
context_bucket = ((replay_context_limit + block_size - 1) // block_size) * block_size
if context_bucket > max_positions:
    raise ValueError("decode graph transition window exceeds resident cache capacity")
```

**The context is rounded up to a `block_size` boundary**, so every replay inside one bucket has
identical shapes, and the key carries `state_generation: position` -- so a graph is valid for one
bucket and is re-captured as the position advances. `steps_per_replay` lets one capture cover
several steps, amortizing the capture cost.

**Nothing about the sequence length is a shape.** That is the whole trick.

## Why gemma4 looks capturable by the same mechanism

The blocker would be an attention kernel that takes the KV length as a **host-side scalar**, since
that value changes every step and would force a re-capture per token. gemma4 does not:

- The architectural invariant is that **`KVLiveSpans` is the attention kernel ABI** -- every
  paged-KV-write and attention-decode kernel reads `(base_offsets, live_counts, token_positions,
  evict_mask)`.
- Those are **device buffers**, not scalars, so the live length is already a runtime value the
  kernel reads rather than a launch parameter.

So the two things that would have blocked capture -- a per-step shape and a per-step host scalar --
are respectively bucketed by the existing design and absent from gemma4's ABI.

## What is not claimed

- **This is an inspection, not a capture.** No graph was built, and no step was checked for
  mid-step host round-trips (`.item()`, synchronization, or an allocation inside the step), which
  is the other half of the precondition and was **not** examined. A capture attempt is the only
  thing that settles it.
- **`steps_per_replay` and `max_replay_steps` semantics were read from the key builder only.** How
  the runner chooses them, and what happens on a bucket transition, was not traced.
- **The gemma4 step's shape stability was not measured across positions.** The argument above is
  structural, from the ABI and the bucketing, not from observing two consecutive steps.
