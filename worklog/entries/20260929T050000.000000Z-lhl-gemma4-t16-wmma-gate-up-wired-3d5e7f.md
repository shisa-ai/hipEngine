# the Q4_K T16 WMMA gate/up route is live: prefill 0.6858 -> 0.66 s

## Summary

The expert gate/up prefill now runs the Q4T16 WMMA leaf instead of the DS4 MMQ32 route.
**Prefill falls from 0.6858 s to 0.66 s** (5 samples, 770 to 775 tok/s, `path parity=True`),
against llama.cpp's 0.563 s -- the gap goes from 1.22x to **1.17x**.

The gain matches the prediction almost exactly: gate/up is 156.5 ms of the prefill and the
measured per-layer ratio is 1.2637, so 156.5 x (1 - 1/1.2637) = **32.7 ms** predicted against
**26 to 36 ms** measured.

## Changes

**`hipengine/loading/gemma4_gguf_device.py`** -- a rank-3 `gguf_q4_k` expert tensor now declares
`allocation_names = ("raw", "t16_gate", "t16_up")`, and `materialize_gemma4_gguf_device_weight`
builds the two tile allocations from the host bytes. `resident_bytes` gained
`derived_allocation_bytes` so the residency figure stays an allocation total rather than a
file-size total, and `derived_half_shape` splits the fused tensor at `intermediate`.

The halves are repacked **separately** because the T16 leaf takes two independent tile pointers
with no expert stride, and the fused layout is gate-rows-first *per expert* -- one fused slab
cannot address both halves.

**`hipengine/kernels/hip_gfx1100/gemma4/gemma4_experts.py`** -- `_gemma4_project_experts_gate_up_wmma_t16`
beside the Q5_K iu8 route, and `gemma4_project_experts_gate_up_mmq` dispatches to it when the
weight carries the tiles. `_gemma4_t16_tiles_ready` reads the `allocations` mapping rather than
calling `has_allocation`, so a stub that models only the raw allocation declines instead of
raising.

**`hipengine/quant/gguf_q4_k.py`** -- `repack_gguf_q4_k_tile16_tile_bytes`, the size formula
`experts x (out/16) x (rows/144) x 2368`, verified to match the repack's own output exactly.

## Cost

**+2.78 percent on the gate/up expert bytes** -- the T16 block is 2368 bytes per 16 columns
against 2304 raw, and that is the whole difference. `tile16_lite` is byte-neutral but the
*non-lite* layout is what this leaf reads. The raw allocation is kept because the strict
fallback route needs it.

## Coverage

`tests/test_gpu_gemma4_expert_route_true_geometry.py` gained
`test_fused_gate_up_t16_route_holds_at_the_true_projection_geometry`, which builds the tiles and
holds the route to **the same envelope as the MMQ32 arm** -- it quantizes no activations, so it
must not be the less accurate of the two. **15 passed**, including the 4 new arms.

The test asserts `gate_up_t16` incremented around the call. Without that it would pass whenever
*either* route served, and the MMQ32 arm satisfies the envelope on its own.

## The production path was confirmed, not assumed

A 512-token `LLM.generate` reports:


**58 is 29 MoE layers x 2**, so the prefill and the first step both take the new route. The
remaining 60 gate/up calls are the decode path at a different call site, which this unit does
not touch.
