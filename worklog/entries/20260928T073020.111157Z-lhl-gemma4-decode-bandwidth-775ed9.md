# the five norms per layer are the dual branch structure not redundancy

## Summary

`20260928T072951` flagged `gemma4_rmsnorm_f32w_bf16` running 5.0 times per layer as high
enough to audit for redundancy before optimizing the kernel, on the grounds that deleting
a norm is cheaper than making five faster. **The audit says they are not redundant.** The
hypothesis is closed, which is worth writing down so it is not re-opened.

## What the five are

Five call sites in `hipengine/kernels/hip_gfx1100/gemma4/gemma4_layer.py`, plus two head
norms:

| line | norm | role |
|---|---|---|
| 383 | attention section | input norm |
| 410, 413 | `gemma4_head_rmsnorm_f32w_bf16` | q_norm / k_norm |
| 505 | dense branch | `pre_feedforward_layernorm_1` |
| 550 | dense branch | `post_feedforward_layernorm_1` |
| 576 | MoE branch | `pre_feedforward_layernorm_2` |
| 596 | MoE branch | `post_feedforward_layernorm_2` |

## Why there are five

**The layer runs a dense branch and a MoE branch in parallel, and each carries its own
pre- and post-norm.** Gemma 4's suffixed norm names encode this directly: the `_1` norms
belong to the dense branch and the `_2` norms to the MoE branch. The code comment at line
505 says so -- "dense branch (parallel with the MoE branch)".

So the count is: 1 input norm + 2 q/k head norms + 2 norms for the dense branch + 2 for
the MoE branch = **7**, of which 5 go through `rmsnorm_f32w` and 2 through
`head_rmsnorm_f32w`. **Each is architecturally required.** There is no redundancy to
delete, and the 160 launches/step this family accounts for are the model's shape rather
than an implementation mistake.

## One real observation, worth less than it looks

`pre_feedforward_layernorm_1` (line 505) and `pre_feedforward_layernorm_2` (line 576)
**both normalize the same `buf("hidden")`** with different weight vectors. That is two
launches reading the same input.

It is not a redundancy -- the weights differ, so the outputs differ and both are used --
and it does not reduce the launch count, which is the thing that costs. It would only pay
if the two could share a single read of the input, which is a bandwidth question and this
work is not bandwidth-bound. Recorded because it is the only structure in the norm chain
that looked like an opportunity, and it is not one at this step's bottleneck.

## Where this leaves the decode target

Unchanged, and now with one hypothesis removed:

- the weight-moving kernels are at 79-92% of DRAM peak;
- **448 zero-byte launches cost 10.37 ms, 29.3% of the step, at 23.1 us per launch**;
- the norm count is not reducible.

**The remaining lever is the 23.1 us per launch itself.** Whether that is launch overhead
or real small-kernel work is the next measurement, and it decides between fusing launches
and making the kernels faster.
