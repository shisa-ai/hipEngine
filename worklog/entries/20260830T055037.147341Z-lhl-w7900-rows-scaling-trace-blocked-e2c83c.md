# W7900: the rows-scaling kernel trace is blocked by two instrument gaps, not by the GPU

## Summary

The next measurement for #14 is a kernel-trace comparison of decode at concurrency 1 vs 2, to name the
kernel families whose duration scales with rows (per-step cost goes 33.2 ms at C1 to 50.4 ms at C2,
where a weight-bound batched step should stay near 33 ms). The attempt is blocked on two instrument
gaps, both fixable and neither of them the GPU. No measurement resulted.

## Changes

No engine or bench code changed. This entry records the blockers and the corrected invocation
knowledge for the next attempt, and kills the two compiler-probe children my own timed-out run
orphaned (`hipcc --version`, `clang++ --version`, aged ~22 min, ppid 1). The 77 older ones were left
alone deliberately - see below.

## Validation

Gap 1 - ROCTX default is wrong for this host. `scripts/gguf_packed_ar_rocprof.py::_default_roctx_sdk`
probes `site-packages/_rocm_sdk_core/lib`, `_rocm_sdk_devel/lib`, and
`/opt/rocm/lib/librocprofiler-sdk-roctx.so.1`. None of those exist here: the pip ROCm SDK packages are
not installed and `/opt/rocm/lib` carries only the legacy `libroctx64.so` (and
`libroctx64.so.4.1.0`). Passing `--roctx-sdk /opt/rocm/lib/libroctx64.so` gets past the check. The
tool should fall back to `/opt/rocm/lib/libroctx64.so` instead of failing, since that is what this
image actually has.

Gap 2 - the run spent its whole 1500 s budget in `warmbuild` and produced an empty stdout log, while
`/tmp/he-c2trace/c1/{warmbuild-c1,warmbuild-c4}` filled. That is the exact failure mode `AGENTS.md`
names: do not let the profiled process compile. The correct sequence is a separate non-profiled
warmbuild first, then a traced run with a precomputed `--compiler-version-file` and
`--require-cached-build`. `rocprofv3` itself is present (`/home/lhl/mambaforge/envs/therock/bin/rocprofv3`),
`hipcc --version` returns in 36 ms and `clang++ --version` in 5 ms, so nothing about the compiler stack
is hanging - the budget was simply too small for a cold cache, and the child writes its own log rather
than inheriting stdout, which is why the parent log looked empty.

Separate environment finding, deliberately not acted on: 77 processes named `clang++ --version` with
ppid 1, aged 32-46 days. They are in state `SN`/`S<` (sleeping, not stopped, not zombie), and the same
commands complete in milliseconds today, which is the signature of a writer blocked on an undrained
pipe from a parent that died - an accumulation of exactly this warmbuild path. They consume no CPU, so
they are a leak rather than a drag, and they predate this session by five to seven weeks: someone else
owns them, so I reported rather than killed.
