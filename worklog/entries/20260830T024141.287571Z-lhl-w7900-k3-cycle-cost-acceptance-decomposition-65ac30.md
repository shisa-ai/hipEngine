# W7900 Qwen3.8: K3 verifier cycle costs 2.95 AR steps at C1 and 5.95 at C8, with tokens per cycle falling 3.11 to 1.93

## Summary

Both halves of the K3 deficit now have measured sizes and their product explains
the whole collapse. Our verifier cycle costs **2.95 of our own AR decode steps at
C1** (100.2 ms vs 34.0 ms) and **5.95 at C8** (489.0 ms vs 82.2 ms), while tokens
per cycle fall **3.11 -> 1.93**. Against our own marginal decode the speculative
path goes from **1.05x (C1)** to **0.32x (C8)**; cost inflation 2.02x times the
yield loss 1.61x is 3.25x, matching the observed 1.05 -> 0.32 (3.28x).

## Changes

- Analysis only; no code or flag changed. Numbers recorded so #9 is driven by
  measured magnitudes rather than descriptions.

Method. Tokens per cycle per lane = `1 + p1 + p1*p2 + p1*p2*p3` for K=3 from the
packet's `acceptance.by_width[w].scopes.all.positions`. Per-lane K3 rate =
published aggregate / lanes. Cycle wall = tokens per cycle / per-lane rate. AR
step wall = `decode_step_ms` from the marginal AR decomposition at the same width.
Cross-check: 3.95 x 8 = 31.6 against the published C8 K3 row 31.445, and
K3/margAR x marginal AR aggregate (0.32 x 97.37 = 31.2) reproduces the same row to
1.3%, so the model closes on the published numbers.

Why acceptance rather than the packet cycle counter: `acceptance.denominators`
defines cycles as "cycles accepting through this position / cycles proposing this
position", and both readings of that field (per-wave vs per-lane) give physically
impossible cycle walls (85 ms yielding under one token per lane, or 678 ms per
cycle). The acceptance-derived cycle is self-consistent at both endpoints, so the
counter definition stays unresolved and is not used for the claim.

What this exonerates: absolute cycle cost is not the C8 story in the way admission
is for AR - a 489 ms cycle is unremarkable for 8 lanes x 4 verifier rows; the bug is
that it is priced at ~6 AR steps, i.e. the cycle does not amortize across the wave.
What stays separate: acceptance falls 0.930/0.773/0.645 -> 0.571/0.469/0.350 inside
this single run at one commit, so it is width-dependent, not session drift, and
fixing packing alone leaves K3 at ~0.5x of marginal AR.

Not claimed: any peer cycle-wall ratio. Splitting the peer gap the same way needs
llama.cpp tokens/cycle, which this packet does not measure; assuming 6 tokens per
cycle would put the peer at 63 ms for C8 and make us 1.34x slower per cycle, but
that number is contingent on the assumption and is not a measurement.
