# the dense term cannot reach the four-wave schedule, and the reason is a missing repack

## Summary

`GGUF_Q8_T16_PREFILL_FOUR_WAVE = True` is declared on gfx1151 and read by nothing in
`hipengine/`. It is the last unconsulted flag on the biggest single prefill term. Following it
down did not find a missing wire -- it found a **missing layout**.

**Refuted, with a named capability miss.** The dense term is raw `gguf_q8_0`; the four-wave
schedule is registered only under `gguf_q8_0_t16_v1`. gemma4's loader has no Q8_0 repack step,
so the T16 layout never exists for these weights and there is no schedule to turn on.

## What the dense term actually is

`scripts/gemma4_dense_dispatch_probe.py`, wrapping `launch_gguf_linear`:

```
quant=gguf_q8_0  variant=None -> 206 calls
  rows=512 out=2816  -> 60      rows=512 out=4096  -> 25
  rows=512 out=2112  -> 60      rows=512 out=8192  ->  5
  rows=512 out=2048  -> 50      rows=512 out=1024  ->  5
  rows=1   out=262144 -> 1      (the lm head)
```

**All 206 are raw `gguf_q8_0`.** Not `gguf_q8_0_t16_v1`, which is the key the gfx1151 override is
registered under:

```python
("linear", "gguf_q8_0_t16_v1", "wmma_prefill_bf16_bf16_out"):
    gguf_q8_0_t16_wmma_prefill_auto_4wave_bf16_bf16_out,
```

So the override cannot match. And a grep for `"gguf_q8_0"` in `hip_gfx1151/__init__.py` returns
**nothing** -- the raw key has no wave wiring at all.

## The machinery is fully built; the layout is what is missing

The schedule is real and admitted, and nothing about it is stubbed:

- `_FOUR_WAVE_VARIANT = "wmma_prefill_4wave_bf16_bf16_out"` and
  `gguf_q8_0_t16_wmma_prefill_auto_4wave_bf16_bf16_out` exist, with `four_wave_default=True`.
- The gate is `tile_m in {32, 64} and tile_n == 32 and out_features >= 2048`, and it overrides
  `tile_m` to 128 when it fires.
- gfx1151 wires the auto-4wave wrapper under `gguf_q8_0_t16_v1`.

**And it is provably never reached.** `scripts/gemma4_q8_t16_wave_probe.py` wraps both gate
functions and `_launch`; a 512-token prefill produces **zero gate calls and zero launches** --
the module is not on the dense term's path at all.

## The reason, in gemma4's own loader docstring

`hipengine/loading/gemma4_gguf_device.py`:

> No repack step. `launch_gguf_linear` serves the `raw` layout for every quant type this artifact
> uses (Q4_K, Q5_1, Q5_K, Q8_0), at both decode and prefill.

The single exception is the stacked Q4_K expert tensor, which carries `t16_gate` / `t16_up`
allocations. **Every other quant, Q8_0 included, is raw-only.** The repack machinery lives in the
`qwen35_*` materializer (`qwen35_gguf_materialize.py`), where the layout is chosen by:

```python
if qtype == Q8_0 and decode_repack and slot_path.startswith("layers.") and len(tensor.shape) == 2:
    ... quant_key="gguf_q8_0_t16_v1", layout=LAYOUT_GGUF_Q8_0_T16
if qtype in (Q6_K, Q8_0):
    ... quant_key="gguf_q8_0", layout=LAYOUT_RAW_GGUF
```

That path defaults `decode_repack` **on** (`HIPENGINE_GGUF_DECODE_REPACK` defaults to `"1"`), so
this is not a flag being off -- **gemma4 simply does not run this materializer.**

## The lever this identifies

**The dense term is 189.3 ms of a 659 ms prefill, the largest single term, and it is pinned at
127 GB/s of weight traffic against an achievable 223** (`20260929T100000`). It is raw Q8_0, so it
takes neither the two-wave nor the four-wave schedule. Both exist, both are admitted as exact, and
both are registered -- **for a layout gemma4's loader never produces.**

So the bounded next unit is: **give gemma4's loader a Q8_0 -> T16 repack**, exactly as it already
does for Q4_K expert tiles, and set `quant_key="gguf_q8_0_t16_v1"`. The pieces already exist --
`hipengine/quant/gguf_t16.py` declares `name = "gguf_q8_0_t16_v1"`, and `repack_gguf_q4_k_tile16`
is the precedent for the call shape.

**No performance claim is made here.** The lever is identified, not taken; 127 -> 223 GB/s is a
target, not a measurement, and the repack costs load time and resident memory that have not been
counted.

## What was ruled out along the way

- **Not a flag plumbed off.** `decode_repack` defaults on and the veto is `per-tensor` by default,
  which the policy docstring says explicitly should not strip Q8_0 tensors.
- **Not a missing kernel.** The 2wave/4wave symbols exist and are registered.
- **Not a missing wire.** gfx1151 wires the auto-4wave wrapper; the key is what does not match.

## Changes

Three probe scripts, all read-only:

- `scripts/gemma4_dense_dispatch_probe.py` -- records the (quant, variant) each
  `launch_gguf_linear` call resolves.
- `scripts/gemma4_q8_t16_wave_probe.py` -- counts gate calls and launched symbols.
- `scripts/gemma4_q8_0_registry_dump.py` -- lists every registered q8_0 kernel and flags the wave
  symbols.
- `scripts/gemma4_q8_t16_wave_gate.py` -- the shape/gate report (its module walk found nothing, so
  it is superseded by the two above and kept only as the failed approach's record).

## Validation

Read-only investigation; no production code changed, so no arithmetic gate applies.

```
.venv/bin/python scripts/gemma4_dense_dispatch_probe.py    # 206/206 raw gguf_q8_0
.venv/bin/python scripts/gemma4_q8_t16_wave_probe.py       # 0 gate calls, 0 launches
.venv/bin/python scripts/gemma4_q8_0_registry_dump.py      # wave symbols exist, T16 key only
python3 scripts/worklog.py check                           # entry schema valid
```

The refutation rests on two independent observations that agree: the dispatch probe shows the
key is raw `gguf_q8_0`, and the gate probe shows the wave module is never entered. Either alone
would be suggestive; together they locate the break at the layout rather than the dispatch.
