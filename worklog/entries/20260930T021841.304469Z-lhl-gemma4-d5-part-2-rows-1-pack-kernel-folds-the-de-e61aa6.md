# Gemma4 D5 part 2: the rows=1 pack kernel - implemented, measured, rejected

## Summary

The pack-head half of punchlist D5 was implemented, proven bit-identical to
the chain it replaces, measured against that chain in one same-session
census A/B, and **rejected: it is slower on device**. The rows=1 decode path
keeps the five-launch chain. Code reverted to HEAD; this entry and the
`d5p2` artifacts carry the result.

`gemma4_moe_pack_rows1` folded the decode compaction chain -
`qwen35_moe_group_compact_active` (count + prefix + scatter), the
`gather_packed_hidden` copy, and the `lane_to_row` inversion - into one
grid-1 / 256-thread launch, selected by `tokens == 1` inside
`gemma4_experts_forward_bf16`. The design settled the ABI question the
punchlist raised first: the layer composer does **not** need to pass the
expert scratch across; a self-contained pack inside the experts forward
reproduces every buffer the row's consumers read (`packed_hidden` +
`sorted_experts` for the selected GEMVs, `lane_to_row` + `sorted_weights`
for the accumulate, `expert_start` for the bf16 by-offset fallback). The
chain's order is deterministic - counts, exclusive prefix, lanes ascending
inside each expert - so the pack sorted `(expert, lane)` and bit-copied
rows to match.

## Validation

**Implementation itself (before the measurement).** RED first: three tests
failed on the missing symbol, then `tests/test_unit_gemma4_pack_rows1.py`
went 3/3 GREEN - a chain-vs-pack differential asserting bit equality on
`expert_start`, `sorted_lanes`, `sorted_experts`, `sorted_weights`
(compared as raw uint32), `packed_hidden`, and `lane_to_row`, at small and
Gemma-shaped (E=128, k=8, H=2816) geometries over distinct- and
repeated-expert routings, plus a 0xDE sentinel proving every packed element
is written. Regression after wiring the forward:
`test_unit_gemma4_gpu_kernels.py`, `test_unit_gemma4_family_census.py`,
`test_unit_gemma4_moe_prefill_routes.py`,
`test_unit_gemma4_mmq_route_guard.py`,
`test_gpu_gemma4_moe_empty_lane_guard.py` - 95 passed, rc=0. The same five
files pass rc=0 again after the revert.

**Measurement: same-session census A/B on the W7900 lane.** Two
`rocprofv3 --kernel-trace` census runs, identical protocol
(`--prompt 1024 --decode 64 --prefill-repeats 2`), identical environment,
back to back on one idle-stable GPU at commit `e6796d9ac`: one with the
chain monkeypatched into the rows=1 path, one with the pack build. Decode
window, per token:

| | chain replay | pack candidate | delta |
| --- | --- | --- | --- |
| `moe.route_glue` | 0.9445 ms @ 180 launches | 1.4000 ms @ 60 launches | **+0.4555** |
| compaction part | 0.4043 (5 kernels, 13.48 us/layer) | 0.8574 (pack, 28.58 us/launch) | +0.4531 |
| `weighted_accumulate` | 0.5401 (18.00 us) | 0.5426 (18.09 us) | +0.0025 (flat) |
| decode device busy | 17.2967 ms | 17.6974 ms | **+0.4007** |
| decode phase span | 17.30 ms | 17.71 ms | +0.41 |

The chain's five kernels measure count 3.45 us, prefix 3.58 us, scatter
2.34 us, gather 2.31 us, lane_to_row 1.80 us per layer at rows=1 - the
launch count the row wants to cut is not where the time sits. Cutting four
launches per layer cost 0.40 ms/token of device busy and 0.41 ms/token of
span; there is no host-gap offset (span tracks busy in both runs).

Earlier same-commit snapshots (tag `d5r` chain against tag `d5p2` pack,
nine minutes apart) showed route_glue +0.506 at 1024 and +0.524 at 4096
with every untouched family also up +6..17% (dense.q8_0 +0.49) - a
run-state inflation that makes the topline pair (decode 57.45 -> 50.72 at
1024, 51.35 -> 46.01 at 4096) unsuitable as deciding evidence. The
back-to-back replay above removes that confound and points the same
direction.

**Why the pack loses, and the open question.** Phase bisection under
rocprof (temporary diagnostic guards, reverted): with the gather disabled,
22.6 us; with the serial prefix also disabled, 21.4 us; with count,
prefix, scatter and gather all disabled - an essentially empty kernel with
three barriers - **still 19.8 us**. Swapping dynamic shared memory for a
static array changed nothing (23.6 us full). About 20 us is a fixed
per-launch cost specific to this kernel, not its work, and it does not
attach to the config either: the chain's
`qwen35_moe_group_prefix_active_parallel` runs the same grid-1 / 256-thread
/ shared-memory shape at 3.58 us. The root cause was not found in this
unit; it is the first thing to explain before a second attempt at the
pack-head half. An event-timed microbench that appeared to show the pack
ahead was host-launch-bound (five ctypes dispatches against one) and does
not contradict the device measurements.
