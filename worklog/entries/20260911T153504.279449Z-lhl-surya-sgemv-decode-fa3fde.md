# Surya decode: single-token GEMM moved to SGEMV, 1.67x decode and 1.61x end-to-end

## Summary

Decode was 2.1x slower than torch generate on the same GPU (32.9 vs 69.2
tok/s), which dominated the 2.051 s end-to-end request. The cause was the BLAS
routine, not the kernels: decode is a single row, and rocBLAS SGEMM is tuned
for a wide `n`, so at `n == 1` it read the weights at roughly a third of the
bandwidth SGEMV reaches. Routing `rows == 1` to SGEMV took decode from 30.07 to
17.96 ms/token and the full request from 2.051 s to 1.276 s.

## Diagnosis

Three measurements, in order:

1. **Not launch-bound.** 187 GEMMs + 236 kernels = 423 launches per decode
   step, but a tiny-kernel launch costs 3.22 us async, so all launches together
   are ~1.4 ms of the 30 ms. The step is GPU-bound.
2. **Not at the hardware floor.** Device weights are 2.663 GB (2.261 GB text,
   which is what decode reads). At a realistic ~200 GB/s that is a ~11 ms/token
   floor. torch generate sits at 14.5 ms/token, essentially at it. The
   hipEngine lane was at 30 ms/token, ~75 GB/s effective, 2.7x off.
3. **The routine was the gap.** On a 3185x1152 fp32 weight, `rocblas_sgemm`
   with one row: 115.1 us (128 GB/s). `rocblas_sgemv`: 46.5 us (316 GB/s).
   2.48x, and decode is 187 of these per token.

## Changes

- `hipengine/core/rocblas.py`: new `Rocblas.sgemv_rowmajor_nt` for
  `out[out_features] = weight[out,in] @ x[in]`, plus the `rocblas_sgemv`
  `argtypes`/`restype` declaration. The declaration is not optional: without
  it ctypes passes the 64-bit pointers as C ints.
- `hipengine/runtime/surya.py`: `_gemm` routes `rows == 1` to SGEMV. The
  `rows > 1` prefill path is untouched.
- `tests/test_rocblas.py`: `rocblas_sgemv` added to the mock library, plus two
  tests pinning the column-major transposition (`trans=T`, `m=in_features`,
  `n=out_features`, `lda=in_features`) and the shape validation.
- `tests/test_surya_gpu.py`: `test_gpu_single_token_gemm_uses_sgemv_and_matches_sgemm`
  pins the routing (a spy must see `gemv` then `gemm`) and checks SGEMV agrees
  with a one-row SGEMM on device.
- `benchmarks/README.md`, `benchmarks/CHANGELOG.md`,
  `benchmarks/results/2026-09-11-gfx1151-surya-lane-compare.json` (rewritten by
  the benchmark script), `docs/MODEL-SURYA.md`.

## The transposition is easy to get wrong silently

rocBLAS is column-major, so `y = W x` with `W` (M,K) row-major is
`trans=T, m=K, n=M, lda=K`. A first attempt used `m=M, n=K, lda=M`, which does
not error — it reads a differently shaped matrix and returns wrong numbers. The
check that caught it was comparing SGEMV against SGEMM for one row:

| Call | max abs diff vs SGEMM | relative |
| --- | --- | --- |
| `m=M, n=K, lda=M` (wrong) | 1.004e-01 | 1.119 |
| `m=K, n=M, lda=K` (correct) | 8.196e-08 | 9.129e-07 |

The relative error is what distinguishes a transposition bug (order 1) from
fp32 summation order (order 1e-6). Both tests above now pin it.

## Results

Same host (Ryzen AI Max+ Pro 395 / Radeon 8060S, gfx1151), same protocol
(`scripts/surya_perf_compare.py --runs 3`, page_small.png, 64 new tokens, fp32),
all four lanes correctness PASS:

| Lane | e2e before | e2e after | decode before | decode after | tok/s before | tok/s after |
| --- | --- | --- | --- | --- | --- | --- |
| hipengine_gpu | 2.051 s | **1.276 s** | 1.947 s | **1.153 s** | 32.9 | **55.5** |
| torch_cuda (HIP) | 2.577 s | 2.676 s | 0.925 s | 0.938 s | 69.2 | 68.2 |
| hipengine_cpu | 20.450 s | 20.456 s | — | — | 3.4 | 3.7 |
| torch_cpu | 149.935 s | 150.212 s | — | — | 0.5 | 0.5 |

- decode: 32.9 -> 55.5 tok/s, **+68.7%** (1.67x)
- end-to-end: 2.051 -> 1.276 s, **-37.8%** (1.61x)
- versus torch HIP end-to-end: 1.26x -> **2.02x faster** (1.276 s vs 2.676 s)

The end-to-end gain exceeds the decode gain because decode is 1.153 s of the
1.276 s total. Decode alone still trails torch generate (55.5 vs 68.2 tok/s),
so no decode-only superiority claim is made; the full request is 2.1x faster.

The torch lanes are unchanged within run-to-run noise (2.577 -> 2.676 s,
69.2 -> 68.2 tok/s), which is the control showing the host did not shift.

## Validation

Both SGEMV and SGEMM accumulate in fp32; the only difference is summation
order, so a near-tie argmax could in principle flip. It did not: the full Surya
suite (98 tests) passes unchanged, including exact greedy-ID parity against the
torch fp32 oracle on all five pages, the text-only path, and the multi-prompt
isolation test. `test_gpu_single_token_gemm_uses_sgemv_and_matches_sgemm` also
asserts the argmax agrees on a real weight.

The first version of that test passed standalone but aborted the full bundle:
its `rows=3` dispatch probe wrote three rows of output into a buffer sized for
one, corrupting the heap. It only surfaced when the whole file ran, which is
the argument for running the bundle rather than the new test alone. Fixed by
sizing the buffer for three rows.
