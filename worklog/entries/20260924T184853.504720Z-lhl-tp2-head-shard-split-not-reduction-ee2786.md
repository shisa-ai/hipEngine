# Localize the head-sharded prefill's error to the sharded compute, not the reduction

## Summary

The head-sharded bulk prefill is still wrong. This entry records where the
error is *not*, so the next round does not re-search it, and localizes it to the
sharded attention compute rather than the cross-rank reduction.

## What the routes disagree by

Same prompt (64 tokens), same two devices, both routes run through
`scripts/tp2_head_shard_agreement_probe.py`, one process per route.

| layer | type | sharded attention output vs unsharded, rel_rms |
| --- | --- | ---: |
| 0 | GDN | 0.061 |
| 1 | GDN | 0.487 |
| 2 | GDN | 1.000 |
| 3 | full attention | 0.321 |
| 4 | GDN | 0.817 |

Output: mean KL 0.3626, top-1 agreement 0.5938. Magnitudes are preserved
throughout (layer 0 `|base|` p50 0.0234 vs 0.0234, max 35 vs 35), so this is the
right tensor with the wrong content, not a scale or overflow problem.

Two facts that constrain the search:

* **Both ranks agree bit-exactly at every captured layer, on both routes.** The
  spin-add writes each rank's output from the same operands, so agreement here
  is by construction and carries no information about correctness.
* **The sharded route is deterministic.** A second run, with a different
  synchronization schedule, reproduced every captured layer bit-for-bit.

## Ruled out this round

**The staging-slot race.** `ShardGroup.reduce_device_payload` picks its slot as
`reductions_per_layer * (layer_id % 2) + phase`, and its own docstring states the
hazard: "the peer is free to overwrite its staging while this rank's spin-add is
still reading it, and the protocol carries no acknowledgement that would prevent
that." With `reductions_per_layer=2` the slot set only alternates on
`layer_id % 2`, so layers 0/2/4 share slots 0-1 and 1/3/5 share 2-3. Nothing in
`_run_bulk_prefill_layers` holds the ranks together: the loop enqueues every
layer without a host wait and synchronizes once at the end, so a rank that
reaches layer L+2 while its peer is still on L overwrites the slot the peer's
spin-add may still be reading.

That is a real hazard and it would produce exactly the observed shape - right
magnitude, uncorrelated content, varying per layer. It is not what is happening
here, for two reasons:

1. Forcing the ranks to one layer apart (`--lockstep`, a host wait after every
   layer) reproduced every number to the last digit. A race does not survive
   being serialized.
2. The error is deterministic across runs. A slot race is a timing hazard.

The hazard is still worth a follow-up on its own terms - it is a latent
correctness bug in the slot scheme, currently masked - but it is not this bug.

**The GDN head split.** Earlier suspicion was that splitting `attn_qkv`'s k
block across ranks breaks the tiled `k_head = v_head % k_heads` mapping. It does
not. `shard_rule_for_tensor` gives the k block 16 groups and rank 0 gets groups
0-7, i.e. k heads 0-7; rank 0's value heads are 0-7, 16-23 and 32-39, whose
required k heads are `v % 16` = 0-7 for all three groups. The k heads a rank owns
are exactly the ones its value heads map to, at every degree. Checked directly
against the rules for `attn_qkv`, `attn_gate` and `ssm_out`.

**The reduction primitive.** See below.

## What is actually wrong: the split computes the wrong partial

The probe now also captures each rank's *pre-reduction* partial
(`scratch.attn_out`) on both routes. On the unsharded route that buffer already
holds the whole attention output; on the sharded route each rank holds only its
own heads' contribution. So summing the two sharded partials and comparing
against the unsharded output tests the split independently of the reduction.

| layer | partials sum vs unsharded output | reduced vs unsharded output |
| --- | ---: | ---: |
| 0 | 0.06109 | 0.06115 |
| 1 | 0.4871 | 0.4869 |
| 2 | 1.0000 | 1.0000 |

The two columns are the same number. The reduction reproduces the sum of its
inputs faithfully, and **the inputs are already wrong**: each rank's head-sharded
attention does not compute the contribution of its own heads. The bug is in the
sharded attention compute, upstream of the exchange.

All three captured layers are GDN layers (the pattern is three GDN then one full
attention), and the error grows 0.061 -> 0.487 -> 1.000 across them. A small
systematic error that compounds is more consistent with a subtle mismatch inside
the GDN block than with a wrong head mapping, which would be large at layer 0
rather than 6%.


## Changes

* `scripts/tp2_head_shard_agreement_probe.py` (new) - consolidates the two
  throwaway probes that produced the earlier evidence, which lived in `/tmp` and
  could not be re-run from the repo. Subcommands `route` (logits for one route),
  `layers` (also capture the post-attention-norm input and each rank's
  pre-reduction partial, per layer and per rank), and `compare` (offline KL,
  top-1, per-layer agreement, and the split check). `--lockstep` adds a host wait
  after every layer as a serialization diagnostic. One process per route,
  deliberately: a session whose constructor raises cannot be closed and leaks a
  rank's VRAM, so retrying in-process turns a transient OOM into a permanent one.

No production code changed. This unit is diagnosis only and used no GPU time
beyond the probe runs.

## Validation

* `python3 scripts/tp2_head_shard_agreement_probe.py compare --out
  /tmp/tp2_layer_consec --layers 0,1,2,3,4` reproduces the recorded layer
  agreement (0.061 / 0.487 / 1.000 / 0.321 / 0.817).
* `... layers sharded --lockstep --out /tmp/tp2_lockstep` reproduces the
  non-lockstep numbers exactly, on every captured layer and on the logits.
* `... layers {baseline,sharded} --out /tmp/tp2_split` then `... compare` gives
  the split table above.

A dtype bug was found and fixed in the probe while doing this: the capture writes
raw bf16 bit patterns, and casting them to float yields the integer value, which
makes a normal tensor look saturated at ~4.8e4. The comparison now shifts into
float32 before comparing. The numbers recorded before the fix were computed
correctly by the throwaway script and are unchanged.

## Next

Isolate the GDN split at layer 0 alone. The error is already 6% there, before any
compounding, and layer 0 is a single GDN block: `attn_qkv` -> conv1d -> gating ->
recurrence -> `ssm_out`. The probe can capture `conv_out`, `linear_z` and
`recurrent_bf16` per rank; those are half-width under sharding so they cannot be
compared elementwise against the unsharded route, but they can be compared
against `hipengine/kernels/cpu_reference/surya.py:_gdn_layer_prefill`, which
takes a config and weights and so can be driven with the sharded config.
