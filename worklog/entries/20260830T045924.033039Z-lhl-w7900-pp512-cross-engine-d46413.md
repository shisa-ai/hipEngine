# W7900: 512-token prefill matches llama.cpp on device time, not on wall

## Summary

Task #13 had no comparator at all: the retained parity entry recorded 883.8 tok/s internal at 512
tokens and stopped there. Measured both sides today on the same W7900. llama.cpp current HIP
(`build-hip-gfx1100`, b19cbe925/10671) `llama-bench -p 512 -n 0 -ngl 99 -r 3` gives
**881.25 +/- 15.18 tok/s**. hipEngine's device-time 883.8 is **+0.29%**, inside llama's own spread, so
the compute matches. The wall through the resident server does not: medians of 3 on the current tree
give 493.4 / 503.6 / 519.8 tok/s at 545 / 569 / 593 prompt tokens, i.e. 0.56x raw and about 0.72x
after removing the ~0.24 s of wall that is not prefill (admission, first decode, sampling, HTTP).

## Changes

Artifact `2026-08-30-w7900-q4km-pp512-cross-engine.json` and a changelog line. No README row: the
submodule scoreboard is wave-shaped (C1-C8) and a llama-bench pp512 number has a different protocol, so

## Validation

| measurement | value | protocol |
| --- | --- | --- |
| llama.cpp current pp512 | 881.25 +/- 15.18 tok/s | llama-bench, warm batch, 3 reps, no admission/sampling |
| hipEngine device time pp512 | 883.8 tok/s | retained packet, shipping AR route, device time/token |
| hipEngine wall pp512-ish | 493-520 tok/s at 545-593 tokens | resident server via HTTP, median of 3, spread <= 0.04 s |

The residual is computed from this tree's own numbers, not assumed: at the packet's 1.13 ms/token
device time plus the ~250 ms fitted prefill fixed cost, 545 tokens predicts ~0.87 s against the
measured 1.1045 s, and the ~0.24 s difference is the server path around the prefill.

I did **not** quote the probe's own fit for this run: it printed `fixed 694.5 ms + 0.76 ms/token`,
which is meaningless because the bracket spans only 545-593 tokens, so slope and intercept are
collinear over it. The published fixed cost stays ~252-271 ms from the wide 1-285 token fits.
