# The sliding read range now applies to prefill blocks, and the per-row bound is the real lever

## Summary

A sliding layer's keep-mask zeroes every key outside its window, but the
attention kernel walked the whole live context anyway. The narrowing that drops
those keys was written for one-row blocks only — "Only a one-row block may skip"
— so decode used it and prefill paid the full walk. It now applies to every
block.

The stated obstacle was real and is the reason this was not a one-line change:
the kernel addresses the mask as `keep_mask + token * keys`, so shifting the mask
base by `key_begin` addresses the right row only when there is one row. A
prefill block needs the mask itself to start at `key_begin`, with `keys`
shortened to match, which is why `_keep_mask` and the layer wrapper had to move
with the range.

The change is bit-exact. Dropping a key whose mask weight is exactly zero leaves
the surviving terms in their original order, so the reduction is unchanged rather
than merely close — the same argument the decode path has always relied on.

## The measurement is honest: this is not a win

| prompt | prefill before | prefill after |
| --- | --- | --- |
| 512 | 271 tok/s | 272 tok/s |
| 1024 | 251 tok/s | 249 tok/s |
| 2048 | 220 tok/s | 222 tok/s |

The effect is inside the noise floor, and **the 1024 point proves it**: prefill
runs in 512-token chunks, so both of 1024's chunks get `key_begin = 0` and the
change is a provable no-op there — yet it moved by 0.8 percent. The 2048 point's
+1.2 percent sits in the same band. This row does not claim a speedup.

The arithmetic says why. The block bound is the *first row's* window, so only the
last chunk of a 2048-token prompt can narrow at all:

| chunk | start | keys | key_begin | walked |
| --- | --- | --- | --- | --- |
| 0 | 0 | 512 | 0 | 512 |
| 1 | 512 | 1024 | 0 | 1024 |
| 2 | 1024 | 1536 | 1 | 1535 |
| 3 | 1536 | 2048 | 513 | 1535 |

5120 keys walked becomes 4606, 10.0 percent less, and attention is 28.9 percent
of a 2048-token prefill, so the predicted overall effect is 2.9 percent. That is
under the measurement's resolution.

## What the profile actually found

This unit started from a `rocprofv3` trace at two prompt lengths, because the
campaign's only prefill attribution was a gfx1100 lane and this host is gfx1151.
The trace is worth keeping on its own:

| kernel | 512 ms | 2048 ms | ratio |
| --- | --- | --- | --- |
| gemma4_attention_prefill | 245.2 | 2684.4 | **10.95x** |
| q5_1_selected_grouped_prefill_staged | 651.7 | 2651.7 | 4.07x |
| gguf_q8_0_exact_prefill_tiled_out | 563.4 | 2237.7 | 3.97x |
| gguf_q4_k_selected_dual_q8_1_ds4_mmq32_fused | 182.9 | 719.3 | 3.93x |
| gguf_q5_k_selected_grouped_row4 | 111.0 | 450.1 | 4.05x |
| q8_0_selected_grouped | 44.8 | 175.9 | 3.93x |
| total | 1922.1 | 9280.9 | 4.83x |

**Every route scales exactly linearly with the token count except attention,
which scales 10.95x.** Attention's excess over linear is 1703.6 ms against the
whole prefill's excess of 1592.5 ms, so attention is the entire length dependence
and the whole gap between this engine's falling prefill rate and llama.cpp's flat
one. The 512 profile reproduces the previously recorded one (651.7 against 673,
563.4 against 562, 245.2 against 245).

## The real lever

The bound that matters is **per row**, not per block. Within a chunk every row
shares one key loop, but a row at position `p` only ever needs `min(p + 1,
window)` keys. At 2048 that is 1573376 keys walked against the block bound's
2359296 — **33 percent less**, worth about **9.6 percent** of a 2048-token
prefill and growing with context.

The prefill kernel already runs one `blockIdx.x` per (token, head) and already
skips the dot product for a masked key, so what it pays is the loop and its
barrier rounds rather than the arithmetic. Starting that loop at the row's own
first kept key, tile-aligned, drops the leading all-masked tiles. It needs the
window and the chunk's absolute start passed to the kernel, which is why it is a
separate unit and was not attempted here.

## Changes

- `hipengine/runtime/gemma4.py`: `_sliding_read_range` no longer restricts
  skipping to one-row blocks and returns `max(0, start - window + 1)`, which is
  the earliest key any row of the block can read and reduces to the old
  `live - window` for a one-row block. `_keep_mask` builds
  `(rows, start + rows - key_begin)` columns starting at `key_begin`.
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_layer.py`: the mask pointer is
  passed unshifted, because the mask now starts at `key_begin` and the kernel's
  `token * keys` stride already lands on each row.
- `tests/test_unit_gemma4_sliding_read_range.py`: `test_multi_row_blocks_never_skip`
  asserted the old limitation and is replaced by tests that pin the block range
  against the block mask across window, context and block lengths, plus a test
  that the mask's column 0 is `key_begin`.

## Validation

RED first: the four new tests failed against the unmodified runtime, including
`assert 0 == ((4096 - 1024) + 1)`.

The unit suite passes in full (12 tests).

Bit-exactness is verified end to end, not asserted. The real artifact's prefill
logits were hashed at 512, 1024 and 2048 with the change and with the three edits
stashed, and all three digests are identical in both arms — same SHA-256, same
top-1 token, same logit sum. No arithmetic moved, so no execution-profile
promotion gate applies.

## Next

The per-row key-loop start in `gemma4_attention.hip`, worth about 9.6 percent of
a 2048-token prefill and more at longer contexts. It needs the sliding window and
the chunk's absolute start in the kernel's argument list, and its own RED
contract: the narrowed loop must produce bit-identical output, which the same
digest harness can check.

That is still a small part of the objective's prefill gap. Against the same-host
llama.cpp reference measured in
[`20260927T191536`](20260927T191536.780145Z-lhl-gemma4-gfx1151-llamacpp-baseline-12f173.md)
this engine is 3.74x to 4.85x off, and the three weight-bound routes are 61
percent of the 512-token prefill. Attention is the length dependence; the
weight-bound routes are the constant factor.
