# Apply the decode crossover uniformly for shallow one-token blocks

## Summary

The 512-token decode gap against llama.cpp (33.53 vs 35.98 tok/s, stable since
before the campaign) is diagnosed and its larger component is fixed. Three
candidate causes were weighed against in-tree evidence:

1. Launch overhead -- refuted by the 2026-09-30 decode-graph work: eager decode
   is already device-bound (host submission hidden under device work; graph
   replay measured negative at the campaign workload).
2. The decode-kernel crossover being bypassed for staged request sets --
   CONFIRMED. `_STRICT_DECODE_WINS_UNTIL_KEYS = 4096` encodes a measured
   crossover (strict decode kernel faster below 4096 keys, staged singleton
   faster above), but the one-token selection branch only applied it when
   staged was *not* in the request set. Every production plan since the staged
   default includes staged in requests, so the singleton served all shallow
   decode steps -- below the crossover where the strict kernel is faster.
3. Batch-1 dense/MoE kernels -- remains the residual owner of the leftover gap.

The A/B (promoted-build prefill on both arms, 512 prompt, 127 decode steps,
three repeats): strict decode kernel 34.64 tok/s median vs staged singleton
32.33 (+7.1%), with identical token IDs across arms -- both routes are
strict-parity, so the switch is routing-only, no new arithmetic surface.

The fix drops the `staged not in requests` condition, making the measured
crossover uniform for every request set -- it already governed WMMA requests,
and the asymmetry was the defect. Explicit single-variant staged requests at
one-token blocks below the crossover now also take the strict decode kernel;
this is a measured routing decision on bit-identical arithmetic, recorded in
the updated tests.

Measured after the fix: the 512 campaign row improves to 34.02 tok/s median
(3 samples, 33.89-34.07) from 33.53, and the public path computes to
~35.1 tok/s (public wall 4.04s minus prefill 0.39s over 128 tokens) against
llama.cpp's 35.98 -- instrumented ratio 0.945x, public ~0.975x. The residual
~2-5% is host-side per-step work in the sampler/logits path; the in-tree
graph-work note already records the clearing route for that (device-positioned
KV appends removing the per-step retarget) as a larger, separate project.
Deep decode is untouched by construction (keys > 4096 keep the singleton); a
fresh 32768 verify shows prefill 931.5 tok/s and decode 26.35 tok/s with
public parity True (decode varies 23.9-26.4 across sessions on this shared
iGPU; one sample, no claim).
