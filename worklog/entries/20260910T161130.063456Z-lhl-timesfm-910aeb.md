# TimesFM 3.0 GPU decode — var attention, single-pass forward

## Summary

GPU decode for TimesFM 3.0 on gfx1151: one non-autoregressive
forward pass (no AR loop, no KV cache), new var_attention kernel,
eps-parameterized qkv_norm_scatter, ReLU elementwise; all other
kernels reused from the 2.5 family. fp32 strict parity 1.1e-5 vs
the torch oracle; fp16 production gate max 0.42% of signal scale;
0.397 s on the metric workload — 3.36x faster than the torch fp32
reference on the same GPU.

## Context

TimesFM 3.0 tier-1 (contract/loader/CPU reference) landed on main
(98a6108e8); this branch (timesfm, fast-forwarded to main) adds the
GPU path. 2.5's GPU decoder (MODEL-TIMESFM.md) supplied the kernel
toolkit and the host/device split pattern.

## Changes

- hipengine/kernels/hip_gfx1100/timesfm3/timesfm3.{hip,py}: new
  family timesfm3 — var_attention (non-causal over the variate axis,
  per-(b,v) leading-mask counts, fully-masked rows -> zeros, internal
  sqrt(D) score scale; fixed a per-warp LDS weight race found by a
  standalone numpy smoke), qkv_norm_scatter (2.5's fused kernel with
  runtime eps for nn.RMSNorm's finfo-eps), relu elementwise.
- hipengine/runtime/timesfm3_decode.py: TimesFM3GPUDecoder — host
  preprocessing/postprocessing mirror the numpy reference (reusing
  cpu_reference helpers); device forward = tokenizer RB + 20 mixing
  layers (seq attention over B=batch*variates with a single scratch
  cache pair reused across layers; var attention; ReLU FFN) + biased
  output head. q/k/v projections concatenated into one [3d, d] GEMM
  weight. SDPA sqrt(D) score scale folded into the K-side norm weight
  (works for both precisions, no kernel changes). Var q/k get
  head_rmsnorm + head_perdim via the rows-trick (B=rows, N=1).
- scripts/timesfm3_gpu_bench.py: --metric (b8 v3 ctx8192 h512) and
  --check (fp32 atol 1e-4 + fp16 2%/0.5% gates on both fixtures).
- tests/test_timesfm3_gpu_decode.py: fp32 strict parity + fp16
  production gate on base+edge fixtures, precision validation.
- MODEL-TIMESFM3.md: per-model record.

## Validation

- fp32 vs torch oracle: base 8.3e-6, edge 1.1e-5 (atol gate 1e-4).
- fp16 vs oracle: base max 0.41%/mean 0.12% of signal scale; edge
  max 0.22%/mean 0.05% (gate 2%/0.5%).
- Metric (fp16): 0.397 s; torch fp32 same GPU 1.334 s (3.36x);
  hipEngine fp32 3.39 s (strict fallback). rocprofv3 --kernel-trace:
  all new kernels run under expected names with plausible durations
  (qkv_norm_scatter_eps, var_attention, relu; reused 2.5 kernels and
  rocBLAS GEMMs). Breakdown recorded in MODEL-TIMESFM3.md.
- pytest: 5 GPU tests green; full timesfm bundle (2.5 GPU decode +
  both models' contract/CPU tests) 26 green; 2.5 bench --check green
  (shared kernels unaffected).

## Debugging notes (for the record)

Three real bugs found and fixed en route: (1) k_ln scaled upload
left float64 bits reinterpreted as float32 (garbage norm weights,
NaN); (2) the SDPA sqrt(D) scale was missing entirely — folded into
the K-side norm weight; (3) var q/k skipped QK norms + per-dim
scale (the standalone kernel smoke fed pre-normalized inputs and
passed). Debug-script broadcast bugs ((1,5)[:,None] aligning to the
wrong softmax axis) also produced two false alarms; layer-by-layer
A/B against the CPU reference localized each real issue.

## Decisions

- Reuse 2.5 kernels everywhere the ops coincide; only three new
  kernels. The fully-masked-row semantics differ between the reused
  kernels (2.5 uniform 1/S) and the oracle (zeros) only at
  leading-pad rows, which decode() slices away — verified by
  end-to-end parity on both fixtures.
- Single scratch cache pair shared across layers (no AR loop).
- fp32 strict path stays slower than torch fp32 at prefill scale
  (naive per-row attention kernel); it is a rollback path only.
