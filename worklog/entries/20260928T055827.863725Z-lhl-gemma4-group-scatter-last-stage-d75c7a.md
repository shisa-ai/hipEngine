# both projections and the gather are cleared leaving the group-scatter as the only unexercised stage

## Summary

Two more stages are cleared, and the set is now complete enough to name the
remaining one by elimination.

**The down projection** was the gap in `20260928T055743`: that probe tested only
`experts_gate_up_proj`. Driven the same way -- hand-built `expert_start` and
`sorted_experts`, `compact_rows=2` against `=4` with the same leading rows -- it
is bit-identical across the two routes:

```
down_proj compact=2: route=selected_gemv   (reference) |row0|=119.4323
down_proj compact=4: route=grouped_prefill row0 vs compact=2 rel=0.00000000 max_abs=0.0000
```

**The gather** was cleared by reading it, not by probing it.
`qwen35_moe_gather_packed_hidden_kernel` computes

```cpp
const int64_t row  = idx / hidden_size;
const int64_t lane = sorted_lanes[row];
const int64_t token_idx = lane / top_k;
if (token_idx >= 0 && token_idx < tokens) {
  value = hidden_states[token_idx * hidden_size + col];
}
```

With lanes token-major (`lane = token * top_k + slot`), `lane / top_k` is the
token, which is the correct mapping. The bounds check zeroes only out-of-range
lanes, and the host wrapper sizes the grid from `total_elements = lanes *
hidden_size`, so the covered range is exactly the compact buffer.

## Why the hand-built probe is not a substitute

The direct probes supply `expert_start` and `sorted_experts` by hand: one
expert, all lanes, compact order equal to row order. That is the *correct*
routing for the single-expert input, and the projections agree on it. It is not
a test of whether the group-scatter *produces* that routing.

The single-expert full-call probe (`20260928T055550`) is the evidence that it
does not, or at least not identically at both lane counts: with every lane on
expert 0, the full call still differs between `lanes=2` and `lanes=4` by 0.9 to
1.9 percent, while the same routing supplied by hand does not.
