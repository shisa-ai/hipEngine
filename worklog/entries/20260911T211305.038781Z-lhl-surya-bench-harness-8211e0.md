# Surya benchmark harness: corrected measurement, frozen workload suite

## Summary

`scripts/surya_perf_compare.py` was reporting numbers that could not support the
decisions being made from them. Three separate defects, all confirmed by reading
the code before changing it:

1. **Stage timings excluded GPU time.** `_timed(prefill_only)` returned before
   the `sync()` on the following line, so a stage measured kernel *launch* time.
   The hipEngine lanes happened to be sound only because `_logits_last()` calls
   `device_synchronize()` before its readback; the torch lanes were not.
2. **Decode was derived by subtraction.** `t_decode = t_generate - t_prefill`
   subtracted two separately timed runs that were measured differently. This is
   what produced the retained "55.5 vs 68.2 tok/s" comparison. The torch
   `t_prefill` in that comparison was a 1.613 s first-call autotuning artifact,
   so the subtraction inflated torch's decode by ~2.3x. Measured directly,
   torch's decode is ~24 tok/s, not 68.2.
3. **The decode stage was not isolated across repeats.** A decode loop advances
   the KV cache and the sequence length, so a repeat that started where the
   previous repeat stopped measured a different computation. `rect` (3 tokens)
   was reported at 1.143 s because the repeats ran 64 steps against stale state
   instead of 3. Worse, `decode_tok_per_s` divided the *end-to-end* token count
   by that corrupted stage time, so the two halves of the ratio came from
   different runs.

The workload was also a single 256x256 page and 64 tokens, which `AGENTS.md`
forbids tuning on.

**The corrected measurement reverses the retained claim.** The rollup said
hipEngine's decode "still trails torch generate" at 55.5 vs 68.2 tok/s, and
before that "decode 32.9 vs 69.2 tok/s, 2.1x slower". Both came from defect 2.
Measured directly over a 12-case suite, hipEngine's decode is a median 2.25x
*faster* than torch's on the same host. The end-to-end comparison was already
correct (that lane's readback synchronized), which is why only the decode column
was wrong.

## Changes

### Measurement (`scripts/surya_perf_compare.py`)

- `_stage(fn, sync)` synchronizes on **both** sides of every timed region, on
  every lane. The leading sync is what makes a stage mean this stage only; the
  trailing sync is what makes it kernel time rather than launch time.
- `_series` discards one warmup and returns every repeat's output, so callers
  can check that repeats agree instead of assuming it.
- `_series_with_setup(setup, fn, ...)` re-runs `setup` untimed before each
  sample. Used for decode on all three lanes, so every repeat times the same
  loop from the same post-prefill state.
- Decode is now **timed directly, never subtracted**, and every lane runs the
  same explicit pipeline (vision, one prefill forward returning logits plus KV
  state, then a manual greedy loop). No lane uses a library's fused `generate`,
  so the decode stage is the same operation everywhere.
- The artifact records a full distribution (min/median/mean/max/stdev) per stage
  and for e2e, plus host identity, git revision/dirty flag, the exact command,
  and the suite definition.

### Validation

- Full-sequence equality against the oracle, with `first_divergence` recorded —
  never a prefix match.
- `termination` (eos vs length) is recorded and `e2e_agrees` asserts the
  end-to-end run produced the same ids as the timed decode stage, so the ratio
  cannot describe a different output than the one reported.
- `decode_repeatable` asserts every decode repeat produced identical ids. This
  is the check that catches defect 3.
- A per-case task check derived from what the oracle actually emits.

### Workload suite

`scripts/surya_bench_pages.py` adds seeded, byte-reproducible fixtures for
Japanese, mixed script, dense small text, a ruled table, a blank page, a
degraded scan, and a block-heavy long page. `scripts/surya_oracle_greedy.py`
gains a `bench` case that captures their torch fp32 reference into
`oracle_bench.json`. The suite is 12 cases split into a `tuning` subset and a
disjoint `heldout` subset, both recorded in the artifact.

Budgets are set so every page reaches EOS rather than its cap: at 128 tokens the
Japanese, mixed, dense and scan pages all hit the limit, which would have gated
only their first 128 tokens. The scan page needs 504.

`format` is per case because Surya returns layout JSON for some pages and
HTML-ish markup for others (`<div><img/></div>` for the blank page), which a
hardcoded expectation would get wrong in both directions.

`scripts/surya_oracle_greedy.py` also had a latent bug: `_greedy_from_page`
called `.numpy()` on tensors, which only worked because it had only ever run
with `--device cpu`. Fixed with `.cpu()`.

## Validation

`benchmarks/results/2026-09-11-gfx1151-surya-suite-baseline.json`, 12 cases x
(hipengine_gpu, torch_cuda) x 3 runs on gfx1151, all 24 rows PASS with
`decode_repeatable` and `e2e_agrees` true:

| | hipengine_gpu | torch_cuda | ratio |
| --- | --- | --- | --- |
| decode tok/s | 51.7 - 55.4 | 20.4 - 26.6 | median 2.25x |
| decode spread | 0 - 3% | 1 - 2% | |

The ratio holds across every document type (2.03x - 2.60x); the widest is the
blank page, whose 3-token decode makes its absolute variance meaningless.

The explicit torch decode loop was checked against the library path before being
trusted as the comparison basis: 28.5 tok/s against `model.generate`'s 29.6 on
the same case, and both reproduce the oracle exactly.

Tests:

- `tests/test_surya_bench_harness.py` (22 tests): the isolation guarantee using
  a stateful counter, warmup discarding, prefix-vs-full rejection, e2e
  disagreement, format-vs-oracle consistency, split disjointness, and that a
  lane with no samples does not abort the run.
- RED for the isolation fix: with `_series` restored in place of
  `_series_with_setup`, `rect` reports decode 1.143 s instead of 0.055 s,
  `FAIL (length)` instead of `PASS (eos)`, and `e2e_agrees` false.
- RED for the admission-ordering fix in the preceding unit was confirmed the
  same way.
- Full Surya bundle + rocblas on gfx1151: 135 passed.

Not addressed here:

- `torch_cpu` is no longer in the default lane set. It runs at ~0.5 tok/s and,
  because the decode series re-runs prefill for isolation, costs ~80 s per
  prefill on a 1024x1024 page. It remains available via `--lanes` for
  oracle-path work. `hipengine_cpu` is likewise expensive on long outputs
  (~3.2 tok/s) and is not in the retained artifact.
- The production numerical gate (mean/p95/p99/max KL, category top-1, BF16
  relative, task quality) that `docs/MODEL-SURYA.md` requires for arithmetic
  changes is still not implemented. This unit fixes measurement and workload
  coverage; it does not add the KL gate.
