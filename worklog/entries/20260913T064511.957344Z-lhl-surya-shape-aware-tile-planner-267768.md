# Shape-aware tile planner: the cap is a small-grid correction, not a ceiling

## Summary

`plan_score_tiles` no longer caps the query block unconditionally. The shape
envelope `max(128, ceil(rows / 32))` rows (rounded down to a multiple of 32) is
consulted only while the byte budget alone would leave the grid in one or two
tiles (`SHAPE_TILE_CAP_MAX_TILES = 2`, i.e. `block * 2 >= rows`); where the
budget already splits the grid further, its own width is kept.

That is exactly where the sweeps separate, and it is one rule for both paths, so
`test_prefill_and_vision_share_one_planner` still holds: no family flag, no
per-path branch, no dispatch change.

- **The cap helps at one or two tiles**, because a tile wider than the grid
  needs starves the batched GEMM of output tiles: at 1024 patches the budget
  admits the whole dense matrix (193.54 ms) against 135.52 ms at 128 rows, and
  at 4096 patches it admits 2730 rows (1123.42 ms) against 874.38 ms at 128 rows.
- **At four or more tiles the budget's own width is at least as good**: 6400
  patches takes 1747 rows (2004.85 ms at 4 tiles) against the cap's 192 rows
  (2125.18 ms, 5.7% slower); the A4 page takes 320 rows (43318 ms) where the
  cap's 1073 rows never binds; and the text prefill's curve is monotone in the
  tile count, so the cap cost it 3.0% at 16384 tokens and 2.1% at 8580.

**Effect on the default path, measured on a quiet gfx1151**: the text prefill
keeps the byte budget's width — 16384 tokens 512 -> 1024 rows, 17.170 -> 16.752 s
pooled (2.4%); 8580 tokens 256 -> 1952 rows, 7.543 -> 7.436 s (1.4%) — and the
6400-patch vision grid keeps its 1747 -> 1728 rows, 2125.18 -> 2004.85 ms (5.7%).
The A4 page (320 rows), the 65536-patch ceiling (160), and the 256/1024/4096-patch
grids (128) are unchanged. The text prefill's peak rises 4.75 -> 5.21 GB for the
page and 6.39 -> 6.66 GB at a full prompt, which is the memory the budget was
already granting.

## The rule

```
block = budget_bytes // (heads * rows * 4)      # widest tile that fits
if block * SHAPE_TILE_CAP_MAX_TILES >= rows:    # the budget leaves <= 2 tiles
    block = min(block, max(SHAPE_TILE_ROWS, ceil(rows / SHAPE_TILE_DIVISOR)))
block -= block % SHAPE_TILE_MULTIPLE            # whole 32-lane wavefronts
block = min(block, rows); block = max(block, 1)
```

`block * 2 >= rows` is `ceil(rows / block) <= 2`, so the condition is a tile
count rather than a width, which is what the evidence is stated in. Every
measured point:

| grid (heads) | budget block | tiles | cap? | block | evidence |
| --- | ---: | ---: | :---: | ---: | --- |
| 256 patches (12) | 65536 | 1 | yes | 128 | 28.07 ms at 2 tiles |
| 1024 patches (12) | 10922 | 1 | yes | 128 | 135.52 vs 193.54 ms dense |
| 4096 patches (12) | 2730 | 2 | yes | 128 | 874.38 vs 1123.42 ms budget |
| 6400 patches (12) | 1747 | 4 | no | 1728 | 2004.85 ms vs the cap's 2125.18 |
| 34320 patches (12) | 325 | 108 | no | 320 | 43318 ms, unchanged |
| 65536 patches (12) | 170 | 410 | no | 160 | 161.4 s estimate, unchanged |
| 1024 tokens (8) | 16384 | 1 | yes | 128 | unchanged |
| 5792 tokens (8) | 2896 | 2 | yes | 160 | unmeasured boundary |
| 5793 tokens (8) | 2896 | 3 | no | 2880 | unmeasured (the 3-tile band) |
| 8580 tokens (8) | 1955 | 5 | no | 1952 | 7.436 s pooled, was 7.543 at 256 |
| 16384 tokens (8) | 1024 | 16 | no | 1024 | 16.752 s pooled, was 17.170 at 512 |

Under the default 512 MiB budget the vision crossing is at 4730 patches
(`rows <= sqrt(budget / (2 * heads))`), and below it `rows / 32` is at most 148,
so the divisor only matters for a raised budget. Three tiles is measured on
neither path and is recorded in `docs/REFACTOR.md`.
