# X4 half-run: the image inventory, and two routes closed

## Summary

Iteration 22 read release notes and refused to conclude anything from them.
This is the half that decides: the `0.14.2b` `gfx110x` bundle downloaded,
digest-verified, and listed, then set against the vendored `0.11.2b` images.
Both questions X4 was created to answer come back **no**, and the negatives
are the value — they retire work that looked promising.

## The two answers

| field | vendored `0.11.2b` (12 images) | upstream `0.14.2b` gfx110x (396 images) |
| --- | --- | --- |
| head dim | one span, `@16_256` | one image per dim: 16, 32, 48, 64, 80, 96, 128, 160, 192, 224, 256 |
| **head dim 512** | **absent** | **absent — max is 256** |
| `CAUSAL_TYPE` | **{0, 3}** | **{0, 3} — identical** |
| dtypes | bf16 only | bf16, fp16, fp32 |
| also varied | `PADDED_HEAD`, `ENABLE_DROPOUT`, `BIAS_TYPE` | same three, now split per head dim |

**1. P2 option (b) — an AOTriton head_dim-512 image — is closed for
AOTriton as a whole, not merely for the vendored copy.** The punchlist had
it closed on vendored evidence only, which left "upgrade AOTriton" sitting
there as an untaken ticket. It is now taken and negative: across every
released gfx110x image set, `BLOCK_DMODEL` tops out at 256. For head_dim
512, **P2 option (a) — porting llama.cpp's `flash_attn_tile<512,512,4,8>`,
measured at 6.7 ms against hipEngine's 39.2 — is the only route left.**

**2. P1 gains nothing from upgrading.** `CAUSAL_TYPE` is `{0, 3}` in both
versions — no new causal or window type appeared upstream. And this
inventory was never capable of settling P1 in the first place: window
alignment is host-side (`left_window = window - 1`), a property of the
launch code, not of which image gets selected. Iteration 22 flagged that
release notes could not answer it; the image list confirms the same limit
from the other side. P1 still stands or falls on reading 0.14's host source
or on running its own four-mask comparison — `rows=512 keys=1536
window=128`, `top_left_window` matching at maxabs 0.0078 while the
alternatives miss.

## What 0.14 does add, and why it is not the point

fp16 and fp32 query images where 0.11 shipped bf16 only, and the single
`16_256` span split into per-head-dim images. Real changes, neither of which
touches P1 or P2. Worth stating precisely because the temptation with a
three-release gap is to assume capability moved with it. Here the version
number moved and the two dimensions we care about did not.
