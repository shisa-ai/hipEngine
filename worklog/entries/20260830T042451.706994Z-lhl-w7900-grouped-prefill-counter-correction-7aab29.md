# W7900: the grouped-prefill promotion's group counters were mis-transcribed, and worse than I remembered

## Summary

`20260830T032618.679523...-3a02c8` (the grouped-prefill promotion, immutable) records the mechanism
evidence as `native_full_prefill_groups` = 10 at C4 and C8, 0 at C1. The 0 at C1 is right. The 10 is
not: the promotion's own `source_packet` (/tmp/he-c1c8-cap8/c1c8-cap8.json, 36 MB, still present)
carries per-prompt counters under `cells[].ar.resident_observability.routes.counts`, and they are
39-56 at C4 and 151-176 at C8. The published promotion is unaffected in every direction - the real
numbers say the mechanism fires far more than the note claimed - but a wrong number in the evidence
chain is still a wrong number, so the artifact and the changelog line are corrected and this entry
supersedes the value in the immutable one.

## Changes

- Artifact `grouping_directly_observed` now reports per-width min-max over all 10 prompts plus the
  exact JSON path, and carries an explicit `correction` field pointing here.
- `benchmarks/CHANGELOG.md` dated line for the promotion amended in place, same reason as above.
- Nothing else cites the value. `20260830T034246...-9d1c32` also names the counter, but about a
  unit-test expectation of 0 in a serial-prefill scenario, which is a different and correct claim.

## Validation

Min-max of `native_full_prefill_groups` and of `native_full_prefill_rows`, all 10 prompts per width,
read from the source packet:

| width | groups (min-max) | native full-prefill rows (min-max) |
| --- | --- | --- |
| 1 | 0-0 | 3-22 |
| 2 | 2-12 | 30-64 |
| 3 | 16-35 | 75-132 |
| 4 | 39-56 | 148-216 |
| 5 | 60-79 | 235-330 |
| 6 | 85-110 | 354-456 |
| 7 | 116-145 | 483-616 |
| 8 | 151-176 | 648-784 |

Groups are exactly 0 at C1 - one request cannot group - then rise monotonically with width, which
is the behaviour the capability is supposed to have and is much stronger evidence for it than the
single mis-transcribed 10 was. The counters live in the `ar` arm under
`resident_observability.routes.counts`; the place I first looked, `cells[].ar.telemetry.route_counters`,
is where the C1-C8 AR promotion keeps *its* counters and does not carry this key here, which is how
a plausible-looking number survived review.

## Next

- Any future promotion that cites a counter should record the JSON path next to the value, the way
  the counter-forged K3 row now does. Two of today's three evidence defects (this one, and the
  earlier forged `baseline_1864`) would have been caught at writing time by a path being quoted.
- The d1 packets (/tmp/he-d1-cap8, /tmp/he-d1-post) carry no `resident_observability` block at all,
  so a one-token run cannot be used to show grouping; only the C1-C8 packets do. Worth knowing
  before someone goes looking for the counter in a d1 packet.
