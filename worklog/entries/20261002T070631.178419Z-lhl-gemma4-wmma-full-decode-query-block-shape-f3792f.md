# the GQA-aware decode shape was never blocked, the analysis held the wrong row count fixed

## Summary

The full-layer decode now launches a query-block shape built for it, and each KV
band is read **once** instead of four times. Measured on one layer with
identical buffers, both arms on the shipped key split: **19.04 to 6.24 ms at
262,144 keys (3.05x)**, 2.46 to 1.22 at 32,768, 0.73 to 0.65 at 8,192. End to
end at a 32,704-token context in a same-session paired A/B, **21.74 to 28.59
tok/s (1.315x)**. The decode shape's teacher-forced gate passes at `kl_max`
1.22e-3 against 0.05 with 100% top-1, and the prefill shape re-gates against its
own frozen baseline at **`kl_max` exactly 0.0**.

**The previous entry in this series was wrong, and the reason is worth keeping.**
It concluded the GQA-aware shape "does not fit in shared memory" from
`kGqaHeads` 4 needing 81.25 KB against a 64 KB budget. That arithmetic was
correct and the conclusion did not follow: it held `kQueryRows` at 16, which is
the *prefill* block width, for a case that has **one query row**. The Q tile is
`kColumns * kQStride` and `kColumns` is `kQueryRows * kGqaHeads`, so the row
count is half the product — and a decode's row count is the one thing that is
free to change. At two rows and eight heads the tile is 16.2 KB and the kernel
is 32.5 KB.

## Changes

- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention_prefill_wmma_full.hip`:
  `kQueryRows`, `kGqaHeads`, the launcher symbol and the device kernel's name
  became build-time parameters with the prefill values as defaults. The kernel
  name carries the shape because it is in an anonymous namespace and the
  launcher symbol does not appear in a kernel trace, so the name is the only
  thing that can distinguish the shapes there.
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention_decode_wmma_full.hip`
  (new): the same source included with the decode shape's macros defined. One
  source, two objects, two cache entries.
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention_prefill_wmma_full.py`:
  `WmmaFullShape` names a shape's geometry and its LDS and thread counts as
  properties of the build rather than as a model of it; `shape_for_tokens`
  selects; the planner and the workspace sizing take the shape.
- `tests/test_unit_gemma4_attention_wmma_slices.py`: 23 cases, up from 12, now
  covering shape selection at the boundary and both shapes' LDS arithmetic.
- `scripts/gemma4_teacher_forced_gate.py`: `--wmma-full-shape`, a third
  independent pin, and the split observer records which shape ran.

## Validation

- Kernel A/B, one layer, alternating repetitions, median, identical buffers and
  arguments, both arms on the shipped split: 262144 keys 19.04 -> 6.24 ms
  (3.05x); 32768 2.46 -> 1.22 (2.02x); 8192 0.73 -> 0.65 (1.12x). Against its
  own unsplit walk the decode shape is 11.53x at 262,144 keys. NaN placement
  equal; the split-vs-whole delta is bit-for-bit the same as the prefill shape
  reports, which is what you expect when the shape reads the same K/V.
- End-to-end A/B through `LLM.generate_detailed`, arms alternated, decode
  isolated by differencing two `max_tokens`: 46.0 against 35.0 ms/token,
  **1.315x**.
- Teacher-forced gate, 527 rows over keys 15857-16383: kl_mean 5.04e-6,
  kl_p95 1.25e-6, kl_p99 1.86e-5, kl_max 1.22e-3 against 0.05, top-1 100%, zero
  flips. `observed_wmma_full_split` records `shapes [2]` and 64 slices on all
  2,635 plans, so the arm is not the vacuous self-comparison.
- **The prefill did not move**, which is the thing that could have gone wrong:
  1250/1234/1223 tok/s prefill and 28.38/28.71/29.82 decode at 512/128 against a
  recorded topline of 1242/28.92, and the prefill shape re-gated against the
  split unit's frozen whole-walk baseline with the same pin it was frozen with
  gives **`kl_max` exactly 0.0**.
- 573 gemma4 tests pass, including all 24 pre-existing parity tests;
  `test_one_token_decode_matches_the_strict_decode_kernel` now exercises the
  decode shape and still matches the strict kernel.
- rocprofv3 kernel trace names `gemma4_attention_decode_wmma_full_kernel`.

## Next

- A **correction to the split unit's artifact**, recorded there rather than
  rewritten: it said the walk moves 537 MB per layer against 134 MB unique. It
  is **4.295 GB against 1.074 GB**, a factor of eight. That does not change the
  split's verdict and it does explain it — at 4.295 GB in 19.04 ms the split
  walk was at **225.6 GB/s against a measured 238.5 GB/s pure-read roofline**,
  up from 73.5 GB/s at 8 blocks. The roofline was measured with a dedicated
  read-only kernel over 4.295 GB, flat from 128 to 4096 blocks.
- The decode shape now moves the unique band in 6.24 ms, which is **172 GB/s**
  against that 238.5 GB/s roofline. The redundancy is gone; what is left is that
  a block reads 1024 of every 2048 bytes, one KV head's row out of a two-head
  record, so consecutive 64-byte sectors are half-used by any single block. That
  is not a shape problem and another shape will not fix it.
- The end-to-end A/B saved 11.0 ms per token where the kernel A/B predicts 6.2.
  **The measured saving is larger than the prediction and this is not
  explained.** The kernel A/B is the primary evidence and the end-to-end pair is
  reported as it was measured.

## Open question

- A `rocprofv3 --pmc` attempt to measure the walk's DRAM traffic directly is
  recorded as a **failure, not a result**. The counter units calibrate exactly
  against a known workload (`GL2C_MC_RDREQ_sum` x 64 B reproduces a pure-read
  probe's 4.295 GB to 0.0 percent), but against this kernel it reports 574 MB
  for the split walk and 537 MB for the unsplit one — the same figure for a
  3.07x difference in time, and less than the 1.074 GB the walk must touch. It
  does not scale with block count, so it is not counting the walk. The roofline
  comparison is what the traffic argument rests on instead, and it is weaker
  evidence than a counter would have been.
