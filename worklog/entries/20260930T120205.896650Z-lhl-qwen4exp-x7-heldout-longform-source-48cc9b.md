# X-7's heldout blocker is open for the right reason, and the long-form source it needs already exists

## Summary

`X-7` (missing qualification evidence for the promoted 16-47 scope) is the gate
that must close before the admitted scope is extended, and its first blocker is
category-heldout numerical evidence. The ledger recorded that blocker as
unmeasurable because the admission suite's prompts are too short to reach the
route's row floor.

I checked whether that is a genuine row floor or a proxy artefact, and found it
genuine. I also found the missing input already in the tree.

## The blocker is held open for the right reason

The suite's longest prompt is **71 tokens** against `dense_wide`'s **257-row
floor**, so the route declines and the run is a control.

I did not take the floor on trust. `_heldout_coverage` compares
`longest_prompt_rows` against `min_engaging_rows`, and `fixture_rows` is
`prompt_tokens` from the fixture - a proxy. So I traced what the route's guard
actually sees:

- The floor is read from the dispatch guard: `_q8_dense_wide_dispatch`'s
  `rows <= 256` (`scripts/execution_profile_q8_wmma_prefill_layers_gate.py:102`).
- `rows` at that guard is `len(tokens)` - `laguna_gguf_runner.py:5059` in
  `_execute_rows`, reached through `_run_layer_rows` -> `_run_dense_ffn_rows` ->
  `launch_gguf_linear(..., rows, ...)`.
- It is **not** the scratch row count. `allocate_scratch` sizes owners at
  `min(chunk_size, max(768, prompt_tokens + 1))`, which is why chunk 1024 and
  4096 are identical at p512 - but that is allocation, not dispatch.

So a 71-token prompt reaches the guard as 71 rows and genuinely declines.
**`prompt_tokens` is a faithful proxy here and the blocker is real.** The gate's
own module note records that this check already produced a false *refusal* once
(a since-removed route's 256-row floor applied to the f16 WMMA route, whose floor
is 2), so the check is worth re-verifying rather than assuming - and this time it
is correct.

## The missing input already exists

`benchmarks/prompts/qwen4exp-natural-long-tasks-v1.jsonl` carries four natural
long tasks, **one per category, all above the floor**, measured through the
retained `build_chat_prompt` builder rather than estimated:

| case | category | tokens | vs 257 floor |
| --- | --- | --- | --- |
| `long_code_booking_merge` | code | 438 | 1.70x |
| `long_general_en_release_decision` | general_en | 508 | 1.98x |
| `long_general_ja_retention_review` | general_ja | 424 | 1.65x |
| `long_mixed_ja_en_acceptance` | mixed_ja_en | 512 | 1.99x |

It is disjoint from the canonical 12-case fixture (which draws on
`mtpbench-code-general-ja.jsonl`) and is already consumed as a longform gate
suite by the `HC-1` GR staged gate.

I measured the token counts rather than estimating them because a characters/4
estimate is badly wrong for Japanese - it put `long_general_ja_retention_review`
at ~188 tokens, below the floor, when the real count is 424. That single
estimate would have led to the opposite conclusion for one of the four
categories.

## Why this is not an in-place fixture edit

The admission suite is **shared**:
`scripts/build_qwen4exp_admission_suite_fixture.py` records that the same 18
prompts are what `scripts/qwen4exp_layer2_profile_gate.py` and the 2026-08-16
threshold calibration consume. The gate also hardcodes both
`ADMISSION_FIXTURE_SHA256` and the expected case-id set.

Extending it in place would change a shared fixture and invalidate every artifact
citing that hash. The long-form protocol belongs in a **sibling** fixture with
its own coverage record - which the gate's `category_heldout` structure already
anticipates, since it produces a separate record that can never set the canonical
`complete` flag.

That sibling fixture and its gate wiring are the next unit, not this one. This
entry establishes that the work is well-posed and names the input.
