# gemma4 gfx1151: co-scheduling the KV band readers, and refuting the L2 hypothesis behind it

## Summary

The WMMA full-layer attention kernel's grid axes are reordered so `gqa_tile` is
the fastest-varying axis. `gqa_tiles` blocks read the *same* KV band -- the band
is read once per `(query_tile, kv_head, gqa_tile)` -- and at ~50 KB of LDS per
block only about one block per CU is resident, so whether they run together is
decided entirely by launch order. Previously the four readers of one band sat 32
blocks apart; now they are adjacent. The change is bit-identical by construction
(only block order moves, not arithmetic) and is worth **2.7% at 262144 keys**.

**The hypothesis this was written to test is refuted, and that is the more useful
result.** The expectation was that co-scheduling the readers would let L2 serve
three of the four redundant reads. It does not. A direct test shows the redundant
traffic is not L2-served even when the whole working set is cache-resident, which
means the redundancy is **irreducible in this kernel** and the only remaining
lever on the walk is fewer bytes per key (KV quantization).

## Why the traffic is redundant, and why ordering cannot fix it

Each KV band is read once per `(query_tile, kv_head, gqa_tile)`. The traffic
floor is `tokens * keys * 32768 / kColumns` bytes: `kColumns` is capped at 32
because the Q tile must stay in LDS (64 columns needs 83 KB against a 64 KB
budget, and holding the Q tile in VGPRs instead needs 512 values per lane). At 32
columns each `(row, key)` pair reads 1024 bytes where 256 would suffice with
perfect head sharing -- 4x redundant.

Measured against depth, and against the 238.5 GB/s DRAM roofline measured by the
roofline kernel on the same device:

| keys | ms | effective GB/s | % of roofline |
| --- | --- | --- | --- |
| 2048 | 3.675 | 292 | 122% |
| 262144 | 551.3 -> 536.3 | 256 | 107% |

The kernel is at the roofline. There is no compute headroom being left unused;
the cost is bytes moved, and the bytes are 4x what the algorithm needs.

**The 2048-key row is the refutation.** At 2048 keys the entire band is
2048 x 2048 B = **4.2 MB** and fits in L2. If co-scheduling worked, the DRAM
traffic there would collapse to the band size and the rate would be set by L2
bandwidth, far above 238.5 GB/s. Instead it reaches **122%** of the DRAM
roofline -- so roughly 18% of the redundant traffic is L2-served and 82% goes to
DRAM even when the entire working set is cache-resident. Putting the readers next
to each other is not sufficient.

## Changes

- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention_prefill_wmma_full.hip`:
  grid is now `dim3(gqa_tiles * slices, query_tiles, num_kv_heads)` for both the
  walk kernel and the combine kernel, with the decompositions matching. The axis
  comment records the measurement, the win, and the refuted L2 hypothesis.

## Validation

- `tests/test_gpu_gemma4_attention_prefill_wmma_full.py`: 27/27, exit 0. Bit-identical
  against the strict kernel, as required -- no arithmetic changed.
- Long-context ladder, 262144 keys: 551.3 -> 536.3 ms (-2.7%). Also -4.2% at
  131072, -3.2% at 65536, -8.4% at 16384.
- `rocprofv3 --kernel-trace`: the walk and combine kernels launch in the new
  order, so the intended path is the one that ran.

## Next

- The walk is at the roofline and its redundancy is not recoverable by ordering.
  **KV quantization is the only remaining lever** -- int8 would halve the bytes
  per key for up to 2x on the ~705 s of walk time -- and gemma4 currently refuses
  it outright ("only BF16 KV storage is implemented"). That is a real project with
  a quality tradeoff, not a tuning change.
- The decode's attention walk sits at ~69% of the roofline rather than the
  prefill's 105-118%, so the decode has headroom the prefill does not. The two
  structural suspects are the decode shape's 64-thread blocks (2 warps per block,
  one block per CU at 32.5 KB of LDS) and the 64-way split's combine pass.
