# Gemma 4: route the Q5_K expert layer through the grouped row4 GEMV

## Summary

The other half of the dynamic-quant layer. Its expert gate/up weights are Q5_K,
and Q5_K has no grouped *prefill* family at all — the only Q5_K prefill kernels
that exist are WMMA and MMQ, both of which change the association — so it ran the
per-row expert gather at 244.4 ms. It does have a grouped **GEMV** that reuses an
expert's weight rows across four rows instead of one, registered only under the
dense `linear` layer. Routing the MoE dispatch through it takes the projection
**244.4 -> 111.7 ms (2.19x)** and the 512-token prefill **3.238 -> 3.119 s
(1.035x)**, bit-exactly.

Measured before building: at 128 experts / 2816 -> 2816 fused / 4096 compact rows
the row4 kernel is **469.31 -> 154.08 ms (3.05x)** against the gather, which is
what justified the wiring work. That ordering mattered — the obvious cheap move
(a preference-list entry) does not work here, and only the measurement showed
that a route was worth adding at all.

## Changes

- `hipengine/kernels/hip_gfx1100/quant/gguf_k_gemv.py`:
  `register_gguf_k_gemv_kernels` also binds
  `selected_grouped_row4_gemv_bf16_bf16_out` under `moe_linear/gguf_q5_k`.
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_experts.py`: new
  `gemma4_project_experts_grouped_row4`, tried between the grouped prefill
  family and the per-row gather. Its launch ABI differs from the prefill family —
  a lane map plus separate source and destination row counts — so it is a
  dispatch step, not a preference-list entry; the compact layout makes the lane
  map the identity, so the launcher takes a null pointer.
- `tests/test_unit_gemma4_expert_route.py`:
  `test_grouped_row4_is_bit_exact_against_the_selected_gemv`, which asserts the
  dispatcher returns `grouped_row4` and compares bits at (2816, 2816) and
  (1408, 2816).

## Validation

- **Bit-exact before wiring.** A probe ran both kernels over the same buffers at
  the fused geometry (8 experts, counts [100, 0, 90, 40, 0, 82, 100, 100],
  identity lane map): **0 of 1,441,792 bf16 outputs differ**, including with a
  null lane map, which is what the route passes.
- **Isolated A/B.** One process, both kernels resolved, five timed launches per
  round, two interleaved rounds: gather 469.31 / 471.36 ms, row4 154.08 /
  154.97 ms.
- **Route.** The attribution harness over a real 512-token forward on two trees:
  `linear/gguf_q5_k/selected_gemv_bf16_bf16_out` 244.4 ms before,
  `moe_linear/gguf_q5_k/selected_grouped_row4_gemv_bf16_bf16_out` 111.7 ms after,
  with every other route unchanged within noise.
- **Public.** The same timing script in two git worktrees (one warm-up plus five
  timed forwards each, medians): 3.238 -> 3.119 s.
- **Tests.** 46 pass in the route file, 508 in the gemma4 bundle.
- **An in-process arm toggle does not work here**, and that is worth recording:
  `unregister` plus a pinned sweep generation still gets re-registered, because
  any *other* lazy registration bumps the generation and re-arms the sweep that
  binds this key. Both arms silently ran the same route, which is why the first
  A/B reported no difference. Two trees is the honest way to compare this one.
