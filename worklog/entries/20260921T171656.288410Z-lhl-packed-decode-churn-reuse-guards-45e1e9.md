# Pin packed-decode reuse guards against slot churn

## Summary

Readiness-checklist item: packed-decode graph reuse after cancellation, pool
growth, slot reassignment, and scale reallocation must not retain stale
pointers or another request's state. The churn cases were untested.

Investigation found **no defect**. The guards exist and are deliberate:

- `_sync_packed_decode_initial_state` (`hipengine/runtime/qwen35_gguf_runner.py:28640`)
  computes `can_reuse` only when the recorded session ids, the recorded
  session tuple, and the recorded per-slot positions all still describe the
  sessions being bound. Its comment names the hazard directly: reusing across
  a private-slot reuse "would attend over the wrong occupant's KV".
- `discard_packed_decode_state` (`:29060`) is the cancel path and clears every
  reuse token, including `_packed_decode_state_dirty`.
- `Qwen35GGUFPackedDecodeGraphKey` (`hipengine/runtime/gguf_packed_decode_graph.py:69`)
  is the binding signature and already carries every churn axis:
  `state_generations` (slot reassignment), `buffer_identity_sha256` (pool
  growth), and `kv_storage_layout` / `kv_scale_dtype` / `kv_scale_granularity`
  (scale reallocation).

The landed work is therefore regression coverage for guards that were correct
but unpinned.

### Correction to an earlier hypothesis in this session

An earlier pass recorded the MTP verify *bucket* key as a stale-binding defect,
on the grounds that `graph_bucket` (`hipengine/runtime/qwen35_gguf_mtp.py:1140`)
is keyed by the 4-tuple `("specdec2", batch.mode, batch.rows,
plan.execution_route)` at `hipengine/generation/qwen35_gguf_mtp2.py:3866`, which
carries no churn identity. **That was wrong and should not be re-chased.**

`TargetVerifyBufferOwner` (`hipengine/speculative/buffers.py:126`) holds only
per-cycle row metadata, per-cycle accept summaries, and named scratch. It holds
no KV page tables, payloads, mirrors, or scale planes; its pointers come from
the workspace via `reserve_tensor` and are stable by design. The bucket is
shape-keyed scratch, so pool growth and scale reallocation cannot invalidate it
and the 4-tuple is correct for that mechanism. The graph binding signature is a
separate mechanism, `Qwen35GGUFPackedDecodeGraphKey`, which does carry the churn
axes.

## Changes

- `tests/test_unit_gguf_packed_churn_reuse.py` (new): six CPU cases over the
  reuse guard, reusing `_sync_fixture` from
  `tests/test_unit_gguf_packed_kv_import_skip.py`.
  - same occupant continues -> imports nothing (positive control, so the
    rejection cases prove rejection rather than an inability to reuse);
  - reassigned private slot at the same position -> re-imports;
  - mismatched recorded session id -> re-imports;
  - same occupant, stale recorded position -> re-imports;
  - `discard_packed_decode_state` then the next round -> re-imports;
  - two-slot control: whole membership matching reuses nothing, then one
    changed member forces a full re-import.
- `tests/test_unit_gguf_packed_decode_graph.py`: added
  `test_packed_decode_graph_key_covers_pool_growth_and_scale_reallocation`.
  The scale axes were present in the `_owner()` fixture but never asserted, so
  case (d) had no coverage at all.
