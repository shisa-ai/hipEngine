# UD MTP width cells: c1 2.46x, c2 1.04x, c4 not a policy cell, c8 out of memory

## Summary

The U6 width question is answered, and the answer is that c1 is the only width
worth declaring for UD MTP on the default hardware. This is a measured result,
not a conservative default.

`scripts/gguf_mtp_c1c8_server_bench.py` on
`Qwen3.8-27B-UD-Q4_K_M.gguf`, canonical ten prompts, 24 output tokens,
`--generation2-diagnostic --mtp-scope-grant`, contract `ar_exact`:

| Cell | AR tok/s | MTP tok/s | MTP / AR | exact | engaged |
| --- | ---: | ---: | ---: | ---: | ---: |
| c1 K3 | 13.891 | **34.205** | **2.4624x** | 10/10 | 10/10 |
| c2 K2 | 30.102 | 31.359 | 1.0418x | 10/10 | 10/10 |

Both cells hold `ar_exact` on all ten prompts and conform the candidate budget,
so the widths are *correct*; c2 is simply not *useful*. Two requests in flight
raise the server path's own AR rate from 13.9 to 30.1 tok/s while MTP only
reaches 31.4, so the speculative advantage collapses from 2.46x to 1.04x.

**These are diagnostic rates, not the retained ones.** The AR arm here is the
server path (`/v1/completions`, blocking barrier-to-last-completion wall), while
the retained Phase 4 paired numbers come from the resident graph-replay leaf at
about 31.9 tok/s AR for the same artifact. The c1 2.46x here and the 1.37x
retained there are the same phenomenon measured against two different
denominators. Nothing in this entry replaces the paired artifact.

## The two cells that cannot be measured

**c4 is not a production physical cell.** `GGUF_SPECDEC2_MTP2_PHYSICAL_WIDTH_DEPTHS`
for `hip_gfx1100` declares `"production": ((1, 2), (1, 3), (2, 2), (8, 3))`.
The bench records the refusal verbatim: `cell (C4, K3) not in policy ((1, 2),
(1, 3), (2, 2), (8, 3))`. So the plan's "c1/c2/c4/c8" over-specifies for this
model family; c4 has no physical kernel cell to qualify, and adding one is kernel
work rather than a measurement.

**c8 is out of memory on the default hardware.** The c8 K3 cell is policy-
admitted and prompt-streaming-admitted for this geometry, but every request fails
with `HIP error 2: out of memory` at capacity 8 — at max-sequence-length 1024,
512 and 256 alike. Physical GPU1 is an RX 7900 XTX with 25,753,026,560 bytes of
VRAM and the UD artifact is 16,464,440,224 bytes, so eight concurrent requests
plus draft residency do not fit. This is a hardware-capacity blocker, not a
kernel or policy one, and it is why the retained C8-K3 evidence is on the plain
dense artifact rather than on UD.

## Consequence for the U6 envelope

`widths=(1,)` is now evidence-backed rather than a narrowing of convenience:

- c1: 2.46x on this protocol, 1.37x retained on the paired one — admit.
- c2: 1.04x — no material benefit, so an evidence row would buy serving
  complexity and a wider admission surface for noise.
- c4: no production physical cell.
- c8: does not fit in the default GPU's memory.

## Validation

- Commands, all on physical GPU1 (RX 7900 XTX, gfx1100):
  - `--widths 1 --resident-capacity 1 --candidate-budget 3 --generation2-diagnostic
    --mtp-scope-grant --correctness-contract ar_exact` → `complete`,
    `passed True`, no failure reasons.
  - `--widths 2 --resident-capacity 2 --candidate-budget 2 ...` → `complete`,
    `passed True`, no failure reasons.
  - `--widths 8 --resident-capacity 8 --candidate-budget 3 ...` at
    `--max-sequence-length` 1024 / 512 / 256 → `HIP error 2: out of memory` on
    every request, no artifact written.
- The scope refusal this flag removes was reproduced first and is quoted in
  `worklog/entries/20260912T213408.856669Z-lhl-ud-c1c8-scope-grant-51e8b8.md`.
