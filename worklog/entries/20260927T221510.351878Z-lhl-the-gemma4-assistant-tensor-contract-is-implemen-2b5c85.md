# The gemma4 assistant tensor contract is implemented and verified against the artifact
## Summary
First implementation unit for the objective's MTP item. The previous two
iterations produced the algorithm from llama.cpp's reference and the artifact's
own hyperparameters; this one turns that into code, and the code is checked
against the real 440 MB head rather than against a fixture.
## What landed
- `hipengine/loading/gemma4_assistant_gguf.py` (new): decodes the
  `gemma4-assistant` metadata into a `Gemma4AssistantConfig`, derives every
  expected tensor name and shape, validates an artifact against that contract,
  and fails closed with a named error on anything missing, unexpected or
  mis-shaped.
- `tests/test_unit_gemma4_assistant_gguf.py` (new): six tests, five synthetic and
  one against the real downloaded artifact.
## The contract, and the part of it that is not uniform
Four blocks of eleven tensors plus five globals is 49, and the shape table is
uniform **except for attention**, where the artifact mixes two kinds:
| block | `attn_q` | `attn_q_norm` | reading |
| --- | --- | --- | --- |
| 0, 1, 2 | `(1024, 4096)` | `(256,)` | 16 heads x `key_length_swa` 256 |
| 3 | `(1024, 8192)` | `(512,)` | 16 heads x `key_length` 512 |
So the last block is full attention and the preceding three are sliding-window,
which is what `attention.sliding_window_pattern` describes. Encoding this
generically rather than hard-coding 4096 matters: a head with a different
pattern or head count would otherwise validate against the wrong widths.
Two more properties the module encodes rather than assumes:
- **No `attn_k` and no `attn_v` anywhere.** `attention.shared_kv_layers` equals
  the block count, so the head attends against the backbone's cache and owns
  none. A test asserts the contract declares no key or value tensors, so a future
  artifact that did would fail loudly rather than silently.
- **`nextn.pre_projection` input is `2 * n_embd_backbone`**, derived rather than
  written down, because that width is the concatenation the forward performs.
## Verification
```
python -m pytest tests/test_unit_gemma4_assistant_gguf.py -q
......  [100%]   6 passed
```
The load-bearing test is `test_real_artifact_satisfies_the_contract`, which scans
`/models/gguf/gemma-4-26B-A4B-it-GGUF/mtp-gemma-4-26B-A4B-it-Q8_0.gguf` with the
engine's own `scan_gguf` and asserts the validation passes with **no missing, no
unexpected and no shape errors** across all 49 tensors. That is a stronger
statement than the tests passing: the contract in the module is the artifact's
actual layout, not an approximation of it.
The test carries a `skipif` on the artifact's presence so a machine without the
head skips rather than fails, and the module touches no HIP, so no ROCm guard is
needed.
## What this does not do
It does not load weights and it does not run the head. `supports_speculative_mtp`
stays `False` in `hipengine/generation/gemma4_gguf.py:63` because nothing has
executed yet; flipping it now would be a claim about behaviour that has not
happened. The remaining units are the weight loader, the forward, the adapter
registration, and the end-to-end measurement.
## Changes
- `hipengine/loading/gemma4_assistant_gguf.py`: new module.
- `tests/test_unit_gemma4_assistant_gguf.py`: new tests.
## Validation
- Six tests pass, including one against the real artifact that asserts zero
  validation errors over 49 tensors.
- The failing paths are tested too: a missing metadata key and a short
  sliding-window pattern both raise `MissingGGUFTensorError` with the key named.
- The per-block shape variation is asserted at both ends (`blk.0` and `blk.3`),
  so a uniform-shape regression would be caught.
- No correctness gate applies beyond these tests: no kernel changed, no
  arithmetic changed, and no performance claim is made.
