# qwen38 gfx1151 R2 c=N fp16-state roofline + c8 profile

## Summary

Follow-up to R2 (`worklog/entries/20260818T092624.046425Z-pi-qwen38-gfx1151-r2-fp16-recurrent-state-dd26e5.md`):
R2 deferred the fp16 recurrent-state device change because the c=1 decode gain
is only ~0.5-0.7%. Since we explicitly target c=N, this entry quantifies the
multi-stream gain (the deferred "concurrency value") and measures the c=8
compute/bandwidth crossover.

Key numbers (full calc in
`benchmarks/results/2026-08-18-gfx1151-qwen38-27b-r2-cn-roofline.json`):

- State geometry (from `qwen35_gguf_runner.py` allocation): recurrent state =
  48 layers x 3.0 MiB = 144 MiB/slot (time_step_rank 48 x state_size 128 x
  value_dim 128 x 4 B); conv = 48 x 0.16 MiB = 7.5 MiB/slot (linear_qkv_width
  10240 x conv_kernel 4 x 4 B). Total **151.5 MiB/slot FP32**; fp16 -> 79.5
  MiB, saves **72 MiB/slot**.
- Per-step decode state traffic = **0.296 GiB/slot** (every GDN recurrent
  layer reads+writes its state per token, confirmed in `gdn.hip`).
- In batched decode weights (~15.8 GiB) are read once per step and shared
  across rows; the state is per-slot, so its byte share grows with c.
- **Bandwidth-bound roofline (fp16 halves state)**: c1 0.8%, c2 1.6%, c4 3.1%,
  c8 5.9%, c16 10.5%, c32 17.4%, c64 25.8% decode gain.
- **Prefill is unaffected**: GDN prefill holds state in a register across the
  whole token loop (1 read + 1 write per layer per prefill, ~288 MiB), so fp16
  state is <0.1-0.2% of prefill wall.
- Capacity is not a lever on gfx1151 (72 MiB/slot x 64 = 4.6 GB vs 128 GiB);
  the win is purely bandwidth, unlike the external's 24 GB VRAM story.
- Caveat: c>1 numbers are a roofline, not a measurement; MLP/attention GEMM
  work grows xN and may turn compute-bound before c16-32. A c8 `rocprofv3`
  decode profile was run to check the crossover.

## c8 measured result (2026-08-18, rocprofv3)

Ran `scripts/gguf_packed_ar_rocprof.py` (c1 + packed-c8, warmbuild outside
rocprofv3, require-cached children, token 9707 exact) on Qwen3.8 Q4_K_S
hip_gfx1151. Surprising and important result:

- **c8 batched decode is NOT on the GEMV decode path.** The dense Q4
  projections at rows=8 fall back to **WMMA prefill kernels**
  (`gguf_q4_t16_dense_wmma_prefill_*`, 340 dispatches = 331.7 ms = 81.1% of
the 408.9 ms step). The native batch decode owners cover rows 1-4 only
(`dense_dual_q8_1x2_split_weight_dp4a` c1, `dense_dual_q8_1x2_rowtile8_dp4a`
rows 2-4); rows 5-8 fall through to a single-projection WMMA prefill path.
- c8 step = 408.9 ms vs c1 = 74.1 ms (**5.52x** for 8x rows); aggregate
  throughput only **19.6 tok/s = 1.45x c1** (13.5) vs the ~8x a proper
  bandwidth-bound batch path would give. Per-stream c8 = 2.45 tok/s.
- **The bandwidth->compute crossover is therefore not the c8 bottleneck - the
decode-path gap is.** The fp16-state roofline gain at c8 (~6%) is only
harvestable after a native rows>=8 GEMV owner exists.
- gdn_recurrent (the state family fp16 targets) scales cleanly: 1.776 ms (c1)
  -> 8.563 ms (c8) = 4.82x for 8x rows. In an uncontaminated c8 decode (~77
  ms) it would be ~11.1% of the step, matching the roofline's 11.7% state
  byte-share - so the fp16-state gain estimate is structurally consistent.

Required env: `HIPENGINE_GGUF_Q6_LM_HEAD_MAX_CHUNK=4` (gfx1151 default 5
chunks rows=8 as (5,3) but the Q6 lm_head FP32 rowtile only supports [2,4]).
Full record: `benchmarks/results/2026-08-18-gfx1151-qwen38-27b-r2-c8-decode-profile.json`.
