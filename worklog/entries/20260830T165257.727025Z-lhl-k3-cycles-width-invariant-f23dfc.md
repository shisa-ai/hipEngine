# K3 cycles per output token are width-invariant, ruling out group splitting

## Summary

Tested one more structural candidate for the K3 onset at C5 - a 4-request capacity in
the MTP provider path
(`max_requests = min(4, ...)` at `qwen35_gguf_mtp2.py:1029`, plus request groups) that
would force group
splitting exactly above four lanes. **Disconfirmed**: cycles per output token are
identical at every width.

## Changes

- No code change. Removes a plausible-sounding structural explanation from #17's candidate list.

## Measured

From `he-k3-r1.json` (K3 explicit, widths 1-8, 10 prompts each), summing row-level
`specdec2_mtp2_cycles` and
`mtp.generated_tokens` over engaged cells:

| C | cycles | tokens | cycles per token |
| ---: | ---: | ---: | ---: |
| 1 | 71 | 240 | 0.296 |
| 2 | 142 | 480 | 0.296 |
| 3 | 213 | 720 | 0.296 |
| 4 | 284 | 960 | 0.296 |
| 5 | 355 | 1200 | 0.296 |
| 6 | 426 | 1440 | 0.296 |
| 7 | 497 | 1680 | 0.296 |
| 8 | 568 | 1920 | 0.296 |

- Cycles grow in exact proportion to width (71 -> 568 = 8x) because they are counted per
  lane, and the
  per-token figure is flat. If widths above 4 required extra accept groups or extra
  cycles, cycles per token would
  step at C5; it does not.
- Consistent with everything else on K3: the same number of cycles, each costing more as
  width rises (accept
  88.0 -> 104.3 ms per cycle from C5 to C8, dominated by the batched blocking readback).
