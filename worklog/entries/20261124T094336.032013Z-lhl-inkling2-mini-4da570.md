# Record the loaded Strix Halo host during resident attention timing

## Summary

A second Strix Halo timing pass for the resident attention change is unusable: the host was running an interactive Firefox session with several web-content processes, so per-request wall times ranged from 6.7 s to 72.8 s within one arm. The correctness results on that machine stand; the timing claim does not, and the campaign should not quote a Strix number for this change until it is rerun on an idle machine.

## Changes

- None. This records why one measurement was discarded.

## Validation

- `uptime` on `strixhalo` reported a load average of 14.91 over 32 cores with 105 of 125 GB in use, and the top processes were Firefox and its isolated web-content children. `fuser /dev/kfd` found no other GPU user, so the contention is host-side, not a second HIP process.
- `TIMING_ONLY=1` on the [resident attention harness](20261124T093241.447865Z-lhl-inkling2-mini-4b3cf8.md), 575 input tokens, four interleaved pairs per arm: host `[9.84, 30.00, 6.74, 13.84]` s, resident `[72.76, 7.50, 8.89, 46.22]` s. The spread within each arm is larger than the effect being measured, so no median from this run is evidence.
- The same harness on the same machine before this pass produced identical generated IDs at five prompt lengths, worst KL from `strict` `5.5e-4` against `6.6e-4` for the host control, and 20 of 20 top agreement. Those checks do not depend on timing and remain valid.
- W7900 timing is unaffected and remains the reported number: 4.176 s to 2.974 s medians of four interleaved pairs.

## Next

- Rerun the Strix Halo timing on an idle machine before quoting any Strix number for this change. Check `uptime` and `fuser /dev/kfd` first, and discard a pass whose within-arm spread exceeds the effect.
