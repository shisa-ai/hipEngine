# Diagnose TTS diffusion drift and validate the arithmetic change at task level

## Summary

The failing oracle-injected diagnostic inherited a different production GEMV
reduction from the one used to calibrate its bound. Pin it to the original
reference arithmetic with fresh caches. Production computation and its measured
0.15524 drift are unchanged. Reject both global arithmetic alternatives because
they introduce independently confirmed speech regressions.

## Diagnosis

The generic diffusion GEMV's block size changes FP32 FMA partitions and its
reduction tree. BF16 rounding differences compound through the iterative solver.
At 64 threads the existing two-speaker diagnostic repeatedly reports normalized
latent drift 0.1552419355 against its unchanged 0.15 bound. This predates the main
rebase. Restoring 256-thread arithmetic makes the diagnostic pass, but numerical
agreement alone is insufficient: the generated-audio gate reveals a regression.
No tolerance, fixture expectation or expected-failure marker was changed.

## Rejected 256-order candidate

A two-CFG-row kernel using 64 physical threads shared weight reads and reproduced
the original 256 virtual FMA partitions/reduction. Across 25 single-speaker and
55 two-speaker recorded calls (1600 solver steps), every eps and latent matched
reference256 bit-identically. Kernel/registry tests passed 14 cases, including
CPU-reference KL/top-1, awkward widths, shape guards, and determinism. The affected
session/diffusion bundle passed 40 tests with one existing expected failure.
The unchanged formerly failing node passed (39.15 s).

A cached-only rocprofv3 trace confirmed the candidate kernel (16351/15029 ns for
rows=2, K=1536, N=257). Source arithmetic was in-tree dense_gemv_out_kernel at
6dd61c0f0. No external port. The full lineage scan could not access the configured
external atlas checkout; no source was copied from it.

`OPENBLAS_NUM_THREADS=1 uv run python scripts/vibevoice_tts_diffusion_linear_bench.py --all-calls --session --json /tmp/vv-drift-final-bench.json`

On zbook / Radeon 8060S / gfx1151, BF16 microsoft/VibeVoice-1.5B: isolated solves
old64 32.3–32.4 ms, reference256 55.2–55.3 ms, candidate 37.6–37.7 ms.
Four interleaved full-session arms (candidate/old/candidate/old), three warm
repetitions each: candidate 3.379/3.379 s versus old 3.265/3.276 s (+3.3% mean).
The candidate's RTF 1.014 was not compared to a fresh torch measurement.

Fresh synthesis plus scoring over all ten seeds returned 58/60, the same failing
request pairs as the baseline. That aggregate concealed an additional failure:
`two-long`, seed 20260918, already failed speaker attribution but now also failed
intelligibility, WER 2.5% -> 17.5%. Independent CPU Whisper-large-v3-turbo with
five beams heard the old archived audio correctly (0% WER), but scored the new
waveform at 12.5%, confirming a synthesis regression. The other worsened ASR row,
`two-2turn` seed 20260920, was 0% under Whisper for both arms.

The candidate is REJECTED, despite passing the numerical diagnostic and matching
the strict reference. Its source patch and original harness/tests are archived
in the rejected-candidate artifact; it is not kept in the runtime or registry.
The artifact and companion 60-row quality evidence record waveform hashes and
preserve the additional failed check instead of claiming quality-neutrality.

Other exploratory alternatives:

- Existing virtual256 local128 rowtile: exact to reference256 but slower.
- Preserving 256 arithmetic only in cached projections: worsens drift to 0.4899;
  discarded. Same-input projection probes found BF16 flips in t_mlp_2, cond_proj,
  and L0_gate; this is arithmetic, not a state/reset failure.

## Rejected 128-thread candidate

The existing generic 128-thread kernel passes the unchanged trajectory node
(39.14 s). At seed 20260918 it produces 5/6, with only the old attribution failure
and long-clip WER back to 2.5%. That was insufficient: across the remaining seeds,
`single-numbers` seed 20260917 newly fails intelligibility at 16.67% WER.
Independent Whisper confirms the regression: old archived PCM 8.33%, new 25%.
Stop scoring after that confirmation (60 generated, 33 scored including the
initial six); do not report a completed 60-request verdict. Restore production
64-thread arithmetic. No 128-thread candidate is promoted.

The first overlapping numerical/quality run approached the memory limit. Stop
only our numerical process cleanly: 9 passed, interrupted while loading the second
session fixture, no failure. Finish validation sequentially. These contended
execution times are not performance evidence.

## Changes

Git history establishes the calibration sequence: bc885fae8 (2026-09-15 19:47
JST) sets the 0.15 bound using the then-current 256-thread head; e62880725 (20:07)
later changes the production head to 64. The diagnostic already injects the
oracle's call-0 positive condition and every negative condition/noise draw; it is
a branch-localization oracle, not unassisted production qualification.

Pin that diagnostic explicitly to its calibrated 256-thread arithmetic. Use a
fresh diffusion head so 64-thread timestep/condition caches cannot contaminate
the reference, restore the original session head/setting with pytest monkeypatch,
and close only the temporary head. Keep the bound at 0.15. Default-path per-step
numerical tests and unassisted audio-quality evidence remain separate gates.

This is a TEST CONTRACT repair, not a reduction of production drift: the
production head still measures 0.1552419355 in this diagnostic. Its executable
AST, after stripping comments/docstrings, is identical to 6dd61c0f0. The
64-thread production computation remains unchanged because both tested global
alternatives regress speech. Strict-reference closeness does not override task
quality; no new production-profile certification is claimed.

runs its own negative LM, injecting only recorded random operands. Corrected.
