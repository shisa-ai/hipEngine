# The Q5_1 blocker was wrong: the selected-expert GEMV path exists and works

## Summary

`20260922T210504.433272Z-lhl-gemma4-gfx1100-q5-1-gap-661149.md` recorded Q5_1 as a
hard blocker on the Gemma 4 GPU path. **That was wrong.** Q5_1 has a working GPU
expert path, and it is the *right* path for experts.

On the real artifact, `qwen4_exp_q5_1_selected_gemv_bf16_bf16_out` over
`layers.0.ffn_down_exps` reproduces a NumPy reference at the rounding floor:

| expert | relative error |
| --- | --- |
| 0 | 0.270% |
| 3 | 0.344% |
| 5 | 0.313% |
| 127 | 0.309% |

Four different experts give four different correct results, so the selected-expert
indexing is honoured rather than ignored.

## Two errors, both in how I looked

**I searched one registry layer and concluded absence.** Q5_1 has no plain
`linear/gguf_q5_1/*` GPU kernel — that part was right. I stopped there. The GPU
kernels live under `moe_linear/gguf_q5_1/*`, which is a *selected-expert*
interface, and selected-expert is the correct interface for a MoE projection
anyway. A plain linear is the wrong shape for an expert: it cannot express which
expert each row belongs to.

**`can_resolve` returning False is not evidence a kernel is absent.** Registration
is lazy and module-triggered. My check imported `hipengine.kernels.hip_gfx1100`
only, so nothing had registered `moe_linear/gguf_q5_1/*` yet and every lookup
returned False. After importing `hipengine.kernels.hip_gfx1100.quant.qwen4_exp_q5_1`:

```
moe_linear/gguf_q5_1/selected_gemv_bf16_bf16_out            True
moe_linear/gguf_q5_1/selected_gemv_wave64_bf16_bf16_out     True
moe_linear/gguf_q5_1/selected_gemv_logical256_t64_bf16_out  True
registered moe_linear/gguf_q5_1 keys: 17
```

Seventeen registered variants. I called the kernel directly and it worked, which
is what proved the point — a negative registry lookup had been treated as a
positive finding about the code.

This is the same class of mistake as the earlier "all four types resolve" claim,
in the opposite direction: there I treated a *positive* dispatch resolution as
proof a GPU kernel existed, and here I treated a *negative* registry lookup as
proof one did not. Both are lookups being asked a question they do not answer.
The thing that settles it is calling the kernel and checking the numbers.

## The ABI, for the wiring that follows

`qwen4_exp_q5_1_selected_gemv_bf16_bf16_out(input, selected, weights, output,
x_rows, rows, num_experts, in_features, out_features, *, threads=256, stream=0)`

From `qwen4_exp_q5_1.hip`:

- `selected` is `int64` — one expert index per **compact row**, not per
  `(row, top_k)` lane.
- `input` is BF16, `x_rows` rows. `rows` is the compact row count and
  `rows % x_rows` must be 0; the kernel reads
  `input[(row / (rows / x_rows)) * in_features]`, so `rows == x_rows` means one
  input row per compact row.
- `weights` is raw Q5_1 blocks, laid out `(num_experts, out_features,
  in_features)`, selected by
  `weights + (expert * out_features + out) * row_bytes` with
  `row_bytes = (in_features / 32) * 24`.
- `threads` must be 256 on this variant.

Gemma 4's `ffn_down_exps` is `(128, 2816, 704)` and `ffn_gate_up_exps` is
`(128, 1408, 2816)`. Both match that layout directly, with `in_features`
divisible by 32 (704/32 = 22, 2816/32 = 88). No repack is needed, which also
retires the "repack into ds4 planes" route the blocked entry proposed as the
better end state — that was solving a problem that does not exist.

## Why this is a better design than what is wired today

The expert forward currently reads `expert_start` back to the **host** and loops
per non-empty expert, launching one GEMV per expert with a byte offset into the
stacked weight. That is a device-to-host synchronisation per layer per token, and
it grows with the number of non-empty experts.

The selected kernels take the compact expert-sorted rows and the per-row expert
index in one launch. The Gemma 4 expert forward already builds `packed_hidden`
and `sorted_lanes`, so the data the selected interface wants is already there.
Wiring it removes the host sync rather than adding a second path beside it.
