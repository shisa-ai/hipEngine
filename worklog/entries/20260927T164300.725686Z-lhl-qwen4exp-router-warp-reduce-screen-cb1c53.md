# Router warp-per-token reduction screens at +1.65% prefill

## Summary

The router logits producer is reduction-structure-bound, and a warp-per-token
reduction wins end-to-end. Same-session two-arm A/B on `code-p4096`, three
repetitions per arm, unprofiled:

| arm | variant | tok/s | median s | per-run walls (s) |
| --- | --- | ---: | ---: | --- |
| A | `f32_hidden_token_tile4_dense_exact` (shipped) | 247.739 | 16.534 | 16.546 / 16.534 / 16.521 |
| B | `f32_hidden_warp_reduce_dense_exact` (candidate) | **251.823** | **16.261** | 16.261 / 16.250 / 16.284 |

`+4.083 tok/s`, `+1.65%`, `-0.272 s` per 4096-token prefill. Arm B's slowest run
is 0.237 s faster than arm A's fastest, so the arms do not overlap; within-arm
spread is 0.15% and 0.21%.

The kernel trace confirms the arms differ rather than assuming it:

| arm | kernel | 1x ms | n | ms/launch |
| --- | --- | ---: | ---: | ---: |
| A | `qwen35_router_logits_f32_token_tile_dense_exact_kernel` | 619.45 | 192 | 3.226 |
| B | `qwen35_router_logits_f32_warp_reduce_dense_exact_kernel` | **287.11** | 192 | **1.495** |

`2.158x` on the router kernel, `332.3 ms` saved, against a 313.6 ms prediction
from the standalone screen - 94% of it realised in situ.

**Not promoted.** The candidate changes the reduction order from a 256-thread LDS
tree to a 32-lane shuffle, so it is not bit-identical to the parent. Promotion
waits on the production envelope.

## Two harness defects found while building this screen

Both produced measurements that looked like results and were not.

**1. The env var never reached the process.** `/tmp/run-gpu.sh` builds the child
environment with `env -i`, so exporting `HIPENGINE_QWEN4_EXP_ROUTER_VARIANT` on
the command line is silently dropped. The committed `warmup-*.json` artifacts
record it directly: `route_env` carries no router variant at all, and the two
arms read 246.259 against 246.265 tok/s - a 0.002% spread between arms that were
supposed to differ by 2x on the router. A null dressed as a measurement.
The harness's own post-binder `--override` is the supported path; it also records
the arm in the artifact.

**2. The runner hardcoded the variant.** Even with the env var delivered, the
call site passed the tile4 variant as a literal, so the profile-level switch was
inert. The runner now resolves the variant at launch and raises on an
unrecognized value rather than falling back, because a silently inert arm is the
failure this route already produced once.

## Next

- Run `scripts/qwen4exp_layer2_profile_gate.py --candidate router_warp_reduce`
  and judge the route on the production envelope. **The binding risk is discrete,
  not drift**: the router logits feed `qwen35_router_select`, so a near-tie
  expert can change which of the 512 experts is selected. A 4.9e-7 logit
  difference is irrelevant as drift and decisive as a selection flip, so a
  KL-only pass is not sufficient evidence on its own - measure expert-selection
  stability over the same rows.
- The gate's default prompt suite is 39-71 tokens. The router route admits at
  `rows >= 2`, so it does execute there, but that is a thin sample for a
  discrete-flip risk. The harness's dispatch count guards against a silent
  no-op; it does not make the sample wide.
- `--override` is a diagnostic class. A promotion run must select the candidate
  through the profile so the manifest carries it.
