# the q5_k iu8 route runs at gemma4's own 704-wide expert half

## Summary

Layer 29's Q5_K gate/up projection now takes the iu8-WMMA route instead of the fp32
grouped fallback: **109.2 ms to 13.2 ms per launch, 8.25x**, measured in a real
2048-token prefill. The route is **bit-identical** to the strict `grouped_row4` owner it
replaces, at the artifact's own 704-wide expert half.

The loop's 512/128 prefill metric moves **1.01 s to 0.92 s (-8.9%)**, 507 to 557 tok/s.

The guard that blocked this was hiding a second, larger bug. `intermediate % 128` was
documented as a tiling limit — the leaf walks output columns as `blockIdx.x * 128` and
Gemma 4's gate/up seam sits at 704, so 704/128 = 5.5 puts the seam mid-block. But the
kernel resolves the half **per column**, so a straddling block already reads the right
weight for each of its columns, and the fused block is 1408 = 11 x 128 so the grid has no
partial block either. Removing the guard alone would have produced **wrong output from the
second expert on**: the leaf strides experts by `local_out_features`, which is the half's
own width, while Gemma 4 stores one `ffn_gate_up_exps` tensor per layer with the gate rows
first *per expert*, so the expert stride is the fused width.

## Changes

- `hipengine/kernels/hip_gfx1100/quant/gguf_q5_k_q8_1_selected_prefill.hip`: both leaves
  (the iu8-WMMA risk kernel and the sparse exact repair) and both host launchers take an
  explicit `expert_stride`, used in place of `local_out_features` when positive. `0` keeps
  the two-separate-buffers layout, where the half's own width *is* the stride. The
  `out_features_a/b % 128` guard relaxes to `% 16`, the width the WMMA tile actually needs.
- `hipengine/kernels/hip_gfx1100/quant/gguf_q5_k_q8_1_selected_prefill.py`: `expert_stride`
  is keyword-only on both wrappers and defaults to 0, so the Qwen4-Exp caller is unchanged.
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_experts.py`: the route passes
  `expert_stride=2 * intermediate` and declines on `intermediate % 16` rather than `% 128`.
- `tests/test_unit_gemma4_expert_route.py`: new
  `test_fused_gate_up_iu8_route_holds_at_gemma4_s_own_half_width`, RED first.

## Why the old guard was there, and what it was hiding

The route's docstring said the leaf "tiles out_features in 128-column units, so an expert
intermediate that is not a multiple of 128 cannot be tiled at all". Reading the leaf says
otherwise: `global_col`, `use_b`, `local_col`, `local_out_features`, the per-half weight
base and `wcol_valid` are all computed per column, so the seam is not a block-level
problem. The `% 128` host guard and the `intermediate % 128` caller guard are both stricter
than the leaf's own Python contract, which checks 16-multiples.

The real blocker was the expert stride, and it is only reachable once a half is *not* 128
wide, which is why the guard concealed it: with `out_features_a = out_features_b = 704` and
the fused layout, a leaf striding by `local_out_features` reads expert 0 correctly and every
later expert from the wrong offset.

## Validation

- **RED first**: the new test failed with `the Q5_K iu8 gate/up route declined the
  artifact's own 704-wide expert half` before the change, and the strict owner served in the
  same run, so the harness was sound.
- **GREEN**: the route serves and its output is **bit-identical** to
  `gemma4_project_experts_grouped_row4` over all 45056 outputs at 8 experts x 704 x 2816.
  Bit-identity is the route's own documented contract, not a tolerance chosen here.
- **Power check**: with `expert_stride=0` (the old half-width stride) the same test reports
  **22508 of 45056 outputs differing**, normalized max 0.367 against a scale of 1.69e4 — so
  the stride is load-bearing and the test is not vacuous.
- **Backward compatibility**: `tests/test_gpu_qwen4exp_q5_k_iu8_exact.py` (the
  two-separate-buffers caller, always 128-wide halves) and `test_unit_gemma4_expert_route.py`
  together: **65 passed**.
- **Route engages in production, not only in the test**: a route/quant probe over a real
  512-token prefill shows `gemma4_project_experts_gate_up_mmq` with `quant=gguf_q5_k`
  returning `True` in **13.239 ms**, against the `rows -> grouped_row4` fallback it used to
  take at 27.3 ms per block. `down_mmq` still returns `False` for `gguf_q8_0`.
- **Model surface**: `scripts/gemma4_real_generate.py` produces coherent text and its first
  tokens still match llama.cpp's.
- **Loop metric**: `scripts/gemma4_campaign_bench.py --prompt 512 --output 128 --samples 3`
  gives prefill 0.91 / 0.92 / 0.92 s, median **0.92 s**, against the 1.01 s recorded best.
  Same run: decode 24.885 tok/s, path parity True.

## Open

The **Q8_0 down projection is still on the fallback** and is now 5.0% of the 512-token step
(43.85 ms of 873 ms), because `gemma4_project_experts_down_mmq` accepts `gguf_q5_1` only.
`gguf_q8_0_mmq_prefill.hip` already exists in this tree, so the missing piece is the
selected/grouped form the expert down needs or an extension of that route to `gguf_q8_0`.
Together with this change that would take layer 29 from 606.6 ms to about 21 ms at 2048.

Not attributed: the decode figure in the loop's verify run reads 24.885 tok/s against the
21.48 tok/s recorded at iteration 78. This change does not touch the decode path — a
one-token step has 8 lanes against the route's 128-lane floor, so it takes the
selected-GEMV route — so that difference is **unexplained** and is recorded rather than
claimed.
