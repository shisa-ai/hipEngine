# Gemma 4 P9b: three launches instead of five — decode recovers and both metrics win

## Summary

Enabling the parallel compaction path (iteration 13) bought **+3.71% prefill
for -0.53% decode**. The decode cost was launch count, not kernel time: the
parallel launcher already runs its own count, prefix and scatter stages
internally, so the call site's separate `_zero(counts)` + `group_count` +
`group_prefix_active` were redundant — five launches where the serial path
issued three. Removing them returns the sequence to three while keeping the
parallel kernels.

**It over-recovered.** Decode is now above the pre-P9 baseline, and
route_glue fell further:

| | p8c (pre-P9) | p8e (parallel, 5 launches) | **p8f (parallel, 3)** |
| --- | ---: | ---: | ---: |
| `moe.route_glue` @1024 | 28.3 ms | 7.3 ms | **6.8 ms** |
| `moe.route_glue` @4096 | 112.9 ms | 29.1 ms | **27.0 ms** |
| device busy @1024 | 469.4 ms | 451.3 ms | **451.1 ms** |
| device busy @4096 | 3418.8 ms | 3349.8 ms | 3350.5 ms |
| prefill @1024 | 2040.9 tok/s | 2116.5 tok/s | 2106.0 tok/s |
| prefill @4096 | 1165.0 tok/s | 1189.0 tok/s | 1188.2 tok/s |
| decode @1024 | 43.80 tok/s | 43.57 tok/s | **44.26 tok/s** |
| decode @4096 | 40.17 tok/s | 39.95 tok/s | **40.60 tok/s** |

Against the pre-P9 baseline this is **prefill +3.19% / +1.99%** and
**decode +1.05% / +1.07%**, with `moe.route_glue` down **76% at both
prompts**. Both headline metrics improved; nothing traded against anything.

Prefill at 1024 reads 2106.0 against p8e's 2116.5, a -0.5% move in the
direction opposite to the change's own effect — that is run-to-run noise on
a single sample, and both readings sit ~3% above baseline.

## Changes

`hipengine/kernels/hip_gfx1100/gemma4/gemma4_experts.py`:

- The grouping block collapses to a single `qwen35_moe_group_compact_active`
  call with `parallel=True`. `_zero(counts)`, `qwen35_moe_group_count` and
  `qwen35_moe_group_prefix_active` are gone from the call site.
- Their two imports are removed.
- `_zero` is deleted: its only caller was that block, and its docstring
  existed solely to explain the `group_count` accumulate contract that no
  longer applies. Nothing imports it.
- `counts = scratch.buffer("counts")` is removed; the scratch sizing entry
  `("counts", num_experts * 4)` is left in place, since the geometry test
  reads that layout and a 512-byte declaration is not worth a test edit.
- The module docstring's kernel list now names the single parallel
  compaction entry instead of the retired three-step chain.

`counts` genuinely has no consumer: after the removal, a repo-wide grep for
`buffer("counts")` returns nothing, and there is no read of `counts.ptr`
anywhere in the module.

## Measurement

Guard (b) required re-running the A/B **in the new sequence**, not reusing
iteration 13's — the caller-side stage no longer runs first, so the parallel
path must stand on its own. Both sequences were run back to back on
identical inputs with all six output buffers sentinel-filled before each
launch:

| lanes | old sequence (count+prefix+compact) | new sequence (compact alone) | all 6 outputs identical |
| ---: | ---: | ---: | :---: |
| 64 | 0.0936 ms | 0.0655 ms | yes |
| 512 | 0.0580 ms | 0.0648 ms | yes |
| 1024 | 0.0633 ms | 0.1008 ms | yes |
| 8192 | 0.0999 ms | 0.1059 ms | yes |
| 32768 | 0.2126 ms | 0.2281 ms | yes |

Every output — `sorted_lanes`, `sorted_experts`, `sorted_weights`,
`expert_start`, `active_experts`, `active_count` — is identical between the
sequences at all five lane counts, with zero sentinel slots left anywhere.
(The timings are sub-0.1 ms and dominated by Python call overhead, so they
are recorded as a sanity check rather than a result; the launched-kernel
count is the thing that changed, and the end-to-end numbers are below.)

The correctness conclusion is unaffected by timing noise: **the parallel
path produces the same bytes with or without the caller's stages.**
