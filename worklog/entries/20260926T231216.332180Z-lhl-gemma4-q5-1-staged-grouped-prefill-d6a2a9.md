# Gemma 4 Q5_1 expert down projection: staged grouped prefill, bit-exact 1.91x

## Summary

The Q5_1 expert down projection was the largest remaining prefill cost on this
host, and it was spending its time on a fetch the earlier Q4_K staging rewrite
had not touched. It launches one block per (expert, out_col), so every block
re-reads the expert's whole activation block from L2: at Gemma 4's own down
geometry the kernel moves ~17 GB in 38.5 ms (441 GB/s) while the weight bytes are
only 0.3 GB of it. A staged variant now gives each block a four-column output
tile and holds the activation elements a thread needs for the current k-chunk in
registers, so one element feeds four outputs. It is **1.91x** on the kernel and
**1.161x** on the 512/128 prefill row, it is **bit-exact**, and because it is
bit-exact it ships on the default path with no flag and no execution-profile
gate - the first prefill change in this campaign that needed neither.

## Changes

- `hipengine/kernels/hip_gfx1100/quant/qwen4_exp_q5_1.hip`: new
  `q5_1_selected_grouped_prefill_staged_bf16_bf16_kernel<4, 4, 256>` and its
  launcher. Each thread owns two logical slots, *t* and *t*+128, and every
  activation element it needs for the current k-chunk, so the tile's outputs
  share one load. The contraction is the incumbent's, not a reassociation: slot
  *t* still accumulates columns *t*, *t*+256, *t*+512, ... in increasing order,
  and the tree is still the 256-wide stride-128 tree, whose first level becomes
  register-local because a thread owns both slots it pairs.
- `hipengine/kernels/hip_gfx1100/quant/qwen4_exp_q5_1.py`: wrapper and
  registration for `selected_grouped_prefill_staged_out4_bf16_bf16_out`.
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_experts.py`: the variant is first
  in `_GROUPED_PREFILL_VARIANTS`, so it selects by default; plus
  `_GROUPED_VARIANT_COUNTS` / `gemma4_moe_grouped_variant_counts()`, because the
  route name reports the family and every variant in it produces the same bits,
  so nothing else could show which fetch strategy actually ran.
- `benchmarks/results/2026-09-27-gemma4-q5-1-staged-grouped-prefill-accepted.json`,
  `benchmarks/CHANGELOG.md`, and the campaign document's prefill section.

## Validation

- **Bit-exactness, kernel level.** 0 of 11,534,336 bf16 outputs differ from the
  incumbent Q5_1 grouped route at in 704 / out 2816 / 128 experts / 4096 compact
  rows, and 0 of 11,534,336 at Qwen4Exp's in 2816 / out 1408 shape.
- **Bit-exactness, unit test.** `tests/test_unit_gemma4_expert_route.py` checks
  every variant named in `_GROUPED_PREFILL_VARIANTS[1:]` against the selected
  GEMV, so the new variant is covered at (2816, 704), (1408, 2816), (64, 128),
  (37, 96) and (16, 32). 36 tests pass.
- **Public path.** `scripts/gemma4_campaign_bench.py` at 512/128, 3 samples and
  1 warm-up, both arms on one tree with the only difference being which kernel
  the variant name resolves to (an in-process registry swap, no code edit between
  arms): prefill **4.239 -> 3.652 s (120.78 -> 140.19 tok/s, 1.161x)**, wall
  10.271 -> 9.678 s, decode **21.06 -> 21.06 tok/s**, and 128 of 128 identical
  greedy token ids from an identical prompt.
- **Intended route confirmed, not inferred.**
  `gemma4_moe_grouped_variant_counts()` reports the staged variant on 29 of 29
  down projections per pass, alongside Q4_K's own staged_out8 29 times, with 58
  `grouped_prefill` projections in total.
- **Tile sweep.** row_batch/out_tile at 8/4, 4/4, 4/8, 8/8, 2/4, 2/8 and 4/6
  (all 256) plus 4/8 at 512: 4/4 wins at both real geometries, 1.91x and 1.55x.
  Two outcomes were dropped rather than shipped - a wider tile alone does
  nothing (the existing out8 variant measures 30.32 ms against the incumbent's
  30.99 ms, because its inner loop still reloads each element per column), and
  K_TILE=512 reaches 17.28 ms but differs in 11,506,914 of 11,534,336 outputs
  because a slot's column sequence depends on K_TILE = 256.
