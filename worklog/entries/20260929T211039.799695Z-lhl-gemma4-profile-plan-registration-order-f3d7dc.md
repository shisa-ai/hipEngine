# Checkpoint: plan registration flips the default on presence alone, so piece (A) must land last

## Summary

Supersedes the build order in `20260929T210910.857619Z-lhl-gemma4-execution-profile-registration-scope-e29a32.md`
(hence this `decision` entry rather than an edit), which listed step 1 as
"write `gemma4_profiles.py` registering strict + production plans". That order
would silently promote gemma4's arithmetic to the production default **before**
the execution-profile gate has run, because the code enforces registration
presence, not certification. The build must produce the gate packet first and
land the registration atomically with a passing gate artifact.

## Changes

- This entry only. No code: it changes the order of the work described in the
  prior scope entry and records the mechanism that forces the order.

## Validation

Read directly from `hipengine/execution_profiles.py`.

- **`resolve_default_execution_profile(model=, backend=, quant=)` at `:314`**
  loops over `(PRODUCTION, STRICT)` and returns `ExecutionProfile.PRODUCTION`
  only if **both** `RuntimeProfileKey`s are present in `_RUNTIME_PROFILE_PLANS`.
  If either is missing it returns `None`, whose `None` keeps the migration path.
  There is no certification argument, no gate artifact check, no
  `promotion_qualified` field anywhere in the function. **Presence is the
  entire condition.**
- Consequence: the first call of `register_runtime_profile_plan(..., profile=PRODUCTION, ...)`
  for `(gemma4, hip_gfx1100, gguf_ud_q4_k_xl)`, paired with the strict
  registration, flips an omitted profile from the migration path to
  `production` on the next load. §2.1's prose ("a certified production plan")
  is a rule the document states and the code does not enforce.
- **Baseline measured:** `registered_runtime_profile_keys()` returns `0` entries
  at import in a fresh process. Plans register lazily on model load -- qwen's
  are absent pre-load too -- so an empty import-time registry is not evidence
  about any specific model. `hipengine/llm.py:336` resolves the requested profile
  via `resolve_requested_execution_profile`, and `:1433` `_resolve_execution_profile`
  applies `resolve_default_execution_profile` for the omitted case.
- **gemma4's native variant vocabulary, enumerated by calling its four lazy
  registrars** (`register_gemma4_attention_kernels`, `..._moe_...`, `..._norm_...`,
  `..._rotary_...`) plus `register_gemma4_cpu_reference_kernels`: **55 keys over
  13 layers** -- `add_rmsnorm_scale`, `branch_add`, `expert_geglu`,
  `gemma4_text` (`gelu_tanh` / `reference_forward` / `router_topk`),
  `head_rmsnorm`, `k_to_v`, `moe_weighted_accumulate`, `partial_rotary`,
  `prefill_attention` (`gemma4_plain` + `gemma4_tiled`), `rmsnorm`,
  `rmsnorm_weightless`, `router_prescale`, `scale`, almost all under the single
  variant `gemma4_plain`. The `gemma4_text`/`reference_forward` key is the
  existing strict oracle for the whole-text layer. Registrations are lazy --
  importing `hipengine.kernels.hip_gfx1100` registers nothing gemma4-related,
  which is why a naive `registered_keys()` probe reported 0.
- The dense, expert and lm_head GEMM variants gemma4 routes through are
  registered by the shared gguf quant modules (`linear/dense_gemv.py`,
  `linear/lm_head.py`, `quant/gguf_k_mmq_prefill.py`,
  `quant/gguf_expert_pack8_gemv.py`, ...), not by the gemma4 package, so the
  `VariantSelection` set for piece (A) spans both the 55 native keys and that
  shared surface -- which is why the curation, not the registration call, is
  the bulk of the work.
