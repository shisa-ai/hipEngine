# Gemma 4 P14 pass-3 lower-bound trim with the literal-zero fast path

## Summary

P14 lands: the class kernel's pass 3 now walks `[first_active, last_active + 1)`
instead of `[0, last_active + 1)`, so a sliding row stops paying for the causal
triangle below its window. On the XTX primary lane this is **-18.1%** on
`attn.sliding`, **+7.9%** topline prefill at 4096 tokens, and no change at all
to `attn.global`.

The interesting part is that the obvious implementation does not work. The
first version won on sliding (-17.8%) and *still lost overall*, because
`attn.global` regressed **+41.1%** -- causal rows, whose first kept key is
already key 0, so they receive no trim and should have been unaffected.
Reproduced twice on an idle GPU, so not thermal.

The cause was isolated by bisecting the change rather than by reading it, and
it is not what the change contains:

- a variant carrying only a **runtime `keys_begin`** and none of the
  bookkeeping reproduced the full slowdown (causal hd256 sum 127.95 ms against
  a 98.45 ms baseline) -- so the `first_active` reduction, the second shuffle,
  the `partial` write and the extra `__syncthreads()` are all innocent;
- a variant carrying **only the extra `__syncthreads()`** measured baseline
  (98.31 ms), and a variant carrying **only the new `keys_begin` parameter with
  a literal `0`** measured baseline (98.32 ms) -- so the signature and the
  barrier are both innocent;
- the compiled kernel was identical in `.amdhsa_next_free_vgpr` (64 / 53),
  `.amdhsa_private_segment_fixed_size` (0, so no spills),
  `.amdhsa_group_segment_fixed_size`, `.amdhsa_kernarg_size` and launch grid,
  and had **fewer** instructions than baseline (1876 vs 2008 at hd512) -- so
  register pressure, occupancy and "the bookkeeping added work" are all
  excluded.

What survives is the runtime lower bound itself. With nothing else changed it
costs **+49.9%** on the causal sums (126.37 -> 189.46 ms at hd512). Hoisting it
out of the loop into pointer bases did not help (188.79 ms), so it is not
address arithmetic inside the loop body. That points at how the compiler forms
the loop's start and its prefetched V addresses when they are not compile-time
constants -- recorded as **inferred, not measured**; the +49.9% is the measured
part.

The fix follows directly: **pass a literal `0` on the path that uses no trim.**
`gemma4_decode_pass3` is `__forceinline__`, so that spelling reproduces the
original loop's code generation exactly, while the windowed path keeps the
runtime bound -- and there the span it cuts is far larger than the penalty, so
it wins even carrying it. `first_active` is block-wide, so the branch never
diverges.

## Changes

- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention.hip`
  - `gemma4_decode_pass3` takes `keys_begin`; the walk starts there and the
    prefetch pipe originates there. Docstring records why starting there cannot
    change the accumulated sum: a masked key's weight is the `0` the walk's
    own `weight == 0` skip already drops, and survivors stay ascending.
  - The class kernel computes `first_active` as the mirror of the existing
    `last_active`: one more compare in the mask walk that already runs, a
    second `__shfl_down` min in the shuffle that already runs, and a block min
    over `partial`, whose 512 slots are free once `denominator` is in a
    register. Both bounds are written under one new `__syncthreads()` and read
    under the barrier that has always published `last_active`.
  - The pass-3 call is spelled twice -- literal `0` when `pass3_begin == 0`,
    `pass3_begin` otherwise -- with a comment separating the measurement from
    the inferred mechanism.
  - Pass 2's range was deliberately left unbounded: its own comment records
    that skipping it entirely saves no time, so bounding it cannot pay.
- `docs/campaigns/GEMMA4-26B-A4B-PUNCHLIST.md` -- P14 moves `open` -> `landed`
  with the three-snapshot A/B, the isolation chain, the fix, and the
  correctness evidence in its Result cell.
- Artifacts committed with this unit: the `p14fix` scoreboard snapshot and its
  four children, the `p14` snapshot and its children (the regressing attempt
  the row cites as the middle column of the A/B), the pre-fix gate, and the
  post-fix gate.
