# The MTP refusal reason reaches the per-request response but not the capability surface

## Summary

The MTP admission decision already computes a machine-readable refusal reason, and
the server already knows its vocabulary. The gap is that the reason reaches the
**per-request response** but not the **capability/readiness surface**, which is
why the task #32 clamp probe (`33cb58220`) saw `serving_route: true`,
`resolved: 5`, and `certified_explicit_scope.key.candidate_budget = 5` for a cell
the engine was refusing. A client reading capabilities cannot tell "MTP active"
from "MTP requested and declined".

The reason is produced by an ordered `(condition, reason)` walk in
`hipengine/speculative/serving.py:525-541`:

    (key.candidate_budget <= row.candidate_budget, "candidate_budget_not_qualified"),
    (key.sampling_mode in row.sampling_modes, "sampling_mode_not_qualified"),
    (key.memory_fit, "insufficient_memory"),

with the full set also covering `artifact_not_qualified`, `backend_not_qualified`,
`target_arch_not_qualified`, `weight_quant_not_qualified`, `kv_storage_not_qualified`,
`kv_layout_not_qualified`, `physical_group_not_qualified`, and
`resident_capacity_not_qualified`. `hipengine/server/api.py:292-305` already
enumerates those codes as `_MTP_SCREENING_REASONS` beside
`_MTP_SCREENING_QUALIFICATION = "explicit_screening_unqualified_cell"`, so the
server side is vocabulary-complete; nothing needs to be invented.

The decision object carries the reason (`hipengine/speculative/serving.py:153`,
serialized at `:228`), and the server's WARNING prints it, so the value is
available at the point the capability response is built.

**The one precedent to follow, and its limitation:** `provider_decline_reason`
already exists (`hipengine/server/api.py:16263`, surfaced at `:16472`), but it is a
per-span provider decline carried on the response, not an admission decision
carried on capabilities.

- None yet. This entry specifies the change; it does not make it.

## Validation

Located by grepping the refusal code across the tree. The three call sites are
`hipengine/server/api.py:304` (the vocabulary), `:13799` (a docstring naming
`candidate_budget_not_qualified` and `insufficient_memory`), and
`hipengine/speculative/serving.py:538` (where the condition is evaluated) with
`:590` excluding it from another branch.

The observation that motivates it is the `/tmp/t32` capability block, which reports
`candidate_budget={"requested": 5, "resolved": 5, "source": "explicit"}` and
`certified_explicit_scope.key.candidate_budget = 5` while the same server logs
`candidate_budget_not_qualified` and the load arm shows `mtp_requests=0` with
`never_entered=2` of 2.

## Next

- Implement: carry the admission decision's `reason` into the capability/readiness
  response using the existing `_MTP_SCREENING_REASONS` vocabulary, so an unqualified
  cell reports the specific code rather than looking active. A default-on MTP is
  not defensible until this exists, because the current surface advertises a route
  the engine declines to take.
- Keep the decision object as the single source: do not recompute the reason at the
  response layer, or the two can disagree.
