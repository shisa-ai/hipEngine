# AR prefill owner trace falsifies the task-#12 dispatch premise

## Summary

I profiled one real AR first-token request on the route the published C1-C8 matrix actually uses, and the
answer overturns the premise the whole prefill sub-campaign has been running on. **The shipping route never
launches a pack8 kernel.** Dense prompt processing is owned by the Q4_T16 WMMA family at 94% device
utilization, so no dispatch declaration - not `GGUF_Q4_PACK8_DUAL_WMMA_SILU_PREFILL`, not
`GGUF_Q4_PACK8_WMMA_BULK_PREFILL`, not any `_POLICIES` entry - could have moved a published row. Every
pack8-versus-T16 number in this campaign, including today's dual-WMMA rejection two commits back, describes a
route the published rows do not execute.

## What this changes

- **Task #12 (C1-C3 prefill) is not a dispatch problem.** 89% of busy time sits in three T16 WMMA prefill
  kernels. For the FFN geometry (rows 35, 5120x17408) a single pass over the weights is ~22 ms and the
  equivalent BF16 compute bound is ~27 ms, against 140 ms measured in the `shared_b` bucket, so there is
  roughly 5x of headroom, but it is kernel arithmetic at small rows, not a registry line.
- **There is no control headroom left at these shapes.** At 0.94 utilization inside 256 ms, admission,
  host-work, and launch-gap theories have nowhere to go. That also merges task #11 (AR C2/C3) into the same
  wall as #12: they are one kernel-efficiency problem, not two.
- **The remaining gap is smaller than the notes claim.** The published C1 deficit is 11.0% (148.72 vs 1472.49
  tok/s). The "2.26x" in the campaign notes is a pp512 whole-prompt comparison in a different regime. 11% of
  a 256 ms request is ~27 ms, i.e. one kernel's tile-shape decision at rows 35-67, which is a plausible
  single-kernel win and not the multi-x rebuild the notes imply.
- **Fusing the rest of the FFN pairs is a trap.** The fused unequal-dual T16 owner covers 24 launches per
  iteration while `silu_mul_separate_out` still runs 64 times, but SiLU totals 0.3 ms. Fusing the remaining
  40 pairs cannot approach the 140 ms in `shared_b`, so it should not be picked as the target just because it
  is the easy diff.
- **pack8 stays registered and undeclared**, and that is now the correct end state for this model: the
  pack8 comparison data (1.19x-1.98x at rows 32-64, today's dual rejection, the shape-policy ordering bug) is
  valid only for the `QWEN35_DENSE_H5120_GEOMETRY` AR-only microbenchmark route, which the handoff already
  notes is "a different model than every published C1-C8 row". I did not identify the default policy constant
  by name; the trace shows only that it is not pack8.
