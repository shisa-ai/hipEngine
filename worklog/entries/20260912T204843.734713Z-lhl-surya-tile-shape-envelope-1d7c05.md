# Surya attention tile shape envelope

## Summary

`plan_score_tiles` (shared by the Surya vision tower and text prefill) took the
widest query block the byte budget admitted. That is a memory rule used as a
shape rule, and where the dense score matrix is small it picks a bad shape: at
1024 patches a 512 MiB budget admits the whole dense matrix (193.54 ms) where
128 rows runs 135.52 ms, and at 4096 patches it admits 2730 rows (1123.42 ms)
where 128 rows runs 874.38 ms.

The block is now the largest value that fits the budget *and* a measured shape
envelope, rounded down to a whole number of wavefronts. The envelope caps the
block at `max(128, ceil(rows / 32))` rows — 128 for every grid up to 4096
patches, growing with the grid above that — which keeps the byte budget the
binding constraint at page scale, where a wider tile is what the page wants. The
wavefront rounding is the unexpected part: on the 34320-patch A4 page every
measured width that is a multiple of 32 runs 43862-44668 ms and every width that
is not runs 45050-48496 ms, and the 512 MiB budget derives 325 rows, which is on
the slow side of that line.

## Results

gfx1151 (Radeon 8060S, Ryzen AI Max+ Pro 395), fp32. For the 256-6400-patch
grids: one runner per shape, one discarded warm-up `vision_forward`, median of 7
timed forwards, old and new default shapes in one run (`--blocks
256,1024,1747,2730 --with-budgets --reps 7`), so those ratios are same-run. For
the 34320-patch A4 grid: median of 2 timed forwards, shape-to-shape from the
`--blocks` sweep — `plan_score_tiles` returns 325 rows for the pre-change
planner and 320 for the current one at the 512 MiB default, pinned by
`test_tile_plan_keeps_the_block_on_a_wavefront_multiple`, and the dense tile is
56.5 GB so there is no dense baseline.

| patches | old default | new default | change | dense | best measured |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 256 | 27.86 ms (256 = dense) | 28.71 ms (128 rows) | 0.971x | 27.86 ms | 27.83 ms (256) |
| 1024 | 193.54 ms (1024 rows) | 135.52 ms (128 rows) | **1.428x** | 192.65 ms | 134.93 ms (256) |
| 4096 | 1123.42 ms (2730 rows) | 874.38 ms (128 rows) | **1.285x** | 1041.99 ms | 879.59 ms (128) |
| 6400 | 2066.60 ms (1747 rows) | 2130.11 ms (192 rows) | 0.970x | 1926.36 ms | 1940.93 ms (96) |
| 34320 | 48496.26 ms (325 rows) | 43862.87 ms (320 rows) | **1.106x** | 56.5 GB, not runnable | 41622.25 ms (2048) |

Score scratch falls wherever the envelope or the rounding binds, because both
only shrink the tile: 48.0 -> 6.0 MiB at 1024 patches, 511.9 -> 24.0 MiB at
4096, 511.8 -> 56.2 MiB at 6400, 510.6 -> 502.7 MiB on the A4 page.

The text prefill shares the planner, so it moves too
(`scripts/surya_attention_memory.py`, mean of 3 timed prefills, same-run dense):

| tokens | dense peak / prefill | new default | tile |
| ---: | ---: | ---: | ---: |
| 2048 | 3600.6 MB / 1.60 s | 3474.8 MB / 1.59 s | 8.4 MB (128 rows) |
| 4096 | 4382.4 MB / 3.36 s | 3862.3 MB / 3.33 s | 16.8 MB (128 rows) |
| 8580 | 7031.2 MB / 7.49 s | 4745.8 MB / 7.54 s | 70.3 MB (256 rows) |
| 16384 | 14709.9 MB / 16.65 s | 6388.4 MB / 17.17 s | 268.4 MB (512 rows) |

The 16384-token peak falls 14.71 -> 6.39 GB (-56.6%) for 3.1% wall-clock, and
the 8580-token page peak 7.03 -> 4.75 GB (-32.5%) for 0.7%. The previous default
shape (1024 rows) sat at 6.66 GB / 16.774 s and 5.21 GB / 7.467 s, so the
envelope buys 268 MB and 466 MB more for 2.4% and 1.0% respectively.

### Why the envelope is a cap and not a fixed width

Two measured effects pull in opposite directions.

Wide tiles are bad where the dense matrix is small. At 1024 patches the shape
curve is 1024 rows 193.81 ms, 512 150.91, 341 139.36, 256 134.93, 160 136.81,
128 136.00, 96 139.65, 64 142.41, 48 150.55, 32 152.77, 16 191.11 — a broad
optimum at 128-256 rows with both ends ~1.4x worse. At 4096 patches 2730 rows is
1124.42 ms and 4096 (dense) 1047.52 against 874.38 at 128 rows.

Narrow tiles are bad at page scale, because every tile re-reads the whole key
range and so the key/value traffic grows with the tile count. On the A4 page:
48 rows (715 tiles) 65983 ms, 96 (358) 49602, 128 (269) 45834, 256 (135) 44383,
512 (68) 44022, 1024 (34) 42449, 2048 (17) 41622. A fixed 128-row cap would cost
13% there against what the 512 MiB budget can buy, so the cap is `rows / 32`
instead: 1073 rows at 34320 patches, which leaves the budget binding (325 -> 320)
and still lets a larger budget buy a wider tile.

### Why the width is rounded to a wavefront multiple

Dividing the grid evenly was the other candidate shape rule, and it does not
predict the measured curve. Of the four grids with an even divisor in the swept
range:

| patches | even (full last tile) | odd (partial last tile) |
| ---: | ---: | ---: |
| 256 | 9 shapes, best 27.73, median 28.58 | 4 shapes, best 28.49, median 28.89 |
| 1024 | 11 shapes, best 136.00, median 143.27 | 5 shapes, best 136.81, median 139.57 |
| 4096 | 13 shapes, best 879.59, median 1090.41 | 6 shapes, best 897.30, median 1076.49 |
| 6400 | 7 shapes, best 1929.69, median 2102.91 | 12 shapes, best 1940.93, median 2124.20 |

Even division wins at 256 and 6400 and loses at 1024 and 4096, and the fastest
measured shape at 6400 is odd-tailed (96 rows, 64-row tail, 1940.93 ms). The A4
page cannot test it at all: 34320 = 2^4 * 3 * 5 * 11 * 13, none of its ten
measured blocks divides it, and its best measured shape (2048 rows, 41622.25 ms)
does not either. That is what makes the wavefront multiple the stronger of the
two — the A4 separation is measured entirely among partial-tailed shapes, so it
is not a tail effect — and it is the one the rule uses.

The A4 page separates cleanly. Every measured block that is a multiple of 32:

| rows | 256 | 288 | 320 | 352 | 384 | 448 | 480 | 512 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| ms | 44383 | 43964 | 43863 | 44568 | 43839 | 44116 | 43663 | 44022 |

Every measured block that is not:

| rows | 272 | 300 | 304 | 325 | 336 | 400 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| ms | 45386 | 46557 | 45505 | 48496 | 46601 | 45050 |

The best non-multiple (45050) is slower than the worst multiple (44568), a 4.8%
gap on the means. The tile GEMMs' `n` dimension is the block, so a width that is
not a whole number of 32-lane wavefronts leaves the last wavefront partly idle;
rocBLAS kernel selection may also move. Rounding down is free memory as well: it
can only shrink the tile, so it cannot break the budget. The same rounding moves
the 6400-patch default from 200 to 192 rows and the 8580-token text default from
269 to 256.

## Changes

- `hipengine/runtime/surya.py` — `plan_score_tiles` caps the budget-derived
  block at `max(SHAPE_TILE_ROWS, ceil(rows / SHAPE_TILE_DIVISOR))` and rounds it
  down to `SHAPE_TILE_MULTIPLE`, with the measurement tables in the constant
  comment. `budget_bytes=None` still means one dense tile, so the strict dense
  fallback is unchanged. New constants `SHAPE_TILE_ROWS = 128`,
  `SHAPE_TILE_DIVISOR = 32`, `SHAPE_TILE_MULTIPLE = 32`.
- `scripts/surya_vision_tiling_cost.py` — `--blocks` lifts the envelope and the
  rounding so the sweep can measure widths the planner would not choose, while
  byte-budget rows keep both (they are the production plan); `--with-budgets`
  puts both in one artifact; each row records `envelope_lifted`;
  `page_small.png` (256 patches) joins the case list; `vs_best_shape` is
  reported per page.
- `tests/test_surya_generation_contract.py` — the two "one dense tile when it
  fits" tests become "one dense tile when the *envelope* covers it", plus a new
  `test_tile_plan_keeps_the_block_on_a_wavefront_multiple` and a rewritten
  `test_vision_tile_plan_is_bounded_by_the_measured_shape_envelope`.
- `tests/test_surya_gpu.py` — the bit-identity test's docstring now describes
  the 32-tile default split instead of the 5-tile one.

## Next

- The envelope is not optimal at every grid, and both misses are recorded rather
  than hidden: at 6400 patches a 96-row tile (67 tiles, 1940.93 ms) beats the
  envelope's 192-row tile (2130.11 ms) by 10%, and at 16384 text tokens the
  envelope's 512 rows cost 2.4% against the budget's 1024. The 6400-patch case
  wants *more* tiles than the envelope's `rows / 32`; nothing in the measured
  set explains why it is the only grid that does, so it is left to a future
  sweep rather than special-cased. The A4 page's own best measured width is 2048
  rows (41622.25 ms), 5.1% below the new default, so the page-scale budget is
  still the thing to raise rather than the cap. See `docs/REFACTOR.md`.
- The A4 page has no dense baseline (56.5 GB) and no torch fp32 reference; the
  page-scale shape evidence is shape-to-shape, not shape-to-dense.
- Raising `max_vision_scratch_bytes` past ~6 GB on an A4 grid makes the vision
  attention launch fail with `hipErrorInvalidConfiguration` (error 9) instead of
  erroring cleanly: block 2048 works, and the 4096/8192/34320 rows of the first
  large-block sweep died in `vision score scale`. The 512 MiB default derives
  320 rows and never reaches it, so this is latent, but a user-raised budget can.
