# Make serving repeat checks profile-aware

## Summary

Corrected serving repeat validation to honor execution-profile semantics. The
first queue1 c32 packet produced two deterministic near-boundary token
trajectories as localhost request arrival changed physical batch composition
between repetitions. The old summary treated cross-schedule generated-ID
identity as binding even in `production`; that is a `batch_invariant` property,
not production same-schedule determinism.

The external FP16 correctness bundle already binds exact three-repeat outputs
under identical manifests and schedules. Actual HTTP serving must additionally
repeat request/control outcomes exactly, while production generated IDs remain
diagnostic as required by `docs/EXECUTION-PROFILES.md` and the user direction.

## Changes

- Made `repeat_determinism_summary()` profile-aware.
- Every profile now binds logical request/prompt membership, prompt/completion
  token counts, finish reason, execution path, and serial-fallback control across
  at least three runs.
- `strict` additionally binds generated output signatures exactly.
  `production` records generated mismatches and hashes but does not fail on them;
  its same-schedule arithmetic repeat gate comes from the validated external
  bundle.
- Added explicit control/generated verdicts and mismatch lists to the artifact.

## Validation

- RED: a production three-run fixture with one generated-ID change failed the
  old universal bit-identity check.
- GREEN: the same fixture passes control repeatability while reporting one
  diagnostic generated mismatch; the strict fixture still fails. Full
  `tests/test_server_f1_concurrency_bench.py` -> 34 passed. Python compilation
  and `git diff --check` pass.
- Actual stopped queue1 c32 diagnostic: every per-run production correctness,
  ownership, native-route, zero-fallback, and completion-count gate passes. Ten
  output-signature differences localize to one repeated near-boundary prompt as
  HTTP admission composition changes; queue1 c17 is exact across all three runs.
  This packet remains diagnostic and is not retained as the queue comparison.
