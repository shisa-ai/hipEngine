# the attention walk's 64-bit address hoist is worth 1.5 percent, and the prologue half was already known inert

## Summary

Pass 3 of the strict prefill attention kernel re-derived its V row pointer inside the
inner loop as `value + (j * num_kv_heads + kv_head) * head_dim`. **The dim loop is the outer
one**, so that expression -- a 64-bit multiply with no hardware support on this target -- was
evaluated `head_dim * keys` times per row. It is now hoisted and advanced by a loop-invariant
stride, and the key/dim indices are 32-bit where they are bounded by the context length and the
head width.

**Prefill falls from 0.66 s to 0.65 s** (5 samples, 782 to 786 tok/s, against 770 to 775
before). All **141 attention tests pass** and the accumulation order is untouched, so the
result is bit-identical rather than merely close.

## The prologue half was already tried and reverted

`20260928T130200` rewrote the block prologue's 64-bit divides with 32-bit intermediates and
**reverted it**: 1,807.9 ms against 1,807.2 ms for the 30 layers at 2048 tokens. Its own
conclusion is the correction that matters here:

> **A region that is a quarter of the static body is not a quarter of the cost** ... The ratio
> also says the loop body is *not* dominated by address arithmetic: 132 scalar against 268
> vector means the vector stream is twice the scalar one inside the loop, so the earlier "the
> scalar stream is the cost" reading was about the kernel as a whole, where the prologue's
> scalar divisions inflate the ratio. **Inside the hot loop the vector stream is the larger
> one.**

So `20260928T121300`'s scalar-issue-bound reading is **superseded** for the hot loop, and the
prologue's 1,622 removable instructions are not the lever. This unit's change is the part that
was *not* tested there: the per-key pointer derivation, which the per-line attribution never
attributed because it sits in the loop body rather than the prologue.

The 1.5 percent is consistent with that: the hoist removes `head_dim * keys` 64-bit multiplies
per row, which is real work on the executed path, but the loop body is vector-dominated so the
ceiling on a scalar-side fix is low.

## Changes

`hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention.hip`, strict prefill kernel only (the
tiled variant was measured 1.44x slower at 2048 and is left alone):

- **Pass 3** -- `v_stride = num_kv_heads * head_dim` computed once; `v_row` hoisted to the first
  kept key plus the thread's dim and advanced by `v_stride` per key. The `weight != 0.0f` test
  became an `if` body rather than a `continue`, so the advance is unconditional and cannot
  desync the pointer.
- **Pass 1, warp path** -- `k_row` hoisted the same way and advanced by `8 * k_stride`, computed
  after the `first_kept` stride-up so it starts at the right key.
- **Pass 1, scalar fallback** -- same hoist.
- **Indices** -- `first_kept`, `walk_end`, the pass-1 key indices and the pass-2 walk index are
  `int`. `blockIdx.x`, `num_heads` and `num_kv_heads` are all far below 2^31, so this is
  provably identical.

## Next

- **The hot loop is vector-dominated**, so the remaining attention lever is fewer *vector*
  operations per key, not fewer scalar ones. `20260928T130200` measured the pass-1 loop body at
  **400 instructions for roughly 55 operations of source work** -- a factor of seven -- and that
  is the number to attack.
- **The 6.1x gap to llama.cpp is still the grid**: one block per (query row, head) re-reads the
  whole KV, where `flash_attn_tile` uses 256x256 query-by-key tiles. The tiled variant in the
  tree tiles over keys only and its grid is also `tokens * num_heads`, so it does not address
  this.
- **Do not re-try the prologue 32-bit rewrite.** It is in `20260928T130200` and it was reverted
  for good reason.
