# Gemma 4 decode attention: 512-thread block for the latency-bound key-class tree (+4% decode)

## Summary

With pass 3 pipelined (iteration 23), passes 1 and 2 were the larger half of the
decode attention kernel: 183-204 us of the 319-340 us launch. Clean ablations
located the cost precisely, each keeping the data dependencies alive so the
compiler could not delete the work being measured:

| ablation (sliding / full, keys=1024) | us | saved |
| --- | --- | --- |
| baseline | 318 / 354 | - |
| shuffle tree replaced by in-lane adds, all loads and FMAs still live | 210 / 279 | **108 / 75** |
| pass-1 key loop skipped entirely | 160 / 234 | 158 / 120 |
| pass-1 LDS logit store removed | 320 / 338 | ~0 |
| pass-2 loop skipped entirely | 322 / 332 | ~0 |
| pass-1 K load replaced by a constant | 294 / 309 | 25 / 31 |

So the tree was the largest single item and it is **latency-bound, not
throughput-bound**: it issues 40 warp-wide shuffles per key (8 elements x 5
levels) in a dependent chain, and a block of 8 warps with one block per
(token, head) - 16 blocks for a decode step - leaves nothing to hide that
latency behind.

**Doubling the block to 512 threads (16 key classes instead of 8)** cuts sliding
318.9 -> 288.4 us and full 339.8 -> 270.1 us at keys=1024, and full 509.5 -> 399
us at keys=2048. Campaign metric **43.6297 tok/s from 41.9049 (+4.1%)**, **+171%
over the 16.0931 baseline**.

## Changes

- `kThreads` 256 -> 512 and keys-per-tile 4 -> 2 in
  `gemma4_decode_class_launch`, with the shared allocation sized for 16 warps.
  Only the key-class split changed: each warp still evaluates the full 256-lane
  tree per key, so every key's own reduction order is untouched.
- **The denominator is pinned to the block kernel's lane count.**
  `gemma4_decode_tree1`'s addition order depends on its lane count, so a
  512-thread block would have rounded the denominator differently from the
  reference. Pass 2 now runs its 256-lane partition and tree on group 0 only;
  the other 256-thread groups execute `gemma4_decode_tree1` with an empty sum
  purely so that every thread reaches its barriers, and every thread reads group
  0's result from `partial[0]`. The LDS layout reserves one 256-float
  denominator region per group, and `kGemma4ReduceThreads` names the constant.
- Rejected, with measurements: level-major interleaving of the four in-flight
  trees (no gain sliding, 11% worse full - the compiler already interleaves and
  the extra live registers cost more), 1024-thread blocks (worse on both
  geometries), and 16-byte vector K loads for pass 1's octet (neutral, which is
  consistent with the K loads costing only 25-31 us).

## Validation

- Decode-parity suite: bitwise equality on every shape, both dtypes, keep and
  holes masks, keys 1..8192. This is the gate that caught both 512-thread
  defects before any campaign row was taken: first an undersized denominator
  region that overran `max_s` (100% of elements wrong), then the unpinned
  reduction order (3.3% of elements off by 1-2 bf16 ulps).
- Attention geometry suite: green.
- Guard suite `pytest tests/test_unit_gemma4_*.py tests/test_gpu_gemma4_*.py -q`:
  exit 0.
- Campaign rows, `--output 128 --samples 3`, label `g3-wide-block`:

| row | decode incumbent | decode now | prefill | public wall |
| --- | --- | --- | --- | --- |
| 1024p (primary) | 41.9049 | **43.6297** (+4.1%) | 129 | 10.58 -> 10.90 s |
| 128p | 48.56 | 48.20 | 139 | 3.58 -> 3.60 s |
| 512p | 46.43 | **47.32** | 135 | 6.56 -> 6.48 s |

`public_path_parity=true` on all four rows. The 128p row is inside the

with a bounded paired rerun rather than treated as a regression: the rerun gave
48.4910, above the iteration-23 incumbent, so the 48.20 reading was run noise.
