# Harden the ShareGPT routing recorder: realized route, error body, coverage cases, refusal cost

## Summary

Five gaps in `scripts/sharegpt_mtp_routing_pass.py` made earlier passes
unreadable, and each one was a real misreading rather than a missing nicety. The
recorder now reports the realized route next to the planned one, records the
in-stream error body of a rejected request, separates the three
speculation-coverage cases, reports per-bucket route refusals, and — the
addition that mattered most in practice — reports the *token* cost of a refusal
next to its event count.

## Changes

### Realized route, not just the planned one

`effective_route` (from `generation_shape.route`), `selected_route`,
`requested_route`, `route_decision_reason`, `k0_class`, `policy_reason`,
`static_intent_allowed`, `realized_group_rows`, `output_horizon_tokens`, and
`selected_candidate_count` are recorded per request, and the summary counts
effective and selected routes separately plus lists every disagreement. Without
this, a pass at c=2 read as "route=speculative_mtp with mtp_used=false" and
looked like a lying route; the server reports the realized route, and the honest
reading is that the route was selected while the plan refused.

### The in-stream error body

A request rejected mid-stream (for example `min_tokens` without `eos_token_id`)
arrives as an ordinary SSE chunk with `finish_reason="error"` and a top-level
`error` object. The recorder recorded only "stream ended without usage", which
hid the cause of every c=4 failure in the first pass. Rows now carry
`error_message`, `error_code`, `error_type`, `error_status_code`, and the full
`error_body`, and the error string itself names them. A row with no error body
still reports the symptom.

### Three speculation-coverage cases

`first_fallback_position` has three states: `0` (speculation never covered a
token), `None` (speculation covered every token after the prompt root, so the
request ended inside it), and a middle value (the request left speculation
mid-stream). The old `if not position` guard collapsed the first and second into
one empty block. `_cliff` now classifies every request, reports the three counts,
measures the rate step only for the mid-stream case, and says why there is no
rate step when there is none.

### Per-bucket route refusals

`prompt_activation_in_flight` (a long prompt still priming its provider) and
`no_provider` (a plan with no provider at all) are counted per prompt-length
bucket, both as requests and as events, plus which of them was the primary
reason. This is what the c=4 pass needed: long prompts lose the route while
mid-length ones keep it.

### Refusal cost in tokens, not only events

The event counts answer "how often was the plan refused", which is not the
question a reader has. A retried planning refusal costs one autoregressive step
and no route. The summary now aggregates the committed-span attribution
(`ar_tokens_by_reason`, `ar_tokens_attributed`) next to the event total, and
prints both against `ar_output_tokens`.

This immediately corrected my own reading of the c=1 result: three requests
reported `no_provider` as their primary fallback reason while being 95.8%
speculative. The spans show why — exactly one AR token per request at position 0,
produced before the provider was ready, after which speculation covered the
remainder. The reason was truthful; only the presentation was ambiguous.

## Validation

- `tests/test_unit_sharegpt_mtp_routing_recorder.py` (new, 9 cases): realized
  versus planned route, error-body capture with and without a body, the three
  coverage cases, mid-stream-only cliff measurement, per-bucket refusal counts,
  route disagreements, token-versus-event separation, and JSON serializability
  of a failed row.
- Live check against the running gfx1151 server (Qwen3.8-27B-Q4_K_M, 3 ShareGPT
  prompts, `--output-len 48`), c=1:
  `mtp_requests=3 (100.0%) mtp_output_share=95.8%`, `effective_routes={"speculative_mtp": 3}`,
  `selected_routes={"speculative_mtp": 3}`, `speculation coverage: never_entered=0 left_mid_stream=0 ended_inside=3`,
  `refusal cost: events=3 spanned_ar_tokens=3 by_reason={"no_provider": 3} (of 6 autoregressive tokens)`.
- The same load at c=2:
  `mtp_requests=1 (33.3%) mtp_output_share=31.9%`, all three still reporting
  `effective_route=selected_route=speculative_mtp`, `spanned_ar_tokens=95` all
  attributed to `no_provider`, `never_entered=2 ended_inside=1`. That is the
  measured baseline for qualifying MTP at wider realized groups (task #24), and
  it is only legible because the route and the token cost are now reported
  together.
- `benchmarks/HARNESSES.md` catalog row updated to describe the new fields.
