# admission prefills one request at a time while a batched path exists

## Summary

Task #14 asked whether the C1-C3 prefill deficit is kernel time or wall time. Reading
the admission loop gives the mechanism: the resident scheduler prefills each admitted
request separately, in a loop, and asserts that it must. A batched prefill entry point
exists in the same engine and is not used here. This is the most concrete prefill lever
found in the campaign.

## Changes

- None. Read-only.

## Validation

`hipengine/generation/qwen35_gguf.py:4413` `admit_available()`:

- it admits while `scheduler.active_count < int(capacity)`, then iterates
  `for request_id in admitted:` and calls `session.prefill_slot(work.token_rows[0], slot=...,
  return_logits=False)` inside that loop, so N admitted requests cost N separate prefill
  calls;
- it enforces this: `next_prefill_work(chunk_size=resident_max_sequence_length)` is
  expected to return work for exactly one request, and the code raises
  "GGUF scheduler prefill order diverged from admission order" if
  `work.request_ids != (int(request_id),)`.

The alternative already exists: `prefill_batch_native` at
`hipengine/runtime/qwen35_gguf_runner.py:20593`, with `_prefill_batch_native_impl` at
:20664 and a single-slab variant at :20908, and the comment at :20627 notes that
`generation/qwen35_gguf.py` binds it. So batching is available and simply is not used on
this admission path.

This matches the independent measurements:

- the admission decomposition reported AR admission scaling 302.4 to 2320.7 ms across
  C1-C8, a 7.68x rise, against the peer's 3.79x, "because our admission does not
  overlap requests". Serial per-request prefill is linear in request count, which is
  exactly a 7.68x-ish shape;
- prefill probes show 167.603 tok/s at 45 rows and 877.025 tok/s at 512 rows. If each
  request prefills alone at 45 rows, the 107-block grid runs at its worst and never
  amortizes;
- we win the cells where batching does happen, C4 and C7, and the published prefill
  packet is from after grouped prefill was declared for gfx1100, so grouped prefill is
  live on other paths but not this one.

Caveat kept: I have not measured how much of the admission wall is `prefill_slot` versus
slot setup, tokenization, or bookkeeping, and this loop may be intentional for slot
ownership or deadline handling. Both need to be checked before changing it.
