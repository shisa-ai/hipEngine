# Phase 4 after the rows sibling: re-ranked candidates, two rejected scoped changes, and the remaining latency-bound levers

## Summary

The rows 2-4 local32 IQ verifier sibling (`2ac44d7a7`, retained in
`1c118fdde`) removed the strict per-row IQ GEMV from the verifier's dominant
slot. This entry re-runs the Phase 1 census on the current tree, per kernel
instantiation, and uses it to close or re-rank the rest of the Phase 4
candidate list. Two scoped candidates were implemented far enough to measure
and were **rejected**; both results localise the remaining headroom.

The verifier at block-rows 4, ten measured steps, ROCTX-filtered (ms/step of
kernel time, share of that arm's verifier kernel time):

| Kernel | UD-Q4_K_M | plain Q4_K_M |
| --- | ---: | ---: |
| `q5_k_t16_dense_rowtile_gemv<ushort,4,4>` | 9.23 (19.6%) | 2.84 (9.0%) |
| `gguf_iq4_xs_local32_gemv<2,4>` | 8.44 (17.9%) | - |
| `gguf_q5_k_t16_dense_dual_wmma_prefill_silu_bf16<1,2,128>` | 5.68 (12.1%) | - |

| `gguf_iq_dense_strict<3,true,8,4>` + `<2,true,8,4>` | 3.37 (7.2%) | - |
| `q6_k_t16_qmicro_planar_gemv_rowtile_col8<ushort,4,false>` | 0.77 (1.6%) | 6.23 (19.9%) |

| **arm total** | **47.09** | **31.39** |

UD's deficit is 15.70 ms/step. It is not one kernel: UD is *cheaper* than the
plain control on Q6_K (-5.46), on the gate/up pair total (6.38 against 8.85,
because the WMMA prefill dual is the cheapest arm measured) and on the Q4_K
rowtile (-1.61), and *dearer* on Q5_K rowtile (+6.39), the IQ4_XS local32
family (+12.24, which is UD's quant choice rather than waste), and the
remaining strict IQ GEMV (+3.37).

**Correction to the census reading.** `rocprofv3` `Grid_Size_X` counts
work-items, not workgroups; the block count is
`Grid_Size_X / Workgroup_Size_X`. Every grid in this artifact is reported in
both forms. The earlier Phase 1 numbers were read as blocks, which is why the
grids looked impossible against the GGUF shapes.

## Candidate 1 (rejected): Q5_K rows 2-8 rowtile column width 4 -> 8

`q5_k_t16_dense_rowtile_gemv_kernel<scalar_t, ROW_TILE, TILE_COLS>` with
`TILE_COLS=4` launches four blocks per 16-column tile and each block reads the
whole 16-column tile (`Q5_T16_BLOCK_BYTES` is a single constant), so the
family re-reads its weights 4x. `TILE_COLS=8` halves that, and the col8
variant is already registered
(`gguf_q5_k_t16_v1 / t16_gemv_rowtile_col8_bf16_bf16_out`) but nothing
dispatches to it. The hypothesis was that the re-read is the limit.

Routing the col4 launcher body at the col8 launcher and re-running the same
census:

| | col4 | col8 | delta |
| --- | ---: | ---: | ---: |
| arm kernel ms/step | 47.09 | 47.90 | +1.7% |
| Q5_K rowtile ms/step | 9.23 | 10.61 | +14.9% |
| Q5_K rowtile us/call | 85.5 | 98.2 | +14.9% |
| VGPR | 56 | 88 | |

**Rejected.** The tile re-read is served by L2 and is not the limit. col4 wins
because it launches twice as many blocks; the family is parallelism-limited,
not L2-bandwidth-limited.

## Candidate 2 (rejected as neutral): local32 activation load vectorization

Each lane in the local32 owners issues eight scalar BF16 activation loads per
(row, blk) from a 16-byte contiguous window. Replacing them with one `uint4`
load (`bf16_load8`) cut the load count per (row, blk) from eight to one in all
three owners. Re-running `scripts/gguf_iq_local32_rows_headroom.py` on the same
four real IQ4_XS tensors:

| | before | after | delta |
| --- | ---: | ---: | ---: |
| rows 2-4 sibling ms (sum, rows 4) | 0.3782 | 0.3708 | -1.9% |
| rows == 1 owner ms (sum, rows 4) | 0.9137 | 0.9273 | +1.5% |
| bit-exactness | preserved | preserved | |

**Rejected as neutral.** Both deltas are inside run-to-run spread. The compiler
already coalesces the contiguous scalar loads, so the family is not
load-issue-bound. The change was reverted; no source in this unit.

Taken with candidate 1, this localises the remaining IQ4_XS headroom to
**memory-level parallelism at fixed occupancy**: 12.24 ms/step at 46%
(`ffn_gate`, N=17408 K=5120) and 58% (`ffn_down`, N=5120 K=17408) of the
960 GB/s DRAM roofline, with 192 VGPRs and `__launch_bounds__` pinned to one
resident block for `ROWS > 1`.

## Candidates closed with the fresh attribution

- **UD Q5 selected-expert path.** `qk_t16_selected_direct_gemv` is 0.367
  ms/step (0.78%) on UD-Q4_K_M and 0.662 (1.46%) on UD-Q4_K_S. No material
  lever at verifier rows.
- **Q5 gate/up dual execution.** The Q5_K gate/up dual runs the WMMA prefill
  owner at verifier rows (5.68 ms/step). The whole gate/up pair costs 6.38
  ms/step against the plain Q4_K dual rowtile's 8.85, so UD's arm is already
  the cheaper one. No action.
- **Q5/Q6 compact residency and raw consumer qualification.** Q6_K col8 is
  0.77 ms/step in UD against 6.23 in plain Q4_K_M; Q5_K residency is the col4
  rowtile measured above, whose col8 alternative lost. UD is already cheaper
  than the control on both.
- **Q3_K strict decode.** Q3_K has no rows==1 local32 owner, so it has no rows
  2-4 sibling. Routing it was measured on gfx1151 at +176.5 tok/s but moved the
  calibrated mean KL 0.000827 -> 0.001061, 6% over the 1e-3 limit. Blocked on
  the calibrated mean-KL gate; the strict per-row GEMV stays the owner.
- **Norm, SiLU, residual, and logits tail.** `rounded_add_rmsnorm` 0.836 +
  `add_rmsnorm` 0.770 + `silu_mul_separate` 0.104 + `full_attn_gate_mul` 0.102
  + head rmsnorm 0.073 = 1.885 ms/step, 4.00% of the UD-Q4_K_M verifier. Below
  the repair threshold at verifier rows.

## Open, with concrete blockers

- **IQ4_XS local32 rows decoder memory access** (12.24 ms/step, 26.0%). The two
  instruction-level candidates above were neutral-to-negative, so the lever is
  memory-level parallelism at fixed occupancy: explicit prefetch or a wider
  row/wave split. Both change the block geometry, so they need a
  hardware-counter unit (occupancy, L2 hit rate, stall reasons) plus a new
  bit-exactness contract.
- **Q5_K rows 2-8 rowtile parallelism** (9.23 ms/step, 19.6%). col8 (fewer,
  fatter blocks) is worse, so the family wants more concurrent blocks or a
  split-K reduction. Split-K changes the per-output accumulation order, which
  `docs/UD-GFX1151-OPTIMIZE.md` already names as the dominant AR-versus-verifier
  drift source, so it owes the full production profile gate rather than a
  bit-exactness screen.
- **Host residual (launch overhead).** 5.25 ms/step against 1032 kernel
  calls/step, 5.09 us per launch; the plain control is 824 calls/step,
  4.39 ms/step and 5.33 us per launch. The residual is launch overhead, so
  reducing it means fewer, wider launches or replay-side launch elision, a
  scheduler/graph-ownership unit rather than a kernel unit.

## Validation

- **Device identity.** Every run set `HIP_VISIBLE_DEVICES=1` with
  `ROCR_VISIBLE_DEVICES` unset; the suite's `--expect-device` check reported
  `AMD Radeon RX 7900 XTX` (gfx1100). Physical GPU0 (W7900) was not touched.
- **Leaf representativeness.** Production-matching native target graph
  (`device_accept_commit=True`, `bulk_attention_mode='native'`,
  `remaining_decode=rows-1`), 8 measured steps after 2 warmup steps.
- **Bit-exactness screen.** The vectorization candidate kept
  `sibling_bit_exact_per_row` true on all four IQ4_XS tensors at rows 2 and 4.
- **Focused tests.** `pytest tests/test_gguf_iq_local32_rows.py
  tests/test_gguf_iq_local32_decode.py` passes with the vectorization applied,
  which is what makes the neutral result a measurement of the load count rather
  than of a broken kernel.
