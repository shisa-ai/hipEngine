# The accept window issues synchronous pageable hipMemcpy, so it cannot overlap

## Summary

Read the accept window's copy path. It is not bookkeeping volume and not the readback: `_enqueue_target_batch_accept`
issues **synchronous `hipMemcpy` from pageable numpy memory** three times per cycle, immediately after the verify
kernels are launched. That forbids host/device overlap by construction, so device queue latency is necessarily
attributed to `mtp2_accept_ms`.

## Changes

- This entry records the code finding; no code change. Task #17 retitled.
- Prior commits stand: `c678c685a` (target-readback counter), `7c0a0c62a` (its 1.6% measurement).

## Code path (read, not inferred)

- `_upload_accept_array` (qwen35_gguf_mtp2.py:2143): `array = np.ascontiguousarray(values)` then
  `copy_host_to_device(..., host_array_ptr(array), ..., runtime=runtime)`. NumPy arrays are pageable.
- `copy_host_to_device` (hipengine/core/memory.py:124) is `runtime.memcpy(ptr, host_ptr, count,
  MemcpyKind.HOST_TO_DEVICE)` -- the **blocking** entry point, not `memcpy_async`, which the file uses elsewhere
  (so the async variant exists and is simply not used here).
- Three such uploads per cycle in the enqueue (:2205, :2223, :2233) plus a per-row `runtime.memcpy_async` loop
  over device pointers (:2246), which is device-to-device and cheap.
- Consequence: with a legacy-default-stream synchronous copy, the first upload waits for the in-flight verify
  work. accept_ms therefore contains device queue time, and the engine does no host work while the GPU verifies.

## What this does and does not explain

- Measured accept is 87.6-104.3 ms per lane-cycle at C5-C8 and target (verify launch window) is 31.4-39.7 ms
  (`/tmp/he-parity/he-readback.json`). A single queue drain explains roughly the target-sized share, not all of it:
  about 50-65 ms per lane-cycle stays unattributed.
- So this is a real, fixable serialization, and it is still not a complete account. The per-upload counter
  (`upload_seconds` carried on `_PhysicalAcceptPending`, not yet written) remains the deciding instrument.

## Candidate fix (not attempted, needs gates)

Stage the three accept arrays through pinned memory -- the repo already has pinned-arena staging precedent in
`scripts/gguf_packed_prefill_block_route_bench.py::_arena_stage` -- or switch the three uploads to the async
variant on the runtime's stream. Either changes when device work is waited on, not arithmetic, but it reorders
host/device interaction, so it needs the exact-output K3 gate plus a same-protocol repeat measurement before it
can be claimed. Not attempted in this session: context exhausted mid-campaign, and a half-validated overlap change
is exactly the class of change that produced the earlier false K2 story.
