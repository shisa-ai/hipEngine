# pm4 and aql graph-submission timings on gfx1100

## Summary

Extended `scripts/inkling2_dispatch_probe.py` with `--transports aql pm4`: the
same captured N-kernel chain is submitted through the in-tree native
submission registry (`hipengine/core/pm4/transport.py`) instead of the HIP
graph path. Same W7900 host, idle at measurement start; one capture, replayed
50 times, timings per launch.

Measured (capture size -> eager Python launch / hipgraph replay / aql / pm4):

- 48 nodes: eager 4.95 us, hipgraph 3.73 us, aql 4.01 us, **pm4 1.77 us**
- 1,300 nodes: eager 4.29 us, hipgraph 2.81 us, aql 3.45 us, **pm4 1.29 us**

pm4 is ~3.3x faster per launch than eager at 1,300 nodes and ~2.2x faster than
hipgraph replay, and the gap grows with chain length. aql lands between eager
and hipgraph. This is direct evidence for the plan's hypothesis that native
submission (not graph capture per se) is the dispatch lever on this part —
exactly the comparison step 0 asked for.

Caveats, honestly:

- Single comparative run for the transport numbers; eager/graph measurements
  across the day show a bimodal pattern (either ~4.3/2.8 us or ~5.5/5.5 us),
  likely clock/power state on an idle card. The pm4-vs-hipgraph ordering held
  within the one run where both were measured back-to-back, but the transport
  numbers have not been replicated yet.
- Both native submissions were accepted by the graph inspector for a chain of
  no-op kernels. Whether real model graphs (with copies and atomics) pass
  inspection is untested.
- These numbers do not include model kernel execution; they are dispatch
  overhead only.

`HIP_FORCE_DEV_KERNARG` sweep (separate process each, `--skip-gemv`, 1,300
nodes): 0 -> eager 5.55 us / graph 5.57 us; 1 -> eager 5.60 us / graph 5.61 us.
No measurable effect on this host/build.
