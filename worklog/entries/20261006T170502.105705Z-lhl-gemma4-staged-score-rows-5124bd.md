# Group eight query heads per staged score CTA

## Summary

The staged score kernel decoded each K vector once per warp for only two
query rows, so at the full-attention geometry (GQA ratio 8) the same K chunk
was decoded four times per (token, kv_head). This unit raises the score CTA's
resident rows from 2 to 8: one warp decode now feeds eight strict trees and
the full-layer score grid loses 4x its CTAs. The per-(row, key) warp-key tree,
the softmax and the ascending-key P*V chain are untouched, so the output stays
bit-identical to the strict family and no execution-profile gate is required.

Measured on the production route (beat-llamacpp-all-depths loop baseline,
zbook/Radeon 8060S, 32768-prompt prefill, context 33024, one warmup and one
sample per run, two runs): 326.23 and 326.11 tok/s against the 324.88 baseline,
+0.4%. The gain is within run-to-run noise. The hypothesis that the score
stage is K-decode-bound or CTA-count-bound is falsified by these measurements:
a 4x cut in full-layer decode work and CTA count moved the metric almost
nothing. The change is kept anyway -- it is bit-exact by construction, passes
every gate, is not a regression, and is the structural foundation the next
score-stage work builds on. Instruction-mix arithmetic alone does not predict
this kernel's throughput; the next change must be justified by profiler
counters, not by issue-count estimates.

## Changes

- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention_staged.hip`:
  `kStagedScoreRows` 2 -> 8, running-max array generalized from a two-element
  initializer to an unrolled loop, and the header/section prose updated (the
  "constant 8 KB" claim replaced with the actual largest term, the 16.6 KB
  eight-row score tile at head_dim 512).
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention_staged.py`:
  `SCORE_ROWS_PER_BLOCK` 2 -> 8 and the matching docstrings.
- `tests/test_unit_gemma4_attention_staged.py`,
  `tests/test_gpu_gemma4_attention_staged.py`: expectations moved to the
  eight-row contract. The invariants the tests protect are unchanged: score
  groups never cross a KV-head boundary and cover every query head exactly
  once, the workspace stays per query row, the shared footprint stays constant
  in `keys` and inside the budget, and the kernel exports match the Python
  planner.
- No workspace-layout change: `staged_plan(...).workspace_bytes` is identical
  before and after, so the capacity probe's depth-transient model is
  unaffected.
