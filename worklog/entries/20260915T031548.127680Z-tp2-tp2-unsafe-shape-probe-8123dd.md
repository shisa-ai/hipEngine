# The fused-route shape probe launched with null device pointers

## Summary

The review is correct, and the previous entry's method was unsafe. To learn
whether the fused gate/up+SiLU kernel accepts a half-intermediate shard shape,
`fused_path_admission()` called the real launcher
`gguf_q4_k_t16_dense_dual_local32_silu_bf16_bf16_out(0, 0, 0, 0, 1, 5120, 8704)`.
The launcher validates the shape, then loads the kernel library and launches - it
has no pointer guard - so on any host where the library loads, a valid shape with
null pointers **enqueues an invalid device launch**. Catching the Python exception
says nothing about what the device was asked to do. The entry that introduced this
is `20260915T024706.345742Z-tp2-tp2-fused-route-admission-808ffc.md`; its finding
stands, its method is withdrawn.

The repo's own convention, visible in
`test_sampler_wrapper_validates_shapes_before_loading_hip` and the q6 GEMV tests,
is that null pointers are only ever passed to launchers with **invalid** shapes,
which raise before any HIP contact. This probe passed a **valid** shape, so it went
past validation into a launch. On the W7900 host - where both the `--device`
probe run and the unit tests execute - the launch was attempted.

## Changes

`hipengine/kernels/hip_gfx1100/quant/gguf_t16_selected_gemv.py` now carries the
shape contract as a pure function:

```python
dense_t16_pair_decode_shape_error(*, rows, in_features, out_features) -> str | None
```

Both pair decode launchers (Q4 dual local32 SiLU, Q5 dual GEMV) consult it and
raise its reason before any HIP contact, so the contract has one source of truth
and the rejecting boundary stays safe to test. The probe asks the validator - no
pointers, no library, no launch, and it now answers on a host with no HIP at all.

Three guards pin the safety property:

- `test_the_launcher_refuses_exactly_what_the_contract_refuses` - with the runtime
  and library loaders monkeypatched to raise `AssertionError`, the launchers must
  reject the contract's invalid shapes with the validator's own reason. Any
  regression that launched before validating fails the test instead of
  enqueueing a launch.
- `test_the_probe_answers_the_admission_question_without_hip` - the same patched
  loaders, then `fused_path_admission` must still produce its record.
- `test_the_shard_shape_satisfies_the_pure_shape_contract` - the contract's
  accepting and rejecting boundary, asked directly.

## Effect on the finding

None. The regenerated artifact
(`benchmarks/results/2026-09-15-w7900-tp2-mlp-shard-plan-probe.json`) records the
same result with honest provenance:

```json
"tp1_admitted": true,
"shard_admitted": false,
"tp1_shape_error": null,
"shard_shape_error": null,
"shape_contract": "dense_t16_pair_decode_shape_error"
```

TP1 `(1, 5120, 17408)` is admitted to `GGUF_DENSE_PAIR_SILU_DECODE_POLICIES`;
the shard `(1, 5120, 8704)` is absent but inside the kernel's shape contract, so
the gap is a policy admission rather than a kernel. The field
`kernel_accepts_shard_shape` (a string describing how far a null-pointer launch
got) is gone; `shard_shape_error` (null means accepted) replaces it.

## Incident scope and device state

The previous artifact run (`--device`, commit e9e678b02) performed the invalid
launch attempt; the unit tests in that commit also reached the launcher, and on
the GPU host they would have attempted it too. What the device was actually asked
to do depends on the driver's handling of a null-pointer launch, which I cannot
prove after the fact; the recorded `RuntimeError` in the old record is consistent
with a synchronous launch failure, but that is an inference, not a measurement.
After the incident and before this artifact was written, the device ran 296 kernel
tests (`tests/test_gpu_gguf_t16_selected_gemv_decode.py`,
`tests/test_gpu_gguf_q4_k_t16_dense.py`) including CPU-oracle comparisons
against the refactored launchers, all passing, so the runtime is healthy. Nothing
else in the packet used the unsafe pattern: the null-pointer calls elsewhere in
`tests/` pass invalid shapes and so raise before HIP contact, matching the repo
convention.
