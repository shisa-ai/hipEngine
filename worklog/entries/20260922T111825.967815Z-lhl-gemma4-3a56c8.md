# Gemma 4 GGUF streaming forward validated on the real artifact

## Summary

Adds a bounded-memory streaming forward for Gemma 4 GGUF artifacts and validates
it against HuggingFace on the real 26B-A4B weights. The dequantized weights feed
both implementations, so the comparison isolates the arithmetic. Layer 0
(sliding attention) agrees to `3.9e-7` relative and the check is repeatable on
the structurally distinct global layer 5 (proportional partial RoPE, 512-wide
heads, `V = K`).

The real-artifact probe produces on-topic chat continuations, which is the first
evidence that the port decodes this model rather than merely running.

## Changes

- `hipengine/kernels/cpu_reference/gemma4_streaming.py`: `Gemma4GGUFStreamingWeights`
  (lazy per-layer dense tensors and per-expert slices, both behind byte-bounded
  LRU caches), `_streaming_layer_forward`, and `gemma4_streaming_forward`.
  The expert axis is outermost in the GGUF, so `raw[expert]` is a contiguous
  slab and one expert dequantizes without touching the other 127.
- `tests/test_unit_gemma4_gguf_streaming.py`: 12 tests over a synthetic fixture —
  streaming logits equal the reference exactly, streaming layer output equals the
  reference layer, appending tokens leaves earlier logits unchanged, expert
  gather matches a full-tensor dequantization, only selected experts are
  dequantized, and the head is refused on a tied artifact.
- `scripts/gemma4_real_layer_dump.py` / `scripts/gemma4_real_layer_hf_check.py`:
  the real-weight differential harness. Dumps one layer as float32 and runs the
  HuggingFace `Gemma4TextDecoderLayer` on those same tensors.
- `scripts/gemma4_real_probe.py`: chat-templated top-k probe on the real artifact.

## Validation

Differential against HuggingFace, same dequantized float32 weights on both sides,
real `text_config` from `google/gemma-4-26B-A4B-it`, real token block:

- Layer 0, `sliding_attention`: max abs diff `2.5e-5`, `3.9e-7` relative to the
  layer output absmax. Per-row diffs are uniform, so this is float32 rounding.
- Layer 5, `full_attention`: max abs diff `6.9e-6`, `2.4e-7` relative. This is
  the structurally distinct branch — `global_head_dim` 512 with 16 query and 2
  KV heads, proportional partial RoPE over 64 of 256 pairs, and `V = K` with no
  `v_proj` tensor at all.

The layer is called with an explicit additive causal mask. A standalone
`Gemma4TextDecoderLayer` with `attention_mask=None` silently falls back to full
attention, which makes every row except the last differ by up to 7.8% of absmax
for a reason unrelated to the reference. This is a trap for anyone repeating the
comparison.

Weight values checked against the official bf16 checkpoint by HTTP range request:

- `blk.0.attn_q.weight` (Q8_0) vs `self_attn.q_proj.weight`: 0.40% max relative
  difference, which is Q8_0 quantization error.
- `blk.0.ffn_gate_up_exps.weight[0]` rows `[0:704]` match HF
  `experts.gate_up_proj[0, 0:704]` to 4.4%; rows `[704:1408]` match
  `[0, 704:1408]` to 5.7%. Cross-comparison is 130-185% off, so the fused
  gate/up halves are not swapped.
- `layer_scalar`, `router.scale`, `router.per_expert_scale` are identical to the
  checkpoint. `layer_scalar` really is 0.0703125 for layer 0 and 0.1953125 for
  the last layer; the small values are trained, not a decode error.

Real-artifact probe, `UD-Q4_K_XL`, chat-templated:

| Probe | Prompt tokens | Top-1 |
| --- | --- | --- |
| capital of France | 20 | `The` (with `Paris` in the top 12) |
| 2 + 2 | 21 | `2` (with `4` in the top 12) |
| say hello in one sentence | 20 | `Hello`, then `hello`, `Hello`, `Greetings`, `hello`, `Hell`, `Hi` |

Raw un-templated prompts are out of distribution for this instruct model and
produce channel markers such as `thought`; that is expected behaviour, not a
defect.

Correctness limits worth recording:

- `gemma4_streaming_forward` is prefill-shaped. Every call re-reads the whole
  token block, so it is quadratic in the prompt. It exists to validate the
  artifact, not to serve requests.
- Agreement is measured per layer with identical weights. It does not bound the
  accumulated error of a 30-layer forward at Q4_K, which the probe exercises but
  does not quantify against a full-precision baseline.

## Next

- The GPU serving path is not implemented. `hipengine.LLM.generate()` cannot
  reach Gemma 4 today; the reference and streaming CPU forwards are validation
  surfaces. Registering the Gemma 4 layers against `hip_gfx1100` is the next
  unit, and `hipengine/models/gemma4.py` already carries the unfused primitive
  plan for both attention kinds.
- `gemma4_streaming_forward` should gain a KV-cached decode step before it can
  back any real workload.
