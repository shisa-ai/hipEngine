# Surya OCR 2 torch oracle fixtures (milestone 1c)

## Summary

FP32/CPU transformers oracle for the Surya port: scripts/surya_oracle_torch.py
captures text-only and image prefill+decode boundaries into
tests/fixtures/surya/ for later RED/GREEN checks of the hipEngine path.

## Changes

- scripts/surya_oracle_torch.py (fixture generator only; hot path stays
  torch-free): synthetic deterministic 256x256 page PNG; text-only +
  image cases; per-case prefill logits, 4 teacher-forced cached decode
  steps (fixed ids 100/5000/20000/42), full-attention KV for layers
  3/23, GDN conv+recurrent state for layers 0/20, 3-axis mRoPE
  position_ids via a rotary-module hook, vision boundaries (patch embed,
  tower pre-merger, merged features).
- tests/fixtures/surya/: oracle_image.npz (8.7MB), oracle_text.npz
  (2.0MB), page_small.png, meta.json (sizes in line with existing
  evie/dflash fixtures).

## Validation

- Fixture contracts (tests/test_surya_oracle_fixtures.py, 8 tests):
  64 image pads expand 1 template placeholder; mm_token_type_ids marks
  exactly the 64-pad contiguous span; position_ids are 3-axis with
  spatial compression (image last mrope 49 < 106 tokens; text 0..39);
  GDN conv state (1,6144,4) matches the manifest conv1d width and
  recurrent state (1,16,128,128) fp32; full-attn KV (1,2,106,256);
  decode steps advance KV by 4; logits finite; image/text first logits
  differ; meta EOS=2 (never the stale 248044).
- transformers 5.15 contract facts captured for the runtime: processor
  returns mm_token_type_ids (required by the model for multimodal
  RoPE); text-only prefill computes positions internally while the
  image path passes them through; torchvision here lacks libPNG so the
  generator passes PIL images, not paths.
