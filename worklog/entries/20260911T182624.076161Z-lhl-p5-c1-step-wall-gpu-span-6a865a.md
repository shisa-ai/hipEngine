# The C1 decode step wall is GPU-span-bound, not host-bound: a cProfile intervention

## Summary

Task #24 asked me to decompose the 14.951 ms/step of host time before choosing
between graph capture and launch reduction. The decomposition answered that
question and then invalidated the premise behind it.

The host time is Python, not HIP API launch cost: the committed trace's HIP API
union is 19.573 ms/step, already about equal to the readback alone, so the ~793
launches add only ~3 ms of API time.

The more important finding came from an intervention. I ran the identical child
twice, once normally and once under `cProfile`, which slows host Python without
touching the GPU kernels:

| Run | Step wall | Blocking readback | Host outside readback | Sum |
| --- | --- | --- | --- | --- |
| Unprofiled | 35.079 ms | 20.186 ms | 14.951 ms | 35.137 ms |
| Profiled | 35.507 ms | 2.330 ms | 33.178 ms | 35.508 ms |

Host Python changed **2.22x** while the step wall moved **+1.22%**. The two phases
trade one-for-one and their sum is conserved to within 0.2% of the wall in both
runs. The readback is simply the GPU time the host has not yet covered.

**Neither candidate lever can work.** Deferring the readback recovers nothing,
because the readback *is* the uncovered GPU time. Speeding up the host recovers
nothing, because the wall does not move when host Python changes by 2.2x. The step
wall is set by the GPU side at a span of roughly 35 ms per step.

## The revised target

The GPU holds the step for ~35 ms while executing only **17.347 ms** of kernels
(device union), so about half the span is inter-kernel gap rather than execution.
The lever is reducing that span: fewer and larger kernels (fusion), or a captured
graph replay that removes per-launch gaps. Graph capture already exists on the c8
packed route while the C1 route is eager.

## Validation

- Two child runs on W7900 / gfx1100, cache-only (`HIPENGINE_REQUIRE_CACHED_BUILD=1`,
  pinned compiler version), 62 measured steps at 2048 prompt rows, Qwen3.8-27B
  `Q4_K_M`, INT8 KV. Second run under `python -m cProfile`. Values above.

Honest limits, recorded in the artifact:

- Two points, not a sweep. The intervention varies host Python by 2.22x in a single
  step; a monotonic series would strengthen the invariance claim, though the
  conservation is already tight to 0.2% in both runs.
- `cProfile` inflates Python cost non-uniformly across functions, so the profiled
  run shows that the host side is not binding but does not give a faithful host-side
  cost ranking. The unprofiled 14.951 ms remains the better estimate of host work.
- The ~35 ms GPU span is inferred as wall minus pre-host time rather than measured
  from the trace's first-launch and last-finish timestamps. A direct span
  measurement should confirm the gap figure before it drives a kernel-fusion plan.
- No optimization was attempted. This is a negative result about two candidate
  levers, not a measurement of any span-reduction alternative.
- `performance_claim` is false and no scoreboard row changed.
