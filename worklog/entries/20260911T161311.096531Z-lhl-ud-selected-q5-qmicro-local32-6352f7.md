# Selected Q5 MoE down: qmicro local32 owner (isolated cycle win, neutral aggregate)

## Summary

A prototype for a selected-expert Q5 local32 decode owner was left in the tree
by a review agent, self-assessed at ~35% complete with "no successful compile or
post-implementation test run". That assessment was too pessimistic in one
direction and too optimistic in another:

- It **does** compile, is registered, and its numerical test passes.
- But the numerical test only covered `x_rows == 1`, which the selected-expert
  dispatch never emits, so the kernel was silently wrong for the real path.
- Its policy key `(17_408, 5_120)` is the **dense Qwen3.6-27B FFN-down** shape,
  and it was keyed on `gguf_q5_k_t16_v1`, while the MoE decode path materializes
  those weights as `gguf_q5_k_qmicro_t16_v1` at `(512, 2048)`. The route could
  never fire.

After retargeting, the kernel is exact and 1.38x faster than the production
owner in isolation at the production shape, and the route is live in a real
decode. The **end-to-end decode rate is neutral** (+0.013%, within noise), so
this is retained as a kernel-level cycle win only, with no topline claim.

## The three real defects

1. **Row-to-x mapping.** The direct selected owner maps each output row to its
   own x row (`x_row_idx = (x_rows == 1) ? 0 : row / (rows / x_rows)`). The
   prototype read one shared x vector for every selected row. Correct only when
   `x_rows == 1`; production always launches `x_rows == rows == top_k` (8 for
   this model), so it was wrong on the real path. Fixed by mirroring the direct
   owner's mapping exactly, in both the plain-T16 and qmicro kernels.
2. **Shape key.** `(17_408, 5_120)` is the dense Qwen3.6-27B FFN-down shape, not
   a selected-expert shape. The MoE selected down for
   `Qwen3.6-35B-A3B-UD-Q4_K_M` is `in=512` (moe_inter) -> `out=2048` (hidden),
   keyed `(in_features, out_features)` as `_launch_selected_raw_gguf_moe_linear`
   names them.
3. **Quant key / layout.** The MoE decode path repacks Q5 expert weights to the
   qmicro planar layout, so the quant key is `gguf_q5_k_qmicro_t16_v1`. The
   prototype's kernel reads the plain T16 planes and its policy was keyed on
   `gguf_q5_k_t16_v1`. A qmicro-planar sibling was written
   (`q5_k_qmicro_t16_selected_local32_gemv_kernel`) that keeps the metadata in
   registers instead of the production owner's cooperative shared-memory unpack.

`EXACT_SELECTED_MODES["gguf_q5_k_qmicro_t16_v1"] == ("single",)` confirms the
down path is the plain `_launch_selected_raw_gguf_moe_linear` route, with no
fused weighted-down bypass, so the new owner is on the real path.

## Changes

- `hipengine/kernels/hip_gfx1100/quant/gguf_t16_selected_gemv.hip`: added
  `q5_k_qmicro_t16_selected_local32_gemv_kernel` (32 lanes, eight columns,
  single wave, register metadata) and `launch_q5_qmicro_selected_local32`; fixed
  the row-to-x mapping in `q5_k_t16_selected_local32_gemv_kernel`.
- `hipengine/kernels/hip_gfx1100/quant/gguf_t16_selected_gemv.py`: wrapper for
  the qmicro variant, registry entries for both local32 owners, `__all__`.
- `hipengine/kernels/hip_gfx1100/__init__.py`:
  `GGUF_T16_SELECTED_C1_VARIANTS_BY_QUANT_SHAPE` retargeted to
  `gguf_q5_k_qmicro_t16_v1` + `(512, 2048)`.
- `hipengine/runtime/qwen35_gguf_runner.py`: `_gguf_t16_selected_c1_variant`
  gates on the geometry the kernel supports (`rows % x_rows == 0`) instead of
  `x_rows == 1`, which the selected path never satisfies.
- `tests/test_gguf_q5_selected_local32_decode.py`: parameterized the numerical
  test over shared-x, production (`x_rows == rows`) and batched row contracts,
  added the qmicro variant compared against the production qmicro tile8 owner at
  the production shape, and replaced the obsolete `x_rows=1` rejection test.
- `benchmarks/results/2026-09-12-gfx1100-selected-q5-qmicro-local32-ab.json`.

## Validation

- `pytest tests/test_gguf_q5_selected_local32_decode.py` — 11 passed.
- RED verification, both kernels: reintroducing the shared-x read fails the
  three multi-row cases while `x_rows=1` still passes (exactly why the original
  test missed it); corrupting the qmicro metadata record index fails all four
  qmicro cases.
- `HIP_VISIBLE_DEVICES=0 pytest tests/test_gguf_ud_dense.py` — all passed (the
  UD numerical gate needs exactly one visible device; without it 638 tests skip).
- `pytest tests/test_gguf_ud_admission.py tests/test_ud_mtp_certification.py` —
  passed.
- Route liveness in the measured sweep decode: 74 resolutions of
  `gguf_q5_k_qmicro_t16_v1` + `selected_t16_local32_gemv_decode_bf16_bf16_out`
  for a 128/16 workload.
- Isolated kernel timing, production geometry (in=512, out=2048, experts=256,
  rows=8, x_rows=8, 400 iterations after warmup):
  production qmicro tile8 **15.91 us** vs qmicro local32 **11.53 us** = **1.3806x**.
- End-to-end A/B, same tree and binaries back to back, only the policy table
  differing (`{}` vs populated), `512/128`, warmup 1, 3 measured runs:
  baseline **93.805** tok/s (stdev 0.044) vs candidate **93.817** tok/s
  (stdev 0.062) = **+0.013%**, neutral.

## Next

- No in-decode kernel trace accompanies this: `rocprofv3 --kernel-trace` hangs
  in this environment on both the pytest and the sweep (30 min and 11 min
  without producing output; the earlier 30-minute run left an orphan holding
  25.6 GiB of GPU0), and the measured decode is graph-captured so per-kernel HIP
  event timing is rejected ("operation not permitted on an event last recorded
  in a capturing stream"). A real profile of the selected-down share is the
  missing piece before this can be claimed as an end-to-end win.
- The end-to-end effect should be re-measured on a model/protocol where the
  selected down projection is a larger share of decode, or at a larger `top_k`.
- If a future profile shows the selected down is immaterial at every supported
  shape, delete the local32 owners rather than keeping two owners for one path.
