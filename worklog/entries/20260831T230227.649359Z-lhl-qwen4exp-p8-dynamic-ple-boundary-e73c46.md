# Resolve Qwen4Exp PLE graph publication boundary

## Summary

Device-only generated-token PLE publication is not a retainable design for the
pinned artifact. The exact boundary is host hash + mmap gather/dequant + one
2,560-wide H2D row, followed by one reusable full graph launch.

## Decision

PLE has 320,001,446 semantic rows, 160 values per row, 16 independently hashed
rows per token, and a 28.8-GB compressed mmap tensor. Current residency already
owns 82.741 GB. Copying the full sparse PLE table to device would materially
increase residency and startup while eliminating its lazy sparse-mmap design;
registering/pinning the entire mmap is likewise not acceptable. Hardcoding or
precomputing generated trajectories would violate anti-gaming and request
semantics. Therefore PLE hash/table lookup remains host-owned.

## Changes

- Added `--dynamic-ple` full-boundary mode.
- Read the previous graph's device argmax token, update exact request-local
  bigram/trigram PLE hash state, gather/dequantize 16 mmap rows, and upload one
  F32 hidden row before each replay.
- Compare generated input/output tokens, full logits, PLE input, and every
  mutable model state owner against eager at each advancing position.
- Include host PLE staging/H2D and token readback in operation-complete timing.

## Validation

Parser/localization tests report 5 passed. An unretained dirty-tree screen passes
four changing-token transitions with no mismatch; three-sample operation wall is
155.478 ms eager versus 63.189 ms graph (2.46x). Task #72 will rerun clean,
profile, and publish the exact host-stage + graph boundary.

## Next

Do not call this one uninterrupted device graph. It is one bounded host PLE
publication plus one request-owned graph submission per token. Gate its real
changing-token lifecycle and retain only if end-to-end positive.
