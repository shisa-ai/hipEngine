# TimesFM 3.0 GPU coverage hardening — covmask fixture, kernel catalog

## Summary

Closed the three remaining gaps from the pre-implementation plan review:
covariate-mask + long-horizon oracle coverage, the kernel-catalog update,
and an explicit check of the fully-masked-covariate attention semantics.

## Changes

- scripts/timesfm3_oracle_torch.py: --case covmask (fully masked past-only
  covariate, partially masked past-future covariate, horizon 640 =
  19 forecast patches of stitching). Fixture
  tests/fixtures/cpu_reference/timesfm_3p0_decode_covmask.npz.
- tests/test_timesfm3_gpu_decode.py + scripts/timesfm3_gpu_bench.py:
  covmask fixture wired into the fp32 strict / fp16 production gates
  (past_only_mask / past_future_mask kwargs).
- docs/KERNELS.md: TimesFM 3.0 rows in the CPU-oracle table and a new
  "TimesFM 3.0 path" GPU section (var_attention, eps scatter, relu,
  reuse notes, the sqrt(D)-fold and uniform-vs-zeros semantics rationale).

## Validation

- Fully-masked covariate: torch, NumPy CPU, and GPU fp32 all produce
  exactly 0.0 for that variate's forecast (the model itself zeroes it;
  the 2.5 kernels' uniform fully-masked-row fallback does not leak).
- covmask fixture: cpu-vs-torch 8.1e-6; GPU fp32 1.1e-5; GPU fp16
  max 6.0e-3 (~0.4% of signal scale).
- pytest 20 green across the GPU/contract/CPU bundles incl. 2.5;
  bench --check green on all 3 fixtures.
- check_lineage.py fails on a missing external reference
  (~/amd-gpu-tuning/reference/atlas, not present on this host) —
  pre-existing environment issue, not from this change.

## Decisions

- The plan review's "fully masked rows must produce zeros" concern is
  confirmed harmless end-to-end: divergence exists only on rows the
  decode slices away, and the fully-masked-covariate case is exactly
  zero on every path.
