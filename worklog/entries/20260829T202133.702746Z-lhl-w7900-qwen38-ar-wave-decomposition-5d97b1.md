# W7900 Qwen3.8 AR wave decomposition: admission, not decode, loses C2/C6-C8

## Summary

The published C1-C8 matrix compares one number per cell, so it cannot say which
submodule loses. Splitting the same waves into the two terms that actually
compose them -
`wall(D, W) ~= admission(W) + (D - 1) * step(W)` - measured on the same ten
prompts, greedy, prefix-cache off, W7900, `Qwen3.8-27B-Q4_K_M`:

1. **hipEngine's steady-state AR decode is faster than both llama.cpp builds at
   every width.** Per co-scheduled step (ms): hipEngine 34.0/42.0/48.3/53.3/60.5/
   67.9/74.8/82.2 for C1-C8 vs llama.cpp current 38.3/42.6/79.1/122.7/113.2/
   105.5/104.2/105.3. llama.cpp's step time collapses from C2 to C3 and never
   recovers; hipEngine's rises smoothly.
2. **hipEngine's admission is serialized and llama.cpp's is batched.** Per-lane
   admission (admission + prompt processing + first visible token) is flat at
   305-336 ms for every width, i.e. the engine pays it once per request in
   sequence. llama.cpp's falls from 223 ms/lane at C1 to 106 ms/lane at C8, i.e.
   its prompt processing co-schedules across the wave.
3. **Admission alone explains the whole published deficit.** Replacing only
   hipEngine's admission with the cheapest admission measured at that width
   (llama.cpp's own number, nothing else changed) projects hipEngine AR at
   23.4/36.2/46.3/50.5/62.0/68.9/71.9/77.6 tok/s versus llama.cpp current's
   published 21.7/35.4/30.8/27.8/36.4/45.5/51.9/58.7 - a win in every cell.

The first-token submodule is also not a transport artifact: `he_http` runs
hipEngine's own server over a real socket driven by the *same* wave client used
for llama.cpp and reproduces the published rates (21.4/30.1/35.5/37.1/41.1/
42.8/43.8/44.5) and the same flat ~335 ms/lane admission. A sequential width-1
probe puts 0.281 s of the 0.316 s request wall inside
`qwen35_gguf_runner._prefill_batch_native_impl`, and a prompt-length scan
(69 tok 0.391 s, 141 tok 0.382 s, 285 tok 0.745 s, 665 tok 1.262 s) shows a flat
floor below roughly 150 tokens, i.e. a fixed short-prompt prefill cost rather
than prompt-processing throughput.

## Changes

- `scripts/gguf_engine_submodule_decomposition.py`: loads either artifact shape
  (hipEngine server-bench packets, llama.cpp matrix packets), accepts the
  one-token arm under either name (`prefill` or `ar`), and emits per-width
  `decode_step_ms`, `admission_ms`, `admission_ms_per_lane`, published rates, and
  a cross-engine `admission_what_if` block that swaps in the cheapest measured
  admission. This is what makes "which submodule loses" a query instead of an
  inference.
- `scripts/llamacpp_c1c8_engine_matrix.py`: added `--flavor openai` plus
  `--served-model-name` so the *same* wave client, denominators, and guard rules
  drive hipEngine's `/v1/completions` and llama.cpp's `/completion`. Per-response
  fields are normalized through `completion_response_fields`, so the openai
  flavor's `usage.completion_tokens`/`prompt_tokens` are used exactly where the
  llama flavor uses `tokens_predicted`/`tokens_evaluated`; the llama-only
  `top_k`/`seed`/`cache_prompt`/`stream` sampling keys are only sent to the llama
  flavor, and greedy is preserved on both (`temperature=0`).
- `scripts/gguf_first_token_probe.py`: measures the first-token submodule alone
  through the in-process server route - `--length-scan` separates fixed cost
  from prompt-processing throughput, `--wave-widths` times barrier-synchronized
  equal-length waves, `--packed-prefill-max-rows` runs the capability diagnostic,
  and `--profile`/`--prof-out` attribute the wall to host functions.
- `scripts/gguf_engine_kernel_bucket_parity.py`: collects same-shape kernel-family
  busy-time buckets for both engines from `rocprofv3` traces for the strict
  per-kernel parity view (support tool; the stage-timing evidence above is what
  currently localizes the loss).

## Admission root cause (measured)

The serialization has an exact cause in code, not in the transport: the engine
loop only emits a multi-request prefill work item when the runner publishes
`packed_prefill_max_rows > 1` (`hipengine/generation/engine_loop.py:2161`), and
that value comes from the backend capability
`GGUF_C2_PACKED_PREFILL_MAX_ROWS` (`hipengine/generation/qwen35_gguf.py:5003`).
`hip_gfx1151` publishes 8; **`hip_gfx1100` does not define it, so it resolves to
1** and W7900 prefills exactly one request per round. That is why per-lane
admission is flat in width here and falling in width for llama.cpp.

Raising the capability to 8 as a diagnostic (module attribute override in
`scripts/gguf_first_token_probe.py --packed-prefill-max-rows`) on waves of
equal-length 64-token prompts, min-of-2 wave walls:

| width | capability 1 | capability 8 | speedup |
| --- | --- | --- | --- |
| C1 | 0.3808 s | 0.3818 s | 1.00x |
| C2 | 0.7408 s | 0.6171 s | 1.20x |
| C4 | 1.4580 s | 0.9571 s | 1.52x |
| C8 | 2.9049 s | 1.8663 s | 1.56x |

It is not promotable, and this is the important negative result: the packed-prefill
byte-parity gate fails on this backend.
`scripts/gguf_packed_ar_state_oracle.py --backend hip_gfx1100 --prefill-mode
packed --decode-steps 4` (greedy, exact GDN selector, every Conv/GDN FP32 and
live K/V byte compared against independent c1):

| rows x prompt | rounds (chunk_rows) | tokens exact | initial state exact | final state exact |
| --- | --- | --- | --- | --- |
| 8 x 45 (mixed 45/33) | [256, 20] | no | no | no |
| 8 x 45 (equal) | [256, 104] | yes | no | no |
| 8 x 32 (equal) | [256] | yes | no | no |
| 4 x 45 (equal) | [180] | yes | no | no |

The first divergence is `phase=prefill row=0 component=linear layer=0
part=recurrent`, and it survives a single-round prefill (8x32 = 256 rows = one
round), so it is not a round-splitting artifact. This is consistent with the
parent entry `20260822T194222` ("gfx1100 remains scalar"): the capability was
only ever published for gfx1151, and the strict state-parity evidence for
gfx1100 does not exist. Promoting it here needs either GDN packed-versus-c1
state parity on gfx1100 kernels or a production-profile numerical qualification,
and neither is a flag flip.

So the retainable fix for the AR admission term is to make the *scalar*
short-prompt prefill cheaper, which needs no arithmetic change at all.
`scripts/qwen35_gguf_bench.py --gpu-stage-timings` device-stage totals explain
why: a 45-token prompt costs 373 ms of prefill device time against 483 ms for a
512-token prompt, i.e. 8.30 ms/token versus 0.94 ms/token, and three stages
*anti-scale* - they cost more absolute time at 45 rows than at 512 rows:
`prefill_linear_attn_ffn_down_residual` 111.9 vs 85.9 ms,
`prefill_linear_attn_ssm_out` 71.6 vs 30.9 ms, and
`prefill_full_attn_ffn_down_residual` 36.3 vs 28.5 ms. The short-prompt prefill
route is the slow submodule; `admission_ms_per_lane` becomes competitive if it
approaches the same workload's marginal rate.
