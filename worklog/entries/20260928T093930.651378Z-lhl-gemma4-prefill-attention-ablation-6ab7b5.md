# prefill attention is not load bound and the unroll warning is not about pass ones pragma

## Summary

Two ablations that **close the two most plausible ways to speed up prefill
attention**, and a correction to a claim the kernel's own comments make.

## Where prefill actually goes at 512 tokens

A traced 512-token prefill, two calls, 1456.7 ms of device time (so ~728 ms per
prefill, matching the bench's 740 ms):

| per prefill | share | kernel |
| ---: | ---: | --- |
| 180.6 ms | 24.8% | `gguf_q8_0_prefill_wmma_kernel<tt,32,64>` |
| **178.3 ms** | **24.5%** | **`gemma4_attention_prefill_kernel`** |
| 153.2 ms | 21.0% | `gguf_q4_k_selected_dual_q8_1_ds4_mmq32_fused` (gate/up) |
| 115.8 ms | 15.9% | `q5_1_mmq_ds4_selected_prefill` (down) |

The four are comparable; attention is the largest single block and the only one
with a structural story. **My earlier note that attention was 178.8 ms against
llama.cpp's 28.8 reproduces at this shape.** An earlier trace at ~96 tokens put
attention at 2.6 percent, which is why the shape matters: attention is quadratic
in tokens and the other three are linear.

Closing attention entirely would take prefill from 728 ms to ~550 ms, i.e. 689 to
~930 tok/s, which is past llama.cpp's 909.3. **So it is the whole gap.**

## Ablation 1: it is not load-bound, so query tiling is not the win

`scripts/gemma4_attention_prefill_bench.py` at `--tokens 512`:

| case | ms/launch | GFLOP/s |
| --- | ---: | ---: |
| swa 256d 16q/8kv window=1024 | 4.64 | 463.9 |
| swa 256d 16q/8kv window=0 | 4.64 | 463.9 |
| full 512d 16q/2kv | 6.86 | 627.2 |
| **the model's 30 attention layers** | | **150.3 ms** |

and with `--mask zero`, which skips every K/V load while leaving the key loop and
the reductions intact:

| case | ms/launch |
| --- | ---: |
| swa 256d 16q/8kv window=1024 | **6.19** |
| full 512d 16q/2kv | **8.31** |

**Removing every K/V load makes the kernel slower.** So the prefill attention
kernel is not paying for bytes, and the obvious structural fix -- tile over query
rows so each K/V tile is loaded once for many rows -- would buy nothing. The
kernel is latency- or issue-bound inside the key loop.

That also means the sliding-window mask is doing no work at this shape:
`window=1024` and `window=0` are both 4.64 ms, because 1024 exceeds the 512 keys.

## Ablation 2: the unroll warning is not about pass 1

The strict kernel's pass-3 comment says:

> the compiler's own "loop not unrolled" warning on pass 1's `#pragma unroll 2`
> is the open thread, since that interleave was written deliberately and is not
> happening.

**That is not supported.** The warning reproduces, twice, attributed to line 182
(the kernel's first line):

```
gemma4_attention.hip:182:17: warning: loop not unrolled: the optimizer was unable
to perform the requested transformation [-Wpass-failed=transform-warning]
```

but changing pass 1's pragma does not change it:

| source | warnings |
| --- | ---: |
| as committed | 2 |
| `#pragma unroll 2` changed to `#pragma unroll` (full) | **2** |

**If the warning were about pass 1's pragma, removing the trip-count request
would change the count.** It does not. The kernel has seven loops and exactly one
real unroll pragma, so the two warnings are about something else -- most likely
the two loops the compiler chose to unroll itself, in passes 2 and 3.

The build's `-mllvm -amdgpu-unroll-threshold-local=N` does not remove them
either, at 200, 600, or 4000.

**So the "open thread" the comment names may not be open at all, and a fix aimed
at it would have been aimed at nothing.** Whoever takes this next should read the
ISA for whether pass 1's two shuffle chains actually interleave, rather than
trusting the warning's line attribution.

## What this leaves

The kernel is issue-bound in the key loop at 464-627 GFLOP/s, against an fp32 FMA
ceiling near 25 TFLOP/s -- roughly 2 percent. That is where the time is, and
neither of the two structural explanations that were on the table (traffic, and a
refused unroll) survives its ablation.

## Next

1. **Read the ISA for pass 1's shuffle chains.** `#pragma unroll 2` was written to
   interleave two independent chains; whether it does is a disassembly question,
   and the warning cannot answer it.
2. **The tiled variant already exists** (`gemma4_attention_prefill_tiled_kernel`,
   launched by `hipengine_gemma4_attention_prefill_tiled_bf16`) and is **not wired
   into dispatch**. Its stated purpose is a context-independent shared footprint
   for long context, not speed, so it is not obviously the answer at 512 tokens --
   but it is one bench run away from being measured, and it is the only other
   prefill attention implementation in the tree.
3. **If the key loop is the floor, the win is more work per key visit**, which is
   what the tiled variant does structurally (one tile of logits resident, two LDS
   accesses per key visit instead of four).
