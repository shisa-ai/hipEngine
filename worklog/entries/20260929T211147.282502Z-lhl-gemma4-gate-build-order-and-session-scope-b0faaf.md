# Checkpoint: the gate smoke cannot run without registered plans, so (A)-identical comes first

## Summary

Corrects the build order recorded in
`20260929T211039.799695Z-lhl-gemma4-profile-plan-registration-order-f3d7dc.md`.
That entry put (B) first and (A) last, with "(A)-with-production-identical-to-strict"
described as a fallback *if plumbing ever needs it*. Reading the smoke's own
`main()` shows the fallback is the only path that works: the smoke resolves both
profile plans before it writes a single manifest, so (B) cannot execute until
(A) has registered them. The build order is therefore **(A)-identical first**,
which is safe precisely because production selections equal strict -- no
arithmetic changes and the default flip is behaviour-preserving -- followed by
(B), (C), the gate, and only then advancing production selections to the
promoted variants.

All three facts read directly from source.

- **The dependency is a hard error, not a preference.**
  `resolve_runtime_profile` (`hipengine/execution_profiles.py:496`) looks up the
  **strict** plan first and raises `MissingRuntimeProfilePlanError("no strict
  execution-profile plan registered for (model, backend, quant)")` when it is
  absent (`:515-520`), then builds the variant manifest from that plan's
  `kv_policy`, `graph_policy` and `selections` (`:521-529`).
- **The smoke calls it for both profiles during setup.**
  `scripts/execution_profile_gguf_control_smoke.py` `main()` resolves
  `ExecutionProfile.STRICT` and `ExecutionProfile.PRODUCTION` and writes
  `strict-variant-manifest.json` / `production-variant-manifest.json` from the
  two `plan.manifest` values **before** any trajectory runs. There is no
  manifest path that skips registration, so no capture, no expected-control
  fixture and no gate invocation is reachable ahead of (A).
- **(A)-identical stays safe under the previous checkpoint's hazard.**
  `resolve_default_execution_profile` (`:314`) flips an omitted profile to
  `production` on registration presence alone, so registering early *does* flip
  the default -- but with production selections identical to strict
  (`selected_variant == strict_fallback_variant`, no `evidence_artifact`) the
  resolved arithmetic is the strict one, which is why that staging changes no
  behaviour. The promoted variants must not appear in the production selections
  until the gate artifact that certifies them exists.

## Next

### (B)'s scope, now sized against the real API

The smoke drives a session object whose contract is
`reset()`, `prefill(ids, use_bulk=, bulk_attention_mode=, return_logits=,
capture_hidden_seed_fp32=)` returning an object with `.logits` and `.token_id`,
`step(token, return_logits=)` returning `.logits`/`.token_id`, and `.position`,
inside a context manager that also exposes `.runner`.

Gemma 4 has **no resident-session class at all**. `hipengine/runtime/` carries
`Qwen35GGUFResidentSession` (qwen35_gguf_runner.py:15964),
`Qwen35ParoResidentSession`, `LagunaGGUFResidentSession`,
`Qwen4ExpGGUFResidentModelRunner` -- and for gemma4 only `Gemma4Runner`
(`runtime/gemma4.py:627`), reached from the generator via
`gemma4_gguf.py:237 _ensure_runner()`. Its public surface differs:

| smoke contract | Gemma4Runner |
| --- | --- |
| `reset()` | `reset()` (`:627` block, exact match) |
| `position` | `position` property (`:810`) |
| `prefill(ids, ...) -> (.logits, .token_id)` | `forward(token_ids, *, apply_softcap=True) -> np.ndarray` (logits only) |
| `step(token, return_logits=) -> (.logits, .token_id)` | none -- the next step is another `forward([token], ...)` |
| `close()` / context manager | `close()` |
| `.runner` | the runner itself |

So (B) is: a `Gemma4ResidentSession` adapter (context manager, `reset`, `close`,
`.runner`, plus `prefill`/`step` shims that wrap `forward` and read the sampled
token through `next_token(logits, temperature=0.0)`) and the smoke's `main()`
adapted -- drop `with _gdn_mode(...)` (Gemma 4 has no GDN; that coupling is
`execution_profile_gguf_control_smoke.py:174` and `:186`), swap
`Qwen35GGUFTokenizer` + `build_chat_prompt` for gemma4's
`tokenize_chat(content, enable_thinking=True)` as `scripts/gemma4_real_generate.py`
already does, and substitute gemma4's model/backend/quant constants for
`QWEN36_GGUF_MODEL/BACKEND/QUANT`.
