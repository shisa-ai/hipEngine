# Size the TP2 bulk prefill workspace to the prompt

## Summary

`bulk_prefill_rows` defaulted to the session's `max_sequence_length`, so a
2048-token session allocated a 2048-row bulk workspace before the prompt was
known: rank 1 (24 GiB XTX) reached 22.55 GiB, leaving 1.5 GiB and precluding the
0.44/0.56 uneven split or any long-context ladder point on the same pair. The
workspace is now a scratch sized to the prompt on first use, and that is both
leaner and faster:

| Config (512-token prompt, 128 decode, c=1, same host/revision) | Prefill tok/s | Decode tok/s | VRAM/rank |
| --- | ---: | ---: | ---: |
| token-serial (committed) | 39.1 | 38.36 | 12.43 GiB |
| **bulk, prompt-sized (512 rows)** | **459.7** | 38.94 | **15.39 GiB** |
| bulk, pinned capacity (2048 rows) | 384.5 | 38.88 | 22.55 GiB |

**11.8x prefill for +2.96 GiB/rank**, decode unchanged. A capacity-sized
workspace is not just 7 GiB more expensive, it is 16% slower: every layer moves
more memory than the prompt has rows.

Runs: prompt-sized `[467.2, 462.9, 459.5, 459.7, 457.4, 456.4]`, capacity
`[385.6, 387.2, 384.5, 383.2, 380.8, 379.5]`, serial `[39.7, 39.4, 39.1, 39.1,
39.0, 39.0]`.

## Correctness

The full-suite production gate with the prompt-sized workspace
(`benchmarks/results/2026-09-18-w7900-tp2-bulk-prefill-gate-prompt-sized.json`)
is **byte-identical** to the capacity-sized run committed with the wiring:
831 rows, mean KL 2.895e-04, p99 3.452e-03, max KL 4.2273e-02, top-1 99.64%,
3 flipped rows, 3-sweep determinism, controls byte-identical. Same numbers to
the last printed digit, which is the batch-composition invariance the execution
profiles require and the strongest available evidence that prompt-sizing changes
allocation and nothing else.

Note the comparison basis, because the TP2 doc and `benchmarks/README.md`
discuss a different one: this gate is the **production arm-vs-tp1-control**
comparison. The teacher-forced sustained-horizon analysis (each arm against the
teacher, D=128) still breaches the max-KL ceiling at decode index 82, exactly as
those documents say, and this unit does not change that.

## Changes

- `hipengine/distributed/tp2_generate.py` - `_build_bulk_prefill_workspace(rows)`
  takes the row count; `_ensure_bulk_prefill_workspace(rows)` allocates on first
  use, grows for a longer prompt (releasing the old workspace first) and reuses
  otherwise; `_release_bulk_prefill_workspace()` owns teardown and is what
  `close()` calls. Bulk buffers moved from `_extra_buffers` to their own
  `_bulk_buffers` so growing frees them exactly once. An **explicit**
  `bulk_prefill_rows` is still built eagerly at construction - see below.
- `scripts/tp2_c1_bench.py` - records `memory_after_warmup` (the deferred
  workspace does not exist at `memory_after_load`, so the old reading
  understated the route's footprint by the whole workspace),
  `bulk_prefill_workspace_rows`, and warms up with the **measured** decode
  length instead of `max_new_tokens=1`.
- `tests/test_unit_distributed_tp2_generate.py` - lazy-sizing contract: nothing
  allocated before use, growth on a longer prompt, reuse on a shorter one, and
  an explicit capacity still pre-allocated.

## Two harness bugs this exposed

1. **Prefill steps counted as tokens.** The old accounting scored the bulk
   route's single step as one token, reporting 0.38 tok/s for a 210 tok/s
   prefill. Fixed with `_rate(..., tokens=...)` and pinned by
   `tests/test_unit_scripts_tp2_c1_bench.py`.
2. **Warmup shape mismatch.** Warming up at `max_new_tokens=1` and then
   measuring 128-token generations left four transient runs inside a 5-run
   median: walls of 8.5 s, 11.5 s, 13.5 s and 7.2 s against a 1.15 s steady
   state, i.e. a reported 102 tok/s for a 440 tok/s route. Ten repeats converge,
   which is how it was identified. The warmup now matches the measured shape.
   This also explains an apparent contradiction between two of this session's
   own runs (463 against 177 tok/s for the same workspace size); the 177 was the
   transient, and 463 reproduces as 459.7 with a correct warmup.

## Deferred (lazy) allocation is not safe for a *large* pinned workspace

Building the workspace lazily while pinning `bulk_prefill_rows=2048` measured
erratic and much slower than building it at construction: `[25.5, 28.5, 100.9,
55.7, 101.3, 136.8]` tok/s against `[385.6, 387.2, 384.5, 383.2, 380.8, 379.5]`
for the same configuration built eagerly. So an explicit capacity keeps the
original eager allocation, which reproduces the previously measured 384-386
tok/s exactly, and only the prompt-sized default is deferred. The mechanism is
not localized; it is recorded rather than papered over.
