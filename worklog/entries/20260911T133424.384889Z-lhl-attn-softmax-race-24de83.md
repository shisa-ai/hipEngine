# Paged attention decode and TimesFM mask softmax: same shared-memory max-reuse race

## Summary

The shared-memory max-reuse race fixed for the EVIE softmax kernels in
`worklog/entries/20260911T133132.486572Z-lhl-evie-softmax-race-bbe31f.md`
(commit `2f85e9d42`) occurs in six more places, including the production paged
full-attention decode path. A source-pattern scan for "read `X[0]`, then write
`X[threadIdx.x]` with no intervening `__syncthreads()`, then reuse `X` for a
second reduction" reported these sites and nothing else:

| File | Lines | Kernel / function |
| --- | --- | --- |
| `hipengine/kernels/hip_gfx1100/attention/paged_attn_decode.hip` | 101 | `qwen35_full_attn_decode_impl` (`__device__`, used by `qwen35_full_attn_decode_context_tensor_kernel`) |
| same | 623 | `qwen35_paged_full_attn_decode_context_tensor_batch_c1_exact_kernel` |
| same | 1800 | `qwen35_paged_full_attn_prefill_gqa_gate_fp16_kernel` |
| same | 2107 | `qwen35_paged_full_attn_prefill_gqa_gate_tree_fp16_kernel` |
| same | 2285 | `qwen35_paged_full_attn_prefill_varlen_gqa_gate_fp16_kernel` |
| `hipengine/kernels/hip_gfx1100/timesfm/timesfm.hip` | 524 | `mask_softmax_kernel` |

All six read the pass-1 row max (`const float max_score = partial[0];` or
`float row_max = partial[0];`) and then overwrote `partial` with the pass-2
partial exponential sums with no barrier in between. A thread whose shared
load landed after another thread's store would use a partial sum as the row
max and corrupt that row's softmax.

That the barrier was simply missed here is supported by the split-K kernels in
the same file: the `chunk_max` / `chunk_sum` sites at lines ~735, ~753, ~899
and ~926 already carry `__syncthreads()` immediately after reading
`partial[0]`, i.e. the author applied the pattern there and not in these six.

## Changes

- `hipengine/kernels/hip_gfx1100/attention/paged_attn_decode.hip`: add
  `__syncthreads()` immediately after `const float max_score = partial[0];` at
  all five sites, with a comment naming the hazard.
- `hipengine/kernels/hip_gfx1100/timesfm/timesfm.hip`: the same barrier after
  `float row_max = partial[0];` in `mask_softmax_kernel`.

No arithmetic, tiling, or dispatch change. The added barrier is the only new
synchronization.

  reported exactly the six sites above before it, and the EVIE pair is already
  clean from `2f85e9d42`).

  `tests/test_qwen35_paged_attn_decode_plan.py`,

  `tests/test_timesfm3_gpu_decode.py`, `tests/test_timesfm_model_contract.py`,
  `tests/test_timesfm3_model_contract.py` → 187 passed, 0 failed.
- Cost of the barrier, measured on
  `qwen35_full_attn_decode_context_bf16` at `context_len=4096`,
  `num_q_heads=16`, `num_kv_heads=2`, `head_dim=256`, 500 launches after a
  20-launch warmup, gfx1151:
  - without the barrier: 472.03, 470.49, 470.64 us → mean 471.05 us
  - with the barrier: 470.90, 470.59, 470.78 us → mean 470.76 us
  - difference −0.29 us (−0.06 %), inside run-to-run noise. The barrier runs
    once per block per decode row, outside the context-length loops.

**Not reproduced.** Unlike the EVIE kernels, no observable failure was
produced for these six sites. The race window is narrow — every thread issues
its `partial[0]` load immediately after the same barrier, and the store only
follows the exponential loop — so on this hardware the load almost always
wins. These sites are changed because the pattern is unambiguously a data
race (the same code is UB regardless of whether it currently manifests), the
split-K siblings already guard it, and the measured cost is zero. No
correctness or performance claim is made from a reproduced failure.
