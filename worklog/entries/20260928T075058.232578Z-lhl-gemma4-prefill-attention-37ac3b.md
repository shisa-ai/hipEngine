# rocprofv3 pmc counters do not land on this setup but the kernel trace carries the register and lds counts that settle occupancy

## Summary

`20260928T074955` said to profile before changing anything, because the 3.4%-of-issue figure was
derived from instruction counts rather than measured. **The profiling attempt did not produce
counters, and I misread a stale file while looking for them.** What it did establish is that
`rocprofv3`'s kernel trace works and carries the per-kernel register and LDS counts -- **which
settle the occupancy question directly, without needing counters at all.**

## What worked and what did not

- **`rocprofv3` 1.3.5 is present** (`/home/lhl/miniforge3/bin/rocprofv3`).
- **`--pmc SQ_WAVES SQ_INSTS_VALU SQ_INSTS_LDS SQ_INSTS_VMEM SQ_WAIT_INST_LDS
  SQ_WAIT_INST_VMEM` produced no counter CSV** -- the output directory contains only
  `*_kernel_trace.csv`. **So the 3.4% figure remains derived, not measured.** Whether the counter
  names are wrong for gfx1151 or the collection silently degraded, I did not determine.
- **`--kernel-trace` works and its CSV is rich.** Columns include `VGPR_Count`,
  `Accum_VGPR_Count`, `SGPR_Count`, `LDS_Block_Size`, `Scratch_Size`, `Workgroup_Size_X`,
  `Grid_Size_X`, and start/end timestamps.

## A mistake worth recording

**My first read of the output took `/tmp/prof_out/prof_kernel_trace.csv` -- a file from a
previous session, timestamped 00:47 -- and briefly treated its contents as my own run's.** It
holds 1558 dispatches including `qwen35_moe_group_*` kernels and 451 `__amd_rocclr_copyBuffer`
entries, so it is not this work. **None of its numbers should be reused.** The directory held
three older traces (`prof`, `prof2`, `dec`) and my run's `-o gemma4` output never appeared,
which is what gave it away.

**This is the same failure mode as the filename-as-coverage-map and the model-absence errors
earlier in this stretch: acting on an artifact's name or location instead of checking that it is
the artifact I think it is.** Third instance. The check that caught it was cheap -- the numbers
did not match my run.

## The useful consequence

**`VGPR_Count`, `LDS_Block_Size` and `Scratch_Size` are static per-kernel properties in the
trace, and together they determine how many blocks fit per CU.** That is exactly the quantity the
whole key-tiled design rests on: `20260928T073811` reasoned from `shared_bytes` alone and
concluded six blocks per CU at 2048 keys and one above 8192, and `20260928T074732`'s 2.40-2.46x
at long context is consistent with it -- **but the reasoning never accounted for registers or
scratch, either of which could cap occupancy below the LDS limit and change which effect the
2.4x actually came from.**

**So the next profiling attempt should collect `--kernel-trace` for the attention kernel alone
and read those three columns**, rather than chasing PMC counters.
