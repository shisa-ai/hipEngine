keys withheld from the gfx1151 alias table are qualified and admitted.

| Key | Exclusion reason before | Disposition |
| --- | --- | --- |
| `linear / gguf_q4_k_t16_v1 / dense_rowtile_col4_bf16_bf16_out` | W7900-only until gfx1151 receives an independent shape crossover and full-model gate | admitted |

The unit also fixes a host-OOM bug in the shared batch diagnostic that this
gate's multi-arm protocol exposed.

the projection is **~0.06%** and **~0.09%** of decode — sub-window wins, not a
topline move. The composite also removes one launch per displaced tensor.

Complete-model gate, generated-token equality against independent c1 in both
the pre-admission control and the candidate configuration:

- `--rows 2,3,4 --max-new-tokens 32` (soak): every cell `eq_ok`, arms
  token-identical, native c-aware decode, no serial fallback.
- `--rows 2,4 --windows --max-new-tokens 8` (full suite): all 10 mtp-bench
  prompts across `code`/`general_en`/`general_ja`/`mixed_ja_en` at both widths,
  `gate_passed: true`, `all_prompts_covered: true`.
- Shipped-configuration check: the batch diagnostic run directly through
  `register_gfx1151_kernels()` with no in-process mutation returns the admitted

Reachability, so the coverage is not accidentally wider than the evidence: the

`_q4_t16_sidecar_decode_variants` to rows<=4 at shape (5120, 1024). Rows 2-4
are therefore the complete reachable band for both keys, and both were
measured at every row in it.

## OOM (why the harness fix is in this unit)

The first two 32-token gate attempts died in the same arm and the third took
the whole host down: each arm constructed an `LLM` and never closed it, so a
six-arm process accumulated ~17 GB per arm and the kernel's global OOM killer
fired at 22:58, killing tailscale, `dbus-broker`, the user systemd, and the
agent harness along with the run. `LLM.close()` releases the generator's
long-lived model resources and every other multi-arm harness in `scripts/`
already calls it; this one did not.

After the fix, six arms hold `MemAvailable` flat (113.2 → 112.7 GiB across the
run) with a ~20 GB per-arm peak that is released at close. Subsequent GPU runs
were additionally executed inside a `systemd-run --user --scope` with
`MemoryMax` (verified: an overrun produces `oom-kill:constraint=CONSTRAINT_MEMCG`
confined to the scope) plus a host `MemAvailable` watchdog, because GPU/GTT
allocations are not charged to the cgroup and only the host-level guard catches
those.
