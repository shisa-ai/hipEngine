# Muse Glimmer prefill: four kernel variants pursued, all slower

## Summary

Per lead directive (major work is not an excuse), built and measured four
projection-kernel variants attacking the PMC-profiled bottlenecks. All are
correct (cosine 0.99992, maxerr 0) but slower than shared_b. The decisive
finding: the kernel is L2-MEMORY-bound (MemUnitBusy 71%), NOT
LDS-conflict-bound — ALUStalledByLDS is 0.019, and cutting the bank conflict
from 48.5% to 5.56% did not speed it up. The activation re-reads across the
416 output-column blocks (grid.x) saturate L2 bandwidth; the activation is
too large for LDS, so tiling cannot remove the bytes, only request count.

## Changes

- Four experimental kernels added then reverted; tree clean at 80091de8d.

## Validation

shared_b baseline ffn_gate rows=512: 6.07-6.19 ms / 22.0-22.4 TF, conflict
48.5%, MemUnitBusy 71%, occupancy 7.8, ALUStalledByLDS 0.019.
- Software-pipelined double-buffer (decode blk+1 before WMMA blk): 8.46 ms,
  0.73x — 51 KB LDS halves occupancy 2->1 block/CU.
- Chunk XOR swizzle (kc ^ (col&15) in decode-write + b-read): 7.07 ms, 0.86x;
  conflict ROSE to 82% (the contiguous column-row load is disrupted).
- Stride 264 (QK_K+8, 16B-aligned): conflict fell to 5.56% but 6.64 ms
  (slower) — proves the conflict was not the bottleneck (memory-bound).
  Stride 274 misaligns (6.99 ms); 288 raises conflict to 74% (6.94 ms).
- Activation per-subblock LDS tiling (act[256][48]+weight[48][48], 2 blk/CU):
  24.87 ms, 0.24x — 8x sync overhead + small decode chunks dominate.

## Next

- The projection is at the L2-bandwidth limit for this N-tiling: activation
  for a row block (~3.4 MB) is re-read by every column block from L2. Reducing
  that needs a larger N-block (register-limited; OUT_TILES>3 spills the WMMA
  accumulator) or a persistent GEMM with global partial-output accumulation
  (a from-scratch redesign). The LDS-conflict and per-subblock-tiling levers
  are now empirically closed. shared_b 22 TF remains the fastest produced.
