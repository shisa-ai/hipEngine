# the Q4_K T16 WMMA route is 1.264x on the expert gate/up at the model's own geometry, for zero bytes

## Summary

The harness that measured this lever had never been run at the model's shapes -- its defaults
are `--hidden 2048 --out-features 4096 --experts 8 --rows-per-expert 64`, and the recorded
"3.40 against 2.84" came from that fixture. **Run at Gemma 4 26B-A4B's actual expert geometry
(hidden 2816, 704 out, 128 experts, 32 rows) the ratio is 1.2637, and the MMQ32 arm reproduces
the in-situ per-layer time to within 2 percent.**

**The repack costs nothing.** `repack_gguf_q4_k_tile16_lite` produces tiles whose byte count is
*exactly* the raw Q4_K byte count, and the non-lite variant is +2.78 percent. The 19.2 GB figure
that made this look expensive was the **pack8** layout, which is a different thing.

## The measurement

`scripts/gguf_q4_k_t16_selected_prefill_microbench.py`, 25 iters, 5 warmup, identical weights:

| mode | ms/call | TFLOP/s |
| :--- | ---: | ---: |
| `q8-1-ds4-mmq32` (production route) | 6.369 | 2.55 |
| `selected-wmma` (Q4T16 WMMA) | **5.040** | **3.22** |
| | **ratio 1.2637** | |

**The transfer check:** the decomposition prices the production gate/up at **156.5 ms over 25
layers = 6.26 ms/layer**, and the harness's MMQ32 arm measures **6.369 ms/call**. The harness
is not an idealised fixture -- it reproduces the in-situ cost.

## The repack is byte-neutral

```
raw bytes             142737408   (0.143 GB for one layer)
tile16                146702336   ratio 1.0278 (+2.78%)
tile16_lite           142737408   ratio 1.0000 (+0.00%)
```

`repack_gguf_q4_k_tile16_lite`'s own docstring: *"Repack rank-3 raw GGUF Q4_K weights into
byte-neutral T16-lite tiles."* The non-lite layout is
`[experts, out_tiles16, blocks_per_row, 2304]` where `2304 = 16 x 144` is exactly the raw Q4_K
bytes for 16 columns -- the +2.78 percent is the 2368-byte variant.

## What it is worth

The two expert MMQ kernels are **260.4 ms of the 687.7 ms prefill** (gate/up 156.5, down
103.9). At 1.2637:

```
260.4 ms -> 206.0 ms,  saving 54.4 ms
the gap to llama.cpp is 122.8 ms, so that is 44 percent of it
```

## Why it is not already wired

`gemma4_project_experts_gate_up_mmq` dispatches on the quant key:

```python
if quant_key == "gguf_q5_k":
    return _gemma4_project_experts_gate_up_wmma_iu8(...)
```

**Q5_K gets a WMMA route and Q4_K does not.** But the Q5_K route is not a plain GEMM -- it is a
3-plane risk+repair route with exact-repair semantics. The harness's `selected-wmma` is the
*plain* leaf, `gguf_q4_k_t16_selected_dual_wmma_prefill_compact32_bf16_bf16_out`, so the Q4_K
twin is simpler than the Q5_K one, not harder. **All the pieces exist**: the leaf, the tile
repack, the tile-map machinery (`qwen35_moe_wmma_tile_map`), the scratch buffers, and a
`Gemma4GGUFDeviceWeight` that already supports named allocations (`allocation("raw")`,
`has_allocation(...)`) so a `t16` allocation can sit alongside `raw` for the strict fallback.
