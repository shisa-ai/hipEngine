# Full-attention context launch: 1.74x from two bit-exact levers

## Summary

The full-attention decode-context leaf was 801.4 ms of the code-p4096 prefill,
and 81.3% of that sat in one launch geometry: 1024 rows at `max_context_len`
2048. Attacking that launch with two changes that touch no floating-point
operation moves it from 54.728 ms to 31.518 ms in situ (**1.736x**), and the
same-session sibling launch at `max_context_len` 1024 from 12.418 to 8.703 ms
(**1.427x**). Summed over the 12 full-attention layers, the three context
launches drop from 812.9 to 488.5 ms per prefill, a **324.4 ms** saving.

The result is byte-identical, not merely within a KL envelope. Every measured
variant matched the shipped route with `maxdiff = 0.000e+00` over all
1024 x 24 x 256 output elements, so this win does not inherit the MoE router's
discrete-amplification problem: it cannot flip an expert choice, because it
cannot change a single logit.

## What the launch actually is

The trace names `qwen35_paged_full_attn_decode_context_tensor_batch_kernel` with
`Grid_Size_X=6144, Grid_Size_Y=1024, Workgroup_Size=256`, and the previous
attribution read that as rows=1024 at context 2048. Two things were wrong.

First, `Grid_Size_Y` is the row count and the row count is `dense_rows`, not the
chunk size. `run_qwen4_exp_attention` launches the dense context leaf as
`dense_attention(spans, dense_rows, start + dense_rows, ...)`, so
`max_context_len` is the absolute position the chunk ends at. With
`dense_equivalent_limit = 2051` and a 1024-token chunk size that gives exactly
three launches per layer: rows=1024 at `max_context_len` 1024, rows=1024 at
2048, and rows=3 at 2051. That matches the observed grid set (24,1024) x2 plus
(24,3) x1 with no free parameters, which is what identified the geometry.

Second, `live_counts` is causal, not uniform. `qwen4exp_fullattn_launch_probe.py`
reads them off the device at the real call site: launch A carries 1..1024
(`live_sum` 524,800) and launch B carries 1025..2048 (`live_sum` 1,573,376). A
uniform-context microbench therefore overstates the work by 33%.

Two entry points were also in play, and they are not the same kernel. The runner
calls `..._batch_fixed256_spans`, which launches the `<true, 2>` instantiation of
`..._tensor_batch_kernel` with 25,607 bytes of dynamic shared memory.
`..._c1_exact_spans`, which the first microbench drove, launches a different
kernel entirely (`..._tensor_batch_c1_exact_kernel`, 9,216 bytes). Benchmarking
the second while the trace described the first produced a 463 ms "reproduction"
of a 54.7 ms launch, an 8.5x error that would have made every later comparison
meaningless.

## Changes

- `hipengine/kernels/hip_gfx1100/attention/paged_attn_decode.hip`
  - `qwen35_paged_full_attn_decode_context_tensor_batch_kernel` gains two
    template parameters, `typename OffsetT = int64_t` and `int QK_TOKENS = 1`.
    Both default to the previous behaviour, so existing instantiations are
    unchanged.
  - The token-offset address construction is hoisted into one
    `token_offset_of` lambda. The precompute and inline routes previously
    duplicated the expression in four places; a divergence between them would
    have been silent.
  - New promoted entry point
    `hipengine_qwen35_paged_full_attn_decode_context_bf16_batch_fixed256_promoted_spans`,
    which selects `<true, 2, false, int32_t, 2>` when the offset range provably
    fits int32 and `<true, 2, false, int64_t, 2>` otherwise.
  - `fullattn_context_offsets_fit_int32` is the single source of truth for that
    decision, exposed for tests as
    `hipengine_qwen35_fullattn_context_offsets_fit_int32`.
- `hipengine/kernels/hip_gfx1100/attention/paged_attn_decode.py` and
  `__init__.py`: Python wrappers and exports for the promoted route and the
  guard.
- `hipengine/runtime/qwen4_exp_runner.py`: the dense full-attention call site now
  uses the promoted route and passes `kv_capacity_tokens` derived from
  `attention_state.key_cache.nbytes // (kv_heads * head_dim * 2)`. A temporary
  `HIPENGINE_QWEN4_EXP_FULLATTN_CONTEXT_LEGACY=1` opt-out exists for same-session
  A/B only.
- `scripts/qwen4exp_fullattn_launch_probe.py`: wraps the dense context entry
  points to log rows, `max_context_len`, live-count distribution, and per-launch

- `scripts/qwen4exp_fullattn_prefill_microbench.py`: replays a dumped launch and

- `tests/test_gpu_fullattn_context_promoted_route.py`: pins the int32 selection
  boundary and byte equality of both capacity choices against the shipped route.
- `docs/ENVS.md`: the canonical `env -i` wrapper silently discarded every
  `HIPENGINE_*` / `QWEN4EXP_*` switch set on the command line, so an A/B whose
  arms differ only by an environment variable measured one arm twice. The
  wrapper now forwards those prefixes explicitly.

## Why these two levers

Both were chosen from the same reading of the kernel: at 54.7 ms the launch
issues about 6.9% of the GPU's warp-instruction capacity, moves 707 GB/s of K/V
that is entirely L2-resident, and uses roughly 5% of LDS bandwidth. None of the
throughput ceilings are close, so the launch is latency-bound, and the two
quantities that were actually scarce were residency and in-flight work.

**int32 token offsets (1.403x alone).** `shared_bytes` is
`float_bytes + 7 + max_context_len * sizeof(int64_t)`, and the offset table is
the dominant term: at `max_context_len` 2048 it is 16,384 of the 25,607 bytes.
Halving the element width drops the request to 17,223 bytes and lifts residency
from 2 to 3 blocks per CU. The 1.47x per-triple penalty that launch B pays over
launch A tracks their 2-versus-3-block residency, which is the independent
evidence that residency was the binding constraint.

**Two-token QK unroll (1.260x alone).** The QK phase scores one token per warp
iteration through an eight-FMA dot product followed by a five-step shuffle
reduction, so each iteration is one serial dependency chain of roughly 500
cycles. Scoring two tokens per iteration gives the scheduler a second
independent chain to interleave. The unroll changes which warp owns which token,
which is safe because the per-warp max fold is order-independent and the
separate exp/sum pass keeps its own token-to-warp map, leaving the denominator
untouched.

The two compose near-multiplicatively: 1.403 x 1.260 = 1.768 against a measured
1.743, which says they relieve largely independent constraints rather than
sharing one.

**A falsified hypothesis, recorded so it is not retried.** With
`VALUE_VECTOR = 2` and `head_dim = 256` the PV loop is
`for (dim_base = threadIdx.x * 2; dim_base < head_dim; dim_base += blockDim.x * 2)`,
so threads 128..255 have `dim_base >= head_dim` and never enter it. Half the
block idles through the entire value phase, which looked like an obvious 2x.
`VALUE_VECTOR = 1` puts all 256 threads on one dimension each and is byte-exact,
and it is **19% slower** (67.663 ms): the value phase is not short of threads, and
halving each thread's independent work costs more than the added warps recover.

## Validation

Host: gfx1151 (Radeon 8060S), TheRock ROCm 10.0.0, `HIPENGINE_HIP_ARCH=gfx1151`,
model `unsloth-Qwen3.8-Flash-Next-UD-Q4_K_XL`, BF16 KV, block_size 256,
prefill chunk 1024, `scripts/qwen4exp_profile_gap.py --mode prefill --case-id
code-p4096 --repetitions 3 --prefill-chunk-size 1024`.

Microbench replay of the captured launch (`/tmp/fullattn-launch.npz`, 15
repetitions each), all variants byte-identical to the shipped route
(`maxdiff = 0.000e+00`):

| variant | ms | speedup | levers |
| --- | ---: | ---: | --- |
| 0 | 54.667 | 1.001x | shipped `<true,2>` geometry |
| 1 | 38.992 | 1.403x | int32 offsets |
| 2 | 43.420 | 1.260x | two-token QK unroll |
| 3 | 31.381 | 1.743x | both |
| 4 | 67.663 | 0.809x | `VALUE_VECTOR = 1` |
| 5 | 46.071 | 1.188x | `VALUE_VECTOR = 1` + int32 |

Promoted route against the shipped route on the same replay, 15 repetitions:

| route | ms | speedup | bit-exact |
| --- | ---: | ---: | --- |
| shipped fixed256 | 54.598 | 1.000x | reference |
| promoted, int64 fallback (capacity 0) | 43.423 | 1.257x | yes |
| promoted, int32 (capacity 4352) | 31.396 | 1.739x | yes |

In situ per-launch times from `qwen4exp_fullattn_launch_probe.py`, 3 repetitions,
device-synchronised around each launch, both arms in one session and selected by
`HIPENGINE_QWEN4_EXP_FULLATTN_CONTEXT_LEGACY`:

| launch | legacy (ms) | promoted (ms) | speedup |
| --- | ---: | ---: | ---: |
| rows=1024, `max_context_len`=1024 | 12.413 | 8.715 | 1.424x |
| rows=1024, `max_context_len`=2048 | 54.731 | 31.562 | 1.734x |
| rows=3, `max_context_len`=2051 | 0.596 | 0.489 | 1.219x |
| per-layer total | 67.740 | 40.766 | 1.662x |
| 12-layer total | 812.9 | 489.2 | 1.662x |
| prefill wall median | 16.6865 s | 16.3325 s | -354.0 ms (-2.12%) |
| tokens/s | 245.415 | 250.813 | +2.20% |

The summed per-launch saving is 324.4 ms and the measured wall saving is 354.0
ms, so the full kernel-level saving reaches the wall. An earlier cross-run
comparison against `plain-a` (16.534 s, 247.739 tok/s) showed only a 182 ms wall
delta; that 142 ms shortfall was session drift, not hidden launch time, which is
why the retained row uses the same-session A/B. The legacy arm of the A/B itself
measured 16.6865 s against `plain-a`'s 16.534 s on the same route, a 153 ms
drift that bounds the cross-run noise.

The same A/B repeated across all four mtp-bench categories at p4096, three
repetitions per case, all eight invocations in one session:

| category | legacy (tok/s) | promoted (tok/s) | change |
| --- | ---: | ---: | ---: |
| code | 246.552 | 253.033 | +2.63% |
| general_en | 248.581 | 252.846 | +1.72% |
| general_ja | 249.248 | 253.567 | +1.73% |
| mixed_ja_en | 248.056 | 253.953 | +2.38% |
| category mean | 248.109 | 253.350 | +2.11% |

Every category improves, in a +1.72% to +2.63% band. That uniformity is expected
rather than encouraging on its own: the change is byte-identical, so no category
can be favored, and the spread only reflects how much of each 4096-token prompt
is full-attention work.

Test gate: `tests/test_gpu_fullattn_context_promoted_route.py`, 4 passed. It pins
the int32 selection boundary (`INT32_MAX // (kv_heads * head_dim)` accepted,
+1 rejected, non-positive capacity rejected) and asserts byte equality of the
int32, int64-fallback, and overflow-rejected routes against the shipped route on
the device.

Correctness: the promoted route is asserted byte-identical to the shipped route
by `tests/test_gpu_fullattn_context_promoted_route.py` across three shapes and
all three capacity choices (int32 selected, int64 fallback, overflow rejected),
and by the microbench over the full 1024 x 24 x 256 production output. Because
the arithmetic is unchanged there is no KL or top-1 gate to satisfy and no
execution-profile promotion applies.

## Next

- The offset table is still 8 KB of the 17,223 bytes at `max_context_len` 2048.
  Storing one `physical_block` per token and deriving `block_offset`
  incrementally in the PV loop would cut it to about 68 bytes, lifting residency
  to roughly 6 blocks per CU from 3. That is the same lever again rather than a
  new idea, and it is byte-exact for the same reason. Estimated 1.2-1.4x on top
  of the current route; not attempted here.
- The same int32-offset and unroll levers apply unchanged to the
  `..._c1_exact_kernel` route, which is a separate kernel and was measured at
  463 ms on this shape while benchmarking the wrong entry point. That number is
  not a valid c1 measurement and the c1 route has not been benchmarked.
- `Qwen4ExpQSAPrefillMetadata.block_tables_host` is declared and never assigned;
  either wire it or drop it.
- The 512- and 1024-token prompt lengths were not re-measured. The win should be
  smaller there because the attention leaf's share of the prefill falls with
  prompt length, but that is a prediction, not a measurement.
