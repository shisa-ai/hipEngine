# YuE2 NAR tensor-core attention

## Summary

The scalar NAR attention ran at ~1.3 TFLOP/s. Profiling the pinned upstream on the
same case for the first time showed why that is a wall: its attention kernel
(`attn_fwd`, grid (2688, 16, 1), 1792 calls at 2.310 ms) does the whole 32-step
solve's attention in **4.14 s**, i.e. 12.4 TFLOP/s on tensor cores, against the
scalar kernel's ~39 s. Scalar FP32 peak on 40 CUs is 25.6 TFLOP/s and the scalar
kernel keeps roughly a quarter of its instructions as useful arithmetic after the
softmax reductions, the weight exchange and the loads, so even a perfect scalar
kernel lands near 6 TFLOP/s (~8.5 s). The remaining distance is arithmetic class,
not loop structure.

This unit adds that arithmetic class as a second attention kernel for the production
head geometry.

## Changes

- `hipengine/kernels/hip_gfx1100/yue2/nar_wmma.hip` (new):
  `yue2_nar_attention_wmma_kernel` + `hipengine_yue2_nar_attention_wmma`. f16 WMMA
  operands (`__builtin_amdgcn_wmma_f32_16x16x16_f16_w32` for the score product,
  `..._wmma_f16_16x16x16_f16_w32` for the value product) with f32 score
  accumulation, a 16-key tile reduced across the two half-wavefronts with
  `lane_xor16`, K and V sharing one 64-key staged buffer, and an f16 output
  accumulator rescaled by the online softmax. Geometry: 32 query rows × 2 query
  heads per block, grid `(ceil(rows/32), 8 key/value heads)`, 128 threads. Every key
  in `[AR cache | NAR]` is visible; the only mask is the tail past the key count.
- Fragment contracts follow the in-tree
  `hipengine/kernels/hip_gfx1100/attention/laguna_flash_attention_prefill.hip`,
  which preserves llama.cpp's HIP `fattn-mma-f16` design (the C fragment's column
  mapping `2 * element + (lane >> 4)`, the probability pairing before the value
  product, and the shared key/value staging buffer).
- `hipengine/kernels/hip_gfx1100/yue2/nar.py`: the kernel joins the `yue2_nar` build
  family and gains a `nar_attention_wmma` wrapper with the scalar kernel's ABI. The
  device entry point guards its own geometry and returns `hipErrorInvalidValue`
  otherwise, so callers fall back on its error code rather than duplicating guards.
- `hipengine/runtime/yue2_nar.py`: dispatches to the tensor-core kernel for the
  production geometry, with `HIPENGINE_YUE2_NAR_ATTENTION=scalar` forcing the strict
  fallback.
- `scripts/yue2_attention_bench.py`: `--kernel {scalar,wmma}` so both can be timed in
  one session.
- `tests/test_unit_yue2_nar_kernels.py`: seven-shape numerical test against the
  independent FP64 NumPy reference (rel L2 < 0.02, cosine > 0.9995, tighter than the
  M4 gate so a regression shows up before the gate) and a geometry-guard test.

## Validation

Kernel time at the production shape (1 299 rows, 1 396 AR keys, 16/8 heads,
head_dim 128), alternating the two sources in one session:

| | run 1 | run 2 | minima |
| --- | ---: | ---: | ---: |
| scalar | 20.08 ms | 20.72 ms | 16.18 / 16.33 ms |
| tensor core | 4.20 ms | 3.85 ms | 3.78 / 3.74 ms |

**5.1x**, and 1.7-1.8x the reference's own 2.310 ms dispatch.

Numerical agreement with the scalar kernel (which is bit-exact to the recorded
parent, so it is the oracle for what this variant costs): worst across eight shapes
**rel L2 0.00540, cosine 0.99998564, max abs 0.00151**, at the production shape
0.00540 / 0.99998564.

Production-profile gates — this variant cannot be bit-exact, so it is held to the
M4 solver gates rather than the parent fixture (thresholds rel L2 0.05, cosine
0.999):

| Gate | Scalar path | Tensor-core path |
| --- | ---: | ---: |
| chunk0 latents | 0.01225 / 0.999926 | **0.01042 / 0.999947** |
| multi-chunk | 0.01071 / 0.999944 | **0.01054 / 0.999946** |
| restricted visibility | 0.00885 / 0.999962 | 0.00938 / 0.999957 |

All three pass; two improve. The tensor-core path tracks the reference's arithmetic
class more closely, which is why chunk0 improves rather than drifts.

End to end, `mandarin-off-s1234`:

| | scalar path | tensor-core path |
| --- | ---: | ---: |
| 2-step solve | 6.69 s | **5.14 s** |
| 32-step product solve | 54.76 s | **32.22 s** |
| 32-step full replay | 74.84 s | **60.28 s** |

The 32-step solve is **1.18x** the reference's 27.32 s, from 16.2x before the
attention and projection work and 2.00x before this kernel. Across all twelve cases
at 2 steps the solver's per-ODE-step ratio falls from 5.79x to **3.93x**, and the
full suite passes 12/12 with every case reproducing its exact frame and sample count
in 464.6 s against 527.4 s. The decode stage is untouched by this change; its own
time moved between runs (20.08 s then 28.06 s), so the solve is the like-for-like
figure. `HIPENGINE_YUE2_NAR_ATTENTION=scalar` reproduces 26.8 s for the 2-step
replay, matching the scalar path's 26.70 s.

## Next

At 32 steps the solver is now ~9.6 s of attention, ~15 s of projections and ~7.6 s of
conditioning prefill and other work (from two solve lengths: 32.22 = 32a + x and
5.14 = 2a + x). The projections are the largest single item and run at hipBLASLt's
rate, so further attention work has less to win than it did; the remaining attention
levers are this kernel's own tuning (the 64-key online-softmax batch against the
reference's grid, two blocks per CU, and whether the f16 output accumulator can give
way to f32 without losing occupancy).
