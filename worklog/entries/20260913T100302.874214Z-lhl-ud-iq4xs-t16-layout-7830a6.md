# The IQ4_XS T16 replacement layout is byte-neutral and verified against real GGUF bytes

## Summary

`gguf_iq4_xs_local32_gemv` is the largest family in UD-Q4_K_M: 117 tensors,
4760.0 MB, 11.373 ms/step (31.3% of UD kernel time). It runs at 425-441 GB/s
against 600-704 GB/s for the t16 rowtile owners. Every bit-identical knob on
it is now measured and closed (`COLS` optimal at 8, the `WAVES` heuristic
optimal on all six real shapes, the `ROWS > 1` launch-bounds floor neutral),
so the remaining lever is structural: IQ4_XS has no tile layout, which is why
the local32 owner is the only option for it.

This unit lands the first half of that lever: the `IQ4_XS T16` replacement
layout plus its CPU packer and inverse. The layout is a **bit-lossless
permutation of the same bytes**, so it is byte-neutral (2176 bytes per
16-column tile against 16 x 136 raw) and costs **no resident footprint**, and
an owner reading it can keep the local32 accumulation order if that is
wanted.

## Changes

- `hipengine/quant/gguf_repack.py`: `IQ4_XS_T16_SHAPE =
  GGUFRepackShape(GGMLQuantizationType.IQ4_XS, 2, 16)`.
- `hipengine/quant/gguf_t16.py`: layout constants, the `GGUFIQ4XSTile16`
  dataclass, `repack_gguf_iq4_xs_tile16`, `unpack_gguf_iq4_xs_tile16`, and
  `__all__` entries.
- `tests/test_gguf_iq4_xs_t16_layout.py`: the byte oracle.

The layout keeps `d` (f16), `scales_h` (u16) and `scales_l` (4 bytes) as
per-column records and transposes the 128-byte `qs` plane from
`[group][byte]` per column to `[group][element][column pair]`, with the even
column in the low nibble and the odd column in the high nibble. The win is
that a single u32 read at one element now yields eight columns' nibbles
instead of one column's eight elements, which is the load-shape difference
between the local32 and t16 rowtile families.

The raw IQ4_XS block, confirmed against `_dequant_iq4_xs_blocks`, is 136
bytes: `d` at 0, `scales_h` at 2 (2 bits per group), `scales_l` at 4 (one
nibble per group, so group `g` is nibble `g` of the little-endian u32), and
`qs` at 8 where group `g` owns bytes `8 + g*16 .. 8 + g*16 + 15` and element
`e = half*16 + byte` lives at byte `byte` in nibble `half`.

## Validation

`pytest tests/test_gguf_iq4_xs_t16_layout.py -q` -> 8 passed. The tests check
three independent things, because a packer can be self-consistent and still
wrong:

1. **Round trip is byte-exact** on random bytes at three shapes and on a real
   IQ4_XS tensor from `/models/gguf/Qwen3.8-27B-UD-Q4_K_M.gguf`.
2. **Tile semantics match the raw layout**, element by element, decoded from
   the documented rules on both sides rather than from the packer.
3. **An independent tile decode reproduces the original GGUF bytes.** This is
   the decisive one: `_tile_to_raw_blocks` re-derives every offset from the
   layout description instead of calling `unpack_gguf_iq4_xs_tile16`, and is
   checked byte-for-byte against the raw tensor bytes for the first two
   out-tiles of a real 47.35 MB tensor at every block. It catches a wrong but
   self-consistent convention, which the round trip cannot.

A fourth test dequantizes the tiled bytes with the repository's own
`_dequant_iq4_xs_blocks` and compares bit patterns with the raw dequantization
(random `d` fields can decode to NaN, so the comparison is on the uint32 view).

Related suites unaffected: `pytest tests/test_gguf_q6_k_t16_gemv_decode.py
tests/test_gguf_q4_k_t16_dense.py tests/test_gguf_q5_k_t16_dense.py -q` -> all
pass.

## Next

The layout has no consumer yet; the second half of the item is the owner. It
should read the tile so that one load serves multiple columns, and per the
measured row-slab gradient (563.1 GB/s at rows=1 against 399.2 at rows=4 at a
fixed byte count) it should minimise live per-row state and keep the
per-element operation count independent of the row slab. Then materialization
at load time, dispatch/registry wiring, and the applicable production-profile
gate. Until the owner exists, the layout is exercised only by its oracle test.
