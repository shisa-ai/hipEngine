## Kernel trace

Command (cached-only child, no compiler under the profiler):

```
hipcc --version > /tmp/hipengine-hipcc-version.txt
rocprofv3 --kernel-trace --output-format csv -d /tmp/yue2-nar-trace -- \
  python3 scripts/yue2_nar_rocprof_smoke.py \
    --compiler-version-file /tmp/hipengine-hipcc-version.txt
```

One NAR velocity evaluation plus a 2-step `solve` on the 34-row / 545-token-AR
chunk, host zbook / gfx1151, 5867 dispatches / 19 distinct kernel names. All five
NAR kernels appear under their expected names:

| Kernel | Dispatches | Total | Average |
| --- | ---: | ---: | ---: |
| `yue2_nar_attention_kernel` | 140 | 144.002 ms | 1028.59 us |
| `yue2_nar_rope_kernel` | 280 | 0.944 ms | 3.37 us |
| `yue2_nar_gather_add_kernel` | 5 | 0.020 ms | 3.94 us |
| `yue2_nar_add_broadcast_kernel` | 5 | 0.013 ms | 2.63 us |
| `yue2_nar_state_update_kernel` | 4 | 0.006 ms | 1.60 us |

The smoke originally drove only `velocity_bits`, which never launches
`yue2_nar_state_update_kernel`; it now runs a 2-step `solve` too, so the solver
kernel is covered. Counts are consistent with the schedule: 28 layers x 5
velocity evaluations = 140 attention dispatches, 2 RoPE launches per layer per
evaluation = 280, and 2 solver steps x 2 updates = 4 state updates.

The attention kernel dominates at ~1.03 ms per call. That is the expected shape
of the current implementation - one thread block per (row, head) pair doing a
straight gather-and-dot over 545 cached keys, ~132 MFLOP per call at ~128
GFLOP/s on an integrated part - and it is the first optimization target once M5
lands, not a claim about the achievable rate.

## Multi-chunk and `nar_cond_end` tooling

- `scripts/yue2_oracle.py nar` now records **every** chunk of the song rather
  than only chunk 0, writes one `chunk{index}.npz` per chunk plus a
  `chunk_reports` list in the manifest, honours `--nar-cond-end`, accepts
  `--context` (the reference's own `song_chunks` takes a context, so a small
  context yields a genuinely multi-chunk song at fixture-friendly sizes), and
  takes `--nar-subdir` so each recorded case gets its own fixture directory. The
  per-chunk replay self-check is retained.
- `scripts/yue2_nar_gate.py` now checks a whole fixture directory: every
  `chunk*.npz` is conditioned and compared, and the gate passes only when every
  chunk passes both its teacher-forced velocities and its own solved trajectory.
  It reproduces the release case exactly (worst velocity `rel_l2` 0.01892, solved
  latents `rel_l2` 0.01225, cosine 0.999926, PASS).
