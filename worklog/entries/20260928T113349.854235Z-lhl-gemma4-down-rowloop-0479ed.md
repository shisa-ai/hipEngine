# the down kernel's row loop is already unrolled; the remaining lever is the dp4a count, not its scheduling

## Summary

The previous entry's named next step was to specialize the down projection's row
loop on its common case so it could unroll, on the reading that `rcount` being
dynamic is what stops the compiler from interleaving the per-row `dp4a` chains.
**Two cheap checks refute it, and the second one was run rather than argued.**

**1. There is no register spill, so the loop is already unrolled.** `acc` is a
32-element local array indexed by the row, and a genuinely dynamic index would
force it into scratch memory. `rocprofv3` reports `Scratch_Size = 0` for this
kernel at both `ROWS_PER_PASS` values, and VGPR count rises 80 to 96 when the
constant goes 16 to 32 -- one register per accumulator, which is what holding
them in registers costs. The compiler had already unrolled enough to make every
index static; the source comment that says the row loop "is not unrolled" was
describing an earlier state, not this one.

**2. Asking for it explicitly changes nothing.** Adding `#pragma unroll` to the
row loop, measured on the microbench at gemma4's shape:

| | uniform 32 rows | Poisson mean 32 |
| --- | ---: | ---: |
| baseline | 2.696 ms/call | 2.828 ms/call |
| `#pragma unroll` | 2.703 ms/call | 2.871 ms/call |

Inside run-to-run noise, and marginally worse on both. Reverted.

**So the row loop's scheduling is not the lever. Its instruction count is.**
Per (thread, row, K32 sub-block) the body issues 16 `dp4a` -- eight for the Q5_1
nibble plane and eight for the high-bit plane -- against roughly as many loads,
scale reads and FMAs. The 16 is not slack: a Q5_1 value is
`(nibble + 16 * bit) * d + m`, so the dot product is two independent 4-bit dots
over the same activation, and no amount of unrolling merges them.

**What would merge them is a resident layout that stores the 5-bit codes as
int8.** Eight `dp4a` per 32 values instead of sixteen, at 1.33x the weight bytes
(190.3 MB to 253.7 MB per layer, so +1.9 GB resident for the model) and a
load-time repack. The bytes are close to free -- the previous entry measured this
kernel's time as invariant to a 20 percent change in fetched bytes -- so the
1.33x is affordable in a way it would not be for a bandwidth-bound kernel. That
is a real project: a new layout, a repacker, a kernel variant, an oracle, and
loader wiring. It is named here rather than started, because it is worth roughly
a quarter of one kernel and the estimate should be checked against the
instrument before it is paid for.

   buffer would settle it in one microbench run and needs no loader work.
