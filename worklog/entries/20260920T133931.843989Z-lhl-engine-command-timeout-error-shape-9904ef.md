# report an unresponsive engine service as retryable engine_unavailable

## Summary

A live `/v1/chat/completions` request answered HTTP 500 `TimeoutError: engine service
command timed out` from `EngineService._control` during `tokenize`. The driver
thread was busy with real work, not stalled: the same request's summary reported a
KV pool growth (`kv_pool_grows=2`) and a 34.8 s prefill, and a command queues behind
whatever the driver is doing. The 30 s budget was therefore shorter than legitimate
engine work - that part was fixed earlier in `adafd0597` (300 s liveness budget,
`ENGINE_COMMAND_SLOW` diagnostics naming the blocking activity) and `b63bf9755`
(the wait moved off the event loop thread, which is what made the stall server-wide).

What remained was the error's shape. An exhausted budget is a property of the
runtime, not of the request that happened to be waiting, but it escaped request
handling as a plain `TimeoutError` and the server answered the non-retryable
`internal_error`, telling a client its own request was at fault for an engine that
never answered.

## Changes

- `hipengine/generation/engine_service.py`: `EngineCommandTimeout(TimeoutError)`,
  raised by `_wait_response` and `_CommandResponse.result` in place of a bare
  `TimeoutError`. It stays a `TimeoutError` for callers that only know it was a
  timeout, and carries the method, budget, and driver activity.
- `hipengine/server/api.py`: the escaped-fault handler reports
  `EngineCommandTimeout` the way it reports `EngineServiceClosed` - HTTP 503
  `engine_unavailable`, retryable, with the exception's own message - instead of
  500 `internal_error` / `unhandled server error: TimeoutError: ...`. The
  `engine_unavailable` taxonomy description now covers an unresponsive service.
- `hipengine/generation/__init__.py`: export `EngineCommandTimeout`.
- `docs/API.md`, `docs/ENVS.md`: an exhausted budget is documented as HTTP 503
  `engine_unavailable` rather than HTTP 500 `internal_error`.
- `tests/test_integration_server_api.py`:
  `test_engine_command_timeout_answers_with_a_typed_unavailable_error` drives a
  preparation-time command timeout through the app and requires 503,
  `code=engine_unavailable`, `exception_type=EngineCommandTimeout`, and the
  method/budget/activity detail in `error.message`.
- `tests/test_integration_generation_engine_service.py`: the exhausted-budget test
  asserts the typed error (and that it is still a `TimeoutError`).

## Validation

- New server test is RED without the `api.py` mapping (`assert 500 == 503`) and
  GREEN with it.
- `tests/test_integration_server_api.py`: 634 tests, exit 0 (includes the error
  taxonomy/capabilities consistency test, so the table and `docs/API.md` agree).
- `tests/test_integration_generation_engine_service.py`,
  `tests/test_unit_llm_generate.py`: exit 0.
- Live on the gfx1151 `Qwen3.8-27B-Q4_K_M` server (pane `%3`, `--info --metrics
  prometheus --log-color always`), reproducing the original shape - a large prompt
  holding the driver thread while a second request arrives 2 s later:

  | run | request | prompt tokens | prefill_ms | status | wall |
  | --- | --- | --- | --- | --- | --- |
  | 1 | large | 7,208 | 27,501.2 | 200 | 28.3 s |
  | 1 | concurrent small | 11 | 302.2 | 200 | 27.0 s |
  | 2 | large | 23,408 | 96,208.8 | 200 | 97.1 s |
  | 2 | concurrent small | 11 | 299.3 | 200 | 95.7 s |

  The second run's 96.2 s prefill is three times the old budget, and both requests
  were served: zero `UNHANDLED_ERROR`/`REQUEST_FAILED` lines and zero
  `ENGINE_COMMAND_SLOW` lines, i.e. the driver kept answering commands between
  prefill ticks while the small request waited for its turn.

## Next

- The 503 path itself is covered by tests rather than a live run: reaching it live
  needs an artificially tiny budget (a second model instance does not fit beside
  the resident one on this host). `HIPENGINE_ENGINE_COMMAND_TIMEOUT_SECONDS=2`
  on a restart reproduces it directly if that evidence is ever wanted.
- The slow-command warning threshold (10 s) is a constructor default, not an env
  var; the budget is the tunable knob.
