# Fix the DMS append compaction race that shifted KV entries

## Summary

The DMS append/decode compaction had a data race in both the INT8 and BF16
kernels: inside a 256-slot chunk each thread copied its kept slot straight from
`src` to `dst`, so a thread whose `dst` was another thread's unread `src`
overwrote it. With one expired row every later slot moves left by one, so the
extent came back with a duplicated and shifted position at random sites. The
chunk boundary protected the cross-chunk case; nothing protected the inside of
a chunk, and the existing tests were too small to show it.

`tests/test_gpu_dms_int8_device_payloads.py` failed on this at 8,193 and 16,385
slots on the campaign base commit `998b7b0a4`, so the defect predates this work.
The failing extent is the DMS steady state at an 8K window, not an exotic input.

## Changes

- `hipengine/kernels/hip_gfx1100/attention/dms_compact.hip` and
  `dms_compact_int8.hip`: pass 2 now stages each 16-slot tile through shared
  memory, reads every source of the tile, then writes the compacted slots. A
  tile's writes can only land in tiles already written because `dst <= src`, so
  the staging makes the move safe without serializing it. Both launchers pass
  the staging size as dynamic shared memory and refuse a `dim` whose staging
  would exceed 64 KiB.
- `tests/test_gpu_dms_append_decode_hip.py`: new
  `test_dms_append_decode_long_extent_compaction_is_exact` runs an 8,193-token
  extent with one expiry against the host oracle and compares live count,
  positions, K/V payload and evict mask. It covers the multi-chunk compaction
  the existing cases never reached; it is coverage rather than a RED case
  because the BF16 kernel did not reproduce the shift on this host.

## Validation

- RED, INT8: `uv run pytest tests/test_gpu_dms_int8_device_payloads.py` failed
  two cases before the fix with `Arrays are not equal ... 5 / 8193` and
  `after.positions` showing a duplicated value, and at base commit `998b7b0a4`
  in a separate worktree with the same two cases.
- Nondeterminism, INT8: five identical trials of the 8,193-slot append produced
  different mismatch sites each time (3, 1, 1, 2, 2), which is the signature of
  a race rather than an arithmetic difference.
- GREEN, INT8: same file `5 passed`, and eight consecutive runs `0/8` nonzero.
- GREEN, BF16 and neighbours: `uv run pytest tests/test_gpu_dms_append_decode_hip.py
  tests/test_gpu_dms_compact_attn_decode_hip.py
  tests/test_gpu_dms_int8_backend_integration.py
  tests/test_gpu_dms_int8_device_payloads.py
  tests/test_gpu_dms_direct_device_pipeline_hip.py
  tests/test_gpu_kvcache_dms_device_hip.py tests/test_gpu_dms_layerwise_kv_release.py
  tests/test_gpu_dms_streaming_pack_hip.py` — 46 passed.
- Cost, same host, 60 appends on an 8,193-slot extent with four heads, old
  kernel vs new: BF16 3.436 -> 3.467 ms (+0.9%), INT8 3.213 -> 3.198 ms (-0.5%).
  The staging is within run-to-run noise at the worst-case extent.
- rocprofv3 `--kernel-trace` on a 2,049-slot append:
  `dms_int8_append_kernel` 3 dispatches, 798.5 us mean, so the profiled kernel
  is the one under test.
- Observation for the DMS lane, not fixed here: the compaction dominates append
  cost at an 8K window (about 3.4 ms per append per layer), which is what
  bounds that route's decode rate. A ring head instead of a memmove would
  remove the move entirely; see `docs/REFACTOR.md`.
