# Correct Gemma flash decode and promote the global route

## Summary

The key-sliced flash decode kernel was returning numerically wrong attention for
every row from the third slice row onward, and the production plan has been
routed through it for the long global decode step. Both are fixed here: the
lookahead defect in the kernel, and the plan change that makes the corrected
route the one the production profile selects.

The defect was live before this unit started. At `308c4c38c` the flash route
served **every one-token decode with keys in `[1024, 15856]`** for the sliding
packing (head_dim 256, GQA ratio 2) and `[1024, 15616]` for the global packing
(head_dim 512, ratio 8) -- above those bounds `global_logits` is true and the
route is the class kernel or the staged candidate. So the wrong arithmetic
covered the ordinary short-to-medium context decode, not one narrow variant.

The plan change is measured, route-labelled, and reproduces an identical argmax
to both the route it replaces and the strict chain at 32K, 64K, and 128K.

## Changes

- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention.hip`:
  `gemma4_attention_decode_flash_kernel` refilled its three-deep V pipeline one
  row early (`jn = jj + 2`). The shift leaves `pipe[2]` holding `V[jj+2]`, so
  the stage to refill is `jj + 3`; loading `jj + 2` wrote the row already sitting
  in `pipe[1]`, and from `jj == 3` on every V row was accumulated against the
  previous row's weight. The resident-bound check and the flash request are also
  reordered so the request is honoured first: the bound describes the class
  kernel's owned global logits, which the flash kernel does not use.
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention.py`: three exported
  helpers -- `flash_min_slices`, `flash_serves`, `flash_request_slices` -- plus
  `prefer_flash` on the private `_launch_prefill`. `flash_request_slices` is the
  single definition of the count a request carries: the larger of the
  occupancy-target policy value and the smallest count whose per-block LDS fits,
  which is what keeps a long global row on the route instead of falling through
  to the class kernel. `DECODE_ATTENTION_FLASH` and
  `gemma4_attention_decode_flash_bf16` register the variant.
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_layer.py`: the exact-decode
  selector resolves the flash candidate after the shape guards, so a prefill
  block, a sliding layer, or a trimmed call keeps the native kernel.
- `hipengine/generation/gemma4_profiles.py`: the production plan's decode scope
  selects `gemma4_flash`; `gemma4_staged` stays registered as the strict chain
  and rollback lever.
- `hipengine/runtime/gemma4_decode_graph.py`: the explicit capture surface
  reserves the launcher's own request count and loads the staged library for
  both routes. This surface is not on the default decode path (its default-on
  attempt measured negative on 2026-09-30 and was reverted), so this keeps it
  consistent rather than fixing a shipped route.
- `tests/test_unit_gemma4_decode_attention_selection.py`: a guard that binds the
  flash variant's forwarded keywords against `_launch_prefill`'s real signature.
- `docs/REFACTOR.md`, `docs/KERNELS.md`: the promotion, the rollback lever, and
  the fallback's removal condition.
- `scratch/flash_plan_ab.py`, `scratch/flash_logits_parity.py`,
  `scratch/flash_route_baseline_probe.py`: the route-labelled A/B, the three-arm
  parity, and the plan-default probe.

The public prefill wrappers keep their keyword set. An earlier revision of this
unit put `prefer_flash` on them; two existing tests pin that keyword set as the
layer's shared call-site contract, and the flash variant now reaches the private
launcher directly instead.

## Validation

- `pytest tests/test_gpu_gemma4_flash_decode.py -v` -> **60 passed in 4.21 s**.
  Before the fix the same file was 44 failed / 16 passed.
- `python3 scratch/flash_oracle_probe.py` against an f64 oracle, same inputs,
  both arms: global head_dim 512 at 4096 keys and scale 1.0 -> single
  `5.394e-06`, flash `5.394e-06`. The pre-fix flash arm on that row was `3.912`.

Route and arithmetic, one model residency each:

- `python3 scratch/flash_plan_ab.py --contexts 32768 65536 131072 --repeats 5`
  (fixed teacher token and KV prefix, rewind each replay, one untimed warmup,
  median of forward/sample/sync). Route reported by the layer's route reporter
  and the launcher's selection counter, not inferred:

  | context | strict plain | staged (pre-change plan) | flash (current plan) | staged/flash |
  | --- | --- | --- | --- | --- |
  | 32K | 65.57 ms | 27.64 ms | **18.31 ms** | 1.51x |
  | 64K | 118.35 ms | 42.34 ms | **24.11 ms** | 1.76x |
  | 128K | 224.31 ms | 73.59 ms | **30.15 ms** | 2.44x |

  All three routes sample the same token at every context (108, 1018, 236825),
  and every row was bitwise-stable across its five replays.
- `python3 scratch/flash_logits_parity.py --contexts 32768 65536 131072` runs the
  three arms by re-registering the variant's registry key, which is the call
  site the layer resolves through. At every context the flash arm's argmax is
  the reference's top-1 token, and the margin is wider than the numerical
  difference at those two logits, so the agreement is not a tie broken
  differently: 32K margin 0.245 vs delta 0.011; 64K 0.336 vs 0.240; 128K 0.694
  vs 0.152. The staged arm is bitwise equal to the strict arm at all three.
- `python3 scratch/flash_route_baseline_probe.py --context 32768` confirms the
  pre-change plan's own decode-variant set resolves to `gemma4_staged` and is
  bit-identical to the strict chain on that KV prefix, so the comparison above
  is against the route the plan actually ran.
- The flash route's decode logits are byte-identical across three independent
  processes today (`6936a96f9a9b86f5`, `0eb5d11f4e75feb6`, `4db00ae9824adf71`)
  and match the earlier `/tmp/gemma4-pv/fixed-decode-attrib.json` exactly.

Regression scope:

One observation is left unexplained rather than resolved: the older
`/tmp/gemma4-pv/baseline-decode-attrib.json` (2026-10-08 08:58, tree clean at

its own route and its logits agree across three processes.
