# Surya text-prefill causal score tiling

## Summary

`SuryaGpuRunner._attention_packed` materialized the full causal score matrix for
the text prefill, `num_attention_heads * tokens^2 * 4` bytes (8 heads). Measured
at `max_seq` 16384: 2.36 GB of a 7.03 GB peak for the 8580 image tokens of a
300-DPI A4 page, and 8.59 GB of a 14.71 GB peak at a full 16384-token prompt.
That was the last quadratic allocation in the Surya path, and it is now tiled by
query rows under `max_prefill_scratch_bytes`, exactly as the vision tower
already was.

The mask was the one thing that did not transfer directly.
`_vision_attention_packed` is bidirectional, so it scales with the generic
`evie_scale_f32` and needs no offset. The text prefill is causal, and a tile's
causal condition is `j <= start + i`, not `j <= i`. Without the offset every
tile after the first would attend to keys it must not see — and would still
produce finite, plausible scores, which is why the offset is pinned on the
kernel directly and not only through the end-to-end logits.

## Results

gfx1151 (Radeon 8060S, Ryzen AI Max+ Pro 395), fp32, `max_seq` 16384, one fresh
runner per (budget, token count) with `reset_memory_stats()` after construction,
mean of 3 timed prefills after the first (peak) prefill. Resident 3086.4 MB
(2663.0 weights + 402.7 KV planes + 18.9 GDN + 1.8 conv). `dense` = no budget.

| tokens | budget | query block | score tile | peak total | prefill | vs dense |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 8580 | dense | 8580 | 2355.7 MB | 7030.5 MB | 7.473 s | 1.000x |
| 8580 | 512 MiB | 1955 | 536.8 MB | 5211.6 MB | 7.467 s | 0.999x |
| 8580 | 128 MiB | 488 | 134.0 MB | 4808.8 MB | 7.539 s | 1.009x |
| 16384 | dense | 16384 | 8589.9 MB | 14709.2 MB | 16.638 s | 1.000x |
| 16384 | 512 MiB | 1024 | 536.9 MB | 6656.2 MB | 16.774 s | 1.008x |
| 16384 | 128 MiB | 256 | 134.2 MB | 6253.6 MB | 17.456 s | 1.049x |

The 16384-token peak falls 14.71 -> 6.66 GB (-54.7%) for 0.8% wall-clock at the
default budget, and the 8580-token page peak 7.03 -> 5.21 GB (-25.9%) for
nothing measurable. Below ~512 MB of dense score the budget is a no-op (2048 and
4096 tokens are one tile), and the non-attention scratch stays linear at
180.8 KiB/token, unchanged from the dense measurement — so the tiling removed
exactly the quadratic term and nothing else. A 128 MiB budget buys a further
0.4 GB for 4.9% at 16384 tokens, so the 512 MiB default sits on the flat part of
the trade.

## Changes

- `hipengine/kernels/hip_gfx1100/surya/surya_ops.{hip,py}` —
  `surya_causal_mask_scale_f32` takes a `query_offset` and renames its `tokens`
  argument to `queries` (the dense case is `queries == keys == head_stride`);
  the mask is `j <= query_offset + query_row`.
- `hipengine/runtime/surya.py` — `plan_score_tiles` is the single query-block
  planner shared by both paths (`plan_vision_attention` is now the vision-shaped
  name for it); `_attention_packed` walks the score matrix one tile at a time;
  `prefill_block` / `prefill_scratch_bytes` / `check_prefill_capacity` mirror
  the vision admission pair and are called from `prefill()` before any device
  work.
- `hipengine/generation/surya_gpu.py`, `hipengine/llm.py` —
  `max_prefill_scratch_bytes` on the generator, `prefill_max_scratch_bytes` on
  the registered factory and on `LLM`, validated like the vision budget.
- `scripts/surya_attention_memory.py` — reports the text tile plan and measures
  per-budget peaks and timings (`--text-budget-bytes`, `0` = dense, `--runs`).
- `benchmarks/results/2026-09-12-gfx1151-surya-text-prefill-tiling.json`.
- `benchmarks/README.md`, `benchmarks/CHANGELOG.md`, `docs/MODEL-SURYA.md`,

## Validation

- **Exactness.** At 1024 tokens under a 64 KiB budget (32 tiles of 32 query
  rows, 32 MiB dense) the tiled and dense GPU logits are `np.array_equal`, and
  the tiled logits match the NumPy CPU reference at KL < 1e-4 with the same
  argmax
  (`tests/test_surya_gpu.py::test_gpu_tiled_prefill_matches_dense_and_cpu_reference`).
  `block >= tokens` issues exactly the dense calls, so the dense plan remains
  the strict fallback, and the planner test pins that
  (`test_prefill_tile_plan_uses_one_tile_when_it_fits`).
- **Page scale, where the default actually splits.** A synthetic 8580-token
  text-only prompt under the default 512 MiB budget (5 tiles of 1955 query
  rows) is also `np.array_equal` to the dense plan
  (`test_gpu_tiled_prefill_is_bit_identical_at_the_default_budget`), so the
  production numerical gate's recorded numbers — which run at
  `max_seq` 16384 with the default prefill budget — still describe the default
  path, and no re-run of
  `benchmarks/results/2026-09-12-gfx1151-surya-numerical-gate.json` is needed.
- **The offset.** A direct kernel test masks tiles starting at 0, 7 and
  `tokens - 1` and compares each against the densely masked matrix
  (`test_gpu_causal_mask_honors_the_query_offset`).
- **Admission.** The admitted bytes equal the allocated bytes for several token
  counts and under a tiling budget; an over-budget prompt is rejected with
  nothing allocated, including through `prefill()` itself
  (`test_gpu_prefill_scratch_admission_*`, `test_gpu_prefill_admission_*`,
  `test_gpu_prefill_rejects_an_over_budget_prompt_before_any_device_work`).
- **Plumbing.** `_factory_capacity_kwargs` forwards both budgets only when set,
  and a non-positive budget is a configuration error at the generator and at
  `LLM` (`test_gpu_generator_forwards_context_and_scratch_budgets`,
  `test_llm_rejects_a_non_positive_score_tile_budget`).
- `tests/test_surya_gpu.py` 40 passed; `tests/test_surya_generation_contract.py`
  39 passed; the non-GPU Surya + `test_llm_generate.py` bundle (221) passed.
- Pre-existing failure, attributed rather than assumed:
  `tests/test_surya_e2e.py::test_end_to_end_greedy_matches_torch_reference`
  raises `MissingGeneratorError: (surya_ocr2, cpu_reference, fp32,
  greedy_one_token); known: <none>` in isolation too. Reproduced at
  `7ec024e8f` in a clean worktree, so it is the import-order registration defect
  already tracked as task #81 and not a regression from this change.
