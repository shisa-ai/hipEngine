# Q5_K t16 rowtile: per-shape col8 is a measured regression on all six verifier shapes

## Summary

The Q5_K t16 rowtile keeps `TILE_COLS = 4` on every shape of the UD-Q4_K_M
verifier. Widening the tile to 8 columns is **equal or worse on all six shapes**,
so the per-shape col8 gate that the cost model below seemed to imply is
rejected. No source change is retained.

## Context

The col4 census gives a measured bandwidth asymmetry inside one kernel at
identical bytes, identical rows, and identical launch geometry class:

| N | K | role | us/call | GB/s |
| ---: | ---: | --- | ---: | ---: |
| 5120 | 17408 | ffn_down | 87.1 | **704** |
| 17408 | 5120 | ffn_gate/ffn_up | 135.1 | **454** |
| 12288 | 5120 | attn_q | 100.0 | 433 |
| 10240 | 5120 | attn_qkv | 84.5 | 426 |
| 6144 | 5120 | ssm_out/attn_gate/attn_output | 53.2 | 406 |
| 1024 | 5120 | attn_k/attn_v | 20.5 | 175 |

A two-parameter model `cost = a * blocks + b * bytes` fitted on ffn_down and
ffn_gate/ffn_up gives `a = 15.6 ns` of fixed cost per block and `b = 913 GB/s`
of streaming, and reproduces attn_q, attn_qkv, and ssm_out within 11% (only the
3.6 MB attn_k/attn_v shape, where launch overhead dominates, misses). At short K
that fixed per-block term is half the measured time, and `TILE_COLS` 4 -> 8
halves the block count, so the model predicted roughly -25% on the short-K
shapes.

The earlier 2026-09-12 rejection of col8 was measured as a single global
aggregate. Because ffn_down is 49% of this kernel's time and is long-K, a global
result cannot separate a short-K win from a long-K loss, so the aggregate was
not sufficient evidence to close the per-shape question.

## Changes

No source change is retained; the experiment rebound a registered variant
name to an already-registered col8 host wrapper, measured, and reverted.

## Measurement

Temporarily rebound the registered `t16_gemv_rowtile_bf16_bf16_out` variant to
the already-registered col8 host wrapper, ran the same census, then reverted the
rebinding. This isolates `TILE_COLS` with no other change.

Command (both arms, physical GPU1, RX 7900 XTX, gfx1100):

```
HIP_VISIBLE_DEVICES=1 PYTHONPATH=/home/lhl/hipEngine-ud \
  python scripts/gguf_mtp_verifier_rocprof.py \
    --model /models/gguf/Qwen3.8-27B-UD-Q4_K_M.gguf --quant gguf_ud_q4_k_m \
    --mode block-verify --block-rows 3 --block-verify-mode native \
    --native-spec-target-cycle --steps 12 --warmup 3
```

Per-shape result, decoded from the raw `rocprofv3` kernel trace by reading the
`TILE_COLS` template argument and `Grid_Size_X / Workgroup_Size_X`:

| N | K | role | col4 us/call | col8 us/call | col4 GB/s | col8 GB/s |
| ---: | ---: | --- | ---: | ---: | ---: | ---: |
| 5120 | 17408 | ffn_down | 87.1 | 91.4 | 704 | 671 |
| 17408 | 5120 | ffn_gate/ffn_up | 135.1 | 135.1 | 454 | 454 |
| 10240 | 5120 | attn_qkv | 84.5 | 87.9 | 426 | 409 |
| 6144 | 5120 | ssm_out/attn_gate/attn_output | 53.2 | 53.9 | 406 | 401 |
| 12288 | 5120 | attn_q | 100.0 | 99.6 | 433 | 435 |
| 1024 | 5120 | attn_k/attn_v | 20.5 | 29.4 | 175 | 122 |

Aggregate: the kernel goes 11.709 -> 11.961 ms/step (**+2.2%**, worse), and total
kernel time 42.872 -> 42.692 ms/step. The other kernels move by -0.18, -0.10,
-0.05, +0.002 ms/step in both directions; none of them is on the Q5_K path, so
those are run-to-run variance and only the +0.252 ms/step on the Q5_K rowtile is
attributable to the change.

## Validation

Both arms ran the identical census command on physical GPU1 with 985 kernel
calls/step in each, so the comparison is shape-for-shape at fixed protocol. The
change under test is a single registered-variant rebinding, and it was reverted
before this entry was written (`git status` clean against the previous commit).

## What the negative result establishes

The `a * blocks + b * bytes` model still fits the col4 data, but its implied
remedy is falsified: **halving the block count at fixed K removes no time on the
ffn_gate/ffn_up shape**, which is bit-identical at 135.1 us/call under both
tilings. The 704-vs-454 GB/s spread is therefore not per-block amortization. It
is invariant to how the columns are grouped, so the remaining explanation is
inside the K-loop steady state itself, which is where the earlier instruction
level attempts (activation-load vectorization, col8) also came back neutral or
negative. Two independent tilings and two independent instruction-level changes
have now failed on this shape; the next attempt on it needs hardware counters
rather than another structural guess.
