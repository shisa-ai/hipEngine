# Gemma 4 KV cache path: capacity-sized scratch and decode-shaped attention

## Summary

The Gemma 4 layer can now generate. Attention takes a **separate key count** from
its query count, the layer appends K/V into a cache and reads it back, and the
scratch buffers became **capacities** rather than identities. A new test drives
six-token prefill plus three one-token decode steps and requires each decode row
to reproduce the corresponding row of a dense nine-token prefill.

This is the plumbing the runner needs; it is not the runner.

## Two real defects this work exposed

Both were latent in the layer that passed its own tests, and both would have
produced wrong output rather than an error at generation time.

### 1. The layer inferred its block size from the scratch allocation

`rows = scratch.tokens` meant a scratch sized for the widest block could not run
a narrower one: a one-token decode step through a nine-token scratch ran as
though it had nine rows, reading past its inputs and writing 288 cache elements
instead of 32. It surfaced as `HIP error 1: invalid argument` from the cache
append, because the offset plus the oversized length ran off the end of the
allocation — an accident that it failed loudly at all.

`rows` is now an explicit argument (defaulting to `scratch.tokens` for the dense
case), bounded above by the scratch capacity. The same defect existed in
`gemma4_experts_forward_bf16`, which likewise derived `tokens` from its scratch.

### 2. The scratch identity checks made a capacity unusable

`gemma4_router_topk_bf16` compared `(tokens, hidden_size, num_experts, top_k)`
for exact equality against the scratch. That is the right check for the shape
parameters, which describe the *weights*, but the wrong one for `tokens`, which
describes the *block*. Generation sizes one scratch for the prefill width and
then routes single-token steps through it, so the exact check made the intended
use impossible. Both the router and the experts now require the shape parameters
to match exactly and `tokens <= capacity`, and reject a wider block rather than
overflowing.

`test_router_scratch_rejects_a_mismatched_shape` asserted the old contract. It is
now `test_router_scratch_is_a_capacity_not_an_identity` and covers all three
cases: a narrower block is served, a wider block is refused, and a shape
disagreement is refused.

## The kernel change

`gemma4_attention_prefill_{bf16,f32}` gained a `keys` argument. The kernel had
used `tokens` for both the query count and the key count — correct for a square
prefill block, wrong for a decode step. `keys` defaults to `tokens`, so the dense
call sites are unchanged, and the shared-memory sizing, the mask row stride, and
all three key loops now use it.

`test_attention_prefill_serves_a_decode_step_over_a_kv_cache` covers `keys >
tokens` directly, with a cache **longer than the live context** so that a kernel
reading past the live keys attends over stale slots and fails rather than passing
by luck.

## The layer's cache contract

`Gemma4LayerKV(key_cache, value_cache, capacity, write_offset)`. When present,
the layer appends this block's rotated K and normalized V at `write_offset` and
attends over `write_offset + rows` cached positions; the mask is already
`(rows, write_offset + rows)`, so stale slots are masked rather than read.

The append is a plain device-to-device move, not a scatter: the cache is
`(capacity, num_kv_heads, head_dim)` and the block is `(rows, num_kv_heads,
head_dim)`, so position `p` of the block lands at `write_offset + p` of the cache
with no stride change.

The cache is a linear buffer, not a ring. Sliding-window layers get their bound
from the mask instead, which costs memory but keeps one cache layout. At 4096
context and 8 KV heads of width 128 that is about 8 MB per tensor, so a ring is
not worth the complexity yet.

## Validation

- `pytest tests/test_unit_gemma4_gpu_kernels.py` — **50 passed** (48 prior + 2 new,
  and one rewritten).
- `test_layer_incremental_decode_matches_a_dense_prefill` — prefill 6, decode 3,
  each decode row within 2% of the dense row. Fails if the append lands at the
  wrong offset, if attention uses the query count as the key count, or if a decode
  mask does not cover exactly the live context. It also asserts the cache holds
  both the prefilled and the decoded keys.
- Gemma 4 unit tier (GPU kernels, CPU reference, GGUF loader, materializer,
  tokenizer, streaming): **all passed**, exit 0.
- `ruff check` clean; `python3 audit/audit.py check` exit 0.

## A test bug worth recording

The first version of the decode test called `device.put(np.empty(...))` for the
output and then read the host array back. `put` copies *to* the device, so the
host array was never written and the assertion compared against uninitialized
memory — which showed up as a mix of plausible values and `1e30` garbage. The
working pattern is `device.out(shape, dtype)` then `device.get(ptr, shape, dtype)`.
The garbage-with-some-correct-values signature is the tell: a wrong kernel
produces a uniformly wrong result, uninitialized memory does not.
