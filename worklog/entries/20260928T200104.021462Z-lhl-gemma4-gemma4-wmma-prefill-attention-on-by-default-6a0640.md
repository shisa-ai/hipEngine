# Gemma 4 prefill: the WMMA attention variant is on, and 512 tokens now matches llama.cpp

## Summary

The BF16 WMMA prefill-attention candidate from `0bcf2dc0b` is now the
`production` execution profile's selection for Gemma 4's 25 sliding layers, and
`production` is the shipped default. Measured on the campaign's own ladder, both
arms, three samples per point:

| prompt | strict | production | gain | gap vs llama.cpp |
| ---: | ---: | ---: | ---: | ---: |
| 512 | 870.0 | **1012.8** | 1.16x | 1.16x -> **1.00x** |
| 1024 | 707.2 | 925.1 | 1.31x | 1.50x -> 1.14x |
| 2048 | 570.0 | 804.6 | 1.41x | 1.88x -> 1.33x |
| 4096 | 456.1 | **628.2** | 1.38x | 2.29x -> **1.66x** |

At 512 tokens the engine now matches the reference: 1012.8 against llama.cpp's
1012.98 tok/s. At 4096 the gap falls from 2.29x to 1.66x. The strict arm
reproduces the recorded baseline within 2 percent at every point, which is what
makes the two arms comparable.

All twelve greedy generations (four prompt lengths, three samples each, 128
tokens per sample) are **token-identical** between the arms.

The isolated kernel is 13.64x; the end-to-end gain is 1.38x at 4096. That
difference is the expected shape and not a shortfall: the sliding layers are
about 52 percent of attention FLOPs, attention was 61 percent of the step, and
the production path is chunked at 512 rows against a growing KV rather than the
bench's single 4096-row launch. `0.683 + 0.317/13.6 = 0.706`, i.e. 1.42x, which
is what was measured.

## Changes

- `hipengine/generation/gemma4_gguf_profiles.py` (new) -- registers a strict and
  a production `RuntimeProfilePlan` for `(gemma4_gguf, hip_gfx1151,
  gguf_q4_k_m)`. Production selects `gemma4_wmma_flash` for
  `(prefill_attention, sliding_head_dim_256)` with `gemma4_plain` as the strict
  fallback and the candidate's evidence artifact named; strict selects
  `gemma4_plain`. Registering both is what makes the shipped default
  `production`. The module also registers the two variants in the four-axis
  registry under both the `hip_gfx1100` key space and its `hip_gfx1151` alias,
  which `_verify_registered_variants` requires before it will accept the plan.
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention.py` -- adds
  `select_prefill_attention`, the capability match. It returns a
  `PrefillAttentionSelection` (variant, launcher, requested variant, reason) and
  falls back to the strict kernel on an unknown variant name or a geometry the
  candidate does not implement, naming what it wanted and what it got. Also adds
  the one-shot `HIPENGINE_GEMMA4_PREFILL_ATTENTION_LOG` diagnostic, because the
  profile selects a variant as a *request* and only the layer knows each layer's
  head geometry.
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_layer.py` -- the layer takes a
  requested variant name and resolves it against its own head geometry, so a
  layer the candidate does not implement keeps the strict kernel rather than
  raising. Resolving in the layer rather than at the call site is forced: the
  sliding layers are head_dim 256 and the full layers are head_dim 512, so one
  decision per model cannot be right for both.
- `hipengine/runtime/gemma4.py` -- `Gemma4Runner` carries the requested variant
  and passes it into the layer.
- `hipengine/generation/gemma4_gguf.py` -- the generator resolves the profile
  once, before the runner exists, and registers the plans at module import.
  `LLM` resolves a profile *before* it constructs a generator, so a plan
  registered any later is a plan the engine never sees.
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention_prefill_wmma.py` --
  `scratch` added to the launcher's signature. The layer passes one argument
  list, and the candidate's signature was missing it, so the two were not
  interchangeable as its own docstring claimed.
- `scripts/gemma4_campaign_bench.py` -- the resolved runtime profile is an
  object, not a name; the artifact now records the profile name, its manifest
  hash and whether it fell back, instead of failing to serialize.
- `tests/test_unit_gemma4_prefill_attention_selection.py` (new) -- 19 cases, no
  GPU. Capability on both sides of the boundary and away from it, unknown
  variant, profile and env selection, an unregistered backend, registry
  membership, and that the two launchers accept the same call-site arguments.
- `docs/ENVS.md`, `docs/REFACTOR.md` -- the diagnostic's entry, and the ledger
  entry naming the outstanding teacher-forced gate.

### What the selection is not

It is not an identity check. The match is on the geometry the variant declares
it implements (`head_dim == 256` and a GQA ratio of 2), and an unfamiliar
artifact that fits the declaration runs. The `hip_gfx1100` backend gets no plan
and therefore keeps the strict kernel; that is a backend with no registered
plan, which is the migration path the profile system already defines, and not a
statement about the kernel's capability.

## Validation

### The path actually ran

`HIPENGINE_GEMMA4_PREFILL_ATTENTION_LOG=1` on a real `LLM.generate()` prefill,
both arms:

```
production:
  prefill_attention=gemma4_wmma_flash requested=gemma4_wmma_flash (capability match) 16q/8kv head_dim=256
  prefill_attention=gemma4_plain requested=gemma4_wmma_flash (capability miss: gemma4_wmma_flash implements head_dim 256 with GQA ratio 2, got head_dim 512 with 16q/2kv) 16q/2kv head_dim=512
strict:
  prefill_attention=gemma4_plain requested=gemma4_plain (strict) 16q/8kv head_dim=256
  prefill_attention=gemma4_plain requested=gemma4_plain (strict) 16q/2kv head_dim=512
```

So the 25 sliding layers take the candidate and the 5 full layers take the
strict kernel, in the arm where that is the intent and not in the arm where it
is not. Every ladder artifact records its own resolved profile and manifest
sha256 (`59bf84fc...` for production, `8114b5b0...` for strict) with
`fell_back_to_strict: false`.

### What is NOT verified

- **The production numerical gate in `docs/EXECUTION-PROFILES.md` §6 has not
  been run.** Twelve token-identical greedy rows at four prompt lengths are a
  screen, not that gate: it wants full-vocabulary teacher-forced rows with a
  KL envelope (mean <= 1e-3, p95 <= 5e-3, p99 <= 2e-2, max <= 5e-2, top-1 >=
  99% overall and >= 97% per scope). The route is a T2 association candidate and
  the gate is what its promotion evidence is made of. Recorded in
  `docs/REFACTOR.md`.
- Token identity is over 128-token greedy rows on one prompt corpus, three
  samples per length. It is not a distributional statement.
- No repeatability study across GPU clock states, thermal states or reboots.
  Each ladder point is three samples after one warmup.
- The head_dim-512 full layers are still the strict kernel and are still 5 of 30
  layers at 427.9 GFLOP/s. They are the other half of the attention FLOPs and
  the obvious next unit; at 4096 tokens the remaining 1.66x gap is mostly them.
