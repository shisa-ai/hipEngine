# prefill attention is 16.6x off the gfx1100 record and the hardware ratio is 2.4x

## Summary

Fresh measurement on this host: the 30 attention layers cost **2207.2 ms** at 2048
tokens, against the campaign's gfx1100 record of **133.02 ms** for the same route at
the same length. That is **16.59x**, while the two parts differ by about **2.4x** in
CU count (96 vs ~40) and **3.75x** in bandwidth (~960 vs ~256 GB/s).

So a factor of roughly **4.4x to 6.9x is unexplained by the hardware**, and this is
the prefill gap the objective describes. Reproducing it here confirms it is current
and not a stale record.

## Measured

```
tokens=2048 iters=5
case                              ms/launch    GFLOP/s  all layers
swa  256d 16q/8kv window=1024         62.23      414.2    1555.9 ms
swa  256d 16q/8kv window=0            77.48      443.7    1937.0 ms   (probe, not in the total)
full 512d 16q/2kv window=0           130.27      527.8     651.4 ms

the model's 30 attention layers: 2207.2 ms
```

The probe's own cross-check is that the in-situ route ablation measured 2295 ms for
the same route, so the isolated number is within 4% of the in-situ one and is not
an artifact of isolation.

The kernel runs at **414 to 528 GFLOP/s**. The gfx1100 record implies roughly
**6.9 TFLOP/s** for the same work (414.2 GFLOP/s scaled by 2207.2/133.02), which is
11% of gfx1100's fp32 peak. Both parts are far below their arithmetic peak, and the
ratio between them is much larger than the hardware ratio.

## Hypothesis, stated as a hypothesis

The prefill kernel's grid is `tokens * num_heads` and each block reads **all
`keys` K rows** for its own query token. K is therefore re-read once per query
token, so the kernel issues `tokens x keys x num_heads x head_dim` K reads where
`keys x num_kv_heads x head_dim` would do -- a factor of `tokens x
(num_heads/num_kv_heads)` of redundant traffic, 2048 x 2 = 4096 at this geometry
for the swa case.

This is the same structural issue as the decode starvation measured in
`20260928T065154`: not enough reuse, and therefore not enough effective work per
byte. A token-tiled (flash-style) kernel that holds a K tile in LDS and uses it for
every query row in the tile would remove it.

**I have not tested this.** The arithmetic says the traffic is large, but a 2207 ms
measurement against a 1032 GB estimate would be 468 GB/s, above this part's
~256 GB/s DRAM peak, so L2 is catching a substantial fraction and the simple
traffic model over-predicts. The hypothesis needs a `--mask zero` style ablation
that removes the K/V loads while keeping the tile loop, exactly as the decode bench
already does, before it should be believed.
