# The decode GEMV is wired, and only a fusion path still keys the legacy variant
## Summary
Following the previous iteration's lead that a kernel named for prefill looked
reachable during decode, this traces the Q8_0 decode GEMV through registration,
selection and fusion. The lead resolves into a naming problem rather than a
dispatch defect, plus one genuine loose end.
## 1. The prefill-named kernel is the decode kernel
`hipengine/kernels/hip_gfx1100/quant/gguf_q8_0_pack8_gemv.py` documents its own
subject as:
> the decode-shaped ``gguf_k_pack8_prefill_out_kernel<unsigned short,
> unsigned short, 8>`` family at ``rows == 1`` shapes

So `gguf_k_pack8_prefill_out_kernel<...,8>` **is** the decode-shaped kernel at
`rows == 1`. The name is misleading, not the dispatch. Seeing it in a decode
window is therefore not evidence of prefill work leaking into decode, and this
part of the earlier lead is dead.
This does **not** weaken the contamination finding. The two `*_prefill_wmma*`
kernels in that window remain unreachable at `rows == 1` because of the
`rows > 1` guards, so the window was still contaminated. It only means this
particular kernel was not part of the evidence for it.
## 2. The dedicated decode GEMV is wired
The same docstring says the `gguf_q8_0_pack8_gemv_decode_*` family is a drop-in
replacement for that kernel "once task #25 wires it". Task #25 is done:
`hipengine/runtime/gguf_linear.py` builds
`pack8_gemv_decode_{activation_dtype}_{output_dtype}_out` at lines **5295** and
**7095**, and the module comment at line 164 states the intent directly — token
projections route through the new `pack8_gemv_decode_*` kernels "instead of the
legacy `pack8_gemv_*` decoders". The four variants are registered at
`gguf_q8_0_pack8_gemv.py:370-401` under
`("hip_gfx1100", "linear", "gguf_q8_0", "pack8_gemv_decode_bf16_bf16_out")` and
siblings.
## 3. The one loose end
Line **7129** of `gguf_linear.py` still keys a **fusion** decision on the legacy
variant:
```python
q8_decode = KernelKey(backend, "linear", "gguf_q8_0", "pack8_gemv_bf16_bf16_out")
if rows == 1 and out_features_b == out_features and dispatch_a.key == q8_decode and dispatch_b.key == q8_decode:
    return "q8_raw_dual"
```
This is a fusion-selection function, not the main projection path, so it does not
mean the legacy decoder runs. It does mean the `q8_raw_dual` fused gate+up path
can only fire if the dispatches happen to carry the legacy key, which after the
line-164 migration they should not. The plausible consequence is that a fused
Q8_0 decode path is **unreachable**, so the decode takes two separate GEMVs where
one fused launch exists.
That is a **hypothesis about reachability, not a measurement**. It has not been
confirmed by observing which variant actually runs, and no timing was taken.
