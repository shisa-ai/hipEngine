# Gemma 4 decode attention pass 3: prefetched V loads and geometry-selected 2-wide loads (bit-exact)

## Summary

Iteration 22 closed with a timing-only ablation that showed pass 3 was 57-71% of
the key-class decode attention kernel and was latency-bound rather than
bandwidth-bound: it moved 16.78 MB unique at full/1024 in 492 us (34 GB/s) while
the same loop with the V loads removed moved 100.66 MB issued in 204 us
(493 GB/s).

The cause was the `weight == 0` skip that the block kernel uses: it stops the
compiler from hoisting the per-key 2-byte V loads, so each lane's walk of all
`keys` serialised at memory latency. This iteration issues those loads
`kPrefetch` keys ahead of the accumulation that consumes them, and - when the row
is wide enough to keep every lane busy - loads two adjacent dimensions per load.

**Bit-exact, and pass 3 is now roughly half its former cost**: sliding 427.9 ->
318.9 us, full 696.0 -> 339.8 us at keys=1024, full 1174 -> 509.5 us at
keys=2048. Campaign metric **41.9049 tok/s from 33.0213 (+26.9%)**, **+160% over
the 16.0931 baseline**.

## What changed

`gemma4_decode_pass3<kDimsPerLane, kPrefetch, scalar_t>` is factored out of
`gemma4_attention_decode_class_kernel`:

- **Pipeline.** `pipe[kPrefetch]` holds the V values of keys `j .. j + kPrefetch`;
  each step consumes `pipe[0]`, shifts, and loads key `j + kPrefetch`. The
  rotation unrolls to register renaming. Out-of-range keys load a zero pair.
- **Load width.** With `kDimsPerLane == 2` lane L owns the dimensions 2L and 2L+1
  and issues one `gemma4_pair2<scalar_t>` load (4 bytes for 16-bit KV, 8 for
  32-bit). The `alignas(2 * sizeof(scalar_t))` on that type is what makes the
  compiler emit a single vector load; it holds because `head_dim` is even for
  every geometry the launcher routes here and the KV base is a device allocation.
- **Selection.** `head_dim >= 2 * threads` -> two dimensions per lane, else one.
  The sliding geometry (256 = threads) keeps the scalar load because a
  two-dimension mapping there idles half the block: 336.9 us two-wide against
  318.9 us scalar, while at `head_dim` 512 it is 326-343 us against 413 us.

Only *when* a load is issued and which lane owns which dimension changed. The
per-dimension ascending-j accumulation order and the `weight == 0` skip are
untouched, so the kernel remains bit-exact against the block kernel.
