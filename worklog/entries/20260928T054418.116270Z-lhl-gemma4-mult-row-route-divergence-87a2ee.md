# a two-row block is not two one-row forwards and the layers are where it diverges

## Summary

The previous entry planned an MTP draft/verify loop on the premise that a
multi-row forward is the same computation as several one-row forwards, because
the attention mask is built from absolute positions. **That premise is false,
and the test written to assert it is what found out.** A one-row block is
bit-exact against a one-row forward, so the new `logits_rows` plumbing is
correct. Two rows are not:

| k | hidden state bit-equal | logits max abs diff | top-1 agrees |
| --- | --- | --- | --- |
| 1 | **[True]** | 0.000000 | — |
| 2 | [False, False] | 1.623520 | [True, True] |
| 3 | [False, False, False] | 2.507651 | [True, True, True] |
| 5 | [False, False, False, False] | 2.507651 | [True, True, True, True] |

The comparison is against the one-row path the decoder already uses, on the
synthetic fixture artifact.

## What the pattern says

Two facts pin the mechanism:

1. **The divergence is in the hidden state after the layers**, not in the final
   norm or head, because the hidden rows are already unequal at every position.
   `logits_rows` only changes the norm and the projection, so it cannot be the
   cause -- and the one-row control being bit-exact confirms that it is not.
2. **Each row's difference is the same whatever the block width is.** Row 0's
   divergence is identical at k=2, k=3 and k=5; so is row 1's. A row therefore
   does not depend on how many rows follow it. The difference is between a
   one-row block and a two-or-wider block.

That is a route selected by block width, not a per-row reduction-order effect.
It is the same class as the recorded `2f1e352a` finding, and the same defect
`test_incremental_decode_matches_a_dense_prefill` fails on. Forcing the exact
MoE gate/up route with `HIPENGINE_GEMMA4_MOE_GATE_UP_MMQ=0` does **not** make it
pass, so that flag is not the whole of it; the census's
`gemma4_project_experts_grouped_row4` is another row-count-named route worth
suspecting next, and `_sliding_read_range` derives a per-block window from
`rows`.

**This predates the change in this unit.** A three-token prefill already
disagreed with three single-token forwards before `logits_rows` existed.

## Consequence for the MTP plan

The verify pass is an **arithmetic change**, not a free one, so promoting it to
the default path needs the `docs/EXECUTION-PROFILES.md` gate rather than the
"it is the same computation" argument the previous entry made. Greedy
acceptance reads the target's argmax at each drafted position and the top-1
token agrees at every position on this fixture, which is why this is a promotion
question and not an immediate correctness failure -- but one fixture is not that
gate.

The performance case is untouched. Per-token cost is still 45.0 ms at one row
against 24.5 at four, so a four-row verify is still worth roughly 1.8x on
decode. What changes is what has to happen before it can be the default.

## What this reframes

Fixing the block-width route is now the higher-value unit, ahead of the draft
loop, for two reasons: a three-token prefill that disagrees with three decode
steps is a **correctness defect** independent of MTP, and it is what stands
between a bit-exact speculative verify and the default path. The draft loop
wires onto whichever arithmetic the runner has; making that arithmetic
row-count-independent is the part that cannot be worked around.

## Changes

`hipengine/runtime/gemma4.py`:

- `Gemma4Runner.max_logits_rows` (default 1) bounds the projection scratch, so
  a 512-wide prefill does not size its logits buffer for the whole block while a
  verify pass can still ask for the trailing rows.
- `forward(..., logits_rows=k)` and `_forward_block(..., logits_rows=k)` return
  the last `k` rows' logits as a `(k, vocab)` array. Only the final block can
  carry them; an earlier block's logits are overwritten before they are read.
- `rewind(position)` gives back a rejected tail by resetting the position and
  each layer's write offset without clearing K/V, since the next forward
  overwrites a position before reading it. `_last_rows` deliberately survives so
  a draft can still be taken from the row that produced an accepted token.

`tests/test_gpu_gemma4_runner_verify_rows.py` is new. It asserts the one-row
control bit-exactly, the trailing-rows shape, the rewind round-trip, the rewind
bounds, and the `max_logits_rows` bound; it marks the two block-width-dependent
value comparisons `xfail(strict=False)` with the mechanism named, so they turn
green if the route is fixed and stay visible until then.

## Validation

- `python3 -m pytest tests/test_gpu_gemma4_runner_verify_rows.py` on the 8060S
  (gfx1151), exit 0: four tests pass and two xfail.
- The k-sweep table comes from a standalone script driving the fixture runner at
  k=1, 2, 3, 5, comparing hidden rows through `hidden_state` and logits against
  `np.stack` of the one-row forwards.
- `HIPENGINE_GEMMA4_MOE_GATE_UP_MMQ=0` was run against the bit-equality test and
  did not change its outcome, which is why the flag is reported as insufficient
  rather than as the cause.
- The hidden-state ULP counts the first version of the script printed are not
  quoted here: they compared BF16 bit patterns as int32, so a near-zero value
  produced a meaningless count. The bit-equal column is the sound one.
