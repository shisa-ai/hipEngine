# Promote the iu8 risk multiplier to 1.0 on measured evidence, replacing refuted grounds

## Summary

`HIPENGINE_QWEN4_EXP_Q4_IU8_RISK_MULT` is now bound to **1.0** in the production
profile (`hipengine/generation/qwen4_exp_profiles.py`), replacing the previous
`"4.0"` pin. The pin's two recorded grounds are both refuted by measurement, and the
benefit is now measured at the kernel level rather than inferred.

The previous comment justified the pin with (a) "the wall benefit does not survive the
canonical protocol" and (b) "the repair kernel launches over `risk_capacity` regardless
of `risk_count`... the real lever is the pass's launch geometry, not its threshold".
**(a) is void because the binder writes this key unconditionally, so the canonical
harness - which reads this profile - could never move the multiplier and every
canonical "flat" reading compared 4.0 against 4.0.** **(b) is false**: the kernel
launches 1024 blocks with a grid-stride loop bounded by `min(risk_count, max_risks)`.

The measurement that settles it: applied through the post-binder override, the repair
queue falls **3.403x** (70,167,220 -> 20,621,412 slots) and the repair kernel's own
traced time falls **4808.346 -> 3386.063 ms**, a **1318.0 ms** window reduction on
`code-p4096` (64981.3 -> 63663.3 ms of kernel time) - **2.03%**.

## Changes

- `hipengine/generation/qwen4_exp_profiles.py`: the binding is `"1.0"`. The comment
  block is rewritten to carry the corrected evidence, the task-gate review, and the
  rollback instruction, rather than the refuted reasoning.
- No kernel change. No arithmetic change. The strict fallback is registered and
  untouched.

## Validation

### Arm identity, proven rather than assumed

The corrected A/B was run through `scripts/qwen4exp_profile_gap.py --override`, which
applies after the binder. Each run records both environments:

| arm | `bound_route_env` | `effective_route_env` | repair slots | calls | rate |
| --- | --- | --- | ---: | ---: | ---: |
| 4.0 | 4.0 | 4.0 | 70167220 | 1504 | 0.80574% |
| 1.0 | **4.0** | **1.0** | **20621412** | 1504 | **0.23886%** |

`over_capacity_calls` is 0 in both arms. The queue ratio is **3.403x**, matching the
3.40x the gate harness recorded (0.7119% -> 0.2092%).

### The kernel trace, both arms genuinely different

| | MULT 4.0 | MULT 1.0 | delta |
| --- | ---: | ---: | ---: |
| repair total | 4808.346 ms | 3386.063 ms | **-1422.283 ms** |
| risk owner total | 21186.563 ms | 21181.639 ms | -4.924 ms |
| window (all kernels) | 64981.3 ms | 63663.3 ms | **-1318.0 ms** |
| launches | 85696 | 85696 | 0 |

The repair falls 29.6% while the queue falls 3.403x, so the pass is **not** purely
proportional. Fitting `time = F + k * queue` over the two arms:

- `k` = 2.871e-5 ms per slot
- `F` = **2794.1 ms** fixed - **58.1% of the repair at 4.0, 4.30% of the window**
- proportional part: 2014.3 ms at 4.0, 592.0 ms at 1.0

So there is a real fixed component worth attacking separately, **and** the threshold is
a real lever. The previous comment's "not its threshold" was wrong.

Separately, and not part of this promotion: the **2794.1 ms fixed component** is a
correctly-grounded launch-geometry question for the first time. It is 4.30% of the
prefill window and is independent of the threshold, so it survives this change
unchanged. It should be attacked on its own terms - the repair kernels' per-launch
cost - and not by re-deriving the retracted fixed-grid mechanism.

## Limits

- One host (gfx1151 APU, **not** the gfx1100/W7900 default hardware), one model, one
  quant, one case (`code-p4096`), one execution profile for the kernel-trace figures.
  The numerical and task gates cover their own wider suites.
- The profiled runs are serialized by rocprofv3, so absolute durations are not
  wall-clock times; the two-arm comparison is valid because both arms are profiled
  identically and their effective environments are recorded.
- The 2.03% figure is kernel time on one case, not a canonical-protocol claim. The
  canonical run is the next step and has not been done.
- `F` and `k` are fitted from two points, so they describe the observed pair and are
  not a validated model of the pass.
