# Measure Qwen3.8 27B XTX server context capacity

## Summary

Measured the real OpenAI server path for `/models/gguf/Qwen3.8-27B-Q4_K_M.gguf` on the 24-GiB RX 7900 XTX. The highest validated context setting is **24,576 tokens** for one active request, but its near-limit request leaves only **0.494 GiB** free. The production-safe recommendation is therefore **16,384 tokens**, which leaves **1.519 GiB** at the measured near-limit peak. A clean 32,768-token server starts but its real near-limit request OOMs, so startup readiness alone is not a capacity gate.

## Changes

- Made no runtime or policy changes; this was a live capacity diagnostic on clean commit `852d47a96`.
- Used the supported default BF16 KV route, MTP off, `--max-active-requests 1`, normal startup warmup/chat smoke/scratch probe, and a 1-GiB startup free-memory guard.
- Started each decisive 16K/24K/32K server from the clean XTX baseline, then submitted one non-streaming `/v1/completions` request with `max_tokens=1` and a near-limit raw-token prompt. Repeated token 9707 was used only to fix the memory shape; no quality or throughput claim is made from these prompts.
- Common launch shape: `HIP_VISIBLE_DEVICES=1 HIPENGINE_HIP_ARCH=gfx1100 GPU_MAX_HW_QUEUES=1 PYTHONPATH=. .venv/bin/hipengine serve --model /models/gguf/Qwen3.8-27B-Q4_K_M.gguf --backend hip_gfx1100 --quant gguf_q4_k_m --max-context-tokens <N> --max-active-requests 1 --startup-min-free-mib 1024 --port 8018`.

## Validation

- Hardware: AMD Radeon RX 7900 XTX, gfx1100, 25,753,026,560 B / 23.984 GiB VRAM. The model is the structurally matched 17,106,775,008-byte Qwen3.8 file already fingerprinted in `benchmarks/results/2026-08-14-gfx1151-qwen36-qwen38-27b-speed-equivalence-diagnostic.json`.
- **16,384 configured:** 16,382 prompt tokens + one generated token + one reserved context slot returned HTTP 200 in 31.158 s. Peak whole-device VRAM was 24,121,712,640 B / **22.465 GiB**, leaving **1.519 GiB**; `/ready` remained true and the 1-GiB KV pool returned fully free.
- **24,576 configured:** 24,574 + 1 + 1 returned HTTP 200 in 50.063 s. Peak was 25,222,713,344 B / **23.490 GiB**, leaving only **0.494 GiB**; `/ready` remained true and the 1.5-GiB KV pool returned fully free.
- **32,768 configured:** startup passed with 2.236 GiB free, but 32,766 + 1 + 1 failed after 60.012 s with `HIP error 2: out of memory`; sampled peak reached **23.963 GiB**.
- Diagnostic 64K and 96K requests under a nominal 128K server also failed. The 64K attempt grew the lazy KV pool from 2 GiB directly to 6 GiB and reached **23.950 GiB** before OOM. A nominal 128K server itself reported ready, demonstrating that the current c1 startup scratch probe does not validate real long-row request headroom.
- Raw response/readiness captures: `/tmp/qwen38-xtx-{16k,24k,32k}-completion.json` and `/tmp/qwen38-xtx-{16k,24k}-ready-after.json`; background logs were `bg-813` through `bg-820`. These timing values are operational diagnostics, not retained performance rows.

## Next

- Use `--max-context-tokens 16384 --max-active-requests 1` for reliable serving today; use 24,576 only when the approximately 0.5-GiB measured margin is acceptable.
- Qualify Qwen3.8 independently on gfx1100 before transferring the model-keyed Qwen3.6 memory policies. Separately make the c1 startup scratch probe exercise long-row request ownership and revisit the 2-to-6-GiB lazy KV growth step so readiness cannot advertise contexts that real requests cannot execute.
