# Surya multi-prompt generate isolation test — catches the decode_step KV leak

## Summary

`TextGenerator.generate` loops `request.prompts` on one runner, so prompts run
back-to-back over shared KV slots and recurrent state. Nothing in the suite
passed more than one prompt: `tests/test_surya_gpu.py` and
`tests/test_surya_generation_contract.py` both use a single-element list, and
the existing isolation test is multimodal -> multimodal only. That is the same
blind spot that hid the `decode_step` off-by-one (91bd23576), so the batch
path was untested for exactly the failure mode that was just fixed.

Added `test_gpu_generator_multi_prompt_isolation`: a lone prompt, then the same
prompt as the head of a three-prompt request, then the request reversed. The
first prompt's output must not change when later prompts join, and reversing
the request must reverse the outputs rather than change them.

## Changes

- `tests/test_surya_gpu.py`: new `test_gpu_generator_multi_prompt_isolation`.
- `docs/MODEL-SURYA.md`: status row for the multi-prompt isolation gate.

## Getting the test to actually catch the bug

The first version used three similarly sized short prompts. It passed with the
`decode_step` off-by-one reintroduced, so it was a false negative. Measured
against the buggy build:

| Prompt set | order-invariant under the bug |
| --- | --- |
| 3 similar short prompts | pass (false negative) |
| long, short | pass (false negative) |
| short, long | pass (false negative) |
| long, short, short | **fail** |

The leak reads KV past the current request's own slots, so it only corrupts a
*short* prompt that follows a *longer* one, and only once a third prompt
follows. The committed test uses a ~4x repeated long prompt followed by
`"Read."` and `"Transcribe this page."`.

This is consistent with the note in 91bd23576 that the bug's manifestation is
input-dependent (the small page gave a false negative there too).

## Validation

- GREEN with the current runtime; RED with the `decode_step` off-by-one
  reintroduced: `AssertionError: generate() is order-dependent: a prompt's
  output depends on which prompts ran before it in the same request`, failing
  at index 1 (the short prompt after the long one). Runtime restored with no
  diff.
- Not vacuous: the three prompts produce three distinct outputs, so the
  order-reversal comparison has discriminating power.
- Full Surya bundle on gfx1151: 92 passed.
