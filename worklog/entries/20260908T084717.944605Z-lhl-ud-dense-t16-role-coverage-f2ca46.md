# Dense T16 role coverage for the UD files

## Summary

Item 2 of `docs/UD-OPTIMIZED-ROUTE-PLAN.md`, continuing from UD-U3
(`d8f5e951c`). Three dense T16 role/shape allowlists were written against the
plain Qwen3.8-27B `Q4_K_S` file, which carries no tensor at the roles the UD
files use, so those UD tensors fell to raw/pack8 GEMV layouts even after the
per-tensor repack fix. Widening them moves another 2.75 GB (K_M) onto the
already-qualified T16 families.

Optimized weight-byte share, K_M: 0.0% (before UD-U3) -> 44.2% (UD-U3) ->
**61.3%**. K_S: 0.0% -> 34.4% -> **44.4%**. Prefill 30.38 -> **41.54 tok/s**
(+36.7%) on the published sweep protocol.

## Changes

`hipengine/loading/qwen35_gguf_materialize.py`:

- `_is_dense_h5120_q5_t16_tensor` becomes a table,
  `_DENSE_H5120_Q5_T16_ROLE_SHAPES`, growing from 3 roles (`ffn_down`,
  `attn_qkv`, `attn_v`) to the full 9-role dense set, which is exactly
  `_DENSE_Q4_T16_SIDECAR_POLICY`'s geometry. Moves 2.32 GB (K_M) / 1.19 GB
  (K_S).
- `_is_wide_rank2_q6_t16_tensor` gains `ffn_up`, `attn_output`, `ssm_out`
  (all >= 5120 wide, so they keep the wide-path measurement the predicate
  encodes); `_is_narrow_q6_attn_v_tensor` gains `attn_k`, identical
  (1024, 5120) geometry to `attn_v`. Moves 0.34 / 0.12 GB.
- `_DENSE_Q4_T16_SIDECAR_POLICY` gains `ssm_out` (5120, 6144), the same
  geometry as `attn_output`. Moves 0.09 / 0.19 GB.

**Why widening is sound.** Every predicate reads "select only the measured …":
measurement scope, not kernel capability. The Q5 scope's own worklog
(`20260816T115357…-qwen38-gfx1151-q4-k-s`) says it admitted three roles because
"Q4_K_M has no Q5 tensors at these shapes". Before changing anything, every
remaining raw Q5/Q6/Q3 tensor was checked through the planner's own
`_planned_t16_nbytes` and all are T16-alignable, and every newly admitted
(role, shape) pair was already admitted for Q4_K on the identical geometry.

## Validation

- RED-first `tests/test_gguf_ud_dense_t16_roles.py` (38 cases): per-role
  coverage for Q5_K/Q6_K/Q4_K on both UD files, non-regression for the three
  originally-admitted Q5 roles, an assertion that no rank-2 Q5_K layer tensor
  is left raw, and a **plain-`Q4_K_S` no-op control**. Includes a guard test
  that the role filters actually match tensors - the first draft silently
  skipped 21 of 23 cases because layer slot keys are bare names, not
  dotted paths.
- 162 planning/admission/policy/parity tests green; `test_gguf_e2e_acceptance`,
  `test_gguf_ud_km`, `test_gguf_ud_ks`, `test_qwen35_gguf_consumer_surface_parity`,
  `test_gguf_ud_dense` green.
- Perf, published sweep protocol, **both arms measured in this session** by
  swapping only `qwen35_gguf_materialize.py` between HEAD and the candidate:
  prefill 30.38 -> 41.54 tok/s (+36.7%), decode 7.28 -> 7.62 (+4.7%). Run
  spread was 30.1-30.4 and 40.8-41.5, so the delta is far outside noise. The
  before arm reproduces item 1's recorded 29.93 on the same host and command.
- Resident weights: planner K_M 16.284 -> 16.309 GB (+25.6 MB, +0.16%), K_S
  15.143 -> 15.111 GB (-32.4 MB). Runtime weight-buffer delta matches the
  planner exactly. Unlike item 1, this one is memory-neutral rather than a
  saving.

**The lost position is a teacher near-tie.** Position 26 (prompt 2, step 8):
the teacher itself splits p(1445)=0.475540 against p(1005)=0.473468, a gap of
2.07e-03. The prior arm's margin there was 4.9e-03 and fell on the teacher's
side; the new arm's is 3.03e-02 on the other. At a 0.2% teacher gap which side
an arm lands on is close to arbitrary, so this is not read as a quality
regression - but UD-U3's "best top-1 measured" distinction is given up, and
that is recorded rather than glossed. mean/p95/p99 remain above the strict
thresholds, the pre-existing campaign state.

## Not a routing gap after all

`GGUF_DENSE_Q4_QMICRO_T16_GATE_UP_FILE_TYPES` excludes `MOSTLY_Q4_K_M`, which
the plan listed as an item-2 candidate. Checked: K_M's 28 Q4_K
`ffn_gate`/`ffn_up` tensors already resolve to `gguf_q4_k_t16_v1`. Adding the
stamp would swap one optimized variant for another, so it is a tuning question
needing its own measurement, not a fallback-to-fast move.
