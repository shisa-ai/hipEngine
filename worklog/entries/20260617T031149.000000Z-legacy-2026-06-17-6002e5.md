# 2026-06-17

## Summary

- Historical pre-Worklog2 journal entry, ported verbatim from `WORKLOG-LEGACY.md` (source lines 95751-95760).
- First appended to the journal in commit `e089d1c2` (subject: perf: GGUF MoE fused activate+down and drop Q8_0 T16 repack).

## Changes

- **G-P4 memory bloat fix.** Found that `Qwen35GGUFResidentSession` allocated its full-sequence hidden state buffers (`_prefill_hidden_a` and `b`) to `max_positions` (131,072) and `_GGUFFullAttentionPrefillScratch` allocated its block table to `capacity` (256 MB) when `use_expert_sidecar=False` in layer-outer chunk-inner mode. Fixed this by dynamically sizing allocations based on `chunk_size` when sidecars are not used and rewritten `_run_bulk_prefill_and_sample` to use a chunk-outer layer-inner loop. This saved ~1.25 GiB memory, allowing `128K/128` context to run comfortably on GPU1 without forcing the 768-token manual limit. Peak memory for `128K/128` on `Q4_K_S` dropped from OOM (>25 GiB) / 23.31 GiB (at 768 chunk) to 22.746 GiB with standard 4096-query chunking. `128K/128` prefill=678.74 tok/s, decode=67.08 tok/s, token=220.
- **G-D3 fused activate+down for selected experts.** Fused SiLU and the second/down GEMV for MoE selected experts into `qk_t16_selected_silu_x_direct_gemv_kernel`. Tested on `Q4_K_M`. Decode throughput slightly dropped or stayed neutral (e.g. 114.46 tok/s vs 114.60 baseline). The launch overhead reduction did not overcome the larger register/math pressure of fusing activation with GEMV in this case.
- Re-checked `qk_t16_selected_silu_x_direct_gemv_kernel`. The bug in stable generation was an indexing error for the `gate` buffer layout in the kernel. `gate_row` array indexing needed to offset to the correct part of the dual buffer (`gate_up + x_row_idx * in_features`). Tested against `Q4_K_M` and output is now stable (`stable=True`), but throughput is still roughly flat (114.47 vs 114.60 baseline). Retaining this fused kernel as it reduces Python-level overhead slightly but does not significantly improve math-bounded W4 T16 selected decode performance.
- Dropped T16 decode-repack for Q8_0 tensors. As noted in the GGUF optimization plan, Q8_0 tensors at T16 layout didn't provide enough decode speedup vs raw to justify the +0.5-1.0 GiB cost of duplicating/expanding them. Reverting them to raw layout saved ~0.55 GiB, taking tracked peak memory for the model from 23.05 GiB down to 22.48 GiB without losing much throughput.
- **G-D2 Pack8 layout optimization.** Dropping `LAYOUT_Q4_K_PACK8` layout materialization and using `LAYOUT_RAW_GGUF` for dense Q4_K tensors reduced memory by ~1.15 GiB, taking peak on 128K/128 down from 23.31 GiB (with 768-token chunk) to 22.75 GiB. This tradeoff between memory and speed (small negative delta on decode, 114.60 -> 114.42 tok/s) unlocks future batch scaling while comfortably fitting inside 24GiB limit.
- **G-H1 C-dispatch for GGUF MoE.** Invalidated. Analysis showed that GGUF uses HIP graph capture for decode (if enabled, as it is by default), so Python dispatch overhead is already bypassed entirely. This also applied to other optimizations involving C-dispatch, confirming that the current logic is optimal without relying on `moe_c1_dispatch` which was designed for PARO where graph capture is not always available.
- **G-H2 Fuse RMSNorm+rotate.** Invalidated. GGUF doesn't use AWQ input-rotation; this optimization is specific to PARO's w4a16 layout. The current GGUF architecture uses rotary position embeddings (`gguf_qwen35_head_rmsnorm_partial_rotary_positions_f32_weight`) applied directly to the query/key outputs AFTER the linear layer, making this specific fusion inapplicable to GGUF.
