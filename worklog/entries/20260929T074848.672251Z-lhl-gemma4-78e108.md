# Gemma 4: the teacher-forced gate cannot see MoE prefill-route changes

## Summary

Iteration 40 left `p3-gate-and-re-measure` as a failed check: the Q8_0 down
registration had landed (`7a91b5735`) with no gate over it. This entry closes
that check with a number, and the number turns out to be a finding about the
gate rather than about the change.

**The run.** `gate --baseline teacher-forced-prefilled-p4096-c3ea386af.npz
--prompt 5120 --prefill 4096 --context 8192` on GPU[0] (rocm-smi: AMD Radeon
Pro W7900, the lane every `-w7900` artifact including the baseline was frozen
on), 44 s:

| metric | HEAD (`d0f5b1ff6`) | HEAD + down fix |
| --- | ---: | ---: |
| kl_max | 0.2177167513641361 | **0.2177167513641361** |
| kl_mean | 3.71e-4 | 3.707e-4 |
| kl_p95 | 5.28e-6 | 5.279e-6 |
| kl_p99 | 1.12e-4 | 1.123e-4 |
| top1_rate | 1.0, 0 flips | 1.0, 0 flips |
| rows | 1023 | 1023 |

`kl_max` and `kl_worst_rows` (894 / 327 / 254) are **exactly equal**, to the
last float64 digit. I did not accept that as "the fix is neutral" — bit-identity
between a GEMV path and an f16-WMMA path is not plausible, so it had to mean
either the path never ran or the gate cannot see it. Both were checked.

**The fix is live.** A dispatch probe wrapping `gemma4_experts_forward_bf16`,
`_build_wmma_tile_plan` and `gemma4_project_experts_wmma` at a production-length
prompt records `block rows [1, 225, 512]`, `lanes [8, 1800, 4096]` against the
threshold `16 * 128 = 2048`, and **`plan calls 30 | wmma calls 30`** — one per
MoE layer on the qualifying block, layer 29 included. Before the registration
the same probe measured `plan calls 0 | wmma calls 0`, and the resolve probe
raised `MissingKernelError`. At a short prompt (153-row block, lanes 1224) it
correctly declines, so the condition behaves on both sides of the threshold.

**The gate cannot see it, for two independent reasons.**

1. The scored rows are decode. `scored_key_range` is 4097-5119, every row is a
   single-token forward, so `lanes = 1 * 8 = 8` — far below 2048 — and layer
   29's down takes the same fallback HEAD takes. Prefill is cache-only and is
   never scored (`capture_chain` discards the prefill return value).
2. Layer 29 is terminal. Its down output feeds only the final norm and the
   lm_head, so nothing it does in prefill can reach the KV cache that the
   scored decode rows read.

So a change that only engages at `lanes >= 2048` in prefill, on the last
layer, is invisible to this evaluator by construction. The gate is not wrong to
return what it returned; it simply has no line of sight to this change. Its
correctness evidence is the kernel's own NumPy-dequant reference test
(`tests/test_gpu_qwen4exp_q8_0_grouped_wmma_down.py`, 4 passed with
`test_gpu_qwen4_exp_q5_1_selected.py`) plus the 636-test unit bundle.

**The consequence for the campaign is the durable part.** Any MoE prefill-route
change — this one, and the gate_up half of P3 when it lands — cannot be
qualified or rejected by the teacher-forced gate as it is currently built,
because it scores decode only. That is a gap in the gate, and recording a pass
here would have been a proxy signal masquerading as coverage. It is written
into the P3 row as a gate limitation instead.
