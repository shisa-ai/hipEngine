# Q4_K_S vs Q4_K_M: decode tie, prefill gap, MTP parity

## Summary

The Packet 3 Q4_K_M/Q4_K_S comparison item is complete on its throughput and
MTP-availability halves (the bytes half landed 2026-09-06). Four back-to-back
same-session bench runs on an idle XTX (512/128, BF16 KV, persistent session,
graph-replay decode, 3 measured runs each, both members of each pair sharing
one build and route flag):

- Shipping AR route: Q4_K_M 978.698 prefill / 33.985 decode; Q4_K_S
  602.499 / 34.022. Decode ties (+0.1%); Q4_K_S prefills 38.4% slower.
- Default route: Q4_K_M 963.254 / 33.996; Q4_K_S 320.149 / 34.112.
  Decode ties (+0.3%); Q4_K_S prefills 66.8% slower.
- MTP tensor availability is identical: both GGUFs carry exactly the same 4
  `blk.64.nextn` tensors (eh_proj, enorm, hnorm, shared_head_norm; 0.052 GiB
  source bytes), scanned through the repo GGUF reader (866 tensors each).

Mechanism: Q4_K_S stores 8 ffn_down, 3 attn_qkv and 1 attn_v as dense BF16
(1.631 GiB) where Q4_K_M stores Q6_K_T16 layouts — those tensors route
through slower prefill dispatch on this build while decode (rows=1) is
insensitive. Combined with the bytes artifact (resident +0.176 GiB, request
peak +2.061 GiB pre-cap), Q4_K_S is not a capacity or speed win on this
engine: it saves 0.918 GiB of file bytes and costs prefill plus parked
memory. Q4_K_M stays the default.

## Operational note

The first Q4_K_S run (default route) printed
`shipping_ar_route_mismatch=true`: the bench's default route under-states
prefill versus the shipping AR session (`use_wmma_prefill` off vs on). Both
quants were therefore measured twice — default and `--public-ar-profile` —
so every comparison is route-matched. The pair numbers are same-session and
are not comparable to older topline rows measured on earlier builds.
