# W7900 Qwen3.8: the grouped multi-request prefill route cannot batch a realistic mixed-length wave, and the prize is already measured

## Summary

`GGUF_C2_PACKED_PREFILL_MAX_ROWS` is undeclared on gfx1100, so the engine loop
never selects the multi-request prefill branch. Declaring it would still not
batch a realistic wave: the grouped route additionally requires **every chunk to
be the whole prompt** and **all chunk lengths equal**. The prize is already
measured, so #8 does not need another microbenchmark to justify the work.

## Changes

- `docs/REFACTOR.md`: new section recording the guard set, the measured cost, and
  the enable-or-delete trigger for the dead grouped-prefill route.
- Killed the queued chunked-quanta A/B (`bg-46`) before it ran: with
  `HIPENGINE_MAX_PREFILL_CHUNK_TOKENS=32` each chunk is a partial prompt and fails
  `chunk == row.prompt_ids`, so the arm was guaranteed neutral by the guards, not
  by performance. `bg-45` (capability 1 vs 8 on the real mixed-length suite) stays
  queued as the empirical check of this reading.

## Validation

Guard set read from the shipping source, `_try_prefill_native_work_batch`
(`hipengine/generation/qwen35_gguf.py:6401`): `len(request_ids) > 1`,
`<= packed_prefill_max_rows`, `_gguf_ar_packed_prefill_enabled()` (env default
**on**), `len({len(chunk)}) == 1`, and per row `prefill_tokens_seen == 0`,
`not prefix_reused_tokens`, `chunk == row.prompt_ids`, `row.slot is None`. The
scheduler itself imposes no length requirement
(`batch_scheduler.next_prefill_batch_work` takes `chunk_size` per request), so the
constraint lives entirely in the runner.

Prompt-length census from the committed packet `0740a9497` (`usage.prompt_tokens`
per prompt id): 35, 36, 36, 39, 39, 43, 46, 48, 60, 67. There is **no 8-wide
equal-length subset**, so the same-length route cannot serve a C8 wave even with
the capability declared. Concurrency in mixed-length waves is the normal case, not
an edge case.

Post-promotion admission refresh (one-token arm at the current engine, widths 1-6,
10/10 cells each): **315.8 -> 301.3 ms (C1, -4.58%)** through **1828.4 -> 1717.3 ms
(C6, -6.08%)**, i.e. today's prefill promotions did land on the server path - but
ms/lane stays flat (301.3 -> 286.2 across C1-C6) while llama.cpp falls 223.4 ->
122.6, so the ratio remains 1.35x (C1) to 2.33x (C6). Cross-session pair (the prior
arm was `78938c645`), so the level is indicative; the flat slope is the finding.

Size of the prize, measured rather than modelled: shipping-route prefill is
167.6 tok/s at 45 rows and **877.0 tok/s at 512 rows** (`--public-ar-profile`,
medians of 2, <=0.25% stdev), which is the rate a grouped ~360-row C8 wave would
hit. Substituting into the verified identity gives C8 admission 2441 -> ~855 ms and
69.97 tok/s versus current 58.74. `scripts/gguf_packed_ar_bench.py` cannot measure
this ceiling - it times packed **decode** graph buckets, not prefill - so any future
same-length ceiling test needs a new harness.
