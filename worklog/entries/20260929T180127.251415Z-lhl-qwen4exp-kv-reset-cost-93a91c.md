# RT-4 attributed: the KV reset is 29.182 ms at 128K capacity and 99.6% wasted

## Summary

RT-4 says "measure before changing clearing contract". Measured: the KV reset is
**linear in capacity at ~220 GB/s**, and at 128K capacity it clears **6 GiB in
29.182 ms**, of which **99.6%** is storage a 512-token request never touched.

The important part is *why* that matters: the memset is **already bandwidth-bound**,
so the only lever is clearing fewer bytes.

## Result

| capacity | cleared per reset | median | effective | wasted at 512 written |
|---:|---:|---:|---:|---:|
| 1,024 | 48.0 MiB | 0.238 ms | 211.6 GB/s | 50.0% |
| 4,096 | 192.0 MiB | 0.885 ms | 227.6 GB/s | 87.5% |
| 16,384 | 768.0 MiB | 3.709 ms | 217.1 GB/s | 96.9% |
| 65,536 | 3,072.0 MiB | 14.619 ms | 220.3 GB/s | 99.2% |
| 131,072 | 6,144.0 MiB | **29.182 ms** | 220.8 GB/s | **99.6%** |

Median of 7 repeats after 2 warmups, device-synchronized on both sides.
Per-token footprint **24,576 B** (12 QSA layers x 2 kv heads x 256 key length x
2 (key+value) x 2 bytes bf16), read from the GGUF metadata rather than assumed.

## Two findings

**1. It is already bandwidth-bound, so the memset itself has no headroom.**
Effective bandwidth is flat at 211-228 GB/s across a 128x range of sizes - ~86% of
this APU's ~256 GB/s LPDDR5X peak, and consistent enough across the ladder to be a
memory limit rather than an overhead artifact. No tuning makes the memset
meaningfully faster. **The only lever is clearing fewer bytes.**

**2. The waste is nearly total at realistic capacities.** A 512-token request at
128K capacity pays 29.182 ms to clear 6 GiB, of which it wrote 24 MiB (0.4%).
Even at 16K the waste is 96.9%.

## What this does not establish

**Not a saving.** This measures the current contract and makes no claim about an
alternative. RT-4's conditions still stand in full: exact visibility/ownership,
preserved recurrent initialization, poison-tested unused storage, and correct
behavior for shorter-after-longer requests, sparse tails, rollback, cancellation
and c2.

The boundary is the K/V memset only - it excludes the recurrent state zero, the
index resets and the position writes, which are the other terms in `reset()`.
`performance_claim: false`.

I also did not restate the ledger's historical "0.24-0.74%" as a millisecond
figure: that is a complete-request percentage at whatever capacity that test used,
and converting it across capacities would be exactly the kind of cross-context
number-mixing I have been correcting all session. The ladder above is the shape of
the curve; the old figure is not comparable to it.

## Validation

- Per-token footprint read from the GGUF metadata via
  `qwen4exp_gguf_config_from_metadata`, not hardcoded from memory.
- Median of 7 repeats after 2 warmups; `device_synchronize` on both sides of each
  sample, so the timing is not measuring launch latency.
- Buffers freed in a `finally` block; the run allocates only KV-sized buffers and
  does not load the model.
- Bandwidth flatness across a 128x size range is what supports the
  "bandwidth-bound, not overhead" reading; a single size could not distinguish it.
- Ledger IDs unchanged (70).
