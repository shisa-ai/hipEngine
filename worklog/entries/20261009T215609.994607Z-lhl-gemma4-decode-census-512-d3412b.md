# Census the 512-depth decode step: launch-bound, not kernel-bound

## Summary

The last trailing ladder cell is 512-token decode (34.55 vs llama.cpp's
35.98 tok/s, 0.96x). A rocprofv3 kernel-trace census of the restored-state
decode at that depth (512-token KV state minted from the same harness,
`/tmp/multiloop-beat-llamacpp/kvstate_512.bin`) shows the deficit is
launch overhead, not kernel time:

- The decode step carries ~505 kernel launches. Per layer per step:
  `q8_0_t16_gemv` 4.2 launches (69.1 us each), `gemma4_rmsnorm` 4
  (6.9 us), one fused attention decode kernel (97.2 us -- the staged
  singleton is not selected at this depth), router topk (30.0 us),
  `qk_t16` and `q5_1_mmq` gemvs, moe accumulation.
- Device kernel time sums to ~18.7 ms per step against a ~29.7 ms wall
  (33.57 tok/s single-sample restore decode; ladder row 34.55 over three
  samples): **~11 ms/step, 37 percent, is inter-launch host overhead**.
- Attention is 2.9 ms of the step at this depth -- the deep-decode PV
  work does not dominate here.

llama.cpp's comparator path is a whole-step HIP graph, which is exactly
the difference. `hipengine/runtime/gguf_decode_graph.py` implements a
state-bound whole-step GGUF decode graph capture in-tree, wired for
Qwen35 (`qwen35_gguf_runner`) only. The next unit wires it for Gemma 4
decode: bind the step's kernels to resident weights/KV/sampler buffers,
respect the state-generation and cursor-window semantics the module
already documents, and gate on restored-decode ID equality plus the
usual bit-parity suites.

## Changes

- None; census and diagnosis only. Raw trace:
  `/tmp/multiloop-beat-llamacpp/pmc-dec512/zbook/853457_kernel_trace.csv`.

## Validation

- Census: `rocprofv3 --kernel-trace -f csv -d /tmp/multiloop-beat-llamacpp/pmc-dec512`
  over `scripts/gemma4_kv_restore_bench.py --mode restore` at 512.
- Kernel durations are device-side and unaffected by the profiler's host
  overhead (the profiled decode wall is 2.4 tok/s; the clean restore
  decode is 33.57 tok/s single-sample).
