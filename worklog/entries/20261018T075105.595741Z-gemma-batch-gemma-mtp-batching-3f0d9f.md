# Implement request-isolated Gemma MTP batching

## Summary

Implement real multi-request Gemma MTP through the existing resident engine.
The previous provider batches draft tokens from one request and shares one
mutable KV cursor. The new owner keeps KV, sampler state and unpublished tokens
request-local while packing target and assistant projections across ready rows.

## Changes

- Refactor the existing sampler/accept walk into bounded cooperative operations;
  the synchronous provider drives the same operations for compatibility.
- Use the existing resident scheduler and EngineService for admission, canonical
  token publication, cancellation and reclaim. A cycle's unpublished tail is
  private to its request, so cancellation does not rewind or modify peers.
- Target packed-forward and assistant packed-proposal implementations are being
  developed independently in their existing runtime owners. Resident verification
  selects the existing row-exact fallback (`verify_dense_exact=True`) in every
  profile; prompt prefill keeps its selected profile variants. This avoids
  promoting changed target arithmetic as a side effect of multi-request packing.
- Intended public capability is C1–C4 physical MTP, including ragged prompt/output
  lengths and sampled requests. Prefill remains independently chunked; attention
  reads independent request KV. No speedup claim or root README edit is planned.
