# the Q8_0 T16 four-wave prefill is 1.4-1.8x the dense route's in-situ rate

## Summary

The cost/benefit test for the loader change, and a correction to how I had been framing the dense
term. **The lever is real: the T16 four-wave kernel runs at 12.2-15.5 TFLOP/s where the dense term
runs at ~8.5.**

## Correction first: the dense term is compute-bound, not bandwidth-bound

I had been describing the dense term as "pinned at 127 GB/s of weight traffic against an achievable
223". **That framing is wrong and I am retracting it.**

The dense term is 189.31 ms for 206 calls of known shape. Its arithmetic:

| quantity | value |
| --- | --- |
| FLOPs | 1.576 TFLOP |
| weight bytes | 2.42 GB |
| **aggregate rate** | **8.33 TFLOP/s and 12.8 GB/s** |

At rows=512 these shapes have an arithmetic intensity near **963 FLOP/byte**. A GEMM that does 963
FLOP per byte read is not bandwidth-bound, and 12.8 GB/s of weight traffic is not a bandwidth
figure at all -- it is what a compute-bound kernel produces. The 127 GB/s number was measuring
something other than the dense term's weight traffic, and the "223 achievable" comparison was
therefore never valid for this term.

**This matters because it changed the sign of the conclusion.** Read as bandwidth, the
microbench's 12.6-16.1 GB/s looks 8-10x *slower* than the in-situ figure, which is what my first
run printed. Read as FLOPs, the same numbers are 12.2-15.5 TFLOP/s against an in-situ ~8.5, i.e.
faster.

## The measurement

`scripts/gemma4_q8_t16_4wave_microbench.py`, rows=512, the model's own dense shapes, 20 iterations
after 3 warmups, HIP event pair, calling the registered
`gguf_q8_0_t16_wmma_prefill_4wave_bf16_bf16_out` wrapper at the tiles the gate selects
(`tile_m=128, tile_n=32` -- the 4wave symbol's allowed set is `{(128,16),(128,32)}`):

| out | in | ms | TFLOP/s | GB/s |
| ---: | ---: | ---: | ---: | ---: |
| 2816 | 2816 | 0.6683 | 12.2 | 12.6 |
| 2112 | 2816 | 0.4169 | 14.6 | 15.2 |
| 4096 | 2816 | 0.7626 | 15.5 | 16.1 |
| 8192 | 2816 | 1.5589 | 15.2 | 15.7 |

## The comparison, and why it is the right one

The dense term's aggregate is 8.33 TFLOP/s, but that aggregate includes the rows=1 lm head, which
is a GEMV and far below the rows=512 rate. That call is `out=262144, in=2816` -- **785 MB of
weights, so roughly 4 ms of the 189.31 ms**. Removing it leaves ~185 ms for 1.575 TFLOP, i.e.
**~8.5 TFLOP/s for the rows=512 calls**.

So the like-for-like comparison is **12.2-15.5 against ~8.5 TFLOP/s: a 1.4-1.8x lever** on the
dense term.

This is the correct comparison for the loader decision because the loader change would *replace*
the raw route with the T16 route, so the aggregate is the thing being replaced. It is not a
kernel-vs-kernel microbench of two candidates under identical harness conditions.

**Applying the ratio to the dense term: 185 ms -> ~105-130 ms, i.e. -55 to -75 ms on a 659 ms
prefill, or -8 to -11 percent.**

## Status of that number

**Expected, not measured end-to-end.** It is an isolated microbench of one kernel at one row count
against an in-situ aggregate. What could move it:

- The microbench uses zero activations and random tile bytes. A GEMM has no data-dependent
  branching so this should not matter, but it is not the same input.
- The in-situ figure includes per-call dispatch overhead that the microbench does not.
- The dense term's actual raw kernel has still not been identified -- `exact_prefill_*` and
  `mmq128_prefill_*` are both plausible. The comparison is against the *aggregate* on purpose, but
  knowing which kernel it is would make the claim sharper.
- Nothing here exercises the decode path, which the loader change also touches.

**The loader change is justified by this, and the claim it would be measured against is a -8 to
-11 percent dense-term reduction.**

## Changes

- `scripts/gemma4_q8_t16_4wave_microbench.py` -- the harness. Its first version reported GB/s and
  printed "slower" for a compute-bound kernel; the header now records why TFLOPS is the metric.
- `scripts/gemma4_dense_resolved_variant_probe.py` -- an attempt to capture the resolved variant
  that instead caught capability enumeration (every count 1, all `moe_linear`). Kept as the record
  of that failure; the raw kernel's identity is still open.

## Validation

Read-only measurement; no production code changed, so no arithmetic gate applies.

```
.venv/bin/python scripts/gemma4_q8_t16_4wave_microbench.py   # 12.2-15.5 TFLOP/s, reproduced twice
uv run pytest tests/test_unit_gemma4_q8_0_t16_repack_roundtrip.py   # 10 passed (repack is lossless)
```

Run twice with consistent results (12.7-15.6, then 12.2-15.5 TFLOP/s).
