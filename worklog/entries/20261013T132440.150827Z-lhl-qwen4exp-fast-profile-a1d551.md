# Qwen4Exp fast execution profile with the T16 down route

## Summary

The owner accepted the X-7 question on 2026-10-13 in the form of a new opt-in
`fast` execution profile: `production` keeps its calibrated envelope and stays
the shipped default, and reduced-precision operand routes land in `fast`,
held to exact control/ownership, determinism, and the outer safety floor until
each is re-reviewed under the production gates. The owner's stated order is
throughput first, then the production correctness pass once `fast` is in the
external engines' throughput class.

`fast` is registered for `qwen4_exp_gguf` / `hip_gfx1151` / `gguf_ud_q4_k_xl`.
Its first plan is the production plan with the three Q5_1 routed-down scopes
on the T16 expert-major compensated WMMA route, all 43 Q5_1 layers.

## Decisions and findings

- **A profile, not a flag set or a threshold change.** `ExecutionProfile.FAST`
  is a fourth public profile; `docs/EXECUTION-PROFILES.md` section 2 states
  its contract. A combination with no registered fast plan falls back to
  strict and says so.
- **Tile residency happens in the binder, after construction.** The benchmark
  and gate scripts pass their own generator factories, so a plan `factory`
  hook cannot own construction. The binder calls
  `generator.populate_t16_resident_stages(("expert_down",))`.
- **Bug found and fixed: late tiles were never dispatched.** The runner's
  layer bindings hold weight objects, so weights republished through
  `swap_weight` after the runner exists were invisible to dispatch - a first
  smoke run reported the fast manifest while running production arithmetic
  (identical output digests, zero T16 kernel calls). The runner now has
  `rebind_resident_weights()` and the populate calls it.
- **The T16 gate/up route is not in the plan and cannot be as designed.**
  `docs/QWEN4EXP-T16-RESIDENCY.md` makes the full window fit by freeing the
  raw expert weights, but the decode owners read the raw layout, so freeing
  them breaks decode. Device residency is 76.8 GiB (103.7 GiB file minus the
  26.9 GiB mmap'd PLE table); gate/up tiles add 41.3 GiB and down tiles
  25.2 GiB against a 120 GiB GTT limit.
- **Even the down tiles alone squeeze the host.** With them resident the
  device holds about 109 GiB and the host reports about 12 GiB available and
  12 GiB of page cache, below the 26.9 GiB PLE table the warm protocol expects
  cached.
- **Direction: a routed kernel that reads the raw layout.** At the 4096-token
  chunk each of the 512 experts receives about 80 routed rows (top-k 10). The
  T16 kernels decode a weight tile once per 16 rows; gufo's
  `RoutedF16GEMMKernel` decodes once per 48-128 rows directly from the raw
  GGUF blocks, with no second weight copy. Routed experts cost 4621 ms per
  code-p4096 prefill here against 812 ms in gufo, so that port replaces both
  T16 routes and removes the residency cost. The owner approved porting the
  MIT-licensed gufo kernel source with attribution.

## Measured

Diagnostic, not a scoreboard row. Model `Qwen3.8-Flash-Next` `UD-Q4_K_XL`
(four shards), Radeon 8060S / gfx1151, machine
`55ea6c509d0b49eea8de7094a1023668`, one process constructed with
`execution_profile=fast`, chunk 4096, compact capture, 128 decode
transitions, arms alternated by toggling `HIPENGINE_QWEN4_EXP_T16_DOWN`
(1, 0, 1, 0), one sample per arm per case, first fast sample discarded as
warmup:

| Case | T16 down off | T16 down on | Change |
| --- | ---: | ---: | ---: |
| code-p512 prefill tok/s | 307.7 / 305.9 | 339.4 | about +10.6% |
| code-p4096 prefill tok/s | 336.7 / 335.5 | 364.4 / 365.4 | about +8.5% |
| decode tok/s (p4096) | 20.58 | 20.59 | unchanged |

The T16 down kernel ran 43 times per prefill in the on arm and zero in the
off arm. The 129-token greedy output is identical between arms on code-p4096
and differs on code-p512. This agrees with the 2026-10-09 engine A/B
(+9.46% over 12 cases). The 12-case canonical run and the benchmark rollup
are deferred to the routed-kernel unit, which replaces this route.
