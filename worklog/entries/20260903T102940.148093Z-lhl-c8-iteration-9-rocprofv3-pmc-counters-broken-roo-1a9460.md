# C8 iteration 15: Q4 grouped kernel-body analysis; no duplicate work to remove

## Summary

Follow-up to iteration 9's roofline fallback: inspected the body of
`q4_k_t16_dense_rowtile_accumulate` (used by
`q4_k_t16_dense_rowtile16_w2_grouped_gemv_kernel<unsigned short, 6/8>`) to find
why achieved bandwidth (~92-144 GB/s) is far below the docs/ROOFLINE.md band.

## Findings

- The two waves of a T16 tile own disjoint column halves, so each packed
  weight byte is read exactly once per call - no duplicate encoded-weight
  traversal exists to eliminate.
- Scale/min metadata is read once per block; the dequantized `weight[]` values
  are computed once per block and reused across all ROW_TILE rows - no
  duplicate dequantization.
- Activations are loaded once per row; the per-row FMA order and wave32
  reduction are unchanged by any load-rescheduling-only change.
- Conclusion: the measured gap to the roofline band is latency/occupancy-bound
  (VGPR 192/224 at workgroup 64 caps resident waves), so an exact candidate
  must cut work or bytes (e.g. narrower metadata, lower VGPR pressure), not
  merely reschedule loads. The "Prefer a mechanism" checklist item stays open
  for an implementation candidate.
