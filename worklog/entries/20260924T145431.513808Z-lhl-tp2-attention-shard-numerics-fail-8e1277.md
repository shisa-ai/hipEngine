# Head-sharded attention reduces correctly but fails the gate, and GDN layers are where it breaks

## Summary

The head-sharded bulk prefill now runs end to end, and its numerics **fail the
correctness gate by a wide margin**. The reduce itself is right; the divergence
comes from the sharded attention output and is injected mainly at GDN
(`linear_attention`) layers.

Measured on the two-GPU host, 64-token prompt, `Qwen3.8-27B-Q4_K_M`, bulk
prefill at `bulk_prefill_rows=64`, head-sharded vs the unsharded route on the
same prompt:

| metric | value | gate |
| --- | --- | --- |
| `mean_kl` | **0.3626** | ≤ 0.05 |
| `max_kl` | **1.3091** | — |
| `top1_agreement` | **0.5938** (26/64 flips) | ≥ 0.90 |
| `mean_abs` | 0.4717 | — |
| `max_abs` | 7.1279 | — |
| non-finite | 0 | 0 |

So the route is **not promotable**, and `attention_shard` stays default-off.

## The reduce is not the problem

Layer-0's post-attention-norm input, dumped on both routes for both ranks
(64 × 5120 bf16 each):

| comparison | identical | max abs | mean abs |
| --- | --- | --- | --- |
| unsharded rank0 vs rank1 | **True** | 0.0 | 0.0 |
| head-sharded rank0 vs rank1 | **True** | 0.0 | 0.0 |
| unsharded vs head-sharded (rank0) | False | 1.590 | 0.0069 |

Both routes are internally rank-symmetric, and the head-sharded reduce produces
**bit-identical** sums on the two ranks - which is exactly what a correct
cross-rank sum of two bf16 partials should do. The magnitudes match too
(`|mean|` 0.0356 unsharded vs 0.0359 head-sharded, ratio 1.01). So the reduce,
the slot layout, and the per-rank attention geometry are all working.

## Where it breaks: GDN layers

Relative L2 error of the post-attention-norm input against the unsharded route,
captured at consecutive layers (`|x|` is the unsharded magnitude):

| layer | type | \|x\| mean | max abs diff | rel L2 |
| --- | --- | --- | --- | --- |
| 0 | GDN | 0.0356 | 1.59 | 0.0611 |
| 1 | GDN | 0.0174 | 1.66 | 0.4869 |
| 2 | GDN | 0.0205 | 5.67 | **1.0001** |
| 3 | full attention | 0.0272 | 16.94 | 0.3207 |
| 4 | GDN | 0.0240 | 2.49 | 0.8165 |

The config is 64 layers: 48 `linear_attention` (GDN) and 16 `full_attention`, in a
3-GDN-then-1-full pattern, so layer 0 is GDN and layer 3 is the first full
attention. A relative L2 of 1.0 at layer 2 means that layer's sharded output is
essentially uncorrelated with the unsharded one - far past any rounding story,
and past the 6% already present at layer 0.

This is **not** bf16 partial rounding. Summing two bf16 partials instead of one
full-width sum costs one extra bf16 rounding, i.e. a sub-percent relative error
per element, and it cannot compound to 100% in two layers.

## Leading hypothesis, not yet confirmed

The GDN shard slice may be taken along the wrong axis or against an interleaved
value-head→output mapping. `ssm_value_dim` stays 128 (per value head) while
`ssm_group_count` and `ssm_inner_size` halve, so each rank's `ssm_out` shard is
columns `[r*half, (r+1)*half)` of a `(hidden, ssm_inner_size)` weight, and its
product is a hidden-size partial. If the groups that map to those output columns
are interleaved rather than blocked, the two ranks' partials would still have the
right magnitude and would still sum to something - just not to the true output.
That matches the observation exactly. The same question applies to
`attn_output` versus the head split, but the full-attention layer is where the
error *drops*, so GDN is the place to look first.

## A second, independent bug: a raising constructor leaks VRAM

`MlpTP2GenerationSession.close()` is an instance method and the class has no
`__del__`, so a constructor that raises leaves every buffer it already allocated
to process exit. Measured consequence: a harness that retried construction in one
process OOM'd at a 16 GiB free window, then at 15, then at 14, and only
succeeded at 13 - each failure had leaked a rank's worth of VRAM and made the
next attempt worse. Running one route per process (so a failure dies with its
allocations) made the same window work first try. Tracked in `docs/REFACTOR.md`.

## Validation

- `python3 -m pytest tests/test_unit_distributed_*.py` -> 240 passed.
- `python3 -m pytest tests/test_gpu_distributed_staged_compiled.py
  tests/test_unit_distributed_shard_group.py` -> 33 passed, 1 skipped.
- New: `test_device_exchange_serves_two_reductions_in_one_layer` drives the
  doubled slot space (`num_layers = 2 * reductions_per_layer`,
  `slot = reductions_per_layer * (layer % 2) + phase`) through the real device
  exchange and checks each phase against its own host sum. **It is not a RED for
  the slot collision**: mutating the slot to collide both phases leaves it green,
  because the hazard is a timing race that a 256-element payload never loses. The
  deterministic guard is the slot-arithmetic assertion in
  `test_unit_distributed_shard_group.py`, and the test's docstring says so.
- End-to-end: 64-token prompt, both routes, same revision, `mean_kl` 0.3626 /
  `top1_agreement` 0.5938 as tabled above.
