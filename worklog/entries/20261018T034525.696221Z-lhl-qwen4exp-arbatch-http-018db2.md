# Live HTTP qualification of opt-in Flash-Next AR batching

## Summary

The opt-in AR batch path (`HIPENGINE_QWEN4_EXP_AR_BATCH=1`) now has live HTTP
evidence at serving capacity 2 on the production checkpoint: C1, C2 and C4
request shapes, blocking and SSE, mixed prompt lengths, cancellation with a
surviving peer, post-cancel recovery, and a labelled mixed AR+MTP diagnostic.
All 72 lifecycle checks passed. A separate capacity-4 run then exercised the
real physical width-4 path (`state_slots=4`, `{"4": 63}` in both blocking and
SSE phases, cancel one of four, recovery): 67 checks passed. The reported
widths are the owner's own `step_widths` histogram, so they prove physical
batch rows rather than logical HTTP concurrency.

The capacity-4 run needs a qualification-only launcher
(`scripts/qwen4exp_arbatch_c4_server.py`) because the plugin declares
`server_plain_ar_max_active_requests = 2` and rejects a larger resident
capacity. That cap is unchanged; the launcher raises it in-process for the
test only.

One configuration condition is now explicit: under the server default
`prefill_decode_policy="protect_decode"`, two synchronized arrivals never share
a step (the second row's prefill waits for the first row's decode). With
`HIPENGINE_PREFILL_DECODE_POLICY=protect_ttft` the identical arrivals step at
width 2. This is the scheduler policy behaving as documented, not an owner
defect, but it means the batch path cannot reach width 2 from independent HTTP
requests under the default policy.

This entry extends the design/contract record in
[`20261018T032510.447761Z-lhl-qwen4exp-ar-batch-optin-1b213b`](20261018T032510.447761Z-lhl-qwen4exp-ar-batch-optin-1b213b.md)
and replaces its "live serving qualification not run" statement for the tested
shape only. No promotion, no default change, no performance or numerical claim.

### Harness

`scripts/qwen4exp_ar_batch_http_check.py` reuses `request`/`compact` from
`scripts/qwen4exp_http_grid.py`, starts every concurrent phase on one
`asyncio.Event` barrier, samples `/ready` queue depth while the phase runs, and
reads `GET /v1/hipengine/decode` before and after each phase. Concurrent phases
pin decode length with `ignore_eos`, because a two-token answer would hide a
missing overlap; the report records `decode_length_forced: true`.

```
python3 scripts/qwen4exp_ar_batch_http_check.py \
  --url http://127.0.0.1:18391 --model qwen38fn-arbatch \
  --output /tmp/he-arbatch-http --with-mtp
```

### Configuration condition: `protect_decode` serializes arrivals

First run used the server default `prefill_decode_policy="protect_decode"`. All
concurrent phases reported width 1 only (`c2_block {"1": 126}` for two
64-token rows; C4 finished 4.4 s apart in strict order). Instrumented ticks
showed `active=2 active_ids=(2, 3)` while `decode_batch` still received one
request id: the second row was admitted but its prefill was deferred until the
first row's decode finished.

An A/B on the same build with two synchronized 8-token forced requests:

| policy | width delta | wall |
| --- | --- | --- |
| `protect_decode` (default) | `{"1": 14}` | 1.476 s |
| `protect_ttft` | `{"2": 7}` | 1.088 s |

Wall times are lifecycle observations, not a performance claim. The policy is
the only difference; the artifacts are below. Consequence for PS8: physical AR
batching of independent HTTP arrivals needs a TTFT-first or fair policy, or a
batcher-side change; the default zero-window, protect-decode server will report
width 1 regardless of how many requests are in flight.

### Serving changes in this unit

- `GET /v1/hipengine/decode` (authenticated, read-only) returns
  `Qwen4ExpGGUFTextGenerator.decode_telemetry()`: selected decode path plus the
  owner's live counters. It probes `engine._text_generator` and then the engine,
  and reports `available: false` for engines without the hook. This is the only
  way to read physical width from outside the server process. A failing hook now
  returns `reason: decode_telemetry_unavailable` and logs the exception detail
  server-side instead of echoing it to the caller.
- `Qwen4ExpARBatchOwner.telemetry()` snapshots counters and the width histogram
  under a lock. Lease insert/remove/clear now take that same lock, so
  `live_slots` is the lease-map size at the snapshot instant rather than a
  later re-count. The docstring states the remaining limit: a step can complete
  between the snapshot and the response, so counters may lag by one step. It
  does not claim a transactional snapshot against device state.
- The harness validates every telemetry body (`require_telemetry`):
  `available: false`, a missing `decode` object, or a non-object `ar_batch`
  raises instead of being scored as zero widths. `--phases c4` runs only the
  width-4 phases.
- Tests: `test_decode_telemetry_endpoint_reports_physical_state_and_auth`
  (auth, unavailable engine, `_text_generator` hop),
  `test_decode_telemetry_endpoint_sanitizes_hook_failures_and_bad_payloads`
  (fixed reason, no raw exception text, non-mapping payload), and
  `test_unit_qwen4exp_arbatch_http_check.py` (width deltas, unavailable and
  malformed payload rejection).
- `docs/API.md` documents the endpoint: auth, read-only, schema, logical versus
  physical width, snapshot staleness, and the two `available: false` reasons.

### Not established here

- **Production numerical gate.** Still not run. This is lifecycle and control
  evidence only; the batch path is not bit-identical to c1 by construction.
- **Long context.** Context was 2048 tokens and prompts stayed below
  `dense_equivalent_limit` (2051 positions at block budget 512), so the batch's
  per-row index selection was never exercised live.
- **Ragged AR+MTP physical batching.** Not attempted; MTP stayed c1 at width 1.
- **Memory.** 27.59 GiB free at capacity 4 with four 2048-token slots (96.41 GiB
  used); the cost at larger contexts is unmeasured.
- **Capacity cap.** The production plugin still caps resident capacity at 2. The
  width-4 run used a test-only launcher that raises the class attribute; no
  serving default changed and the cap decision remains open.
- **Failure recovery under load.** The poisoned-step path is still fail-closed
  and unexercised live; the cancellation phase produced no owner failure.
- **PS8 closure.** `docs/QWEN4EXP-PRODUCTION-SERVING.md` PS8 stays open: this
  qualifies C1/C2, C4 queueing, and physical width 4 for the tested shape, but
  not the default policy, long context, or ragged speculative rows.
