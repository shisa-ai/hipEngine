# W7900 Qwen3.8: shipping-route prefill attribution by kernel owner; earlier stage captures were off-route

## Summary

Two things, one of which corrects my own earlier measurements. First: the
prefill stage-attribution captures used earlier today to argue that the small-row
route is kernel-shaped were taken **off the shipping AR route** -
`effective_use_wmma_prefill` was `False` in every measured run, which is exactly
what `shipping_ar_route_mismatch` exists to catch. Corrected shipping-route
anchors are now recorded, and the deficit survives the correction: a 45-token
prefill takes 0.2685 s, i.e. 63.7 GB/s of effective weight streaming against a
~24 ms memory floor. Second: a kernel trace of the shipping route now names the
owners instead of inferring them, and the Q6 four-wave-parallel idea that the
trace geometry suggests turns out to be already decided against below 512 rows by
the peer backend, so it is parked with its numbers rather than retried blind.

The paired A/B promotions from earlier today (fused gate/up from rows 33, unequal
QKV dual from rows 16) are **not** invalidated by the route finding: in those
comparisons both arms ran the same route, so the deltas hold. What does not hold
is reading the older absolute per-stage milliseconds as shipping-route costs.

## Changes

- Added `scripts/gguf_kernel_trace_rollup.py`: aggregates a `rocprofv3
  --kernel-trace` CSV into per-kernel total time, launch count, mean duration and
  launch geometry (`Grid_Size_X` / `Workgroup_Size_X` / `VGPR_Count` /
  `SGPR_Count`), with an optional kernel-name regex. Geometry is the point - it is
  what identifies which owner actually served a stage.

## Validation

W7900 (gfx1100/RDNA3), Qwen3.8-27B-Q4_K_M (17,106,773,984 bytes), production
profile, `--require-cached-build` with `/tmp/compiler-version-gfx1100.txt`,
`HIP_VISIBLE_DEVICES=0 ROCR_VISIBLE_DEVICES=0`.

Shipping-route anchors (`--public-ar-profile --gpu-stage-timings
--persistent-session`, `shipping_ar_route_mismatch: false`,
`effective_use_wmma_prefill_all: [true, true, true]`):

| rows | prefill s | tok/s | effective weight BW |
| --- | --- | --- | --- |
| 45 | 0.2685 | 167.6 | 63.7 GB/s |
| 512 | 0.5838 | 877.0 | 29.3 GB/s (compute-side bound) |

- Off-route comparison for the same 45-row shape: 0.4573 s / 98.4 tok/s, so the
  flag is not decorative - the route changes prefill wall by +70%.
- Roofline position at 45 rows: memory floor 17.1 GB at ~700 GB/s is ~24 ms and
  the compute floor is ~5 ms, against 268 ms measured. Neither bound explains the
  time; the regime is owner-inefficiency-bound. At 512 rows the same forward does
  ~27.6 TFLOP in 0.584 s = ~47 TFLOP/s, about half of the BF16 dense peak, which
  is respectable. The 45-row case is not.
- Owner breakdown, shipping route, 45 rows (6358 kernel records; 3 measured
  prefills plus one decode token):

  Every top owner lands near ~3% of BF16 peak, which is consistent with weight

- Tool validation: run against both traces; the first version reported zero

  `Duration` column - duration is now computed as the difference, and rows with
  non-positive duration are dropped.

### Parked lead: Q6 four-wave prefill on gfx1100

The Q6/Q5 owners run one wavefront per block while the Q4 owners run four, and
the four-wave Q6 launcher already exists in this tree
(`gguf_q6_k_t16_qmicro_planar_wmma_prefill_shared4_bf16_bf16_out`). It is
registered and dispatched only on **gfx1151**, whose selector gates it at
`GGUF_Q6_PLANAR_PREFILL_SHARED4_MIN_ROWS = 512` and
`GGUF_Q6_PLANAR_PREFILL_SHARED4_SHAPES = {(17408, 5120)}`; gfx1100 has no
selector for this owner at all. The parked part is the row floor: the peer's
retained decision (`benchmarks/results/2026-08-15-gfx1151-qwen38-27b-q6-standard-
shared4-prefill.json`) admits shared4 **only at rows >= 512**, so carrying it to
45 rows contradicts existing evidence and needs a gfx1100-specific owner screen
first, not a registration plus hope. Related structural hole worth naming: the
source-F16 rocBLAS prefill tables (`GGUF_Q6_T16_F16_ROCBLAS_PREFILL_POLICIES`)
also start at rows 512, so rows 9..511 currently have no tiled route for these
shapes at all - closing that hole with a small-M tiling/K-split owner is a bigger
and better-founded target than widening a floor the peer already rejected.
