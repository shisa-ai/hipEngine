# Make Gemma expert MMQ gate/up leaves capturable

## Summary

HIP decode-graph capture failed with HIP error 900 inside the Gemma expert
MMQ-family gate/up leaves. Each leaf sized its tile grid from a device readback
of the padded row count the group-scatter tile map wrote, and synchronized the
stream to make that readback visible. Both are illegal inside an active
capture. When the stream is capturing the leaves now launch the
routing-independent upper bound instead; the tile map already fills every
unused `tile_expert` slot with `-1` and the leaves return early on a negative
expert, so the bounded grid produces the same output and only adds blocks that
exit immediately. The non-capture path keeps the exact readback and its
overflow check.

## Changes

- `hipengine/core/hip.py`: add `HipRuntime.stream_is_capturing`, binding
  `hipStreamIsCapturing`. Returns `True` for any status but `None`, so an
  invalidated capture is treated like an active one -- host synchronization is
  illegal in both.
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_experts.py`: add
  `_stream_capturing` and `_tile_rows_or_bound`, and route all three MMQ-family
  gate/up leaves (`gate_up_mmq32`, `gate_up_t16`, `gate_up_iu8`) through it.
  Under capture the MMQ32 bound `compact_rows + 31 * num_experts` is rounded up
  to the leaf's required 32-row alignment; the WMMA (16-row) leaves use the
  existing `_wmma_tile_upper_bound`. Unused imports removed from the leaves.
- `tests/test_unit_gemma4_merge_ownership.py`: the fake runtime used by the
  iu8 producer-stream ownership test now answers `stream_is_capturing` (False),
  preserving its existing sync/readback/route assertions. Added three focused
  tests: capture skips the readback and launches the bound, the bound rounds and
  guards capacity, and the non-capture path still reads the exact total back.
- `tests/test_unit_gemma4_decode_graph_capture_cleanup.py`: new. A failed
  capture must end the capture, destroy the partial graph, and re-raise the
  original failure even when ending an already-invalidated capture reports
  HIP 904. The containment in `gemma4_decode_graph._capture` was already
  correct; these are regression guards, not a behavior change.
