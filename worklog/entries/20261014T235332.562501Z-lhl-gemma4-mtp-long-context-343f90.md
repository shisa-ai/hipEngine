# Gemma 4 MTP verify and draft attention at long context

## Summary

MTP was slower than plain decoding on long prompts (32K: 17.27 s against
14.68 s for 128 tokens). Three routes put long global rows on the owned-logits
class kernel: the production multi-row verify block (gemma4_plain prefill
request; five rows 133.7 ms at 32K), a one-row verify block (65.0 ms), and the
draft head's native attention launch (12.8 ms a draft token). Fixed by serving
a 2-16 row verify block with one multi-row launch of the plan's flash decode
variant from 256 keys (the C dispatcher already handled tokens > 1), giving a
one-row verify block the decode step's variants exactly, and attending the
draft head through the long-row flash launcher in every profile. 32K: MTP
13.93 s against 14.65 s plain (decode phase 1.43 s against 2.18 s); 8K 3.48 s
against 4.26 s.

## Changes

- `gemma4_attention.py`: `FLASH_MULTI_ROW_MAX_TOKENS = 16`; `flash_admits(max_tokens=)`;
  `_launch_prefill` admits multi-row flash only under `prefer_flash`, uses the
  decode ABI for it and skips the four-row global batching.
- `gemma4_layer.py`: `attend` consults the decode selector first for a
  multi-row block carrying a decode scope; the selector admits flash for 2-16
  rows from 256 keys on either packing.
- `runtime/gemma4.py`: `step_like` (decode step or one-row verify) takes the
  decode variants; a non-row-exact multi-row verify block carries the decode
  scope beside its `gemma4_plain` fallback.
- `runtime/gemma4_assistant.py`: head attention via
  `gemma4_attention_decode_flash_long_bf16`.
- Tests: selection (multi-row admission/refusal), runner forwarding (GPU).
- Docs: MTP reference (verify contract, Long prompts), `docs/KERNELS.md`.
