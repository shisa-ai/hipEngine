# the tiled prefill attention kernel is bit exact below the key tile and wins only on 512 wide heads

## Summary

`gemma4_attention_prefill_tiled_kernel` has existed in the tree, exported as
`hipengine_gemma4_attention_prefill_tiled_{bf16,f32}`, with **no Python wrapper
and no caller** -- so it had never been benched against the strict kernel it would
replace. It now has been, across six geometries, with an elementwise comparison.

**It is a 512-dim-head win and a 256-dim-head loss, which makes it a wash on this
model at the benchmarked shape.** The lead is closed for prefill at 512 tokens.

It also **corrects a claim in the kernel's own comment**, and I have to correct a
claim of my own from the previous entry.

## The A/B

New script `scripts/gemma4_attention_prefill_tiled_ab.py` drives both kernels
through ctypes on identical device buffers, times them median-per-iteration with a
device sync, and compares outputs elementwise. `keys` and `window` are set
independently, which is what separates the single-tile regime from the multi-tile
one.

| geometry | strict ms | tiled ms | ratio | bit-identical | max abs diff | mismatches |
| --- | ---: | ---: | ---: | --- | ---: | ---: |
| 512t 256d 16/8 w=1024 | 4.63 | 4.90 | **1.059 slower** | yes | 0 | 0 |
| 512t **512d 16/2** w=0 | 6.95 | 5.63 | **0.811 faster** | yes | 0 | 0 |
| 512t 256d 16/8 w=0 | 4.84 | 5.36 | 1.106 slower | yes | 0 | 0 |
| 1024t 256d w=1024 | 19.08 | 19.63 | 1.029 slower | yes | 0 | 0 |
| 2048t 256d w=1024 | 64.61 | 67.16 | 1.040 slower | yes | 0 | 0 |
| 2048t 256d w=0 | 78.57 | 82.00 | 1.044 slower | **no** | 9 | 18 / 8.4M |
| 2048t **512d** w=0 | 131.93 | 111.92 | **0.848 faster** | **no** | 1 | 15 / 16.8M |
| 4096t **512d** w=0 | 656.81 | 466.62 | **0.710 faster** | **no** | 16 | 95 / 33.6M |

Two clean results fall out.

**The bit-identity boundary is the key tile.** `kTile` is 1024. Below it the whole
key range is one tile, no rescale happens, and the tiled kernel is **bit-exact** --
0 mismatches in 2,097,152 and in 8,388,608 elements. Above it the row max is not
known until the walk ends, the accumulation is rescaled as the max grows, and the
two diverge by 1 to 16 bf16 ulps on 15 to 95 elements in 8 to 34 million.

**The source comment is therefore right about the mechanism and imprecise about
where it applies.** It says the reassociation is "why this is a registered
production variant with a tolerance gate rather than a replacement for the strict
kernel". That is true only for `keys > 1024`. For any context at or below 1024 --
which is the whole of this model's sliding-window geometry, since
`sliding_window = 1024` -- the tiled kernel is a **bit-exact** drop-in and does not
need the tolerance gate at all.

**And it is not a general speed win.** It is faster only where `head_dim == 512`
(15 percent at 2048 tokens, 29 percent at 4096) and slower where `head_dim == 256`
(3 to 11 percent). The reason is visible in the launcher: `kTile` is fixed at
1024, so at 512 keys the tiled kernel carries a 1024-entry logit tile for a
512-entry walk, and the extra shared memory costs occupancy that the strict
kernel's context-sized tile does not pay at this shape.

## This model's shape, from the artifact

Read out of the campaign GGUF's own metadata rather than inferred:

```
gemma4.block_count                  = 30
gemma4.attention.head_count         = 16
gemma4.attention.key_length         = 512     key_length_swa    = 256
gemma4.attention.sliding_window     = 1024
gemma4.attention.head_count_kv      = {8: 25, 2: 5}
gemma4.attention.sliding_window_pattern = [1,1,1,1,1,0] * 5
```

**25 sliding layers at 256d/8kv and 5 full layers at 512d/2kv**, the full ones at
indices 5, 11, 17, 23, 29. The bench's own total independently agrees: 25 x 4.63
+ 5 x 6.95 = **150.5 ms** against the 150.3 ms it reports.

**So switching the default to tiled at 512 tokens gives 25 x 4.90 + 5 x 5.63 =
150.65 ms against 150.5 -- 0.1 percent worse.** At 2048 tokens it is about 1.6
percent better; the 5 full layers gain 15 percent and the 25 sliding layers lose 4.
The win is real but it is a long-context win, and the objective's prefill
measurement is at prompt 512.

## A correction to my own previous entry

Last unit I reported that `--mask zero` makes the kernel **slower** (6.19 against
4.64 ms) and concluded **"the kernel is not load-bound, so query tiling would buy
nothing."**

**That ablation does not support that conclusion, and I should not have drawn it.**
An all-zero mask makes every logit `-inf`, and the softmax then evaluates
`expf(-inf - -inf)`. The ablation changes the arithmetic as well as the loads, so
the two arms are not the same computation with traffic removed.

The outputs are not NaN -- the kernel guards that -- but the timing difference is
still confounded: mask-zero measured 5.56 ms against 4.63 ms here, and the expf
and softmax work on the degenerate row is a different cost profile, not a
load-free version of the same one.

**The honest statement is that the mask-zero probe is inconclusive, not that the
kernel is load-bound or load-free.** A clean traffic ablation needs a variant that
keeps the arithmetic identical while removing bytes -- the bench's own `--dtype
f32` switch is closer to that, since it doubles bytes moved without changing the
work.
