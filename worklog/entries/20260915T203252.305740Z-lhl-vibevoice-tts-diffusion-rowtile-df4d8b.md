# Diffusion head is bit-exact under rowtile but the win is noise; the stage is not GEMV-bound

## Summary

The diffusion head issues 22 GEMV calls per solver step and **every one is rows=2**
(CFG). `dense_gemv_out_kernel` tiles rows on `blockIdx.y`, so each row reads the
whole weight matrix and a rows=2 call reads it twice; the already-registered
`dense_gemv_rowtile_out_bf16` (ROW_TILE=4) reads it once. I verified the two are
**bit-identical across all 440 in-pipeline calls** at the production thread count,
then reverted the change anyway: at `_GEMV_THREADS = 64` the saving is ~1.2% of warm
synthesis, below the 1.201-1.269 run-to-run spread, so it cannot be shown to be a
win. The investigation's real value is a correction: **the diffusion stage is not
GEMV-bound**, so the "45% of its weight-traffic floor" framing was measuring the
wrong quantity.

## Changes

No code change. One immutable worklog entry.

An experimental routing of the diffusion head's `rows in [2,4]` GEMVs to
`dense_gemv_rowtile_out_bf16` (plus `'dense_gemv_rowtile_out_bf16'` in
`PRIMITIVES`) was written, verified, and then reverted with
`git checkout -- hipengine/runtime/vibevoice_tts_diffusion.py
hipengine/kernels/vibevoice.py`. The tree is clean; both files match `d4081e6db`.

## Validation

### The measurement trap that nearly produced a false 20x claim

The first A/B ran both kernels at `threads=256` and reported `(2,1536,4608)` at
2375.9 us for the GEMV against 118.0 us for rowtile -- **20.1x** -- and a per-step
total of "6.04x, saving 1.21 s". Both numbers were artifacts:

- 2375.9 us was the **first** shape measured, so it carried the first-launch module
  load amortised over only 30 iterations. Adding warmup and interleaved best-of-3
  took the same shape to 172.2 us (**1.19x**).
- `threads=256` is not what the head uses. `_GEMV_THREADS = 64`. At 256 threads and
  `in_features=1536`, `vec_stride = 256*8 = 2048 > 1536`, so `main_end = 0` and the
  vectorized 8-wide main loop executes **zero** iterations -- every element falls
  into the scalar `main_end + tid` tail loop. That is a ~10x cliff, and it is why
  the head uses 64 threads.

### Bit-exactness (verified, at the real thread count)

Two independent checks at `threads=64`:

- Isolated: `dense_gemv_out_bf16` vs `dense_gemv_rowtile_out_bf16` on all 7 shapes
  the head issues -- identical on all 7.
- In-pipeline: both kernels run into separate buffers on **every** `_gemv` call
  during one 20-step solve -- **440 calls compared, 0 mismatches.**

A first end-to-end A/B reported 62 of 64 outputs differing. That was **my test's
bug**: the "old" arm called `dense_gemv_out_bf16(..., threads=256)` while the
production path uses 64, so it compared rowtile@64 against gemv@256. The control
run (same `_gemv`, `sample_speech_tokens` twice) is bit-identical, confirming the
head itself is deterministic and the difference came from the mismatched arm.

### Why the win is not retained

Per-step GEMV totals at `threads=64`, weighted by the measured per-step
multiplicity (12x 1536->4608, 4x 4608->1536, 2x 1536->1536, 1x each of
1536->3072, 256->1536, 64->1536, 1536->64):

```
gemv    ~1.02 ms/step
rowtile ~0.92 ms/step      -> ~0.10 ms/step, ~0.05 s over 500 steps (~1.2% of warm)
```

Warm synthesis is 4.005-4.230 s across runs (pooled RTF 1.201-1.269). A 1.2%
effect is inside that spread, so it cannot be separated from noise on this host.
Landing a dispatch branch on an unverifiable win is worse than not landing it.

## Next

The correction that matters: at `_GEMV_THREADS = 64` the per-step GEMV total is
~1.0 ms against a **2.75 ms/step** diffusion stage (1.373 s / 25 frames / 20 steps),
so roughly **63% of the diffusion step is not GEMV at all**. The stage's cost is in
the elementwise/normalisation kernels (`vv_diff_rmsnorm_*`,
`vv_diff_rmsnorm_modulate_bf16`, `vv_diff_silu_bf16`, `vv_diff_add_bf16`,
`vv_diff_gated_residual_bf16`, `silu_mul_separate_out_bf16`) and/or in the
host-side launch cost of the solver loop, not in weight traffic. That is the thing
to profile next, with `rocprofv3` per-kernel counts and durations on one
`sample_speech_tokens` call, exactly as the semantic-stage entry did. Any earlier
conclusion that the diffusion stage sits "at 45% of its weight-traffic floor" should
be re-derived before it is reused.
