# the gemma4 prefill attention rate is flat, so the fix is a query tile

## Summary

The gfx1151 prefill attribution names attention as the first candidate for this
engine's falling prefill rate (271.0 tok/s at 512 against 220.0 at 2048, where
llama.cpp is flat at 1012.98 against 1067.14) because attention is the only
O(n^2) term in the route list. Measuring the kernel in isolation says that
framing is wrong, and the difference decides which fix to write.

**The rate is flat.** Sliding-window layers, at the artifact's own geometry:

| tokens | ms/launch | GFLOP/s | all 25 layers |
| --- | --- | --- | --- |
| 512 | 5.04 | 426.9 | 126.0 ms |
| 1024 | 19.01 | 452.2 | 475.3 ms |
| 2048 | 61.20 | 421.2 | 1530.0 ms |

Full layers: 604.6, 574.0, 528.2 GFLOP/s at the same three lengths. Time tracks
the FLOP count and nothing else. There is no length-dependent inefficiency in
the kernel; it is at about 1.4 percent of this part's fp32 rate at every length,
and the prefill's falling tok/s is the growing *share* of a constant low rate.

**The mechanism is the reduction, not the K/V reads.** The kernel launches one
block of 256 threads per (token, head) and runs three passes over the keys:
logits into a shared array of `keys` floats, a block max and denominator, then a
weighted sum over V. At head_dim 256 or 512 with 256 threads, pass 1 gives each
thread exactly one multiply-add per key. At 2048 tokens the sliding-window launch
is 32768 blocks over about 1536 keys each in 61.2 ms -- 1.87 us per block, 3.5
cycles per key at 2.9 GHz, for one FMA per thread. The file's own comment reaches
the same conclusion from the other side: 147 GFLOP/s before the register-tree
rewrite, 286 after, and "invariant to the work inside the key iteration".

**So the fix is a query tile**, which amortizes both the K/V reads and the
reduction tree by its height: one loaded K row then feeds R dot products, and one
warp-tree round serves R logits. Shared memory bounds the tile at R = 4 for 1024
keys (16 KB) and R = 4 for the full layers' 2048 keys at head_dim 512 (32 KB).

**The prize is smaller than the route list suggests, and the expert GEMM is the
bigger half.** At 2048 the prefill is 7.536 s: routed experts 3.070 s (40.7%),
sliding-window attention 1.530 s, full attention 0.651 s. A 4x attention kernel
takes attention from 2180.8 ms to about 545 ms and the prefill from 271.8 to 347
tok/s, which is 1.28x. It cannot close a 4.85x gap, because the routed experts
alone cost 3.070 s against llama.cpp's 1.92 s for the entire 2048-token prefill.
Attention is the shape prize; the expert GEMM is the ratio prize.

  scripts/gemma4_attention_prefill_bench.py --tokens 512 --iters 3 --warmup 1`
  and the same at 1024 and 2048. The 2048 sliding-window row reproduces the
  attribution's 2249.8 ms for the same route to within 2 percent, so the probe is
  measuring the kernel and not a wrapper.
- The bench's own all-layers total at 2048 is 4111.6 ms where the route ablation
  measured 2295 ms for the same route in situ, so the isolated bench is 1.79x
  slower than in-situ and only its scaling and rate are read here. Recorded as
  not established rather than smoothed over.
- The gfx1100 record for this kernel at 2048 is 133.02 ms for the route against
  2295 ms here, which the CU and bandwidth ratio between the parts does not
  explain. The artifact is built for this host -- the cache manifest records
  `target_arch=gfx1151`, `-O3`, `-mcumode` -- so it is not a wrong-arch build.
  Not attributed.
