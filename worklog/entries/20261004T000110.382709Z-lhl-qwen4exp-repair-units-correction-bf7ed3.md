# Correction: the repair flat-time anomaly is real but the fixed-grid mechanism was a units error

## Summary

The preceding entry (`20261003T235834.331560Z-lhl-qwen4exp-repair-fixed-grid-e11326.md`)
reported that the iu8 sparse exact repair pass dispatches a fixed 131072-block grid
and inferred a 128x over-launch worth up to 3394 ms. **That mechanism is wrong and
the 3394 ms prize derived from it does not exist.** `rocprofv3`'s `Grid_Size_X` is
**total work-items, not blocks**; the repair's real grid is 1024 blocks x 128 threads
= 131072 work-items, which is exactly the wrapper default and exactly what the source
passes to `dim3(grid_blocks)`.

The **flat-time observation survives unchanged**: the repair costs 4808.702 ms at
multiplier 4.0 and 4844.580 ms at 1.0. What is now unexplained is *why*, since the
launch geometry is proportional.

The preceding entry is committed and immutable; this one supersedes its mechanism and
its prize, and links to it rather than editing it.

## Validation

### How the error was caught

`qwen35_moe_wmma_tile_map_kernel` is launched from `group_scatter.hip:959-963` with
`dim3(1)` blocks and `dim3(threads)` threads, where
`threads = next_power_of_two_i64(512) = 512`. The same production trace reports
`Grid_Size_X = 512, Workgroup_Size_X = 512`. **A block count of 1 cannot produce
512**, so `Grid_Size_X` must be work-items.

### Independent confirmation

`scripts/qwen4exp_repair_grid_probe.py` launches the repair kernel directly under
`rocprofv3` at a known `grid_blocks`:

| `grid_blocks` passed | work-items reported | implied blocks | ratio to blocks |
| ---: | ---: | ---: | ---: |
| 1024 | 131072 | 1024 | x128 |
| 8192 | 1048576 | 8192 | x128 |

Both are `grid_blocks x 128`, matching `dim3(grid_blocks)` with `dim3(128)` threads
at `gguf_q4_k_selected_prefill.hip:2511`. The source and the runtime agree; the
earlier reading was the error.

### The open question, restated correctly

The repair kernel's grid is 1024 blocks and its inner loop is
`for (slot = blockIdx.x; slot < min(risk_count, max_risks); slot += gridDim.x)`.
The bound is proportional to `risk_count`, so the work *should* scale. It does not.

Two candidate explanations remain, and `risk_count` itself has not been measured:

1. **`risk_count` does not in fact differ 3.40x between the two multipliers on this
   production path.** The 3.40x figure came from a different harness and is the
   assumption this anomaly turns on. If the production queue depth is similar at both
   settings, there is no anomaly at all and the flat time is simply correct.
2. **The repair's cost is dominated by per-launch work that does not scale with the
   slot count** - LDS staging, the expert lookup, or the fixed prologue of each of the
   3072 launches across the window.

The deciding measurement is `scripts/qwen4exp_profile_gap.py --risk-diagnostics` at
both multipliers, which reads the queue count back per `(route, role)`. It is running.

## Next

Read `risk_count` at both multipliers. If the counts differ ~3.40x and the time still
does not move, explanation 2 is live and the target becomes the per-launch fixed cost
of the repair kernels. If the counts are similar, the anomaly was never real, the
multiplier change is simply neutral, and this whole line closes - in which case the
repair's 4808 ms stands as a cost to attack on its own terms, not as a
launch-geometry question.

Do not build anything on the withdrawn mechanism in the meantime.
