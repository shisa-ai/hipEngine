# Gemma 4 GGUF cross-checked against llama.cpp and the thinking-mode trap

## Summary

Cross-checks the Gemma 4 GGUF port against a second independent implementation.
llama.cpp and hipEngine render the chat template to the same 23-token prompt and
choose the same first token on three prompts. Getting there required finding a
template trap that changes which of two valid prompts you get.

## The trap

The Gemma 4 chat template ends with:

```jinja
{%- if add_generation_prompt -%}
    {%- if ns.prev_message_type != 'tool_response' and ns.prev_message_type != 'tool_call' -%}
        {{- '<|turn>model\n' -}}
        {%- if not enable_thinking -%}
            {{- '<|channel>thought\n<channel|>' -}}
        {%- endif -%}
    {%- elif ns.prev_message_type == 'tool_response' and enable_thinking -%}
        {{- '<|channel>thought\n' -}}
    {%- endif -%}
{%- endif -%}
```

``enable_thinking`` is read as a bare Jinja variable, so **leaving it undefined
is not neutral** — undefined is falsy, so the template appends a closed empty
thinking channel and the model is forced to answer immediately. The two modes
differ by three tokens:

| ``enable_thinking`` | Tokens | Rendered tail |
| --- | --- | --- |
| ``True`` | 23 | ``<|turn>model\n`` |
| ``False`` / undefined | 20 | ``<|turn>model\n<|channel>thought\n<channel|>`` |

Thinking-on additionally injects a leading ``<|turn>system\n<|think|>\n<turn|>``
turn, which is where the other three tokens come from.

The first real-artifact probe in `20260922T111825.967815Z-lhl-gemma4-3a56c8`
omitted ``enable_thinking``, so its results are the thinking-suppressed mode.
Those results stand, but they are not the mode llama.cpp defaults to and they
are not what a user asking a hard question would get. Any serving path that
renders this template must pass ``enable_thinking`` explicitly.

## Changes

- `scripts/gemma4_llamacpp_compare.py`: renders the thinking-on prompt, runs the
  streaming forward, and writes the top-k distribution per prompt so it can be
  compared against llama.cpp on an identical token sequence.

## Validation

Two independent implementations, same artifact
(`UD-Q4_K_XL`), same 23-token prompt:

| Prompt | llama.cpp greedy | hipEngine top-1 |
| --- | --- | --- |
| Say hello in one short sentence. | `<|channel>thought` | `<|channel>` (id 100) |
| What is the capital of France? | `<|channel>thought` | `<|channel>` (id 100) |
| What is 2 + 2? | `<|channel>thought` | `<|channel>` (id 100) |

llama.cpp's continued greedy output is coherent reasoning: `The user is asking
for the capital of France`, `The user is asking a simple arithmetic question:`.

The prompt token count is the check that the render matches: hipEngine renders
23 tokens with ``enable_thinking=True`` and llama.cpp's ``--jinja`` path reports
23, and the rendered strings are byte-identical.

Build and invocation:

- `~/beellama.cpp` at `v0.2.0` (`c6dfa39e3`), CPU build in `/tmp/beellama-build`
  and HIP build in `/tmp/beellama-hip`. Both are outside the repo, so they are
  not tracked.
- The HIP build runs this model; the CPU build aborts in
  `ggml_compute_forward_scale` because `src0->type` is not `GGML_TYPE_F32`. That
  is a defect in the fork's CPU path, not in the artifact — the same artifact
  loads and generates correctly on the HIP build.
- llama.cpp's `-rea off` / `--reasoning off` does **not** change the template
  render; the prompt stayed 23 tokens. Use `enable_thinking` in the render call
  rather than a CLI reasoning flag when comparing renders.
