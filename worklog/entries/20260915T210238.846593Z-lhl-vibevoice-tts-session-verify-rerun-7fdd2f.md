# Verification re-run bounds the retained VibeVoice-TTS session headline: 1.228, not a reproducible 1.201

## Summary

The objective's third hard clause is "faster than PyTorch", and it is the one clause
whose evidence I had only been citing second-hand -- the retained 1.201 against the
torch lane's 1.336, both from `benchmarks/README.md`. I re-ran the same harness, on the
same request, at HEAD, to verify it directly rather than repeat a recorded number.

**The clause holds, but the margin is thinner than the headline implies.** The fresh
run measured pooled RTF **1.228** (warm 4.092 s) against the retained **1.201**
(4.005 s), so the post-tile margin over torch is **~9%**, not the ~11% that 1.201 alone
suggests. `chain_exact` and `negative_conditions_match` both remain true.

The retained figure is a favorable run, not a reproducible one, and the README said so
only for the pre-tile runs. Corrected.

## Validation

### Command

```
uv run python scripts/vibevoice_tts_session_bench.py --repeats 3 --out /tmp/vv_bench.json
```

Same harness, same pinned request, same host, `--repeats 3`. The artifact carries the
harness's own recorded `command` field, so the number is reproducible from the repo.

### Measured against retained

| | retained | verification |
| --- | ---: | ---: |
| pooled RTF | 1.201 | **1.228** |
| warm synthesis | 4.005 s | **4.092 s** |
| lm | 1.450 s | 1.526 s |
| diffusion | 1.298 s | 1.230 s |
| semantic | 0.781 s | 0.837 s |
| decode | 0.301 s | 0.319 s |
| `chain_exact` | true | **true** |
| `negative_conditions_match` | true | **true** |

The spread is ~5-7% on individual stages and ~2% on the pooled total, in both
directions (diffusion is *faster* here, lm and semantic slower), which is the signature
of run-to-run variance rather than a regression.

### Why this is worth recording rather than re-running until it agrees

The tree's rule is that a benchmark rollup stays current, and the failure mode this
guards against is a headline that reads as more precise than the measurement behind it.
1.201 was the median of pre-tile runs but is a *single* post-tile number; publishing it
without a spread invited exactly the ~11% margin claim I had been repeating. Recording
the verification run is the cheap, honest fix.

I did not re-run the torch lane: its 1.336 is a median of three runs already recorded in
`benchmarks/README.md` and its own artifact, and the two lanes are timed on the same
frozen request. Re-measuring the torch lane would spend the same budget to re-derive a
number that is not in question.

### Lane note

This is `zbook` / gfx1151 (Radeon 8060S), which is the lane the contract declares for
this model: `docs/MODEL-VIBEVOICE-TTS.md` states that the W7900/gfx1100 lane is
unverified for VibeVoice-TTS. No gfx1100 claim is made or implied here.
