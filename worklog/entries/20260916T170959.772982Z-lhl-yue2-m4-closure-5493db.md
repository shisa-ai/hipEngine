# YuE2 M4 closure: NAR solver parity across chunk boundaries and visibility limits

## Summary

M4's device-parity contract is met. The torch-free NAR runtime
(`hipengine/runtime/yue2_nar.py`) matches the pinned upstream flow-matching
solver on three independently recorded cases: the release chunk, a song crossing
a real chunk boundary, and a restricted-visibility case. Every chunk of every
case passes both its teacher-forced velocities and its own solved trajectory.

The two new cases found two real defects that the single release chunk could not
expose, both now fixed.

## Defects found and fixed

1. **Stale midpoint boundary rows.** `load_state` staged the ODE state but not
   the midpoint buffer. `nar_state_update_kernel` writes only the content rows,
   so `_mid`'s boundary rows kept whatever an earlier, longer chunk had left
   there. Equal-length chunks were unaffected - their boundary rows stayed zero
   from allocation - which is exactly why the single-chunk release case never
   showed it. The last, shorter chunk of the multi-chunk song evaluated its
   midpoint against stale values and its solved latents landed **0.16667**
   relative L2 from the reference; writing both padded buffers takes it to
   **0.01071**. This was a regression introduced when `_write_state` was
   refactored into `load_state`; the original wrote both buffers.

2. **hipBLASLt problems prepared only for the buffer tile.** Buffers are sized
   for the largest chunk seen, so a later, shorter chunk keeps the older `_tile`
   and launches with its own row count. `_prepare_gemm` built keys for `tile`
   only, so chunk 3 (20 rows against a stale 28-row tile) raised
   `KeyError: (20, 2048, 1024)`. It now prepares every row count the solver will
   actually launch with, which is at most two values per chunk.

## Changes

- `hipengine/runtime/yue2_nar.py`: `load_state` writes the padded midpoint buffer
  as well as the state; `_prepare_gemm` prepares the actual per-tile row counts
  and all of that count's key shapes (latent/hidden, hidden/latent, Q, K/V, gate,
  up, down).
- `scripts/yue2_oracle.py nar`: records the whole-song noise draw (`song_noise`)
  instead of only the chunk's view, since the gate rebuilds the chunking from it;
  `FIXTURE_FAMILIES` gains the two new families.
- `tests/fixtures/yue2/nar-multichunk/`, `tests/fixtures/yue2/nar-condend/`: new
  recorded cases, both with zero replay residual; `integrity.json` refrozen.
- `tests/test_unit_yue2_fixtures.py`: the two families registered.
- `benchmarks/README.md`, `benchmarks/CHANGELOG.md`: rows for the new cases.

## M4 status

Complete. Deliverables: cached AR conditioning (`condition` prefills one chunk's
AR prefix once and keeps its per-layer K/V as the NAR conditioning keys),
bidirectional NAR attention over cached-AR plus live-NAR keys, timestep and
position features, and the device midpoint loop with the reference's own BF16
rounding. Exit condition ("per-step/chunk fixtures pass, including a request
crossing a real chunk boundary") is met by the multi-chunk case above; the
non-default `nar_cond_end` visibility behaviour is frozen by its own case.

Not claimed: throughput. The NAR attention kernel is ~1.03 ms per call on this
host and is the obvious M7 target.
