# The Q5_1 pack8 selected GEMV lifts decode 15.9 percent

## Summary
The selected-GEMV dispatcher prefers an eight-output-per-block variant wherever
one is registered, and Q4_K, Q5_K, Q6_K and Q8_0 all registered one. **Q5_1 did
not**, so gemma4's expert down projection -- the Q5_1 tensors -- silently took
the scalar one-output-per-block fallback while the Q4_K gate/up on the same
layer took the eight-output shape. Registering the sibling measures **decode
21.48 -> 24.89 tok/s (+15.9%)** at unchanged prefill.

## The gap
`gemma4_project_experts_selected` resolves `_SELECTED_PACK8_VARIANT`
(`selected_pack8_gemv_bf16_bf16_out`) first and falls back to
`_SELECTED_VARIANT` (`selected_gemv_bf16_bf16_out`) when it misses, guarding on
`out_features % 8 == 0`. Both keys exist for Q4_K, Q5_K, Q6_K and Q8_0. For Q5_1
only the scalar one did, so `resolve_variant` returned None and the fallback ran.
The eight-output shape reads the x row once per eight outputs and pays the block
reduction once per eight outputs instead of once per one.

## Why it is a replacement and not a candidate
The k walk (`column = tid; column += blockDim.x`), the per-element dequant and
the reduction tree are properties of an **output**, not of the block, so the
pack8 kernel reproduces all three per output: the same `dequant_q5_1`, the same
strided halving from `blockDim.x / 2` down to 32, and the same warp shuffle over
offsets 16..1.

It deliberately does **not** borrow the Q4_K pack8 tree. That one reduces within
each warp and then sums the per-warp partials, which is a different association
order and would have made this a numerical candidate against the route it
replaces rather than a drop-in. Measured against the scalar owner at the real
down-projection geometry (out 2816, in 704, 4 experts, 8 rows), the outputs are
identical **as bf16 bit patterns**, not merely close.

## Shape constraints
`in_features` must be a multiple of 32 (gemma4's down width is 704 = 22 x 32) and
`out_features` a multiple of 8 (2816 = 352 x 8). 704 is a multiple of 32 but not
of 256, which is why the existing `logical256` Q5_1 variants are not an answer
for this model. A width failing either guard is an error from the launcher rather
than a silent tail, so the dispatcher's own `out_features % 8` check falls back
to the scalar route.

## The route did run, and establishing that took a correction
A first instrumented `LLM.generate()` reported **zero** launches of both Q5_1
variants while the route counter said `selected_gemv: 944`. That looks like the
route never ran. It had: the weight's backend is `hip_gfx1151`, which the
registry aliases to the `hip_gfx1100` tree, so a probe that instruments the
literal `hip_gfx1100` key counts nothing. Instrumenting the key the dispatcher
actually resolves gives **pack8 464 launches, scalar 0** on the real artifact.
Recorded because the failure mode is silent and the wrong conclusion is the
comfortable one.

## A latent fixture defect the registration exposed
`test_rows_keeps_the_selected_gemv_below_one_lane_per_expert` registered a
recording lambda for the scalar selected key only, then called the rows router
with **placeholder pointers** `0x1000`/`0x2000`/`0x3000`/`0x4000`. While Q5_1
had no pack8 sibling the dispatcher fell to the lambda and nothing launched.
Registering one made the dispatcher prefer the real kernel, which launched on
those pointers: `HSA_STATUS_ERROR_MEMORY_FAULT` in
`q5_1_selected_pack8_gemv_bf16_bf16_kernel`, faulting addr `0x4000` -- literally
the placeholder. Reproduced by running `tests/test_unit_gemma4_contracts.py`
before `tests/test_unit_gemma4_expert_route.py`, bisected to that pair; the file
alone passed. Both router fixtures now pin both selected variant keys.

This is a fixture defect, not a kernel defect, and it is the general hazard: a
fixture that pins one variant stops pinning the route the moment a quant gains a
sibling, and these fixtures pass placeholder pointers.

## Changes
- `hipengine/kernels/hip_gfx1100/quant/qwen4_exp_q5_1.hip`: adds
  `q5_1_selected_pack8_gemv_bf16_bf16_kernel` and its launcher.
- `hipengine/kernels/hip_gfx1100/quant/qwen4_exp_q5_1.py`: adds the wrapper and
  registers it under `selected_pack8_gemv_bf16_bf16_out` on both `linear` and
  `moe_linear`.
- `tests/test_unit_gemma4_expert_route.py`: adds the Q5_1 down-projection
  geometry to the bit-exactness cases, adds the vacuity guard that the two
  variant keys resolve to different functions, and fixes the two router fixtures.
- `benchmarks/results/2026-09-28-gemma4-q5-1-pack8-selected-gemv-accepted.json`.

No new flag: the shape is selected by a preference that already existed for every
other quant, so there is no new default to roll back.

  passed including the new Q5_1 case.

- Production path: in a fresh process with no manual registration,
  `KernelKey(hip_gfx1151, linear, gguf_q5_1, selected_pack8_gemv_bf16_bf16_out)`
  is registered and resolves to the new kernel, and a real `LLM.generate()` took
  it 464 times and the scalar route 0 times.
- `scripts/gemma4_campaign_bench.py --prompt 512 --output 128 --samples 3
  --warmup 1`: decode 24.95/24.85/24.88 tok/s, prefill 1.01/1.00/1.01 s, public
  path parity True.
- No correctness gate is owed beyond the bit-exactness comparison: the route is
  bit-identical to the one it replaces, so it is not a changed-arithmetic path.
