# Task 43 results: the admission window is worth 1.36-2.07x, and AR does not care about it

## Summary

`bg-240` produced the first valid autoregressive baseline for task #39, from two
independent sources that agree to 0.02 tok/s. With a real denominator, raising
the MTP admission window from the qualified 1,023 tokens to 8,192 is worth
**1.36x-2.07x decode** across 517-6,972 prompt tokens at 0.992 MTP coverage.
At the shipped window the benefit is 1.69x at 517 tokens, decays to 1.53x by
945 as coverage falls to 0.602, and disappears entirely at 1,804+.

The run also settled two open questions from the earlier attempts.

**The request field does disable MTP.** `{"speculative_mtp": false}` on an
MTP-enabled server produced `effective_route = None` and 11.90 tok/s at 6,972
tokens, matching a `--speculative-mtp-serving off` server's 11.90 exactly. So
the task-39 arms can share one server process after all, which removes
process-to-process variance from the pair.

**The window does not change autoregressive speed.** AR at window 8,192 and AR
at window 1,023 agree to 0.02 tok/s at every shape. That retires the confound
that made the `bg-238` numbers unusable: with AR flat across the window, the
difference between a default-window and a raised-window run is MTP, not a
window effect on the baseline.

## Status of this claim

Diagnostic, **not retainable**. It is one synthetic prompt per shape with two
repeats, not the full multi-prompt mtp-bench category suite
(`benchmarks/prompts/mtpbench-code-general-ja.jsonl`, all of
`code`/`general_en`/`general_ja`/`mixed_ja_en`) plus category-heldouts, so per
`docs/BENCHMARK.md` "Anti-gaming" it cannot be published as an MTP speedup.
Token identity between the MTP and AR arms was not probed either
(`--identity-tokens` was not passed), so the greedy-equivalence property is
unverified here.

What it does establish is that the window is the binding constraint and that
the effect is large enough to be worth a proper category-suite run, which is
now a well-posed question with a known expected shape rather than a hunt.

## Changes

- `scripts/gguf_mtp_server_pair_bench.py` - `route_satisfies()` makes the arm
  contract semantic instead of a string comparison. Autoregressive decoding has
  two representations and both are legitimate: a server that considered MTP and
  fell back reports `effective_route="default"`, while a server whose MTP is off
  for the process or whose request disabled it reports no route decision at all
  (`None`). The first version of `--expect-route` accepted only `"default"` and
  therefore false-failed both AR arms of this very run, even though both had
  genuinely run autoregressively. A run showing speculation activity
  (`mtp_used` true, or any `speculative_cycles`) never satisfies an AR arm, so
  the duplicate-route failure stays caught.
- `tests/test_unit_gguf_mtp_server_pair_bench_acceptance.py` - the
  missing-route case is now the AR-representation case, plus an explicit
  `backend_k0_fallback` row and two speculation-accounting rejections.

## Validation

- `uv run pytest tests/test_unit_gguf_mtp_server_pair_bench_acceptance.py -q` -
  exit 0.
- Guard checked against real artifacts rather than synthetic rows only:
  - `mtp-w8192.json` as `--expect-route speculative_mtp` -> PASS
  - `mtp-w8192.json` as `--expect-route default` -> REJECT (15 mismatches)
  - `bg-238`'s duplicate "AR" arm as `--expect-route default` -> REJECT (6
    mismatches), which is the exact failure the guard exists to catch
  - `bg-238`'s "MTP" arm as `--expect-route speculative_mtp` -> REJECT (9
    mismatches), correctly reporting that it fell back to AR at 1,804+
- `bg-240` arm log: `ar-request-w8192 exit=3` and `ar-off-w1023 exit=3` - the
  harness refused to write both artifacts, so the false-fail was loud rather
  than a silently missing denominator. `mtp-w8192` passed and wrote its
  artifact.
