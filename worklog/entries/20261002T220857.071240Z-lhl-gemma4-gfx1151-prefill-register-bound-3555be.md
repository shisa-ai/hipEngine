# gemma4 gfx1151: the prefill attention kernel is register-starved at the 256-VGPR ceiling, and that is why it is at 4 percent of every roofline

## Summary

The campaign's objective is to sustain the roofline limits. The decode walk reaches
82.1% of DRAM; the prefill attention kernel sits at 4.0% of DRAM, ~1% of the BF16
tensor rate, and 0.47% of the nominal instruction-issue capacity, while reporting
100% SQ-busy. This entry says why, and it is one number.

**`arch_vgpr_count` is 256** -- the wave32 architectural ceiling -- with a 32-byte
private segment, so the kernel spills. At 256 VGPRs per lane a wave occupies 32 KB
of the SIMD's 64 KB register file, so **at most two waves are resident per SIMD**.
A latency-hiding kernel wants eight to sixteen. The sequencer therefore reports
busy because a wave is present, but it issues into a wave that is waiting on
memory or on the matrix unit, with nothing else to switch to.

That single fact explains all four observations at once:

| observation | explanation |
| --- | --- |
| 100% SQ-busy, 0.60 instructions per SQ-cycle | the wave is resident, so the SQ counts busy, but it stalls |
| 4.0% of DRAM | two waves per SIMD is not enough outstanding traffic to saturate memory |
| ~1% of the BF16 tensor rate | not enough concurrent waves to keep the matrix units fed |
| 0.47% of nominal issue capacity | 139.6M instructions in 75.3 ms on 160 SIMD slots at 2.48 GHz |

## Where the registers go

The source already documents the first half: a wave owns `(columns it owns) *
(dimensions it owns) / 32 lanes` accumulator floats, and at `dim_groups = 2` that
is `16 * 256 / 32` = **128 accumulator floats per lane**, chosen deliberately
because the unsplit shape needs 256 and "cannot compile without spilling".

The kernel still lands at 256 VGPRs, so the other ~128 are fragments, the
score/max/sum state, and addressing. The accumulator is half the budget and it is
the half that is parameterised.

## The obvious fix is measured and it is worse

`GEMMA4_WMMA_FULL_DIM_GROUPS = 4` halves the accumulator to 64 floats per lane.
Measured on the same probe, 65,536 keys, 256 tokens, one full layer, three runs:

| dim_groups | ms | unique GB/s | % of roofline |
| --- | --- | --- | --- |
| **2 (shipped)** | **75.31** | 956 | 401% |
| 4 | 99.90 | 688 | 288% |

**1.33x slower**, and reverted. The reason is the trade the source also documents:
the waves sharing a column group each need the full head_dim score for those
columns, so the score dot is issued once per dimension group. At 2 that is the
"1.5x the ideal WMMA count"; at 4 it is 2.5x. The extra issue costs more than the
occupancy gains.

So **the dimension split is not the lever**, even though it is the parameterised
one. Any fix has to cut registers without duplicating the score dot.

## What is left, and it is a real design problem

The column axis is the free one -- the source calls it "a free tiling axis: a
wider block re-reads the same K/V, a narrower one re-stages it", and widening it
would cut the staging work that is 33.6% of the instruction count. But it is
blocked twice over:

- The Q tile is `columns * 520 * 2` bytes of LDS, and `(columns + K_BATCH) * 520 *
  2 <= 65536` (verified against the device: `sharedMemPerBlock` is 65,536) caps
  `columns` at 32 with `K_BATCH` 16. Dropping the eight-element padding buys
  nothing useful; the ceiling is real.
- The accumulator grows with columns, so widening the block makes the register
  problem worse rather than better.

The two constraints pull against each other: columns want to be wide for staging
efficiency and narrow for registers, and the dimension split that would decouple
them costs a duplicated score dot. That is the shape of the problem, and it is not
solved here.

## Changes

- None. The `dim_groups = 4` experiment was applied, measured, and reverted; the
  tree is unchanged (`GEMMA4_WMMA_FULL_DIM_GROUPS` is back to 2).

## Validation

- Register and segment counts read from `rocprofv3`'s own
  `rocpd_info_kernel_symbol` table for the shipped kernel, not from a compile log.
- Instruction mix from `rocprofv3 --pmc` on the shipped kernel, 65,536 keys, 256
  tokens: VALU 64,850,384 (46.4%), LDS 46,935,839 (33.6%), SALU 19,126,438
  (13.7%), BRANCH 6,298,035 (4.5%), FLAT 2,408,308 (1.7%), 139,619,200 total in a
  75.31 ms dispatch.
- The `dim_groups` A/B is three runs per arm on `scripts/gemma4_prefill_kernel_bw.py`
  with identical buffers, and the revert was verified by re-reading both files.
- `sharedMemPerBlock` 65,536 read from `hipGetDeviceProperties` on this device.

## Next

- **Cut registers without duplicating the score dot.** The accumulator is 128
  floats/lane; the candidates are holding the score tile in a narrower form, or
  restructuring so a wave owns fewer output dimensions without a second wave
  needing the same score. Neither is designed.
- The staging is 33.6% of the instruction count and happens once per query-head
  tile -- four times per KV head at `gqa_heads = 2`. It is served by L2 (DRAM
  fetch is 1.0x the band) but the *instructions* are still spent.
- `docs/ROOFLINE.md`'s decision tree still does not branch on registers, which is
  the binding resource here.
