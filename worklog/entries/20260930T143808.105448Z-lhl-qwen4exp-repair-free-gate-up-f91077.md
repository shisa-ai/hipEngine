# The repair-free gate/up configuration is a registered gate candidate, and the decisive run is launched

## Summary

The previous unit established that the production repair is a **bit-parity** mechanism
and that the ledger's largest lever (1,219.978 ms = 7.75% of the prefill union) may be
reachable as a **configuration** rather than the multi-day F16 kernel build MX-1
assumed. This unit turns that into a runnable gate candidate and starts the run.

**The candidate.** Added `repair_free_gate_up` to `CANDIDATES` in
`scripts/qwen4exp_layer2_profile_gate.py`:

| setting | value | why |
| --- | --- | --- |
| `HIPENGINE_QWEN4_EXP_EXACT_GROUPED_Q4` | `0` | clears `exact_grouped_q4_gate`, which the dispatch tests **before** the `q4_iu8` branch, so the plain iu8 owner becomes selectable |
| `HIPENGINE_QWEN4_EXP_Q4_IU8_PREFILL` | `1` | already production, but only reachable once the branch above yields |
| `HIPENGINE_QWEN4_EXP_Q4_IU8_LAYERS` | `all` | production binds this to **35-47** while the repair route carries **no layer restriction**; widening covers exactly the scope the repair currently serves |

`base_profile="production"`, `candidate_key=("hip_gfx1151", "moe_linear", "gguf_q4_k",
"selected_dual_wmma_iu8_prefill_bf16_bf16_out")`, `fallback_key=(..., 
"selected_dual_wmma_prefill_compact_bf16_bf16_out")`, `count_registered_dispatch=True`.

**Q5_1 down is deliberately left at production.** There is no plain non-risk iu8
sibling for it, so changing it would swap the fast iu8 route for the slower bit-exact
logical256 owner and confound the measurement. This run isolates the **gate/up** half:
573.211 ms of the repair.

## Changes

- `scripts/qwen4exp_layer2_profile_gate.py` — the `repair_free_gate_up` candidate,
  documented in place with the branch-order and layer-scope reasoning.

## Validation

- **The candidate is registered and reads back correctly** (30 candidates total),
  verified by importing the gate module and printing the spec.
- **Both dispatch keys resolve under `hip_gfx1151`** — verified by importing
  `hipengine.kernels.hip_gfx1100.quant.gguf_q4_k_selected_prefill`, registering the
  gfx1151 backend, and resolving both variants. This check also explained a false
  negative: the variants resolve only after that module is imported, because the
  gfx1151 backend aliases every key registered under gfx1100 (minus an exclusion list)
  and the module is not in `_GFX1100_MODULES` by name. Neither variant appears in
  `_GFX1151_ALIAS_EXCLUSIONS`.
- **The gate refuses to run on a dirty tracked tree** — it failed its first launch with
  "profile qualification requires a clean committed tracked tree", which is why this
  entry and the harness change are committed before the run. Good behaviour; recorded
  because it is the reason the first launch attempt produced no measurement.
- **ROCm confirmed alive** for the run: `libamdhip64.so` loads once `LD_LIBRARY_PATH`
  includes `$($PY -m rocm_sdk path --root)/lib` (the bare `python3 -c "import ctypes;
  ctypes.CDLL('libamdhip64.so')"` from the playbook fails on this host without it).
- **No measurement yet.** The gate was launched and is running; nothing is claimed
  about its result.

## Next

- Read `benchmarks/results/2026-09-30-qwen4exp-repair-free-gate-up/gate.json` when the
  run lands. The decision turns on the **envelope** (mean/p95/p99/max KL, top-1,
  determinism, isolation, task gate) and on **engagement**: `candidate_dispatch_calls`
  must show the plain iu8 owner running on all layers and the repair kernels absent.
  The DP-8 lesson applies — a route the harness cannot see is not a measured route.
- If the envelope passes, the gate/up half of the repair (573.211 ms) is banked and the
  remaining work is a plain sibling of `q5_1_selected_wmma_iu8_risk_prefill_kernel` for
  the down leg (661.210 ms), which is a small build on an existing body.
- If it fails, the failure mode decides the next move: a broad-based envelope miss
  points at the iu8 arithmetic itself and returns the campaign to MX-1's F16 port; a
  tail-only miss invites a layer-scoped variant of this same configuration.
