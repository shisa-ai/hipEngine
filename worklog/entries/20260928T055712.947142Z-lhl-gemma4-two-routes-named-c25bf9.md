# the two expert routes are grouped_prefill and selected_gemv behind one shared threshold

## Summary

The two arithmetic families that disagree (`20260928T055408`) are now named.
`gemma4_project_experts_rows` carries its own preference order, and the one that
matters is the first two entries:

1. **`grouped_prefill`** -- *"one launch per (expert, out_col) that reads the
   expert's weight row once and reuses it across that expert's rows. Only when
   the block has at least one row per expert and the weight's quant key
   registers a grouped family."*
2. `pack8_selected` -- the same selected GEMV over a packed layout.
3. **`selected_gemv`** -- *"one block per (out_col, lane), one weight read per
   lane, over the raw blocks."*
4. `per_expert_offset` -- the fallback.

Entry 1 requires at least one row per expert, so the switch is
`compact_rows >= num_experts`; below it, entry 3 runs. That is the **same
threshold and the same condition** as `gemma4_moe_prefill_route_enabled`
(`lanes >= _PREFILL_MIN_LANES_PER_EXPERT * num_experts`), in a second place.

## What that makes the forced-route experiment

`20260928T055408` forced `_PREFILL_MIN_LANES_PER_EXPERT` to 0 and to 1e9 and
found each configuration internally consistent with the two disagreeing. With
the preference order read, those two configurations are:

| forced setting | `gemma4_moe_prefill_route_enabled` | resulting projection route |
| --- | --- | --- |
| 0 (on) | True | `grouped_prefill` |
| 1e9 (off) | False | `selected_gemv` |

So the disagreement is **`grouped_prefill` against `selected_gemv`**, and the
`grouped_prefill` side is the one that reads each weight row once and reuses it
across the expert's rows -- which is the structure that cannot contaminate rows,
matching `20260928T055550`'s finding that this side is the invariant one.

## The suspect, and why the census agrees

`selected_gemv` is *"one block per (out_col, lane)"* -- the per-lane geometry
whose lanes were shown not to be independent. The census names a
`grouped_row4` variant, and that variant is the Q4_K member of the
`selected_gemv` family, so the kernel to fix and the kernel the census points at
are the same one.

## Why the earlier reading was incomplete

`20260928T055550` attributed the divergence to a crossover in
`gemma4_moe_prefill_route_enabled` and treated that function as the switch.
There are two switches with the same condition, and the inner one
(`gemma4_project_experts_rows`'s preference order) is the one that actually
selects the arithmetic. Forcing only the outer one happened to move both,
because the condition is shared, which is why the experiment was still decisive
about *which side* is wrong even though it named the wrong mechanism for the
switch.

That also means there is no single gate to change: making the routes agree
requires the arithmetic to be fixed, not a threshold moved.
