# Post-merge working baseline on gfx1151: cache A/B and served AR/MTP arms

## Summary

A fresh baseline on the merged tree (`19f2dd45e`, "merge: integrate upstream
prefix caching with local MTP fixes"), so the MTP latency work that follows has
a same-host reference instead of the pre-merge numbers it was carrying. Six
runs: the upstream in-process cache A/B on two models, and the live served path
with cache off and on, an AR control and a speculative arm inside every load, at
c=1 and c=4, plus a cancellation load.

The cache side reproduces the merge screening rows on this host, which is the
useful part: the MoE 35B all-lane arm measures **28.19 -> 33.88 tok/s
(-16.8% wall, 16/27 hits, 42,496 reused tokens)** against the screening run's
28.15 -> 33.48 at identical turn and token counts, and dense 27B code lanes
measure **5.64 -> 7.35 tok/s (-23.3% wall, 9/18 hits, 39,168 reused tokens)**
with median prefill 6,362 -> 2,953 ms.

The served side, measured per request with the AR control in the same load:
rows that used MTP decode at **25.34 tok/s against the control's 12.27 (2.07x)**
with median ITL **82.8 -> 40.1 ms**, and the matched per-turn medians favour the
speculative arm at every turn (12.4/28.6, 12.3/24.6, 12.2/25.4, 12.1/16.1 tok/s
for control/speculative). At c=4 that advantage is gone — **9.59 against 9.30
(1.03x)** with ITL 108.9 against 110.2 ms — while the load aggregate rises to
21.65 tok/s, so concurrency buys the aggregate and the route adds nothing per
request on this load. Warm prefix hits do not use MTP at all: on the radix
server only 2 of 8 speculative-arm rows engage and both are misses, while all
six hit rows refuse with `no_provider`; at c=4 no hit row engages and the
speculative lane loses coverage to activation (2 of 6 rows, 635 `no_provider`
events) rather than to group width, since every realized group in all five loads
is one row.

Two smaller results matter for the queue. Served diagnostics are populated on
the merged tree — `fallback_reason`, `effective_route`, `policy_reason`,
`k0_class` and `mtp_used` all carry values on the speculative arm, where the
pre-merge rows reported nulls — so task #27 is a gap-filling exercise (provider
readiness and realized group width), not a plumbing build. And the cancellation
load completes safely: 10 requests, 2 cancelled after their first tokens, 0
failures, MTP active in the same load.

**Correction made in this unit, kept deliberately.** The first pass of this
baseline reported the harness's per-arm `decode_tokens_per_second` as a
throughput-parity result (76.50 against 74.84 tok/s). That field divides a
group's tokens by its longest request duration (`wall = max(e2e_ms)`), and with
per-conversation arm assignment both arms' rows are spread across the whole load
(13.4 against 13.7 s), so it reports nearly the same value for both arms by
construction and cannot compare them. The 1.90x sampled-accept row of
2026-09-19 used the same field legitimately because that protocol assigned the
arm per request in consecutive pairs, where the span is each arm's own. The
artifact now derives the per-request rate from the rows, and the retraction is
recorded in its findings so the trap is not repeated.

## Validation

- Cache A/B, dense 27B code lanes (6 lanes x 3 turns), cache off then radix:
  18 turns per arm, 0 hits -> 9 hits / 18 lookups, 39,168 reused tokens,
  wall 408.8 -> 313.6 s, output 5.64 -> 7.35 tok/s, median prefill 6,362 ->
  2,953 ms.
- Cache A/B, MoE 35B all lanes, cache off then radix: 41 turns per arm, 0 -> 16
  hits / 27 lookups, 42,496 reused tokens, wall 211.1 -> 175.7 s, output
  28.19 -> 33.88 tok/s, median prefill 667 -> 218 ms. This reproduces the merge
  qualification's screening arms (28.15 -> 33.48 tok/s, same 41 turns and token
  counts) on the same host and protocol.
- Served arms, dense 27B, `--route-mix off,auto` in every load, 0 failures and 0
  cancelled rows in all five loads (16/16, 12/12, 16/16, 12/12, 10 completed + 2
  cancelled). Per-request decode rate is the median of
  `completion_tokens / ((e2e_ms - ttft_ms) / 1000)` over rows, split by arm and
  by whether the row used MTP:
  - cache off c=1: MTP rows 25.34 against AR rows 12.27 tok/s (2.07x), ITL 40.1
    against 82.8 ms, TTFT median 2,254 against 1,838 ms, 7 of 8 speculative rows
    engage (887 of 2,048 output tokens from MTP), acceptance 0.602, one
    `target_context_k0` refusal on the 1,023+ prompt bucket. Load wall rate
    12.34 tok/s over 165.9 s.
  - cache off c=4: MTP rows 9.59 against AR 9.30 (1.03x), ITL 108.9 against
    110.2 ms, 2 of 6 rows engage, 635 `no_provider` events, load wall rate
    21.65 tok/s.
  - cache radix c=1: MTP rows 28.46 against AR 12.21 (2.33x, two rows), ITL 35.7
    against 83.2 ms; 12 of 16 requests hit the prefix cache, 2 of 8 speculative
    rows engage (both misses) and all six speculative-arm hit rows refuse with
    `no_provider`. Median TTFT 1,271 ms (hits 1,327, misses 1,152).
  - cache radix c=4: MTP rows 9.34 against AR 9.12 (1.02x), 6 of 12 hits, no hit
    row engages; hits reach first token faster than misses (6,178 against
    9,252 ms median). Load wall rate 22.75 tok/s.
  - radix c=4 cancellation: 10 requests, 2 cancelled after 4 tokens, 0
    failures, 2 speculative rows with 234 MTP tokens.
  - Every realized group in all five loads is one row
    (`groups_by_realized_rows` has the single key `"1"`).
- Prometheus: MTP acceptance 0.602 (652/1,083 drafts) cache off and 0.672
  (411/612) radix; `hipengine_mtp_serving 1` in both; KV-pool high water 2.40 ->
  2.52 GB, and the radix server records 17 `grow_failures_total` with 0 grow
  events and no request failures (the off arm records 0).
