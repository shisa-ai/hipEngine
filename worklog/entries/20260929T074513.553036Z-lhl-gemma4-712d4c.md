# Gemma 4: split P3 into a routing defect and a missing leaf, fix the down

## Summary

Punchlist P3 (layer 29's experts have no fast owner, ~60 ms / +13%) asked for
Step 1 first: decide whether the cause is *routing* or a *missing leaf*. It
turns out to be both, one half each, and the two halves need completely
different work.

**Down (Q8_0) — routing, now fixed.** `gemma4_project_experts_wmma` resolves

```python
KernelKey(weight.backend, "moe_linear", weight.spec.quant_key,
          "selected_grouped_wmma_prefill_compact_bf16_bf16_out")
```

Resolving that key directly, before the change:

| layer axis | quant | result |
| --- | --- | --- |
| `moe_linear` | `gguf_q5_1` | `qwen4_exp_q5_1_selected_grouped_wmma_prefill_compact_bf16_bf16_out` |
| `moe_linear` | `gguf_q8_0` | **`MissingKernelError`** |

That asymmetry *is* the bug: every other layer's down reaches the WMMA owner
through the `qwen4_exp_q5_1` binding, and layer 29's Q8_0 down reaches nothing,
so it falls through the whole chain — WMMA fails, MMQ fails (`_MMQ_DOWN_QUANT_KEY`
is `gguf_q5_1`), grouped fails — to the selected GEMV at 44.4 ms.

The owner it should have found was already written and already proven.
`gguf_q8_0_selected_grouped_wmma_prefill_compact_bf16_bf16_out` takes
`expert_start_compact_ptr` / `expert_start_wmma_ptr` / `tile_expert_ptr` — the
expert ABI, identical in signature to the q5_1 wrapper — and its docstring says
so outright: "the f16-WMMA dequant GEMM contract of the promoted Q5_1 grouped
WMMA down, applied to Q8_0 expert weights". It is pinned against a NumPy dequant
reference through `qwen35_moe_wmma_tile_map` in
`tests/test_gpu_qwen4exp_q8_0_grouped_wmma_down.py`. It was simply bound on the
dense axis only, under the dense name `selected_grouped_wmma_prefill_bf16_bf16_out`,
never on `moe_linear` under the `compact` name the expert dispatcher asks for.

Fix is one `register()` in `register_gguf_q8_0_prefill_kernels()`. Plain form
only: `auto` returns `compensated=False`, and no compensated Q8_0 wrapper
exists.

**Gate_up (Q5_K) — missing leaf, Step 2 stands.** `moe_linear` + `gguf_q5_k`
resolves to nothing for either WMMA variant, and `_MMQ_DUAL_QUANT_KEY` is pinned
to `gguf_q4_k`, so the fused-gate_up int8 MMQ leaf structurally cannot serve
Q5_K. No registration can fix that; it needs the tile loader the row already
names.

**A hang found while validating, and ruled out as mine.** The gemma4 unit bundle
timed out at 2400 s. Bisected per file: `test_unit_gemma4_generate.py` and
`test_unit_gemma4_runner.py` both hang past 600 s. To test whether my
registration caused it, the edited file was copied to `/tmp`, `git checkout`ed
back to pristine, and the test re-run — **it still timed out (rc=124)**, then the
fix was restored from the copy. So the hang pre-dates this change and is
unrelated to it. It needs its own punchlist row; it was not chased here.

Two assertion mistakes were made writing the V2 test in the previous unit and
are worth keeping straight, because both were confident and backwards: the
window's visible span is `(start - window, start]`, not `[:window]`, and a
query's own key sits at column `start + i`, not `i`, because the mask spans the
whole cached range rather than the block.
