# Canonical production-load fault localized to first serving poll

## Summary

Re-attempted the canonical C2-6 production load packet after the conv_out
aliasing fix (`422209168`), suspecting the historical "ROCm page fault"
blocker might have been that bug. It was not: the gate still aborts with
`Memory access fault by GPU node-1 ... Page not present` deterministically
(now 9+ total attempts). Flush-trace instrumentation (since removed) localized
the fault precisely: all 13 same-owner serial-c1 references complete,
`create_app`/batcher wiring succeeds, uvicorn `/ready` succeeds, the first
tuning workload (`tuning_r0_0_token_budget_128`) starts, and the process dies
inside the FIRST `adapter.poll()` of the serving phase — before a single engine
event is emitted. So the fault is in the request-admission/prepare/prefill path
of concurrent serving on an owner that has just produced 13 reference
trajectories, under the tuned loop configuration (token_budget, 128-token
chunks, reconfigured batch window).

## Changes

- None retained; the gate script's temporary TRACE instrumentation was removed
  (worktree clean).

## Validation

- Gate reruns (3x post-fix, exact canonical command): identical fault, each
  after `reference 13/13`, inside the first serving poll.
- Minimal same-owner repro (LLM + full gate env incl. chunked prefill + KV pool
  page config + 13 references + live_loop_snapshot + create_app + memory
  snapshot + uvicorn /ready + small concurrent HTTP bursts n=2/4): runs clean.
  At n=8 the repro hits a clean server-side `HIP error 2: out of memory` 500
  (repro pool-config artifact), not the fault. The gate-only ingredients still
  missing from the repro: `_reconfigure_loaded_loop` (policy/chunk/burst/window
  reconfiguration after references), the mixed-arrival tuning spec shape, and
  streaming requests.

## Next
