# Publish the row's own activation reason, provider readiness, realized group width, and group AR decision

## Summary

Task #27. A served row could not report why it never speculated: the response
published one folded `fallback_reason`, so a row whose provider was still
priming and a row whose prompt activation was never attempted both read as
`no_provider`, and a row that decoded autoregressively for its whole life still
carried the route-level `k0_class=not_k0` (which describes the route's intent,
not the plan the row ran under) beside a serving-key width of 1.

Confirmed first on the merged tree, from the committed 2026-09-20 c=1 baseline
rows (`/tmp/baseline-merged/serve-{off,radix}-c1.json`) and a fresh live probe
with `HIPENGINE_MTP2_TRACE_DECLINE=1 HIPENGINE_DEBUG_SAMPLED_ROUTE=1`:

- `effective_route`/`selected_route`/`requested_route`/`route_decision_reason`
  are populated (the pre-merge nulls are gone); `policy_reason` is
  `qualified_automatic_realized_singleton_c1_b3`.
- The folded `fallback_reason` is `no_provider` on **both** the engaged miss row
  (`fallback_event_counts={no_provider: 1}`, 42 cycles, coverage 0.984) and the
  0-cycle prefix-hit rows (`{no_provider: 127}`, `first_fallback_position=0`).
- The 0-cycle hit rows carry `k0_class=not_k0` with 0 cycles, and
  `prompt_fallback_reason` is absent from their rows (so the fold had no
  admission reason to prefer) — the hit rows' refusal was **silent**.
- `grep -c '[mtp2-decline]'` on the traced server log was 0: no adapter gate
  recorded a decline. The refusal is the *silent* early return in
  `capability()`; its own debug fields name the cause:
  `rid=3 state=False prompt_hidden=False prompt_fallback=None
  first_token_emitted=True prefill_seen=419` (hit row) versus
  `rid=2 first_token_emitted=False state=True` (miss row, transient).

Two structural causes, both fixed here:

1. `_begin_mtp2_prompt_streaming` filters out rows with
   `prefix_reused_tokens > 0` *before* the adapter's own reuse gate runs, so a
   hit row was never labelled with the refusal the adapter already has a name
   for (`prefix_reuse_k0`), and `_prefill_native_chunk`'s prefix-reuse branch
   never called the activation entry at all.
2. The adapter's silent `return None` in `capability()` recorded nothing, so the
   only surviving reason was the planner's `no_provider`.

### The c=4 finding the new fields produced

A second live cache-on load (same server, `--num-prompts 4 --turns 2
--max-concurrency 4`, artifact
`benchmarks/results/2026-09-20-gfx1151-q4km-mtp2-refusal-facts-c4.json`) names
what the c=4 lane actually is. Eight rows, two cycles total:

| conv | turn | hit | cycles | `plan_group_rows` | `provider_readiness` | `provider_decline_reason` |
| --- | --- | --- | --- | --- | --- | --- |
| PqbAs6M | 0 | no | 1 | 1 | `ready` | - |
| yMwEvl7 | 1 | no | 1 | 1 | `ready` | - |
| t0WCBTW | 0 | yes | 0 | 3 | `declined` | `width 3 exceeds static group bound 1` |
| t0WCBTW | 1 | no | 0 | 4 | `declined` | `width 4 exceeds static group bound 1` |
| PqbAs6M | 1 | no | 0 | 2 | `declined` | `width 2 exceeds static group bound 1` |
| j432BUt | 0 | no | 0 | 4 | `declined` | `width 4 exceeds static group bound 1` |
| j432BUt | 1 | yes | 0 | 3 | `declined` | `width 3 exceeds static group bound 1` |
| yMwEvl7 | 0 | no | 0 | 3 | `declined` | `width 3 exceeds static group bound 1` |

So at c=4 the starvation is **not** provider-activation serialization and not
contention: every multi-row due group is refused by the static eligibility bound
(`max_realized_group_rows=1`, the same value the route decision names as
`qualified_automatic_realized_singleton_c1_b3`) *before* any provider work, so
those rows never get provider state at all. The only rows that speculate are the
ones the scheduler happened to plan as a singleton group. Two rows also carry
both refusal facts at once (`activation_reason=prefix_reuse_k0` beside
`provider_readiness=declined`), which is exactly the case a single folded
`fallback_reason` could not express.

This is a correction to the earlier reading of the same load (which inferred
"one row takes the provider, four starve" from `fallback_event_counts` alone):
the rows starve because the group they were planned in is refused, and the
refusal names its bound.
