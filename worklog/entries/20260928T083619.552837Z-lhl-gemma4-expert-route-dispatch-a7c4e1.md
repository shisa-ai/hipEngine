# pack8 was already measured as a decode route and loses by 2.73x so my candidate framing was wrong

## Summary

`20260928T081147` and `20260928T082433` both frame the packed expert layout as a
promising candidate, on the strength of an isolated kernel measurement showing
`selected_pack8` 1.25x faster than `selected` (54.0 against 43.4 GB/s). **That
framing is wrong and the question was already settled, with an artifact, before I
started.**

`docs/REFACTOR.md` carries the entry "Gemma 4's pack8 expert layout is off by
default", and its first line reads:

> **SETTLED 2026-09-28: the packed layout is never ahead, so the deletion below is
> unblocked.** ... prefill 343.2 against 340.0 tok/s (a 0.9 percent difference,
> inside run-to-run variation) and decode **21.24 against 7.78 tok/s**,
> reproducing the documented 2.73x regression on a fresh run. Evidence:
> `benchmarks/results/2026-09-28-gemma4-gfx1151-expert-pack8-layout-settlement.json`.

Three things follow, all of which I got wrong.

**`pack8_selected` has been run as a decode route.** The ledger records it as the
route that ran, at 7.78 tok/s against 21.24. `20260928T081147` asserts it "has
never been run as a decode route at all". That assertion is false, and I made it
from a dispatch trace without checking the refactor ledger -- the one place a
settled question of this kind would already be written down.

**An isolated kernel win does not carry to the route.** `selected_pack8` is 1.25x
faster than `selected` on identical shapes, and the route built on it is 2.73x
*slower*. The packed layout costs 1.33x more device memory (19.2 GB on this
artifact: 60 rank-3 expert tensors at 14.4 GB raw) and the kernel-level advantage
does not survive whatever the layout does to the surrounding access. I treated a
per-kernel number as evidence about a route, which it is not.

**There is no A/B to run.** `20260928T082433`'s "next" step was to measure
`pack8_selected` against the MMQ default. That measurement exists, is recorded,
and the answer is that pack8 loses by 2.73x. The flag is a legitimate default-off
case -- a measured cause, not a missing qualification -- and its clearing
condition has been met in the direction that unblocks deletion.

The dispatch-trace findings themselves still hold: `gemma4_project_experts_rows`
has no caller, its documented preference order is not executed, and the decode
path calls route-specific entry points directly. But that is cleanup debt on a
route the ledger already plans to delete
(`gemma4_project_experts_pack8` is on its deletion list), not an opportunity.
Nothing about it is worth optimising.
