# Diagnose C2 stage tile and acceptance blockers

## Summary

Explain why repaired K1 turns 91.67% acceptance into 0.5180x AR and why
C2/K2 code regresses to 0.8796x. Both reduce to measured mechanisms, not
model quality.

## Changes

  `benchmarks/results/2026-08-28-w7900-qwen38-q4km-c2-stage-tile-acceptance-diagnosis.json`

  position-1 acceptance tables, and the C1 strict/production deconfounder.
- Update the campaign doc P8 section with the diagnosis and next steps.
- No runtime or default-path change.

## Validation

- accept stage absorbs a full `device_synchronize()`; per request-cycle K1
  165.6 ms / K2 44.4 ms / K3 178.8 ms vs target forward 23-28 ms.
- gfx1100 admits only rows6 production rowtiles (`{6}`); off-tile cycles cost
  ~5.1x (fit 30.7 + 126.7 x ragged fraction, measured inside one K2 run where
  pure-R6 routes run 29.7-30.9 ms).
- K1 paradox: 91.67% acceptance executed on an always-off-tile R4 verify.
- Code acceptance drop is concurrency-caused: C1 strict == C1 production
  (0.9365/0.8485/0.8788/0.9375), C2/K2 code 0.7292, position-1 0.7733.
- Conditional position-1 acceptance (code): after reject K2 0.4706 (n=17),
  K3 0.3043 (n=46); K1 1.000 (n=6) with 23 k0 catchups; after full accept
  C1/K2 0.9615 vs C2/K2 0.8444.
- Healthy repair path is the k0 catchup (`advance_state_only` with
  `target.last_target_hidden`); the reject path uses
  `restore_request_root_state` (conv/recurrent + cursors) plus verify-hidden
  re-seeding.
- D24 walls are ~50% prefill for both AR and MTP.
