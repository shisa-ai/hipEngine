# Share staged score K loads across GQA heads

## Summary

The default staged score kernel now loads and decodes each K vector once for
two query heads of the same KV head. It preserves the strict warp-key multiply,
FMA and reduction order. Odd GQA ratios leave one row in the final pair. Score
workspace rows, per-row chunk maxima, softmax, P*V and strict fallback selection
are unchanged. This is T0 arithmetic, not a WMMA promotion.

On zbook / Radeon 8060S (gfx1151), Gemma 4 26B-A4B-it `UD-Q4_K_XL`, production
profile, BF16 KV, context 33024, one greedy output token, same-process public
requests measure:

| Prompt | Baseline median wall | Paired K reuse | Wall reduction |
| ---: | ---: | ---: | ---: |
| 512 | 0.463481 s | 0.453959 s | 2.05% |
| 8192 | 14.556015 s | 13.690739 s | 5.94% |
| 32768 | 114.184656 s | 104.585167 s | 8.41% |

One full-shape warmup per arm and two measured samples per arm/shape; measured
order baseline/candidate/candidate/baseline. Wall includes prefill, first-token
sampling and final device synchronization. All generated IDs match both arms,
warmups and repeats. Baseline/candidate library selection counts are 3690 each,
consistent with all 30 layers executing every prompt block in every request.
This is not cached-prefix throughput or decode throughput. The two baseline
32K samples vary from 110.84 to 117.53 s; the two candidate samples are
103.23 and 105.94 s. These are bounded measurements, not a general speed bound.

## Correction to the earlier diagnosis

This entry corrects
`worklog/entries/20261004T212906.001083Z-lhl-gemma4-prefill-gap-fix-12b034.md`.
Q was already staged in dynamic shared memory. P*V already staged weights and
reused V across grouped heads. The profiler's `LDS_Block_Size=0` did not account
for dynamic shared memory. Scores use a warp per key, not one thread per score.
The hypothetical 101 TB unstaged read count is not measured traffic. WMMA
changes arithmetic as well as data movement; its 5.121x timing ratio cannot be
attributed to staging alone or promised for an arithmetic-preserving change.
Strict parity is still a required numerical gate; only the reassociated-
arithmetic promotion packet can be avoided for this T0 change.

The original trace timings and raw profiler fields are preserved. Its script,
artifact note, CHANGELOG interpretation and REFACTOR paragraph now state these
limits. The committed earlier entry is immutable and is not edited.
