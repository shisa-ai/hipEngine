# Compare W7900 GGUF and PARO MTP output and diagnostics

## Summary

Inspect the current GGUF and PARO speculative-decode paths after the PARO
README refresh. The GGUF README headline is the July `llama-compat` opt-in
measurement, not a measurement of the October public Generation-2 path.
PARO now publishes GGUF's shared per-request MTP output accounting on blocking
and streaming responses. Arithmetic, dispatch, token selection, and defaults
are unchanged.

## Changes

- The current GGUF MoE C1 path calls `run_native_spec_mtp_cycle`, uses its native
  target graph, and selected depth two without an override in this check.
- PARO's C1/K1 adapter calls `verify_chain_bulk_and_commit` with `graph_mode="off"`,
  backs up target state into its spare slot, and updates the provider after
  verification. It already has a bulk verify/commit entry point; a future native
  graph port is a separate performance change, not an accounting fix or a
  demonstrated numerical repair.
- Reuse `record_speculative_outputs`, `record_autoregressive_step`,
  `speculative_output_accounting`, and `accounting_timing_fields` rather than
  adding another public schema. Accepted draft tokens stay distinct from all
  output committed by speculative cycles, including correction/bonus tokens.
- Declare the shared helper's counters and optional span field on the slotted
  PARO row. Existing diagnostic span recording remains off by default; this
  change adds no flag.
- Publish `diagnostics.specdec2_mtp2` and timing mirrors for speculative intent;
  leave plain AR without a speculative block. Proposal, target, and provider
  update timing sums include committed cycles only.
- Attribute accepted AR emissions after lifetime-cancellation filtering but
  before scheduler publication/reclaim. Refresh their prebuilt telemetry, so a
  terminal AR tail is counted and intermediate stream snapshots are current.
- Capture committed speculative accounting and the tokenizer before publication
  can reclaim its row, then decorate canonical scheduler events. Render empty
  speculative text using PARO's existing per-token decoder; preserve any text
  already present, the scheduler's per-token counts, token IDs, finish metadata,
  and logprobs.

## GGUF output observations

The diagnostic uses raw code, English, Japanese, and mixed-language prompts
from `benchmarks/prompts/mtpbench-code-general-ja.jsonl`, production profile,
BF16 KV, one active request, greedy sampling, natural EOS, default depth two,
and two repeats at limits 24 and 128. It executes real native target graphs;
these observations do not provide a new throughput or quality headline.

| Output limit | AR stable across repeats | MTP stable across repeats | MTP equals AR, paired runs |
| --- | ---: | ---: | ---: |
| 24 | 10/10 prompts | 10/10 prompts | 16/20 |
| 128 | 10/10 prompts | 1/10 prompts | 6/20 |

All ten speculative output prefixes repeat exactly at limit 128. The nine
repeat differences begin in the AR continuation after speculation stops near
absolute context 95. This localizes the first visible differences, not their
cause. Production differences from AR and differences between equivalent
repeats are separate findings.

A fresh-load follow-up interleaves four AR/MTP pairs for `code_merge_intervals`.
Both arms repeat exactly, including MTP's AR tail; the MTP result matches matrix
run zero but not matrix run one. Thus the one-prompt check does **not** reproduce
the matrix failure. Prior requests or runtime reuse may matter, but neither
state ownership nor graph reuse nor arithmetic has been proven causal. No
GGUF numerical fix, default change, or new headline is claimed.

The first GGUF attempt used `ignore_eos=True` and failed explicitly with
`mtp_sampling_unsupported`; the completed check uses natural EOS. The artifact
preserves both that capability result and the completed matrix rather than
silently relabeling the failed request.
