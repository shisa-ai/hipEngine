# EVIE fp16 GEMM production path

## Summary

Added a precision="fp16" production path (loader + runner): all projection
GEMMs run FP16 storage / FP32 accumulate with FP16 outputs (matrix cores,
14-26 TF/s vs ~2 TF/s fp32 SGEMM and ~4 TF/s for the f32-out gemm_ex
variant), activations cast fp32->fp16->fp32 around each GEMM. Strict fp32
path unchanged and still passing. Benchmark 8p+8q: 11.68 s -> 4.52 s
(doc 3.60 s, query 0.92 s) — now faster than the torch fp32 baseline
(4.148 s); torch bf16 (1.356 s) still ahead.

## Changes

- `hipengine/loading/evie.py`: precision param; GEMM weights (predicate
  `evie_gemm_weight`: .weight, excluding norm/embed_tokens/pos_embed/
  conv1d) converted to fp16 host-side. conv1d.weight MUST stay fp32 — it
  is read by the fp32 conv kernel (bug found via layer-0 bisect).
- `hipengine/runtime/evie.py`: precision param; `_gemm` casts x to a
  persistent f16 staging buffer, runs
  `gemm_ex_rowmajor_nt_fp16_compute_f32` into an f16 out buffer, casts
  back to fp32. Residual stream and all elementwise kernels stay fp32.
- `evie_ops.hip`: `hipengine_evie_cast_f32_to_f16` and
  `hipengine_evie_cast_f16_to_f32` kernels.
- `scripts/evie_hip_bench.py`: --precision flag.

## Validation

- Fixture parity, fp16 mode: query embeddings max 1.0e-3 / cos 0.9999991,
  doc embeddings max 2.8e-2 / cos 0.99987, MaxSim 5.9231 vs 5.9114
  reference (+0.2%). Deterministic repeat.
- Strict fp32: tests/test_evie_gpu_runtime.py 3/3, model contract +
  CPU-reference suites pass.
- Debugging note: the earlier "GDN fp16 causes activation-scale drift"
  conclusion was wrong — it was the conv1d-as-fp16 corruption; with that
  fixed, GDN projections in fp16 give bit-comparable accuracy to fp32
  GDN projections.
