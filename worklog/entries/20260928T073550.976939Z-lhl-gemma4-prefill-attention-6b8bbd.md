# the prefill kernel is three passes over one lds logits array so online softmax is a fusion and cannot be bit exact

## Summary

The prefill gap (584 vs 1013 tok/s) has been diagnosed for many entries as "one logit per
live key in LDS, three LDS round trips per key visit". Reading the kernel shows exactly
what those three round trips are, which makes the job a **fusion of three existing passes**
rather than a new kernel -- and shows that the acceptance criterion I have been carrying is
wrong.

## The three passes

`hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention.hip`, kernel body roughly lines
182-410:

**Pass 1** -- compute a logit per key, write it to `logits_s[j]`, track the running max:

```cpp
logit = gemma4_warp_key_logit<scalar_t, 8>(q_s, k_row, lane);
logit *= scale;
if (lane == 0) { logits_s[j] = logit; }
running_max = fmaxf(running_max, logit);
```

**Pass 2** -- read each logit, exponentiate, **store the weight back over the logit**:

```cpp
const float weight = expf(logits_s[j] - row_max);
local_sum += weight;
logits_s[j] = weight;
```

**Pass 3** -- read the stored weight instead of recomputing it, and accumulate the output.

The kernel's own comment explains why pass 3 reads rather than recomputes: recomputing was
"head_dim redundant evaluations per key -- 256 per key at this artifact's sliding-window
geometry, and the whole of the kernel's inner loop". So pass 2's write-back is a deliberate
optimization, and it is what forces `logits_s` to be one entry per live key.

**That single array is the constraint.** It must hold every key's logit (pass 1) and then
every key's weight (pass 2), which caps the tile and hence the context -- the LDS budget the
launcher at line 411 picks the largest tile to fit.

## So the fix is a fusion, not a new kernel

Online softmax processes keys in tiles and rescales the output accumulator when the running
max changes, keeping the weight **in a register** rather than writing it back. That is:

- pass 1 and pass 2 fused -- the logit is used immediately, so no logit array;
- pass 3 fused in -- the weight is consumed by the same iteration that produced it;
- `logits_s` eliminated, which removes both the LDS cap and the tile cap.

**It is a fusion of code that already exists, not new mathematics.** Pass 3 already consumes
a weight rather than recomputing it; the online version just keeps that weight in a register
instead of round-tripping it through LDS. That is a materially easier job than "write a
flash-attention kernel", and it is the framing a next worker should start from.

## A correction to my own acceptance criterion

Earlier entries, including the consolidated handoff, say the new kernel's acceptance test is
**exact equality** against `gemma4_attention_prefill_*` on the same device. **That is
impossible and I should not have written it.**

The existing kernel's comment records that it is bit-identical *by construction*: "every
pair added is the pair the block tree adds, in the same order, so the logits are
bit-identical". Online softmax **reassociates** -- it rescales the accumulator by
`expf(old_max - new_max)` as the max grows -- so it produces a different summation order and
therefore different bits.

**The correct gate is a tolerance**, on the same footing as any other reassociating
candidate: `docs/EXECUTION-PROFILES.md` owns the numerical gate, and a production candidate
that reassociates is evaluated against it rather than against exact equality. Stating this
now matters because an exact-equality gate would fail a correct kernel, and the failure
would look like a bug in the new code.
