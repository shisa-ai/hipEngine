# W7900: all-GEMV prefill measured 1.57x/3.20x slower, closing the last non-kernel lever

## Summary

Task #12's last cheap lever is measured and closed. At 45 rows a 16x16 WMMA tile wastes 12 of 16
rows, which made the GEMV prefill family look worth testing. It is not: all-GEMV prefill is
**1.57x slower at 42 tokens (0.4632 s vs 0.2950 s) and 3.20x slower at 285 tokens (2.2764 s vs
0.7115 s)**, medians of 3, same probe, route flag the only difference. The route choice is already
right, so what remains for small-row prefill is kernel work with a RED gate, not a route switch.

## Changes

Artifact `2026-08-30-w7900-q4km-all-gemv-prefill-arm-rejected.json`, plus a `docs/REFACTOR.md`
section (`c1d0c6834`) recording that the public route booleans are inert. The experiment ran on a
revertible scratch edit of the 11 literal `use_wmma_prefill=True` sites; the file is restored and
`git status` is clean for it, so nothing in the tree changes route.

## Validation

The interesting part is the arm that would have been reported wrongly. First attempt flipped only
`_GGUF_PUBLIC_USE_WMMA_PREFILL` (through `__wrapped__.__kwdefaults__`, since the scope is a
contextmanager) and produced walls identical to baseline within 0.2% - 0.2956 vs 0.2950 s and
0.7121 vs 0.7115 s. That is a vacuous arm, not a neutral result, and the route log proved it: inside
the "flipped" process sessions were still constructed with `use_wmma_prefill=True`, because warmup
pools pass the literal and the measured AR route reuses a pooled session. Only after flipping the
literals did the log show `False` and the walls move 1.6x-3.2x. Third time this week I have caught a
control that did not reach the kernel by logging the control rather than trusting the knob - tile
sweep, `--backend` argparse arms, and this one.

Baseline stability: 0.7115 s here against 0.7124 s in an independent run earlier today, 0.13% apart,
so a 3.20x effect needs no repeats.
