# VibeVoice-TTS torch oracle: deterministic fixtures, and a correction to the scaling-factor claim

## Summary

`scripts/vibevoice_tts_oracle_torch.py` now captures the full reference
generation path and writes the milestone-1 fixture set for one single-speaker and
one two-speaker request. Two independent runs of the same command produce
**byte-identical** artifacts for all ten files, so the oracle is reproducible
rather than merely seeded.

Writing it also falsified a claim I made in the previous entry. I stated that
`speech_scaling_factor` and `speech_bias_factor` are not checkpoint values and
are computed from the reference audio at first use. **That is wrong.**
`model.speech_scaling_factor` and `model.speech_bias_factor` are weights in shard
1 of the checkpoint, as bf16 scalars `0.1962890625` and `-0.04931640625`. The
earlier entry's original doc text was correct and my correction to it was not.
The superseded path is `worklog/entries/20260915T025539.131560Z-lhl-vibevoice-tts-oracle-env-9fbede.md`
and the affected doc bullet has been restored.

## Changes

- `scripts/vibevoice_tts_oracle_torch.py` (new): the oracle. Wraps the reference
  module or method that performs each piece of work -- `sample_speech_tokens`,
  `prediction_head.forward`, `noise_scheduler.step`, `acoustic_tokenizer.decode`,
  `semantic_tokenizer.encode`, and `torch.randn` / `torch.randn_like` -- and
  records what passes through. No arithmetic is reimplemented, so a fixture
  cannot disagree with the reference by construction.
- `tests/fixtures/vibevoice_tts/` (new): the committed fixtures and
  `manifest.json`.
- `docs/MODEL-VIBEVOICE-TTS.md`: the `speech_scaling_factor` bullet is restored
  and now carries the measured evidence for where the values actually live.

## Notes

- **The scaling factors are weights, not config.** `config.json` has no such
  keys, which is what misled me. The state dict does, and `from_pretrained` loads
  them over the `NaN` default that the module registers at construction. The
  inference path only ever *applies* them; the `NaN`-triggered recomputation
  exists only in the training model at `modeling_vibevoice.py:307`. My previous
  entry inferred the inference behaviour from the training code, which is exactly
  the kind of cross-file inference that should have been checked against the
  state dict first. The practical consequence is unchanged and is what the doc
  now says: a model built from config without a weight load keeps `NaN` and
  poisons every speech embedding.
- **`voice_samples` is a flat list per batch item, not a list per speaker.**
  `voice_samples=[[alice, carter]]` is correct; `[[alice], [carter]]` is parsed
  as two batch items with one voice each. The failure is quiet: generation still
  runs and still produces audio, but the reference audio covers only the first
  voice, `all_speakers_list` reports `[[0]]`, and the prompt is 137 tokens
  instead of 352. I only caught it because `single_reference.npz` and
  `two_reference.npz` came out the same size. A shape assertion would not have
  caught it; the two are legitimately shaped, just wrong.
- The reference voices ship at **16 kHz** and the model needs 24 kHz. The
  processor owns resampling, so the oracle takes `speech_tensors` from the
  processor instead of reading the WAV. Reading the voice files directly and
  asserting 24 kHz fails immediately.
- Full-vocab logits for all 121 prompt positions is ~73 MB of float32, which is
  not committable. The fixture stores `--logit-positions` (default 4) positions,
  split between the start and end of the prompt, plus the position indices.
  `single_lm.npz` went from 35 MB to 2.3 MB; the whole set is 7.0 MB.
- Token ids and masks are saved with their native dtype via `_npi`. Routing them
  through the float32 helper would round-trip for values under 2^24, but it
  discards the type contract for no reason.
- The oracle still runs on gfx1151 (Radeon 8060S), not the default gfx1100.
  These are reference outputs, not hipEngine performance claims.
