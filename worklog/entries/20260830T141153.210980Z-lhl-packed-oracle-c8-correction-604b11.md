# The c8 byte-exactness suggestion named the wrong oracle, and its flag is refused by design

## Summary

Supersedes one paragraph of `worklog/entries/20260830T134942.798537Z-lhl-w7900-submodule-parity-gate-651f3d.md`
(that file is immutable, so this is the correction). That paragraph said
`scripts/gguf_packed_ar_category_oracle.py` "already compares packed groups against independent c1
byte-exactly" and that "running it at `--group-size 8` is the honest version of the opt-in question".
Both halves are wrong: the byte-exact comparison lives in a different script, and `--group-size 8` is
refused by an unconditional guard. Two queued GPU jobs died on that guard in one second each, which is
the only thing they accomplished.

## Changes

- No code change. This is the record of what the two failed runs prove and what they do not.
- Wrong script named. `scripts/gguf_packed_ar_category_oracle.py` is the B4 *category* oracle: it
  measures acceptance/economics over the prompt suite plus category heldouts (`_group_prompt_rows`,
  `reference_sessions=tuple(sessions[group_size : ...])`). The byte-exact packed-vs-independent-c1
  comparison - tokens, every post-layer BF16 row, Conv/GDN state, live K/V - is
  `scripts/gguf_packed_ar_state_oracle.py`, which does take `--rows 8`.
- The flag is refused by design, not by oversight. `scripts/gguf_packed_ar_category_oracle.py:331`:
  `if group_size != 4: raise ValueError("B4 category oracle requires the production c4 group cap")`.
  `group_size` is load-bearing beyond grouping - the repeat schedule is `2 * group_size - 1` (line 374)
  and the reference slice is `sessions[group_size : ...]` (line 397) - so asking it a c8 question means
  changing its contract, not passing a flag.
- The c8 question I wanted is already answered, in the negative, by the state oracle: `/tmp/he-oracle-
  hidden-r8.json` and `/tmp/he-oracle-hidden-r2.json` (both `status: failed`, `passed: false`, run with
  `--prefill-mode packed --gdn-prefill-mode exact --decode-mode eager --capture-layer-hidden`) report
  `tokens_exact: true` and `lifecycle_state_exact: true`, but `initial_state_exact: false` and
  `final_state_exact: false`, with first divergence at `prefill_hidden` step 0, layer 1, 941 mismatched
  elements, `max_abs 0.0009765625` (one BF16 ulp near 1.0), identical at rows 2 and rows 8.
- That result is not new either, and is not a blocker: `worklog/entries/
  20260830T005330.724870Z-lhl-w7900-qwen38-packed-prefill-state-gate-3df834.md` already records the
  same non-exactness at both widths and states the asymmetry is structural, with the explicit
  instruction not to re-run the byte-exact oracle expecting it to pass. My reruns reproduced it and
  added nothing, so no further GPU time goes there.
- Net statement to use instead of the superseded one: grouped packed prefill is token- and
  lifecycle-exact against independent c1, and is *not* state-byte-exact; the divergence is one BF16 ulp
  on 941 prefill hidden elements plus the layer-0 recurrent state hashes. Anyone wanting a c8 economics
  verdict must extend the category oracle's contract and declare which profile it then speaks for.
