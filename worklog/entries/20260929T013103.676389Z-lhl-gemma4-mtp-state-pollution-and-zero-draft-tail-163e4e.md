# The Gemma 4 MTP route ran on the previous request's KV, and its zero-draft tail read a flat logits array

## Summary

**The objective's regression is fixed, and the recorded baseline is restored.**
`--tokens 64 --budget 6` now reports `outputs identical: True` at **2.301x** (three
samples of that point: 2.301x, 2.243x, 2.252x) against the 2.101x baseline, with
`tokens emitted: plain 64, spec 64`, and a full sweep is identical at every budget:

| tokens | budget | plain tok/s | spec tok/s | speedup | outputs identical |
| ---: | ---: | ---: | ---: | ---: | :---: |
| 64 | 1 | 29.06 | 42.29 | 1.455x | yes |
| 64 | 2 | 28.15 | 50.58 | 1.797x | yes |
| 64 | 3 | 28.04 | 55.21 | 1.969x | yes |
| 64 | 4 | 28.13 | 58.89 | 2.094x | yes |
| **64** | **6** | **28.00** | **64.43** | **2.301x** | **yes** |
| 64 | 8 | 27.91 | 44.96 | 1.611x | yes |
| 32 | 1 | 27.74 | 37.49 | 1.351x | yes |
| 32 | 2 | 28.12 | 46.69 | 1.661x | yes |
| 32 | 3 | 25.67 | 39.96 | 1.556x | yes |

**The overshoot hypothesis was wrong, and it is worth saying so plainly: the route
never emitted more than `max_tokens`.** Both routes emit exactly the requested count
(32 vs 32, 64 vs 64 tokens); the character-count excess in the symptom table was the
first token of a *different* continuation, not extra tokens. That was invisible
because the probe asked `GenerationOutput` for `token_ids`, got `None`, and printed no
token counts at all — so a divergence had to be read off character lengths, and a
character is not a token. The probe now prints both token sequences and the shared
token prefix.

There are two independent defects, both in `hipengine/generation/gemma4_mtp.py`:

1. **The route never reset the runner.** Its prefill appends the prompt at the runner's
   *current* position and attends over everything already in the KV cache, so the
   output was a function of the previous request rather than of the prompt. The probe
   runs the plain route first, so the speculative route was measured on the plain run's
   own KV: `position=74` with the previous request's 74 tokens live, instead of `0`.
   The AR route does the opposite (`gemma4_gguf.py:201` calls `runner.reset()` per
   prompt); this route has to as well.
2. **The zero-draft tail read a flat logits array.** `Gemma4Runner.forward` returns
   `(k, vocab)` for `k > 1` but a flat `(vocab,)` for `k == 1`
   (`hipengine/runtime/gemma4.py:1016`), and the tail cycle added by `91797c177` for the
   `max_tokens` bound is exactly the one-row case. `rows[0]` on that array is the scalar
   logit of vocabulary entry 0, whose `argmax` is always 0, so every such cycle committed
   token 0 (`<pad>`) instead of the model's next token.

Defect 2 is the whole of the budget-1 and budget-2 failures at 32 tokens: the two routes
agree on 31 of 32 tokens and the last is `0` against plain's `7217`. Defect 1 is the whole
of the 64/6 failure: the routes agree on **0** of 64 tokens because the polluted prefill
samples a different continuation.

## Root cause of the regression: state the route was always reading, exposed by an arithmetic change

The route was always polluted. What changed is that a prefill-arithmetic change made the
pollution visible. `git worktree add` at each candidate, same probe, same 64/6 command:

| commit | probe | outputs identical |
| --- | --- | --- |
| `91797c177` (the fix this regression was measured against) | 2.097x | yes |
| `0bcf2dc0b` (WMMA prefill attention candidate, not selected) | 2.336x | yes |
| `dfc329348` (WMMA prefill attention **on** for the sliding layers) | 26.794x | **no** |
| `25c76d141` (WMMA prefill for the full layers) | 26.105x | **no** |
| `eb4c47399` (HEAD) | 1.733x | **no** |

**`dfc329348` is where the failing comparison starts**, and the mechanism is in the
polluted prefill, not in that commit's arithmetic being wrong. At `dfc329348` the
speculative output is **one token**: the prefill, run on the previous request's KV,
sampled EOS (`106`, `<turn|>`, 7 chars — the probe's `spec 7 chars`, `'\n' vs '<'` at
char 0), and the 26.8x "speedup" is the probe dividing 64 requested tokens by the time
one took. At HEAD the same polluted prefill samples a different attractor instead:
`[1030, 563, 1547, …]` (`' It is because of the way the light is.'`) against plain's
`[108, 36425, 506, …]` (`'\n\nwhy the sky is blue.'`).

That the trigger is the attention arithmetic rather than the MoE compactor, the router
logits, or the T16 leaf is confirmed by profile alone: `HIPENGINE_EXECUTION_PROFILE=strict`
changes exactly one thing (the `prefill_attention` variant, the only layer in the Gemma 4
plan) and the same polluted 64/6 run is then identical 64/64. The clean-context output is
unchanged from `91797c177` to HEAD, so no clean-path arithmetic regression is visible:
plain still produces the same 200-character completion.

The measurement that separates the two defects from the arithmetic is a single explicit
`runner.reset()` before the speculative call, with nothing else changed: `position=0`,
**2.220x, identical**. The fix moves that reset into the route, where it belongs, so the
probe exercises it instead of depending on it.

## Changes

- `hipengine/generation/gemma4_mtp.py`
  - `runner.reset()` before the prefill, with the reason: a runner carries the previous
    request's position and KV, and this route's whole correctness argument is that the
    batched verify reproduces a single-token forward *for this request's own context*.
    This is also what makes a packed serving call correct — the engine loop packs
    multiple speculative children into one `generate_speculative_mtp_detailed` call and
    this provider loops `_generate_one` per prompt.
  - `rows = rows.reshape(1, -1)` when `forward` returns the flat one-row array, so the
    zero-draft cycle reads row 0 rather than a scalar. The dead `logits = rows[accepted]`
    assignment went with it: it was the same shape assumption, unread.
- `tests/test_unit_gemma4_mtp_cycle_accounting.py` — new, CPU-only, no artifact and no
  HIP. It drives the real provider with a fake generator, runner and drafter, and pins
  the four contracts that were unguarded: the prefill starts from a reset runner; the
  output does not depend on the runner state it inherits; a zero-draft tail commits the
  model's next token; and every budget (1, 2, 3, 4, 6, 8) stops at exactly `max_tokens`
  with the greedy sequence. `_FakeRunner.forward` is shape-faithful to
  `Gemma4Runner.forward`, including the flat one-row return, so the provider is pinned
  against the shape a real runner produces.
- `scripts/gemma4_mtp_probe.py` — reports the token sequences and the shared token
  prefix, and warns when a route emitted fewer tokens than requested (the case that
  produced a 26.8x reading above from one token). Two separate reasons it had printed
  nothing before: it asked `GenerationOutput` for `token_ids`, which the class does not
  carry (it is `generated_token_ids`), and it read the plain route through
  `LLM.generate`, which returns bare strings, so no token IDs existed on that side at
  all. The plain route now goes through `LLM.generate_detailed`, which is the same call
  `generate` makes (`generate` is `[output.text for output in
  self.generate_detailed(...)]`), so the timed work is unchanged and the tokens are
  available.

## Next

- **The probe's plain-first call order is now load-bearing and should stay.** It is the
  only end-to-end check that the route does not read inherited state; adding a reset to
  the probe would hide a regression of this fix.
- **A GPU-tier cycle test would be worth having** and is not in this unit: the CPU test
  pins the accounting against a fake runner, and nothing in the default tier runs the
  cycle against a real `Gemma4Runner` with the assistant sidecar. The pieces are in
  `tests/test_gpu_gemma4_assistant_forward.py` (artifact-guarded) and the runtime is a
  26B load, which is why the end-to-end check is the probe.
- **`Gemma4Runner.forward`'s one-row shape is a trap that has now bitten once.** Its
  docstring says `(k, vocab)`; the code returns `(vocab,)` for `k == 1`. Either the
  docstring or the shape should change, and `hipengine/runtime/gemma4_speculative.py:145`
  is the one other caller that indexes rows and guards itself explicitly. Left alone here
  because the plain AR route and the existing verify-rows test both depend on the current
  return, and changing it is a separate unit.
- The MoE compactor, the router logits and the T16 leaf were each suspected and are each
  cleared by the evidence above: the clean-context output is unchanged across them, and
  `HIPENGINE_EXECUTION_PROFILE=strict` (which changes none of them) makes the polluted run
  identical.
