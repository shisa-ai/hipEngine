# P6 q/k/v fusion: split kernel, loader fusion, layer wiring, parity gate

## Summary

Implements punchlist P6 (`#37`): the three attention projections become one
resident weight and one `gemma4_project` launch, with a device-side split
putting the result back into the three buffers every consumer already reads --
route (b) of `#41`, which deliberately avoids widening the attention, norm,
rotary and cache-append ABI.

The row asked for the split's cost to be investigated *before* promoting, so
both sides were measured rather than modelled. On the fixture geometry
(`attn_q` 256->256, `attn_k` ->128) the projection costs 18.54/33.03/20.11/27.85
us at rows 1/128/1024/4096 against the split's 5.67/5.96/9.71/19.69 us, so the
split costs 18-71% of the launch it replaces and every size is a net win of
8-27 us per fused layer. The projection is launch-bound at these tiny widths;
it scales with `in*out` while the split scales only with `out`, so real gemma4
widths move the ratio further in the split's favour. The split alone runs
6-100 us at 460-487 GiB/s (memory bound) and costs 1.0-1.7x
`gemma4_scale_bf16` given a byte-identical read/write pattern.

Two costs the row did not state, both folded into the design:

- **Memory.** The transient fused buffer doubles the q/k/v scratch region
  (1.6 KiB at 1 row, 1.6 MiB at 1024 rows gemma4 dims, up to 24 MiB at 4096
  rows with wide kv). In-place rearrangement does not remove it: writing the
  packed blocks clobbers source rows not yet read, which was checked directly
  rather than assumed.
- **k_eq_v layers are a net loss, not a saving.** They already run two
  projections (q, k); fusing gives projection + split = two launches, so the
  split's 5.7-19.7 us and the scratch would buy zero reduction. The loader
  therefore never fuses those layers, and the parity gate asserts that.

Fusion is capability-gated, never identity-gated: `can_fuse_gguf_device_weights`
asks whether the artifact's storage is uint8 blocks at a single width, so any
artifact that can fuse does regardless of its name, and one that cannot keeps
the three weights it always had.

## Changes

- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_norm.hip`: new
  `gemma4_qkv_split_bf16_kernel` plus its `extern "C"` launcher. Copies raw
  BF16 bits (so the split is bitwise transparent), writes q and k on
  `parts == 2` and leaves `v` untouched, and rejects a stride that disagrees
  with `(parts, q_width, kv_width)` before launching.
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_norm.py`:
  `_ARGTYPES_QKV_SPLIT`, `_SYMBOL_QKV_SPLIT`, and the `gemma4_qkv_split_bf16`
  wrapper deriving `stride = q_width + (parts - 1) * kv_width`.
- `hipengine/loading/gemma4_gguf_device.py`: `can_fuse_gguf_device_weights`,
  the storage/width predicate the loader consults instead of catching the
  materializer's `ValueError` (which would also swallow a real load failure).
- `hipengine/runtime/gemma4.py`: fusion block in `_build_layer` materializing
  q/k/v as one weight, skipping those three slots in the per-slot loop so the
  rows are not held resident twice, and `qkv_proj` added to
  `_PROJECTION_FIELDS` so an unfused layer gets the `0` default. Not fused when
  `config.geometry(index).k_eq_v`.
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_layer.py`: `qkv_proj` field,
  the `"qkv"` transient scratch entry, the collapsed projection + split branch,
  and a guard so the unfused path still runs its own V projection.
- `tests/test_gpu_gemma4_qkv_fusion_parity.py` (new): the end-to-end gate --
  three projections versus fused + split, `assert_array_equal`, plus the two
  assertions that fusion is *not* engaged on k_eq_v layers.
- `tests/test_unit_gemma4_gpu_kernels.py`: three split tests (bitwise
  separation, k_eq_v leaving a sentinel-filled `v` untouched, bad parts count
  rejected before launch).
- `tests/test_unit_gemma4_weight_geometry.py`: adds `gemma4_qkv_split_bf16` to
  the layer-forward recorder's mock list.

## Validation

- New parity gate: 1 passed -- fused + split is bitwise identical to three
  separate projections on the same artifact.
- Split unit tests: 3 passed.
- Commit bundle (parity + split tests + `test_unit_gemma4_gguf_device.py` +
  `test_unit_gemma4_weight_geometry.py` + `test_gpu_gguf_dual_column_independence.py`
  + `test_unit_gemma4_mmq_route_guard.py`): **31 passed, exit 0, zero failures
  and zero GPU faults**.
- Full `tests/test_unit_gemma4_*.py` sweep: 6 failures, all in
  `test_unit_gemma4_runner.py`, and the failure set was diffed against a run
  with these changes stashed -- **identical**, so they are pre-existing at
  `faf00bbe1` and not introduced here. Left alone as another agent's area.
- Two earlier faults were my own bugs, recorded because both looked alarming:
  the recorder fakes `malloc` at `0x30000` and mocks every other real kernel
  but not this one, so the split launched against a fake pointer and surfaced
  as a teardown-time `Memory access fault ... on address 0x31000`; and a first
  stride of `q + parts*kv` instead of `q + (parts-1)*kv` showed up as q and k
  asserting clean while only v's slice mismatched.
