# Accept window is 96.5% pageable sync uploads; K3 plateau is self-serialization

## Summary

The two counters in `84f2518c3` close the accept-window accounting, and the answer is
not host bookkeeping. At
C5-C8, **96.5% of the MTP accept window is the pageable synchronous host-to-device
uploads** issued by
`_enqueue_target_batch_accept`: 85.4-101.6 ms per lane-cycle out of an 88.2-105.2 ms
window. The per-row tail is
0.0-0.1 ms and the residual is 0.1 ms, so there is nothing left to explain.

## Why this costs 85-102 ms for a few hundred bytes

- `copy_host_to_device` (hipengine/core/memory.py:124) is `runtime.memcpy(...,
  MemcpyKind.HOST_TO_DEVICE)`: the
  blocking entry point. `_upload_accept_array` (qwen35_gguf_mtp2.py:2143) passes
  `np.ascontiguousarray(values)`,
  i.e. **pageable** host memory. A blocking copy from pageable memory stages through
  driver-owned memory and
  synchronizes the device, per call. There are roughly seven such arrays per cycle
  (token_ids, positions,
  parent_rows, draft_depths, row_to_request, active_mask, remaining, plus pads).
- Measured part: those calls take the time. Inferred part: in a round-robin multi-lane
  server, each of those
  device-wide syncs also drains work other lanes have already queued, so the accept phase
  absorbs cross-lane
  queue latency and the pipeline serializes itself. That inference is what predicts the
  shape below; it is not
  separately measured.
- Shape consistent with it: K3 output rate is flat 30.2-30.8 tok/s across C5-C8 while the
  peer scales x1.59 over
  the same widths, and per-cycle cost grows w^0.76 against AR's w^0.36. Acceptance is
  width-invariant, so the
  plateau is not an accept-rate problem.

## Fix spec for #17 (not implemented here)

- Pack the per-cycle accept arrays into one pinned host arena and issue a single copy on
  the stream that ran the
  verify kernels, or keep the separate copies but make them pinned and use `memcpy_async`
  (already available:
  hipengine/core/runtime.py:85 takes a `stream` argument). Either removes the per-array
  blocking sync.
- This changes *when* the host waits, not arithmetic, but it reorders host/device
  interaction, so the gate is the
  K3 exact-output check plus a same-protocol repeat measurement, not a test suite alone.
- Prediction, explicitly unmeasured: accept is 104.3 ms of a ~153 ms per-lane cycle at C8.
  Driving it near the
  1.5 ms commit cost would roughly halve the cycle. Anything that leaves a per-array sync
  in place will not
  capture most of it.
