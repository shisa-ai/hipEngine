# Staged-f32 gate run was a false pass: selector missing from the dispatch cache key

## Summary

**The 0-47 gate run reported `mean_kl 0.0`, `max_kl 0.0`, `top1 1.0` and
`hard_gates_passed: true`. It is not a pass. It is a false pass, and the staged
tile never executed.**

Decisive evidence from the artifact:

```
strict_logits_sha256    = 550bb9b832bc7ba273f6b3b3dc24fddcdb8edff724f19a2c781c46a400e118f6
candidate_logits_sha256 = 550bb9b832bc7ba273f6b3b3dc24fddcdb8edff724f19a2c781c46a400e118f6
```

Bit-identical logits across all 12 cases. A KL of *exactly* zero is not an
excellent result; it is the signature of zero route engagement.

## Root cause

`_raw_k_staged_f32_dispatch` reads its selector live from the environment, but
`launch_gguf_linear` only reaches the dispatch chain inside `if cached is None:`.
The dispatch memoization key did not include
`HIPENGINE_QWEN4_EXP_Q8_STAGED_F32_LAYERS`. The teacher arm resolved and cached
the exact chain; the candidate arm hit the same key and **replayed the teacher's
dispatch**.

The sibling `dense_wide` route documents this hazard directly above its own key
term: *"All three must be in the memoization key or the first resolution for a
shape is replayed for every layer and the scope becomes an artifact of cache-fill
order rather than a contract."* I read that comment while building the route and
did not connect it to my own selector.

For the staged route the consequence is worse than a wrong scope: a gate's two
arms are the same shapes on the same weight pointers and differ **only** in this
selector, so the omission makes the arms identical *by construction*. And the
failure mode is silent - identical logits look like a flawless pass.

## What this says about my own pre-flight check

I verified the wiring before launching and reported it as "ROUTE WIRING
VERIFIED". That check called `_raw_k_staged_f32_dispatch` **directly** with a
synthetic weight. It confirmed the function's logic and could never have caught
this, because the defect is that the function is not *called* - it is skipped by
a cache hit upstream. A pre-flight check that bypasses the caller does not test
the call.

The check that would have caught it is the one the gate itself prints and I did
not read carefully enough: `blockers` already listed *"candidate route
engagement"*. `qualification_coverage()` verifies the protocol (fixture identity,
12 cases once each, D128, three repeats) and does **not** verify engagement, so
`measurement_valid: true` and `hard_gates_passed: true` are both fully consistent
with a route that never ran. A green status covered the protocol, not the
objective.

## Changes

  index) added to the dispatch memoization key, with a comment recording why the
  omission is silent rather than loud.
- `tests/test_unit_qwen4exp_staged_f32_route.py`: a regression test that records
  the key the real `launch_gguf_linear` uses.
- `benchmarks/results/2026-09-29-q8-staged-f32-dense-prefill-layers-gate/INVALID.md`,
  and the artifact's `status` set to `invalid` with a reason.

## Validation

RED/GREEN verified, which took two attempts:

- **First attempt was worthless and I verified it was worthless.** The test drove
  the real memoization and asserted the candidate arm created a new cache entry.
  It passed with the key term removed, so it caught nothing. Cause: the registry
  `generation()` is the first key element and the lazy kernel registration inside
  the call bumps it, so every call misses for an unrelated reason. A test that
  cannot fail is not evidence.
- **Second attempt records the key tuple itself** rather than observing misses.
  RED with the term removed: `KeyError`-free failure showing the identical key
  `(3218, (False, None, None), 'raw_gguf', 'gguf_q8_0', 1024, 2560, ...)` for
  selectors `"3"` and `"4"`. GREEN with it restored: 9 passed.
- Full file: 9 passed.

## Next

**Re-run the gate on the fixed code.** The artifact is retained only as the
record of the invalid run. Nothing about the staged tile's arithmetic is
disproven here - this run says nothing at all about it, which is the point.

The fix is necessary but not proven sufficient: the memoization was one way to
miss engagement, and the re-run must be checked for the same signature. A
candidate/teacher logits hash that matches the teacher's is a failed run
regardless of what the KL summary says.
