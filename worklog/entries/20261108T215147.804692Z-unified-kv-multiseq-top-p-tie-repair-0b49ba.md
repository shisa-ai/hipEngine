# Top-p sampler: tie-repair hardening; production cost is argsort-bound

## Summary

Investigated the Muse campaign's remaining host-sampler follow-up ("top-p
full-vocab argsort ~5-6 ms/token", `MUSE-GLIMMER.md` §11.1 host-sampler track).
Result is a **correctness-preserving worst-case hardening, not a production
hot-path speedup** — reported honestly as such.

Finding 1 — a latent full-vocabulary lexsort. `_apply_probability_filters`
re-sorted the entire support with `np.lexsort((token_ids, -probs))` whenever the
incoming probability order was broken. Softmax is monotonic, so a broken order
can only be new equal-probability groups whose IDs are not ascending (float32
shift rounding in `_softmax` creates these). Replaced the full lexsort with a
targeted repair of just those tie groups to lower-ID order — the same
(group<<32 | ID) packed-key idiom `_top_k_candidate_ids` already uses — with a
monotonicity/ID-width guard and a post-repair safety net that falls back to the
general sort for inputs the assumption does not cover (e.g. NaN probs).
Byte-identical output. On an adversarial float32 tie row the filter stage drops
**25.82 -> 1.28 ms (-95%)**.

Finding 2 — the production path does not hit it. `select_token` ->
`_process_row` upcasts logits to **float64** before softmax, so float32
shift-rounding ties do not arise and the `ordered=True` fast path already skips
the lexsort. Same-host full `select_token` top-p A/B is therefore flat within
noise (std-1 6.06->6.01, std-3 5.76->5.71, std-5 5.60->5.56 ms/token; first
token identical). The tie-repair benefits callers that reach
`_apply_probability_filters`/`processed_support` with float32-derived or
otherwise tie-broken probabilities, and removes a latent O(V log V) lexsort; it
does not move the float64 sampled-AR hot path.

Finding 3 — the real production cost is the argsort, and it is already tight.
The remaining top-p cost is the full-vocabulary descending argsort in
`_top_k_candidate_ids` (~1.9 ms at 201,088). Interleaved quicksort-vs-heapsort
measurement gives **1.92 ms for both** (an earlier sequential run suggested
heapsort ahead; the interleaved control falsified it), so no sort-kind change
was made. Exact ordering is required for the seeded RNG map, so the argsort
cannot be dropped without changing sampling semantics.

## Changes

- `hipengine/generation/sampling.py`: `_apply_probability_filters` tie-group
  repair replaces the unconditional full lexsort on broken-order input;
  general-sort fallback preserved for non-monotonic / wide-ID / NaN cases.
- `tests/test_unit_sampling_top_p_tie_repair.py`: 73 tests — byte-identical
  parity vs the previous full-lexsort implementation across 70 adversarial
  tie/boundary/min_p/top_p cases, a RED test asserting the tie path no longer
  calls `np.lexsort`, an inverted-input fallback case, and a seeded
  `select_token` determinism case.

## Validation

- New file 73/73; full `tests/test_unit_sampling*.py` suite green (exit 0,
  ~384 tests incl. the 311-test pre-existing sampling suite).
- Parity oracle is the previous implementation embedded in the test; outputs
  compared with `assert_array_equal` on both IDs and probabilities.
- Same-host full-path A/B (old filter monkeypatched in vs new): first sampled
  token identical at logit std 1/3/5; wall flat within noise. Filter-stage
  micro-A/B on the float32 tie row: 25.82 -> 1.28 ms, byte-identical, kept=3.
- No GPU used; CPU-only unit + probe, safe alongside the running serving A/B.

## Next

  `_softmax`, the tie-repair already covers its rounding ties.
- This closes the "top-p argsort" follow-up as investigated-and-characterized;
