# gfx1151 audit review: gfx1100-only inventory, INT8-KV re-check, AR rollup

## Summary

Reviewed `docs/20260909-GFX1151-GFX1100-TRANSFER-AUDIT.md` against the current
tree on the physical gfx1151 host (Ryzen AI MAX+ 395 / Radeon 8060S, ROCm
`10.0.0`, `GPU_MAX_HW_QUEUES=2`), at commit `f3b20c1f2` with a clean tracked
tree. The audit's "what is gfx1100-only" question now has a mechanical answer
instead of a reading exercise: the gfx1151 package aliases the gfx1100 key space
and subtracts an explicit list. At this commit the two backends hold **1307
shared variants, 105 gfx1100-only variants, 7 gfx1151-only variants, 241
declared exclusions, and 18 body overrides**, and exactly **five** gfx1100-only
variants sit on the Qwen3.8-27B dense path. Each of the five carries a written
reason and a named gate that would clear it, so the remaining gfx1100-only
surface is a short, enumerated list rather than an unknown.

Four rows changed status; one real code finding fell out of the review.

- **A1 (decode GEMV floor) is closed by measurement.** Dense decode streams
  ~89% of the practical read roof, so the row no longer gates anything.
- **C4 (INT8 KV) is the largest gfx1151 lever and is now being re-checked.**
  gfx1151 records the capability as *rejected* while gfx1100 records the same
  quant/KV/scale contract as *qualified*, and the gfx1151 rejection predates
  the current paged-attention owners.
- **B2 (integer MMQ) is reversed.** gfx1151 is the donor, and the open item is
  on the gfx1100 side.
- **D1 narrowed to one named key** (`paged_kv_write / gguf_q4_k_m /
  mixed_bf16_shared_batch_spans`).

The code finding: `hipengine/runtime/qwen35_paro.py` resolves every
paged-attention decode through a hardcoded `_PAGED_KV_REGISTRY_BACKEND =
"hip_gfx1100"`, so PARO on gfx1151 bypasses the gfx1151 package's own body
override for `paged_attn_decode / w4_paro / bf16_context_batch_c1_exact_spans`.
That override is the only one of the 18 that changes the reduction rather than
the geometry, and PARO is a live gfx1151 lane, so the divergence is on the
shipped path. Recorded in `docs/REFACTOR.md` rather than fixed here, because
fixing it means threading a backend through `Qwen35ParoDecodeState` and that
needs a gfx1151 PARO-vs-GGUF parity check alongside it.

The published `Q4_K_M` lane was reproduced end to end and its two blank topline
cells filled (380.366 tok/s prefill / 12.213 tok/s AR decode at 512/128). The
published `Q4_K_S` row turned out **not** to be reproducible on this host: its
artifact is absent and the local `UD-Q4_K_S` file is a different model.
