# Expert forward uses the uniform selected dispatch; registration cannot rely on import order

## Summary

The Gemma 4 expert forward now runs one selected-expert projection over all
compact rows instead of looping one GEMV per non-empty expert. The
device-to-host read of `expert_start` is gone from the projection path.

Two things made this necessary rather than merely faster: Q5_1 has no plain raw
linear kernel, so the offset path could not serve `ffn_down_exps` at all; and the
uniform registry key `linear/<quant>/selected_gemv_bf16_bf16_out` covers every
quant type in the artifact, so there is one route and no per-quant branching.

The bf16 path keeps the offset loop. That is a check on the weight's storage form,
not on a quant name: the selected family is a GGUF quantized-block concept and a
bf16 weight is not a GGUF quant. `gemma4_project_experts_selected` returns
`False` for it and the caller falls back, which is the same type dispatch
`gemma4_project` already does.

## A real bug: registration does not survive import order

`gemma4_project_experts_selected` first relied on a lazy
`import hipengine.kernels.hip_gfx1100.quant` to trigger registration. The test
passed alone and failed when the whole file ran.

`tests/conftest.py` snapshots the registry at `pytest_collection_finish` and
restores that baseline after every test. An earlier test in the file registered
the quant family *during its body*; its teardown restored a baseline that predated
it; and by then the module was already in `sys.modules`, so re-importing it
re-registered nothing. The lookup then reported a kernel missing that exists and
works.

The fix is the mechanism the GGUF runtime dispatch already uses:
`_ensure_linear_kernel_registered(key)`, which checks `is_registered` and re-runs
the registration functions if not. Its own comment describes this exact failure —
"keep GGUF runtime dispatch independent of previous test/import order".

Worth naming because the symptom is nasty: the test is green in isolation and red
in a suite, which reads like a flaky test rather than a design error.

## The test

`test_selected_expert_dispatch_matches_the_bf16_offset_path` compares the selected
path against the offset path, which is already validated against the CPU
reference. It builds a grouped expert-start array, runs the offset path over
rows grouped by expert, and ungroups the result before comparing, so the two are
compared in the same row order.

It also asserts that the selected path has an effect: rows 0 and 3 request the
same expert and row 2 a different one, and the test requires rows 0 and 2 to
differ. A kernel that ignored `selected` and used one expert for every row would
pass a plain agreement check but fails that one.

| Q5_1 `layers.0.ffn_down_exps` | True | 0.270% | 0.313% | 0.309% | 0.344% |
