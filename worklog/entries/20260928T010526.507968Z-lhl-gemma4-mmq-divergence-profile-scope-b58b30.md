# production permits cross-width drift, so the MMQ divergence is a profile-scope finding

## Summary
Correction to
`worklog/entries/20260928T010419.970827Z-lhl-gemma4-mmq-prefill-decode-divergence-e5e16f.md`,
which is committed and therefore not edited. The bisect and the causal
attribution in it stand unchanged: commit `940255881` flipping the fused MMQ
gate/up route on is what makes `test_incremental_decode_matches_a_dense_prefill`
fail, and `HIPENGINE_GEMMA4_MOE_GATE_UP_MMQ=0` makes it pass at HEAD.

What that entry got wrong is the *status* of the divergence. It called it "a
batch-composition invariance violation" and framed the repair as an
arithmetic-promotion decision the lead owns. Reading the normative contract:

`docs/EXECUTION-PROFILES.md` section 2 gives `production` -- the normal
deployment profile -- a batch-composition contract of "**Cross-width
generated-ID equality is diagnostic, not a promotion requirement.** Same-width
neighbor data must never contaminate a request." The profile that promises
cross-width equality is `batch_invariant`, which is opt-in through
`LLM(..., execution_profile=...)`, server `--execution-profile`, or
`HIPENGINE_EXECUTION_PROFILE`.

So a `lanes`-dependent route selection that changes the arithmetic between a
4-wide prefill and four 1-wide decodes is **permitted on the default path**. It
is not a defect against the shipped contract, and it is not a bug in the MMQ
route, which passed its own teacher-forced gate. The correction matters because
the earlier entry's framing would have made an open lead decision look like a
bug that had to be fixed.

## Changes
- No code change. This entry records the corrected scope of the finding.

## Validation
- The contract text is quoted directly from `docs/EXECUTION-PROFILES.md`
  section 2, whose front matter declares it `normative` and owning
  "strict/production/batch-invariant contracts". Its status is `normative`, so
  it binds.
- Two things the earlier entry asserted that remain true and are not weakened:
  the failure is real and reproducible at HEAD (identical `max abs diff 4.417`),
  and the cause is a single named commit confirmed by the flag's rollback.
- **One consequence that is a real defect, stated precisely.** The chunking
  argument that set `DEFAULT_PREFILL_BLOCK = 512` in
  `20260923T043353` rested on this exact test: "a one-token-at-a-time path is
  already bit-identical to a dense prefill, which is the same computation as a
  two-block split". With a `lanes`-dependent route, splitting a prefill into
  smaller blocks changes `lanes` and can change the route, so **block-split
  exactness no longer holds** and that justification is stale. The default
  itself is still the right call on memory grounds, which is what that entry
  measured; only the invariance argument for it needs re-deriving.
- **A second consequence that is a real defect.** The runner's own unit test
  asserts cross-width logit equality on the default path, which is a stronger
  property than `production` promises. Either the test is asserting a
  `batch_invariant`-scoped property without saying so, or the runner intends a
  guarantee it does not have. Both readings are worth resolving, and neither is
  resolved here: relaxing a test to match observed behaviour is exactly the move
  that hides a defect, so the test is left failing and loud.
- No correctness gate applies: no code changed and no performance claim is made.

## Next
- **Decide the test's scope, not the arithmetic.** The arithmetic is already
  contract-compliant for `production`. What is unresolved is whether
  `test_incremental_decode_matches_a_dense_prefill` should (a) assert its
  property only under `batch_invariant`, (b) assert a documented cross-width
  tolerance for `production` while keeping exactness under `batch_invariant`, or
  (c) remain as a known-failing diagnostic. That is a call about what the
  default path promises, which is the lead's.
- **Re-derive the `DEFAULT_PREFILL_BLOCK` justification** without the
  block-split-exactness argument, or restore exactness by making the route
  selection independent of `lanes`.
- **MTP is the case where this stops being diagnostic.** A draft and a verify
  pass run in different batch shapes by construction, so an MTP loop on this
  branch would draft with one arithmetic and verify with another unless it runs
  under `batch_invariant`. That is an argument for the head's draft/verify loop
  being scoped to `batch_invariant` from the start rather than an argument for
  changing the MMQ route.
