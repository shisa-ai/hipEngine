# Native-cycle diagnostic: consumed-input control and packed lane resolution

## Summary

The committed diagnostic (e185c4625) compared the native commit against the
wrong token sequence and mislabelled packed request groups. Both are fixed and
covered by executable CPU tests.

`_run_ar_control_arm` was called with `native_arm["visible"]`, which is
`drafts[:accepted] + [target_top1[commit_row]]` -- the output predictions. The
N2 graph consumes and commits `input_token_ids[:commit_row + 1]`: the root input
plus the accepted drafts. The two lists have the same length, so the cursor
matched while the sequence did not: the control dropped the root input and
stepped the bonus prediction that the graph never fed back. The previous
`state_numeric_delta` and `ar_control_vs_native` calculations would therefore
compare different token sequences. No GPU result from that version was used to
clear the native path.

The same mistake appeared in the fingerprints. Native recorded
`result.token_ids[-1]`, the unconsumed bonus prediction; it now records
`result.commit_token`, which the ownership contract independently proves equals
`input_token_ids[commit_row]`. The AR and serial arms recorded their own
predictions; they now name the last consumed input, `verifier_inputs[-1]`.
That also removes a false `inconclusive_serial_control_mismatch`: `ar_vs_serial`
compares fingerprints, so one top-1 difference between the AR and serial arms at
the last row used to make the whole run inconclusive.

`resolve_lane(auto, ...)` returned the singleton lane for a two-request group and
for the explicit `packed_c1_target` route. `auto` now follows the request group,
and an explicit singleton claim on packed work raises instead of relabelling it.

## Changes

- `scripts/gguf_mtp_native_state_attribution.py`:
  - `ar_control_consumed_tokens(commit)` returns
    `input_token_ids[:commit_row + 1]`, and returns `[]` for a commit row outside
    the captured inputs (negative, past the end, or no inputs).
  - `_run_ar_control_arm` takes `consumed_input_tokens` instead of
    `visible_tokens`, raises on an empty list, steps exactly those tokens, and
    fingerprints `consumed[-1]`. The report field is now
    `consumed_input_tokens`.
  - `_run_native_arm` fingerprints `result.commit_token`, records
    `input_token_ids` and `consumed_input_tokens` in the commit block, and passes
    the verifier row count and the expected linear layers into the capture and
    ownership checks.
  - `_run_ar_arm` and `_run_serial_arm` fingerprint `verifier_inputs[-1]`.
  - `main` derives the control's tokens from the native commit block. When the
    device commit row falls outside the captured inputs the control is skipped,
    `ar_control_skipped` names the reason, and the ownership contract decides the
    verdict.
  - `resolve_lane`: `auto` resolves to packed for `request_count >= 2` or an
    explicit `packed_c1_target`; explicit `singleton` raises on either.
  - `session_factory` and `fingerprint` are keyword-only seams on the AR,
    control, and serial arms so CPU tests can run the real arm bodies against a
    recording session. Defaults are the GPU path, unchanged.
- `tests/test_unit_gguf_mtp_native_state_attribution.py`: 17 new tests, 56 total.
- GPU execution exposed two additional control-harness defects. AR steps return
  logits shaped `[1, vocabulary]`; the arm now normalizes each row before
  stacking it. Both AR arms now pass `capture_hidden_seed_fp32=True` to `step()`
  before fingerprinting that buffer, rather than reading the last prefix seed.
  Both changes have RED/GREEN regressions.

## Commit-contract repairs

Inspecting `commit_ownership_check` and its capture helpers found three concrete
defects beyond the two the review named:

- An out-of-range `commit_row` raised `IndexError` from
  `input_tokens[commit_row]` instead of reporting anything. It is now an
  `accept.commit_row` mismatch with `out_of_range: True` and
  `commit_row_in_range: False`, and `_capture_commit_rows` refuses to read a
  source row past the captured rows (the offset would address memory the
  verifier never captured).
- A `target_top1` list shorter than the verifier rows raised `IndexError` from
  `target_top1[commit_row]`. It is now an `accept.target_top1_rows` mismatch, and
  the committed-token comparison is skipped rather than guessed.
- Partial layer capture was reported as `exact`. `_capture_commit_rows` skips a
  layer whose source pair or destination is missing, and the check counted only
  the layers it received. The record now carries `expected_layers` (the model's
  `LINEAR_ATTENTION` layer ids, from `_expected_linear_layers`) and every missing
  layer is reported separately in `missing_captures`. Missing capture makes the
  copy contract `not_checked`, not `exact` and not a proven copy failure. The
  native arm also requires a hidden-tap capture; a missing hidden row is likewise
  inconclusive. A proven byte mismatch still fails even if another capture is
  missing. The result reports `layers_expected` next to `layers_checked`.
