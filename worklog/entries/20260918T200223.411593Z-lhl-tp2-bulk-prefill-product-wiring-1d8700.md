# Wire bulk prefill into the TP2 product path

## Summary

The rank-local bulk prefill candidate was reachable only from
`teacher_forced_logits` and the diagnostic scripts. `MlpTP2GenerationSession.generate`
- the method a user actually calls - walked the prompt token by token no matter
how the session was built, so `bulk_prefill=True` bought a second resident
weight set and the extra workspace and changed **no schedule at all**. The
candidate is now consumed by `generate`, and the throughput picture changes
completely:

| Route (512-token prompt, 128 decode, c=1, same session) | Prefill tok/s | Decode tok/s | VRAM/rank |
| --- | ---: | ---: | ---: |
| token-serial (committed) | 39.44 | 38.78 | 12.40 GiB |
| bulk, `bulk_prefill_rows=2048` | **385.84** | 39.21 | 22.51 GiB |
| bulk, `bulk_prefill_rows=640` | 152.54 | 39.20 | 16.05 GiB |

**9.8x prefill** on the same session, same prompt, same revision, with decode
and the gate untouched. The doc's "0.045x the single-card bulk route" is now
**0.44x** (385.8 against the single-card bulk route's 875.8), and prefill stops
being the route's defining deficit.

## Changes

- `hipengine/distributed/tp2_generate.py` - `generate` calls `bulk_prefill(prompt)`
  once when the session has it enabled, emits one `prefill` step trace for the
  whole prompt (with the wall of the bulk call, so a rate measured from
  `step_traces` is right), seeds `next_token` from the last bulk row and starts
  the loop at the first decode position. The docstring no longer promises a
  token-by-token prefill unconditionally.
- `scripts/tp2_c1_bench.py` - `--bulk-prefill` and `--bulk-prefill-rows`, and
  `_rate(..., tokens=...)`. The old accounting counted prefill **steps**, which
  coincides with the token count only for the token-serial schedule; scoring the
  bulk route's single step as one token reported 0.38 tok/s for a 210 tok/s
  prefill. This is a harness bug that would have hidden the win.
- `tests/test_unit_distributed_tp2_generate.py` - `test_generate_consumes_the_prompt_through_bulk_prefill`
  (RED before the wiring: the bulk row cannot be consumed by a token-serial walk,
  so the fake raises) and the contrasting
  `test_generate_keeps_the_token_serial_prefill_when_bulk_is_off`.
- `tests/test_unit_scripts_tp2_c1_bench.py` - new; pins the step-vs-token rate
  accounting that produced the bogus 0.38 tok/s row.

## Correctness

The full-suite production gate passes **with** the candidate
(`benchmarks/results/2026-09-18-w7900-tp2-bulk-prefill-gate-even.json`):
831 rows, mean KL 2.895e-04 (< 1e-3), p99 3.452e-03 (< 2e-2), max KL 4.2273e-02
(< 5e-2), top-1 99.64% (>= 99%), 3 flipped rows, all four categories inside
their top-1 bars, 3-sweep determinism, controls byte-identical, resolved
`prefill_schedule=bulk-tp2`.

The committed token-serial control at the same split, same revision
(`benchmarks/results/2026-09-18-w7900-tp2-serial-gate-even.json`) is numerically
better: max KL 1.2125e-02, top-1 100%, 0 flips. So the bulk route is a pass with
a thinner tail (4.2e-02 against a 5e-02 ceiling), not a free win.

The doc's blocker paragraph says both diagnostic prompts "still exceed the
production envelope" and cites max KL 0.167053 against the **resident TP1 bulk
teacher**. That measurement is bulk-vs-teacher; the envelope in
`docs/EXECUTION-PROFILES.md` binds the arm-vs-control comparison, which is what
the gate above scores. The 12-row post-residency smoke measures bulk-vs-teacher
max KL **0.000372** on the same `mixed_ja_en_translate` prompt the doc cites at
0.167053, so the teacher-relative gap has also moved a long way from that
number - but the 12-row window is a tail-blind sample and is not the basis for
any envelope claim. Both readings are now recorded rather than one replacing
the other.

## Promotion status: blocked on memory, not on correctness

The candidate is left opt-in. The blocker is concrete: `bulk_prefill_rows`
defaults to the session's `max_sequence_length`, so a 2048-token session
allocates a 2048-row bulk workspace and rank 1 (24 GiB XTX) ends at **22.51 of
24.00 GiB**. That leaves 1.5 GiB of headroom, which precludes the 0.44/0.56
uneven split and any long-context ladder point on the same pair. The 640-row
workspace costs 16.05 GiB and fits, but measured 152.54 tok/s - and its three
runs were still climbing (96.3, 133.1, 152.5), so it is not converged and may be
JIT-warming a rows-dependent variant rather than genuinely slower. Convergence
is being measured; the workspace-sizing unit follows.
