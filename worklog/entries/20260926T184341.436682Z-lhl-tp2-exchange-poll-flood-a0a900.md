# Bound the spin-add polling grid: 512-token prefill 1038.9 to 1216.5 tok/s

## Summary

The TP2 route's two per-layer device reductions were 39% of the 512-token
prefill wall, and the cost was the flag protocol rather than the payload. Each
spin-add block's lead thread polls the peer's flag, which lives in host memory,
so one poll is a full 64-byte PCIe transaction on the link the payload read is
using. The kernel launched one block per 256 payload elements, so a 512-row
prefill had 10,240 pollers flooding that link while they waited.

## Evidence

Isolated, two ranks, `CompiledDeviceExchange` at the prefill shape (512 rows x
5120 hidden bf16, 5.24 MB per rank per direction):

| arm | ms/reduction |
| --- | ---: |
| shipped kernel (10,240 pollers) | 1.440 |
| bounded grid, 64 pollers | 0.875 |
| bounded grid, 256 pollers | 0.906 |
| bounded grid, 1,024 pollers | 0.935 |
| same work with the wait removed (upper bound) | 0.895 |

Supporting measurements that ruled out the alternatives:

- Copy engine round trip for the same bytes: **0.751 ms** (13.96 GB/s);
  two-rank concurrent staging with no flag protocol: **0.786 ms**. The
  transport is not the problem, and it does not degrade under concurrency.
- A kernel reading host memory at the production access pattern reaches
  **13.3 GB/s**, the same as the copy engine, and vectorizing the read changes
  nothing (13.3 GB/s at 16 B and 32 B per thread). The read pattern was not the
  problem either.
- P2P is not available here: `hipDeviceCanAccessPeer` returns 0 in both
  directions and the ACS redirect bits are set on both GPU bridges, so staging
  through pinned host memory is the only route. `s_sleep`-based backoff did not
  help (1.498 -> 1.588 ms), consistent with the hint being ignored.

## Changes
`tp2_dev_spin_add_bf16` takes a grid-stride pass over the payload and the launch
bounds its grid to `kSpinAddMaxBlocks = 256`. Poll count drops 40x; the payload
still streams from 65,536 threads. Decode's own grid (20 blocks at one row) is
below the bound either way, so its launch is unchanged.

## Validation

- **Numerically free, exactly.** The exchange payload bytes are identical to the
  shipped kernel on both ranks at 1 and 512 rows, and end to end
  **8,939,520 logits values are byte-identical**: 32 prompt rows of the head
  projection (32 x 248,320) plus four graphed decode steps, with only the
  device-exchange library differing between the arms. The teacher gate's numbers
  therefore transfer by construction rather than by re-measurement.
- **End to end on the shipped route**, `scripts/tp2_prefill_phase_attribution.py
  --prompt-tokens 512 --repeats 3 --attention-shard` on `epyc` (W7900 device 0 +
  RX 7900 XTX device 1, Qwen3.8-27B `Q4_K_M`): wall **492.8 -> 420.9 ms**,
  **1038.9 -> 1216.5 tok/s (+17.1%)**; `attn_reduce` 96.0 -> 51.6 ms and
  `mlp_exchange` 95.6 -> 51.5 ms. Both now sit at the transport floor (0.806 and
  0.805 ms per layer against 0.786 ms measured for the same round trip with no
  flag protocol), so what remains is the PCIe round trip itself.
- **Matched c=1 cell** (`scripts/tp2_c1_bench.py --mode tp2 --prompt-length 512
  --decode-tokens 128 --repeats 3`): prefill **1066.3 -> 1216.95 tok/s
  (+14.1%)**, decode **41.64 -> 41.55 tok/s** (unchanged, as expected: at one row
  the grid was never a flood and the reduction is launch-bound).
- CPU: 142 cases across the device-exchange, tp2-generate, staged/shard and
  shard-group unit suites. GPU: `tests/test_gpu_distributed_exchange_capture_state.py`
  (capture state and the unobserved-work refusal) passes.
- Tree sweep for the same pattern: the other spin loops in the tree
  (`paro_awq_gemv.hip` barriers, `moe/router.hip` completion counter) poll device
  memory, which is L2-cached, so this was a single instance.

## Notes

- The `mlp_chain` phase gained 10.5 ms back (171.6 -> 182.1 on rank 0) inside an
  `mlp` phase that improved by 33.5 ms overall. Recorded as measured, not
  explained.
- A first ladder run of this revision stalled on the 768-token row (468.7 tok/s
  against 1051.2 before); the artifact was re-recorded rather than quoted. The
  re-recorded run measures 1226.4 tok/s on that row.
- A second ladder attempt stalled host-side rather than on the device: `py-spy`
  showed the process inside `CompiledStagedExchange.reduce` ->
  `tp2_staged_reduce_rows` (the *staged* transport's `hipStreamSynchronize`, a
  file this change does not touch) in the graphed build's eager warmup, burning
  200% host CPU with no syscall while **both** cards reported
  `Last signaled fence == Last emitted` on `gfx_0.0.0`, i.e. no outstanding
  device work, and `dmesg` had no `amdgpu` reset or ring timeout. That is a
  host-side lost wakeup in the runtime's stream sync, and it did not reproduce
  on the next run of the same command. Recorded as an observed runtime event:
  it is intermittent, it is in a transport this change does not modify, and the
  GPU was idle when it happened. Four idle `clang++` processes from two days
  earlier are still holding `/dev/kfd` in this environment; they are cruft, not
  a demonstrated cause.

## Next

The exchange is at the host-staged transport floor. The remaining lever is
pipelining: the read cannot overlap the peer's staging copy because a payload
still being written would be read stale, but per-chunk flags would overlap them
and turn `copy + read` into roughly `max(copy, read)` (~0.45 ms against
0.79 ms per reduction, up to ~45 ms per prefill). Recorded in `docs/REFACTOR.md`;
not attempted here.
