# The census's GDN lever was already known, already built, and already priced slower — iteration 40's claim retracted

## Summary

Iteration 40's prefill stall census measured `qwen4_exp_gdn_prefill_f32_kernel<true,true>`
at 5.93% of prefill device time, 9.6 waves per busy CU cycle, and **0.92 instructions per
CU-cycle** (~23% of the issue ceiling) with `VGPR_Count` 256 and `LDS_Block_Size` 0, and
named **state-in-LDS** as a new, unblocked lever. **That claim is retracted.** It is wrong
on three independent grounds, and the third is fatal.

This entry corrects the ledger row, the census artifact, and the benchmark rollup rather
than leaving a wrong lever in the ranking. The census's *measurements* stand; only its
*ranking conclusion* was wrong.

## Changes

### 1. Not new — the kernel's own comment already says it

`hipengine/kernels/hip_gfx1100/linear_attn/qwen4_exp_gdn.hip:1110-1117`, written by an
earlier unit:

> The UD-Q4_K_XL production lane's recurrence — the wave-norm register route,
> `qwen4_exp_gdn_prefill_f32_kernel<true, true>` — holds 128 floats of state per thread and
> compiles at **VGPR_Count 256, the hardware maximum, which permits only 2 waves per SIMD
> of a 64-wave-per-CU maximum (~12.5% occupancy). It is latency-bound by register-file
> capacity, confirmed by hardware counter.**

The 256-VGPR register-file-capacity finding, and its hardware-counter confirmation, were
already recorded at the site. I read the census numbers off a profiler and presented a
conclusion that was written in the source file I had not opened.

### 2. Not unbuilt — the LDS route exists and is GD-4

`qwen4_exp_gdn_prefill_wy_f32_kernel` (the Woodbury-Young chunked form, `20261001T`) keeps a
128x32 state tile **in LDS** at 28,576 B with 16 state elements per thread instead of 128,
which is precisely the lever. It is correct: state parity against tiled16 is 5.59e-09 max
absolute, and it also matches an fp64 serial GDN recurrence.

**And the state does not fit in LDS anyway.** The full tile is 128 x 128 floats per v_head =
**65,536 B, the entire per-block LDS budget on this hardware.** GD-4 had to shrink the tile
to 128x32 and chunk 8 tokens to fit it. There is no version of this lever where the state
simply moves.

### 3. Not faster — and worst exactly where the campaign is aiming

GD-4's own artifact (`benchmarks/results/2026-10-01-qwen4exp-gd4-wy-kernel-built/artifact.json`)
records the LDS route against **the current UD production route** (`wy_vs_wave_norm_ud_lane`):

| rows | wy_chunked vs current UD production route |
| ---: | ---: |
| 512 | **1.0546x** |
| 1024 | 0.8727x |
| 2048 | 0.7922x |

At `code-p4096` — the case the census profiled — this is a **~20%+ regression**, and the one
arm it wins is `1.0546 x 5.93% = +0.3%` of the prefill window. Against the other routes it
is worse still: 0.83/0.82/0.87 against tiled16_nonmulti and 0.44 against
`tiled16_multi_nonud_lane`.

Register counts from the same artifact, which is what makes the shape of the problem clear:

| route | VGPR | LDS | selected by profile |
| --- | ---: | ---: | --- |
| wave_norm (UD production, `<true,true>`) | **256** | **0** | **yes** |
| register_state (`<true,false>`) | 256 | 0 | no |
| columnwarps | 46 | 0 | |
| tiled16_nonmulti | 56 | 16,640 | |
| **tiled16_multi_production** | **85** | 16,640 | **gated off in UD** |
| wy_chunked (the LDS route) | 169 | 28,576 | |

### What the census legitimately adds, and where the real lever is

**Kept:** the *share*. 5.93% of prefill device time at chunk 4096 for the register route had
not been quantified for the UD lane, and the 0.92 inst/CU-cycle rank is a genuine
worst-in-class placement. The census's central finding — that the prefill is **not**
uniformly stalled, HC-1 being the only LDS-stalled family at 30.82% against <=0.35% for
everything else — is untouched by this correction.

**The real lever is a profile question, not a kernel rewrite.** `tiled16_multi_production`
escapes the register bound at **85 VGPR** and is gated off in the UD lane because
`GDN_COLWARPS_PREFILL` is one of `PRODUCTION_ARITHMETIC_RECOVERY_FLAGS`
(`hipengine/generation/qwen4_exp_profiles.py:62`), so the UD binder sets it to `"0"` and
closes the gate the variant feeds. And that route's own q4_k_m gate **already fails**
(max KL 0.05958, `benchmarks/results/2026-09-30-qwen4exp-gdn-multicolumn-q4km/gate.json`) —
which is why it is gated off. That is the same numerical-envelope threshold question as
every other blocked prefill lever, not a new engineering route.

## Validation

Read-only: no kernel, no default, and no engine code changed. The pricing came from
committed artifacts (`2026-10-01-qwen4exp-gd4-wy-kernel-built`), the kernel source at the
cited lines, and the profile binder's own flag list — no GPU run was needed, and none was
taken. Ledger row corrected in place; census artifact and `benchmarks/README.md` corrected
to drop the lever claim and keep the measurement.

**The durable rule this is the fourth instance of:** a register count that explains a
measurement is not evidence that the explanation is new. Check the kernel comment and the
artifact directory for the route before naming it a lever — the census cost 25 minutes of
GPU time to re-derive a conclusion that was already written down, twice.

## Next

The GDN register route is **closed** — no reopen condition is met, and the ledger row now
says so. What is left in this family is the profile question, not a kernel: the 85-VGPR
`tiled16_multi_production` route escapes the bound and is gated off in the UD lane, and its
own q4_k_m gate already fails at max KL 0.05958. That is the same numerical-envelope
threshold decision as the other blocked prefill levers (the dense-wide scope boundary and
HC-1's staging screen), so it belongs to the campaign's threshold question rather than to a
kernel unit.

Ranked levers after this correction, unchanged in shape from iteration 40's list minus the
GDN entry:

   near the issue ceiling — **not** levers.
