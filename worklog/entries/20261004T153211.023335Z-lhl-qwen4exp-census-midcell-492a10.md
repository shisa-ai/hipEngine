# The head+tail method failed on 4 of 72 rows — and X-6 is fixed, unblocking DP-7

## Summary

Iteration 159 read all 72 status cells head and tail and reported 26 rows needing work. **That
method is insufficient, and my own iteration-159 hypothesis named exactly how.** It said: *"if
reading both ends still leaves a row whose state is stated only in the middle of a long cell, then
the head+tail method is as insufficient as the two positional methods."* I then reported the count
without running that check. This iteration runs it.

**Result: 25 of 72 rows state a status token mid-cell that head+tail misses, and 4 of those
actually flip the row's state.** Corrected census: **21 open + 3 partial + 14 gated + 33 closed +
1 not-a-candidate = 72** — **24 rows needing work**, not 26.

## X-6 is fixed, and its cause was not the one I assumed

**X-6 is closed, and the fix is verified in-tree:** commit `ccd9f7a84` (*fix: clear the wide route in
both arms of the wmma gate*), test `tests/test_unit_qwen4exp_wmma_gate_route_arms.py`, **2 passed**.

**Its recorded cause is also not the memoization key.** That was the *first* revision, and X-6's own
cell records it as **withdrawn**: *"the false pass reproduced unchanged with the key fix in place"*.
The real cause:

> the route cleared only its own selector, never `HIPENGINE_QWEN4_EXP_Q8_DENSE_WIDE`, which the
> certified plan binds to 16-47; `_q8_dense_wide_claims_parent` accepts the wmma-rewritten parent
> as well as the exact parent, so **the wide route claimed the dispatch in both arms and the gate
> compared one configuration against itself.** Fixed by clearing the wide route in both arms, as
> the composed and staged routes already did.

**I assumed the memoization-key fix was the resolution because I found its code comment first** —
`_q8_wmma_layers_scope()`, which documents the *same* failure mode ("the key cannot observe a
`ContextVar` holding a callable, which is exactly how the teacher arm of a numerical gate came to
replay the candidate arm's dispatch"). That fix is real and landed (`a7ad30e5f`), but it fixed the
**staged-f32** route, not X-6's. **Reading the code before the ledger produced a confident wrong
conclusion in one step** — the same shape as the five earlier corrections, with the sources
swapped.

## What this unblocks

X-6 was, per the reading pass, the **sole blocker** on DP-7's chunk-4096 promotion — a measured
**−4.94%** complete-engine prefill win (15.625 s → 14.854 s on Radeon 8060S gfx1151, UD-Q4_K_XL,
production profile). **X-6 being fixed means that blocker is gone.** DP-7's own cell says
promotion is "blocked only on `X-6`", so DP-7 should now be re-checked for promotion rather than
left in the gated set. This is the highest-value consequence of the whole census thread and it is a
one-row follow-up, not a campaign.

  proven right.
