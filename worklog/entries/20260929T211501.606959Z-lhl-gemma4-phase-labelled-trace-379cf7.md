# Checkpoint: phase-labelled dispatch trace, and why production==strict staging is wrong for gemma4

## Summary

Step 1 of the recorded plan is done: every registry-resolved key now carries a
prefill/decode label with counts that reconcile against independent
measurements. In working through those counts, this entry also **corrects a
safety-relevant claim in the two preceding entries** -- that registering
"production selections byte-identical to strict" is behaviour-preserving. For
gemma 4 it is not, because the routes that run today are changed-arithmetic
relative to strict, so production and strict are genuinely different sets and
declaring either one as the other changes what executes.

## Validation

### Method, corrected mid-run

The first attempt differenced a `max_tokens=1` run against `max_tokens=5` and
divided by 4. It produced `P = -29` for two keys and a non-integral delta for a
third, because **`max_tokens=1` needs no decode step at all** -- the first token
comes out of the prefill logits -- so that arm is `P`, not `P + 1*D`. The
working method differences runs that differ by **exactly one decode step**
(`max_tokens=2` vs `max_tokens=3`, both on 1024-token prompts of different
text so prefill work is identical), giving `D = B - A` and `P = A - D` with no
division and no assumption. All 12 keys came out non-negative.

### The correction

The two preceding entries advise registering **production selections identical
to strict** as a behaviour-preserving staging step. That advice rests on an
unverified equivalence, and I could not verify it:

- The routes that run on the default path today are the ones in the table above
  -- `mmq32` dual prefill, grouped WMMA prefill, `wmma_prefill`, `pack8_gemv` --
  measured with no route env vars set, so they are what an omitted profile
  actually executes today.
- **Whether those routes satisfy the strict contract is not established
  anywhere I could find.** `promotion_qualified: false` appears repeatedly in
  `GEMMA4-26B-A4B-OPTIMIZATION.md` ("the campaign logits gate is necessary but
  not sufficient; the execution-profile gate ... is the named clearing command",
  and "the route stays opt-in and off the default path until that gate runs").
  A search of `docs/` finds no exactness claim for `gemma4_mmq32_prefill`, and
  the punchlist does not mention that kernel at all. (An earlier draft of this
  entry cited "X2" for such a claim and quoted the phrase "Exactness not
  established"; both were wrong -- X2 is the XTX headroom row and the phrase
  does not exist in the tree. Struck rather than softened, because the citation
  was the whole basis of that version's argument.)
- So the equivalence is **unestablished in both directions**, and that is
  exactly the gap the gate exists to close. Registering both profiles from one
  tuple set would either assert an equivalence nobody has proven, or -- if the
  strict set turns out to differ -- silently move the default path onto
  different arithmetic while being presented as a no-op. Neither is acceptable,
  and neither is what the staging note should have recommended.

The ordering advice stands in shape ((A) must precede (B), because
`resolve_runtime_profile` raises without it), but the *content* of (A) is now
clearer than either prior entry stated: **production selections are the measured
table above, and strict selections are a set that must be curated with a named
exactness property per scope before anything registers.**
