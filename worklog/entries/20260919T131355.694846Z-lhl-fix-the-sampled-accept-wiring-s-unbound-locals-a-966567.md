# Fix the sampled-accept wiring's unbound locals and correct the no_provider attribution

## Summary

The previous unit's wiring (`3db16a0d2`) had two Python scoping defects that a
serving run hits immediately: a sampled-accept plan created as a
`propose_batch` local and read in `execute_target_frontier`, and a
`sampled_library` bound only inside one branch of the N2 capture and read
unconditionally at the end of it. Both raise, both are *contained* by the engine
loop, and a contained failure drops the request with `disable=True`, so every
later cycle plans `no_provider`: MTP was dead in serving for **all** rows,
greedy included, and the only trace was a single `[cycle-failure]` line.

This entry also **corrects the previous entry's attribution**. That entry
reported that MTP did not attach a provider "independently of sampling mode and
independently of this unit", on the strength of a greedy control that failed the
same way. That conclusion was wrong: the greedy control failed *because of* this
unit's own defect. The greedy path reads the same `sampled_device_plan` name in
the shared singleton `prepare(...)` call, so no row could enter a cycle.

A third instance of the same predicate confusion was fixed while re-measuring:
the adapter's route probe and the device-plan admission both read the row's raw
request through `speculative_sampling_mode(params)`, which answers `processed`
for a temperature request that carries EOS, while the planner (reading the
scheduler's resolved sampler block) answers `sampled` for the same row. The
planner's answer is now recorded per request in `capability()` and reused by both
adapter-side probes.

## Changes

- `hipengine/generation/qwen35_gguf_mtp2.py`
  - `_MTP2RequestState.sampled_accept_plan` carries the staged-draw plan across
    the propose/execute seam; `propose_batch` publishes it and
    `execute_target_frontier` reads it (and drops it once the launch has
    consumed the draws, so a rollback cannot reuse a stale stream position).
  - `_sampling_mode_by_request` records the planner's resolved mode per request
    in `capability()`, is consulted by `_sampled_route_request` and by
    `_device_sampled_accept_plan`, and is cleared on request drop.
  - The three `[cap-silent-none]` / `[route-debug]` diagnostic fields gained the
    row's slot type, token count, fallback-output state, and prompt fallback
    reason. They stay behind `HIPENGINE_DEBUG_SAMPLED_ROUTE`.
- `hipengine/runtime/gguf_native_spec_cycle.py`
  - `sampled_library` is initialized with the other kernel handles, and the
    argmax accept kernel is resolved for both topologies: the sampled variant
    replaces its launch, not its registration, and leaving it unbound made a
    sampled capture fail its own primitive guard.
- `tests/test_unit_qwen35_gguf_mtp2_c1_physical.py`
  - `test_sampled_accept_plan_rides_the_request_state_between_phases` pins the
    seam (the plan is published on the state and read from the state). It is RED
    at `3db16a0d2`: neither the publish nor the read exists there.

## Acceptance (b) is still not met

The sampled arm measures **6.50 tok/s against its in-load 13.67 tok/s
autoregressive control = 0.475x**, which reproduces the rejected artifact's
0.47x exactly. MTP engages, acceptance is unchanged (89 accepted over 38 cycles),
and there are no contained failures, so the cost is in the cycle itself, as the
artifact's cost model said.

The device accept is still not being exercised. `_device_sampled_accept_plan`
now reads the planner's mode, so its first gate passes, but the measured cycle
cost is unchanged, which means one of its remaining gates declines. The
remaining suspects, in order: the sampled graph readiness gate
(`getattr(target, graph_name, None) is None`, which is the same
bootstrap-shaped question as the two fixed here: the graph is warmed only after
the plan exists and the plan only after the graph is warmed), `_needs_processors`
reading the unresolved request, and the verifier's own
`device_proposal_ready(budget)`. The next diagnostic is a
`HIPENGINE_DEBUG_SAMPLED_ROUTE` print of the plan gate that returns None plus the
row's `mtp2_device_accept_calls` counter after a sampled arm.

No evidence row was written and the sampled-mode guard stays closed.

## Next

- A contained execution failure disables the request's provider for the rest of
  its life, so a transient programming error in a cycle path presents as a
  silent, permanent `no_provider` on every cycle with one `[cycle-failure]` line
  as the only trace. When MTP "does not engage", read
  `grep cycle-failure` on the server log before anything else.
- `HIPENGINE_DEBUG_SAMPLED_ROUTE=1` **on the server process** prints
  `[plan-debug]` (capability set/none with the per-row reason), `[cap-debug]`,
  `[cap-silent-none]` (which clause of the capability gate failed), and
  `[route-debug]` (the adapter's own route probe). Setting it only on the
  harness shows nothing.
- The planner's mode and the adapter's raw-request mode can disagree; anything
  adapter-side that decides whether a row is sampled must read the recorded
  planner mode.
