# the gemma4 expert down projection fetches 62 GB a step re-reading its activation once per output-column block

## Summary

Two things landed in this unit, and they are different kinds of result.

**1. The fused T16 gate/up route now exists and is bit-exact against production.**
The previous entry's measured 1.13x T16 win was unreachable because gemma4's
expert weights are stored gate and up fused in one per-expert row block, while
the T16 branch indexed its tiles as though each half were its own expert. The
T16 branch now derives its tile count from the fused width and offsets the up
half's tiles past the gate half's; a `hipengine_gguf_q4_k_t16_selected_dual_q8_1_ds4_mmq32_fused_prefill_compact32_bf16_bf16_out`
entry point and its Python wrapper select the layout. The new test runs the
production raw fused route and the T16 fused route on the same weights and
asserts **bit equality**, over three count profiles including one that crosses a
32-row tile boundary. It passes.

The load-time repack this needs was measured before any kernel code was written:
`repack_gguf_q4_k_tile16` on one layer's fused gate/up tensor (128 experts,
1408 out, 2816 K, 272 MiB) takes **0.47 s**, so 30 layers is about **14 s**. That
is affordable but not free, and it is the number the route swap has to justify.

**2. The expert down projection is the largest DRAM consumer in prefill, and it
is bandwidth-bound.** `rocprofv3 --pmc FETCH_SIZE` over a real 512-token prefill,
per step:

| kernel | n | GB/step | ms/step | GB/s |
| --- | ---: | ---: | ---: | ---: |
| `gguf_q8_0_prefill_wmma_kernel` | 205 | 14.27 | 174.94 | 81.6 |
| `gemma4_attention_prefill_kernel` | 30 | 2.27 | 170.91 | 13.3 |
| `gguf_q4_k_..._ds4_mmq32_fused...` (gate/up) | 29 | 20.78 | 153.28 | 135.6 |
| `q5_1_mmq_ds4_selected_prefill_kernel` (down) | 29 | **62.33** | 118.25 | **527.1** |

The down projection's weights are 190.3 MB per layer (`ffn_down_exps` is Q5_1
`(128, 2816, 704)`), so 5.7 GB across 30 layers. It fetches **62.33 GB**, and it
sustains **527 GB/s** while doing it -- the other kernels sit at 13-155 GB/s. A
kernel running at 527 GB/s for 118 ms is bandwidth-bound by definition, so this
is the one kernel in the step where cutting bytes converts directly into time.

**The mechanism is identified in the source but its arithmetic does not close,
and that is stated rather than smoothed over.** `q5_1_mmq_ds4_selected_prefill.hip`
gives one output column to each thread (`out_col = blockIdx.x * 128 + threadIdx.x`,
grid `(ceil(out_features/128), num_experts)`), and the weight row is unpacked once
per `ROWS_PER_PASS` (=16) row pass. That predicts:

- weight re-reads: `22 blocks x ceil(32/16)=2 passes x 528 B x 128 threads` per
  expert = 415 MB per layer, 12.5 GB per step;
- activation: all 128 threads read identical addresses, so it is broadcast and
  the unique bytes are 68 MB per layer, 2 GB per step.

Neither reaches 62 GB, and the same discrepancy appears on the gate/up kernel:
the microbench prices the raw layout at 14.5 MB per (expert, row-tile), which
over the 183 row tiles a real 512-token step produces is 2.65 GB per layer, while
the real trace says 716 MB. **So the `FETCH_SIZE` column is trustworthy as a
ranking and as a bandwidth figure -- 527 GB/s is computed from it and from the
same trace's duration -- but the per-launch byte attribution is not yet
reconciled between the microbench and the real run.** The next step is to
reconcile it before acting on a mechanism, not to pick the mechanism that fits.

## Changes

- `hipengine/kernels/hip_gfx1100/quant/gguf_q4_k_q8_1_selected_prefill.hip`
  - The T16 branch of the shared body derives its output-tile count from the
    fused width when `FUSED_EXPERT_LAYOUT` is set, and offsets the up half's
    tiles by `out_features_a / Q4_K_TILE16_COLS`. The fused and non-fused cases
    are unchanged when the flag is clear.
  - New `gguf_q4_k_t16_selected_dual_q8_1_ds4_mmq32_fused_prefill_compact32_kernel`
    and its launcher branch, plus the `..._t16_..._fused_prefill_compact32_bf16_bf16_out`
    entry point.
- `hipengine/kernels/hip_gfx1100/quant/gguf_q4_k_q8_1_selected_prefill.py`
  - `_SYMBOL_T16_FUSED_DS4_MMQ32_BF16` and
    `gguf_q4_k_t16_selected_dual_q8_1_ds4_mmq32_fused_prefill_compact32_bf16_bf16_out`.
    The docstring records that both weight pointers take the **tile base**, not a
    row offset: the raw fused route offsets the up pointer by `out_features_a`
    rows, the T16 route offsets tiles inside the kernel, because a tile index is
    derived from the fused width rather than from the pointer.
- `tests/test_gpu_gguf_q4_k_q8_1_selected_prefill.py`
  - `_run_q8_1_ds4_mmq32_selected_dual_gpu` gains `fused=`, which concatenates the
    two halves on the output axis the way `ffn_gate_up_exps` stores them and
    applies the raw route's up-half pointer offset.
  - `test_q4_k_t16_fused_q8_1_ds4_mmq32_selected_prefill_matches_raw_fused`,
    parametrized over three count profiles.

No production route, loader, dispatch or default changed. The gemma4 expert
route still selects the raw fused symbol.

## Next

1. **Reconcile the `FETCH_SIZE` arithmetic before acting on a mechanism.** The
   down projection is the right target -- 62 GB and 527 GB/s is not in dispute --
   but the source-level model predicts 14 GB, so the per-launch bytes are being
   mis-attributed somewhere. A single-kernel microbench for
   `q5_1_mmq_ds4_selected_prefill` at gemma4's real shape (128 experts, in 704,
   out 2816, 32 rows/expert), run under the same counter, settles it.
2. **Then fix the down projection.** Its two candidate levers are `ROWS_PER_PASS`
   (currently 16, so an expert averaging 32 rows takes two passes and re-unpacks
   every weight row twice) and output columns per thread (currently 1, so 22
   blocks per expert each re-read the activation). Both are byte reductions on a
   kernel that is demonstrably bandwidth-bound.
3. **The T16 gate/up route swap is validated but not yet worth its cost.** The
   kernel is bit-exact and the repack is 14 s, but the gemma4 decode path reads
   the same tensor through `expert_stride_bytes` on the raw allocation, so
   swapping prefill to T16 means either keeping both layouts resident (+8.7 GB on
   a 19 GB model) or moving decode to T16 as well. At 1.13x on 24 percent of
   prefill that trade is not obviously good; the down projection above is four
   times the size for no resident-memory cost.
