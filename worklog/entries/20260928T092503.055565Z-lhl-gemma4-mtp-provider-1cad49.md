# the gemma 4 mtp provider is registered and runs through the generator but llm generate does not select it

## Summary

`hipengine/generation/gemma4_mtp.py` exists, is registered, attaches through the
`LLM` path, and its cycle runs and is measured. **`llm.generate()` still takes
the plain autoregressive route**, and that is the remaining gap. This unit stops
short of claiming item 6 shipped.

## What works

`LLM(model=..., speculative_provider="gemma4_mtp", draft_model=<sidecar>,
speculative_candidate_budget=3)` resolves and attaches. The generator reports
`supports_speculative = True`, and its speculative entry point produces:

```
execution_path: gemma4_mtp_batched_exact_verify
sampler_mode  : greedy_speculative_mtp
verify        : batched_exact bit_identical_to_target_ar_greedy
cycles        : 10   accepted: 14 / 30 = 0.467   tokens/cycle: 2.5
phase ms      : target_prefill 198.8  proposal 148.5  target_verify 578.7
```

**That is the same cycle `20260928T092027` measured at 1.37x, reached through the
generator rather than from a script.** The acceptance is lower here (0.467
against 0.742) because this is the bare "The capital of France is" prompt rather
than the chat-templated one the sweep used.

Pieces landed:

* `hipengine/generation/gemma4_mtp.py` -- the provider, with the cycle, the
  telemetry, and lazy construction of the assistant head (it needs the
  backbone's embedding and output norm, which do not exist until the target is
  materialized, and the provider attaches before that).
* `Gemma4GGUFGenerator` grows `_speculative_provider`, `supports_speculative`,
  `attach_speculative_provider`, `speculative_capabilities`,
  `generate_speculative_detailed`, `generate_speculative_mtp_detailed`, and
  `stream_speculative_detailed`, and `_ensure_runner` now sizes
  `max_logits_rows` from the attached provider's declared `max_verifier_rows`.
* `register_builtin_speculative_providers` imports the module.

## The quant-agnostic registry key, and why it is not an allowlist

The first attempt registered one key per quant name. It failed on the very first
run: the resolved quant is `gguf_q4_k_m`, which is **not** in
`registered_quants()` -- that returns scheme names (`bf16`, `fp16`, ...), a
different namespace from the resolved GGUF artifact quant. So the working
examples' pattern (a written list, as in `qwen4_exp_mtp.py` and
`laguna_dflash.py`) is a genuine allowlist, and it is the thing this project
forbids: *"Never key admission on identity... an enumerated list of known-good
`(model, backend, quant)` combinations."*

**The provider has no quantization dependence to declare.** The assistant head is
a separate sidecar and the verify reads whatever logits the backbone produces, so
the target's quantization is not an input to it. That is now expressible:
`hipengine/speculative/registry.py` gains `QUANT_AGNOSTIC = "*"`, and
`resolve_speculative_provider` falls back to it after an exact-key miss. A
provider that *does* depend on the quantization still registers exact keys and is
never matched by the wildcard, so nothing existing changes behaviour.

## What does not work, and what I tried

`llm.generate()` returns output whose telemetry is `None`, i.e. the plain route.
The engine loop's capability probe is
`SubmitPollTextGenerator.supports_speculative_mtp`, which returns False unless
`self._inner` has a truthy `supports_speculative_mtp` attribute *and* a callable
`generate_speculative_mtp_detailed`. I added both -- the method, and a property
returning whether a provider is attached -- and **`llm.generate()` still did not
route there.**

I reverted the property. `tests/test_unit_gemma4_speculative_wiring.py` pins
`"supports_speculative_mtp" not in vars(Gemma4GGUFGenerator)` for a good reason
-- any class-level declaration short-circuits `engine_loop` before it consults
the runner's staged hooks -- and **the property bought nothing, so breaking a
reviewed invariant to keep it would have been the wrong trade.** The method
stays, since `engine_loop` finds a missing attribute and a present method
correctly; the comment at the class records why the attribute is still absent.

So the route selection is elsewhere, and `LLM.generate` may not consult the
speculative capability at all -- the serving path (`submit_speculative_many_detailed`)
is the other candidate. **That is the next thing to establish, and it should be
established by reading `LLM.generate`'s path rather than by adding declarations
until something changes.**
