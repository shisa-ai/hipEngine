# packet5 C1 R5-R8 blocker: kernel rowtiles cap at 4 rows

## Summary

The C1 singleton native-verify chain at rows 5-8 is blocked by compiled
kernel rowtile bounds, not by state handling. After the rows-cap fix
(15d427a2e) the native path runs at K4+ and fails inside the target
kernels: `ValueError: rows must be 2, 3, or 4` from the fused
rounded-add-rmsnorm rowtile and the Q4_K pack8 GEMV rowtiles, recorded
per row as `precommit_failure_ar_fallback` (bg-54 failure trace).

## Changes

- 15d427a2e: `_effective_target_verify_mode` derives its native rows cap
  from `_GGUF_MTP_CANDIDATE_BUDGETS` (was `rows > 4` literal), so C1 K4+
  reaches the native spec target-graph path instead of the serial
  journal fallback.

## Validation

- C1/K4 probe bg-54: rows still exact (K0 fallback), engagement 0/10;
  per-row failures `ValueError: rows must be 2, 3, or 4` at
  `kernels/hip_gfx1100/fused/gguf_ops.py:425`
  (`gguf_rounded_add_rmsnorm_bf16_f32_weight`) and
  `kernels/hip_gfx1100/quant/gguf_q4_k_gemv.py:427/468` (pack8 rowtile /
  dual rowtile SiLU). The earlier journal invalid-arg (bg-53) was the
  serial_exact fallback; the native path is the correct route.
- The native spec target-graph layer itself accepts rows 2-8
  (`gguf_native_spec_cycle.py` "one cached B1-B7 target bucket"); the
  wall is the rowtile launch shapes inside the captured graph.
