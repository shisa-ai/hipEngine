# X-6 gate at chunk 4096 passes and is bit-identical to chunk 1024

## Summary

RT-1's first promotion blocker was the ledger's `X-6` requirement to re-run the
numerical gate at the new chunk size. Re-run at chunk 4096 for the promoted route
at canonical depth: **it passes, and both arms reproduce the chunk-1024
certification bit-identically.**

## Result

| | chunk 1024 (recorded) | chunk 4096 (this run) |
|---|---:|---:|
| teacher logits sha256 | `550bb9b8...` | **`550bb9b832bc7ba2...`** |
| candidate logits sha256 | `65370710...` | **`65370710c0b9c40f...`** |
| mean KL | 3.79552e-4 | **3.795524e-4** |
| `hard_gates_passed` | true | true |

Not merely the mean KL agreeing to six figures - the **full trajectories hash the
same**. So the route's arithmetic *and* its drift are invariant to the prefill
chunk size over 1024 -> 4096.

Other gates: p95 1.762e-3, max 1.530e-2, `top1_rate` 0.99354,
`repeat_deterministic: true`, `canonical_numerical_qualification_claim: true`,
teacher rows 1548, chunk recorded as 4096.

## Checked the false-pass mode first

This gate previously returned **KL exactly 0.0 with `measurement_valid: true`** on
a route that never ran, so a clean pass is the thing to rule out *before* reading
it as good news. Engagement is recorded here, not inferred:

- `candidate_route_engaged: true`, `teacher_route_engaged: false`
- `wmma_prefill` candidate rate **0.373585** against the teacher's **0.0**
- **792** launches of `wmma_prefill_f32_f32_out`
- `selectors_observed_in_one_arm_only: []`
- KL nonzero; teacher genuinely `exact coltile8_rowbatch4_f32_f32_out`

The recorder built earlier in this session is what makes this check possible, and
it is now part of the gate's own artifact.

## What this clears, and what it does not

**Clears** RT-1's first blocker for the promoted route.

**Does not clear** the second blocker (`RT-3`: short-request behaviour and the
+4.96 GB allocation) or `X-7`'s remaining profile blockers, which the gate still
reports unchanged: category-heldout, strict-teacher/BF16-relative,
control/isolation/graph/lifecycle, task-quality, engagement/repair-oracle. Those
are pre-existing; the chunk change neither creates nor worsens them.

**Still not promoted.** No default changed.

## Next

RT-1's second blocker: short-prompt behaviour at chunk 4096. Note that
`rows = min(chunk_size, remaining)`, so for a prompt <= 1024 tokens chunk 4096 and
1024 produce *identical chunking* - the kernels see the same rows - so RT-3's
short-request cost cannot come from different chunking and must come from the
eagerly-allocated scratch (`min(chunk, max_seq_len)`). That is a testable claim
and the next measurement.
