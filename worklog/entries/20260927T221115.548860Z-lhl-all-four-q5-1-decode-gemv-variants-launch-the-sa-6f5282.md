# All four Q5_1 decode GEMV variants launch the same scalar kernel
## Summary
The previous entry established that gemma4's decode expert projections route
through `selected_gemv_bf16_bf16_out`, the scalar Q5_1 GEMV. The obvious cheap
follow-up was to switch that route to one of the vectorised siblings the profile
file uses for qwen4, since a variant swap is a one-line change where a kernel
rewrite is not. **That option does not exist**, and finding out why took one read.
## The variants are launch configurations, not different kernels
`hipengine/kernels/hip_gfx1100/quant/qwen4_exp_q5_1.hip:2189`:
```c
extern "C" int hipengine_qwen4_exp_q5_1_selected_gemv_wave64_bf16_bf16_out(...) {
  ...
  constexpr int threads = 64;
  const int64_t row_bytes = (in_features / 32) * 24;
  hipLaunchKernelGGL(
      q5_1_selected_gemv_bf16_bf16_kernel,
      dim3(static_cast<uint32_t>(rows * out_features)), dim3(threads),
      threads * sizeof(float), stream, ...);
}
```
`wave64` launches **the same `q5_1_selected_gemv_bf16_bf16_kernel`** that the
default variant does. The only difference is the block size, 64 against 256. The
`logical256_t64` and `logical256_t128` names follow the same pattern: same kernel,
different thread count.
So the four registered variants are **launch configurations of one scalar
kernel**, not four implementations. There is no vectorised Q5_1 decode GEMV to
switch to, and the scalar loop at `qwen4_exp_q5_1.hip:1169` is the whole
implementation rather than one option among several.
## Consequence for the work
The cheap path is closed. Recovering Q5_1 decode bandwidth requires an actual
kernel change — vectorising the contraction to the `blockDim.x * 8` shape the
Q4_K and pack8 GEMVs use — not a dispatch or registration change. That is a
larger change and it needs its own correctness gate, so it is the right unit of
work to scope separately rather than attempt as a variant swap.
One shape constraint is now known and worth recording for that work: the launch
guards require `in_features % 32 == 0`, and gemma4's expert `in_features` is 704,
which is 22 x 32 and also 11 x 64. So 704 is compatible with a 64-wide
vectorisation and is **not** a multiple of 256, which is why the `logical256`
names are not the answer for this model even if they had been different kernels.
