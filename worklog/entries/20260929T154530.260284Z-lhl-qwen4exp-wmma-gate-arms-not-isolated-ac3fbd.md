# The wmma gate arms do not isolate the WMMA route

## Summary

Found while trying to explain a prefill-scope discrepancy between the canonical
and heldout runs. The discrepancy is explained by this, but the finding is larger
than the discrepancy: **the gate's two arms are not isolating the route they
claim to measure.**

## The env var gates more than the WMMA dispatch

`use_wmma`, derived from `HIPENGINE_QWEN4_EXP_Q8_WMMA_LAYERS`, is used in
`launch_gguf_linear` for decisions unrelated to the WMMA prefill route:

```python
f_rowtile = (not use_wmma) and _resolve_use_q4k_rowtile(None)      # decode path
if (_native_batch_decode_session_enabled and (2 <= rows <= 8)
        and not use_wmma and ...):                                  # decode path
```

and further down the same call it also gates `enabled=not use_wmma`,
`use_rowtile=f_rowtile` and `use_rowtile=f_rowtile and not use_q4_pack8_wmma`.

So setting or clearing the variable moves **at least four** selectors, several of
which bite at row counts the WMMA route itself refuses (`rows <= 1`). The gate
records its surface as `post-binder HIPENGINE_QWEN4_EXP_Q8_WMMA_LAYERS`, which
reads as "this run measures the WMMA route". It does not.

## It explains the asymmetry, but as inference

The canonical run reports `shape=prefill_last` at `4.41452e-09` and `steady` at
`3.82518e-04`. That is what a decode-path side effect looks like: a selector that
only bites at rows <= 8 leaves the prefill output identical and moves the decode
steps.

**Verified:** the arms differ in more than the WMMA route. **Inferred:** the
mapping from that to the exact per-scope numbers. I am labelling it that way
deliberately - this packet has already recorded three cases where I asserted a
mechanism from adjacent code and was wrong.

## Engagement depends on dispatch order

`_dispatch_can_use_wmma_prefill` requires the variant to start with `prefill_`:

| variant | rows=1 | 64 | 512 | 1024 |
|---|---|---|---|---|
| `coltile8_rowbatch4_f32_f32_out` (exact leaf) | False | False | False | False |
| `prefill_q8_0_f32_f32_out` | False | **True** | **True** | **True** |
| `prefill_f32_f32_out` | False | **True** | **True** | **True** |
| `gemv_q8_0_f32_f32_out` | False | False | False | False |

So whether the route engages depends on which variant the dispatch carries when
`_wmma_prefill_dispatch` runs - a dispatch-order property the gate's env surface
neither controls nor records.

## Consequence

The 2026-09-16 certification and its bit-identical HEAD re-run measure a
compound. They are reproducible and not meaningless, but the drift **cannot be
attributed to the WMMA route alone**, and the gate says it can. Re-attributing it
needs a run that isolates `use_wmma` from `f_rowtile` and the batch-decode
session, or a per-selector ablation. Neither exists.

This is the same class as the two false passes and the qualification-claim
over-reach already recorded here: a green number whose scope is narrower than its
label.
