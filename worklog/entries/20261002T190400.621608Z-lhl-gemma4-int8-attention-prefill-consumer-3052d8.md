# Gemma4 direct INT8 multi-row prefill consumer

## Summary

Third bounded Gemma D12 prerequisite: a registered, representation-consistent
INT8 prefill consumer. The strict decode consumer (`d0dfe8afb`) is single-row;
the BF16 Gemma 4 fast prefill takes BF16 rows, so neither could serve a
multi-token prompt over the BF16-source per-token/head INT8 writer. This unit
adds a direct FP32-query / FP32-output multi-row sibling that reads exactly the
writer's representation -- INT8 payload plus a per-token/per-KV-head FP16 or
FP32 scale, reconstructed as `float32(int8) * float32(scale)` -- and computes a
masked row per (query row, query head) over `KVLiveSpans`.

It is a correctness prerequisite, not a speed claim. The BF16 kernels and the
existing single-row decode kernel/ABI are untouched; there is no
runtime/config/cache-owner wiring, no flags, no torch, no artifact-identity
gates, and no backend/quant branches.

A focused pre-commit repair adds an explicit HIP launch row-count bound: the
launcher's `unsigned int` grid.y cast silently wrapped `rows = 2**32 + 1` to one
row, so the launcher and `_check_prefill_shape` now refuse any row count above
the 65535 HIP grid.y maximum before the cast and before the device metadata
readback / build.

## Multi-row semantics (declared)

The consumer declares **one shared logical KV prefix**: every query row reads
the same logical slot sequence through a single 1-D `base_offsets` page table.
Each query row carries its own live count (`live_counts[row]`, its causal prefix
length) and its own explicit absolute position (`row_positions[row]`). A
row-major / per-row page table is a *separate* prefix and is refused before
build with a named error. That structural rule is also what keeps a multi-row
decode span (row-major) from being silently reinterpreted as prefill: the
wrapper requires exactly `rows` live counts and exactly `rows` row positions, so
a single-row decode span is refused too. The kernel launches one block per
(query row, query head) with bounded per-block shared scratch
(`capacity + head_dim + 2*num_warps` floats, <= 64 KiB); no persistent BF16
shadow is allocated. The row count is bounded to the 65535 HIP grid.y maximum:
the host refuses a larger count with a named capability error before the device
metadata readback, and the launcher re-checks it before the `unsigned int` grid
y cast.

## Numerical / metadata contract

Defined on the quantized representation, not the original BF16 rows:

* Reconstruction is `float32(int8_payload) * float32(scale)`, scale widened from
  FP16 or FP32. Matches the writer codec and `dequantize_kv_int8_per_token_head`.
* Per row `r` and head `h` (GQA `kv_head = h / (Hq/Hkv)`):
  `logit = (sum_d q[r,h,d] * K[j,d]) * scale_param` (Gemma 4 passes `scale=1.0`).
* Keep is span-native: slot `j` is visible when it is not evicted, its absolute
  `token_positions[j]` is non-negative and no later than `row_positions[r]`, and
  -- on a sliding layer -- strictly inside `sliding_window`. Absent
  position/eviction tensors are the uniform dense fill (slot `j` at position
  `j`).
* A zero live count is a supported empty row (zeros); a row whose position leaves
  no visible slot is all-masked (zeros); a negative or `> max_context_len` count
  is a NaN row and a host `ValueError`.
* A *visible* out-of-range page id, non-finite logit, or non-finite
  reconstructed V writes a NaN row for that (row, head) only -- the failure is
  head-local, independent of the softmax weight. A masked slot never
  participates, so a poisoned masked K/V scale cannot leak.
* The checked path reads the per-row counts, row positions, and the shared
  page-table prefix with a synchronous D2H copy, synchronized against a supplied
  non-blocking stream first. It is a correctness path: no graph-capture or async
  promise.

The oracle is compared on that same representation. Agreement is FP32
`expf`/reduction-order level (`rtol=1e-3`, `atol=3e-4`); the original
unquantized FP32 fixture rows are compared only diagnostically (correlation).
This fixture does not establish writer-to-consumer integration or BF16-source
quality.

## Capabilities and limitations

- Supported: `(Hq, Hkv, head_dim)` in `{(16, 8, 256), (16, 2, 512)}`,
  `block_size` any positive value, `spans_mode == "uniform"`,
  `storage_dtype == INT8_PER_TOKEN_HEAD`, `per_token_head` scale granularity,
  fp16 or fp32 scales, one shared 1-D page table, per-row live counts and row
  positions, `max_context_len` up to the 64 KiB shared-memory bound.
- Refused before build with a named error: grouped granularities, non-uniform
  spans, non-INT8 storage, unsupported geometry, mismatched scale shape, short
  block table/scale coverage, non-int64 positions, a rank>=2 (separate-prefix)
  page table, a count/position count that does not equal `rows`, missing row
  positions, a row count above the 65535 HIP grid.y maximum, oversized context,
  non-contiguous tensors.
- The checked path synchronizes the supplied stream and performs a synchronous
  D2H read: it is a correctness path, not an async or graph-capture path.
- The BF16-source INT8 writer's prompt path
  (`qwen35_write_paged_kv_int8_per_token_head_bf16_prompt_spans`, shared arena)
  takes a row-major `[rows, block_table_len]` table whose rows may repeat, while
  this consumer declares a single shared 1-D table. The two describe the same
  shared arena; integration must pass the writer a row-major table and this
  consumer the equivalent 1-D table (or the parent must reconcile the shapes).
  This unit does not change the writer and makes no integration claim.
- Not in this unit: runtime/config/owner wiring, whole-D12 integration, a
  flash/fused optimization, and any speed claim.
