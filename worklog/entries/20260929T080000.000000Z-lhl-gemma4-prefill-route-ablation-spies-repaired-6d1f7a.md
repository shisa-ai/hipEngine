# the prefill route ablation was reporting that the experts cost nothing; it spies on the wrong functions

## Summary

`scripts/gemma4_prefill_route_ablation.py` is the campaign's instrument for choosing prefill
levers. It ran and printed a full table, and **every arm except `no_attention` was wrong**:

| arm | reported before | measured after | share after |
| --- | ---: | ---: | ---: |
| `no_experts` | saves **-0.009 s (-1.4%)** | saves **0.305 s** | **46.3%** |
| `no_dense_q8` | saves -0.006 s (-0.9%) | saves 0.181 s | 27.5% |
| `no_all_gemv` | saves -0.005 s (-0.8%) | saves 0.184 s | 27.9% |
| `no_attention` | saves 0.106 s (16.2%) | saves 0.122 s | 18.5% |
| `no_router` | 0.005 s (0.8%) | 0.022 s | 3.4% |
| `no_moe_elementwise` | 0.013 s (1.9%) | 0.019 s | 2.9% |
| `no_norm_rope` | 0.002 s (0.2%) | 0.012 s | 1.8% |

`no_all_gemv` skips **every** dense projection and reported **-0.8 percent** -- it was skipping
nothing. `no_experts` reported the experts were 1.4 percent of prefill when they are 46 percent.

## Why

The probe patched leaf launchers that are no longer the live path:

- It patched `gk._launch` (`gguf_k_gemv`) and `gq._launch_selected` (`gguf_q4_k_gemv`). The
  dense route the layer actually takes is **`launch_gguf_linear`**
  (`hipengine/runtime/gguf_linear.py`), reached from `gemma4_layer.gemma4_project` -- neither
  leaf is on that path, so the dense arms skipped nothing.
- It patched `ex.gemma4_project_experts_rows` and `ex.gemma4_project_experts_selected`. The
  T16 gate/up route landed after the probe was written, and the live path is
  `gemma4_experts_forward_bf16`'s own dispatch -- so the expert arm skipped nothing either.

`no_attention` worked because it patched `gl.gemma4_attention_prefill_bf16`, a **module global
in the layer's own namespace**. That is the property the other arms lacked.

## The fix

Spy at the layer, not at the leaves. `gemma4_layer` calls `gemma4_project` and
`gemma4_experts_forward_bf16` as module globals, so patching those two covers whichever leaf the
dispatch picks and **cannot go stale when an internal route changes** -- which is exactly the
failure above.

```python
orig_project = gl.gemma4_project
orig_experts_forward = gl.gemma4_experts_forward_bf16

def spy_project(x_ptr, weight, out_ptr, *a, **kw):
    if mode == "all_gemv":
        return None
    if mode == "dense_q8" and _is_q8_0(weight):
        return None
    return orig_project(x_ptr, weight, out_ptr, *a, **kw)
```

`_is_q8_0` reads `weight.spec.quant_key`, which is what keeps the `dense_q8` and `all_gemv` arms
distinct now that both go through one spy. The dead leaf spies, their `orig_*` bindings, the
`gk`/`gq` imports and the write-only `skip` set are removed -- dead attribution code that *looks*
live is what produced this bug.

## The attribution it now gives

At pp512, 0.659 s baseline, arms summing to ~100 percent:

**The experts are 305 ms -- 46.3 percent -- and the T16 gate/up route is already live.** That
makes the expert block, not attention and not the dense term, the place the remaining 96 ms
(0.659 against llama.cpp's 0.563) has to come from. `20260929T040000`'s reading that "the gap to
llama.cpp is 122.8 ms" was measured against a prefill of 0.686 s and priced from the same broken
instrument; the terms it lists are superseded by this table.

## Changes

`scripts/gemma4_prefill_route_ablation.py` -- layer-level spies, quant filter for the dense arm,
dead leaf spies and write-only `skip` removed.
