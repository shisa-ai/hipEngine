# gfx1151 gfx1100-only capability pin inventory for the Qwen3.8-27B dense path

## Summary

Worked the `docs/20260909-GFX1151-GFX1100-TRANSFER-AUDIT.md` rows against the
code at `7ed5c5559` and separated the gfx1100-only surface by *mechanism*, because
the mechanisms have different clearing costs. The audit previously recorded the
registry surface (105 gfx1100-only variants) but not the capability surface.

Headline: the Qwen3.8-27B dense path is **net ahead on gfx1151, not behind**. Of
the 124 distinct `GGUF_*` capabilities its modules read, gfx1151 defines 50 that
gfx1100 does not, against 18 in the other direction (31 differ in value, 23 match,
2 are absent on both). A sweep that reads the `hip_gfx1100` literals in the runtime
and concludes gfx1151 is behind has the sign backwards.

The one real defect found is documentation asymmetry, not missing performance:
**none of the 18 gfx1100-only capability gates is mentioned anywhere in the
gfx1151 package** — no constant, no comment, no exclusion entry — while all 105
registry exclusions carry a written reason. A name that exists only on gfx1100
reads as an ordinary call-site default, so a gfx1151 regression from its absence
is invisible in review.

Two concrete, code-level divergences land on this artifact, both from the same
cause (the dense scratch gates are keyed on `(geometry, file type)` and the two
backends populated different file types):

- `GGUF_DENSE_PREFILL_SCRATCH_LIVENESS_POLICIES` has a `MOSTLY_Q4_K_M` entry on
  gfx1100 and is absent on gfx1151, so dense scratch liveness aliasing is off
  there. gfx1151's `GGUF_PREFILL_SCRATCH_LIVENESS_MIN_ROWS = 768` is read only in
  the MoE branch and does not substitute.
- `GGUF_DENSE_PREFILL_SCRATCH_ROW_CAP_POLICIES` is keyed `MOSTLY_Q4_K_M` on
  gfx1100 (1,024-row ceiling) and `MOSTLY_Q4_K_S` on gfx1151 (4,096 at capacity
  >=4,096, 1,024 at >=8,192). The local file's `file_type_name` is
  `MOSTLY_Q4_K_M`, so on gfx1151 it resolves to no ceiling at all — no clamp, not
  a tighter one. gfx1100 relies on that clamp to stop a 4,096-row auto query
  chunk from overrunning metadata buffers sized at allocation (the 2026-09-09
  INT8 comparison-protocol crash recorded in `_dense_prefill_scratch_row_cap`).

## Validation

- Registry census reproduced with section H's snippet: **1307 shared, 105
  gfx1100-only, 7 gfx1151-only, 241 declared exclusions, 18 body overrides** —
  identical to section H's numbers at `f3b20c1f2`.
- Capability census: every `backend_package_capability(backend, "NAME", ...)` call
  site in `hipengine/` was extracted by regex (298 distinct names, 380 call sites),
  the reading modules were attributed per name, and the Qwen3.8-27B dense-path
  subset (124 `GGUF_*` names) was compared between the two backend packages with
  `repr()` equality rather than a formatted summary — an earlier pass that
  compared formatted strings mis-reported `GGUF_DENSE_PREFILL_SCRATCH_ROW_CAP_POLICIES`
  as equal because both sides were `dict(1)` with different keys.
- The five dense-path registry exclusions were confirmed present in
  `_GFX1151_ALIAS_EXCLUSIONS` with their comments intact.
- The geometry pin was read at its source: `launch_q4_dual_pairreuse_direct`,
  `kernels/hip_gfx1100/quant/gguf_t16_selected_gemv.hip:6868` (`block(128)`,
  `rows <= 64`, `rows % x_rows == 0`), and the kernel is absent from the 18
  `_GFX1151_OVERRIDES`, so gfx1151 runs the shared body and geometry.
- The file-type key was verified against the real artifact rather than assumed:
  `GGUFReader("/models/gguf/Qwen3.8-27B-Q4_K_M.gguf").info.file_type_name` returns
  `MOSTLY_Q4_K_M`, which is the key gfx1151's row-cap dict does not contain.
- The "none of the 18 is mentioned on gfx1151" claim was checked by grepping all
  18 names against `hipengine/kernels/hip_gfx1151/__init__.py` (0 hits), and the
  "twelve carry a gfx1100-side comment" count by walking back over contiguous
  comment lines above each definition in the gfx1100 package (12 comment, 6 none).
- Corrected two overstatements during the write-up: the first draft said none of
  the 18 had a comment on either side (12 do, on the gfx1100 side), and it grouped
  `GGUF_RAW_K_PREFILL_ROLE_VARIANTS` under Q4_K_M prefill when the raw-K family
  admits only `{gguf_q8_0, gguf_q5_k, gguf_q6_k}`.
- Docs-only change; no GPU run and no correctness gate applies.
