# YuE2 AR decode measured on matched work: 1.89x, plus the context and sampling split

## Summary

The AR decode is the whole remaining gap between the torch-free product path and the
pinned upstream, and until now it was only measured per *generated* token, with the two
sides producing different token counts and the earlier product run capped by a
configuration defect. This unit drives both implementations over the same recorded token
trajectory for the same number of steps, with the same prefixes and the same two CFG
branches, timed alternately in one session. On matched work the reference is **1.89x
faster** (30.87 ms per decode step against our 58.30), not the 2.63x the per-token
reading of the product run implied. Two further measurements split the product's 82 ms
per token into three levers: **13.17 us per context token** of context-dependent device
work (fitted over four budgets, max residual 0.28 ms) and **7.61 ms per token** of
host-side sampling, leaving about 62 ms of step work.

## Changes

- `scripts/yue2_ar_matched_timing.py` (new): loads the case's recorded prefix, negative
  prefix and semantic trajectory, drives the torch-free AR runtime with the recorded
  token in place of sampling, times prefill and decode separately over repeated passes,
  and can compare two side JSONs or merge them into one artifact. It refuses to compare
  sides whose prefix, negative-prefix or trajectory digests differ, so a protocol drift
  cannot pass as a result.
- `scripts/yue2_reference_ar_timing.py` (new, oracle only): the same protocol on the
  reference's own `GraphAR` path - the one its `generate_tokens` uses under a CUDA graph,
  which is what produced the recorded timings this campaign compared against - with the
  recorded token passed to `step()` and the per-step reduction kept so the device still
  finishes inside the timed window.
- `scripts/yue2_ar_sampling_cost.py` (new): CPU-only split of the per-step host work
  (CFG combine, penalty/top-k/top-p distribution, softmax, categorical draw) on a real
  history, plus the product loop's context scaling recorded in the artifact.
- `benchmarks/results/yue2_ar_matched_timing_20260917.json`,
  `benchmarks/results/yue2_ar_sampling_cost_20260917.json` (new artifacts),
  `benchmarks/README.md`, `benchmarks/CHANGELOG.md` (corrected AR reading and the split).
- No runtime change: this is a measurement unit.

## Validation

- Command:
  `python3 scripts/yue2_ar_matched_timing.py --case mandarin-off-s1234 --warmup 1 --repeats 2 --json /tmp/yue2_ar_hip_1.json`,
  then
  `PYTHONPATH=~/yue2-shootout/shared/upstream ~/venvs/vibevoice-tts-oracle/bin/python scripts/yue2_reference_ar_timing.py --case mandarin-off-s1234 --warmup 1 --repeats 2 --json /tmp/yue2_ar_ref_1.json`,
  then the same pair again, all sequentially so the two sides never contend for the GPU.
- Protocol identity is enforced in code: prefix digest, negative-prefix digest, trajectory
  digest, step count and case must match across sides. Positive prefix 98 tokens,
  negative 12 tokens, 1 296 decode steps, guidance 1.01.
- hipEngine: 58.30 / 58.35 ms per decode step (75.56 s / 75.67 s over 1 296 steps),
  prefill 0.157 s, `torch` not imported. Reference: 30.87 / 30.95 ms per step (40.01 s /
  40.54 s), prefill 0.240 s, `cuda_graph`. Pass 1 and pass 2 were separated by a full
  reference run and agree within 0.1%.
- The reference's 30.87 ms per step agrees with its own recorded product timing for this
  request (40.597 s / 1 298 tokens = 31.28 ms), which is a cross-check that the harness
  reproduces the recorded number rather than something adjacent to it.
- Context scaling, measured with `generate_tokens` at fixed budgets on the same case:
  300 steps / context 398 -> 20.29 s / 67.62 ms per token; 700 / 798 -> 50.80 s / 72.57;
  1 100 / 1 198 -> 85.47 s / 77.70; 1 451 / 1 549 -> 120.20 s / 82.84. Least squares over
  those points: 13.17 us per context token, 62.20 ms intercept, max residual 0.277 ms.
- Sampling split, CPU-only medians of 30 runs at vocabulary 184 704 and history 1 296:
  `distribution` (repetition penalty + top-k + top-p) 5.32 ms, CFG combine 1.03 ms,
  categorical draw 0.66 ms, softmax 0.20 ms, bf16 decode 0.03 ms, total 7.61 ms.
- Consistency check between the three measurements: the product loop at context 398 costs
  67.62 ms per token; the fixed-token harness measures 58.30 ms per step of model work at
  an average context near 700; the sampling path is 7.61 ms. 58.30 + 7.61 = 65.9 against
  the product loop's 67.62 at the shorter context, so the decomposition closes within
  about 2 ms.

## Next

- The AR now has three measured levers rather than one: about 62 ms per token of step
  work (the seven projection GEMVs plus the 756 MB head per branch, at 87 GB/s against
  the reference's 116 GB/s), about 8 ms of host sampling, and about 20 ms of
  context-dependent device work at this case's context. The context term is fitted, not
  attributed: a per-kernel `rocprofv3` diff at two context lengths is what would attribute
  it, and the arithmetic says the live-span K/V read is 229 KB per context token per step,
  which at 13.17 us would be only ~17 GB/s.
- Branch batching (a two-row forward) is the candidate for the step-work term, with the
  row-tile pattern already present in the tree
  (`dense_pair_gemv_bf16_f32w_bf16_out_rowtile2_kernel` reads its weight once for two
  rows) and no f32-out row-tile variant registered yet. Measure it against the serial
  path, including the output head, before changing the default.
- The sampling term has a clear target: the reference reduces to a single element on the
  device before it crosses to the host.
