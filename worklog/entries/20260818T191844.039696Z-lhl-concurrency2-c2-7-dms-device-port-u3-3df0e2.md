# C2-7 U3: DMS append/decode HIP kernel, bit-exact parent walk

## Summary

Continues the campaign from
[`20260818T142057.271575Z-lhl-concurrency2-c2-7-dms-device-port-83cd09.md`](20260818T142057.271575Z-lhl-concurrency2-c2-7-dms-device-port-83cd09.md)
(U1 = 9791576ad, U2 = 3cd91e060). U3 lands the decode-append kernel: the
no-shadow decode half of the C2-7 BF16 port. One design finding reshaped
the unit: the host parent's overflow victim loop can never drop a row
(every evictable+out-of-window row already failed the keep rule), so
`append_decode` is exactly *recompute keep over the whole extent, append
the new row, fail closed on overflow* — the kernel implements that
walk directly (chunked 256-slot scan) instead of the planned
steady-state single-drop, which is its special case.

## Changes

- `dms_append_decode_kernel` (+ launcher `hipengine_dms_append_decode_bf16`)
  in `hipengine/kernels/hip_gfx1100/attention/dms_compact.hip`: one
  workgroup per (row, head). Pass 1 (read-only) counts keepers
  (`~evict | p - pos <= window`) per 256-slot chunk via Hillis-Steele
  prefix over per-slot flags; if `keepers + 1 > range_capacity` the
  kernel writes `status = 1` and returns without touching any buffer
  (host parent raises `MemoryError` without mutating state). Pass 2
  repeats the scan and compacts keepers in the same strided order
  (exclusive rank = chunk_rank + inclusive_prefix - 1 <= slot index, so
  writes are self-or-backward and never clobber a pending read; chunk
  ranks are monotone across chunks); the new row lands at `base + keepers`,
  `live_counts` is published, `status = 0`. Extents beyond one 256-slot
  tile (window up to ~4096) are handled by the chunk loop.
- `dms_append_decode_bf16` ctypes wrapper + registration
  `("hip_gfx1100", "dms_append_decode", "bf16", "compact_append_evict")`
  (cpu_reference sibling is the strict fallback) in `dms_compact.py` +
  `attention/__init__.py` export.
- Strict RED test `tests/test_dms_append_decode_hip.py` (7 tests, 6 GPU):
  registration/build-plan, wrapper validation, and five bit-exact
  device-vs-`DMSCompactBackend.append_decode` cases — in-window growth,
  drop+shift compaction, batched rows (2 rows x 4 KV heads x D128,
  offset row starts), overflow fail-closed (synthetic full never-evicted
  extent: host raises MemoryError, device leaves every buffer byte
  untouched with status=1), and a corrupted-steady-state multi-drop
  recompute (two evicted+out-of-window rows dropped in one append — the
  case where a steady-state single-drop would fail closed).
- Test plumbing: shared prompt/step data generation between the host
  oracle and the device run (same BF16 bits on both sides), absolute
  device positions vs row-relative host positions reconciled per side.

## Blockers / follow-ups

- **LATENT U2 BUG (filed, not fixed here):** the committed U2
  `dms_streaming_pack_kernel` computes per-thread output ranks as a
  lane prefix of per-thread keep counts, which equals the true global
  keep rank only while `row_tokens[r] <= 256` (one tile). With longer
  prompts the packed order/destinations are wrong. U2b follow-up: RED
  test with a >256-token prompt, then port this unit's chunked-scan
  structure to pack. No production exposure yet (DMS path not wired);
  recorded while the context is fresh.
- Test-design lessons (for U4+): host state positions are row-relative
  (prompt 0..T-1, decode T+step) while the device extent holds absolute
  positions (row_start + t) — each side needs its own position base;
  steady-state preconditions are an admission invariant, so
  overflow/multi-drop cases synthesize the violating extent directly
  instead of reaching it through valid steps.
