# Amend the server/direct parity roadmap with a follow-up code trace

## Summary

User-requested read-only comparison of the direct engine and server INT8 KV
routes. The roadmap committed at `648e99ae2` already covers the substance
(F1-F9, P0-P7), so this unit adds only what the trace established and leaves
the packet structure untouched. Its headline is the answer to F1's own open
instruction, "Trace the direct arm before describing its actual attention
kernel family": the direct arm is AOTriton compact varlen above the 512-row
crossover, so the server route differs from it by kernel selection rather than
by arithmetic contract. No production code changed and no measurement was
taken.

## Decisions

- **The direct arm's attention family is AOTriton, not a WMMA score-GEMM.**
  `_prefill_bulk()` calls the common
  `_run_full_attention_prefill_layer_aotriton()` with `allow_aotriton` at its
  default `True`. `_full_attention_prefill_scratch_for_layer()` swaps only
  `key_cache`/`value_cache` to the BF16 oracle pair and leaves
  `append_spans`/`prefill_spans` BF16, so the wrapper's `direct_int8_prefill`
  term is False even for INT8-KV sessions; `_gguf_aotriton_prefill_allowed()`
  has no gfx1100 capability entry and returns its `True` default. This
  confirms the roadmap's existing "Important correction" and closes the
  trace instruction it carried.
- **`_gguf_slot_local_prefill_allow_aotriton()` is the sole admission gate.**
  The second site, `_prefill_batch_native_single_slab()` clearing
  `force_aotriton_slots` for `direct_int8_prefill`, drops only the per-slot
  `aotriton_min_tokens=1` override and returns those slots to the 512-row
  crossover. Consequence recorded for the P1 gate: after the flag, slabs at or
  above 512 rows take AOTriton while sub-512 tail slabs keep the native
  kernel, so the trace check must expect two kernel identities and the
  numerical packet must include a prompt with a sub-512 final slab.
  `_plan_packed_ar_prefill_chunks()` does not merge tails and
  `_chunk_ranges(min_chunk_size=2)` merges only below two rows, so both
  routes produce such slabs.
- **The 1,024-row slab cap is a policy value, not a constant.**
  `GGUF_DENSE_PREFILL_SCRATCH_ROW_CAP_POLICIES` declares one
  `max_rows_by_capacity` entry for this geometry, so
  `_gguf_dense_prefill_scratch_row_cap()` resolves to 1,024 at every capacity
  at or above 1,024, and `oracle_per_layer = len(chunks) > 1` therefore fires
  for every prompt longer than one slab. Recorded as a P3 contrast and as a
  named plan input; the same policy's comment records 1,024-row chunks as
  faster than 4,096-row chunks, so raising it is not a free lever.
- **F5's blocking boundary is a per-call oracle release.**
  `prefill_batch_native()`'s `finally` releases the oracle buffers and clears
  `_int8_prefill_oracle_per_layer` on every call return, while within one call
  the oracles already survive all internal slabs. P6's checkpointable owner is
  an extension of that existing cross-slab lifetime, constrained by the
  release-on-failure guarantee the `finally` provides.
- **Dropped before writing:** an apparent divergence in the AOTriton isolated
  prefill stream (the slot-local call site passes no bridge). Verified
  immaterial on this backend:
  `_gguf_aotriton_isolated_prefill_stream_applies()` resolves
  `GGUF_AOTRITON_ISOLATED_PREFILL_STREAM`, which is absent for gfx1100 and
  defaults False, so the direct arm's bridge is inert there too.
