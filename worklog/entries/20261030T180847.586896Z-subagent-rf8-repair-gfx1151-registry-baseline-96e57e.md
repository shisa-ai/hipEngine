# Isolate gfx1151 registry baseline from collection order

## Summary

`tests/test_unit_gfx1151_backend.py` imports `hipengine.kernels.hip_gfx1151`
before `hipengine.kernels.hip_gfx1100.quant.gguf_q8_0_t16_gemv`. The gfx1151
package aliases the gfx1100 key space only at its own import time, so that
order leaves the Q8T16 dual/triple GEMV aliases unregistered. The shared
`tests/conftest.py` collection baseline then snapshotted the incomplete alias
set, and its per-test teardown restored that snapshot after every test. The
combined order therefore failed 16 `test_unit_gguf_linear_dispatch.py` cases
(all eight `hip_gfx1151` rows for
`test_t16_pair_package_policy_selects_actual_launch` and all eight
`triple` rows for
`test_t16_broad_package_policy_selects_single_and_triple_launch`) because
`is_registered(KernelKey("hip_gfx1151", "linear", "gguf_q8_0_t16_v1",
"t16_dual_gemv_decode_bf16_bf16_out"))` was false, so
`_resolve_gguf_linear_pair_kind` returned `none` and the pair/triple launch
declined.

This is a test-isolation defect, not a production routing defect:
`load_backend_kernel_package()` calls `register_backend_kernels(replace=False)`
at runtime and refreshes missing aliases. No production file was edited.

## Changes

- `tests/conftest.py`: after importing every gfx1100 module, call
  `register_gfx1151_kernels()` before snapshotting `_BASELINE_KERNELS`, so the
  baseline contains the aliases for source modules imported after the gfx1151
  package, regardless of collection order.
- `tests/test_unit_gfx1151_registry_baseline.py`: new focused regression that
  imports gfx1151 before the Q8T16 GEMV source module and asserts the
  collection baseline contains the gfx1151 dual alias and that restoring the
  baseline keeps it registered. RED before the conftest change, GREEN after.
