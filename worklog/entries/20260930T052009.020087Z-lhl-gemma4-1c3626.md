# x7 phase 1 design: bucket-keyed single-step capture for gemma4 decode, host sampling v1

## Summary

Design study of `hipengine/runtime/gguf_decode_graph.py` (701 lines, the
production qwen module) against Gemma4's decode forward. The design below is
the deliverable; no production code changed.

**What the qwen module does (patterns to port):**
- Dedicated capture stream (`runtime.stream_create()`); the legacy default
  stream cannot capture — confirmed independently by the X7 screen (HIP 900).
- Position/context live in **device scalar buffers** set before capture and
  advanced *inside* the graph by the captured `advance_decode_position_i64`
  kernel, so replay needs no host argument updates.
- A graph key records full state identity: buffer pointers, weights/roles
  hash, start position, `context_bucket`, transition window; replay refuses
  outside the declared window or against a moved cursor (state generation
  checks), and `rearm_replay_window` only resets host accounting after the
  caller restores byte-identical state.
- `steps_per_replay` chains N steps in one graph; sampling runs device-side
  (`_sample_device_from_hidden`) so the loop closes on the device and tokens
  are read back through an indexed record kernel, not a per-step D2H.
- Attention is bounded by the bucket: kernels are launched against
  `replay_context_limit`/`context_bucket` for the whole window.

**Gemma4 v1 design (single-step, host sampling):**
1. Capture region: `[token H2D (async, enqueued first) -> embed -> scale ->
   30 x layer -> final rmsnorm -> lm_head]`, ending **before** the logits
   D2H. Logits D2H + softcap + argmax stay host-side (the D2H is the
   sampler's inherent dependency, iteration 145's decision), and the next
   token's H2D is enqueued on the capture stream ahead of the next graph
   launch. Staging uploads (rope cos/sin, mask) are enqueued ahead of the
   graph on the same stream — iteration 145 already made them stream-ordered
   async.
2. Explicit stream threaded through `_forward_block_inner` (all wrappers
   take `stream`, default 0 today).
3. **Bucket keying**: capture at a `context_bucket` (ceil to block, like
   qwen); within a bucket every host-visible launch argument is constant:
   `keys = bucket` (an argument, not a grid input, in
   `launch_gemma4_attention_decode`), and `decode_slices(keys, head_dim)`
   takes one of 1/2/4 discrete values that stabilize once
   `keys > 2048` (sliding layers: after the 1024 window cap). Recapture
   once per bucket crossing; staging buffers for rope/mask are allocated at
   bucket size once so their device pointers stay stable (content-only
   updates each step).
4. **Mask is the semantic boundary**: the padded bucket-sized keep-mask
   carries zeros past the live position, so replaying with `keys = bucket`
   attends exactly the live columns. Cache columns beyond live are garbage
   and multiply into masked softmax lanes only.

**The RED (owned by the build unit, not committable until wiring exists):**
capture one decode step, replay it, and assert the replayed output equals
the launched path **bitwise across ≥2 consecutive positions**. The known
risk it must answer: launched-at-actual-keys vs replayed-at-bucket may
accumulate masked columns in a different order (the pass-1 fully-masked-tile
skip may or may not make them identical). If they differ, the contract falls
to parent-parity (same arithmetic, different zero-contribution lanes) under
`docs/EXECUTION-PROFILES.md` and goes through the campaign's teacher-forced
gate; launched-at-bucket == replayed-at-bucket is exact by construction.

**Ceiling (unchanged):** host submission ~1.4 ms/step (screen), wall bounded
by the ~1.7 ms wall-minus-busy gap; the v1 graph does not touch the logits
D2H wait.
