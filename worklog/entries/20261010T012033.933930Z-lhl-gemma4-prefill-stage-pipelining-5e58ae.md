# Stage multi-block prefill content off the compute stream

## Summary

A host profile of three 8192-token prefills on W7900 put 6.0 of 8.1 host
seconds inside `_stage_block_content`'s uploads: each block's rope tables and
keep-masks are megabyte uploads from pageable memory, and `hipMemcpyAsync` did
not return for them until the compute stream had drained the previous block.
The device then waited while the host queued the next block (about 35 ms of
host launch work per 1024-token block).

A prompt of several blocks now stages that content through a second,
non-blocking stream into one of two alternating staging slots. A block records
an event on the compute stream once its launches are queued, and the block that
reuses its slot two blocks later waits on that event before rewriting it, by
which time the block in between is fully queued. Token ids stay on the compute
stream; a single-block prompt and every decode step are unchanged.

Measured on AMD Radeon Pro W7900, Gemma 4 26B-A4B `UD-Q4_K_XL`, production,
BF16 KV, 128 outputs, one warmup and three samples,
`scripts/gemma4_campaign_bench.py`: prefill 2986.2 -> 3038.1 tok/s at 8192
(1.017x) and 2364.6 -> 2420.8 at 32768 (1.024x), against `18c515d87`. At 65536
it reads 1946.4 tok/s; the nearest earlier row is 1874.3 at `548322470`, which
also predates the gather change. Decode is level and `public_path_parity` is
true on all rows.

The gain is smaller than the host stall suggested. A device-idle union over
both queues in a `rocprofv3` trace fell from 14% to 4.6% of the prefill span,
but the MoE stream keeps the device loaded during much of what the single-queue
view counted as idle.

## Changes

- `hipengine/runtime/gemma4.py`: `_prefill_stage_begin` / `_prefill_stage_end`
  / `_prefill_stage_release`, the `slot` argument of `_stage_block_content`, and
  the slot assignment in the two multi-block loops (`forward`,
  `forward_argmax`).
- `tests/test_unit_gemma4_staged_prefill_integration.py`: the upload stream and
  slot of each block's content, the drain before launch, the event recorded per
  block, the wait before a slot is reused, release at close, and the unchanged
  single-slot path.

## Validation

- Teacher-forced captures with a four-block and a sixteen-block prefill
  (`--prompt 8192 --prefill 4096`, `--prompt 16384 --prefill 15856 --context
  16384`) are bitwise equal to the captures taken before this change and before
  the gather change, over 4,095 and 527 rows.
- `pytest` default unit tier: exit 0. The edited test file passes 71/71.
- Not adopted, measured in the same session: staging the Q8_0 T16 dense
  kernel's weight tile through a per-wave transposed LDS window was bitwise
  identical and under 1% (3009.1 against 2986.2 at 8192), so it was dropped.
  Removing that kernel's int8-to-half conversion outright, with output
  discarded, reads about 3590 tok/s at 8192, so the conversion is roughly half
  of that kernel's time.

## Next
