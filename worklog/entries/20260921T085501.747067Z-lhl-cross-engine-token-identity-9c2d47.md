# hipEngine and llama.cpp tokenize the agentic fixture identically

## Summary

Cross-engine comparison needs one of two conditions to hold: the same model, or
matched tokens. This entry settles which one we have, because the answer decides
whether a hipEngine-versus-llama.cpp row can be taken at all.

**Both engines read the same GGUF vocabulary, and on real fixture text they
produce byte-identical token ids.** The condition therefore holds by
construction, not by normalization: same model *and* same tokens.

Method: hipEngine's tokenizer was rebuilt from GGUF metadata alone
(`scan_gguf` then `Qwen35GGUFTokenizer.from_gguf_info`, vocab 248320, no GPU and
no server), and `llama-tokenize` was run on the same strings against the same
`Qwen3.8-27B-Q4_K_M.gguf`.

| sample from the agentic fixture | ids | identical |
| --- | ---: | --- |
| plain prose sentence | 8 | yes |
| 400-character tool result | 139 | yes |
| assistant tool-call function name | 1 | yes |
| tool-call arguments JSON (`{"command":"git show a12d4b64e --stat | head -15"}`) | 22 | yes |

The tool-call arguments row is the one that matters most: tool-call JSON is the
bulk of an agentic workload's text, and it is where a byte-BPE disagreement
would surface first.

## Changes

- No code change. This is a measurement, recorded because it is the fairness
  foundation for any cross-engine agentic row and because it was previously
  assumed rather than checked.

## Validation

- Four samples of real fixture text tokenize identically, including the
  tool-call JSON.
- One unresolved anomaly, stated rather than smoothed over: a synthetic
  double-escaped variant of the same JSON (the arguments string passed through
  `json.dumps` a second time, giving a quoted and backslash-escaped form) came
  back with equal length but different ids, diverging at index 0 with
  llama.cpp reporting id 1. That form is not what a real request sends, so it
  was not chased, and its cause is not known. It is either a tokenizer
  difference on backslash-heavy text or an artifact of how the CLI received the
  escaped string. Anyone relying on this entry for escaped-text equivalence
  should reproduce that case first.

## Next

- The live agentic lanes already measure the two axes that matter here, and both
  take `--base-url`: `scripts/agentic_coding_live.py` for real-world speed
  (per-round latency and goodput over deterministic tool rounds) and
  `scripts/agentic_coding_quality.py` for task performance (deterministic file,
  lookup, calculator, patch, and test oracles). Neither could be pointed at
  llama.cpp as written, and the reason is not the GPU or the weights file: they
  call hipEngine-only control endpoints -- `/v1/hipengine/tokenize`,
  `/detokenize`, `/count_tokens`, `/sessions`, and `/capabilities`.
- The token-identity result above is what makes those endpoints removable. The
  lanes use `/hipengine/tokenize` to build their exact-token oracle, but this
  entry shows a local GGUF tokenizer reproduces llama.cpp's ids exactly, so the
  oracle can be built CPU-side from the model file instead of from the server
  under test. That is the smallest change that makes one lane drive both engines.
- `scripts/agentic_session_compare.py`, added earlier the same day, measures
  neither axis: it replays a frozen transcript and discards the model's own
  output, so it cannot score task performance and its rate is not the real agent
  loop. It is a prefill/prefix-cache probe over a realistic transcript, not a
  cross-engine agentic comparison, and should not be cited as one.
