# YuE2 NAR attention softmax weight layout

## Summary

Follow-on to the tile-maximum entry. That unit established that the packed
attention kernel is instruction-issue-bound (94% L2 hit rate, negligible DRAM
traffic, ~75% of the issue limit) and named the accumulation loop's shared-memory
reads as the next measurable cut. This unit takes it.

The kernel's address arithmetic had grown as large as its math. `rocprofv3 --pmc`
on the previous kernel counts **3829 scalar-ALU instructions per lane-tile against
9060 vector-ALU**: the weights were stored row-major (`[row][key]`) with the row
stride taken from the runtime block size, so one key's weights for eight rows cost
eight index computations (`r * blockDim.x` against a runtime `blockDim.x`) and
eight shared-memory requests, paid by every lane for every key.

## Changes

`hipengine/kernels/hip_gfx1100/yue2/nar.hip`: the softmax weights are now stored
key-major — `weights[key * ROWS + row]`, eight consecutive floats per key — so the
row index is a compile-time offset inside an unrolled loop, one base address serves
the whole row block, and the block arrives in two 16-byte requests. The `scores`
array stays row-major, which is what the tile maximum wants (a contiguous row to
reduce with `float4`).

The write side pays a bank conflict (lanes are 32 bytes apart, so an eight-way
conflict on a 128-bit store) in exchange for 738 fewer requests and 738 fewer
scalar instructions per lane-tile; measured shared-memory wavefronts are not the
constraint, instructions are.

The sums still walk the tile key-ascending, so the accumulation order per row is
unchanged.

## Validation

Instruction counts per lane-tile (rocprofv3, dispatch 1 of 228624):

| Counter | Before | After | Delta |
| --- | ---: | ---: | ---: |
| VALU | 9 060 | 8 066 | -11.0% |
| SALU | 3 829 | 3 091 | -19.3% |
| LDS | 1 265 | 527 | -58.3% |
| FLAT | 386 | 386 | — |
| **Total** | **14 539** | **12 070** | **-17.0%** |

Counters are deterministic and unaffected by the host's clock drift, so this is the
primary evidence; the wall clock is the secondary check.

Paired same-session A/B, `--repeat 40`, sources alternated:

| Pair | row-major | key-major | ratio |
| --- | ---: | ---: | ---: |
| 1 | 27.05 ms | 26.25 ms | 1.030 |
| 2 | 27.40 ms | 26.38 ms | 1.039 |
| 3 | 27.57 ms | 26.55 ms | 1.038 |

Median-of-medians **1.039x**. End-to-end `--only mandarin-off-s1234 --steps 2`:
solve 7.77 / 7.72 s -> 7.61 / 7.63 s, replay 27.7-27.8 s -> 27.6-27.7 s.

Seventeen percent fewer instructions buys 3.9% of wall clock, which is what a
kernel at ~75% of its issue limit with the rest in stalls can show. Sixteen rows per
block is still not viable with the cheaper traffic: 37.80 / 38.08 ms against
26.46 / 26.58 ms at eight.

Gates: bit-identical to the recorded parent-bits fixture (max abs diff 0.0);
`tests/test_unit_yue2_nar_kernels.py` 15 passed; the 2-step e2e gate passes.

## Next

Scalar ALU is still 3091 per lane-tile against 8066 vector ALU. The accumulation
loop now spends one base address per key, so what remains is the two key walks'
pointer stepping and the tile-loop bookkeeping — a smaller prize than this change
was, and not obviously separable without restructuring the walks.

Closing the rest of the gap to the reference needs the register-blocked layout (a
lane holding several keys' dot products, softmax reductions moved to shuffles),
which changes arithmetic and therefore needs the production profile gates rather
than bit parity. The solver's remaining distance is quantified in the
reference-comparison entry: 5.79x slower per ODE step across all twelve cases.
