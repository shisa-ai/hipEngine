# Replay Gemma 4 decode from the whole-step graph; guard the split window

## Summary

The 512-depth census (previous entry) showed the decode step carries ~505
kernel launches with ~11 ms/step of host-side submission gaps at shallow
depth. The whole-step decode graph capture
(`hipengine/runtime/gemma4_decode_graph.py`, built 2026-09-30 and left
unwired after it measured negative at 1024/128 on the old build) is now the
production decode route, guarded to the depths where replay is bit-exact:

- **The split-window guard.** The decode split route (`decode_slices`)
  engages host-computed slice geometry at 1024 keys; a capture bakes it and
  replay diverges — measured at a 1024-token prompt: ~10 percent relative
  logit error, 52/128 steps differing (argmax usually unchanged, so a
  greedy-only spot check would have missed it). Buckets whose replay window
  can reach 1024 keys now fall back to the launched step inside the session
  (`_SPLIT_ROUTE_MIN_KEYS`, `launched_fallbacks` counter), so the graph runs
  only where replay is bit-identical and deep decode is untouched.
- **Production wiring.** `Gemma4GGUFGenerator.generate_detailed` replays
  decode steps from the graph from its second per-token forward (the first
  stays launched so the capture records only loaded kernels), behind
  `HIPENGINE_GEMMA4_DECODE_GRAPH` (default on, `0` restores launched
  decode). The session is cached per generator and keyed to the runner
  instance; an INT8-KV runner refuses capture and keeps its launched step.
- **Bench mirror.** The campaign bench's instrumented decode loop drives the
  same session in the same order, so `decode_tps` measures the production
  route; the public `generate_detailed` wall was already on it.

## Results (zbook, Radeon 8060S, gfx1151)

- 512/128 production A/B through `hipengine.LLM.generate` (greedy, 128 IDs
  bit-identical): wall 4.13 s launched → 3.70 s graph = **+11.6 percent**.
- Campaign bench 512/128, 3 samples: decode **34.68 → 37.75 tok/s**; vs
  llama.cpp's 35.98 the last trailing ladder cell flips 0.96x → **1.049x**.
- Direct session A/B (1024 prompt, before the guard): graph replay of the
  split window diverged ~10 percent; after the guard: bit-identical
  (launched fallback).
- 32768 verify (primary metric): decode 30.007 tok/s vs the 30.003
  baseline (fallback by design, unchanged); prefill 997.1 tok/s, inside the
  session band.
- Deep production run (2048 prompt): 0 captures, 62 fallbacks, clean output.

The earlier negative verdict (2026-09-30, -5 percent at 1024/128) was
measured on the pre-promotion build whose launched decode was device-bound;
today's faster kernels leave the device idle between launches at shallow
depth, which is the regime the graph exists for.
