# The K_TILE=512 q5_1 shape is an incomplete kernel, not a gate candidate

## Summary

**A recorded "gate candidate" is a broken kernel doing 63.6% of the work.**

The rejected-tile artifact for the Q5_1 staged grouped prefill said the route had
one measured faster shape left: the same kernel at K_TILE=512, 17.28 ms against
20.23 ms, "a gate candidate of the same class as the Q4_K MMQ route". That claim
sent me into this unit, so it is worth recording that it is wrong.

**It is not a different association, it is an incomplete contraction.** In
`qwen4_exp_q5_1.hip` the staged kernel sets `SUBS = K_TILE/32`, and its inner loop
reads only `chunk*SUBS + sub` and `chunk*SUBS + sub + 4` for `sub = threadIdx.x>>5`
in 0..3 -- eight 32-wide weight blocks per chunk -- while `chunks =
ceil(in_features/K_TILE)`.

At K_TILE=256 those eight blocks exactly tile a 256-wide chunk, so three chunks
cover all 22 blocks of the 704-wide row, 24 slots for 22 blocks with the excess
guarded. At K_TILE=512 the chunk is twice as wide but the loop still reads eight
blocks, so two chunks read blocks 0-7 and 16-23 and **never read blocks 8-15**.
That is 256 of 704 columns, 36.4% of the contraction, skipped.

Every output sums over all k, so nearly every output is wrong -- which is exactly
what the recorded difference shows: **11,506,914 of 11,534,336 outputs differ,
99.76%**. The output-difference number was in the record the whole time and is
consistent only with this explanation. The 17.28 ms measures a kernel doing 63.6%
of the work, so the apparent 1.17x is the omission, not a faster shape.

**A correct K_TILE=512 would not obviously help anyway.** It needs the inner loop
to iterate `SUBS/8` block groups, which is a rewrite rather than an instantiation.
And it would still owe a reason to be faster: the accepted row records the staged
kernel at ~3.5 GB in 20.2 ms, 173 GB/s, against the incumbent's 441 GB/s, so it is
not bandwidth-bound, and the tile sweep already refuted occupancy with the
smallest-footprint shapes measuring slower.

**The artifact's own conclusion was right; only its reason was wrong.** It said the
route has no remaining bit-exact lever that measurement supports. That stands, and
this correction strengthens it rather than weakening it. What was wrong was the
accepted row's explanation -- "not bit-exact because a slot's column sequence
depends on K_TILE = 256" -- which describes a legitimate reassociation and hides
that the shape is missing a third of its input.

## Validation

- Block coverage computed from the kernel's own indexing rather than reasoned
  about: K_TILE=256 reads 24 slots for 22 needed blocks, missing none; K_TILE=512
  reads 16, missing blocks 8-15.
- The 99.76% output difference in the existing record is consistent with 36.4% of
  the contraction being skipped and with nothing else.
- `grep` for other references to the 17.28 claim: none. The two corrected files are
  the only places it appears, so no worklog entry or doc repeats it.
