# Resolve pre-load execution profiles through the registered builtin plans

## Summary

`create_app` reads `LLM.resolved_execution_profile` while it assembles the
application, and the R0494 usage script builds that app before the first
generation. Runtime-profile plan registration lived only on the generation
path (`_construct_text_generator` calls `register_builtin_generators()` before
resolving), so a fresh process resolved the property against an empty registry:
an explicit `production` request raised `MissingRuntimeProfilePlanError`, and
the same declaration with no explicit profile silently reported the migration
path instead of the plan generation would select.

`LLM._resolve_execution_profile` now refreshes the same idempotent builtin plan
tables before resolving. Pre-load property access therefore returns the plan
first generation uses, without constructing a generator, loading weights or
touching a device. A declaration with no registered plan still raises
`MissingRuntimeProfilePlanError`, so genuinely unsupported combinations keep
their named failure.

## Changes

- `hipengine/llm.py`: `_resolve_execution_profile` calls
  `register_builtin_generators()` (function-local import, same lazy
  torch-free path generation already takes) immediately before it imports and
  calls the resolver, with a comment naming the pre-load caller and the
  idempotence guarantee.
- `tests/test_unit_llm_preload_execution_profile.py` (new): seven host tests
  that start from a cleared registry (`clear_runtime_profile_registry_for_tests`;
  `tests/conftest.py` restores the collection-time registry afterwards) and
  never register a plan by hand. They cover the public property, equality with
  what the registry serves any other resolver, a second LLM reusing the same
  plans (idempotent refresh, not a duplicate-registration trap), the default
  profile path, `create_app(config, llm=llm)` with no generator constructed,
  the preserved missing-plan error for an unknown declaration, and a
  real-header-only run of the observed declaration.

No other file is touched. `generation/__init__.py` is unchanged: the fix reuses
its public entry point instead of adding a second registration list, so the
coordination that edit would need never arises.

## Decisions

- Fixed in `llm.py` rather than in `execution_profiles.py`: the registry is a
  plain table that model plugin modules populate, and importing those modules
  from the resolver would invert the dependency. `register_builtin_generators`
  already documents that it refreshes these idempotent plans on every call so a
  prior lifecycle cannot make resolution depend on collection order, which is
  exactly the property the pre-load path needs.
- Registration is unconditional on the resolution path, not memoized: tests
  deliberately reset the registry between cases, so a memo would reintroduce
  the same empty-registry failure.

## Limitations

- The fix makes the pre-load path import the generation modules. Any environment
  that cannot import `hipengine.generation` now surfaces that import error from
  profile resolution instead of `MissingRuntimeProfilePlanError`; that is the
  same import the generation path already requires, so no supported
  configuration loses resolution.
- On-device proof is still outstanding: the R0494 usage script needs a GPU and
  the real shards. This unit only shows that `create_app` no longer fails
  before load and that the property resolves the registered plan.
- R0494 model-count validation stays open; this unit does not assert anything
  about prompt-token accounting or image handling.
