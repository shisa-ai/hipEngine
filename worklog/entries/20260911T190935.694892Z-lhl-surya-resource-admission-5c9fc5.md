# Surya resource admission: vision capacity checked before vision, scratch bounded

## Summary

Reviewer-raised gaps, both confirmed by reading the code before changing it.

1. `SuryaOCRGeneratorGPU._generate_ocr` ran `runner.vision_forward` and only
   then reached `check_prompt_capacity` inside `_decode_greedy`. A request that
   could never fit still ran the whole vision tower, and vision allocates
   scratch quadratic in the patch count, so an over-capacity page could
   allocate gigabytes before being rejected.
2. Nothing bounded that scratch. `_vis_scores` allocates
   `heads * stride * 4` bytes with `stride ~= n^2`, which is 805 MB for a
   1024x1024 page (64x64 grid) and 4.1 GB at 96x96. `SURYA_MAX_PIXELS` is
   16_777_216, which permits a 14400-patch grid and a ~9.95 GB allocation.

## Changes

`hipengine/runtime/surya.py`

- `_permanent()` tracked its allocations in a list named `_head_bias_bufs`,
  which holds every long-lived buffer (state, KV cache, staging) and has
  nothing to do with head bias. Renamed to `_permanent_bufs`. This was a
  naming defect, not a leak: `close()` already freed the whole list, so
  `_conv_state` / `_gdn_state` / `_kv_cache` being `.clear()`ed without an
  explicit `hip_free` is correct.
- `_vis_score_stride(n)` extracted so the admission size and the allocation
  cannot drift apart.
- `vision_scratch_bytes(grid_thw)` — the quadratic size for a grid.
- `check_vision_capacity(grid_thw)` — two independent checks, because they
  fail for different reasons: a configured cap that bounds one request
  regardless of host memory, and free device memory via
  `runtime.mem_get_info()` (the pattern `qwen4_exp_gguf` already uses). Only
  the *growth* over an existing cached `vis_scores` buffer is charged against
  free memory, since `_buf` reuses it.
- `DEFAULT_MAX_VISION_SCRATCH_BYTES = 4 GiB`, which admits a 300-DPI A4 page
  (77x109 grid, ~3.4 GB) and rejects the `max_pixels` ceiling with a clear
  error. `max_vision_scratch_bytes=None` disables the cap and leaves the memory
  check. Tiled vision attention is what removes the need for a large scratch;
  until then this cap is the admission contract.
- `vision_forward` calls `check_vision_capacity` before patch embed.

`hipengine/generation/surya_gpu.py`

- `_generate_ocr` reordered: preprocess -> grid -> image-token count -> prompt
  -> mRoPE positions -> `check_prompt_capacity` -> `check_vision_capacity` ->
  vision -> prefill/decode. Preprocessing and the prompt are host-side and
  cheap, so admission now costs nothing. `_decode_greedy` keeps its own context
  check for the text-only path; it is O(1) and the duplication is deliberate.
- Advertises `max_seq` and `max_vision_scratch_bytes` so a caller can admit a
  request before submitting it. These sit alongside the existing non-protocol
  `supports_vision` / `speculative_candidate_budget` attributes.

## Validation

- `test_gpu_vision_scratch_admission_matches_the_allocation`: for three grids,
  the real `_vis_scores` allocation is at least the admitted size and the
  stride formula agrees. This is the check that would catch the two
  computations drifting.
- `test_gpu_vision_admission_rejects_over_budget_grid_before_allocating`: a
  64 MiB cap rejects 64x64 with the cap message, admits 16x16, and leaves
  `_scratch` untouched.
- `test_gpu_vision_admission_can_be_disabled`: `None` skips the cap.
- `test_gpu_generator_checks_capacity_before_vision`: spies on
  `vision_forward` and asserts it is not called for an over-capacity request,
  then asserts a fitting request *does* call it so the spy is not vacuously
  empty. RED confirmed: with the original ordering restored it fails with
  `vision ran before the capacity rejection: ['vision']`.
- Full Surya + rocblas bundle on gfx1151: 113 passed.

## Not addressed here

- The quadratic scratch itself. Bounding it makes an over-budget page fail
  cleanly instead of OOMing; it does not make large pages work. Tiled vision
  attention is the fix and is listed under the large-page optimization.
- `SURYA_MAX_PIXELS` still admits pages the vision path cannot run, so
  `smart_resize` and the runtime disagree above ~4 GiB of scratch. Resolving
  that is part of the tiled-attention work.
- A dedicated leak test for `close()` already exists
  (`test_gpu_runner_repeated_create_use_close_releases_memory`); this change
  renames the list it guards and updates its docstring.
