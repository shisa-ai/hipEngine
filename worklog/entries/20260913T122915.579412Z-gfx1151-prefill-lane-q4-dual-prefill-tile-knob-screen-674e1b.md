# Q4 dual WMMA prefill tile knobs: both axes lose when shrunk, occupancy is pinned

## Summary

The `gfx1151` Q4_K_M dense WMMA prefill owner
(`gguf_q4_t16_dense_dual_wmma_prefill_silu_bf16_kernel<false, false, 4, 4>`, the
fused gate/up dual-SiLU kernel that holds 33.0-36.5% of prefill kernel time at
512/1024/4096 prompt tokens) has three tile-geometry knobs: rows per block
(tokens, 256 today), columns per block (weights, 32 today) and waves per block
(4 today, always launched as 128 threads). This unit measured which direction
each knob moves at prefill rows before any new variant is written, and the answer
is that **shrinking either axis loses and tile geometry cannot move occupancy**:

* Row tile, real `Qwen3.8-27B-Q4_K_M` gate/up tiles, shape 5120x17408, 5 row
  counts: the 256-row parent wins every cell. Versus the parent, 128 rows is
  0.84-0.88x, 64 rows 0.46-0.47x, 48 rows 0.40-0.44x and 32 rows 0.40x.
* Column tile, single-matrix sibling at the same shape, 2 row counts: 48 columns
  (30.82 ms at 4096 rows) beats 32 columns (39.11-42.97 ms) and 16 columns
  (52.15-56.91 ms); at 512 rows the same order holds. The 32- and 48-column arms
  are occupancy-neutral, so the 1.27-1.39x gap is not an occupancy effect.
* Occupancy: every registered dual variant reports 248 allocated VGPR and 32768
  LDS bytes, i.e. 2 workgroups per CU and 2 waves per SIMD for the whole ladder.
  LDS is a union whose weight member (2 matrices x 256 K x 32 columns x 2 B) is
  independent of rows and row tiles per wave, and `__launch_bounds__(128, 1)`
  lets the compiler spend the registers that smaller accumulators free.

Mechanism: per-block time does not fall with rows per block (at 4096 rows, 6.00
us per block at 256 rows, 3.42 us at 128, 3.19 us at 64, 1.86 us at 32), so the
per-row cost rises as the tile shrinks. A source-level instruction count for the
parent block gives about 3840 warp instructions per K block for 8.39 MFLOP, of
which roughly 1536 are weight decode (2 matrices x 32 columns x 256 weights at
about 3 instructions per weight) and roughly 2304 are the WMMA phase; the decode
is the rows-independent part, about 40% of the issue stream.

The llama.cpp fork's dense MMQ change
(`654803517b06da47f5210553a661bf6c80deb97f`, `mmq-config-rdna3-5.cuh`: 128-thread
I=64 entries beside the 256-thread I=128 entries at J=128) maps onto this kernel
as a halved weight axis plus halved threads. Both measured equivalents of that
direction lose here (1.14x for rows halved, 1.27-1.39x for columns halved), so
the fork's tile change is not transferable to this kernel.

Candidate direction for the next unit, ranked with the rationale in the
artifact: (1) 16 columns x 512 rows, row tiles per wave 8, 4 waves, 128 threads -
halves per-block decode and b-fragment loads per WMMA at the same 32 KiB LDS,
128 accumulator VGPRs and 2 waves per SIMD, predicted about 20% by the
instruction-stream count, at the risk of doubling activation traffic per FLOP;
(2) the same 16-column tile with row tiles per wave 4 and `launch_bounds` min 4
blocks per CU, the only arm that can raise resident waves; (3) 32 columns x 512
rows with 8 waves and 256 threads plus a register-local SiLU epilogue, which
keeps the measured-good column tile and doubles decode amortization only;
(4) a decode restructure at unchanged geometry, since the decode reads one packed
byte per thread per two weights.

## Changes

* `scripts/gguf_prefill_kernel_resources.py` (new) - compiles a HIP source with
  `hipcc -save-temps` and reports per-kernel VGPR/SGPR/LDS/private bytes from the
  `.amdhsa_kernel` metadata plus the gfx11 wave32 occupancy those imply
  (`min(8, 512 / round_up_8(vgpr))` waves per SIMD, `floor(65536 / lds)` workgroups
  per CU).
* `benchmarks/results/2026-09-13-q4-dual-prefill-tile-knob-screen/` (new) -
  `resource_table.json` (all 49 kernels of `gguf_k_t16_selected_prefill.hip`),
  `rowtile_prefill.json`, `col_tile_owners.json`, `assemble.py`, `artifact.json`,
  `README.md`. `assemble.py` derives every number in `artifact.json` from those
  inputs; regenerating it is idempotent apart from `provenance.generated_at`.
* No engine, kernel, dispatch or test code changed. No published benchmark number
  moves, so `benchmarks/README.md`, `benchmarks/CHANGELOG.md` and the root
  `README.md` are untouched.

Dispatch facts recorded for the next unit: the dual-SiLU variant policy
(`GGUF_SPECDEC2_Q4_DUAL_SILU_ROWTILE_POLICY`,
`GGUF_SPECDEC2_Q4_DUAL_SILU_PRODUCTION_R28_POLICY`) is keyed by exact row counts
(28, 32, 36) plus an optional `strict_layer_modulus` layer schedule, so every
prefill row count above 36 selects the 256-row parent. A prefill-scale variant
needs a range-based capability; the precedent is
`GGUF_Q4_T16_PHYSICAL_SHARED_B_ROW64_ROWS = range(33, 193)` in
`hipengine/kernels/hip_gfx1100/__init__.py`.

## Validation

* Row-tile sweep: `scripts/qwen38_packet4_q4_dual_silu_row_leaf.py --model
  /models/gguf/Qwen3.8-27B-Q4_K_M.gguf --rows 256 512 1024 2048 4096 --burst 4
  --repetitions 3 --warmups 2`, event-timed medians. Bit-exactness against the
  parent holds in 20 of 20 cells (the harness fails closed on any mismatch).
* Column-tile sweep: `scripts/gguf_q4_t16_dense_prefill_owner_microbench.py
  --rows 512 4096 --in-features 5120 --out-features 17408 --warmup 3 --iters 10`.
  Bit-exactness holds in 12 of 12 non-reference cells.
* Cross-check against independent evidence: the sweep's parent median at 512 rows
  (6.629 ms) matches the in-situ profiled owner in
  `benchmarks/results/2026-09-13-qwen38-gfx1151-prefill-kernel-profile`
  (424.762 ms over 64 launches = 6.637 ms, +0.1%). The resource table reproduces
  the profiler's own VGPR and LDS figures for the dual (248 / 32768), the
  single-matrix `shared_b` (256 / 24576) and the q6 planar owner (176 / 16384).
* Compile and extraction: `python3 scripts/gguf_prefill_kernel_resources.py
  --source hipengine/kernels/hip_gfx1100/quant/gguf_k_t16_selected_prefill.hip
  --arch gfx1151 --waves-per-workgroup 4` under the `therock` environment
  (AMD clang 23.0.0git, HIP 7.15.26333), 49 kernels parsed, no spilling
  (`private_bytes` 0 everywhere).
* `python3 scripts/worklog.py check` after staging.
