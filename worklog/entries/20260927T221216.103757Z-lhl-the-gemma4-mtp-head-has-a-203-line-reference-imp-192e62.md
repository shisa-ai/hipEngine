# The gemma4 MTP head has a 203 line reference implementation in llama.cpp
## Summary
The objective's "make sure our MTP is working" was blocked on not knowing what the
`gemma4-assistant` head computes. That is no longer open. llama.cpp ships a
reference at `src/models/gemma4-assistant.cpp`, **203 lines**, in the same tree
and at the same commit the objective's baseline was measured against
(`llama.cpp@17252c769`, the commit `benchmarks/README.md` records for the
gfx1151 llama.cpp row). This entry records the structure so the port has a spec
rather than a guess.
## The algorithm, read from the reference
```c
ggml_tensor * x  = ggml_get_rows(ctx0, model_other->tok_embd, inp_tokens);
x                = ggml_scale(ctx0, x, sqrtf((float) n_embd_backbone));
ggml_tensor * xh = ggml_concat(ctx0, x, inp_h, 0);
ggml_tensor * cur = ggml_mul_mat(ctx0, model.nextn_proj_pre, xh);

for (int il = 0; il < n_layer_nextn; ++il) { ... attention, then FFN ... }

ggml_tensor * h_next = ggml_mul_mat(ctx0, model.nextn_proj_post, cur);
```
1. Take the **next token's embedding from the target model** (`model_other`), and
   scale it by `sqrt(n_embd_backbone)`.
2. **Concatenate** it with the backbone's hidden state `inp_h`.
3. **Pre-project** through `nextn_proj_pre`.
4. Run `n_layer_nextn` transformer layers, each with attention and an FFN, and
   with per-layer RoPE base/scale and `n_rot`, including sliding-window layers
   (`hparams.is_swa(il)`).
5. **Post-project** through `nextn_proj_post` to get `h_next`, the next-token
   hidden state.

The tensor shapes from `load_arch_tensors` match what the artifact's header
reports, which is an independent check that the port target is the file I
downloaded:
| tensor | reference shape | artifact |
| --- | --- | --- |
| `nextn_proj_pre` | `{2*n_embd_backbone, n_embd}` | `[5632, 1024]` |
| `nextn_proj_post` | `{n_embd, n_embd_backbone}` | `[1024, 2816]` |
| layers | `n_layer_nextn` | 4 blocks, `blk.0`..`blk.3` |
The concat width confirms the reading: `n_embd_backbone = 2816` (the target's
width) and `n_embd = 1024` (the head's width), so `2 * 2816 = 5632` is exactly
the pre-projection input. `load_arch_hparams` also asserts
`n_layer_nextn == n_layer_all`.
## Why this is bounded work rather than research
- The reference is 203 lines and uses the same primitives this engine already
  has: embedding gather, scale, concat, a linear, RMS norm, RoPE, attention, and
  an FFN. The 4 layers are ordinary transformer layers at width 1024.
- The head is 49 tensors and 440 MB, already downloaded.
- The engine has an **adapter registry** for exactly this shape of plugin:
  `register_gguf_mtp2_adapter(key, factory)` in
  `hipengine/generation/qwen35_gguf_mtp2_registry.py`, with `"dense_nextn"` and
  `"moe_nextn"` already registered for qwen35.
- `hipengine/generation/gemma4_gguf.py:63` currently declares
  `supports_speculative_mtp = False`; that declaration is what the work has to
  make true, not a gate that blocks the work.
## What this does not establish
That the port will reach the objective's 2X decode. `benchmarks/README.md`
records MTP decode at **25.34 against 12.27 tok/s per request, 2.07x** for a
different model on this host, which is the reason to expect a decode win and the
number to compare against — but it is a different model's result, and this
head's acceptance rate on Gemma 4 is unmeasured. The win also depends on
acceptance, so a fast head with low acceptance buys little.
