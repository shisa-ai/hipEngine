# the expert block's host readback is 1.27 ms, not a pipeline drain; and the down kernel reuses weights across rows

## Summary

`20260928T172000`'s split probe documents the expert block's glue as containing a device-to-host
readback per layer -- *"reads the tile row count back to the host and passes it as a launch
argument. The read-back is a pipeline drain inside a 30-layer loop, and neither the census nor
the route ablation can see it."* The census does see 30.32 ms of glue, so the readback was the
obvious candidate for it.

**Measured: 30 readbacks, 1.273 ms total, 0.0424 ms each, 0.19 percent of the step.** It is not
a lever. The hypothesis is refuted and should not be revived.

| part | n | total ms | ms/call | % of step |
| --- | ---: | ---: | ---: | ---: |
| device->host readback | 30 | 1.273 | 0.0424 | 0.19% |
| activation pack (down) | 30 | 2.649 | 0.0883 | 0.40% |
| **q5_1 down MMQ (dp4a)** | **29** | **104.518** | **3.6041** | **15.94%** |
| q5_k gate_up WMMA iu8 (layer 29) | 1 | 10.139 | 10.1387 | 1.55% |
| q5_k exact repair | 1 | 3.533 | 3.5327 | 0.54% |

The glue's 30.32 ms is therefore **not** the readback and not the activation pack. Whatever it
is, it is still unaccounted for, and this entry does not claim to have found it.

Note the absence of the Q4_K gate/up MMQ leaf: this probe patches
`gguf_q4_k_selected_dual_q8_1_ds4_mmq32_...`, which the T16 route replaced, so the arm is stale
for the same reason the route ablation was (`20260929T080000`). Only layer 29, whose experts are
Q5_K, still appears -- 10.139 ms for one call, against the census's 143.7 ms over 29 T16 layers
(4.96 ms each).

## The down kernel reuses weights across rows

`gguf_q5_1_mmq_selected_prefill.hip`:

```cpp
__global__ __launch_bounds__(128, 4)
void q5_1_mmq_ds4_selected_prefill_kernel(...)          // block = 128 threads
  const int64_t out_col = blockIdx.x * 128 + threadIdx.x;
  ...
  const unsigned int expert_grid = num_experts > 512u ? 512u : ...;
  dim3(out_tiles, expert_grid), dim3(128), 0, stream    // grid = (out_tiles, experts)
```

**The grid has no row dimension: one block per (output-column tile, expert), and the block walks
every compacted row for its expert.** So a block's weight slab is fetched once and reused across
its rows, and `20260928T114215`'s row series agrees -- 8/16/24/32 rows per expert cost
1.369/1.738/1.991/2.710 ms, far below the 4x a per-row fetch would give, and its 190.3 MB figure
is a per-pass fetch.

**This resolves the ambiguity `20260929T083000` left open.** The expert block's exact 2.00x
scaling with token count is the number of *passes* doubling -- 4096 routed pairs over 128 experts
is ~32 rows per expert, one pass each; 8192 is ~64, two passes each -- not a per-row re-read. The
"14.4 GB of expert weights" figure is `pairs x bytes-per-expert`, an arithmetic identity, and the
real per-pass traffic is nearer 429 MB. **The expert projections are not bandwidth-bound.**

## What that leaves

The down kernel is 104.5 ms over 29 calls at 3.60 ms/call, moving ~429 MB of weight in that time
-- 1.4 GB/s, nowhere near a bandwidth limit, and `20260928T114215` measured that removing 28.7
percent of its VALU buys 2.3 percent. Low bandwidth and low compute together mean **stalled**,
and the geometry says why: one thread per output column puts adjacent threads' weight rows
`row_bytes` apart -- 528 bytes at `in_features = 704`, which is 4.1 cache lines -- so a warp's
load instruction touches 32 distinct lines and uses 4 bytes of each. Each thread does consume
its whole row eventually, so the bytes are not wasted at the source; the cost is transaction
count and memory-level parallelism, which is what a stall-bound kernel runs out of.

That is `bbe844ecb`'s observation, which `e88a5322e` retracted. **The retraction was of the "25
percent line efficiency" arithmetic, not of the pattern** -- the pattern is in the source above
and is not in dispute. What is still missing is a measurement that separates "poor MLP from
strided rows" from the alternatives, and the fix either way is a coalesced layout, which
`20260928T114215` prices at a repacker plus a new variant plus an oracle plus loader wiring.

## Next

- **The 30.32 ms of expert glue is still unaccounted for.** The readback and the activation pack
  together are 3.9 ms of it. The tile map, the gelu, the lane-to-row accumulation and the
  scatter are the remaining candidates, and none is priced.
- **The down kernel's strided weight rows are the best-supported stall explanation**, and the
  cheap way to test it is a measurement that changes only the access pattern, not the layout --
  a variant where a warp cooperatively reads one thread's row, or one where `out_col` is
  remapped so a warp's lanes share a row.
- **Do not treat the expert block as bandwidth-bound.** 1.4 GB/s rules it out, and any lever
  premised on weight traffic is aimed at the wrong limit.
