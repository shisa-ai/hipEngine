# prefix-cache server-transport multi-turn benchmark

## Summary

The prefix-cache A/B now runs through the live OpenAI-compatible server instead
of calling the engine in process. `scripts/prefix_cache_multiturn_bench.py
--transport server` drives `/v1/chat/completions` over an in-process ASGI client,
attributes TTFT from the SSE stream, and differences the aggregate
`prefix_cache` counters on `/ready` around each turn to recover per-turn
telemetry (mode, hits/lookups, reused tokens, snapshot entries/bytes, admission
fallbacks). It supports alternating A/B arm order and unmeasured warmup turns,
and each arm loads and tears down its own engine.

## Changes

- `scripts/prefix_cache_multiturn_bench.py`
  - `--transport {inprocess,server}`; the server path creates
    `create_app(ServerConfig(...), llm=LLM(prefix_cache=mode))`, drives chat
    completions with `stream_options={include_hipengine, include_usage}`, and
    records per turn: `ttft_ms`, `wall_ms`, `prompt_tokens` (server usage,
    authoritative) plus `local_prompt_tokens` (renderer cross-check),
    `output_tokens`, `reasoning_tokens`/`answer_tokens`, and the prefix block.
  - `_prefix_counter_delta` differences nested counter maps, because the API
    exposes prefix telemetry in aggregate, not per request.
  - `--arm-order {sequential,alternating}` with `_arm_plan`; `--warmup-turns`
    with `_run_warmup` (a short ready turn plus an unrelated warmup
    conversation, so a radix arm does not start a measured lane already holding
    its prefix); `--allow-multi-mode` for a one-process A/B with per-arm
    teardown, recording `gtt_bytes_after_teardown`.
  - `--merge` folds one-arm-per-process artifacts into a single A/B artifact,
    pairing the modes by sequence position so a mirrored run (off, radix,
    radix, off) is drift-cancelling, and taking hardware/model/protocol from the
    first arm so the merged record describes the measurement, not the merge.
  - `--dump-sse` appends every raw SSE line, which is how the buffered-client
    and `invalid_tool_call` behaviours above were pinned.
  - `_run_lane` takes a `run_turn` callable so both transports share lane
    construction, lane ordering, and summarization.
  - `_summarize_mode` reports a TTFT distribution; `by_kind` buckets now carry
    `output_tokens_per_second`; `_compare` adds TTFT medians and their delta.
- `tests/test_unit_prefix_cache_multiturn_bench.py` (19 tests): counter
  differencing, server-side TTFT precedence over buffered client arrival, TTFT
  from reasoning-only and tool-call streams, usage precedence, fallback-reason
  derivation, `finish_details` on a suppressed stream, warmup separation,
  arm/lane ordering, artifact merge pairing and protocol inheritance, parser
  defaults.

## Served A/B result (gfx1151, Qwen3.6-35B-A3B UD-Q4_K_M)

Four arms, one engine per process, mirrored order (off, radix, radix, off),
two unmeasured warmup turns each, 14 lanes x 3 turns = 41 measured turns per
arm, `scripts/prefix_cache_multiturn_bench.py --transport server --lane-kinds
all --turn-limit 3 --warmup-turns 2 --sharegpt-tokens 96 --sharegpt-long-tokens
384 --code-tokens 128 --max-sequence-length 12288`, merged with `--merge`.
Artifact: `benchmarks/results/2026-09-18-gfx1151-qwen36-gguf-prefix-cache-server-multiturn-ab.json`.

| arm | position | wall | output rate | TTFT median |
| --- | --- | --- | --- | --- |
| off | first | 363.2 s | 14.62 tok/s | 438.6 ms |
| radix | second | 494.1 s | 10.85 tok/s | 657.0 ms |
| radix | first | 455.1 s | 11.78 tok/s | 461.9 ms |
| off | second | 397.9 s | 13.34 tok/s | 483.2 ms |

Position drift is symmetric (+9.6% for off, +8.6% for radix), so the mirrored
pairs bracket the mode effect: **+36.0% wall when radix runs second, +14.4% when
it runs first**; the drift-corrected ratio is **+24.7% wall, -20% output rate**.
Both radix arms reuse exactly the same prefix tokens (6 hits, 22 lookups,
26,112 of 84,330 prompt tokens = 31%), so the reuse profile is reproducible
across processes.

Paired per-turn analysis (both repetitions, 82 paired turns):

- **Reuse pays only above a reuse-ratio threshold.** `cumulative-medium_repo`
  turn 1 reuses 8,192 tokens with a 183-token suffix (45x) and gains **TTFT
  -58%/-66% and wall -41%/-51%** in the two repetitions. `small_repo` and
  `growing_history` turn 1 reuse 2,048 tokens with a ~190-token suffix (10x) and
  lose **TTFT +37%/+74%, wall +18%/+41%**. The measured crossover matches the
  cost model: avoided batched prefill is ~1.8 ms/token while the reused-suffix
  path costs ~34 ms/token, so reuse needs a ratio above ~19x. `fixture-medium_repo`
  shows the same split on wall time (-42.7%/-45.0% at 46x).
- **Zero-reuse turns are close to neutral once position is accounted for:**
  ShareGPT +46.2% wall in repetition 0 but +4.2% in repetition 1; cumulative
  coding +5.7% / +0.0%. The apparent +26% median on ShareGPT across both
  repetitions is mostly the position effect, not the cache.
- **The one consistent regression is the agentic fixture lanes** (+85.2% / +80.2%
  wall, +41.6% / +39.6% TTFT in both positions). Those turns are degenerate:
  the server answers with `finish_details.reason = "invalid_tool_call"`,
  suppresses the stream, and stops after ~26 tokens, so they are not a healthy
  agentic turn and are reported separately rather than folded into the verdict.

Lane caveat worth recording: the ShareGPT lanes spend their 96-token budget in
the reasoning channel (`finish_details.phase = "reasoning"`), so the served
harness carries an empty assistant message into the next turn and those
transcripts grow more slowly than the in-process A/B's (which carried the whole
decoded reply). That makes this run's reuse profile smaller (6 hits vs 16), so
its regression figure is conservative rather than generous. A `--thinking` knob
for the chat lanes is the follow-up, not a re-run of this evidence.

## TTFT over an in-process ASGI client (harness finding)

Client-observed TTFT through `TestClient` is **not** a first-token latency: the
test client buffers ASGI body chunks, so the first `iter_lines()` yield arrives
at the end of the turn. On the first four-arm run every one of the 164 measured
turns reported `ttft_ms / wall_ms == 1.000`. `scripts/gguf_live_server_bench.py`
already documents this ("TestClient may buffer ASGI body chunks; scheduler
latency is the retained TTFT/ITL source"); this harness now takes the same
route and reads the server's own stamp from the top-level
`hipengine.timing.ttft_ms` on each chunk, keeping the client-observed value as
`client_observed_ttft_ms` for diagnosis. A probe on the live server confirms the
split: a 30-token ShareGPT turn reports `ttft_ms=220` with
`server_elapsed_ms=3858` and `wall_ms=3860`.

The same probe found why the agentic fixture lanes report no TTFT at all: the
server answers those prompts with `finish_details.reason = "invalid_tool_call"`
and `cache_action = "append_none"`, suppresses the streamed content, and emits
only role, finish, and usage chunks. No token is ever emitted, so there is no
TTFT to report; per-turn records now carry `finish_details` so the artifact
explains itself.

## Next

  below-threshold reuse turns are the two cost centres. The served artifact
  carries per-turn `resident_bytes`, `snapshot_bytes`, `state_clone_bytes`, and
  `stats` deltas to attribute them; the first candidate is the per-turn 63.75 MiB
  snapshot clone that every completed request pays, including
  `prompt_too_short` turns that never look up.
- Harness follow-up: a `--thinking` knob so the chat lanes answer instead of
  spending their budget in the reasoning channel, which would restore the
  in-process run's larger reuse profile under the served protocol.
