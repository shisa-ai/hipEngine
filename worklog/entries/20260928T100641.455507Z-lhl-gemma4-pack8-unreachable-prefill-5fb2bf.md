# the expert pack8 layout is unreachable at prefill by construction so its byte economics never apply there

## Summary

I set out to attack the MoE path's 4x bandwidth gap with the one lever whose own
documentation invited the test: the expert pack8 layout is default-off because of a
**decode** measurement (21.03 -> 7.64 tok/s), while the loop metric is **prefill**,
and its docstring says clearing the gate "needs a measurement showing the packed
layout ahead at some other row count."

**Measured at prefill: 692 tok/s against 693 with it off. A null result -- and the
reason is structural, not economic.** The route the layout feeds is unreachable at
prefill by construction, so the byte economics never get to apply.

## The measurement

```
HIPENGINE_GEMMA4_EXPERT_PACK8_LAYOUT=1 \
  scripts/gemma4_campaign_bench.py --prompt 512 --output 128 --samples 3 --warmup 1
```

| | prefill tok/s | decode tok/s | load |
| --- | ---: | ---: | ---: |
| layout off (default) | **693** | 28.06 | 1.1 s |
| layout on | **692** | 27.87 | **116.6 s** |

No prefill gain, a slight decode regression, and **116 seconds of load-time repack**.

## Why it could not have helped

The route is not selected, and enabling the layout cannot make it selected. Read
from the engine's own counters with the layout on and a 128-token prompt:

```
expert routes:
  down_mmq32                   240
  gate_up_mmq32                240
```

**Both projections still run the MMQ32 route.** The gate/up selection at
`gemma4_experts.py:486` is:

```python
route_width = scratch.tokens
if not (gemma4_moe_gate_up_mmq_enabled()
        and gemma4_moe_prefill_route_enabled(lanes=route_width, num_experts=num_experts)
        and gemma4_project_experts_gate_up_mmq(...)):
    _record_moe_route(gemma4_project_experts_rows(...))   # the ladder, which has pack8
```

and `gemma4_moe_prefill_route_enabled` is a threshold at `_PREFILL_MIN_LANES_PER_EXPERT
= 1`:

> The crossover is one lane per expert: below it most experts are empty, so a grouped
> launch's per-expert grid would spend its blocks on nothing and the per-lane GEMV
> grid is cheaper.

**At prefill there is always more than one lane per expert** -- a 128-token prompt is
1024 lanes over 128 experts, 8 each -- so the MMQ route takes the gate/up and the
ladder containing `pack8_selected` is never consulted.

**So the pack8 route is reachable only when lanes per expert is below 1, which is the
decode regime.** That is exactly the regime where it was measured 2.75x slower. The
flag's default-off cause is therefore correct for the only regime in which the
feature can run at all, and the byte-economics argument -- 1.33x the bytes bought
back as fewer decode instructions per element -- never gets a chance to be tested at
a row count that would favour it.

**The gate is not merely un-cleared; it is un-clearable by the experiment its own
docstring proposes.** A large-batch decode where `rows` exceeds the expert count is
still below one lane per expert only if... it is not: 4096 rows over 128 experts is
32 lanes each, which selects `grouped_prefill`, not pack8. **The docstring's clearing
condition and the ladder's threshold are in tension**, and the row count that would
favour the packed form is precisely the row count at which the route is skipped.

## What this closes

The MoE path's 4x gap against pack8 GEMV is **not** addressable by turning on the
expert pack8 layout. Combined with `20260928T094722`, all three routes for the
gate/up are now measured at the shapes where each is reachable:

| route | reachable at | measured |
| --- | --- | --- |
| MMQ32 fused (current) | prefill and decode | **best at both** |
| fp32 grouped / selected ladder | prefill and decode | 2.2x worse prefill, 1.14x worse decode |
| pack8 selected | decode only | 2.75x worse decode; **unreachable at prefill** |

**The MMQ32 is the best available route for this projection at every shape it runs
at, and the remaining 4x gap is inside that kernel** -- what it pays that the pack8
GEMV does not. That is a profile-with-stall-attribution question, not a routing one.
