# Close the two instrument gaps that let the staged-prefill overrun through

## Summary

The Q5_1 staged prefill overrun (`ff7569f41`, fixed in `ebe2cc48b`) was not only a
wrong template argument. Two instruments that should have stopped it were unable
to, and both are now fixed.

**The optimizing loop's guard could not see the change it kept.** The
`gemma4-perf` loop's acceptance policy was a 64K production **decode** throughput
reading, and its guard ran four hand-listed test files -- none of which was
`tests/test_unit_gemma4_expert_route.py`. That file compares the staged prefill
kernel against a dequantized reference, ran in the default tier, and failed six
times under the commit that overran its staging buffer. So the loop's metric was
a phase the change did not act on, and its guard omitted the only tests that
owned the arithmetic the change altered.

**The public route probe could not see the decode scope at all.** Its observer
wrapped the layer's native launcher functions; the registered decode variants
(`gemma4_flash`, the staged split) do not go through them, they all pass through
`attention._launch_prefill`. At 16,384 prompt tokens under the promoted default
the probe reported 420 prefill launches and **zero** singleton ones -- the exact
shape of "this scope is not reached", produced by a scope that was reached and
merely invisible.

## Changes

- `docs/TESTING.md` -- new subsection "A guard must exercise the path the change
  touches", under the existing pre-existence rules: the metric must move with
  the change (both phases when a change can affect both, with the targeted one
  deciding), and a guard's test list is a snapshot that must gain the changed
  family's tests before the iteration is accepted. It cites the expert-route
  file as the concrete case.
- `scripts/gemma4_public_route_probe.py` -- observes decode through
  `attention._launch_prefill` as well as prefill through the layer functions, and
  reports the registered variant name from `attention.decode_selection` (0 block,
  1 plain, 2 staged, 3 flash) rather than a raw id. The module docstring now says
  why the two phases need different hooks.
- `tests/test_unit_gemma4_public_route_probe.py` -- one test that a singleton
  launch is recorded as the registered variant and a multi-token one is not, one
  parametrized over all three selections asserting the name comes from the
  constants rather than a literal, plus the restoration assertion.

## Validation

- `pytest tests/test_unit_gemma4_public_route_probe.py`: 11 passed. The first
  draft of the parametrized test asserted selection 1 was `gemma4_staged`; it is
  `gemma4_plain`, and the test now reads the constants instead of literals, which
  is the assertion that would have caught it.
- `python3 scripts/docs/check_all.py`: passes.
- The probe's new hook is not yet re-run against a real 16K request; the CPU
  tests cover the record shape and the naming, and the first GPU re-run is what
  will confirm singleton rows appear under the promoted default.
