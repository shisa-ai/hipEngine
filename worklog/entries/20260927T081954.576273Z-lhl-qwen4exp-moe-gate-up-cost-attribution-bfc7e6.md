# MoE gate/up is 82.5% matmul and 17.5% repair; expert-population tiles are dead

## Summary

Sprint M asked to attribute `expert_gate_up` (3377.1 ms post-unroll, 2640.6 ms of
the code-p4096 gap) to packing, maps, repair or reduction before fusing, to
include the 1.240 s repair pass, and to test expert-population-aware tiles on
real skew rather than a balanced model.

**Attribution.** The `moe:layers.*.expert_gate` roctx role decomposes exactly
into the three published families - 826 launches, 22 symbols, 6596.2 ms - and the
two family sums reproduce the published numbers to the decimal.
`expert_gate_up` = 2775.1 ms main matmul (`gguf_q4_k_selected_dual_wmma_iu8_risk_prefill_kernel<bf16,3>`
2708.8 + `gguf_q5_k_selected_dual_wmma_iu8_risk_prefill_kernel` 66.3) + 627.3 ms
repair (`gguf_q4_k_selected_dual_sparse_exact_repair_bf16_kernel` 568.2 +
`gguf_q5_k_selected_dual_sparse_exact_repair_bf16_kernel` 59.1) = 3402.4 ms.
Post-unroll with the 1240 ms repair included: **82.5% main matmul, 17.5% repair,
0% packing/maps/reduction.** The gate/up repair share is the pre-unroll 627.3 ms
scaled by the measured 5.8% unroll gain on that inner loop.

**So there is nothing to fuse.** The router logits (618.0 ms), reduction (67.6),
scatter (52.1) and silu (29.2) are `moe_reduce`, a separate 766.9 ms family, not
part of gate/up. The repair floor is already measured: MLP-bound, not bytes-bound
(3.3x less traffic is 22% slower; four grid sizes within 4%; 13.8% from L2
locality).

**Expert population, all 48 layers of a 1024-token prefill.** The tile map pads
each expert to a multiple of `tile_rows = 16` (`qwen35_moe_wmma_tile_map_kernel`,
`group_scatter.hip:328`). Measured: 10240 assignments/layer, **203.0 of 512
experts used (39.6%)**, median 5.9 rows, p95 339.9, max 937.6, **max/median
181.5x**. Real skew gives **772.9 tiles** against the balanced model's 725.2 -
the balanced model **understates by 6.6%**. Ideal unpadded is 640.0, so padding
overhead is 1.21x. The engine's `wmma_total_rows` matched the model exactly on
every layer, so the model is verified.

**The balanced model is genuinely wrong, but wrong by 6.6% - and the tile count
it predicts is not the constraint.** Tile sweep: tile8 1394.1, tile16 772.9
(shipped), tile32 468.8 (0.61x), tile64 322.0 (0.42x). The 2026-09-22 j32 packet
measured the 32-row tile at 1.3-2.2x slower with only **6.3%** real DRAM
reduction against the model's 39%, and its own conclusion is the falsification:
the tile-count model counts *distinct* weight reads and a taller tile makes them
shared rather than distinct, and sharing only pays if it is explicit. L2 already
deduplicates one expert's repeated weight reads across its tiles.

**Consequence: expert-population-aware tiling is measured dead as a direction.**
It moves a quantity that is not the constraint. Even eliminating every padded row
caps the tile-count win at 21%, and the real DRAM win would be a fraction of that,
bought with the occupancy loss that already killed the 32-row tile. The lever the
evidence supports is Sprint H's: explicit LDS weight staging, a different weight
path rather than a tile-height parameter.

## Next

Do not build an expert-population-aware tile. If the gate/up matmul is attacked,
the target is the weight path: explicit per-block LDS staging of the quantized
weight chunk (Sprint H, `benchmarks/results/2026-09-27-moe-down-lds-weight-staging/`).
Note that the at-risk flags are already in LDS (`qwen4_exp_q5_1.hip:1069`), so the
staging change is scoped to the weight operand, not the risk state.
