# Qwen3.8-27B MTP pass: verify-dominated, already optimized; no large missed win

## Summary

Profiled the shipping native MTP B3 cycle (rocprofv3 kernel-trace + ROCTX, full
mtpbench path, Q4_K_M, gfx1151 zbook). Per-cycle cost attribution (14 cycles):

| Stage | ms/cycle | share |
| --- | ---: | ---: |
| target_verify | 132.2 | ~85% |
| proposal (NextN) | 22.9 | ~15% |
| scheduler/accept/replay host residual | 0.85 | <1% |
| target_commit_finish | 0.01 | ~0% |

MTP decode 21.98 tok/s on the 2-prompt profile slice (full-suite baseline 18.05,
task #13). The cycle is overwhelmingly target-verify bound. The verify is
GPU-weight-bound (reads the ~16 GB target once per cycle for 4 rows) AND
AR-exactness-constrained: it uses the exact rowtile path; a reassociating WMMA
prefill would be faster but breaks the binding exact-ID contract, so it is not a
legal lever for exact MTP. The host residual (<1 ms) shows the verify is already
graph-captured (no muse-glimmer-style eager dispatch bubble to remove).

Already-applied optimizations confirmed in the path (closed campaign + base
50824318d): HIP graph capture for proposal and target verify; NextN hot-vocab +
fused linear+argmax top-1 head; production Q4 rowtile verify; and the transferred
Muse Glimmer wins — the Q6 rowtile metadata hoist (same
q6_k_t16_qmicro_planar_gemv_rowtile_col8 kernel) and the host-sampler incremental
penalty fix — both already in this branch's base.

Conclusion (measured explanation, not a win): no large missed MTP optimization on
this host. The cycle is verify-dominated, the verify is at its exact-path
ceiling, and the transferable Muse Glimmer levers are already present. Remaining
theoretical headroom is the exactness contract itself (production-profile
reassociation) which the campaign binds to exact IDs, and the proposal (~15%),
already hot-vocab/fused-head optimized.
