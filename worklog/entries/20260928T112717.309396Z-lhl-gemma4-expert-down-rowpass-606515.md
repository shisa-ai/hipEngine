# the expert down projection re-read its weights once per 16-row pass; ROWS_PER_PASS 32 cuts 27 GB and 2.5 percent of prefill

## Summary

**The lead the previous entry opened resolved into a one-constant fix with a
measured end-to-end win.** `q5_1_mmq_ds4_selected_prefill.hip` unpacks a weight
row once per row pass and reuses it across `ROWS_PER_PASS` rows, so an expert
whose row count exceeds `ROWS_PER_PASS` re-reads its entire weight block once per
pass. Gemma 4's experts average 32 rows at a 512-token prompt, and
`ROWS_PER_PASS` was 16, so **every expert read its weights exactly twice**. The
constant is now 32.

**Measured, same host, same geometry, one kernel under one counter:**

| | FETCH_SIZE | kernel ms/step | VGPR |
| --- | ---: | ---: | ---: |
| `ROWS_PER_PASS = 16` | 62.33 GB | 118.25 | 80 |
| `ROWS_PER_PASS = 32` | **34.89 GB** | **104.84** | 96 |

**End-to-end prefill at 512 tokens, six runs, two instruments:**

```
0.725  0.731  0.736   (kernel census, repeats 5)
0.723  0.729  0.734   (dense probe, repeats 5)
median 0.7305 s   (701 tok/s)
```

against the baseline 0.7495 s (682 tok/s): **2.5 percent faster**. The down
projection leaf fell from 127.11 ms to about 111 ms of the step, and its share
from 17.0 to 15.2 percent.

**This also confirms the weight-re-read model and corrects the previous entry's
open question.** The 62.33 GB was not activation re-reads; it was the weight
stream, read twice. The residual at `ROWS_PER_PASS = 32` is about 29 GB, which is
neither the weight bytes (5.7 GB for the whole model's down projections) nor a
pass-count artifact, so a second mechanism remains -- but the ranking and the
bandwidth figure from the previous entry both held up.

**Why 32 and not more.** The cost of a larger pass is one accumulator per row, and
that is the whole register budget: 16 rows to 32 rows moved the kernel from 80 to
96 VGPRs, and `__launch_bounds__(128, 4)` caps it at 128. 64 would not fit without
dropping the occupancy bound. It would also buy little here: at a mean of 32 rows
per expert, 32 is already one pass for most experts, so the remaining gain would
come only from the tail that exceeds 32.

**The rate tells the next story.** At 16 rows the kernel ran at 527 GB/s, which is
DRAM-saturated. At 32 rows it runs at 333 GB/s for 104.84 ms -- the bytes fell by
44 percent and the time by only 11 percent, so the kernel is no longer
bandwidth-bound and something else now sets the floor. The 22 output-column blocks
per expert, each of which re-reads the whole activation tile, are the standing
candidate.

## Changes

- `hipengine/kernels/hip_gfx1100/quant/gguf_q5_1_mmq_selected_prefill.hip`
  - `ROWS_PER_PASS` 16 to 32, with the weight-reuse reasoning recorded where the
    constant is defined. A pure loop-blocking factor: each row's accumulator sees
    the same terms in the same order, so the arithmetic is unchanged.
- `tests/test_gpu_gguf_q5_1_mmq_selected_prefill.py`
  - The test's count profile was `[4, 7, 0, 12, 1, 3, 0, 6]`, whose largest expert
    is 12 rows, so **it never took a second row pass and could not have caught
    this either way**. Counts are now a parameter with a second profile of
    `[31, 32, 33, 0, 1, 64, 65, 2]`, which exercises one, two and three passes and
    puts one expert exactly on the boundary. Same oracle: the strict grouped
    owner, the dequantized matmul, and the production-variant envelope.

```
# the surface a user reaches, and that the intended route ran
# -> gemma4_project_experts_down_mmq n=30 in the census on every layer
# -> greedy generation is byte-identical before and after the change
```

The generation check is worth spelling out, because its first reading looked like
a regression. Prompted with a raw string, this instruction-tuned model produces
degenerate continuations ("The capital of France is" -> " a bit.\n```\n[\n]"). That
is the missing chat template, not the engine: with the template it answers
correctly. **The relevant evidence is that the degenerate text is byte-identical
with the change stashed and restored**, which is what a pure blocking-factor change
must produce, and it is a stronger end-to-end check than a token-count comparison.

## Next

1. **Attack the ~29 GB residual on the down projection.** The kernel now sits at
   333 GB/s, so it is no longer DRAM-bound; the 22 output-column blocks per expert
   each re-read the activation tile and are the standing candidate. Giving each
   thread more than one output column shares those activation loads and cuts the
   block count in the output dimension at the same time. That is a real kernel
   change and it needs its own microbench and oracle, not another constant.
2. **Re-examine the gate/up projection against the same model.** It fetches
   20.78 GB at 135.6 GB/s for 153 ms, so it is *not* bandwidth-bound and the
   traffic reduction is not where its time goes. Its 1.13x T16 win is validated
   and bit-exact but costs 8.7 GB resident or a decode-side layout change, which
   at 24 percent of prefill is a worse trade than the down projection's remaining
   29 GB for no resident cost.
