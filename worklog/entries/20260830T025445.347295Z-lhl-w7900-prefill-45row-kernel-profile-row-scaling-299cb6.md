# W7900 Qwen3.8: 45-row shipping prefill profile - GPU-bound, 85 percent wmma GEMMs, 6.9x per-token cost vs 512 rows

## Summary

The ~300 ms/token admission cost is GPU work, not host overhead, and it is
overwhelmingly prefill GEMM time. Aggregating the retained shipping-route kernel
trace at `prompt_length=45` gives 287.0 ms of GPU busy time per pass against a
295 ms cell wall (2.7% host/queue gap), split 84.9% wmma prefill GEMM / 10.2%
gemv / 1.8% attention / 1.3% norm+eltwise / 1.2% other / 0.7% copy. The same
pipeline at 512 rows costs 0.921 ms/token against 6.378 ms/token at 45 rows, so
per-token prefill cost is 6.9x row-count dependent. Grouping, not attention or
Python, is the lever.

## Changes

Analysis only - no code or benchmark-rollup change. Adds this entry plus the
aggregation method (kernel-family bucketing over a retained `rocprofv3` kernel
trace) so the numbers above are reproducible from the artifact rather than from a
re-run. The control/capability-8 measurement still in flight will carry any
benchmark row.

## Method

No new run: the artifact from the shipping-route trace was already on disk
(`/tmp/he-trace-ship-45.json` plus `epyc/101786_kernel_trace.csv`, 6358 kernel
records, 1 warmup + 2 measured passes of the same 45-token prompt, so per-pass
figures are total/3). Durations from `End_Timestamp - Start_Timestamp` - this
`rocprofv3` build emits no `DurationNs` column. Model identity: Qwen3.8-27B
Q4_K_M, `total_tensor_nbytes` 17,095,778,304 (17.10 GB) from the artifact itself.

| 3.5% | 10.0 | `q4_k_t16_dense_dual_local32_silu_gemv_kernel` |
| 3.4% | 9.8 | `gguf_q4_t16_dense_unequal_dual_wmma_prefill_bf16_kernel` |
| 2.2% | 6.3 | `q4_k_t16_dense_single_local32_gemv_kernel` |

Family totals: wmma prefill GEMM 243.6 ms (84.9%), gemv 29.4 ms (10.2%),
attention/GDN 5.2 ms (1.8%), norm/eltwise/rotary 3.6 ms (1.3%), other 3.6 ms,
copy/fill 2.0 ms.

Two things this settles. First, attention is irrelevant to the admission gap at
these lengths - 1.8% of the time. Second, 29.4 ms/pass still routes through
`*_local32_gemv` kernels at 45 rows, which is the small-row prefill defect that
#8 also covers: those launches are decode-shaped work inside a prefill.

## Roofline context

One-pass-equivalent streaming: 17.10 GB / 287 ms = 59.6 GB/s, 6.9% of the
864 GB/s theoretical GDDR6 peak in `docs/ROOFLINE.md` (that table records the
W7900 at 18 Gbps x 384-bit; the measured 960 GB/s figure there is for the 7900
XTX at 24 Gbps, so this is the right reference for this host). At 512 rows the
same arithmetic gives 36.3 GB/s one-pass but 0.921 ms/token, i.e. far better
work per byte moved. With 16-row tiles a 45-row prefill re-reads weights ~3x
(~178 GB/s effective), which explains part - not all - of the gap and is exactly
what packing more rows per step amortizes.

## Correction to what I said earlier in this session

I first read the C1-C8 admission walls as "growing 2.9 s per lane, so 7.7x worse
under concurrency" and separately described the trace as "59.2% + 38.8% unnamed
buckets". Both were my parsing errors: the summary's `wall_seconds` is summed over
the 10 cells at each width while each cell generates `width` tokens, so per-token
admission cost is flat (302 ms at C1 to 290 ms at C8) - the finding is *zero*
concurrency gain, not degradation; and the name buckets came from stripping
everything after `(` on `void (anonymous namespace)::...` symbols.

## Validation

Cross-checks on the numbers themselves, since this entry makes no perf claim:

- GPU busy (287.0 ms/pass) is within 2.7% of the independently measured AR cell
  wall (295.1 ms, `/tmp/he-d1-clean/he-d1-clean.json`, width-1 cell
  `code_merge_intervals`, `decode_steps: 0`), so the trace and the packet agree on
  what one admission costs even though they came from different runs.
- Kernel records (6358) divided by the artifact's declared 3 passes give
  2119 launches/pass over 64 layers' worth of stages, which is consistent with the
  per-kernel launch counts in the table (e.g. 64 and 112 per pass).
- `total_tensor_nbytes` (17,095,778,304) is read from the artifact's `gguf` block,
  not assumed, and the bandwidth arithmetic is stated as one-pass-equivalent
  because the 16-row tile count is not recorded in the trace.
- `python3 scripts/worklog.py check` passes for this entry.
