## Changes


- Completed a read-only review of qwen-kernel `52e240f9c6d91750d0e5e692976cfb67fd9bc603` plus the local 12-line trailing-MTP clamp, its complete `docs/amd-opt/{REPORT,NOTES}.md` evidence, active engine dispatch, IQ3/IQ4/Q6/router/shared/GDN/attention shaders, and baseline records. Also read all 2,674 lines of `../hipEngine-main/docs/HIP-vs-VULKAN-HISTORY.md` and ROCm issue [#6409](https://github.com/ROCm/ROCm/issues/6409), including the one public comment. Neither external tree was edited; there is no ROCm engineering response yet.
- The current GPU1 qwen-kernel row is 512/128 **829.30 pp / 189.96 tg** (`5.264 ms/token`) on the 15.930 GiB UD-Q3_K_M file. The same baseline's hipEngine UD-Q4_K_M row is **3,073.85 pp / 105.791 tg** on a 21.107 GiB file. The 1.325x file-size ratio explains part, not all, of the decode delta; formats, active bytes, activation precision, and engines differ, so this is a target/context pair rather than a controlled kernel ratio.
- The qwen baseline is not its best documented prefill configuration. Its command omits retained `QK_MOE_GROUP_PREFILL`, `QK_MOE_GU_ROWTILE`, `QK_MOE_SELECT_HIER`, `QK_MOE_SHARED_GU_64`, and `QK_MOE_SHARED_DOWN_32`. In the qwen campaign, counting-sorted expert-major IQ3 gate/up moved token-major **595.31 -> 767.69 tok/s** (+29.0%) on XT; grouped gate/up+down reached **858.33** (+44.2%). The final XTX grouped prefill median was **1,153.31 tok/s**, +33.6% versus its matched token-major samples. These runs are not substituted into the July-19 baseline, but they prove the reported 0.7-0.83K pp is not a qwen architecture ceiling.
- The prefill pathology is algorithmic: token-major selected GEMV rereads an expert row once per `(token,slot)` assignment. At 512 tokens, top-8 routing nearly fills all 256 experts and averages about 16 assignments/expert. Wider chunks alone recovered only 8-19%; qwen's sort/reuse recovered 34-44%. hipEngine should therefore run its Q3 prefill pass immediately after the direct correctness/profile baseline, using the existing compact count/prefix/scatter-gather/tile-map ABI. A qwen-style scalar grouped kernel is a useful control/fallback, but closing a 4-5x gap to hipEngine Q4 requires the higher-upside path: dequantize IQ3/IQ4 codebook tiles into F16/BF16 fragments and reuse them across sorted token lanes with the existing wave32 WMMA machinery.
- The hot qwen IQ3 decode mapping is directly transferable as a source hypothesis: hidden=2048 produces exactly 256 eight-value work units, one per lane in a 256-thread workgroup; gate and up share the input load and SiLU is fused. Its decode-only row-stationary variant retains each lane's eight inputs across output rows. `ROW_TILE=4` reduced `moe.gu` **791.9 -> 726.2 us** (-8.3%) and moved direct wall by about 0.5-1.5%; rowtile8 regressed to **918.4 us** from register pressure. hipEngine will land rowtile1 as the correctness control and measure 1/2/4/8 after the prefill pass rather than assuming ACO's rowtile4 result transfers.
- qwen's routed down is not merely a single selected GEMV. `moe_down_iq4.comp` and `moe_down_q6k.comp` apply routing weights inside one all-route reduction and emit one routed vector. For the common IQ4 top8/n_ff=512 shape, there are exactly `8 * (512/32) = 128` useful tasks; local128 improved the qwen routed-down stage 5-6%. The raw-IQ foundation task now includes a fused routing-weighted IQ4_XS down composite plus the single-selected primitive and weighted-sum chain as its mandatory unfused fallback. Q6 outlier layers stay on the existing path initially.
- qwen also overlaps independent commands by omitting barriers between router/selection and shared gate/up, and between routed and shared down, before a fused residual+RMS tail. This is a genuine Vulkan command-DAG opportunity, not automatically a HIP win. A later task is profile-gated to test explicit HIP graph branches or a narrower producer/consumer fusion; it must reject cleanly if one-stream bandwidth contention or HIP queue/runtime behavior erases the overlap.
- Several prominent qwen techniques are already present in hipEngine and should not be reimplemented: one-launch cooperative expert/shared router+top-k, fused recurrent GDN+rmsnorm+gate, live-span split attention with grouped-GQA policies, fused gate/up+SiLU registration with unfused fallbacks, shape-specific dense/shared kernels, GPU sampling, and one-step graph replay. qwen submits and waits once per serial token; `QK_CHUNK=8` batches the host API/output budget but does not encode eight dependent tokens into one command buffer. Prior hipEngine multi-step graph replay is already a measured neutral/regression and remains out of scope.
- The HIP/RADV evidence narrows compiler risk. On matched gfx1100 timing-contract-v2 rows, Vulkan's serialized packed-integer advantage is **1.052x-1.133x**, while tiny command replay is **2.44x-10.12x** faster and independent small-kernel geometry/reduction can favor Vulkan by about **1.10x-4.04x**. Both compilers emit dot4; production Q4/Q6 quantize+dot controls favor HIP. Thus ACO alone cannot explain qwen's ~1.8x topline over hipEngine Q4. For IQ3, inspect the actual HIP HSACO for constant-table loads, the 98-byte block's unaligned aux-u32 load, address/wait structure, VGPRs, occupancy, and scratch; try byte-load versus packed/memcpy source forms only when a concrete miss appears.
- Explicit non-targets from the combined evidence: no broad wave64, fixed-block, VOPD, LDS-staging, generic dot4, or hand-ISA campaign; no production Vulkan backend; no repeated multi-step graph sweep; no full expert-FFN megakernel (the existing Q4 version won microbench but regressed c=1 E2E); and no blk.40 Q3_K work without GGUF-MTP approval. A q8_1+signed-dot IQ3 candidate is conditional on the raw kernel remaining a measured dequant/instruction bottleneck and must include activation materialization and full-model quality.
- Reprioritized task graph: #7 now includes the weighted IQ4 down composite; #8 registers/wires it with a loud unfused fallback; #10 records one-step graph parity plus stage/byte/code-object evidence without rerunning qwen; #11 is the high-priority grouped scalar versus compact-WMMA prefill pass; #15 then performs the rowtile/codegen decode pass; #16 finally tests profile-gated graph-DAG overlap/fusion. Deferred #12 remains blocked behind this AR chain and still requires explicit MTP ABI approval.
