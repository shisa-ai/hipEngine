# Keep the provider's early-EOS cause in speculative normalization

## Summary

The public Gemma 4 plain/MTP early-stop mismatch is a service-boundary relabel,
not a decode difference. Both Gemma 4 routes publish the same two tokens and
report `reason="stop"` with the model end-of-generation token in
`eos_token_id`. `EngineService._normalize_speculative_output` re-derived `"eos"`
from `trim_speculative_output` and overwrote the provider's cause even though it
had shortened nothing. The MTP route therefore reported a different
`finish_details.reason` than the plain route for identical output, and on the
resident token-event stream the `"eos"` label also suppresses the terminal token
while the blocking reply keeps it.

The repair keeps a provider's terminal cause when the service did not shorten
the published run. A provider that reported `"length"` while its run ends at a
terminal token is still corrected, so the existing `length`-to-`eos`/`stop`
normalization and overrun trimming are unchanged.

## Cause evidence

- Plain Gemma 4 sets `finish_reason="stop"` and `eos_id=token` for a configured
  end-of-generation token (`hipengine/generation/gemma4_gguf.py`, decode loop).
- MTP Gemma 4 sets `reason="stop"` and `eos_token_id=generated[-1]` when no
  stop sequence matched (`hipengine/generation/gemma4_mtp.py`,
  `generation_steps`). Both routes keep the terminal token in the reply text
  because `visible` subtracts only `stop_sequence`.
- Only speculative children are normalized: `_finish_ready_children` calls
  `_normalize_speculative_output` for `verify_chain`/`verify_tree`
  (`hipengine/generation/engine_service.py`), so the plain AR route never sees
  it.
- `trim_speculative_output` classifies a token equal to `eos_token_id` as
  `"eos"` (`hipengine/speculative/streaming.py`), which is the label the service
  substituted.
- The difference is public: the HTTP server exposes
  `choices[].finish_details.reason` unchanged through
  `_finish_details_payload`, so this was not only an internal probe label.
- The recorded public HTTP matrix already fixes the intended Gemma 4 semantics:
  `benchmarks/results/2026-10-17-mtp-corrected-public-matrix.json`,
  `models.gemma.rows[21,22,32,33]` show natural EOS stops (token 106) on both
  routes reporting `reason="stop"` with `eos_token_id=106`, including
  `sampler_mode="greedy"` and `"greedy_speculative_mtp"`. Rows 32/33 are the
  long-context case that completed after two output tokens ending in EOS, the
  same shape as the probe repro. The later shared speculative normalization is
  what made the MTP route disagree.
- Existing CPU fakes reproduce the provider contract exactly: both routes emit
  `[26, 3]`, `reason=stop`, `eos_token_id=3`, `stop_sequence=()`; only
  `sampler_mode` differs (`greedy` versus `greedy_speculative_mtp`), which the
  probe does not compare.

## Changes

- `hipengine/generation/engine_service.py`: in the no-trim branch of
  `_normalize_speculative_output`, return the provider output when the trim's
  terminal boundary is `eos` and the provider already reported `stop` with that
  token in `eos_token_id`. The provider owns the model's cause vocabulary; the
  trim owns the boundary and still corrects a `length`-only report or a run it
  actually shortens.
- `tests/test_integration_engine_service_speculative_finish.py`: new
  `EarlyEOSDriver` and `test_an_early_model_eos_keeps_the_provider_cause_on_both_routes`.
  It runs the same early-EOS output through the plain child path and the
  speculative child path and checks reason, `eos_token_id`, sampler mode, token
  IDs, blocking text, streamed text, and the terminal chunk's finish details.
- `tests/test_unit_gemma4_generation_controls.py`: new
  `test_an_early_model_eos_reports_the_same_cause_on_both_routes` pinning the
  provider-level contract both routes must preserve.

Not changed: generated token IDs, sampling, visible text, stop-sequence
truncation, `trim_speculative_output`, the probe, the server mapping, or the
Gemma 4 provider labels.
