# GD-4's build plan: cooperative L is the difference between a 2%-of-peak and a 25%-of-peak bar

## Summary

Working GD-4's design against the validated reference and the existing ABI surfaced four
constraints, three of which the ledger row does not state. **The decisive one: L and QK are
value-column independent, so computing them per warp instead of cooperatively costs 16x -
+66.7% arithmetic at chunk 16 against +4.17% cooperative - which converts the priced
1.05 TFLOP/s break-even into a ~15 TFLOP/s requirement.** Also: chunk 32 fits LDS (56.6 KB of
64 KB), and the block decomposition must change from `tiled16`'s `(48, 8)` grid to a
two-kernel chunk-axis design, because the current grid makes 8 blocks per v-head recompute L
while one block per v-head leaves half the 96 CUs idle.

## Validation

- The algorithm is transcribed from `scripts/gdn_chunk_drift_screen.py::_chunk_local`,
  the validated reference whose direct suffix product is locked by
  `tests/test_unit_gdn_chunk_drift_screen.py`, not re-derived.
- The cooperative/redundant figures are computed, not asserted: at chunk 16,
  `L+QK = 120x128 + 136x128 = 32,768` MACs per chunk per head, which is
  `32,768/16/49,152 = 4.17%` cooperative and `4.17% x 16 = 66.7%` per-warp.
- The LDS figures are summed from the declared staging set at 4 B per float.
- The grid shape `(num_v_heads, col_blocks)` and the 96-CU figure are read from
  the existing `tiled16` launcher and the host's device properties.
- Build plan only: no kernel written, compiled or timed.
- `python3 scripts/worklog.py check` passes.

## Why the design pass was worth doing before the code

The row says the remaining work is "the kernel build". It is - but three of the four
constraints above are invisible from the row, and two of them change the kernel's
*structure* rather than its tuning.

The one that matters most: a builder who ports `tiled16`'s grid and computes L per
warp produces a kernel that is **66.7% over its arithmetic budget**, and no amount of
timing will say why. The feasibility screen said the bar is 2% of peak; the same
kernel built the other way faces a 25%-of-peak bar. **The constraint has to be known
before the code is written, because it is not discoverable from the result.**

Same class as the DP-5 re-scoping earlier this session: a row that reads as a bounded
build turns out to carry a structural requirement that only appears when the design is
worked.

## Still not a win

No kernel was written, compiled or timed. The deliverable is the design and its
constraints. GD-4 remains actionable and is now cheaper to start - but the campaign
still has no retained optimization from this session, and that is the objective's
actual bar.
