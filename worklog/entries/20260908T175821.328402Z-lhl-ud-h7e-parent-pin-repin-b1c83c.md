# Re-pin the H7E parent-source drift guard

## Summary

Correction to `018bc80eb` and `6e2e88df9`. Both edited
`gguf_iq_source_mmq_prefill.hip` to add IQ4_NL and IQ3_S arms, which changed
the body of `gguf_iq_selected_mmq_i128_j128_k256_q8_1_ds4_kernel`.
`tests/test_laguna_h7e_iq3_d4x2_source_mmq.py` pins a SHA256 of that
declaration as a drift guard for the H7E d4x2 candidate, which forks it. **I
did not run that file in either unit, so both commits shipped with it failing.**

## Changes

`tests/test_laguna_h7e_iq3_d4x2_source_mmq.py`: `_SOURCE_KERNEL_SHA256`
re-pinned, with the reason recorded beside it.

## Validation

The guard is doing its job, and re-pinning is the right response rather than
weakening it:

- Only the kernel-body pin moved. `_SOURCE_LAUNCH_SHA256`, both export pins,
  the metadata pin and all Python-side pins are unchanged, so the shared launch
  path and ABI did not drift.
- The d4x2 candidate forks the IQ3_XXS path, whose expansion and addressing I
  did not touch; the QTYPE 1/2 arms and the `block_bytes` selection are
  additive.
- The other nine tests in that file pass against the modified parent, so the
  candidate still behaves.
- Swept every SHA-pinned suite that references the three files this campaign
  edited (`gguf_iq_source_mmq_prefill`, `gguf_iq_dense`, `gguf_iq_gemv`):
  `test_gguf_ud_admission.py` and the five `test_laguna_h6*` suites are green,
  so this was the only broken pin. In particular the `gguf_iq_dense.hip` grid
  extraction broke nothing.
