# Muse Glimmer graph-captures exact block verify (4/5-row graphs), bit-identical

## Summary

Task #4 (§11 #5). The exact DFlash block verify ran ~740 eager kernel launches
per cycle. Captured it into HIP graphs mirroring the shipped AR decode graph:
a kernel-only `_verify_graph_body` (bit-identical row-independent projections +
shared-row attention + fused residual boundaries), graph-stable staging (token
ids/positions in the scratch buffers, live key end in a device buffer the shared
attention reads via key_end_dev), and fixed tap/logits buffers (the eager path
mallocs these per call; a graph records pointers). Graphs are keyed by
(tokens, tap_layers); the shipping budget-4 cycle verifies 4 or 5 rows depending
on a pending root, so two graphs cover it. verify_with_taps replays the matching
graph and falls back to eager on capture failure / unsupported rows / other tap
layouts / image overrides. Replay is bit-identical to eager (logits AND taps,
0.0 diff), so verify-written KV still equals true AR.

Measurement caveat (thermal): the wall-time saving measures only ~0.5 ms/cycle
in the current session because the laptop is power-capped/thermally throttled
after sustained load — verify is GPU-weight-bound (~134 ms/cycle) and the host
dispatch of 740 launches hides under kernel compute, so removing it barely moves
the wall. The shipped AR decode graph shows the SAME ~0 ms saving now versus its
historical ~9 ms/step at full GPU speed (test_live_muse_glimmer_runner comment):
the graph benefit appears when host dispatch is on the critical path (fast GPU).
The §11 ~7 ms verify estimate is that full-speed host-dispatch bubble; it is
inferred from the decode-graph analog, not confirmable under current throttling.
The launch-count reduction (740 -> 1 graph launch/cycle) is real and
thermal-independent (less host CPU dispatch work). Ship-on per Product Defaults:
working, bit-identical, non-regressive, engages by default; the engagement test
guards silent fallback.
