# Q6_K o_proj support in the Q4 prefill route; batched prefill found non-deterministic in both lanes

## Summary

Closes the remaining sub-clause of the first review finding: the batched
prefill's o_proj path hard-required Q4_K while the loader accepts Q6_K for any
tensor, so an accepted file with a Q6_K o_proj would have failed prefill.

`gemm_f32_f32` now dispatches on the resolved type. Q4_K keeps the native
f32-in/f32-out WMMA prefill it already used; Q6_K narrows the f32 attention
output to bf16, runs the Q6_K bf16/bf16 prefill kernel and widens the result.
Anything else still raises. This deliberately does **not** follow the review
suggestion to unify o_proj onto the bf16 path: doing so would narrow the
already-validated Q4_K arithmetic (the path the real model uses and that the
benchmark numbers were measured on) to buy nothing. Adding the Q6_K branch
supports both types with no change to the Q4_K result.

## Finding: the batched prefill is not deterministic in either lane

Writing the zero-weight cross-check surfaced something larger. Two identical
`prefill_rows` calls on identical inputs produce different hidden rows:

| lane | differing hidden elements | argmax |
| --- | --- | --- |
| bf16 (hipBLASLt, untouched by this work) | 318156 / 318976 | stable in 2 of 3 runs |
| Q4_K_M | 318118 / 318976 | 151644 -> 1335 across runs |

The sequential row-by-row route is bit-exact across repeats. So the
non-determinism belongs to the shared batched orchestration
(`runtime/vibevoice_qwen2.py::_prefill_batched`, the `vv_kv_write_spans` +
`vv_attention_spans` path), not to the Q4 prefill route, and it is pre-existing.

This changes how the earlier KL gate must be read. The production envelope
requires deterministic repeatability, and top-1 agreement against a separate
sequential run is contaminated by this noise: 94.5% top-1 measured on the Q4
route is not evidence about the Q4 arithmetic. All four KL metrics do pass
(mean 6.1e-4, p95 3.0e-3, p99 3.5e-3, max 4.4e-3 against 1e-3 / 5e-3 / 2e-2 /
5e-2), so the distribution-level agreement is real even though the argmax-level
claim is not yet measurable.

`test_batched_prefill_determinism_and_top1` encodes this as an xfail
(`strict=False`) so the suite stays green and an XPASS flags the day the engine
becomes deterministic. The top-1 clause is deliberately **not** asserted as
passing anywhere.

## Next

- Root-cause the batched prefill non-determinism. Candidates: a race in the

  finished writing. It affects both lanes, so it should be fixed once, in the
  shared path, before any batched-prefill perf claim is promoted.
- Re-run the production KL envelope once determinism holds; the top-1 clause is
  the only part currently unmet.
