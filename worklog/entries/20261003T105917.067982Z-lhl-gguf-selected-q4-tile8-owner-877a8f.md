# Selected Q4_K gate+up tile8 owner: byte-identical, -6.8% on the MoE selected stage

## Summary

`decode_ffn_moe_selected` was the largest remaining bandwidth-efficiency gap in
the decode step: 597.8 MiB/token at **170.4 GB/s** (72% of the 237 GB/s
ceiling), 3.678 ms of a 17.81 ms step. Its Q4_K gate+up leaf ran at VGPR 200 and
1024 bytes of LDS per workgroup with only 32 resident workgroups, so it was
register/occupancy-limited rather than bandwidth-limited. A new owner,
`q4_k_t16_selected_dual_silu_tile8_gemv_kernel`, covers **8 columns per
workgroup instead of 16** while keeping the 16-column owner's thread K
ownership and reduction tree, so it is **byte-identical** and halves register
pressure. The real stage drops **-6.83%** and decode rises **+1.76%**.

## Why it is byte-identical

Both owners launch `dim3 block(128)` — the 16-column owner is declared
`__launch_bounds__(256, 1)` but its host wrapper passes 128, which is what makes
this a pure work-partitioning change rather than an arithmetic one:

| | 16-column owner | tile8 owner |
| --- | --- | --- |
| block | 128 | 128 (`kThreads`) |
| K ownership | `k_in_block = tid; k += blockDim.x` | `k_in_block = tid; k += kThreads` |
| K-block loop | `for blk < blocks_per_row` | same |
| wave reduce | `GGUF_T16_WAVE_REDUCE` per column | same |
| cross-wave sum | `sub_groups = blockDim.x >> 5` = 4, ordered `g = 0..3` | `kThreads >> 5` = 4, same order |
| BF16 round-trip, fused SiLU | present | same |

Only the column count per workgroup differs, and `col_base = (out_group & 1) *
kTileCols` maps the two half-tiles back onto the 16-column layout. The nibble
and coefficient loads become one aligned `uint32` per buffer per column pair,
which changes how values are fetched, not which values are combined or in what
order.

Verified three ways:

- `tests/test_gpu_gguf_t16_selected_gemv_decode.py::test_qwen_c1_selected_q4_tile8_matches_col16_production_bits`
  runs both owners at the production 2048x512x8 shape and asserts
  `np.testing.assert_array_equal` (HIP-guarded, so no-ROCm runners skip it).
- The delegated run's 120-config sweep over heavy-tail inputs with scales
  0.5-120: **491,520 outputs, 0 mismatches, worst ULP 0**.
- The delegated run's real-model check: 512-token prefill plus 16 greedy steps
  produced **byte-identical final logits** (993,280 bytes) and the same token
  ids.

## Validation

### Mechanism (rocprofv3, production 2048x512x8 shape)

| kernel | VGPR | LDS | block | grid.x | dispatches |
| --- | ---: | ---: | ---: | ---: | ---: |
| `..._dual_silu_direct_gemv_kernel` (16-col) | 200 | 1024 | 128 | 32 | 3 |
| `..._dual_silu_tile8_gemv_kernel` (new) | **88** | **512** | 128 | **64** | 200 |

Both at 128 threads, which is the precondition for byte-identity. Halving the
live accumulator set doubles resident workgroups and is the whole mechanism.

### Real decode step (same-session A/B, GPU stage recorder)

`run_q4tile8_ab.py {baseline,patched}` toggles the real flag, so both arms run
one tree and one session shape. Coordinator's independent re-run:

| measurement | baseline | patched | delta |
| --- | ---: | ---: | ---: |
| `decode_ffn_moe_selected` | 125.727 ms/32tok | 117.140 | **-6.83%** |
| decode | 53.4247 tok/s | 54.3652 | **+1.760%** |
| prefill | 1410.50 tok/s | 1410.47 | -0.002% (flat) |

The stage saving is 268.4 us/token against an 18.7 ms step = +1.434% predicted,
and +1.760% was measured, so the transfer is complete. The delegated run read
125.715 -> 117.215 (-6.76%) and 53.598 -> 54.327 (+1.36%), so the stage delta has
reproduced across two independent sessions.
