# GR-up cost attribution: weight-bandwidth-bound on a 256x re-read

## Summary

`q8_0_gr_up_sigmoid_mean_coltile2_branch4_rowbatch4_f32<true>` is the largest
single kernel in the prefill and it had never been attributed. It is
**weight-bandwidth-bound at 59% of DRAM peak**, with **90% of its traffic being a
256x re-read of one 3.48 MB tensor**, because the dequantized weight is amortized
over only `ROW_BATCH=4` rows.

| | |
| --- | --- |
| 1x time | **2507.0 ms** (384 launches/prefill, 6.529 ms each) |
| share of prefill kernel time | **15.5%** of 16189.5 ms - rank 1 |
| shape | rows=1024, K=320 (`low_rank`), N=10240 (4 branches x 2560) |
| grid | (1280, 256) x 128 threads = 327680 blocks |
| measured | **1.03 TFLOP/s** = 3.4% of FP32 peak |
| traffic | 987 MB/launch, **151 GB/s** = 59% of DRAM peak |
| operational intensity | **6.8 FLOP/byte** against a machine balance of ~117 |

**The 2431.8 ms figure the task started from is stale.** The kernel is unchanged;
the `dense_wide256` layer-scope promotion moved the composition around it. Current
is 2507.0 ms.

## Two measurement traps cleared first

- `Grid_Size_X/Y` in a rocprofv3 CSV are **total work-items**, not grid
  dimensions. `163840 = 1280 x 128` and `256 = 256 x 1`. Read as grid dims this
  gives 4.2e7 blocks instead of 327680. This is the same trap that produced the
  QSA "768 heads" anomaly.
- `--repetitions 1` still traces **two** prefill passes, so the raw count is 768
  launches, not 384.

## The re-read mechanism

`row_base = blockIdx.y * ROW_BATCH` and `blockIdx.y` spans `rows/ROW_BATCH` = 256,
so every row-batch sweeps all 1280 hidden tiles and the reuse distance is the full
3.48 MB weight tensor - DRAM, not cache.

**The access pattern is not the problem.** `q8_0_weight_wave_scale`
(`gguf_k_gemv.hip:105`) uses `__builtin_amdgcn_readfirstlane` for the block index,
so all 32 lanes read one 34-byte q8_0 block with the scale broadcast and the quant
bytes lane-indexed. It is coalesced. The problem is how often it happens.

## A traffic-basis correction to the recorded GR-up numbers

`docs/REFACTOR.md` recorded the fused kernel's weight traffic as **3.565 GB and
1.88 FLOP/byte**. That is the **f32-dequantized** size (`10240 x 320 x 4 =
13.11 MB`, x256 = 3.355 GB), not the **packed q8_0** tensor the kernel reads
(`3.48 MB`, x256 = **891 MB**). The real intensity is **7.53 FLOP/byte** - 4x the
recorded figure. The conclusion survives; the magnitude does not.

The wide tile's recorded "13.9 MB, 483 FLOP/byte" has the same conflation: 13.9 MB
is its **f16 LDS staging** size, while its DRAM read is the same 3.48 MB packed
tensor. That also weakens the framing of *why* the wide tile wins - it amortizes
**dequantization work** over 256 rows, not DRAM traffic, since it reads 3.48 MB
either way. `docs/REFACTOR.md` is corrected in place.

## Ranked levers

1. **`ROW_BATCH` 4 -> 8 at `HIDDEN_TILE=2` - bit-exact, ~900 ms estimated.**
   Halves the re-read (891 -> 445 MB/launch), taking intensity from 6.8 to 12.4
   FLOP/byte. The per-output k-order, the 16/8/4/2/1 shuffle tree, and the 4-wave
   LDS sum are all untouched; `ROW_BATCH` only adds independent row accumulators.
   Cost: `acc[8][4][2]` = 64 floats against 32, estimated 66 -> 98 VGPRs, so about
   7 -> 5 blocks/CU. Occupancy loss is why the prize is an upper bound.
2. **Drop the dead `gate` store - bit-exact, ~107 ms.** In the `fused_up` path
   `scratch.gate` is written by the kernel and read by nothing: the epilogue uses
   its local `sigmoid_gate` to build `mixed`, and the follow-up
   `qwen4_exp_sigmoid_f32` is guarded by `not fused_up and not fused_sigmoid_mean`
   (`qwen4_exp_runner.py:3127`) so it is skipped. 41.9 MB/launch, 16.1 GB/prefill.
   Use a template parameter rather than deletion - `gr_wide` and `gr_iu8` **do**
   read it back through their separate epilogue kernels.
3. **`HIDDEN_TILE` 2 -> 4 - bit-exact.** Doubles the FMAs per `x` load and halves
   the block count, but does not change weight traffic, because the re-read factor
   is `rows/ROW_BATCH` and is independent of the hidden tiling. The kernel is at
   3.4% of FP32 peak, so this addresses a non-binding resource.
4. **Fuse the grouped-rmsnorm producer of `normalized`** - 41.9 MB/launch of
   reads. Producer not identified in this pass.
5. **"Recover projection ILP" is not a lever.** At `4 x 4 x 2` there are already
   32 independent FMA chains per thread. ILP is not the limiter; traffic is, and
   lever 1 is the traffic lever.

## The RB8/HT1 0.80x result does not test lever 1

`docs/REFACTOR.md` recorded the 2026-09-06 `RB8/HT1` retile as halving the re-read
and measuring 0.80x, "does not fit a pure-bandwidth story and is open". It changed
**two** things at once: `HT1` halves the FMAs per `x` load and doubles the block
count. It is a confounded experiment, not evidence about row batching.

**Only a `rowbatch4` kernel exists in-tree** (`gguf_k_gemv.hip:952`). No clean
RB8/HT2 variant has ever been built here, so lever 1 is genuinely untested rather
than previously rejected.

## What this pass did not measure

The projection/epilogue split. The epilogue runs on 8 of 128 threads and, from
source, is about 13% of that warp's critical path while three warps idle - but it
is an **instruction-count estimate, not a counter reading**, and no trace column
separates it. The `gate` stores are also scattered (4 branches at 10 KB stride, 4
rows at 40 KB), so they may carry write-coalescing amplification; whether the
neighbouring blocks' partial lines merge depends on their co-residency, which this
pass does not establish. Splitting projection from epilogue needs a variant
microbenchmark at the same geometry.
