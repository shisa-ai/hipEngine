# Size the Gemma4 prefill block to the card so generate() works on the XTX

## Summary

`hipengine.LLM.generate()` was failing at HEAD on the 24 GB RX 7900 XTX
with `HipError: HIP error 2: out of memory` partway through decode. The
cause was `3871b31c7`, which raised `DEFAULT_PREFILL_BLOCK` from 512 to
1024 after six paired measurements on the 48 GB Radeon Pro W7900 — the
card the commit's own arithmetic was written against ("resident context
goes from 22.14 GB to 25.43 GB … still inside the 48 GB"). The XTX has
24 GB, and the run measured 25,690,779,648 of 25,753,026,560 bytes used,
99.76%, 62 MB free.

Two things let it through. The block was validated only through
`run_instrumented`, a benchmark harness, never through the path a user
reaches; and the scratch that scales with the block is taken lazily on
the first forward, so an oversized block does not fail at load, where it
would be obvious, but during decode. The census I was running to
refresh the loop's `attn.sliding` metric is what surfaced it: it sat for
30 minutes at GPU use 100% with memory bandwidth 0% and thread `wchan`
`kfd_wait_on_events`, which is an allocator stalling against a full card
rather than a deadlock.

The fix is automatic selection between two working block sizes rather
than a flag or a blanket revert. `hipMemGetInfo` free memory, taken
after the weights are already resident, is compared against an upper
bound on what the runner would hold, and the block steps down only when
the card genuinely cannot take it.

## Changes

- `hipengine/runtime/gemma4.py`: added `_resident_bytes()`, which sums
  the runner's own buffers, the per-layer KV cache, and every scratch
  buffer a block of N rows can take; `_fit_prefill_block()`, which steps
  the block down by halves until that sum fits `mem_get_info()` free
  memory minus a 512 MB `_FIT_RESERVE_BYTES`; and a call in
  `Gemma4Runner.__post_init__` guarded by a new `auto_block` flag, so
  only a block the runner chose itself may be shrunk and one passed in
  by a caller reaches the allocator untouched. A runtime that will not
  answer the memory query returns the block unchanged — a missing
  measurement is not a reason to refuse to run.
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_layer.py`,
  `gemma4_experts.py`, `gemma4_router.py`: each `_size_of()` built its
  own `sizes` dict and looked one name up. Split into a single
  `_sizes()` table shared by `_size_of()` and a new `resident_bytes()`,
  so the allocator and the memory planner read the same source and
  cannot drift. `Gemma4LayerScratch.resident_bytes()` also includes its
  expert and router sub-scratches.
- `tests/test_unit_gemma4_prefill_block_fit.py`: 5 CPU-only tests — the
  premise that the resident set grows with the block, the larger block
  kept when it fits, the step-down when it does not, a runtime that
  cannot answer leaving the block alone, and the selector never raising
  a block.
- `docs/campaigns/GEMMA4-26B-A4B-PUNCHLIST.md`: P13's status was
  `landed (default 1024, caveats in source)` with an empty Result
  column, which hid the regression; it now records the failure, the
  fix, and both cards' outcomes.

## Validation

- **The user path, on both cards, not a harness.** With only
  `DEFAULT_PREFILL_BLOCK` patched at runtime to 512 before the fix, the
  XTX returned `GENERATE_OK_512` in 5.5 s against the unpatched HEAD's
  `HipError: out of memory`. After the fix, the same call unpatched
  reports `max_block selected = 512` and returns in 6.0 s; the W7900
  reports `max_block selected = 1024` and returns in 6.1 s, so the
  measured +9.5% prefill is kept where it fits.
- `tests/test_unit_gemma4_prefill_block_fit.py` — 5 passed.
- The gemma4 unit tier reaches `[100%]` with exit 1 and exactly the six
  failures that predate this unit, all `nan` from the confirmed fp16
  staging overflow (`gguf_q8_0_prefill.hip`): `sliding-window run
  diverged: max abs diff nan against scale 2277`, `cap not applied`,
  `reset left stale state: max abs diff nan`, `assert nan > 0`. A grep
  for `resident_bytes`, `_sizes`, `_fit_prefill`, `AttributeError` and
  `TypeError` across the output returns nothing, so the refactor
  introduced no new failure.
- `python3 scripts/docs/check_all.py` — only the pre-existing published
  command drift fails. `python3 audit/audit.py check` passes.
