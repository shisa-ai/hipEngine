# the resident logit design caps prefill at 15872 keys and the full layers have no window

## Summary

Verifying the previous entry's arithmetic by bisection turned up a **capability
ceiling**, not just a performance one.

`gemma4_attention_shared_bytes` accepts at most:

| geometry | largest accepted `keys` |
|---|---|
| `head_dim=256` | **15,872** |
| `head_dim=512` | **15,616** |

Above that it raises `NotImplementedError`. The previous entry said "~16000"; these
are the exact values, and they are the boundary where `(head_dim + keys + 256) * 4`
first exceeds 65,536.

## Why this matters

`gemma4_attention_prefill_kernel`'s `keys` argument is the **live context** for a
windowless layer. The artifact's 30 layers split 25 sliding with `window=1024` and
**5 full with `window=0`** (`20260928T065251`'s own case list). For those five,
`keys` is the whole context, so:

**A prefill above 15,616 tokens cannot run its full-attention layers at all.**

The sliding layers are safe -- their window bounds `keys` -- so this is specifically
the five windowless layers. It is the same resident-logit design that
`20260928T065753` identified as the latency chain: the kernel holds one logit per
live key, so the key count is capped by LDS, and a windowless layer's key count is
the context.

## What is correct here, and what is not

**The failure is loud, which is right.** It raises a named `NotImplementedError`
naming the geometry and the byte count, rather than silently downgrading or
truncating the context. That is what this repository requires of a capability miss.

**What is not established:** whether the prefill route chunks long prompts before
reaching this, which would make the ceiling unreachable in production. I did not
check the route. If it chunks, this is a latent limit; if it does not, it is a live
one. That check is the next step and it is one grep, not a benchmark.
