# Attribute the PP8192 gap from the engine comparison

## Summary

Kernel-trace attribution of hipEngine's PP8192 deficit versus nasone32
(777.235 vs 943.141 tok/s in the 2026-09-08 RX 7900 XTX comparison,
same model/protocol). A cache-only `rocprofv3 --kernel-trace` of the
comparison's own driver
(`scripts/qwen35_gguf_bench.py --prompt-length 8192 --decode-tokens 8
--persistent-session --force-bulk-prefill`, GPU1, one warmup + one
measured run) shows the timed prefill work is projection-dominated:

| Prefill component (per session, approx) | kernel time | share |
| --- | ---: | ---: |
| Q4_T16 WMMA projection prefill (dual+SiLU pair + shared-B rowtile) | ~6.25 s | ~63% |
| attention prefill (`attn_fwd`) | ~1.2 s | ~12% |
| GDN recurrence prefill (`...segments_wave32_xor` + rmsnorm/gate + prepare + conv) | ~0.8 s | ~8% |
| norms/elementwise/misc | remainder | ~17% |

(Session T16/qmicro materialization kernels - `q6_k_t16_qmicro_planar`
56.9 s and `qk_t16_selected_direct` 26.0 s over two sessions - run
outside the timed prefill window and do not affect the tok/s.)

Conclusion: the PP8192 gap is a **projection prefill** problem, not a
GDN problem. Even a hypothetically 2x faster chunked GDN would recover
only ~4% of the 18% gap. This deprioritizes the nasone32 chunked-GDN
donor (4169fbbf5) for this objective and points at the arithmetic class
nasone32 uses for bulk prefill: Q8_1-activation integer MMQ with the
same efa4e8641-family load-reuse boosts - versus our float T16 WMMA
owners. The gfx1151 tree already carries a qualified integer MMQ
prefill composite (`gguf_q4_k_q8_1_selected_prefill`, planar-Q6 K17408
down / K5120 narrow-V, rows 17-48); extending a Q8_1-activation integer
MMQ route to the gfx1100 bulk prefill shapes is the concrete candidate,
with the full production-profile gate plus strict fallback required.

Model census for context: Qwen3.8-27B Q4_K_M has 48 fused-qkv GDN
layers and 17 separate-q attention layers, so GDN prefill being only
~8% of prefill compute is a property of our recurrent prefill kernels
already parallelizing the scan well, not of a small GDN share.
