# Establish rank-local MLP materialization and the shard dispatch identity

## Summary

The first bullet of the MLP TP2 packet is done: rank-local materialization exists
for a representative MLP with its real quant types, the local bytes round-trip
bit-exactly, the local shapes are admissible for the resident layouts, and - the
finding that matters most for cost - **a shard-shaped MLP weight resolves to the
same registered kernel as the TP1 shape**. No shard-specific MLP kernel is
missing. The shard MLP needs exactly **one 20,480-byte reduction per layer**, the
payload the transport screen already measured.

## Changes

New probe `scripts/tp2_mlp_shard_plan_probe.py` (artifact
`benchmarks/results/2026-09-15-w7900-tp2-mlp-shard-plan-probe.json`) answers four
questions with evidence instead of assumption, on `blk.0` of
Qwen3.8-27B-Q4_K_M at world size 2:

| Tensor | Source | Kind | Local shape/rank | Layout | t16 admissible | Dispatch = TP1 |
| --- | --- | --- | --- | --- | --- | --- |
| `ffn_gate` | Q4_K (17408, 5120) | column, axis 0 | (8704, 5120), 25.1 MB | `gguf_q4_k_t16_v1` | yes (8704 % 16 = 0) | yes |
| `ffn_up` | Q4_K (17408, 5120) | column, axis 0 | (8704, 5120), 25.1 MB | `gguf_q4_k_t16_v1` | yes | yes |
| `ffn_down` | Q6_K (5120, 17408) | row, axis 1 | (5120, 8704), 36.6 MB | `raw_gguf` / `gguf_q6_k` | yes | yes |

TP1 MLP weights 173.4 MB, shard 86.7 MB per rank, ratio exactly 0.5. The round
trip (`reconstruct_tensor` over the rank payloads vs the source payload) is
byte-identical for all three tensors.

**Why the dispatch identity is the important result.** `resolve_gguf_linear_dispatch`
keys on `(layout, activation, output, quant_key, variant_for_rows)`. The weight's
own row count is a launch parameter, not a dispatch key, so the column-split Q4_K
gate/up resolves to `dense_single_local32_bf16_bf16_out` and the row-split Q6_K
down to `gemv_bf16_bf16_out`, identically at both shapes. The probe asserts this
equality rather than assuming it, so a future change that made dispatch
shape-keyed would fail the test instead of silently breaking the shard path.

**Why the reduction count is one per layer.** The down projection is row-parallel:
each rank holds a partial output over the *full* hidden size (5120), so the two
partials are summed once per layer. That is 20,480 bytes at fp32 - the exact
payload the native staged-exchange screen measured at 20.45 us, so the transport
term for the MLP shard is already measured rather than extrapolated.

## Next

The segment walls themselves are still unmeasured, which is the rest of the
packet: complete TP1 and local-shard MLP segment times on both cards
(normalization, gate/up, activation, down projection, output dtype and residual
boundary), the shard outputs connected through the native exchange into the next
consumer with enqueue skew included, validated against the CPU split oracle and
the TP1 teacher under the production numerical contract, then repeated across the
distinct MLP geometries and quant combinations. The decision rule stays
`segment saving = matched TP1 segment wall - measured TP2 segment wall`, and an
MLP-only variant must still carry full replicated attention/GDN execution.

One structural note for that work: the 17 full-attention blocks and 48 linear
(GDN) blocks differ in what a shard would have to replicate, so the MLP-only
versus full-TP choice has to be evaluated per block class, not per model.
