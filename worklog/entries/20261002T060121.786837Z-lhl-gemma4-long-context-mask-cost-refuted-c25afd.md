# the 256K keep-mask is 0.6 percent of the prefill, and deriving it costs more than it saves

## Summary

The previous unit made a 262,144-position context runnable. This one was meant to
make it cheap, by removing the dense `(rows, keys)` uint8 keep-mask the runtime
builds per layer geometry per prefill block. **It does not remove a real cost,
and the change was measured, found to be a regression, and reverted.**

**The mask is 0.6 percent of the run, not the tens of minutes it looked like.**
At 256K the deepest full-layer block's mask is `(512, 262144)` = 134.2 MB, and
over the whole prefill both geometries together materialise **34.8 GB** of mask.
Built on this host that takes **6.4 s**, measured directly, which is 0.6 percent
of the 998.1 s baseline. The arithmetic that made it look expensive — 133 MB per
block, 342 GB across a prefill — was right and the conclusion drawn from it was
wrong: numpy writes that mask at 5.47 GB/s and the upload overlaps with compute,
so 34.8 GB is seconds, not minutes.

**Deriving the mask costs more than reading it.** `_keep_mask` builds exactly
`key_position <= row_position` ANDed, only when a window exists, with
`row_position - key_position < window`, and every kernel that reads it already
has `row_offset`, `window` and its own column index, so a null mask can mean
"compute it instead". Implemented in both WMMA prefill kernels and wired through
a `derives_mask` capability on the prefill selection, it is **correct and
bit-identical** — 12 parity cases run each kernel twice on identical buffers and
compare raw bits, and a full 262,140-token prefill reproduces the baseline's
generated ids exactly. It is also **slower**: a same-buffer A/B on the deepest
block at 65,536 keys measures **+4.5 percent**, falling to **+2.0 percent** once
the comparison is done in 32 bits instead of 64.

That 32-bit result is the one that identifies the cause. A 64-bit compare is
three scalar instructions on this ISA where a 32-bit compare is one, and this
codebase already keeps `first_kept` and `walk_end` in 32 bits for exactly that
reason; using `int64_t` in a loop that runs once per key per row was a defect in
the implementation rather than a property of deriving. Fixing it halved the
regression, and the remaining 2 percent is the branch between the two paths
inside the unrolled key loop. Closing that would need the loop specialized on
`derive_mask`, which is real kernel complexity and a second parity surface, and
its ceiling is the 6.4 s it saves.

**So the net is negative and the change is not landed.** The walk is ~75 percent
of a 256K prefill and the mask is 0.6 percent, so +2 percent on the walk costs
about 15 s against the 6.4 s saved. The measured end-to-end pair agrees on
direction, though not on size: 1182.7 s against 998.1 s. That pair is one sample
per arm with an 18 percent spread in construction time between them, so the
micro-benchmark is what the decision rests on, not the pair.

**What this redirects to.** With the mask excluded, a 262,140-token prefill is
approximately 240 s of non-attention work, 6.4 s of mask, and **~750 s of
attention walk** — 5 full layers whose per-block key walk grows with the block's
own position. That walk's arithmetic is 5.6 PFLOP, so it is running at about
**7.5 TFLOP/s**, and that number, not the mask, is what a long-context unit
should be aimed at.

## Validation

The decision is a negative result, so what matters is that the measurement is
sound and that the reverted path was genuinely correct before it was dropped.

**The mask cost, measured directly** (`_keep_mask` on the real geometries, host
timing, no GPU):

| shape | mask | time | rate |
| --- | ---: | ---: | ---: |
| full layer, deepest 512-row block | 134.2 MB | 25 ms | 5.47 GB/s |
| full layer, first 512-row block | 0.3 MB | 0 ms | 2.43 GB/s |
| sliding layer, deepest block | 0.8 MB | 1 ms | 0.53 GB/s |
| **whole 262,144 prefill, both geometries** | **34.8 GB** | **6.4 s** | — |

The sliding layer's mask is 0.8 MB rather than 134 MB because
`_sliding_read_range` trims the band to `window + rows - 1` columns, so only the
5 full layers pay, and 6.4 s is 0.6 percent of the 998.1 s baseline.

**The kernel A/B** (`/tmp/ab_mask_kernel.py`; same device buffers, same
arguments, both arms alternated within one process so drift shows in both,
`gemma4_attention_prefill_wmma_full_bf16`, `tokens=512`, `window=keys`):

| keys | row_offset | reps | explicit mask | derived | ratio |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 65,536 | 65,024 | 5 | 152.93 ms | 164.03 ms | **1.073x** |
| 65,536 | 65,024 | 15 | 154.77 ms | 162.38 ms | **1.049x** |
| 131,072 | 130,560 | 7 | 314.93 ms | 329.01 ms | **1.045x** |
| 65,536 | 65,024 | 15 | 150.55 ms | 153.58 ms | **1.020x** |

The last row is the same measurement after the derived comparison was narrowed
from `int64_t` to `int`. The ranges separate cleanly at 15 reps (explicit
143.0-152.0, derived 146.2-156.0) and the effect reproduces at twice the key
count, so the 2 percent is real rather than drift.

**Correctness of the reverted path**, recorded because it bounds what a future
attempt would have to re-establish: 12 new cases across the two WMMA test files
run each kernel twice on identical buffers — once with the caller's mask, once
with null — and assert `explicit.view(uint32) == derived.view(uint32)`, i.e.
bit-identical rather than within tolerance. All pass, alongside all 44
pre-existing parity tests in those files. The end-to-end run with the change
generated exactly the baseline's ids, `[237032, 239185, 236945, 239691]`.

**End to end**, same command both arms (`capacity = 262144`, 262,140-token
prompt, 4 generated):

| arm | wall | prompt tok/s | generated ids |
| --- | ---: | ---: | --- |
| baseline (reads the mask) | **998.1 s** | 262.6 | `[237032, 239185, 236945, 239691]` |
| derived mask | 1182.7 s | 221.6 | `[237032, 239185, 236945, 239691]` |

Both produced coherent text (`'と秋の紅'`). The 18.5 percent gap is larger than
the micro-benchmark predicts and is not explained; it is reported as measured and
not used as the basis for the decision.

The unit tier passes except for two pre-existing `vibevoice_tts_diffusion`
failures that the change cannot reach: that file imports only numpy and
`cpu_reference`, and the assertion reports `eps 0.3655 of peak`, the exact value
its own comment attributes to the drifted environment.

## Next

- **The attention walk, not the mask.** ~750 s of a 998 s 256K prefill is the 5
  full layers' key walk at ~7.5 TFLOP/s. A unit aimed at long context should
  start there, and should start by asking why that rate is what it is.
- **The end-to-end discrepancy is open.** The micro-benchmark says +2 percent on
  the walk; the single A/B pair says +18.5 percent on the run. One of them is
  missing a term, and a two-sample-per-arm repeat would settle it.
- **Revisit only if the mask grows.** The 6.4 s figure is for this geometry and
  this host. It is quadratic in context and linear in block count, so it is worth
  re-measuring before any future attempt to remove it, rather than assuming
  either this number or the 342 GB projection.
