# The repair-free gate/up configuration is measured closed — the repair is load-bearing on the prefill path

## Summary

The ledger's `MX-1` is the largest remaining lever: the routed-expert repair is
**1,219.978 ms = 7.75%** of the 15,741.963 ms prefill union, and its prescribed route was
a from-scratch F16 kernel port. Reconnaissance found the repair's own documentation
calling it a **bit-parity** mechanism, with the multiplier's docstring adding that under
the production contract a rare escape is *"bounded drift, **not a contract violation**"*.

If that reading held, the prize was available as a **configuration**: select the plain
iu8 owner, which publishes identical arithmetic without the risk criterion or the repair
pass. The gate says **no**.

**Result: `hard_gates_passed: false`, `decision.next: "reject candidate and keep strict
fallback"`.** Every aggregate gate passes; the failure is **per-scope**, concentrated on
exactly the rows the repair operated on.

## What this establishes

**The repair is not decorative.** Its docstring's claim holds **per element** at a 0.71%
incidence (`EG-3`), but across 48 layers the accumulated drift lands on the prefill path
and exceeds the calibrated per-scope envelope. The `prefill_last` rows are precisely the
ones the prefill route produces, and they run at **5x** the `steady` rows' mean KL.

**So `MX-1`'s premise is correct after all: removing the repair requires changing the
arithmetic.** Dropping it while keeping iu8 does not pass. The F16 port is the route, and
it now has a measured justification rather than an inferred one.

**A planned follow-on is ruled out, which is the main cost avoided here.** The next step
was a plain-iu8 sibling of `q5_1_selected_wmma_iu8_risk_prefill_kernel` for the down leg
(661.210 ms). That was conditional on the gate/up half passing; the same prefill-path
drift would be expected, and **it is not to be built on this evidence.** Gating the cheap
configuration before writing any kernel is what bought this.

## Configuration

`EXACT_GROUPED_Q4=0` (clears `exact_grouped_q4_gate`, which dispatch tests *before* the
`q4_iu8` branch) + `Q4_IU8_PREFILL=1` + `Q4_IU8_LAYERS=all` (production binds 35-47; the
repair route has no layer restriction). **Q5_1 down left at production deliberately** — it
has no plain non-risk iu8 sibling, so changing it would swap the fast iu8 route for the
slower bit-exact owner and confound the measurement. This isolates the gate/up half:
573.211 ms of the repair.

## Validation

`measurement_valid: true`, **360 candidate dispatches** at the real gate/up shapes
(`[390..500, 2560, 640, 640]`), repair kernels absent.

The first run of this candidate reported `candidate_dispatch_calls: 0` — an **instrument
artifact**, fixed in `8ec9e3bc3`: the gate's counter replaces the **registry** entry while
the runner calls the plain iu8 owner as a **direct module attribute**
(`qwen4_exp_runner.py:4397`). Same defect class as `84290f3dd`.

**Provenance:** the re-run's quality summary is **identical to every printed digit** of
the first run (mean 5.278e-4, p95 2.806e-3, p99 5.267e-3, max 2.469e-2, top-1 0.99556).
That is both the determinism evidence and confirmation that the first run *was* this
candidate — the counter, not the route, was broken.
