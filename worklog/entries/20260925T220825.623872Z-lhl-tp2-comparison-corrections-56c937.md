# Two claims in the matched comparison are wrong and withdrawn

## Summary

The 2026-09-25 comparison entry
(`20260925T171125.365538Z-lhl-tp2-tp1-llamacpp-three-way-83951a.md`) and the
artifacts and rollup text committed with it carried two statements that do not
survive checking. Both are withdrawn here, and both corrections are made in the
files rather than only in prose.

**1. The Q6_K dispatch defect is not the current bulk-prefill blocker; it is
recorded as fixed.** The entry described bulk promotion as blocked by "the
recorded Q6_K `attn_qkv` dispatch divergence". `docs/REFACTOR.md` records
"2026-09-17 TP2 bulk prefill omits the resident dispatch context - fixed":
`resident_prefill_dispatch_session` is entered per rank, and after the fix **all
15 layer-0 producer fields are bit-identical** between the resident TP1 bulk
teacher and the TP2 bulk candidate on identical input, weights and initial state
(`results/2026-09-17-w7900-tp2-bulk-vs-resident-tp1-layer0.json`). The
`attn_qkv` rel 3.73e-03 reading is the pre-fix measurement that localized the
cause, not a live failure.

**2. llama-bench does not project every prompt row.** The entry claimed the
prefill deficit was understated because llama-bench's `pp512` projects the
prompt's output rows where this route uses `logits_rows=1`. That is wrong, and
the source says so at the build that was measured (15995a1):

- `tools/llama-bench/llama-bench.cpp:2222` - the prompt test calls
  `llama_decode(ctx, llama_batch_get_one(tokens.data(), n_tokens))`.
- `llama_batch_get_one` leaves `batch.logits` null, and llama-bench never sets
  `logits_all` or `set_embeddings` anywhere in that file.
- `src/llama-batch.cpp:120-128` - with `output_all` false, it marks **only the
  last token's** output.

So both engines request the same output projection work at this shape and the
deficit needs no adjustment. No measured number changes; only the reading of the
comparison does.

## Validation

The two corrections rest on repository records and on llama.cpp source at the
measured build, both cited above. This entry does not change any measurement.

What is still true and is the actual state of bulk prefill:

- The promotion bar for this route is the **arm-vs-control** production
  comparison, and the then-current candidate **passed** it on 2026-09-18: 831
  rows, mean KL 2.895e-04, p99 3.452e-03, max KL 4.2273e-02, top-1 99.64%, 3
  flipped rows, 3-sweep determinism, controls byte-identical
  (`results/2026-09-18-w7900-tp2-bulk-prefill-gate-prompt-sized.json`).
- The committed token-serial route passes the same gate with a better tail (max
  KL 1.2125e-02, top-1 100%, 0 flips), so the candidate was a pass with a thinner
  margin.
- The **teacher-relative / cross-route** reading still shows a gap. It describes
  the remaining bit-exactness difference and is a diagnostic, not the bar.
- The 2026-09-18 pass predates two arithmetic changes: the device-side MLP
  reduction and the head-sharded attention default. It therefore does not
  validate the configuration that would ship today, which is why the gate is
  being re-run on the current revision rather than cited.
- Bulk stays opt-in until that re-run passes, and the workspace contract
  (no chunked prefill, so an over-capacity prompt is rejected rather than
  handled) is a separate limitation to resolve.
