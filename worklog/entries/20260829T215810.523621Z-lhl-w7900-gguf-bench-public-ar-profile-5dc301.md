# GGUF bench gains --public-ar-profile so short-prompt prefill rates are shipping-route rates

## Summary

`scripts/qwen35_gguf_bench.py` left `use_wmma_prefill`/`use_gemv_decode` unset
by default, so they resolved through `HIPENGINE_GGUF_WMMA_PREFILL` /
`HIPENGINE_GGUF_GEMV_DECODE` to `False`, while the shipping GGUF AR session
passes both as `True` (`hipengine/generation/qwen35_gguf.py:1107`, 1180, 2068,
2490, 2655). Every default-route prefill number from that harness therefore
measured a route the product does not run, worst at short prompts: measured
159.7 tok/s on the shipping route against 99.0 tok/s on the harness default
route at 45 tokens (+61.7% measured again in this unit, +62.4% in the prior
unit), and only +1.7% at 512 tokens.

Added `--public-ar-profile` plus two recorded protocol fields so the mismatch
cannot be silently re-read as an engine rate:

- `apply_public_ar_profile()` sets both shipping selectors and raises on an
  explicit `--no-use-wmma-prefill` / `--no-use-gemv-decode` conflict, so a run
  can never claim the shipping profile while measuring something narrower.
- Protocol records `public_ar_profile`, `public_ar_profile_applied`, and
  `shipping_ar_route_mismatch` (True only when a *measured* run resolved
  `effective_use_wmma_prefill=False` without the profile; a backend that has no
  WMMA route at all resolves `None` and is not flagged), and the same condition
  prints one stderr warning naming the measured delta.
- The generated-token identity is unchanged by the profile (id 9707 both ways)
  but the final logit moves 22.1395 -> 21.9644, so this stays a
  production-profile arithmetic difference, not exact parity. No product code
  changed, so no correctness gate applies.

## Changes

- `scripts/qwen35_gguf_bench.py`: new `--public-ar-profile`
  (BooleanOptionalAction), `PUBLIC_AR_PROFILE_KWARGS`,
  `apply_public_ar_profile()`, `shipping_ar_route_mismatch()`, the three
  protocol fields, one note line, and the stderr warning.
- `tests/test_qwen35_gguf_bench_public_ar_profile.py`: CPU-only, no HIP guard
  needed. Covers opt-in defaults, conflict rejection, the `None`-resolution
  carve-out, and asserts the alias still matches the product path by grepping
  `hipengine/generation/qwen35_gguf.py` for `use_wmma_prefill=True` /
  `use_gemv_decode=True`, so the alias fails loudly if the product ever stops
  passing them.
- `docs/REFACTOR.md`: new ledger row giving the removal trigger (collapse the
  alias once the bench resolves defaults through the same session-profile helper
  the product uses, or once retained short-prompt artifacts are re-measured and
  the low-level selectors leave the bench surface).

## Validation

- `pytest tests/test_qwen35_gguf_bench_public_ar_profile.py
  tests/test_qwen35_gguf_bench_metadata.py -q` -> 12 passed (4 new, 8 existing
  bench metadata tests, no GPU).
- W7900 (gfx1100), exclusive device, `Qwen3.8-27B-Q4_K_M`, production profile,
  `--prompt-length 45 --decode-tokens 1 --persistent-session`:
  `--public-ar-profile` -> prefill median 0.2811 s (160.1 tok/s),
  `public_ar_profile=true`, `applied=true`, `shipping_ar_route_mismatch=false`,
  `effective_use_wmma_prefill_all=[true,true,true]`.
- Same command without the flag -> 0.4546 s (99.0 tok/s),
  `shipping_ar_route_mismatch=true`, and the warning line appears once on
  stderr. Both medians reproduce the prior unit's independent measurements
  (0.2818 s / 0.4577 s), so the flag resolves the same route as
  `--use-wmma-prefill` did manually.
