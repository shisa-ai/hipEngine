# Gemma 4 P8: the prescale fold does not pay, and the bug that hid it

## Summary

P8's second open item — fold `gemma4_router_prescale` into the router logits
launch — was built, gated, measured, and **rejected**. The measurement that
made it look worth doing was right: prescale is 0.0198 ms of the 0.0913 ms
pair, 22%, or **4.6 ms of a 4096-token prefill**, which is exactly the gap
between the shipped 20.5 ms and the ~16 ms llama.cpp implies. The fusion
simply does not capture it. The fused kernel loses to the two-kernel pair at
every width — best case **0.1223 ms against 0.0913, i.e. 0.75x, 34% slower** —
because accumulating each row's sumsq and reducing a second shared array costs
the GEMM more than running the separate norm costs. The obvious suspect,
`scale[k+j]` being reloaded from the innermost loop 16 times per vector step,
was hoisted beside `w[8]` and moved the needle only 0.1546 -> 0.1483. The
shipped state is unchanged: two kernels, `token_tile_16` at 128 threads, gate
passed, `moe.router_gemm` 13.4 -> 5.2 ms at 1024 and 53.2 -> 20.5 at 4096.

The larger lesson is in "The bug", below: the fused kernel's very first
correctness run passed every check I thought to apply to it while writing only
**2048 of its 65536 outputs**.

## Measurement

Standalone, rows=512, hidden=2816, 128 experts, 50 warmup passes then 400
timed, GPU 1:

| kernel | ms |
| --- | ---: |
| `gemma4_router_prescale_bf16` | 0.0198 |
| `token_tile_16` threads=128 | 0.0716 |
| **two-kernel pair** | **0.0913** |
| fused, threads=64 | 0.1223 |
| fused, threads=128 | 0.1483 |
| fused, threads=256 | 0.2375 |

Before hoisting `scale` out of the innermost loop the fused kernel read
0.1546 / 0.1483 / 0.2375 at 64 / 128 / 256, so the hoist bought 4% at 128 and
nothing at 64. Prescale's share of the pair is 22.2%, which projects to 4.6 ms
across a 4096-prefill's 240 launches — and the census agrees: `moe.router_gemm`
measured 20.5 ms at 4096 in the run immediately before this one, split 5.2 ms
at 1024 as prescale 1.14 + logits 4.02 and 20.6 ms at 4096 as prescale 4.6 +
logits 16.1.

The regression run `p8d` confirms it end to end: `moe.router_gemm` went 5.2 ->
12.3 ms at 1024 and 20.5 -> 47.6 ms at 4096, prefill fell 2040.9 -> 2016.0 and
1165.0 -> 1157.5, decode 43.80 -> 43.75. The artifacts are kept because a
refuted measurement is worth as much as a won one.

One thing the fused route does have, and it is real: against a float64
reference it lands at **4.0e-08** max abs error where the two-kernel route
lands at **4.06e-04**, because the intermediate bf16 rounding of the
prescaled buffer disappears. Top-1 agrees 512/512 either way. That is four
orders of accuracy bought with 34% of the time, and it is not worth it here —
but the gate recorded it, so the option is documented rather than lost.

## The bug

The first fused-kernel correctness run reported `maxabs=nan` and, when I
re-ran it in isolation, reported agreement with the float64 reference to
**eight significant digits**. Both were true. The kernel was writing
2048 of 65536 outputs; row 0 is one of them, and row 0 matched perfectly.

Three separate checks all passed on a kernel that did 3% of its job:

1. **Spot comparison against a reference** — row 0 and the first eight
   columns were correct, because the only token block that ran was
   `blockIdx.y == 0`.
2. **Top-1 agreement** — computed over whatever happened to be in the buffer.
3. **`np.isfinite`** — returned clean when the output buffer's stale device
   contents happened to be finite, and reported 1048 NaNs when they were not.
   I read that as a scattered race. It was uninitialized memory showing
   through, and the count changed with how many buffers `malloc` had handed
   out.

The root cause was one line. `hipLaunchKernelGGL` takes a grid and a block:

```cpp
hipLaunchKernelGGL(fn, dim3(grid.x, grid.y), dim3(block.x), shared, stream, ...);
```

I had written two `dim3` arguments, `dim3(num_experts)` and
`dim3(ceil(tokens/16))`, reading the second as if it were `grid.y`. It is the
**blockDim**. So the grid was `(128, 1)` with a 32-thread block: every expert
ran, one token block ran, and `threads=128` was silently ignored. The shared
allocation was sized for 128 threads while 32 launched, which is why nothing
faulted.

What caught it was not any of the checks above. It was **pre-filling the
output buffer with a sentinel** (`-12345.0`) and counting elements that still
held it:

```python
copy_host_to_device(lb, host_array_ptr(np.full(T*E, SENT, dtype=np.float32)), runtime=rt)
# ... launch ...
print("sentinel intact:", int((B == SENT).sum()))   # -> 63488
```

63488 of 65536 untouched. The whole diagnosis took one run after that, and
the row/column histogram of what *was* written (`rows 0..15, all 128 cols`)
named the parameter directly.

**The lesson for any new kernel in this repo: a correctness test must assert
full coverage, not just agreement on the elements it happens to inspect.**
Comparing against a reference is necessary and not sufficient — compare the
*shape* of what was written too, or sentinel-fill first. `np.isfinite` over an
uninitialized buffer is not a coverage check.

## Next

P8's only remaining open item is the top-8 fusion: softmax + top-k +
renormalization + per-expert scale in one kernel as llama.cpp's
`topk_moe_cuda` does, worth about 0.22 ms per 1024-token prefill. `moe.router_
gemm` stands at 5.2 ms at 1024 and 20.5 ms at 4096 against the pre-P8 13.4 and
53.2. Two directions are now closed with measurements and should not be
retried without new information: the expert x token retile (iteration 10) and
this prescale fold. Any future kernel work here should start with the sentinel
coverage check.
