# Gemma decode route ABI replaces the signed slice count (R0056)

## Summary

R0056 is implemented. The Gemma 4 decode entry points no longer take a signed
`split_slices`: the route is named, and the flash key-slice count travels in its
own argument. The old integer meant three things by sign -- `1` the single
kernel, above one the dimension partition, below zero the flash request -- so a
caller could not state a route without also inventing a count.

New decode tail: `(workspace, route, flash_slices, live_extent)`, with
`kGemma4DecodeRouteStrict = 0`, `kGemma4DecodeRouteSplit = 1`,
`kGemma4DecodeRouteFlash = 2` in the kernel and `DECODE_ROUTE_{STRICT,SPLIT,
FLASH}` on the host. `flash_slices` is the flash request's key-slice count and
is zero on every other route.

Nothing about the arithmetic, the route defaults, or the capability gates moved:

- The single-kernel oracle is still route 0, including the resident-bound
  owned-scratch class kernel (`selection` 4) and the block fallback.
- The dimension partition is still entered at 1024 keys. `decode_slices` is
  replaced by `DECODE_SPLIT_MIN_KEYS` / `decode_split_engages(keys=...)`, which
  is the whole policy now that the partition grid is the head width's. The
  2026-09-26 narrow-head "4 slices at 1024 keys" rule is retired with it: the
  split launcher never read that count (its grid is `(head_dim + 31) / 32`
  blocks per head) and `gemma4_decode_split_workspace_bytes` ignored it, so the
  rule had no effect on any launch. Its measurement is kept here rather than
  lost with the test docstring that carried it: on the sliding geometry at 1024
  keys, 4 slices measured 192.2 us against 244.4 us for 2 (paired, two passes
  each). The finding still describes that kernel; there is no longer a slice
  count to act on.
- Reachability is unchanged and worth stating plainly: for an admitted flash
  packing (both Gemma 4 geometries) a one-token decode takes flash from that
  same 1024-key threshold, preference or not, exactly as at HEAD. The partition
  therefore serves the shapes flash cannot — GQA ratio 4 at `head_dim` 512, for
  instance — and the multi-token prefill launcher keeps its own strict entry
  (`route=STRICT`, null workspace), which is the bit-identical class kernel. No
  public `LLM.generate()` on the 26B-A4B artifact reaches `selection` 2; the
  partition's arithmetic guard is the GPU parity battery's explicit route
  request.
- Flash still engages at the partition threshold, or from
  `FLASH_DECODE_PREFERRED_MIN_KEYS` (256) under a plan that prefers it, and
  still carries the count `flash_request_slices` fits.
- Fallbacks are preserved exactly. A rejected flash launch falls through to the
  dimension partition on the same workspace when the request carried a servable
  count, and to the strict route otherwise; a request with no servable count
  never reaches the ABI as flash. The host still sizes the workspace as
  `max(split, flash)`, and the whole-step graph capture still reserves the
  launcher's own expression before it starts recording.
- No backend branch, no model/artifact identity, no new flag, no default change.

`gemma4_decode_split_workspace_bytes` lost `head_dim` and `slices`, which never
affected its result; it is `(tokens, num_heads, keys)`.

## Changes

  enum, replaced `split_slices` with `(route, flash_slices)` in the decode
  forward declaration, launcher and both exports, validated the route value,
  kept the flash-rejection fall-through, dropped the unused `slices` parameter
  from `gemma4_decode_split_launch`, and narrowed

The two tracked diagnostic probes are migrated too, because they are raw ABI
callers like the tests: `scratch/flash_scale_probe.py` (single-kernel oracle
`route=DECODE_ROUTE_STRICT`; flash arm `route=DECODE_ROUTE_FLASH,
flash_slices=slices`) and `scratch/gemma4_flash_slice_sweep.py` (the same two
routes, with the swept count as `flash_slices`). Both go through the parity
battery's `_raw_launch`, so the migration is the keyword tail; their diagnostic
semantics are unchanged, including a rejected flash request falling through to
the partition the way a negative count used to. No compatibility shim was
added: the signed encoding is exactly what R0056 removes.
