# TimesFM 3.0 fp32 strict parity: double-accumulating GEMM

## Summary

`tests/test_gpu_timesfm3_gpu_decode.py::test_gpu_decode_fp32_strict_parity[base]`
failed on physical gfx1100 (462/6912 elements, max 3.93e-4 vs the strict
`atol=1e-4` / `<5e-5` gate). The cause is the fp32 strict path's rocBLAS SGEMM
accumulation order, not a kernel logic bug: on gfx1100 rocBLAS picks a solution
whose fp32 accumulation differs from the CPU/torch fp32 oracle, and the
20-layer stack plus the CPM RevIN refinement amplify the ~1e-6-per-GEMM
difference past the gate. Routing the strict path's GEMMs through a new
double-accumulating SGEMM kernel (`timesfm3_sgemm_f64acc`) makes each GEMM
effectively exact, so the device result differs from the fp32 oracle only by
the oracle's own rounding. All three strict fixtures now pass with margin
(base 5.7e-6, edge 1.14e-5, covmask 6.8e-6). No tolerance, fixture, or default
(fp16) production behavior changed.

## Localization

- Fresh replay on GPU1 (gfx1100, W7900) reproduced the failure exactly.
- GPU fp32 vs the NumPy CPU reference (same inputs) = 3.93e-4; CPU reference vs
  the torch oracle = 5.7e-6. So the divergence is device-side.
- Captured device intermediates vs the reference pipeline: tokenizer output
  matched to 7.6e-5 (rel 6e-7); the leading fully-masked patches (batch 1
  target variates) differed by 1616 (expected: the reused 2.5 sequence
  attention uses a uniform fallback where the reference uses SDPA zeros).
  Zeroing those rows fixed the raw logits there but left the final error at
  3.93e-4 — the leading patches are sliced away, so that was a red herring.
- Per-patch raw logits for the live patches differed by 5e-5..2.6e-4 on values
  ~1700 (rel ~1.5e-7, i.e. fp32 floor). Recomputing every GEMM on the host in
  float64 and casting back dropped the final error to 5.72e-6 — identical to
  the reference's own agreement with torch. All of the divergence is SGEMM
  accumulation order.
- Measured single-GEMM accuracy vs float64: rocBLAS SGEMM 1.2e-6 rel on
  gfx1100 vs NumPy `@` 3.1e-7 rel. rocBLAS `gemm_ex` with F32 data + F64
  compute returns `rocblas_status_not_implemented`, so a library route was not
  available.

## Changes

- `hipengine/kernels/hip_gfx1100/timesfm3/timesfm3.hip`: new
  `sgemm_f64acc_kernel` (32x32 tile, 16x16 threads, 2x2 per thread, double
  accumulators, fp32 in/out) and its `timesfm3_sgemm_f64acc` C ABI wrapper.
  Computes row-major `C[M,N] = A[M,K] @ B[N,K]^T`.
- `hipengine/kernels/hip_gfx1100/timesfm3/timesfm3.py`: launcher
  `timesfm3_sgemm_f64acc`.
- `hipengine/runtime/timesfm3_decode.py`: the fp32 branch of `_gemm` now calls
  `timesfm3_sgemm_f64acc`; the fp16 production branch keeps rocBLAS
  `gemm_ex`.
- `tests/test_gpu_timesfm3_gpu_decode.py`: new
  `test_sgemm_f64acc_matches_float64_reference` pinning the double-accumulation
  accuracy and the NT layout (rows=152 also exercises the 32-row M-tail).
- `docs/model-cards/MODEL-TIMESFM3.md`: corrected the fp32 precision-mode
  description (was "rocBLAS SGEMM + FP32 kernels").
