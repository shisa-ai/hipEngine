# the expert gate/up T16 leaf is issue-bound, not DRAM-bound: it already reads below its irreducible bytes

## Summary

The leaf was priced at **65.4 GB/s** by dividing *unique* bytes by wall time and the gap to a
~221 GB/s read roof was read as bandwidth headroom worth ~580 ms. **Measured with the validated
GL2C DRAM read counter, the leaf is not DRAM-bandwidth-bound, and the traffic it does move is
already below the irreducible floor for its own work.**

**The two headline numbers, at a 4096-token prefill, in situ, 232 calls per prefill:**

| | value |
| :--- | ---: |
| DRAM read traffic per leaf call | **277.3 MB** (277.45 / 277.18 on two runs, 0.1% apart) |
| irreducible read bytes for that work | **316.5 MB** (293.4 MB of tiles once + 23.1 MB of activations once) |
| measured / irreducible | **0.88x** |
| leaf kernel time | **1159.30 ms** of a 4353 ms step (26.6%), 4.997 ms/call |
| DRAM read rate | **57.3 GB/s** |
| achievable read rate, same session, same counter | **239.6 GB/s** |

**The denominator check came first, and it is the cheapest possible refutation, so it was done
first. It did not fire.** The prior entry's 328 MB is `293.4 (tiles once) + 23.1 (activations
once) + 11.5 (output once)`, and every term is correct as a unique-bytes count: `compact_rows` is
tokens x top_k = 512 x 8 = 4096, so the activation footprint really is 4096 x 2816 x 2 and the
output really is 4096 x 1408 x 2. It is **not** an 8x rows error. What it is instead is a traffic
*model* error: it treats unique bytes as if they were DRAM traffic. The kernel's demand is 2x the
tiles (a 16-row tile walks every output tile of its expert, and the model has 32 rows per expert)
and 88x the activations (each 32-column block re-reads its rows' full K row once per 16-column
half, across 44 blocks). Measured at that geometry the DRAM reads are **400.4 MB**, so the real
figure is **75.1 GB/s, 1.22x higher** — the correction makes the apparent gap *bigger*, not
smaller. And the 11.5 MB output term was a write counted into a read rate.

**So the premise that the leaf runs far below the roof survives; the premise that the gap is
recoverable bandwidth does not.**

## The pre-registered refutation test, and both halves fired

Stated before measuring: the bandwidth hypothesis is refuted if **either**

- **(R1)** the measured DRAM read rate is at or below half the achievable rate, or
- **(R2)** the measured DRAM read bytes are at or below the irreducible bytes for the work
  (i.e. no reuse is left to capture).

**Both fired.** R1: 57.3 GB/s against 239.6 GB/s is 24 percent. R2: 277.3 MB against 316.5 MB is
0.88x. And both are measured with a counter that sits *above* the MALL, so both are upper bounds —
the true DRAM rate is lower than 57.3 GB/s, which makes the negative verdict conservative rather
than generous.

## What the time is going to instead

**Instruction issue.** Three independent lines agree:

1. **Runtime is proportional to wave count, and indifferent to bytes.** Across a 6x range of
   block counts, `us_per_block` is 0.496 / 0.471 / 0.472 / 0.469 / 0.466 — flat within 3 percent —
   while DRAM bytes per block fall 59.2 -> 24.2 kB, a 2.4x change, with no effect on the time.

   | rows/expert | blocks | DRAM read MB | kB read/block | ms | us/block | GB/s |
   | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
   | 16 | 5632 | 333.5 | 59.2 | 2.793 | 0.496 | 119.4 |
   | 32 | 11264 | 400.4 | 35.6 | 5.304 | 0.471 | 75.5 |
   | 48 | 16896 | 491.6 | 29.1 | 7.969 | 0.472 | 61.7 |
   | 64 | 22528 | 599.9 | 26.6 | 10.568 | 0.469 | 56.8 |
   | 96 | 33792 | 818.9 | 24.2 | 15.743 | 0.466 | 52.0 |

2. **The instruction count is ~150 per WMMA.** Per wave (one 32-thread block, 352 WMMAs):
   45,556 VALU, 7,760 global loads, 1,825 SALU. That is **129.4 VALU and 22.0 scalar global loads
   per 16x16x16 WMMA**. Disassembling the same source gives 137.2 VALU and 22.5 global loads per
   WMMA, so the static and dynamic counts agree to 6 percent. The kernel does its Q4T16 tile
   decode one byte at a time in registers, with **LDS = 0**.

3. **Those instructions consume 79 percent of the machine's issue slots.** 593.2M issued
   instructions against 80 SIMDs x 9,354,023 active cycles = 748.3M slots. Wave occupancy is not
   the constraint and cannot be: mean waves in flight is **1235.3 against a hardware maximum of
   1280** (40 CU x 32 waves/CU), 96.5 percent.

The L2 side says the same thing from a different direction: the leaf issues **26.28M L2 read
requests per launch (3.36 GB at 128 B/request), 8.4x its DRAM request count**, at an 87.4 percent
hit rate. Its L2 request *rate* is 4.955G requests/s against the cold stream's 1.872G, so the leaf
already asks for 2.6x the request rate that a 240 GB/s stream needs. Whether the CU-to-L2 fabric
has a request-rate ceiling above that is not measured; what is measured is that the leaf is not
short of requests. It is short of instructions left over for anything but decoding the tile.

## Headroom

| | |
| :--- | ---: |
| memory floor, irreducible bytes at the measured 239.6 GB/s | **1.321 ms/call** |
| in situ, as measured | **4.997 ms/call** |
| headroom | **3.68 ms/call -> 852.9 ms of the 4353 ms step (19.6%)** |
| at the prior unit's 4260 ms step | 20.0% |
| projected step if captured | 3500 ms, **1170 tok/s** (from 941) |

**This is not bandwidth headroom and it cannot be captured by a byte-level change**, because the
traffic is already below the floor. It is what is left if the instruction-side bottleneck is
removed. A kernel change captures it only by issuing far fewer instructions per byte: stage the
Q4T16 tile (or its decoded fragments) in LDS once per block and consume it with vector reads
instead of ~21 scalar global byte loads per lane per K-iteration, and/or widen the block so one
decode serves more output. The target is ~150 instructions per WMMA down to ~20; at 20 the leaf
would land on the memory floor rather than below it.

## Validation

### The counter was validated before it was trusted

`scripts/gemma4_t16_gate_up_dram_probe.py --mode stream`, a contiguous int4 buffer read exactly
once, under `rocprofv3 --pmc GL2C_EA_RDREQ_DRAM_sum`:

| buffer | expected | measured requests | measured bytes | error |
| ---: | ---: | ---: | ---: | ---: |
| 32 MB | 33,554,432 | 262,145 | 33,554,560 | **+0.0004%** |
| 128 MB | 134,217,728 | 1,048,577 | 134,217,856 | **+0.0001%** |
| 512 MB | 536,870,912 | 4,194,305 | 536,871,040 | **+0.00002%** |

Worst error **0.0004 percent**, i.e. one request in 4.2 million, and that residual is the launch's
own metadata reads. Corroborated by an independent counter block: `GCEA_RDRAM_REQ_PER_CLIGRP_sum`
gives 15,741,141.5 requests on the leaf, which at the established 25.6 B/request is 402.97 MB
against GL2C's 400.40 MB - **0.64 percent agreement between two independent blocks.**

`GL2C_HIT`/`GL2C_MISS` are 128-byte units, calibrated the same way: the 512 MB cold stream reports
`GL2C_MISS_sum = 4,194,305`, exactly buffer/128, with `GL2C_HIT_sum = 3`.

### The MALL caveat was demonstrated, not assumed

`GL2C` sits above the MALL, so every figure here is an **upper bound** on true DRAM reads. The
16 MB MALL-resident case still reports its full 16.78 MB as DRAM requests while running at
**600 GB/s**, above the 256 GB/s DRAM peak. That is the proof that the counter cannot see through
the MALL, and it is why the negative verdict is the conservative direction.

### The achievable rate is same-session and same-counter

239.6 GB/s (512 MB) and 243.4 GB/s (128 MB), against 256 GB/s theoretical and the ~221 GB/s
recorded in `docs/reference/ROOFLINE-gfx1151.md`. The 32 MB point reads at 702 GB/s and is
reported only as the MALL demonstration.

### The standalone fixture reproduces the in-situ kernel

`scripts/gemma4_t16_gate_up_dram_probe.py --mode leaf --rows-per-expert 32` measures 5.006 ms best
against the census's 5.016 ms in situ, and the counter reports `Grid_Size = 360448`, which is the
production 44 x 256 blocks of 32 threads exactly.

### What was not measured

- **True DRAM reads.** The counter is an upper bound; the direction is stated above.
- **Stall reasons.** `rocprofv3` PC sampling is unavailable on gfx1151 ("Given PC sampling
  configuration is not supported on any of the agents"), so "issue-bound" rests on instruction
  counts, issue-slot arithmetic, and the block-count proportionality rather than on a stall sample.
- **`SQ_BUSY_CYCLES` could not be reconciled** with the instruction counts (it implies 25-50
  percent busy against a 79 percent issue-utilization model) and its instance aggregation is not
  documented in the counter list. It was collected and is deliberately not used.
- **The L2 traffic decomposition leaves 28 percent unexplained** (3.36 GB measured against a
  2.62 GB demand model). The measured request count is reported as measured; no claim rests on the
  decomposition.
- **Whether a memory-optimal rewrite actually reaches 240 GB/s on this access pattern.** The roof
  is a fully coalesced cold stream, which is the optimistic case for a kernel reading 2368-byte
  tiles scattered across 293 MB.
- **The write amplification is measured but not diagnosed**: 45.5 MB written for 11.5 MB of output
  (3.9x), because a block writes 32 bytes into each of 16 rows that are 2816 bytes apart.

## Next

- **Do not build a bandwidth-motivated change on this leaf.** The traffic is at the floor; there is
  nothing to save by moving fewer bytes. The lever is instructions per byte.
- **The named unit is a decode-in-LDS rewrite of the leaf**: stage the Q4T16 tile per block in LDS
  and read it vectorized, so the ~21 scalar global loads and ~130 VALU per WMMA collapse toward
  ~20 total. That is the only route to the 852.9 ms.
- **The same diagnosis should be checked on the sibling MMQ32 route and the Q5_K iu8 route before
  assuming it generalizes.** They are different kernels with different decode paths; the shared
  fact is only that they read the same expert tensors.
- **The write amplification (3.9x) is a separate, cheap-looking defect** in the store pattern: a
  block writes 32 contiguous bytes per row into 16 rows. It is 45.5 MB of a 323 MB traffic budget,
  so it is not the lever, but it is free to fix if the store pattern is being touched anyway.
