# Close the c=8 beyond-1024 prefill refusal

## Summary

Task #17 asked for one thing: re-run its original c=8 beyond-1024 HTTP reproducer
against the merged tree and confirm every request either completes or fails with
a typed, honest error. It does. **16 of 16 requests returned HTTP 200 with no
traceback in either arm**, including the 3,474-token prompt that was the last
failing shape. The earlier run of this same load failed 4 of 8 rows with
`NotImplementedError` from the packed paged AR prefill context refusal, plus two
secondary chunk-drift failures that appeared only after a row of the same batch
had been retired; neither recurs now, because no row is retired.

The original command, both arms, one production-profile server, dense 27B
`Q4_K_M`, bf16 KV, 8192-token context, gfx1151:

```text
scripts/sharegpt_mtp_routing_pass.py --cases beyond --max-prompt-len 4096 \
  --max-total-len 8192 --num-prompts 8 --max-concurrency 8 \
  --route-mix <off|on> --output-len 32 --seed 373
```

`off` is the arm the earlier run used (the prefill bound is an AR-route
decision); `on` requests MTP on the same load.

| Arm | Rows | Completed | Failed 5xx | Prompt tokens |
| --- | ---: | ---: | ---: | --- |
| `route-mix off` | 8 | 8 | 0 | 1,066-3,474 |
| `route-mix on` | 8 | 8 | 0 | 1,066-3,474 |

## Validation

- The reproducer above: 16/16 HTTP 200, `traceback_lines=0` in the server log,
  every row reconciled.
- A first attempt capped prompts at 1,965 tokens because the harness's default
  `--max-total-len 2048` filters the loader's rows; it passed 16/16 as well, but
  it did not cover the failing shape. It was re-run with `--max-total-len 8192`
  so the 3,474-token prompt is included, which is the run recorded here. The
  discarded attempt is why this entry states the prompt range explicitly.

## Secondary finding: MTP declines above its qualified window, honestly

The `on` arm completes every row and uses no speculation on any of them, which
is worth recording because it looks like a defect and is not one. Each row
reports `effective_route=speculative_mtp`, `mtp_used=false`,
`activation_reason=target_context_k0`, `plan_reason=no_provider`, and a fully
reconciled autoregressive output split.

That is the documented 1,023-token qualified window
(`HIPENGINE_MTP2_MAX_CONTEXT_TOKENS`, `docs/ENVS.md`): every retained MTP
measurement was taken inside it, and the verifier route the adapter selects above
the 1,024-token transition is not qualified for promotion. Raising the bound is a
qualification experiment, not a performance setting, so this entry records the
observation rather than changing it. The same load also shows the concurrency
side of the qualification: at c=8 with candidate budget 3 the refusal is
`width 3 exceeds static group bound 1`, since the artifact's evidence row
qualifies one realized group row.
