# the expert MMQ kernels are DRAM-bound at 25 percent line efficiency, not latency-bound

## Summary

The decomposition in `20260928T144500` reports both expert MMQ kernels moving their weights at
**49.3 and 49.5 GB/s** -- an agreement to 0.4 percent across two different quantizations and two
different kernels -- and reads it as "19 percent of the 256 GB/s DRAM peak", concluding the
kernels are latency-bound because neither axis is near a ceiling.

**Both halves of that are wrong, and the 0.4 percent agreement is the clue.**

## The weight read is uncoalesced

`q5_1_mmq_ds4_selected_prefill_kernel` maps **one thread to one output column**
(`out_col = blockIdx.x * 128 + threadIdx.x`), and each thread's weight row is addressed as:

```cpp
const uint8_t* weight_row = qweight +
    (expert * out_features + out_col) * (in_features / QK5_1) * Q5_1_BLOCK_BYTES;
```

With `in_features = 704`, `QK5_1 = 32` and `Q5_1_BLOCK_BYTES = 24`, **adjacent threads' weight
rows are 528 bytes apart -- 4.1 cache lines.** A warp's 32 lanes therefore each pull their own
128-byte line to use 32 bytes of it:

```
per warp load: 32 lanes x 32 bytes used = 1024 bytes
               but 32 lines touched     = 4096 bytes
line efficiency: 25.0 percent
```

**Three quarters of every weight fetch is discarded.**

## Counted in lines, both kernels are at the DRAM roofline

`20260928T231000` measured four configurations. Counting useful bytes gives 2.8 to 3.2 TMAC/s
and "19 percent of peak". **Counting the lines the 25 percent efficiency actually moves gives a
different picture entirely:**

| config | ms | passes | GB/s of line traffic |
| --- | ---: | ---: | ---: |
| uniform, 32 rows | 2.687 | 1 | 236.1 |
| poisson, 32 rows | 2.897 | 1 | 219.0 |
| poisson, 64 rows | 5.290 | 2 | 239.8 |
| poisson, 128 rows | 10.201 | 4 | **248.8** |
| | | | **DRAM peak 256** |

(158.6 MB of useful Q5_1 weights across 128 experts, 634.4 MB of DRAM traffic per pass at 25
percent efficiency.)

**86 to 97 percent of the DRAM peak across four configurations that vary the work by 4x.** The
kernel is not latency-bound. It is saturated, and it is saturated on traffic it does not need to
move.

## This explains every open question at once

- **The 0.4 percent agreement between two different quants and two different kernels.** Both are
  column-per-thread GEMVs with a strided weight row, so both land on the same useful-byte
  ceiling. It is not a shared mystery; it is a shared layout defect.
- **Why the 4x weight-traffic sweep in `20260928T231000` left the rate flat.** The rate *is* the
  ceiling. Four times the traffic at the same ceiling takes four times as long, which is exactly
  what was measured -- and which I read as "traffic is free" when it meant "traffic is the
  limit".
- **Why occupancy, unrolling, planes and launch bounds all did nothing.** None of them is the
  limit.
- **Why the T16 route measures 1.16x on gate/up.** It coalesces partially -- 16-wide tiles put
  16 lanes on one line instead of one -- and partial coalescing is a partial win.

## And it is the right size for the objective

The gap to llama.cpp is 122.8 ms of the 687.7 ms prefill, and the two expert MMQ kernels are
260.4 ms of it. **llama.cpp's MMQ uses a repacked weight layout that is coalesced by
construction**, which is what its 1.36x is. At our 49 GB/s of useful bytes against a ceiling of
`256 GB/s x 25 percent = 64 GB/s`, a full coalescing fix is worth up to
`64 / 49 = 1.31x` on these two kernels, and llama.cpp's own 1.36x implies it is at roughly 50
percent line efficiency against our 25.

## The wrong conclusion this replaces

`20260928T144500` concluded the kernels were latency-bound and that "the lever is more
independent work in flight per weight byte". **There is no headroom in work in flight: the
memory system is saturated.** The lever is **fewer lines per byte**, and the machinery for it
already exists in the tree -- `repack_gguf_q4_k_tile16` and `repack_gguf_q4_k_x8` put
consecutive output columns' data contiguously.

## Next

- **Coalesce the weight read.** It is worth up to 1.31x on the two kernels that are 260.4 of the
  expert block's 287.7 ms. The layouts exist; the port does not.
- **Measure in place with `gemma4_expert_mmq_wrapper_split.py`.** The microbench reproduces the
  same ceiling, so it cannot show the win.
- **Do not re-test distribution, occupancy, planes, unrolling or K width.** All five are
  eliminated, and this entry says why: none of them is the limit.
- **Correct the record wherever the 49 GB/s figure is quoted as 19 percent of peak.** It is
  77 percent of peak in the units the memory system actually charges for.
