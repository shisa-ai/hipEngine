# the expert block is 84 percent kernel and the prefill is uniform at 5 TFLOP per second

## Summary

The loop's metric is **prefill seconds at 512 tokens**, and the only prefill
attribution this tree had was at 2048, where attention is 38 percent of the step.
The kernel census's own `Next` said to re-run it at 512 first, "so it targets the
metric's own operating point rather than 2048's". This is that run, plus three
probes that close four standing hypotheses. **No kernel changed and the metric
did not move** -- it is 0.865 s (592 tok/s) before and after. What changed is
where the remaining 0.36 s is.

## The operating-point attribution

`scripts/gemma4_prefill_kernel_census.py --prompt 512`, default path, real
artifact, 98.4 percent of the step accounted:

| block | ms | share |
| --- | --- | --- |
| routed experts | 370.1 | **42.3%** |
| dense projections (WMMA) | 281.8 | **32.2%** |
| attention | 174.0 | 19.9% |
| router | 17.1 | 2.0% |
| norms, rotary, residual, gelu | ~18 | 2.0% |
| host and unmeasured | 13.7 | 1.6% |

**At the metric's operating point the two GEMM families are 74.5 percent of the
prefill and attention is 19.9 percent.** The session's attention work has been
aimed at a block that is a fifth of the metric, not the 38 percent the 2048
census reports. The target is llama.cpp's pp512 of 1012.98 tok/s = 0.505 s, so
the gap is 0.360 s.

## The expert block is the kernel, not the wrapper

Two prior entries named the `copy_device_to_host` inside
`gemma4_project_experts_gate_up_mmq` as "worth its own look" and neither looked.
`scripts/gemma4_expert_mmq_wrapper_split.py` times every part of the block in
place with a HIP event pair on the compute stream (the imports are function-local,
so patching the source modules intercepts them):

| part | calls | total ms | ms/call | % of step |
| --- | --- | --- | --- | --- |
| q4k gate_up MMQ kernel | 29 | 154.611 | 5.3314 | 17.84% |
| q5_1 down MMQ kernel | 29 | 155.235 | 5.3529 | 17.92% |
| activation pack (gate_up) | 29 | 9.096 | 0.3136 | 1.05% |
| activation pack (down) | 30 | 2.571 | 0.0857 | 0.30% |
| **device->host readback** | 30 | **1.522** | 0.0507 | **0.18%** |
| tile map (gate_up) | 29 | 0.359 | 0.0124 | 0.04% |

**The readback is 1.5 ms of an 865 ms step.** The hypothesis is closed. The two
MMQ kernels are 309.8 ms of the block's 370.1 ms, so **84 percent of the largest
block is pure kernel time**; the wrapper's whole cost, packs included, is 13.5 ms.

## Both GEMM families run at about 5 TFLOP/s

- **Experts**: 13.94 GB of Q4_K/Q5_1 weights in 309.8 ms is 45 GB/s, and
  1.41 TFLOP in the same time is **4.55 TFLOP/s**. At 512 rows each of 128
  experts is selected, so every expert's matrix is read once and reused across
  its ~32 rows; the byte rate is a consequence of the compute rate, not a bound.
- **Dense**: 1.79 TFLOP in 281.8 ms is **6.35 TFLOP/s**, reading only 1.75 GB, so
  it is compute-bound and 8x less weight-hungry per FLOP than the expert route.

So the 1.71x gap to llama.cpp is **a uniform quantized-GEMM efficiency gap spread
across both families, not one broken route**. That is the single most important
thing this iteration establishes, because it rules out the shape of fix the last
several units were looking for.

## Attention: occupancy is not the explanation

The previous entry's one-command step -- read `VGPR_Count`, `LDS_Block_Size` and
`Scratch_Size` -- was never run. It is now, from the compiler rather than a
profiler (`hipFuncGetAttributes` returns `hipErrorInvalidDeviceFunction` for these
host stubs, so the resource-usage remark is the instrument):

```
gemma4_attention_prefill_kernel<bf16>          VGPRs 36   SGPRs 44   scratch 0
gemma4_attention_prefill_tiled_kernel<bf16,1024,2>  VGPRs 51
gemma4_attention_prefill_tiled_kernel<bf16,1024,1>  VGPRs 48
```

and the launcher's dynamic LDS is exactly `(head_dim + keys + threads) * 4`, which
is **4 KiB at 512 keys**. Registers allow seven blocks per CU and LDS sixteen, so
the wave limit binds: **the strict kernel already runs at full occupancy at the
metric's operating point.** Its ~3 percent issue rate is therefore stall, not
occupancy, and the tiled variant's long-context win is not an occupancy recovery
at 512 tokens because there was none to recover.

Two follow-ups, both negative and both worth recording so they are not retried:

- **A four-key manual unroll of pass 3 is neutral.** 4.90 against 4.66 ms/launch
  on the sliding case, with the `window=0` probe moving the other way by about the
  same amount. Pass 3's per-key global load is not the exposed latency. Reverted;
  the reason is recorded at the loop in `gemma4_attention.hip`.
- **The `--mask zero` ablation does not do what its help text says.** An all-zero
  mask removes pass 1's K traffic and *adds* the same volume of pass 3 V traffic,
  because every logit becomes `-inf`, `row_max` becomes `-inf`, and
  `expf(-inf - -inf)` is NaN, which is not `== 0.0f`, so pass 3's skip never fires.
  It measured 6.65 against 4.66 ms with equal byte counts -- which is why the
  ratio is 1.43 rather than the 2.0 the help text reads as "paying for bytes".

**The open thread on attention is now narrow and concrete: pass 1's
`#pragma unroll 2` does not apply.** The compiler emits "loop not unrolled: the
optimizer was unable to perform the requested transformation" for the strict
kernel, in the unmodified source as well as the modified one, so the two-key
interleave the comment says was written deliberately is not happening. That loop
is the 5-shuffle reduction chain, not a load/FMA, which is the one structure the
neutral pass-3 result does not cover.

## The dense WMMA route is on by default, and it is worth 1.41x

`HIPENGINE_GGUF_WMMA_PREFILL=0` against the default, same 512-token prefill:

| arm | prefill | dense block |
| --- | --- | --- |
| WMMA off | 1.235 s (414.5 tok/s) | 598.80 ms (48.5%) |
| WMMA on (default) | 0.875 s (585.2 tok/s) | 281.82 ms (32.2%) |

**`benchmarks/results/2026-09-28-gemma4-wmma-dense-prefill-short-row-divergence.json`
records this route as `status: reverted, not landed` and says the Gemma 4 path
"never opts into" it. That is stale**: the default arm reproduces the WMMA-on
number, so the route is on. Its recorded short-row divergence (KL 0.6577 and a
top1 flip at 4 rows) is therefore either fixed or now covered by a guard, and
which of those it is was not checked here.

## The dense Q8 MMQ128 route is real but not competitive

`scripts/gemma4_dense_q8_mmq_ab.py` opens `q8_mmq_prefill_session` over a gemma4
policy and A/Bs it against the route that runs without it. Two results, and the
first is a method note:

- **With WMMA on the A/B is vacuous.** `_q8_mmq_prefill_dispatch` only rewrites a
  dispatch whose variant is `prefill_bf16_bf16_out`; with WMMA on the variant is
  `wmma_prefill_bf16_bf16_out`, so the hook never matches and the first run of
  this probe reported 0.996x on a treatment that never applied. The probe now
  counts the variant each hook returns, which is what caught it. **That is the
  fourth time this stretch that a check of the treatment saved a null result, and
  the pattern is the same each time: reading the dispatch code and reasoning as if
  the route had been confirmed.**
- **With WMMA off it is real**: 350 of 410 dense dispatches took
  `mmq128_prefill_q8_1_d4x3_guarded_bf16_bf16_out` (the other 30 are `ffn_down`,
  whose `in_features` 2112 fails the route's own `% 256` constraint), and the
  prefill went **1.2288 to 1.1657 s, 1.054x**.

So the ladder at 512 tokens is: exact tiled 1.2288 s, MMQ128 1.1657 s, **WMMA
0.865 s**. The MMQ route beats the route it replaces by 5.4 percent and loses to
the route already in use by 1.42x. **The dense MMQ lever is closed.**
