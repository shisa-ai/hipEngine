# The two "pre-existing" ASR qualification failures were a broken monkeypatch

## Summary

Two failures in `tests/test_unit_vibevoice_wer_qualification.py` had been carried
through several units as "pre-existing ASR driver tests". They were neither
pre-existing in the sense of unfixable nor caused by the TTS work. The test's
monkeypatch never reached the code under test.

## What the tests actually do

`_run_driver` patches `wer._load_clips` and then calls `driver.main()`. But
`scripts/vibevoice_asr_wer_full.py::_load_wer` builds a **fresh module object on
every call**:

```python
spec = importlib.util.spec_from_file_location("wer", WER_SCRIPT)
module = importlib.util.module_from_spec(spec)
sys.modules["wer"] = module
spec.loader.exec_module(module)
return module
```

So the test patched the instance it loaded, `main()` loaded a second unpatched
instance, and the real LibriSpeech loader ran. That loader's first statement is
`import soundfile`, which is not a declared dependency of this package, so the
test failed with `ModuleNotFoundError: No module named 'soundfile'` at
`scripts/vibevoice_asr_wer.py:147`.

## Establishing it rather than asserting it

- `scripts/vibevoice_asr_wer.py`, `scripts/vibevoice_asr_wer_full.py` and the test
  file are **byte-identical** between `9f62d57a1` (the commit that introduced them)
  and HEAD (`git diff 9f62d57a1..HEAD -- <those three>` is empty).
- In a worktree at `9f62d57a1` the file reported **5 passed**. That is an
  environment artifact, not code: `soundfile` imports successfully inside that
  worktree's `pytest` process, and fails from `uv run python -c "import
  soundfile"` in the same worktree.
- The same worktree at `ab3f1d7c6` (the parent of the introducing commit) has no
  such test file, so there is no earlier revision in which the failure exists.

So the label "pre-existing" was wrong in both directions: the tests never failed
because of this work, and they were not failing for a reason anyone had
established.

## Changes

- `tests/test_unit_vibevoice_wer_qualification.py`: pin the module instance the
  test patches (`monkeypatch.setattr(driver, "_load_wer", lambda: wer)`), with a
  comment naming the reason. The test no longer depends on `soundfile` being
  installed.
- `scripts/vibevoice_asr_wer.py`: the loader now raises `SystemExit` naming the
  missing module and saying it is not a declared dependency, instead of a bare
  `ModuleNotFoundError` from deep inside a harness.

## Validation

- `pytest tests/test_unit_vibevoice_wer_qualification.py` -> 5 passed.
- `pytest tests/ -k vibevoice` -> 115 passed, 4 skipped, 0 failed.

## Not fixed here

`soundfile` (and `scipy`) are genuine undeclared dependencies of the comparative
WER driver's clip loader. The fix above makes the failure legible; declaring an
extra or vendoring a fixture would be the real repair, and it is not needed for
the TTS work this branch is doing.

## Next

Declare the WER driver's clip-loader dependencies (or give it a committed fixture)
so the comparative WER lane can run without an ad-hoc environment. Until then the
driver exits with the actionable message added above.
