# Muse Glimmer AR int8 shared-B WMMA kernel: correct, register-constrained, rejected

## Summary

Wrote a dense int8 shared-B WMMA Q4T16 prefill kernel (cooperative Q4->u8 LDS
decode reused across row tiles + 16x16x16 iu8 WMMA + per-subblock scale/min/
activation-sum application). It is CORRECT (cosine 0.99983 vs bf16 WMMA,
maxerr 0.0052) but SLOWER than the bf16 owner and was reverted. Recorded as a
rejected candidate so the design space is not re-walked blindly.

## Changes

- Experimental kernel + wrapper added then reverted (tree clean at 71ea1bd62).
  Also lifted the Q6 dense integer-MMMQ 64-row wrapper cap to any multiple of
  64 (the kernel grid already tiles rows); correct (cosine 0.99995) but only
  1.06x on Q6 ffn_down at 512 rows, so not promoted.

## Validation

- int8 shared-B Q4 ffn_gate 6656->19968 rows=512: bf16 WMMA 6.2ms (22 TFLOPS);
  int8 kernel best config 11.3ms (12 TFLOPS) -> 0.54x. cosine 0.99983.
- Two bugs found and fixed during bring-up: (1) q4_t16_quant needs the
  tile-local column, not the block-wide column (cosine 0.10 -> 0.90); (2) the
  iu8 B-fragment lane->col map is identity (verified by per-col cross-corr).
- Resource wall: the per-subblock scale application keeps both the i32x8
  integer dot accumulators AND the float8 output accumulators live; with
  OUT_TILES=2/ROW_TILES=2/WAVES=4 the compiler spills ~76-141 KB to local
  memory (LDS limit 64 KB), and even ROW_TILES=1 overflows. Reducing tiles
  kills the weight reuse that motivated the design. An activation ds4 LDS
  cache pushed LDS over the limit.

## Findings

- The bf16 shared_b kernel avoids this by dequantizing Q4->bf16 in LDS (scale
  baked in) and accumulating float directly; it has only the float acc live.
  int8 MMQ cannot bake the per-subblock scale, so it carries double
  accumulators + activation scale/sum reads -> register/LDS pressure that
  offsets the 2x iu8 compute peak on gfx1151.
- Q6 dense integer-MMMQ at large rows reads the weight once per 64-row tile
  (8x for 512 rows), so it does not amortize like the bf16 shared-B owner.

## Next

- The prefill attention (25% of 512 prefill) is a scalar online-softmax GQA
  kernel; a WMMA flash-prefill attention is the next kernel lever (free
  attention alone takes 512 prefill 320 -> ~427, beating llama.cpp's 394,
  though 4K also needs the projection gap closed).
- Decode (+9% gap) is memory-bound GEMV near roofline; norm fusion is ~1-2%.
