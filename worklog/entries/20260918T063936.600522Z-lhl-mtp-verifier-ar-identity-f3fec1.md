# MTP verifier AR-identity regression: the staged chain launched the short-context leaf with an unvouched-for cap

## Summary

The 2026-09-18 MTP exactness regression is fixed, and the matched c=1 serving
lane it had halved is back at **23.46 tok/s against true AR's 11.74 (2.00x)**.
`085bdd86b` is the right
commit, but the cause is not the gate the previous entry named. It is the staged
full-attention verifier chain's **per-row attention leaf** for rows below the
1,024-token split threshold. The chain used to launch the plain span leaf
(`qwen35_paged_full_attn_decode_context_bf16_spans` with the span-wide
`attention_context_limit`, a leaf whose loop is bounded by the row's own live
count). The commit made it reproduce the scalar owner's short-context batch leaf
(`_full_attn_decode_short_batch_fn`), which takes the row's `position + 1` cap as
a **scalar argument** instead of reading a live count. That substitution only
fires where the backend publishes `GGUF_SHORT_C1_BATCH_ATTN_MAX_CONTEXT`
(`hip_gfx1151`: 1023; `hip_gfx1100`: nothing), so the executed kernel changed on
the serving host while every gfx1100 unit test kept passing.

Traced routes on the shipping server (gfx1151, `--max-context-tokens 8192`,
Qwen3.8-27B-`Q4_K_M`, production profile) during the divergent request:

```
session rows=4 start=14 end=18 mode=native views=True limit=1023 scalar_caps=False
layer=3 full rows=4 start=14 limit=1023 views=True strict=False staged_linear=False staged_full=True
  staged-chain layer=3 rows=4 limit=1023 quant=None batch_fn=False shared=False split_rows=False
```

`views=True` with `end=18` cannot come from the eager view builder (its own
`context_limit` gate declines spans below 1,024), so the views are the captured
target graph's and this is the graph route. Inside the chain `batch_fn=False` —
the `bf16_context_batch_shared_native_exact_spans` variant resolves only for the
`gguf_q4_k_m`/`gguf_ud_q3_k_m` quant keys and `_gguf_prefill_quant` is `None` on
this path — and `split_rows=False`, so the **per-row** branch is the executed
one. The cap handed to the batch leaf there comes from
`row_scratch.position_host`, a host mirror: the eager verifier stages the
metadata it reads back, but the graph updates positions on device, so the mirror
is a capture-time value rather than the row's live count. Launched with that cap
the batch leaf attends the wrong span; the plain span leaf is immune because it
reads the row's live count from the spans.

The fix therefore keeps the commit's leaf **only where the caller vouches for the
row position** — the eager verifier sets `row_views_keep_scalar_caps` when it
staged the metadata itself — and uses the plain span leaf otherwise. Both
measured contracts then hold at once: the serving ladder's AR identity, which the
batch leaf broke, and the long-context gate's per-row teacher parity, which the
commit's leaf exists to satisfy and which dropping the leaf entirely broke (all
five straddling cases `target_logits_exact=False`).

Two earlier hypotheses were implemented, measured on the same ladder, and
rejected before this one: (1) the commit's eager view synthesis
(`_eager_native_row_views`) reaching short batches, and (2) the
`staged_dense_full` gate accepting any resolvable row set. Each was a real route
change and each left the divergence exactly where it was (shared prefix 7/16).
Both were removed.

## Changes

- `hipengine/runtime/qwen35_gguf_runner.py`: the staged full-attention chain
  takes `row_views_have_scalar_caps` from its caller and uses the short-context
  batch leaf only under that guarantee; otherwise it launches the plain span leaf.
  Rows at or above the threshold keep the split-K per-row leaf selection the
  commit added, which its own retained evidence measures.
- `tests/test_live_gguf_native_spec_cycle.py`:
  `test_staged_full_attention_below_threshold_leaf_follows_the_caller_guarantee`
  publishes the gfx1151 capability (1023) and asserts both sides — plain leaf with
  the span limit for graph-style views, batch leaf with the row's own cap
  (`12..15`) when the caller staged the metadata.
- `scripts/gguf_mtp_api_gate.py`: the single-prompt identity cases now compare
  true AR against MTP at 8 and 16 tokens (32 as a diagnostic) and report the
  first divergent budget and token index. The old 8-token case covered only the
  first verify cycles, which is exactly where this regression was invisible, and
  its autoregressive arm left the route to the server's automatic policy, so on a
  promoted configuration it compared two speculative arms. New
  `--max-context-tokens` / `--kv-storage` / `--execution-profile` flags let the
  gate reach the staged verifier route at all: its historical configuration
  reports exact on the unfixed head.
- `benchmarks/results/2026-09-18-gfx1151-qwen38-mtp-verifier-ar-identity-fix.json`,
  `benchmarks/README.md`, `benchmarks/CHANGELOG.md`: the fix's evidence, the
  corrected mechanism in the serving-status paragraph, and the dated rollup line.

That is a second, independent RED/GREEN for the same fix. Two gate findings are
worth keeping:

- The gate's historical configuration (no context budget pinned) reports **exact
  on the unfixed head**, because those rows never reach the staged verifier route.
  The new `--max-context-tokens` / `--kv-storage` / `--execution-profile` flags
  exist for that reason; without them the extended ladder could not have seen the
  regression it was extended for.
- With the AR arm pinned, a 32-token diagnostic run reports one divergence on the
  raw completions arm at token 14 - four `248045` tokens under true AR against
  three under MTP, after which the arms track each other exactly. The control
  tree `f607e3184` reports the **identical** divergence on the identical tokens,
  so it is pre-existing rather than introduced here, it is the same late,
  prompt-dependent class the 2026-09-18 entry recorded at tokens 47 and 155 on
  two of seven natural prompts, and it is a production-envelope question (KL,
  top-1) rather than a byte-identity one. The default ladder therefore stops at
  16 and 32 stays a diagnostic.

## Post-fix serving baseline

The matched c=1 ShareGPT protocol from
`benchmarks/results/2026-09-18-gfx1151-qwen38-sharegpt-natural-serving-baseline.json`
(6 prompts, natural output lengths, greedy, `--max-total-len 1024`, one warmup
discarded, `--record-ids`, `HIPENGINE_MTP2_OUTPUT_SPANS=1`, one server process
per arm on this host), re-run on the fixed tree:

| Arm | Wall | tok/s | MTP requests | MTP output share | Accepted drafts/cycle |
| --- | ---: | ---: | ---: | ---: | ---: |
| `c1-off` (true AR) | 186.8 s | 11.74 | 0/6 | 0.0% | — |
| `c1-auto` | 93.5 s | **23.46** | 6/6 | 99.7% | 2.04 |
| `c1-mix` (3 off, 3 auto) | 171.5 s | 12.79 | 3/6 | 16.0% | 2.14 |

The head measured 9.37 tok/s against 11.75 (0.80x) with acceptance 0.10-0.24, and
the control tree 23.60 against 11.79 (2.00x). The fix restores **23.46 against
11.74 = 2.00x** with 99.7% of tokens from speculative cycles, so the serving win
and the AR identity were one regression and both return together. Acceptance
moving from 0.10-0.24 to 2.04 accepted drafts per cycle of a budget of 3 is the
same statement from the verifier's side: a verifier that does not reproduce the
target's own path also rejects the drafts the target would have made.

The `c1-mix` arm's 16.0% share is by construction (half the rows are pinned to
AR); it exists as the in-run control for the same load, and its speculative rows
still group at realized width 1, which is task #2's subject.

Focused unit tests: `tests/test_live_gguf_native_spec_cycle.py` and
`tests/test_unit_sharegpt_mtp_routing_recorder.py` pass.
