# Defer speculative prefill starts instead of forfeiting the MTP provider

## Summary

At c>=2 almost no request ran MTP. The 2026-09-17 repair stopped the crash by
refusing a request whose first prefill chunk ran while another request held the
MTP prompt-activation claim, but the refusal was permanent: the row's candidate
budget was zeroed and it decoded at AR speed for its whole life. Two concurrent
long prompts produced one MTP request and one permanent refusal.

This unit schedules around the claim instead of forfeiting to it. A row that
still needs the claim is deferred by the scheduler, so its first chunk runs
later with the sink it needs, and at most one claim-opening chunked row is
admitted per prefill item. The refusal path stays as the last resort, but it is
no longer what a concurrent arrival normally hits.

The first live check found a second forfeit inside one prefill item: the serial
prefill path activates each row immediately before its own first chunk, so a
multi-row item let its first row take the claim and its remaining rows forfeit.
That is what the `prefill_needs_activation` cap fixes.

## Changes

- `hipengine/generation/qwen35_gguf_mtp2.py`: `prompt_activation_available()`
  reports whether a new prompt activation can start this tick.
- `hipengine/generation/qwen35_gguf.py`:
  - `prefill_activation_ready(request_id)` is false only for a row that has not
    started prefill, has a candidate budget, and does not reuse a prefix; that
    row would forfeit its provider if its first chunk ran now.
  - `prefill_needs_activation(request_id)` is true for the same class of row, so
    the scheduler can admit only one per prefill item.
- `hipengine/generation/batch_scheduler.py`: `next_prefill_work`,
  `next_prefill_batch_work`, and `next_round_robin_prefill_work` take optional
  `ready` and (batch only) `needs_activation` predicates. A deferred row keeps
  its cursor, so no prompt chunk is consumed by a row that did not run it.
- `hipengine/generation/engine_loop.py`: passes both predicates, falls through
  to decode when every prefill candidate is deferred, and keeps an unfiltered
  retry so the loop cannot stall when no decode work exists either.
- Tests: 6 new cases. `test_prefill_ready_filter_defers_a_row_without_advancing_its_cursor`,
  `test_prefill_batch_ready_filter_excludes_only_deferred_rows`,
  `test_round_robin_prefill_ready_filter_skips_blocked_slots`,
  `test_prefill_batch_selects_at_most_one_claim_opening_chunked_row`,
  `test_prefill_batch_does_not_cap_rows_that_need_no_activation`,
  `test_prefill_batch_does_not_cap_a_single_chunk_prompt`, plus
  `test_prompt_activation_available_tracks_the_active_claim`,
  `test_prefill_activation_ready_defers_only_unstarted_speculative_rows`, and
  `test_prefill_needs_activation_marks_only_unstarted_speculative_rows`.

## Validation

Live check (gfx1151, Qwen3.8-27B-Q4_K_M, bf16 KV, explicit `speculative_mtp`)

Four long prompts (734-812 tokens), c=2, stagger 200 ms, 3072-token budget:
2 of 4 requests ran MTP with 61.8% of output tokens speculative, 0 failures.
The pre-change pass over the same shape refused 4 of 4 with
`prompt_activation_in_flight`.

This is a diagnostic, not a serving result. The same run also shows the two
remaining gaps and is why the numbers are not retained as a win:

- The two rows that did not speculate report `no_provider` for their whole
  (short) generation and `target_graph_context_bucket_miss` events; the
  prompt-time reason was not yet reported by the harness, so this unit adds no
  claim about which gate refused them.
- Every request realized `realized_group_rows == 1`, so no wider MTP group
  formed even at c=2 with both rows speculating. Median TTFT was 5.8 s, which is
  the cost of serialized activation, not a measurement of the fix's value.
