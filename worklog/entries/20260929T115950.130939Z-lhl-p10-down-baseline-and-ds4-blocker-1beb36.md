# Isolate P10 down-projection baseline and find its activation-pack blocker

## Summary

P10 (`docs/campaigns/GEMMA4-26B-A4B-PUNCHLIST.md`) asks for a llama.cpp-shaped
Q5_1 MMQ for the expert down projection at K=704. Two things were needed before
any kernel edit: a measured denominator, and a check that the stated shape can
even reach the existing MMQ leaf. Both are now settled, and the second one
blocks the row as written.

**Profiling recipe that was costing hours.** Two `rocprofv3 --kernel-trace`
attempts hung — python pinned at 100% CPU for 30+ minutes with the log frozen
at `HSA version 1.18.0 initialized`, while the unprofiled prebuild took
seconds. `docs/KERNELS.md` states the rule ("Do not let a profiler-injected
child spawn hipcc/clang") but it had not been applied here. Setting
`HIPENGINE_COMPILER_VERSION_FILE=/tmp/hipengine-hipcc-version.txt` (generated
with `hipcc --version` outside the profiler) made the identical command finish
in **6.27 s**. The host explains why the rule exists: it carries five orphaned
`/opt/rocm/lib/llvm/bin/clang++ --version` processes aged 1d18h, 1d18h, 1d17h,
3d15h and 5d02h, all state `S` at 0% CPU — that spawn genuinely blocks here.

**Baseline isolated.** The trace of one 512-token prefill forward recorded 1571
dispatches, 35 distinct kernels, 203.373 ms device total. The down projection
is `q5_1_selected_grouped_wmma_prefill_bf16_bf16_kernel<32, 16, false>` at
**27.053 ms over exactly 29 calls** (932.9 µs/call) — one dispatch per layer
for 29 layers. It reconciles with the family census's 44.545 ms / 58 calls at
1024 tokens (same kernel over 2 blocks × 29 layers), so the two measurements
now agree rather than merely look similar.

**The blocker.** `scan_gguf` reports `blk.27.ffn_down_exps.weight` =
`(128, 2816, 704)`, confirming K=704 (22 × 32). But `_DS4_BLOCK_VALUES = 128`
and **704 % 128 = 64**, so `gguf_q5_1_mmq_selected_prefill`'s own
`in_features % _DS4_BLOCK_VALUES` gate rejects this shape. The trace confirms
it independently: it carries the WMMA grouped owner and **no q5_1 MMQ dispatch
at all**. The gate is load-bearing, not cosmetic — `gguf_q8_1_mmq_ds4_pack_bf16_kernel`
computes `blocks_per_row = hidden / Q8_1_MMQ_BLOCK`, which floors to 5 and
would pack only 640 of 704 values, **silently dropping 64**; the consumer
mirrors the same floor in `ds4_blocks = in_features / Q8_1_MMQ_BLOCK`. Ceil is
not sufficient by itself: at `kb = 5` the consumer's
`w_base = weight_row + kb * 96` needs 576 bytes against a 528-byte weight row
(22 × 24) — an **out-of-bounds read of 48 bytes** — so its `for sub in 0..4`
must stop at 2 sub-blocks for the partial block. llama.cpp is unaffected
because `mul_mat_q` steps in 32-value blocks.

**Correction withdrawn.** An earlier record claimed the census's
`moe_wmma:gguf_q5_1` was the `moe_wmma_tile_map` registry key from
`group_scatter.py` rather than a matmul. That was wrong:
`scripts/gemma4_prefill_census.py:148-151` labels `gemma4_project_experts_wmma`
as `moe_wmma:{quant}`, and gate_up has its own separate label (`moe_wmma_dual`,
line 171), so `moe_wmma:gguf_q5_1` **is** the down projection. The original
attribution of the census's 44.5 ms to the row's 46.8 ms was correct. No repo
file ever carried the wrong claim.
