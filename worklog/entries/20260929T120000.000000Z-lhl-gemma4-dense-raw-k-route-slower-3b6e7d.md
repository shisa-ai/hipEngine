# the dense term's disabled raw-K rowbatch route is slower here, so the host policy is right

## Summary

The dense projections are the largest single prefill term (189.3 ms, 28.3 percent) and sit at a
127 GB/s plateau with 16x weight re-reads (`20260929T020000`). The raw-K prefill dispatch has a
row-reuse mechanism whose own comment says it exists *"so raw-resident Q5/Q6 prefill routes
through the fixed row-reuse kernels instead of the per-row generic prefill path"*, and
**gfx1151 declares it off**:

```
hip_gfx1100:  ROWBATCH_SUPPORTED = True,  ROWBATCH = 32, VARIANT = "coltile"
hip_gfx1151:  ROWBATCH_SUPPORTED = False, ROWBATCH = 0,  VARIANT = "rowbatch"     <- this host
```

with the reason recorded next to it:

> WPF-1/WPF-1T are W7900 raw-Q5/Q6 candidates. gfx1151 retains its independently admitted
> Q4_K_M/T16 matrix schedules and must not inherit their rowbatch or output-column selectors.

That is a policy decided on the W7900. **It does not answer whether the disabled route is faster
on this host at this shape**, which is a measurement, so this measures it rather than assuming
either way.

## Measured: the disabled route is slower

One session, `scripts/gemma4_dense_route_ab.py`, arms run in order on the same loaded model,
512-token prefill, median of 3 after 1 warmup:

| arm | median s | tok/s | vs default |
| --- | ---: | ---: | ---: |
| **default (host policy)** | **0.6496** | **788.2** | -- |
| rowbatch32 + coltile | 0.6567 | 779.6 | +7.1 ms |
| rowbatch32 + rowbatch | 0.6583 | 777.8 | +8.7 ms |
| rowbatch8 + coltile | 0.6659 | 768.9 | +16.3 ms |

**All three arms of the disabled route are slower. None is faster.** The session demonstrably
reached the dispatch -- `raw_k_prefill_rowbatch_session` /
`raw_k_prefill_variant_session` were seen as `rowbatch=32 variant=coltile` inside the arm, and the
timings moved, which they could not have if the route were unchanged.

Against this host's ~1.5 percent noise floor (`20260929T100000`, ~9.7 ms at this magnitude), only
the rowbatch8 arm clearly exceeds it. The other two are inside it. **What the data supports is
that no arm of the disabled route is faster; it does not support a claim about how much slower
each is.** The arms ran sequentially rather than interleaved, which is the weaker protocol.

## What this settles

- **The gfx1151 policy is confirmed for this shape.** The W7900 rowbatch/coltile route is not
  being wrongly withheld here; enabling it would cost time, not save it. The recorded reason
  stands on its own and now has a gfx1151 measurement behind it too.
- **The dense term has no routing lever left.** Its routes (`20260929T100000`), its tile family
  (`20260929T020000`), and now the alternative route it does not take have all been measured.
  **The 127 GB/s plateau is a kernel unit, not a mis-selected route.**
- The `GGUF_RAW_Q8_F32_PREFILL_ROWBATCH_SUPPORTED = True` declaration on gfx1151 is **not** a gap
  for this model: it is the *F32-input* raw-Q8 family, and gemma4 runs bf16 activations.

## Changes

`scripts/gemma4_dense_route_ab.py`: the harness, kept so the policy can be re-checked on another
shape or host without rebuilding it.

## Validation

```
export HIPENGINE_HIP_ARCH=gfx1151 ROCR_VISIBLE_DEVICES=0 PYTHONPATH=.
.venv/bin/python scripts/gemma4_dense_route_ab.py --prompt 512 --repeats 3 --warmup 1
```

One session, one host. Per `20260928T114215`, absolute milliseconds are not comparable across
sessions. The arm order is the default first, which is the conservative ordering for a drift
argument: if drift made later arms slower, that bias works *against* the disabled route being
better, and it was already slower.
