# the 80.20 decode target is 7900 XTX arithmetic and this host's comparator is 41.92

## Summary

The decode distance-to-target I have been reporting is wrong for the host I am
measuring on. `80.20` is not a gfx1151 number and never was: it is campaign
arithmetic on the **RX 7900 XTX (gfx1100)** host, `0.70 x 114.57`, where 114.57 is
the same-GPU Qwen3.6-35B-A3B shipping-route decode rate. The same entry pins the
llama.cpp same-artifact comparator at **68.92 tok/s**, also on the 7900 XTX, and
records that 68.92 sits *below* the 80.20 target, so the campaign bar requires
beating the incumbent external engine on this artifact.

The gfx1151 comparator is different. The decode traffic census
(`20260927T225558`) measures the **same-host llama.cpp reference at 41.92 tok/s**.
That is the apples-to-apples number for the 8060S, and it is 1.64x below the
7900 XTX's 68.92 rather than the 3.4x the two hosts' raw bandwidth ratio would
suggest.

So the honest decode position depends entirely on which comparison is meant:

| comparison | reference | current | distance |
| --- | --- | --- | --- |
| same-host, gfx1151 | 41.92 (llama.cpp, 8060S) | 27.31 | **1.53x** |
| campaign target, gfx1100 | 80.20 (0.70 x Qwen, 7900 XTX) | 27.31 | 2.94x |

Quoting 2.94x while measuring on the 8060S mixes hosts. The 1.53x is the number
that describes this branch's actual remaining gap, and it is also the harder
statement to make progress against, because the 41.92 reference is an external
engine measured on the same silicon.

The objective's "2X on decode" is a third framing again: 2x the branch's own
baseline, which the census and the route ablation both put at **24.85** tok/s for
the pre-fix mixed configuration. That target is roughly **49.7 tok/s**, which is
*above* the same-host llama.cpp reference by about 19%. So reaching the
objective's decode bar on this host means beating llama.cpp, not merely matching
it.
