# Gemma 4 prefill attention: one warp per key, register tree, bit-exact 3.08x

## Summary

Prefill attention was the largest un-attributed cost on this host and it was
paying it entirely in synchronization. The kernel is one block per (token, head)
that walks keys serially and calls a 256-lane block reduction for every key, so
at a 512-token prompt it runs eight `__syncthreads` rounds per key — 5120
barriers per block — against one multiply per thread of actual work. Measured
**147 GFLOP/s**, invariant to the work inside the key iteration. Running the same
tree with one warp per key and the partials in registers takes the kernel
**28.63 -> 9.29 ms (3.08x)** at 512 tokens and **468.05 -> 133.02 ms (3.52x)** at
2048, and 512/128 prefill **3.637 -> 3.309 s (1.099x)**. It is bit-exact, so it
ships on the default path with no flag and no execution-profile gate.

## Changes

- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention.hip`: pass 1 of
  `gemma4_attention_prefill_kernel` gains a `head_dim == 256 && blockDim.x == 256`
  path that runs one warp per key. Lane *l* holds logical threads *l* + 32k, so
  the 128/64/32 stages and the final stride-1 stage are intra-lane and strides
  16..1 are warp shuffles; the leaves are computed under `#pragma clang fp
  contract(off)`. Every other shape keeps the original loop unchanged.
- `tests/test_unit_gemma4_gpu_kernels.py`: a readable reference for the
  association (the logit tree, the exact maximum, the denominator tree, the
  serial numerator) and a bit-exactness test against recorded outputs.
- `tests/fixtures/gemma4/attention_prefill_head_dim_256_{f32,bf16}.npy`: the
  recorded tensors, captured from the pre-change kernel (12 tokens x 4 heads x
  256 dim, causal plus masked-out recent keys).
- `hipengine/runtime/gguf_linear.py`: `_ensure_linear_kernel_registered` now
  snapshots the registry before its sweep and restores the entries it overwrote.
  The sweep registers with `replace=True`, so it was clobbering fixture kernels
  that callers had deliberately installed — the opposite of what its own comment
  promises — which made two tests in `tests/test_unit_gemma4_expert_route.py`
  order-dependent and let one of them launch the real kernel against fake
  pointers, which is what had been dumping core in the gemma4 bundle.
- `benchmarks/results/2026-09-27-gemma4-attention-prefill-register-tree-accepted.json`,
  `benchmarks/CHANGELOG.md`, and the campaign document's route-attribution
  section (which now carries the current per-route prefill budget).

## Validation

- **The tree is the block tree.** A standalone device kernel runs both trees over
  the same 256 leaves: 0 of 64 random rounds differ, and the device block tree
  matches a numpy model of it. The register scheme was also checked in numpy on
  the fixture's own 296 logits: 0 differ.
- **Outputs are bit-identical.** `test_attention_prefill_head_dim_256_is_bit_identical_to_recorded_outputs`
  asserts array equality against the recorded tensors, f32 and bf16.
  62 tests pass in `tests/test_unit_gemma4_gpu_kernels.py`, 501 in the
  `tests/test_unit_gemma4_*.py` + `tests/test_gpu_gemma4_*.py` bundle.
- **The association is pinned in readable form.**
  `test_attention_prefill_head_dim_256_follows_its_reduction_association`
  reproduces the logit tree, the maximum, the denominator tree and the serial
  numerator in numpy and compares at one fp32 ulp of the device `expf`.
- **Public path.** `scripts/gemma4_campaign_bench.py` at 512/128, 3 samples and
  1 warm-up, two arms on one tree with `gemma4_attention.hip` the only
  difference: prefill **3.637 -> 3.309 s (140.76 -> 154.75 tok/s, 1.099x)**,
  public wall 9.656 -> 9.358 s, decode 21.063 -> 21.048 tok/s, 128 of 128
  identical greedy token ids.
- **Kernel level, two geometries.** 512 tokens (16 heads, 8 kv heads, head_dim
  256): 28.627 -> 9.288 ms, 150.0 -> 462.4 GFLOP/s. 2048 tokens: 468.054 ->
  133.017 ms, 146.8 -> 516.6 GFLOP/s.
- **Registry sweep fix.** 501 passed in the gemma4 bundle where it previously
  core-dumped; 265 passed across the GGUF dispatch and registration-sweep unit
  tests.

## Next

- The remaining prefill budget at 512 tokens, measured by route: `Q4_K` gate/up
  1156 ms (its fastest route is the gated MMQ path, waiting on the lead's
  `kl_max` call), `Q8_0` dense 694 ms, `Q5_1` down 651 ms, layer 29's `Q5_K`
  246 ms, attention ~330 ms after this unit.
- **Do not chase the `Q8_0` dense route with less traffic.** A row-grouped
  variant that moves 4.56 GB instead of 9.30 GB is not faster (21.23 ms against
  22.13 ms): achieved bandwidth falls from 428 to 220 GB/s, so the kernel is
  limited by 1-byte weight load transactions rather than by DRAM. The lever is
  fewer, wider loads, which needs a different association and therefore the
  gate. The variant was reverted rather than shipped.
