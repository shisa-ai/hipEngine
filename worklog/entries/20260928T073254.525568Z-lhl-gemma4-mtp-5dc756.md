# the mtp drafter is measured working but the generator does not implement the serving route and a plain generate returns immediate eos

## Summary

`20260928T073209` measured draft acceptance at 0.796 and left two open questions: whether
the draft path is reachable from the user surface, and whether accepted drafts translate
into a decode speedup. Driving `hipengine.LLM` directly answers the first with a clear
**no**, and turns up a separate problem with the plain decode baseline.

## The answer to question 1: the serving route is not implemented

```
generator            : SubmitPollTextGenerator
supports_speculative_mtp: False
speculative_mtp_serving : None

generate_speculative_mtp_detailed: NOT SUPPORTED
  -- speculative MTP generation is not supported by this generator
```

`LLM.generate_speculative_mtp_detailed()` exists as a first-class API method, but the
Gemma 4 generator reports `supports_speculative_mtp = False` and the call raises
`NotImplementedError`. **The acceptance harness reaches the drafter through the low-level
`Gemma4Runner` + `Gemma4MtpDrafter`, bypassing `LLM` entirely.**

So the objective's MTP status is: **the drafter is done and measured competitive; the
generator integration is missing.** That is a much narrower gap than "MTP not working",
and a much larger piece of finished work than "wiring not started" implied -- the hard
part is the drafter, and it exists.

Worth noting for the record: the claim I repeated for fifteen iterations without checking
("engine wiring not started") turns out to be **right about the serving route**. It was
still wrong to state it unchecked, and the reason it was worth checking is that it hid how
much of MTP is already finished.

## The separate problem: plain generate returns immediate EOS

```
plain generate()  : 541.76 tok/s  (35.81/541.76)
text sample (plain): '\n<eos>'
```

**The 541.76 tok/s is not a decode rate.** The two repeats differ by 15x -- 35.81 then
541.76 -- and the returned text is an immediate end-of-sequence. The prompt produced
essentially no output, so the second repeat's "rate" is a division by near-zero work.

**The plain baseline from this script is therefore unusable, and the immediate-EOS
behaviour is its own defect that this entry does not explain.** Two candidates, neither
tested:

1. the chat template is not being applied, so the model sees a raw prompt it terminates on;
2. something in the default sampling path commits EOS on the first step for this artifact.

The script has no assertion on the generated token count, which is why it printed a
number that looks like a result. **That is a flaw in the probe, and it is the same class of
error as the rest of this stretch: a number accepted at the resolution it was printed.**

## What is established and what is not

**Established:**
- the Gemma 4 drafter's acceptance is 0.796 overall, mean 4.10 tokens/round, and it beats
  llama.cpp at three of four draft positions (`20260928T073209`);
- `LLM.generate_speculative_mtp_detailed()` is not supported by the Gemma 4 generator.

**Not established:**
- whether accepted drafts would produce an end-to-end speedup, because the route to test
  it does not exist yet;
- why a plain `generate()` on this prompt returns immediate EOS;
- whether the 35.81 tok/s first repeat is a valid decode rate. It is in the range the
  route ablation reports (28-35 tok/s), so it is plausible, but one sample is not a
  measurement.
