# Prefill attribution: GPU-bound, expert projections are 97%, host sweep waste removed

## Summary

The gfx1151 Gemma 4 prefill is **GPU-kernel-bound and almost entirely the two
expert projections**. A host-side defect found on the way (a per-layer kernel
registration sweep) is fixed and pinned, but it moves no wall time, and this
entry records that honestly rather than as a speedup.

Three measurements, in the order they were taken:

1. **Host or device?** One 512-token prefill, timed with and without a sync:
   submit 4.157 s, submit+drain 4.157 s. The host profile then showed 3.14 s of
   the 4.149 s in `hip.py:110(memcpy)` - which turned out to be a single 1 MiB
   logits D2H (`forward:624 -> _forward_block:748`) that waits for the queue.
   Its duration *is* the GPU prefill time.
2. **Which kernels?** `rocprofv3 --kernel-trace` on a 512-token prefill, 2581
   dispatches. Kernel busy 8.418 s of a 31.8 s profiled span (profiling inflates
   gaps, not kernel bodies; the unprofiled prefill is 4.2 s). Ranked by time:
   Q5_1 selected grouped prefill 58 launches x 43.7 ms = 2.53 s (30.1%), Q4_K
   selected grouped prefill (staged) 58 x 40.7 ms = 2.36 s (28.0%), Q8_0 exact
   prefill 410 x 3.4 ms = 1.39 s (16.5%), `gemma4_attention_prefill` 60 x
   22.5 ms = 1.35 s (16.1%), `gguf_k_selected_prefill` 4 x 159 ms = 0.64 s
   (7.6%), everything else 1.7%. Allowing for profiling overhead on the two big
   kernels, they are ~97% of the real prefill.
3. **How fast are they running?** The Q4_K staged kernel moves ~4.3 GB (285 MB
   of weights, ~4 GB of activation re-reads) in 35.6 ms = **121 GB/s** against a
   ~500 GB/s roof, and does ~23 instructions per weight element against the
   part's ~333 G lane-ops/s issue rate. So it is **instruction-throughput-bound,
   not bandwidth-bound**: the activation re-read is L2 traffic that the kernel is
   not waiting on. This is the honest explanation of the gap to llama.cpp's
   1014 tok/s (8.4x): their MMQ path uses large out-tiles and int8 dot products,
   which is ~4 MACs per instruction and ~128 output columns per block, against
   this path's 8-column tile and 1 MAC per FMA.

Also confirmed by measurement: prefill is linear in prompt length at ~8.2 ms per
token (128/128 = 1.043 s, 512/128 = 4.235 s), so there is no prompt-length
pathology - the earlier 122 -> 77 tok/s falloff across shapes is just the fixed
per-token cost with the fixed per-request overhead amortized away.

## Changes

- `hipengine/runtime/gguf_linear.py`: `_ensure_linear_kernel_registered` now
  memoizes its full repair sweep on the registry generation. The sweep is a
  repair path for a registry a test cleared, not a per-call requirement; the
  Gemma 4 grouped route's variant-preference probe misses on purpose for a
  variant that is not built (Q5_1 staged), once per MoE layer, and each miss
  re-ran ~650 registrations. Any registry mutation still re-arms the sweep, so
  test-isolation semantics are unchanged.
- `tests/test_unit_gguf_linear_registration_sweep.py`: five tests pin the
  contract - a registered key never sweeps, a missing key sweeps once per
  generation, an unrepairable key still sweeps only once, and both
  `clear_registry_for_tests()` and `register()` re-arm it.

## Validation

- `tests/test_unit_gguf_linear_registration_sweep.py`: 5 passed. RED verified by
  disabling the memo guard in place (2 failed, 3 passed), then restoring it.
- `tests/test_unit_gguf_linear_dispatch_cache.py`,
  `tests/test_unit_gguf_linear_dispatch.py`, `tests/test_unit_kernel_registry.py`:
  exit 0. The dispatch-resolve memo shares this generation mechanism, so these
  were run to confirm the new memo does not disturb it.
- Wall time: **unchanged**. 512/128 prefill 4.235 s (baseline 4.240 s, MAD
  0.022) and 128/128 1.043 s (baseline 1.045 s), parity true in both. cProfile
  had shown the sweep as 0.70 s of host CPU; that is profiling-inflated and
  fully overlapped with GPU work in the real path.

## Next

- Cut instructions per weight element in both expert kernels. The cheapest
  bit-exact step is hoisting the staged activations into registers outside the
  output-tile loop (8 shared loads per weight element become 8 per k), which by
  instruction count is worth ~1.5x on kernels that are ~97% of prefill.
- Beyond that the remaining wins change arithmetic (int8 dot products, larger
  output tiles) and therefore need the production execution-profile gate rather
  than bit-exactness.
