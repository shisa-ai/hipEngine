# DP-3 split-F16-operand tile is rejected on measured cost

## Summary

`DP-3` (split-F16-operand variant) was the one ledger candidate with no prior
work. Its named next action was "microbenchmark against `dense_wide256` before
any scope work". That microbenchmark now exists and **rejects the scheme**.

## What was built

`WMMA_REP` as a template parameter **defaulting to 1**, so every existing
instantiation is byte-identical, plus a `dense_wide256_split3` export that issues
the same product three times on identical operands. That isolates the **WMMA
issue cost** of the split scheme and nothing else.

Its result is the accumulator summed three times over - **not** a precision
improvement, **not** a candidate route. Only the timing is meaningful, and the
artifact says so in a `not_claimed` block so nobody later mistakes the probe for
a candidate.

## Measured, same host

| role | `f32in` (1) | `f16in`+cast | `split3` (3) | ratio 3/1 | split vs `f32in` |
|---|---:|---:|---:|---:|---:|
| attn_qkv | 2.6130 | 1.4263 | 4.5880 | 1.756 | **0.958** |
| attn_q | 2.8149 | 1.7834 | 5.1905 | 1.844 | 1.168 |
| attn_gate | 1.5622 | 0.9733 | 2.7919 | 1.787 | 1.113 |
| ssm_out | 1.7431 | 1.1360 | 2.9045 | 1.666 | 1.086 |
| shared_gate | 0.2307 | 0.1938 | 0.4699 | 2.037 | 1.711 |

**Three products cost 1.787x, not 3x.** Marginal product 0.996 ms against a
2.6007 ms baseline, so issue is ~38% of tile time and memory/LDS ~62%. Issue
cost is not prohibitive.

## The number that decides it

`f16in` is the promoted route, so a split would be built on it and must still
beat the `f32in` route it would replace. Borrowing an `f16in` figure from the
DP-7 artifact would have been a cross-machine comparison, so it was timed in the
same process with the cast inside the timed region.

**Median 1.113** - a split on the promoted route is *slower* than the route it
would replace on four of five shapes, by 71% on `shared_gate`. And that is a
**lower bound**: a real split also pays doubled LDS operand bytes, the hi/lo
splitting arithmetic and extra registers, none of which the probe issues.

My prediction was "about 2.7 ms, above the f32in route" - correct for the median,
but **`attn_qkv` came in at 0.958**, contradicting a blanket claim. Reported
rather than smoothed: it is a 4.2% margin against overheads certainly larger than
4.2%, so it does not support building the split.

## Reversal condition

A real split measuring below 1.0 on the shapes carrying dense prefill time would
overturn this. Stated so the negative is falsifiable rather than merely final.

## A guard caught my own change

`test_every_export_has_a_wrapper_variant` failed: its parser regex matched only
`HIPENGINE_DENSE_WIDE_EXPORT(`, so the new `_REP` export was invisible and would
have made the guard vacuous for exactly the new code. Extended the regex to both
macros rather than special-casing the variant.

Also confirmed the promoted route is untouched: 32 GPU+unit tests pass,
including the CPU-reference comparisons, so `WMMA_REP = 1` is numerically
identical to before.
