# P6e cancellation-delay sweep: acknowledgement is flat from 600 ms to 3500 ms

## Summary

P6's declared gate is "bounded command acknowledgement/cancel delay", but the
harness exercised a single cancellation point at 600 ms. One point cannot establish
a bound, and different delays land at different places in the resumable segment
loop. This unit sweeps early, mid, and late cancellation inside the same prefill
window and gates on every point.

## Changes

- `--cancel-delay-ms` accepts a comma-separated sweep (a bare value still works).
  `_parse_cancel_delays()` sorts ascending — a non-monotonic artifact would imply a
  non-monotonic prefill — and rejects empty, zero, and negative values.
- The cancel/refill arm now runs once per delay, recording per point: admission,
  `bytes_before_close`, cancellation-counter delta, prefill work delta, request
  failure delta, acknowledgement latency, and survivor digest.
- New gate `cancellation_sweep_bounded`: every point must be admitted, move the
  cancellation counter, arrive with **zero** bytes already streamed (so the cancel
  landed during the prefill rather than after output began), and be acknowledged
  within the declared limit. Failures are listed per point with the delay named.
- The single-delay gates report the final sweep point, which is the one closest to
  prefill completion and therefore the least likely to have yielded; the sweep gate
  covers every point.

## Validation

`--cancel-delay-ms 600,2000,3500` on the resumable INT8 route, 3072-row prompt:

| Delay | Admitted | Bytes before close | Cancel delta | Acknowledgement | Survivor sha256 |
| --- | --- | --- | --- | --- | --- |
| 600 ms | yes | 0 | 1 | 764.6 ms | `118cf54787fe…` |
| 2000 ms | yes | 0 | 1 | 767.9 ms | `118cf54787fe…` |
| 3500 ms | yes | 0 | 1 | 772.1 ms | `118cf54787fe…` |

All **nine** gates PASS, sweep failures empty. The result is stronger than three
passing points: acknowledgement varies by **1.0%** (764.6 → 772.1 ms) across a
**5.8×** range of cancellation timings, against a 3000 ms limit. A delay-dependent
stall would show up here as a trend; there is none. All three refills reproduced the
reference byte-for-byte, so the survivor guarantee also holds at every cancellation
point rather than only at 600 ms.

## Honest limits

- A defect in this unit crashed a completed GPU run at artifact-write time:
  `_StreamOutcome` has no `text_chars`, so the sweep raised `AttributeError` after
  doing the whole workload. Fixed, and a test now asserts the attributes the
  artifact assembly reads, so the same rename is caught in under a second rather
  than ten minutes into a run.
- The sweep points are 600/2000/3500 ms against a prefill that completes around
  4.7 s, so "late" is still ~75% through the prefill rather than at its edge. A
  point beyond the prefill duration would legitimately fail the
  `bytes_before_close == 0` check, which is what that check is for.
- Cancellation is still a raw TCP close; no other disconnect shape is exercised.
- The layer budget remains 4, so the sweep does not vary the segment size.
