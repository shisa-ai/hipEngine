# P6e root cause: the service harness never enables INT8 KV, so the resumable route is unreachable

## Summary

The P6e audit has been chasing a "decline" — why the layer-outer resumable route
does not engage in the service. The answer is that it was never asked to. The
service proof runs with **BF16 KV**, so the entire INT8 resumable prefill route is
unreachable, and every gate in that harness measures the default route.

Measured directly, by exporting each resident session's own `kv_attention_source`
(the field `qwen35_gguf.py:8084` reads to decide whether to attempt the resumable
executor), rather than reading the route manifest, which the previous entry proved
belongs to the decode phase:

```
SESSION kv_attention_sources: {"bf16": 2.0}
resumable requires          : int8_direct
manifest (decode-phase)     : "unavailable"
executor_modes              : {"None": 2.0}
oracle observed peak owners : 0.0
packed_layer_outer_env_seen : "1"
```

## The mechanism

`qwen35_gguf.py:8084` is the outer gate:

```python
if getattr(lease.session, "kv_attention_source", None) == "int8_direct":
    if self._prefill_resumable_int8_chunk(row, chunk, final_chunk=final_chunk):
        return
    self._fallback_reasons["int8_direct_full_prompt_prefill"] += 1
    ...
```

With `kv_attention_source == "bf16"` the branch is not entered, so:

- `_prefill_resumable_int8_chunk` is never called, which is why **no** fallback
  counter fired — the previous entry could only infer this from an empty counter.
- The code falls through to the chunk-outer packed path, which builds a
  `last_packed_prefill_plan` **without** `executor_mode`, producing the observed
  `executor_modes: {"None": 2.0}`.
- No per-layer oracle owner is ever allocated, producing the observed zero peak.

Every observation now reconciles with a single cause, and that cause is
configuration rather than engine behaviour.

The configuration gap is concrete. `ServerConfig` already accepts the setting
(`hipengine/server/api.py:327-329`):

```python
kv_storage: str = "auto"
kv_scale_dtype: str = "fp16"
kv_scale_granularity: str = "per_token_head"
```

and `resolve_kv_policy` documents what `auto` means
(`hipengine/kvcache/policy.py:120-122`):

> ``auto`` deliberately resolves to BF16 unless the caller marks the request as
> requiring INT8 for admission. Explicit ``int8_per_token_head`` records that the
> user/test requested INT8 rather than an admission fallback.

The P6e harness constructs `ServerConfig(...)` without any KV field and
`LLM(model, backend=backend, max_sequence_length=...)` without a `kv_policy`, so
`auto` resolves to BF16. The direct-call GPU proof, by contrast, sets
`resolve_kv_policy("int8_per_token_head", scale_dtype="fp32")` explicitly — which
is exactly why that proof exercises the resumable route and the service proof does
not.

## Changes

- `hipengine/generation/qwen35_gguf.py`: `prefill_transient_owner_inventory()`
  records each session's `kv_attention_source` alongside the executor modes it
  already collected.
- `hipengine/server/api.py`: exports it as
  `hipengine_resident_kv_attention_source_total{source="..."}`.
- `scripts/gguf_p6e_cancel_refill_proof.py`: reads it, and keeps it strictly
  separate from the manifest-derived value (`kv_attention_sources` versus
  `manifest_kv_attention_source`) so the two measurements cannot be conflated
  again.
- Incidental fix: `qwen35_gguf.py` used `sys.stderr` in `_trace_mtp2_resolution`
  without importing `sys`, so setting `HIPENGINE_MTP2_TRACE_DECLINE` to a non-zero
  value raised `NameError` instead of printing. Found by lint while editing the
  file; verified fixed by running the path.

## Honest limits

- The claim "the route was never attempted" rests on `kv_attention_source` being
  read at `qwen35_gguf.py:8084` and on the session attribute being the same field
  exported here. That chain was verified by reading both sites, not by
  instrumenting the gate itself. A direct counter on the branch would be stronger.
- `kv_attention_sources` reports the settled value after the run, not a per-request
  history, so a session that changed layout mid-run would report only the last.
- The export counts sessions, and the harness runs two, so `{"bf16": 2.0}` means
  both resident sessions were BF16. It does not say whether any request was ever
  admitted with a different layout.
- Whether the resumable route *works* once INT8 is enabled in the service is still
  unmeasured; this unit only establishes that it was never reachable before.
