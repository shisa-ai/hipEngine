# production_moe_restore rejected on the task gate, not on speed

## Summary

`production_moe_restore` is rejected. It restores the WMMA-MoE27 prefill route on
layers 27-47 (iu8-WMMA gate/up plus the compact f16-WMMA down), replacing the
exact grouped iu8-risk+repair route production runs today.

**It passes the production numerical envelope in every category and fails the
task gate on three of eighteen prompts, deterministically.**

| Gate | Outcome |
| --- | --- |
| lifecycle | pass — both arms return to 0 allocated bytes |
| numerical envelope | pass — all four categories, every bar |
| state / determinism | pass — no repeat mismatches over 3 repeats per prompt |
| task gate | fail — 15/18 strict-exact, `requires_review` |
| decision | `reject candidate and keep strict fallback` |

The candidate's own mechanism text asked for an individual verdict rather than
inheriting the 2026-09-14 arithmetic sweep's, observing that the sweep's
triggering candidate (`production_q8_fallback`) declared "other production paths
unchanged" and failed on **task quality** rather than on this route. This run
gives the route that individual verdict, and it fails on the same axis. That is
the substantive finding: the sweep was over-broad in the sense that its stated
trigger did not implicate this route, but re-testing the route on its own merits
reaches the same disposition.

## Provenance and the dirty-tree question

The first run (`bg-138`) finished while the Q8 iu8 route removal was in flight
and carried `source.tracked_clean: false`. Rather than retain a packet with a
known provenance gap, the gate was re-run on the clean committed tree.

**The two packets are identical** — the envelope matches to every printed digit
and the same three prompts diverge. That is expected: the candidate's bound
environment is `{PRODUCTION_MOE_PREFILL: "1", Q4_IU8_PREFILL: "1"}` on
`moe_linear` keys, and the removal touched the generic dense `linear` path. The
clean run is the citable one; the earlier packet is recorded in `artifact.json`
under `source_packet.supersedes`.

**One reading that looked alarming and is not.** The packet's `bound_environment`
shows both flags as `"0"` while the spec requests `"1"`, which suggests the
binder zeroed the candidate's own override and the route never ran. It did run.
`bound_environment` is captured *before* `os.environ.update(candidate_spec.environment)`
and exists to restore the pre-override values in the `finally` block; the
override is applied after generator construction, which is the order the
pre-binder-override warning requires. The 3-of-18 divergence would be impossible
if both arms were the same configuration. The field name is misleading, but the
gate is correct.
