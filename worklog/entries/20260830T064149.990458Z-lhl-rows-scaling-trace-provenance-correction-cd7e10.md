# Provenance corrections to the rows-scaling trace, and the process failure behind them

## Summary

Four provenance fields in the rows-scaling artifact I committed 20 minutes earlier (5a89dafb5), plus
a supersession citation in its entry, were wrong. Every one of them was caught by cross-reading the
packets, `rocm-smi` and `uname` - not by any gate, because no gate checks these fields. The
measurements themselves are unchanged and stand; the labels under them did not.

## What was wrong

1. **Model.** The artifact said "Qwen3.5-9B GGUF Q4_K_S, mtp_type=none, 152001 KiB". Both packets
   the driver, say `/models/gguf/Qwen3.8-27B-Q4_K_M.gguf`. The invented quant was baked into the
   artifact *filename* (`...q4ks...`), which is how it survived a read-through.
2. **Hardware.** "10.5 GB visible" - `rocm-smi` reports 48,301,604,864 B (48.3 GB) on device 0.
3. **Host.** "Linux 6.17.0-35-generic x86_64, 230359 MB RAM" - this host is `7.1.3-2-cachyos` with
   64,192 MB. Neither string was read from anything.
4. **Supersession.** Both the artifact and entry `20260830T063749...-76ab42` cite
   `w7900-gguf-q4ks-ar-amortization-prefill-split-2026-08-30.json`, a file that has never existed.
   The real one is `2026-08-30-w7900-q4km-decode-amortization-c2.json`.
5. Caught before it landed: a changelog draft of mine quoted "0.95/0.90/1.11..." ratios and a
   "0.295 s fixed + 42.5 ms/token" fit that no artifact contains. Deleted rather than sourced.

That last point is the tell. The numbers I derived *in this session* from files in front of me were
all correct. Every wrong string came from writing provenance from memory of what the run was
*supposed* to be, which is exactly the field class AGENTS names (model + quant + workload + host +
hardware + command) because it is the class nobody re-checks.

## Changes

- Artifact corrected in place with a 4-entry `corrections` array, and renamed to
  `benchmarks/results/2026-08-30-w7900-q4km-ar-rows-scaling-kernel-trace.json`.
- `supersedes_detail` rewritten: my first version explained the other artifact's 1.52x as an
  arithmetic slip ("divided the wave wall by 24 steps while subtracting one prefill"). That was a
  reconstruction of their method from memory. What this trace can actually support is a *mechanism*
  contradiction - the per-row-GEMV hypothesis is dead and decode kernel time amortizes at 1.24x for
  2x rows - with C3-C8 explicitly out of scope.
- `benchmarks/CHANGELOG.md` row rewritten to cite only figures computed in this session.
- New `scripts/gguf_c1c8_ar_only_control.py` + 6 CPU-only tests (e21dc16e1): the published command
  had referenced a `/tmp` driver, which my own command-drift gate calls `SCRIPT-NOT-IN-REPO`.

## Validation

- Model re-read from the packet bytes (`re.findall(r'...\.gguf', raw)` -> single hit) and from the
  driver, which agree.
- VRAM from `rocm-smi --showmeminfo vram`; kernel and RAM from `uname -r` and `/proc/meminfo`.
- Superseded-file check now done the cheap way: `ls benchmarks/results | grep <name>`.
- `benchmarks/results/2026-08-30-w7900-q4km-ar-rows-scaling-kernel-trace.json` parses, and its
  measurements block was untouched by the correction.

## Next

- Prevention, as a gate rather than a resolution: extend the published-artifact checks to assert
  that (a) every `supersedes`/`links` filename in an artifact exists, and (b) when a `model` value
  appears as a path inside a cited packet, the two agree. Parse-only, no GPU, same shape as
  `scripts/check_published_command_drift.py`. Tracked as task #16.
- Personal rule worth keeping: fill provenance fields from files in hand - packet, `uname`,
  `rocm-smi` - in the same command that writes the artifact, never from the run's intent.
