# Qwen4Exp served context is capped at the QSA dense-equivalent constant

## Summary

Read-only static diagnosis, prompted by tool-eval-bench rejecting 58/69
scenarios as `context_length_exceeded` against a 2,051-token cap on a
262,144-token model. No code changed, no GPU touched, nothing measured this
session; GPUs were in use for other benchmarking.

Three findings. First, `2051` is not a tuned threshold or a memory budget: it is
`qsa_token_budget(2048) + qsa_compression_ratio(4) - 1`, the largest live
context at which QSA top-k selection is provably the identity function. Below it
sparse attention is exactly dense attention; at 2,052 the 513th complete block
appears, the 512-block budget is oversubscribed, and the indexer begins genuinely
selecting. It is a correctness boundary, not a performance crossover — crossing
it costs about 29 ms/token, so no empirical tuning would have chosen it.

Second, the number means two unrelated things: the model constant
`qsa_dense_equivalent_max_tokens` / `dense_equivalent_limit` / selection-buffer
capacity (geometry, must never change), and the default runner/generator
`max_sequence_length` (a bring-up policy default frozen at the same value). A
blanket edit on `2051` would silently break exactness.

Third, the capacity is not raisable through any served path.
`make_qwen4_exp_gguf_generator_gfx1151` (`hipengine/generation/qwen4_exp_gguf.py:764-777`)
neither accepts nor forwards `max_sequence_length`, so `--max-context-tokens` can
only clamp downward and startup fails until `2051` is passed by hand. Internal
harnesses bypass the factory and pass their own capacity — `qwen4exp_row4_state_gate.py`
runs at 4,352 and P10 evidenced 4K/16K/64K retrieval — so this is a plumbing gap,
not missing functionality.

The decisive design point for whoever fixes it: the dense/sparse branch keys off
*live* token count, not allocated capacity (`qwen4_exp_runner.py:2284`). Raising
the cap costs memory (24 KiB/token KV plus index state; 7.90 GiB per sequence at
256K, 15.79 GiB at c2) but does not move short requests onto the sparse path.
