# The warp-per-key attention path now covers head_dim 512

## Summary

The five global layers in `gemma4_attention_prefill_kernel` were gated out of the
fast warp-per-key path by `head_dim == 256`, so they ran the block path whose own
comment calls the per-key barrier rounds "the whole cost of this kernel". The
gate now covers 512 as well.

| | before | after | |
| --- | --- | --- | --- |
| prefill, 512/128 | 257.1 tok/s | 266-268 tok/s | **+3.7%** |
| global layer | 23.5 ms | 12.04 ms | **1.95x** |
| sliding layer | 7.1 ms | 7.45 ms | +5% |
| attention total | 301.09 ms | 246.55 ms | **-18.1%** |

The tree moved into a templated device function,
`gemma4_warp_key_logit<scalar_t, kLeaves>` with `kLeaves = head_dim / 32`, which is
the codebase's own style for this kernel family. No new flag.

## The arithmetic detail that mattered

The first attempt was wrong, and the parity test said so rather than a review.
It computed the second leaf as a rounded multiply and then added it, and
`test_decode_symbol_bit_matches_prefill_symbol` failed at head_dim 512 with 54.6%
of elements differing in the seventh digit.

The block and decode kernels both accumulate a key's dot as
`dot = 0; for (d = tid; d < head_dim; d += threads) dot += q[d] * k[d];` with
contraction left on. At head_dim 512 with blockDim at the 256 thread cap that is
two leaves per thread, so the second is a fused multiply-add into the first. At
head_dim 256 there is one leaf per thread, and `fma(a, b, 0)` is exact, so a
single rounded multiply is already what the block kernel computes - which is why
the 256 path had never revealed the distinction. Writing the second leaf as
`fmaf(q, k, p[k])` fixed it and the suite went green.

That is precisely the hazard the kernel's existing comment about rounding once
instead of twice was describing, and it is worth recording that the oracle caught
it: a tree stage that is structurally correct can still be arithmetically wrong
in the last bits.
