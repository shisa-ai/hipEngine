# P2: server-faithful allocation probe with while-live transient capture

## Summary

Roadmap P2, first tranche: the allocation probe now drives the real server
process (actual pool binding, slot views, packed slot-local prefill entry on
the promoted-AOTriton route) instead of the direct scalar session, and the
per-domain envelope - including the per-layer oracle transient while live -
is measured, not inferred from post-request counters.

## Changes

- `hipengine/runtime/qwen35_gguf_runner.py`:
  `prefill_batch_native`'s finally records the while-live oracle peak
  (`_int8_prefill_oracle_observed_peak_bytes/_owners`, monotonic) before the
  release clears the owners. This is required because /metrics scrapes block
  on the loop lock while a synchronous prefill runs, so out-of-process polling
  can never observe the oracle buffers mid-call (the first probe run showed
  exactly that: live gauges flat at zero through a 3 s prefill).
- `hipengine/generation/qwen35_gguf.py`:
  `prefill_transient_owner_inventory` reports the observed peaks (max across
  resident sessions) alongside the live-owner fields.
- `hipengine/server/api.py`: new gauges
  `hipengine_resident_packed_workspace_owner_sessions`,
  `..._leased_pool_bytes`, `..._prefill_oracle_owner_bytes/_owners`,
  `..._prefill_oracle_observed_peak_bytes/_owners`,
  `..._prefill_hidden_owner_bytes`, with descriptions stating the accounting
  domains.
- `scripts/gguf_server_allocation_probe.py` (new): spawns the real server
  (census flag shape, prefix/MTP off, capacity 1), waits for readiness,
  drives ONE /v1/completions request with the parity manifest's exact 2,048
  token IDs (two 1,024-row slabs; same deterministic spec for other
  --prompt-rows), polls /metrics at 50 ms for during-request peaks, and
  verifies clean SIGTERM teardown. Reports per-domain GiB separately: pool
  current/high-water/pinned, workspace owner-deduplicated, workspace leased
  pool planes, prefill oracle live + observed peak, hidden/bulk owners,
  request-owned KV after.
- `benchmarks/HARNESSES.md`: harness catalog row.
- Artifacts: 16K and 32K declared-context probe points.

## Validation

- W7900 GPU0, 27B Q4_K_M, int8_per_token_head + FP32 scales, AOTriton
  default on:
  - 16,384 declared: pass, clean teardown, request wall 3.06 s (2,048-row
    prompt + 8 tokens). Domains: pool high-water 0.579 GiB, pinned 64
    pages, workspace owner-deduped 0.947 GiB, workspace lease 0.508 GiB,
    **oracle observed peak 2.0 GiB / 16 owners**, hidden+bulk 0.273 GiB,
    request-owned KV 0 after the request.
  - 32,768 declared: pass, clean teardown. **Oracle observed peak 4.0 GiB**,
    workspace lease 1.016 GiB, pool high-water 1.087 GiB - the pool-backed
    oracle sizing scales linearly with declared context and doubles the
    direct engine's single shared pair (the F2+F3 amplification, now
    measured on the real route; at 32K the server pays ~6.4 GiB of
    route-specific transients vs the direct route's shared pair).
- The oracle peak equals pool-backed capacity (2x declared positions) x 4
  KiB/pair-position x 16 pairs, confirming the address-space coupling F3
  describes.
- Tests: server-api metrics nodes (incl. the new gauges) and
  packed-workspace-stability bundles green.
