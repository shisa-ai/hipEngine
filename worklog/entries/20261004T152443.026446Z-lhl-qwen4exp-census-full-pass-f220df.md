# The census's actionable set was incomplete, not just stale — and no token classifier can count this ledger

## Summary

Iteration 156 re-ran the ledger's open-candidate census by diffing the 18-row actionable set from
the 2026-09-30 census. This iteration ran the corrected anywhere-in-cell rule over **all 72 rows**
— the pass iteration 156 never did — and it produces two results that change how the campaign's
central question should be answered.

**1. The census's 18-row actionable set is incomplete, not merely stale.** Four rows outside it
have status heads reading `OPEN`:

| row | its own status head |
| --- | --- |
| **MT-2** | `OPEN for diagnostics; admission blocked` |
| **MT-6** | `OPEN, after MT-2` |
| **QA-6** | `OPEN — after memory/consumer census, independent of QA-2` |
| **X-4** | `...stable wall and serving-wrapper attribution still OPEN under X-10/DE-5` |

Iteration 156 inherited this gap by diffing only the 18 rows. A fifth row, **MT-3**, is correctly
outside it — its head reads `BLOCKED ... STILL BLOCKED, ON MT-2` — which is the check that the
four above are genuine omissions rather than my misreading.

**2. No token classifier can count this ledger, and this pass is the second demonstration.** The
first attempt (iteration 156) produced 51 "open" by swallowing rows whose tails carry no state
token. This attempt produced **49 closed / 16 open / 3 gated / 4 unknown** — and it is wrong in
both directions:

- **False positive: `X-7` classified CLOSED.** Its status cell reads **`NOT RESOLVED`**. A
  terminal-token matcher sees `RESOLVED`. Iteration 156 correctly called this row gated.
- **False positive: `QA-8`, whose status reads `NOT CLOSED`.**
- **False negative: `DP-6` returned "unknown"** for a status of `PARTIALLY PRICED (20260929T)` —
  a real state the token list does not contain.
- **22 of the 49 "closed" hits are negation-trap candidates** — a terminal token with a negation
  within 120 characters before it. Most are legitimate (`that claim IS WITHDRAWN`, `the signature
  figure IS SUPERSEDED`), which is exactly why the count cannot be trusted: the same pattern
  covers both a true closure and its opposite.

## What this means for the campaign's central question

Ledger §11 states the question in its own words: *"whether every candidate in this ledger has been
run through... a punchlist, not a single metric, so the answer is a classification of all 71 rows."*

**The classification cannot be done by counting.** Three attempts now — the 2026-09-30 census,
iteration 156's automated pass, and this one — have each produced a different answer, and the two
automated ones were wrong for opposite reasons. The ledger's status cells are 200-2000 character
prose that states closures, reversals, retractions and conditions in natural language; a token
matcher cannot separate `CLOSED` from `NOT RESOLVED`, and a positional rule cannot handle a cell
that opens with its conclusion (DE-1) or buries it (MX-1).

**The honest answer to "have we run through everything" is therefore: not determinable by a
census, and the two census-shaped answers on record both undercount.** The remaining work is a
**reading pass over all 72 status cells** — roughly 72 cell reads, not a metric. That is a
bounded, finite task, and it is the only route to an answer that will not need retracting.

## What is solid

Stripping the unreliable classifier, three findings from this campaign hold because each was
verified by reading:

1. **The three actionable speed candidates are all priced low-value.** DP-2 at 7.478 ms, QA-4 at a
   measured 3.02% ceiling at 64K, DP-6 at a 1.090% scope (85.791 ms ceiling). Every remaining
   speed candidate on the punchlist has a measured sub-2% ceiling. *(worklogs `20261004T152301`,
   `20261004T152356`)*
2. **§11's end-of-cell rule misclassifies DE-1**, whose cell opens with its conclusion. Corrected
   rule recorded. *(worklog `20261004T152356`)*
3. **§11's actionable set omits at least MT-2, MT-6, QA-6 and X-4.** New here.
