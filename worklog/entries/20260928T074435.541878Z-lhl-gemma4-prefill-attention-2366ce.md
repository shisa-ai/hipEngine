# the tiled kernel compiles and exports but produces mostly zeros and my test harness hid how much was failing

## Summary

Wrote the tiled production variant, compiled it, and ran it against the strict kernel.
**It builds and exports both symbols, and it produces wrong output.** The attempt is reverted;
this entry records what was built, the exact symptom, and a bug in the test harness that made
the first result look far better than it was.

## What was built

A `gemma4_attention_prefill_tiled_kernel<scalar_t, kTile, kDPerThread>` with `kTile = 1024`,
plus `launch_gemma4_attention_prefill_tiled` and two `extern "C"` entry points
(`hipengine_gemma4_attention_prefill_tiled_bf16` / `_f32`). **The `extern "C"` wrappers are
required for the templates to be instantiated at all** -- without them a build passes without
compiling the new code.

**Build result: OK, both symbols present.** The only warnings are pre-existing (line 182, the
strict kernel's unroll).

## The symptom

`keys=1024`, `window=0`, `tokens=8`, 16 heads, head_dim 256, n_kv 2:

```
strict nonzero=32768   tiled nonzero=576   tiled rows-with-data=8/8
maxrel = 2.65e+01      bit-exact = 84/32768
```

**The strict kernel fills all 32768 outputs. The tiled kernel fills 576 of them** -- about 1.8%,
spread across all 8 rows rather than confined to some. So it is not a missing row and not a
single wrong head; most of each row is zero.

## The harness bug, which matters more than it looks

My first run reported **four of five shapes "100% bit-exact"** and one failure. **That reading
was wrong.** `hipGetLastError()` is sticky: the tiled launch in the first case left an error,
and every subsequent case reported `err=1` while producing no output at all. **The later cases
were comparing a zero buffer against a zero buffer, which is trivially bit-exact.**

Re-running with the cases separated showed it plainly -- `strict nonzero=0` for three cases
that had been reported as passing. **Only one case actually executed.**

**So the honest result is not "four of five pass". It is: one shape executed, and it failed.**
The other four are untested. **A test that reports success when both kernels fail to launch is
worse than no test**, and this is the second harness-level error in this stretch after the
filename-as-coverage-map mistake.

## What I did not find

I did not locate the defect. The shared-memory layout is consistent (`q_s[head_dim]`,
`tile_s[kTile]`, `partial[256]`, `shared_bytes = (head_dim + kTile + threads) * 4 = 6144`),
`kGemma4AttentionMaxThreads` is 256 as assumed, the tile loop's warp mapping covers every index
(`i = warp; i < tile; i += 8` over 8 warps), the phase barriers are in the right places, and
`running_sum += weight` is outside the `weight != 0` guard. **The one place I would look first
is the interaction between `gemma4_attn_block_max` inside the tile loop and the final
`gemma4_attn_block_sum` both using `partial` as scratch** -- they are separated by a
`__syncthreads()`, but I have not verified that the helpers are re-entrant across iterations.
