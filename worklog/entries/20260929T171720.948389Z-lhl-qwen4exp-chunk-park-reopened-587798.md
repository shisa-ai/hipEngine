# The parked chunk-selection rationale: resume condition met, one premise falsified

## Summary

`docs/REFACTOR.md` parks automatic prefill-workspace chunk selection with two
named resume conditions. **One is now met**, and re-measuring its two premises
this session shows **one is falsified and one is correct for the comparison it
actually made**.

I found this by reading the park entry after my own suite measurement, not by
looking for it. It reframes RT-1: the interesting lever is not "raise 4096" but
the **256** default that the recorded tradeoffs never examined.

## What the park says

- Best case: "the 4K prefill gain already measured for the explicit options
  (2.32-3.94%), against short-request regressions of 0.18-0.40%".
- Resume only after gap-attribution ranks it back into the top of the
  seconds-recoverable list, **or if a default chunk change makes the ownership
  split load-bearing**.

## Resume condition met

The serving path's chunk default is **256**
(`EngineLoopConfig.max_prefill_chunk_tokens`), not the 1024 these tradeoffs
assume. A default chunk change is therefore exactly the live question - the
second named resume condition.

## Premise 1 falsified: the short-request regression does not reproduce

A 512-token request is **byte-identical** in wall time and peak allocation at
chunk 1024 vs 4096: medians 2.0074 vs 2.0114 s (+0.20%, which is 0.08x the
within-arm spread, arms overlapping), peak 83,857,109,608 B in both arms.

Mechanism, verified at the call site: `rows = min(chunk_size,
max_sequence_length)` and `max_sequence_length = max(768, prompt_tokens + 1)`, so
a 512-token prompt resolves to 768 rows at both chunk sizes. The workspace is
**already shape-aware**; the recorded 0.18-0.40% is not reproduced here.

## Premise 2 correct as stated, but measured against the wrong baseline

The 2.32-3.94% is a **1024 -> 2048/4096** figure, and we measure -4.94% for
1024 -> 4096 - the same order. The park was not wrong about that comparison.

What was never measured is the **256** baseline the serving path actually uses.
Measured across all 12 fixture cases: **256 -> 4096 is -28.2% to -37.6%**,
monotone in prompt size, flat across all four categories, 12/12 completely
separated.

So the lever is far larger than the park assumed, and its cost is confined to
peak memory (+0.77 / +1.24 / +6.20 GB at p512 / p1024 / p4096) rather than
short-request latency.

## Still not enabled

The park's qualification prerequisites are unchanged and unmet: full
state/lifetime and c2 behavior, accounting for all owners and host staging in
public construction, preserving strict setup, and short/long requests on the same
prepared owners. The reserve check is still not public memory admission.

Recording the resume condition as met is a claim about the *question*, not a
claim that the mechanism is ready. Enabling an unqualified selector on the
strength of a timing measurement would be the same over-reach I have been
correcting all session.

## Next

Measure **256 -> 1024 in a single run** - both arms, all 12 cases - because
`REFACTOR.md` explicitly forbids claiming a direct comparison from separate runs,
and the cross-run arithmetic (256 -> 4096 = -38% while 1024 -> 4096 = -4.94%)
implies 256 -> 1024 carries most of the value at a quarter of the memory cost. If
that holds, the promotion candidate is 256 -> 1024, which is also already the
documented global default - meaning the serving path sits *below* documented
policy. That run is launched (`bg-51`).
