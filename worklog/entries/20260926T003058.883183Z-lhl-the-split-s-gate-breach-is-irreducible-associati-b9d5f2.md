# The split's gate breach is irreducible association reordering, not a defect: phase 1 verified faithful

## Summary

Diagnostic, no product change, and it closes the mechanism question left open by
iteration 37. The two-phase decode split's divergence from the strict path is a
**pure association reordering** of the weighted-V sum: phase 1 hands phase 2 the
incumbent kernel's own f32 weights, the workspace is f32, and the difference is
present at the minimum split (2 slices) with the same magnitude as at 16. It
cannot be made bit-identical, because pass 3 is a strictly sequential f32 chain
and any parallel split of that range reassociates it by construction. What
remains is a decision about how much the reordering matters, which is the lead's.

## Changes

None to any product path. Two fixes to the harness added in iteration 36:

- `force_slices` patched a one-argument lambda while the launchers call
  `decode_slices(keys, head_dim)`. The unit test passed because it called the
  patch with one argument; every real launch would have raised `TypeError`. Found
  by running the harness, fixed, and pinned by a new test that calls the patch
  the way the launchers do.
- The campaign document records the mechanism.

## Validation

Read from `hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention.hip`:

- Pass 2 computes `weight = expf(logits_s[j] - row_max)`, stores it back into
  `logits_s[j]`, and reduces the denominator with the tree pinned to
  `kGemma4ReduceThreads` (256) so its addition order matches the block kernel's.
- The split stores exactly those weights (`split_weights[head_index * keys + j] =
  logits_s[j]`) plus a `(denominator, row_max)` header. So every slice's summands
  are bit-identical to the incumbent path's - the design claim holds.
- The workspace is `float` throughout (`float* __restrict__ split_weights`; the
  sizing function multiplies by `sizeof(float)`), so there is no precision
  round-trip.

Measured against the same frozen strict baseline (1023 paired rows, keys
1025-2047):

| slices | kl_p99 | kl_p99.9 | kl_max | rows>1e-3 | rows>0.05 | median max\|dlogit\| |

| 4 | 3.955e-05 | 3.611e-02 | 5.559e-02 | 2 | 1 | 1.085 |

Per-row KL correlation against the 4-slice arm: 0.790 at 2 slices, 0.987 at 8,
0.821 at 16. Row 864 measures 0.056-0.060 in all four arms. A 2-slice combine
can differ from the single kernel's chain by one rounding step, so a shared
one-logit difference at 2 slices localises the source to the split's existence,
not its width.

## Next

- **The mechanism question is closed; the policy question is the lead's.**
  Making phase 2 bit-identical is not available: pass 3 is a strictly sequential
  f32 chain over ascending keys, and any split of that range computes partial
  sums in parallel and combines them, which reassociates the sum by construction.
  A higher-precision accumulator would still not be bit-identical to the strict
  f32 chain. The remaining options are to accept the split under the aggregate
  bars plus top-1 - p50 row KL 2.592e-08, p90 1.040e-06, p99 3.955e-05 against
  bars of 1e-3, 5e-3 and 2e-2, with top-1 rate 1.0 and zero flips on all 1023
  rows - and treat an absolute `kl_max` as inapplicable to a reordering-class
  change; or return the strict path as the default.
- If the split is accepted, the reverted slice-count table is worth +5.3% at the
  metric row and +7.4% at 4096p and should be re-landed with it.
