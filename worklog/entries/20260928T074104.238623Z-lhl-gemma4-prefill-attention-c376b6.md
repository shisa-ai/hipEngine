# the current kernel does four lds operations per key not three because pass 2 stores the weight back

## Summary

Reading the kernel body to write the production variant found **my own LDS accounting wrong in
the previous entry.** The corrected ratio is better than I claimed, and the entry that
recommended the two-variant split rests on a number that was too pessimistic.

## The correction

`20260928T074031` said the current kernel does three LDS operations per key visit
(write + read + read). **Pass 2 also writes the weight back over its logit** -- the comment
says so explicitly:

> Pass 2: denominator, storing each weight back over its logit for pass 3.
> ...
> Pass 3 then reads the weight instead of recomputing expf per (element, key)

So the real count is:

| | ops per key visit |
|---|---|
| pass 1 -- write the logit | 1 write |
| pass 2 -- read the logit | 1 read |
| pass 2 -- **store the weight back** | **1 write** |
| pass 3 -- read the weight | 1 read |
| **total** | **4** |

And the tiled production variant is **2** (phase 1 writes the logit, phase 3 reads it once and
keeps the weight in a register for that thread's output element).

**So the reduction is 4 -> 2, a 50% cut, not the 33% the previous entry stated.** That entry's
calibration note -- that a 33% LDS cut cannot explain a 60x headroom -- **still holds a
fortiori at 50%**, so its conclusion is unaffected. But the number was wrong and the plan's
expectation should carry the right one.

## The counterweight this exposes

**The tiled variant adds barriers.** The current warp-per-key path has three barriers in
total (after the query load, after the block max, after the block sum). The tiled variant
needs two per tile, so at 2048 keys with a 1024-key tile that is four plus the query load --
**five, against three.**

**So the production variant trades LDS traffic for barrier count**, and which dominates is an
empirical question, not a derivable one. **That is now the thing to measure first**: if the
tiled kernel is not faster, the barrier count is the first explanation to test, and the fix
would be a larger tile (fewer barriers) rather than a different algorithm.

## Validation

Read of `gemma4_attention.hip`: pass 1 writes `logits_s[j]` (lines 245-252, 270-272), pass 2
computes `weight = expf(logits_s[j] - row_max)` and assigns `logits_s[j] = weight` (lines
302-306), pass 3 reads `logits_s[j]` as the weight (lines 313-320). The barrier count comes
from `__syncthreads()` after the query load (211), after `gemma4_attn_block_max` (281), and
after `gemma4_attn_block_sum` (308).
