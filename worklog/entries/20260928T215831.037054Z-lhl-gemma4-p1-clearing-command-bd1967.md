# P1's blocker, read from the header we ship

## Summary

Reading `aotriton/flash.h` from the vendored runtime answers two questions
P1 had only ever answered by measurement, and changes what its clearing
command should be. The window-alignment miss is a **compile-time exclusion
upstream has kept in place for three feature releases**, so no future
release will clear it — and the alignment markers it does ship are
documented as **varlen-specific**, which is a configuration P1 never tried.

## Fact 1: the alignment types are deliberately not compiled

```cpp
// TopLeftAligned and BottomRightAligned are supported in Triton kernel, but
// not compiled into the binary GPU kernels
struct AOTRITON_API CausalType {
  static constexpr int8_t None = 0;
  // static constexpr int8_t TopLeftAligned = 1;
  // static constexpr int8_t BottomRightAligned = 2;
  static constexpr int8_t WindowedAttention = 3;
};
```

This is why both the vendored `0.11.2b` and the `0.14.2b` gfx110x image sets
carry `CAUSAL_TYPE ∈ {0, 3}` — iteration 23 saw the symptom, the header gives
the cause. It also sharpens iteration 23's conclusion: X4 reported the domain
as *unchanged*, which could read as "upstream might still fix this." The
header says otherwise — the code exists in their Triton source and is
**commented out of the binary build on purpose**, and has stayed that way
from 0.11.2b to 0.14.2b. Waiting for a release is not a plan.

## Fact 2: the window markers are "Special value for varlen"

```cpp
struct AOTRITON_API WindowValue {
  static constexpr int32_t TopLeftAligned = -2147483647;      // Special value for varlen
  static constexpr int32_t BottomRightAligned = -2147483646;  // Special value for varlen
};
```

P1's sweep reported an otherwise puzzling result: `window_right` at the
`BottomRightAligned` sentinel gave bottom-right alignment but **"the sentinel
carries no bound"**, and `window_left` then had no effect at all. The
header's four-word comment explains it — a varlen marker in a **non-varlen**
launch has no `cu_seqlens` to derive a bound from, so it aligns and then has
nothing to align *to*.

And `aotriton_wrap.cc` already exposes that mode:

```cpp
extern "C" int hipengine_aotriton_attn_fwd_v3_compact_varlen(
    ..., const HipengineAotritonTensor1* cu_seqlens_q,
         const HipengineAotritonTensor1* cu_seqlens_k, ...);
```

## The revised clearing command

P1's old command was *"install a runtime whose windowed images take absolute
or bottom-right bounds."* Iteration 23 has since shown no such runtime ships
or is coming, so that command cannot be executed — a gate nothing can clear.

**Revised: re-run the same four-mask comparison through
`hipengine_aotriton_attn_fwd_v3_compact_varlen`, with
`window_left = WindowValue::BottomRightAligned` and real `cu_seqlens`, so
the sentinel has a length to work against.** Same discriminating shape
(`rows=512 keys=1536 window=128`), same four candidate masks, same scores.

This is a **hypothesis, not a result**, and P1's row now says so. Three
outcomes, all acceptable: the masks resolve bottom-right and the plumbing
can be restored with a flip observed first; they still resolve top-left and
the miss is confirmed structural, leaving P2's option (a) as this gap's only
route; or varlen does not bind the window at all, which is itself the answer.
The plumbing restores only after a flip.
