# the gate up grid is 44 by 8 and the traces 5632 was grid x times the block size

## Summary

`20260928T090757` left one integer open: is the MoE gate/up MMQ's `grid.x` 44
or 5632? **It is 44. The 5632 was my own units error -- rocprofv3's
`grid_size_x` is work-items, not workgroups.**

I settled it by instrumenting the launcher instead of reading more code. A
temporary `HIPENGINE_DBG_GRID` print after the `dim3 grid(...)` definition at
`gguf_q4_k_q8_1_selected_prefill.hip:4994`, one decode, then reverted:

```
     58 [dbg-grid] ofa=704 ofb=704 ne=128 total_rows=256 grid=(44,8)  compact_rows=8  in_features=2816
      6 [dbg-grid] ofa=704 ofb=704 ne=128 total_rows=672 grid=(44,21) compact_rows=40 in_features=2816
      5 [dbg-grid] ofa=704 ofb=704 ne=128 total_rows=608 grid=(44,19) compact_rows=40 in_features=2816
      3 [dbg-grid] ofa=704 ofb=704 ne=128 total_rows=736 grid=(44,23) compact_rows=40 in_features=2816
      3 [dbg-grid] ofa=704 ofb=704 ne=128 total_rows=480 grid=(44,15) compact_rows=40 in_features=2816
```

**`grid.x` is 44 in every call, and `out_features_a = out_features_b = 704` is
what the caller passes -- exactly what reading the source said.**

## The error, and why it survived two iterations

The same trace reports `grid_size_x = 5632` with `workgroup_size_x = 128`:

```
5632 = 44 * 128 = grid.x * workgroup_size_x
```

**`grid_size_x` is the x extent in work-items.** `grid_size_y` is not scaled --
and that is the tell I had in hand and did not use: the trace's `grid_size_y`
matched the source's `mmq_total_rows / 32` exactly at every point (`256 -> 8`,
`672 -> 21`, `608 -> 19`, `736 -> 23`, and the instrumented run reproduces the
trace's counts per value). **One column agreed with the source and one did not,
and I spent two iterations trying to explain the disagreement instead of asking
why the agreeing column agreed.** A units mismatch in one column and not the
other is a units mismatch, not a mystery.

The arithmetic that made 5632 look plausible is what kept it alive: `5632 = 44 *
128 = grid.x * num_experts`, and gemma4 has exactly 128 experts. A coincidence
between the block size and the expert count is not evidence.

## What this closes

**The over-launch lead is dead.** There is no 128x block over-launch and no
cheap fix there. The grid is 44 column-tiles by 8 row-tiles = **352 blocks**, of
which every one does useful work.

That makes `20260928T090630`'s second branch the live one, and it is a harder
problem: the gate/up streams 17.8 MB per layer in about 244 us -- **73 GB/s
against the dense q8_0 path's 199** -- on 352 blocks, and `20260928T090630`
established it is not arithmetic-bound. Each block runs a K-loop of
`2816 / 32 = 88` iterations and each iteration loads a 32x32 weight tile, about
576 bytes, behind a barrier. **576 bytes per block per iteration is the number
to attack**, not the block count.

## Also worth carrying forward

`compact_rows = 8` against `total_rows = 256` on a single-token decode, and
`grid.y = 8` -- so 8 row-tiles carry 8 real rows, one per expert, and 248 of the
256 rows are padding the kernel skips. That is the padding geometry
`20260928T090630` refuted as a cost, and the instrumentation confirms the shape
of it: the row dimension is 97 percent padding and the kernel's early-out is
what keeps it free.

## Next

The gate/up's 73 GB/s. **Load more per block per K-iteration.** The column
tile is fixed at 32 by `grid.x = out_features_total / 32`, but the *rows* are
not: a block could take more than one 32-row tile, which would read the same
weight tile once for more rows and would raise bytes-per-barrier without
changing the grid. That is the same move `20260928T084954` proposed for the
decode path and it is worth trying here with the padding geometry in hand --
with one real row per tile the arithmetic stays free, so the only question is
whether the extra rows are free too.
