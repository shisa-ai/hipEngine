# Gemma 4: route the Q8_0 expert layer through its grouped family

## Summary

The route attribution for the 512-token prefill showed two dense projections
running the per-row expert gather instead of a grouped kernel: one Q5_K and one
Q8_0, one launch each, **314.8 ms** together, where a grouped layer costs about
40 ms for the same shape. The cause is that this artifact is an unsloth dynamic
quant: one MoE layer carries Q5_K gate/up and Q8_0 down weights while the other
29 layers are Q4_K/Q5_1.

The Q8_0 half is fixed. Its grouped family already existed and was already
implemented, but was registered only under the dense `linear` layer, so the MoE
route — which resolves `moe_linear` — could never find it. Binding it under
`moe_linear` and naming the variant last in `_GROUPED_PREFILL_VARIANTS` takes
that projection **68.13 -> 37.19 ms (1.83x)**, bit-exactly.

## Changes

- `hipengine/kernels/hip_gfx1100/quant/gguf_q8_0_prefill.py`:
  `register_gguf_q8_0_prefill_kernels` also binds
  `selected_grouped_prefill_compact_bf16_bf16_out` under `moe_linear`.
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_experts.py`:
  `_GROUPED_PREFILL_VARIANTS` gains
  `selected_grouped_prefill_compact_bf16_bf16_out` last, as the fallback for a
  quant whose family has no staged or rowbatch8 variant.
- `tests/test_unit_gemma4_expert_route.py`: a `gguf_q8_0` case with four
  geometries, including the artifact's own 704 -> 2816 down shape, plus a fix to
  the cleanup path's unbound `extra_outputs`, which had been turning route
  failures into `UnboundLocalError`.

## Validation

- **RED first.** With the Q8_0 case added but the variant still unreachable, the
  new parametrization failed with "the gguf_q8_0 grouped family did not resolve
  on this backend". 44 pass after the change.
- **Bit-exact, not tolerance.** The grouped route reproduces the selected GEMV's
  association (column = t, t + blockDim.x, ... through the same tree), so the
  test compares bf16 bits. Four geometries, four experts with one empty, so the
  comparison also pins that row order follows `expert_start`.
- **In-run A/B.** One process, both routes resolved, five timed launches per
  round, two interleaved rounds, synthetic Q8_0 weights at the artifact's
  geometry: 68.13 -> 37.19 ms and 68.17 -> 38.64 ms.
- **The route actually changed.** Re-running the attribution over a real
  512-token forward shows
  `moe_linear/gguf_q8_0/selected_grouped_prefill_compact_bf16_bf16_out` at
  43.4 ms, and the `linear/gguf_q8_0/selected_gemv_bf16_bf16_out` row is gone.
- No separate generation-parity arm: the routes are bit-identical at the kernel
  level, which the device test pins, so a token-id comparison could only restate
  it.

## Next

- **The Q5_K half is the larger one and is still open.** That layer's expert
  gate/up (fused, 244.4 ms) has no exact grouped family: the only Q5_K prefill
  routes that exist are `selected_wmma_prefill_compact` and the MMQ family, both
  of which change the association and therefore need the numerical gate. The
  exact options are a new grouped Q5_K kernel or the Qwen35 dual gate/up prefill,
  which needs the compact scheduler ABI (`expert_start_compact`,
  `expert_start_wmma`, `tile_expert`) that the Gemma 4 MoE path does not build.
  Expected value if grouped cost holds: about 200 ms of a 3.29 s prefill.
- The Q8_0 family's WMMA grouped variant is a gate candidate, not a bit-exact
  route.
