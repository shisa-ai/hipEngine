# gfx1100 rdna3 transfer packet G MTP width depth reject

## Summary

Audit packet G closes **rejected with a concrete blocker**.
`GGUF_SPECDEC2_MTP2_PHYSICAL_WIDTH_DEPTHS` is unchanged on `hip_gfx1100`. No
width qualifies for addition: the only engageable production cell (width 8)
does not beat its own AR arm on this host today, and candidate widths 3/4
cannot be admitted by the two policy tables alone. The packet also found that
the retained C8/K3 automatic 1.1178x row does not reproduce at its own commit.

## Changes

- No capability changed. The width-3/4 experiment was made and committed only
  inside a temporary worktree, which was removed; `main` never carried it.
- `benchmarks/README.md`: the C8/K3 automatic MTP row is marked under review

## Validation

All runs: physical W7900, Qwen3.8-27B `Q4_K_M` BF16 KV, canonical 10-prompt
`benchmarks/prompts/mtpbench-code-general-ja.jsonl`, D24, candidate budget 3,
20 ms batch window, greedy, `ar_exact` contract, each MTP arm paired with a
same-process AR arm over the same prompts.

- **Width 8 does not beat AR.** Six engaged runs, ratio MTP/AR:
  - explicit mode r1 0.9939, r2 0.9929
  - automatic mode r1 0.9939, r2 0.9942
  - automatic with `GPU_MAX_HW_QUEUES` unset 0.9932
  - automatic at retained commit `c1bb38d49` 0.9919

  All 10/10 exact with `route_expectation_passed`. The result is stable across
  request mode, queue configuration, and source commit.
- **Widths 1 and 2 never engage** at resident capacity 8 (engaged 0/10): the
  production route is scoped to the physical C8 serving key, so those table
  cells are unreachable in this configuration. Their apparent 0.96-0.98 ratios
  compare two AR-equivalent arms and are not MTP-versus-AR evidence.
- **Widths 3 and 4 are blocked.** Extending both
  `GGUF_SPECDEC2_MTP2_PHYSICAL_WIDTH_DEPTHS` (adding (3,2),(3,3),(4,2),(4,3))
  and `GGUF_SPECDEC2_PHYSICAL_PROMPT_STREAMING_POLICIES` (dense key to
  (1,2,3,4,8)) in an isolated worktree still gives engaged 0/10 at resident
  capacity 4 and at capacity 8. The automatic serving-evidence resolver
  declines these widths for a reason beyond the two policy tables, so admitting
  them is a resolver change rather than a policy fill. This is the packet's
  blocker.
- The remaining qualification battery (delayed admission, retirement,
  cancellation, compaction, isolation, deterministic repeats, task quality,
  memory recovery, production load gate) was **not** run, because no candidate
  cell reached the engagement precondition that would give those gates meaning.
  Recorded rather than silently skipped.

### Retained C8/K3 row does not reproduce

Re-running the retained row's own source commit `c1bb38d49` today, in a
throwaway worktree, measured **MTP 91.884 / AR 92.631 (0.9919x)** against its
recorded **98.643 / 88.250 (1.1178x)**
(`benchmarks/results/2026-09-05-w7900-q4km-k3-c8-automatic-promotion.json`).

Controls that match between the fresh run and the record, and between the old
commit and HEAD:

- model sampled fingerprint `2512f262...` and size identical;
- runtime-profile manifest `2adc137a...` identical to the retained run;
- protocol identical (suite, width, resident capacity, budget, horizon, batch
  window, sampling);
- acceptance ledger **byte-identical** between HEAD and `c1bb38d49`:
  504 cycles, 1,512 proposed, 1,168 accepted, draft acceptance 0.772487.

So the MTP arm performs the same work at both commits, and this is **not a
regression from any packet retained in this campaign** — the pre-campaign
commit measures the same ratio today as HEAD. At a fixed commit the two arms
moved in opposite directions relative to September (AR faster: 92.631 vs
88.250; MTP slower: 91.884 vs 98.643). Code, model, manifest, request mode,
queue count, and acceptance are excluded; the cause is environmental or
temporal and is **not resolved here**.

Disposition: the row is flagged in `benchmarks/README.md`, not deleted, and no
replacement rate is claimed. It needs its own investigation.
