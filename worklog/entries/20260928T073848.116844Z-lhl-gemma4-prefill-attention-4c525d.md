# a tiled online softmax prefill attention kernel already exists in this tree so the fix is a port not a write

## Summary

Five entries have treated the prefill fix as a kernel to be written. **It already exists.**

`hipengine/kernels/hip_gfx1100/attention/laguna_flash_attention_prefill.hip`, **498 lines**,
is a tiled online-softmax flash-attention prefill kernel with the structure
`20260928T073623` derived from first principles -- including the rescale that was the whole
point of the plan.

## The structure matches the plan

| plan (`20260928T073623`) | existing kernel |
|---|---|
| size the weight buffer by tile, not by keys | `TILE_COLUMNS = QUERY_ROWS * GQA_HEADS`, `shared_tile[HEAD_DIM + K_PAD]` |
| process keys in tiles | `for (int key_tile = 0; key_tile < K_BATCH / 16; ++key_tile)` |
| keep a running max | `float running_max = -INFINITY;` (line 166) |
| rescale the accumulator when the max grows | lines 265-271, below |
| reuse the buffer per tile | `__syncthreads()` around each tile load |

The rescale, verbatim:

```cpp
const float next_max = has_data ? fmaxf(running_max, batch_max) : 0.0f;
// A causal query tile can exhaust its visible keys before the shared
// ...
    : isfinite(running_max) ? expf(running_max - next_max) : 0.0f;
...
    has_data && isfinite(score) ? expf(score - next_max) : 0.0f;
...
running_max = has_data ? next_max : running_max;
```

**That is online softmax, with the first-tile guard already handled** (`isfinite(running_max)`
covers the `-INFINITY` start).

## Why this changes the job

The estimate was "write a ~200-line kernel". It is now "**adapt 498 existing lines**", and
the adaptation is the part that is specific to Gemma 4 rather than the part that is hard:

- **head_dim** 256 and 512 (Laguna's constant is a different width);
- **the sliding window and `gemma4_attn_first_kept`**, which the existing kernel has no
  equivalent of -- it is a causal-only kernel;
- **the bit-identical `gemma4_warp_key_logit` requirement.** `gemma4_attention.hip`'s comment
  says its warp reduction is "bit-identical to the block kernel's over the same values" and
  that "the parity test catches it". **A port must keep that reduction, not replace it with
  WMMA fragments**, or the parity test will fail for reasons that have nothing to do with the
  tiling.
- **the `KVLiveSpans` ABI** -- `(base_offsets, live_counts, token_positions, evict_mask)` is
  the attention kernel ABI per `AGENTS.md`, so the port must read spans rather than assume a
  dense causal range.

**Note the tension:** the existing kernel gets much of its speed from WMMA fragments, while
Gemma 4's parity contract pins the logit reduction. **A port cannot take both.** The
question to answer first is whether the Gemma 4 parity test constrains the *logit bits* or the
*final output*; if it is the logit bits, the WMMA path is unavailable and the port is the
tiling alone.

## What this does not change

- The diagnosis (`20260928T073550`): three passes, one LDS round trip per key visit.
- The ceiling and its confirmation (`20260928T073623`, `20260928T073705`).
- The two separate payoffs and the need to measure at both lengths (`20260928T073811`).
- The gate: a **tolerance**, not exact equality, because the cross-tile rescale reassociates.
