# Qwen4Exp fork-idea audit: covered vs remaining

## Summary

Audited the apepojken `qwen4exp-spec-mtp` fork's headline fixes against our
in-tree implementations. Most are already covered independently; the two
real remaining campaigns are the MoE MMQ cooperative prefill dataflow and
batch-invariant MTP verification.

## Changes

- No code changes; audit recorded here and reflected in
  `docs/QWEN3.8-FLASH-NEXT.md` section 0.3.

## Validation

Covered in-tree (verified in source, with prior retained evidence):

- GPU radix top-k: `qsa_topk_expand_f32_i64_kernel` in
  `hipengine/kernels/hip_gfx1100/attention/qwen4_exp_qsa.hip` already does an
  exact stable 8-bit radix select (256-bin histogram passes, exact kth
  threshold with tie handling) on device; no CPU fallback at any width. The
  fork's radix port fixed a llama.cpp-only CPU argsort fallback.
- Incremental pooled-key cache: persistent `pooled_keys` device buffer is
  write-once per complete 4-token block (`qsa_prepare_index_keys`, block
  completion gating); the fork's +17% at 32k fixed llama.cpp recomputing all
  block summaries per token.
- Gathered decode attention: `qsa_sparse_attention_*` kernels already consume
  per-query `selected_positions` (~2,048-token budget) instead of dense+mask.
- GDN conv concat: our Conv path is the registered decode-order-exact K4 bulk
  kernel (`7ef8b7388`); no non-contiguous concat remains in the runner (only
  host-side numpy concats for MTP hidden-seed capture).
- Permute-free indexer scoring: no permute/transpose on the QSA scoring path;
  scoring is chunk-batched exact.
- MTP combiner: `_fuse_inputs` packs per-branch
  `[norm(embedding) | norm(hidden_branch)]` rows through the fused sidecar
  `eh_proj` and runs the full 4-branch hyper-connection draft layer with
  distinct streams; there is no naive mean anywhere. The fork's 0.47-acceptance
  mean bug does not exist here. Greedy identity (AR-identical MTP IDs) is
  already an enforced gate (10/10).

Remaining (the actual campaigns):

1. MoE MMQ cooperative prefill dataflow: llama.cpp pp508 Q4_K/Q5_1/Q8_0 MMQ
   total 1.226 s over 638 launches (MFMA integer pipeline, one kernel per
   MoE GEMM) versus our 8.753 s total; our grouped owner dequantizes to float
   and contracts with scalar FMA. `gguf_q4_k_mmq_prefill`/
   `gguf_q8_0_mmq_prefill` infrastructure exists in-tree but is not the
   Qwen4Exp grouped-MoE route. Chunk-size sweep (256 vs 512 vs 1024, their
   `-ub 2048` gave +10%) is a cheap first measurement.
2. Batch-invariant MTP verify: verification is a serial per-candidate
   `target.step()` loop (budget 1..4), so each drafted token costs a full
   target decode row. The earlier multirow candidate was rejected because
   `rows >= 2` routes MoE into the grouped-prefill dataflow whose arithmetic
   differs from the rows=1 decode GEMV (batch-composition invariance failure,
   changed a continuation token). The fix is a rows<=8 verify path whose
   per-row bits equal serial decode - either per-row decode-order kernels
   packaged into one launch (honest: same tree, fewer submissions) or a
   proven bit-equal batched kernel - then sweep budget 4->6 as the fork's
   n-max 6 with verify <=8 suggests.
3. Skinny-GEMM routing (their m=4 inject fix): our GR/PLE projections are
   batched per prefill chunk (m=chunk, not m=4); no analogous pathology
   found. Revisit only if a trace shows a thin GEMM on a tiled path.
