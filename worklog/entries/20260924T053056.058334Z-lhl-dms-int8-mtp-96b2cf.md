# DMS prefill kept last_target_hidden pointing at released scratch

## Summary

Building #12's live harness surfaced a hard defect on the first DMS MTP attempt:
`Qwen35GGUFTransactionalVerifier.prepare` segfaulted inside the state
journal's initial-state snapshot. The bulk prefill publishes the final trunk row
as `_last_target_hidden_ptr` from bulk scratch, and
`_finalize_external_dms_prefill` releases that workspace before returning, so
`last_target_hidden` handed the journal a raw pointer into freed device memory.
`Tensor.from_handle` cannot detect that, and the D2D copy read it.

Fixed by retaining the row in the session's persistent hidden buffer
(`_hidden_a`, one BF16 row, already allocated for exactly this purpose) before
the release. The DMS MTP cycle now runs and matches the AR oracle.

## Changes

- `hipengine/runtime/qwen35_gguf_runner.py`: new
  `_retain_published_target_hidden`, called from
  `_finalize_external_dms_prefill` immediately before
  `_release_bulk_prefill_workspace()`. It copies the published row into
  `_hidden_a` and repoints `_last_target_hidden_ptr` at it, and is a no-op
  when no row was published or the pointer already names that buffer.
- No flag, no fallback: the DMS serving path keeps publishing a valid trunk row
  for its whole lifetime, which is what `last_target_hidden`'s own contract
  already promises ("valid until the next target forward overwrites its
  scratch").

Two further defects found while reaching that point, both still open and
recorded here so they are not lost:

1. **DMS + INT8 dense KV storage produces NaN logits on the first decode step.**
   `FixedPagedKVPolicy(storage_dtype=INT8_PER_TOKEN_HEAD)` with an external DMS
   sidecar attaches and prefills, then `step` raises
   `FloatingPointError: GGUF resident lm-head logits contain NaN or Inf`. The
   same session with the auto-resolved BF16 dense policy decodes correctly, so
   the trigger is the dense KV dtype. The DMS pack consumes
   `self.scratch.full_cache(physical_layer)` directly, so an INT8 dense layout
   feeds it bytes it does not interpret. The DMS serving scripts never pass an
   INT8 `kv_policy`; "DMS+INT8" in the readiness doc means the quantized DMS
   payload and scales (the codec), which is the arm that works.
2. **`target_verify_mode="native"` cannot run on a DMS session.** It reaches
   `verify_target_block` and raises `RuntimeError: GGUF resident bulk prefill
   buffers are closed`, because the DMS prefill releases that workspace.
   `serial_exact` is the mode that works, which matches the journal's
   serial-capable design note.
