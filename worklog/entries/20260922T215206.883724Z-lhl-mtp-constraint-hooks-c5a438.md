# Text-keyed output constraints through sampled speculative MTP

## Summary

Task 8's second half. `json_object_close_forcing` and `tool_call_constraint` are
served by the sampled MTP route, and a json_object request publishes the
autoregressive arm's ids token for token, closing its object at the budget.

These two are the text-keyed family: their hook reads the *decoded text* of the
token a request emitted. It advances a JSON/tool DFA, masks the row's support
from that DFA state (`accepts_token_text` through
`processed_distribution`'s `token_allowed`), and -- when the remaining decode
budget is exactly the length of the closing suffix -- queues that suffix as
forced tokens. The row walk observed token ids only, so inside a cycle the later
rows were masked against a DFA that had not seen the earlier rows' tokens. The
regression test pins the defect in both directions: the child row of a cycle
could not close the object it was inside, and could open a second one.

## Changes

- `hipengine/generation/mtp_sampled_accept.py`: `_row_prefix_walk` takes an
  optional `observe_text(state, token_id, depth)` and calls it for each candidate
  row after observing the parent's token, so the row's state carries the DFA
  state `_process_row` would see at that point of an autoregressive decode.
  `row_prefix_states`, `sampled_accept_summary`, `chain_token_logprobs`, and
  `observe_published_tokens` all thread it. The logprob path takes the same
  observer because a constrained row's reported value comes from the same mask
  the accept used: scoring it against an unobserved state could report `-inf`
  for a token the cycle published.
- `hipengine/generation/qwen35_gguf_mtp2.py`: `_constraint_text_observer` builds
  the observer from the tokenizer and the cycle's remaining decode budget.
  `depth` is the number of tokens published before the row's own token, so
  `remaining_decode - depth - 1` is the budget the autoregressive route compares
  the closing suffix against. The commit observes the published tokens' text into
  the live state, one autoregressive step per published token, so the live DFA
  and its queued suffix advance exactly as they would have on the AR route.
- `hipengine/generation/sampling.py`: `constraint_skips_token_text` is the shared
  EOS rule (the AR route observes no text for an EOS token under a constraint),
  so the two routes cannot drift. `json_object_close_forcing` and
  `tool_call_constraint` move to `SAMPLED_MTP_SERVABLE_BLOCKERS`;
  `SAMPLED_MTP_UNSERVABLE_BLOCKERS` is now `("thinking_budget",)`.
- `docs/reference/SAMPLING.md`: the blocker paragraph now names the text-keyed
  constraints as served and `thinking_budget` as the only refused field.
- `scripts/mtp_forced_token_gate.py`: a `json_object_close` case, and a fix the
  case exposed -- `_run_arm` built its fields from `_forced_ids` alone, so a
  case's own `extras` never reached the request and a case carrying a sampler
  field would have tested nothing.
- Tests: the walk/commit/logprob observers, the depth arithmetic, and the
  constraint-masking regression in both directions; the partition and
  server-route tests move the two fields and keep `thinking_budget` as the
  refused case.

The json_object case published `\n\n{"city":"Kyoto","unit":"Celsius"}` -- a closed
object at exactly its 12-token budget -- with identical ids on both arms, and the
speculative arm reported `execution_path=gguf_specdec2_mtp2`. The gate asserts
that closure, which is the observable effect of the constraint's closing suffix;
the autoregressive arm runs the same rule, so parity is the claim, not the suffix
itself.

## What is still refused

`thinking_budget`, with its cause and clearing command in
`SAMPLED_MTP_UNSERVABLE_BLOCKERS`. It is a policy refusal, not a structural one:
the server's default `hint` policy relaxes the budget before the blocker check
(`relax_thinking_budget_for_mtp`), so the refusal only bites under `hard`, which
serves plain AR. Clearing command: measure a thinking request through this route
on both policies, then move the field.

`tool_call_constraint` is servable and travels the same per-row text walk, but no
live case exercises the tool branch: the tool case needs a chat-templated prompt
whose tool branch actually triggers, which is its own unit. The json_object case
is the evidence for the walk; the tool case is the evidence for the branch.
