# the query tile trades ILP for overhead and loses

## Summary

The query-tiled prefill attention kernel predicted by
`worklog/entries/20260928T025924.486086Z-lhl-gemma4-prefill-attention-scaling-31ed59.md` was
implemented, measured, and **reverted**. A 4-row tile is slower at every length:

| tokens | single row | 4-row tile | change |
| --- | --- | --- | --- |
| 512 | 5.04 ms | 6.07 ms | +20% |
| 1024 | 19.01 ms | 29.68 ms | +56% |
| 2048 | 61.20 ms | 157.71 ms | +158% |

The kernel is unchanged; the tree is clean. No default moved.

## What the tile was, and why it was predicted to win

One block per (token, head) gives each warp exactly one key at a time, so a loaded K row feeds
one dot product, a loaded V element feeds one multiply, and each key costs an 8-deep dot plus a
five-stage shuffle chain that serializes. The earlier unit read that as a latency-bound inner
loop and predicted a 4-row tile would fill the shuffle stages, share the K and V loads, and run
the four reductions through one barrier sequence. The implementation did all four: K and V
loads shared across rows, and `gemma4_attn_block_max_rows` / `_rows` carrying all four values
through one barrier sequence so the tile did not pay four times the ~200-cycle barrier cost.
Shared memory was budgeted from the artifact's own arithmetic, `kRows * (head_dim + keys +
256)` floats, which is 16 KB at 512 tokens and 40 KB at 2048.

Bit-identity held: the four attention geometry suites pass with zero failures, because each row
still walks the same `(t, t + stride)` pairs in the same descending order, and a row whose first
kept key is later than the tile's sees weight 0 for the extra keys, where `0.0f + w * v` is
exactly `w * v`.

## Why it lost, measured rather than assumed

The obvious explanation is occupancy: the tile's weights array is `kRows * keys`, so shared
memory grows with the tile height and blocks per CU fall by the same factor. That explanation is
**wrong**, and a one-line probe settles it. Padding the *single-row* kernel's shared-memory
request to the tile's exact footprint -- the kernel uses only the first quarter, the rest is
dead space -- costs 5.04 to 5.31 ms, about 5 percent. The real tile at the same footprint costs
20 percent. So the shared-memory footprint accounts for a quarter of the loss at 512 tokens and
the tile's own code accounts for the rest.

The likely remainder is that the tile's per-row arrays are indexed by a loop variable the
compiler was not told to unroll. `running_max[kRows]`, `local_sum[kRows]`, and `acc[kRows]` are
each written through `r` inside the hot loop without `#pragma unroll`, which is the shape that
puts a small array in local memory and turns register traffic into L1 traffic. The row loop
also carries a `rows` bound check per row per key. **That was not tested**, and it is the one
lead this unit leaves open.

The occupancy probe also says something about the single-row kernel that the earlier unit did
not know: at 512 tokens it is limited by threads, not by shared memory, so its shared budget
has about 5 percent of headroom to spend. Any future tiling should be read against that number
rather than against the shared-memory total.

## Validation

- The tile was built and run through the same bench the earlier unit used, at all three
  lengths, with the same iteration and warmup counts, so the three rows are comparable to the
  three rows in `benchmarks/results/2026-09-28-gemma4-gfx1151-prefill-attention-length-scaling.json`.
- Correctness while it existed: `tests/test_gpu_gemma4_attention_geometry.py`,
  `test_unit_gemma4_attention_geometry.py`, `test_unit_gemma4_attention_routing.py`, and
  `test_unit_gemma4_attention_scratch.py` all passed with zero failures, including the
  bit-identity case `test_a_narrowed_prefill_walk_is_bit_identical_to_a_full_walk`.
- The occupancy probe was a temporary change to the single-row kernel's `shared_bytes`, reverted
  with the rest.

## Next

- The unroll hypothesis above is untested. If it is wrong, the latency framing in
  `20260928T025924.486086Z` needs revisiting: a kernel whose rate is flat in length can be
  bound by issue throughput rather than by dependency latency, and those want opposite fixes.
- **`launch_gguf_linear` is 32.0 percent of the 512-token prefill** (276.2 ms over 206 calls,
  about 7 per layer) and has no attribution at all. That is a larger share than attention's
  19.8 percent and is unexplored, so it is the better next target.
- The routed experts are 42.7 percent, already at a good rate for their shape after the Q5_K
  and Q8_0 routes, and want a shape-level attribution before anything else is tried there.
