# Surya KV path migrated to KVLiveSpans: spans-aware scatter plus a fused fp32 GQA-4 split-K decode kernel

## Summary

Surya's KV write and decode now read the `(base_offsets, live_counts,
token_positions, evict_mask)` `KVLiveSpans` ABI, closing the open item in
`docs/REFACTOR.md` and the `docs/MODEL-SURYA.md` "Open ABI gap". The dense
head-major fp32 `(nk, max_seq, hd)` plane layout is unchanged, so the prefill
attention path keeps addressing the same planes the scatter writes; what changed
is that the write and the decode now resolve slots through span metadata instead
of a host-supplied `(tokens, token_offset)` pair.

Two new kernels in `hipengine/kernels/hip_gfx1100/surya/surya_ops.{hip,py}`:

- `hipengine_surya_scatter_kv_f32_spans` — maps each logical token index through
  the page table and skips it when it is outside `live_counts`, has a negative
  `token_positions` entry, or is marked in `evict_mask`.
- `hipengine_surya_full_attn_decode_split_k_f32_spans` +
  `..._split_k_reduce_f32` — a fused fp32 head_dim-256 GQA-4 split-K producer and
  its reduce, replacing the batched-SGEMM QK^T + scale + row-softmax + batched-
  SGEMM AV chain over a materialized `(nq, max_seq)` score row.

The producer runs one block per `(kv_head, context chunk)` and computes all four
query heads of that KV head from one K/V read, so each plane is read once per KV
head instead of once per query head. Split-K keeps the launch wide without a
`capacity`-sized LDS score row: at Surya's 16384-token default that row would
need 66560 B, above the gfx11 64 KiB workgroup limit.

The dense policy fills every span field uniformly — identity page table,
`arange` positions, all-false eviction mask — rather than leaving
`token_positions`/`evict_mask` null, so the default path exercises the metadata
it claims to honour and a test can evict a slot and see the answer change. The
request's `live_counts` and `row_positions` move once per decode step through two
8-byte H2D copies against persistent host mirrors (no device synchronize, unlike
the transient-temporary `_upload` path).

## Validation

### RED gate (written first, failed on the missing symbol)

`tests/test_surya_kv_spans.py`, 8 tests. Two device fixtures pin the ABI:

- `test_scatter_f32_spans_honors_page_table_and_eviction` writes through a
  **reversed** page table with one `token_positions = -1` slot and one
  `evict_mask` slot inside the written range, and requires exact equality with a
  NumPy reference that honours all three. It also asserts the fixture is
  discriminating (the identity/no-evict view differs), so an implementation that
  ignores any field fails.
- `test_decode_f32_spans_honors_page_table_and_eviction` does the same for
  decode against a float64 reference, and asserts the identity view differs.
- `test_decode_f32_spans_matches_rocblas_parent_on_a_dense_fill` is the
  parent-parity gate. It is deliberately run on the **identity dense fill**: the
  parent reads no span metadata, so a permuted page table would make the
  comparison meaningless. Declared bound `atol = 5e-5`; observed `max|diff|` is
  1.6e-7 - 3.9e-7 across 128-16384 tokens, a >100x margin.

The four host-only tests cover the planner (identity table, `arange` positions,
empty mask, split coverage), planner rejection, both wrappers' pre-build
validation, and a source assertion that all four span fields appear in both
public C entry points.

### End-to-end numerical gate

`tests/test_surya_gpu.py` (40 passed) exercises `decode_step` on the fused path
and asserts **exact greedy-token parity** against the torch-free CPU reference
over 16 decode steps, plus torch-oracle prefill KL < 1e-4.
`tests/test_surya_generation_contract.py` (39 passed). Non-GPU Surya bundle +
`test_llm_generate.py`: 144 passed. `tests/test_surya_kv_spans.py`: 8 passed.

`tests/test_surya_e2e.py::test_end_to_end_greedy_matches_torch_reference` fails
with `MissingGeneratorError: no generation implementation for (surya_ocr2,
cpu_reference, fp32, greedy_one_token)`. This is the pre-existing import-order
registration defect tracked as task #81, not a regression: it fails identically
in isolation and the change touches no generation-registry code.

Same-fill `max|diff|` 1.6e-07 - 3.3e-07 at every length, all `PASS`. The
sub-512 ratios are noisy in both directions because both routes are tens of
microseconds there and the parent's own per-layer time swings 39-61 us across
runs (three runs of this script put 256 tokens anywhere between 2.12x and
2.86x); the monotone region is 512 tokens and up, where the parent's
materialized `(nq, max_seq)` score row and its per-query-head K/V reads
dominate.

The split plan is the load-bearing tuning knob and it is a function of the
context length, not of the prompt. `plan_surya_decode_splits` targets a constant
**split count** (64) rather than a constant chunk, because the producer's
parallelism is `num_kv_heads * num_splits`: measured on the same host, a
2048-token context ran at 0.96x the parent with chunk 1024 (4 blocks) and 6.2x
with chunk 32 (128 blocks), while at 16384 tokens chunk 256 (128 blocks) beat
chunk 32 (1024 blocks) because the split-K reduce then has 512 partials per head
to combine. The chunk sweep (32/64/96/128/192/256/384 x 170/512/2048/8580/16384)
is the evidence for that formula; the planner's default LDS is 4864 B at
<= 4096 tokens and 9344 B at 16384.

## Next

- `docs/REFACTOR.md` retains two explicit paths: `attention_decode_rocblas_f32`
  (strict fallback for head_dim != 256 / GQA repeat != 4, and the parent-parity
  oracle) and `surya_scatter_kv_f32` (pre-spans scatter, used by
  `scripts/surya_gpu_debug_attn.py`). Remove both when the fp32 spans decode
  kernel is shared with the Qwen3.5 decode path or the debug script stops
  needing the parent.
- The producer passes `chunk_size` as the score GEMM's `m`, so a chunk whose
  tokens are mostly invisible does the same QK^T work as a full one. Bounding
  each chunk's keys to its last visible token would cut that; the dense policy
  has no invisible tokens, so there is nothing to measure yet.
- Task #80 (Surya GPU family fails only inside a full-suite run) is unaffected
  and still open.
