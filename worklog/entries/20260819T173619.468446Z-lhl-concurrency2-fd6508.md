# Enable physical native_c8 (rows=8) packed route: lm_head chunk cap + FFN rowtile 2x4 split

## Summary

The physical 8-row `native_c8` packed route now runs end-to-end and is
prefix-exact. It was blocked in two places: (1) the prefill/decode Q6_K lm_head
f32 rowtile only accepts rows in [2,4], so 8 rows raised `ValueError: qmicro
planar rowtile requires rows in [2,4]`; and (2) the packed decode step only
enabled `native_batch_decode_session` for rows 2-4, so c8's dense FFN fell back
to the slow `t16_wmma_prefill` GEMM. Fixes: cap the lm_head rowtile chunk at 4
(the f32 owner's real limit; the default was 6, a latent bug) and add a 2x4
split to the t16 rowtile sidecar so rows=8 runs as two exact rows=4 groups.
Result: c8 **215 ms -> 125 ms/step** (rowtile FFN), **63.6 tok/s** (was 37.1
with the wmma fallback; the route previously crashed). c2/c4 unchanged
(`c1_c2_c4_prefix_exact = True`). c8 is functional and correct but **not yet
close-to-linear**: c8 per-row (15.7 ms) > c4 per-row (10.7 ms) because the 2x4
split reads each weight twice. A true ROW_TILE=8 t16 rowtile (weight read once)
is the next step to bring c8 to ~80 ms (close-to-linear).

## Changes

`hipengine/runtime/qwen35_gguf_runner.py`:
- `_verify_lm_head_rowtile_chunked`: `if rows <= 6` -> `if rows <= 4` and cap
  `max_chunk = min(max_chunk, 4)`. The `t16_gemv_rowtile_bf16_f32_out` lm_head
  owner accepts rows in [2,4]; the previous default max_chunk=6 produced 6-row
  chunks that failed, and the `rows <= 6` direct path failed for rows 5-6.
  Rows 2-4 go direct; rows 5-8 chunk into <=4-row groups (8 -> 4+4).
- `_enqueue_packed_decode_model_step`: `native_batch_decode_session(2 <= rows <= 4)`
  -> `(2 <= rows <= 4 or rows == 8)`, so the c8 decode selects the native
  rowtile projection family (like c2/c4) instead of the wmma fallback.

`hipengine/runtime/gguf_linear.py`:
- `launch_gguf_linear` rowtile-sidecar gate: `2 <= rows <= 4` ->
  `(2 <= rows <= 4 or rows == 8)`.
- `launch_gguf_q4_t16_sidecar_decode`: for rows==8, recurse as two rows=4
  groups with offset x_ptr/out_ptr (BF16, 2 bytes/elem). The t16 weight-tiles
  sidecar is rows-independent and reused; each half preserves the rows=4 exact
  contract and the two output halves are disjoint, so the combined [8, N] write
  is exact.
