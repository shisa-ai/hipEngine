# max_tokens=1 cannot engage MTP: the parity arm failed silently, so failure now states its reason

## Summary

The C1-C8 parity refresh finished both arms: the `max_tokens=24` arm returned `complete`, and the
`max_tokens=1` arm returned `failed` with no reason anywhere - no traceback, no message, no gate name,
just 20 KB of per-prompt rate lines and a status string. Diagnosing it took reading the payload by
hand. Exactness was perfect at every width in both arms; what failed is the route expectation, and at
`max_tokens=1` that expectation cannot be satisfied by construction. The harness now states its reason.

## Changes

- `scripts/gguf_mtp_c1c8_server_bench.py`: added `verdict_reasons(summary, *, expected_cells,
  max_tokens)`, a pure function that returns one line per failed condition. `run()` now computes
  `passed = not reasons` and publishes `failure_reasons` in the payload; `main()` prints each reason.
  The pass predicate itself is unchanged and the equivalence is tested over a grid, not asserted.
- `tests/test_gguf_mtp_c1c8_server_bench.py`: five tests - clean run, grid equivalence against a local
  copy of the original predicate, cell-mismatch wording, the reproduced d=1 shape, and absence of the
  single-token note when tokens allow speculation. 19 tests pass in the file (14 pre-existing).
- No flag, no default change, no GPU behavior change.

## Finding

Measured from the two packets this run produced (`/tmp/he-parity/he-d24.json`, `/tmp/he-parity/he-d1.json`,
model `Qwen3.8-27B-Q4_K_M.gguf`, widths 1-8, `--resident-capacity 8 --batch-window-ms 20
--mtp-request-mode explicit --generation2-diagnostic`, 10 prompts per width):

- `max_tokens=24`: `exact_cells == budget_conformed_cells == cells == 10` and
  `route_expectation_passed` at all eight widths. `engaged_cells` 10/10. This is the parity-relevant
  gate and it holds.
- `max_tokens=1`: exactness and budget conformance are equally perfect (10/10/10 at all eight widths),
  but `engaged_cells` is **0/10 at every width**. The expectation is
  `engaged_cells == cells if mtp_expected else engaged_cells == 0` and `expected_mtp_widths` is
  `[1..8]`, so one generated token can never engage a draft/verify cycle and the run can only fail.
- The trap: at `max_tokens=1` the harness still prints rates, and width 4 reads AR 6.57 vs MTP 8.58
  tok/s, `+30.7%`, with zero draft tokens engaged. That ratio measures admission and prefill overhead
  inside a one-token request, not speculation. Reporting it as an MTP speedup would be exactly the
  benchmark misuse `AGENTS.md` forbids, so it is recorded here as non-evidence for MTP value. The
  same-server AR-vs-MTP ratios from the `max_tokens=24` arm are w1 +43.33%, w2 +22.98%, w3 +23.19%,
  w4 -4.86%, w5 -24.13%, w6 -31.98%, w7 -29.39%, w8 -29.91%, and are the internal route comparison -
  not the published external tok/s table in `benchmarks/README.md`, which is a different lane.
