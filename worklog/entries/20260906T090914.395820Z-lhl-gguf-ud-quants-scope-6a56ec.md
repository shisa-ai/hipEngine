# UD campaign scope narrowed against QUANTS.md type coverage

Refines [`20260906T090729.182948Z-lhl-gguf-ud-quants-4b76c6.md`](20260906T090729.182948Z-lhl-gguf-ud-quants-4b76c6.md);
does not supersede it. That entry's measurements and decisions stand.

## Summary

Writing `docs/UD-QUANTS.md` as a standalone document let it drift from
`docs/QUANTS.md`, which already carries a per-GGML-type coverage table. The two now
cross-reference each other, and the reconciliation narrowed the campaign: three of
the formats the dense route refuses already have on-device block decode in this
tree, just not a dense consumer.

What the coverage table says and what the audit measured are compatible once the
word "native" is scoped. `QUANTS.md` marks `IQ3_XXS`/`IQ4_XS` "Native,
selected-MoE focused" and `Q3_K` "Native selected-MoE" — kernels that read the
compressed block for **routed expert** shapes. The dense route's format set is
narrower, which is why the same type can be native there and still refuse a dense
load. `docs/UD-QUANTS.md` now states that reading order explicitly instead of
leaving two tables to contradict each other.

Confirmed in the kernel tree, not inferred from the table:

| Format | In-tree device decode | Consequence for the campaign |
| --- | --- | --- |
| `IQ4_XS`, `IQ3_XXS` | `gguf_iq4_xs_selected_*`, `gguf_iq3_xxs_selected_*` families, at fixed expert widths (K=1024, K=3072/N=1024/E=256, compact-row variants) | Phase 1 is a consumer job — dense-width resident layout plus repack — not a new decoder |
| `Q3_K` | `build_gguf_q3_k_gemv` present | dense consumer needed; decode exists |
| `IQ4_NL` | no kernel, but its codebook values are already embedded in the IQ4_XS implementation, per `QUANTS.md` ("not a standalone `IQ4_NL` kernel") | likely near-free after Phase 1 |
| `IQ3_S`, `IQ2_S` | layout only today | the only two refused formats that need a decoder written and gated |
| `IQ2_XS` | native selected decode/prefill per `QUANTS.md`; dense materializer excludes it | excluded from dense, expands to BF16; out of campaign scope |

So the campaign's real gap is one dense read path plus repack (Phase 1), then two
new decoders (`IQ3_S`, `IQ2_S`) and one cheap codebook path (`IQ4_NL`) — narrower
than "six formats", and narrower than the entry this one refines implied for
Phase 2.

## Changes

- `docs/UD-QUANTS.md`: added `QUANTS.md` to the related-documents list; stated that
  the coverage table's "native" can mean the selected-expert route and that the
  dense set is narrower; Phase 1 now names the existing `selected` kernel families
  and defines the work as dense consumer + repack; Phase 2 split by decode status
  (Q3_K has a GEMV builder, IQ4_NL rides the IQ4_XS codebook, IQ3_S/IQ2_S need real
  decoders).
- `docs/README.md`: index row for `UD-QUANTS.md`, beside `QUANTS.md`.
- `docs/QUANTS.md`: one paragraph under the coverage table noting the table is
  engine-wide, that a native type may be unavailable on a narrower route, and
  pointing at `UD-QUANTS.md` for measured dense-route per-format outcomes.

No code, kernel, dispatch, benchmark, or scoreboard change. No GPU used.
