# the assistant head geometry resolves against the backbone and fails closed

## Summary
`hipengine/runtime/gemma4_assistant.py` now resolves the head's four blocks to
the backbone layers they attend against, and refuses a binding that does not
match. Verified against both real artifacts: blocks 0-2 bind **backbone layer
28** (sliding, 8 KV heads, head width 256, `rotated_pairs` 128) and block 3
binds **layer 29** (full, 2 KV heads, head width 512, `rotated_pairs` 64).

The match is a property of how the two artifacts were built. Nothing in the head
says "read layer 28" and nothing in the backbone says "an assistant head reads
me", so the resolution checks the equality rather than assuming it: a head whose
block count, Q head count, KV head count, head width, or attention kind
disagrees with the layer it would bind fails at construction instead of
producing silently wrong attention.

This is the forward's first half. The module is deliberately geometry and mask
only -- no stub forward. An earlier draft of it carried a `forward` raising
`NotImplementedError` and an `_upload` referencing a field that did not exist;
that was removed rather than committed, because a stub that cannot run is not a
smaller unit of work, it is an untested path that looks tested.

## Changes
- **New `hipengine/runtime/gemma4_assistant.py`**: `Gemma4AssistantGeometry`,
  `gemma4_assistant_geometry(config, backbone)`, and
  `gemma4_assistant_keep_mask(position, keys, sliding_window)`.
- **`rope` is the bound layer's own config, not a second schedule.** The head's
  metadata and its `rope_freqs` independently produce the same two configs the
  backbone's layers 28 and 29 carry, so the head reads the backbone's
  `rope_for_layer` and there is one definition of the schedule.
- **The keep-mask is the head's own.** It is single-token, so the mask has one
  row, but it is still causal and still windowed on the three sliding blocks.
- **New `tests/test_unit_gemma4_assistant_geometry.py`**: 6 tests, 3 against both
  real artifacts, 3 numpy-only.

## Validation
- 6 tests pass. The geometry tests assert the binding, the per-block head widths,
  the KV head counts, the q widths (4096/4096/4096/8192), and that the three
  sliding blocks share one rope config while the full block has its own.
- The fail-closed tests drive wrong KV head counts, wrong Q head counts, a flipped
  attention kind, and a backbone with too few layers, and each raises.
- The mask test walks **every** position 0-8 against windows 1, 2, 3, 8, 16
  rather than checking gate points, because the windowed predicate has an
  off-by-one at `position - window` that a single-position test would miss. It
  also asserts a sliding row always keeps its own position.
- Two test failures on the first run were wrong tests, not code:
  `Gemma4GGUFRoPEConfig` exposes `rotated_pairs`, not the CPU-reference name
  `rope_angles`; and the flipped-kind case trips the KV-head check first, because
  the backbone's two bound layers differ in kind *and* KV head count. The second
  assertion was narrowed to "refuses" with the reason recorded in the test, since
  isolating the kind check would need a backbone whose two layers agree on head
  counts and differ only in kind, which no real artifact is.
- **One real code bug found and fixed by the tests**: the first version compared
  `config.block_count` to `config.nextn_predict_layers` and called the mismatch a
  binding error. Both are 4, so the check was a tautology whose message
  contradicted itself. It is replaced with the check that was meant: the head
  must have at least one block and no more blocks than the backbone has layers.
- No correctness gate applies: no kernel changed, no arithmetic changed, and no
  performance claim is made.
