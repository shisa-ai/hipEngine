# correction the pack8 clearing experiment is runnable and the question was already settled against the layout

## Summary

**`20260928T100641` is wrong on its central claim and I have reverted the
`docs/REFACTOR.md` entry it produced.** This entry supersedes it.

That entry concluded the expert pack8 layout is "a gate whose clearing experiment
cannot be run", on the strength of a prefill measurement where the route never
fired. **The experiment is runnable, it has already been run, and it settled the
question the other way.**

## What I got wrong

My run set only `HIPENGINE_GEMMA4_EXPERT_PACK8_LAYOUT=1` and measured prefill at
692 against 693 tok/s, with the engine's counters reporting `gate_up_mmq32` and
`down_mmq32`. From that I concluded the ladder containing `pack8_selected` is
unreachable at prefill and therefore the flag's own clearing condition -- "a
measurement showing the packed layout ahead at some other row count" -- could never
be satisfied.

**That inference needed one more step I did not take: disabling the MMQ route so the
ladder is consulted at all.** `HIPENGINE_GEMMA4_MOE_GATE_UP_MMQ=0` does exactly that,
and it is how the existing entry's clearing condition was met.

## What the tree already said

`docs/REFACTOR.md`'s entry *"Gemma 4's pack8 expert layout is off by default"* had
already been updated, **dated 2026-09-28, before my run**:

> **SETTLED 2026-09-28: the packed layout is never ahead, so the deletion below is
> unblocked.** The clearing condition this entry set was measured at 512 prefill rows
> against 128 experts, the one regime the ladder does not give to `grouped_prefill`:
> prefill 343.2 against 340.0 tok/s (a 0.9 percent difference, inside run-to-run
> variation) and decode 21.24 against 7.78 tok/s, reproducing the documented 2.73x
> regression on a fresh run. Evidence:
> `benchmarks/results/2026-09-28-gemma4-gfx1151-expert-pack8-layout-settlement.json`.
> Delete the flag, the seven unreached symbols, and the pinning test that exists only
> to keep the flag from flipping.

**So the entry I wrote duplicated an existing one and contradicted it.** The two
things my run did establish stand -- the route is not selected at prefill while the
MMQ route is enabled, and enabling the layout costs 116.6 s of load time and 19.2 GB
-- but neither supports the conclusion I drew from them, and the first is the
already-documented consequence of the ladder's one-lane-per-expert threshold.

## The process failure, since it is the repeatable part

**I read the flag's docstring in the loader and did not read the ledger entry for the
same flag.** The ledger is where this project records exactly this kind of
settlement, it is named in `AGENTS.md`'s key-files table, and one `grep` for the flag
name in `docs/REFACTOR.md` would have returned the settled entry. I had already
grepped that file for `pack8` earlier in the session -- the grep is in this
transcript -- and read past the hit because I was looking for a kernel entry rather
than for the flag.

**Two costs, both avoidable:** a unit spent re-measuring something settled, and a
wrong claim written into a normative ledger file that had to be reverted. The
revert also churned 165 orphaned audit decisions and 17 re-keyed rows, which is
itself evidence the file is load-bearing.
