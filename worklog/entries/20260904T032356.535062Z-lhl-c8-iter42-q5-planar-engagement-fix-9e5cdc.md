# C8 iter42: planar-Q5 route engagement deadlock fix (iter41 L4 gate was vacuous)

## Summary

**The iter41 "bit-exact L4 gate" was invalid: the planar route never
fired.** An in-process launch counter through the full runner verify path
(the L4 capture regime) showed `planar launches: 0` with the env on, the
sidecar resident, and rows=24 — the candidate side ran the same raw MMQ
owner as the strict side, so bit-exact outputs proved nothing. Root
causes, two independent defects in the iter40 route:

1. **Wrong guard conflation:** the planar branch required
   `not source_layout`, but `session.source_layout` is a session-wide
   flag that defaults ON (the source-owner env defaults to 1) and only
   *applies* at rows == 32. With the flag always True, the branch could
   never fire at any rows. Fixed by gating on `rows == 24` alone (the
   source owner keeps R32 because the planar branch never matches 32).
2. **Registration deadlock:** the branch requires
   `is_registered(planar_key)`, but the planar family only registered
   inside `_ensure_linear_kernel_registered` — which fires only when a
   RESOLVED key is unregistered. A fallback-gated variant can never
   trigger it (the raw mmq key registers via its own module-import at
   gguf_k_mmq_prefill.py:849, which is why the raw owner always worked).
   Fixed by module-import registration in the planar wrapper module,
   mirroring the mmq family.

Engagement evidence after the fix: the same probe counts
**`planar launches: 144`** = 3 candidate passes x 48 Q5 weights, exactly.
The k2 bench arms also confirmed loader engagement independently:
candidate arms hold exactly +1,226,833,920 bytes and +48 allocations over
controls (48 x 25,559,040 sidecar, 1923 vs 1875 allocations).
