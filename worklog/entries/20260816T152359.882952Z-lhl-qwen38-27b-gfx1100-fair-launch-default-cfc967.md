# Default gfx1100 GGUF Q4_K_M launch policy to fair; route-cap and continuous-batching follow-up

## Summary

Why the 16K BF16 c8 Qwen3.8-27B Q4_K_M server on the W7900 (gfx1100) showed
zero concurrency scaling (c8 burst measured **26.8 tok/s aggregate**, flat from
c1 to c8) was root-caused and the gfx1100 GGUF Q4_K_M plain-AR launch policy is
now scoped-default to `fair`, mirroring the F4-retained gfx1151 default.

## Root cause (measured, not inferred)

Three independent findings, all measured on the 16K/BF16/c8 server
(`/tmp/qwen38-w7900-256k-serve/server-c8*.log`):

1. **Default `protect_decode` policy serializes requests.** With
   `prefill_decode_policy=protect_decode` (the generic engine-loop default),
   the tick trace for a 4-request burst was `prefill(r1) -> decode(r1) ->
   decode(r1) -> prefill(r2) -> ...`: a request's decode runs to completion
   before the next request even prefills. Counters after the burst:
   `native_c1_decode_steps=634`, `native_packed_decode_steps=0` — no batched
   decode ever executed. The scheduler's `next_prefill_work` emits one row per
   tick, so with decode protection the active group never exceeds width 1.
2. **`fair` produces true width-4 packed decode.** Re-launching the identical
   server with `HIPENGINE_PREFILL_DECODE_POLICY=fair`: 37 of 45 decode ticks
   ran at rows=4, `native_packed_decode_steps=40` (all width 4),
   `native_c1_decode_steps=2`, `serial_decode_fallback_steps=0`.
3. **The plain-AR route cap is 4, not 8.** `--max-active-requests 8` is
   clamped by the registry-owned `GGUF_Q4_K_M_SERVER_PLAIN_AR_MAX_ACTIVE_REQUESTS`
   capability: **4 on gfx1100** (`hipengine/kernels/hip_gfx1100/__init__.py`,
   conservative physical-C4 default against the measured 4K/C8 resident-session
   OOM; 13 rows only qualified inside the 768-position envelope), **8 on
   gfx1151**. This is the `route_cap value=4 applied=true` / resident bucket
   capacity 4 seen in server telemetry.

Note: the A1–A6 gfx1100 coding-agent program retained
`protect_decode:256/burst-1` for the **UD-Q4_K_M 35B-A3B** configuration after
the A4 routing/SLO gate produced p512/d48 ID divergences under fair candidates
(open repair: CONCURRENCY queue item 17). That configuration is a different
quant (`gguf_ud_q4_k_m`) and is not affected by this scoped default; the
explicit env pin remains available for it.

## Changes

- `hipengine/kernels/hip_gfx1100/__init__.py`: new scoped capabilities
  `GGUF_Q4_K_M_PREFILL_DECODE_POLICY = "fair"`,
  `GGUF_Q4_K_M_MAX_PREFILL_CHUNK_TOKENS = 256`,
  `GGUF_Q4_K_M_FAIR_PREFILL_BURST_CHUNKS = 1` (+ `__all__`).
- `hipengine/generation/qwen35_gguf.py`: new factory
  `make_qwen35_gguf_q4_k_m_generator_gfx1100` registered for
  `("hip_gfx1100", "gguf_q4_k_m")`, declaring
  `engine_loop_config_defaults = fair:256/burst-1` via the capabilities and
  preserving the existing `server_plain_ar_max_active_requests` (4) and
  by-max-sequence-length (768->13) registry values. `HIPENGINE_PREFILL_DECODE_POLICY`
  (and the chunk/burst envs) still override when set — `llm.py` applies
  registry defaults only when the env is unset.
- `docs/ENVS.md`: `HIPENGINE_PREFILL_DECODE_POLICY` note now records the
  gfx1100/gfx1151 Q4_K_M package default.
- `docs/CONCURRENCY.md`: policy-default paragraph updated; new **Future
  campaigns** section for (a) the route-cap follow-up (re-qualify the C4 cap
  at 16K/256K and align `--max-active-requests` semantics) and (b) true
  continuous batching (KV-pool-capacity-driven admission/sharing/eviction
  instead of fixed c=N row caps), with a matching active-execution-queue item.
- `docs/REFACTOR.md`: entry tracking the scoped default and the env-pin
  rollback until fair is proven globally.
- `tests/test_llm_generate.py`: host test pinning the gfx1100 Q4_K_M factory
  defaults (fair:256/burst-1, cap 4, env override, no inheritance by other
  quants).

Debugging instrumentation: temporary env-gated (`HIPENGINE_GGUF_AR_SERVE_DIAG`)
prints were added to `qwen35_gguf.py` and `engine_loop.py` to capture the
tick-level decode widths and fallback reasons, then removed after the root
cause was captured above; the tree is clean of that instrumentation. The
running 16K fair server (detached, user-owned) still carries it in memory and
logs to `server-c8-fair.log`; it was left untouched per instruction.
