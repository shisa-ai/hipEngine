# Qwen4Exp batch packed per-step metadata

## Summary

H1 of the Flash-Next serving host-overhead track
([campaign](../../docs/campaigns/QWEN38FN-SERVING-FOLLOWUP.md)). A shared-batch
decode step used to upload each QSA owner's dynamic metadata separately: three
small host-to-device copies per QSA layer (append position, decode context, and
index query position), so 36 copies per step on the production 12-QSA-layer
model. Those three vectors now live in one packed buffer that every owner
publishes through stable, non-owning views, and a step uploads them with one
copy. No math, registry key, kernel, default, or flag changed.

## Changes

- `hipengine/runtime/qwen4_exp_batch_state.py`: new
  `Qwen4ExpBatchStepMetadata` (one `int64[layers, 3, state_slots]` buffer,
  `stage`, `upload`, cached `views`, retry-safe `close`) plus
  `Qwen4ExpBatchPackedMetadataViews` and `Qwen4ExpBatchAttentionRowPlan`.
  `Qwen4ExpBatchAttentionState` gained optional `position_view`/`context_view`
  and the `validate_rows` → `publish` split; `prepare` is now
  `publish(validate_rows(...))` and keeps its old behavior, including the
  unchanged-page-table upload suppression.
- `hipengine/runtime/qwen4_exp_batch_qsa_index.py`: same split
  (`Qwen4ExpBatchQsaIndexRowPlan`, `validate_rows`, `publish`), optional
  `position_view`, and the published row set now carries `positions_device` so
  `select_active` reads the vector that was actually published instead of the
  owner's own buffer.
- `hipengine/runtime/qwen4_exp_batch_runner.py`: allocates the packed buffer
  before the pooled K/V slabs (so pool sizing sees it) and before the QSA
  owners (so it is freed last), hands each layer its views, validates every
  owner's row set in `_plan_owners` before the step's first device write, and
  replaces the per-layer `prepare` loop with stage-all → one upload →
  publish-all.

Design points that the unit has to keep:

- **Layout is `[layer, column, slot]` with the physical slot count as the row
  stride.** A view's address therefore never depends on the active width, and
  `upload` always copies the whole buffer (constant address, constant size).
  That is the property a captured graph would need; the attention stage that
  reads this metadata is eager today, so this is currently a stability
  guarantee rather than a capture dependency. The copy moves
  `layers * 3 * state_slots * 8` bytes per step, which equals the old
  `3 * layers * rows * 8` at full width and is larger at narrow widths, so the
  win being measured is call count, not bytes.
- **Validation before publication.** `validate_rows` is pure host work, so the
  runner validates every attention and index owner's rows before the packed
  upload. `publish` re-checks a plan's scalar invariants before its first device
  write, and a plan built for another geometry is refused.
- **Suppression preserved.** The page table still uploads only when it changed,
  and the GDN/PLE slot-index vectors are untouched, so steady decode performs no
  per-layer copy in the QSA owners at all.
- **Lifetime.** Views are slices of one buffer allocated once per runner; the
  owners hold them as non-owning `DeviceBuffer`s and free only their own
  buffers. `close` frees the packed buffer last, after the owners.
