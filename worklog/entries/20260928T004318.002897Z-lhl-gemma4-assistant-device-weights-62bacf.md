# the gemma4 assistant head loads to device in 49 slots

## Summary
The Gemma 4 MTP head's second loading half exists and runs: 49 forward slots,
440.5 MB of device allocations, verified against the real 461.8 MB artifact. The
previous unit validated the head's metadata and tensor names and named the weight
loader as the next step; this is that step, and the forward is now the only thing
between the head and a token.

`hipengine/loading/gemma4_assistant_device.py` plans and materializes the head
through the same functions the backbone's loader uses, so the two cannot disagree
about how a GGUF block type becomes a resident layout. It adds a forward-facing
slot vocabulary (`blocks.2.attn_q`, `nextn_pre_projection`, …) so the forward
does not build GGUF names or need to know which slots carry a `.weight` suffix.

## Changes
- **New `hipengine/loading/gemma4_assistant_device.py`**: `assistant_slot_names`,
  `assistant_tensor_name`, `plan_gemma4_assistant_device_specs`,
  `materialize_gemma4_assistant_device_weights`,
  `load_gemma4_assistant_device_weights`, `assistant_resident_bytes`, and a
  `Gemma4AssistantDeviceWeights` holder with `weight`/`block`/`buffer` accessors.
- **`hipengine/loading/gemma4_gguf_device.py`**: `_plan_one` is now reachable as
  the documented public `plan_gguf_weight_spec`, so the head plans through the
  backbone's block-type-to-layout decision rather than a second copy of it.
  Renaming would have churned two test imports for no gain, so it is a wrapper.
- **New `tests/test_unit_gemma4_assistant_device.py`**: 8 tests, 3 against the
  real artifact.
- **Slots are forward identifiers, not GGUF names.** The mapping is the one
  function `assistant_tensor_name`, and a test asserts its image over every
  planned slot equals the validated map's tensor set exactly — every slot resolves
  to a tensor and no tensor goes unplanned. That single equality is what keeps the
  forward's vocabulary and the artifact's tensor list from drifting apart, which is
  the failure this module is most likely to have.
- **Materialization is all-or-nothing.** A head that fails partway is not a head
  with some weights, it is a head that cannot run, and holding 440 MB for one costs
  the next load. A test induces the failure with a bogus tensor name appended after
  the real specs, so the uploads before it have already happened.
- **`rope_freqs` is carried as a dense F32 allocation.** It is not a weight the
  forward multiplies by — it is the `freq_factors` table the full-attention blocks
  read — but it is F32 on device, so it plans as one.
- **`token_embd` is also the head's output projection.** The reference loader marks
  the output tensor `TENSOR_DUPLICATED` against `token_embd`, so the vocabulary
  projection is tied and there is no second tensor to load. That is why the global
  slot list is five and not six.

## Validation
- 8 new tests pass, including three against the real artifact. 29 pass across the
  assistant and backbone device-loading bundle, so exposing the shared planner
  regressed nothing.
- The real head loads to device with every slot present, every allocation the
  planned byte count, and every pointer non-zero. `nbytes()` is 440.5 MB, and the
  planned total equals the artifact's own summed tensor bytes, so no layout expands
  or drops data.
- Two tests failed on their first run against real code and **both were wrong
  tests, not defects**:
  1. The planned layout split is **23 raw Q8_0 blocks and 26 dense F32**, not the
     44/5 first guessed. The real split is forced by the head's tensor list: five
     linears per block plus `token_embd` and the two `nextn` projections is
     `5 * 4 + 3 = 23`; six per-block norms plus `output_norm` and `rope_freqs` is
     `6 * 4 + 2 = 26`. The assertion now records the arithmetic, so a linear
     appearing as F32 or a norm as raw blocks is caught.
  2. A second `free()` raises `HIP error 1: invalid argument`.
     `DeviceTensorAllocation.free` is not idempotent on this tree, the backbone's
     loader included, so the test asserted a contract the codebase does not
     promise. It was replaced with the all-or-nothing test above, and the
     non-idempotency is recorded in the test module's RED note rather than asserted
     as if intended. Making `free` idempotent is a separate unit: it touches every
     allocation site and could mask a real double-free.
- No correctness gate applies: no kernel changed, no arithmetic changed, and no
  performance claim is made.
