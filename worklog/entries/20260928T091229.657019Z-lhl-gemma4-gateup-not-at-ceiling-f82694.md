# the gate up at 73 GB/s is not at the one row ceiling and the dense path proves it

## Summary

`20260928T091201` closed the over-launch lead and pointed at the gate/up's
73 GB/s. Before designing a kernel change I searched the worklog for the same
regime, and found a full measured study of it in
`20260915T183902` -- **including the `grid_size_x` units rule I had just spent
two iterations rediscovering.** Two things came out of that, and the second one
overturns the first reading I took from it.

## The rule was already written down

`20260915T183902` says, verbatim: *"The reported grid reconciles only once
rocprofv3's `grid_size_x` is read as **work-items** rather than workgroups"*,
and it worked the arithmetic the same way I did -- divide by the block size.
**I had the answer in this repository and did not search for it.** Two
iterations went into a phantom. The lesson is not "check the docs" in the
abstract; it is that a surprising number in a profile output is a
**units** question first, and this repo has a written answer to that units
question.

## The ladder, and why it is not the ceiling

`20260915T183902` measured a 1-row WMMA kernel at **77 GB/s for K=2048** and
**34 GB/s for K=8192**, and named the mechanism: the K-loop is serialized by
`__syncthreads()`, and too few workgroups cannot hide the latency between
barriers. My gate/up is K=2816 at 73 GB/s, which interpolates to about 67 on
that ladder -- so on first reading the gate/up looked like it was **at** the
ceiling and the 2.7x gap to the dense path looked like an artifact of comparing
different shapes.

**That reading is wrong, and `20260928T084824` already contained the refutation
in a table I wrote myself:**

| path | bytes per token | ms | GB/s |
| --- | --- | --- | --- |
| dense GEMV (`pack8<tt,8>`) | 1.749 GB | 8.78 | **199** |
| lm_head (`pack8<tf,8>`) | 0.784 GB | 3.46 | **227** |
| MoE gate_up (`mmq32`) | 0.534 GB | 7.09 | **75** |

The dense GEMV is **also a single-token GEMV** and reaches 199 GB/s -- 78 percent
of the part's 256. So the regime supports 199, and the vibevoice ladder's 77 was
the ceiling **for that kernel's 128x64 WMMA tile with 64 workgroups**, not for
the regime. The vibevoice entry's own fix proves it: BM=64, i.e. *more
workgroups*, bought 1.16x-1.65x on the same shapes, bit-exact.

**The gate/up's 75 GB/s is therefore a real gap, not a shape artifact.**

## What is actually different

The dense path reads a **pre-packed** layout (`pack8`) built for a 1-row GEMV.
The MoE path reads the **raw Q4_K layout** in 32x32 MMQ tiles. At one row per
expert -- which is what a single-token decode is -- a 32x32 tile spends 31/32 of
its arithmetic on padding, and `20260928T090630` showed the kernel skips that
arithmetic rather than doing it, so the tile's shape buys nothing and costs the
access pattern. **The gate/up is running a many-row kernel on a one-row
problem.**

That makes the lever a GEMV-shaped gate/up for the low-lane case, not another
tile tweak -- and it points at a question the instrumentation already raised.

## The open question this leaves

`gemma4_moe_prefill_route_enabled` exists precisely to choose between a
row-reusing prefill route and a per-lane GEMV route, and `9eb796652` made it
read the runner's declared width so the choice is a property of the runner
rather than of the batch. **The instrumentation shows the mmq32 kernel running
58 times in a single-token decode, i.e. once per layer -- so decode is taking
the MMQ route.** Whether the per-lane GEMV route is reachable for a 1-token
decode, and what it measures if it is, is the next thing to establish, and it
is a much cheaper question than writing a new kernel.
