# Gemma 4 G2: per-geometry staging dedup in the decode path

## Summary

Removed the per-layer rebuild and re-upload of RoPE tables and keep masks from
`Gemma4Runner._forward_block`. Both depend only on the layer *geometry* and
the block's positions/range, so layers of the same kind were pushing
byte-identical copies thirty times per decode step on the production model
(30 layers x 3 tensors = 90 tiny H2D copies per step). They are now staged
once per distinct rope contract and once per distinct sliding window per
block: 90 copies down to at most 6, and 60 numpy table/mask builds down to 4.

T0 by construction: the uploaded bytes are identical (same numpy functions,
same inputs), only the count changes, and no buffer is rewritten while the
block runs — the next block's copies are stream-ordered behind this block's
kernels exactly as the per-layer staging was. `Gemma4RopeConfig` and
`Gemma4AttentionGeometry` are frozen dataclasses, so the rope config is a
value key; `_keep_mask` reads only `sliding_window`, `start`, and `rows`.

Measured effect — decode 20.42 -> 23.15 tok/s at 1024/128 (+13.4%), which
means the per-step copies were not just host cost: they were inserting stream
serialization between layer kernels. Cumulative campaign metric since the
baseline: 16.09 -> 23.15 (+43.9%). Every other primary row improved as well,
none regressed (see table below), and prefill benefits from the same dedup
(a prefill block has the same 30-layer x 3-upload pattern x 8 blocks).

| prompt | decode before | decode after | prefill | public wall |
| --- | ---: | ---: | ---: | ---: |
| 128 | 33.96 | 43.12 | 139.7 | 3.85 s (was 4.68) |
| 512 | 26.56 | 31.26 | 134.9 | 7.85 s (was 8.58) |
| 1024 | 20.42 | 23.15 | 129.2 | 13.42 s (was 14.25) |
| 4096 | 11.71 | 12.62 | 109.0 | 47.66 s (was 48.76) |

## Changes

- `hipengine/runtime/gemma4.py`: `_forward_block` stages cos/sin keyed by the
  frozen rope config and masks keyed by the sliding window, once per block.
- `tests/test_unit_gemma4_runner.py`: RED/GREEN contract — a four-layer
  two-kind fixture must end a prefill+decode round with `2 * rope_kinds +
  window_kinds` staging buffers (12 -> 6 before the fix).
