# startup warmup: warm the width the server admits and the speculative route

## Summary

Two gaps in eager startup, both found from a live server's own `/ready` payload:

1. The scratch probe was sized from `config.max_active_requests or 1`. That setting
   is unset by default and unset means "no server-wide cap", so the probe asked for
   `max_batch_size=1` and `prepare_request_scratch` skipped every packed AR and MTP
   prefill/verifier warmup it exists to run. On the running server the probe
   reported `packed_ar_prefill_reason=batch_width_le_1_or_disabled`,
   `packed_mtp_prefill_reason=batch_width_le_1_or_disabled` and
   `scratch_probe_s=0.000776` — it warmed nothing.
2. Nothing at startup ran the explicit-MTP route. The raw warmup is a plain
   generate, the scratch probe warms prefill/verifier kernels only, and the chat
   smoke is a request without `speculative_mtp`, which resolves to the default
   route. The first user request that asks for MTP by name paid for everything the
   speculative path had not touched.

## Changes

- `hipengine/server/api.py`:
  - `_startup_scratch_probe_batch_size(config, engine)` returns the width the server
    can actually admit: `max_active_requests` when set, capped by
    `_GGUF_DEFAULT_AR_MAX_ACTIVE_REQUESTS` for GGUF models (the batcher takes the
    smaller of the server-wide cap and the route cap), and the route cap alone when
    no server-wide cap is set. Non-GGUF models keep the previous behavior.
  - `mtp_route_enabled` is computed once, before the probe, from the requested
    policy *and* engine capability. The probe's internal env marker still follows
    the requested policy alone, unchanged.
  - New `mtp_smoke` startup stage: when `--startup-chat-smoke` is on and the MTP
    route is enabled, one bounded chat request with `speculative_mtp: true` goes
    through the production batcher before readiness — prompt built from
    `--eager-load-prompt` repeated to `_STARTUP_MTP_SMOKE_PROMPT_WORDS` (128) words,
    `_STARTUP_MTP_SMOKE_MAX_TOKENS` (8) output tokens. It resolves its route through
    `_generation_route_for_request` like a served request, submits with
    `include_batch_metadata=True`, and records both the resolved `route` and the
    `realized_route` the batcher reports, so a silent fallback to AR is visible.
  - A failing MTP warmup is recorded as `status: "failed"` with its exception type
    and logged at warning level, but does not fail startup: the route has its own
    decline-and-fall-back path and the request that would have paid the cost still
    runs. Startup memory is sampled after a successful warmup only.
  - `mtp_smoke_s` joins `last_startup_timings` and the `LOAD_TIMING` log line.
- `hipengine/server/__main__.py`: `--startup-chat-smoke` help now says it covers the
  speculative route too.
- `hipengine/chat_cli.py`: the `/help` row for `/bench` states the defaults
  (`default 512 in, 32 out`). `/bench [in] [out]` already accepted both arguments;
  only its discoverability changed.
- `docs/ENVS.md`: `HIPENGINE_STARTUP_CHAT_SMOKE` and
  `HIPENGINE_STARTUP_SCRATCH_PROBE` rows describe the new behavior.
- `tests/test_integration_server_api.py`: four new cases — GGUF width without a
  server cap, a smaller server cap still winning, the MTP warmup running on the
  speculative route with the expected prompt and token count, the warmup skipped
  when the route is off, and a failing MTP warmup leaving the server ready with a
  `failed` check.

## Validation

- `tests/test_integration_server_api.py`: 668 passed (18s).
- `tests/test_unit_server_log_style.py`, `tests/test_integration_server_speculative_provider.py`,
  `tests/test_unit_chat_cli.py`: 131 passed.
- `python3 scripts/check_test_tiers.py`: 0 issues.
- `python3 scripts/docs/check_all.py`: all 4 gates passed.
- Live evidence of the gap, from the running `qwen3.8-27b` server's `/ready`:
  `scratch_probe` `status: passed` with `result.reason=batch_width_le_1_or_disabled`
  and `scratch_probe_s=0.000776`.
- Live evidence that a short prompt still exercises the speculative route, against
  that server: three explicit `speculative_mtp: true` requests at 9, 48, and 208
  prompt tokens each reported `cycles=1`, `accepted_draft_tokens=2`, and no
  activation, prompt-fallback, or provider-decline reason. This is why the warmup
  prompt does not need to be long to engage the route.
- Memory: the probe's warmups use pooled resident sessions with prompts capped at
  `min(128, max_prompt_tokens)` at widths up to the admitted cap, and release them
  after probing, so the width change does not allocate max-context scratch per
  slot.
- Not verified live: the cold-start delta itself. The running server predates this
  change, and the effect is per-process, so it needs a server restart. Expected
  cost is roughly 1-3s of added startup for the speculative warmup.
