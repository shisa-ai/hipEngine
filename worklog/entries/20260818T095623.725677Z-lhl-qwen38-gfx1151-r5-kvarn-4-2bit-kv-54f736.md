# R5: KVarN 4/2-bit K/V decision (mention-only, not pursued)

## Summary

R5 is a decision item, not a build: the campaign doc framed KVarN 4/2-bit K/V
as "mention; lower priority" and "not something we necessarily want". The
evidence confirms it should **not** be pursued for the Qwen3.8 Q4_K_S gfx1151
campaign. KVarN (Huawei CSL: Hadamard + variance normalization + 4-bit keys /
2-bit values per 128-token tile, ~840 B/token/layer, calibration-free vLLM
backend) exists to fit ~262k context on a 24 GB card. None of that motivation
applies to this campaign's hardware:

1. **gfx1100 W7900** — INT8 K/V already reaches the **256K model limit**
   (admitted KL 1.04e-5 / 1.35e-4, 100% top-1, 126K verified, projects to the
   model's max-position ceiling). 4/2-bit KVarN would add **zero** capacity
   headroom there; the model, not memory, is the binding constraint.
2. **gfx1151 (this campaign)** — the Halo has **128 GB unified memory**;
   context is not the constraint. And R1 (this campaign) just re-closed the
   native INT8 K/V lane on the current Q4_K_S head: both natively-supported
   INT8 representations reject at 512/8 under the no-mirror + KL/top-1
   contract (`pure_int8_per_token_head_fp32_scale` keeps a 48 MiB BF16 mirror
   so the layout gate fails; `tail4_hadamard_group32_fp16_scale` is
   mirror-free but top-1 0.889 on `general_en_explain` < 0.90 floor). KVarN
   4/2-bit is strictly **lower** precision than INT8, so it would face an
   even harder quality gate with no capacity win on this backend.
3. **XTX (not this campaign)** — the only backend where INT8's 126K -> ~200K
   extension argument has some pull; out of scope for this gfx1151 campaign.

**Decision:** do not implement or test KVarN in this campaign. If ever
revisited, gate on the same KL/top-1 curve plus bytes-vs-quality versus our
own INT8 (not the external's capacity headline), and only on a backend where
context capacity is actually the binding constraint (XTX-style), never gfx1151.

## Changes

- No code, kernel, or numeric changes. Pure decision/assessment, consistent
  with the campaign doc's "mention only" framing.
- Re-verified the external KVarN claim (Huawei CSL vLLM backend, arXiv
  2606.03458, 3-5x capacity / ~1.3x throughput / FP16-level accuracy,
  calibration-free) so the framing in the campaign doc is accurate.

- Cross-checked our Qwen3.8 context-capacity reality: gfx1151 is not
  context-bound (128 GB unified); gfx1100 is model-limit-bound, not
  memory-bound, at 256K.
