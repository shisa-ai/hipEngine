# Prefix cache serving performance campaign

## Summary

Opening a measured campaign to make GGUF prefix caching pay for real multi-turn
serving on gfx1151. The retained decision from the 2026-07-21 W7900 agentic A2
packet keeps `HIPENGINE_PREFIX_CACHE=off`, and its numbers say why: every C1
family regressed both primary metrics, and the `small_repo` family regressed
**64.19% goodput with 0/12 hits**. A regression with zero hits is an overhead
finding, not a hit-rate finding, so the campaign separates the two.

Code reading before measuring produced one hypothesis that later measurement
**refuted**, and the correction is the useful part. The hypothesis was that the
general greedy prefill path never records an entry at the prompt end, so a
prompt of length `L` with `L % 256 != 0` leaves no usable prefix entry and only
`_prefill_processed_argmax_chunk` (which splits at `floor(L/256)*256`) can reuse
pages. Measurement shows the greedy path does record one: `_processed_tokens`
returns the processed prompt prefix, `_refresh_prefix_cache` captures at every
256-aligned chunk boundary, and chunked prefill reaches `floor(L/256)*256` as a
chunk boundary. The RED test in
`20260918T045446.502434Z-prefix-cache-serving-review-prefix-cache-prompt-boundary-capture-aafbd2.md`
records `snapshot_capture_calls == [256, 512]` before that change, which is two
captures for a 512-token prompt. What the greedy path does not do is capture the
unaligned prompt end, so the usable boundary is `floor(L/256)*256` — a
granularity limit, not a missing entry.

The measured reason for sparse reuse was different, and is fixed in
`20260918T051721.812204Z-prefix-cache-serving-review-prefix-shared-admission-contiguity-c1ad29.md`:
shared admission placed the private suffix at the lowest free pages, so a
retained snapshot pinning the pages after a prefix produced a gapped allocation,
which forces the packed AR prefill off its slot-local route and fails outright
above 1024 tokens. With that repaired, the same A/B resolves 16 of 27 lookups.

The remaining cost is on the reuse path itself: a reused request prefills its
unmatched suffix through one `session.step()` per token at 34.0 ms/token against
1.8 ms/token for a batched full prefill, which is why the measured A/B is still
net-negative and why `HIPENGINE_PREFIX_CACHE` stays `off`.

This entry records the campaign setup and the corrected mechanism.

## Changes

- Branch `perf-prefix-caching` from `9493d4224`.
- Added `scripts/prefix_cache_multiturn_bench.py`: an in-process multi-turn
  benchmark over the production resident loop and the server's own chat
  renderer. Lanes are (a) the pinned ShareGPT conversations in
  `benchmarks/prompts/qwen38-sharegpt-soak-v1.json` run cumulatively, (b) the
  checked-in synthetic repository workloads in
  `benchmarks/prompts/agentic-coding-v1.json` driven exactly as the A2 packet
  drives them (fixture transcript rebuilt each turn), and (c) the same long
  repository prompts carried forward with the model's own replies. Per turn it
  records prompt/output tokens, engine-attributed prefill and decode wall, and
  the runner's per-request prefix telemetry (hit, matched/reused tokens, source,
  fallback reason). A/B runs `off` and `radix` and reports paired deltas.
- Response budgets are mixed on purpose: short chat replies (96), long chat
  replies (384 on the two longest ShareGPT lanes), and code turns (192) over
  2,048- and 8,192-token repository prefixes.
