# R0523 c4 race: GDN per-slot state prep (slot_is_current reuse) + single-base chain conv

## Summary

Traced the packed c4 GDN state path end-to-end after localizing the R0523 corruption
to GDN blocks (bg-168). Identified the per-slot base-state import with a reuse
optimization and the single-base chain conv consumer as the two concrete suspects.
Static inspection has not yet pinned the intermittent race; next step is a rocprofv3
dispatch/memory trace of a reproducing step. No production behavior changed;
diagnostics env-gated and uncommitted.

## Validation

Code trace (eager packed c4, Qwen3.8-27B-Q4_K_M dense):
- GDN dispatch: `_run_native_attention_bulk_ffn_layer_rows` -> staged_dense_linear ->
  `_run_linear_attention_attn_chain_rows_exact` -> `_try_run_linear_attention_chain_journal_rows_exact`.
- Per-slot base import: `_sync_packed_decode_initial_state` (runner:27400) copies each
  session's conv/recurrent state to `packed_state.linear_state_pair(layer)` at
  `slot_index*nbytes`, BUT skips the copy when `slot_is_current` (can_reuse and
  prior_positions[slot]==start_position). Reuse across steps is the intermittent lever.
- Chain conv consumer `qwen35_linear_attn_chain_conv_decode_lowp_tloop_kernel`
  (conv.hip:723) loads ONE base_conv_state and chains t=0..max_nodes; chain-journal
  commit (runner:5901) copies only the LAST row's state back to the single resident
  conv_state/recurrent_state. Tree-style single-base semantics vs four independent
  slots is the structural suspect; a deterministic single-base chain alone would not
  be intermittent, so the race is in the per-slot base PREP/restore/reuse ordering.
