# Engine command budget and wait diagnostics; honest decode-rate fields

## Summary

Two defects surfaced together on the live gfx1151 `Qwen3.8-27B-Q4_K_M` server
(`hipengine serve --info --metrics prometheus`): a large-prompt request returned
HTTP 500 `TimeoutError: engine service command timed out` from `tokenize`, and a
completed 20,878-token request logged `stream_tok_s` (then `decode_tok_s`) of
266.62 tok/s, roughly 20x above what the hardware can do.

Root cause for both: `EngineService` runs the engine on one driver thread, so a
command queues behind whatever that thread is doing. A control command (the
server's `tokenize`) waited behind that work with a 30 s budget, which is shorter
than legitimate engine work — a context prepare that grows the KV pool, or one
prefill tick. The timeout then surfaced as an untyped 500 with no record of what
blocked it, and the event-loop-thread wait stalled the server's SSE streams, so a
request's delivered tokens arrived in a burst, collapsing the observed decode
window (168.8 ms for 45 tokens) that the summary line reported as a rate.

## Changes

- `hipengine/generation/engine_service.py`: `DEFAULT_COMMAND_TIMEOUT_SECONDS` is
  300 s, with `slow_command_warn_seconds` (default 10 s) and a `_wait_response`
  helper that all command waits go through. A wait past the warning threshold logs
  one `ENGINE_COMMAND_SLOW` line naming the blocking activity
  (`driver_command`/`driver_command_s`, `driver_tick_s`, `queued_commands`,
  `active_requests`, `driver_alive`); an exhausted budget raises a `TimeoutError`
  carrying the same detail. A command the driver has already started is not
  reported as blocked by itself, since it is not waiting behind anything.
- `hipengine/llm.py`: `engine_command_timeout_seconds` on `LLM` (env
  `HIPENGINE_ENGINE_COMMAND_TIMEOUT_SECONDS`), plumbed into the resident
  `EngineService`.
- `hipengine/server/api.py`: the `--info` summary now labels its decode basis
  instead of reusing one field for two measurements. Streamed requests report
  `stream_decode_ms`/`stream_tok_s` (the server-observed first-to-last-token
  window); blocking requests report `decode_ms`/`decode_tok_s` from engine phase
  accounting (`request_total_ms - prefill_ms`). A streamed request never reads
  `request_total_ms` as a decode span: engine telemetry inside a stream carries it
  as a prefill-time snapshot (measured 6,304 ms for a 13.6 s request), which would
  have reported 68 tok/s for a 7.36 tok/s decode.
- `docs/API.md`, `docs/ENVS.md`: the budget, the diagnostics, and the two decode
  bases with their window caveat.

  carries `stream_*` and no engine-derived decode fields even when the timing
  payload has a prefill-time `request_total_ms`; the blocking line derives
  `decode_ms=5097.4`/`decode_tok_s=10.01`; absent phases are omitted, the flag-off
  path is silent, prompts are never logged, and KV fields are reported. Exit 0.
- `tests/test_unit_llm_generate.py::test_llm_engine_command_timeout_defaults_generously_and_respects_env`:
  the default is >= 300 s, env parsing accepts `600`/` 12.5 `, rejects `soon` and
  `0`, and the resolved budget reaches the resident `EngineService`. Exit 0.
- `tests/test_integration_generation_engine_service.py`: three new tests — a
  command blocked by a tick warns once with `driver_tick_s=` and
  `active_requests=1`; an exhausted budget raises with `method=`, `budget_s=`,
  `driver_tick_s=`, `driver_alive=yes`, and the abandoned command still runs on the
  driver thread afterwards; a long command does not warn about itself. Whole file
  plus the `--info` server tests: 36 passed, exit 0.
- Live reproduction before the fix (gfx1151, `Qwen3.8-27B-Q4_K_M`, 8k-token
  prompt): `ERROR: REQUEST_FAILED ... message=unhandled server error: TimeoutError:
  engine service command timed out`, twice, once with the server otherwise idle.
- Live honest-stream measurement (1,730-token prompt, `max_tokens=48`,

  `decode_elapsed_ms=6575.3`, `decode_tokens_per_second=7.3`, backend
  `prefill_ms=5603.5` over 7 chunks.

## Next

- The 266 tok/s line is a symptom of a delayed stream, not of the metric alone:
  engine control calls are still issued synchronously from async request handlers
  (`_prepare_prompt_input`/`engine.tokenize` at `hipengine/server/api.py`
  `_prepare_prompt_input`, `chat_context_candidate`, `prepare_prompt`), so a slow
  engine command blocks the event loop and every in-flight SSE stream. Offloading
  those waits (`asyncio.to_thread`, as `ensure_resident_context` already does for
  `prepare`) is the next unit; until then `stream_tok_s` can still be inflated and
  should be read with `stream_decode_ms`.
- `stream_tok_s` remains a window rate because the engine exposes no per-request
  decode timing in stream telemetry (`DecodeState` carries step/token counters but
  no timestamps). An engine-side decode span would make a single honest rate
  possible for both modes.
