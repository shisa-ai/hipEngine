# W7900 Qwen3.8: MTP K3 is flat across C1-C8 because verify cycles are per-request, and acceptance collapses with wave width

## Summary

The explicit-K3 row in the published matrix is nearly constant (31.146, 29.639, 30.547,
31.033, 30.755, 30.248, 30.596, 30.845) while AR rises 21.871 -> 44.338 over the same
widths, so K3 goes from +42% over AR at C1 to -31% at C8, versus llama.cpp K3 rising
32.553 -> 94.735. Decomposing the sha-verified baseline packet
(`/tmp/gfx1100-qwen38-final-k3-c1c8.json`, engine `d12be41188`, `status complete`,
80/80 engaged, raw_sources sha `d94c8843ef48...` matches) separates two independent
defects:

**1. No wave-level cycle sharing.** Verify cycles/second is essentially constant at every
width - 9.2, 10.1, 11.9, 11.6, 11.0, 11.0, 11.6, 11.5 - while total cycles scale
~linearly with concurrency (71 at C1 -> 718 at C8; 89.75 cycles/request). Eight times the
concurrency buys no additional verify throughput. The code explains it: the native
spec-decode target submits one graph per request per cycle
(`gguf_native_spec_cycle.py`, cache name `_native_spec_b{rows-1}_target_graph`), and the
`rows in {2..8}` gate is *per request* (root plus B1-B7), not per wave. I initially
suspected `_effective_target_verify_mode`'s `rows > 4 -> serial_exact` gate, but that
`rows` is also per-request (`batch.request_ids[0]`, `device_proposal.budget + 1 ==
batch.rows`), so at K3 rows = 4 and the gate never fires. Fixing this means verifying the
wave's rows in one target block, which is the only route to llama.cpp-like K3 scaling.

**2. Wave-dependent acceptance collapse.** Draft acceptance falls 0.789 (C1) -> 0.614 (C2)
-> ~0.467 (C3) and stays ~0.47-0.52 through C8; position-1 acceptance falls 0.93 -> 0.571.
Position 1 depends only on the last accepted token and that slot's state, so a
concurrency-dependent drop there cannot be model math. It is also not slot aliasing:
per-slot acceptance is fairly uniform (C4 0.484-0.577, spread 0.093; C8 0.454-0.726, spread
0.273, no dead slot), and route telemetry labels are identical at C1 and C8
(`native_caware_decode: true`, `serial_decode_fallback: false`) - my earlier route-switch
idea came from the wrong-flags budget-2 packet where MTP was not engaged at all, and is
withdrawn. Outputs stay AR-exact throughout, so this is a throughput defect: correct draft
tokens are rejected and recomputed.

Interim from the canonical K3 rerun (widths 1-4 complete, per-cell means, not the
published `mean(tokens)/mean(wall)` convention): AR +1.04/+1.30/+2.05/+2.28% and K3
+1.63/+1.93/+2.20/+2.24% over this baseline. So today's prefill promotions helped both
arms by roughly 1-2%, and neither defect above is affected by them.

## Next

- Discriminating experiment for defect 2 (needs the device, ~10 min): at C1, C2 and C8,
  capture per-cycle position-1 proposal ids against the AR trajectory and classify each
  reject as a genuine draft miss, an off-by-one state read, or a cross-slot read. Rejects
  that match the AR token of another index or another slot identify the corrupted-state
  path; a genuine-miss rate matching C1 would move the investigation to the verifier.
- The `native_graph_fallback_reason` string is plumbed to
  `session.last_native_spec_target_fallback_reason` and surfaced only by
  `scripts/gguf_mtp_long_context_gate.py` / `..._task_gate.py`, not by the C1-C8 packet.
  Adding it to the packet's telemetry would make the fallback rate visible per width.
- Defect 1 is a design change (verify the wave's rows in one target block, then let the
  acceptance commit fan back out per request). It should not be attempted without defect
  2 resolved first, because acceptance losses currently mask the benefit of larger verify
  blocks.
