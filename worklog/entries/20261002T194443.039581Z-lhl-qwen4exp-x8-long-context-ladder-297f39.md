# X-8 long-context ladder: the decode column is a host-clock measurement, prefill is 4-5x behind

## Summary

`X-8` asked for our own context-scaling curve before any long-context kernel
work. Measured 8K-256K on the `gfx1151` Framework host (`55ea6c50…`,
`gguf_ud_q4_k_xl`, production profile, BF16 KV, warm PLE, 1024-token chunks, 128
AR transitions, one warmup and one repetition per case), with two same-host,
same-file, same-token llama.cpp-family ladders beside it (pwilkin `strix-halo`
`40a9f4d01`, f16 KV; upstream `6011c34ce`, bf16).

**Prefill is the clean column and the real gap:** 260.5 -> 255.6 -> 242.7 ->
208.8 -> 183.8 -> 149.7 tok/s at 8K / 16K / 32K / 64K / 128K / 262,008
(**-42.5%**), and the
262,008-token rung (the largest prompt the harness can serve inside the model's
native 262,144 context) reads 149.7 tok/s. The comparator's prefill is flat
across the same ladder (982.7 / 991.3 / 894.4 tok/s), so the ratio against it
**widens with depth, 3.8x -> 4.1x -> 4.9x**. Upstream `6011c34ce` falls **49.4%**
(462.0 -> 381.0 -> 233.9), faster than our 42.5%, so against it we are only
**1.76x -> 1.59x -> 1.27x** behind: **the prefill gap has two very different
sizes and the larger one belongs to the fork tuned for this part.** That is the
long-context work to do, and it is GPU-bound.

**The decode column is not a depth curve.** The 8,192-token rung reads 13.53 and
6.79 tok/s four cases apart at the same prompt size (2.0x); the 32,768 rung holds
both 148.8 and 382.5 ms/step. Held still, the step is **flat**: 51.6 ms at 8K and
52.4 ms at 32K (+1.5% for 4x the context), measured with a 30 s settle and the
host at boost (max core 4,943-5,149 MHz, GPU 79% busy). At 64K a 30 s settle
cannot restore boost and the step is 170.9 ms with the max core at exactly
2,000 MHz in all 512 in-window samples.

**The host is the difference, and it is measured two ways.** (a) The requested
clock reads **exactly 2,000 MHz - the base clock - in all 291 samples** that cover
the ladder's four largest rungs (30 + 101 + 53 + 107), with the median core also
pinned at 2,000, and a 300 s recovery probe reaching 3,603 MHz at most. (b) A
fixed CPU workload that takes 116-118 ms between runs takes **730-762 ms during a
comparator rung (6.4x)** and **5,800-7,400 ms during the 256K rung (50-64x)**, at
89.8 C CPU / 90.0 C GPU and 165 W. Across those same states **pwilkin's
decode does not move at all** (42.9-56.9 ms at 8K, 46.8-54.9 at 32K, 47.8-55.1 at
128K), **upstream's does** (56.1 -> 73.7 -> 160.3 ms, +186%, the depth curve this
family actually has), and in the settled state our decode **sits between the two
builds**: 1.09x faster than upstream and 1.09x / 1.04x slower than pwilkin at
8K / 32K. The ladder's 7.2x decode gap at 32K is the host state, not the engine.

**Consequences for the ledger.** `QA-4` and `QA-7` are not long-context levers:
the existing owner profile prices QSA index selection at **2.490 ms/step, 3.02%**
of that run's own 82.459 ms/token wall at 64K (1.116 ms, 1.35% at 16K), and the
decode step is host-dispatch-bound at every depth measured. The concrete decode
lever is the **per-step dispatch path** - 353-545 launches, 958 `build_hip` JIT
cache-key resolutions, 375 file opens, 12,798 environment lookups and 209,933
Python calls per step, identical at p1024 and p65536 while each call costs 9-14x
more. The prefill lane keeps its existing owner list (dense quantized matmul
10,749.6 ms against pwilkin's 1,485.2 on a single `code-p4096` prefill).

Also recorded: the pwilkin fork **asserts F16 KV** (`qwen4exp.cpp:1360`) and
aborts on bf16 KV, so the 2026-09-15 comparator protocol's bf16 KV is not usable
for that fork; and this host runs the `powersave` governor with the
`accelerator-performance` tuned profile **not** active.

## Validation

- Every rate is a single measured 128-transition window from
  `scripts/qwen4exp_canonical_ar_bench.py` (one warmup, one repetition) on the
  host named in each artifact; the settled probes are
  `scripts/qwen4exp_de5_wall_split.py` with `--settle-ms 30000 --split-steps`.
- Comparator rows run through the same harness against the same fixture token
  arrays, `-ngl 999 -fa on -b 8192 -ub 2048 -t 4`, context sized to the rung,
  zero warmups; f16 KV for pwilkin, bf16 for upstream. The f16 requirement was verified by a load test: the
  same binary listens normally with `-ctk f16 -ctv f16` and aborts with bf16.
- Host attribution is from two independent instruments recorded during the runs
  (`host-clock-watch.jsonl`, 360 samples covering the four largest rungs;
  `cpu-speed-watch.jsonl`, 423 samples covering the comparator rungs), not from
  a post-hoc assumption. GPU sclk is 2,900 MHz (its maximum) in all three
  settled windows, so the GPU clock is not a confound.
- Prefill-vs-decode separation is structural: the harness times the prefill and
  the 128 decode transitions separately, and the prefill rates are reproducible
  within 6% across four categories at every rung that has four.
- Limits: one host (integrated APU, not the gfx1100/W7900 default hardware), one
  model/quant/profile, one measured repetition per case and no interleaving; the
  boost-clock 64K step (~80 ms) is an estimate derived from that window's own
  GPU-busy fraction, not a measurement; two comparators rather than the whole
  family (halo-box and gufo absent, neither comparator ran 262,008, and the two
  KV types are each build's own requirement rather than a controlled variable);
  no end-to-end request rate is claimed.
