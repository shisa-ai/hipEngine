# Resident prefill stall root-caused: first eager sample readback never returns

## Summary

A self-dumped faulthandler stack (5-minute timer, permission-free) names the
bare `Qwen35GGUFResidentSession` prefill stall precisely: the host blocks in
a blocking device→host memcpy at the **first eager-route prefill token's
sample readback** —

```
prefill (runner:20041) -> _sample_from_hidden (:29825)
  -> _read_sample (:29834) -> copy_device_to_host (memory.py:243)
  -> hipMemcpy (hip.py:290)   [never returns]
```

while GPU[0] spins at ~94-100% in the preceding eager-route kernel. So the
GPU is stuck executing (or livelocked inside) one of the resident eager
prefill kernels; the memcpy is where the host waits, not the defect. The
qualified TP1/TP2 harness never takes this path — `MlpTP2GenerationSession`
drives its own `_forward_token` dispatch (attn-only leaves + shard chains)
over the same FullStackRunner — which is why every gate on this host is
clean. The D1 bulk route also runs (its NaN is the separate ee20cd defect).
Resident-eager-prefill evidence is gfx1151-lane qualified only.

## Changes

- `scripts/tp2_mtp27b_engage_probe.py`: added
  `faulthandler.dump_traceback_later(300, repeat=True)` (self-dump, no
  ptrace needed) — the tool that produced the decisive stack.

## Validation

- Stack captured at the 5-minute mark on a fresh run (bg-32 log
  /tmp/mtp27b_probe.log): matches all three earlier stall repros (same
  outer frame chain, GPU ~100%).
- py-spy cannot attach on this host (ptrace permission denied); the
  in-process faulthandler path is the standing substitute.
