# Compact-DMS transaction carries allocator ownership

## Summary

Task #10's store half: a compact-DMS transaction now restores allocation
ownership, not only the visible payload planes. `DMSOperation` gained
`DMSAllocatorSnapshot`, captured by `begin_transaction` and applied by
`rollback`, carrying the per-head extents and range capacities, the extent
pool's ownership and free ranges, and the resource ledger's ownership,
provisional reservations and counters.

The gap this closes was measured, not assumed. Disabling only the new restore
block leaves the eviction/compaction cycle test green and fails only the shrink
case, so an in-cycle eviction moves payload but releases no ownership, while a
shrink (`_shrink_after_streaming_pack` -> `_shrink_committed`) releases
provisional slots through `ResourceLedger.apply_delta` and re-allocates extents
through `CompactExtentPool.shrink`. Payload restoration alone therefore left the
allocator holding the post-cycle layout after a rolled-back shrink.

## Changes

- `hipengine/kvcache/dms.py`: added `DMSAllocatorSnapshot`; `DMSOperation`
  gained an `allocator_snapshot` field; `begin_transaction` captures it and
  `rollback` restores the extent pool, the ledger, `range_capacity`,
  `base_offsets` and `state.extents`. `CompactExtentPool` gained
  `state_snapshot`/`restore_state` (distinct from the existing health-reporting
  `snapshot`).
- `hipengine/kvcache/ledger.py`: `ResourceLedger` gained
  `state_snapshot`/`restore_state` covering `_used`, `_high_water`,
  `_used_by_lifetime`, `_owners`, `_reservations`, `_reservation_by_owner`,
  `_next_reservation_id`, `_stats` and `_blocking_counts`. Ownership records are
  frozen dataclasses, so containers are copied and the mutable counters rebuilt.
- `tests/test_unit_dms_cycle_transaction_journal.py`: new CPU-only unit file
  (no HIP needed, so it lands in the reviewed default tier). Three cases: a
  rejected cycle after a real eviction and compaction restores payload, scales,
  positions, live counts, evict mask, range capacity, base offsets, extents and
  counters; a commit keeps the cycle in place; a rolled-back shrink restores
  extent ownership, free ranges and ledger reservations.
