# Answer the Gemma 4 sliding-fallback mask question and freeze the 4096-prefill gate baseline

## Summary

Two checks the Gemma 4 punchlist listed as prerequisites (V3 and V1).

**V3 answered: the sliding fallback does apply the window mask, so today's
4096-token prefill output is not wrong.** The 49x growth in `attn.sliding`
(29.9 ms at 1024 tokens to 1478.7 ms at 4096) is not an unwindowed fallback. It
is a kernel swap (1024 used `attn_fwd`; 4096's later blocks do not) multiplied
by the exact kernel's three-pass structure, in which the window bounds pass 1
only. The window buys about **3%** at 4096, not the ~4x its key count implies.
P1's premise and its ~1300 ms estimate both stand, but for a different reason
than the punchlist row assumed.

**V1 done: a pre-P1 gate baseline now covers a prefill block with
`keys > 1024`,** which no recorded gate ever has, plus a determinism self-gate
at `kl_max` exactly 0.0.

No engine code changed. This unit is one measurement, one code audit, and the
punchlist rows they close or correct.

## Validation

**V3, by code audit.** Every step of the mask path was read, not inferred:

- `_keep_mask` (`hipengine/runtime/gemma4.py:966`) applies *both* bounds:
  `key_positions <= queries` and `(queries - key_positions) < sliding_window`.
- `_sliding_read_range` returns 0 unless `rows == 1`, so a 512-row block gets
  the full windowed mask rather than a shifted pointer.
- `aotriton_prefill_admits` refuses the flash path when
  `keys > sliding_window`, so the windowed mask is never silently dropped in
  favour of the flash kernel's own causal masking. Confirmed by direct call:
  `(rows=4096, keys=4096, head_dim=256, sliding_window=1024,
  mask_is_causal=True)` returns `False`; the same call at `keys=1024` returns
  `True`.
- The fallback reads the mask: `mask_row = keep_mask + token * keys`, and pass 1
  skips fully-masked key tiles.

**V3, by controlled measurement.** The 5 global layers fall back at *both*
lengths with the same head_dim 512, so they isolate the exact kernel's scaling
from any kernel swap: 7.84 ms/layer at 1024 and 122.1 ms/layer at 4096, or
**15.6x for 4x the tokens — quadratic**. The sliding fallback at 4096
(head_dim 256) measures 59.1 ms/layer against **61.05 ms/layer predicted from
that same measurement for a fully unwindowed row** (122.1 scaled by the
head_dim ratio). Pass 3 walks `[0, last_active + 1)` on sliding and global rows
alike, so head_dim is the only difference between them, and the 3% residual is
all the window recovers.

The decomposition of 49.5x is then 16x (quadratic full-key walk) x 3.3x (exact
kernel where 1024 used `attn_fwd`), which closes to 52.5x predicted against 49.5x
observed.

Pass structure, read from `gemma4_attention.hip`: pass 1 skips fully-masked
tiles (`active[t] = mask_row[...] != 0`), **pass 2 walks every key** (`expf(-inf)
= 0`), and **pass 3 trims only the tail** (`last_active`, itself derived from the
mask row by a byte walk plus a warp max-reduce). So the window's lower edge
reaches pass 1 alone. This is also why the fix has to be a single-pass kernel
rather than a narrower walk.

**V3, dispatch verified.** `DEFAULT_PREFILL_BLOCK` is 512, so a 4096-token
prefill is 8 blocks; `launch_gemma4_attention_prefill` tries the decode family
first whenever `tokens > 1`, which is why blocks 3-8 run
`gemma4_attention_decode_class_kernel<...,1>` (head_dim 256) and `<...,2>`
(head_dim 512) and only blocks 1-2 reach `attn_fwd`. The punchlist's evidence
row was correct; an earlier reading of mine that the block kernel served those
blocks was wrong.

**V3, P1's plumbing verified.** `aotriton_wrap.cc:456-461` already selects
`CausalType::WindowedAttention` and passes `WindowValue::BottomRightAligned` for
both `window_left` and `window_right` — which is why the `_3_0` windowed image
already runs today, as plain causal. The windowed images exist (12 files under
`aotriton.images/amd-gfx11xx/flash/attn_fwd`, all `*bf16@16_256_*`, including
`_3_0`). Passing `window_left = sliding_window - 1` and `window_right = 0` is
therefore the whole change.
