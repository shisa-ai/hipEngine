# Add repeatability and isolation checks to the INT8 MTP server gate

## Summary

Readiness item: the full public HTTP matrix at the shipping profile, with
determinism and isolation.

The acceptance requires, alongside the three gates passing, "a repeatability run
showing identical ids across two schedules and an isolation check with a
neighbouring request."

**Neither check existed.** All three gates
(`int8_mtp_server_gate.py`, `int8_mtp_server_lifecycle_gate.py`,
`int8_mtp_prefix_gate.py`) had zero references to repeatability, identical ids,
or isolation, so no run of them could have produced that evidence. The server
gate ran the matrix once, sequentially, and compared only the AR/MTP/stream
triple within each row -- which every row sees against the same history, so
state that leaks forward between requests is invisible to it.

## Changes

- `scripts/int8_mtp_server_gate.py`:
  - **Repeatability.** After the forward pass, the gate re-runs the whole
    schedule **in reverse** and requires every row's ids to match the forward
    pass. The reversed order is the point: each row then runs against a
    genuinely different request history, which is what catches a pooled buffer
    or retained snapshot whose contents depend on what ran before it.
  - **Isolation.** A neighbouring row is run in a thread on the same server
    while the target is in flight, and the target must reproduce the ids it
    produced alone. The neighbour's ids are captured too, so a run where both
    were corrupted cannot pass by agreeing with each other.
  - `run_triple`, `request_payload`, and `single_row_ids` extract the request
    construction and the triple assertion so the three passes share one code
    path instead of three copies that could drift.
  - `--skip-determinism` for a fast diagnostic run, and the report records
    `determinism_required` plus `determinism.skipped`, so a determinism-free
    run cannot be read as complete evidence.

## Validation

The gate needs a live server, so it cannot run here. Its **checks** can, and
that is the distinction that matters: a determinism check that only ever passes
is indistinguishable from no check at all. `tests/test_unit_int8_mtp_server_gate_checks.py`
drives the real script as a subprocess against a fake server speaking the same
wire shape, and exercises each check in both directions:

- a well-behaved server passes, and the report shows the checks ran;
- a server whose ids depend on which pass over a prompt they belong to fails
  the **repeatability** check;
- a server whose ids are contaminated while two requests overlap fails the
  **isolation** check;
- `--skip-determinism` passes and the report says the checks were skipped.

`pytest tests/test_unit_int8_mtp_server_gate_checks.py
tests/test_unit_int8_mtp_serving.py tests/test_unit_int8_mtp_teardown.py`
-> 41 passed. The new module was run three times consecutively with exit 0
each time, because it is concurrency-sensitive by construction.

### Two harness bugs found while writing it, both mine

Recorded because both are the kind of thing that would have made the checks look
green without proving anything:

- The first fake made ids depend on a global request counter, which broke the
  AR/MTP/stream triple **before** the repeatability check was ever reached, so
  the test passed for the wrong reason. Ids now depend on a per-prompt visit
  count divided into passes, so they agree inside a triple and differ across
  passes.
- The first contamination model keyed off the instantaneous in-flight count,
  read after a sleep, so whichever request woke first saw the overlap and the
  other did not -- the isolation check fired only by luck. The server now
  latches "overlap was observed" and both parties read the latch after the
  window closes.

  follow-up on the same pattern.
