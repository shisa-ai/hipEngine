# Muse Glimmer AR: dp4a MMQ port slower than bf16 WMMA; space exhausted

## Summary

Studied llama.cpp's RDNA3.5 MMQ (mmq-config-rdna3-5.cuh: Q4_K I=64 rows,
J=128 cols, 128 threads, occupancy 2; vec_dot_q4_K_q8_1_impl_mmq uses dp4a
with a SINGLE local int accumulator + float sum[] — the register discipline
that avoids the AGPR spill of the int8 WMMA attempts). Ported that discipline
to a dense Glimmer dp4a kernel (one column per thread, weight nibbles reused
across the row tile, Q8_1 activation staged in LDS). Correct (cosine 0.99983)
but ~4x SLOWER than bf16 WMMA. The projection design space is now exhausted.

## Changes

- Experimental dp4a kernel added then reverted (tree clean at 7083e1df2).

## Validation

- dp4a TILE_M=16: 26.95 ms / 5.1 TFLOPS (0.24x bf16); TILE_M=64: 24.72 ms /
  5.5 TFLOPS (0.25x). cosine 0.99983, maxerr 0.0052. bf16 shared_b: 6.1 ms /
  22 TFLOPS.
- The dp4a int8 path achieves only ~5.5 TFLOPS in practice (serialized
  per-thread dp4a + per-column global weight reads), ~4x below the bf16 WMMA
  leaf. The "dp4a peak ~ bf16 peak" roofline estimate does not hold for this
  kernel structure on gfx1151.
