# the down projection's lever is a tile layout, and the gate/up route is the template

## Summary

The expert down projection is **104.5 ms over 29 calls (3.60 ms/call), 15.94 percent of the
prefill**, and it is the best-supported remaining lever. This entry fixes the mechanism and the
template; it does not build the unit.

## The mechanism, from the source

`gguf_q5_1_mmq_selected_prefill.hip` puts **one thread on one output column**:

```cpp
__global__ __launch_bounds__(128, 4)
void q5_1_mmq_ds4_selected_prefill_kernel(...)
  const int64_t out_col = static_cast<int64_t>(blockIdx.x) * 128 + threadIdx.x;
  dim3(out_tiles, expert_grid), dim3(128), 0, stream
```

A thread's weight row is at `out_col * row_bytes`, and `row_bytes = (in_features / 32) * 24` --
**528 bytes at `in_features = 704`, which is 4.1 cache lines.** So a warp's load instruction
touches 32 distinct lines and uses 4 bytes of each. The bytes are not wasted at the source (each
thread does consume its whole row), so this is not a bandwidth loss: it is **32x the
transactions and 32x the outstanding-miss pressure for the same bytes**, which is what a
stall-bound kernel runs out of. `20260928T114215` measured exactly that profile -- removing 28.7
percent of the VALU buys 2.3 percent, and the kernel moves ~429 MB in 104.5 ms, **1.4 GB/s**.

## The template already exists

`_gemma4_project_experts_gate_up_wmma_t16`'s own docstring states the fix as the difference
between the two routes:

> its weight operand is the **Q4T16 tile layout**, which is one 16-column tile per 256-wide K
> block **rather than a column-strided walk of raw Q4_K rows**

and prices it:

> The tiles cost **2.78 percent more** than the raw blocks they are built from and are produced
> once at materialize time, so the route adds no per-call work and no second copy of the tensor.

**That route already gave 1.264x on gate/up** (5.040 ms against 6.369 ms per layer). The
accepted `2026-09-28-gemma4-q5-1-down-mmq-load-width-accepted` candidate, which is already
promoted on the default path, names the same gap from the other side:

> the down projection is still **1.29x behind the gate_up per byte**, and the residue is the
> Q5_1 five-bit format's second sudot4 pass for the high bit, which is real work rather than
> waste; **what is left beyond that is the gate_up's LDS staging, which the down does not do**

So the down projection has neither the tile layout nor the LDS staging the gate/up route has,
and both are already implemented one function away.

## What the unit is

A Q5_1 tile layout for the down projection, mirroring the Q4T16 route: a repacker run at
materialize time, a WMMA prefill variant consuming it, an oracle, and loader wiring. **The
Q4T16 route is the template for all four**, which is what makes this bounded rather than open --
`20260928T114215` priced a *different* layout (int8-unpacked) at 1.9 GB resident, and the tile
approach is 2.78 percent of the weight instead.

Ceiling: the down projection is 15.94 percent of the prefill and the sibling route's measured
gain is 1.264x, so the shape of the win is 104.5 x (1 - 1/1.264) = **21.8 ms**, or about a
quarter of the 94 ms gap. The `1.29x behind the gate_up per byte` figure says the true ceiling is
somewhat higher if the tile layout closes more of that residue.

## A separate defect, not on this path

The promoted candidate's `leaves_open` flags: *"The same four-byte or-chain load appears in nine
other files under `kernels/hip_gfx1100/quant/` and was not checked for this defect."*

**Checked here, and it is not nine files.** The contiguous form -- `uint32_t(p[0]) |
(uint32_t(p[1]) << 8) | (uint32_t(p[2]) << 16) | (uint32_t(p[3]) << 24)` over `p[0..3]` -- occurs
only in **`gguf_iq_dense.hip` (7 sites) and `gguf_iq_wmma_prefill.hip` (2 sites)**.
`gguf_t16_selected_gemv.hip`'s three sites are **not** this defect: `t16_q4_pack4` gathers its
four bytes from four different tile rows, so there is no contiguous dword to load.

**None of the IQ files is on the gemma4 prefill path** -- the artifact is UD-Q4_K_XL
(Q4_K/Q5_K/Q6_K/Q8_0). It is a real defect for the IQ-quant models and belongs in the cleanup
ledger, but it cannot move this objective's metric and should not be scheduled against it.
