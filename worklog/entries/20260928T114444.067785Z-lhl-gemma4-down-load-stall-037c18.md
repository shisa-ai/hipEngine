# the row loop's activation load is a scalar load with a full waitcnt and no pipelining

## Summary

The previous entry established that the down kernel still takes 2.4 ms with every
high-bit-chain instruction deleted, so roughly 2.1 ms is neither VALU issue nor
the dp4a count nor DRAM bandwidth. This entry finds where it is, in the
generated assembly.

**The loop structure.** Compiling the kernel standalone and finding backward
branches recovers the nesting the source declares:

```
kb loop          lines  145-1016   871 lines, 780 instructions
  sub loop 0     lines  370- 440    71 lines,  59 instructions, 16 v_dot4
  sub loop 1     lines  542- 612    71 lines,  59 instructions, 16 v_dot4
  sub loop 2     lines  713- 783    71 lines,  59 instructions, 16 v_dot4
  sub loop 3     lines  883- 953    71 lines,  59 instructions, 16 v_dot4
```

Four 70-line inner loops of 16 `v_dot4` each -- the four sub-blocks' row loops,
exactly as written. No loop interchange, no unexpected hoisting.

**What the innermost loop actually issues.** The row loop body contains **two
memory operations and no `global_load` at all**:

```
.LBB0_16:                                    ; row loop body
        s_clause 0x1
        s_load_b256 s[64:71], s[40:41], 0x10 ; 32 B activation
        s_load_b32  s61, s[40:41], 0x0       ; 4 B scale
        ...
        s_waitcnt lgkmcnt(0)
        v_dot4_i32_iu8 v63, v35, s64, 0 neg_lo:[1,1,0]
        ...
```

Three things follow, and all three are good news about the compiler and bad
news about the schedule:

1. **The activation reads are already scalar (uniform) loads.** The compiler
   proved the address is wave-uniform and promoted the two `uint4` reads and the
   scale read to `s_load`, so the activation occupies SGPRs and costs no VGPR
   pressure and one transaction per wave. That is the right encoding and it is
   not a defect.
2. **The `x` operand of every `v_dot4_i32_iu8` is an SGPR pair** (`s64`, `s68`,
   `s65`, ...). The quants never touch VGPRs.
3. **The two loads are followed immediately by `s_waitcnt lgkmcnt(0)` and then
   the dp4a.** The wait is unconditional and complete, and it sits before the
   first consumer, so there is no overlap between one row's load and the
   previous row's arithmetic.

**Why there is no pipelining.** A `b256` scalar load lands in eight consecutive
SGPRs, and the next iteration's load wants the same eight. That is a write-after-
read hazard the scheduler cannot rename away, so it has no choice but to wait.
The compiler is not failing; the source gives it one register set and a
loop-carried reuse.

**This is the stall, and it fits every other measurement.** The row loop is 59
instructions, of which 16 are `v_dot4`, and the useful arithmetic is 16 cycles
against a scalar-load latency that is tens to hundreds of cycles depending on
whether the line survives in L1 -- which a 190 MB weight stream actively
evicts. The block's warps all read the same uniform address, so they miss and
recover together rather than staggered, which is why 5 blocks per CU still leaves
VALU issue at 17.7 percent. It also explains why deleting half the dp4a bought
2.3 percent (the dp4a were never the exposed resource), why unrolling the row
loop by two was slower rather than faster (it duplicates pressure without giving
the allocator a second SGPR set), and why `ROWS_PER_PASS` helped by amortizing
the *weight* unpack while leaving this untouched.

The 11 `s_delay_alu` annotations inside a 59-instruction loop are the compiler
telling us it knows those dependencies stall; they are consistent with the
waitcnt reading and are not independent evidence.

## Next

**Software-pipeline the row loop.** The mechanism is now specific: give the
allocator two activation register sets so iteration `r+1`'s scalar load can issue
before iteration `r`'s dp4a consume the first set. In source terms that means
loading row 0 before the loop, loading row `r+1` at the top of iteration `r`, and
consuming row `r`'s values after -- which is a change to the row loop only, and
which is falsifiable in the same two ways this entry used: the timing, and
whether `s_waitcnt lgkmcnt(0)` still sits between the load and the first `v_dot4`
with no independent load in flight.

The 12-percent regression from `#pragma unroll 2` is not evidence against this.
That directive asked for two rows of *arithmetic* without asking for two sets of
*loads*; the scheduler answered by duplicating the body and keeping the same
wait. A manual double-buffer is a different request.
