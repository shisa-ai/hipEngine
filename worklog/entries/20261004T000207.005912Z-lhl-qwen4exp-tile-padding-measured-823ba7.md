# Measured MoE prefill tile padding is 1.25x, not the modelled 1.60x

## Summary

The per-expert tile padding recorded in
`20261003T235118.067749Z-lhl-qwen4exp-moe-tile-padding-8a6b02.md` was **modelled**
from a uniform-routing assumption and put the production chunk at 16384 padded rows
for 10240 real - a 1.60x work ratio. It is now **measured** off the production kernel
trace: the gate/up risk owner launches `Grid_Size_Y = 800` for all 1504 launches in
the window, so `wmma_total_rows = 800 x 16 = 12800` padded rows against 10240 real.

**The finding stands; its size is 1.25x, not 1.60x.** Real top-10 routing is sparser
than uniform: 800 tiles over 512 experts means 224 experts hold at most one tile, so
fewer than 512 experts own rows. The modelled estimate was pessimistic.

- No code change, no default change, nothing promoted.

## Validation

### Derivation

`gguf_q4_k_selected_dual_wmma_iu8_risk_prefill_kernel` launches
`dim3 grid = ((out_features_total + 127) / 128, wmma_total_rows / TILE_ROWS)` with
`dim3 block = q4_k_iu8_warps<16>() * 32 = 128` threads
(`gguf_q4_k_selected_prefill.hip:2471-2478`). Since rocprofv3 reports `Grid_Size` as
total work-items, the block count in Y equals `Grid_Size_Y` directly, and
`wmma_total_rows = Grid_Size_Y x 16`.

The same launch cross-checks the work-item interpretation: `out_features_total =
1280` gives 10 column blocks, and the trace reports `Grid_Size_X = 1280 = 10 x 128`.
A block count of 10 cannot produce 1280, so the column is work-items.

### Numbers

| quantity | value |
| --- | ---: |
| real rows (1024 chunk tokens x top-10) | 10240 |
| padded rows (`Grid_Size_Y` 800 x 16) | 12800 |
| padding waste | 25.0% |
| work ratio | **1.25x** |

Observed identically across all 1504 launches of the q4_k gate/up risk owner in the
`code-p4096` window, so the routing distribution is stable within the prompt.

### The prize, as an upper bound

Eliminating padding entirely would take the row space from 12800 to 10240, a **20%
reduction in gate/up WMMA work**. Gate/up is 32.56% of the prefill window, so the
upper bound is **~6.5% of the window**.

This is a bound, not a plan: the fix needs a row space that packs tail rows from
multiple experts into shared tiles, which requires a kernel able to switch weight
pointers mid-tile or a tail path cheaper than a quarter of the WMMA path. The exact
grouped fallback is not that path - it already loses by median +157.8% while doing
1.25x *less* work at this shape.

## Limits

- One host (gfx1151 APU, **not** the gfx1100/W7900 default hardware), one model, one
  quant, one case (`code-p4096`), one chunk size, one execution profile.
- **Single prompt.** The routing distribution is prompt-dependent, so 1.25x is this
  prompt's figure. A sparse-routing prompt would pad more.
- The 12800 figure is the row space the kernel is launched over; it is not itself a
  timing.
- No correctness gate applies: no arithmetic changed and no default was modified.
