# retraction: the expert MMQ kernels are not line-bound, and the 25 percent figure was wrong

## Summary

`20260929T003000` concluded the expert MMQ kernels were DRAM-bound with 75 percent of their
traffic wasted on partially-used cache lines, and that coalescing the weight read was worth up
to 1.31x. **That is wrong.** The line efficiency is **82 percent**, not 25, the 49 GB/s figure
really is about 19 percent of DRAM peak, and the decomposition's "latency-bound" reading stands.
**No port was built on the wrong finding**, which is the only reason this cost nothing.

## The error

I computed the line waste as if each 32-byte load pulled a fresh 128-byte line:

```
per warp load: 32 lanes x 32 bytes used = 1024 bytes
               but 32 lines touched     = 4096 bytes
line efficiency: 25.0 percent
```

**The second line is wrong because the lines are reused.** A thread does not read one 32-byte
fragment and stop; it walks its own weight row:

```cpp
weight_row = qweight + (expert * out_features + out_col) * (in_features / QK5_1) * Q5_1_BLOCK_BYTES;
w_base     = weight_row + kb * (Q8_1_MMQ_BLOCK / QK5_1) * Q5_1_BLOCK_BYTES;   // kb * 96
w_sub      = w_base + sub * Q5_1_BLOCK_BYTES;                                 // + sub * 24
```

Over `kb` 0..21 and `sub` 0..3 that covers offsets **0 to 2112 of a 528-byte row, contiguously.**
Consecutive `sub` reads land in the same line, and `kb` steps the row in 96-byte increments. The
row spans **5 lines for 528 bytes used -- 82 percent efficiency**, and the small remainder is
ordinary edge waste that a coalesced layout would also pay.

**So the DRAM traffic is roughly the useful bytes, and 49 GB/s is 19 percent of peak after
all.** The decomposition's conclusion -- "neither number is close to a ceiling, so the kernels
are latency-bound" -- was right and I talked myself out of it with an arithmetic error about
cache behaviour.

## The experiment that caught it

Varying `in_features` changes the stride, so I expected tighter strides to raise the rate if
coalescing were the limit. **The rate rises with larger `in_features`, the opposite of the
prediction:**

| in_features | median | GMAC/s |
| ---: | ---: | ---: |
| 32 | 0.206 ms | 1788 |
| 64 | 0.385 ms | 1916 |
| 128 | 0.607 ms | 2432 |
| 256 | 1.115 ms | 2648 |
| 704 | 2.674 ms | 3036 |

That is a fixed per-call component being amortized, and it fits `time = a + b * in_features`
with **a = 0.224 ms**. (The two smallest points sit below the line, so the fixed part is not
purely per-call -- some of it scales with the `kb` loop rather than with the call.)

The sweep could not have tested coalescing anyway, which is the more useful lesson: the stride
is `(in_features / QK5_1) * Q5_1_BLOCK_BYTES` and the per-thread row length is the same
expression, so **the layout is self-similar and the ratio of stride to row length is constant at
every `in_features`.** A layout defect of this kind cannot be probed by changing a dimension.

## What this leaves standing

Everything in `20260929T000000` and `20260928T233500` that was measured rather than reasoned:
the routed distribution costs 7.4 percent with 50 percent more tile passes; more rows per expert
helps under poisson and not under uniform; occupancy, planes, traffic, unrolling and K width are
all eliminated. **And the decomposition's own inference is back in force:** the two kernels
agreeing at 49 GB/s says the rate is set by something shared -- the pass structure, the
activation load path, or the launch geometry -- and launch geometry is the only one of the three
that has been tested.

## The corrected statement of the open problem

The expert MMQ kernels run at **2.3 to 3.0 TMAC/s and 49 GB/s of weight traffic, about 19
percent of DRAM peak, with neither axis saturated.** They are latency-bound. Why two different
quants and two different kernels land on the same rate is still unexplained, and the activation
load path remains the one named suspect nobody has touched.

None. No code was changed on the strength of the retracted finding.

## Next

- **The activation load path is still the untested named suspect.** It is where the next unit
  should go.
- **Do not build a coalescing port.** The read is already 82 percent line-efficient and the
  arithmetic that said otherwise is in this entry.
- **Treat a self-similar layout as untestable by a dimension sweep.** That is why the sweep came
  back inverted and why it took a second look to see the error.
