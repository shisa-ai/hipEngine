# VibeVoice-TTS oracle environment pinned and verified

## Summary

The VibeVoice-TTS torch oracle cannot run under the host interpreter. The
community fork calls `AutoModel.register(VibeVoiceAcousticTokenizerConfig, ...)`
at `modular_vibevoice_tokenizer.py:1188`, and `AutoModel.register` keys on the
`model_type` string, which transformers 5.15.0 already claims for
`vibevoice_acoustic_tokenizer`. The fork therefore needs a pinned interpreter
environment. That environment is now built reproducibly, locked, and verified
end-to-end: it loads `microsoft/VibeVoice-1.5B` and produces non-empty 24 kHz PCM
for both a single-speaker and a two-speaker script.

The pin is not incidental bookkeeping. It is also the finding that determines
scope: transformers 5.15.0 natively registers `vibevoice_acoustic_tokenizer`,
`_encoder`, `_decoder` and `vibevoice_asr`, but has **no** `vibevoice`
`AutoModelForCausalLM` entry. The acoustic waveform decoder is therefore reusable
rather than new work, while the diffusion head and generation loop remain
fork-only.

## Changes

- `scripts/vibevoice_tts_oracle_requirements.txt` (new): the locked dependency
  set, resolved in a single `pip install` so it is mutually satisfiable.
- `scripts/setup_vibevoice_tts_oracle_env.sh` (new): builds
  `/home/lhl/venvs/vibevoice-tts-oracle` with `--system-site-packages` (reusing
  the host's ROCm torch rather than installing a mismatched wheel), installs the
  lock, and asserts the two constraints that silently break the oracle.
- `docs/MODEL-VIBEVOICE-TTS.md`: new "Oracle environment" section recording the
  checkpoint and fork revisions, the measured parameter count, the resolved
  pins, the collision error verbatim, and the reproduction command. The
  `speech_scaling_factor` bullet and the "two surfaces must be built new"
  paragraph were corrected; see Notes.

## Validation

- Fork import under transformers 5.15.0, measured:
  `ValueError: '<class 'vibevoice.modular.configuration_vibevoice.VibeVoiceAcousticTokenizerConfig'>' is already used by a Transformers model.`
  raised at `modular_vibevoice_tokenizer.py:1188`.
- transformers 5.15.0 native registry, measured: `AutoModel` has
  `vibevoice_acoustic_tokenizer`, `vibevoice_acoustic_tokenizer_decoder`,
  `vibevoice_acoustic_tokenizer_encoder`, `vibevoice_asr`; `AutoModelForCausalLM`
  has none.
- `scripts/setup_vibevoice_tts_oracle_env.sh` run to completion from scratch:
  `transformers 4.51.3`, `tokenizers 0.21.4`, `huggingface_hub 0.36.2`,
  `torch 2.13.0+rocm10.0.0`, HIP available `True`, `environment OK`.
- On the rebuilt venv, `microsoft/VibeVoice-1.5B` loads as 2704.0 M parameters
  in bf16 (5.41 GB, 3 shards), and generation produces non-empty PCM:
  single speaker 70400 samples (2.93 s at 24 kHz, rms 0.0583) and two speakers
  259200 samples (10.80 s, rms 0.0397).
- `speech_scaling_factor` / `speech_bias_factor` measured at
  `0.1962890625` / `-0.04931640625`, identical across separate runs.

## Notes

- The lock must be resolved as one set. Installing `transformers==4.51.3` first
  and `diffusers` second leaves `huggingface-hub` at 1.31.0, which 4.51.3 and
  `tokenizers` 0.21.4 both reject, and then downgrading the hub leaves an
  inconsistent `diffusers` 0.40.0 behind. Applying `huggingface-hub<1.0` in the
  same resolution yields a consistent tree and pins **diffusers 0.39.0**, not
  0.40.0. The first version of the requirements file was a flat list of the
  sequentially-installed versions and did not resolve at all
  (`ResolutionImpossible`); it has been replaced with the real lock.
- `speech_scaling_factor` and `speech_bias_factor` are **not** checkpoint values.
  The config has no such keys; the fork registers them as `NaN` buffers and
  computes them from the reference-audio latents on the first request
  (`scale = 1 / std`, `bias = -mean`). They are model buffers, so they persist
  across requests and a later request with a different reference voice silently
  reuses the earlier scale. The doc previously said to load them from the
  checkpoint and called a NaN value a loader error, which is backwards; both
  claims are corrected.
- The doc also claimed the acoustic waveform decoder must be built new. It is
  native in 5.15.0 with `decoder_ratios [8, 5, 5, 4, 2, 2]` (x3200) and
  `vae_dim` 64, matching the checkpoint. Corrected; the port still owes chunk
  flush and sample accounting.
- **The oracle is not yet deterministic.** The smoke runs drew the diffusion
  noise from an unseeded global RNG, so two runs of the same script produced
  83200 and 70400 samples. The scaling factors were stable across those runs
  because they come from the reference audio, not the RNG. This is the concrete
  reason the fixtures must record the random tensors rather than a seed:
  `sample_speech_tokens` draws `torch.randn(2 * n_tokens, 64)` at the *doubled*
  CFG batch size and discards the second half, so the draw order is part of the
  contract.
- The lane is an AMD Radeon 8060S (gfx1151), not the default W7900/gfx1100.
  These are oracle-side reference outputs, not hipEngine performance claims.
