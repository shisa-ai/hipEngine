# Correction: 124 GiB of device memory means both layouts fit, so the fallback need not change

## Summary

**A correction to my own previous entry, and it simplifies the plan.**

The previous entry concluded that keeping both expert layouts was "almost certainly
beyond what is affordable" and therefore that the `per_expert_offset` fallback
would have to be made pack8-aware. That was wrong.

Measured: `hipMemGetInfo` reports **total 124.0 GiB, free 121.6 GiB**, and
`free -g` agrees at 125 GB total. Against that ceiling:

| option | total | fits? |
| --- | --- | --- |
| keep both layouts | 36.2 GB | yes, comfortably |
| drop raw after promotion | 21.8 GB | yes, easily |

So the drop-raw requirement is **not forced**. That simplifies the implementation
unit rather than complicating it: the fallback route can keep reading the raw
layout, `per_expert_offset` needs no change, and promotion carries one less risk.

**How the error happened:** I asserted a constraint from an estimate (17.0 -> 36.2
GB, "+113%") without measuring the ceiling it had to fit under. The ceiling was the
easy half of the question - one `hipMemGetInfo` call - and I had already decided
the answer was no before checking. Recording the correction rather than quietly
dropping the claim, because the earlier entry states it confidently and a reader
would otherwise carry a false constraint into the implementation unit.

## Changes

- `benchmarks/results/2026-09-27-gemma4-gfx1151-decode-kernel-profile.json`:

## Validation

- `hipMemGetInfo` directly, corroborated by `free -g`, on the target box.
- The two plan figures are the measured residency totals from the previous entry.
- **Not verified:** peak memory during a real decode run with both layouts, which

  weights against 121.6 GiB free there is ample room, but the promoted
  configuration's peak is a measurement for the unit that promotes it.
