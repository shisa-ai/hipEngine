# XTX capacity Packet 1: repaired probe, engaged INT8 route

## Summary

Repaired `scripts/gguf_context_ceiling_probe.py` per the campaign's Packet 1
audit and re-ran the Qwen3.8-27B `Q4_K_M` startup-boundary matrix on the RX
7900 XTX. The repaired harness reproduces the historical BF16 peaks exactly,
shows the earlier "INT8 saves no memory" row measured an unengaged BF16
fallback, and — after fixing a server-startup regression that broke every
non-default KV policy since commit 9701985dd — measures the qualified compact
INT8 route passing 4,096 declared tokens where BF16 fails, first failing at
5,120. No concurrency or throughput claim is made.

## Changes

- **Probe rewrite** (`scripts/gguf_context_ceiling_probe.py`, schema 2):
  exact prompt fitting to a live token target through the server tokenizer
  with drift correction; usage/finish-reason/authoritative-token-ID
  validation; continuous 20 ms sysfs VRAM sampling with stage peaks;
  card resolved by PCI id with unique_id recorded and the server-reported
  device cross-checked; OOM classified only from matching evidence with
  distinct `oom_startup`/`hip_error_N`/`ready_timeout`/`request_timeout`/
  `device_mismatch`/`kv_fallback`/`ownership_leak` statuses; effective KV,
  pool, prefix, graph and MTP state recorded from `/ready` and
  `/v1/hipengine/capabilities`; port-in-use and idle-baseline gates; bounded
  ownership drain treating the packed-workspace lease as persistent baseline
  (`expected_workspace_lease_pages` mirrors the server formula).
- **Startup regression fix** (RED-first,
  `tests/test_generation_qwen35_gguf_sampling.py`): since 9701985dd the eager
  `prepare_runner()` in `SubmitPollTextGenerator.__init__` resolved
  `auto`→BF16 before any request, so a server started with
  `--kv-storage int8_per_token_head --kv-scale-dtype fp32` raised
  "GGUF resident session KV policy cannot change after preparation" at
  startup. `LLM` now accepts `kv_storage`/`kv_scale_dtype`/
  `kv_scale_granularity` and publishes them as `request_kv_policy_hint`;
  `_prepare_kv_policy(None)` locks the hinted policy. The no-hint behavior is
  unchanged and explicit-policy switches still fail closed (existing tests).
- **Soak generalization** (`scripts/qwen38_int8_server_context_soak.py`):
  `--quant`, `--kv-storage` (bf16 skips scale flags), `--kv-scale-dtype`,
  `--kv-scale-granularity`, `--resident-slots N` (server
  `--max-active-requests` N with offered client concurrency C, pool sized by
  N) for the Packet 1 N-vs-C attribution runs; protocol block records the
  actual values.
- **Artifacts**: seven per-point JSONs plus a rollup
  (`2026-09-06-rx7900xtx-startup-boundary-repaired-probe.json`) and the
  Packet 0 controls file from the previous unit.

## Measured (RX 7900 XTX, GPU[1]=card0=0000:10:00.0, 25,753,026,560 B)

| Point | Status | Whole-card peak | L/D validated |
| --- | --- | ---: | --- |
| BF16 2048 | ok | 21.869 GiB | 2031/16, finish=length |
| BF16 3072 | ok | 23.328 GiB | 3055/16 |
| BF16 4096 | oom_startup | 23.951 GiB | warmup HIP error 2 |
| INT8 fp32 2048 | ok | 21.349 GiB | 2031/16, runtime_action=admit |
| INT8 fp32 3072 | ok | 22.601 GiB | 3055/16 |
| INT8 fp32 4096 | ok | 23.751 GiB | 4079/16 |
| INT8 fp32 5120 | oom_startup | 23.942 GiB | warmup HIP error 2 |

- BF16 peaks match the 2026-09-06 aggregate artifact exactly; the failing
  point's true peak is 23.951 GiB, not the 16.9 GiB of incomplete sampling.
- The earlier "INT8 byte-identical peaks" came from `runtime_action
  fallback_bf16`: the default FP16 scale contract is unqualified, so the
  server silently served BF16. With the qualified FP32 contract the route
  engages and saves 0.5-0.7 GiB at the same context.
- Both routes share an ~18.95 GiB fixed intercept; declared-token slopes are
  1.459 MiB (BF16) and 1.203 MiB (INT8) versus 64 KiB / 32.5 KiB payloads.
  The eight-slot packed-workspace lease (max(8,N) x ceil(ctx/256) pages) is
  one confirmed component; full attribution is Packet 2.
