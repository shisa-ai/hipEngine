# Gemma 4 P8 landed: router logits variant selection, 2.35x on prefill

## Summary

P8's router-logits half landed. `gemma4_router_topk_bf16` called the generic
`qwen35_router_logits_bf16_f32w`, which defaults to `threads=512` over a
four-token tile: at hidden 2816, 160 of 512 threads — 31% of every block —
have no K range at all and idle behind a nine-round barrier tree for 64 FLOPs
per useful thread. Prefill-size token counts now take the already-built
`token_tile_16` at `threads=256`, measured at **2.35x** standalone
(0.2309 ms -> 0.0982 ms, 1.60 -> 3.76 TFLOP/s) for the same 2.861e-06 drift
against a float64 reference. The output is not bit-identical, so the
teacher-forced gate gated it: **passed, 1023 rows, 0 top-1 flips, kl_mean
7.06e-06, kl_max 1.30e-03.** End to end `moe.router_gemm` fell **13.4 -> 7.2
ms at 1024 and 53.2 -> 28.4 ms at 4096**, taking prefill busy down 5.7 ms and
21.5 ms and prefill throughput up +0.94% and +0.56%, with decode unchanged or
slightly up. Every other family moved under 1.5 ms. Below 32 tokens the route
keeps the untiled path, which is faster there — without that split decode lost
0.6%. P8 stays open: prescale fusion and the top-8 fusion remain, ~3 ms /
~13 ms of opportunity left.


P8 in `docs/campaigns/GEMMA4-26B-A4B-PUNCHLIST.md` (moe.router_gemm) carried a
~10 ms / ~38 ms prefill opportunity at 1.7 TFLOP/s. Working it from the
estimation end first: nothing here is a claim until the numbers are measured on
the W7900.

## Decision

Select the router logits kernel by token count instead of always taking the
generic entry point.

`gemma4_router_topk_bf16` called `qwen35_router_logits_bf16_f32w`, which
defaults to `threads=512`. That symbol dispatches to
`launch_qwen35_router_logits_token_tile<TOKENS_PER_BLOCK=4>` once tokens >= 4.
At hidden 2816 the main loop's K range covers `k = tid*8; k+7 < 2816`, so only
threads 0..351 do any work — **160 of 512 threads, 31% of every block, are
idle behind a nine-round barrier tree for 64 FLOPs of work per useful thread.**
8192..16384 blocks per launch pay that.

A better variant already existed in the same library and was not selected by
anything: `qwen35_router_logits_bf16_f32w_token_tile_16` at `threads=256`.

Prefill-size token counts now take it; below `_TOKEN_TILE_16_MIN_TOKENS = 32`
the route keeps the untiled path. That is size-based automatic selection of
the same kind the C layer already does inside `launch_qwen35_router_logits`
(`tokens >= 4` picks the tile over the untiled kernel) — not a flag, not an
identity gate.

## Measurement

Standalone sweep at the production shape (tokens=512, hidden=2816,
128 experts, 200 repeats, GPU 1 RX 7900 XTX), from
`scripts/gemma4_router_logits_variant_bench.py`:

| variant | ms/launch | TFLOP/s | max drift vs f64 |
| --- | --- | --- | --- |
| `bf16_f32w` (threads=512, TPB=4) — the old default | 0.2309 | 1.60 | 2.861e-06 |
| `token_tile_8` (threads=256) | 0.1021 | 3.62 | 2.861e-06 |
| `token_tile_16` (threads=256) | **0.0982** | **3.76** | 2.861e-06 |
| `auto_256` | 0.1138 | 3.24 | 2.861e-06 |

2.35x for the same accuracy against the float64 reference. The 1.60 TFLOP/s
confirms the punchlist's "~1.7 TFLOP/s".

Token sweep (base vs `token_tile_16`):

| tokens | base | token_tile_16 | winner |
| --- | --- | --- | --- |
| 1 | 5.16 us | 6.98 us | base |
| 16 | 8.88 us | 9.94 us | base |
| 20 | 16.60 us | 10.30 us | token_tile_16 |
| 64 | 25.12 us | 19.30 us | token_tile_16 |
| 512 | 183.68 us | 94.06 us | token_tile_16 |

Crossover between 16 and 20 tokens; 32 keeps clear of both sides. Choosing the
tile unconditionally costs about 0.6% of decode (measured: decode fell
43.80 -> 43.53 tok/s at 1024 before the split, recovered to 43.82 after).

## Arithmetic

Not bit-identical: base vs `token_tile_16` differ on 46264 of 65536 outputs,
max abs 3.81e-06. The tiling changes which thread owns which K range and the
shape of the reduction, so rounding differs. Arithmetic-changing, so the gate
applies.

showed a real decode regression (43.53 tok/s, tight non-overlapping range

GPU reports a runaway store as a page fault, then hangs the next sync.
