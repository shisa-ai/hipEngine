# Capture the prefix checkpoint from the streaming prompt sink, and fix the cursor convention

## Summary

Task #21 unit 1b is complete and live: the checkpoint is now captured on the
route the served engine actually primes a provider through, and a live c=1 run
shows two captures landing at their boundaries. The live check also exposed a
cursor-convention bug in unit 1 that would have made every capture skip, so the
two are one unit.

## Changes

- **The sink captures** (`hipengine/runtime/qwen35_gguf_mtp.py`):
  `_StreamingNextNPromptSink` takes `prefix_capture` and `capture_boundary`. After
  a chunk's enqueues, when the cumulative absolute position reaches the boundary,
  it calls back with `(prefix_len, boundary_row_ptr)` where the row is the
  chunk's *last* row -- the row the sink carries forward and the next draft step
  consumes, because the sink feeds token[p] against row[p-1]. The callback is
  contained: a refused capture sets `_capture_failed` instead of failing the
  row's prefill.
- **Reachable boundaries are named, not assumed.** One chunk's enqueues are
  batched, so the provider cursor only sits at a chunk end; a boundary inside a
  chunk can never be captured this way. The shipped configuration satisfies the
  alignment (sink chunk rows and cache block size are both 256), so the sink
  records `_capture_missed` and traces when a chunk spans a boundary rather than
  silently never capturing if the chunk width ever changes.
- **Adapter wiring** (`hipengine/generation/qwen35_gguf_mtp2.py`): the sink is
  built with a callback bound to that request (request id, prompt ids, provider,
  target, hidden stride) rather than reading adapter state, so two sinks in
  flight cannot swap rows. `_capture_prefix_checkpoint` now takes `rows=None`
  for the sink route, where the boundary row is already in device memory, and
  keeps host staging for the walk route.
- **Cursor convention fixed** (`hipengine/runtime/qwen35_gguf_nextn.py`): the
  host mirrors are `(last consumed position, consumed count)`, so a prefix of P
  is `position_host == P - 1` with `context_host == P`. Unit 1 required
  `position_host == P`, which no priming route produces -- `_run_block` publishes
  `position_host[0] = position` and `context_host[0] = position + 1` -- so every
  capture would have been skipped. The check now matches the established pair in
  `capture_request_checkpoint` / the after-root snapshot
  (`context_length != consumed_position + 1` is an inconsistent cursor), and
  `restore_prefix_state` publishes the session cursor as `context_length` (the
  next position), matching `restore_request_root_state`.

## Validation

- RED first: the checkpoint tests were rewritten to the real convention and
  failed 4/6 against unit 1's check, then passed after the fix
  (`tests/test_unit_mtp_nextn_prefix_checkpoint.py`, 6 passed).
- New sink tests (`tests/test_unit_qwen35_gguf_mtp_session.py`): the capture
  fires once, at the configured boundary, with the chunk's last row as the
  boundary row; a refused capture is contained and still finishes the sink; a
  boundary no chunk ends on is recorded as missed.
- Focused bundle (session, seam, checkpoint, store, accounting) -> 217 passed;
  `-k "mtp or prefix"` over the suite -> exit 0.
- **Live, served route** (gfx1151, dense Qwen3.8-27B-Q4_K_M, MTP on, capture
  entries=2, trace on, `scripts/sharegpt_mtp_routing_pass.py --num-prompts 2
  --turns 1 --route-mix on --max-concurrency 1`, prompts of 363 and 515 tokens):

  ```
  [mtp2-prompt-sink] first consume request=2 chunk_start=0 rows=256
  [mtp2-prefix-checkpoint] captured prefix=256 blocks=1 held=1
  [mtp2-prefix-checkpoint] captured prefix=512 blocks=2 held=2
  ```

  Both requests completed with no errors. This is the first execution of the
  device-side snapshot on a real executor: the cursor check passes, the KV
  prefix copies at the packed slot/row strides succeed, and the store validates
  the row's block ids.
