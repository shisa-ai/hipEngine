# VibeVoice-ASR Q4_K_M batched prefill: raw-block Q4_K/Q6_K WMMA prefill beats the bf16 lane

## Summary

The Q4_K_M backbone's prefill was a row-by-row loop through the decode path
(3.74 s for an 89-row prompt). It now runs the raw-block Q4_K/Q6_K WMMA
prefill kernels, which read the unmodified GGUF block bytes: no repack, no
fp16 weight copies, no extra resident memory. Measured on zbook / gfx1151,
89-row prompt, both lanes batched through `prefill_rows` in one process,
5 reps after a warmup:

| stage | dense bf16 | Q4_K_M | ratio |
| --- | --- | --- | --- |
| prompt prefill (89 rows) | 0.296 s | **0.195 s** | 1.52x faster |
| decode | 72.2 ms/token | **48.1 ms/token** | 1.50x faster |
| resident weights | 16.66 GB | **6.10 GB** | 2.7x smaller |
| greedy 16 tokens end-to-end | 1.410 s | **0.995 s** | 1.42x faster |

Against the route being replaced: 3.74 s -> 0.195 s = **19.2x**. Token chains
from both lanes are identical.

## Changes

- `kernels/hip_gfx1100/vibevoice/q4.py`: `q4_prefill` is now a batched
  function mirroring `runtime/vibevoice_qwen2.py::_prefill_batched` but with
  the raw-block WMMA prefill GEMMs. Per role: q/k/v and gate/up use
  `gguf_q4_k_wmma_prefill_bf16_f32_out`; o_proj keeps f32 activations and
  uses `gguf_q4_k_wmma_prefill_f32_f32_out`; ffn_down uses the Q4_K bf16/f32
  variant on half the layers and the Q6_K bf16/bf16 variant on the other half
  (Q6_K has no f32-output entry point, so it widens once from a bf16 scratch).
  The bf16 lane's fp16 staging for hipBLASLt is unnecessary here and is gone.
- `tests/test_gpu_vibevoice_qwen2_q4_runner.py`: new
  `test_batched_prefill_matches_row_by_row` oracle.
- `benchmarks/results/2026-09-14-gfx1151-vibevoice-q4-batched-prefill.json`,
  `benchmarks/README.md`, `benchmarks/CHANGELOG.md`, `README.md`.
- `docs/REFACTOR.md`: notes the orchestration duplication against the base
  prefill and the per-call scratch allocation.

## Evidence

Per-GEMM at 146 rows, raw-block WMMA vs the naive raw-block prefill kernels
on the same weights: ffn_gate 170.2 -> 1.92 ms (88.4x), attn_q 27.1 -> 0.35 ms
(77.2x), ffn_down Q4_K 161.5 -> 1.51 ms (107.2x), ffn_down Q6_K 159.8 ->
7.49 ms (21.3x), attn_v Q6_K 3.0 -> 0.51 ms (5.8x), dual gate+up 3.70 ms for
two GEMMs. The dense bf16 lane averages ~1.5 ms per GEMM over its 196 GEMMs,
so the Q4_K route is at parity per GEMM despite dequantising inline.

Q6_K ffn_down is the outlier at 7.49 ms and dominates the remaining prefill
time; a better tile choice or a dedicated Q6_K path is the obvious next lever.

## Validation

  including the greedy chain 16/16 vs the torch fixture and first-position
  logits.
- Batched vs row-by-row post-prefill: top-1 identical, top-5 set identical,
  max logit drift 5.9e-3 relative to the logit scale, cosine 0.99991. The
  batched WMMA tiles reassociate, so this is a same-schedule-class check, not
  bit equality.
- 20-clip WER re-check with the batched prefill launched in the background;
  the 50-clip gate and the 20-clip pack8-decode check are both WER-identical
  to bf16, and the token chains here are unchanged.
