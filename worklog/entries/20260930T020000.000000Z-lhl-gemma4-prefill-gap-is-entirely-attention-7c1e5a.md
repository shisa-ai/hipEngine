# the prefill gap is one kernel: attention is 61 percent at 4096 tokens, and every other term is already linear

## Summary

The loop has optimized a 512-token prefill for roughly three hundred iterations. Measured on the
current tree against the same-host llama.cpp reference, **the gap is not a constant factor — it
widens with prompt length, and at every length the entire gap is attention.**

| prompt | engine tok/s | reference tok/s | gap |
| ---: | ---: | ---: | ---: |
| 512 | 870.4 | 1012.98 | 1.16x |
| 1024 | 704.3 | 1057.48 | 1.50x |
| 2048 | 567.8 | 1067.14 | 1.88x |
| 4096 | **453.9** | **1039.85** | **2.29x** |

The engine's rate falls 2.47x per doubling. **The reference is flat within 3 percent across the
same eightfold range.** So the objective's long-prompt cases are the worst case, and the 512
metric the loop has been holding has been reporting the easy end of the problem.

## The attribution is exact, and it is one term

`gemma4_prefill_kernel_census.py` at three lengths, HIP event pairs around every kernel wrapper,
accounted to 98.5 / 98.9 / 98.9 percent:

| kernel | 512 ms | 2048 ms | 4096 ms | 4096 share | x8 for 8x tokens |
| --- | ---: | ---: | ---: | ---: | ---: |
| **`gemma4_attention_prefill_bf16`** | **134.2** | **1835.2** | **5520.7** | **61.0%** | **41.13** |
| `gemma4_experts_forward_bf16` | 299.1 | 1131.7 | 2250.2 | 24.9% | 7.52 |
| `launch_gguf_linear` | 123.1 | 465.4 | 927.9 | 10.2% | 7.54 |
| `gemma4_router_topk_bf16` | 15.1 | 56.5 | 112.0 | 1.2% | 7.44 |
| `gemma4_rmsnorm_f32w_bf16` | 5.1 | 19.9 | 39.2 | 0.4% | 7.62 |
| `gemma4_head_rmsnorm_f32w_bf16` | 4.6 | 18.1 | 36.0 | 0.4% | 7.84 |
| `gemma4_partial_rotary_bf16` | 3.0 | 11.6 | 22.9 | 0.3% | 7.60 |
| `gemma4_add_rmsnorm_scale_bf16` | 2.8 | 10.9 | 21.3 | 0.2% | 7.57 |

**Every non-attention term scales at 7.4 to 7.8x for 8x the tokens** — linear, and the same shape
as the reference. Attention is the only superlinear term.

**And the non-attention total at 4096 is 3534 ms against the reference's entire 4096-token prefill
of about 3940 ms.** The engine's non-attention work is already at the reference's *whole* prefill
cost. Nothing else in the step is the gap; attention is.

The same holds at the other end: at 512 the non-attention total is 469.7 ms against a reference
prefill of about 505 ms, and attention's 134.2 ms is the excess.

## Why attention is slow, restated with the numbers that matter

The kernel performs **1524.7 GFLOP of attention in 5.5207 s at 4096 tokens — 276 GFLOP/s**, on
the order of **one percent** of this part's bf16 rate.

**The rate is flat in length.** `2026-09-28-gemma4-gfx1151-prefill-attention-length-scaling.json`
measured 426.9, 452.2 and 421.2 GFLOP/s on the sliding layers at 512, 1024 and 2048. So there is
no length-dependent inefficiency to remove: **the kernel is slow at every length and its share
grows only because it is the one quadratic term.**

`20260929T073000` already decomposed it in place: `--mask zero`, which skips every K/V load but
keeps the key loop, removes **25 percent**. The other **75 percent is per-key loop machinery** —
the mask test, the LDS write of the logit, the block max, the softmax rescale, and the loop's own
scalar work. Its structure explains both numbers:

- **one block of 256 threads per (token, head)**, so with head_dim 256 each thread does **one
  multiply-add per key** and the rest of the iteration is overhead, and
- **no query tiling**, so every K/V row is re-read once per query token.

## What this makes the next unit

**A tiled, tensor-core online-softmax prefill attention for gemma4.** Both halves of the current
kernel's cost go away with the standard structure: a block holds a tile of query rows for one
head and walks key tiles, so the K/V load is amortised across the query tile (the 25 percent),
and the score and output products go to the matrix unit instead of a scalar loop with per-key
bookkeeping (the 75 percent).

The tree already contains a working template on this backend:
`hipengine/kernels/hip_gfx1100/attention/laguna_flash_attention_prefill.hip`, an F16-WMMA
FlashAttention with `QUERY_ROWS = 8`, `K_BATCH = 64` online-softmax batches, a `SPAN_SLIDING_RING`
span mode, and the `KVLiveSpans` inputs. It is specialised to `HEAD_DIM = 128`, `KV_HEADS = 8`,
`GQA_HEADS = 8`, so it does not fit gemma4's geometry, but the technique ports.

**gemma4's geometry, from the artifact's own metadata:**

```
embedding_length 2816, block_count 30, head_count 16
key_length 512 / key_length_swa 256
sliding layers (25): head_count_kv 8, window 1024
full layers (5):     head_count_kv 2, no window
```

so the port needs head_dim 256 with 8 kv heads and head_dim 512 with 2 kv heads, at 16 query
heads each.

**The prize, stated conservatively.** At 4096 the step is 9055 ms; attention is 5521 of it. The
non-attention part is 3534 ms and the reference's whole prefill is 3940 ms, so a gemma4 attention
that merely matched the rest of the step's linearity — 134.2 ms at 512, so about 1074 ms at 4096
— would put the step at 4608 ms, **889 tok/s, 1.17x off the reference at every length instead of
2.29x at 4096.**

## What is not claimed

- **The reference ladder is from the recorded baseline artifact, not re-run here.** It was taken
  on this host and artifact with `llama-bench -p 512,1024,2048,4096 -n 128 -r 3 -ngl 99`.
- **The 276 GFLOP/s is my arithmetic** from the artifact's geometry and the sliding window, not a
  counter. The measured rates in the length-scaling artifact (426.9 to 604.6 GFLOP/s) are the
  isolated kernel's and are higher, so 276 is a floor on the in-situ rate, not the kernel's own
  rate. Either way the order of magnitude is one percent of peak.
- **No attention kernel has been written or attempted.** The 889 tok/s projection assumes a
  replacement matching the rest of the step's linearity; it is not a measured result, and the
  current kernel has already survived several optimization attempts (`20260929T060000`,
  `20260929T073000`, iteration 294's address-hoist) that each moved a few percent.
- **The chunking means "attention at 4096 tokens" is 8 chunks of 512**, so the kernel is never
  launched at a 4096-row query tile. A replacement has to be correct and fast at every chunk
  shape, not only at the largest.
