# P5 t1: R0-R4 C1 decode-boundary baseline ladder

## Summary

Roadmap P5, first deliverable: "Capture the R0-R4 C1 decode baseline before
optimizing host code." New harness `scripts/gguf_decode_boundary_ladder.py`
drives the same model, quant, KV policy, prompt token IDs (rng 20260909,
the parity manifest fixture), greedy sampler, and eager (non-graph) mode
through each in-process stack layer and reports per-token-boundary
statistics.

## Changes

- `scripts/gguf_decode_boundary_ladder.py` (new): R0 raw
  `Qwen35GGUFResidentSession.prefill/step` with the shipping selectors; R1
  the packed slot-local server executor entry
  (`prefill_batch_native` + step); R3 the public `LLM.generate` token-ID
  path (EngineService, commands, collectors) with `llm.prepare()` growing
  the resident sessions to the serving context first. R2 (scheduler
  without service wrapper) and R4 (HTTP) come from the existing
  engine-comparison harnesses and the server allocation probe.
- `benchmarks/HARNESSES.md`: harness row (with the PYTHONPATH pinning
  note - site-packages may point at another worktree).

## Validation

W7900 GPU0, 27B Q4_K_M, int8_per_token_head + FP32, 2,048-row prompt,
63 measured decode-token boundaries each:

- R0: prefill 747.9 tok/s; step median 35.146 ms (p95 35.32, min 34.45).
- R1 (packed entry, chunk-outer executor): prefill 732.3 tok/s; step
  median 35.217 ms - **R1/R0 ratio 1.002, +0.07 ms**: the server's
  executor route adds no material decode-boundary overhead.
- R3 (public LLM): 64 tokens in 5.00 s wall; decode-only ~28.6 tok/s vs
  R0's 28.5 - the whole service wrapper costs ~0.1 s (~2%) for the
  request.
- R4 reference: the server allocation probe measured the same request
  wall on the full HTTP route.
