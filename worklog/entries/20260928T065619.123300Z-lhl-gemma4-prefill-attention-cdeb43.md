# the cost is per visited query key pair so token tiling amortizes it and bytes were never the issue

## Summary

Three measurements now agree, and together they name the fix.

The kernel's time is proportional to the number of **(query token, key) pairs it
visits**, and nearly independent of both the bytes moved and the arithmetic
performed inside each visit. A block visits one pair at a time: it holds one query
row and walks every key. Tiling over query rows is therefore the lever, and it is a
different reason from the one flash attention is usually proposed for -- not to
reduce K re-reads, which are nearly free, but to amortize a fixed per-visit cost
over several query rows at once.

## The three measurements

**1. Time tracks work, not blocks.** `full 512d`, `keys = tokens`, `iters=5`:

| tokens | pairs | blocks | ms/launch | GFLOP/s |
|---|---|---|---|---|
| 512 | 131,328 | 8,192 | 6.95 | 618.9 |
| 1024 | 524,800 | 16,384 | 29.67 | 579.6 |
| 2048 | 2,098,176 | 32,768 | 130.94 | 525.1 |

Pairs scale 1 : 4.00 : 15.98 and blocks scale 1 : 2 : 4. Time scales
**1 : 4.27 : 18.84**, which follows work and not the grid. **Wave quantization is
excluded**, which is what this run was for.

**2. Time tracks the key count at fixed grid.** From `20260928T065448`, `tokens=2048`
fixed: work rises 4.27x from 256 to 2048 keys while time rises 6.49x. The
superlinearity is real but modest, and it is not a cache effect -- see below.

**3. Bytes are nearly free.** From `20260928T065531`, bf16 against f32, same
arithmetic and same shapes: **1.024x** on the sliding case and **1.130x** on the
full one for **2x the bytes**.

Add the kernel's own source comment -- the cost is "invariant to the work inside the
key iteration" -- and the picture is consistent: the kernel pays a fixed cost per
key visit, that cost does not depend on `head_dim` (the work inside a visit), and
the bytes are nearly free.

## What the fix is

The achieved rate is 525 to 619 GFLOP/s, which is a few percent of a part that
should sustain tens of TFLOP/s in fp32. The kernel is not short of bandwidth and not
short of FLOPs; it is short of **work per key visit**.

`gemma4_attention_prefill_kernel` launches `tokens * num_heads` blocks and each
block walks the whole key range for **one** query row. Visiting a pair costs what it
costs regardless of how much arithmetic rides on it, so the total is proportional to
`tokens x keys x heads` visits. A block that held `TQ` query rows and walked the keys
once would do the same FLOPs in `1/TQ` of the visits, and the fixed cost of each
visit would be amortized across `TQ` rows.

**This is the same shape as the decode block-count finding** (`20260928T065154`):
both paths are limited by how much work each block can put behind a unit of
scheduling and loop overhead, not by bytes or arithmetic.

## Why this is not the flash-attention argument

The earlier entries proposed token tiling to reduce K re-reads. That reason is dead:
the bf16/f32 ablation shows the re-reads cost at most 13%. Tiling is still the right
change, for the other reason -- fewer visits, same FLOPs. Anyone implementing it
should not expect the win to come from the K traffic, and should measure visits per
block rather than bytes moved.

comparable across entries.

## Caveats

- The pairs-vs-time fit is close but not exact (18.84 against 15.98 at the top end).
  The residual is unmodelled and could be the mild rate decline from 618.9 to 525.1
  GFLOP/s across the three sizes.
- "Fixed cost per visit" is an inference from three scaling measurements plus a
  source comment, not a direct observation of the loop's instruction mix. A profile
  would confirm it and would say which part of the visit dominates.
- `TQ` is not chosen here. Register pressure and LDS budget decide it, and neither
  has been checked.
