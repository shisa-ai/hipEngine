# Establish the F16 Q5_1 down 16-row tile map on the production gate/up path

## Summary

Repairs the runtime prerequisite that blocked the MX-1 **down-only** candidate
`f16_compact_down` (`HIPENGINE_QWEN4_EXP_EXACT_GROUPED_DOWN=0` +
`HIPENGINE_QWEN4_EXP_Q5_1_WMMA=1`). The `elif q5_wmma:` down branch in
`run_qwen4_exp_moe` called the F16 Q5_1 grouped down owner with a host
`wmma_total_rows` that stayed `0` whenever the gate/up leg ran the production
exact route, so the kernel raised
`ValueError: compact_rows, num_experts, and wmma_total_rows must be positive`
before any arithmetic (the blocker recorded in
`20261007T032313…-qwen4exp-mx1-f16-down-only-layer2-gate-blocker-d29d51`).

The branch now establishes a current 16-row WMMA tile map and reads back its
host row count immediately before the owner call. The map is rebuilt from the
current invocation's compact expert starts, so it cannot borrow a stale count or
map, and it overwrites a preceding 32-row `q4_k_mmq_prefill` map that the F16
owner cannot consume. Only the F16 down route pays the extra map launch and D2H
readback; no default production/strict path reaches this branch (`q5_wmma` is
false unless `HIPENGINE_QWEN4_EXP_Q5_1_WMMA` or `PRODUCTION_MOE_PREFILL` is set,
and the production profile pins both off).

This is a control/ownership fix, not arithmetic: no kernel body, no quant
branch, no threshold, no new flag, no default-owner change. The registered
strict fallback (`selected_wmma_iu8_risk_prefill_bf16_bf16_out`) is unchanged.

## Changes

- `hipengine/runtime/qwen4_exp_runner.py`:
  - New module-level helper `_run_qwen4_exp_q51_wmma_down(...)`. It runs
    `qwen35_moe_wmma_tile_map` on the caller's `group_expert_start` buffer,
    synchronizes the stream when one is supplied, copies `group_wmma_total` to a
    host `int64`, validates `0 < rows <= tile_capacity * 16` and `rows % 16 == 0`,
    then calls `qwen4_exp_q5_1_selected_grouped_wmma_prefill_compact_bf16_bf16_out`
    with that count and returns it.
  - The `elif q5_wmma:` branch now calls this helper instead of passing the
    stale host `wmma_total_rows` directly. The owner is still the module-global
    alias the gate's direct-dispatch counter patches, so alias counting is
    unaffected.
- `tests/test_unit_qwen4exp_q51_wmma_down_tile_map.py` (new): mocked CPU
  recording tests. They assert map -> stream sync -> readback -> owner ordering,
  the exact positional count the owner receives, the map arguments come from the
  caller's current buffers, and that zero / non-multiple-of-16 / over-capacity
  counts raise without calling the owner. No stream means no explicit sync.
- `tests/test_gpu_qwen4exp_q51_wmma_down_tile_map_smoke.py` (new): HIP-guarded
  live smoke on the real model. It selects the down-only route, counts the F16
  down owner (recording its row count), the production exact iu8-risk gate/up
  owner, and the sparse repair, and asserts all engaged with the down count a
  positive multiple of 16.

## Ownership and ordering

- Map ownership: the helper rebuilds the 16-row map from this invocation's
  `group_expert_start` (`qwen35_moe_group_prefix` output), so the map and count
  belong to the current call. This covers the production exact gate/up route
  with `Q4_IU8_EXACT` both enabled and disabled, the full F16 composition, and a
  preceding `q4_k_mmq_prefill` 32-row map.
- Stream ordering: the map launch and the readback are on the caller's stream;
  the helper synchronizes that stream before the D2H copy only when a stream is
  supplied, matching the existing tile-count readback pattern.
