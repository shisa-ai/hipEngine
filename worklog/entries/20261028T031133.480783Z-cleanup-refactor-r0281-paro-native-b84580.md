# Fail closed after PARO native graph submission errors

## Summary

The native PARO/DFlash target submission adapter must not replay directly after
an exception from a launcher that may already have mutated device state. Preserve
pre-submission fallback and defer the separate process-wide control migration.

## Changes

- `_try_submit_native_spec_provider_target_graph` propagates exceptions from
  both `launch` and `launch_bound`. Result conversion/validation can fail
  after real submission; the prior catch returned `False`, causing the caller
  to launch the same graph a second time. Terminal result statuses already
  raise; control construction and factory rejection still permit fallback.
- CPU regression tests exercise first/cached submission, RuntimeError,
  TypeError, ValueError and interrupts, assert only one mutation/graph launch,
  no successful replay count, and complete graph-handle cleanup. Additional
  control/factory failures confirm direct pre-submission fallback remains.
- Add public PARO MTP failure nodes using real captured HIP graphs and
  injected launcher-result errors on both submission paths, with checkpoint
  equality, next-request repeat output and session teardown checks. This
  does not claim native-C++ registration on the local gfx1151 backend.
- Move the remaining row6217 interface migration to bottom
  `R0281-PARO-NATIVE`: submission/selected-commit variants need coherent
  profile/diagnostic ownership, provider-specific repair and cache binding.
  Missing backend registration and complete proposal ownership are separate
  implementation work, not evidence-based admission restrictions.
- No flags/defaults removed, kernel/arithmetic changes or speed claims.
