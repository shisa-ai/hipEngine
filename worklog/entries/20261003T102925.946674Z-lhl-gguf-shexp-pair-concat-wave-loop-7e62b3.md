# Route the rows==1 Q8T16 shared gate+up pair through the wave-strided split kernel (bit-identical, -13.8% stage)

## Summary

The Qwen3.6-35B-A3B shared-expert gate+up pair was the worst-bandwidth stage in
the decode step that was not already explained: 87.1 MiB/token at **103 GB/s**
against 199 GB/s for the main dense GEMVs in the same step. The cause is
instruction overhead, not memory behaviour. At rows==1 the pair now runs
`q8_0_t16_dual_split_gemv_kernel` (`WAVE_BLOCK_INDEX = true`), whose loop derives
`block_idx` directly and strength-reduces the tile address, instead of
`q8_0_t16_dual_gemv_kernel`, which recomputes `k/32` and the tile address from a
thread-strided `k` every iteration. Both enumerate the identical `(lane, block)`
set in the identical order, so the change is **bit-identical**.

## Why the two kernels are bit-identical

- concat: `for (k = tid; k < in_features; k += blockDim.x)`, then
  `block_idx = k / 32`, `lane = k & 31`.
- split (`WAVE_BLOCK_INDEX`): `lane = tid & 31`, `wave = tid >> 5`, and
  `for (block_idx = wave; block_idx < blocks_per_row; block_idx += waves)`,
  then `k = block_idx * 32 + lane`.

With `blockDim.x = 128` there are 4 warps, so `waves = 4` and the concat
enumeration `k = tid + 128j` maps to `block_idx = tid/32 + 4j`, `lane = tid & 31`
- exactly the split enumeration. Per-thread `acc[col]` therefore accumulates the
same FP32 terms in the same order, and both finish with the same
`GGUF_T16_WAVE_REDUCE` plus the same 4-sub-group sum. The memory access pattern
is also identical (a warp reads one Q8_0 block per iteration in both), so this
is purely an address-arithmetic difference.

## Changes

- `hipengine/runtime/gguf_linear.py`, `launch_gguf_linear_pair_concat`: at
  `rows == 1` on the Q8T16 dual path, route to
  `gguf_q8_0_t16_dual_gemv_decode_bf16_bf16_out` and write the two halves of the
  concatenated buffer directly (`out_a = out_ptr`, `out_b = out_ptr +
  out_features * sizeof(bf16)`). `rows > 1` keeps the concat kernel, whose
  single-buffer row-strided layout is required.
- `tests/test_unit_gguf_linear_dispatch.py`: the existing dispatch pin now
  asserts the rows==1 split call **and** the rows>1 concat call, including the
  `out_b` offset.

No arithmetic, quantization, or accumulation-order change. No new flag, no
fallback change, no registry change.

## Environment note worth keeping

The `hipengine` editable install points at **`/home/lhl/hipEngine-main`**, a
different tree. A bare `import hipengine` from a directory that is neither the
repo root nor an in-repo `scripts/` entry point resolves there, so a probe script
living in `/tmp` silently measures the wrong commit. In-repo scripts are safe
because they self-insert `REPO_ROOT` (for example `scripts/qwen35_gguf_bench.py`
lines 35-37), and `$PY -c` from the repo root is safe because the cwd leads
`sys.path`. Any out-of-repo probe must set `PYTHONPATH=/home/lhl/hipEngine`. The
chunk work in
`worklog/entries/20261003T100200.274738Z-lhl-gfx1151-h2048moe-prefill-chunk-1024-promoted-d001da`
is unaffected: `scripts/gguf_prefill_chunk_boundary_gate.py` and
`scripts/qwen35_gguf_bench.py` self-insert the repo root, the promoted runs
report `reason=geometry_prefill_chunk_policy` which does not exist in the other
tree, and the shape sweep set the path explicitly.

## Next

- The gate+up shape is now at 142.5 GB/s. The remaining gap to the ~181 GB/s
  ceiling needs more than 64 blocks, which is **not** bit-identically reachable
  at this shape: a K-split reassociates the FP32 sums, `col8` reads strided
  (108 GB/s, slower), and a row-tile wastes rows at rows=1. A wider-block split
  variant (256-1024 threads) changes the reduction tree from 4 to 8 sub-groups
  and would need the production numerical gate; that is the next candidate if
  this stage is revisited.
- `decode_ffn_moe_shared_down` remains at 109 GB/s and is the next-worst weight
  stream after the F32 stages.
- The change is bit-identical with **identical register pressure** (VGPR 56,
  SGPR 128, LDS 512, 128 threads for both kernels) and an identical access
  pattern, so it is not gfx1151-specific by mechanism; gfx1151 compiles the
  gfx1100 kernel bodies, so both backends share the path. The perf magnitude is
  measured on gfx1151 only and is **unverified on gfx1100/W7900**.
