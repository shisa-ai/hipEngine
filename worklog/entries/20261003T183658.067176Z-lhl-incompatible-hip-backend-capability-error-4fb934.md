# Refuse an explicit HIP backend the selected device cannot execute

## Summary

The product segfaults when a caller explicitly selects a HIP backend whose
kernels are compiled for an architecture the selected device does not have. The
live INT8 MTP prefix-reuse module pinned `hip_gfx1151` on a gfx1100 host; the
generator compiled every JIT kernel with `--offload-arch=gfx1151`, and HIP 7.2
aborted the process with a host segmentation fault at the first launch (the raw
Q4_K token embedding). This unit makes that request fail with a named
architecture capability error before any model load or kernel launch.

The check is at execution selection, not in the compiler. Offline
cross-compilation still works: `plan_hip_build`/`build_hip` and
`hip_target_arch_environment("gfx1151")` on a gfx1100 host produce a gfx1151
artifact as before.

## Design

- `hipengine/kernels/backends.py` gains
  - `BackendDeviceCapabilityError(RuntimeError)`,
  - `selected_device_arches()`: the arches of the selected visible HIP device,
  - `require_backend_device_compatibility()`: refuses a HIP backend whose
    declared target arch (`HIP_BACKEND_TARGET_ARCH`) is absent from a known
    selected-device set.
- `hipengine/llm.py` `LLM._resolve_backend()` calls the check after
  `resolve_backend`, before the generator is built or weights load. This is the
  seam the public `LLM` API, `LLM.generate`, and the server (`LLM(...)` at
  `server/api.py:5253`) all pass through.

Decisions the parent's constraints pinned:

- **Selected visible device, not any host device.** `selected_device_arches`
  filters the host arch list by `HIP_VISIBLE_DEVICES`/`ROCR_VISIBLE_DEVICES`
  indices, so a mixed host with the wrong device selected still refuses.
- **`HIPENGINE_HIP_ARCH` is not hardware evidence.** The check reads device
  arches from the ROCm probe only; `HIPENGINE_HIP_ARCH` remains a build override.
- **Unknown detection does not block.** An empty device set, an opaque (UUID)
  visibility selection, or an out-of-range index returns an empty selected set,
  and the check then declines to refuse. Only a known selected-device set that
  lacks the target arch raises.
- **No new engine/dispatch branches.** The check keys off the existing backend
  declaration table.
- **`resolve_backend` stays a pure key resolver.** Registry helpers such as
  `resolve_vibevoice_kernels("hip_gfx1151")` resolve a backend for a dispatch
  table without a device; validating there broke
  `tests/test_unit_vibevoice_registry.py`. The capability check belongs at the
  execution seam, so it is not in `resolve_backend`.

## Changes

- `hipengine/kernels/backends.py`: `BackendDeviceCapabilityError`,
  `selected_device_arches`, `_visible_device_indices`,
  `require_backend_device_compatibility`.
- `hipengine/llm.py`: `LLM._resolve_backend` calls
  `require_backend_device_compatibility`.
- `tests/test_unit_backend_device_capability.py` (new): CPU coverage for the
  named error, compatible execution, auto selection, offline compilation,
  visible-device selection, opaque selection, `HIPENGINE_HIP_ARCH`, and the
  public `LLM` seam.
