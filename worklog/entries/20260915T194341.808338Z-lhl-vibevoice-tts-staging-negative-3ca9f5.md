# Negative result: shared-memory staging is bit-exact but does not recover the dual GEMV's ~1.23x

## Summary

`dense_dual_gemv_out_bf16` reaches 169.5 GB/s at `threads=64` against 138.1 GB/s at
the 256 default, but the thread count moves the reduction width and therefore the
summation order (5 of 17920 outputs by one ulp), which fails the generated-audio
gate. A bit-exact variant was built to capture the win: at K=1536 with 256 threads
the kernel's vectorised main loop never runs (`vec_stride` is 2048, so `main_end`
is 0) and every element is fetched by the scalar stride-256 tail loop, so staging
the weight row through shared memory with 8-wide loads should recover load
efficiency while leaving each thread's element set and order untouched.

It works exactly as intended arithmetically and does nothing for performance.
**Bit-exact on all four shapes tested; 0.99x.** The variant is reverted rather than
kept as neutral code.

## What was measured

Bit-exactness against the original at `threads=256`, rows=1:

| shape (K, N) | result |
| --- | --- |
| 1536, 8960 | BIT-EXACT |
| 1536, 1536 | BIT-EXACT |
| 1024, 4096 | BIT-EXACT |
| 2047, 512 | BIT-EXACT |

Speed, DRAM streaming with the 256 MB flush written **and synchronized** before
timing, median of 12, at (rows=1, K=1536, N=8960, 55.1 MB of weights per call):

| variant | us | GB/s |
| --- | ---: | ---: |
| original | 403.5 | 136.4 |
| staged | 408.3 | 134.8 |

## Why it failed

The kernel is **latency-bound on DRAM**, not limited by load width. The 55 MB of
weights stream from DRAM either way, and at 136 GB/s the original is already at
about 68% of this GPU's ~200 GB/s. The `threads=64` advantage comes from having
more workgroups resident per CU, which hides that latency better; it is not
recoverable by making the same workgroup's loads wider.

That closes both obvious routes to the ~1.23x: a bare thread-count change moves the
arithmetic, and staging is neutral. What remains is a change to workgroup
scheduling or to how many outputs a workgroup owns, and any such change must keep
the 256-wide tree pairing per output to stay bit-exact.

## Changes

- `hipengine/kernels/hip_gfx1100/linear/dense_gemv.hip` and `dense_gemv.py`: the
  staged kernel, its host wrapper and its Python entry point were added, measured,
  and **reverted**. No net change.
- `docs/REFACTOR.md`: records the attempt, its bit-exactness result, its 0.99x, and
  that the two obvious routes are now closed.

## Validation

- `uv run python /tmp/staged_test.py` -> BIT-EXACT on all four shapes; 403.5 us
  original against 408.3 us staged at threads=256 with the flush synchronized.

## Next

The dual GEMV's ~1.23x needs a scheduling or work-partitioning change that keeps
the 256-wide tree pairing, not a load-width change. The larger remaining question
is whether the ~68%-of-peak figure is worth chasing at all against the other
stages, given the LM is 1.450 s, diffusion 1.298 s and semantic 0.781 s of a
4.005 s request.
