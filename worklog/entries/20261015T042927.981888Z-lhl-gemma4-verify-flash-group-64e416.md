# Gemma 4 verify-block flash with one thread per dot product

## Summary

Item 2, second step. After the token-group kernel (bit-identical, 39.6 -> 37.4
ms for five rows at 32K) the remaining cost was the per-(row, key) warp tree.
The group kernel now gives each thread whole dot products (one key, a share of
the rows, eight-element vector loads), reduces row maxima and denominators per
warp, reads query rows from global memory so shared memory holds only the
slice logits, and caps groups at 16 query rows (wider groups lose occupancy:
29.6 ms at 32, 31.5 at 64). Five rows at 32K: 29.1 ms; 8K: 23.2 ms; 600 keys:
21.8 ms. Long-prompt MTP decode phase 2.07x (8K) and 1.89x (32K). This is
production arithmetic (different dot and denominator order); exact verify uses
the single-token kernel per row and is unaffected.

## Changes

- `gemma4_attention.hip`: the group kernel rewritten (thread-per-dot only; the
  bit-identical tree form is removed rather than kept behind a constant),
  `gemma4_load8_as_float`, `kFlashMultiMaxRows = 16`, LDS sizing without staged
  queries.
- `tests/test_gpu_gemma4_flash_decode.py`: multi-token vs per-token now a
  tolerance check (two bf16 ulps of the head row's scale).
- Docs: MTP reference (verify contract, tables), `docs/KERNELS.md`.

## Validation

- Row KL vs one-token decode at 600/1100/8K/32K keys at most 1e-6, no flips.
  A 9-row block at 129 keys shows KL 0.70 with one flip at a 0.43-logit near
  tie; bisected to `5823df24c` (production experts), outside this kernel's
  256-key entry, recorded in the artifact.
- Flash and verify-rows GPU tests 141 passed; the cleaned kernel is bitwise
  equal to the measured build.
- Public path: long-prompt MTP at 8K/32K, identical outputs.
