# the gemma4 MTP head binds to backbone layers 28 and 29 and its spec had lost wo

## Summary
The MTP head's binding to the backbone is now verified against both real
artifacts rather than described, and the reference pseudocode in
`docs/reference/GEMMA4-ASSISTANT-MTP.md` was wrong in a way that would have
produced incorrect output: **it omitted the `wo` output projection entirely.**

Two independent findings, both checked against `llama.cpp@17252c769`
(`src/models/gemma4-assistant.cpp`) and against our own decoders:

1. **`wo` sits between the attention and `attn_post_norm`.** The pseudocode went
   straight from `attention(...)` to `rmsnorm(attn, post_attention_norm)`. The
   real graph is `cur = build_attn(inp_attn, wo, ...)` then
   `cur = build_norm(cur, attn_post_norm, ...)`. The shapes settle it
   independently: `attn_output` is `[n_embd_head*n_head, n_embd]` and
   `post_attention_norm` is `[n_embd]`, so the norm cannot see the
   unconcatenated `[n_head*n_embd_head]` attention output at all.

2. **The input embedding and the output projection are different tables.** The
   graph reads `model_other->tok_embd` — the *backbone's* embedding, width 2816 —
   and uses the head's own `token_embd` (width 1024, `TENSOR_DUPLICATED` as
   `output`) only for the logits. The head's `token_embd.weight` is never an
   input embedding. The pseudocode wrote `x = token_embd[token] # [2816]`, which
   reads as the head's own table but cannot be: the head's is 1024 wide.

Both are recorded in the spec now, along with the binding and rope geometry
below. The forward is the next unit and this is the contract it will be built
from, so an error here is cheaper to fix now than in an acceptance-rate number.

## Changes
- **`docs/reference/GEMMA4-ASSISTANT-MTP.md`**: corrected forward pseudocode
  (`wo` restored, `freq_scale` un-hardcoded to `freq_scale`), five easy-to-get-wrong
  details instead of three, and the KV-binding section extended with the
  head-count match and the rope-config equality. "What is implemented" now
  records the device loader; "What is not" records why the head's blocks are not
  `gemma4_layer_forward_bf16`.
- **New `tests/test_unit_gemma4_assistant_kv_binding.py`**: three tests asserting
  the binding across both real artifacts. No HIP — both sides are metadata plus
  one 1 KB `rope_freqs` tensor.
- **The head's per-block KV head counts are not arbitrary.** The head declares
  `head_count_kv = [8, 8, 8, 2]`; the backbone's per-layer pattern is
  `[8, 8, 8, 8, 8, 2]` repeating over 30 layers. Layer 28 is `28 mod 6 == 4` (8 KV
  heads, sliding-window) and layer 29 is `29 mod 6 == 5` (2 KV heads, full
  attention). Three SWA head blocks read layer 28 and ask for 8; the full block
  reads layer 29 and asks for 2. Both sides also carry `head_count = 16` with
  `key_length` 512 and `key_length_swa` 256.
- **So the shared cache needs no head remapping and no GQA adaptation** for the
  two layers the head reads: the head's attention geometry is *identical* to the
  backbone layer's. A test asserts the equality block for block, plus a second
  test asserting the two bound layers differ in KV head count (8 vs 2) so the
  first equality cannot pass for a head that ignores its own `head_count_kv`.
- **The head's rope geometry is the backbone layers' own.** Decoding the
  backbone gives layer 28 as `(default, head_dim=256, rotated_pairs=128,
  freq_base=1e4)` and layer 29 as `(proportional, head_dim=512, rotated_pairs=64,
  freq_base=1e6)`. Decoding the head's metadata and its `rope_freqs`
  independently gives exactly those two. The head's `rope_freqs.weight` is 256
  entries — the first 64 exactly `1.0`, the remaining 192 `1e30` — which is the
  same span-marker encoding the backbone uses and which
  `gemma4_rotated_pair_count` already decodes. So the head reads the backbone's
  tables rather than deriving a second schedule, and the equality is itself the
  check.

## Validation
- 3 new tests pass against both real artifacts, and 32 pass across the assistant
  and loading bundle.
- Every claim above was computed, not read: `head_count_kv`, `is_sliding`,
  `head_dim`, and `rope_for_layer` for layers 28/29 were decoded through our own
  `gemma4_gguf_config_from_metadata` and compared to the head's decoded config
  field by field, printing `MATCH=True` for all four blocks. The `rope_freqs`
  content was read from the artifact (`64` values equal to `1.0` of `256`).
- The reference source was read directly at the pinned commit rather than
  trusted from the spec's transcription, which is what surfaced the `wo`
  omission.
- `python3 scripts/docs/check_all.py`: all 4 gates pass.
- No correctness gate applies: no kernel changed, no arithmetic changed, and no
  performance claim is made.

## Next
1. **The forward.** Now fully specified. The head's blocks are not
   `gemma4_layer_forward_bf16` — that does pre-norm with a KV write and a
   `1/sqrt(head_dim)` scale, where this does post-norm with a shared-KV read and
   scale 1.0 — so the forward composes `launch_gguf_linear`,
   `gemma4_rmsnorm_f32w_bf16`, the rope tables and the attention kernel directly.
2. **The KV read path.** The backbone runner has to expose layer-28/29 K and V,
   the backbone's embedding table, and the layer-28/29 rope tables; the draft step
   has to sit at the position the backbone last wrote.
3. Registration through `register_gguf_mtp2_adapter`, then `supports_speculative_mtp`.
4. End-to-end through `hipengine.LLM.generate()`: acceptance rate and decode rate
   against the 22.38 tok/s non-MTP baseline.
