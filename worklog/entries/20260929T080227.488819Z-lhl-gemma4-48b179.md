# Gemma 4 P2: ABI mapping for flash_attn_tile, and the dtype fork

## Summary

Iteration 43 proved `flash_attn_tile<512,512,4,8>` instantiates on gfx1100.
This one reads the upstream launcher to learn what the kernel actually expects,
maps it onto Gemma's layout, and finds the one decision that has to be made
before any wrapper code is written.

## The mapping

`launch_fattn` in `fattn-common.cuh` is the single place the 33 kernel
arguments are constructed:

```c
const uint3 ne01 = init_fastdiv_values(Q->ne[1]);
fattn_kernel<<<blocks_num, block_dim, nbytes_shared, stream>>>(
    Q->data, K_data, V_data, mask?->data, sinks?->data, KV_max.ptr,
    dst, dst_tmp_meta.ptr,
    scale, max_bias, m0, m1, n_head_log2, logit_softcap,
    Q->ne[0], ne01, Q->ne[2], Q->ne[3], Q->nb[1], Q->nb[2], Q->nb[3],
    K->ne[0], K->ne[1], K->ne[2], K->ne[3], nb11, nb12, nb13,
    nb21, nb22, nb23,
    mask->ne[1], mask->ne[2], mask->ne[3], mask->nb[1], mask->nb[2], mask->nb[3]);
```

with `n_head = Q->ne[2]` and `scale/max_bias/logit_softcap` copied out of
`op_params`. Against Gemma's row-major tensors this is straightforward:

| argument | Gemma expression |
| --- | --- |
| `ne00` | `head_dim` |
| `ne01` | `init_fastdiv_values(tokens)` |
| `ne02` / `ne03` | `num_heads` / `1` |
| `nb01..03` | `head_dim*2`, `head_dim*num_heads*2`, `0` |
| `ne10..13` | `head_dim`, `keys`, `num_kv_heads`, `1` |
| `nb11..13` | `head_dim*2`, `head_dim*num_kv_heads*2`, `0` |
| `nb21..23` | same as `nb11..13` (V has the K shape) |
| `ne31..33`, `nb31..33` | from the keep mask `(tokens, keys)` |

## The geometry matches exactly

The model config is the reason this row quotes `<512,512,4,8>` and not some
other shape:

- global layers: `global_head_dim: 512`, `num_attention_heads: 16`,
  `num_global_key_value_heads: 2` → **GQA ratio 8**
- `launch_fattn_tile_switch_ncols2` picks `ncols2 = 8` on
  `gqa_ratio % 8 == 0`, and `cols_per_block = 32` on `Q->ne[1] > 16/ncols2`
  (any prefill wider than 2 tokens), giving `ncols1 = 32/8 = 4`

So the shape falls out of the model rather than being chosen. Two gates guard
it: `use_gqa_opt` needs a mask present and `max_bias == 0` (Gemma is ungated,
no ALiBi), and `K->ne[1] % FATTN_KQ_STRIDE == 0` with **`FATTN_KQ_STRIDE =
256`** — keys must be a multiple of 256. 512 and 1024 qualify; partial contexts
do not, and fall back to the exact block kernel, which is the fallback the
invariant requires anyway.

## The fork: dtype

`launch_fattn` asserts `Q->type == GGML_TYPE_F32`, `KQV->type ==
GGML_TYPE_F32` and `mask->type == GGML_TYPE_F16`, and passes
`need_f16_K/need_f16_V` so that non-f16 K and V are converted into staging
buffers. Gemma holds Q and the output in BF16, the keep mask as uint8, and the
KV cache in BF16.

Staging the way upstream does is not free. Per global layer per call at 1024
keys: roughly 2 MB of bf16→f16 for the KV, and for Q
`512 tokens x 16 heads x 512 dims` written out as f32 — about 16 MB of f32
staging per layer before the kernel executes a single FMA. Against a 39.2 ms
budget for all five global layers, that is not a rounding error.

Two ways out, and they are not equivalent:

1. **bf16-native load path.** Modify the kernel to read `__nv_bfloat162` and
   use `v_dot2_bf16_bf16_f32`, which RDNA3 has. Keeps the ABI clean and avoids
   all staging, but means editing the ported kernel body, which weakens the
   "this is upstream's kernel, verified upstream" argument.
2. **f16 KV mirror.** Keep an f16 copy of the KV cache for these five layers,
   written at append time, so the kernel's `need_f16_K` path never fires.
   Leaves the kernel body untouched but adds memory and a second write path
   into the paged-KV machinery.

This decision comes *before* the wrapper, because it decides whether the kernel
body is reused unmodified or not. It is recorded rather than resolved here: it
is a real trade between port fidelity and staging cost, and picking it without
measuring both would be a hunch dressed as a decision.
