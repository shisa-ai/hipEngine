# Resolve EVIE/Surya runtime library ownership

## Summary

R0483 resolves on its explicit-ownership branch: `EvieRunner` and
`SuryaGpuRunner` keep owning the whole-library JIT artifacts they dispatch
through, and that boundary is documented rather than migrated to
backend-provided runtime operations.

The alternative is not a documentation gap but a new subsystem. Whole-library
lifetime already has an owner outside the four-axis registry: `hipengine.core.build`
compiles, keys and caches the loaded `ctypes.CDLL`, and the family runtime holds
the reference it passes to the launch wrappers. A backend-operations migration would need a distinct declared boundary to
avoid either a fifth registry axis or a duplicate per-operation table. This
unit chooses the existing explicit-reference contract instead; it does not
assert that every possible backend-provider design would be invalid.

The same explicit-ownership pattern is the dominant family-runtime convention:
`hipengine/runtime/qwen35_gguf_runner.py` holds 14 distinct library handles
across 23 acquisition sites, 21 modules under `hipengine/runtime/` assign a
library-handle attribute, and `MoonshineDecoderLibraries` is the injectable
variant. EVIE/Surya are not outliers. No arithmetic, HIP target, injection
parameter or symbol dispatch changes under this decision.

### Inventory the decision rests on

- Builders, all in the backend tree: `build_evie_ops` and `build_surya_ops`
  (`hipengine/kernels/hip_gfx1100/{evie/evie_ops.py,surya/surya_ops.py}`,
  families `evie_ops` / `surya_ops`), `build_qwen35_linear_attn_conv` and
  `build_qwen35_linear_attn_gdn`
  (`hipengine/kernels/hip_gfx1100/linear_attn/`). Each forwards to
  `hipengine.core.build.build_hip`.
- Constructors: `EvieRunner.__init__` (`hipengine/runtime/evie.py:185-187`)
  acquires `library`, `conv_library`, `gdn_library` with
  `X or build_X(load=True)` and accepts all three as keyword injections.
  `SuryaGpuRunner.__init__` (`hipengine/runtime/surya.py:573-576`) does the same
  for those three and additionally builds `self.surya_library` unconditionally;
  `surya_library` has no injection parameter.
- Cache and target arch: `build_hip` keys the loaded-library cache on family,
  profile, output name, source paths, cache root, resolved target arch, compiler,
  compiler version, include dirs and extra flags, and memoizes the result in
  `_LOADED_LIB_CACHE` / `_RESOLUTION_CACHE` / `_FAST_PATH_CACHE`. Target arch is
  explicit `target_arch` or `HIPENGINE_HIP_ARCH`, participates in the cache key
  and is emitted as `--offload-arch`. The gfx1151 backend package documents that
  it compiles the gfx1100 kernel bodies for its own architecture, and `build_hip`
  keeps the target arch in the cache key, so the runtime import path does not
  narrow a supported target.
- Symbol dispatch: one runner dispatches 25 distinct `hipengine_evie_*` symbols
  from `self.library` (EVIE) or 16 of them (Surya), plus conv/GDN symbols through
  the shared launch wrappers, plus 3 direct `hipengine_surya_*` lookups and 6
  wrapper calls passing `library=self.surya_library`. The registry granularity is
  the operation, not the shared object.
- Lifetime: neither `close()` unloads a library, and no `dlclose` exists anywhere
  under `hipengine/`. A default library therefore lives in the process cache; an
  injected handle is held by the runner for its own lifetime and is never
  released by it. There is no use-after-unload path in either direction.
- Registry state: `register_evie_ops_kernels` exists but is never called, and
  `surya_ops` registers nothing. Conv/GDN register per-operation callables whose
  wrappers do `library = library or build_X(load=True)`, i.e. they resolve the
  same process-cached handle when the runner passes none.

### Proposed edit 1 — `docs/ARCHITECTURE.md`

Insert as a new paragraph after the sentence ending "add model/backend branches
to the scheduler." (line 32), before `## Production request path`:

```text
Whole-library JIT artifacts sit on a separate ownership boundary from those
keys. A backend source family (`evie_ops`, `surya_ops`,
`qwen35_linear_attn_conv`, `qwen35_linear_attn_gdn`) compiles to one shared
object whose launch wrappers accept the loaded library as an argument.
`hipengine.core.build` owns compilation, the target architecture
(`HIPENGINE_HIP_ARCH` / `--offload-arch`), the cache key and the process-level
loaded-library cache, so repeated `build_X(load=True)` calls with the same build
identity return the same `ctypes.CDLL`. The family runtime that dispatches
through a library owns the reference it passes: `EvieRunner` and
`SuryaGpuRunner` hold `library`, `conv_library` and `gdn_library`
(`SuryaGpuRunner` also `surya_library`) for their own lifetime, accept
caller-supplied handles for the shared families, and never unload one, including
in `close()`. Adding a kernel family adds a builder in the backend tree and an
explicit owner in the dispatching runtime; it does not add a library registry or
a fifth kernel-key field.
```

### Observations that do not block closure

- `SuryaGpuRunner.surya_library` is built unconditionally and cannot be injected,
  unlike the three shared handles. That asymmetry is an injection convenience
  gap, not an ownership contradiction; no test or script currently injects any
  runner-level library, so nothing depends on it either way.
- `register_evie_ops_kernels` is an unreferenced hook that would register one
  evie symbol while the runner dispatches 25 directly. If it were ever wired up,
  the process cache would still return the same `CDLL`; it is dead code, not a
  second owner.
- Both runners import the gfx1100 backend tree directly. That is coherent while
  the only GPU routes are the two HIP backends that compile those sources. A
  non-HIP backend for Surya or EVIE would need a runtime-side backend selection
  seam; that port is the trigger to revisit this boundary, not missing evidence.
