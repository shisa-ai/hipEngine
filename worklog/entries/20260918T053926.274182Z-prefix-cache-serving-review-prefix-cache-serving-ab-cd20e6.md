# Measure prefix caching for multi-turn serving: reuse works, the suffix prefill does not pay

## Summary

Same-host A/B of `HIPENGINE_PREFIX_CACHE=off` against `radix` on the multi-turn
serving harness, one repetition per mode, identical command otherwise. Radix now
resolves **16 of 27 lookups** and reuses **42,496 of 87,582 prompt tokens**, but
the run is **6.4% slower overall** (399.0 -> 424.5 s wall, 14.92 -> 14.02 output
tok/s).

| Lane kind | off wall | radix wall | delta | radix hits |
| --- | ---: | ---: | ---: | ---: |
| code cumulative | 122.6 s | 112.4 s | **-8.3%** | 6/9 |
| code fixture | 118.9 s | 119.0 s | +0.0% | 3/9 |
| sharegpt | 157.4 s | 193.1 s | **+22.7%** | 7/23 |

The reuse path is the cause, and it is not the prefix bookkeeping. Every hit
turn prefills its unmatched suffix through `prefix_c1_suffix_prefill_chunks`,
which runs one `session.step()` per suffix token. That costs a **constant
34.0 ms/token** (31.5-34.5 across all 16 hit turns, independent of suffix
length), against **1.8 ms/token** for the batched full prefill the same turns
would otherwise run. Reuse therefore pays only when the suffix is short relative
to the reused prefix: an 8,192-token reuse with a 196-token suffix saves about
14 s of batched prefill for 6.7 s of serial suffix work (that is the code
cumulative win), while a 256-token reuse with a 70-token suffix spends 2.4 s to
save 0.7 s (that is the ShareGPT loss).

Prefix bookkeeping is cheap by comparison: 35 snapshot captures totalling
2.34 GB for 41 turns, 1.07 GB of state clones across the 16 hits, and zero
admission fallbacks. All 16 hits came from retained snapshots, and the deepest
reuse was 8,448 tokens.

Decision: `HIPENGINE_PREFIX_CACHE` stays `off`. The flag remains available.

## Validation

Exact command (one invocation per mode, `off` first, same process count and host):

```
HIP_VISIBLE_DEVICES=0 python3 scripts/prefix_cache_multiturn_bench.py \
  --backend hip_gfx1151 --lane-kinds all --modes off --repetitions 1 \
  --turn-limit 3 --agentic-workloads small_repo growing_history medium_repo \
  --sharegpt-tokens 96 --sharegpt-long-tokens 384 --code-tokens 128 \
  --max-sequence-length 12288 --json /tmp/ab-off.json
HIP_VISIBLE_DEVICES=0 python3 scripts/prefix_cache_multiturn_bench.py \
  --backend hip_gfx1151 --lane-kinds all --modes radix --repetitions 1 \
  --turn-limit 3 --agentic-workloads small_repo growing_history medium_repo \
  --sharegpt-tokens 96 --sharegpt-long-tokens 384 --code-tokens 128 \
  --max-sequence-length 12288 --baseline-artifact /tmp/ab-off.json \
  --json /tmp/ab-radix.json
```

- Host `zbook`, AMD Radeon 8060S / `gfx1151`, Qwen3.6-35B-A3B `UD-Q4_K_M`,
  repo revision `6123174da`, 14 lanes, 3 turns each, greedy `ignore_eos`, one
  repetition per mode.
- Both modes ran the same 5,918 c1 decode steps, so the delta is prefill and
  admission only.
- Correctness: this is a serving-economics A/B; it does not re-run the byte-exact
  gfx1100 prefix gates or the generated-ID task gates. Reuse correctness is
  covered by the prefix gates named in the two preceding entries.
- Single repetition per mode on one host, so the per-lane-kind deltas carry
  run-to-run variance the harness does not yet quantify; the 34.0 ms/token
  suffix cost is a mechanism measurement and is not variance-sensitive.
