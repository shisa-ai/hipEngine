# Re-measure the per-prefill attribution and compare both engines in one taxonomy

## Summary

Two things, and the second is the one with new information.

**The attribution re-measures and reproduces.** The 2026-09-16 protocol re-run at
`725794c3f` on a clean tree gives 22083.6 ms attributed over a 22698.6 ms window,
9652 kernels, 0 ms unattributed -- the same kernel count, a window 1.0% smaller,
and **the same `logits_sha256` and `token_id` as the production profile in the
2026-09-16 recoverable-time artifact**. The default path is byte-identical
across the two days, which turns "nothing changed" from an assumption into a
check.

**The comparison is now one taxonomy instead of two.** The earlier comparison put
our per-role table next to the comparator's per-family table, which compares two
taxonomies: hipEngine carries the tensor role in a ROCTX range, so one symbol
serves several roles, while the comparator names the family in the symbol.
`scripts/qwen4exp_comparator_role_map.py` already existed to express both in one
vocabulary and already classified the comparators; it gained a `map_hipengine`
mapper, so all three engines are classified from kernel symbols by one module
with one family list.

### The gap decomposition repoints the tuning

`22083.6 - 3760.4 = 18323.2 ms`. Dense projection is **50.1%** of it, and four
families -- dense, expert gate/up, hyper-connection and expert down -- are
**87%**. The ratio column and the gap column disagree about priority and the gap
column is the one that matters: `qsa_attention` has the worst ratio at 9.01x but
only 6.8% of the gap.

### Two readings the ratio column gets wrong

**`elementwise_norm` is not a gap.** We are at 180.2 ms against PR #63's
331.7 ms, 0.54x, with the comparator spending 8.8% of its kernel time there
against our 0.8%. The status document listed elementwise/norm fusion as an open
mechanism; that item is retired.

**`expert_down` is not one of our better families.** Against the base it reads
2.08x, our second-best ratio; against PR #63 it is 5.79x, because PR #63 cut
that family by 64.1% and we have no equivalent kernel. The base column flatters
us on exactly the family where the comparator moved furthest.

### The repair fold is visible, not hidden

Our 1434.4 ms of iu8 exact-repair is folded into the matmul family it corrects,
because that is the operation whose cost it is, and also totalled separately as
`risk_or_repair_ms`. The comparator has no equivalent pass, so that 1.43 s is a
real cost of our current default sitting inside `expert_gate_up` and
`expert_down`.

## Validation

- `--strict` on the comparison: the mapper places every hipEngine kernel above
  1 ms. It found one on the first run -- the prompt K/V write, now mapped to
  `elementwise_norm` to match the comparator rules, where the same bytes are a
  `set_rows`/`cpy` op and land in that family.
- Regression check on the pre-existing mappers: `map_llamacpp` and `map_mmb`
  still return the same families for the Q4_K gate/up, Q5_1 down, `hc_combine`,
  GDN, `mmb_routed_glu`, `mmb_routed` and `mmb_dense` cases the comparator side
  depends on.
- The comparison is deterministic: a re-run produces a byte-identical JSON.
- Reproduction: same 9652 kernels, same `logits_sha256`, window within 1.0%.

## Two protocol traps, both now recorded

Neither is recoverable from an artifact, and each cost a run:

1. `--launch-census` only names the output path. Collection is off unless
   `HIPENGINE_KERNEL_CENSUS` is set, and without it the run completes normally
   and writes a well-formed census with `total_launches: 0`. Nothing in the child
   report distinguishes that from a real result.
2. `rocprofv3` writes into a `gfx1151/` subdirectory of the directory it was
   given, so the analysers cannot glob the parent.

`--require-cached-build` is not part of this protocol; it fails closed on any
kernel not built under the current environment's cache key.
