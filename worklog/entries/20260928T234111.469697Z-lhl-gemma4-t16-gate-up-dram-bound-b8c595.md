# correction to the T16 leaf demand paragraph, and the verified in-situ call geometry

## Summary

Corrects and extends
`worklog/entries/20260928T233806.520482Z-lhl-gemma4-t16-gate-up-dram-bound-0619de.md` and the
matching fields in `benchmarks/results/2026-09-29-gemma4-t16-gate-up-dram-counter-measurement.json`.
**No measured number changes and the verdict does not change.** Three things were fixed:

1. The demand paragraph conflated the standalone fixture with the model.
2. The premise correction mixed a corrected numerator with the wrong duration.
3. The counter profile's structure was misread, so the in-situ call geometry is now verified
   directly instead of inferred.

One new open question is recorded, and it is a real disagreement between the measurement and the
model: **the leaf reads 16.0 MB less from DRAM per call than its own distinct weight tiles.**

## 1. The demand paragraph: the fixture's uniform load is not the model's load

The superseded entry said the tile bytes are "demanded 2x at the model's 32 rows per expert". The
fixture runs a *uniform* 32 rows per expert, so `ceil(32/16) = 2` row tiles per expert. The model's
real 4096 compact rows over 128 experts are a multinomial split that pads to **300.1 row tiles per
call**, i.e. **2.345** tiles per expert, so the in-situ weight demand is **687.9 MB**, not 586.8 MB.
The activation multiple is likewise 88.0x on the fixture and **103.2x** in situ.

The earlier numbers were internally consistent - 586.8 + 2,030.0 = 2,616.9 MB over the fixture's
5.304 ms is 493.4 GB/s, and `weight_demand = tiles x row_tiles_per_expert` is correct for a uniform
load. The defect was labelling: a fixture figure presented as "the model's".

## 2. The demand model, now derived from the kernel rather than asserted

Read off `hipengine/kernels/hip_gfx1100/quant/gguf_q4_k_t16_selected_prefill.hip` lines 279-312:

- The kernel walks `tm = 0..1` (two 16-column output tiles per 32-column block) and for each walks
  all `blocks_per_row = 11` K blocks, so a block reads **22 tiles**, not 44.
- `expert_id = tile_expert[row_tile]`, so one row tile belongs to exactly one expert and each
  expert's weight is read once per 16-row tile of that expert.
- Each `tm` re-reads the same 16 rows' full K row, so a block demands
  `2 x 16 x 2816 x 2 = 180,224 B` of activation.

| | uniform fixture, 32 rows/expert | in situ, 4096-token prefill |
| :--- | ---: | ---: |
| blocks | 11,264 | 13,203 |
| row tiles | 256 | 300.1 |
| weight demand | 586.8 MB (2.0x) | 687.9 MB (2.345x) |
| activation demand | 2,030.0 MB (88.0x) | 2,379.9 MB (103.2x) |
| total demand | 2,616.9 MB | 3,067.8 MB |
| duration | 5.304 ms | 4.997 ms |
| GB/s of demand | 493.4 | 613.9 |
| measured DRAM reads | 400.4 MB | 277.3 MB |
| cache-served fraction | 84.7% | **91.0%** |

The 91 percent cache-served fraction is the useful output of this correction: it agrees with the
independently measured **87.4 percent L2 hit rate** on the same kernel, from a different counter.

## 3. The in-situ call geometry, verified instead of inferred

The counter profile holds **464 dispatches = 2 prefills x 232 calls**, and segmenting on
inter-dispatch gaps above 20 ms splits it into **8 chunks of 29 layer dispatches**, i.e. 8 chunks of
512 tokens over the 29 Q4_K layers. `scripts/gemma4_t16_leaf_call_geometry.py` wraps the production
launcher and records that every call is handed the same thing:
`compact_rows = 4096, num_experts = 128, in_features = 2816, intermediate = 704` - **one distinct
geometry across all 232 calls**, identical to the fixture's.

`Grid_Size` in the counter CSV is in **work-items, not blocks**. Read correctly: 382,976 to 459,008
work-items over 32-thread blocks, mean 422,485, i.e. **13,203 blocks and 300.1 row tiles** per call.
The fixture's own `Grid_Size` is 360,448 = 11,264 blocks = 256 row tiles, exactly its uniform value.
So the fixture's geometry is the in-situ geometry with the expert load flattened, and the only
difference between them is the row distribution.

This also settles the premise: the prior entry's 4096 x 2816 x 2 activation footprint is correct.
The numerator was right about the footprint and wrong about the traffic, which is the distinction
this artifact turns on.

## 4. A denominator fix on the premise correction

The superseded entry quoted "75.1 GB/s, 1.22x higher". The ratio is right but 75.1 GB/s mixed a
corrected numerator with the fixture's median duration. Apples to apples, on the prior entry's own
5.016 ms denominator: **400.4 MB / 5.016 ms = 79.8 GB/s**, against the prior 65.4 GB/s. The artifact
now carries both that and the fixture-duration figure.

## 5. New open question: the measured read is below the kernel's own tile bytes

**Per dispatch the measured DRAM read is 277.45 MB (run 1) and 277.18 MB (run 2), 0.1 percent
apart. The kernel's distinct tile set is 293,404,672 B = 293.4 MB, and all 128 experts are used in
every call, so every tile is touched. A full pass must fetch 293.4 MB from DRAM. The measurement is
16.0 MB below that.**

**The fixture does not reproduce it.** At rows/expert 16 the fixture demands the tile set exactly
once (5,632 blocks x 22 tiles = 123,904 tile reads, the distinct tile count) and measures 333.5 MB -
*above* the tile bytes, as expected. At rows/expert 32 it demands it twice and measures 400.4 MB. So
the fixture reads at least its tile set in both cases, and the sub-floor reading is specific to the
in-situ run.

**Ruled out, each with a check:**

| candidate | why it is out |
| :--- | :--- |
| geometry mismatch | Verified above: identical geometry, one distinct shape across 232 calls. |
| a different tile repack | Production calls `hipengine.quant.gguf_q4_k.repack_gguf_q4_k_tile16` (`hipengine/loading/gemma4_gguf_device.py`), the function the fixture calls, and the kernel template argument is `qmicro = false`. |
| the wrong kernel symbol | The counter matched `gguf_q4_k_t16_selected_dual_wmma_prefill_compact32_kernel<unsigned short, false>`. The 232 calls per prefill and the 4.8 ms per call both match the census's t16 gate/up leaf line, and the `_shared_x` sibling cannot match the regex. |
| counter inaccuracy | Exact to 0.0004 percent on a known-answer cold stream; an independent GCEA block agrees to 0.64 percent. |
| cross-call MALL retention | The profile is chunk-major, so 29 other layers' tile sets (about 8.5 GB) pass between two calls for the same layer. A 32 MB MALL cannot carry 16 MB across that. |

**Untested candidates, listed as candidates:**

- Part of each 2368-byte tile is never read by the kernel, and the unread bytes are whole 128-byte
  lines. `123,904 x 2240 B = 277.5 MB`, which is 0.02 percent from the measurement - but the same
  arithmetic does not fit the fixture, so this is arithmetic that fits rather than a demonstrated
  mechanism.
- A request is issued for fewer than 128 bytes and the DRAM burst is shorter than the counter's unit
  assumption on this access pattern. The counter was calibrated on a coalesced contiguous stream,
  not on a 2368-byte stride.
- Part of the tile set is resident from the same layer's preceding kernel, if the tile buffer is
  touched outside this kernel.

**Verdict impact: none, and the direction is conservative.** The measurement says the leaf pays for
*less* DRAM than its own weight pass requires. Every version of this makes the bandwidth hypothesis
weaker, not stronger.
