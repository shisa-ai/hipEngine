# Screen first GDN scratch allocation on real Q5 decode owner

## Summary

Real Q5_1 decode down/combine shows no large persistent penalty across the
first GDN scratch allocation. No optimization or runtime change is proposed.

## Changes

- New `scripts/qwen4exp_decode_scratch_probe.py`: real layer0 Q5_1 weights,
  synthetic BF16 activations/routes, exact output checks and clocks. Validate
  tensor quant/shape before launch. Hash actual loaded libraries and weights.
- `benchmarks/results/2026-09-28-qwen4exp-decode-scratch/` records all commands,
  model/quant/shape/physical host/hardware, samples and compact trace evidence.
- Four fresh sham/scratch/scratch/sham after/before median ratios:
  0.975027/0.991009/0.993447/0.999158. This is a causality screen, not a rate win.

## Validation

- Four unprofiled processes and a separate cached-build profiler run succeed.
  Victim outputs identical before/after and across processes. GDN output/state
  matches strict parent checked only after timing to preserve first-trigger order.
- Trace proves six zero-scratch Q5_1 calls before the first 1,638,400-byte scratch
  allocation, one 36-byte GDN call, three Q5_1 calls, then the GDN oracle. All
  victim/trigger calls and allocation use queue1.
- Boundary snapshots SCLK2900/MCLK1000 throughout, not continuous telemetry.
- `python3 -m py_compile scripts/qwen4exp_decode_scratch_probe.py` passes.
- Existing variants only; targeted real GPU runs are the executable checks.
  No math/dispatch change and no RED-first timing hypothesis test is possible.
  This does not replace any production numerical admission gate.
