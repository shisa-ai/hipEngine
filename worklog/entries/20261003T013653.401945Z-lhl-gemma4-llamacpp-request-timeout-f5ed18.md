# Make Gemma llama.cpp long-context request timeout explicit

## Summary

The same-artifact llama.cpp reference harness now accepts
`--request-timeout <seconds>` for completion requests. The default remains 600;
long-context rows can explicitly use 3,600 or more without changing their timing
accounting. Both warmup and sample requests use the declared timeout, which is
recorded in the JSON artifact. Nonpositive and nonfinite values fail before
model loading or GPU access.

The CPU-side comparison audit found an inaccurate docstring: it described the
comparator as graph-free. Its local `build-hip/CMakeCache.txt` enables
`GGML_HIP_GRAPHS`, and this harness passes no graph-disable flag. The docstring
now says to preserve the comparator's shipped graph configuration and record
actual runtime graph behavior from its server log. The comparator source is
`~/llama.cpp/llama.cpp-hip` at
`17252c769a63c1cb650ce98ae309cf4de0da7778`; this unit does not rebuild or edit it.

## Changes

- `scripts/gemma4_llamacpp_reference_bench.py`: finite positive timeout option,
  forwarding to both request loops, recorded timeout, corrected graph prose.
- `tests/test_unit_gemma4_llamacpp_reference.py`: RED on the absent timeout
  option; mocked CPU request flow verifies forwarding to both loops and that
  both warmup and sample records survive. Invalid values fail before loading.

## Validation

- `.venv/bin/python -m pytest tests/test_unit_gemma4_llamacpp_reference.py
  tests/test_unit_gemma4_campaign_bench.py -q`: 23 passed.
- The mock drives the CLI with `--request-timeout 2400`, records exactly two
  calls at 2400 seconds, and verifies the artifact timeout. It starts no server
  and calls no GPU runtime.
- No live comparator timing is claimed by this unit. The full numerical quality
  packet owns the GPU while this independent host-side repair is validated.
