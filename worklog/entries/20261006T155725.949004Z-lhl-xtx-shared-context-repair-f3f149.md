# Repair GPU1 shared context allocation and growth

## Summary

Repair startup, shared KV pool growth, and memory accounting for Qwen3.8-27B Q4_K_M on GPU1 (RX 7900 XTX, 24 GiB). Acceptance requires growing shared context and efficient memory use, not a small-context workaround. No arithmetic changes are planned.

## Changes

- Investigation: global pool creation subtracts a hard-coded 3 GiB from free memory after session allocation, independently of the configurable capacity-estimator reserve.
- Investigation: the pool requests a 128-page initial floor plus workspace pages even when the requested context is small.
- Reproduced in earlier server logs: the retry schedule continues through zero to negative contexts when its attempt budget is raised.
- A read-only review is checking multi-growth pointer tables, backing offsets, and prefix sharing. A bounded implementation assignment covers retry termination.

## Validation

- ROCm runtime library loads; GPU1 identifies as RX 7900 XTX with 25,753,026,560 bytes total VRAM and 28,000,256 bytes used before the baseline probe.
- Running the unmodified Tier-1 capacity probe at 40,960 BF16 context, 257 prompt tokens, four decode tokens on GPU1; result pending.
- Regression tests will run before implementation where practical. Earlier short HTTP runs do not establish long-context growth correctness or prove the original intermittent fault fixed.

## Push checkpoint

The user requested pushing this work to origin. This is a partial implementation checkpoint, not closure of the full growing-context and memory-efficiency objective.

Implemented startup retry termination, demand-sized workspace, protected prefix admission, INT8 prefill boundary capture, and HIP virtual-memory-backed KV planes. The virtual-memory primitive has retryable cleanup; its multi-plane rollback helper is not yet wired into the runtime growth path.

GPU1 serving with Qwen3.8-27B Q4_K_M, INT8 per-token-head KV, radix caching, speculation off, and a configured 40,960-token context completed five sequential requests. Prompt/cached token pairs were 445/0, 3133/256, 12349/3072, 24637/12288, and 36061/24576. Each returned ORCHID-731. The server shut down cleanly. This establishes sequential prefix reuse through 36,061 tokens, not full-context or concurrent correctness, numerical parity, or physical growth beyond the initial arena.

The initial floor commits both payload and scales for 160 pages; it is not metadata-only. No arena growth occurred during that live probe. A separate near-limit baseline request timed out after 600 seconds.

Remaining review findings:

- Physical VMM commitment and alignment overhead are absent from runtime allocation counters and pool budget accounting.
- Exported VMM symbols do not establish driver support; unsupported operations do not yet fall back to chunk storage.
- Failed pointer-table uploads can leak the just-allocated table.
- Replacing the backing object during growth can prevent live-source prefix cloning across growth.
- Runtime multi-plane rollback still needs integration with the cleanup helper.

These are unresolved defects, not merely missing benchmarks. Earlier completion summaries overstated readiness. Follow-up must repair them, validate concurrent shared requests and live growth, and rerun the affected checks. Existing regression evidence includes the focused VMM/prefix bundle and 41 passing capacity tests; the final push check records its own result in the session.
