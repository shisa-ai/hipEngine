# GGUF bench: the documented eager fallback now happens, and the mode names the measured route

## Summary

Found while measuring the TP2 matched TP1 controls, fixed as its own unit. Two
defects in `scripts/qwen35_gguf_bench.py`:

1. **`--graph-replay-decode` crashed on an unadmitted KV layout instead of
   falling back.** The flag's help text promises "If the session cannot capture
   it, record the disabled reason and fall back to eager decode", but
   `capture_qwen35_gguf_decode_graph` raises
   `RuntimeError: GGUF decode graph requires BF16 KV or the admitted
   tail4_hadamard_group32 layout`, and `_decode_graph_disabled_reason` did not
   consult that admission. With the flag defaulting to true since the production
   default changed, the plain INT8-KV command
   (`--kv-storage int8_per_token_head --kv-scale-granularity per_token_head`)
   aborted with a traceback. The check now asks the same predicate the capture
   path asks, and only when the session publishes a KV layout, so capability
   probes without one are unaffected.
2. **`mode` named the request rather than the measurement.** An artifact from a
   run that fell back to eager decode still reported
   `resident_default_prefill_graph_decode`. The mode is now derived from the
   measured runs' `effective_graph_replay_decode`, falling back to the request
   only when no run detail exists.

Neither defect changes any retained number: the 2026-09-13 baseline was measured
when the flag still defaulted to false, and the matched TP1 pair for the
break-even passes `--no-graph-replay-decode` explicitly.

## Changes

- `scripts/qwen35_gguf_bench.py` - admission check in
  `_decode_graph_disabled_reason` (`kv_layout_not_admitted`), and
  `_measured_graph_replay_decode` feeding `_mode_name`.
- `tests/test_unit_qwen35_gguf_bench_metadata.py` - two tests: the unadmitted
  layout returns the reason while BF16 and the admitted
  `tail4_hadamard_group32` layout stay enabled, and the mode reports the
  measured route rather than the request.
