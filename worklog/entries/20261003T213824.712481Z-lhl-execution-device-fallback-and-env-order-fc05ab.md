# Known unsupported device uses its own fallback; configure HIP env before load

## Summary

Reviewer `9ccd8bd8` confirmed two remaining defects in `bb17f2f63`. Both were
reproduced against the pre-change tree, and both are fixed here.

### P2a — a known execution device without a native backend borrowed another device's backend

`select_backend(execution_device=True)` returned only when the selected
architecture had a mapping; otherwise it fell through to the ambient hardware
probe even though the selected device was known.

Counterexample (reproduced): physical `(gfx1102, gfx1151)`,
`ROCR_VISIBLE_DEVICES=0`, `backend="auto"` resolved `hip_gfx1151` from device 1,
and `require_backend_device_compatibility` then refused it. Auto should take the
existing unsupported-architecture fallback for the **selected** `gfx1102`.

Fix: when `selected_device_arches` returns a non-empty set, the execution-device
branch either maps it to a backend or returns the fallback
(`source="execution_device_fallback"`) with `_auto_backend_warning(device_arches,
...)`, which already names the selected architecture and points at forcing a
nearby backend. The ambient probe is now reached only when the device identity
is unresolved (empty set), matching "ambient fallback only for unresolved
identity".

### P2b — the current-device query loaded HIP before the process environment was configured

`_current_hip_device_ordinal()` called `ctypes.CDLL("libamdhip64.so")` and
`hipGetDevice` directly. `get_hip_runtime()` in `core/hip.py` deliberately calls
`configure_hip_process_environment()` first because the queue/scratch policy is
read during HIP/HSA initialization, so backend selection could initialize HIP
before the intended process-start policy was applied.

Reproduced: with `detect_hip_target_arches` reporting `(gfx1151, gfx1102)` and
`GPU_MAX_HW_QUEUES` unset, the recorded order was
`["cdll", ("queue", None)]` — the load happened first and the configuration never
ran at all.

Fix: `_current_hip_device_ordinal()` calls `configure_hip_process_environment()`
before the library load, mirroring `core/hip.py`. There is no recursion:
`configure_hip_process_environment` uses the ambient arch probe, never the
runtime query. Existing environment values are never overwritten, and the
homogeneous path still short-circuits in `selected_device_arches` without
calling this function, so a single-arch host still performs no HIP work.

## Changes

- `hipengine/kernels/backends.py`: `select_backend` execution-device branch
  returns the selected device's unsupported-architecture fallback instead of
  falling through to ambient selection; docstring updated.
  `_current_hip_device_ordinal` configures the process environment before
  `ctypes.CDLL`/`hipGetDevice`.
- `tests/test_unit_backend_device_capability.py`: added the known-unsupported
  selected-device case (library and public `LLM`), the
  ambient-only-when-unresolved case, and the configure-before-load ordering case
  plus an explicit-override case. The runtime-query tests now stub
  `configure_hip_process_environment` so they cannot mutate the real
  environment; the homogeneous test also forbids the configuration call.
