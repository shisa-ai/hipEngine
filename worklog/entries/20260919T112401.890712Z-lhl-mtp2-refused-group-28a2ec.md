# MTP2 refused-group audit: the group-wide K0 is the cheaper route, so the activation a refused row pays is not recoverable by splitting

## Summary

Task #13 asked for the provider activation a refused speculative row pays to stop
being paid. The earlier audit (2026-09-19T103729.143027Z) measured the pre-fix
tree and found the activation is used wherever a cycle is admitted (96.9-99.4% of
the speculative arm's output tokens in the pair lanes) and left one measured cost
in the coupling lane: 417 `no_provider` events, one row with zero MTP tokens. This
entry closes the question with the mechanism and the decisive experiment.

Mechanism, from an activation trace (`[act] begin/finish/drop` per request, plus
`[abort]/[discard]/[reclaim]`), a capability trace (`[cap-silent-none]`,
`[prefill-debug]`, `[mtp2-decline]`) and the engine loop's own code:

- The two short same-tick rows activate together (`begin ids=(3,5)`), both receive
  provider state (`finish state rid=3 prime_rows=20`, `rid=5 prime_rows=17`), and
  the decline traces show what refuses them afterwards: `width 2 exceeds static
  group bound 1`. `engine_loop._maybe_run_speculative_cycle` plans a refused or
  mixed due group K0 *as a whole*, and the alternative (one provider cycle per
  capable row) is behind `HIPENGINE_SPEC_MTP_SPLIT_REFUSED_GROUPS`, default off.
  So the 417 events are the documented trade, not a missing provider: the earlier
  "one unadmitted row poisons its group-mates" reading is refuted for this lane.
- The task's TTFT criterion already holds in the default route: the refused row
  reports 967 ms against the AR arm's short rows at 1255 ms and 967 ms, because
  it decodes autoregressively in the same batch. The criterion that does not hold
  is reporting: the response carries the plan's `no_provider`, and the row's own
  `specdec2_mtp2_prompt_fallback_reason` has no consumer in-tree.
- One run showed a row's provider state released immediately after activation
  (`drop rid=5 disable=False` between the activation and the batch's other rows),
  which is the shape the task describes. It did not reproduce in two later runs
  (all drops at request reclaim) and is recorded as an open item rather than
  claimed as the cause.

The decisive experiment re-measured the rejected split route on the current tree,
in the lane where the trade costs the most share: the coupling c=4 lane, one
production-profile server per arm, two runs per arm. The split route raises the
speculative arm's MTP share **0.534 -> 0.994 (+86%)** and gives the zero-MTP row
207 MTP tokens, but lowers the speculative arm's decode rate **8.76 -> 7.25
(-17.2%)** and **8.15 -> 7.73 (-5.1%)** and lowers the co-resident AR arm's rate
by the same margins (11.62 -> 9.62, 10.81 -> 10.26). That reproduces the
2026-09-18 rejection: the extra provider cycles cost more than the batch AR decode
they replace, so the group-wide K0 stays the shipped route and the activation a
refused row pays is not recoverable by splitting.

Two candidate fixes were implemented and dropped because the measurement does not
support them: an intent-gated prompt hidden-row capture (a row refused an
activation slot still captured its hidden rows so `prepare_k0` could attach a
provider later) and a refusal-report helper. The capture has no effect on this
lane (both rows already stream, `[prefill-debug] hidden_seeds=False` for every
auto row) and would add provider activation cost for rows that may never use it,
which is the opposite of the task's goal.

## Validation

- Protocol: `scripts/sharegpt_mtp_routing_pass.py --cases short,long
  --max-total-len 1024 --route-mix off,auto --num-prompts 8 --max-concurrency 4
  --seed 373 --record-ids`, one server per arm on port 8081 with
  `--backend hip_gfx1151 --execution-profile production
  --speculative-mtp-serving auto --speculative-candidate-budget 3
  --max-context-tokens 8192 --kv-storage bf16`, `HIPENGINE_MTP2_OUTPUT_SPANS=1`,
  and `HIPENGINE_SPEC_MTP_SPLIT_REFUSED_GROUPS=1` for the split arm. Default arm:
  three runs plus one traced run, all at share 0.534 with 417 events. Split arm:
  two runs at share 0.994. Per-arm `decode_tokens_per_second` is comparable
  *across configs* (identical prompts per arm by seed) but not across arms.
- The reverted capture fix was RED-then-GREEN on
  `tests/test_unit_qwen35_gguf_mtp2_seam.py` (3 new tests: 3 failed before, 3
  passed after, full file 108 passed) before it was dropped, so the revert is a
  decision, not a missing test.
- The lane's TTFT is not a discriminator: the same default configuration measured
  a 1881 ms and a 5849 ms median in two runs, so only share and per-token rate
  are used.
