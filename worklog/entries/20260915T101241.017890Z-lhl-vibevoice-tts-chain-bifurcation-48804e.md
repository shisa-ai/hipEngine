# VibeVoice-TTS two-speaker chain: a bifurcation in the first diffusion solve, not the prompt rows

## Summary

The two-speaker 59-token chain diverges at token 32. It is not a defect in our
implementation and not the prompt rows: it is a **bifurcation** in that request's
first diffusion solve, which turns our 1.8% condition error into a different
trajectory branch. The single-speaker request, which shares the entire path, is
exact end-to-end from our own reference-audio encode. This supersedes the
localization in `20260915T091156.145004Z-…-two-speaker-prompt-f6fe75.md` (rows)
and corrects the attribution in `20260915T093817.135483Z-…-chain-condition-diagnosis-e536a6.md`
(which named the rows as the source of the condition error).

## The prompt rows are not the cause

The chain breaks at the same token with three different row sources:

| Prompt rows | Diffusion calls | First mismatch | Call-0 latent error |
| --- | ---: | ---: | ---: |
| our encoder, generation draws | 59 | 31 | 3.573 |
| `ref["connected"]` (what the generation used) | 59 | 31 | 3.616 |
| `lm["prefill_connected"]` (the other pass) | 57 | 31 | 3.616 |

The solved call-0 latent is 3.6 off in every case, so nothing about the rows
explains it. The single-speaker request is exact with our encoder's rows, with
`ref["connected"]`, and with `prefill_connected`.

## Fixture semantics found on the way

Each fixture records **two** encoder passes. `_Recorder` captures an explicit
`pre = model(**moved)` forward and then the generation, so:

- `<name>_reference.npz["connected"]` — the generation's rows, which produced
  `generated_ids`.
- `<name>_lm.npz["prefill_connected"]` — the extra prefill forward's rows.

`encode0_mean` agrees between them exactly; they differ only through the sampling
draw (0.185 relative on single, 0.135 on two). The single-speaker chain tests
were feeding `prefill_connected`, i.e. rows the generation never used, and were
passing anyway. They now use the generation's rows, which drops the call-0
condition error from 0.044 to 0.011. Comparisons against `prefill_last_hidden`
and `prefill_logits` still use `prefill_connected`, because those outputs came
from that pass.

## The bifurcation

Adding white noise to the oracle's condition on the two-speaker call 0:

| Noise (fraction of condition peak) | Solved-latent error |
| --- | --- |
| 0 (oracle condition) | 0.036 |
| 0.005 | 0.053 / 0.071 / 0.161 |
| 0.020 | 0.222 / 0.161 / 0.254 |
| 0.050 | **3.552 / 3.960 / 3.788** |
| 0.150 | 0.356 / 4.175 / 4.046 |

It is a threshold, not a smooth gain. The same sweep on the single-speaker call
is smooth: 0.013 / 0.046 / 0.106 / 0.464 at 0.005 / 0.020 / 0.050 / 0.150.

Our own call-0 condition error is 0.018 of peak — just inside the threshold — so
the solve lands on the wrong branch, and call 1 inherits it (its condition is
1.27 off, versus 0.008 once the branch is restored).

## The loop is stable; only its entry point is not

Forcing the oracle's recorded condition for the first `n` calls:

| `n` | Calls | First mismatch | Latent error, calls 0..7 |
| ---: | ---: | ---: | --- |
| 0 | 59 | 31 | 3.573 0.812 1.114 0.539 1.083 1.279 1.075 1.360 |
| 1 | 48 | 31 | 0.036 0.011 0.012 0.012 0.023 0.022 0.026 0.032 |
| 2 | 48 | 31 | 0.036 0.022 0.027 0.010 0.018 0.013 0.014 0.025 |
| 3 | 48 | 31 | 0.036 0.022 0.008 0.015 0.022 0.011 0.016 0.027 |
| 5 | 48 | 31 | 0.036 0.022 0.008 0.010 0.006 0.011 0.014 0.032 |

One forced call is enough to put the loop on the branch and keep it there:
errors stay at 0.01-0.03 with no growth in depth. The chain still flips at
token 31, and only forcing **all 55** conditions makes it exact.

So the requirement is essentially zero error rather than a smaller one. A bf16
language model accumulating over a 352-token prompt cannot supply that, which is
why the two-speaker request is compared numerically rather than token for token.
The earlier entry's "the condition error has to fall by about 4x" is true of the
blend sweep it measured but is not the binding number: even a 4x better entry
point leaves the token-31 decision to drift.
