# Add depth-wave mixed QSA attention/index adapter

## Summary

Added the execution adapter that runs one Qwen4Exp QSA layer's attention and
index stages over the mixed target row layout from `314cdcaac`. The batch
attention and index owners admit one row per unique slot, so a prepared chain
cannot be passed as independent rows; the adapter splits the layout into depth
waves, publishes each wave's unique slots and matching positions, runs the
committed mixed-mixer attention stage over the wave, scatters the wave's gated
rows to their physical positions, and runs one output projection over the whole
pass. This is one layer's state stage: it admits no request,
owns no runner, drives no GDN/conv/PLE state, samples nothing, and decides no
acceptance. Nothing was committed and no GPU work was run.

## Changes

- `hipengine/runtime/qwen4_exp_mixed_qsa.py` (new, torch-free).
  - `plan_qwen4_exp_mixed_qsa_waves(layout)` → `Qwen4ExpMixedQsaWave` per depth:
    every physical row at that depth in ascending physical row order, with
    parallel `request_ids`, `physical_rows`, `slot_ids`, `positions`. Wave `d` is
    a subset of the layout's rows, so a physical permutation reorders the wave
    and never rewrites a row's request, depth, position or token. Every request
    contributes a root row, so wave `0` is the full request width and each later
    wave is a strict subset: the widest wave is `physical_request_width`, the
    wave count is `max_chain_rows`.
  - `Qwen4ExpMixedQsaScratch`: twelve wave-sized slabs, two full-row slabs, and a
    per-wave `Qwen4ExpBatchQsaSelectionScratch`. The twelve slabs named
    `q_projected`..`gated` carry exactly the attribute contract
    `Qwen4ExpQSAScratch` gives the mixer's stages, so those stages run
    unmodified; `hidden_rows` is the gather target for the caller's shared input
    hidden and the pointer the mixer projects wave index queries from. The wave
    slabs are sized for the widest wave (one row per request), not the row count.
    `gated_rows` is `[total_rows, q_width]` and collects each wave's gate output
    at its rows' physical positions; `output` is `[total_rows, hidden]`, the pass
    result. `output_scratch()` returns the small
    `Qwen4ExpMixedQsaOutputScratch` view naming those two, because the wave
    scratch's own `gated` is the per-wave staging buffer the gate stage writes and
    cannot also be the scatter target. `allocate` checks every geometry and byte
    product before the first allocation and frees what it took on failure;
    `close` frees the selection owner then the slabs, popping each only after its
    free returns, so a partial close resumes instead of leaking or double
    freeing.
  - `validate_qwen4_exp_mixed_qsa_pass(...)`: the pre-mutation admission gate.
    Refuses, in this order, closed/closing owners, a mismatched index/attention
    pair, an already-pending rollback token, runtime identity, head and index
    geometry, projection shapes and norm pointers, a non-positive or misaligned
    `mixed_ptr`, a shared-projection scratch that cannot cover every physical
    row, scratch geometry against the pass, positions past the attention
    capacity, the attention context limit, owner tokens (through the caller's
    `owner_of`, compared exactly, bools and numpy scalars refused), start-cursor
    equality, and every wave's row set through the owners' own pure
    `validate_rows`. It writes nothing: the tests assert zero device copies.
  - `run_qwen4_exp_mixed_qsa_attention(...)`: captures one
    `Qwen4ExpBatchQsaIndexState.begin_rollback()` token, then per wave gathers
    five slabs (`hidden`, `attn_q`, `attn_k`, `attn_v`, `index_k`) row by row,
    publishes the wave's slots and positions on both owners, admits the wave with
    `validate_qwen4_exp_batch_qsa_mixed_mixer`, runs
    `run_qwen4_exp_batch_qsa_attention`, and scatters the wave's gated rows to
    their physical positions in `gated_rows`. After the last wave it runs one
    `run_qwen4_exp_batch_qsa_output_projection` over **every** physical row under
    `Qwen4ExpMixedQsaPassPlan.output_plan()`, reading the scattered gate output.
    The projection is per row, so this is the same arithmetic as projecting each
    wave and scattering its output, with one GEMM instead of `max_chain_rows` and
    one extra `[total_rows, q_width]` slab. It runs inside the pass transaction,
    so a failure there also rolls the token back before re-raising. Returns
    `Qwen4ExpMixedQsaRun` with the result buffer, the token, `wave_rows`, and
    `index_query_rows`.
  - `commit_qwen4_exp_mixed_qsa_attention(run, accepted_counts, ...)`:
    re-checks ownership, builds the plan through
    `Qwen4ExpMixedLayout.commit_destinations`, checks every cursor still sits
    where the pass left it, builds and validates every new cursor and pooled
    counter into fresh arrays, and only then discards the token and publishes.
    Each slot's cursor becomes `start_position + accepted + 1`, so the committed
    prefix is visible and the rejected suffix is not; the pooled counter is
    clamped to that cursor's complete blocks so a later step re-pools a block
    that spanned a rejected row. Prefixes and slots outside the layout are
    untouched.
  - `abort_qwen4_exp_mixed_qsa_attention(run, ...)`: applies the token, rewinding
    every layout slot's cursor and pooled counter to its pre-pass value.
  - Chain semantics come from positions, not from the row set: wave `d` appends
    at `start_position + d` and its context covers the prefix plus the earlier
    rows of its own chain, which earlier waves wrote. Appends are therefore
    exactly the suffix `[start_position, start_position + depth]`.
- `tests/test_unit_qwen4exp_mixed_qsa.py` (new, 37 CPU tests). Every device call
  the committed mixer makes is a module-level name, so the tests replace them
  with recorders; the attention and index owners and their host mirrors are used
  for real against a fake runtime, because their contracts are what the adapter
  must satisfy.
- `tests/test_gpu_qwen4exp_mixed_qsa.py` (new, 5 GPU tests, not executed here).
  The reference is the same committed mixer run the way a single request reaches
  it — one row per step, one request at a time, on a separate owner pair seeded
  with the same committed prefix — so a difference can only come from this
  adapter's wave gather, per-wave publish, physical scatter, or pass-wide
  projection. Cases: ragged chains of three, one, and two rows with an AR peer,
  all inside the dense bound; the same requests under a parent-first
  interleaving permutation that leaves no wave contiguous, compared both against
  the reference and against the in-order run row for row; a nine-row chain that
  crosses the dense bound mid-pass while its AR peer stays dense, so one pass
  holds both row kinds and a sparse row selects from keys its earlier dense
  waves captured; a commit that rejects both chains down to their root row,
  where the pooled clamp withdraws a block that covered a rejected row, followed
  by one sparse row decoded at the committed cursor and compared with the
  reference for that same prefix; and abort, which restores every layout slot's
  cursor and pooled counter, leaves a slot outside the layout and every
  committed prefix cache row bit-identical, and re-runs the pass to the same
  bytes. Real weights, real owners, real kernels: `Weights`, `_cpu_kv_table`,
  `_cpu_index_table`, `_cpu_selection`, `_upload`/`_download`, `_fill_prefix`,
  and the geometry are imported from the two existing mixed-mixer GPU tests
  rather than rebuilt. Arithmetic is bounded and printed — `ADAPTER_ATOL =
  C1_ATOL` (2e-5) for adapter-vs-reference because both sides are different GEMM
  widths, plus the CPU layer oracle at the existing
  `ORACLE_ATOL`/`ORACLE_RTOL` for one dense and one sparse row, so the reference
  itself is checked against an independent arithmetic path.

Reused rather than duplicated: all attention, selection, normalization, gate and
projection arithmetic is `run_qwen4_exp_batch_qsa_attention` /
`run_qwen4_exp_batch_qsa_output_projection` /
`validate_qwen4_exp_batch_qsa_mixed_mixer`; commit destinations are
`Qwen4ExpMixedLayout.commit_destinations`; row validation is the owners'
`validate_rows`; the rollback transaction is the index owner's
`begin_rollback`/`rollback`/`discard_rollback`. This module adds the wave
orchestration, its pre-write validation, and the append/commit/abort binding.

Costs, recorded rather than hidden: five row gathers per wave (`5 * total_rows`
small device copies per pass), one gated scatter per row, one `index_q`
projection per wave that holds any sparse row — sized by the whole wave, because
that is the mixer's own rule — and, across the pass, one `attn_output` projection
over all rows plus one extra `[total_rows, q_width]` device slab to hold the
scattered gate output. Real batching would need attention and index kernels that
take a repeated slot per row set, which the owners do not have.

Deliberately not restored by a commit or an abort: the attention owner's KV bytes
past the committed cursor (unreachable, and the next step rewrites those
positions) and both owners' active row sets, which name the last wave of a pass
that no longer exists. The caller re-prepares them for its next step. MRoPE
position pointers are not plumbed through the wave gather.

## Parent validation

- The five GPU cases pass on the local Radeon 8060S across the focused runs.
  Dense and sparse chains, parent-first physical permutations, accepted-prefix
  continuation and abort/repeat meet the declared assertions.
- The first sparse reference exposed a real singleton selection-staging defect;
  `d0a610f04` fixes it with a RED/GREEN CPU regression. The continuation fixture
  also indexed a follow-up row past its AR peer's prepared history; it now gives
  both owners the same new deterministic hidden row, preserving the original
  numerical assertion. No tolerance was relaxed.
- The four-adapter CPU bundle passes 104 checks. The full-model mixed executor
  consumes the adapter, and the 18-prompt strict-teacher comparison passes the
  calibrated numerical envelope and three same-schedule repeats.
- MRoPE position-pointer plumbing and repeated-slot attention kernels remain
  outside this unit. There is no performance claim from these correctness runs.

## Next

- M2 integration: a caller that computes the shared input projections over all
  physical rows, drives this adapter per QSA layer, and threads the accepted
  counts from verification into the commit. GDN/conv/PLE state for the same row
  set, the runner's per-layer loop, and the request lifetime remain outside this
  unit.
- The physical batching this adapter works around is still the real target: a
  repeated-slot attention row ABI and a per-row key-base index score ABI would
  remove the gathers and the per-wave `index_q` projections.
- The pass-wide output projection is already one call over all physical rows, so
  the remaining per-wave overhead is the five gathers and the gated scatter, not
  the projections.
- Unverified until the parent's device run: the 2e-5 adapter-vs-reference bound,
  and the bit-exact row-for-row equality between the in-order and permuted runs.
  The permuted comparison is the one assertion that would need relaxing to
  `ADAPTER_ATOL` if a rows-reordered GEMM turns out not to be bit-identical.
  Coverage this file does not have: MRoPE position pointers (the adapter does
  not plumb them), any runner/scheduler/serving surface, and the c1 dense decode
  mixer — the reference here is the committed mixed mixer at one row, so this
  file bounds the adapter's orchestration, not the mixer's own arithmetic, which
  the two mixed-mixer GPU tests already cover.
