# the Q8_0 T16 four-wave prefill lands: -61.4 ms, -9.4 percent on a 512-token prefill

## Summary

The dense term now runs the admitted Q8_0 T16 four-wave WMMA prefill. **512-token prefill median
0.6525 -> 0.5911 s, i.e. -61.4 ms or -9.4 percent**, with the teacher-forced output unchanged in
all five runs.

The predicted range from the isolated microbench in `20260929T163000` was **-55 to -75 ms (-8 to
-11 percent)**. The measurement landed inside it.

## The root cause, which the previous attempt missed

`20260929T183000` reverted this change because a tiles-only spec crashed in `_launch_wmma_raw`
with `KeyError: 'raw'`, and recorded the blocker as "the route table at 8830 does not follow the
quant key". **That diagnosis was wrong in a useful way.** The route table was fine; the input to
it was wrong.

```python
def resolve_gguf_linear_dispatch(weight, *, ...):
    resolved_backend = _weight_backend(weight, backend=backend)
    contract = resolve_linear_consumer_contract(
        weight.spec.layout, activation_dtype, output_dtype,      # <-- the layout
        quant_key=weight.spec.quant_key, rows=rows,
    )
    return GGUFLinearDispatch(contract.key(resolved_backend), contract.abi)
```

**The layout, not the quant key, selects the contract row and therefore the launch ABI.** The
previous attempt set `quant_key="gguf_q8_0_t16_v1"` but kept `layout=LAYOUT_RAW_GGUF`, reasoning
that the tiles are uint8 blocks so the raw layout described them. That reasoning was about
*storage* and the field means *route*: the raw layout matched the raw rows, produced `abi="raw"`,
and the raw→`wmma_raw` prefill rewrite then asked for an allocation a tiles-only spec correctly
does not have.

**The fix is the layout constant.** `LAYOUT_GGUF_Q8_0_T16 = "gguf_q8_0_t16_v1"`, the same value
the qwen35 materializer uses, so the shared consumer-surface table resolves the same rows for both
loaders. Verified directly before running anything:

```
rows=   1 -> variant=t16_gemv_decode_bf16_bf16_out abi=t16
rows= 512 -> variant=t16_gemv_decode_bf16_bf16_out abi=t16
```

and at rows>1 the existing `_dispatch_wmma_prefill` rewrites that decode variant to
`t16_wmma_prefill_*` while keeping the `t16` ABI, which is what maps to `allocation("tiles")`.

## Changes

- **`gemma4_gguf_device.py`**: `LAYOUT_GGUF_Q8_0_T16`; a `_plan_one` branch giving a rank-2 Q8_0
  `layers.*` tensor that layout, the T16 key, and a `("tiles",)` allocation; a materializer branch
  repacking via `repack_gguf_q8_0_tile16`; the raw upload made conditional on
  `"raw" in spec.allocation_names`; `resident_bytes` and `derived_allocation_bytes` taught about
  tiles.
- **`gguf_linear.py`**: `raw_weight_ptr` guarded by `"raw" in weight.spec.allocation_names` instead
  of `layout == LAYOUT_RAW_GGUF`. That guard was already wrong -- it is true for a tiles-only spec
  because the storage really is uint8 blocks -- and it is what produced the earlier crash's second
  site.

## What is not claimed

- **Decode was not measured.** The T16 layout has its own GEMV decode kernels and the run
  exercises them, but no decode throughput comparison was taken, and the objective wants 2x there.
- **The dense term's own time was not re-measured in isolation.** The -9.4 percent is the
  end-to-end prefill delta.
- **The four-wave schedule reassociates.** Its admission claims LCP-3 exactness and the
  teacher-forced output is unchanged, which is the evidence this change rests on; no bit-exactness
  claim is made beyond that.
