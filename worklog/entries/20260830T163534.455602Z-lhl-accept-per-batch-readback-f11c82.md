# Accept is per batch, so the readback is already batched; only pipelining remains

## Summary

Checked the normalization behind every accept-window number in this campaign and the
result is good news for the
measurement and bad news for one option I just proposed. The accept window is **per
batch**, not per lane: one
`commit_batch` and one `_read_target_batch_accept` cover all lanes, and the single
`accept_seconds` local is added
to each row while each row also does `mtp2_cycles += 1`. So dividing summed ms by summed
cycles returns the
**batch** window per cycle - the width cancels in numerator and denominator - and my
"per lane-cycle" label was
wrong but the magnitudes were right.

## Changes

- Decision entry; no code change. Corrects the option list in `20260830T163448…`.

## Structure (read, at the accumulation site)

- `qwen35_gguf_mtp2.py:3177` `row.mtp2_cycles += 1` and `:3192-3196` add the same `target_seconds` /
  `accept_seconds` / `accept_enqueue_seconds` scalars to every row. The window itself is
  one call chain over the
  whole batch: `_enqueue_target_batch_accept(batch, ...)`, `commit_batch(results, targets, ...)`,
  `_read_target_batch_accept(pending, ...)`.
- Consequence: the "cheaper first step" in `20260830T163448…` - stop reading back per lane
  and read once across
  lanes - is **void**. It already reads once for the whole batch.

## Cross-validation that the magnitudes are right

- With the batch reading, accept is 88.0-104.3 ms of a ~153 ms cycle at C8, i.e. ~68% of
  the cycle. That matches
  the share I derived from raw (unnormalized) telemetry early in the campaign, from a
  different code path. Two
  independent routes agreeing on 68% is the check that the ratio is not a width artifact.
- So the K3 shape at C5-C8 is: about two thirds of a cycle is spent in one batched commit-
  plus-readback chain
  waiting on device work that the same cycle issued, and the device is at most ~55% busy
  while doing it.

## What remains

- The wait is structural to the cycle: issue batch, commit, read results, and the next
  cycle's work depends on
  those results. Removing it needs overlap *across* cycles - software pipelining that can
  issue cycle N+1's
  device work before consuming cycle N's accept - or capture, which is what makes AR's
  cycle ~95% device-busy.
  Both are cycle redesigns in `hipengine/generation/` plus the runtime, and neither is a
  local patch.
- Measured out and not to be re-opened: pinned copies and upload counts, enqueue host work
  (0.2 ms), readback
  payload size, per-lane readback batching (this entry), and front-section host work.
