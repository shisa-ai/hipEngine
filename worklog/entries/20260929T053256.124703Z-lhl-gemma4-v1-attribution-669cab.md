0.2177 against a 0.05 limit on 2 of 1023 rows — and eight commits touching

## P14 is cleared, and now has a measurement

P14's row claims bit-exactness by argument: a masked key contributes weight 0
to every dimension, so dropping it from pass 3's walk leaves the ascending-key
accumulation unchanged. The argument is sound, but iteration 33 found that
P14's own 4096 gate ran at `c41aa2217`, whose attention sources are
byte-identical to the baseline — so it never exercised the trim.

Gating at `7e9670c9a` does. `git diff c3ea386af 7e9670c9a` across the gemma4
kernel directory touches only `gemma4_attention.hip` (93 insertions, 14
deletions), so that tree is the baseline plus the trim and nothing else. It
passes with `kl_max` exactly 0.0 over all 1023 rows. The claim is now
measured rather than argued.

## The culprit is the router, not attention

`74fb74ffe` — *"select the Gemma 4 router logits kernel by token count"* — is
the first commit where the deviation appears. It is a routing decision: which
kernel computes the router logits, chosen by token count. A different kernel
there changes the expert selection at some tokens, which changes the mixture
that feeds the rest of the layer.

Two details support that reading:

- **The same two rows fail every time.** Row 894 (key 4991) and row 327
  (key 4424) are the offending pair at `74fb74ffe`, at `d0f5b1ff6`, and at
  HEAD. A routing divergence at specific positions would look exactly like
  this — two tokens whose expert choice moved.
- **`d0f5b1ff6` modulates rather than causes.** The later router tile change
  moves `kl_max` from 0.224071 down to 0.217717 and shifts row 327's share
  from 0.179 to 0.083, but the failure is already present before it lands.

Iteration 34's `--slices 1` probe fits this too: bypassing the decode split
entirely left the statistics byte-identical, so the divergence is established
before decode chooses a path — consistent with a router decision made during
the forward pass rather than a decode-kernel artefact.

Neither attention change is implicated. Both attention-touching commits in the
range (`7e9670c9a`, `cc44f33f2` — the latter also touching the gather fold)
pass at `kl_max` 0.0.

## What this means for V1

V1's row said P1 changes a path with no numerical coverage. The coverage now
exists, it was run, and it found a real regression introduced by a performance
commit that was never gated at 4096. `74fb74ffe` and `d0f5b1ff6` both landed
on the strength of scoreboard measurements; neither had a numerical gate run
against the p4096 baseline.

The gate still fails. That is the honest state: HEAD does not pass the 4096
gate, the cause is named, and repairing it belongs to whoever owns the router
kernel selection.
