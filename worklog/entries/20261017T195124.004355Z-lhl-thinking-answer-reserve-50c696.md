# Lower thinking caps with complete close-token cost

## Summary

Thinking-budget admission now leaves space for the actual tokenized close
sequence and the admitted answer reserve. Max-think-only and positive-reserve-
only requests activate enforcement instead of silently remaining prompt hints.
This fixes shared HTTP lowering; task 16 still needs live positive validation.

## Changes

- `max_think_tokens` supplies a cap if no explicit hard-cap alias is present.
  With an explicit hard cap it remains a soft target. Effort defaults do not
  overwrite that explicitly supplied max-only limit.
- Compute the sampler cap after tokenization from the admitted generation
  budget, close-token count and answer reserve. Reject impossible combinations
  before generation; streaming reports the error in SSE after HTTP headers.
- `allow_unbounded` disables the effort-derived cap, not the answer reserve.
  A positive reserve still forces closure at the remaining-budget boundary.
  Explicit zero reserve with unbounded thinking does not create a cap.
- Zero hard cap no longer fabricates an answer reserve equal to the full
  generation budget, which would leave no room for the close sequence.
- Diagnostics use the same lowered cap for initial state. Prompt hints may
  retain a looser requested bound; the sampler closes earlier when necessary.
- Updated API documentation and affected expectations; no model/kernel math or
  automatic MTP admission policy changed.
