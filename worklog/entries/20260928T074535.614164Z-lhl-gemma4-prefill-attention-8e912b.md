# the tiled kernel was wrong because pv accumulation needs every thread to see every key not a strided subset

## Summary

The defect from `20260928T074435` is located. **It is a structural error in my phase 3, not a
subtle one** -- and finding it also corrects the LDS claim that motivated the design.

## The diagnostic that found it

Fixing the harness bug (clear the sticky error, re-run the strict kernel before comparing) and
dumping *which* outputs were nonzero gave a perfectly regular pattern for the failing shape
(`tokens=8`, `keys=1024`, mask keeps keys `0..t`):

```
nonzero per token: [ 16  32  48  64  80  96 112 128]
nonzero per head : [36 36 36 ... 36]                      (all 16 heads equal)
nonzero per dim  : [128 112  96  80  64  48  32  16   0   0 ...]
```

**Those two tables say the same thing: output `(token t, dim d)` is nonzero exactly when
`t >= d`.** `dim 0` is written for all 8 tokens (8 x 16 heads = 128); `dim 7` only for token 7
(1 x 16 = 16); `dim 8` and above never.

## Why

My test's mask keeps keys `0..t`, so **token `t` has only `t+1` visible keys.** In my phase 3
the loop is

```cpp
for (int64_t i = threadIdx.x; i < tile; i += blockDim.x) {
  const float weight = expf(tile_s[i] - new_max);
  running_sum += weight;
  ... acc[t] += weight * v_row[d] ...     // d = threadIdx.x
}
```

**Thread `tid` visits keys `i = tid, tid+256, ...`, and `d = tid`.** With only `t+1 <= 8`
visible keys and `blockDim = 256`, thread `tid` sees a nonzero weight **only if `tid <= t`** --
which is exactly the `t >= d` pattern the dump shows.

**The error: I merged the weight computation, which is strided over keys, with the PV
accumulation, which requires each thread to see *every* key for its own output dimension.** The
strict kernel keeps them separate -- pass 2 strides over keys to build the weights, pass 3 has
every thread loop over all keys -- and I collapsed them into one loop to keep the weight in a
register.

## What this corrects about the design

`20260928T074104` claimed the tiled variant cuts LDS operations per key visit from four to two
by keeping the weight in a register. **That is not achievable in this decomposition.**

**The block is one (token, head) and each thread owns one output dimension, so every thread must
read every key's weight.** The weight cannot stay in the register of the thread that computed
it, because that thread does not own the output element that needs it. **The floor is four LDS
operations per key visit -- write the logit, read it for the max, write the weight, read the
weight -- exactly the strict kernel's count.**

**So the tiled variant's real and only benefit is the one `20260928T073811` identified: the
shared footprint becomes independent of context, so occupancy stops collapsing above roughly
8192 keys.** The LDS-traffic saving I claimed does not exist, and the 50% figure in
`20260928T074104` should be discarded.

**That also removes the tension the previous plan was built around.** The tiled variant still
reassociates (the online-softmax rescale), so the strict/production split and the tolerance gate
stand unchanged -- but the expected win is smaller and narrower than advertised, and it should be
measured at long context, where occupancy is the mechanism, rather than at 2048 tokens.

## The harness fix, which is worth keeping

The sticky-error bug made four failing shapes look bit-exact (`20260928T074435`). **The fix that
matters: clear `hipGetLastError()` between launches and assert the *reference* kernel's output
is nonzero before comparing anything.** A comparison test must fail when its reference did not
run.

**The degenerate mask was the second harness weakness.** With `tokens=8` and a causal mask, only
`t+1 <= 8` keys are visible, so most threads had no work and the failure looked like a
structured pattern rather than a wrong sum. **A correctness test needs a mask where most keys
are visible** -- otherwise it exercises almost none of the accumulation.
