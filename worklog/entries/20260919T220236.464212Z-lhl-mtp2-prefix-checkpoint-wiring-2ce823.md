# Wire prefix-checkpoint capture into the runner, and measure which priming route the served engine uses

## Summary

Task #21 unit 1b, third piece: the runner now publishes the checkpoint key to
the adapter, the batch priming walk captures too, and the capture path is
observable. The live check that was supposed to confirm the wiring instead
measured something more important: **on the served route the provider is primed
by the streaming prompt sink, not by either catch-up walk**, so the capture does
not fire in the configuration the server actually uses. That is recorded here as
the route fact it is, with the traces that show it.

## Changes

- **Runner wiring** (`hipengine/generation/qwen35_gguf.py`):
  `_configure_mtp2_prefix_checkpoint_capture(adapter)` sets
  `prefix_checkpoint_capacity` from `HIPENGINE_MTP2_PREFIX_CHECKPOINT_ENTRIES`
  (default 0, so capture stays off), `prefix_checkpoint_block_size` from the
  cache's `_GGUF_PREFIX_CACHE_BLOCK_TOKENS`, and `prefix_checkpoint_key` to
  `_prefix_checkpoint_block_ids`, which answers with the row's own allocation
  blocks covering the requested prefix -- `block_ids[:prefix_len // block_size]`,
  and `None` when the prefix is shorter than one block or longer than the
  allocation. It is called from `_resolved_mtp2_adapter` beside the factory call.
- **Batch walk capture** (`hipengine/generation/qwen35_gguf_mtp2.py`): the same
  boundary capture in `_catch_up_provider_batch`, which is the walk the
  group-opening path uses. Its rows are packed into the front of the shared
  hidden buffer in *active* order, so a row's slice is its offset within that
  iteration's active set, not its index in the batch; the test pins this by
  giving two rows different boundaries and asserting which one captures and at
  which position.
- **Capture observability**: the capture is silent by design, which makes a
  swallowed failure indistinguishable from capture being switched off. Every
  decision point now echoes under `HIPENGINE_MTP2_TRACE_DECLINE` -- configured
  capacity and block size, walk entry with the boundaries it computed, and each
  skip reason (capture disabled or unreleasable, no key provider, key provider
  raised, no block ids, executor cannot snapshot) or success (prefix length,
  block count, held entries). The prompt sink echoes its first consume, which is
  how the route below was measured.

## Measured: which route primes the provider

Two live c=1 requests through the ShareGPT harness, MTP on, capture enabled with
`HIPENGINE_MTP2_PREFIX_CHECKPOINT_ENTRIES=2`, `HIPENGINE_MTP2_TRACE_DECLINE=1`,
prompts of 363 and 515 tokens (`scripts/sharegpt_mtp_routing_pass.py
--num-prompts 2 --turns 1 --route-mix on --max-concurrency 1`, server on
gfx1151, `--speculative-mtp-serving enabled --speculative-candidate-budget 3`):

- **served (streaming on, the default)**: `begin_prompt_streaming ids=(2,)`,
  `[mtp2-prompt-sink] first consume request=2 chunk_start=0 rows=256`,
  `finish_prompt_streaming ids=(2,) success=True`, and **no walk trace**.
  The sink consumes 256-row chunks and advances the provider itself; neither
  `_catch_up_provider` nor `_catch_up_provider_batch` runs for a plain c=1
  request. Chunk rows (256) and the cache block size (256) are the same constant
  today, so the block-aligned boundary lands on a chunk end in this
  configuration.
- **streaming off** (`HIPENGINE_GGUF_SPECDEC2_STREAMING_PROMPT=0`): no sink, and
  still no walk trace. The engine reads that switch as "no provider at all" --
  `_begin_mtp2_prompt_streaming` sets `mtp2_candidate_budget = 0` with
  `operator_disabled_streaming_prompt_k0` -- so the walk is not a fallback for
  it either. Both runs completed with no request errors.

So the capture as wired is reachable only on the attach-to-group and warm
paths, and the hook that matters for a first-turn prefix-cache hit is inside
`_StreamingNextNPromptSink.consume`. That sink is also where the *restore* will
plug in: its constructor already takes `start_position` and `initial_hidden`, so
a restored checkpoint primes a later turn through the existing warm-priming
interface rather than a new one.

## Incident: a trace raised inside prefill

The first two live attempts failed every request with
`execution_failed ... cause=NameError: name 'sys' is not defined`,
`state_mutation=partial`, which is how a diagnostics bug in the sink trace
surfaced: `hipengine/runtime/qwen35_gguf_mtp.py` did not import `sys`. Two
things came out of it, both kept: the module imports `sys`, and every trace
helper now swallows its own exceptions, because an operator-visible line is not
worth a partially-mutated prefill. The capture path itself had already
swallowed its failures; the traces had not.
