# Contained resident execution failures keep the shared engine serving

## Summary

The engine service owns one shared driver. Any exception that escaped a driver
tick reached `except BaseException: self._fail_all(exc)`, so one request's
failure aborted every active request and closed the service; later requests
failed with `engine service is closed`. Injecting a failure into the shared
driver's poll with two requests active reproduced it exactly: both requests
aborted, the service closed, and the next request was refused.

A step's own pre-device validation failure is now contained instead: the runner
that owns the device decides whether the failed step is safe to continue past,
the loop fails exactly the rows that step named, and the service keeps serving.
A failure the runner cannot vouch for stays fatal, and now says why.

## Changes

### The runner owns the containment decision (`hipengine/generation/qwen35_gguf.py`)

`Qwen35GGUFResidentModelRunner.contain_execution_failure` returns an
`ExecutionFailure` only when it can prove both halves of the claim: the failed
step never reached a device call, and every row it names can be reclaimed.

The proof is a mutation window. A step's entry sets
`_execution_mutation_window = "none"` and records which row it is validating
(`_execution_step_request_id`); the window flips to `"unknown"` at the first
device call. The default is `"unknown"`, so any phase that does not mark itself
stays fatal. A packed step's scratch state is shared, so the classifier also
refuses a `HipError` (the device itself reported a fault) and refuses a phase
outside `{"prefill", "decode"}`.

`_quiesce_after_execution_failure` establishes device completion before the
claim is made: it resolves each affected row's `HipRuntime` through
`row.slot.session.runtime` and `row.lease.session.runtime`, calls
`device_synchronize()` on each, and returns False if no runtime is reachable or a
synchronize fails. A row whose device state cannot be shown quiescent is not
containable.

### The loop fails exactly those rows (`hipengine/generation/engine_loop.py`)

`ResidentEngineLoop._contain_execution_failure` asks the runner, validates the
answer (`ExecutionFailure` or None; no row outside the failed work; at least one
row), then cancels and fails exactly the named rows. A contained cancellation
reports the `GenerationCancelled` the caller already expects rather than
inventing an engine fault; anything else becomes `GenerationExecutionFailed`,
which names the phase, the affected rows, the work kind, the state mutation, and
the cause. A runner that raises while trying to contain, returns a malformed
scope, or returns None is fatal.

The four step entry points (`prefill`, `decode`, `speculative_prepare`,
`speculative_cycle`) route through it, and a contained step keeps the loop's own
bookkeeping consistent (`_record_contained_decode_step`), because the policy that
picks the next work item reads those fields.

`SubmitPollTextGenerator` retires the submission and releases the loop row for
every `failed`/`rejected` event, so the service never waits on a result that will
not arrive.

### The service reports instead of dying silently (`hipengine/generation/engine_service.py`)

`health()` reports `ok` / `unhealthy` / `closed` plus `serving`, and an unhealthy
report names the exception type, message, phase, request ids, and the deepest
traceback frame. `_closed_service_error()` includes that reason, so a refused
request explains itself. `_route_events` treats `failed` like `rejected` and
gives a terminal event without its own error object a named fallback.

### The client can tell a request failure from a server failure

`GenerationExecutionFailed` maps to HTTP 500 `execution_failed` with
`retryable: true` and `error.hipengine.execution` (phase, request_ids,
work_kind, state_mutation, cause_type, reason), emitted by both the blocking and
streaming paths through `_finish_queued_generation` and
`_finish_stream_queued_generation`. `/ready` reports `status: "unhealthy"`,
`ready: false`, and an `engine_service` block when the service has stopped
serving, and stays `ok` after a contained failure. `LLM.engine_service_health()`
exposes it without forcing a model load. `docs/API.md` documents the new code in
the error taxonomy table, which the capabilities manifest test cross-checks.

## Validation

`scripts/gguf_execution_failure_containment_proof.py` on the default gfx1151 host
(Qwen3.8-27B-Q4_K_M, 4096-token context, greedy, 12 tokens, artifact
`benchmarks/results/2026-09-17-gfx1151-q4km-execution-failure-containment.json`,
103.5 s, `passed: true`, 10/10 checks):

- The fault fired in `decode_batch` on the third matching prologue call — a real
  resident decode step, after both requests had already emitted tokens.
- The classifier saw `phase="decode"`, `mutation_window="none"`,
  `step_request_id=2`, and contained row 2 only, leaving row 1's canonical state
  untouched in the same packed step.
- Quiesce resolved real `HipRuntime` objects for both rows and
  `device_synchronize()` succeeded.
- The co-resident completed with token ids identical to a pre-fault reference run
  and a follow-up request on the same driver reproduced them exactly.
- `health_after_fault.status == "ok"`; the injected row saw a plain
  `GenerationCancelled`, not an engine fault.
- Control with `contain_execution_failure` forced to return None: the same fault
  closed the service (`status: "unhealthy"`), the co-resident died, and the
  injected row saw the raw injected exception. That is the pre-repair behaviour,
  so this is a RED/GREEN rather than a demonstration of an untestable path.

Tests: `tests/test_unit_generation_execution_failure_containment.py` (new, 13
cases: containment, refusal, fatal fallback, malformed scopes, row retirement),
plus the engine-loop, spec-dec, engine-service, batch-scheduler, prefix-cache,
MTP-accounting, MTP-API-gate, MTP2-seam, and server-API suites (11 files in one
command, 1136 collected) — 0 failed with `-p no:randomly`.

## Notes

- Containment is deliberately narrow. A failure at or after the first device call
  stays fatal even when the failing check is in a step's own loop, because a
  packed step's device state may already have advanced for rows the scheduler has
  not recorded. The first proof run hit exactly this: arming the injection on the
  prefill path's second call made the failure fatal, which is the intended
  answer for a step whose packed batch had already run.
- `_execution_mutation_window` is per-runner state, not per-thread state. The
  service drives one runner from one thread, so this is correct today; a
  multi-threaded driver would need it on the work item.
- A fatal failure still closes the service rather than attempting recovery.
  Restart is the documented remedy, and `/ready` now says so.
