# `python3 scripts/*.py` in this tree imports `hipengine` from the hipEngine-main clone

## Summary

Running a harness as `python3 scripts/<harness>.py` from `/home/lhl/hipEngine`
with the conda interpreter imports **`/home/lhl/hipEngine-main/hipengine`**, a
separate clone on branch `main`, not the working tree. `uv run python
scripts/<harness>.py` imports the working tree correctly. This session's
chunk sweep, chunk-4096 kernel trace and dense-wide layer A/B were all run the
first way, so their hipEngine rows describe `hipEngine-main` while their
artifacts record `/home/lhl/hipEngine`'s commit hash.

No code is broken. The harnesses, the registry and the kernels are fine. What is
broken is the provenance of any measurement taken with the raw interpreter, and
that is a blocker for trusting an artifact's `source.head` field.

## Changes

### The mechanism

```
$ cat /home/lhl/miniforge3/envs/therock/lib/python3.12/site-packages/_editable_impl_hipengine.pth
/home/lhl/hipEngine-main
/home/lhl/hipEngine-main
```

`python3 script.py` sets `sys.path[0]` to the *script's directory*
(`/home/lhl/hipEngine/scripts`), not the cwd, so the working tree's
`hipengine/` package is never on the path and the editable-install `.pth`
decides:

```
$ /home/lhl/miniforge3/envs/therock/bin/python3.12 scripts/_whichmod.py
sys.path[0] = /home/lhl/hipEngine/scripts
hipengine    -> /home/lhl/hipEngine-main/hipengine/__init__.py

$ uv run python scripts/_whichmod.py
sys.path[0] = /home/lhl/hipEngine/scripts
hipengine    -> /home/lhl/hipEngine/hipengine/__init__.py
```

`uv run` uses `/home/lhl/hipEngine/.venv`, whose `.pth` is
`/home/lhl/hipEngine` and is therefore correct. The `therock` and
`therock10-staging-20260828` conda envs both point at `hipEngine-main`.

### Why it is not a same-code alias

- `/home/lhl/hipEngine-main` is a **separate clone**, not a worktree: it has its
  own `.git` directory, and `git worktree list` in the working tree does not
  mention it. Both clone from `git@github.com:shisa-ai/hipEngine.git`.
- Its HEAD `5e6b863c6` (2026-09-27) is **not present in the working tree's
  repository at all** (`git log 5e6b863c6` fails there).
- **209 non-`__pycache__` files differ**, including `qwen4_exp_profiles.py`,
  `qwen4_exp_gguf.py`, `runtime/gguf_linear.py`, and the Qwen4Exp / Q4_K / Q8_0
  prefill kernel sources and wrappers.

The profile bindings differ in five places:

| binding | hipEngine-main | working tree |
| --- | --- | --- |
| `QWEN4_EXP_Q8_IU8_WMM` | `1` when production | absent |
| `QWEN4_EXP_Q4_IU8_RISK_MULT` | absent | `1.0` |
| `QWEN4_EXP_Q8_DENSE_WIDE` / `_LAYERS` | absent | `1` / layers 16-47 |
| `QWEN4_EXP_Q8_DOWN_VARIANT` | absent | `selected_grouped_wmma_prefill_bf16_bf16_out` |
| `QWEN4_EXP_GDN_TILE16_VARIANT` | absent | present |

`hipEngine-main` has no profile binder for the risk multiplier at all; its
`runtime/qwen4_exp_runner.py` reads the env var directly with default `4.0`.

### Measured cost of the mistake

`code-p4096`, production profile, chunk 1024, 1 warmup + 3 repetitions, one
process per arm, cached build:

| interpreter | tree actually imported | pp tok/s | tg tok/s |
| --- | --- | ---: | ---: |
| `uv run python` | working tree | **272.46** | **17.40** |
| `uv run python` (repeat) | working tree | 272.79 | 17.40 |
| `python3` (conda) | hipEngine-main | 290.84 | 19.03 |

Within-arm drift is **0.12%**; the between-tree difference is **-6.3% prefill
and -8.5% decode**. So the two trees are not interchangeable and the choice
changes a headline number by 6-9%.

### Consequences for this session's committed artifacts

- The 8-run chunk sweep (`2026-10-04-qwen4exp-chunk-order-balanced`) and the
  chunk-4096 kernel trace (`/tmp/c4096-trace`) describe `hipEngine-main`. Their
  internal comparisons stay valid (one tree throughout), but the absolute rates
  and the family shares are not this tree's.
- The dense-wide layer A/B patched
  `/home/lhl/hipEngine/hipengine/generation/qwen4_exp_profiles.py`, a file that
  was never imported. **Both arms ran identical code**, which is why the result
  was a 0.54% no-op against 0.54% same-code drift. That experiment must be
  re-run, not interpreted.
- The chunk-size conclusion is directionally unchanged in-tree but smaller:
  chunk 1024 -> 4096 measures **272.46 -> 295.40 tok/s (+8.41%)** against 0.12%
  drift, not the +13.6% the contaminated arms showed.
- The **decode regression reported from the contaminated sweep does not exist
  in-tree**: decode is 17.40 at chunk 1024 and 17.72 at chunk 4096, i.e. the
  larger chunk is **+1.8%** on decode rather than -6.1%.

## Limits

- The comparison is between two branches, not two commits of one branch, so the
  -6.3%/-8.5% is a branch difference and not yet attributed to any one change.
- One case (`code-p4096`), one chunk size per arm, one repetition count per
  process; the working-tree arms were run twice and agree to 0.12%.
- No attempt was made to reconstruct which earlier sessions' committed artifacts
  used which interpreter; the mechanism predates this session (the `.pth` is
  dated 2026-09-21) and the exposure is unknown and probably broad.
