# Measure the Inkling GGUF decode arms in paired runs at 47 prompt tokens and keep the decode graph opt-in

## Summary

Campaign task 6. The decode graph is measured where decode dominates and R0528 has its decision:
it stays a bounded, opt-in experiment. The graph is 1.87 times the default path after 47 prompt
tokens, but it is not the default path's output over 128 tokens, and it is slower at depth.

`scripts/inkling2_decode_pairs.py` ran the four decode arms in fresh processes, five pairs in the
listed order and five in reverse, three repetitions after one warmup each, 47 prompt tokens and
128 outputs, on `epyc` (Radeon Pro W7900, gfx1100, HIP 7.2.53211), mainline `UD-Q4_K_M`, `fast`
profile, FP32 KV, one greedy stream, prefix cache off, drafting off, at `7f18ae19f` on a clean
tree. Each arm is the decode bench with a set of Inkling variables.

| Arm | Decode | ms per token | Ratio to default, forward and reverse | Same 128 output IDs as default | Syncs per token | Host blocked per token | Kernels per step |
| --- | ---: | ---: | --- | --- | ---: | ---: | ---: |
| Default | 17.80 tok/s (17.63 to 17.84) | 56.2 | | | 241 | 16.8 ms | 17.3 ms, 1,568 launches |
| Device routes | 19.50 tok/s (19.40 to 19.57) | 51.3 | 1.098 and 1.096 | no | 193 | 15.9 ms | not traced |
| Resident decode | 32.75 tok/s (32.62 to 32.81) | 30.5 | 1.845 and 1.839 | no | 3 | 12.7 ms | 22.3 ms, 2,415 launches |
| Decode graph | 33.21 tok/s (33.14 to 33.26) | 30.1 | 1.868 and 1.867 | no, same as resident decode | 4 | 28.6 ms | 22.5 ms, 2,392 launches |

- **Graph accounting.** One capture per request, 27.6 ms, in the first decode step; 126 replays
  in 127 steps. One `graph_launch` per token costs the host 0.06 ms. The host then waits 28.6 ms
  for the graph.
- **Cost per dependent node.** Wall 30.1 ms against 22.5 ms of kernels over 2,392 nodes: 3.2 µs
  per node. Resident eager shows the same figure (3.4 µs), so the host keeps up with launches once
  the step is this long. This is the number that converts a node budget into milliseconds.
- **The default path's host work.** 56.2 ms per token, of which 16.8 ms is spent blocked in 241
  synchronizations. The other 39 ms is host work and launch submission around 17.3 ms of kernels.
- **Device routes alone** gain 9.7% at this depth by removing the per-layer logits download: 48
  fewer synchronizations per token. Their output differs from the default's on this prompt too.
- **Transport A/B cannot run yet.** `HIPENGINE_SUBMISSION_TRANSPORT=aql` and `pm4` refuse the
  graph: `Pm4InspectionError('unsupported HIP graph node type 1')`, a memcpy node. The graph holds
  about 321 per step: 74 host uploads, 256 device copies in the loop and controller work, 3
  downloads. The step falls back to resident eager with the same output (smoke at 48 outputs:
  34.6 against 34.8 tok/s under `hipgraph`). The in-tree inspector takes kernel nodes only.

## Decision under R0528

The flag stays at `0` and the entry stays open. The task's rule promotes an arm only with a win
above 3% in both orders and the reference's output. All three arms win; none has the default's
output over 128 tokens. The graph adds 1.4% over resident decode at this depth and loses at depth
(14.2 against 17.5 tok/s after 1,717 prompt tokens, [previous entry](20261124T185419.107449Z-lhl-inkling2-mini-d74d5c.md)).
Its value is not in question; the path it replays is not ready. What reopens it:

1. A decode attention kernel for the resident path (task 19), which removes 45 ms of the 70 ms
   step at 1,717 keys.
2. Fewer nodes, or a kernel-only graph that the `aql` and `pm4` transports accept: at 3.2 µs per
   node, dispatch is 7.6 ms of the 30 ms step.
3. The Inkling adapter for the production numerical gate (task 8), which decides promotion for
   every changed-arithmetic arm, device routes included.

## Limits of this measurement

- One prompt, the bench's repeated seed text, at one depth. It answers the decode question the
  task posed; it is not the campaign's 47/575/2,057 comparison, which needs the step to win at
  depth first.
- Device routes were not traced; their kernel column is empty on purpose.
- The transport rows are a smoke, not a paired run: the native transports did not replay.
- Kernel time is what the profiler reports, and the profiler slows the step (37 ms of wall under
  it against 30 ms without, for the graph). Wall per token comes from the unprofiled paired runs.
