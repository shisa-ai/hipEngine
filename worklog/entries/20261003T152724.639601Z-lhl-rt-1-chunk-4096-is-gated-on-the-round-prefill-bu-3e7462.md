# RT-1 chunk 4096 is gated on the round prefill budget, not memory admission

## Summary

`docs/QWEN4EXP-OPTIMIZATION-LEDGER.md` row `RT-1` and `docs/REFACTOR.md` both
record the remaining blocker for the measured `chunk 1024 -> 4096` step as **a
memory-admission question**: can the host afford an 89.40 GB peak for the
`-4.94%` prefill win. Reading the code, that is not the binding constraint.

The chunk the engine actually runs is `min(prefill_chunk_size,
round_prefill_token_budget)`:

```python
# hipengine/generation/engine_loop.py, _run_token_budget_round
prefill_budget = self.round_prefill_token_budget          # 1024
while prefill_budget > 0 and self.scheduler.has_prefill_work():
    work = self.scheduler.next_round_robin_prefill_work(
        chunk_size=min(self.prefill_chunk_size, prefill_budget)
    )
```

`DEFAULT_ROUND_PREFILL_TOKEN_BUDGET` is 1024, and
`tests/test_unit_engine_loop_prefill_chunk.py` pins
`DEFAULT_MAX_PREFILL_CHUNK_TOKENS == DEFAULT_ROUND_PREFILL_TOKEN_BUDGET`. So
raising the chunk cap to 4096 either (a) has **no effect at all** if the round
budget stays at 1024, because `min(4096, 1024)` is 1024, or (b) requires raising
the round budget to 4096, which is the per-tick bound that protects decode
interleaving.

Two consequences, and both are corrections to what the ledger and REFACTOR
currently say:

1. **A larger workspace owner cannot deliver the `-4.94%`.** The ledger's
   "concrete next step if pursued: memory-bounded chunk selection" and
   REFACTOR's "the one genuinely useful survivor is the capacity question (what
   peak can the host admit for a single larger owner)" both assume that
   admitting a larger owner is the lever. It is not, and this project's own
   `RT-3` measurement is what refutes it: the workspace is **scratch**, and
   kernel work scales with the actual token count, not with the size of the
   scratch handed to it (two-owner A/B, 1024 vs 4096 rows against a 4352
   sequence: 3.2068 s vs 3.1730 s, 1.06% *slower* on the small owner at 0.017x
   the within-arm spread, identical `logits_sha256`). A 4096-row owner under a
   1024 round budget still executes `4 x 1024`, which is the measured-slow
   configuration. The selector that would pick owners is already parked for
   removal for exactly this reason.
2. **`1024 -> 4096` is a real fairness trade, and `256 -> 1024` was not.** The
   landed `256 -> 1024` promotion is admissible precisely because per-tick work
   is unchanged - at 256 the engine processed 1024 budgeted tokens as `4 x 256`,
   at 1024 the same 1024 as `1 x 1024`, so there was no tick to lengthen. That
   argument does **not** transfer to 4096: raising the round budget to 4096
   quadruples per-tick prefill work and therefore the worst-case delay before a
   concurrently decoding request gets its next step. The ledger states this
   requirement correctly in the `256 -> 1024` blocker segment ("Raising it 4x
   makes each prefill tick up to 4x longer ... DECODE LATENCY UNDER CONCURRENCY
   ... is unmeasured, and it is the prerequisite"), but its final `RT-1` segment
   for the 4096 step names only memory and drops it.

This is a code-reading finding, not a measurement. It changes what the missing
experiment is: **not** a capacity probe, but a decode-interleaving /
peer-fairness measurement at `round_prefill_token_budget = 4096`. `RT-3`
independently lists "no peer-fairness measurement" as an unmet gap, and this is
the same measurement.

The `-4.94%` itself is not retracted. It was measured with
`qwen4exp_profile_gap.py --mode prefill`, which calls `runner.prefill(ids)`
directly and therefore bypasses `_run_token_budget_round` entirely - so it is a
valid direct-prefill-path result, and the ledger's note that "a prefill-only or
batch path is directly supported" is the correct scope for it. What it is not is
reachable through the engine loop without paying the tick cost.

## Changes

- `docs/QWEN4EXP-OPTIMIZATION-LEDGER.md`: appended a segment to row `RT-1`
  recording the round-budget constraint, the two corrections above, and the
  restated missing experiment.
- `docs/REFACTOR.md`: qualified the parked selector's "capacity question"
  survivor so a later reader does not treat owner admission as the 4096 lever.

No code, default, flag, test or artifact changed. No performance claim.

## Next

- If the 4096 step is pursued, measure decode interleaving under concurrency at
  `round_prefill_token_budget = 4096` against 1024 - same host, same model, a
  decoding peer plus a long prefill - and only then decide. A capacity probe
  alone does not answer it.
- Do not promote 4096 on a memory-admission argument; that argument is what this
  entry corrects.
