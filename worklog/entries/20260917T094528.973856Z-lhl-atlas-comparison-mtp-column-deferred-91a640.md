# Correct the Atlas comparison's MTP diagnosis and defer the rerun

## Summary

`docs/COMPARISON-vs-atlas.md` described the pre-2026-09-17 resolver as current
policy: it presented the execution-profile manifest, session length, prompt
context, and output horizon as binding admission axes, reported "at least one
further axis is unmet", and told readers to reproduce hipEngine MTP by starting
a 1024-token session with `HIPENGINE_EXECUTION_PROFILE=strict` and issuing at
most 67 prompt tokens with `max_tokens: 25`. None of that is needed now that
admission is physical (commit `25121713c`), and the "further axis" question was
never answered by that investigation because the four removed axes were already
sufficient to fail the request.

The section now separates the four removed axes from the physical axes that
still gate, states that the measured rates are unaffected because both hipEngine
rows are AR rows, and records that the hipEngine MTP column needs a rerun of the
same protocol. The strict-scope startup recipe is gone.

The rerun itself was started and then cancelled on request before either arm
produced a measured row, so no new performance number exists. The one thing the
partial run did settle is worth keeping: the local artifact
`/home/lhl/models/gguf/Qwen3.8-27B-Q4_K_M.gguf` hashes to
`7e78da5d7e3ae28d178121f58646953305f3e5bd3cb46f4a75584e8b6c6fe169` at
17,106,775,008 bytes, exactly the value every gfx1151 evidence row pins, so the
artifact axis is not an obstacle to admission on this host.
