# Measure Qwen3.8 XTX BF16 context roof

## Summary

Bracketed the exact Qwen3.8-27B `Q4_K_M` single-request BF16 server roof on the
24-GiB RX 7900 XTX. With the existing contiguous pool pre-sized to request
capacity, 53,248 total tokens complete at `23.959 GiB` whole-device peak with
only `0.025 GiB` free. The next 1K boundary, 54,272 tokens, aborts with
`HSA_STATUS_ERROR_OUT_OF_RESOURCES`; all larger controls through 64K fail.
This is the observed physical ceiling, not an operating recommendation. The
validated 32K row retains `2.115 GiB` and remains the supported setting.

## Changes

- Added a compact artifact with the exact model/hardware identity, server and
  raw-token protocol, pool shape, 32K/default-cliff/tuned-roof rows, failed upper
  bound, source hashes, and explicit diagnostic-vs-operational decision.
- Updated `docs/KVCACHE.md` and the internal benchmark rollup/changelog. No
  runtime or kernel source changed.
- Used the existing `HIPENGINE_KV_POOL_INITIAL_PAGES` control only for physical-
  roof rows. The default 128-page pool keeps its first 2-GiB backing and must
  allocate a second contiguous backing above 32K: 33,024 tokens complete but
  leave only `0.031 GiB`.

## Validation

- Default 32K: 32,766 prompt IDs + one output + one reserved slot return HTTP
  200 at `21.869 GiB` peak with `2.115 GiB` free and `/ready` true afterward.
- Default 33,024: HTTP 200 at `23.953 GiB`, only `0.031 GiB` free, proving the
  duplicate-backing cliff is operationally unsafe.
- Pre-sized 48K/48.5K/49,920/52K all return HTTP 200 with clean teardown. The
  highest row is 53,246 prompt IDs + one output + one reserved slot at
  `23.959 GiB`, `0.025 GiB` free, and a 208-page / 3.25-GiB logical BF16 pool.
- Pre-sized 53K/54K/56K/63K/64K all abort with HSA out-of-resources and zero-MiB
  free diagnostics. The refined bracket is `[53,248 pass, 54,272 fail]`.
- Every pass uses exact raw token IDs, one active request, HTTP 200, one generated
  token, post-request readiness, zero KV growth failure, and clean process/GPU
  teardown. JSON parsing, benchmark README sync, worklog validation, and diff
  checks are run before commit.
