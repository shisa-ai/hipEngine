# QSA flash prefill port spec

## Summary

Port specification for the last prefill family: QSA dense attention
(12 layers; 24 q-heads x 256 dim, 2 kv-heads GQA 12:1, paged bf16 KV,
dense-equivalent limit 2051). The current path runs
qwen35_paged_full_attn_decode_context_bf16_batch_spans — a per-(head,row)
decode kernel — at ~11.8 ms/layer (141.5 ms family total at pp508,
~1.07 TFLOP/s scalar). llama's flash_attn_tile<256,256,8,4> (lineage
ggml-org/llama.cpp@17252c769 ggml/src/ggml-cuda/fattn-tile.cuh +
fattn-common.cuh) reaches 1.21 ms/layer on the same GPU.

## Changes

- None yet; records the port design.

## Validation

- Source analysis of both kernels; geometry from the GGUF metadata
  (qwen4exp.attention.head_count=24, head_count_kv=2, key_length=
  value_length=256, full_attention_interval=4).

## Next

- Port plan: adapt flash_attn_tile for our QSA layout. Block = one Q-column
  tile (ncols ~64 queries of one head pair) x 256 threads (8 warps);
  RDNA config for DKQ=DV=256: nthreads=256, nbatch_fa=64, nbatch_K=64.
  Key adaptations: (1) K/V live in the paged bf16 cache — iterate KV tiles
  via block-table spans (or gather the <=2051-token chunk K/V into a
  contiguous f32 scratch first; 2051x512x2x4B = 8.4 MB scratch, gather cost
  trivial vs 10x kernel win); (2) causal mask from the per-row position
  (start+row); (3) Q from scratch.query (f32, rows x 24 x 256); (4) output
  to scratch.context (bf16); (5) online softmax in f32, V accumulate f32,
  dst_meta not needed (write directly). Numerics: f32 accumulation with
  bf16/f16 operand rounding — closer to the current f32 path than the
  dp4a-class routes; boundary screen then packet as usual. Route env
  HIPENGINE_QWEN4_EXP_QSA_FLASH_PREFILL with layer set, strict fallback =
  the existing spans kernel. RED test vs the spans kernel on synthetic
  paged KV, then microbench, screen, packet, binder fold-in.
