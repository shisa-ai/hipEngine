# Mixed dense/sparse N-row QSA batch mixer

## Summary

Extends the committed dense batch mixer (`cf9a213c5`) past its equivalence bound
on top of the committed index owner (`bee0ef3b7`). The dense entry point,
`run_qwen4_exp_batch_dense_qsa_token_mixer`, is unchanged: it still rejects any
prepared row past its bound before the first dispatch. The new
`run_qwen4_exp_batch_qsa_mixed_token_mixer` takes the same attention owner plus
the index owner and a new `Qwen4ExpBatchQsaSelectionScratch`, and runs one step
of mixed independent requests where each row's context may be on either side of
the bound.

Three properties define the unit:

1. **`index_k` is projected and appended for every row on every step**, including
   rows still inside the dense-equivalence bound. That is what makes a request
   that crosses the bound later still hold its complete index history; a mixer
   that captured keys only once a row went sparse would silently start with a
   truncated key stream.
2. **One selection representation for both row kinds.** A row inside the bound is
   attended with *all visible positions* as its selection, so dense and sparse
   rows share one `(positions, counts)` entry in one buffer and the whole batch is
   attended by a single
   `qwen4_exp_qsa_sparse_attention_paged_bf16_rows_f32` dispatch over the per-row
   page tables. No partition, no gather of query/output rows, no aliasing, no row
   written by two kernels.
3. **Row kinds come from the index owner's own rule** (`partition_rows`), not
   from a second copy of it. `dense_equivalent_limit == output_stride ==
   block_budget * ratio + ratio - 1`, so the mixed mixer takes no limit argument
   and cannot disagree with the index state about where the boundary is.

No runner, server, default, kernel, registry, or doc change. Uncommitted, left
for review.

The selection scratch is a device owner, so it carries the same lifecycle
contract as the batch attention and index owners: byte products are checked
before the runtime is touched, host mirrors are built before the device slabs,
``close()`` poisons accessors before the first free and pops each slab only after
its free returns, and the accessors refuse a closed or half-closed owner. Section
"Review repair" records why: the first version of this class repeated three
lifecycle bugs that the sibling owners had already fixed.

## Design decisions

**Unified selection, and what it costs.** The alternative was two dispatches:
the dense decode kernel over all rows (per-row live counts) and then the rows
kernel, relying on `selected_count == 0` rows being skipped. That keeps the dense
decode arithmetic but does dense work for every sparse row, which is the exact
work sparse selection exists to avoid. The chosen form does one dispatch and only
the selected positions per row, and pays for it in arithmetic: a dense row in a
mixed batch runs the sequential online-softmax rows kernel instead of the dense
decode kernel. That difference is measured, not assumed, and bounded by the tests
below; a caller that needs the dense decode arithmetic keeps those rows on the
dense entry point.

**A real bug found by the exact selection comparison.** `select_active` indexes
its query rows by the row order of the active set it is given, which for the
sparse group is the group's own order, while `scratch.index_query` is laid out in
batch-row order. The first implementation passed `scratch.index_query.ptr`
directly. With two sparse rows in a three-row batch, sparse row 0 (batch row 1)
was scored with batch row 0's query against batch row 1's keys, selecting
`[0, 1, 6, 7, 8]` where the correct answer is `[0, 1, 2, 3, 8]`. Pooled keys
matched bit-exactly on both sides, so a pooled-key check would have passed and a
tolerance-based output check would have looked like ordinary GEMM-variant drift.
The fix gathers each sparse row's prepared query into `selection.queries` with one
device-to-device copy per sparse row before selecting. The regression test
compares the batch selection against a c1 owner fed the batch's *own* key and
query bytes, which is the only comparison that isolates selection from projection
rounding.

**Recovery is the caller's, and is stated instead of implied.** The call mutates
the index cursors (append) and the KV cache before the attention reads them, so it
is not transactional. The docstring contract is: capture
`index_state.begin_rollback()` before the call; on any failure
`index_state.rollback(token)` and re-run the same step, which restores the cursors
and rewrites the same KV bytes at the same positions; on success
`discard_rollback()`. A test injects a failure after the append commits, asserts
the cursor really advanced, rolls back, and asserts the re-run is byte-identical
to an uninterrupted twin. The mixer also restores the index owner's active set to
the full row list before returning, so the next step's `append_active` sees every
row even though selection published the sparse group.

**Preflight before any mutation.** `_validate` gained a keyword-only
`require_dense: bool = True`; the dense entry point's call is unchanged and keeps
every check in the same order, so its behaviour is identical (all existing dense
unit tests pass untouched). The mixed path disables only the per-row limit loop
and adds `_validate_index`: index owner closed/closing, runtime identity, the
index owner mirroring *this* attention owner, index geometry, the two index
projections and both norm pointers, index scratch sizing, selection scratch rows
/ stride / query geometry, active-slot agreement in row order, per-row
`cursor == attention position`, per-request index capacity, and the predicted
dense/sparse split. `_stage_selection` re-checks each row's count against the
stride before uploading. A rejected call dispatches nothing and leaves cursors,
KV bytes, index slab bytes, and selection buffers untouched (asserted).

## Review repair

Parent review rejected the first version of `Qwen4ExpBatchQsaSelectionScratch`
for repeating lifecycle bugs the sibling owners already fixed. Three real
defects, all in code this unit introduced:

1. **`close()` leaked on a partial free.** It did
   `self._pending_free, buffers = [], self._pending_free` and then looped
   `free(...)`. If one free raised, the not-yet-freed slabs were already detached
   from the owner, so a retry freed nothing and every remaining slab leaked. Fixed
   with `_free_pending`, which pops only after a free returns, so a retry frees
   the remainder exactly once and a further call frees nothing.
2. **`allocate` could leak every device slab on a host allocation failure.** The
   two host mirrors (`np.zeros`) were built *after* the three `malloc` calls and
   outside the cleanup `try`, so a host `MemoryError` propagated with all three
   device buffers still allocated. Fixed by checking the byte products first, then
   building the host mirrors, then allocating device slabs inside the `try`.
3. **The accessors did not refuse a released owner.** `__enter__` returned
   `self` and `query_row_ptr` returned a device address without checking the
   lifecycle, so a closed or half-closed scratch handed out a dangling pointer.
   Both now call `_require_open`, and `close()` sets `closing` before the first
   free (it already did) so a partial close poisons access instead of appearing
   usable.

Added with the repair: `_selection_products`, an addressability guard over the
three slab byte products (`rows * stride * 8` also bounds the per-row query
offsets) that runs before the runtime is resolved; and `close()`'s fallback that
seeds `_pending_free` from the named slabs when an owner was built without it, so
`close()` can never free nothing.

RED evidence: reintroducing the three original behaviours (discard-then-free,
host mirrors after the device allocation, no open guard) fails four of the new
tests — `test_host_mirror_failure_allocates_no_device_buffer`,
`test_partial_close_failure_is_retried_exactly_once`,
`test_access_is_refused_after_close_and_close_is_idempotent`, and
`test_close_releases_a_hand_built_owner_without_a_pending_list` — and the fixed
tree passes all 25.

Seven tests cover the contract, all on the fake runtime so they need no GPU:
host-mirror `MemoryError` allocates no device buffer; three unaddressable shapes
(`stride`, `rows`, `index_dim`) are rejected before any allocation; a free that
fails on the second call leaves the owner `closing`/not `closed`, poisoned for
`__enter__` and `query_row_ptr`, then the retry frees the remainder exactly once
and the total freed set is each slab once; access after a full close is refused
and `close()` is idempotent; and a hand-built owner with no pending list still
releases all three slabs newest-first.

## Dispatch shape

Measured with the unit recorder (one step, one call):

| step | dispatches | composition |
| --- | --- | --- |
| 2 rows, both dense | 11 | 9 batched N-row + 2 index scatters |
| 3 rows, 2 sparse | 18 | 12 batched N-row + 3 scatters + 1 pool + 2 scores |

Batched (one dispatch for the whole batch, any row count): `attn_q`/`attn_k`/
`attn_v`, `index_k`, `index_q` (only when some row is sparse), the Q/K split
norm+RoPE+gate, the index query norm+RoPE, the KV write, the block selection
(`topk_expand_rows_f32_i64`), the attention, the gate, and `attn_output`.

Serial, accepted as the current fallback and labelled as such in the docstring:
the index append (one scatter per row — the committed scatter takes one page
table and one position scalar), block pooling (at most one dispatch per sparse
row), block scoring (one per sparse row — every score ABI shares one
`pooled_keys`), the query gather (one small memcpy per sparse row), and the two
host metadata uploads. No stage loops the c1 mixer.

Fixture geometry: 4 slots, `max_positions=1024`, `block_size=256`, 8 hidden,
2 query heads / 1 KV head of 4 dimensions, index 2 heads x 4 dimensions, index
ratio 2, index budget 2, so `dense_equivalent_limit = 5`. Rows start at
positions 3 / 8 / 2 on slots 0 / 1 / 2 and each advances three steps: row 0 is
dense at contexts 4 and 5 and sparse at 6, row 1 is sparse throughout, row 2 stays
dense, and slot 3 is never touched.

**Control, exact.** Row-to-slot mapping and the published positions/cursors are
asserted after every step; each row's appended K/V lands in its own slot; slot 3
stays bit-zero in both the KV cache and the index slab; a repeat run from the same
state reproduces the output and selection bytes; the same requests permuted across
rows reproduce each slot's own output and selection byte for byte; invalid
metadata dispatches nothing and leaves KV/index/selection bytes and cursors
unchanged; a failed step is recovered by `rollback` plus a re-run and is
byte-identical to an uninterrupted twin.

**Selection, exact.** Dense rows carry exactly `arange(context)`. Sparse rows are
bit-identical to a c1 `Qwen4ExpQSAIndexDeviceState` fed the batch's own raw-key
and prepared-query bytes, and equal to the CPU oracle
(`qsa_prepare_index_keys` / `qsa_index_scores` / `qsa_select_positions`) as a set,
for all nine step/row pairs. The c1 mixer's internal selection also matches.

**Arithmetic, measured.** Per step, `max|c1-batch|` and `max|oracle-batch|` were
printed; worst observed values:

| row kind | `max|c1 mixer - batch|` | `max|CPU layer oracle - batch|` |
| --- | --- | --- |
| sparse | `0.000e+00` (bit-identical) | `2.3e-05` |
| dense | `1.9e-09` | `3.5e-05` |

Sparse rows are bit-identical to the c1 mixer because both run the same
online-softmax kernel body with 256 threads; dense rows differ by FP32 round-off
because the rows kernel is not the dense decode kernel. The oracle column is
dominated by the N-row vs single-row GEMM variants, the same property the dense
batch mixer already records.

No production-profile numerics, no task gate, no serving path, and no speed claim
were run: this unit is the mixer, its focused tests, and the owner lifecycle
repair. The numerical qualification above is therefore the whole of it — the
output comparisons bound dense rows at `1.9e-09` and the CPU oracle at `3.5e-05`
on the fixture geometry only, and nothing here says how the mixed path behaves on
a real checkpoint, on longer contexts, or against the calibrated production
envelope in `docs/EXECUTION-PROFILES.md`.

  layer, a request-to-slot map shared with the attention owner, a per-step
  `prepare` on both owners in the same row order, an explicit state move on
  compaction, and routing each row to the dense or mixed mixer by
  `partition_rows`.
- **Prefill chunks.** The indexed recurrence and this mixer are one token per row;
  a multi-token chunk needs the prefill owners plus per-token state rows, and its
  rows are sequence positions rather than independent requests.
- **MTP.** Not claimed. One live token per row, no replay after a rewind and
  overwrite beyond the rollback token's append-only contract.
- **Capacity.** The index slab is still `state_slots x (raw + pooled)` per layer
  and nothing here shares or compacts slots.
- **Kernel variant.** The generic `..._rows_f32` kernel is used for every head
  dim; the `h256_wave_rows` and `rows_wave32` variants exist but are not wired
  here, so head_dim 128 / 256 currently take the 256-thread body.
