# Register scoped staged sliding prefill attention

## Summary

The gfx1100 production profile now prefers the staged multi-row attention
candidate for one geometry: a sliding prefill block the tiled and AOTriton
routes refuse (a sliding layer whose presented key count exceeds its window),
which the native exact kernel serves by walking all presented keys from column
0. The candidate keeps the native arithmetic and adds the per-row window trim,
so the substitution is byte-identical on the exercised matrix.

On a same-process paired A/B at an 8192-token prompt and 128 outputs, the scoped
substitution lowers prefill from 9.4851 s to 8.3245 s (-12.24%, 863.7 to 984.1
prefill tok/s) and total wall from 11.3942 s to 10.3258 s (-9.38%). Decode in
the same pair is **slower**: 1.9089 s to 2.0291 s (+6.29%, 66.53 to 62.59 tok/s).
This entry records a scoped prefill/wall win, not a universal non-regression and
not full-goal completion; it makes no MTP or whole-profile quality claim.

The substitution preserves the inspected reduction order, supported by direct
parity tests. No kernel arithmetic was changed in this unit. The strict native
kernel remains registered as the fallback.

## Changes

- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention.py`: added a third
  registration of the same two launchers under a new structural layer key
  `exact_prefill_attention` (`EXACT_PREFILL_ATTENTION_LAYER/QUANT/PLAIN/STAGED`).
  **No kernel body changed**; the diff is constants only.
- `hipengine/generation/gemma4_profiles.py`: registered `gemma4_plain` and
  `gemma4_staged` under the new key; `production` selects the staged variant,
  `strict` (and the unregistered `batch_invariant`, which falls back to strict)
  keeps the native kernel; the binder carries the selection onto the generator.
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_layer.py`: added
  `_select_exact_prefill_attention` and its registry resolver, mirroring the
  decode-attention selector. It returns `(None, None)` outside the scope (a
  global block or a one-row block), and within the scope it returns the staged
  candidate only when `staged_plan` accepts the shape; otherwise the registered
  plain fallback runs under the `exact` route. `window`/`row_offset` are
  forwarded only to the staged launcher; the strict native entry and the decode
  fallback keep their previous keyword set.
- `hipengine/runtime/gemma4.py` and `hipengine/generation/gemma4_gguf.py`:
  forwarded `exact_prefill_attention_variants` to the layer, disabled for a
  genuine decode step and a verify block.
- The tiled/AOTriton split, the existing `prefill_attention` scope, the decode
  scope, and every other route are unchanged. The `window=0` graph-capture path
  is forwarded verbatim (the staged launcher then walks the full range).
