# the context ceiling belongs to the windowless layers, not to the context length

## Summary

The target is inference at 256K context. The first blocker found is not a kernel
limit but a wrong model in the capacity guard, and this entry fixes that half.

`gemma4_require_context_capacity` charged **every** layer the whole configured
capacity. But 25 of Gemma 4 26B-A4B's 30 layers have a sliding window of **1024**,
and such a layer reads a band, never the context. Measured against the real
function, the guard demanded **1,050,688 bytes** of LDS for a layer whose actual
read is 1024 keys, which needs **6,208**. That is a 169x over-charge on 25 of 30
layers, and it is why the error message named `keys=16384` for a sliding layer
that can never present more than 1535 columns.

**This does not by itself lift the 256K limit, and the entry should not be read as
claiming it does.** The bisected ceiling on the real 30-layer config is still
**15616**, because the 5 windowless layers (head_dim 512, 2 KV heads, no window)
read the whole context and still bind. What changed is *which* layers impose the
ceiling: it now belongs to the full layers alone, which is what the tiled
decode-attention work has to answer for. A sliding-only config went from 15856 to
unbounded, which is the direct evidence that the over-charge was the sliding
layers'.

## Changes

- `hipengine/runtime/gemma4.py`: add `gemma4_layer_key_count(attention, capacity,
  *, rows)`, which returns `capacity` for a windowless layer and
  `min(capacity, window + rows - 1)` for a windowed one, and rewrite
  `gemma4_require_context_capacity` to charge each layer that count.
- `Gemma4Runner.__post_init__` passes `rows=self.max_block`, because the band
  widens with the block: a 512-row prefill block presents `window + 511` columns.
- The guard's `rows` defaults to `min(capacity, DEFAULT_PREFILL_BLOCK)` -- the
  block the runner derives when it is not told one -- so the generator's
  pre-load check reaches the same answer the runner will rather than admitting a
  context construction then refuses.

The band formula is not a heuristic; it is what the mask already is.
`_keep_mask` gives a windowed layer column 0 as key `max(0, start - window + 1)`
and its last column as key `start + rows - 1`, so the span is `window + rows - 1`
however long the context grows. A decode step is `rows == 1` and reads exactly
`window`.

## Validation

- `tests/test_unit_gemma4_attention_context_ceiling.py`: **12 passed**. Four tests
  added: the band formula at `rows` 1 and 512 with the capacity cap; a windowless
  layer still charged the whole capacity; the guard's default `rows` agreeing with
  the runner's derived block; and a windowed layer served at 262,144 positions.
  The old `test_a_sliding_window_does_not_lift_the_ceiling` asserted the behavior
  this entry fixes and is replaced rather than deleted, with the reasoning kept.
- **RED confirmed** by restoring the pre-fix guard body in a scratch copy: both
  new behavioral tests fail (`test_a_sliding_window_lifts_the_ceiling_it_is_charged`,
  `test_a_sliding_only_config_is_served_at_a_long_context`) and pass again once
  restored.
- `pytest -k gemma4` over `tests/`: **exit 0**. One stub-based test in
  `test_unit_gemma4_attention_geometry.py` built a geometry without
  `sliding_window`; the real `Gemma4AttentionGeometry` always carries the field,
  so the stub was completed rather than the guard made tolerant of a stub.
- Ceilings bisected against the real artifact's config (`gemma-4-26B-A4B-it-UD-Q4_K_XL`):
  mixed config **15616** (unchanged), sliding-only **4194304** (the bisection's
  own upper bound; was 15856). Per-layer charge at capacity 262144: layer 0
  (window 1024) **1535** keys, layer 5 (no window) **262144** keys.

## Next

- The 5 windowless layers are the remaining blocker. The strict key-class decode
  kernel holds one logit per live key in LDS at `(keys + 528) * 4` bytes and no
  `decode_attention` variant is registered anywhere, so a tiled decode attention
  for head_dim 512 / 2 KV heads / GQA 8 is what lifts the ceiling. That is the
  next unit.
- **Recorded, not fixed: the KV cache is still capacity-sized for every layer.**
  At 256K that is **59.06 GB**, of which the 25 sliding layers hold **53.48 GB
  they can never read** (a window-bounded cache would be 5.58 GB). The run still
  fits without it -- 59.06 GB of KV plus a 17 GB model against 109 GB available,
  with 124 GB of GTT addressable on this host -- so it is an optimization rather
  than a precondition. It is the largest single memory win available and it needs
  a ring buffer, because a window-sized cache wraps and the attention kernels
  currently index the cache linearly.
- Prefill at long context also builds a dense `(rows, keys)` uint8 mask per layer
  per block: 133 MB per block for the full layers at 256K, and roughly 342 GB of
  materialisation over a whole prefill. That is a throughput problem rather than
  a correctness one, and it is the next unit after the decode kernel.
