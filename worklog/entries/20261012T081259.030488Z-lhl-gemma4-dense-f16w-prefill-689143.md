# Hold the dense Q8_0 prefill weight operand pre-converted to f16

## Summary

The wide-wave Q8_0 T16 WMMA prefill converts each int8 weight to the half
operand it multiplies on every launch; a discard experiment put that conversion
at about half of the kernel's time. Every dense Q8_0 projection that carries
T16 tiles now gets a second, f16 copy of that operand ("f16w", `in * out * 2`
bytes), built on the device from the tiles with the kernel's own expression.
The two-wave and four-wave launches load it instead of converting. The output
is bit-identical, so there is no flag.

The copy costs 3.29 GB on Gemma 4 26B-A4B (125 projections). It is a memory
rule: `Gemma4DeviceWeights.ensure_dense_f16w` runs at the end of runner
construction, after KV and scratch are allocated, takes the copy only when the
device keeps 2 GiB free afterwards, and is all or nothing. The outcome is on
`weights.dense_f16w_status`.

Measured on AMD Radeon Pro W7900, production, BF16 KV, 128 outputs, one warmup
and three samples, `scripts/gemma4_campaign_bench.py`, measured 2026-10-10
against `edd7905e1` (the 512 row against `18c515d87`): prefill 3242.3 -> 3756.1
tok/s at 512 (1.158x), 3038.1 -> 3363.9 at 8192 (1.107x), 2420.8 -> 2635.3 at
32768 (1.089x), 1946.4 -> 2073.2 at 65536 (1.065x). Decode is level and
`public_path_parity` is true on every row.

## Changes

- `hipengine/kernels/hip_gfx1100/quant/gguf_q8_0_t16_prefill.hip`: the n-wave
  kernel takes an `F16W` template flag and an `f16w` pointer; the conversion
  kernel `q8_0_t16_tiles_to_f16w_kernel`; exports for the size, the conversion,
  and the two-wave and four-wave f16w launches.
- `hipengine/kernels/hip_gfx1100/quant/gguf_q8_0_t16_prefill.py`: the launches,
  and a table keyed by tiles pointer through which the auto wrapper's two-wave
  and four-wave branches find a registered copy at `tile_n == 32`.
- `hipengine/runtime/gemma4.py`: `ensure_dense_f16w`, its release in `free()`,
  and the call from `Gemma4Runner.__post_init__`.
- `docs/REFACTOR.md`: the pointer table and its removal condition.
  `docs/KERNELS.md`: the catalog row.

## Validation

- `tests/test_gpu_gguf_q8_0_t16_wmma_prefill.py` on W7900: 92 passed. The new
  test compares the f16w launch with the decoding launch byte for byte over six
  shapes, for both schedules, and shows the auto wrappers take the f16w route
  only while a copy is registered for that shape.
- Teacher-forced captures at `--prompt 1024`, `--prompt 8192 --prefill 4096`
  and `--prompt 16384 --prefill 15856 --context 16384` are bitwise equal to the
  captures taken before the change (1,023 / 4,095 / 527 rows).
- `tests/test_unit_gemma4_dense_f16w.py`: the memory rule on both sides of the
  reserve, all-or-nothing on allocation failure, idempotence, and release.
- Default unit tier: exit 0.
- Defect found and fixed before commit: the first unit-tier run hung in
  `tests/test_unit_gemma4_weight_geometry.py`. That test replaces this module's
  runner allocator with one that returns made-up pointers while its fused
  weights are real device allocations, so the conversion kernel wrote to a
  made-up address. The copies now come from `hipengine.core.memory` directly.
  An 8192 rerun after that fix reads 3363 / 3348 / 3333 tok/s prefill, 69.86
  decode, parity true.
- The four-wave f16w launch is covered by the kernel test only. The backend
  that selects four-wave by default (gfx1151) was not run in this unit.
- One earlier small kernel test in this unit ran on the second GPU while the
  first was busy; every measurement above is from the W7900.
