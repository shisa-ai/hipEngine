# gemma4 decode cost map: the host floor alone is 9.66 ms/token, and attention is the largest device term

## Summary

Decode is 28.0 tok/s and the objective wants 2x. Two measurements now bound where the time goes.

**The host floor is 9.66 ms/token = 103.5 tok/s**, measured by
`scripts/gemma4_decode_host_floor.py`, which makes every launch funnel return immediately so the
decode loop runs its full Python call chain and synchronization but issues nothing. At 28.0 tok/s
a token takes about 35.7 ms, so **the host path is 27 percent of every token**, and removing it
entirely would give about **38.4 tok/s**.

The device side is dominated by attention. The 2026-09-25 profile puts one decode step at
**attention 24.03 ms (52.6 percent)**, host and gaps 8.04, MoE GEMV 6.22, dense 3.88. The traffic
census agrees that bandwidth is not the limit: **3219.6 MB of weight traffic is only 12.9 ms at
256 GB/s** against a 43.9 ms step.

## The two levers, and why only one of them is small

**Fewer host launches.** 825.6 launches per step at 7.2 us each is about 5.9 ms of the 9.66 ms
floor. There is already an accepted host-dispatch fastpath artifact, so part of this is done; the
remaining 9.66 ms caps decode at 103.5 tok/s, which is **above the 56 tok/s target but only 2.7x of
headroom**.

**A different attention decomposition.** The profile is unusually explicit that the obvious work
cannot win here:

> the per-key cost (~0.5-0.6 us, ~1000+ cycles) is invariant to the work inside the key iteration:
> removing the mask load, the K load, the dot product, the 256-lane reduction tree...

and it rejects both the KV-bandwidth-bound and the barrier-bound hypotheses with ablations. Its
stated lever is **one warp per (token, head), 32 lanes x 8 dims, 16-byte vector loads**, with the
constraint that any such change must preserve the lane-to-dimension mapping, the ascending-j
publish order, and the 256-lane tree -- all enforced by
`tests/test_gpu_gemma4_attention_decode_parity.py`.

**That is a kernel rewrite, not a tuning pass**, and it is the largest single term.

## What is not claimed

- **The attention number is gfx1100 at 1024 context, not gfx1151 at the campaign's 8192.** The
  campaign artifact records `context = 8192`; attention is O(context), so its share on the target
  configuration is likely **higher** than 52.6 percent, not lower. No gfx1151 per-kernel decode
  trace was taken here.
- **The host floor is a diagnostic with wrong output by design** -- only its timing is read.
- **The 24.03 ms attention figure is from a profiler that inflates absolute durations by about 24
  percent**; the profile says to read shares and rankings from it, and absolute per-launch numbers
  from the unprofiled microbenchmark.

## Next

- **Re-trace decode per-kernel on gfx1151 at context 8192** before writing any attention kernel:
  the 52.6 percent share is inherited from a different GPU and a different context, and the whole
  case for rewriting attention rests on it.
- **The host floor is the cheaper lever** and is bounded and measurable on its own.
