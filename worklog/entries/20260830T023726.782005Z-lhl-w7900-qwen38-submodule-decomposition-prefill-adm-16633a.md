# W7900 Qwen3.8: AR complete-wall loss localizes to the prefill/admission submodule; decode submodule beats both peers at every width

## Summary

The published AR C1-C8 complete-wall deficit (loses C2, C6-C8) is **entirely the
prefill/admission submodule**. The decode submodule is faster than both peers at
every width. The cause is a routing gate, not kernel throughput: the engine loop's
multi-request prefill branch is unreachable on gfx1100 because no backend package
declares `GGUF_C2_PACKED_PREFILL_MAX_ROWS`, whose lookup default is 1.

## Changes

- No production code changed. Added `scripts/gguf_backend_capability_exec.py`, a
  harness-only injector that sets a backend-package capability and runs the target
  **in-process** with `runpy` (an `os.execv` first draft was wrong: a fresh
  interpreter wipes the injected attribute, so the target saw the default 1).

## Validation

Decomposition re-derived offline from retained packets with
`scripts/gguf_engine_submodule_decomposition.py --arm ar --arm-d1 prefill`
(hipEngine d1 `/tmp/gfx1100-qwen38-d1-renamed.json`, d24
`/tmp/gfx1100-qwen38-final-k3-c1c8.json`; llama.cpp arms are the `prefill`/`ar`
cells inside `qwen38-w7900-{current,laurent}-c1c8-ar-prefill.json`). The identity
`long_wall = admission + (tokens-1) x decode_step` holds to <0.5 ms at all widths.

Our admission per lane is flat at ~305 ms while llama.cpp's falls 223 -> 106 ms,
so total admission grows at exactly 304 ms/lane (316, 610, 910, 1221, 1526, 1828,
2135, 2441 ms; intercept ~12 ms) - the signature of zero cross-lane grouping.
Shipping-route prefill rate measured with `scripts/gguf_first_token_probe.py`
(`--public-ar-profile`, never combined with `--gpu-stage-timings`): **167.6 tok/s
at 45 rows** (median of 2, 0.25% stdev) vs **877.0 tok/s at 512 rows**. The peer
prefill row already in `benchmarks/README.md` is 200.946 -> 424.072 tok/s
(C1->C8), so our aggregate prefill is ~167.6 flat (serialized) against their
rising 424.1, while our grouped-capable rate (877.0) exceeds their best.

Code cause chain: `hipengine/generation/engine_loop.py:2162` selects
`next_prefill_batch_work` only when `runner.packed_prefill_max_rows > 1`;
`hipengine/generation/qwen35_gguf.py:5003` reads it as
`backend_package_capability(backend, "GGUF_C2_PACKED_PREFILL_MAX_ROWS", 1)` and
no backend package defines it; `backend_package_capability` is a plain `getattr`
with no env override (`hipengine/kernels/backends.py:123`). The capability alone
may not suffice: `_try_prefill_native_work_batch` (`qwen35_gguf.py:6401`) refuses
unequal chunk lengths and `ResidentBatchScheduler` (`batch_scheduler.py:982`)
buckets prefill by a shared block-table length, while
`_gguf_ar_packed_prefill_enabled` (`qwen35_gguf.py:305`) already defaults on.

Falsifiable target: substituting grouped prefill into the identity gives C8
admission 2441 -> ~855 ms and **69.97 tok/s vs current 58.74**, flipping C3-C8,
with C2 at 33.8 (linear-in-rows) to ~36 (weight-bound) i.e. parity.

Retracted claim (chat only, never committed): `hipengine/serve/scheduler.py`
`Scheduler.step()` does not exist; the real paths are those cited above.
`hipengine/runtime/qwen35_gguf_mtp.py:1729` builds a capacity-1 scheduler for its
per-request helper and must not be conflated with the server's capacity-8 runner.
