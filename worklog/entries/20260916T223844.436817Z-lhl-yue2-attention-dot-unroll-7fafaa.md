# YuE2 NAR attention dot-product row specialization

## Summary

Follow-on to the weight-layout entry. That unit left the kernel at 12 070
instructions per lane-tile with 3 091 scalar-ALU instructions, and named the two key
walks and the tile bookkeeping as what was left. Static analysis of the compiled ISA
(`hipcc -S -O3 --offload-arch=gfx1151`) found something larger first: **the row loop
inside the dot product was rolled**, at 46 instructions per (row, eight dimensions)
against eight multiply-adds and two 16-byte loads.

The loop's bound is `r_valid` — how many of the block's eight rows still have query
data — which is only known at run time, so the compiler could not unroll it and had
to index `dots[8]` and `q_rows[8]` dynamically. That costs `v_movreld`/`v_movrels`
register shuffles per row plus loop control. Sixteen dimension groups times eight
rows is 128 executions of that body per lane-tile.

This is the same class of defect as the weight layout: the kernel's bookkeeping had
grown past its arithmetic. `docs/ROCM-AI.md` is the tree's own note on the seam.

## Changes

`hipengine/kernels/hip_gfx1100/yue2/nar.hip`:

- **Full row set specialized.** When `r_valid == YUE2_NAR_ROWS_PER_BLOCK` (every
  block but the last one) the row loop is a `#pragma unroll` over a compile-time
  bound, so `dots` and `q_rows` stay in registers. The rolled path remains for the
  partial block and the scalar path for a `head_dim` that is not a multiple of eight.
- **Both accumulation walks carry running pointers and a 32-bit trip count.** The
  rolled form recomputed the weight address from the key (`weights + t * ROWS`) and
  counted in `int64`, which the compiler turned into a shift, an add, a 64-bit carry
  chain and a scalar-to-vector move per key. Each walk is now `#pragma unroll 4`, which
  also lets the shared-memory loads for later keys issue while earlier ones compute.

Both changes keep every sum in the same ascending key order, so they are bit-exact.

## Validation

Instruction counts per lane-tile (rocprofv3, deterministic):

| Counter | Before | After | Delta |
| --- | ---: | ---: | ---: |
| VALU | 8 035 | 5 147 | -36.0% |
| SALU | 3 079 | 1 692 | -45.0% |
| LDS | 525 | 525 | — |
| FLAT | 385 | 139 | -63.9% |
| BRANCH | 558 | 314 | -43.7% |
| **Total** | **12 581** | **7 816** | **-37.9%** |

The global-load count falling by 64% is a second-order effect: with the row loop
unrolled the compiler schedules the query reads far better than it could around
dynamic register indexing.

Paired same-session A/B, `--repeat 20`, sources alternated: 25.90 / 26.27 / 26.49 ms
-> 19.33 / 18.91 / 20.91 ms, **median ratio 1.359x** (minima 1.53x).

End to end:

| Configuration | Before | After | Ratio |
| --- | ---: | ---: | ---: |
| 2-step solve, `mandarin-off-s1234` | 7.61 s | **6.69 s** | 1.14x |
| 32-step product solve, same case | 81.13 s | **54.76 s** | 1.48x |
| 32-step full replay (solve + decode) | 101.23 s | **74.84 s** | 1.35x |

The 32-step solve is now **2.00x** the pinned upstream's 27.32 s, from 16.2x before
the attention and projection work and 2.97x before this change.

Gates: bit-identical to the recorded parent-bits fixture (max abs diff 0.0);
`tests/test_unit_yue2_nar_kernels.py` 15 passed, and its parametrization covers full
row sets (nar_rows 40), partial ones (34, 7, 1) and a non-multiple-of-eight head_dim
(100), so all three paths in the kernel run; the 2-step and 32-step e2e gates pass.

Eight rows per block is still the optimum with the new balance: four rows 22.53 ms,
eight 19.96 ms, sixteen 25.39 ms — sixteen is now only 27% behind instead of 45%.

## Next

The reference's own attention was measured for the first time by profiling the pinned
upstream on the same case: `attn_fwd` at grid (2688, 16, 1) with a 128-thread
workgroup, **1792 calls at 2.310 ms, 4.140 s total** for the whole 32-step solve. That
is 12.4 TFLOP/s of attention arithmetic. This kernel's share of the 32-step solve is
about 39 s, so it is **9.4x** off a tensor-core flash attention.

That distance is a kernel-design change, not more loop surgery. This kernel is scalar
FP32 FMA: its ceiling is the 25.6 TFLOP/s of scalar FP32 on 40 CUs, and it keeps
roughly a quarter of its instructions as useful arithmetic after the softmax
reductions, the weight exchange and the loads. Even a perfect scalar kernel would
land near 6 TFLOP/s, or about 8.5 s for this workload. Closing the rest means matrix
cores (BF16 WMMA with FP32 accumulation, which is what the reference uses), a new
registered variant with its own production-profile gates.
