# The IQ4_XS T16 layout has a bit-exact consumer, but it is not faster on wide-N shapes

## Summary

The IQ4_XS T16 layout landed byte-neutral and bit-lossless on 2026-09-13 but had
no consumer, so its structural claim was untested. There is now a decode kernel
that reads it, and it is bit-identical to the shipped raw-layout owner on every
measured shape. It is also slower on the wide-N shapes, so it is not promoted.

## Changes

- `hipengine/kernels/hip_gfx1100/quant/gguf_iq_dense.hip` —
  `gguf_iq4_xs_t16_local32_gemv_kernel<WAVES, ROWS>` plus
  `launch_iq4_xs_t16_local32_rows<ROWS>` and the two `extern "C"` entry points
  `hipengine_gguf_iq4_xs_t16_local32_gemv` and
  `hipengine_gguf_iq4_xs_t16_local32_rows_gemv`.
- `hipengine/kernels/hip_gfx1100/quant/gguf_iq4_xs_t16_local32.py` — new
  launcher. Reuses `_local32_waves` and `_default_library` from
  `gguf_iq_dense` so the split-K wave count and with it the cross-wave reduction
  order cannot drift between the raw and T16 owners.
- `tests/test_gguf_iq4_xs_t16_local32_parity.py` — new, 16 tests.
- `benchmarks/results/2026-09-13-ud-gfx1100-iq4-xs-t16-local32-decode.json` —
  new, the rate measurement.

## Decision

The kernel keeps the raw owner's lane ownership (lane k = lane*8..lane*8+7),
per-column FMA order, wave32 shuffle tree and serial wave-0..WAVES-1 cross-wave
sum. Only the weight load pattern changes: the T16 qs plane is
`[group][element][column pair]`, so one u32 load at a fixed (group, element)
yields all four column pairs -- eight output columns -- for that element. In the
raw layout a lane's 8-byte payload window is read twice, once per nibble half
(lane 4g+0 for the low nibble, lane 4g+2 for the high nibble), so a 256-element,
8-column block moves 2048 weight bytes raw and 1024 in T16.

Because the arithmetic is unchanged, the contract is exact equality of the bf16
outputs rather than a tolerance. That is the decisive check for the layout: a
wrong-but-self-consistent nibble or column-pair convention round-trips through
the packer's own inverse, but it cannot reproduce the raw owner's numbers.

Two bugs were caught by that contract and are worth recording, because both
would have survived a round-trip test:

- The first version hoisted the per-column `d`/`scales_h`/`scales_l` read out of
  the K loop. Those fields live *inside* each 2176-byte tile block, so the scale
  varies per block. Only column 0 happened to agree; every other column was
  wrong.
- The fused codebook LUT takes the whole byte (`s_cb[v]` is `iq4_values[v & 15]`
  and `s_cb[256 + v]` is `iq4_values[v >> 4]`), so the nibble is selected inside
  the LUT. Passing an already-shifted nibble double-shifted it, which left even
  columns correct and odd columns wrong.

## Results

Measured with `/tmp/phase8/t16-bench.py`, 60 repeats after 15 warmups, synthetic
IQ4_XS bytes with `d` forced to f16 1.0 so no output is NaN. Every cell is
bit-exact.

| K | N | raw ms | T16 ms | speedup | raw GB/s | T16 GB/s | bit-exact |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 17408 | 5120 | 0.067 | 0.098 | 0.679x | 711.0 | 482.6 | yes |
| 5120 | 17408 | 0.093 | 0.134 | 0.695x | 507.4 | 352.6 | yes |
| 5120 | 13824 | 0.080 | 0.135 | 0.597x | 467.5 | 278.9 | yes |
| 17408 | 2048 | 0.053 | 0.041 | **1.281x** | 357.7 | 458.0 | yes |

## Why it is not promoted

Halving the payload bytes does not help where it matters. The wide-N shapes are
not DRAM-bound: the raw owner already runs at 467-711 GB/s there, and its
duplicate window reads are L1 hits, so both owners issue the same number of load
requests. The T16 path adds cost elsewhere -- three header fields read per column
instead of two, and eight live per-column scales, which the compiler reports as
missing the occupancy target (14 of 16 waves per EU at `WAVES=1`). The one shape
that improves, N=2048, is the one that is actually bandwidth-starved (raw at
357.7 GB/s).

So the layout's first consumer is real and verified, and the measured conclusion
is that the layout's byte saving is not the binding constraint on the shapes
that dominate UD decode time. The kernel stays registered as a non-default owner
with its measurement recorded rather than being wired into dispatch.

## Validation

```
HIP_VISIBLE_DEVICES=1 python3 -m pytest tests/test_gguf_iq4_xs_t16_local32_parity.py -p no:randomly
```

16 tests pass: bit-exact parity against the raw owner on the real IQ4_XS fixture
at K=17408 and K=5120, bit-exact parity on random payloads covering every nibble
and every scale in -32..31, the rows 2/3/4 sibling against the raw rows sibling,
each sibling row against the rows==1 owner on that same activation row, and
argument validation.

The wider bundle is unaffected: 105 tests pass across
`tests/test_gguf_iq_local32_decode.py`, `tests/test_gguf_iq_local32_rows.py`,
`tests/test_gguf_iq4_xs_t16_layout.py` and the new parity file.

## Next

The concrete follow-up this measurement motivates is the wide-header variant:
read `d`, `scales_h` and `scales_l` for eight columns as contiguous u32 vectors
(4 + 4 + 8 loads instead of 24 mixed loads) and keep them in registers. That
attacks the cost that made the wide-N shapes slower, which the payload-byte
saving cannot. Dispatch wiring, registration in the four-axis registry, and a
`rocprofv3` kernel trace are all still open.
