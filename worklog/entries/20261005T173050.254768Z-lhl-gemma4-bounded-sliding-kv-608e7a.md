# Bounded sliding-window KV ownership for Gemma 4 BF16

## Summary

The Gemma 4 runner allocated `capacity` BF16 KV rows for **every** attention
layer, even though 25 of the 26B-A4B artifact's 30 layers are sliding and read
only `window + max_block - 1` keys.
The original 131200 and 262272 allocation probes failed with `HIP error 2`.
The bounded implementation passes both allocation probes and short public
requests; full-depth performance is separate validation.

This unit bounds a sliding layer's cache to the band it can actually read
(`window + max_block - 1` rows) plus one decode-graph bucket of history, while a
global layer keeps the full context. It adds a per-layer cache base, an exact
rebase/compaction step, and cache-relative offset translation at launch. Global
history, logical positions, multi-block attention, reset, and speculative
verification are preserved, and both consumers that index by absolute position
now consume the base:

- the MTP assistant offsets its keep-mask predicate and the kernel's
  `row_offset` by `view.base`;
- the decode-graph capture rebases before capture, refuses a runner whose
  history reserve is smaller than its bucket, and translates every frozen
  absolute offset to a cache slot.

The history reserve is what makes the graph's frozen bucket origin and end stay
inside the retained band at every rebase. Without it the captured attention
shape would have to be clamped, which changes the presented key count and the
flash/split partition across the rebase. Rewinding below a bounded sliding
layer's retained base is refused by name rather than silently shifting the
window.

## Changes

- `hipengine/runtime/gemma4.py`
  - New `GEMMA4_SLIDING_BUCKET_WIDTH = 64` (defined before the first default
    argument that uses it).
  - `gemma4_layer_key_count` documents that its band is the *read* span;
    `_resident_bytes` charges each layer `gemma4_sliding_cache_rows(...)` instead
    of one full-context term, and adds the runner's one compaction-staging plane
    (`(window - 1 + reserve) * kv_width * 2`) for the widest bounded sliding
    layer.
  - New `gemma4_sliding_cache_rows(attention, capacity, *, rows, reserve)`: the
    cache owns `window - 1 + reserve + max(rows, reserve)` rows, capped at the
    context. New `gemma4_sliding_cache_base(*, base, capacity, window, start,
    rows, reserve)`: the pure rebase planner. No-op while `start +
    max(rows, reserve) <= base + capacity`; otherwise rebases to
    `max(0, start - window + 1 - reserve)`, the earliest key any row of the block
    reads, minus one bucket of history.
  - `Gemma4Runner` gains `sliding_reserve` (defaults to the bucket width,
    validated non-negative), `_kv_capacity`, `_kv_base`, `_bounded_sliding`, and
    a reusable `_compact_staging` buffer. Sliding layers allocate the bounded
    band; global layers keep `capacity`. `__post_init__` forwards
    `sliding_reserve=self.sliding_reserve` to `_fit_prefill_block`, so a
    non-default reserve is charged by the fit that picks the block as well as by
    the allocation that follows it.
  - `_prepare_sliding_caches` / `_compact_sliding_layer` shift the retained band
    down when a block would overflow. The copy goes through one staging buffer
    because source and destination can overlap. `reset` clears the base; `rewind`
    keeps it and validates every sliding layer first, refusing a target whose
    window starts below the retained base (history below the base was compacted
    away) with a message naming `reset()` + re-prefill as the clearing action.
  - `_launch_block` translates `write_offset` and `key_begin` to cache-relative
    slots using `_kv_base`; global layers have base 0 and are unchanged. No clamp
    is needed anywhere: the reserve keeps both the prefill first key
    (`kv_write_offset - window + 1`) and the graph's frozen origin
    (`max(0, bucket.start - window)`) at or above the base, so the mask built
    from absolute `key_begin` and the kernel's key pointer address the same first
    key.
  - `Gemma4SharedKV` gains `base`; `shared_kv` reports the bounded capacity and
    `live = position - base`.
- `hipengine/runtime/gemma4_assistant.py`
  - `gemma4_assistant_keep_mask` gains `base`: the causal/window predicate is
    evaluated on absolute positions (`base + slot`) while the returned mask stays
    slot-indexed.
  - `Gemma4AssistantHead.forward` computes `slot_position = position - view.base`
    and passes it as `row_offset`, with the mask built through `base=view.base`.
    Both are the identity for a global block (base 0).
- `hipengine/runtime/gemma4_decode_graph.py`
  - `step` rebases the bounded caches on the session stream before capture (so
    the memcpys are not recorded). Both bounded and unbounded runners cut the
    final bucket at the physical context end, never at the sliding band.
  - `_capture` asserts the reserve invariant: the runner's reserve must be at
    least the bucket width, and for every bounded sliding layer `base <=
    bucket.start - window` and `bucket.end - base <= band`. A violation raises
    naming `sliding_reserve` instead of clamping the mask.
  - New `_context_end_bucket(position, capacity)` cuts the bucket at the physical
    context end for **every** runner. `_Bucket.for_position` rounds the end up,
    so at a context that is not a bucket multiple the last bucket's end runs
    past `capacity`; every global layer's cache holds exactly `capacity` rows,
    and a bounded runner keeps those global caches at the full context, so the
    cut is required there too. It is never cut at the sliding band -- that would
    change the frozen shape at every rebase. The cut only lowers the end, so the
    reserve invariant still holds against the cut bucket.
  - `_finalize_capture` is split out so the graph-exec cleanup on a failed
    instantiate/identify/zero-tail is directly testable.
  - `_CaptureAppend` carries the layer base; `_identify_appends`,
    `_zero_pending_tail`, and `_retarget_appends` all subtract it.
  - The capture key includes `tuple(runner._kv_base)`, so a rebase recaptures.

Memory formula, 26B-A4B UD-Q4_K_XL (25 sliding 8x256, 5 global 2x512, window
1024, max_block 1024, reserve 64), BF16 K+V:

- before: `KV(capacity) = capacity * 225280 B`
- after: `KV(capacity) = 25 * min(capacity, 2111) * 8192 + 5 * capacity * 4096`
  plus a constant 4,452,352 B staging plane.

| capacity | before GiB | after GiB | saved |
| --- | --- | --- | --- |
| 8320 | 1.746 | 0.562 | 1.184 |
| 32896 | 6.902 | 1.030 | 5.872 |
| 131200 | 27.526 | 2.905 | 24.621 |
| 262272 | 55.027 | 5.405 | 49.622 |

These are calculated KV payload sizes, excluding the constant staging plane,
weights and other workspaces; they are not measured process peaks. No
llama.cpp memory-equivalence claim is made.

- Note for the GPU run: the planner does **not** rebase every decode step. After
  a rebase at start `S`, `base = S - window + 1 - reserve` and
  `base + band = S + max_block`, so the next rebase triggers at
  `start > S + max_block - reserve`. With the default `max_block=1024` and
  `reserve=64` that is a rebase every 961 decode steps in steady state (the
  first is at position 2048), i.e. the `window - 1 + reserve` = 1087-row
  retained tail is copied ~1.1 rows per step per sliding layer (213 MiB per
  rebase, ~0.22 MiB/step over 25 layers). An every-step rebase is the
  small-block case only (`max_block <= reserve`). These copy-volume estimates
  do not establish negligible latency; throughput measurement is still needed.
- The INT8 per-token/head cache still owns the full context; bounding it is a
