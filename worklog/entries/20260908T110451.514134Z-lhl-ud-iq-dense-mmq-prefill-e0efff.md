# Dense raw-IQ integer-MMQ prefill on gfx1151

## Summary

Item 3 of `docs/UD-OPTIMIZED-ROUTE-PLAN.md`, the last and largest routing
block. Raw dense IQ4_XS/IQ3_XXS prefill now runs on the existing source-shaped
integer-MMQ kernel instead of the strict per-row GEMV. **Prefill 41.54 ->
127.20 tok/s (3.06x)** on the published sweep protocol, decode unchanged.
Prefill GPU time 12,477 -> 4,051 ms; the IQ4_XS kernel alone 9,280 -> 791 ms.

Campaign cumulative on that protocol: **22.1 -> 127.2 tok/s (5.75x)**, and the
gap to the plain `Q4_K_S` file on the same host and protocol **13.3x -> 2.32x**.

No new kernel, no repack, no weight sidecar.

## Changes

- `gguf_iq_source_mmq_prefill.py`: dense route beside the selected one -
  `IQDenseMMQWorkspace`, `iq_dense_mmq_session`/`_workspace`/`_nbytes`, the
  single-expert metadata builder, and dense launchers for IQ4_XS/IQ3_XXS whose
  signature matches the raw GGUF linear launch ABI so the dispatcher swaps them
  in by variant name alone.
- `quant/__init__.py`: import the module so its keys exist for the gfx1151
  alias pass. This is what puts the dense keys on gfx1151.
- `hip_gfx1151/__init__.py`: `GGUF_IQ_DENSE_MMQ_PREFILL_POLICY`.
- `gguf_linear.py`: `_iq_dense_mmq_prefill_dispatch` wired after the raw-K
  rowbatch selection, plus the workspace in the dispatch cache key.
- `qwen35_gguf_runner.py`: `_ensure_iq_dense_mmq_buffer` /
  `_iq_dense_mmq_context`, entered wherever the planar-Q6 integer context is.

**Why the dense case is free.** The kernel addresses weights as
`qweight + expert*expert_bytes + out_row*weight_row_bytes + block*block_bytes`
with `expert_bytes = out_features*weight_row_bytes`, so at `expert == 0` it
reads exactly the dense raw GGUF layout. Dense is the degenerate single-expert
case; only trivial per-`rows` metadata and a Q8_1 activation plane are new.

**gfx1151 scope, as asked.** The dense keys register on both HIP backends
through the normal alias path, but only gfx1151 declares the policy, so the
route is inert on gfx1100 pending its own qualification. Importing the module
does **not** leak the selected/MoE keys onto gfx1151 - verified and pinned by
test.

## Numerics

Context512, 18 prompts x 9 forced steps, production config, independent
tokenwise teacher; consumed tokens verified against the teacher input binary.

| arm | mean | p95 | p99 | max | top-1 |
| --- | --- | --- | --- | --- | --- |
| UD-U3 | 0.0012376 | 0.0053786 | 0.0211052 | 0.0332762 | 162/162 |
| role coverage | 0.0012709 | 0.0048322 | 0.0239101 | 0.0387342 | 161/162 |
| **dense MMQ** | **0.0010796** | 0.0051188 | 0.0217009 | 0.0354152 | **162/162** |

Outer gate passes (max 0.0354 <= 0.05, top-1 100%). The MMQ arm has the best
mean of any default measured and recovers the top-1 position the role-coverage
step lost.

**Read that carefully.** This is agreement with a *llama.cpp* teacher while
adopting *llama.cpp's own* MMQ dataflow, so part of the improvement is
convergence toward the reference implementation rather than evidence of higher
absolute quality. It should not be quoted as a quality win without a
BF16-teacher or task gate. mean/p95/p99 remain above the strict thresholds -
the pre-existing campaign state.

## Limitations

- gfx1100 unchanged by design; separate follow-up.
- IQ4_NL, Q3_K, IQ3_S, IQ2_S, IQ2_XS have no MMQ kernel and stay on the strict
  GEMV: 1.77 GB and roughly 44% of the residual prefill GPU time in K_M.
- `min_rows=32` is an unswept first choice, not a measured crossover.
- Task and repeat/serving gates outstanding, as for every default here. All
  zbook rates provisional pending the desktop gfx1151.
