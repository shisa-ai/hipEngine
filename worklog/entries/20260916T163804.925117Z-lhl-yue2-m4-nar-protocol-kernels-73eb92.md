# YuE2 M4 NAR protocol and kernels

## Summary

M4 (HIP NAR: cached AR conditioning, bidirectional NAR attention, timestep and
position features, device midpoint loop) is **in progress**. This checkpoint
lands the two halves that are complete and validated: the CPU-side protocol
(chunking, one-draw noise slicing, the FP64 solver schedule, the BF16 time shift,
the timestep sinusoid, `nar_cond_end` visibility) and the four new device
kernels (bidirectional GQA attention, position-embedding gather-add, timestep
broadcast-add, two-rounding state update). The `Yue2NarRuntime` that stitches
them into a chunk solver is designed below but not yet written.

## Upstream contract (pinned `yue2` 0.1.5)

Read from `/tmp/yue2whl/yue2/nar.py` and `modeling_yue2.py`, which the oracle
fixtures were generated with:

- `song_chunks` draws **one** `[frames, 64]` FP32 noise tensor for the whole song
  (`torch.Generator(device="cpu").manual_seed(seed)`), then takes a per-chunk
  *view*, so a chunk's noise depends on the global frame index. Chunk size is
  `min((context - prefix_tokens - 3) // 2, context)`; each chunk's AR
  conditioning is `prefix + [codec_id + CODEC_OFFSET] + [MUSIC_END]`.
- `CachedNAR` prefills that AR prefix once through the **AR** weights
  (`self_attn`, `mlp`) and retains each layer's K/V. `nar_cond_end > 0` restricts
  NAR visibility to the first `nar_cond_end` AR positions ("text-only"); `0` is
  the release path and sees the whole prefix.
- `velocity(state, raw_t)`: `F.pad(state, (0, 0, 1, 1))` (zero boundary rows),
  `vae2llm(x) + time_embedder(shifted) + latent_pos_embed(local)` where the local
  positions start at 0 and clamp to `max_latent_frames - 1`, then per layer
  `nar_self_attn` with RoPE at positions `ar_length + i`, attending to the cached
  AR keys **plus all** NAR keys (no causal mask), then `nar_mlp`; finally
  `llm2vae(model.model.norm(x))[1:-1]`.
- `solve`: `h = 1/steps`, `t = 1 - i*h`, `raw = clamp(logit(t), -20, 20)` in
  **FP64**, `u = velocity(state, raw)`, `mid = state - u*(h/2)`,
  `state = state - velocity(mid, clamp(logit(t - h/2))) * h`, all in BF16, with
  the final latents returned in FP32.

## Findings worth keeping

- **Attention reduction bug found by the RED gate.** The first attention kernel
  reduced `running_sum` across the block, but every lane already walks the whole
  key loop and therefore already holds the full denominator, so the reduction
  multiplied it by `head_dim` (a clean 128x error). The fix removes the
  reduction; the kernel now matches the FP64 reference within `rtol=2e-3`.
- **Transcendental functions are gated at BF16 resolution.** The timestep
  sinusoid computed in NumPy differs from torch's FP32 path by up to 7 ulp, and
  **all 256 entries still round to the same BF16 value** — which is the only thing
  the `TimestepEmbedder` MLP consumes. The same reasoning applies to the
  `latent_pos_embed` table, except that the table is a **checkpoint buffer**, so
  the runtime must load it rather than recompute it: the recomputed formula
  agrees with the stored table on 98.2% of 50.3 M entries and differs by exactly
  one BF16 ulp elsewhere (libm vs SLEEF).
- **The state update must round twice.** torch computes `state - v * (h/2)` as
  BF16 tensor ops, so the product rounds before the subtraction; the existing
  `vv_scale_residual_bf16` uses a fused multiply-add (one rounding) and is
  therefore not equivalent. `nar_state_update_bf16` mirrors torch and is verified
  bit-exact against NumPy.
- **Shared memory cannot hold all attention scores.** `ar_length + nar_length` may
  reach the full model context (24,576 keys = 98 KB of FP32 scores), so the
  attention kernel tiles its key loop and rescales a running softmax.
