# Batch runner sparse threshold qualified at 2050-2100 tokens

## Summary

The batch runner's per-row top-k index selection -- the path that only exists
past `dense_equivalent_limit = block_budget*ratio + ratio - 1 = 2051` positions
for UD-Q4_K_XL -- ran on the real checkpoint and agrees with c1 on every
semantic surface measured: routing at the crossing, selected counts, imported
state, and the documented selection rule. No policy, routing, or state-ownership
defect appeared. The isolation evidence is diagnostic -- an idle neighbour stays
byte-identical and a row's keys are nearer its own reference than its
neighbour's -- not a per-write proof of the exact ownership contract.

The selected *sets* differ in 105 of 336 sparse-layer comparisons (1,096
positions of 688,596 selected). That difference is not a different rule: each
side's selection reproduces the documented host rule exactly on its own device
score bytes (336/336 both sides), and running c1's scalar top-k entry point on
the batch's score bytes reproduces the batch's selection exactly (105/105). No
difference occurs at a cut the measured drift cannot reach -- on every differing
comparison at least one side's cut margin is within 4x the largest score delta --
but that test is deliberately conservative (one large delta anywhere marks the
comparison near-tie), so the policy claim rests on the host-rule and cross-feed
checks, not on that count. The cause is index-query drift, quantified below.

This is correctness evidence at depth for three prompts, six forced steps, two
compositions, one host, one artifact. It is **not** a production admission:
the calibrated short-suite envelope and the normative long-prompt gate are both
unrun for the batch path (see "Not established").

## Changes

New diagnostic script `scripts/qwen4exp_batch_sparse_threshold_check.py` and a
CPU unit regression `tests/test_unit_qwen4exp_batch_sparse_threshold_check.py`
(no production file changed, no flag added, `docs/REFACTOR.md` untouched,
no benchmark rollup entry: this measures correctness, not throughput):

- builds prompts of an exact token length from three distinct sources, so the
  first continuation step lands on a chosen side of the bound;
- shares one weight residency between c1 references and the batch owner;
- audits every import by logical position through each side's own page table;
- wraps `run_qwen4_exp_dense_qsa_layer` and `run_qwen4_exp_batch_qsa_layer`
  with host-side taps that read, immediately after each layer returns, the index
  query bytes, pooled index keys, block starts, raw device scores, and selected
  positions/count;
- compares each side's selection against
  `kernels/cpu_reference/qwen4_exp.qsa_select_positions` on its own score bytes,
  and cross-feeds the batch's score bytes through c1's scalar
  `qwen4_exp_qsa_topk_expand_f32_i64` entry point;
- digests one idle slot's whole state across a neighbour's steps;
- repeats two prompts side by side and compares every row against its own
  single-row result.

The CPU regression covers the four repairs above, the page-table gather, the
cut-margin helper, and the near-tie classifier including the case that shows it
is conservative.

Four defects were found in the script itself while building it and are fixed in
this candidate version: the c1 graph-capture profile leaked into the reference
arm, the sparse-score tap read mixer rows instead of sparse-subset rows (visible
as 12 false "policy mismatch" entries in a mixed dense/sparse step), the slot
digest read the KV slab from block 0 instead of the slot window, and the
composition baseline was keyed by slot instead of prompt. Each is now a named
helper (`_apply_eager_profile`, `_sparse_subset_row`, `_slot_window_offset`,
`_baseline_for`/`_selection_baseline_key`) with a CPU unit test, and
re-introducing any of the four makes that test fail.

Threshold crossing, measured rather than inferred: the 2050-token prompt's step
0 lands at context 2051 and runs **0** sparse layers in both arms; step 1 lands
at context 2052 and runs **12** in both. c1's rule (`count > 2051`) and the
batch's rule (`count // ratio > 512`, i.e. `count >= 2052`) are the same
predicate for every budget/ratio pair, because
`(budget+1)*ratio - 1 = budget*ratio + ratio - 1`.

Attribution of the set differences, per layer:

- Imported raw keys are bit-identical, so a complete block made only of imported
  keys pools to bit-identical values: 108 of 336 comparisons measure a pooled
  delta of exactly 0.0. A continuation key enters a complete block as soon as
  `count % ratio == 0`, and once it does the pooled key for that block drifts and
  stays drifted, which is why the remaining 228 comparisons show a nonzero
  pooled delta.
- The index query differs from the first step on (0 of 336 comparisons have
  equal query bytes): e.g. layer 3 at context 2053, `max|dq| 5.25e-3` on
  `|q|max 3.22`, `max|dscore| 2.95e-3` on `|score|max 10.63`, cut margin
  `5.42e-3` -> same selection.
- Flips appear where the drift reaches the cut. Across the C2 comparisons the
  differing selections have median margin 0.049 against median score drift
  0.659; the identical ones have median margin 0.115 against median drift 0.183.
  The near-tie test itself is conservative: it compares a cut margin with the
  *largest* score delta on that layer, so one large delta anywhere marks the
  comparison near-tie. It is supporting evidence, and the policy claim rests on
  the host-rule and cross-feed checks, which do not depend on it.
- Composition changes the arithmetic but not the rule: 25 of 132 C2 selections
  differ from the same row running alone (all on near-tie cuts), while top-1
  stays 100% and KL stays <= 1.2e-4. Cross-width equality is diagnostic under
  `docs/EXECUTION-PROFILES.md`; nothing here shows neighbour *data*
  contamination, which the idle-slot and ownership checks contradict.

## Not established

- **Normative long-prompt gate.** `docs/EXECUTION-PROFILES.md` section 6.1 gates
  2K-class prompts against a round-off floor: `strict` rerun with one BF16 ulp
  flipped in one prompt embedding row, per seed, plus 8K/16K retrieval. That is
  `scripts/qwen4exp_long_context_gate.py`, which drives profile candidates
  (`CANDIDATES` in `scripts/qwen4exp_layer2_profile_gate.py`); the batch runner
  has no candidate adapter, so it is not admitted by it. The numbers above are
  batch-versus-c1 diagnostics, and c1 is not the strict teacher.
- **Short-suite calibrated envelope** (mean/p95/p99/max KL, top-1 by category,
  task checks on 450 teacher-forced rows) is unrun for the batch path.
- **Deterministic repeat** of this ladder was not run; the run reproduced
  step-for-step across two invocations, but that is not a formal repeat gate.
- **Serving integration.** Nothing in this unit is wired: no engine, server,
  scheduler, or default-path route selects the batch runner, so "the sparse path
  works" here means the runtime entry point works, not that a server serves it.
- Contexts past 2,106 tokens, more than two concurrent rows, C4 width, and
  prefill *inside* the batch (the batch has no prefill; it imports c1's).
- **MTP/speculative qualification.** The batch runner's rollback tokens are
  unit-tested but no speculative decode has run against this path at depth.
- **Ownership.** The idle-slot digest and the proximity check are diagnostics:
  the first proves a *neighbouring idle slot* is untouched, the second that a
  row's keys are closer to its own reference than to its neighbour's. Neither is
  a proof of exact isolation, which the profiles doc states as an exact
  ownership contract and which would need a per-write audit.
