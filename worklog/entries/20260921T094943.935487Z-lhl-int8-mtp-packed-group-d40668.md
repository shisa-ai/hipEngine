# Packed INT8 MTP group: root cause is the BF16-only packed target verifier, not the declaration

## Summary

A speculative INT8 request group (`c>1`) does not speculate. The starting hypothesis
was that `gguf_dense_int8_native_chain` refused it at admission because
`max_group_rows=1` plus `group_rejection_reason="packed_int8_mtp_not_implemented"`.
Widening the declaration does admit the group, but it does **not** make the group
speculate. A live gfx1151 run showed the group is admitted, coalesced, and then
fails one layer deeper, so the declaration is necessary and not sufficient.

Three gates sit in series. Only the third one is the real gap:

1. **Admission (declaration).** `hipengine/models/qwen35.py:810` refuses a
   multi-row INT8 group with `packed_int8_mtp_not_implemented`. Widening
   `max_group_rows` to the offered width admits it; the request then reaches the
   runtime instead of being refused up front.
2. **Packed AR direct INT8 prefill.**
   `qwen35_gguf_runner.py:23848` refuses multi-session packed prefill with
   `"packed AR direct INT8 is admitted only for single-row prefill until shared
   prefill ownership is qualified"`. That is a qualification claim, not a
   capability statement, so it was opened experimentally. With it open the packed
   prefill completes (`prompt_fallback_reason: None`, `candidate_budget: 3`) and
   the group's generated ids match the autoregressive control, so the route is
   numerically sound at 2 rows on this artifact and prompt.
3. **Packed target verifier.** `verify_target_blocks_batch`
   (`qwen35_gguf_runner.py:21612`) raises
   `NotImplementedError("packed target verifier currently supports BF16 KV only")`
   for `kv_storage_dtype != DType.BF16`. The grouped MTP cycle calls it
   (`qwen35_gguf_mtp2.py:5183`), so the cycle fails before commit, recovers to
   autoregressive, and **permanently disables the provider for that request**
   (`_drop_request(rid, disable=True)` from `rollback_cycle`,
   `qwen35_gguf_mtp2.py:6158`). Every later cycle then declines with
   `request N unregistered or disabled`.

The kernels for a rows>1 INT8 verify already exist and are registered on both
backends: `_full_attn_shared_batch_spans` binds `INT8_PER_TOKEN_HEAD` with
per-token-head scales in the `verify_chain` role,
`_run_full_attention_attn_chain_rows_exact` quantizes each appended row and
attends all of them through `per_token_head_gqa_splitk_gate_bf16_verify_chain_spans`
(a single spans registration that takes rows as a parameter, so width is not the
limit), and gfx1151 imports and re-registers the gfx1100 attention kernels. The
gap is therefore **route selection**, not a missing kernel: that chain is reached
today only from AR decode (`_run_native_attention_bulk_ffn_layer_rows`, call site
`qwen35_gguf_runner.py:8021`), never from the grouped MTP verify.

## Changes

- `tests/test_unit_int8_mtp_serving.py`: adds
  `test_dense_int8_mtp_admits_the_packed_group_its_verifier_implements[2|4]`,
  marked `xfail(strict=True)`. It pins the intended contract, records the
  measured failure and its exact source line, and names the clearing command.
  `strict=True` means the suite fails the moment the route lands, which forces
  the marker to be removed rather than left behind.
- No production change. The declaration widening was written, measured, and then
  reverted: with the verify route still BF16-only it would convert a clean
  admission refusal into a failed cycle plus a disabled provider while leaving
  the request autoregressive, which is a worse path than the refusal.

## Validation

- Unit: `.venv/bin/python -m pytest tests/test_unit_int8_mtp_serving.py -q` →
  `2 xfailed` (the new `[2]` and `[4]` params) plus 23 passed. The xfail is the
  intended RED state; `strict=True` guards it.
- Live, gfx1151 (`zbook`, Qwen3.8-27B-Q4_K_M, `--kv-storage
  int8_per_token_head --kv-scale-dtype fp32`, `--max-context-tokens 16384`,
  `--max-active-requests 4`, `--generation-batch-window-ms 50`,
  `--speculative-mtp-serving enabled --speculative-candidate-budget 3`), both
  runs confirmed `KV cache int8_per_token_head (fp32 scales)` and
  `kv_attention_source: int8_direct` with `persistent_bf16_mirror_bytes: 0`, so
  this is a compact-INT8 measurement and not the short-context BF16 mirror:

  | Run | c1 MTP | c2 MTP | c2 AR | ids match |
  | --- | --- | --- | --- | --- |
  | pristine declaration | 0 cycles | 0, 0 | 0, 0 | yes |
  | declaration widened | 7 cycles | 0, 0 | 0, 0 | yes |

  With the declaration widened the c=2 diagnostic reports
  `plan_group_rows: 2`, `plan_ar_only: true`, `plan_reason: no_provider`,
  `provider_decline_reason: request 3 unregistered or disabled`,
  `recoverable_failures: 1`, `failure_reason_counts:
  {precommit_failure_ar_fallback: 1}`. `HIPENGINE_DEBUG_SAMPLED_ROUTE=1` printed
  the underlying cause:
  `[cycle-failure] ids=(3, 4) reason=NotImplementedError:packed target verifier
  currently supports BF16 KV only`.
- With the prefill gate additionally opened, the packed INT8 prefill itself
  succeeds and the group's ids match both the c=1 MTP arm and the c=2
  autoregressive control (`c2_ids_match_c1: true`, `mtp_ids_match_ar: true`),
  which isolates gate 3 as the remaining blocker.

Two environment facts cost earlier attempts and are worth keeping:

- `strixhalo` cannot JIT at all right now: its mambaforge `_rocm_sdk_devel` is
  missing `lib/llvm/lib/clang/*/lib/amdgcn`, and the cache entry
  `~/.cache/hipengine/build/runtime_state-96ac7ba34df3a387` holds only
  `manifest.txt` with no `.so`. Pristine and patched trees fail identically with
  `clang++: error: cannot find ROCm device library`.
- This artifact (17,106,775,008 bytes) carries a recorded compact-INT8 quality
  rejection, so a plain `--kv-storage int8_per_token_head` server silently starts
  on BF16 KV. Forcing compact INT8 needs
  `HIPENGINE_GGUF_INT8_KV_ALLOW_UNVERIFIED_LONG=1`,
  `HIPENGINE_GGUF_INT8_KV_BF16_PREFIX_FULL_LAYERS=0`, and a context above the
  8192 short-context BF16-mirror threshold; the startup KV line then reads
  `int8_per_token_head (fp32 scales)`. A run without that line is not an INT8
  measurement.

## Next

- Route the grouped MTP verify through the INT8-capable rows>1 chain
  (`_run_full_attention_attn_chain_rows_exact` / `_full_attn_int8_verify_fn`), or
  teach `verify_target_blocks_batch` INT8 KV. Then widen
  `gguf_dense_int8_native_chain.max_group_rows` and drop the `xfail` marker; the
  contract test will fail loudly if the marker is left in place.
- Open gate 2 (multi-session packed INT8 prefill) as part of the same unit. Its
  message is a qualification claim, and the measured run above shows the route
  produces the autoregressive ids at 2 rows.
- Do not widen the declaration on its own. Measured: it admits the group and the
  cycle then fails pre-commit and disables the provider for that request.
