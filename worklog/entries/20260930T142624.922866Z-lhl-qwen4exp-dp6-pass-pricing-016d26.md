# DP-6 fully priced from committed data: the SSM causal conv is 2.1x the attn_qkv side, so the prescribed order inverts

## Summary

`DP-6` (projection epilogue fusion) was the one remaining actionable row whose own
experiment column ended in an unresolved conditional — *"Attribute the conv, q/k-norm,
RoPE and KV-store passes at 16-47 in X-3; build the `attn_qkv` epilogue first **if it is
the larger**"*. The attribution was never done, so the row could not be ranked against
`DP-5`'s 131.001 ms and nobody knew which of its two halves to build.

The X-3 capture's raw `rocprofv3` kernel trace is **still on disk**
(`/tmp/qwen4exp-ledger-20260928-current/role-trace/gfx1151/3033290_kernel_trace.csv`,
sha256 recorded in that artifact's `raw_sha256`), so the passes were attributed from
**committed data with no GPU run**.

## Result

Against the capture's own **15,741.963 ms** kernel union:

| pass | ms | % of union |
| --- | ---: | ---: |
| **SSM causal conv** (`conv_prefill_exact` 115.213 + `conv_prefill_state` 0.908) | **116.121** | **0.738%** |
| q/k norm + RoPE (`qsa_split_norm_rope` 47.872 + `qsa_norm_rope` 3.693 + `qsa_pool_norm_rope` 0.634) | 52.199 | 0.332% |
| KV store (`write_paged_kv_mixed_value_prompt_position_tensor`) | 3.263 | 0.021% |
| **attn_qkv side** | **55.462** | **0.352%** |
| **DP-6's whole scope** | **171.583** | **1.090%** |

**The SSM causal conv is 2.09x the entire `attn_qkv` side**, so the conv fusion is the one
to build first. The row's conditional resolves, and it resolves against the order the
column implied.

## The 319.494 ms bucket would have overstated this row 5.8x

The row's warning — *"Do not build the `attn_qkv` epilogue on the strength of 319.494 ms —
that number covers more passes than this row would fuse"* — was correct, and the
decomposition quantifies it: **74.1% of that bucket is `grouped_rmsnorm_*`**, which this
row does not fuse, plus 8.9% `qsa_gate_context`. Acting on the bucket would have claimed
**5.76x** the real `attn_qkv` opportunity.

## Applicability holds at the measured operating point

gufo's `DenseF16SsmGemm` conv fusion requires **>=1024 rows**. The capture ran
`prefill_chunk_size: 1024` with **264 launches at `rows=1024`** on the wide route
(`hipengine_gguf_q8_0_dense_wide256_f16in_f32_f32_out`), so both conditions this row needs
— the row floor and the wide route — hold together here. A chunk size below 1024 breaks
the first, so the pricing does not transfer to a smaller-chunk configuration unexamined.

## An incidental finding that touches the GDN rows

In this capture the SSM causal conv is **116.121 ms of the 844.295 ms GDN bucket (13.8%)**,
so the GDN family is not the recurrence alone. This is **not** comparable to `GD-3`'s
"the GDN recurrence *is* the GDN family: 194.487 ms of 3,914.468 ms" — a different capture
at a different shape (p512 vs this p4096/chunk-1024 run) — and neither is restated as the
other. Recorded so the next reader of GD-3/GD-4 knows the family has another component.

## A verification bug caught in my own check

The first verification pass reported `conv 115.213 ms` and `kv store 0.000 ms` because it
looked kernels up by exact name and two of the three carry a `void ` prefix in the CSV
(`void (anonymous namespace)::qwen35_write_paged_kv_...`). Re-run with substring matching,
every figure above reproduces exactly — including the derived ratios (2.09x, 5.76x, 13.8%)
and the bucket remainder (2.151 ms). Recorded because a silently-zero lookup is exactly the
failure that produces a confident wrong number.
