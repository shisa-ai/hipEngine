# Review staged exchange ordering, timing claims, and next measurements

## Summary

Reviewed `025e9bb05` without changing its implementation. The same-stream,
double-buffered batched exchange is a reasonable successful-path optimization;
the stored same-session serial/batched diagnostic supports pursuing it further.
It does not establish a qualified model-level TP speedup or a physical transport
latency floor. Keep the candidate and proceed to bounded native-orchestration
and actual local-segment measurements, not public/default promotion.

## Changes

### P1: projection is being promoted to a qualified model result

`benchmarks/README.md:962-969` and the campaign's Packet 0 decision call the
projected 1.04-1.17x a qualified win delivered by the exchange. The artifact
`tp2_break_even_staged_exchange_batched.json` explicitly says `certified: false`
and records no shard-kernel evidence. Actual local kernels, state trajectories,
production numerical gates, and end-to-end TP latency have not been measured.

Keep the transport diagnostic, but describe the model estimates as conditional
projections. Passing this synthetic sum check is not passing the model's
production profile. A 1.3x result remains an aspiration, not the admission bar.

### P1: the event probe does not establish a 30.8 us physical floor

`scripts/tp_collective_bench.py:1101-1153` records an event, submits a copy from
Python, then records the end event, on an otherwise idle stream. HIP events
timestamp when they reach the stream head; elapsed event time can therefore
include submission gaps and scheduling/ordering overhead. The probe runs ranks
serially, takes only three samples per rank/direction, and pools ranks into a
median. It is not a trace of the batched chain's actual DMA critical path.

The measured 15.4 us intervals are legitimate probe observations, but not an
immutable cost for every future transport implementation. Do not add those
intervals to wall-clock host counters as independent costs: the counters already
include time spent inside submission and synchronization. The inequality
`42.9 < 30.8 + 26.4` does not measure overlap.

Consequently, neither "device signalling can only remove 9.4 us" nor "1.3x is
unreachable through transport work" follows. Conversely, a different protocol
does not make data-readiness latency disappear. Both require measured critical
paths. Use an actual copy trace or a prequeued/captured copy probe that removes
host starvation, retain rank-specific samples, and distinguish the probe from
in-chain copy latency.

### P2: phase accounting omits potentially important native-loop work

The stored batched marginal is 42.874 us, while host phase counters sum to
26.387 us. These are different statistics/populations (ladder slope versus
averages over warmup and timed work), so their 16.487 us difference is a
diagnostic discrepancy, not an exact new phase.

There is nevertheless concrete unaccounted work: phase clocks begin inside
`scoped_current_device` in submit/wait helpers, excluding context entry/exit
and device get/set/restore. Python loops, helper calls, pointer preparation,
counter maintenance and timing overhead are also outside parts of the counters.
The accumulation creates NumPy views and copies a new array each step.

Thus the claimed native-loop ceiling of 10.2 us submission plus 6.5 us
accumulation is unsupported. Earlier submission can also change exposed waits,
so the Python wait measurement is not necessarily constant in native code.
Reconcile total wall with exclusive phases using the same iterations and depth;
keep detailed instrumentation separate from performance runs.

The quoted 0.2 us return-wait number is the final chain drain amortized over
steps. It is not a paired measurement of the benefit of removing per-step
return waits. Serial versus batched changes both rank batching and return waits.
Add a batched-with-return-waits arm if separate causal attribution is required.

### P2: selective sharding must restore the unsharded compute term

`docs/QWEN38-27B-GFX1100-TP2.md:554-559` says MLP-only sharding cuts reductions
"without restoring replicated attention or GDN work". Relative to full TP it
does restore the full attention/GDN work on each rank when these are replicated.
The slower rank can determine that segment's completion time. Single-owner
attention instead needs the corresponding result broadcast; it is not free.

Measure both cards' actual complete and shard-shaped segments with local layout,
output dtype, residual/norm boundaries and relevant context. Measure representative
sequences of compute -> exchange -> compute, not merely an idle-buffer exchange.
Choose MLP-only, full TP or static per-family/layer selection from segment
savings net of exposed communication. One global fixed-share assumption and
whole-model weight ratio cannot resolve that choice.

### P2: asynchronous slot-lifetime testing is still missing

The success-path ordering is sound as written: H2D reads and subsequent D2H
writes on a rank use the same stream, and CPU accumulation waits for both D2H
operations. Two alternating host slots and final drain protect reuse in this
specific loop. A real runner must preserve or explicitly bridge those stream
dependencies before its next compute consumer.

The new test counts waits, but `_ShadowChainRuntime.memcpy_async()` copies bytes
immediately and its synchronize method only increments a counter. It cannot
expose premature host-slot mutation while an H2D read remains outstanding.
Hardware validation also reads only element zero after filling all ranks and
elements with the same seed; it is insufficient for general vector/rank ownership.

Before serving integration, add a delayed stream-queue oracle with H2D reads at
execution time, injected rank skew, odd/even depths, repeated slot reuse and
drain/cancellation. Verify full vectors with rank-distinct finite inputs and a
bounded recurrence informative through the maximum timed depth. Test timeout
and teardown; this screen still uses unbounded stream synchronization.

### Guidance

Do not replace one unmeasured optimistic claim with an unmeasured impossibility
claim. The screen justifies a bounded next experiment, not a general statement
that this gain exceeds every available kernel/transport change or that native
code cannot help. No GPU-side spinning or PCIe isolation change is warranted
from these timings alone.
