# Batch the staged exchange's submission and drop the return-copy waits

## Summary

The previous unit left the host-staged exchange at 71.1 us per reduction and
attributed ~55 us of that to "copy plus host wait", with the transfer estimated
at ~2 us each way. Both parts of that reading were wrong, and correcting them
moved the TP2 projection above 1.0x.

The orchestration was the problem. The serial structure performed four host waits
per reduction - submit and wait for rank 0, then for rank 1, then the same for
the return copies - so the two transfers of a pair never overlapped. Submitting
both device-to-host copies before awaiting either, and not awaiting the return
copies at all, costs two waits per reduction:

| Protocol | Host waits/reduction | Per-reduction | 128 reductions | Projection at 0% / 10% / 20% / 30% |
| --- | ---: | ---: | ---: | --- |
| one rank at a time | 4 | 71.7 us | 9.17 ms | 1.016x / 0.963x / 0.916x / 0.873x |
| both ranks in flight | 2 | **42.9 us** | **5.49 ms** | **1.170x / 1.101x / 1.040x / 0.985x** |

Host orchestration is worth **28.8 us per reduction** on its own, and the
projection now clears 1.0x at 0%, 10% and 20% fixed-cost share.

Dropping the return-copy waits is safe, and the reason is worth recording because
it looks like removing a dependency. The host write into a staging slot for step
`i + 1` must not race the return copy that read that slot at step `i`. It cannot:
the slot is reused two steps later, the device-to-host copy for that step is
enqueued after that return copy on the same rank stream, and the host waits for
the device-to-host copy before accumulating. The wait the host already performs
is therefore also the slot-reuse guard, and the extra return-copy wait buys no
ordering. The chain itself is ordered by the same stream: the return copy for
step `i` and the device-to-host copy for step `i + 1` run on one stream in host
enqueue order.

The phase attribution is now separated instead of lumped. Per reduction: **4.7 us**
to submit the device-to-host copies, **9.4 us** waiting for them, **5.7 us** to
submit the return copies, **0.2 us** of return-copy wait, and **6.5 us** of host
accumulation - against **15.4 us per copy measured on the device with events**.
So the earlier "~2 us of transfer" estimate was wrong by 8x, the copies (30.8 us
for the pair) now overlap the host work (26.4 us) rather than sitting beside it,
and **copy time, not host wait, is the binding term**. Each staged byte crosses
PCIe twice, so peer DMA would halve it, and peer DMA is unavailable on this host.

Two consequences for the plan. First, a device-signalled protocol now has a
ceiling: it can remove the 9.4 us of exposed wait, so ~33 us per reduction is the
floor for that work. Second, **1.3x is not reachable through transport work on
this host** - it would need ~24 us per reduction, below the measured 30.8 us cost
of the two copies alone. The 1.04-1.17x qualified win the design accepts is what
this transport delivers, and the remaining levers are the exposed reduction count
and the fixed-cost share, not the transport.

A first measurement of the batched structure read 2.2x rather than 1.67x: the
serial baseline was calling a wait-all-ranks helper from inside a per-rank loop,
so it waited twice per rank. Both protocols are now measured in one session, and
the corrected serial figure (71.7 us) reproduces the previously retained 71.1 us,
which is what identified the bug.

## Changes

- `scripts/tp_collective_bench.py` - `_measure_staged_exchange_chain` takes a
  `protocol` (`serial` | `batched`); the batched form double-buffers the staging
  slots, submits both ranks before awaiting either, and defers the return-copy
  waits to a single drain at the end of the chain; phase counters now separate
  submission from exposed wait per direction; a `device_probe` measures the copy
  itself with events, because the host counters cannot; the serial path waits only
  the rank it just submitted to. New `staged_exchange_batched` mode is in the
  default set, with the serial one retained as the measured baseline.
- `scripts/tp_break_even.py` - `--dependent-chain-mode` accepts the batched mode.
- `tests/test_unit_scripts_tp_collective_bench.py` - the shadow runtime counts
  stream synchronizations, and a new test pins the structure: the batched protocol
  performs exactly two waits per step plus one drain per chain, which is
  `2 * steps - 2 * chains` fewer than the serial protocol.
