# V5's boundary hypothesis is refuted; the divergence is a function of bulk width

## Summary

V5 asked for prompt lengths 511/512/513 and 1023/1024/1025 to test "window
and chunk boundaries", comparing chunked prefill against tokenwise execution
and an independent oracle.

Built the missing comparator, ran every named length, and the boundary
hypothesis **does not survive the measurement**. What the data shows instead
is that the disagreement between the two paths is a **pure function of the
bulk prefill width**, invariant to prompt length, sliding window, and split
threshold.

Two results, both measured:

1. **The named boundaries do nothing.** `kl_max` is *bit-identical* across
   all six prompt lengths for a given width, and top-1 flip counts are
   constant. 511/512/513 are indistinguishable from 1023/1024/1025 and from
   1537.
2. **Bulk width is everything.** A single incomplete block diverges
   badly and deterministically; widths spanning at least one full block plus a
   tail agree within the production thresholds.

## Changes

- **New `scripts/gemma4_boundary_compare.py`** (~300 lines): a two-subcommand
  comparator. `run` loads the artifact once and captures every
  `(length, prefill)` arm, then judges each non-zero width against the
  tokenwise arm; `compare` re-analyses cached `.npz` with no GPU. It imports
  the campaign gate's `capture_chain`, `evaluate`, `row_kl_divergence`,
  `route_summary`, `observe_decode_routes` and `save_capture`/`load_capture`
  so the numerics and thresholds are the gate's own, not a re-derivation.
- **No engine or kernel source touched.** This is measurement only.
- `docs/campaigns/GEMMA4-26B-A4B-PUNCHLIST.md`: V5's status carries the full
  result and states that its prompt-length premise is refuted.

## Why a new script was needed

The campaign `gate` subcommand validates that both arms share one chain
geometry and refuses to compare arms whose `--prefill` differs, because their
row counts differ. That refusal is correct for its own job and is exactly the
gap `scripts/gemma4_boundary_compare.py` fills. It imports the gate's own
`capture_chain`, `evaluate`, `row_kl_divergence` and `observe_decode_routes`,
so the KL arithmetic, nearest-rank percentiles and thresholds are the code
that gates promotion; the script contributes **alignment only**.

Alignment rule from `capture_chain`'s contract: row `t` of an arm taken at
prefill `P` is the distribution after consuming `prompt_ids[P + t]`. Two arms
match at absolute position `s` as `A[s - P_a]` against `B[s - P_b]`, over
`s in [max(P_a, P_b), len(ids) - 2]`.

The script loads the 17 GB artifact **once** and reuses the runner for every
arm (`capture_chain` resets the cache itself). Arms are cached as individual
`.npz` so re-analysis needs no GPU.

## Validation

### The determinism control

Before trusting any cross-path number, the same arm was captured twice in a
separate directory. **The two files are bit-identical.**

So the engine is fully reproducible run-to-run for a fixed configuration, and
every divergence below is real rather than noise. The gate's docstring states
this as its own smoke — *"A capture run twice on the same tree must gate at
KL == 0"* — and it holds.

## Measurement: the named boundaries do nothing

Six prompt lengths, widths 0/64/128/256/512/1024 (512 and 1024 only where
`prefill < prompt - 1` allows). Each non-zero width is judged against the
tokenwise arm at matched positions with the gate's `evaluate`.

| bulk width | `kl_max` across **all** lengths | top-1 flips | `kl_mean` range | arms |
|---|---|---|---|---|
| 64 | **1.7444816155494507** (every one) | **12** (every one) | 8.92e-03 .. 2.94e-02 | 6 |
| 128 | **3.5428931232712273** (every one) | **18** (every one) | 1.47e-02 .. 5.41e-02 | 6 |
| 256 | **1.7446299083839871** (every one) | **5** (every one) | 5.27e-03 .. 2.58e-02 | 6 |
| 512 | 0.15926513474608106 | 0 | 2.56e-04 .. 5.09e-04 | 4 |
| 1024 | 0.0010156537817620243 | 0 | 6.50e-06 | 1 |

`kl_max` and flip count are **identical across every prompt length** for a
given width. `kl_mean` moves only because longer chains add agreeing rows and
dilute the average.

Consequences:

- **The 512 sliding window is not implicated.** `sliding_window: 512` comes
  from `hipengine/models/maple.py`, and at L=513 no scored row exceeds 512
  keys. If the window were the cause, 511/512/513 would differ from
  1023/1024/1025. They do not.
- **The 1024 decode split is not implicated either.** It *does* engage from
  L=1024 onward (`selections [1, 2]`, `split_keys [1024, L-1]`, 30780 split
  launches at L=1537) and the divergence pattern is unchanged.
- So V5's premise — that these lengths are where behaviour changes — is
  **refuted by measurement**, and the row's premise should be rewritten
  around bulk width rather than prompt length.

## Measurement: production-shaped widths pass

Production prefill is one `forward(N)`: full `DEFAULT_PREFILL_BLOCK` (512)
blocks plus a partial tail. Tested at L=1537:

| bulk width | shape | `kl_mean` | `kl_max` | flips | verdict |
|---|---|---|---|---|---|
| 64 | partial only | 8.917e-03 | 1.744 | 12 | **FAIL** |
| 128 | partial only | 1.470e-02 | 3.543 | 18 | **FAIL** |
| 256 | partial only | 5.270e-03 | 1.745 | 5 | **FAIL** |
| 512 | exactly one full block | 2.562e-04 | 0.1593 | 0 | fail (max only) |
| 576 | full + 64 tail | 2.170e-05 | 7.970e-03 | 0 | **PASS** |
| 640 | full + 128 tail | 8.420e-05 | 3.048e-02 | 0 | **PASS** |
| 768 | full + 256 tail | 6.775e-06 | 7.769e-04 | 0 | **PASS** |
| 1024 | two full blocks | 6.502e-06 | 1.016e-03 | 0 | **PASS** |

Thresholds from `docs/EXECUTION-PROFILES.md`: mean 1e-3, p95 5e-3, p99 2e-2,
max 5e-2, top-1 99%.

**Every production-shaped width passes with top-1 = 1.0.** The failing
configurations are all a *single incomplete block* — a shape production only
reaches for a prompt shorter than one 512-token block.

Note the non-monotonicity that keeps this honest: exactly 512 (one full
block, zero flips) still misses on a single row at `kl_max` 0.159, while 576
(one block plus 64) is clean at 7.97e-03. Width alone is not a smooth
predictor; it separates "partial only" from "full block present", and the
512-exact case is its own oddity.

## What this does and does not establish

**Establishes:** the two paths are bit-reproducible individually; they
disagree with each other deterministically; the disagreement is independent of
prompt length, sliding window and split threshold; it is governed by bulk
width; production-shaped widths agree within the production contract.

**Does not establish:** which arm is correct. Both are hipEngine arms, so a
shared wrong mask would be invisible here — V5's own Why column says so. The
tokenwise arm is the mathematically-defined sequence, which makes it the
natural reference, but that is an argument, not evidence. **Resolving this is
V2's job** (an independent oracle), and V5's oracle leg stays open until V2
exists. No correctness claim about the shipped path is made here.

**Also not established:** root cause. `Gemma4Runner`'s docstring says *"a
decode step is a prefill of one token"*, so both paths share code, but they
differ in launch geometry (256 queries vs 1), and the divergence appears
immediately after a partial block and not after a full one. Localising that
is follow-up work.

## Reproducing

```
scripts/gemma4_boundary_compare.py run --lengths 511 512 513 1023 1024 1025 1537 \
    --prefills 0 64 128 256 512 1024
scripts/gemma4_boundary_compare.py compare --dir ~/.cache/hipengine/tmp/v5   # no GPU
```

33 arm captures under `~/.cache/hipengine/tmp/v5/`, report at
`v5_report.json`. A repeat capture to a scratch directory is the determinism
control. Runtime was minutes, not hours: model load 4.8 s, ~22 ms per scored
row.

## Next

- **V2** (independent oracle) is now the binding dependency for both V5's
  oracle leg and for saying which path is right.
- V5's punchlist row should be rewritten around **bulk width**, not prompt
  length, since the length axis was measured and showed nothing.
- The single-partial-block divergence deserves a root-cause look; it is the
  only failing shape and production reaches it only below 512 tokens.
