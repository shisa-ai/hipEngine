# The diffusion head's forward() has ~930 us/call unexplained by any kernel I can measure

## Summary

`VibevoiceTTSDiffusionHeadGPU.forward()` measures **2069 us/call** (20 calls per
frame), but every kernel it issues, measured individually, sums to only **~1138
us/step**. The **~930 us/call gap** is 43% of `forward()` and roughly **0.45 s of the
1.298 s diffusion stage (~11% of warm synthesis)**. This iteration eliminated the
remaining candidate explanations -- the last unmeasured kernel, dependency
serialization between the 42 dependent kernels, launch configuration, and cache
artifacts -- and none of them accounts for it. No code change; the gap is recorded as
the largest unexplained quantity in the pipeline, with `rocprofv3` named as the
decisive next step.

## Changes

No code change. One immutable worklog entry.

## Validation

### The last unmeasured kernel is normal

`silu_mul_separate_out_bf16` (4 calls/step at the head's real shape,
`rows=2, features=4608` where `ffn_dim = hidden 1536 * head_ffn_ratio 3.0`):

```
silu_mul_separate_out_bf16 (2, 4608) : 10.67 us/call  -> 42.7 us/step
```

Ordinary. Not an outlier, so it does not explain the gap.

### Dependency serialization is not the cause

The 42 kernels in a step are dependent (each GEMV consumes the previous elementwise
output), so I tested whether chaining adds a stall beyond the kernel's own cost, by
running the 22-call GEMV sequence with and without an intervening dependent
`vv_diff_silu_bf16` on the GEMV output:

```
22 GEMVs alone                   :  895.8 us/step
22 GEMVs + 22 dependent silu ops : 1080.2 us/step   (delta +184.4 us for 22 silu)
implied per-silu cost in-chain   :    8.38 us  (isolated: 10.75 us)
```

The in-chain cost is *lower* than the isolated cost, so there is no dependency-stall
penalty to recover. This also refutes the hypothesis that the gap is serialization
overhead.

### The component sum against forward()

```
GEMV (22 calls)             896 us
vv_diff_silu_bf16 x6         64 us
vv_diff_rmsnorm_modulate x5  90 us
vv_diff_gated_residual x4    36 us
vv_diff_add_bf16 x1          10 us
silu_mul_separate x4         43 us
                            -------
sum                       ~1138 us/step
forward() measured         2069 us/call
gap                        ~ 931 us
```

The per-step kernel profile from `20260915T203624.733692Z` lists exactly these six
kernel names and 42 launches, so the call set is complete -- there is no unprofiled
kernel hiding in the step.

### What has been eliminated

- **Elementwise kernel cost** (`20260915T204837.504087Z`): 8.92-17.93 us each, normal.
- **D2H readback**: 9.90 us, not a bottleneck.
- **Launch configuration**: ordinary `(n + 255) / 256` blocks of 256.
- **L2 artifact**: real-sequence GEMVs are *faster* than same-shape repetition, and
  land at ~204 GB/s (~80% of peak), so the isolated figures are not cache-inflated.
- **Dependency serialization**: measured, absent (above).
- **`silu_mul_separate_out_bf16`**: 10.67 us, normal (above).

Note the GEMV figure moved between runs (1205.9 us in
`20260915T204837.504087Z`, 895.8 us here) on identical shapes, so there is real
run-to-run variance in this measurement and part of the "gap" may be that variance
rather than a fixed unexplained cost. That is itself a reason to stop inferring and
measure the device directly.

## Next

**`rocprofv3 --kernel-trace` on a single `forward()` call is the decisive step** and
should be the first action of the next iteration. It returns per-kernel device
durations, which settles the gap in one measurement instead of by subtraction: either
the 42 kernels really do occupy ~2.0 ms of device time (in which case my isolated
per-kernel figures are optimistic and the cause is per-kernel overhead I am not
reproducing), or they occupy ~1.1 ms (in which case ~0.9 ms is host-side or
gap-time inside `forward()` and the target is dispatch, not kernels).

Caveat for whoever runs it: `forward()` contains a synchronous D2H, and this tree has
a documented JIT-cache gotcha, so prebuild the `.so` outside the profiler and run with
`require_cached` rather than letting the profiled process spawn `hipcc`.

Do not act on the ~930 us figure until that trace exists -- it is a subtraction
residue, not a measured quantity, and this session has already produced two
subtraction-based inferences that direct measurement refuted (the 52 us elementwise
figure and the L2-artifact concern).
