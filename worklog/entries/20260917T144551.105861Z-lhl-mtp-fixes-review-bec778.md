### P1: AR attribution records preparation, not committed output

`hipengine/generation/qwen35_gguf_mtp2.py:2151` calls
`record_autoregressive_step` inside `prepare_k0`, before AR execution/emission.
`hipengine/generation/engine_loop.py:2356-2372` retries the speculative subset of
a mixed desired-AR/MTP work item when the full plan returns no speculative
result. Both attempts can select AR and call preparation. Only one AR decode
then emits output.

CPU reproduction with the existing `_SwitchableQualificationRunner` fixture,
`enabled=False`, one speculative-intent row and one plain-AR row:

```text
tick 2: prepared plans [(0, 1), (0,)]
        AR calls [(0, 1)]
        token events [(0, 9000), (1, 9010)]
tick 3: prepared plans [(0, 1), (0,)]
        AR calls [(0, 1)]
        token events [(0, 9001), (1, 9011)]
```

This counts two preparations for one token on the speculative-intent row.
Exceptions before AR commit can also leave a preparation counted as output.
Move output attribution to successful token commit, retaining the selected
reason as pending metadata. Add mixed-intent retry and failed/cancelled decode
coverage; assertions about preparation alone do not establish emitted counts.

### P1: Screening ignores additional failed safety predicates

`hipengine/speculative/serving.py:639` retains only the first failed reason for
the best-matching evidence row. `_mtp_screening_static_eligibility` in
`hipengine/server/api.py:13306` authorizes screening based on that one reason,
without independently checking the key's safety fields.

CPU reproduction with the real Qwen model evidence, verified artifact,
gfx1151/BF16/capacity4/C1, candidate budget 4, greedy sampling and
`memory_fit=False`:

```text
resolver reason: candidate_budget_not_qualified
plan.key.memory_fit: False
screening helper returns eligible payload: True
```

This contradicts the documented rule that memory-fit rejection always stays
closed. It demonstrates a helper/contract defect, not an observed unsafe GPU
launch: normal server call sites currently pass `memory_fit=True`, and later
resource checks may still prevent execution. Fix it before generalizing
screening. Evaluate content verification, memory fit and supported sampling
independently of the summary reason; carry all failed axes or a typed
screenability decision. Test simultaneous failures, not only one-axis cases.
Missing benchmark evidence may be bypassed for experiments; invalid ownership,
unsupported storage/sampling implementations and insufficient memory may not.

### P2: Reconciliation is arithmetic consistency, not attribution verification

`hipengine/server/api.py:15808-15821` derives AR as completion minus MTP and
sets `reconciled` from the nonnegative remainder. The API gate validates that
same identity. A synthetic response with completion=5, MTP=3, and
`ar_output_tokens_in_cycles=99` reports AR=2, `reconciled=True`, and passes
`scripts/gguf_mtp_api_gate.py::_mtp_output_accounting_contract`.

Deriving the remainder is useful for display, but cannot detect missing or
duplicated attribution. At minimum check independently committed AR counts
against the remainder and verify cycle/depth/count consistency. For stronger
proof, record committed output spans with mode, reason and absolute target
position; validate a non-overlapping cover of the emitted IDs. Keep the prefill
root explicit. Separate event counts (one prompt refusal or recovery event)
from token counts: the 3530-token artifact has one prompt-refusal event for
128 AR outputs. Comparing AR/MTP generated IDs establishes sequence agreement,
not the provenance of each output token.

### Work-in-progress ShareGPT harness: good routing probe, incomplete evaluator

The inspected draft has several limitations to fix before using it as the
quality/performance acceptance result:

- Default prompt filtering is <=1024 raw tokens and prompt+expected-output is
  <=2048. Keep this as a pinned vLLM-compatible lane, but add a separately
  labeled broader-context ShareGPT lane. Otherwise prompts at 4K/8K and beyond
  are excluded before reaching the server. Record post-template prompt lengths,
  dataset revision/hash, seed and source IDs. Fixed-output runs are useful
  diagnostics, not the natural output-length distribution.
- `_rate_windows` selects 16 timeline entries, not 16 committed tokens. A CPU
  probe with four-token chunks produces 64-token windows. `_cliff` uses the
  same parameter as a token distance, so a supposedly pre-boundary window can
  cross the boundary. Use actual token endpoints, reject straddling windows,
  distinguish per-cycle/chunk latency from per-token latency, and report
  absolute context positions as well as output indices.
- `decode_tokens_per_second` is completion tokens divided by whole-load wall
  time, which includes prefill/queueing. Label it end-to-end output throughput;
  compute decode-window throughput separately.
- The draft retains only text length, not full outputs/IDs or a quality score,
  and measures only one server arm per invocation. Persist outputs and identity
  and pair with an explicit no-MTP baseline. A ShareGPT assistant answer is a
  length reference, not an exact-answer oracle.
- Requests do not pin thinking behavior and TTFT only observes `delta.content`.
  With reasoning output, that is time to first answer content, not necessarily
  time to first generated token. Pin the intended thinking/sampling protocol
  for matched runs or measure and label both channels.

These are observations of an actively edited draft; coordinate with its owner
rather than modifying or staging it from this review.
