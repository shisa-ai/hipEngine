# V2: production keep-mask bound to the HF-validated reference

## Summary

Punchlist V2 read: *"Build an independent oracle for the windowed path. The
gate compares two hipEngine arms against a captured baseline, so it cannot
detect a wrong mask that both arms share."* Its options were to score prefill
logits against llama.cpp's, or to add a naive CPU reference for windowed
attention.

The naive reference already exists and is independently validated:
`hipengine/kernels/cpu_reference/gemma4.py` implements `gemma4_attention_mask`
and `gemma4_text_forward`, gated against the HuggingFace `Gemma4ForCausalLM`
oracle in `tests/test_unit_gemma4_cpu_reference.py`. The gap was narrower than
the row stated, and in a different place:

- **Kernel to naive reference already existed** for a causal mask
  (`test_attention_prefill_f32_matches_the_reference`) and for an inline
  sliding-window mask (`test_attention_prefill_applies_the_mask_it_is_given`),
  both at `atol=rtol=1e-5`. So the kernel was covered — but the mask in those
  tests was built *by the test*, not by production.
- **Nothing checked `_keep_mask`** — the single function in
  `hipengine/runtime/gemma4.py` that builds the keep-mask for every block of
  every arm. That is literally the mask both arms share: chunked and tokenwise
  arms call the same builder, and the campaign gate compares their logits, so a
  wrong builder is invisible to it.

The two derivations are written differently — production accumulates
`(queries - key_positions) < W` while the reference intersects `key > query - W`
— so agreeing is a real comparison rather than a shared expression.

## Changes

- `tests/test_unit_gemma4_keep_mask_reference.py` (new, 235 tests): binds
  `_keep_mask` to `gemma4_attention_mask` across 9 window widths
  (None, 1, 2, 3, 7, 8, 16, 512, 1024) x 5 block offsets (0, 1, 4, 127, 511) x
  5 block widths (1, 2, 3, 8, 17), plus targeted cases: the exclusive window
  bound asserted at `q-k == W` versus `q-k == W-1` (an interior point cannot
  separate `< W` from `<= W`), the vacuous `keys <= window` region as pure
  causality, and the decode-shape block that must not mask past its own write
  range.
- `tests/test_unit_gemma4_gpu_kernels.py`: added
  `test_attention_prefill_matches_the_reference_through_the_production_mask`,
  the end-to-end seam — production `_keep_mask` output fed straight into the
  HIP kernel and compared against the naive numpy reference, over four
  geometries including `start=10, rows=1`, the decode/paged shape where the key
  range runs ahead of the query rows and which the causal-only tests never
  construct.

Together these close a composition gap: HF-validated mask rule to production
mask builder to GPU kernel to numpy reference. Every link is now bound to the
one beside it, so drift anywhere breaks a test instead of propagating through
both arms identically.

First run of the end-to-end test returned all-NaN for `start=10, rows=1`. That
was the test's own bug: `gemma4_attention_prefill_f32` takes
`keys: int | None = None` and it was never passed, so the kernel ran with
`keys=1` against an 11-column mask. Passing `keys=` fixed it; the kernel was
correct.
