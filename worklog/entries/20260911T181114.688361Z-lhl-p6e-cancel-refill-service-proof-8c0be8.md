# P6e service proof: cancel during real prefill, refill, survivors byte-identical

## Summary

P6e's second half, and the one `gguf_live_server_bench.py` could not measure: it
has no cancel path. The in-process half (previous unit) proved the yield mechanism
on GPU; this half proves the *service* consequence - a long prompt cancelled
mid-prefill must not damage the request being served alongside it, and must not
leak its own state.

All five gates pass on W7900 / gfx1100, with every limit declared before measuring:

| Gate | Result |
| --- | --- |
| Cancellation reached the backend | PASS - counter 0 -> 1 |
| Survivors exact | PASS - refill sha256 `118cf547...` == reference |
| Bounded acknowledgement | PASS - 825.8 ms (limit 3000 ms) |
| Bounded decode gap | PASS - refill max 39.566 ms vs reference max 42.430 ms (limit 2.5x) |
| Cleanup | PASS - scheduler drained, prefill owner bytes back to baseline |

The load-bearing evidence is `bytes_before_close: 0`. The probe held the
connection open 600 ms after admission and received **nothing**, so no token had
been produced and the prefill was still running when the socket closed. That is
what makes this a cancel-during-prefill proof rather than a cancel-after-prefill
one. The long prompt's prefill ran three work items before the cancel landed.

## Changes

- `scripts/gguf_p6e_cancel_refill_proof.py` (new). Runs the real FastAPI app under
  `uvicorn` in a thread of the same process, so the app is reachable over a real
  socket while the scheduler stays observable. Streams a reference completion,
  cancels a long prefill through a raw TCP close, refills, and evaluates the five
  gates. `evaluate_gates` is a pure function so every failure path is testable.
  Exits non-zero when a gate fails.
- `tests/test_gguf_p6e_cancel_refill_proof.py` (new, 14 tests). Drives each gate
  through its failure path with synthetic measurements.
- `benchmarks/results/2026-09-11-w7900-p6e-cancel-refill-service-proof.json`,
  `benchmarks/CHANGELOG.md`, `benchmarks/HARNESSES.md`.

## Why a raw socket

`TestClient` cannot express this test. During a long prefill the SSE stream
carries no bytes - there is no keepalive and no prefill event - so a reader
blocked in `iter_lines()` never observes an abort request, and exiting the
`client.stream` context only takes effect once the reader returns. A genuine
mid-prefill disconnect needs a connection that can be closed from outside the
reader, which is why the probe opens a raw socket and closes it.

The server side needed no change. It relies on Starlette's `StreamingResponse`
cancelling its body iterator on disconnect, and `account_active_stream_cancellation`
records that through `_record_openai_error`, which increments
`hipengine_request_cancelled_total` for `code == "cancelled"`. I verified that
path rather than assuming it, because the counter staying at zero was initially
indistinguishable from a broken cancel.

## Two harness bugs, neither a server defect

Worth recording because the second one produced a convincing false negative:

1. **The SSE stream carries `choices[0].text`, not `token_ids`.** My first
   extraction found nothing, so the reference run looked empty. Survivor truth is
   now the completion text and its sha256, which is also what the live bench uses
   for cross-arm content equality.
2. **The harness had inherited the live bench's KV-pool sizing**, which is tuned
   for 512-token contexts (`max_rows * 3` pages). A 3072-row prompt needs far
   more, so the long request was **rejected before it ever reached a cancellable
   prefill**. That presented exactly as a failing cancellation gate: admission
   looked fine, the request produced a response, and the cancellation counter
   never moved. The diagnostic that separated the two was
   `hipengine_resident_work_prefill_total` - zero prefill work, so there had been
   nothing to cancel - plus `hipengine_request_failed_total` moving by one. I did
   not report a server defect, because the evidence said the request never got
   that far. Sizing the pool for the long prompt made all five gates pass with no
   server change.

## Validation

- `uv run pytest tests/test_gguf_p6e_cancel_refill_proof.py` - 14 passed.
- GPU run, cache-only (`HIPENGINE_REQUIRE_CACHED_BUILD=1`, pinned compiler version),
  3072-row long prompt vs 512-row short prompt, 24 decode tokens, 600 ms hold,
  `max_active_requests` 2. Artifact values above.

Honest limits:

- The reference and refill are both 48 characters and 23 inter-token gaps, so the
  survivor comparison covers a short completion. It is exact, but it is not a long
  generation and it does not exercise a multi-token cancellation race.
- Cancellation is verified through the metrics counter and the drain, not by
  observing the cancelled request's internals: I do not assert that its suspended
  prefill buffers were released at a specific instant, only that the scheduler
  drained and owner bytes returned to baseline afterwards.
- Only one cancel timing (600 ms after admission), one long-prompt shape, and one
  layer budget were run. The gates are declared constants, not swept.
- `performance_claim` is false and no scoreboard row changed: this is a
  control-and-liveness proof, not a throughput result.
