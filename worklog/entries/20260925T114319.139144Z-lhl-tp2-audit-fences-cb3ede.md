# Refresh two recorded audit fences that later work invalidated

## Summary

`tests/test_unit_core_device_ownership.py` failed twice on `tp2` for reasons
unrelated to the head-shard work: both failures are recorded audit numbers that
later commits invalidated, and both fences exist precisely so the growth is
looked at rather than absorbed.

## Changes

- `test_distributed_package_binds_devices_through_one_mechanism` asserted the set
  of modules binding a rank device is exactly `{context.py, rccl.py}`. Four more
  modules bind their own rank's device through the same primitive:
  `shard_exec.py` (rank-local weight allocation, `eeb5734de`), `staged.py`
  (`5fcc34df6`), `shard_group.py` (`0dbe4e3f1`), and `tp2_generate.py`
  (`e18aebcbc`). The assertion now lists those six with the reason each one
  binds, and keeps the part that carries the real invariant: no module may call
  `hipSetDevice(` or `set_device(`.
- `test_kernel_launch_surface_stays_visible_to_the_audit` recorded Packet 1's
  launch surface (51 modules, 31 `_check_launch` definitions, 452 calls). The
  tree now has 53, 32, and 461. The delta is
  `hip_gfx1100/vibevoice/{codec_ops,qwen2_ops}.py`, which launch on the ambient
  device like every other wrapper and are not reachable from
  `hipengine/distributed/` or the rank-bound runner, so the added surface needs
  no device binding. The numbers are updated with that reason attached.

## Validation

- `uv run --with pytest python -m pytest tests/test_unit_core_device_ownership.py
  -q` - 28 passed. Both tests fail on `6ea51bf61` without this change.
- The added-module claim is measured, not read: the launch-module set was
  recomputed from the tree at the fence's own commit `aa2cb6288` and diffed
  against the current tree (51 -> 53, added = the two vibevoice files, removed =
  none), and the `_check_launch` counts were recomputed the same way.
