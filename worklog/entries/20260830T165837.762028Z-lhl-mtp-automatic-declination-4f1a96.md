# Automatic MTP declination is evidence-ledger coverage, not a safety test

## Summary

On the physical C1-C8 matrix `--mtp-request-mode automatic` engages in **0/80 cells**
with 0 accepted draft
tokens, declined as `artifact_not_qualified` (C1), `resident_capacity_not_qualified` (C2) and
`physical_group_not_qualified` (C3-C8). Reading the producer: `_evidence_checks`
(`hipengine/speculative/serving.py:503-537`) compares the live configuration key field-
by-field against a
pre-qualified `SpeculativeMTPServingEvidence` row - artifact sha256 and size, backend,
target arch, weight
quant, execution profile and its manifest sha, kv_storage, kv_layout, `realized_group_rows`,
`resident_capacity`, `candidate_budget` - and any single miss declines. So these reasons are
**promotion-ledger coverage gaps**, not runtime safety constraints.

31.455 vs 21.999 at C1
(+43%) and 39.820 vs 31.916 at C2 (+25%). At those widths what withholds the gain is qualification
bookkeeping, not kernels. From C5 the ordering flips - K3 47.960 against AR 61.881 - so mechanically
qualifying C3-C8 would regress the product, and those rows should stay unqualified until
the accept-window
work (#17) lands.
