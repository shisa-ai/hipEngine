# Gate the worklog kind on actionable markers only

## Summary

`audit.py check` gated every untriaged `worklog` row. That population grows with
ordinary work — 1,078 rows at this commit, with roughly 27 rows a day crossing
the age window — so the ceiling measured the rate of work rather than a backlog,
and the gate sat red on rows nobody had decided (one fresh `checkpoint` entry was
enough to fail it by one). A gate that is red by default is a gate nobody reads,
and the only ways out of it are triaging in-flight work or raising the number
`AGENTS.md` forbids raising.

The budget now carries a per-kind `select` policy. `worklog` gates on
`evidence.status` in `{blocked, handoff}` — the two markers that mean a worker
stopped and someone must act. The other 990 untriaged rows stay untriaged, stay
listed by `open worklog`, and stay counted in the state table; they no longer set
the ceiling. Ceiling recorded at 88, down from 1,076.

This changes the gate, not the extractor. The `worklog` kind still reports every
entry that declared unfinished business, exactly as the observation-only design
in `20260920T213631.272038Z-pi-audit-worklog-ingestion-15d997.md` specifies; only
which of those rows count toward the ceiling moved.

## Changes

- `audit/hipaudit/report.py`: `gate_spec`, `in_gate`, and `open_counts` — one
  implementation of "which untriaged rows count", used by `check`, `status`,
  `refresh`, and `save_budget`. A spec matches row fields, `evidence.<name>` reads
  the row's evidence, a list of values means any of them, and a list of specs is
  ORed. `save_budget` now preserves `select` (a policy is not a count) and records
  the gated population.
- `audit/audit.py`: the gate, the `status` budget line, and the `refresh` todo
  list read the gated counts. `check` and `status` name the ungated queue
  explicitly, so visibility does not depend on the ceiling.
- `audit/budget.json`: `select.worklog = {evidence.status: [blocked, handoff]}`;
  ceiling re-recorded 1,076 -> 88 with `budget --lower-only`.
- `audit/README.md` and `audit/agents/triage.md`: the `select` schema, and what a
  red gate now means for the triage lane.
- `audit/tests/test_audit_core.py`: `GateSelect`, six tests — a narrow gate, a
  kind with no selector unchanged, ungated rows still open in the state table, an
  ORed spec list, the ratchet recording the gated count, and the policy surviving
  `save_budget`.
- `audit/inventory/`: regenerated with the new entry (worklog 1,077 -> 1,078
  rows; the new row is a `checkpoint` and lands in the ungated queue).

## Validation

  six new tests produced 5 errors and 1 failure against the unmodified tool.
- `python3 audit/audit.py budget --lower-only` — `worklog: 88`, with `select`
  intact in the payload.
- `python3 audit/audit.py check` — exit 0, printing `outside the gate (untriaged,

- `python3 audit/audit.py status` — budget line reports the gated count and names
  the ungated queue.
- `python3 scripts/docs/check_all.py` — passes.

## Next

  (73 `blocked`/`handoff` markers were created in the last 30 days), and each pass
  lowers the ceiling through `budget --lower-only`. A red gate now means the
  actionable backlog grew, which is worth stopping for.
- The 990 ungated rows are 845 in-flight `checkpoint` entries, 109 pre-cutoff
  `### Next` markers, and 36 entries whose `Next` names a dependency. They are a
  queue with no gate. If the project wants pressure there, that is a separate
  policy call — the `select` block can express it, including as an ORed list.
