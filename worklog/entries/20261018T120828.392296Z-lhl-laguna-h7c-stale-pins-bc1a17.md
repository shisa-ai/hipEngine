# Repair stale pinned-source assertions in the Laguna H7C test

## Summary

`tests/test_gpu_laguna_h7c_raw_q6_dpp_wave_reduction.py` failed three cases on
the campaign base commit `998b7b0a4`: the immutability guard compares pinned
source hashes and a declaration lookup, and both had drifted from the code they
guard. Neither failure reflects a change in the guarded arithmetic.

## Changes

- `_GENERIC_LAUNCH_WRAPPER_SHA256` re-pinned to the current
  `hipengine.kernels.hip_gfx1100.quant.gguf_k_gemv._launch`. The only difference
  from the previously pinned source is one `launch_census.record_launch(...)`
  telemetry call added between validation and the launch, verified by diffing
  the function against `125581729^`.
- `_declaration` now skips a forward declaration when a `;` precedes the first
  `{`, so the guard inspects the definition it asserts about. The kernel source
  gained a forward declaration for `h7c_reduce_wave_accumulators_dpp`, and the
  old helper returned the declaration plus the following template body, which
  made every step lookup fail with `substring not found`.

## Validation

- RED at base `998b7b0a4` in a separate worktree: the same three cases fail, so
  this is drift, not a regression from the current branch.
- `uv run pytest tests/test_gpu_laguna_h7c_raw_q6_dpp_wave_reduction.py` —
  22 passed.
- The guard still asserts what it was written for: the generic kernel body, the
  generic launcher declaration, the wrapper factory, `_validate` and the raw
  dispatch hash all still match their pins, and the reduction-step ordering,
  `__shfl_down`, `row_shl:1` and the DPP masks are still checked.
