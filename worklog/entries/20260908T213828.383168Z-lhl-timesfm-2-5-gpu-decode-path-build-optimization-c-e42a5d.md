# TimesFM 2.5 GPU decode path: build + optimization campaign

## Summary

Built the torch-free HIP GPU decode path for TimesFM 2.5 200M on the
Radeon 8060S (gfx1151) host and iteratively optimized it from a 1.096 s
FP32 baseline to 0.0986 s for batch=8 / context=8192 / horizon=512 — 11.1x
over the first working GPU implementation, 7.2x over the official torch
reference on the same GPU (0.707 s), and 93x over the NumPy CPU reference
(9.13 s). Correctness is gated two ways: an FP32 strict-parity path
(atol 5e-4 / rtol 1e-2 vs the committed torch oracle fixture) and an FP16
production path calibrated at max <= 2% / mean <= 0.5% of per-series
signal scale (measured: max 0.86%, mean 0.06%).

## Changes

- `hipengine/kernels/hip_gfx1100/timesfm/timesfm.hip/.py`: templated
  `<T>` kernels in `_f16`/`_f32` variants — rmsnorm (multiplicative scale,
  eps inside rsqrt), norm+add post-norm residual, bias/bias+swish/swish,
  add, RoPE (non-interleaved halves, precomputed timescale table),
  per-head RMSNorm, per-dim softplus query scaling, packed-QKV head-major
  k/v cache scatter, masked softmax (register-resident two-pass, -inf for
  masked keys, uniform 1/S for all-masked rows), head transpose, and the
  merged qkv-norm+scatter kernel with in-kernel RoPE.
- `hipengine/core/rocblas.py`: `gemm_ex_strided_batched_f16_f32acc`
  wrapper (FP16 storage, FP32 accumulate, element strides).
- `hipengine/runtime/timesfm_decode.py`: `TimesFMGPUDecoder` — packed-QKV
  GEMMs via rocBLAS `gemm_ex` (FP16/FP32-acc), batched-GEMM attention
  (QK^T + masked softmax + AV over head-major caches), merged
  RoPE+QK-norm+scatter, host-side vectorized patch running stats, AR-loop
  feedback, quantile head restricted to last-patch single-column batched
  GEMMs, AR steps skip the quantile head, zero-initialized KV caches.
- `scripts/timesfm_gpu_bench.py`: `--metric` (fixed workload timing) and
  `--check` (fp32 strict + fp16 production gates, NaN-hardened).
- `tests/test_timesfm_gpu_decode.py`: both gates as pytest with HIP /
  checkpoint / fixture skips.

## Optimization iterations (measured, b8/ctx8192/h512, best-of-N)

| Step | Seconds | Change |
| --- | ---: | --- |
| FP32 baseline (rocBLAS SGEMM + naive kernels) | 1.096 | correctness-first build |
| FP16 storage / FP32-accum GEMMs | 0.492 | 28.5 vs 2.1 TF/s on gfx1152 matrix cores |
| Batched-GEMM attention | 0.368 | QK/AV onto matrix cores |
| Block-per-row cooperative reductions | 0.174 | row-serial kernels were latency-bound |
| Host-path (vectorized stats, last-patch D2H) | 0.141 | ~25 ms of Python loop removed |
| RoPE timescale table + 128-thread head blocks | 0.122 | powf per element dropped |
| Quantile head work reduction | 0.115 | 53 -> 0.4 GFLOP |
| Merged qkv norm+scatter kernel | 0.104 | halved packed-QKV re-reads |
| RoPE folded into merged kernel | 0.099 | one fewer full q/k pass |

rocprof attribution at 0.174 s: ~57 ms GEMMs (near matrix-core limits at
these shapes), ~15 ms masked softmax (bandwidth-bound at ~209 GB/s ≈ peak),
rest fused kernels + ~25 ms host. A fusion experiment (rope+norm+scatter in
one kernel with 256-float register arrays) measured SLOWER (110.7 vs
90.1 ms per 3 decodes) and was reverted; the final merged design avoids
register spills entirely.

## Correctness campaign (critical)

The initial `--check` guard compared thresholds with `nan > 0.02`-style
checks that silently pass on NaN. After adding a pytest that asserts
properly, three latent fp16-path bugs surfaced (all present since the
batched-GEMM attention change, hidden on fresh zeroed pages):

1. All-masked softmax rows (front-padded queries) produced 0*inf=NaN;
   now uniform 1/S as the reference softmax over all-masked scores.
2. The register-resident softmax stored 0 for masked keys, so they leaked
   exp(0 - row_max) weight; masked vals are now -INFINITY.
3. KV caches were malloc'd uninitialized; the full-cache batched GEMMs
   read not-yet-written AR slots and 0 * dirty-page garbage = NaN after
   any prior large allocation (e.g. an fp32 decode in-process). Caches
   are now zero-initialized at allocation.

The guard is NaN-hardened (fails on non-finite output). fp32 strict
parity passes in fresh processes and fp32-then-fp16 sequences.

## Next

- Remaining bottleneck is GEMM-bound (~57 ms at ~60% of FP16 matrix-core
  peak); next class of work is a flash-attention-style fused causal kernel
  (~15 ms softmax + attention GEMM traffic) and rocBLAS solution tuning —
  both are new engineering efforts, not incremental tweaks.
- The naive `_f32` attention kernel remains as the strict-path fallback;
  if a strided-batched FP32 GEMM attention is wanted for strict-path
  speed, port the same layout changes.
- Benchmark protocol note: this host (Ryzen AI MAX+ 395 / Radeon 8060S,
  gfx1151) is an independent lane from the W7900 (gfx1100) scoreboard.
