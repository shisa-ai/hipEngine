# the 52.6 percent attention share is stale; on gfx1151 attention is about 14 percent of the token

## Summary

`20260929T213000` recorded attention at 24.03 ms, 52.6 percent of a decode step, and named the
one-warp-per-(token, head) rewrite as the lever. **That share does not survive measurement on the
target configuration.** The gfx1151 decode attention kernel costs about **5.6 ms per token** at the
campaign's real context, roughly **14 percent**, not 52.6.

**The rewrite would have targeted a minor term.**

## The measurement

`scripts/gemma4_attention_decode_bench.py`, gfx1151, 50 iterations, the artifact's own geometry
(25 sliding layers of 16 heads / 2 kv / dim 256, 5 full layers of 16 heads / 8 kv / dim 512):

| geometry | keys | us/launch | unique-KV | issued |
| --- | --- | --- | --- | --- |
| sliding | 1024 | 186.7 | 11.2 GB/s | 269.6 GB/s |
| sliding | 8192 | 1745.6 | 9.6 GB/s | 230.7 GB/s |
| full | 1024 | 190.0 | 88.3 GB/s | 529.9 GB/s |
| full | 8192 | 3884.8 | 34.5 GB/s | 207.3 GB/s |

Per token that is `25 x sliding + 5 x full`:

- **at 1024 keys: 25(186.7) + 5(190.0) = 5.62 ms**
- at 8192 keys: 25(1745.6) + 5(3884.8) = 63.1 ms -- impossible, because the token takes 35.7 ms

The 8192 row is the tell: **the 25 sliding layers have a window**, so they never attend 8192 keys,
and the `--keys` flag does not model that. Only the 5 full layers scale with context, which is why
a naive per-token sum overshoots the wall clock by 1.8x.

**The campaign's real context is about 640 keys, not 8192.** The artifact records
`context = 8192` as the *allocated* length, but the workload is prompt 512 + output 128, so
attention never sees more than 640 positions. At 640 the full layers interpolate to about 119 us
each, giving roughly **4.3 ms per token**.

## Changes

None. This entry records a measurement that contradicts a prior recorded number.

## Validation

```
.venv/bin/python scripts/gemma4_attention_decode_bench.py --keys 1024 8192 --iters 50   # exit 0
```

## Why the inherited number was wrong

Three differences, all in the same direction:

1. **Different GPU.** The profile is gfx1100 (RX 7900 XTX); this is gfx1151. At 1024 keys the same
   geometry costs 5.62 ms here against the profile's 24.03 ms -- a 4.3x difference.
2. **Different context.** The profile measured at 1024 prompt; the campaign reaches about 640.
3. **A profiler that inflates absolute durations by about 24 percent**, which the profile itself
   says to read only for shares and rankings.

**The share was the one field that did not transfer, and it was the field the decision rested on.**

## The corrected decode map

| term | ms/token | share | source |
| --- | --- | --- | --- |
| host floor (no launches issued) | 9.66 | 27% | `20260929T213000`, measured |
| MoE GEMV | 6.22 | 17% | 2026-09-25 profile, gfx1100 |
| **attention** | **~4.3-5.6** | **~12-16%** | measured here |
| dense projection | 3.88 | 11% | 2026-09-25 profile |
| norms | 1.35 | 4% | 2026-09-25 profile |

Those sum to about 26 ms of a 35.7 ms token, leaving roughly 10 ms unaccounted -- so the profile's
bucket split is not itself trustworthy for the smaller terms either.

## What is not claimed

- **The MoE and dense numbers are still the gfx1100 profile's**, for the same reason attention's
  was wrong. They are smaller terms and their error matters less, but they are not re-measured.
- **No per-kernel trace on gfx1151 was taken.** This is a direct kernel microbenchmark, not a
  profiled decomposition, so the ~14 percent share is derived from per-launch costs times layer
  counts rather than read off a trace.
- **The window size of the sliding layers was not confirmed from the artifact.** The conclusion
  that the 8192 sum is impossible holds regardless, since it exceeds the wall clock.

## Next

  does not require a kernel rewrite.
- **Re-derive the MoE and dense terms on gfx1151** before acting on them, for the same reason this
