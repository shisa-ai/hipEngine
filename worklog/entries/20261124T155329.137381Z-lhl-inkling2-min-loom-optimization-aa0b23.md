# Decode residency cost attributed to blocking download, not plan build

Corrects the attribution in the preceding entry (20261124T155205.146714Z-lhl-inkling2-min-loom-optimization-506c2f.md).

## Summary

A cProfile of the scalar-decode resident path (rows=1, fast profile, \u003e48 warm tokens) shows the
regressions are NOT in plan construction. Per 48 tokens: `_attention_plan` totals 0.105 s and
`_project_groups` overheads are unchanged versus baseline; the added cost is `stream_synchronize`
growing 0.693 s to 1.348 s and the single arena-wide `download()` at the end of
`project_attention_resident` (1.30 s cumulative across 4,608 calls, ~2 per visit). The resident path
issues the whole attention chain back-to-back and then blocks the host on one copy of the branch
output; the interleaved baseline path instead overlaps small host ops with device work and spreads
its synchronization. At rows=1 the GPU finishes each tiny kernel faster than the host can enqueue the
next one, so neither path is GPU-bound; the resident path simply serializes worse. The plan cache idea
recorded in the previous entry would not have fixed this and is off the table.

The verifier of record for the "resident slower at rows=1" call remains the 3-rep A/B: baseline
2.633/2.636/2.638 s vs patched 3.063/3.065/3.066 s per 48 tokens, token-identical.

## Next

Any future resident-decode attempt must overlap the branch-output download with host-side work for the
next visit (e.g. issue the download, then build the next visit's plan, then consume the buffer) rather
than block immediately — otherwise rows=1 residency cannot win. Also reconsider reducing kernel count
per visit; 35+ launches per visit at ~6-10 us launch overhead is the other floor on decode speed.
