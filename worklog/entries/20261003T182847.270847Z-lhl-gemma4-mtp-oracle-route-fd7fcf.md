# Gemma 4 MTP candidate oracle needs the llama.cpp-compatible MoE route

## Summary

`test_the_draft_chain_reproduces_llamacpps_candidates` failed at draft step 3:
the head's candidates were `[139, 623, 3729]` where llama.cpp's are
`[139, 3729, 623]`. It was the only failing node in the file (229 passed, 14
skipped, 4 xfailed).

The oracle is llama.cpp's own `--verbose` MTP log, so the test implicitly
requires the backbone to reproduce llama.cpp's arithmetic. The exact/default
route does not; the split-projection MMQ route does, bit-for-bit. The test now
pins that route and says why.

The decisive measurement is a `git bisect` of the runtime against a fixed
self-contained diagnostic (load backbone, sample the first token, prime the
head, print the four draft candidate lists):

- Last good commit `e57a5189b`, first bad commit `eb1d1a4fd`
  ("fix: restore Gemma default continuation correctness").
- `e57a5189b` default: `[139, 3729, 623]`, `v623=14.97130 v3729=15.10509`.
- HEAD default: `[139, 623, 3729]`, `v623=15.24178 v3729=14.93324`.
- HEAD with `HIPENGINE_GEMMA4_MOE_PREFILL=mmq`: `[139, 3729, 623]`,
  `v623=14.97130 v3729=15.10509` -- identical to `e57a5189b`.

Isolating the route: `gemma4_moe_expert_route_counts()` shows the gate/up owner
is identical between `e57a5189b` and HEAD (`selected_gemv: 29` +
`gate_up_iu8: 1`); only the **expert-down** owner differs. Restoring just the
pre-repair tiles-only override (`use_mmq = True`, gate/up untouched) reproduces
`[139, 3729, 623]` at `v623=14.88330 v3729=15.06295`, i.e. the WMMA down
(`selected_grouped_wmma_prefill_compact_bf16_bf16_out`, a registered production
owner) is the sole determinant. The default now uses the grouped ladder instead.

This is a real conflict between two contracts, not a bug in either kernel:

- `scripts/gemma4_generated_history_gate.py` compares production (`auto`)
  against strict (`grouped`) and requires production to track strict. Run with
  the WMMA down restored, it fails 8 of 10 cases: combined `kl_mean` 5.79e-3
  (bar 1e-3), `kl_max` 0.39890 (bar 5e-2), `top1_rate` 0.98689 (bar 0.99).
- The MTP candidate oracle is llama.cpp parity, and llama.cpp's quantized MoE
  lands on the WMMA side of the knife edge.

A strict-profile comparison settles the question the assignment asked: the
oracle does **not** expect strict arithmetic. `HIPENGINE_GEMMA4_MOE_PREFILL=grouped`
is the full strict binder (it is the only key the strict plan writes), and it
produces `[139, 623, 3729]` -- the failing order. So no exact-route pin can
satisfy the oracle, and the default cannot be moved onto the oracle's route
without regressing the exactness screen.
