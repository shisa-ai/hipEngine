# the Q5_1 down MMQ spends four fifths of its inner loop on memory traffic that the compiler did not merge

## Summary

The previous entry measured the Q5_1 expert down projection at 3.01 TFLOP/s
against the Q4_K gate_up projection's 6.19 on the same rows, half the FLOPs and
two thirds the bytes in the same wall time, and named it the sharpest measured
inefficiency in the prefill. This unit found the cause in its innermost loop and
fixed it.

**Prefill at 512 tokens goes from 0.859-0.867 s to 0.819-0.830 s, 596 to 621
tok/s, 4.1 percent.** The down kernel itself drops from 156.3 to 117.5 ms, 24.9
percent, at both 512 and 1024 tokens.

The change is a load-width and loop-invariant fix. It is bit-exact by
construction -- no arithmetic was reordered -- and the kernel's own
bounded/deterministic test and the gemma4 expert-route integration suites pass
unchanged.

## What the inner loop was doing

`q5_1_mmq_ds4_selected_prefill_kernel` is one thread per output column walking
its expert's rows in 16-row passes. Its per-row, per-sub-block body read:

```cuda
const uint32_t bytes4 = load_qs_bytes(w_sub + 8, w);   // four byte loads, or-ed
...
const uint32_t x_lo = static_cast<uint32_t>(xw[w]);    // one dword load
const uint32_t x_hi = static_cast<uint32_t>(xw[4 + w]); // one dword load
```

and `load_qs_bytes` was:

```cuda
return static_cast<uint32_t>(qs[4 * w]) |
    (static_cast<uint32_t>(qs[4 * w + 1]) << 8) |
    (static_cast<uint32_t>(qs[4 * w + 2]) << 16) |
    (static_cast<uint32_t>(qs[4 * w + 3]) << 24);
```

Four byte loads, three shifts and three ors to fetch one dword, for each of four
`w` values, for each of eight activation dwords, for each row of each sub-block.
Per `(row, sub-block)` that is **24 scalar memory operations** -- 16 byte loads
for the weight and 8 dword loads for the activation -- against 16 `sudot4`
instructions. The memory side of the loop was larger than the arithmetic side.

Two things were wrong with it:

- **The weight side was not hoisted.** `w_lo`, `w_hi`, `w_hlo` and `w_hhi` depend
  only on `w_sub` and `qh`, which are fixed for the whole sub-block, so the four
  qword loads, the eight nibble planes and the eight high-bit expansions were
  being redone for every row. The row loop's trip count is dynamic, so there is
  no unrolled body for a second use to hoist against.
- **The activation side was not vectorized.** The eight dwords a sub-block needs
  are one 32-byte contiguous run, and the block header is 16 bytes (32 in the
  fp32 twin) with a block stride that is a multiple of 16, so the address is
  16-byte aligned by construction. It was being read as eight separate dword
  loads.

Both are now fixed: the weight side is unpacked once per sub-block, and the
activation is two `uint4` loads. **24 scalar memory operations per (row,
sub-block) become 6** -- one hoisted weight group plus two vector loads.

## Measured

Same host, same session, same artifact, same command, both arms:

| | prefill 512 | down kernel 512 | down ms/layer | down kernel 1024 |
| --- | --- | --- | --- | --- |
| before | 0.8594, 0.8665, 0.8594, 0.8611 s | 156.3 ms | 5.391 | 5.347 |
| after | 0.8193, 0.8302 s | 117.5 ms | 4.051 | 4.031 |

The before arm is four independent runs (three probe runs and the kernel census)
all inside 0.859-0.867 s; the after arm is two runs inside 0.819-0.830 s. The two
arms do not overlap and the gap is four times the ~1.3 percent run-to-run spread
within the after arm.

In rate terms the down kernel goes from 35.3 to **46.5 GB/s** and from 3.01 to
**3.97 TFLOP/s**, so it is now 1.29x behind its sibling per byte rather than
1.54x, and 1.56x behind per FLOP rather than 2.06x. The Q4_K gate_up kernel is
unchanged within noise (5.246 to 5.309 ms/layer), which is the control: nothing
outside the edited loop moved.

At 1024 tokens the prefill goes 2.007 to 1.936 s, and the down kernel's per-layer
time falls by the same 24.6 percent, so the fix is not specific to the 512-token
operating point.

## Changes

`hipengine/kernels/hip_gfx1100/quant/gguf_q5_1_mmq_selected_prefill.hip`:
`load_qs_bytes` is one dword load instead of four byte loads or-ed together; the
weight nibble planes and high-bit expansions are hoisted out of the row loop; the
eight activation dwords are two `uint4` loads instead of eight dword loads. No
signature, launch configuration, or arithmetic changed.

## Validation

- **Model / quant:** `gemma-4-26B-A4B-it-UD-Q4_K_XL.gguf`, `gguf_q4_k_m`
  resolution (experts Q4_K gate_up, Q5_1 down; layer 29 Q5_K).
- **Workload shape:** 512-token prefill, batch 1, greedy, one output token.
- **Hardware:** gfx1151, AMD Radeon 8060S, host `zbook`, kernel 7.2.7-1-cachyos.
  **This is not the default gfx1100/W7900 lane.** The change is in
  `kernels/hip_gfx1100/quant/gguf_q5_1_mmq_selected_prefill.hip`, which the
  gfx1151 backend imports and recompiles from source (it is in
  `hipengine/kernels/hip_gfx1151/__init__.py`'s `_GFX1100_MODULES`), so both
  backends take the edit -- but **the gfx1100 speedup is unverified and needs a
  W7900 measurement before it is claimed.**
- **Command:**
  `env -u HIP_VISIBLE_DEVICES ROCR_VISIBLE_DEVICES=0 HIPENGINE_HIP_ARCH=gfx1151
  PYTHONPATH=. .venv/bin/python scripts/gemma4_expert_mmq_wrapper_split.py
  --prompt 512 --repeats 5`
- **Result:** 0.8302 s median, 616.7 tok/s, down kernel 117.5 ms over 29 layers.
- **Correctness gate:** `tests/test_gpu_gguf_q5_1_mmq_selected_prefill.py` (2
  passed), `tests/test_gpu_gemma4_expert_route_true_geometry.py` and
  `tests/test_gpu_gemma4_expert_row_invariance.py` (15 passed),
  `tests/test_unit_gemma4_expert_route.py` (63 passed). 80 tests, no failures.
  The kernel's declared contract is bounded-and-deterministic against the strict
  owner, and it is unchanged because the edit moves no arithmetic.

## Shipping path

The probe drives `llm.generate_detailed` on the default path with no environment
variable set, and it counts the leaf calls it intercepts: 29
`q5_1_mmq_ds4_selected_prefill_bf16_bf16_out` calls per prefill, one per layer,
all through the route that was edited. The route is chosen by
`gemma4_project_experts_down_mmq` on the weight's `quant_key`, so a Q5_1 expert
down projection takes it by construction. Nothing else in the file changed, so no
fallback or variant selection moved.
