# The fused IQ4_XS local32 dual SiLU owner loses above rows 2

## Summary

`gguf_iq4_xs_local32_dual_silu_kernel` fuses an IQ4_XS `ffn_gate`/`ffn_up` pair
into one launch with one shared activation window and one shared codebook LUT,
and the kernel comment declares it bit-exact with the unfused
single/single/`silu_mul` chain. It is `template<int WAVES>` with no `ROWS` and
its `extern "C"` rejects `rows != 1`, so it only serves the autoregressive
decode. IQ4_XS carries **30** `ffn_gate`/`ffn_up` pairs in UD-Q4_K_M, i.e. 60 of
its 117 verifier tensors, so extending the owner to the verifier row envelope
would have removed 30 launches/step.

This unit built the `ROWS` sibling that the single owner
(`gguf_iq4_xs_local32_gemv_kernel<WAVES, ROWS>`) already uses, and measured it
in isolation before doing any dispatch plumbing. **The dual is a loss for
rows >= 3 and was rejected.** The register pressure of two accumulator sets
costs more occupancy than the shared activation window and codebook LUT win
back, which is the failure mode the pre-measurement was written to catch.

## Changes

None retained. All edits were made to a scratch copy of
`hipengine/kernels/hip_gfx1100/quant/gguf_iq_dense.hip`, which was restored
byte-for-byte afterwards (`git status -sb` clean, verified). The scratch edits
were:

1. `template<int WAVES>` -> `template<int WAVES, int ROWS = 1>` on
   `gguf_iq4_xs_local32_dual_silu_kernel`, with the single owner's launch-bounds
   relaxation (`ROWS > 1 ? 1 : 16 / WAVES`).
2. `acc_a[COLS]`/`acc_b[COLS]` -> `acc_a[ROWS][COLS]`/`acc_b[ROWS][COLS]`,
   `xv[8]` -> `xv[ROWS][8]` with `xp = x + r * K + blk * 256 + lane * 8`, the
   inner FMA loop over `r`, and `xwave_a`/`xwave_b` widened to
   `[WAVES][ROWS][COLS]` with the output written to `out[r * N + n0 + t]`.
3. A scratch `extern "C" hipengine_scratch_iq4_xs_local32_dual_rows` that
   selects `ROWS` from `rows` exactly as
   `hipengine_gguf_iq4_xs_local32_rows_gemv` does (2, 3 or 4; `grid.y == 1`, so
   no padded row is ever read), instantiating `WAVES` 2 and 4.

The real `hipengine_gguf_iq4_xs_local32_dual_silu` entry is untouched and still
rejects `rows != 1`.

## Validation

Harness `/tmp/phase8/dualbench.py` reads the real `blk.1.ffn_gate.weight` and
`blk.1.ffn_up.weight` IQ4_XS payloads (47.35 MB each, K=5120, N=17408) out of
`/models/gguf/Qwen3.8-27B-UD-Q4_K_M.gguf` and compares the dual against two
`launch_local32_rows` calls on the same weights, best of 5 x 50 reps after 5
warmup launches, `waves = _local32_waves(5120, 17408) = 2`:

| rows | dual us | 2x single us | speedup |
| --- | --- | --- | --- |
| 2 | 202.40 | 212.85 | 1.052x |
| 3 | 254.34 | 205.84 | 0.809x |
| 4 | 502.74 | 233.65 | 0.465x |

Command:

```
HIP_VISIBLE_DEVICES=1 /home/lhl/hipEngine-main/.venv/bin/python /tmp/phase8/dualbench.py <rows>
```

Rows 3 is the native verifier target cycle, so the dominant case is a 19%
loss, and rows 4 is a 54% loss. The rows=2 case is a 5% win on a single-row
slice and does not justify a second owner plus its gate.

## Next

unchanged: the T16 repack (largest ceiling, largest unit) and the 12-pair
Q5_K T16 dense dual rowtile SiLU sibling of
`q4_k_t16_dense_dual_rowtile_silu_gemv` (bounded at roughly 0.8 ms/step).
Do not re-open the local32 dual `ROWS` extension without a register-lean
accumulator scheme that keeps one accumulator set live at a time.
