# Retraction: the MTP refusal reason is already on the capability surface

## Summary

**Retracts `worklog/entries/20260920T053421.722261Z-lhl-mtp-refusal-reason-gap-6add29.md`.**
There is no gap. The MTP refusal reason is already on the capability surface, with
the exact code and the full failed-axis list, in the same response I had read when
I claimed it was missing.

`/tmp/t32/capabilities.json` at `sampling.speculative_mtp` contains:

    serving_route: True | default_enabled: False
    certified_explicit_scope: {
      admitted: False,
      reason: "candidate_budget_not_qualified",
      failed_axes: ["candidate_budget_not_qualified"],
      selected_route: "default",
      selected_candidate_count: 0,
    }

Every field a client needs is present: the admission verdict (`admitted: false`),
the machine-readable code (`reason`), the complete axis set (`failed_axes`), the
route actually taken (`selected_route: "default"`), the depth actually used
(`selected_candidate_count: 0`), and whether MTP is on by default
(`default_enabled: false`). Nothing is advertised that the engine declines.

**Why there is no gap in the mechanism.** `_speculative_mtp_capability`
(`hipengine/server/api.py:1483`) populates `certified_explicit_scope` from
`_engine_speculative_mtp_serving_capability` (`:11782`), which at `:11791` does
`value.as_dict() if callable(getattr(value, "as_dict", None)) else value`. That is
the full `SpeculativeMTPServingDecision.as_dict()` (`hipengine/speculative/serving.py:459`),
which serializes `admitted`, `reason`, and `failed_axes` alongside the plan
fingerprint and key. The refusal reason was therefore never on a separate path
from the capability response; the two are the same call.

**How I got it wrong.** I read `serving_route: true` and
`candidate_budget = {requested: 5, resolved: 5, source: explicit}` from the t32
block and concluded the refusal was hidden, without reading the sibling
`certified_explicit_scope` key that carried the answer. `serving_route` is
`configured_mode != "off" and engine_supported` (`api.py:1486-1487`), where
`engine_supported` is `_engine_supports_speculative_mtp(engine)`, i.e. whether the
model carries MTP tensors. It is a statement about the route being wired, not about
any request being admitted, and `default_enabled` sits next to it as the admission
signal. I also inferred a vocabulary-plumbing gap from
`_MTP_SCREENING_REASONS` existing separately, which does not follow: that frozenset
classifies screening qualification, it is not the only place the codes appear.

Consequence for the release: **this was never an MTP default-on blocker, and the
item I twice described as the last GPU-free blocker does not exist.** The
`provider_decline_reason` precedent I cited (`api.py:16263`, surfaced at `:16472`)
is unrelated: it is a per-span provider decline, and no analogous plumbing was
needed for admission.
