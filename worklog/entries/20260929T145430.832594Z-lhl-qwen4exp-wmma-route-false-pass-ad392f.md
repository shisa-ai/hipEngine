# The promoted wmma route produces a false pass at HEAD

## Summary

While running a control for the staged-f32 outlier review, the control itself
came back invalid - and it exposed a defect in the **already-promoted** WMMA
route, not in the staged-f32 work.

`--route wmma --layers 16-47` at HEAD, which is the certified configuration:

```
strict_logits_sha256    = 83732d4542e1847fd8975ca6...
candidate_logits_sha256 = 83732d4542e1847fd8975ca6...
```

Identical. KL exactly `0.0` on every statistic, `top1 1.0`, and the run reports
**`status: complete`, `measurement_valid: true`, `requires_outlier_review: false`**.

`83732d45...` is the **WMMA@16-47** hash - byte-identical to the teacher hash of
the composed staged runs, whose teacher arm explicitly binds `WMMA_LAYERS_ENV` to
16-47. The exact chain is `550bb9b8...`. So the teacher arm, recorded as
`teacher_selector: "cleared"` and `teacher_chain: "exact
coltile8_rowbatch4_f32_f32_out"`, did not resolve to the exact chain.

## It is a regression

The 2026-09-16 certification of this same route had a genuine exact-chain teacher
(`550bb9b8...` against candidate `65370710...`), mean KL 3.796e-4. Engagement was
real then.

**So the WMMA 16-47 gate cannot be re-run at HEAD to reproduce its
certification.** A re-run returns KL exactly 0.0 and a green status. That is the
worst possible failure shape: it looks like a perfect result.

## Mechanism, verified rather than inferred

- The dispatch memoization key carries **no WMMA layer-scope term**. It carries
  `use_wmma` as a boolean; the scope is applied separately through
  `wmma_prefill_weight_filter_session`, a context-local `ContextVar`.
- A probe that records the key the real `launch_gguf_linear` uses shows the key
  is **identical between the route's candidate and teacher arms**.

So the teacher arm hits the candidate arm's cache entry and replays its
WMMA@16-47 dispatch. `launch_gguf_linear` only reaches the dispatch chain inside
`if cached is None:`.

This is the **same defect class** as the staged-f32 false pass. The staged routes
are correct only because `_staged_f32_key` was added to the key; the WMMA route
has no equivalent term. My own earlier bug and this one are the same bug in two
places, and I only found the second because I ran a control instead of trusting
the first comparison.

## I did not fix it here, deliberately

The fix touches a promoted route and a dispatch key several routes share, in a
high-conflict file, and it needs its own RED test plus a gate re-run to
re-establish the 16-47 certification at HEAD. Folding it into the staged-f32 unit
would have buried it in an unrelated commit.

## What this does not affect

The staged-f32 results are unaffected, and that is checkable rather than assumed:
every staged run's teacher hash was verified to be `550bb9b8...` (the exact
chain) and every candidate hash verified to differ. The composed end-to-end
certificate has teacher `550bb9b8...`, candidate `87dbf445...`.

It does mean the composed run's **WMMA@16-47 component is not independently
re-verified at HEAD** by this packet; it is inherited from the 2026-09-16
certification. That is a real gap in the composition's evidence chain and is
recorded as such.
