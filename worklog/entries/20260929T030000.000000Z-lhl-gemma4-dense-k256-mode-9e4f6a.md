# the dense GEMM is bimodal in K mod 256, and two claims in the previous entry were overclaims

## Summary

The dense Q8_0 prefill GEMM runs at **13.7 to 14.1 TFLOP/s when `K % 256 != 0`** and at **6.5 to
11.9 when `K % 256 == 0`** -- a 1.75x swing set by an arithmetic property of K, exact across a
fine sweep and persisting at every supported tile. **Every K in the model qualifies for the slow
class, and 92 percent of the dense term's milliseconds are in it.**

The addressable gain is **10.8 ms of the 122.8 ms prefill gap, 9 percent** -- real, but far
below the 90 ms I estimated before doing the arithmetic, because K = 2816 carries most of the
term and takes only a mild penalty. The severe case is K = 4096 and 8192.

**Two claims in `20260929T020000` do not survive contact and are retracted below.**

## The pattern

`scripts/gguf_q8_0_dense_prefill_shape_time.py`, rows=512, out=2816, tile (32, 64):

| K | blocks = K/32 | ms | TFLOP/s | |
| ---: | ---: | ---: | ---: | :--- |
| 2560 | **80** | 0.904 | **8.16** | `% 8 == 0` |
| 2624 | 82 | 0.544 | 13.91 | |
| 2688 | 84 | 0.551 | 14.08 | |
| 2752 | 86 | 0.573 | 13.84 | |
| **2816** | **88** | 0.778 | **10.44** | `% 8 == 0` |
| 2880 | 90 | 0.604 | 13.74 | |
| 2944 | 92 | 0.611 | 13.90 | |
| 3008 | 94 | 0.621 | 13.96 | |
| 3072 | **96** | 1.186 | **7.47** | `% 8 == 0` |
| 3136 | 98 | 0.658 | 13.75 | |
| 3200 | 100 | 0.671 | 13.75 | |

**The slow points are exactly the multiples of 8 blocks**, equivalently `K % 256 == 0`. K = 2048
(64 blocks), 4096 (128) and 8192 (256) are all slow, which is why the first sweep saw a
"plateau": the three K values it probed most were all in one class.

**It is not the tile.** Crossing K against every supported tile keeps the gap:

| tile | K=2816 | K=2944 | ratio |
| :--- | ---: | ---: | ---: |
| (32, 64) | 10.24 | 13.98 | 1.37 |
| (16, 64) | 8.69 | 9.79 | 1.13 |
| (64, 32) | 8.73 | 11.30 | 1.29 |
| (32, 32) | 5.99 | 8.48 | 1.42 |

So it is a property of the K-loop trip count, not of the tile's addressing.

## The penalty grows with K, which is why the payoff is small

| in | out | n | ms | TFLOP/s |
| ---: | ---: | ---: | ---: | ---: |
| 4096 | 2816 | 25 | 44.79 | **6.59** |
| 8192 | 2816 | 5 | 18.10 | **6.53** |
| 2816 | 1024 | 5 | 2.04 | 7.24 |
| 2816 | 4096 | 25 | 30.72 | 9.61 |
| 2816 | 2048 | 50 | 29.88 | 9.88 |
| 2816 | 2112 | 60 | 35.22 | 10.38 |
| 2816 | 8192 | 5 | 10.22 | 11.56 |
| 2112 | 2816 | 30 | 15.36 | 11.89 (fast class) |

K = 2816 is in the slow class but only loses 1.2 to 1.3x; K = 4096 and 8192 lose the full 1.75x.
**92 percent of the term's 189.8 ms is in the slow class, but re-rating all of it at the fast
class's 13.8 TFLOP/s saves only 10.8 ms.** That is 9 percent of the gap, and it assumes the
fast class is reachable at K = 4096 and 8192 -- which is exactly what is not yet known.

## Retractions

**1. The "127 GB/s plateau" is not independent evidence of anything.** The tiling fixes the
arithmetic intensity at `tile_m / (34/32)` = 30.1 MAC per byte, so a constant TFLOP/s rate
*implies* a constant GB/s rate. Four shapes agreeing at 127 GB/s is the same observation as four
shapes agreeing at 7.7 TFLOP/s, restated. I presented it as a separate ceiling.

**2. The lm head comparison was apples to oranges.** A 1-row GEMV has no weight reuse and its
223 GB/s is pure DRAM streaming. The GEMM's traffic is not DRAM-bound at all, which the tile
test proves: **(64, 32) halves the M-tiles and therefore doubles the arithmetic intensity, and
it is 1.16x SLOWER, not 0.75x faster.** If weight traffic were the constraint, doubling the
intensity would have helped. The binding constraint is on the compute side.
