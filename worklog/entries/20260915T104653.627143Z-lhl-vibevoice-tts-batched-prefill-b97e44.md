# VibeVoice-TTS session: batched prompt prefill, RTF 2.573 -> 1.868

## Summary

The TTS generation session was prefilling its prompt with one single-token GEMV
forward per prompt row. On the pinned single-speaker request that is 121 forwards
at a measured 20.86 ms each — **2.52 s of the 4.00 s LM stage and 29% of the
whole request**. The runtime already had a batched hipBLASLt prefill
(`VibevoiceQwen2Runtime.prefill_rows`) which the ASR path already used through
`greedy_generate`; the session simply never called it. Switching to it:

| Metric | Before | After | Delta |
| --- | ---: | ---: | ---: |
| Pooled RTF | 2.573 | **1.868** | **-27.4%** |
| Warm synthesis | 8.577 s | 6.227 s | -27.4% |
| Time to first audible chunk | 2.835 s | **0.444 s** | **-84.3%** |
| LM stage | 3.997 s | 1.614 s | -59.6% |
| Cold start | 8.290 s | 6.068 s | -26.8% |

Correctness is unchanged on the same run: `chain_exact` is true and
`negative_conditions_match` is true, both end-to-end from the session's own
reference-audio encode (no prompt embeddings and no negative conditions
injected). The same request in the pinned torch oracle venv measures RTF 1.303
on this host, so hipEngine goes from 1.94x slower to **1.43x slower**.

## Where the time went

A direct split of the LM stage on the single-speaker prompt:

| Component | Time |
| --- | ---: |
| per-token prefill, 121 rows | 2.524 s (20.86 ms/row) |
| `logits_argmax`, 3.14 ms x ~52 | 0.55 s |
| positive decode, 27 forwards | 0.563 s (20.85 ms/fwd) |
| negative forwards, 25 | 0.493 s (19.74 ms/fwd) |

Sum 4.13 s against the 3.997 s the bench attributed to the LM stage.

The per-row prefill is weight-bandwidth bound: it streams the 3 GB of backbone
weights once per row. Batching reads them once for the whole prompt, which is
why the stage falls by an order of magnitude.

## Changes

- `VibevoiceQwen2Runtime.prefill_host_rows(rows, *, capture_hidden=False)` —
  uploads the fp32 hidden rows, calls `prefill_rows`, copies the last row into
  `_hidden` so `hidden_state()`, `logits_argmax()` and the next
  `forward_layers()` continue from the right place, and sets `_ctx_len`.
  `capture_hidden` returns the post-final-norm hidden of every position, so the
  session's trace stays complete; the timed path leaves it off and pays neither
  the extra norm launch nor the copy.
- `greedy_generate` now calls it instead of open-coding the same upload /
  prefill / last-row-memcpy sequence.
- `VibevoiceTtsSession.generate` calls it instead of the per-row loop.

## Arithmetic

The batched route reassociates every prompt projection through hipBLASLt, so it
is **not** bit-identical to the per-row loop it replaces. Measured on the ASR
prompt: 0.028 relative on the last prompt hidden and 0.024 on its logits, with
the same argmax. Two consequences worth recording:

- The single-speaker 27-token chain is still exact, so the reassociation is
  inside the envelope that chain tolerates.
- The two-speaker trajectory-stability envelope widens from 0.055 to 0.090, and
  that test's gate moves from 0.08 to 0.15. A loop that has lost the branch
  reads 0.5-1.3, so the gate still discriminates by more than 5x.

## Tests

- New `test_batched_prefill_matches_the_per_row_loop` in
  `tests/test_gpu_vibevoice_qwen2_runner.py`, parametrized over the `strict` and
  `hipblaslt` routes. It localizes a prefill regression to the prefill rather
  than to a 16-token chain mismatch. Gates are the measured envelope (0.05 on
  hidden and logits) plus the argmax; agreement with torch is gated separately
  by `test_greedy_chain_matches_torch` and `test_teacher_forced_top1`, which both
  exercise the batched route.
- `test_two_speaker_trajectory_is_stable_once_call0_is_on_branch` gate widened
  from 0.08 to 0.15 as above.
