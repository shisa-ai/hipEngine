# MTP streaming survives a slow consumer: the chunk mailbox is the request's own budget

## Summary

A streaming MTP request was cancelled after roughly one hundred output tokens on
`gfx1151` / `Qwen3.8-27B-Q4_K_M`, so every real ShareGPT-shaped prompt lost its
answer to `finish_reason: "error"`, `budget_pressure: "client_backpressure"` and
no `usage` block. The cause was a policy, not a kernel: both internal
engine-to-consumer queues were fixed at 64 entries and treated "full" as "cancel
this child". The mailbox holds at most one entry per committed output token, so a
child's own output budget is its natural bound; the fixed 64 turned a slow
consumer into a dead request. The bound is now the request's budget (floor =
configured value, hard cap 4096 entries), and a cancelled stream reports the
`usage` it delivered so a client can detect the truncation.

Measured on `gfx1151` (zbook), default server configuration
(`--max-context-tokens 16384 --kv-storage bf16`, automatic MTP resolving to depth
3), single request, `stream: true`,
`stream_options: {include_usage: true, include_hipengine: true}`:

| Request | Before | After |
| --- | --- | --- |
| "Write a 300 word essay about the ocean." (200 tokens asked) | cancelled at **96** tokens after 3.92s, no usage | **200** tokens in 13.98s, usage present |
| Jeff Walker launch-formula prompt (128 tokens asked) | cancelled at **107** tokens after 5.3s, no usage | **128** tokens in 6.55s, usage present |

Isolating the trigger by request shape (same host, same prompt, 200 tokens):

| Variant | Result |
| --- | --- |
| `stream: true`, `include_hipengine: true` | cancelled at 96 tokens, 3.92s, 85 KB of chunks |
| `stream: true`, `include_hipengine: false` | **completed** 203 chunks, 10.06s, 45 KB |
| `stream: false` | **completed** 200 tokens, usage with accepted/rejected draft counts |
| `stream: true`, `speculative_mtp: false` | **completed** 200 tokens, 16.77s |
| `stream: true`, `include_hipengine: true`, thinking disabled | cancelled at 110 tokens |

Per-chunk telemetry roughly doubles the per-chunk cost of the consumer and is
what tipped a marginal consumer below the producer's rate; the cancel itself was
triggered by the fixed bound, which is why removing it fixes every variant.

## Changes

- `hipengine/generation/concurrency2.py`: add `stream_mailbox_bound()` (floor =
  configured bound, bound = `max_tokens + 8`, hard cap
  `STREAM_MAILBOX_HARD_CAP_CHUNKS = 4096`) and export it with both constants.
- `hipengine/generation/engine_service.py`: resolve each streaming child's
  collector `max_chunks` through `stream_mailbox_bound(configured, max_tokens)`
  instead of using the fixed configured value.
- `hipengine/generation/engine_loop.py`: resolve each resident stream's
  `state.events` bound through `_resident_stream_queue_bound(state)`, which reads
  the submission's request budget, instead of the fixed
  `DEFAULT_RESIDENT_STREAM_QUEUE_MAX_CHUNKS = 64`.
- `hipengine/server/api.py`: the `GenerationCancelled` handlers of both streaming
  endpoints emit a `usage` chunk (built from the text actually delivered) before
  the error chunk when `stream_options.include_usage` is set, so a truncated
  stream is both detectable and countable.
- Tests: `tests/test_unit_generation_stream_mailbox_bound.py` (new; bound
  resolution, collector behavior at the budget and at the hard cap, resident
  helper reads the submission budget) and
  `tests/test_integration_generation_engine_service.py` — the previous
  `test_engine_service_backpressure_and_cancel_are_child_scoped` asserted the old
  policy (a child that has not been drained is cancelled) and is replaced by
  `test_engine_service_slow_consumer_and_cancel_are_child_scoped` (a child
  buffers its whole budget and completes; explicit cancel stays child-scoped)
  plus `test_engine_service_stream_budget_overrun_is_client_backpressure`, which
  keeps the guard meaningful: a child that publishes **past its own budget** is
  still cancelled with `client_backpressure` and still leaves its neighbor alone.

The safety net is unchanged in kind and sharper in meaning: `_publish_token_locked`
still rejects a child that exceeds `max_output_tokens`, so the backpressure cancel
now fires for a runaway child rather than for a consumer that is merely slower
than the producer. Memory stays bounded: the mailbox can hold at most the child's
budget, capped at 4096 entries per child.

## Validation

- `pytest tests/test_unit_generation_stream_mailbox_bound.py -q` → 8 passed.
- `pytest tests/test_integration_generation_engine_service.py tests/test_unit_generation_stream_mailbox_bound.py -p no:randomly` → 37 passed.
- Live E2E on `gfx1151` (see table): the two previously-cancelled streaming
  requests complete with `usage` and `generated_tokens` equal to
  `completion_tokens`; both ran the automatic MTP route.
- Diagnosed with temporary `[DEBUG-QUEUE]` instrumentation on the three rejection
  sites (reverted before this commit): only the collector's CHUNK branch fired,
  at `depth=64 max=64`, after the mailbox grew 29 → 62 → 64 while the consumer
  drained one entry per `drain(max_chunks=1)` call.
