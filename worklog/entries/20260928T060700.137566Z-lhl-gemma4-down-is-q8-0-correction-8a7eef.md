# the fixture's down is q8_0 so it takes the down MMQ route and my grouped-family claim was wrong

## Summary

`20260928T060604` claimed the fixture's down projection is Q4_K, that
`gemma4_project_experts_down_mmq` therefore declines it, and that the fixture's
down runs the fp32 grouped family -- which made the down's scope question the
live one while the gate/up's was answered. **The premise is wrong.** Read from
the loaded weights object:

```
backend   = 'hip_gfx1100'
quant_key = 'gguf_q8_0'
```

The fixture's `experts_down_proj` is **Q8_0**. `gemma4_project_experts_down_mmq`
handles *"a Q5_1 or Q8_0 expert down projection"*, so it **accepts** this weight
and the fixture's down takes the **down MMQ route**.

## What this changes

The correction reverses the disposition table:

| defect | route | disposition |
| --- | --- | --- |
| gate/up | fused MMQ (optional accelerator) | answered: toy-shape only, production unaffected |
| down | **down MMQ (optional accelerator)** | **same class as the gate/up, not the general path** |

So the previous unit's conclusion -- *"the grouped family is what every expert
down projection takes that is not Q5_1 or Q8_0, including the Q4_K artifact this
work is built around, so if it is row-count dependent at the true shape then
production prefill and decode disagree"* -- does not hold as stated. Both pinned
defects are in **MMQ accelerator routes**, and both therefore have the same
prospect: a toy-shape artifact with a rollback lever rather than a defect in the
general path.

That prospect is a hypothesis, not a result. It still has to be measured for the
down the way `20260928T060531` measured it for the gate/up.

## How the error happened, and the check that catches it

The claim was an *inference* from the route guard's docstring -- "Q5_1 or Q8_0"
-- combined with an *assumption* about the fixture's quant that was never read.
The gate/up discussion in the same investigation had been about Q4_K throughout
(the fused gate/up MMQ route is the Q4_K one), and the down's quant was carried
along from that context without being checked.

The check is one call and would have taken a minute:

```python
weights.layers[0].experts_down_proj.spec.quant_key
```

The general rule this is an instance of: a route-disposition claim is a claim
about a *specific weight*, so it needs the weight's `quant_key` read, not the
route's docstring quoted. The same mistake was available in
`20260928T060531`'s gate/up case, which is correct only because the gate/up
really is Q4_K there.

## What the down test needs

The test being written at the time -- a row-count case for the down at the true
`2816 -> 704` shape -- was building a `gguf_q4_k` weight, which would have
exercised the **grouped** family and measured a route the fixture does not use.
It needs `make_q8_0_weight` (or the Q8_0 equivalent) and
`quant_key='gguf_q8_0'` to match the artifact, so that it measures the same
route the failing case does.

A second thing it surfaced: `make_q4_k_weight` requires `in_features` to be a
multiple of `QK_K` (256), and the model's down input is **704 = 2 x 256 + 192**,
i.e. three Q4_K blocks per row with a partial tail. Whatever weight helper is
used has to accept a row that is not a whole number of blocks, or the case has
to substitute a shape that preserves the block structure.
