# W7900 Qwen3.8: the model misses the faster prefill route by one geometry field

## Summary

Continuing `20260830T042147...-2412d6`, which established that small-M prefill has no runtime
lever. The cheapest remaining question was whether the source-F16 rocBLAS prefill route is even
reachable for this model as a diagnostic. It is not, and the reason is one field: comparing the
GGUF metadata against the admitted `QWEN35_DENSE_H5120_GEOMETRY`, **12 of 13 fields match** and
`file_type_name` is exactly the admitted `MOSTLY_Q4_K_M`. The mismatch is `block_count` **65 vs
64**, which is the model's nextn (MTP) layer. So Qwen3.8-27B on W7900 is excluded from a faster
dense-prefill route by a constant authored for a 64-block file, not by any structural difference.

## Changes

Analysis only. No engine edit: adding a 65-block geometry to a kernel admission map is an
admission decision with its own numerical gate, not something to slip in beside a measurement.

## Validation

Via the engine's own `scan_gguf` (no weights loaded) against
`hipengine/kernels/policy.py:112`, which `_gguf_policy_identity` uses as the admission key:

| field | model | admitted |
| --- | --- | --- |
| block_count | **65** | 64 |
| hidden 5120, ffn 17408, heads 24, kv heads 4, key/value 256 | match | match |
| full_attention_interval 4, ssm inner 6144 / group 16 / state 128 / conv 4 / tsr 16 | match | match |
| file_type_name | MOSTLY_Q4_K_M | MOSTLY_Q4_K_M |

The metadata also carries `qwen35.nextn_predict_layers`, which accounts for the extra block, and
`GGUFModelGeometry.from_config` takes `block_count` raw (`policy.py:45`) with `layer_types`
generated from it, so a 65-block file produces a distinct geometry tuple rather than collapsing
onto the 64-block one. Route reachability today:

- `_gguf_t16_f16_rocblas_prefill_policy` (`qwen35_gguf_runner.py:11224`) returns None unless the
  identity is a key of the backend package's `GGUF_DENSE_T16_F16_ROCBLAS_PREFILL_POLICIES`, whose
  only entry is `(QWEN35_DENSE_H5120_GEOMETRY, "MOSTLY_Q4_K_M")`. Our identity is not it.
- Even if admitted, that route applies row buckets starting at 512 with explicit losing-shape
  ceilings, so M=45 would still fall back to the WMMA rowtile family. The diagnostic therefore
  needs both the geometry and a row floor below 512, and both are admission changes.

So the honest shape of task #12: the fast alternative is a *kernel admission* question with a
numerical gate attached (F16 dequant changes production arithmetic), and its first step is
authoring the 65-block geometry rather than any measurement.
