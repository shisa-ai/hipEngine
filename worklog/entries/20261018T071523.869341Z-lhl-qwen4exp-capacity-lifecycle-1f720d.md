# qwen4exp capacity and lifecycle qualification

## Summary

Task #23 asked for capacity, cache, and lifecycle evidence at supported bounds.
All three were measured on the served route, and one production-safety defect
was fixed on the way: an operator-level resident refusal used to reach clients
as a bare `500 Internal Server Error`.

**Capacity.** `scripts/gguf_capacity_probe.py` rejects architecture `qwen4exp`,
so the Tier-1 probe for this model is the admission planner,
`scripts/qwen4_exp_memory_plan.py`:

| context | 4 slots | required | KV | index |
| --- | --- | --- | --- | --- |
| 32768 | passes | 89.25 GiB | 3.00 GiB | 0.95 GiB |
| 65536 | passes | 93.20 GiB | 6.00 GiB | 1.90 GiB |
| 131072 | passes | 101.10 GiB | 12.00 GiB | 3.79 GiB |
| 262144 | passes | 116.89 GiB | 24.00 GiB | 7.58 GiB |

Available device memory on this host is 121.6 GiB of 124.0 GiB. The planner is
memory math; the engine also enforces a *qualified* width, and the two differ
at long context. At `max_sequence_length=262144` the engine admits at most 2
resident slots and refuses 4 with:

```
Qwen4Exp resident capacity must be within 1..2 for max_sequence_length=262144;
the production bound is 2, and HIPENGINE_QWEN4_EXP_AR_BATCH=1 qualifies up to 4
slots at <= 2048 positions
```

Both numbers are real and they answer different questions: the envelope fits,
the qualified width does not. Serving qualification uses the qualified width.

**Retrieval at depth (Tier 2).** A 262,144-context server with 2 slots and MTP
enabled answered the seeded retrieval prompts with 4/4 correct at 10/40/70/95%
depth:

```
8,165 prompt tokens   en 13.1s  ja 10.9s
16,337 prompt tokens  en 19.1s  ja 18.5s
65,517 prompt tokens  en 75.9s  ja 75.6s
200,666 prompt tokens en 314.3s
```

**Lifecycle.** 14 checks pass against a 2048-context, 4-slot server: four
concurrent live slots observed mid-flight and released to 0 afterwards, six
oversubscribed requests all answered, a client that disconnects after four SSE
chunks releases its slot and the server keeps serving, and a stateful chat
session reports `append_visible_only`, lists, and deletes.

**Cache.** `prefix_cache` is `off` and stays unclaimed. Session commits are
app-local transcript replay (`resident_kv_commit=false`), which the capabilities
payload already states.

**Defect fixed.** A refusal during resident preparation raised a plain
`ValueError` from the generator constructor. Endpoints that probe the engine
outside the request-error mapping — `/v1/hipengine/capabilities` and the chat
prompt-preparation path — turned that into an unhandled 500 with no message,
while `/ready` said `ready: false`. `LLM` now raises `ResidentPreparationError`
for generator-construction refusals, and the server maps it to a 503 with
`code: resident_prepare_failed`, the refused setting, and a remedy. A resident
slot refusal now names both fixes (`--max-active-requests`, or a context the
qualified width covers) instead of a generic configuration hint.

## Changes

- `hipengine/llm.py`: `ResidentPreparationError`; generator construction
  failures are raised as that type.
- `hipengine/__init__.py`: exports the type.
- `hipengine/server/api.py`: `_resident_prepare_http_error`, a handler for the
  type, capabilities wrapped so introspection answers with the refusal instead
  of a 500, and a slot-bound branch in `_resident_prepare_guidance`.
- `tests/test_integration_server_api.py`:
  `test_resident_prepare_refusal_returns_a_structured_remedy`.
- `tests/test_unit_server_startup_guidance.py`: slot-refusal guidance test.
- `scripts/qwen4exp_http_long_context_gate.py`: seeded retrieval over HTTP at
  any depth, scored per question.
- `scripts/qwen4exp_http_lifecycle_gate.py`: slots, oversubscription,
  cancellation, and session checks; reads both published decode shapes so a
  "no leaked slots" verdict is never vacuous.
- Artifacts under `benchmarks/results/`: capacity ladder, long context,
  lifecycle.
