# both expert routes are self-consistent so the oracle has to be external

## Summary

`20260928T055408` established that the two expert routes disagree with each
other while each is internally consistent across row counts, and left
"establish which route is correct" as the next step. This unit tests the
strongest available internal invariant and finds it does not discriminate.

**Identical rows must produce identical outputs.** Two rows with byte-identical
hidden input and byte-identical routing are the same computation and must give
byte-identical results. For every row count and both routes:

| route | rows | rows byte-identical within the call |
| --- | --- | --- |
| per-lane GEMV (prefill route off) | 2, 3, 4 | **True** |
| row-reusing (prefill route on) | 2, 3, 4 | **True** |

and each route's `rows=4` row 0 equals its own `rows=1` row 0 with
`rel=0.00000000`.

So both routes are internally sound. The invariant is necessary and not
sufficient: it cannot say which of two self-consistent computations is the right
one, and an external oracle is required.

## What the oracle can be

The fixture's expert projections are `Gemma4GGUFDeviceWeight` -- the same object
type and the same quantized-block storage the dense linear funnel takes -- not a
raw bf16 pointer:

```
experts_gate_up_proj: Gemma4GGUFDeviceWeight  slot=layers.0.ffn_gate_up_exps
experts_down_proj:    Gemma4GGUFDeviceWeight  slot=layers.0.ffn_down_exps
```

`launch_gguf_linear` is already established as bit-exact across row counts
(`20260928T054834`) and is the funnel every dense projection uses, so it is a
sound oracle for one expert's `(rows, in) x (in, out)` product. What it needs is
a per-expert view: it takes a whole `GGUFDeviceWeight` and does not index by
expert the way the expert routes do, so the oracle is one expert's slice of
`ffn_gate_up_exps` and `ffn_down_exps` presented as a weight of its own.

## Shapes worth noting

The fixture's expert geometry is small: `num_experts=4`, `moe_intermediate=64`,
`hidden=256`, `top_k=2`. The fused gate/up width is 128 and the down projection
is `(256, 64)`. Those are exactly the sizes where a tile or block boundary is
likely to land badly, and the spurious differences observed are round
powers-of-two multiples -- so a boundary in the row-reusing route's tiling is
the leading hypothesis, with the per-lane GEMV as the other side.

## Validation

  byte-identical rows and identical routing, at rows 2, 3 and 4, under both
  `_PREFILL_MIN_LANES_PER_EXPERT = 1e9` (per-lane GEMV) and `= 0` (row-reusing),
  comparing rows within each call and row 0 across row counts. Exit 0.
- The projection types are read from the loaded weights object, not assumed from
  the layer docstring's "either a bf16 pointer or a GGUF weight".
- The claim that `launch_gguf_linear` does not index by expert is from its
  signature and its use in the dense path, both read.
