# The oracle divergence is cross-schedule bit non-determinism, and the gate does not gate the production schedule

## Summary

The dense27B oracle divergence is schedule-dependent bitwise non-determinism in
the batched prefill arithmetic, and the gate that reports it as a failure does
not gate the schedule the engine actually runs. A fresh `code` run with the
mismatch lists recorded (the committed qualification artifact kept only the
booleans) shows the candidate matching the production 256-row chunked route
bit-for-bit while differing from both other references in essentially every
layer -- and those two references are the ones in the gate's `passed`
expression, while the production comparison is emitted with `gating: false`.

## Changes

- None to production code. One gate run for `code` with the existing
  `--json` output, whose `prefill_oracle.semantic_boundary_mismatches` and
  `initial_state_mismatches` lists the committed artifact had summarized away.

## Validation

- One gate run: `scripts/gguf_prefix_reuse_gate.py` with the artifact's recorded
  command for `code`, `--json /tmp/t30-code/code.json`, gate exit 0. The
  mismatch lists cited above are that run's own output, not a re-derivation.
- The `passed`-expression and `gating: false` readings are from
  `scripts/gguf_prefix_reuse_gate.py` lines 823-833 and 937-946.

## Evidence

`/tmp/t30-code/code.json`, from the artifact's own recorded command (same
model, backend, quant, 1024+200 tokens, 4 teacher-forced steps, active
lifecycle, `greedy_fast`):

| comparison | reference schedule | mismatches |
| --- | --- | --- |
| `clone_boundary` | the source session it was cloned from | **0** |
| `scheduler_chunk_diagnostic` boundary / final | 256-row chunks (**the production schedule**) | **0 / 0** |
| `semantic_boundary` | one-shot `prefill(prefix)` | **126**: 47 layers conv + 47 recurrent + 16 kv.key + 16 kv.value |
| `initial_state` | `prefill(prefix)` + 200 per-token `step()` | **128**: 48 conv + 48 recurrent + 16 kv.key + 16 kv.value |

`position` is in neither mismatch list, so the earlier "a position difference
would explain a universal False" hypothesis is ruled out: the states agree on
where they are and differ in their bytes. The mismatching components are the
per-layer Conv/GDN `conv` and `recurrent` fingerprints and the full-attention
`key`/`value` fingerprints -- i.e. every layer of both state families, which is
what a hash over the whole buffer reports when a schedule changes the
accumulation order anywhere in it.

The gate's own comment calls the chunked route the gating reference ("The
gating reference privately processes every token through the exact same
256+suffix production chunks that prefix reuse replaces") and the one-shot route
a diagnostic ("Keep the one-shot bulk route as a diagnostic because its
row-count arithmetic can differ from scheduler chunking"). The code does the
opposite: `passed` (line 823) requires `semantic_boundary_exact` and
`initial_state_exact` -- the one-shot and serial references -- and never
mentions `scheduler_boundary_mismatches` / `scheduler_state_mismatches`, which
are emitted only under `scheduler_chunk_diagnostic` with `gating: false`.

That is the concrete defect behind the task's puzzle that the HIT/MISS state
check passes while the gate fails: the check that passes *is* the production
comparison, and the gate does not use it. Under the project's contract -- exact
control/ownership, same-schedule determinism, and a calibrated numerical
envelope, explicitly not bit-equality to a strict parent (AGENTS.md,
`docs/EXECUTION-PROFILES.md`) -- cross-schedule bit equality is not a
requirement any BF16 batched prefill can meet, and requiring it from a one-shot
and a decode-shaped per-token reference is over-strict by construction.

## What this does not resolve

The teacher-forced numerical envelope against the serial reference is a
separate, real question, and it is not explained by "the gate is over-strict":
`code` agrees to `kl_mean` 3.9e-05 with an exact trajectory, but Japanese
measures `kl_mean` 0.68 with `top1` 75% and two of four teacher-forced
predictions degenerate (candidate `[271, 271, ...]` against reference
`[96026, 98222, ...]`), and its `initial_output_exact` is False, so the two
routes disagree on the *first* token after prefill. Which route is numerically
right is undetermined by anything measured so far: the candidate matches the
production schedule bit-for-bit, but that only says the production route is
self-consistent, not that it is the accurate one.

## Next

1. Determine the direction with a higher-precision reference for the Japanese
   category: the CPU/fp32 reference under `kernels/cpu_reference/`, or the
   `serial_exact` verify teacher the sampled-MTP work already uses. If the
   production route is the accurate one, the serial oracle is the inaccurate
   side and the envelope should be measured against a third reference rather
   than against a decode-shaped schedule; if not, the production prefill route
   has a real accuracy defect to fix.
2. Gate the production schedule: make `passed` require the chunked comparison
   (which is bit-exact today) and keep the one-shot and serial comparisons as
   diagnostics with their KL/top-1 recorded, or bound them explicitly.
3. Only then the calibrated mean/tail/top-1 and task gates, and the full
   mtp-bench category suite plus heldouts for any performance claim.
