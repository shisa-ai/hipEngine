# the expert forward is the row-count divergence and it contributes spurious power-of-two values

## Summary

`gemma4_experts_forward_bf16` is the last kernel in the layer with row-count
structure, and it is the defect. Driven directly with a **fixed routing shared
byte-for-byte across both calls**, so the expert set and its weights are
identical and the only difference is the block width:

| routing | row | bit-equal | relative L2 | max absolute |
| --- | --- | --- | --- | --- |
| [0, 2] | 0 | **False** | 0.01793236 | **8192.0000** |
| [0, 2] | 1 | **False** | 0.01003062 | **2048.0000** |
| [1, 3] | 0 | **False** | 0.01754680 | **12288.0000** |
| [1, 3] | 1 | **False** | 0.01048195 | **1536.0000** |

Every comparison is row `i` of a two-row call against a one-row call on that
same row's own input. The fixture's router shape is `hidden=256,
num_experts=4, top_k=2`.

## The magnitudes are the evidence

The max absolute differences are **8192, 2048, 12288 and 1536** -- every one a
small integer times a power of two. A difference in summation order produces
values on the scale of the inputs; these are three to four orders of magnitude
larger, and they are round. That is the signature of a **spurious or stale
contribution entering the sum**, not of a reassociation.

It is also not a single bad row or a single bad expert set: it reproduces at
both rows and under two disjoint routings, with the relative error always in the
1 to 2 percent band.

This closes the chain. The expert forward diverges at rows=2 against rows=1, the
layer diverges by 0.8 and 0.4 percent with a random pre-layer input
(`20260928T055057`), and the model diverges at layer 0 by 0.63 percent
(`20260928T055010`). Six other kernels were cleared in isolation on the way, and
this is the one that was left.

## What this means beyond the divergence

**It is a correctness defect, not an arithmetic difference.** A spurious
8192-magnitude term in an expert sum is a wrong answer, not a different order of
the right one. The 1 to 2 percent aggregate relative error is what survives
after the layer's norms and residual scaling damp it.

**It affects prefill as much as decode.** Prefill runs this kernel at
`rows > 1` on every block, so prefill output quality is affected by the same
path, not only the speculative verify that led here.

**It explains the long-standing failing test.** `test_incremental_decode_matches_a_dense_prefill`
compares a dense prefill against one-token-at-a-time decode, which is exactly a
`rows > 1` expert call against `rows == 1` calls. Its failure has been attributed
to a MoE gate/up route selection; the gate/up flag was tested here and does not
fix it. This is the mechanism behind that failure.

## Where to look

The kernel's own docstring says the scratch is *"a capacity, not an identity:
the caller sizes it for the widest block it will run and then runs narrower
blocks through it."* The scratch here is sized for `tokens=64` while the calls
run 1 and 2 rows, so the candidate mechanisms are the ones that turn capacity
into work: the group-scatter's row accounting (`compact_rows`, `total_rows`), the
`gemma4_project_experts_grouped_row4` leaf that the census names, and any
padding row the grouped layout reads when the block is narrower than the scratch.

A stale or padded row read as a real one would produce exactly this: a large
round value from whatever the buffer held, scaled by the routing weight.

## Changes

None. This unit is a measurement.

## Validation

- Probe on the 8060S (gfx1151) calling `gemma4_experts_forward_bf16` directly
  with the layer scratch's own expert scratch and the fixture's expert
  projections, at rows=1 and rows=2, comparing row `i` against a one-row call on
  the same input. Exit 0.
- The routing arrays are uploaded once per call from the same host values, and
  row 0's hidden input is byte-identical across the two calls, so neither the
  expert set nor the input can explain the difference.
- Two disjoint routings and both rows are reported, so the result is not a
  single-sample artifact.
- The `max_abs` reading is a value comparison on the F32 expert output, not on
  BF16 bit patterns, so the round numbers are real magnitudes.

## Next

Fix the row accounting. The cheapest first probe is the grouped scatter: dump
`compact_rows` and `total_rows` for a two-row call and check them against the
2 rows and 4 expert slots the routing actually selects. A second candidate is
whether the tile-capacity bound (`total_rows > tile_capacity * 32`) is being
satisfied by a padded count rather than the real one.
