# a lane-per-key flash prefill attention is the port that removes gemma4's reduction

## Summary

gemma4's prefill attention is 19.1 percent of the 864 ms step (164.7 ms: 130.5
for the 25 sliding 256-wide layers and 34.2 for the five 512-wide ones) and runs
at 405-628 GFLOP/s against 3000 for the linear projections. The reduction is the
reason, and there is an in-tree kernel that has already solved it with the
opposite layout.

`hipengine/kernels/hip_gfx1100/attention/qwen4_exp_qsa_flash.hip` is described
in the catalog as "Flash-style dense prefill attention" and its own comment
states the design:

> Key-parallel layout: lane k owns key k. Per row: 256 serial-dim FMAs for the
> QK dot (no per-key shuffles); softmax max/sum use one butterfly per row; p
> values stage through LDS so the accumulation phase reads them by (row, key).
> Accumulators live in LDS and survive tiles with the online rescale.

**No per-key shuffles.** gemma4's kernel gives one warp to each key and reduces
32 lanes with five shuffles plus a broadcast, which is where its instruction
budget goes. The unroll landed this unit improved the 512-wide geometry by 15
percent by interleaving two of those chains, but it cannot remove them: at
head_dim 256 the per-key-per-lane count is roughly 30 instructions for 8 MACs,
about 27 percent of the one-MAC-per-instruction issue peak, and the reduction
tree is 12 of those 30.

This is a different framing in the sense `docs/ROOFLINE.md` §11 requires when it
says not to repeat a rejected approach unchanged. The rejected attempt was the
query tile, which traded occupancy for ILP and lost 20 percent. This changes who
owns a key, not how many rows a block holds.

## What the reference actually does

- `QSA_QT = 32` query rows per block, `QSA_KT = 32` KV keys per tile, 256
  threads, `__launch_bounds__(QSA_THREADS, 2)`.
- Q, K and V tiles staged in shared as BF16, 256 dims wide.
- One lane owns one key, so the QK dot is 256 serial FMAs per (row, key) with
  **no cross-lane reduction at all**. `ACC_CELLS = QSA_QT * 256 / QSA_THREADS`
  is 16, so each thread keeps 16 (row, dim) accumulators live in registers and
  the mapping is stable across tiles.
- Online softmax state (`m_run`, `l_run`, `rescale`) in shared, so the KV loop
  never needs the whole row's logits resident and never revisits a tile.
- Output is F32.

## What a gemma4 port needs beyond it

| requirement | QSA today | gemma4 needs |
| --- | --- | --- |
| head_dim | 256 hard-coded in the tile arrays | **256 and 512** |
| GQA | `q_heads / kv_heads` computed | 16/8 and 16/2 |
| sliding window | none | `gemma4_attn_first_kept(window, row_offset, token)` |
| eviction mask | none | the `KVLiveSpans` `evict_mask` row |
| KV dtype | BF16 gather | BF16 resident cache, already this |
| output | F32 | BF16 for the layer input |

The 512-wide head is the only structural change: the tile arrays are sized
`QSA_QT * 256`, and `ACC_CELLS` is derived from that 256. Both need to become
head_dim-parameterised, and the 512 case doubles the accumulator count per
thread unless `QSA_QT` halves.

## Where it plugs in

`hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention.py` registers the current
kernel as `KernelKey("hip_gfx1100", "prefill_attention", quant, "gemma4_plain")`.
The four-axis registry makes this a new variant rather than a branch: register
`gemma4_flash`, and let the attention dispatch select it by registry lookup.
That is the shape the invariants require, and it keeps `gemma4_plain` as the
strict owner for the parity tests and as the fallback the profile gate compares
against.

## Expected win, and its arithmetic status

Attention is 164.7 ms of 864. If the reduction really is the instruction cost,
removing it takes the kernel toward the FMA issue peak rather than 27 percent of
it -- the same class of gain the per-key-barrier removal already produced once
(147 -> 405-446 GFLOP/s, recorded in the kernel's own comment). A 2.5 to 3x
attention win is 110 ms, which is 13 percent of the step and would take the loop
metric from 0.876 to roughly 0.76.

**This is a reassociation, not a bit-identical change.** The QK dot becomes a
serial 256-FMA chain per lane instead of a 32-lane tree, so it cannot be the
strict owner and cannot land as the default on correctness alone. It is a
production candidate: it may reassociate during evaluation, and default
promotion requires the `docs/EXECUTION-PROFILES.md` gate. The strict owner stays
`gemma4_plain` and the existing geometry suites keep pinning it.

## Plan

1. Parameterise the QSA structure on head_dim (256 and 512) and write
   `gemma4_attention_flash.hip` with the sliding window and the eviction mask.
2. Register it as `gemma4_flash` under `("hip_gfx1100", "prefill_attention", quant)`.
3. Validate against `gemma4_plain` on the existing geometry suites, which already
   cover both head widths, GQA ratios, window values, and the narrowed-walk case.
4. Measure with `scripts/gemma4_attention_prefill_bench.py` at 512/1024/2048, then
   run the profile gate before any default flip.
