# the Q5_1 MMQ route lands on the expert down projection for 38 percent more prefill

## Summary

The previous entry recorded that the Q5_1 expert down projection is 43.4% of
gfx1151 prefill at 8.6 GB/s with no MMQ route, and named the fix: a partial
trailing block in the Q5_1 MMQ kernel and its DS4 activation pack. This unit
does it.

**Prefill 7.191 -> 5.213 s, 284.8 -> 392.9 tok/s (+38.0%).** The expert share
falls from **43.4% (3.087 s) to 11.0% (0.573 s)**. The down projection takes
`down_mmq32` on 116 of its 120 launches, and the grouped family falls from 120
launches to 4 -- the Q5_K and Q8_0 layers, which have their own routes.

## Changes

- `hipengine/kernels/hip_gfx1100/quant/gguf_q5_1_mmq_selected_prefill.hip`: the
  consumer rounds `ds4_blocks` up to `ceil(in_features/128)` and skips the Q5_1
  sub-blocks a trailing group does not have. `full_group` keeps the guard off the
  common path so the four-way unroll survives. The launcher's guard moves from
  `in_features % 128` to `in_features % QK5_1`.

- `hipengine/kernels/hip_gfx1100/quant/gguf_q4_k_q8_1_selected_prefill.hip`:
  `gguf_q8_1_mmq_ds4_pack_bf16_kernel` rounds `blocks_per_row` up and reads
  `0.0` past `hidden` for the trailing block. `valid_q8_1_mmq_ds4_pack` moves to
  `hidden % 32`.

- `hipengine/kernels/hip_gfx1100/quant/gguf_q4_k_q8_1_selected_prefill.py`: the
  two wrappers that route to `launch_q8_1_mmq_ds4_pack_bf16` relax to a 32-wide
  requirement. The `_f32` pack variants use a different kernel and keep 128.

- `hipengine/kernels/hip_gfx1100/quant/gguf_q5_1_mmq_selected_prefill.py`: a
  `_ds4_blocks` helper, `ds4_workspace_nbytes` sized from it, and the consumer
  wrapper's guard at 32.

- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_experts.py`:
  `gemma4_project_experts_down_mmq`, tried before the grouped family at the down
  call site; `gemma4_moe_down_mmq_enabled` with `HIPENGINE_GEMMA4_MOE_DOWN_MMQ`
  as the rollback lever; and `mmq_workspace` sized for
  `max(hidden_size, intermediate)` so the down's own width cannot overflow the
  buffer the gate_up sized.

- `tests/test_gpu_gguf_q5_1_mmq_selected_prefill.py`: parametrized over
  `in_features` 640 (the control, a multiple of 128) and **704** (the artifact's
  width). 704 raised `ValueError` before this change.

## Why the padding is exact

The elements past `hidden` are zero, and **a zero cannot raise a `max_abs` or
move a sum**, so the scale the real elements get is the one they would have got
without the padding. On the consumer side the skipped sub-blocks multiply
activation elements that do not exist, so their contribution is zero either way.
The change is a rounding-direction fix, not an approximation.

## Execution profile

The route quantizes activations to DS4 Q8_1 over `_MMQ_ACTIVATION_PASSES = 1`
plane -- the same plane count and the same envelope as the Q4_K gate_up route,
which already ships at one plane. Per `docs/EXECUTION-PROFILES.md` section 2.9 a
cell no retained row covers still runs, and this one is now covered at the kernel
level by the table above. Raising the plane count changes a production default's
arithmetic and still needs its own gate; that is unaddressed here.

## The finding that matters more than the speed

**The model does not generate coherent text on this branch.**

```
'The capital of France is' -> ' it is it is it is it is it is it is ...'
'2 + 2 ='                  -> ' 2 = 2 = 2 = 2 = 2 = 2 = ...'
'Hello'                    -> 'HelloHelloHelloHelloHelloHello ...'
```

Greedy token ids cycle `568, 609, 568, 609`. **This is pre-existing and identical
with the down MMQ route on and off**, so it is not a regression from this change
-- but it means the objective's premise, "we have a working Gemma 4 26B-A4B
implementation", does not hold for generation. `test_incremental_decode_matches_a_dense_prefill`
failing at `max abs diff 4.417` is very likely the same defect rather than an
unrelated test problem, which is how it was recorded earlier in this session.

The +38% figure is a **speed measurement on an implementation whose generation
path is broken**. It is a real measurement of a real route, and it is reported
here with that bound attached.

## Next

Find the generation defect. It is the highest-value work on this objective:
decode and prefill speed are already measured against a target, and llama.cpp's
1012.98 tok/s pp512 on this host is now within reach at 392.9, but a fast engine
that emits `HelloHelloHello` is not a working implementation.

The dense-prefill-versus-incremental-decode divergence is the most specific
signal available and is the place to start.
