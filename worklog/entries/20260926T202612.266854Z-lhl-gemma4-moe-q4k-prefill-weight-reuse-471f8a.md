# Gemma 4 Q4_K routed-expert prefill weight reuse

## Summary

The routed-expert prefill weight-reuse family landed for Q5_1 only, which left
the artifact's *larger* prefill projection on the per-lane path: attribution put
Q4_K gate/up at 53.40% of 512-token prefill kernel time against Q5_1 down's
31.40%. This unit registers the same grouped-prefill route for Q4_K, so both
expert projections now read each expert's weight matrix once per prefill block
instead of once per row.

Paired on one tree, one session, 512p/128o, `gguf_q4_k_gemv.{hip,py}` the only
difference between the arms: prefill **9.252 s -> 5.531 s (55.34 -> 92.57
tok/s, 1.673x)**, decode 21.08 -> 21.11 tok/s, public wall 15.340 -> 11.597 s,
identical greedy ids and `public_path_parity` true in both arms. Against the
session's pre-loop baseline of 11.617 s (44.07 tok/s), the loop's two weight-reuse
units together are **2.10x** on this shape.

## Changes

- `hipengine/kernels/hip_gfx1100/quant/gguf_q4_k_gemv.hip` (+134):
  `hipengine_gguf_q4_k_selected_grouped_prefill_compact_rowbatch8_bf16_bf16_out`,
  one block per (expert, out_col) walking that expert's rows.
- `hipengine/kernels/hip_gfx1100/quant/gguf_q4_k_gemv.py` (+66): launcher,
  `in_features % 256` / 8-column-tile validation, and registration under
  `(backend, moe_linear, gguf_q4_k, selected_grouped_prefill_compact_rowbatch8)`.
- `tests/test_unit_gemma4_expert_route.py`: the two GPU tests now run both
  quants through one helper and per-quant geometry tables, because Q4_K's block
  is 256 wide and cannot represent every shape Q5_1 can.

Q4_K's selected prefill reduces 128 lanes with `reduce_block_sum`, not the
256-wide shared tree the Q5_1 family uses. The grouped kernel therefore reduces
through that same tree at the same 128-thread k-stride, which is what keeps the
two bit-identical rather than merely close. That is also why the bit-exactness
test is the load-bearing correctness check here: a different-but-plausible
association would pass a tolerance check while moving every prefill logit.
