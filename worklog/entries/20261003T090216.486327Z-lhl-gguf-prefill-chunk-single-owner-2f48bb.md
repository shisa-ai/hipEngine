# GGUF prefill chunk resolution: one owner, explicit precedence, truthful record

## Summary

Fixes the dispatch defect recorded on 2026-10-03: `resolve_prefill_config_for_sequence`
is now the **single owner** of the final linear/MoE prefill chunk sizes, the
geometry policy and the architecture profile are inputs to it rather than
post-hoc rewrites, and `prefill_chunk_tuning["chunk_sizes"]` always describes the
config the call returned.

**What was broken.** `_gguf_prefill_chunk_sizes_for()` ran in the
`Qwen35GGUFResidentSession` constructor *after* the resolver and after any
explicit `PrefillConfig`, so on the H2048-MoE geometry an explicit
`PrefillConfig(linear_chunk_size=1024, moe_chunk_size=1024)` resolved to
effective `(512, 512)`, `--prefill-linear-chunk-size` /
`--prefill-moe-chunk-size` were silently ignored, and the recorded tuning said
1024/1024 while the session ran 512/512. Separately,
`_ARCH_CHUNK_PROFILES["gfx1151"]` (256/256) was unreachable on the GGUF path
because the runner never passed `target_arch`, while the PARO runner already did.

**The change.**

- `resolve_prefill_config_for_sequence` gains a keyword-only
  `geometry_chunk_sizes: tuple[int, int] | None` and documents the precedence:
  an explicit non-zero field on the incoming config wins outright; otherwise the
  geometry layer (model+quant keyed) is applied on top of the architecture layer
  (per-arch), which is applied on top of the shape/memory policy.
- The manual contract is preserved **all-or-nothing**, deliberately: an explicit
  chunk size returns the config untouched, so passing one manual size cannot
  silently change the arithmetic or the scratch headroom of the other stages.
  This is pinned by a test so the choice is visible rather than accidental.
- The tuning record always carries the effective `chunk_sizes`, plus
  `manual_chunk_sizes`, `base_chunk_sizes`, `arch_profile_applied`,
  `geometry_profile_applied`, and the winning layer's `reason`/`source` (the arch
  layer's own `reason`/`source` stay visible as `arch_reason`/`arch_source` when
  the geometry layer overrides it). The previously recorded `base_reason` and
  `base_source` keys are preserved.
- The runner passes `target_arch=self.runner.target_arch` and
  `geometry_chunk_sizes=_gguf_prefill_chunk_sizes_for(...)`, and the post-hoc
  `replace(...)` is deleted.

**Consequence for the H5120 dense lane, measured.** Wiring `target_arch` makes
the gfx1151 architecture profile live on the GGUF path, which changes the H5120
dense geometry from the 1024 default to the profile's 256. That is an
improvement, not a regression:

| linear/MoE chunk | 27B Q4_K_M, 4096 tokens, ms samples | median ms | tok/s | vs 256 |
| ---: | --- | ---: | ---: | ---: |
| **256** | 10270.9 / 10276.0 / 10277.2 | **10276** | **398.6** | - |
| 512 | 10322.1 / 10321.3 / 10307.2 | 10321 | 396.8 | -0.45% |
| 1024 | 10566.2 / 10575.4 / 10560.4 | 10566 | 387.7 | -2.73% |
| 2048 | 11446.6 / 11441.9 / 11437.2 | 11442 | 358.0 | -10.19% |

Monotonically decreasing with chunk size, so the profile's 256 is right for this
geometry and the lane gains **+2.8%** (387.7 -> 398.6 tok/s) against what it was
actually running.

**The H2048-MoE geometry is unchanged by this commit** (512/512 via the geometry
policy) and its own chunk value is promoted separately.

## Changes

- `hipengine/runtime/prefill.py`: resolver restructured around
  `_apply_chunk_policy` and `_geometry_profile_dict`; `_has_manual_chunk_sizes`
  replaced by `_manual_chunk_fields`; `_apply_arch_chunk_profile` removed.
- `hipengine/runtime/qwen35_gguf_runner.py`: single-owner call site; the
  `_gguf_prefill_chunk_sizes_for` docstring now describes it as a resolver input.
- `tests/test_unit_gguf_prefill_chunk_precedence.py` (new): 14 tests pinning the
  precedence order, the truthful record, the manual contract, the geometry/arch
  interaction, auto-tune-off, and the zero-entry cases.
- `docs/REFACTOR.md`: the chunk-override entry is superseded by this fix.

## Validation

`tests/test_unit_gguf_prefill_chunk_precedence.py` (14 new),
`tests/test_unit_gguf_prefill_chunk_row_cap.py`,
`tests/test_unit_qwen35_resident_batch_layout.py`,
`tests/test_unit_gguf_bulk_prefill_workspace_release.py` - **207 passed, 1
skipped**. The RED state was confirmed first: three of the new tests failed
against the unmodified resolver (the geometry layer overriding a manual request,
the per-field expectation, and the shape policy overwriting a manual field), and
two pre-existing tests in `test_unit_qwen35_resident_batch_layout.py` caught the
two contract details that had to be preserved (`tuned is manual` with reason
`manual_chunk_sizes`, and `base_reason`/`base_source`).

Resolution check on the real geometries, `max_sequence_length=4352`,
128 GiB host, `target_arch="gfx1151"`:

| geometry | geometry policy | resolved linear/moe | reason |
| --- | --- | --- | --- |
| H2048-MoE (35B-A3B) | (512, 512) | 512 / 512 | `geometry_prefill_chunk_policy` |
| H5120 dense (27B) | none | 256 / 256 | `gfx1151_paro_prefill_recovery` |

Blast radius: the resolver has exactly two callers.
`qwen35_paro_runner.py` already passed `target_arch` and passes no geometry
policy, so it is unaffected. `Qwen35GGUFResidentSession` on gfx1151 is the only
path whose behaviour changes, and `LagunaGGUFResidentSession` and the qwen4exp
(Flash Next) generator use different classes, so neither lane moves.

Host state for every measurement here: the `accelerator-performance` profile
active, `scaling_governor=performance`; the 27B sweep used the shipping AR route,
3 s settle before each timed prefill, one session per size with `reset()` between
repetitions, 3 repetitions per size.

## Next

- Promote the H2048-MoE geometry policy value. The 4K matrix measured
  256 = 1363.7, 512 = 1459.3, 1024 = 1487.7, 2048 = 1459.3, **4096 = 1503.9**
  tok/s, so the shipping 512 is second-worst and a larger chunk is worth
  +2.0% (1024) to +3.1% (4096). A shape sweep at 1K/16K/64K is running to decide
  between them, because a 4096-row linear/MoE chunk changes how many chunks a
  long prompt is cut into.
- **Corrects an earlier figure.** The 2026-10-03 `+6.40%` for 1024 over 512 was
  measured with an explicit `PrefillConfig`, which under the manual contract
  left `full_attn_query_chunk_size` at 0 (full attention unchunked) - a
  confound that inflated the delta. On the production config shape the 512 -> 1024
  delta is **+1.95%** (2807 -> 2753 ms), and the correct comparison is the matrix
  above.
- The published H5120 gfx1151 lane uses `Qwen3.8-27B-UD-Q4_K_S.gguf`, which this
  tree cannot materialize (`unsupported Qwen3.5 GGUF tensor type 'Q3_K' ...
  token_embd.weight`), so the 27B evidence here is the same geometry and backend
  on `Qwen3.8-27B-Q4_K_M.gguf`. The UD-Q4_K_S lane's own chunk value is
  **unverified**.

## Limits

One host, one prompt shape (4096) for the chunk matrix, one route, one file per
geometry. The 27B evidence is on a different file from the published H5120 lane.
No correctness gate has been run yet for either geometry's chunk change - the
arithmetic changes with chunk boundaries, so the applicable
`docs/EXECUTION-PROFILES.md` gate is still owed before either value is treated
as retained.
