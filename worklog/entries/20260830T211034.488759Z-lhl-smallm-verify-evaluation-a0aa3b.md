# smallm measured 1.5x over single-wave at rows 2-16 but verifier scope uses rowtile

## Summary

Task #9 asked whether `smallm` can replace the shared-B 256-row tile for ragged MTP verify cycles. Measured:
on `(rows, 5120, 17408)` it is **bit-identical (ULP 0)** to the strict owner at every row 2-16 and
**2.07x-2.31x faster than shared-B**, which is more than the promoted single-wave band achieves. Against the
**current** owner it is still **1.52x-1.62x faster** (0.300 ms vs 0.458 ms at row 12). It is not promotable
yet, for a reason the sweep exposed rather than a numerical one: the rows that MTP verify cycles actually run
are not routed through the leaf this measurement covers.

`smallm` rejects rows above 16 by contract (`ValueError: small-M Q4T16 WMMA requires rows <= 16`), so it is a
decode/verify-band kernel only.

Why this does not promote: `hipengine/runtime/gguf_linear.py:2746` ranks the verifier and native-batch-decode
rows through `_q4_t16_sidecar_decode_variants`, which returns `dense_rowtile_col4_bf16_bf16_out` /
`dense_rowtile_bf16_bf16_out` for `2 <= rows <= 8` and nothing above 8, gated by
`_Q4_T16_DENSE_ROWTILE_MAX_ROWS_BY_QUANT = {gguf_q4_k_t16_v1: 8, gguf_q4_k_qmicro_t16_v1: 4}`. So MTP verify
rows 2-8 are owned by `dense_rowtile`, a kernel this sweep never measured - what I measured under the name
`rows6_rowtile` is the prefill dispatcher `gguf_q4_k_t16_physical_c1_rowtile_gfx1100_bf16_bf16_out`, which
falls through to single-wave above row 6. Claiming 1.53x for the MTP cycle on this evidence would be exactly
the source-reading substitution this campaign has been correcting all session.

## Next

- Blocking measurement: sweep `dense_rowtile_bf16_bf16_out` (and `dense_rowtile_col4` for rows <= 4) at
  `(rows, 5120, 17408)` for rows 2-8 against `smallm`, in the verifier-scope selection order, and record ULP.
  smallm only displaces anything if it beats `dense_rowtile`, not shared-B.
- Second gap: rows 2-16 outside verifier scope on the prefill dispatcher are only short-prompt admissions,
  which this suite does not produce (35-67 tokens). If a future workload admits 2-16 token prompts, the
  measured smallm band is pre-registered here.
- rows 9-16 remain the interesting region: single-wave owns them today at ~0.46 ms and smallm measures
  0.300 ms there, but no production route reaches rows 9-16 through the prefill dispatcher for this suite.
