# Q5T16 verifier rowtile: a single-wave owner with the four-wave parent kept as the parity contract

## Summary

The Q5T16 verifier rows-2-8 rowtile moves to a single-wave eight-column owner:
on the verifier the Q5_K family falls **11.75 -> 7.98 ms/step (-32%)** and the
whole-kernel step **40.9 -> 38.4 ms/step**, which shows up end-to-end as
**UD-Q4_K_M MTP b3 46.192 -> 49.409 tok/s (+6.96%)** and MTP/AR
**1.4476 -> 1.5487x** at an unchanged AR denominator (31.909 -> 31.904,
-0.02%). The two plain (non-UD) control arms move +1.16% and +0.41% over the
same interval, so the change is Q5_K-specific.

The first form of this change rebound `t16_gemv_rowtile_bf16_bf16_out` itself,
which broke a declared parent-parity relation with the grouped rows6/rows8
owners. The retained form keeps that entry point as the four-wave parity parent
and selects the single-wave variant through a backend policy instead.

## Changes

Add `q5_k_t16_dense_rowtile_single_wave_gemv_kernel` and select it as the
Q5T16 verifier rows-2-8 rowtile owner through the backend capability
`GGUF_T16_NATIVE_ROWTILE_SINGLE_WAVE_BY_QUANT`, leaving
`t16_gemv_rowtile_bf16_bf16_out` bound to the four-wave WG128 owner.


### Why the four-wave parent stays bound

The first form of this change rebound `t16_gemv_rowtile_bf16_bf16_out`
itself to the single-wave body. `tests/test_gguf_t16_selected_gemv_decode.py`
caught it immediately: `test_q5_t16_grouped_rows6_matches_repeated_rows6_bits[24]`
and `[36]` assert that the grouped rows6/rows8 owners are bit-identical to the
same entry point applied to six-row chunks. The grouped owners are a
different launch-ownership shape (grid.y chunks) of the *same* four-wave
arithmetic, so rebinding the entry point silently broke a declared
parent-parity relation. That is a contract, not an implementation detail, so
the fix is a policy selection instead:

- `t16_gemv_rowtile_bf16_bf16_out` stays the four-wave WG128 parent-parity
  owner and keeps the grouped rows6/rows8 parity relation intact.
- `t16_gemv_rowtile_single_wave_bf16_bf16_out` is a separately registered
  production-profile variant.
- `_t16_native_rowtile_variant()` in `hipengine/runtime/gguf_linear.py` picks
  the production owner by quant, honouring an env switch
  (`HIPENGINE_GGUF_Q5_T16_ROWTILE_SINGLE_WAVE`) for rollback and bisection.


### Geometry

The four-wave owner runs WG128 as four wave32 waves and sums the four partial
vectors through shared memory. The single-wave owner runs one wave32 per
output block over eight columns: each lane owns eight contiguous `k` inside
the 256-element block, so the subblock `d`/`dmin`/`scale`/`min` decode hoists
out of the inner loop, and the block needs no shared-memory cross-wave
exchange or `__syncthreads()`. This is the Q4_K rowtile geometry already
retained for that quant.

policy switch is the only selector.

### Paired end-to-end suite (`scripts/ud_mtp_paired.py --runs 2`)

Same host, same GPU, same protocol, same prompt suite; the plain (non-UD)
arms are the negative control because this change only touches Q5_K weights.

| arm | true AR tok/s | MTP b3 tok/s | ratio | prev MTP | delta |
| --- | --- | --- | --- | --- | --- |
| ud-q4-k-m | 31.904 | 49.409 | 1.5487 | 46.192 | +6.96% |
| ud-q4-k-s | 30.428 | 46.955 | 1.5432 | 47.023 | -0.14% |
| plain-q4-k-m | 37.313 | 63.885 | 1.7121 | 63.153 | +1.16% |
| plain-q4-k-s | 39.774 | 66.709 | 1.6772 | 66.437 | +0.41% |

The UD-Q4_K_M arm gains 6.96% end-to-end at an unchanged AR denominator
(31.909 -> 31.904, -0.02%), so the ratio gain is the kernel gain and not a
denominator shift. The two plain arms move +1.16% / +0.41%, which is the
session noise floor and confirms the change is Q5_K-specific.

### Test-side fallout

Selecting the single-wave owner by policy changed which registered variant the
native-batch-decode and target-verifier routes resolve to, which exposed two
test defects that register a fake kernel only for the four-wave name and then
call `launch_gguf_linear` with placeholder pointers:

- `tests/test_gguf_gemv_decode_dispatch.py`: `_Q5_T16_ROWTILE` was the only
  faked Q5T16 rowtile, so the rows 5-8 route now reached the real kernel with
  `x_ptr=100`/`out_ptr=200` and segfaulted. Fixed by adding
  `_Q5_T16_ROWTILE_SINGLE_WAVE` to the faked set, asserting it in the rows 5-8
  test, and adding `test_native_batch_decode_q5_t16_single_wave_kill_switch`
  for the env rollback. File passes in full (24 tests).
- `tests/test_gguf_linear_dispatch.py::test_q5_t16_routes_decode_bounded_native_rowtile_and_dense_wmma`:
  this node segfaulted at HEAD before this unit, because it faked
  `t16_gemv_decode_bf16_bf16_out` while the rows == 1 `(6144, 5120)` route
  resolves to `dense_single_local32_bf16_bf16_out` through
  `GGUF_T16_C1_VARIANTS_BY_QUANT_SHAPE`. Faking the leaf the route actually
  selects, and the single-wave rowtile, makes the node pass; it is the same
  "fake-kernel override is bypassed" defect recorded on 2026-09-12. Fixing it
  reveals the next node in that file,
  `test_launch_q6_raw_wmma_prefill_uses_resident_raw_abi`, which is the
  already-recorded known defect and is unrelated to this change. With that
  node deselected the file passes in full.
