# the prefill kernel re-reads k and v 1536 times because a block holds one query row and one head

## Summary

The tiled variant fixed occupancy at long context (`20260928T074732`) but **does not move the
2048-token case**, which is what requirement 4 is measured on. Working out where the 2048-token
time goes found a different and much larger structural problem: **the kernel's grid is
`tokens x num_heads`, so every key's K and V are re-read once per (token, head) pair that needs
them -- 1536 times at this geometry.** Tiling over query rows instead of keys is the standard
remedy and it is a much bigger lever than anything tried so far.

## The arithmetic

Grid is `tokens * num_heads` = 2048 x 16 = **32768 blocks**, one block per (token, head). Each
block reads K and V for its whole key range. At the artifact's `16q/8kv`, `head_dim 256`,
`window 1024`:

| | |
|---|---|
| K + V read | **25.78 GB** |
| unique K/V (one pass over kv_head x key) | **16.78 MB** |
| **redundancy** | **1536x** |

The redundancy has two sources:

- **GQA: 2x** -- `16q/8kv` means two query heads share each kv head, so each K/V row is read
  twice for that reason alone.
- **query rows: ~768x** -- every query row walks its own key range and each key in it is read
  separately by each of the ~1024 rows whose window covers it.

**A block holds exactly one query row and one head, so there is no reuse at all across either.**

## What the measurement says about the limit

Measured strict time is **56.70 ms** for that shape. 25.78 GB / 56.70 ms = **454 GB/s**.

**That is above the ~256 GB/s LPDDR5X figure for this part, so L2 is serving a large share of
it.** The kernel is therefore not purely DRAM-bound -- but **454 GB/s of L2 traffic with compute
at 1.7% of peak (0.455 TFLOP/s of ~26.6) is consistent with a kernel that is bound by moving
K and V rather than by arithmetic.**

**One data point argues against pure bandwidth being the whole story:** `dense 256d keys=2048`
takes **116.30 ms** against the swa case's **56.70 ms**, a **2.05x** ratio for a walk-length
ratio of about **1.14x** (2048 keys per row dense versus ~1792 swa, since `first_kept` only
trims the tail rows). **Superlinear in key count is not what a purely bandwidth-bound kernel
does.** So there is at least one other effect, and it is probably the same three-pass LDS
dependency `20260928T073550` identified.

## The lever

**A block that holds R query rows reads each key once for all R of them.** Projected K+V
traffic, at the artifact's geometry:

| R | redundancy | K + V | at 256 GB/s |
|---|---|---|---|
| 1 (today) | 1536x | 25.78 GB | 100.7 ms |
| 8 | 192x | 3.22 GB | 12.6 ms |
| 32 | 48x | 0.81 GB | 3.1 ms |
| 64 | 24x | 0.40 GB | 1.6 ms |

**These projections are optimistic and should be read as directions, not predictions**: the
measured R=1 point already exceeds the DRAM figure by 1.8x because L2 is absorbing traffic, so
the real curve will flatten well before 1.6 ms. **But the direction is not in doubt, and neither
is the size of the reduction available.**

## Why this is the right frame

**This is the structure the Laguna flash-attention prefill kernel already has** --
`TILE_COLUMNS = QUERY_ROWS * GQA_HEADS` (`20260928T073848`). **Its first constant is the thing
this kernel lacks.** `20260928T073848` proposed porting that kernel for its online-softmax
tiling; **the query-row dimension is the more important half of it, and it is the half that
addresses the measured 2048-token case rather than long context.**

**It also explains the gap to llama.cpp without invoking anything exotic.** llama.cpp's
flash-attention prefill tiles over query rows, so it reads K and V once per tile; this kernel
reads them once per (row, head). **The 1.74x end-to-end gap and the 1.6%-of-peak figure are both
consistent with that difference, and neither requires the three-pass LDS story to be the
primary cause.**

## Scope

**All of this is arithmetic on measured times and known geometry**, plus the one measured
ratio above. No query-row kernel has been written or run. **The redundancy figure is a count of
bytes the grid implies, not a profiler measurement** -- L2 is demonstrably absorbing some of it,
so the effective redundancy is lower than 1536x by an unknown factor.
