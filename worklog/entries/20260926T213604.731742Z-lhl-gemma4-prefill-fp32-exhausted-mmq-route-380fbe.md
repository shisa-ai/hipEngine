# Gemma 4 prefill: fp32 expert kernels are at their instruction limit; MMQ route is the remaining lever

## Summary

The last bit-exact avenue on the fp32 expert kernels is closed by measurement, and
the reason the remaining gap exists is now identified with a named next unit.

**Register hoisting does nothing.** The staged kernel already holds the activations
in registers across the output-tile loop, and making the alternative explicit
changes nothing: at (in 2816, out 1408, 128 experts, 4096 compact rows) the
register-x form measures 35.51 ms and the shared-x form 35.68 ms, both bit-identical
to the incumbent (0 differing outputs). The compiler had already hoisted it. The
kernel is bound by the per-weight-element instruction stream - the dequant is ~6
operations per weight element and the FMA one per (weight, row) - not by shared
memory, and the earlier isolation put 30 of 49 ms in that dequant. It cannot be
reduced further without changing arithmetic.

## Changes

No production code changed. The measurements and the identified next unit are
recorded below so the port has its constraints and open questions written down.

## Why the gap exists

Gemma 4's prefill runs **raw fp32-dequant kernels for every quant it uses**, while
this tree already contains int8-dp4a MMQ and dequant-to-16-bit routes for the same
quants, and those are what the fast MoE path uses:

| Gemma 4 quant | kernel Gemma 4 runs | in-tree alternative |
| --- | --- | --- |
| Q4_K gate/up | `gguf_q4_k_selected_grouped_prefill` (staged), 58 launches x 40.7 ms | `gguf_q4_k_selected_dual_q8_1_ds4_mmq32_prefill_compact32_bf16_bf16_out` (dual, gate+up in one launch, int8 dp4a) |
| Q5_1 down | `q5_1_selected_grouped_prefill`, 58 x 43.7 ms | `gguf_q5_1_mmq_ds4_selected_prefill_bf16_bf16_out` (needs `ffn % 128 == 0`; Gemma 4's 704 does not qualify) |
| Q8_0 dense | `gguf_q8_0_exact_prefill_tiled_out`, 410 x 3.4 ms | `gguf_q8_0_mmq128_*` (f32/f32 only today), `gguf_q8_0_t16_v1` wmma |

Qwen3.6-35B-A3B is a Q4_K MoE with a comparable active-parameter count and measures
1418 prefill tok/s on this host against Gemma 4's 121 - and its runner
(`qwen35_gguf_runner`) imports the Q4_K Q8_1 selected prefill. That is the
mechanism behind the gap, not a micro-optimization difference.

## The named next unit

Wire the Q4_K gate/up projection to the dual MMQ kernel. Its constraints are
satisfied by Gemma 4's geometry: `in_features % 128 == 0` (2816), `out % 32 == 0`
(704 for both gate and up), and the ABI is the same expert-start layout the route
already builds. The plumbing is three existing pieces:

1. `gguf_q8_1_mmq_ds4_pack_bf16` (d4x3) to quantize the layer's activations into a
   workspace of `compact_capacity * (hidden // 128) * 144` bytes.
2. `qwen35_moe_mmq32_tile_map(expert_start_compact, mmq_expert_start, tile_expert,
   mmq_total, num_experts, tile_capacity=...)` to build the 32-row tile map.
3. The dual MMQ launch, which takes gate and up in one call.

Open questions to settle first, in a scratch harness rather than in production: what
`mmq_total_rows` the launcher needs when expert starts are produced on device (a
safe upper bound is `32 * (ceil(compact/32) + num_experts)` if the kernel skips
empty tiles), and the numeric distance of Q8_1 activation quantization from the raw
path - this changes arithmetic, so it needs the production execution-profile gate
rather than bit-exactness.

The Q5_1 down projection (30.1% of prefill) has no qualifying MMQ variant at
`ffn = 704`; its options are a tail-handling MMQ variant or leaving it on the fp32
path, which is already at its limit.
