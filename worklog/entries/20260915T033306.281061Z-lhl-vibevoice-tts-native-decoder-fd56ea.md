# VibeVoice-TTS: the native acoustic decoder is a different topology, not this checkpoint's

## Summary

I corrected the document's "the acoustic waveform decoder must be built new"
claim during the environment work, and the replacement I wrote was **also wrong**.
I claimed transformers 5.15.0's native `VibeVoiceAcousticTokenizerModel` /
`...DecoderModel` match the checkpoint because they share `vae_dim` 64 and
`decoder_ratios [8,5,5,4,2,2]`. They do share those values, and the networks are
still different.

Measured: building the native decoder from
`microsoft/VibeVoice-1.5B`'s `acoustic_tokenizer_config` produces a
**175,793,409-parameter** network with decoder stage counts
`[3, 3, 3, 3, 3, 3, 8]`. The checkpoint's decoder is **343,695,969 parameters**
with `[8, 3, 3, 3, 3, 3, 3]`. The two groupings are reversed, so the checkpoint's
decoder weights cannot be loaded into the native module.

The reason is that they are **different checkpoints**. transformers 5.15.0
implements the `vibevoice/VibeVoice-1.5B-hf` conversion, not the
`microsoft/VibeVoice-1.5B` original this lane uses. The fork's own README records
the split ("VibeVoice is part of Transformers ... Check the model cards
(1.5B-hf ...)"). The `-hf` weight index uses the native naming
(`model.audio_tower.decoder.conv_layers.N.stage.M`), which is exactly the
structure the native class builds.

The net effect on the port: the decoder still has to be built against the
original's weights. What changes is that the native implementation is now known
to be a reference for streaming and padding-cache mechanics rather than a
drop-in, and a matching `vae_dim` or `decoder_ratios` is not evidence of
equivalence.

## Changes

- `docs/MODEL-VIBEVOICE-TTS.md`: the acoustic-decoder paragraph is rewritten with
  the measured comparison table, and the "Oracle environment" section no longer
  says that sharing a `model_type` means sharing an architecture.

## Validation

- Checkpoint decoder, from the safetensors index and headers: 276 tensors,
  343,695,969 parameters, stage counts `[8,3,3,3,3,3,3]` over channels
  `[2048,1024,512,256,128,64,32]`, key shapes `stages.N.M` / `upsample_layers.N`.
- Native `VibeVoiceAcousticTokenizerDecoderModel` built from the same
  `acoustic_tokenizer_config`: 276 tensors, 175,793,409 parameters, stage counts
  `[3,3,3,3,3,3,8]`, key shapes `stem.stage.N` / `conv_layers.N.stage.M` /
  `conv_layers.N.convtr`.
- Native `forward` signature is `(hidden_states, padding_cache=None,
  use_cache=False, **kwargs)`, confirming the streaming contract the doc cites.
- Forcing `decoder_depths="8-3-3-3-3-3-3"` on the native config changes nothing
  (still 175,793,409 / `[3,3,3,3,3,3,8]`): the native module ignores
  `decoder_depths` and uses `depths`, which the config derives from
  `encoder_depths`.
- The fork derives decoder depths as `reversed(encoder_depths)` when
  `decoder_depths` is null (`modular_vibevoice_tokenizer.py:1024-1028`), turning
  `"3-3-3-3-3-3-8"` into `[8,3,3,3,3,3,3]`, which is what reproduces the
  checkpoint's shapes.
- `vibevoice/VibeVoice-1.5B-hf` config and weight index, fetched from HF: the
  config stores `depths: [3,3,3,3,3,3,8]` directly under `audio_config`, and the
  index names the decoder `model.audio_tower.decoder.conv_layers.N...`, matching
  the native structure rather than the checkpoint's.
- transformers 5.15.0 exports exactly two VibeVoice families,
  `vibevoice_acoustic_tokenizer` and `vibevoice_asr`. There is no VibeVoice
  causal-LM or diffusion head. The `Diffusion*` symbols it exports are
  `DiffusionGemma`.

## Notes

- The near-miss is worth naming: `vae_dim` and `decoder_ratios` matched, the
  tensor *count* matched (276 both sides), and the `convtr`/`conv`/`head` kernel
  shapes matched exactly. Only the stage *distribution* differed. A check that
  stopped at the tensor count or at any single matching shape would have
  concluded equivalence. Comparing parameter totals and per-group stage counts is
  what exposed it.
- The `-hf` conversion also renames `speech_scaling_factor` /
  `speech_bias_factor` to `latent_scaling_factor` / `latent_bias_factor`. Anyone
  moving between the two checkpoints has to remap those two keys as well.
- This supersedes the decoder half of
  `worklog/entries/20260915T025539.131560Z-lhl-vibevoice-tts-oracle-env-9fbede.md`,
  which recorded the claim as a finding. The diffusion-head half of that entry
  ("exists only in the fork") is re-verified above and stands.
- Not verified: whether the `-hf` decoder produces equivalent audio quality. It
  is a different network, so that is a separate question and not one this lane
  needs answered.
