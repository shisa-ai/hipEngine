# Land M2: Gemma4Runner.forward exposes every row's post-output_norm h

## Summary

Punchlist M2 asks for `h` -- the post-`output_norm` hidden state of every
verified row, llama.cpp's `t_h_nextn` -- exported from `Gemma4Runner.forward`,
which previously normalized only the last row into a single-row buffer. The
runner now takes `return_hidden: bool = False`: when set, the final block's
norm runs over **all** its rows instead of one, the states stay device-resident
for a multi-row lm_head to consume without recomputing, and
`normalized_hidden` / `normalized_hidden_rows` expose them. The default path
is untouched -- same kernel call, same single row, same projection input.

## Changes

- `hipengine/runtime/gemma4.py` -- `forward(return_hidden=...)` threaded
  through `_forward_block` into `_forward_block_inner`; `_normalized` grown
  from one row to the whole block (2.9 MB at 512x2816 against 25 GB in use);
  the norm now takes `rows` from the branch instead of a hard-coded `1`, and
  the projection reads `base + (norm_rows - 1) * stride` -- which is the base
  itself when `norm_rows == 1`, i.e. byte-for-byte the old address. Two new
  properties, a `_normalized_hidden_rows` field, and `reset()` invalidating it.
- `tests/test_live_gemma4_forward_hidden.py` -- one live test behind a HIP +
  artifact guard.

## Validation

- `pytest tests/test_live_gemma4_forward_hidden.py -q` -- **1 passed** (5.37 s).
  The oracle is byte-level: path A (default) copies the single normalized row
  out, path B (after `reset()`) copies all four, and the last row of B must
  equal A's only row via `assert_array_equal`, with the logits compared too.
  It also asserts the row count across a one-token step (1), across a default
  call (0, so nothing claims stale rows), and after `reset()`.

### A harness interaction worth knowing about

The test was first written as two functions and the second failed with
`MissingKernelError: linear/gguf_q5_1/gemv_bf16_bf16_out`. It passed when run
alone, and passed in a bare script doing the same two sequences -- which
localized it to `tests/conftest.py`: an autouse fixture restores the kernel
registry to a **collection-time snapshot after every test**, dropping kernels
the model load registered lazily, and the next load inside the same module
cannot resolve them. Production never restores the registry, so this is a
harness artefact and not a product defect; the test was merged into one
function rather than depending on either behaviour. Whoever owns
`tests/conftest.py` may want the restore to preserve lazily-registered
entries; that is not this unit's call.
