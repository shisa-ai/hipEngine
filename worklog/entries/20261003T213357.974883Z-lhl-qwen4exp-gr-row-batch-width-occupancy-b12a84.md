# GR up row-batch widening beyond 4 is dead by occupancy, not by weight traffic

## Summary

The largest single kernel in a `code-p4096` prefill is the fused GR up composite
(`q8_0_gr_up_sigmoid_mean_coltile2_branch4_rowbatch4_f32`, 2507 ms, 15.5% of the
kernel union). Its recorded cost attribution reads it as weight-bandwidth-bound
with **90.3% of its traffic in a 256x re-read** of the 3.48 MB packed Q8_0 weight,
so halving that re-read looks like the reachable bit-exact win. The ledger's
tried-registry already records two rejections in the *constant-accumulator* form
of that lever (RB8/H1 0.848x, RB2/H4 1.005x, both 2026-09-06), which traded weight
decodes for activation loads.

This entry closes the untried form: **`ROW_BATCH` 8 with `HIDDEN_TILE` 2**, which
keeps every operand load count per FMA at the parent's and only halves the weight
decodes per output (8 decodes per k-step per thread for 64 FMAs instead of 32),
plus `ROW_BATCH` 16 as the trend point.

**Both lose, and the mechanism is measured:**

| arm | VGPR | waves/CU | occupancy | speedup vs production RB4/HT2 (rows 512 / 1024) |
| --- | ---: | ---: | ---: | --- |
| RB4/HT2 (parent) | 72 | 28 | 87.5% | 1.000 |
| RB8/HT2 | **130** | **15** | **46.9%** | **0.833-0.844x** |
| RB16/HT2 | **256** | **8** | **25.0%** | **0.430-0.437x** |

Every arm is **bit-identical** to the parent (`gate` and `mixed` compared as raw
`uint32` bits on real weights, 32 case rows, twice per case), so this is a pure
retile comparison. No arm spills (scratch 0), so the loss is occupancy, not spill
traffic: `acc[ROW_BATCH][4][2]` is 32 → 64 → 128 float accumulators per thread,
and 130 VGPR crosses the 128-VGPR granule.

**The negative also refutes the traffic model that motivated it.** Halving the
re-read is 16% slower and quartering it is 2.3x slower; a DRAM-bandwidth-bound
kernel cannot do that. Together with `HC-3`'s dead-store result (removing 4.2% of
the modelled traffic is a 2% *regression*) the consistent reading is that the
re-read is cache-served, the kernel is latency-bound at 87.5% occupancy, and its
real cost is the per-output structure - the 128-way reduction tree per output, the
per-row-batch decode, and a 2.5-iteration K loop. That is the structure `HC-1`'s
LDS-staged tile removes (2.388x, rejected on numerics), so this does not reopen
`HC-1`; it corrects why that route wins, which matters for how it is ever
re-argued.

No default, flag, dispatch or production path changed. Nothing promoted.

## Changes

- `hipengine/kernels/hip_gfx1100/quant/gguf_k_gemv.hip` - `ROW_BATCH` promoted from
  a `constexpr` to a third template parameter of the fused GR up kernel body
  (default 4, so every existing instantiation and symbol is unchanged) with the
  measured negative recorded in the comment; three candidate exports added
  (`rowbatch8_f32`, `rowbatch8_wave_scale_f32`, `rowbatch16_wave_scale_f32`). The
  launcher takes the same parameter and derives its grid from it.
- `hipengine/kernels/hip_gfx1100/quant/gguf_k_gemv.py` - `_row_batch` on the
  wrapper (validated to 4/8/16; `no_gate` stays 4-only), three thin wrappers. **The
  retile is deliberately NOT registered**: a registry key would make a measured-dead
  path reachable from dispatch, so no key was added and a test scans the whole
  registry to prove none resolves to a widened wrapper. The exports stay because the
  screen names them and a wider-register-file machine class may want to re-measure;
  `docs/REFACTOR.md` carries the removal condition.
- `tests/test_gpu_qwen4exp_gr_row_batch8.py` - RED/GREEN for the parameterization:
  rejection tests for an unknown width and for `no_gate` at a widened width, a
  whole-registry scan proving the widened wrappers are unreachable from dispatch, and
  bit-exactness of all three candidates against both parents at eight shapes
  including `rows` 1021 and 1024 (tail masking) and `h=6/18` (hidden tail). The
  bit-exactness test also instruments `_cached_fn` to assert that each call resolved
  its **own** symbol, which is what makes the comparison evidence rather than two
  calls to one kernel.
- `scripts/qwen4exp_q8_wave_scale_screen.py` - `--gr-parent` and `--gr-candidate`
  symbol overrides, so the GR composite arms can be named instead of being pinned
  to the test module's constants. Needed to compare the candidates against the
  production *wave-scale* parent rather than the plain one.
- `benchmarks/results/2026-10-04-qwen4exp-gr-row-batch-width/` - the four screen
  artifacts, the filtered register census, and the README with the tables,
  mechanism, limits and reproduction commands.
- `docs/QWEN4EXP-OPTIMIZATION-LEDGER.md` - §7D's row-reuse row extended with this
  measurement and mechanism; `HC-1`'s opportunity cell corrected so its 2.388x is
  no longer justified by a weight-traffic saving.
- `benchmarks/CHANGELOG.md` - dated entry.

## Validation

- `tests/test_gpu_qwen4exp_gr_row_batch8.py`: 11 passed (2 rejection tests, 1
  whole-registry reachability scan, 8 shapes x 3 candidates x 2 repeats).
- Engagement verified independently of the test: each wrapper was instrumented
  through `_cached_fn` and resolves its own distinct symbol
  (`rowbatch4_f32`, `rowbatch4_wave_scale_f32`, `rowbatch8_f32`,
  `rowbatch8_wave_scale_f32`, `rowbatch16_wave_scale_f32`), so the bit-exactness
  comparison is not two calls to one kernel. This is the `DP-8` `INVALID.md`
  failure mode and it was checked for rather than assumed.
- Screen: `scripts/qwen4exp_q8_wave_scale_screen.py --gr-composite`, 20
  order-balanced pairs per case, `rows` 512 and 1024, `K=320`, `N=10240`, two real
  Q8_0 tensors (`blk.0.hc_attn_up.weight`, `blk.0.hc_ffn_up.weight`), both against
  the production wave-scale parent and against the plain parent. Parent medians
  reproduce the recorded production shape (6.35-6.39 ms at rows=1024 against the
  attribution's 6.529 ms).
- Register census: `scripts/qwen4exp_repair_register_census.py --source
  hipengine/kernels/hip_gfx1100/quant/gguf_k_gemv.hip --threads-per-block 128`.
  VGPR 72/72/72/130/130/256 for the six GR instantiations, scratch 0 in the
  screen's resource record.

## Next

- The GR up composite has no remaining bit-exact lever. Its largest single
  measured cost is the per-output reduction structure, and the route that removes
  it (`HC-1`, staged f32, 2.388x) is rejected by the production numerical gate -
  not by anything this packet changes.
- The widened exports are retained as the record and as a checked starting point for
  a re-measurement; `docs/REFACTOR.md` carries the condition for removing them.
- Reopen the width lever only on a different machine class where 130 VGPR still
  buys the full 32 waves/CU (a larger register file per CU at the same wave
  ceiling), or together with a body change that lowers the accumulator cost.
- The next prefill item with a measured, promotable win is RT-1's chunk 4096
  (-5.74% prefill wall through the engine loop, peer-fairness free, +10.63 GiB peak
  at c2 native context). Its recorded binding point is
  `qwen4_exp_profiles._bind_default_chunk`, and the ledger's own prescription is a
  capacity guard keyed on the admitted context rather than a blanket flip.
