# DE-5 closes: the loop-start transient is a host CPU clock clamp, not engine host code

## Summary

DE-5's last open item was the reproducible per-prefill transient: every decode
loop that follows a prefill spends its first ~30 steps far above the
steady-state step time (~1.5-1.9 s of extra wall), and a 5 s idle between the
prefill and the decode removes it at a net cost of +3.3 s. The remaining
candidates were named as "a graph cache, a residency or page-table effect, or
allocation churn", and the churn probe was void because it used
`runtime.memory_info()`, which returns `None` on this runtime.

**The mechanism is a host CPU package clock clamp.** Every post-prefill decode
runs its first ~2 s with all 32 cores pinned at the **2.0 GHz base clock**; the
warmup decode of the same loop reaches 5.09-5.12 GHz within ~0.7 s (it starts
at 3.2-3.5 GHz) and steps at a flat 52 ms. How deep the decode starts tracks how
much of the prefill ran clamped, not the prefill's length: the warmups' prefills
are clamped for 0.65-0.78 of their samples and their decodes start at 3.2-3.5 GHz
with 57-60 ms steps, while the repeats' prefills are clamped for 0.97-0.98 and
their decodes start at exactly 2000 MHz with 162 ms steps. The step time tracks the
clock, not the work:

| loop | step ms by eighth | max CPU core MHz by sixteenth |
| --- | --- | --- |
| warmup | 59.5 52.7 52.4 52.1 51.8 52.3 51.6 52.3 | 3267 3553 4724 **5117 5093 5110 5097 5086** ... |
| rep1 | **159.9 87.1 57.7** 49.6 49.3 49.2 49.3 49.4 | **2000 x6** 2032 3578 4130 2994 3416 3507 ... |

The clamp is established **during the prefill** (its own second eighth reads
2000; the warmup's prefill shows it engaging ~1 s in), **scales with the
prefill** (p512's 1.99 s prefill: 102.3 ms transient and ~1.5 s clamp; p1024's
4.05 s: 162.1 ms and ~2 s), and **releases ~2 s after it**.

* **A correction to this row's own earlier reading: the steady state is not
  host-submission-bound.** 49.3 ms/step while the package is still at the 2.0 GHz
  clamp and 49.3 ms/step after it returns to 3.9-4.5 GHz, and 49.35 ms flat in
  the settled arm at 5.0-5.1 GHz: over a 2.5x clock range the step does not move,
  so the device is the limit above the base clock; `call_ms ~= 49.4`
  with `wait_ms ~= 0.03` is device-paced blocking inside the launch calls, not
  49 ms of host CPU.

  measuring the package clock as much as the engine. Sample `scaling_cur_freq`
  in any before/after on this machine; a 2.5x clock swing is worth 3.3x on a
  host-bound step and is invisible in the GPU counters.

## Validation

**Causal confirmation.** With `--settle-ms 5000` the clock is already back at
boost at the first decode step and the transient is gone - the step series is
**49.35 49.14 49.22 49.42 49.37 49.39 49.41 49.41**, flat from step 0. That is
the arm DE-5 priced at +3.3 s net, now explained: the idle waits out the clamp
rather than removing work.

**The named candidates are excluded by direct counters (graph capture, allocation churn) or made
unnecessary (residency/page-table), and the host-side suspects as well:**

| candidate | measurement |
| --- | --- |
| graph cache | 48 MoE captures in the warmup's first 16 steps, **0** in every band of every later decode; capture costs ~100 ms in total |
| allocation churn | **0.00 MiB in every band of every rep**; the warmup prefill allocates 167,772,176 B and frees 52,428,808 B, every later prefill allocates and frees **0 B** |
| cyclic GC | **0 collections in the transient bands** (the warmup's reclaim 45 objects); with `gc.disable()` the transient is unchanged at 151.1 / 84.3 / 58.0 against 152.4 / 78.2 / 54.8 ms |
| cgroup throttling | `nr_periods 0`, `nr_throttled 0`, `throttled_usec 0` |
| device-paced queue blocking | with a sync per step the device wait is **0.03-0.14 ms in every band** while the host call half carries the transient (153.8 -> 49.4 ms) |
| extra host work | process CPU time tracks the wall (193.0 -> 81.1 ms/step); `cProfile` shows the same function mix at ~1.5x per-call cost, i.e. the same work at a lower clock |

**The trigger is the prefill's own load.** A control probe applies each load
class in isolation (5 s arms, burner in a subprocess so the sampler is not
GIL-starved, 32 cores sampled every 100 ms). Median max-core clock: idle 3533,
**cpu 5117**, **cpu_mem 5117**, gpu 3536, **cpu+gpu 5118**, mem+gpu 3555 MHz.
**No synthetic arm reaches the 2.0 GHz base clamp.** The one consistent trend is
that GPU load alone suppresses the boost to ~3.5 GHz without clamping - the
shape of a shared package power budget - and the prefill's heavier load goes
further.

Commands: `scripts/qwen4exp_de5_wall_split.py --case code-p1024 --steps 96
--repeats 1 [--instrument] [--split-steps] [--no-gc] [--prefill-clocks]
[--settle-ms 5000]`, `scripts/qwen4exp_de5_clock_burst_probe.py --seconds 5`.

## Next

* The transient is a **platform power-management response to the prefill**, not
  an engine host-code defect. Nothing in `reset()`, the wrapper, the graph cache,
  the allocator or the GC owns it, and there is no in-tree fix. The only measured
  mitigation remains the idle settle, and it stays **net-negative** (+3.3 s
  against a ~1.5-1.9 s transient).
* **Limits:** one host (integrated APU, not the gfx1100/W7900 default hardware),
  one model, one quant, one profile, one case family; wall medians around a
  device synchronize, not a serving-path throughput measurement. The clamp
  cannot be pinned for a direct causal test - writing `scaling_min_freq`
  requires root and this session has none - so the causal link rests on the
  settle arm plus the clock/step-time correspondence across four independent
  repetitions. `cpuinfo_avg_freq` is a per-CPU attribute, not a package average
  (one thread pinned to cpu4 reads 5118 MHz there while cpu0 and cpu8 read
  2000). The burst control does not include a compute-heavy GPU kernel loop, so
  the prefill's own GPU power profile remains the untested candidate trigger.
* **No performance claim, no promotion, no default changed.**
