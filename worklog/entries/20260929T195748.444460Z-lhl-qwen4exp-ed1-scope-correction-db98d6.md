# ED-1's negative screen measures a Q5_1 family production has not selected for that shape since 2026-09-06

## Summary

ED-1's ledger row read as a closed negative on LDS-staged expert weights. Reading the
dispatch path shows the row is a closed negative on **one Q5_1 family that production
does not select for the shape it measured**. The row's own premise - replace the per-lane
Q5_1 block gather with cooperative LDS staging - is already implemented in the owner
production does select. Status is unchanged; the scope is narrowed so a future reader
does not treat ED-1 as evidence about the production path.

This is a source-reading correction with no new measurement.

## Evidence

Both ED-1 artifacts measure only the `wmma_iu8_risk` Q5_1 family
(`selected_wmma_iu8_risk_prefill_bf16_bf16_out` and its `_j32_` sibling):

- `benchmarks/results/2026-09-29-qwen4exp-ed1-lds-screen/` (2026-09-29 09:01)
- `benchmarks/results/2026-09-29-qwen4exp-ed1-population-replay/` (2026-09-29 09:13)

The dispatch path says that family is not what runs for the measured shape:

- `hipengine/generation/qwen4_exp_profiles.py` selects
  `selected_grouped_prefill_compact_rowbatch8_out8_expertgrid64_bf16_bf16_out` for
  `moe_linear` / `prefill_rows_ge512_k640_exact_grouped_q5_1_down`.
- `962217138` (2026-09-06 22:49) added that entry with that variant; `3b97eb47d`
  (2026-09-07 03:49) renamed the shape to add `_k640`. The variant has not changed.
- Scanning every `_selection(...)` block in the manifest, **exactly one** entry selects a
  `wmma_iu8_risk` variant, and it is the q4_k gate_up `_dual_` one. The q5_1 down variant
  ED-1 screened is selected by zero manifest entries.

So the screen ran 23 days after the family it measured had stopped being the selection for
that shape.

Structurally, the production owner already does what ED-1 proposed. Its launch
`q5_1_selected_grouped_prefill_logical256_bf16_bf16_kernel<row_batch=8, out_batch=8>`
(grid `(N/8, 64)`, 128 threads, LDS `8*256*4 + 20*12` = 8,432 B) stages the Q5_1 metadata
cooperatively - the first `blocks_per_row`=20 threads load `d`, `m` and the high-bit word
into `shared_d` / `shared_m` / `shared_qh` - once per output row. It computes `weight_row`
outside the row loop, so the 480-byte row is reused across every `ROW_BATCH` of the expert.
Only the 4-bit nibbles are read per-lane, and out of a row that is already L1-resident.

The screened kernel is gather-shaped by construction: `warp_col * 32 + lane` assigns each
lane its own output column, and each lane reads its own `row_bytes` weight row.

This also explains the 2.92% DRAM movement the row records: the bytes staging moved were
already being re-read from cache, not from DRAM.
