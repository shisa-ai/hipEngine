# Gemma 4 P3: the Q8_0 down re-measurement

## Summary

P3 owed two things after `7a91b5735` landed the Q8_0 down registration: the
perf re-measurement ("the 21.9 / 44.4 ms re-measurement showing the fast leaf
now runs at 1024") and the teacher-forced gate. The gate went first and turned
out to be blind to the change (previous entry). This one is the perf half.

**What was measured.** `scripts/gemma4_p3_down_ab.py` wraps
`gemma4_project_experts_wmma` -- the dispatcher P3 re-points -- and the whole
`gemma4_experts_forward_bf16` in HIP events. Geometry at `--repeat 34` is 1021
prefill tokens in two blocks (512 + 509), 30630 token-layers, 150 forward
calls. Four paired runs:

| run | expert FFN, fixed | expert FFN, pre-fix | delta |
| --- | ---: | ---: | ---: |
| 1 | 455.163 ms | 491.029 ms | 35.866 ms |
| 2 | 456.382 ms | 491.365 ms | 34.983 ms |
| 3 | 457.575 ms | 494.112 ms | 36.537 ms |
| 4 | 454.118 ms | 489.269 ms | 35.152 ms |

Mean delta **35.8 ms**, spread **0.8 ms**, **-7.3%** of routed-expert work at
prompt 1024. Layer 29's own down measures **1.43 ms** on the fixed side; adding
the delta puts the pre-fix figure near 37 ms, consistent with the 44.4 ms the
P3 row recorded from a kernel-level breakdown -- same order, different method,
so it corroborates rather than equals.

**The control, and why it took three attempts.** The point of a control here is
to change *only* layer 29, because HEAD lacked an owner for that one Q8_0 down
and nothing else.

1. *Raise `MissingKernelError` from outside the dispatcher.* Fatal during the
   decode tick. The dispatcher does
   `_ensure_linear_kernel_registered(key); try: resolve(...) except
   MissingKernelError: return False` -- an exception raised outside that
   `try` never gets the treatment the real path gives it, so it propagates to
   the engine. This was instructive: it proves the missing-registration path
   never raises at all, it returns `False`.
2. *Force `_build_wmma_tile_plan` to decline.* Measurable but wrong -- that
   disables WMMA for all 30 layers, not just Q8_0, and gives 938 -> 459 ms,
   which is the value of the whole WMMA down route rather than of this row's
   change.
3. *`unregister()` the key plus suppress lazy re-registration for that key
   only.* Correct. Unregistering alone does not stick, because the dispatcher
   calls `_ensure_linear_kernel_registered` before `resolve`, which would
   re-register the very key I removed; blocking that one key from the ensure
   hook leaves every Q5_1 owner intact in both arms.

**Population view, which is method-independent.** Layer 29's down runs at
**0.803-0.814x** the average of the already-fast Q5_1 layers on the fixed side,
against **0.388-0.399x** on the control side (where the real work escapes the
timer by design). Before this row existed, layer 29 was the lone outlier; it is
now inside the fast population.
