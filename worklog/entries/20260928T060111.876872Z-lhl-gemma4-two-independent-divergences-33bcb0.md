# the gate-up MMQ route is one divergence and the down projection is a second independent one

## Summary

`20260928T060012` localized the divergence to `gate_up_out` by reading the real
intermediates, and proposed aliased rows as the trigger. **That proposal is
refuted** -- the isolated projection probe with byte-identical rows is still
bit-identical across the two routes. The actual trigger is a route the probes
never exercised: **the fused MMQ gate/up route, which is on by default.**

Running the same buffer instrumentation twice, with and without the rollback
lever:

| buffer | `HIPENGINE_GEMMA4_MOE_GATE_UP_MMQ` unset (on) | set to `0` (off) |
| --- | --- | --- |
| `packed_hidden` | 0.00000000 | 0.00000000 |
| **`gate_up_out`** | **0.00646647** | **0.00000000** |
| **`activated`** | **0.00953000** | **0.00000000** |
| **`expert_out`** | **0.00919143** | **0.01353754** |
| `out` | 0.00919143 | 0.01353754 |

## Two independent divergences

**The gate/up MMQ route diverges.** With the gate off, `gate_up_out` and
`activated` become *bit-identical* across `rows=1` and `rows=2`. That is the
route `gemma4_moe_gate_up_mmq_enabled` enables by default, documented as
*"the measured faster path (1.27x on the 512/128 prefill)"* whose *"numerical
decision that held it back has cleared"*. Every probe in this investigation
called `gemma4_project_experts_rows` directly and therefore never ran it. The
real call reaches it at `rows=2` (`lanes=4 >= num_experts=4`) and not at
`rows=1` (`lanes=2 < 4`), which is the same threshold as the projection's own
switch but a *different* family.

**The down projection diverges independently.** With the gate off,
`gate_up_out` and `activated` are bit-identical and `expert_out` *still*
differs -- at 0.0135, worse than the 0.0092 it shows with the gate on. So the
down has its own defect, and the gate's contribution was partially cancelling
it.

The down cannot take the MMQ route here: `gemma4_moe_down_mmq_enabled` is the
Q5_1 DS4 route and the fixture's `ffn_down_exps` is Q4_K, so
`gemma4_project_experts_down_mmq` returns False and the fp32 grouped family runs.
That family is what the isolated probes cleared, which means **the isolated
probes and the real call are not running the same thing for the down either**.

## Why the isolated probes kept clearing the projections

They call `gemma4_project_experts_rows` with a scratch-less, hand-built routing.
The real call reaches the projections through a *preference chain* that starts
with an MMQ attempt, and the gate/up attempt succeeds here. A probe that enters
below that chain cannot see it. This is the second time in this investigation
that a probe's input or entry point was unrepresentative -- the first was
distinct-rows, this one is the entry point -- and both produced "cleared"
verdicts for a stage that is not cleared.

## What this means for the earlier gate-off observation

`20260928T055408`-era work recorded that
`HIPENGINE_GEMMA4_MOE_GATE_UP_MMQ=0` does not fix
`test_incremental_decode_matches_a_dense_prefill`, and treated that as evidence
the flag was not the mechanism. That reading holds and is now explained: turning
the gate off removes one divergence and leaves the other, so the test still
fails. It is not evidence that the MMQ route is innocent -- the buffer
measurement above shows it is directly responsible for the first one.

## Changes

None. This unit is a measurement.

## Validation

- Probe on the 8060S (gfx1151) running the identical buffer instrumentation
  under `HIPENGINE_GEMMA4_MOE_GATE_UP_MMQ` unset and set to `0`, printing the
  observed value of that variable in each run so the two are distinguishable.
  Exit 0 for both.
- The isolated aliased-row probe is the refutation of the previous unit's
  trigger hypothesis: `packed_hidden` rows 0 and 1 byte-identical, `compact=2`
  against `=4`, both projections bit-equal at rows 0 and 1. Exit 0.
- The default-on claim is quoted from `gemma4_moe_gate_up_mmq_enabled`'s own
  docstring, and the Q5_1-only claim from `gemma4_moe_down_mmq_enabled`'s.

## Next

Fix the MMQ gate/up route first: it is the one the buffer measurement isolates
exactly, it is on by default in production, and turning it off makes the whole
gate/up stage bit-exact. Then re-measure the down with the gate off to work the
second divergence from a clean `activated`. Both need a regression test asserting
row-count invariance of the *whole* expert forward, not of a hand-entered
projection call -- that is the test whose absence let both defects through.
