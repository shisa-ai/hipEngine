# Muse Glimmer batched-invariant DFlash block verify

## Summary

Replaced the sequential single-row DFlash verify (15 target forwards/cycle)
with one batched-invariant block forward. The whole draft block now verifies
in a single forward whose per-row arithmetic is bit-identical to true AR
decode, amortizing weight reads across the block. Exactness gate green;
DFlash decode 2.59 -> 4.52 tok/s (1.75x) on the full mtpbench suite. Still
below AR (11.0) and Gate B (21.30): the remaining bottleneck is draft
acceptance (15% vs llama.cpp 55%), not verify speed.

## Changes

- `kernels/hip_gfx1100/quant/gguf_t16_selected_gemv.py`: register the exact
  weight-amortized Q4 T16 rowtile owner (`dense_rowtile_gemv_bf16_bf16_out`,
  rows 2-8) for gguf_q4_k_t16_v1 and qmicro; gfx1151 inherits via bulk alias.
- `runtime/gguf_linear.py`: `launch_gguf_linear_exact_rows` — resolves the
  rows=1 decode owner, then runs the block through its exact row-independent
  multi-row form (registered rowtile sibling chunked <=8, or the row-independent
  Q5/Q6 `t16_gemv_decode`), falling back to sequential rows=1 for any owner
  without a declared exact multi-row form. Registry-keyed by parent variant;
  no model identity. Always bit-identical to AR decode.
- `runtime/muse_glimmer.py`: `verify_with_taps` runs one `_forward_block(...,
  exact_multirow=True, all_logits=True)`; `_linear` routes exact-multirow
  projections through the helper (never the reassociating WMMA prefill);
  attention uses the decode split count (n_splits=64) with the kernel's
  per-row causal+SWA clamp, so row i equals a single decode step at
  position_offset+i bit-for-bit.
- `tests/test_live_muse_glimmer_exact_rows.py`: helper bit-identity vs per-row
  decode across rows 1/2/4/8/9/15 (incl. the >8 chunk boundary) for Q4/Q6
  weights.

## Validation

- Bit-identity pre-check: Q4 T16 dense_rowtile and Q5/Q6 t16_gemv_decode at
  rows=4 == per-row decode, 0 diff elements (gfx1151).
- `tests/test_live_muse_glimmer_exact_rows.py`: 30/30 passed.
- `tests/test_live_muse_glimmer_dflash_exactness.py`: 2/2 passed — DFlash IDs
  == true AR on the 10-prompt suite + public LLM speculative surface.
- Full-suite bench (repeats=1, max_tokens=512, /tmp/glimmer-dflash-batched-r1.json):
  AR 11.03, DFlash 4.52 tok/s (transition-norm 4.51), exactness True,
  speedup vs AR 0.41x. Acceptance 2423/16200 = 15.0%, tokens/target-forward
  1.60. Sequential-verify baseline was 2.59 tok/s.

## Acceptance bottleneck (next)

The verify now amortizes well, but DFlash commits only ~1.6 tokens/cycle
because draft acceptance is 15% overall and near-zero on prose
(general_en_explain 46/795=5.8%, general_ja_plan 0/30, mixed_ja_en_review
36/255=14%); code prompts ~24%. llama.cpp draft-dflash reports 55% overall
(37-48% on the same prose prompts). At ~356 ms/cycle, beating 21.30 tok/s
needs ~7.6 committed tokens/cycle (~50% acceptance). The draft acceptance gap
— not verify speed — is now the binding problem. Investigate per-position
acceptance and draft-vs-oracle logit parity to localize whether the drafter
proposals are systematically wrong (bug) or decay with block depth
(economics); compare against the llama.cpp draft mechanism.
