# Review: piffa.net Eaman llama.cpp MTP patch applicability to hipEngine verifier

## Summary

Reviewed https://store.piffa.net/lm/bug/ (the "Eaman" llama.cpp ROCm/MTP patch
collection for Qwen 27B) to find MTP optimizations that apply to, or should be
tested against, hipEngine's MTP verifier. **Verdict: the piffa work is a
VRAM/context-capacity fitting patch for llama.cpp's server auto-fit, not an
MTP-verification-speed patch. It offers essentially no verification-speed
optimization that applies to hipEngine.** The dominant verifier wall buckets
(W4 GEMV, MoE gate/up/down, GDN, LM-head; ~832 launches/pass) are untouched by
anything in the piffa patch.

## Changes

Reviewed artifacts (via web_fetch):
- `improvemets_list.md` / `history.md` / `possible_improvements.md` (change
  inventory)
- `mtp_rs_only_8144f31.patch` (recurrent-state rollback + on-device checkpoint
  reservation)
- Final patch set = MTP context sizing, MTP memory accounting, pipeline
  scheduling, per-device fitting, and HIP VEC quantized-KV attention dispatch.

Item-by-item applicability to hipEngine:

1. **Fitted MTP context sizing / MTP memory accounting / refinement passes** —
   llama.cpp `speculative.cpp` + `server-context.cpp` auto-fit logic. hipEngine
   is torch-free with its own memory management and no llama.cpp server fitter;
   NOT applicable.
2. **Pipeline-parallel control / non-pipeline MTP scheduling** — llama.cpp
   scheduler semantics. hipEngine has no llama.cpp scheduler; NOT applicable.
3. **Per-device multi-GPU fitting** — llama.cpp `fit.cpp`; NOT applicable.
4. **HIP VEC quantized-KV flash attention** — the one genuinely
   performance-adjacent item. Eliminates the context-sized F16 conversion
   workspace by dequantizing quantized K/V in-register. hipEngine already keeps
   full BF16 mirrors of quantized (INT8) KV
   (`full_bf16_mirror_*_caches`, `bf16_mirror_layer_indices` in
   `qwen35_gguf_runner.py`) and the verifier requires BF16 KV, so this is the
   direct analog — but it is a VRAM/capacity saving, not a verifier-speed lever
   (full-attention is not the dominant verifier bucket).
5. **`--spec-mtp-rs-depth` recurrent rollback depth / on-device checkpoint
   reservation** — VRAM saving for recurrent-layer MTP rollback (Qwen3.6
   RS buffers). hipEngine uses GDN recurrent layers and scratch-to-resident
   copies with a single live state; reducing rollback depth trades memory for
   deep-rejection replay cost, not verification speed. NOT a speed lever.

## Validation

Grounded in hipEngine's measured verifier economics:
- docs/MTP.md current row: B=1 `decode_batched`, 14.134 ms/cycle wall =
  12.415 ms verify + 1.700 ms proposal. Verifier is ~88% of cycle wall.
- Current verifier profile families (ms/pass): w4_dual_gemv 1.439,
  moe_gate_up_dual_gemv 1.213, w4_single_gemv 1.084, linear_attention_gdn_decode
  1.041, w8a16_linear 0.808, moe_paro_rotate_in 0.800, moe_down_gemv 0.772;
  ~832-833 launches/pass. None of these are addressed by the piffa patch.
- hipEngine MTP verifier already consumes BF16 KV for full-attention
  (NotImplementedError if not BF16; `full_bf16_mirror_*_caches` materialized in
  `_allocate_qwen35_gguf_kv_chunk`).

## Next

No code change from the piffa patch is warranted for verification speed. Real
verifier-speed levers remain our already-documented lanes (reduced-DAG
layer-surround batching, adaptive budget policy, D64 exactness correctness
work). Optional future note: the BF16 KV mirror is a memory/capacity analog to
the piffa VEC change; only pursue in-register quantized-KV attention if a fresh
profile shows full-attention becoming a live verifier bucket, or if VRAM
capacity becomes a serving constraint.
