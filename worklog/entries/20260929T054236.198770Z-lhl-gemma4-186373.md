# Gemma 4: close the router kl_max routing-flip hypothesis on the production chain

## Summary

Task V1 in the punchlist was open at "fix or record the router `kl_max`
regression breaking the 4096 gate". The open *mechanism* question was whether
`74fb74ffe` (select the router logits kernel by token count) flips expert
selection on real data. Until now the only evidence was
`tests/test_gpu_gemma4_router_variant_selection.py` on **random** weights: 0 of
512 tokens disagree. A trained router is not Gaussian, so that was weak
evidence against a flip under the actual gate.

`scripts/gemma4_router_variant_flip_probe.py` closes it. It wraps
`qwen35_router_logits_bf16_f32w_token_tile_16` at the module the call site
actually reads, and for every prefill invocation also runs the untiled kernel
into a scratch buffer from the *same* prescaled hidden, then reads both buffers
back and compares elementwise and against a float64 reference. The model's own
output buffer is only ever written by the real kernel; the scratch result is
never consumed.

Measured on the gate's exact geometry (`--prompt-tokens 5120 --prefill 4096
--context 8192`): **240 tile invocations (8 blocks x 30 layers), 122880 tokens
compared, 0 tokens selecting differently, max `|tiled - base|` 9.537e-07, and 0
rows where either kernel's top-8 differs from float64.** A free-running
generation agrees (30 calls, 8310 tokens, 0 flips). The routing-flip hypothesis
is therefore excluded on production activations, not just synthetic ones.

What remains is not a defect. `scripts/gemma4_router_logits_variant_bench.py`
already records that both variants carry the *same* `2.861e-06` max drift
against float64: neither kernel is wrong, the tiling reorders the reduction,
and forcing identical order would undo the tiling. There is no bit-exact fix.

So the classification stands as the punchlist had it: T2 association drift
under `docs/EXECUTION-PROFILES.md`, admitted to `production` only after the
full gate — and §6.1's maximum-row-KL `5e-2` is a binding absolute ceiling,
against which the measured 0.2177 sits 4.35x over. The commit's own gate passed
at `--prefill 1024` (`kl_max` 1.30e-03) and does not extend to 4096. Because
the ceiling is binding and §6.1 bars rows over `2e-2` from automatic admission
even when the ceiling passes, this is not something the punchlist can accept on
its own; the call belongs to the lead. Recorded there with both options priced:
reverting the prefill selection costs only the tile's measured benefit
(prefill `+0.94%` / `+0.56%`, decode unchanged) and buys a clean gate, while
the tile kernel, its bench, and its test stay in the tree either way.

## Validation

- `scripts/gemma4_router_variant_flip_probe.py --prompt-tokens 5120 --prefill
  4096 --context 8192`: 240 calls, 122880 tokens, 0 flips, max delta
  9.537e-07, 0 float64 mismatches on both arms, 0 observation errors.
- Same probe in free-running mode (`--prompt 6 --output 8`): 30 calls, 8310
  tokens, 0 flips — the model generated normally, confirming the wrapper does
  not perturb what it observes.
- A plain `LLM.generate()` with the wrapper removed succeeds on the same
  prompt, isolating two bugs found while building the probe: `copy_device_to_host`
  takes a `DeviceBuffer` (it reads `.nbytes`), so a raw int pointer raises; and
  the bf16 readback array must be sized in elements, not bytes.
- `python3 scripts/docs/check_all.py`: the `published command drift` gate
  reports 1 violation, `2026-09-21-zbook-fast-cpu-gpu-sampling.json ->
  /home/lhl/hipEngine-main/scripts/gguf_native_sampler_gate.py`. It predates
  this work (commit `97d65ae0b`, 2026-09-21) and points at a different
  worktree; the other three doc gates pass. Not touched here.
