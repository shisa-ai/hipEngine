# PF-1d MMQ retile rejection and template retention

## Summary

Measured the bit-exact MMQ tile-retile hypothesis (occupancy lever) and
rejected it: both alternative tiles lose to the retained 128x128 reference.
The kernel is now tile-parametrized (single source of truth) with the default
instantization bit-identical; the losing variants were removed after
rejection. PF-1d's remaining lever is activation-plane reduction (2.40x
measured), which is a production-profile arithmetic change gated on the
calibrated numerics campaign.

## Changes

- `gguf_q8_0_mmq_prefill.hip`: `q8_0_raw_mmq128_q8_1_d4_kernel` became
  `q8_0_raw_mmq_tile_q8_1_d4_kernel<MMQ_M_T, MMQ_N_T, ...>` with
  WAVES-generalized load loops; `launch_mmq_tile<>` added; `launch_mmq`
  delegates with `<128,128>`. Extern-C/python surfaces unchanged.
- `tests/test_qwen4exp_pf1_dense_parity.py`: new
  `test_pf1_mmq_chain_variants_bit_identical` (cross-variant bit parity at all
  7 policy shapes — the permanent RED gate for future retiles) and a shared
  chain-runner helper; coltile parametrize decorator restored after a splice
  bug.
- Rejected variants (m64x64, m32n128 wrappers/registrations/entry points)
  removed after measurement; `MMQ_CHAIN_VARIANTS` documents the mechanism.

## Measurements (zbook/gfx1151, guarded d4x3 chain, rows=512, warmup 3,
10 timed reps, memset risk_count before every guarded launch)

Verdict: 64x64 = 0.89x (wins only out<=640 shapes by 1.23-1.39x, ~1% of
family time), 32x128 = 0.35x. Occupancy (2 blocks/CU at 28.7KB shared vs 1 at
57.9KB; gfx1151 LDS=65,536B confirmed via hipDeviceGetAttribute) is not the
binding constraint — token-tile shrink doubles weight global re-reads and
dominates. The 128x128 tile is measured-optimal among tested geometries;
deeper schedule work (async copy/double-buffered staging) would be a rewrite
with the same weight-traffic bound.

## Gotcha recorded

The guarded ABI requires `risk_count` zeroed before every launch. A timing
script that skipped the memset crashed with a GPU memory fault whose ROCm
hang analysis reports grid/workgroup in work-items (grid=[640,32] =
blocks[20,4] x wg[32,8]), which misleads attribution. Production paths and
the PF-1b suite always memset; scripts must too.
