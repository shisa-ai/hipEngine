# dense plugin defaults to the clamped MTP2 adapter, proven by the plugin attribute

## Summary

The previous entry reached the right conclusion through the wrong evidence: it
pointed at the string "dense_nextn" near the dense provider path, but that occurrence
is a draft-provider pool cache key, not the adapter registry key. Same string, two
namespaces. The route is now proven properly, in three static links, and one runtime
quantity remains open.

## Validation

The chain, each link read directly:

1. hipengine/models/qwen35.py:567 - the dense model plugin declares
   speculative_mtp2_adapter = "dense_nextn" as its default. The MoE plugin at :604
   declares "moe_nextn". This is the model-plugin attribute the engine actually
   consults.
2. hipengine/generation/qwen35_gguf.py:6079-6092 - the engine reads
   model_plugin.speculative_mtp2_adapter, returns None if empty, then calls
   resolve_gguf_mtp2_adapter(adapter_key). A dense plugin therefore resolves the
   dense key by default, with no configuration needed.
3. hipengine/generation/qwen35_gguf_mtp2_registry.py:63 - registers
   Qwen35GGUFMTP2Adapter for "dense_nextn". tests/test_qwen35_gguf_moe_mtp2.py:238
   asserts exactly that mapping, so it is covered by a test rather than inferred.

That adapter is where max_requests becomes min(4, max(1, capacity)) at line 1029,
where admitted widths are (1, 2, 4) at line 1063, and where group growth is refused
past provider.executor.max_requests at lines 1392 and 1405.

Not established, and not claimed here:

- owner.capacity at C5-C8 in the retained run. If it is below 4 the clamp binds
  exactly at four; the curve turning after C4 is consistent with that but does not
  prove the value.
- that the retained explicit-K3 packet used the MTP2 adapter route rather than
  another speculative path. The dense plugin makes it eligible by default; the
  packet's own fields decide it.
- therefore the clamp remains the leading hypothesis for the C5-C8 collapse, not a
  diagnosis.
