# P1: packed INT8 prefill shares one BF16 oracle across layers under a chunk-outer executor

## Summary
The packed slot-local INT8 prefill route produces wrong output for any prompt
that spans more than one prefill chunk (>1,024 rows on the dense H5120 Q4_K_M
geometry). `int8_direct` sessions are forced onto this entry unconditionally by
`_gguf_single_row_block_table_prefill_required`, so this is the shipping server
path for every INT8 KV request above 1,024 prompt tokens.

Found by acting on external review feedback, then reproduced with a three-point
A/B and a clean control. No fix applied; the fix has a real memory tradeoff and
belongs to its own unit.

## Mechanism
`_int8_prefill_oracle_cache_for_layer` keys the BF16 oracle pair `-1` - one
shared pair for all INT8 layers - whenever the lifetime plan mode is
`layer_outer_shared_oracle`. That function's own docstring states the invariant:

> Chunk-outer bulk prefill revisits each layer once per prompt chunk, so it
> keeps one full-length pair per INT8 layer. A memory-positive layer-outer plan
> instead owns the full hidden plane and safely reuses one pair after each layer
> completes.

But `_prefill_batch_native_impl` chunks the prompt by
`_bulk_prefill_scratch.rows` and `_prefill_batch_native_single_slab` iterates
layers *inside* each chunk - chunk-outer, layer-inner - while
`_plan_gguf_int8_prefill_lifetime` still selects `layer_outer_shared_oracle`
purely from a memory comparison (`use_shared = projected_delta < 0`). Plan and
executor disagree. From the second chunk onward, the shared oracle's positions
`0..chunk_start` hold the *last* INT8 layer's K/V from the previous chunk, and
every layer attends over that instead of its own history.

## Changes
- `scripts/gguf_prefill_route_ab.py`: `--use-wmma-prefill` / `--use-gemv-decode`
  (default ON, matching the shipping serving owner) with `--no-` rollbacks, and
  both recorded in the artifact. Without these the harness measured a
  non-shipping low-level default roughly 6x below the real route.
- Artifact above. No production code changed by this unit.

## Validation
W7900 (GPU0), gfx1100, Qwen3.8-27B `Q4_K_M`, `int8_per_token_head` + FP32
scales, `max_sequence_length` 16384 (route `int8_direct`, no mirror), shipping
selectors `use_wmma_prefill=True use_gemv_decode=True`, deterministic varied
prompt (`default_rng(20260909)`), 8 greedy IDs,
`scripts/gguf_prefill_route_ab.py`:

| prompt rows | chunks | oracle | scalar_bulk IDs | packed IDs | agree |
| ---: | ---: | --- | --- | --- | :-: |
| 1,024 | 1 | shared (shipped) | `[62,198,197,197]` | `[62,198,197,197]` | yes |
| 2,048 | 2 | shared (shipped) | `[198,197,197,1]` | `[14,198,248046,198]` | **no** |
| 2,048 | 2 | per-layer (patched) | `[198,197,197,1]` | `[198,197,197,1]` | yes |

The scalar arm is the control and is unchanged by the oracle variant (742.28 vs
749.29 tok/s, identical IDs) because scalar bulk prefill is layer-outer. Packed
prefill measures 449.16 tok/s in *both* oracle variants, so correcting the
lifetime is speed-neutral at this shape - it costs memory only.

Artifact: `benchmarks/results/2026-09-10-w7900-int8-packed-shared-oracle-defect.json`.

## Corrections this forces to earlier conclusions
- **The packed-vs-scalar divergence is not GDN arithmetic.** It was attributed to
  "different GDN state-capture arithmetic" on the strength of the comment at
  `hipengine/generation/qwen35_gguf.py:7406-7408`. With per-layer oracles the two
  entry points produce identical generated IDs, so that comment does not explain
  the observed divergence (logit max abs diff 7.79 at 4,096).
- **The oracle route is not slow, and my absolute rates were invalid.** The
  earlier A/B omitted `use_wmma_prefill`/`use_gemv_decode`, which every shipping
  call site sets. With them the scalar oracle route reaches 742-749 tok/s at
  2,048, consistent with the retained XTX oracle-route control at 761.58 tok/s
  (`results/2026-09-09-rx7900xtx-gguf-int8-direct-prefill-blocked.json`). The
  claim that a residual ~6x was the oracle's double-write/cast is **withdrawn**.
- **The AOTriton admission gate's interpretation is weakened.** Its before/after
  method was sound and the flag is default OFF, so nothing shipped changed, but
  both arms shared the same corrupted multi-chunk history, so its 1.97e-05 mean
  KL does not qualify the route. Re-qualify after the oracle lifetime is fixed
  and against the shipping selectors.

## Next
- **Fix the oracle lifetime.** Three options, none free:
  (a) make the packed executor layer-outer so the shared pair is valid -
  preserves the memory win, largest change;
  (b) have the plan choose per-layer oracles whenever the executor is
  chunk-outer - correct and speed-neutral as measured, but the oracle cost goes
  from ~4 KiB/token to ~64 KiB/token on this geometry, which will move the
  server context ceiling down;
  (c) repopulate the shared oracle's preceding history per chunk from the
  retained INT8 store - reintroduces a dequantized read and needs its own gate.
- Then re-run the packed-vs-scalar agreement check at 8,192+ and on real
  (non-synthetic) prompts, and re-qualify the AOTriton flag.
- Separately, review finding still open: `_prefill_batch_native_single_slab`
  calls `_sync_packed_decode_initial_state` (line 22555) once per slab, which
  copies positions `0..session.position` into packed storage, and the
  `slot_local_full_prefill` branch then clears `_packed_decode_session_ids` /
  `_packed_decode_positions`, so the next slab re-imports. At 32K in 1K slabs
  that sums to ~15.5 full-prompt history copies before decode, traversed in
  Python with separate D2D copies for payload and scales. Slot-local attention
  reads request-owned KV, so these packed KV imports look removable while
  retaining the Conv/GDN imports. Not yet profiled.
- `_int8_prefill_oracle_capacity_positions` sizes the oracle by
  `backing_pages * block_size` - the whole pool - not the request context, so
  wider serving capacity inflates transient oracle allocations too.
