# Plan Qwen4Exp one-layout residency

## Summary

Added F3 one-layout residency/admission planning and sparse PLE mmap ownership.
Every hot tensor keeps one raw GGUF device owner; the PLE table has one cached
mmap owner, zero device/alternate bytes, CPU row dequant, and a bounded
optionally HIP-page-locked double staging ring.

## Changes

- Planner reports raw payload, device weights, replacements, alternates, PLE
  mmap, staging, and bytes by qtype; replacement/alternate are exactly zero.
- Admission accounts BF16 K/V, compressed QSA index, FP32 GDN/Conv/PLE states,
  widened BF16 residual, scratch, and reserve at explicit context/capacity.
- PLE table enforces semantic row bounds (excluding Unsloth's 90 unreachable
  padding rows), supports every registered CPU-dequant qtype including IQ4_NL,
  maps once, gathers only requested rows, and closes idempotently.
- Staging owns exactly two FP32 row buffers, rejects over-capacity requests,
  page-locks both through `HipRuntime.host_register`, and unregisters on close.

## Validation

- RED: residency tests failed collection because the materialization module did
  not exist; a follow-up RED pinned one mmap owner/idempotent close.
- GREEN: `uv run pytest -q tests/test_qwen4_exp_residency.py` -> `4 passed`.
- Residency/mapping plus Qwen35 compatibility bundle -> `23 passed, 3 skipped`.
- Real frozen Unsloth header plan: raw 111,323,630,080; PLE mmap 28,800,138,240;
  hot device weights 82,523,491,840; replacement/alternate 0 bytes.
- On the local 124,521-MiB gfx1151 pool, c1/262K with 4-GiB scratch + 4-GiB
  reserve requires 97,880,505,856 bytes and leaves 32,689,226,240 bytes planned
  headroom. This is header-derived admission, not yet a successful full load.
