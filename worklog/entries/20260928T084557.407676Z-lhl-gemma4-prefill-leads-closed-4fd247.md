# two prefill leads close on mechanism not timing the dequant cast is a no-op and attention is not bandwidth bound

## Summary

Two directions opened by `fa0f95893` and `20260928T084150` are closed, and both
close on a mechanism rather than on a timing that could be noise.

**The Q8_0 dequant's float detour cannot be removed from the source.** Writing
`static_cast<half_t>(qs[k])` in place of
`static_cast<half_t>(static_cast<float>(qs[k]))` produces **byte-identical
device code** -- the whole kernel differs only in the `__hip_cuid_*` source
hash. The `v_cvt_f16_f32` the ISA shows is not something the source asked for
and can take back.

**The prefill attention kernel is not bandwidth-bound**, so the query-tiling
direction that `fa0f95893` named as "the 147 ms" is not the fix at these
lengths. That entry's reasoning is superseded by the measurement below.

## The dequant cast is a no-op

The ISA of the `<32,32>` instantiation before and after the edit:

```
diff <(asm before) <(asm after)   ->  66 lines, all of them __hip_cuid_* hashes
```

The instruction histogram is unchanged in every count: 209 `s_delay_alu`, 112
`v_mov_b16_e32`, 64 `v_cvt_f16_i16_e32`, **64 `v_cvt_f16_f32_e32`**, 64
`v_bfe_i32`, 32 `v_pk_mul_f16`.

`_Float16` has no integer-source conversion on this target, so both spellings
route through f32 and the compiler canonicalises them. **The dequant's
conversion count is therefore not a source-level lever**, and the ~5.25
instructions per weight element the histogram implies are what the compiler
chooses, not what the source over-specifies.

The edit was reverted. An intermediate sweep appeared to show 3 to 10 percent
on four shapes; that was run-to-run spread, and the same spread was visible
earlier between two sweeps of one shape and tile (1.891 against 2.189 ms). A
timing with no mechanism behind it does not survive the mechanism check, which
is the reason to run the mechanism check.

## Attention is not bandwidth-bound

The committed harness's own traffic ablation, `--dtype bf16` against
`--dtype f32`, doubles every K/V byte while leaving the shapes and the work
identical. At 512 tokens:

| case | bf16 ms | f32 ms | ratio |
| --- | --- | --- | --- |
| swa 256d 16q/8kv window=1024 | 4.96 | 5.04 | **1.02x** |
| full 512d 16q/2kv window=0 | 7.03 | 7.84 | 1.12x |

**Doubling all K/V bytes costs 2 percent on the dominant case.** The kernel
reads 4.29 GB per sliding layer at 923 GB/s, which looks like a bandwidth
ceiling until the ablation says moving twice those bytes is free.

The mask ablation, for completeness: `--mask zero` removes every K/V load and
leaves the key loop, and the kernel gets **slower** (4.96 to 5.88 ms). That
ablation is confounded and was already noted as such in
`20260928T074732`; it is reported here only so the two are read together.

So the kernel is latency-bound -- about 11 percent of issue capacity -- and the
fix has to shorten the critical path or put more bytes in flight per
instruction, not move fewer bytes. Query-tiling moves fewer bytes.

`fa0f95893`'s recommendation is superseded on this point. Its decomposition of
the gap (attention 6.1x, GEMM 1.47x, and 100 percent of our prefill being
kernel time) is unaffected and still the working picture.

## The one asymmetry worth naming

Pass 1 reads K with one 16-byte load per lane, so a warp consumes a whole
256-dimension row in one instruction. Pass 3 reads V with one **2-byte** load
per thread, so consuming the same row takes eight warps' worth of instructions
for the same bytes. Pass 3 is also the longer loop: 512 iterations per thread
against pass 1's 64 per warp.

That is a bytes-in-flight-per-instruction problem, which is the shape the
ablation says this kernel has, and it is where the next attention attempt
should start rather than at tiling.
