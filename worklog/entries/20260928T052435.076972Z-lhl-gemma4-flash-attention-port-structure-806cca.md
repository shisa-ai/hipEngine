# the qsa flash win is tile-amortized reduction, not a missing reduction

## Summary

`20260928T052350.126404Z` scoped the flash port from the QSA kernel's own source
comment, which says the QK dot runs with "no per-key shuffles". Reading the
kernel body rather than the comment shows that is precise but misleading: the
dot needs no reduction, but the softmax statistics still do, and they use two
full five-stage `__shfl_xor` butterflies per row per tile. The expected win is
unchanged and the port is unchanged, but the *mechanism* is different, and the
difference is what makes the estimate defensible rather than optimistic.

## What the code actually does

Phase 1, per warp-row, with lane `k` owning key `k`:

```cpp
float dot = -3.4e38f;
if (row_ok && k0 + lane <= pos && lane < k_count) {
  dot = 0.0f;
#pragma unroll 8
  for (int d = 0; d < 256; ++d) dot += q(qrow[d]) * q(krow[d]);
  dot *= scale;
}
float mx = dot;
#pragma unroll
for (int offset = 16; offset > 0; offset >>= 1) mx = fmaxf(mx, __shfl_xor(mx, offset));
// ... row_max, rescale, m_run ...
const float p = expf(dot - row_max);
float l_partial = p;
#pragma unroll
for (int offset = 16; offset > 0; offset >>= 1) l_partial += __shfl_xor(l_partial, offset);
// ... l_run, s_p[q_row * QSA_KT + lane] = p ...
```

Two butterflies, each 5 shuffles, per (row, tile). `s_p` stages the weights
through LDS, and phase 2 accumulates into 16 register cells with a serial loop
over the tile's keys and no shuffles at all.

## The mechanism, quantified

Per key, per lane:

| | FMAs | shuffles |
| --- | --- | --- |
| QSA (`QSA_KT = 32`, 2 butterflies per tile) | 8 | **0.31** |
| gemma4 `gemma4_plain` (one warp per key) | 8 | **6** |

Roughly **20x fewer shuffles per key**, and it is amortization, not elimination.
The count matters because the shuffle is what the earlier instruction census
identified: gemma4 spends about 30 instructions per key per lane for 8 MACs, of
which the reduction tree is 12, and the tree is what put the kernel at roughly 27
percent of the one-MAC-per-instruction issue peak. Take the reduction from 12
instructions to well under 1 and the mix is essentially the FMAs plus `expf`.

The one new cost is `expf`, one per (row, key) per lane, about one per 8 FMAs.
That is the trade the layout makes and it is why this is a reassociation rather
than a free win: the softmax is online, the weights are recomputed in a
different order, and the sum is no longer the same tree gemma4_plain builds.

## The port, concretely

For head_dim 256 only, which covers the 25 sliding layers and 130.5 of
attention's 164.7 ms. The QSA tile arrays are 256 wide already, so nothing about
the staging changes; only the addressing does.

- Grid `(rows / 32, q_heads)`, 256 threads, `QSA_QT = QSA_KT = 32`.
- Q staged `[32][256]` BF16, K and V `[32][256]` BF16, from gemma4's resident
  BF16 cache with the `kv_head = q_head / (q_heads / kv_heads)` mapping.
- Sliding window is per row, not per tile, so the QSA key-validity test
  `k0 + lane <= pos` becomes
  `k0 + lane >= gemma4_attn_first_kept(window, row_offset, row) && k0 + lane <= pos`,
  and the eviction test `mask_row[k0 + lane] != 0` joins it.
- Output is BF16 for the layer input rather than QSA's F32.
- `ACC_CELLS = QSA_QT * 256 / QSA_THREADS`.

Register as a new four-axis variant `gemma4_flash` alongside the existing
`gemma4_plain`, and select by geometry. `gemma4_plain` stays the strict owner
for the parity suites and for head_dim 512, which this port does not cover.
