# R0053-R0056 audit and the R0053/R0054 kernel-safety cleanup

## Summary

`692cb2f603`. All four section texts were still byte-identical to the sweep
snapshot (their `sha256` values match the file at this commit), so no earlier

## Per-entry dispositions

### R0053 -- fixed in this unit

The plain block kernel narrowed both window bounds through a 32-bit cast without
clamping: `gemma4_attn_first_kept` returned an unclamped int64 that the call
site narrowed to `int`, and the inline `walk_end` expression did the same. A raw
launch with an extreme `window` or `row_offset` could therefore land the two
bounds on opposite sides of zero and walk backwards over the allocation. The
launcher checked positive shapes, the GQA divisibility, and the LDS budget, but
never bounded the `tokens * num_heads` grid product before forming it, and never
bounded the int64 LDS sum.

The fix mirrors the staged reference. `gemma4_attn_sat_add`/`_sat_sub`
(`:163`, `:171`) use `__builtin_{add,sub}_overflow` and saturate;
`gemma4_attn_first_kept` (`:190`) and the new `gemma4_attn_walk_end` (`:209`)
clamp to `[0, keys]` before the `int` cast, and the call sites are `:275` and
`:294`. The launcher (`:449`) now validates the grid product
(`:474-477`) and each LDS term plus their sum (`:503-507`), returning
`hipErrorInvalidValue` before a launch. No legal shape is refused: the grid
ceiling is the device's own `INT32_MAX`, and the LDS ceiling is the same 64 KiB
the old `size_t` comparison applied.

The arithmetic is unchanged for legal inputs. For `window > 0` and
`0 <= row_offset + token < keys`, `first_kept` is still
`max(0, row_offset + token - window + 1)` and `walk_end` is still
`min(row_offset + token + 1, keys)`; `window == 0` still keeps the full walk. The
clamp only replaces a wrapped cast at the edges. This remains a raw-launch
boundary issue, not a measured regression on model-generated coordinates. The
pre-repair staged reproducer that faulted the GPU queue is the RED evidence and
is not re-run.

Reachability is raw-launch only, as the entry says. `attention_symbol`
(`gemma4_attention.py:904-906`) sends `tokens == 1` to the decode symbol, and
the C++ prefill launcher routes `tokens > 1` into the decode launch
(`gemma4_attention.hip:481-488`), so the plain block kernel is the fallback for
shapes that decode refuses, plus direct ctypes callers. That is why the new test
drives `hipengine_gemma4_attention_prefill_f32` directly.

Regression coverage: `tests/test_gpu_gemma4_attention_prefill_bounds.py` has
seven huge-coordinate cases (positive and negative, including `2**32`, which is
the shape that crossed zero before the clamp, and `2**63 - 1`, where `own` can
overflow int64) and two invalid-grid cases (`tokens = 2**31` and
`num_heads = 2**31 + 1`). The coordinate cases assert NaN for an empty clamped
walk and the staged CPU oracle for a clamped non-empty one; the grid cases assert
`hipErrorInvalidValue` through the raw prefill symbol. The Python wrapper is not
a second surface for that check: it selects the decode symbol for every row
count, and the decode launcher is a separate path. The
existing `tests/test_gpu_gemma4_attention_geometry.py` narrowed-walk test and
`tests/test_gpu_gemma4_attention_staged.py` parity test remain the arithmetic
checks.

### R0055 -- corrected to keep; not dead code

`_q8_mmq_prefill_dispatch` (`hipengine/runtime/gguf_linear.py:10209`) does match
only the un-rewritten `prefill_bf16_bf16_out`, `gemv_f32_f32_out`, and
`prefill_f32_f32_out` names, and `_wmma_prefill_dispatch` (`:10892`) does run
first in the chain (`:5024` before `:5105`). But that rewrite is gated on
`use_wmma`, and the opt-in is not unconditional. `_gemma4_block_wmma_session`
(`hipengine/runtime/gemma4.py:1022-1033`) leaves `use_wmma` false for a
verification block and for any partial block when
`HIPENGINE_GGUF_WMMA_PREFILL` is unset, and the env var is the documented
rollback lever. With `DEFAULT_PREFILL_BLOCK` at 1024 (`gemma4.py:184`, `:1185`)
and the policy's 512-row floor (`gemma4.py:1066-1072`), a 512-row tail reaches
the chain in the shipped configuration. `_forward_block` enters the MMQ session
(`gemma4.py:2552`) on both the verification path (`:2062`) and the packed path
(`:2326`), so the session is live wherever the opt-out applies.

The policy comment says the same thing in code: the chain is "only reachable
where that is the incumbent" and is what a shape runs when WMMA prefill is off
(`gemma4.py:1034-1046`). `tests/test_unit_gguf_q8_mmq_prefill_ordering.py:93`
pins a WMMA-claimed shape away from the chain, and `:118` pins the chain taking
the shape when `use_wmma` is false. The 2026-09-26 instrumentation (680 rejected
on the key mismatch, none on policy) was a WMMA-on measurement, so it proves the
shadow, not unreachability. The reorder measurement (29% slower, 1054 against
1367 tok/s; `kl_max` 0.000893 against 0.001341) and the 1.44x owner comparison
(258.6 against 373.2 ms at 512 rows, campaign iteration 154) are unchanged and
are the reason not to promote the chain, not a reason to delete it.

The entry's own removal condition ("any edit to the dense branch or the Gemma
`Q8MMQPrefillPolicy` shape table") was met on 2026-09-27 by `667abdece`, the
commit that added the Gemma table after the finding. The decision at that point
is keep. The branch goes only if the exact owner is retired or WMMA prefill
becomes unconditional for every block; then the branch, the three variant
names, and the policy table go together and the ordering guard is updated.

Minimum coherent implementation: none. Do not delete the branch or the policy.
One adjacent code-comment staleness is worth fixing when the branch is next
touched: `gemma4.py:1061` says the runner block size is 512 while
`DEFAULT_PREFILL_BLOCK` is 1024. That comment is outside this task's edit
scope. Focused check: `pytest tests/test_unit_gguf_q8_mmq_prefill_ordering.py`
(CPU only) is the guard and must stay green.

### R0056 -- corrected prose; keep until the ABI is replaced

The positive-value description is still right: `decode_slices`
(`gemma4_attention.py:358`) returns 1 for the single kernel and above one for
the dimension partition, and the legacy two-pass key-slice and combine kernels
are gone. Two things were missing. First, a negative `split_slices` is the live
flash request: the launcher takes `split_slices < 0` and re-enters it as
`-split_slices` (`gemma4_attention.hip:2213-2229`), and Python sends
`request = -request_slices if flash else slices` (`gemma4_attention.py:1048`),
with the magnitude derived by `flash_request_slices`. The flash key-slice and
combine kernels (`gemma4_attention_decode_flash_kernel`,
`..._flash_combine_kernel`) are live and are not the removed legacy pair.
Second, the caller list was incomplete: `hipengine/runtime/gemma4_decode_graph.py:584,672`
reserves the capture workspace from `decode_slices`, and the launch site itself
(`gemma4_attention.py:1027,1048`), `scripts/gemma4_teacher_forced_gate.py`
(`force_slices`, `--slices`), `tests/test_gpu_gemma4_attention_decode_parity.py`,
`tests/test_unit_gemma4_attention_scratch.py:189`,
`scratch/flash_scale_probe.py:76,84`, and
`scratch/gemma4_flash_slice_sweep.py:75` all pass a count.
`gemma4_decode_split_workspace_bytes` (`:1399`) still ignores `head_dim` and
`slices`, as recorded.

Minimum coherent implementation: replace the signed count with an explicit route
selection carrying the single-kernel oracle, the two-pass dimension partition,
and the flash key-slice request; migrate every caller above; then drop
`decode_slices`, the `split_slices` argument, and the unused workspace
parameters. Do not delete the negative request as if it were the legacy ABI.
Focused checks: `tests/test_unit_gemma4_attention_scratch.py` (CPU), the GPU
decode-parity test, and one public generate past 1024 keys (dimension pass) plus
one with a flash-preferring plan at 256 or more keys (negative request).
