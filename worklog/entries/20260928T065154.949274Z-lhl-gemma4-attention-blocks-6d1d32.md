# the split does not add blocks and my 6.9x block-count figure was a per-head normalization

## Summary

Two measured results and one correction to my own previous entry.

The bench now reads `decode_selection()` and `decode_slices()` back and prints the
launched block count, so a row says which path ran instead of leaving it to
inference. Running it resolved the discrepancy `20260928T065052` flagged, and it
showed that my own quoted figure was wrong.

## Result 1: the split engages, and adds no blocks

`sliding` geometry, `tokens=1`, `mask=keep`, 20 iterations, gfx1151:

| keys | selection | slices | blocks | us/launch | unique GB/s | issued GB/s |
|---|---|---|---|---|---|---|
| 512 | 1 | 1 | 16 | 96.7 | 10.8 | 260.3 |
| 1024 | 2 | 4 | **16** | 225.2 | 9.3 | 223.5 |
| 2048 | 2 | 4 | **16** | 359.9 | 11.7 | 279.7 |
| 4096 | 2 | 4 | **16** | 572.9 | 14.6 | 351.4 |

So the two-phase split **is** selected from 1024 keys up -- the previous entry's
doubt about whether it engages is settled -- and **the block count does not move**.
`blocks` is `tokens * num_heads` = 16 in every row. That confirms what
`decode_slices`'s docstring says: the split partitions output dimensions, not keys,
so it divides work within the same 16 blocks rather than adding any.

The probe's recommendation and the implementation are therefore not the same
thing, and the discrepancy was real rather than a stale docstring. The
block-count lever is **still open**.

## Result 2: the same entry point reaches 3.2x the bandwidth at 4x the blocks

`keys=512`, `sliding`, varying `--tokens`:

| tokens | selection | blocks | us/launch | issued GB/s |
|---|---|---|---|---|
| 1 | 1 | 16 | 97.8 | 257.4 |
| 2 | 0 | 32 | 119.7 | 420.4 |
| 4 | 0 | 64 | 122.8 | **819.9** |

Four times the work costs 1.26x the time, and issued bandwidth rises from 257 GB/s
to 820 GB/s of a ~960 GB/s peak. That is the starvation signature.

**This is suggestive, not controlled**, and the reason matters: `selection` changes
from 1 to 0 between the first row and the rest, so the rows differ in both block
count and kernel. The controlled version of this experiment is the probe's own,
which varies `num_heads` through one kernel.

## Correction: 6.9x was `us/head`, not a speedup

`20260928T065052` said the probe's finding was "worth up to 6.9x on the decode
attention share". That is wrong, and the probe's own table says so:

```
heads  blocks  us/launch  us/head
   16      16      280.6     17.54
   64      64      163.2      2.55
  128     128      201.7      1.58
```

Total launch time falls **280.6 -> 163.2 us = 1.72x**, and 128 blocks is worse in
total time than 64. The 6.9x is `us/head`, which divides by a head count that grew
4x; it is a normalized figure, not a speedup, and reading it as one inflated the
lever by 4x.

The honest figure is **1.72x on the attention kernel**, with the machine saturating
around 64 blocks. On the decode census's 19.1% attention share that is about
19% x (1 - 1/1.72) = **8% end to end** -- real, and well short of the 1.53x the
objective needs on its own.

## Changes

- `scripts/gemma4_attention_decode_bench.py`: reads `decode_selection()` and
  `decode_slices()` back after the timed loop and adds `selection`, `slices` and
  `blocks` to each row and to the printed line. The three decode paths are
  numerically close by design, so a timing cannot distinguish them; without this a
  row does not say what it measured, which is also the project's requirement to
  confirm the intended path ran.

## Validation

```
env -u ROCR_VISIBLE_DEVICES PYTHONPATH=. .venv/bin/python \
    scripts/gemma4_attention_decode_bench.py --keys 512 1024 2048 4096 \
    --geometry sliding --iters 20
```

and the same command with `--keys 512 --tokens 1|2|4`. Both completed and are the
source of every number above. Measured on gfx1151, 1 device, 20 iterations per row,
`head_dim=256`, `num_heads=16`, `num_kv_heads=2`.

The bench's own note applies: it passes the full capacity as `keys`, so each row is
a lower bound on the production cost at that context.

## Next

1. A key-range split that holds traffic constant is the remaining lever, worth
   ~1.72x on attention and ~8% end to end. It is not what `decode_slices` selects
   today.
2. The port stays dropped (`20260928T065052`).
3. 512 keys -- the production sliding-window context -- takes the unsplit path
   (`slices=1`) at 10.8 GB/s of useful traffic. Whether the split helps there at
   all is untested; the rows above only show it engages from 1024.
