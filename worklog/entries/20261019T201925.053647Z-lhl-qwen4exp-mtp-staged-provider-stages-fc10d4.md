# Qwen4Exp MTP staged proposal, target rows and acceptance

## Summary

M1 provider-stage prerequisite of the Flash-Next serving mixed-execution track
([campaign](../../docs/campaigns/QWEN38FN-SERVING-FOLLOWUP.md)). In
`hipengine/generation/qwen4_exp_mtp.py`, `iter_generate` performed draft
proposal, target verification and accepted-prefix commit inside one generator
step, so no caller could prepare a proposal without the target and no caller
could supply target row results from somewhere else. The three stages now exist
as separately callable functions, and the existing batched-verification cycle
runs through them. Committed tokens, cycle splits, sampler/grammar/RNG ownership,
telemetry, the serial fallback, candidate budgets, demotion, environment
controls and every capability limit are unchanged.

This is a prerequisite, not shared execution. One speculative request per cycle
is still the only admitted shape; candidate rows are not merged with
autoregressive peers and no capability or plan advertises that.

## Changes

- `hipengine/generation/qwen4_exp_mtp_stages.py` (new, torch-free, pure host
  code):
  - `Qwen4ExpMTPProposal` — immutable prepared chain naming `start_position`,
    `root_token` and `candidates`, with `rows`/`depth` derived.
  - `Qwen4ExpMTPTargetRows` — immutable per-row target results (`token_ids`,
    optional per-row `logits`, one hidden row per verified row).
  - `Qwen4ExpMTPAcceptance` — immutable accepted prefix (`tokens`, `accepted`,
    `mismatch_token`, `consumed_rows`, new `root_token`/`root_hidden`, and the
    caller's own finish object).
  - `prepare_proposal(draft_runner, *, start_position, root_token,
    target_hidden_seed, draft_n_max, compact_output=False)` — draft-only. It
    takes no target owner, so it cannot step, prefill, verify or commit the
    target, and it owns the pre-proposal cursor invariant.
  - `verify_proposal_rows(target_runner, proposal, *, capture_kwargs=None)` —
    calls the target's state-row verifier once for `(root, *candidates)` and
    returns the rows. It commits nothing and decides nothing.
  - `consume_proposal_rows(proposal, rows, *, prior_tokens, select,
    finish_for)` — consumes rows in order, sampling only the consumed prefix, so
    a later row scored with speculative history cannot advance RNG or
    processors after an earlier rejection.
- `hipengine/generation/qwen4_exp_mtp.py`: `iter_generate`'s batched branch now
  calls the three stages; the device commit of the consumed rows, the draft
  catch-up on a full match, the draft trim and the sampler/grammar closures stay
  in the iterator. The serial fallback still verifies one row at a time inside
  its own step and does not use the row stages.
- `tests/test_unit_qwen4exp_mtp_stages.py` (new, 20 tests): stage contracts plus
  iterator integration.

Design points the unit keeps:

- **Preparation is structurally target-free.** `prepare_proposal` has no target
  parameter (asserted by signature), and the iterator test snapshots the target
  owner's prefill/step/verify counters around every preparation call.
- **Row consumption order is the acceptance rule.** Row `i`'s target token
  checks candidate `i`; the first mismatch ends the cycle with the target's own
  token for that row; a full match consumes the bonus row.
- **One target row per committed token.** `consumed_rows == len(tokens)` is an
  invariant of the acceptance result, and the row set must hold
  `len(candidates) + 1` rows.
- **Hidden seeds are part of the row contract.** A row set without one hidden
  row per verified row is refused, because the next proposal needs the last
  consumed row's hidden seed.
