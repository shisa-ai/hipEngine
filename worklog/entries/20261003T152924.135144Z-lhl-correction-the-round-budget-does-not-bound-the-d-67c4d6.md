# Correction: the round budget does not bound the default prefill path

## Summary

Supersedes the mechanism in
`worklog/entries/20261003T152724.639601Z-lhl-rt-1-chunk-4096-is-gated-on-the-round-prefill-bu-3e7462.md`.
That entry's **conclusion** survives and is in fact strengthened; its **mechanism
is wrong for the default scheduler policy** and is corrected here.

**What was claimed.** That the chunk the engine runs is
`min(prefill_chunk_size, round_prefill_token_budget)`, that the round budget is
1024, and therefore that raising the chunk cap to 4096 "either does nothing at
all while the round budget stays 1024, or requires raising the round budget to
4096". The entry called the round budget the binding constraint.

**What is actually true.** The `min(...)` split is applied **only** by
`_run_token_budget_round`, which runs **only** when
`prefill_decode_policy == "token_budget"`:

```python
# hipengine/generation/engine_loop.py:2218
if self.prefill_decode_policy == "token_budget":
    events.extend(self._run_token_budget_round())
    return tuple(events)
...
# :2245 - the default path
prefill = self.scheduler.next_prefill_work(chunk_size=self.prefill_chunk_size)
events.extend(self._run_prefill(prefill))
return tuple(events)
```

`EngineLoopConfig.prefill_decode_policy` defaults to **`protect_decode`**
(`engine_loop.py:101`, `:1883`; `_env_prefill_decode_policy` at `:1832`), and
`next_prefill_work` uses `chunk_size` directly (`batch_scheduler.py:1218`, no
extra cap). So on the **default** path one round runs exactly one prefill chunk
of `self.prefill_chunk_size` (= `max_prefill_chunk_tokens`), and
**raising the cap to 4096 does raise the executed chunk to 4096**.

**Consequences, restated correctly.**

- The round-budget constraint is real but **policy-scoped**: it binds under
  `token_budget` only, where the cap alone is inert and the round budget must
  rise with it. `tests/test_unit_engine_loop_prefill_chunk.py:26` pins
  `DEFAULT_MAX_PREFILL_CHUNK_TOKENS == DEFAULT_ROUND_PREFILL_TOKEN_BUDGET` as a
  cross-policy consistency pin, not as evidence that the round budget bounds the
  default path. The superseded entry read that pin as the latter.
- **Either policy reaches 4096 only by quadrupling per-tick prefill work.** On
  the default path that is caused directly by the cap, since one round is one
  chunk; under `token_budget` it is caused by the round budget that must rise
  alongside the cap. So the conclusion - that the real blocker is the per-tick
  prefill bound protecting decode interleaving, and the missing experiment is a
  decode-interleaving measurement rather than a capacity probe - is unchanged,
  and the causal chain is shorter than the superseded entry claimed.
- **A larger workspace owner still cannot deliver the `-4.94%`.** This half of
  the superseded entry is correct and rests on the project's own `RT-3`
  two-owner A/B (1024 vs 4096 rows against a 4352 sequence: 3.2068 s vs
  3.1730 s, 1.06% slower on the small owner at 0.017x the within-arm spread,
  identical `logits_sha256`): the workspace is scratch and kernel work scales
  with the actual token count, so owner admission changes nothing. What is
  corrected is only the *reason* the owner is not the lever - it is not that a
  round budget caps the chunk, it is that the owner does not set the chunk at
  all.
- **The `-4.94%` remains un-retracted** and remains a direct-prefill-path
  result (`qwen4exp_profile_gap.py:717` calls `runner.prefill(ids)`, bypassing
  the engine loop entirely).

**Method note.** The superseded entry generalised from one call site without
checking which policy reaches it, and the equal-pair test read as confirmation
rather than as a constraint scoped to one branch. The correction came from
reading the policy dispatch at `:2218` and the default at `:101`. Both the
ledger segment and the `docs/REFACTOR.md` note are corrected in this unit.
