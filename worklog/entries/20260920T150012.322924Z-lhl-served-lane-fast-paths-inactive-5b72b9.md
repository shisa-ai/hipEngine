# prefix cache and MTP were both inactive on the served lane

## Summary

The gfx1151 `Qwen3.8-27B-Q4_K_M` served lane felt slow for two configuration
reasons, both measured on the live server before and after a restart:

1. **The prefix cache was off.** `hipengine serve` defaults `--prefix-cache` to
   `off`, so every turn re-prefilled its whole prompt: a 7,208-token prompt cost
   30.9 s of prefill. The engine loop's own default is `radix`, and `docs/ENVS.md`
   claimed `radix` for the server row, so the running server was not what the docs
   described. With `--prefix-cache radix` the same prompt costs 0.8 s on a resend
   and 0.9 s with a new suffix (`/ready`: `hits=2`, `reused_tokens=14336`).
2. **MTP was configured but never served.** `hipengine_mtp_serving 1` while
   `hipengine_mtp_requests_total 0`: every response reported
   `effective_route=default`, `decision_reason=kv_storage_not_qualified`. The
   server defaults `--kv-storage` to `int8_per_token_head`, and the only certified
   MTP serving evidence cell is `bf16` (`_evidence_checks` requires
   `key.kv_storage == row.kv_storage`), so the route fell back to autoregressive
   decode. Switching to `--kv-storage bf16` costs nothing here: at 262,144 context
   the bf16 geometry needs 207,456 bytes/token (~52 GiB of a 98 GiB KV budget), so
   `/ready` still reports `allocatable_context_tokens=262144`.

Measured after both flags (same host, same model, greedy, live server):

| case | before | after |
| --- | --- | --- |
| 7,208-token prompt, first send | 30.9 s | 30.9 s |
| 7,208-token prompt, resend | 30.9 s | **0.8 s** |
| 7,208-token prompt, +1 new sentence | 30.9 s | **0.9 s** |
| 128-token greedy generation, short prompt | 9.72 tok/s (AR) | **24.62 tok/s** (MTP, acceptance 0.72) |
| 48-token greedy generation, 69-token prompt | 8.9 tok/s | 20.9 tok/s (MTP) |
| 48-token greedy generation, 7.2k prompt | 8.95 tok/s | 8.95 tok/s (still AR) |

Two limits remain, both measured rather than assumed:

- **MTP stops engaging beyond ~512 context tokens.** Greedy requests with 69, 159,
  and 309 prompt tokens served through `speculative_mtp`; 609 and 1,209 prompt
  tokens returned `effective_route=default` with `decision_reason=backend_k0_fallback`
  (the server selected the MTP route and the engine ran AR: its fixed native
  target-graph bucket did not cover the request). An agent turn with a 20k-token
  prompt therefore still decodes at the autoregressive rate, ~9 tok/s.
- **Sampled decode is much slower than greedy on long context**: 48 tokens at
  `temperature=0.7, top_p=0.95` against a 7.2k-token prompt took 38.3 s
  (1.25 tok/s) against 8.95 tok/s for the same request at `temperature=0`. Short
  prompts show the same shape (6.5 vs 18.1 tok/s). The server's request default is
  `temperature=0.0`, so clients that omit sampling parameters are unaffected.

## Changes

- `docs/ENVS.md`: the `HIPENGINE_PREFIX_CACHE` row now states the server default
  (`off`) and that the library/engine-loop default is `radix`, instead of claiming
  `radix` for the server.
- Local launcher (`/tmp/hsrv.sh`, not tracked): the pane's server now runs with
  `--prefix-cache radix --kv-storage bf16` alongside `--info --metrics prometheus
  --log-color always`.

## Validation

- Measurements above are single-sample live A/B runs on the pane's server (gfx1151,
  `Qwen3.8-27B-Q4_K_M`, greedy, `max_tokens` 48-128), not the retained benchmark
  protocol; each configuration was repeated and was stable across tries. The
  retained MTP serving evidence for the bf16 cell at c1/1024-context is 9.45 ->
  12.42 tok/s (1.31x), so the 2.5x seen here is a different (serving, short-context)
  configuration and is reported as such.
- `/ready` after the restart: `prefix_cache.mode=radix`, `kv_capacity.storage=bf16`,
  `allocatable_context_tokens=262144`.
- MTP accounting: `mtp_requests_total=1`, `draft_tokens_accepted_total=22`,
  `draft_acceptance_rate=0.917` on the first served request.

## Next

- **Server defaults are the open decision.** The prefix cache is a measured win and
  the engine already defaults to `radix`, yet the server CLI defaults to `off`; and
  the default `int8_per_token_head` KV silently disqualifies the only certified MTP
  cell. Both want either a default change (with the KV-capacity trade-off measured
  per host) or a loud startup warning when MTP is enabled and the KV storage
  disqualifies its evidence.
- **MTP has no certified scope for long context.** Every agent turn beyond ~512
  tokens pays the AR rate. Widening it is a benchmark/certification task (the
  retained cell is `qwen38-q4km-gfx1151-strict-bf16-cap4-realized-c1-b3`), not a
  flag.
- **Sampled decode on long context is 7x slower than greedy** (1.25 vs 8.95 tok/s
  at 7.2k). This looks like a per-token cost in the sampled path rather than
  attention, and it deserves its own profile before any claim about it.
