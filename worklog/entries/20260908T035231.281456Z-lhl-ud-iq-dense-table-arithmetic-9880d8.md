# IQ dense decode: sign/magnitude table arithmetic, and a measured rejection

## Summary

First unit of the raw-IQ dense optimization pass. Two `__constant__` table
lookups in the strict decode inner loop are replaced by arithmetic that
produces bit-identical values; a third substitution of the same shape was
implemented, measured, and **rejected**. The retained change is an
instruction-count reduction, not a claimed throughput win: it sits at or below
this host's resolvable noise.

## Method: interleaved A/B, because the single-shot leaf bench cannot resolve this

The existing leaf-bandwidth bench (`/tmp/ud-gemv-bandwidth.py`, one variant per
process) reported IQ3_S at 58.8 then 64.8 GB/s across two runs of *identical
machine code*. Sequential single-variant runs on this laptop cannot resolve
anything under ~10%.

Replacement screen: `scratchpad/ab_leaf.py` builds each candidate into its own
cache entry and alternates their launches inside one process, reporting
min-of-7-rounds x 30 reps. Interleaving cancels thermal drift; the minimum is
far more stable than the mean under a power cap. IQ3_S and Q3_K compile to
byte-identical ISA under every variant below, so their spread is a direct
readout of the residual noise floor: **+/-5%**.

## Changes

`hipengine/kernels/hip_gfx1100/quant/gguf_iq_dense.hip`:

1. **`iq_signs[128]` -> `iq_sign_bits(i) = i | ((__popc(i) & 1) << 7)`.** The
   published table is exactly `i` carrying its own odd-parity flag in bit 7.
   Verified entry-for-entry against the llama.cpp table. Removes 16
   `global_load_u8` per inner body from IQ3_XXS and IQ2_XS. The table is
   deleted from `gguf_iq_dense_tables.h` and now lives in the test as the
   reference the arithmetic is checked against.
2. **IQ2_XS magnitude ladder -> one packed immediate.**
   `code == 0 ? 8 : (code == 1 ? 25 : 43)` becomes
   `(0x2B2B1908u >> (8*code)) & 0xff`, replacing a two-deep compare/select
   chain per decoded element.

ISA effect (gfx1151, `bf16_bf16_out`, T=8, per inner body):

| quant | loads before | loads after | VALU before | VALU after |
| --- | --- | --- | --- | --- |
| IQ3_XXS | 50 | 34 | 396 | 429 |
| IQ2_XS | 50 | 34 | 569 | 562 |

Measured (interleaved A/B, min-of-7, gfx1151 zbook): IQ2_XS 41.9 -> 43.9 GB/s
(+4.9%), IQ3_XXS 74.6 -> 75.4 (+1.1%). Both are inside the +/-5% floor
established by the unchanged-ISA quants in the same table, so **no throughput
claim is made**. The retainable evidence is the instruction-count delta plus
bit-exact parity.

## Rejected: IQ4 codebook as packed immediates

`iq4_values[16]` is `__device__ __constant__ int8_t`; under a lane-varying
index that is global memory, and it compiled to one `global_load_i8` per
decoded element (16 per inner body). Two register-resident replacements were
built and measured:

- select tree over four `uint32` immediates: IQ4_XS VALU 329 -> 489;
- `__builtin_amdgcn_perm` byte gather (2x `v_perm_b32` + select): VALU 329 ->
  441, loads 34 -> 18.

Interleaved A/B, same table as above: IQ4_XS **84.6 -> 80.4 GB/s (-5.0%)**.

The reason matters for the rest of this campaign: this kernel already runs at
the full 16 waves/SIMD with 43 VGPRs and zero scratch, so VMEM latency is
thoroughly hidden and the limiter is VALU issue. Trading an L1-resident byte
load for ~7 VALU is the wrong direction here. **Removing loads is only a win
when it does not add arithmetic.** The candidate is dropped, not deferred; the
kernel carries a comment saying so, so it is not re-derived.

This also corrects the prediction in the session's planning artifact, which
ranked this substitution as the highest value-per-line item in the queue.
