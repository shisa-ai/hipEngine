# the context ceiling is reproduced as a test a runner one key past it refuses by name

## Summary

The chain is no longer a code reading. `tests/test_unit_gemma4_attention_context_ceiling.py`
constructs a real `Gemma4Runner` at and above the ceiling and pins the behaviour.
**7 passed.**

```
uv run pytest tests/test_unit_gemma4_attention_context_ceiling.py -v
# 7 passed in 0.39s
```

The reproduction is that a runner configured with a capacity one key past the
ceiling raises `NotImplementedError` naming the geometry and the key count, **before
allocating anything**. That last part is asserted, not incidental: the stub
allocator fails the test if it is ever reached, so a future change that reorders the
check after allocation is caught.

## What the tests pin

| test | what it holds |
|---|---|
| `test_the_ceiling_is_where_the_lds_budget_runs_out` | the boundary is the LDS budget's, bisected from the real function, at both widths |
| `test_a_capacity_at_the_ceiling_constructs` | the ceiling itself is **accepted** -- an off-by-one the other way would refuse a context the kernel can serve |
| `test_a_capacity_above_the_ceiling_is_refused_loudly` | one key past refuses, by name, before allocating |
| `test_a_sliding_window_does_not_lift_the_ceiling` | a window does not help, because the check is on capacity and not on the live key count |

That last one is the one worth having. A sliding layer bounds how many keys any
query attends to, so it is natural to assume the window lifts the limit. It does
not: the construction path validates the full capacity against the LDS budget
regardless. The test asserts the reading so the two cannot drift.

## CPU-only, deliberately

`Gemma4Runner.__post_init__` reads only `weights.config`, so a `SimpleNamespace`
stands in for the weights and no device is touched. The file carries no HIP guard
because it needs no HIP, which puts it in the default unit tier where a change to
the attention kernel's LDS layout will see it immediately.

## What this does not establish

The cap is now reproduced, but **no end-to-end request has been run at a context
above it**, and the objective's own numbers came from runs that constructed
successfully. Whether any production caller in this tree actually configures a
capacity that high is still unchecked -- the tests show the refusal happens, not that
anything in the shipped path triggers it.
