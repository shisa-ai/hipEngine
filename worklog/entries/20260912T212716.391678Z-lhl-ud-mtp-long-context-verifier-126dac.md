# The MTP verifier degenerates to the AR route at 1024 context

## Summary

The Phase 5 4096-token point returned **mean = p95 = p99 = max KL = 0.000e+00
and top-1 = 1.0000 over 162 rows**. A perfect score over 162 rows is not a
result; it is the signature of a comparison that is not happening. It is not a
harness bug. Above 1023 active context the packed multi-row verifier stops
running multi-row arithmetic and reproduces the single-row AR route
bit-for-bit, so the exactness gate is trivially satisfied and the verification
buys nothing.

## Mechanism

`Qwen35GGUFResidentSession.verify_target_block` decides the attention chain per
layer from `hipengine/runtime/qwen35_gguf_runner.py`:

```python
strict_long_rows = (
    rows > 1
    and not bool(self.weights.config.is_moe)
    and _use_gguf_full_attention_split_decode(start_position + rows)
)
staged_dense_linear = (
    layer_type == LINEAR_ATTENTION
    and rows > 1
    and not bool(self.weights.config.is_moe)
    and not strict_long_rows
)
```

When `staged_dense_linear` holds, the layer runs
`_run_linear_attention_attn_chain_rows_exact`, the batched exact rows chain.
When `strict_long_rows` suppresses it, the layer falls through to the
`else` branch, which is a literal per-row loop:

```python
else:
    for row in range(rows):
        position = start_position + row
        ...
        row_dispatch = native_batch_decode_session(False)
```

`_use_gguf_full_attention_split_decode` is
`active_context >= _GGUF_FULL_ATTN_DECODE_SPLIT_MIN_CONTEXT_DEFAULT`, and that
default is `1024` (line 10544). The per-row loop uses the same per-token
kernels as `session.step`, so its logits are bit-identical to the AR teacher
and `max_abs_diff` is exactly `0.0`.

## Measured boundary

`scripts/ud_mtp_ar_verify_numerics_gate.py` on
`Qwen3.8-27B-UD-Q4_K_M.gguf`, one canonical prompt, one repeat, budget 1
(`rows = 2`):

| prompt tokens | start + rows | max_abs_diff | kl_max | route |
| ---: | ---: | ---: | ---: | --- |
| 768 | 770 | 8.75e-02 | 3.60e-08 | batched exact rows |
| 1019 | 1021 | 7.34e-02 | 4.65e-09 | batched exact rows |
| 1020 | 1022 | 2.80e-01 | 4.70e-08 | batched exact rows |
| 1021 | 1023 | 2.38e-01 | 9.54e-08 | batched exact rows |
| 1022 | **1024** | **0.0** | **0.0** | per-row |
| 1023 | 1025 | 0.0 | 0.0 | per-row |
| 1024 | 1026 | 0.0 | 0.0 | per-row |
| 1536 | 1538 | 0.0 | 0.0 | per-row |
| 2048 | 2050 | 0.0 | 0.0 | per-row |
| 4096 | 4098 | 0.0 | 0.0 | per-row |

The flip is exactly at `start_position + rows == 1024`, which is the
`_use_gguf_full_attention_split_decode` threshold, and not at the
`target_context_k0` policy bound of `min(1023, max_sequence_length)` in
`hipengine/generation/qwen35_gguf_mtp2.py`. The two agree on the same number
for a different reason: the adapter refuses MTP when `prompt + 1 >= 1023`, and
the verifier stops batching at `prompt + rows >= 1024`. A three-budget run
crosses one row earlier, at 1020 prompt tokens for `rows = 4`.

## Why it matters

The 4096-token point cannot qualify the multi-row verifier, because at 4096
there is no multi-row verifier to qualify. Two consequences:

- The honest declared `context_max` for the UD MTP envelope is **1023**, and it
  is bounded by the verifier rather than only by adapter policy. A measured
  verifier KL of zero above that line is evidence about the per-row fallback,
  not about the verifier, and must not be reported as a long-context pass.
- The batched exact rows chain is already implemented and already exact; it is
  simply gated off above the split-decode threshold. Admitting it in the
  split-decode regime is the concrete long-context MTP optimization, and it is
  the difference between MTP that accelerates and MTP that is a no-op.
