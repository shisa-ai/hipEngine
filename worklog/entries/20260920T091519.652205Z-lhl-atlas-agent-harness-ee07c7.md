# atlas 1:1 harness: cross-quant by necessity, and atlas needs a ROCm build and batch 3 at 256K

## Summary

Built `benchmarks/atlas-agent/` as a self-contained, replicable 1:1 comparison
between hipEngine and `~/atlas` on this host. Three setup findings are worth
recording before any number is produced, because each one silently invalidates
the comparison if missed.

**1. The quant cannot be matched, so this is a cross-quant comparison.** Atlas's
kernels are organised `kernels/<platform>/<model>/<quant>/` and every entry is
`nvfp4`; a search for k-quant kernel directories across its tree returns nothing,
so atlas cannot load a Q4_K_M GGUF. hipEngine's GGUF reader knows the NVFP4
*layout* (`hipengine/quant/gguf.py`) but has no NVFP4 execution kernels. Each side
therefore runs its own shipped quant -- atlas `nvidia/Qwen3.8-27B-NVFP4` (W4A8
DP4A), hipEngine Q4_K_M -- and every reported number must say so. Matched instead:
model, host, GPU, protocol, client, BF16 KV, 256K context, prefix caching on.
Speculation depth differs by necessity too: atlas K=4 is its headline, K=3 is the
deepest budget hipEngine's serving evidence qualifies.

**2. Atlas needs a ROCm build, and only `serve-amd.sh` can run it.** Both
`~/atlas/target/release/spark` and `/tmp/atlas-e2e/target/release/spark` were CUDA
builds linking `libcuda.so` and could not start. `ATLAS_TARGET_HW=strix-hip
./build-amd.sh` with `ATLAS_ROCM_HOME` pointed at the conda ROCm SDK
(`_rocm_sdk_devel`, HIP 7.15 -- atlas's README numbers were taken on 7.13) built
in **2m02s** with a warm kernel cache (122 `.cu` files across four `strix-hip`
targets). The resulting binary still references `libcuda.so` because that is
atlas's HIP-to-CUDA shim, which `build.rs` writes to
`target/release/build/atlas-kernels-*/out`; `serve-amd.sh` locates it and prepends
it to `LD_LIBRARY_PATH`, so invoking the binary directly fails and the script must
be used. atlas is a read-only peer: the build writes only to its own `target/`.

**3. Atlas at 256K supports `--max-batch-size` 3, and overcommitting fails
silently rather than degrading.** atlas reports `max_model_len: 262144`, so 256K
is accepted, but it sizes the KV pool from `--gpu-memory-utilization` and then
warns: `KV OVERCOMMIT: pool fits 3 seq(s) at full --max-seq-len=262144 but
--max-batch-size=8 requested`. With batch 8 the server still came up and answered
`/v1/models`, then failed every prefill with
`alloc_sequence failed: cuMemsetD32Async failed: status 901`, never allocated its
SSM MTP intermediate buffers, and core-dumped on teardown. `MAX_BATCH` therefore
defaults to 3 in `serve-atlas.sh`, and a wider concurrency ladder needs a shorter
`MAX_SEQ_LEN`.

Memory check for 256K, computed from the checkpoint config (64 layers, of which
48 are `linear_attention` with constant-size state and 16 are `full_attention`,
4 KV heads, head_dim 256): 16 x 4 x 256 x 2 x 2 bytes = 64 KB/token, so about
16 GB of BF16 KV at 262144 tokens, and `max_position_embeddings` is 262144 so no
rope scaling is needed. Both engines fit this host's 120 GB GTT.

**Correction carried in the same unit.** Earlier in this session I quoted a
"raising the MTP window alone measures 0.57x" figure as current-head fact. It is a
2026-09-17 diagnostic at ~3,530 prompt tokens and it predates the 2026-09-18
verifier-leaf fix (`docs/REFACTOR.md:581`), which measures cycle wall
8.129 s -> 7.893 s median with 10/10 direct cases exact. The long-context MTP
workstream is tracked as tasks #39-#43 in the order: current-head profiling and
graph correctness first, then long-context proposal capture, then attention
optimization where measured necessary.

## Changes

- `benchmarks/atlas-agent/README.md` -- the protocol, the matched/unmatched table,
  prerequisites, replication steps, knobs, arms, and how to read the result.
- `benchmarks/atlas-agent/http_1to1_bench.py` -- the engine-agnostic OpenAI
  streaming client, moved out of `scripts/`. It measures from the SSE stream only,
  with no engine-specific field, so one script runs unchanged against both servers.
  Completion length is fixed and early stop is not expected, so both engines emit
  exactly N tokens and the rate does not depend on tokenizer or SSE chunking; the
  delta count and any `usage` block are both recorded so a chunk-batching engine
  cannot have its rate overstated.
- `benchmarks/atlas-agent/serve-hipengine.sh`, `serve-atlas.sh` -- the two server
  configurations, with the shim, ROCm and batch-size constraints documented inline.
- `benchmarks/atlas-agent/run.sh` -- orchestration, one engine at a time, with the
  readiness wait, capability probe, arms and teardown.
- `benchmarks/atlas-agent/analyze.py` -- assembles the artifact and carries the
  caveat list, so the caveats travel with the numbers.

## Validation

Build: `ATLAS_TARGET_HW=strix-hip ATLAS_TARGET_MODEL='*' ./build-amd.sh` exit 0 in
2m02s, HIP 7.15.26333, clang 23.0.0git, atlas head
`95f674951d6ab8f491f7907804a462c170f9c048`.
Atlas startup at `MAX_SEQ_LEN=262144`: `/v1/models` returned
`{"id":"qwen3.8-27b-nvfp4","max_model_len":262144}` and the log recorded
`Speculative decoding: ENABLED (4 drafts/step)`, `MTP gate: throughput-arbitrated
(K=4)`, `Scheduler started (batched mode, max_batch=8, mtp=true)`.
The harness parses atlas's SSE framing and its `/v1/chat/completions` route
answers; the first attempt's failures were the batch overcommit above.
