# Audit catchup positions and post-K0 proposal staleness

## Summary

Instrument the one-shot post-reject cooldown with the device-chain oracle and
wrapped `advance_state_only` to audit the catchup's positional/hidden
semantics. Result: the catchup mechanics are verifiably correct, but post-K0
spec proposals are stale-shifted, narrowing the defect to frontier/proposal
seeding after K0-decode cycles.

## Changes

- `/tmp/qwen38_c2_catchup_probe.py` (session-local): wraps
  `advance_state_only` to log (request, position, token); runs the full suite
  with `HIPENGINE_SPECDEC2_DEVICE_CHAIN_ORACLE=1` and
  `HIPENGINE_SPECDEC2_POST_REJECT_COOLDOWN=1`.
- No tree changes; the cooldown flag remains default-off.

## Validation

- 51 advance events; all 44 catchup advances show correct continuity:
  catchup consumes g1@(p+1), the K0 cycle commits g2@(p+2), and the next spec
  root is g2@(p+2) with a distinct token (delta 1, no hole/double-consume).
- `last_target_hidden` provenance audited in code: the packed batch commit
  selects the commit row's hidden via `dflash_commit_chain_i32` into
  `_hidden_a` (singleton decode sets the decoded row's trunk hidden), so the
  catchup seeds from the correct row by construction.
- Whole-group dynamics confirmed: mixed K0/K2 plans fail closed in
  `claims_fit` and replan all-K0, so BOTH requests get catchup advances when
  either rejects (economics cost; 49 catchups vs ~26 rejects).
- Residual defect: post-K0 spec proposals are stale-shifted. rid-27
  `general_en_explain`: advance consumed 65393@50, frontier root 2998@51, yet
  the cycle proposed 65393 (position 50's token) - a two-position lag.
  Post-accept spec cycles stay healthy (0.885-0.920) and first cycles are
  1.000, so the break is specific to cycles seeded after K0 decodes: the
  frontier `target_hidden`/proposal input path after a K0-decode cycle.
- Token signatures (post-reject, cooldown): code 6/6 correct; en 1 correct,
  7 other, 2 `proposes_g1`; ja 2 correct, 2 other, 2 `proposes_g1`.
