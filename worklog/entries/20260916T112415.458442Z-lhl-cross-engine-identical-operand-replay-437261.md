# Build and validate the identical-operand cross-engine replay harness

## Summary

Built the missing bridge: a harness that runs hipEngine and the pinned
llama.cpp-family comparator on **byte-identical operands** for one dense
projection, with dispatch proof, numerical attribution and counterbalanced
timing. It is validated end-to-end on Q8_0 `attn_qkv`.

The first result it produces is large. On `layers.8.attn_qkv` (rows=1024,
K=2560, M=10240, 53.69 GFLOP) hipEngine's production kernel takes **17.361 ms**
against the comparator's **1.492 ms** — **11.70x**. The exact-arithmetic kernel
takes 13.29x. One projection geometry accounts for **2500 ms** of a 4096-token
prefill, 11.2% of the most recent published 4K prefill time.

Radeon 8060S / `gfx1151`, three counterbalanced rounds of ten repetitions:

| Engine | Kernel | Complete ms | TFLOP/s | Conversion ms |
| --- | --- | ---: | ---: | ---: |
| hipEngine production | `coltile8_rowbatch4_wave_scale_f32_f32_out` | 17.361 | 3.09 | fused |
| hipEngine strict | `coltile8_rowbatch4_f32_f32_out` | 19.716 | 2.72 | fused |
| comparator | `mmb_dense_kernel<128, 256, 64, 64, 1>` | **1.492** | **35.99** | 0.149 |
| comparator, cache hit | same | 1.342 | 40.01 | 0 |

The gap has a measured mechanism rather than a suspected one: hipEngine's kernel
covers 4 rows per block with 512 bytes of LDS, the comparator's covers 256 rows
with 55,296 bytes. Derived weight traffic is 7.13 GB against 0.111 GB.

The result also closes the open `attn_qkv` byte accounting that
`benchmarks/README.md` carried as a flagged caveat. That caveat counted each
operand once, giving 80.3 MB per launch and an impossible 4.6 TB/s. From the
measured launch geometry the operation moves 20.6 GB per launch — 7.13 GB of
weight reads, 13.42 GB of activation reads and 41.9 MB of output writes — which
is 1186 GB/s aggregate. Serving that needs L2 rather than DRAM, and it can: the
weight is 27.85 MB and the activation 10.49 MB, both inside the 32 MB MALL.

## Changes

New harness under `tools/replay_bridge/`:

- `capture_packet.py` — hooks the dense-linear dispatch in a real production
  prefill and records one packet: the resolved dispatch key and launch ABI, the
  raw weight bytes with a sha256 identity, the activation matrix in the dtype the
  kernel was actually handed, the output, and the model/prompt/chunk/layer
  geometry. It wraps the kernel, calls it unchanged, and copies buffers aside
  afterwards, so no model output changes.
- `build_shim.sh` — builds the comparator adapter against a pinned build. It
  derives the compile command from that build's own `compile_commands.json` and
  includes that revision's `common.cuh`, so the shim cannot silently target a
  different toolchain or a different context layout.
- `mmb_replay_shim.cpp` — drives the comparator's exported
  `ggml_cuda_mul_mat_mmb` on caller-supplied operands.
- `hipengine_adapter.py` — loads a packet, requires an exact-key registration,
  and runs the recorded kernel on the packet's bytes.
- `replay_ab.py` — runs both adapters on one packet, counterbalances the round
  order, and reports complete-operation time, conversion cost separately, and the
  numerical difference against four float64 references.

Result artifact at `benchmarks/results/2026-09-16-cross-engine-replay/`
(`README.md`, `artifact.json`, `assemble.py`), a `benchmarks/CHANGELOG.md` entry,
a `benchmarks/README.md` subsection, and a `benchmarks/HARNESSES.md` row.

Two corrections had to happen first, and both are the reason the harness is
worth trusting:

**Events were on the wrong stream.** The first shim recorded `hipEvent_t` on the
legacy default stream. ggml creates its streams with `cudaStreamNonBlocking`, so
those events did not order against its kernels at all and reported a 128.8 GFLOP
matmul at 0.002 ms — 64 PFLOP/s. The shim now includes the comparator's own
`common.cuh` and records on `bctx->stream()`. Event and host-wall times now agree
to 0.05% (17.3456 against 17.3547 ms), which is the check that would have caught
it.

**A claim that would have been wrong.** The first capture ran under the strict
execution profile and recorded `coltile8_rowbatch4_f32_f32_out`. Reporting
"hipEngine is 13.3x slower" from that would have been misleading, because the
production profile selects a different variant. Re-capturing under production
gives `coltile8_rowbatch4_wave_scale_f32_f32_out` at 17.361 ms. Both are
reported, and the production one is the headline.

## Validation

- **Replay identity.** hipEngine's replay reproduces the output captured during
  the model run bit-exactly: maximum absolute difference 0.0. The adapter is
  therefore running the same kernel on the same bytes, not a reconstruction.
- **Operand identity.** Three independent full-model prefills — strict,
  production, and production with `HIPENGINE_QWEN4_EXP_Q8_MMQ_PREFILL=1` —
  produced identical weight, activation and output sha256. A packet is
  reproducible, and the strict and production kernels are bit-identical on this
  operation.
- **Dispatch proof.** One `rocprofv3 --kernel-trace` capture of the replay shows
  both engines' kernels with launch geometry, LDS and register counts. Neither
  adapter can report a fallback: the hipEngine side requires `is_registered`
  (exact key, no fallback, unlike `resolve`) and the comparator side requires
  `ggml_cuda_mmb_supported_mm`.
- **Numerical attribution.** hipEngine tracks the exact float64 reference (mean
  absolute difference 4.33e-08, maximum 2.06e-06). The comparator tracks the
  both-bf16 reference (mean 2.17e-06, maximum 1.10e-04). Each engine matches the
  reference that describes its own arithmetic, which is what makes the remaining
  hipEngine-versus-comparator difference (maximum 1.47e-02, mean 7.87e-04 on RMS
  0.834) attributable to bf16 rounding rather than to a bug.
- **The strict path was not slow because of a bad launch.** Both hipEngine
  kernels report the same `gridDim` (1280, 256, 1), block 128, LDS 512 B and 72
  VGPRs; the wave-scale variant differs only by the `WAVE_SCALE` template
  argument.
- **Byte accounting.** The traffic figures are derived from the measured
  `gridDim`, block size and template arguments, not from hardware counters. The
  LDS allocation that causes the gap is measured, not derived: 512 bytes against
  55,296 bytes. The derived weight-read ratio, 64, is close to the measured
  11.70x time ratio, and the direction is the one the roofline predicts for a
  kernel that re-reads its weight 256 times. A memory-counter capture remains the
  confirming measurement.
- `python3 scripts/sync_benchmark_readme.py --check` passes; the worklog
  validator passes; no test, default, flag or registry entry changed, so no
  suite was run.

## Next

- The mechanism points at row reuse, and the harness can now measure a fix
  directly on the same packet instead of through a full-prefill A/B. A coltile
  variant with a larger row batch, or an LDS-staged weight tile reused across
  rows, is the obvious candidate. The derived traffic says the kernel is already
  L2-bandwidth bound at 1186 GB/s aggregate, so the fix is to read less rather
  than to schedule better.
- Extend the same packet and adapter pattern to the next families in the role
  map: the M = 12288 `attn_q`, where the disabled MMQ production route lives,
  then `expert_down` and `hyper_connection`, which carry the largest measured
  shares.
- The MMQ session needs a workspace, risk counter and risk-index queue before
  that route can be replayed. `q8_mmq_prefill_session` takes raw pointers, so the
  adapter can build one. Its ABI also takes the activation as bf16, which the
  variant name does not say, so the capture now records the launch ABI as well.

Limitations: one operation geometry, one layer, one chunk, one prompt, one host,
so the per-operation ratio is not a model-level rate. The comparator's 1.492 ms
is a cold-activation per-operation cost; in a full graph the converted activation
is shared by the projections reading the same tensor, so the amortized figure is
nearer 1.342 ms. The 11.2%-of-prefill share combines a same-capture per-call time
and call count (144 calls, observed in the capture and counted in the model file)
with a published prefill total from a different commit, so it bounds the share
rather than measuring an end-to-end delta. Per-round values spanned
17.355-17.390 ms for hipEngine and 1.488-1.496 ms for the comparator, so the
ratio is stable to about 0.2% within this session; no cross-session repeatability
claim is made.
