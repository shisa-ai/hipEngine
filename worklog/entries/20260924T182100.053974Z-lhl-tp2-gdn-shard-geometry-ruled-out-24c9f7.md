# Rule out the GDN weight sharding as the source of the head-shard divergence

## Summary

Follow-up to the failing head-sharded numerics
(`worklog/entries/20260924T145431.513808Z-lhl-tp2-attention-shard-numerics-fail-8e1277.md`).
That entry left "the GDN shard slice is taken against the wrong axis or an
interleaved value-head mapping" as the leading hypothesis. **This unit falsifies
it**, along with four neighbouring hypotheses, using host-side evidence only -
no GPU was needed for any of the checks below.

What survives: the GDN *weights* are partitioned correctly and consistently, so
the divergence has to come from how the rank's **state** or the **kernels**
interpret the sharded value axis, not from which weights the rank loaded.

## The empirical shape of the error, restated

Relative L2 of the post-attention-norm input against the unsharded route, per
layer, from the captured per-layer dumps:

| layer | type | \|\|x\|\| | \|\|d\|\| | \|\|d\|\|/\|\|x\|\| | growth |
| --- | --- | --- | --- | --- | --- |
| 0 | GDN | 106.4 | 6.51 | 0.061 | - |
| 1 | GDN | 29.2 | 14.23 | 0.487 | 2.19x |
| 2 | GDN | 23.6 | 23.65 | 1.000 | 1.66x |
| 3 | full | 83.9 | 26.90 | 0.321 | 1.14x |
| 4 | GDN | 21.1 | 17.23 | 0.817 | 0.64x |

The error norm grows ~2x per layer, which is systematic amplification, not
noise. Layer 0's 6.1% is ~30x what one extra bf16 rounding of a summed partial
would cost (~0.2% per element), so the route is wrong from the first layer.

## Falsified: the weights are sharded correctly

1. **Local shapes are exactly half the source.** Every GDN slot on both ranks:
   `attn_qkv` (10240, 5120) -> (5120, 5120); `attn_gate` (6144, 5120) ->
   (3072, 5120); `ssm_out` (5120, 6144) -> (5120, 3072); `ssm_alpha` /
   `ssm_beta` (48, 5120) -> (24, 5120); `ssm_a` / `ssm_dt_bias` (48,) -> (24,);
   `ssm_conv1d` (10240, 4) -> (5120, 4). Each is a clean half, and they agree
   with the halved derived widths (`linear_qkv_width` 10240 -> 5120).
2. **The partition is contiguous, not round-robin.** `partition_groups`
   (`hipengine/loading/qwen35_gguf_shards.py`) splits each axis segment into
   `world_size` contiguous runs of whole groups, and its docstring says
   explicitly that round-robin is rejected because it "would hand rank 1 KV head
   1 while its queries attend to KV head 0, which is silent wrong attention
   rather than a refusal". Rank 0 owns value heads `[0, 24)` and rank 1
   `[24, 48)`.
3. **`ssm_out`'s value axis uses the same partition as its siblings.**
   `ssm_out` (axis 1), `attn_gate`, `ssm_alpha`, `ssm_beta`, `ssm_a` and
   `ssm_dt_bias` (axis 0) all derive their segments from `_gdn_value_segments`,
   so a rank's `ssm_out` input columns are exactly the value heads its other GDN
   tensors cover. There is no axis or offset mismatch.
4. **The element order is blocked by value head, so halving does not reorder
   it.** The GGUF value block is tiled as `k_head = v_head % k_heads`, and within
   a tile of `k_heads` value heads that is just the block index - so the layout is
   v_head-ordered, and both the full and sharded configs give `tiles = 3`
   (48//16 and 24//8). The split boundaries land on tile edges either way.
5. **The GDN prefill variant is the same on both routes.** The resolver keys the
   variant on `(quant, ssm_group_count, ssm_time_step_rank, ssm_state_size,
   head_v_dim)` (`_gguf_gdn_prefill_session_mode`), which head sharding changes
   from `(q4_k, 16, 48, 128, 128)` to `(q4_k, 8, 24, 128, 128)`. That looked like
   a strong candidate, but the quant-shape table resolves to **zero entries** in
   this environment, so both keys miss and both fall back to the same backend
   default, `chain_compact_peer_wave32`. The fused kernel would have been handed
   `num_k_heads=8, num_v_heads=24` from the sharded config, but this route does
   not take it.

## Changes

- None in production code: this unit is diagnosis, and `attention_shard` stays
  default-off.
- Probe scripts live in `/tmp` (`tp2_layer0_probe.py` captures the
  post-attention-norm input per layer; `tp2_route_run.py` runs one route per
  process). Neither is in-tree yet; they should be before the next round, since
  they are what produced the layer-wise evidence.

## Validation

- Host-only geometry checks against the real GGUF
  (`materialize_attention_shards(..., world_size=2)`), no GPU involved.
- Per-layer captures from both routes at layers 0-4 on the 64-token prompt,
  `Qwen3.8-27B-Q4_K_M`, bulk prefill at `bulk_prefill_rows=64`.
- Cross-check: both routes' two ranks are **bit-identical** to each other at
  every captured layer, which is the control that says the captures are not
  racing the kernels. An earlier version of the probe did race (it memcpy'd on
  the default stream while the kernels ran on the rank's non-blocking stream) and
  produced NaNs and spurious rank mismatches; the fix was to synchronize the
  rank's stream first.

## Operational hazard found

The wedge on the target XTX followed this work's own end-to-end run. The TP2
device exchange uses a device-side spin (`tp2_dev_spin_add_bf16`,
`max_spins=2_000_000`), so a rank that enqueues its spin-add while the peer never
publishes leaves a kernel spinning on the device, and the harness killed the run
with `timeout` (SIGTERM) while it held ~15 GiB per rank. Avoid SIGTERM-killing a
TP2 run that may have a spin in flight; prefer runs that complete, and treat a
wedge as a possible consequence rather than a coincidence.

## Next

1. The divergence is not in the weights, so probe the rank's **state** and the
   GDN block's intermediates at layer 0: `conv_out` / `recurrent_bf16` before and
   after the recurrent step, compared against the unsharded route. A single-layer
   comparison localizes inside the GDN block without the 64-layer run.
2. Check the state sizing against the kernel's indexing: the recurrent and conv
   state are sized from the halved config, so if a kernel indexes them with the
   source `k_heads` the layout would be silently wrong in exactly this way.
3. Move the two probe scripts in-tree before the next round, so the evidence is
   reproducible from the repo rather than from `/tmp`.
