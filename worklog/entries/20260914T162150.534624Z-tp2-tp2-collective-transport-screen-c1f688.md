# Screen three dependency-bearing reduction structures and re-project TP2

## Summary

The previous decision rested on one number: 177.8 us per reduction for a
dependency-bearing all-reduce, which put TP2 at 0.62-0.68x against the faster
matched single-GPU arm and made the optimistic bound (1.24x with free rank-weight
reads) miss the plan's 1.3x target. That number was correct but unexplained, and
the structure it came from contained two costs that are not inherent to a
two-rank reduction: an intermediate device copy between reductions, and per-step
host submission. This unit separates them, screens a transport that avoids RCCL
altogether, and re-projects.

Three structures now carry the dependency, all verified by the same arithmetic
check - the chain must reproduce the closed form `seed * 2 ** depth`, which only
holds if every reduction consumed its predecessor:

| Structure | Per-reduction | 128 reductions | Speedup at 0% fixed share |
| --- | ---: | ---: | ---: |
| RCCL, one group per reduction, with the intermediate copy | 179.2 us | 22.94 ms | 0.680x |
| RCCL, one group per reduction, copy removed | 153.6 us | 19.66 ms | 0.738x |
| RCCL, copy removed, replayed from a captured graph | 146.0 us | 18.69 ms | 0.757x |
| Two-rank page-locked host exchange with a host-side sum | **71.1 us** | **9.11 ms** | **1.018x** |

The host exchange crosses the 9.61 ms break-even line at zero fixed-cost share
with 1.06x headroom, and still loses at the plan's assumed shares: 0.965x at 10%,
0.918x at 20%, 0.875x at 30%. Reaching 1.3x at zero fixed share needs ~24 us per
reduction, so the remaining gap is one more 3x on the exchange, and the
attribution says where it is.

Attribution per reduction: the intermediate device copy is **25.6 us**, host
submission is **7.6 us**, and collapsing N dependent reductions into a single
group saves **119.3 us**. The last figure is the one that matters for reading the
earlier evidence - the fast 34-38 us structures are fast because the reductions
collapse, not because they avoid host overhead - and the 7.6 us figure corrects a
first pass that attributed the whole 119 us to host submission.

The host exchange itself spends **27.7 us** on device-to-host copy plus host
wait, **28.5 us** on host-to-device copy plus host wait, and **6.4 us** on host
accumulation. The transfers are ~2 us each way for 20 KB, so the exposed host
wait dominates and a device-signalled completion is the next lever.

Capturing the dependency-bearing chain works: 128 reductions, one native group
each, captured into a HIP graph and replayed, with the closed form reproduced and
a `0xFF`-poisoned tail buffer proving the replay did the work. It buys 7.6 us per
reduction. An earlier attempt reported `HIP error 900: operation not permitted
when stream is capturing`, which turned out to be this harness calling
`transport.sync()` inside the capture rather than a transport limitation; the fix
was to enqueue without waiting. Capturing the whole chain as a *single* group is
both invalid (the reductions collapse) and unsafe on this host - it faults the
GPU at depth 32 - so it stays opt-in and out of a default run.

## Changes

- `scripts/tp_collective_bench.py` - added a mode selector for the dependent
  chain, a copy-free alternating structure, a per-depth captured-replay structure,
  and a two-rank page-locked host exchange; corrected the attribution so host
  submission is measured by replaying the same device structure instead of by
  comparing different device structures; added a per-depth
  `value_check_informative` flag so a saturated fp32 chain (depth 128, where
  `inf == inf` passes trivially) cannot supply the dependency verdict, and made
  the verdict come from the deepest depth whose closed form is finite; moved the
  single-group capture into `OPT_IN_CHAIN_MODES`; captured one graph per depth so
  a ladder point is a measured depth rather than the deepest chain divided by a
  depth it never ran.
- `scripts/tp_break_even.py` - `--dependent-chain-mode` accepts the structures
  whose dependency check passes, and the recorded `depends_on_every_step` flag is
  checked rather than the mode name.
- `scripts/tp_dep_chain_probe.py` - optional mode filter and a value-check print,
  so a stall or a failed check names the structure and depth that caused it.
- `tests/test_unit_scripts_tp_collective_bench.py` - the shadow transport now
  models a collective as one operation across ranks (applied once per batch of
  `world_size` calls, every rank's row receiving the same total) and moves real
  bytes through page-locked host staging; added tests for the saturated-depth
  verdict, the opt-in mode set, and the per-depth capture.
- `docs/QWEN38-27B-GFX1100-TP2.md` - the collective section, the "Runtime and
  communication" screen, and the Packet 0 punchlist carry the measured structures
  and the revised projection.
- `benchmarks/README.md`, `benchmarks/CHANGELOG.md` - retained rows and the dated
  one-liner.
- `docs/REFACTOR.md` - when the single-group capture mode should be deleted.

## Next

- Remove the exposed host wait from the exchange. The measured budget is 27.7 +
  28.5 us of copy plus host wait against ~2 us of transfer each way, and the
  target is ~24 us per reduction for 1.3x at zero fixed-cost share. This needs a
  bounded device-side completion signal with a declared timeout, not an unbounded
  spin, plus a stress test that a stalled peer trips the timeout instead of
  hanging.
- The projection still loses at the plan's assumed fixed-cost shares, so the
  fixed share itself (attention, GDN recurrence, launch overhead) and the exposed
  reduction count are now the two remaining levers that do not depend on the
  transport. Selective sharding is the untested one: MLP-only sharding would cut
  the count without changing the per-reduction cost.
- `docs/REFACTOR.md` carries the single-group capture mode as a deletion target.
