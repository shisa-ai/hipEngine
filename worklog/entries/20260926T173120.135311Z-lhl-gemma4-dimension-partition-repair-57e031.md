# Replace key-slice Gemma attention split with dimension partitioning

## Summary

The default two-pass Gemma decode attention accumulated each key slice
separately and summed the partials, which breached the binding production
`kl_max` bar. The value pass now partitions output dimensions instead, so every
output keeps the single-kernel path's full ascending-key accumulation chain.
The 1023-row teacher-forced comparison reports zero KL and 100% top-1 agreement;
strict and default logits are bit-identical on eight category prompts including
repeats, and greedy public token ids are unchanged.

This is a correctness repair, not a speed win. At 1024 prompt / 128 output the
repaired default measures 43.7400 decode tok/s against 45.7474 / 45.8617 /
45.7550 for the numerically failing implementation it replaces, a 4.4% cost on
the same host, workload and artifact, and +172% over the 16.0931 campaign
baseline. The cost is recorded rather than presented as an improvement.

## Changes

`hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention.hip`: the key-slice and
combine kernels are removed and `gemma4_attention_decode_dimension_kernel` runs
one block per 32 output dimensions per head, loading the exported f32 weights
into LDS and calling the single-kernel pass 3 with a whole-head stride. The
split workspace shrinks from `(weights + header + slices*head_dim)` to
`(weights + header)` floats per (token, head); `gemma4_decode_split_workspace_bytes`
keeps its `head_dim`/`slices` parameters because they remain in the launch ABI.

`hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention.py`:
`gemma4_attention_decode_variant` now maps selection 2 to `"split"` instead of
mislabelling it `"block"`, and `decode_slices` documents that its value above one
selects the dimension pass rather than a key-slice count.

`tests/test_gpu_gemma4_attention_decode_parity.py`: the split parity tests assert
bit-equality rather than `rtol=1e-2, atol=1e-3`, which is what "within one ULP"
claimed but did not enforce; new cases cover the workspace size, both head
widths, and key counts below, at and above the split threshold.

`docs/campaigns/GEMMA4-26B-A4B-OPTIMIZATION.md` records the invalidated
historical qualification claim and the current status. `docs/REFACTOR.md`
records the legacy slice-count ABI and its clearing condition.

## Next

The repair removes the correctness blocker that stopped the optimization loop,
but it does not recover the 4.4% the failing implementation was faster by, and
G4/G5 remain open. The next bounded optimization should start from this
corrected baseline: the dimension pass reads each head's full weight vector into
LDS and then walks every key, so the measured cost is in that pass rather than
in phase 1. Whether the fastest correct shape is dimension partitioning at a
different width, or a key-slice split with a compensated accumulation, is an
open question and needs its own hypothesis rather than another prefetch sweep.
