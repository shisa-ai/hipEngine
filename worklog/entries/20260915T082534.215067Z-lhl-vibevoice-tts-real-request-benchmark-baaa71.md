# VibeVoice-TTS benchmark measures the real request path

## Summary

The session benchmark no longer replays recorded model outputs, and the
torch-lane comparison basis is now in the repository instead of a commit
message. The correction is material: **pooled RTF is 2.53, not 2.323**, and the
same-host torch lane is **1.303**, so hipEngine is **1.94x slower** rather than
the 1.65x the previous basis implied. Time to first audible chunk is measured for
the first time: **2.825 s**.

## What was wrong

`scripts/vibevoice_tts_session_bench.py` injected `prefill_connected` (a model
output) and every recorded `callN_neg_condition`, which bypassed the negative-LM
branch entirely, omitted reference-audio preparation, enabled trace downloads
inside the timed region, hardcoded time-to-first-audio to `None`, and divided by
the oracle fixture's audio duration instead of the produced waveform's. The
injection hid real work: the negative branch is about 0.57 s of the warm total.

## Changes

- `scripts/vibevoice_tts_session_bench.py` (rewritten): builds the prompt from
  the frozen reference PCM through `voice_prompt_rows()`, runs the session's own
  negative LM (`neg_hook` is never passed), disables tracing for the timed runs,
  measures time to first audible chunk from request start to the first completed
  decode, and derives the output duration from the produced chunks. Correctness
  is gated by a separate traced, untimed run: the 27-token chain must be exact
  and the negative conditions must match the recorded ones. The artifact records
  the request identity (reference PCM SHA-256, manifest voice hashes verified),
  what is injected (recorded random operands only), and what is not.
- `scripts/vibevoice_tts_torch_bench.py` (new): the torch-lane harness, run in
  the pinned oracle venv. It reads the same manifest request, verifies the voice
  hashes, and reports the protocol numbers. Previously the 1.408 figure existed
  only in a commit message, with its harness uncommitted in `/tmp`.
- `benchmarks/results/2026-09-15-gfx1151-vibevoice-tts-session-real-request.json`
  and `benchmarks/results/2026-09-15-gfx1151-vibevoice-tts-torch-lane.json` (new
  artifacts); `benchmarks/CHANGELOG.md` entry and `benchmarks/README.md`
  `Last updated`.

## Measured

Same host (`zbook`, AMD RYZEN AI MAX+ PRO 395 w/ Radeon 8060S, gfx1151), same
frozen request (121 prompt tokens, 27 generated ids, 25 diffusion frames, 20 DDPM
steps, cfg 1.3, 3.333 s of output audio):

| Lane | Pooled RTF | Warm | Cold | Load |
| --- | ---: | ---: | ---: | ---: |
| hipEngine HIP bf16 | 2.530 | 8.433 s | 8.407 s | 3.279 s |
| torch bf16 sdpa (pinned venv) | 1.303 | 4.343 s | 6.293 s | 2.376 s |

hipEngine time to first audible chunk: 2.825 s. Warm stage split: LM 3.871 s,
diffusion 2.091 s, decode 1.278 s, semantic 1.015 s, prompt 0.178 s.

Correctness on the same run: `chain_exact` true and `negative_conditions_match`
true, so the real request path reproduces the oracle.

## Next

- The two RTF figures are not comparable: 2.323 came from the fixture-assisted
  basis. The metric series has a discontinuity here, and 2.53 is the honest
  real-request baseline.
- The torch lane draws its own random tensors, because a seed does not align
  torch and HIP random streams, so this is a duration comparison of the same
  request rather than the same random draw. The HIP lane's chain exactness is
  gated separately against the frozen fixtures.
- Reference-audio preprocessing (librosa resample from the 16 kHz voice WAV plus
  the fork's dB normalizer) is outside the timed path. The request is defined at
  the PCM boundary the model consumes, which the manifest's reference-PCM hash
  pins. The doc's protocol asks the manifest to hold speaker-reference *PCM*
  hashes; it currently holds WAV hashes, and the PCM hash lives in the artifact.
  That gap is recorded rather than fixed, because the fixture set is frozen and
  byte-reproducible.
- The goal's headline target is RTF below the torch lane's 1.303 on this host.
  At 2.53 hipEngine is 1.94x slower, so the remaining work is the LM stage
  (3.871 s of 8.433 s) and diffusion (2.091 s). No performance claim is made by
  this unit.
- The `two`-speaker diffusion parity failure is unrelated and pre-existing; see
  the previous entry and task #7.
