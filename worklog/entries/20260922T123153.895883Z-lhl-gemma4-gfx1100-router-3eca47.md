# Gemma 4 router assembled; prescale output is bf16, not f32

## Summary

`hipengine/kernels/hip_gfx1100/gemma4/gemma4_router.py` assembles the Gemma 4
router from four kernels that are each tested on their own, and matches the
reference `gemma4_router_topk`:

| Stage | Kernel |
| --- | --- |
| weightless RMSNorm × `scale` × `hidden_size**-0.5` | `gemma4_router_prescale_bf16` |
| logits (BF16 activation, F32 weights) | `qwen35_router_logits_bf16_f32w` |
| top-k + softmax + renormalise | `qwen35_router_select` |
| per-expert scale | `gemma4_expert_weight_scale_f32` |

`Gemma4RouterScratch` holds the two intermediates (`prescaled`, `logits`) and is
reused across layers and decode steps. `selected` (int64) and `weights` (F32) are
written directly into caller buffers, so the router output feeds the expert
forward's group-scatter chain without a copy.

## The contract, pinned from the reference

`gemma4_router_topk` normalises **without a weight**, applies the learned
`router.scale` and `hidden_size**-0.5`, projects to expert logits, softmaxes over
**all** experts, keeps the top `k`, renormalises those to sum to one, then
multiplies by `per_expert_scale` of the selected experts.

Two details of that are easy to get wrong:

- **The router norm is weightless.** Gemma 4 has no router-norm weight tensor.
  The GGUF carries only `ffn_gate_inp` and `ffn_gate_inp_scale`, and
  `_gemma4_gguf_names` maps no norm weight for the router, so
  `gemma4_router_prescale_bf16` — which folds the norm, the learned scale, and
  `root_size` into one launch — is the whole pre-projection step.

- **`qwen35_router_select` softmaxes over the selected set, not all experts.**
  That is equivalent, not a shortcut: the reference computes `p_i = exp(l_i)/Z`
  over every expert and then divides by the sum of the selected `p`, so `Z`
  cancels and both reduce to `exp(l_i) / sum_selected exp(l_j)`. They differ only
  in rounding.

## The composition bug this unit found

**The prescale output is BF16, not F32.** `gemma4_router_prescale_kernel` is
templated on `scalar_t` for *both* its input and its output, so the `_bf16`
symbol writes BF16. I allocated the `prescaled` buffer as F32 and paired it with
`qwen35_router_logits_f32_f32w`; the logits kernel then read the bf16 row as f32
pairs and produced logits that were **uncorrelated** with the reference (max abs
diff 0.063 against a reference magnitude of 0.054). Expert selection differed on
18 of 20 slots.

The matching variant is `qwen35_router_logits_bf16_f32w`. Worth recording
because the prescale kernel's own test
(`test_router_prescale_matches_the_reference_router_input`) passed the whole
time — the kernel was correct and only the composition was wrong. That is
precisely the failure mode a composition test exists to catch, and it would not
have been caught by any amount of kernel-level testing.

The second ABI question resolved without a code change: the sibling
`qwen35_router_select_sigmoid_shared_kernel` reads a shared-expert gate column at
`logits[token * logits_stride + num_experts]`, but it only sigmoids that column
*after* selection — the selection itself reads `[0, num_experts)`. Gemma 4 has no
shared expert gate, so `logits_stride = num_experts` with the plain kernel is
correct and no dummy column is needed.

## The selection contract is not "exact match against f32"

The prescale rounds the activation to BF16, so the kernel does not compute the
f32 reference exactly. My first attempt asserted exact selection agreement and
passed — then a margin guard showed the fixture's smallest k-th/(k+1)-th
probability margin was 0.11% against a 0.29% activation-relative prescale cost.
The pass was luck, and the test would have been flaky on another seed.

The right contract, now encoded: measure the perturbation **in logit space**,
which is where the decision lives, and require agreement wherever the
k-th/(k+1)-th logit gap exceeds it, asserting separately that every disagreement
is inside it. The logit-space perturbation is **8e-5** — about 70× smaller than
the activation-relative cost, because the projection averages the rounding out,
so comparing a probability margin against an activation cost was comparing the
wrong quantities.

Measured on the fixture: perturbation 8e-5, **all 5 tokens decisive, all 5
agree**, weights within **9e-6** of the f32 reference. The weight tolerance is
now derived from the measured perturbation (`4 * perturbation`) rather than a
hand-picked constant.
