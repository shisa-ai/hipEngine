# the decode expert route prefers the bit-exact pack8 selected GEMV

## Summary

The gemma4 decode expert route resolved `linear/<quant>/selected_gemv_bf16_bf16_out`,
one output column per block, and it now prefers
`selected_pack8_gemv_bf16_bf16_out` where the quant registers it and
`out_features` is a multiple of 8. Measured on the campaign bench, decode goes
from **22.32 to 22.80 tok/s (+2.2%)** and the two arms emit the same 64 token
ids, so the change is bit-exact end to end. Fixing the preference also required
fixing how the route tests whether a variant exists, which was silently
resolving a NumPy kernel.

## Changes

- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_experts.py`:
  `gemma4_project_experts_selected` now tries `_SELECTED_PACK8_VARIANT` before
  `_SELECTED_VARIANT`, and both lookups go through a local `resolve_variant`
  helper.
- The same helper requires `is_registered(key)` before calling `resolve`.
  `resolve` broadens a miss to the variant-less key and then to the
  `cpu_reference` backend (`_candidate_keys`), which is right for dense dispatch
  and wrong here: `("cpu_reference", "linear", "gguf_q5_1", "")` is the NumPy
  `linear(x, weight, bias)`, so a broadened hit handed device pointers to a
  NumPy kernel. That was already reachable before this change for any quant with
  no exact selected variant; it now returns `False` and the caller uses the
  per-expert offset path, which is what the boolean was always documented to
  mean.
- `tests/test_unit_gemma4_expert_route.py`: four route tests (prefers pack8,
  declines a width that is not eight wide, falls back when the quant declares no
  sibling, still returns `False` when neither variant is registered) and a GPU
  test that launches both variants on the same weights and rows and compares
  bf16 output bit patterns for Q4_K, Q5_K and Q8_0 at the artifact's own expert
  geometries. `_grouped_backend` gained a branch so Q5_K and Q8_0 can register
  their linear families, and `_WEIGHT_MAKERS`/`_GGML_TYPES` gained `gguf_q5_k`.
- `benchmarks/results/2026-09-28-gemma4-selected-pack8-route-ab.json`: the A/B
  artifact.

## Validation

Bit-exactness, kernel level:

```
python3 -m pytest tests/test_unit_gemma4_expert_route.py \
  -k pack8_selected_is_bit_exact -q
# 4 passed -- gguf_q4_k 1408x2816, gguf_q4_k 2816x2816,
#             gguf_q5_k 1408x2816, gguf_q8_0 2816x704
# 0 differing bf16 outputs in every case
```

Bit-exactness, model level, and the timing, from one A/B run:

```
python scripts/gemma4_campaign_bench.py --prompt 8 --output 64 --samples 2 \
  --warmup 1 --expect-gpu 8060S
# pack8 arm:  decode_s 2.7630, 2.7635  -> 22.80 tok/s
# single arm: decode_s 2.8344, 2.8119  -> 22.32 tok/s
# identical generated_token_ids in both arms
```

The `single` arm is the pre-change route reproduced in-process by pointing the
route's pack8 slot at the single-output variant name, so both rows share a
process image, a load, a warmup and a token stream.

Narrow suites: `tests/test_unit_gemma4_expert_route.py`,
`tests/test_unit_gemma4_gpu_kernels.py`, `tests/test_unit_gemma4_contracts.py`,
`tests/test_gpu_gemma4_expert_route_true_geometry.py` -- 137 passed.

Why no numerical gate applies: this is the same arithmetic in a different block
shape. The k walk, the per-element dequant and the reduction tree are per
output, and the pack8 kernel reproduces all three per output, which the GPU test
checks bit for bit and the identical token stream confirms end to end.

## Next

The gain is +2.2%, not the 1.41x the isolated Q4_K gate/up benchmark suggested.
At rows=8 the x row is 5.6 KB and 1408 output blocks read it, so it is
L2-resident; the pack8 saving is the amortized block reduction, not x traffic.

The overhead-free decode ablation puts this route's family at 31.5% of a
44.73 ms token. Dense Q8_0 GEMV is 30.2% and **34% of the step is not accounted
for by any GEMV arm at all** -- that unattributed share is larger than either
weight path and is where the next measurement goes. The ablation gained a
`no_all_gemv` wildcard arm and a `no_norm_rope` arm for exactly that.

Q5_1, which carries this artifact's expert down projection, does not register
this sibling: `selected_pack8_gemv_decode_compact_bf16_bf16_out` is on
`moe_linear` and takes a compact expert-start array instead of a per-row
selected index, so reaching it needs the compact MoE scheduler chain
(`moe_group_count` / `moe_group_prefix` / `moe_group_scatter_gather`) that the
qwen35 runner builds and gemma4 does not.
