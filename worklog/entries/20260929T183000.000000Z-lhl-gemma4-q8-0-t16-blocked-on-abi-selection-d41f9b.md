# the Q8_0 T16 loader change is blocked on route selection, and the loader tests were already RED

## Summary

Attempted the loader change planned in `20260929T173000`. It does not work, and **the reason is
one layer below where the plan looked.** The change was reverted; the tree carries only the test
fix described in the second half.

Two findings, both worth more than the reverted patch:

1. **The dispatch picks a raw ABI for a T16 weight**, so a tiles-only spec crashes at decode.
2. **`tests/test_unit_gemma4_gguf_device.py` was already failing three tests on unmodified
   `HEAD`** — the Q4_K `t16_gate` branch landed without updating them.

## Finding 1: the ABI is chosen above the quant key

The plan's central claim was: *"declare a `tiles` allocation, set `quant_key="gguf_q8_0_t16_v1"`,
and the dispatch reads `weight.allocation("tiles")` on its own -- no dispatch change is needed."*

**The first half is right and the second half is wrong.** With the change applied, decode fails:

```
File ".../hipengine/runtime/gguf_linear.py", line 9106, in _launch_wmma_raw
    weight.allocation("raw").tensor.ptr,
KeyError: 'raw'
```

raised through `launch_gguf_linear` line 3658, from `gemma4_project` on `layer.q_proj` during
decode.

The `{"t16": "tiles"}.get(dispatch.abi)` mapping is real, but it only fires **once the ABI is
already `t16`**. The ABI is chosen earlier -- `gguf_linear.py:8995` sets `abi = "wmma_raw"` from a
route table at 8830 -- and that selection does not follow the quant key to the T16 family. So the
weight advertises `gguf_q8_0_t16_v1`, gets routed to a raw launch, and the raw launch asks for an
allocation that a tiles-only spec correctly does not have.

**One further fix was needed and applied before reverting:** `raw_weight_ptr` was guarded by
`weight.spec.layout == LAYOUT_RAW_GGUF`, which is true for a tiles-only spec because the storage
really is uint8 blocks. It now asks `"raw" in weight.spec.allocation_names`, which is the precise
question. That fix is correct and independent of this feature, but it is not enough alone.

**What the next attempt needs:** find where the route table at 8830 chooses between
`wmma_raw` and the T16 family, and make it consult the quant key the way the allocation mapping
already does. That is a dispatch change, contrary to the plan's claim that none was needed.

## Finding 2: the loader tests were already RED on HEAD

Before touching anything I checked whether my change caused the failures:

```
git checkout -- hipengine/loading/gemma4_gguf_device.py
uv run pytest tests/test_unit_gemma4_gguf_device.py    # 3 FAILED, unmodified tree
```

The three failures were `test_quant_keys_follow_the_artifact`,
`test_a_stacked_expert_tensor_stays_one_allocation`, and
`test_resident_bytes_is_the_artifact_bytes` -- all asserting `allocation_names == ("raw",)` or
artifact-equal residency, which the Q4_K `t16_gate` branch had already made false. **The tests
encode a contract the loader stopped honouring, and nothing caught it.**

They are now GREEN, fixed against the **current** behaviour rather than a hoped-for one:

- The expert test asserts per tensor: the Q4_K gate/up stack carries `("raw", "t16_gate",
  "t16_up")` and the Q8_0 down stack stays `("raw",)`. A uniform expectation was the original bug
  -- the two expert tensors genuinely differ, because the Q4_K branch requires
  `shape[1] % 32 == 0`.
- The quant-key test uses `spec.slot_path` to decide the dense-leaf case, not `spec.source.name`.
  The tensor name is `blk.0.attn_q.weight` and never starts with `layers.`, so the name is the
  wrong string for this question.
- The residency test asserts the raw-only specs sum to their artifact bytes, and records why the
  aggregate cannot be checked on this fixture: its rank-3 Q4_K expert is smaller than one Q4T16
  tile row, so `derived_allocation_bytes` raises. **That is a fixture/planner mismatch, left
  unfixed and named.**
