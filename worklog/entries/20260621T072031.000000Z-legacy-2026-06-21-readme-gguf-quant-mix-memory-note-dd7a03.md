## Changes


- User asked to make the GGUF support README explicit that the PARO-vs-GGUF long-context gap is mostly base/weight residency, not a different KV slope. Audited local GGUF tensor payloads directly from `/models/gguf/Qwen3.6-35B-A3B-UD-Q4_K_M.gguf` and `/models/gguf/Qwen3.6-35B-A3B-UD-Q4_K_S.gguf` using `GGUFReader` + `qwen35_gguf_config_from_metadata`.
- Resulting raw tensor payload mix: Q4_K_M total `21.097 GiB` = Q4_K `11.531 GiB` (`54.7%`), Q5_K `6.531 GiB` (`31.0%`), Q8_0 `1.932 GiB` (`9.2%`), Q6_K `1.004 GiB` (`4.8%`), F32/BF16 metadata `0.098 GiB`; Q4_K_S total `19.909 GiB` = Q4_K `16.875 GiB` (`84.8%`), Q8_0 `1.932 GiB` (`9.7%`), Q6_K `1.004 GiB` (`5.0%`), F32/BF16 `0.098 GiB`, no Q5_K. Delta is `-1.188 GiB` for Q4_K_S vs Q4_K_M, almost entirely MoE/router/shared (`18.428 -> 17.271 GiB`) because selected-MoE Q5_K expert-down payload is replaced by Q4_K.
- Updated README GGUF Support caveats with this quant-family table and the interpretation: Qwen3.6 full-attention KV slope is the same 10-layer shape as PARO; GGUF starts from a larger loaded-weight baseline (`~21.10 GiB` Q4_K_M, `~19.91 GiB` Q4_K_S, vs packed PARO `~19.07 GiB`) and hipEngine's resident T16/pack8 decode layouts add allocator shape. Current Q4_K_M BF16-KV support on 24 GiB remains mid-context unless a lower-memory KV/weight policy is explicitly enabled. Also refreshed the top status bullet so it no longer says 24 GiB cards should expect only ~64K with Q4_K_S; Q4_K_M is now labeled the active 1:1 comparison target, with Q4_K_S as lower-memory secondary.
