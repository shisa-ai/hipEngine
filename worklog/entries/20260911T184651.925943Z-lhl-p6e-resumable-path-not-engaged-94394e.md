# The P6e service proof does not exercise P6's resumable yield: it passes on the default route

## Summary

A completion audit of task #14 asked whether the P6e service proof's green status
actually covered the deliverable. It did not.

Two independent problems, both now measured:

1. **No harness sets `HIPENGINE_GGUF_PACKED_LAYER_OUTER`.** `_EXACT_ENV` does not
   either, and a repo-wide search finds the variable only in the runner, the docs,
   and the unit tests. The layer-outer route is **default OFF**, and the resumable
   prefill lives on it. So every P6e service run so far took the route at its
   default OFF.
2. **Turning the flag on is not sufficient.** Re-running with
   `--packed-layer-outer` gives `packed_layer_outer_enabled: true` and still
   **oracle owner peak 0.0**, while the other seven gates pass. The resumable path
   additionally requires `kv_attention_source == "int8_direct"`
   (`hipengine/generation/qwen35_gguf.py:8084`); when that does not hold it
   increments `_fallback_reasons["int8_direct_full_prompt_prefill"]` and falls back
   to the fail-closed full-prompt route.

So the cancel, refill, blocking, and slow-consumer gates are real measurements, but
they describe the **default chunk-outer route**, not the deliverable. P6's
resumable mechanism is demonstrated only by the direct-call GPU proof, which
invokes `prefill_batch_native_layer_outer_resumable` directly and therefore
bypasses the scheduler wiring this service proof was supposed to test.

## The gate that makes this visible

`resumable_path_engaged` was added to `evaluate_gates`. It requires the layer-outer
route's shared per-layer oracle owner (`hipengine_resident_prefill_oracle_owners`,
`hipengine_resident_prefill_oracle_owner_bytes`) to be observed **non-zero while a
long prefill is in flight**. A single scrape cannot do this — the owner is allocated
during prefill and released before the request returns — so a poller samples the
peak across the long blocking arm's window.

It **fails**, which is the correct and useful outcome. Before it existed, this proof
would have certified P6 with gates that had nothing to do with P6.

This is the same failure class as the no-op cache-only env guard fixed earlier
(`7ec8020f3`): a harness that asserts a condition it never actually establishes.
The remedy is the same — assert the condition positively and let it fail.

## Next

Determine whether the service can engage the resumable path at all:

- Check the service's KV layout: `_gguf_kv_attention_source` returns `int8_direct`
  only when some INT8 layer has **no** BF16 mirror. If the service config mirrors
  every INT8 layer, the route is unreachable from the service by construction, and
  that is the concrete blocker to record.
- If it is reachable, find why it declined and re-run the harness with the
  engagement gate passing, which would make the service-level proof real.

Until then, #14's service-level half is **unproven**, and the direct-call GPU proof
is the only evidence for the mechanism.

## Honest limits

- The engagement indicator is the oracle owner gauge. If the resumable path could
  run without allocating that owner, the gate would be a false negative. The P6a
  entry describes the layer-outer executor as owning one shared oracle pair, so the
  indicator matches the documented design, but it is a proxy rather than a direct
  route counter.
- `_fallback_reasons` is not exposed as a metric, so the decline could not be read
  directly; the requirement at `qwen35_gguf.py:8084` was read from the source
  instead. Exposing that counter would make this diagnosable from the artifact.
- `performance_claim` is false and no scoreboard row changed.
