# the capacity question belongs to the paths a run selects, and the tiled decode is bit-exact with the strict one

## Summary

The previous unit established that the context ceiling belongs to the 5
windowless layers. This one makes those layers servable, and it turns out that
needed no new kernel.

**The guard was asking the strict kernel's question and reporting it as the
model's answer.** `gemma4_require_context_capacity` called
`gemma4_attention_shared_bytes` per layer, which describes the strict family's
LDS layout. Above 15,616 positions that refuses — for every profile, including
one that had already selected a tiled path for exactly those layers. The
question is now asked of the whole family through `gemma4_attention_serves_keys`,
with the run's selected variants as an input. Measured by bisection on the real
artifact's config: **strict 15616, production unbounded.**

**The decode route had the same shape of error.** `_select_prefill_attention`
sent every one-token block to the strict decode kernel, because the candidates
tile 16 query rows wide and a decode step uses one. That is a *performance*
argument and it is correct wherever it applies — but the strict decode kernel
holds one logit per live key in LDS and stops at **15,856** keys, and above that
the candidate is not the wasteful choice, it is the only one. The rule is now
bounded by capability: the strict kernel keeps the routing while
`keys <= gemma4_decode_max_keys()`, and a selected candidate takes over past it.

**The tiled decode is byte-identical to the strict decode on the same input.**
This is the result that matters, and it was measured as an A/B on one prompt at
one key count rather than inferred. At 8,193 keys both paths can run, so
patching `gemma4_decode_max_keys` to 2048 moves the full layers (8,193 keys) onto
the candidate while leaving the sliding layers (1,024 keys) on the strict kernel
— a switch of exactly the routing decision under test and nothing else:

| arm | full-layer decode variant | generated ids |
| --- | --- | --- |
| A | `gemma4_plain` (`decode:` reason) | `[236769, 7633, 236768, 973, 236743, 236778, 236842, 107]` |
| B | `gemma4_wmma_flash_full` (capability match) | `[236769, 7633, 236768, 973, 236743, 236778, 236842, 107]` |

Identical, and the routing is confirmed different between the arms rather than
assumed. The continuation decodes to `'(items) // 2]\n'`, which is coherent for
a corpus carrying code-like fragments. So the candidate's changed arithmetic did
not move a single greedy token across eight steps of a real 8,193-token context.

## Changes

- `gemma4_attention.py`: add `gemma4_attention_serves_keys`, which returns `None`
  when some path serves a layer at a key count and the reason when none does —
  the strict kernel first, then each selected variant that declares the geometry.
  Add `gemma4_decode_max_keys()`, the strict decode kernel's own key bound, so the
  number is derived from the LDS budget rather than written down a second time.
  Name the budget and the decode layout as `_LDS_BUDGET_BYTES` and
  `_DECODE_LDS_FLOATS`, because three places now ask the same question of them.
- `_select_prefill_attention` / `select_prefill_attention` take `keys`, and the
  one-token rule is conditional on `_strict_decode_serves(keys)`. An unknown key
  count keeps the incumbent routing: a caller that did not say how many keys it
  has is not evidence that it has too many.
- `gemma4_layer.py` computes the key count once and passes it to both the
  selection and the launcher, so the two cannot disagree.
- `gemma4_require_context_capacity` takes `variants` and asks
  `gemma4_attention_serves_keys` per layer; `Gemma4Runner` passes its own
  `prefill_attention_variants`, and the generator's pre-load check passes the
  variants it resolved, so the early check and the construction-time check agree.

## Measured, and it is the next unit

**A one-token decode launches 2 blocks, and that is now the binding limit.** The
candidate's grid is `(query_tiles, num_kv_heads, gqa_tiles)`, which for a decode
step is `(1, 2, 1)`. Measured at `tokens=1`:

| keys | ms/call | K+V read | effective GB/s |
| ---: | ---: | ---: | ---: |
| 8,192 | 1.71 | 0.034 GB | 19.7 |
| 32,768 | 7.14 | 0.134 GB | 18.8 |
| 131,072 | 28.52 | 0.537 GB | 18.8 |
| 262,144 | 57.02 | 1.074 GB | 18.8 |

Bandwidth is flat at **18.8 GB/s** across a 32x range, which is one block's worth
of streaming on this part and not a scaling curve. At 262,144 keys that is
57 ms per windowless layer, so **285 ms per token across the five of them** —
before the MoE. Splitting the key range across blocks and combining partial
online-softmax states is what turns that into a scaling curve, and it is the
next unit rather than part of this one. The 16-row tiling wasting fifteen
sixteenths of every WMMA op costs nothing here, which the flat GB/s is the
evidence for: at 2 blocks the kernel is memory-limited per block, not
compute-limited.

The strict decode kernel is not a faster baseline to fall back on at these
lengths — it measures 3.01 ms at 8,192 keys and 10.17 ms at 15,616, i.e. 6.3 GB/s
at the top of its range.

## Next

  above.
- The KV cache is still capacity-sized for every layer, so a 256K runner
  allocates **59.06 GB** of which the 25 sliding layers hold 53.48 GB they can
  never read. Construction at 256K fits (59.06 GB of KV plus a 17 GB model
  against 109 GB available), so this remains an optimization rather than a
  precondition, and it needs a ring buffer because a window-sized cache wraps.
- Prefill at long context still materialises a dense `(rows, keys)` mask: 133 MB
  per block for the windowless layers at 256K. Decode does not, because a
  one-row mask is `keys` bytes.
