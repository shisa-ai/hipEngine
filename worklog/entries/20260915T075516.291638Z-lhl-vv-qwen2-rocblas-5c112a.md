# Route the VibeVoice Qwen2 GEMMs through rocBLAS

## Summary

M3c: the hand-tiled f16 GEMM from M3b was the decode-step bottleneck, so all
QKV / O / MLP GEMMs now run through `hipengine.core.rocblas` (f16 storage,
f32 accumulate) and the non-GEMM chain is covered by three new elementwise
HIP kernels in `qwen2_ops.hip` (`bias_add`, `add`, `silu_mul`). The model
loop allocates one bump arena per forward call, replacing ~280 per-layer
hipMalloc/free pairs per decode step.

## Correctness

14 tests green (`tests/test_gpu_vibevoice_qwen2_lm.py` +
`tests/test_unit_cpu_reference_vibevoice_qwen2.py`): device LM vs CPU
reference, CPU reference vs pinned HF oracle, codec streaming paths.

## Walls (W7900, 64-token prefill / 32 decode steps, 7-8 repeats)

- Device (`scripts/vibevoice_qwen2_device_walls.py`):
  prefill 42.3 ms (660.8 us/token), decode 31.9 ms/step (p95 35.2).
- Torch fp16 reference (`scripts/vibevoice_qwen2_torch_walls.py`):
  prefill 18.1 ms (283.5 us/token), decode 18.8 ms/step (p95 19.9).

Device is still ~1.7-2.3x slower than torch. Per-layer kernels sum to
~0.15 ms x 28 = 4.2 ms, so ~26 ms/step is outside the layer loop —
launch overhead / attention / elementwise dispatch is the next target,
not the GEMMs. Artifacts:
`benchmarks/results/2026-09-15-vibevoice-qwen2-{device,torch}-walls.json`.
Diagnostic comparison, not a retained benchmark row.
