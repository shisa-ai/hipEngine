# Give the real-workload harness its true-AR, boundary, prefix, occupancy, and cancel arms

## Summary

`scripts/sharegpt_mtp_routing_pass.py` could measure one shape of one arm: a
24-prompt greedy singleton load with a fixed 128-token output override, filtered
to 4..1024 prompt tokens, always taking whatever route the server policy chose.
The reviewer's validation matrix needs the opposite: a true-AR control, natural
output lengths, a boundary-crossing row beside a healthy one, prefix-hit beside
prefix-miss, changing occupancy, and a cancellation. Those are now command-line
switches on the same harness rather than five scripts, and the summary reports
the quantities that decide a routing change (realized group composition and a
per-request decode rate that excludes prefill), not only MTP usage.

This is the measurement foundation for the concurrent-coverage work
(`#24`/`#31`): a route that is reported as speculative while its rows run at
width 1 is visible in `groups_by_realized_rows`, and a coverage improvement is
only retained if the per-request decode rate improves against the `off` arm from
the same server process.

## Changes

- `scripts/sharegpt_mtp_routing_pass.py`
  - `--speculative-mtp {auto,on,off}`: sends the per-request
    `speculative_mtp` field. `off` is the true autoregressive control - the same
    load, same server process, provider explicitly disabled - instead of
    inferring an AR baseline from a verifier-derived row. `auto` omits the field
    and keeps the server policy.
  - `--min-prompt-len` (default 4): selects the boundary-crossing prompt the
    vLLM-compatible filter excludes, so a healthy short request and a row that
    crosses the provider's context window can run in one load.
  - `--stagger-ms`: spaces submissions so requests arrive while others decode
    (changing occupancy); 0 keeps the previous burst.
  - `--prompt-repeats`: sends every prompt N times; repeats after the first
    reuse the prefix and exercise the prefix-cache hit path beside the miss.
  - `--cancel-count` / `--cancel-after-tokens`: aborts the last N requests after
    their first generated token, so the server's cancel/refill path runs beside
    completed requests. Cancelled rows are recorded as `cancelled`, excluded
    from `failed_requests`, and counted separately.
  - `summarize()` adds `groups_by_realized_rows` (requests, MTP requests, MTP
    output tokens and completion tokens per realized physical group width),
    `median_decode_tokens_per_second_per_request` (completion tokens over
    post-first-token time, per request, because concurrent requests overlap and
    an aggregate wall rate also carries prefill and queueing), and
    `cancelled_requests`. Rows carry `repeat_index` and the
    `speculative_mtp_request` override that produced them.
  - The module docstring documents the arm switches and the two new summary
    quantities.

## Validation

- `uv run pytest tests/test_unit_sharegpt_mtp_routing_recorder.py`: 13 passed
  (9 retained + 4 new). The new cases pin: the `off`/`on`/`auto` request
  payload (including that `auto` omits the field), deliberate cancellation
  closing the stream and marking the row instead of failing it, group
  composition plus the per-request decode rate, and `--min-prompt-len`
  selecting the long row.
- `uv run python scripts/sharegpt_mtp_routing_pass.py --help` parses, and
  `compileall` succeeds.
- No server run and no performance claim in this unit; the arms are exercised
  against the live server by the concurrent-coverage measurement that follows.
