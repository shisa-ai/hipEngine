# the assistant head forward runs end to end but does not yet track its target

## Summary
**Checkpoint, not a completed unit.** `Gemma4AssistantHead.forward` now runs the
whole MTP forward against a real backbone without crashing: the embedding gather
from the backbone's table, the concat, the pre-projection, four blocks each doing
per-head Q norm, Q-only rope, shared-KV attention with scale 1.0, `wo`,
post-attention norm, FFN with both norms, and the layer output scale, then the
output norm, logits and `h_next`.

**It is not yet correct.** The oracle is the head's own training objective: an MTP
head is trained so `nextn_proj_post @ cur` predicts the target model's hidden
state one position ahead, so `h_next` should track the backbone's own hidden
state at the next position. Measured cosine is **-0.058**, where a correct forward
should be well above 0.5. A wrong forward scores near zero or negative, which is
what it does.

This is recorded as a checkpoint rather than a feature because the forward has
not met its gate. The test that measures it is committed alongside, so the next
unit has a pass/fail signal rather than a description.

## Changes
- **`hipengine/runtime/gemma4_assistant.py`**: `Gemma4AssistantScratch`,
  `Gemma4AssistantHead` with the full `forward`, `_stage`, `_linear`,
  `_layer_scale`, `close`, and `_bf16_to_float32` / `_float32_to_bf16` helpers.
- **`tests/test_gpu_gemma4_assistant_forward.py`**: the cosine oracle, guarded on
  HIP and on both artifacts. Not in the default unit tier (it is a `test_gpu_`
  module), so it does not break the reviewed suite while it is red.

## Validation
- The forward executes: all four blocks, both attention kinds, both post-norms.
  It returns finite logits of the right shape (262144) and a finite `h_next` of
  the right width (2816) that is not all zeros.
- The test's two guards fire as intended: it asserts the source and target hidden
  states differ, so a forward that returned its input could not pass, and it
  stages the input hidden state into its own buffer because `Gemma4Runner` reuses
  one hidden buffer across forwards -- passing `runner.hidden_state()` after the
  second forward would have handed the head the *target* as its input and made
  the comparison meaningless.
- **Four bugs found and fixed while writing this, three of them real:**
  1. `launch_gguf_embedding`'s last argument is the vocabulary size, not the
     embedding width. I passed 2816 instead of 262144. Fixed; it turned out to be
     a bounds check only, since the output was bit-identical afterwards.
  2. `gemma4_rope_cos_sin_tables` takes the CPU-reference `Gemma4RopeConfig`, not
     the loader's `Gemma4GGUFRoPEConfig`. The geometry now converts
     (`freq_base` -> `rope_theta`, `rotated_pairs` -> `rope_angles`), which is a
     field rename rather than a second derivation.
  3. `gemma4_attention_prefill_bf16` needs `row_offset` set to the query's
     absolute position; the default 0 makes the kernel treat the single query as
     position 0. The backbone passes `write_offset - key_begin`, and the head
     passes `key_begin = 0`, so it is the position itself. `window` is passed too,
     matching the backbone.
  4. **BF16 was being decoded as float16.** `bits.view(np.float16)` reinterprets
     rather than converts: BF16 is the top 16 bits of a float32 with 8 exponent
     bits and 7 mantissa bits, while float16 has 5 exponent bits and 10 mantissa
     bits. Both the forward's return and the test's helper did this. It was caught
     because two substantive changes (`vocab_size` and `row_offset`) produced
     *bit-identical* output, which is impossible unless the result is garbage
     regardless of the fix. Both sides now widen to uint32 and shift left.
- **The first two fixes changed nothing at all**, which is what exposed bug 4.
  Bug 3 and bug 4 together moved the cosine from -0.0437 to -0.0584, so the
  forward is now doing something different and still wrong.
- No correctness gate applies to the forward yet: it has not met one.

## Next

   strongly negative, so this looks like a stage that contributes noise rather

   head's *logits* argmax is a plausible next token at all, and whether
   `nextn_pre_projection` alone tracks anything. A CPU reference for the head

   investment before more GPU round-trips.
