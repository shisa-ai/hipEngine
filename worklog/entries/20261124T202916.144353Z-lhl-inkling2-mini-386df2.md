# Add a bit-exact one-row decode attention kernel for the Inkling GGUF resident path

## Summary

Campaign task 19 for the resident path. The opt-in decode step ran attention through the block
kernel at one row, which walks the live keys serially and took 919 µs per visit at 1,717 keys: 45 ms
of a 70 ms step. The new `decode_table_sigmoid` variant takes 160 µs per visit there and is bit-exact
with the block kernel, so the resident path's output did not change.

Measured on `epyc` (Radeon Pro W7900, gfx1100, HIP 7.2.53211), mainline `UD-Q4_K_M`, FP32 KV,
one greedy stream, prefix cache off, drafting off, `fast` profile, 128 outputs, three repetitions
after one warmup:

| Path | 47 prompt tokens | 1,717 prompt tokens |
| --- | ---: | ---: |
| Default | 17.87 tok/s, 56.0 ms | 17.31 tok/s, 57.8 ms |
| Device routes + resident decode | 36.56 tok/s, 27.4 ms (was 32.9, 30.4) | 29.39 tok/s, 34.0 ms (was 14.2, 70.5) |
| Device routes + resident decode + graph | 37.16 tok/s, 26.9 ms (was 33.3, 30.0) | 29.68 tok/s, 33.7 ms (was 14.2, 70.4) |

- **The opt-in path now beats the default at both depths:** 2.08 times after 47 prompt tokens and
  1.71 times after 1,717, where it was 0.81 times before.
- **Output IDs are those of the earlier resident path at both depths.** After 1,717 prompt tokens
  they are the default's 128 IDs. After 47 they differ from the default's somewhere in the 128.
- **Kernel time per step** (rocprofv3, 31 steps): 20.7 ms after 47 prompt tokens (was 22.3) and
  27.6 ms after 1,717 (was 65.0), in about 2,460 launches. The attention trio is 20.6 µs per visit
  after 47 (was 54.8) and 160 µs after 1,717 (was 919): scores 27 µs, values 132 µs, the commit 2 µs.
- **Known-answer check:** 9 of 12 for resident decode and for the graph, with the default's IDs
  and no regressed case; `strict` 9 of 12 in both runs. **Graph identity:** ten fresh 48-token
  runs after a different-length warm request, at 67 and at 1,717 prompt tokens, zero logit
  difference against resident eager at every one of 47 steps.

## The kernel

- `decode_table_scores` gives one wave to each key under a fixed grid: wave w of block b serves
  keys 4b + w, 4b + w + 4B, and so on. A captured launch therefore serves every later step of a
  session. Each score is the block kernel's 128-way tree over the query-key dot, plus the same
  wave reduction of the lag table row against the head's relative scores. One extra grid row turns
  the raw gate logits into gains, with the block kernel's expression.
- `decode_values` is one 128-thread block per head. Each 32-key tile computes the online-softmax
  factors exactly as `split_values` does, then loads the tile's value vectors into registers before
  the serial chain consumes them in slot order. The block kernel loads one value vector per chain
  iteration, which is why it cost about 0.5 µs per key.
- The row's K/V is committed before attention instead of after. That ring slot held no live key,
  and the committed bytes are the ones the block kernel read from its staging row.
- The eager path still passes `min(extent, live)` as the bias extent; a recorded launch bakes the
  whole extent, which the kernel handles because it visits keys only up to the live count.

## Validation

- GPU parity: `tests/test_gpu_inkling2_decode_table_attention.py` steps the new route and the
  block route on the same inputs for 20 to 143 positions over five geometries (capacity 5 to 130,
  3 to 24 query heads, head width 16 to 128, bias extent 9 to 64, relative width 1 to 32) and
  compares every output as uint32. All equal.
- `pytest tests/test_unit_inkling2_*.py`: 180 passed.
  `pytest tests/test_gpu_inkling2_*.py`: 108 passed.
- Rates: `scripts/inkling2_decode_bench.py <model> --backend hip_gfx1100 --execution-profile fast
  --quant UD-Q4_K_M --prompt-tokens 47 1717 --output-tokens 128 --reps 3 --warmup 1 --counts`, one
  process per path with its variables. Output identical across repetitions at every depth.
- Trace: the documented `rocprofv3` decode-trace command, reduced with
  `scripts/inkling2_decode_pairs.py trace` over 31 steps.

## What is left in the step

At 1,717 prompt tokens the 27.6 ms of kernel time split as: `decode_values` 6.5 ms (2.4 µs per
32-key tile; each tile still waits for its loads), rocBLAS GEMV 4.8 ms over 413 launches, the Q8_0
dense GEMV 3.9 ms, the NVFP4 expert chain 3.4 ms, the head 1.7 ms, `decode_table_scores` 1.3 ms.
Wall is 33.7 ms, so about 6 ms is dispatch between 2,440 nodes.
