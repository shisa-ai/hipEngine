# Attribute the bulk prefill by phase: the exchange eats the sharding win

## Summary

The kernel inventory ranked kernels but could not say how much of the wall is
not kernel execution, and its per-kernel durations proved unreliable for this
route. `scripts/tp2_prefill_phase_attribution.py` answers the complementary
question with stream events instead of a profiler: it wraps the production layer
helpers, records two events per phase boundary per layer per rank in stream
order with no intermediate syncs, and then calls the real `bulk_prefill`, so each
span is that rank's device execution of that phase including any bubble inside
it.

The accounting closes exactly: phase spans sum to 540.71 ms against a 540.43 ms
wall (100.0%, 0.28 ms unaccounted).

| phase | rank 0 | rank 1 | share of wall |
| --- | ---: | ---: | ---: |
| attention / GDN (replicated) | 224.9 | 203.8 | 42% |
| norm + residual | 2.8 | 2.2 | 0.5% |
| mlp total (sharded) | 312.0 | 333.6 | 62% |
| - shard chain (real compute) | 185.4 | 174.1 | 34% |
| - exchange | 76.3 | 109.6 | 20% |
| - f32 -> bf16 cast | 47.8 | 47.8 | 9% |
| - residual add | 2.1 | 1.8 | 0.4% |
| tail (final norm + head) | 1.1 | 1.1 | 0.2% |

## The finding

**The exchange plus its cast costs 1.94 ms/layer and consumes 67% of the
2.90 ms/layer that halving the MLP saves.** The route leads the single-card
route by only 6% measured (574.8 -> 540.4 ms) because of it.

A per-layer model built from these spans reproduces both routes' measured walls
within 5% (TP2 537 ms modelled vs 540 measured; single card 599 modelled vs
574.8 measured), which is what makes the decomposition trustworthy rather than
merely plausible.

The cost is PCIe traffic, not arithmetic. The staged transport copies each
rank's 5.24 MB bf16 partial device->host (10.5 MB per layer), the host sums in
f32, and the f32 result is published into **pinned host memory**, where the
consumer reads it **zero-copy over PCIe** - 10.5 MB per layer - before a
separate kernel casts it to bf16. The measured 0.75 ms cast for 15.7 MB moved is
~21 GB/s, i.e. it is PCIe-read-bound.

Two corrections to earlier beliefs, both worth recording:

- The replicated attention/GDN phase is **42%** of the wall, not the ~7% implied
  by the profiled kernel-sum share. The earlier figure was wrong because the
  profiled sum was dominated by the (then unshipped) all-rows head.
- The profiled per-kernel durations agree with the event spans for the attention
  kernels (~222 ms profiled vs 225 ms spanned), so the profiler is usable for
  *relative* ranking; it was the aggregate sums that were unstable.

## Levers, ranked

| lever | share of wall | kind |
| --- | ---: | --- |
| exchange + cast | 23% | transport plumbing |
| replicated attention / GDN | 42% (halving saves 21%) | sharding or kernel work |
| shard chain (Q4_K/Q6_K WMMA) | 34% | kernel work |

The exchange is the best contained target. `CompiledDeviceExchange` already
performs the reduction **on the device** with a peer-spin kernel writing to a
device buffer - no host sum, no f32 PCIe read-back, no cast - and its decode
gates are bit-identical (the kernel does bf16 widen -> f32 add -> bf16 round,
the same arithmetic as the host path). It rejects `rows != 1` by construction
("batched prefill uses the staged transports instead"), so the unit is to
generalize it to batched rows.

## Changes

- `scripts/tp2_prefill_phase_attribution.py` - new phase attribution tool. Also
  reports the group's own `exchange_walls_s` so a host-bound reduce can be told
  from a device-bound one, and refuses to report if it wrapped the decode group
  instead of the bulk group.
- `tests/test_unit_scripts_tp2_prefill_phase_attribution.py` - 7 tests pinning
  the two ways the accounting can silently lie (summing the MLP breakdown on top
  of the MLP total; reading the exchange wall from the decode group) plus the
  slot arithmetic and the warmup gating.

Two bugs found and fixed while building it, both of which produced plausible but
wrong numbers rather than errors:

- the prefill drives `_bulk_shard_group`, a different object from the decode
  `_shard_group`; wrapping the latter recorded nothing, which surfaced as a HIP
  invalid-resource-handle on the unrecorded events;
- `_bulk_shard_group` is built lazily by the first bulk prefill, so capturing it
  before that read the decode group's (empty) exchange walls while the recorder
  had correctly wrapped the bulk group.

## Next

Generalize the device-side exchange to batched rows and wire it into the bulk
prefill's shard group. Expected saving is the host sum, the f32 PCIe read-back
and the cast kernel: up to ~1.3 ms/layer of the 1.94, i.e. roughly 15% of the
wall, before counting the loss of the per-layer host synchronization. The
numerics contract is exact - the kernel's widen/add/narrow must reproduce the
host sum followed by the cast, which is verifiable bit-for-bit.
