# Prefill probe plans 256 scratch rows at 45 live rows (lead, unverified)

## Summary

Ran the packed-prefill slab probe at 45 / 135 / 225 prompt tokens per lane hoping for a
fixed-versus-marginal
prefill decomposition. It did not provide that - `wall_seconds` is ~68 s at all three
sizes, i.e. dominated by
model load, and `measurements` carries no prefill-only duration. What it did surface is
one lead, stated below as
unverified.

## Changes

- No code change; probe run only (`scripts/gguf_packed_prefill_slab_probe.py --require-
  cached-build`, clean tree
  `c7702f71c`, packets `/tmp/he-pf/slab-{45,135,225}.json`).

## Measured

| prompt tokens per lane | wall_seconds | bulk_prefill_scratch_rows | prefill_scratch_rows_planned | first_splitting_wave |
| ---: | ---: | ---: | ---: | ---: |
| 45 | 68.12 | 256 | 256 | 6 |
| 135 | 67.551 | 256 | 256 | 2 |
| 225 | 67.617 | 256 | 256 | 2 |

- The probe reports a fixed 256-row prefill scratch plan at 45 live rows, identical at 135 and 225.

## Lead, explicitly unverified

- If prefill *computed* extent followed that plan, it would be a direct mechanism for the
  ~250 ms fixed cost
  measured at ~45 rows (`20260830T153252…`): doing 256 rows of work for 45.
- I could not confirm or kill this cheaply: `bulk_prefill_scratch_rows` and
  `prefill_scratch_rows_planned` do not
  exist anywhere in `hipengine/` (they are probe-side plan names), and a targeted search
  for a prefill launch
  taking live-row arguments found nothing. So it is unknown whether 256 is an allocated
  capacity (free) or the
  launch extent (costly). Recording a fixed capacity as a fixed cost would be unsupported.
- Decisive check for whoever picks this up: read the grid/extent arguments of the Q4_K
  prefill launches at 45
  live rows in a `rocprofv3 --kernel-trace` (block dimensions per launch), or trace the
  `rows` argument at the
  launch site. If the extent is live rows, drop this lead and go straight to tiling/occupancy.

## Also worth noting

- `first_splitting_wave` is 6 at 45 rows and 2 at 135/225, so the probe's wave splitting
  behaves differently in
  the small-row regime. Same caveat: probe-side field, engine meaning unverified.

## Validation

- Three successful probe invocations (exit 0 each) at the named packets; no rate claim is
  made from them, since
  wall_seconds is load-dominated.
