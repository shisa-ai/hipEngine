# Batched Gemma 4 assistant head proposal forward

## Summary

`Gemma4AssistantHead` had one recurrent buffer and one `forward()` call that
issued every launch at `rows=1`, so a multi-request MTP cycle had to run the
proposal step once per request. This adds an independent batched API on the same
loaded weights: one packed launch per dense projection across all active
requests, and one attention launch per request because each request's KV, live
count, position and keep-mask are its own. `forward`, `prime` and
`Gemma4MtpDrafter` are unchanged, and the head keeps no cursor in the batched
path, so a provider cycle owns its returned states and can subset or reorder
active rows.

## Changes

`hipengine/runtime/gemma4_assistant.py`:

- `forward_batch(token_ids, *, positions, shared_kv, recurrent_states)` returns
  `(logits (C, logits_width) float32, next_states (C, backbone_width) uint16 BF16
  bits)`. `shared_kv[i]` is request `i`'s `{backbone_layer: view}` mapping;
  `recurrent_states` is request `i`'s recurrent row as BF16 bits (`uint16`, its
  `uint8` byte view, or float32 values encoded round-to-nearest-even).
- Packed at physical row width C: token gather, embedding scale, pre-projection,
  per-block `attn_q`/`attn_output`/`ffn_gate`/`ffn_up`/`ffn_down`, all norms, the
  Q rotation (per-row rope tables from each request's position), the GeGLU, the
  output projection and the post-projection.
- Per request: one `gemma4_attention_decode_flash_long_bf16` launch per block at
  `tokens=1`, with that request's key/value pointers, `keys=view.live`,
  `row_offset = position - view.base`, and its own mask bytes. The packed mask
  buffer is one upload with a per-request offset.
- `prime_batch(hidden_states)` applies the backbone's final norm to each raw
  hidden row in one launch and returns host BF16 rows, so it seeds
  `forward_batch` directly. It takes either a sequence of per-request device
  buffers (`Gemma4Runner.hidden_state(row=...)`, the resident owner's current
  call) or a host `(C, backbone_width)` BF16 matrix (uint16 bits, their uint8
  byte view, or float32 values). No device-to-device copy exists, so the
  device-buffer form gathers the rows on the host once.
- Gate and up write two separate packed buffers and the GeGLU uses the existing
  `gemma4_gelu_tanh_mul_split_bf16`, which is element-for-element the fused
  kernel's arithmetic. A fused `(rows, 2 * intermediate)` destination cannot hold
  two packed projections without dropping the up projection back to one launch
  per request.
- Validation is complete before the first device write: token id range,
  non-negative positions, per-request count agreement, `live > 0`, `base >= 0`,
  `0 <= position - base <= live`, the bound layer present in every request's
  mapping, the view's four fields, and the state array's dtype/shape. A refused
  batch launches nothing and leaves the packed scratch as it was.
- `_stage` was factored onto a `_grow(pool, ...)` helper so the batched path has
  its own grow-on-demand pools (`_batch`, `_batch_scratch`); `close()` releases
  them. The batched path never touches `_staged` or `_recurrent`.
- `_logits_width` is the head's tied output-projection width, read once at
  construction and used by *both* paths: `forward`'s logits row and
  `forward_batch`'s `(C, vocab)` buffer. `GGUFTensorInfo.shape` is the row-major
  logical shape, so a linear's output count is `shape[0]` and its input width is
  `shape[1]` -- the same reading the backbone loader uses for `ffn_gate`. The
  input width is checked against `n_embd` at construction, so a transposed table
  fails loudly instead of presenting the hidden width as a vocabulary.

### Defect found on real artifacts and fixed

The first version read `shape[1]` (the input width) as the vocabulary. On the
shipped head `token_embd.weight` is row-major `(262144, 1024)`, so the batched
path emitted 1024-wide logits while `forward`'s literal produced 262144, and a
public smoke could only ever sample ids below 1024. The parent's GPU oracle
`tests/test_gpu_gemma4_mtp_batch_parity.py` caught it on its first assertion
(`shapes (1024,) (262144,) mismatch`); the leading logits agreed because a Q8_0
dot product per output row does not depend on the output count. Fixed by reading
`shape[0]`, validating `shape[1] == n_embd`, and giving both paths the one width
so they cannot disagree again. Verified from the artifact's GGUF metadata on CPU
(no HIP): `token_embd.weight` row-major `(262144, 1024)`, `n_embd = 1024`, derived
width 262144.

`tests/test_unit_gemma4_assistant_batch_forward.py` (new, 33 nodes): a fake
device (byte-addressed store + launch log) replaces `malloc`/`free`/the copy
helpers and every launch, so the tests assert pointer arithmetic and row contents
rather than argument shapes alone. Covered: one `rows=C` launch per projection;
one attention launch per request with that request's KV, `keys`, `row_offset`,
window and mask bytes, including a request whose two blocks sit in different slot
frames because its sliding band was rebased; per-request rope table rows;
per-request token and state landing in their own concat row; `next_states`/`logits`
row order and freshness; C4 then C1 then a C2 subset of a previous cycle with no
leftover width or state; validation-before-mutation over 14 malformed batches (no
launch, scratch bytes unchanged); `prime_batch` from device buffers and from a
host BF16 matrix, each applying the backbone norm per row and feeding
`forward_batch`; the shared logits width spanning the whole vocabulary in both
paths and a transposed output table refused at construction; and
`forward`/`prime` still running at row width 1.

## Validation

- `pytest tests/test_unit_gemma4_assistant_batch_forward.py` -> 33 passed.
- Same file plus `test_unit_gemma4_assistant_{device,geometry,kv_binding,
  forward_guard,gguf}`, `test_unit_gemma4_mtp_admission`,
  `test_unit_gemma4_sliding_kv_ownership` -> 100 passed, 14 skipped
  (artifact/HIP nodes).
- CPU metadata read of the real head GGUF (`scan_gguf`, no HIP): derived logits
  width 262144 for `n_embd` 1024.
- `python3 audit/audit.py check` -> no new row (no flag, no dispatch branch).
- Mutation checks on the harness: forcing the pre-projection to `rows=1`,
  reading block 0's slot frame for every block, reusing request 0's mask, and
  replicating row 0's state each fail a node, so the tests are not vacuous.
- `test_unit_gemma4_mtp_serving_route` has two failures in the shared worktree
  from other in-flight edits (`engine_loop.py`/`gemma4_mtp.py`/`gemma4.py`); the
  same module passes 27/27 in a clean `HEAD` worktree with only this module's
  change applied, so they are not caused by this unit.
- Not run: any GPU execution. The packed projections at `rows=C` (Q8_0 prefill /
  row-tiled schedules), the per-request `tokens=1` attention launches against
  real caches, and numeric agreement of a batched proposal with the same request
  proposed alone all need the parent's GPU box.
