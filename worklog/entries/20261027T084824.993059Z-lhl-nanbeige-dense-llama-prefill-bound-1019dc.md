# Dense Llama prefill bound is a geometry fact, not the decode constant

Supersedes the context-cap decision in
`worklog/entries/20261027T054330.388941Z-lhl-nanbeige-dense-llama-generation-8d143f.md`,
which treated `MAX_DENSE_DECODE_CONTEXT` (16128) as the whole servable context.

## Summary

`MAX_DENSE_DECODE_CONTEXT` is the KV cache capacity, not the longest prompt. The
strict causal prefill kernel also stages one FP32 logit row per key in LDS —
`max(head_dim + keys + threads, keys + 528)` floats — and for a 128-wide head
that admits 15856 keys, 272 fewer than the cache holds. Nothing checked it, so a
prompt in `(15856, 16128]` passed admission and then raised
`NotImplementedError` from the attention launcher, after a 66 GB weight load and
partway into the prompt pass.

The two bounds are both real and distinct: the prompt pass admits 15856 tokens,
and the cache can hold 16128, so the extra 272 are generation headroom for a
maximum-length prompt. `max_dense_prefill_tokens(spec)` now derives the prompt
bound from the launcher's own admission rule and the generator refuses a longer
prompt by name before loading anything.

## Changes

- `hipengine/runtime/llama_dense.py`: `max_dense_prefill_tokens(spec)` bisects
  `gemma4_attention_shared_bytes` over the cache capacity. Bisection is sound
  because that predicate is monotonic in `keys`; it asks the kernel family's own
  rule rather than restating the formula, so a change to the LDS row cannot drift
  from the admission check. A geometry that cannot fit even one key raises
  instead of returning a bound it cannot serve.
- `hipengine/generation/llama_dense.py`: `max_prompt_tokens` is computed at
  construction, and `generate_detailed` tokenizes and bound-checks every row
  before `_ensure_runner()`. The per-row prompt and total-context checks moved
  out of `_generate_row` into `_validate_prompt_length`, which now holds both
  bounds in one place.
- `tests/test_unit_llama_dense_generation.py`: the bound per head width
  (32/128 → 15856, 512 → 16128, because the 256/512 class kernel moves logits to
  request-owned global scratch instead of refusing), the prompt bound never
  exceeding the cache, the refusal landing before the weight load, and the
  no-room-to-generate case.
- `tests/test_gpu_llama_dense_decode.py`: a request that fills the fixture's
  declared 512 positions (508 prompt + 4 generated) must reproduce the reference
  tokens, which exercises the widest admitted prompt row count and a decode step
  at the final position.
- `docs/REFACTOR.md`: the entry now records both budgets and names the tiled
  flash prefill, not only the paged decode route, as what lifts them.

## Validation

- `uv run pytest tests/test_unit_llama_dense_generation.py` — 27 passed.
- `uv run pytest tests/test_gpu_llama_dense_decode.py` — 5 passed, including the
  new full-declared-context request.
- Launcher boundary, `head_dim=128`: 15856 keys → 65536 bytes of LDS, admitted;
  15857 → 65540 bytes, refused by name. Confirmed by
  `gemma4_attention_shared_bytes` and by running the kernel at 15856 keys.
- Prefill correctness at the admitted maximum: one 15856-key launch at the
  Nanbeige geometry (56/8 heads, 128 wide) completed and matched an FP64
  reference on the first, last, and middle rows to 9.8e-4. That residual is the
  kernel's BF16 output storage, not arithmetic: rounding the reference to BF16
  first leaves a maximum of 2.4e-4 at 256 and 1024 rows, which is one to two
  BF16 ulps of double-rounding.
- Dense decode correctness at the cache ceiling: at `max_context=16128`,
  `context_len=16128`, the FP32 kernel matched an FP64 reference to 6.2e-8
  absolute (4.1e-6 relative), and the same at `context_len=16000`.
- The kernel launches at exactly 65536 bytes of dynamic LDS on this
  architecture, so the 64 KiB budget is usable in full rather than a bound that
  has to be discounted for launch overhead.
- Nanbeige 4.3 33B FP8 on `hip_gfx1151`, through `LLM.generate_detailed` with
  `max_sequence_length=8192`: an 8081-token prompt plus 12 greedy tokens
  completed in 1876 s wall, of which about 120 s is the weight load. The
  continuation is coherent and on-topic (`"\n\nUnified memory lets a discrete
  accelerator read the same"`), so the full default context runs on the real
  checkpoint and not only on the fixture.
- Cost, measured per layer in isolation at the Nanbeige geometry: 32.4 s at 8192
  keys and 174.2 s at 15856. Attention is therefore about 1685 s of that 1876 s
  across 52 layers, which is where the wall time goes.

## Next

- **Full-context prefill is quadratic and expensive.** One layer at 15856 keys
  takes 174 s, so a 52-layer prompt at the admitted maximum is roughly 2.5 hours;
  8192 keys is 32 s per layer, which is the ~31 minutes measured end to end
  above. This is the exact block kernel walking every key from column 0 for
  every query row, one block per (token, head). The tiled flash prefill stages a
  fixed K/V tile, so it is the route to a usable long-context prompt pass, and it
  needs its own correctness and timing gate before it becomes the default.
  Recorded in `docs/REFACTOR.md`.
- Decode is not the bottleneck at these lengths: it is weight-bandwidth bound, so
  a longer context adds KV reads to a step that already streams 66 GB of weights.
  The earlier 25-token-context measurement of 3.12 tokens/s should be re-measured
  at 8k context before any claim about it is made; this unit did not separate it
  from prefill.
- The mask is materialized host-side at `tokens x keys` bytes, 251 MB at 15856
  rows. It is not a correctness problem but it is the next thing a tiled route
  should stop paying for.
