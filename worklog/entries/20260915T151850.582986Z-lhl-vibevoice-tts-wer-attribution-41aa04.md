# The 35.3% WER failure was a real synthesis failure; the evaluator floor is now a standing control

## Summary

The reviewer asked whether the 0.353-WER two-speaker run was a synthesis failure or
an evaluator error, and to answer it by comparing against the torch lane. It was a
**genuine synthesis failure**, established by running two independent ASRs on the
archived waveform rather than by trusting the one the gate uses.

The reason this needed more than one ASR: the suite's evaluator is
`microsoft/VibeVoice-ASR-HF` running through **hipEngine's own `LLM.transcribe`** —
the same runtime the suite qualifies. A WER from that lane is not by itself
attributable.

## The measurement

`openai/whisper-large-v3-turbo` (different architecture, different training data,
5-beam, separate environment) on the identical archived PCM:

| archived PCM | HIP ASR (the gate) | whisper-large-v3-turbo | |
| --- | --- | --- | --- |
| `two-2turn` s15, pre-decoder (the reported failure) | 0.353 — "I can see you in the world this morning" | 0.471 — **"I agree and the budget question is finally settled."** | turn 1 **absent** |
| same file, first 3.3 s only | 0.882 — "I can see you in the world this morning" | 0.824 — "I'm cleaning my wall this morning." | both wrong, **differently** |
| `two-2turn` s17, both-changes-on runaway | 0.647 | 0.471 | both hear the **doubled sentence** |
| `two-2turn` s15, kept revision | 0.0 | 0.0 | clean |
| `two-2turn` s16, kept revision | 0.059 | 0.0 | clean |
| `two-2turn` s17, kept revision | 0.0 | 0.0 | clean |
| reference `single_audio.pcm` | 0.0 | 0.0 | evaluator floor |
| reference `two_audio.pcm` | 0.0 | 0.0 | evaluator floor |

Two independent models, on the same region, produced **different** confabulations
("I can see you in the world" / "I'm cleaning my wall") while both transcribe the
reference implementation's audio exactly. That is the signature of audio that does
not encode the intended words, not of an ASR artifact — an ASR artifact tends to be
a plausible reading of the same phonetics, and whisper dropped the region outright
in the whole-file case. The runaway is likewise real: both ASRs hear the sentence
twice.

The kept revision is clean under both evaluators, so the decoder FFN GEMM that this
branch retained is quality-neutral and the reverted semantic dispatch was the
harmful change. That closes the reviewer's item 3 with the same verdict the
three-seed A/B reached, now from an evaluator the suite does not own.

## What was added to the suite

`_evaluator_floor` transcribes `single_audio.npz` / `two_audio.npz` — the reference
implementation's own PCM for the pinned requests, which contains every word — and
records the WER as `evaluator_floor` in the artifact. Each request now also carries
`wer_above_evaluator_floor`. It is two transcriptions per scoring run.

The floor measures **0.0** on both requests, and the artifact's `interpretation`
says what that does and does not buy: it bounds the evaluator's systematic error, but
a floor of 0.0 does not make every non-zero WER attributable to the TTS lane, because
the evaluator can still mishear audio whose phonetics differ from the reference. That
is exactly the case the cross-check found — the HIP ASR scored 0.059 on `ab-dec` s16
and 0.118 on `ab-now` where whisper scored 0.0, and 0.118 on the **fork's own** audio
where whisper scored 0.059. So the HIP ASR lane contributes roughly 0.06-0.12 WER of
its own on this lane's audio even though it is exact on the reference audio.

That is worth stating plainly for the gate: `wer_max = 0.1` is close to the
evaluator's own reach on this lane's audio, so a single request at 0.059-0.118 is not
evidence of a synthesis defect. The gate was left at 0.1 rather than relaxed on this
evidence — relaxing it would need a measured floor on *this lane's* audio, which the
suite does not yet produce — and the limitation is recorded in both the artifact and
`benchmarks/prompts/vibevoice-tts-quality.json`.

## The speed harness

All three reviewer points were already closed earlier in this session and are
verified again here: the generation budget comes from the request's declared
`max_audio_seconds` (4.333 s, a 35-token cap) rather than the oracle's 27-token
answer; the torch lane serves the fixture's recorded random operands by shape, with a
consumption ledger, reproducing the fixture's step-0 `eps` at `max_abs_diff` 0.0; and
the reported cold start is the first synthesis after load, measured before the traced
correctness run.

## Next

The evaluator's floor on *this lane's* audio is the missing measurement: it would
need either the fork's ASR (unavailable — `vibevoice_asr_processor.py` imports
`VibeVoiceASRTextTokenizerFast`, which this fork revision does not define) or an
independent ASR in-tree. Until then `wer_max` should be read as approximately
`0.1 + evaluator reach`, not as a pure TTS bound.
