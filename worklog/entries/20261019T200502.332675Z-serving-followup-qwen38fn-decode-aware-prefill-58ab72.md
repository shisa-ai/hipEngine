# Bound Flash-Next prefill work while decode is due

## Summary

P1's token-only candidates missed the frozen latency/cost criteria. P2 now
keeps useful token chunks and suspends at quiescent completed-layer boundaries
while peer decode is due. The paired HTTP experiment is running; no final
performance claim or commit is made by this checkpoint.

## Changes

- Add optional `EngineLoopConfig.decode_prefill_token_budget` and its positive
  CLI/environment control. Other generators retain `None`; Flash-Next declares
  `min(1024, runner.prefill_chunk_size)` on its normal route. Explicit operator
  round budgets suppress this implicit bound unless the active bound is also
  explicitly selected.
- Extract the existing prefill loop into a drainable iterator without changing
  layer operations. Idle prefill drains it normally. Active-decode prefill uses
  a request-owned saved Python context and returns at completed-layer boundaries
  after a target share of 150 ms, or 80 ms for narrow chunks below 257 tokens.
  The share is not a hard bound: one layer cannot be interrupted.
- Flush deferred residual writes and synchronize before yielding; invalidate
  transient F16 publications before resuming. Staging buffers stay owned by the
  suspended runner. Reset and close end its saved iterator before reuse.
- Rewind planned scheduler cursors for incomplete chunks. Only a completed
  chunk publishes prompt progress, import readiness or a first-token result.
  Cancellation and failed work cannot publish unfinished prompt tokens.
- Record planned and committed tokens separately with request IDs, selected
  budget, starting context, due decode width and completed-segment wall time.
  The HTTP harness also captures per-wave policy telemetry and source hashes.
