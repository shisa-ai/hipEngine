# the default route is deliberately unchanged by attaching a provider and that is a product decision not a plumbing gap

## Summary

I tried to make `llm.generate()` honour a configured speculative provider, on the
grounds that an explicit request should not be silently downgraded. **The attempt
was reverted**, because it contradicts a reviewed pin whose name states the
design:

```
tests/test_unit_llm_generate.py::
    test_llm_attaches_explicit_speculative_provider_without_changing_default_route
```

**Attaching a provider is not meant to change `generate`'s route.** That is a
product decision the engine already made, and the previous unit's note that
flipping it "changes the semantics of the primary public entry point" was the
right instinct.

## What the attempt measured, because it is the number the objective needs

With the routing in place, a configured provider made `generate_detailed` take
the MTP path:

```
execution_path : gemma4_mtp_batched_exact_verify
decode tok/s   : 48.6      (against 28.4 plain)
```

**1.71x on `llm.generate()` itself**, which is the number that would count if the
route were adopted. It is a real measurement of the decision's value, taken
before the decision was made, and it is why this is recorded rather than simply
dropped.

## A fact that removes an objection

The Gemma 4 runner's own plain path is **already greedy-only**:

```
Gemma 4 basic runner: temperature must be 0; top-p/top-k/min-p sampling is not
implemented
```

So the MTP provider's greedy-only restriction costs nothing on this model --
there is no sampled route for it to fall back from. My first routing attempt
carried a `_is_greedy_speculative_request` guard to keep sampled requests on the
plain path; for Gemma 4 that guard was a no-op, and the guard itself is what
`gemma4` would not need. **A future attempt should not re-add it on the theory
that it protects sampling.**

## Where this leaves the objective

**Item 5, 2X decode, now splits cleanly in two, and neither half is plumbing:**

| route | tok/s | against the 56.2 target |
| --- | ---: | --- |
| `generate()` as designed (plain AR) | 28.4 | 1.98x short |
| `generate_speculative_mtp_detailed()` (opt-in MTP) | 47.1 | 1.19x short |
| `generate()` with MTP routed in (measured, reverted) | 48.6 | 1.16x short |

The 2X target is reachable through MTP and not through the plain path -- the
weight-traffic floor `20260928T091614` computed is 12.4 ms per token against a
17.8 ms target, and the plain path has no mechanism to amortize it. **So item 5
is now gated on a product decision about which entry point the objective is
measured at, and I am not making that call unilaterally.**

## The other item

Prefill is 1.33x short and its sub-gap is attention. **The flash-attention port
is already in flight**: `20260928T100244` has the reduction-order oracle landed
as an executable test (`tests/test_unit_gemma4_attention_logit_tree.py`, 6
passed), and the kernel port itself is the remaining work. That is the
highest-value remaining item and it is too large to start at the end of a
context -- it needs a fresh unit.
