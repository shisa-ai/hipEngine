# EVIE batched encode campaign: scoped handoff

## Summary

User approved executing the batched-encode campaign (the measured
dominant lever: torch gains 1.99x from batching; our sequential path
already beats torch's sequential 1.33x). Scoping against the code found
the full vertical slice needs one new attention kernel, one new conv
kernel variant, and rewiring; it does not fit in the remaining session
context, so this entry records the verified build plan instead of a
half-implementation. Nothing in the tree was changed for this campaign.

## Build plan (verified against current code)

Batched query encode first (uniform ~20-token sequences), then documents.
Concatenate B sequences (pad to max length with the existing
mask-compression trick applied per sequence), one text_forward over the
concatenated stream, split outputs per segment.

1. **Attention (text full-attention layers, 8 of 32): needs segment
   masking.** Text attention is BIDIRECTIONAL in this model (ColPali
   enable_bidirectional_attention; runtime \_attention is the
   bidirectional helper — see also the fixture docstring). Concatenated
   sequences would attend across boundaries. Cheapest fix that does not
   touch existing kernels: a new small kernel
   `hipengine_evie_scores_segment_mask_{f16,f32}` run between the QK^T
   GEMM and the softmax: scores[i,j] = -inf when seg[i] != seg[j]
   (segment ids as an int32 per token; pass a (T,) device array). The f16
   path applies it to the scores planes; the f32 pointer-array path
   applies it to the scores buffer before its softmax.
2. **Conv prefill (GDN layers): needs a segments variant.**
   `qwen35_linear_attn_conv_prefill_f32` chains conv_state across the
   whole call, so boundaries leak. Write
   `qwen35_linear_attn_conv_prefill_f32_segments` (copy the kernel; on
   token index == cu_seqlens[s] reset the state to zero before the tap
   accumulation) + host wrapper. RED test first on a CPU-reference
   segment fixture.
3. **GDN recurrence: segments variant already exists** —
   `qwen35_gdn_prefill_recurrent_normalized_segments_cluster8_f32`
   (cu_seqlens + state_indices; per-segment state slots). Wire it in
   _gdn_layer behind a segments argument; per-segment state slots sized
   n_state * B (zero all before each layer — the GPU scale-zero kernel
   extends to the larger buffer).
4. **RoPE/positions**: build positions per segment (each starts at 0) —
   lm_rope_positions per sequence, concatenate; _mrope_tables already
   takes arbitrary positions.
5. **Gates/l2norm/rmsnorm/embed**: per-token, no cross-token state — no
   changes.
6. **API**: `encode_queries(list_of(ids,mask)) -> list of embeddings`;
   same for documents later (documents additionally need batched
   vision_forward — vision attention is already bidirectional per page,
   so the vision tower processes each page independently; simplest v1:
   run vision per page as today, batch only the text stack across
   pages).
7. **Tests**: extend the fixture-based parity: batched encode of the
   same (single) query repeated B times must equal the sequential
   encode bit-for-bit (fp32) — a strong exactness oracle for
   segment isolation. Then a 2-distinct-query CPU-reference fixture.
8. **Gate**: sequential-vs-batched exactness (fp32 bit-equal or <=1e-6),
   fp16 manifest thresholds unchanged, bench 8-query batched vs
   sequential, then documents.

## Expected result

If the batching gain matches torch's, ~8 queries drop from ~510 ms to
~260 ms and 8 pages from ~1620 ms to ~850-900 ms (vision per page), i.e.
total ~1.2 s vs torch bf16 1.30 s.
