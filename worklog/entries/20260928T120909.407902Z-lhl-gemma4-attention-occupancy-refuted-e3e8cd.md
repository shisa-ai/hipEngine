# the mask-zero probe is not a load probe, and the tiled attention variant is a dead route

## Summary

Two probes, both aimed at the attention kernel's 2 percent of fp32 FMA peak, both
negative. One retires a diagnostic this tree proposed for itself. The other
refutes the occupancy explanation and turns up a dead kernel route on the way.

### `--mask zero` does not isolate the K/V loads

The bench script documents it as "the ablation that does not also remove the
work": an all-zero keep-mask runs the same shapes, skips every K/V load, and
leaves the key loop and the reductions intact. Measured at 2048 tokens, one
session:

| case | `--mask keep` | `--mask zero` | delta |
| --- | ---: | ---: | ---: |
| swa 256d window=1024 | 48.56 ms | 34.56 ms | -28.8% |
| swa 256d window=0 (probe) | 77.71 ms | 95.42 ms | **+22.8%** |
| full 512d window=0 | 130.76 ms | 175.00 ms | **+33.9%** |

**Removing every K/V load makes two of the three cases slower.** The two
window=0 cases have the same load reduction as the sliding case and move the
other way, so the delta cannot be attributed to the loads in any of them.

The mechanism is in the arithmetic the ablation creates. With every key masked,
`running_max` stays `-INFINITY`, so pass 2 evaluates
`expf(logits_s[j] - running_max)` as `expf(-inf - -inf)` = `expf(NaN)` = NaN,
and pass 3 accumulates NaN. The probe replaces one special-value path with
another; it does not remove the work.

`scripts/gemma4_attention_prefill_bench.py` keeps the mode and its docstring
should stop calling it a load ablation. It is still useful as a
special-value-input case, which is how the bit-exactness A/B below uses it.

### The tiled variant is not faster, and it is not a different contract

The strict kernel materialises one logit per key in shared memory, so its shared
array is `(head_dim + keys + 256) * 4` bytes and its occupancy ceiling falls with
context:

| keys | head_dim | LDS/block | blocks/CU at 64 KB |
| ---: | ---: | ---: | ---: |
| 512 | 512 | 5120 B | 12 |
| 2048 | 512 | 11264 B | 5 |
| 4096 | 512 | 19456 B | 3 |

The tiled kernel was written to make that footprint constant, and an earlier
entry measured it as a wash -- **at 512 tokens, where the footprint is 5120 bytes
and 12 blocks fit.** That is the one size at which the theory cannot show up.
Measured at 2048 with `scripts/gemma4_attention_prefill_tiled_ab.py`, both
kernels through ctypes on the same device buffers, 5 iters and 2 warmups:

| tokens | head_dim | strict | tiled | ratio |
| ---: | ---: | ---: | ---: | ---: |
| 512 | 256 | 150.5 ms | 150.65 ms | 1.00 |
| 2048 | 256 | 46.72 ms | 67.21 ms | **1.44 (slower)** |
| 2048 | 512 | 88.83 ms | 95.52 ms | **1.075 (slower)** |

**Making the footprint constant makes the kernel slower**, by 44 percent at
head_dim 256. Occupancy is not what limits the strict kernel, and the shared
logit array is not the lever.

**And the two kernels are bit-identical.** 0 mismatched elements out of 8,388,608
and 16,777,216; max abs diff 0; max rel diff 0. They are one arithmetic contract
with two schedules, not two contracts. So the tiled route is dead on both counts
-- slower everywhere it has been measured, and carrying no behaviour the strict
kernel does not already have -- and it is now a `docs/REFACTOR.md` removal entry.
Nothing selects it and it has no Python wrapper, so deleting it preserves
everything.

### What the occupancy measurement did establish

`rocprofv3 --pmc OccupancyPercent` on the three launches at 2048 tokens:

| launch | achieved occupancy | LDS/block |
| --- | ---: | ---: |
| swa 256d window=1024 | 57.0% | 10240 B |
| swa 256d window=0 (probe) | 34.0% | 10240 B |
| full 512d window=0 | 21.5% | 11264 B |

The first two have identical grid, identical LDS and identical block count, and
differ only in how many keys each block walks -- and they land 23 points apart.
Achieved occupancy here tracks the work rather than a fixed capacity limit, which
is why it is not the explanatory quantity the table above refuted it as.

## Next

- Five explanations for the attention kernel's cost are now closed by
  measurement rather than argument: traffic (`--dtype f32`, 1.08-1.14), the
  masked-column walk (the causal-tail trim, spent at -17.9 percent), pass-1 ILP
  (the refused unroll, inert at 0.2 percent), the K/V loads (`--mask zero`,
  removing them is slower), and occupancy (the tiled variant, 1.44x slower at
  2048). The next probe has to be a different kind of measurement, not another
  loop-level ablation -- a stall-reason counter on the sliding case, which is the
  larger attention term at 1162.6 ms of the 1811.3 ms, would say which of
  latency, LDS or issue is actually exposed.
- Run the tiled removal from `docs/REFACTOR.md` as its own unit: delete the
  kernel, the launcher, the two exports and the A/B script, then confirm
  `python3 audit/audit.py check` and the gemma4 attention tests.
