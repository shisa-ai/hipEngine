# halving ROWS_PER_PASS costs 19 percent: the down projection is reuse-bound, not occupancy-bound

## Summary

The in-situ decomposition put both expert MMQ kernels at 49 GB/s of weight traffic and
2.3 to 3.0 TMAC/s, far from both ceilings, and named them latency-bound. The Q5_1 down
projection compiles to **96 VGPRs**, which caps it at five 128-thread blocks per CU --
**640 of 2048 threads, 31 percent occupancy** -- so occupancy was the obvious lever, and
`ROWS_PER_PASS` is the knob that controls it: the constant exists to amortise the weight
unpack over rows, and its 32 accumulators are the register pressure.

**The trade goes the other way.**

| `ROWS_PER_PASS` | rows/expert | median | GMAC/s |
| ---: | ---: | ---: | ---: |
| **32** | 32 | **2.703 ms** | **3004.4** |
| 16 | 32 | 3.215 ms | 2525.9 |
| 32 | 16 | 1.631 ms | 2489.0 |
| 16 | 16 | 1.638 ms | 2478.7 |

**Halving `ROWS_PER_PASS` costs 19 percent at the production shape.** The last two rows
are the control: at 16 rows per expert both settings do one pass over the weight stream
and the times are identical to 0.4 percent, so the loss is entirely the second pass the
16-row setting needs to cover 32 rows.

The constant's own comment predicted exactly this -- "an expert averaging 32 rows
therefore reads its weights twice at 16 and once at 32" -- and the measurement confirms
that the weight stream is worth more than the occupancy it buys. The change was reverted;
`git diff` is empty.

## What this leaves

**The kernel is reuse-bound, and its reuse factor is already optimal for its shape.**
`ROWS_PER_PASS` = 32 matches the 32 rows an expert averages at a 512-token prompt, so
the weight stream is read once and cannot be read less. That closes the shape lever on
this kernel: there is no value of the constant that beats 32 at this prompt length, and
the 31 percent occupancy is a consequence of the choice rather than a defect in it.

**So the 49 GB/s is not explained by occupancy or by reuse.** Two kernels with different
quantizations, different weight sets and different arithmetic both land on 49 GB/s to
within 0.4 percent, which points at something they share: the activation load path, the
DS4 block layout, or the launch geometry. Each thread loads 704 activation bytes per row
against 528 weight bytes per pass, so the activation side is 43 times the weight side per
thread and is served from L1 -- if that path is serialised the kernel waits on it while
the DRAM bus is idle, which is what a 19 percent-of-peak weight rate with an unsaturated
arithmetic unit looks like.

## Changes

None. `ROWS_PER_PASS` was set to 16, measured, and reverted.

## Next

- **The shape lever on the down projection is closed.** Do not revisit `ROWS_PER_PASS`;
  32 is optimal at 512 tokens and the only way past it is a prompt long enough to
  average more rows per expert.
- **The next question is the shared 49 GB/s, and the activation load path is the
  candidate.** Each thread reads 704 activation bytes per row from a 32-row, 22.5 KB
  block working set, which fits L1 -- so the question is whether those reads are
  vectorised and issued independently or serialised behind the weight unpack. A
  counter that separates L1 traffic from L2-to-CU traffic would answer it; `FETCH_SIZE`
  cannot, because it counts the latter.
- **Note the shape of this negative.** Three consecutive units have now priced a
  candidate and closed it -- the down projection's ceiling, the readback drain, and now
  the reuse constant. That is progress in the sense that the excluded set is now large
  and each exclusion rests on a measurement, but the prefill number has not moved. The
  next unit should prefer a candidate with a *mechanism* for the shared rate over
  another single-kernel constant.
