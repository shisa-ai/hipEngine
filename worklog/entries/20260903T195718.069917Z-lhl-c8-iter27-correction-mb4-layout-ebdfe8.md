# Correction: iter27 mb4 probe measured under wrong activation layout

Supersedes the mechanism conclusion in
`20260903T194935.868342Z-lhl-c8-iter27-q5-raw-mmq32-minblocks-neutral-6c9c5f.md`
as follows; the committed entry is immutable per policy, so this decision
corrects the record.

## Summary

The iter27 minblocks-probe timing conclusion was measured under the wrong
activation producer layout; under the production (non-kmajor d4s4) layout
the mb4 arm is 1.1164x slower, not neutral. The per-block-MLP limiter
analysis stands; the mb4 lever does not.

## What was wrong

The iter27 leaf fed all arms from
`gguf_q8_1_d4s4_f32_quantize_bf16_kmajor` (the source-layout producer).
Production feeds raw MMQ32 owners from `gguf_q8_1_d4s4_f32_quantize_bf16`
(non-kmajor). Under the wrong layout the serial mb2 arm ran 10.170 ms per
48-weight R24 pass versus 9.109 ms under the correct layout, so the
"mb4 neutral (0.9986x)" reading was taken against a slowed control.

## Corrected result (measured 2026-09-04, correct layout)

- mb2 serial owner: 9.109 ms (registered default, unchanged).
- mb4 forced: 10.170 ms = **1.1164x SLOWER** (regressive, not neutral).
- pipe (iter28 variant): 9.123 ms = 1.0015x (neutral).
- All arms bit-identical under both layouts.

The per-block-MLP limiter analysis stands (all 160 blocks are resident at
mb2), but the mb4 arm is not a viable lever under production feeding. See
`benchmarks/results/2026-09-04-w7900-q4km-k3-c8-q5-raw-mmq32-pipe-leaf.json`
and the docs/KERNELS.md layout gotcha.
