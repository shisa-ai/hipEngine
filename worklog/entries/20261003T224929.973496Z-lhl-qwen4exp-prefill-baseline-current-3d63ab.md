## The gap, and why its shape is the useful part

Against the fastest same-file comparator (halo-box PR #63 head `c4aa30229`, BF16,
479.4 / 860.8 / 1051.6):

| Length | hipEngine | comparator | gap |
| ---: | ---: | ---: | ---: |
| 512 | 300.2 | 479.4 | 1.60x |
| 1024 | 297.4 | 860.8 | 2.90x |
| 4096 | 265.9 | 1051.6 | 3.96x |

**The gap grows with length**, which rules out a fixed per-token deficit. Marginal
cost between the measured points:

| Interval | hipEngine ms/token | comparator ms/token | ratio |
| --- | ---: | ---: | ---: |
| 512 -> 1024 | 3.43 | 0.24 | 14.5x |
| 1024 -> 4096 | 3.98 | 0.88 | 4.5x |

So the deficit is in the **constant**, not the exponent: the comparator's own
marginal cost rises 3.7x across those intervals while ours rises 1.16x, i.e. it
carries the larger quadratic term. Fitting `a*n + b*n^2` gives `a = 3.34 ms/token`
and `b = 6.0e-5 ms/token^2`, putting only about 1000 ms of the 15702 ms 4K prefill
in the quadratic term (6.4%). **The 512 ratio looks comparatively flattering
because the comparator pays a large fixed cost there** - 1068 ms for 512 tokens -
not because this engine is close.
