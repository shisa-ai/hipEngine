# ShareGPT pass: first-token latency is 1.15 s, not 5.99 s; and no request was fallback-free

## Summary

Two readings in
[`20260917T162126.651176Z`](20260917T162126.651176Z-lhl-sharegpt-mtp-routing-pass-8d7978.md)
were wrong, both from the recorder rather than the engine. Corrected by
`scripts/sharegpt_mtp_routing_pass.py` and a re-run of the same c=1 load:

1. **The reported TTFT was time to the first *answer* token, not the first
   token.** Qwen-style replies stream their reasoning on `delta.reasoning_content`,
   which the recorder ignored, so `ttft_ms` only fired on `delta.content` - after
   the whole thinking block. Every one of the 24 requests streamed a thinking
   block first, and 20 of them had produced no answer text at all when the
   128-token budget ran out, so the field was populated for 4 of 24 rows and the
   "5,988.7 ms median" was a median over four samples of a different quantity.
   The recorder now times both channels separately: **median 1,150 ms to the
   first generated token (441 ms minimum, 4,314 ms on the first request of a
   cold server, and the largest values on the longest prompts - 2,715 ms at 841
   tokens)**, and a separate 5,961 ms median to the first *answer* token over the
   4 requests that reached one.
2. **"No request fell back" was true at request level and wrong at token level.**
   All 24 requests report `mtp_used: true`, and the summary's request-level
   fallback counter was therefore empty, but every request also carries exactly
   one `no_provider` event: the first output token, emitted before a speculative
   cycle has a provider. 29 of 3,072 emitted tokens (0.94%) came from outside a
   cycle - 19 requests emitted one such token, 5 emitted two. The stronger claim
   that does hold: no request abandoned speculation mid-stream
   (`first_fallback_position` is unset for all 24) and the rate-cliff detector
   found no request.

The routing result itself is unchanged and now carries a per-request table:
24 of 24 requests ran MTP, 3,043 of 3,072 tokens (99.1%) came from speculative
cycles, depth 3 for nearly every cycle, and the 1,023-token MTP window did not
limit anything (the longest prompt is 841 tokens). The c>=4 crash finding is
unaffected: the engine service still dies on a concurrent prompt activation, and
the c=4 requests that completed still ran no MTP (`fallback_reason:
no_provider`).

## Changes

- `scripts/sharegpt_mtp_routing_pass.py`: records `reasoning_content` and
  `content` separately, times the first token of each channel, keeps
  `first_decode_state_ms` from the first chunk that reports
  `decode_state.generated_tokens`, and reports the thinking/answer split
  (`thinking_requests`, `answer_requests`, `median_first_thinking_ms`,
  `median_first_answer_ms`) plus the total non-cycle token count in the summary.
- `benchmarks/results/2026-09-17-gfx1151-qwen38-sharegpt-mtp-routing.json`: the
  c=1 arm is the re-measured run, with a 24-row per-request table and a note
  explaining the three different first-token figures (first SSE chunk, first
  generated token, first answer token).
- `benchmarks/CHANGELOG.md`: the c=1 entry now states the token-level attribution
  and the corrected latency.

configuration as the first pass (24 prompts, `--max-concurrency 1`,

(noise at c=1).
