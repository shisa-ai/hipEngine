# the mask ablation removed the dot as well as the loads so it never isolated traffic

## Summary

The previous entry said `--mask zero` proved the prefill attention kernel "is not
traffic-bound". **That inference was wrong.** The ablation removes the per-key dot
as well as the loads, so it cannot separate them, and a new measurement points the
other way.

## The flaw

The kernel's key loop is

```
if (mask_row[j] != 0) {
  logit = gemma4_warp_key_logit(q_s, k_row, lane);   // loads AND multiplies
  ...
} else if (lane == 0) { logits_s[j] = -INFINITY; }
```

`gemma4_warp_key_logit` both reads `k_row` and performs the 8 multiplies and the
reduction. Zeroing the mask skips the whole call, so it removes **100% of the
traffic and 100% of the arithmetic at once**. Whatever that measurement shows, it is
not a statement about traffic.

What survives from `20260928T065333`: **removing all per-key work makes the kernel
34% slower**, which is a real and surprising result. What does not survive is
attributing it to traffic, and the list of "ruled out" directions in that entry --
token-tiled flash attention, cache blocking -- was ruled out on a confounded
measurement and should be treated as open again.

## The new measurement, which points the other way

`--keys` now sets the KV length independently of the query token count, so the key
loop can be scaled without scaling the grid. `full 512d 16q/2kv window=0`,
`tokens=2048` fixed, `iters=5`:

| keys | ms/launch | GFLOP/s |
|---|---|---|
| 256 | 20.07 | 802.7 |
| 512 | 39.44 | 762.5 |
| 1024 | 82.30 | 626.4 |
| 2048 | 130.16 | 528.2 |

Work rises **4.27x** from 256 to 2048 keys (causal pairs 491,648 to 2,098,176) while
time rises **6.49x**, so the achieved rate falls from 802.7 to 528.2 GFLOP/s. Time
grows faster than work.

That is what a cache effect looks like. At `keys=256` the K tensor is 256 x 2 x 512
x 4 B = **1 MB**; at `keys=2048` it is **8.4 MB**. The small case fits a cache and
the large one does not, so the large case pays for K more than once per query token.
This is the mechanism the previous entry's hypothesis described.

**It is suggestive, not decisive.** Wave quantization, occupancy, and the mask
build cost all vary with `keys` too, and none is excluded here. The measurement
does not prove traffic either; it removes the evidence against it.

The `keys=2048` row reproduces the earlier geometry (130.16 ms / 528.2 GFLOP/s
against 130.27 / 527.8), which is the sanity check that the `pairs` fix below
changed nothing when `--keys` equals `--tokens`.

## Changes

- `scripts/gemma4_attention_prefill_bench.py`: adds `--keys`, independent of
  `--tokens`, defaulting to it. `--tokens` scales the grid and the loop together,
  so it cannot separate a cost that tracks key iterations from one that tracks
  blocks; `--keys` scales only the loop.
- The same file: **fixes the GFLOP/s column**, which computed `pairs` from `tokens`
  and `window` and ignored the key count. It reported the flops for a different
  geometry whenever `--keys` differed from `--tokens` -- the 3369.9 GFLOP/s printed
  at `keys=256` before this fix was wrong. `pairs` now uses the kept range
  `[lo, min(t + 1, key_count))`, the same range the mask encodes.

## Validation

```
for k in 256 512 1024 2048; do
  env -u ROCR_VISIBLE_DEVICES PYTHONPATH=. .venv/bin/python \
    scripts/gemma4_attention_prefill_bench.py --tokens 2048 --keys $k --iters 5
done
```

Completed; gfx1151, one device. The `keys=2048` row matches `20260928T065251`'s
independent run to 0.1%, which is the check that the flops fix is a no-op at the
geometry the earlier entries used.

## Next

1. A clean traffic ablation needs a kernel change, not a mask change: read the same
   K row for every key (stride 0) so the loop and the dot run unchanged while the
   bytes moved collapse. That separates the two, which no mask setting can.
2. Until then, token-tiled flash attention is **open again**, not ruled out.
3. Decode's block-count lever is unaffected by this and stays open
   (`20260928T065154`, ~1.72x on the attention kernel).
