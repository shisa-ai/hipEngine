# The cycle commit applies the autoregressive finish rule to a verified chain

## Summary

The cycle commit implemented one finish rule — EOS on the last visible token of a
greedy chain — so `min_tokens`, `eos_token_id`, `stop_token_ids`, and
`stop_token_sequences` had to stay off the speculative routes. It now applies the
autoregressive finish rule to the whole verified chain, selects the terminal
prefix, and reports `eos` or `stop`. The four fields are servable.

## The rule, in one place

`chain_finish_index` (`hipengine/speculative/streaming.py`) is the rule as a pure
function over a visible token list:

- **EOS** — the terminal token is the row's EOS, suppressed until the
  `min_tokens` floor. The floor is EOS suppression and nothing else, matching the
  autoregressive processor: it does not delay a stop id or a stop sequence.
- **Stop token id** — the terminal token is in `stop_token_ids`.
- **Stop sequence** — a `stop_token_sequences` entry matches at the terminal
  token, evaluated over `published_tokens + visible[:i+1]` so a sequence that
  starts before this cycle and completes inside it is caught. Without the
  published prefix the commit would publish past the stop, which is the defect
  the rule exists to prevent.

`limit_chain_accept_finish` applies it to a verified chain and returns
`(summary, ChainFinish | None)`. `ChainFinish` carries `reason`
(`"eos"`/`"stop"`), `stop_token_id`, and `stop_sequence`, so the commit publishes
the same detail the autoregressive route publishes rather than a bare reason.

The returned summary commits the prefix **before** the terminal token, keeps the
terminal token as `next_tokens`, sets `full_accept=False`, and leaves
`commit_positions` at the terminal index — so no model state is retained beyond
the prefix. `limit_chain_accept_eos` survives as the EOS-only entry point that
delegates to it, because the standalone
`Qwen35GGUFMTPVerifier.generate` loop has no request object in scope and therefore
no stop metadata to honour. It has no production callers.

## Wiring

`hipengine/generation/qwen35_gguf_mtp2.py`, the MTP2 commit path, now calls
`limit_chain_accept_finish` with the row's `stop_token_ids`,
`stop_token_sequences`, `min_tokens`, and `ignore_eos`, and passes
`published_tokens=tuple(slot.generated_ids)`. The `finish_reasons` entry is now
`chain_finish.reason` instead of a hardcoded `"eos"`, so a stop reports
`stop`.

## Blocker move

`SAMPLED_MTP_SERVABLE_BLOCKERS` gains the four finish-rule fields and
`SAMPLED_MTP_UNSERVABLE_BLOCKERS` loses them. Note which set is operative:
`sampled_speculative_mtp_blockers` filters the base blocker list by
`SAMPLED_MTP_SERVABLE_BLOCKERS`, so the servable tuple is the whitelist and the
unservable tuple is the advertised complement. Editing only the latter changes
documentation and no behaviour — which is how the first attempt at this failed.

Measured after the move:

| request | mode | unservable |
| --- | --- | --- |
| `temperature=0.7` | `sampled` | — |
| `+ stop_token_ids` | `sampled` | — |
| `+ eos_token_id` | `sampled` | — |
| `+ min_tokens` | `sampled` | — |
| `+ stop_token_sequences` | `sampled` | — |
| `+ logprobs` | `processed_argmax` | `logprobs` |
| `+ forced_tokens` | `processed_argmax` | `forced_tokens_pending` |
| `+ json_object_close` | `processed_argmax` | `json_object_close_forcing` |

The metadata and caller-override fields stay unservable, which is tasks 7 and 8.

## A defect this exposed: greedy requests mislabelled sampled

Removing the finish-rule fields from the blocker list made
`supports_sampled_speculative_mtp` true for requests whose only open fields are
finish-rule fields. Both mode decisions then fell through to their `"sampled"`
branch and labelled a `temperature=0` request sampled for a temperature it does
not have. `sampler_fast_path_blockers` is the guard that keeps the label honest,
and it is the same guard the serving-mode decision already used.

There are **two** copies of that decision — `speculative_sampling_mode` in
`hipengine/generation/sampling.py` and `_speculative_sampling_mode` in
`hipengine/generation/engine_loop.py` — and both needed it. They remain separate
implementations, which is a cleanup candidate rather than something to fix here.

  `limit_chain_accept_eos` as a delegating EOS-only entry point.

  test's own contract (`eos_token_id` still in
