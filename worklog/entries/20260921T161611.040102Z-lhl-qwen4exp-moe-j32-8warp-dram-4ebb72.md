# MoE 32-row M tile rejected: real DRAM traffic falls 6.3%, not the modeled 45%, so a taller tile buys nothing

## Summary

Supersedes the decision in `20260921T160629.891497Z-lhl-qwen4exp-moe-j32-tile-1e0d40`
(which recorded the 128-thread spilling variant and named the 8-warp block as
the next step). The 8-warp block was built, is spill-free and bit-identical, and
is still a **net loss**: the 32-row M tile for the routed-MoE main kernels is
rejected. Measured DRAM read traffic falls only 6.3% where the tile-count model
predicts 45%, because a taller tile makes the weight read *shared* between its
two row groups instead of distinct, and the sharing misses cache. Kernels run
1.3-2.2x slower than the 16-row owner.

## Why the model was wrong

The tile-count model counts *distinct* weight reads and assumes the rows sharing
a tile share the read for free. They do read the same bytes, but not inside the
cache's reuse window: warps 0-3 and 4-7 sit on different SIMD units, iterate
`sub` and `chunk` independently, and each streams the expert's whole slice
(1.2 MB for the down tensor). With 8 warps x 1.2 MB in flight per block across
16 CUs the working set is far beyond L2, so both row groups fetch from DRAM and
the tile pays the 16-row tile's traffic plus one block per CU instead of two,
taller padding (6.4x vs 3.2x at 2560 rows) and a bigger staging pass.

Register pressure was a real but separate failure: the first 128-thread version
doubled the per-lane row state (48 -> 96 registers of `sum`/`kahan_err`/
`abs_terms` plus 32 accumulator registers), hit the 256-VGPR ceiling and spilled
492 B/thread, running 4.8-8.1x slower. The 8-warp layout removed that (VGPR 208,
scratch 0) and took the loss from 8x to 1.3-2.2x, but could not remove the
traffic problem.

## Next

- Stage the K chunk's quantized weights in LDS once per block (32 KB per 128
  columns x 256 K chunk) and have all 8 warps read one copy, instead of each
  lane gathering its own column's blocks from global. That is the change that
  would actually bank the traffic reduction, and it is the prerequisite for any
  taller tile to pay. Removal trigger for the unused 32-row variants is in
  `docs/REFACTOR.md`.
- The lane-scoped prefill chunk lever (task #11) is unaffected and still the
  largest queued win; it is memory-blocked, not kernel-blocked.
