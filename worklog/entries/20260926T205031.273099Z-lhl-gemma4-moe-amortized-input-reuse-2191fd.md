# gemma4-moe-amortized-input-reuse

## Summary

The grouped Q4_K gate+up owner was reading the expert's whole input slice once
per output column. A scaling probe settled it: device time is linear in compact
rows (1.90x / 3.64x / 7.09x / 15.86x for 2x / 4x / 8x / 16x the rows), which is
what a kernel that re-walks the input per column does, and the arithmetic says
the same thing -- `out_features * rows * in_features * 2` bytes is 65 GB for one
fused gate_up call against 2.8 GB of weight traffic, about 1.5 TB/s of L2 reads
and one 2-byte input load per FMA.

Swapping the loop nest so a CTA covers four output columns and loads the input
row batch once per k-block instead of once per column took the projection from
22.2 to 8.1 ms per call and the whole prefill from 4.242 s to 3.360 s on the
W7900 lane (241.4 -> 304.8 tok/s) and from 253.0 to 319.0 tok/s on the RX 7900
XTX lane. The route stays bit-identical: `kl_max` is still exactly 0.000000 over
1023 teacher-forced rows, because the loop swap changes no output's summation
order -- a thread still owns columns `t, t+128, ...` in ascending order and the
reduction is still the same 128-thread tree per output.

Cumulative for the campaign's prefill column: 128.5 -> 319.0 tok/s (+148%),
first-token latency 7.97 -> 3.21 s, decode flat at 43.91.

## Changes

- `hipengine/kernels/hip_gfx1100/quant/gguf_q4_k_selected_prefill.hip`: the
  grouped rowbatch dual kernel takes a fifth template argument,
  `AMORTIZE_INPUT`. When set, the row batch is the outer loop and the output
  columns the inner one, so the input values for a row batch are loaded once per
  k-block and reused across `OUT_BATCH` columns; the block metadata slab becomes
  `OUT_BATCH` wide and is still preloaded once per CTA. The default is false, so
  every existing instantiation -- including the ones the Qwen MoE paths use --
  compiles to the same code as before. A new launcher
  `hipengine_gguf_q4_k_selected_dual_grouped_rowbatch8_out4_amortized_bundle_bf16_bf16_out`
  instantiates `<8, 4, true, true, true>` with the fused stride arguments.
- `hipengine/kernels/hip_gfx1100/quant/gguf_q4_k_selected_prefill.py`: wrapper
  and registry entry for
  `selected_dual_grouped_rowbatch8_out4_amortized_bf16_bf16_out`, with the same
  stride keywords as the row-batch variant and an explicit `in_features <= 4096`
  guard, the widest input whose block metadata fits the shared slab.
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_experts.py`:
  `gemma4_project_experts_grouped_dual` now probes the amortized variant first
  and falls back to the row-batch variant, then to the selected GEMV. Both
  variants take the same arguments, so the call site is unchanged.
- `tests/test_gpu_gguf_q4_k_selected_wmma_prefill.py`: the fused-stride test also
  runs the amortized owner and asserts its bits equal the row-batch owner's.

## Measurement

| W7900 lane, 1024 prompt tokens, 60 layer calls, default route | before ms | after ms |
| --- | ---: | ---: |
| fused gate_up (grouped dual) | 1452 | 471 |
| Q5_1 down (grouped) | 1101 | 1130 |
| attention prefill | 901 | 905 |
| dense Q8_0 | 575 | 552 |
| layer-29 MoE (selected) | 201 | 201 |
| **layer total** | **4242** | **3348** |

Isolated projection timings on the same artifact, 128 experts, 8192 compact
rows, five repeats after two warmups:

| route | ms |
| --- | ---: |
| row-batch owner (`<8, 1>`) | 44.3 |
| amortized `<8, 4>` | 15.8 |
| amortized `<4, 8>` | 21.8 |

The `<4, 8>` shape halves the input traffic again but doubles the weight passes
and drops occupancy from 8 to 6 waves per SIMD, so it loses. Register pressure
is the binding constraint on going wider: `<8, 4>` compiles to 173 VGPRs with no
spills at 8 waves per SIMD, `<4, 8>` to 230 at 6.

## Validation

Teacher-forced gate, default route, prompt 2048 with prefill 1024, 1023 scored
rows against `/mnt/nvme1/gemma4-eval/teacher-forced-prefilled-strict-001c4fec3.npz`:
`kl_max` 0.000000, `kl_mean` 0.0, top-1 rate 1.0, zero flips, pass. The route is
bit-identical to the strict reference, so no promotion gate applies.

Campaign bench, RX 7900 XTX, 1024 prompt / 128 output, three samples after one
full-shape warmup, public `LLM.generate` path: prefill 3.21 s (319 tok/s), first
token 3.21 s, decode 43.9149 tok/s, wall 6.10 s, `public_path_parity` true.

Tests: the GPU Q4_K prefill suite (including the fused-stride bit-equality test
that now covers the amortized owner), the Q5_1 selected suite, and the Gemma 4
MoE-routing unit suite all pass.

## Next

The Q5_1 down projection is now the largest item at 1130 ms (33.7%) and its
owner (`q5_1_selected_grouped_prefill_bf16_bf16_kernel`) has the identical
structure -- output column outer, row batch inner, input re-read per column --
so the same swap should apply. It differs in three ways that matter: 256 threads
with a stride-128 to 1 LDS tree instead of a shuffle tree, a `SHARED_METADATA`
option whose slabs are per output row, and a `partial` scratch sized
`ROW_BATCH * blockDim.x`. Amortizing four output columns needs that scratch at
`OUT_BATCH * ROW_BATCH * blockDim.x` (32 KB at `<8, 4>`), which fits the 64 KB
limit. After that, attention prefill is 905 ms (27.0%) and the 410 dense Q8_0
linears are 552 ms (16.5%); neither has an amortized or tiled owner wired for
this model.
