# Router token-tile equivalence: both variants match float64, so V1's failure is a promotion question

## Summary

Iteration 35 isolated `74fb74ffe` ("select the Gemma 4 router logits kernel by
token count") as the first commit where the 4096 gate fails, with `d0f5b1ff6`
modulating it. The open question was whether one of the two router kernels is
defective or whether they are merely differently rounded.

**They are equivalent.** `tests/test_gpu_gemma4_router_variant_selection.py`
runs both at the production shape (512 tokens x 2816 hidden -> 128 experts,
top-8) and reports:

```
tokens where base != tiled : 0/512
base   vs float64 reference: 0/512
tiled  vs float64 reference: 0/512
max |tiled - base| logits  : 3.815e-06
```

The logit difference reproduces the 3.81e-06 the commit itself reports, both
kernels match a float64 yardstick on every token, and no selection ever moves.
A second test confirms selection is reproducible run to run.

So the working hypothesis from iteration 35 -- that a near-tie in the router's
top-k flips an expert and amplifies -- is **not** supported on random
production-shape inputs. What remains is simpler and does not involve routing
at all: two correct kernels whose reductions differ in the low-order bits
produce slightly different routing weights, and those differences compound
through 8 prefill blocks and 30 layers into a large KL at two positions.

## Why this is a promotion question, not a bug fix

There is no defect to repair. Both variants are as accurate as each other
against float64, so "fixing" the tiled kernel means nothing -- the difference
is inherent to tiling and thread width, which is exactly what the commit's own
comment says ("Neither choice is bit-identical to what it replaces: the tiling
and the width both change the reduction").

That makes `74fb74ffe` a **changed-arithmetic kernel path on the default
path**, which under `AGENTS.md` and `docs/EXECUTION-PROFILES.md` requires its
execution-profile gate to promote. The complication is that it *had* one:

- `benchmarks/results/2026-09-28-gemma4-26b-a4b-router-token-tile-gate.json`
  records `passed: true`, 1023 rows, 0 flips, `kl_max` 1.30e-03 -- but its
  `baseline_path` is `~/.cache/hipengine/tmp/gate_base_mmq.npz` at
  `prefill: 1024`, a temporary baseline rather than the frozen p4096 one.
- The frozen p4096 baseline did not exist as a *gated* configuration for any
  candidate, which is precisely V1's stated gap: "no gate has ever exercised a
  prefill block with `keys > 1024`".

The change therefore passed the gate regime in force when it landed and fails
the extended one. At `--prefill 4096` it reaches `kl_max` 0.224071 against a
0.05 production limit, on 2 of 1023 rows, with 0 top-1 flips and
`kl_mean`/`kl_p95`/`kl_p99` all comfortably passing.

## The options, and why this entry does not pick one

1. **Revert the prefill-side selection** (`_TOKEN_TILE_16_MIN_TOKENS`), which
   restores gate parity and gives up the measured win: router_gemm
   53.2 -> 28.4 ms at 4096, `token_tile_16` 2.35x on its own, prefill +0.56%.
2. **Record acceptance** of the 4096 deviation with the gate artifact attached.
3. **Re-derive a baseline** if the production reference is judged to be the
   post-router tree rather than `c3ea386af` -- but that moves the yardstick to
   accommodate the change, which is the anti-gaming pattern
   `docs/OPTIMIZATION.md` exists to prevent.

Options 1 and 2 are opposite product calls on a landed, measured, gate-passing
performance commit, and option 3 is the one that must not be taken casually.
Under `AGENTS.md` "Decision Authority" that is the human lead's call, so this
entry states the evidence and stops rather than picking.
