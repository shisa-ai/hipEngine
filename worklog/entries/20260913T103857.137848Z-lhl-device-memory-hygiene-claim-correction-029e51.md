# Device-memory hygiene claims corrected: use-after-free, not DMA timing

## Summary

Review of `e764d0903` + `2d3c8c3cd` found that the sweep's *claims* outran its
evidence in three places and that a committed test imported an untracked helper.
This entry is the correction. The reviewer's central mechanism objection is
right and is now measured, not argued: an inline H2D source is a **use-after-free
at call time**, not a transfer that outlives `hipMemcpy`.

Two measurements settle it (`tests/test_h2d_source_lifetime.py`):

- **The temporary is dead before the copy is entered.** Instrumenting the
  pointer helper shows `alive at call entry: [False]`; CPython drops the last
  reference when `host_array_ptr` returns. The freed 4096-byte block is handed
  straight back to the next same-size allocation at the same address
  (`0x55a3595bc370` both times), so the copy reads the new owner's bytes.
- **The transfer is complete when the copy returns.** Overwriting the source in
  place immediately after `copy_host_to_device` returns leaves the destination
  100% original at 1, 16, 64, and 128 MiB on gfx1151. A named local is therefore
  sufficient on its own, and a per-call `device_synchronize()` buys nothing for
  source lifetime.

So the "DMA reads the host buffer after `hipMemcpy` returns" story that
`SuryaGpuRunner._upload` and `docs/KERNELS.md` carried is wrong. It is corrected
in both, plus the comments it was copied into.

## Changes

**Corrected claims and the code they justified:**

- `hipengine/runtime/surya.py::_upload` -- docstring now states the
  use-after-free mechanism; the `device_synchronize` is described as defensive
  (load-time path, future async variant), not as the fix. No behaviour change.
- `docs/KERNELS.md` "Device-memory hygiene" -- the third bullet is split in two:
  bind the source because the pointer is a bare address; the transfer is
  complete on return so a named local needs no synchronization. Includes the
  measurement and the "do not add one to a decode loop" consequence.
- `hipengine/runtime/timesfm_decode.py`, `timesfm3_decode.py` -- the per-call
  `device_synchronize()` added in `e764d0903` is **removed**. It was a
  device-wide queue stall on the decode path justified only by the disproven
  claim; the named locals it was protecting are alive through their copies.
- `hipengine/runtime/evie.py`, `qwen35_gguf_runner.py`, and the touched tests and
  scripts -- same comment correction. Evie's sync is kept and labelled
  defensive (cache-miss path); `qwen35_gguf_runner`'s is on a setup path.

**Committed the missing dependency (the reviewer's blocker):**

- `tests/_poison_probe.py` was untracked while four committed test files imported
  it, so a clean checkout could not collect them. It is now committed, with
  `tests/test_poison_probe_helper.py` -- 10 unit tests over `collect_device_buffers`
  (walks dataclasses/sequences/mappings, skips weights-runtime-tokenizer, reports
  an arena through its owner, honours `max_depth`, terminates on a cycle),
  `group_by_prefix` (index-stripped bucketing), `poison` (skips empty buffers,
  counts bytes, synchronizes once), and `assert_poison_invariant` (clean verdict,
  offender naming, non-finite detection). All of it runs without a GPU:
  `DeviceBuffer` is a `(ptr, nbytes)` dataclass and the only runtime capability
  used is `memset` + `device_synchronize`, which a fake records.

**New tests for the mechanism (`tests/test_h2d_source_lifetime.py`):**

- `test_inline_temporary_is_dead_before_the_copy_is_entered` (the load-bearing
  assertion), `test_the_freed_block_is_available_to_the_next_allocation`,
  `test_a_named_local_is_alive_for_the_whole_call`,
  `test_transfer_is_complete_when_the_copy_returns` (GPU-gated, 1/16/64/128 MiB),
  and `test_host_array_ptr_is_just_the_data_address`.
- The demonstration deliberately allocates through a factory function, which is
  also the honest illustration of a limit: a source-level lint cannot see
  `host_array_ptr(_fresh())`.

**Lint documented as partial, with its gaps pinned:**

- `tests/test_device_memory_hygiene.py` now states in its module docstring that
  it is a partial lint and lists what it misses:
  `host_array_ptr(np.zeros(n).reshape(2, -1))` (the allocation is inside the outer
  call), `host_array_ptr(np.ascontiguousarray(x))` (copies only for a
  non-contiguous `x`; ~100 call sites are safe as written), and it explains that
  `np.asarray` stays flagged as a **deliberate over-flag** because it returns its
  argument when the dtype matches and binding to a local is correct either way.
  `test_the_lint_is_documented_as_partial_and_its_gaps_are_pinned` fails if a
  documented gap is silently closed.
- `docs/REFACTOR.md`: the old "hoist without synchronizing" entry is replaced by
  the reviewer's structural fix -- an upload API that retains the array owner
  (`upload_host_array(buffer, array)`) so the hazard cannot be expressed at all,
  with `copy_host_to_device` kept only for genuine raw addresses.

## Reclassified claims (what the evidence does not establish)

- **TimesFM 3.0 `q_offset` is not a proven read-before-write.** It is a
  constant-zero attention input, initialized when its buffer is allocated and
  never invalidated by any execution path. Poisoning it deliberately corrupts
  initialized data, and the probe's own rule excludes once-uploaded metadata for
  exactly that reason. The per-call `_zero_q_offset` is kept as *defensive
  reinitialization* -- cheap, and it removes the dependence on the allocator --
  but `e764d0903`'s "real read-before-write, not a latent-style nit" is withdrawn
  for this site.
- **TimesFM 2.5 is a credible hazard, not a demonstrated production failure.**
  The mechanism is sound and the reviewer's framing is the right one: a still-owned,
  initialized allocation is not corrupted by recycling. The plausible path is that
  a *slot written non-finite by an earlier request on the same shape* (non-finite
  input data, or an fp16 overflow) is read by a later request with a zero weight,
  and `0 * NaN == NaN` contaminates the GEMM. Nothing has demonstrated that
  transition yet, so the per-call `_zero_caches` is retained as a guard and the
  poison probe is described as a *stronger-than-production* guard rather than as
  proof. Required evidence, recorded below.
- **Evie's RED test proves cache reuse, not source-lifetime correctness.** The
  upload-on-miss change is real and removes one H2D per batched GEMM call; the
  `assert 3 == 2` assertion pins the cache behaviour. Source lifetime now has its
  own test in `tests/test_h2d_source_lifetime.py`, which is where the
  synchronization question is answered (it is not needed).

  output. If it fails on the pre-`e764d0903` code, the V-cache fix is a proven
  repair and the entry's original claim can be restored; if it passes, the fix is
  a guard and should be described that way.
