# EVIE-8B port: single-head variant + merger geometry fix

## Summary

Port of tencent/EVIE-8B (single-head 4096-d variant) onto the 4.5B
runtime; reviewer-found merger geometry bug fixed; fp32 parity gates
pass at the 4.5B class; fp16 documented as a weaker tier.

## Context

EVIE-4.5B batched encode campaign (d1cf71dbf, 2e2e69150) landed; the
8B sibling checkpoint (`tencent/EVIE-8B`, local HF cache) is
architecturally identical except for geometry and the head, so we
ported it before merging the evie branch to main.

## Changes

- `hipengine/models/evie.py`: spec parsing handles the non-MRL
  single-head configs (8B has no `head_dims`; `custom_text_proj` =
  Linear(4096, 4096), full 4096-d embeddings, `default_head = dim`);
  per-variant expected-dims tables (4.5B / 8B).

## Merger geometry bug (reviewer-found, fixed here)

The reviewer (a1b61b82c) caught that my first parameterization pass
set the merger fc1 output width to `vision_intermediate_size` (the
vision block MLP width, 4304 for 8B). The checkpoint's merger fc1 is
square — (4608, 4608) for 8B, (4096, 4096) for 4.5B — i.e. width
`merge^2 * vh`, which coincides with `vision_intermediate_size` only
on 4.5B (4096 = 4*1024 = the block MLP width). FC2 then read row
boundaries FC1 never wrote. Fix: fc1 width = `merge * merge * vh` for
in and out; `merged_in` scratch resized to match. Their regression
test (4.5B pass / 8B fail pre-fix) now passes both.

Important process note: I had misdiagnosed the resulting divergence
as inherent fp32 ill-conditioning of the 8B vision tower (f64-vs-fp32
CPU runs differ by ~16 in visual features; torch bf16-vs-fp32 doc cos
min 0.36; random-perturbation gain ~10^3). Those measurements are real
but describe noise floors far above the 2e-4 parity scale — they do
not excuse a geometry bug, and fp16/fp32 self-consistency can preserve
a shared bug. Elementwise parity was attainable all along.

## Validation

- fp32 strict parity vs torch fp32 oracle: query max|d| 6.2e-7;
  doc max|d| 1.3e-4 (mean 2.2e-6); visual features max 6.1e-3;
  maxsim 3.5190 vs oracle 3.5194.
- fp16: query cos ~1.0; doc cos mean ~0.99 but min ~0.5 on a few
  tokens — the 8B vision tower amplifies fp16 activation-storage noise
  (unlike 4.5B). rocBLAS f16 GEMM output also varies slightly across
  process loads (address-dependent split-k accumulation); within a
  process, encode is deterministic. fp32 is the recommended precision
  for 8B; the fp16 test gates at doc cos mean >= 0.98 + determinism.
- Tests: 26 GPU (4.5B strict/batched/fp16/lifetime/ownership + 8B +
  merger contract) and 13 CPU/contract, all green at commit a1b61b82cdd96dcf2e38d75ceac55e15b868649c.

## Decisions

- 8B gates mirror 4.5B's fp32 parity class (atol 2e-4); fp16 is a
  separate, weaker tier with the model's amplification documented in
  the test docstring. No benchmark claims for 8B yet (bench harness
  still pins 4.5B; extending it is follow-up work).
