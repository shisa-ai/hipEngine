# MoE 32-row M tile: weight traffic halves exactly, but 492B/thread spills make it 8x slower

## Summary

Both routed-MoE main kernels were templated to a 32-row M tile and measured: the
weight-traffic prediction holds exactly (tile count falls 1.67-1.82x) but the
kernels run 4.8-8.1x slower because the per-lane fp32 risk state doubles past
the 256-VGPR ceiling (492 B/thread spilled). The 16-row tile stays production;
the exact-but-slower variants are registered, tested, and unused.

- `hipengine/kernels/hip_gfx1100/quant/gguf_q4_k_selected_prefill.hip`,
  `hipengine/kernels/hip_gfx1100/quant/qwen4_exp_q5_1.hip`: `template <int
  TILE_ROWS = 16>` on the gate/up and down kernels and launchers; new 32-row C

- `rocprofv3 --kernel-trace` on the packet: `kernel<16>` VGPR 192 / scratch 0;

## Next

- 32-row tile as an 8-warp (256-thread) block with two row groups x four column
  groups, so the register geometry stays at 16 rows per lane and the two row
  groups share one weight read through L2. See `docs/REFACTOR.md`.
## Question

The MoE main kernels (`gate/up` q4_k and `down` q5_1, both iu8 WMMA) read expert
weights at a flat 104-126 GB/s independent of row count. Their weight traffic is
`Σ ceil(rows_per_expert / TILE_ROWS) × tensor_bytes`, so the per-expert M tile
height sets the read amplification. A 32-row tile should halve the reads
whenever an expert holds 16 or fewer rows per tile.

## What was built

Both kernels are now templated on `TILE_ROWS` and expose a 32-row entry point
alongside the 16-row owner:

- `hipengine/kernels/hip_gfx1100/quant/gguf_q4_k_selected_prefill.hip` and
  `.../qwen4_exp_q5_1.hip`: `template <int TILE_ROWS = 16>` on the kernels and
  their launchers, plus
  `hipengine_qwen4_exp_q5_1_selected_wmma_iu8_risk_j32_prefill_bf16_bf16_out`
  and the q4_k equivalent.
- Python wrappers share one validated body
  (`_q5_1_iu8_risk_prefill` / the q4_k counterpart); registry keys
  `selected_wmma_iu8_risk_j32_prefill_bf16_bf16_out` under
  `("hip_gfx1100", "moe_linear", "gguf_q5_1")` and the q4_k key.
- `scripts/qwen4exp_moe_main_kernel_cost.py --tile-rows` drives both tile

## Result: the traffic model is right, the speed model is wrong by 8x

Measured on gfx1151, 512 experts, 2560 hidden, 640 ffn, median of 15 launches:

| rows | dist | tiles 16→32 | gate ms 16→32 | down ms 16→32 | gate GB/s 16→32 |
| --- | --- | --- | --- | --- | --- |
| 2560 | balanced | 512 → 512 | 8.72 → 70.45 | 5.63 → 50.67 | 108.2 → 13.4 |
| 10240 | balanced | 857 → 512 | 14.80 → 71.94 | 8.93 → 51.71 | 106.7 → 13.1 |
| 40960 | balanced | 2801 → 1536 | 45.27 → 200.94 | 27.33 → 148.21 | 114.1 → 14.1 |
| 10240 | uniform | 1024 → 512 | 17.22 → 71.73 | 10.21 → 51.89 | 109.6 → 13.2 |
| 40960 | uniform | 2560 → 1536 | 41.70 → 200.14 | 25.26 → 147.89 | 113.2 → 14.2 |

Tile counts drop exactly as predicted (1.67x at 20 rows/expert, 1.82x at 80),
but time rises 4.8-8.1x and achieved bandwidth collapses to ~13 GB/s.

## Mechanism (rocprofv3 --kernel-trace, same geometry)

| kernel | VGPR | Scratch | LDS/block |
| --- | --- | --- | --- |
| `q5_1_..._risk_prefill_kernel<16>` | 192 | 0 | 16 KB |
| `q5_1_..._risk_prefill_kernel<32>` | 256 (arch max) | 492 B | 32 KB |

Per-lane row state is 3 floats per (row, column) pair and each lane owns
`TILE_ROWS / 8 × 8` rows: 48 registers at 16 rows, 96 at 32, plus 32
accumulator registers (`acc[4 planes][8]`). `__launch_bounds__(128, 2)` already
lets the compiler spend the whole CU register file (2 x 128 x 256 = 65536) and
it still spills 492 bytes per thread, so the true demand is above the 256-VGPR
architectural ceiling. The spills sit in the K loop, so the kernel becomes bound
by its own spill traffic rather than by weights.

## Correctness

- `tests/test_gpu_qwen4exp_q4_iu8_j32_tile.py`: 18 passed on gfx1151. Bit
  identity against the 16-row owner for both kernels across six expert-count
  shapes and two risk multipliers, identical risk queues, registry binding, and
  a chain test that runs the sparse exact repair after a 32-row tile.
- The packet's first run caught a genuine bug in the widened down kernel: the
  `lds_row_atrisk` clear guard was still `tid < 16`, so entries 16-31 were
  uninitialized shared memory. Outputs stayed bit-identical (the flag only gates
  the risk queue) but the queue grew 106 → 14522 entries. Parameterized to
  `tid < TILE_ROWS`; the RED test now covers this case, and the gate/up kernel
  already had the correct guard.

## Decision

The 32-row tile is a **measured dead end at 128 threads / 32 columns per warp**
and is not wired into any dispatch default. The 16-row tile stays production.
The registered 32-row variants are kept because they are exact and tested, and
they are the substrate for the only viable redesign: an 8-warp (256-thread)
block covering 32 rows x 128 columns as two row groups x four column groups, so
two warps share one weight read through L2 while each warp keeps the current
16-row register footprint. `docs/REFACTOR.md` carries that plan and the
condition for removing the unused variants.
