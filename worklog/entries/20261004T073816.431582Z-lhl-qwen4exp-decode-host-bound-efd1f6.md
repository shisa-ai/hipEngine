# Decode is host-bound: the GPU drains every step before the host finishes enqueuing

## Summary

The decode gap to llama.cpp is a **host-side** problem, not a kernel problem.
Two experiments locate it and one direct probe measures it.

1. **The 17% decode fall from p512 to p4096 is real and not thermal.** Reversing
   the measurement order after a 300-second idle - `code-p4096` first from a cold
   42 °C, then `code-p512` from 46 °C - gives **17.55 / 17.75 / 17.84** and
   **21.01 / 21.01 / 21.02**. Order does not matter.
2. **It is not device work.** Profiling the canonical bench's own decode loop
   shows total kernel time of **46.19 ms/step at p512 and 47.13 ms/step at
   p4096 - +2.0%** - where the unprofiled rate falls 17%.
3. **It is host enqueue cost, and the GPU is idle throughout.** A new probe
   separates host enqueue time from device drain time and finds
   **`device_drain_ms = 0.0` at every depth**: the GPU completed all 128 queued
   steps before the host finished enqueuing them. Host cost is flat at 79-80
   ms/step through 1024 and jumps **+36%** at 4096.

**No kernel, default, flag or dispatch changed.** One diagnostic script was
added.

## Changes

### New script

`scripts/qwen4exp_decode_host_bound_probe.py` - runs the canonical bench's
decode loop but splits it into (a) host enqueue time with a single synchronize
at the end and (b) the device drain after that synchronize, then repeats the
loop with a synchronize after every step. `device_drain_ms` near zero means the
loop was host-bound for its entire length. It is a diagnostic and says so: it
runs two 128-step loops on one growing sequence, so its absolute rates are not
comparable with the canonical bench.

### The device does not explain it

`rocprofv3 --kernel-trace` over
`qwen4exp_canonical_ar_bench.py hipengine --case-id <case> --warmups 1
--repetitions 1`, one case per process, isolating the 128-step decode window:

| family | p512 | p4096 |
| --- | ---: | ---: |
| `qwen35_paged_full_attn_decode_context` | **252.7 ms** | 0 |
| `qsa_sparse_attention_paged_bf16_ordered_*` (3 variants) | 0 | 257.4 ms |
| `qsa_topk_expand_f32_i64_kernel` + `qsa_score_f32_kernel` | 0 | 62.8 ms |
| `gguf_k_pack8_prefill_out_kernel` | 3015.8 ms | 3028.2 ms (+0.4%) |
| **total kernel per step** | **46.19 ms** | **47.13 ms (+2.0%)** |
| launches per step | 1729 | 1811 |

**The decode path switches kernels between these depths.** Below the switch it
uses dense `qwen35_paged_full_attn_decode_context`; above it uses QSA sparse
attention plus a top-k expansion. Attention rises **252.7 -> 320.1 ms (+27%)**,
but attention is only **4-5%** of a decode step while `gguf_k_pack8_prefill_out_kernel`
is **50%** of it and flat. The total moves +2.0% where the rate moves -17%.

### The host explains it

`scripts/qwen4exp_decode_host_bound_probe.py`, production profile,
`--require-cached-build`:

| case | host enqueue / step | device drain | host-bound |
| --- | ---: | ---: | --- |
| code-p512 | 79.121 ms | **0.0 ms** | yes |
| code-p1024 | 80.063 ms | **0.0 ms** | yes |
| code-p4096 | **107.444 ms** | **0.0 ms** | yes |

Host cost growth 512 -> 4096: **1.358x**. The curve is flat through 1024
(79.1 -> 80.1) and then steps up at 4096, **coinciding with the dense-to-QSA
path switch the kernel trace shows.**

`device_drain_ms = 0.0` is the load-bearing number: after the host has enqueued
all 128 steps, `device_synchronize()` returns immediately, so the device had
already finished. At 46 ms of device work per step against 79 ms of host work
per step, the GPU is idle for the whole loop.

## Validation

- **Order-reversed cold-start test**: 300-second idle, then `code-p4096`
  (start 42 °C, the coldest achievable) and `code-p512` (start 46 °C), each
  with 1 warmup and 3 repetitions, fresh process per case. This rules out both
  the thermal trajectory and the measurement order.
- **Profiled decode windows**: one case per process, `--warmups 1
  --repetitions 1`, phases separated by launch-rate buckets in the trace; only
  the p512 window is compared against the p4096 window, never a profiled
  absolute against an unprofiled one.
- **Host/device probe**: run once end to end, all three cases in one process,
  `--require-cached-build`, artifact JSON and log under
  `benchmarks/results/2026-10-04-qwen4exp-thermal-protocol-and-llamacpp-basis/`.
- The `device_drain_ms = 0.0` result is reproduced identically by the throwaway
  version of the probe that preceded the committed script (two independent
  runs, same three cases, same conclusion).

## Limits

- **The probe's absolute rates do not match the canonical bench's.** The probe
  reports 12.6 / 12.5 / 9.3 tok/s where the bench reports 21.01 / 19.40 /
  17.40 for what should be the same loop, and the ratio is not constant (1.66 /
  1.55 / 1.87). The probe runs two 128-step loops on one growing sequence plus
  8 warm steps, so it is not the same loop - but the discrepancy is **not
  explained**, and the canonical bench's absolute decode rate is therefore not
  independently reproduced. The host-vs-device split and the +36% growth are
  measured within the probe and are unaffected by this; the absolute rates are
  not comparable across the two.
- One host (`gfx1151`), one model file, one quant, one execution profile, one
  category. Three depths, not a curve.
- The +36% host jump is **correlated** with the dense-to-QSA path switch, not
  proven to be caused by it. The probe and the trace are separate runs.
- `device_drain_ms` is measured with `device_synchronize()`, which is a full
  device barrier; the number is sound but does not say *where* in the host path
  the time goes. No host profile was taken.
- The ~1729 launches per step are counted from the trace, which was taken under
  the profiler; launch counts are not inflated by profiling but were not
  cross-checked unprofiled.

## Next

- **Find where the ~79 ms/step of host time goes.** No host profile has been
  taken. That is the single highest-value next step, because decode is entirely
  host-bound and the gap to llama.cpp is 0.80-0.96x.
- **Confirm the +36% jump is the QSA path switch** by forcing one path at both
  depths and re-measuring host cost.
- **Reconcile the probe's absolute rate with the bench's.** Until they agree,
  the campaign's headline decode numbers have an unexplained calibration.
- Fix the `--max-sequence-length` default in `qwen4exp_profile_gap.py --mode
  decode`, which silently sizes the KV cache to 128 for any `--prompt-file`.
