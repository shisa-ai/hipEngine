# Gemma 4 routed-expert prefill reuses each expert's weights

## Summary

Gemma 4 prefill on gfx1151 spent 84.8% of its kernel time in two expert
projections that each launched one block per (out_col, lane) and therefore
re-read the whole expert weight matrix once per lane. A prefill block now
projects its compact rows through a registered grouped-prefill family when the
weight's quant key declares one: one launch per (expert, out_col) that reads the
expert's weight row once and reuses it across that expert's rows.

On the real `UD-Q4_K_XL` artifact that is **39.82 -> 48.57 prefill tok/s at 2048
prompt (+22.0%, 1.220x)**, public wall 51.957 -> 43.503 s, with decode and the
generated token ids unchanged. The route is **bit-exact**, so it consumes no
numerical budget: a 1023-row teacher-forced gate against the frozen strict
baseline reports KL exactly 0.0 at mean/p95/p99/max with 100% top-1.

That pair is the tightest provenance available here: both arms ran on the final
tree in one session, back to back, and the harness's own record shows the file
under test dirty in the candidate arm and clean in the incumbent arm. An earlier
pair, taken before this change's final refactor, agrees at 39.69 -> 48.99
tok/s.

The larger candidate that this was split out of - routing the Q4_K gate/up
through the per-expert WMMA row-slice prefill as well - measures **2.807x**
prefill (111.43 tok/s) on the temporary candidate tree it was evaluated in, but
breaches the binding production `kl_max` bar (0.167959 against 0.05 on 2 of 1023
rows) and is recorded as rejected rather than shipped. It carries 70% of the
available saving, because the Q4_K gate/up is 53.4% of prefill kernel time and
has no bit-exact grouped family in this tree. The candidate path was removed
rather than left behind a switch.

## Changes

- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_experts.py`:
  - `gemma4_project_experts_grouped_prefill()` resolves
    `moe_linear/<quant>/selected_grouped_prefill_compact_rowbatch8_bf16_bf16_out`
    from the registry and launches it, or returns `False` when the weight's
    quant key registers no such family. A bf16 weight is a bare pointer with no
    quant key and always returns `False`.
  - `gemma4_project_experts_rows()` applies the preference order for one
    projection - grouped family, then per-row selected GEMV, then the per-expert
    offset path - and returns the route that ran. `gemma4_experts_forward_bf16`
    calls it once per projection and records the route.
  - `gemma4_moe_prefill_route_enabled()` holds the crossover at one compact lane
    per expert: below it most experts are empty and the grouped launch's
    per-expert grid would spend its blocks on nothing.
  - `gemma4_moe_expert_route_counts()` exposes the route counters.
- `tests/test_unit_gemma4_expert_route.py` (new): route selection across the
  crossover and at values unrelated to it, the fallback order, the route
  diagnostic, the grouped kernel against a dequantized Q5_1 reference with an
  empty expert in the middle of the list, and grouped-versus-selected
  bit-exactness at five geometries.
- `scripts/gemma4_kl_row_report.py` (new): per-row KL with both distributions at
  each breaching row. The gate reports the distribution but not the rows, and
  diagnosing a single-row `kl_max` breach needed the rows.

admissible by argument.

## Next

The remaining prefill win needs a **single-output, weight-reusing Q4_K expert
prefill kernel** whose per-row reduction reproduces
`gguf_q4_k_selected_prefill_out_kernel`'s association. That kernel accumulates
`k = threadIdx.x, threadIdx.x + blockDim.x, ...` and reduces with
`reduce_block_sum()` - a 32-lane shfl tree per wave, then a sequential sum of
the wave totals by thread 0 - and is the only reason the Q4_K gate/up cannot
use the grouped route. A row-reusing kernel that keeps that exact reduction and
walks the expert's rows inside the block would be bit-exact the way the Q5_1
grouped family already is, and would move the remaining 53.4% of prefill kernel
time (70% of the available saving) onto the same free footing. The measured
target is `benchmarks/results/2026-09-27-gemma4-moe-prefill-wmma-rowslice-rejected.json`.

Secondary: the 512-token and 4096-token prompt rows, and a same-artifact
llama.cpp prefill comparator on this host, are unmeasured for this change.
