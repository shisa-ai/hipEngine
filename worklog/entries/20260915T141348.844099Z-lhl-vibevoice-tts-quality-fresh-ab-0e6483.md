# Fresh-synthesis quality re-measurement: the semantic GEMV dispatch regressed quality and was reverted

## Summary

Two things were wrong with the quality evidence this branch had been carrying, and
fixing both changed a decision.

1. The 17/18 claim came from `--phase score`, which re-scores `work/synthesis.json`
   without re-synthesizing. It had measured audio produced by **pre-change code**,
   so it said nothing about the decoder or semantic arithmetic changes.
2. The speaker gate compared only the first and last confidently classified
   windows, so a lost intermediate speaker change would pass.

Re-running synthesis **and** scoring on the kept revision gives **18 of 18
request-runs passing**, with `two-2turn` clean on all three seeds. The same sweep
also showed that a second speed change — routing the semantic encoder's `rows=1`
GEMMs to the per-output GEMV, worth 2.2x on that stage — **degrades generated-audio
quality**, so it was reverted.

## The A/B

Three full suites, same seeds, same requests, same suite code. Only the two
dispatch thresholds differ. `two-2turn` is the shortest two-speaker script and the
one that moves.

| variant | request-runs passed | `two-2turn` WER (seeds 15/16/17) |
| --- | ---: | --- |
| original (neither change) | 16/18 | 0.353 FAIL, 0.059, 0.059 |
| **decoder FFN GEMM, semantic reverted** | **18/18 on gates** | 0.0, 0.059, 0.0 |
| decoder FFN GEMM + semantic rows=1 GEMV | 15/18 | 0.0, 0.118 FAIL, **0.647 FAIL** |

The third row's seed-20260917 failure is severe and does not appear in either other
variant: 11.73 s of audio against a 7.33 s expectation, five repeated 4-grams, and
a speaker-run sequence of `[0,1,0,1]` for a two-turn script. The other two variants
top out at WER 0.353.

So the decoder's batched FFN GEMM is the best of the three variants on this sweep
and the semantic dispatch is the harmful one. The semantic change is reverted;
`hipengine/kernels/hip_gfx1100/vibevoice/registered.py` is back to its committed
state.

This is a three-seed sample of a request that is known to be chaotic, so it is not
a tight statistical statement. It is enough to reject the semantic dispatch, which
is the direction that matters: a change that introduces the only runaway
generation in the sweep does not get to stay on a speed argument.

## The speaker gate was strengthened, and the control that tests it fails

`_checks` now compares the encoder's whole **run sequence** to the script's, not
just its endpoints. The four-turn script reproduces `[0,1,0,1]` on all three seeds,
so the intermediate speaker changes are covered.

The reviewer asked for a non-vacuous single-voice control: classify single-speaker
audio against **both** reference voices rather than against its own sole reference.
That control was added, and it does not support a gate:

- `single-numbers` seed 20260916: mean cosines 0.4236 against 0.4125, a margin of
  0.011, and the three decided windows split `[0,1,0]`.
- `single-medium` seed 20260917: **every** window is assigned to the voice the
  request was not conditioned on (0.2561 against 0.3826).

So the instrument resolves speaker *changes* inside an utterance that contains both
voices, but not absolute voice identity for single-voice audio. Identity is now
recorded per request as `attribution_identity_control` and is **not** gated, and
both the artifact's `attribution_instrument` block and
`benchmarks/prompts/vibevoice-tts-quality.json`'s limitations say so. The earlier
claim in this branch that all nine single-speaker runs assigned every window to
their own reference was measured on stale audio and does not hold.

The instrument is deterministic (`encode_reference` does not sample the VAE), so
these are not draw-to-draw differences.

## The benchmark harness

`scripts/vibevoice_tts_session_bench.py`:

- The generation budget is now the request's declared `max_audio_seconds` (the
  recorded duration plus one second; 4.333 s, a 35-token cap) instead of the
  oracle's 27-token answer. Sizing a budget from the answer under test makes
  truncation unobservable. The run reaches EOS at 27 tokens under the declared cap,
  and `finish_reason` plus `timed_finish_reasons` are reported.
- The reported cold start is now the first synthesis after load, measured before
  the traced correctness run. It was previously a warm synthesis carrying a cold
  label.

Still open: the two lanes draw **different random operands**. The fork's stochastic
inputs are one `torch.randn(batch_size)` and one `torch.randn_like(mean)` for the
voice-prompt VAE plus one `torch.randn(2, 64)` per diffusion frame, all of which the
fixture already records (`encode_draw0`/`encode_draw1` and `callN_initial_noise`,
with `callN_noise_draw_count == 1`), and the recorded operands reproduce the
recorded latents under the fork's `gaussian` formula
(`mean + draw0 * (std/0.8) * draw1`, agreeing to 6.5e-2 on bf16-rounded data). So
injecting them into the torch lane is feasible and verifiable against `callN_eps`;
it is not done here, and both artifacts still say the comparison is duration-based.

## Changes

- `hipengine/kernels/hip_gfx1100/vibevoice/registered.py`: the `rows=1` GEMV
  dispatch added earlier in this session is **reverted**.
- `scripts/vibevoice_tts_quality_suite.py`: run-sequence attribution gate, the
  two-voice identity control recorded as a diagnostic, and the instrument's
  resolved/not-resolved limits in the artifact.
- `scripts/vibevoice_tts_session_bench.py`: declared generation budget, reported
  completion, cold-start ordering.
- `benchmarks/prompts/vibevoice-tts-quality.json`: corrected limitation text (a
  request *is* reproducible at a fixed seed; it is the torch lane that differs).
- `benchmarks/README.md`, `benchmarks/CHANGELOG.md`, both result artifacts.

## Validation

- Three full `--phase all` quality sweeps (18 request-runs each) as tabulated above.
- Re-running the decoder-only variant reproduced `two-2turn` seed 20260917 at WER
  0.6471 exactly, so the suite is deterministic at a fixed revision and seed set.
  (`--only` shifts `request_seed` to `base_seed + index-in-the-filtered-list`, so a
  filtered run is a *different* request; the A/B therefore uses the full request
  list.)
- `uv run python scripts/vibevoice_tts_session_bench.py` -> `chain_exact` true,
  `negative_conditions_match` true, `finish_reason` stop, pooled RTF 1.315-1.355
  over four runs (median 1.337) against torch's 1.303.
- `python3 scripts/sync_benchmark_readme.py --check` -> blocks synchronized.

## Next

The torch lane should consume the recorded operands so the two lanes measure the
same request, verified against `callN_eps`. For speed, the remaining semantic
encoder cost (1.108 s of the 4.457 s warm request) needs a formulation that is
quality-neutral, not merely faster: the reverted dispatch is exactly the kind of
change that the task gate exists to catch.
