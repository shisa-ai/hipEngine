# YuE2 M0 closure: 0.1.6 wheel review and an independent oracle repeat

## Summary

M0's two remaining items are closed. The 0.1.6 release does not touch any module
the pinned oracle is derived from, so the oracle stays pinned to 0.1.5 and no
fixture is regenerated. An independent re-run of one production case reproduces
the committed fixture **bit-for-bit on every recorded array**, including the
2,061 semantic tokens and the 96,000x2 stereo PCM excerpt.

## Changes

- `scripts/yue2_oracle.py`: add `wheel-diff --wheel <whl> [--sha256sums <file>]
  [--json <out>]`. It verifies the wheel hash against a release `SHA256SUMS`,
  compares the wheel's package against the pinned oracle source, and exits
  non-zero when a module in `ORACLE_SOURCE_FILES` differs, i.e. when the release
  is a re-pin decision rather than a note. `compare_wheel_source` is the pure
  function; `tests/test_unit_yue2_fixtures.py` covers both verdicts with
  synthetic trees.
- `docs/MODEL-YUE2.md`: record the 0.1.6 review result and mark M0 complete.

## Validation

0.1.6 versus the pinned 0.1.5 oracle, measured on the release artifact:

- `yue2_infer-0.1.6-py3-none-any.whl` sha256
  `129a015327a2eca530760ffd2163ccb8cb65f7e601715de1d9626a40c568e2e2`, which
  matches the `SHA256SUMS` asset of release `yue2-v0.1.6` (published
  2026-09-09T19:10:05Z).
- `python3 scripts/yue2_oracle.py wheel-diff --wheel <0.1.6 wheel> --sha256sums
  <release SHA256SUMS>` -> 12 of 14 modules byte-identical, `changed:
  ['__init__.py', 'cli.py']`, no module present on only one side, and
  `pinned oracle modules changed: none`. `__init__.py` differs in the version
  string alone (4-line diff); `cli.py` is 1 line added / 12 removed (244 -> 233).
  Every file in `ORACLE_SOURCE_FILES` (protocol, sampling, modeling_yue2, nar,
  modeling_vae, pipeline, tokenization_yue2, storage) is identical, as are
  `cuda_graph.py`, `fast.py`, `progress.py` and `quantization.py`.
- The dist-info moved with the release, not the model: summary, license
  expression (CC-BY-NC-4.0), project URLs and a `MODEL_LICENSE` file were added,
  the `bench` and `serve` extras were dropped, and a `test` extra was added. The
  runtime dependency list is unchanged (`torch==2.10.0`, `transformers==4.57.6`,
  ...), and `pipeline.py` - which imports `fast.py` only inside its opt-in vLLM
  paths - is byte-identical, so the default generation path did not move.
- The shootout's pinned `shared/upstream/yue2` is byte-identical to the **0.1.5
  wheel's** package (only `__pycache__` differs), so `oracle_env.json`'s source
  hashes describe the wheel the fixtures came from.

Independent repeat of a production case, in a fresh process:

- `/home/lhl/venvs/vibevoice-tts-oracle/bin/python scripts/yue2_oracle.py --out
  /tmp/yue2-repeat --compact /tmp/yue2-repeat cases --only english-melody-s1234`
  (the interpreter named in the script docstring: numpy 2.4.4, tiktoken 0.14.0,
  torch 2.13.0+rocm10.0.0). The committed fixtures were generated in this
  environment; the miniforge base interpreter no longer matches it (numpy 2.5.2,
  no tiktoken) and fails on import.
- Comparison against the committed fixture: `abc_ids` (682), `prefix` (794),
  `semantic` (2061), `latent_excerpt` (64x64), `latent_shape`, `latent_norm`,
  `audio_excerpt` (96000x2), `audio_rms`, `audio_peak` all **bit-identical**, and
  the manifest's `identity`, token counts and truncation flags match. The repeat
  took 401.8 s of generation against the recorded 291.3 s: the wall time moved,
  the output did not.
- `python3 scripts/yue2_oracle.py validate` -> fixture tree intact;
  `python3 -m pytest tests/test_unit_yue2_fixtures.py` -> 11 passed.
