# The pack8 fix is two parts: declare the layout, then resolve the key

## Summary

The diagnosis is complete and the fix is **two parts, in order**. Confirmed from
the materializer rather than assumed:

**Layout materialization is declaration-driven.**
`hipengine/loading/qwen35_gguf_materialize.py:147` maps `LAYOUT_Q4_K_PACK8` to
`_ResidentRepack(Q4_K_PACK8_SHAPE, repack_gguf_q4_k_pack8)`, and laguna does the
same at `laguna_gguf_materialize.py:1022`. A weight carries the pack8 layout
**only if its loader declares that layout**.

**Qwen35 then resolves an explicit key map.**
`qwen35_gguf_runner.py:35458` maps `gguf_q4_k`/`q5_k`/`q6_k` to the
`moe_linear` / `expert_pack8_selected_bf16_bf16_out` variants.

**Gemma 4 has neither half**: no pack8 mention in its loader, and a MoE route that
resolves `linear` / `selected_gemv`.

So:

1. Declare the q4_k pack8 layout in Gemma 4's materialization.
2. Resolve the `moe_linear` / `expert_pack8_selected_bf16_bf16_out` key in the
   MoE route, keeping the current route as fallback.

**Part one must come first, and that is a safety property rather than an
optimization.** A lookup change alone would hand the kernel an unpacked weight,
which reads garbage instead of failing - the failure mode is silent, not loud.
This is the ordering the earlier plan assumed; it is now confirmed from the
materializer's own structure.

## Changes

- `benchmarks/results/2026-09-27-gemma4-gfx1151-decode-kernel-profile.json`:

## Validation

- The declaration-driven claim is read from the `_ResidentRepack` mapping in two
  independent materializers, not inferred.
- The consumer contract is read from Qwen35's own `KernelKey` map.
- Gemma 4's two gaps are each established by an empty grep rather than by
  absence of memory.
- **Not yet verified:** that declaring the layout succeeds for this artifact's
  expert tensors, and that the pack8 kernel is numerically correct on Gemma 4's
  geometry. Both belong to the implementation unit.
