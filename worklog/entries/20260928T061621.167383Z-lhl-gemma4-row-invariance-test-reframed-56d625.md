# the row-invariance test now asserts what the design promises and passes with no xfails

## Summary

`tests/test_gpu_gemma4_expert_row_invariance.py` is **4 passed**, with both
`xfail(strict=True)` cases replaced. Nothing in it is expected to fail any more.

## The measurement that closed it

`20260928T061522` established that the divergence is route selection. This unit
found the second crossover and confirmed the whole picture with one run.

There are **two** independent MMQ levers, each gated on the live lane count by
`gemma4_moe_prefill_route_enabled(lanes, num_experts)`:

- `HIPENGINE_GEMMA4_MOE_GATE_UP_MMQ`
- `HIPENGINE_GEMMA4_MOE_DOWN_MMQ`

The old second xfail was named *"with the MMQ route disabled"* and set **only the
gate/up one**, so the down route remained free to change route between the two
calls. Running that same test with `HIPENGINE_GEMMA4_MOE_DOWN_MMQ=0` added gave
**`XPASS(strict)`** -- rows=1 and rows=2 agree once neither route can be
selected.

| configuration | rows=1 against rows=2 |
| --- | --- |
| both MMQ routes on | diverge (grouped against MMQ) |
| gate/up MMQ off only | still diverge (the down crosses on its own) |
| **both MMQ routes off** | **agree** |

So the test's old reason text -- *"the down projection diverges across row counts
even with the MMQ gate/up route disabled, so disabling that route does not
restore the property"* -- attributed the failure to the wrong route. Disabling
the gate/up route does not restore the property because **the down route is a
separate crossover**, not because the down projection is intrinsically row-count
dependent.

The env reads are not cached (`gemma4_moe_gate_up_mmq_enabled` and
`gemma4_moe_down_mmq_enabled` read `os.environ` on every call), so `monkeypatch`
does take effect and the old result was a genuine coverage gap rather than a
stale-flag artifact.

## What the file asserts now

- **`test_expert_forward_row_zero_is_invariant_with_both_mmq_routes_disabled`**
  -- row 0 is unchanged when a row is appended, with neither MMQ route
  selectable. This is the property a caller can depend on, and it passes.
- **`test_the_lane_count_selects_the_mmq_route`** -- pins where the route
  boundary is. The gate opens exactly at the expert count: closed at
  `lanes = num_experts - 1`, open at `lanes = num_experts`, open at
  `num_experts + 1`, and reachable from the row counts (`1 * top_k` closed,
  `2 * top_k` open at this fixture). A change to the gate is now visible rather
  than silent.
- The two `test_gate_up_stage_is_invariant_*` cases are unchanged; they pass.

The removed pair asserted a property `docs/EXECUTION-PROFILES.md` does not
promise -- bit-exactness between a strict path and a reassociating production
candidate -- which is why they had to be expected failures.
