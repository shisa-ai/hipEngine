# HC-1's gate is wired: the layer2 profile gate qualifies GR routes whole-route, so the recorded layer-scope blocker does not apply

## Summary

`HC-1`'s staged-f32 GR-up tile (`coltile2_branch4_rowbatch4_staged_f32`, selected by
`HIPENGINE_QWEN4_EXP_GR_STAGED`) is screened at **2.388x** with the arithmetic intact and is
default-off pending its production gate. The recorded blocker said that gate could not be run.
**That blocker is specific to one gate, and a different gate in the tree already qualifies GR
routes.** The route is now wired into it as `production_gr_up_staged`.

## Changes

`docs/REFACTOR.md`'s GR staged-f32 entry states the gate "cannot be run for this route yet"
because every route in `scripts/execution_profile_q8_wmma_prefill_layers_gate.py` is
*layer-scoped* while `run_qwen4_exp_gr_read` takes no layer index. That objection is correct
**for that gate**, which formats `{layers}` into its selectors and whose scope checks certify a
layer range.

It does not apply to `scripts/qwen4exp_layer2_profile_gate.py`, which qualifies a
**whole-profile candidate against its strict parent** - 18 prompts x prefill-last plus 24 c1
rows, 450 full-vocabulary rows, three candidate repeats, request-local state fingerprints and
32-token free outputs - and whose scope is the route, not a layer range. That gate **already
carries `production_gr_up_restore` and `production_gr_up_wide` for this exact route**, both
binding GR selectors with no layer scope at all. So the instrument for HC-1 already existed and
was already used on its siblings.

This matters beyond HC-1: the recorded blocker reads as a property of the route when it is a
property of one harness. A reader taking it at face value would not look for a second gate.

### What I added

`CANDIDATES["production_gr_up_staged"]` in `scripts/qwen4exp_layer2_profile_gate.py`:

- `classification="T1"` - the only arithmetic difference from the fused exact parent is the
  summation order, so it is a production-gate candidate rather than a strict one;
- `candidate_key=("hip_gfx1151", "linear+gr_gated_mean", "gguf_q8_0",
  "coltile2_branch4_rowbatch4_staged_f32")`, `fallback_key` the exact parent
  `coltile2_branch4_rowbatch4_f32_exact`;
- the environment sets `HIPENGINE_QWEN4_EXP_GR_STAGED=1` and turns `GR_WIDE`, `GR_IU8` and
  `GR_IU8_DOWN` off, so the gate measures the staged tile rather than whichever selector wins;
- `direct_dispatch_target` counts the runner's direct `gr_staged_f32_up` call, which is how the
  route is reached - it **bypasses variant selection entirely** (the runner evaluates
  `rows > 256 and low_rank % 64 == 0` and calls the kernel), so a dispatch count is the only
  proof of engagement.

Verified before running anything: the counter's alias check passes, meaning the runner's
`gr_staged_f32_up` is the same object as the kernel module's. That is the check that catches a
rename on either side.

### Registration trap found while wiring (a real latent defect)

My first version of the test asserted the candidate key was registered and **failed**, while the
same assertion passed in a fresh process. Root cause, established by bisection and then by
reading source:

- the GR staged variant is registered **only** by the module-level
  `register_gr_staged_f32_kernel()` call in `gguf_q8_0_gr_staged_f32.py`;
- `register_gfx1151_kernels` reaches that module through `import_module`, which is a **no-op**
  once the module is already imported, so the self-registration does not re-run;
- `hipengine/kernels/hip_gfx1100/__init__.py` exposes **no** `register_backend_kernels`, so no
  backend-package entry point can re-create the key either;
- `tests/conftest.py` restores the registry to its **collection-time** baseline after every
  test, so the key is gone and cannot be restored by either `register_gfx1151_kernels` or
  `load_backend_kernel_package`.

Production is unaffected (the registry is never wiped) and the gate is **fail-closed** -
`count_candidate_dispatch` raises `ValueError("exact candidate key is not registered")` rather
than silently measuring an unengaged route. But it makes registration order-dependent.

**The same root cause explains a pre-existing failure I did not introduce.** Running
`tests/test_unit_qwen4exp_gr_staged_dispatch.py` together with
`tests/test_unit_qwen4exp_layer2_profile_gate.py` fails
`test_gfx1151_registry_contains_layer2_candidate_and_strict_fallback`; the layer2 file alone
passes. **Reproduced at `2812d8789` in a clean `git worktree` with no other changes**, so this
is a pre-existing order dependence, not a consequence of this unit. It is now recorded in
`docs/REFACTOR.md` with the cleanup: give the staged GR module a registration hook the gfx1100
and gfx1151 packages call explicitly, as `gguf_k_gemv` already does via
`register_gguf_k_gemv_kernels`.

My test therefore calls the two module registrars explicitly before registering the gfx1151
aliases, with a comment saying why. It passes 5 consecutive full-file runs (13 passed each).
