# The dense-wide f16 activation hoist is live and worth 48% - the ledger's dense TFLOP/s figure is stale

## Summary

**Production already runs the f16-activation-hoisted dense-wide kernel, it is 48%
faster than the f32 variant at the same shape, and the campaign ledger's headline
dense figure describes the variant that does not run.**

Three results, in order of importance.

### 1. The tile-family sweep was never done for this family, and it found 48%

`scripts/qwen4exp_dense_wide_tile_sweep.py` (new) times every registered
`dense_wide` variant at the packet shape `rows 1024, K 2560, N 10240` - the shape
`QWEN4EXP-OPTIMIZATION-LEDGER.md` §4A quotes.

| variant | BM | BN | best ms | TFLOP/s | vs default | max abs diff |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| **`dense_wide256_f16in`** | 128 | 256 | **1.3207** | **40.65** | **-48.25%** | **0.000e+00** |
| `dense_wide128x128_f16in` | 128 | 128 | 1.4311 | 37.52 | -43.92% | 0.000e+00 |
| `dense_wide256` (f32 act) | 128 | 256 | 2.5518 | 21.04 | baseline | - |
| `dense_wide128x128` | 128 | 128 | 2.6543 | 20.23 | +4.01% | 0 |
| `dense_wide64x256` | 64 | 256 | 2.9910 | 17.95 | +17.21% | 0 |
| `dense_wide64x128` | 64 | 128 | 3.3044 | 16.25 | +29.49% | 0 |
| `dense_wide256_split3` | 128 | 256 | 4.5115 | 11.90 | +76.80% | timing only |

**The hoisted variants are bit-identical (`max abs diff` exactly 0) and 48%
faster**, which is what the mechanism predicts: hoisting the f32-to-f16 activation
conversion out of the K loop performs the same rounding once instead of once per
K-stage.

**The sweep was genuinely unmeasured.** The ledger's tile row
("`128x64`, `64x64`, `64x128` ... 128x128 optimal in family") is for the **MMQ**
family, and every other reference to these tile variants in the tree is a
correctness test. The kernel's own comment invited the measurement: *"The narrower
layouts give up some weight reuse (traffic is M * K * rows / BN) for headroom;
which one wins is a measurement, not an argument."*

The tile ordering itself is a small result: **128x256 beats 128x128 beats 64x256
beats 64x128**, so the widest BN wins and the narrower layouts lose as the comment
predicted.

### 2. Production already uses the hoisted kernel

`scripts/qwen4exp_q8_dense_wide_route_probe.py --case code-p4096` reports the
launched symbols:

```
hipengine_gguf_q8_0_dense_wide256_f16in_f32_f32_out   1156 launches
hipengine_gguf_q8_0_gemv_coltile8_rowbatch4_wave_scale_pipelined_dpp_f32_f32_out   436
hipengine_gguf_q8_0_pack8_gemv_f32_f32_out              3
```

**1156 launches of the `f16in` symbol.** So the hoist is live and engaged, and the
remaining dense work is the exact coltile chain on the layers the wide route does
not cover.

### 3. The ledger's §4A figure is stale, and production is ahead of the reference

§4A says `dense_wide256` "runs the packet shape in 2.573 ms, **20.9 TFLOP/s**". The
microbenchmark reproduces that number exactly for the **f32-activation** variant
(2.5518 ms) - so the figure has the right provenance and simply describes the
variant production does not run.

**The measured production figure is 40.65 TFLOP/s.** For comparison, §4A records
gufo reporting **30-34 TFLOP/s** for its F16 dense kernels and **19-26 TFLOP/s**
for hipBLASLt. **On this operation the promoted route is ahead of both.**

**This changes what the dense block's remaining opportunity is.** It is not the
wide route's throughput. It is the layers still on the exact coltile chain, which
is exactly the 8-47 scope lever - and that is closed by accumulation-order drift
(see `20261004T132643.298003Z`). So the dense block's recoverable milliseconds are
gated by the numerical envelope rather than by kernel efficiency.

## Correction: an earlier claim in this session was wrong

`20261004T131xxx` recorded that `HIPENGINE_GGUF_Q8_DENSE_WIDE_F16_ACT` is "a no-op
at these shapes" because setting it to 0 reproduced the default's KL figures
exactly. **The observation was correct and the inference was wrong.**

The two paths are **bit-identical by construction** (`max abs diff` exactly 0 in
the sweep), so **no numerical gate can distinguish them** - the gate reproducing
the default's numbers is what the mechanism requires, not evidence of a no-op.
**The knob moves speed by about 48% and numerics by nothing.** It is therefore a
clean A/B lever for the hoist, and its "no-op" label should not be reused.

**The transferable lesson:** when two paths are bit-identical by construction, a
numerical gate is not a test of whether the path changed. Any question about which
one is engaged has to be answered by a symbol census or a speed measurement. The
symbol census in §2 is the check that would have settled it immediately.

## Changes

- `scripts/qwen4exp_dense_wide_tile_sweep.py`: new microbenchmark over every
  registered `dense_wide` tile family at the packet shape. Times each variant,
  reports TFLOP/s and the per-variant spread, and checks every variant against the
  default's output so a tiling that changes results cannot be mistaken for a win.
  `dense_wide256_split3` is excluded from that comparison because it deliberately
  issues three WMMA products per accumulator on identical operands, so only its
  timing is meaningful.

## Validation

- `scripts/qwen4exp_dense_wide_tile_sweep.py` ran clean at the packet shape,
  3 warmup + 7 repeats, and wrote `/tmp/tile-sweep.json`.
- Every non-timing-only variant matched the default's output at `max abs diff`
  exactly 0, so the 48% is a pure speed effect and not an arithmetic change.
- The symbol census is from `scripts/qwen4exp_q8_dense_wide_route_probe.py`
  (a real 4096-token prefill through the production profile, `prefill_seconds`
  15.35), and its own docstring notes that a selector can report engaged without
  having replaced the leaf - which is why the symbol count is the load-bearing
  evidence.
- **No end-to-end speed claim is made here.** The 48% is a microbenchmark of one
  GEMM shape. An interleaved A/B of `F16_ACT=1` against `F16_ACT=0` at
  `code-p4096` is running to price it end to end.
