## The two biggest terms are not bandwidth-bound

- **`group compact (active)` is 12.354 ms over 30 calls -- 0.41 ms each -- to write
  `sorted_lanes`, `sorted_experts` and `sorted_weights` for 4096 lanes.** That is roughly 49 KB
  per call, so the kernel is running at **~0.12 GB/s**. Nothing about 49 KB takes 0.41 ms at any
  bandwidth; it is latency- or serialization-bound.
- **`gather packed hidden` is 9.580 ms over 30 calls -- 0.32 ms each -- moving
  `lanes x hidden_size` = 4096 x 2816 bf16 = ~23 MB**, so ~2.4 GB/s. A per-lane row gather is
  inherently scattered, but 2.4 GB/s is far below what the same host's dense GEMM sustains
  (127 GB/s, `20260929T020000`).

**Together these two are 21.9 ms, 3.3 percent of the prefill**, and both are small kernels doing
a little work very slowly rather than large kernels doing a lot of work near a limit. That makes
them a **cheaper candidate than the down projection's tile layout** (`20260929T093000`, ~21.8 ms
expected but a repacker plus a new WMMA variant plus an oracle plus loader wiring): the target
here is the same ~22 ms, on two kernels whose inputs are tens of kilobytes.

This is not yet a diagnosis. Both kernels need their launch geometry read before anything is
claimed about *why* they are slow, and `20260928T114215`'s warning applies -- the expert block
has already produced one confident stall story that a later measurement retracted.

## The instrument trap, hit again

The first run of the extended probe reported **none** of the seven new arms. `gemma4_experts.py`
binds these kernels with module-level `from ... import name`, so replacing the attribute on the
*defining* module leaves the consumer's already-bound reference untouched. **Patching the
consumer (`gemma4_experts`) is what works**, and it is the identical trap the route ablation hit
and had repaired earlier in this session (`20260929T080000`). The probe now carries a comment
saying so. **Any future probe in this tree must patch the module that calls the symbol, not the
module that defines it.**
