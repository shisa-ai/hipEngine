# halo-box PR 63 is 13.9% faster on shallow prefill with identical output

## Summary

**Decision: use the PR #63 head `c4aa30229` as the halo-box comparison target
instead of `69946438a`.** Both conditions the review set are met: the prefill is
measurably faster and the output is identical. The existing `69946438a` numbers
are retained as the baseline of record for the before/after pair.

## Result

Matched protocol, same host, same session, both arms `--no-warmup` with one
unmeasured warmup then one measured request on fixture case `code-p4096`:

| arm | prompt_ms | tok/s | 48-token greedy output |
| --- | ---: | ---: | --- |
| `69946438a` | 5552.5 | 737.7 | reference |
| `c4aa30229` | **4873.5** | **840.5** | **identical, 48/48** |

**+13.9%.** The baseline re-measured under `--no-warmup` reads 5552.5 ms against
its historical 5531.0 ms, 0.4% apart, so the flag did not perturb the window and
the comparison is like for like.

## What PR #63 is

23 commits from pwilkin's `codex/halobox-modules-20260914` into
`halo-box:master`. It is **open, not merged**. Its base `cfe6bb14e` is already
newer than our baseline `69946438a`.

The structurally important commit is `08de004`, which ports the Strix Halo
optimization line's MMB kernels into halo-box: weights of any quantized type are
dequantized to BF16 in LDS, activations are converted to BF16 once per graph and
cached, and the product accumulates in F32 on the 16x16x16 BF16 WMMA path. This
is pwilkin's `mmb_dense_kernel` / `mmb_routed_kernel` / `mmb_routed_glu_kernel`
family, and the PR63 trace now contains those kernels verbatim. **The two
comparator lanes converge on this merge.**

## Attribution

Kernel time per family, matched protocol. The profiled window covers the warmup
and measured prefill together, so the deltas are meaningful and the absolute
totals are not a single prefill.

| family | baseline ms | PR63 ms | delta % |
| --- | ---: | ---: | ---: |
| expert_down | 2301.4 | 1132.8 | **−50.8%** |
| quantize_pack | 567.9 | 0.0 | **−100.0%** |
| moe_reduce | 405.0 | 208.5 | **−48.5%** |
| elementwise_norm | 1049.8 | 677.9 | −35.4% |
| hyper_connection | 843.0 | 688.8 | −18.3% |
| dense_projection | 3116.4 | 2774.2 | −11.0% |
| gdn | 569.9 | 530.7 | −6.9% |
| expert_gate_up | 1665.5 | 1556.3 | −6.6% |
| qsa_attention | 311.4 | 626.5 | **+101.2%** |
| indexer | 11.2 | 29.8 | +166.1% |
| other | 14.7 | 12.2 | −17.0% |
| **total** | **10856.3** | **8237.6** | **−24.1%** |

The four largest gains are one or two changes each: `expert_down` and
`quantize_pack` are both `08de004` (the MMQ kernel and its per-matmul activation
quantization disappear together), `moe_reduce` and `hyper_connection` are
`60c26d0` (BF16 hyper-connection streams and BF16/float4 reduction variants), and
most of `elementwise_norm` is `0106857` (one wave per row for narrow RMS).

The kernel sum falls 24.1% while the wall rate improves 13.9%. The profiled
window holds two prefills and the warmup benefits more than the measured request,
so **the wall number is the one to retain.**

## Two things that look like regressions, only one of which is

**`qsa_attention` is a real regression.** Same kernel, same template arguments,
same 48 dispatches, 2.16x the time:
`flash_attn_ext_f16<256, 256, 16, 4, false, false, false>` goes 270.98 -> 585.69 ms.
The PR touches this area directly (`e09da52` adds a masked sparse prefill
attention path; `c4aa302` is the tip commit on selection sentinels), so the likely
cause is that the dense path now does more work per call, but **the cause is not
established, only the measurement.** It costs ~315 ms against ~2400 ms of gains
and does not change the sign.

**`indexer` +166% is classification, not regression.** The baseline's top-k ran
through hipCUB and landed in `elementwise_norm`: indexer 11.2 ms plus 17.4 ms of
rocprim trampoline against PR63's 29.8 ms plus 0.6 ms. Combined, 28.6 -> 30.4 ms,
which is +6% and inside the noise floor. `ec05a66` replaced the hipCUB sort with
named `top_k_radix_*` kernels; the work moved between families rather than
appearing.

## Changes

- `scripts/qwen4exp_comparator_role_map.py`: the two dialect mappers now delegate
  to each other, because PR #63 puts `mmb_*` kernels in a llama.cpp-family build.
  The delegation guard uses substring matching, not `startswith`, since trace
  names carry a `void (anonymous namespace)::` prefix — `startswith` silently sent
  every MMB kernel to `other`. Added `rms_rows` and `qsa_expand` to the llama.cpp
  rules, which `map_mmb` had and it lacked. Added burst delimitation
  (`--delimit`, `--burst-gap-ms`) and burst reporting.
- `scripts/qwen4exp_llamacpp_prefill_comparator.py`: `--server-arg` (repeatable)
  and `--marker-trace`. `--server-arg` needs the `=` form, since argparse reads a
  following `--flag` as a new option.
- `scripts/llamacpp_pair_token_compare.py` (new): greedy token-sequence
  comparison between two servers, for the correctness half of the gate.
- `benchmarks/results/2026-09-15-flashnext-engine-comparison/`: `pr63-vs-baseline.md`
  and `roles-halobox-pr63-c4aa30229-bf16.json`; the two existing role maps were
  regenerated under the unified mapper.

## Validation

- Both arms built from a clean tree (`dirty: false`), same CMake configuration,
  same server arguments, same fixture case and token ids.
- Correctness: 48/48 identical greedy tokens over 48 decode steps.
- Role mapping leaves 0.1% of baseline and 0.1% of PR63 kernel time unattributed;
  pwilkin's map returns to 0.2% under the unified mapper.
- Delimitation is still open: both traces report a kernel-sum to measured-prompt
  ratio of ~1.7x because the profiled window holds the warmup prefill as well.
  The family **deltas** are valid under the matched protocol; per-component
  absolute figures are not, and task #13 remains open for that.

## Caveats

1. **The PR is not merged.** This is a measurement of `c4aa30229` specifically.
   If the head moves, the comparison is against that commit and not against
   "PR #63".
2. **The PR changes numerics.** Its own commits record WikiText2 perplexity
   2.0285 -> 2.0259 and 2.0259 -> 2.0254. Output is identical at this prompt, but
   a post-merge halo-box-versus-hipEngine comparison carries a small numerical
   change alongside the speed change and should say so.
3. Single repetition per arm. The +13.9% is far outside the ~1.4% run-to-run
   spread measured for this class of capture, but a repeat would make it firm.
