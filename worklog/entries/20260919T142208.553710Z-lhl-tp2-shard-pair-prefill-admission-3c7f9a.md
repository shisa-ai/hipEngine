# The sharded prefill can reach the fused pair now, and it does not matter yet

## Summary

The TP2 rank-local bulk prefill's sharded MLP ran two t16 WMMA prefill singles
plus a separate SiLU-multiply, while the fused gate/up+SiLU prefill owner sat
unreachable. The reason was one comparison: `_q4_t16_dual_wmma_silu_dispatch`
required `out_features == 17408`, the *unsharded* FFN width, and a sharded rank
activates `ffn_size // ranks` (8_704). So the ladder returned `None` and the
launcher fell through to the decode-shaped variant.

The fused owner is now admitted at the shard width and the shard chain attempts
it at batched rows, with the unfused chain as its fallback.

**It is bit-identical and it is faster in isolation, and on the product path it
changes nothing.** All three of those are measured, and the third is the
interesting one.

## What was measured

Kernel-level, at the real shard shape (5_120 → 8_704), against the unfused chain
the chain actually runs — two `shared_b` singles plus `silu_mul_separate_out_bf16`:

| rows | fused variant | vs unfused | bit-identical |
| ---: | --- | ---: | --- |
| 32 | row32 | 2.41x | yes |
| 48 | row48 | 2.08x | yes |
| 64 | row64 | 1.81x | yes |
| 128 | row128 | 1.67x | yes |
| 256 | generic | 1.14x | yes |
| 512 | generic | 1.27x | yes |

The band-named variant is fastest in every band, so the existing ladder is reused
unchanged — only the admission was missing. The fused owner also replaces three
launches per layer per rank with one (384 → 128 launches per prefill).

**A correction worth keeping.** The first version of this measurement used the
plain `t16_wmma_prefill` single as the control and read 1.74x at rows=512. The
chain runs the `shared_b` single, which is faster, so that figure was overstated
by a third. The existing production-shape parity test in
`tests/test_gpu_gguf_q4_k_t16_dense.py` uses `shared_b` as its control, which is
what exposed the error; the artifact records the superseded number rather than
quietly replacing it.

End-to-end on the product path (`logits_rows=1`, 512 rows), paired in one session
with the capability toggled and four alternating rounds:

| | wall ms | tok/s |
| --- | ---: | ---: |
| unfused | 492.8 (median) | 1039.0 |
| fused | 493.5 (median) | 1037.6 |

**−0.14%.** Paired deltas `+4.32, −0.27, −0.07, −0.22`. The phase attribution
agrees: `mlp_chain` 189.74 → 189.50 ms, wall 491.2 → 495.4 ms.

The `tp2_c1_bench.py` row reads 1043.2 against the retained 1032.9 (+1.0%), but
that is within run-to-run noise and the paired A/B is the controlled comparison.

## Why the saving vanishes

The sharded MLP phase is **rendezvous-bound, not arithmetic-bound**. Each layer
ends in a peer exchange whose sync latency is fixed, so the ~30 ms of chain work
this removes per prefill is absorbed as extra wait instead of shortening the wall.

The evidence is in the attribution's rank asymmetry: rank 1 carries 168.7 ms of
chain against rank 0's 189.5 ms while waiting 111.5 ms at the exchange against
rank 0's 64.6 ms. The wait is absorbing both a real imbalance and the fixed
latency, and it grows to cover whatever the chain gives back.

The saving does reach the wall whenever the wall is not sync-bound. The same
paired A/B **without** `logits_rows=1` — where ~560 ms of full-row head
projection dominates the critical path — reads **+3.16%**, all four paired deltas
positive. That is the control that shows the ~30 ms is real and simply has
nowhere to land on the product path.

## Correctness

Bit-identical end to end: `scripts/tp2_bulk_prefill_diagnostic.py --reduce-mode
device` produces the same `logits_sha256` for both prompts
(`b4c14c35…`, `af4b3ce0…`) and identical metrics before and after. The route's
pre-existing KL gap is untouched, so this change neither causes nor hides it.

## Why it is retained

It is exact, it is strictly less work, and it removes 256 launches per prefill.
`docs/REFACTOR.md` records it as debt with the two conditions that would make it
pay (the exchange stops being a per-layer rendezvous, or the MLP phase stops
being straggler-bound) and states that the admission can be withdrawn without
losing throughput if neither changes.

## The finding that matters more than the change

**MLP arithmetic is exhausted as a lever on this route.** The phase attribution
puts attention at 47.2% and the MLP at 57.0%, but the MLP's arithmetic is not on
the critical path — its rendezvous is. Further gate/up/down kernel work will read
as wins in isolation and as nothing on the wall, exactly as this did.

The next lever is the attention phase, which is also where the correctness
blocker lives. That is now the same investigation twice over.

- `hipengine/kernels/hip_gfx1100/__init__.py` —
  `GGUF_Q4_DUAL_SILU_PREFILL_OUT_FEATURES`, with the neutral-wall result written
  into the comment so the admission is not mistaken for a throughput win.
