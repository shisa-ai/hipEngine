# Corrected LM/diffusion GEMV picture: 3 of my inferences were wrong; the LM decode tail-loop cliff is quality-blocked, not overlooked

## Summary

Chasing the diffusion head's unexplained per-call cost produced three **corrections to
my own earlier inferences** and one important confirmation. The diffusion head is at
**80% of peak memory bandwidth** and has essentially no kernel-level headroom. The LM
decode does fall into the scalar tail loop for 6 of 7 weight matrices per layer
(`forward_layers` never passes `threads=`, so it uses the default 256 with
`hidden=1536`), but that fast path is **already a documented quality rejection**, not
an overlooked win: `threads=64` is 1.23x on the kernel and takes the ten-seed quality
suite from 58/60 to 57/60 by moving 5 of 17920 outputs one ulp.

## Changes

No code change. One immutable worklog entry.

## Validation

### Correction 1: the elementwise kernels are fast, not slow

Iteration 34 inferred ~52 us per elementwise kernel by subtracting an isolated GEMV
figure from `forward()`. Direct measurement at n = 2 x 1536 (12 blocks x 256, the
standard `(n+255)/256` grid):

```
vv_diff_silu_bf16             10.75 us
vv_diff_add_bf16              10.12 us
vv_diff_rmsnorm_modulate_bf16 17.93 us
vv_diff_gated_residual_bf16    8.92 us
```

So ~20 elementwise kernels are ~250 us/step, not ~1050 us. The launch config is
ordinary (`(n + 255) / 256` blocks of 256); there is no launch pathology.

### Correction 2: the D2H readback is not a bottleneck

```
sync hipMemcpy D2H (512 B) :  9.90 us
bare device_synchronize()  :  0.23 us
sync hipMemcpy H2D (512 B) : 12.23 us
```

### Correction 3: there is no L2 artifact in the diffusion GEMV figures

I suspected my isolated per-shape GEMV benchmark was L2-inflated because it ran each
shape 50x consecutively. Measuring the 22 calls in their real per-step sequence
instead of repeating one shape:

```
22 GEMVs, real sequence order  : 1205.9 us/step
22 GEMVs, one shape repeated   : 1407.7 us/step   (slower, not faster)
weight traffic per step        :  246.55 MB
implied bandwidth (real order) :  204.4 GB/s  (~80% of ~256 GB/s peak)
```

The diffusion head's weight traffic is near the roofline. This is the same
`3530fa959` L2-artifact trap the tree has hit before, and here the check came back
clean.

### Confirmation: the LM decode does hit the tail-loop cliff

`grep -n "threads=" hipengine/runtime/vibevoice_qwen2.py` returns **nothing** --
`forward_layers` never overrides the thread count, so every GEMV uses the default
256. The LM's `hidden_size` is 1536 (confirmed by the earlier
`cannot reshape array of size 48000 into shape (1,1536)` error), so
`vec_stride = 256 * 8 = 2048 > 1536`, `main_end = 0`, and the vectorised 8-wide main
loop executes **zero** iterations: every element is fetched by the scalar
stride-256 tail loop. That covers q/k/v (in=1536), o_proj (in=1536) and gate/up
(in=1536) -- **6 of the 7 weight matrices per layer**. Only `down_w` (in=ffn) has
`main_end > 0`.

### But it is quality-blocked, not overlooked

This was already tested and rejected:

- `benchmarks/results/2026-09-15-gfx1151-vibevoice-tts-quality-threads64-rejected.json`
  -- "Rejected arm: LM decode gate+up dual GEMV at threads=64. 57/60 against the
  baseline 58/60, adding a single-numbers failure at WER 0.1667 on seed 20260917."
  `chain_exact` stayed true and the correctness suite stayed green, which is the
  documented evidence that `chain_exact` is not a sufficient gate here.
- Commit `232da8ab4 fix: reject the threads=64 decode GEMV; chain_exact is not a
  sufficient gate`.
- The dual GEMV reaches 169.5 GB/s at `threads=64` against 138.1 GB/s at 256, and the
  thread count moves the reduction width and therefore the summation order (5 of
  17920 outputs by one ulp).

### And the bit-exact route is already closed too

`worklog/entries/20260915T194341.808338Z` built the obvious bit-exact variant --
stage the weight row through shared memory with 8-wide loads so each thread's element
set and order are untouched while the loads widen. It was **BIT-EXACT on all four
shapes and measured 0.99x** (403.5 us original vs 408.3 us staged at threads=256).
The diagnosis: the kernel is **DRAM-latency-bound, not load-width-bound**. The
`threads=64` advantage comes from more workgroups resident per CU hiding that
latency, and that is not recoverable by making the same workgroup's loads wider.

## Next

Both obvious routes are closed, so the remaining avenue is narrow and specific: **a
change to work partitioning that raises resident work per CU while keeping the
256-wide tree pairing per output bit-exact.** The most concrete form is a block that
owns R output columns instead of one: each thread holds R accumulators, and the
8-level shared-memory tree runs on R values per thread per level, so the eight
`__syncthreads()` are amortised across R trees rather than paid per output. That
preserves the per-output tree pairing exactly (bit-exact by construction) and targets
the measured latency-bound behaviour rather than load width.

Upside is bounded by the dual GEMV's own figure: 138.1 -> 169.5 GB/s is ~1.23x on
the LM's decode GEMMs, and the LM stage is 1.450 s of 4.005 s, so a full capture
would be roughly 0.2-0.3 s (~5-7% of warm). It cannot approach 2x, consistent with
the arithmetic in `20260915T204702.890224Z`.

Anyone re-attempting the bare `threads=64` switch should know it is a genuine 1.23x
kernel win that has already been measured against the quality suite and rejected
once; repeating it without new quality evidence would be re-running a known result.
