# Pinned accept staging is perf-neutral: the wait is device latency, not the copy

## Summary

I implemented the pinned-staging fix (#17 route (a)) and it is **performance-neutral**.
The blocking pageable
uploads were 96.5% of the accept window; after staging them through page-locked memory
they cost 0.1 ms, and
the accept window did not shrink. So the copies were not the cost - they were where an
unavoidable device wait
was being charged. This is the third consecutive accept-phase hypothesis this campaign
has killed with its own
measurement.

## Changes

- `790eaee91` - page-locked accept staging, kept in the tree (see "Keep or revert" below).
- This entry records the verdict and redirects #17. It supersedes the prediction in
  `20260830T155357…`, which expected accept to roughly halve.

## What the result means

- Before: the first blocking `hipMemcpy` absorbed the device queue drain, so the wait
  appeared as `upload_ms`.
  After: `memcpy_async` returns immediately, and the same ~100 ms per lane-cycle reappears
  as unattributed time
  inside the same window. The window's size was never about the copies.
- Reading of the shape: the cycle consumes verify results as soon as it enqueues them, so
  per-cycle latency *is*
  device latency and nothing short of not waiting there can reduce it. That is consistent
  with AR (graph
  capture, w^0.36) versus MTP (eager cycle, w^0.76) in `20260830T155541…`, and with peers
  scaling x1.59 across
  C5-C8 while we sit flat at 30.2-30.8 tok/s. Inference, labelled: the measured facts are
  the table above.

## Keep or revert

- Kept. It removes ~7 device-wide synchronization points per cycle, it made the telemetry
  honest (the upload
  counter can no longer hide a wait), and it is a prerequisite for any future overlap
  work. It is retained as
  neutral, with its blocking fallback intact; no performance claim is attached to it anywhere.
