# Ranked port list: Qwen3.8-27B / Flash-Next levers to gfx1151 Qwen3.6-35B-A3B

## Summary

Ranked by expected return against the two deficits this unit measured on the
gfx1151 Qwen3.6-35B-A3B GGUF path: prefill at 14.6% of the FP16 peak and a
decode step whose addressable 24% is concentrated in compute-only stages and
small MoE GEMVs. Each item names the in-tree lineage it ports from, the measured
basis, and what has to be true before it is retainable. Ordering is by
(basis strength x addressable ms), not by novelty.

The direction matters: **the R12 dense-Q8 MMQ work already measures the same
7-11 int8 TF/s ceiling on this GPU that this unit measures at 14.6% of FP16
peak**, so the prefill lane is a continuation of an existing campaign rather
than a new port.

## Changes

No code changed. This entry is a ranked plan; each item below names the
in-tree lineage it ports from, the measured basis, and its retain condition.

### 1. Ship the 1024-row linear/MoE chunk, and remove the override defect first

- **Basis (measured today):** 4096-token shipping-route sweep, 3 reps, 3 s
  settle, one session per size with `reset()` between reps: 512 = 1372.6 tok/s,
  **1024 = 1460.5 (+6.40%)**, 2048 = 1412.6 (+2.91%). The shipping value is the
  worst of the three.
- **Lineage:** in-tree; `GGUF_PREFILL_CHUNK_SIZES_BY_GEOMETRY` is ours, and the
  gfx1151 arch profile already carries 256/256 as its intended value.
- **Blocker:** the override rewrites chunks after the resolver and after any
  explicit `PrefillConfig`, so the value is unreachable through the public flags
  and `prefill_chunk_tuning` misreports it. See `docs/REFACTOR.md`.
- **Retainable when:** one code path owns the final chunk size, `target_arch` is
  passed from the runner so the arch profile is reachable, and the applicable
  `docs/EXECUTION-PROFILES.md` correctness gate passes at the new chunk size
  (chunk boundaries change reduction grouping).
- **Note:** gufo uses `kPrefillChunkTokens = 2048`; 2048 measured +2.91% here, so
  their value is not automatically ours.

### 2. Continue the R12 dense-Q8 MMQ tiling/occupancy work onto the 35B-A3B shapes

- **Basis (measured today):** the shipping-route prefill trace is 98.5% kernel
  time with no host gap, and the GGUF-shape compute basis puts the kernels at
  **8.68 TFLOP/s = 14.6% of the 59.4 TFLOP/s FP16 peak** — 3.7x above the
  chunk-512 memory floor and 6.8x above the compute floor.
- **Lineage:** `20260910T090000.000000Z-lhl-qwen4exp-r12-dense-q8-mmq-design-basis-081ebd`
  measures every dense Q8 leg on this same GPU at **7-11 int8 TF/s** and
  concludes "the gap is tiling/occupancy/staging, not the arithmetic family",
  with the sharpest clue that wide-N `attn_qkv` (7.0 TF/s) is 1.5x slower than
  `attn_q` (10.6 TF/s) at the same K. R12's tile-plane screen and d4x2 rejection
  are already recorded.
- **Why it ranks here:** it is the only item with a pre-declared target rate and
  an existing owner, and it explains our number exactly.
- **Retainable when:** the R12 tile/occupancy change lands for the H2048-MoE
  shapes (K=2048, N=8192/4096) and passes the same gate.

### 3. Fuse or re-shape the decode stages that carry no weight traffic

- **Basis (measured today):** **2.48 ms of 17.81 ms (14%)** is compute-only with
  zero weight bytes — `decode_full_attn_core_gate` 0.848, `decode_linear_attn_gdn`
  0.603, `decode_ffn_moe_combine` 0.438, `decode_ffn_post_norm_residual` 0.363,
  plus 0.247 in five small stages. GPU busy is 99%, so these are executing, not
  waiting.
- **Lineage:** the 27B/Flash-Next fused composites (`gate_combine_residual`,
  `rmsnorm+rotate`) and the `20260901T092206.054890Z-pi-qwen38-gfx1100-q4-r36-fused-row48-retained-072153`
  fused row48 owner. Any fused composite must keep its registered strict unfused
  fallback (architectural invariant).
- **Retainable when:** exact control/ownership holds in every profile and the
  strict unfused chain is registered under the primitives.

### 4. Fix the small MoE GEMV shapes (shared expert + router + F32 stages)

- **Basis (measured today):** the shared-expert pair costs **0.67 ms** at
  **98-103 GB/s** and the router **0.29 ms at 118.6 GB/s**, against a 237 GB/s
  ceiling that the four largest streams already reach (84-100%). The F32
  `alpha_beta` (55.4 GB/s) and `conv` (21.4 GB/s) stages add 0.37 ms.
- **Diagnosis:** per-layer traffic is 1.1-2.2 MiB, i.e. ~5-11 us of ideal work
  per layer at 41 layers — short enough that launch geometry and latency, not
  bandwidth, set the rate. This is the same class as the R12 wide-N finding.
- **Lineage:** the 27B small-shape work and the gfx1151 GEMV rowtile family
  (`GGUF_Q8_T16_DECODE_ROWTILE_*`).
- **Note:** the shared expert is Q8_0 while the selected experts are Q4_K/Q5_K,
  so the shared expert should be *faster* per byte, not 1.7x slower.

### 5. An int8 decode KV copy, with F16 kept for prefill

- **Basis:** gufo retains 64K/128K with a per-32-value-F16-scale int8 copy written
  at decode and read by the decode attention, keeping F16 for prefill. Our
  `--kv-storage int8_per_token_head` exists but `auto` resolves to BF16 and the
  27B campaign closed INT8 KV for gfx1151 under its quality contract.
- **Why it is ranked here and not higher:** at 4K the KV term is small relative to
  2.446 GiB of weights, so the win is a long-context item; and it is
  quality-gated, not free.
- **Retainable when:** the calibrated mean/tail/max KL, top-1 by category, and
  task gates in `docs/EXECUTION-PROFILES.md` pass on the full multi-prompt
  mtp-bench suite — never on a single prompt.

### 6. Make the exact MTP path competitive, rather than adding a new one

- **Basis:** the published gfx1151 35B-A3B MTP row is `llama-compat` MTP-2 at
  56.09 -> **80.10 tok/s = 1.4282x**, retained as an explicit opt-in and
  explicitly **accuracy-traded versus normal AR** (`benchmarks/README.md`). gufo's
  `MtpLengthController` reaches ~1.44x and their `VerifyGreedyDraft` truncates a
  draft chain when the draft's own probability < 0.5, which is exact for greedy
  decoding and saves verify cost.
- **So the gap is exactness, not ratio.** The portable mechanism is the
  expected-tokens-per-cost depth controller plus the exact greedy truncation
  rule, applied to our verifier — not a new draft model.
- **Retainable when:** it passes the same strict-teacher and task gates the
  accuracy-traded row does not, on the full multi-prompt suite.

## Explicitly not ported

- **A WMMA prefill route for dense or selected-MoE.** We already have both; the
  shipping-route trace names them (`dense Q8_0 WMMA` 25% and `MoE expert WMMA`
  38% of prefill kernel time). The gap is throughput inside those kernels, which
  is item 2.
- **MMQ prefill kernels.** Already in tree (`gguf_k_mmq_prefill`,
  `gguf_q4_k_q8_1_mmq_prefill`, `gguf_q8_0_mmq_prefill` under
  `kernels/hip_gfx1100/quant/`).
- **A load-time Q8_0 prefill copy of the k-quant dense matrices (gufo
  `PrefillQ8`).** Our dense/attention is already Q8_0 in this file — the highest
  type present — so there is nothing to upgrade on the dense side. The experts
  stay k-quant in gufo's prefill too.
- **Prefix caching as a pp-rate lever.** It is a TTFT lever (F5: 249.269 ->
  21.188 ms, 11.765x) and it is opt-in because A2 measured a concurrency-goodput
  regression; it does not change the timed window in either protocol.

in this entry was re-measured for the plan itself, and no item is promoted.
