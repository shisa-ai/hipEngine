# RT-1 peer fairness measured: the 1024->4096 cap is free

## Summary

RT-1's promotion of Qwen4Exp prefill chunk 4096 was withheld on a peer-fairness
objection: raising `max_prefill_chunk_tokens` 1024 -> 4096 was said to "quadruple
the per-tick prefill bound that protects decode interleaving". **Measured, that
objection is false.** A decoding peer's inter-token latency and time-to-first-token
are unchanged, and so is the prefill wall.

The mechanism is wrong, not merely unmeasured:

- `protect_decode` protects decode by **priority**, not by bounding the tick. While
  a decode row is due the loop schedules decode, so a continuously decoding peer is
  never interrupted - it starves the *prefill* instead.
- `Qwen4ExpResidentServingRunner.prefill_batch` advances `row.prefill_tokens_seen`
  across slices and then calls `row.runner.prefill(row.prompt_ids)` - the **whole
  prompt** - once the last slice arrives. The executed GPU prefill is one 4096-token
  call at either cap. The cap changes how many loop ticks accumulate it, not how
  much work any tick does.

So the cap is a *scheduling* knob that does not change the executed chunk. That
also means the cap is not a route to the -4.94%, for the same reason RT-1 already
found a larger workspace owner is not: the workspace is scratch and kernel work
scales with the actual token count.

**Not cleared:** the generator-level chunk 4096 (which *does* change the workspace)
was not exercised in the serving path - see Limits.

## Changes

- `scripts/qwen4exp_prefill_peer_fairness.py` (new). Two rows on one engine loop:
  a 4096-token `code-p4096` row and a decoding peer. One process per arm, one arm
  per model load. Orders: `queued` (both rows enqueued before the first tick, long
  row first), `peer_first` (peer decodes, prefill submitted mid-stream),
  `prefill_first` (abandoned, see below).
- `benchmarks/results/2026-10-04-qwen4exp-prefill-peer-fairness/` - README plus

## Validation

Host gfx1151 APU, `/etc/machine-id` `55ea6c509d0b49eea8de7094a1023668`, model
`unsloth-Qwen3.8-Flash-Next-UD-Q4_K_XL/UD-Q4_K_XL`, production profile, cached
build, `max_sequence_length=4097` matching RT-3's protocol
(`max(768, prompt_tokens+1)`), since the workspace is
`min(prefill_chunk_size, max_sequence_length)` rows. `tuned-adm` reported
`accelerator-performance` and the CPU governor `performance` in every arm.

**A) A continuously decoding peer (400 tokens, ~20 s), long prefill submitted
mid-stream** (`--order peer_first`):

| arm | cap | prefill ticks | peer ITL median | peer ITL max | prefill wall |
|---|---:|---|---:|---:|---:|
| `g1024_l1024` | 1024 | `[16, 1024, 1024, 1024, 1024]` | 49.662 ms | 54.978 ms | 35.268 s |
| `g1024_l4096` | 4096 | `[16, 4096]` | 49.608 ms | 54.753 ms | 35.250 s |
| **delta** | | | **-0.11%** | -0.41% | -0.05% |

The trace shows the two rows never overlap: the peer finished at +19.4 s and the
prefill only then began. Under `protect_decode` there is no overlap to measure.

**B) A second request queued behind the long prefill before the first tick**
(`--order queued`), both arms comparable because the loop's own FIFO decides:

| arm | cap | prefill ticks | peer TTFT | prefill wall |
|---|---:|---|---:|---:|
| `g1024_l1024` | 1024 | `[1024, 1024, 1024, 1024, 16]` | 16.860 s | 15.999 s |
| `g1024_l4096` | 4096 | `[4096, 16]` | 16.841 s | 16.012 s |
| **delta** | | | **-0.11%** | +0.09% |

**Engagement is recorded from inside the run, not inferred.** The session's
`_prefill_workspaces[*].prefill_chunk_size` and the loop's `prefill_chunk_size` are
read back after `prepare()`, and every `prefill_batch` call is traced with its row
count: `loop_prefill_batch_chunks` goes `[1024, 1024, 1024, 1024, 16]` ->
`[4096, 16]` and the call count 5 -> 2. The cap reached the scheduler and changed
the tick decomposition 4x - the exact change the blocker predicted would cost
fairness.

**Two harness defects found and fixed, both of which had produced misleading
numbers:**

- Submitting both rows *before* the ordering branch made `prefill_first` and
  `peer_first` identical (16 + 4x1024 = 4112 accounted for the observed batch
  sizes). Submissions are now inside the branch.
- `--order prefill_first` is unusable and its result is **not** reported: `poll()`
  runs a whole tick synchronously, so at cap 4096 the first `poll()` does not
  return until the prefill is finished and the peer gets enqueued *after* it. That
  produced a spurious "peer TTFT 0.88 s vs 16.88 s" that was purely an artifact of
  when the harness managed to submit. `queued` exists because of this.

## Next

- **The generator-level chunk 4096 in the serving path is still unmeasured.** RT-1
  measured -4.94% by calling `runner.prefill(ids)` directly; whether the
  generator chunk (which changes the workspace, unlike the cap) delivers it through
  the engine loop is open. Forcing it currently fails with `copy size 32768 exceeds
  device buffer size 8192`: `qwen4_exp_profiles._bind_default_chunk` resets
  `generator.runner.prefill_chunk_size = 1024` after construction whenever the
  factory left `_implicit_profile_chunk_size` True - which is always, when `LLM`
  passes no chunk - so the workspace stayed 1024 rows. Fixing that override is the
  prerequisite for the measurement.
- **Cap and workspace are different knobs.** Any future RT-1 write-up should not
  treat them as interchangeable, and the -4.94% should not be attributed to the cap.
- Repetition. All deltas here are <=0.11%, so the supported claim is "no measurable
  degradation", not a resolved zero. One repetition per arm, one peer shape, one
  policy (`protect_decode`); the `token_budget` policy was not exercised.
