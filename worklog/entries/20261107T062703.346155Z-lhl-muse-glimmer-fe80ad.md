# Muse Glimmer prefill LDS stride sweep + decode-fusion assessment

## Summary

Swept the shared_b weight-slab LDS stride to attack the 48.5% b_reg bank
conflict. 272 (QK_K+16) is optimal: 274 breaks 32-byte alignment (548 B) and
288 raises the conflict to 74%. The conflict is inherent to the WMMA
half16 b-fragment load pattern in this column-major layout, not a simple
stride miss. Also assessed decode fusion: the fusible overhead is only ~3%
(casts 0.2%, norms 3%), so fusion cannot close the GEMV-bandwidth decode gap.

## Changes

- Temporary stride edits to gguf_k_t16_selected_prefill.hip line 983, reverted
  (tree clean at b421ce063).

## Validation

- shared_b ffn_gate rows=512: stride 272 = 6.19 ms / 22.0 TF / conflict 48.5%;
  stride 274 = 6.99 ms / 19.5 TF (misaligned); stride 288 = 6.94 ms / 19.6 TF /
  conflict 74.2%, occupancy 7.8, MemUnitBusy 69%.
- Decode fusion target inventory (graph body, per layer): 4 bf16<->f32 casts
  around the f32 QK-norm (0.2% of decode), rmsnorm/add_rmsnorm (3%), KV append
  (0.1%), gate_mul/silu (0.2%). A bf16-input QK-norm variant already exists
  (gguf_split_qgate_..._qk_bf16_f32_weight) but eliminating the casts buys
  ~0.2%. GEMV is 80.8% of decode and memory-bound (~90% roofline).

## Next

- Projection: the remaining lever is a conflict-free XOR-swizzled WMMA LDS
  layout (the half16 b-fragment spans 8 banks; a plain stride cannot remove
  the overlap) and/or activation tiling to cut the per-column-block global
  re-reads (MemUnitBusy 71%). Both are substantial kernel-rework, not tuning.
- Decode: fusion ceiling ~3%; the +10% gap is GEMV bandwidth (199 vs 221
  GB/s), micro-tuning space already searched/rejected. Hot-path Python is
  0.344 ms/step (negligible; decode is GPU-bound).
