# EAGLE-4 graph verify device-route gap: corrected root-cause characterization

## Summary

Follow-up to 9f4049f90 (graph verify integration, cycle wall -10%). Investigated
why the graph replay's device compute (~125 ms) exceeds the eager verify's synced
device compute. The first hypothesis (graph forced a slower per-row attention
route) was WRONG and is corrected here by measurement.

What the measurements actually show (gfx1151, Qwen3.8-27B-Q4_K_M, n_draft=2, short
prompt ~100 tokens, median per cycle):

1. Graph replay device compute is real, not a draft confound. With an explicit
   `device_synchronize()` after the device-resident draft step (draining pending
   draft work), graph `submit_ms` (the blocking `launcher.launch()`) is still
   124.7 ms, readback 0.29 ms. So ~125 ms is genuine verify device time.

2. The staged full-attention chain — the route the graph uses — is FASTER than
   the eager short-context shared-cache owner, not slower. Same-process eager A/B
   (`/tmp/full_attn_route_ab.py`, sync_stage_timings):
   - shared-cache owner (decode_row_scratches=None, eager short-context default):
     layer_total 95.4 ms, full_attn 40.9 ms, linear_attn 54.8 ms.
   - staged chain (forced per-row views, the graph's route): layer_total 66.3 ms,
     full_attn 17.0 ms, linear_attn 49.3 ms.

3. Therefore the gap is NOT route selection. The graph captures the fast staged
   route, yet replaying it costs ~125 ms vs ~66 ms layer_total (+~5 ms lm_head)
   when the same route runs eagerly — a ~50 ms graph-replay discrepancy that is
   not yet attributed. Candidate causes: a kernel variant frozen at capture time
   that differs from eager dispatch, capture-time memory layout
   (scratch_row_start=0, bucket-sized buffers), or HIP graph-replay overhead on
   gfx1151 for this graph structure.

Code facts confirmed along the way:
- `_eager_native_row_views` returns (None,None) for BF16 KV + context < 1024, so
  eager short-context uses the shared-cache batched owner; the graph always
  passes device-driven per-row views (`_dynamic_native_decode_row_scratches`).
- Those graph views DO set `position_host = start+row` (capture-time), so
  `_staged_full_attention_rows_ready` resolves True for short buckets and the
  graph takes `staged_dense_full` -> `_run_full_attention_attn_chain_rows_exact`.
- `staged_dense_linear` is identical for both routes (linear_attn ~49-55 ms).
- Split-decode threshold default is 1024; the short bucket (~128) is below it, so
  `full_attention_prefused_ready` / `chain_dense_next_rms` are not disabled by
  context. Entry-point `use_wmma_prefill` defaults False.
