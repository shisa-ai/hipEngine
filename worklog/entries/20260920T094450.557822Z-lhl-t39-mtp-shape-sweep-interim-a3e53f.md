# Task 39 interim: MTP stops at the boundary, and the in-window loss is a target-graph bucket miss

## Summary

Interim result for task #39, from the MTP arm of a shape sweep on current HEAD
`ef78a3e39`. Two findings, one of which reframes the workstream.

**The MTP-vs-AR shape sweep, default window (MTP arm, one server process):**

| shape | prompt tokens | decode tok/s | TTFT | effective_route | MTP out | coverage |
| --- | --- | --- | --- | --- | --- | --- |
| 512 | 517 | 20.41 | 1767 ms | `speculative_mtp` | 127/128 | 0.992 |
| 1024 | 945 | 18.21 | 2878 ms | `speculative_mtp` | 77/128 | 0.602 |
| 2048 | 1804 | 11.40 | 4547 ms | `default` | 0 | -- |
| 4096 | 3530 | 11.04 | 8732 ms | `default` | 0 | -- |
| 8192 | 6972 | 11.75 | 17930 ms | `default` | 0 | -- |

Runs are reproducible to under 0.3% between repeats.

**Finding 1: the falloff is a cliff, and the smooth part is below the boundary.**
MTP does not degrade gradually past 1,023; it stops. Coverage is 0.992 at 517
tokens and 0.602 at 945 -- both *inside* the qualified window -- and then 0 beyond
it. So the interesting degradation is the in-window one, and the boundary is a
discontinuity rather than the end of a slope.

**Finding 2: the in-window loss is a target-graph context bucket miss, not the
adapter window.** The harness records the server's per-cycle fallback counts, and
they name the constraint directly:

- shape 1024 (945 tokens, coverage 0.602): `speculative_cycles=23`, accepted 54,
  rejected 12 (81.8% acceptance), `fallback_event_counts = {'no_provider': 1,
  'target_graph_context_bucket_miss': 49}`.
- shape 2048 (1804 tokens, coverage 0): `fallback_event_counts = {'no_provider':
  127, 'target_context_k0': 1}`.

At 1804 tokens `target_context_k0` fires **once** -- that is the adapter's
1,023-token admission window refusing the row, which sets `candidate_budget = 0`
and leaves the row with no provider for its whole life. The 127 `no_provider`
events are the consequence of that single decision, not 127 separate faults. So
`no_provider` is a *symptom* label and must not be read as the cause.

`backend_k0_fallback`, which the harness reports as the shape's `decision_reason`
beyond the boundary, is also derived rather than diagnostic:
`hipengine/server/api.py:16378` computes
`backend_k0_fallback = (selected_route == _SPECULATIVE_MTP_BATCH_ROUTE and not used)`,
i.e. "the MTP route was selected but produced zero tokens". It says nothing about
why. The reason is the row-level `target_context_k0`.

Consequently the lever for in-window coverage is **`target_graph_context_bucket_miss`**
(49 of 50 fallback events at 945 tokens), which is a target-graph bucket-geometry
question, not an admission-window question. That is the concrete answer to task
#39's "which remaining work buys speed": widening the adapter window cannot help
in-window coverage at all, because the adapter is not what is declining there.

**Two defects in this measurement, both caught and corrected.**

1. *The "forced window" arm was a no-op.* `/tmp/t17-env.sh` runs
   `exec env -i ...`, which clears the environment, and forwards only
   `HIPENGINE_HIP_ARCH` and `HIPENGINE_MTP2_OUTPUT_SPANS`. The
   `HIPENGINE_MTP2_MAX_CONTEXT_TOKENS=8192` set for the forced arm was therefore
   stripped before reaching the server, and that arm reproduced the default arm
   exactly (11.40 against 11.40 at shape 2048). I nearly recorded "raising the
   window changes nothing" as a finding; it would have been an artifact of my own
   harness. `/tmp/t39-env.sh` now forwards the variable, and the corrected sweep
   runs it.
2. *The first sweep had no AR control.* `gguf_mtp_server_pair_bench.py` runs one
   arm per invocation, selected by `BENCH_EXTRA_JSON` (`{"speculative_mtp": false}`
   for AR); "pair bench" means the pair is produced by two invocations, not by one.
   Task #39's acceptance criterion requires a true same-protocol AR baseline, so
   both arms now run against the same server process.

Until the corrected sweep lands, the 18.21 -> 11.40 step across the boundary still
confounds "lost MTP" with "longer context costs more attention per token". The
routing blocks show MTP contributed nothing beyond the boundary, which bounds the
confound, but the AR arm is what settles it.
