# Gemma 4 gfx1100 partial rotary and K-to-V kernels

## Summary

Adds the two remaining Gemma 4-specific GPU primitives the gfx1100 layer forward
needs: a split-half partial rotary with a per-token doubled angle table, and the
`attention_k_eq_v` raw-K-to-V copy. Both are new kernels rather than reuse of the
Qwen3.5 family, for two reasons that are load-bearing rather than cosmetic.

**The only standalone partial-rotary wrapper in the tree is FP32.** Gemma 4 shares
the attention and KV-write kernels with Qwen3.5, and those are BF16-only
(`hipengine_qwen35_paged_full_attn_decode_context_bf16_spans`,
`hipengine_qwen35_write_paged_kv_bf16_spans` — no F32 variant exists). A BF16 layer
forward therefore needs a BF16 rotary. The fused alternative,
`qwen35_head_rmsnorm_partial_rotary_f32_bf16`, applies the Gemma-2 `normed * (1 + weight)`
norm, which is the wrong convention for Gemma 4 (see the prior norm entry).

**Gemma 4's rotated elements are not a contiguous prefix.** HuggingFace builds its
table as `emb = cat(freqs, freqs)` and applies `rotate_half` over the full head width,
so element `i` pairs with `i + head_dim // 2`, and on global layers only the first
`rope_angles` pairs carry a real inverse frequency — the remaining pairs get exactly
zero, which drives cosine to one and sine to zero. The rotated set is therefore
`[0, rope_angles) ∪ [head_dim // 2, head_dim // 2 + rope_angles)`, with a gap between
the two spans. Calling the Qwen3.5 kernel with `rotary_dim < head_dim` would rotate a
contiguous prefix and silently corrupt the tail, so the wrapper rejects
`rotary_dim != head_dim` rather than accepting a plausible-looking wrong value.

`gemma4_partial_rotary_kernel` is templated on `scalar_t` with BF16 and FP32
instantiations. The FP32 entry point exists so the kernel can be checked against the
reference rotation at f32 precision, where a mismatch is unambiguous; the BF16 entry
point is the production path.

`gemma4_k_to_v_kernel` implements `attention_k_eq_v`. Gemma 4 global layers have no
`attn_v.weight`; V is the **raw K projection**, taken before `k_norm` and before the
rotation. The reference confirms the ordering (`value_states = key_raw`, then
`key = gemma4_rmsnorm(key_raw, k_norm, eps)`, then rope applied to `key` only), so the
copy must run on the pre-norm pre-rope tensor.

### Bug found and fixed during the unit

The first version of `gemma4_partial_rotary_kernel` computed one row stride,
`(token * (num_q_heads + num_kv_heads) + head) * head_dim`, and used it for both
buffers. Query and key are **separate** buffers with their own head counts, so the
key writes ran past the end of the key buffer and the query reads were offset for
every head but the first. The f32 reference comparison caught it immediately — head 0
matched and everything after was wrong. Each buffer now uses its own row stride
(`heads_in_buffer`). This is the failure mode that would have produced a
plausible-looking but wrong layer forward, so the f32 exactness check earns its keep
as the primary test in this unit.
