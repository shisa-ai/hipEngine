# gemma4 gfx1151: the decode shape was running half the threads the staging loop was written for

## Summary

`kDimGroups` was a single `constexpr` shared by both builds of the full-layer
kernel. `kWaves` is `kColumnGroups * kDimGroups`, so with the decode shape's
`kColumnGroups` of 1 against the prefill's 2, the shared 2 gave the decode build
**64 threads where the prefill build got 128** -- and the prefill's walk runs at
105-118% of the DRAM roofline while the decode's ran at 74.7%.

Making the grouping per shape, so both run 128 threads, takes the decode walk to
**87.2% of the roofline at 262,144 keys** (6.02 -> 5.16 ms). Parity is 27/27 and
the arithmetic is unchanged -- the thread count moves work between lanes, not the
order any lane accumulates in.

| keys | 64 threads (was) | 128 threads | walk gain |
| --- | --- | --- | --- |
| 16,384 | 0.55 ms (51.3%) | **0.42 ms (66.5%)** | 1.31x |
| 65,536 | 1.70 ms (66.4%) | **1.40 ms (80.4%)** | 1.21x |
| 131,072 | 3.08 ms (73.0%) | **2.91 ms (77.4%)** | 1.06x |
| 262,144 | 6.02 ms (74.7%) | **5.16 ms (87.2%)** | 1.17x |

Against the *shipped* configuration before this unit and the last one together
(64 slices, 64 threads), 262,144 goes 6.42 -> 5.16 ms, **1.244x**.

## Why 128 is the number, and not an arbitrary doubling

Two independent lines agree:

- The staging loop is written for it. `kRowStep = kThreads / kChunksPerRow` is 2
  at 128 threads and 1 at 64, and the source comment above it says "128 threads
  cover two rows per iteration and each thread walks its own key stride". At 64
  threads the decode shape was staging one row per iteration with half the loop
  it was designed around.
- A pure-read probe says the grid is the residual and the KV layout is not. Same
  bytes, same grid, only the address sequence varying: at the walk's own 32 x 64
  grid a flat contiguous read reached **101.1 GB/s** while the strided read
  reached **158.8** -- so the stride was not the cost -- and the same contiguous
  read at 1024 x 256 reached **231.0 GB/s**, 97% of the roofline. 2,048 threads
  is too few; the layout is fine. See
  `worklog/entries/20261002T203636.120453Z-lhl-gemma4-gfx1151-walk-residual-threads-04d9b2.md`.

## Changes

- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention_prefill_wmma_full.hip`:
  `kDimGroups` becomes `GEMMA4_WMMA_FULL_DIM_GROUPS`, defaulting to 2 so the
  prefill build is byte-for-byte the kernel it was. The constant carries the
  reason the split is per shape.
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention_decode_wmma_full.hip`:
  defines it to 4. Two column groups against four dim groups is the same 128
  threads the prefill shape runs.
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention_prefill_wmma_full.py`:
  `WmmaFullShape` carries `dim_groups`, `waves` uses it, and the new
  `DECODE_DIM_GROUPS = 4` sits beside `DIM_GROUPS = 2`.
- `tests/test_unit_gemma4_attention_wmma_slices.py`: the assertion that every
  shape's waves are `column_groups * 2` is replaced by one that each shape's
  waves use its own grouping, plus a test that the two shapes reach the same 128
  threads by different routes and that both group the head dimension evenly.

## Validation

- `tests/test_unit_gemma4_attention_wmma_slices.py` + selection: **62 passed,
  exit 0**. RED first: `assert 4 == (1 * 2)` on the old waves assertion.
- `tests/test_gpu_gemma4_attention_prefill_wmma_full.py`: **27/27, exit 0**. The
  thread count changed, so this is the gate that says the arithmetic did not.
- Shared memory is unchanged at 33,280 bytes for the decode shape, so the
  occupancy story is the same: one block per CU, and the extra threads are
  within that block rather than from a second one.
- Walk sweep, one full layer, tokens=1, median of 9: the table above. 16 slices
  is still the fastest at every key count, so the split target from the previous
  unit stands.
- End-to-end, `scripts/gemma4_campaign_bench.py`, same device and artifact:
  **8192 keys 28.95 -> 29.41 tok/s (1.016x)**, **32768 keys 26.53 -> 27.29
  (1.029x)**, prefill unchanged (`path parity=True`).
- Teacher-forced gate at `--prompt 8192 --prefill 4096`: `passed: true`,
  `failed: []`, `kl_max` 0.0229 against 0.05, `top1_rate` 1.0, zero flips. The
  thread count moves work between lanes rather than changing any lane's
  accumulation order, so the distribution is the same one the previous unit's
  split produced.

## Next

- **256 threads is worse, so 128 is the optimum and not a waypoint.** Setting
  `GEMMA4_WMMA_FULL_DIM_GROUPS` to 8 (`kDimPerWave` 64, `kDimTilesPerWave` 4)
  measures 7.09 ms at 262,144 keys, 63.5% of roofline against 128 threads' 5.16
  ms and 87.2% -- and worse than 64 threads' 6.02 ms as well. The constant is
  back at 4. The reason is not established; the staging loop's `kMaxIters` falls
  from 8 to 4 as `kRowStep` rises from 2 to 4, so each thread has fewer loads in
  flight, but that should be offset by the extra warps and is not.
- **The old 64-slice default would now be much worse.** At 128 threads, 64 slices
  measures 9.92 ms against 16 slices' 5.16 at 262,144 keys -- 1.92x, where at 64
  threads it was 1.07x. The two fixes interact: more threads per block makes the
  block count target relatively smaller. That the split was corrected first is
  what kept this from being a regression.
- 87.2% leaves ~13%. The probe reached 97% at 1024 x 256, so the remaining gap is
  not thread count and not the KV layout; it is the walk's per-tile structure.
  Untested.
- The decode's non-attention floor is ~33.9 ms of a 262,144-key token, 50%, and
  is characterized separately (see the campaign doc's decode attribution).
