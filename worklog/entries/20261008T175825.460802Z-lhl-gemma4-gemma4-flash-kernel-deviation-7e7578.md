# Closed: the decode flash route receives no production-only inputs

## Summary

Closes the second of the two mechanisms left open by
`worklog/entries/20261008T175723.624342Z-lhl-gemma4-gemma4-flash-kernel-deviation-a549c9.md`
-- that the kernel-level diagnostic might be blind to an input the production
route actually receives, which would make the model-level divergence a defect
rather than amplification. It is not: there is no such input.

Three checks, all against the decode route specifically (the prefill AOTriton
path is a different kernel and does take a causal flag instead of a mask, which
is where the "reads no mask" docstring belongs):

- **The decode ABI takes a mask, not a trimmed view.** Both symbols are
  `(query, key, value, keep_mask, out, tokens, num_heads, num_kv_heads,
  head_dim, scale, stream, keys, split_workspace, split_slices)`. The 11th
  parameter the battery passes as a literal `0` is `hipStream_t` -- the default
  stream -- not a live-spans pointer or a window. The window reaches the kernel
  as mask columns, and both arms of every model-level run receive the same
  buffer.
- **Admission is shape-only.** `flash_admits` tests `tokens == 1`, a valid GQA
  ratio, and `(head_dim, ratio) in ((256, 2), (512, 8))`. It has no mask, window,
  or density condition, so a windowed or holed mask is admitted in production --
  which means the battery's `window` and `holes` cases are not a synthetic
  stand-in for production but the production regime itself, and they agree to
  4.7e-7 .. 9.1e-7 like every other case.
- **The model-side route selection adds no mask input.** The only production
  caller (`hipengine/runtime/gemma4_decode_graph.py:555`) branches on shape and
  slice count alone.

So the amplification conclusion stands without that caveat: the same ~1e-6
attention difference, on the same inputs, is amplified by the model as it stands
now far more than it was on 2026-09-30, and the metric is non-monotone in the
flash layer count. Nothing in the route's inputs differs between the arms.
