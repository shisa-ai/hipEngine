# The WMMA prefill difference compounds with depth rather than breaking

## Summary

Checkpoint on
`worklog/entries/20260927T211523.189346Z-lhl-the-wmma-prefill-kernel-is-exonerated-and-the-ca-e8e55d.md`,
which exonerated the kernel and left the cause open with two live candidates: a
mis-invoked kernel (wrong `rows`, padded stride, aliased scratch) or something
else entirely. **Both are now closed, and there is no defect to find.**

## How it was resolved

Cross-process comparison cannot separate an argument difference from allocator
layout, and comparing only final logits cannot say which of the 205 dispatches
diverged. So I ran **both arms in one process**, driving the switch with
`wmma_prefill_session` instead of the env var, and captured every q8_0 prefill
dispatch's output buffer.

**Arguments are eliminated.** The shape triple `(rows, in_features, out_features)`
is identical in both arms for all 205 calls. Pointer offsets differ, but that is
allocator layout — which is exactly why the same-process run was necessary.

**The difference compounds.** Relative difference in each call's `sum_abs`:

| calls | difference |
| --- | --- |
| 0–5 | 5e-06 to 6.5e-05 |
| 18–50 | ~1e-03 to 5e-03 |
| 96–130 | ~1e-02 to 5e-02 |
| 160–204 | up to **8.02e-02** |

No non-finite outputs anywhere.

It does not appear at one dispatch. It starts at ~5e-06 in the first layers —
roughly the f16 activation narrowing the WMMA route performs against the tiled
route's f32 — and compounds smoothly across the 30 layers to 8e-02 by the last.
**That is amplification of a small per-layer arithmetic difference through a
recurrent stack, not a discrete defect.**

This is consistent with everything measured along the way, and explains why both
of my searches came back negative:

- A single bare GEMM matches to 1.1e-03 because there is nothing to amplify.
- The kernel is correct, so there was no kernel defect to find.
- The dispatch feeds both routes the same shapes, so there was no invocation
  defect to find.
- The route is simply a **different arithmetic path**, and the network amplifies
  it as far as its depth allows.

I spent two iterations looking for a bug that does not exist. The measurement
that settled it took one same-process run.

## What this does and does not change

**The revert stands.** The gate is the binding criterion and it still fails at
`--prefill 256` (kl_max 1.60 against 0.05, 6 top-1 flips in 255 rows). A
compounding difference is not less of a problem than a discrete one; it is just
harder to attribute.

What changes is the question. It is no longer "what is broken" but "at which
shapes does a compounding difference stay inside the gate". The evidence already
points at block boundaries rather than row counts: a 1024-row prefill is two full
512-token blocks and passes, a 256-row prefill is one partial block and fails,
and a direct 512-row comparison landed at 3.9e-06.

## Changes

- `scripts/gguf_q8_0_prefill_sameproc_ab.py` — the same-process A/B with per-call
  output capture. This is the instrument that resolved it; it generalizes to any
  two-route comparison where cross-process layout noise is a confound.
- `benchmarks/results/2026-09-28-gemma4-wmma-dense-prefill-short-row-divergence.json`
  gains a `same_process_ab_resolves_it` section and a rewritten `next`.

No production code changed, so no promotion gate applies.

## Validation

- Same-process execution removes allocator layout as a variable; the argument
  check is therefore meaningful rather than noisy.
- Every dispatch is captured, so the growth curve is not an inference from a
  final-logit comparison.
- The curve is smooth and monotone with depth, which is what distinguishes
  amplification from a defect; a defect would show as a step at one dispatch.
- The 512-row and 256-row gate results come from the campaign evaluator on its
  own thresholds.
