# Root cause: expert group kernels were given scratch capacity as the live lane count

## Summary

The Gemma 4 GPU fault is fixed. `gemma4_experts_forward_bf16` set
`lanes = scratch.total_lanes` — the scratch buffer's *capacity* — and passed that
to the group-scatter kernels as the number of live lanes. The runner sizes the
expert scratch once for `max_block` and then pushes single-token decode steps
through it, so a decode step announced 64 lanes where only 2 had been written.
The kernels walked the 62 unwritten lanes, indexed with uninitialized expert ids
and offsets, and read outside every expert buffer. The device raised an SQ
privilege fault (`sq_intr: type 2, priv 1`) it never recovered from, so the next
synchronizing call blocked forever with no error reported.

`lanes = tokens * top_k` is the fix, where `tokens` is already narrowed to
`rows`.

## Changes

- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_experts.py`: `lanes` is now the
  live lane count for the call rather than the scratch capacity.
- `tests/test_unit_gemma4_gpu_kernels.py`:
  `test_experts_forward_runs_a_narrow_block_through_a_wide_scratch`,
  parametrized over a wider and a much wider scratch than the block. Every
  previous expert test sized the scratch to exactly the block width, which is
  why none of them could see this.

## Validation

- RED/GREEN: the new test exits 124 (timeout — the hang) with the fix reverted
  and 0 with it applied.
- `pytest tests/ -k gemma4` — 156 passed, exit 0.
- `Gemma4Runner.forward()` on the GGUF fixture: prompt forward plus 24
  incremental decode steps completes at position 25 and exits cleanly. Before
  the fix the same loop wedged the device within 1-4 steps.
- `dmesg`: no new `sq_intr` faults during the post-fix run.

## The fault, and why it took this long

Four properties made it expensive to localize:

1. **The device does not report it.** No exception, no fault message on stderr.
   The only record is `amdgpu ... sq_intr: error, detail 0x00000000, type 2,
   priv 1` in `dmesg`, which I did not read until late. Read `dmesg` first when a
   GPU call blocks without an error.
2. **The traceback names an innocent call.** The fault is asynchronous, so the
   blocking call is whatever synchronizes next — a `hipFree`, then a `hipMemcpy`.
   I twice "fixed" the reported call site. Removing the per-call `free()` was
   correct on its own merits and moved the block without changing the fault,
   which was the signal that it was a symptom.
3. **Every test passed.** The fixtures sized the scratch to the exact block
   width, so the capacity and the lane count were always equal and the bug was
   unobservable. Coverage that cannot distinguish two configurations the
   production path uses does not cover the production path.
4. **The repro is a capacity mismatch, not an operation.** The fault needed a
   *narrower block through a wider scratch*, which is only what the runner does.

## The measurement that found it

Same call, same weights, same rows=1, differing only in the scratch's declared
capacity:

| scratch `tokens` | `total_lanes` | rows | result |
| --- | --- | --- | --- |
| 1 | 2 | 1 | passes |
| 32 | 64 | 1 | hangs |

That single axis isolated it. The weight type was a red herring — the dense bf16
path faults identically, which ruled out quantization and pointed at the group
kernels rather than the projection.
