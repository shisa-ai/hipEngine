# the refused pragma unroll 2 is inert: the compiler already interleaves those two keys

## Summary

Two entries in this tree name pass 1's refused `#pragma unroll 2` as an open
thread. One says "the compiler's own 'loop not unrolled' warning on pass 1's
`#pragma unroll 2` is the open thread, since that interleave was written
deliberately and is not happening". The other withdrew the thread on a bad test:
it changed the pragma to a full unroll, saw the warning count stay at 2, and
concluded the warning was about something else.

**The count stays at 2 because there are two instantiations.** Changing the
pragma to `unroll 1` takes it to zero, and the warning's own location is the
prefill kernel, not the tiled one:

```
# with `#pragma unroll 2` at line 264:   2 warnings, "loop not unrolled", :182:17
# with `#pragma unroll 1` at line 264:   0 warnings
```

So the warning really was about pass 1, and the interleave really was not
happening. That looked like the answer.

**It is not. Writing the two keys out explicitly, so both keys' loads issue before
either key's reduction, changes nothing:**

| case, 2048 tokens | `#pragma unroll 2` (refused) | written out (0 warnings) |
| --- | ---: | ---: |
| swa 256d window=1024 | 45.95 ms | 46.50 ms |
| swa 256d window=0 probe | 77.67 ms | 77.23 ms |
| full 512d window=0 | 131.70 ms | 129.74 ms |
| the model's 30 layers | 1807.2 ms | 1811.3 ms |

Both arms in one session, 5 iters and 2 warmups. The differences are inside the
noise in both directions and the totals differ by 0.2 percent.

**The conclusion is that the compiler was already interleaving those iterations.**
It declined to *unroll* the loop -- that is what the pass-failed diagnostic
reports -- but its scheduler had the two keys' loads and reductions overlapped
anyway, which is the only thing the pragma was there to buy. A refused
transformation is not the same as an unachieved schedule, and this tree spent two
entries treating them as the same.

The change was reverted. It added 57 lines for no measured effect, and the
logits it produced are identical either way, so there is nothing to keep.

## What this closes, and what it leaves

It closes the shuffle chain as the exposed latency. Pass 1's per-key reduction is
a 5-deep `__shfl_down` chain and the obvious reading was that serializing two
such chains per warp was the stall. It is not: with the chains demonstrably
overlapped the kernel does not move.

That leaves the attention kernel at 464 GFLOP/s against an fp32 FMA ceiling near
25 TFLOP/s -- about 2 percent -- with three structural explanations now closed by
measurement rather than argument:

| explanation | probe | result |
| --- | --- | --- |
| paying for K/V bytes | `--dtype f32`, 2x bytes, same arithmetic | 1.08-1.14, not traffic-bound |
| walking masked columns | the causal-tail trim | real, and spent: -17.9% of the 30 layers |
| a refused unroll on pass 1 | write the interleave out | 0.2%, inert |

The kernel is issue- or latency-bound for a reason none of those three reaches,
and the next probe should be the one that separates them: `--mask zero` runs the
same shapes with an all-zero keep-mask, which removes every K/V load while
leaving the key loop and the reductions intact. That is a diagnostic, not a
claim, because it also removes the work inside the masked branch.
