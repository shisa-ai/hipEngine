# iu8 sparse exact repair is a fixed-grid over-launch, not a proportional cost

## Summary

A rocprofv3 kernel trace of the production prefill window at risk multiplier 4.0 and
1.0 settles the question the previous unit left open. The repair pass costs
**4808.702 ms at 4.0 and 4844.580 ms at 1.0** - a 0.7% difference with the tighter
multiplier marginally *slower*. Tightening 4.0 -> 1.0 cuts the repaired row share
3.40x, so **the repair kernel's time is independent of how much it repairs**. The
launch geometry shows the mechanism directly: every repair kernel uses a large fixed
one-dimensional grid that is byte-identical at both multipliers.

The fixed-cost anomaly is real and the launch-geometry unit is worth building. The
recoverable time is **~3394 ms, 5.2% of the prefill window**, and the fixed sweep is
waste at every multiplier, so that is a lower bound.

## Changes

No kernel was written, no default changed, nothing promoted. This unit produced the
deciding measurement and the artifact that carries it.

- `scripts/qwen4exp_repair_trace_sum.py` - sums repair and risk-owner kernel durations
  from a rocprofv3 kernel trace. `--kernel-trace` emits
  `Start_Timestamp`/`End_Timestamp` rather than a duration column, so duration is
  computed; a first version that looked for `DurationNs` silently matched nothing,
  which is recorded here because the same trap will catch the next reader.
- `benchmarks/results/2026-10-04-qwen4exp-repair-launch-geometry/artifact.json`.

## Validation

### The measurement

Production profile, `code-p4096`, chunk 1024, JIT warmed outside the profiler with
`--require-cached-build` plus a precomputed compiler-version file so no `hipcc` ran
under it.

| | MULT 4.0 | MULT 1.0 |
| --- | ---: | ---: |
| total kernel time | 65.068 s | 65.358 s |
| total launches | 85696 | 85696 |
| **repair total** | **4808.702 ms** | **4844.580 ms** |
| repair share of window | 7.39% | 7.41% |
| risk owner total | 21188.779 ms | 21181.150 ms |
| risk owner share of window | 32.56% | 32.41% |

Both arms are 0.45% apart in total kernel time, and the tighter multiplier is the
*slower* of the two. **No kernel-level effect of the multiplier change is detectable.**

Per family, MULT 4.0 / MULT 1.0:

| family | 4.0 ms | 1.0 ms | launches |
| --- | ---: | ---: | ---: |
| `gguf_q4_k_..._sparse_exact_repair_bf16` | 2107.456 | 2125.251 | 1504 |
| `q5_1_..._sparse_exact_repair_row_publish` | 2069.181 | 2081.321 | 1376 |
| `q8_0_..._sparse_repair` | 390.625 | 396.181 | 160 |
| `gguf_q5_k_..._sparse_exact_repair_bf16` | 241.440 | 241.826 | 32 |

### The mechanism, in the launch geometry

| kernel | grid | workgroup | identical at both multipliers |
| --- | --- | ---: | --- |
| q4_k gate/up repair | 131072 x 1 | 128 | yes |
| q5_1 down repair | 131072 x 1 | 128 | yes |
| q8_0 repair | 524288 x 1 | 128 | yes |
| q4_k risk owner (contrast) | 1280 x 800 | 128 | yes |

The repair kernels are launched over a **capacity-shaped** grid, not over
`risk_count`. The gate/up repair alone dispatches 131072 blocks x 1504 launches =
**197.1 million blocks** across the window, and the same grid is dispatched when
3.4x fewer rows are flagged - so the blocks whose index exceeds `risk_count` must be
returning immediately. The cost is block dispatch and index scan, not repair work.

The risk owner, by contrast, uses a two-dimensional 1280 x 800 grid sized to
row-tiles x column-tiles, which is its natural shape, and is likewise flat across
multipliers - as expected for a kernel that always covers the full padded row space.

### The prize

4808.702 ms x (1 - 1/3.40) = **3394 ms = 5.2% of the prefill window**, using the
3.40x repaired-row reduction previously measured for the 4.0 -> 1.0 tightening. This
is a lower bound: the fixed sweep is waste at every multiplier, so a grid that tracks
`risk_count` would also cut the 4.0 arm's cost, not just the 1.0 arm's.

### Correction to a prior record

The previously recorded **359 ms saving** from the risk-multiplier promotion
4.0 -> 1.0 is **not visible in kernel time**. Both arms are flat in the repair
families, flat in the risk owner, and flat in the window total - with the tighter arm
290 ms slower. Whatever produced that figure is outside the traced kernel set or is
noise. The promotion to 1.0 stands on its numerical-gate margin (3.3-6.4x, with a
274x improvement on the exact scope that rejected a prior candidate), **not on a
demonstrated speed win**, and it should be recorded that way from here on.

## Next

Write the proportional-grid repair. The change is to launch
`ceil(risk_count / rows_per_block)` blocks instead of the fixed capacity grid, with
`risk_count` read from the device counter the repair kernels already receive. That is
a host-side launch-geometry change plus whatever guard the kernel needs to handle a
grid smaller than its capacity, not a new kernel.

First measurement after that: re-run this same trace at both multipliers. Success is
the repair total falling proportionally with the repaired-row count instead of
staying at 4808 ms, with the state/logits/KV hashes unchanged - the repair is an
exactness path, so a bit-identical result is the correctness gate, not a numerical
envelope.

## Limits

- One host (gfx1151 APU, **not** the gfx1100/W7900 default hardware), one model, one
  quant, one case (`code-p4096`), one execution profile. No absolute rate here is
  comparable to a W7900 row.
- The profiled run is serialized by rocprofv3, so absolute durations are not
  wall-clock prefill times. The 4.0-vs-1.0 comparison is valid because both arms are
  profiled identically.
- The 3.40x repaired-row reduction is carried over from the previous iteration's
  measurement, not re-derived here.
- No correctness gate applies to this unit: no arithmetic changed and no default was
  modified.
