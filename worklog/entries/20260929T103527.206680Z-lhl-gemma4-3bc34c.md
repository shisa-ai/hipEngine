# P6: fuse the dense gate/up projections into one resident weight

## Summary

P6's gate/up half is implemented. The dense MLP's two projections — which read
the same normalized hidden state and are numerically separable — now live in one
resident weight and one launch, and the dense path uses the registered fused
GeGLU instead of the split form that existed only because the artifact stored
the tensors separately.

The artifact premise was checked before any code moved:
`gemma-4-26B-A4B-it-UD-Q4_K_XL.gguf` carries 658 tensors with separate
`blk.N.ffn_gate.weight` and `blk.N.ffn_up.weight` and **no** non-expert
`ffn_gate_up`, so the fusion applies as written rather than being already done.

The layout needed no reblocking. Both tensors are `(2112, 2816)` Q8_0,
6319104 bytes each, `byte_shape (2112, 2992)`; 2992 = 88 rows x 34 bytes, so
Q8_0 blocks are row-contiguous and `gate_raw + up_raw` **is** the fused
`(4224, 2816)` / 12638208-byte storage. The synthesized `GGUFTensorInfo`
differs from the head member only in name, the leading shape dim, and the byte
counts.

The CPU-reference oracles were deliberately left alone. `Gemma4LayerPointers`
is not referenced anywhere under `cpu_reference/`; those modules declare their
own `ArrayLike` dataclass and read the artifact arrays directly, so a GPU-side
resident-layout change does not touch them — and they stay a genuine cross-check
of the fused path instead of being rewritten to match it.

## Changes

- `hipengine/loading/gemma4_gguf_device.py`: new
  `materialize_fused_gguf_device_weight(reader, specs, ...)`, exported. It
  validates that members share layout, quant key, ggml type, `in_features` and
  bytes-per-row (naming the offending slot), concatenates their raw blocks along
  axis 0, asserts the result has the expected fused `byte_shape`, and uploads
  once. The fused spec's `source` is synthesized because the artifact stores the
  members separately; nothing resolves the synthetic name back through the
  reader, and the quantized linear dispatch keys only on `spec.layout` and
  `spec.quant_key`.
- `hipengine/runtime/gemma4.py`: `_GATE_UP_FUSION` names the fused triple;
  `_SLOT_TO_FIELD` drops `ffn_gate`/`ffn_up` with a comment explaining why;
  `_PROJECTION_FIELDS` carries `mlp_gate_up_proj` in their place; `_build_layer`
  materializes the pair fused and still reports either slot missing by name
  rather than defaulting to a split projection.
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_layer.py`:
  `Gemma4LayerPointers.mlp_gate_proj`/`mlp_up_proj` become the single
  `mlp_gate_up_proj`; scratch drops `dense_gate`/`dense_up` for one
  `dense_gate_up` of `rows * 2 * dense_intermediate`; the dense branch makes one
  `gemma4_project` at `2 * dense_intermediate` and calls
  `gemma4_gelu_tanh_mul_bf16`, the same form `gemma4_experts.py` uses.
  `gemma4_gelu_tanh_mul_split_bf16` loses its only caller.
- `docs/REFACTOR.md`: new entry recording the now-callerless split wrapper, its
  removal order (wrapper before HIP symbol) and its clearing condition.
- Tests: `test_unit_gemma4_gguf_device.py` gains three fusion tests (member
  compatibility, mismatch rejection by name, and device byte identity against a
  fresh concatenation); `test_unit_gemma4_gpu_kernels.py` and
  `test_unit_gemma4_weight_geometry.py` build the fused pointer from
  `np.concatenate([gate, up], axis=0)`, and the geometry test now asserts one
  call at `2 * width` per layer while the down projection still reads `width`.

## Validation

- `tests/test_unit_gemma4_gguf_device.py` — **11 passed**, including the new
  `test_fused_blocks_are_the_members_bytes_in_order`, which compares the device
  buffer against a fresh concatenation of the reader's byte views. That is the
  whole claim behind fusing: the concatenation *is* the fused storage.
- `tests/test_unit_gemma4_weight_geometry.py` — **5 passed**. This drives
  `load_gemma4_device_weights` -> `Gemma4Runner` -> the real
  `gemma4_layer_forward_bf16`, so the loader, the fused weight, and the single
  launch at `2 * width` are exercised together.
- `tests/test_unit_gemma4_gpu_kernels.py` — **passed** (exit 0), including
  `test_layer_forward_matches_the_reference`: the fused layer's output matches
  the CPU reference, which is the arithmetic check that matters.
- Every other `tests/test_unit_gemma4_*.py` file passes. Two do not complete,
  and **both behave identically with these changes stashed**, see Next.
- `python3 scripts/docs/check_docs.py` — 151 documents valid, 46 pre-existing
  `owns:` warnings in untouched files.
- Structural launch effect, arithmetic rather than a benchmark row: two
  projections become one per dense layer block, so 180 launches at 1024 tokens
  and 720 at 4096 under the 512-token prefill block. No row is claimed for this
  until it is measured.

  `test_unit_gemma4_generate.py` aborts and `test_unit_gemma4_runner.py`
  completes only 2 of 11 tests. A minimal reproduction loads the fixture in
  0.07 s and the runner in 0.01 s, then stalls 60 s+ inside
  `copy_device_to_host` (`hip.py:114 memcpy`) called from `_forward_block_inner`
  right after `launch_gguf_linear(head, ...)`. Re-running the same reproduction
  with all six changed files stashed to HEAD reproduces the identical stall at

  failing test files: `_forward_block_inner` returns early when `needs_logits`
  is false, so anything that only counts launches (the prefill census) runs,
  while anything that needs the next-token distribution — `runner.forward`,
  `LLM.generate()` — stalls at the lm_head. **P6's end-to-end validation through
  `LLM.generate()` is therefore still outstanding, blocked on this.** The layer
  itself is validated against the CPU reference via `test_unit_gemma4_gpu_kernels.py`.
