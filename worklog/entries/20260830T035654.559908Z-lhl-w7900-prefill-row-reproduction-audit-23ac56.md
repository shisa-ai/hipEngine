# W7900 Qwen3.8: prefill row reproduces exactly; the phantom 154.767 aggregate was mine

## Summary

I quoted a "prefill aggregate of 154.767 tok/s over 0.0794 s" and a "+184% capability gain"
against it for most of the afternoon. Neither number is in any committed artifact, and the
script that produced them no longer exists. This audit settles which prefill numbers are
reproducible, withdraws the ones that are not, and replaces the throwaway with the committed
rollup so the question cannot recur.

## Changes

- `scripts/gguf_prefill_row_rollup.py` restructured so `aggregate()` and `drift()` are
  importable, and its output now prints exactly what the rollup publishes - the eight per-width
  rates and the C1->Cmax flatness - with the lane-weighted total printed as
  `lane-weighted ... (lane-weighted is not the published row)`. Two implementations of "the
  prefill row" is how this happened; now there is one.
- `benchmarks/results/2026-08-30-...-prefill-row.json` gains a `reproduction` block and a
  precise caveat (below). Artifact fields and their meaning are unchanged otherwise.

## Validation

**Published row reproduces exactly.** On `/tmp/he-d1v3/he-d1v3.json` the tool prints
148.891 / 154.209 / 154.187 / 153.517 / 154.061 / 154.408 / 154.588 / 154.767 and flatness
**+3.95%**, matching the artifact's `measured_tok_s.hipengine` and
`flatness_c1_to_c8_percent.hipengine` digit for digit. Row definition, now written in the
module docstring: per cell `prompt_tokens x width` against wall `width / ar.tok_s` (the cell
rate is lanes per second with one completion token per lane), per width
`mean(tokens)/mean(wall)`.

**The "aggregate" was a copy of C8.** The tool's honest lane-weighted total is **154.187**; the
154.767 I kept quoting is exactly the published C8 rate, and `0.0794 s` appears nowhere in any
artifact. Both came from a throwaway analysis script that was never committed, so
`--prior`-based "+184% grouping gain at the prefill protocol" is withdrawn: the grouped gain is
published per width (148.891 -> 149.072 at C1 through 154.588 -> 426.692 at C7, up to +176.0%)
and that is the form to cite.

**The prior's failure cause is now measured, not inferred.** `/tmp/he-d1-clean` reports
`status='failed'`, but with `exact_cells == cells == 10` at all eight widths and only
`route_expectation_passed` False. The mechanism is `server_bench.py:580`,
`expected = set(widths if expected_mtp_widths is None else expected_mtp_widths)`: omitting the
flag makes **every** width expected to engage MTP, which a one-token AR-only arm cannot do. The
artifact previously said the packet "was run with" that expectation, which reads as a passed
flag; it inherited a default. Its AR walls remain valid, so the 0.41% repeatability stays
directional rather than a two-sided band.

**Both packets are pre-promotion**, so the flat row is a legitimate capability-off baseline:
`git merge-base --is-ancestor 72a29e9ad <commit>` is false for both `a93fee18e` (prior) and
`3cbda5e9e` (current). Guards verified: default run warns on the non-`ok` prior, `--strict-prior`
exits 3 naming the reason.
