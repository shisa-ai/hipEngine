# the batched verify mtp cycle is bit exact and gives 1.37x because the moe rows are not free

## Summary

The Gemma 4 MTP cycle is **working and bit-exact**, and it is **1.37x**, not the
3.2x the forward count suggests. The gap is the finding: on a mixture-of-experts
model the rows a verify pass adds are **not** free, because each row routes to
its own experts and the MoE weight traffic is linear in rows.

`scripts/gemma4_mtp_batched_verify.py` implements the cycle and enforces the gate
that matters: **the batched cycle must produce exactly the token sequence plain
greedy decoding produces.**

```
prompt tokens      : 66
tokens requested   : 96   drafts per round: 3
exact match        : True
drafts accepted    : 66  = 0.742
tokens per round   : 3.20
greedy             : 3.60s  (26.7 tok/s)
speculative        : 2.64s  (36.4 tok/s)
speedup            : 1.37x
forwards           : greedy 96  spec 30  = 3.20x fewer
```

## Why the existing harness could not measure this

`scripts/gemma4_mtp_acceptance.py` verifies one token at a time
(`runner.forward([consumed])` in a loop), which is the right shape for measuring
acceptance and the wrong shape for measuring speed: a serial verify produces one
token per backbone forward, so it cannot beat plain decoding. Its 0.796
acceptance number was correct and is reproduced here.

The batched cycle forwards the whole draft in **one** call with
`logits_rows=len(drafts) + 1`. `Gemma4Runner.forward`'s docstring names this case
directly -- *"which is what a speculative verify pass reads"* -- and guarantees
the property that makes it legal: *"Each returned row is the same computation a
single-token forward would produce for that position: the mask is built from
absolute positions, so a row never depends on how many rows accompany it."*

## The two off-by-ones, both real bugs

1. **`drafts[0]` predicts the token *after* `token`, not `token`.** The drafter is
   fed the sampled token plus the hidden row that produced it, so its first
   output is the guess for the next position. Comparing it against the pre-verify
   logits -- which predict `token` itself -- double-emitted the token. The first
   run's output shows it: `greedy=[100, 45518, 107, ...]` against
   `spec=[100, 100, 45518, 107, 107, ...]`.
2. **Accepting every draft still needs one more row.** Row `i` is the logits
   after the forward has processed row `i`, so `drafts[i]` is tested against
   `rows[i]` and the token after `j` accepted drafts comes from `rows[j]`. With
   only `len(drafts)` rows, `j = len(drafts)` has no row to read. The verify
   therefore forwards `[token, *drafts]` and reads `len(drafts) + 1` rows, which
   also removed the need for a short-circuit path: `rows[0]` always exists, so
   the `j = 0` case needs no special handling.

`Gemma4Runner.rewind`'s docstring documents the seed contract this depends on
from the other side: *"the hidden rows of the forward that was just rewound are
still in the scratch buffer... That is what lets a caller draft from the last
accepted position after rewinding: the row that produced an accepted token is
indexed from the verify pass, not from a forward that has not happened yet."* So
`seed_row = accepted`, indexing the verify pass's own rows.

`max_logits_rows` must be raised to `drafts + 1` at construction; it defaults to
1 and the projection buffer is sized from it.

## The sweep, and the reason it plateaus

| drafts | tokens/round | accepted | speedup |
| ---: | ---: | ---: | ---: |
| 2 | 2.59 | 0.797 | 1.34x |
| **3** | **3.20** | **0.742** | **1.37x** |
| 4 | 3.52 | 0.630 | 1.31x |
| 6 | 3.84 | 0.483 | 1.13x |

Bit-exact at every value. **Three is the optimum**, and the curve turns over
because acceptance decays faster than tokens-per-round rises: six drafts buy 20
percent more tokens per round for 25 percent more rows each.

**The ceiling is the model's architecture, not the cycle.** Greedy costs 96
row-forwards for 96 tokens; at three drafts the cycle costs 30 forwards over 120
rows, i.e. **25 percent more rows to produce the same tokens.** For a dense model
that would be nearly free -- `20260915T183902` measured rows=1 at 376 us against
rows=64 at 784 us for a dense projection, so rows really are almost free there.
**For an MoE they are not: each row activates its own top-k experts, so the
expert weight traffic scales with rows while only the attention, shared-expert,
and lm_head traffic amortizes.** That is why 3.20x fewer forwards becomes 1.37x
in wall time, and it is a property of the 26B-A4B routing rather than of this
implementation.
