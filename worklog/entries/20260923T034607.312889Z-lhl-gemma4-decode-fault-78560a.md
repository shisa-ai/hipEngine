# Experts forward with GGUF weights hangs the device: minimal repro and eliminations

## Summary

Reduced the Gemma 4 GPU fault to a four-line repro: `gemma4_experts_forward_bf16`
on GGUF weights returns normally, then every subsequent device operation blocks
forever with no fault message. Ruled out the runner's memory management, the
row count, the KV path, the build cache, and the norm and linear-projection
kernels — each by a run. The composition itself is the trigger; the router logits
and router select kernels are the only uncovered steps left.

## Changes

- `hipengine/runtime/gemma4.py`: `Gemma4Runner` now owns persistent staging
  buffers and uploads into them, instead of allocating and freeing per call. This
  removes a device sync per layer per token and a use-after-free window; it did
  not fix the hang.

## Validation

- `tests/test_unit_gemma4_gguf_device.py` — exit 0, including
  `test_selected_expert_dispatch_matches_the_bf16_offset_path` on real Q4_K weights.
- `tests/test_unit_gemma4_gpu_kernels.py::test_layer_forward_matches_the_reference`
  — passes (synthetic bf16 weights).
- Standalone probes that pass: minimal `hipMemcpy` on a fresh device,
  `gemma4_router_prescale_bf16`, `gemma4_scale_bf16`, and `q_proj` / `k_proj` /
  `mlp_gate_proj` on GGUF weights.
- Standalone probes that hang after the call returns: `gemma4_experts_forward_bf16`
  at rows=1 and rows=5; the full layer forward at rows=1 and rows=5, with
  `kv=None` and with a live cache; identical under `HIP_VISIBLE_DEVICES=1`.

## Next

## The fault has a four-line repro

`gemma4_experts_forward_bf16` on GGUF weights **returns normally**, and then
*every* subsequent device operation blocks forever — no fault message, no
exception, GPU pinned at 0% / ~13 W. The blocking call is whichever device call
comes next; the traceback therefore points at an innocent memcpy.

```python
w   = load_gemma4_device_weights(GGUFReader(fixture))
run = Gemma4Runner(weights=w, capacity=32)
x   = run._stage_upload("x", np.ones((1, 256), np.float32))
out = run._stage_upload("o", np.zeros(256, np.float32))
sel = run._stage_upload("sel", np.array([[0, 1]], dtype=np.int64))
wts = run._stage_upload("wts", np.array([[0.5, 0.5]], np.float32))
gemma4_experts_forward_bf16(x.ptr, sel.ptr, wts.ptr, L.experts_gate_up_proj,
    L.experts_down_proj, out.ptr, scratch=run._scratches[0].experts, rows=1)
copy_host_to_device(probe, host_array_ptr(zeros64), 256)   # <-- blocks forever
```

This reframes the earlier entries: the `hipFree` and `hipMemcpy` tracebacks in
`20260923T02*` were the *next* device call, not the cause.

## What this is not

Each elimination below is a run, not an inference.

| Hypothesis | Experiment | Result |
| --- | --- | --- |
| Broken HIP runtime / driver | minimal `malloc`→`hipMemcpy`→`free` on a fresh device | passes |
| Degraded GPU 0 specifically | identical repro under `HIP_VISIBLE_DEVICES=1` | hangs identically |
| Runner memory management | removed all per-call `free()`; only `close()` frees now | hang unchanged |
| Mask or staging buffer size | rows=1 (1-byte mask) vs rows=5 (25-byte mask) | both hang |
| Row count | full layer forward at rows=1 and rows=5 | both hang |
| KV cache / attention ABI | layer forward with `kv=None` vs a live cache | both hang |
| Corrupt build cache | no zero-length or recently written `.so` in `~/.cache/hipengine/build` | clean |
| Norm library broken by my scale kernel | `gemma4_router_prescale_bf16` and `gemma4_scale_bf16` standalone | both pass |
| GGUF linear projection dispatch | `q_proj`, `k_proj`, `mlp_gate_proj` standalone | all pass |
| Selected-expert GEMV dispatch | `test_selected_expert_dispatch_matches_the_bf16_offset_path` | passes |
| Whole layer is broken | `test_layer_forward_matches_the_reference` (synthetic bf16) | passes |

So: the layer is sound with bf16 weights, and every GGUF primitive the expert
forward uses passes in isolation. The hang appears only when
`gemma4_experts_forward_bf16` composes them.

## Where that leaves the bisection

`gemma4_experts_forward_bf16` is the composition of, in order: router prescale
(norm lib), router logits, router select, per-expert weight scale, the selected
GEMV, and the combine. Of those, the norm-lib calls and the selected GEMV are
individually verified above. That leaves the **router logits and router select
kernels**, which come from the `qwen35` quant family and are the only steps in
the function with no standalone coverage yet. That is the next experiment.

## Correction to the previous entry

Removing per-call `hipFree` was the right change on its own terms — it dropped a
device sync per layer per token — but it was not the fix. The hang moved from
`hipFree` to the next `hipMemcpy` and stayed. Recording that so the next session
does not re-derive it.
