# Gemma 4 projections dispatch to quantized weights; a bf16 readback bug hid in the test

## Summary

The layer's seven projections now go through `gemma4_project`, which dispatches on
the weight's storage form: an `int` is a bf16 device pointer and goes to
`dense_gemv_out_bf16`, anything else is a GGUF device weight and goes to
`launch_gguf_linear`.

On the real artifact a quantized projection reproduces the NumPy reference to
**0.209%** and the bf16 GEMV to **0.287%** — the combined bf16 and Q8_0 rounding
floor. The dispatch is correct.

The tests I wrote for this were initially passing while proving nothing, because
my readback converted bf16 **bit patterns to integers**. Details below; it is the
part worth reading.

## The readback bug

My first version read a BF16 output buffer like this:

```python
raw = np.empty(rows * out_features, dtype=np.uint16)
copy_device_to_host(...)
return raw.astype(np.float32)
```

`astype(np.float32)` converts the **integer value** of the bit pattern. BF16
4.375 is the bit pattern `0x408C`, so it read back as **16524.0**.

This is a nasty failure mode because the wrong answer looks like an activation:
the numbers were in the thousands, varied plausibly across rows, and the test
compared two GPU paths that were both being misread the same way, so they agreed
*exactly* and the test passed. I only caught it by adding a NumPy reference,
which showed both GPU paths 450000% off.

The fix is a shift and a reinterpret, because the high 16 bits of a float32 *are*
its bf16 encoding:

```python
return (raw.astype(np.uint32) << np.uint32(16)).view(np.float32)
```

Two lessons worth keeping:

- **A test that compares two implementations of the same wrong thing proves
  nothing.** The quantized and bf16 paths shared the readback, so agreement
  between them was guaranteed regardless of either being correct. Every
  comparison here now has a NumPy reference on one side.
- **A "suspiciously exact" result deserves investigation, not celebration.** The
  fixture test first reported *exactly* zero difference, which I investigated and
  explained (the fixture's Q8_0 values have at most 7 significant bits, so bf16
  is lossless for them). That explanation was true and still left the readback
  bug in place, because exactness was the wrong thing to be looking at.

## Why the tolerance is tight

The fixture's Q8_0 weights are `d * q` with `d = k * 2**-5` for `k <= 5` and
`|q| <= 15`, so every value has at most 7 significant bits and is exactly
representable in bf16. On that fixture the two paths differ only by bf16 rounding
of the output, under half an ulp. The assertion is `rtol=5e-3`, not the 2e-2 I
first wrote: 2% was loose enough to pass a kernel that read the wrong layout.

There is also a check that the quantized output is not constant per row, which is
what a kernel reading one block for every row would produce — independent of the
tolerance.

## Real-artifact validation

`layers.0.attn_q`, Q8_0, 4096x2816, four rows, against a NumPy `x @ w.T`:

| comparison | relative error |
| --- | --- |
| bf16 GEMV vs NumPy | 0.228% |
| quantized dispatch vs NumPy | **0.209%** |
| quantized vs bf16 GEMV | **0.287%** |

All three at the rounding floor, which is the expected result and not a
coincidence of tolerances.

| quant | specs | ranks |

**Every rank-2 projection in this artifact is Q8_0**, and every non-Q8_0 weight is
a rank-3 stacked expert tensor. So the seven converted call sites are exercised
by the real artifact end to end, and the experts are the entire remaining
conversion — they need the selected-expert dispatch rather than a whole-tensor
linear, because a rank-3 weight is a per-expert gather.

That is the next unit.
