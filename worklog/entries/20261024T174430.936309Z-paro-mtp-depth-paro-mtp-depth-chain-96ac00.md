# PARO MTP candidate depths 1-3 with exact prefix repair

## Summary

The packed-PARO MTP2 adapter plans, drafts and verifies a candidate chain of one
to three rows instead of a fixed single candidate. The depth is resolved once,
through the existing serving policy, and the same number reaches the planner as
its desired candidate count and the adapter as its per-request intent, so no
second policy and no new flag exists.

A cycle now drafts candidates sequentially from host token ids, keeps one
provider snapshot per candidate it may have to undo, and repairs the provider to
the accepted prefix before taking the target's bonus row. Depth-one cycles are
unchanged in every observable way: same device candidate handoff, same two
provider calls, same eager route, same verify-row count, same context bound.

## Changes

- `hipengine/generation/qwen35_paro_mtp2.py`
  - `PARO_MTP2_MAX_CANDIDATE_DEPTH = 3` is the structural bound: `depth + 1`
    target verify rows and `depth` provider draft advances per cycle.
  - `register_request` stores `min(budget, candidate_budget)` instead of
    discarding the requested depth; `request_depth` exposes it.
  - `capability` derives `max_candidates_per_request`, `max_frontier_rows`,
    `target_row_buckets`, the capability key and the policy fingerprint from the
    registered depth. `graph_supported` stays true; the runner still selects
    eager.
  - `max_context_tokens = max_sequence_length`, the target's context capacity,
    with no depth term. The shared planner computes `context_room =
    max_context_tokens - context_tokens - 1` and clamps the count against it, so
    its own `- 1` is the root row's reservation; subtracting the depth as well
    reserved the whole chain twice and refused shallower tails near capacity.
    Bound: a cycle verifies the root at `context_tokens - 1` and candidate `k` at
    `context_tokens - 1 + k`, so the highest position it touches is
    `context_tokens - 1 + count`, and `_check_position` requires that below
    `max_sequence_length`. With `count <= max_sequence_length - context_tokens -
    1` the highest touched position is at most `max_sequence_length - 2`, and
    session sizing guarantees `context_tokens <= max_sequence_length - 1`, so
    the bound holds at every context. This is the same value the dense GGUF
    declaration publishes. The previous depth-one constant `- 2` was already
    conservative by two positions; the corrected value restores them at every
    depth.
  - `claims_fit` / `prepare_requests` accept `1 <= count <= depth`;
    `component_claims` reports `count + 1` target rows.
  - `propose_batch` drafts the chain: candidate 0 is the provider's current host
    token, each later candidate comes from `advance_with_previous_hidden` at
    `position + 1`, and `save_state(1 + k)` records the state after consuming
    candidate `k` for `k = 0 .. count - 2`. A device-only result leaves
    `current.token` at its sentinel, so a chained draft refuses rather than
    drafting from `-1`. Depth one keeps the device scalar handoff and takes no
    snapshot, so its per-cycle work is unchanged.
  - `_repair_provider_after_verify` replaces the single-candidate repair with the
    full accept table: `accepted == count` consumes the last candidate from the
    live draft state, `accepted == count - 1` needs no restore, and a shorter
    prefix restores `draft_snapshots[accepted]`. Snapshot slot 0 stays reserved
    for the cycle checkpoint.
  - The three advance sites that must publish a host token at depth > 1
    (`_ParoPromptPrimeSink.complete`, `consume_prompt_row`'s root row, the bonus
    advance) pass `read_token_id` from the registered depth; at depth 1 they keep
    `False`.
  - `observe_prefill_result` reserves `depth + 1` verify rows and a context
    bucket covering the highest position the cycle touches, clamped to the
    session's own capacity. The proposer capacity requirement adds `depth` rows
    through `_proposer_token_requirement`.
  - `_verify_target` declares `capture_hidden_concat` as `(batch.rows, 0)`
    instead of the literal `(2, 0)`. The verifier rejects a capture buffer
    shorter than the cycle (`capture rows outside capture_hidden_concat`) and
    the graph-commit bucket requires the leading dimension to equal the verify
    rows, so a fixed two-row shape would have refused every deeper cycle.
  - `_restore_target_and_provider` clears `draft_snapshots`, so a rollback,
    cancellation or dropped request cannot leave a stale repair point.
- `hipengine/generation/qwen35_paro.py`
  - `speculative_candidate_budget_default()` prefers two candidates, clamped
    to the plugin's declared capability and the structural bound. Explicit
    depths one and three are unchanged. The comparison used three-candidate
    capacity for every arm before selecting this preference.
  - `mtp2_candidate_depth()` is the single resolved depth; the adapter's budget,
    `speculative_desired_candidate_count`, the serving key's `candidate_budget`
    and the session's verify rows all read it.
  - `speculative_desired_candidate_count` returns the resolved depth (capped by
    `max_tokens`) instead of `1`. This is the one lever a depth comparison
    patches, and the planner still clamps against capability, output room and
    context.
  - `register_speculative_request` publishes the adapter's clamped depth on the
    row rather than the literal `1`.
  - `_ensure_session` sizes `max_batch_size` from
    `mtp2_verify_row_requirement()` and reuses a session only when it has enough
    verify rows, failing with a named reason instead of silently launching a
    too-small verifier.
- `hipengine/models/qwen35.py`: both PARO declarations raise
  `max_candidate_count` from 1 to 3.
- Tests: new `tests/test_unit_qwen35_paro_mtp2_depth.py` (62 cases) plus updates
  to `tests/test_unit_qwen35_paro_mtp2_seam.py` and
  `tests/test_unit_paro_mtp_serving_route.py`.
