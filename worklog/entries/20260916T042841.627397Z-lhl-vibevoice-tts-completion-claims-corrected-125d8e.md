# Correct five overclaims in the VibeVoice-TTS contract and the completion audit

## Summary

The VibeVoice-TTS completion audit and the contract it audits carried five claims
that are stronger than the evidence behind them. Four are corrected in place in
`docs/MODEL-VIBEVOICE-TTS.md`; the fifth is a benchmark-protocol definition that was
silently misleading. The three immutable worklog entries that made the original
claims are **not** edited -- this entry supersedes their claim language, and each
correction below names the entry it supersedes.

| # | Claim as written | Correction |
| --- | --- | --- |
| 1 | "Matches the oracle" justified by "fixture parity ... ten-seed generated-audio quality 58/60" | 58/60 is a **task-quality** gate on six English scripts, not a numerical claim. Oracle agreement is carried by fixture parity and `chain_exact`; the two are separate and are now reported separately. |
| 2 | "Quality and timing are qualified" | Qualification is **partial**. Blinded listening, held-out voices, Chinese, turns beyond 40 words, interrupted requests and mixed-length batches are required by the contract and **not covered**. Now listed explicitly. |
| 3 | Whole-suite gate: `pytest -k vibevoice` -> 130 passed, 11 skipped | That is a **scoped subset**, not the milestone gate. The gate is `uv run pytest --suite all`. |
| 4 | "Zeroing the entire LM stage yields ... 0.77 RTF ~= 1.74x, so no single-stage optimization reaches 2x" | Zeroing one stage bounds **that stage's removal** only. It does not show 2x is unreachable, because combined stage wins or a solver/step-count trade are not bounded by it. |
| 5 | Cold start compared across lanes (HIP 4.341 s vs torch 6.107 s) | `cold_start_seconds` **excludes** `weight_load_seconds`, and the lanes load at different rates. Loading-inclusive: **7.662 s vs 8.014 s = 4.4%**, not ~40%. |

## Changes

`docs/MODEL-VIBEVOICE-TTS.md`:

- **Status header** -- was stale at "milestones 1-4 closed" with a superseded
  RTF 1.868 / 1.303 comparison and an "open work is integration correctness"
  paragraph that milestone 5 closed. Now records milestone 5, the current 1.201
  retained / 1.228 verify against torch 1.336, and names the qualification gap.
- **"Executable protocol"** -- the cold-start bullet now says explicitly that the
  figure excludes weight loading, and a new bullet requires adding
  `weight_load_seconds` back before any cross-lane cold-start comparison, with the
  4.4% worked example.
- **Milestone 5 closure** -- adds a "the qualification is partial" paragraph
  listing what is not covered and why (the held-out axis is the script; the voice
  sets are fixture-pinned); separates the task-quality figure from the numerical
  claim; and replaces the `-k vibevoice` gate with `--suite all`.
- **"The speed target is not met"** -- scopes the 1.74x bound to the LM stage's own
  removal and states that it does not establish 2x is unreachable.

No runtime code changed. No artifact changed: the artifacts report
`cold_start_seconds` and `weight_load_seconds` separately, which is correct; only
the prose that read them was wrong.

## Validation

### Each correction is grounded in a file, not in re-reading the audit

- **Coverage gap (2).** `benchmarks/prompts/vibevoice-tts-quality.json` holds six
  requests -- `single-short`, `single-medium`, `single-numbers`, `two-2turn`,
  `two-4turn`, `two-long` -- all English, 1-4 turns, over two voices. Its own
  `limitations` field already states "The held-out axis is the script. Only the two
  voice sets the fixtures pin are used". The contract's gate list at "Task and
  performance gates" asks for considerably more. Both are in-tree; the audit simply
  did not compare them.
- **Cold start (5).** `scripts/vibevoice_tts_session_bench.py` measures
  `weight_load_seconds` and `cold_start_seconds` as separate fields, with the cold
  run taken *after* load ("the first synthesis after load", line 202).
  `scripts/vibevoice_tts_torch_bench.py` does the same. The recorded values are HIP
  3.321 + 4.341 = 7.662 and torch 1.907 + 6.107 = 8.014
  (`benchmarks/results/2026-09-15-gfx1151-vibevoice-tts-session-verify.json`,
  `.../2026-09-15-gfx1151-vibevoice-tts-torch-lane.json`). 8.014 -> 7.662 is -4.39%.
- **The 1.74x bound (4).** The arithmetic is unchanged and still correct, and the
  correction is to what it is taken to prove, not to the number. Against the
  retained 4.005 s warm, removing the 1.450 s LM stage leaves 2.555 s, which is
  0.77 RTF over 3.333 s of audio, and 1.336 / 0.77 = **1.74x against torch**. The
  same computation on the verification run's 4.092 s warm and 1.526 s LM gives
  2.566 s and 0.77 RTF, so the two runs agree. What the figure bounds is the LM
  stage's own removal; the contract now says so instead of generalizing it to
  "no single-stage optimization reaches 2x".

### Full-suite gate

This entry corrects *what the gate is*; it does not claim to have re-run it, and a
docs-only change cannot affect any test, so the applicable tier is document review.
What was checked:

- **`--suite all` collection succeeds with no collection errors** --
  `uv run pytest --suite all --collect-only -q -p no:cacheprovider` ->
  **17,084 tests collected in 22.81 s**, exit 0. This is the same local check the
  v0.5.0 release validation used (`20260913T055154.761550Z`), where full *execution*
  is delegated to publish CI.
- **The scoped subset result is retained and correctly labeled.**
  `python3 -m pytest -k vibevoice` -> 130 passed, 11 skipped, 0 failed. That is a
  scoped subset of the VibeVoice tests and is *not* the milestone gate; a VibeVoice
  change can break shared kernel, registry or dispatch code that `-k vibevoice`
  never collects.

A full `--suite all` **execution** was started and deliberately stopped after ~90
minutes. It was spending that time in live GPU quality tiers for unrelated model
families -- `py-spy` showed it inside
`test_live_evie_gpu_runtime_8b.py::test_8b_fp16_doc_quality_tier`, streaming an 8B
EVIE checkpoint's weights to device. Running 17,084 tests, most of them live GPU
quality sweeps for models this change cannot touch, is not the narrowest
deterministic check for a prose edit, and it holds the GPU against concurrent
work. The correction to the *claim* stands on the collection result and on the
scoped run; the milestone gate itself is the full suite, which is what the
document now says.
