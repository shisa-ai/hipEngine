# d1 teacher stall is call-count: 4th teacher_forced_logits call stalls

## Summary

The stall is NOT row length. Evidence across this iteration:

- Bisection run A: 16 x3 OK, then 24 STALL.
- Bisection run B (fresh session): 17 x3 OK, then 18 STALL.
- Bisection run C (fresh session): 18 x3 OK — a length that STALLed in run B.
- Same-tokens repeat test on d1: calls 0-2 OK (0.4-0.5 s), **call 3 (the
  4th call) STALLS**.

So on device 1 the harness's `teacher_forced_logits` exhausts some
per-session state after three calls; d0 completed 64 calls cleanly (entry
b0142a). The signature (host blocked in a readback, GPU[1] idle, device
recoverable only by process exit) plus the call-count trigger fits a
per-call state contamination in the staged exchange — the device-side wait
spins on a mailbox/flag whose state the 4th call never satisfies, while
d0's ordering happens to tolerate it. The eager schedule runs both ranks
on stream 0 (per-device default), so the contamination is in the exchange
mailbox/epoch lifecycle or the compiled host driver's flag state, not in
stream scheduling.
