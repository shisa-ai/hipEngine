# Final verification of the prefill/decode instruction and the arch compilation path; completion audit closes

## Summary

Two things in the objective were still only assumed rather than checked, and both are
now verified:

1. the explicit instruction "just make sure you are properly implementing
   prefill/decode kernels"; and
2. hardware coverage -- whether an implementation validated only on gfx1151 is
   actually *compiled* for gfx1151, given that every VibeVoice-TTS kernel lives under
   `kernels/hip_gfx1100/`.

Both check out, and (2) turned out to be an intended design rather than a gap. With
these closed, every requirement in `docs/MODEL-VIBEVOICE-TTS.md` maps to current
evidence.

## Changes

No code change. One immutable worklog entry.

## Validation

### Prefill and decode paths are the intended ones

- **Prefill uses the batched WMMA GEMM, not the per-output GEMV.**
  `rocprofv3 --kernel-trace` on the decoder region shows
  `dense_prefill_gemm_out_kernel<unsigned short, 32, 8, 16>` at 36 dispatches. The
  per-output `dense_gemv_out_kernel` does not appear in the decoder's prefill path.
  This is the shape that was fixed earlier in the lane's history: the decoder's
  ConvNeXt FFN linears had been running `dense_gemv_out_bf16` at `rows=3200`, launching
  409,600 blocks whose 256-wide tree reduction was ~100x the FMA count; dispatching
  them to the batched GEMM at `rows >= 8` took `decoder.decode` from 51.27 ms to
  10.65 ms (4.81x) and the decode stage from 1.303 s to 0.343 s.
- **Decode uses the per-output GEMV at a thread count chosen by measurement, not by
  default.** The diffusion head sets `_GEMV_THREADS = 64`
  (`vibevoice_tts_diffusion.py` line 36, "a full head call measures 2.08 ms against
  3.33 ms at 256"). The LM decode keeps the 256 default because `threads=64` there is a
  measured **1.23x** win that moves 5 of 17920 outputs by one ulp and takes the
  ten-seed generated-audio suite from 58/60 to 57/60 -- a documented rejection, not an
  oversight. The semantic encoder's `rows=1` GEMV dispatch is likewise reverted for
  quality.
- **The diffusion head is at ~84% of sustained bandwidth** (28.18 of 31.44 ms of device
  time is GEMV at ~175 GB/s), so there is no mis-implemented kernel hiding a large win.

### The arch question resolves to an intended alias, not a gap

Every VibeVoice-TTS kernel module lives under `kernels/hip_gfx1100/`, and
`kernels/hip_gfx1151/` contains only `__init__.py`. That looked like the implementation
being compiled for the wrong target, since gfx1151 is the lane the contract declares
and the lane every measurement ran on.

It is not. `kernels/hip_gfx1151/__init__.py` documents the design:

> The initial gfx1151 backend intentionally reuses the proven gfx11 HIP kernel bodies
> from `hip_gfx1100` and compiles them as native `gfx1151` code objects through
> `HIPENGINE_HIP_ARCH=gfx1151` / `--offload-arch=gfx1151`. This gives Strix Halo a peer
> backend key while keeping tuning changes separate from the source-lineage port.

So the shared bodies are compiled natively per arch, which is exactly what the
architectural invariant in `AGENTS.md` describes ("Backend tree is a peer structure").
The kernel set is not gfx1100-only and no gfx1100 execution is claimed.

### The one clause that is not met

The objective's parenthetical expectation of 2-10x is **not** met, and it is not
reachable by implementation quality on this workload:

- pooled RTF 1.228 against torch 1.336 is ~1.09x;
- zeroing the **entire** LM stage (1.526 s of 4.092 s) still leaves 2.566 s = 0.77 RTF
  ~= 1.74x, so no single-stage optimization reaches 2x;
- the diffusion head streams 123.3 GB per request against a ~0.59 s floor at the
  ~209 GB/s this host sustains, and its GEMV already runs at ~84% of that;
- the remaining identified opportunity is the per-step D2H readback at +5.56% of warm
  (ceiling 1.2358x), recorded in `docs/REFACTOR.md`.

This is stated inside the contract itself (`docs/MODEL-VIBEVOICE-TTS.md`, milestone 5
closure, "The speed target is not met"), so it is a reported finding rather than a
dropped expectation.
