# qwen38 gfx1151 R6 int8-activation/MLP prefill assessed not pursued

## Summary

R6 asked whether int8-activation (W4A8/W8A8) MLP **prefill** is worth building
for the Qwen3.8 Q4_K_S gfx1151 campaign (prefill is compute-heavy; we already
see an INT8 boost in decode). Verdict: **not pursued — no dispatchable
int8-activation prefill path exists for the dense Q4_K_S MLP on gfx1151**, and
building one is a full new-kernel unit aimed at a phase (prefill) that is not
this campaign's bottleneck.

Key findings (code archaeology, no GPU run needed):
- Dense Q4_K_S MLP **prefill** dispatches `pack8_dual_wmma_prefill_bf16_bf16_out`
  — BF16 WMMA with Q4_K weights, **no activation quantization**.
- Dense pair_silu **decode is already int8-activation (W8A8)**: the Q8_1
  activation quantizer (`gguf_q4_k_quantize_bf16_q8_1`) feeds the Q8_1x2 dp4a
  GEMV owners (`dense_dual_q8_1x2_split_weight_dp4a` serial c1,
  `dense_dual_q8_1x2_rowtile8_dp4a` native rows 2-4). The "perf boost on INT8"
  this item referenced is already captured on the memory-bound path where it
  matters.
- The only W8A8 *prefill* prototype (`gguf_q4_k_q8_1_selected_prefill`,
  hip_gfx1100) is a MoE selected-expert diagnostic microbench, not wired into
  dense dispatch and gfx1100-only. The sole registered q8_1 prefill on gfx1151
  (`selected_mmq_i128_j128_k256_q8_1_ds4_prefill_compact`) is MoE-only
  (iq3_xxs/iq4_xs).

Payoff: prefill is compute-bound (370-380 tok/s at 512/1K/4K, already beating
llama.cpp 352-368) so a W8A8 prefill could in principle help, but the topline
bottleneck is decode (~13 tok/s, memory-bound, already W8A8), and the
external's W4A8 only paid at 40-64 concurrency (+2.2-3.7% PPL) — a regime
outside this c=1-8 unified-memory campaign.
