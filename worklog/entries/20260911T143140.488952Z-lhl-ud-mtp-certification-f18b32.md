# U6: UD MTP certification unit — mechanism landed, scope pin withheld

## Summary

U6 was an unscoped gap ("UD NextN draft admission is refused"). It is now three
concrete items, two of them landed and gated. UD MTP admission is a separate
certification table keyed by the same role-manifest fingerprint as the AR
certificate, and that table is empty: no UD artifact is MTP-certified, and the
draft materializer still refuses UD MTP before any allocation.

The two blockers that made UD MTP impossible were found by relaxing the gates in
an uncommitted probe and walking the failure chain, not by reading code:

1. **Draft dtype identity.** The UD draft block is Q6_K (`eh_proj`, `attn_q`,
   `attn_output`, `ffn_gate`, `ffn_up`, `ffn_down`) with Q8_0 `attn_k`/`attn_v`;
   the plain control's expectation is Q4_K/Q8_0, so strict draft validation
   failed with 7 dtype errors. The UD signature coincidentally equals the
   Qwen3.8 native-XL expectation, but that map is selected by a caller-claimed
   `hipengine.quant.variant` and the validator already documents refusing a
   foreign file that merely coincides with it — so it is unusable here. Fixed
   with an artifact-pinned per-slot manifest resolved from the admitted preset
   identity.
2. **Accept-chain resolution.** `Qwen35GGUFTransactionalVerifier` resolves
   `dflash_accept_chain` with the *session quant identity*. That kernel is
   quant-agnostic (int32 accept buffers) and was registered for
   `w4_paro`/`gguf_ud_q3_k_m`/`gguf_q4_k_m`/`gguf_q4_k_s`; the UD
   `gguf_ud_q4_k_m` / `gguf_ud_q4_k_s` identities were missing, so the verifier
   raised `MissingKernelError` before any draft work.

With both relaxed in-process, UD MTP ran end to end on the K_M artifact and
produced `status: complete_exact` with `all_exact_greedy` and
`all_gpu_accept_match_cpu` true. No new kernel was needed: the draft's Q6_K
slots already route through `launch_gguf_linear` and the Q6_K pack8/T16 GEMV
builders.

### The K_S divergence is an AR-path outlier, not an MTP defect

Token IDs at output position 12 of `general_ja_plan`:

| lane | tokens at position 12 |
| --- | --- |
| plain `Q4_K_S` AR | `211768, 34610, 247208, ...` |
| plain `Q4_K_S` MTP | `211768, 34610, 247208, ...` (exact) |
| UD K_M AR | `211768, 34610, 247208, ...` |
| UD K_M MTP | `211768, 34610, 247208, ...` (exact) |
| **UD K_S AR** | **`99720, 5205, 180367, ...`** |
| UD K_S MTP | `211768, 34610, 247208, ...` |

The plain K_S control is `complete_exact` over the same seven prompts including
`general_ja_plan`, and its AR and MTP agree. UD K_S MTP also agrees with the
other three lanes. The only outlier is the **UD K_S AR path**, at absolute
sequence position 55 (prompt 43 + 12), well below the gfx1100 serial-route
boundary of 95, so it is not the journal/serial-row route.

This reframes the K_S blocker: it is a UD K_S **AR** correctness investigation,
not an MTP-admission gap. It is a near-tie argmax flip (all other prompts and
both repeats are exact), so it also matters for the K_S AR certificate, which
was qualified before this run existed.

Token rates in the artifact are correctness-run rates measured while an
unrelated full pytest suite was running on the host; they are not performance
claims.
