# The multi-column GDN promotion's gate: route exonerated, declaration corrected, and the q4_k_m composition is the documented out-of-envelope one

## Summary

The R02 multi-column GDN prefill promotion was verified end to end on the
`gguf_q4_k_m` production profile, and the verification produced three results
that the promotion's own record did not have.

**1. The repaired binding dispatches.** `production_gdn_multi_q4km` (empty env
override, `count_registered_dispatch=True`) reports **1350 dispatches** of
`qwen4_exp_gdn_prefill_tiled16_multi_f32`. Before the binding repair the same
probe observed **0**. The route is no longer inert in the profile whose
column-warp gate is open.

**2. The gate fails, and the failure is not this route's.** The q4_k_m
production arm fails the calibrated production envelope on one
`heldout_general_ja_speculative` row (max KL **0.05958** > 0.05, top-1
unchanged, strict margin 0.9091, top-5 overlap 1.0) and on the `prefill_last`
scope (mean KL **1.333e-3** > 1e-3). The candidate arm is the **whole q4_k_m
production composition**, not the multi-column route, so the failure cannot be
attributed to the route without a control. The control was built and run:
`production_gdn_tiled16_q4km` is the same profile with the GDN prefill owner
pinned to `qwen4exp_gdn_tiled16_prefill`, the callable the binder fell back to
before the repair. **It fails identically, and slightly worse**: max KL
**0.06645** vs 0.05958, `prefill_last` mean **1.475e-3** vs 1.333e-3, the same
five scope failures and the same single over-review row. Both arms ran 1350
dispatches of their own kernel and produced different candidate logits hashes
(`cac32441…` vs `a5e7d37e…`), while both used the byte-identical strict teacher
(`strict_logits_sha256` `e5ae994e…`, `strict_selected_token_ids_sha256`
`1b7ffc91…` — the same values the UD gates recorded). So the arms differ only
in the GDN prefill owner, and the multi-column route is **exonerated**: it is
not the cause of the q4_k_m failure and is marginally better on the tail.

**3. The failure itself is a documented, pre-existing condition, not a new
one.** `benchmarks/results/2026-09-14-q8-prefill-numerics/README.md` measured
this same composition at max KL `0.054642` with prefill-last mean/p95 also
failing, and its "Conservative Recovery" section states the decision in
advance: *"The Q4_K_M profile, model files, KV ABI and other backends are
unchanged."* The 2026-09-14 recovery zeroed the fifteen arithmetic selectors
for `gguf_ud_q4_k_xl` only. Today's run re-measures that composition on the
current tree at 0.05958 over 450 rows — the same class of result.

## What the gate also exposed: the manifest declared a kernel that did not run

Both q4_k_m arms record `candidate_manifest_sha256` **`a47225d0…`** while
different kernels dispatched underneath them. The manifest's
`prefill_rows_ge16_hk16_hv32_48_d128_layers27_47` row declared
`qwen4exp_gdn_tiled16_prefill`, but the binder installs
`HIPENGINE_QWEN4_EXP_GDN_TILE16_VARIANT=qwen4exp_gdn_tiled16_multi_prefill`,
and the runner reads that env var. One manifest hash therefore covered two
different kernels — a provenance defect in the evidence chain, of the same
class the codebase already guards against for the router producer
(*"so the runner's launch-time switch cannot disagree with the resolved
selection"*).

Cause: the GDN selection's variant was conditional on a `dpp` parameter whose
value was `quant == "gguf_ud_q4_k_xl"`. That condition is true only for the
quant that also passes `recovery=True`, and the recovery pass replaces tiled
variants **by name** before the manifest is built — so the conditional's
`dpp=True` branch never reached a manifest, and the `dpp=False` branch reached
the q4_k_m manifest unchanged. The docstring on the existing test claimed that
branch "is therefore inert"; it was inert only for the recovery quant.

Fix: the row now names `qwen4exp_gdn_tiled16_multi_prefill` unconditionally and
the unused `dpp` parameter is gone. That is safe precisely because the recovery
pass deactivates tiled variants by name — for the recovery quant both candidate
values map to the same exact owner.

## Findings that are not this unit's to act on, recorded so they are not lost

- **The shipped default is the unrecovered composition.** The model plugin
  declares `default_quant = "gguf_q4_k_m"` and an omitted profile resolves to
  `production` for it (both read from the code, not inferred). So a caller who
  loads this UD-Q4_K_XL GGUF without naming a quant gets the binder whose
  composition fails the calibrated envelope at max KL 0.0596, while the
  in-envelope recovery arithmetic is reachable only by naming
  `quant="gguf_ud_q4_k_xl"` explicitly. `docs/EXECUTION-PROFILES.md` §2.1 lists
  `qwen4_exp_gguf`/`hip_gfx1151`/`gguf_q4_k_m` among combinations whose
  production plan is "certified", and the 2026-09-14 decision to leave that
  profile unchanged predates that list. **No default was changed here**: the
  recovery costs a measured 40-55% of prefill throughput, so the choice between
  the two profiles is a policy decision, not a bug fix.
- **Scripts outside the repo root import a different checkout.** Running a
  probe as `/tmp/x.py` puts `/tmp` first on `sys.path`, and `import hipengine`
  then resolved to **`/home/lhl/hipEngine-main/hipengine`** — a different tree
  whose `_production_selections` has no `recovery` parameter. The first probe
  in this unit silently measured that tree and produced a manifest hash
  (`6a24cb28…`) matching no artifact. The gate script is safe because it inserts
  `parents[1]` itself; ad-hoc probes are not. Every probe in this entry asserts
  `hipengine.__file__` starts with `/home/lhl/hipEngine/`.
