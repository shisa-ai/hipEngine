# Share device identity between automatic backend selection and validation

## Summary

Review of `d311bd2af` (and the `8a9b6e113` test-isolation follow-up) found that
the capability check had been corrected to validate the *current logical device*
while automatic selection still took the *first ambient architecture*. The two
disagreed whenever they pointed at different devices, so public
`LLM(..., backend="auto")` could refuse a compatible device. Two further defects
came with it.

All four counterexamples were reproduced against the pre-change tree:

| Defect | Old behaviour |
| --- | --- |
| P1a filtered mixed host: physical `(gfx1100, gfx1151)`, `ROCR_VISIBLE_DEVICES=1` | auto resolved `hip_gfx1100`; validation resolved `gfx1151` and **refused a compatible device** |
| P1a current device 1, unfiltered mixed host | auto resolved `hip_gfx1100`; validation **refused a compatible device** |
| P2 unresolved current device on a mixed host | `_current_hip_device_ordinal()` -> `None` became ordinal 0, so `hip_gfx1151` was **refused although the current device was never established** |
| P1b offline target list: `amdgpu-arch` unavailable, `ROCM_TARGET_LST` -> `gfx1151`, real GPU `gfx1100` | physical probe returned `('gfx1151',)`, so `hip_gfx1100` was **refused** and `hip_gfx1151` **admitted** from an offline list |

## Fix

- **One device identity for selection and validation.**
  `select_backend`/`resolve_backend` gained
  `execution_device=False, physical_arches=None, current_device=None`. With
  `execution_device=True` automatic selection resolves the current logical device
  through `selected_device_arches` and maps its architecture to a backend
  (`source="execution_device"`), so it cannot name a device other than the one
  `require_backend_device_compatibility` validates. `LLM._resolve_backend` passes
  the flag. Without it, automatic selection is unchanged, so registry resolution
  (`resolve_vibevoice_kernels('auto')`) and `provenance.py` keep the ambient
  behaviour.
- **P1b: hardware-only evidence.** `_HARDWARE_ARCH_COMMANDS` contains only
  `amdgpu-arch`; `rocm_agent_enumerator` stays in `_ARCH_COMMANDS` for ambient
  reporting (diagnostics, provenance, scripts) but is excluded from
  `detect_hip_physical_device_arches` and the new
  `detect_hip_hardware_target_arches`, which is the execution fallback. Verified
  in the installed `/opt/rocm/bin/rocm_agent_enumerator`: `readFromTargetLstFile`
  consults `ROCM_TARGET_LST` or the adjacent `target.lst` **before** KFD/lspci/
  rocminfo. Setting `ROCM_TARGET_LST` to a path that cannot exist does
  neutralize both (verified: the enumerator falls back to `gfx1100` hardware),
  but that relies on one release's control flow, so execution evidence uses the
  hardware-only producer instead. `_hardware_probe_env()` also points
  `ROCM_TARGET_LST` at a nonexistent path as belt-and-braces for `amdgpu-arch`.
- **P2: unknown is not device zero.** On a heterogeneous visible set with no
  supplied ordinal, a missing or failed `hipGetDevice` now returns an empty
  tuple (unknown, permissive) instead of assuming ordinal 0. A homogeneous
  visible set still short-circuits to its single architecture without loading the
  HIP runtime.

## Changes

- `hipengine/kernels/backends.py`: `_HARDWARE_ARCH_COMMANDS`, `_ENV_ROCM_TARGET_LST`,
  `_probe_arches`, `_hardware_probe_env`, `detect_hip_hardware_target_arches`;
  `detect_hip_physical_device_arches` and `detect_hip_target_arches` now share
  `_probe_arches`; `selected_device_arches` P2 fix; `select_backend` /
  `resolve_backend` execution-device parameters.
- `hipengine/llm.py`: `LLM._resolve_backend` resolves with
  `execution_device=True`.
- `tests/test_unit_backend_device_capability.py`: replaced the `lambda: None`
  isolation case (which encoded the unknown-to-zero defect) with the correct
  cases; added public auto cases for the filtered and current-device mixed hosts,
  a fake-runtime case for success and failure of `hipGetDevice`, and fake-probe
  cases proving an offline target list neither admits nor refuses. All cases
  monkeypatch the probes and the runtime query, so no ROCm or device is needed.

## Validation

- RED against the pre-change tree (backends.py + llm.py stashed): the table above
  reproduces all four defects.
- GREEN with the change: filtered mixed host auto -> `hip_gfx1151` (admitted);
  current-device-1 mixed host auto -> `hip_gfx1151` (admitted); unresolved mixed
  host -> `selected_device_arches() == ()` and both backends permissive; offline
  target list -> physical `()`, hardware `()`, auto `cpu_reference`, both
  backends permissive.
- `tests/test_unit_backend_device_capability.py`: `26 passed`.
- Affected CPU bundle (`test_unit_backend_device_capability`,
  `test_unit_gfx1151_backend`, `test_unit_cuda_sm120a_backend`,
  `test_unit_ud_hip_guard`, `test_unit_gemma4_expert_route`,
  `test_unit_vibevoice_registry`, `test_unit_llm_generate`): `198 passed` in
  125 s.
- Live host probes: `detect_hip_physical_device_arches()` ->
  `('gfx1100','gfx1100')`, `detect_hip_hardware_target_arches()` ->
  `('gfx1100',)`, `detect_hip_target_arches()` -> `('gfx1100',)`.
- Public fail-fast, CPU, real model path: `LLM(..., backend="hip_gfx1151")`
  raises `BackendDeviceCapabilityError` in 0.54 s.

## Next

- Generator/session constructors that call `resolve_backend` directly with
  `backend='auto'` do not pass `execution_device=True`; the public path resolves
  before they are built, so this only matters for direct construction, which is
  also outside the capability-check seam.
- `ROCM_TARGET_LST` is not cleared from the ambient `detect_hip_target_arches`
  path, so ambient reporting can still reflect an offline target list. That is
  intentional: it is reporting, not hardware evidence.
