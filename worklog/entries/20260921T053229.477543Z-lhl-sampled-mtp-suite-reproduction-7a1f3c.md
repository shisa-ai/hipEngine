# Sampled MTP against true AR, re-measured on a quiet machine after v0.6.0

## Summary

A concurrent session landed native sampled MTP concurrency work
(`645d80b10 feat: enable concurrent native sampled MTP and repair startup
warmup`) while an earlier attempt at this suite was in flight. That attempt
produced no artifact, so its measurement could not stand as a current-head
number. This is the clean rerun, and it reproduces the suite row already in the
scoreboard.

One server process, arm selected by the request's own `speculative_mtp` field,
so both arms share KV layout, sampler, and warm caches:

| arm | decode tok/s (median across 10 prompts) |
| --- | ---: |
| sampled MTP | 20.31 |
| true AR | 10.72 |
| paired ratio | **1.895x** (min 1.59x, max 2.62x) |

Per category: code 2.39x, mixed_ja_en 1.87x, general_en 1.67x, general_ja 1.67x.
MTP coverage 0.984-0.992. Every MTP row was admitted automatically
(`decision_reason: automatic_native_sampled_c1_c4`) with no explicit request and
no retained evidence row, and every AR row reports `mtp_used: false`. The
scoreboard's existing ten-prompt suite row (22.37 against 11.30 tok/s, 1.979x)
is therefore reproduced within about 5%, so the concurrency work did not
invalidate it.

Lane: desktop `gfx1151`, machine_id `55ea6c509d0b49eea8de7094a1023668`. This is
**not** the zbook lane (`87c566d30a5645cf8d12ed7ef6b6e1e8`); both run gfx1151 and
`docs/OPTIMIZATION.md` section 2 makes same-architecture hosts independent lanes.
The artifact records this so the two sets of absolute rates are not compared.

## Validation

- Both arms exited 0 and both wrote their JSON; 60 requests total, 10 prompts,
  two repeats plus one warmup per prompt per arm.
- `scripts/sync_benchmark_readme.py --check` reports "README benchmark blocks are
  synchronized".
- The control arm is a true autoregressive arm on the same server process:
  `mtp_used: false` and `effective_route: null` on all ten AR rows.
- GPU contention was checked immediately before the run. The only other
  hipengine process was a server on port 8000 whose `resident_prepare` had
  already failed at startup and which served no successful request; it was
  returning HTTP 500 to everything on
  `OSError: libamdhip64.so: cannot open shared object file`, because it had been
  started through the console script without the ROCm environment on the loader
  path. Not a code defect, but `hipengine serve` invoked that way is a confusing
  failure mode worth knowing about.
- Caveat recorded with the artifact: two of the ten prompts stop early on both
  arms (62-63 and 43 tokens against 128 requested). They stay paired and their
  ratios are still computed, but their decode rates cover fewer tokens than the
  other eight.
