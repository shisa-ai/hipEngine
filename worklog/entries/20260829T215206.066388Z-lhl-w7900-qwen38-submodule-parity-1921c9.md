# W7900 Qwen3.8 submodule parity: admission loses on small-row prefill, MTP cycles do not pack


## Summary

The published C1-C8 rows say hipEngine wins AR at C1/C3-C5 and loses at C2 and
C6-C8. This entry attributes each remaining deficit to one named submodule on
one host (`GPD7-099448`, W7900/gfx1100, exclusive device per run), model
`/models/gguf/Qwen3.8-27B-Q4_K_M.gguf`, production profile, greedy, engine
reference `llama.cpp @ 7492f8b` (`--fit off`), all measured on this branch.

1. **Decode stays a win and is not the reason for any loss.** Per co-scheduled
   AR step, hipEngine 33.98/42.01/48.32/53.33/60.53/67.85/74.82/82.16 ms vs
   llama.cpp current 38.33/42.60/79.07/122.65/113.16/105.53/104.18/105.28 ms
   for C1-C8 (retained decomposition packet, 44.9-token prompts).
2. **Admission is the AR loss, and admission is prefill.** Per-lane admission
   is flat at 315.8/305.0/303.2/305.1/305.2/304.7/305.0/305.1 ms for C1-C8
   while llama.cpp's falls 223.4 -> 105.9 ms, so the ratio grows 1.41x (C1) to
   2.88x (C8). One hipEngine lane pays one 45-token prefill (282 ms measured
   below) and never amortizes it across the wave.
3. **hipEngine's small-row prefill is the submodule that must improve.** On the
   shipping AR route: 159.7 / 302.0 / 480.4 / 570.5 / 883.8 tok/s at 45 / 96 /
   192 / 256 / 512 prompt tokens. A 45-token prefill costs 49% of a
   512-token one, i.e. 6.32 vs 1.29 ms/token of device time (5.5x). The same
   retained packet gives the llama.cpp comparator the same shape: 223.4 ms of
   admission with a 38.3 ms first step at 44.9 tokens, i.e. ~185 ms of prompt
   processing (~243 tok/s) against hipEngine's 281.8 ms (159.7 tok/s) - a
   1.52x prefill-rate deficit at the shape that dominates admission.
4. **The packed multi-request prefill route exists on this host but is not
   numerically qualified**, which is why admission cannot amortize. The oracle
   passes token equality at rows 8 with equal lengths but fails state
   equality: 1008 initial-state and 1013 final-state mismatches (752 linear
   plus 256 KV entries across 64 layers), with zero route fallbacks.
5. **MTP cycles do not pack across the wave.** Cycle cost grows from 63 ms at
   C1 to 380 ms at C8, so one cycle costs 1.88 AR steps at C1 and 5.33 at C8.
   A separate defect sits on top: per-prompt acceptance is bimodal under wave
   composition (0.16-1.00 for byte-identical outputs).

## Changes

No product-code change: this unit is measurement and attribution. Every number
above is reproducible with committed tools:

- `scripts/gguf_engine_submodule_decomposition.py` on the retained server-bench
  and matrix packets -> per-width `decode_step_ms`, `admission_ms`,
  `admission_ms_per_lane`, and the cross-engine winner table.
- `scripts/gguf_engine_kernel_bucket_parity.py` -> `kernel_time_per_generated_token`
  parity per width.
- `scripts/qwen35_gguf_bench.py --persistent-session [--use-wmma-prefill]
  [--gpu-stage-timings]` -> prefill scaling, the WMMA route A/B, and stage
  attribution.
- `scripts/gguf_first_token_probe.py --packed-prefill --rows 8 --equal-length
  128` -> packed prefill route audit and parity result.

Two instrument findings are recorded here rather than as code because they are
protocol facts, not defects in a call site: the GGUF bench's default prefill
route is not the shipping route (+62.4% at 45 tokens), and stage timings need
the `--gpu-stage-timings` flag rather than the environment variable alone.

## Validation

- Analysis-only unit: no kernel, dispatch, or registry change, so no correctness
  gate applies. Product behavior is unchanged for every profile.
- All claims are same-host, same-protocol re-reads of retained artifacts plus
  the reruns listed above on `GPD7-099448` (W7900, gfx1100), exclusive device,
  production profile, greedy.
- Cross-checked derivations: the AR step ladder from the decomposition packet
  (34.0 -> 82.2 ms) matches the independent two-point D4/D24 decomposition
  (33.8 -> 71.3 ms) and the published matrix rates; the MTP cycle-vs-width
  growth (1.88 -> 5.33 AR steps) holds under both admission derivations
  (1.89 -> 4.95).

## Rejected and corrected evidence

- Cross-engine kernel-name equality is not measurable: hipEngine/GPU is 93.7%
  "unclassified" under rocprofv3 while llama.cpp/GPU has 69.59% unattributed
  device time (the `gap` bucket). Only total device-busy time compares, which is
  the bucket metric above.
- llama.cpp's `eval_count`-derived prompt rate at short prompts is not a
  prompt-throughput measurement: the per-request timings window covers only the
  prompt chunk evaluated before the first response, so it inflates at small
  prompt counts. The admission term (wall to first visible token minus one
  decode step, both engines) is the comparator used above.
- The retained cross-engine packets contain no 512-token prompt arm, so "long
  prompt prefill beats llama.cpp" remains an internal-only observation and is
  not a claim here.
- Transport parity was checked: the llama wave client's `/health` poll answers
  in ~1 ms while `/metrics` costs ~20 ms, so the sampler asymmetry is under 5%
  of C1 admission and changes no verdict.
- The 64-token `--sample-streams` packed-prefill probe aborts with a documented
  runtime error (sampled KV block-table host copy), so only the 128-token
  equal-length probe is used as evidence.

## Instrument defect found in the GGUF bench harness

`scripts/qwen35_gguf_bench.py` leaves `use_wmma_prefill` unset (so it resolves
through the env var to `False`), while the shipping session path passes
`use_wmma_prefill=True` (`hipengine/generation/qwen35_gguf.py:1107`, 1180,
2068, 2490, 2655). Same protocol, 4 measured runs, `--persistent-session`:

| prompt tokens | bench default route | shipping (WMMA) route | delta |
| --- | --- | --- | --- |
| 45 | 0.4577 s (98.3 tok/s) | 0.2818 s (159.7 tok/s) | +62.4% |
| 512 | 0.5892 s (869.0 tok/s) | 0.5793 s (883.8 tok/s) | +1.7% |

The generated token id is identical (9707) and the final logit changes
(22.1395 -> 21.9644), so this is a production-profile arithmetic change, not
exact parity. Two consequences:

- Short-prompt prefill rates taken from that harness's default route understate
  the shipping route by up to 1.62x and must not be quoted as engine rates.
  The 8.6x internal short-vs-long gap reported while this entry was in progress
  was that route, not the shipping route; the shipping gap is 5.5x.
- Any future default-route bench claim should record
  `effective_use_wmma_prefill` (it already does) and be rejected if it disagrees
  with the shipping profile. Tracked as a candidate in "Next gated actions".

`--gpu-stage-timings` is a CLI flag, not an env-only toggle: passing only
`HIPENGINE_GGUF_GPU_STAGE_TIMINGS=1` produces `{"enabled": false}` and an empty
stage map. First WMMA-route attribution attempt was silently empty for that
reason.

## Small-row prefill attribution (shipping route, device-kernel markers)

`scripts/qwen35_gguf_bench.py --prompt-length {45,512} --decode-tokens 1
--warmup-runs 1 --measured-runs 1 --persistent-session --gpu-stage-timings
--use-wmma-prefill`:

- 45 rows: 284.2 ms of device time inside a 285 ms prefill (100% busy) =
  6.32 ms/token.
- 512 rows: 661.9 ms of device-stage time against a 582 ms prefill (114%,
  because the two 256-row rounds have overlapping markers) = 1.29 ms/token.

Per-token gap at 45 rows vs 512 rows, largest offenders on the shipping route:

| stage | 45 rows ms/tok | 512 rows ms/tok | gap | total ms (45 vs 512) |
| --- | --- | --- | --- | --- |
| full_attn_output | 0.148 | 0.023 | 6.6x | 6.7 vs 11.6 |
| linear_attn_attn_qkv_gate | 0.929 | 0.158 | 5.9x | 41.8 vs 81.0 |
| linear_attn_ffn_gate_up | 1.483 | 0.338 | 4.4x | 66.8 vs 173.1 |
| full_attn_ffn_gate_up | 0.494 | 0.113 | 4.4x | 22.2 vs 57.8 |
| linear_attn_conv | 0.021 | 0.009 | 2.3x | 1.0 vs 4.7 |
| linear_attn_gdn | 0.118 | 0.076 | 1.5x | 5.3 vs 39.0 |

For contrast, the same stages on the bench default (non-WMMA) route anti-scale
far worse: `linear_attn_ssm_out` 1.591 vs 0.060 ms/tok (26.3x) and
`linear_attn_ffn_down_residual` 2.487 vs 0.168 (14.8x). So the WMMA route
already removes the two worst small-row offenders, and what is left to fix is
the QKV/gate projection family plus the attention output projection below 512
rows. The row gate that keeps them off the faster chain is in the backend
package: `GGUF_Q4_T16_F16_ROCBLAS_PREFILL_POLICIES` anchors start at 512 rows
and `GGUF_T16_F16_ROCBLAS_VARIANT_POLICIES` intervals start at `(512, 4096)`,
with `GGUF_Q4_K_M_MAX_PREFILL_CHUNK_TOKENS = 256` capping a round.

## Packed multi-request prefill: route engages, parity does not

`scripts/gguf_first_token_probe.py --packed-prefill --rows 8 --equal-length
128` (and the rows-4/45-token variant) on this host:

| probe | tokens exact | initial state exact | final state exact | passed |
| --- | --- | --- | --- | --- |
| rows 8, mixed lengths | no | no (1008) | no (1013) | false |
| rows 8, equal lengths | yes | no (1008) | no (1013) | false |
| rows 4, 45-token prompts | yes | no (1008) | no (1013) | false |

Mismatch spread: 752 `linear` (Conv/GDN `recurrent` parts) and 256 `kv`
entries across all 64 layers, first entry `layer 0 / linear / recurrent`.
Route audit: `packed_linear_state_route=segmented_in_place_final_state`,
`packed_gdn_kernel_route=decode_order_bf16_segments`, `gdn_prefill_mode=exact`
against `GGUF_GDN_PREFILL_EXACT_MODE=chain_lds32_direct_nonvolatile`,
`row_capacity=256`, `max_batch_rows=8`, zero fallback reasons. So the blocker
is numerical qualification of the gfx1100 packed prefill state write (both the
GDN recurrent state and the KV write), not capacity, scheduling, or a missing
flag. This is what keeps admission at one prefill row per step.

## MTP: cycle cost scales with the wave instead of packing

Two-point decomposition of the retained rows (`wall(D) ~= admission + (D-1) x
step` on the D4 and D24 arms of the same prompts), cycles from the same
packet's MTP telemetry:

| W | AR step ms | admission ms | MTP wall s | cycles | tokens/cycle | cycle ms | cycle/step |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 33.8 | 321 | 0.771 | 7.1 | 3.38 | 63.3 | 1.88 |
| 2 | 40.2 | 651 | 1.620 | 8.3 | 2.89 | 116.7 | 2.90 |
| 3 | 44.3 | 1003 | 2.357 | 10.0 | 2.40 | 135.5 | 3.06 |
| 4 | 47.6 | 1351 | 3.094 | 9.3 | 2.58 | 187.3 | 3.93 |
| 5 | 53.7 | 1683 | 3.902 | 7.4 | 3.24 | 299.8 | 5.58 |
| 6 | 59.6 | 2018 | 4.761 | 10.3 | 2.33 | 266.3 | 4.47 |
| 7 | 65.2 | 2357 | 5.491 | 9.2 | 2.61 | 340.6 | 5.23 |
| 8 | 71.3 | 2691 | 6.225 | 9.3 | 2.58 | 379.9 | 5.33 |

Using the retained decomposition packet's measured admission instead of the
two-point estimate gives 64.1/121.7/144.7/201.4/321.0/284.8/364.7/406.8 ms and
ratios 1.89/2.90/3.00/3.78/5.31/4.20/4.88/4.95 - the absolute cycle number is
admission-sensitive, the growth from ~1.9x to ~5x an AR step is not. AR decode
batches 3.4x across the same wave (34.0 -> 82.2 ms for 8 lanes), so the
draft+verify cycle is the term that fails to amortize.

Two candidate mechanisms are visible in code and both point at physical group
width, not at the draft model itself:

- `Mtp2Adapter.partition_max_requests`
  (`hipengine/generation/qwen35_gguf_mtp2.py:1072`) bounds one physical group
  to `min(4, capacity, max_realized_group_rows)`, and the gfx1100 plugin still
  records "model-plugin evidence still admits only exact C2 keys; C4 and
  automatic physical policy remain fail-closed", so a wide wave needs several
  serial physical groups per cycle.
- `GGUF_SPECDEC2_NATIVE_TARGET_GRAPH_MAX_CONTEXT = 95` keeps target
  verification out of the captured graph above 95 tokens of context, which is
  the whole 155-token mean suite.

The result is bimodal: a prompt either keeps its C1 cycle count (6-8 cycles,
0.57-1.00 acceptance) or collapses to 11-13 cycles at 0.16-0.34, and which
side it lands on depends on the wave rather than on width alone. Realized
drafts per cycle stays at ~2.8 either way, so this is draft-proposal quality,
not a smaller realized K, and since drafts are verifier-checked it costs
throughput rather than correctness. It is not explained by cycle cost and must
not be folded into the row-scaling item; localizing it needs per-request draft
proposal/verdict telemetry inside one cycle.
