# QA-8 closed: split-K sparse attention is already implemented, promoted, and exact

## Summary

`QA-8` is filed as *"A historical unmeasured alternative to one-wave attention, not a demonstrated
successor to today's H256 route"*, action: *"After `X-3`, screen one real 24-query/2-KV-head/D256
packet against the current owner, charging partial-output scratch and merge. Preserve selected
positions and tails; changed softmax/reduction association is T2 and needs §3.1. Stop if the
complete owner loses."*

**`X-3` is CAPTURED at `2789c19d6`, so the dependency was satisfied - and the screen is
unnecessary, because the split already exists, already is today's H256 route for c1 decode, and is
already promoted with whole-model evidence. Close `QA-8`.** The row's premise is out of date on
both counts.

## Changes

## The split exists, in the shape the row describes

The ordered three-pass family in `hipengine/kernels/hip_gfx1100/attention/qwen4_exp_qsa.{hip,py}`:

| pass | kernel | role |
|---|---|---|
| 1 | `qsa_sparse_attention_paged_bf16_ordered_scores_f32_kernel` | scores |
| 2 | `..._ordered_coefficients_...` | softmax normalization (the merge) |
| 3 | `..._ordered_values_...` | value accumulation |

Pass 1's decomposition is decisive:

```cpp
const int64_t q_head         = blockIdx.x;
const int64_t selected_index = blockIdx.y;   // one block per selected position
const int64_t dimension      = threadIdx.x;
```

**`grid = (query_heads, selected_count)` - one block per selected position, so the
selected-position reduction is split across blocks.** That is exactly the split-K decomposition
`QA-8` asks to screen.

**The scratch the row asks to charge is charged, and visibly so**: the host wrapper
`qwen4_exp_qsa_sparse_attention_paged_bf16_ordered_f32` takes explicit `scores_ptr` and
`coefficients_ptr` parameters - materialized intermediates sized `query_heads x selected_count`
floats each - and pass 2 is the merge. **Positions are preserved by construction**: the kernel
iterates `selected_index` over exactly `selected_count`, so any count gets one block per position
and there is no tail assumption to violate.

**The production route is the stricter version of the proposal.** A classic split-K merges partial
max/sum, which changes the reduction association; the ordered route materializes *all* scores and
normalizes globally, so it **charges more scratch than a partial-merge split would** and buys
exactness with it. The row's cost concern is already paid at a higher rate than the proposal
implies.

## The T2/§3.1 concern does not bind

The row warns that "changed softmax/reduction association is T2 and needs §3.1". That gate would
apply to a *partial-merge* split whose association differs from the strict route. **The promoted
ordered route does not change the result**: `all_cross_route_logits_exact` and
`cross_mode_output_exact` are both true and `mismatched_case_ids` is empty. It is an **exact (T0)**
route that happens to use a split decomposition, so it clears the arithmetic bar by construction.
No §3.1 pass is owed.

## What this does not close

- **Prefill.** The ordered family has a multi-row entry point
  (`qwen4_exp_qsa_sparse_attention_paged_bf16_ordered_rows_f32`), but the *selected* prefill
  variant remains `strict_rows_spans`. A split prefill owner is unmeasured - and is not what this
  row asked. `QA-2` remains the open prefill-side arithmetic question.
- **A different split shape.** Another decomposition (different pass count, different scratch
  layout, partial merge with exact renormalization) would be a *new* candidate needing its own row
  and its own whole-model A/B, not a reopening of `QA-8`.
- **Any new timing.** None taken.
