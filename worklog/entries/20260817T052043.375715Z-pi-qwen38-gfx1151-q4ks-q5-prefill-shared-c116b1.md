# Retain Q4_K_S Q5 source-F16 prefill at 512/1K/4K with capacity-conditional scratch

## Summary

Answered the open question "is Q4_K_S prefill inherently more compute-intensive,
or is the K_S-K_M gap relative kernel-optimization coverage?" with a tensor-role
header scan plus fresh same-stream GPU profiles: the gap is owner coverage, not
precision physics. K_S carries 48 byte-identical `gguf_q5_k_t16_v1` K6144/N5120
ssm_out tensors (identical to K_M), but the K_M-derived
`GGUF_DENSE_T16_F16_ROCBLAS_PREFILL_POLICIES` admission was keyed to
`MOSTLY_Q4_K_M` only, so all 60 K_S Q5 prefill tensors fell to the single-wave
exact WMMA owner. This unit retains the source-F16 route for K_S at 512/1K/4K
and keeps 8K+ unchanged via a capacity-conditional bulk-prefill scratch cap.

## Changes

- Extended `GGUF_DENSE_T16_F16_ROCBLAS_PREFILL_POLICIES` in
  `hipengine/kernels/hip_gfx1151/__init__.py` with
  `(QWEN35_DENSE_H5120_GEOMETRY, "MOSTLY_Q4_K_S"): True`, admitting the 48
  byte-identical Q5T16 K6144/N5120 recurrent outputs to the existing source-F16
  route. The 12 role-Q5 tensors K_S owns instead of K_M's Q6 (3 attn_qkv, 1
  attn_v, 8 ffn_down) do not match the Q5 policy shape and remain exact WMMA.
- Made the gfx1151 Q4_K_S bulk-prefill scratch row cap capacity-conditional in
  `GGUF_DENSE_PREFILL_SCRATCH_ROW_CAP_POLICIES`
  (`max_rows_by_capacity` {4096: 4096, 8192: 1024}): 4K-class requests grow to
  the natural full-attention 4096-row plateau (which admits source-F16 at 4K,
  +2.95%), while 8K and larger keep 1,024-row chunks because 4,096-row chunks
  measured -2.3% slower at 8K regardless of source-F16. Memory therefore stays
  flat as context grows past 8K.
- Extended `_gguf_dense_prefill_scratch_row_cap` in
  `hipengine/runtime/qwen35_gguf_runner.py` to resolve the largest threshold a
  request capacity reaches from `max_rows_by_capacity` (flat `max_rows` form
  still supported as a fallback), and capped the chunk_outer prefill chunk size
  by the resident `_bulk_prefill_scratch.rows` so a small-shape request inside a
  larger-shape session can never overrun the resident buffer (mixed-shape
  sessions like `--workloads 4K/128 8K/128`).
- Updated `tests/test_gfx1151_backend.py` (K_S admission) and
  `tests/test_qwen35_gguf_prefill_scratch_liveness.py` (capacity-conditional
  row cap) to the retained state.

## Validation

- Tensor-role scan (`hipengine/loading/gguf.py` header): K_M has 66 Q6_K
  tensors; K_S replaces them with 54 Q4_K + 12 Q5_K. Gate/up, q/k/output,
  `ssm_out` (Q5 in both), and lm_head are identical. K_S is byte-identical to
  K_M on all 48 Q5T16 recurrent outputs, so the source-F16 route exercises the
  exact same weights/arithmetic already gated for K_M (min per-prompt top-1
  96.97%, max KL 0.009339, 330 transitions).
- Fresh same-stream pp512 kernel profile (rocprofv3, cached build): K_M Q5
  ssm_out on rocBLAS F16 Cijk (~39 ms) vs K_S all-Q5 single-wave WMMA
  (~191 ms) — a ~150 ms / ~11% pp512 wall difference, matching the K_S-K_M gap.
  K_S Q4 shared_b (501 ms) is already faster than K_M's Q4+Q6 mix (556 ms).
- Counterbalanced 512/1K prefill A/B (5 interleaved pairs per shape, alternating
  order, one discarded warmup + three measured resets per process, fresh process
  per variant, shared JIT cache, only the one policy dict entry differs):
  512/128 prefill 379.30 -> 396.09 tok/s (+4.51% paired median, 5/5 pairs win),
  1K/128 376.33 -> 387.65 tok/s (+3.02%, 5/5 pairs win); decode flat both
  (-0.09% / +0.02%). Matches the frozen G6 baseline in the off variant
  (379.605 vs 379.398) and the task31 candidate in the on variant (396.006 vs
  396.222).
- Full ten-prompt/four-category natural gate on K_S with the enablement
  (`scripts/qwen36_dense_gguf_suite.py`, quant `gguf_q4_k_s`, runs=3, budgets
  1/2/3, 25 outputs/24 transitions, warmup, cached builds): status
  `complete_exact`; all 120 requests greedy-exact, every GPU accept matches CPU,
  zero teardown. AR 13.382, B1 20.011 (1.495x), B2 23.634 (1.766x),
  B3 24.500 tok/s (1.831x); no compiler children during measured runs.
- 4K capacity-conditional (source-F16 active, one discarded warmup + three
  measured resets): prefill 369.43 -> 380.31 tok/s (+2.95%), tracked peak
  15.494 -> 17.863 GiB (fixed +2.30 GiB bulk-prefill scratch; the F16 workspace
  itself is only +0.06 GiB), final token 9707 stable, finite logits, zero
  teardown.
- 8K+ unchanged (1,024-row chunks, source-F16 off): 8K prefill 359.09 tok/s
  (old 358.9-359.3), tracked peak 15.795 GiB (scratch flat vs 4K's 1024-row
  shape), final token 9707 stable, finite logits, zero teardown. 4,096-row
  chunks measured -2.3% slower at 8K regardless of source-F16
  (350.7-351.1 vs 359.0), so the cap returns to 1,024 there.
- Combined-session regression found and fixed: `--workloads 4K/128 8K/128` in
  one resident session previously overran the 1,024-row resident buffer when the
  4K workload chunked at 4,096 rows; chunk_size is now capped by resident
  `_bulk_prefill_scratch.rows` and the combined session completes cleanly.
- Scoping: the row-cap policy and K_S source-F16 admission exist only in the
  gfx1151 backend package. gfx1100 has no `GGUF_DENSE_PREFILL_SCRATCH_ROW_CAP_POLICIES`
  and admits only `MOSTLY_Q4_K_M` to source-F16, and 24GB-class cards already
  drop the full-attn query chunk to 1024/768 at 52K+/128K+ by autotune, so this
  change cannot affect 24GB/gfx1100 cards.
- Narrow CPU/HIP bundle: `test_gfx1151_backend.py`,
  `test_qwen35_gguf_prefill_scratch_liveness.py`, `test_gguf_linear_dispatch.py`,
  `test_qwen35_gguf_runner.py`, `test_qwen35_gguf_mapping.py`,
  `test_gguf_q6_k_f16_rocblas_prefill.py` all pass (202 passed across the
  first three).
