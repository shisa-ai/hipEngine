# P2 isolated on the census, and the census could not see it

## Summary

The prefill census wrapped exactly one attention launch site —
`gemma4_attention_prefill_bf16`, the exact kernel. P2 moved the global layers
off it and the sliding layers were already on AOTriton, so **neither route
reached the wrapper**: the census showed no attention row at all and 46.7% of
layer time sat in `unattributed`. The measurement tool was blind to the path
production runs. All three routes are now wrapped and labelled separately, so
the census reports which kernel ran instead of only that attention cost
something.

That immediately produced the evidence P2's dispatch owed: at 1024 prefill
tokens (two blocks of 512), `attention_prefill_tiled` reports **10 calls —
exactly 2 blocks x 5 global layers** — while `attention_prefill_aotriton`
reports 50 (the sliding layers) and the exact row is absent. The tiled symbol
is the one that ran.

**A correction to a number reported last iteration.** The earlier bench A/B
forced `_select_prefill_route` to `"exact"` for *every* block, so its
2246 vs 1613 tok/s read as "+39.2% from P2". It was not P2 alone: that run
also moved the sliding layers off AOTriton. Isolating properly — diverting only
`tiled -> exact` and leaving sliding on AOTriton — gives **2083 -> 2246
tok/s, +7.8%**, which is P2's real share. The remaining 1613 -> 2083 (+29%)
is AOTriton against the exact kernel on the sliding layers, which predates P2
and belongs to no row in this change. The +39.2% figure describes the default
path against an all-exact path and should not be quoted as P2's win.

At the family level the same ten calls cost **10.505 ms tiled against 42.477
ms exact — 4.04x per call** — and `layer_total` falls 462.838 -> 432.959 ms.

`rocprofv3 --kernel-trace` hangs on this workload: attempted twice, at 1024
and 64 tokens, killed at 1200 s and 420 s, with the profiled process reaching
model load and then producing nothing (a trivial `/bin/echo` target does
complete, so the tool itself runs). This matches what the census docstring
already records — kernel-trace perturbs a launch-bound workload — so the
breakdown below comes from HIP event pairs rather than a profiler trace.

## Changes

- `scripts/gemma4_prefill_census.py` — wrap
  `gemma4_attention_prefill_tiled` and `gemma4_attention_prefill_aotriton`
  alongside the existing exact wrap, as `attention_prefill_tiled` and
  `attention_prefill_aotriton`. Additive: the `attention_prefill` row keeps its
  meaning, so existing readers are unaffected.

  | attention_prefill_aotriton | 50 | 89.529 | 20.7% |
  | moe_wmma:gguf_q5_1 | 58 | 42.552 | 9.8% |
  | moe_grouped_dual:gguf_q5_k | 2 | 21.716 | 5.0% |
  | attention_prefill_tiled | 10 | 10.505 | 2.4% |
  | unattributed inside layers | | 139.305 | 32.2% |
  | outside layers | | 8.453 | |

  `unattributed` fell from 198.499 ms / 46.7% to 139.305 ms / 32.2% purely
  because attention became visible again.

- Same census with global layers diverted to exact, sliding untouched:
  `attention_prefill` 10 calls / 42.477 ms, `layer_total` 462.838 ms,
  `unattributed` 139.349 ms. The attribution is stable across the A/B, so the
  comparison is like-for-like.
- Campaign bench, W7900 GPU0, 1024p/128o, 3 samples, `public_path_parity`
  true: default 2262 / 2222 / 2246 (median **2246**); global-only-exact 2087 /
  2083 / 2077 (median **2083**); all-exact 1617 / 1613 / 1613 (median
  **1613**). Decode flat at 40.05 / 39.94 / 39.69 tok/s across the three.
- `pytest -k census` → 0 failures, 0 errors. `compileall` on the changed
  script → clean. No Gemma 4 census test exists to extend; the script's own
  `--json` output is its artifact.
