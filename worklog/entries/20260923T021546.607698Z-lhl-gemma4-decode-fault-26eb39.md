# Decode fault narrowed: over-read is layout-sensitive and outside the runner's own buffers

## Summary

Follows `worklog/entries/20260923T020151.588610Z-lhl-gemma4-decode-fault-b43475.md`,
which is the blocker record. This entry adds one bisection result to it.

## The experiment

Monkeypatched `Gemma4Runner._alloc` to over-allocate every buffer the runner owns
by 1 MiB — token ids, hidden, normalized, logits, and both KV caches — leaving the
layer scratch untouched. 24 decode steps.

## The result

It faulted **earlier**, before the prompt forward completed, with no output at all.

That is the useful part: over-allocating the runner's buffers did not remove the
over-read, it moved where the fault lands. Combined with the earlier result that
1 MiB of padding on the mask and both rope tables also failed to remove it, the
over-read is not in any buffer the runner allocates and not in the per-call
uploads.

## What that leaves

The layer scratch (`Gemma4LayerScratch`, sized for `max_block` tokens and reused
across steps without being cleared) and the attention path's own internals. The
scratch is now the leading candidate: it is allocated per layer, its size does
not change between steps, and it is the one set of buffers this experiment could
not pad.

A kernel reading a full tile of a scratch region that was only partially written
would read stale data, and whether that faults depends on the scratch's own
allocation rather than the caller's — which is exactly the layout-sensitivity
both experiments show.
