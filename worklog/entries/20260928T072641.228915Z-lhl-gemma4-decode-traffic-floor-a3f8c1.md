# the decode traffic floor is 2729 MB per token so llama.cpp achieves 114 GB/s not 135

## Summary

The artifact's own metadata gives an independent check on the decode traffic
budget, and it changes the reference number the census derives from it.

Read from `gemma4_gguf_config_from_metadata` on the real 17 GB
`gemma-4-26B-A4B-it-UD-Q4_K_XL.gguf`:

```
hidden_size = 2816
expert_count = 128
expert_used_count = 8
expert_feed_forward_length = 704
```

That is enough to compute the traffic a decode step *must* move, with no
instrumentation:

| component | per token | arithmetic |
| --- | --- | --- |
| expert gate+up (Q4_K) | 535.3 MB | 8 x 2 x 2816 x 704 x 0.5625, over 30 layers |
| expert down (Q5_1) | 327.1 MB | 8 x 2816 x 704 x 0.6875, over 30 layers |
| **expert total** | **862.4 MB** | |
| dense (Q8_0) | 1866.7 MB | measured, and row-count independent |
| **floor** | **2729.1 MB** | |

Two consequences, both of which move a number I had been quoting.

**The expert share of the census is inflated.** `20260927T225558` reports
1348.1 MB of expert traffic against this 862.4 MB floor, a factor of 1.56 (q4_k
793.4 vs 535.3, q5_1 528.9 vs 327.1). The census divides by 15 forwards while its
shape table shows a `rows=8` group at fractional per-step counts, which is the
`--prompt 8` prefill leaking into the average, and expert weight bytes scale with
selected rows where dense weight bytes do not. That is a candidate explanation,
not a confirmed one.

**The reference bandwidth changes.** The census computes llama.cpp's 41.92 tok/s
as 135 GB/s "on the same traffic", using 3219.6 MB. Against the 2729.1 MB floor
that is **114 GB/s**, not 135. Our own decode at 27.31 tok/s is 36.6 ms/token,
which is **74.6 GB/s** on the same floor. So the same-host gap is 1.53x in
throughput and about 1.53x in achieved bandwidth, and llama.cpp is at 45% of the
256 GB/s an isolated pack8 Q8_0 GEMV reaches, not 53%.

**A real check that passes.** Reading all 128 experts would be 13797.9 MB per
token, five times the floor. The census's 3219.6 MB total is 1.18x the floor, so
the router is selecting experts and the kernels are not reading the full expert
tensor. Whatever the 1.18x is, it is not a routing defect.

## Changes

None. No source file changed. This entry is arithmetic over metadata the loader
already exposes plus figures already recorded in `20260927T225558`, and it
supersedes nothing -- it narrows what that entry's totals mean.

## Validation

```
G=/models/gguf/gemma-4-26B-A4B-it-GGUF/gemma-4-26B-A4B-it-UD-Q4_K_XL.gguf
env PYTHONPATH=. python3 -c "
from hipengine.loading.gguf import GGUFReader
from hipengine.loading.gemma4_gguf import gemma4_gguf_config_from_metadata
print(gemma4_gguf_config_from_metadata(GGUFReader('$G').info))
"
```

gave `hidden_size = 2816`, `expert_count = 128`, `expert_used_count = 8`,
`expert_feed_forward_length = 704`. The byte products above use q4_k at 4.5 bits
and q5_1 at 5.5 bits per element, matching the `BPE` table in
`scripts/gemma4_decode_traffic_census.py`, and 30 layers.

The dense figure is taken as measured rather than computed, because a dense
projection's weight bytes are read once per launch regardless of row count, which
is why the census's dense total is not subject to the prefill-leak effect that
inflates the expert share.

The 1.56x expert inflation is reported as a candidate explanation with its
mechanism named, not as a settled cause; separating the prefill rows from the
decode rows in the census is the test.
