# Fix the packed multi-chunk shared-oracle defect with per-layer keying

## Summary

Fixes the P1 recorded in
`20260909T152235.420179Z-lhl-int8-packed-shared-oracle-defect-6f101c.md`: the
packed slot-local INT8 prefill route produced wrong output for any prompt
spanning more than one prefill chunk, because one BF16 oracle pair was shared
across layers under a chunk-outer executor.

`_int8_prefill_oracle_cache_for_layer` now keys the oracle per INT8 layer when
the session's `_int8_prefill_oracle_per_layer` flag is set.
`_prefill_batch_native_impl` sets it once per call, before the first slab, when
`len(chunks) > 1`; `prefill_batch_native`'s `finally` clears it alongside the
oracle release so per-layer keying can never leak into a later single-chunk call
and read an unwritten pair. The scalar bulk (layer-outer) executor is untouched
and keeps the shared pair, so the direct engine's memory model is unchanged.

Generated IDs now match the scalar-bulk parent exactly at 2 and 8 chunks. Speed
is neutral. Cost is a transient peak increase of ~0.94 GiB at 16,384 declared
positions, and that cost scales with declared context.

## Decisions

- **Executor-aware keying, not a plan change.** Forcing the *plan* to per-layer
  whenever chunking is possible would also penalise the scalar bulk path, which
  is layer-outer and provably safe with the shared pair, and would regress the
  direct engine's 155,648-token ceiling for nothing. Keying at the point of use
  confines the cost to the executor that needs it.
- **Decide once per call, not per slab.** Switching keys mid-call would leave the
  per-layer prefix unwritten, which is a different wrong answer. The flag is set
  before the first slab and cleared in the existing `finally`.
- **This is a correctness fix, not the memory-optimal one.** The recommended
  long-term target remains the layer-outer packed executor (option 1 in the
  campaign doc): the shared plan already budgets
  `required_hidden_capacity = positions` precisely so the executor can be
  layer-outer, so that option restores correctness *and* keeps one oracle pair.
  This unit takes the smaller, verifiable step because it is correctness-first
  and speed-neutral.
- **The 8-chunk slowdown is not mine and is not fixed here.** Packed prefill runs
  67 tok/s at 8 chunks against the scalar parent's 692. A pre-fix control in the
  same session measured 67.2 tok/s, so this fix changes it by nothing. It is the
  per-slab whole-history import (open review finding), and it is the real cause
  of the slow long-prompt server path - not the BF16 oracle.

## Changes

- `hipengine/runtime/qwen35_gguf_runner.py`:
  - `Qwen35GGUFResidentSession._int8_prefill_oracle_per_layer` field (default
    False).
  - `_int8_prefill_oracle_cache_for_layer` honours it when choosing between the
    shared `-1` key and per-layer keys, with the invariant spelled out inline.
  - `_prefill_batch_native_impl` sets the flag for multi-chunk calls on every
    session in the slab.
  - `prefill_batch_native`'s `finally` resets it per session.
