# the mmq barrier hypothesis is refuted by the down kernel and both mmq kernels sit at 50 gb per second

## Summary

I set out to start on the open prefill lever -- the MoE gate/up at 54 GB/s -- and
formed the obvious hypothesis from the kernel's structure: **88 K-blocks, each
ending in a `__syncthreads()`, against only about 5,600 cycles of useful dp4a work
per thread, so the barriers would be roughly 3x the compute.**

**The tree refutes it without my touching the kernel.** The down projection uses the
same MMQ32 structure with a different `in_features`, so it runs **22 barriers where
the gate/up runs 88** -- and it is **slower per MAC**, not faster. More barriers,
higher throughput.

**The real signal is underneath, and it is a cleaner one: both MMQ kernels sit at
about 50 GB/s while the dense pack8 GEMV reaches 199.**

## The barrier hypothesis and its refutation

`gguf_q4_k_q8_1_selected_prefill.hip:1099` fixes `MMQ_K = 32`, and the K loop is
`k32_iters = in_features / MMQ_K`. There is exactly one `__syncthreads()` in that
loop (at the end of the K-block body), so:

- gate/up, `in_features = 2816` -> **88 barriers** per workgroup
- down, `in_features = 704` -> **22 barriers** per workgroup

Per workgroup the gate/up does about 720K dp4a over 128 threads, i.e. ~5,600 per
thread, against 88 barriers at roughly 200 cycles each. On that arithmetic the
barriers look like the dominant cost, and cutting them -- a wider `MMQ_K` or
double-buffered tiles so one barrier serves two K-blocks -- would be the fix.

**Both kernels measured, per layer, at the prefill shape:**

| kernel | in_features | k32_iters | G MAC/layer | ms/layer | T MAC/s |
| --- | ---: | ---: | ---: | ---: | ---: |
| gate/up | 2816 | **88** | 21.82 | 5.28 | **4.13** |
| down | 704 | **22** | 8.12 | 3.99 | **2.03** |

**The kernel with four times the barriers has twice the throughput per MAC.** The
barrier count is not what sets the rate, and a double-buffered K loop would be work
spent on a hypothesis the tree already contradicts.

`MMQ_K = 32` is also structural rather than arbitrary: the loop derives
`weight_block = k32 >> 3` and `subblock = k32 & 7`, so 8 subblocks of 32 make up
q4_k's 256-element block. Widening it is not a constant change.

## What the two kernels agree on

| kernel | weight bytes | time | rate |
| --- | ---: | ---: | ---: |
| gate/up | 8.28 GB | 153.2 ms | **54 GB/s** |
| down | 5.52 GB | 115.8 ms | **48 GB/s** |
| dense pack8 GEMV (decode, same box) | | | **199 GB/s** |

**Both MMQ kernels sit at roughly 50 GB/s, within 12 percent of each other, despite
very different `in_features`, different quants (Q4_K against Q5_1), different row
counts and a 4x difference in barrier count.** That consistency is the finding: the
limit is a property of the MMQ path itself -- the int8-dp4a arithmetic with its q8_1
activation quantization -- and not of either kernel's tiling.

It also cross-checks the decode case. The same gate/up kernel measured 35 GB/s at
decode against 54 at prefill, and the down kernel is at 48 here; the decode figure
was for a single row per expert with almost no reuse. **The rate moves with reuse but
never approaches the dense path's 199.**

## Why I did not edit the kernel

The edit that the barrier hypothesis called for is real work in a large kernel:
`MMQ_K` is structural, the tile caches are shared-memory sized for the current
K-block, and the k32 loop carries the subblock decode. **Doing it on a hypothesis
the down kernel already refutes would have been a day spent to reproduce a
measurement I could get from the tree in one arithmetic step.**

This is the same shape as the two withdrawn readings earlier in this campaign -- the
45,056-block reading and the mask-zero conclusion -- and the check that caught it was
the same kind: compare against a case the tree already contains.

## What this leaves

The prefill MoE kernels are 36.9 percent of prefill and both run at about 50 GB/s
where the dense path shows 199 is reachable on this hardware. **The question is now
specific: what does the MMQ path pay that the pack8 GEMV path does not?** The
candidates are the q8_1 activation quantization (a separate kernel, 1.3 percent of
prefill, so not the cost itself), the dp4a arithmetic's lower effective rate against
a 32x32 tile, and the shared-memory tile staging with its per-K-block barrier.

That is a question for a profile with stall attribution, not more arithmetic.
