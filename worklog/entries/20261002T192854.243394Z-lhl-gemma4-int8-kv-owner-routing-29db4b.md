# Gemma4 INT8 KV cache owner and layer routing

## Summary

The fourth bounded Gemma D12 prerequisite, and the first that makes the INT8
path *reachable*: the runtime cache owner the writer and consumers operate on,
the layer routing that selects them, and the request/runner wiring that reaches
them through `hipengine.LLM.generate()`.

The previous three units registered the BF16-source per-token/head INT8 writer
and the single-row decode and multi-row prefill consumers, each gated against an
independent CPU representation oracle. Nothing allocated the buffers they read,
nothing handed a layer one `Gemma4LayerInt8KV`, and `Gemma4GGUFGenerator`
rejected every `kv_storage` other than BF16. This unit closes that gap:

* `hipengine/runtime/gemma4_int8_kv.py` (new) owns the INT8 payload, the
  per-token/per-KV-head scale plane, one shared identity page table, the
  per-row live counts and absolute append positions, and the FP32
  query/context scratch the consumers require -- and nothing else. There is no
  persistent BF16 shadow and no BF16 K/V cache on this path.
* `gemma4_layer` gains `_run_int8_attention`, which widens the BF16 query to
  FP32, runs the registered writer and consumer, and narrows the FP32 context
  back to BF16; and `_select_int8_kv_kernels`, which resolves both from the
  registry by declared capability and launch shape (never by model or artifact
  identity).
* `Gemma4Runner` accepts `kv_storage`/`kv_scale_dtype`/`kv_scale_granularity`,
  resolves them to a concrete mode, and allocates either the BF16 caches or the
  single INT8 owner.
* `Gemma4GGUFGenerator` resolves the request's storage controls, rebuilds the
  runner when the requested storage changes, and refuses an unsupported
  layout by name.

It is a correctness and reachability unit, not a speed or memory claim. The
default BF16 path is unchanged byte-for-byte; the BF16 kernels, the writer and
both consumers are untouched; there are no new flags, no torch, no artifact
identity gates, and no backend/quant branches in dispatch or engine code.

## Integration defect found and fixed

`_run_int8_attention` (written in the previous unit) called the prefill
consumer without its `rows` argument:

```
gemma4_attention_prefill_int8_per_token_head_spans(
    query, key, value, out, spans, rows, max_context_len, block_size, ...)
```

The layer passed `max_context_len` where `rows` belongs, so every argument after
`spans` was shifted. The decode consumer has no `rows` argument, so the decode
path was correct and the bug was invisible until a multi-row prefill actually
ran. The consumer's shape check refused it (`scale shape must match block_size
and num_kv_heads`) rather than computing a wrong answer, which is why the GPU
route test caught it as a launch-time metadata refusal. The call is now built
explicitly per shape: the row count is inserted between the spans and the
context bound for the multi-row prefill consumer only.

This is exactly the gap the previous entry's "Next" flagged: the prefill
consumer had a registration and an oracle but no caller, so the wiring was never
exercised.

## Design decisions

* **One owner, not per-layer caches.** The INT8 layout, page table and scale
  metadata are shared across layers; only the payload and scale pointers differ.
  One `Gemma4Int8KVCache` per runner keeps the page table a single resident
  identity buffer and the live counts/positions a single pair of staged arrays.
* **Two views of one page table.** The writer's prompt ABI indexes a row-major
  `[rows, block_table_len]` table; the multi-row prefill consumer declares one
  shared 1-D `[block_table_len]` table. Both are aliases of one identity page
  table whose rows all repeat, so they describe the same shared arena rather
  than two prefixes -- which is what the previous entry required of the
  integration. `Gemma4LayerInt8KV` carries both as `writer_spans` and
  `consumer_spans`.
* **One extra page.** `int8_kv_block_table_len` is `capacity // block_size + 1`,
  so `block_size * len` is strictly greater than `capacity`. The writer refuses
  a table whose `block_size * block_table_len` does not strictly exceed its
  `max_live_count`; a full cache reaches exactly `capacity`, so the extra page
  is what keeps a full request runnable instead of a boundary refusal.
* **Absolute positions.** `begin_block` stages `positions[i] = write_offset + i`
  and `counts[i] = positions[i] + 1`. The writer consumes the position as the
  append slot; the consumer consumes the count as the causal prefix and the
  position as the query's own absolute position. A decode step at absolute
  position 5 therefore reads slot 0 *at position 5*, which a slot-index oracle
  silently gets wrong -- the GPU test asserts exactly this case.
* **`auto` is BF16.** `kv_storage="auto"` resolves to `bf16`, so the comparison
  path is what an unqualified request gets. `int8_per_token_head` is the only
  INT8 layout the writer and consumers implement; `per_token_head` granularity
  and fp16/fp32 scales are the only accepted combinations. Anything else is a
  named capability miss, never a silent downgrade to BF16.
* **Decode-graph capture is refused, not disabled.** The direct INT8 consumer
  validates its live counts, row positions and page table with a synchronous
  device-to-host readback, which cannot be recorded into a HIP graph. The
  session refuses capture up front, before staging anything, and names both
  routes that make the request runnable ("Run without capture, or request bf16
  KV storage"). It does not silently drop the requested storage: the INT8 cache
  is still exactly what runs without capture.
* **Rebuild on storage change.** A runner's storage is fixed for its lifetime,
  so a request that changes it rebuilds the runner (the loaded weights are
  reused) rather than silently serving the previous mode's cache.
* **Block-fit planning follows the storage.** `_resident_bytes` and
  `_fit_prefill_block` take the selected storage and scale dtype, so the INT8
  path is planned against the INT8 owner's size, not the BF16 cache's.

## Review repairs

An independent source review of this candidate (still unstaged at
`e6a958948`) confirmed four defects. All four are repaired here; none loosens a
consumer's limit and none changes arithmetic.

**1. The runner validated the unselected consumer's shared-memory bound.**
`runtime/gemma4.py` called the BF16 `gemma4_attention_shared_bytes` after
storage resolution regardless of which consumer was selected. At `head_dim`
512 the direct INT8 consumer needs `(capacity + head_dim + 16) * 4` bytes and
the BF16 prefill kernel needs `(capacity + head_dim + 256) * 4`, so contexts
between the two bounds -- including the INT8 edge itself -- were refused for a
kernel the request would never launch. `runtime/gemma4_int8_kv.py` now exposes
`int8_kv_consumer_shared_bytes`, and the runner validates only the selected
consumer's contract. Both limits are unchanged.

*RED/GREEN*: `tests/test_unit_gemma4_runner_lifecycle.py` gains admission cases
at 8192 (unrelated to both bounds), 15700 (between them), 15856 (the INT8 edge),
15857 (one past it), and 15700 on BF16. Reverting the fix fails the three
cases that must distinguish the bounds and leaves the two controls passing.

**2. `close()` on an unused runner needed the HIP runtime.**
`Gemma4LayerScratch.free` called `get_hip_runtime()` unconditionally, so the
fake-allocated lifecycle tests failed on a host without `libamdhip64.so` -- a
no-ROCm CI or publish runner. An unused scratch owns no events, so its release
is now a pure host operation and acquires the runtime only when it has events to
destroy.

*RED/GREEN*: the mock-level guard is
`test_close_releases_an_unused_runner_without_loading_the_hip_runtime`. Because
that only proves a mock was reached, `tests/test_integration_gemma4_no_hip_lifecycle.py`
re-runs the lifecycle and layer-contract modules in a subprocess where
`ctypes.CDLL` refuses to load `libamdhip64.so` at all, and requires every
collected case to pass with nothing skipped. Reverting the `free` fix fails that
subprocess gate for real.

**3. The live gate leaked the model.**
`tests/test_live_gemma4_int8_kv_generate.py` created an `LLM` and never closed
it. The body now runs under `try/finally llm.close()`, so an assertion failure
still releases the resident weights, and it additionally asserts that the
replaced INT8 owner is closed after the storage switch and that public
`close()` clears the runner and the weights.

**4. The INT8 layer route silently dropped an arbitrary mask.**
`gemma4_layer_forward_bf16` accepted an INT8 cache while ignoring
`keep_mask_ptr` and `attention_mask_is_causal`. The direct INT8 consumer derives
its mask from causal order plus the layer's sliding window and never reads a
keep mask, so the route supports exactly the causal/window contract. It now
rejects a non-causal mask -- and a second cache alongside the INT8 one -- before
any device work, naming the contract it needs.

*RED/GREEN*: `tests/test_unit_gemma4_int8_kv_layer_contract.py` records every
launcher the layer would call and asserts the call list is empty on refusal, and
that the causal/window case still enters `_run_int8_attention`.

## Capabilities and limitations

- Supported: `kv_storage` in `{"auto", "bf16", "int8_per_token_head"}`;
  `per_token_head` scale granularity; fp16 or fp32 scales; the two Gemma 4
  geometries `(16, 8, 256)` and `(16, 2, 512)`; any positive `block_size`; and
  any context that fits the *selected* attention consumer's 64 KiB shared-memory
  budget. Those budgets differ: the direct INT8 consumer needs
  `capacity + head_dim + 16` floats and the BF16 prefill kernel needs
  `capacity + head_dim + 256` floats, so at `head_dim` 512 the INT8 bound is the
  looser one -- 15856 tokens against 15616. The 15700-token admission test lies
  between these limits. Admission applies exactly one of
  them, chosen by the resolved storage.
- Refused by name: any other `kv_storage` value, any other scale granularity or
  scale dtype, and a context that cannot fit the selected consumer's shared
  memory. These are capability refusals, not evidence gates.
- Decode-graph capture is unsupported on the INT8 path and says so; the INT8
  cache runs normally without capture.
- No persistent BF16 shadow is allocated, so this is *not* a bit-exact match to
  the BF16 path: it is the writer's INT8 representation reconstructed as
  `float32(int8) * float32(scale)`. The GPU route gate is on that
  representation, against the independent CPU oracle.
- No quality, throughput, latency, memory-savings or long-context claim is made.
  Only that the route runs, is selected, and matches the representation oracle.
- The INT8 owner uses one `block_size` (default 256) for all layers; it does not
  yet key page size per layer type.
- `hipengine serve` reaches the same generator, but no server-level request was
  exercised in this unit.
