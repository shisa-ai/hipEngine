# the narrowed-walk bit-identity argument rests on lane assignment which key-parallel changes

## Summary

The sliding-window optimisation ships without a numerical gate, and the reason is
stated in `tests/test_gpu_gemma4_attention_geometry.py`:

> A sliding row's mask is zero for every column below `max(0, row_offset + row -
> window + 1)`, so the kernel may start its walk there. The dropped columns
> contribute `expf(-inf) == 0` to both reductions and **the surviving terms keep
> their lane assignment and their order**, so the result is bit-identical rather
> than merely close. That is what lets the per-row bound ship without a numerical
> gate, and **it is the whole safety argument**.

That argument is specific to the current lane mapping, where lane `l` holds
dimensions `l + 32k` of a key and the key-to-warp assignment is independent of
where the walk starts. A key-parallel layout assigns **lane = key**, so dropping a
row's leading keys shifts every surviving key's lane. The tree in
`20260928T093102` sums over lanes in a fixed descending order, so a shifted
assignment sums the same values in a different order and the result is no longer
bit-identical.

Two consequences for the port, neither of which the plan records:

**The narrowed-walk optimisation cannot be carried over naively.** It is not
enough to start the loop at `first_kept`; the key-to-lane mapping has to be made
independent of the walk start, or the window bound needs a numerical gate it does
not need today. The first is preferable and is a design constraint on the kernel,
not a detail.

**The existing geometry suite does not gate a new kernel.** It asserts
bit-identity between two walks of the *same* kernel, over `head_dim` 256 (the
warp-per-key path) and 6 (the block-sum path). A `gemma4_flash` route needs its
own test comparing it against `gemma4_plain` on the same inputs at exact equality,
which is the shape the suite already uses -- `np.testing.assert_array_equal` over
`rng.standard_normal` inputs, not an allclose tolerance.

## Changes

None. No source file changed and no kernel written. This entry records a
constraint read from an existing test's own statement of its safety argument.

## Validation

Read from `tests/test_gpu_gemma4_attention_geometry.py`:

- `test_a_narrowed_prefill_walk_is_bit_identical_to_a_full_walk` builds
  `tokens, keys = 8, 16`, draws `query`, `key`, `value` from
  `rng.standard_normal`, builds a sliding mask
  `[[np.uint8(c <= t and t - c < window) for c in range(keys)] for t in range(tokens)]`,
  and ends with `np.testing.assert_array_equal(narrowed, full)`. Exact equality
  over non-trivial random data, so the gate is not vacuous.
- Its docstring carries the lane-assignment sentence quoted above, and notes that
  `head_dim` 256 takes the warp-per-key path while 6 takes the block-sum path, so
  both are covered independently.

The lane mapping it depends on is from `gemma4_warp_key_logit`: `const int d =
lane + 32 * k`, with the key-to-warp assignment from `gemma4_attention_prefill_kernel`
(`j = threadIdx.x >> 5` stepping by 8 warps).

## Next

   start, so the window bound keeps shipping without a numerical gate. Treat that

2. Add the `gemma4_flash` vs `gemma4_plain` exact-equality test alongside the
   existing geometry cases; the suite's own idiom is the template.

   directly rather than only through an end-to-end comparison, so a violation
