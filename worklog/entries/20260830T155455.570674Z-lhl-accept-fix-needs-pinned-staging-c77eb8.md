# Accept upload fix needs pinned staging; async alone is not enough

## Summary

Before #17 is implemented, two constraints found by reading the call sites. They change
the fix from "switch
`memcpy` to `memcpy_async`" into "needs a pinned staging arena", and they are cheap to
honour but expensive to
discover by shipping a silently-wrong change.

## Changes

- Decision only; no code touched.
- Supersedes nothing: refines the fix spec in `20260830T155357…`, which measured 96.5% of
  the accept window in
  these uploads.

## Constraints

1. **Async on stream 0 does not fix it.** Every existing copy in
   `_enqueue_target_batch_accept` passes stream
   `0` (qwen35_gguf_mtp2.py:2260-2275, `HipMemcpyKind.DEVICE_TO_DEVICE, 0`), i.e. the
   legacy default stream.
   For pageable host memory, CUDA-family runtimes document that `MemcpyAsync` may execute
   synchronously, and the
   legacy default stream additionally synchronizes with all blocking streams. So routing
   the same pageable numpy
   arrays through `memcpy_async(..., 0)` can keep the exact same stalls. That behaviour
   must be measured on
   gfx1100, not assumed either way -- but a pinned arena is what makes the win structural
   rather than dependent
   on driver generosity.
2. **There is no pinned host allocator in the tree.** `hipengine/core/memory.py` exposes
   only device allocation
   plus blocking `copy_host_to_device` / `copy_device_to_host`; `grep` for `HostAlloc`/`pinned` in
   `hipengine/core/hip.py` finds nothing. So the fix adds one (a once-allocated, reused
   host arena), which puts
   it in `hipengine/core/*`, a declared high-conflict file, not in the engine module alone.
3. **Lifetime hazard if the copy becomes async.** `_upload_accept_array` copies from
   `np.ascontiguousarray(values)`;
   that temporary is freed when the call returns. Once the copy is merely enqueued, the
   array can be freed while
   the transfer is still in flight, which corrupts accept inputs silently - arithmetic
   stays defined, results are
   wrong. Any async variant must retain the source arrays on `_PhysicalAcceptPending` (it
   already survives to
   `_read_target_batch_accept`, which synchronizes) and say so in a comment.

## Validation

- Read from source at the cited lines; no command run for this entry. Constraint 1's
  runtime behaviour is flagged
  as needing measurement rather than being asserted as fact for this driver.
