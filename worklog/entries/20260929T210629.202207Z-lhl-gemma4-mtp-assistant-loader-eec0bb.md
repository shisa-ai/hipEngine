# M1: admit the Gemma 4 MTP assistant on capability and map its shared KV

## Summary

Punchlist M1, the prerequisite that opens the MTP chain: hipEngine can now read
a `gemma4-assistant` sidecar, decide whether it can execute alongside a given
target on capability alone, compute which target KV cache every draft layer
reads, and discover `MTP/*.gguf` next to a target artifact. The contract was
derived from the real files rather than assumed, because the punchlist's prose
and the metadata disagree in an instructive way: the assistant's own
`embedding_length` is 1024 while its `embedding_length_out` is 2816, and the
*target's* hidden size is 2816 -- so M1's stated check ("`embedding_length_out`
equal to the target's hidden size") is exactly right once you know the target
width is 2816 and not the 1024 the MTP section quotes for the assistant.

## Validation

- **Ground truth read from the artifacts.** Assistant: arch
  `gemma4-assistant`, `block_count` 4, `embedding_length` 1024,
  `embedding_length_out` 2816, `head_count_kv` (8,8,8,2), pattern
  `[T,T,T,F]`, 49 tensors (2 root + 4x11 + 3 tail), F32/Q8_0 only. Target:
  `embedding_length` **2816**, 30 layers, pattern `[T,T,T,T,T,F] x 5`,
  `head_count_kv` `[8,8,8,8,8,2] x 5`, attention `q(4096, 2816)`,
  `k/v(2048, 2816)`.
- **Mapping matches what M3 already specifies.** `shared_kv_target_layers`
  returns **(28, 28, 28, 29)** -- sliding draft layers on the target's last
  sliding layer, the global draft layer on its last global layer, both derived
  from the two patterns. That is the "target's layer 28 / 29 cache" M3's draft
  step reads, so the mapping was confirmed against an independent row rather
  than invented here.
- **Admission is capability-only.** Rejects on: wrong arch, output width that
  is not the target's hidden size, a vocabulary the target cannot embed,
  shared-KV width that differs from the mapped slot, a missing
  `nextn.pre_projection`, shape drift on a shared tensor, and a layer table
  that disagrees with `block_count`. No file name, path or digest takes part.
  Each rejection names the capability, so `require_gemma4_mtp_valid` raises a
  message a user can act on.
- **Tests.** 13 unit + 2 live pass. The broader `-k "loading or gguf_loader or
  mtp or gguf_header or discover"` batch: **2735 passed, 2 skipped, 0 failed**.
- **Docs gates:** `check_all.py` still reports only the pre-existing
  `published command drift` (the 2026-09-21 zbook artifact citing a script in
  `hipEngine-main`); `check_docs.py` 151 documents valid.
- **Audit gate fails pre-existing and not on this change:**
  `python3 audit/audit.py check` exits 1 with 11 candidate / 18
  doc-path-drift / 2 kernel / 2 ledger / 2 stub / 8 ungoverned-flag-branch
  untriaged rows. Grepping every kind's open list for this change's files
  matches nothing (the only `mtp` hit is `runtime/qwen35_gguf_mtp.py` drift in
  `docs/REFACTOR.md`, another unit's). Budget not raised -- triage belongs to
  whoever owns those rows.
- **Not RED-first, recorded as `docs/TESTING.md` asks:** the capability
  contract (2816-vs-1024, the 28/29 mapping, the per-layer KV widths) could
  only be read from the real artifacts; a test written first would have encoded
  a guess about a contract nobody had yet observed.
- **Correction to an internal figure:** iteration 123's check evidence said
  "three separate 2112/1024/1024 projections". The target's projections are
  `q(4096, 2816)` and `k/v(2048, 2816)`. The wrong figure appeared only in
  loop-internal measurement text and in no committed file; this entry records
  the right one.
