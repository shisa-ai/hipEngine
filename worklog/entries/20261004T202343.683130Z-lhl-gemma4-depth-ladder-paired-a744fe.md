# Gemma 4 depth ladder paired against llama.cpp, and the prefill census repaired for the current tree

## Summary

The ten-shape depth ladder is measured on both engines and joined into one
artifact, and the prefill census that explains the gap is repaired and run
across depth. Decode is competitive through the middle of the ladder and
crosses below the comparator past 16384. Prefill is ahead at 512 alone and
falls monotonically after it, reaching **0.23 at 131072**. The loss is not
distributed: measured attention is **19.9 percent of the prefill step at 512
and 92.9 percent at 131072**, and the selected variant is `gemma4_staged` at
every depth, so the profile never takes the WMMA prefill path at any shape in
this ladder.

## Changes

- `scripts/gemma4_prefill_kernel_census.py` — repaired for the current tree.
  It intercepted **no attention** and priced the MoE block at **0.2 ms**,
  charging 71 percent of the step to host time. Two changes since the
  2026-09-28 census caused that, and both had to be fixed:
  - Production prefill attention now resolves through the kernel registry.
    `gemma4_gguf_profiles._register_attention_variants` registers the launcher
    **by function object**, so patching the attention module's attribute
    reaches nothing; the route probe shows the production profile selects
    variant `gemma4_staged`. The census now wraps the *selection*
    (`dataclasses.replace(selection, launcher=spy)`), which also survives a
    variant being added later — the property whose absence produced the silent
    zero. The layer's own route names (`_bf16`, `_tiled`, `_aotriton`) are
    patched too, for the path taken when `prefill_attention_variants` is unset.
  - The MoE block launches on its own stream (`stream=moe_stream`), so an
    event pair recorded on stream 0 brackets nothing and the block reads as
    free while its work reappears as host time. Events are now recorded on the
    stream each call was launched into, and the stream is reported per kernel.
  - Also: `--context` (the probe was pinned at 4096, which caps depth below one
    block), `--corpus {synthetic,campaign}` (the synthetic id range prices the
    expert block for a routing pattern no real prompt produces — it is 2x
    slower at the same shape, 5.242 s against 2.66 s at 2048), the missing
    expert routes in `_EXPERT_LEAVES` (the `_dual`, `wmma`, `mmq` and
    `grouped` leaves were absent, so their time showed as glue), and the
    harness now records its own command.
- `scripts/assemble_gemma4_depth_ladder.py` — new. Joins both ladders and
  refuses to pair a row unless `prompt_ids_sha256` matches across engines, which
  is what makes the ratios paired rather than coincidental. Also joins the
  census and computes the findings block from the rows, so a re-run cannot drift
  from the prose.
- `benchmarks/results/2026-10-04-gemma4-gfx1151-depth-ladder-paired.json` — new.
  Nine paired rows, six census points, five limitations, three open items.
- `benchmarks/CHANGELOG.md` — one line for the artifact.

## Validation

- All ten shapes ran on both engines. `prompt_ids_sha256` **matches at every
  shape**, and `public_path_parity` is True on every hipEngine row.
- llama.cpp 8192 and 16384 are **rejected by that harness's own repeatability
  gate** (its greedy output ids differ between samples). Their timings are kept
  as diagnostics and no ratio from them is a published claim.
- 262144 is not measured on either engine. llama.cpp cannot serve it: it caps
  the slot context at the model's training context (262144) and a
  262144-token prompt leaves no room for a sampled token. hipEngine needs about
  95 GiB against about 94 GiB available and about 91 minutes per pass.
- Drift: llama.cpp's warmup-matched control moves +0.6 percent prefill and
  -0.2 percent decode, so the ladder's internal comparisons are sound.
  hipEngine's own control ran `warmup 0` against the ladder's `warmup 1`, so its
  delta is a cold-start penalty rather than drift; the artifact says so instead
  of quoting it as drift.
- The census repair was verified by its own failure signal: the zero-attention
  warning fired before the change and attention is attributed after it. The
  accounting closed from 28.9 percent to 100.2-105.2 percent of wall time.
- Gates: `scripts/docs/check_all.py` (4/4), `scripts/check_artifact_provenance.py`
  (208/208 parsed, 0 violations), `scripts/sync_benchmark_readme.py --check`.

## Measured attribution

Campaign corpus, production profile, HIP event pair around every kernel the
decoder layer launches, recorded on that kernel's own stream.

| Prompt | prefill wall | attention | share | expert block | dense + lm head |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 512 | 468.3 ms | 93.1 ms | 19.9% | 215.3 ms | 120.9 ms |
| 2048 | 2673.2 ms | 1261.0 ms | 47.2% | 802.1 ms | 432.2 ms |
| 8192 | 14675.9 ms | 9184.0 ms | 62.6% | 3135.2 ms | 1686.5 ms |
| 32768 | 110690.8 ms | 88820.0 ms | 80.2% | 12409.7 ms | 6659.7 ms |
| 65536 | 396101.8 ms | 346920.6 ms | 87.6% | 27842.7 ms | 14883.4 ms |
| 131072 | 1405497.1 ms | 1305993.5 ms | **92.9%** | 55528.2 ms | 29661.0 ms |

Attention cost per prompt token rises 0.182 → 9.964 ms while cost per token per
token of depth *falls*, which is the sliding-window signature: the window-bounded
layers stop growing and the global layers keep scaling. This confirms the fitted
cost model independently and shows it is if anything conservative — the fit
implies about 89 percent at 262144 while the measurement already reads 92.9
percent at 131072.

The selected variant is `gemma4_staged` at every depth, on stream 0.

## Side finding, not investigated

The main stream (~225 ms at 512) and the MoE stream (~215 ms) **sum to about the
wall time**, so across 30 layers the two streams are effectively serialized
rather than overlapped. The census accounts for slightly over 100 percent of wall
time because a small part does overlap. A side stream that buys no overlap is a
separate question from depth and is recorded rather than pursued.
