# Attribute the strix-llama.cpp HIP prefill lead on Qwen3.8-27B Q4_K_M

## Summary

The `strix-llama.cpp` HIP prefill lead on Qwen3.8-27B `Q4_K_M` (gfx1151) is now
attributed. About half of it is one compile-time table:
`ggml/src/ggml-cuda/mmq-config-rdna3-5.cuh`, the RDNA3.5 MMQ tile configuration.
Rebuilding upstream llama.cpp `002a12ad2` with that single file replaced by the
fork's version — and nothing else — lifts 4K/128 prefill from **382.918 to
409.464 tok/s (+6.93%)**, 1K/128 from **389.939 to 416.313 (+6.76%)** and 512/128
from **386.342 to 413.539 (+7.04%)**, i.e. 52-54% of the fork's
**432.427/440.554/436.867** over the same upstream binary. The remaining ~1.2 s
per 4K pass is the fork's tiled Gated DeltaNet kernel with its transposed concat,
the Q8_1 MMQ activation quantizer, flash attention, and norm/convert fusions.

## Validation

- **Isolation by rebuild.** Scratch tree = `git archive` of upstream
  `002a12ad2` + the fork's `mmq-config-rdna3-5.cuh` copied over, built with the
  same `build-hip.sh` flags as the upstream binary. `diff` confirms the config
  file is the only source difference.
- **End-to-end.** `scripts/llamacpp_bench_with_peak.py --phases prefill
  --workloads 512/128 1K/128 4K/128 --repetitions 5` (llama-bench, `-ngl 99
  -fa 1 -ctk/-ctv bf16 -dev ROCm0`), one binary at a time, same host and session
  as the main comparison. Artifacts:
  `ablation/upstream-hip-prefill.json`, `ablation/upstream-hip-mmqconfig-prefill.json`,
  `ablation/halobox-hip-prefill.json`.
- **Kernel attribution.** `rocprofv3 --kernel-trace` on `-p 4096 -n 0 -r 1` for
  all three binaries. Total kernel time 21.115 s (upstream) / 19.726 s
  (config-only) / 18.612 s (fork) over two 4096-token passes. Q4_K MMQ
  12.095 / 10.763 / 10.827 s; every non-MMQ group is within 0.01 s between
  upstream and the config-only build. Profiled throughput matches the unprofiled
  runs (383.29 vs 383.40 upstream, 430.70 vs 431.94 fork), so profiler overhead
  is negligible.
- **Geometry.** Same kernel name, same 4608 dispatches, same 240 VGPR / 128 SGPR
  per thread; 136x4 blocks of 256 threads (upstream) become 272x4 blocks of 128
  threads (config/fork) for the 17,408-row FFN projections. `rocprofv3` reports
  grid dimensions in work-items, which is why both reported dimensions move.
  An env-gated `printf` in `launch_mul_mat_q` (`ablation/launcher-args.txt`)
  confirms `nrows_x`/`ncols_max`/`J` are unchanged and only `I` (128 -> 64) and
  `nthreads` (256 -> 128) differ, so the observed geometry is fully explained.
- **Output smoke check.** All three builds served one greedy prompt
  (`temperature 0`, `top_k 1`, `n_predict 48`) through `llama-server` and
  returned identical token ids; `ablation/output-check.txt`. This is one prompt
  and 48 tokens, not a numerical-equivalence proof.
- No RED test and no hipEngine kernel change, so no in-tree correctness gate
  applies to this unit; the correctness question here is the external engines'
  own numerics, covered by the smoke check above.
