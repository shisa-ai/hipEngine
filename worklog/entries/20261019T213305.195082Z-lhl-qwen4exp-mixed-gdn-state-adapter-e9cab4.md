# Qwen4Exp mixed-layout GDN and Conv state adapter

## Summary

M2 prerequisite. `qwen4_exp_mixed_layout.py` names a shared target pass — root
rows, prepared candidate rows, and the physical request slot each request owns —
but the request-indexed Conv and GDN owners require the state slots named in one
dispatch to be distinct, so a prepared chain cannot be handed to them as
independent rows: depth 1 extends depth 0's state inside the same request.

`hipengine/runtime/qwen4_exp_mixed_gdn.py` is the adapter between those two
contracts. It consumes one mixed layout plus one set of shared projected rows and
runs the same two indexed primitives in depth waves. Wave `d` carries each
request's row at depth `d` — at most one row per request — so every slot in a
dispatch is unique, and row `(request, d)` reads the snapshot its parent row
produced. Working state is one `Qwen4ExpBatchGdnState` with one slot per physical
row, so provisional slot `p` *is* physical row `p`, root slots are copied from the
caller's live owner, and deeper slots from their parent row. Nothing in the pass
writes the live owner, so verification cannot mutate the state it is deciding
about. Two admission rules keep that safe: an optional `owner_of(slot)` callback
re-checks every request's layout owner token before `run` and `commit` touch the
device, and a commit consumes the completed pass before its first copy so a
partially applied transaction cannot be replayed.

Scope: adapter and tests only. No kernel, registry, scheduler, serving or runner
change; no new flag; no attention, PLE, QSA or output-projection work. Sharing the
input projections across every physical row is the future caller's job, so this
does not close shared mixed execution and does not claim to.

## Changes

- `hipengine/runtime/qwen4_exp_mixed_gdn.py` (new):
  - `Qwen4ExpMixedGdnGeometry` — the GDN/Conv geometry read from the live state
    owner, so a chain is never verified against a different head geometry than
    the state it commits into. Rejects `head_dim != 128`, a non-integral
    `num_v_heads / num_k_heads`, a `qkv_width` that is not a multiple of 4 (the
    float4 Conv-row alignment the recurrence requires), and the conv owner's
    channel and kernel bounds.
  - `Qwen4ExpMixedGdnWave` / `Qwen4ExpMixedGdnPlan` / `plan_qwen4_exp_mixed_gdn`
    — pure host decomposition: one wave per prepared depth, rows in ascending
    physical order (so a wave depends on physical positions, not on request
    declaration order), `parent_rows[i] == -1` at depth 0 and the parent's
    physical row otherwise, `slots == rows`. The plan re-derives its waves from
    the layout and refuses a mismatch, checks every request slot against the live
    slab width, and admits each wave through both primitives' own admission
    helpers (`qwen4_exp_gdn_indexed_state_indices`,
    `qwen4_exp_conv_indexed_state_indices`) so the row bound and slot uniqueness
    are the owners' rules rather than restated ones.
  - `Qwen4ExpMixedGdnProjectedRows` — the caller's four projected row buffers
    (`attn_qkv`, `attn_gate`, `ssm_alpha`, `ssm_beta`), one packed row per
    physical row.
  - `Qwen4ExpMixedGdnWaveScratch` — the widest wave's contiguous operand rows
    (`qkv`, `gate`, `alpha`, `beta`, `conv`, `core`) with `row_ptr`/`width` and a
    retry-safe `close` (free newest-first, pop after each free).
  - `Qwen4ExpMixedGdnAdapter.allocate/run/commit/close` — allocates the
    provisional state, wave scratch and per-physical-row result buffer after every
    layout/ownership/geometry check, and releases a partial allocation on failure.
    `run` copies root snapshots from live, copies each deeper snapshot from its
    parent, gathers the wave's four operands, dispatches
    `qwen4_exp_linear_attn_conv_decode_indexed_f32` then
    `qwen4_exp_gdn_decode_rowsplit_indexed_f32` once per wave, and scatters the
    gated output into `core` (`[total_rows, core_width]`, physical row order) for
    the caller's shared `ssm_out` projection. `commit(accepted_counts)` validates
    counts through `layout.commit_destinations` and copies exactly those two
    snapshot blocks per request into the live slot.
  - Admission epoch (`owner_of`). A layout names the owner token each request was
    admitted under, but the adapter only knew the live state owner, so it could
    not tell a current layout from one whose slot had been released and re-admitted
    to another request — those rows would copy the new occupant's state as a root
    snapshot and commit over it. `allocate(..., owner_of=slot -> token)` stores an
    optional callback and `require_owner_epoch()` compares every request's layout
    token against the slot's token now: at allocation, and again in `run` and
    `commit` before the first device copy. A mismatch (including token `0`, which
    means the slot is unowned) is refused with the slot, both tokens and the
    request named. Without the callback the adapter trusts the caller's slot
    ownership and the check is a documented no-op.
  - One pass, one commit. `run` publishes `verification_pending` only after the
    last wave, and `commit` requires and then consumes it *before* its first copy.
    A commit that fails partway through has already written some requests' live
    state, so replaying it would apply a half transaction as if it were whole; the
    next `commit` refuses until a fresh `run` rebuilds every snapshot from the live
    owner. Validation failures (rejected accepted counts, stale owner token) raise
    before the flag is cleared, so a corrected call is still the same transaction.
- `tests/test_unit_qwen4exp_mixed_gdn.py` (new): 31 CPU cases with a recording
  fake runtime and recorded dispatches — wave decomposition, ragged chains and AR
  peers, three topological physical permutations, the full copy/dispatch order of
  one pass, repeated-pass reproducibility, live-state immutability, every selected
  accepted depth, admission-epoch reuse (re-admitted slot, unowned slot, per
  request, and rejection before allocation), commit containment (partial commit
  not repeatable, failed pass not committable, recovery via a fresh pass),
  rejection before allocation, rejection before mutation, and cleanup retry.
- `tests/test_gpu_qwen4exp_mixed_gdn.py` (new): 9 device cases against the real
  indexed kernels, with an explicit HIP-availability guard and the shared
  `hip_test_target_arch` build fixture. The oracle is the existing
  `tests/test_gpu_qwen4exp_batch_gdn.py::_cpu_step` (segmented CPU recurrence plus
  sigmoid-gated RMSNorm), replayed wave by wave over a physical-row provisional
  slab; the caller's shared input projection and the `ssm_out` projection are the
  same numpy expressions that module already uses, applied on the CPU. Coverage:
  two chains of different lengths plus an ordinary AR peer, semantic and
  interleaved physical orders, per-row output and snapshot equality with the
  oracle, exact permutation invariance of row results, live-state isolation during
  a pass, an unowned live slot keeping every byte, every partial accepted prefix
  and full acceptance committed byte-exactly from the right snapshot, and
  cancellation by discarding a provisional pass and rerunning it byte-identically.
  **Not executed here**: the parent owns the device, so these cases were compiled
  and collected on CPU only (`--collect-only`, 9 collected).

Design points worth keeping:

- **No new arithmetic.** Both indexed owners run their per-row body per block, so
  a row's output and final state are the same bytes
  `run_qwen4_exp_batch_gdn_token_mixer` produces for the same row inputs and input
  state, whatever the wave width. The adapter adds no numerical variant and its
  tests assert dispatch shape and state provenance, not kernel values.
- **Snapshot per physical row, not per wave.** Every snapshot must stay
  addressable for an accepted-prefix commit, so the pass keeps `total_rows`
  snapshots instead of ping-ponging one working slot per request.
- **Ownership is an epoch, not a slot index.** `slot` says where a request's state
  lives; `owner_token` says whose it is. Only the callback can answer the second
  question at run time, which is why it is re-checked per call rather than cached
  from allocation.
- **Cost, stated rather than hidden.** Gather, scatter and snapshot copies are
  synchronous device-to-device copies: about `7 * total_rows` copies per pass, and
  the state copies dominate the bytes (`2 * total_rows` blocks of
  `num_v_heads * 128 * 128 * 4` bytes each — one mebibyte per four-deep request at
  four value heads). The buffer mapping (`core`, `wave`, `working_state`, the
  `*_row_ptr` and `*_snapshot_ptr` accessors) is what a later runner needs to
  replace those copies with strided operands or a wave-shaped projection.
- **The GPU tolerance is inherited, not re-measured.** The device cases reuse
  `ORACLE_ATOL`/`ORACLE_RTOL` (`4e-6`) from the independent-request mixer test,
  whose envelope covers the row-split recurrence and the row-count-dependent GEMM
  variants. The mixed pass adds one difference that envelope did not see: the
  projections are one numpy GEMM over all physical rows while the oracle projects
  per wave. Each device case prints its measured maxima so a bound that is too
  tight is visible in the log rather than silent.

## Next

- Runner integration: one shared input projection over every physical row, then
  this adapter, then the shared `ssm_out` projection from `core`. The runner should
  pass `owner_of` from the batch owner's admission table — without it the adapter
  cannot see a slot released and re-admitted between layout compilation and the
  pass. Attention, PLE and QSA state for mixed rows are separate prerequisites;
  this unit deliberately does not reach them.
- If the synchronous gather/snapshot copies become the bottleneck, the next step
  is a wave-shaped projection (project only the wave's rows) or strided operands,
  not a wider adapter.
