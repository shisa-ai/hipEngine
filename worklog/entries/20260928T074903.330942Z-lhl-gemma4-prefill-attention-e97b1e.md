# an eight times larger k and v working set costs only 25 percent so the kernel is not bandwidth bound

## Summary

`20260928T074823` found that the prefill kernel reads K and V 1536 times more than necessary and
projected 4-8x from tiling over query rows. **An experiment that varies only the K/V working set
shows the kernel is far less sensitive to those bytes than the projection assumed.** The
redundancy is real; the sensitivity is not what the byte count implies. **The projection was
wrong by roughly an order of magnitude and query-row tiling is a ~25% lever, not a 4-8x one.**

## The experiment

Hold everything that determines work fixed -- `tokens=2048`, `heads=16`, `head_dim=256`,
`keys=2048`, `window=1024`, so **32768 blocks and identical FLOPs and identical LDS traffic** --
and vary only `nkv`. That changes the K/V working set by 16x without changing a single
arithmetic operation:

| nkv | query heads per kv head | unique K/V | strict ms | tiled ms |
|---|---|---|---|---|
| 1 | 16 | 2.10 MB | **50.29** | 55.32 |
| 2 | 8 | 4.19 MB | 55.85 | 61.88 |
| 4 | 4 | 8.39 MB | 60.21 | 65.81 |
| **8** | **2** | **16.78 MB** | **62.74** | 66.93 |
| 16 | 1 | 33.55 MB | 62.55 | 67.73 |

## What it says

**An 8x working-set increase (2.10 MB to 16.78 MB) costs 1.25x in time.** A kernel dominated by
K/V traffic would lose far more than 25% to that.

**So the kernel is not bandwidth-bound at 2048 tokens.** There is a real and measurable cache
effect of about 25% -- L2 matters, and the curve flattens above `nkv=8` where the working set
exceeds what the cache holds -- but it is a secondary term.

**And the strong form of `20260928T074823`'s claim is refuted.** The 1536x byte redundancy is
correct arithmetic, but **the measured sensitivity to those bytes is ~25%, so query-row tiling
would gain at most about that at this shape.** The 4-8x projection came from dividing bytes by a
bandwidth figure **without first testing whether the kernel was sensitive to the bytes at all.**

**What survives from that entry, and is worth having:** the artifact's `16q/8kv` geometry sits at
**62.74 ms** while the best case in the table is **50.29 ms** at `nkv=1`. **So a real ~20-25% is
available from better K/V reuse** -- worth doing, and not the headline fix.

## What the primary cost still is

**With the bandwidth explanation measured and largely excluded, the three-pass LDS dependency of
`20260928T073550` is again the standing explanation for the 2048-token figure**, and this is the
second independent result pointing there -- the first being that `dense keys=2048` is
superlinear in key count (2.05x time for 1.14x keys), which a bandwidth-bound kernel would not
be.

**The tiled variant's consistent ~10% deficit at this shape (55.32 vs 50.29, 66.93 vs 62.74) is
also consistent:** at one tile it pays barriers without any occupancy benefit, so it measures
what the extra barriers cost.

## The method note

**This cost one experiment and no kernel.** The previous entry built a 4-8x projection from a
byte count and a bandwidth spec, and this one tested the premise in about a minute of GPU time.
**Projecting from a resource total is not the same as measuring sensitivity to that resource**,
and the gap here was an order of magnitude. The cheap experiment should have come first.
