Mechanism notes for the remaining attention headroom:

- The decode kernel launches `tokens * num_heads` = 16 blocks (the
  `grid_size.x=4096` in the trace is work-items, 16x256), so 16 of 96 CUs are
  occupied per layer launch, and each block walks its key range serially in
  tiles (tile 8 = 5 barriers per 8 keys). Per-launch cost tracks the
  microbenchmark's keys-linear prediction (0.263 ms at 544 keys -> ~0.53 at
  ~1088), i.e. the kernel is behaving as measured; it is simply still the
  dominant term.
- Splitting keys across more blocks would need a cross-block combine whose
  FP reordering is **changed arithmetic** (the row-max chain itself would stay
  exact — masked logits enter as `-INFINITY` — but slice sums rescale), so it
  is gated on the deferred teacher-forced evaluator freeze.
- Sliding-window prefix slicing would be bit-exact (masked keys already enter
  the max chain as `-INFINITY` and contribute exact zero addends) but does not
  help the metric row: at 1024p decode the position tracks ~1088 against a
  window of the same order, so the removable prefix is a few percent.

q4_k candidate, corrected from G1: `hipengine/kernels/hip_gfx1100/quant/gguf_q4_k_pack8_gemv.py`
registers four `pack8_gemv_decode_*` entry points (the G1 note "no registered
q4_k family" is wrong). What is still true: the production rows=1 q4_k tensors
run `gguf_q4_k_selected_prefill_out` (58 launches/step), and
`_gemv_decode_dispatch`'s q4_k branch only rewrites variants already named
`gemv_*` (`gguf_linear.py:7819`), so the rewrite never fires on the variant
the runtime actually arrives under. The selection point that assigns that
variant is the next thing to locate before touching dispatch. Registering or
re-routing any of this is changed arithmetic against the current default and
likewise owes the evaluator freeze.
