# The exported route manifest cannot answer the P6e prefill question: it is a decode manifest

## Summary

This unit set out to replace the last inference in the P6e audit with a
measurement. It did not succeed, and the reason is worth recording because it is a
trap the next attempt would fall into too.

The inference: `_prefill_native_chunk` only attempts the resumable executor when
the session's `kv_attention_source` is `int8_direct` (`qwen35_gguf.py:8084`). Since
`fallback_reasons` was empty, the branch that fires
`int8_direct_full_prompt_prefill` on a decline was never entered, which implied the
source is not `int8_direct` and the resumable path is never even attempted.

`hipengine_resident_route_manifest_info` already exports `kv_attention_source` as a
label, so the plan was to read it from the existing scrape with no engine change.
The harness now does that, using a new `_metric_sample_labels()` (multi-label, since
the existing single-label helper would lose the meaning) with a
quote-aware `_split_prometheus_labels()`.

## Changes

The harness gained `_metric_sample_labels()` and a quote-aware
`_split_prometheus_labels()` so a multi-label family can be read without losing
which label carries the meaning. The engagement gate records `kv_attention_source`
and `resumable_kv_source` beside `executor_modes`. Four tests were added.

## Validation

Measured on GPU, `--packed-layer-outer`, env confirmed seen as `"1"`:

```json
{
  "claim_level": "exact_hybrid",
  "kind": "gguf_packed_ar_execution_manifest",
  "kv_attention_source": "unavailable",
  "logical_c": "2",
  "mode": "decode",
  "physical_execution_width": "2",
  "rows": "2",
  "serial_decode_fallback": "false",
  "throughput_claim_eligible": "false"
}
```

The label reads `unavailable` because the exported manifest is the **last
execution manifest**, and by the time the scrape happens that is a **decode**
manifest (`mode: decode`, `kind: gguf_packed_ar_execution_manifest`), whose builder
does not populate `kv_attention_source`. Only the serial-fallback manifest kind
carries it. So the metric answers "what did the last decode do", not "what is this
session's KV layout", and reading it as the latter would have produced a wrong
conclusion from a real measurement — the failure mode this audit exists to catch.

The gate now records `kv_attention_source` and `resumable_kv_source` beside
`executor_modes`, so the artifact states that the value is `unavailable` rather than
implying the question was answered. Other readings are unchanged:
`packed_layer_outer_env_seen: "1"`, `executor_modes: {"None": 2.0}`,
`oracle_observed_peak_owners: 0.0`, `resumable_path_engaged` FAIL, the other seven
gates PASS, `passed: false`, `performance_claim: false`.

31 tests pass in `tests/test_gguf_p6e_cancel_refill_proof.py`, including that
`_metric_sample_labels` reads a five-label family, that an absent family yields
nothing rather than a fabricated source, and that `_split_prometheus_labels` does
not split on a comma inside a quoted value or on an escaped quote.

## Honest limits

- This unit produced no new information about why the layer-outer route declines.
  It removed a wrong way to find out. The previous entry's inference still stands
  unverified.
- The harness reads one sample of the manifest family. If several sessions publish
  manifests, only the first is read, so the recorded labels describe one session,
  not necessarily the one whose prefill was instrumented.
- The `unavailable` value is the engine's own fallback spelling for a missing
  manifest field, so it cannot be distinguished from a genuinely absent manifest by
  the label alone. The accompanying `kind` and `mode` labels disambiguate it here.
