# An open MTP breaker scope resolves the request to AR and says so

## Summary

The restart-scoped MTP circuit breaker failed the request it was protecting:
an explicit `speculative_mtp: true` request whose (model, backend, profile,
context) scope was open got `503 mtp_circuit_breaker_open`, while an operator
rollback of the *same* condition resolved the request to AR and reported
`route_decision.reason = mtp_operator_rollback`. Both states mean one thing —
the promoted MTP route cannot run for this scope — and AR is the exact fallback
for every admitted MTP scope, so a 503 withheld a completion the client could
have received, and left it to rediscover the downgrade. The two states now
behave identically: resolve to AR, report why, keep serving.

Decision: **degrade to AR, never 503.** The route decision carries the breaker
snapshot, and `hipengine.speculative_mtp` carries `effective_route="default"`
plus `decision_reason="mtp_circuit_breaker_open"`, so a client that asked for
MTP can see the substitution in the same response instead of inferring it from
an error body. The breaker still does its job — no MTP launch happens for an
open scope — and the operator still sees the regression in the state, the
transition log, and the capabilities manifest.

Two adjacent defects surfaced while making the reported state truthful:

1. **The scope's context bucket was never computed.** `_MTPCircuitBreaker.scope`
   called `_prepared_context_tokens(prompt)` for each prompt, but that helper
   takes an *engine* and reads the resident session's `max_sequence_length`
   (`api.py:10991`). For any prompt — text, token tuple, or
   `PreparedPromptInput` — it returned `None`, so every scope collapsed to
   `(model, backend, profile, "unknown")` and the documented "context scope" did
   not exist. It now buckets by the realized prompt token length (rounded up to
   256) via `_prompt_context_tokens`, leaving text prompts scope-unknown rather
   than counting characters as tokens. Live: the opened scope is
   `["unknown", "hip_gfx1151", "production", "256"]`.
2. **Streaming resolved the route outside the batcher.** The batcher's batch
   shape reports the realized route for non-streaming requests, but a streamed
   response reports it in the done chunk from the endpoint's own
   `generation_route`/`generation_route_decision`. Applying the fallback only in
   `_run_group` would have downgraded the work while the client still read
   `speculative_mtp`, so the two streaming endpoints resolve it too.

The response surface is unchanged for every other case: a request that already
resolved to AR keeps its decision, and the promoted automatic route is only
touched when the breaker is actually open for its scope.

## Changes

- `hipengine/server/api.py`: new `_mtp_unavailable_route_fallback` — the single
  authority for "this MTP route cannot run", covering operator rollback and an
  open scope. Called from the batcher's streaming branch, the batcher's realized
  route resolution, and both streaming endpoints (before dispatch, so the
  reported route and the executed route are the same value); re-checked in
  `_generate_prompts` so a direct caller degrades instead of launching a closed
  route. The 503 raise is gone.
- `hipengine/server/api.py`: new `_prompt_context_tokens`; `_MTPCircuitBreaker.scope`
  uses it instead of passing a prompt to the engine helper.
- `docs/API.md`: the breaker paragraph now states the bucket definition and the
  AR resolution with its reported fields.
- `tests/test_integration_server_api.py`: RED first — the batcher case expected
  `OpenAIHTTPError(503)` and now asserts AR with no third MTP launch; new
  non-streaming and streamed endpoint tests assert 200 +
  `route_decision.reason` + breaker snapshot + `effective_route` /
  `decision_reason`; new scope test pins the bucket math and the text-prompt
  case. The operator-rollback test also pins the snapshot now in its decision.

## Next

- Streaming MTP failures are not recorded against the breaker: only
  `_generate_prompts` calls `record_failure`, so a streaming-only client can
  never open a scope (a stream that fails mid-response is contained by the
  endpoint's error path instead). The downgrade above therefore only fires for
  streaming after a *non-streaming* failure opened the scope. Recording the
  failure in `_stream_single`/`_stream_many` is the obvious fix and needs its own
  RED contract.
- The scope's model field reads `"unknown"` on this engine: `scope()` falls back
  to `getattr(engine, "model_id"/"model_path")`, and the resident GGUF engine
  exposes neither, so two different models on one server would share a scope.
  Harmless today (one model per server) but it is the wrong identity to report.
