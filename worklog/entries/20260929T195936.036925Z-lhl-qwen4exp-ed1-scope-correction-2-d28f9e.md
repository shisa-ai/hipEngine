## What was verified, and one claim narrowed

The production default `hipengine_qwen4_exp_q5_1_selected_grouped_prefill_pair2_row_publish_bf16_bf16_out`
is `launch_q51_pair2<true, true, true, true>`, launching
`q5_1_selected_grouped_prefill_pair2_bf16_kernel<true, true, true, true>` at grid
`((n+7)/8, min(experts,64))`, 128 threads, LDS
`2*8*128*sizeof(float) + (k/32)*24` = 8,192 + 480 = 8,672 B for k=640.

Its body stages the Q5_1 metadata cooperatively: `threadIdx.x < blocks` loads `d`,
`m` and the high-bit word into LDS once per output pair, `wr[p]` is hoisted outside the
`base` row loop, and `REGISTER_CACHE` additionally caches five weights per thread per pair
through `q51_cached_weight`. The fallback `compact_rowbatch8` owner stages the same three
fields the same cooperative way.

**Narrowed:** the earlier entry implied the production owner stages what ED-1 proposed.
More precisely, both production owners stage the **metadata** (d, m, qh); the **nibbles**
are still read per-lane from global in both, via `wr[p]`. So the staging ED-1 proposed is
implemented for the metadata operand, not for the full 24-byte block.

**One reading I checked and rejected:** the launch's `(k/32)*24` term looks like a full
24-byte-per-block staging budget, but the LDS pointers `d` / `m` / `qh` consume only
`blocks*2` floats + `blocks*2` floats + `blocks` uint32 = 400 B at k=640. The `24` is an
allocation allowance, not evidence of a full block copy. Treating it as a block copy would
have overstated the claim.
