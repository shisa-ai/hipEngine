# Gemma 4 prefill attention: AOTriton flash for the sliding layers

## Summary

The 25 sliding-window layers now run the vendored AOTriton BF16 flash-attention
kernel at `head_dim` 256 for prefill blocks instead of the engine's exact
staged-logit class kernel, which a kernel trace showed to be ALU-bound on its
per-key reduction. W7900 prefill at 1024 tokens: 1394 -> 1702.8 tok/s (+22.1%),
decode flat at 39.27. RX 7900 XTX, a lane the model could not run before the
gate/up split removal freed peak memory: 1886.8 prefill / 43.87 decode. Traced
attention falls 216 -> 73 ms of a 555 ms per-prefill kernel budget.

## Changes

- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention.py`:
  `aotriton_prefill_admits` states the four-term mask-semantics predicate
  (mask asserted causal, more than one query row, window non-binding, vendored
  image for the head dim); `gemma4_attention_prefill_aotriton` is the leaf.
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_layer.py`: the prefill attention
  dispatch consults the predicate and calls the flash leaf when it holds.
- `hipengine/runtime/gemma4.py`: exposes the causal-mask assertion the predicate
  needs.
- Tests: `tests/test_unit_gemma4_attention_flash_admission.py` (predicate truth
  table), `tests/test_gpu_gemma4_attention_aotriton_parity.py` (fixture parity
  against the exact kernel at both head geometries).
- Docs: campaign iteration 153, recommended-order item 2 updated;
  `benchmarks/README.md` Gemma section, `benchmarks/CHANGELOG.md`,
  `benchmarks/results/2026-09-27-gemma4-flash-attention-prefill-{xtx,w7900,
  2048-w7900}.json`.

## Validation

- Campaign gate `gemma4_teacher_forced_gate.py gate --prompt 2048 --prefill 1024`
  against `gate_auto.npz`: `kl_max` 0.000773 against the 0.05 bar, `kl_mean`
  5.5e-06, `kl_p95` 1.5e-05, `kl_p99` 1.4e-04, 0 of 1023 top-1 flips. Lower than
  the 0.001341 the same gate measures with the exact attention kernel.
- Gate verdict bit-identical before and after the host-side wrapper caching pass.
- Artifacts carry `public_path_parity` true; the prefill and decode rates come
  from the public `LLM.generate()` path.
- Kernel trace (`rocprofv3 --kernel-trace`) confirms the intended path: the
  sliding instantiations are gone from the class-kernel totals and
  `attn_fwd`/`FONLY__*bf16@16_256_*` appear with the expected per-launch times.
