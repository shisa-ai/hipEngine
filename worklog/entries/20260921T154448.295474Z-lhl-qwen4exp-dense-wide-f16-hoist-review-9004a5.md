# Wide F16 activation hoist: review list closed, engine steps blocked on host memory

## Summary

The wide Q8_0 dense prefill activation hoist is wired at launch time
(`_launch_dense_wide_f16_staged` + `wide_f16_activation_session`, env opt-out
`HIPENGINE_GGUF_Q8_DENSE_WIDE_F16_ACT=0`) but not yet promoted: its census,
interleaved A/B and qualification need the 4096-token `code-p4096` run on
UD-Q4_K_XL, and the host currently has 22 GB available against a 98.6 GB GTT
allocation held by an `hipengine serve` process in the sibling worktree
`/home/lhl/hipEngine-main` (Qwen3.8-27B-Q4_K_M, started 17:48). That process is
not this worktree's and was left alone.

What *was* closed is the reviewer's validation list, four of five items with
hardware evidence:

1. **Real activations**: `tests/test_gpu_qwen4exp_dense_wide_f16_activation_hoist.py`
   passes 7/7 on gfx1151, including bit-identical output against the f32-input
   owner at rows 257/512/1024 with the activation scaled so the f16 conversion is
   lossy. The kernel's own invariant explains why: the f32 owner converts during
   LDS staging with `static_cast<half_t>` and the hoisted
   `q8_0_f32_to_f16_kernel` uses the same cast, so both paths put identical f16
   bytes in LDS.
2. **Tail instantiations**: the wide dispatch selects exactly one variant,
   `dense_wide256_f32_f32_out`, and it has a registered
   `dense_wide256_f16in_f32_f32_out` sibling, so the hoist covers 100% of the
   route's launches. The other registered tilings (`dense_wide64x256`,
   `dense_wide64x128`) have no f16-input export and are unreachable from the
   dispatch; they keep the f32-input owner by design.
3. **Scratch lifetime**: the workspace is the same bounded allocation the B2
   staging route binds (`_ensure_prefill_f16_staging_buffer`), bound by two
   context managers in the same `with` block, and both the cast and the consumer
   launch run on one stream, so consecutive launches are serialized. The GPU test
   `test_scratch_is_converted_per_launch_not_cached` pins the per-launch
   conversion.
4. **Reset / graph replay**: `_wide_f16_activation_context` is entered per
   prefill call, so the buffer pointer is re-read after any reset rather than
   captured once. No prefill path is graph-captured (`stream_begin_capture`
   appears only in `maple_graph`, `moe_graph`, and the moonshine runtimes, none
   of which is this prefill), and a captured launch would capture the cast and
   the consumer together anyway.
5. **Fallback path**: an absent or undersized workspace, an unregistered
   sibling, a non-wide variant, and the env opt-out all keep the f32-input owner
   (unit + GPU tests).

A coverage guard was added so the one silent failure mode cannot come back:
`test_route_variant_has_a_registered_f16_sibling` runs the real dispatch and
asserts the selected variant's f16 sibling is registered under the kernel
backend. A renamed route variant (`dense_wide512_*`) or a dropped export fails
it; the two unexported tilings are asserted to stay unregistered. This is the
same silent-decline shape that hid the route once already, when
`_ensure_linear_kernel_registered` was missing from the launch-time lookup and
the census showed the f32-input symbol 792 times.
