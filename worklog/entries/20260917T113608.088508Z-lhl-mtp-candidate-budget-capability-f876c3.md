# Resolve the speculative candidate budget from model capability data

## Summary

A default Qwen3.8 server now executes speculative MTP without any speculative
flag. `--speculative-candidate-budget` no longer defaults to a hardcoded 4: an
omitted value resolves from the loaded model's retained serving evidence (the
deepest depth the resident physical cell qualifies), a generic provider keeps
its own declared shape (Laguna B4), and a pinned value is used unchanged. On
`gfx1151` with `Qwen3.8-27B-Q4_K_M`, a server started with no speculative flags
reports `candidate_budget {requested: null, resolved: 3, source:
model_plugin_evidence}`, promotes the automatic route, and a plain greedy
request runs 18 draft cycles with 45 of 54 drafts accepted.

The reported depth, its source, and the admission reason are now visible at
startup and in `/v1/hipengine/capabilities`, and an explicitly enabled MTP
server that cannot admit logs a warning naming the rejecting axis instead of
silently falling back to normal decoding.

## Changes

- `hipengine/speculative/serving.py`: `resolve_max_qualified_candidate_budget`
  answers the deepest depth the retained rows authorize for a physical cell. It
  drops only the requested-depth axis, so every other identity axis must still
  match, and prefers automatic-eligible rows over explicit-only ones exactly as
  admission does. `None` means no retained row describes the cell.
- `hipengine/models/qwen35.py`: both Qwen GGUF plugins expose
  `max_qualified_candidate_budget(key=...)` over their own evidence.
- `hipengine/generation/qwen35_gguf.py`: the serving key construction moved into
  `_speculative_mtp_serving_key` and is now shared by plan resolution and the new
  `max_qualified_speculative_candidate_budget`, so the capability answer cannot
  drift from the admission key. `speculative_candidate_budget_default()` exposes
  the dense MTP owner's own declared depth.
- `hipengine/llm.py`: `speculative_candidate_budget` accepts `None`. An omitted
  budget resolves through evidence, then the generator's declared default, then
  stays unresolved (no typed plan, admission off). Because evidence describes a
  physical cell, the lookup waits until the owner declares the capacity it will
  serve — a constructed-but-unprepared generator has no resident runner and only
  a fallback capacity, and resolving there reported `generator_default` for a
  cell whose evidence does qualify. The pinned depth is still published on the
  resident owner that consumes it. `speculative_candidate_budget_resolution`
  reports requested/resolved/source.
- `hipengine/server/api.py` / `__main__.py`: `ServerConfig` accepts an omitted
  budget, the CLI reads the environment value only when set, and one decision
  function reports requested/resolved/source for capabilities, the startup line
  and the provider-route check. Startup warns when `speculative_mtp_serving` is
  `enabled` and the retained evidence rejects the cell, naming the reason.
- `hipengine/speculative/registry.py`: `DEFAULT_PROVIDER_CANDIDATE_BUDGET` is the
  single source of the provider's declared shape (the `SpeculativeProviderConfig`
  default), shared with the server's pre-load report.
- `docs/ENVS.md`, `docs/QWEN38-GFX1151-MTP-SERVING-IMPROVEMENTS.md` (P0 marked
  done), `docs/REFACTOR.md` (candidate-budget entry resolved; two follow-up debts
  recorded: the two budget knobs, and the three-source resolution ladder).

No backend or model branch was added to the engine: the resolution asks the
loaded model plugin's evidence, the attached provider's declared shape, or the
generator's declared default.

`candidate_budget=requested:None resolved:None source:pending`, and the
post-load line reports `resolved:3 source:model_plugin_evidence`. Arm B's
generated text is byte-identical to arm A's, so the unqualified pinned depth
falls back to normal decoding rather than to a different route. No unsupported
route gained admission.
