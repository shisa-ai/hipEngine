# the gemma4 MTP draft loop accepts 78 percent of its proposals

## Summary

The verified assistant head now drives an actual draft loop, and the loop's
acceptance is measured. Over 48 rounds of four drafts on a fixed chat-templated
prompt, greedy on both sides:

| draft slot | 0 | 1 | 2 | 3 |
| --- | --- | --- | --- | --- |
| compared | 48 | 39 | 32 | 26 |
| accepted | 39 | 32 | 26 | 16 |
| rate | 0.812 | 0.821 | 0.812 | 0.615 |

Overall 113/145 = 0.779, mean accepted length 4.06 tokens per round including the
free one. llama.cpp's `--temp 0 --top-k 1` MTP run on this artifact reports
`#acc rate/pos = (1.000, 0.750, 0.500, 0.500)` and `#mean acc len = 3.75`, but
over four draft calls against a different prompt; this is 48 rounds and a more
reliable estimate.

`Gemma4MtpDrafter` exists because the three things a caller can get wrong from
outside are all silent:

- **The seed.** It must come from the forward that produced the token being
  drafted from, before any later forward moves the runner's hidden row. Priming
  from a stale row still produces fluent drafts, just not ones the target agrees
  with.
- **The views.** `Gemma4Runner.shared_kv` captures the live position count when
  it is called. Views taken per step, or taken after a verify pass, either read a
  moved count or expose the query's own K/V to the head.
- **The position.** Every step of one draft uses the same `n_past`; advancing it
  is llama.cpp's non-shared branch and is wrong for a Gemma 4 assistant.

The class proposes and does not accept. Acceptance stays with the caller's verify
pass, which is what the measurement script drives.

## Changes

- `hipengine/runtime/gemma4_assistant.py`: `Gemma4MtpDrafter`, a dataclass over a
  head and a runner with `draft(token) -> list[int]`. `Gemma4Runner` is imported
  under `TYPE_CHECKING` so the module keeps no runtime dependency on the backbone
  runner.
- `scripts/gemma4_mtp_acceptance.py`: the measurement, with the fixed prompt, the
  greedy verify, and the per-slot accounting. A round stops at its first
  rejection, so a slot's rate is over the rounds that reached it -- the same
  convention as llama.cpp's `#acc rate/pos`.
- `tests/test_gpu_gemma4_assistant_forward.py`:
  `test_the_drafter_proposes_tokens_the_backbone_accepts`, 8 rounds, asserting a
  first-slot rate and an overall rate above 0.5.

## Validation

- `uv run pytest tests/test_gpu_gemma4_assistant_forward.py -q` -- 3 passed.
- `uv run python scripts/gemma4_mtp_acceptance.py --rounds 48 --drafts 4` --
  `accept rate/pos : (0.812, 0.821, 0.812, 0.615)`, `overall : 113/145 = 0.779`,
  `mean acc length : 4.06`, 162 tokens in 7.4 s.
- The test's bar is 0.5, far below the measured 0.779, because what it is for is
  a draft loop that does not work at all. A mis-seeded recurrence, a stale view,
  or an advancing position each collapses acceptance to near zero while leaving
  the single-step forward test green.
