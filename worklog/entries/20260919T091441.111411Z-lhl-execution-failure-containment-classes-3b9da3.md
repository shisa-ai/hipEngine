# Claim the `partial` and `committed` containment classes, and cover the fatal paths

## Summary

`docs/EXECUTION-PROFILES.md` section 4.3 declares four mutation classes, but the
only runner that claimed containment ever emitted `none`: any failure at or
after a step's first device call closed the whole service. The 2026-09-18
decision entry recorded that as the open remainder
(`worklog/entries/20260918T015727.780379Z-...-abff1a.md`: "Claimable
`partial`/`committed` mutation classes need a runner-specific quiesce-and-restore
proof"), together with "cleanup-failure and simulated-fatal-device coverage are
named requirements in 4.3; only the fatal-reporting path has a test today".

The proof turned out to be **step accounting plus retirement**, not a rebuild.
The runner knows exactly which rows can have reached device work — it marks each
row immediately before its first device call, and marks every row of a grouped
prefill call before that call — so a claim can name precisely those rows, and
the loop already retires named rows through the per-request release path that a
single-row claim uses. Rows the step never reached are provably canonical and
stay unnamed. No context replay is needed, which matters because a replay would
have to re-prefill every peer of a cancelled row.

Two classes are now real:

- **`partial`** — prefill or decode entered its device phase without claiming a
  canonical commit. The claim names the marked rows plus the row that raised.
- **`committed`** — a speculative cycle recorded a canonical commit before the
  failure. The eager commit path publishes the row's visible tokens and cursor
  while the outer scheduler is still behind it, so those rows cannot fall back
  to autoregressive decoding.

`unknown` stays unclaimable and is now *reported*: a refused failure is raised
as a named `GenerationExecutionFailed` with `state_mutation: "unknown"`, so
`health()` names the phase, the affected rows and the deepest cause instead of
a bare exception.

A third case surfaced on the real device rather than in review: a decode tick
whose device phase has no packed work (every row's first token came from
prefill) was refused, because the step's mutation window had already flipped to
`unknown` even though nothing in that tick could have advanced a row. The
runner now records that a device phase completed with no enumerated work, so a
failure in its post-device check is `none` over the failing row and a
cancellation landing there no longer closes the engine.

## A real defect in the eager commit path

Auditing the eager path for a `committed` claim found a live misclassification.
`_commit_eager_cycle_row` appends a row's visible tokens, advances its cursor and
records its outputs, but the outer scheduler only learns about them when the
cycle result is returned. If a later row of the same cycle failed, the adapter's
`recover_cycle_failure` ran its pre-commit check (`session.position ==
slot.seq_position`), which a *committed* eager row still satisfies because
`_commit_eager_cycle_row` sets `seq_position` from the target session's own
position. The cycle was therefore recovered as `precommit_failure_ar_fallback`
and the row continued autoregressive decoding **from the advanced position**,
dropping the committed tokens from the client stream and advancing the model
past tokens the scheduler never recorded.

The adapter now records each row's commit on the runner as it happens and
refuses the AR fallback for a cycle that committed anything
(`postcommit_eager_commit_ar_fallback_refused`). Containment then claims those
rows as `committed` and retires exactly them, so the service keeps serving the
rest of the batch instead of closing. The defect is covered by a RED test at the
adapter seam.

## Next

- The scope choice for a failure after a *completed* packed step is the whole
  stepped group: the group's results are discarded by the failed step, so the
  peers are retired rather than replayed. A per-row replay (the MTP target
  rebuild already does this for its own rows) would keep peers alive at the cost
  of re-prefilling their contexts; it is not obviously worth the cost for a
  cancellation, but it is the remaining narrow-scope opportunity.
- The empty-device-phase claim rests on `decode_batch` being the only decode
  entry point that reaches device work. A future device path added without a
  mark would leave `_execution_device_phase_empty` set and be contained as
  `none`; the mark-before-device-call discipline is what the claim depends on,
  and the proof's post-device scenario is the regression check for it.
- The staged `_PhysicalTargetCommitError` path still refuses containment
  (`unknown`): the commit may or may not have landed, and the doc requires the
  status to be resolved before retirement. Resolving it would need the physical
  commit to report its own boundary.
- `HIPENGINE_DEBUG_SAMPLED_ROUTE` remains the debug switch for cycle-failure
  reasons; the new refusal reason is recorded on the row either way.
