# P6 service yield holds for blocking requests and slow consumers

## Summary

Task #14 (the P6 parent) names coverage axes beyond the streaming cancel/refill
path that the P6e service proof already covered. Two of them had no evidence at
all: the **blocking (non-streaming)** request mode and **slow consumers**.

Both are now covered, and all seven gates pass on W7900 / gfx1100.

The reasoning for why these are the right test: the resumable yield lives in the
*scheduler*, not the transport. A yield that only worked for streaming readers
would be a real gap — a blocking caller and a backpressured reader must both leave
the engine free to serve another request. So each arm submits the same short prompt
as the reference arm while a long request runs concurrently, which makes the
reference text the exact expectation.

| Gate | Result |
| --- | --- |
| Cancellation reached the backend | PASS — counter 0 → 1 |
| Survivors exact (refill) | PASS — sha256 `118cf547...` |
| **Blocking survivor exact** | PASS — sha256 `118cf547...` |
| **Slow-consumer survivor exact** | PASS — sha256 `118cf547...` |
| Bounded acknowledgement | PASS — 825.9 ms |
| Bounded decode gap | PASS — refill p95 36.17 ms vs reference max 42.42 ms |
| Cleanup | PASS — drained, owner bytes back to baseline |

Arm detail: the blocking long request ran to completion (6,063 ms wall, 48 chars,
`finish_reason: length`) rather than being rejected, so it genuinely occupied a
slot during the survivor's window. The slow consumer's long request also completed
with 48 chars. Both survivors carry the identical sha256 as the reference.

## Changes

- `scripts/gguf_p6e_cancel_refill_proof.py`: `_completion_payload` takes a `stream`
  flag; SSE line handling is factored into `_consume_sse_line` so every streaming
  arm shares it; `_blocking_completion` adds the non-streaming mode;
  `_stream_completion` takes `per_line_delay_s` to model a slow consumer; two new
  concurrent arms and two new gates.
- `tests/test_gguf_p6e_cancel_refill_proof.py`: 5 new tests (19 total), including
  that an empty blocking survivor fails rather than passing vacuously, and that a
  slow reader which never completes is surfaced as its own field rather than hidden
  behind a passing survivor gate.
- `benchmarks/results/2026-09-11-w7900-p6e-cancel-refill-service-proof.json`
  (re-taken), `benchmarks/CHANGELOG.md`, `benchmarks/HARNESSES.md`.

## Validation

- `uv run pytest tests/test_gguf_p6e_cancel_refill_proof.py` — 19 passed.
- GPU run, cache-only (`HIPENGINE_REQUIRE_CACHED_BUILD=1`, pinned compiler version),
  3072-row long prompt vs 512-row short prompt, 24 decode tokens, 600 ms cancel
  hold, 600 ms concurrent lead, 40 ms per-line slow-reader delay,
  `max_active_requests` 2. Values above.

Honest limits:

- The slow-consumer arm throttles the *reader* (40 ms per SSE line). That models
  backpressure, but it does not drive the server's stream queue to a full-buffer
  stall, so a deeper backpressure bug would not necessarily surface here.
- The blocking arm's concurrency window is 600 ms of lead plus the survivor's own
  run; the long request is still prefilling when the survivor is submitted, but the
  arms do not assert that overlap from server-side state, only from the timing.
- Both survivors are 48 characters, so the exactness comparison is short (the same
  limit recorded for the cancel/refill gates).
- Still uncovered for #14: BF16 on this route, and host-side sampling. Long prefix
  suffixes are covered as a fail-closed decline (tested at the CPU level) rather
  than as a working yield path.
- `performance_claim` is false and no scoreboard row changed.
