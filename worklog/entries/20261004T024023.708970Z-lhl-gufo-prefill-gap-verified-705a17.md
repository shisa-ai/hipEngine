# The Qwen4Exp prefill gap to gufo is 5.2x, verified same-file and by wall clock, and uniform across families

## Summary

The `2026-10-04-gfx1151-gufo-vs-hipengine-same-file` packet reports gufo prefill
at 4.6x-7.0x hipEngine's on Qwen3.8-Flash-Next. That number is load-bearing for
the whole prefill campaign, and it was recorded without checking whether gufo's
`pp` is a real full-prompt prefill. **It is.** Two independent checks, both
below, confirm it, so the packet's ratio stands and the campaign's target is
5.2x, not the ~1.7x the older Vulkan-lane tables implied.

At matched granularity - one 4096-row pass, both sides traced - the gap is
**5.69x and uniform across every bucket**: dense projections 6.8x, routed MoE
5.6x, attention/GDN/router/other 4.6x. So no single kernel family is the
answer. It is also **not launch count or scheduling**: gufo issues 4,237
launches per prefill against our 2,766.

**Correction to this entry's first revision.** It claimed the gap was
"MoE-specific" on the strength of the same-file 27B `Q4_K_M` table. That table
is **not a dense-vs-MoE control**: `Qwen3.8-27B-Q4_K_M.gguf` declares
architecture `qwen35` (65 dense layers) while Flash-Next declares `qwen4exp`.
They are different model implementations with different kernel paths, so the
table shows the *qwen35* path is at parity with gufo, not that dense is fine.
The matched-granularity trace below is the correct reading and it refutes the
MoE-specific framing.

## Changes

### Why gufo's `pp` needed checking

gufo's table prints `pp4096 = 1695.37`. 4096 tokens in 2.416 s on a 40-CU
`gfx1151` iGPU is 15.6 TFLOP/s against a 29.7 TFLOP/s FP32 peak. That is
achievable but high, and gufo's own README describes `pp` as a "marginal rate",
which reads like a cached-prefix number. If it were cached, the 4.6x-7.0x
framing would collapse. No new benchmark was run for this decision beyond the
two checks and the two traces described here.

### Check 1: the source

`/home/lhl/gufo-src/src/cli/bench/bench.cpp`, Qwen path, prompt loop:

```cpp
restore_depth();                        // outside the timed region
const auto t0 = std::chrono::high_resolution_clock::now();
prefill();                              // ForwardPromptBatch(prompt_tokens, depth)
                                        //   + hipDeviceSynchronize()
const auto t1 = std::chrono::high_resolution_clock::now();
runs.push_back(static_cast<double>(p_len) / elapsed_sec);
```

The timed region contains the whole `ForwardPromptBatch` for `p_len` tokens and
a device synchronize. `restore_depth()` (which resets state) is outside it. The
same file's validation path cross-checks `ForwardPromptBatch` against
per-token `ForwardToken` under `[Prefill Validation]`. There is no cache reuse
inside the timed window.

### Check 2: wall clock

Predicted wall for `-p 4096 -n 0 -d 0 -r 2` is model load + 3 prefill passes
(1 warmup + 2 measured) at 2.40 s each = load + 7.2 s.

```
$ time gufo bench -m <shard1> -p 4096 -n 0 -d 0 -r 2 -v
[Model Load]: 45.2962 s
| Qwen3.8 Flash Next | 103.69 GiB | ROCm (HIP) | pp4096 | 1705.94 ± 0.85 |
WALL 53 s
```

53 s - 45.30 s load = 7.7 s against 7.2 s predicted. The rate is real, and
reproduces (1705.94 now, 1695.37 in the packet).

### The gap, stated as one protocol

Both numbers are a full 4096-token synchronized prefill on physical host
`gfx1151` (`55ea6c509d0b49eea8de7094a1023668`), UD-Q4_K_XL, production profile,
cached build. Prompt token sequences differ (gufo cycles `(i%1000)+100`;
hipEngine uses the committed fixture), which is a prompt-content caveat, not a
protocol one.

| engine | 4096-token prefill | tok/s |
| --- | ---: | ---: |
| gufo `98641a6` (prebuilt `8ca63994…`) | 2.40 s | **1705.94** |
| hipEngine, chunk 4096 | 12.42 s | 329.94 |
| hipEngine, chunk 1024 | 14.08 s | 290.47 |
| hipEngine, chunk 512 | 15.57 s | 261.48 |

**5.17x** at chunk 4096. The hipEngine rows are the counterbalanced pass sweep
(`20261004T020800.274714Z-lhl-qwen4exp-chunk-order-balanced-b49a03`), two
orderings, three reps per arm, arms agreeing to 0.3%.

### The 27B control is a different architecture, not a dense control

`benchmarks/README.md`, same-file same-host, Qwen3.8-27B `Q4_K_M`:

| shape | gufo pp | hipEngine pp (per-shape) | hipEngine pp (1 session) |
| --- | ---: | ---: | ---: |
| 512 | 383.53 | 357.10 | 407.99 |
| 1K | 392.36 | 406.18 | 405.90 |
| 4K | 382.74 | 398.82 | 398.56 |

At 1K/4K the two engines are within 4%. But `Qwen3.8-27B-Q4_K_M.gguf` declares
architecture `qwen35` (65 dense layers) and Flash-Next declares `qwen4exp`, so
this compares two *model implementations*, not two expert counts. What it
establishes is that the **qwen35 path is at parity with gufo**. It says nothing
about whether the qwen4exp dense projections are fast, and the trace below shows
they are not.

### Where the time goes: gufo

`rocprofv3 --kernel-trace` over `gufo bench -p 4096 -n 0 -d 0 -r 1`
(raw at `/tmp/gufo-prof/raw_kernel_trace.csv`, 8,475 launches, gufo held
1675.38 tok/s under the profiler):

- Total kernel time **4.84 s for 2 prefill runs = 2.42 s per prefill**.
- The trace spans 50.35 s against 45.37 s of model load, so the prefill window
  is ~97% GPU-busy.
- gufo's MoE is one fused family, `RoutedF16GEMMKernel<WeightType, ...>`, doing
  the gather, the quantized GEMM and the scatter together: 1.586 s over 2 runs
  = **0.793 s per prefill across 192 launches** (4 per layer x 48 layers).

### Where the time goes: hipEngine

From `2026-10-04-qwen4exp-prefill-kernel-breakdown` (chunk 1024, 4 prefill runs
in the trace, 85,696 launches):

- Total kernel time 65.358 s / 4 = **16.34 s per prefill**.
- MoE gate/up 20.42% + MoE down 11.49% + gate/up repair 3.25% + down repair
  3.18% = 38.34%, i.e. **6.265 s per prefill across 720 launches**.

Two things fall out that were not visible at chunk 1024:

- **The gap is uniform.** Every bucket is 4.6x-6.8x off, so this is not one
  broken kernel. The single widest bucket is the dense projections at 43.2% of
  prefill time, not MoE.
- **It is not launch count.** gufo issues 4,237 launches per prefill against our
  2,766 - **1.53x more**. The difference is per-kernel throughput, not
  granularity, and that refutes the "gufo fuses and we do not" reading of this
  entry's first revision.
- **240 `dense_gemv` launches run during prefill**, 0.498 s/run (3.6%). These
  are decode-shaped kernels on a prefill path.

### Derived efficiency, same arithmetic

Per 4096-token prefill the routed MoE reads ~73 GB of quantized expert weights
and does ~21.8 TFLOP (10 of 512 experts active, `expert_feed_forward_length`
640, `hidden_size` 2560, 48 layers, plus shared expert and router).

| | per-prefill | weight bytes/s | TFLOP/s |
| --- | ---: | ---: | ---: |
| gufo routed MoE | 0.793 s | ~92 GB/s | ~27.5 |
| hipEngine MoE (chunk 1024) | 6.265 s | ~11.7 GB/s | ~3.5 |

Peaks for `gfx1151` at 40 CUs / 2900 MHz: 29.7 TFLOP/s FP32, 59.4 TFLOP/s
FP16, ~256 GB/s LPDDR5X. gufo's routed MoE is at ~46% of FP16 peak and 36% of
bandwidth; ours is at ~6% of FP16 peak and ~5% of bandwidth. **8x apart on the
same math on the same silicon.**

This ratio is MoE-only and is quoted for the routed-expert block specifically;
the matched-granularity table above is the overall reading.

## Limits

- Prompt token content differs between the two engines. The 5.2x is a
  same-shape, same-host, same-file ratio, not a same-prompt ratio.
- gufo is a prebuilt binary at `98641a6` with `source.patch` applied; its
  current `gufo-src` HEAD is one commit ahead. The binary is what was measured.
- The TFLOP/s and GB/s figures are derived from config arithmetic, not from
  hardware counters. They are consistent across both engines and both
  directions, but they are estimates.
- One host, one model, one quant, one repetition count per engine.
