# the prefill kernel issues 3.4 percent of capacity so it is latency bound and the superlinearity is still unexplained

## Summary

With bandwidth excluded (`20260928T074903`), counting the kernel's instructions gives a hard
bound on the remaining explanation: **it issues 3.4% of what the machine could issue.** That
rules out throughput in every form and leaves latency. **One candidate mechanism fits, but it
does not yet explain the measured scaling, and that gap is recorded rather than smoothed over.**

## The count

For `dense keys=2048 tokens=2048 256d`, average 1024.5 keys walked per row:

| | warp-instructions | ms if fully issued |
|---|---|---|
| pass 1 (warp-per-key logit, ~25 per key) | 8.39e8 | 2.02 |
| pass 3 (LDS read + global read + FMA per key per thread) | 8.06e8 | 1.94 |
| **combined** | **1.65e9** | **3.95** |
| **measured** | | **116.30** |

Against 40 CU x 4 SIMD x 2.6 GHz = 4.16e11 warp-instructions/s. **So the kernel runs at 3.4% of
issue capacity.** Combined with 296 GFLOP/s against a ~26.6 TFLOP/s FP32 peak (1.1%), and with
the bandwidth alternative measured and excluded, **the kernel is latency-bound.**

**This also subsumes the three-pass LDS story.** `20260928T073550` framed the cost as three
passes over `logits_s`; the counting shows the *instruction* cost of those passes is under 4 ms.
**What matters is not how many LDS operations there are but that the chain through them is
serial.**

## The candidate mechanism, and where it fails

**Pass 3 is 2048 sequential iterations per thread, each: LDS read the weight, global read
`v_row[d]`, FMA into `acc`.** The global read is ~400 cycles of latency, and with ~48 warps per
CU the memory-level parallelism is nowhere near enough to cover 2048 of them in sequence.

**But the candidate does not explain the scaling.** Two measured points:

| window | keys walked | V loads per row | measured |
|---|---|---|---|
| 1024 | 1792 | 768.0 | 56.70 ms |
| 0 | 2048 | 1024.5 | 116.30 ms |
| **ratio** | **1.14x** | **1.33x** | **2.05x** |

**Neither walk length nor V-load count explains a 2.05x time ratio.** A latency model driven by
the number of dependent global loads would predict ~1.33x. **So the mechanism is incomplete, and
the superlinearity is currently unexplained.** Saying so is more useful than picking the
nearest story.

## What this changes

**Every fix attempted so far has been a throughput fix** -- tile the buffer to raise occupancy,
reduce LDS operations, improve K/V reuse. **All of them address how many operations the kernel
performs. A latency-bound kernel is not fixed by performing fewer operations; it is fixed by
exposing more independent work.** That is a different class of change:

1. **Register-block over keys in pass 1** so several independent reduction chains interleave.
   The kernel already carries `#pragma unroll 2` for exactly this reason, which is evidence the
   author saw the chain; 2 may be too few.
2. **Unroll pass 3** so several `v_row[d]` loads are in flight at once instead of one dependent
   load per iteration.
3. **Raise occupancy further** -- the tiled variant's context-independent 7 KiB already helps at
   long context, and the same argument applies at 2048 keys if latency is the binding
   constraint.

**All three are ILP/MLP changes rather than traffic changes, and none of them has been tried.**

## Validation

Instruction counts from the kernel's structure in `gemma4_attention.hip` (pass 1's warp-per-key
loop at ~25 warp-instructions per key including the 8 FMAs, 7 tree adds and 5 shuffle-adds; pass
3's per-key LDS read, global read and FMA). Issue capacity is 40 CU x 4 SIMD x 2.6 GHz. Times
from `20260928T074732` and `20260928T074903`. **These are counts and a capacity figure, not a
profiler trace** -- the 3.4% is an upper bound on issue utilisation derived from them, and a
profiler would settle it.
