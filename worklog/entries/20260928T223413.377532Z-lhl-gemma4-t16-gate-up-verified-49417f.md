# the gemma4 expert T16 route was already live, and its tile residency was unpriced

## Summary

This unit was assigned to wire up a "dead" Q4T16 gate/up route. **The route was
already live**: `a8b59363b` (worklog `20260929T050000`) wired it 42 commits before
this branch tip, and the assignment's premise -- "nothing in production ever sets
`t16_gate` or `t16_up`" -- does not hold at `5465e816b`. No wiring change was
needed, so this unit is the verification the assignment asked for plus **one real
defect that the wiring commit introduced**.

**The route, confirmed on the public surface, not asserted.** A 4096-token
`LLM.generate` under `HIPENGINE_EXECUTION_PROFILE=production` makes 8 prefill
chunks x 30 layers = 240 gate/up calls, of which **232 = 8 x 29 ran the T16 leaf**
and the remaining 8 are the single `gguf_q5_k` layer (29 layers are `gguf_q4_k`,
one is `gguf_q5_k`), which takes its own iu8 route. The loaded weights carry
`raw` 285,474,816 + `t16_gate` 146,702,336 + `t16_up` 146,702,336 bytes on all 29
Q4_K layers.

**End-to-end effect of the route, measured against its own fallback in one
process**: forcing the tiles unavailable (the fallback a tile-less weight takes)
gives 4.578 s median against 4.232 s for the live route on the same 4096-token
prefill -- **1.0817x, +8.2 percent, 346 ms per 4096-token prefill**, and the
fallback serves all 240 calls, so the required MMQ32 path still works in situ.

**The defect: `resident_bytes` raised on the real artifact.** The T16 wiring added
`derived_allocation_bytes`, which prices the tiles through
`derived_half_shape`. That helper read `spec.source.shape[2]` as `bytes_per_row`,
but GGUF reports shapes in *elements* -- `ffn_gate_up_exps` is
`(128, 1408, 2816)` where a row is 1584 bytes -- so the row length it passed was
`hidden` (2816), which is a multiple of 256 but not of the 144-byte Q4_K block.
`Q4_K_T16_SHAPE.validate` therefore raised `ValueError: bytes_per_row must be a
positive multiple of 144` for every real Q4_K expert stack, and
`plan_gemma4_gguf_resident_specs` + `resident_bytes` -- the loader's own
pre-allocation total, quoted as working over this artifact on 2026-09-27 -- could
no longer total anything. The row length is now derived from the tensor's own byte
count, which is exact for any block type the loader carries.

The cost figure is worth stating precisely, because the wiring entry's "+2.78
percent on the gate/up expert bytes" is the tile layout against the raw blocks it
is built from, not the resident cost of the change. The loader keeps `raw` (the
strict fallback reads it) and adds both tile halves, so one layer's gate/up
expert weight goes 285.5 MB -> 578.9 MB and the model's planned residency is
**16.995 GB of artifact bytes plus 7.92 GB of tiles = 23.75 GB** (the planner's
own figure, now computable). The measured `after_load` device figure on this run
is 28.4 GiB including the 8192-token KV cache and scratch.

## Changes

- `hipengine/loading/gemma4_gguf_device.py`: `derived_half_shape` returns
  `(experts, out_features // 2, nbytes // (experts * out_features))` instead of
  the logical third dimension, with a docstring that says which units the
  element is in and why the element count is not one. The only other caller,
  `materialize_gemma4_gguf_device_weight`, uses the first two elements and
  discards the third, so the repack path is untouched.
- `tests/test_unit_gemma4_gguf_device.py`:
  `test_expert_tiles_are_priced_from_the_stored_bytes` derives the expected tile
  bytes from the layout arithmetic (a tile block is 2368 bytes where the 16 Q4_K
  blocks it replaces are 2304) and asserts `resident_bytes(specs) == artifact
  bytes + tile bytes`. The stale comment in
  `test_resident_bytes_is_the_artifact_bytes` -- which described the raise as a
  fixture/planner mismatch -- is replaced by the reason the raw-only sum is still
  checked on its own.
