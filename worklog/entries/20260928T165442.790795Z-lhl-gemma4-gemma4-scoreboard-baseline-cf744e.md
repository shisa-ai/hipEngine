# Freeze the Gemma 4 scoreboard baseline with a one-command snapshot

## Summary

Before starting the punchlist's optimization candidates, the scoreboard needed
a baseline that both halves of it -- the unprofiled topline and the
`rocprofv3` family breakdown -- were actually linked to. They were not: the
measurement contract in the punchlist requires compact artifacts under
`benchmarks/results/` for the headline runs and family rollups, and a search
found none for the 2026-09-28 scoreboard. The table existed without its
evidence.

This unit adds `scripts/gemma4_scoreboard_snapshot.py`, which produces both
halves in one command against one commit on one physical GPU, and runs it to
freeze the baseline at `6d886f473`.

## Changes

- `scripts/gemma4_scoreboard_snapshot.py` (new): warms the JIT cache, runs
  `gemma4_campaign_bench.py` at each prompt length, traces the census driver
  under `rocprofv3 --kernel-trace`, rolls the trace up by family, and writes
  one combined artifact plus four per-run artifacts. Usage:
  `--gpu <index> --tag <name>`. Raw traces land in `/tmp` and are not
  committed. `--skip-topline` / `--skip-census` allow a partial refresh.
- Five artifacts: `-scoreboard-baseline.json` (combined), `-topline-{1024,
  4096}-baseline.json`, `-family-{1024,4096}-baseline.json`.
- `docs/campaigns/GEMMA4-26B-A4B-PUNCHLIST.md`: new `### Baseline at HEAD`
  section with the delta against the published table, a footnote on the decode
  table, an updated `### Basis` bullet, and `### How to regenerate` now naming
  the script (the manual recipe stays for the llama.cpp comparator, which the
  script does not run).

## Protocol

RX 7900 XTX, physical GPU 1, otherwise idle. hipEngine at `6d886f473` (8
commits after the table's `df867de1f`, **none of them touching `hipengine/`**).
Artifact `gemma-4-26B-A4B-it-UD-Q4_K_XL.gguf`, BF16 KV, default production
route, HIP 7.2.53211. Topline: `--prompt P --output 128 --samples 3 --warmup 1
--context 8192`, median of 3, fixed length (EOS ignored). Family: `rocprofv3
--kernel-trace` around `gemma4_family_census.py drive --prompt P --decode 64
--prefill-repeats 2`, rolled up with `--decode-steps 64`. Those are the
defaults the punchlist's recipe already specifies; the script passes them
explicitly so a default change cannot silently move the numbers.

## Finding: the published decode at 1024 is the one row that does not reproduce

Every prefill family reproduces within 0.4% and decode at 4096 within 1%.
Decode at 1024 does not: 19.47 ms of device busy against the table's 21.30.

The whole difference sits in `moe.gate_up` (4.79 against 5.42), `attn.sliding`
(3.65 against 4.28), `moe.down` (2.64 against 2.83) and `lm_head` (0.97
against 1.15). What makes this an error in the old trace rather than a
difference in work is the shape of the baseline itself:

| family | baseline @1024 | baseline @4096 | published @1024 | published @4096 |
| --- | ---: | ---: | ---: | ---: |
| moe.gate_up | 4.79 | 4.79 | 5.42 | 4.79 |
| attn.sliding | 3.65 | 3.64 | 4.28 | 3.64 |
| moe.down | 2.64 | 2.64 | 2.83 | 2.63 |
| lm_head | 0.97 | 0.96 | 1.15 | 0.97 |
| attn.global | 0.75 | 2.82 | 0.75 | 2.82 |

None of the first four reads the context, so they must be equal at both
lengths -- and in the baseline they are, to two decimals. In the published
table they differ, while the published 4096 column matches the baseline's 4096
column to 1%. Only `attn.global` moves between the lengths, in both, as it
must. Launch counts are identical (1146 per token), so what moved is time per
launch, not work. Read as clock or thermal state in the older 1024 trace.

## Decision: do not rewrite the paired table

The decode table is a *paired* head-to-head: its llama.cpp column was measured
in the same session as its hipEngine column. Replacing only the hipEngine
cells from a run that did not include llama.cpp would break the pairing the
comparison rests on, and the measurement contract asks for paired,
interleaved runs precisely to avoid this. So the table keeps its cells and
gains a footnote; the baseline section carries the discrepancy and states which
number is the reference for future work. Re-pairing that row needs a fresh
llama.cpp trace, which this baseline does not include.

Practical consequence for the punchlist: the decode gap arithmetic built on
21.30 ms is now 19.47 ms against llama.cpp's 9.65, so the gap is 9.82 ms rather
than 11.65. The *ranking* of decode candidates is unchanged -- `moe.gate_up`,
`attn.sliding`, `moe.down` and routing are still the four largest -- but their
estimated gains should be read against the smaller number.
