# INT8 automatic width bound follows the storage, not the singleton declaration

## Summary

Automatic MTP intent for INT8 KV was withheld at a realized due width above one
(`automatic_mtp_scope_not_promoted`), which is the open row in
`docs/reference/INT8-MTP-SERVER-READINESS.md`. The cause was that a request's
static width bound was read off the *narrowest covering* declaration for its own
realized width: a single-prompt INT8 request selected
`gguf_dense_int8_native_chain` (depth 7, one row) and carried
`max_realized_group_rows = 1`, so `partition_max_requests` resolved a due width-2
group to zero and the group fell to AR.

A static width bound is not a statement about the width this request realizes
alone. It is the widest due group the request may be a *member* of, and the
resident planner forms that group from concurrent requests. It now follows the
widest automatic-eligible declaration for the key's storage and backend
(`Qwen35GGUFModel._widest_automatic_group_rows`). Depth is deliberately **not**
widened: it stays with the declaration the realized width selects, which is what
keeps a wider cell the package does not list fail-closed at the resident owner
instead of admitted by the bound.

The change is confined to the implementation-declaration branch. A retained
evidence row still returns first and keeps its own measured width, so the
BF16 cells with evidence rows are unaffected.

## Changes

- `hipengine/models/qwen35.py`: added
  `Qwen35GGUFModel._widest_automatic_group_rows`, and
  `resolve_speculative_mtp_serving_plan` now widens
  `static_max_realized_group_rows` to it when the selected declaration is
  narrower.
- `tests/test_unit_int8_mtp_serving.py`: pinned the widened bound in
  `test_dense_int8_mtp_uses_implementation_admission` (which asserted the old
  `== 1`), and added
  `test_int8_automatic_width_bound_follows_the_storage_not_the_singleton_declaration`,
  which reads the gfx1151 production cell table through
  `backend_package_capability` and asserts both halves of the rule: the width-2
  cell a budget-2 request would now form is listed, and a depth the package does
  not list stays outside the policy at the widened bound.

## Validation

What was established by running, before the live sweep:

- `tests/test_unit_int8_mtp_serving.py` -- 36 passed (RED first: the widened
  assertion failed with `assert 1 == 4` against the old selection).
- `tests/test_unit_speculative_mtp_serving_capability.py`,
  `tests/test_unit_qwen35_gguf_mtp2_c1_physical.py`,
  `tests/test_unit_gguf_mtp_c1c8_server_bench.py` -- 10 passed. The capability
  suite exercises the evidence branch directly and is unchanged by this.
- `/tmp/probe_int8_auto_width.py` (scratch, not committed) resolved the plan for
  budgets 2, 3 and 7 and applied the resident owner's own cell computation
  (`min(adapter_budget, static_candidate_bound)` against the package table). At
  budget <= 3 every width 2..4 cell was listed and the *only* refusal was the
  static width bound; at budget 7 the cell is `(2,7)`, which the package does not
  list, so widening the bound alone cannot admit it. That is why the sweep below
  runs at its recorded `--candidate-budget 2`.

The named live verification is in flight and its result is not claimed here: the
readiness row's clearing route is
`scripts/gguf_mtp_c1c8_server_bench.py --mtp-request-mode automatic` with
`HIPENGINE_KV_STORAGE=int8_per_token_head`, and it must show `engaged_cells` and
`route_expectation_passed` at c1, c2 and c4. The prior automatic artifact
(`benchmarks/results/2026-09-23-gfx1151-qwen38-int8kv-mtp-vs-ar-c1c4.json`, commit
`8eaf06fc`, status failed) is the baseline this run is compared against: it
engaged 10/10 at c1 and c4 and 0/10 at c2, with
`failure_reasons: ["w2: route expectation engaged=0/10 mtp_expected=True"]`.
