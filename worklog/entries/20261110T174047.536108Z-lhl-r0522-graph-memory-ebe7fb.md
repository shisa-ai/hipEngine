# R0522 streaming-cohort graph-capture memory: bounded retention, not a leak

## Summary

Resolve R0522 (discovery entry
`20261108T194835.580722Z-lhl-gfx1100-physical-mtp-closures-f5c86c.md`):
attribute the cancellation-independent streaming-cohort memory growth on the
W7900 dense C8 path and decide leak vs bounded retention.

**Decision: bounded retention, not an unreleased-capture-buffer leak.** The
per-recapture packed decode-graph buffers are properly released on close. The
observed growth is per-session speculative-rollback GDN state buffers
(`ResidentStateStorage.linear_rows` and `.initial`) allocated once on each
session's first singleton native-B2 target capture and retained for reuse.
The bound is the resident session count; tracked memory plateaus across repeated
identical cohorts and teardown returns to zero. No production code change is
warranted: the retention is the intentional state-buffer-reuse trade-off that
avoids hot-path reallocation.

## Validation

All runs: W7900 GPU0 (gfx1100), hermetic TheRock env, model
`/models/gguf/Qwen3.8-27B-Q4_K_M.gguf`, real `create_app`/TestClient server,
opt-in explicit MTP (`speculative_candidate_budget=3`), C8 streaming cohorts
(8 requests x 64 tokens, temperature 0, max_context 1024).

Attribution:
- Model geometry (`scan_gguf`): 65 blocks (64 layers + NextN),
  `full_attention_interval=4` -> 48 GDN + 16 full layers; hidden=5120,
  ssm conv_kernel=4, state_size=128, time_step_rank=48, inner_size=6144.
- The four recurring growth sizes decode exactly as per-GDN-layer state rows:
  163840 = Conv x1 row (10240x4x4), 655360 = Conv x4 rows,
  3145728 = recurrent x1 row (48x128x128x4), 12582912 = recurrent x4 rows.
  48 of each = one per GDN layer.
- Central malloc/commit stack tracer (dump inside the live server context) names
  the owner: `state.linear_rows.ensure` and `state.initial.ensure` in
  `hipengine/runtime/qwen35_gguf_state.py` `LinearStateStorage.ensure`, reached
  from `capture_qwen35_gguf_native_b2_target_graph` via
  `_ensure_verify_linear_state_row_buffers` (rows=4) and
  `_ensure_verify_linear_initial_snapshot_buffers` (rows=1, exact). These are
  session state-storage, NOT graph-handle buffers.
- Ptr-ownership tracer: live leak buffers belong to a few slot-view storages
  (linear_rows rows=4 ~606 MiB each, initial rows=1 ~151.5 MiB each) plus the
  packed-owner linear_rows at the current max physical width (legitimate
  workspace). `LinearStateStorage.ensure` frees its own prior buffers on growth,
  so a single persistent storage does not accumulate.
- Creation tracer: `resident_slot_view` called exactly 14x (7 target slot views
  at load + 7 NextN slot views at first MTP cohort); `ResidentStateStorage`
  created once per session and reused, not per cohort.

Leak-vs-bounded decision (20-cohort controlled loop, `r0522_long.py`):
- Large-buffer growth steps at cohorts 1 (+154.6 MiB), 2 (+768.9 MiB),
  4 (+768.9 MiB) — three sessions' first singleton native-B2 capture — then
  PLATEAUS at 29.1689 GiB for cohorts 5-19 (15 consecutive flat cohorts).
- Plateau-cohort small allocations total ~193 KB over 15 cohorts (negligible).
- `AFTER_CLOSE current_allocated_bytes=0 active_allocations=0`: clean teardown.
- Graph-bucket entries return to zero; graph handle `close()` frees its
  active_mask/record/discard buffers plus submission/graph/stream. The
  "unreleased capture buffers" hypothesis is disproven.

## Next

- None required for R0522. Optional product trade-off (not a defect): the idle
