# Correction: the C1 decode-graph floor is 24 on gfx1100, not a scalar-vs-packed inconsistency

## Summary

The entry `20260911T233045.766311Z-lhl-ikv-c2-c1-decode-graph-6dce6a.md`
(committed in `f65d16ba8`), its `docs/REFACTOR.md` removal condition, its
`benchmarks/CHANGELOG.md` line, and task `#28`'s description all state that the
scalar C1 decode-graph eligibility floor is the backend default 24 while
`packed_decode_graph_min_replay_steps` applies a model/width policy floor of 128
for dense H5120 `Q4_K_M` at one row. **That claim is wrong.**

Verified directly against the backend packages:

| Value | gfx1100 | gfx1151 |
| --- | --- | --- |
| `GGUF_DECODE_GRAPH_MIN_REPLAY_STEPS` | 24 | 128 |
| `GGUF_PACKED_DECODE_GRAPH_MIN_REPLAY_STEPS_BY_POLICY` | `{}` (undefined) | `{(dense H5120, MOSTLY_Q4_K_M): {2: 23}}` |

`_resolve_gguf_packed_decode_graph_min_replay_steps` returns
`max(1, ceil(default_minimum / physical_rows))` when the policy mapping has no
entry for the geometry. gfx1100 defines no such entry, so at one row it returns
`ceil(24 / 1)` = **24** — the same value `decode_graph_min_replay_steps()`
returns. There is no inconsistency between the scalar and packed floors on this
device.

The 128 comes from a *different* capability,
`GGUF_DECODE_GRAPH_SUBMISSION_POLICIES`, whose
`min_replay_steps_by_physical_rows` field is consumed by
`_resolve_gguf_decode_graph_submission_transport`. That function uses it to
choose the submission **transport**: at `steps_per_replay == 1` and
`replay_steps >= 128` it keeps the package default `pm4`, and below that it
falls back to `hipgraph`. It does not gate eligibility at all.

## Consequences

1. **Task `#28`'s stated work item does not exist.** There is no scalar floor to
   correct, so the first and second steps of that task are void. The task is
   re-scoped to the remaining real question: whether the INT8 graph admission is
   a repeatable win at the existing floor.
2. **The INT8 flag's blocker is restated honestly.** It is not a floor
   inconsistency. It is that the measured delta (-0.53% with capture included,
   -2.48% replay-only, from one pair) is not separated from run-to-run noise, so
   promotion is not yet justified. Repeats are the evidence that would settle it.
3. **The measured INT8 run used the `pm4` transport**, because 128 decode tokens
   is exactly the transport threshold for this geometry at one row. A horizon
   between 24 and 127 steps would submit through `hipgraph` instead, which was
   never measured. That is a real open question and is now stated as such.
4. The claim never affected a promoted default: `HIPENGINE_GGUF_INT8_KV_DECODE_GRAPH`
   stayed default-off throughout, and the layer-outer promotion in `7444dd705`
   is unrelated to the decode graph.
