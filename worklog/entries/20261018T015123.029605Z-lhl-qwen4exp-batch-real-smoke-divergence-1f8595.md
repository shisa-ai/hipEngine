# Batch decode step does not reproduce c1 at production geometry

## Summary

The first real-checkpoint run of `scripts/qwen4exp_batch_runner_real_smoke.py`
found that the N-row batch decode step does **not** reproduce the c1 decode step
on the production artifact, while `import_prefilled` is bit-exact. The synthetic
GPU suite cannot see this: at hidden 256 with four layers the batch and c1 agree
bit for bit, and they still do after the per-layer KV repair in `655dc7b46`.

Measured on this host (AMD Ryzen AI MAX+ PRO 395, gfx1151, ROCm alive), model
`/models/gguf/unsloth-Qwen3.8-Flash-Next-UD-Q4_K_XL/UD-Q4_K_XL` (UD-Q4_K_XL,
76.86 GiB device-resident, 12 QSA of 48 layers, per-slot state 174.1 MiB at
context 2048):

```
uv run python3 scripts/qwen4exp_batch_runner_real_smoke.py \
    /models/gguf/unsloth-Qwen3.8-Flash-Next-UD-Q4_K_XL/UD-Q4_K_XL \
    --context 2048 --steps 5 --rows 4 --json-out /tmp/qwen4exp-batch-real-smoke.json
-> kl_c1_to_batch max 2.572e-02 (mean 6.44e-03, p95 2.372e-02),
   kl_batch_to_c1 max 2.808e-02, top-1 agreement 1.000,
   max|dlogit| 2.158 (mean 1.242), mean|dlogit| 0.394,
   smoke floor kl_pass=True top1_pass=True
```

The gap is deterministic and reproduces to the digit at every row count:
`--rows 1` gives the same `kl_c1_to_batch max 2.572e-02` with `max|dlogit| 1.099`,
so it is not cross-row contamination. A dedicated one-token probe (a c1 prefill
of one token, then one teacher-forced step through both paths) still shows
`max|dlogit| 3.84e-01` (mean 5.90e-02) at position 1, `1.20e-01` at position 3,
`9.01e-02` at position 5, so it is the decode step's own arithmetic, not history
or state.

## Excluded causes

- **State import is bit-exact.** After `import_prefilled`, all 12 QSA K/V caches,
  all 36 GDN conv and recurrent layers, the PLE conv history, and all 12 index
  raw-key slabs hash-match the c1 source (`MISMATCHES: none`, per-layer SHA-256
  over the valid prefix). Batch cursor 11 = c1 prefill position 11.
- **Not the per-layer KV cache defect** fixed in `655dc7b46`; the probe above
  runs with that fix in place.
- **Not row composition.** Deterministic and row-count independent; the
  composition-order control (see below) is byte-identical.
- **Not execution-profile kernel selection.** No `HIPENGINE_QWEN4_EXP_*` variable
  exists in the process after `Qwen4ExpGGUFTextGenerator` construction (count 0),
  so neither path had a production profile bound: both ran the default selection.
- **Not c1 graph capture.** Identical numbers with
  `HIPENGINE_QWEN4_EXP_MOE_GRAPH=0 HIPENGINE_QWEN4_EXP_LAYER_GRAPHS=0`.
- **Not c1's `reset()`.** `reset()` plus a fresh `prefill_serial` reproduces the
  c1 prefill and step logits bit-identically.

## Changes

`scripts/qwen4exp_batch_runner_real_smoke.py`:

- Disables `HIPENGINE_QWEN4_EXP_MOE_GRAPH` and `HIPENGINE_QWEN4_EXP_LAYER_GRAPHS`
  before constructing the generator, matching the synthetic GPU batch tests. c1's
  single-request graph capture is a different execution profile from the eager
  batch path.
- Records the `HIPENGINE_QWEN4_EXP_*` / `HIPENGINE_EXECUTION_PROFILE*` environment
  in the report, so a run states which kernel selection it actually used.
- **Fixes an invalid control pass.** It previously compared the ladder schedule of
  pass A against a *reversed* ladder, so each slot advanced a different number of
  times in the two passes and unrelated states were compared; it reported
  divergence on all four slots for that reason alone. It now runs two uniform
  passes (every row every step) from a fresh import, ascending versus reversed row
  order inside each step, so each slot has an identical history. With the fix the
  control pass is **byte-identical on every slot** — the batch path is
  order-invariant at production geometry.

## Validation

```
uv run python3 scripts/qwen4exp_batch_runner_real_smoke.py ... --context 2048 \
    --steps 5 --rows 4
-> control pass B: every slot's state and logits are byte-identical to the

uv run python3 scripts/qwen4exp_batch_runner_real_smoke.py ... --plan-only
-> plan: device weights 76.86 GiB, PLE mmap 26.82 GiB, free 121.60 GiB, fits=True
```

Batch-family regression suite from `655dc7b46` still applies (143 passed).

## Next

Localize the divergence per stage, not per model: run one row through c1 and the
batch runner and compare the residual after every layer (GDN layers 0-35, QSA
layers at their indices, the PLE stage at layer 1, the head). The batch bodies
call their own kernels (`run_qwen4_exp_batch_gdn_layer`,
`run_qwen4_exp_batch_qsa_layer` via the mixed mixer, `run_qwen4_exp_moe`) rather
than c1's per-layer decode bodies, so the suspect list is a shape-dependent
kernel or argument difference inside those three families at production
geometry — `head_dim` 256 with 24 query and 4 KV heads, 512 experts top-10,
residual 10240.

Once the stage is known, the fix belongs in the batch layer body with a RED test
built from the production geometry (not the synthetic 4-layer fixture, which is
too small to reproduce any of this).

The top-1 agreement of 1.000 and the passing smoke floor mean this is not a
serving-blocking quality failure yet, but a batch path that differs from c1 by
2.6e-2 KL max before any profile difference cannot be certified against the
production gate in `docs/EXECUTION-PROFILES.md`, which is stated relative to the
strict teacher.
