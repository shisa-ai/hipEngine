# P6/D9 census: measure the q/k/v fusion launch chain and validate the user surface

## Summary

P6's fusion landed in `17f745d6c` but the row still carried two explicitly
outstanding items -- the family-census launch re-count had not been re-run, so
its net -25 was arithmetic, and the figure still turned on how many gemma4-26b
layers are `k_eq_v`. D9 additionally still read `open` although its fusion

## Validation

- **Launch chain (three comparable census runs).** Decode `dense.q8_0`
  **206 -> 176 -> 126 launches/token** (`2026-09-29-gemma4-family-{1024,4096}-p2`
  -> `2026-09-30-gemma4-family-4096-blockfit` -> this run) with decode dense
  busy **2.9385 -> 2.8039 -> 2.690 ms**; prefill dense at 1024
  **412 -> 350 -> 252**. 206->176 is exactly -30 (gate/up, 30 layers) and
  176->126 exactly -50 (25 sliding layers x 2).
- **Route (b) confirmed, not assumed.** `gemma4_qkv_split_bf16_kernel` appears
  as exactly **25 launches in `other`** (0.055 ms decode; 1.674 ms over 50
  prefill launches), so -50 dense + 25 split = **net -25**, the figure the row
  predicted. It stays in `other` with `other_top` naming it -- honest and
  comparable, rather than bending a family rule for a new kernel.
- **`k_eq_v` settled from the artifact, not prose:** 5 of 30 layers carry no
  `attn_v` (indices 5, 11, 17, 23, 29), so **25 layers fuse**, exactly matching
  the split's 25 launches.
- **User surface (`hipengine.LLM.generate()`).** A spy on the split recorded
  **200 calls = 25 layers x 8 forwards** (1 prefill + 7 decode), all
  `parts={3}` and `rows` in {1, 5}: the fused route runs on every forward
  through the public API.
- **Transparency proof.** The same prompt through the same API with fusion
  disabled at the loader (`can_fuse_gguf_device_weights -> False`) yields
  **byte-identical output** to the fused arm (split calls 0 vs 200), so the
  change cannot have altered results.
- **Output shape explained, not hand-waved.** Raw prompts through
  `LLM.generate()` repeat degenerately (`' it it it ...'`) on both arms. The
  cause is the API, not the engine: `LLM.generate(str)` tokenizes raw text, while
  the chat template is applied only on the server path
  (`hipengine/server/api.py:1142` -> `render_gemma4_chat`). Rendering through
  `llm._get_text_generator().tokenizer.chat_template` + `render_gemma4_chat`
  answers `4` and `Paris` correctly. Pre-existing behaviour of this surface,
  unchanged by P6.
- Docs gates: `python3 scripts/docs/check_all.py` -- 1 failure, the pre-existing
  `published command drift` from the 2026-09-21 zbook artifact citing a script
  in `hipEngine-main`; the new artifact's own command resolves.
