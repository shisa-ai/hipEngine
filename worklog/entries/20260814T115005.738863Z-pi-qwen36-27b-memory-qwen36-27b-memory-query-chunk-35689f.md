# Reject dense 27B prefill query chunking for memory

## Summary

Rejected 1024- and 2048-row full-attention query chunk caps for the dense Qwen3.6-27B XTX default. Both recover real 4K/128 memory, but lose 17.30% and 15.76% prefill respectively and still miss the lower Vulkan peak. This is not an acceptable memory-for-speed trade.

## Changes

- No runtime or default changed.
- Added `benchmarks/results/2026-08-14-qwen36-27b-prefill-query-chunk-memory-rejected.json` with raw benchmark/VRAM hashes and the two candidate comparisons.
- Stopped the first diagnostic before measurement after noticing that one explicit chunk field disables auto-population of the other fields; both recorded runs explicitly hold linear/MoE/post/RoPE at the package-default 1024 rows and change only full-attention query rows.

## Validation

- Current 4096-row control: 988.405 prefill tok/s, 31.401 decode tok/s, 16.263-GiB tracked, 17.022-GiB whole-device peak.
- 1024-row candidate: 817.405 / 31.505 tok/s, 15.860-GiB tracked, 16.459-GiB whole-device peak. It saves 412.426 MiB tracked / 576.160 MiB whole-device and beats llama.cpp HIP memory by 0.103 GiB, but loses 17.30% prefill and remains 0.547 GiB above Vulkan.
- 2048-row candidate: 832.673 / 31.449 tok/s, 15.985-GiB tracked, 16.741-GiB whole-device peak. It saves 284.367 MiB tracked / 287.656 MiB whole-device, loses 15.76% prefill, and remains 0.829 GiB above Vulkan.
- Both candidates produced finite logits and exact `[9707, 9707, 9707]` final IDs in all measured resets, reused the decode graph after capture, and returned tracked ownership to zero after close.

## Next

The liveness audit proves the 488-MiB arena is at its current weighted-clique lower bound, so the next lane must shorten/alias real simultaneous lifetimes rather than reorder allocations. Separately screen AOTriton runtime/workspace ownership because 184-195 MiB remains after session close and whole-device peak exceeds tracked ownership by 0.5-0.8 GiB.
