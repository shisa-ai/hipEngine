# Sampled MTP on INT8 is refused by route scope, not by a capability miss

## Answer to the task's acceptance question

**Not a real capability miss, and not an INT8 declaration omission either.** The
sampled accept path is storage-agnostic — verified by construction, not inferred
— and the device-side accept that the declaration named as the second
precondition has already landed. What remains is the route's own open finish-rule
gap, which is contained per request rather than fixed. That gap belongs to the
route (task 6), not to INT8.

Three findings, in the order they close off the alternatives:

### 1. The accept is storage-agnostic — so INT8 KV is not the blocker

`sampled_accept_summary` (`hipengine/generation/mtp_sampled_accept.py:96`) takes the
verify batch, the verifier's **row-major logits matrix**, the request's sampler
state, its params, and its draw stream. It forwards to
`sampled_accept_from_distributions` (`hipengine/speculative/sampling.py:202`),
which takes `TargetVerifyBatch` plus two `SparseDistribution` sequences per row.
Neither module reads KV storage, a storage dtype, or a device buffer.

The logits the accept needs are already requested on INT8. The sampled route sets
`return_logits=True` whenever it is not on a device accept plan
(`Qwen35GGUFMTP2Adapter.execute_target_frontier`), and the non-native verifier
branch fills `prepared.target_logits` from
`self.target.step(..., return_logits=True)`. Storage does not enter that path.

### 2. The device-side accept landed, so that precondition is discharged

`Qwen35GGUFMTP2Adapter._device_sampled_accept_plan` returns a plan for
native-sampler rows using the sorted algorithm with no processors, `top_k == 0`,
no tool-call or JSON constraint, no forced tokens, and `temperature > 0`; every
other shape declines to the eager host path. So the eager host-logit restriction
is lifted for the shapes the route covers. The declaration comment still names it
as a precondition, which is now conservative rather than accurate.

### 3. The remaining gap is the finish rule, and it is not INT8-specific

`docs/REFACTOR.md` "Sampled-route finish-rule blockers (open)": the cycle commit
ends a row only when its last visible token is the row's EOS, and a stochastic
accept has no `greedy_chain_eos_limit` bound, so a stop token or EOS can land
mid-cycle. The request-level blocker set (`min_tokens`, `eos_token_id`,
`stop_token_ids`, `stop_token_sequences`) keeps those shapes off the route, which
is containment. That is task 6.

This is why the scope is conservative **for every storage**: all seven
declarations in the plugin are `("greedy_fast",)`, BF16 and INT8 alike, and
gfx1151 BF16 is served only through its four evidence rows
(`automatic_native_sampled_c1_c4`). INT8 is refused for exactly the reason every
BF16 declaration is refused.

The sampling law reaches the sampled route with no unservable blocker; the
finish-rule and metadata fields do not reach it at all and are refused on **both**
storages. That is task 6's territory.

### Not run: the live INT8 server trace

The task asked for a `temperature > 0` MTP request against an INT8 KV server.
That host is this machine and it cannot start a second hipEngine server: another
session's server holds 96.3 GiB of GTT, leaving less than the engine's own 3 GiB
reserve after the model loads. Its startup ladder halved the context
23552 -> 11776 -> 5888 -> 2816 and failed at every step, so no context or
active-request setting fits. The refusal was traced through the real plugin's
`resolve_speculative_mtp_serving_plan` — the same function the server calls —
which is a stronger basis here, because the refusal is deterministic admission
logic that fires before any GPU work and a server log line would only restate it.
