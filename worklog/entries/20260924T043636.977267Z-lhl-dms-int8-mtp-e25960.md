# DMS MTP takes the eager row path, and the decline that gates it

## Summary

Task 9 item 2, and a re-scoping finding that changes how the rest of the DMS MTP
work should be read.

**The staged INT8 verify chain is not the path a DMS MTP row takes today.** The
chain that carries the paged ``verify_chain_spans`` leaf, and the compact leaf
added in ``aa64fce25``, is entered only when ``decode_row_scratches`` is present,
and those rows are built only under ``bulk_attention_mode == "native"``
(``gguf_native_spec_cycle.py``, the ``_dynamic_native_decode_row_scratches``
call). The native target graph refuses a session with a ``_dms_backend`` outright
(``gguf_native_spec_cycle.py``, the four-way conjunct that ends the graph path),
and the eager callers pass ``bulk_attention_mode="bulk"``. A DMS row therefore
verifies through the scalar per-row full-attention path, which attends through
the compact store's existing single-row route. That route already reads
per-head extents and their scale planes, which is why the compact leaf is
reachable only once a DMS row is admitted at all.

**The decline is not stale.** ``compact_dms_mtp_transaction_not_implemented`` was
checked against the verifier rather than assumed. ``Qwen35GGUFTransactionalVerifier``
publishes an accepted prefix by resetting resident span position and context
metadata, and rolls back by restoring the pre-verify metadata. A compact-DMS row
has no resident span metadata to reset: its writes land in per-head extents with
per-slot payload and scale planes. A journaled commit would therefore publish a
prefix the store never wrote. The route that lifts the decline already exists on
the store side and is simply not driven by the verifier yet:
``DMSCompactBackend.begin_transaction``/``commit``/``rollback`` snapshot per-head
live counts, token positions and eviction, the host payload and scale planes, and
the device store.

So the work that unblocks DMS MTP is the journal, which is tasks 10 and 11, not
the staged verify chain. Task 10's ``blocked by 9`` dependency was wrong for the
same reason and has been cleared.

## Changes

- ``hipengine/generation/qwen35_gguf_mtp2.py``: the ``_dms_backend`` decline now
  carries the concrete cause and the clearing route, naming the store transaction
  the verifier has to drive, instead of only a reason code. No behavior change.

## Validation

- ``pytest tests/ -k "mtp2 or dms" --suite unit``: 307 passed, exit 0. The change
  is a comment on a refusal, so the narrowest gate is that the refusal's own
  tests still pass and nothing else moved.
- The re-scoping claim is read from code, not inferred: the ``decode_row_scratches``
  ternary, the DMS refusal in the graph builder, the eager callers' mode, and
  ``staged_dense_full``'s requirement that the rows be present.

## Findings

- The compact verify-chain leaf added in ``aa64fce25`` has no caller today. That is
  a consequence of the re-scoping above rather than an oversight: the leaf is the
  right shape for the DMS verify path, and the path is gated by the journal. It is
  recorded as a requirement of task 10 so it cannot be lost, because a leaf that
  nothing reaches is not a shipped capability.
- Task 9's acceptance (an INT8 verify-chain parity run over a DMS-shaped span set
  against the AR route for the same retention policy) is met by the two GPU gates
  in ``tests/test_gpu_dms_int8_device_payloads.py``, and its binding deliverable is
  met by the store and leaf work in ``bf16ec05a`` and ``aa64fce25``.
