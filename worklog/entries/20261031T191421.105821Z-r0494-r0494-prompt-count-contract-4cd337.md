# R0494 prompt-count contract: one owner, explicit zero, legacy fallback

## Summary

`usage.prompt_tokens` now has exactly one authoritative producer,
`GenerationOutput.prompt_tokens`. `None` means the generator cannot state the length, and only then
does the serving front end count the prepared prompt itself. A stated `0` is an empty prompt and is
reported as `0`. The two diagnostic mirrors, `DecodeState.prompt_tokens` (defaults to zero) and
`telemetry.usage["prompt_tokens"]` (optional), no longer authorize a usage number, because neither
can tell "empty" from "unknown". The compatibility fallback for legacy plugins that return no count
is unchanged, and it is now the only second path.

Before this unit the multimodal chat route chose between three sources per request (output field,
then telemetry usage, then a text tokenizer count) while `_usage` counted prompts with the tokenizer
only, so a text request to a generator that knew its exact length reported a different number than
the same request through the multimodal route.

## Changes

- `hipengine/server/api.py`
  - `_reported_prompt_token_count(detail)` is the single precedence rule: output field only, `None`
    when unstated, `max(0, int(value))` otherwise.
  - `_prompt_token_total(engine, prompts, *, details)` sums per-row counts, keeps the
    prepared-prompt count for rows that report nothing, and falls back for every row when the
    detail rows do not align with the prompts (so an `n>1` batch cannot double-count a prompt).
  - `_usage` calls `_prompt_token_total` instead of summing the tokenizer count.
  - The multimodal chat branch calls the same helpers and counts a token-id prompt by length
    through `_prompt_token_count` rather than assuming `engine.count_tokens` accepts one.
  - `_coerce_generation_output` preserves `prompt_tokens`, so a duck-typed plugin output keeps its
    exact count instead of being handed to the text fallback.
- `hipengine/generation/registry.py`: `GenerationOutput.prompt_tokens` documents the ownership
  contract, the `None`-means-unknown rule, the explicit-zero rule, and why the mirrors are
  diagnostic only.
- `hipengine/generation/qwen4_exp_gguf.py`: the multimodal generator sets the output field
  alongside its telemetry mirror. It was the only producer publishing `usage["prompt_tokens"]`
  without the output field, so no producer lost its count. Gemma 4 (`gemma4_gguf`, `gemma4_mtp`) and
  Surya already set the field.
- Tests: new `tests/test_unit_server_prompt_token_contract.py` (12 cases: precedence, explicit zero,
  legacy fallback, mixed batch, non-aligned rows, telemetry/decode-state mirrors ignored, speculative
  accounting, token-id prompt, coercion both ways) and new
  `tests/test_integration_server_prompt_token_contract.py` (3 cases over `create_app` + `TestClient`
  for a plugin with only `generate()`). `tests/test_integration_qwen4_exp_server_multimodal.py`
  asserts the contract instead of the old three-way precedence, and
  `tests/test_unit_generation_qwen4_exp_gguf.py` asserts the producer field.
