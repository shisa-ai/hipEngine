# CFG negative-branch share was over-measured

## Summary

A previous iteration reported that the CFG negative LM branch is 49.8% of single-row
LM forward time and that batching the branches would roughly halve LM weight
traffic. **That measurement is retracted.** The negative branch is bounded by
`stages.lm_total_seconds` (1.563 s of 4.230 s warm synthesis, shared with the
positive branch) — roughly ~18% rather than ~40% — and cross-branch batching needs a
per-row cache-pointer kernel ABI plus speculation and KV rollback.

## Changes

No code change. One immutable worklog entry.

Supersedes `20260915T194956.602768Z-lhl-vibevoice-tts-cfg-branch-traffic-3bfd87`,
which reported the ~47% traffic share from the same flawed per-call-sync
instrumentation. That entry's *structural* observation stands (the negative branch
re-runs the positive branch's feedback rows through its own KV cache); only the
magnitude was wrong.

### Why the original measurement was wrong

The instrumentation wrapped `VibevoiceQwen2Runtime.forward_layers` and called
`runtime.device_synchronize()` after *every* call. A full device sync waits for all
previously enqueued work, so each measured interval absorbed outstanding kernels
from other stages (diffusion, decoder, semantic frontend). The per-call sums
therefore overlapped the other stage timers and exceeded what the whole session can
contain:

```
sum of wrapper intervals : 1729.8 + 1712.7 = 3442.5 ms
other stage timers       : prompt 0.180 + diffusion 1.373 + decode 0.319 + semantic 0.794 = 2.666 s
wrapper sum + other      : 6.11 s   >   warm_synthesis_seconds = 4.23 s
```

A component cannot be measured by serializing the pipeline it runs inside.

### Corrected bound

`scripts/vibevoice_tts_session_bench.py` derives `stages.lm_total_seconds` as
`elapsed - prompt - diffusion - decode - semantic`, i.e. it is the LM catch-all and
**already contains the negative branch**. Host `zbook` (AMD RYZEN AI MAX+ PRO 395 w/
Radeon 8060S, gfx1151), frozen fixture request:

```
warm_synthesis_seconds 4.230   pooled_rtf 1.269
lm_total  1.563  (37%)
diffusion 1.373  (32%)
semantic  0.794  (19%)
decode    0.319  ( 8%)
prompt    0.180  ( 4%)
```

So the negative branch is bounded by 1.563 s shared with the positive branch, not an
additive 1.71 s on top. The plausible share is roughly half of `lm_total`
(~0.7-0.8 s, ~18% of warm synthesis). Any future claim about this branch must use a
single sync around the whole loop, or `rocprofv3`.

### Why cross-branch batching is not a small refactor

The dependency chain inside one generation step is strictly sequential:

```
pos_forward(k-1) -> next_token -> neg_forward(k) -> diffusion(k) -> pos_forward(k)
```

`neg_forward(k)` cannot be hoisted: whether iteration `k` diffuses is decided by the
logits that `pos_forward(k-1)` produces. Note `neg_forward(k)` consumes
`_prev_feedback` = `feedback(k-1)`, which is the *same input row* `pos_forward(k-1)`
consumed, so a speculative batch is semantically sound — but it needs a rollback of
the negative KV position when the speculation misses.

The existing multi-row machinery does not reach across runtimes.
`_prefill_batched(hidden_rows, rows, start_pos)` already does batched causal prefill
with per-row positions and spans, but:

- each `VibevoiceQwen2Runtime` owns its own `self.layers` weight buffers, so a single
  GEMV cannot read both branches' weights from one pointer;
- `vv_kv_write_spans(...)` and `vv_attention_spans(...)` take a **single**
  `k_cache` / `v_cache` pointer, and the two branches hold different KV caches.

A true cross-branch batch therefore requires new kernel variants taking per-row cache
pointers, plus speculative execution and KV rollback in the session loop. That is a
kernel-ABI change, not a tuning change, and it would reassociate arithmetic (so it
would need the production-profile numerical gate rather than the bit-exact
parent-parity gate).
