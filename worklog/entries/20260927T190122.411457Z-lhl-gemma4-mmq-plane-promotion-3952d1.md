# Hold the MMQ plane count at 1 and promote 3 through the gate

## Summary

Supersedes the `_MMQ_ACTIVATION_PASSES` decision in
[`20260927T185444.658791Z-lhl-gemma4-mmq-activation-planes-a58366.md`](20260927T185444.658791Z-lhl-gemma4-mmq-activation-planes-a58366.md),
which recorded the constant being raised to 3 in the same commit as the leaf's
min-correction fix. The fix landed; the constant does not.

`AGENTS.md` puts arithmetic promotion under evidence: "Making a changed-arithmetic
kernel path the default requires its execution-profile gate." The three-plane
route qualifies as that - `git log -L` shows the constant was introduced at
`37ce89541` already at 1, so this route has only ever shipped one plane and three
is a new default arithmetic, not a restoration.

There is no gate to clear it today. The one that exists,
`scripts/execution_profile_q8_mmq_plane_gate.py`, drives Qwen4Exp's
`Q8MMQPrefillPolicy.planes`; Gemma 4's MMQ gate/up route reads a module constant,
so the gate has nothing to flip. Raising the constant would be asserting an
envelope that nothing measured.

The fix is unaffected by this. With `ACTIVATION_PASSES == 1` the pass loop runs
once with `activation_pass == 0`, so the guard emits the same two operations in
the same order as the original single expression: a fixed one-plane forward
hashes identically against the pre-fix and post-fix kernels
(`6a3f884259148eb8e131a7652a2eacc75e0719af0b0e8e2e89c040b537f3dac4`). The
defect is removed from the three-plane path without moving the one-plane path
that production runs.

## Changes

- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_experts.py`: `_MMQ_ACTIVATION_PASSES`
  back to 1, and the imports back to the one-plane pack and leaf. The note on the
  constant now records both defects, the three-plane candidate's accuracy and
  cost, and the three-step route that would lift it.
- No kernel change: the leaf guard from
  [`20260927T185444.658791Z`](20260927T185444.658791Z-lhl-gemma4-mmq-activation-planes-a58366.md)
  stands as committed.
- The RED test added by that entry is unchanged and still guards the three-plane
  path, because it drives the plane count and the pack/leaf symbols itself rather
  than reading the production constant. Re-checked against the pre-fix kernel: 58
  of 1280 output elements change when the later planes' stored sums are blanked.

## Validation

`tests/test_unit_gemma4_expert_route.py` passes in full (49 tests) with the
constant at 1.

The production path is bit-identical to the pre-fix kernel by the digest above,
which is the strongest available statement that this commit does not move the
arithmetic production runs.

## Next

Three steps to promote three planes, in order:

1. Route the plane count through the variant policy so a gate can resolve it, the
   way Qwen4Exp's `Q8MMQPrefillPolicy.planes` already is.
2. Run `scripts/execution_profile_q8_mmq_plane_gate.py` for the candidate against
   the strict teacher.
3. Raise the constant.

Before step 2 it is worth pricing a two-plane point instead. The f32 pack exposes
`d4`, `d4x2` and `d4x3`, but the bf16 pack only exposes `d4` and `d4x3`, so a
two-plane route needs one more C++ instantiation and export. If the prefill
penalty is linear in the plane count - 10.0 percent at 512 prompt tokens, 11.2
percent at 1024 - two planes buy roughly 256x over one for about half the cost,
which may be the better thing to put through the gate.
