# MTP plateau quantified: cycle cost scales w^0.76 where AR scales w^0.36

## Summary

No new GPU run - the model volume is still missing (20260830T143438…). The C5-C8 MTP plateau from
20260830T142952… is now quantified from the same packet, and it is a **scaling-exponent**
problem, not
an acceptance or base-cost problem: one MTP cycle's wall grows as **w^0.76** across
concurrency, while
one AR decode step's wall grows as **w^0.36**, with accepted tokens per cycle fixed at 3.38.

Source: `/tmp/he-parity/he-d24.json` (`Qwen3.8-27B-Q4_K_M.gguf`, explicit MTP, 10 prompts/width,
exactness 10/10/10 at all widths). Batch-cycle ms = `mtp.wall_seconds / (cycles / width)`;
batch-step ms = `ar.wall_seconds / (generated_tokens / width)`.

- No code change, and deliberately no `benchmarks/` rollup update: nothing was optimized and no

## Finding

- The per-lane view hides the defect. Dividing by `cycles` (which is per-lane aggregate, exactly
  71 x width) gives a flat ~62 ms per lane-cycle from C3 to C8, which reads as "no growth with
  lanes". The batch view is the one that matters, because a cycle serves all resident lanes at once:
  106.2 ms at C1 to 492.9 ms at C8, a **4.64x** growth for 8 lanes, against AR's **2.27x** for the
  same 8 lanes.
- Log-log fits: MTP cycle exponent 0.76, AR step exponent 0.36. Near-linear for the speculative
  route, properly sublinear for the batched route.
- The model is not hand-waved: it reproduces the measured headline. At C8, lanes x tokens-
  per-cycle /
  batch-cycle wall = 8 x 3.38 / 0.4929 s = **54.9 tok/s**, which is exactly the measured 54.86.
- Counterfactuals from the same relation, holding acceptance and base cost fixed: if the
  cycle scaled
  with our own AR exponent (0.36) the C8 rate would be about **120 tok/s**, ahead of both
  peers; if it
  scaled with the measured llama.cpp-current K3 exponent (32.55 -> 94.74 over 8 lanes = w^0.51) it
  would be about **88 tok/s**, which is effectively the peer number. Actual: 54.9. So the
  whole C5-C8
  deficit lives in the exponent, not in acceptance (width-invariant) and not in single-lane cost
  (106.2 ms is competitive at C1, where MTP is 1.43x AR).
- What this does **not** settle is the mechanism, and it must not be reported as settled. Two
  candidate causes produce the same near-linear batch cycle: a verifier block whose rows
  cost linearly
  (rows = lanes x (K+1) = 32 at C8), and draft/verify work that is serialized per lane. Flat
  per-lane
  cost is consistent with both. The discriminator is the blocked experiment: sweep `--block-rows` at
  fixed width. If cycle cost is linear in rows even at fixed width, the rows themselves are the cost
  and the fix is to fold lanes into one verify block; if cost jumps only when lanes are added, the
  route is serialized per lane.
