# the prefill attention kernel is scalar-issue-bound: the scalar stream is 62 to 95 percent of its runtime

## Summary

Five explanations for the attention kernel's cost had been closed by measurement --
traffic, the masked-column walk, pass-1 ILP, the K/V loads, and occupancy -- and
none of them reached it. Counting instructions rather than ablating loops reached
it on the first try.

`rocprofv3` reports both instruction streams. The scalar one is not a rounding
error next to the vector one:

| launch, 2048 tokens | `SQ_INSTS_SALU` | `SQ_INSTS_VALU` | SALU/VALU |
| --- | ---: | ---: | ---: |
| swa 256d window=1024 | 1,939,590,784 | 2,631,778,080 | 0.74 |
| swa 256d window=0 (probe) | 4,708,794,368 | 5,284,693,552 | 0.89 |
| full 512d window=0 | 6,891,159,552 | 8,924,946,272 | 0.77 |

The scalar unit on this part issues one instruction per cycle per CU, against four
VALU pipes. On 32 CUs at 2 GHz that is 64e9 scalar instructions per second, so the
scalar stream alone accounts for

| launch | SALU time at 1/cyc/CU | measured | share |
| --- | ---: | ---: | ---: |
| swa 256d window=1024 | 30.3 ms | 48.56 ms | 62% |
| swa 256d window=0 | 73.6 ms | 77.71 ms | **95%** |
| full 512d window=0 | 107.7 ms | 130.76 ms | **82%** |

**The kernel spends most of its time issuing scalar instructions.** It was never
FMA-bound, which is why "2 percent of fp32 FMA peak" was the wrong frame for it --
the FMA work is a minority of what it issues.

### Where the scalar instructions come from

The SASS says it directly. The strict prefill kernel's body is 32,630
instructions, of which only 6,811 are `v_*`:

```
s_delay_alu   2735      s_mul_i32     2021      s_addc_u32  1590
s_mul_hi_u32  1387      s_add_u32     1384      movq        1375
s_waitcnt     1178      s_add_i32     1078      s_cselect_b32 1065
s_mov_b32      907      leaq           875
```

Roughly 9,700 of them are 64-bit address and index arithmetic -- `s_mul_i32` paired
with `s_mul_hi_u32` and `s_addc_u32` is the 64-bit multiply, and `movq`/`leaq`/
`s_add_u32` are the 64-bit adds that carry it -- and another ~1,640 are
`s_cselect_b32` and `s_or_b32`, which is what a 64-bit loop induction variable with
overflow checking lowers to. `s_delay_alu` at 2,735 is the scheduler padding
dependent scalar chains, which is the symptom rather than a cost of its own.

The source is doing that arithmetic per key and per dim:

```cpp
const scalar_t* k_row = key + (j * num_kv_heads + kv_head) * head_dim;   // 64-bit mul
for (int64_t d = threadIdx.x; d < head_dim; d += blockDim.x)             // 64-bit induction
  for (int64_t j = first_kept; j < walk_end; ++j)                        // 64-bit induction
```

Every one of `j`, `d`, `num_kv_heads`, `kv_head`, `head_dim` and the pointers is
`int64_t`, so each loop iteration re-derives a 64-bit address from scratch and each
loop bound check is an overflow-checked 64-bit compare.

### Why this explains every earlier negative

The five closed probes were all measuring the right kernel and the wrong thing, and
the scalar diagnosis predicts each result:

| probe | result | why, given a scalar-bound kernel |
| --- | --- | --- |
| `--dtype f32` | 1.08-1.14 | address arithmetic is unchanged by the element type |
| causal-tail trim | real, -17.9% | fewer iterations, so proportionally fewer scalar ops |
| pass-1 unroll written out | inert, 0.2% | the interleave was already scheduled; the scalar work is per-iteration and stayed |
| `--mask zero` | 22.8-33.9% **slower** | removing the loads leaves every scalar op and adds a NaN path |
| tiled variant | 1.44x slower at 2048 | it has *more* scalar bookkeeping: per-tile max, rescale, strided partials |

## Next

- **Strengthen the address arithmetic, which is bit-exact by construction and does
  not touch the arithmetic contract at all.** Three changes, in expected order of
  value:
  1. Hoist the K and V row pointers out of their loops and advance them by a
     constant stride. `key + (j * num_kv_heads + kv_head) * head_dim` becomes one
     add per iteration instead of a 64-bit multiply-add chain.
  2. Use 32-bit `int` for `j`, `d` and the shared-memory indexing. The ranges are
     bounded by the context length and `head_dim`, both far below 2^31, so this is
     provably safe and it removes the `s_mul_hi_u32`/`s_addc_u32`/`s_cselect_b32`
     overflow machinery.
  3. Test the mask through a pointer rather than an index.
- Re-measure `SQ_INSTS_SALU` after each, against the 1.94e9 / 4.71e9 / 6.89e9
  baselines above. A drop in the scalar count is the mechanism confirming itself
  even before the wall-clock moves, and the wall-clock should follow it: at 95
  percent share on the `swa window=0` probe there is very little else in the
  kernel to move.
- The same per-key 64-bit arithmetic appears in the decode kernel and in the tiled
  variant, so if this works the pattern is worth a sweep rather than a one-off fix.
