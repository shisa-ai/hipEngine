# Per-instance AR batch qualification capacity

## Summary

The width-4 qualification no longer needs a test-only launcher. The AR batch
switch now resolves a **per-instance** plain-AR capacity ceiling: the plugin's
class bound stays 2, and with `HIPENGINE_QWEN4_EXP_AR_BATCH=1` one generator
accepts up to 4 resident rows only when the configured context is at most 2048
positions, the bound the live width-4 run measured. A normal
`python -m hipengine.server --max-active-requests 4` started on that
configuration and passed 67/67 C4 lifecycle checks. `scripts/qwen4exp_arbatch_c4_server.py`
was deleted because nothing in it is needed now.

This entry supersedes the launcher paragraph in
[`20261018T034525.696221Z-lhl-qwen4exp-arbatch-http-018db2`](20261018T034525.696221Z-lhl-qwen4exp-arbatch-http-018db2.md);
its C2/C4 lifecycle evidence and both existing artifacts still stand.

## Changes

### Supported opt-in configuration

| item | default-off | `HIPENGINE_QWEN4_EXP_AR_BATCH=1` |
| --- | --- | --- |
| plain-AR capacity ceiling | 2 (plugin class bound) | 4 at `max_sequence_length <= 2048`; 2 otherwise |
| explicit width | n/a (batch path off) | `HIPENGINE_QWEN4_EXP_AR_BATCH_SLOTS` 1..4, and <= serving capacity |
| longer or unknown context | production bound 2 | still 2; requesting 4 raises at generator construction |
| MTP | unchanged | unchanged: no MTP width attribute, route bound derived independently |
| scheduling | operator/default policy | operator/default policy; `protect_ttft` is required for independent arrivals to overlap, never overridden |

Implementation: `ar_batch_capacity_ceiling` and the two qualified-bound
constants in `hipengine/generation/qwen4_exp_ar_batch.py`;
`Qwen4ExpGGUFTextGenerator.__init__` reads the class bound through
`type(self)`, validates `resident_capacity` against the per-configuration
ceiling, and publishes the resolved value on the instance only. `LLM` then
reads that instance capability for `loop_config.max_active_requests` and the
batcher route caps, so generator admission and server admission agree. The
class attribute and its context mapping are never assigned.

`docs/API.md` documents the configuration under the decode-telemetry endpoint;
`docs/REFACTOR.md` records the ceiling as part of the batch switch's removal
scope. The module docstring states the capacity/context bound and that
`protect_ttft` is the operator's choice.

### Telemetry malformed hook

`GET /v1/hipengine/decode` previously reported `available: true` with
`decode_path: "unknown"` when the engine hook returned a non-mapping payload.
It now returns `available: false` with `reason: decode_telemetry_malformed` and
logs the payload type. `docs/API.md` lists all three unavailable reasons. The
existing endpoint test now asserts the malformed response instead of the
fabricated path.

## Validation

CPU boundary tests (`tests/test_unit_qwen4exp_ar_batch_capacity.py`):
ceiling table on/off at 1024/2048/2049/unknown context; switch-off rejects
capacity 4; switch-on accepts 4 at 2048, rejects 4 at 4096 and at unknown
context; `AR_BATCH_SLOTS=5` rejected as above the qualified width; a
qualified instance and a default instance coexist with the class bound still
`2` and its `{1024: 2}` mapping unchanged; the MTP route bound is identical
with the switch on and off and the plugin still publishes no MTP width.

### Not established / blockers

- **Production numerical gate.** Unrun; this remains lifecycle and control
  evidence. The batch path is not bit-identical to c1 by construction.
- **Long context.** The supported width-4 envelope stops at 2048 positions.
  Above that the production bound 2 applies and the batch path itself is
  unqualified live.
- **Ragged AR+MTP physical batching.** Mixed MTP stays on its own bound and
  never joins the AR batch; no speculative width claim is made.
- **Poisoned-step recovery under load.** Fail-closed path still unexercised
  live; the cancel phase produced no owner failure.
- **Default policy.** Independent arrivals overlap only with `protect_ttft`.
  Whether the default should change is a scheduler decision, not made here.
- **Capacity cap policy.** The plugin's production bound is still 2 and the
  width-4 ceiling exists only under the qualification switch. Promoting it is
  a separate decision that needs the numerical gate and a long-context memory
  probe.
