# Separate compact DMS configuration from observed storage

## Summary

The INT8 compact DMS server previously reported default BF16 capability
provenance, and its public `DMSConfig` path left `dms.policy` and the requested
metadata path null. Readiness now separates server requests, prepared compact
configuration, current backend formats and historical observed formats. It does
not certify a full-context allocation or request.

## Changes

- Both sidecar-path and `DMSConfig` session construction record loaded sidecar
  settings, selected route, resolved storage/scales and prefill/decision modes.
- Compact DMS capability provenance reports prepared storage, or null before
  preparation, and explicitly scopes this to configuration rather than dense
  approximate-KV evidence. No dense qualification or promotion is fabricated.
- Runner snapshots expose `active_stores` read from backend objects and
  `last_observed_store` captured before DMS session cleanup. Only host-side format
  metadata survives cleanup; no session, device allocation, request data or
  generated text is retained by this record. Existing retention fields remain.
- `GET /ready` resolves either DMS selection form and reports `prepared`,
  `requested` or `disabled` separately. Generic KV fields retain their values and
  are labelled `configuration_source: "server_request"`; compact INT8's resolved
  FP32 scales are reported in the DMS configuration and observed store metadata.
- Context diagnostics add `capacity_verified_by_readiness: false`. This says what
  the probe verifies, not that an external capacity test has never run. A scratch
  probe and short successful request are not full-depth capacity evidence.
- Added deterministic format, lifecycle, lazy/not-selected and HTTP serialization
  regressions. API documentation defines field sources and historical-store
  semantics; the root README is unchanged.

## Validation

- RED: six initial format/helper tests failed, as did all four new HTTP readiness
  cases, before implementation.
- Initial affected serving/ownership bundle passed 871 cases. Public constructor
  wiring tests additionally assert that sidecar settings and resolved scales
  reach the prepared policy. A new cleanup test calls `_release_row_resources`
  and checks that the format survives closure without retaining the session.
- Read-only independent review found no concrete blocking defect in the new
  provenance or lifecycle paths. It did not run tests or independently certify
  the live server; real serving validation is a separate coordinator check.
- All four documentation gates passed with 46 existing front-matter warnings.
- The default unit suite and deterministic bundle passed: compileall, fixtures,
  registry/CPU fixture smoke, smoke-add-plan, test tiers and diff whitespace.
  The final constructor/readiness unit bundle passed all 19 cases after adding
  the real cleanup-method regression.
- A real streamed completion on `bg-61` reported one device-backed compact INT8
  store during generation, then zero active stores and the same format in
  `last_observed_store` after cleanup. Both prepared and observed scales were
  FP32 per token/head. Generic capability provenance no longer reported BF16.
- `docs/testing/20261029-dms-readiness.json` records the real before/during/after
  check summary, request/response hashes and final production source hashes.
  Source hashes match startup and disk. The short probe did not test full-depth
  capacity. The normal server keeps 204,800 configured context, INT8 compact KV,
  FP32 scales and layer-outer prefill; no observation wrapper is installed.
