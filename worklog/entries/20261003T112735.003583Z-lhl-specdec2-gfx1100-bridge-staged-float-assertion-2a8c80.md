# Fix float-exact bridge aggregate assertion for staged complete_request_seconds

## Summary

`tests/test_unit_specdec2_perf_gfx1100_bridge.py::test_bridge_contract_accepts_complete_clean_strict_packet`
failed with `33.000000000000014 == 33.0`. The cause is an over-strict
exact-float assertion, not a calculation defect. The test builds 30 `staged`
rows with a per-request `complete_request_seconds` of `1.1`, and
`aggregate_bridge_rows` sums those per-request wall times. `1.1` is not exactly
representable in binary64, so `sum([1.1] * 30)` accumulates a 4.3e-16 relative
error (`1.1 * 30 == 33.0` exactly, but 30 sequential additions do not). The
`true_ar` (2.0) and `direct` (1.0) arms are exactly representable, which is why
only the `staged` assertion failed.

## Changes

- `tests/test_unit_specdec2_perf_gfx1100_bridge.py`: changed the `staged`
  `complete_request_seconds` assertion from `== 33.0` to
  `== pytest.approx(33.0)`, matching the `pytest.approx` already used for the
  derived speedup ratios two lines below. No production code changed; the
  aggregator's float summation, denominator selection, timing-ownership checks,
  and validation semantics are untouched.
