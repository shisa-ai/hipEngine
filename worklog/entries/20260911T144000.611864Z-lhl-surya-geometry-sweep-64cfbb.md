# Surya vision geometry sweep: resize and grid branches pinned in-suite

## Summary

The rect bring-up exposed a tile-addressing bug that only appeared on a
non-square grid, so the geometry axes of the vision tower are worth pinning.
The eight-geometry sweep recorded in `...0e2000` passed but was never a test,
leaving the `smart_resize` ceil branch and orientation symmetry unguarded.

Added a parametrized `test_gpu_vision_geometry_sweep_matches_cpu_reference`
covering four cheap cases. It asserts the produced grid *and* the vision
merger against the CPU reference, so a change to the resize branch fails
before the numerics are even compared.

## Changes

- `tests/test_surya_gpu.py`: new parametrized
  `test_gpu_vision_geometry_sweep_matches_cpu_reference`, with cases

  | Input | smart_resize | grid | branch exercised |
  | --- | --- | --- | --- |
  | 64x64 | 256x256 | 1x16x16 | below min_pixels, ceil up |
  | 100x100 | 256x256 | 1x16x16 | below min_pixels, ceil up |
  | 128x256 | 352x192 | 1x22x12 | non-square |
  | 256x128 | 192x352 | 1x12x22 | non-square, transposed |

  Each case asserts `tuple(grid) == expected_grid`, then vision vs the CPU
  reference with the same max/mean bounds as
  `test_gpu_vision_matches_cpu_reference`, plus finiteness.

The two non-square cases are deliberate transposes of each other, so a
row/column mix-up cannot cancel out. They are the same case the rect fixture
hits at a different grid, which is what makes them worth keeping separately.

## Scope

3:1 aspect ratios (512x1536, 1536x512, 1024x192, 192x1024) were measured in
`...0e2000` and pass, but each costs 12.8 s of CPU vision, so they are not
committed. The docstring records that and the measured bounds.

## Validation

- All four cases pass on gfx1151.
- Grid assertions are live: swapping the two non-square expectations fails with
  `128x256 resized to grid (1, 22, 12), expected (1, 12, 22)`, then restored.
- Full Surya bundle on gfx1151: 96 passed.
