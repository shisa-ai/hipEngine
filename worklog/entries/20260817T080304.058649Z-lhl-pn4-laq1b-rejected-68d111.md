# PN4: reject P3-LAQ1-B (Q8 dual T0 variants at practical limit)

## Summary

Implemented and rejected the P3-LAQ1-B candidate (T0 bit-exact variant of the
Q8_0 t16 dual GEMV that serves the c1 linear-attention qkv/gate stage).

First, the PN4 host-vs-GPU bound question was resolved with a complete-wall A/B
(`scripts/pn4_host_bound_ab_probe.py`): a memoized fast path on
`launch_gguf_linear` (skips key construction / env reads / session gets /
`_DISPATCH_RESOLVE_CACHE` lookup, jumps to the launch tail; 4400 of 5781 calls)
moved the sync'd eager wall 30.59 -> 29.73 ms/token (-857 us, -2.8%). The model
is ~94% GPU-bound; a launch-memoization refactor of gguf_linear.py is not
worth it, so the GPU-side P3-LAQ1-B was the correct mechanism family.

Three T0 variants of the Q8_0 t16 dual GEMV were implemented and measured
(owner stays default; all candidate code reverted after rejection):

- wordload (d[16] as 2x uint64 + q[16] as 4x uint32): bit-exact, ~62.4 us/layer
  vs owner 62.0 us (no gain; not load-instruction-bound).
- wordload + occupancy (launch_bounds 128,8): bit-exact, ~58 us/layer (best
  single run, ~9%, not reproduced on re-measure).
- wordload + 2-block ILP + occupancy (128,8): bit-exact, interleaved A/B
  60.0 vs 62.0 us/layer (delta -1.9 us, ~3%, within clock noise).
- owner threads=64: slower (75.6 us) AND not bit-exact (different reduction
  tree) -> not usable.

The 20-30% RED target (42-48 us/layer) is unreachable. The kernel is
latency/occupancy-bound (one block per 16-col tile, 768 blocks, per-block wave
reduce + xchg + syncthreads) at ~510-540 GB/s vs a ~650 GB/s marginal L2
ceiling (size-scaling probe), matching the Q4_K T16 precedent (P3-LAQ1: vecq
-10%, tile16 +5/-7%). The qkv_gate stage stays kernel-bound at ~2.29 ms/token.
