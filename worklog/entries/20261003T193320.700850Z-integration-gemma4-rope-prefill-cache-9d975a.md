# Gemma bounded host rotary-table reuse

## Summary

The default runner passes the existing warm-repeat regression protocol.
On zbook/Radeon 8060S, Gemma-4-26B-A4B-it `UD-Q4_K_XL`, production/BF16 KV,
512 prompt tokens and 128 fixed greedy outputs, pre-rebase A5 → integrated D1
prefill is **0.490560431 → 0.464509743 s (−5.31%)**, seven samples after one
full-shape warmup. All warmup, sample and public output IDs equal baseline.
1024/2053/4096 also improve and preserve output IDs.

This is not a cold-miss speed fix: first/new ranges compute the original tables.
The optimization reuses only position/configuration-derived host RoPE arrays;
no tokens, activations, logits, KV, device uploads or weights are cached by it.

Evidence: `benchmarks/results/2026-10-03-gemma4-gfx1151-rope-prefill-cache.json`.
This follows
`worklog/entries/20261003T190631.654325Z-integration-gemma4-short-prefill-diagnostics-a57b3c.md`.
Capacity-probe files, capacity worklogs and stash are unrelated and untouched.

## Changes

- Add a runner-local host-only cache of one multirow dense position range per
  frozen `Gemma4RopeConfig`, keyed by absolute start and row count. Decode
  bypasses it; reset retains only these position/configuration-derived tables.
  Each block still uploads token IDs, masks, cosine and sine to its own stream.
  Replacing a range replaces its host entry; close clears entries. No new device
  allocations, flags, dispatch routes, kernel changes or arithmetic change (T0).
- Add CPU regressions for non-power-of-two ranges, distinct rope contracts,
  changed positions/lengths, token independence, stream changes, decode/reset,
  one-entry bounds, runner isolation, cleanup and actual staging allocation reuse.
- Update the benchmark rollup, preserving the earlier pre-cache diagnostic as
  history and distinguishing warm-hit from miss behavior. No model topline,
  cold-speed, full-depth or llama.cpp claim is implied.
