# Root cause of the UD prefill gap: a model-wide raw-IQ repack veto

## Summary

Static follow-up to the route-gap measurement. The UD files do not put
"most" of their weights on the slow path; they put **all** of them there.
Through the real materialization planner, both published UD files plan
**0.0%** of their weight bytes into a layout the optimized kernel families can
consume, against **94.8%** for the plain `Qwen3.8-27B-Q4_K_S` file.

The cause is one model-wide boolean, and the fix is already named in the
code's own docstring as "UD-U3 layout selection".

## Changes

No code change. Static analysis, a promoted audit script, and a plan.

- `scripts/gguf_resident_layout_audit.py` (new): plans any GGUF through the
  real planner and reports optimized-versus-fallback bytes by
  (quant, layout, role). CPU-only, safe to run while the GPU is busy.
- `docs/UD-OPTIMIZED-ROUTE-PLAN.md` (new): the ordered plan.

## Mechanism

`plan_qwen35_gguf_materialization` computes a single boolean

    ar_repack_veto    = gguf_ar_decode_repack_veto(ar_layer_types)  # ANY tensor
    use_decode_repack = requested_decode_repack and not ar_repack_veto

and threads it into every `_spec_for_tensor` call.
`gguf_ar_decode_repack_veto` is
`any(type in {IQ2_XS, IQ3_XXS, IQ4_XS})` over all AR layer tensors.

So 117 IQ4_XS tensors in K_M (172 IQ4_XS + 5 IQ3_XXS + 1 IQ2_XS in K_S) strip
the T16/x8/planar layouts from all 554 rank-2 tensors. Rank-2 Q4_K then falls
to `q4_k_pack8` and Q5_K/Q6_K/Q3_K/IQ to `raw_gguf`, and those layouts have
only GEMV-shaped prefill kernels. This is why the earlier kernel census showed
even the UD file's **Q4_K** tensors on `gguf_q4_k_pack8_prefill_out`.

**The veto's rationale does not apply to these files.** Its comment reads
"Raw-IQ models' selected kernels consume compressed rank-3 GGUF layouts".
Measured: both UD files have **no rank-3 tensors at all** (554 rank-2, 312
rank-1), and every veto-triggering IQ tensor is rank-2 dense. It is a
MoE/selected-path guard firing on a dense model.

## Measurements (static, CPU-only)

| File | optimized bytes today | with `repack_veto=False` | resident weight bytes |
| --- | ---: | ---: | ---: |
| `UD-Q4_K_M` | 0.00 GB (0.0%) | 7.11 GB (44.2%) | 17.265 -> 16.284 GB (-5.7%) |
| `UD-Q4_K_S` | 0.00 GB (0.0%) | 5.15 GB (34.4%) | 15.972 -> 15.143 GB (-5.2%) |
| plain `Q4_K_S` (reference) | 15.03 GB (94.8%) | - | - |

**It is faster and smaller.** There is no memory/speed trade here:
`q4_k_pack8`, the fallback for rank-2 Q4_K, stores qweight+scales+mins at
`n*k*0.75` bytes (~6 bpw) where the source Q4_K is ~4.5 bpw and T16 is
compact. The veto currently costs both throughput and about 1 GB of VRAM.

## Decision

Queue, in order (full detail in `docs/UD-OPTIMIZED-ROUTE-PLAN.md`):

0. **Reconstruct the published 396.1 tok/s prefill protocol** before quoting
   any before/after. `use_wmma_prefill` defaults off and
   `Qwen35GGUFResidentSession.prefill()` has no per-call override; and
   `resolve_qwen35moe_fastpath_safety`'s docstring is stale where it says
   "T16 has no WMMA prefill kernels yet" - the plain-file trace runs
   `gguf_q4_t16_dense_wmma_prefill_shared_b_bf16_kernel` 212 times.
1. **Per-tensor repack eligibility (UD-U3).** Veto repack only for a tensor
   whose own type is raw-IQ, or only for rank-3 tensors, which is what the
   rationale actually describes. Keep `gguf_ar_f32_linear_contraction`
   model-wide and untouched - UD-U1 split these knobs for exactly this move.
2. **Close the remaining non-IQ fallbacks**: Q5_K raw (2.32/1.19 GB, role-scope
   gaps plus our own `ca4e01581` rank-2 flip), Q3_K (no T16 layout exists),
   Q6_K role gaps, the Q4_K `ssm_out` shape, and the
   `GGUF_DENSE_Q4_QMICRO_T16_GATE_UP_FILE_TYPES` stamp that admits
   `MOSTLY_Q4_K_S` but not `MOSTLY_Q4_K_M`.
3. **IQ4_XS** (4.76/6.29 GB, the largest single remaining block): dense entry
   point over the existing selected-shape IQ integer-MMQ kernels first;
   an IQ4_XS T16 repack, or prefill-only dequant to a BF16 workspace, as
   alternatives.

Item 1 is an arithmetic change, not a scheduling one - it changes which kernels
serve most of the model - so it needs the full production-profile numerics gate
plus the admission/consumer-surface suites, not just exact-parity tests.
