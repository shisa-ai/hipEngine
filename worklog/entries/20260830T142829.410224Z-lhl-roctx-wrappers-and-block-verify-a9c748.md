# ROCTX default fixed in three more wrappers; block-verify is blocked by a sentinel token id

## Summary

Two things came out of relaunching the block-rows trace that bg-76 lost. Discovery is fixed in three
more profiler wrappers (the fourth was fixed in 8c59be6d8), and the arm is now blocked behind something
else: `--mode block-verify` receives `token_id 2147483647` from prefill and dies on the vocabulary
check. That is a pre-existing defect, not a consequence of the ROCTX fix - the original queued arm
would have hit it immediately afterwards.

## Changes

- `scripts/gguf_continuous_owner_rocprof.py`, `scripts/gguf_decode_rocprof.py`,
  `scripts/gguf_packed_ar_rocprof.py`: `_default_roctx_sdk()` now builds candidates over
  `{sys.prefix, sys.base_prefix} x {_rocm_sdk_core, _rocm_sdk_devel} x {.so.1, .so}` plus `/opt/rocm`.
  Verified resolving to the installed library on this host for all three; `gguf_mtp_verifier_rocprof.py`
  resolves too (8c59be6d8). Diff is +9/-17 per file, discovery only; the `which("rocprofv3")` helper at
  `gguf_packed_ar_rocprof.py:988` is untouched (verified my diff removed no `which` lines).
- New `tests/test_scripts_roctx_sdk_discovery.py`: parametrized over all four wrappers, asserting the
  default **exists** when the SDK is installed under base_prefix. Asserting existence rather than path
  shape matters: a wrong default is a perfectly valid-looking `Path`.
- `docs/REFACTOR.md`: status update on the duplication entry, plus a correction - it claimed the
  earlier fix had landed in `gguf_packed_ar_rocprof.py`; that file had the `which`-based *helper*, but
  its `_default_roctx_sdk` was still prefix-only, so its `--roctx-sdk` default was broken like the rest.

## Blocker

`--mode block-verify --block-rows 8` fails after model load:

```
ValueError: token_id 2147483647 outside [0, 248320)
  scripts/gguf_mtp_verifier_rocprof.py:_run_parent -> child -> block_inputs = [int(cur)] * block_rows
```

`cur` comes from `cur = int(first.token_id)` where `first = session.prefill(prompt_ids, use_bulk=True,
return_logits=False)` (`scripts/gguf_mtp_verifier_rocprof.py:183-184`), so the resident session returned
INT32_MAX as its first token. Ruled out: it is not a Python literal in `hipengine/` nor in `kernels/`
(no `2147483647`, `INT32_MAX` or `0x7FFFFFFF` sentinel assignment found). Untouched question: whether
`return_logits=False` skips sampling and leaves an int32 buffer at its maximum, or whether a kernel
writes the sentinel deliberately. Measured: `--mode block-verify` fails. Inferred, not measured:
`--mode serial-step` takes the same `cur` into `session.step(cur)`, so it is expected to fail the same
way, and both are treated as unusable on this route until the sampler question is answered.

## Footgun found while relaunching

`DEFAULT_MODEL` in `scripts/gguf_mtp_verifier_rocprof.py` is `Qwen3.6-35B-A3B-UD-Q4_K_M.gguf`, and
`DEFAULT_PROMPT_IDS` is a fixed id list for that model. My relaunch omitted `--model`, so the first
relaunch profiled a different model than every measurement in this campaign - the same class of error
as trusting a label instead of reading metadata. Any invocation of these wrappers must name `--model`
explicitly. `DEFAULT_PROMPT_IDS` should probably be required rather than defaulted.

Also note the wrapper's exit code is meaningless here: `timeout … ; echo exit=$?` inside my launcher
meant bg-78 reported exit 0 while the python child failed. Same pattern as bg-77.

## Slip record

My first pass at the shared candidate list introduced two defects that only the smoke test caught, not
reading the diff: a double-escaped f-string (`f"python{{sys.version_info.major}}…"`, yielding a literal
`python{sys.version_info.major}` path) and then a dropped literal dot (`python312` instead of
`python3.12`). Both produced `exists=False`, which is exactly why the test asserts resolution.
