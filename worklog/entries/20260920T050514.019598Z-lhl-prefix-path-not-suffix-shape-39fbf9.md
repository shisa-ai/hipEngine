# The serial control flips too: the divergence is between two prefix prefill paths, not the suffix shape

## Summary

The control invalidates the suffix-shape attribution. Running the gate with
`HIPENGINE_GGUF_PREFIX_BATCHED_SUFFIX=0` -- so the candidate computes its suffix
with the same serial steps as the reference, and the suffix shapes match -- still
flips and still produces large KL, at a **higher** rate than the production
packet. The divergence therefore originates in the **prefix** prefill path, not
in how the suffix is computed. This supersedes the suffix-shape localization in
`20260920T033547.660457Z-lhl-dense27b-oracle-suffix-shape-localized-5e052a`,
whose 2-vs-1 vote split along the suffix shape but never controlled for the
prefix path.

## Changes

- None. Control measurement: the gate's recorded commands with
  `HIPENGINE_GGUF_PREFIX_BATCHED_SUFFIX=0` and `--teacher-forced-steps 128` on the
  three worst scopes. Driver `/tmp/t30-control.sh`, raw artifacts
  `/tmp/t30-control`.

## Validation

| scope | flips / 128 | mean KL | max KL | `semantic_boundary_mismatches` | `scheduler boundary_exact` |
| --- | --- | --- | --- | --- | --- |
| `category-general_ja` | 3 | 0.019561 | 1.322687 | 126 | True |
| `heldout-code` | 1 | 0.025313 | 3.160502 | 126 | True |
| `heldout-general_en` | 4 | 0.016631 | 1.882287 | 126 | True |

Eight flips over 384 rows is a **2.1%** rate, against the production packet's 11
over 1,024 rows (**1.07%**). Making the suffix shapes identical did not reduce
the flips; it increased them. The suffix shape is not the discriminator.

What every run in this investigation does show is a constant 126-component state
difference on the **prefix**: `semantic_boundary_mismatches` is 126 in the
control runs exactly as it was in the first `code` and `general_ja` measurements,
spread over every layer of both state families (47 conv + 47 recurrent + 16
kv.key + 16 kv.value for `code`), while `clone_boundary_exact` is 0 and the
native chunked oracle's boundary matches the candidate exactly
(`scheduler boundary_exact` True in all three control scopes). Two prefix paths
disagree:

- **Path A**, the runner's `prefill_batch` / `prefill_batch_native`, which the
  candidate uses and the served engine uses. It is self-consistent: bit-exact
  against an independent implementation of its own shape (0/0 in every category)
  and byte-stable across prefill chunk widths 128-1,024 on a 1,416-token
  Japanese prompt.
- **Path B**, `oracle_session.prefill(prefix)`, which the gate uses as its
  numerical reference. It differs from Path A by 126 state components on the
  same tokens.

Every flip and every large row in the 1,024-row packet is measured against Path
B, so the packet's verdict describes a **path difference**, not a production
defect. The packet measurement itself stands as recorded in
`20260920T045619.781116Z-lhl-prefix-reuse-calibrated-packet-50a069` -- the
comparison does fail the §6.1 bars at the standard's row count -- but its
attribution changes: the failing comparison is Path A versus Path B, and the
control shows Path B is the side that disagrees with a shape-matched arm.

## Next

- Identify the kernel/route difference between the two prefix paths. The 126
  components covering every layer of both state families point at the prefill
  kernel selection rather than at one layer: compare the dispatch plan and
  kernel names for `prefill_batch(prefix)` against `session.prefill(prefix)` on
  the same tokens, and check whether `session.prefill` takes the per-token or a
  different-tile route.
- Then the accuracy question, now correctly scoped to that pair: a
  `kernels/cpu_reference/` fp32 check on one layer's prefill can settle which of
  the two paths is accurate, which the whole-model question could not.
- Do not re-run the calibrated packet until the reference path is resolved;
  its verdict currently describes the path difference.
