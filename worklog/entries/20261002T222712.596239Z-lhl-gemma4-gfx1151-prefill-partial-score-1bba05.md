# gemma4 gfx1151: sharing the score dot across dimension groups makes the wider split pay, and the long-context prefill is 1.20x

## Summary

The previous two entries diagnosed the prefill attention kernel as register-starved
at the 256-VGPR ceiling and then measured every outside-in lever as negative. This
entry fixes it from the inside, and the fix is the one those entries named as the
open problem.

**The score is what the dimension groups have in common.** `C[key][column]` is a
dot over the whole head dimension, so every dimension group needs all of it -- and
the kernel was computing the complete dot independently in each one. That is pure
redundancy, and it is why the wider split lost: a four-group block issued the same
dot four times and the extra issue cost more than the smaller accumulator bought
(99.90 ms against 73.70 at the two-group shape).

Each wave now walks **only its own slice of the head dimension** and the partials
are summed through LDS before the softmax, so the dot is issued once across the
group. The D-fragment layout is identical across dimension groups -- element `e` of
lane `l` is row `2e + (l >> 4)`, column `l & 15` -- so matching `(lane, element)`
pairs are matching scores and the reduction is an elementwise add with no shuffle.
The cost is one barrier and one 4 KB LDS round trip per K batch.

## Measured, one full layer, median, same device and artifact

Prefill, 256 tokens, `scripts/gemma4_prefill_kernel_bw.py`:

| keys | before | after | speedup |
| --- | --- | --- | --- |
| 16,384 | 17.56 ms | **15.70 ms** | 1.12x |
| 65,536 | 73.70 ms | **59.49 ms** | 1.24x |
| 262,144 | 292.64 ms | **243.24 ms** | **1.20x** |

Decode, `--tokens 1` (the same probe's decode calibration point), 65,536 keys,
median of 9, measured as an A/B with the old build restored between arms:

| build | ms | % of DRAM roofline |
| --- | --- | --- |
| before | 1.42 | 79.2% |
| **after** | **1.39** | **80.7%** |

**No decode regression** -- it shares this kernel and the same redundancy, so it
gains slightly.

The split ladder at 65,536 keys, five runs per arm, which is what shows the
mechanism rather than just the total:

| shape | ms |
| --- | --- |
| two groups, duplicated dot (shipped before) | 73.70 |
| two groups, shared dot | 65.84 |
| **four groups, shared dot (shipped now)** | **61.11** |
| four groups, duplicated dot | 99.90 |

Sharing the dot is worth 1.12x on its own, and it is what makes the four-group
split worth a further 1.08x. The four-group shape halves the accumulator to 64
floats per lane, which is the register relief the earlier entries were looking for
and could not reach from the outside.

## The bug that made the first attempt wrong, and why it is recorded

The first version of this change produced `max abs diff 7.094e+00` against an
output peak of `4.656e+00` -- a wrong answer, not a tolerance miss. The cause was
not the reduction logic, which was correct on inspection: **the launcher computes
the LDS size in the `.hip`** (`gemma4_attention_prefill_wmma_full.hip`, the
`shared_bytes` at the top of the launcher), and it still sized only the Q and K/V
tiles, so the kernel wrote its partials past the end of the allocation. The
Python `WmmaFullShape.shared_bytes` property is an unused mirror of that number and
updating it changed nothing. Both are now correct, and the `.hip` one is the one
that matters.

This is worth recording because the failure mode is silent: nothing errored, the
kernel ran, and the only signal was wrong numbers.

## Changes

- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention_prefill_wmma_full.hip`:
  the score loop walks `kDimTilesPerWave` tiles starting at this wave's own
  `dim_group` slice instead of all `kDimTiles`; the partial is published to LDS and
  the groups' partials are summed after the barrier. The launcher's `shared_bytes`
  adds `kDimGroups * kColumnGroups * 32 * kKeyTiles * 8` floats. The header
  geometry comment now records the measured ladder, and the stale "128 threads
  cover two rows" line is `kRowStep`.
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention_prefill_wmma_full.py`:
  `DIM_GROUPS` 2 -> 4, and `shared_bytes` accounts for the partials.
- `tests/test_unit_gemma4_attention_wmma_slices.py`: the shared-memory test
  computes the partials too, and the thread-count test asserts each shape's own
  measured count rather than a shared one.

## Validation

- `tests/test_gpu_gemma4_attention_prefill_wmma_full.py`: **27/27, exit 0**, at the
  shipped four-group shape. RED first: the same file failed on the LDS-size bug
  above, which is what found it.
- `tests/test_unit_gemma4_attention_wmma_slices.py` +
  `test_unit_gemma4_prefill_attention_selection.py`: **62 passed**, after RED on
  both edited tests.
- The decode A/B restores the old build between arms and re-measures, so the
  1.39/1.42 pair is not a cross-session comparison.
- **The arithmetic contract is a tolerance, not bit-identity, and this change stays
  inside it.** The test file asserts `worst <= RTOL * peak` with `RTOL = 7.9e-3`
  and says in its own header that it is "loose enough not to flake on a
  reordering"; `assert_array_equal` applies only to NaN *placement*. Reassociating
  the score dot is the same class of divergence the kernel already declares
  ("summation order in the score dot").

## Next

- **The kernel is still at ~4% of the DRAM roofline**, and this unit moved its
  *time*, not its traffic: 243.24 ms at 262,144 keys is 1.20x but the DRAM fetch is
  unchanged. The register ceiling is relieved, not removed -- 64 accumulator floats
  against a 256-VGPR budget is still tight.
- **Eight dimension groups do not fit.** `kDimGroups = 8` needs 16,384 bytes of
  partials against 49,920 of tiles, 66,304 total against a 65,536 budget. Buying it
  would mean dropping the eight-element row padding or K_BATCH, and the padding is
  load-bearing for the fragment loads.
- The staging is still 33.6% of the instruction count and still happens once per
  block. Widening `kColumns` past 32 is now the untested axis: the accumulator
  argument against it is weaker than it was, and the LDS argument is unchanged.
