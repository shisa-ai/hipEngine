# The CFG negative LM branch is ~47% of the LM weight traffic; batching it is bit-exact and unexploited

## Summary

`VibevoiceTtsSession` builds **two** LM runtimes over the same weights, `positive`
and `negative`, for classifier-free guidance. `_negative_condition` runs a **full
LM forward for every diffusion frame**, and `forward_layers` streams all 28 layers'
weights for a single row. At 25 frames that is 25 x 2.62 GB = **65.5 GB**, against
the positive branch's 2.62 GB prefill plus 27 x 2.62 GB = 70.8 GB of decode.

So the negative branch is **about 47% of the LM's weight traffic** (65.5 of
138.9 GB), and the LM as a whole runs at roughly **110 GB/s** against the ~209 GB/s
this host sustains.

Batching the two branches into one rows=2 pass would halve that traffic and is
**bit-exact**: a GEMV's output element `(row, col)` is reduced over `k`
independently of every other row, so adding a second row changes no existing
output. This is the same property that made the accepted BM=64 WMMA column tile
safe, and it is the first substantial opportunity found in this session that is
not blocked by the quality gate.

## The numbers

LM weights per layer, from the loaded session: **93.6 MB** over 28 layers, or
**2.62 GB** per row of weight streaming.

| branch | rows | weight traffic |
| --- | ---: | ---: |
| positive prefill (batched) | 121 | 2.62 GB |
| positive decode | 27 | 70.8 GB |
| **negative decode** | **25** | **65.5 GB** |
| total | | **138.9 GB** |

At the measured 1.265 s of LM decode (1.450 s less 0.185 s of prompt) that is
**110 GB/s**, or about 53% of the 209 GB/s sustained peak measured on this host.
Batching the two decode branches would take the traffic from 138.9 GB to about
73 GB, which at the same rate is roughly **0.6 s saved** -- LM 1.450 s toward
0.86 s and pooled RTF 1.201 toward 1.05.

## Why it is not just "use rows=2"

The two runtimes are not interchangeable rows of one batch today:

- they own **separate KV caches** and separate positions, and the negative branch
  walks `[speech_start, feedback_0, ..., feedback_{n-1}]` while the positive walks
  the generated token sequence;
- they run at **different rates** -- the positive decodes once per generated token,
  the negative once per diffusion frame -- so a batched pass would need to pad or
  interleave rows that do not advance together;
- the attention kernels take `KVLiveSpans` per row, so a two-row pass needs two
  span sets rather than one.

None of that is a correctness obstacle -- the reduction argument above is what
makes the arithmetic safe -- but it is a real refactor of the session's LM
orchestration, not a kernel change.

## Why this matters for the objective

The previous two entries concluded that this model's remaining headroom is behind
arithmetic changes the generated-audio quality suite rejects. This finding is the
exception: it reduces **traffic** rather than improving the kernel, and it does so
without moving any summation order. It is the first concrete route toward the
objective's 2-10x framing that does not require a quality tradeoff, and it should
be attempted before any lower-precision-diffusion-weights campaign, which would.

  -> `_negative_condition` at line 285 calls `self.negative.forward_layers(...)` once
  per invocation, and the generation loop calls `_negative_condition` once per frame.
- `uv run python /tmp/lm_weights.py` -> 93.6 MB per layer, 2.62 GB per row.
- `uv run python /tmp/rows_probe.py` -> the GEMV bandwidth is a function of rows at
  fixed weight shape (85.0 GB/s at rows=1 falling to 52.5 GB/s at rows=8), so
  merging two rows=1 passes into one rows=2 pass is a traffic win rather than a
  free one; the saving is in the weight reads, which are shared.
