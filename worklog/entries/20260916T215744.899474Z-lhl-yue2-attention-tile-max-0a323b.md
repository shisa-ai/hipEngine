# YuE2 NAR attention tile maximum vectorized

## Summary

Follow-on to the attention-packing and hipBLASLt-algorithm entries. With both
landed, the product's 32-step solve of `mandarin-off-s1234` is 443.4 s -> 81.13 s,
of which attention is ~53 s and the projections ~15 s. Before reaching for a layout
rewrite, this unit asks what the attention kernel is limited by now.

**Finding: issue-bound, not traffic-bound.** `rocprofv3 --pmc L2CacheHit TA_TA_BUSY`
on the packed kernel at the production shape gives **L2CacheHit 94**, `TA_TA_BUSY`
1.35e8 against `GRBM_COUNT` 4.6e7 cycles (each of the ~40 texture address units busy
~7% of the time), and negligible `FETCH_SIZE`. The kernel's own K/V request volume
is 3.66 GB per call at eight rows per block (~124 GB/s) and 94% of it is served by
cache, so DRAM is not involved.

At eight rows the instruction budget is ~12 500 per lane-tile (about 10 100 VALU,
1 964 LDS, 385 FLAT) and a call executes ~228 600 lane-tiles, i.e. ~2.9e9
warp-instructions against ~128e9 issue slots per second: **~75% of the issue
limit**. The remaining levers are instruction count and dependency-chain length, not
reuse.

## Changes

The per-tile maximum walked the tile's shared-memory scores one float at a time: 128
LDS requests and 128 `fmax` in a single dependent chain per row per tile, ~16% of
the kernel's instructions and the longest chain left. It now reads four entries per
instruction (`float4`) into four independent accumulators and combines them at the
end, with the scalar walk kept for a `head_dim` that is not a multiple of four (the
rows are then not 16-byte aligned).

A maximum over a set is exact and order-independent for finite scores, which the
projections and the BF16 K/V guarantee, so the interleaved walk returns the same
bits as the serial one. The `fmax` sentinel for out-of-range keys (`-FLT_MAX`) is
unchanged, so a fully masked row still yields `expf(0) = 1` exactly as before.

## Validation

Per-call kernel time at the production shape (1 299 rows / 2 695 keys), alternating
the two sources within one session, `--repeat 8`:

| Pair | serial | vectorized | ratio |
| --- | ---: | ---: | ---: |
| 1 | 32.04 ms | 31.21 ms | 1.027 |
| 2 | 32.82 ms | 31.34 ms | 1.047 |
| 3 | 33.37 ms | 31.46 ms | 1.061 |

Median-of-medians ratio **1.047x**. End-to-end, `--only mandarin-off-s1234 --steps
2`: replay 28.2 / 28.0 s -> 27.9 / 27.9 s, solve 7.95 s -> 7.79 s.

**Absolute times drift ~10% between batches on this host**: the same vectorized
source measures 27.4-28.5 ms in the batch run right after, against 31.2-31.5 ms
here. Only the paired ratio is claimed; the 28.34 ms in the attention-packing
artifact is a same-batch figure from that session and is not comparable across
sessions.

The shorter chain does **not** make a larger row block viable: sixteen rows with the
vectorized maximum lands at 41.62 / 42.18 / 42.85 ms against 27.38 / 28.50 / 28.06 ms
at eight, so the accumulation and weights work still scales with the row count and
eight stays the optimum.

## Next

At the product's 32 steps the solve is 81.13 s against the pinned upstream's 27.32 s
(**2.97x**): attention ~53 s, projections ~15 s, conditioning prefill ~4 s, the rest
~9 s. The attention runs at 0.97 TFLOP/s against the projections' 15.6 TFLOP/s, so it
is the target, but the levers left inside this design are small — the accumulation
loop still reads eight shared-memory weights per key, which four-key groups would cut
to two (~6% of instructions). Closing the rest needs the register-blocked layout (a
lane holding several keys' dot products with shuffle reductions), which changes
arithmetic and therefore needs the production profile gates rather than bit parity,
and is a kernel unit of its own.
