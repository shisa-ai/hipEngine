# Add RF2 split-K target graph buckets

## Summary

Implemented and qualified RF2 host-side graph ownership for long-context native
target verification with split-K attention. Exact steady-schedule graph buckets
are retained for explicit diagnostics, but no long bucket is admitted to
automatic routing because complete graph wall is neutral versus eager and MTP
is materially slower than true AR.

## Changes

- Replaced the single per-budget target graph assumption with a bounded cache
  keyed by `(candidate_budget, N1/N2, context_limit)`.
- Kept the dedicated short context limit 1023 and added split-workspace buckets
  through the backend's 4K stream-ordered metadata cap. Admission rejects cycles
  that cross the 1024 short/split boundary, a 256-token split-count boundary, or
  a kernel-family boundary such as generic->grouped GQA at 4096. Those cycles
  remain eager; exact steady buckets include 1032, 2K, and 4095.
- Passed the immutable context limit into capture compatibility, dynamic
  `KVLiveSpans`, scalar-row views, and split-K workspace ownership.
- Bounded each session to eight target graph entries; eviction closes graph exec,
  stream, workspace, device-KV pins, and legacy aliases.
- Extended the RF1 oracle driver with direct target-graph mode and same-session
  repeats so RF2 can prove first capture and replay without diagnostic logits.
- Preserved short legacy aliases and cached-only device-proposal admission. Long
  proposal graphs remain capped independently, so long RF2 starts with host
  proposal plus reusable target graph rather than unsafe chaining.
