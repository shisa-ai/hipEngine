# gemma4 gfx1151: the decode walk's residual is its thread count, not the KV layout

## Summary

The decode walk reads one KV head's 1024-byte row out of each 2048-byte key
record. A committed entry explains its residual against the roofline like this:

> a block reads 1024 of every 2048 bytes, one KV head's row out of a two-head
> record, so consecutive 64-byte sectors are half-used by any single block. That
> is not a shape problem and another shape will not fix it.

**That mechanism is wrong.** 1024 bytes is sixteen *full* 64-byte sectors; the
gap a block leaves is a different block's data, and between them the two
`blockIdx.y` values demand the whole record. Measuring it instead of arguing it
gives the opposite conclusion from the one recorded: **at the walk's own grid a
flat contiguous read is slower than the strided one**, so the stride is not what
the walk is losing. The grid is.

## The measurement

`/tmp/kv_read_pattern_probe.py` and `/tmp/gemma4_kv_read_probe.hip`. Both arms
read the same 536,870,912 bytes -- 262,144 keys x 2 KV heads x 512 dims x 2 bytes
-- and differ only in the address sequence. The strided arm uses the walk's
shape: `blockIdx.y` selects the head, so the two blocks reading one key's two
halves run concurrently and between them demand the whole record.

| grid | contiguous (flat) | strided (the walk's pattern) |
| --- | --- | --- |
| 32 blocks x 64 threads (the walk's grid) | 101.1 GB/s | **158.8 GB/s** |
| 1024 blocks x 256 threads | 227.3 GB/s | 116.0 GB/s (invalid, see below) |

The valid comparison is the first row, and it inverts the recorded explanation:
**the strided read is 1.571x faster than the contiguous read at the same grid.**
A 32 x 64 grid is 2,048 threads, and a grid-stride loop over a flat array with
that few threads has each thread walking the whole buffer, so it is the
*contiguous* arm that suffers. The stride is not the cost.

The second row's strided number is **not usable**: the strided kernel parallelises
`for (i = threadIdx.x; i < half4; i += blockDim.x)` with `half4` = 64, so a
256-thread block idles three quarters of its threads. That arm is reported here
only to record that it was run and why it does not count.

The same-session achievable rate is **231.0 GB/s** at 1024 x 256, which is 97% of
the 238.5 GB/s figure the roofline kernel measured, so the control agrees with
the roofline it is being compared against.

  the roofline it is compared against.
- The strided arm's 1024 x 256 number is explicitly marked invalid in the table
  and in the text, with the reason (`half4` = 64 against a 256-thread block).

## What this points at

The walk reaches **178 GB/s** at 16 slices, against 231 achievable -- 77%. Its
grid is 32 blocks x 64 threads = **2,048 threads**, and that is the number the
probe says is too small. The prefill shape, whose walk runs at 105-118% of the
roofline, has **128 threads** per block; the decode shape has **64**, because
`kDimGroups = 2` is a single `constexpr` shared by both builds and the decode
shape's `kColumnGroups` is 1 where the prefill's is 2:

    kWaves = kColumnGroups * kDimGroups     decode 1 * 2 = 2  ->  64 threads
                                            prefill 2 * 2 = 4 -> 128 threads

The staging geometry is written for 128: `kRowStep = kThreads / kChunksPerRow`
is 2 there and 1 for the decode shape, and the source comment says "128 threads
cover two rows per iteration". So the decode shape is staging one row per
iteration with half the threads the loop was designed around.

## Next

- The thread-count hypothesis is **not tested**. It needs `kDimGroups` to become
  a per-shape build parameter (`GEMMA4_WMMA_FULL_DIM_GROUPS`), the Python
  `DIM_GROUPS` mirrored per shape, and a rebuild; that is the next step and this
  entry is the evidence that it is worth taking.
- `slices=16` at 32 blocks leaves 8 of 40 CUs idle, yet it measured faster than
  64 blocks. If the limit is threads rather than blocks, that is consistent: 32
  blocks x 64 threads is 2,048 threads either way, and more blocks only adds wave
  quantization. It also predicts that raising the threads per block is worth more
  than raising the block count, which is the experiment above.
