# DE-1 scope corrected: production decode already runs the exact variant, and the dp4a revert does not cover it

## Summary

Following the per-kernel localization (previous unit), this unit resolves **which variant the
production profile actually selects** and what that implies for `DE-1`'s action. Three findings, each
changing what the row should do next.

## Finding 1 — the capture is production, and production already runs the exact variant

`scripts/qwen4exp_context_decode_profile.py` builds its generator with
`_make_generator(factory_args, "production")`, and its report labels it
`"execution_profile": "production"`.

`hipengine/generation/qwen4_exp_profiles.py` defines two selection sets: `_strict_selections()`
selects `selected_dual_silu_logical128_t64` (exact); `_production_selections()` selects
`selected_dual_q8_1_dp4a_silu_logical128_t64` (dp4a). **But for this model's quant
(`gguf_ud_q4_k_xl`) the call site passes `recovery=True`**, and the recovery block applies:

```python
replacements = {
    "selected_dual_q8_1_dp4a_silu_logical128_t64_gemv_bf16_bf16_out":
        "selected_dual_silu_logical128_t64_gemv_bf16_bf16_out",
}
```

**So production decode runs the exact variant** — which is why the trace shows
`gguf_q4_k_selected_dual_silu_logical128_t64_kernel`. **The previous unit's 63.43 GB/s is therefore a
production-path measurement, not a strict-profile artifact.** That was the main risk in the previous
unit's result and it is now cleared.

## Finding 2 — the warp256 structure exists only as dp4a

`DE-1`'s action asks for "an exact-activation variant of the warp256 structure (the structure, not
the dp4a arithmetic)". The tree contains:

- `gguf_q4_k_selected_dual_q8_1_dp4a_silu_warp256_gemv_bf16_bf16_out` (gate/up)
- `qwen4_exp_q5_1_selected_weighted_sum_warp256{,_fast}_bf16_bf16_out` (down)

with the docstring: *"One block per output column with 32\*rows threads; warp w serves expert row w
(rows <= 12); lanes stride the 4-element groups by 32 ... Warp shuffle reductions, no barriers."*

**Every warp256 variant is dp4a. No exact-activation warp256 exists.** The recovery's
dp4a→exact replacement covers only the `logical128_t64` structure, so **the row's action is a real,
unbuilt unit.**

## Finding 3 — the dp4a revert does not cover the decode linear

`_ARITHMETIC_RECOVERY_EVIDENCE` is `benchmarks/results/2026-09-14-q8-prefill-numerics/artifact.json`.
Its failing candidate is `production_q8_fallback`, mechanism *"strict Q8 selected-down and dense Q8
MMQ fallback; **other production paths unchanged**"*, and it failed on **task quality, not numerics**:
the candidate produced *"Llama-2-7B uses GQA, reducing KV cache size by 4x compared to MHA"*, a claim
absent from the strict arm. `task_review.status` is `rejected_for_default_promotion`.

**That candidate did not change the decode linear.** Yet the recovery's `replacements` dict sweeps the
decode dp4a linear into the revert. The recovery's own gate then passes
(`conservative_recovery.status: passed`, `task_gate: passed_exact`, 18/18) — which shows the
**conservative configuration works**, not that the decode dp4a linear fails.

**And the decode dp4a linear has its own passing acceptance.**
`_DECODE_EVIDENCE` = `2026-08-29-gfx1151-qwen38-flash-next-production-dp4a-safe43-decode.json`:

- `status: accepted_explicit_production_profile`
- `numerical_gate.mean_kl: 2.72e-4`, `max_kl: 5.77e-3`

The warp256 dp4a variant failed admission at **max KL 0.121-0.431** — roughly **20-75x worse**.
**These are different arithmetic outcomes and must not be treated as one class.**

## What this does NOT establish

**That re-admitting the decode dp4a linear is safe today, or would pass the current production
envelope.** The recovery was a deliberate conservative response to a real task failure, and reverting
non-exact owners broadly was a reasonable choice at the time.

**No speedup is claimed**, and the row's 2.0x/5.8x figures belong to the **warp256** variant, not to
the reverted `logical128` dp4a variant.

## Two distinct next units
