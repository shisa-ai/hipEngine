# Pin dense-27B INT8 KV blocker and reject temporal-tail-first design

## Summary

Dense Qwen3.6-27B GGUF has no native INT8 K/V quality verdict. Its generic
policy, allocator, writer, and prefill bridge accept the model, but the direct
per-token/head INT8 GQA split-K decode consumer is specialized to block 256,
16 query heads, 2 K/V heads, and head dim 256. The 27B file requires 24 query
heads and 4 K/V heads, so the no-mirror native 4K/16 attempt fails closed before
producing any candidate decode logits.

A same-weight host reconstruction screen does not justify implementing a recent
BF16 temporal tail first. Pure INT8 reconstruction and disjoint recent 4K/8K
BF16 tails all passed one mixed 32K/16 prompt, but pure INT8 was both cheapest
and numerically best. BF16 K/V remains the only supported dense-27B route.

## Validation

- W7900/gfx1100 same-weight host emulation, mixed `32768/16`, BF16-teacher
  forcing: pure INT8 mean/max KL `0.00009635/0.00132275`, recent-4K BF16
  `0.00159868/0.02681615`, and recent-8K BF16
  `0.00095465/0.01571611`; all are `17/17` top-1. At 256K, projected K/V is
  `8.0625/8.1865/8.3105 GiB` respectively. This is host emulation, not a native
  correctness or performance claim.
- Native W7900 forced-long no-mirror mixed `4096/16` reaches the INT8 candidate
  and then stops with `ValueError: Qwen3.5 INT8 GQA split-K specialization
  requires block_size=256, num_q_heads=16, num_kv_heads=2, head_dim=256`.
  Model metadata is 64 layers, 16 full-attention layers, 24 query heads, 4 K/V
  heads, and head dim 256.
- Oracle memory arithmetic from live allocation code: PARO reuses one layer
  workspace (`1.0 GiB` for 27B versus `0.5 GiB` for 35B at 256K); GGUF keeps
  one per INT8 layer during chunk-outer prefill (`16 GiB` for pure 27B INT8,
  `8 GiB` if the unqualified 35B prefix-eight count were copied).
