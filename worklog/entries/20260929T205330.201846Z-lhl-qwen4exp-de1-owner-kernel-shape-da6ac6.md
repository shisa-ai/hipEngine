# DE-1 addendum: the expert GEMM owner is `selected_dual_wmma` at grid 1280

## Summary

Following the bandwidth-first gate (previous unit: the MoE block reaches 81.73 GB/s = 37.0% of the
documented roof, while a dense GEMV in the same capture reaches 226.67 GB/s = 102.6%), this unit
identifies the **owner kernel and its launch geometry** from the trace already in the tree, so
`DE-1`'s next cut starts from the real shape rather than from the family name.

## Findings

**The expert GEMM owner is `gguf_q4_k_selected_dual_wmma_iu8_risk_*`.**

- `selected` refers to **selected experts** (MoE routing), not selected positions.
- **`dual` confirms gate and up are FUSED into a single kernel.**
- It appears **188 times** in the capture totaling **2,709.02 ms**, at **`grid = 1280`,
  `workgroup = 128`**.

**1,280 is exactly the gate+up output row count for one expert** (640 gate rows + 640 up rows). So
the decomposition is **one workgroup per output row, each reducing over 2,560 input columns** - a
128-thread workgroup spanning the entire reduction axis.

**The router is separate and much wider:** `qwen35_router_logits_f32_token_tile_de*` at
**`grid = 131072`, `workgroup = 256`** (192 dispatches, 617.19 ms). This is the 251.66 MB/step router
term in the traffic model.

## Why this is worth recording

`DE-1`'s action targets *"the structure, not the dp4a arithmetic"*. The per-output-row decomposition
with a full-width reduction inside each 128-thread workgroup is a **structural** property, and it is
a plausible source of the 2.77x gap: one workgroup per row means the parallelism is capped at the
row count (1,280), and each workgroup's 128 threads must cooperatively stream 2,560 weights.

Naming the kernel also settles a naming trap: without reading the trace, `moe:expert_gate` suggests
a gate-only family, and the fusion structure (`dual`) is not visible from the family name at all.

## What this does NOT conclude

**Whether the per-row decomposition is the cause.** The raw trace spans **68 s** of prefill + warmup
+ measured steps (18,941 dispatches, 22.58% kernel-busy), so it **cannot separate kernel execution
from inter-kernel gaps at step granularity** without redoing the join that `attribution.json` already
performs. **No claim is made that changing the decomposition recovers the gap**, and no timing claim
is made here at all.

## Validation
