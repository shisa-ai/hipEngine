# TP2 resource ownership and allocation-failure cleanup

## Summary

A read-only review found four resource-ownership defects in the TP2
model-owning path, none of which change arithmetic:

1. `_apply_attention_shard` merges `ShardWeight` objects into each runner's
   resident layer map, whose `free` traversal calls `weight.free`. `ShardWeight`
   had no `free`, so `Qwen35GGUFResidentWeights.free` raised `AttributeError`
   part-way through; `MlpTP2GenerationSession.close` swallowed it and left every
   weight after the failing one unreleased. The uploaded attention shards were
   never released either.
2. `_build_rank` allocates the decode `_FullStackScratch` and the session owns
   it, but `close` cleared `_scratches` without freeing `scratch.buffers`.
3. `_build_bulk_prefill_workspace` registered allocations only after each rank
   finished, so a mid-rank failure leaked that rank's buffers, and `close`
   gated workspace cleanup on `_bulk_shard_group is not None or _bulk_rows`, so a
   partial build that never stamped `_bulk_rows` was skipped entirely.
4. `upload_shard_weights` and `ShardWeightAllocation` lost already-acquired
   buffers when a later upload/copy failed.

All four are now fixed with idempotent, device-scoped frees and fail-closed
partial-build cleanup. Kernel arithmetic, dispatch defaults, evidence
artifacts, and `docs/PLAN.md` are untouched.

## Changes

- `hipengine/distributed/shard_exec.py`
  - `ShardWeightAllocation` now tracks `_freed` and its `free()` is idempotent,
    so the resident map traversal and the session's uploaded-shard cleanup can
    both reach the same allocation without a double free.
  - A failed H2D copy in `ShardWeightAllocation.__init__` now frees the buffer it
    acquired before re-raising.
  - `ShardWeight.free(*, runtime=None)` added: it releases the backing
    allocation (once). This is the method the resident weight-map traversal
    already assumed existed.
- `hipengine/distributed/shard_weights.py`
  - New `free_uploaded_shard_weights(uploaded, *, runtime=None)`: releases every
    uploaded shard weight once, containing per-weight failures.
  - `upload_shard_weights` now tracks each created weight as it is made and
    frees the whole set on any failure before re-raising; the failed upload's own
    buffer is released by `ShardWeightAllocation`.
- `hipengine/distributed/tp2_generate.py`
  - Imports `free_uploaded_shard_weights`.
  - `_build_bulk_prefill_workspace` registers the scratch and each acquired
    buffer in `_bulk_scratch`/`_bulk_buffers` immediately, and wraps the build in
    a `try/except BaseException` that calls `_release_bulk_prefill_workspace()`
    before re-raising. `_bulk_rows` is stamped only on full success.
  - `close` now also treats a non-empty `_bulk_scratch` as a reason to release
    the workspace, frees `_attention_shard_weights` through
    `free_uploaded_shard_weights`, and frees each rank's decode scratch
    (`full_attn_split_growth_buffers` + `buffers`) under its device scope before
    clearing `_scratches`.
- `tests/test_unit_distributed_staged_and_shard.py`
  - `test_shard_weight_free_is_device_scoped_and_idempotent`
  - `test_shard_weight_allocation_frees_buffer_when_upload_copy_fails`
- `tests/test_unit_distributed_shard_weights.py`
  - `test_upload_shard_weights_frees_every_acquired_buffer_on_failure`
  - `test_free_uploaded_shard_weights_is_idempotent`
- `tests/test_unit_distributed_tp2_generate.py`
  - Fixture: fake attention shard weights now record frees
    (`attention_shard_weights_created`).
  - `test_close_frees_attention_shard_weights_exactly_once`
  - `test_close_frees_the_decode_scratch_buffers`
  - `test_bulk_workspace_partial_allocation_failure_frees_acquired_buffers`
  - `test_close_frees_a_partial_bulk_workspace_without_a_group_or_rows`

## Limitations

- The failures the parent reported (125 broad CPU failures that reproduce at
  the original `0433c6688`) are unrelated and were not touched.
- No GPU allocation/free counter was measured; the allocation-count evidence is
  the CPU fake-runtime `malloc`/`free` recording, which is the same oracle the
  existing shard-rank ownership tests use.
- The bulk workspace's `MlpShardGroup` construction is not itself wrapped in
  new cleanup beyond releasing the already-registered workspace; a
  partially-constructed group's internal buffers remain the group's own
  responsibility.
