# the q8_0 mmq candidate is slower than the wmma owner gemma4 already uses

## Summary

The dense Q8_0 MMQ prefill route was wired into the Gemma 4 runner, made to
actually claim the dispatch, and measured. It is slower on every admitted shape
at the most favourable setting, and much slower at the setting that keeps the
output exact:

| shape | WMMA GFLOP/s | MMQ, risk_threshold=0.0 | MMQ, risk_threshold=1e-5 |
| --- | --- | --- | --- |
| 2816 -> 2112 | 6508 | 4058 | 2712 |
| 4096 -> 2816 | 5153 | 3509 | 2863 |
| 2816 -> 4096 | 7153 | 3672 | 3225 |
| 2816 -> 2048 | 6493 | 3733 | 3155 |
| 8192 -> 2816 | 4281 | 3164 | 2618 |
| 2816 -> 8192 | 7150 | 4158 | 3135 |

Route total 273.3 ms retained, 468.5 ms at threshold 0.0, 575.2 ms at 1e-5. The
loop metric is unchanged: 580-587 tok/s before and after. The wiring and the
policy module were reverted; the tree is clean at `1b24ab1bc`.

## Why the lead looked good, and what it actually compared against

`resolve_q8_mmq_prefill_policy` carries this note on the Qwen4Exp policy:

> the float-coltile owner loses 6.4-7.3x to MMQ128 at these shapes

That is a real 6.4-7.3x. It is against the **float-coltile** owner. Gemma 4's
dense projections do not run on the float-coltile owner -- they run on the BF16
WMMA route (`prefill_bf16_bf16_out`), which is a different and much better
baseline. The MMQ candidate was never going to beat it, and now that is measured
rather than assumed.

The chain is also exact rather than approximate, which is what made it
attractive: `_launch_raw_mmq_d4x3` follows the GEMM with
`sparse_exact_correct_bf16` over the rows flagged as near a BF16 rounding
boundary, so the emitted BF16 matches the strict owner. The exactness was never
in doubt; the speed was.

## The dispatch-ownership defect, which outlives this candidate

The first wiring attempt changed nothing at all -- 272.1 ms against 273.3 ms,
every row within noise. The MMQ gate was firing and admitting every shape, and
still not running. An instrumented gate shows why:

```
[mmq-gate] rows=512 in=2816 out=2112 session=True policy=True
           abi=wmma_raw quant=gguf_q8_0 variant=wmma_prefill_bf16_bf16_out
```

`_wmma_prefill_dispatch` runs at `gguf_linear.py:3433`, before
`_q8_mmq_prefill_dispatch` at `:3494`. When the WMMA opt-in is on it rewrites
the variant to `wmma_prefill_bf16_bf16_out` **and the ABI to `wmma_raw`**, after
which the MMQ gate's `dispatch.abi == "raw"` test can never pass. The gate's own
comment says the WMMA step "does not override an explicit WMMA opt-in: only
fires when WMMA is off" -- true of the step it names, and misleading about the
interaction, because the MMQ step is downstream of it.

The fix is that the two are competing owners of one dispatch point, so whichever
is going to run has to be the one that claims it. Withholding the WMMA opt-in
made the MMQ fire, and also exposed the shape of the fix: **withholding it is
block-wide while admission is per-shape.** The refused shapes lost their WMMA
owner as collateral and regressed hard -- `2112 -> 2816` went 22.44 ms to
60.57 ms, `2816 -> 1024` went 1.83 ms to 5.00 ms. The correct mechanism already
exists one level down: `_wmma_prefill_weight_filter` is a per-weight
`ContextVar`, so a future takeover can decline WMMA for exactly the weights it
admits instead of for the whole block. That is the reusable finding here, and it
is not specific to this candidate.

## risk_threshold is a large, non-obvious lever

The Qwen4Exp policy sets `risk_threshold=0.0` and says why:

> a 1e-5 threshold queues a large fraction of all floats and degenerates the
> repair pass into a near-full exact recompute (measured 0.634 s at pp508).
> Threshold zero queues only exact-boundary values, making the repair
> effectively free; the arithmetic change is covered by the production profile
> gate.

The same lever moves this route by 107 ms (575.2 -> 468.5) on a BF16-output
path. Threshold 0.0 is **not** an exact configuration -- it is a changed
arithmetic that the Qwen4Exp note explicitly defers to a profile gate -- so the
two rows in the table above are not two settings of one route, they are an exact
route and a candidate. The exact one is the slower one.

## Changes

None. `hipengine/runtime/gemma4.py` is byte-identical to `1b24ab1bc`, and the
`gemma4_q8_mmq_policy.py` written during the attempt was removed.

## Validation

- Per-shape tables measured with the same event-timed spy, 512-token prefill,
  2 repeats after 1 warmup, on the 8060S (gfx1151).
- The route was confirmed to actually run before any speed number was believed:
  the trace above is the gate's own decision for each shape, and the second
  table is what changed once the WMMA opt-in stopped claiming the dispatch.
- The metric was re-measured after the revert and matches: 580-587 tok/s.
- `tests/test_unit_gemma4_runner.py` has two failures. One is mine and was
  fixed before the revert (a session that allocated 110 KB of scratch for a
  one-token decode). The other, `test_incremental_decode_matches_a_dense_prefill`,
  fails identically on the clean tree and is **not** an unexplained defect:
  `2f1e352ac` bisects it to `940255881` and names the mechanism -- the MoE
  gate/up route is selected through `gemma4_moe_prefill_route_enabled(lanes,
  num_experts)`, so a 4-token prefill takes the int8-dp4a route while decoding
  those tokens one at a time takes the fp32 grouped route. That is a
  batch-composition invariance violation, and `HIPENGINE_GEMMA4_MOE_GATE_UP_MMQ=0`
  clears it. It is recorded as an open arithmetic-promotion decision, and it
  matters for MTP, where draft and verify run in different batch shapes by
  construction.

## Next

Four route- and geometry-level leads are now closed by measurement: the
attention query tile (lost 20 percent), the MMQ tile geometry (0.984x, swept
previously), the WMMA preference for dense Q8_0 (the env var does not move
shapes between routes), and this candidate (1.6-2.1x slower). What remains is
not route selection. The dense linears run at 4-8 TFLOP/s of int8 DP4A with
residency ruled out, so the open question is the work per instruction in the
retained kernel's inner loop -- the per-k-step tile-load instruction count and
the barrier count -- and that is a kernel measurement rather than a dispatch
one.
