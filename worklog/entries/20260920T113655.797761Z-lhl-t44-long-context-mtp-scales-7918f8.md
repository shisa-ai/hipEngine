# Task 44: MTP already scales to 12K context at 1.42-1.74x - the 1,023 gate is the only blocker

## Summary

MTP works at long context today. With `HIPENGINE_MTP2_MAX_CONTEXT_TOKENS=32768`
on one server process, MTP beats a same-process autoregressive arm by
**1.42x-1.74x** from 1,804 to 12,142 prompt tokens, at 0.992-0.996 output
coverage, with greedy output byte-identical to AR at every shape. A prompt of
512 tokens decoded 2,048 tokens - crossing the 1,024 attention transition
mid-generation - ran at 1.27x with **0.999 coverage and no bucket miss at all**.

There is no kernel problem to fix. The 1,023 window is an admission gate over
territory whose numerics have not been qualified, and it is the only one of the
three 1,023 boundaries on this path that refuses work.

## Measured

One server process, `--speculative-mtp-serving enabled`,
`HIPENGINE_MTP2_MAX_CONTEXT_TOKENS=32768`, `--max-context-tokens 16384`,
`--execution-profile production`, `--speculative-candidate-budget 3`,
`--kv-storage bf16`, `--prefix-cache off`. Both arms from that process, the AR
arm selected by `{"speculative_mtp": false}`, both asserted with
`--expect-route`. Qwen3.8-27B-Q4_K_M, `hip_gfx1151`, greedy, 2 repeats.

Long prompts, 256 decode tokens:

| shape | prompt tokens | AR tok/s | MTP tok/s | ratio | MTP coverage |
| --- | --- | --- | --- | --- | --- |
| 2048 | 1,804 | 11.51 | 16.31 | **1.42x** | 0.996 |
| 8192 | 6,972 | 11.90 | 20.69 | **1.74x** | 0.992 |
| 14336 | 12,142 | 10.91 | 16.72 | **1.53x** | 0.996 |

Crossing the transition, prompt 512 with 2,048 decode tokens:

| arm | tok/s | ratio | coverage | cycles | accepted | rejected | fallback events |
| --- | --- | --- | --- | --- | --- | --- | --- |
| AR | 11.90 | - | - | - | - | - | - |
| MTP | 15.06 | **1.27x** | 0.999 | 1,063 | 983 | 2,204 | `no_provider: 1` |

The crossing arm emitted 2,046 of its 2,048 output tokens from MTP and 2 from
AR. Greedy identity against the AR arm is exact at every shape
(`--identity-tokens 8`: identical, longest common prefix = full string, 45-51
characters).

Command: `/tmp/t44-sweep.sh` driving `scripts/gguf_mtp_server_pair_bench.py`.

## The earlier bucket-miss diagnosis was wrong

`bg-238` reported 49 `target_graph_context_bucket_miss` events and 0.602
coverage at 945 prompt tokens, and the obvious reading was that decode cycles
crossing 1,024 are refused by `_native_target_graph_context_limit`'s
`if start < 1024: return None`. **That reading is wrong.** Raising the window
removes the misses entirely: the crossing arm above straddles 1,024 for
hundreds of cycles and reports no bucket miss, and `bg-240`'s 945-token shape
reached 0.992 coverage at the raised window.

The misses were a consequence of the adapter gate, not an independent
limitation. Once the gate refuses a row, the row drops to the K0 path and the
graph-level accounting records misses on the way down. So the graph bucket
selector is not binding while the window admits, and the 256-token split-count
boundary is not the constraint either.

That leaves one real boundary: the adapter's prompt gate. `docs/REFACTOR.md`
had already recorded this ("of the four boundaries on this path only the
adapter window refuses a request"); this run shows what that gate is costing.

## Why 1,023 exists

The gate is a conservative admission window over a route whose numerics were
never qualified at long context, not a kernel capability limit. The adapter
comment states it directly: streaming activation is retained only through the
already-qualified short target context, and longer requests stay K0 until an
exact shifted-page eager target owner is qualified independently of graph
capture. The kernels themselves are fine - the graph path served 12,142 prompt
tokens at 0.996 coverage.

The prior long-context evidence (`benchmarks/results/2026-09-17-gfx1151-qwen38-
long-context-mtp-screen.json`) is stale and understates the current state. It
measured 6.29 tok/s at 3,530 tokens for the per-row strict route (0.57x of AR)
and 13.82 tok/s for a batched-row arm that had to disable split decode globally
at ~9% cost to normal decoding. This run measured 17.37 tok/s at the same 3,530
tokens with split decode at its default.

## Status of this claim

Diagnostic, **not retainable**. One synthetic prompt per shape, two repeats,
128-256 decode tokens. Not the mtp-bench category suite, and the production
numerical gate (mean/p95/p99/max KL, top-1 by category, determinism, isolation,
task quality) was not run. Greedy identity over 8 probe tokens is an
observation, not that gate. What it establishes is that the window, not the
kernels, is the binding constraint - so qualifying the long-context route is a
gate-running exercise rather than a kernel project.

The crossing arm's lower ratio (1.27x) is a draft-acceptance effect, not a
crossing penalty: its accepted/(accepted+rejected) is 983/3,187 = 31% against
47% for the 6,972-token shape, and the two arms use different prompt text, so
acceptance is not comparable across them.

## Validation

- All four arms passed their `--expect-route` contract and wrote artifacts
  (`mtp-long`, `ar-long`, `mtp-cross`, `ar-cross`, all exit 0). An arm that ran
  the wrong route would have exited 3 and written nothing, so the route claims
  above are enforced rather than asserted by hand.
- Greedy identity probe (`--identity-tokens 8`) compared MTP against AR per
  shape: identical text at 2048, 8192, 14336 and 512, longest common prefix
  equal to the full string (51/51, 48/48, 48/48, 45/45 characters).
- The AR arm is a same-process control selected by the request field, and its
  rates (11.51 / 11.90 / 10.91) match the independent
  `--speculative-mtp-serving off` baselines measured in task 43 (11.53 / 11.90)
  to within 0.02 tok/s at the shapes both cover.
- Not run: the production numerical gate and the mtp-bench category suite. See
  "Status of this claim" above.
