# QSA grid/head_count anomaly is a profiling artifact; K/V reuse is measured dead

## Summary

Sprint Q's gate was to resolve the grid/head_count observation before any kernel
work. **There is no anomaly.** `rocprofv3` reports total *work-items* in
`Grid_Size_X/Y`, not grid dimensions, so the traced `(192, 1021, 1)` is a true
grid of `(6, 1021, 1)` and `6 = query_heads/HEADS = 24/4` - exactly the
metadata's `head_count` 24. The "768" was `6 x 32` (blocks x workgroup) read as
heads and multiplied by 4.

Verified exactly on three kernels whose launches are known from source:
`qwen35_moe_group_scatter_gather_kernel` `dim3(10240), dim3(256)` -> reported
(2621440, 1) = 10240x256; `weighted_lanes_sum_out_kernel` `dim3(20, 1024),
dim3(128)` -> reported (2560, 1024) = 20x128; the QSA kernel `dim3(6, rows),
dim3(32)` -> reported (192, rows) = 6x32.

The production route is `strict_h256_head_quad_rows_spans` (HEADS=4), chosen by
the **profile**, which sets `HIPENGINE_QWEN4_EXP_QSA_H256_WAVE_PREFILL=page256` and
`HIPENGINE_QWEN4_EXP_QSA_HEAD_PAIR=quad` itself. The benchmark command sets
neither, which is why an env-only reading misses it.

grid.y is `sparse_rows`, not the chunk length:
`dense_rows = max(0, min(count, dense_equivalent_limit - start))`,
`dense_equivalent_limit = 512*4+3 = 2051`. For code-p4096's four 1024-token chunks
that is 0, 0, **1021**, **1024** - the two observed grids, 24 launches each over
24 QSA layers.

## Family cost

48 QSA launches, 1237.3 ms total. `qsa_sparse_attention_h256_wave_rows_f32_kernel`
is **910.8 ms (73.6%)** at 18.98 ms/launch; `qsa_score_f32_kernel` 212.2 ms
(17.1%); the remaining six kernels 114.3 ms.

## Ranking (the second half of the acceptance)

The GQA ratio is 24/2 = 12, so HEADS=4 captures a third of the K/V reuse ceiling.
The existing `scripts/qwen4exp_qsa_head_tile_microbench.py` prices this at the real
geometry and its variants are **bit-identical**, so it measures the
arithmetic-preserving ceiling directly. First run to an artifact:

| HEADS | blocks/row | K/V GB | median ms | eff GB/s | vs HEADS=4 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 24 | 51.59 | 54.938 | 939.1 | 0.352 |
| 2 | 12 | 25.80 | 20.823 | 1238.8 | 0.929 |
| **4 (shipped)** | **6** | **12.90** | **19.335** | **667.1** | **1.000** |

**The 2 -> 4 step halves K/V traffic and buys 1.08x.** Effective bandwidth falls
from 1238.8 to 667.1 GB/s as the tile widens - the signature of a kernel that has
stopped being traffic-limited and started being issue-limited. Extrapolating,
HEADS=12 would cut traffic to 0.33x for roughly 8%, about 73 ms of 910.8.

Ranking: **(1) tensor cores** - changing arithmetic, needs the production gate plus
a registered strict fallback, and the only lever on the real bottleneck;
**(2) K/V reuse via HEADS** - preserving, measured dead, ceiling ~8%;
**(3) LDS staging** - preserving, dead for the same reason, and the block is a
single 32-lane wave so there is no intra-block cross-warp sharing without a
multi-wave restructure. Ranks 2 and 3 are one lever (K/V traffic) and the
measurement says K/V traffic is not what costs.

## Next

Do not spend on K/V reuse or LDS staging for QSA prefill. The sparse attention
kernel is issue-limited, so the next unit is a WMMA `Q*K^T` / `P*V` candidate with
a registered strict fallback, gated on the production profile. Note the kernel is
exact (`__fmul_rn` with an asm barrier to stop contraction), so a tensor-core
variant changes arithmetic and needs the full gate, not a parity argument.
