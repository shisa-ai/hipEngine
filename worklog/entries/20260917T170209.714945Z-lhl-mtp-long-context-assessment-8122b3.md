# Long-context MTP: one admission limit, two graceful declines, and the piece that is missing

## Summary

The reviewer's three-layer description of the 1,023-token cap is confirmed in the
code, with one correction that changes what the first candidate should be: only
the first layer is an *admission* limit. The other two are performance declines
that already fall back without giving up correctness, and the draft side has the
same shape as the target side.

| Layer | Where | Nature | What actually happens past the boundary |
| --- | --- | --- | --- |
| Serving adapter window | `qwen35_gguf_mtp2.py:132` `_MTP2_QUALIFIED_CONTEXT_WINDOW = 1023`; prompt gate at `:1372` (`target_context_k0`), advertised `max_context_tokens` consumed by `speculative/policy.py:394` (`target_graph_context_bucket_miss`) | **request-level** | the request never gets prompt streaming, so it decodes with no draft provider (`no_provider`) for its whole life |
| Target graph bucket | `runtime/gguf_native_spec_cycle.py:413-475` `_native_target_graph_context_limit` | **per-cycle** | the cycle runs the **eager** target verify (`verify_target_block`) and records `last_native_spec_target_fallback_reason = target_graph_context_bucket_miss`; the request continues to speculate |
| Split-K boundary in the verifier | `runtime/qwen35_gguf_runner.py:11095` (`_GGUF_FULL_ATTN_DECODE_SPLIT_MIN_CONTEXT_DEFAULT = 1024`) and `:7703-7713` (`strict_long_rows`) | **per-span route** | rows are verified one at a time through the exact per-row route, because `_run_full_attention_attn_chain_rows_exact` raises `"staged full-attention chain currently requires non-split decode"` |
| Draft proposal graph | `runtime/qwen35_gguf_nextn.py:216` `_NEXTN_EXACT_CHAIN_GRAPH_MAX_CONTEXT = 1023` | **per-cycle** | the graph is skipped with status `eager_long_context` and the eager proposal chain runs, bounded only by resident capacity |

Two details worth recording, because they are what make the ordering below what
it is:

- The graph bucket selector is not a 1,023 limit. For `start >= 1024` it returns a
  bucket whenever the span keeps one split count and one split-kernel identity,
  and the backend already declares
  `GGUF_SPECDEC2_NATIVE_TARGET_GRAPH_MAX_CONTEXT = 65544` on `gfx1151`. The two
  cases it declines are a span that *straddles* 1,024 and a span whose split
  count changes mid-span, and both decline per cycle into the eager path.
- The split-K predicate that forces the per-row verifier is the *normal decoding*
  threshold, not a verifier-specific policy. Raising it is therefore a global
  trade, and it is the trade the earlier screen measured: about 9% off normal
  decoding at 3,530 prompt tokens (10.96 to 10.01 tok/s) to buy the batched
  verifier route.

## What the earlier screen already measured

From
[`20260917T110423.127720Z`](20260917T110423.127720Z-lhl-long-context-mtp-window-screen-729b4b.md)
and the two `docs/REFACTOR.md` entries it produced: with the window raised, the
long-context MTP route is **0.57x** at 3,530 tokens when the verifier is forced
onto the per-row strict route, and **1.38x** when rows batch. Both are diagnostic
screen arms, not retained evidence rows, and the screen artifact is
`benchmarks/results/2026-09-17-gfx1151-qwen38-long-context-mtp-screen.json`.

So the layers are not three independent blockers to fix in sequence. Raising the
adapter window alone produces a *slower* MTP route; the per-row verifier is what
makes it slower, and the only lever that currently removes it costs normal decode.

## First concrete candidate

**Give the staged multi-row verifier chain a split-K attention leaf.** Today
`_run_full_attention_attn_chain_rows_exact` attends every verifier row in one
non-split call and therefore refuses to run at all once
`_use_gguf_full_attention_split_decode(start_position + rows)` is true; that
refusal is what `strict_long_rows` exists to route around. A split-K leaf that
takes N rows with a shared split count would remove the refusal, and the graph
bucket selector already guarantees the input space is well defined: it only ever
selects a bucket for spans that keep one split count and one split-kernel
identity across all rows.

The alternative REFACTOR already names - a verifier-scoped row schedule that
keeps split-K per row while batching the non-attention work - is the same win by
a different cut, and may be cheaper if the attention leaf turns out to be the
expensive part.

Either way the gates are the declared ones, and they are the reason this is a
campaign rather than a patch: a strict/production numerical gate at depth against
the per-row exact route as teacher (the split-K accumulation order is not the
short-path order, so this is a real arithmetic change and needs the calibrated
mean/tail/max KL, top-1 by category, determinism and isolation gates), then an
AR-versus-MTP ratio at 3.5K-8K over the full mtp-bench category suite with a true
no-MTP AR denominator from the same protocol.

## What is missing

- No measured production-profile numerical evidence for MTP spans at or beyond
  1,024 tokens. The window screen is diagnostic; nothing has been run through the
  profile gates at depth, so "long-context MTP is exact" is currently unverified
  rather than verified.
- No batched split-K leaf, and no verifier-scoped row schedule.
- The interim lever (raise `HIPENGINE_GGUF_FULL_ATTN_DECODE_PAGED_MIN_CONTEXT` to
  the session capacity) is a global setting with a measured normal-decode cost,
  so it cannot be the retained answer.
- The adapter window and the draft graph cap are knobs, not blockers: both have a
  working fallback path behind them, and both must keep reading the same value as
  the advertised `max_context_tokens` so admission and per-cycle policy cannot
  disagree.

## Changes

- `docs/REFACTOR.md`: added the draft-side graph cap to the long-context entry
  and recorded the ordering conclusion (the graph and split layers degrade
  gracefully; the batched leaf is the only piece that turns long-context MTP into
  a win).
- No code change. This unit is an assessment; the candidate it names needs its
  own RED contract before any implementation.
