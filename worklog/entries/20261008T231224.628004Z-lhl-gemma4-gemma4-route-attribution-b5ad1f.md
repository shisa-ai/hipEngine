# Correct the flash route's scope and the decode route counter's attribution

## Summary

Two statements I published today are wrong, both about which variant serves a
decode launch. The measurements they came from are unaffected; the
interpretation is.

**The scoped decode route has a resident-bound guard I described away.**
`_select_exact_decode_attention` returns the scoped variant only for a one-token
untrimmed global call (head_dim 512, GQA ratio 8) whose key count is past the
resident LDS bound. Measured on the fixed tree,
`gemma4_attention_resident_overflows(head_dim=512, keys)` is False at 4,096,
8,191 and 15,616 keys and True at 15,617, so the scoped selection does not apply
below ~15.6K keys. An A/B run at 2,049 and 8,193 keys confirms it from the other
side: all three arms report route `exact` and their logits are **bit-identical**
(`5f3e5471...`, `7c37fffa...`), which can only happen if the arms ran the same
kernel.

So the sliding-band gate's line "122,695 of 122,695 decode launches were flash
across both head dims" over-claims. Its head_dim-512 launches at keys 4,097-8,191
were not the scoped flash route.

**`decode_selection` is a sticky counter, not a per-launch label.** It is set
inside the C launcher that honors a flash request, and my observers read it
immediately after each call and attributed the value to that call. That is only
valid when the call set it. Below the bound the layer keeps the native path,
which may reach a launcher that never writes the counter, and then the reading
carries the *previous* call's answer. The gate's `flash_launches` therefore
counts "calls after which the counter read 3", not "calls that launched flash".

What still stands: the flash kernel does run for one-token decode below the
bound when a caller passes the negative-slice request, because the launcher tries
that request before the resident-bound check (source, `gemma4_attention.hip`).
Which calls in that run did so is not established by this evidence.

## Changes

- `docs/KERNELS.md` -- the `gemma4_flash` row now states the scoped selection's
  real guards (one token, untrimmed global, head_dim 512 with GQA ratio 8, past
  the resident LDS bound, native path kept below it) and separately the
  launcher's flash-request-first behavior, instead of the two paragraphs I
  published earlier in the day, the first of which dropped the bound entirely.
- `scripts/gemma4_public_route_probe.py` -- records the route the layer resolved
  for each one-token call (`scoped decode resolution`, the accurate per-call
  answer) alongside the launcher counter, now labelled
  `launcher selection counter` with `launcher_selection_sticky: True`. The module
  docstring says which record to count from and why.
- `tests/test_unit_gemma4_public_route_probe.py` -- a test for the resolver
  record, and the counter test updated for the labelled field. 12 passed.
- No measurement is withdrawn. The gate verdicts' numeric bars, the A/B timings
  above the bound, and the promotion are unchanged.

## Validation

- `gemma4_attention_resident_overflows(head_dim=512, keys)` printed directly at
  4,096 / 8,191 / 15,616 / 15,617 / 16,384 keys: False, False, False, True, True.
- The resolver's guards read at source (`gemma4_layer.py`, lines 705-758).
- A/B at 2,049 and 8,193 keys
  (`benchmarks/results/2026-10-09-gemma4-flash-plan-ab-short-and-256k.json`):
  plain 12.40 ms, staged 15.52 ms, flash 12.37 ms, all three route `exact`, all
  three logits `7c37fffa...`. The timings are not a route comparison, because
  there is no route difference; the staged arm's 25% is not explained by this
  evidence and is not claimed as one.
- `pytest tests/test_unit_gemma4_public_route_probe.py`: 12 passed.
- `python3 scripts/docs/check_all.py`: passes.

  not affected by this, but it was not verified with the better instrument either.
