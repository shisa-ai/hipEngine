## Changes


- Critical path is AR blk.0-39 only: raw IQ3_XXS selected gate/up, raw IQ4_XS selected down plus blk.39 gate/up, registry-driven resident dispatch, GPU1 full-model correctness, decode-graph coverage, and then grouped/compact prefill. The correctness-first direct `x_rows` ABI must cover both c=1 (`x_rows=1`, `rows=top_k`) and per-token prefill (`rows=x_rows*top_k`) before any compact optimization.
- Kernel family scope is `hipengine/kernels/hip_gfx1100/quant/gguf_iq_gemv.{hip,py}` with raw-pointer BF16 I/O. It must expose an IQ3_XXS **single selected GEMV primitive** as well as fused IQ3_XXS gate+up+SiLU, because the fused composite requires a numerically equivalent unfused chain; IQ4_XS needs a single selected GEMV primitive, which also serves both halves of blk.39 gate/up through the existing separate SiLU chain. The fused IQ3 path must preserve the fallback's BF16 rounding boundaries, not merely approximate a shader's FP16 ordering.
- RED/GREEN microkernel coverage must use deterministic synthetic rank-3 weights plus real row bytes from `tests/fixtures/gguf/q3km_iq_dequant_oracle.json`, nonzero/repeated expert selections, c=1 and `x_rows>1`, and invalid-shape/ID cases. Expected outputs come from the torch-free NumPy dequantizers and BF16-rounded CPU math. Acceptance is the repository kernel gate (KL <= 0.05 and top-1 >= 90%), finite output, fused-vs-unfused numerical equivalence, explicit no-ROCm skips, and GPU1 `rocprofv3 --kernel-trace` evidence for each landed symbol.
- Runtime wiring must resolve the four-axis registry keys rather than add another quant-name branch in engine/model dispatch. Add the public `gguf_ud_q3_k_m` generator registration, standard selected-single/selected-dual-SiLU registry variants, and declarative decode-graph symbol groups/regex coverage. Keep raw IQ allocations raw under both decode-repack modes and prove unsupported/mixed pairs fall back loudly rather than selecting the wrong kernel.
- Real-model gate sequence on GPU1 (RX 7900 XTX/gfx1100): prebuild the new `.so` with the cached compiler-version file; run a one-layer/selected-FFN probe; run resident serial/direct prefill + eager decode; run bulk prefill through the correctness-first `x_rows` path; run public `LLM.generate()` against a pinned llama.cpp token oracle; then compare eager vs decode-graph replay and capture a cached-build kernel trace. No performance row is promoted until finite logits, deterministic output, and the formal KL/top-1 gate pass.
- Only after the direct path is correct, establish its 512-token MoE baseline and implement grouped/compact IQ prefill using the existing hipEngine compact scheduler ABI. The grouped candidate must compare against the direct path on identical selected routes, retain the direct primitives as fallback, and become default only if exact/non-regressive. Any retained result updates `docs/KERNELS.md`, `WORKLOG.md`, `benchmarks/results/`, `benchmarks/README.md`, and `benchmarks/CHANGELOG.md` with the full evidence tuple.
- Pinned math/port references: qwen-kernel `52e240f9c6d91750d0e5e692976cfb67fd9bc603` (`shaders/moe_gateup_iq3.comp`, `moe_gateup_iq3_grouped.comp`, `moe_gateup_iq3_rowtile.comp`, `moe_down_iq4.comp`, `moe_down_iq4_grouped.comp`, `iq_tables.glsl`, `src/quants.h`) and llama.cpp HIP `1ebf790cda38d827559548f67b0469189690cc8c` (`ggml/src/ggml-quants.c`, `ggml/src/ggml-common.h`). Port only the quant math/layout; use hipEngine's gfx1100 wave32 reduction and ABI conventions. The latest `scripts/check_lineage.py --kind kernel --diff stat` report contains only the known nano-vllm-amd drift and does not cover qwen-kernel, so re-pin/check both external commits at implementation start.
- Principal risks: IQ3 grid/sign/subscale bit ordering; IQ4_XS packed scale/nibble ordering; FP16 shader vs BF16 runtime rounding; a fused-only implementation violating fallback invariants; blk.39's IQ4_XS gate/up outlier; direct prefill launch volume; missing public quant registration; graph capture silently omitting new symbols; and accidentally pulling blk.40 Q3_K nextn work into AR scope.
- Explicit deferment: native Q3_K expert GEMV and blk.40 Q4_K down are GGUF-MTP work only. Start them only after a nextn materialization/execution ABI is approved; they do not block base `generate()` and must not be used to expand the current AR kernel task.
