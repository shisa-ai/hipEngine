# Gemma 4 two-phase split accepted: threshold corrected to 1024 keys (+3.0% metric, +10.9% at 4096p)

## Summary

The split is accepted on its corrected slice policy. Final rows, incumbent ->
candidate: **1024p 43.9827 -> 45.3015 tok/s (+3.0%)**, 4096p 28.5889 -> 31.7066
(**+10.9%**), 512p 48.1231 -> 48.0158 (flat), 128p 51.9685 -> 51.9240 (flat). The
policy now splits only from 1024 keys and then grows aggressively, and both halves
of that rule were forced by measurement rather than chosen.

## Changes

- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention.py`: `decode_slices`
  entry threshold raised from 513 to 1024 keys, with the growth above it unchanged
  (doubling while a slice still carries more than 512 keys, capped at 4).
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention.hip`: exported
  `hipengine_gemma4_decode_selection` so a caller can confirm which decode kernel a
  real request took instead of inferring it from timings.
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention.py`: matching
  `decode_selection()` accessor.
- `tests/test_unit_gemma4_attention_routing.py`: the threshold test now pins 1023 ->
  1, 1024 -> 2, 1025 -> 4 and the plateau, with values unrelated to any boundary.
- `docs/campaigns/GEMMA4-26B-A4B-OPTIMIZATION.md` and
  `benchmarks/results/2026-09-26-gemma4-26b-a4b-two-phase-split-accepted.json`: the
  accepted row and the correction.

## Validation

- Campaign verify (`--prompt 1024 --output 128 --samples 3`): **45.3015 tok/s**,
  public wall 10.76 s, path parity True.
- Other primary rows: 512p 48.0158, 128p 51.9240, 4096p 31.7066, all with path
  parity True and no row regressed.
- Campaign guard (`tests/test_unit_gemma4_*.py tests/test_gpu_gemma4_*.py`): pass.
- Gate: kl_max 0.006746 against the 0.05 bar, top-1 1.0 over 1023 rows.
- Intended path confirmed on the public surface: `LLM.generate()` with the
  campaign's 1024-token prompt reports `decode_selection() == 2`.

## What the acceptance rows caught

The first shipped policy split from 513 keys, and the 512p row caught it: 48.12 ->
46.31. A paired interleaved A/B (single 48.0433/47.9830 against split
46.5579/46.5885 tok/s) confirmed a real 3.0% loss, because the split's fixed cost -
a weights round trip through global memory, two extra launches, a combine - is not
paid back at 512 keys. Raising the threshold fixed 512p, but the first version of
that fix also held every slice at 512+ keys, which the primary row itself rejected:
4 slices over keys 1025-1151 measure 45.3015 against 41.7934 with 2. So "when to
split" and "how many slices" are separate questions with opposite answers.

## Next

- Geometry-aware policy: the full geometry at short context is the one losing cell
  (+20% at full/1024, 5 of 30 layers, worth ~0.24 ms per step). The A/B that would
  justify a change was taken under contention, so re-measure it on an idle device
  first.
- The per-launch A/B under contention is not usable: the first pass reported the
  split 2.2x slower at sliding/1024, contradicting the end-to-end row, because a
  peer job held 10.7 GiB of the device. Interleaving the arms is what makes the
  ratios usable at all; absolute values need an idle device.
