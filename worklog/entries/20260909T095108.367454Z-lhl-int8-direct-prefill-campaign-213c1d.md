# Direct INT8 prefill numerics campaign, capacity bound, and the two-tier capacity protocol

## Summary

Close out the recorded preconditions for `HIPENGINE_GGUF_INT8_PREFILL_DIRECT`:
the production numerics campaign (rejected for default-on), the capacity bound
(measured, opt-in lever), and a process fix so capacity questions are never
again answered with multi-hour full-prompt runs.

## Decisions

- **Numerics: REJECTED for default-on.** Teacher-forced vs the BF16 reference
  (mixed-KV suite, 4,096 tokens, `--max-sequence-length 16384` so no
  short-context BF16 mirror exists - the only configuration where the direct
  route is even planned): oracle route 0.003 mean row-KL, direct route 0.215
  (max 6.4, top-1 to 0.71, 9/11 rows fail the 0.05 smoke ceiling). The flash
  and sequential kernels show the identical failure profile (0.215 vs 0.216),
  so the drift is the INT8-read prefill arithmetic itself, not the kernel
  restructure. The BF16 oracle pair is what preserves prefill quality on the
  pure-INT8 route. Gate stays default OFF permanently unless the read
  precision changes; the route is an opt-in capacity lever.
- **Engagement control**: at <= 8,192 max positions the session keeps a BF16
  mirror and the direct env is inert (bit-identical logits both arms). Any
  future gate over this route must set max positions above the mirror
  threshold or it measures nothing - encoded in the new gate script.
- **Capacity: 232,448 tokens** (23.87 GiB tracked peak) is the largest passing
  context measured; 235,520 OOMs. Memory model: 16.45 GiB fixed (16.25
  weights) + 33.6 KiB/token (16 full-attn layers x 2 x 1 KiB int8 KV + scales
  + metadata; verified against the 196,608 census). The model's full 262,144
  context needs a predicted 24.8 GiB and cannot fit on this 24 GB card.
  External Q8_0 engines: 196,608.
- **Process: two-tier capacity protocol** (see `benchmarks/HARNESSES.md`
  "Capacity testing", pointed to from `AGENTS.md` verification tiers): tier 1
  is `scripts/gguf_capacity_probe.py` (~3 min/point, allocation validity -
  per-layer KV/scales/metadata are sized by max_positions at session init, so
  a short prompt proves the same envelope a full prompt does); tier 2 is the
  full-prompt harness point (~1 min per 32K tokens) reserved for
  completion/stability and tok/s-at-depth claims. Never bracket bounds with
  tier 2. This session paid three ~50-90-minute full-prompt points before
  internalizing that the allocation decision they tested is made in the first
  ~3 minutes.

## Changes

- scripts/execution_profile_gguf_int8_direct_prefill_gate.py: floor the
  session max positions above the BF16-mirror threshold (16,384) so the
  candidate arm actually runs the direct route.
- scripts/gguf_capacity_probe.py: new tier-1 capacity probe (route envs set
  by the caller, short prompt, finite logits, tracked peak).
- benchmarks/HARNESSES.md: two-tier capacity-testing protocol section +
  probe row in the harness catalog.
- AGENTS.md: verification-tier row for capacity questions + Key Files
  pointer.
- Artifacts: gate (5 suite evidence JSONs + summary), capacity (tier-1/tier-2
  ladder with per-point tier labels, memory model), two probe JSONs.
- docs/REFACTOR.md: direct-route entry updated to the final state (speed
  fixed, numerics rejected, opt-in capacity lever, chunk row-cap fix).

## Validation

- Gate A/B (GPU0, 4,096 tokens): oracle 0.003 / direct-flash 0.215 /
  direct-sequential 0.216 mean row-KL; the flash kernel is behavior-preserving
  vs sequential at route level.
- Capacity: tier-2 passes 163,840 (21.70 GiB, 51.6 tok/s) and 196,608
  (22.74 GiB, 45.3 tok/s, finite logits); tier-1 probes 229,376 (23.77 GiB)
  and 232,448 (23.87 GiB) pass, 235,520 and 262,144 OOM.
