# Task 45: removed the MTP 1,023 window - a guard whose only cause was that nobody had tested past it

## Summary

The dense MTP adapter's fixed 1,023-token context window is gone, along with its
`HIPENGINE_MTP2_MAX_CONTEXT_TOKENS` override. The adapter is now bounded only by
the target's own `max_sequence_length`, which is allocated capacity rather than
an evidence gap, and the advertised `max_context_tokens` reads that same value so
admission and per-cycle policy cannot disagree.

The window was a guard whose only stated cause was that no measurement had been
taken past the 1,024 attention transition. `docs/EXECUTION-PROFILES.md` section
1.1 requires a restriction to name a concrete cause - an implementation bound,
unsupported semantics, resource pressure, a schedule transition, or an observed
failure - and says plainly that "a guard that exists only because a case was not
tested is an evaluation and cleanup task, not a permanent safety boundary."
Section 2.9 is more specific still: prompt context, output horizon, session
length, and the execution-profile manifest are **not** admission axes, gating on
them "silently disables an already-qualified path," and
`max_sequence_length_not_qualified`, `context_bucket_not_qualified`, and
`output_horizon_not_qualified` were already removed as rejection reasons
elsewhere. This window was a surviving instance of a ruled-out axis.

The catch-22 is the reason to act rather than defer: a guard justified by
"untested" prevents the measurement that would retire it, so it is permanent by
construction unless someone removes it deliberately.

Both of the window's stated causes were resolved before removal. The staged
linear-attention chain is byte-exact above the split threshold on the dense
Q4_K_M path (2026-09-19, `docs/REFACTOR.md`), so `strict_long_rows` no longer
covers it and the multi-row verifier is what runs there. Measured long-context
MTP then reaches 1.42x-1.74x from 1,804 to 12,142 prompt tokens at 0.992-0.996
coverage with greedy output identical to AR, and a 512-token prompt decoded
2,048 tokens across the 1,024 transition at 0.999 coverage with no bucket miss
(`worklog/entries/20260920T113655.797761Z-lhl-t44-long-context-mtp-scales-7918f8.md`).

## Changes

- `hipengine/generation/qwen35_gguf_mtp2.py`
  - Deleted `_MTP2_MAX_CONTEXT_ENV`, `_MTP2_QUALIFIED_CONTEXT_WINDOW`, and
    `_mtp2_context_window()`.
  - The prompt gate in `begin_prompt_streaming` now refuses only a prompt that
    leaves no room for even one generated token inside the target's own
    capacity (`len(prompt_ids) + 1 >= max_sequence_length`). It still reports
    `target_context_k0`, so the remaining refusal stays observable.
  - The advertised `max_context_tokens` is the minimum of the targets'
    `max_sequence_length` instead of the 1,023 sentinel.
- `hipengine/server/api.py` - `_mtp2_context_window_resolution()` now reports
  the policy (`{"policy": "target_capacity", "fixed_cap": None, ...}`) rather
  than an env/resolved pair, and the startup `EFFECTIVE_MTP:` line renders
  `mtp2_context_window=env:none resolved:target_capacity`. The machine-readable
  block stays so a harness can assert which policy is in effect instead of
  inferring it from rates; a non-null `fixed_cap` would mean a guard survived.
- `scripts/bench_env_preflight.py` - `find_context_window()` became
  `find_env_resolution_block(payload, env_name)`, driven by the requested
  variable names instead of one hard-coded knob, so the "export present but the
  resolved value disagrees" check keeps working for future knobs.
- `scripts/gguf_mtp_long_context_gate.py` - dropped the removed variable from its
  tracked-environment provenance list. This script is the explicit runnable
  evaluation path section 1.1 asks for on removal.
- Docs: `docs/REFACTOR.md` entry marked removed with the reasoning and the
  remaining draft-side boundary documented as a permitted per-cycle schedule
  choice; `docs/ENVS.md` row deleted; `benchmarks/README.md`,
  `benchmarks/atlas-agent/README.md`, `benchmarks/HARNESSES.md`, and
  `docs/QWEN38-GFX1151-MTP-SERVING-IMPROVEMENTS.md` updated.
- Tests: the seam tests now assert that a 1,022-token prompt against a
  16,384-token target **reaches the provider** (the old gate refused it with
  `target_context_k0`) and that a prompt filling capacity is still refused;
  `max_context_tokens` is asserted at 4096 for a 4096-token target; the
  capabilities and replay-artifact expectations carry the new policy block; the
  preflight tests cover the retired-export case.

## Validation

- `uv run pytest tests/test_unit_qwen35_gguf_mtp2_seam.py
  tests/test_unit_bench_env_preflight.py tests/test_integration_server_api.py -q`
  - exit 0. Before the test updates the failures were exactly the intended
  behavior change, and one real bug of my own: `min(*(generator))` with a single
  target becomes `min(16384)`, which iterates the int and raises
  `TypeError: 'int' object is not iterable`. The original always had two
  arguments so the trap was invisible. Now `min(generator)`.
- `uv run pytest -q` (reviewed unit tier) - run as `bg-242`; see the commit.
- `uv run --with ruff ruff check --select E4,E7,E9,F` on every changed Python
  file - the only two findings (`E731` in `qwen35_gguf_mtp2.py:1637`, `F841`
  `yellow` in `api.py`) are present in the committed baseline.
- `python3 scripts/sync_benchmark_readme.py --check` - README benchmark blocks
  are synchronized.
- Not yet re-measured end to end: the removal changes which requests reach the
  speculative route, so a same-protocol MTP-vs-AR run at long context with the
  guard gone is the confirming measurement. Task 44's numbers were taken with
  the window raised by hand, which is now the default behavior.
