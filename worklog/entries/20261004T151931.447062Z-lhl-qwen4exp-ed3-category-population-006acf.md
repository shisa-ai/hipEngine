# ED-3 category coverage: the population is category-dependent at 12.6%, and the synthetic probe is a 45% outlier against every category

## Summary

Iteration 151 measured the natural `code-p4096` population at 385.48 of 512 (75.3%) against the
historical synthetic probe's 202.96 (39.6%) and named the cheapest completion: the same capture
on the other three categories. Done, and the answer splits in two.

**Every arm below is at the identical shape — 1,024 tokens x top-10 = 10,240 assignments per
layer — so all five are directly comparable:**

| arm | active of 512 | share | range across layers | vs synthetic |
| --- | ---: | ---: | ---: | ---: |
| synthetic `4000..5023` | 202.96 | 39.6% | — | — |
| `code-p1024` | 385.48 | 75.3% | 304–444 | +89.9% |
| `general_en-p1024` | 359.10 | 70.1% | 268–412 | +76.9% |
| **`general_ja-p1024`** | **341.54** | **66.7%** | 210–402 | +68.3% |
| `mixed_ja_en-p1024` | 387.92 | 75.8% | 279–444 | +91.1% |
| **natural mean** | **368.51** | **72.0%** | | |

**1. The synthetic input is an outlier against every category, not just code.** The 39.6%
regime appears in no natural prompt measured. The 1.9x error iteration 151 found for code is
1.7x–1.9x for the other three.

**2. The population IS category-dependent**, which fires this iteration's stated falsification
branch. **`general_ja` — the category this campaign's task gates treat as the sensitive one —
is the LOWEST at 341.54 (66.7%)**, 46.4 experts below `mixed_ja_en`'s 387.92. The spread is
**12.6% of the natural mean**. So the correct model is a per-category band, not one number:
**~368 of 512 (72%) instead of 203, with `general_ja` ~7% below that mean.**

**Hypothesis outcome, stated against what was predicted:** I predicted all four natural
categories would land in a 70–85% band and that the population would be category-invariant.
The band was close but slightly low (66.7–75.8%), so the first half holds in regime terms; the
second half is **refuted** — `general_ja` is materially below the others, and the row's own
condition ("especially `general_ja`... then the population IS category-dependent") is met.

## Changes

No engine, kernel, dispatch or default change. Measurement unit; nothing to keep or revert.

The practical correction the campaign should carry: **the MoE population model is ~368 of 512
(72%), not 203 (39.6%)**, and the MoE is 25.3% of the prefill. As in iteration 151, the
traffic consequence is an **inference, not a measurement**: at 72% of experts active the
expert-weight traffic behind the selected MoE kernels is close to the full matrix, so a
selected/sparse route's headroom over a dense one is far smaller than the 40% model implied.
The census times remain measured and unaffected.

**The per-layer ranges are wide (210–444 across categories, and 354–493 at 4,096 tokens), so
any tuning that depends on the per-layer population rather than the mean must read the
per-layer table**, which is in `populations.json` under `category_arms.per_layer`.

## Validation

| | |
| --- | --- |
| Harness | `uv run python scripts/qwen4exp_profile_gap.py --mode prefill --moe-telemetry` |
| Cases | `code-p1024` (from the p4096 capture's first two chunks), `general_en-p1024`, `general_ja-p1024`, `mixed_ja_en-p1024` |
| Shape | 1,024 tokens x top-10 = 10,240 assignments per layer, identical to the synthetic probe |
| Profile / chunk | production, chunk 512 |
| Interpreter | `uv run`, not `python3` (this loop's iteration 149 tree-provenance finding) |

Four categories measured, four captures, three of them new in this iteration. The `code-p1024`
arm reuses iteration 151's `code-p4096` capture restricted to its first two chunks rather than
re-running, and its 385.48 reproduces that iteration's figure exactly.

**Limits.** Counts, not throughput measurements. One model, one quant, one host (gfx1151, not
the gfx1100 default hardware). One prompt family per category — the fixture builds each
category from two to four source prompts, so this is a category sample, not the category
distribution. The synthetic arm is the recovered fixture, not a re-run. The p4096 arms
(iteration 151) show the population keeps rising with token count (75.3% -> 87.2% for code), so
these 1,024-token figures are a lower bound for long prompts.
