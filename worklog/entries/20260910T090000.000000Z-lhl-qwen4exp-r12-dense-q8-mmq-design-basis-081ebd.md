# R12 step 1: dense Q8 MMQ design basis (current owners, geometries, rates, external mechanism)

## Summary

R12 step 1 establishes the design basis for closing the dense Q8 prefill gap
**before** any kernel is written. Every dense leg currently runs at 7-11 int8
TF/s while the 8060S dp4a ceiling is several times higher, so the gap is
tiling/occupancy/staging rather than the arithmetic family. The R2e ledger puts
the linear total at 3.47s versus old Vulkan 1.02s (excess +2.45s), the largest
single prefill gap after MoE.

The sharpest clue: `attn_q` (10.6 TF/s, N=6144) is 1.5x faster than `attn_qkv`
(7.0 TF/s, N=10240) at the same K=2560, so the wide-N leg underperforms. External
attribution on the halo box (`5f851647f`, `302ec43e6`) shows the reference mixes
`mul_mat_q<type,128>` MMQ with a rocBLAS WMMA GEMM per dense leg, shares one
`quantize_mmq_q8_1` activation plane, and folds hyper-connection combine/mix
tails into the GEMM consumers via fused `hc_*` epilogues.

## Changes

- No code change: this entry records the measured design basis and the
  pre-declared experiment ladder, per the campaign rule that a tuning ladder does
  not start without target rates.
- Basis recorded: the per-op owner/geometry/rate table for the dense Q8 legs at
  code-p4096 (R2e profile, 4x1024-row chunks), the `attn_q` versus `attn_qkv`
  asymmetry, and the halo-box external mechanism.

## Key observation

Every dense leg runs at 7-11 int8 TF/s. The dp4a ceiling on the 8060S
is several times that, so the gap is tiling/occupancy/staging, not the
arithmetic family. attn_q (10.6 TF/s, N=6144) is 1.5x faster than
attn_qkv (7.0, N=10240) at the SAME K - the wide-N leg underperforms,
pointing at tile-shape/occupancy interaction with N, or activation-plane
reuse across the K dimension.

## External mechanism (halo-box 5f851647f HIP attribution, 302ec43e6)

- Dense legs: `mul_mat_q<type,128>` MMQ (7825+4885+640 ms across the

  `Cijk_Alik_Bljk_SB_MT32x32x8` WMMA GEMM (2772 ms) - they mix MMQ and

- Activation planes: `quantize_mmq_q8_1` (1100 ms over 12 cases).

  12 cases) fold the hyper-connection combine/mix elementwise tails into
  the GEMM consumers.

## Validation

- Owner/rate table measured in-tree at code-p4096 (R2e profile, 4x1024-row
  chunks): linear.attn_qkv 1.079s, ssm_out 0.626s, attn_q 0.424s, attn_gate
  0.587s; repair 2.9-3.1ms/op (noise, not a lever); quantize planes 3-25ms/op.
- Rates derived from those measurements: 6.96-10.63 int8 TF/s across the
  MMQ-family legs, 7.69 for `attn_gate` (`q8_0_iu8_wmma_prefill`).
- The external mechanism is an attribution capture from a **different machine**
  (halo box, `5f851647f` / `302ec43e6`) and is used as a mechanism reference, not
  as a same-host baseline.
- Stated limit: the external attribution is whole-run, so per-op external rates at
  these exact geometries are not yet established - deriving them is ladder step 1.

## Experiment ladder (before any kernel code)

1. **Window the external trace per p4096 case** (the current attribution
   is whole-run): attribute the external mul_mat_q/GEMM dispatches to
   requests via timestamps and grid sizes; derive their per-op ms at
   the SAME geometries. This gives the target rates - do not start a
   tuning ladder without them (campaign rule).
2. **Microbench the current MMQ at these exact geometries** (M=1024
   chunks, K=2560/6144, N=10240/6144/2560) against tile variants:
   64/128/256 N-tiles, d4x2 vs d4x3 planes, register-staged next-K
   loads. The attn_q-vs-attn_qkv asymmetry is the first thing to
   explain.
3. **Activation-pack reuse**: attn_qkv, attn_q (and the QSA
   projections) consume the same 2560-wide normalized hidden - one
   shared Q8_1 plane per chunk instead of per-op quantize passes.
   Confirm the consumers' exact input sets from the runner dataflow.
4. **BLAS-GEMM leg trial**: measure rocBLAS WMMA GEMM at attn_qkv
   geometry as a candidate owner for the wide-N leg (the external mix).
5. RED/oracle per the campaign kernel standard: CPU reference floor +
   expected kernel trace + bit-exactness target for any
   precision-preserving variant (dp4a int path is exact-reproducible;
   keep the d4x3 residual-correct semantics initially).

Precision initially preserved (T0 exact); any arithmetic change
(WMMA/BLAS dequant paths) routes through the production gates.
