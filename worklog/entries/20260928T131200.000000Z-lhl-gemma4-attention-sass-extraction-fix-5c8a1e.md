# the SASS counts were whole-file: the strict kernel is 1520 instructions and its prologue is 45 percent of them

**This entry corrects the instruction counts in
`20260928T121300.000000Z-lhl-gemma4-attention-scalar-bound-7f2b1a.md` and
`20260928T130200.000000Z-lhl-gemma4-attention-per-line-attribution-3b7e9d.md`.**

## Summary

Both entries attributed SASS to a kernel by splitting the `.s` output on a line
containing `define`. **`clang -S` emits assembly, which has no `define` lines**, so
the split never matched and the "kernel body" was the entire file. Every absolute
instruction count in those two entries is a whole-file total across the 22 kernels
`gemma4_attention.hip` instantiates.

The real boundaries are the label lines `_Z…: ; @_Z…`, one per kernel. Corrected:

| kernel | instructions |
| --- | ---: |
| `gemma4_attention_prefill_kernel<unsigned short>` (strict bf16, production) | **1,520** |
| `gemma4_attention_prefill_kernel<float>` (strict f32) | 1,498 |
| `gemma4_attention_prefill_tiled_kernel<…>` x4 | 1,189-1,272 |
| `gemma4_attention_decode_class_kernel<…>` x4 | 1,814-1,878 |
| `gemma4_attention_decode_dimension_kernel<…>` x2 | 1,004-1,027 |
| `gemma4_attention_decode_kernel<…>` x10 | 434-1,479 |
| whole file | 32,630 |

The 32,630 and 6,811 figures quoted in the scalar-bound entry are the *file* totals,
and the "24 percent of the body" in the per-line entry is the prologue's share of the
file, diluted by ten decode kernels that do not contain it.

### The corrected per-line picture

Strict bf16 prefill kernel, 1,520 instructions, 410 VALU:

| line | instrs | VALU | source |
| ---: | ---: | ---: | --- |
| 178 | 194 | 140 | `return lane + ((from - lane + stride - 1) / stride) * stride;` |

| 204 | 166 | 7 | `const int64_t kv_head = head / kv_groups;` |
| 201 | 163 | 7 | `const int64_t token = static_cast<int64_t>(blockIdx.x) / num_heads;` |
| 282 | 53 | 12 | the fallback key loop |
| 265 | 51 | 30 | the warp key loop |
| 343 | 47 | 10 | pass 3's `d` loop |
| 207 | 27 | 12 | the `q_s` load loop |
| 149 | 22 | 10 | the shuffle chain |

**The prologue is 689 of 1,520 instructions -- 45 percent of the body, not 24** -- and
the four hot loops together are about 170. The earlier entry's "line 431 is the pass-1
loop body at 400 instructions" was the *tiled* kernel's phase-1 loop, because the
line-number attribution was over a file-wide instruction stream and line 431 belongs
to a different kernel's source region.

### What survives

**The measurement that decided the previous unit stands**, because it compared two
builds with the same extraction: 1807.9 ms with the 32-bit prologue against 1807.2 ms
without it. A same-metric comparison is unaffected by what the metric is called, and
the conclusion -- the prologue is not on the critical path -- is now *better*
supported: at 45 percent of the body, halving it and moving nothing is a stronger
statement than at 24 percent.

**The dynamic picture is consistent.** The prologue runs once per block; the warp key
loop runs once per eight keys. At 512 tokens a block walks about 256 keys, so the loop
runs 32 times against one prologue, and the loop's 51 instructions per iteration beat
the prologue's 689 for a block that does any work at all. A static majority that is a
dynamic minority is exactly what the measurement showed.

**The scalar-bound conclusion is unaffected in substance.** `SQ_INSTS_SALU` is a
runtime counter, not a static extraction, so the 5.576e9 SALU and its 0.74 ratio to
VALU in the prefill are correct as measured. What changes is only the explanation of
where the static instructions sit.
