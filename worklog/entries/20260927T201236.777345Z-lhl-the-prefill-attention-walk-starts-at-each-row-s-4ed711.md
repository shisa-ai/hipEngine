# The prefill attention walk starts at each row's own first kept key

## Summary

The prefill attention kernel now starts each row's key walk at that row's own
first kept column instead of at column 0. This is the per-row lever the previous
unit identified and did not attempt.

A sliding row's mask is zero for every column below
`max(0, (start - key_begin) + row - window + 1)`, so the leading columns of a
multi-row block are dead weight that the block-level bound cannot reach: the
block bound is the *first* row's window, and rows later in the chunk have later
windows. The kernel now takes the window and the block's start in the mask's
column frame and computes that bound per row.

All three passes had to narrow together. Pass 1 writes `logits_s[j]` for every
column it visits, so if only pass 1 skipped its leading tiles, passes 2 and 3
would read uninitialised shared memory below the bound. Pass 2's lane-to-column
partition is preserved rather than merely shortened, because the terms a lane
drops are `expf(-inf) == 0` and dropping them must not reorder the survivors.

The kernel may only do this when the mask is zero below the bound. A sliding
causal mask is, by construction; an arbitrary caller-supplied mask need not be.
So `window` defaults to 0 -- meaning no promise and a walk from column 0 -- and
the runtime passes the same geometry value the mask was built from, so the two
cannot drift apart. This mirrors `key_begin`, which carries the same contract.

## The change is bit-exact, and it was verified rather than argued

Dropping zero terms leaves the surviving terms in their original lane and order,
so the reduction is unchanged rather than close. The real artifact's prefill
logits were hashed at four lengths with the change and with `window=0`, which is
exactly the pre-change code path: `first_kept` is 0 and every walk starts at the
lane offset the original loop used.

| length | digest (both arms) |
| --- | --- |
| 512 | `4f4e617d38028d43aa46f07dd03efcba663359f46a1d813c92cccc3d93a5bf8b` |
| 1024 | `eac1fa31124fe7071a3444e8283353ea80cf832cc407073056a3e5451f2f5744` |
| 2048 | `faee8a68dcd296232db496e781950cd11701c38b2c5c29a6f39c3b79f0cd1dae` |
| 4096 | `b12f5202818ba8728c1ca8e83e9278833e1f0b209e8b07be695e9009dad746aa` |

Identical in both arms at every length, including top-1 and the logit sum. 512
and 1024 are provable no-ops -- a row skips nothing until `start - key_begin`
reaches the window -- so 2048 and 4096 are the lengths that exercise the skip.

## The measurement

| prompt | window off | window on | delta |
| --- | --- | --- | --- |
| 512 | 270.7 tok/s | 270.4 tok/s | -0.10 percent |
| 2048 | 222.5 tok/s | 225.5 tok/s | +1.35 percent |
| 4096 | 197.4 tok/s | 201.0 tok/s | +1.78 percent |

`rocprofv3` isolates the kernel: at 2048 `gemma4_attention_prefill` runs 3343.2 ms
per forward against 3497.7 ms, **4.4 percent faster**, and its share of prefill
falls from 28.5 to 27.6 percent. The end-to-end gain is smaller because attention
is only 28 percent of prefill. The effect grows with length, which is the
expected shape: a row only starts skipping once it is further than `window` into
the block.

## Measuring one arm then the other gave a false regression

The first attempt at this measurement ran the control arm and then the changed
arm and read **-1.0 percent at 512**, which is a provable no-op and must read
zero. Reversing the arm order reversed the sign: the arm run *first* was faster
in both orderings. Run-order drift on this GPU is about the size of the effect.

The fix was to interleave the arms inside one process, forcing the control by
wrapping the layer forward with `window=0` so both arms run the same compiled
kernel and alternate forward by forward. The interleaved method reads -0.10
percent at 512, which is what a correct measurement of a no-op must read. That
control is what makes the 2048 and 4096 rows trustworthy; their sample ranges do
not overlap between arms.

This is recorded because the first number was wrong in a way that looked like a
real cost, and because the same method will be needed for the next few-percent
change.

## Changes

- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention.hip`: the kernel takes
  `window` and `row_offset`, computes `first_kept` per row with
  `gemma4_attn_first_kept`, and narrows all three passes.
  `gemma4_attn_stride_first` restores a lane's position in the stride partition;
  callers guard it with `lane < from` so the division stays off the hot path.
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention.py`: both entry points
  take `window`/`row_offset`. `_ARGTYPES_PREFILL` and `_ARGTYPES_DECODE` now
  derive from a shared `_ARGTYPES_COMMON`, because their tails differ and the
  decode tail is not a prefix extension of the prefill one -- appending to
  `_ARGTYPES_PREFILL` would have silently corrupted the decode signature.
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_layer.py`: `window` is a sibling
  of `key_begin` on the layer forward, documented as carrying the same contract.
  `row_offset` is derived from `kv.write_offset` and `key_begin`.
- `hipengine/runtime/gemma4.py`: passes the window from the same geometry the
  mask was built from.
- `tests/test_unit_gemma4_sliding_read_range.py`: `test_every_column_below_the_per_row_bound_is_masked`.
- `tests/test_gpu_gemma4_attention_geometry.py`: `test_a_narrowed_prefill_walk_is_bit_identical_to_a_full_walk`.

## Validation

- `tests/test_unit_gemma4_sliding_read_range.py` pins the contract the kernel
  relies on: for every (window, start, rows) shape the bound must be a zero
  prefix of the mask *and* tight. A bound that lags the mask would silently give
  back the win; a bound that leads it would drop a kept key.
- `tests/test_gpu_gemma4_attention_geometry.py::test_a_narrowed_prefill_walk_is_bit_identical_to_a_full_walk`
  runs the kernel both ways and requires bit-identical output, over head_dim 6
  (block-sum path) and 256 (warp-per-key path) and window 1 and 4. Moving the
  bound one column too far fails all four parameterisations, so the test is not
  vacuous.
- `pytest -k gemma4`: 400+ tests, exit 0.
- `tests/test_unit_gemma4_runner.py` keeps its pre-existing
  `test_incremental_decode_matches_a_dense_prefill` failure (max abs diff
  4.417). It is present before this change and recorded in
  `benchmarks/results/2026-09-27-gemma4-gfx1151-pack8-expert-route-measured.json`.
  It is a decode-versus-prefill divergence, not a read-range one, and it
  regressed mid-campaign: 2026-09-23 entries record this test passing.
- No promotion gate applies: the change is bit-exact, so it is not a
  changed-arithmetic default and has no execution profile to promote.

## Next

Pass 3 recomputes `expf(logits_s[j] - row_max)` per (element, key) and loads V
for every kept key; only the skipped columns are saved. The decode kernel already
stores the weight over its logit and reads it back, which the prefill kernel does
not do. That is the remaining structural difference between the two.

The arithmetic bounds what a read-range change can ever deliver here: at 2048 the
per-row bound removes 11.1 percent of the walk (2096640 keys against 2358272)
and bought 4.4 percent of the kernel, so the walk is about 40 percent of
attention's cost. Attention is 28 percent of prefill, so **no read-range change
alone can exceed roughly 12 percent of prefill**. Prefill speed has to come from
the weight-bound routes, which are 61 percent of a 512-token prefill.

`benchmarks/results/2026-09-28-gemma4-prefill-per-row-read-range.json` carries
the full evidence, including the run-order drift finding.
