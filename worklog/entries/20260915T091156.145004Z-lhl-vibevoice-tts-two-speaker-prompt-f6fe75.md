# VibeVoice-TTS multi-voice prompt construction and the two-speaker chain gap

## Summary

The session can now build the two-speaker prompt, and the batch-max reference
padding the fork depends on is implemented and pinned by a test. The
two-speaker **greedy chain is not exact** and the gap is recorded as a strict
xfail with its cause localized: the 208-frame voice's connected rows are 0.206
off the oracle, which is what pushes the first span past its end.

## Why the padding matters

The fork batches every voice of a request into one `forward_speech_features`
call (`vibevoice/modular/modeling_vibevoice.py`, `speech_tensors.unsqueeze(1)`),
so `speech_tensors` is zero padded to the longest reference in the batch and
`speech_masks` selects each voice's real frames afterwards. `VibeVoiceProcessor.
_pad_speech` uses a plain `max(s.shape[0] for s in speech_inputs)` with no frame
rounding.

That pad is arithmetic, not storage: the acoustic encoder is not translation
invariant at its tail, so a voice encoded outside the batch disagrees on its
final frame. Measured on the frozen fixture, voice 0 (70 frames) against the
oracle's connected rows:

| Voice 0 encoded as | Max relative error |
| --- | ---: |
| batch of one, its natural 222480 samples | 0.233 |
| inside the batch, padded to 665600 samples | 0.039 |

So a per-voice encode cannot be substituted, and the pad cannot be dropped.

## Changes

- `hipengine/runtime/vibevoice_encoder.py`: new `REFERENCE_HOP_SAMPLES` and
  `reference_frame_count(samples)`, the `ceil(samples / 3200)` frame count the
  non-streaming pass emits. `voice_prompt_rows_multi` needs each voice's real
  frame count to slice the batch-padded encode without encoding twice.
- `hipengine/runtime/vibevoice_tts_session.py`: new
  `voice_prompt_rows_multi(ref_pcms, ...)` returns each voice's sampled latents
  and the concatenation of the per-voice connected rows in mask order.
  `voice_prompt_rows` delegates to it with one element, so the one-voice path is
  bit-identical and the single-speaker RNG stream is unchanged (the draw is
  still `(1, frames, 64)` then `(1,)`). The session now draws one noise tensor
  and one scale vector per batch, matching the fork's single `torch.randn` over
  `speech_mode` rather than one draw per voice.
- `tests/test_live_vibevoice_tts_session_gpu.py`: four new tests (below).
- `docs/MODEL-VIBEVOICE-TTS.md`: new "Multi-speaker reference padding" section
  with the padding measurement and the current two-speaker status.

## Measured

Two-speaker prompt construction, injected recorded VAE draws, no RNG:

| Quantity | Value |
| --- | ---: |
| Frame counts | 70 + 208 = 278 rows |
| Voice 0 sampled latents, max relative | 0.036 |
| Voice 1 sampled latents, max relative | 0.072 |
| Connected rows, median row | 0.0067 |
| Connected rows, worst row (voice 1) | 0.206 |
| Final-position prefill logits, relative | 0.012, argmax 151654 both |

For scale, the frozen single-speaker voice has the same 0.036 latent error, so
voice 0 is at the encoder's normal bf16 noise floor and voice 1 is 2x worse on a
3x longer reference.

## The chain gap, localized

The 59-token two-speaker chain: the first 31 tokens are exact, and token 32 (the
first span's end) is the first divergence. The oracle emits `speech_end`; this
session emits another `speech_diffusion`, and the top-2 gap there is 9 logits
(`speech_diffusion` 24.41 vs `speech_end` 15.45), so it is not a near tie. The
session then runs 59 diffusion calls where the oracle recorded 55.

The cause is the prompt rows, not the LM and not the diffusion head:

- The diffusion head, fed the oracle's own `condition`, `neg_condition` and
  `initial_noise`, reproduces the oracle's `call0` latent to 0.036 and `call1` to
  0.022, both before and after a full prompt encode and prefill on the same
  session. So the head has no state or scratch contamination from the longer
  prompt.
- The LM, given the oracle's own `prefill_connected`, reproduces the oracle's
  prefill hidden to 0.05 across the single-speaker prompt, which is the existing
  `test_prefill_trace_matches_fixture` gate.
- Our connected rows are the input that is off, at 0.206 for voice 1. The
  connector is exact on the oracle's own `features_scaled` (0.0019), so the
  error is the encoder's 0.072 latent drift on the 208-frame voice amplified
  about 10x in relative terms by the connector.
- Feeding our prefill hidden as the diffusion condition gives 3.57 latent
  error, while feeding the oracle's condition plus N(0, 0.33) noise gives 0.33;
  the sensitivity is real but modest, so the divergence is compounding over the
  span rather than one bad frame.

## Validation

- `uv run pytest tests/test_live_vibevoice_tts_session_gpu.py
  tests/test_gpu_vibevoice_encoder_kernels.py` — 18 passed, 1 xfailed.
- New tests: `test_reference_frame_count_matches_encoder` (formula vs encoder on
  three frozen voices), `test_voice_prompt_rows_multi_single_voice_is_unchanged`
  (bit-identical one-voice path), `test_two_speaker_prompt_rows_match_reference`
  (frame counts, 278-row shape, per-voice latents and rows, and the
  padded-vs-unpadded 0.039 vs 0.233 contrast), and
  `test_two_speaker_prefill_logits_match_reference`.
- `test_two_speaker_greedy_chain_matches_torch` is `xfail(strict=True)` and
  fails with `assert 59 == 55`, so it will fail loudly rather than silently pass
  once the chain is exact.
- `uv run pytest tests/ -k vibevoice` — 104 passed, 3 skipped, 3 failed. All
  three failures are pre-existing and unrelated: `test_diffusion_replay_matches
  _fixture_chain[two]` is the known two-speaker diffusion parity gap, and the
  two `test_unit_vibevoice_wer_qualification.py` driver tests fail identically
  with these source changes stashed.

## Next

- The two-speaker chain needs the encoder's per-row accuracy on a 208-frame
  reference reduced to the single-speaker voice's level. The connector amplifies
  per-row input error roughly 10x in relative terms, so the useful target is the
  encoder's `encode0_mean`, not the connector.
- `reference_frame_count` is only exercised against the encoder on the frozen
  voices; a reference whose length is an exact hop multiple and one that is not
  are both covered (665600 and 222480).
- Still open from the reviewer's list: request `reset()` for session reuse, and
  the `length` / `eos` completion status the API contract table requires.
- The single-speaker chain remains the only exact end-to-end path.
