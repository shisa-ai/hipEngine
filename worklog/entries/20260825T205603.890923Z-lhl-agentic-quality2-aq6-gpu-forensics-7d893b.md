# Diagnose AQ6 previous-boot GPU hang

## Summary

Previous-boot journal and coredump evidence localize the failed AQ6 attempt before
model prefill or constrained decoding. The first request was still reserving its
scheduler-owned KV allocation and blocked in a synchronous **64-byte
host-to-device copy** of the resident session's local block table. The request
had 1,735 prompt positions and reserved seven KV pages, but the block-table copy
size was the normal fixed 16 × int32 layout.

The first serious AMDGPU event in the entire previous boot was a DMCUB/display
Panel Self Refresh failure at 05:00:23.220 JST. SMU stopped responding ten
seconds later. At 05:01:26 the driver could not suspend/remove MES queues and
began a Source-3 GPU reset; ROCr's hardware-exception thread then deliberately
aborted the server. This is a whole-APU display/power/queue failure, not evidence
of bad model arithmetic or a nested-schema generation kernel.

The evidence does not identify a single firmware or kernel root cause. The
first DMCUB/PSR warning and subsequent SMU collapse make a display-power/firmware
transition the leading boundary. The blocked `hipMemcpy` also makes the default
SDMA copy route a controlled diagnostic hypothesis, not a proven fix.

### Server coredump

- timestamp: 2026-08-26 05:01:26 JST;

```text

                  nbytes=64, kind=HOST_TO_DEVICE)
```

builds a 16-entry int32 local block table, then performs this copy. Request
prefill occurs only after successful admission, so no request model kernel or
JSON-schema sampling step had run.

## Validation

### Interpretation

- **Ruled out by the boundary:** OOM, output parser/scorer, constrained JSON
  decoding, nested tool execution, and request prefill/decode arithmetic.
- **Unlikely:** stale JIT artifact. Cached startup model warmup completed, while
  the failed request had not dispatched its prefill kernels.
- **Leading hypothesis:** integrated-display DMCUB/PSR or SMU power-state failure
  during the transition into the request's first device operation.
- **Secondary testable hypothesis:** gfx1151's default SDMA route contributed to
  the blocked H2D operation. AMD's ROCR documentation confirms
  `HSA_ENABLE_SDMA=0` disables DMA engines for H2D/D2H/D2D copies, but it does
  not by itself prove this incident is an SDMA bug. An unofficial Strix Halo
  field report recommends the setting for hangs; treat that only as a lead.
