# Gemma 4 Q4_K expert prefill: staged activations and hoisted weight metadata

## Summary

Fresh attribution on the post-weight-reuse tree contradicted the assumption the
last two units were built on. With both expert projections reading each expert's
weights once per prefill block, the grouped kernels were still **68% of prefill
kernel time** (45.1% Q4_K gate/up, 23.0% Q5_1 down) and achieved only ~4 GB/s of
weight bandwidth, so the cost was never the weight read.

Isolating the parts of the shipped grouped kernel at the artifact's own geometry
(in 2816, out 1408, 128 experts, 4096 compact rows) put 30 ms of 49 ms in the
Q4_K dequant and 21 ms in the activation-side FMA, with 3.6 ms in staging. Both
were fetch problems, not arithmetic ones: the kernel re-read every activation
element from L2 once per output column, and it re-extracted a Q4_K scale/min pair
(plus two fp16 conversions) for every weight element it touched.

Rewriting the fetch strategy - the block's expert rows staged in shared memory
so they are read once per eight output columns, and each column's `d * scale` /
`dmin * min` pairs hoisted into shared per 32-element sub-block - is **2.07x** on
that kernel at the same geometry (73.68 ms -> 35.57 ms) with **zero differing
bf16 outputs**, because the per-thread k-partition and the reduction are
untouched. Paired in one session on the full model, that is **5.548 s -> 4.200 s
of 512-token prefill (92.28 -> 121.90 tok/s, 1.321x)**, public wall 11.629 ->
10.240 s, decode and the generated tokens unchanged, and the teacher-forced gate
reports KL exactly 0.0 at every statistic.

## Changes

- `hipengine/kernels/hip_gfx1100/quant/gguf_q4_k_gemv.hip` (+199):
  `gguf_q4_k_selected_grouped_prefill_staged_kernel<ROW_BATCH=8, OUT_TILE=8,
  K_TILE=256>` and its launcher. The grid covers eight output columns per block;
  `out_features` need not be a multiple of eight, since the tail block guards the
  columns past the end.
- `hipengine/kernels/hip_gfx1100/quant/gguf_q4_k_gemv.py` (+67): wrapper and
  registration under `(hip_gfx1100, moe_linear, gguf_q4_k,
  selected_grouped_prefill_staged_out8_bf16_bf16_out)`.
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_experts.py`: the grouped-prefill
  route now walks an ordered preference list instead of resolving one variant
  name, so a quant that registers only a later variant still runs it.
- `tests/test_unit_gemma4_expert_route.py`: the bit-exactness test asserts every
  grouped variant the quant registers, not only the preferred one, and two tests
  cover the preference order and the fall-through.

Two things made this cheap to accept. The metadata hoist is an exact rewrite:
`d * scale * q - dmin * min` becomes `(d*scale) * q - (dmin*min)` with the same
two products in the same order, so it cannot round differently. And staging the
activation rows does not change which columns a thread owns - it still owns
`k = tid, tid + 128, ...` in ascending order - so the per-thread partials and the
32-lane shfl plus wave-total reduction are the shipped ones.

## Validation

- Kernel-level micro-harness (no model load, artifact geometry, three timed
  launches each): shipped grouped 73.68 ms, staged (rb8/out8/k256) 35.57 ms,
  bit-diff 0 of 5,767,168 outputs. Rejected by measurement: rb8/out4 48.95,
  rb8/out16 41.50, rb16/out8 46.26, rb16/out4 67.70, rb32/out4 155.93 ms
  (register spills).
- `pytest tests/test_unit_gemma4_expert_route.py -q`: 31 passed, including ten
  bit-exactness cases across both quants and both grouped variants.
- `scripts/gemma4_teacher_forced_gate.py gate` against the frozen strict
  baseline, 1023 teacher-forced rows at keys 1025-2047 with the decode split
  engaged (30690 split launches), `chain_sha256` matching the baseline:
  `passed true`, `failed []`, kl_mean/p95/p99/max all exactly 0.0, top-1 rate
  1.0 with zero flips.
- `scripts/gemma4_campaign_bench.py --prompt 512 --output 128 --samples 3
  --warmup 1 --context 8192`, paired with the three changed files restored from
  `HEAD` for the incumbent arm (sha256 verified before and after the swap):
  incumbent prefill 5.534/5.546/5.566 s, candidate 4.177/4.201/4.223 s; decode
  21.10 against 21.14 tok/s; public wall 11.629 -> 10.240 s; identical greedy
  ids and `public_path_parity` true in both arms.
