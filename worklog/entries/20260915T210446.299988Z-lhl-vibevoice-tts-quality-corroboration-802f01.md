# Fresh ten-seed runs independently reproduce both VibeVoice-TTS quality claims (58/60 accepted, 57/60 rejected) exactly

## Summary

Two ten-seed generated-audio quality runs finished and they reproduce the two quality
claims the completion audit rests on, **exactly** -- same pass counts, same failing
(seed, request) pairs, same WER. This upgrades those claims from "recorded in an
artifact" to "reproduced by a fresh run".

| Arm | Result | Failures |
| --- | --- | --- |
| BM=64 low-row WMMA (**accepted**) | **58/60** | seed 20260918 `two-long`, seed 20260919 `two-2turn` |
| dual GEMV `threads=64` (**rejected**) | **57/60** | seed 20260917 `single-numbers`, seed 20260918 `two-long`, seed 20260919 `two-2turn` |

The rejected arm's extra failure is `single-numbers` at seed 20260917 with
**WER 0.1667**, duration ratio 0.667 -- matching the recorded rejection exactly.

## Changes

No code change. One immutable worklog entry. Raw run outputs were left under `/tmp`
(not committed, per the never-commit-raw-benchmark-logs rule).

## Validation

### Command

```
uv run --with jiwer --with transformers python scripts/vibevoice_tts_quality_suite.py
```

as recorded in each artifact's own `command` field. Both runs: 10 seeds, 6 requests
per seed, **60 request-runs** each; `measurement_basis:
unassisted-generated-audio-quality`; `injected: nothing (own VAE draw, own diffusion
noise, own negative LM)`; host `zbook` / Radeon 8060S (gfx1151), which is the lane
`docs/MODEL-VIBEVOICE-TTS.md` declares.

### What this corroborates

1. **The accepted BM=64 semantic tile is 58/60** with failures `two-2turn`
   (seed 20260919) and `two-long` (seed 20260918) -- the same two (seed, request)
   pairs named in the milestone 5 closure I added to the contract, and the same
   `two-2turn` WER 0.1176 that closure cites.
2. **The `threads=64` LM decode rejection is real and is a quality cost**, not a
   conservative default: 58/60 -> 57/60 with a new `single-numbers` failure at
   WER 0.1667. This is the evidence behind the contract's "`chain_exact` is not a
   sufficient gate" section and behind `quality-threads64-rejected.json`.

Both arms ran the same suite, same host, same request set, same gates
(`wer_max 0.1`, `duration_ratio_range`, `max_repeated_4grams 0`, and the
`voice_attribution` gate). The only difference between them is the dispatch under
test, so the 1-request delta is attributable to it rather than to protocol drift.

### Why it matters for the audit

The completion audit cited 58/60 and the `threads=64` rejection from recorded
artifacts. Reproducing both from fresh runs means the two clauses that depend on
generated-audio quality -- "matches our oracle" and the justification for keeping the
LM decode at the 256 default -- are confirmed rather than inherited. It also means the
`threads=64` rejection would survive a re-litigation, so no future session should
re-open it on the theory that the recorded number was stale.
