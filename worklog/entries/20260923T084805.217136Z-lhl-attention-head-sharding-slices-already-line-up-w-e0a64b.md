# Attention head sharding: the manifest slices already line up with a sharded config

## Summary

Design feasibility for the unit the previous entry sized at 11.7%. The intended
implementation gives each rank a *sharded attention geometry* (halved head counts
and GDN group/inner widths) plus the rank's own slice of each attention tensor, so
the existing full-attention and GDN prefill helpers compute sharded attention
without a parallel implementation. This checkpoint verifies that the two halves of
that plan agree, on the real artifact, before any code is written.

They agree exactly. `build_shard_manifest` already produces the attention slices,
and every derived width the runner computes from a halved config matches the
corresponding slice's local shape.

## Changes

No code changed. This entry records the verified mapping; the plan doc's Packet 3
head-sharding checklist item now carries it.

## Validation

Read from the real artifact, no device work:

```
python3 - <<'PY'
from hipengine.loading.gguf import scan_gguf
from hipengine.loading.qwen35_gguf import qwen35_gguf_config_from_metadata
from hipengine.loading.qwen35_gguf_shards import build_shard_manifest
info = scan_gguf("/models/gguf/Qwen3.8-27B-Q4_K_M.gguf")
cfg  = qwen35_gguf_config_from_metadata(info)
man  = build_shard_manifest(info, world_size=2, model_hash="probe", uneven_split=None)
PY
```

Full-attention layer (`blk.3`, `blk.7`), rank-0 local shapes:

| role | kind | local shape | equals |
| --- | --- | --- | --- |
| `attn_q` | group | (6144, 5120) | `2 * q_width` at `head_count=12` |
| `attn_k` | group | (512, 5120) | `kv_width` at `head_count_kv=2` |
| `attn_v` | group | (512, 5120) | `kv_width` |
| `attn_output` | row | (5120, 3072) | columns `= q_width = 12 * 256` |

Linear-attention (GDN) layer (`blk.0`), rank-0 local shapes:

| role | kind | local shape | equals |
| --- | --- | --- | --- |
| `attn_qkv` | group | (5120, 5120) | `linear_qkv_width = 2*8*128 + 3072` |
| `attn_gate` | group | (3072, 5120) | `ssm_inner_size = 3072` |
| `ssm_alpha` / `ssm_beta` | group | (24, 5120) | `ssm_time_step_rank = 24` |
| `ssm_a` / `ssm_dt.bias` | group | (24,) | `ssm_time_step_rank = 24` |
| `ssm_conv1d` | group | (5120, 4) | sharded conv channels |
| `ssm_out` | row | (5120, 3072) | columns `= ssm_inner_size = 3072` |

So the sharded config is exactly: `head_count` 24 -> 12, `head_count_kv` 4 -> 2,
`ssm_group_count` 16 -> 8, `ssm_inner_size` 6144 -> 3072, `ssm_time_step_rank`
48 -> 24, with `key_length`, `value_length`, `ssm_state_size`, `ssm_conv_kernel`,
`hidden_size` and `feed_forward_length` unchanged. `attn_norm`,
`post_attention_norm`, `ssm_norm` (128) stay replicated.

`gdn_head_map(cfg, rank, 2)` gives rank 0 key heads 0-7 and rank 1 key heads 8-15,
with 24 value heads each in tile-major order (rank 0: `(0..7, 16..23, 32..39)`),
which is the order the materialized value rows are already in.

The runner side is also config-derived rather than shape-hardcoded:
`_run_full_attention_prefill_attn_rows` and
`_run_linear_attention_prefill_attn_rows` take `self.q_width`, `self.kv_width`,
`cfg.head_count`, `cfg.head_count_kv`, `cfg.key_length` and the `cfg.ssm_*` fields,
all of which resolve from the runner's own `weights.config`. The KV cache and the
conv/recurrent state are sized from that same config, so both become per-rank
automatically.

What remains, in order:

1. Admit the `group` kind (and raw/dense layouts) to `_rank_payload` in
   `hipengine/distributed/shard_weights.py`, which today raises for any layout
   `_t16_repack_for_layout` does not resolve, and select the attention role set.
2. Substitute the uploaded `ShardWeight`s and the sharded config into the rank's
   runner via `dataclasses.replace` on the frozen
   `Qwen35GGUFResidentLayerWeights` / `Qwen35GGUFResidentWeights`, and extend the
   slot allowlist to drop the full-width attention copies.
3. Add the attention-output reduce (`attn_output` and `ssm_out` are row-split, so
   each rank produces a partial) to the bulk prefill loop, then to the
   graph-captured decode schedule.
4. Run the production gates. Sharding attention changes arithmetic in the decode
   route as well as prefill, so the decode gate matrix is part of this unit, not a
   follow-up.
