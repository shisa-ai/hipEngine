# Correction: the dual GEMV thread-count speedup was an L2 artifact, not a 3.8x opportunity

## Summary

The preceding entry reports that `dense_dual_gemv_out_bf16` is **3.8x faster** at
`threads=64` than at the `threads=256` default (283.0 -> 74.8 us at rows=1,
K=1536, N=8960) and that the change took the LM stage from 1.450 s to 1.266 s.
**The 3.8x figure is wrong and is corrected here.** It was an L2-caching artifact
of the benchmark, and under the DRAM streaming the real workload performs the
thread count makes no difference at all.

The rejection of the change stands, and the quality regression it records is real.

## What the benchmark did wrong

The isolated benchmark allocated one weight buffer and ran 30 iterations against
it. The dual projection's weights are 55 MB (two 1536x8960 bf16 matrices), which
stays resident in L2 across those iterations, so the measurement was reading
cache rather than DRAM. Repeating with a 256 MB flush buffer written between calls
gives the honest picture:

| threads | us | GB/s |
| --- | ---: | ---: |
| 64 | 1419.4 | 38.8 |
| 128 | 1464.2 | 37.6 |
| 256 | 1478.5 | 37.2 |

Cold-versus-warm confirms the mechanism directly: `threads=256` shows no
difference at all (264.7 us cold against 263.9 us warm), so it already streams
from DRAM, while `threads=64`'s warm 82.1 us collapses to 2149.6 us on a cold
call. The apparent speedup was `threads=64` exploiting L2 that `threads=256` was
not reaching.

The real workload cannot cache these weights: 28 layers at 55 MB each is 1.5 GB
of gate+up weights against a far smaller L2, so every call streams from DRAM.
That is also why the end-to-end gain was 184 ms rather than the order-of-magnitude
the isolated numbers implied.

## What the real limit is

**~37 GB/s against roughly 200 GB/s available.** That is a memory-access-pattern
problem, not a launch-configuration one. The kernel gives each workgroup one
output column and has it read a full row of both weight matrices; with K=1536 and
`threads=256` the vectorized main loop never executes at all (`vec_stride` is
2048, so `main_end` is 0) and every element is fetched by the scalar stride-256
tail. Fixing that means changing which thread sums which elements, which moves the
summation order, which means the generated-audio quality gate.

## What is unchanged

The change is still correctly rejected. It moved **5 of 17920** outputs by one
ulp, kept `chain_exact` true, kept the correctness suite green at 126 passed, and
still took the ten-seed generated-audio suite from **58/60 to 57/60** by adding a
`single-numbers` failure at WER 0.1667. The lesson recorded there -- that an
identical token chain does not imply identical audio, because the LM hidden state
conditions the diffusion head -- is unaffected.

## Changes

- `docs/REFACTOR.md`: the entry is retitled and rewritten. The 3.8x claim is
  retracted, the flushed table replaces the cached one, the real lever is named as
  the bandwidth gap, and a method note records that an isolated kernel benchmark
  reusing one input buffer measures L2 rather than the workload.

## Validation

- `uv run python /tmp/l2_flush.py` -> 1419.4 / 1464.2 / 1478.5 us at threads 64 / 128 / 256 with a 256 MB flush between calls (median of 12), against 74.8 / 117.6 / 283.0 us warm.
- `uv run python /tmp/l2_check.py` -> cold 2149.6 / 133.5 / 264.7 us against warm 82.1 / 114.2 / 263.9 us at the same thread counts.

## Next

access-pattern change and therefore the quality gate. The earlier sweep's numbers
for the decode q/k/v and o_proj projections carry the same L2 caveat and should be
re-measured with a flush before anything is built on them.
