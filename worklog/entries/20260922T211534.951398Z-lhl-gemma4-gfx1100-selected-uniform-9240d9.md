# One uniform selected-expert dispatch covers all 60 expert tensors

## Summary

`linear/<quant>/selected_gemv_bf16_bf16_out` resolves to a **GPU** selected-expert
GEMV for every quant type in the artifact:

| quant | resolved to | kind |
| --- | --- | --- |
| `gguf_q4_k` | `gguf_q4_k_gemv` | gpu |
| `gguf_q5_1` | `qwen4_exp_q5_1` | gpu |
| `gguf_q5_k` | `gguf_k_gemv` | gpu |
| `gguf_q8_0` | `gguf_k_gemv` | gpu |

So the expert forward needs **one** dispatch route, resolved from the registry by
quant key. No per-quant branching, no fallback chain, no stragglers.

This **supersedes
`20260922T211322.846682Z-lhl-gemma4-gfx1100-selected-experts-58fc27.md`**, which
reported 58 of 60 tensors covered with Q5_K and Q8_0 as stragglers needing a second
route. That was wrong.

## The same mistake a third time

The superseded entry checked `moe_linear/gguf_q4_k/` for a selected GEMV, found
nothing, and concluded Q4_K needed the offset path. The kernels are registered
under `linear/<quant>/`, and `selected_gemv_bf16_bf16_out` is present there for
**all five** quant types.

That is now the third time this session that a registry lookup answered a
different question than the one being asked:

1. A positive `resolve_gguf_linear_dispatch` read as proof a GPU kernel existed
   (it resolved to the CPU reference for Q5_1).
2. A negative `can_resolve` read as proof one did not (registration is lazy).
3. A negative lookup in `moe_linear/` read as absence, when the key lives in
   `linear/`.

Each time the fix was the same: stop reading the registry and call the kernel.
The Q4_K selected GEMV was verified working on the real artifact *before* the
registry was checked, and it was the registry check that was wrong.

## What was verified on the real artifact

Both the Q4_K and Q5_1 selected GEMVs reproduce a NumPy reference at the rounding
floor, with four different experts giving four different correct results:

| tensor | expert 0 | expert 3 | expert 5 | expert 127 |
| --- | --- | --- | --- | --- |
| Q4_K `ffn_gate_up_exps` (128x1408x2816) | 0.319% | 0.230% | 0.259% | 0.290% |
| Q5_1 `ffn_down_exps` (128x2816x704) | 0.270% | 0.344% | 0.313% | 0.309% |

Q5_K and Q8_0 resolve to `gguf_k_gemv` under the same variant name. That module
shares the `_launch_selected` ABI, but **its selected GEMV has not been called on
a real Q5_K or Q8_0 tensor**, so it is resolved-and-registered rather than
verified. The two tensors it covers are one layer each; the same applies to Q6_K,
which this artifact does not use.

## The ABI

```
(x_ptr, selected_ptr, qweight_ptr, out_ptr,
 x_rows, rows, num_experts, in_features, out_features, *, threads, stream)
```

- `selected` is `int64`, one expert index per compact row. The expert scratch
  already builds exactly this as `sorted_experts` (`lanes` entries), so no new
  buffer is needed.
- `rows % x_rows == 0`; `rows == x_rows` means one input row per compact row.
- Weights are raw blocks laid out `(num_experts, out_features, in_features)`,
  which Gemma 4's stacked expert tensors match directly.
- Default `threads` differs by wrapper (128 for Q4_K, 256 for Q5_1) and each
  wrapper sets its own, so the caller must not pass it.

## Why this is the better route

The expert forward currently reads `expert_start` back to the **host** and loops
one GEMV per non-empty expert — a device-to-host synchronisation per layer per
token, growing with the number of non-empty experts. The selected route is one
launch over all compact rows with no sync.

Since the uniform key covers every quant type, the per-expert offset path in
`gemma4_project_expert` becomes dead code once this is wired. It should be removed
rather than kept as a fallback, and `docs/REFACTOR.md` should not need an entry
because nothing is left behind.
