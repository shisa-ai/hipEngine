# Gemma 4 P9 landed re-scoped: the Q8_1 pack now gathers and packs in one kernel

## Summary

P9 asked to fuse the Q8_1 activation pack into `pre_ffw_norm_2` because "the
norm already reads the row". It does not read the row the pack reads. A top-k
gather sits between them and multiplies the row count:

```
rmsnorm(hidden -> normalized)                  # tokens rows
  -> gather(normalized -> packed_hidden)       # lanes = tokens * top_k rows
  -> ds4_pack(packed_hidden -> ds4)            # the pack reads THIS
```

At the real artifact that is 512 rows against 4096. The two stages operate on
different tensors, so the pack cannot fold into the norm as written.

The same saving was reached from the other end, where the data actually
touches: **`gguf_q8_1_mmq_gather_ds4_pack_bf16` now gathers and packs in one
kernel**, and on the MMQ route the BF16 `packed_hidden` staging buffer is never
written at all. That buffer's write-then-read round trip was 45.9 MB per
(block, layer), 11.0 GB over the 240 gather+pack pairs of a 4096-token prefill.

Net effect at 4096 tokens: **busy -22.5 ms (-0.65%)**, prefill **+0.6%**
(1149.9 -> 1156.7 tok/s) and **+1.6%** at 1024 (1989.3 -> 2020.1 tok/s), with
decode unchanged. Teacher-forced KL is identical to the recorded run to every
digit.

## Validation

**Why the fusion is exact.** The gather is a bit copy of `uint16`, so reading
`hidden_states` through the same lane index yields precisely the float the
unfused pack quantized. There is no new arithmetic anywhere -- only the removal
of a store and a load. That is what makes it safe without changing any gate.

**RED then GREEN.**
`test_q8_1_mmq_gather_ds4_pack_is_byte_exact_to_gather_then_pack` (3 shapes:
4x8x256, 3x2x512, 5x4x128) builds a random lane permutation with ~1/7 of lanes
invalidated to exercise the gather's bounds path, computes the unfused
reference on the host (gather, then the existing `pack_q8_1_mmq_ds4_from_bf16`
oracle), and requires `assert_array_equal`. RED was an ImportError on the
missing launcher; GREEN after the kernel landed.

One finding inside the test itself: the first attempt fed uniform random
`uint16` bits, which encode BF16 values near 1e38. The GPU handled them, but the
CPU oracle stores scale and sum as `float16` and silently overflowed to `inf`,
so 134/9216 bytes disagreed for a reason that has nothing to do with fusion.
The test now generates activation-scale values (standard normal x 4) and records
why.
