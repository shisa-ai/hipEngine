# Land the t16 gate_up repack dispatch wiring

## Summary

Implementation of the design entry
`20260930T011723.382520Z-lhl-gemma4-t16-repack-design-84f169.md`: the
Q4_K gate_up stacks now convert to the t16 tiles layout at load and dispatch
under the layout's own registry key, on by default.

Two deviations from the design, both forced:

- **Strict-row owner.** The design named `selected_gemv_bf16_bf16_out` (the
  linear alias) as the strict plan's selected for the t16 scope, but that raw
  variant name is not registered under `gguf_q4_k_t16_v1` at `moe_linear`.
  The rows carry `selected_t16_gemv_decode_bf16_bf16_out` instead — the same
  function registered under its own t16-native key at `moe_linear`, which the
  quant-change rule (`execution_profiles.py:428`) accepts and `_verify_
  registered_variants` can resolve.
- **The kernel defect the design's "mmq32 arithmetic is unchanged" claim hid.**
  The real-artifact smoke found production prefill logits wrong while the
  strict arm was correct. The t16 branch of the mmq32 device body indexed
  every expert at *half-width* tile columns (`expert_id * out_tiles` with
  `out_tiles` from the local half) and ignored `expert_stride_rows`, so a
  fused `gate | up` stack — which is the only form Gemma wires, and the form
  the Python test had explicitly excluded ("fused_stride requires the raw
  single-pass layout") — read expert ≥ 1 from wrong tiles. The conversion
  walked production into a combination that was never modeled. Fixed in the
  device code to honor the same expert-stride contract as the raw branch,
  with a loud `% 16` wrapper guard for non-tile-aligned strides.

## Changes

- `hipengine/loading/gemma4_gguf_device.py`: `materialize_...` converts
  t16-planned tensors (bit-lossless repack, `tiles` allocation); dense dirty
  paths derive stride from `spec.dense_stride_rows()` instead of
  `expert_stride_bytes // experts`.

  the `(linear, gguf_q4_k_t16_v1, selected_gemv_bf16_bf16_out)` alias — the
  decode chain resolves that key, and the strict grouped-miss fall-through
  must land on it rather than on the raw-layout by-offset launch.

  `weight.allocation()` (layout-resolved) at the mmq launch and by-offset
  sites; `gemma4_project_experts_by_offset` and the by-offset launch wrapper
  raise loudly on a non-raw resident layout.
- `hipengine/generation/gemma4_profiles.py`: the `gate_up_q4_k` and
  `moe_decode_q4_k` rows (both plans) carry `registry_quant
  = gguf_q4_k_t16_v1`; production's declared fallback for that scope becomes
  the t16 exact owner; strict's selected for the scope becomes the same
  owner. Manifest truth only — the binder pins the route env, dispatch stays
  weight-driven.
- `hipengine/kernels/hip_gfx1100/quant/gguf_q4_k_q8_1_selected_prefill.hip`:
  T16 branch honors `expert_stride_rows` (stride tiles = rows / 16 when set,
  half-width tile count when 0, i.e. split tensors). Comment updated; the X8

  the only fused-stride caller and never resolves x8).
- `hipengine/kernels/hip_gfx1100/quant/gguf_q4_k_q8_1_selected_prefill.py`:
  `_require_t16_tile_stride` in the t16 ds4 mmq32 wrapper (positive stride
