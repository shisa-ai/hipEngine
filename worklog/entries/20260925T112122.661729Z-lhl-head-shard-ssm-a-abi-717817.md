# The head-sharded route uploaded ssm_a in the wrong ABI

## Summary

The head-sharded bulk prefill disagreed with the unsharded route from token 1 on
(~5% per-token rel_rms, token 0 exact). The cause is a source-to-kernel ABI
conversion that only the replicated materializer applied: GGUF `ssm_a` holds the
negative decay coefficient, the GDN kernels take `A_log`, and
`hipengine/loading/qwen35_gguf_materialize.py` converts the whole tensor with
`_gguf_ssm_a_to_kernel_a_log` before upload. The rank-payload path
(`_rank_payload` in `hipengine/distributed/shard_weights.py`) sliced source bytes
verbatim, so each rank's device `ssm_a` held the raw coefficient.

The kernel computes `decay = exp(-exp(a_log) * softplus(alpha + dt_bias))`. With
the raw coefficient in place of `A_log`, `exp(a_log)` is `exp(A)` instead of
`exp(A_log) = -A`. For `blk.0.ssm_a[0] = -3.203125` the kernel used `-0.040635`,
so every head's decay changed and the recurrent state diverged. The state is
zero at token 0 and the decay only multiplies it, which is why token 0 stayed
exact while everything after it was wrong.

## Changes

- `hipengine/loading/qwen35_gguf_shards.py`: new `materialize_payload_slice`,
  which is `materialize_slice` plus the slot's ABI step, and it is now the only
  way a payload is built. `materialize_manifest` and `iter_rank_payloads` use it
  too, so the streaming loader path and the reconstruction oracle cannot drift
  from the runtime path. `verify_manifest_round_trip` keeps the raw slicer on
  purpose (it checks the plan partitions the source, not the upload bytes) with a
  comment saying so.
- `hipengine/loading/qwen35_gguf_materialize.py`: new
  `ssm_a_slice_to_kernel_a_log`, the byte-range form of the existing
  `_gguf_ssm_a_to_kernel_a_log`. One definition of the ABI, two callers.
- `hipengine/distributed/shard_weights.py`: `_rank_payload` builds payloads
  through `materialize_payload_slice`.
- `tests/test_unit_distributed_shard_weights.py`: new
  `test_attention_ssm_a_payload_is_the_kernel_a_log_abi_not_the_source` covers
  the runtime and the streaming paths. Two existing tests that asserted the raw
  coefficient for `ssm_a` now assert the converted one
  (`test_attention_runtime_payloads_carry_the_tiled_local_slices`,
  `test_raw_attention_payloads_are_the_owned_heads_rows`). They were written from
  the shard plan's point of view and pinned the bug: a payload test that never
  crosses the ABI boundary agrees with itself.
- `scripts/tp2_head_shard_agreement_probe.py`: captures the recurrence inputs,
  the linear state, the per-layer scratch pointer maps, and a linear-launch
  trace, which is what localized this.

## Validation

- `tests/test_unit_distributed_shard_weights.py` +
  `tests/test_unit_loading_qwen35_gguf_shards.py`: 98 passed.
- `tests/test_unit_distributed_staged_compiled.py`,
  `test_unit_distributed_shard_group.py`,
  `test_unit_scripts_tp2_head_shard_agreement_probe.py`,
  `test_unit_scripts_tp2_layer0_mlp_reference_check.py`,
  `test_live_qwen35_gguf_materialize_helpers.py`,
  `test_integration_gguf_gdn_geometry_contract.py`,
  `test_unit_distributed_tp2_generate.py`: passed.
- RED proof: with the conversion disabled in `materialize_payload_slice`, the new
  test fails with `rank 0 ssm_a payload is not the kernel A_log ABI` and the
  corrected payload test fails with `ssm_a rank 0 holds the wrong heads`.
- CPU evidence, no GPU needed: for `blk.0.ssm_a`, rank 0's payload is now
  `[-3.203125, -4.65625, -2.828125, -3.921875, ...]`, which is the replicated
  materializer's `log(-coefficient)` for heads 0-7 of tile 0, and rank 1's is the
  same for tile 1's heads 8-15. Before the fix both were the raw coefficients
  `[-0.040635, -0.009502, -0.059124, ...]`.
- Inverting the kernel's decay formula on the sharded route's `prefill_decay`
  recovered `log(exp(a_log)) = -0.0406, -0.0095, -0.0591, ...` for the first
  heads, i.e. exactly the raw payload values, and the same inversion reproduces
  the unsharded route's own decay and `linear_alpha` to 5 decimals as a control.
  That is what identified `ssm_a` rather than the alpha projection, which the
  same run showed was byte-identical to the unsharded route's tiled heads.
- End-to-end, on the fixed build: the head-sharded route's `prefill_decay` is
  byte-identical to the unsharded route's decay at the heads it owns
  (`max|diff| = 0` for all 24 heads on both ranks), and its recurrent state is
  byte-identical too (`rel = 0.0` per head, both ranks). Before the fix the same
  comparison was `rel = 0.01-0.96` per head with a median of 0.58, and the decay
  was wrong at 0 of 24 heads.
- End-to-end logits, same 64-token prompt, both routes measured in the same
  session: mean KL `0.3626 -> 0.001169`, top-1 agreement `0.5938 -> 0.9844`.
  The residual is the reduction's own floor, not a compute difference: at every
  layer the sharded-vs-unsharded attention difference equals the
  `partials_sum_vs_full` difference of the split itself (0.0016 vs 0.0021,
  0.0052 vs 0.0046, 0.0082 vs 0.0082, 0.0091 vs 0.0092, 0.0117 vs 0.0116),
  which is what rounding each rank's partial to bf16 before the exchange costs.
  Both ranks agree with each other exactly at every layer, and the host-sum
  reduction check is exact at every layer.
- This is a correctness repair, not a performance claim, so no benchmark row is
  retained for it.
