# W7900 Qwen3.8: hypothesis on record - MTP cycles run eager while packed AR decode replays graphs

## Summary

Candidate mechanism for the 3.21x per-row verify cost, written before the K1/K3/K7
profile (`bg-59`) can judge it: **packed AR decode replays captured graphs, MTP verify
cycles do not**. `hipengine/generation/qwen35_gguf.py:8033-8051` captures and replays a
per-width packed decode graph and counts `native_packed_graph_captures` /
`native_packed_graph_replays` / `native_packed_decode_steps` around the replay. In
`hipengine/runtime/qwen35_gguf_runner.py`, the only line matching verify *and*
graph/replay is a comment (line 1602) - there is no capture or replay machinery on the
verify path.

## Changes

Hypothesis only. No code or benchmark change.

## Validation

Static reading, plus the measurement it has to explain: AR marginal 6.71 ms/row
(graph-replayed decode) vs MTP marginal 21.51 ms/verified row, with MTP's *fixed* cost
lower than AR's (21.4 vs 27.6 ms) - a shape consistent with per-row launch overhead
rather than per-cycle setup.

Not proof, and stated as such: an eager verify cycle also does genuinely more work per
row than an AR decode row (row-attention across candidate positions, candidate-tree
gather, accept kernels). The profile decides, because
`scripts/mtp_verifier_rocprof.py` reports `kernel_time_share_of_host_window` for the
traced region.

Decision rule to apply to `bg-59`, before seeing it:
- If the cycle region's kernel share is far below what the graph-replayed decode path
  achieves (rough guide: below ~0.7 vs ~0.9), the gap is host/launch bound and the fix is
  to extend graph capture to verify cycles.
- If the share is comparable, the 3.21x is real kernel work and the fix is kernel-level,
  with the per-family table naming which family owns the marginal.

Either outcome is useful; only a mixed signal (share high but marginal concentrated in a
family that is itself launch-bound at 2-4 rows) would need a further cut.
