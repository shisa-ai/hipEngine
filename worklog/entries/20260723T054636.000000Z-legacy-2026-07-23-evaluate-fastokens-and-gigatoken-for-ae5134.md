# 2026-07-23 — Evaluate fastokens and Gigatoken for hipEngine tokenization

## Summary

- Historical pre-Worklog2 journal entry, ported verbatim from `WORKLOG-LEGACY.md` (source lines 177108-177118).
- First appended to the journal in commit `dc571d62` (subject: docs: record tokenizer acceleration study).

## Changes


- Mapped the active paths. Laguna and Qwen GGUF public generation use the in-tree pure-Python byte-BPE implementation (`hipengine/tokenization/gguf.py`), including an unbounded per-pretoken dictionary; the native/safetensors Qwen helper instead uses Hugging Face's Rust `tokenizers`. Laguna request tokenization happens in `_prepare_request()` before the generator's `started` timestamp, so the retained 1.620-s AR TTFT and 512/1K/4K model-prefill measurements exclude tokenization even though HTTP wall time includes it. Streaming output already uses a direct incremental byte-piece decoder, so encode—not decode—is the relevant replacement boundary.
- Researched Gigatoken 0.9.0/source `ecf968da2b7300e33f90e8bd9c96a11a335a01ae` and fastokens 0.2.1/source `326cb5afc5a033d2f7885832d12fd43b9ea50cdd`. fastokens loads Poolside revision `179ee67c` `tokenizer.json` directly. Gigatoken rejects Laguna's ordered two-Split pre-tokenizer because it only dispatches recognized regex lists; a diagnostic proxy that removes the preliminary newline Split and retains the exact Qwen2 Split plus ByteLevel stage loads through its optimized Qwen2 scanner. That proxy is not production-qualified until Laguna receives a first-class upstream scheme or the redundancy of the newline stage is proven exhaustively.
- Built both candidates only in `/tmp/hipengine-tokenizer-bench-venv`; no project dependency changed. On Ryzen AI Max+ 395 (16C/32T), Python 3.10.20, HF tokenizers 0.23.1, all four Laguna encoders matched on 334 edge/template/canonical/generated inputs, and a further 160 disjoint 128/512/1K/2K/4K tracked-source windows had zero mismatches. This establishes local diagnostic parity, not the repository's required exhaustive tokenizer gate. The direct fastokens route is therefore the lower-risk prototype; the Gigatoken proxy remains directional only.
- Exact ten-prompt Laguna suite (864 tokens / 4,059 input bytes): current pure Python first/hot suite `7.228/2.113 ms`, HF `0.803/0.249 ms`, fastokens `0.900/0.131 ms`, and Gigatoken proxy `22.142/0.021 ms`. The Gigatoken first batch pays worker/cache startup and is slower; its warm path is about 101x faster than current. Per request, current hot overhead is only about 0.211 ms, so fastokens saves about 0.198 ms on these short prompts.
- Single-request prefix-sharing medians at 128/512/1K/2K/4K tokens were current `0.465/1.596/2.677/5.469/11.238 ms`, HF `0.188/0.589/1.022/2.189/4.767 ms`, fastokens `0.027/0.052/0.077/0.146/0.275 ms`, and Gigatoken proxy `0.005/0.012/0.022/0.039/0.075 ms`. Thus fastokens is 17-41x versus current and Gigatoken proxy about 93-150x. On 32 disjoint tracked-source windows, current -> fastokens is `0.889 -> 0.045`, `1.945 -> 0.078`, `3.319 -> 0.126`, `8.709 -> 0.204`, and `17.521 -> 0.329 ms` (20-53x); the proxy reaches `0.008/0.020/0.035/0.060/0.081 ms` (97-215x). Fresh-cache 4K single-input latency is current/HF/fastokens/proxy `20.875/8.871/1.026/0.447 ms`; tokenizer construction is excluded and costs about `45/182/512/260 ms`, hidden inside the roughly 49-s Laguna load.
- Amdahl result: at current 512/1K/4K model-prefill times of about 10.790/22.833/106.277 s, fastokens saves only about 1.5-1.9/2.6-3.2/11.0-17.2 ms, or roughly **0.01-0.02% of current end-to-end TTFT**. It does not change 16.38 tok/s decode. Even at the campaign's 500 tok/s stretch, the measured 4K saving is only about 0.13-0.21%. This becomes important for high-KV-hit frontends, token counting/routing, very fast small models, or high request concurrency—not for current Laguna model throughput.
- Separate Qwen3.6 diagnostic found the optimized libraries apply directly, but also exposed an existing oracle issue: the GGUF Python tokenizer does not apply the source tokenizer's NFC normalizer. For `e\u0301 cafe`, current GGUF returns `[68, 52033, 39579]`, while NFC input, HF, fastokens, and Gigatoken return `[933, 39579]`. Do not use the current GGUF implementation as the Qwen parity oracle in a tokenizer-backend promotion.
- Recommendation: prototype an optional registry-backed **encode-only fastokens backend** for Laguna first, keep the existing incremental decoder, preserve exact raw-token bypasses, and retain the Python fallback. Gate with the frozen Poolside fixtures plus broad random/Unicode/CRLF/atomic-special and full prompt-suite parity, long-running cache/RSS and concurrency tests, and actual server tokenization telemetry. Do not add either dependency to the default runtime solely for the current 0.01-0.02% TTFT gain. Revisit Gigatoken after first-class Laguna pre-tokenizer support and bounded-memory/concurrency qualification. Diagnostic outputs: `/tmp/hipengine-tokenizer-comparison.json`, `/tmp/hipengine-tokenizer-disjoint.json`, and `/tmp/hipengine-qwen-tokenizer-comparison.json`.
