# Fix the DMS append compaction read/write race in both codecs

## Summary

`append_layer`'s chunked keep-scan moved a retained row leftward while a later
keeper could still need the slot it wrote to. Pass 2 read its own source and
wrote its destination in one instruction sequence with only chunk-iteration
barriers between, so when a row expired every later keeper shifted and the loser
of the race read a value another thread had already moved: one position
duplicated, another lost. The count was unchanged, which is why neither
`finalize_device_append`'s count-only cross-check nor the DMS+INT8 MTP parity
gate could see it. Both codecs now stage each keeper's row so a barrier
separates the whole read phase from the whole write phase.

## Changes

- `hipengine/kernels/hip_gfx1100/attention/dms_compact_int8.hip`
  (`dms_int8_append_kernel`, pass 2) and
  `hipengine/kernels/hip_gfx1100/attention/dms_compact.hip`
  (`dms_append_compact_kernel`, pass 2): when a chunk shifts, every keeper
  stages its payload, scales, position and eviction flag in shared memory, a
  barrier separates the read phase from the write phase, and the payload moves in
  eight-column tiles. A chunk shifts when it dropped a row **or** inherits an
  earlier chunk's drop; only a chunk that neither drops nor inherits skips the
  staging, so the no-eviction path costs what it did before.
- `tests/test_gpu_dms_int8_append_shift.py` (new): the focused case the task
  asked for, plus a repeatability case.
  - One expiry, whole sequence: `window=64` at 600 tokens puts exactly one row
    at `t=535` in the window where packing keeps it (`tokens-1-t <= window`) and
    the append drops it (`tokens-t > window`). The head carrying the eviction
    must shift and the other must not. Every position, every quantized payload
    element, every scale and every eviction flag of every head is asserted
    against the host rule, including the appended row, so a duplicate-and-loss
    cannot pass on a matching length or live count.
  - Repeatability: the same append runs four times in one process and the
    position, payload, scale and eviction bytes must be identical each time.

## Validation

- `run1151 pytest tests/test_gpu_dms_int8_device_payloads.py --suite gpu` --
  **7 passed**, including the two long cases (8193, 16385) that failed before,
  and **5 passed on each of three consecutive runs** of the append case alone,
  which is the determinism the defect broke.
- `run1151 pytest tests/test_gpu_dms_*.py --suite gpu` -- **57 passed, 1
  skipped, 0 failed**, covering the BF16 sibling's own append and pipeline gates.
- Lineage: neither edited file appears in `docs/source_lineage.json`, so they are
  not tracked ports and the lineage gate does not apply. `scripts/check_lineage.py`
  itself fails on this host for an unrelated reason -- the manifest's parent
  repo `~/dflash` is not present.

## Next

- The first attempt at the guard skipped the staging whenever a chunk dropped
  nothing, which is wrong: a chunk that inherits an earlier chunk's drop still
  shifts every keeper. That showed up as a deterministic off-by-one from the
  first chunk boundary on (96.9% of positions at 8193), not as a race. The
  condition is now `chunk_rank != chunk0 || chunk_total != chunk_rows`.
- The staging costs two barriers per eight columns on chunks that shift. A chunk
  that drops nothing and inherits nothing still skips it entirely.
