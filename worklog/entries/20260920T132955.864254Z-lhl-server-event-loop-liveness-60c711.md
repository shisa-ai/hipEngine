# keep engine command waits off the event loop thread

## Summary

The server tokenizes prompts through `EngineService`, whose control commands wait
on one driver thread behind whatever that thread is doing: a context prepare that
grows the KV pool and captures graphs, or a single prefill tick of a large prompt.
Those waits ran on the event loop thread, so nothing else the server owed a client
made progress for the duration - SSE deltas were not flushed (a client saw its
remaining tokens arrive in one burst after the wait), and health checks,
cancellation, and other requests queued behind it. Raising the command budget to
300 s made the failure rarer but widened the stall it could cause. The waits now
run on worker threads, so they are paid by the request that asked for them.

`EngineService._activity_snapshot()` also read its activity fields twice: a driver
thread that finished its tick between the check and the read turned a diagnostic
into `TypeError: unsupported operand type(s) for -: 'float' and 'NoneType'`. Each
field is now sampled once into a local before use.

## Changes

- `hipengine/server/api.py`: `_prepare_prompt_input(s)` gained async wrappers that
  run the engine call via `asyncio.to_thread` when the engine exposes
  `tokenize`/`count_tokens` (an `EngineService`); all five server call sites use
  them. `chat_context_candidate` and `chat_context_fit_payload` calls (including
  the thinking-budget ladder) are offloaded the same way, since rendering and the
  context-fit checks issue engine control commands too.
- `hipengine/generation/engine_service.py`: `_activity_snapshot` samples
  `_active_command_kind`, `_active_command_method`, `_active_command_started_at`,
  and `_tick_started_at` once each.
- `tests/test_integration_server_api.py`: new `BlockingPrepareFakeLLM` (a
  `tokenize` that blocks on a release event, a stream that runs until stopped) and
  `test_blocked_engine_command_does_not_stall_an_in_flight_stream`, which posts a
  streaming chat request straight into the ASGI app, blocks a second request's
  engine command, and requires body messages to keep arriving while it is blocked.
  `TestClient` collects a response body before returning, so the app is called
  directly to observe delivery.
- `tests/test_integration_generation_engine_service.py`:
  `test_activity_snapshot_samples_each_field_once` forces the driver to clear
  `_tick_started_at` between the check and the read.

## Validation

- New test is RED without the `api.py` change (stashed it, re-ran):
  `AssertionError: the in-flight stream stalled while another request's engine
  command was blocked on the event loop thread`. GREEN with it.
- `python3 -m pytest tests/test_integration_generation_engine_service.py
  tests/test_integration_server_api.py -q`: 667 tests, no failures.
- `python3 -m pytest tests/test_unit_server_request_info.py
  tests/test_unit_llm_generate.py tests/test_unit_server_log_style.py -q`: pass.

## Next

- The measured effect is delivery continuity, not throughput: a request whose
  engine command is slow still waits for that command, and its own first token is
  still delayed by it. What changed is that other in-flight streams, health
  checks, and cancellation keep running.
