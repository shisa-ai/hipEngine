# TP2 Packet 1: KV geometry is backend-owned and KV admission is ledger-owned

## Summary

The review's R10 item was that `hipengine/distributed/kv.py` had invented a
parallel memory-accounting world: private `KvClaim`/`KvClaimSet` classes, a
sequential callback allocator, no `KVPoolPlan`/`ResourceClaimSet`/
`ResourceDelta`, and no integration with the existing `ResourceLedger` - so a
TP2 KV claim was not a scheduler-owned atomic reservation. Its geometry also
ignored `value_length` and assumed four int32 metadata fields per token per
layer, while `KVLiveSpans` is mode-specific.

Both halves are now integrated rather than rescoped.

**Backend-owned geometry.**

- K and V head widths are read as separate config fields. `bytes_per_token` sums
  `key_length + value_length`, so unequal widths are sized correctly; a config
  that omits `value_length` gets equal widths and the geometry records
  `value_head_dim_assumed_equal: true` instead of silently doubling one width.
- The metadata term comes from a declared `KvSpansLayout`. The three real modes
  carry different tensors, and only some are per token:
  - `paged_uniform(max_pages_per_sequence)`: int32 block table per layer per
    sequence plus int32 live counts, int64 `row_positions` per sequence, no
    per-token metadata - so it scales with the page table, not the context;
  - `per_head_variable(kv_heads)`: int32 `base_offsets` and `live_counts` per
    head per layer; the optional `token_positions`/`evict_mask` shapes are not
    fixed by the ABI, so their per-token cost must be stated rather than assumed;
  - `sliding_ring(slots_per_sequence)`: int64 positions, a mask byte and an
    int32 base offset per capacity slot, i.e. per token per layer, plus one
    int64 `row_positions` per sequence;
  - `dense_policy()`: the historical four-32-bit-fields-per-token-per-layer
    figure, kept as a named layout so the retained capacity numbers stay
    traceable to the assumption they were computed under.
- `resolve_kv_geometry` now **requires** the spans layout. There is no default,
  so no mode's footprint can be applied to another mode by omission.
- Schema version is 2 (the geometry fields changed), and the version check still
  refuses anything else.

**Ledger-owned admission.**

- `build_group_kv_plan` declares each rank's stable `KVPoolPlan` (a plane byte
  pool and a spans byte pool) and the `ResourceClaimSet` this group takes from
  it. The pools are the rank's KV budget, so a second group cannot claim the same
  region - the ledger's capacity check refuses it, and the refusal names the
  pool.
- `reserve_group_kv` takes a provisional reservation in **every** rank's own
  `ResourceLedger` (each rank owns its device memory) and returns a
  `KvGroupReservation`. Commit applies to all ranks; a failure on any rank rolls
  back the holds already taken and raises with the rank that could not fit.
  Callers may pass the scheduler's existing per-rank ledgers so ownership is
  shared with the rest of admission.
- `claim_all` remains the device-buffer path and is documented to run *after*
  the ledger commits, so the ledger owns accounting and the callback owns
  buffers.

The retained capacity figures do not move: 258/514 MiB at 8192 and 1032/2056 MiB
at 32768 are the dense-policy layout's numbers, now labelled as such in
`benchmarks/README.md` and the plan doc.

## Changes

- `hipengine/distributed/kv.py` - `KvSpansLayout`, backend-owned
  `KvPoolGeometry` (separate K/V widths, declared spans layout, schema 2),
  `build_group_kv_plan`, `KvRankPlan`, `KvGroupReservation`,
  `reserve_group_kv`, and the pool-id helpers.
- `tests/test_unit_distributed_kv.py` - 27 tests: the mode-driven footprints
  with hand-computed bytes, unequal and inferred K/V widths, the paged layout not
  growing with context, per-rank pool/claim agreement, provisional holds visible
  before commit, commit/rollback semantics, a second group refused by capacity,
  a later-rank failure rolling back earlier holds, and the device allocator
  running after commit.
- `tests/test_gpu_distributed_transport.py` - a two-GPU test that commits a
  ledger-owned group reservation on real ledgers, refuses a second group, and
  then allocates one device buffer per rank.
- `docs/QWEN38-27B-GFX1100-TP2.md`, `benchmarks/README.md`,
  `benchmarks/CHANGELOG.md` - Packet 1's KV item closed with what was built, and
  the KV geometry prose corrected to name the layout.

## Validation

- `uv run pytest tests/test_unit_distributed_kv.py` - 27 passed.
