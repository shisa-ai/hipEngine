# Gemma 4 campaign harness and decode baseline (G0)

## Summary

- The first optimization-loop attempt (`gemma4-moe-perf/g0-start`) hit a state-machine
  misfire: the baseline-setting `multiloop_measure` call and a second call needed to echo
  the configured prompt verifier created a phantom delta-0 iteration whose only accepted
  disposition was a false `revert` of correct work. That run was stopped before any
  `results.jsonl` entry was written and relaunched as `gemma4-moe-perf/g0`. Lesson for
  the loop: measure exactly once per iteration, with the configured prompt verifier text
  echoed verbatim in `checks`.
- G0's separated-phase measurement harness now exists: `scripts/gemma4_campaign_bench.py`
  reports load, warmup, prefill (incl. the last-row output head inside
  `Gemma4Runner.forward`), first-token latency, decode, and one untouched public
  `LLM.generate` wall row over the exact same token ids. It freezes prompt ids,
  provenance (commit, dirty files, artifact fingerprint, visibility env, clocks), and
  prints the campaign metric `decode_tps=<median>`.
- Baseline on physical GPU1 (RX 7900 XTX, `ROCR_VISIBLE_DEVICES=1`), commit `68d240ca9`,
  artifact `gemma-4-26B-A4B-it-UD-Q4_K_XL.gguf`, 1024 prompt / 128 output, context 8192,
  greedy, 1 warmup + 3 samples: **decode 16.08 tok/s** (stdev 0.01), prefill 128.6 tok/s,
  first token 7.96 s, instrumented wall 15.86 s, public wall 15.88 s. Instrumented and
  public paths produced identical token ids (`public_path_parity=True`); resolution was
  `hip_gfx1100` + `gguf_q4_k_m` through `SubmitPollTextGenerator` delegating to
  `Gemma4Runner(capacity 8192, max_block 512)` — no hidden fallback. The artifact was
  written while the two harness files were still untracked; that is recorded honestly in
  its provenance.
