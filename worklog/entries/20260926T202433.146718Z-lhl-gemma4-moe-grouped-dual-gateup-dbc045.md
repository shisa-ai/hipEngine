# gemma4-moe-grouped-dual-gateup

## Summary

The fused Q4_K `gate_up` projection was 56.7% of the default prefill (3951 ms
of 6982 ms, 68.1 ms per call) because the selected dual GEMV ran one CTA per
(row, output column) and re-read every weight row once per compact row. The
repository already had a grouped rowbatch8 dual owner for Q4_K, with an existing
test asserting it matches the strict selected dual bit-for-bit, but Gemma could
not reach it: the probe uses the single-output grouped variant name, and the
dual owner takes two separate weight tensors and two separate output buffers,
while Gemma's `gate_up` is one allocation holding both halves.

Threading the fused expert stride and an explicit output row stride through that
owner, and probing it for the fused `gate_up`, took the default prefill from
6.982 s to 4.242 s on the W7900 lane (146.7 -> 241.4 tok/s) and from 154.0 to
253.0 tok/s on the RX 7900 XTX lane. The arithmetic did not change: the gate
reports `kl_max` of exactly 0.000000 over 1023 rows, because the owner
reproduces the selected dual's strict 128-thread reduction tree.

Cumulative for the campaign's prefill column: 128.5 -> 253.0 tok/s (+97%),
first-token latency 7.97 -> 4.05 s, decode unchanged at 43.84 tok/s.

## Changes

- `hipengine/kernels/hip_gfx1100/quant/gguf_q4_k_selected_prefill.hip`: the
  grouped rowbatch8 dual kernel takes `output_row_stride` and
  `expert_stride_rows`. Both default to zero, which keeps the two-tensor
  convention (each side's own width) and leaves every existing variant's
  arithmetic and layout unchanged; a fused `gate_up` passes the fused width for
  both. The five other launchers of the same kernel pass zero for both.
- `hipengine/kernels/hip_gfx1100/quant/gguf_q4_k_selected_prefill.py`: the same
  two keyword arguments on the wrapper, with the C argument list extended by
  two `int64`.
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_experts.py`: new
  `gemma4_project_experts_grouped_dual`, probed for the fused `gate_up` before
  the single-output grouped owner and the selected GEMV. It passes the fused
  width as both strides, offsets the up half's output pointer one gate width
  into the fused row, and offsets the up half's weight pointer one half into the
  fused allocation. The last of those is the same convention
  `gemma4_project_experts_wmma_dual` already uses, and it is required: the owner
  strides experts by the fused width while indexing each side from its own
  origin.
- `scripts/gemma4_prefill_census.py`: the new helper gets its own family label,
  so the gate+up time stops landing in "unattributed inside layers".
- `tests/test_gpu_gguf_q4_k_selected_wmma_prefill.py`: new
  `test_grouped_rowbatch8_fused_stride_matches_the_two_tensor_form_bits`, which
  runs the fused form and the two-tensor form over the same weights and asserts
  bit-equality of both halves. Neither stride failing is loud, so this is the
  test that pins the fused layout.

| **layer total** | **6982** | **4242** |

Teacher-forced gate, default route, against
`/mnt/nvme1/gemma4-eval/teacher-forced-prefilled-strict-001c4fec3.npz`, prompt
2048 with prefill 1024, 1023 scored rows: `kl_max` 0.000000, `kl_mean` 0.0,
`kl_p99` 0.0, top-1 rate 1.0, zero flips, pass. The exact figure matters more
than the pass here: this route is bit-identical to the strict reference, so the
prefill win carries no numerical cost and owes no promotion gate.

Campaign bench on the RX 7900 XTX lane, 1024 prompt / 128 output, three samples
after one full-shape warmup, public `LLM.generate` path with parity reported:
prefill 4.05 s (253 tok/s), first token 4.05 s, decode 43.8357 tok/s, wall
6.96 s. Decode is unchanged because a decode step is too narrow to reuse a
weight row.

Tests: 34 passed across `tests/test_gpu_gguf_q4_k_selected_wmma_prefill.py`,
`tests/test_gpu_qwen4_exp_q5_1_selected.py` and
`tests/test_unit_gemma4_moe_prefill_routes.py`, including the new fused-stride
bit-equality test and the pre-existing
`test_grouped_rowbatch8_matches_strict_selected_dual_bits` that pins the
two-tensor form to the strict selected dual.

layer-29 MoE is still on the selected GEMV for both projections: `gguf_q5_k` has
a registered single-output WMMA owner that would take the fused width, and
`gguf_q8_0` has none.
