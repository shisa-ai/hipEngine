# BLOCKED: intermittent GPU page fault in Gemma 4 incremental decode

## Summary

Incremental decode through `Gemma4Runner` intermittently faults the GPU with a
page-not-present error, typically around the third or fourth decode step. It is a
memory over-read somewhere in the layer path. I have not root-caused it, and I
am stopping here rather than guessing at a fix I cannot validate.

This is **not** in the generation adapter. It reproduces with the runner called
directly, with no generator involved.

## Reproduction

```python
w = load_gemma4_device_weights(GGUFReader(path))
run = Gemma4Runner(weights=w, capacity=64)
logits = run.forward([27])              # prompt: ok
for _ in range(20):
    logits = run.forward([run.next_token(logits)])   # faults at step 3-4
```

Observed failure:

```
Memory access fault by GPU node-1 (Agent handle: ...) on address 0x7f01967b1000.
Reason: Page not present or supervisor privilege.
```

The address is page-aligned, which is what an over-read past the end of an
allocation looks like.

## It is intermittent, and that matters

The same script has run 3 clean decode steps and 12 clean decode steps on some
invocations and faulted on step 2, 3, and (once, with padding applied) on the
*first* prompt forward. `test_incremental_decode_matches_a_dense_prefill` passes
5 decode steps every run under pytest.

So the fault depends on where the allocations land, not on a specific step
count. That is the signature of reading uninitialized or out-of-bounds memory:
whether it faults depends on whether the address happens to be mapped.

**A wedged GPU is part of the symptom.** After the first fault, GPU 0 sat at 100%
utilization and 81 °C spinning, and every subsequent run hung rather than
faulting. Killing the orphaned process cleared it. Any agent picking this up
should check `rocm-smi` first: a hang after a fault is the device, not the code.

## What I eliminated

- **Not the generation adapter.** Reproduced calling `Gemma4Runner.forward`
  directly.
- **Not the mask width.** The layer passes `keys = write_offset + rows`, which is
  exactly the `(rows, write_offset + rows)` mask the runner builds.
- **Not a use-after-free from the per-call uploads.** `malloc`/`free` map to
  `hipMalloc`/`hipFree` directly, with no pooling. Padding the mask buffer with
  8 KiB of slack moved the failure one step later; padding the mask *and* both
  rope tables with 1 MiB did not prevent it, and one run faulted on the prompt
  forward with that padding in place. So it is not the rope or mask allocations.
- **Not a free/realloc race.** Padding changes sizes but not the free ordering,
  and it did not fix it.
- **Not the fixture.** Occurs with both `fixture_metadata()` and
  `tokenizer_fixture_metadata()` artifacts at vocab 64.

## Where I would look next

The remaining buffers that grow with position are the KV caches, and they are the
ones I have not been able to pad. Specifically worth checking:

1. `_append_kv`'s offset and size units. The layer passes an **element** offset
   (`write_offset * kv_width`) and an element count; confirm the wrapper converts
   both to bytes consistently and does not double-count.
2. Whether `gemma4_attention_prefill_bf16` reads the KV cache past `keys` to a
   tile boundary. With `capacity=64` a read to a 16- or 32-wide tile is still
   in-bounds, which would explain why the fault needs the *mask* to be the tight
   allocation — but the 1 MiB mask padding not fixing it argues against this
   being the only over-read.
3. The scratch buffers, which are sized for `max_block` tokens and are reused
   across steps without being cleared. A kernel that reads a full tile of a
   scratch region it only partially wrote would read stale data; whether that
   faults depends on the scratch's own allocation, not the caller's.

A cheap decisive experiment I did not get to: allocate every scratch and cache
buffer through a single large arena with a guard region after each, so an
over-read faults deterministically at the buffer that caused it instead of
intermittently at a random one.
