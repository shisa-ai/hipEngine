# Served MTP admission, the prefix-cache default, and the sampled route

## Summary

Three claims about the served lane were checked on `gfx1151` against the running
server. One was a real documentation defect, one was already fixed in code but
still described as current in three other places, and one is a wiring gap rather
than a kernel gap.

1. **Prefix caching is not on by default in `hipengine serve`, and that is
   deliberate.** The documentation said otherwise and has been corrected.
2. **There is no 512-token MTP boundary.** The 1,023-token window was removed on
   2026-09-20 (`b8fd83566`) and the adapter admits to the target's own capacity;
   greedy MTP was measured engaging from 128 to 11,291 prompt tokens.
3. **Sampled decode is not a kernel problem.** The served GGUF path samples on
   the host by default (documented as future work), the sampler costs 1.6x, and
   losing MTP costs 4.3x more than the sampler does.

## 1. The prefix-cache default is a documented decision, not an oversight

`hipengine serve` defaults `--prefix-cache off` while the engine loop defaults to
`radix`. `docs/ENVS.md` and `benchmarks/README.md` both stated that `hipengine
serve` defaults to `radix`, and commit `04b879ad3` ("enable radix prefix caching
by default", 2026-09-19) changed `EngineLoopConfig` and the public prose without
touching the server. That combination reads as an omission.

It is not one. `docs/REFACTOR.md` carries the decision and its removal condition:
"HTTP default-on is blocked by these numerical results and missing INT8/fp32
prefix-reuse qualification. Keep HTTP `--prefix-cache off` as the default, with
explicit radix opt-in." The blockers are measured on W7900/gfx1100, which is the
project's default hardware:

- `benchmarks/results/2026-09-20-w7900-gfx1100-prefix-gate-bf16.json`: of eight
  category/heldout scopes only the two `completed`-lifecycle `general_ja` scopes
  pass all eight binding terms; the six `active`-lifecycle scopes fail the
  scheduler state-byte comparison with 120 final-state component mismatches, and
  `heldout-code` exceeds the section 6.1 mean-KL (`2.264e-3` vs `1e-3`) and max-KL
  (`0.2753` vs `0.05`) ceilings.
- `benchmarks/results/2026-09-20-w7900-prefix-completed-code-control.json`: the
  completed-source parent control has exact scheduler state and 100% top-1, but
  mean/p99/max KL of `0.00678/0.12955/0.67657` still exceed the calibrated
  limits. Root cause is unlocalized.
- The A2 packet recorded in the `GGUF RadixCache production admission` ledger row
  rejects the agentic economics on the same host: radix hits only 0/12, 3/24 and
  3/18 C1 turns, regresses active-SSE goodput 64.19%/65.63%/26.64%, and worsens
  tool-ready latency 181.90%/196.09%/38.81%.

An earlier worker attempted exactly this default flip on 2026-09-20
(`worklog/entries/20260920T085126.388074Z-readme-v060-http-prefix-default-fb301a.md`),
passed 58 focused tests plus all 635 server integration tests, and withdrew it on
these results. This entry does not reopen that decision; it fixes the
documentation that contradicts it. `docs/ENVS.md` and `benchmarks/README.md` now
state the server default, the engine-loop default, the measured gfx1100 blocker,
and the removal condition.

The default was flipped during this unit and reverted after the ledger entry was
read. The reverted state is what is committed.

## 2. No 512-token MTP boundary exists

A report from another host concluded that "MTP stops engaging past ~512 context
tokens" and attributed it to a fixed native target-graph bucket. Measured on
`gfx1151`, `Qwen3.8-27B-Q4_K_M`, BF16 KV, candidate budget 3, one server process,
unique per-case prompts so a prefix hit cannot be confused with a length effect:

| endpoint | prompt tokens | route | acceptance |
| --- | --- | --- | ---: |
| `/v1/completions` | 128, 512, 600, 1,024, 1,025, 2,048, 4,096, 8,192 | `speculative_mtp`, `used=true` | 0.79-1.00 |
| `/v1/chat/completions` | 917, 1,738, 5,674, 11,291 | `speculative_mtp`, `used=true` | 0.58-0.89 |

Every row reports
`decision_reason=qualified_automatic_realized_singleton_c1_b3`. The adapter's own
source states the bound and why: `hipengine/generation/qwen35_gguf_mtp2.py`
computes `max_context = min(target.target_layout.max_sequence_length)` with the
comment "The 1,023 admission window is gone: it was a guard over unmeasured
territory, not a capability bound."

What the same probe did reproduce is the two refusals that look like "the server
picked MTP and the engine ran AR":

- `ignore_eos=true` on an otherwise greedy request ->
  `sampling_mode_not_qualified`. `speculative_mtp_sampling_blockers` lists
  `ignore_eos` as a greedy-route blocker; `SAMPLED_MTP_SERVABLE_BLOCKERS` lists it
  as servable on the sampled route, which is not promoted for this scope.
- `temperature=0.7, top_p=0.95` -> `automatic_mtp_scope_not_promoted`.

The other host's report did not read `hipengine.speculative_mtp.execution`, which
carries `activation_reason`, `provider_decline_reason` and `plan_reason`. The
server-level `decision_reason=backend_k0_fallback` only says "the route was
selected and no draft tokens were used"; it names no cause.

Three places still described the removed window as current behaviour, and the
atlas launcher shipped a dead knob:

- `benchmarks/atlas-agent/serve-hipengine.sh` told readers the adapter admits only
  inside 1,023 tokens, named the deleted `_MTP2_QUALIFIED_CONTEXT_WINDOW`, and its
  `FORCE_LONG_MTP=1` branch exported the inert `HIPENGINE_MTP2_MAX_CONTEXT_TOKENS`
  and passed a `--max-context-tokens` the base command already passed.
- `benchmarks/atlas-agent/README.md` carried the same claim in prose, an example
  command and a knob-table row.
- `benchmarks/atlas-agent/analyze.py` emitted a `LONG-CONTEXT MTP` caveat into
  every artifact saying the hipEngine arm is autoregressive at agentic lengths.

All three now state the measured admission range. `docs/REFACTOR.md` records the
removal under the existing long-context-window section.

## 3. Sampled decode is a wiring gap, not a kernel gap

The other host measured 1.25 tok/s at `temperature=0.7` against 8.95 tok/s
greedy. Measured here with MTP disabled per request so both arms run the same
autoregressive decode, 1,700-token prompt, 48 tokens, from the server's own
`REQUEST_INFO` accounting:

| arm | decode tok/s (two runs) | versus greedy AR |
| --- | --- | ---: |
| greedy AR | 10.69, 10.63 | 1.00x |
| sampled AR (`temperature=0.7`, `top_p=0.95`) | 6.71, 6.78 | 0.63x |
| greedy with MTP (policy `auto`) | 28.68, 29.75 | 2.69x |

So the sampler costs 1.6x and losing MTP costs 4.3x. The 7x in the other host's
report conflates the two.

Neither is a missing or broken kernel. `hipengine/kernels/hip_gfx1100/sampling/sampler.py`
registers `sample_top_p_temperature_f32_rows_i32`, and `docs/AGENTIC.md` is
explicit that its default-on route covers PARO while "GGUF ... remain[s] future
work for the native route". The GGUF path wires `native_gpu_available` to
`_native_gpu_sampler_requested()`, which reads the env-only
`HIPENGINE_QWEN35_NATIVE_SAMPLER` and returns False when unset, so temperature
sampling reads the full vocabulary back to the host per token.

Turning it on does not work yet. With `HIPENGINE_QWEN35_NATIVE_SAMPLER=1` the same
sampled request fails:

```
POST /v1/completions status=500 code=execution_failed
message=generation execution failed during prefill (request_ids=[2], work_kind=prefill,
state_mutation=partial, cause=ValueError: packed native sampler row 0 exceeds capacity 0)
```

`sample_native_from_packed_logits` raises because `_verify_lm_rows_capacity` is 0:
the native sampler is reading packed *verify* logits from a plain prefill batch
whose verify lm-head rows were never allocated. This matches the 2026-09-11
`benchmarks/CHANGELOG.md` record ("the packed native sampler has capacity 0"). It
is a capacity-wiring defect on the native sampler route, not a defect in the
sampler kernel.

## Changes

- `hipengine/server/api.py`: `_log_pretty_startup_summary` now reports the
  prefix-cache mode and the speculation state beside the KV storage it already
  reported, and the label column widened to keep the values aligned. An operator
  no longer has to probe `/ready` to learn any of the three serving decisions.

  `off` default now carries the reason and a pointer to the ledger entry, so the

  ledger decision rather than reading as a stale override.
- `docs/ENVS.md`, `benchmarks/README.md`: the prefix-cache default is stated per
  entry point, with the gfx1100 blocker and the removal condition.
- `benchmarks/atlas-agent/`: the removed MTP window is no longer described as
  current, and the dead `FORCE_LONG_MTP` knob, its provenance line and its
  `analyze.py` caveat are gone.
- `docs/REFACTOR.md`: records the atlas residue removal and corrects a sentence
  that still asserted the adapter window refused long prompts.
