# packet5 requested-depth reporting on SpecRequestPlan

## Summary

The campaign admission contract ("min(requested, qualified) admission
may still cap a request, but must report that cap and cannot count as
deeper-depth execution evidence") is now reportable end to end:
`SpecRequestPlan` carries `requested_candidate_counts` (the pre-bounding
desired depth) alongside `candidate_counts` (the admitted depth), the
policy passes the desired tuple at every construction site, and the
engine-loop observability snapshot exposes both in
`recent_speculative_plans` and `last_speculative_plan`.

## Changes

- `hipengine/speculative/frontier.py`: new defaulted
  `requested_candidate_counts` field; defaults to `candidate_counts`
  for legacy construction sites; validated for alignment/non-negativity.
- `hipengine/speculative/policy.py`: all three `SpecRequestPlan(...)`
  sites pass `requested_candidate_counts=desired`.
- `hipengine/generation/engine_loop.py`: observability records include
  both counts.

## Validation

- RED-first: `test_policy_reports_requested_depth_alongside_admitted_cap`
  failed with AttributeError before the field existed; GREEN after.
  The test pins: a K7 request capped by a 3-candidate capability reports
  (7,) requested vs (3,) admitted; unbounded admission reports equality;
  suppression zeroes the admitted count while preserving the request;
  the legacy defaulted path reports requested == admitted.
- Existing suites unchanged: specdec2 policy (19), engine loop (17),
  simulator matrix + cycle simulator + C1 depth matrix all pass.
