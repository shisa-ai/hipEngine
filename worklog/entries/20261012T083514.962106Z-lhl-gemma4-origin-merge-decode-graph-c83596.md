# Merge origin/gemma4 decode-graph default and validate gfx1100 on W7900

## Summary

Merged the eight `origin/gemma4` commits through `094b5ef99` (whole-step decode
graph on by default in the generation loop and the campaign bench, the flash
kernel's device-resolved live-extent slot, capture window of 2176 keys, three
Radeon 8060S benchmark rows) into the local branch at `72e010479`, and
validated the result on the W7900.

On the W7900 the merged tree generates the same public ids as the pre-merge
tree at 512, 8192, 32768 and 65536 prompt tokens, with prefill and decode
level: 3748.5 / 3337.0 / 2612.1 / 2073.2 prefill and 70.38 / 70.51 / 53.71 /
41.46 decode tok/s, against 3756.1 / 3363.9 / 2635.3 / 2073.2 and 70.86 /
71.09 / 53.69 / 41.63 measured at `72e010479` on 2026-10-10 (production, BF16
KV, 128 outputs, one warmup and three samples,
`scripts/gemma4_campaign_bench.py`, `public_path_parity` true on every row).

The decode graph does not pay on this device. With
`HIPENGINE_GEMMA4_DECODE_GRAPH=1` against `=0` at the default window, decode
reads 75.46 against 76.45 tok/s at 256 prompt tokens (0.987x), 70.38 against
70.36 at 512, 76.14 against 76.60 at 1024 (0.994x), 69.51 against 74.44 at 1536
(0.934x) and 69.08 against 74.57 at 2048 (0.926x; a repeat read 69.10 against
74.56), with equal generated ids wherever both artifacts were kept. The capture
window is therefore a backend capability now: `hip_gfx1100` declares
`GEMMA4_DECODE_GRAPH_CAPTURE_MAX_KEYS = 0` and its decode steps stay launched;
every other backend keeps the 2176-key default. After that change the default
path reads 73.95 decode tok/s at 2048 and 70.36 at 512, ids equal to the
graph-off runs.

## Changes

Conflicts, five files:

- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention.hip`: the local branch
  had moved the flash request ahead of the resident-bound check; kept that
  order and passed origin's `live_extent` argument through it.
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention.py`: kept
  `flash_request_slices` as the request count and added origin's live-extent
  slot lookup after it.
- `hipengine/runtime/gemma4_decode_graph.py`: origin's capture-window guard,
  then the local bounded sliding-cache rebase, both ahead of staging.
- `tests/test_unit_gemma4_decode_graph_workspace.py`: kept the local
  reservation model. `benchmarks/CHANGELOG.md`: both sides, in date order.

Changes beyond conflict resolution:

- `hipengine/runtime/gemma4_decode_graph.py`: `_capture_max_keys(backend)` and
  `CAPTURE_MAX_KEYS_CAPABILITY`; `hipengine/kernels/hip_gfx1100/__init__.py`
  declares the gfx1100 value with its measurement.
- A capture failed on the W7900 with HIP error 900. The local reservation can
  call `Gemma4AttentionScratch.buffer` twice for one layer, the second call
  retires the first buffer behind a stream event, and `buffer` then polls that
  event from inside the recording, which HIP refuses on a capturing stream.
  `Gemma4AttentionScratch.settle` waits for and frees retired buffers, and
  `_capture` calls it before `stream_begin_capture`. The two capture unit tests'
  fake runtimes now refuse an event query while capturing.
- The device re-derives the flash slice count as `flash_slices(live)` under a
  live-extent slot, while a launched step carries `flash_request_slices`. They
  are equal for every key count up to 2176 on both packings (first divergence
  at 97,793 keys on the global packing);
  `tests/test_gpu_gemma4_flash_decode.py` pins that over the capture window.
- Unit tests that were failing on `origin/gemma4` itself, checked in a scratch
  worktree at `094b5ef99` (14 failures in three files): the fake runners in
  `tests/test_unit_gemma4_campaign_bench.py` and
  `tests/test_unit_gemma4_contracts.py` cannot hold a graph session, so those
  files pin the launched loop with `HIPENGINE_GEMMA4_DECODE_GRAPH=0`; the fake
  weights in `tests/test_unit_gemma4_merge_ownership.py` gained `layers`.
- `docs/REFACTOR.md`: the per-backend window, and a new entry for the missing
  gfx1100 registration refresh hook. `docs/ENVS.md`, `benchmarks/README.md`,
  `benchmarks/CHANGELOG.md`, and the artifact
  `benchmarks/results/2026-10-12-gemma4-gfx1100-origin-merge-validation.json`.

## Validation

- Default unit tier: exit 0 on the merged tree.
- `tests/test_gpu_gemma4_decode_graph_capture.py` on the W7900: replayed logits
  byte-equal to launched decode at 60-131 keys, at 1024 and 2048 prompt tokens,
  and at 16384 with the window lifted; 4096 takes the launched fallback. Each
  of the three tests was run as its own pytest invocation. Run together, the
  second and third fail at model load with `MissingRuntimeProfilePlanError`:
  the gfx1100 backend package has no `register_backend_kernels` hook, so
  kernels removed by the registry-isolation teardown are not refilled. That is
  recorded in `docs/REFACTOR.md`; it does not occur outside pytest.
- Gemma 4 attention, flash decode, staged prefill, long-decode parity,
  Q8_0 T16 prefill and MoE gather GPU test files on the W7900: pass. The two
  tests in `tests/test_gpu_gemma4_kv_restore.py` skipped (their artifact guard
  did not resolve the model) and were not run.
- `python3 audit/audit.py check` and `python3 scripts/docs/check_all.py` pass.
- Nothing here ran on gfx1151. The changes that reach that backend are the
  conflict resolutions above, `settle` before capture (a no-op unless a buffer
  was retired), and the four-wave f16w launch from the previous unit.
