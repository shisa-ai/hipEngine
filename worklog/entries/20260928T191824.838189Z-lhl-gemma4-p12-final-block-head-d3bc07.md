# Gemma 4 P12 landed: lm_head restricted to the final prefill block

## Summary

P12 is landed. `Gemma4Runner.forward` forwarded a prompt as consecutive
512-token blocks and ran the final norm, the vocab-wide projection and a
device-to-host copy of the logits **for every block**, while the loop kept only
the last block's array and overwrote the rest. That is 1 wasted block-head at
1024 tokens and 7 at 4096. The head now runs only on the block whose logits
survive.

P12's estimate was ~1 ms / ~6.7 ms. Measured on the XTX primary lane:
`lm_head` **7.8 -> 1.0 ms at 4096 (-6.9 ms)** and **2.0 -> 1.0 ms at 1024
(-1.0 ms)** -- the census counts exactly the launches removed.

The change is output-neutral by construction (the surviving block computes the
same values on the same inputs) and confirmed by measurement: the teacher-forced
gate returns KL **identical to the recorded run to every digit**.

## Changes

- `hipengine/runtime/gemma4.py` -- `forward` computes the index of the final
  block once and passes `needs_logits` down through `_forward_block` into
  `_forward_block_inner`. A block that does not need logits advances
  `self._position` and returns an empty array before the norm / projection /
  D2H section. Decode is unaffected: a decode block holds one token, so it is
  always the final block and `needs_logits` is already true.
- `tests/test_unit_gemma4_runner_lifecycle.py` --
  `test_multi_block_forward_takes_the_head_only_on_the_final_block` stubs the
  module-level kernels and counts norm and projection calls across a two-block
  forward. RED first (2 calls), GREEN after (1 call).
- `docs/campaigns/GEMMA4-26B-A4B-PUNCHLIST.md` -- P12 status `open` ->
  **landed**, with the census A/B, the totals and the gate result.

## Finding: two unit-tier Gemma4 generate tests hang indefinitely

Discovered while trying to exercise the change through the user surface, and
**confirmed pre-existing**: with `hipengine/runtime/gemma4.py` restored to HEAD
those tests hang identically.

`tests/test_unit_gemma4_generate.py` has 5 tests. Three are HIP-gated:

| test | result |
| --- | --- |
| `test_llm_generate_reaches_the_gemma4_generator` | **hangs** (> 240 s, killed) |
| `test_llm_generate_honours_max_tokens` | **hangs** (> 75 s, killed) |
| `test_llm_max_sequence_length_reaches_the_gemma4_generator` | passes |

A `faulthandler` dump at the hang puts the thread inside `hipMemcpy`:

```
hipengine/core/hip.py:114        memcpy
hipengine/core/memory.py:185     copy_device_to_host
hipengine/runtime/gemma4.py:907  _forward_block_inner   (the logits D2H copy)

hipengine/runtime/gemma4.py:691  forward
hipengine/generation/gemma4_gguf.py:179  generate_detailed
```

It blocks in the device-to-host copy of the logits during `LLM.generate` on the
**synthetic fixture** model. The same call on the real artifact returns in 5.2
s, and the campaign bench and the gate both run normally on this GPU, so the
device is healthy -- the fixture-driven path is what hangs.

This is not P12's scope and this entry does not fix it, but it is recorded here
because it is a real blocker: the unit file that exists to prove `LLM.generate`
reaches the Gemma 4 generator cannot currently be run to completion, and anyone
running that file burns 40 minutes before `timeout` fires.
