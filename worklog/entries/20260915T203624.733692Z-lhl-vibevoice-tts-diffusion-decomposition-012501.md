# Diffusion stage decomposes: 83% head forward, 17% host solver loop; CPU enqueue is not the bottleneck

## Summary

The diffusion stage (1.373 s, 32% of warm synthesis) is the largest single stage.
Iteration 33 established it is not GEMV-bound (~1.0 ms/step of a 2.75 ms/step).
This entry decomposes the remaining cost with isolation and instrumentation rather
than a profiler, and finds no single dominant culprit: **`forward()` -- the head's
42 kernels plus its D2H readback -- is 83% of the stage**, the **host-side solver
loop is 17.1%**, and **CPU enqueue is only 26% of the step**, so the stage is not
host-launch-bound either. The one cleanly bounded opportunity is the host solver
round-trip (8.5 ms/frame, ~5% of warm), which needs the CFG combine and DPM step
moved onto the device.

## Changes

No code change. One immutable worklog entry.

## Validation

### The stage cost is real, not a timer artifact

`sample_speech_tokens` measured in isolation (warmup, then best of 3 x 25 calls,
one `device_synchronize()` around the whole loop):

```
sample_speech_tokens isolated : 49.891 ms/frame   (2.495 ms/step over 20 steps)
bench diffusion_seconds       : 54.900 ms/frame   (2.745 ms/step)
ratio isolated / bench        : 0.909
```

The bench timer runs ~10% higher because it wraps the call in `_sync()` and carries
in-loop work. The stage is genuine.

### Decomposition

`forward()` is called once per solver step, so 20x per frame:

```
forward() alone (head device work + D2H) :  2.069 ms/call
  20x forward()                          : 41.382 ms/frame   (83%)
full sample_speech_tokens                : 49.891 ms/frame
  -> host solver-loop overhead           :  8.509 ms/frame   (17.1%)
```

The 17.1% is the host round-trip: `sample_speech_tokens` splits `raw_eps` with
`np.split`, computes `bf16_round(uncond_eps + bf16_round(cfg_scale * (cond_eps -
uncond_eps)))` in NumPy, concatenates, runs `DPMSolverMultistepScheduler.step` on
host, and re-uploads `combined` for the next step. That is 20 D2H syncs and 20 H2D
uploads per frame, 500 of each per session, with the GPU idle during the host math.

### CPU enqueue is not the bottleneck

Wrapping every callable in `dh.kernels` and accumulating CPU enqueue time over one
20-step solve:

```
840 launches / 20 steps = 42.0 launches/step
CPU enqueue            = 0.648 ms/step  (26% of the 2.495 ms/step device wall)

kernel                                 calls/step   us/step  us/call
dense_gemv_out_bf16                          22.0     0.271     12.3
silu_mul_separate_out_bf16                    4.0     0.127     31.8
vv_diff_silu_bf16                             6.0     0.124     20.6
vv_diff_rmsnorm_modulate_bf16                 5.0     0.063     12.5
vv_diff_gated_residual_bf16                   4.0     0.049     12.3
vv_diff_add_bf16                              1.0     0.014     14.4
```

The CPU spends 0.648 ms enqueueing work that occupies the device for 2.495 ms, so
the device is the limiter. Note `dense_gemv_out_bf16` is 22 of the 42 launches and
0.271 ms of the 0.648 ms of CPU enqueue time.

### Where the remaining 83% sits

Per iteration 33, the 22 GEMVs total ~1.02 ms/step at `_GEMV_THREADS = 64`. Against
`forward()` at 2.069 ms/call, that leaves ~1.05 ms/call across the ~20
elementwise/normalisation kernels -- on tensors of only `2 x 1536` elements, where
73 us per launch is far above the arithmetic. This is device-side per-kernel
overhead across many very small kernels, not bandwidth and not host launch cost.

## Next

Two bounded options, in order of cleanliness:

1. **Move the CFG combine and DPM solver step onto the device**, keeping `eps` and
   `speech` resident across all 20 steps and doing one D2H per frame instead of 20.
   Worth up to 8.5 ms/frame (~0.21 s, ~5% of warm). The registered primitives
   `vv_diff_cfg_combine_bf16`, `vv_diff_mul_bf16` and `vv_diff_add_bf16` already
   exist, so this is dispatch work plus a device-side DPM update, not new math.
2. **Cut the per-kernel overhead on the elementwise kernels** (fuse the
   norm+modulate+silu chains, or raise work per launch), which targets the larger
   ~1.05 ms/call but needs per-kernel `rocprofv3` durations to confirm the split
   between execution and launch gap.

Neither should be attempted without first re-deriving the earlier "diffusion sits at
45% of its weight-traffic floor" claim, which iteration 33 showed measured the wrong
quantity.
