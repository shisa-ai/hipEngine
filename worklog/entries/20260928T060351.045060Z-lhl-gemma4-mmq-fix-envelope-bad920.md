# the MMQ gate-up route is the first defect and its row handling is where the fix goes

## Summary

`20260928T060111` established the gate/up MMQ route as one of two independent
row-count divergences, and `20260928T060316` pinned it as an xfail. This unit
reads the route's row handling to bound the fix. It is a checkpoint: no cause is
claimed yet.

## What the route does per call

`gemma4_project_experts_gate_up_mmq` is a *preference-chain* entry above
`gemma4_project_experts_rows`, so a caller entering at the latter never reaches
it. Per call it:

1. packs the call's `compact_rows` activations into `mmq_workspace`
   (`pack_activations(x_ptr, workspace.ptr, compact_rows, in_features)`),
2. rebuilds the tile map from the live `expert_start`
   (`qwen35_moe_mmq32_tile_map(..., num_experts, tile_capacity=...)`),
3. reads `total_rows` back to the host and rejects it if
   `total_rows <= 0 or total_rows > tile_capacity * 32`,
4. launches `mmq_gate_up` with **both** `compact_rows` and `total_rows`.

Steps 1 to 3 are live: the pack is sized by the call's `compact_rows`, the tile
map is derived from the call's `expert_start`, and the bound is checked. That
rules out the obvious "capacity leaked into the work" mechanism, which is what
the earlier candidates were.

## The one cached object

```python
if not scratch.mmq_identity_ready:
    # The pack reads compact rows in compact order, so the tile walk's
    # compact-to-source map is the identity over the scratch capacity. It is
    # written once per scratch object, not once per layer.
    arange = np.ascontiguousarray(np.arange(scratch.total_lanes, dtype=np.int64))
    copy_host_array_to_device(identity, arange, runtime=runtime)
    scratch.mmq_identity_ready = True
```

`identity` is `arange(capacity)`, written once and reused. That is consistent
with the comment -- a fixed permutation over the capacity -- and it is not by
itself a defect, because `total_rows <= lanes <= capacity` so every index the
tile walk uses is populated. It is recorded because it is the only state the
route carries between calls, so it is the only place a *first-call* shape could
be baked in. If the tile walk ever consults it beyond `total_rows`, or if the
pack's ordering is not in fact the identity, this is where that would surface.

## Geometry, and why the fixture is a degenerate case

The existing true-geometry test's own docstring is the warning:

> A route can hold at a toy geometry and fail at the real one whenever a stride,
> a block count or a column tile is derived from a shape that the toy makes
> trivial: ``256`` input features is one Q4_K block per row and ``88`` is a full
> row of Q8_1 blocks, while the real row is eleven Q4_K blocks and 88 Q8_1 blocks
> with an odd block count.

At the fixture's geometry this route runs at its most degenerate point in **two**
dimensions at once:

| quantity | fixture | real (26B-A4B) |
| --- | --- | --- |
| `in_features` | 256 | 2816 |
| Q4_K blocks per row | **1** | 11 |
| fused gate/up width (`2 * intermediate`) | **128** | 1408 |
| column tile (128 wide) | **1 tile, no partial** | 11 tiles |

So the fixture's `intermediate=64` gives a fused width of exactly one 128-wide
column tile with no partial block, and `in_features=256` gives exactly one Q4_K
block per row. The route's own comment in the Q5_K twin notes the same shape of
issue: *"Gemma 4 26B-A4B's 704 (5 x 128 + 64) therefore runs; the fused width
1408 is 11 x 128, so the grid has no partial block either."*

**This is the open question that decides the fix's scope.** If the row-count
dependence comes from the degenerate column tile or the single Q4_K block, it
may not affect production prefill at 2816/1408 at all -- in which case the
correct action is to fix the fixture-geometry case *and* confirm production is
unaffected, rather than to treat a production route as broken. If it survives at
the true geometry, production prefill is affected and the route needs the fix
before it can stay on by default.
