# the DS4 fp16 pack saturates instead of emitting inf

## Summary

The DS4 expert down routes now pack their activations in the **fp32** activation layout, which
the codebase already had for exactly this case and which its own struct comment names:
"Range-safe counterpart used for post-SiLU selected-down inputs." A down projection's input is
a GeGLU output, so that is the layout it belongs on. The fp16 layout stays on the gate/up
route, whose input is a hidden state, and now clamps rather than overflowing.

This was not a theoretical defect. The gemma4 test fixture's own GeGLU output reaches
**7.6e7**, which is **9.1x** past what an fp16 scale can hold, and the route turned that into
NaN on every output. Nothing caught it before because no down route had ever been exercised on
that fixture: the fixture's expert down is Q8_0, the Q5_1 route accepted only Q5_1, and the
Q8_0 route did not exist until the previous unit.

The loop's 512/128 prefill metric is unchanged at **0.876 s** (584 tok/s) against the 0.88 s
measured before this change, so the wider activation block costs nothing measurable.

## The failure chain, in full

It took a while to find because the symptom is four steps away from the cause:

1. A down projection's input is a GeGLU output. The fixture's reaches 7.6e7.
2. The DS4 pack computes `scale = max_abs / 127` and stores it as **fp16**. Past 65504 that
   converts to **inf**, so `amax` past `65504 * 127` (about 8.3e6) overflows. Q5_1 runs out
   far sooner, because its `m * xs` term needs the *block sum* to fit fp16 as well and 32
   values of 2048 already exceed it.
3. The consumer evaluates `d * xd * dot`. With `xd` inf that is inf where the dot is nonzero
   and **NaN where it is zero** -- and in the fixture the weight's `d` is zero for those
   blocks, so the result is NaN rather than inf, with no infs anywhere to point at the cause.
4. A NaN in the expert output flows into the residual stream. The next layer's router turns a
   NaN logit into its **-1 no-expert sentinel** for every lane, so `expert_start` is all zeros
   and the following gate/up call sees an empty expert range and raises.

That last step is why the failure looked like a gate/up bug: `test_reset_rewinds_the_cache`
died in `gemma4_project_experts_gate_up_mmq` with "tile row count 0 is outside capacity",
which is nowhere near the projection that was actually broken.

## Changes

- `hipengine/kernels/hip_gfx1100/quant/gguf_q4_k_q8_1_selected_prefill.hip`:
  - The fp16 DS4 pack clamps its scale and its block sum to the largest finite fp16
    (`kDs4Fp16Max`) before the conversion. Clamping *before* the quantization is what makes
    the saturated `q` and the stored scale agree, so the reconstruction stays finite and its
    error stays bounded by the quantization step -- the contract the MMQ family claims.
  - The fp32 DS4 pack rounds its block count **up** and bounds its read, so it can pack a
    partial trailing block. It floored before, which silently dropped the last 64 columns of a
    704-wide contraction -- the same defect the Q5_1 consumer hit once already, on the other
    side of the same format.
- `hipengine/kernels/hip_gfx1100/quant/gguf_q4_k_q8_1_selected_prefill.py`: the f32 pack's
  wrapper no longer requires `hidden % 128 == 0`; the kernel handles a partial block now.
- `gguf_q8_0_mmq_selected_prefill.{hip,py}` and `gguf_q5_1_mmq_selected_prefill.{hip,py}`:
  the consumers are templated on the activation scale type, with an fp32-activation twin
  exported alongside each fp16 entry point. The two layouts share their member order, so only
  the stride and the scale reads change.
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_experts.py`: both down routes pack with the
  fp32 layout and consume it. `Gemma4ExpertScratch` sizes `mmq_workspace` as the larger of the
  gate/up's fp16 requirement and the down's fp32 one, instead of the single formula that
  happened to be right for one of them.

## Validation

- **Four route tests**, both quants, at the real 704 -> 2816 geometry and at a magnitude past
  the fp16 range: both within the same envelope (normalized max under 2e-2, mean under 2e-3
  of scale) against an independent dequantized reference. The out-of-range case is the one
  that was NaN, and it asserts the envelope rather than finiteness, because finiteness alone
  would pass a route that saturates: a clamped fp16 pack stays finite and is wrong by 90
  percent, which the runner tests' 5 percent tolerance rejects.
- **Power checks.** Reverting the clamp turns all 90112 outputs of the out-of-range test NaN
  for both quants, and the trailing-block check in the in-range test compares against a
  reference with the last 64 contraction columns removed.
- **gemma4 suite: one failure**, `test_incremental_decode_matches_a_dense_prefill`, which is
  the same single pre-existing failure this suite had before the previous unit. The regression
  this work was opened for is gone: the count went 1 -> 7 -> 3 -> 1 across the two fixes.
- **q8_0 / q5_1 / ds4 selection: zero failures.**
- **Loop metric**: `scripts/gemma4_campaign_bench.py --prompt 512 --output 128 --samples 3`
  gives prefill **0.876 s** (584.4 tok/s), against 0.88 s before the layout change, with
  decode 24.844 tok/s and path parity True.

## Next

- The gate/up route still packs in fp16. Its input is a hidden state, whose magnitude is set by
  the model's own norms rather than by an activation function, and it is the route whose scale
  the clamp now protects. If a model is ever found whose hidden state exceeds 8.3e6, that
  route wants the same fp32 layout, and the template already supports it.
- The Q5_1 down route's own artifact measured its geometry but never its activation range, so
  nothing would have caught this on that route either. The range is now covered by a test for
  both quants.
- `gguf_k_mmq_prefill.hip` has the same fp16 scale conversion in its K-major DS4 pack. It is
  not on the gemma4 expert path; its `d_inv == 0` fallback already avoids the worst case, but
  it has the same latent limit.
