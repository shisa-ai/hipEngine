# V1: the first 4096 gate run — HEAD fails kl_max, and P14 never gated its own trim

## Summary

Punchlist V1 existed because no recorded gate had ever exercised a prefill
block with `keys > 1024`. Every run used `--prefill 1024` or `--prefill 0`, and
the frozen baselines are `--prompt 2048 --prefill 1024`: two 512-row blocks
whose keys land at 512 and 1024, both at or under the sliding window and both
on `attn_fwd`. The baseline for V1 was already frozen
(`teacher-forced-prefilled-p4096-c3ea386af.npz`, 1023 rows, self-gating at
`kl_max` 0.0); what remained was the candidate run.

Ran it on the same GPU and geometry the baseline was frozen on (AMD Radeon Pro
W7900, `--prompt 5120 --prefill 4096 --context 8192`, `ROCR_VISIBLE_DEVICES=0`,
44.6 s). Candidate was HEAD `13564b97d`.

**The gate fails, on `kl_max` only.**

| metric | value | limit | verdict |
| --- | --- | --- | --- |
| kl_mean | 3.707e-4 | 1e-3 | pass |
| kl_p95 | 5.279e-6 | 5e-3 | pass |
| kl_p99 | 1.123e-4 | 2e-2 | pass |
| **kl_max** | **0.217717** | **5e-2** | **fail** |
| top1_rate | 1.0 (0 flips) | 0.99 | pass |

**2 of 1023 rows clear the limit**: row 894 (key 4991) at 0.217717 and row 327
(key 4424) at 0.0832214. Row 254 (key 4351) sits just under at 0.041288, and
every remaining row is at or below 0.0173 with p99 of 1.12e-4. So this is not
broad numerical drift — it is two positions, one of them a clear miss.

Artifact: `benchmarks/results/2026-09-29-gemma4-p4096-p14-gate-w7900.json`.

## P14's own 4096 gate does not cover P14

`benchmarks/results/2026-09-28-gemma4-p14-gate-w7900.json` reports `kl_max`
0.0, `passed: true`, same baseline npz, same 4096/1023/`[4097, 5119]`
geometry — which would read as P14 being bit-exact at 4096. It is not that.

Its candidate is `c41aa2217` (2026-09-29 01:55), while P14's actual trim
`7e9670c9a` landed twenty-five minutes later (02:20).
`git diff c3ea386af c41aa2217` across both attention sources
(`gemma4_attention.hip`, `gemma4_attention.py`) is **empty**. That run compared
identical attention code against the baseline, so `kl_max` 0.0 is the identity
comparison the gate's own docstring warns about, not evidence about the trim.

P14's row claims bit-exactness by argument — a masked key contributes weight 0
to every dimension, so dropping it leaves the ascending-key accumulation
unchanged. That argument is sound and is the same one `key_begin` relies on.
But **the trim has never been run through the 4096 gate**, and the argument is
not a measurement.
