# DE-3 screened: output-pairing is already applied for q8_0 decode, and exhausted

## Summary

DE-3's next step is "screen row-pairing on the largest exact GEMV (attn_qkv)", from
halo-box PR #56's "two output rows per block in MMVQ, bit-exact, +12% TG on the
27B".

**The lever is already applied and exhausted.** The q8_0 decode path already
computes **8 output features per block** - four times the proposed two - and a
sweep of alternative output-tile widths at equal work shows the current tiling is
the best of them.

## The lever is already applied

`launch_gguf_k_pack8_gemv_out`, the kernel the decode census shows at rows=1:

```cpp
const int64_t out_packed = out_features >> 3;   // 8 output features per block
const dim3 grid(out_packed, rows);
```

`attn_qkv` decode (10240 out) already runs 1280 blocks of 8 packed features. The
in-tree `pair` kernels implementing DE-3's idea
(`gguf_q5_k_pair_pack8_decode_out_kernel`, `gguf_q6_k_pair_pack8_decode_out_kernel`)
exist for **q5_k and q6_k only** - there is no q8_0 pair kernel, because q8_0
already packs wider than a pair.

## And widening further does not help

Sweep at `attn_qkv` (2560 -> 10240), rows=1, median of 40 after 8 warmups, sync
both sides. **All variants compute the same 10240 output columns**, so this is
equal work:

| variant | out cols/block | us | vs baseline |
|---|---:|---:|---:|
| **`pack8` (current decode path)** | **8** | **63.70** | **1.00x** |
| `coltile4_rowbatch8` | 4 | 110.52 | 0.58x |
| `coltile8_rowbatch4` | 8 | 80.47 | 0.79x |
| `coltile8_rowbatch8` | 8 | 110.23 | 0.58x |
| `coltile16_rowbatch2` | 16 | 77.01 | 0.83x |
| `coltile16_rowbatch4` | 16 | 211.93 | 0.30x |
| `coltile32_rowbatch1` | 32 | 133.69 | 0.48x |

No monotonic benefit in the output-tile width: narrower (4) is worse, wider (16,
32) is worse, and the best alternative is 0.83x. This is consistent with MT-1's
independent measurement of the same `coltile8_rowbatch4` kernel at rows=1 (0.80x).

## A corrected test, recorded

The first version of this sweep compared the coltile variants at
`out_features=32` against a baseline at `out_features=10240` - **different total
work** - and produced meaningless ratios (0.00x). I discarded it and re-ran at
equal work. The table above is the corrected measurement, and the first run is not
cited anywhere.

## What this does not settle

- **The alternatives carry rowbatch machinery that is dead weight at rows=1.**
  They are prefill-shaped, so this **bounds** the output-tile axis rather than
  isolating it. A purpose-built output-pair kernel with no row dimension was **not
  measured**; the q5_k/q6_k `pair` kernels are the closer structural analogue and
  testing that shape is the honest follow-up.
- **Kernel-level only.** No end-to-end TG, no attention or MoE, and DE-3's 24.73
  ms/token family figure was **not** re-attributed.
- **Not a bit-exactness result** - a timing screen. The coltile variants'
  bit-exactness is covered by
  `test_q8_0_f32_rowbatch32_matches_scalar_prefill_bits`.
- One host, one quant, one shape, one width.
- **No rate was transferred** from the external +12% (different engine, quant, and
  model).

## Next

The honest follow-up, if this lever is still wanted, is a purpose-built
output-pair q8_0 kernel with no row dimension, tested against the current pack8 at
equal work. Everything measured here says the current 8-wide packing is not the
place to look. Task #3 remains open.
