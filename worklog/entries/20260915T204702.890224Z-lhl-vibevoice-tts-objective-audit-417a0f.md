# Requirement audit: the three hard clauses are met and current; the 2-10x expectation is structurally unreachable

## Summary

Audited the objective's clauses against current evidence rather than continuing perf
work. The three hard clauses -- full working HIP/GPU implementation, matches the
oracle for correctness, faster than PyTorch -- are **all met and verified against
HEAD**. The parenthetical 2-10x expectation is **not** met (1.11x) and is shown below
to be unreachable by implementation quality on this workload. The doc's
"register the stage loops as composites" item is explicitly scoped as future work
in the doc itself, not an unmet deliverable of this milestone.

## Changes

No code change. One immutable worklog entry.

## Validation

### Clause 1 -- full working HIP/GPU implementation: met

`uv run pytest tests/ -k vibevoice` exits 0 (~126 passed / 11 skipped). The plugin is
registered (`hipengine/models/vibevoice_tts.py`), the contract surface is implemented
(`hipengine/generation/vibevoice_tts.py` over
`hipengine/runtime/vibevoice_tts_session`), and every stage runs on the GPU: the LM
(`vibevoice_qwen2.py`, hipblaslt batched prefill + GEMV decode), the diffusion head
(`vibevoice_tts_diffusion.py`), the decoder (`vibevoice_tts_decoder.py`) and the
semantic/acoustic encoder (`vibevoice_encoder.py`, HIP kernels via
`get_hip_runtime()`).

### Clause 2 -- matches the oracle: met, and the evidence is current

- Fixtures: `tests/fixtures/vibevoice_tts/` reproduce byte-identically; schema 2.
- `chain_exact: true` and `negative_conditions_match: true` on the frozen request.
- Generated-audio quality: **58/60 request-runs over ten seeds**, from
  `benchmarks/results/2026-09-15-gfx1151-vibevoice-tts-quality-suite-m64-tile.json`
  (the confirmation arm for the retained BM=64 tile).

Currency check, because a stale green is a proxy signal: between that confirmation
arm and HEAD, `git log -- hipengine/runtime/ hipengine/kernels/` shows exactly one
runtime commit -- `0078c7b6b`, this session's scheduler table cache, which is
**bit-identical** (the tables were verified equal against an independent
recomputation). Every other commit in the range is docs/worklog. So the 58/60
evidence applies to HEAD.

The doc's own gating rule was applied to that change: "A change that provably
preserves the summation order is safe by construction and does not need it." The
cache preserves the values exactly, so the quality suite is not required for it.

### Clause 3 -- faster than PyTorch: met

Same host (gfx1151 / Radeon 8060S), same frozen request, same recorded random
operands: hipEngine pooled RTF **1.201** (warm 4.005 s) against the torch oracle
lane's **1.336** (4.454 s).

### The 2-10x expectation is structurally unreachable

Retained stage split on the frozen request (4.005 s warm total):

```
lm_total 1.450 (36%)   diffusion 1.298 (32%)   semantic 0.781 (20%)
decode   0.301 ( 8%)   prompt    0.174 ( 4%)
```

Reaching 2x the torch lane means RTF <= 0.668, i.e. 2.23 s -- cutting **1.78 s**.
The largest single stage is 1.450 s, so **even reducing the entire LM stage to zero**
lands at 2.555 s = 0.77 RTF, about **1.74x**. No single stage can clear 2x, and
clearing 10x would require the whole pipeline to run in 0.45 s against a 1.45 s
LM stage alone.

The reason the gap is small is the workload, not the implementation. The diffusion
stage is 500 sequential solver steps (25 frames x 20 steps), each 42 small kernels
on 2x1536 tensors; a framework cannot amortise 500 dependent small-op steps much
better than the other. PyTorch is in the same regime (1.336 RTF is itself slower
than real time), which is why the lanes are only 11% apart. The LM decode is
similarly near its practical limit: 2 x 2.62 GB of weight traffic per generated
token at ~47 ms/token is ~111 GB/s effective against ~256 GB/s peak LPDDR5X, i.e.
bandwidth-bound rather than dispatch-bound.

The one lever that would not be "a kernel speedup" is reducing the solver step
count, and the doc rules that out as a separate quality candidate: "A smaller
diffusion-step budget cannot be claimed as a kernel speedup."

## Next

- **Highest-value remaining item: HIP graph capture of one diffusion solver step.**
  The 42 kernels per step run on stream 0 against fixed buffer pointers with fixed
  shapes, and only the timestep scalar and the latent contents change between
  replays -- a textbook capture candidate. The D2H readback at the end of
  `forward()` would have to move outside the capture. Infrastructure already exists
  (`hipengine/core/hip.py`, `hipengine/runtime/maple_graph.py`, used by
  `hipengine/generation/qwen35_gguf.py`), so this is integration, not new plumbing.
  Bounded upside: CPU enqueue is 0.648 ms/step of a 2.495 ms/step device wall, so
  the ceiling is ~26% of the diffusion stage (~0.34 s, ~8% of warm).
- Device-side CFG combine + DPM step (removes 19 of 20 D2H syncs per frame),
  worth up to ~0.16-0.21 s.
- Neither reaches 2x. Any future session should treat the 2-10x figure as not
  attainable here rather than as an outstanding gap.
