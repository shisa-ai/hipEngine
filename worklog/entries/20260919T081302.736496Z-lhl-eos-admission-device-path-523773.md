# The EOS admission probe now requires the device-accept path it depends on

## Summary

`runner.speculative_eos_supported(request_id)` is the only way an EOS-bearing
request can relax the shared MTP blocker, and it answered from a *static*
property: the adapter is enabled and the request holds packed one-row physical
ownership. The EOS finish rule it promises is not static. EOS is handled on the
device-accept path, where `_limit_target_batch_eos` bounds the greedy chain so
EOS stays the last visible token; the eager host-proposal path refuses an EOS row
outright (`qwen35_gguf_mtp2.py:4286`,
`EOS requires native device acceptance before selected commit`). That refusal is
deliberate — the 2026-09-07 EOS design entry records "host acceptance without
device-result ownership fails closed for EOS" — but the admission never checked
which of the two paths the cycle would take.

So a statically eligible row at a position where the target graph is not ready
(long context beyond the graph bucket, or a bucket that has not been captured)
was admitted, entered a cycle, and raised; containment then decoded that cycle
autoregressively. The realized output was correct, the admission was not: it
claimed a capability the route it selected could not honor.

The probe now asks the same question the proposal path asks. The adapter gains
`eos_finish_supported(request_id)`: packed one-row physical ownership, a
registered verifier, a graph-supporting target, and the verifier's own
`device_proposal_ready(budget)` — the predicate that reports
`target_graph_context_bucket_miss` and its siblings before any proposal work
launches. A row that fails it stays on `processed` for that cycle, which is an
autoregressive step decided by plan rather than a cycle that raises and is
contained. The probe is consulted only for an EOS-only blocker, so the promoted
automatic route (which never carries one, since the server sends an EOS-bearing
request to K0) is untouched.

No production serving behavior changes: the server's route decision does not
consult this probe, so an explicit-EOS request still resolves to K0/AR. What
changes is the library path, where the relaxation is now honest.

## Next

- With the probe honest, the remaining EOS promotion is a *server* decision:
  `_speculative_mtp_route_for_request` sends any blocker to K0 without asking the
  engine, so clients that pass `eos_token_id` explicitly (or an OpenAI `stop`
  string that lowers to token stops) still decode autoregressively. Admitting the
  EOS-only case would need live token/finish-reason parity between the MTP device
  accept and AR on the same prompts, which this unit does not measure; the engine
  would then fall back per cycle wherever the graph is not ready.
- The eager host-proposal path still refuses EOS rows. Teaching it the same
  bounded-accept rule (`greedy_chain_eos_limit` is host-side and does not need
  device ownership) would remove the fallback for long-context EOS rows, but it
  changes the accept path and needs its own RED contract.
