# Gemma 4 decode attention: key-class kernel keeps 128-warp concurrency and drops the per-key cross-warp round trip (+34% decode)

## Summary

Iteration 21's warp-per-head kernel proved the intra-warp shuffle tree is both
bit-exact and fast, but it paid for that with concurrency: one warp per
`(token, head)` is 16 warps for a decode step against the block kernel's 128, so
it lost on the sliding geometry. This iteration keeps the block kernel's
concurrency and removes the cross-warp round trip from the key walk.

**Eight warps share one `(token, head)`; warp `w` owns the keys `w, w+8, w+16, ...`
and reduces each of their logits with the shuffle-exact 256-lane tree.** Pass 1
therefore has no LDS traffic and no barriers at all. The two cross-warp
reductions move out of the key walk: each warp publishes its own running maximum
and the row maximum is the `fmaxf` of the eight, which is order-independent and
so bit-exact. Pass 2 and pass 3 are the block kernel's own partitions verbatim.

Result: **bit-exact, and faster on both geometries** — 421-428 us against the
block kernel's 652-700 us at sliding/1024 and 665-696 us against 1186 us at
full/1024. Campaign metric **33.0213 tok/s from 24.5964 (+34.3%)**, and +105% over
the campaign's 16.0931 baseline. Public-path parity true.

The key-class kernel wins on **both** geometries, so it replaces the
warp-per-head kernel entirely: that kernel is removed rather than kept as an
unselected variant, and `hipengine_gemma4_attention_decode_variant()` now reports
`class` for `head_dim` 256 and 512 and `block` for every other geometry.

## Why this shape works

- Pass 1 was the whole cost. In the block kernel a key's reduction spans eight
  warps, so each key pays a shared partial row, three LDS tree rounds, a
  publish/broadcast pair and a barrier sequence. Iteration 20's ablations showed
  the per-key cost is invariant to what the key iteration computes, and a
  grid-scaling run showed the machine is ~16x idle (16 blocks 695 us, 256 blocks
  1116 us), so the block kernel's cost was per-block latency, not throughput.
- Splitting keys by warp class keeps 128 warps busy while removing that
  machinery. Each warp evaluates the *whole* 256-lane tree for its own keys, which
  costs 8x more tree work per key than the block kernel's distributed tree - but
  it is issue work, not a barrier-and-LDS round trip, and there is enough
  concurrency to hide it.
- Bit-exactness is preserved by construction and checked: same tree pairs in the
  same order, same pass-2 lane partition, same pass-3 chains.
