# a phase splitter for rocprof censuses, and the overfetch is 3.6x, not 107x

**This entry corrects `20260928T123600.000000Z-lhl-gemma4-prefill-traffic-correction-2d9f8b.md`,
which was itself a correction.** That entry's own headline number was wrong, and the
tool added here is what exposed it.

## Summary

### The tool

`scripts/gemma4_campaign_bench.py` runs a prefill and then a decode loop, so a
profiled run holds both phases in one dispatch stream and summing a counter over the
whole run mixes them. At 512/128 decode is 94.6 percent of the read traffic, so the
mixture is not a rounding error. Two entries in a row reported a "prefill" figure
that was mostly decode before the split was applied by hand.

`scripts/rocprof_phase_split.py` makes the split structural. It reads rocprofv3
counter-collection CSVs, finds the first dispatch of a marker kernel -- by default
`gemma4_attention_decode_class_kernel`, the first thing the decode loop launches that
the prefill does not -- and reports per-kernel totals and dispatch counts either side
of it. Both layouts `rocprofv3 -d <dir> -o <name>` writes are found: the flat one, and
`pass_N/` subdirectories.

Seven unit tests in `tests/test_unit_rocprof_phase_split.py` pin the behaviour that
matters: the boundary is the marker's *own* first dispatch rather than the one before
it, dispatches are assigned by id rather than by file order, both CSV layouts are
found, and a run with no marker says so and lists the kernels it did see instead of
silently reporting one phase.

### The number it corrected

Running the splitter on the census that produced the previous entry reproduces its
hand-applied split exactly -- and adds the per-phase **dispatch counts**, which is what
the hand split had thrown away:

```
=== PREFILL: 97,388,467 counter units over 1,608 dispatches
    q5_1_mmq_ds4_selected_prefill_kernel      38,436,112  39.5%  n=29
    gguf_q4_k_..._mmq32_fused_prefill_compact 29,778,306  30.6%  n=29
    gguf_q8_0_prefill_wmma_kernel             14,023,727  14.4%  n=205
    q8_0_mmq_ds4_selected_prefill_kernel       3,980,879   4.1%  n=1
    gemma4_attention_prefill_kernel            3,232,578   3.3%  n=30
```

**n=29.** The gate/up and down MMQ kernels run once per layer, not once per prefill.
The previous entry compared the prefill's whole fetch against **one layer's** weights
and reported a 107x overfetch. The weights are per layer: 30 layers of gate/up is
7.98 GB and 30 layers of Q5_1 down is 9.75 GB, not 272 MB and 333 MB.

Corrected:

| kernel | prefill fetch | weights, all 30 layers | overfetch |
| --- | ---: | ---: | ---: |
| expert gate/up MMQ32 | 28.40 GB | 7.98 GB | **3.6x** |
| Q5_1 down MMQ | 36.66 GB | 9.75 GB | **3.8x** |
| whole prefill | 95.1 GB | ~18 GB of expert weights | ~5x |

**This corroborates the original entry's 3.4x rather than overturning it**, which is
the useful outcome: the raw-layout overfetch is real, it is about 3.6x, and the
microbench that measured 3.4x was measuring the right thing. The intermediate entry's
"107x" was an arithmetic error about which weights to divide by.

### What this leaves standing

The substantive conclusion of the previous entry survives the correction, because it
never depended on the magnitude: **the overfetch is not what binds.** T16 cut this
kernel's traffic 3.5x (980 MB to 281 MB) and bought 1.13x, and that comparison is
between two modes at the same geometry with the same body, so it is unaffected by how
the weights are counted. A 3.5x traffic reduction for a 1.13x speedup says the kernel
is only weakly traffic-sensitive, and the scalar census is the instrument that named
it the prefill's largest scalar consumer at 6.2x the attention kernel's stream.

Two consecutive corrections is a signal about method, not just about arithmetic. Both
came from dividing a total by the wrong denominator, and both would have been caught
by printing the dispatch count beside the total -- which is what this script now does
by default.

## Changes

- `scripts/rocprof_phase_split.py` (new): split a rocprofv3 counter census by

## Next

- **Use `--top` and the `n=` column together before quoting any counter ratio.** Both
  corrections on this branch were a total divided by the wrong denominator, and the
  dispatch count is what distinguishes "per prefill" from "per layer" from "per
  token".
- The next target remains the scalar stream in the two expert MMQ kernels, not their
  traffic. The Q5_1 down projection is the larger of the two on prefill traffic
  (39.5 percent) and the gate/up is the larger on scalar count, so take both kernels'
  scalar profiles before choosing between them. A per-region attribution is still
  missing -- static instruction counts moved by six instructions across two inert
  source-level rewrites on the attention kernel, so a static count cannot say which
  loop emits the scalar stream.
