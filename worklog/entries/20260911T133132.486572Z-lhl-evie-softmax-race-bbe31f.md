# EVIE softmax shared-memory race: first-call nondeterminism on both f32 and f16 kernels

## Summary

`evie_softmax_rows_kernel` (f32) and `evie_scale_softmax_rows_f16_kernel` (f16)
read the pass-1 row maximum from `sm[0]` and then reused the same `__shared__`
array for the pass-2 partial exponential sums with **no barrier in between**.
A thread that reached `sm[threadIdx.x] = denom` before another thread had
executed `const float mx = sm[0]` made the slow thread pick up a partial sum
instead of the max, corrupting that row's softmax. The result was
timing-dependent and therefore non-repeatable: on the Surya vision tower the
*first* `vision_forward()` call on a freshly constructed runner diverged by
~1e-1 while every later call on the same runner was bit-exact. Adding one
`__syncthreads()` between the max read and the `sm` reuse fixes both kernels.

The f16 variant is the production EVIE attention softmax
(`hipengine/runtime/evie.py`), so the same defect affected the text path, not
only Surya's vision path.

## Changes

- `hipengine/kernels/hip_gfx1100/evie/evie_ops.hip`
  - `evie_softmax_rows_kernel` and `evie_scale_softmax_rows_f16_kernel`: add
    `__syncthreads()` immediately after `const float mx = sm[0];`, with a
    comment naming the hazard. No other change to either kernel; the added
    barrier is the only new synchronization and both kernels are
    latency-insensitive relative to the surrounding GEMMs.
- `tests/test_surya_gpu.py`
  - `test_gpu_vision_first_call_on_fresh_runner` (new): constructs a *fresh*
    `SuryaGpuRunner` three times, asserts each runner's **first**
    `vision_forward` matches the torch oracle within 5e-3 (the fixed path
    measures 3.862e-5) and that the first and second calls on that runner are
    bit-identical. The module-scoped `runner` fixture cannot catch this class
    of bug because it is already warm by the time any test runs.

## Validation

Diagnosis (pre-fix, `HIPENGINE_HIP_ARCH=gfx1151`, `page_small.png` vs
`tests/fixtures/surya/oracle_image.npz:vision_merged`):

- Fresh runner, first call: `max|d|` between 1.9e-2 and 9.1e-1 depending on
  allocation layout; second and later calls on the same runner: 3.862e-5 and
  bit-identical to each other. Varying the number and size of dummy scratch
  allocations moved the first-call error from 3.0e-2 to 9.1e-1, and neither a
  1 MiB scratch pad nor `hipDeviceSynchronize` after every launch changed it.
- Ordering every intermediate through a hook in one run isolated the failure
  to a single op: `b0_norm`, `b0_qkv` and the post-scale **pre-softmax** scores
  were bit-identical between call 0 and call 1, while the **post-softmax**
  scores differed by 6.5e-1. Identical input plus a differing output from one
  launch is only possible if that kernel is internally nondeterministic.
- `rocblas_sgemm_rowmajor_nt` and `rocblas_sgemm_strided_batched` were verified
  bit-repeatable over four identical launches each, ruling out rocBLAS.
- A NaN pre-fill of every scratch buffer left NaN only in the trailing padding,
  proving no op reads a region it never wrote.

Fix evidence:

- RED: with the two barriers removed, the new test fails —
  `attempt 0: first call on a fresh runner diverged: max|d|=3.977e-02`
  (threshold 5e-3).
- GREEN: with the barriers restored, the same test passes, and an explicit
  four-runner loop gives `call0 max|d|=3.862e-05`, `call0 == call1: True` on
  every runner.
- f16 kernel, direct launch probe (`build_evie_ops`, heads=12, tokens=256,
  head_stride=65536, six fresh-buffer launches vs a reference launch):
  - pre-fix: `run 0: bit-identical=False  max|d|=1.614e-03`
  - post-fix: all six runs `bit-identical=True  max|d|=0.000e+00`
- `HIPENGINE_HIP_ARCH=gfx1151 python3 -m pytest
  tests/test_surya_model_contract.py tests/test_surya_oracle_fixtures.py
  tests/test_surya_text_decoder.py tests/test_surya_vision.py
  tests/test_surya_e2e.py tests/test_surya_public_api.py
  tests/test_surya_generation_contract.py tests/test_surya_gpu.py -q`
  → 88 passed.

Not run: the full-weight `tests/test_evie_gpu_runtime_fp16.py` production
gate. The direct kernel probe above establishes the f16 bit-repeatability
property that gate asserts, so the expensive 4.5B-weight run was not spent.

## Next

- **Same defect found in five more kernels by source scan.** A pattern scan for
  "read `X[0]` then write `X[threadIdx.x]` with no intervening
  `__syncthreads()` and a later reduction reuse" reports:
  - `hipengine/kernels/hip_gfx1100/attention/paged_attn_decode.hip` lines 101,
    623, 1800, 2107, 2285 — the production paged attention decode softmax
    reads `const float max_score = partial[0];` and then writes
    `partial[threadIdx.x] = local_sum;` with no barrier in between. This is the
    main text-path decode kernel, so the exposure is wider than EVIE/Surya.
  - `hipengine/kernels/hip_gfx1100/timesfm/timesfm.hip` line 524 —
    `mask_softmax_kernel`, identical structure.
  None of these six sites has been reproduced as an observable failure; they
  are identified from the source pattern only. They need their own unit with
  its own evidence before being changed.
- The f16 production gate (`tests/test_evie_gpu_runtime_fp16.py`) has not been
  re-run since this fix. It asserts bit-repeatability of repeated encodes, so
  run it before the next EVIE production claim.
