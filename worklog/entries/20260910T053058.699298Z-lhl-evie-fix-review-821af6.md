# EVIE fix review: RGB regression and incomplete memory cleanup

## Summary

Reviewed `046f72bdc` against the previous eight findings. The allocation-size
fix and constructor precision guard pass targeted CPU probes. Mask compression
now supplies matching valid-token IDs and positions and returns compact
embeddings as declared in the coder's handoff. The spatial patch order is
corrected, but its new transpose regresses the channel/temporal layout.
Memory cleanup and cache bounding remain incomplete. Consequently the
"all fixed" assessment in
[the coder handoff](20260910T051950.311239Z-lhl-evie-546522.md) is not supported.

### P1: Patch-order fix regresses RGB/temporal layout

`scripts/evie_hip_bench.py:79` emits `(pr, pc, r, c, t, ch, p, p)`.
The model requires each patch flattened as `(ch, t, p, p)`, as established
by `hipengine/kernels/cpu_reference/evie.py:399` and the checkpoint's
Conv3d weight layout. For one RGB pixel the temporal duplication must place
planes as `[R,R,G,G,B,B]`; this fold places `[R,G,B,R,G,B]` instead.
Change the permutation to `(2,5,3,6,1,0,4,7)` and gate both the spatial
permutation and full patch contents using unequal RGB values.

A numbered 4x4 patch grid with channels `[v,80+v,160+v]`, no resize,
unit standard deviation and zero mean differs from independently constructed
block-major/channel-major patches in **16,384 of 24,576 elements (66.7%)**,
maximum absolute difference **0.3137255**. These are preprocessing differences,
not model drift measurements. An equal-channel grayscale image would hide
this permutation. The existing black/white benchmark also cannot expose it.
The reported `5.9e-08` comparison is not bit equality and does not establish
correct RGB layout.

### P1: Four-entry scratch bound leaves other per-shape caches unbounded

`hipengine/runtime/evie.py:1133` bounds only `_scratch`.
`_scores_scratch`, `_scores16_scratch`, and `_plane16_scratch` at lines
319-354 still retain allocations keyed by exact dimensions independently
of that cache. `_rope_cache` and `_ptr_array_bufs` also have no eviction.
The actual token count still reaches attention, so bucketing scratch does
not bucket those keys. A fake-allocator probe for lengths 1-20 leaves one
main scratch bucket but **20 score buffers and 20 plane buffers**. Real
attention uses multiple plane buffers, each with another 1-MiB padding.
Variable-length query/page streams still accumulate memory. Reuse capacities
or bound all caches together and assert a memory plateau across shape changes.

### P2: Pointer-array allocations are still leaked by close

`hipengine/runtime/evie.py:197` frees `_scores_bufs` and `_plane16_bufs`
but omits `_ptr_array_bufs`, explicitly named in the earlier finding. The
strict attention path uses `_dev_ptr_array`, whose allocations each include
1 MiB padding. A mocked owner at pointer 123 remains unfreed after close.
The added weight free does address the primary model-residency leak; it
does not fix this remaining runner-owned leak. Include the third cache and
assert that every owned allocation is released exactly once.

### P2: Repeated close now double-frees model weights

The new unconditional `self.loaded.free(runtime=self.runtime)` at runtime
line 205 is not idempotent. The preceding scratch cleanup clears/nulls its
owners, but `EvieLoadedModel.free()` and `DeviceWeightMap.free()` retain
their allocation entries. Calling close twice invokes the same owning free
twice (confirmed with a mocked weight owner), so overlapping cleanup/finally
paths can issue a second HIP free on released pointers. Add a closed/ownership
guard and document that the runner now owns the loaded weights. Test double
close and successful teardown's return to baseline allocation counters.

### P2: Comparison/certification corrections are only partial

`docs/MODEL-EVIE.md:116` adds an appropriate protocol caveat, but then says
"Same shapes" immediately after stating 12-token versus 20-token queries.
`benchmarks/README.md:110` still says the production path "beats torch fp32"
without that caveat. The model document also retains "strict fp32 fallback
registered" and bounds from a "recorded manifest" despite acknowledging no
EVIE resolved production manifest. The matched protocol and profile gate are
deferred, not fixed. Remove unsupported same-workload/certification language
consistently from current exports and retain qualification as open work.

### Validation coverage remains the central gap

The fix commit adds no regression tests. The unchanged all-valid, single-page
fixture suite cannot cover color-plane permutation, allocation accounting,
double-close, mask compression, or bounded caches. Preserve the passing
single-fixture GPU evidence, but add tests specifically asserting repaired
contracts before closing these findings. The strict loader's padding remains
`np.empty` rather than explicitly initialized; the element-count fix is valid,
but zero-filled-tail claims still need an implementation/test correction.
Historical host-panic attribution is plausible, not causally established by
this review; no crash reproducer was run.
