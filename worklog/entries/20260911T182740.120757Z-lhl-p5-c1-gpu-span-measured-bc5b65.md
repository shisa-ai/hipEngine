# The C1 decode step window is exactly the GPU span; 53% of it is inter-kernel gap

## Summary

The previous unit could only *infer* the ~35 ms GPU span, as wall minus host time.
That was not solid enough to drive a kernel-fusion plan, so this unit measures the
span directly by re-parsing the existing committed trace (`--trace-dir`, no new GPU
run):

| Quantity | Per step |
| --- | --- |
| Span (first kernel start to last kernel end) | 36.434 ms |
| Busy (device union inside the span) | 17.110 ms |
| Interior gap | 19.421 ms |
| Leading gap | 0.0 ms |
| Trailing gap | 0.0 ms |
| Duty cycle | 0.4696 |

The zero edges are the load-bearing result. Leading and trailing gaps being zero
means the measured step window *is* the GPU span: the window starts at the first
kernel launch and ends at the last kernel's completion, so the host's Python sits
*between* launches rather than outside them. No host-side reordering outside the
launch sequence can help.

That reduces the optimization target to one number: **cut the 19.421 ms/step of
interior gap (53.3% of the span)** by removing host-in-the-loop launch points —
fusion (fewer, larger kernels) or a captured graph replay (same kernels, no
per-launch host cost). Graph capture already exists on the c8 packed route while
the C1 route is eager.

## Changes

- `scripts/gguf_c1_decode_attribution.py`: `summarize()` gains a `gpu_span` block
  partitioning each window into leading gap, span, and trailing gap, and each span
  into busy time and interior gap.
- `tests/test_gguf_c1_decode_attribution.py`: 2 new tests (35 total) asserting the
  span partitions the window and that a window holding no kernels contributes no
  span, so an empty window cannot inject a zero that drags the medians down.
- `benchmarks/results/2026-09-11-w7900-p5-c1-decode-gpu-span-measured.json` (new).
- `benchmarks/CHANGELOG.md`.

## Validation

- `uv run pytest tests/test_gguf_c1_decode_attribution.py -q` — 35 passed.
- Re-parse of the committed W7900 / gfx1100 trace, 62 step windows, 2048 prompt
  rows, Qwen3.8-27B `Q4_K_M`, INT8 KV. Values above.

One test-writing note worth keeping: the first version of the span tests used
nanosecond-scale synthetic intervals, and `round(value, 3)` in the millisecond
conversion collapsed 0.0003 ms to 0.0, so the assertions failed on the rounding
rather than on the logic. The tests now use millisecond-magnitude inputs.

Honest limits, recorded in the artifact:

- The span comes from profiler clock timestamps. Leading and trailing gaps of
  exactly 0.0 ms are consistent with the ROCTx marker being pushed immediately
  before the first launch and popped immediately after the last kernel, but a
  sub-microsecond gap would round to zero at the reported precision.
- One trace, one prompt length (2048 rows), one width (C1). The duty cycle may
  differ at other depths, where attention kernels grow and the launch mix changes.
- Interior gap is not yet decomposed into launch latency versus host Python between
  launches, so this does not say how much of the 19.421 ms a graph replay would
  remove versus how much needs fewer kernels.
- No optimization was attempted.
- `performance_claim` is false and no scoreboard row changed.
