# KV state identity is caller-named fields, not a commit binding

## Summary

The first KV-restore run after a new commit refused its own state:
`engine_commit` was part of the identity, so every commit -- including
decode-only or documentation changes -- invalidated every minted state. That
defeats the harness's purpose, which is to iterate decode work at depth across
engine revisions without re-paying the prefill.

The binding is now what the caller says it is. `restore_kv_state`'s identity
check is a requirement, not a full-record comparison: every key the caller
passes must be present with the same value in the file's identity, and keys the
caller does not name do not participate. The harness binds a state to the
fields that actually determine its bytes -- prompt-id hash, artifact head
hash, context, output width -- and records the engine commit in the artifact
as provenance instead. A prefill arithmetic change that could change the bytes
cannot land without the strict-parity or execution-profile gates, and the
harness's own restored-vs-fresh ID comparison would catch any drift loudly.

Measured consequence: the 65536 state minted at commit `1117be219` restored
and decoded under `3b3d612c2`, and its 128 greedy IDs are identical to the
mint-time fresh decode's -- cross-build bit-exactness of the decode path
proven at depth, and the singleton unroll's parity claim confirmed end to end
against a different build.

## Changes

- `hipengine/runtime/gemma4.py`: `restore_kv_state` compares the caller's
  identity dict as a subset requirement against the file's; docstring updated.
  A null file identity with a caller requirement is still a mismatch.
- `scripts/gemma4_kv_restore_bench.py`: the harness identity drops
  `engine_commit` (moved to the artifact as provenance).

## Validation

- `pytest tests/test_gpu_gemma4_kv_restore.py`: 2 passed (the mismatch and
