# the port forks and the branch that keeps the bit exact gate cannot fix the measured case so it lands as two registered variants

## Summary

`20260928T073956` recommended "tile the buffer, keep the reduction tree and the key-visit
order, and the existing bit-exact gate keeps passing". **Counting the LDS operations per key
visit shows that recommendation is internally inconsistent: that branch cannot move the number
it was written to move.** The fix is to stop treating this as one change to choose between.

## The LDS count per key visit

| design | LDS ops per key visit | reassociates? |
|---|---|---|
| **current** -- 3 passes, `logits_s[keys]` | write + read + read = **3** | no |
| **A** -- tile + online-softmax rescale | write + read = **2**, weight stays in a register | **yes** |
| **B** -- tile + recompute logits | write + recompute-write + read + read = **3-4** | no |

## Why the previous recommendation was inconsistent

It said to take B and justified it with "the tiling is the measured fix". **B does not reduce
the per-key-visit LDS work at all -- it is 3-4 ops against the current 3.** Its only effect is
on the **footprint**, hence occupancy, and `20260928T073811` already showed occupancy at the
measured 2048-token point is six blocks per CU and not obviously the limiter there. **B
therefore cannot fix the case the artifact measured.** It addresses long context only.

**A is the only one of the two that touches the measured cause** -- it removes one of three
LDS ops and keeps the weight in a register instead of round-tripping it. **And A reassociates,
so it fails `test_decode_symbol_bit_matches_prefill_symbol`.**

**So the fork is real: the branch that keeps the gate cannot fix the measured case, and the
branch that fixes it cannot keep the gate.**

## The resolution: do not choose

**The repo already has the mechanism for exactly this.** `AGENTS.md` states that production
candidates may reassociate during evaluation and that default promotion requires the full
profile gate, and `docs/EXECUTION-PROFILES.md` owns the strict/production split. **So the
port lands as a registered variant, not a replacement:**

| variant | kernel | gate |
|---|---|---|
| **strict** | the current kernel, **unchanged** | `test_decode_symbol_bit_matches_prefill_symbol`, bit-exact -- **never relaxed** |
| **production** | tiled online softmax | a new tolerance test, plus the boundary exercise |

**This is better than either previous plan on every axis:**

1. **The bit-exact contract is never spent.** It keeps covering the path it covers today.
2. **The measured cause gets addressed**, by A, without waiting for a decision to relax
   anything.
3. **Both are measurable against each other**, which is what makes the production variant's
   promotion a measurement rather than an argument.
4. **It answers "what is the port's acceptance test"** -- the strict variant's is the existing
   bit-exact test; the production variant's is new, and per `AGENTS.md` it must exercise the
   space rather than the gate point.

## Calibration for the first measurement

**A saves one of three LDS ops -- a 33% reduction in LDS traffic. That does not by itself
explain a 60x headroom to peak.** The barrier structure (two barriers between three passes
today versus one per tile) and the register-resident weight are the other candidates. **The
first measurement should be read with that in mind: a 33% LDS cut showing up as a 2x kernel
win would mean something else was also fixed, and that something else is worth knowing.**
