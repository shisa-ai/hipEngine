# ShareGPT MTP routing: every request at c=1, none at c>=4, and the engine service dies there

## Summary

A canonical ShareGPT load (vLLM's loader and pruning criteria, 128-output override)
was driven through a default-configuration `gfx1151` server at c=1, c=4 and c=8,
with the standard serving metrics from `vllm bench serve --backend openai-chat`
and a recorder client that reads the per-request `hipengine.speculative_mtp` block
and `generation_shape.route_decision`.

**At c=1 the speculative path carries the whole workload: 24 of 24 requests ran
MTP and 3,043 of 3,072 emitted tokens (99.1%) came from speculative cycles**, with
no request falling back, in every prompt-length bucket (0-511, 512-767, 768-1022).
`vllm bench serve` on the same load reports 20.68 output tok/s, mean TPOT
48.71 ms, and 148.5 s for 24 requests.

**At c>=4 the load cannot be measured**: the engine service dies and every later
request fails with HTTP 500. The crash is a single-slot prompt-activation guard in
the MTP adapter. An incremental (multi-chunk) prefill opens prompt-activation
claims that stay open until the request's final chunk, so the next request's
prompt activation raises `RuntimeError: GGUF MTP2 prompt activation claims are
already reserved` inside the driver thread; `_fail_all` then cancels every
in-flight child and closes the service. The four requests that did complete at c=4
report `mtp_used: false` with `fallback_reason: no_provider` - the activation never
primed provider state, so the planner selected autoregressive decoding for the
whole output. So concurrency does not merely slow the MTP path down; it either
crashes the service or silently disables the route.

Measured `vllm bench serve` on the same load and server configuration:

| c | completed / failed | output tok/s | mean TPOT | mean TTFT | notes |
| --- | --- | ---: | ---: | ---: | --- |
| 1 | 24 / 0 | **20.68** | 48.71 ms | 3.04 ms | full load, 128 outputs each |
| 4 | 8 / 16 | 8.70 | 182.27 ms | 9.03 ms | one driver crash |
| 8 | 11 / 21 | 8.71 | 203.57 ms | 3,763 ms (p99 27,675 ms) | one driver crash, 64 closed-service errors |

## Findings

1. **c=1 routing: 100% MTP, no fallback reason to report.** 24/24 requests, 3,043
   of 3,072 tokens from speculative cycles, `mtp_output_share 0.991`, decode
   20.11 tok/s, median time to the first content token 5,988.7 ms. Prompt length
   did not change the outcome: the two 768-1022-token prompts (the bucket just
   under the MTP window) ran MTP as well.
2. **The c>=4 failure is a state bug, not a capacity limit.** The traceback lands
   on `qwen35_gguf._prefill_native_chunk` (line 8876) opening a streaming prompt
   activation while a previous activation is still open, and
   `qwen35_gguf_mtp2.begin_prompt_streaming` (line 1372) rejects it. The
   `_active_prompt_claims` slot is single-valued while prompt streaming is
   inherently concurrent across requests.
3. **A request-level exception kills the service.** The driver thread does not
   survive the raise, `_fail_all` fires, and every later request is answered with
   `engine service is closed. Try a lower --max-context-tokens or --kv-storage
   int8_per...` - a memory-settings message for a state bug. At c=8, 64 requests
   were answered that way after one crash.
4. **Surviving concurrent requests lose MTP silently.** All four c=4 requests
   that completed had `mtp_used: false`, `fallback_reason: no_provider`, 0 MTP
   tokens of 128. The route decision still says
   `qualified_automatic_realized_singleton_c1_b3`, so the response advertises a
   route it did not run.
5. **`vllm bench serve` TTFT is a first-byte figure on this server.** The server
   opens an SSE stream with a role-only chunk, so vLLM reports 3.04 ms at c=1
   while the first *content* token arrives after 5.99 s (median). Both numbers are
   in the artifact with that reading.

## Changes

None to the engine: this unit measures. `scripts/sharegpt_mtp_routing_pass.py`
(the recorder client) is committed with it, including the fixes that made this
pass readable at all: a stream that ends without a usage block is recorded as a
failure instead of an all-null success row, and the summary reports the fallback
reason of every request that did not run MTP.
