# IQ dense prefill row tile: 3-4x kernel, 1.73x end-to-end prefill

## Summary

The recorded -15% prefill regression from `ca4e01581` is repaired and passed:
raw IQ dense prefill is 2.97-4.05x faster at the kernel and 1.73x end to end.
The cause was not a missing kernel but a registration fact: `register_gguf_iq_dense_kernels()`
registered the identical launcher under both the `gemv_*` and `prefill_*`
variant keys, and `run<Q>()` launched `grid = (ceil(N/T), rows)`. Every prompt
row was its own block row, so the weight column was re-read and re-decoded once
per row and weight traffic scaled as `rows x bytes`.

## Changes

`hipengine/kernels/hip_gfx1100/quant/gguf_iq_dense.hip`:

1. **`R` rows-per-block template parameter** alongside the existing T=8 column
   tile. Phase B hoists R activation loads and reuses each decoded weight
   across them; phase A (header preload) is row-independent and unchanged.
   Grid becomes `(ceil(N/T), ceil(rows/R))`; the kernel now takes `rows` to
   mask the ragged tail.
2. **Parallel reduction tail.** The old tail had lane 0 serially sum four wave
   partials and store all T outputs. Now one thread per live `(r, t)` output,
   with the four partials still summed in index order so each output keeps the
   declared serial wave-0..3 accumulation.
3. ABI gains a `rowbatch` argument; `run<Q>` dispatches over R in {1,2,4,8}.

`gguf_iq_dense.py`: `row_batch` parameter with validation, a default policy
(`_row_batch`: largest supported slab the prompt actually fills, so rows=1
keeps R=1), and `_default_library()` memoizing the loaded CDLL.

**Why this is strict, not production-profile.** R changes only which rows share
a workgroup. For each `(row, column)` the k ownership, FMA order, wave32
shuffle tree and serial wave sum are identical to R=1, so every R is
bit-identical. This is the same argument that let WPF-1 land the raw-K
rowbatch kernels as exact. It also means batch-composition invariance holds:
splitting a prompt into chunks that select different R cannot change output.

## Validation

- RED-first `tests/test_gguf_ud_dense_rowbatch.py` 195/195: every R in
  (2,4,8) bit-identical to R=1 across all seven quants, both output dtypes and
  13 row counts, including ragged tails (3,5,7,9,15,17,33). Output canaries
  assert the padding rows of a partial slab never store.
- `tests/test_gguf_ud_dense.py` 84/84 with the new default selection active.
- `test_gguf_ud_admission.py`, `test_qwen35_gguf_consumer_surface_parity.py`,
  `test_gfx1151_backend.py`, `test_gguf_iq_dense_tables_closed_form.py`,
  `test_gguf_e2e_acceptance.py`, `test_gguf_ud_km.py`, `test_gguf_ud_ks.py` green.
- rocprofv3 `--kernel-trace` (prebuilt .so, `HIPENGINE_REQUIRE_CACHED_BUILD=1`,
  explicit compiler-version file): `gguf_iq_dense_strict_kernel<0, true, 8, 8>`
  is the production prefill route, 117 calls / 1748.57 ms. Raw IQ dense fell
  from 50.2% to 25.2% of prefill device time; `gguf_k_prefill_out_rowbatch_kernel<*,*,5,32>`
  (raw Q5_K) is now the largest prefill consumer at 41.5%.
- Resource usage, IQ4_XS bf16-out: R=1 43 VGPRs / 16 waves per SIMD
  (**unchanged from before this commit**, so decode codegen is untouched),
  R=2 53, R=4 74 (still 16 waves), R=8 132 at 10 waves, none with scratch.
  R=16 hits the 256-VGPR cap and spills 48 B/lane; R=8 is the retained maximum.

At rows=1, R=1 is fastest for every family (IQ4_XS 0.552 vs 1.039 ms at R=8),

**7.60 -> 13.17 tok/s (+73%)**, decode 4.23 -> 4.23 (identical by
construction). Artifact: `benchmarks/results/2026-09-08-zbook-ud-iq-dense-rowbatch.json`.

## Contingent and inconclusive

Recorded now because re-measurement on the desktop gfx1151 is cheap and these
laptop rows have a measured +/-5% floor. Full list in
`docs/OPTIMIZE-KERNEL-IQ-DENSE.md`.

- **R=8 over R=4 is only 10-13%** and costs occupancy (10 vs 16 waves/SIMD).
  The crossover may move on a thermally stable host; re-sweep before treating
  R=8 as final.
- **T x R has not been swept jointly.** T=8 was tuned at R=1.
- Per-role slab selection is unmeasured; the shipped policy is one global
  function of `rows`, where the raw-K family instead qualifies specific
  `(quant, output, K, N)` shapes.
- This unit's end-to-end harness reports decode 4.23 tok/s where the
  `ca4e01581` row reports 6.39 from a different harness. Only the within-session
  ratio is claimed here; the protocols should be reconciled.
