# Gemma 4 decode attention ablation: cost is invariant per-key scaffolding, not loads/tree/barriers; warp-per-head redesign next

## Summary

Iteration 19 measured `gemma4_attention_decode_kernel` at 53% of the decode token
(24.0 ms of 45.7 ms) and closed two cost hypotheses: the reduction tree and the
K/V loads. This iteration ran a systematic **ablation study** on the sliding
geometry to find where that 24 ms actually goes. The answer is that it is *not*
attributable to any component inside the per-key iteration:

| Variant (sliding, keys=1024, ~600-708 us baseline) | us/launch | vs baseline |
| --- | --- | --- |
| baseline | 600-708 | - |
| reduction tree removed (3 shared rounds + 5 shuffle rounds) | 585 | ~0 |
| all 4 tile-loop barriers removed | 684 | worse |
| K loads removed (dot += q_s[d]) | 591 | ~0 |
| K and V loads removed | 591 | ~0 |
| mask byte load removed (keep = j < keys) | 1118 | worse (all K loads now run) |
| minimal tile body: `partial[kb*threads+tid] = q_s[tid]` only | 525 | -15% |
| publish broadcast + running-max update removed | 696 | ~0 |

Every structural ablation leaves the time within noise of baseline. The kernel
costs ~0.5-0.6 us per key and that per-key cost is **invariant to the work
inside the key iteration**: removing the mask load, the K load, the dot product,
the reduction tree, the barriers, the publish and the running-max chain each
changes nothing.

## Corrections to iteration 19

- The zero-mask "loads are only 11%" measurement in the iteration-19 record is
  **invalid** and is withdrawn. With every key masked, `logit = -INFINITY` for
  all keys, so `row_max = -INFINITY` and `exp(logit - row_max) = exp(NaN) = NaN`.
  `if (weight == 0.0f) continue;` never fires on NaN, so pass 3 still loaded
  every V row: the ablation removed nothing.
- Redone correctly (K and V loads replaced, mask left valid), loads are ~0% of
  the sliding geometry and **26% of the full geometry** (871 us vs 1186 us at
  keys=1024). The full geometry is the memory-sensitive one.

## Measured structure

- Per-launch cost is linear in the number of 8-key tiles: 18.4 us at 1 tile,
  74.8 us at 8, 284.2 us at 32, 707.9 us at 128 -> **~5.3 us per tile,
  ~15 us fixed launch cost**.
- Per-key cost is ~0.5-0.6 us (~1000+ cycles at 2 GHz) for ~8 dims of work per
  thread. This is 30x the latency of the L2 hit it is waiting on and survives
  removal of every load, so it is not a memory-latency effect.
- rocprofv3 SQ_BUSY_CYCLES = 15.6M per dispatch summed over SQs (~1M cycles per
  busy SQ) confirms the GPU is genuinely busy for the measured window; the
  kernel is executing, not queueing. Only SQ_WAVES, SQ_BUSY_CYCLES,
  SQ_INSTS_FLAT/LDS, SQ_WAIT_ANY and SQ_WAIT_INST_LDS are reported for this
  agent, and the instruction/wait counters all read 0 (not implemented on
  gfx1100), so no stall breakdown is available from PMCs.

## Conclusion

The 256-thread, 8-warp, 5-barrier-per-8-keys structure is the cost. Per-key work
is spread across 256 lanes with a shared-memory round trip and a barrier
sequence for every 8 keys, and the measured per-key cost is insensitive to what
those lanes compute. Micro-optimizing inside the existing loop cannot win.

## Next candidate: warp-per-head with vectorized loads and a shuffle-only tree

One warp per `(token, head)`: 32 lanes x 8 dims = 256 dims for the sliding
geometry. Each lane holds 8 `q` values in registers and loads 8 consecutive
`bf16` (16 B vector load) per key, so per-key work drops to one vector load plus
8 FMAs with no shared-memory traffic and no barriers.

The 256-lane tree maps onto this layout with **identical association order**, so
the result stays bit-exact against the strict reference:

| original stride | flat indices | lane distance | mechanism |
| --- | --- | --- | --- |
| 128 | i, i+128 | 16 | shuffle |
| 64 | i, i+64 | 8 | shuffle |
| 32 | i, i+32 | 4 | shuffle |
| 16 | i, i+16 | 2 | shuffle |
| 8 | i, i+8 | 1 | shuffle |
| 4 | i, i+4 | in-lane (elem 0,4) | register add |
| 2 | i, i+2 | in-lane | register add |
| 1 | i, i+1 | in-lane | register add |

Five shuffle rounds plus three in-lane rounds reproduce the strict tree exactly,
removing all 5 barriers and the `partial`/`logits_s` shared round trips from the
tile loop.
