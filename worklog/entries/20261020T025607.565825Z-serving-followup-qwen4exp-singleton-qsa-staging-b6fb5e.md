# Keep singleton sparse QSA selection staging writable

## Summary

A one-row QSA selection scratch could not switch to sparse attention: NumPy's
`ascontiguousarray(broadcast_to(...))` kept the already-contiguous singleton
view read-only. Allocate an owned C-order copy at every width.

## Changes

- Keep the existing selection contents and device layout; require writable host
  storage before sparse selection overwrites it.
- Add CPU coverage at widths 1, 2 and 4 for contiguous writable storage and a
  sparse publication.

## Validation

- RED: the new width-one CPU case fails on `flags.writeable`; widths 2 and 4
  pass. GREEN: the QSA mixer, mixed-QSA adapter and mixed-serving CPU bundle
  passes 78 checks after the allocation fix.
- On the local Radeon 8060S in the clean TheRock environment, the original GPU
  failure occurs in the independent singleton reference at the dense/sparse
  transition. With the fix, that transition passes. A later fixture failure
  indexed a follow-up hidden row beyond the AR peer's generated history; a new
  deterministic follow-up row now drives both reference and candidate.
- The focused GPU continuation/abort checks and batch-runner file pass 18
  checks. Other mixed-QSA dense, permutation and transition checks passed in
  the preceding run. The change does not alter arithmetic or selection values.
- The full CPU deterministic bundle passed earlier in the campaign; the
  changed QSA allocation and focused CPU cases were rerun here.
