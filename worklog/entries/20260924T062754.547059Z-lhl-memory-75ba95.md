# Unified admission budget with a named pre-allocation refusal

## Summary

The KV-pool admission priced exactly one consumer -- the pool itself -- against
`mem_get_info()` free bytes minus a hardcoded 3 GiB, and every other resident
consumer (draft/provider KV, verifier scratch, captured graphs, retained prefix
ownership) was discovered later as a HIP out-of-memory fault from the middle of a
request. This lands the budget those consumers are priced through, the named
refusal it raises before anything is allocated, and the HTTP mapping that answers
the refusal as capacity rather than as an internal fault.

## Changes

- `hipengine/runtime/memory_admission.py` (new): `MemoryConsumer`,
  `MemoryAdmissionDecision`, `MemoryAdmissionRefused` (a `MemoryError` subclass
  carrying `code`, `refused_consumer`, and the priced totals), and
  `price_memory_admission` / `require_memory_admission`. Consumers are priced in
  declaration order and the first that does not fit the remaining headroom is the
  named reason, so the message points at the allocation that has to shrink rather
  than at a total. `headroom_bytes` is `available - required` and is negative on a
  refusal.
- `hipengine/runtime/qwen35_gguf_runner.py`: the KV-pool construction now prices
  its pool through the budget instead of computing `free - 3 GiB` inline. The
  default reserve is the same 3 GiB, so the arithmetic is unchanged for the one
  consumer wired today; what changed is that the refusal names the consumer and
  that a second consumer needs no new arithmetic. The explicit
  `kv_pool_memory_budget_mib` ceiling is priced with a zero reserve, preserving
  its previous meaning.
- `hipengine/server/api.py`: `MemoryAdmissionRefused` maps to 503 with its own
  `insufficient_memory` code and its message, instead of falling through to
  `internal_error`. The refusal is raised before any allocation, so the engine is
  still healthy and the same request may fit later.

## Validation

- `tests/test_unit_memory_admission.py` (new, 18 passed): each of the five named
  consumers is the refusal reason when *it* is the one that does not fit (both
  sides of its own edge, parametrized), the exact boundary admits with zero
  headroom, an unrelated consumer size (777) and an unrelated free-memory value
  behave as plain arithmetic, declaration order decides who is blamed, a zero-byte
  consumer is never blamed, the reserve is deducted before pricing, and
  `require_memory_admission` raises a `MemoryError` whose message names the
  consumer and whose code is the API code.
- `tests/test_integration_server_api.py`: a request refused by the budget is
  answered 503 with `error.code == "insufficient_memory"`, not `internal_error`,
  and the message names `kv_pool`.
- `tests/test_unit_gguf_packed_workspace_stability.py -k "kv_pool or budget or
  pool"`: 23 passed, including the existing `kv_pool_memory_budget_mib = 1`
  refusal, which now travels through the new path and still matches on "budget".
- `tests/test_unit_qwen35_gguf_capacity.py`: passed (auto-context estimation is
  untouched; it computes its own estimate and does not read the pool admission).
- `tests/test_integration_server_api.py -k "unavailable or admission or closed or
  internal_error"`: passed, so the existing liveness 503 mapping is unchanged.

## Next

- The budget prices every consumer it is given, but only the KV pool is wired in
  at its construction site today. Remaining wiring, per the task: draft/provider
  KV, INT8 MTP verifier scratch (which grows dynamically into the persistent
  session root), captured graphs, and retained prefix ownership. Retained prefix
  ownership is already measured (`retained_kv_bytes` / `snapshot_bytes` in
  `hipengine/generation/qwen35_gguf.py`), so it is the cheapest of the four to
  price; the scratch and graph consumers need explicit byte inputs from their
  owners.
- Admission is still a startup decision. A per-request admission (refusing one
  oversized request on an otherwise healthy server) does not exist; that is the
  other half of the task's deliverable.
- API convention note, stated once: the repository's existing capacity refusal is
  `GenerationAdmissionRejected` -> 429 `engine_busy` with `Retry-After` and
  `routing.overload_source = "kv_pool_capacity"`. This change maps the budget
  refusal to 503 with its own code because the task's acceptance asks for a
  503-class error; folding it into the existing 429 `engine_busy` shape is the
  consistent alternative if that convention is preferred.
