# Move the shard chain and staged exchange into runtime components

## Summary

Handoff step 1: the TP2-A-proven shard execution and the measured
host-staged exchange now exist as reusable runtime components instead of
benchmark-script internals, with persistent allocations and explicit
rank/device ownership.

- `hipengine/distributed/staged.py` - `StagedExchangeTransport`: the measured
  batched protocol (both D2H submitted before either wait, one wait per
  stream per reduce - which is also the staging-slot reuse guard - host f32
  sum over the contiguous (ranks, hidden) view, H2D to every rank with no
  return wait). Double-buffered pinned staging and reduced-payload slots;
  persistent per-rank reduced device buffers; any enqueue/wait failure
  poisons the transport and it refuses further reductions (the caller fails
  the whole group). Two slot sets keep a host write from racing the previous
  call's H2D even if a caller pipelines reductions.
- `hipengine/distributed/shard_exec.py` - `MlpShardRank`: one rank's resident
  shard weights plus persistent activation buffers allocated once (x, gate,
  up, act, f32 down partial). `forward_partial()` enqueues the unfused chain
  (gate GEMV, up GEMV, SiLU-mul, down GEMV -> f32 partial) or the fused
  pair+SiLU candidate, under a scoped current device, with no host sync
  inside; the device-resident partial pointer is the exchange's producer.
  Every launch and free is device-scoped; close() frees exactly once.

These are components, not a serving path: the staged transport still needs
the stress/qualification the plan doc requires before it is a default, and
the fused chain remains a scoped candidate.

## Changes

- `hipengine/distributed/staged.py`, `hipengine/distributed/shard_exec.py`:
  the two components.
- `tests/test_unit_distributed_staged_and_shard.py`: 15 CPU tests over a
  write-through fake runtime - submission order (both D2H before any wait,
  H2D after, no return wait), f32 sum correctness, slot alternation,
  poisoning, per-device free/unregister, persistent-allocation discipline
  (no malloc in forward), launch order/device scoping, fused-variant gating,
  closed-rank refusal.
- `tests/test_gpu_distributed_shard_components.py`: two-GPU integration
  (W7900 + XTX): both ranks upload dense_bf16 shards, run the unfused chain
  into persistent partials, the staged exchange reduces into each rank's
  device buffer, and every rank's reduced output matches the numpy bf16
  contract within 4e-2 (bf16 precision + accumulation noise). Caught the
  stream-ownership rule concretely: a stream created under device 0 makes
  rank 1's launch fail with HIP error 400 - streams are now created under
  each rank's scoped device.
