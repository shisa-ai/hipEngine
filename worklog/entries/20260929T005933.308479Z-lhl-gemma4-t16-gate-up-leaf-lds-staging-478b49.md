# T16 gate/up leaf: stage the K-major tile in LDS, bit-identical, prefill +8.3%

## Summary

The T16 gate/up WMMA leaf reads sixteen scalar global byte loads per weight fragment, and the
previous two units disagreed about why that matters: one called the leaf issue-bound, the next
found that the compiler's register-hungry load schedule is worth 2.2x by itself and named
decode-in-LDS staging as the concrete next attempt. **That attempt works.** Staging the tile's Q
region in LDS and reading one fragment per 128-bit LDS load is worth **prefill 1147 -> 1242 tok/s at
512/128 (+8.3%)**, decode 28.374 -> 28.924 tok/s, and a public wall of 4.86 -> 4.38 s, all measured
in one session with only the kernel, its wrapper, its route and its loader repack differing. The
output is **bit-identical**.

The leaf goes **4.087 -> 2.987 ms per call at 512 tokens and 4.170 -> 3.0723 at 4096** (29 and 232
calls, 1.368x and 1.357x). Its static body goes **3982 -> 3174 instructions, 124.4 -> 99.2 per
WMMA**.

**The direct read of the same fragment is 1.98x slower, and that is the finding.** One 128-bit load
per fragment instead of sixteen scalar byte loads leaves the compiler nothing to batch, so to hide
L2 latency it keeps far more fragments in flight: 256 VGPRs, the ISA maximum, with 202 spilled
instructions, against the row-major decode's 175 VGPRs and no spill. The LDS read is short-latency
enough that no batching is needed, and the same source lands at **172 VGPRs with no spill**. So the
lever on this leaf is not the count of memory operations but the **latency** of the one that
remains.

## Changes

1. **`hipengine/quant/gguf_q4_k.py`** — `repack_gguf_q4_k_tile16(..., column_major=True)` writes the
   Q region K-major: the byte for (byte column `p`, K value `k`) at `p * 16 + (k % 16)` inside its
   128-byte K tile. That is a **pure permutation** of the row-major order — the same bytes, the same
   tile size, the same decoded values — and `_tile16_q_region_inverse` inverts it exactly. The
   default is unchanged, so no other caller of the repack moves.
2. **`hipengine/kernels/hip_gfx1100/quant/gguf_q4_k_t16_selected_prefill.hip`** — a `column_major`
   template argument on the compact32 kernel selects a K-major decode, and that decode reads its
   fragment from LDS. Each sub-block's Q region is staged by one coalesced 128-bit load and one
   128-bit LDS store per lane, published with `s_barrier`, and read back as one 128-bit LDS load per
   fragment. The header (d, dmin, scale, minv) is not staged; it stays a global read.
3. **The staging window is the tuning knob and it is not monotone.** One sub-block: 172 VGPRs, no
   spill. Two: 256 VGPRs, 83 spills. Four: 256 VGPRs, 196 spills. The barrier that publishes a fill
   is also a scheduling fence, so everything decoded between two barriers is live at once, and a
   wider window buys fewer barriers at the cost of more live state.
4. **The Gemma-4 route binds the K-major symbol and the loader repacks K-major for it**
   (`hipengine/loading/gemma4_gguf_device.py`). The row-major symbol, the row-major repack default
   and the row-major decode all remain in the tree and every other consumer is untouched. No flag and
   no dispatch route was added: the route that already existed now calls a different symbol.

## Why the direct read is slower and the staged one is not

Four measurements, each isolating one thing:

- **The direct K-major read asks for the ISA maximum of VGPRs and spills.** The same decode with the
  fragment read straight from global memory is 256 VGPRs and 202 spilled instructions against the
  row-major path's 175 and 0. Measured in situ at 4096 it is 9.9161 ms per call against 5.0157 for
  the pre-hoist row-major in its own session (1.98x slower), and against 4.136-4.170 for the hoisted
  one. The decode is identical either way; only the latency of the read differs, so the register
  budget is what changed.
- **Staging the same bytes in LDS drops it below the spill cliff.** 172 VGPRs, no spill, and the
  fragment read becomes one 128-bit LDS load that the surrounding decode covers without batching.
- **A wider staging window is worse, and it is the barrier that does it.** Two sub-blocks is 83
  spills, four is 196. The publish barrier is a scheduling fence, so the decode of everything
  between two barriers is live at once.
- **The prior attempts on this leaf all lost for the same reason.** A row-paired geometry with 2.35x
  fewer static instructions per WMMA, a byte-pair-packing decode, and a sweep of launch-bounds floors
  reduced instructions or load registers while leaving the fragment read's latency where it was. This
  change moves the latency, and it wins where they did not.

## Next

- The staging fill is 8 of the K loop's 76 remaining global memory operations. The next largest group
  is the 36 header loads (d, dmin, scale, minv) per K block, which are per (sub-block, column) rather
  than per K value, so staging them is a smaller win than the fragment read was.
- A **double-buffered** staging window would let the next fill issue before the current window's
  barrier, and the barrier is the fence that costs the register budget. One sub-block is the widest
  window that does not spill, so double buffering is the way to spend LDS instead of VGPRs. It was
  not built.
- The fp16 instantiation of the same template is now also instantiated K-major and is not on the
  Gemma-4 route.
