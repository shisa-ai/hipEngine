# c=8 beyond-1024 closure arms both complete, and the MTP arm fell back to AR on every cycle

## Summary

The c=8 beyond-1024 HTTP reproducer runs to completion in both arms against the
merged tree: `failed_requests: 0` in `off` and `on`, so the original error this
reproducer was built for no longer occurs. But the `on` arm did **not** exercise
MTP: of its 256 AR output tokens, **248 were attributed to AR with planner reason
`no_provider`**, which is the reason code for a row that registered a candidate
budget but whose provider never admitted it. The remaining 8 are unaccounted
inside that breakdown.

That makes this run a clean closure of the *failure* question and an open
question for the *MTP admission* one: in this configuration MTP requested on the
request side produced no provider engagement, so the arm measured AR throughput
under an MTP request rather than an MTP speedup.

Interpretation is explicitly open. The two arms are also not symmetric in
accounting: `off` reports `accounted_requests: 0` and `ar_output_tokens: 0`
while `on` reports `accounted_requests: 8`, so the harness attributed nothing in
the `off` arm. Until that asymmetry is explained, the two arms must not be read
as an A/B throughput comparison.
