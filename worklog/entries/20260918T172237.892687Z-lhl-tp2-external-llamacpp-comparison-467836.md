# TP2 external sanity check vs llama.cpp RDNA3 fork

## Summary

The user asked for an external sanity check on both performance and memory for
the TP2 work, against a purpose-tuned RDNA3 llama.cpp fork. Measured on the same
host and the same `Qwen3.8-27B-Q4_K_M.gguf` (sha256 `7b2aec3b…`), c=1,
512-token prompt, 128 decode tokens, f16 KV, no speculative decoding, ROCm
7.2.4 / gfx1100, the fork at build `15995a1`.

Result: hipEngine is at parity on single-card prefill/decode and on TP2 decode,
and has two quantified gaps that were previously only predicted — TP2 prefill
and TP2 per-rank residency.

| Route | Prefill tok/s | Decode tok/s | Device memory |
| --- | ---: | ---: | ---: |
| llama.cpp TP=1 (W7900) | 941.8 | 30.44 | 15.38 GiB |
| hipEngine TP1 (W7900, bulk prefill) | 875.8 (−7.0%) | 30.76 (+1.1%) | 17.70 GiB (+15.1%) |
| llama.cpp TP=2 `-sm tensor` | 1474.6 (+56.6% vs its TP1) | 41.30 (+35.7%) | 7.75 GiB/rank (−49.6%) |
| hipEngine TP2 | 39.5 (−95.5% vs own TP1) | 38.8 (+26.1% vs own TP1) | 22.37 GiB/rank (+26.4% vs own TP1) |

- **TP2 decode is at parity** (38.8 vs 41.3 tok/s) and is 1.26x this project's
  own single-card decode, so the staged exchange plus graphed decode schedule is
  competitive with a tensor-split fork on the same two cards.
- **TP2 prefill is the dominant gap** and it is a known registered fallback, not
  a new mystery: `MlpTP2GenerationSession` drives prefill token-by-token, so it
  lands at 0.045x the production single-card bulk route, while llama.cpp's
  tensor split *gains* 1.57x over its own TP=1. This is the cell the rank-local
  bulk TP2 prefill plan in `docs/QWEN38-27B-GFX1100-TP2.md` targets, and the
  comparison now gives that plan an external baseline.
- **TP2 does not reduce per-rank residency.** Measured 22.37 GiB/rank against
  the shard manifest's planned 7.83 GiB/rank of resident weights (851 tensors,
  209 replicated but only 0.003 GiB of replicated bytes), while llama.cpp's
  tensor split halves per-rank weights to 7.49 GiB. ~14.5 GiB/rank is therefore
  unexplained by the shard plan. The capacity consequence is concrete: after a
  TP2 load the 24 GiB RX 7900 XTX rank has **1.58 GiB free**, which is why the
  2026-09-18 capacity ladder was tight. This is a follow-up audit item, not a
  conclusion about the cause.

## Validation

- Device-scoped memory measurement was proven before being used: allocating
  2 GiB on device 1 moved only device 1's `hipMemGetInfo` delta
  (0.035 → 2.035 GiB, device 0 unchanged), so the per-rank numbers are not an
  aggregate or a wrong-device read. The two TP2 ranks report identical
  22.402 GiB, which is expected for an even split and consistent with a real
  per-device read.
- llama.cpp's `Meta()` buffer report is a **per-rank** value, confirmed from the
  same logs by the KV cache halving (128.00 → 64.00 MiB) and the recurrent-state
  buffer halving (149.62 → 74.81 MiB) between TP=1 and TP=2; the model buffer
  halves the same way (15345.66 → 7674.12 MiB).
- The shard manifest was recomputed on CPU for this entry: 851 tensors,
  7.827 GiB planned resident per rank at world_size=2, 15.65 GiB of sharded pool,
  0.003 GiB replicated.
- hipEngine cells are 3 measured generations after a warmup on one resident
  session (medians 39.49 prefill / 38.79 decode tok/s, per-run samples recorded
  in the artifacts). llama.cpp cells are `llama-bench -r 3` medians. Both are
  the same 512/128 c=1 protocol on the same host and model file.
- `python3 -c "import ast..."` syntax check on the edited harness; artifact JSON
  written and re-read.
