# One load measures both arms and both prompt cases; concurrency never groups speculative rows

## Summary

The real-workload harness now measures the reviewer's matrix inside a single
load: `--route-mix off,auto` assigns the arm per request in submission order, so
the true-AR control and the speculative arm share one server process, one
occupancy history and one cache state; `--cases short,long` puts a healthy short
request beside the boundary-crossing row and labels both; `--record-ids` adds a
per-run `arm_identity` comparison that reports whether the arms produced the same
greedy tokens and where they part. Running that coupling arm on the last tree
whose control prompt was exact shows that **concurrency never batches speculative
rows** (every speculative request ran at realized width 1 at c=2 and c=4), that
the provider is starved as occupancy rises (non-speculative tokens attributed to
`no_provider` go 8 -> 456 from c=2 to c=4, speculative output share 49.7% ->
39.8%), and that the speculative arm's advantage over its in-run AR control
(+21% at c=2) is gone at c=4 (-2%). The identity comparison also found a residual
divergence on that tree that no retained evidence row reported: 2 of 7 natural
prompts differ between the arms, sequentially, without prefix reuse.

## Changes

- `scripts/sharegpt_mtp_routing_pass.py`:
  - `--route-mix` (per-request arm assignment, cycled in submission order),
    recorded per row as `route_arm`.
  - `--cases short,mid,long` (labelled prompt-length mix in one load) with the
    row's `case`, so a provider-ready request and a boundary-crossing one are
    measured together.
  - `--record-ids` and `_arm_identity`: per-run comparison of the arms' greedy
    token ids per prompt, with the shared-prefix length where they differ and a
    `QUALITY` line when they disagree. It keys on the prompt, not the repeat
    index, because a route mix alternates arms across repeats.
  - `_serving_metrics` plus `by_route_arm` / `by_case` summary blocks:
    throughput, TTFT, inter-token latency, MTP share and refusals per slice.
  - Inter-token latency is measured over windows of 16 committed tokens and the
    row's number is the whole-timeline average. The previous consecutive-pair
    median reported 0.29 ms for a row whose cycles cost ~250 ms, because a
    speculative cycle's reports are read microseconds apart while the wait for
    the next cycle is reported nowhere.
- `tests/test_unit_sharegpt_mtp_routing_recorder.py`: case-mix selection,
  per-arm/per-case splits, identity with ids and the digest fallback, a buffered
  commit burst, and a stalled window that must move the tail.

- The width-1 result is the concrete blocker for concurrent coverage: a
  speculative row never joins a wider group, so no amount of route admission

  needs.
