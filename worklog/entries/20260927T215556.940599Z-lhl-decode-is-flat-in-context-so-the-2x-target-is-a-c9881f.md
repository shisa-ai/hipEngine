# Decode is flat in context, so the 2X target is a weight-path target
## Summary
The withdrawn decode profile needed a replacement method, not a better
denominator. This is that replacement: the benchmark's own `decode_tps`, taken
warm, at three context lengths. It carries no profiling overhead, and decode rate
versus context separates the weight-bound part of a decode step from the
attention-bound part, because only attention grows with context.
| prompt | decode tok/s | ms/token | prefill tok/s |
| --- | --- | --- | --- |
| 8 | **22.38** | 44.7 | 41.4 (launch-bound, not a prefill figure) |
| 512 | **21.09** | 47.4 | 341.0 |
| 2048 | **19.67** | 50.8 | 271.8 |
## The finding
**Decode is flat in context.** A 256-fold increase in context length costs 12
percent of decode rate. The attention-dependent part of a decode step is the
difference between the shortest and longest point here, about 2.7 tok/s out of
22.4, so roughly 12 percent. The other 88 percent is weight streaming: the MoE
expert path plus the dense projections, which cost the same per token no matter
how long the context is.
**The objective's 2X decode target is therefore a weight-path target.** Decode is
22.38 tok/s at short context and llama.cpp is 41.92, so the entire 2.09x gap
lives where the weights are read. No amount of attention work closes it, and the
attention work already landed (dimension-partitioned decode attention, key-class
decode, the two-phase split) is not where the remaining gap is.
## Bandwidth arithmetic, labelled as arithmetic
At 44.7 ms per token and about 2.25 GB of active weights per token — 4B active
parameters at Q4_K, roughly 4.5 bits per parameter — decode reaches about **50
GB/s of the 256 GB/s peak, 20 percent**. llama.cpp reaches about 94 GB/s on the
same host and artifact.
This lands near the withdrawn profile's 18 percent **by coincidence**: that
profile's shares were unsound, but the clean wall-clock numbers give a similar
utilisation. The headroom reading survives; the attribution behind it did not.
## What this does not establish
Which kernel, or which part of the weight path, is slow. It rules attention out
and points at weight streaming. It does **not** distinguish the MoE expert gather
from the dense projections, and it does not explain why 50 GB/s is reached rather
than 94. That needs an ablation, not a profile.

  and with the WMMA landing, which is a consistency check on the harness.

  launch-bound rather than presented as a prefill measurement.
- No correctness gate applies: no production code changed and no performance
  claim is made.
