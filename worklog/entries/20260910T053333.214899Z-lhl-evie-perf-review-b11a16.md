20-token queries, 151-token documents, real processor inputs, full 8x8

here. Its gate is synthetic score/argmax comparison; this is not a real
retrieval-quality qualification. No exact executable matched-harness command
is retained in that artifact or its worklog, so reproducibility remains open.

Conditional on those reported timings, CPU image preprocessing cannot explain
the remaining gap: it is outside both timers. Vision-tower GPU work is part
of document encoding and must be distinguished from CPU image preprocessing.
Queries have no vision tower and are also slower. FP16 vs BF16 is a comparison
of deployment choices, not identical arithmetic. Torch already executes GPU
kernels; replacing its host with HIP does not alone guarantee faster GEMMs.

Batching is an important structural difference and a strong optimization
candidate, but the new handoff's attribution of the entire gap to batching
is not established without Torch batch-1 timing and a device trace. The
FP32-versus-FP32 gap also needs the same batch-size control.

### Do not treat wrapper timing as a GPU work breakdown

The older worklogs report 16.3 ms dense GEMM plus 2.3 ms attention GEMM in
a 231 ms page, and 4.97 ms cast overhead. The cast entry describes wrapping
`runner._k`; neither entry retains the harness or documents GPU events or
synchronization around the measurement. The runtime's rocBLAS and HIP launch
wrappers are asynchronous. Host-call timing can measure submission and charge
earlier GPU execution to a later blocking copy. Thus the claim that all
remaining time is launch overhead, or that GEMM/cast optimization has a proven
small upper bound, is not established by the retained evidence. Even a correct
non-GEMM total includes real recurrence and elementwise GPU computation.
The cluster8 kernel still loops over token order in
`linear_attn/gdn.hip:3407`; its cost must be measured separately.

### Proposed pass, in order

1. **Make the matched protocol reproducible and collect the missing split.**
   Commit a shared-input benchmark with matched timing/output-transfer scope;
   run Torch batch 1 and batch 8, hipEngine batch 1, for documents and queries
   separately on the same host. Retain actual shapes and precision. Collect a
   warmed device/API trace separating GEMMs, attention/softmax, recurrence,
   elementwise kernels, allocations, copies, host submission, and GPU idle
   gaps. Use GPU events or trace timestamps for GPU duration. Prebuild JIT
   libraries outside rocprofv3 and require cached builds during profiling.

2. **Remove obvious host transfers and per-call allocation.**
   `EvieRunner.project()` reads the already resident head bias back to CPU
   (`_read_bias`) and immediately uploads it again with `_to_dev`; use the
   original device pointer. Every GDN layer builds and synchronously uploads
   128 KiB of zeros to conv state: 24 uploads per encode. Replace this with
   stream-ordered device zeroing while preserving exact reset semantics.
   Cache vision position/rotary tables by grid and reuse buffers for pixels,
   IDs, visual merger output and head scratch. Cache ctypes bindings/signatures
   at construction instead of setting them in each `_k` call. These are
   concrete avoidable operations; no speedup estimate is asserted.

3. **Batch queries, then pages.**
   The current benchmark calls the full network eight times sequentially.
   Batch dense projections across requests to amortize launches and improve
   weight reuse. Short queries offer a simpler starting point without the
   vision tower. GDN state and attention masks must remain independent per
   request; flattening requests into one recurrent sequence is incorrect.
   Then support compatible page/grid buckets with segmented vision attention.
   Require solo-vs-batch isolation, masking and quality gates. Measure batch-1
   latency separately from batch throughput.

4. **Capture stable execution in HIP graphs.**
   After eliminating allocation and blocking host copies in the compute path,
   test warmed per-shape graph replay against eager execution. The 24 vision
   and 32 text layers currently dispatch many small operations from Python.
   Graph capture addresses submission overhead, not time spent computing an
   individual recurrence/kernel. Preserve stable buffer lifetime across cache
   eviction and exact per-request state reset; graph pins and cache ownership
   must be designed together.

5. **Fuse the operations the trace identifies.**
   Natural candidates are vision bias+GELU, residual+normalization, and
   normalization+FP16 cast. Reuse one cast activation across projections of
   the same input (GDN qkv/z/b/a, text q/k/v, MLP gate/up) before attempting
   a larger GEMM concatenation redesign. Prior GDN four-projection fusion was
   rejected because downstream consumers assume separate contiguous planes;
   account for that layout blocker. Materialized attention currently uses
   gather, score GEMM, softmax, value GEMM and scatter; fused/streaming
   attention is a candidate if its measured family cost warrants it. Evaluate
   existing in-tree kernels/lineage before any new kernel campaign. Arithmetic
   changes require their declared strict or retrieval-profile gate.

6. **Compute only the 128-dimension retrieval head.**
   `project()` computes 2048 channels and then slices to 128 before L2 norm.
   The Prefix-MRL contract permits projecting just the first 128 weight/bias
   rows. This removes 15/16 of this projection's arithmetic, not 15/16 of
   model work. A fused bias+normalization step can also remove the slice pass.
   GEMM shape changes can alter floating-point results; verify the declared
   gate rather than claiming automatic byte equality. This is a small scoped
   candidate, not a likely explanation for the entire runtime gap.

INT8/FP8 should remain lower priority given the recorded library-support
blocker, but re-measure device time before using the old wrapper breakdown
to categorically reject all arithmetic, attention, or FP16-stream work.
