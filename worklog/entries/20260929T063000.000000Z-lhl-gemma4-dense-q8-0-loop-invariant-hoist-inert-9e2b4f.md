# the dense Q8_0 prefill's loop-invariant 64-bit multiplies were already hoisted; the source change is inert and reverted

## Summary

Following the attention hoist (`20260929T060000`) that was worth 1.5 percent, the same
pattern was applied to the dense Q8_0 prefill kernel -- 189.8 ms, or 29 percent of the
0.65 s prefill. Two expressions were recomputed inside the `blk` loop even though they do
not depend on `blk`:

- `block_ptr[tm] = qweight + safe_out[tm] * row_bytes + blk * Q8_0_BLOCK_BYTES`, where
  `row_bytes` is a runtime value and so the multiply is a full 64x64 with no hardware
  support on this target.
- `x_row = x + safe_token[tn] * in_features`, recomputed inside the `kt` loop *and* the
  `blk` loop -- `blocks_per_row * K_TILES_PER_BLOCK * TN` times where `TN` would do.

Both were hoisted to per-lane arrays derived once before the walk.

**The wall clock does not move.** Five samples at 0.65 s, 783 to 786 tok/s, against 0.65 s
and 782 to 786 tok/s before. All **170** Q8_0 prefill tests pass -- the change is
bit-identical, it simply is not worth anything.

**Reverted rather than kept**, by the standard `20260928T130200` set for the attention
prologue: it does not earn its lines.

## What this establishes

The attention hoist's 1.5 percent did **not** come from removing loop-invariant address
math, because the dense kernel proves the compiler already does that on this target. The
difference has to be the part of the attention change that was *not* loop-invariant:
narrowing `j`, `walk_end` and `first_kept` to 32-bit removes the overflow-checked 64-bit
induction that lowers to the `s_cselect_b32`/`s_or_b32` pairs `20260928T130200` counted
1,640 of. **The compiler strength-reduces invariant address arithmetic; it cannot remove
an induction variable's width.**

That is the transferable finding, and it sets the bar for the next attempt: on this
compiler, a source-level hoist of loop-invariant pointer math is not a lever, and a
measurement is the only way to tell.
