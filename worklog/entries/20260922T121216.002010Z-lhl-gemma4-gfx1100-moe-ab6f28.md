# Gemma 4 gfx1100 routed-expert GeGLU and weighted accumulate

## Summary

Adds the two Gemma 4-specific primitives of the routed-expert FFN — the GeGLU
activation over a fused `gate_up` buffer, and the routing-weighted accumulate —
plus the lane-inversion helper the accumulate needs. Everything else in the
expert path is reused from kernels already in the tree.

The reference computes, per token and per selected slot:

```
projection = gate_up[expert] @ row
gate, up   = split(projection, 2)
activated  = gemma4_gelu_tanh(gate) * up
out[token] += down[expert] @ activated * weights[token, slot]
```

**Reused rather than rebuilt.** `qwen35_moe_group_compact_active` already builds
the per-expert compact metadata (`expert_start` prefix, `active_experts`,
`sorted_lanes`, `sorted_weights`) in one device-resident pass, and
`dense_gemv_out_bf16` already does the per-expert GEMV: with the compacted rows
for expert `e` contiguous, one launch with `rows = count[e]` and a pointer offset
to `gate_up_proj[e]` is the whole per-expert projection. That is `num_active`
launches rather than `tokens * top_k`.

**Not reused, deliberately.** The activation kernels already in the tree are
`maple_clamped_swiglu_bf16` (SwiGLU) and one-offs under `vision/` and
`vibevoice/`. Gemma 4 uses `gelu_pytorch_tanh`, and `gelu_tanh` is not `silu`;
substituting one would silently change the arithmetic of every expert in every
layer. The test asserts both that the kernel matches `gemma4_gelu_tanh` and that
it does **not** match `silu(gate) * up`, so the plausible wrong reuse fails
loudly rather than looking approximately right.

### The race this unit had to fix

The first version of the accumulate gave each compacted row its own block and did
a read-modify-write on the destination token row. Compaction orders rows by
expert, so a token's `top_k` lanes land in `top_k` different rows — and therefore
in `top_k` different blocks — whenever those lanes route to different experts.
Those blocks then read-modify-write the same output elements concurrently. The
result depends on block scheduling: contributions get dropped or double-counted
non-deterministically, which is exactly the failure mode that passes a small test
and corrupts a real forward.

The fix owns a whole token per block: each column is accumulated in a register by
exactly one thread over that token's lanes and written once. No atomics, no
race. This needs the inverse of the compact permutation, hence
`gemma4_moe_lane_to_row_i32` (`lane_to_row[sorted_lanes[row]] = row`); the compact
list is a full permutation of lanes because every selected expert has at least
one lane.

The regression test uses a deliberately interleaved compact order
(`sorted_lanes[slot * tokens + token] = token * top_k + slot`), which forces each
token's lanes into different blocks. A per-row kernel fails it; a per-token
kernel passes. That is the test that would have caught the original version.

One documented deviation: each expert's down-projection result is BF16 before it
is accumulated, while the reference keeps per-lane outputs in FP32. That is a
per-lane rounding difference, not a structural one, and it is noted at the
kernel rather than left implicit.
