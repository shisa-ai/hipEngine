## Changes


- User direction: use GPU1/RX 7900 XTX 24GB to baseline Q4_K_M prefill/decode/max-context, then work memory policy without short-gate prefill/decode regressions.
- Baseline command family: isolated TheRock ROCm 7.13 env (`HIP_VISIBLE_DEVICES=1`, `HSA_OVERRIDE_GFX_VERSION=11.0.0`, `HIPENGINE_HIP_ARCH=gfx1100`, `HIPENGINE_GGUF_DECODE_REPACK=1`, cached compiler version `/tmp/hipengine-hipcc-version-713.txt`) running `scripts/qwen35_readme_sweep.py --engine gguf --model /models/gguf/Qwen3.6-35B-A3B-UD-Q4_K_M.gguf --quant gguf_q4_k_m --force-bulk-prefill --bulk-prefill-attention-mode bulk --use-wmma-prefill --use-gemv-decode --require-cached-build`.
- Short baseline (`benchmarks/results/2026-06-18-gpu1-gguf-q4km-memory-baseline-short.json`, 1 warmup + 3 measured): `512/128` median `2292.039` prefill / `125.218` decode tok/s, stable IDs `[318]*3`, `22.487 GiB`; `4K/128` `2602.404` / `114.129`, stable IDs `[220]*3`, `22.487 GiB`.
- Baseline max-context fit search (`benchmarks/results/2026-06-18-gpu1-gguf-q4km-memory-baseline.json`, one measured run per long shape): `32K/128` pass `2038.815/96.257`, `23.051 GiB`; `48K/128` pass `1771.827/89.750`, `23.373 GiB`; `51K/128` pass `1597.225/86.356`, `23.434 GiB`; `52K/128` allocated but failed during AOTriton prefill with `Available Free mem : 0 MB` / `HIP error 701`; `54K+` failed allocation/OOM. Treat `51K/128` pass and `52K/128` fail as the pre-policy 24GB window.
- Memory analysis: current mid-context failure is the 4096-row full-attention query chunk driving resident bulk-prefill scratch over available headroom. Manual 1024-row full-attn query chunks on the unmodified tree proved `64K/128`, `80K/128`, and `96K/128` fit; `112K/128` still OOM, so 128K requires KV/weight residency work beyond prefill scratch.
- Code change: `hipengine/runtime/prefill.py` now applies a 24GB mid-context policy on devices with `total_memory_bytes <= 26 GiB`: at `max_sequence_length >= 52K`, keep linear/MoE/post/RoPE chunks at 1024 and lower full-attn query from 4096 to 1024 rows. 512/4K gates are below the threshold and should use the prior policy path. The existing 128K-class 768-row low-memory policy remains unchanged.
- Targeted host test: `python3 -m pytest tests/test_qwen35_resident_batch_layout.py::test_prefill_config_autotunes_gt1k_chunks_from_budget -q` -> passed.
- Post-policy short gates (`benchmarks/results/2026-06-18-gpu1-gguf-q4km-memory-policy-short.json` plus one `/tmp` rerun) kept stable IDs and `22.487 GiB` peak. Because the short gates are below the 52K threshold, their policy path is unchanged; two 3-run samples varied within roughly `-1.3%..+1.2%` vs the immediately-before baseline and are recorded as run-to-run noise, not a retained short-gate speed change.
- Post-policy max-context fit search (`benchmarks/results/2026-06-18-gpu1-gguf-q4km-memory-policy-midcontext.json`): `52K/128` now passes `1303.061/89.728`, `64K/128` passes `1170.043/81.923`, `96K/128` passes `912.718/75.723`, `100K/128` passes `882.919/73.786`, `102K/128` passes `873.302/71.377`, `103K/128` passes `866.728/71.053`, all with stable one-run IDs and 1024-row chunks; `104K/128` and above OOM. Net measured window moved `51K/128 -> 103K/128` (+102% prompt tokens), with `103K/128` tracked peak `23.484 GiB`.
- Remaining blocker: Q4_K_M `128K/128` on 24GB still needs BF16 full-attention KV and/or GGUF weight-residency reduction. Do not claim 128K Q4_K_M support on GPU1 until that gate passes with short-gate prefill/decode/ID floors intact.
