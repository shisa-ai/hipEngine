# the down MMQ fix is 6.6 percent on the canonical instrument and bit-exact by measurement

## Summary

`20260928T081634.604650Z-lhl-gemma4-down-mmq-load-width-397816.md` recorded the
Q5_1 down MMQ load-width fix at **4.1 percent** from the expert-split probe, which
was the instrument that found the defect. This unit re-measures it on the
campaign's own loop metric with only the one changed file differing between the
arms, verifies bit-exactness by measurement rather than by argument, and files
the rollup. **The canonical figure is +6.6 percent, so the earlier entry's 4.1
percent is superseded.**

## Same-commit A/B on the canonical instrument

`scripts/gemma4_campaign_bench.py --prompt 512 --output 128 --samples 3
--warmup 1`, with the parent revision of
`gguf_q5_1_mmq_selected_prefill.hip` restored into the worktree for the baseline
arm and the committed revision for the candidate arm. Nothing else differs, so
this is one declared protocol measuring both arms in one session rather than two
absolute rates from different revisions.

| arm | prefill | decode |
| --- | --- | --- |
| parent revision | 0.8840 s, **579.2 tok/s** | 27.626 tok/s |
| committed revision | 0.8295 s, **617.3 tok/s** | 28.061 tok/s |
| delta | **-0.0545 s, 1.066x, +6.6%** | **+1.6%** |

`public_path_parity` and `public_generated_equals_expected` are true in both
arms, greedy sampler, so both produce the expected tokens on the public path.

**The decode movement is not incidental and has a verified mechanism.**
`gemma4_moe_prefill_route_enabled` keys on `scratch.tokens` -- the runner's
declared width -- rather than the live row count, and its own docstring says why:
"Passing the declared capacity instead makes the route a property of the runner,
so a runner's prefill and its single-token decodes take the same path." A runner
built for 512 tokens therefore runs this same MMQ kernel on its decode steps, so
the fix reaches both phases. That is worth stating rather than leaving as an
unexplained 1.6 percent.

### The audit gate and three false positives

`python3 audit/audit.py check` failed on three untriaged rows, and **none of them
are from this change**: with the kernel edit reverted the gate fails identically,
on the same two kernel rows and the same flag-branch row. All three are extractor
false positives, recorded `NOT-DEBT/keep` with the evidence in the note:

- `kernel/.../gguf_q8_0_mmq_selected_prefill.hip` -- its `no __global__ entry
  point found` signal is wrong: line 103 is `__global__ __launch_bounds__(128, 4)`
  with the kernel name on line 104, so a pattern expecting the name on the
  `__global__` line misses it. The route runs: a kernel trace of one 512-token
  prefill shows `q8_0_mmq_ds4_selected_prefill_kernel` with 2 launches and 12.5 ms
  (the layer-29 Q8_0 expert down route), reached from
  `hipengine/kernels/hip_gfx1100/gemma4/gemma4_experts.py:971`.
- `kernel/.../gguf_q8_0_mmq_selected_prefill.py` -- the same route from the
  wrapper side. `no runtime caller found` fires only because the caller is itself
  under `hipengine/kernels/`.
- `ungoverned-flag-branch/hipengine/generation/gemma4_gguf.py:322:HIPENGINE_HIP_ARCH`
  -- there is no branch. `HIPENGINE_HIP_ARCH` occurs **once** in that file and it
  is inside the factory docstring. `docs/ENVS.md:152` documents it as a HIP JIT
  build input (`Force native HIP offload arch in build cache keys`), so unset
  means "use the host device" rather than "feature disabled".

Both kernel rows' `no test file names it` signal is true but the coverage is by
route rather than by name: `tests/test_gpu_gemma4_expert_route_true_geometry.py:429`
sets `quant_key="gguf_q8_0"` and drives `gemma4_project_experts_down_mmq`, which
selects this kernel. `audit.py check` exits 0 with `audit: ok` after the refresh
and the three decisions.

## Next

   defect** -- it reads its weights from LDS caches -- so the remaining lever
   there is its 32-wide column tile or its dequant, not its memory traffic.
2. **The dense block at 277.6 ms is the second-largest and was not checked.** Its
   Q8_0 WMMA kernel dequantizes with 16 scalar byte loads per column per K-block

   block stride makes 16-byte alignment unprovable there, so the fix would need
   `__builtin_memcpy` rather than a cast, and its dequant is only about 130
   instructions per four WMMAs so the ceiling is lower than the down's was.
