# Build the Gemma4 control-smoke packet producer: a valid packet, and the envelope verdict it measures

## Summary

Piece (B) lands: ``scripts/gemma4_control_smoke.py`` is the Gemma 4 analogue
of ``scripts/execution_profile_gguf_control_smoke.py`` -- the template the
campaign recorded as missing ("The packet does not exist for Gemma4 ...
promotion is a build, and it is the highest-value remaining work"). It runs
the strict and production arms of the registered plans through
``Gemma4ResidentSession`` under their route pins, writes both variant
manifests, all four captures (strict, production, repeat, isolation), the
expected-control fixtures and task results, and invokes
``scripts/execution_profile_gate.py`` on what it wrote.

The first full packet evaluates end to end. Its verdict: **controls,
determinism and isolation all pass; the quality envelope does not.** At the
width where the declared production variant actually executes, production
(auto, grouped-int8 MMQ gate_up) against strict (grouped exact) measures
kl_mean 0.0033, kl_p95 0.0193, kl_p99 0.0584, kl_max 0.1227, top-1 98.52%
(601/610) -- all five calibrated limits missed (1e-3 / 5e-3 / 2e-2 / 5e-2 /
99%), with rows above the 0.02 review boundary, so
``status=failed automatic=false``. That is evidence for the §2.1 decision
(task #43), not a defect in the telemetry; per the evidence policy the
production route stays the default regardless -- the gate answers admission.

## Changes

- ``scripts/gemma4_control_smoke.py`` (new): gemma4 couplings swapped into
  the template's model-agnostic capture/fixture assembly -- session, route env
  (``HIPENGINE_GEMMA4_MOE_PREFILL`` grouped vs auto, the pin read per prefill
  call), the registered ``(gemma4_gguf, hip_gfx1100, gguf_q4_k_m)`` plans,
  chat-template prompt rendering, and no GDN/bulk knobs (Gemma 4 has neither;
  the session accepts those kwargs by contract). Task-artifact mode is not
  carried over: it reports the Qwen lane's retained-evidence note; main mode
  already writes the ``task-results.json`` the gate consumes.
- ``hipengine/benchmark/control_capture.py``: ``schedule_c1_control_records``
  gained an optional ``step_offset`` (default 0, so the template's callers are
  byte-unchanged) so several prompts can share one scenario.
- ``tests/test_unit_gemma4_control_smoke.py`` (new): 11 tests -- the route pin
  must be live during *every* forward of a trajectory, forced rows must carry
  the teacher's chain, step bands, the prompt loader's exactly-one-field and
  dedup rules, width padding, ``_moe_prefill_width`` derivation, and a RED
  test reproducing the exact gate collision.

### What building it corrected

- **The template's forced rows record the candidate's own emissions.** That
  works only while the arms never diverge (the Qwen smoke's no-change case);
  the Gemma 4 MMQ-vs-grouped split does diverge, so the gate rejected the
  captures with "strict and candidate capture rows must align". Forced runs
  now take the full teacher chain and record *its* tokens per row
  (``teacher_row_ids``), with a validation error when it is missing or
  misthreaded.
- **Multi-prompt fixtures collided at step 0 on physical slot 0** -- the
  template's latent ``--limit 1`` assumption (its default). Each prompt now
  occupies its own ``prompt_index * (decode_steps + 1)`` step band, in both
  the live trajectory and the schedule fixture; the RED test pins the
  collision and the fix.
- **A packet below the route width is not a route certificate.** The MMQ/WMMA
  plans need ``_WMMA_PREFILL_MIN_LANES_PER_EXPERT * expert_count`` = 2048
  lanes and the grouped folds 512; the default ``--prompt-tokens`` derives
  that width from the artifact's own metadata and records it in
  ``smoke-env.json``, cycling each row's own text (the campaign corpus-cycling
  practice).
- The envelope miss at that width is **not reconciled with the
  ``gemma4_experts`` docstring's kl_max 0.001341 measured at
  ``--prompt 1024``** -- a width below the 2048-lane plan threshold, where
  auto cannot engage the MMQ leaf. Reconciling which campaign gate produced
  that number is part of the §2.1 work, not this unit's.
