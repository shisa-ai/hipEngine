# PARO paged-KV backend pin is load-bearing

## Summary

A transfer review listed the hardcoded `_PAGED_KV_REGISTRY_BACKEND = "hip_gfx1100"`
pin at `hipengine/runtime/qwen35_paro.py:213` as the top gfx1151 defect: PARO
bypasses the gfx1151 attention override, described as "a backend-selection defect,
not proof of incorrect outputs or a speed regression."

**That characterization is wrong, and clearing the pin breaks correctness.** The
pin is load-bearing. Threading the session backend into the four paged-KV /
paged-attention resolutions does reach the gfx1151 override, and it
deterministically fails the retained PARO batch-vs-c1 equality contract.

Measured on the physical gfx1151 host (Ryzen AI MAX+ 395 / Radeon 8060S),
Qwen3.6-35B-A3B PARO, c=2, prompt 512, 128 decode tokens, `native_batch` full-attn
path compared against independent c1 through the same packed prefill/decode path:

| Arm | Result |
| --- | --- |
| Session backend threaded → gfx1151 `fixed256` body | **25/137 equal**, row 0 diverges at decode token 25 |
| Session backend threaded, repeat run | **25/137 equal**, bit-identical to the first run |
| Historical gfx1100 pin → `c1_exact` body | **137/137 equal** |
| `per_row` control | **137/137 equal** |

The change was reverted. What landed instead is a source comment recording the
measurement, a behavioural regression guard, and a correction to the audit
document that had counted this pin as clearable.

## Changes

- `hipengine/runtime/qwen35_paro.py` — comment-only. The pin now states why it
  exists, names the measurement, and says not to clear it without re-running the
  gate. **No behaviour change.**
- `tests/test_qwen35_decode_state.py` — new
  `test_qwen35_decode_state_paged_kv_backend_stays_pinned_to_gfx1100`, which
  asserts the constant and drives the real
  `decode_full_attention_context_gate_fp16_batch` call site to prove it resolves
  against `hip_gfx1100` rather than a session backend.
- `docs/20260909-GFX1151-GFX1100-TRANSFER-AUDIT.md` — the six-mechanism table's
  "Live code pin" row moves from clearable **yes** to **no**, with a new
  subsection carrying the measurement. This makes the pin the second mechanism a
  gfx1151 package change cannot safely reach, for a measured reason rather than a
  structural one.

## Validation

Command: `scripts/qwen35_batch_retained_bench.py --model
/models/hipengine/Qwen3.6-35B-A3B-PARO-packed-MTP-BF16 --fixture <derived
1024-token fixture> --prompt-length 512 --batch-size 2 --decode-tokens 128
--warmup-decode-tokens 8 --batch-decode-full-attn-path {per_row,native_batch}`,
hermetic TheRock environment, `HIPENGINE_HIP_ARCH=gfx1151`, `GPU_MAX_HW_QUEUES=2`.
Four runs, one GPU, back to back.

The fixture used for the gate is derived from
`fixtures/qwen35_paro/parent_512_32_seed1234.json` as
`prompt_ids + reversed(prompt_ids)`, because c=2 at prompt 512 needs 1024 tokens
and the parent fixture carries 512. It was removed after the gate; it was not a
golden-token oracle and its `expected_generated_token_ids` belonged to the
512-token parent.

The harness reports `status: blocked` / `decision.accepted: false` on every arm
because this run had no repo-relative artifact path, no primitive-correctness,
c1-baseline, serial-bridge, or profiler sidecar, and no `--require-cached-build`.
Those are retained-promotion plumbing requirements, not numerical ones. The field
this unit gates on is `correctness.generated_token_equality.passed`, which is the
native_batch-vs-independent-c1 comparison and is independent of that plumbing.

Reproduce with `scripts/qwen35_batch_correctness.py` is **not** sufficient here:
that harness imports `qwen35_paged_full_attn_decode_context_bf16_batch_spans`
directly and therefore tests the kernel body, not the backend selection that this
unit is about.

Narrow tier: `tests/test_qwen35_decode_state.py` and `tests/test_kv_dispatch.py`
pass (89 tests), and `tests/ -k paro` passes. The source diff is a comment, so no
GPU correctness gate applies beyond the gate above.
