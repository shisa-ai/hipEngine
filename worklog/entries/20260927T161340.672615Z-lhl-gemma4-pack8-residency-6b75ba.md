# Both expert layouts must coexist until the fallback is pack8-aware

## Summary

Closed the residency question the previous entry left open, and the answer is
**both layouts must coexist for now**.

**What does not constrain it.** The CPU reference reads `ffn_gate_up_exps`
through `layer_map.tensor(...).name` and dequantizes from the file
(`cpu_reference/gemma4.py`, `gemma4_streaming.py`), so it consumes raw GGUF bytes
rather than anything resident on device.

**What does.** `gemma4_project_experts_rows`' route 3 is `per_expert_offset`,
which reads the **raw block layout**, and the route list is a preference list that
degrades when a kernel is missing. So promoting pack8 without making the fallback
pack8-aware means holding **both** layouts.

For a 26B model's expert weights, roughly doubling that tensor's resident cost is
a real budget item rather than a rounding error - the earlier synthetic repack of
the 285.5 MB raw tensor produced a `22528 x 2816` int32 `qweight` plus fp32
`scales` and `mins`.

**The deliberate choice for the implementation unit** is therefore either to
accept the doubling, or to make the fallback pack8-aware as well so the raw copy
can be dropped. Naming both options here so the decision is made rather than
discovered when memory runs short.
