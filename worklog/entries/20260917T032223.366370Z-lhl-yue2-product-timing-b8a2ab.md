# YuE2 product-path timing against the pinned upstream, all three stages

## Summary

The M7 solver work closed the gap the campaign started from, but every comparison in
that campaign timed the solver and the decoder against recorded conditioning, so the
AR stage was never on either side of the table. This unit measures the complete
torch-free product path on one recorded case at the product's 32 ODE steps and
compares each stage against the reference's own recorded timing for that same
request. Result: the acoustic solver is now **matched** (21.2 ms per frame against
21.1 ms) and the FP32 decoder is **3.44x faster** (15.5 ms against 53.3 ms), but the
AR semantic decode is **2.63x slower** (82.1 ms per token against 31.3 ms), which is
69% of the whole path and the entire remaining end-to-end gap: 154.1 s against
137.8 s, i.e. 1.12x slower. The cause is measured: the reference batches both CFG
branches into one forward per step, this path forwards them separately and so reads
the 3.63 B-parameter weight set twice per token.

## Changes

- `scripts/yue2_case_timing.py` (new): drives one oracle case through
  `Yue2Session` with that case's own request and generation config, caps the
  semantic stage at the reference's token count, prints a per-stage table against
  the case's recorded `result.json`, and writes a provenance-bearing artifact. It
  uses the recorded `cfg_scale` on the request rather than a runtime knob, because
  `GenerationConfig` has no guidance field.
- `benchmarks/results/yue2_product_case_timing_20260917.json` (new artifact),
  `benchmarks/README.md` (product-path stage table and the branch-batching
  analysis), `benchmarks/CHANGELOG.md`, `docs/MODEL-YUE2.md` (M7 bullet).
- No runtime change: this is a measurement unit.

## Validation

- Host: zbook, Ryzen AI Max+ 395 / Radeon 8060S, gfx1151, ROCm; `torch` not
  imported (`False` printed by the run).
- Command:
  `python3 scripts/yue2_case_timing.py --case mandarin-off-s1234 --steps 32 --json benchmarks/results/yue2_product_case_timing_20260917.json`.
- Case: `mandarin-off-s1234`, 51.9 s of audio, 1 297 reference semantic tokens,
  32 ODE steps.
- Reference side is the pinned upstream's own recorded run for the same request
  (`artifacts/yue2/oracle/cases/mandarin-off-s1234/result.json`: semantic 40.597 s /
  1 298 output tokens, `execution: cuda_graph`, `attention: flash`; nar 27.317 s;
  vae 69.092 s; e2e 137.798 s).
- Reproduced twice within 0.03% (AR 119.12 s / 119.16 s, solver 30.56 s / 30.79 s,
  decoder 22.42 s / 22.47 s) with identical output sizes (1 451 semantic tokens,
  1 451 frames, 2 785 856 samples, peak 0.8049), so the comparison is deterministic
  on this host.
- Matched-unit arithmetic: AR 119.16/1451 = 82.13 ms per token against
  40.597/1298 = 31.28; solver 30.79/1451 = 21.22 ms per frame against
  27.317/1297 = 21.06; decoder 22.47/1451 = 15.49 ms per frame against
  69.092/1297 = 53.27. Total normalised to the reference's 1 297 frames: 154.12 s
  against 137.80 s.
- Weight-traffic check for the AR claim: `m-a-p/YuE2-3B` is a dense 28-layer,
  hidden-2048, vocab-184 704 checkpoint, 7.26 GB bf16 (3.63 B parameters), of which
  the gathered embedding table is 0.76 GB, so a decode step reads ~6.5 GB. The
  reference's 31.3 ms per token implies 208 GB/s; two separate branch forwards at
  82.1 ms per token is 158 GB/s; 6.5 GB in 31.3 ms with the branches apart would
  require 415 GB/s, above the host's ~256 GB/s shared-LPDDR5X peak.
- Cross-checked in the reference's source that the batching is real:
  `~/yue2-shootout/shared/upstream/yue2/sampling.py` builds
  `GraphAR(model, [prefix, negative], ...)` and calls `graph.step()` once per token,
  returning both branches' logits from one batched forward, while its eager path
  makes two model calls. Our `yue2_session.py` generation loop calls
  `runtime.forward_layers(position, branch=0)` and then `branch=1`, and
  `forward_layers` runs a single row per call, so the two forwards cannot share a
  weight read today.

## Next

- Batch the two CFG branches into one two-row AR forward. Measured expectation:
  ~41 ms per token at the current per-forward efficiency (whole path 1.37x faster
  than torch), and ~31 ms per token if the per-forward efficiency also reaches the
  reference's, which would make the whole path 1.56x faster. The AR decode's kernels
  take `rows` already, so this is a runtime change (staged rows per branch, spans for
  two rows, one logits read) rather than a new kernel family, but it changes AR
  arithmetic and needs the AR replay and session gates re-run.
- The per-token comparison is at different context lengths (our run's context is
  longer, since it generated more tokens), which if anything understates the gap;
  a same-token-count run would settle it exactly.
