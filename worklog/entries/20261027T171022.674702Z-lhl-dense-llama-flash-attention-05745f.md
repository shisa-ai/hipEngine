# dense llama tiled flash attention replaces the LDS context ceiling

## Summary

The dense Llama path now runs both attention passes on a tiled kernel whose
shared memory is a fixed K/V tile instead of a per-key score row, so the context
ceiling is the checkpoint's declared positions rather than 64 KiB of LDS. A
16,390-token prompt — longer than the 15,856 the exact kernel admitted — prefills
in 484 s on Nanbeige 4.3 33B FP8, where the exact kernel needed about 2.5 h at
15,856. The path also stops materializing a `tokens x keys` causal mask: a null
mask means "causal", which the walk bound already enforces.

## Changes

- `hipengine/kernels/hip_gfx1100/attention/dense_flash_prefill.{hip,py}` (new):
  tiled causal attention, `head_dim` 128, one block per 8 or 16 query rows and
  head, K/V staged in `kKeyTile = 64` slices with an online softmax. `tokens == 1`
  is the decode case: `position_base` is the last cached position, so the causal
  bound covers the whole context and decode needs no mask at all.
  `dense_flash_prefill_admits` returns the reason it cannot serve a shape, so the
  caller decides rather than discovering it inside a launch.
- `dense_prefill_attention.py`: `dense_causal_prefill_bf16` routes to the tiled
  kernel by default and keeps the exact block kernel as `strict`. A null
  `keep_mask_ptr` is accepted on the tiled route and refused on the fallback,
  which reads a mask unconditionally.
- `hipengine/runtime/llama_prefill.py`: `_attention_is_tiled` is computed once
  from the launcher's own admission rule; it selects the prompt bound and decides
  whether a causal mask is uploaded at all.
- `hipengine/runtime/llama_dense.py`: `MAX_DENSE_DECODE_CONTEXT` is gone. The
  cache checks only that the context is positive; memory is the bound. Added
  `max_dense_context` (the checkpoint's positions), `kv_bytes_per_token`,
  `resident_weight_bytes`, and `default_dense_context_length`, which caps the
  default at half the post-weights budget so a default never leaves the machine
  with less free memory than its own cache holds. `_DecodeScratch` keeps only the
  logit vector on the tiled route; the mask row exists for the exact fallback.
- `hipengine/generation/llama_dense.py`: the default context is
  `default_dense_context_length` (140,920 tokens for Nanbeige on this card, 28 GiB
  of KV) instead of the checkpoint's 524,288, which does not fit beside 62 GiB of
  weights. `max_prompt_tokens` is now clamped by the served context.
- `docs/REFACTOR.md`: the "no flash owner at head_dim 128" entry is closed and
  replaced by what is left — the tiled kernel only carries `head_dim` 128.

## Validation

- `uv run pytest tests/test_gpu_llama_dense_prefill.py tests/test_gpu_llama_dense_decode.py tests/test_gpu_llama_dense_rope.py tests/test_unit_llama_dense_generation.py`:
  49 passed.
- New `test_tiled_attention_matches_the_exact_kernel` covers `keys` 7/37/128/129/
  1024 at `head_dim` 128, so 1 key and 1024 keys take the same path and the
  partial tail is exercised. It asserts the tiled output against the exact kernel
  **and** against an FP64 oracle over the same BF16 operands, so a bug shared by
  both kernels cannot pass, and it asserts a null mask is bit-identical to the
  explicit causal mask. Tolerance is 5e-3 of peak because both kernels emit BF16.
- Real checkpoint, `head_dim` 128, `LLM(MODEL, max_sequence_length=16448)`:
  16,390-token prompt plus 8 greedy tokens in 483.6 s compute (weight load
  measured separately at 106.9 s), 33.9 tok/s end to end. Decode was not
  separated from prefill in this number.
- Prior measurement on the same checkpoint, exact kernel, `max_sequence_length=8192`:
  8,081-token prompt plus 12 tokens in 1,876 s wall of which ~120 s was load, so
  ~4.6 tok/s. Per-token cost drops about 7x at equal length and the growth is now
  linear instead of quadratic, which is why 16,390 tokens costs less than half of
  what 8,081 did.
- `python3 scripts/docs/check_all.py`: all 4 gates passed.

Two probe errors were mine, not the kernel's, and are recorded because both
looked like kernel bugs: `dense_causal_prefill_bf16(keys=None)` means "keys ==
tokens", so a 1-token prompt over a 3-key cache must pass `keys=3` or the kernel
is correctly told the cache is one entry long; and `strict=True` with a null mask
faults the GPU because the exact fallback dereferences the mask.

## Next

- **`execution_profile="strict"` cannot reach the dense path yet.**
  `LLM(MODEL)` resolves to the migration path and the tiled route (verified on the
  real checkpoint: `attention_is_tiled=True`), but
  `LLM(MODEL, execution_profile="strict")` raises
  `MissingRuntimeProfilePlanError` for `(llama_dense, hip_gfx1151, bf16)` because
  no plan is registered. `LlamaDenseGenerator(execution_profile="strict")` does
  select the exact kernel, and the runner honours it, so the fallback exists and
  is tested -- it is the public selector that is blocked. Recorded in
  `docs/REFACTOR.md` with the plan registration as its clearing action.
- **The tiled kernel carries one head width.** `head_dim` 128 only; other widths
  fall back to the exact kernel and its 15,856-token prompt bound. A dense
  checkpoint at another width is still LDS-bounded. Recorded in `docs/REFACTOR.md`.
- **The default context is a memory policy, not a measurement.** Half the
  post-weights budget is a choice; it gives 140,920 tokens and 28 GiB of KV here.
  If the lead wants a different fraction or the checkpoint's full 524,288, that is
  a one-line change in `default_dense_context_length`.
- **Decode at long context was not measured.** The 483.6 s figure includes 8
  decode steps whose share was not separated. Decode is now the same tiled kernel
  at `tokens == 1`, so a step reads the whole KV cache; that is where a long-context
  inter-token measurement should start.
- **Prefill is still one launch per layer over the full prompt.** No chunking, so
  a prompt's peak memory is its whole K/V plus logits. Fine at 16k; a 140k-token
  prompt should be measured before it is claimed.
