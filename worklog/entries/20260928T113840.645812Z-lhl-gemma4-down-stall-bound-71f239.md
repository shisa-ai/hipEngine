# the down kernel is stall-bound, not issue-bound: dp4a is 57 percent of VALU but VALU is 18 percent of the clock

## Summary

**Three consecutive iterations have now planned a down-projection rewrite and
retired it before writing it. This one retires the third, and corrects the
framing the first two shared: the kernel is not issue-bound at all.**

The claim to check was that the 16 `dp4a` per 32 values are half the row loop,
so an int8-unpacked Q5_1 layout that collapses them to eight is worth about a
quarter of the kernel. One PMC read prices it.

**First, the hardware.** This host is a Radeon 8060S (Strix Halo, `gfx1151`):
**40 compute units at 2.9 GHz**, not the 96 of a W7900. That fixes both rooflines:

```
dp4a issue peak   40 CU x 4 SIMD x 32 lanes x 2.9 GHz = 14.85 T dp4a/s = 59.4 T MAC/s
VALU issue peak   40 CU x 4 SIMD x 2.9 GHz             =    464 G wave-instructions/s
```

**Second, the instruction mix.** `SQ_INSTS_VALU` on the microbench reports
221.4 M wave-instructions per kernel call. The derived `dp4a` count is
`22 blocks x 128 threads x 32 rows x 22 sub-blocks x 16 / 32 = 126.9 M`, so:

```
dp4a share of VALU issue                57.3 %
VALU issue at peak, all 221.4 M          0.477 ms
measured kernel                          2.696 ms
VALU occupancy of the issue slots        17.7 %
dp4a rate                                1.51 T dp4a/s = 10.2 % of peak
```

**Third, what that means.** If the kernel were issue-bound, its 221.4 M VALU
instructions would retire in 0.477 ms. It takes 2.696 ms, so **82 percent of the
SIMD cycles have no ready VALU warp**. The kernel is stall-bound. Halving the
`dp4a` therefore removes 28.7 percent of VALU instructions but is worth **at most
5.1 percent of the clock** -- 28.7 percent of 17.7 percent -- unless it also
relieves the stall, which it does not by construction.

**So the int8-unpacked Q5_1 layout is not worth building.** It costs 1.9 GB
resident, a repacker, a new kernel variant, an oracle and loader wiring, and its
ceiling is a twentieth of one kernel that is itself 15 percent of the step.

**This also corrects the two previous entries.** Both described this kernel as
issue-bound, which is what made an instruction-count lever look attractive; the
measured issue occupancy says otherwise. The earlier facts they recorded stand --
no spill, already unrolled, time invariant to a 20 percent change in fetched
bytes, 5.96x overfetch -- and the last of those is now explained rather than
merely observed: a stall-bound kernel does not care how many bytes it fetches
past the point where they are covered.

**What the stall is, is now the open question.** At 96 VGPRs and 128-thread
blocks the kernel runs 4 blocks per CU, about 25 percent occupancy, and each
(thread, row, sub-block) issues roughly four memory operations -- two 16-byte
activation loads and two scale reads -- against 16 `dp4a` and about ten other
VALU. Every one of those memory operations is a broadcast: all 128 threads read
identical addresses, so the byte volume is tiny and the *latency* is not. That is
the shape to test next, and occupancy is the cheapest lever on it.

## Validation

```
# device
rocminfo | grep -A4 gfx1151     # -> AMD Radeon 8060S Graphics, 40 CUs, 2900 MHz

# instruction count, isolated kernel
rocprofv3 --pmc SQ_INSTS_VALU --output-format csv -d <dir> -- \
  .venv/bin/python scripts/gguf_q5_1_down_mmq_microbench.py \
  --rows-per-expert 32 --warmup 1 --iters 3
# -> 885575680 over 4 launches = 221.4 M wave-instructions per call

# timing for the same shape
# -> 2.696 ms/call median
```

Two caveats on the counter. `SQ_INSTS_VALU_INT`, `SQ_INSTS_VMEM` and
`SQ_INSTS_VALU_FMA_F` all return zero rows on this part, so the mix below the
VALU total is derived from the source rather than measured, and only the total is
evidence. And a multi-`--pmc` request runs as several passes but wrote only the
first pass's CSV here, so the counters were collected one at a time.

## Next

1. **Test the occupancy hypothesis before touching the arithmetic.** The kernel
   runs 4 blocks per CU at 96 VGPRs. The microbench makes this cheap: a build
   with `ROWS_PER_PASS` at 16 costs registers (80 VGPRs, 6 blocks per CU) and one
   with `__launch_bounds__(128, 6)` asks for the same explicitly. If time falls
   when occupancy rises, the stall is latency and the lever is resident warps;
   if it does not, the stall is dependency latency inside the row loop and the
   lever is more independent chains.
2. **Only then re-open the arithmetic.** Nothing in this measurement rules out a
   different inner loop, but the instruction-count argument for one is now
   bounded at 5 percent of this kernel, so a proposal has to come from the stall
   side rather than from counting instructions.
