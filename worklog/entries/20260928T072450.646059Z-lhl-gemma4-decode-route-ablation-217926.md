# the dense q8 route is 43 percent of decode and attention is 5.8 not 19

## Summary

I ran the decode route ablation for the first time, on current code, because every
decode conclusion I had been carrying rested on a share table I had never verified
myself. **The table I had been using is wrong by a wide margin, and the priority it
implied was wrong with it.**

Baseline: **35.53 ms/token, 28.14 tok/s**.

| route skipped | saves | share of step |
|---|---|---|
| `no_dense_q8_both` | 15.23 ms | **42.9%** |
| `no_all_gemv` | 15.10 ms | 42.5% |
| `no_dense_q8_bf16` | 7.14 ms | 20.1% |
| `no_norm_rope` | 4.05 ms | 11.4% |
| `no_lm_head_q8_f32` | 3.79 ms | 10.7% |
| `no_moe_elementwise` | 3.09 ms | 8.7% |
| `no_router` | 2.76 ms | 7.8% |
| `no_attention` | 2.06 ms | **5.8%** |
| `no_experts` | 0.54 ms | **1.5%** |

## What I had been carrying, and what is actually true

| route | what I had believed | measured |
|---|---|---|
| experts | **55.1%** | **1.5%** |
| attention | **19.1%** | **5.8%** |
| dense | **20.6%** | **42.9%** |

The belief came from a census figure I cited in several entries without running the
instrument. The instrument measures something different, and on current code the
picture is inverted: **the dense Q8 path is the step**, and the expert path -- which I
had treated as the dominant cost -- is nearly free.

## What this changes

**The decode attention lever is worth far less than I claimed.** I wrote that the
probe's 1.72x on the attention kernel was "about 8% end to end" on a 19.1% share.
At a **5.8%** share, the same 1.72x is worth **2.4% end to end**. That does not move a
1.53x gap, and it was never going to. Every entry that carried the 8% figure
overstates it by 3.3x.

**The real target is the dense Q8 GEMV path.** 42.9% of the step, with the `lm_head`
alone at **10.7%** -- a single GEMV costing more than a tenth of the token. That is
where a 1.53x has to come from.

`no_dense_q8_both` (42.9%) and `no_all_gemv` (42.5%) are nearly equal, and the two
individual dense routes sum to 30.8% rather than 42.9%, so the arms overlap and the
individual shares are not additive. The reliable statement is that the dense GEMV
family is ~43% and the expert family is ~1.5%.

## A host fact worth knowing before anyone profiles

The ablation's own docstring:

> `rocprofv3 --kernel-trace` serializes dispatches on this host, so a traced decode run
> inflates kernel durations about **19x** and its shares do not survive.

So a profile-derived share table is not usable on this host. This ablation is the
instrument that is, which is why the shares above are the ones to trust.

## Validation

```
env -u ROCR_VISIBLE_DEVICES PYTHONPATH=. .venv/bin/python \\
    scripts/gemma4_decode_route_ablation.py --json /tmp/abl.json
```

Completed on gfx1151, one device, backend resolved to `hip_gfx1151` and quant to
`gguf_q4_k_m`. The probe times each arm at two output lengths and takes the difference,
so the per-token figure is steady-state decode with prefill and first-token latency
removed. It is a skip-the-launch diagnostic, so outputs are wrong on purpose and only
the timing is read.

The 28.14 tok/s baseline is consistent with the objective's recorded 27.31 tok/s,
which is the check that this is measuring the same thing those runs did.
