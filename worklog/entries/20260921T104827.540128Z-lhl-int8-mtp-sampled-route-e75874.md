# Sampled MTP on INT8 KV: the refusal is a declaration gate, not a capability miss

## Summary

A `temperature > 0` speculative MTP request on INT8 KV is refused with
`mtp_sampling_unsupported`. The question was whether the sampled accept path is
storage-agnostic or genuinely blocked on INT8 KV. It is **storage-agnostic**: the
accept consumes verified rows and their distributions, never KV storage. The gap
is a **declaration only**, and the declaration is the single missing axis.

## The chain, traced end to end

1. **Request → sampling mode.** `speculative_serving_sampling_mode`
   (`hipengine/generation/sampling.py:897`) returns `"sampled"` for any request
   that actually samples. Measured directly:

   | request | mode | unservable blockers |
   | --- | --- | --- |
   | `temperature=0` | `greedy_fast` | — |
   | `temperature=0.7` | `sampled` | — |
   | `temperature=0.7 + repetition_penalty` | `sampled` | — |
   | `temperature=0.7 + presence_penalty` | `sampled` | — |
   | `temperature=0.7 + logit_bias` | `sampled` | — |
   | `temperature=0.7 + suppress_token_ids` | `sampled` | — |
   | `temperature=0.7 + ignore_eos` | `sampled` | — |
   | `temperature=0.7 + min_tokens` | `processed_argmax` | `min_tokens`, `eos_token_id` |
   | `temperature=0.7 + stop_token_ids` | `processed_argmax` | `stop_token_ids` |
   | `temperature=0.7 + logprobs` | `processed_argmax` | `logprobs` |

   The sampling law reaches the sampled route with no unservable blocker; the
   finish-rule and metadata fields do not reach it at all, and are refused on
   *both* storages. That is task 6's territory, not this gap.

2. **Sampling mode → refusal.** Admission resolves evidence first, then the
   implementation declaration (`hipengine/models/qwen35.py:860`). No INT8 evidence
   row is sampled-keyed, so the declaration decides. Every INT8 declaration omits
   `sampling_modes`, so it inherits `("greedy_fast",)` from
   `hipengine/speculative/serving.py:566`, and the sampled key fails the check at
   **`hipengine/speculative/serving.py:592`** with `mtp_sampling_unsupported`.
   Measured through the real plugin on the gfx1151 artifact:

   | storage | mode | rows | admitted | reason |
   | --- | --- | --- | --- | --- |
   | `int8_per_token_head` | `greedy_fast` | 1 | yes | `implemented_gguf_dense_int8_native_chain` |
   | `int8_per_token_head` | `greedy_fast` | 2 | yes | `implemented_gguf_dense_int8_gfx1151_group_native_chain` |
   | `int8_per_token_head` | `sampled` | 1 | **no** | **`mtp_sampling_unsupported`** |
   | `int8_per_token_head` | `sampled` | 2 | **no** | **`mtp_sampling_unsupported`** |
   | `bf16` | `sampled` | 1, 2 | yes | `automatic_native_sampled_c1_c4` (evidence) |
   | `bf16` | `processed_argmax` | 1, 2 | no | `mtp_sampling_unsupported` |

3. **Is the accept storage-agnostic?** Yes, by construction.
   `sampled_accept_summary` (`hipengine/generation/mtp_sampled_accept.py:96`) takes
   the verify batch, the verifier's **row-major logits matrix**, the request's
   sampler state, its params, and its draw stream. It forwards to
   `sampled_accept_from_distributions` (`hipengine/speculative/sampling.py:202`),
   which takes `TargetVerifyBatch` plus two `SparseDistribution` sequences per
   row. Neither module references KV storage, a storage dtype, or a device
   buffer; `hipengine/speculative/sampling.py` imports exactly one thing from the
   rest of the engine, `AcceptResult` and `TargetVerifyBatch`.

   Whichever attention path produced the logits — the BF16 context-batch
   decoder, the direct INT8 split-K leaf, or the retained INT8 planes — the
   verifier returns the same logits matrix, and the accept is a function of that
   matrix alone.

## Statement of the gap

**A declaration gap, not a capability miss.** The kernels that produce the
sampled route's inputs already run on INT8 KV: the greedy INT8 declarations admit
the same backends, layouts, widths, and scale contract that the sampled route
needs, and the packed INT8 verifier that produces the logits rows is landed
(commit `e1808ac64`). The single differing axis is `sampling_modes`.

The one thing that is genuinely **unmeasured** is numerical: the sampled route's
induced-law gate (824/824 comparisons, max total variation 4.5e-16) was measured
on BF16. Whether the INT8 verifier's row logits reproduce that law as tightly is
not known. That is a promotion/claim question, not a runnability one
(`docs/EXECUTION-PROFILES.md` section 1.1; AGENTS.md "Capability is the only
gate"). It does not refuse the request.

## Changes

- `tests/test_unit_int8_mtp_serving.py`:
  - `test_dense_int8_mtp_serves_the_sampled_route_its_accept_path_implements`
    (`[1]`, `[2]`), marked `xfail(strict=True)`. It pins the intended contract
    and carries the measured failure and its exact source line in the reason.
    `strict=True` fails the suite the moment the declaration lands, so the marker
    cannot be left behind. Verified as a true RED with `--runxfail`: it fails with
    `AssertionError: mtp_sampling_unsupported`,
    `failed_axes=('mtp_sampling_unsupported',)`,
    `implementation_key='gguf_dense_int8_native_chain'`.
  - `test_sampled_accept_takes_verified_rows_and_no_storage_input`: asserts the
    accept's parameter set exactly, and that no parameter is storage-shaped, so a
    future storage input has to be argued rather than added.
  - `test_bf16_sampled_mtp_is_admitted_so_the_int8_refusal_is_storage_keyed`:
    without this contrast, `mtp_sampling_unsupported` would be
    indistinguishable from a blanket refusal of the sampled mode.
- No production change. This unit identifies the gap; widening the declaration is
  the next unit's work, and the strict xfail is what will force it.

### Not run: the live INT8 server trace

The task suggested tracing the refusal against a live INT8 KV server on gfx1151.
That host is this machine, and it cannot start a second hipEngine server: another
agent session's server (PID 4175913, tmux session `therock`) holds 96.3 GiB of
GTT (`/proc/4175913/fdinfo/17: drm-total-gtt: 100940920 KiB`), leaving less than
the engine's own 3 GiB reserve after the model loads. Its startup ladder halved
the context 23552 -> 11776 -> 5888 -> 2816 and failed at every step, so no context
or active-request setting fits. The refusal was therefore traced through the real
plugin's `resolve_speculative_mtp_serving_plan` — the same function the server
calls — which is a stronger basis for this particular question than a server log
line, because the refusal is deterministic admission logic that fires before any
GPU work.
