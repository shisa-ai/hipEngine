# GGUF automatic resident context sizing

## Summary

`hipengine serve --model <gguf>` with no sizing flags used to give the dense GGUF
route a **256-token resident context**. The server reported
`max_context_tokens=auto` and `docs/API.md` claimed it preallocated
`min(model max context, estimated allocatable context)`, but that sentence
described the PARO route only: on GGUF the omitted `--max-context-tokens` reached
`_acquire_shared_session` as `max_sequence_length=None`, and
`_FullStackScratch.allocate` fell back to `block_size` = 256 positions.

The resident GGUF route now sizes its own context. After weights load it prices
the full resident footprint against current free HIP memory and takes the largest
block-aligned context that fits with a safety reserve. An allocation failure
re-prices from the memory that is actually free and retries smaller, so a near
miss degrades instead of aborting startup.

Measured on the W7900 (48 GiB), no sizing flags, one short chat request each:

| Model | KV geometry | Selected context | Old behavior |
| --- | --- | ---: | ---: |
| Qwen3.8-27B-Q4_K_M | 16 full-attn layers x 4 KV heads x 256 | 45,568 | 256 |
| Qwen3.6-35B-A3B-UD-Q4_K_M | 10 full-attn layers x 2 KV heads x 256 | 98,304 | 256 |
| Qwen3.8-27B-Q4_K_M, 8.12 GiB usable (24 GB-class budget via reserve) | as above | 11,520 | 256 |

No per-model table is involved. The selection follows each model's own KV growth
rate and the free memory at load time, which is the property the two rows above
are checking.

## Changes

- `hipengine/generation/qwen35_gguf.py`: `Qwen35GGUFBringupGenerator` gains
  `_resident_capacity_estimate`, `_resolve_auto_context`, `_recalibrated_auto_context`,
  `_construct_shared_session`, and `_attach_capacity_estimate`. `_acquire_shared_session`
  resolves the context when the caller pinned none, and `create_resident_model_runner`
  now stores the owner on the generator so the server's existing
  `_resident_session_for_engine` lookup finds a session. `Qwen35GGUFResidentModelRunner`
  gains a `_session` property returning the batch owner for reporting.
- `hipengine/runtime/qwen35_gguf_runner.py`: the capacity estimate exposes
  `bytes_per_token` / `requested_kv_bytes` / `requested_context_overhead_bytes`
  aliases so the server's PARO-shaped KVCache log and `/ready` payload cover both
  resident routes without branching on the route.
- `hipengine/server/api.py`: `_prepare_resident_session` logs the KVCache summary
  once the resident session exists, so the summary appears on the lazy-load path
  as well as the eager path. The summary and the below-model-max warning now name
  the resident slot count, because the slot count is what makes the selected
  context smaller than a reader might expect.
- `scripts/gguf_capacity_probe.py`: `--max-batch-size`, so a Tier-1 probe can
  certify the serving envelope. The server reserves one full-context KV plane per
  resident slot, so a batch-1 probe does not price the configuration the server
  actually runs.
- `docs/API.md`: the automatic-sizing paragraph now states that it covers both
  resident routes, describes the re-price/retry fallback, and names the
  `HIPENGINE_GGUF_AUTO_CONTEXT=0` escape hatch.

### Sizing model

The estimator is the existing closed form, reused rather than reimplemented:
`estimate_qwen35_gguf_kv_capacity` bisects block-aligned contexts against a
`price()` that returns `scratch + kv_pool + workspace_lease + transient`. Free
memory is measured *after* weights load, so weights are excluded rather than
guessed at.

The marginal cost is exactly linear above the INT8 mirror threshold and is
composed of measured terms, not fitted ones:

```
marginal_bytes_per_token = slots * page_bytes/256          # KV plane
                         + slots * page_bytes/256          # packed-verify lease
                         + transient_bytes_per_token      # 74 KiB default
```

For the 27B at 4 slots and BF16 KV that is `262144 + 262144 + 75776 = 600064`,
against a measured `600963`. The residual is scale/metadata bytes. The two
endpoint checks in `tests/test_unit_qwen35_gguf_capacity.py` pin this identity.

### Slot count, not just free memory

`Qwen35GGUFResidentModelRunner` reserves `capacity` slots and prices the context
with `max_batch_size=capacity` (4 for auto-selected GGUF). That is deliberate:
the server advertises four concurrent AR requests, and a context priced for one
slot cannot serve four. It is also the dominant term — on the 27B the 4-slot
reservation costs about 3x the context a single slot would allow. The startup
warning names `--max-active-requests` as the lever for that trade.

### Fallback policy

`HIPENGINE_GGUF_AUTO_CONTEXT_ATTEMPTS` (default 4) bounds the retry loop. Each
retry re-prices from live free memory, and the step size depends on what the
re-price says:

- The re-priced model now claims less than what failed: the model is tracking
  this machine, so trim its answer by a quarter and keep the remaining context.
- The re-priced model still claims more than the allocator refused: its transient
  term is not describing this machine, so halve instead of trimming. Geometric
  decay converges inside the attempt budget where a 25% trim does not.

The failed attempt is a hard upper bound, and a fallback updates the session pool
key so a reduced session is never handed out under the original key.

## Validation

Unit: `tests/test_unit_qwen35_gguf_capacity.py` (24 tests) covers the estimate
model, the plan/allocator equivalence, and the new resolver — caching per batch
size, the disable flag, geometry-unavailable degradation, reserve sensitivity,
the OOM retry converging under a ceiling, pinned contexts *not* retrying, and the
recalibration step staying strictly smaller and block-aligned. All pass.

`pytest tests/ -k "unit and gguf"` — 2196 passed.
`pytest tests/ -k "unit and (gguf or server or api or context or kv)"` — 2805
passed, 1 failed: `test_unit_grammar_masks.py::test_server_schema_does_not_use_json_tool_prefix_for_xml_engine`,
a pre-existing `ModuleNotFoundError: No module named 'llguidance'` environment
gap unrelated to this change.

Tier-1 capacity probe at the auto-selected context, certifying the exact server
envelope (BF16 KV, 4 slots):

```
python3 scripts/gguf_capacity_probe.py --model /models/gguf/Qwen3.8-27B-Q4_K_M.gguf \
  --max-sequence-length 45568 --kv-storage bf16 --kv-scale-dtype fp16 \
  --max-batch-size 4 --prompt-length 128 --decode-tokens 8 \
  --json benchmarks/results/2026-09-12-w7900-27b-auto-context-45568-bf16-c4-probe.json
```

`status=pass`, `finite_logits=true`, `tracked_peak_gib=28.89`.

Server runs (`python3 -m hipengine.server --model <gguf> --no-eager-load`,
W7900 GPU0, one short chat request each):

| Model | `HIPENGINE_GGUF_KV_CAPACITY_RESERVE_MIB` | Selected | KVCache summary |
| --- | ---: | ---: | --- |
| 27B | default (512) | 45,568 | `slots=4 ... usable=27.12 GiB reserve=0.50 GiB bytes_per_token=600963` |
| 27B | 19968 | 11,520 | `slots=4 ... usable=8.12 GiB reserve=19.50 GiB bytes_per_token=600963` |
| 35B-A3B | default (512) | 98,304 | `slots=4 ... usable=23.27 GiB reserve=0.50 GiB bytes_per_token=240386` |

All three loaded, allocated, and generated (`finish_reason=length` on the 27B at
`max_tokens=16`, `finish_reason=stop` on the 35B-A3B). `/ready` reports the
resolved context and the full estimate payload.

`HIPENGINE_GGUF_AUTO_CONTEXT=0` end to end: `max_context_tokens=unknown`, no
estimate payload, generation still works — the historical behavior.

One defect was found and fixed during this validation: `_packed_workspace_lease_needed`
first read `_engine_loop_config` / `_prefix_cache_mode` off the generator, but
those attributes live on `Qwen35GGUFResidentModelRunner`, so the mirror always
took its conservative fallback. It now reads them from the resident model runner
stored by `create_resident_model_runner`. The server path was unaffected because
its 4-slot owner short-circuits the first check; the batch-1 path was affected.

### Open item: the packed-verify workspace lease is a reservation

The estimator prices a second full-context KV plane for the packed-verify
workspace lease. On the clean-device run the pool reported
`current_bytes=23.7 GB` against `high_water_observed_bytes=11.9 GB`, and the
device had only 27.12 GiB free — so the lease is not physically backed at
reservation time. Pricing it fully is the safe direction (a 4-way concurrent
packed-verify batch would need it) but it roughly doubles the priced KV term and
therefore roughly halves the selected context.

Whether the auto-selection should price the lease at full reservation or at
expected occupancy is unresolved. It is a real capacity decision, not a
bookkeeping one, and it needs a concurrent-batch measurement rather than a
reasoning step. The current behavior is the conservative one and is what the
fallback path protects.
