# the long-context ladder runs to 256K, and it found the decode dip the boundary hid

## Summary

hipEngine's Gemma 4 prefill and decode are measured end to end from 4096 to
262,144 tokens, all through the public surface, with `public_path_parity` True
at every point. **The ladder runs all the way to 256K**, which the 2026-09-30
boundary diagnostic could not do above 8192 because the strict attention
kernel's shared-memory bound refused it.

| prompt | prefill tok/s | decode tok/s | peak GiB |
| --- | --- | --- | --- |
| 4096 | 1111.9 | 25.59 | 31.75 |
| 8192 | 1061.6 | **16.83** | 32.63 |
| 32768 | 819.5 | 25.98 | 37.89 |
| 65536 | 631.8 | 23.47 | 44.77 |
| 131072 | 407.5 | 19.39 | 58.58 |
| 262144 | 248.2 | 14.79 | 86.20 |

The 256K request completes, generates exactly 128 tokens, and the continuation
is coherent — the frozen corpus's last sentence is cut mid-word and the model
finishes it and resumes the cycle.

**The decode curve is not monotone, and that is the finding.** Decode at 8192
keys (16.83 tok/s) is slower than at 262,144 keys (14.79 is lower, but at
32,768 it is 25.98) — the dip is isolated and reproducible: the 2026-09-30
diagnostic recorded 16.72 at the same point against 25.24 at 4096.

## What the dip is

It is not the context. It is which kernel a one-token block selects.

`select_prefill_attention` serves a one-token block with the strict decode
kernel whenever `gemma4_decode_max_keys()` admits the key count, and with the
WMMA full kernel's decode shape above that. The rule's stated reason is that
the WMMA kernels tile 16 query rows wide, so one row wastes fifteen sixteenths
of every op.

That premise is stale in two ways, and I measured both. One layer, tokens=1,
identical buffers and arguments in both arms, alternating repetitions, median
of 9:

| keys | strict | WMMA decode shape | WMMA/strict |
| --- | --- | --- | --- |
| 512 | 0.12 ms | 0.27 ms | 2.35x |
| 1024 | 0.21 ms | 0.47 ms | 2.21x |
| 2048 | 0.37 ms | 0.50 ms | 1.33x |
| 4096 | 0.87 ms | 0.55 ms | **0.64x** |
| 8192 | 3.35 ms | 0.64 ms | **0.19x** |

The crossover is between **2048 and 4096 keys**, not 15,856. At 8192 keys the
strict kernel is **5.2x slower**, and it is super-linear: 0.87 ms at 4096 and
3.35 ms at 8192, 3.9x for a 2x key increase. The WMMA kernel is no longer 16
rows wide for a decode — `shape_for_tokens(1)` picks the 2-row, 8-GQA-head
shape, so one of *two* rows is wasted, not fifteen of sixteen — and the strict
decode kernel's parallelism is structurally low, `grid = tokens * num_heads` =
16 blocks, which is the same limitation the key split was added to work around.

## A live defect, found while measuring

**A context in [15617, 15856] prefills successfully and then raises on the
first decode.**

    LLM(max_sequence_length=15928), a 15800-token prompt, 4 greedy tokens:
    GenerationExecutionFailed ... cause=NotImplementedError: Gemma 4 gfx1100
    attention requires 66276 bytes of shared memory for head_dim=512,
    keys=15801; this kernel supports at most 65536 bytes

The same script at a 15600-token prompt returns normally.

Two bounds disagree by 240 keys. `gemma4_decode_max_keys()` is 15856 — the
decode kernel's own `keys + 528` floats — and `_strict_decode_serves` admits
the strict variant up to it. The launcher validates with
`gemma4_attention_shared_bytes`, which takes
`max(block_requirement, decode_requirement)` and so refuses above 15616. The
selection promises a path the launcher will not start.

It is pre-existing — it arrived with the WMMA variants that made contexts above
15616 servable at all, not with this unit — and it fails loudly rather than
answering wrongly. **I did not fix it here**: the fix is a change to which
kernel a one-token block selects, which is a routing change to production
arithmetic and needs its own gate. Filed as a follow-up with the measurement.

## Changes

- `scripts/gguf_capacity_probe.py` routes on the artifact's
  `general.architecture`. Before this, a gemma4 artifact died inside the
  loader with `expected GGUF architecture 'qwen35' or 'qwen35moe', got
  'gemma4'` — **the tier-1 protocol could not answer a capacity question about
  this model family at all**, so the only option was the expensive point tier 1
  exists to avoid. gemma4 resolves the same generator `LLM` would and drives
  its runner; qwen35/qwen35moe keep the resident-session route; any other
  architecture exits by name before allocating.
- `tests/test_unit_gguf_capacity_probe.py` (new, 6 cases, no device).
- `benchmarks/results/2026-10-02-gemma4-gfx1151-262144-capacity-tier1.json`,
  `benchmarks/results/2026-10-02-gemma4-gfx1151-long-context-ladder.json`.

## Validation

- **Tier 1 first, as the protocol requires**: the 262144 envelope allocates and
  runs a short prefill and decode with finite logits, 82.33 GiB peak against
  124 GB unified, in 40 s. The full-length point cost 1056 s.
- All six ladder points ran to completion with `public_path_parity` True.
- The 4096/8192 boundary re-run reproduces the recorded rows within 1-2 percent
  (1103 -> 1111.9 and 25.24 -> 25.59; 1042 -> 1061.6 and 16.72 -> 16.83).
- The 256K continuation decoded with the artifact's own tokenizer and checked by
  reading it.
- Kernel A/B for the dip, plus the refusal reproduced end to end at two prompts
  that differ only in whether the first decode key lands in the window.

## Next

- The follow-up: fix the routing. Both halves are one decision — use the
  measured crossover instead of `gemma4_decode_max_keys()` — which fixes the
  [15617, 15856] refusal *and* the 5.2x decode loss at 8192. It needs a gate,
  because moving the crossover changes which kernel serves contexts that work
  today.
- The prefill at 262144 is 1056 s. From the mask-cost unit's decomposition that
  is roughly 240 s non-attention, 6.4 s mask, and ~750 s of attention walk at
  about 7.5 TFLOP/s. The walk is the long-context target and it is still
  unprofiled.
