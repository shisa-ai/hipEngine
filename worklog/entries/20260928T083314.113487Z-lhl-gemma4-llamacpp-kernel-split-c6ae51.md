# llama cpp traces at 495 ms of device time against our 830 and the whole gap is two numbers attention at 6x and the gemms at 1.5x

## Summary

The prefill gap is now measured on both engines with the same instrument
(`rocprofv3 --kernel-trace`), and it decomposes cleanly. **hipEngine's prefill is
829.8 ms of device time against llama.cpp's 495 ms, and 100 percent of our
830 ms is kernel time** -- there is no host overhead, launch gap, or dispatch
cost to reclaim. Of the 334 ms difference, **147 ms is attention** (ours 175.4 ms
against llama.cpp's 28.8 ms, a 6.1x gap) and **185 ms is GEMM** (ours 580.6
against llama.cpp's 395.9, a 1.47x gap).

The attention gap has a named cause: **both of our prefill attention kernels
launch one block per (query row, head), so every block re-reads the whole KV.**
llama.cpp's `flash_attn_tile` uses 256x256 query-by-key tiles. That is a 1024x
re-read against a tile, and it is why the kernel runs at 923 GB/s of L2 traffic
instead of at compute.

The one lead that looked free is not: the tiled variant added in `75f8ef6aa` is
**worse** at the objective's context lengths, measured here, and the reason is
that it tiles over keys only -- its grid is also `tokens * num_heads`.

## The attention defect, quantified

`launch_gemma4_attention_prefill` and `launch_gemma4_attention_prefill_tiled`
both do:

```
const dim3 grid(static_cast<unsigned int>(tokens * num_heads));
```

One block per (query row, head). At pp512 with the artifact's shapes (16 query
heads, 8 KV heads, head_dim 256 on the 25 sliding layers) that is 8192 blocks per
layer, each reading all 512 keys at 256 dimensions for both K and V:

```
8192 blocks x 512 keys x 256 dim x 2 tensors x 2 bytes = 4.29 GB per layer
```

The KV actually stored for that layer is 512 x 8 x 256 x 2 x 2 = 4.19 MB. **The
re-read factor is 1024.** Measured, the sliding row takes 4.65 ms per layer
launch, so 4.29 GB / 4.65 ms = **923 GB/s** -- the kernel is L2-traffic bound,
not compute bound.

llama.cpp launches `flash_attn_tile<256,256,16,2,false>` twice per layer (the
causal diagonal and the off-diagonal, 50 dispatches for 25 layers) and covers
256 query rows per block, so it reads the KV a small constant number of times.
Its 20.2 ms over 25 layers is 0.81 ms per layer, and at 8.4 MB of KV traffic that
is 10 GB/s -- **compute bound at 5.3 TFLOP/s** where we are traffic bound at
0.93 TFLOP/s.

## The tiled variant is worse here, and its grid says why

Measured directly against the strict kernel through both `extern "C"` entry
points on identical inputs, bf16, median of 5:

| tokens | case | strict ms | tiled ms | ratio | bit-exact |
| --- | --- | --- | --- | --- | --- |
| 512 | swa 256d 16q/8kv window=1024 | 4.65 | 4.94 | **0.94x** | yes |
| 512 | full 512d 16q/2kv window=0 | 6.88 | 6.29 | 1.09x | yes |
| 1024 | swa 256d 16q/8kv window=1024 | 18.99 | 21.25 | **0.89x** | yes |
| 1024 | full 512d 16q/2kv window=0 | 29.53 | 26.59 | 1.11x | yes |

Weighted by the artifact's 25 sliding and 5 global layers, wiring the tiled
variant in would cost **4.3 ms at 512 tokens and 41.9 ms at 1024**. All four rows
are bit-exact, so this is a performance result and not a correctness one.

That agrees with `20260928T074732`, which measured 0.91x to 1.06x at 2048 keys
and 2.46x at 8192. **The tiled kernel buys occupancy by shrinking the LDS
footprint, and occupancy is only the binding constraint once the strict kernel's
footprint forces one block per CU -- which happens at 8192 keys, not at 512.**
Its grid never changed, so it never touched the traffic problem.

## Next

1. **Query-tile the prefill attention.** One block should own a tile of query
   rows and stream key tiles through LDS, so the KV is read once per query tile
   instead of once per query row. That is the 147 ms, and it grows with context
   -- the 2026-09-27 baseline already showed our prefill falling from 257 to 230
   tok/s between 512 and 1024 prompt tokens while llama.cpp rises from 909 to
   1183. This is a real kernel, and the previous tiled attempt's 3a/3b
   correctness split is the part to get right.
2. **The dense q8_0 path is the GEMM gap**: 277.7 ms against llama.cpp's 105.6 on
   the same weights. The ISA shows our dequant is already vectorized (12
   `global_load_b128`, no scalar byte loads) but spends about 8 instructions per
   element on a `bfe -> cvt_f16_i16 -> cvt_f16_f32 -> mov_b16 -> pk_mul_f16`
   chain, 209 of the kernel's 1191 instructions being `s_delay_alu` stalls. The
   `v_cvt_f16_f32` is a float detour the source asks for and the value cannot
   need.
3. The expert block is at parity with llama.cpp and needs nothing.
