# Prove the Gemma4 session adapter is arithmetic-transparent on the real artifact

## Summary

Piece (B)'s adapter shipped in the previous entry with only stub-backed tests.
This wires it to a real runner: one greedy trajectory runs directly through
`runner.forward` and the same trajectory through `Gemma4ResidentSession`, on
the 17 GB fixture, and the logits must be byte-identical. They are. The
adapter adds, reorders and re-scales nothing, so it cannot perturb a gate
result later.

## Decisions

- **Two stub rows triaged `NOT-DEBT` rather than fixed.** The extractor reads
  `raise NotImplementedError` in runtime code and calls it a stub; both of
  mine are message-bearing contract rejections with the opposite intent:
  - `gemma4_session.py:89` refuses to fake a `reset()` by mutating position,
    because only the runner knows what accumulated state to clear
    (`Gemma4Runner.reset` exists at `runtime/gemma4.py:773`).
  - `gemma4_session.py:155` refuses `return_logits=False`, because
    `forward` always computes logits (`runtime/gemma4.py:813`), so honoring
    the flag would do the work and throw it away. The kwarg exists only for
    the smoke's signature, which passes `True` at lines 191/226/257.
  Both notes cite the file:line evidence and name what the check mistook, per
  `audit/agents/triage.md` ("NOT-DEBT is a first-class outcome"). The budget
  was not raised.
- **The full smoke `--architecture gemma4` mode was not attempted.** `main()`
  resolves the strict and production plans up front
  (`execution_profile_gguf_control_smoke.py:603-615`), and
  `resolve_runtime_profile` for gemma 4 raises `ExecutionProfileNotRegistered`
  until (A) lands. Adding a mode that skipped that would be a smoke without
  its gate, so the wiring test above is this iteration's deliverable instead.
