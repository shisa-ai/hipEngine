# gfx1151 Q4 dual-SiLU prefill: 16-column tile rejected and removed

## Summary

The 16-column dual-SiLU prefill arms registered in
`worklog/entries/20260913T123232.885727Z-lhl-q4-dual-prefill-col16-candidates-d1b3ba.md`
are **rejected by measurement and removed**. They are bit-identical to the
retained 32-column owner and 29-59% slower at every prefill shape, so the
retain-if-exact-and-non-regressive rule fails on the second clause.

Same-host A/B on real `blk.0.ffn_gate`/`blk.0.ffn_up` Q4_K tiles, the tile-knob
screen's own harness and flags, three invocations per shape. Ratios are
control/candidate.

| Rows | Control (32 cols x 256 rows) | `col16_row256` | ratio | `col16_row512` | ratio |
| --- | --- | --- | --- | --- | --- |
| 256 | 3.312 ms | 4.640 ms | **0.714** | 8.099 ms | **0.409** |
| 512 | 6.622 ms | 9.895 ms | **0.669** | 9.314 ms | **0.711** |
| 1,024 | 13.125 ms | 20.788 ms | **0.631** | 18.984 ms | **0.691** |
| 2,048 | 26.026 ms | 42.444 ms | **0.613** | 38.142 ms | **0.682** |
| 4,096 | 52.146 ms | 85.978 ms | **0.607** | 78.163 ms | **0.667** |

Worst per-cell spread across invocations **3.9%** against a 29-59% effect;
**bit-identical in all 30 cells**; the control column reproduces the in-situ
profiled owner within **0.1%** (6.622 ms here, 6.629 ms in the screen, 6.637 ms
in the profile).

The blocker is structural, not a tuning miss. The weight decode needs
`threads/4 >= 2 matrices x (columns/2)` decode pairs, exactly saturated at 32
columns with 128 threads. At 16 columns only 64 of 128 threads decode, each doing
the same 32 k-values per sub-block, so a block's decode takes as long as the
parent's while its WMMA work halves. Blocks double for the same output, so total
decode time doubles and total WMMA time is unchanged. With the decode at about
40% of the parent's issue stream, that predicts roughly 1.4x; the measurement
gives 1.40-1.65x. The screen's first-ranked candidate had assumed that halving
columns halves the per-block decode for the same compute; the screen's own
sibling measurement (16 columns 1.7x slower) was right and its instruction-stream
ranking was wrong.

sha256 in the artifact, BF16 KV):

```bash

  PYTHONPATH=. .venv/bin/python scripts/qwen38_packet4_q4_dual_silu_row_leaf.py \
    --model /models/gguf/Qwen3.8-27B-Q4_K_M.gguf \

    --output /tmp/q4-col16-ab/run$i.json

  --out /tmp/artifact-check.json   # byte-identical to the committed artifact
```

Correctness gate: the harness compares each arm's full output buffer against the
parent owner's on real model tensors, and every one of the 30 cells is
bit-identical; `assemble.py` fails closed otherwise. The arms' own RED gates
(parent parity, unfused-chain parity, and `kernels/cpu_reference` on both
projections) passed in the previous unit and are removed with the arms.

Revert verification: `git diff 88e0e6b38 -- hipengine/kernels/hip_gfx1100/quant/gguf_k_t16_selected_prefill.{hip,py} tests/test_gpu_gguf_q4_k_t16_dense.py scripts/qwen38_packet4_q4_dual_silu_row_leaf.py`
is empty, so the shipped kernel, launcher, tests, and harness are the exact
artifacts that passed the family gate before the candidate existed. Re-run on the
reverted tree anyway, as the narrow affected set: the family GPU file
(`tests/test_gpu_gguf_q4_k_t16_dense.py`) 131 collected, exit 0 (the 6 removed
arm cases account for 137 -> 131), the five-file unit bundle 263 collected, exit
0, and the reverted harness reproduces the control column (6.6235 ms at 512 rows,
+0.02% against this unit's A/B control).

No resident-session 512/128, 1K/128, 4K/128 arm was spent, deliberately. The
candidate has no dispatch path, so an end-to-end arm needs a new temporary
selector for a kernel this owner-level measurement already shows is 1.40-1.65x
slower; with the owner at 33-36% of prefill kernel time that is 13-23% of
prefill wall by arithmetic, and no end-to-end result could have been
non-regressive. The 13-23% figure is an inference from the measured owner share,
not a measurement, and the artifact says so.

## Next

- The tile-geometry axis is now settled for this kernel: 32 columns x 256 rows
  with 4 waves is the measured best among the expressible tiles, and every shrink
  (rows or columns) loses. Three directions remain, each with its prerequisite
  recorded in `docs/REFACTOR.md`:
  1. decode lane remap or a 4-byte-per-thread load pattern (the decode is the
     only part rows per block amortize and about 40% of the issue stream);
  2. a 48-column tile, which needs the decode to reach 192 threads or a lane
     remap, since 128 threads cannot cover 48 decode pairs;
  3. 32 columns x 512 rows per block, expressible today but its epilogue union
     becomes the whole 64 KiB of LDS, so it needs either that occupancy drop or
     the 256-thread register-local-SiLU epilogue rewrite.
- Occupancy remains a dead end through launch bounds: measured 219 VGPR with and
  without `__launch_bounds__(128, 4)`, literal and template spellings both.
