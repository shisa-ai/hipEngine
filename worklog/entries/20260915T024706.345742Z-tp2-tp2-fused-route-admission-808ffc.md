# The fused gate/up decode route is shape-keyed and does not admit a shard

## Summary

A shard MLP segment would **not** get the incumbent fused gate/up+SiLU decode
route. The route is selected by an exact `(rows, in_features, out_features)`
lookup in `GGUF_DENSE_PAIR_SILU_DECODE_POLICIES`, whose only admitted shape for
this model is `(1, 5120, 17408)`. A half-intermediate shard is
`(1, 5120, 8704)`, which is **absent**, so
`_gguf_dense_pair_silu_decode_variant` returns None and the segment falls back to
the unfused chain.

The kernel itself accepts the shard shape: its validation is
`out_features % 16 == 0` and `in_features % 256 == 0`, and 8704 satisfies both.
So the gap is a **policy admission**, not a missing kernel - but it is a real cost
difference (one fused launch versus two GEMV launches plus a separate
SiLU-multiply), and it is exactly the kind of thing the earlier "no new kernel
needed" claim glossed over.

## Changes

`scripts/tp2_mlp_shard_plan_probe.py` gains `fused_path_admission()`, reported
under `fused_path_admission` and deliberately **not** one of the pass/fail
questions: it is a known gap the execution test has to resolve, not a missing
prerequisite. The record:

```json
{
 "lookup_key": "(rows, in_features, out_features)",
 "tp1_key": [1, 5120, 17408],
 "tp1_variant": "dense_dual_local32_bf16_bf16_out",
 "tp1_admitted": true,
 "shard_key": [1, 5120, 8704],
 "admitted_shapes": [[1, 5120, 17408]],
 "shard_admitted": false,
 "kernel_accepts_shard_shape": "passed argument validation, then: RuntimeError",
 "gap": "the shard shape is accepted by the kernel but absent from the policy table"
}
```

`kernel_accepts_shard_shape` is obtained by **calling the kernel's own
validation** with a null-pointer launch rather than by reading its bounds test:
the launch cannot succeed, but a `ValueError` would mean the shape itself was
refused, and it did not raise one.

The policy table's own comment confirms the shape-keying is intentional for other
geometries - "Other shapes stay on the unfused chain" - so extending it for a
shard is a decision that needs the same gate the existing entries had (the
Q5 entry records "bit-exact with the unfused chain, verified on the real blk.25
pair"), not a silent addition.

## Validation

```
uv run python3 scripts/tp2_mlp_shard_plan_probe.py --model /models/gguf/Qwen3.8-27B-Q4_K_M.gguf \
  --layer 0 --world-size 2 --device \
  --json benchmarks/results/2026-09-15-w7900-tp2-mlp-shard-plan-probe.json
uv run pytest tests/test_unit_scripts_tp2_mlp_shard_plan_probe.py
```

23 tests pass, including three new ones pinning the shape-keying, the kernel's
acceptance of 8704, and that an odd intermediate is reported rather than floored.

## Next

Two consequences for the execution test, both now explicit rather than assumed:

1. Measure the shard MLP segment on the **unfused** chain as it resolves today
   (two GEMV launches plus a SiLU-multiply), and measure the TP1 segment on the
   fused route. That difference is part of the segment saving, not a detail.
2. Then decide whether to admit `(1, 5120, 8704)` to the policy table. The gate
   is the one the existing entries used: the fused result must be bit-exact (or
   within the production numerical envelope) against the unfused chain on the real
   shard weights, plus the CPU split oracle.

The rest of the packet is unchanged: partials validated against an independent CPU
split oracle, connected through the native exchange into the residual/next
consumer, complete TP1 and TP2 segment walls measured on both cards, and the
reduction dtype resolved before either.
