# pair32 clears the repeated-128K gate and becomes the gfx1151 selected-expert prefill default

## Summary

The paired multi-wave LDS-staged selected-expert prefill bodies landed in
`93b9a9300` bit-exact and at +10.54%, but as an **opt-in selector** behind a real
blocker: `docs/REFACTOR.md` GPF-3A documents a silent repeated-128K lifecycle
stall in this same LDS-staging family, isolating
`gguf_q4_k_t16_selected_dual_wmma_prefill_compact32_shared_x_kernel<uint16_t>`,
with the promotion bar set at three independent 128K warmup+3 processes. That
gate is runnable, so it was run. **Both profiles passed 12/12**, `pair32` is now
the gfx1151 automatic route, and the default-path A/B measures **+12.58%**.

## What was done

1. Added two gate profiles to `scripts/qwen35_readme_sweep.py`:
   - `q4_pair32` — the conservative selector set plus `pair32`, the direct
     analogue of `q4_shared_x`, i.e. the profile under which the stall was
     characterized.
   - `q4_pair32_production` — package defaults except the one family under test,
     mirroring `q4_baseline`'s shape. **This is the profile that authorizes
     promotion**, because it is what the automatic route actually runs.
2. Ran three independent 128K warmup+3 processes under each profile.
3. Promoted: `GGUF_Q4_T16_SELECTED_PREFILL_AUTO_MODE` `"baseline"` -> `"pair32"`
   in `hipengine/kernels/hip_gfx1151/__init__.py`. gfx1100 is unchanged at
   `shared_x`.
4. Updated the resolver test that encoded the old `auto -> baseline` contract,
   and added a companion asserting the rollback still resolves.
5. Corrected the rollup, which the landing commit had written to describe an
   opt-in result.

helps long context as well as 4K. The `compact32_shared_x` stall precedent does
not extend to `pair32` on either profile.

with no override, 4096-token prefill, chunk 1024, three measured runs each, one

## Decisions worth recording

- **The conservative gate alone was not sufficient.** It exercises the same
  bodies through the same repeated-128K pattern, but it forces GDN `chain`, conv
  `baseline`, 512 router threads, and device metadata off, so it is not what
  ships. A stall could in principle be a profile interaction, and a stall is a
  hard hang for every gfx1151 user, so the production-shaped gate was run
  separately rather than assumed.
- **The compact `baseline` body was kept.** The landing plan proposed deleting
  the `baseline` mode entry and the mode map once promoted. That would have
  removed the rollback for a family that has already needed one restored, and
  both `AGENTS.md` and the task's acceptance criteria require a retained strict
  fallback. It stays registered as an opt-out.
- **gfx1100 was not touched.** It still resolves `shared_x`; the gate was
  gfx1151-specific and no equivalent evidence exists for gfx1100.
