# Phase 4 candidate A: a rows 2-4 local32 IQ verifier sibling

## Summary

The Phase 1 census put 135 strict per-row GEMV launches per verifier step on the
UD artifacts' raw-IQ tensors, and Phase 2 measured the rows == 1 local32 decode
owner at 2.0-7.4x that GEMV on the same tensors. The verifier could not use it
because the local32 kernel was hard-coded to one prompt row per block, and
because the block verifier never bound the dense-IQ execution-owner session, so
its raw-IQ projections could not be re-routed at all.

Both halves are now fixed. `ROWS` is a template parameter of the existing
local32 IQ kernel bodies: one block owns `ROWS` prompt rows, decodes each weight
block once and applies it to every row. Each row keeps the rows == 1 owner's
per-(row, column) k ownership, FMA order, shuffle tree and cross-wave sum, so
every row's output is **bit-identical** to the rows == 1 owner's output for that
row. The sibling adds no arithmetic of its own; it is the same already-admitted
approximate owner at a different execution geometry.

Measured on real UD tensors (4 largest shapes per quant, interleaved min-of-5
rounds x 3 reps, rows 1/2/4), summed per quant:

| Quant | rows | strict GEMV | local32 per row | sibling | vs GEMV | vs per-row | bit-exact |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| IQ4_XS | 2 / 4 | 0.755 / 0.881 ms | 0.505 / 0.914 | 0.312 / 0.378 | 2.42x / 2.33x | 1.62x / 2.42x | yes |
| IQ4_NL | 2 / 4 | 1.061 / 1.110 ms | 0.359 / 0.668 | 0.250 / 0.290 | 4.25x / 3.83x | 1.44x / 2.30x | yes |
| IQ3_S | 2 / 4 | 0.503 / 0.773 ms | 0.438 / 0.754 | 0.246 / 0.269 | 2.05x / 2.88x | 1.78x / 2.81x | yes |
| IQ3_XXS | 2 / 4 | 0.438 / 0.536 ms | 0.359 / 0.663 | 0.222 / 0.258 | 1.97x / 2.08x | 1.62x / 2.57x | yes |
| IQ2_S | 2 / 4 | 0.314 / 0.301 ms | 0.218 / 0.332 | 0.113 / 0.114 | 2.79x / 2.63x | 1.93x / 2.90x | yes |
| IQ2_XS | 2 / 4 | 0.281 / 0.269 ms | 0.214 / 0.355 | 0.119 / 0.126 | 2.36x / 2.13x | 1.80x / 2.82x | yes |

K_M rows are the UD-Q4_K_M tensors, K_S rows the UD-Q4_K_S ones; the numbers
above are the K_S sums for IQ3_XXS/IQ2_S/IQ2_XS and the K_M sums otherwise
(both models agree to within a few percent on the shared quants). Q3_K has no
rows == 1 local32 owner, so it has no rows 2-4 sibling and keeps the strict
per-row GEMV.

End to end on the same host and protocol (physical GPU1, RX 7900 XTX, c1,
natural25, B3, ten prompts, two repeats), all three ratios:

| Tier | AR before -> after | MTP B3 before -> after | MTP/AR before -> after | UD/plain AR | UD/plain MTP |
| --- | ---: | ---: | ---: | ---: | ---: |
| `UD-Q4_K_M` | 31.99 -> 31.90 | 35.54 -> **43.69** (+22.9%) | 1.1109 -> **1.3696** | 0.883 | 0.713 (was 0.560) |
| `UD-Q4_K_S` | 31.31 -> 31.33 | 33.06 -> **45.46** (+37.5%) | 1.0559 -> **1.4511** | 0.787 | 0.705 (was 0.516) |

Both UD arms are now generated-ID exact against their own true-AR denominator
and report `complete_exact`; the UD-Q4_K_S `general_ja_plan` near-tie
divergences recorded before this change are gone.

## Changes

- `hipengine/kernels/hip_gfx1100/quant/gguf_iq_dense.hip`: `ROWS` template
  parameter (default 1) on `gguf_iq4_xs_local32_gemv_kernel`,
  `gguf_iq4_nl_local32_gemv_kernel` and `gguf_iq_split_local32_gemv_kernel`,
  plus `extern "C"` entries `hipengine_gguf_iq4_xs_local32_rows_gemv`,
  `hipengine_gguf_iq4_nl_local32_rows_gemv` and
  `hipengine_gguf_iq_split_local32_rows_gemv`. `__launch_bounds__` keeps the
  original minimum-block request for `ROWS == 1` and relaxes it to one block
  for `ROWS > 1`, so the existing owner's codegen is unchanged by construction.
  The row loop is outermost only for the activation loads and the accumulator;
  the weight decode stays inside the column loop exactly as before, so each row
  sees the same FMA order. Output is `(ROWS, N)` row-major.
- `hipengine/kernels/hip_gfx1100/quant/gguf_iq_dense.py`:
  `launch_local32_rows` and registration under the new variant
  `local32_rows_gemv_bf16_bf16_out` for the six IQ quants. The split-K wave
  rule moved into a shared `_local32_waves` helper so the rows == 1 owner and
  its sibling cannot drift apart on the cross-wave reduction order - that
  shared rule is what makes the bit-exactness claim structural rather than
  copied.
- `hipengine/kernels/hip_gfx1100/__init__.py`: `GGUF_IQ_DENSE_VERIFY_POLICY`,
  `{min_rows: 2, max_rows: 4, variant: local32_rows_gemv_bf16_bf16_out}` for
  the six IQ quants. gfx1151 declares no such policy, so it keeps the strict
  owner, exactly as it already does for decode.
- `hipengine/runtime/gguf_linear.py`: `_iq_dense_decode_dispatch` now selects by
  row regime. `rows == 1` arrives under the `gemv_bf16_bf16_out` parent and
  takes `GGUF_IQ_DENSE_DECODE_POLICY`; rows 2-4 arrive under the
  `prefill_bf16_bf16_out` alias (the strict GEMV is reached through the prefill
  name until the dense-IQ prefill policy claims it at 8 rows) and take
  `GGUF_IQ_DENSE_VERIFY_POLICY`. The per-slot strict pin covers both regimes.
- `hipengine/runtime/qwen35_gguf_runner.py`: `_iq_dense_mmq_verify_context`,
  entered by `verify_target_block` around its layer loop, and
  `_iq_dense_verify_binding_needed`, which admits the binding only for row
  counts a verifier policy declares. Without the binding every raw-IQ verifier
  projection kept the strict GEMV and the new policy could never fire. The
  session is workspace-less on purpose: it runs inside stream capture for the
  native target graph, where allocating is not an option, and scoping it to the
  declared verifier rows keeps the dense-IQ prefill policy (min_rows 8) out of
  the verifier, so rows 5-8 keep their previous owner. `_iq_dense_mmq_context`
  gained the shared `_iq_dense_policy_present` helper and now also treats a
  verifier-only backend as reason to bind.
- `tests/test_gguf_iq_local32_rows.py` (new) and
  `tests/test_gguf_iq_local32_decode.py`: the sibling's RED contract -
  registration on both HIP backends, policy-driven admission per row regime,
  decline without a session, decline without a policy entry, decline for a
  pinned slot, decline for unaligned N, decline above four rows, decline
  through the wrong parent variant, argument validation, the allocation-free
  verifier binding and its row window, the structural assertion that the block
  verifier enters it, the shared split-K rule, GPU bit-exactness of every row
  against the rows == 1 owner for all six quants at rows 2/3/4, and GPU
  agreement with the strict GEMV.
- `scripts/gguf_iq_local32_rows_headroom.py`: extended to the three-arm
  measurement above (strict GEMV / local32 per row / sibling) with per-row
  bit-exactness screening.
- `scripts/gguf_iq_local32_rows_trace.py` (new): the `rocprofv3` smoke.
- `benchmarks/results/2026-09-12-ud-gfx1100-phase4-local32-rows-headroom.json`
  (diagnostic) and `...-phase4-ar-verify-numerics.json` (correctness gate).
- `docs/UD-GFX1151-OPTIMIZE.md`: Phase 4 candidate A checked off, with the
  t16 decode-versus-rowtile accumulation order recorded as the dominant
  remaining verifier drift.

Registry keys: `KernelKey("hip_gfx1100", "linear", <quant>,
"local32_rows_gemv_bf16_bf16_out")` for `gguf_iq4_xs`, `gguf_iq4_nl`,
`gguf_iq3_s`, `gguf_iq3_xxs`, `gguf_iq2_s`, `gguf_iq2_xs`. Source lineage: the

## Validation

- **Device identity.** Every run set `HIP_VISIBLE_DEVICES=1` with
  `ROCR_VISIBLE_DEVICES` unset on physical GPU1 (RX 7900 XTX, gfx1100).
- **Bit-exactness.** `pytest tests/test_gguf_iq_local32_rows.py` compares each
  row of the sibling against the rows == 1 owner run separately, for all six
  quants at rows 2, 3 and 4: every element equal, no tolerance. The same
  property is screened in the headroom script's three-arm sweep.
- **Tests.** `pytest tests/test_gguf_iq_local32_rows.py
  tests/test_gguf_iq_local32_decode.py` (81 pass, includes the GPU numerics),
  plus `tests/test_gguf_iq_dense_mmq_route.py`,
  `tests/test_gguf_iq_dual_owner_gate.py`,
  `tests/test_gguf_linear_dispatch_cache.py`,
  `tests/test_gguf_q5_selected_local32_decode.py`,
  `tests/test_gguf_block_verify_low_rows.py` (67 pass).
- **Kernel trace.** `rocprofv3 --kernel-trace` around the section-6.1 gate on
  the 64-token arm shows `gguf_iq4_xs_local32_gemv_kernel<2, 2>`, `<2, 3>`,
  `<2, 4>`, `<4, 2>` and `<4, 3>` in the verifier path, and leaves
  `gguf_iq_dense_strict_kernel` at rows 1. The standalone smoke
  (`scripts/gguf_iq_local32_rows_trace.py`, prebuilt extension,
  `--require-cached-build`) shows `<2, 4>`, `<4, 4>`, `<2, 2, 4>`, `<4, 4, 4>`,
  `<5, 4, 4>` and `<6, 4, 4>` with 74-271 us durations.
- **Production numerical gate.** All four section-6.1 arms pass the complete
  screen with at least 24x margin on the binding mean limit and 100% top-1
  overall and per category, with two bit-identical repeats. Against the Phase 3
  arm means the tail improved on three of four arms (K_M 512 mean 3.51e-05 ->
  1.82e-05, p95 2.46e-04 -> 8.37e-05, max 7.00e-04 -> 4.34e-04) while K_S 64
  and K_S 512 moved up inside the envelope (mean 3.06e-05 -> 4.23e-05 and
  1.03e-05 -> 1.50e-05). The residual did not collapse: it is dominated by the
  t16 decode-versus-rowtile accumulation order, not by the IQ owner, so the
  Phase 3 note over-attributed it to the strict IQ GEMV.
- **Paired benchmark.** `scripts/ud_mtp_paired.py --runs 2 --device-index 1
  --expect-device "7900 XTX"`. All four arms report `timing_evidence_valid`,
  complete 20-row-per-group evidence, deterministic repeats, GPU/CPU acceptance
  agreement, a positive MTP/AR ratio and generated-ID exactness.
- **Evidence caveat.** The paired run above was taken with the worktree dirty
  and five untracked files, so its `speed_claim_eligible` flag is false. It is
  a diagnostic measurement of this change, not the retained artifact; the
  retained artifact is re-measured on the clean commit and rolled up
  separately.
- `python3 scripts/worklog.py check`: valid.
