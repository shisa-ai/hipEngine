# IKV-C2 promotion safety audit and packed-owner cancellation coverage

## Summary

`baf7729b9` raised the gfx1100 Qwen3.8-27B INT8-KV capability `max_direct_rows`
from 1 to 4, which promotes row-batched direct INT8 decode to the default C>1
serving route. That commit proved the route correct (primitive gate, width-4
model gate, retire/admit transition gate, live-server throughput) but did not
audit what else reads the number it changed. This entry closes that audit and
closes the one real coverage hole it found.

Two findings.

First, the promotion is contained. Five consumers read the capability, all are
width-consistent, none assumes width 1, and two independent escape hatches keep
a refused width from becoming a failure: `_packed_ar_layout_for_sessions` raises
`NotImplementedError` above the admitted width, and
`_step_ar_serving_slot_chunk_packed` catches it and falls back to per-slot
serial. MTP is not a consumer at all. Packed-decode-graph refusal is keyed on KV
storage type, not width, so width 4 does not newly attempt a capture.

Second, the cancellation mechanism was untested. The P5 gate requires exact
cancellation; for the promoted route that guarantee lives in
`_flush_ar_packed_decode_owners_if_chunk_changed`, which decides whether a formed
physical group may keep its accumulated packed state or must write it back
before the group re-forms. Every existing test stubbed that method to
`lambda: None`, so the branch structure that makes a cancellation exact had never
been executed.

## Changes

- `tests/test_gguf_packed_owner_chunk_flush.py` (new, 10 tests). Calls the real
  `Qwen35GGUFBringupGenerator._flush_ar_packed_decode_owners_if_chunk_changed`
  and pins both branches:
  - unchanged composition + dirty owner -> keep the owner, do not flush (the
    per-step fast path);
  - anything else -> flush the owner once, then clear it from every slot it
    owned.
  Cases cover a clean owner, a shrinking chunk (cancellation), a newcomer
  reusing a freed lane at *equal width* (which a length comparison would wrongly
  accept), a reorder, mixed owners flushed exactly once each, ownerless slots
  that neither flush nor block, an owner with no `flush_packed_decode_state`
  hook, and an owner missing `_packed_decode_state_dirty` (must default to
  flush, never to silent reuse).

No production code changed. The two mutation checks below were applied and
reverted; the final source is byte-identical to `baf7729b9`.

## Validation

CPU-only, no GPU run needed.

- `uv run pytest tests/test_gguf_packed_owner_chunk_flush.py -q` -> 10 passed.
- Mutation RED, proving the tests are load-bearing rather than restating the
  implementation:
  - fast path disabled (`if False and owner_dirty and ...`) -> exactly
    `test_steady_group_keeps_its_owner_without_flushing` fails;
  - identity comparison replaced by length comparison -> exactly
    `test_newcomer_reusing_a_freed_lane_flushes_the_owner` and
    `test_reordered_sessions_flush_the_owner` fail.
  Source restored to an empty `git diff` and re-green after each.
- Related suites (packed verify layout, INT8 transition gate, INT8 KV
  capability, server cwidth probe, GGUF sampling): 108 + 124 passed, 1 skipped.
- `uv run pytest --collect-only` -> 13262 tests collected, no collection errors.

Audit evidence (read-only inspection, no code change):

- Consumers of the promoted number: `_qualified_kv_decode_batch_route`
  (`qwen35_gguf_runner.py:14097`), `__post_init__` setting
  `packed_decode_max_rows`/`_retained_decode_kernel` (`:15544-15560`),
  `_packed_ar_layout_for_sessions` (`:22297`),
  `_packed_ar_direct_decode_kernel_for_sessions` (`:24626`), and the scheduler's
  `packed_decode_limit` fallback (`qwen35_gguf.py:8461`).
- `allow_direct_int8_decode` is read only inside `_packed_ar_layout_for_sessions`,
  reached only from `packed_ar_decode`/`step_batch_native`; the MTP verifier
  `verify_target_blocks_batch` reads none of `packed_decode_max_rows`,
  `_retained_decode_kernel`, or `int8_kv_no_mirror`.
- `gguf_packed_decode_graph.py:428` raises
  `NotImplementedError("packed decode graphs currently support BF16 KV only")`
  on `kv_storage_dtype != BF16`, ahead of any width-dependent work; the per-slot
  `packed_decode_graph_unavailable` latch (`qwen35_gguf.py:8717`) is O(1).
- `_step_ar_serving_slot_chunk_packed` catches `NotImplementedError` and returns
  `None` (`qwen35_gguf.py:2648`), and `_try_step_ar_serving_slots_batch` then
  steps each slot serially.

## Next

- Packed decode graphs and the MTP spec target graph still require BF16 KV.
  Enabling either on INT8 is separate work, not a correctness gap in this
  promotion.
- Batched prefill on the INT8 direct route remains IKV-C3-blocked.
- An earlier note that per-request latency at C>N was measured but unpublished
  is stale: `benchmarks/README.md` already reports it (4.95 s C1, 7.97 s C2,
  14.1 s C4). The artifact's `per_request_wall_s` makes the tradeoff explicit:
  C4 concurrent 14.15 s against a 5.06 s serial control is 2.80x per-request
  latency for 1.42x aggregate throughput.
