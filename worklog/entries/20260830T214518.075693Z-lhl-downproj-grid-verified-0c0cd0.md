# down projection launches 107 blocks at every prefill row count

## Summary

Task #11 was built on a grid estimate I had inherited, not measured. It is now
verified from source, and it comes with a second finding: the shared-B prefill
kernel uses 256-row tiles, so **grid.y stays at 1 for every row count in this
suite**. Rows 33 and rows 192 launch the same 107 blocks. That predicts the flat
1.00x-1.06x dispatcher behaviour I measured today on `(17408, 5120)` at rows
32-192, which I had recorded without an explanation.

## Changes

- None. Source read only: `gguf_k_t16_selected_prefill.hip`.

## Validation

Grid math, from `launch_q4_t16_dense_wmma_prefill_shared_b_bf16` at line 1750:

- `T16_COLS = 16` (line 31), `Q4_DENSE_TILE_COLS = 3 * T16_COLS = 48`,
  `Q4_DENSE_TILE_ROWS = 4 * 4 * 16 = 256`, `dim3 block(128)`.
- `grid = (ceil(out_features / 48), ceil(rows / 256))`.
- Down projection `(in 17408, out 5120)`: `grid = (ceil(5120/48), ceil(rows/256)) =
  (107, 1)` for all rows <= 256. So 107 blocks x 128 threads = 13,696 threads,
  one 4-warp block per compute unit at best, with no second dimension until row 257.
- Gate/up `(in 5120, out 17408)`: `grid = (363, 1)` at the same rows, which is why the
  same rows cost 0.60 ms there and 1.01 ms here. The gap is the grid, not the FLOPs.

Consistency check against measurement: with `grid.y` pinned at 1, extra prefill rows
add no parallelism, so throughput at rows 32-192 should look flat. It does
(1.00x-1.06x across that span on this shape). Source and measurement agree.

## Next

Two routes for #11, in the order I would now try them:

1. Finer row tiling. The 256-row tile depth is what keeps `grid.y` at 1. A variant at
   32 or 16 rows would give 6-12 blocks in y at prefill rows, i.e. 641-1284 blocks.
   The constant is structural (`4 * 4 * 16`), so this is a kernel change, not a flag.
2. Split-K over `in_features` with a reduction, which is the original plan. Same
   parallelism benefit, but adds a second kernel and an accumulator.

Both need the `kernels/cpu_reference` RED gate. Neither is reachable from Python: the
grid is computed inside `.hip`, and `_launch_dense_t16` is a plain ctypes wrapper.
