# Reusable staged speculative-provider runner seam

## Summary

Task #10, smallest reusable speculative-provider seam. `ResidentEngineLoop`
drove the staged target/provider lifecycle by duck-typing six
`getattr` probes on the runner, so a runner that advertised staged support but
lacked a stage fell back to AR silently and no single contract named what the
scheduler required.

Added `StagedSpeculativeRunner`, a `runtime_checkable` protocol in
`hipengine/speculative/provider.py` that names the scheduler-facing staged
lifecycle, plus `validate_staged_speculative_runner` (rejects an owner missing
any required stage by name) and `resolve_staged_speculative_runner` (returns the
validated owner, or `None` for a target-only runner). The required set is the
one `ResidentEngineLoop._run_staged_speculative_cycle` actually needs:
`speculative_capability`, `speculative_component_claims`,
`reserve_speculative_claims`, `release_speculative_claims`,
`prepare_speculative_requests`, `propose_speculative_batch`, and
`execute_target_frontier`. `speculative_claims_fit`,
`speculative_frontier_available`, `speculative_kv_live_spans_owner`, and
`rollback_speculative_cycle` stay optional hooks the loop consults when present,
so an owner without them keeps working (the PARO runner has no
`speculative_frontier_available`).

`Qwen35GGUFResidentModelRunner.staged_speculative_owner()` opts the Qwen GGUF
MTP path into the seam; `ResidentEngineLoop` now resolves the owner through
`resolve_staged_speculative_runner` in both `_supports_staged_speculative_mtp`
and `_run_staged_speculative_cycle`. No defaults, plan/K selection, typed
contracts, target-frontier ownership, or failure/rollback behavior changed: the
resolved owner is the runner itself, and the same stages run in the same order.

**DMS boundary (intentionally not migrated).** `Qwen35GGUFDMSModelRunner`
inherits the Qwen staged methods structurally, but its compact KV store cannot
provide the frontier's typed KV binding and liveness plane, and
`configure_engine_loop` already refuses speculative serving with
`ValueError("DMS compact KV has no speculative serving adapter; use
speculative_mtp_serving='off'")` (and `prefix_cache` with its own error). DMS
was left unchanged; the config gate, not the seam, is the boundary. The
quantized-KV refusal stays where it already lives (`LLM`/`ServerConfig`). This
is recorded as an explicit boundary rather than weakening the DMS checks.

## Changes

- `hipengine/speculative/provider.py`: `StagedSpeculativeRunner` protocol,
  `_STAGED_RUNNER_METHODS`, `validate_staged_speculative_runner`,
  `resolve_staged_speculative_runner`; `TargetFrontier` import; `__all__`.
- `hipengine/speculative/__init__.py`: export the new protocol and helpers.
- `hipengine/generation/qwen35_gguf.py`: `staged_speculative_owner()` opt-in on
  `Qwen35GGUFResidentModelRunner`.
- `hipengine/generation/engine_loop.py`: resolve/validate the staged owner
  through the seam helper in `_supports_staged_speculative_mtp` and
  `_run_staged_speculative_cycle`.
- `tests/test_unit_specdec2_provider.py`: protocol rejects incomplete owners;
  resolver validates explicit opt-in, accepts a complete duck-typed owner, and
  returns `None` for a target-only runner.
- `tests/test_unit_qwen35_gguf_mtp2_seam.py`: Qwen staged resolution preserves
  capability/claims/proposal/frontier/rollback delegation; DMS runner keeps its
  named unsupported-composition errors.
