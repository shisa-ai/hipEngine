# The MTP head is a separate `gemma4-assistant` artifact, and the engine has no support for it
## Summary
Two of the objective's six items resolve here, both with evidence rather than
assumption: the rebase is already satisfied, and MTP is not a missing feature on
an existing artifact but a **different artifact with a different architecture**
that the engine does not support at all.
## 1. The rebase is already done
```
git merge-base HEAD origin/main  -> 9c31ba9fe
git log -1 origin/main           -> 9c31ba9fe
git log --oneline HEAD..origin/main | wc -l  ->  0
```
`HEAD` contains every commit in `origin/main`; the merge base **is** main's tip.
The `ahead 338, behind 97` in `git status` is measured against the stale
`origin/gemma4` remote branch, not against main, and is not a rebase signal.
The objective's second item is satisfied and needs no work.
## 2. MTP is a separate artifact, measured rather than assumed
`general.name` is `Gemma-4-26B-A4B-It`, `general.architecture` is `gemma4`, and
the 658 tensors are all `blk.*` (655), `output_norm`, `rope_freqs` and
`token_embd`. **There are no MTP tensors in the base artifact.** A header parse
looks for `mtp|nextn|draft|eagle|speculat` and finds none. A `strings` grep over
the header does match "draft", but those are tokenizer vocabulary entries, which
is why the parse was done properly rather than by substring.
Upstream confirms it by shipping the head separately, under `MTP/`:
`mtp-gemma-4-26B-A4B-it-BF16.gguf`, `-F16.gguf`, `-Q8_0.gguf`.
Downloaded `MTP/mtp-gemma-4-26B-A4B-it-Q8_0.gguf` (461,766,816 bytes) to
`/models/gguf/gemma-4-26B-A4B-it-GGUF/` and parsed it:
| field | value |
| --- | --- |
| `general.architecture` | **`gemma4-assistant`** |
| tensors | 49 |
| blocks | 4 (`blk.0` … `blk.3`) |
| linear type | Q8_0 (type 8), norms F32 |
| head pair | `nextn.pre_projection` [5632, 1024], `nextn.post_projection` [1024, 2816] |
| embedding | `token_embd.weight` [1024, 262144] |
It is a 4-block draft head with the next-N projection pair and the full
vocabulary. Note the architecture string differs from the target's `gemma4`.
## 3. The engine has no support for it
- `gemma4-assistant` appears **nowhere** in `hipengine/`; grep returns nothing.
- `hipengine/generation/gemma4_gguf.py:63` declares
  `supports_speculative_mtp = False`.
- `nextn` support exists, but only for qwen35:
  `hipengine/generation/qwen35_gguf_mtp2_registry.py`,
  `hipengine/runtime/qwen35_gguf_nextn.py`,
  `hipengine/loading/qwen35_gguf_nextn.py`.
So the objective's "make sure our MTP is working" is **not satisfied**, and the
reason is a named capability miss rather than a gate: no loader, no runner and no
registered adapter for a `gemma4-assistant` artifact.
## What makes this tractable
There is already an **adapter registry pattern** to follow:
`register_gguf_mtp2_adapter("dense_nextn", Qwen35GGUFMTP2Adapter, replace=True)`
and a `"moe_nextn"` registration beside it. A gemma4 assistant adapter is the
concrete shape of the work, and the head is small — 4 blocks, 49 tensors, 440 MB
— so it is a bounded task rather than a research question.
