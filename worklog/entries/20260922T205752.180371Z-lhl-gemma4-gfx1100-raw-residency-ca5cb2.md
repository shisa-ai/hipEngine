# Raw GGUF device residency for Gemma 4: 17.00 GB on a 48 GB device

## Summary

`hipengine/loading/gemma4_gguf_device.py` plans and loads the Gemma 4 text tower
as raw GGUF blocks on device. No dequantization, no repack.

On the real artifact the planner produces **657 specs totalling 17.00 GB** against
a 48 GB device — a 2.8x headroom. The bf16 alternative was 50.5 GB and did not
fit at all.

This is the loading half of the quantized-projection refactor recorded in
`20260922T124343.841312Z-lhl-gemma4-gfx1100-quant-weights-6d6544.md`. It is the
half that had to exist before any projection call site could be converted.

## Changes

- `hipengine/loading/gemma4_gguf_device.py` (new): `Gemma4GGUFWeightSpec`,
  `Gemma4GGUFDeviceWeight`, `plan_gemma4_gguf_resident_specs`,
  `materialize_gemma4_gguf_device_weight`, `resident_bytes`.
- `hipengine/loading/gemma4_gguf_materialize.py`: added
  `gemma4_layer_slot_names`, a public name for the per-layer slot mapping.
- `tests/test_unit_gemma4_gguf_device.py` (new): 6 tests.

## The slot mapping is shared, not copied

The reference materializer already knows which slots a layer owns, including the
rule that `attn_v` exists only on sliding layers and is absent on
`attention_k_eq_v` layers. The device planner calls that same mapping through a
new public name rather than keeping a second copy. Two copies would drift, and
the failure mode is silent: the device path would load a tensor set the
reference does not have, or miss one it does.

`plan_gemma4_gguf_resident_specs` also requires every slot the reference reads,
raising `MissingGGUFTensorError` naming the slot rather than loading a partial
layer.

## A stacked expert tensor stays one allocation

The rank-3 expert tensors are planned whole, not split per expert. The
per-expert gather is the kernel's job and the quantized dispatch selects the
expert by index, so splitting here would multiply the allocation count by the
expert count while leaving the resident total identical.

`test_a_stacked_expert_tensor_stays_one_allocation` pins this. My first version
of that test asserted `nbytes == sum(nbytes)` — a tautology that could not fail.
The replacement checks that each stacked tensor is planned exactly once and that
its byte count divides evenly across the expert axis.

## Validation

On the real artifact (`UD-Q4_K_XL`, 658 tensors):

| | |
| --- | --- |
| planned specs | 657 |
| resident bytes | **17.00 GB** |
| device | 48 GB |
| unplanned | `rope_freqs.weight` (metadata, correctly absent) |

Resident mix, by planned quant key:

| quant key | specs |
| --- | --- |
| `f32` | 391 |
| `gguf_q8_0` | 207 |
| `gguf_q4_k` | 29 |
| `gguf_q5_1` | 29 |
| `gguf_q5_k` | 1 |

That is 266 raw block weights and 391 f32 (the norms, which are f32 in the
artifact and stay f32).

The 29 `gguf_q4_k` and 29 `gguf_q5_1` specs are the stacked expert tensors: the
uploader's dynamic mix puts one expert projection in Q4_K and the other in Q5_1,
which is why the artifact cannot be described as a single quant.

Tests: `pytest tests/test_unit_gemma4_gguf_device.py` — **6 passed**. The device
test is HIP-guarded and compares the resident buffer against the reader's own
byte view, not against a shape or a size, so a loader that dequantized or
truncated anything would fail it.

`ruff check` clean.
