# Gemma 4 P1 blocked: vendored AOTriton aligns integer windows top-left

## Summary

P1 (windowed AOTriton for sliding chunks past the window, ~1300 ms at 4096
tokens) was implemented end to end, failed its parity test, and was reverted
uncommitted. **Nothing landed; production behaviour is unchanged.**

The blocker is not the plumbing, which verified exactly as the punchlist
described. It is that the vendored AOTriton 0.11.2b interprets integer
`window_left` / `window_right` **top-left aligned** -- row `i` of the *query
block* -- while a sliding layer's mask is **bottom-right aligned** over
absolute positions. That distinction is the whole difference between the two
for any block that does not start at key 0, which is every block but the
first.

A sweep over `window_left` in {sentinel, 0, W-2, W-1, W, W+1} x `window_right`
in {sentinel, 0, -1} shows the two frames cannot be mixed: while
`window_right` is the sentinel, all five integer `window_left` values produce
output identical to plain causal (meanabs 0.00008 against the causal
reference), so `window_left` is simply not read. Only `window_right` changes
anything, and only as a pair.

Offsetting `window_left` cannot repair this either. The integer bounds put the
*right* bound at block-local `i` as well as the left one, so a suffix block
cuts at `i` instead of `start + i`; `window_left = window - 1 - start` would
have to go negative for every block past `start >= window`, and a negative
value is the sentinel that means "unbounded".

So the legal refusal is the first one in the capability list: **no
implementation for these inputs or semantics.** Not a missing benchmark, not a
missing qualification.

## Validation

- **RED first, as the testing discipline asks.** Admission: 11 tests green
  before, then `assert _admits(keys=1025, sliding_window=1024) is True` failed
  against `False`. Parity: `TypeError: unexpected keyword argument
  'sliding_window'` on all five new cases.
- **GREEN then not reached.** With the plumbing in place the parity suite ran
  `....FFFFF`: all four causal cases passed, all five windowed cases failed
  with 97.6% mismatched elements and max absolute difference 2.60.
- **Causal was ruled out as the culprit before blaming the window.** At keys
  1536 / 2048 / 3000 / 4096 / (512,4096) the unplumbed flash path matched the
  exact kernel at maxabs 0.0078, meanabs 0.00008 -- every one passing. So the
  failure was window-specific, not large-key handling.
- **The alignment measurement.** Flash launched at
  `window_left = window - 1, window_right = 0`, scored against exact-kernel
  outputs built from four candidate masks, at `rows=512 keys=1536 window=128`:

  | candidate mask | maxabs | meanabs | within tolerance |
  | --- | ---: | ---: | --- |
  | `top_left_window` | 0.0078 | 0.00009 | **yes** |
  | `bottom_right_window` (Gemma's) | 2.7266 | 0.35227 | no |
  | `plain causal` | 2.6406 | 0.28943 | no |
  | `block_local_causal` | 2.5859 | 0.13893 | no |

  This shape is the discriminating one: `keys > rows` so the two frames
  differ, and a window narrower than the block so it binds inside it. At the
  more obvious `rows=64 keys=1536 window=1024` the top-left window is vacuous
  and degrades to block-local causal, which matches for the wrong reason --
  both scored 0.00009 there, so that shape proves nothing on its own.
- **The sweep.** `window_left` in {sentinel, 0, 1022, 1023, 1024, 1025} with
  `window_right` sentinel or -1 all gave meanabs 0.09337 against the windowed
  reference and 0.00008 against the causal one -- byte-identical to unplumbed
  causal. With `window_right = 0` the meanabs moved to 0.35373 (0.44631 for
  `window_left = 0`), so only the pair changes anything.
- **Reverted with `git apply -R`** on the six files' own diff rather than a
  checkout, saved to `/tmp/p1_top_left_attempt.patch`, leaving the worktree
  clean apart from another worker's `audit/` edits. The admission suite was
  re-run afterwards: 11 tests green, back to the committed state.
