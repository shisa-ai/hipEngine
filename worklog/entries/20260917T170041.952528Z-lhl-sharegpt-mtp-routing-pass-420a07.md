# ShareGPT re-measurement after the concurrency fix

## Summary

The same protocol as the first pass - same dataset slice, seed, 128-output
override, default server configuration - re-run after
[`20260917T165119.888504Z`](20260917T165119.888504Z-lhl-mtp-prompt-activation-concurrency-1ff172.md)
repaired the prompt-activation guard. All six arms now exist (three concurrency
levels, both clients), where the first pass could only produce c=1.

**Serving metrics** (`vllm bench serve --backend openai-chat`, ShareGPT loader
and pruning, 128-output override):

| Concurrent requests | Before | After |
| --- | --- | --- |
| 1 | 24 / 0 completed, 20.68 output tok/s, mean TPOT 48.71 ms | 24 / 0, **20.69**, 48.70 ms |
| 4 | 8 / 16 completed, 8.70 output tok/s, mean TPOT 182.27 ms | **24 / 0, 28.39**, 140.16 ms |
| 8 | 11 / 21 completed, 8.71 output tok/s, mean TPOT 203.57 ms | **32 / 0, 27.23**, 277.04 ms |

**Routing change** (recorder, same 24-prompt load at every level):

| Concurrent requests | Requests that ran MTP | MTP share of output tokens | Non-MTP reasons |
| --- | ---: | ---: | --- |
| 1 | 24 of 24 | 99.1% | none |
| 4 | 5 of 24 | 12.7% | `no_provider` 13, `prompt_activation_in_flight` 6 |
| 8 | 11 of 24 | 15.6% | `no_provider` 10, `prompt_activation_in_flight` 3 |

The c=1 result is unchanged to the token (3,043 of 3,072 MTP tokens, identical
prompt-length buckets), so the fix is inert on the single-request path. What
changed is that concurrency is measurable at all: the first pass lost 20 of 24
requests at c=4 to a closed engine service, and the four survivors ran no MTP.

At c=4 and c=8 speculation covers a fifth to a half of requests rather than all
of them, for two reasons that are recorded rather than fatal: the serving
evidence row for this cell matches only `realized_group_rows == 1`, so a request
admitted while it is alone can be batched into a wider decode group where the
route is not qualified; and a group mixing rows with and without a draft provider
fails closed before provider mutation. Five c=4 requests did run MTP, three of
them covering 127 of 128 tokens at depth 3, so the path is reachable under
concurrency but not reliable. Both gaps are in
[`docs/REFACTOR.md`](../docs/REFACTOR.md) with their follow-up tasks.

## Measurement note

The c=8 recorder arm's per-window decode rates are consumer-limited and must not
be read as decode: two requests show 16-token windows at 2,100-2,500 tok/s, which
is chunk-delivery burst after stream backpressure from a single Python client
holding 24 streams. Its aggregate rate (24.97 tok/s) agrees with the vllm bench
rate (27.23 tok/s) within 10%, and the rate-cliff detector reported a 667x
"speedup" on those two rows as an artifact of the same bursts. The aggregate is
the figure to use, and the cliff block from that arm should be ignored.
