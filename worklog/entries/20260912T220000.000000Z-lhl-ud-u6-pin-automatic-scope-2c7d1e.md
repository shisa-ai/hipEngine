# Correction: the U6 pin grants opt-in MTP, not automatic MTP

## Summary

`worklog/entries/20260912T214609.660168Z-lhl-ud-u6-pin-minted-426042.md`
describes the pin as enabling "automatic MTP admission" for the UD artifacts,
following the U6 item-6 contract's wording. The measurement says otherwise, and
this entry records the correction.

Measured on physical GPU1 with the pin in place and no in-process grant:

| Request mode | Engaged | AR tok/s | MTP tok/s | MTP / AR | exact |
| --- | ---: | ---: | ---: | ---: | ---: |
| explicit (`speculative_mtp=true`, server `opt_in`) | 10/10 | 14.09 | **33.78** | **2.3967x** | 10/10 |
| automatic (`speculative_mtp` omitted, server `auto`) | **0/10** | 14.10 | 14.17 | 1.0047x | 10/10 |

The automatic arm records `requested_route: speculative_mtp_auto`,
`effective_route: default`, `used: False`, and
`decision_reason: automatic_mtp_scope_not_promoted`.

## Why

The scope pin and the automatic-eligibility flag are separate gates.
`hipengine/server/api.py` resolves the automatic route as

```python
if route == _SPECULATIVE_MTP_AUTO_ROUTE:
    if admitted and not automatic_eligible:
        reason = _SPECULATIVE_MTP_AUTO_REJECTION_REASON
    admitted = admitted and automatic_eligible
```

`automatic_eligible` comes from the `SpeculativeMTPServingEvidence` row that
admitted the plan, and the UD artifacts have no such row — that is the same
ordering constraint recorded in
`worklog/entries/20260912T172746.747765Z-lhl-ud-phase5-width-scope-14e699.md`.
So the pin closes the *scope* half of admission and leaves the *evidence* half
open, which is exactly what the two-table split in
`hipengine/loading/qwen35_gguf_admission.py` is designed to make visible.

## What is actually true now

- Pinned UD presets resolve to `scopes=('ar','mtp')`, verified directly and by
  the admission tests.
- An explicit `speculative_mtp=true` request engages and is faster: 2.3967x on
  the server-path diagnostic denominator.
- The automatic route does not engage, and will not until a UD
  `SpeculativeMTPServingEvidence` row exists with `automatic_eligible=True`.

## Changes

- `benchmarks/CHANGELOG.md`: the pin entry now states opt-in-versus-automatic
  explicitly and names the remaining blocker, instead of implying automatic
  admission.

## Validation

- `scripts/gguf_mtp_c1c8_server_bench.py --widths 1 --max-tokens 24
  --candidate-budget 3 --correctness-contract ar_exact` in both
  `--mtp-request-mode explicit` and `--mtp-request-mode automatic`; the
  explicit arm is `complete`/`passed`, the automatic arm fails only the route
  expectation with `engaged=0/10`.
- `hipengine/server/api.py` lines around the automatic-route branch, quoted
  above.

## Next

Building the UD serving-evidence row is a separate unit: it needs the artifact
sha256 and size, the exact execution-profile manifest sha256 the run uses,
`realized_group_rows=1`, `resident_capacity=1`, the candidate-budget and
sampling-mode axes, and the context/horizon buckets, with
`automatic_eligible=True`. The width census fixes `realized_group_rows` and
`resident_capacity` to 1 and gives the evidence to cite.
