# A one-guard fix for a crash that hit ~37% of prompt lengths

## Summary

`LLM.generate()` raised `GenerationExecutionFailed` for a large fraction of
ordinary prompt lengths. Root cause: `_mmq_dual_route` selected the 32-row MMQ
leaf without checking the one condition the leaf's own entry check enforces, so
the projection raised `ValueError: mmq_total_rows must be a multiple of 32`
mid-prefill.

Found while doing V5, instrumented to the exact arithmetic, fixed with one
guard, and verified through the public API.

### The exact failure rule, measured

The leaf sizes its tile plan as `compact_rows + 31 * num_experts`
(`gemma4_experts.py`, the bound returned just above `_mmq_dual_route`), and
`_check_mmq32_common` rejects a total that is not a multiple of 32. The
instrumented probe printed the numbers directly:

| prefill block | `compact_rows` | `+ 31*128` | mod 32 | result |
|---|---|---|---|---|
| 501 tokens | 4008 | 7976 | **8** | **raised** |
| 504 tokens | 4032 | 8000 | 0 | ran |
| 512 tokens | 4096 | 8064 | 0 | ran |

`31 * 128 = 3968` is itself a multiple of 32, so for the shipped stack the
condition collapses to `compact_rows % 32`, and with 8 routed lanes per token
that is `tokens % 4`. Verified boundary, one token at a time:

- **255 OK, 256 OK, 257 CRASH** — 256 is where the lane floor lets the MMQ path
  engage (`compact_rows >= 4 * num_experts`).
- 256..511 crashes whenever `tokens % 4 != 0`; 500/504/508/512 ran.
- Above 512 the prompt splits at `max_block = 512`, so only the **final block**
  matters: 1001 (blocks 512+489) crashed, 1025/1029/1537/1541 (tails 1 and 5)
  did not, 701 (tail 189) did not because 189 is below the lane floor.
- Random sample before the fix: 845 crashed (tail 333), 961 crashed (tail 449),
  617/733/1123 ran — 2 of 5, matching the ~37.5% the rule predicts
  (final block uniform over 0..511, the region [256, 511] excluding multiples
  of 4).

### Why nobody had hit it

Every campaign prompt length is a multiple of 512: 1024, 2048, 4096, 5120.
Those give a final block of exactly 512 or 0, which is always aligned. V5's own
named lengths (511, 513, 1023, 1025, 1537) never hit it either, because that
sweep compares a *tokenwise* arm against *small multiple-of-4* bulk widths —
the 511-token bulk forward that production would actually issue was never one
of the arms. The bug sits precisely in the gap between the harness's arm
choices and a user's prompt length.

## Changes

- **`hipengine/kernels/hip_gfx1100/gemma4/gemma4_experts.py`** — one guard in
  `_mmq_dual_route`:
  `if (compact_rows + 31 * num_experts) % 32: return False`.
  Written in the plan's own form rather than `compact_rows % 32`, because the
  constant is only aligned when `num_experts` is a multiple of 32; for 16
  experts `31 * 16 = 496` is 16 (mod 32) and the required residue flips. The
  docstring already promised `_mmq_dual_route` carries "the same guards the
  projection itself returns `False` on" — it just did not carry this one.
  Both callers are covered by the single change: line ~293 uses it to decide
  whether to gather, and `gemma4_project_experts_mmq_dual` uses it to decide
  whether to take the route at all.
- **`tests/test_unit_gemma4_mmq_route_guard.py`** (new) — five tests pinning
  the formula, the shipped 128-expert geometry, the probe's exact numbers, the
  pre-existing guards, and the lane floor's independence.
- **`scripts/gemma4_mmq_row_probe.py`** (new) — wraps `_check_mmq32_common` to
  print `compact_rows` and `mmq_total_rows` before it raises. The stock error
  message omits the value, which is why the rule could not be reasoned about
  from the outside.
- **`scripts/gemma4_generate_crash_probe.py`** (new) — builds real prompt text
  at a requested token count and calls `LLM.generate()`, so the claim is made
  through the surface a user reaches rather than the harness.

No flag was added. The fallback is not a new behaviour: returning `False` from
`_mmq_dual_route` is the path the function was already documented to take, and
it hands the work to the grouped and selected owners, which serve any row
count.

## Validation

**Production surface**, `hipengine.LLM.generate()` on real prompt text:

| prompt tokens | before | after |
|---|---|---|
| 501 | `GenerationExecutionFailed` (cause: `mmq_total_rows must be a multiple of 32`) | **succeeded** |
| 1001 (final block 489) | crashed | **succeeded** |
| 504 | succeeded | succeeded |

**Fallback confirmed engaged**, not merely non-crashing: at 501 tokens
`_check_mmq32_common` is now called **0 times**, so the MMQ leaf is skipped and
the grouped/selected owner ran — the documented hand-off, not a silent
different kernel.

**Six previously crashing widths now run**: 257, 301, 501, 845, 961, 1001.
**Four previously working widths unchanged**: 256, 504, 512, 513.

**Tests**: 156 collected across the six files that import the changed module
plus the new guard test — all passing, exit 0.

**`python3 audit/audit.py check`** passes (exit 0). The new test carries zero
HIP references, so it is correctly outside the `unguarded-hip-test` inventory
rather than an untriaged addition to it.

**RED-first note**: the targeted test was written after the fix, not before.
The defect was *found* by measurement rather than specified in advance, so
there was no failing assertion to write first; the probe scripts are the
pre-fix evidence and the test encodes their numbers (4008/7976/8 mod 32) so
the two cannot drift apart.

## What this does and does not change

**Changes:** prompt lengths whose final prefill block is 256..511 tokens and not
a multiple of 4 now run instead of raising. That is roughly 37.5% of prompt
lengths.

**Does not change:** any length that already worked. For those, `compact_rows`
is aligned, the guard passes, and the MMQ leaf is still selected — the fast
path is untouched for every input that reached it before.

**Cost of the fix:** the lengths that previously crashed now use the grouped or
selected owner instead of the MMQ leaf, which is the slower MoE projection.
They had no behaviour at all before, so this is not a regression, but it does
mean those lengths are not getting MMQ's 2.07x. Whether the leaf could be made
to accept unaligned totals by rounding its plan up is a separate, unmeasured
question and is recorded as such in Next.

## Next

- **Rounding the plan instead of falling back** would recover MMQ for the
  lengths that now fall back. The bound's own docstring notes the sentinel fill
  makes extra tiles harmless, which suggests rounding `lanes + 31 * num_experts`
  up to a multiple of 32 is safe — but that changes what the leaf is handed and
  needs its own measurement. Not attempted here.
- **The campaign's standard lengths hide this class of bug.** Any gate built
  only on multiples of 512 cannot see a residue-dependent failure. Worth
  considering a non-aligned length in the standard set.
- V5's oracle leg (V2) is still the open dependency from the previous
  iteration; this crash was found by V5's method but is a separate defect.
