# Review the Maya Inkling engine for transferable optimizations

## Summary

Read-only review of `alesha-pro/maya-inkling-mini` (clone at `~/maya-inkling-mini`, commit `fcd523faca0c825131df45100b24eacb47dd2cf1`, MIT) against the Inkling campaign. Nothing from the repository was built or run; its numbers are the author's. It is a CUDA engine for the same Unsloth `UD-Q4_K_XL` file as the Loom lane and reports 128 tok/s plain decode and 2,742 tok/s prefill at 4,096 tokens on one RTX 3090, against 57 and 1,052 for `llama.cpp` on the same card. Three findings matter for us:

- **Decode is launch-bound in hipEngine, and Maya removed the launches rather than tuning kernels.** A token is one CUDA graph of 781 launches (`docs/INKLING2-MINI.md` "How it works"; 1,404 before fusion) with every expert resident, routing in one launch through a device pointer table (`route_token_kernel`, `src/ik2/ik2_kernels.cu:3856`), and no host wait between the embedding and the logits. Fusions: convolutions in the preceding products (`mv_q8p_conv`, `ik2_kernels.cu:6238`), q, k and v in one launch, three norms and four loop messages in one launch, sampling candidates chosen on the device. hipEngine issues about 246 stream synchronizations per decode row ([host decode boundaries](20261123T084317.753898Z-lhl-inkling2-mini-dc148d.md)) and about 1,230 dispatches per row ([four-row trace](20261123T054727.109209Z-lhl-inkling2-mini-399b3e.md)), near Maya's pre-fusion count.
- **Wide prompt chunks are what make its prefill fast.** The default chunk is 2,048 tokens (`src/ik2/ik2_main.cu:4488`), products run as FP16 GEMMs with FP32 sums (`gemm16`, `ik2_main.cu:419`), and prompts up to 96 tokens use a grouped path that reads each expert once for up to eight of its tokens (`IK2_RG_SLOTS`, `ik2_main.cu:5412`; `experts_block_gu_kernel`, `ik2_kernels.cu:5142`): 12 new tokens take 56 ms instead of 118. hipEngine's packed GGUF path uses 64-token blocks, so each block re-reads every expert: 573.3 MB per NVFP4 visit, 25.23 GB per block over 44 visits and 227.0 GB over the nine blocks of a 575-token prompt. At nominal peak bandwidth that is 394 ms on W7900 (576 GB/s) and 887 ms on Strix Halo (256 GB/s), above Loom's measured 0.524 to 0.540 s first text at 575 input. The [current trace](20261123T114259.749259Z-lhl-inkling2-mini-797a10.md) puts the grouped NVFP4 kernel at 600.55 ms for that prompt, 66% of the W7900 bound, so at this block size the kernel has little left and only fewer re-reads help. The earlier width test kept 64 after finding no consistent win, but it ran under `strict` ([entry](20261122T045321.615371Z-lhl-inkling2-mini-3f564e.md)), where experts go per route and width cannot change the traffic.
- **A wide chunk needs a matrix-core expert kernel, with a usable arithmetic recipe.** Maya's token kernel (`experts_mma_kernel`, `ik2_kernels.cu:2790` to 2870) decodes each NVFP4 code with its E4M3 scale to FP16 in registers, which is exact, feeds the FP32 input as two FP16 limbs so the columns sum to the FP32 product, accumulates in FP32 and writes SwiGLU in FP16. Its first tensor-core kernel was slower than the scalar one (100 against 118 tok/s) until eight warps shared each 16-row group on separate K strides with a one-step lookahead. Our [FP16 matrix-instruction screen](20261122T054650.102910Z-lhl-inkling2-mini-0d2355.md) lost to the FP32 four-route control on Strix Halo at 13 and 64 rows, where a 16-row tile is mostly padding, and the [integer-dot prototype](20261122T054919.424003Z-lhl-inkling2-mini-af60dd.md) was faster but is not FP32 arithmetic. The source cannot be ported as is: its matrix-core paths are `mma.sync` behind `__CUDA_ARCH__ >= 890` (`ik2_kernels.cu:70`, `:905`), and the HIP build (commit `003f225`, opt-in `STRATA_HIP_IK2_SPIKE`) is reported tested on gfx1201 only.

Also recorded there: `--parallel 4` reaches about 205 tok/s aggregate against 120 alone by grouping expert picks across requests on the device; the official drafter's five-token window costs 15.6 ms against 7.8 for one token and helps prose only 4% (131 against 126), new code 19% and edits 71%; FP8 KV halves cache bytes at a median KL of `1.1e-3` from FP16. Reported not to help: two int8 limbs with DP4A for the expert input (125 tok/s, GSM8K 71 against 73), skipping value reads for small attention weights, more lookahead in the dense Q8 kernels, and the drafter through the general prompt path.
