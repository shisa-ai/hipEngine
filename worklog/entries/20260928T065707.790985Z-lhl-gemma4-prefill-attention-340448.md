# the prefill kernel runs at 4 percent of issue capacity with bytes free so it is latency bound

## Summary

Two independent bounds now bracket the prefill attention kernel, and together they
leave latency as the only explanation.

The kernel issues **1.74 G warp-instructions** to do 67.1 M key visits at 26 issues
each, in 130.94 ms -- an achieved rate of **13.3 G warp-instructions/s**. A part with
40 CUs at 4 SIMD units each and 2.0 GHz can issue **320 G**, so the kernel runs at
**4.2% of issue capacity** (2.9% at 2.9 GHz).

Its byte traffic, if K were re-read once per query token, would be 68.7 GB in
130.94 ms = **525 GB/s, above this part's ~256 GB/s DRAM peak**. That model cannot be
right, which is the same conclusion the bf16/f32 ablation reached from the other
direction: L2 is absorbing the re-reads and bytes are nearly free.

**4% of issue capacity, with bytes nearly free.** Neither throughput nor bandwidth
explains the time. What is left is that the kernel does not have enough independent
work in flight to hide the latency of its own dependency chains.

## Why this is the useful framing

It explains every measurement in the preceding four entries at once:

- **Bytes nearly free** (`20260928T065531`, 1.02x-1.13x for 2x bytes): memory latency
  is being hidden by other warps, so adding bytes costs little.
- **Time tracks key visits, not blocks** (`20260928T065619`): each visit carries its
  own dependent chain, so time follows the number of chains, not the grid.
- **Cost invariant to the work inside a visit** (the kernel's own comment, 147
  GFLOP/s at both head_dim 256 and 512): the chain is the same length either way.
- **`--mask zero` makes it slower** (`20260928T065333`): removing the loads removes
  the latency there was to hide behind, so the loop's own dependent work is exposed
  with nothing to overlap it. That is the mechanism I declined to claim at the time;
  the issue-capacity figure now supports it without proving it.

## What it implies for the fix

Three ways to put more independent work behind each visit, in the order I would try
them:

1. **More query rows per block (token tiling).** A block holding `TQ` rows turns one
   dependent chain per visit into `TQ` independent ones, and cuts the visit count by
   `TQ` at the same FLOPs. This is the recommendation from `20260928T065619` and this
   entry strengthens its case: the win is latency hiding *and* fewer visits.
2. **More warps per block.** The same argument with less restructuring, and it does
   not reduce visits.
3. **A shorter chain per visit.** This is what the key-parallel port was for
   (`20260928T064926`), and in a latency-bound kernel removing five shuffle stages
   from the critical path is the right idea -- my dismissal of it used an *issue
   count*, which is a throughput model and the wrong model for a kernel at 4% of
   capacity. It stays dismissed only because its 512 LDS reads per key per lane
   would add a longer chain than they remove, which is an argument I have not
   measured.

## Changes

No code. The entry is arithmetic over the pinned tree's 26-issue visit count and the

## Validation

The 26-issue count is from `20260928T100244`, which pins the reduction tree and whose
GPU comparison (`20260928T064822`) confirmed the tree is the kernel's order. The
67.1 M visit count and the 130.94 ms are from `20260928T065619`'s `tokens=2048`,
`keys=2048` row. The 320 G issue capacity assumes 40 CUs, 4 SIMD units per CU, and
2.0 GHz; each is a published figure for this class of part and none is measured here,
so the 4.2% is an order-of-magnitude statement, not a precise utilization.

## Caveats

- The issue count is per **warp**, and a block runs 8 warps. The 1.74 G figure counts
  every warp's instructions, so the comparison against a per-SIMD issue capacity is
  like for like.
- Issue capacity is not achievable capacity. Real kernels lose some to stalls that
  even perfect latency hiding cannot remove, so "4%" understates the gap to a
  realistic ceiling rather than overstating it.
- This is an accounting argument, not a profile. It says throughput and bandwidth
  are both excluded and latency is what remains; it does not say which instruction in
  the visit dominates the chain. A profile would answer that and is still the right
  first step before choosing `TQ`.
