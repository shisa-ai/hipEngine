# VibeVoice prefill GEMM probe: hipBLASLt bf16 unsupported on this ROCm

## Summary

Prefill cost analysis for the Qwen2 VibeVoice backbone and a probe of
hipBLASLt as a faster GEMM route. Follow-up to
`20260914T000538.174057Z-lhl-vibevoice-asr-speed-2d2c8f.md`.

## Changes

- `hipengine/core/hipblaslt.py`: `problem()`/`HipblasLtProblem` gained
  `ab_type`/`cd_type` parameters (defaults preserve the fp16-in/fp32-out
  production path byte-for-byte).

## Validation

- Prefill accounting (146 rows, gfx1151): 29.5 ms/layer, of which the
  three FFN GEMMs are ~25.5 ms - the in-tree WMMA bulk GEMM runs the
  146x3584x18944 shape at ~0.55 TFLOPS (tuned for large row counts;
  two row-tiles with 87% padding on the second). q/k/v/o GEMMs and the
  new prefill attention are 0.7-0.8 ms each. Fixing the FFN prefill
  GEMM shape (about 8x headroom to torch's rocBLAS rate) would take the
  E2E total below torch.
- NEGATIVE: hipBLASLt heuristics return status 6 (NOT_SUPPORTED) for
  bf16 A/B inputs under every valid compute type (2, 4, 5) and every
  C/D combination on this ROCm 7.15.26333 build; fp16 (type 2) works.
  Raw dtype probing beyond valid combos segfaults the heuristic call -
  do not brute-force enum values.
- Existing fp16 hipBLASLt path: 47 tests pass unchanged
  (test_gpu_hipblaslt + test_unit_laguna_f16_hipblaslt).

## Next

- Candidate routes for the FFN prefill GEMM: (a) extend the WMMA GEMM
  with a small-rows tile shape, (b) bf16->fp16 converted weights for the
  prefill-only GEMM path (numeric drift within bf16 rounding), or
  (c) a rocBLAS bf16 GEMM wrapper if core/rocblas.py exposes one.
