# Design: a portable prefix checkpoint for prefix-cache hits, and what it must contain

## Summary

Prefix-cache hits report `prefix_reuse_k0` with zero cycles and decode at AR
speed because a reused prefix produces no hidden rows for a provider to be primed
from. The fix is a portable provider checkpoint captured once per completed
prompt at its block-aligned prefix length and restored for a later request whose
matched prefix equals it exactly. This entry establishes what such a checkpoint
must contain, why the existing request-local checkpoint cannot serve, the
alignment contract, the one storage decision left open, and the ordered plan.

## Decision

Task #21 is implemented by capturing one **portable provider checkpoint per
completed prompt** and restoring it for a later request whose matched prefix
equals it exactly. It is not implemented by replaying the target over the cached
prefix, and not by extending the existing request-local checkpoint's lifetime.

## What already exists, and why it is not enough

`Qwen35GGUFNextNExecutor` already has the machinery for a *rewind* checkpoint:

- `Qwen35GGUFNextNRequestCheckpoint(request_id, slot, state_pairs, position,
  context_length)` -- backups of the mutable Conv/GDN state plus the logical
  cursor. It deliberately does not copy KV: restoring the cursor is what makes a
  rejected proposal's KV suffix invisible.
- `capture_request_checkpoint` / `restore_request_checkpoint` /
  `release_request_checkpoint`, driven by the adapter's
  `restore_provider_checkpoint` bundle for pre-commit failure recovery.

Three properties make it unusable for a prefix-cache hit:

1. It is bound to a **provider request slot** (`_request_slots[request_id]`) and
   `restore_request_checkpoint` raises when slot ownership changed. A new
   request that reuses a cached prefix is a different request, so it needs the
   prefix state to be *portable across requests*, not rewindable within one.
2. It does **not contain the provider's KV**. The NextN provider's KV is
   provider-private, not shared with the target's paged KV:
   `_singleton_slot_scratch` slices `full_key_caches` / `full_value_caches` per
   private slot and rebases the block table to cache-local page coordinates. So
   the prefix's provider KV lives in provider-private buffers that the radix
   cache neither owns nor evicts.
3. It has **no hidden row**. The shifted NextN alignment needs the boundary
   hidden row, which is target state (`target._last_target_hidden_ptr`), not
   provider state.

## The alignment contract

`_catch_up_provider` walks the prompt as: at position `p`, consume token
`prompt_ids[p]` with hidden `rows[p-1]` (zeros at `p == 0`); afterwards it copies
`rows[-1]` into the root buffer, which the first draft step consumes together
with the next root token. So after walking tokens `0..P-1` the provider is
positioned "at `P-1`'s hidden, ready for the token at `P`".

A checkpoint taken at prefix length `P` must therefore contain exactly:

| component | why |
| --- | --- |
| provider KV rows for `0..P-1` | the private KV the draft step attends to |
| Conv/GDN recurrent state at `P-1` | the mutable state `capture_request_checkpoint` already backs up |
| the boundary hidden row `rows[P-1]` | the shifted input the next draft step consumes |
| `position = P`, `context_length = P` | the provider cursor after the walk |

Restoring it for a hit row makes the suffix walk the same loop with an initial
hidden row and an initial position, i.e. `_catch_up_provider(...,
start_hidden=checkpoint.hidden, start_position=P)`. The first suffix step
consumes the checkpointed boundary hidden, so no hidden row for the prefix is
needed beyond that one row.

## Capture point and reuse rule

The cache match is block-aligned (`complete_blocks * block_size`), and a later
turn's prompt is the previous prompt plus a new user turn -- so the reused prefix
ends exactly at the previous prompt's end. That makes one capture point
sufficient: **the block-aligned prefix length of the prompt just prefilled**, and
the reuse rule is an exact match (`matched_token_count == checkpoint.prefix_len`).

The currency rule from the priming-source work carries over unchanged: a restored
checkpoint is a valid source only while the row is at its first draft step
(`generated <= 1`), because the checkpoint positions the provider at `P` and
nothing advances it over tokens the target has already produced.

## The open question that decides the storage design

The checkpoint's KV portion must live and die with the target KV blocks it
describes: if the radix cache evicts those blocks, a checkpoint of the provider's
view of them is meaningless, and a retained checkpoint is a memory leak that
grows with the number of cached prefixes (provider KV is private, so it is a
*second* copy of the prefix's KV).

Two candidate homes, to be chosen when the capture path is implemented:

- a side table keyed by the radix node's block ids, evicted by the same policy
  hook that evicts the node; or
- a per-request checkpoint retained only while the owning request's blocks are
  still resident, released on eviction.

The first is the design that matches `PrefixCacheEntryState` ("pointer-independent
state attached to one live radix prefix node"), and it is the one to try first.
The cost is bounded by one checkpoint per cached prefix, at block granularity.

## Plan, in order

1. **Capture.** At the end of a streamed prompt, snapshot the provider state and
   the boundary hidden row at the block-aligned prefix length, and attach it to
   the matching radix node. One unit, testable without a live server: capture,
   attach, release.
2. **Restore.** `_priming_source` gains the `restored_checkpoint` class; the
   provider attach path skips `_catch_up_provider` for the prefix and walks only
   the suffix from the restored boundary. RED cases: a hit row whose matched
   prefix equals the checkpoint (speculates), a hit row whose match is shorter
   (falls back to absent, AR), a stale checkpoint (row past its first draft step,
   AR), and an evicted checkpoint (AR).
3. **Measure.** Live cache-on c=1, turns 2+, dense 27B on gfx1151: the hit rows
   currently report `prefix_reuse_k0` with 0 cycles and decode at AR speed
   (~12 tok/s/request against the 28 tok/s the miss rows reach). Success is those
   rows engaging at the miss rows' rate on the same load, with the same output
   and no acceptance collapse.

## Why this is the right shape

The reviewer's constraint on #21 was to reconstruct provider inputs from a
checkpoint rather than by replaying the target's cached prefix. The existing
request-local checkpoint shows the provider can snapshot its mutable state
cheaply; what is missing is portability (a slot-independent blob), the KV
portion, and the boundary hidden row -- all three named above, with the one
storage decision left explicitly open rather than guessed.
