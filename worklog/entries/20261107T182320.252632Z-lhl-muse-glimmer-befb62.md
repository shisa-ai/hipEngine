# Muse Glimmer long-context prefill: multi-token flash attention

## Summary

The Glimmer WMMA flash prefill ran one wave per (query token, KV head), so
every staged 16-key K/V tile served one token's 16 Q heads and was re-read by
every token of the chunk; prefill fell from 387 tok/s at 4K to 265 at 32K. A
multi-token sibling (8 waves = 8 adjacent tokens per block, shared K/V tile,
uint4 staging, tiles aligned to absolute 16-key boundaries) is now the default:
4K 387 -> 432, 16K 321 -> 393, 32K 265 -> 354 tok/s (r=1, zbook,
power-capped at 70 W PPT). 16 tokens per block measured slower (422/340).

Also removed the per-chunk keep-mask build + two synchronous H2D uploads
(two [chunk x max_context] uint8 masks no kernel reads; ~135 MB each per chunk
at a 128K context) and the unused gemma4 prefill attention import.

Negative result (not landed): a split-K (8-wave) Q4 decode GEMV with
bit-consistent multi-row verify siblings was 1.04-1.07x in isolation but
identical in the decode graph (57.09 vs 57.20 ms Q4 per step; both ~219 GB/s,
the in-graph read ceiling here). A vector-header load change to the exact
grouped kernel was also neutral end-to-end. Neither shipped.

## Changes

- hipengine/kernels/hip_gfx1100/attention/muse_glimmer_flash_prefill.{hip,py}:
  multi-token kernel + launcher; wrapper defaults multi_token=True.

- tests/test_gpu_muse_glimmer_flash_prefill.py: production contract vs the

  chunk offsets, tails.
