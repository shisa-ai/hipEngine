# Dense GGUF mixed-format (UD) audit, campaign plan, and strix-halo review

## Summary

Answered why a "UD-" (Unsloth Dynamic) mixed-format GGUF loads on the Qwen3.6-35B-A3B
mixture-of-experts route and refuses on the dense route, turned that into a staged
campaign plan with measured memory targets, and reviewed the third-party
`pwilkin/strix-halo` stack for anything reusable. No GPU was used: the whole
analysis reads GGUF metadata and runs the existing load planner on CPU.

Dense Qwen3.8-27B, three files, same 65 layers, same shapes, same plugin tensor-map
result (851 present, 0 missing, 0 unexpected, 0 shape errors), differing only in the
format assigned per tensor:

| File | Formats (excl. F32) | Stored | BF16-converted | Refused | Resident if refusals tolerated |
| --- | --- | --- | ---: | ---: | ---: |
| `Qwen3.8-27B-Q4_K_M` | Q4_K 294, Q6_K 67, Q5_K 48, Q8_0 1 | 15.92 GiB | 0 | 0 | 15.92 GiB |
| `Qwen3.8-27B-UD-Q4_K_M` | 8 kinds | 15.32 GiB | 277 | 18 | 37.20 GiB |
| `Qwen3.8-27B-UD-Q4_K_S` | 11 kinds | 14.29 GiB | 270 | 41 | 35.76 GiB |

Formats with no dense decode path at all, which are what abort the load: Q3_K (13),
IQ3_S (15), IQ4_NL (7), IQ3_XXS (5), IQ2_S (1) in `UD-Q4_K_S`; Q3_K/IQ4_NL/IQ3_S in
`UD-Q4_K_M`. Formats that load only by expanding to dense BF16: IQ4_XS (172),
Q5_K (80), Q6_K (17 of 18), IQ2_XS (1). Targets are 32 GiB (gfx1100 W7900) and
39 GiB (gfx1151), so expanding is disqualified: the UD file ends up needing more
resident bytes than the plain `Q4_K_M` file it is meant to improve on.

Measured campaign ordering for `UD-Q4_K_S` (planner verdicts, both backends
identical):

| Step | Converted | Resident | vs plain Q4_K_M |
| --- | --- | ---: | ---: |
| nothing implemented | 270 (8.67 -> 30.14 GiB) | 35.76 GiB | +19.84 GiB |
| decode repack for raw IQ blocks | 244 (8.18 -> 28.75 GiB) | 34.86 GiB | +18.94 GiB |
| that plus IQ4_XS as a dense read path | 80 (2.32 -> 6.68 GiB) | 18.65 GiB | +2.73 GiB |

So repack alone is worth under a gigabyte and IQ4_XS is worth 16.2 GiB; the
ordering in `docs/UD-QUANTS.md` follows that, not intuition about which kernel is
easiest.

Two decisions recorded:

1. **Dense 27B Q4_K_S evidence stays blocked on a plain (non-UD) Q4_K_S file.** The
   file downloaded for the rerun is `Qwen3.8-27B-UD-Q4_K_S.gguf` (8.37 of ~14.6 GiB
   on disk at review time, tensor table complete, tensor data incomplete). Its
   format mix is not Q4_K_S and it cannot load, so it cannot substitute for the
   layout the retained 2026-08-16/17 rows describe.
2. **UD dense support is a campaign, not a flag.** Phase 0 is a layout decision,
   not a kernel: the cost is set by how many distinct formats a file uses. Phases
   are IQ4_XS, then Q3_K/IQ3 family, then replacing format-stamp switches.

External review (`pwilkin/strix-halo`, its llama.cpp branch, and the
`ilintar/qwen3.8-27b-gguf-strix-halo` card) found **no quantization kernel to
port**: the installer repo holds `install.sh`, site files, and benchmark JSON; that
fork's README/model card attribute its custom work to a unified-memory scheduler
ring, ROCm top-k from llama.cpp PR 28313, and a retained-PM4 command-list path in a
forked ROCm. Useful findings are methodological: their 27B target deliberately
converged on **two formats** (496 IQ4_XS + 10 Q8_0 + 360 F32, with an explicit
tensor map to avoid the `MOSTLY_IQ4_XS` preset's Q5_K substitutions), which is the
Phase 0 argument in measured form; their IQ4_XS speculative draft beat a Q8_0 draft
by +1.79%..+5.67% with matching target-output hashes; and they report IQ4_XS
perplexity 15.3977±0.73357 vs BF16 15.1721±0.72292 on 16 held-out 512-token chunks
(their own note: small local evaluation, not a quality benchmark). All third-party
figures are unverified by us and are recorded as external anchors only, not
comparisons.

## Changes

- `docs/UD-QUANTS.md` (new): what a UD file is, measured per-format routing on both
  backends, the memory arithmetic, why the experts route differs, the
  header-stamp trap, staged campaign scope with gates, out-of-scope list, and the
  strix-halo assessment with confidence and non-portable items.
- `scripts/gguf_quant_route_audit.py` (new): prints the per-format kernel /
  BF16-expand / refuse verdicts and resident-memory deltas by reusing
  `hipengine.loading.gguf` decoders, `build_qwen35_gguf_tensor_map`, and
  `plan_qwen35_gguf_weight_spec` with flags read from backend package capabilities.
  Deliberately does not import `hipengine.kernels.*` (that registers kernels and
  needs the HIP runtime) and skips only `scan_gguf`'s final byte-range size check,
  so a partial download is still readable. `--check-constants` fails if a capability
  constant disappears from every backend.
- `tests/test_scripts_gguf_quant_route_audit.py` (new): five CPU tests. Two pin
  bugs found while writing the script: reading `frozenset({"mostly_q4_k_s"})` as one
  token, which silently reported the gfx1151 FP16-recurrent-state default as off
  for a Q4_K_S-stamped file; and treating a capability defined on one backend only
  as a rename. Plus a truncated-file header test.
- `docs/GGUF.md`: new "Mixed-format (Unsloth Dynamic) files" section stating the
  dense/MoE split and pointing at the audit and the campaign doc.
- `docs/REFACTOR.md`: new open entry for the two gfx1151 switches that key on
  `general.file_type` instead of the actual format histogram, with the replacement
  trigger and the fixture that should exist.

No engine, kernel, dispatch, benchmark, or scoreboard file changed.

## Validation

- `.venv/bin/python scripts/gguf_quant_route_audit.py` over the three 27B files with
  `--check-constants --json`: reproduces the tables above; identical verdicts on
  gfx1100 and gfx1151; `fp16_recurrent_state=on` only for gfx1151 on the
  Q4_K_S-stamped file.
- Repack counterfactual run in-session (`decode_repack` True vs False, same file):
  conversions 270 -> 244, Q5_K 20 and Q6_K 7 tensors reach T16 kernels. This is the
  source of the Phase 1 ordering table.
- `.venv/bin/python -m pytest tests/test_scripts_gguf_quant_route_audit.py -q` -> 5 passed.
- Docs re-read end to end. Two draft errors were caught that way and corrected
  against measurement before committing: a tensor count of 278 (actual 277) and a
  per-family table built from suffix collisions, which misreported the token
  embedding, `attn_gate`, and `output` rows. Corrected from a per-suffix sweep that
  also surfaced two facts worth keeping: recurrent alpha/beta go F32 -> Q8_0 and the
  MTP projection goes Q8_0 -> Q6_K between the two files.
- Not verified: the strix-halo fork's full diff was not read; the claim that its
  IQ4_XS path is upstream rests on its README/model card plus a commit-message
  search that returns zero matches and may only cover the default branch.
