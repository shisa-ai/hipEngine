# Decode-graph node leaked its LLM owner, starving later MTP resident sessions

## Summary

The six order-dependent MTP OOMs recorded in
`worklog/entries/20261003T210847.101473Z-lhl-mtp-order-vram-exhaustion-f4c5d0.md`
have a named cause: `tests/test_gpu_gemma4_decode_graph_capture.py` opened a
public `hipengine.LLM` (17 GB Gemma-4 GGUF) through `_get_text_generator()`
and `_ensure_runner()` and never closed it. The graph session closed itself,
but the model weights and KV cache belong to the `LLM`'s text generator, so
they stayed resident for the rest of the process. Measured: 21.19 GB after the
runner load, 28.49 GB after one short forward, 0 B after `LLM.close()`. On the
48.3 GB card that left roughly 19.8 GB free — below the ~20.5 GB a later
`Qwen35GGUFResidentSession` needs — which is why the MTP nodes only failed when
they ran after this file and never failed alone.

This entry supersedes the "sufficiency, not confirmed original cause" caveat in
the diagnostic entry above; the mechanism is now reproduced end to end.

## Changes

- `tests/test_gpu_gemma4_decode_graph_capture.py`: added `_owned_llm(model)`, a
  context manager whose `finally` calls `LLM.close()` on success, assertion
  failure, or any exception; added the `gemma4_llm` fixture that wraps it; the
  node now takes `gemma4_llm` instead of constructing a bare `hipengine.LLM`.
  Replay assertions and sequence shapes are byte-for-byte unchanged.
- `tests/test_unit_gemma4_decode_graph_llm_owner.py`: new CPU regression that
  fault-injects a failing body through `_owned_llm` with a fake `LLM` and
  asserts close runs on normal exit, on an exception, and on an early assertion
  failure; one structural test pins that the GPU node requests the owner
  fixture so a future edit cannot silently drop it.

## Validation

Environment for every device run:
`env -u HIP_VISIBLE_DEVICES ROCR_VISIBLE_DEVICES=0 HIP_PATH=/opt/rocm ROCM_PATH=/opt/rocm HIPENGINE_COMPILER_VERSION_FILE=/tmp/gemma4-16k-hipcc-version.txt`.

- Unclosed-owner measurement (same public API the node used): 0 B before, 21.19 GB
  after `_ensure_runner()`, 28.49 GB after one forward, 28.49 GB left live
  unclosed, 0 B after `LLM.close()`.
- Fixed pair, one process (graph node then
  `test_gpu_m4_gguf_mtp_draft.py::test_m4_resident_session_hidden_seed_capture`),
  with live `memory_stats()` bookkeeping around each node: `2 passed in 141.29s`;
  `current_allocated_bytes` was 0 B before and after the graph node and before
  and after the MTP node — no retained model ownership, no OOM.
- Counterfactual, one process: replicate the old node (open `LLM`, ensure
  runner, one forward, do not close) → 28,489,352,604 B live, then run the same
  MTP node → `1 failed in 90.31s` with `hipengine.core.hip.HipError: HIP error
  2: out of memory`. This is the exact failure shape the six nodes showed.
- CPU regression: `tests/test_unit_gemma4_decode_graph_llm_owner.py` `4 passed`.
- Graph replay assertions ran unchanged in both the pair run and the earlier
  four-file run; no assertion was relaxed.
