# Sampled serving arm blocked: the adapter's route check never qualifies at runtime

## Summary

The sampled-acceptance mechanism is implemented and its distribution gate passes
(`9b588fec2`), and the server import breakage that the first serving attempt found
is fixed (`990f6af41`). The serving arm itself is **blocked**: with the route opened
by a temporary evidence-row edit, a `temperature 0.7` request still never reaches
the adapter's sampled branch, so there is no serving measurement to qualify a row
with. This entry records exactly how far the request gets, which is three gates
further than the previous handoff knew.

Measured on zbook / gfx1151, Qwen3.8-27B `Q4_K_M`, production profile, bf16 KV,
`--max-context-tokens 8192 --speculative-mtp-serving auto
--speculative-candidate-budget 3`, `scripts/sharegpt_mtp_routing_pass.py
--temperature <t> --route-mix off,off,on,on --output-len 128`:

- **Greedy explicit MTP works on this tree**: the `on` arm decodes **26.93 tok/s
  against the in-run AR arm's 20.64 (+30%)**, 253 of 256 tokens from speculative
  cycles, 89/87 accepted drafts, `reconciled=2/2`. So the harness, the row edit,
  the explicit route, and the planner are all sound.
- **Temperature 0.7 selects `default` and emits nothing speculative**: with
  `speculative_mtp: true`, the response reports
  `decision_reason=automatic_mtp_scope_not_promoted`, `selected_route=default`,
  `k0_class=transitional_k0`, 0 draft cycles, and **254 `no_provider` events**
  (one per autoregressive step) at 13.06 against the AR arm's 13.59 tok/s.

## Changes

- None retained. The three temporary edits used for the diagnosis were reverted;
  the tree is at `990f6af41` with no uncommitted changes.

## Validation

The diagnosis chain, each step observed rather than inferred:

1. **Third gate, server-side.** `hipengine/server/api.py:13222`
   (`_speculative_mtp_route_for_request`) returns `_SPECULATIVE_MTP_K0_ROUTE` for
   *any* request with a sampling blocker (`if blockers: return K0`), so a
   temperature request never reaches the model-plugin resolver at all. That is why
   the previous entry's two refusal points (the resolver's
   `sampling_mode_not_qualified` and the adapter's `_sampled_route_qualified`)
   never fired: the request was already K0.
2. **With that routing opened** (temporary edit: a servable sampled request keeps
   typed intent), the plan does select `speculative_mtp` (`selected_route` and
   `effective_route` both report it) but every tick still refuses: 254
   `no_provider` events, 0 draft cycles, no MTP tokens.
3. **The adapter's sampled branch never runs.** Temporary instrumentation at both
   `propose_batch`'s sampled proposal and `execute_target_frontier`'s sampled
   prepare printed nothing across a full run, so `_sampled_route_request()` is
   returning False, which means `_sampled_route_qualified()` is False in the
   server process - even though the same interpreter's resolver admits the same
   row for `sampling_mode="sampled"` (verified directly in the vllm env, with
   `hipengine` resolving to the repo copy).
4. The four static checks in `_sampled_route_qualified()` are
   `backend == "hip_gfx1151"`, `target_arch == "gfx1151"` (a generator property
   derived from the backend, read at `hipengine/generation/qwen35_gguf.py:1263`),
   `weight_quant == "gguf_q4_k_m"` (the adapter's default), and
   `artifact_size_bytes == _adapter_artifact_size(generator)`. The first three
   match by inspection; the fourth is the prime suspect because it depends on the
   weight index being loaded when the capability is built.
