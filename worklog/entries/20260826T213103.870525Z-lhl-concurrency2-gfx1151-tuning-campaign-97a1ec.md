# gfx1151 CONCURRENCY2 T1.0 prefill attribution and route correction

## Summary

Completed T1.0 attribution and corrected the earlier additive interpretation of
the forced-legacy response timing fields.

Two same-host p512 Q4_K_M A/B probes show target prefill itself is healthy:
`prefill_batch_native` is 1333-1338 ms (382.7-384.2 tok/s) across plain,
GDN-capture, hidden-seed return, and full llama-compat MTP env variants;
`session.prefill` is 1274-1276 ms (401.2-401.9 tok/s) across bulk/capture/plain
variants, and the 512xhidden D2H is 0.3 ms. Capture/hidden return costs <0.4%.
No prefill kernel candidate is admitted.

The old forced route (`gguf_llama_compat_mtp_server`) retains the full prompt
hidden slab and serial `Qwen35GGUFResidentMTPDraftRunner.write_kv_rows()`
post-prefill NextN catch-up (one seed/token/KV write per prompt row + drain).
That is the already-solved OI-3 owner. Staged MTP2 already uses the retained
`_StreamingNextNPromptSink` and the existing exact evidence reports p512 TTFT
13.079 -> 10.356 s (-20.82%) with the slab replaced by one 10,240-byte row.
Do not add a duplicate sink or optimize the legacy fallback.

A current public c1/canonical-suite/max_tokens=4 smoke requested MTP explicitly
but all 10 cells routed to AR with typed reason
`execution_profile_not_qualified`; backend path was
`gguf_packed_ar_server_decode`. Therefore the campaign critical path is T0.4:
exercise and production-qualify staged MTP2. Per user direction, speed gains
bind to the production execution-profile numerical/task gate, not generated-ID
bit equality; strict fallback remains required.

Correction: packed chunk wall is copied into each member request's telemetry.
Wide-cell `prefill_ms` / `target_verify_ms` records cannot be summed across
requests. The prior “c8 wall equals summed per-request work” and derived
per-position timing statement are withdrawn.
