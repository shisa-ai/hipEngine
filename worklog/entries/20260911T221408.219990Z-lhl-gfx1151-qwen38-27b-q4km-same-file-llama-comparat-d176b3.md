# gfx1151 Qwen3.8-27B Q4_K_M same-file llama.cpp comparator

## Summary

The gfx1151 Qwen3.8-27B `Q4_K_M` lane now has a same-file, same-host,
same-session llama.cpp comparator on both prefill and decode, and the comparison
shows hipEngine does **not** lead this file at every working shape. The lane's
published hipEngine rows were re-measured at HEAD and reproduce to within 0.22%,
so no published number changes; what changes is that the row is now externally
grounded, and the "beats llama.cpp at every working shape" prose in the `Q4_K_S`
section can no longer be read as covering it.

The unit also corrects a provenance claim I recorded earlier in
`docs/20260909-GFX1151-GFX1100-TRANSFER-AUDIT.md` section I. That section stated
the binding llama cells `352.426/364.443/367.993` "come from the Q4_K_S
campaign". They do not. They come from
`benchmarks/results/2026-08-15-gfx1151-qwen38-27b-p0-baseline.json`, whose
`model` block is the **`Q4_K_M`** file, sha256 `7e78da5d…c6fe169` — the same
artifact this lane measures. The `Q4_K_S` campaign borrowed them and its own key
names say so (`llama_hip_q4km_prefill_tok_s`), while measuring a separate
`same_file_llama_prefill_512` for its own file. That P0 artifact also carries
`true_ar_tok_s` and a uniform `token_sha256_i64`, so this lane had a token-exact
same-file comparator on both axes all along; it lacked publication, not a
comparator.

recorded rather than one being promoted. `llama-bench` generates its own prompts
and cannot accept the repeated-token prompt the hipEngine sweep uses, so that
tier is a split-timing comparator and not a token-exact one; its decode is
decode-at-offset (`-p 0 -n 128 -d <prompt>`), a different timing scope from a
resident-session AR decode after a real prefill.

Narrow tier run: `scripts/sync_benchmark_readme.py --check` passes, and
`tests/test_docs_publish_provenance_gate.py` plus the worklog tests pass. No
kernel, dispatch, or engine source changed, so no GPU correctness gate beyond
the sweep's own in-run gates applies.

## Next

1. **A defect was hit and is not fixed in-tree.**
   `hipengine/benchmark/provenance.py::detect_device_name` resolves the device
   through `ctypes.CDLL("libamdhip64.so")`, which is not on the default loader
   path on a TheRock-only host with no system ROCm. The first comparator attempt
   completed all six `llama-bench` cells and then died in artifact assembly with
   `ValueError: GPU artifact provenance requires device_name`, discarding them.
   `scripts/run_gfx1151_readme_refresh.sh` runs its `llamacpp` phase with a bare
   `PYTHONPATH=... "$THEROCK_PY"` instead of the `"${THEROCK_ENV[@]}"` array its
   `hipengine` phase uses, so that maintained script hits the same failure on
   this host. Either prefix the phase with the hermetic env or make
   `detect_device_name` fall back to `rocminfo`/`--card-name`.
2. **Section I targets 2 and 3 remain open** and are unchanged by this unit:
   record a gfx1151 verdict for each of the 18 gfx1100-only capability gates,
   and settle whether the missing `MOSTLY_Q4_K_M` dense-prefill scratch row
   ceiling is safe on gfx1151.
3. **Decode is still the weaker axis on this file.** hipEngine trails Vulkan
   decode at every shape by 4-6%, which is the largest remaining same-file gap
   on this lane and is not addressed here.
4. **`scripts/worklog.py new` writes a topic its own `check` rejects.** For a
   title whose slug exceeds the 48-character `slugify` limit, `new()` truncates
   the slug in the generated filename but stores the untruncated value in the
   `topic:` front-matter field, so `check` then fails the entry on both
   `topic must be a lowercase kebab-case slug` and `filename does not match
   entry metadata`. Reproduced here: the first generated entry for this unit was
   rejected for exactly that reason and had to be corrected by hand. The same
   mismatch occurs for any title containing `.` or `_`, which `slugify` rewrites
   but `new()` does not. `scripts/worklog.py` is a listed high-conflict file, so
   this is recorded rather than patched.
