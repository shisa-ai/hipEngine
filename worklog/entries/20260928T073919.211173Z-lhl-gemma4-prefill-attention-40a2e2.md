# the parity constraint is a unit test on the logit reduction order and no prefill output gate exists

## Summary

`20260928T073848` said the port's first question is whether Gemma 4's parity contract pins
**logit bits** or **final output**, because that decides whether the WMMA path in the Laguna
kernel is available. The answer is more specific than either option, and it changes what the
port has to preserve.

## What the constraint actually is

`gemma4_attention.hip`'s comment says the warp-per-key reduction is "bit-identical to the
block kernel's over the same values" and that "the parity test catches it". The test is:

**`tests/test_unit_gemma4_attention_logit_tree.py`** -- a CPU unit test whose docstring is
"The exact reduction order of gemma4's warp-per-key attention logit". It asserts that the
tree matches a reference (`assert got == lanes[0]`), that it differs from a plain sum in a
discriminating way (`assert discriminating > 0`), and that the tree is closer to the
reference than the plain sum (`assert tree_matches > plain_matches`).

**So the contract is on the reduction *order of the helper function*, not on any kernel's
output.** It pins `gemma4_warp_key_logit`'s tree; it does not compare a prefill kernel against
anything.

## And there is no prefill output gate

The only attention parity test in the tree is **`test_gpu_gemma4_attention_decode_parity.py`**
-- **decode**, not prefill. Nothing pins the prefill kernel's output against a reference
implementation.

## What that means for the port

**The WMMA path is available.** Replacing the QK^T and PV work with WMMA fragments does not
break an existing output gate, because there is no prefill output gate to break. The
logit-tree contract survives as long as `gemma4_warp_key_logit` keeps its ordering for
whatever still calls it -- which the port may or may not do.

**But the port must add the gate it is removing the need for.** A ported kernel whose
numerics nothing checks is worse than the slow kernel it replaces. Concretely:

1. **a tolerance comparison against the current prefill kernel's output**, at both 2048 tokens
   and a long context, since the two payoffs are separate (`20260928T073811`);
2. **plus the boundary exercise** -- 15872 accepted, 15873 refused, and a value unrelated to
   the threshold -- per the "validate the space, not the gate point" rule, since the port is
   what makes the ceiling move.

## A separate observation worth recording

**The current prefill kernel's numerical behaviour is not pinned against anything.** That is
not a defect in the port's plan -- it is a gap that exists today, and it means any change to
the prefill path, port or otherwise, has no reference to be checked against until one is
written. Worth knowing before the port, not after.
