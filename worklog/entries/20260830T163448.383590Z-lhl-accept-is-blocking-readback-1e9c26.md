# Accept window is the blocking readback; enqueue is 0.2 ms

## Summary

The new `specdec2_mtp2_accept_enqueue_ms` counter (`6c490b5db`) closes the accept-window
accounting exactly
(residual 0.0 ms) and refutes the inference in `20260830T161414…`. There is no front-
section host cost: the
enqueue call costs **0.2 ms**. The window is the **commit call (~20-24 ms)** plus the
**blocking target-accept
readback (~67-80 ms)**, which is where the pipeline waits for the GPU.

## Changes

- `6c490b5db` (committed): the enqueue counter, additive, 21 tests pass.
- This entry: the measurement, and a correction of `20260830T161414…`, which attributed
  the unattributed ~100 ms
  to host work inside `_enqueue_target_batch_accept`. That was wrong.

- Before `790eaee91` the same window reported upload 85-102 ms, commit 1.5 ms, readback
  1.5 ms. After it, upload
  0.1 ms, commit ~20 ms, readback ~67-80 ms. Totals match in both readings, so **no
  measurement was wrong**:
  the wait is charged to whichever call synchronizes first. When the copies were blocking
  pageable memcpys, the
  first copy absorbed the queue drain; with pinned async copies the charge moved to the
  operations that actually
  need the results.
- Interpretive rule for this telemetry: these are nested wait points, not additive work.
  Never read a change in
  one counter as a change in cost without re-reading the whole window sum - which is what
  `20260830T155357…`
  and `20260830T161414…` each did in opposite directions.

## Coherent model now

The engine enqueues the cycle's device work lane by lane, then waits per lane inside the
accept window for
results it just asked for. The readback wait of 67-80 ms per lane-cycle with the device
at most ~55% busy
(`20260830T161414…`) fits a launch-bound eager cycle with idle gaps rather than a
bandwidth-bound one, and pairs
with AR being graph-captured at ~95% device-busy. That is a strong indication, still not
a measurement of the
mechanism.

## Fix direction this points to

- Route (b) from `20260830T155541…` - capture the cycle the way AR captures decode - is
  now the better-supported
  option, since the cost is issue-and-wait, not any single host call.
- A smaller intermediate option worth pricing first: stop reading back per lane inside the
  cycle - issue the
  remaining lanes' work first and read once, so the wait covers a batch instead of a lane.
- Do not re-open pinned copies, upload counts, enqueue host work, or the readback size:
  each is now measured.
