# D9 t16 decode wiring: tiles side allocation, census A/B, gates

## Summary

Wired the D9 t16 decode route into production: every rows==1 GGUF Q8_0
dense projection launch now rewrites to the registered
`t16_gemv_decode_bf16_bf16_out` sibling when its weight ships the
byte-neutral Q8T16 tiles side allocation. The rewrite lands on the
production surface (verified through `hipengine.LLM`'s runner path and the
family census), prefill is untouched, and all correctness gates pass at
KL == 0.0 / top-1 100% / identical greedy-128 ids.

The authoritative performance number is the **census kernel-trace A/B**
(two trace pairs, both arms from one driver): the dense decode kernel
family runs **-6.3% and -6.8%** (2.858 -> 2.664 and 2.853 -> 2.672 ms/tok),
prefill busy is neutral with an identical true-prefill launch count (134
both arms), and total decode busy moves within run-to-run noise
(-1.3%, +0.7%). The t16 tuning screen's -39% headline does not reproduce in
production (see the correction below); the row's Result cell cites the
census.

## Changes

- `hipengine/loading/gemma4_gguf_device.py`: `_plan_one` gives rank-2
  Q8_0 tensors at the seven dense projection slots under `layers.*` an
  `allocation_names=("raw", "tiles")` spec, gated fail-open on
  `Q8_0_T16_SHAPE.validate` (same shape-gate pattern as the Q4_K stacks).
  Root slots (`token_embedding`, `lm_head`) and stacked expert tensors
  keep raw alone. `_planned_nbytes` doubles the dual specs explicitly (the
  tiles copy is the same 34-byte Q8_0 blocks per 16 rows, transposed).
  Both materializers (`materialize_gemma4_gguf_device_weight` and the
  fused qkv / gate_up path) upload the repack beside the raw copy; the
  fused repack runs on the concatenated rows, so a fused weight carries
  tiles for the whole fused shape.
- `hipengine/runtime/gguf_linear.py`: `_q8_t16_tiles_decode_dispatch`
  inserted after `_registered_variant_dispatch` in the launch cache-miss
  chain. Conditions: `abi == "raw"`, `rows == 1`, in/out are tile-16
  multiples, quant `gguf_q8_0`, the weight answers `has_allocation("tiles")`,
  the variant is the legacy `pack8_gemv*` alias (an explicit
  `pack8_gemv_decode` opt-in is a user choice and is left alone), and the
  `t16_gemv_decode_<suffix>` sibling is registered. Hit -> `abi="t16"`
  under quant `gguf_q8_0_t16_v1`; miss -> dispatch unchanged. Capability
  reads `has_allocation` only: an `allocation("tiles")` lookup fallback
  looked correct but routed old test fakes (whose allocation dict contains
  a `tiles` entry) into real kernels with fake pointers and segfaulted the
  suite -- `has_allocation` is the protocol that means "ships tiles".
  `lm_head` (root slot, no tiles) correctly stays on pack8; the 11
  `pack8_gemv_bf16_f32_out` resolutions with no registered t16 sibling
  also stay, which is the capability gate doing its job.
- `tests/test_unit_gguf_q8_t16_tiles_decode_dispatch.py`: 11 new tests --
  route hit/decline matrix (no tiles, rows>1, other quant, explicit
  pack8_gemv_decode opt-in, pre-pack8 base variant, non-tile shape, no
  registered sibling) plus two launch-level tests asserting the t16 ABI
  reads the tiles pointer and the raw path reads the raw pointer.
- `tests/test_unit_gemma4_gguf_device.py`: dual-spec planning tests, a
  byte-neutrality round-trip test (repack -> unpack == raw, host only),
  and the three existing contract tests updated to the new allocation
  tuple (quant keys, gate_up layout plan, resident-bytes summation).
- `benchmarks/results/2026-09-30-gemma4-d9-t16-decode-wiring.json`: the
  census A/B pairs, per-cluster timings, route counts, gate results, and
  the screen-discrepancy note.
- Punchlist D9 row updated with the wiring result.

### Correction to the D9 tuning screen claim

The tuning screen artifact (`2026-09-30-gemma4-d9-pack8-tuning-screen.json`)
timed the pack8 incumbent 1.3-1.8x slower per shape than the same kernel
runs inside the production census pipeline (fused gate/up: screen 34.6 us
vs production 19.42 us; o+down: screen 20.8-33.5 vs production 17.19
blend). Its -39% "t16 over legacy" headline therefore does not describe
the production A/B, and the punchlist row's ~0.5-0.9 ms busy estimate
overstates the takeable win by roughly 3x. The screen's measurements
stand for that instrument (isolated hipEvent launches); the census numbers
above are the production truth and are what the D9 Result cell now cites.
