# GD-4's chunked WY prefill is built, parent-parity correct, and slower than every route that matters

## Summary

I built the FP32 chunked triangular/Woodbury-Young GDN prefill that my previous
entry recommended as GD-4's first build step. It is correct - parent-parity with
the production `tiled16` route at 5.96e-07 on core and 5.59e-09 on state, and in
independent agreement with an fp64 serial GDN recurrence - and it is slower than
every route that matters:

| route | 512 | 1024 | 2048 | vs `wy_chunked` |
| --- | ---: | ---: | ---: | --- |
| `wy_chunked` | 2.620 ms | 6.202 ms | 13.545 ms | — |
| `tiled16` (the screen's baseline) | 2.177 | 5.063 | 11.828 | wy 1.20x / 1.22x / 1.15x slower |
| `wave_norm` (**UD-Q4_K_XL production**) | 2.763 | 5.413 | 10.731 | wy 1.05x faster / 1.15x / 1.26x slower |
| `tiled16_multi` (q4_k_m production) | **1.157** | **3.150** | **7.741** | wy 2.26x / 1.97x / 1.75x slower |

The build issues 1.19x the MACs of the serial chain (58,368 against 49,152 per
token per v-head: the `C x C` key/key and query/key dots recomputed in full by
each of the four value-column blocks, plus the solve and output combination),
which matches the measured 1.15-1.22x.

**I have to correct my own first reading of this unit.** I initially concluded
that the row's 256-VGPR premise was stale because production had moved to
`tiled16`. That was wrong twice: the trace's 72 dispatches are
`<true,true>` = **`wave_norm`**, not `register_state`; and 56 VGPR is the
non-multi `<16,16,4,1>` instantiation, which no profile selects. The lane split
is the real story:

- **`gguf_ud_q4_k_xl` (the lane the trace measured, and the gfx1151 topline
  lane):** `PRODUCTION_ARITHMETIC_RECOVERY_FLAGS` zeroes
  `GDN_COLWARPS_PREFILL`, so the runner takes the register path, which
  `GDN_REGISTER_PREFILL=1` + `GDN_WAVE_NORM=1` resolve to
  `qwen4exp_sigmoid_wave_norm_prefill` - `<true,true>`, **256 VGPR**. The
  premise holds.
- **`gguf_q4_k_m`:** the gate is open and `GDN_TILE16_VARIANT` names
  `qwen4exp_gdn_tiled16_multi_prefill` - `<16,8,4,8>` built with DPP +
  MULTI_COLUMN, **85 VGPR**.

So the row's mechanism is real, but it is not the cheapest escape: the
multi-column route already escapes the register bound at 85 VGPR and is
**1.39-2.39x faster than the UD lane's `wave_norm` route**. It is gated off on
UD by arithmetic admission (not bit-exact; NMSE 1.8e-14), and on q4_k_m the
composition fails its envelope for a pre-existing reason with an attribution
control that fails worse.

## Validation

- Parent parity vs `tiled16` on the GD-3 fixture shape (Hk16/Hv48/Dk=Dv=128,
  64 tokens, synthetic inputs): core max abs 5.96e-07 (3.8e-7 of ref max),
  state max abs 5.59e-09 (1.9e-7 of ref max).
- Independent check against an fp64 serial recurrence of the textbook GDN rule:
  2.9e-05 on output, 4.2e-04 on state.
- Speed, 7 reps after warmup, medians, gfx1151, all seven routes in one session
  via `scripts/qwen4exp_gd3_recurrence_screen.py --tokens 512 1024 2048
  --reps 7`: the table above. Largest rep spread 6.1%, most under 2.6%; a first
  5-arm run reproduced the `tiled16`/`wy` columns within 1.3%, and
  `tiled16_multi`'s 1.157 ms at 512 matches the promotion artifact's own
  1.112 ms.
- Register counts re-derived from `.amdhsa_next_free_vgpr` on a fresh compile of
  the current source (`amdclang++ -x hip --offload-arch=gfx1151 -O3 -mllvm
  -amdgpu-unroll-threshold-local=600 [--cuda-device-only -S]`, with
  `-DHIPENGINE_QWEN4_GDN_DPP=1 -DHIPENGINE_QWEN4_GDN_MULTI_COLUMN=1` for the
  production multi build): `wave_norm` 256 / 0, `register_state` 256 / 0,
  `columnwarps` 46 / 0, non-multi `tiled16` 56 / 16640, **`tiled16_multi`
  85 / 16640**, `wy_chunked` **169** / 28576. `rocprofv3` reports the allocated
  counts (169 -> 176 VGPR, 28576 -> 28672 B LDS), which is the cross-check that
  caught the first wrong parse (I had read a `.set` symbol as the count).
- Lane selection read from `hipengine/generation/qwen4_exp_profiles.py`
  (`_production_selections` line 378, the env bindings at 763-764/824-826, and
  `PRODUCTION_ARITHMETIC_RECOVERY_FLAGS` at 59-64) against
  `hipengine/runtime/qwen4_exp_runner.py:286-320` and `:6039-6200`, and
  cross-checked against
  `benchmarks/results/2026-09-30-qwen4exp-gd4-family-share/rocprof/prefill_kernel_trace.csv`
  (72 dispatches of `<true,true>`, zero tiled, bound env
  `GDN_COLWARPS_PREFILL=0`, model root `UD-Q4_K_XL`).

## Next

- GD-4 is closed: the FP32 build is correct and slower, and the register bound
  it was meant to escape is already escaped by a registered route
  (`tiled16_multi`, 85 VGPR, 1.39-2.39x faster than the UD lane's route). The
  fp16 WMMA arm should not be started on the register-capacity argument.
- The remaining question is **arithmetic admission for `tiled16_multi` on the
  UD lane**, which is a governed profile/gate question rather than a kernel
  build. That is a separate unit and needs the full envelope, not a screen.
- The GD-3/GD-4 family share (194.487 ms, 4.97%) is measured on the UD lane's
  `wave_norm` route, which is the right route for that lane, so the figure
  stands for UD; it should not be read as the q4_k_m lane's share.
- One measurement trap recorded for future route comparisons: the production
  prefill wrappers apply `core_norm_gate` in place after the recurrence, so a
  new recurrence kernel that writes raw `core` will look ~100% wrong against
  them while its state matches exactly.
