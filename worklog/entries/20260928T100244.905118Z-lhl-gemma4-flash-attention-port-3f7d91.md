# the intra-lane pairing is not the left-to-right reading and the test caught it

## Summary

The logit tree is now an executable, CPU-only oracle:
`tests/test_unit_gemma4_attention_logit_tree.py`, **6 passed**. It pins the order
that `20260928T093102` recorded in prose, and writing it caught an error in that
prose.

The kernel's intra-lane stages are

```
for (k = 0; k < 4; ++k) p[k] += p[k + 4];   // (0,4) (1,5) (2,6) (3,7)
for (k = 0; k < 2; ++k) p[k] += p[k + 2];   // (0,2) (1,3)
p[0] += p[1];                                // (0,1)
```

which produces

```
((p0 + p4) + (p2 + p6)) + ((p1 + p5) + (p3 + p7))
```

**not** the left-to-right grouping

```
((p0 + p4) + (p1 + p5)) + ((p2 + p6) + (p3 + p7))
```

that a reader naturally writes when summarising the three stages. The two are
different trees and disagree in the last bits. I wrote the second form into the
first version of the test as an "independent route" and it failed on both widths
(`6.7671127` against `6.767112` at head_dim 512), which is how the mistake
surfaced. `20260928T093102`'s prose describes the stages but not the pairing, so
it was ambiguous rather than wrong; this entry makes it explicit.

That the two groupings disagree on real inputs is itself asserted
(`test_the_intra_lane_pairing_is_the_kernel_pairing` counts the disagreements over
64 random inputs and fails if there are none), so the pin cannot pass vacuously.

## Changes

- `tests/test_unit_gemma4_attention_logit_tree.py` (new): four tests. The tree
  oracle at both widths with the leaves' contraction-off multiply and the
  512-wide fused second leaf; a check that the tree and a plain dimension-order
  sum disagree on random data, so the order is observable and worth pinning; a
  fixed-input regression pin written as the kernel's three literal stages; and a
  boundary check that 8 leaves at head_dim 256 and 16 at 512 each cover every
  dimension exactly once, which is what selects the branch.

CPU-only, no HIP guard needed, so it runs in the default unit tier.

## Validation

```
uv run pytest tests/test_unit_gemma4_attention_logit_tree.py -v
# 6 passed in 0.32s
```

The file is a specification, not a parity test: it cannot show that the GPU
kernel matches the tree, because it never runs the kernel. The comparison that
does is the port's acceptance test and belongs beside
`tests/test_gpu_gemma4_attention_geometry.py`, whose exact-equality idiom it
should adopt.
