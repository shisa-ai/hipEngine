# the long-context boundary is decode attention, and the campaign ladder does not reproduce

## Summary

The request was to measure prefill at 8K/16K/32K/64K/128K for hipEngine and
llama.cpp on the same host and artifact and compare. **Four of the five lengths
have no hipEngine answer**, and establishing that honestly turned into the
larger part of the work.

Three results, in order of how much they change the campaign's picture:

1. **The boundary is decode attention, not prefill and not memory.** hipEngine
   refuses any capacity above **15616 tokens**, at construction, before weights
   load. Under the default `production` profile both prefill geometries are
   already tiled (`gemma4_wmma_flash`, `gemma4_wmma_flash_full`), so prefill does
   not bind. Decode does: **no `decode_attention` variant is registered
   anywhere**, and `decode_slices` "partitions output dimensions, not keys", so
   the split does not reduce per-call LDS. Decode still runs the strict
   key-class kernel at `(keys + 528) * 4` bytes, capping at 15856. A perfectly
   profile-aware guard would move the cap from 15616 to 15856 and still refuse
   16384, so **the guard is not the thing to fix.**

2. **hipEngine leads llama.cpp at every length up to 4096 and loses at 8192.**
   Matched protocols, medians of three samples after one warmup: 1175 vs ~1055
   at 512, 1163 vs 1070.02 at 1024, 1137 vs 1078.20 at 2048, 1103 vs 943.18 at
   4096, and 1042 vs 1193.6 at 8192. The crossover is between 4096 and 8192.
   hipEngine's own decline is smooth and shallow, 1175 -> 1042 across a 16x
   prompt range (-11%), while llama.cpp's is non-monotone and much steeper
   beyond 4096: 1078 -> 943 -> 1194 -> 835 -> 692 -> 547 -> 326.

3. **The recorded campaign ladder does not reproduce, and the harness had two
   defects.** One is fixed here. The other is recorded and unfixed.

## The capability refusal, verbatim

```
Gemma 4 gfx1100 attention requires 67648 bytes of shared memory for head_dim=256,
keys=16384; this kernel supports at most 65536 bytes and needs tiled attention
for this context
```

Measured per requested length, `gemma4_require_context_capacity` on the real
artifact's geometry:

| prompt | context needed | result |
| ---: | ---: | --- |
| 8192 | 8320 | accepted |
| 16384 | 16512 | refused |
| 32768 | 32896 | refused |
| 65536 | 65664 | refused |
| 131072 | 131200 | refused |

The binding geometry is the **5 full layers** (head_dim 512, 2 KV heads, no
window), not the 25 sliding ones. The two terms are
`(head_dim + keys + threads) * 4` for the strict prefill block kernel and
`(keys + 528) * 4` for the key-class decode family; at head_dim 512 the block
kernel gives 15616 and the decode family gives 15856, and the guard reports the
smaller. Production replaces the block kernel with a tiled one, so the surviving
constraint is decode's 15856.

Memory is not the constraint. KV is **0.2253 MB/token** (25 sliding layers at
8 KV heads x head_dim 256, 5 full at 2 x 512), so 128K needs **29.5 GB** against
103 GB available on this host.

**What would clear it:** a tiled decode attention for head_dim 512 / 2 KV heads /
GQA 8 — the decode twin of the `gemma4_wmma_flash_full` prefill kernel that
already exists. A profile-aware guard is *not* the clearing route and would buy
240 tokens.

## Changes

- `scripts/gemma4_campaign_bench.py`: build the LLM with
  `max_sequence_length=int(context)`. The harness previously called
  `hipengine.LLM(model=...)` and assigned `generator.context_length` afterwards.
  That assignment moves only the generator's own request validation; the runner
  sizes its KV cache from the value the factory received at construction, so
  capacity stayed pinned at the 8192 default and `--context` was decorative.
  Every artifact recorded the disagreement — `context_length` 640 / 1152 / 2176
  / 4224 against `runner_capacity` **8192** in all four runs. The effect is not
  cosmetic: the 8192-token point failed outright with
  `prompt (8192 tokens) plus max_tokens (128) exceeds runner capacity 8192`,
  and the shorter points were measured against a KV allocation 13x larger than
  llama.cpp's.
- `tests/test_unit_gemma4_campaign_bench.py`: add
  `test_resolve_generator_passes_the_context_to_the_llm_factory`, which captures
  the factory kwargs through a fake `hipengine.LLM` and asserts the requested
  context reaches it. **RED confirmed** by restoring the pre-fix call form in a
  scratch copy: the assertion fails with `max_sequence_length` absent from the
  captured kwargs. The existing 12 tests did not cover the construction path at
  all, which is why the defect survived.

- `tests/test_unit_gemma4_campaign_bench.py`: **13 passed** with the fix, and the

- **Warmup ramp, established by re-measurement.** pp4096 and pp8192 came back
  bimodal in the forward run. A fresh-process re-run with `-r 5` and 8192 first
  reproduced the split at 8192 (`[873.3, 876.4, 1184.1, 1132.8, 1193.6]`), which
  identifies it as the first ~2 samples after a model load being depressed by
  ~25%, not engine variance. **Any `-r 3` mean that includes them is biased
  low**, which is why pp512 and pp4096 in the forward run are not quotable and
  the recheck values are used instead.
- llama.cpp `tg128` is **not decode-at-length**: `llama-bench` runs it with
  `n_prompt: 0`. It reproduces the recorded reference (41.92 -> 41.04) as a
  protocol control and says nothing about decoding with 128K of KV resident.
- Peak memory was **not** measured. `llama-bench` does not report it and RSS is
  not a proxy: the process showed 1.49 GB resident while holding a 17 GB model
  plus KV, because gfx1151 reports `VMM: no` and the GPU allocations are GTT
  pages outside RSS. The 29.5 GB / ~46.5 GB figures above are computed from
  geometry, not measured.

## Open, recorded rather than resolved

- **The recorded campaign ladder does not reproduce.** It reads 1012.8 / 925.1 /
  804.6 / **628.2** for 512/1024/2048/4096; this session measures 1175 / 1163 /
  1137 / **1103**. The 512 delta is consistent with the T16 LDS-leaf promotion
  (+8.3%), but 4096 is +76%, far too large for it. The LDS-leaf artifact
  recorded the same day independently reports **1103.1 at 4096**, matching this
  run, so the campaign ladder is the one that looks wrong. Not explained.
- **The published 512/128 topline is not self-consistent.** `benchmarks/README.md`
  states 1242 prefill / 28.92 decode / 4.38 s wall. `512/1242 + 127/28.92 =
  4.80 s`, not 4.38 s. Solving the stated wall gives **32.0 decode**, which is
  what this session measures (32.32). The same triple appears in the leaf
  artifact, so it is not a downstream transcription error. Which of the three
  figures is wrong is unresolved and the README was deliberately left unchanged
  rather than guessed at.
- **llama.cpp's pp4096 (943) is anomalously low** against both pp2048 (1078) and
  pp8192 (1194), reproducibly in two independent runs. Growing attention cost
  does not predict that shape. No explanation.
- **KV allocation size materially moves the measurement.** At 512, capacity 640
  versus 8192: prefill 1180 vs 1108 (+6.5%), decode 32.3 vs 28.7 (+12.6%), wall
  4.37 vs 4.89 s (-10.6%). A ladder mixing capacities is not quotable.
- **Decode is not yet comparable across engines.** hipEngine's decode at length
  is in the table above; llama.cpp's is not. A real decode comparison needs the
  server-based reference bench, and it can only cover 8192 and below.
