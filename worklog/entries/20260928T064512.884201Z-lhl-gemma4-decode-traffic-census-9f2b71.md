# the decode traffic census under-counts the MMQ route so its byte total is stale

## Summary

The decode traffic census under-counts the current default. Re-running it after
the MMQ capacity gate became the decode route (`ba97b2cd6`) shows the expert
family collapsed to **0.0 MB** and a new `expert-mmq gate_up` row at 32 launches
and 0.0 MB, with the step total falling from 3219.6 MB to **1868.4 MB**. The
expert traffic did not disappear; the census stopped seeing it.

The numbers that are still trustworthy:

| quantity | value | note |
| --- | --- | --- |
| launches/step | 730.7 | was 825.6, about 95 removed |
| dense `gguf_q8_0` | 1866.7 MB, 218.67 launches | unchanged, as expected |
| step total | 1868.4 MB | **under-counts by the expert share** |

The launch-count drop is consistent in direction with the 9.7% decode win: the
route fix removed launches and gained throughput. Dense traffic is unchanged
because the fix touched only the expert path. But the byte total is not the
current traffic, so any bandwidth derived from it would be wrong.

`spy_mmq` increments a counter and returns; it never sums weight or activation
bytes, unlike `spy_selected`. Two further gaps sit behind that one. The MMQ
**down** projection is not hooked at all -- the census hooks
`gemma4_project_experts_gate_up_mmq`, which is gate/up only, and the down half
lives in a separate `gemma4_project_experts_down_mmq` entry point that appears in
no row of the output. And the installed argument conventions differ per entry
point, so a copy of `spy_selected`'s accounting is not valid for either MMQ hook.
The real signatures, read from the module:

```
gemma4_project_experts_gate_up_mmq(weight, x_ptr, out_ptr, expert_start,
    compact_rows, num_experts, in_features, intermediate, *, scratch, stream,
    runtime) -> bool

gemma4_project_experts_down_mmq(weight, x_ptr, out_ptr, expert_start,
    compact_rows, num_experts, in_features, out_features, *, scratch, stream,
    runtime) -> bool

gemma4_project_experts_selected(weight, x_ptr, selected_ptr, out_ptr, x_rows,
    rows, num_experts, in_features, out_features, *, stream) -> bool
```

The census's own comment for `spy_selected` describes an older convention
(`(x, selected, qweight, out, x_rows, rows, ...)`) in which `x` is first, but the
spy is installed as the function itself and so receives the `Gemma4Projection`
weight first. Its unpacking
(`rows, num_experts, in_features, out_features = a[1], a[2], a[3], a[4]`) reads
`selected_ptr, out_ptr, x_rows, rows` under the real signature. That does not
match the comment, and the resulting byte figures should be re-derived rather
than trusted. This is unresolved here, not settled.

`20260927T225558`'s budget is still the best available and its conclusion is
unrefuted: one step moves 3219.6 MB, which at the 256 GB/s a pack8 Q8_0 GEMV
reaches in isolation is 12.6 ms, while the step took 43.88 ms at 22.79 tok/s --
**29% of achievable**. The same-host llama.cpp reference is 41.92 tok/s, which is
135 GB/s on the same traffic, **53% of peak**. The lever is therefore achieved
bandwidth, not peak, and the residual is roughly 12.6 ms of unavoidable traffic
against about 31 ms of everything else: 825 launches, of which 416 are
norm+rotary costing 2.24 ms, plus an 8.12 ms host floor that is hidden under the
GPU.

## Changes

None. This entry records a measurement result and a defect in the probe that
produced it; no source file was modified. The census, the route ablation and the
host-floor probe are as `20260927T225558` left them.

The defect is recorded rather than fixed because this script has already produced
one silent-hook failure: the route ablation's `no_all_gemv` arm hooked only
`gguf_k_gemv._launch` and so excluded the Q4_K selected family that owns this
artifact's expert gate/up, which made a superset arm measure less saving than its
own subset. Adding a third hook without checking what it catches would repeat
that mistake, and a census that reports a confident wrong byte total is worse
evidence than one that reports nothing for a family.

## Next

1. Hook `gemma4_project_experts_down_mmq`, and give both MMQ hooks byte
   accounting that matches their real signatures.
2. Re-derive `spy_selected`'s accounting against the real signature and check the
   result against a hand-computed expert-matrix size, since its comment and its
   unpacking disagree.
3. Re-read the budget against the current default, then pick the lever. The
   per-family bandwidth spread in the old census -- expert GEMV at 96 GB/s
   against dense at 135 GB/s on the same host -- is the first place to look.
4. The engine-side MTP integration is deliberately not started. The adapter is
   proven at the primitive level (`ec9a95607`) but the opaque protocol needs a
   full `SpecCycleTransaction` cycle with cursor deltas, KV ownership and
   cancellation semantics, and the staged protocol needs six more methods. A
   partially correct speculative cycle commits wrong tokens rather than failing
   loudly, so it should be built as one unit with its own validation.
