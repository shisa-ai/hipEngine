# chat /bench table: one column per metric, MTP switch, colored numbers

## Summary

The `/bench` table in `hipengine chat` is now one column per metric, with units
in the header and right-aligned bare numbers under them: `mtp | cache | prefill
tok/s | prompt tok/s | decode tok/s | ttft s | tpot ms`. TTFT and TPOT are
separate columns because they are the two sides of the speculative tradeoff MTP
trades against decode throughput. The `route` column became an `mtp` switch
(`on` / `off`), and the numeric columns are colored in the terminal theme.

## Changes

- `hipengine/chat_cli.py`:
  - `_BENCH_HEADERS` carries the units, so `_bench_prefill_cell`,
    `_bench_prompt_cell`, `_bench_decode_cell`, `_bench_ttft_cell`, and
    `_bench_tpot_cell` return bare numbers (`259`, `1,656`, `32.7`, `0.00`,
    `30.6`) or `—`. `_bench_cell_text`, which split a cell into a receding token
    count and a colored rate, is gone with the `N tok · R tok/s` cells it
    served.
  - `_Turn.prompt_token_count()` returns the prompt length the request was
    served — usage when the server reports it, else executed prefill plus cached
    tokens — and `_Turn.prompt_rate()` divides it by the prefill window. The
    per-reply stats line adds `prompt X tok/s` when a cache hit made the
    prefilled portion smaller than the prompt, which is the number the cache is
    buying; without a hit the two rates agree and only `prefill` is shown.
  - `_Turn.decode_ms_per_token()` returns `1000 / decode_rate()`, so TPOT is the
    exact inverse of the decode rate the table already shows and inherits the
    engine-reported measurement when the server sends one.
  - `_Bench.add_run` writes `on` / `off` in the first column; the full route
    name (`mtp on`, `mtp off`) stays in the notes, where it reads as a sentence.
  - `_bench_plain_lines` builds the table for the line-oriented client from the
    same headers and cells, right-aligning every column after the first two, so
    both clients print the same table.
  - Theme: `hip.metric.prefill` / `.prompt` / `.decode` / `.ttft` / `.tpot`
    color the metric columns, `hip.hit` (mint) and `hip.miss` (coral) color the
    cache outcome, and `/usage`'s `cached` row now uses `hip.hit` so a cached
    count reads the same in both places. Rich columns use `justify="right"`;
    plain columns use `rjust`.
- `tests/test_unit_chat_cli.py`: the rich bench case now asserts the header line,
  the `on/on/off/off` switch column, per-column values, and that every row's
  numeric cells end at the header's column ends (right alignment). The plain
  case asserts the same table. New `_plain_bench_text` helper replaces the
  inlined `run(...)` calls, and a TPOT case covers the client-timing fallback
  (24 tokens over one decode second is 23 inter-token gaps, 43.5 ms each) and
  the no-reply `—`.

## Validation

- `tests/test_unit_chat_cli.py`: 30 passed, 0 skipped. `rich` and
  `prompt_toolkit` were missing from `.venv`, so the rich-mode cases had been
  skipping in this worktree; installing the `chat` extra
  (`uv pip install --python .venv/bin/python "rich>=13" "prompt_toolkit>=3.0"`)
  made them run for the first time here. They pass unchanged.
- `python3 scripts/check_test_tiers.py`: 0 issues.
- Live, `qwen3.8-27b` on `hip_gfx1151`, through the real rich client and the real
  plain client against the running server (`/bench 512 32`), MTP on then off,
  cold then cached: `prefill tok/s` 271 / 24 / 297 / 31, `prompt tok/s` 271 /
  960 / 297 / 1,163, `decode tok/s` 26.3 / 27.7 / 10.8 / 11.6, `ttft s` 1.94 /
  0.55 / 1.77 / 0.45, `tpot ms` 38.1 / 36.1 / 92.6 / 85.9. Both clients printed
  the identical table.
- Table width is 74 columns, down from 114 with per-cell units, so it renders
  without truncation on an 80-column terminal. Verified by rendering at width 80.
- Observed, not investigated: the first MTP-on request of a fresh server process
  ran far slower than its cached repeat on every metric (`8.27s` ttft, `64 tok/s`
  prefill, `11.2 tok/s` decode) and improved across successive benches in the
  same process (`3.71s` / `142` / `11.2`, then `1.94s` / `271` / `26.3`). This is
  client-side sanity output, not a benchmark row; the effect is consistent with
  one-time MTP warmup and was not measured as such.
