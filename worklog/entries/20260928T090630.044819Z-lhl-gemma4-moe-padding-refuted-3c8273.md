# the moe row padding skips its own arithmetic so the smaller tile fix is withdrawn and the geometry does not reconcile

## Summary

`20260928T084954` read `grid=(5632, 8, 1)` on a 1-token decode and concluded the
gate_up MMQ "computes 32 rows per expert where 1 is real -- a 32x arithmetic
overrun on 24.5 percent of decode", worth 7 to 15 percent, with a smaller row
tile as the fix.

**The kernel already skips that arithmetic.** `gguf_q4_k_q8_1_selected_prefill.hip:1314`:

```cuda
for (int wsic = 0; wsic < WNITER; ++wsic) {
    if (wsic * 4 + tiwc >= valid_rows) continue;
    ...  dp4a ...
}
```

`valid_rows` is `expert_count - tile_row_in_expert` clamped to `MMQ_N`, so for
an expert with one real row 31 of 32 rows take the `continue` and issue no
dot products. **The row padding costs no arithmetic, a smaller row tile would
not recover anything, and the 7-to-15-percent projection is withdrawn.**

What the block still pays is the weight tile load, the activation tile load and
the `__syncthreads()` **once per K-block**, unconditionally. So the gate_up's
73 GB/s is not an arithmetic property at all.

## The geometry does not reconcile

The launcher sets `grid.x = out_features_total / 32`
(`gguf_q4_k_q8_1_selected_prefill.hip:4990`, inside
`launch_selected_dual_q8_1_ds4_mmq32_compact32`). The trace's 5632 therefore
requires `out_features_total = 180,224 = 128 x 2 x 704`, and 704 is gemma4's
`expert_feed_forward_length`, so the launcher is receiving the **full fused
tensor width** rather than one expert's.

But `gemma4_experts.py:1212` passes `intermediate` for both `out_features_a`
and `out_features_b`, and `scratch.intermediate` sizes the gate_up output as
`lanes * 2 * intermediate` (`:335`), which is only sensible at 704 -- at
90,112 the 512-token scratch would want 1.5 GB. Both cannot hold.

**So either the caller's `intermediate` is 90,112 and the scratch sizing is
128x over-provisioned, or the trace is from a different call site.** The
per-expert stride compounds it: `expert_stride_rows = out_features_a +
out_features_b` under `FUSED_EXPERT_LAYOUT`, so an expert's base is
`expert_id * 180,224` rows, which runs off the end of a 180,224-row tensor for
every expert but the first. **That is not a claim, it is the thing to resolve**,
and it needs the fused tensor's actual shape from the artifact rather than more
reading.

I am recording the contradiction rather than picking the branch that fits the
story I started with.

## Why this matters for the fix

`20260928T084954`'s next step was to template the MMQ body on a smaller row
tile. **That is now the wrong change** and it is not worth the multi-file edit
it would need. The gate_up is at 73 GB/s while skipping 31 of 32 rows'
arithmetic, so the cost is the per-K-block tile loads and barrier on a grid
whose real work is 44 column tiles by 8 row tiles. **The lever is more
parallelism over the weight stream -- a narrower column tile or a split-K --
not a narrower row tile.**
