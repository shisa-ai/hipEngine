# Surya HTTP serving verified against a loaded checkpoint: LLM did not forward the generator's vision declarations

## Summary

The serving unit (`20260912T102908.898036Z-lhl-surya-http-serving-49e812`) was
qualified against a fake generator and said so. Serving a real 300-DPI A4 page
through `hipserver` found **two defects that a fake could not**, and the path now
reproduces the direct call exactly.

**1. `LLM` did not forward the generator's vision declarations.** The serving
front end holds an `LLM`, but `vision_max_pixels` / `vision_media_input` /
`vision_prompt_marker` / `vision_default_prompt` live on the generator it wraps.
`LLM` exposed `supports_vision` and nothing else, so the server read `None`
off the engine, kept its 1 MP / 1024 px Qwen4Exp default, and rejected every real
A4 page with `unsupported PNG geometry`. `supports_vision=True` was true the
whole time, which is why the capability check passed and the failure looked like
a bound problem.

`LLM` now forwards them. The forwarding **raises `AttributeError`** for an
undeclared attribute rather than returning `None`, so `getattr(engine, name,
default)` in a caller still sees the absence: Qwen4Exp declares no vision bounds
and must keep the caller's default (including its inline `<|vision_start|>...`
prompt marker), while Surya declares them and must override it. A property that
returned `None` would have silently stripped Qwen4Exp's marker.

The test file now wraps every fake in a real `LLM` via `_engine(...)`, so the
whole file exercises the boundary that was broken, and three cases pin the
delegation directly: forwarded, absent-when-undeclared, and absent-before-load.

**2. The server's `usage.prompt_tokens` could not be computed for Surya.**
`chat_completions` called `engine.count_tokens(prompt)`, which raises
`NotImplementedError` for a generator without a tokenizer count. That is not
merely a crash: a vision prompt is text *plus* image tokens (8701 for this page —
121 text and 8580 image), so a text tokenizer count cannot produce the right
number anyway.

`GenerationOutput` gains an optional `prompt_tokens`, and the Surya generators
report `len(input_ids)` from the prompt they actually built. The server prefers
it and falls back to the tokenizer for the text-only generators that report
nothing. The A4 request reports `prompt_tokens` 8701, which is the real prompt.

## Changes

- `hipengine/llm.py` — `_generator_vision_declaration` plus
  `vision_max_pixels`, `vision_media_input`, `vision_prompt_marker`,
  `vision_video_prompt_marker`, `vision_default_prompt` properties.
- `hipengine/generation/registry.py` — `GenerationOutput.prompt_tokens`
  (optional, non-negative, validated in `__post_init__`).
- `hipengine/generation/surya.py`, `hipengine/generation/surya_gpu.py` —
  `_generate_ocr` returns the prompt length; the output reports it.
- `hipengine/server/api.py` — prefer the reported prompt length.
- `tests/test_surya_server_multimodal.py` — fakes wrapped in a real `LLM`;
  three new delegation cases; 19 tests total.
- `scripts/surya_http_e2e.py` — new; serves one page through `TestClient`,
  scores it with the direct-call scorer, and asserts equality against the
  committed direct-call artifact.

That is equality, not similarity: the script compares `completion_tokens` and ten
score fields (`finish_reason`, `n_blocks`, `n_candidate_lines`,
`lines_expected`, `lines_found`, `line_recall`, `line_exact_rate`, `cer`,
`reading_order_violations`, `table_cells_matched`, `table_cell_accuracy`)
against the committed direct-call row and fails on any difference. The HTTP wall
is 119.9 s against the direct call's 114.3 s; the delta is server overhead and
the first-request path, not a different computation.

## Next

- The `LLM` vision properties are read off `self._text_generator` without
  forcing a load, matching `supports_vision`. A caller that reads a declaration
  before the generator exists gets the absent case, which is the safe direction,
  and the server resolves the engine first when a request carries media. Worth
  revisiting only if a caller ever needs the declaration pre-load.
- `prompt_tokens` is now available on every generator output but only Surya sets
  it. The text-only generators could set it too, which would remove the
  tokenizer-count fallback in the server.
