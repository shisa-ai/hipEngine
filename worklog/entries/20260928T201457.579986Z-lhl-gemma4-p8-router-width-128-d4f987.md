# Gemma 4 P8: router thread width 128, retile refuted, one claim corrected

## Summary

P8 moved twice more. The expert x token retile that iteration 9 was scoped
around was built and **lost at every thread width**, so that direction is
closed. What beat it was a sweep the retile prompted: on the token tile that
already shipped, **thread width is the lever and it is non-monotone** — 0.0927
ms at 64 threads, **0.0666 at 128**, 0.0943 at 256, 0.1546 at 512. The route
now sets 128 instead of the binding's 256 default. End to end
`moe.router_gemm` goes **13.4 -> 5.2 ms at 1024 and 53.2 -> 20.5 ms at 4096
from the pre-P8 baseline, down 61%**, prefill busy falls to 469.4 / 3418.8 ms
and prefill rises to 2040.9 (+1.03%) and 1165.0 (+0.72%), with decode at
43.80 / 40.17 — unchanged or slightly up. The gate passed again at the new
arithmetic. This entry also corrects a false claim in
`20260928T195306.004780Z-lhl-gemma4-p8-router-logits-variant-be9163.md`.

## Findings

**The retile hypothesis is refuted.** One block owning four experts over
sixteen tokens, at `threads=64`, carries ~2816 MACs per thread against the
token tile's ~179 — the exact shape the 1.67 TFLOP/s reading said we were
short of. It still lost:

| threads | token_tile_16 | expert_tile_4x16 |
| --- | ---: | ---: |
| 64 | 0.0927 | 0.1070 |
| 128 | **0.0680** | 0.1333 |
| 256 | 0.0993 | 0.2091 |
| 512 | 0.1546 | fail (hipError) |

Cutting thread count by 16x did not help, so thread launch and scheduling
overhead were never the binding constraint. Weight traffic is identical
either way (blocks x one expert row = 46 MB per launch regardless of tiling),
and the hidden re-read the tile was meant to amortise was already being
served from cache. The direction is closed.

**Width is the actual lever, and it is not monotone.** On the token tile
already shipped, with grid and tile fixed, width sets only the K stride
(`blockDim.x * 8`) and the reduction shape:

| threads | 1st pass | steady | TFLOP/s |
| --- | ---: | ---: | ---: |
| 64 | 0.0927 | 0.0927 | 3.98 |
| 128 | 0.0938 | **0.0666** | **5.43** |
| 256 | 0.0991 | 0.0943 | 3.72 |
| 512 | 0.1546 | 0.1546 | 2.39 |

At 64 the blocks starve; at 128 every thread still owns a full K slice (all
128 sit inside the 352 vectors hidden 2816 needs) while carrying 2.75 vector
steps instead of 1.4; at 256 the threads go thin; at 512 a third have no K
range at all. The first pass at 128 is slower than its steady state, so a
single sample would have missed the win — three warmed passes caught it.

## Arithmetic

Neither the shipped route nor the width change is bit-identical to what it
replaces. Width 128 against width 256 differs on logits by up to
3.814697265625e-06, because `blockDim.x` sets both the K stride and the
reduction tree. Drift against a float64 reference is 3.815e-06 at width 128
and 2.384e-06 at 256 — the same order, so width 128 trades a little accuracy
for a 1.42x time win.

`scripts/gemma4_teacher_forced_gate.py gate` at the new arithmetic:
**passed**, 1023 rows, top-1 rate 1.0, **0 flips**, `kl_mean` 9.736646e-06
(bar 1e-3), `kl_p95` 2.120546e-05 (bar 5e-3), `kl_p99` 1.100531e-04 (bar
2e-2), `kl_max` 3.785709e-03 (bar 5e-2), 41.3 s.

## Correction

The earlier entry
`20260928T195306.004780Z-lhl-gemma4-p8-router-logits-variant-be9163.md`
states: *"`observed_routes`: `router_gemm=gemma4_router_topk_bf16@gpu0` — the
changed path ran"*. **That is false.** The gate's `observed_routes` carries
only attention and decode fields — `decode_launches`, `head_dims`,
`selections`, `split_key_range`, `split_launches` — and is byte-identical
between the two gate runs. No artifact anywhere in `benchmarks/results/`
contains `gemma4_router_topk_bf16@gpu`. The claim was written from memory,
not from the artifact.

What actually shows the router path ran is the **family census**: the delta
lands in `moe.router_gemm` and in nothing else (every other family moved
under 2 ms, inside the day's spread). The gate's real contribution is the KL
and top-1 numbers above, which are correct and which this entry reproduces.
The earlier entry is immutable and stands as written; this paragraph is the
correction. The same false claim is repeated in the iteration-9 record in the
multiloop results file, which is also not editable; treat it as corrected by
this entry.
