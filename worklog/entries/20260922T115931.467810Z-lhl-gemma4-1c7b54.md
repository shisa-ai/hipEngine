# Gemma 4 gfx1100 kernel family: plain-weight norms and the rotary table layout

## Summary

Starts the Gemma 4 serving path with the kernel family it needs. Four primitives
the hip_gfx1100 tree did not have are added and checked against the CPU
reference, and one primitive I expected to have to write turns out to be
unnecessary.

The reason the norm family is separate rather than a variant of the Qwen3.5 one
is a real hazard, not a style choice: HuggingFace's `Gemma4RMSNorm` computes
`normed * weight` while `qwen35_rmsnorm_kernel` computes `normed * (1 + weight)`.
Reusing it would add one to every weight in the model.

## Changes

- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_norm.hip` and `gemma4_norm.py`:
  plain-weight RMSNorm (f32 and bf16 rows), weightless RMSNorm, per-head RMSNorm
  with an optional weight, the router pre-scale, `(residual + rmsnorm(x)) *
  layer_scalar`, per-expert routing-weight scaling, and the dense/expert branch
  add. Registered as six layer keys under variant `gemma4_plain` for the quant
  keys `gguf_q4_k_m`, `gguf_q4_k_xl`, `gguf_q8_0`, and `gguf`.
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_rope.py`: builds the rotary table
  in the layout `qwen35_partial_rotary_kernel` indexes. It reuses the CPU
  reference's frequency math and only doubles the half-width table.
- `tests/test_unit_gemma4_gpu_kernels.py`: 19 tests. The rotary-layout tests
  need no GPU; the kernel tests carry the repository's HIP-availability guard.

## Validation

No new rotary kernel is needed. `qwen35_partial_rotary_kernel` rotates pairs
`(i, i + rotary_dim // 2)` and reads `cos[dim]` by element index, so calling it
with `rotary_dim = head_dim` and HuggingFace's doubled table
(`emb = cat(freqs, freqs)`) reproduces Gemma 4's rotation exactly. The rotated
elements are not a contiguous prefix — they are `[0, rope_angles)` together with
`[head_dim // 2, head_dim // 2 + rope_angles)` — so a table truncated to
`rope_angles` would be wrong. Tests assert the doubled table plus the kernel's
formula equals HF's `rotate_half` for both layer kinds (sliding 256/10000 and
global 512/1000000 with 64 of 256 pairs rotated), that the proportional tail
carries cos 1 and sin 0, and that the rotation preserves the pair norm.

Kernels against `hipengine/kernels/cpu_reference/gemma4.py`, 19 tests passing:

| Kernel | Check |
| --- | --- |
| `gemma4_rmsnorm_f32w_f32` | exact f32 agreement, plus a negative check that the `1 + weight` form is rejected |
| `gemma4_rmsnorm_f32w_bf16` | bf16 agreement, plus the same negative check |
| `gemma4_rmsnorm_weightless_bf16` | matches the reference with no weight |
| `gemma4_head_rmsnorm_f32w_bf16` | matches a per-head reference; null weight is weightless |
| `gemma4_router_prescale_bf16` | matches the reference router input; dropping either scalar is detected |
| `gemma4_add_rmsnorm_scale_bf16` | applies the real layer scalar; null scalar skips it |
| `gemma4_expert_weight_scale_f32` | the scale lands on the selected slot's own expert |
| `gemma4_branch_add_bf16` | sums the two branches |

One trap worth recording. `resolve` falls back from the exact key to the same
key with an empty variant, then to the fp16 quant, then to the `cpu_reference`
backend. Because Gemma 4 and Qwen3.5 disagree on the norm weight convention, a
fallback hit is a silent correctness bug rather than a missing kernel. A test
records that an unpinned or misspelled variant does not reach the Gemma 4 kernel,
which is why the runner must pass `variant="gemma4_plain"` on every norm call.
