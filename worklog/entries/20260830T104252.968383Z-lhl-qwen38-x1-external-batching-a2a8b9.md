# X1 external MTP verification-batching survey

## Summary

Executed punchlist item X1 of the Qwen3.8 gfx1151 scaling campaign: a
read-only survey of what the verification batch dimension actually is in the
surveyed external engines, to test diagnosis A2's premise that our width-4
sequential-subgroup decomposition is unusual. Produced
`docs/EXTERNAL-MTP-BATCHING.md` with a comparison table (batch dimension,
per-cycle model passes, width caps), cited by file and commit. No vendoring,
no code port, no performance claim.

## Changes

- New `docs/EXTERNAL-MTP-BATCHING.md`: seven engines surveyed — llama.cpp

  pins laurent `c28d538d`, nathan `0eb52805`, q38rocm `5d097740` (engine fork

- Checked off X1 in `docs/QWEN38-GFX1151-SCALING-CAMPAIGN.md`.

## Findings

- **All seven engines flatten verification across requests.** Each in-flight
  request contributes `draft_i + 1` rows to **one** target decode (llama.cpp
  `handle_last_sampled_token` shared-batch path; vLLM
  `_calc_spec_decode_metadata` / `uniform_decode_query_len = 1 +
  num_spec_tokens`; SGLang flattened-tree `run_eagle_verify` "Batch 1:
  Target verify"). None issues sequential complete proposal+verify cycles per
  small request group. A2's shape has no external analogue.
- **Caps are token budgets, not widths.** `n_batch` (default 2048; server
  batch `max(n_batch, n_parallel)`; `add()` refuses past cap),
  `max_num_batched_tokens`, `max_num_seqs`/`n_parallel`/`max_running_requests`
  — shared with non-speculative decode. No fixed per-cycle request width of 4
  anywhere.
- **Draft passes are batched too.** llama.cpp drafts all drafting slots per
  step in one draft-ctx decode (`speculative.cpp:282-370`); vLLM
  (`llm_base_proposer.py:690`) and SGLang (`eagle_worker_v2.py:510,529`)
  draft the whole batch each step. Passes per cycle is
  `draft_steps + 1 target` for the whole batch, not `× groups` — our
  per-subgroup loop pays proposal cost once per subgroup.
- Implication for M1: single wide verify group over all due requests is the
  standard shape; bounding by rows (C8×D24+8 ≈ 200 rows < 2048-token budget)
  is what the capability-owned bound should express.
