# UD-U1 F3: concrete backend consumer qualification

## Summary

Closes the F3 finding of the UD-U1 independent review (docs/UD-QUANTS.md U1
round 6) on CPU only: admission coverage now binds every positive certificate
to a concrete backend that actually registers GGUF consumers and to concrete
four-axis consumer contracts that mirror the real runtime dispatch surface,
and the lm-head dtype coverage now matches the ACTUAL operation-caller dtype
instead of a convenient kernel input. F1 (native dependency enforcement wired
into loader/entry defaults) remains open and untouched.

F3 gaps closed:

1. Backend binding. `_KNOWN_HARDWARE_BACKEND_KEYS` (any HIP/CUDA arch name)
   no longer suffices for a positive certificate: each hardware backend
   package now declares `GGUF_CONSUMER_LAYERS` as a source literal
   (hip_gfx1100/hip_gfx1151 declare the full certified surface; cuda_sm120a
   declares `frozenset()` after a real inventory — its scaffold registers
   moonshine/maple/PARO families but zero `gguf_*`
   linear/embedding/dense/router/GDN/selected-expert consumers, so nothing
   existing breaks). Admission reads the declarations with a bounded AST
   literal reader (audit capability-reader convention; handles annotated and
   plain assignments; missing/nonliteral reads as "none" and fails closed).
   A slot whose certified consumer layer is undeclared is refused
   `consumer_unqualified` with the missing layer named, aggregated before any
   allocation.
2. Concrete consumers. New CPU-safe module
   `hipengine/loading/qwen35_gguf_consumer_surface.py` mirrors
   `runtime/gguf_linear._DISPATCH_TABLE` row-for-row (layout, activation,
   output, layer, quant token, variant, ABI) plus the `_variant_for_rows`
   multirow rewrite (Q4-T16 special case included) and the raw-layout
   per-source quant resolution. Certified records are generated FROM that
   surface: concrete layer/quant/variant everywhere (rows=1 and rows>1
   variants), per-source-type raw records, concrete norm/GDN/conv/router/
   embedding/moe-selected keys. The placeholder forms are gone: no
   `<from-weight>`/None quant/variant records, and the never-registered
   `moe_selected`/`gdn_chain` layer names are replaced by the real
   `moe_linear`/`gdn_recurrent_rmsnorm_gate` registrations. One documented
   exception: raw rank-3 Q4_K selected experts are consumed by the direct
   `gguf_q4_k_gemv:gguf_q4_k_selected_gemv_bf16_bf16_out` module wrapper the
   runtime actually calls (not registry-mediated today); the record names the
   module symbol, the parity test proves it exists, and the registry gap is
   filed in docs/REFACTOR.md.
3. Dtype repro (the F3 counterexample). The default coverage records now
   mirror the actual production callers: BF16 activations without an input
   override. A dense-F32 lm-head has NO default `lm_head_f32_logits` record —
   `runtime/gguf_linear._DISPATCH_TABLE` has no `(dense_f32, bf16, f32)` row
   (the runner's `logits_from_hidden_bits`/native-rows/packed-verify callers
   all pass BF16 `scratch.norm`/hidden) — so preflight refuses `root.lm_head`
   with a reason naming the missing dispatch row, before any allocation
   (loader-level zero-allocator sentinel proven). The registered
   F32-activation route (`dense_gemv/f32/f32_hidden_f32_out`) remains
   certifiable when the caller declares
   `preflight_qwen35_gguf_artifact(..., f32_input_operations=(lm_head_f32_logits,))`:
   the declaration is validated fail-closed (must name requested known
   operations), admits only layouts that actually have an F32-activation row
   (Q4 pack8 stays on its BF16 record, exactly the runtime's per-slot
   fallback), and is recorded on `Qwen35GGUFPlanContract.f32_input_operations`
   so certificates never transfer across activation contracts. The loader
   (`materialize_qwen35_gguf_weights`) forwards the parameter; wiring the
   native head's F32-input dependency into loader/entry DEFAULTS is the open
   F1 unit and is explicitly not claimed here (the F32 head is refused, not
   silently treated as inapplicable).
