# C2 packed decode 4.7x: enable native_batch_decode_session for the exact dense_rowtile decode kernel

## Summary

Qwen3.8-27B-Q4_K_M packed decode had no near-linear scaling (c1 33.5 ms/step but
c2 173 ms, c4 192 ms, ~5x c1 with only ~14 ms between c2 and c4). Root cause: the
packed decode step `_enqueue_packed_decode_model_step` was missing
`native_batch_decode_session`, so the exact `dense_rowtile` t16 decode kernel was
skipped and the large Q4_K projections fell back to the slow `t16_wmma_prefill` GEMM
(~120 ms/step for the FFN alone). Adding `native_batch_decode_session(2 <= rows <= 4)`
to the packed decode step selects the exact dense_rowtile decode kernel (it reads the
existing `tiles`). Result: c2 **174 ms -> 36.7 ms/step (4.7x)**; c1/c2/c4 aggregate
**29.69 / 52.41 / 91.00 tok/s** (c2 1.77x, c4 3.07x c1, near-linear);
**c1_c2_c4_prefix_exact = True** (batch-composition invariant, not gamed). A one-line
fix in `hipengine/runtime/qwen35_gguf_runner.py`. (An earlier in-session checkpoint
hypothesized the Q4_K pack8 rowtile GEMV was the bottleneck; that was incorrect and is
superseded here — the model is t16, and the pack8 GEMV is never on its live path.)

## Changes

`hipengine/runtime/qwen35_gguf_runner.py`: in `Qwen35GGUFResidentSession._enqueue_packed_decode_model_step`,
added `native_batch_decode_session(2 <= rows <= 4)` as the first scope in the `with (...)`
block, matching the sibling `_enqueue_native_rows_model` (which already had it). This
selects the exact small-row native projection families (the `dense_rowtile` t16 decode
kernel) for the packed c2/c4 decode instead of the `t16_wmma_prefill` prefill GEMM.

Diagnosis (measured, gfx1100 W7900, /models/gguf/Qwen3.8-27B-Q4_K_M.gguf):

1. Initial hypothesis (Q4_K pack8 GEMV bandwidth) was WRONG. Built a high-bandwidth
   pack8 rowtile GEMV (128-thread one-sweep; 1.4-1.6x faster in isolation) and wired it
   into `_pack8_rowtile_dispatch`, but the full-model c2/c4 numbers did NOT move; tracing
   confirmed the packed decode never calls the pack8 rowtile GEMV. That experiment was
   reverted (see Next).
2. The 27B dense decode weights are `gguf_q4_k_t16_v1` (t16, not pack8). A resolved-variant
   trace on `launch_gguf_linear` showed the large projections resolve to
   `t16_wmma_prefill_bf16_bf16_out` (a WMMA GEMM / prefill kernel), not a decode GEMV.
3. Microbenchmark on the real FFN tiles (scripts/tmp_t16_wmma_bench.py, 64 dense layers,
   gate/up 5120x17408 x2 + down 17408x5120 x1 per step): t16_wmma_prefill gate/up 0.410 ms,
   down 1.063 ms (rows=2) -> 120.5 ms/step (~70% of the 173 ms step), ~130-150 GB/s
   effective (3-4x below a 500 GB/s GEMV); `down` (out=5120) is 2.6x slower than `gate/up`
   (out=17408) at identical element count -> parallelism-limited. rows=2 ~= rows=4
   (weights amortized, not a per-row sweep).
4. The fast exact decode kernel `dense_rowtile_bf16_bf16_out` IS registered for
   `gguf_q4_k_t16_v1` and reads the SAME existing `tiles` allocation: gate/up 0.080 ms,
   down 0.086 ms (rows=2) -> 15.7 ms/step, **7.68x faster** than wmma_prefill for the FFN.
5. The rowtile sidecar decode path in `launch_gguf_linear` is gated on
   `_native_batch_decode_session_enabled` (rows 2-4, not use_wmma); the packed decode step
   was missing that scope, so the exact dense_rowtile decode was skipped.

## Validation

Full c1,c2,c4 packet (prompt 256, decode-steps 48, warmup 1, measured 2, gfx1100 W7900;
artifact `benchmarks/results/2026-08-19-concurrency2-qwen38-27b-packed-decode-rowtile-accepted.json`,
source /tmp/hb-c124-fix.json):
- **c1_c2_c4_prefix_exact = True** -> c2/c4 trajectories are prefix-exact to the independent
  c1 oracle (batch-composition invariance preserved; NOT gamed). dense_rowtile is exact.
- Scaling (aggregate decode tok/s): c1 = 29.69, c2 = 52.41 (**1.77x c1**), c4 = 91.00
  (**3.07x c1**). Before the fix c2 = 11.48 (0.38x c1), c4 ~12 (0.4x c1).
- All configs passed=True, repeatable=True. c2 step 174 ms -> 36.7 ms.
- Quick c2 (prompt 64, decode-steps 2) trajectory identical pre/post fix (row0
  [9707,9707,9707], row1 [264,6669,2020]) -> arithmetically exact.
- Legacy pack8 rowtile suite: 39 passed (no segfault) after the highbw revert below.
- native_c8 (rows=8) unchanged: rowtile sidecar is rows 2-4 only; rows 8 hits a pre-existing
  `qmicro planar rowtile requires rows in [2,4]` (task #11, still pending). The fix is scoped
  to rows 2-4 so it does not change the rows>=5 path.
