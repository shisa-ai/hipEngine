# the MMQ32 kernel executes 176 barriers per block against 5632 dp4a per thread

## Summary

`20260928T204000` proposed that the K staging depth is the prefill's remaining 1.36x and
`20260928T210000` found the edit spans a shared struct. This entry reads the kernel's inner
loop and **quantifies the mechanism**, which turns the structural comparison into an
arithmetic one:

**For the gate/up projection, `in_features = 2816` and `MMQ_K = 32` give 88 iterations per
block, each carrying two `__syncthreads()` -- 176 barriers per block.** The compute in the
same block is **64 dp4a per thread per iteration, 5632 per thread total**.

| barrier cost on a 4-warp block | 176 barriers | against |
| ---: | ---: | ---: |
| 20 cycles | 3520 cycles | 5632 dp4a per thread |
| 35 cycles | 6160 cycles | 5632 dp4a per thread |
| 50 cycles | 8800 cycles | 5632 dp4a per thread |

**At any plausible barrier cost the synchronisation is the same order as the entire dot-product
workload.** At llama.cpp's staging depth of 256 the same arithmetic needs 11 iterations and
**22 barriers.**

## And the traffic is not the problem

The inner loop reads a *different* slice each iteration -- `subblock = k32 & 7` walks the
eight subblocks of a Q4_K superblock, and `ds4_idx = k32 & 3` walks the four 32-element
groups inside a `block_q8_1_mmq_ds4`. **Neither re-reads the same bytes.**

So the eight-times-finer staging costs **no extra traffic**, which rules out the
amplification story: the earlier L2 fetch amplification (66.6 GB against a 13.2 GB weight
set) is not this, and the mechanism here is purely **loop and barrier count**. That matters
because it means the fix is a restructuring of the staging loop, not a change to the data
layout.

## The natural target is 128, not 64

`ds4_idx = k32 & 3` exists because the activation is stored in **ds4** form -- a
`block_q8_1_mmq_ds4` holds **four** 32-element groups, so the activation's natural
granularity is **128 K elements**. At `MMQ_K = 128` the block index advances once per
iteration and `ds4_idx` is always zero; at 64 it advances every second iteration.

**128 is therefore the setting that matches the layout the activation is already in**, and it
takes the barrier count from 176 to 44.

## Why the edit was not made

**This is the third consecutive entry to scope the same change rather than make it**, and the
reason is worth stating plainly: the edit restructures the staging loop, the subblock
indexing, the ds4 indexing and the compute's accumulation together, and it fails as a wrong
answer rather than a compile error. **The quantified case above is what was missing from the
first two scoping entries** -- it says the mechanism is real and worth the edit -- but the
edit is a careful one and has not been started.

**What this entry does provide is that the next unit is now unambiguous**: change
`MMQ_K` to 128 in one kernel, widen its staging to hold four subblocks, and index
`ds4_idx` as a constant zero. The correctness gate is route parity with the strict owner,
which the other MMQ variants already use.
