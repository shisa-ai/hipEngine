# T16 gate/up leaf: hoist the K-loop bookkeeping, bit-identical, prefill +7.0%

## Summary

The T16 gate/up WMMA leaf recomputed, once per (sub-block, k-tile, 16-column half), a weight tile
pointer, an activation row-validity predicate, a column-validity predicate and a nibble shift
amount, and branched on the last two. All four are loop invariants or removable, and removing them
is worth **prefill 1064.2 -> 1139.1 tok/s at 512/128 (+7.0%)**, decode 28.314 -> 28.697 tok/s, and
a public wall of 4.9306 -> 4.6510 s, all measured in one session with only this one file differing.
The output is **bit-identical**: 0 of 5,767,168 bf16 output bits differ from the parent revision.

The static body goes **6114 -> 3983 instructions, 191.1 -> 124.5 per WMMA, 1.535x fewer**, and the
wall clock improves 1.294x on the standalone fixture and 1.200x in situ. That gap is the substantive
finding of this unit and it corrects the previous verdict: **this leaf is not issue-bound** in the
sense `20260928T233806.520482Z-lhl-gemma4-t16-gate-up-dram-bound-0619de.md` claimed. What it is
bound by is the latency of its sixteen per-lane scalar byte loads per weight fragment, and the
compiler's ability to keep those in flight is worth more than any instruction-count reduction.

## What changed

`hipengine/kernels/hip_gfx1100/quant/gguf_q4_k_t16_selected_prefill.hip`, production kernel only.

1. **The column-validity predicate is gone.** `valid_col` decided whether a lane's columns were in
   range. Every out-of-range column is discarded by the store loop's own range test, so an
   out-of-range half is redirected to the first half's tile instead and no stored value can observe
   the difference. `out_tile < out_tiles` implies `local_col < local_out_features` because
   `out_features_a` and `out_features_b` are both multiples of `T16_COLS`, which
   `valid_selected_dual_t16_common` already requires.
2. **The nibble is taken with a loop-invariant shift.** `(col & 1) ? (packed >> 4) : (packed &
   0x0Fu)` and `(packed >> (4 * (col & 1))) & 0x0Fu` are the same function of `packed` and `col`;
   the second form hoists the shift out of the unrolled loop and drops a select per value. Measured
   alone, this is 1.155x on the fixture.
3. **Both 16-column halves run in one K loop over one activation fragment load.** The parent placed
   `tm` outside the K loop and reloaded the identical activation fragment for each half. Each
   accumulator still sees the same sequence of WMMA operations over the same operands, so the
   accumulation order is unchanged.
4. **The remaining invariants are hoisted**: the tile pointer, the activation row index, its
   validity test and the nibble shift, all of which depend only on values fixed before the K loop.

No flag, no alternate symbol and no dispatch route was added. The kernel was rewritten in place, so
the change is on the default path by construction.

## Why 1.535x fewer instructions is only 1.200x in situ

Four measurements, each isolating one thing:

- **The compiler's load schedule is worth 2.2x.** The same candidate source built with a
  16-blocks-per-CU launch-bounds floor asks for 61 VGPRs instead of 175 and runs **10.49 ms against
  4.76 ms**. At 61 VGPRs the sixteen per-lane byte loads of a weight fragment serialize behind an
  `s_waitcnt` each; at 175 the compiler batches them. Occupancy is not the binding constraint —
  the low-occupancy build is the fast one.
- **A row-paired geometry with 2.35x fewer static instructions per WMMA is slower.** Two 16-row
  tiles per block, one decode serving 32 output rows: 232 instructions per pair of WMMAs against
  the candidate's 249 for the same two. Best case **1.203x** at a 4-to-6 block launch-bounds floor
  and **0.61x to 0.66x** at every other floor tried (1, 2, 3, 8, 10, 12). Not landed.
- **Packing byte pairs into one VGPR to halve the load registers is slower too.** Bit-identical,
  best case 1.23x, and more sensitive to the floor. Not landed.
- **The removed instructions were the cheap ones.** Removing 34.9% of the static body buys 22.5% of
  the fixture's wall time.

So the lever on this leaf is **memory operations, not instructions**. The sixteen scalar byte loads
per fragment per lane, each touching a distinct 32-byte sector, are what the register-hungry
schedule is hiding. The decode-in-LDS staging the prior unit proposed is the concrete form of the
next attempt, and the prior unit's demand model applies to it unchanged: it would cut global memory
operations per fragment from sixteen to one, at the cost of LDS traffic and one barrier per K block.

## A defect this unit introduced and then fixed

The first revision hardcoded `Q4_T16_BLOCK_BYTES` as the per-block tile stride. That is the
non-qmicro layout constant, so the `qmicro` instantiation of the same template walked its tiles at
the wrong stride. `test_sh2_m4_q4_qmicro_wmma_matches_t16_production_bytes` caught it — 7168 of 7168
elements wrong — and the stride is now selected by the `qmicro` template argument.

**The standalone fixture did not catch it**, and that is the reusable part: `scripts/gemma4_t16_leaf_ab.py`
exercises only the non-qmicro route, so it reported 0 of 5,767,168 bits differing while a sibling
instantiation of the same kernel was completely wrong. The test file's byte-equality contracts
between the production, qmicro and shared_x routes are what caught it, which is what they are for.
