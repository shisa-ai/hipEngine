# Materialize the MLP shard through the incumbent path and check it on device

## Summary

Reviewer step 1 of the MLP packet is done: the MLP slots are materialized through
the **incumbent** path on device, the resident tiles read back from the card equal
the host repack of the same source payload byte for byte, and each rank's shard is
a verified sub-range of that resident weight on the axis its split moves. Seven
questions now answer yes; none of them claims kernel execution.

## Changes

`scripts/tp2_mlp_shard_plan_probe.py` gains an opt-in `--device` stage
(`device_stage()`) and two further questions. It calls
`materialize_qwen35_gguf_weights(..., selected_slots=['layers.0.ffn_gate', ...],
device=Device('hip', 0))`, reads each slot's `tiles` allocation back with
`copy_device_to_host`, and compares it against the host repack of the same GGUF
payload. The allocation is freed in `finally`.

| Slot | Layout | Device bytes | Host repack | Match | Rank slices |
| --- | --- | ---: | ---: | --- | --- |
| `ffn_gate` | `gguf_q4_k_t16_v1` | 51,527,680 | 51,527,680 | yes | `out_tiles[0:544]`, `[544:1088]` |
| `ffn_up` | `gguf_q4_k_t16_v1` | 51,527,680 | 51,527,680 | yes | `out_tiles[0:544]`, `[544:1088]` |
| `ffn_down` | `gguf_q6_k_t16_qmicro_planar_v1` | 73,113,600 | 73,113,600 | yes | `blocks[0:34]`, `[34:68]` |

The two new questions:
`device_resident_bytes_match_the_host_repack` and
`rank_shard_is_a_sub_range_of_the_resident_weight`.

**Why this is worth having even though it is not execution.** Without it, a shard
could be constructed correctly in isolation and still not be a slice of the weight
the TP1 path actually runs: the host probe validates a construction, this validates
that the construction agrees with the incumbent resident layout. A mismatch here
would mean every segment time measured on the shard describes a different tensor
from the one TP1 uses, which is the failure the previous probe's guessed layout
would have produced.

**What it still does not establish**, and the artifact says so: no kernel has been
launched. Reading bytes back from an allocation does not show that a GEMV accepts
the shard shape or that its output is correct. Two tests pin that - the scope
string must state the probe does not qualify device execution, and no question name
may mention a kernel or execution.

## Next

Reviewer steps 2-5 remain, and they are the ones that qualify execution:

1. Execute gate/up -> activation -> down on both ranks through the resolved
   incumbent variants, and validate the partials against an independent CPU split
   oracle (not against the TP1 output alone - the oracle is what catches a shard
   that is self-consistently wrong).
2. Connect the partials through the native exchange into the residual/next
   consumer; add the residual once and verify the resulting boundary against TP1.
3. Resolve the down projection's actual output dtype first, then pick the
   reduction option explicitly (fp32 partials versus bf16 partials converted and
   summed in f32); conversion does not recover precision lost at each partial's
   rounding, and it costs time the halved payload does not pay for.
4. Measure complete TP1 and TP2 segment walls on both cards including conversions,
   ordering and communication, with `segment saving = matched TP1 segment wall -
   measured TP2 segment wall`.
5. Sweep the actual MLP quant/layout geometries before choosing MLP-only or full
   TP. The 16 full-attention and 48 GDN blocks differ in what a shard must
   replicate, so this is a per-block-class decision.
