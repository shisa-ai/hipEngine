# W7900: my rollup rewrite broke a published artifact's own repro command

## Summary

Thirty minutes after committing the rollup rewrite, `benchmarks/results/2026-08-30-...-prefill-
row-grouped.json` still named a command that no longer ran: its `source_command` ends in
`--prior-config-changed`, which my rewrite had deleted, so the headline grouped prefill row
(+14.1% to +176.0%) had a repro recipe that exits with `unrecognized arguments`. The rewrite
also quietly swapped the repeatability statistic from a **max per-width spread** to an
aggregate delta, which is the wrong statistic for a band - two packets can match to 0.1% on the
aggregate while one width moves 0.4%. Both restored, plus tests over the CLI and the guards.

## Changes

- `scripts/gguf_prefill_row_rollup.py`: `--prior-config-changed` restored with its original
  semantics - the per-width delta is an **effect size**, the same-protocol drift band does not
  apply, and it returns 0. It prints the per-width deltas and warns when the protocol hash or
  model also differ, so only a declared configuration delta may be cited.
- `spread()` added and wired into the drift line, so the repeatability statistic the artifact
  stores is the one the tool prints. The aggregate is still printed beside it, never instead.
- `tests/test_scripts_gguf_prefill_row_rollup.py`: nine tests over synthetic packets pinning
  the row definition (prompt-admission throughput, not completion tokens), refusal of a wave
  that admitted fewer lanes than requested, refusal of cells with no rate or prompt count,
  max-per-width-spread-over-aggregate, two-sided drift only with an `ok` prior, default warning
  versus `--strict-prior` refusal, effect-size mode, model-mismatch refusal, and empty packet
  as an error rather than a 0.0 row.

## Validation

- The grouped row's recorded command runs again and reproduces the artifact's gain table
  exactly: **+0.1 / +14.1 / +37.6 / +107.4 / +103.0 / +125.1 / +176.0 / +156.9** against
  `gain_pct_vs_control` `{0.12, 14.07, 37.65, 107.41, 102.96, 125.13, 176.02, 156.94}`, labelled
  "effect size, not drift".
- The off row's published repeatability reproduces: **0.41% max per-width**. My aggregate-only
  version printed 0.10% and would have passed the ~1% band while hiding the moving width.
- The promotion artifact is self-standing, and my earlier "the grouped packet is gone" alarm was
  a path I had invented in conversation: it cites `source_packet=/tmp/he-c1c8-cap8/c1c8-cap8.json`
  and `prior_packet=/tmp/he-c1c8-k3/c1c8-k3-packet.json`, both of which exist, and their own
  `summary[width].ar.tok_s` reproduces the published AR row within 0.02-0.29% (after C8 78.521
  vs 78.667, before C8 45.657 vs 45.684). No committed claim depends on a file I made up.
- Control hygiene, checked rather than assumed: the grouped row's control is the `complete`
  packet (`he-d1v3`, `route_expectation_passed` true at every width), so the +176% is two-sided;
  only the separate 0.41% drift claim rests on the `failed` prior, and that is caveated.
- `pytest tests/test_scripts_gguf_prefill_row_rollup.py -q`: 9 passed.

## Next

- Standing rule for tools whose invocation is recorded in a committed artifact: cover the CLI in
  a test, or a refactor will eventually make the artifact's own command unrunnable. That holds
  for this rollup now and is the pattern to copy for `gguf_engine_submodule_decomposition.py`.
- Raw packets under `/tmp` remain ephemeral; the compact artifact plus the committed rollup is
  the retained evidence, and a fresh packet costs about seven minutes if one is ever needed.
