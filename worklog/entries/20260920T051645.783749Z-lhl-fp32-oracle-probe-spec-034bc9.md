# Item 3 instrumented: the high-precision chunkwise/WY oracle and the conv reference are in-tree, with the exact inputs each needs

## Summary

The accuracy check does not need a new oracle and does not need a whole-model
fp32 run. `hipengine/kernels/cpu_reference/ops.py` already holds the three
references the first diverging component needs, including one the source itself
calls the **high-precision** oracle. What is missing is only the capture of the
per-layer inputs, which are layer-local and small.

Note the path: the CPU reference lives at `hipengine/kernels/cpu_reference/`,
not `kernels/cpu_reference/` as `AGENTS.md` states.

## Changes

- None. Source reconnaissance.

## Validation

References, with signatures read from source:

- `linear_attn_conv_prefill_segments(hidden_states, conv_state, conv_weight,
  cu_seqlens, state_indices) -> (out, state)` at line 1912 -- the convolution
  reference. `hidden_states` is packed `[T_total, channels]`; `conv_state` is a
  mutable-state snapshot shaped `[state_slots, channels, kernel_size]`.
- `gdn_prefill_recurrent_segments(query, key, value, beta, decay,
  recurrent_state, cu_seqlens, state_indices)` at line 1967 -- the recurrent GDN
  prefill reference over packed prompt rows.
- `gdn_prefill_chunkwise_wy_segments(query, key, value, beta, decay,
  recurrent_state, cu_seqlens, state_indices, *, chunk_size=8)` at line 2015 --
  documented as the "High-precision chunkwise/WY oracle for packed GDN prefill
  segments".

The probe this specifies, in order:

1. Capture, for layer 0 and layer 1 on the same 1,024-token prefix, the per-layer
   GDN inputs from both routes: `query`, `key`, `value`, `beta`, `decay`, the
   `recurrent_state` entering the layer, the conv `hidden_states` and
   `conv_weight`, and the initial `conv_state`. These are the exact arguments the
   three references take, and they are layer-local rather than model-wide.
2. Run `linear_attn_conv_prefill_segments` on the captured conv inputs. If both
   routes produce the same conv output and state from the *same* captured input
   rows, the convolution is exonerated and the difference is upstream in the qkv
   values, as the previous entry deduced.
3. Run both GDN references on the captured q/k/v/beta/decay. Whichever route's
   recurrent state matches `gdn_prefill_chunkwise_wy_segments` more closely is
   the more accurate contraction order, and whether the other route matches
   `gdn_prefill_recurrent_segments` identifies which algorithm each route
   implements.

This is the direct answer to "which side is closer to fp32" that the whole-model
comparison cannot give: the packed route and the single-session route differ in
~127 of 128 state components, so the question is which of the two contraction
orders is closer to the high-precision oracle, and that is decidable per layer on
the CPU.

`tests/fixtures/cpu_reference` exists alongside these references, so the probe can
follow the established fixture convention rather than inventing one.
