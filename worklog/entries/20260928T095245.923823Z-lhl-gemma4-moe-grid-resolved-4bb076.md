# the moe gate up receives 704 twice so it runs 352 blocks and is under parallel not over

## Summary

`20260928T095039` left a factor-of-128 contradiction between the grid the decode
trace shows and the grid the call site appears to pass, with three candidate
explanations. **Two are now eliminated by direct measurement, and the answer
reverses that entry's conclusion about the fix.**

**The caller is exactly what it looked like: `intermediate = 704`.** So the launcher
builds `grid.x = (704 + 704) / 32 = 44`, and the gate/up runs **44 x 8 = 352
blocks**, not 45,056. The "3 bytes per thread / 45,056 blocks / per-block setup
dominates" reading in my previous entry **is wrong and is withdrawn.**

## What was measured

Intercepted the route function on a live runner rather than reading the call site:

```
MMQ gate/up received: {'intermediate': 704, 'compact_rows': 8,
                       'num_experts': 128, 'in_features': 2816}
grid.x = 2*intermediate/32 = 44
```

Both Python wrappers on the path are **plain passthroughs**, so nothing rescales on
the way to the FFI call:

- `gguf_q4_k_selected_dual_q8_1_ds4_mmq32_fused_prefill_compact32_bf16_bf16_out`
  forwards `out_features_a`, `out_features_b` unchanged and only swaps `_symbol`.
- `gguf_q4_k_selected_dual_q8_1_ds4_mmq32_prefill_compact32_bf16_bf16_out` calls
  `_check_mmq32_common(...)` and then passes the same values to ctypes.

And the C launcher is unambiguous, the only definition of its name:

```cuda
const int64_t out_features_total = out_features_a + out_features_b;
const int64_t row_tiles = mmq_total_rows / 32;
const dim3 grid(out_features_total / 32, row_tiles);
```

**So candidate 1 (wrapper reorders or scales) and candidate 3 (different dispatch)
are out.** `intermediate = 704` is the per-expert half width that
`runtime/gemma4.py:297` sets from `gguf.expert_feed_forward_length`, and it is also
the offset used for the up-half pointer, which is only correct at that value.

## What remains unresolved, and it is narrow

The trace still reports `grid=5632x8` for
`gguf_q4_k_selected_dual_q8_1_ds4_mmq32_fused_prefill_compact32_kernelILi1EEE`,
and `5632 = 128 x 44`. **The factor of 128 is `num_experts`.**

That leaves candidate 2 in a specific form: **`rocprofv3`'s `grid_size_x` column is
not the launch's x dimension as I assumed.** The same suspicion applies to the other
rows of that table, and one of them checks it: the MoE down projection reports
`grid=2816x128` where `hidden_size = 2816`, i.e. also the full feature width rather
than a feature width divided by a tile. Two kernels with different tile widths both
reporting a full feature extent in the x column is more consistent with the column
meaning something else -- total workgroups, or a product -- than with two
independent 128x and 32x miscalculations in the launchers.

**I am not asserting that; it is the one remaining reading and it needs one check of
the profiler's column semantics before anything is built on it.** What is settled is
that the launchers pass 704 and compute 44.

## Why the fix changes direction

At 352 blocks of 128 threads on 40 CUs, the gate/up has **8.8 blocks per CU** for a
1-token decode. That is thin -- too little concurrency to hide the weight-stream
latency, which is the opposite of the "45,056 blocks, 99 percent idle" picture my
previous entry drew.

**So the lever is more parallelism, not less**, which is what `20260928T090630`
concluded from the kernel body and what this now supports from the launch geometry
instead of contradicting: a narrower column tile or a split-K multiplies the block
count. A narrower *row* tile does not, which is why that entry withdrew it.

The per-thread work also refutes the setup-domination story directly: 352 blocks x
128 threads = 45,056 threads for 8 rows x 1408 columns x 2816 K, which is about
**704 MACs per thread**. Each thread has real work to do; it just does not have
enough neighbours in flight.
