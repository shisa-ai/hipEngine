# the MMQ expert path moves 995 GB of read traffic for a 0.69 s prefill, and the counter's absolute unit is not resolved

## Summary

The scalar census named the expert gate/up MMQ32 kernel as the prefill's largest
scalar consumer. This asks the same question of read traffic, and the answer is the
same kernel, by a wider margin.

`rocprofv3 --pmc FETCH_SIZE` on `scripts/gemma4_campaign_bench.py --prompt 512`
(the verify metric's shape), summed over every dispatch:

| kernel | FETCH_SIZE | dispatches | per dispatch |
| --- | ---: | ---: | ---: |
| `gguf_q4_k_selected_dual_q8_1_ds4_mmq32_fused_prefill_compact32_kernel` | 604,234 MB | 7,424 | 81.39 MB |
| `q5_1_mmq_ds4_selected_prefill_kernel` | 391,387 MB | 7,424 | 52.72 MB |
| `gemma4_attention_prefill_kernel` | 6,565 MB | 60 | 109.41 MB |

The expert weights are 272 MB (128 experts x 1408 out x 2816 K x 0.5625 B) and the
Q5_1 down weights are of the same order, so **the two MMQ expert kernels move about
995 GB of read traffic to produce a 0.69 s prefill from roughly 500 MB of
weights** -- while the attention kernel, which is the kernel the tree has spent the
most effort on, moves 6.6 GB.

Whatever the amplification is attributed to, the split is not close, and it lands on
the same kernel the scalar census did. Both instruments agree that the expert MMQ32
gate/up kernel is where the prefill's inefficiency is concentrated, and that the
attention work recorded earlier in this branch was aimed at the smaller term.

### The absolute unit is not resolved, and the entry above's framing inherits the problem

Converting these counts to a rate does not give a DRAM number. 604,234 MB over the
kernel's 180.08 ms of measured time is **3.36 TB/s**, which is well above what this
part's memory can deliver, so `FETCH_SIZE` is not counting DRAM fills in production
however its derived-counter description reads. The attention kernel gives 109.41 MB
per dispatch against a few MB of unique K/V at that shape, which is the same story
from the other direction: this is cache-level read traffic, not memory traffic.

That matters for the earlier entry, which computed an "implied DRAM rate" of 320 GB/s
for the raw layout and 122 GB/s for T16 from the same counter and built a
"DRAM-bound on a weight-layout overfetch" conclusion on it. Those two figures are
internally consistent with each other, and the T16-versus-raw *comparison* stands on
its own -- 5.218 ms against 5.911 ms, non-overlapping ranges, one session, one host.
What does not stand is the label: at production geometry the same counter reads
10 times faster than the microbench's "DRAM rate", so the traffic being measured is
cache traffic and the earlier entry's DRAM framing should be read as cache framing.

No rate is quoted from these numbers here, and none should be quoted from them until
the unit is pinned. **The ratios are usable**: they are counter-to-counter within one
run, so any constant factor cancels.

## Next

- **Both instruments now point at the same kernel, so the next unit is the expert
  gate/up MMQ32 kernel's read traffic.** The T16 body is measured 1.13x faster on the
  identical launch, its kernel-side fused-stride work is already done -- the T16
  branch in `gguf_q4_k_q8_1_selected_prefill.hip` already computes `out_tiles` and
  `tile_base` under `FUSED_EXPERT_LAYOUT` -- and production still selects the raw
  symbol. What is missing is the load-time `repack_gguf_q4_k_tile16`, whose wall time
  has to be measured before it is accepted: this model's expert tensors are 8.5 GB
  and a previously deleted layout cost 116.6 s of load time.
- **Pin the `FETCH_SIZE` unit first, because it decides whether the repack is worth
  it.** A repack that fixes a cache-traffic problem and a repack that fixes a
  DRAM-traffic problem have different ceilings. One launch of a kernel whose traffic
  is computable from its own source is enough, and it is the same shape of check the
  scalar census still needs for its own constant.
- Do not re-open WMMA for the expert gate/up at this geometry. It is measured slower
  under both weight layouts.
