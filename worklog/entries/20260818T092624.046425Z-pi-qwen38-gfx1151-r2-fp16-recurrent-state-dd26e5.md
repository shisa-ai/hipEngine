# R2: fp16 recurrent state quality tradeoff (host-side emulation)

## Summary

Executed R2 from `docs/QWEN38-27B-GFX1151-CAMPAIGN.md` Section 12: measured
the quality tradeoff of fp16 vs bf16 recurrent-state storage on real Qwen3.8
GDN layer-0 boundary arrays. Because the state is `float*` in every GDN device
kernel (fp16_lowp variants change only the output dtype), a full device change
would span the entire ~40-kernel GDN family; the host-side emulation answers
the quality question first without touching device code. Result: fp16 state is
quality-neutral (drift ~0.05x the device's own already-accepted bf16 output
rounding), bf16 state is catastrophic (~539x), confirming the external repo's
explicit fp16-not-bf16 choice. Decode-traffic framing: the GDN gate kernel is
1.43% of decode wall, so fp16 state is worth roughly 0.5-0.7% decode at c=1 on
gfx1151; the external's real win (concurrency via 150MB/request state) does
not apply to our c=1 target.

## Changes

- Captured real Qwen3.8-27B Q4_K_S gfx1151 GDN layer-0 boundary arrays
  (conv_out, linear_z, ssm_alpha, ssm_beta, recurrent_out, recurrent_bf16) for
  a 64-position window (positions 0-63) of a concatenated natural corpus
  prompt via `scripts/gguf_linear_boundary_capture.py`, and a 16-position
  window (positions 0-15) of the default greeting prompt.
- Built a faithful host-side GDN recurrence replay (mirroring
  `scripts/gguf_gdn_replay_compare.py::replay_gdn`, real layer-0
  `ssm_norm`/`ssm_dt_bias`/`ssm_a` weights, eps=1e-6) with the recurrent state
  stored in fp32 (reference), fp16 (round-trip each step), and bf16, all
  accumulating in fp32.
- Measurements over the 64-position window:
  - fp16-state recurrent-output drift vs fp32-state: max_abs 4.69e-4, rms 4.72e-6.
  - bf16-state recurrent-output drift vs fp32-state: max_abs 2.51, rms 5.50e-2.
  - Device's own already-accepted bf16 output rounding (captured
    `recurrent_out` vs `recurrent_bf16`): max_abs 7.76e-3, rms 1.02e-4.
  - fp16 drift is 0.05x the accepted output rounding; bf16 drift is 539x.
- Decode-traffic framing from the retained post-qmicro decode profile
  (`benchmarks/results/2026-08-16-gfx1151-qwen38-27b-post-qmicro-decode-profile.json`):
  GDN recurrent gate family = 1.43% of selected kernel wall (1.12ms/token of
  78.5ms). Halving state traffic via fp16 state therefore bounds decode gain
  near 0.5-0.7% at c=1 on gfx1151.

## Validation

- Replay uses the same math and helpers as the committed GDN replay compare
  harness and is validated by matching the fp32-state output to the device's
  captured fp32 recurrent output within expected drift (device bf16 rounding
  is the only difference).
- Capture is real device output: `scripts/gguf_linear_boundary_capture.py`
  against `/models/gguf/Qwen3.8-27B-Q4_K_S.gguf`, backend hip_gfx1151,
  compiler version `/tmp/qwen38-task22-q5-dense-tile8-integration/hipcc-version.txt`
  (HIP 7.15.0 / clang 23.0.0git, AMD Radeon 8060S).
- Raw artifacts: `/tmp/qwen38-r1/r2-qwen38-gdn-layer0-pos0-15.json`,
  `/tmp/qwen38-r1/r2-qwen38-gdn-layer0-pos0-63.json`.

## Result / decision

- fp16 recurrent state is quality-neutral at the layer-0 recurrence level
  (drift ~0.05x the device's accepted bf16 output rounding, bounded over 64
  positions). bf16 state is rejected (drift 539x).
- Decode value at c=1 on gfx1151 is small (~0.5-0.7% ceiling) because the GDN
  gate kernel is only 1.43% of decode wall. The external repo's material win
  was concurrency (state halves 150MB/request), which is outside our current
  c=1 scope.
- Decision: do NOT invest in the full multi-kernel fp16-state device change for
  the c=1 campaign. If a concurrency/multi-request target is adopted later,
  the fp16-state change is quality-plausible and should be revisited then,
  still gated on the full natural-suite KL/top-1 profile. Registered FP32 state
  remains the strict default.
