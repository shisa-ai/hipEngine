# Gemma 4 attention split rejected by teacher-forced gate (G4)

## Summary

The multi-block decode-attention split (G4's measured 62%-share candidate) is
correct and fast but **fails the binding teacher-forced gate**, so it is
reverted from the worktree and recorded as a rejected candidate.

- **Candidate:** `gemma4_attention.hip` decode launcher partitions the key
  range into up to 16 independent slices at keys > 256 (slice kernel +
  sync-free combine over retained workspace); keys <= 256 keeps the exact
  single-kernel path untouched.
- **Perf (measured, microbench, 3 stable runs):** decode symbol 0.102 ms vs
  0.263 ms baseline at the campaign attention shape — **2.6x faster**.
- **Correctness (measured):** f32 parity vs the parent kernel bounded at
  worst rel 1.14e-4 / abs 1.4e-6 across keys 257..4096 (reassociation band);
  92/92 attention suite tests green including a 256/257 boundary pair and an
  exported slice-policy contract.
- **Gate (measured, binding):** mean 8.56e-4 (bar 1e-3) PASS, p95 2.14e-4
  (5e-3) PASS, p99 0.011 (0.02) PASS, top-1 0.999 (0.99) PASS, but
  **kl_max 0.3036 vs bar 0.05 FAIL** at rows 272/278/288/291 (1 top-1 flip).
- **Control (measured):** policy forced to S=1 (parent path byte-for-byte)
  reproduces the frozen baseline **bit-identically, KL = 0.0** — all gate
  divergence is attributable to the split arithmetic.

## Mechanism (why the gate fails)

Instrumented capture (30,690 decode calls, 30 layers/step) pinned the model's
real attention configs: **(heads=16, kv=8, head_dim=256)** and
**(heads=16, kv=2, head_dim=512)**, scale 1.0, dense mask, keys = row + 1
(split engages exactly at row 256). At these configs the split's f32 noise
(~1e-4) is small but **does cross bf16 output rounding boundaries**: direct
parity shows occasional **1-ulp bf16 flips** (e.g. hd=256 keys=257,
hd=512 keys=292). Each flip enters the residual stream and the bf16 KV cache
and amplifies chaotically across 30 layers x 1023 rows; a few rows burst to
nats-scale logit shifts and blow the kl_max bar while mean/p95/p99 stay
inside. Because any nonzero f32 difference can land near a bf16 midpoint,
**bit-exactness is arithmetically unattainable while the reduction is
re-grouped** — the candidate cannot pass the production table as designed.
A future attempt must make the split's f32 outputs match the parent's more
closely (e.g. weights shifted by the global row max via a pre-pass, so exp()
arguments match the parent exactly) and re-run this same gate; the bars are
not adjustable.

Slice-count bisection (dynamic vs fixed S=2) left the verdict essentially
unchanged (same 4 rows, kl_max 0.3036 to 4 digits) — the failure is driven by
the exp-shift/grouping difference common to any split, not by slice count.
