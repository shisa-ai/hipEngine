# Muse Glimmer decode fusion/grouping/compact assessment (task #19)

## Summary

The decode GEMV is at 98% of the measured 211 GB/s read ceiling (task #15), so
fusion/grouping cannot buy bandwidth. The recoverable candidates are bounded:
the T16 +2.78% resident-byte expansion (compact layout), narrow-K/V grouping,
and the in-step logits softcap. Each is small relative to the +10% gap.

## Changes

- None (assessment only).

## Validation

- Compact layout: T16 Q4 block 2368 B vs raw GGUF 2304 B per 4096 weights
  (+2.78%). Storing raw bytes would recover ~2.78% decode but the WMMA prefill
  decode relies on the T16 rearrangement; a raw layout would slow prefill
  decode-of-weight. Net likely negative; deferred.
- Grouping Q/K/V/gate (shared normed input): the input re-read is ~13 KB/token
  (tiny); narrow K/V (256 cols) is 52 GB/s but only ~19 us each. Concatenation
  improves fill marginally; absolute gain small.
- GPU softcap fusion: the CPU scale+tanh in decode_step is ~0.08 ms/step
  (task #11 measurement); moving it on-device saves little. The ~6.5% host/gap
  share is dominated by the synchronized step boundary, not the softcap.
