# the K staging is 32 and it is the only MMQ dimension with no variant in the tree

## Summary

`20260928T202000` compared hipEngine's MMQ32 kernel against llama.cpp's RDNA3.5 Q4_K
configuration and cited `weight_tile[32]` as the K staging. **That citation was wrong**:
`weight_tile` is indexed by the output-feature tile coordinate
(`weight_tile[tiwr * TM + cr]`), so the 32 is `MMQ_M`, the tile-I. **The conclusion survives
-- the K staging is eight times smaller -- but it rests on a different constant, and this
entry corrects the evidence.**

**The kernel's actual constants:**

```cpp
constexpr int MMQ_N = 32;    // token tile (llama.cpp's J)
constexpr int MMQ_K = 32;    // K staged per pass
constexpr int THREADS = 128;
constexpr int MMQ_M = 32;    // output-feature tile (llama.cpp's I)
const int k32_iters = static_cast<int>(in_features / MMQ_K);
for (int k32 = 0; k32 < k32_iters; ++k32) {
    const int weight_block = k32 >> 3;
    const int subblock = k32 & 7;
```

A second kernel in the same file uses `MMQ_M = 64, MMQ_K = 32`.

## The comparison, corrected

| dimension | hipEngine | llama.cpp RDNA3.5 Q4_K |
| --- | --- | --- |
| `I` output features | **32**, and a 64 variant | 64 to 128 |
| `J` tokens | 32 | 16 to 128 |
| **`K` staged per pass** | **32** | **256** |
| threads | 128 | 128 or 256 |
| occupancy target | 2 | 2 |

**`I` already has a 32 and a 64 variant, and `J` was swept. `K` is 32 in every kernel in the
tree and has no variant anywhere.** That is the untested dimension, and it is the one where
llama.cpp differs by the largest factor.

## The mechanism, precisely

`weight_block = k32 >> 3` and `subblock = k32 & 7` mean a Q4_K superblock -- 256 K elements,
eight subblocks of 32 -- is spanned by **eight consecutive `k32` iterations**. The superblock's
scale and min are therefore re-read on each of those eight passes rather than once.

**More importantly, the loop itself runs eight times as often for the same arithmetic.**
Per iteration the block stages 32 columns x 32 K = 1024 elements across 128 threads, so each
thread moves 8 elements, and the loop overhead -- index arithmetic, the column validity test,
the activation staging, the barrier before the compute -- is paid `in_features / 32` times
instead of `in_features / 256`.

**Whether that loop overhead is the 1.36x is not established.** It is a plausible mechanism
with a measured structural difference behind it, and it is the first such candidate after
route, tile, occupancy, bandwidth, launch, gap and packing were all closed.

## Why the correction matters

The previous entry's conclusion was right and its reasoning was one array off. **Recording
the correction rather than letting it stand matters because the wrong citation points at the
wrong edit**: someone acting on `weight_tile[32]` would resize the output-feature tile, which
has already been swept, instead of `MMQ_K`, which has not.

## Next

  arithmetic -- measured on the existing expert microbenchmark. This is the experiment the
  previous entry proposed and it is unchanged by the correction; only the constant to edit
  is different.
- **`MMQ_K` must divide the Q4_K superblock, 256, and `in_features` is 2816 and 704 in the
  two expert projections.** 64 and 128 both divide 256; 704 is 11 x 64 and 2816 is 22 x 128,
  so both are admissible for the gate/up and down shapes. The `k32 & 7` subblock indexing
  becomes `k64 & 3` and `k128 & 1` at those settings and needs to move with the constant.
