# Report the real device kind and the real device identity

## Summary

Repairs review findings R7 (P2) and R11 (P2), committed together because both
live in the same interleaved region of `hipengine/core/hip.py`. Both are cases
where the device-identity layer reported something that was not true: a CUDA
buffer labelled as HIP, and a device UUID that matched no other tool on the
host. Neither was caught by the existing tests, which covered the formatter but
not the field it reads.

R11 turned out to be larger than a truncation bug. The fix is two-part: read all
16 bytes, then interpret them honestly. This also corrected three artifacts this
branch had already published.

## R7 - buffers are attributed by the runtime's own kind

`core/memory.py:_runtime_device()` hardcoded `Device("hip", ...)` for any runtime
exposing `get_device()`, and `DeviceBuffer` refused any label whose kind was not
`hip`. `CudaRuntime` exposes `get_device()` and allocates through these same
helpers, so every CUDA buffer was labelled `hip:N`, and the correct CUDA label
was rejected as well.

- `HipRuntime.device_kind = "hip"` and `CudaRuntime.device_kind = "cuda"`.
- `_runtime_device()` reads `device_kind`; a runtime that declares none stays
  unattributed rather than guessed, so an unknown runtime cannot be mislabelled.
- The explicit-device allocation path labels from the same runtime kind.
- `DeviceBuffer` now rejects only a host (`cpu`) device, which is the real
  invariant: a host device cannot own a device pointer.
- `_device_index()` accepts any device kind instead of demanding `hip`.

The test that asserted `DeviceBuffer` rejects a CUDA label encoded this defect
and was rewritten; `FakeDeviceRuntime` in the ownership tests now declares
`device_kind = "hip"` because it stands in for a HIP runtime.

## R11 - the UUID is the runtime's identity text, not hex to re-encode

`device_get_uuid_bytes()` read `bytes(uuid.bytes)` from a `c_char * 16` field, so
an embedded NUL truncated the value. The reviewer's repro (a device whose unique
ID starts with a zero byte) returned length zero and `device_get_uuid()` raised.

Reading exactly 16 bytes then exposed the deeper defect: ROCm fills `hipUUID`
with the device's **ASCII** unique ID. Measured on this host:

```
HIP 0  AMD Radeon Pro W7900   pci=0000:0d:00.0  raw=b'e282895b62c2b295'
HIP 1  AMD Radeon RX 7900 XTX pci=0000:10:00.0  raw=b'cc4d02090dc9c3ff'
sysfs card1 (0000:0d:00.0) unique_id = e282895b62c2b295
sysfs card0 (0000:10:00.0) unique_id = cc4d02090dc9c3ff
```

The old formatter hex-encoded those ASCII characters and returned
`65323832-3839-3562-3632-633262323935` for HIP 0 - a UUID-shaped value that
matches no other tool, while the rest of this repository's artifacts record
`GPU-e282895b62c2b295` from `rocm-smi`. Name, PCI bus ID, and UUID now agree per
device, which also rules out the device-order mismatch this reviewer flagged
separately for `collect_devices()`.

- `HipUuid.bytes` is now `c_ubyte * 16`, and the reader uses
  `ctypes.string_at(..., 16)`: exactly 16 bytes, NUL-independent.
- New `decode_hip_uuid()`: printable text is returned as text (NUL padding
  dropped), otherwise canonical 8-4-4-4-12 hex, so a binary CUDA-compat UUID
  still formats correctly.
- `device_info()` keeps `uuid_hex` as the lossless raw field and now reports
  `uuid` through `decode_hip_uuid()`.

## Changes

- `hipengine/core/memory.py`, `hipengine/core/hip.py`, `hipengine/core/cuda.py`.
- `tests/test_unit_core_device_ownership.py`: nine new tests, one rewritten.

## Validation

- RED before the fix: `Device(kind='hip') == Device(kind='cuda')` failed; the
  UUID tests reported `len(b'') == 0` and `hipUUID must contain exactly 16 bytes`.
- GREEN after: `tests/test_unit_core_device_ownership.py`, 28 passed.
- GPU-tier files that allocate through the shared helpers
  (`test_gpu_memory_stats.py`, `test_gpu_moonshine_cuda_sm120a_runtime.py`):
  36 passed, 10 skipped.
- Full unit tier during this work: 9068 passed, 22 skipped, 0 failed, exit 0.
- Real-device read-back cross-checked against sysfs `unique_id` for both cards,
  as quoted above.

## Consequences

- `benchmarks/results/tp2_collective_bench.json`, `tp2_graph_capture_probe.json`,
  and `tp2_host_inventory.json` record the old double-encoded UUID. They are
  regenerated by the in-flight R3/R4 work rather than hand-edited.
- `device_get_uuid()` returns the runtime's identity text on ROCm. Any consumer
  parsing it as a canonical 8-4-4-4-12 UUID must read `uuid_hex` instead.
