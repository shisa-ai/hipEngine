# the two expert routes disagree and each is internally row-count-consistent

## Summary

`20260928T055238` found `gemma4_experts_forward_bf16` to be the block-width
divergence and left the row accounting as the suspected cause. It is not the row
accounting. The caller passes `lanes = tokens * top_k` correctly, and every
kernel in the chain is parameterized by it.

**The divergence is a route crossover.** `gemma4_moe_prefill_route_enabled`
selects between two arithmetic families:

```python
return int(lanes) >= _PREFILL_MIN_LANES_PER_EXPERT * int(num_experts)
```

with `_PREFILL_MIN_LANES_PER_EXPERT = 1`. For the fixture's `num_experts=4`,
`top_k=2`:

| rows | lanes | route |
| --- | --- | --- |
| 1 | 2 | per-lane selected GEMV (`2 < 4`) |
| 2 | 4 | row-reusing prefill route (`4 >= 4`) |
| 3 | 6 | row-reusing prefill route |
| 4 | 8 | row-reusing prefill route |

That predicts the sweep exactly: rows=2, 3 and 4 give the *identical* difference
against rows=1 -- `rel=0.01814481, max_abs=8192.0` in all three -- which is a
two-route split and not a padding or tiling artifact, since a tile effect would
vary with the row count.

## Forcing each route names the defect precisely

| configuration | rows=1 against rows=2 | max absolute |
| --- | --- | --- |
| as shipped | **0.01814481** | **8192.0** |
| prefill route forced ON for every row count | **0.00000000** | **0.0** |
| prefill route forced OFF for every row count | **0.00000000** | **0.0** |

Each route is internally consistent across row counts, to bit-equality. The two
routes disagree with each other by 1.8 percent, with a spurious term of
magnitude 8192.

The docstring presents the crossover as a **performance** choice -- *"below it
most experts are empty, so a grouped launch's per-expert grid would spend its
blocks on nothing and the per-lane GEMV grid is cheaper"* -- so the two are
supposed to be arithmetically equivalent. They are not. One of them has an
arithmetic bug, and which one is not yet established.

## What this explains

Everything in the chain, now at its root:

- the expert forward diverging at rows=2 against rows=1
  (`20260928T055238`),
- the layer diverging by 0.8 and 0.4 percent with a random pre-layer input
  (`20260928T055057`),
- the model diverging at layer 0 by 0.63 percent (`20260928T055010`),
- and `test_incremental_decode_matches_a_dense_prefill`, which compares a dense
  prefill against one-token-at-a-time decode and therefore compares the
  row-reusing route against the per-lane GEMV.

It also explains why `HIPENGINE_GEMMA4_MOE_GATE_UP_MMQ=0` does not fix that test:
that flag gates the *MMQ* route, while this crossover is
`gemma4_moe_prefill_route_enabled`, a different gate on a different family.

## Why it matters

**It is a correctness defect, not an arithmetic difference.** A spurious
term of magnitude 8192 in an expert sum is a wrong answer. One of the two routes
is wrong for every input it handles, which means either all prefill blocks or
all decode steps have been computing the wrong expert FFN -- and the two
disagree, so at least one of them is.

**The fix is to make the routes agree, not to remove the crossover.** The
crossover is a legitimate performance choice and the docstring's reasoning for
it is sound; what is missing is the arithmetic equivalence it assumes.

## Changes

None. This unit is a measurement.

## Validation

- Probe on the 8060S (gfx1151) calling `gemma4_experts_forward_bf16` directly at
  rows 1 through 4 with a fixed routing shared byte-for-byte across calls, and
  again with `_PREFILL_MIN_LANES_PER_EXPERT` patched to 0 and to 1e9 to force
  each route for every row count. Exit 0.
- The route prediction (`lanes >= num_experts`) is read from the function that
  implements it, not inferred from the results.
- The 2, 3, 4 sweep agreeing to the last digit is what distinguishes a route
  crossover from a tile or padding effect.

## Next

Establish which route is correct, then fix the other. The cheapest oracle is
the CPU reference for the expert FFN if one covers this shape; otherwise
`gemma4_project_experts_rows` and the selected-GEMV leaf can each be compared
against a hand-computed expert sum for one lane on one expert, which is small
enough to do in numpy. A `docs/REFACTOR.md` entry is warranted either way: this
crossover currently has no arithmetic-equivalence test, and adding one is what
would have caught it.
