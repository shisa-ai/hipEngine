# Device-side sampled MTP accept kernel validated against the host law oracle

## Summary

A sampled MTP row can now take its accept decision from device logits without a
full-vocabulary readback. The new `sampled_accept` kernel pair reduces each
verified row's processed logits to the two scalars its softmax needs and walks
the drafted chain with the request's own counter-based sampler stream, emitting
the same seven-field accept/commit payload the argmax chain emits. The kernel's
decision and its induced law match the host oracle exactly on the same logits
and the same draws.

This is the first acceptance item of task #19. The kernel is **not yet wired
into the N2 target graph**, so the sampled serving route still runs its host
accept and the sampled-mode evidence guard stays closed. The serving
re-measurement (item b) is still open.

## Why this is the enabling piece

`hipengine/generation/mtp_sampled_accept.py` defines the sampled accept on the
host: accept the drafted token `x` with `min(1, p(x)/q(x))` and, on rejection,
draw from `normalize(max(0, p - q))`. The serving route could not use the target
graph because the graph commits the argmax accept on device; a sampled row ran
`allow_graph=False` and paid one full-vocabulary logits row per verified prefix
on the host. The measured cost of that detour was 0.47x of an in-load AR control
at c=1 temperature 0.7, with a sampled cycle costing 5.3x the identical greedy
cycle.

## Changes

- `hipengine/kernels/hip_gfx1100/speculative/sampled_accept.hip`:
  - `sampled_accept_row_stats_kernel` — per-row block reduction over the
    processed logits producing `(row_max, row_inv_sum)`, the two scalars a
    row's softmax needs;
  - `sampled_accept_chain_i32_kernel` — one request per thread walking the
    drafted chain: `alpha = p(x)` from the row statistics, accept when
    `u < alpha`, otherwise draw from the residual `p` with `x` removed,
    renormalized (the scan threshold is `u * (1 - alpha)`, which is the host's
    renormalize-then-search in one pass), and on a fully accepted chain draw the
    bonus from `p`. Emits the same payload as
    `dflash_accept_chain_i32_native_cycle`: `accepted_counts`, `commit_rows`,
    `commit_tokens`, `commit_positions`, `next_tokens`, `full_accept`,
    `committed_output_ids/lengths`, `packed_payload[7]`, `visible_output_*`, and
    the resident cursor.
- Draws come from the same counter-based stream the native row sampler uses
  (`splitmix64(seed ^ (row+1)·C1 ^ (step+1)·C2 ^ (slot+1)·C3)`), so a sampled
  decision is reproducible from the row's seed and step index: slot 0 is the
  acceptance test, slot 1 the residual or bonus sample, in the host oracle's
  draw order.
- `hipengine/generation/mtp_sampled_accept.py::sampled_accept_uniform` — the
  host mirror of that stream, so a host replay reconstructs the device's draws.
- `hipengine/kernels/hip_gfx1100/speculative/sampled_accept.py` — raw-pointer
  wrappers, build plan, and registration under
  `(sampled_accept_chain, <session quant>, native_v1_i32)` and
  `(sampled_accept_row_stats, f32, rows)`; exported from the backend package.
- `tests/test_gpu_sampled_accept_chain.py` — four GPU tests.

## Validation

`source /tmp/hipenv.sh` (therock SDK root + `hipcc` on PATH), then:

```
pytest tests/test_gpu_sampled_accept_chain.py tests/test_unit_mtp_sampled_accept.py \
       tests/test_unit_mtp_sampled_accept_distribution_gate.py -q
→ 24 passed in 5.12s
```

The four new tests:

1. `test_device_walk_matches_the_host_oracle_on_its_own_draws` — 3-row chain,
   64-token vocab, 12 seeds. The host oracle replayed with the draws the device
   walk consumed reproduces the device's accepted count and emitted token
   exactly. This pins the decision rule *and* the draw order.
2. `test_device_walk_uses_every_row_of_a_wider_chain` — 4-row chain, 512-token
   vocab, 40 seeds, drafted tokens made attractive so the walk reaches later
   rows; the same identity holds and accepted counts 1, 2, and 3 all occur.
3. `test_device_accept_emits_the_target_law` — the speculative identity: with a
   depth-1 chain whose child row carries the root's law, the cycle's first
   visible token is distributed as `p` itself. 4000 seeds, 6-token vocab:
   device and host empirical laws are both within 0.04 of `p` in every bin and
   within 0.03 of each other.
4. `test_argmax_accept_rule_is_detected_by_the_same_measurement` — RED control:
   the greedy rule is a point mass on the target's mode, which the same
   measurement rejects by more than 0.2.

RED/GREEN on the kernel itself: with the accept test patched to always accept,
tests 1 and 3 fail (`assert 2 == 0`; law deviation 0.958 against a 0.04
tolerance), so the measurement detects a broken *device* rule, not just an
abstract one. The patch was reverted and the four tests re-run green.

## Scope limits

- The device path handles the unfiltered support only: `top_k == 0`,
  `top_p == 1.0`, `min_p == 0.0`, no active token constraint. That is the
  serving default and the case the host oracle defines; a filtered or
  constrained row must keep the host route, and the caller decides that.
- The host oracle still computes its row laws in float64 while the device
  accumulates in float32, so the two agree as laws and on decisions with
  well-separated logits, not bit-for-bit on razor-thin boundaries.
- Nothing in the serving path calls these kernels yet. Wiring the row
  statistics and the chain walk into `Qwen35GGUFNativeB2TargetGraph` (device
  accept/commit for a sampled row, per-row processor inputs and seeds/steps) is
  the remaining work before the ShareGPT re-measurement.
