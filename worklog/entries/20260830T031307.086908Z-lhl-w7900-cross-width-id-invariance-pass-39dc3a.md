# W7900 Qwen3.8: cross-width id gate passes, so batched numerics do not explain the acceptance drop

## Summary

Batch-composition invariance, which no retained packet had ever asserted, holds: for
every width 2..8 the same prompt's full 24-token output is **id-identical** to running
that prompt alone - **420 comparisons, 0 divergent**, across both the AR and MTP arms of
the retained native K3 packet. Consequence for the MTP investigation: the width-dependent
acceptance drop cannot be blamed on batching moving the target model argmax.

## Changes

- `scripts/gguf_mtp_acceptance_compare.py --invariance`: joins lanes to prompts through
  `rows[].usage.prompt_tokens`, compares each lane's ids against that prompt's width-1
  reference, and reports per-width matches/divergences plus the excluded ambiguous lengths.
- No engine or kernel change.

## Validation

| C | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
| - | - | - | - | - | - | - | - |
| matches | 24 | 36 | 48 | 60 | 72 | 84 | 96 |
| divergent | 0 | 0 | 0 | 0 | 0 | 0 | 0 |

Why the packet's own `correctness` block could not have caught the opposite result:
`ar_mtp_equal` compares the two arms inside one cell, so if batching moved the argmax,
both arms would move together and the cell would still pass. A cross-width comparison is
the only way to see it.

Stated limits, so this is not over-read:
- 6 of 10 suite prompts join. Two pairs share prompt lengths (36 and 39 tokens), and
  those four prompts are excluded rather than guessed.
- Id equality proves the sampled trajectory is width-invariant; it is not bitwise logit
  equality. An argmax shift that happened to land on the same tokens for these prompts
  would be invisible here - which is why this narrows, but does not by itself close, the
  numerics hypothesis.
- Acceptance counts are width-dependent (`accepted 0.75` at C1 falling to 0.57-0.66), and
  the same packet shows MTP entering the packed route at width >= 2, so the loss lives in
  draft proposal/selection or the packed accept rule while the verified output stays put.
