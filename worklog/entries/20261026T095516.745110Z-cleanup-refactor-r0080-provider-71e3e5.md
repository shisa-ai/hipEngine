# Resolve provider candidate budgets from registration metadata

## Summary

Provider defaults now live on speculative provider registrations and are read
by a shared accessor in `LLM` and server capability reporting.

## Changes

- Registrations carry a positive candidate budget; existing factory resolution
  still returns the factory, with exact then quantization-agnostic precedence.
- Built-in providers declare their existing defaults. Direct config construction
  keeps its compatibility default; no provider's numerical path changed.
- Before load, a consistent declaration resolves without scanning a model.
  Axis-dependent declarations report pending via a typed ambiguity condition.
  Unknown providers still fail explicitly.
- Construction supplies the known model, backend and quantization axes. Review
  caught and repaired an initial name-only lookup that would have rejected an
  otherwise runnable provider with heterogeneous declared depths.
- Tests cover registration validation, missing and ambiguous declarations,
  explicit/engine/pending precedence and actual LLM construction with different
  defaults under one provider name.
