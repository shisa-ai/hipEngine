# RX 7900 XTX Qwen3.8 context ceiling regression

## Summary

Measured on the physical RX 7900 XTX, Qwen3.8-27B `Q4_K_M` reaches only about
**3K context at one request**, against a published 32K on BF16 and 112K/126K on
pure INT8. **INT8 KV saves no memory at all** on this path. Two user-facing
capacity claims are withdrawn; the underlying cause is not yet diagnosed.

## Changes

- `benchmarks/README.md`: the 24 GB capacity bullet now carries the measured
  XTX ceiling and states that INT8 KV does not extend context. The earlier
  32K/112K figures, which I had carried forward from the older published rows,
  are removed. Root README re-synced.
- No engine change. This entry records a defect, not a fix.

## Validation

Physical RX 7900 XTX (GPU 1, 23.984 GiB) via `python -m hipengine.server` with
`--max-active-requests 1` and an explicit `--kv-storage`, one completion per
point, VRAM sampled from `rocm-smi` on that card.

| KV | context | result | peak |
| --- | ---: | --- | ---: |
| bf16 | 2048 | OK | 21.869 GiB |
| bf16 | 3072 | OK | 23.328 GiB |
| bf16 | 4096 | HIP OOM at warmup | - |
| bf16 | 8192 | HIP OOM at warmup | - |
| int8_per_token_head | 2048 | OK | **21.869 GiB** |
| int8_per_token_head | 3072 | OK | **23.328 GiB** |
| int8_per_token_head | 4096 | HIP OOM at warmup | - |

Every failure is `HipError: HIP error 2: out of memory` raised during eager
server warmup, before any request is issued, so it does not depend on the
prompt. Fitting the two BF16 successes: **1.459 MiB per token** over **18.951
GiB** fixed, which is 15.932 GiB of weights plus ~3.019 GiB of runtime state.
That predicts a 3,532-token ceiling and matches the observed 3,072/4,096
boundary.

### Two distinct problems

1. **INT8 KV is inert.** `int8_per_token_head` and `bf16` give byte-identical
   peaks at 2,048 and at 3,072 and fail at the same 4,096. Whatever dominates
   the footprint is not KV element width, so the option currently buys nothing.
   This alone invalidates the published INT8 context rows.
2. **1.459 MiB per token is very high** for a 27B model. It is the reason only
   ~3K fits once weights and fixed state are paid for.

### Relationship to the published rows

The scoreboard published 32K BF16 and 112K/126K INT8 for this card. Measured
today it is ~3K on either. The published BF16 memory figure -- 21.869 GiB peak
with 2.115 GiB headroom -- **reproduces exactly here at 2,048 context**, so the
memory number survives while the context label does not. That is a strong hint
the original row's context labelling, or the configuration behind it, differs
from a default server rather than the footprint having grown 16x.

## Next

- Diagnose why `--kv-storage int8_per_token_head` changes nothing. Either the
  request is not reaching the INT8 path or the allocation is sized before the
  KV dtype is applied.
- Attribute the 1.459 MiB/token. For a 27B model that is large enough to
  suggest full-width KV across all layers, or a pool sized to context rather
  than to live tokens.
- Reconstruct the original 32K/112K configuration. These runs use a minimal
  default invocation and did not attempt chunked prefill, prefix cache, or a
  growing KV pool, any of which the published rows may have relied on.
- Re-check the W7900 concurrency figures against this fixed-overhead model;
  they were consistent at c1 (19.6 GiB measured versus 19.7 predicted) but the
  same INT8 defect would affect any long-context serving claim there too.
