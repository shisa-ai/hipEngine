# The pack8 port lands in gemma4_gguf_device.py, which already anticipates it

## Summary

The thread's last open question - whether Gemma 4's loader could accept a repack
step - is answered, and **the loader says so itself**.

`hipengine/loading/gemma4_gguf_device.py:15`:

> No repack step. `launch_gguf_linear` serves the `raw` layout for every quant ...
> so resident-layout conversion is a later performance question.

The module defines exactly two layouts, `LAYOUT_RAW_GGUF` (:44) and
`LAYOUT_DENSE_F32` (:45), and `materialize_gemma4_gguf_device_weight` (:203)
branches on `spec.layout` at :215 and :225 and raises on anything else at :228.

So a resident-layout step can be inserted **where that dispatch already is**.
Part one is a **port of the qwen35 `_RESIDENT_REPACKS` pattern**, not a new
materialization path - bounded, and the module's own comment anticipates it as
"a later performance question". This profile is that question answered: roughly
4-6x of bandwidth headroom on a line that is 28.0% of decode.

**A file-identification correction.** `gemma4_gguf_materialize.py` is the **CPU
reference** materializer - `Gemma4GGUFReferenceWeights`, importing
`kernels.cpu_reference.gemma4` - not the device path. The previous entry's grep for
repack machinery there was looking in the wrong file, and its conclusion ("no
resident-repack machinery") was right for the wrong reason. The device loader is
`gemma4_gguf_device.py`, and it is the file that matters.
