# Screen dense-wide scratch growth against scratch-enabled GDN

## Summary

Dense-wide scratch growth does not cause a large persistent slowdown on the
scratch-enabled GDN victim in this bounded synthetic screen. X-5 stays open
for complete kernel metadata and representative decode victims. No promotion.

## Changes

- Extend `scripts/qwen4exp_scratch_order_probe.py` with wave-norm victim,
  dense-wide trigger, CPU F16-reference check and boundary clock snapshots.
- Packet: `benchmarks/results/2026-09-28-qwen4exp-scratch-growth/README.md`
  and `artifact.json` contain exact commands, physical host, hardware, shapes,
  quant, library hashes, timing samples, clocks and compact profiler evidence.
- Four fresh serial sham/scratch/scratch/sham processes yield after/before
  median ratios 0.996043/0.997469/0.998558/1.004023. This is a scratch-growth
  diagnostic, not a same-host old-to-new optimization or serving-rate claim.

## Validation

- Four unprofiled runs plus one cached-build rocprofv3 run pass exact GDN
  output/state checks. All four unprofiled output/state hashes match.
- Dense Q8_0 rows257/K256/N256 passes CPU F16-operand reference with maximum
  absolute error 3.7104e-6 on reference scale 9.2502; no arithmetic changed.
- rocprofv3 confirms six 36-byte GDN calls, one 92-byte dense-wide call,
  three more 36-byte GDN calls on the same queue. Allocation changes
  1,638,400 → 3,932,160 bytes before the dense trigger, matching the hypothesis.
- Boundary clock snapshots show SCLK2900/MCLK1000 MHz at all boundaries.
  Continuous telemetry is not claimed.
- `python3 -m py_compile scripts/qwen4exp_scratch_order_probe.py` passes.
- As with the prior pilot, live GPU runs and assertions are the targeted test;
  no kernel/dispatch changes or broad gate rerun. RED-first is not applicable
  to a timing observation on existing variants. Raw logs stay in `/tmp`.
