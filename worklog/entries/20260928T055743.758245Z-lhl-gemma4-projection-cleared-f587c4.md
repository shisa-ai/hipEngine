# the projection agrees across both routes so the defect is in the routing or the gather

## Summary

`20260928T055712` named `selected_gemv` as the suspect on the strength of the
census and the per-lane geometry. Driven directly, it is **cleared**:

```
hidden=256 moe_intermediate=64 fused=128 num_experts=4
compact=2: route=selected_gemv   (reference) |row0|=2199.8823
compact=4: route=grouped_prefill row0 vs compact=2 rel=0.00000000 max_abs=0.0000
```

`gemma4_project_experts_rows` is called with a **hand-built `expert_start` and
`sorted_experts`** -- expert 0 owning every compact row, so compact order equals
row order -- and the same leading input rows. Compact row 0's output is
**bit-identical** across the two routes, at `max_abs=0.0`.

So the projection family is not the divergence, and the two routes it selects
between agree on this input.

## What the probe bypassed, and why that matters

The direct call takes `x` as the already-packed compact buffer. It therefore
skips the two stages that sit between the caller's hidden block and the
projection:

1. the **group-scatter** (`qwen35_moe_group_count`,
   `qwen35_moe_group_prefix_active`, `qwen35_moe_group_compact_active`), which
   produces `expert_start`, `sorted_lanes`, `sorted_experts` and
   `sorted_weights`; and
2. the **gather** (`qwen35_moe_gather_packed_hidden_lowp`), which pulls hidden
   rows into compact order using `sorted_lanes`, `lanes * hidden_size`, `tokens`,
   `top_k` and `hidden_size`.

The full call diverges and the direct call does not, so the divergence is in one
of those two stages. That is a positive narrowing, not a failure to find one.

## Correction to the previous unit

`20260928T055712` concluded that the suspect was `selected_gemv`/`grouped_row4`
because the census named it and its per-lane geometry is the one whose lanes
were shown not to be independent. That reasoning was sound about *which side* of
the outer gate is invariant but wrong about the kernel: the projection's
arithmetic is fine, and what is not independent is something upstream of it.

The earlier "single active expert" result is still consistent with this. With
one active expert, the group-scatter has one group, and the gather is the only
stage whose lane-to-token mapping changes with `lanes`.

## The leading candidate

The gather. It is the only stage where `lanes`, `tokens` and `top_k` interact to
map a compact row back to a token, via `sorted_lanes[row] / top_k`, and it is the
stage that fills the buffer the projection then consumes. A wrong mapping there
would put another row's hidden vector into compact row 0 -- which is exactly the
"rows contaminate each other" signature, and it would be invisible in a probe
that hands the projection the packed buffer directly.

The group-scatter is the second candidate: if `sorted_lanes` or `expert_start`
is built from a stale or wider lane count, the gather is handed a wrong
permutation rather than computing one wrongly.

## Validation

- Probe on the 8060S (gfx1151) calling `gemma4_project_experts_rows` directly
  with hand-built int64 `expert_start` (expert 0 owning all compact rows) and
  `sorted_experts` (all zeros), at `compact_rows=2` and `=4`, on the fixture's
  `experts_gate_up_proj`, comparing compact row 0's F32 output. Exit 0.
- The reported route string is the function's own return value, so the two calls
  are confirmed to have taken `selected_gemv` and `grouped_prefill` -- the two
  routes the earlier forced-route experiment separated -- rather than silently
  taking the same one.
- `max_abs=0.0` is a value comparison on the F32 output, not a bit-pattern
  comparison on BF16, so it is a real equality.
