# DP-9 closes: the decode MoE gate/up owner DP-9 was re-ranked UP for was already captured by DE-1's dp4a promotion

## Summary

DP-9 ("small projection load scheduling and immutable shape plans") was re-ranked **UP**
on 2026-09-30 after its measured-owner prerequisite was satisfied. That ranking rested on
a decode capture in which `gguf_q4_k_selected_dual_silu_logical128_t64` is the largest
less-examined owner at **13.968 ms/step = 26.10% of decode**.

That capture **predates** the `DE-1` promotion of the decode dp4a logical128 route into the
production default. The owner DP-9 names **is DE-1's kernel**, and after the promotion it
runs at:

| | ms/step | GB/s | % of in-block comparator |
| --- | --- | --- | --- |
| before (exact logical128) | 14.013 | 63.18 | 34.2% |
| after (dp4a, production scope) | **5.404** | **163.72** | **88.7%** |

The gap to the comparator fell from 2.94x to 1.12x, leaving **0.613 ms/step = 1.29%** of the
47.390 ms/step decode kernel sum. The screen therefore answers itself: the owner is **near
roof, not latency-bound**, so there is no surviving shape worth the ordered load-ahead or
preselected library algorithm this row proposed.

**The row is closed as "target captured by a sibling row's promotion", not as "screened
and rejected".** That distinction matters for the ledger: no work was wasted and no
candidate failed; a different row's promotion consumed the opportunity first.

## Validation

**The traffic model was re-derived from the model's own GGUF metadata, not taken from the
row.** Shard 1 of 4 of `unsloth-Qwen3.8-Flash-Next-UD-Q4_K_XL` reports
`embedding_length 2560`, `expert_feed_forward_length 640`, `expert_count 512`,
`expert_used_count 10`, `block_count 48`. With Q4_K at `QK_K 256` / 144 B per block
(`hipengine/kernels/hip_gfx1100/quant/gguf_q4_k_gemv.hip`):

```
row_bytes  = (2560 / 256) * 144 = 1440 B
per-layer  = 10 experts * 640 out_features * 1440 B * 2 (gate+up) = 18,432,000 B
48 layers  = 884.74 MB/step
```

That sits **0.5% below** the 888.83 MB/step the recorded rates were computed from — the
difference is a shared-expert term this unique-expert model omits, so the derived value is
a strict floor. Both recorded rates reproduce from it:

```
884.74 MB / 14.013 ms = 63.18 GB/s   (row records 63.43 at 888.83 MB)
884.74 MB /  5.404 ms = 163.72 GB/s  (row records 164.48 at 888.83 MB)
```

**A correction to how this row's own `grid=40960` reading should be read.** DP-9's state
recorded `grid=40960` from launch-signature inference, which the row itself flagged as
non-unique because `--kernel-rename` replaces decode kernel names by construction. The
authoritative per-kernel join charges **10 unique experts per layer**, not a 64-row
expansion. The signature figure is superseded by the join.

**RED/GREEN verified by mutation.** Each of the four tests was confirmed to be a real RED
test by breaking the condition it pins, then restoring:

| mutation | result |
| --- | --- |
| `TOP_K` 10 → 8 | 3 tests FAIL |
| owner time = pre-promotion 14.013 ms | 2 tests FAIL |
| `Q4_DP4A64` removed from `PRODUCTION_Q8_QSA_RESTORED_FLAGS` | 1 test FAILS |
| `Q4_DP4A64` removed from `PRODUCTION_ARITHMETIC_RECOVERY_FLAGS` | 1 test FAILS |
| restored | 4 pass, `git diff` clean |

The two-sided flag pin is deliberate: DE-1's recorded mechanism is that "`Q4_DP4A64` moved
into `PRODUCTION_Q8_QSA_RESTORED_FLAGS`; the base profile already set it to `1` and the
blanket arithmetic-recovery sweep was the only thing suppressing it". That is an
interaction between two structures, so a test that pins only one side cannot detect the
revert that matters.

Bundle: `tests/test_unit_qwen4exp_dp9_decode_moe_closure.py` +
`tests/test_unit_qwen4_exp_profiles.py` = **13 passed**.
