# Resident-block divergence was a measurement artifact

## Summary

An earlier session reported a 255.8 absmax divergence between the resident
device block (`Inkling2GGUFText` path) and the host/reference paths at
"boundary 18" of the Japanese-prompt prefill. That divergence does not exist.
It was an off-by-one in the comparison harness, not a numerical or device bug.

Root cause of the misread:

- `_traverse` captures `capture(boundary, h)` at the *top* of the loop
  iteration, *after* the `restart_from_prelude` rebind at visits 18 and 30.
  `capture(18)` is therefore the post-restart state (fresh `prelude_hidden`),
  not the post-visit-17 residuals.
- The block-side reference was run with `limit=18`, which stops after visits
  0..17, i.e. it holds post-visit-17 residuals and *has not applied* the
  visit-18 restart.
- Comparing those two tensors is comparing two different logical points on
  opposite sides of the deliberate pass-boundary state reset, so a ~255 absmax
  gap is the expected value, not a defect. The same artifact made an
  env-var flip appear to "flip" the outcome depending on which file was
  compared.
- Visit indices that looked like "flip points" (17/18/29/30/47) are exactly the
  pass boundaries (restarts at 18 and 30; last core visit before the final
  prelude tail), confirming the off-by-one rather than a chaotic kernel.

## Changes

- None (investigation only). Temporary env-gated dump hooks
  (`INKLING_DUMP_BOUNDARIES`/`INKLING_DUMP_DIR`/`INKLING_DUMP_ONLY` in
  `inkling2_gguf.py` / `inkling2_mini_reference.py`) were used and then
  reverted; the tree is clean.

## Validation

Full 48-visit prefill of the 64-token Japanese probe, dumping the `hout`
residual at every visit boundary, three implementations:

- hip_gfx1100 device resident block (`_resident_block`, `limit=48`)
- device host path (`prefill_block` via `_traverse`)
- NumPy fallback (device attention/conv disabled)

Pairwise max abs diff per boundary, all 48 visits: worst host-vs-block
1.60e-04, worst host-vs-oracle 1.22e-04, worst block-vs-oracle 1.03e-04
(worst at visit 23; all other visits <= 1.6e-05). All three agree to fp32
accumulation noise everywhere, including the pass boundaries. Device-host
dumps are bitwise reproducible across processes and across env-dump
configurations.

## Next

- None for this artifact. Note for future debugging of this model: never
  compare `capture(k)` against post-visit-k state across a
  `restart_from_prelude` visit; compare like-for-like points (both post-visit
  via dumps, or both post-restart via capture). If host/block bitwise parity
  is ever required, it is not attainable by design (different summation
  orders); use a tolerance gate (~1e-3 abs on residuals) instead.
