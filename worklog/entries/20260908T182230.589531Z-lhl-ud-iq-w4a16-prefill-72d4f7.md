# W4A16 IQ prefill: strict-GEMV accuracy at GEMM speed

## Summary

Adds a W4A16 prefill route for raw dense GGUF IQ weights, following the
reviewer's suggestion that a 16-bit-float path is the only way to recover the
mean KL the integer-MMQ route trades away.

It works: **W4A16 reaches the strict GEMV's accuracy** (1.67e-03 against
1.66e-03, both at the bf16 output floor) where the integer MMQ sits 3.35x
above at 5.60e-03. But it is **1.4-2.1x slower** than the integer MMQ, so per
the standing decision rule the integer MMQ stays the production owner and
W4A16 is retained as a registered, unrouted exact-family path.

## Changes

- `gguf_iq_wmma_prefill.hip` (new): TILE_M x TILE_N wave32 WMMA kernel
  modelled on `gguf_q6_k_prefill_wmma_kernel`. Raw IQ blocks expand per element
  into fp16 operands using the strict dense kernel's own decode expressions;
  activations are read straight from the caller's bf16 buffer, so there is **no
  quantized activation plane and no workspace**.
- `gguf_iq_wmma_prefill.py` (new), `quant/__init__.py`: wrapper matching the raw
  linear launch ABI, registration for all seven quants, exports.
- `tests/test_gguf_iq_wmma_prefill.py` (new, 30 cases).

## fp16, not bf16 - and why that mattered

The reviewer proposed bf16 WMMA. A host simulation on real tensors, run before
any kernel was written, says bf16 would have been mostly wasted:

| path | relative error vs f32 |
| --- | --- |
| int8 activations (today's MMQ) | 5.3e-03 |
| **fp16 both operands** | **2.1e-04** |
| bf16 both operands | 1.6e-03 |
| bf16 weights, exact activations | 1.6e-03 |

bf16's 8-bit mantissa puts ~0.4% error back onto the **weights**, which the
integer path keeps exact - so it recovers 3.2x where fp16 recovers 25x. fp16 is
also the format hipEngine already uses: 49 in-tree uses of
`wmma_f32_16x16x16_f16_w32` against zero bf16 WMMA.

## Measurements

Leaf, largest aligned tensor per quant, min-of-5, accuracy against an f64 host
reference from the CPU dequantizer so all three paths are judged against the
same truth:

| quant | rows | GEMV | MMQ | W4A16 | GEMV err | MMQ err | W4A16 err |
| --- | --- | --- | --- | --- | --- | --- | --- |
| IQ4_XS | 512 | 87.9 ms | 8.2 | 11.4 | 1.66e-03 | 5.60e-03 | 1.67e-03 |
| IQ4_NL | 512 | 118.6 | 8.5 | 15.5 | 1.66e-03 | 5.60e-03 | 1.67e-03 |
| IQ3_S | 512 | 92.4 | 7.9 | 14.5 | 1.66e-03 | 5.59e-03 | 1.67e-03 |

W4A16 and the GEMV are **both at the bf16 output floor**, so the 1.67e-03 is
the output format, not either kernel's arithmetic - they are accuracy
equivalent. W4A16 is 0.48-0.72x of the integer MMQ and 5-8x faster than the
GEMV.

**Tile sweep** (IQ4_XS 512 rows, TILE_M x TILE_N ms): 64x16 33.3, 64x32 24.7,
32x32 20.8, 32x64 17.2, 16x64 12.0, 16x96 12.6, **16x128 11.4**, 32x128 15.1,
128x16 42.2. Row reuse dominates. The first shape tried (64x16) was 2.9x off
the best and made IQ3_S look pathological at 259 ms; at 16x128 it is 14.5 ms.
The sweep is recorded in the kernel so the shape is not re-guessed.

## Decision

The integer MMQ remains the production default - it is faster, and the
four-quant policy trade was accepted deliberately. W4A16 is registered on both
HIP backends and selected by **no** dispatch policy, which a test asserts. It
is the natural owner if a profile later needs the mean KL back, because it is
the only route that reaches strict-GEMV accuracy at GEMM speed.

## Validation

30 cases: registration on both backends for all seven quants, an assertion
that no policy selects it, argument validation (including the bf16-only output
contract and IQ4_NL's 32-element block alignment), and a numerics comparison
against the strict dense GEMV on real fixture rows for IQ4_XS/IQ4_NL/IQ3_S/Q3_K.

Artifact: `benchmarks/results/2026-09-09-zbook-ud-iq-w4a16-prefill.json`.

## Next

Closing the remaining 1.4-2.1x means adopting the integer MMQ's structure:
decode once into an LDS tile reused across 128 rows, instead of per element per
lane with 128 rows of reuse. Also unimplemented: f32 output, and any
model-level gate (none was run because it is not a default).
