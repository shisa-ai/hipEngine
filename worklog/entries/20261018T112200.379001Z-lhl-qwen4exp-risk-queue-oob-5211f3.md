# Fix the out-of-bounds risk-queue write that aborted long GPU runs

## Summary

The SIGABRT that kept the local `pytest --suite all` gate from completing is
found and fixed, and it was a test bug rather than a kernel bug.
`test_j32_tile_survives_the_exact_repair_chain` seeded the risk counter with the
count measured by a preceding launch and sized the index queue to that same
count. The prefill publishes its queue through `atomicAdd(risk_count, 1)`, so
the counter is an append cursor: the launch appended a second full queue behind
the seeded value and wrote past the end of the allocation. Measured on the
test's own fixture the kernel published 2,480 entries into a buffer sized for
1,240 int32, i.e. 4,960 bytes past the end.

## Changes

- `tests/test_gpu_qwen4exp_q4_iu8_j32_tile.py`: the repair-chain test now zeroes
  the counter and sizes the index queue to the worst case
  (`compact_rows * out_features_total`), matching `_run_tile` and the production
  runner, which already memsets the counter before every launch.
- `tests/test_gpu_qwen4exp_q4_iu8_j32_tile.py`: new
  `test_risk_counter_accumulates_so_the_queue_must_start_zeroed` pins the append
  contract — two launches without a reset report `2 * first`, a reset returns the
  original count — so the zeroing step cannot be dropped again.
- `docs/REFACTOR.md`: the abort entry now records the cause, the measured
  overrun, and the fix instead of a localization plan.

## Validation

- Direct measurement of the old sequence on the test's fixture (32-row tile,
  counts `[17, 0, 64, 3, 129, 32]`, multiplier 4.0): `capacity=62720
  zeroed_count=1240 seeded_count=2480`, so the old code's 1,240-int32 queue
  received 2,480 entries — 4,960 bytes past the end. This is the heap
  corruption that surfaced as `SIGABRT` in `hipMemcpy`/`hipFree` at whichever
  later test consumed the damaged metadata.
- `uv run pytest tests/test_gpu_qwen4exp_q4_iu8_j32_tile.py` — 19 passed,
  including the new contract test.
- Explains every prior observation: the abort moved between files because it
  depended on which allocation followed the overrun; the aborting file passed 25
  consecutive standalone runs because a fresh heap left the overrun in unused
  memory; and `HipError` was never raised because no HIP call itself failed.
- The production runner was never affected: `qwen4_exp_runner.py` memsets the
  counter before each risk launch.
- Full-suite gate re-run: `uv run pytest --suite all -q` started on this commit;
  result recorded in the follow-up entry.
