# UD Phase 5: lift the rows 5-8 verifier cap and attribute the cliff at five rows

## Summary

The native verifier cycle now runs the whole declared two-to-eight row
envelope. The cap at four rows was **one guard on one wrapper**, not a kernel
limit.

The guard was `rows not in (2, 3, 4)` in
`gguf_rounded_add_rmsnorm_bf16_f32_weight` (registry key
`hip_gfx1100/add+rmsnorm/gguf_f32_weight/rounded_bf16_out`) plus the matching
`rows > 4` test in the C launcher
(`hipengine/kernels/hip_gfx1100/fused/gguf_ops.hip`). Its device kernel is one
block per row with an identical 256-thread reduction tree, so it is row-count
agnostic; the guard was narrower than the `2 <= rows <= 8` envelope every
caller already declares (`qwen35_gguf_runner` gates `chain_dense_next_rms` and
the row LM head at `rows <= 8`, and the graph builder admits 2-8).

The earlier claim that the device accept/commit kernels also cap at four rows
is **wrong**. The verifier binds positions from a device array
(`prepare_packed_decode_metadata_from_positions`). The four-scalar
`position0..position3` ABI belongs to `prepare_packed_decode_metadata`, which
has no in-tree runtime caller at all.

Measured consequence, UD-Q4_K_M, native cycle with device accept/commit and
deferred linear-state commit, physical GPU1 (RX 7900 XTX), one prompt, three
measured steps after one warmup:

| rows | host ms/step | kernel ms/step | kernel share | calls/step | ms/row | IQ family owner |
| ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 4 | 51.15 | 45.54 | 0.890 | 1032 | 12.79 | `gguf_iq4_xs_local32_gemv` (26.0%) |
| 5 | 91.32 | 85.48 | 0.936 | 1096 | **18.26** | `gguf_iq_dense_strict` (61.8%) |
| 6 | 94.97 | 88.64 | 0.933 | 1160 | 15.83 | `gguf_iq_dense_strict` (60.9%) |
| 8 | 104.76 | 97.38 | 0.930 | 1288 | 13.09 | `gguf_iq_dense_strict` (59.5%) |

**The cliff is at five rows.** Above four rows the IQ family leaves the rows 2-4
local32 verifier sibling and reverts to `gguf_iq_dense_strict`, which then owns
59.5-61.8% of verifier kernel time. Rows 5 costs 91.32 ms/step against 51.15 at
rows 4, so 25% more rows costs 78% more time. The strict kernel is nearly
row-count independent (52.8 / 54.0 / 57.9 ms/step at rows 5 / 6 / 8) because it
is dominated by the per-step IQ weight stream, which is why rows 5 is the worst
per-row point of the four.

Budget 4 is the **only** newly reachable production shape, because
`_GGUF_MTP_CANDIDATE_BUDGETS` is `(1, 2, 3, 4)` and rows is one root row plus
the budget. Rows 6-8 need a budget policy that admits 5-7, which the declared
envelope does not. The default path is unchanged: `max_candidate_budget`
defaults to 3 and `candidate_budget` to 1, so budget 4 is explicit opt-in.

The newly reachable rows-5 shape is numerically qualified against the same
section-6.1 envelope (physical GPU1, c1, short point, native graph, budgets
1-4, 252 pooled rows per repeat, two repeats):

| Arm | mean KL | p95 | p99 | max | top-1 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `ud_q4_k_m` | 3.479e-05 | 1.696e-04 | 2.462e-04 | 3.475e-04 | 1.0000 |
| `ud_q4_k_s` | 3.855e-05 | 2.056e-04 | 3.764e-04 | 6.980e-04 | 1.0000 |

Top-1 is 1.0000 at budget 4 (90 rows) as well as at budgets 1-3, and in every
category. So the cap lift turns an admitted-but-broken configuration into a
correct one; it does not make budget 4 economical.

## Changes

- `hipengine/kernels/hip_gfx1100/fused/gguf_ops.py`: the wrapper guard is now
  `not 2 <= rows <= 8`, with a docstring recording why the kernel is
  row-count agnostic. This is the only arithmetic-path change; the device
  kernel body is untouched.
- `hipengine/kernels/hip_gfx1100/fused/gguf_ops.hip`: the C launcher guard is
  `rows > 8` instead of `rows > 4`.
- `scripts/gguf_mtp_verifier_rocprof.py`: `NATIVE_SPEC_TARGET_ROWS` is now
  `{2..8}` and the refusal message names the real envelope. Separately,
  `_hardware_label()` resolved the *first* gfx agent in `rocminfo` regardless
  of `HIP_VISIBLE_DEVICES`, so every census artifact on this two-card host
  claimed the W7900 while measuring the XTX. It now resolves the visible
  ordinal and names the card, and falls back to an explicit unknown when the
  selection is a UUID.
- `tests/test_qwen36_gguf_rounded_next_rmsnorm.py`: the bit-exactness test is
  parametrized over rows 2-8 instead of 2-4, and the boundary test rejects 1
  and 9.
- `tests/test_scripts_gguf_mtp_verifier_rocprof.py`: the four-row-stop test
  becomes an admit test, plus coverage for the device label.
- `benchmarks/results/2026-09-12-ud-gfx1100-verifier-rows-4-8-census.json`
  and `benchmarks/results/2026-09-12-ud-gfx1100-rows5-budget4-gate.json`.

## Next

The follow-up that makes budget 4 worth using is to extend the rows 2-4 local32
IQ verifier sibling's policy to rows 5-8. That is a Phase 4-shaped change and
owes the full production-profile gate, because it changes the accumulation
geometry. Until then, budget 4 is correct but 1.8x the rows-4 step.

Also unblocked by the cap lift: the Phase 1 open item to capture representative
verifier rows. Rows 6 and 8 are now capturable; 9+ are not, because the native
target graph is defined for two to eight rows.
