# gemma4 gfx1151: the prefill kernel is issue-busy and tensor-idle, and the suspects are named

## Summary

The previous entry established with hardware counters that the prefill attention
kernel runs at **4.0% of the DRAM roofline**. This narrows what it *is* bound by,
and rules out the two obvious answers.

| counter | value | reading |
| --- | --- | --- |
| `SQ_BUSY_CYCLES` / `SQ_CYCLES` | 187.2M / 187.5M | **99.8% busy** -- not stalled |
| `SQ_CYCLES` / duration | 187.5M / 75.7 ms | 2.48 GHz, i.e. the counter is the clock |
| `SQ_INSTS_VALU` | 64.86M | |
| `SQ_INSTS_LDS` | 46.94M | |
| instructions / SQ-cycles | 111.8M / 187.5M | **0.60 IPC per SQ** |

Measured on the shipped prefill shape, `tokens=256, keys=65536`, one full layer,
all-ones mask, under `rocprofv3 --pmc`. Two dispatches, 75.7 ms and 76.7 ms, with
instruction counts agreeing to 0.003%.

## What this rules out

- **Not memory-stalled.** `SQ_BUSY_CYCLES` is 99.8% of `SQ_CYCLES`, so the shader
  sequencer is issuing essentially every cycle. A kernel waiting on DRAM does not
  look like this.
- **Not the tensor unit.** The source documents that the head-dimension split
  "issues 1.5x the ideal WMMA count"; at that count the kernel is about **1.2%**
  of the part's 54.6 TFLOP/s BF16 rate.
- **Not occupancy-limited by shared memory in a way that shows as idling.**
  Nothing is idling.

## What it leaves

The kernel is **instruction-issue-bound on non-tensor work**: 111.8M instructions
in 187.5M SQ-cycles, of which 46.9M are LDS and 64.9M are VALU, at 0.60 IPC per
SQ. The named suspects, in the order the source's own notes suggest them:

1. **The staging loop's LDS traffic.** 46.9M LDS instructions is 42% of the
   instruction count. The block stages a 16-key x 512-dimension K and V tile per
   K-batch and the walk is over the whole context, so this scales with
   `keys / 16` per row block.
2. **The per-batch online-softmax serial chain.** Every K-batch runs mask, max,
   rescale and accumulate in sequence, and `previous_scale != 1.0f` guards a
   128-float-per-lane multiply. The source calls that guard out as "the most
   expensive thing in the batch after the walk itself".
3. **The 1.5x WMMA issue from the output-dimension split.** Not the tensor unit's
   throughput but the *issue slots* the duplicate score dot consumes.

This is a checkpoint, not a conclusion: none of the three is measured, and the
next step is to attribute the 111.8M instructions between the staging loop, the
softmax chain and the WMMA issue rather than to guess.

## Validation

- `env -u HIP_VISIBLE_DEVICES PYTHONPATH=. HIPENGINE_HIP_ARCH=gfx1151 rocprofv3
  --pmc SQ_LEVEL_WAVES SQ_BUSY_CYCLES SQ_CYCLES SQ_INSTS_VALU SQ_INSTS_LDS
  --kernel-include-regex gemma4_attention_prefill_wmma_full -d <dir> --
  .venv/bin/python scripts/gemma4_prefill_kernel_bw.py --reps 1 --keys 65536
  --tokens 256`
- `SQ_LEVEL_WAVES` reads 0 on both dispatches, so it is not supported on gfx1151
  and is not used for anything. Recorded so the gap is visible rather than
  silently absent.
- The two dispatches are independent launches of the same configuration and agree
  on every instruction count to within 0.003%.
