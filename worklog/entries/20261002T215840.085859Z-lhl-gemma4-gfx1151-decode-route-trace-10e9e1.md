# gemma4 gfx1151: the 8192-key decode route is confirmed by a kernel trace, closing task 30

## Summary

Task #30's five acceptance criteria were met by commits `2c1bf6b71` and
`e289015b4`, but one was recorded as outstanding: the rocprofv3 kernel trace
naming the decode shape at 8192 keys. It is now taken.

`rocprofv3 --kernel-trace` on a real 8192-token prompt through
`scripts/gemma4_campaign_bench.py`:

| kernel | launches | role |
| --- | --- | --- |
| `gemma4_attention_decode_wmma_full_kernel` | 150 | **the full layer's decode** |
| `gemma4_attention_wmma_combine_kernel` | 150 | its split-walk combine |
| `gemma4_attention_decode_dimension_kernel` | 750 | the sliding layers' decode, unchanged |
| `gemma4_attention_decode_class_kernel` | 750 | the sliding layers' decode, class stage |
| strict full-layer decode | **0** | **absent** -- this was the 8192-key path before the unit |

The full layer's decode reaches the WMMA decode shape and the strict kernel it
used to take does not appear at all. The sliding layers keep their own strict
decode kernels, which is the half the crossover must not move: a sliding layer
presents 1,024 window keys at any configured context, so it sits below the 4,096
threshold and stays put.

## The five criteria, and where each is evidenced

1. **A one-token block at keys in [15617, 15856] runs instead of raising.**
   `benchmarks/results/2026-10-02-gemma4-gfx1151-decode-crossover.json`
   `end_to_end.correctness_window_closed`: a 15,800-token prompt that previously
   raised `NotImplementedError` on its first decode returns normally.
2. **A one-token block at 8192 keys reaches the WMMA decode shape.** This entry
   and `benchmarks/results/2026-10-02-gemma4-gfx1151-decode-route-trace-8192.json`
   for the trace; the routed variant is asserted by
   `tests/test_unit_gemma4_prefill_attention_selection.py`.
3. **The end-to-end curve at 4096/8192/16384 is monotone non-increasing.**
   28.4891 / 28.3992 / 27.3668 tok/s. The dip to 16.83 at 8192 is gone.
4. **The teacher-forced gate re-run with the new crossover.** Run over 4,095 rows;
   its one breach was the 64-way key split, resolved by `58609c484`, and the same
   gate now passes at `kl_max` 0.0229 against 0.05.
5. **The strict kernel's bound check made consistent.**
   `test_the_rule_never_selects_a_strict_launch_that_cannot_start` asserts the
   whole window routes away and that `gemma4_attention_shared_bytes` refuses
   15,617 keys while accepting 15,616.
