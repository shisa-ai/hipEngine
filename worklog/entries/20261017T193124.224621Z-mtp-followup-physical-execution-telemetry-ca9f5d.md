# Expose physical MTP work separately from HTTP grouping

## Summary

The HTTP replay showed that `queue_group` and `backend_groups` are per-submission
records, not proof of physical MTP width. Q4_K_M C1-C4 requests were all
successful and MTP-used; the public choice diagnostics needed to expose the
resident row counters so a client can distinguish singleton target passes from
batched proposal/target launches.

## Changes

- Add `diagnostics.specdec2_mtp2.physical_execution` with proposal/target
  batch-call counts and width histograms.
- Include `target_pass_count` so singleton target passes are not confused with
  absent target work.
- Document the distinction in `docs/API.md` and cover response accounting and
  independent-MTP admission behavior in focused tests.

## Validation

- Focused accounting, server policy, and independent-admission tests pass:
  `.venv/bin/python -m pytest tests/test_unit_mtp_output_accounting.py
  tests/test_integration_server_mtp_policy_batching.py
  tests/test_integration_mtp_independent_admission.py -q` (32 passed).
- `scripts/docs/check_all.py` passes.
- The Q4_K_M real C1-C4 replay passed 10/10 requests; physical counters
  showed proposal widths 2/3/4 and target widths 8/12/16 as rows joined or
  retired. This is diagnostic evidence, not a throughput claim.
