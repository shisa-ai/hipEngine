# Full-grid dimension partition passes numerics but loses throughput

## Summary

One dimension per lane improves the earlier exact dimension implementation, but
is still slower than the incumbent. Median decode is 43.72581740167139 tok/s
against the same-host incumbent's 45.747405590036514 tok/s (4.4% lower).
The 1023-row teacher-forced comparison has zero KL and 100% top-1 agreement.
The patch was reverted as a performance candidate; the numerical repair remains
unfinished on the default path.

## Changes

The proposed value pass launches ceil(head_dim/32) blocks per head, each with
32 threads and the full weight vector in LDS. Each lane accumulates one dimension
in ascending key order. Six exact-schedule fixtures were reintroduced; four failed
on the incumbent before the implementation. All six pass on the candidate.
No new flag. Patch and reports are preserved in
`benchmarks/results/2026-09-26-gemma4-dimension-full-grid-rejected.json`.

## Validation

Host `epyc`, physical GPU1 RX 7900 XTX, Gemma 4 26B-A4B-it UD-Q4_K_XL,
context 8192, BF16 KV, greedy, 1024 prompt / 128 output, three measured samples.
The public `LLM.generate()` comparison passes; all 30,690 scored teacher-forced
launches use the split entry. 83 focused GPU tests and the 446-test Gemma guard
pass. No secondary workload matrix or complete promotion is claimed because
primary decode throughput regressed.

## Next

performance loss without changing numerical results. A bounded next test can
increase independent memory prefetch within each lane, using this full-grid
layout rather than the earlier serial multi-dimension layout. Keep the same
