# the assistant route passes the whole live cache as keys with no chunking

## Summary

The previous entry left one question open: is the 15,616-key ceiling live or
latent? **In the one route I checked it is live.** `hipengine/runtime/gemma4_assistant.py`
passes

```python
gemma4_attention_prefill_bf16(
    ..., tokens=1, keys=int(view.live), ...
    window=0 if block.sliding_window is None else int(block.sliding_window),
)
```

`keys` is the **whole live cache**, there is no chunking loop around it, and the
window is 0 for any layer whose `sliding_window` is `None`. So on that route a
windowless layer with more than 15,616 live keys reaches
`gemma4_attention_shared_bytes` and raises.

## Scope of what I checked

I checked **one route**: the assistant path in `gemma4_assistant.py`, by grepping the
gemma4 files for the attention call and reading the call site. I did **not** check the
main prefill route, and I am not claiming it behaves the same way. The grep for
chunking in the gemma4 runtime files returned nothing, which is suggestive but is not
the same as reading the main path.

So the accurate statement is: **the ceiling is reachable on the assistant route**,
and the main route is unchecked.

## Why it is still worth recording

The failure is a named `NotImplementedError` rather than a silent downgrade or a
truncated context, which is the behaviour this repository requires. So this is not a
correctness bug and nothing is being computed wrongly.

It is a **capability limit with a known cause and a known fix**, and it is the third
consequence of the same resident-logit design:

1. the three LDS round trips per visit that are the latency chain
   (`20260928T065753`),
2. the `TQ ~ 4` ceiling on amortizing visits over query rows (same entry),
3. and now a hard key-count ceiling that the assistant route reaches without
   chunking (`20260928T065832` and this one).

A token-tiled online-softmax kernel removes all three.
