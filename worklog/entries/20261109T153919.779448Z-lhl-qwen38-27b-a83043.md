# EAGLE-4 device accept (task #25b) measured: 0.048ms standalone, defer to graph-captured cycle

## Summary

Decision: do not land a standalone device-side accept kernel for the EAGLE-4
cycle; the measured standalone win is ~0.048 ms/cycle (0.03% of the ~162 ms cycle),
and the change would be redundant. Task #25's acceptance (AR-exact + measured
host-overhead/verify-cost drop) is already met by (a) graph verify, (c) device fc
projection, and (d/e) device head/draft. This records why (b) is deferred so it is
not re-investigated.

Measured accept/commit phase (`/tmp/eagle4_accept_profile.py`, 10 steady cycles,
n_draft=2, real Qwen3.8-27B-Q4_K_M, gfx1151):
- host accept prefix-match loop: 0.005 ms (nothing to move on-device).
- `_commit_verify_linear_state_row` call: 0.390 ms in-cycle.
- context: draft chain 39.3 ms, verify 110.7 ms, append ~12 ms.

Commit internals split (`/tmp/eagle4_commit_split.py`, stream idle, 50 reps):
- H2D of the single i32 row index k: 0.0478 ms.
- full commit call: 0.3121 ms (the rest ~0.26 ms is the fused
  `linear_state_pair_commit_chunked_i32` host launch + table-ensure check).

Why standalone device accept is not a coherent win: the fused commit ALREADY reads
the row index from a device i32 buffer (`_verify_linear_state_commit_row_i32_buf`);
the host only H2Ds k into it. A device accept kernel would remove that 0.048 ms H2D
but the host still needs k/bonus/tokens for output accounting, stop-check, and the
max_new_tokens budget (it already has them from `bres.token_ids`), so k would be
computed twice. Net ~0.048 ms for a new kernel + a verify-result device-token field
+ commit rewiring on a correctness-critical path. The MTP `device_graph_i32x2` is a
candidate-handoff format tied to MTP's CandidateGraph topology, not a lift-and-shift
accept kernel for EAGLE's prefix-match.
