# d8 host attribution: 45% of the decode step is HIP host time; logits D2H is 3.42 ms

## Summary

- Built `scratch/d8_host_attribution_probe.py` (D8's "measure host launch and
  synchronization gaps directly" requirement): wraps every `hip*` symbol at the
  `ctypes.CDLL.__getattr__` funnel and times each host call, wraps the engine's
  `_tick_once` / runner `decode_batch` for wall, and run-differences two
  `LLM.generate_detailed` runs (prefill+8 vs prefill+136 tokens) so the decode
  step separates from prefill in one instrument.
- Three ctypes findings had to be fixed for the probe to see anything: the
  wrapper must delegate `argtypes`/`restype` to the real `_FuncPtr`
  (`signed_kernel_fn` assigns them on whatever object it gets, and a plain
  function swallows that -> `c_float` conversion refused), the wrapper must be
  installed into `lib.__dict__` (ctypes stashes the first resolution there and
  later dict hits bypass `__getattr__` entirely), and `hipengine_*` kernel
  symbols need their own launch bucket (they contain no "Launch" substring).
- Measured per decode step at prompt 1024 (probe wall 16.47 ms; d7 census busy
  14.21 ms, d7 topline wall 15.92 ms): HIP host time is **7.37 ms = 45% of
  wall** over 1031.9 calls — 784 launches 2.53 ms (3.2 us each), 98
  memcpy-class 4.47 ms, 150 sync-class 0.37 ms.
- The memcpy-class cost is eight blocking `hipMemcpy` calls, named by caller:
  the full-vocab logits D2H at `gemma4.py:1133` is **3.42 ms/step on its own
  (21% of the step**, including the queue drain it forces), six
  `_stage_upload` H2D staging copies 0.55 ms, token-ids H2D 0.19 ms.
- D8's open question about "the 97 per-token rocclr copies/fills" is answered:
  those are the census's async `runtime_copy_fill` family (0.22 ms device) and
  are cheap on both sides. The host gap lives in the synchronous copies, not
  the census 97. Engine tick/decode_batch wrappers fire per-generate (2 ticks /
  1 batch per run), so those counters are published raw, not differenced.
