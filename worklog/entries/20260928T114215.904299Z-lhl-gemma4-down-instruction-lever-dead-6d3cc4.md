# removing half the dp4a buys 2.3 percent: the int8-unpacked layout is dead by direct experiment, and unrolling the row loop is 12 percent slower

## Summary

The previous entry bounded the int8-unpacked Q5_1 layout at 5.1 percent of the
down kernel by inference: dp4a is 57.3 percent of VALU issue, but VALU issue is
only 17.7 percent of the clock. That bound is now measured rather than argued.
The probe is the exact change the layout would make -- eight of the sixteen
`dp4a` per 32 values deleted from the high-bit chain, replaced with one integer
AND so the loop still consumes `w_hlo` -- run same-session against the
unmodified kernel:

| arm | ms/call | runs |
| --- | ---: | --- |
| baseline | 2.484 median | 2.479 / 2.525 / 2.484 |
| 8 of 16 dp4a removed (28.7 % of VALU) | **2.428 median** | 2.383 / 2.499 / 2.428 |

**2.3 percent for 28.7 percent of the VALU instructions.** The predicted ceiling
was 5.1 percent, so the bound holds and the measured effect is below it. The
probe output is wrong by construction and was reverted; only the timing is
evidence.

**This closes the instruction-count question.** The layout would cost 1.9 GB
resident plus a repacker, a new kernel variant, an oracle and loader wiring, to
buy 2.3 percent of one kernel that is 14 percent of the step -- 0.3 percent of
prefill. Not built, and no longer worth re-deriving.

## The second negative: the row loop must not be unrolled

The row loop is dynamic (`rcount`) and unrolled by neither the compiler nor the
source. Since the kernel is stall-bound, the obvious hypothesis was that
consecutive rows' loads cannot interleave. One line tests it:

```
#pragma unroll 2
for (int r = 0; r < rcount; ++r) {
```

**2.684 / 2.826 / 2.830 ms against a 2.479 / 2.525 / 2.484 ms baseline --
12 percent slower, same session.** The compiler's choice was right. Whether this
is the extra live `x_lo`/`x_hi` registers or the doubled accumulator pressure was
not separated, and does not need to be: the change is not a candidate.

## A measurement-discipline finding

The unmodified kernel measures **2.696 ms** in one session and **2.484 ms** in
another for identical code and arguments -- 8 percent drift, larger than any
effect measured this campaign. Every A/B here was therefore run with both arms
inside one session, three runs per arm. Results carried across sessions are
flagged as such, and the earlier `ROWS_PER_PASS` win, whose two arms were also
same-session, is unaffected.

**This also retracts a number the previous entry offered.** That entry decomposed
the kernel into a 0.584 ms fixed per-pass weight fetch plus 0.066 ms per row,
from a two-point fit at 16 and 32 rows. Re-measuring the row series in one
session does not support a fixed-intercept model:

```
rows/expert    8      16      24      32
ms/call      1.369   1.738   1.991   2.710
```

The marginal cost per row is 0.36, 0.25 and 0.70 microseconds across the three
segments -- non-monotonic by 2.8x, and the 8-row point is *faster* than the
4-row point despite doing the same 190.3 MB weight fetch. There is no stable
fixed term to attack, and the previous entry's 0.584 ms should not be treated as
a decomposed cost.

## Next

The dp4a probe says the kernel still takes 2.4 ms with **zero** of the high-bit
chain's instructions left, and 158 M of 221.4 M VALU remain -- 0.34 ms of issue
at peak. So roughly 2.1 ms is neither VALU issue, nor the dp4a count, nor DRAM
bandwidth (the kernel streams its weights at 333 GB/s where the same kernel at
`ROWS_PER_PASS` 16 saturates 527 GB/s). The remaining candidates are the two
memory-op groups in the row loop: two 16-byte activation loads and two scalar
scale reads per (row, sub-block), all broadcast across the block. The next probe
should delete the scale reads specifically, since they are the one group that a
contained change can remove -- all eight scales for a 128-wide group live in the
first 16 bytes of the block header and are currently fetched two at a time,
twenty-two times over.
