# Correct the bulk TP2 prefill divergence claim and fix the active-rows metadata

## Summary

Two results. First, the prior claim that the opt-in bulk TP2 prefill
divergence is "the known bulk-vs-serial T2 association difference ... not a
control/ownership defect, proven by near-matching argmax" was unjustified and
is retracted: matching argmax on 127/128 rows does not establish the absence of
an ownership/control defect, and the heldout "token-serial max KL below 0.05"
is one of five envelope metrics, not proof the heldout gate passes (the heldout
bulk arm fails four of five). Second, a bounded investigation found and fixed a
real control/metadata defect (the capacity-sized bulk scratch was handed to the
full-attention prefill helper, which derives its row count from
``scratch.rows``) and then localized the first numerical divergence: the
**layer-0 linear-attention output** differs by 0.52% (max_abs 0.25, same
argmax) between the bulk prefill helper and the token-serial decode helper even
though the layer-0 GDN conv state is bit-identical and the recurrent state
matches to 3.2e-7. The post-attention norm (0.147%) and the sharded MLP (0.63%)
only amplify it. The divergence is therefore a GDN output-kernel arithmetic
difference, not the MLP batching, not the norm, and not an ownership defect.

## Changes

- `hipengine/distributed/tp2_generate.py`
  - `_bulk_attention_layer` / `_bulk_norm_residual_layer` /
    `_bulk_sharded_mlp_layer` now read `self._bulk_chunk_scratch[device]`.
  - `bulk_prefill` narrows the capacity-sized bulk scratch to the active
    prompt rows with `for_chunk(0, rows, rows, runtime=..., stream=...)` once
    per rank before the layer loop, exactly like the resident bulk caller.
    `_GGUFFullAttentionPrefillScratch.allocate` leaves `scratch.rows` at the
    capacity and never calls `for_chunk`, while
    `_run_full_attention_prefill_attn_rows` has no explicit `rows` argument and
    reads `rows = scratch.rows`. Without the fix a 64-token prompt on a
    200-row capacity ran the full-attention layers at 200 rows and wrote KV for
    200 positions. `close()` clears the new dict.
- `tests/test_unit_distributed_tp2_generate.py`
  - `RunnerSpy` records `prefill_attn_scratch_rows` / `prefill_attn_rows_arg`;
    `FakeBulkScratch.for_chunk` records `bulk_for_chunk_calls`.
  - New RED-then-GREEN tests `test_bulk_prefill_sets_the_active_chunk_metadata`
    and `test_bulk_full_attention_uses_the_active_prompt_rows`.
- `scripts/tp2_bulk_prefill_first_divergence.py` (new, diagnostic only)
  - Compares bulk vs token-serial TP2 at prefill end, captures the GDN
    conv/recurrent state and the full-attention KV cache per layer, and can
    capture the layer-0 attention output and sharded-MLP input/output. Also has
    `--mlp-per-row` to force the bulk sharded MLP through the same group one row
    at a time.
- `scripts/tp2_bulk_prefill_diagnostic.py`: `--bulk-capacity` override.

## Validation

- RED: `HIP_PATH=/opt/rocm python3 -m pytest
  tests/test_unit_distributed_tp2_generate.py -q -k "active_chunk_metadata or
  active_prompt_rows"` failed with `assert [8, 8, 8] == [4, 4, 4]` (capacity
  8 vs active 4). GREEN after the fix; full file 50 passed.
- The metadata fix does **not** change the failing-prompt logits: the
  diagnostic with `--bulk-capacity 64` produced byte-identical logits to the
  capacity-200 run (`logits_sha256
  7b5fc4e643ef9759c115b03e39c8933e2ff51da1274a47810814f2aef075e3e9`, max_kl
  0.48714). So it is a genuine control/metadata defect, but not the cause of
  the regression.
- First divergence, `HIP_VISIBLE_DEVICES=0,1 HIP_PATH=/opt/rocm python3
  scripts/tp2_bulk_prefill_first_divergence.py --prompt mixed_ja_en_translate
  --capture-mlp --json /tmp/tp2_attn.json`:
  - prefill end (bulk vs serial): kl 7.89e-05, top1 1.0, argmax 332 both.
  - `L0.conv` max_abs 0 (bit-identical), `L0.recurrent` max_abs 8.58e-06
    (rel 3.19e-07); `L1.conv` rel 3.92e-03, `L1.recurrent` rel 5.25e-03;
    `F3.key`/`F3.value` first-64-position rel ~5.4e-03, growing to ~1.9e-02 by
    `F63`. (The KV tail beyond position 64 is uninitialized NaN bit patterns in
    both routes and was excluded.)
  - layer 0 `attn_out` rel 5.21e-03 (max_abs 0.25, argmax 3994 both); layer 0
    post-attention norm rel 1.47e-03; layer 0 sharded-MLP output rel
    6.29e-03.
- Not the MLP batching: `--mlp-per-row` gave the same layer-1 divergence
  (`L1.conv` rel 3.92e-03, `L1.recurrent` rel 5.23e-03 vs 5.25e-03 batched).
  Both bulk variants use `_bulk_shard_group`, so the first differing primitive
  is upstream of the MLP.
- Envelope unchanged; the path stays opt-in/default-off. No threshold relaxed,
  no prompt/token special case, no serial-denominator substitution.

## Next

- Compare the resident TP1 bulk's layer-0 `attn_out` against the resident TP1
  serial `attn_out` on the same prompt. If the resident shows the same ~0.5%
  GDN output difference, the divergence is inherent to the prefill-vs-decode
  GDN output kernels (a T2 association fact, and the bulk route cannot be
  promoted on this prompt without a GDN output kernel that is
  decode-order-exact). If the resident matches, the ~0.5% is a TP2 bulk wiring
  or kernel-argument defect and is the next thing to fix.
- Do not launch the D128 suite and do not promote the bulk route until the
  heldout prompt clears the full five-metric envelope that token-serial already
  clears on max_kl.
