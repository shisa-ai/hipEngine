# The prefix-checkpoint store: token-keyed with block-id validation

## Summary

Task #21 unit 1b, first half. The design entry left the checkpoint's storage
home open with a recommendation (a side table keyed by radix node block ids,
evicted with the node). Implementing it changed the key, and the reason is worth
recording: **a radix block id is not stable content.** The allocator hands a
freed id to different tokens, so a table keyed on ids alone can hand a row a
checkpoint that describes a prefix it never ran. The store therefore keys on the
**token prefix** and treats the block ids as a **validation**:

- a token hit whose ids match is a hit;
- a token hit whose ids differ is a **miss**, and the entry is dropped, because
  the id it recorded has been reused and it can never be validated again;
- a token miss is a miss regardless of ids.

The second deviation from the recommendation is lifetime: attaching device
buffers to radix nodes would put ownership of memory the cache never allocates
inside the cache. The store instead holds an explicit `release` callback and
calls it exactly once per entry it drops -- on overwrite, LRU eviction, `drop`,
`clear`, or a block-id mismatch -- with a per-entry flag making a double drop
harmless rather than a double free.

Capacity is bounded and an evicted entry is not a correctness problem: the row
falls back to autoregressive decoding, which is what every prefix-hit row does
today. That is why an LRU cap is an acceptable answer to "the radix tree never
told us it evicted": being wrong costs a slower row, never a wrong one.

`PrefixCheckpointStore` is deliberately payload-agnostic. It stores whatever the
provider hands it and calls the callback it was given, so the provider keeps
ownership of its own buffer layout and the store never learns it.

## Validation

`tests/test_unit_speculative_prefix_checkpoint_store.py` pins the three
properties that make the store safe to hand a row device state:

- **a reused block id is a miss, not a wrong checkpoint** -- same ids with
  different tokens finds nothing, and the same tokens with different ids misses
  *and* releases the entry, because that id can never be validated again;
- **every dropped payload is released exactly once** -- the recorder rejects a
  double release, and the tests cover overwrite, LRU eviction, `drop`,
  `drop_missing`, `clear`, and the mismatch path, plus a zero-capacity store
  that releases immediately so a caller keeps one code path when caching is off;
- **capacity is a bound** -- the least recently used entry is evicted and
  released, and a `get` is what makes an entry recently used (the test asserts
  the eviction order after a read, not just the insertion order).

Also pinned: an empty prefix or block list is refused, a negative capacity or
missing release callback is refused, and `stats()` accounts for every decision
(stored, hits, misses, block-id mismatches, evicted, replaced, released).

## What this does not do

The store has no caller yet, exactly as the checkpoint blob did not: the capture
hook that fills it and the lookup that reads it are the other half of unit 1b
and unit 2. Committing it now is deliberate rather than incidental -- the
keying decision is the part that is expensive to change later, and it is the
part the design left open.
