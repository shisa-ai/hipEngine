# The U6 certification now names its own artifact-scoped strict manifest

## Summary

`docs/UD-GFX1151-OPTIMIZE.md` item "Explicit artifact-scoped strict manifest" was
open. The U6 certification artifact recorded rates and exactness for `ud-q4-k-m`
and `ud-q4-k-s` but did not name the strict execution-profile variant set behind
those numbers, so its strict claim was only checkable with external context. The
scope is now derived from two sources of truth and stamped into the artifact.

## Changes

- `scripts/ud_strict_manifest.py` — derives the strict scope from the artifact's
  own GGUF tensor types (`GGUFReader`) intersected with the admission table's
  `source_ggml_types`, builds one strict manifest per (registry quant, owner
  class), verifies every named variant against the live registry, writes one file
  per artifact, and stamps the bundle into the certification. `--check`
  re-verifies the checked-in files.
- `benchmarks/results/ud-q4-k-m.strict-manifest.json`,
  `benchmarks/results/ud-q4-k-s.strict-manifest.json` — new.
- `benchmarks/results/ud-mtp-certification-u6.json` — both artifact entries now
  carry `strict_manifest_bundle_sha256`, `strict_manifests` and
  `strict_manifest_scope`.
- `tests/test_ud_strict_manifest.py` — new, 5 tests.
- `docs/UD-GFX1151-OPTIMIZE.md` — item closed with the derivation and the
  constraints that forced the bundle shape.

## Decision

The scope comes from the artifact's GGUF bytes and `CERTIFIED_OPERATION_COVERAGE`,
not from a hand-written list, so it cannot drift from either.

Three schema properties forced the bundle shape rather than one flat manifest, and
each surfaced as a hard error first:

- The manifest keys selections by `(layer, scope)`, but the admission table
  carries several registry quants under one `(layer, scope)` —
  `dense_gemv/prefill_rows` is both `bf16` and `f32`. So the bundle holds one
  manifest per registry quant.
- Within a quant, `linear/prefill_rows` in `gguf_q5_k` carries both the dense
  owner `gemv_bf16_bf16_out` and the selected-row owner
  `selected_gemv_bf16_bf16_out`. So the bundle also splits by owner class.
- Within `(layer, scope)` the table lists one owner per output dtype, because the
  F32-logits comparison surface needs an f32-output variant of the same kernel.
  The selection is the serving owner (no `f32`/`fp16` token) and the alternates
  are recorded in `alternate_output_dtype_owners` rather than dropped.

Records with `consumer_module` set are certified by a symbol in that module rather
than by a registry key, so they contribute provenance (`consumer_modules`) and
cannot be selections.

## Validation

```
HIP_VISIBLE_DEVICES=1 python3 scripts/ud_strict_manifest.py \
    --artifact ud-q4-k-m --artifact ud-q4-k-s \
    --output benchmarks/results/ud-mtp-certification-u6.json
HIP_VISIBLE_DEVICES=1 python3 -m pytest tests/test_ud_strict_manifest.py -q
```

5 tests pass. They validate every manifest with the profile gate's own
`validate_variant_manifest`, check every named variant against the live registry,
re-derive the GGML types and in-scope record count from the GGUF bytes, and assert
the certification's bundle hash matches the manifest file.

## Next

The bundle scopes the strict claim; it does not by itself re-run the profile gate.
Wiring `strict_manifest_bundle_sha256` into an admission pin, and the
separately-tracked 4096/32768 context coverage, remain open.
