# Surya vision attention tiled; context/output/memory budgets wired through the generator

## Summary

Three defects in the Surya HIP path, all confirmed before the fix:

1. **Vision attention materialized the full score matrix.** `_vis_scores`
   allocated `vision_num_heads * n^2 * 4` bytes for `n` unmerged patches — 805 MB
   for the 4096-patch fixture, **56.5 GB for a 300-DPI A4 page** (220x156 grid,
   34320 patches) and **206 GB at the checkpoint's `SURYA_MAX_PIXELS` ceiling**
   (256x256, 65536). Admission rejected the A4 page by 13x, so a routine
   document could not run at all.
2. **The registered generator discarded capacity configuration.**
   `make_surya_generator_gpu` took `**_kwargs`, and
   `LLM._factory_capacity_kwargs` forwards a limit only to a factory that
   declares it by name. `LLM(max_sequence_length=...)` was therefore silently
   dropped and the runner stayed at its low-level 2048 default. A 300-DPI A4
   page alone is 8580 image tokens, so every real document failed the context
   check — and the check happened even though the limit could not be raised
   through the public path.
3. **The text-prefill memory envelope was unknown.** The text prefill still
   materializes a full causal score matrix, and nobody had measured what that
   costs at page scale.

The generator now defaults to a 16384-token context (upstream Surya budgets
12,288 context tokens per OCR slot and 18,000 for vLLM), and the vision score
tile, the text context, and the output budget are all explicit, validated, and
advertised.

## Changes

**`hipengine/runtime/surya.py`**

- `plan_vision_attention(n_patches, num_heads, budget_bytes)` returns
  `(query_block, scratch_bytes)`: the largest query block whose tile
  (`num_heads * n * block` fp32 elements) fits the budget. `None` disables the
  budget and returns one dense tile. A budget below one query row still returns
  `block == 1` so admission can report the shortfall instead of emitting an
  unusable plan.
- `_vision_attention_packed` walks the score matrix one query tile at a time.
  Each tile holds the **full key range** for its queries, so the softmax rows
  are exactly the rows the dense path computed; the tiles partition the queries,
  not the image, and the result is unchanged. Per tile: one strided-batched SGEMM
  `K^T @ Q_blk`, the existing scale and `evie_softmax_rows_f32` kernels, then one
  strided-batched SGEMM `V @ P`. The final partial tile packs tighter
  (`tokens * bq`) than the largest one, so no scratch element is read without
  having been written by that tile.
- `_vis_score_stride` (quadratic, 16-byte aligned) is replaced by
  `_vis_tile_elements(n, block) == n * block`; `_vis_scores(n, heads, block)`
  allocates `heads * n * block * 4`.
- `vision_block(grid_thw)` and `vision_scratch_bytes(grid_thw)` both derive from
  `plan_vision_attention`, so admission and allocation cannot disagree.
  `check_vision_capacity` now rejects only a grid whose *one query row* exceeds
  the budget (with the required value in the message) plus the free-memory
  check; it still runs before any device work.
- `DEFAULT_MAX_VISION_SCRATCH_BYTES` is now the **tile** budget, 512 MiB (was a
  4 GiB cap on the dense matrix). `DEFAULT_MAX_SEQ = 16384` is the generator's
  default context. The constructor validates both (`max_seq > 0`,
  `max_vision_scratch_bytes > 0` when set).
- The module docstring no longer claims the vision tower is a host-side
  follow-up; it runs on the device.

**`hipengine/generation/surya_gpu.py`**

- `SuryaOCRGeneratorGPU(max_seq=None, max_vision_scratch_bytes=None)` resolves
  `None` to `DEFAULT_MAX_SEQ` / the runner default, validates both, and keeps
  advertising `max_seq` and `max_vision_scratch_bytes` for pre-admission.
  `None` at this layer means "use the runner default", because the runner reads
  `None` as "no budget"; only an explicit value is forwarded.
- `make_surya_generator_gpu` declares `max_sequence_length` and
  `vision_max_scratch_bytes` (plus `vision_model_path`) instead of `**_kwargs`,
  so an unknown keyword is now a `TypeError` rather than a silent drop.
- Both `check_prompt_capacity` calls pass a hint naming the knob to raise.

**`hipengine/generation/surya_contract.py`** — `check_prompt_capacity` takes an
optional `hint` appended to the failure message.

**`hipengine/llm.py`** — `LLM(vision_max_scratch_bytes=...)`, validated, and
`_factory_capacity_kwargs` forwards it to factories that declare it. Other
factories are unaffected because the helper only forwards declared names.

**`scripts/surya_attention_memory.py`** (new) — emits the vision tile plan for
the A4 and `SURYA_MAX_PIXELS` grids and measures text-prefill peak memory. The
prefill measurement uses a fresh runner per token count with
`reset_memory_stats()` after construction, because the peak counter is
process-global and a reused runner would carry the previous size's high-water
mark into the next row.

## Validation

RED first, against the unmodified code: 5 new pure tests in
`tests/test_surya_generation_contract.py` failed on `plan_vision_attention` not
existing and on `max_sequence_length` not being a declared factory parameter
(the failure message printed the old `**_kwargs` signature). 5 new/updated GPU
tests failed on `_vis_scores` arity, on the A4 grid being rejected, and on the
2048-token default. Then the implementation, then GREEN.

Tiling is exact, not approximately exact. On the 4096-patch page under an 8 MiB
budget the plan gives `block = 42`, i.e. 97 full tiles plus a 22-query partial
tile: the tiled result matches the **dense GPU** result at `max|d| < 1e-4` and
the torch fp32 oracle at `max|d| < 2e-3` / `mean|d| < 1e-5`, the same gates the
dense path is held to. The non-square 22x12 and 12x22 grids (where a row/column
mix-up in the block offset would show up) match the CPU reference under a 2 MiB
budget.

Memory, from `scripts/surya_attention_memory.py` on gfx1151 (Radeon 8060S,
Ryzen AI Max+ Pro 395), budget 512 MiB:

| grid | patches | dense score | query block | tiled score | reduction |
| --- | --- | --- | --- | --- | --- |
| 220x156 (300-DPI A4) | 34320 | 56.54 GB | 325 | 535.39 MB | 106x |
| 256x256 (`SURYA_MAX_PIXELS`) | 65536 | 206.16 GB | 170 | 534.77 MB | 386x |

Text-prefill peak at `max_seq` 16384, measured (not extrapolated) at each size:

| tokens | attention scores | non-attention | peak total |
| --- | --- | --- | --- |
| 2048 | 134.2 MB | 379.4 MB | 3.60 GB |
| 8580 (300-DPI A4) | 2355.7 MB | 1588.4 MB | 7.03 GB |
| 16384 | 8589.9 MB | 3032.9 MB | 14.71 GB |

Non-attention scratch fits 180.8 KiB/token across every size; the score term is
exactly `8 * tokens^2 * 4`. Resident at `max_seq` 16384 is 3086 MB (2663 MB
fp32 weights, 403 MB KV planes, 20.7 MB GDN/conv state).

Public-path integration, not just the factory signature:

```
LLM('datalab-to/surya-ocr-2', backend='hip_gfx1151',
    max_sequence_length=16384, vision_max_scratch_bytes=64*1024*1024)
  -> generator max_seq 16384, max_vision_scratch_bytes 67108864
LLM('datalab-to/surya-ocr-2', backend='hip_gfx1151')
  -> generator max_seq 16384, max_vision_scratch_bytes 536870912
```

## Next

- The text prefill still materializes `8 * tokens^2 * 4` causal scores
  (8.59 GB of the 14.71 GB peak at a full 16384-token prompt). Tiling it needs
  the same treatment as vision plus a query offset in
  `surya_causal_mask_scale_f32`, because the causal mask is relative to the
  tile's first query. Recorded in `docs/REFACTOR.md`; the measured envelope is
  in `docs/MODEL-SURYA.md`.
- `SURYA_MAX_PIXELS` now admits the 256x256 grid on memory grounds, but that
  grid is 1.6e14 FLOPs of vision attention — the ceiling is compute-bound, not
  memory-bound. No compute-time admission exists.
- `max_seq` 16384 is a default, not a measured optimum. The KV planes cost
  24.6 KiB per context token (403 MB at 16384); a smaller default would trade
  document reach for resident memory.
