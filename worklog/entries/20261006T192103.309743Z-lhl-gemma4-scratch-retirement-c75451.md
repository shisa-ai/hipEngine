# Retire superseded attention scratch behind stream events

## Summary

The deep-context allocation defect is fixed. `Gemma4AttentionScratch` grew its
per-stream workspace by doubling and retained every superseded allocation until
`close()`, so a deep prefill held the whole doubling chain for its entire run:
the 2026-10-02 tier-1 capacity run measured 32.5 GiB of retained depth
transients and a 113.05 GiB resident-plus-transient peak at context 262144.
The scratch now retires each superseded buffer behind a stream event recorded
after its last queued user and reaps it once the device passes that event, so
queued kernels keep valid pointers exactly as before while the old allocation
is freed within a later request instead of living until close.

Measured after the fix (probe run through the repaired in-flight
`scripts/gguf_capacity_probe.py`, whose depth rehearsal drives 7,710 workspace
requests through the real scratch owner): retained transients are 16.54 GiB --
one buffer at the largest doubled capacity (workspace 16.03 GiB + keep-mask
0.50 + rope 0.006) -- and the resident-plus-transient peak is 97.57 GiB,
15.5 GiB lower than the 113.05 GiB recorded on 2026-10-02. That before-number
comes from the prior probe version, so the peak delta is cross-version; the
like-for-like evidence is the walk's own retained bytes, which now equal a
single doubled buffer rather than the doubling-chain sum. At context 33024 the
production bench's device memory after runs drops 39.81 -> 37.87 GiB. The
262144 probe passes with finite logits. The production 32768 prefill metric
holds (350.59 tok/s vs 351.18, -0.17%, inside the 0.03-0.4% same-tree spread
observed in this loop), so the fix is performance-neutral as expected for an
allocation-lifetime change.

A PV-stage address-hoist attempt made in the same iteration (stepping a V tile
pointer instead of recomputing `j * v_stride + d` per key, hoisting the
dimension predicates) measured 348.42 tok/s -- metric-neutral -- and was
reverted rather than kept as unearned churn; the compiler evidently already
strength-reduces that address stream.

## Changes

- `hipengine/core/hip.py`: `HipRuntime.event_query` (hipEventQuery;
  `hipErrorNotReady` treated as a poll result rather than a failure) with its
  prototype registration and a named constant.
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention.py`:
  `Gemma4AttentionScratch` gains `_pending` retirement parking plus
  `_retire`/`_reap_pending`; `buffer` and `named_buffer` reap on every entry
  and retire the previous buffer on growth; `close` synchronizes the pending
  streams too and drains them. Growth still doubles; only the lifetime changed.
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention_staged.py`: the
  workspace-ownership docstring states the new semantics.
- `tests/test_unit_gemma4_attention_scratch.py`: event-aware mock runtime and
  the retirement/reap contracts (parked-not-freed, reaped after the device
  passes the event, only the current buffer left once the stream quiets).
- `tests/test_unit_gemma4_runner_lifecycle.py`,
  `tests/test_unit_gemma4_decode_graph_workspace.py`: their mock runtimes gain
  the event trio; the decode-graph reservation test stays green with
  event-query answered False so nothing reaps during capture.
