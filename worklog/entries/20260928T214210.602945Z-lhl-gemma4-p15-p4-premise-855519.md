# Gemma 4: settling P4's premise — gate_up is compute-bound, not bandwidth-bound

## Summary

`moe.gate_up` is **114.1 ms, 25.3% of a 451 ms prefill at 1024** and 457.4 ms,
13.7% at 4096 — the highest item that ranks top-four on both prompts. P4 asks
for larger int8 MMQ tiles, but the punchlist's own dead-ends note carries a
warning that had to be resolved before any kernel work:

> **P4 assumes rows-per-expert matters, and iteration 126 refuted that** for
> the current owner: the MoE is bandwidth-bound... P4's premise is tile shape
> and occupancy against llama.cpp's `mmq_x=64`, which is a different claim —
> but state which one the change rests on.

This entry states which one. **It is tile shape and occupancy. gate_up is
compute-bound**, and iteration 126's bandwidth conclusion does not transfer
to it.

## The arithmetic

Model dimensions from `docs/campaigns/GEMMA4-26B-A4B-OPTIMIZATION.md`: hidden
2816, `moe_intermediate_size` **704**, 128 experts. Per prefill at 1024 the
census reports 58 launches (29 MoE layers x 2 blocks of 512), 4096 routed rows
per block, and 114.1 ms for gate_up / 47.6 ms for down.

| | FLOP | time | rate | vs 75.3 TOPS |
| --- | ---: | ---: | ---: | ---: |
| `moe.gate_up` | 1.884 TFLOP | 114.1 ms | **16.51 TFLOP/s** | **22%** |
| `moe.down` | 0.942 TFLOP | 47.6 ms | 19.79 TFLOP/s | 26% |

`docs/ROOFLINE.md` line 167 records **INT8 WMMA measured at 75.3 TOPS**
(`torch._int_mm`, 61% of the 123 TOPS spec). P4's row puts llama.cpp at about
**33 TFLOP/s** on the same work — 44% of the same peak. So the gap P4 claims
is real: **2.0x behind llama.cpp, 4.5x behind the measured kernel peak.**

| | bytes | rate | vs 864 GB/s |
| --- | ---: | ---: | ---: |
| gate_up weights (Q4_K, ~0.57 B/weight) | 8.39 GB | 73.5 GB/s | **9%** |
| down weights (Q5_1, ~0.69 B/weight) | 5.08 GB | 106.7 GB/s | 12% |

**Arithmetic intensity = 224.6 FLOP/byte against a ridge point of 70.9
FLOP/byte** (864 GB/s into 61.3 TFLOP/s FP32, `docs/ROOFLINE.md` §ridge). At
3.2x the ridge point the roofline says compute-bound, and the bandwidth
number agrees independently: gate_up pulls only **9% of peak memory
bandwidth** while sitting at 22% of peak INT8. Nothing about this kernel is
waiting on DRAM.

Two further corroborations, neither dependent on the byte estimates:

- **The time ratio is the tell.** gate_up/down is 2.40 in time, but only
  2.00 in MACs and 1.65 in bytes. gate_up is disproportionately slow *for its
  own arithmetic*, which is what a tile-shape defect looks like and is not
  what a bandwidth limit looks like.
- The 16.51 TFLOP/s figure uses only dimensions, the census time and a FLOP
  count — no byte or precision assumptions — so it is exact.

**Which claim P4 rests on:** tile shape and occupancy (`mmq_x=64`, I = 64, one
launch across experts), **not** rows-per-expert reuse. Iteration 126 refuted
the latter and stays refuted; this measurement is about a different mechanism
and does not reopen it.

## Why this is not a free win either

The dead-ends table also records iterations **101, 102, 112 and 131 —
expert-grid retune, wider out-blocks, an occupancy ladder — as neutral or
refuted**, and iteration 142's int8 MMQ leaf for the MoE down at 8.2x slower.
So the neighbourhood has been walked. What none of those tested is P4's
actual change: a different tile geometry (`mmq32` -> J = 64) rather than a
retune of the existing one. That distinction is the same one the dead-ends
note draws, and it is now backed by the roofline rather than by assertion.

An honest ceiling: taking gate_up from 22% to llama.cpp's 44% of peak is
**2x on this kernel, ~57 ms, ~13% of a 1024-prefill**. Reaching the full 4.5x
would be ~89 ms. P4's "up to ~63 ms" sits inside that range and is not
optimistic.
