# Refuted: eliminating the redundant per-step condition upload is neutral; the H2D copies were never the cost, the D2H is

## Summary

`20260915T205121.492340Z` measured 78 host/device copies per diffusion frame and found
that the gaps *after* a copy average 84.4 us (vs 7.0 us after a compute kernel),
totalling 6.50 ms/frame of GPU idle. The obvious cheap reading was: some of those
copies are redundant, so delete them.

I found a genuine redundancy -- `VibevoiceTTSDiffusionHeadGPU.forward()` uploads the
**condition** on every call (line 189), and the solver passes the *same* condition for
all 20 steps, so it is uploaded 20x per frame and ~500x per request -- implemented the
memoization, and measured it.

**It is neutral: 0.9967x (-0.150 ms/frame, -3.8 ms/request, ~-0.09% of warm).** The
change was reverted. The measurement refutes the copy-elimination route and, more
usefully, narrows the 84 us stalls to the **D2H** specifically.

## Changes

None retained. The edit was applied, measured, and reverted; the working tree is clean
(`git status --porcelain` on the file is empty) and the diffusion tests still pass.

## Validation

### The redundancy is real

`forward()` issues four copies per call (78 / 20 steps = 3.9, consistent with the
trace):

- L175 H2D `x_rows` -- changes every step
- L183 H2D `t_freq_rows` -- recomputed every step (timestep differs)
- **L189 H2D `cond` -- byte-identical on all 20 steps**
- L239 D2H `eps` -- the readback

So the condition upload is 19 of 20 copies that could be skipped. The implementation
memoized the previous upload and re-sent only when `np.array_equal` failed.

### Correctness held

`python3 -m pytest tests/test_live_vibevoice_tts_diffusion_gpu.py` -- 5 passed, exit 0,
including `test_gpu_diffusion_replay_parity[single|two]` and
`test_gpu_head_step0_matches_cpu_reference`. Skipping the copy is bit-exact because it
is taken only when the bytes are identical.

### It does not help -- measured in-process A/B

Cross-process comparison was unreliable (46.297 ms/frame vs the traced 43.95 ms span,
which is not an apples-to-apples baseline), so I forced the upload on and off *within
one process* by patching `np.array_equal` to return `False` for the "old" arm:

```
upload cond every step : 47.366 / 45.668 ms/frame  -> best 45.668
memoized cond          : 45.818 / 46.287 ms/frame  -> best 45.818
=> 0.9967x  (-0.150 ms/frame, -3.8 ms/request)
```

Two runs per arm, best-of-7 each. The effect is inside run-to-run variance.

### Why -- and what it tells us

The 84.4 us mean gap after a copy is **not** a property of copies in general:

- An **H2D** (`hipMemcpy` host->device) completes as soon as the bytes are written.
  The host blocks for microseconds, so removing 19 of them changes nothing -- which is
  exactly what the A/B shows.
- A **D2H** must wait for every previously enqueued kernel to drain before it can
  return. The host blocks for the full remaining device time, and only then does the
  solver's numpy step run, so the GPU sits idle.

Therefore the ~6.5 ms/frame of copy-induced idle is **essentially all D2H**, and the
only way to remove it is to stop needing `eps` on the host -- i.e. move the solver step
onto the device. Deleting H2D copies cannot recover it.

### Why the change was reverted rather than kept

The tree's guidance is that H2D/D2H count reductions are retainable even when the
headline ratio is flat. I did not apply that here because the reduction is not
established as a win by any measurement: 0.9967x is inside the noise band of this
harness, and keeping it would add mutable state (`_cond_uploaded`) to a hot-path class
whose invalidation depends on content comparison. That is exactly the kind of
unproven-path-plus-state that `docs/REFACTOR.md` exists to track, so the honest action
is to revert and record, not to bank a neutral edit as a "win".

## Next

Unchanged from `20260915T205121.492340Z`, but now better targeted: **move the DPM solver
step to the device so `eps` never leaves the GPU.** That removes the 20 D2H readbacks
per frame and the ~6.5 ms/frame of idle they cause (~162 ms, ~4.1% of warm), plus the
host numpy solver time. Copy elimination is off the table as a route.

This remains the only well-evidenced opportunity above 1% of warm, and it still does
not approach 2x.
