# RETRACTION: the GD-4 state-drift screen modelled gated linear attention, not the gated delta rule

## Summary

GD-4's prescribed state-drift screen, reported earlier this session as passing at 1.106e-07
state NMSE, **modelled the wrong recurrence**: the script computes gated *linear* attention,
while GDN is the gated *delta* rule. Measured against the real oracle the two differ by
**NMSE 1.009735e+00** — 100% of the signal magnitude. The screen is retracted in full, the
ledger cell, artifact README and changelog carry the retraction, and GD-4's numerical screen
is **not done**.

## What is retracted

`worklog/entries/20260930T155056.069340Z-lhl-qwen4exp-gd4-chunk-scan-drift-8f19a4.md` reports
that GD-4's prescribed state-drift screen **passes**, with state NMSE 1.106e-07 flat in chunk
size, no tail penalty, no compounding over the prompt, and a 1.3x cost for fp16 intra-chunk
accumulation.

**All of those numbers are invalid. The screen modelled a different recurrence.**

`scripts/qwen4exp_gdn_chunk_scan_drift_screen.py` computes:

```python
state = gate[t] * state + kk[t][:, :, None] * v[t][:, None, :]
out[t] = q @ state
```

That is **gated linear attention**. GDN is the gated **delta** rule. The production kernel
(`qwen4_exp_gdn_prefill_f32_kernel`) computes:

```c
memory = sum_c key[c] * k_scale * S[c][v] * decay;
delta  = (v_in - memory) * beta;                     // <-- the delta term
S_next = S[c][v] * decay + key[c] * k_scale * delta;
core   = sum_c query[c] * q_scale * S_next[c][v];
```

The screen **has no `beta` term at all** — its signature is `chunked(q, k, v, gate, chunk,
...)`, and its reference `sequential(q, k, v, gate)` likewise. It never subtracts the state's
own prediction from `v`.

## Proof, measured not argued

On identical random inputs at the model's shape (Hk16/Hv48/Dk=Dv=128, 64 tokens, beta in
[0.1, 0.9], decay in [0.7, 0.999]), comparing the screen's `sequential` against the real
oracle `hipengine.kernels.cpu_reference.gdn_prefill_recurrent_segments`:

| | value |
| --- | ---: |
| NMSE(screen, oracle) | **1.009735e+00** |
| screen out RMS | 1.505106e-02 |
| oracle out RMS | 8.277325e-03 |
| max abs difference | 8.345179e-02 |
| oracle max abs out | 7.590295e-02 |

**The two recurrences differ by 100% of the signal magnitude.** The mismatch is present from
the first token: at `t=0` with `S=0` the delta rule writes `beta*v` (mean beta 0.5388) where
gated linear attention writes `v`.

## What survives

- **The methodological finding.** The script's own f32-reassociation control caught a
  formulation bug in the script — out NMSE was identical across all three variants at each
  chunk size while the control showed state NMSE 8.7e-13, which is only possible if the
  discrepancy is structural. That control did its job. It simply could not catch *this* bug,
  because the control compared against the same wrong reference: a control validates the
  implementation against its own specification, not the specification against the problem.
- **The general fact** that pure f32 reassociation of a chunked linear-attention form sits at
  fp32 round-off (1.9e-13 … 1.5e-11). That is a property of reassociation, not of GDN.

## What the correct screen requires

The triangular/WY form the row's reference uses:

```text
delta[t] = beta[t] * (value[t] - P[t]*key[t]@H0 - sum_{s<t} R[t,s]*(key[t]@key[s])*delta[s])
out[t]   = P[t]*(query[t]@H0) + sum_{s<=t} R[t,s]*(query[t]@key[s])*delta[s]
H1       = P[last]*H0 + sum_s R[last,s]*outer(key[s], delta[s])
```

This is already implemented and validated in
`hipengine.kernels.cpu_reference.gdn_prefill_chunkwise_wy_segments` (algebraically equal to an
independent token-serial f64 definition at chunk sizes 1/2/3/8/16 plus a 17-token tail), and
it has **no GPU implementation anywhere in the tree**. The only in-tree model-level evidence
about this form is **GPF-8's KL 0.056522 at FP32 with the kernel byte-exact at one token**.

## Why this is worth recording rather than quietly fixing

A wrong screen is worse than no screen: it converted GD-4's largest open risk from "unknown"
into a false "passed", and on that basis this session was about to justify a large kernel
build. **The error was not in the arithmetic of the script but in the specification of the
problem** — the same class as the `candidate_dispatch_calls: 0` counter, the DP-8 launch
counter, and the GPF-8/X-1 already-settled rows. In each case the instrument was the defect.

## Scope and limits

- The comparison above is on synthetic random inputs at the model's shape, not on real
  activations. It establishes that the recurrences are different, which is a structural fact
  and does not depend on the input distribution.
- No kernel was written, no performance claim, no default changed.
