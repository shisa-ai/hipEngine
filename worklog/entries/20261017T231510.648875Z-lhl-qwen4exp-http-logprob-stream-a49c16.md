# Enable resident HTTP logprobs without dropping UTF-8 fragments

## Summary

HTTP completion and chat streams can use resident Flash-Next target logprobs without full-response buffering. Task 20 remains open; live hardware validation and the remaining stop/tool/direct-provider paths are not qualified by these CPU tests.

## Changes

- The resident runner declares `supports_stream_token_logprobs`; `SubmitPollTextGenerator` resolves the capability from the active runner, not the direct provider. A unit test verifies ownership and disabling the runner capability.
- Both single-response HTTP loops retain logprob records from empty-text chunks until the next decoded text delta. This preserves byte-fallback records while the native decoder withholds incomplete UTF-8.
- HTTP tests now exercise the actual `EngineService` owner instead of the buffered direct provider. Streaming logprob cases require multiple payloads; ten completion/chat tests compare blocking and streaming text, byte records, candidates, generated IDs, usage and semantic finish at lengths 1/2/3/4/7.
