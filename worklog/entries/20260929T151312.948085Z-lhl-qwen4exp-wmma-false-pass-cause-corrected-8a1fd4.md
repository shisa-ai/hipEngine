# Corrected: the wmma false pass is not caused by the dispatch key

## Summary

Supersedes the causal claim in
`worklog/entries/20260929T145430.832594Z-lhl-qwen4exp-wmma-route-false-pass-ad392f.md`.
That entry named the dispatch memoization key as the **verified** cause of the
`wmma` route's false pass. **That was wrong.** The entry itself is immutable and
stays; this is the correction.

The defect is real and unchanged: `--route wmma --layers 16-47` at HEAD returns
identical candidate/teacher logits hashes, KL exactly `0.0` on every statistic,
and `status: complete` with `measurement_valid: true`. It is a regression - the
2026-09-16 certification of the same route had a genuine exact-chain teacher and
mean KL 3.796e-4 - and it means the 16-47 certification is not reproducible at
HEAD.

## What I got wrong

I fixed the dispatch key (`a7ad30e5f`), re-ran the gate, and **got the identical
false pass**: same hashes, same KL of exactly 0.0, same green status
(`artifact-control-wmma16-47-vs-exact-fixed.json`). So the cache key was not the
cause.

The key genuinely did lack a WMMA layer-scope term - a real latent defect, and a
real instance of the defect class, worth the fix and the RED test it got. But a
latent defect that is not the cause is not a diagnosis, and I published it as
"verified mechanism" after confirming only that the key was identical between
arms. Confirming a mechanism requires showing the fix changes the outcome, and I
did not do that before writing it down.

## Corrected state

- Cause: **not established.**
- Leading hypothesis, explicitly unconfirmed: `HIPENGINE_QWEN4_EXP_Q8_DENSE_WIDE`
  is bound to 16-47 by the certified plan, and `_q8_dense_wide_claims_parent`
  accepts **both** the exact parent (`raw`) and the WMMA-rewritten parent
  (`wmma_<parent>`, ABI `wmma_raw`). The wide route runs later in the launch
  chain, so if it claims the parent in both arms the final variant is
  `dense_wide256_f32_f32_out` regardless of whether WMMA ran - the WMMA layer
  selector cannot change the arithmetic for 16-47 and both arms are one kernel.
  The function's own docstring supports it: the production default binds the WMMA
  route to 16-47, "which is the window this route is scoped to".
- Why unconfirmed: my probe cannot settle it. A synthetic weight resolves to
  `exact_prefill_tile16x4_bf16_bf16_out`, which is not in
  `_Q8_DENSE_WIDE_EXACT_PARENTS`, so the wide route declines and the real
  dispatch path is never reached. Confirming needs a real resident weight or an
  instrumented gate run. I stopped rather than keep guessing at it.

## The generalisable lesson, which the first entry got right by accident

**A gate's green status does not prove its route ran.** Check that the candidate
and teacher logits hashes differ *before* reading any KL; an identical pair is a
failed run regardless of the summary statistics. Both artifacts here report
`measurement_valid: true`.

And a second one this turn earned: **confirming a mechanism means showing the fix
changes the outcome.** Establishing that a suspected cause is *present* is not
the same as establishing that it is *the* cause.
