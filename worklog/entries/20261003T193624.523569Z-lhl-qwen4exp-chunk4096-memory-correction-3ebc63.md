# Correction: the chunk-4096 memory cost is real but is not a blocker; the context sweep gives the guard its envelope

## Summary

The immediately preceding entry (`20261003T193019.939334Z`) reported that a blanket
production chunk-4096 "leaves 84-168 MB of scratch margin" and called that a
measured blocker. **The structural finding in it is right and the blocker claim
overstated the evidence.** This entry corrects the claim, adds the context sweep
that entry listed as unestablished, and records the accurate numbers.

**What was wrong:** the reported figure is the probe's **allowance** margin,
`scratch_margin_bytes = declared_allowance - observed_scratch`. That is a
budget-saturation signal, not host headroom. The admission number is **peak vs
GTT**, which the earlier entry did not compute.

**Corrected measurements** (Tier-1 probe, GTT 120 GiB, one process per arm, ~52 s):

| config | ctx | peak GiB | free GiB | free % | allowance unused |
|---|---:|---:|---:|---:|---:|
| c1, chunk 1024 | 262144 | 86.64 | 33.36 | 27.8% | 2299 MiB |
| c1, chunk 4096 | 262144 | 91.95 | 28.05 | 23.4% | 160 MiB |
| c2, chunk 1024 | 262144 | 96.42 | 23.58 | 19.7% | 4578 MiB |
| c2, chunk 4096 | 262144 | **107.05** | **12.95** | **10.8%** | 240 MiB |
| c2, chunk 4096 | 131072 | 98.14 | 21.86 | 18.2% | 240 MiB |
| c2, chunk 4096 | 65536 | 93.68 | 26.32 | 21.9% | 240 MiB |
| c2, chunk 4096 | 32768 | 91.45 | **28.55** | 23.8% | 240 MiB |

Deltas: **c2 +10.63 GiB (+11.02%)**, **c1 +5.31 GiB (+6.13%)**.

**So the accurate statement is: the promotion roughly halves the absolute headroom
at c2 native context (23.58 -> 12.95 GiB free, 19.7% -> 10.8%). It does not exhaust
it, and no OOM was produced.** That is a real cost for a global default, and it is
not a blocker.

The **allowance** saturation is still a genuine second signal - observed scratch
14.18 GiB against a declared allowance of 14.33 GiB, 240 MiB unused, against
4578 MiB of 8.00 GiB at chunk 1024 - and it is constant at 240 MiB across every
context, because both the allowance and the workspace depend only on the chunk.
But it says the model has reached its own declared budget, not that the host is
out of memory.

## The context sweep (what the prior entry listed as unestablished)

The prior entry said "the crossover context below which chunk 4096 is admissible is
NOT established". The sweep shows **that framing was the wrong question**: because
the workspace is `min(chunk, context)`, the workspace delta is **constant at 3072
rows for any context above 4096**, so there is no chunk-vs-context crossover. The
lever is that a **smaller context frees KV memory**, which pays for the larger
workspace:

| c2, chunk 4096 | peak GiB | free GiB | vs chunk 1024 at native |
|---|---:|---:|---:|
| ctx 262144 | 107.05 | 12.95 | -10.63 GiB |
| ctx 131072 | 98.14 | 21.86 | -1.72 GiB |
| ctx 65536 | 93.68 | 26.32 | +2.74 GiB |
| ctx 32768 | 91.45 | **28.55** | **+4.97 GiB** |

**At 32K context, chunk 4096 leaves more absolute headroom (28.55 GiB) than chunk
1024 does at native context (23.58 GiB).** The guard has a real operating envelope:
comfortable at reduced context, tight only at the full 256K configuration.

## Next

  length. It should take chunk 4096 when the admitted context leaves adequate

  unambiguous.
- **Still not measured: an actual admission failure.** This packet bounds the
