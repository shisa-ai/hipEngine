# Bulk TP2 prefill P1: batched rank-local MLP shard and exchange rows, GPU-validated

## Summary

P1 of the rank-local bulk TP2 prefill plan is implemented and validated at the
MLP level on CPU and on two GPUs with the real GGUF shard quant types. The
**whole bulk route is still partial**: there is no batched attention/GDN prefill
yet and no end-to-end quality run, so the D128 sustained gate is not re-run and
no performance claim is made.

## Changes

- **`MlpShardRank` (`hipengine/distributed/shard_exec.py`)**: opt-in integer
  `rows` capacity plus an `active_rows` count. `write_input`,
  `write_input_from_device`, `read_input`, `read_partial`, and `forward_partial`
  now either use the declared active count exactly or reject the call before any
  launch; non-integer/bool row values and over-capacity values are rejected
  (`transport.require_rows_value`). A preflight (`_require_batched_route`) checks
  the dispatch surface admits a multi-row launch for the weight's
  layout/activation/output combination.
- **`MlpShardGroup` (`shard_group.py`)**: threads the capacity to every rank and
  the transport; `forward`/`enqueue_chain`/`enqueue_rank_chain`/`reduce_partials`
  take `rows`; `cast_reduced` casts the full capacity so the inactive bf16 output
  tail is explicit zeros (the transport zeroes its reduced-payload tail).
- **`StagedExchangeTransport` (`staged.py`)**: `rows` capacity; `reduce(rows=n)`
  stages and sums exactly the active rows, zeroes the trailing capacity rows, and
  rejects a `slot` (no fixed slots on this route).
- **`CompiledStagedExchangeTransport` (`staged_compiled.py`) + native driver
  (`staged_exchange_host.cpp`)**: capacity rows at create; new
  `tp2_staged_reduce_rows` / `tp2_staged_reduce_at_rows` stage/sum exactly the
  active rows and zero the tail. The capacity-1 single-row path calls the
  original ABI functions unchanged.
- **`CompiledDeviceExchange` (`device_exchange_compiled.py`)**: the device-graph
  exchange stays the single-row decode route and rejects `rows != 1` with a
  pointer to the staged transports.
- **Tests**: `tests/test_unit_tp2_prefill_shard.py` (rewritten) and
  `tests/test_unit_tp2_prefill_transport.py` (new) cover rows 1/2/3/4, partial
  rows, active-row mismatch, row-value validation, dtype/layout preflight,
  batched Python reduction math (active-only sum + zeroed tail), the compiled
  rows ABI selection, group rows propagation, and teardown. A guarded GPU test
  (`test_gpu_distributed_shard_components.py`) adds an exact numpy oracle for
  batched dense-bf16 rows and tail zeroing. `scripts/tp2_batched_prefill_probe.py`
  runs the real GGUF batched chain.

## Key finding (dispatch)

The real `launch_gguf_linear` rewrites `rows>1` to leaves the dispatch-surface
helper does not name: Q4_K t16 gate/up → `t16_wmma_prefill_bf16_bf16_out`,
Q6_K t16 qmicro planar down → `t16_gemv_rowtile_bf16_bf16_out` (and `_f32_out`).
`resolve_gguf_linear_dispatch` alone reports `t16_gemv_decode_*` for the down and
has no f32 surface for Q4_K t16. The shard preflight is therefore a dtype/layout
support check only; the GPU probe is the rows-aware validation. Q4_K t16 + f32
output fails before launch.

## Environment note

The host's `hipcc` does not add `/opt/rocm/include` unless `HIP_PATH=/opt/rocm`
is set; without it the native driver rebuild fails with `hip/hip_runtime.h not
found`. This is pre-existing and affects every native build, not just these
drivers. The compiled evidence above was produced with `HIP_PATH=/opt/rocm`; no
environment was restored or changed.
