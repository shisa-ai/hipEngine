# v0.5.0 gfx1151 scope and Qwen3.6/3.8 identity decision

## Summary

Two decisions on top of the section J release checklist:

1. **Scope.** The v0.5.0 Qwen3.8-27B pass is gfx1151 only. gfx1100 is out of
   scope, the test-tier migration is excluded and owned elsewhere, and anything
   else that surfaces is qualified only if its artifact is already on this host
   — otherwise it gets a backlog entry with a named reopen condition.
2. **Identity.** Qwen3.6-27B and Qwen3.8-27B are one dispatch identity, so audit
   finding 3 is closed as not a defect and the profile key must not be split per
   model name. What replaces it is a measurement: A/B the gfx1100 dense
   composition against the gfx1151 one on gfx1151, as part of initial
   qualification.

## Evidence behind the identity ruling

- `hipengine/kernels/policy.py` module docstring: "Human-facing model names are
  provenance, not dispatch keys ... compatible finetunes and renamed exports
  inherit the same policy."
- `GGUFModelGeometry` is a plain `@dataclass(frozen=True, slots=True)`, so the
  policy key is the structural identity of its 20 fields. Both dense 27B files
  resolve to `QWEN35_DENSE_H5120_GEOMETRY`.
- Resolved at this commit: `(qwen3_5_gguf, hip_gfx1100, gguf_q4_k_m)` and
  `(qwen3_5_gguf, hip_gfx1151, gguf_q4_k_m)` are both registered, and an omitted
  profile resolves to `production` on both. The two plans differ in binder env
  flags and variant selections, which is the A/B target.

## Reachability facts recorded with the A/B item

- `GGUF_SPECDEC2_Q4_DUAL_SILU_PRODUCTION_R28_POLICY` and
  `GGUF_SPECDEC2_Q4_DUAL_SILU_ROWTILE_POLICY` are defined only in the gfx1100
  package, and `hipengine/runtime/gguf_linear.py::_q4_t16_physical_dual_silu_variant`
  reads them through `backend_package_capability(backend, name, {})`. On gfx1151
  they resolve to `{}`, so two of the gfx1100 binder's flags are inert there by
  construction and a naive env-swap A/B measures only the reachable subset.
- The gfx1100 binder does not set
  `HIPENGINE_EXECUTION_PROFILE_MANIFEST_SHA256`; the gfx1151 binder does. The
  A/B artifact must record the manifest hash by hand.
- `graph_policy` has no runtime consumer (`grep -rn graph_policy hipengine/`
  finds only the registrations and an unrelated PARO local), so the two plans'
  differing values are not evidence of a decode-graph behavioural difference.
