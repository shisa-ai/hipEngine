# The DP-8 prefill A/B harness could not see its own route

## Summary

DP-8's composition passes every hard gate, but its **value** has only ever been
an estimate (`~0.66% of prefill`, from `3 layers x 8.985 ms x 4 chunks`). That
arithmetic is exactly what the source artifact's own `extrapolation_warning`
forbids, so a harness was built to measure the share directly: one resident
generator, one prompt, both arms interleaved, wall time of a real prefill on each
side.

**Its first engagement instrument was blind, and it blamed the route.** The
counter wrapped `resolve_gguf_linear_dispatch`. That function is *inside* the
memoization it was meant to observe: `launch_gguf_linear` caches the whole
selector chain - including the staged-f32 rewrite - in `_DISPATCH_RESOLVE_CACHE`,
and the warmups fill that cache for both arms. The measured repetitions
therefore hit the cache and never call the resolver, so the counter read
`{}` for both arms and the harness refused with:

> "the staged variant was not resolved in the candidate arm and/or was resolved
> in the baseline arm, so this run does not measure the route"

which reads as "the route did not run". It had run. A harness whose refusal
message accuses the route of a defect that belongs to the instrument is worse
than no harness, because the refusal is plausible and the census it prints is
empty rather than wrong.

**The fix is to count where the cache is not**: the cached kernel callable, which
`launch_gguf_linear` invokes once per launch. Wrapping the callables counts real
launches and never touches the dispatch chain, so the timed region is unchanged -
which matters here, because the quantity being measured is 0.15% of prefill.

Two failure modes were closed rather than one, because both produce a *silent*
zero:

1. **A counter that reads zero through a warm cache.** Pinned by a test that
   installs the wrap, calls through the cache twice per key, and requires the
   per-variant counts.
2. **A counter that silently undercounts when a dispatch-cache entry appears
   after installation.** The harness re-installs before every measured arm and
   records `uncounted_cache_entries_by_arm`; a non-zero value after an arm makes
   the run refuse, because that arm's census is incomplete.

A malformed cache entry raises instead of being skipped, so a changed cache
layout fails loudly rather than reporting a clean zero.

**The replacement also answers a second question for free.** Wrapping the cached
callable means every launch is counted, so the artifact now carries the full
per-arm launch census - which is how the measurement can show *what* ran rather
than only *whether the staged variant ran*.

## Changes

- `scripts/qwen4exp_dp8_staged_scope_prefill_ab.py` - `_install_dispatch_counter`
  replaced by `_wrap_cached_launches`, which wraps the cached kernel callables
  and reports `(wrapped_this_call, total_wrapped)`; `_staged_layer_of` recovers
  the model layer index from the dispatch cache key (present only while a scope
  is bound) and returns `None` rather than guessing; `_layer_census` renders the
  per-layer rows. The report prints the launch census, the refusal messages name
  the actual counts and distinguish "the route declined" from "the instrument
  cannot see the path", and a new refusal covers the incomplete-census case.
- `scripts/run_qwen4exp_dp8_staged_scope_prefill_ab.sh` - forwards `"$@"` after
  its own defaults, so an override is honoured. Without it the wrapper's
  hardcoded `--prompt-length 4096 --warmups 2 --repetitions 9` silently win and
  a caller asking for a 1024-token smoke test runs the full measurement instead.
- `tests/test_unit_qwen4exp_dp8_staged_scope_launch_counter.py` - the two silent
  zero modes, idempotent re-install, the malformed-entry error, and the
  attribution that must decline rather than guess.

No kernel, dispatch, default, flag or retained metric changed.

## Validation

- The wrap, the per-variant counts, the per-layer attribution, idempotence and
  the malformed-entry error were exercised against a stub dispatch cache before
  any GPU run.
- `uv run pytest tests/test_unit_qwen4exp_dp8_staged_scope_launch_counter.py -q`
  - 10 passed.
- The instrument's first real run reports the census the arithmetic requires:
  the exact-chain leaf falls by **exactly** the staged count (4824 -> 3924 with
  900 staged launches), the staged launches appear on layers 13, 14 and 15 only,
  and the two unaffected variants are identical in both arms. That one-for-one
  replacement is what a correct counter must produce and what the resolver-level
  counter could not.
