# prefix-cache hits on a multi-turn load cost 24.9x the prefill per token and forfeit MTP

## Summary

Task #5 asked for a prefix-cache hit rate on a realistic multi-turn load before
deciding whether a hit should get a path into MTP. The hit rate is high (12 of
16 requests, every turn after the first) and the hit path is a measured loss:
the reused-prefix suffix is prefilled at **decode** speed, one `session.step`
per token, so a hit costs **24.9x the prefill per executed token** of a miss
(82.1 against 3.3 ms) and 28.9x the TTFT, and the same refusals that block the
suffix also block the draft provider, so a hit row is 100% autoregressive. On
the same load `--prefix-cache radix` decodes at **3.47 tok/s against 46.52**
with the cache off. No MTP row for hits is written; the prerequisite is a
batched suffix prefill, and the mechanism for MTP on a hit after that is a
draft-provider checkpoint, not a target-state rebuild.

## Changes

- `scripts/sharegpt_mtp_routing_pass.py`: `--turns N` expands each dataset
  conversation into N growing prompts (turn `t` submits the first `t` user turns
  and their dataset replies), so every turn after the first shares a token-exact
  prefix with the turn before it; `--route-mix` then assigns the arm per
  conversation so both arms submit identical prompt sequences. The harness also
  keeps the terminal chunk's `diagnostics` and backend `timing`, and reports
  `by_prefix` and `by_turn` slices. Single-turn runs are unchanged.
- `tests/test_unit_sharegpt_mtp_routing_recorder.py`: five tests for the
  multi-turn expansion (prefix chain, conversation-level keep/drop), the prefix
  telemetry mapping, and the two new summary slices.
- `benchmarks/HARNESSES.md`: the harness row documents `--turns` and the new
  slices.
- `benchmarks/results/2026-09-18-gfx1151-qwen38-prefix-hit-multiturn-rejected.json`:
  the measurement, the mechanism, and the decision.

## Validation

zbook / Radeon 8060S (gfx1151), Qwen3.8-27B Q4_K_M, bf16 KV, production
profile, commit `f46912963`, one server process per cache mode,
`HIPENGINE_MTP2_OUTPUT_SPANS=1`,
`scripts/sharegpt_mtp_routing_pass.py --num-prompts 4 --turns 4
--min-prompt-len 256 --max-prompt-len 1200 --max-total-len 2048 --output-len 128
--record-ids --seed 4242 --route-mix off,on`:

| cache mode | requests | failures | wall s | decode tok/s | median TTFT ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| off | 16 | 0 | 186.1 | 46.52 | 2,338 |
| radix | 16 | 0 | 590.5 | 3.47 | 26,702 |

- Hit rate 12/16 (0.75): 4/4 turn-0 rows missed, 12/12 turn>=1 rows hit, source
  `completed_snapshot`, matched 256 or 512 tokens, 158,859,264 state-clone bytes
  per hit.
- Cost per executed prefill token, from the backend's own `prefill_ms` in the
  terminal chunk's timing block: hits 81.6-82.8 ms (median 82.1), misses 2.8-3.4
  ms plus one 12.6 ms first-request outlier (median 3.3) -> **24.9x**. TTFT
  median 33,475 (hit) against 1,160 ms (miss) -> 28.9x. Decode ITL is unchanged
  (83-86 ms) because the row is autoregressive either way.
- MTP on a hit: `prompt_streaming=0`, `prompt_prime_rows=0`,
  `prompt_carried_bytes=0`, `draft_cycles=0`, `mtp_output_tokens=0`, 127
  `no_provider` events (one per output token). The matching miss row on the same
  arm: `prompt_streaming=1`, `prompt_prime_rows=420`, 10,240 carried bytes, 42
  cycles, 126 of 128 tokens from speculation, one `no_provider` event.

## Mechanism

- `hipengine/generation/qwen35_gguf.py`: both `_prefill_native_chunk` and
  `_prefill_processed_argmax_chunk` take an `if row.prefix_reused_tokens:`
  branch that runs the suffix through one `session.step(token_id)` per token,
  where the miss path calls the batched prefill. A single-token step costs a
  decode step (82 ms at ~700 tokens of context), so reuse trades a 3.3 ms/token
  batched prefill for an 82 ms/token loop.
- `hipengine/generation/qwen35_gguf_mtp2.py`: `_open_prompt_streaming_sinks`
  returns `None` as soon as a row has `prefix_reused_tokens > 0`
  (`mtp2_prompt_fallback_reason = "prefix_reuse_k0"`), so the provider never
  receives the prompt's hidden rows and `capability()` reports no draft state
  for every cycle.
- The reused prefix cannot supply those rows: the draft provider is a stateful
  recurrent head whose catch-up replays the whole prompt from the target's
  hidden rows, and a reused prefix never ran the target in this request.
- `docs/CONCURRENCY.md`'s retained 249.269 -> 21.188 ms slice is a **p256+s1**
  packet, where the per-token loop costs exactly one step. That is the single
  shape in which this implementation's weakness cannot show, and it is why the
  retained number and this measurement disagree so sharply.

## Decision

- No MTP row for prefix hits. A hit already costs 24.9x the prefill per token
  and loses MTP entirely; admitting MTP on a hit would optimize the smaller half
  of a path that is 13x slower end to end than not using the cache.
- Bound on the follow-up's value: on the hit rows, decode is 10.4-10.6 s of a
  31-70 s request, so the prefill fix is worth roughly 4x more than the decode
  fix. Both are needed before prefix reuse is worth promoting.
- When the batched suffix prefill lands, MTP on a hit should be a **draft
  checkpoint**: capture the provider's recurrent state at each 256-aligned
  boundary during the catch-up it already performs, and restore it on a
  matching hit instead of replaying the prompt. Rebuilding the target's hidden
  rows for a reused prefix re-runs the target over the whole reused prefix,
  which is the cost reuse exists to remove.
