# Probe: pool-size invariance confirmed; mixed-length empty splits quantified

## Summary

Measured confirmation of the PR #29510 review decision
(`20261108T144148.195290Z-...-llamacpp-kv-rows-review-6399a2.md`) on the
production split-K batched decode wrapper. Two findings:

1. **Pool-size invariance holds (the port is unnecessary).** Running c4 equal
   8K contexts against a 32K-token physical pool vs a 512K-token pool changes
   attention time by **+0.25%** (767.3 -> 769.2 us median). hipEngine attention
   walks each row's `live_counts` through its own page table, so enlarging the
   shared pool 16x adds no traversal. The llama.cpp unified-cache penalty
   (attend the whole pool, mask other sequences away) is absent, now measured
   rather than only source-inspected.

2. **Mixed-length empty splits are real, measurable redundant work** — the
   reviewer's first-choice experiment is confirmed as an overhead that exists,
   though not yet shown to be an end-to-end bottleneck. The production launch
   formula `num_splits = ceil(max_context_len/256)` is driven by the *longest*
   row, so short rows launch split blocks that only zero partial buffers and
   return, and the reduce kernel still iterates those empty splits.

Key isolations (kernel attention time, context kernel + gated reduce):

| Arm | Config | Median us | Empty blocks |
| --- | --- | ---: | ---: |
| B4 | 4 x 1K, num_splits=4 (compact) | 80.2 | 0 |
| B3 | 4 x 1K, num_splits=128 | 157.6 | 1984 |
| B7 | 4 x 1K, num_splits=512 | 671.4 | 8128 |

Identical valid work; only `num_splits` changes. Empty-split overhead is
**+77.5 us at 128 splits (49.1% of the inflated time, ~+97% over compact)**
and **+591.2 us at 512 splits**. A short request's attention cost is dominated
by empty splits when a long request shares the batch. Mixed-length batches
show the same effect end-to-end at the kernel: `[32K,1K,1K,1K]` (862.4 us) is
**+8.98%** over an equal-total-token `[4x8960]` batch (791.4 us);
`[128K,1K,1K,1K]` (3129.6 us) is **+11.46%** over the long-only 128K row
(2807.8 us).

Scope and hardware caveat: this is a **diagnostic kernel-level probe on
gfx1151 / Strix Halo (Radeon 8060S), ROCm SDK 10.0.0**, host `gfx1151`, kernel
`7.3.1-1-cachyos`. It is **not** the default W7900/gfx1100 lane and the
absolute microseconds do not transfer there. It times attention only, not a
full decode step or serving latency; it proves the overhead exists and its
kernel-level magnitude, not that it is the serving bottleneck. No arithmetic,
no production default, and no registry change was made.

## Changes

- `scripts/probe_paged_decode_pool_invariance.py`: self-contained probe. Calls
  the exact production wrapper
  `qwen35_paged_full_attn_decode_split_k_gqa_gate_bf16_batch_spans` with the
  runner's geometry arguments (`gate_stride1=head_dim`, `gate_stride2=1`,
  `scale=head_dim**-0.5`) and the runner's `num_splits` formula. Includes a
  numpy bf16 oracle, HIP-event timing over back-to-back calls, and JSON export.
- `benchmarks/results/2026-11-08-pr29510-paged-decode-pool-invariance-diagnostic.json`:
  compact diagnostic artifact (identity, method, oracle, per-arm stats, verdict).

## Validation

- Oracle passes before timing: merged split-softmax * sigmoid(gate) vs numpy
  bf16 reference, `max_abs_diff = 6.10e-05`, all finite. Confirms the probe is
  wired to the real ABI, not a stub.
- Kernel library loaded from the existing gfx1151 JIT cache (0.0-0.1 s), so the
  measured code object is the production-compiled one for this arch.
- Geometry is the supported `(24 Q, 4 KV, head_dim 256, block 256)` Qwen3.8-27B
  specialization; wrapper shape checks pass for every arm.
- Reproducible: two consecutive runs agree within ~1% on every arm (e.g. Arm A
  delta +0.35% then +0.25%; B3 157.7 then 157.6 us).
- This is a diagnostic, not a promotion: no `docs/OPTIMIZATION.md` correctness
  or production-profile gate applies because no arithmetic or default changed.
