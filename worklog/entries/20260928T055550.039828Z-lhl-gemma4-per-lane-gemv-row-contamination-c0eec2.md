# the per-lane selected GEMV is the buggy route and it contaminates rows across lanes

## Summary

`20260928T055408` established that two expert routes disagree while each looked
internally consistent, and `20260928T055459` failed to separate them with an
internal invariant. This unit separates them by **collapsing the grouping**: run
each route with a routing that puts every lane on one expert, so the
row-reusing route has exactly one group and the per-lane GEMV has every lane on
the same expert. A grouping defect would disappear; a per-expert arithmetic
defect would not.

| routing | per-lane rows1 vs rows2 | row-reusing rows1 vs rows2 | routes disagree |
| --- | --- | --- | --- |
| both lanes expert 0 | **0.00919143** | **0.00000000** | 0.00919143 |
| both lanes expert 1 | **0.01614113** | **0.00000000** | 0.01614113 |
| lanes split 0 and 1 | **0.01280104** | **0.00000000** | 0.01280104 |
| lanes split 0 and 3 | **0.01138550** | **0.00000000** | 0.01138550 |
| both lanes expert 3 | **0.01859668** | **0.00000000** | 0.01859668 |

**The row-reusing route is row-count-invariant to bit-equality in all five
routings. The per-lane GEMV is not, in any of them** -- and the routes'
disagreement is *numerically identical* to the per-lane route's own row-to-row
inconsistency (0.00919143 in both columns of the first row, and so on). The
per-lane route is therefore the entire source of the divergence.

It is not the grouping: the single-expert routings collapse the grouping to one
group and the difference survives unchanged.

## The mechanism: rows contaminate each other

The per-lane selected GEMV is documented as launching "one block per
`(out_col, lane)`", which makes each lane an independent computation. It is not
independent: row 0's output changes when row 1 is added to the same call.

That is why `20260928T055459`'s invariant passed. With **byte-identical rows**,
a contaminating contribution is indistinguishable from the correct one -- the
value that leaks in is the value that was already expected. The invariant was
tested with identical rows and is only violated by distinct ones.

This also explains the round magnitudes reported in `20260928T055238`: a
contaminating read contributes a value on the scale of another lane's
activations, not a rounding-level delta.

## Which route is correct

The row-reusing route. Three independent reasons:

1. It is invariant under the change that breaks the other one: every row count
   and every routing gives `rel=0.00000000` against its own one-row call.
2. It is the route the model actually uses for prefill, which is the path whose
   outputs have been validated end to end.
3. Its structure is the one that makes the invariance plausible: it reads each
   weight element once per expert and reuses it across that expert's rows, so
   there is no cross-lane sharing to get wrong.

## What this means

**Decode has been computing the wrong expert FFN.** `rows == 1` gives
`lanes = top_k = 2`, which is below `num_experts = 4`, so every decode step
takes the per-lane GEMV. Prefill takes the row-reusing route. The two have
disagreed by 1 to 2 percent on every token the model has generated.

**It is a correctness defect, not an arithmetic difference.** The per-lane route
is wrong for every multi-lane call it handles, and it is the route that serves
decode.

**`test_incremental_decode_matches_a_dense_prefill` was right.** It compares a
dense prefill against one-token-at-a-time decode -- the row-reusing route against
the per-lane GEMV -- and it fails because decode is wrong, not because the test
is over-strict.

**The fix is in the per-lane route**, either by repairing its lane isolation or,
as an interim, by making the crossover select the row-reusing route for decode
shapes too. The second is a behavior change that would cost decode throughput
and is not the right fix; it is recorded only as the rollback lever.

## Changes

None. This unit is a measurement.

## Validation

- Probe on the 8060S (gfx1151) calling `gemma4_experts_forward_bf16` with five
  routings, at rows=1 and rows=2, under `_PREFILL_MIN_LANES_PER_EXPERT = 1`
  (as shipped) and `= 0` (row-reusing forced) and `= 1e9` (per-lane forced).
  Exit 0.
- The decisive column is `rowreuse rows1vs2`, which is `0.00000000` in all five
  routings while the corresponding per-lane column is not -- so the attribution
  does not rest on the cross-route comparison alone.
- The single-expert routings are what exclude the grouping as the cause, since
  they leave exactly one group.
- The reason the earlier invariant test passed is stated as a property of the
  test (identical rows) rather than left as an unexplained negative.

## Next

Find the cross-lane read in the per-lane selected-GEMV leaf. The
`(out_col, lane)` launch geometry is the place to look: a lane index derived
from the block id, an output write that lands on a neighbouring lane's row, or a
scratch buffer shared across lanes. A regression test should assert row 0's
output is unchanged when extra distinct rows are appended to the call, which is
the property this unit measures and the one the existing invariant test missed.
