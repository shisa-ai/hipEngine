# Correct Qwen3.8 context limit classifications

## Summary

Corrected the Qwen3.8 dedicated-XTX context frontier without running new GPU measurements. The prior rollup incorrectly converted a chosen 512-MiB headroom diagnostic into execution pass/fail. That classification is withdrawn: request success, readiness/ownership, and actual runtime/startup errors now control pass/fail, while headroom remains measured risk data.

This entry supersedes only the limit classification in `20260815T170916.823440Z-lhl-qwen38-int8-context-soak-b2c964.md` and `20260815T182245.795089Z-lhl-qwen38-dedicated-context-qualification-59a182.md`; those committed entries remain immutable historical records.

## Changes

- Corrected the compact artifacts and public documentation: c1 passes 112K and first actually OOMs at 128K (120K was policy-blocked without execution); c2 passes through 6,144/request and actually fails 0/2 at 8,192 with HTTP-500 HIP OOM; physical c4 passes 1,536/request for 16/16 multi-turn requests with no tested failure; offered c8 passes 2,048/request with no tested failure, while shape-aware rows show two physical c4 waves.
- Reclassified the c2 4,352/4,608/4,864/5,632/6,144, c4 1,536, and c8 1,536/2,048 rows as execution passes despite low measured headroom. Recorded exact raw hashes and preserved the distinction between the pre-shape-accounting c8 2,048 row and later shape-aware rows.
- Changed `scripts/qwen38_int8_server_context_soak.py` so top-level pass/fail no longer uses any headroom threshold and the limit-discovery default disables the server's policy startup guard (`--startup-min-free-mib 0`). The harness still records exact peak and headroom bytes; server startup, request exactness, post-burst readiness, zero ownership, and runtime errors determine execution success.
- Updated `benchmarks/README.md`, `benchmarks/CHANGELOG.md`, `docs/KVCACHE.md`, and `docs/REFACTOR.md` to report observed passes, actual failures, untested ceilings, and policy-blocked rows without inventing a reserve-based limit.
