# Gemma 4 MTP verify block gets an exact form; strict uses it, production keeps the WMMA block

## Summary

The lead asked what an exact MTP verify block costs, said strict should have an
exact path, and said production should default to the production-envelope block
if the accuracy difference is small. The previous entry,
`worklog/entries/20261012T190026.866783Z-lhl-gemma4-mtp-status-820a2d.md`, had
found that a multi-row verify block is not the arithmetic of one-token decode
without isolating why.

Three operators differ, found by comparing layer scratch buffers between a
one-token forward and a multi-row `verification=True` forward:

1. Dense projections. `gemma4_project` passes `use_wmma_prefill=True`
   unconditionally (since `dc434347b`), which overrides the runner's
   `_gemma4_block_wmma_session(False)` for a verify block. With WMMA off, row 0
   of layer 0 is bit-identical.
2. Attention. The decode kernel partitions its reduction by key count
   (`decode_slices`, flash slices), and a multi-row launch hands every row the
   block's range. First differing layer 2 to 4 at 600 and 1100 prompt tokens
   once dense was exact.
3. The MoE router. `gemma4_router_topk_bf16` takes a fused launch at
   `tokens == 1` whose projection reduces in a different order from the chain;
   1 to 8 bytes of the routing weights differed at the first differing row.

The exact form replaces each: row-exact dense schedule, one decode-shaped
attention launch per row over that row's own key range and with the decode
step's variant requests, and the one-token router per row. It is bit-identical
to one-token decode on 72 of 72 rows in both profiles (prompts 120/600/1100,
3/5/7/9 rows).

Cost, W7900, budget 4, 18 prompts, 128 greedy tokens, whole public call, nothing
else running: production with the WMMA block 73.7 -> 102.8 tok/s (1.40x, 11 of
18 prompts token-identical to plain greedy); production forced exact 73.5 ->
88.5 (1.20x, 18 of 18); strict, exact by default, 73.2 -> 87.5 (1.19x, 18 of
18). A five-row block is 28.0 ms on WMMA and 33.5 ms exact; seven rows 32.7 and
43.9. The WMMA block's rows differ from one-token decode by a row KL of at most
8.8e-2 with no argmax change in 72 rows.

Per the lead's rule the production profile keeps the WMMA block and strict
verifies exactly. The selector is `Gemma4Runner.verify_dense_exact`, set by the
generator from the bound execution profile; a runner built without a profile is
exact. It is a profile property rather than a flag, so it has no
`docs/REFACTOR.md` entry.

## Changes

- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_layer.py`: `gemma4_project`
  takes `use_wmma_prefill`; the layer takes `dense_wmma_prefill` and
  `row_decode_attention` (`Gemma4RowDecodeAttention`); the attention call site
  became an inner `attend` so a row can be launched over its own range; the
  router is launched per row when rows are exact.
- `hipengine/runtime/gemma4.py`: `verify_dense_exact`, `_row_decode_attention`,
  and the corrected `forward` docstring.
- `hipengine/generation/gemma4_gguf.py`: `verify_dense_exact` property from the
  execution profile, passed to the runner.
- `hipengine/generation/gemma4_mtp.py`: docstring and telemetry report the
  contract that ran (`verify_equivalence`, `target_verify`, `execution_path`).
- `scripts/gemma4_mtp_probe.py`: token identity is required unless the MTP
  arm's telemetry declares the production envelope; a divergence is then
  recorded with its position.
- Tests: `tests/test_unit_gemma4_verify_row_exact.py`, additions to
  `tests/test_gpu_gemma4_runner_verify_rows.py` and
  `tests/test_unit_gemma4_mtp_probe.py`.
- `docs/reference/GEMMA4-ASSISTANT-MTP.md`, `benchmarks/CHANGELOG.md`,
  `benchmarks/results/2026-10-13-gemma4-gfx1100-mtp-exact-verify.json`.

## Validation

- Unit: every `unit_gemma4` test passes; the new unit file and the probe tests
  pass.
- GPU: `tests/test_gpu_gemma4_runner_verify_rows.py` 12 passed on the W7900.
- Row equality and block timing from a scratch script over the real artifact;
  public-path numbers from `scripts/gemma4_mtp_probe.py`. An earlier run of the
  three arms was discarded because unit tests were running on the host at the
  same time and lowered the plain rate to 49 to 70 tok/s; the numbers above are
  the rerun.
- No RED-first test for the layer change: the defect was a bitwise mismatch on
  the real artifact that the synthetic fixture does not show (its existing
  multi-row equality test already passed), so the fixture tests pin the request
  plumbing and the real-artifact comparison is the evidence.
