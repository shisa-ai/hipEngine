# R0404 tail4-Hadamard direct-prefill gate extension and evaluation

## Summary

R0404's per-token-head direct-prefill numerical choice was already resolved; the remaining
"tail-four Hadamard coverage" is the calibrated quality evaluation of the direct Hadamard
prefill route on the mixed `tail4_hadamard_group32` KV layout. The clearing gate only drove
mirror-free uniform `int8_per_token_head`, so this unit extends it with a `--kv-layout`
selector and runs the Hadamard evaluation on gfx1100. The numerical envelope passes; a
clean-provenance re-run is pending because the gate extension itself was uncommitted during
the first full run.

## Changes

- `scripts/execution_profile_gguf_int8_direct_prefill_gate.py`: add
  `--kv-layout {per_token_head,tail4_hadamard}` (default `per_token_head`, behavior unchanged).
  For `tail4_hadamard`: resolve the `tail4_hadamard_group32` policy (fp16 / hadamard_group32),
  set the session `kv_scale_dtype`/`kv_scale_granularity`, use a layout-specific admission check
  (the mixed layout's BF16 prefix is real storage, not a short-context mirror, so the uniform
  `no_mirror_qualified` predicate does not apply; instead assert the layout + granularity are
  engaged), and record the layout in the candidate mechanism, `scenario_id`, `kv_dtype` and
  `kv_policy` metadata. No production/arithmetic change.

## Validation

- Key facts established by inspection: `_mirror_free_direct_int8_capability` requires
  `storage_layout == "uniform"`, so the tail4 layout uses the mixed path
  (`int8_kv_no_mirror_qualified=False`); `PURE_INT8_ENV`'s `HIPENGINE_GGUF_INT8_KV_BF16_FULL_LAYERS=none`
  is ignored for non-uniform layouts, so it does not collapse the tail4 prefix. The direct
  Hadamard leaf (`qwen35_paged_attn_prefill_int8_hadamard_group32_gqa_gate_fp16_spans`) engages
  from the append spans' `hadamard_group32` granularity in the bulk prefill path.
