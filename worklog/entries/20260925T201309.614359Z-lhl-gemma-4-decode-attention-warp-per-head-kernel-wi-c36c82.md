# Gemma 4 decode attention: warp-per-head kernel with a shuffle-exact 256-lane tree wins the full-layer geometry (+6.3% decode)

## Summary

Iteration 20 left the decode attention kernel's ~0.6 us per-key cost unexplained by
any component inside the key iteration. This iteration went after the structure
that remained: the 256-lane tree spanning eight warps, which costs a shared-memory
round trip and a barrier sequence per key. The replacement keeps the tree's exact
association but puts all 256 tree lanes inside one warp, so the reduction is five
shuffles plus three in-lane adds with no LDS traffic and no barriers in the key
walk.

Result: **bit-exact, and 28% faster on the full-layer geometry** (`head_dim` 512,
851-870 us vs the block kernel's 1186 us at keys=1024, microbenchmark), which moved
the campaign metric to **24.6025 tok/s from 23.1517 (+6.3%)** with public-path
parity true. The same kernel is **slower** on the sliding geometry (`head_dim` 256,
822 vs 700 us), so the dispatch selects it only for `head_dim == 512` and leaves
sliding on the block kernel.

## The tree mapping that makes it bit-exact

Warp lane `w` owns tree lanes `[8w, 8w+8)`. The block kernel's tree strides then
map onto the warp as:

| block stride | tree lanes updated | warp mechanism |
| --- | --- | --- |
| 128 | 0..127 | shuffle, lane distance 16 |
| 64 | 0..63 | shuffle, lane distance 8 |
| 32 | 0..31 | shuffle, lane distance 4 |
| 16 | 0..15 | shuffle, lane distance 2 |
| 8 | 0..7 | shuffle, lane distance 1 |
| 4 | 0..3 | in-lane add, element distance 4 |
| 2 | 0..1 | in-lane add, element distance 2 |
| 1 | 0 | in-lane add |

Same pairs, same order, so every logit and the denominator are bit-identical. The
shuffles stay outside their lane guards for the reason the block kernel's do: a
`__shfl_down` whose source lane sits in an inactive branch returns 0 on gfx1100
and silently drops terms.

Pass 2 and pass 3 keep the block kernel's own partitions - tree lane `L`
accumulates keys `j == L (mod 256)` ascending, and each dimension keeps its own
ascending-j chain - so the only thing that changed is who evaluates the tree.

## Why the sliding geometry loses, and the clock caveat

One warp per `(token, head)` means 16 warps for a decode step (16 heads, one
token). The block kernel runs 128. The warp kernel removes the cross-warp
machinery but also removes eight ninths of the concurrency, and at `head_dim` 256
there is not enough work per key to pay that back. Grid scaling on the block
kernel shows the machine is far from throughput-bound - 16 blocks 695 us, 32
blocks 1097, 64 blocks 1093, 128 blocks 1653, 256 blocks 1116 us, so 16x the work
costs 1.6x the time - which is why a *low-concurrency* kernel can lose despite
doing less work per key.

Microbenchmark timings depend on the clock state: the same sliding/1024 case
measures 652 us at 40 iterations and 486 us at 400, so every A/B in this entry
compares runs at the same iteration count, back to back.

## What was refuted on the way

The iteration's first candidate was a branchless batched tile: hoist the tile's
mask bytes into registers, then issue all `kTile` K-row loads unconditionally
(masked keys read a clamped row and are discarded at publish). It measured
**910 us vs the 695 us baseline** and was reverted. The load path is not the
serialization; removing the control dependency on the mask byte made the kernel
slower, not faster.

## Changes

- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention.hip`:
  `gemma4_warp_tree` (the eight-value shuffle tree), the warp-per-head decode
  kernel, its launcher, and a dispatch that selects it for `head_dim == 512` only.
  The block kernel is untouched and remains the reference and the fallback for
  every other geometry.
- `tests/test_gpu_gemma4_attention_decode_parity.py`: four shapes that exercise
  the warp path - `(16, 2, 256, 1024)`, `(16, 8, 512, 1024)`, `(16, 2, 256, 2055)`
  (past the tile edge), `(16, 2, 256, 8192)` (context cap).
- `scripts/gemma4_attention_decode_bench.py`: `--tokens` knob, so grid scaling can
  separate latency-bound from throughput-bound behaviour.
- No flag, no env var: the selection is a measured geometry choice inside the
  launcher, and the arithmetic on both paths is bit-identical.

## Validation

- `tests/test_gpu_gemma4_attention_decode_parity.py`: bitwise prefill-vs-decode
  equality on every shape and both dtypes, including the four new warp-path
  shapes - the warp kernel is bit-exact at `head_dim` 256 and 512, keys 1..8192.
- Guard suite `pytest tests/test_unit_gemma4_*.py tests/test_gpu_gemma4_*.py -q`:
  exit 0.
- Campaign rows above, all with `public_path_parity=true`.
- No spills in the new kernel's ISA (no `scratch_` instructions in the compiled
  object).

## Next

  denominator) hoisted to once per launch instead of once per key.
