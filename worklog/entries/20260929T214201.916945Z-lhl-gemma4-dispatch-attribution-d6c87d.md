### What the sites mean

flow** (~340-390) reaches `grouped_dual` at :354, `grouped` at :368 and
`selected` at :381, with the MMQ leaf (`:969`) underneath; the **down flow**
(~410-470) reaches `wmma` at :419, `grouped` at :450 and `selected` at :463.
So:

- production **gate_up** = MMQ leaf (:969), with `grouped_dual` (:1255) as the

### Corrections to the curation entry

1. **`wmma_prefill` prefill count is 250, not 375.** The 375 came from
   differencing the 2-vs-3-token arms (`P = A - D`, `D = 0`): that method only
   holds for keys whose per-step cost is constant, and this key does first-step
   work too -- the direct prefill-only arm gives 250 while the 2-token arm
   gives 375. The curation entry's *variant set* is unaffected; the count and
   anything derived from it are.
2. **The probe prompt is ~2048 tokens, not ~3072.** The corrected count makes
   the cross-check exact: 250 = 2 x 125, and the prior session measured 125
   at a 1024-token prompt (`...phase-labelled-trace-379cf7.md`), so the probe
   prompt is twice that width. That also re-validates the prior table rather
   than merely disagreeing with it.

### Open, not smoothed

MoE q4_k production counts do not match across runs: the prior 1024-token run
recorded mmq32 = 87 and **no `rowbatch8` row at all**, while this run records
mmq32 = 232 plus `rowbatch8` = 29 (232 = 4 blocks x 29 layers x 2

but the gate's own captures must settle it rather than inherit either number.

### Scope-naming design, now determined

`_resolved_selections` requires the production plan's scopes to be a
**subset** of strict's, so scopes must name the *logical projection* (the same
scope in both profiles), not the launch site -- the site itself differs between
arms (`wmma` :837 under production, `grouped` :1338 under strict, same `down`
scope). Proposed axis:

| layer | scope | carries |
| --- | --- | --- |
| `embedding` | `lookup` | q8_0 / `lookup_bf16_out` in both arms |
| `linear` | `dense_prefill` | q8_0, production `wmma_prefill` / strict unresolved (**B1**) |
| `linear` | `dense_decode` | q8_0 + the q4_k/q5_1/q5_k decode GEMVs, strict unresolved (**B2**) |
| `linear` | `lm_head_f32` | q8_0 f32 out, counts data-dependent (**B4**) |
| `moe_linear` | `gate_up` | q4_k/q5_k: production mmq32 + fallback, strict `grouped_dual` |
| `moe_linear` | `down` | q5_1/q8_0: production `wmma`, strict `grouped` |

One `moe_linear`/`gate_up`/q4_k scope still covers **two** production variants
(232 mmq32 + 29 fallback). The plan type holds one variant per scope, so the
manifest will record the MMQ leaf as `selected_variant` and the fallback has to
live either as a second scope that strict also lists, or in the plan's
provenance text -- a decision for the profiles module, flagged here so it is
not made silently.
