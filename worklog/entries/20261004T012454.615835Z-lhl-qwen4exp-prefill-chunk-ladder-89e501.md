# The canonical prefill chunk is 512, not 1024; 2048 is +18.4% prefill with bit-identical output

## Summary

Following the GPU-bound finding (`20261004T004727`), the next question was where the
kernel work actually goes. Two facts came out of that investigation and both are
larger than the tile-padding lever I had queued.

**First: the canonical protocol has been running the wrong chunk.** The production
profile intends `prefill_chunk_size = 1024`
(`hipengine/generation/qwen4_exp_profiles.py:674`), but that binding only fires when
`generator._implicit_profile_chunk_size` is true, which
`hipengine/generation/qwen4_exp_gguf.py:939` sets to `prefill_chunk_size is None`.
`scripts/qwen4exp_canonical_ar_bench.py:798` **always** passes an explicit value
whose default is **512**. No call site anywhere in the tree passes `None`, so the
profile's 1024 is **dead code** and every canonical number was measured at 512. The
committed canonical artifact confirms it: `/tmp/canonical-mult1/result.json` records
`protocol.prefill_chunk_size = 512`.

**Second: the chunk is a large, monotonic lever.** One `code-p4096` ladder, one
sequential session, 1 warmup and 3 measured repetitions per arm:

| chunk | pp tok/s (median) | vs 512 | decode tok/s | output hash | bit-identical to 512 |
| ---: | ---: | ---: | ---: | --- | --- |
| 512 | 261.77 | 1.000 | 19.649 | `4c9bee44` | — |
| 1024 | 291.47 | **+11.3%** | 18.927 | `4c9bee44` | **yes, 129/129** |
| 2048 | 309.854 | **+18.4%** | 18.561 | `4c9bee44` | **yes, 129/129** |
| 4096 | 328.666 | **+25.6%** | 17.792 | `603391a9` | no, 118/129 differ |

**The 2048 arm is a bit-identical change** — all 129 generated token IDs match the
512 arm exactly, and every arm is internally deterministic (one distinct output hash
across its three repetitions). 4096 is the only arm that changes arithmetic, which
matches the existing comment at `hipengine/kernels/hip_gfx1151/__init__.py:1620`
recording 4096 as "faster still at 1K/4K but is NOT bit-exact (KL 3.1e-07)".

Within-arm spread is tight (coefficient of variation 0.10% to 0.65%), so the ladder
ordering is far outside noise.

## A committed artifact was wrong by 2x

`benchmarks/results/2026-10-04-qwen4exp-moe-tile-padding-measured/` claimed **1.25x**
tile padding on the stated basis `chunk_tokens = 1024`. The chunk is 512, so real
rows per chunk-pass are `512 x top-10 = 5120` and the padded row space is
`800 tiles x 16 = 12800` — **2.50x**, not 1.25x.

The trace's own launch counts fix the chunk independently of the harness:
router logits runs 1536 times = `48 layers x 32 chunk-passes`, gate/up runs 1504 =
`47 layers x 32 chunk-passes`, so there are **32 chunk-passes**. At chunk 512 that is
`4 prefills x 8 chunks`; at chunk 1024 it would need 8 prefills, i.e. 126 s of
prefill inside a 68.26 s window, which is impossible.

**The padding finding stands and is twice as large as reported: up to 60% of the
gate/up WMMA row space is padding at chunk 512, not 40%.**

## Changes

- New artifact `benchmarks/results/2026-10-04-qwen4exp-prefill-chunk-ladder/artifact.json`:
  the ladder, the correctness comparison, the composite cost, the dead-code
  mechanism, and the 2x correction to the padding artifact.
- **No default, flag, kernel or dispatch changed.** The promotion of 2048 is

## Validation

- All four arms in one sequential session on the same host, no other GPU work,
  identical command apart from `--prefill-chunk-size`.
- Correctness is the strongest available signal for a partitioning change:
  **byte-identical `output_token_ids` across 512/1024/2048**, plus per-arm
  determinism across three repetitions.
- The 512 arm reproduces the committed canonical rate (261.77 vs 259.61 median),
  which is what ties this ladder to the existing scoreboard.
- The dead-code claim is verified at the call sites, not inferred: the binder guard,
  the flag assignment, and the harness default were each read, and a tree-wide
  search finds no `prefill_chunk_size=None` caller.
- **Decode regresses monotonically with chunk size and is NOT explained.** It is
  recorded as an open question, not priced in.

## Next

- **Promotion evidence**: the full twelve-case suite at 512 and 2048 is running.
  2048 cannot be promoted on a single case, even a bit-identical one.
- **The decode regression is the open question, and it may not be a chunk effect at
  all.** All four arms ran sequentially in one ~10-minute session, so the regression
  is monotonic in *time* as well as in chunk. The prefill improvement moves the
  opposite way, which argues against uniform thermal drift, but the confound is real
  and the suite's 512 arm is a delayed replicate that will separate them. If it is a
  chunk effect, `resolve_qwen4_exp_context` is the mechanism to check: the chunk
  feeds the scratch reservation, which drives the context-admission binary search,
  so a larger chunk admits a smaller context and changes KV layout.
- **4096 needs the production numerical gate** before it can be a default. It is
  +25.6% but changes arithmetic, and the existing comment says it also costs more at
  64K, so 2048 is the likely landing point.
- The corrected 2.50x padding figure makes the padding lever roughly 3x larger than
  the queued estimate, but it must be re-derived at chunk 2048 before it is acted on
  — padding falls as the chunk grows, so most of the 2.50x may already be captured by
  the chunk change rather than being separately available.
