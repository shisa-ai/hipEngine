# An engine-neutral agentic session replay harness

## Summary

The repo had an agentic workload fixture and an agentic measurement, but no way
to run either against a second engine. Both existing pieces are hipEngine-only:

- `scripts/prefix_cache_multiturn_bench.py` runs **in process**. It imports
  `hipengine`, drives `LLM.generate_detailed`, and measures the resident loop, so
  it cannot address another engine's HTTP surface at all.
- `benchmarks/atlas-agent/http_1to1_bench.py` is engine-neutral but its `multi`
  arm is a synthetic `--turns` loop, and its prompt loader keeps only `role` and
  `content`. Sending a recorded transcript through it would drop every
  `tool_calls` array and every `tool_call_id`, so a server would receive a
  different, and in most cases invalid, request than the real client sent.

`scripts/agentic_session_compare.py` closes that gap. It reads
`benchmarks/prompts/agentic-session-replay-v1.json` (a real Jouzu coding-agent
session: 65 entries, 32 cumulative request boundaries, tip `77d12a62`) and
replays it against any OpenAI-compatible endpoint over HTTP.

## Changes

- `scripts/agentic_session_compare.py`: new harness. Sends the system prompt plus
  `entries[:request_ends[k]]` per request, preserving `tool_calls`,
  `tool_call_id`, and `name` verbatim, and passing the fixture's `tools` array
  (with `--no-tools` to omit it). Requests `stream_options.include_usage` so each
  turn carries the engine's own `usage`. Records per turn `prompt_tokens`,
  TTFT, `decode_tok_s`, total wall, content deltas, and tool-call chunks;
  aggregates cold and warm passes separately with a per-turn TTFT profile.
- `benchmarks/HARNESSES.md`: catalog row for the new harness.

## Validation

- `--dry-run` (offline, contacts no server) confirms request fidelity: 32
  requests, cumulative prefixes 2..64 entries, and the largest payload carries
  **32 assistant messages with `tool_calls` and 32 tool messages with
  `tool_call_id`**. Nothing is flattened.
- End-to-end HTTP path validated against a local mock SSE server: 32/32 turns
  clean, `usage` captured from the stream, and the decode rule behaves as
  intended (`completion_tokens: 4` yields `decode_tokens: 3`, the token arriving
  at TTFT being excluded).
- Both target engines were checked in source for the two payload features the
  harness depends on. hipEngine accepts `tools`/`tool_choice`
  (`hipengine/server/api.py:2045`) and reads the standard
  `stream_options.include_usage` (`_stream_include_usage`). llama.cpp's server
  supports both.
