# YuE2 M4 NAR device runtime

## Summary

`Yue2NarRuntime` is implemented and **matches the pinned upstream reference at
every solver step** on the recorded workload: teacher-forced velocities at the
reference's own four states agree to BF16 noise (`|v|` 38.11 vs 38.12, 39.14 vs
39.07, 44.58 vs 44.54; step 0 `max_abs` 0.086 on a norm of 48.30). The
per-step traces stored in `tests/fixtures/yue2/nar/chunk0.npz` beyond step 0 are
**not** reproducible from their own recorded states by either implementation, so
that fixture is being re-recorded with a self-check (see below); the runtime
itself is not implicated.

## Changes

- `hipengine/runtime/yue2_nar.py`: `Yue2NarRuntime` composes a resident
  `Yue2ArRuntime` -- the AR prefix is prefilled once per chunk and every velocity
  evaluation reads that per-layer K/V cache as the NAR conditioning keys.
  Query rows are tiled (2048 rows/tile) so a full-context chunk costs a few
  hundred megabytes of scratch instead of a few gigabytes; the NAR key/value
  projection for a layer still covers every row before any query tile attends,
  because the NAR attention is bidirectional. Adds `condition`, `velocity_bits`,
  `state_bits`, `solve` (the reference midpoint rule) and `synthesize`
  (original chunks solved serially and concatenated).
- `hipengine/kernels/hip_gfx1100/yue2/`: new `yue2_nar_rope_kernel` /
  `nar_rope_f32` with the same rotate-half convention as the vibevoice/AR rope,
  but allowing either head count to be zero -- the NAR rotates all keys for a
  layer in one pass that produces no queries, then rotates each query tile
  separately. The vibevoice launcher rejects zero-head passes, so the NAR family
  needs its own entry point.
- `scripts/yue2_nar_gate.py`: the M4 gate. Runs the fixture's chunk through the
  native runtime and reports per-step state/velocity error, relative to the
  recorded latent norm, with a provenance block.
- `scripts/yue2_oracle.py`: the NAR recorder now records `steps` and
  `nar_cond_end` in the manifest, accepts `--nar-cond-end`, and **replays every
  recorded velocity at its own recorded state before writing the fixture**,
  failing the recording if the trace is not self-consistent.

## Findings worth keeping

- **A fused Linear bias must stay FP32.** The checkpoint stores `vae2llm.bias`,
  `llm2vae.bias` and both `time_embedder` biases in BF16, but the reference adds
  them inside the Linear, i.e. to the FP32 accumulator, rounding once. Feeding
  the BF16 buffers to `vv_add_bias_f32` (which reads FP32) silently produced
  garbage: the embedding stack was off by 45x. The runtime now uploads FP32
  copies of those four biases. This was the only functional bug found by the
  gate; everything after it matched upstream to BF16 noise.
- **The recorded NAR fixture is internally inconsistent.** Evaluating the pinned
  upstream `CachedNAR.velocity` at `states[1..3]` with the fixture's own recorded
  timesteps gives `|v|` 38.12 / 39.07 / 44.54, while the fixture records
  46.81 / 45.25 / 46.70; the native runtime gives 38.11 / 39.14 / 44.58, i.e. it
  agrees with the reference, not with the fixture. Step 0 matches to `max_abs`
  0.086. Neither the noise nor either schedule phase reproduces the recorded
  step-1..3 velocities at any plausible alignment. The recorder's loop is
  correct as written, so the re-record adds a replay self-check to catch this
  class of error instead of trusting the write path.
- **`F.pad(state, (0, 0, 1, 1))` is the leading/trailing zero boundary row**, and
  the reference's `mid` uses the *first* velocity while the step uses the second:
  `mid = state - v(state, raw) * (h/2)`, `state = state - v(mid, raw_mid) * h`.
  The runtime keeps a padded `[nar_length, 64]` state buffer so the boundary rows
  stay zero across the whole solve.
