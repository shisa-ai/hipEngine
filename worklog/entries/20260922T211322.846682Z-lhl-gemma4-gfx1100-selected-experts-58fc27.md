# A uniform selected-expert GEMV covers 58 of 60 expert tensors on raw blocks

## Summary

Two raw-layout selected-expert GEMVs share one ABI and between them cover every
expert tensor in the artifact that carries real weight:

| quant | slot | layers | kernel | verified |
| --- | --- | --- | --- | --- |
| Q4_K | `ffn_gate_up_exps` | 29 | `gguf_q4_k_selected_gemv_bf16_bf16_out` | yes |
| Q5_1 | `ffn_down_exps` | 29 | `qwen4_exp_q5_1_selected_gemv_bf16_bf16_out` | yes |
| Q5_K | `ffn_gate_up_exps` | 1 | none on raw | — |
| Q8_0 | `ffn_down_exps` | 1 | none on raw | — |

Both verified kernels reproduce a NumPy reference at the rounding floor:

| tensor | expert 0 | expert 3 | expert 5 | expert 127 |
| --- | --- | --- | --- | --- |
| Q4_K `ffn_gate_up_exps` | 0.319% | 0.230% | 0.259% | 0.290% |
| Q5_1 `ffn_down_exps` | 0.270% | 0.344% | 0.313% | 0.309% |

The two kernels take the same arguments in the same order:

```
(x_ptr, selected_ptr, qweight_ptr, out_ptr,
 x_rows, rows, num_experts, in_features, out_features, *, threads, stream)
```

They differ only in the default `threads` (128 for Q4_K, 256 for Q5_1), which each
wrapper already sets.

## The two stragglers are not a gap

Q5_K and Q8_0 have no raw selected GEMV, but they do have raw *plain* linear
GEMVs (`gguf_k_gemv.wrapper`, confirmed earlier), so the per-expert offset path in
`gemma4_project_expert` serves them. That is one layer each, and it is already
implemented and working for Q4_K.

So the expert forward needs two dispatch routes, and both are justified by what
the kernels actually offer rather than by a preference:

- **selected** — one launch over all compact rows, taking the per-row expert index
  from `sorted_experts`, which the expert scratch already builds. Covers Q4_K and
  Q5_1, which is 58 of 60 expert tensors.
- **per-expert offset** — a loop over non-empty experts offsetting into the
  stacked tensor. Covers Q5_K, Q8_0, and bf16 weights.

The selected route is the better one where it exists: the current offset loop
reads `expert_start` back to the **host** and launches one GEMV per non-empty
expert, which is a device-to-host synchronisation per layer per token. The
selected route is one launch with no sync.

`sorted_experts` is `int64` with `lanes` entries, which is exactly the
`selected_ptr` the kernels want, so no new buffer is needed.

## Validation

Real-artifact selected GEMV over `layers.0.ffn_gate_up_exps` (Q4_K, 128x1408x2816)
and `layers.0.ffn_down_exps` (Q5_1, 128x2816x704), four experts each, against a
NumPy `x @ w[expert].T` — tables above. Four different experts give four different
correct results in both cases, so the selected index is honoured rather than
ignored.

No code changed, so no test or benchmark run applies.
