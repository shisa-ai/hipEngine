# The decode-context deficit is not reproduced; device work is flat across context

## Summary

The previous entry in this session
(`20261004T064907.775042Z`, "sustained load throttles gfx1151") reported that
hipEngine's decode falls 17% from p512 to p4096 while llama.cpp's is flat, and
called it the most actionable finding in the packet. **That claim is withdrawn.**
A second harness measures decode as flat across the same two contexts, and a
kernel trace shows the device work is context-independent.

The measurement itself stands - `qwen4exp_canonical_ar_bench.py` really does
report 20.98 / 19.40 / 17.40 tok/s at p512 / 1K / 4K. What is not established
is that context causes it. **No code, default, flag or dispatch changed.**

## Changes

### What was measured

`qwen4exp_profile_gap.py --mode decode`, `--prompt-file` at 512 and 4096 tokens
(both round-trip exactly through the in-tree tokenizer), 16 decode steps,
explicit `--max-sequence-length` of 648 and 4232, cooldown to <= 50 °C before
each run, `uv run`, production profile, `--require-cached-build`:

| harness | p512 | p4096 | delta |
| --- | ---: | ---: | ---: |
| `qwen4exp_canonical_ar_bench.py` | 20.98 | 17.40 | **-17%** |
| `qwen4exp_profile_gap.py --mode decode` | 19.46 | 20.07 | **+3%** |

They disagree in **opposite directions**.

A `rocprofv3 --kernel-trace` of the two `profile_gap` runs shows why the device
is not the explanation:

| quantity (16 decode steps) | p512 | p4096 |
| --- | ---: | ---: |
| decode launches | 44495 | 44482 |
| total kernel time | 1081.8 ms | 1075.9 ms |
| `qwen35_paged_full_attn_decode_context` | 1.790 ms (n=288) | 1.799 ms (n=288) |
| `qwen35_write_paged_kv_position_tensor` | 0.550 ms (n=288) | 0.542 ms (n=288) |
| `qwen4_exp_gdn_decode_f32_kernel` | 55.6 ms (n=900) | 55.3 ms (n=900) |
| `gguf_k_pack8_prefill_out_kernel` | 563.3 ms | 557.2 ms |

Launch counts are identical, total kernel time differs by **0.5%**, and the
attention kernel - the only decode kernel whose work should scale with context -
differs by **0.5%**. Every family delta is within +/-2.2% except two sub-2 ms
kernels. **Device work in decode does not scale with context in this harness.**

## Why the two harnesses differ

They measure decode differently:

- `qwen4exp_canonical_ar_bench.py` calls `runner.step()` 128 times in one tight
  Python loop with a **single** `device_synchronize()` after the loop, and
  normalizes the whole span to 128 transitions.
- `qwen4exp_profile_gap.py --mode decode` runs 16 steps after 8 warm steps.

The canonical bench's p4096 decode rows were also taken **inside the 12-case
in-process suite** whose thermal trajectory the previous entry documents
(decode 17.68 -> 10.14 tok/s on the same case mix minutes apart), so those rows
carry a confound that the fresh-process `profile_gap` rows do not.

**Which harness is right is unresolved.** Resolving it is the next step, not a
conclusion of this entry.

## Two harness and method defects found on the way

1. **`qwen4exp_profile_gap.py --mode decode` silently under-sizes the KV cache.**
   `--max-sequence-length` defaults to **128** in decode mode and is not raised
   when `--prompt-file` supplies a longer prompt (the fixture path does raise
   it, the prompt-file path does not). A 512-token and a 4096-token decode both
   ran against a 128-slot allocation, produced the same `token_id`, and reported
   the same rate. **Any decode measurement through this harness without an
   explicit `--max-sequence-length` is invalid.** Not fixed here - it is a
   harness change, not a measurement.
2. **A profiler-derived occupancy figure is not usable.** The trace's span
   (175 ms/step) is ~3.5x the unprofiled wall (~50 ms/step) because
   `rocprofv3` serializes launches, while its kernel total (67 ms/step) is only
   ~1.35x inflated. Dividing them gives ~40%, but the unprofiled kernel total
   is close to the unprofiled wall, so the real figure is far higher. **The
   "decode is 60% idle" reading is a profiler artifact and is not claimed.**

## What the trace does establish

Same-protocol comparisons within the trace, which are valid:

- **`gguf_k_pack8_prefill_out_kernel` is 52% of decode kernel time** (563 of
  1082 ms) at **786 launches per step**.
- A decode step issues **~2781 kernel launches**.
- Both are context-independent, so both are live candidates for the decode gap
  to llama.cpp (0.80-0.96x) regardless of how the context question resolves.

## Validation

- Both `profile_gap` runs: cooldown to <= 50 °C, start/end temperature
  recorded (40 °C and 38 °C at start), `--require-cached-build`, artifact JSON
  under `benchmarks/results/2026-10-04-qwen4exp-thermal-protocol-and-llamacpp-basis/`.
- Prompt files verified to round-trip exactly: 512 ids -> text -> 512 ids,
  4096 -> text -> 4096.
- Trace comparison is same-harness, same-protocol, same step count; only the
  p512 vs p4096 pair is compared, never a profiled absolute against an
  unprofiled one.
- The retraction is recorded in the artifact README as well as here, so the
  withdrawn claim does not survive in the results tree alone.

## Limits

- One host (`gfx1151`), one model file, one quant, one execution profile, one
  category, one prompt pair. The two prompts share a 506-token prefix, so they
  differ in their last ~6 tokens and in total length - they are not
  independent contexts.
- 16 decode steps is short; a slower per-step effect that only appears over 128
  steps would not show here. This is a real limitation of the refutation.
- The `profile_gap` decode path and the canonical bench's `runner.step()` loop
  may not exercise the same runtime path; the trace covers only the former.
- No per-domain thermal or clock telemetry, so the previous entry's ~9%
  in-process prefill loss remains inferred.

## Next

- **Settle the harness disagreement first**, before any decode work is scoped.
  The cheapest decisive test is to run the canonical bench's own
  `runner.step()` loop under `rocprofv3` at p512 and p4096 and compare kernel
  totals the same way; if those totals are also flat, the canonical bench's
  decode trend is a measurement artifact and the ledger's decode rows need the
  same treatment as its prefill rows.
- Then attack the two context-independent decode facts: 786
  `gguf_k_pack8_prefill_out_kernel` launches per step (52% of decode kernel
  time) and ~2781 total launches per step.
- Fix the `--max-sequence-length` default in decode mode so the harness cannot
  silently measure a short context.
