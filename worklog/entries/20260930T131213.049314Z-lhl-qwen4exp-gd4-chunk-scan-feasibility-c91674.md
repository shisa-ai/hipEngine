# GD-4's chunked scan costs only C/384 extra FLOPs, so the build is justified at a 1.3 TFLOP/s break-even

## Summary

GD-3's screen showed the GDN recurrence is not traffic-bound; it did not show what a
chunked scan would cost. This is that screen. **The chunked scan adds only `C/384` extra
FLOPs** (+8.3% at chunk 32, +33.3% at chunk 128), so **break-even is 1.05-1.62 TFLOP/s =
1.7-2.7% of the fp32 peak**, against the **974 GFLOP/s (1.60%) the sequential route already
reaches.** The build is justified: the chunked schedule needs only to be about twice as
efficient as a route at 1.6% of peak, while exposing `C x` more parallelism.

## A wrong number of my own, corrected

An earlier pass in this session estimated the chunked scan at "16x more FLOPs" and
used it to argue the build was risky. That was wrong by a factor of three: I
compared the added `C^2 x 128` MACs against a **single** 128x128 product per token,
when the sequential route does **three** (`memory = k.S`, `state update =
k (x) delta`, `output = q.S`). The true ratio is `C/384`, i.e. 8.3% at chunk 32.

The corrected number reverses the conclusion - from "probably not worth it" to
"break-even at 2% of peak, worth building". Recording it because the wrong version
was stated confidently and would have killed a viable candidate.
