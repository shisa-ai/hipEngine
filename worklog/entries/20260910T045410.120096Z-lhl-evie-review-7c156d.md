# EVIE review: reopen memory, masking, benchmark, and profile gates

## Summary

Review of `f6df049a8` (the quoted `4ab3c17eb` plus a newline-only test
change) finds implementation and evidence blockers to the EVIE completion
claim. This decision corrects the closure assessment in
[the final handoff](20260910T043129.320110Z-lhl-evie-2e2030.md) and the
single-resident-model assumption in
[the fp16 gate handoff](20260910T042120.159635Z-lhl-evie-bb30fc.md).
It does not establish a new GPU performance result or dispute the reported
single-fixture cluster8 arithmetic measurements.

### P1: Weight padding confuses bytes with element counts

`hipengine/loading/evie.py:132` and `:149` pass `host.nbytes + weight_pad`
as a NumPy element count. The FP32 branch therefore allocates four times
the intended bytes; the FP16 branch allocates twice the intended bytes.
The upload helper uploads that entire oversized array. Applying the actual
expressions to the cached checkpoint's validated shapes gives **70.55 GiB
instead of 17.64 GiB** for strict weights, and **26.23 GiB instead of
10.36 GiB** for mixed FP16 weights, including intended 1-MiB-per-weight
padding. These are calculated allocation sizes, not measured resident RSS.
The strict branch also uploads uninitialized padding despite the stated
zero-padding policy. Use element counts plus padding divided by item size,
initialize the tail, and assert allocation bytes in a fake-runtime loader test.

### P1: Teardown does not enforce the claimed single-model residency

`tests/test_evie_gpu_runtime.py:49` and
`tests/test_evie_gpu_runtime_fp16.py:53` load owning weight maps but only
call `r.close()`. `EvieRunner.close()` (`hipengine/runtime/evie.py:174`)
does not free `loaded.weights`; `DeviceWeightMap` and `DeviceBuffer` have
no automatic destructor that does so. Module fixture teardown therefore
leaves the strict model's allocations alive when the FP16 model loads.
Given the allocation inflation above, this is directly relevant to the
reported memory-pressure incidents, although this review does not diagnose
the historical host panic.

Independently, `close()` omits its own `_scores_bufs`, `_plane16_bufs`,
and `_ptr_array_bufs` caches, allocated by helpers at runtime lines 286-340.
A mocked close with one owner in each cache frees none of them. Define
weight ownership explicitly, free all runner-owned caches, and use
exception-safe fixture teardown with memory-counter restoration assertions.
The benchmark has the same missing explicit weight cleanup.

### P1: Masked inputs misalign RoPE and leave padding active

`hipengine/runtime/evie.py:1177` and `:1206` build positions using
`lm_rope_positions`, which filters to valid tokens, but forward all original
IDs and use their unfiltered count for every layer. A three-token input with
mask `[0, 1, 1]` reaches `text_forward` with only two RoPE positions.
`evie_rope_kernel` indexes the tables by the full token index, so it reads
beyond initialized table contents into allocation padding and assigns the
wrong positions to valid tokens. No attention mask reaches the attention
or GDN kernels, and the returned embeddings are not mask-zeroed, unlike
the CPU projection contract. Process only valid tokens and restore masked
output rows, or implement masking throughout; otherwise reject nontrivial
masks before dispatch. Add left/right-padding and request-isolation tests.

### P1: Benchmark patches still have the wrong spatial order

`scripts/evie_hip_bench.py:73` flattens `(ph, pw)` in raster order. The
runtime attaches block-major position embeddings and merges each four
consecutive patches as a 2x2 spatial block. On a 64x64 image whose 16x16
patches are numbered 0-15, preprocessing returns `[0,1,2,3,4,5,...]`;
the required order starts `[0,1,4,5,2,3,6,7,...]`. The RGB/temporal fold
repair did not fix this separate spatial permutation. Reshape around both
spatial-merge axes and compare against the actual processor on a colored,
spatially asymmetric image. Existing GPU fixtures use the real processor
and therefore cannot catch this benchmark-only bug.

### P1: Torch ratios compare different workloads

`scripts/evie_hip_bench.py:187` hashes whitespace words into arbitrary IDs
and supplies an approximate chat template. The fixed example is 12 tokens;
the real processor's tokenizer plus its ten-token augmentation yields 20.
The document template and preprocessing also differ. At line 134 hipEngine
scores only eight zipped pairs, whereas `scripts/evie_gpu_bench.py:117`
scores the full 8x8 matrix. Torch encodes batches of eight and preprocesses
outside its timer; hipEngine processes single items and includes CPU
preprocessing. Different engine batch strategies can be compared if declared,
but different tokenized inputs and scoring scope cannot support the stated
same-workload ratios. Use shared processor-produced inputs, equal scoring
scope and timing boundaries, record actual shapes, and rerun before retaining
the cross-engine ratios. Internal optimization timings remain evidence about
the existing synthetic harness, with the preprocessing caveat above.

### P1: The documented production certification is not implemented

`docs/MODEL-EVIE.md:80` calls the path manifest-pinned production with a
registered strict fallback. The test module pins numerical bounds on one
query/document fixture, not a resolved EVIE variant manifest or its hash.
The runner directly selects precision and recurrence; there is no EVIE
production-plan registration connecting these selections to the execution
profile mechanism. A few primitive registrations do not supply that plan.
The document explicitly leaves retrieval ranking validation open, while
`docs/EXECUTION-PROFILES.md` sections 6.4 and 8 require task non-inferiority
and a resolved immutable plan. T1 classification does not waive those gates.
Describe FP16 as an explicitly selected experimental precision until a
retrieval-specific paired corpus/heldout gate, predeclared margins, and
profile/manifest/fallback integration exist. Do not substitute language-model
KL mechanically for the appropriate retrieval metrics.

### P2: Loader and runner precision can silently disagree

`EvieLoadedModel` does not record its precision, while `EvieRunner` accepts
an independent precision at runtime lines 125-139. Loading with FP16 then
calling `EvieRunner(loaded)` uses the default FP32 GEMM interpretation on
FP16 weight storage; the opposite mismatch similarly misinterprets weights.
Store the representation in the loaded model and derive runner precision or
reject mismatches before any GPU work. Cover both mismatch directions with
CPU constructor-contract tests.

### P2: Scratch caches grow with every distinct input length

`hipengine/runtime/evie.py:1119` retains a full 34-buffer scratch set per
exact token count until close, and attention helpers also retain per-shape
buffers. This is separate from the missing frees at close: even a single
long-lived correctly closed-at-exit runner accumulates memory across a corpus
of variable query lengths/page sizes. Fixed-shape benchmark repetition does
not expose it. Use capacity-based reuse or bounded buckets/eviction and test
that allocations plateau across many lengths.

### Additional evidence/documentation corrections

- `MODEL-EVIE.md` calls text full attention causal, but both the runtime and
  reference benchmark use bidirectional full attention. Align the description
  with the actual retrieval mode.
- The assertion that reducing recurrence time makes the unchanged GEMM share
  smaller has its direction reversed. No post-cluster8 instrumentation was
  located to support the new '~190 of ~200 ms' breakdown; label extrapolation
  as such or collect a fresh trace. This does not imply INT8 would be worthwhile.
- The cluster8 artifact calls a nonzero reduction-order difference 'T0/T2'.
  Distinguish algebraic equivalence, repeatability, declared fixture tolerance,
  and parent-byte equality rather than treating them as interchangeable.
