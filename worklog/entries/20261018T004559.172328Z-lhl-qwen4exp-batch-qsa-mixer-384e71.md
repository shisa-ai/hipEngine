# Independent-request dense QSA token mixer over batch state

## Summary

Adds the N-request form of the dense QSA decode mixer on top of the committed
request-owned batch attention state (`3f096fe5a`). `run_qwen4_exp_dense_qsa_token_mixer`
(`runtime/qwen4_exp_runner.py:2425`) stays the strict single-row oracle; the new
`hipengine/runtime/qwen4_exp_batch_qsa.py` runs the same dense arithmetic for N
independent requests, one dispatch per stage instead of a loop of single-row
mixers.

Each row is an independent request: its own physical slot, its own page table,
and its own position. The mixer consumes `Qwen4ExpBatchAttentionState.prepare`'s
active rows and never re-uploads, reorders, or re-derives them.

This is the task-21 mixer unit. It is not wired into the runner and carries no
production qualification: no generation/server/default change, no new kernel, no
registry or profile edit.

## Changes

- `hipengine/runtime/qwen4_exp_batch_qsa.py` (new, 444 lines):
  `run_qwen4_exp_batch_dense_qsa_token_mixer(mixed_ptr, weights, *, attention_state,
  scratch, rows, hidden, query_heads, kv_heads, head_dim, rotary_dim, theta,
  dense_equivalent_limit, rope_positions_ptr=None, attention_context_limit=None,
  eps=1e-6, stream=0, runtime=None)`. Stage order matches the oracle's dense path,
  one launch each:
  1. `attn_q` (2x `query_heads*head_dim`), `attn_k`, `attn_v` through
     `launch_gguf_linear` with `rows=N`, F32 activation/output (the registry
     resolves the variant; no backend or quant branch here).
  2. `qwen4_exp_qsa_split_norm_rope_rows_f32` (or `..._mrope_rows_f32` when
     `rope_positions_ptr` is given) reading `active.position.ptr`, writing query,
     key, and the gate split for all N rows.
  3. `qwen35_write_paged_kv_f32_batch_spans` with `active.append_spans` and
     `rows=N`.
  4. `qwen35_paged_full_attn_decode_context_bf16_batch_spans` with
     `active.decode_spans`, `rows=N`, and the context limit.
  5. `qwen4_exp_qsa_gate_context_f32` over `rows * query_heads * head_dim`.
  6. `attn_output` projection `[N, q_width] -> [N, hidden]`.
  Returns `scratch.output`; reuses the existing `Qwen4ExpQSAMixerDeviceWeights`
  and `Qwen4ExpQSAScratch` types, so no runner edit was needed.
- `_validate` admits a call before the first dispatch: closed/closing state and
  scratch, runtime identity across the three owners, positive geometry, even
  `rotary_dim <= head_dim`, `query_heads % kv_heads`, `head_dim <= 256`,
  finite positive `theta`/`eps`, head geometry equal to the state cache,
  `block_size == 256` (the dense decode wrapper's ABI, checked here so a
  misconfigured state cannot write a token the decode cannot read), required
  projections and non-zero Q/K norm weights, an 8-byte-aligned MRoPE position
  pointer when one is given, the four projection source shapes, `rows == prepared
  active rows`, `rows <= state_slots`, context limit within
  `[max_context_len, max_positions]`, block-table coverage,
  `live_counts`/page-table element counts matching `rows`, every prepared row
  within `dense_equivalent_limit`, and per-buffer scratch capacity for that row
  count and head geometry.
- `dense_equivalent_limit` is a required keyword argument, not a hint. The caller
  states the context length up to which dense attention is equivalent to the
  sparse path (the bound the runner's index state carries); a row whose context
  exceeds it is rejected with its row index before the first dispatch. Sparse
  index selection is not implemented in this mixer, so this bound is what stops
  a future integration from silently computing dense attention where sparse
  selection is required. Passing a bound that covers the rows is the explicit
  way to ask for diagnostic dense attention.

### Post-KV check audit

The KV write is stage 3; the decode, the gate, and the output projection run
after it, so any argument they reject is a partially mutated cache. Each one's
preconditions, against what `_validate` now covers:

| Wrapper check after the write | Status |
| --- | --- |
| `_check_decode_shape`: uniform spans, bf16 storage, int64 `live_counts` | state-constructor invariant, not caller-reachable |
| `max_context_len > 0`, `block_size == 256`, `base_offsets.numel > 0` | validated |
| `num_q_heads`/`num_kv_heads` positive and divisible | validated |
| `head_dim > 0` | validated |
| `head_dim <= 256` | **was unvalidated → added** |
| `ceil(max_context_len/block_size) <= block_table_len` | validated as `needed_blocks <= blocks_per_request` |
| `live_counts.numel >= rows`, `rows >= 1` | validated as equality with the prepared row count |
| gate: `elements > 0` | validated (`rows * q_width`) |
| `attn_output` projection geometry | **was unvalidated → added** (source-shape preflight for all four projections) |
| `attn_output` dispatch resolution | not preflighted: the variant depends on the env-selected GEMM policy inside `launch_gguf_linear`, so a duplicate preflight could resolve a different variant than the real launch and reject a valid call. Residual failure mode: a missing registry route surfaces after the write |
| `_check_write_batch_shape` (the write itself): `max_live_count < block_size * table_len_per_row` | state-constructor invariant (`max_positions - 1 < block_size * ceil(max_positions/block_size)`) |

- `tests/test_unit_qwen4exp_batch_qsa_mixer.py` (new, 11 tests): every device call
  is a module-level name, replaced by recorders. Asserts the exact dispatch
  sequence (3 input projections, split+RoPE, KV write, attention, gate, output
  projection), one call per stage, `rows=N` on each, the pointers and metadata
  that reach each kernel (`active.position.ptr`, `active.append_spans`,
  `active.decode_spans`, the context limit, `rows*q_width` gate elements),
  `rows=1` degenerate shape, the mrope variant selection, context-limit override,
  and that 27 malformed-metadata cases dispatch nothing at all, including the
  review cases: non-finite/negative `theta` and `eps`, zero and misaligned
  `rope_positions_ptr`, mismatched `attn_k`/`attn_output` source shapes, and a
  prepared row over `dense_equivalent_limit`. Two more review cases get their own
  tests: `head_dim=512` against a fully matching 512-wide state and scratch, and
  the dense-equivalent boundary (context 21 admitted at limit 21, row 1 rejected
  at limit 20 with no dispatch). Also covers unprepared/closed/closing states and
  a non-256 block size.
- `tests/test_gpu_qwen4exp_batch_qsa_mixer.py` (new, 3 tests / 5 items): small
  valid dense F32 GGUF weights (`tests/test_gpu_qwen4_exp_runner_gr._dense_f32_weight`),
  hidden 8, 2 query heads, 1 kv head, head_dim 4, rotary 4, block 256,
  4 slots x 1024 positions. Tokens `0..position-1` are bulk-filled from
  CPU-computed K/V into each row's own blocks, then the mixer appends token
  `position` and decodes. C1 (`slots=[1]`, position 256), C2 (`[3,1]`, 255/256),
  C4 (`[2,0,3,1]`, 3/255/256/700) are compared against independent
  `run_qwen4_exp_dense_qsa_token_mixer` runs on `Qwen4ExpDenseAttentionState`
  with the same `max_positions`, and against the `qsa_sparse_gqa_attention` CPU
  oracle. Because these weights carry real GGUF tensor-info shapes, the new
  projection-geometry preflight is exercised on the passing path too, not only
  by the rejection case.

The first command includes the two pre-existing strict single-row mixer tests, so
the c1 oracle path is unchanged.

GPU measurements (W7900 gfx1100, kernels JIT-built for the detected target):

| case | rows | positions | max abs(c1 - batch) | max abs(oracle - batch) |
| --- | --- | --- | --- | --- |
| C1, slot [1] | 1 | 256 | 8.73e-11 | 2.85e-06 |
| C2, slots [3,1] | 2 | 255, 256 | 2.33e-10 | 3.74e-06 |
| C4, slots [2,0,3,1] | 4 | 3, 255, 256, 700 | 0.0 | 2.16e-05 |

Row-count-dependent GEMM variants are not asserted bit-identical: C1/C2 are
compared to the c1 mixer with `atol=2e-5` and C4 measured exactly equal. The CPU
oracle is compared at `rtol=2e-4, atol=2e-4`. The residual is the rows>1 versus
rows=1 projection variant plus the batch decode kernel's 1024-thread geometry
when `rows <= 2 and max_context_len < 1024`; no attempt was made to force parity.

Exact control asserted on every case:

- `state.active.slot_ids == slots`, `active_rows == rows`,
  `position_host[:rows] == positions`, and `block_table_host[:rows]` equals
  `block_host[slot]` per row after the run: the mixer consumed the prepared
  metadata and changed none of it.
- Each row's appended token K lands at
  `block_host[slot][position // 256] * 256 + position % 256` and is bit-identical
  to the CPU bf16 K for that row, so the KV write used the right slot and
  position for every row (this is what would break first under cross-request
  aliasing).
- Slots outside the active set stay bit-zero across both caches, and everything
  above `position + 1` inside a written slot stays zero.
- A repeated run with the same prepared rows and cache reproduces the output
  bytes exactly.

## Next

- Runner integration (not done here): `runtime/qwen4_exp_runner.py:8849-8861`
  still passes `attention_state=self.attention_states[binding.qsa_state_index]`
  with `rows=1` and `position=self.position`. Wiring this mixer needs the runner
  to own one `Qwen4ExpBatchAttentionState` per QSA layer, a request-to-slot
  assignment with `prepare`, and an explicit state move on slot compaction. The
  integrator must also supply `dense_equivalent_limit` per call: the value on
  `Qwen4ExpQSAIndexDeviceState` (`block_budget * compression_ratio +
  compression_ratio - 1`, `runtime/qwen4_exp_runner.py:1272`). The per-row test
  here matches the runner's own dense/sparse boundary at
  `runtime/qwen4_exp_runner.py:2504` (`position + 1 > dense_equivalent_limit`
  selects the sparse path).
- Dense-only by construction: sparse index selection is not implemented here.
  `dense_equivalent_limit` is required and enforced per row, so an integration
  cannot run dense attention past the bound; it has to route those requests
  through the sparse path (or pass a bound that covers them, which is an
  explicit diagnostic-dense request). There is no `index_state`,
  `device_position_owned`, or selected-position path here.
- No production-profile gate was run. This unit's evidence is a CPU oracle plus
  a c1 mixer comparison on fixture weights; the calibrated
  mean/p95/p99/max KL, top-1-by-category, determinism/isolation, BF16-relative,
  and task gates in `docs/EXECUTION-PROFILES.md` still have to be run on a real
  checkpoint before any promotion or speed claim.
- Not covered: prefill chunks and verify/MTP rows. Those are sequence and
  candidate rows sharing one position space, not independent requests, and must
  not be admitted as active rows of this state.
- `_validate` re-derives scratch capacity from buffer byte counts because
  `Qwen4ExpQSAScratch` does not record its `rows`/`hidden`; a stored geometry
  would be cleaner if the scratch type is ever extended.
- Residual post-KV failure mode (see the audit table): a missing registered route
  for the `attn_output` projection still surfaces after the KV write. Preflighting
  it would have to duplicate `launch_gguf_linear`'s env-selected GEMM policy, which
  risks rejecting valid calls; the GPU tests cover the configured policy end to
  end instead.
