# DPP wave reduction in the Q8 prefill leaf: bit-identical, 1.5-1.7%, and the launch order is refuted

## Summary

The Q8 dense prefill leaf (`coltile8_rowbatch4_wave_scale_pipelined_f32_f32_out`)
is the single most valuable kernel in a Flash-Next prefill: 10070 ms of a 22046 ms
`code-p4096`, 45.7% of the total, running at 3327 GFLOP/s against a measured
16467 GFLOP/s for its own instruction mix. The tile space is exhausted and
pipelining depth 1 is already promoted, so this unit asked what the disassembly
says instead of what the traffic model says.

**Disassembly, not a model.** 378 static instructions, of which the largest class
is `ds_bpermute_b32` at 128 per thread - the wave reduction's five `__shfl_down`
levels, one LDS round trip each - plus 113 `s_waitcnt` (mostly `lgkmcnt`) and 130
adds to go with them. The tree is 4 rows x 8 cols x 5 levels = 160 shuffle ops per
thread for 32 accumulators, about 40% of the static stream.

**Two changes, one win, one negative.**

**1. DPP reduction: promoted, bit-identical, 1.5-1.7%.** The file already carries
`h7c_reduce_wave_accumulators_dpp` for the q6_k prefill kernels. It folds the same
pairs in VALU (`v_permlanex16`, then `v_mov_dpp` row shifts 8/4/2, then
`v_add_f32_dpp row_shl:1`) with no LDS access at all. **It is the same tree**, so
it is an implementation swap: bit-identical on the raw `uint32` bits at eight
shapes and against the wave-scale grandparent. 378 -> 309 static instructions at
**identical** VGPR (76) and occupancy (25 waves/CU), and 15.8936 / 15.8694 /
15.8689 / 15.8438 / 15.8465 ms against the parent's 16.1395 / 16.1421 / 16.1266 /
16.1177 / 16.1191 on layers 0/9/22/34/46, **mean -1.64%**, all five layers winning.

Promoted as the preferred leaf behind `HIPENGINE_QWEN4_EXP_Q8_DPP_REDUCTION`
(default on). The rewrite is `is_registered`-guarded so the chain degrades DPP ->
pipelined -> wave-scale parent -> unscaled exact parent, and the flag is in the
dispatch memoization key so a flip inside one process cannot replay the other arm's
leaf. The engine-level gate passes: three arms, five hashes identical, and the DPP
leaf's call count is 0 / 1072 / 0 - engagement recorded, not assumed.

**2. Launch order: free, bit-identical, and 2.1-2.9% slower.** `ROW_FIRST` swaps
which grid axis carries the column tile. The default sweeps all 1280 weight slices
of one row batch before any is needed again (27.85 MB of weight plus 10.49 MB of
activation against a 32 MB MALL); `ROW_FIRST` keeps one 21.8 KB slice resident
across the row sweep. Identical VGPR, identical instruction count, identical bits -
and slower on all five layers.

**This is the third independent refutation of the traffic reading of this kernel
family.** If the weight re-read were the binding cost, keeping the slice resident
could not lose; sequential streaming is better because it is what the hardware
prefetches. Together with the GR up result in this session (halving a modelled
90.3% re-read costs 16%) and `HC-3` (removing 4.2% of modelled traffic costs 2%),
the consistent reading is that these kernels are latency-bound and their cost is
instruction structure and stall exposure, not bytes. **So the 6.2x gap is not
closable by any locality change**, and the next target is the operand
representation - see Next.

## Validation

- `tests/test_gpu_qwen4exp_q8_dpp_reduction.py` + the existing pipeline file: 25
  passed.
- Leaf A/B: 5 layers, 20 repetitions, `bit_identical_to_production: true` with
  `max_abs_diff_vs_production` 0.0 on all 15 rows of both runs; the pipelined
  parent reproduces its recorded 16.1369 ms mean.
- Register census: DPP 76 VGPR / 309 instructions against the parent's 76 / 378, so
  the win is the removed LDS round trips and not a resource change.
- State gate: `status: passed`, `exact: true`, five hashes identical across three
  arms, DPP call count 0 / 1072 / 0.
- The state gate's `step_seconds` are single diagnostic steps and are explicitly
  **not** used as a rate; no prefill wall claim is made from them.

## Next

- **The prefill gap needs the operand representation, and the measured route is
  already in the tree.** `dense_wide256_f32_f32_out` runs this same operation in
  **2.570 ms against 17.319 ms, 6.74x**, on identical resources and launch geometry
  (256 VGPRs, 55296 B of LDS, grid 20480x4). It is registered but not a default for
  exactly one reason: f16 operands put it at 2.83e-03 against the exact float64
  reference and **no production gate has been run**. `AGENTS.md` is explicit that
  the binding contract is production correctness and that a candidate which is not
  bit-exact must be re-reviewed under the production gates before any rejection, so
  that gate is the next action - not another pass over this leaf. A timing-only
  probe of the same kernel reading a pre-converted f16 activation runs 1.303 ms
  against the comparator's 1.339 ms, which attributes the remaining gap to the
  activation representation rather than to the kernel.
- A 1.64% leaf gain is about 165 ms of a 22046 ms prefill (0.75%) on the recorded
  role attribution - worth keeping, and not worth another campaign.
