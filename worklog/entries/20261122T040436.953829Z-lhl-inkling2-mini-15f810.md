# Isolate FP16 KV rounding in the pinned Inkling output comparison

## Summary

Rounding K/V inputs to FP16 at the cache boundary did not explain the first observed ordinary-output difference against Loom. It left the short divergence at the same point and introduced earlier divergence at 575 input tokens.

## Changes

- No runtime changes. The scratch wrapper rounds the prepared keys and values through FP16 on both single-token and block paths before their existing FP32 HIP transfers. It does not change physical cache allocation, query arithmetic, or scheduling.

## Validation

- On `strixhalo` (`gfx1151`), hipEngine `d449f14d2` and the pinned Loom Q4_K_XL, `python -u ./hipengine_inkling_fp16_rounding_pilot.py ./hipengine_inkling_ordinary_output_pilot.py "$model" "$tokenizer"` ran the [same inputs and greedy generation settings](20261122T040138.321705Z-lhl-inkling2-mini-78ad60.md) as the FP32 pilot. Prompt digests remained the same; both returned 128 tokens with a length finish. Both scalar and block cache paths ran, with finite rounded inputs. Timing is not meaningful with the extra host casts.
- The 47-input reasoning shared 115 characters with Loom under either cache rounding. The 575-input reasoning shared 131 characters at FP32 and 75 with FP16 rounding. Within hipEngine the first changed generated token was at zero-based index 40 and 16 respectively. This rules out FP16 cache rounding alone as an explanation, not all interactions with Loom's other arithmetic. Log: `/tmp/kendex-pi-bg/bg-56-1795320167244.log`.
