# two keys per warp iteration cut the 512-wide prefill attention by 15 percent

## Summary

`#pragma unroll 2` on the warp-per-key loop in pass 1 of
`gemma4_attention_prefill_kernel` lets the compiler interleave two independent
shuffle chains instead of serializing one. It is bit-identical and worth 15
percent on the 512-wide geometry:

| case | before | after | change |
| --- | --- | --- | --- |
| swa 256d 16q/8kv window=1024 | 5.04 ms | 5.25 ms | within noise |
| swa 256d 16q/8kv window=0 | 4.82 ms | 5.36 ms | within noise |
| full 512d 16q/2kv window=0 | 8.05 ms | **6.84 ms** | **-15%** |
| model's 30 attention layers | 173.1 ms | 165.5 ms | -4.4% |

`#pragma unroll 4` measures 166.1 ms against unroll 2's 165.5, so two is enough;
deeper unrolling adds register pressure without adding ILP.

The loop metric does not move: 581-586 tok/s against a 580-587 baseline. That is
expected rather than disappointing. The whole gain is the five 512-wide layers
(40.3 -> 34.2 ms, -6.1 ms), and the 25 sliding layers are unchanged, so it is
about 0.7 percent of the 864 ms prefill step -- below what three samples can
resolve. The kernel-level measurement is unambiguous, the change is
bit-identical, and it costs one pragma, so it is kept on the evidence of the
targeted bench rather than the end-to-end one.

## Why this and not the query tile

The query tile tried earlier was rejected because it traded occupancy for ILP
and lost. This is the same underlying diagnosis with a different intervention.
Reading the kernel's own comment at the pass-1 loop:

> Doing that per key costs eight `__syncthreads` rounds per key, which is the
> whole cost of this kernel (measured 147 GFLOP/s and ~5.3 us per key at 512
> tokens, invariant to the work inside the key iteration). One warp per key runs
> the same tree in registers instead.

So the per-key barrier was already found and already fixed, and it was worth
roughly 3x (147 -> 405-446 GFLOP/s). What remains is the reduction the warp path
still has to run. Counting it for `head_dim = 256`, per key per lane: 8 multiply,
8 K loads, 7 intra-lane tree adds, **5 shuffles plus a final `__shfl_sync`**, a
mask load, a scale, a max, and a lane-0 store -- on the order of 700 instructions
for the key's 256 MACs. The shuffles are about a quarter of that and are pure
latency. The tile attacked the *rows* and shared K/V; this attacks the *keys*
within one warp's own loop, which is where the serial dependency actually is.

The mask test is per key rather than per lane, so the branch is warp-uniform and
does not diverge -- which is what makes the loop unrollable at all. That is worth
noting for the next change here: the branch looks like an obstacle to unrolling
and is not one.

## Roofline context

`docs/ROOFLINE.md` puts this in scale. INT8 `v_dot4` is 123 TOPS and BF16 WMMA
is 123 spec / **84.8 measured** on this class of part. The dense linears run at
5000-8000 GFLOP/s, which is 6-9 percent of the measured WMMA figure, and
llama.cpp on this same model at 1012.98 tok/s works out to about 3.6 TFLOP/s
against our 2.07 -- 4.2 percent of the same ceiling against our 2.5. So the
practical ceiling in this regime is around 4-5 percent, we are at half of it, and
the remaining 1.7x is not going to come from any single kernel running near peak.

Two entries in the doc's §11 "what not to chase" table predicted the two negative
results in the preceding units exactly, and are worth quoting because they are
about decode and the mechanism transfers:

- *"Naive dp4a on AWQ/pack8 layout ... activation quant overhead dominated"* --
  which is what the Q8_0 MMQ route measured, and why it lost.
- *"LDS staging in any form ... L1/L2 already adequate; barrier cost exceeded
  savings"* -- which is the per-k-step tile load and barrier in the MMQ kernel,
  and the likely reason its rate falls monotonically with `k_iters`.

Both were tried here without that context and rejected on measurement, which is
the expensive way to learn what the doc already says.

  --iters 3 --warmup 1`, the same instrument the earlier attention units used.
- Metric before and after: 580-587 and 581-586 tok/s.
- Bit-identity is by construction as well as by test: the two unrolled
  iterations touch disjoint keys, and no pair of values is added in a different
  order, so each key's tree is the same tree.

## Next

- The 256d sliding geometry is unchanged at ~5.25 ms and is now the larger of
  the two attention costs (130.5 ms against 34.2). Its K/V traffic is only
  ~51 GB/s, so it is not bandwidth-bound either; whatever bounds it is the same
  reduction cost the 512d case just improved, and the unroll did not reach it.
- The decision tree's remaining branch for a compute-bound bucket with high AI
  is instruction mix, and the count above says the reduction tree is the
  instruction. A version that assigns fewer lanes per key would cut the tree
  length but changes the summation order, so it is an arithmetic candidate
  rather than a free win.
