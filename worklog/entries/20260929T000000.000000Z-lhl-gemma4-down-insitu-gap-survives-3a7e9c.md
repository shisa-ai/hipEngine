# the down projection's in-situ gap survives five more explanations

## Summary

`20260928T233500` left one number unmatched: the down projection runs at **2.34 TMAC/s in situ
against 2.95 in its own microbench**, a 21 percent gap larger than any of the three effects
tested there. This entry tests five more explanations. **Four are eliminated, one is a real
effect worth 7 percent, and the gap survives them all.**

## What the routed distribution costs: 7 percent, measured

The microbench defaults to a uniform 32 rows per expert; the prefill's router does not. That is
a real difference and it is measurable:

| distribution | GMAC/s | median | `row_passes_at_32` |
| --- | ---: | ---: | ---: |
| uniform | 3022 | 2.687 ms | 128 |
| **poisson** | **2800** | **2.897 ms** | **192** |

**The routed distribution costs 7.4 percent, and the mechanism is visible in the pass count:**
uneven experts need 192 tiles for 4091 rows where uniform needs 128 for 4096, so **tile-rounding
waste is 50 percent more weight traffic.** This is a property of the engine, not of the kernel,
and it is the first honest partial explanation of the gap.

It also explains a number from `20260928T231000`: more rows per expert helps *under poisson*
(2867 at 32 rows, 3056 at 64, 3176 at 128), because a larger expert amortizes the tile-rounding
waste. Under uniform the same sweep was nearly flat. **The uniform default was hiding the
effect.**

## Four eliminations

| explanation | result |
| --- | --- |
| **launch bounds / occupancy** -- `__launch_bounds__(128, 4)` caps 512 threads per CU | `(128, 8)` gave 2871 against 2843 GMAC/s, **1 percent, within noise** |
| **DS4 activation planes** -- more planes would multiply the work | **The route uses one.** `_MMQ_ACTIVATION_PASSES = 1` at `gemma4_experts.py:95`, and the measured cost is linear: 2874, 1702, 1215 GMAC/s at 1, 2, 3 planes |
| **weight traffic** (from `20260928T231000`) | 4x traffic costs 3 percent |
| **K staging width** (from `20260928T224000`) | at most 10 percent, nothing at the production K depth |

All edits reverted; the tree is at HEAD.

**The planes elimination is worth stating plainly because it was a live hypothesis.** The
constant's own comment records the decision: three planes are 22x more accurate (0.030 against
0.655 percent relative) and cost 10.0 percent of prefill at 512 tokens and 11.2 at 1024, and it
is held at 1 because raising it changes the arithmetic of a production default and needs its
execution-profile gate. **That is a measured, documented, gated tradeoff, not an oversight, and
it is not the in-situ gap.**

## Where that leaves the gap

The down projection's in-situ 3.58 ms per layer against the microbench's 2.85 at the same row
count is **1.27x**, and it survives: distribution, occupancy, planes, traffic, unrolling, and K
width. The decomposition's own inference stands and is now better supported:

> The two 49 GB/s figures agreeing to 0.4 percent across two different quantizations and two
> different kernels is itself information: it says the rate is set by something shared -- the
> pass structure, **the activation load path**, or the launch geometry -- rather than by either
> kernel's arithmetic.

**Launch geometry is now eliminated. That leaves the pass structure and the activation load
path**, and the activation load path is the one that has not been touched. The Q5_1 kernel
reads activations from global memory per row with a stride of `ds4_blocks * x_block_bytes`,
two `uint4` loads per row per sub-block, and no shared-memory staging.

## A correction to how this was being measured

**The microbench cannot reproduce the in-situ number, so it is the wrong instrument for this
gap.** It reproduces the kernel's own rate well -- uniform and poisson both land in the 2.8 to
3.0 TMAC/s band the decomposition reports -- but the 22 percent that separates the microbench
from the real sequence is invisible to it by construction. `scripts/gemma4_expert_mmq_wrapper_split.py`
times each part in place with a HIP event pair on the compute stream and is the instrument that
can see it.

## Next

- **The activation load path is the last named suspect.** It is the only item in the
  decomposition's own list that has not been tested, and the kernel reads activations from
  global memory per row with no shared-memory staging.
- **Measure any candidate change in place with `gemma4_expert_mmq_wrapper_split.py`.** The
  microbench cannot see the gap, so a microbench win is not evidence about the gap.
- **Do not re-test distribution, occupancy, planes, traffic, unrolling, or K width.** All six
  are eliminated above with their numbers.
