# The Gemma 4 D2H abort is wider than recorded, and is not the window-parameter change

## Summary

Validating the AOTriton window-parameter commit (`3d084638d`) with the CPU
deterministic bundle surfaced a hard failure. Every candidate explanation
pointing at that commit was tested against the commit's own parent, and **the
failure reproduces identically without the change**. Along the way the blast
radius turned out to be larger than the worklog records: **a second test file
is affected, and it is not the one P12 documented.**

## The failure

Fatal Python error: Aborted
  hipengine/core/hip.py:114        memcpy
  hipengine/core/memory.py:185     copy_device_to_host

  hipengine/runtime/gemma4.py:765  _forward_block

| `tests/test_unit_gemma4_runner.py` | `test_runner_prefill_matches_the_reference` (line 203) |

## Not the window-parameter change

Both files were run twice each — once at `3d084638d`, once with the two
modified files reverted to the parent `68e49c4ad` — with a `trap` restoring
HEAD afterwards and `git diff HEAD` confirmed empty after every run.

| | with change | at parent |
| --- | --- | --- |
| `test_unit_gemma4_runner.py` | **EXIT 134**, 1 fatal, `gemma4.py:907` | **EXIT 134**, 1 fatal, `gemma4.py:907` |
| `test_unit_gemma4_generate.py` | hang past 780 s | **EXIT 134**, 72 s, `gemma4.py:907` |

Identical exit codes, identical fatal counts, identical stack frames. The
generate file's symptom varies between abort and hang across runs, so the
difference in that row is nondeterminism in a stuck operation, not a
signature of the change.

A second line of evidence rules out the ABI concern directly: `window_left`
and `window_right` were inserted **before** `stream` in the shim's parameter
list, so a stale 13-parameter `.so` loaded under the new 15-argument
`argtypes` would put `-2147483646` where `stream` belongs. There is no
shipped shim binary — `find` over the tree returns only `libaotriton_v2.so`,
the AOTriton library itself, and `hipengine/core/build.py` keys builds on
source bytes — and the parity test, which drives this exact wrapper on the
GPU, passes.

## What is newly known: a second file

P12 documented the hang for `test_unit_gemma4_generate`, and P9 records "two
pre-existing hangs" there. **`tests/test_unit_gemma4_runner.py` is not among
them** — P12's two hits on the string are `test_unit_gemma4_runner_**lifecycle**`,
a different, passing file.

That matters because this file used to pass: entries from 2026-09-22 through
2026-09-24 record `tests/test_unit_gemma4_runner.py` — 9 passed, and again in
the RED/GREEN contract entry. Nothing in the worklog records it failing. So
this is a **regression that landed after 2026-09-24**, and it is currently
invisible to anyone reading P12's note, which scopes the problem to one file.

## Effect on validation

The CPU deterministic bundle (`python3 -m pytest -q`) **cannot complete**:
it aborts inside `test_unit_gemma4_runner.py` at 7 %. Its other members all
pass — `compileall`, `check_fixtures`, and all three `smoke.py` modes
(`registry`, `cpu-fixtures`, `smoke-add-plan`) are green, and the full
`-k aotriton` selection is 0 failed / 0 errors.

The narrow tier for this change is unaffected and green:
`test_gpu_gemma4_attention_aotriton_parity.py`,
`test_unit_aotriton_wrap_exception_boundary.py`,
`test_unit_aotriton_discovery.py`.

## A process note

The first background run of the bundle reported **success (exit 0)**. It was
wrong: the shell sequence used `;` separators, so pytest's exit 134 was
discarded and the trailing `echo` supplied the code. The green banner was a
proxy signal, and reading the log rather than the status is what surfaced the
real result. Worth remembering for any batched command whose value is its
exit code.
