# Prefill block width re-test: 64 vs 128 vs 256 vs 512 (fast profile)

## Summary

Re-tested `Inkling2GGUFGenerator.prefill_block_width` on the packed public
route (`execution_profile="fast"`, 575-token prompt, greedy, 8 output tokens,
`prefix_cache=off`, W7900, `Inkling-2-Mini-UD-Q4_K_M-mainline.gguf`) via
`scripts/inkling2_prefill_width_probe.py`, one process per width:

| width | runs (s to first text) | mean | output ids (all runs identical) |
|-------|------------------------|------|-------------------------------|
| 64    | 6.31, 6.30, 6.18       | 6.26 | 68014 31485 154710 68014 38522 174941 198 371 |
| 128   | 5.85, 5.85, 5.90       | 5.87 | identical |
| 256   | 5.93                   | 5.93 | identical |
| 512   | 5.94, 5.98             | 5.96 | identical |

128 (~0.4 s, ~6.5% TTFT) is the only width that helps; gains saturate by 256.
Per-visit expert traffic math says saving ~4 block-passes of the expert bank
(~4 GB at 0.5625 B/weight) should be ~20-50 ms, so the observed delta is in
the host/dispatch envelope, not bandwidth. Replicates the earlier strict-
profile finding that width alone is not a prefill lever on W7900, now under
the `fast` profile.

Generated token ids are byte-identical across every width and run — no
correctness drift from widening the block on this prompt.

Default NOT flipped: one host, one prompt, single-run 256/512. Needs Strix
Halo confirmation before changing the shipped `prefill_block_width = 64`.

## Changes

- `scripts/inkling2_prefill_width_probe.py` (new; one width per process,

## Validation

- Four probe invocations per width group above; identical output ids across
  all 8 runs.
- Not a gate: no production code changed.
