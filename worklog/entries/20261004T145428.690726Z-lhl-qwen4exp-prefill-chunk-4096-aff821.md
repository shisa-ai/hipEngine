# The prefill chunk capacity guard is implemented: production takes the largest chunk its admission can afford

## Summary

**The campaign measured the 1024 -> 4096 chunk step three times, agreed on the
design (a capacity guard), and never implemented it. It is now implemented.**
The production path takes the **largest chunk whose admission still yields the
requested context**, falling back 4096 -> 2048 -> 1024 when the device cannot
afford it, and it keeps the **full native 262144-token context** on this host.

The guard exists because `RT-3` established the workspace is **context-aware,
not prompt-aware**: rows are `min(chunk, max_sequence_length)` and the runner's
`max_sequence_length` comes from the model's native context, so in a serving
session the larger chunk is paid at construction for **every** session
regardless of traffic. That is why a blanket default flip is the wrong form and
the guard is the right one.

**This unit is a self-correction.** I first wrote a blanket `4096` flip, then
found `benchmarks/README.md` already recording the 1024 -> 4096 step as
**measured and not promoted**, and `RT-3` already naming the capacity guard as
the lever. The blanket flip was reverted before commit and replaced with the
guard the campaign asked for.

## Changes

- `hipengine/generation/qwen4_exp_gguf.py`: new `_select_prefill_chunk`
  capacity guard and `_AUTO_PREFILL_CHUNK_LADDER = (4096, 2048, 1024)`.
  `prefill_chunk_size=None` now means "let the guard choose"; the constructor
  records the choice as `self.admitted_prefill_chunk_size`. Both callbacks are
  pure arithmetic on the residency plan, so the **whole ladder is evaluated
  before any weight is materialized** — a fallback costs no device memory and no
  time.
- `hipengine/generation/qwen4_exp_gguf.py`:
  `make_qwen4_exp_ud_q4_k_xl_generator_gfx1151` passes `None` when the caller
  gave no chunk, so the qualified production factory is what invokes the guard.
- `hipengine/generation/qwen4_exp_profiles.py`: `_bind_default_chunk` binds
  `admitted_prefill_chunk_size` when the guard ran, keeping the pre-binding
  allocation and the bound runner chunk consistent; it keeps the 1024/512
  fallback when no admission ran (a caller-supplied resident runner).
- `tests/test_unit_qwen4exp_chunk_default.py`: 12 tests, including direct
  coverage of the guard — largest-rung selection, context-driven fallback,
  `MemoryError` fallback, re-raise when no rung fits, and the
  unreachable-context case.

### What this unit measured that was not already recorded

The campaign had the 1024 -> 4096 step at `-4.94%` prefill (`RT-1`), the gate
re-run passing bit-identically at chunk 4096 (`X-6`), and the memory cost as
`+4.96 GB` (`RT-1`) / `+5.31` and `+10.63 GiB` at native context for c1/c2
(`RT-3`). Three things were new:

**1. Decode improves rather than regresses.** `code-p4096`, production, 6 samples
per arm, interleaved A/B/A/B:

| chunk | prefill tok/s | spread | decode tok/s | spread |
| ---: | ---: | ---: | ---: | ---: |
| 1024 (was production) | 279.28 | 1.03% | 18.127 | 1.30% |
| 2048 | 292.59 (+4.77%) | 0.72% | 18.152 (+0.14%) | 0.71% |
| 4096 | **302.81 (+8.43%)** | 1.13% | **18.431 (+1.68%)** | 1.24% |

The earlier 1024-against-512 trade recorded **-1.15% decode**, so a decode cost
was the expected direction for a larger chunk. At 4096 decode is **+1.68%**, so
the step is not a prefill-for-decode trade.

**2. Chunk 2048 is free.** The scratch reservation is
`max(4 GiB per-runner floor, mandatory + wide-f16 staging)` and is linear in
the chunk until it crosses the floor:

| chunk | staging (host) | scratch (reserved) | required | context tokens |
| ---: | ---: | ---: | ---: | ---: |
| 1024 | 20.97 MB | 8.59 GB | 112.62 GB | **262144** |
| 2048 | 41.94 MB | **8.59 GB** | 112.65 GB | **262144** |
| 4096 | 83.89 MB | 15.39 GB | 119.49 GB | **262144** |

**2048 stays under the floor and costs no device memory**, which makes it the
correct fallback rung rather than a dead intermediate.

**3. A same-session asymmetry.** In the **strict** profile chunk 4096 is
*slower* (70.56 vs 72.35 tok/s, `-2.48%`), while in production it is 8.43%
faster. The gain belongs to the production tile path, whose efficiency grows
with the row batch; it is not a property of chunking as such.

### Numerical qualification

Layer2 gate, `--candidate production_baseline --prefill-chunk-size 4096`
(18 prompts / 450 rows / 3 repeats / 32-token free outputs):

| axis | value | threshold | margin |
| --- | ---: | ---: | ---: |
| kl_mean | 3.039e-4 | 1e-3 | 3.3x |
| kl_p95 | 1.785e-3 | 5e-3 | 2.8x |
| kl_p99 | 4.271e-3 | 2e-2 | 4.7x |
| kl_max | 7.771e-3 | 5e-2 | 6.4x |
| top1 | 0.99556 (448/450) | 0.99 | pass |
| top1 mismatches outside flip-eligible | **0** | 0 | pass |
| `numerical_passed` / `state_passed` / `lifecycle_passed` | **true** | | |
| `scope_failures` | `[]` | | |

**Every number is identical to the recorded production@1024 gate**, which is what
bit-identical token ids predict. Token ids are identical across all four
configurations (`c18d529b...`): strict@1024 = strict@4096 = production@1024 =
production@4096, 6 samples per arm. `X-6` had already shown the same invariance
on a different route, so this is a second independent confirmation.

### End-to-end verification of the guard

Through `resolve_runtime_profile(...).construct_generator(...)` with the real
model: `admitted=4096`, `runner_chunk=4096`, `context=262144`,
`profile=production`. The guard selected the top rung and the binder bound it.

## Validation

- `uv run pytest` over the chunk, capacity, context, gate, canonical-bench,
  allocation-census and campaign-retention bundles -> **85 passed**.
- The layer2 numerical gate above (`hard_gates_passed: true`,
  `measurement_valid: true`).
- Bit-identical token ids, 6 samples per arm, both profiles, both chunk sizes.
- End-to-end guard verification through the real production binding path.
- The admission probe at all three chunk sizes with the GPU otherwise idle. The
  first attempt failed with `MemoryError: ... do not fit even minimum context`
  because a bench run was still holding device memory; it was re-run after that
  exited rather than read as a result.

## Next

- **The guard has no dedicated GPU test.** It is covered by unit tests and by the
  end-to-end binding probe above, but no automated test asserts the ladder on a
  memory-constrained device. A test that shrinks `available_device_bytes` and
  asserts the rung is the natural follow-up.
- **The 2051/2052 boundary and ragged final chunks remain unmeasured** (`RT-3`'s
  own stated gap), as does separate repair-queue / F16-workspace accounting.
- **The 8K-256K ladder should be measured with the guard active**, since the
  objective moves there next and the chunk only helps prompts longer than one
  chunk.
- Limits: one model, one quant, one case (`code-p4096`), one host (gfx1151, not
  the gfx1100 default hardware). The 256K-context preservation is an admission
  result on this host's 120 GiB free device memory, not a guarantee on a smaller
  device — which is exactly what the guard exists to handle.
