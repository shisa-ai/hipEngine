# Compact DMS verify-chain leaf over per-head variable spans

## Summary

Task 9, unit 1 continued: the compact layer now has its own verify-chain leaf, and
the store's multi-row extent planes are per layer.

``dms_compact_int8_verify_chain_gate_bf16_spans`` is registered under
``(dms_compact_attn_decode, int8_per_token_head, verify_chain_gate_bf16_spans)``.
It is a composition of two primitives that already existed and were already
tested: the DMS split-K INT8 attention producer, then
``qwen35_full_attn_gate_mul_bf16``. That second one is FP32-in and BF16-out, which
is why the leaf needs no cast step and why the earlier concern about an FP32
result plane was a wiring question rather than a missing primitive.

The leaf is a separate key from the paged verify-chain leaf rather than a second
reading of it, because the two disagree about what ``spans`` means. A paged span
set carries one page table and one live count per row; a DMS span set declares a
dense extent per ``(row, kv head)`` and indexes its int8 scale planes per slot.

Two corrections to the previous commit (``bf16ec05a``) came out of writing this
leaf, and the second one is the kind of thing that only shows up when the real
caller is built:

- ``KVLiveSpans`` declares ``per_head_variable`` extents as ``[rows, layers,
  heads]``, not ``[rows, heads]``, and requires scale metadata for INT8 storage.
  The first commit's gate had built a two-dimensional span set, which the
  constructor refuses. The leaf therefore takes the store's own per-layer
  ``[rows, kv_heads]`` planes as explicit arguments, exactly as the AR route
  passes that store's ``[kv_heads]`` planes, and uses ``spans`` as the layout
  guard.
- The store's multi-row extent planes are now per layer. A single shared pair was
  a footgun: binding layer 1 would silently redirect layer 0's attention, so a
  caller that bound every layer up front and attended later would read the wrong
  extents. Per-layer planes match the store's existing persistent metadata, and a
  caller may now bind every layer and attend them in any order.

## Changes

- ``hipengine/kernels/hip_gfx1100/attention/dms_compact_int8.py``: the leaf, its
  span-set guard, and its registration. The guard rejects a paged span set, a
  BF16 span set, a declared extent that does not cover every (row, kv head), a
  base/live pair that disagrees on layers, and any stride that is not contiguous,
  naming each condition.
- ``hipengine/kvcache/dms_device.py``: ``_rows_base``/``_rows_live`` become
  per-layer lists; ``_ensure_row_planes`` allocates them for every layer;
  ``bind_row_spans`` writes the bound layer's pair; ``attention_rows_device``
  defaults to that layer's pair.
- ``tests/test_unit_dms_int8_verify_chain_spans.py`` (new, unit tier): 23 cases.
- ``tests/test_gpu_dms_int8_device_payloads.py``: a GPU case for the leaf.

## Validation

- GPU, desktop gfx1151 lane: 22 passed across the two new cases, the kernel's own
  five-case gate, and the neighbouring device gates
  (``test_gpu_kvcache_dms_device_hip.py``, ``test_gpu_dms_int8_backend_integration.py``).
- Unit: 23 passed in the new file, plus 11 in ``test_unit_test_tier_names.py``,
  which enforces that a unit-tier test does not import an integration-tier one.
- The leaf's GPU oracle is the AR route itself: the same kernel called once per
  row through ``attention_layer``, each row finished by the same gate multiply,
  agreeing within 3e-5. Rows must also differ from one another, which a leaf that
  ignored the row axis would not.
- The gate law is pinned exactly rather than by a proxy. The first version of that
  check asserted a zero gate zeroes the output and failed, which is correct: the
  kernel computes ``attn * sigmoid(gate)``, so a zero gate is 0.5. The check now
  asserts half the FP32 result plane.
- The unit tier pins the wiring without a device: which pointers reach the
  split-K producer (the store's planes, not the span set's declared tensors), the
  row and geometry arguments, and that the gate multiply covers exactly
  ``rows * q_heads * head_dim`` elements of the result plane.

## Findings

- The ``[rows, layers, heads]`` span shape means the kernel's flat
  ``row * heads + head`` indexing only reads one layer at a time, which is why
  the per-layer planes matter and why the leaf cannot take the extents out of
  ``spans`` directly. A future leaf that wanted to read the span set's own
  tensors would need a strided base/live ABI and a kernel change; nothing needs
  that today.
- The pre-existing nondeterministic failure recorded in the previous entry
  (``test_int8_pack_append_attention_and_restore[8193-256-4-24]``) is unchanged
  and still unfiled as its own task.
