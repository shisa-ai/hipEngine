# Gemma 4 sliding-window prefill: a BF16 WMMA candidate at 13.7x the strict kernel

## Summary

A new BF16 F16-WMMA flash-attention prefill kernel for Gemma 4 26B-A4B's 25
sliding-window layers (head_dim 256, 16 query heads, 8 KV heads, GQA ratio 2,
window 1024, causal) measures **6344.7 GFLOP/s against the strict
`gemma4_attention_prefill_bf16` kernel's 462.0 GFLOP/s on the same row at 4096
tokens** -- 9.48 ms against 130.17 ms, **13.73x**. The 2x bar is cleared by
6.9x at the model's real geometry.

This is a **candidate, not a promotion**. The strict kernel is byte-for-byte
unchanged, still what `attention_symbol` selects, and nothing in the layer
wrapper, the runtime, or dispatch routes to the new kernel. Promotion needs the
`docs/EXECUTION-PROFILES.md` gate for a changed-arithmetic path, which has not
been run and is not claimed here.

The kernel is a **tensor-core rewrite and is a different thing from the refuted
`gemma4_attention_prefill_tiled_kernel`**. That variant kept the strict kernel's
execution unit -- one warp per key and a scalar cross-lane reduction -- and only
changed when logits were materialised, which is why its occupancy theory was
refuted and it measured 1.44x *slower* at 2048 tokens. This kernel changes the
execution unit: a 16x16x16 WMMA tile consumes sixteen keys at once, so the
per-key reduction the strict kernel's ceiling is made of does not exist to pay
for. Different schedule versus different unit; the refuted variant's
bit-identity is not a property this kernel has.

## Changes

- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention_prefill_wmma.hip` (new)
  -- the kernel. One block per (16-query-row tile, KV head, GQA tile), 64
  threads (2 waves), QUERY_ROWS 16 x GQA_HEADS 2 = 32 WMMA columns, K_BATCH 32
  keys, 33.8 KB of LDS (Q tile + a K/V tile reused between the two passes).
  Fragment conventions are the ones the two in-tree WMMA kernels already use:
  A holds `A[l & 15][k]`, B holds `B[k][l & 15]`, and the FP32 D element `e` is
  `D[2e + (l >> 4)][l & 15]`. Scores are `C[key][column]`, so the softmax
  reduction over keys is exactly the `l >> 4` split and costs one shuffle per
  tile instead of one per key. Both dots use the FP32-accumulate WMMA; the P
  operand is built in B layout by pairing a lane with its `xor 16` partner.
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention_prefill_wmma.py` (new)
  -- ctypes launcher with the strict kernel's ABI argument for argument, so the
  two can be driven on the same device buffers with no adapter. Registers a new
  four-axis variant `gemma4_wmma_flash`, which no existing resolution can reach.
  Raises `NotImplementedError` on a geometry it does not implement rather than
  running something else.
- `scripts/gemma4_attention_prefill_bench.py` (additive, `--compare-wmma`) -- an
  extra row per case, timed on the same device buffers, shapes, mask and
  arguments as the strict row above it. Without the flag the script's output and
  behaviour are unchanged (verified: identical rows and totals before and after
  the edit).
- `tests/test_gpu_gemma4_attention_prefill_wmma.py` (new) -- 20 cases, HIP-guarded.

### Geometry and the tiling choice

QUERY_ROWS 16 is forced: WMMA's M is 16, and the strict kernel has no query
tiling at all, which is the whole reason its cost is per-key loop machinery.
GQA_HEADS 2 is the model's own GQA ratio, so a tile covers both query heads that
share a KV head and each K/V row is staged once for both. COLUMNS 32 at 64
threads puts the accumulator at 256 x 32 / 64 = **128 FP32 registers per lane**,
which is the same operating point the in-tree INT8 WMMA prefill
(`paged_attn_decode.hip`, HEAD_DIM 256, COLUMNS 48) chose. Register pressure,
not shared memory, is the binding constraint at head_dim 256: the Q operand is
re-read from LDS per dimension tile rather than held in registers, because
holding it would cost another 128 registers per lane.

Compiler-reported resources for the shipped kernel:
`VGPRs: 256, TotalSGPRs: 40, ScratchSize: 16 bytes/lane (VGPRs Spill: 3)`.
256 is the ISA ceiling for wave32, so the kernel is register-saturated and the
compiler spills three registers. Occupancy is therefore capped at 2 waves per
SIMD32, and that is a real cost: the measured WMMA ceiling on this part is
**49-51 TFLOP/s** (see below), and the kernel's raw tensor-core work runs at
~7.1 TFLOP/s, about 14 percent of it. The ablation in "What did not work" below
locates the gap.

### Walk bounds

`window > 0` is the caller's promise that the mask is sliding-causal. It is
spent on two block-level bounds -- `first_kept` from the tile's first row and
`walk_end` from its last -- which is the same promise, applied to a block
instead of a row, that the strict kernel already spends on
`gemma4_attn_first_kept` and `row_offset + token + 1`. Every column the bounds
drop is masked, so dropping it changes no sum. `window == 0` promises nothing
and the walk covers every column, with only the mask deciding visibility. This
matters for correctness, not just speed: the production frame at 4096 tokens is
`keys = 4096` against `tokens = 512` and `row_offset` up to 3584.

### The WMMA ceiling this is measured against

`docs/ROOFLINE.md`'s 123 TFLOP/s figure is gfx1100 (96 CU). gfx1151 has 40 CUs,
so a probe was written rather than the figure being scaled. A standalone
throughput kernel (5120 blocks x 2 waves, 8 independent FP32-accumulate F16
WMMA accumulators, `wmma_f32_16x16x16_f16_w32`) measures:

```
8 chains (throughput)          261.60 ms      51.3 TFLOP/s
4 chains (throughput)          133.96 ms      50.1 TFLOP/s
2 chains (throughput)           67.25 ms      49.9 TFLOP/s
1 chain (throughput)            33.93 ms      49.4 TFLOP/s
1 dependent chain (latency)     33.32 ms      50.4 TFLOP/s  (20000-deep chain)
```

Two things follow. The part's practical WMMA rate is **~50 TFLOP/s**, and a
fully dependent accumulator chain runs at the same rate as independent ones --
the tensor unit is throughput-limited, not latency-limited, so accumulator
splitting is not the lever. The probe is a standalone artifact and is not
committed; the numbers are recorded here so the claim is not read against a
gfx1100 figure.

    tests/test_gpu_gemma4_attention_prefill_wmma.py

20 passed, 0 skipped, 0 failed (the repo's conftest suppresses the summary

with the same arguments, so the only difference between the outputs is the
arithmetic.

Cases covered:

- The model's real sliding geometry at 512 and 1024 tokens, window 1024, causal.
- The production mask frame `gemma4_layer` actually passes (`row_offset =
  window - 1`, `keys = tokens + window - 1`, column 0 at `key_begin`) at 512 and
  1024 tokens. A kernel that assumed `keys == tokens` passes the previous case
  and fails this one.
- Chunked prefill with `row_offset > 0` and `keys > tokens`: (512, 1024, 512)
  and (256, 4096, 3840).
- `window == 0` with an arbitrary mask: random 50 percent, blocky, and one row
  fully masked. The fully masked row is compared too -- both kernels produce
  0/0 there and neither may invent or drop a NaN.
- `tokens < QUERY_ROWS`: (1,1), (5,8), (15,16) and (17,32), the last being one
  row into a second tile.
- A narrow window (1, 2, 4, 17) where each row keeps few keys, so the walk trim
  is load-bearing rather than a 1-in-1024 perturbation.
- `scale=0.25`, since Gemma 4 only ever passes 1.0 and a candidate that folded
  the scale into the staged Q would be wrong only away from 1.0.
- The launcher refusing head_dim 512, and `attention_symbol` still selecting
  the strict kernel.

**Tolerance, and why it is not bit-exactness.** This is a changed-arithmetic
candidate. The two exactness properties it *does* have: every BF16 value in
FP16's normal range converts losslessly (FP16 carries three more mantissa bits
and the exponent rebias is exact), and a product of two FP16 values is exact in
FP32. What changes is summation order inside the matrix unit, and the rounding
of the softmax weights to FP16 for the P*V dot. The measured agreement is far
tighter than that description suggests -- **99.0-99.6 percent of output BF16 bit
patterns are identical** across every case, and the worst absolute difference is
**1.562e-2, which is exactly one BF16 ulp at the largest output magnitude** --
so the reassociation is mostly below the output representation's own
granularity. The test asserts a declared bound of `RTOL = 7.9e-3` relative to
each case's output peak (about four BF16 ulps, roughly 2x the worst measured
ratio of 3.7e-3), plus exact NaN-placement equality. It is **not** claimed to be
bit-exact and no reduction-order match was attempted.

The bound was checked for teeth rather than assumed. Injecting an off-by-one
into the leading walk trim (`tile_first_position - window + 2`) fails the
production-frame cases, the (256, 4096, 3840) chunked case, and all four
narrow-window cases; the real-geometry and `window == 0` cases still pass, which
is the expected shape of a trim bug and also the honest limit of the bound -- at
window 1024 a single wrongly dropped column moves the output by about one part
in 1024, which is inside a four-ulp tolerance because it genuinely is that
small. The narrow-window cases exist to make that class of error an assertion.

### What is NOT verified

- Not promoted, not selected, no execution-profile gate, no calibration run.
  Nothing outside the benchmark row and the test calls this kernel.
- End-to-end prefill or generation throughput is not measured. The claim is the
  kernel's rate at the model's geometry in isolation, which is what the
  census in `20260930T020000.000000Z-lhl-gemma4-prefill-gap-is-entirely-attention-7c1e5a.md`
  identifies as the unit; the whole-model gap closing is a separate measurement
  that has not been run.
- The head_dim-512 full layers (5 of 30) are not implemented. They are 512-wide
  with GQA ratio 8, which would need 256 accumulator registers per lane at this
  tiling and a different structure; a separate follow-up unit.
- No accuracy check against a float64 CPU reference, and no quality metric. The
  comparison is against the strict kernel only, as the unit specifies.
- No multi-run stability study. Each row is the median of 5 launches after 2
  warmups, and the two kernels' rates were reproduced across four separate runs
  (strict 462.6/459.0/462.0/465.3 GFLOP/s, candidate 6017/6345/6290 GFLOP/s) on
  one device in one clock state, but not across reboots, GPU clock states,
  thermal states, or a second device.

## What did not work, and what it showed

All of the following were measured with the same command as the final row.

1. **`#pragma unroll 2` on the score phase's dimension-tile loop** (to cut the
   20 bytes/lane spill): 216 VGPRs, no spill, and **slower** -- 11.07 ms against
   9.99 ms. The spill is cheaper than the lost instruction-level parallelism, so
   the shipped kernel keeps the full unroll and the spill.
2. **Two accumulators per key tile in the score phase** (four independent RAW
   chains instead of two, on the theory that a 16-deep dependent WMMA chain was
   the limit): 10.15 ms against 9.99 ms, and the register count stayed at 256.
   The ceiling probe above explains why: a 20000-deep dependent chain runs at
   50.4 TFLOP/s, so WMMA accumulator dependencies were never the constraint.
3. **`#pragma unroll 4` on the three staging loops**: 10.25 ms against 9.99 ms.
4. **Ablating the global loads from both staging passes** (keeping the
   conversion and the LDS stores, wrong results, timing only): 5.66 ms against
   9.99 ms. This is the one that located the problem -- **43 percent of the
   runtime is global-load cost in the K/V staging**, not the tensor cores and
   not the LDS fragment reads.
5. **Ablating the P*V value-fragment read** (512 scalar LDS reads per batch):
   9.13 ms against 9.99 ms, only 9 percent, which ruled out the LDS read pattern
   as the main cost.
6. **Hoisting the 64-bit address chain out of the staging loops** (the rewrite
   the strict kernel's pass 1 and pass 3 both needed): 9.99 -> 9.55 ms. Kept --
   it is in the shipped kernel -- but it recovers a tenth of what the ablation
   attributed to the loads, so the remaining cost is exposed memory latency
   rather than address arithmetic.

The open thread is therefore memory latency: the staging loop is a
load-convert-store chain whose loads are consumed immediately, with a barrier
right behind it, and only 2 resident waves per SIMD32 to hide it. The structural
fix is prefetching (issue the next batch's loads before the current batch's
barrier) and it is not done, because the register budget is already at the ISA
ceiling. `K_BATCH 16` with double-buffered K and V tiles would fit LDS (50.6 KB)
but would halve the keys per batch; that, or a tiling that gets the accumulator
below 168 VGPRs to reach 3 waves per SIMD32, is the next thing to try. It is
recorded here rather than attempted: the unit's bar was 2x and this is 13.73x.
