# gfx1151 capability ledger: a verdict for every gfx1100-only live-read name

## Summary

Closes section J's "Give all 18 gfx1100-only capability settings a gfx1151
verdict" and section K's carried-forward ledger item. Nineteen `GGUF_*`
capability names are defined on gfx1100, absent on gfx1151, and live-read
through `backend_package_capability`, so each absence resolves to a call-site
default. All 19 now carry a written gfx1151 verdict: **13 declined** (the
default disables a W7900-measured optimization and the retained owner runs) and
**6 N/A** (the name cannot select anything on gfx1151). No shipped value
changes.

| Group | Names | Verdict |
| --- | ---: | --- |
| Dense Q4 prefill geometry | 3 | 1 N/A, 2 declined |
| Dense prefill scratch liveness | 1 | declined (more scratch, no arithmetic change) |
| F16 rocBLAS prefill | 3 | N/A (build-bound indices, kernel unregistered here) |
| Raw-K prefill role variants | 1 | N/A (all entries are raw-Q6, declined upstream) |
| C8 Q5 MMQ SSM-out | 1 | declined |
| SPECDEC2 verifier / native target | 9 | 1 N/A, 8 declined |
| Server plain-AR admission | 1 | N/A (gfx1151 has its own flat number) |

Three properties make the declined rows safe rather than gaps: every call-site
default is conservative (`False` / `()` / `{}` / `0`), every gated route has a
registered gfx1151 owner, and the numeric rows are W7900 measurements that must
not be copied (the rocBLAS indices are bound to one library build hash; the
row48 crossover and the `{768: 13}` admission are W7900 results).

## Why the ledger is in the document, not inline in the gfx1151 package

The first attempt added the ledger as an inline comment in
`hipengine/kernels/hip_gfx1151/__init__.py`, which is where section I says the
names are invisible. Four tests pin that package's bytes —
`tests/test_unit_laguna_h8a_source_default.py`,
`tests/test_unit_laguna_h8b_source_default.py`,
`tests/test_gpu_laguna_h7u_parallel_moe_compaction.py`,
`tests/test_gpu_laguna_h7y_swa_lane_major_cache.py` — and two of them are
GPU-tier, so the re-pin could not be validated here. The comment was reverted
and the placement rationale recorded in the ledger itself.
