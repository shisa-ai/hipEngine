# DE-1 bandwidth-first gate: the routed-expert MoE block is not bandwidth-bound

## Summary

`DE-1` is the largest measured opportunity in the ledger: the routed-expert MoE block is
**24.5504 ms/step = 45.28% of decode kernel time**, more than every other family combined, spread
over 48 layer-roles with no dominant member - so only a whole-family lever can matter.

Its action is *"an exact-activation variant of the warp256 structure (the structure, not the dp4a
arithmetic), **measured for bandwidth first**"*. **This is that first measurement, and the answer is
a clear yes: the family has ~15.7 ms/step of headroom.**

## Changes

- **New script:** `scripts/qwen4exp_de1_moe_bandwidth_gate.py` - a reproducible derivation that
  pairs the exact GGUF weight bytes with the already-captured per-family kernel time.
- **New artifact:** `benchmarks/results/2026-09-29-qwen4exp-de1-moe-bandwidth-gate/` (`gate.json` +
  `README.md`).
- **Ledger `DE-1` advanced**; CHANGELOG entry added. No code, kernel, dispatch or default changed.
- **No GPU execution** - this is a derivation from the existing profiled capture.

## Method

**Traffic model.** For a decode GEMV every weight byte of every *selected* expert is read exactly
once, and the 1.5 GB working set far exceeds any cache on this host, so each read is a DRAM read.
Bytes are the **exact GGUF payload sizes** read from the model's own tensor table (1224 tensors
across 4 shards), not a bits-per-weight estimate.

| component | derivation | bytes/step |
|---|---|---:|
| routed experts | 48 layers x 10 of 512 x (gate+up+down) | **1,504.26 MB** |
| shared expert | 48 layers x (gate+up+down) | 250.68 MB |
| router | 48 layers x `ffn_gate_inp` (GEMV over all 512 experts) | 251.66 MB |
| **total** | | **2,006.59 MB** |

**Comparator.** `linear:root.lm_head` is a single dense GEMV in the **same profiled capture**,
streaming its own 675.43 MB weight in 2.9798 ms. It bounds what the MoE block could reach without
relying on a datasheet number.

## Result

| family | bytes/step | ms/step | kernels | achieved | vs 221 GB/s roof |
|---|---:|---:|---:|---:|---:|
| **`moe:expert_gate`** | **2,006.59 MB** | **24.5504** | **583** | **81.73 GB/s** | **37.0%** |
| `linear:root.lm_head` (comparator) | 675.43 MB | 2.9798 | 1 | **226.67 GB/s** | **102.6%** |

**The same host, in the same decode step, in the same capture, streams a dense GEMV at 226.67 GB/s
while the MoE block manages 81.73 GB/s - a 2.77x gap.**

| derived quantity | value |
|---|---:|
| MoE block floor at the comparator's rate | **8.85 ms** |
| headroom | **15.70 ms/step** |
| headroom as share of the 54.218 ms kernel sum | **29.0%** |
| per-kernel time (583 kernels) | 42.11 us |

**Verdict: not bandwidth-bound.** The proposed structural lever has a quantified target of roughly
**15.7 ms/step = ~29% of decode kernel time**, before any arithmetic is touched.

## Why the comparator is the right control

- **Same run, same host, same step** - no cross-session or cross-host inference.
- **It independently validates the roof and the traffic model.** 226.67 GB/s against the documented
  221 GB/s practical read roof is 102.6%; an unsound traffic model would not land on the roof.
- **Same shape of work** (a decode GEMV streaming a large weight matrix), so the comparison isolates
  the family's own inefficiency rather than contrasting workload classes.
- **It is one kernel vs 583**, so part of the gap may be launch/tail effects rather than pure
  streaming - a hypothesis for `DE-1` to test, which does not change the conclusion.

## One correction made along the way

**`moe:expert_gate` is a misnomer.** `scripts/qwen4exp_profile_gap.py:97` wraps the whole
`run_qwen4_exp_moe` call and merely *names* the role after the gate weight's slot:

```python
"run_qwen4_exp_moe": lambda a, _k: "moe:" + slot(a[1]["expert_gate"]),
```

So the family covers gate **and** up **and** down **and** the shared expert **and** the router. The
traffic model counts all of them. Without checking this, the family would have looked like gate-only
and the achieved rate would have been reported as 36.2 GB/s instead of 81.73 - an understated
traffic model, i.e. an overstated gap.

## What this does and does not establish

**Established:** the routed-expert MoE block runs at 37.0% of the documented roof while a dense GEMV
in the same capture reaches 102.6%; the gap is ~15.7 ms/step.

**Not established:** *which* structure is responsible. The measurement says the family is not at the
roof; it does not say the warp256 variant is the fix, nor that the gap is launch overhead rather
than address generation, gather efficiency, tail quantisation across 583 small kernels, or staging
traffic. **Nor any end-to-end speedup.**

## Limits

- **Derived from a PROFILED capture.** The source artifact's own `limits` state the wall and
  per-kernel times are *diagnostic, not a performance measurement*. Profiling inflates kernel times,
  so the true family time may be somewhat below 24.5504 ms - which would narrow the gap but cannot
  close a 2.77x ratio.
- **The model makes 81.73 GB/s a LOWER bound**: if the kernels stage or dequantize into wider
  buffers, actual DRAM traffic exceeds 2,006.59 MB.
- One case (`code-p4096`), one live count (4097), one model, one host, one execution profile.
