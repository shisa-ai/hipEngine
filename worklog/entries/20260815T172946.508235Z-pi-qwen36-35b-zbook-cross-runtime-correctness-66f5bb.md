# Validate ZBook Qwen3.6 BF16 and GGUF loads

## Summary

Admitted the completed official Qwen3.6-35B-A3B BF16 snapshot and ran one
matched, officially rendered correctness smoke through the BF16 CPU reference,
hipEngine Q4_K_M, llama.cpp HIP, and llama.cpp Vulkan. All routes load, consume
exactly the same 40 prompt IDs, and agree on first-token top-1. hipEngine is
deterministic across fresh processes and exactly matches llama.cpp HIP over the
eight-token Q4_K_M continuation. Vulkan diverges at one close argmax after a
six-token common prefix, so this is a preliminary pass with a numerical
follow-up, not the full multi-prompt quality gate or a speed claim.

A material product limitation is now explicit: hipEngine can parse the official
HF snapshot and resolve its Qwen plugin, but no BF16 Qwen generator is
registered. The only HF-safetensors route for this plugin is packed PARO W4.
The 71.9-GB BF16 payload also exceeds the current 62.5-GiB GPU/TTM mapping, so
BF16 remains a Transformers CPU quality oracle for this campaign.

## Validation

- BF16 snapshot `995ad96eacd98c81ed38be0c5b274b04031597b0`:
  - all 26 resolved shard SHA-256 values match their Hugging Face blob/LFS
    object names;
  - 71,903,776,776 shard file bytes and 71,903,645,408 indexed tensor bytes;
  - exact safetensors index/header map, 1,045 BF16 tensors: 1,026 AR plus 19
    MTP tensors;
  - official Transformers 5.15 / PyTorch 2.10 CPU load, finite 248,320-logit
    forward, and eight-token greedy generation pass.
- Prompt contract:
  - used official HF chat rendering for `general_en_explain`, generation prompt
    enabled and thinking disabled;
  - all four routes consumed the exact same 40 IDs, SHA-256
    `3e8bfe394535b68702963bdf6ba1e7b68cb786da0891a9f4f7b00f7f239e95ea`;
  - official and Unsloth GGUF native template hashes differ, so rendered bytes
    were fixed rather than selected per runtime.
- hipEngine GGUF `hip_gfx1151` public API:
  - load/generate PASS twice in fresh processes with identical IDs
    `[44812,42903,383,2136,68022,369,10813,2972]`;
  - finite full-vocabulary logits; first top-1 agrees with BF16; one-row
    `KL(BF16 || Q4_K_M)=0.0038508413`.
- llama.cpp HIP build 10423 / `a94d563ed` on `ROCm0`:
  - exact input IDs and full offload command accepted;
  - generated IDs exactly match hipEngine for all eight tokens;
  - first-row top-10 log-prob maximum absolute delta versus hipEngine is
    `0.16840`.
- llama.cpp Vulkan build 10415 / `1d2869c6e` on RADV `Vulkan0`:
  - exact input IDs and full offload command accepted;
  - IDs match hipEngine through six tokens, then choose `45239` instead of
    `10813`, followed by the same final `2972`;
  - first-row top-1 agrees, with top-10 maximum absolute log-prob delta
    `0.26393` versus hipEngine.
- Close-argmax attribution:
  - on the common context `Transformer inference on local GPUs is`, Vulkan
    prefers `45239` over `10813` by `0.17485` log-prob;
  - llama.cpp HIP server prefers `45239` by only `0.00378`, while HIP completion
    and hipEngine choose `10813`;
  - an earlier `is`/`on` choice is also close and changes between HIP server and
    completion execution shapes. This is not evidence of a gross state failure.
- Documentation link, JSON semantic, worklog, and whitespace checks pass. No
