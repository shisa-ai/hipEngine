# The 16-47 outlier is a rank-2 swap, and chunk 4096 adds no numerical cost

## Summary

Working the next-ranked §4 rows (`RT-1`, `DP-7`, `DP-8`), the load-bearing item was
`DP-7`'s claim that RT-1's chunk promotion is "blocked only on X-6". Reading the
artifacts rather than the summary found two things the ledger recorded
incompletely, and one it recorded not at all.

## 1. The outlier that revokes qualification is a near-tie, not a degraded row

`requires_outlier_review` is what flips `measurement_valid` to false, and it is
driven by **one row of 1548**. Characterized:

| field | value |
| --- | --- |
| location | `general_en-p512`, teacher step 82, scenario step 469 |
| `kl` | 0.02341195 (crosses 0.02 review; clears `max_kl_max` 5e-2 by 2.1x) |
| strict top-1 | `318` - which is the **candidate's rank 2** |
| `topk_overlap` | **1.0** - top-5 sets identical, only the top-two order moved |
| `strict_margin` | 0.109 |
| `max_abs_logit_delta` | 0.421 (against 2.338 across all rows) |
| top-1 mismatches | 9, **all** flip-eligible; `top1_mismatches_outside_flip_eligible: 0` |

So the review the gate is requesting is an ordering question on a near-tie, not a
demonstration that the route degrades a row. That distinction is what a reviewer
needs, and it was not recorded.

## 2. Chunk 4096 is screen-only for the same single reason, and adds no cost

`artifact-wmma16-47-chunk4096.json` runs the full canonical 12-case /
4-category protocol (1548 rows, 128 steps, 3 repeats, determinism passed) and is
**bit-identical to the chunk-1024 run** on both hashes (`294e6c08d5b2c315` /
`10fd0ae50b6eb9ce`), on every KL moment, on top-1 (0.994186) and on the
over-review row itself.

**RT-1's stated limit was "ONE case in ONE category - the 12-case 4-category
suite run is the evidence that would generalize." That evidence exists and is
stronger than requested**: 4096 is not merely admissible across all four
categories, it is indistinguishable from 1024.

The chunk-4096 promotion's remaining blockers are therefore the **pre-existing**
outlier review and the **+4.96 GB memory admission** - not numerics, and not X-6
coverage, which is `complete: True` with all six checks passing.

## What I did not do

I did not re-record the chunk-invariance result as new: X-6 already carries it as
a secondary result ("chunk 1024 and chunk 4096 at HEAD are bit-identical on both
hashes"), and the screen-only status and `measurement_valid: false` are already in
RT-1 and the changelog. Re-adding them would have inflated the diff without adding
a fact. I checked before writing.

I also did not call `DP-7`'s "blocked only on X-6" wrong in the row: X-6 is the
row that owns chunk re-gating, so the attribution is defensible. What was missing
is that X-6's coverage is complete and the actual blocker is the outlier review -
which the RT-1 addition now states.
