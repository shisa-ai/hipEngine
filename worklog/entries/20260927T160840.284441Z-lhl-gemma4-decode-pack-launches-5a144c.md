# The 202-per-step pack launches are the seven dense q8_0 projections

## Summary

Closed the open question the decode profile left: why the dense path issues about
seven pack launches per layer per token.

The kernel is `gguf_k_pack8_prefill_out_kernel`, but it lives in
`hipengine/kernels/hip_gfx1100/quant/gguf_q8_0_pack8_gemv.py` and that module's
docstring calls it "the decode-shaped" kernel. So it is the q8_0 dense decode
GEMV and the "prefill" in the name is historical, the same way it was for the
MoE kernels. 12915 calls over 64 decode steps and 29 layers is 7 per layer, which
is the seven dense projections: q, k, v, o, gate, up, down.

That matters for how the finding should be read. The launches are separate
because each projection has its own weight matrix, so this is not a batching
oversight that a fusion pass would fix. The lever is the per-launch cost and the
kernel's efficiency at the decode shape - 44.7 us per launch for a GEMV at this
size - rather than a reduction in launch count by combining unrelated
projections. The 26.0% share is therefore a per-kernel efficiency question, and
the honest next step is to profile that one kernel rather than to restructure the
dispatch.
