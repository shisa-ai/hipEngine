# the prefill attention kernel recomputed expf per element and now reuses pass 2's weight

## Summary

The prefill attention kernel was the second-largest route in gfx1151 prefill and
had no measured mechanism. It now does: **pass 3 recomputed `expf` for every
(element, key) pair** — 256 redundant evaluations per key at the artifact's
sliding-layer geometry, 512 at its full-layer geometry — and pass 2 had already
computed the identical expression for the denominator and thrown it away.

Pass 2 now stores each weight over its logit and pass 3 reads it. **Bit-exact,
1.48x on the kernel, +5.6% end-to-end prefill** (269.8 -> 284.8 tok/s).

The decode kernel in the same file has done exactly this since it was written,
and its comment already recorded the argument. The block kernel simply never got
the change. This unit makes it match its twin rather than introducing a pattern.

## Changes

- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention.hip`:
  `gemma4_attention_prefill_kernel` pass 2 becomes
  `const float weight = expf(logits_s[j] - row_max); local_sum += weight; logits_s[j] = weight;`
  and pass 3 reads `logits_s[j]`. Both loops are otherwise untouched.

  In-place is race-free because the pass 2 stride is `blockDim.x` and thread `t`
  only ever touches `j == t (mod blockDim.x)`, so no thread writes a key another
  thread reads and no key is visited twice. Coverage of `[first_kept, keys)` is
  complete either way: a thread with `t >= first_kept` starts at `t`, and one
  with `t < first_kept` starts at the first value congruent to `t` at or above
  `first_kept`. Pass 3 loops from `first_kept`, so every weight it reads was
  written.

- `tests/test_gpu_gemma4_attention_decode_parity.py`: **repair of a pre-existing
  break.** The file passed 12 arguments to a 14-argument symbol. The prefill
  symbol gained `window` and `row_offset` (see `_ARGTYPES_PREFILL`) and two of
  the file's three `_raw_launch` call sites were never updated, so **57 tests in
  that file raised `TypeError` before launching anything.** The shared helper now
  appends the prefill tail as `0/0` — which makes `first_kept` 0, so prefill
  visits every key exactly as decode's `keep_mask` does, which is the parity the
  file asserts — and the one direct call site in
  `test_public_wrapper_tokens_one_routes_to_decode_result` now passes `0/0`,
  matching the Python wrapper's defaults that it compares against.

  The file went from **57 failed / 94 passed to 95 passed**. The bit-exactness
  contract this unit depends on had no working coverage before it.

- `benchmarks/results/2026-09-28-gemma4-prefill-attention-weight-reuse-accepted.json`:
  the evidence row, including the measured launch geometry and one rejected
  hypothesis.

## What the measurement changed

The end-to-end saving is 399 ms while the isolated kernel is 1.48x faster,
because the real forward is chunked. Wrapping `gemma4_attention_prefill_bf16` and
timing each of its 120 launches with HIP events attributes **1959.71 ms** of the
7191 ms prefill to attention, corroborating the ablation's 1.923 s arm and
superseding an earlier inference from the single-launch bench.

That breakdown also **killed the largest remaining lead.** The sliding-window
layers pass `keys=1535` against a 1024-key window, which looked like 1.5x of
walked-and-masked work. A keys curve at fixed tokens=512 and window=1024 gave
6.43/14.31/17.43/18.82/18.41/18.39 ms for keys 512/1024/1280/1535/2048/3072:
**the cost saturates at about 18.4 ms and does not grow with `keys` out to 3072**,
so `first_kept` does bound the walk and there is no tail waste to reclaim. The
cost tracks visible pairs (8.4M vs 6.3M explains 18.4 vs 14.3 ms), which is the
kernel working as designed.

Attention is now **27.3% of prefill at a flat ~450 GFLOP/s with no reclaimable
work.** The remaining lever is the kernel's rate, not its work: pass 3 is a
rank-1 update with one thread per output element looping over every visible key,
one 2-byte V element and one broadcast LDS weight per iteration. Tiling it — one
block per (query tile, head) reading a K/V tile once for the whole tile — is the
flash-attention structure and is a kernel project, not an edit.

## Next

Two routes remain in gfx1151 prefill: the routed experts at 43.4% (3.087 s) with
no measured mechanism, and the dense Q8_0 share, which the ablation's
`no_dense_q8` and `no_all_gemv` arms report as about -1% and which therefore
remains **unmeasured, not zero** — skipping every GEMV cannot save less than
skipping the experts alone. The prefill attention kernel is at its structural
limit without a query tile.
