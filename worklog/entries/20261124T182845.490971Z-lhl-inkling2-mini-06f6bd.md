# Record the W7900 Inkling 2 Mini GGUF baseline with an in-tree decode bench

## Summary

The control for the Inkling 2 Mini GGUF optimization campaign (step 0 of
`docs/campaigns/INKLING2-MINI-GGUF-EXECUTION.md`), recorded before the decode-graph work.
Measured on `epyc` (Radeon Pro W7900, gfx1100, HIP 7.2.53211), mainline `UD-Q4_K_M`, FP32 KV,
one greedy stream, prefix cache off, drafting off, `fast` profile with no Inkling variable set,
at `7dceaa6b8` on a clean tree. Five repetitions after one warmup, 128 output tokens, 127 decode
steps per request, identical output across repetitions at every depth:

| Prompt tokens | First text | Decode | Per token |
| --- | ---: | ---: | ---: |
| 47 | 0.258 s (0.256 to 0.262) | 18.17 tok/s (17.99 to 18.23) | 55.05 ms |
| 575 | 2.978 s (2.966 to 2.984) | 18.01 tok/s (17.94 to 18.04) | 55.53 ms |
| 2,057 | 11.968 s (11.955 to 12.018) | 17.61 tok/s (17.51 to 17.64) | 56.78 ms |

The rate timed inside the engine loop agrees with the streamed rate within 0.2%.

- **Decode does not depend on depth on this host:** 55 to 57 ms per token from 47 to 2,057
  prompt tokens. The token is not waiting on K/V reads.
- **Each decode step makes 241 synchronizing host exchanges:** 241 async uploads (5.76 MB per
  step at 47 tokens, 10.18 MB at 2,057 as the relative-bias rows grow), 241 async downloads
  (5.13 MB) and 241 stream synchronizations, plus 48 event records and 48 event queries. The
  host blocks 15.9 ms per step inside those synchronizations at 47 tokens and 18.1 ms at 2,057.
  The remaining time is host work and launch submission.
- **The shipped default is slower than `fast`.** With no `--execution-profile`, a 47-token prompt
  takes 0.794 s to first text against 0.258 s and decodes at 14.72 tok/s (67.9 ms per token)
  against 18.17, with the same output IDs. Diagnostics differ only in `expert_activation`
  (`split_host` against `split_device`). This is the gap step 8 of the campaign closes.
- **Output sanity at the campaign's starting commit `748e15c97`:** the known-answer check, run
  with no Inkling variable set and `fast` before `strict`, gives 9 of 12 for both profiles with
  no regressed case, the same as the November 22 reference.

Artifact: `benchmarks/results/2026-11-25-w7900-inkling2-mini-gguf-baseline.json`. These are
development-lane numbers. They are not a Loom comparison and do not update the scoreboard, which
has no Inkling rows.

## What the harness had to get right

Three counting errors surfaced before the baseline was accepted. Each would have biased every
later comparison by the same harness, and the first two produced numbers that were quoted and
then withdrawn.

1. The stream emits a chunk only for non-empty text and carries token IDs only on its last
   chunk, so the first text delta reported no tokens and the window was one step long.
2. The public `LLM` stream runs through the engine loop. Hooks on the text generator never fire.
3. The engine loop calls `Inkling2GGUFText.decode_rows` once per tick. The first tick carries no
   rows and only samples the first token from the prompt logits, and a token's chunk reaches the
   caller just after the next step has started. The window is therefore defined from the tokens
   that decode to text and timed from step entry to step exit, with the streamed window kept as
   a cross-check.

A model path must keep the spelling the caller used: the local GGUF is a symlink to a file
without a `.gguf` suffix, and resolving it turned the model into an unreadable safetensors
directory.
