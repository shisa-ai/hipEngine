# IQ4_XS dense MMQ prefill is feasible with no repack, and worth 10.7x

## Summary

De-risking probe for item 3 of `docs/UD-OPTIMIZED-ROUTE-PLAN.md`, after a
census showed the IQ dense family is now **88.5% of UD prefill GPU time**. The
existing selected/MoE integer-MMQ kernel runs correctly on a **dense** tensor
as the degenerate single-expert case, straight from the raw GGUF bytes, and is
**10.7x faster** than the strict GEMV on the same tensor. No repack, no
sidecar, no new kernel.

## Changes

`scripts/gguf_iq_dense_mmq_probe.py` (new): the probe itself. No production
code changed.

## Why prefill is still slow, measured

rocprofv3 kernel census, UD-Q4_K_M, 512-token prefill, production config
(bulk + WMMA prefill), after the role-coverage work:

| family | calls | ms | share |
| --- | ---: | ---: | ---: |
| `gguf_iq_dense_strict_kernel` (all quants) | 135 | 11,038 | **88.5%** |
| T16 WMMA prefill (Q5/Q6/Q8) | 259 | 870 | 7.0% |
| Q4_K T16 WMMA prefill | 98 | 345 | 2.8% |
| everything else | 1,079 | 224 | 1.8% |

Total 12,477 ms, down from 37,299 ms before this campaign's routing work.

Cost per GB of resident weights tells the story:

| path | ms | GB | ms/GB |
| --- | ---: | ---: | ---: |
| IQ4_XS `gguf_iq_dense_strict` (GEMV, R=8) | 9,280 | 4.76 | **1,950** |
| Q5_K T16 dense WMMA prefill | 750 | 4.83 | 155 |
| Q4_K T16 dense WMMA prefill | 345 | 3.40 | 101 |

Q5_K carries **more** bytes than IQ4_XS and takes **12.4x less time**. The
remaining gap to the plain file is one kernel family.

## The probe

`gguf_iq_source_mmq_prefill.hip` addresses weights as

    qweight + expert*expert_bytes + out_row*weight_row_bytes + block*block_bytes

with `expert_bytes = out_features * weight_row_bytes`. At `expert = 0` that is
**exactly the dense raw GGUF layout**, so the dense case needs no repack and no
sidecar - only trivial single-expert metadata
(`build_iq_source_mmq128_metadata([rows])`, `expert_start_compact = [0, rows]`,
`num_experts = 1`).

Measured on `blk.0.ffn_down.weight` (IQ4_XS, N=5120, K=17408, 47.3 MB) at 512
rows, against the trusted strict dense GEMV:

- **finite, corr 0.999983, max relative error 0.0061** - the approximation is
  the Q8_1 activation quantization, as expected for an MMQ path.
- **strict GEMV 84.0 ms -> MMQ 7.9 ms = 10.7x** (10.77x and 10.67x on two runs).
- Traffic explains it: at R=8 the GEMV re-reads the weight column 64 times for
  512 rows (~36 GB/s effective of redundant traffic); the MMQ reads it once.

## Projected ceiling

If the IQ family reached the Q5_K T16 WMMA rate, prefill GPU time would go
12,477 -> ~2,316 ms (**5.4x**), i.e. roughly 41.5 -> ~224 tok/s and the gap to
the plain file 7.1x -> ~1.3x. The probe's 10.7x on the dominant tensor is
consistent with that.

## What integration still needs

The probe is a leaf call, not a route. Remaining:

1. A dense entry point beside the selected wrappers, building the single-expert
   metadata.
2. **gfx1151 registration.** The kernel is registered `moe_linear` on
   `hip_gfx1100` only - `tests/test_gguf_iq_source_mmq_prefill.py` explicitly
   asserts it is *not* registered on gfx1151.
3. Dispatch in `gguf_linear.py`: route raw IQ4_XS prefill above a row
   threshold, keeping the strict GEMV as the registered fallback and as the
   rows=1 decode owner.
4. Workspace ownership for the Q8_1 K-major activation records. One quantize
   per `(rows, K)` can be shared across every projection with the same K, which
   is an additional saving the probe does not capture.
5. Production-profile numerics gate: Q8_1 activations make this a T2
   arithmetic change, not an exact one.

IQ3_XXS gets the same treatment for free (the kernel supports it). IQ3_S,
IQ2_S, IQ2_XS, IQ4_NL and Q3_K have no MMQ kernel and would stay on the GEMV;
in K_M those are 0.75 GB against IQ4_XS's 4.76 GB.

## Validation

Probe only; no production code changed, so no suite was rerun. The probe
compares against the in-tree strict dense GEMV and is reproducible via
`PYTHONPATH=. .venv/bin/python scripts/gguf_iq_dense_mmq_probe.py`.
