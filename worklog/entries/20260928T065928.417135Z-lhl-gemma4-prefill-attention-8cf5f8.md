# the LDS ceiling is enforced against capacity at construction so it caps the model not the prompt

## Summary

I checked the main route, which was the remaining unknown, and the limit is **more
severe and differently shaped** than the previous entry described.

`hipengine/runtime/gemma4.py` line 500, in the runner's construction path:

```python
for attention in config.attention:
    gemma4_attention_shared_bytes(head_dim=attention.head_dim, keys=self.capacity)
```

It validates against **`self.capacity`** -- the runner's full KV cache capacity, a
caller-supplied field declared at line 474 -- and not against the live context or the
prompt length.

So the ceiling is **not** "a long prompt fails". It is:

**A runner whose `capacity` exceeds 15,872 (head_dim 256) or 15,616 (head_dim 512)
cannot be constructed at all.**

That is a cap on the model's usable context, applied before any request arrives.

## Correction to the previous entry's framing

`20260928T065852` said the assistant route "reaches" the ceiling because it passes
`keys=int(view.live)` with no chunking. That is true of that call, but it is not
where the limit first bites: the construction-time check fires earlier and harder, on
`capacity`, and it fires for **every** route that builds this runner. The assistant
finding is a second, narrower instance of the same limit.

## What is correct here

The refusal is **loud**: a named `NotImplementedError` naming the geometry and the
byte count, raised during construction rather than at request time. Nothing is
silently truncated and no context is silently dropped, which is what this repository
requires of a capability miss. The bug is the limit's existence, not its manner.

## What I have not established

- Whether `capacity` is normally set from the model's declared context length or from
  a smaller runtime default. If callers pass a modest capacity, the ceiling is
  unreachable in practice; if it tracks the model card, it is hit immediately. I did
  not trace where `capacity` is supplied from.
- Whether `DEFAULT_PREFILL_BLOCK = 512` means prefill is already chunked into
  512-token blocks (`self.max_block = min(self.capacity, DEFAULT_PREFILL_BLOCK)`,
  line 492). If it is, the *attention call* during prefill never sees a large `keys`,
  and only the construction check is binding. That reading is consistent with the
  code but I did not confirm it by following a prefill request.

Both are one grep each and neither is done.

No code.

## Validation

The call site is quoted from `hipengine/runtime/gemma4.py` line 500 with its
surrounding validation block (lines 489-500) read in full. The ceiling values are
from `20260928T065832`, which bisected the real function and confirmed it accepts at
15,872 / 15,616 and raises at the next value.

This is a reading of the code, not a measurement. I have not constructed a runner
with a large capacity to watch it fail, and I am not claiming to have.
