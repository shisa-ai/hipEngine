# gemma4 gfx1151: the long-context full-layer walk's traffic is DRAM and is exactly the unique band, so there is nothing to reorder

## Summary

Task #29 asked for a `rocprofv3` trace of the split walk at 262,144 keys to decide
whether its traffic is DRAM or L2, because that decides whether the L2 reorder is
worth a prefill regression risk. The trace says **DRAM**, and it says something
stronger than that:

| | |
| --- | --- |
| unique-band model: `keys * 2 kv_heads * 512 dims * 2 B * 2 tensors` | **1073.7 MB** |
| `FETCH_SIZE`, measured | **1074.4 MB** |
| model / counter | **0.999x** |
| duration | 5.49 ms (best of two; 6.17 ms cold) |
| achieved | **195.8 GB/s = 82.1% of the 238.5 GB/s roofline** |
| grid | 2048 blocks x 128 threads |

The walk reads K and V exactly once each and nothing else. **The 4x GQA redundancy
the task was written around does not exist**, so the L2 reorder has no traffic to
remove and should not be attempted.

## Why the premise was wrong

The task records that "the split walk moves about 537 MB per layer at 262144 keys
where the unique band is 134 MB, and the 4x is the gqa_tiles each reading their own
copy". Two things are off:

- **The unique band is 1,074 MB, not 134 MB.** 134 MB is 512 bytes per key;
  head_dim 512 in BF16 is 1,024 bytes per tensor per key, and there are two KV
  heads and two tensors, so 4,096 bytes per key. The counter confirms 1,074 MB to
  0.07%, so the model in the task is the one that is wrong.
- **There is no per-GQA-tile copy.** The decode shape sets `kGqaHeads = 8`, which
  is *all sixteen* query heads in one block, so each KV head is read once and
  every query head that needs it is already in the block. The 4x was inferred from
  the prefill shape's `kGqaHeads = 2` without accounting for the decode shape's
  different geometry.

## What this closes

- **The L2 reorder is not worth a prefill regression risk.** Its whole
  justification was removing redundancy that is not there. `docs/REFACTOR.md` and
  task #27's follow-up should not carry it forward as a live experiment.
- **The walk is near its bound.** At 82.1% of the DRAM roofline with zero wasted
  traffic, the remaining 18% is latency hiding and tail effects, not a traffic
  problem. Combined with the split work (block count was the parallelism bound)
  and the thread-count work (`kDimGroups` was the issue bound), the walk is now
  bounded by DRAM and close to it.
- The decode path's byte model is confirmed by hardware for the third time
  (65536 keys: 0.06% apart; 262144 keys: 0.07% apart).

## Validation

- `env -u HIP_VISIBLE_DEVICES PYTHONPATH=. HIPENGINE_HIP_ARCH=gfx1151 rocprofv3
  --pmc FETCH_SIZE --kernel-include-regex gemma4_attention_decode_wmma_full -d
  <dir> -- .venv/bin/python scripts/gemma4_prefill_kernel_bw.py --reps 1 --keys
  262144 --tokens 1`
- Two dispatches, 1074.4 MB both, so the count is stable; the durations differ
  (6.17 ms cold against 5.49 ms warm), which is why the rate is quoted from the
  warm one and both are shown.
- The counter was calibrated before use against a case with a known answer
  (decode shape, `tokens=1, keys=65536`: 268,435,456 bytes modelled, 262,313.375 KB
  counted, 0.06% apart). See
  `worklog/entries/20261002T214531.740943Z-lhl-gemma4-gfx1151-prefill-roofline-counters-ad03cb.md`.
