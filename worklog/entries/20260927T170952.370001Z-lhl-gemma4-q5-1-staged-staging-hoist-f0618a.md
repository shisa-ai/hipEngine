# The Q5_1 staged prefill kernel stages its weights once, not once per row batch

## Summary

**The largest prefill kernel now fetches its weights once per block instead of
once per row batch, for +3.5% on the whole prefill, bit-identical.**

The Q5_1 staged grouped-prefill kernel staged its expert weights inside the
k-chunk loop, which sits inside the row-batch loop. The staged bytes depend only
on the expert and the output column, never on the row, so a block re-fetched the
same 8448 bytes for each of its 8 row batches: 88 global round trips where 11
suffice, each one closed by two block-wide barriers. The staging now runs once
per block into dynamic shared memory. Barriers per block fall from 248 to 73 and
registers from 112 to 88.

Paired, back to back in one session at 512 prompt / 128 output, the per-chunk arm
measured 1.94, 1.95, 1.95 s (263.0 tok/s) and the staged-once arm 1.87, 1.88,
1.89 s (272.3 tok/s). Kernel-level, by `rocprofv3 --kernel-trace`, 714.91 ms to
670.5 ms per prefill, 1.066x. Decode is unchanged at 20.98 tok/s.

**The barrier hypothesis was only partly right, and that is the main finding.** I
went in expecting barriers to dominate, because the counter profile had just
measured 248 of them against about 5035 issue instructions per wave. Removing 176
of them bought 1.066x, not the multiple the count implies. Barriers that warps
reach together are nearly free, so a barrier count is not a cost model. The 82%
of cycles the kernel spends not issuing is not mostly barrier time.

**What the probe says instead.** I ran the scratch probe the acceptance artifact's
own method uses: replace the inner loop's two global packed-byte loads with a
constant and time the remainder. It comes out at 604.5 ms per prefill against
670.5 with the loads, so those loads are worth 66 ms, 9.9% of the kernel, and
they are re-read 8 times per block for the same 5632 bytes. Barriers (44 ms) and
byte loads (66 ms) together account for 110 ms of 715. The other 85% is latency:
the kernel issues on about a fifth of cycles and is not short of resident waves,
since 88 VGPRs holds 23 of 32.

## Changes

- `hipengine/kernels/hip_gfx1100/quant/qwen4_exp_q5_1.hip`: staging hoisted out
  of the row-batch loop into one pass over the whole row. The weight arrays moved
  from a static `[OUT_TILE][SUBS]` array to dynamic shared memory sized by the
  whole row, with slots laid out `[chunk][out][sub]`. The launcher sizes the
  dynamic shared memory and returns a named error above the budget.
- `hipengine/kernels/hip_gfx1100/quant/qwen4_exp_q5_1.py`: the host raises a
  named capability error above 38144 input features, naming the byte count, the
  budget and the bound, and pointing at the per-chunk routes.
- `benchmarks/results/2026-09-27-gemma4-q5-1-staged-staging-hoist-accepted.json`:
  the candidate artifact.

Two things the change got wrong first, both worth recording. The first version
indexed shared memory as `[out][global sub]`, which needs a runtime multiply per
access where the old `[out][sub]` had a compile-time stride the compiler hoisted
out of the chunk loop; it measured VALU 4521 per wave, +300 over the incumbent's
4221, and the `[chunk][out][sub]` layout brought it back to 4304. A change that
removes work can add instructions, and only the counter says which happened. The
first version was also wrong on rows whose width is not a multiple of K_TILE:
sizing the slot count as `in_features/32` lets `chunk*SUBS + sub + 4` read past the
array into the next output column's slot. The slot count is `chunks*SUBS` so a
tail chunk keeps its full SUBS width, exactly as the per-chunk staging did.

## Validation

Bit-identical, verified rather than argued. I A/B'd the same kernel on seeded
inputs: run the modified kernel, stash the change, run the original, compare bf16
output bits. The reference is the kernel's own prior behaviour, so no cross-kernel
equivalence is assumed.

- Artifact geometry (in 2816, out 1408, 128 experts, 4096 compact rows):
  5,767,168 bf16 outputs, 0 differ.
- Ragged geometry (in 320, not a multiple of K_TILE=256, out 40, 24 experts,
  occupancy 1/7/33/64/65/3): 27,680 outputs, 0 differ. This is the geometry that
  covers the partial final row batch, the `row < end` guard, and the tail chunk.
  The artifact geometry is a multiple of K_TILE and would never have shown the
  tail bug.
- `pytest tests/test_unit_gemma4_expert_route.py -q`: 48 passed.
- `audit.py check`: ok. Two rows from the earlier pack8 unit in this session were
  triaged in this pass: the ledger row as NOT-DEBT (the extractor's "states no
  removal condition" signal is wrong; the entry names its clearing measurement at
  `docs/REFACTOR.md:9226-9232`) and the flag row as LOST-OPT/keep.

Limits: one box, one artifact, one session. The ragged geometry is a correctness
check only and no timing was taken on it. The scratch probe removes work rather
than moving it, so 604.5 ms is an upper bound on what staging the byte loads
could recover, not a prediction. No 2048- or 4096-token prompt row, no llama.cpp
comparator on this host, no multi-request or served-path row. The 2.5 GHz nominal
clock behind the cycle arithmetic is not measured.

## Next

Stage the inner loop's packed bytes in shared memory. The probe prices that at
9.9% of the kernel and the bytes are already re-read 8 times per block, so it is
a real hypothesis with a measured upper bound rather than a guess.

Past that, the remaining 85% of the kernel is latency with adequate occupancy,
which means the next question is why the waves stall rather than which structural
change to make. A stall-reason counter would answer it; the barrier-cost figure in
the counter profile is inferred from cycle accounting, not measured directly.
