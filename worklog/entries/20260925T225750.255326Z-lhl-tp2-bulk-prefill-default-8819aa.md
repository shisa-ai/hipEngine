# Bulk prefill becomes the shipped TP2 schedule

## Summary

The rank-local bulk prefill is now the default TP2 prefill schedule
(`MlpTP2GenerationSession(bulk_prefill=None)` resolves to on for tp2, off for
tp1). `bulk_prefill=False` stays as the registered rollback and as the reference
arm for gate comparisons.

Two things had to be true first, and both were measured on the revision that
ships rather than cited from September.

**The production comparison passes with the default engaged.**
`scripts/tp2_teacher_coverage_broad.py --repeat-tp2 3` with **no bulk flag**
resolved the tp2 arm to `prefill_schedule: bulk-tp2`, `bulk_prefill_enabled:
true`, `attention_shard: true`, `reduce_mode: device`, `driver: compiled`,
`shard_widths {0: 8704, 1: 8704}`, both ranks
`dense_dual_local32_bf16_bf16_out`, and passed every gate
(`benchmarks/results/2026-09-25-w7900-tp2-bulk-default-gate.json`):

| metric | value | bound |
| --- | ---: | ---: |
| rows | 831 | - |
| mean KL | 2.107e-04 | 1e-03 |
| p95 KL | 7.948e-04 | 5e-03 |
| p99 KL | 4.589e-03 | 2e-02 |
| max KL | 1.157e-02 | 5e-02 |
| top-1 | 99.88% | 99% |
| category top-1 | code 99.63%, general_en / general_ja / mixed_ja_en 100% | 97% |

Three determinism sweeps matched per row, the reset/reuse, intervening-prompt
and reset-after-generation boundaries were bit-exact, no row was non-finite or
shape-mismatched, and the two TP1 controls were byte-identical to each other
(`b898c101...`). The same run with the flag passed with **identical** metrics
(`2026-09-25-w7900-tp2-bulk-current-gate.json`), so the flag and the default
select the same route and the numbers reproduce to the last digit.

Against the 2026-09-18 candidate this is a better pass on every tail metric:
mean 2.895e-04 -> 2.107e-04, max 4.2273e-02 -> 1.157e-02 (3.7x), top-1
99.64% -> 99.88%.

**The workspace contract was exercised, and the recorded blocker did not
reproduce.** `scripts/tp2_bulk_workspace_contract.py` (new) walks one session
through a length ladder and back, under three workspace policies.

- Every length tested (52, 128, 511, 512, 513, 600, 768, 1024) produced finite
  logits with the correct argmax, and every length also ran
  ``generate`` (prefill then decode) in the same call.
- The workspace grows on demand (52 -> 1024 rows recorded per step) and is
  reused afterwards: the closing 52-token prompt reuses the 1024-row workspace
  rather than rebuilding.
- A pinned workspace refuses an over-capacity prompt with the documented
  message ("prompt of 513 tokens exceeds the bulk prefill capacity 512; chunked
  bulk prefill is not implemented"), which satisfies "an explicit bulk request
  must run or report the actual capacity/resource limitation".
- **The deferred-allocation slowdown does not reproduce.** At the same size, a
  lazily built workspace measured 0.889 s for a 1024-token prefill against
  0.938 s for one allocated at construction (1027 rows pinned), i.e. deferred is
  5% *faster*, not the erratic 25-137 tok/s recorded on 2026-09-18. That claim is
  retired as a live blocker.

## Changes

- `hipengine/distributed/tp2_generate.py` - `bulk_prefill` is now a tri-state:
  `None` (default) resolves to on for tp2 and off for tp1, so a tp1 session is
  never asked to resolve a tp2-only flag, while an explicit `True` on tp1 still
  raises. Docstrings for the constructor, `generate`, `bulk_prefill` and
  `prefill_schedule` updated to describe the shipped schedule and the rollback.
- `scripts/tp2_teacher_coverage_broad.py` - `--tp2-bulk-prefill` is a tri-state
  `BooleanOptionalAction` (default `None` = the session default) so an unflagged
  run measures what ships; `_session_factory` passes `None` through.
- `scripts/tp2_resident_control.py` - `create_native_adapter` passes `None`
  through instead of coercing it to `False`, so a harness that does not name the
  schedule measures the schedule the engine ships.
- `scripts/tp2_bulk_workspace_contract.py` - new ladder harness (lengths,
  growth/reuse, allocation variants, refusal, prefill->decode) with a
  `logits` fact block per call (shape, dtype, non-finite count, last-row
  finiteness and argmax).
- `tests/test_unit_distributed_tp2_generate.py` - `test_bulk_prefill_is_on_by_default`
  replaces `test_bulk_prefill_is_off_by_default`; a new
  `test_bulk_prefill_can_be_rolled_back` pins the rollback's schedule and its
  "not enabled" refusal; the four token-serial loop tests and the graphed helper
  pin `bulk_prefill=False` because they assert the serial loop's launch pattern.

## Validation

- Production comparison on the shipped default: 831 rows, gates as tabled above,
  `all_gates_passed=true`, `gate_failures=[]`
  (`benchmarks/results/2026-09-25-w7900-tp2-bulk-default-gate.json`).
- Workspace ladder: `all_checks_passed=true` for the prompt-sized and pinned
  variants, refusals recorded in-band
  (`benchmarks/results/2026-09-25-w7900-tp2-bulk-workspace-contract.json`).
- Focused unit bundle: `tests/test_unit_distributed_tp2_generate.py`,
  `tests/test_unit_scripts_tp2_teacher_harness.py`,
  `tests/test_unit_tp2_resident_control.py`,
  `tests/test_unit_gguf_bulk_prefill_workspace_release.py` - all pass.
- Prefill rate on the shipping route at 512 tokens: 1057-1085 tok/s in the
  ladder and 1066 tok/s in the matched c=1 cell, against 43.99 tok/s for the
  token-serial rollback measured the same day, i.e. ~24x. At 52 tokens the
  ladder measures 0.170 s with a 52-row workspace against ~1.18 s inferred for
  token-serial at its measured 22.7 ms/token, so the bulk route is faster at
  short prompts too.

Two observations that are not blockers and are recorded as limitations:

- **The workspace never shrinks.** A 52-token prompt after a 1024-token one
  costs the 1024-row workspace's time (0.508 s against 0.170 s). It is still
  ~2.4x faster than the token-serial rollback at that length, so this is a
  latency detail rather than a reason to prefer serial, but a session that
  serves mixed lengths keeps the largest workspace it has seen.
- **No chunked prefill.** A prompt above the session capacity is refused, the
  same as the token-serial route; a pinned `bulk_prefill_rows` refuses earlier
  and says so.

One measurement in this unit did not reproduce and is recorded rather than
retained: the first ladder run measured 357 tok/s at 513 tokens against 990 at
512, and two later runs of the same configuration measured 930 and 972 tok/s at
513. The first reading is treated as an outlier; there is no established
prompt-length cliff.

## Next

With the default shipped, the prefill work continues against the head-sharded
profile rather than the older replicated one: rank 0 spends 89.1 ms in the
attention reduction and 88.1 ms in the MLP exchange of a 479.6 ms prefill, and
the three enqueue steps (staging `hipMemcpyAsync` D2H, `tp2_dev_publish_flag`,
`tp2_dev_spin_add_bf16`) are separable in `device_exchange_host.cpp`, so the
staging/wait/read-add split is measurable. The single-card bulk controls also
need re-measuring on this revision: the 1.08x scaling figure mixed a fresh
token-serial TP1 arm with a 2026-09-14 int8-KV bulk one.
