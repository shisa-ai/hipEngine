# Per-request KV overload is already capacity-class at 429; only the startup refusal was untyped

## Summary

The task's investigation recorded that the memory admission is "a startup check,
not a per-request admission" and that "the acceptance's 'push each consumer to its
budget edge' implies a per-request decision, which does not exist yet". Reading the
request-admission path shows that is wrong for the device KV pool: a per-request
refusal already exists, is already named by resource, and already answers with a
capacity-class status. That changes what the remaining work is, so it is recorded
before the wiring continues.

## Changes

- No code. This is a reading result recorded so the next unit does not build a
  second capacity path beside the existing one.

## Validation

- `hipengine/generation/qwen35_gguf.py:7214-7235`: `pool.allocate(row.request_id,
  pages, ...)` is wrapped in `except MemoryError as exc:` which raises
  `GenerationAdmissionRejected(str(exc), resource="device_kv_pool",
  request_id=..., requested_units=pages, current_units=..., capacity_units=...)`.
  So a per-request pool refusal is already typed, already carries the resource and
  the requested/current/capacity units, and is already retryable.
- `hipengine/server/api.py:643-666`: `_generation_admission_http_error` maps that
  type to **429** with `code="engine_busy"`, `error_type="rate_limit_error"`, a
  `Retry-After` header, `routing.reason="engine_busy"`,
  `routing.overload_source="kv_pool_capacity"`, and `routing.admission =
  exc.to_json_dict()`.
- `hipengine/kvcache/device_global.py:333-356`: the bare `MemoryError` raised when a
  request cannot fit its pages in one backing chunk within the pool budget
  ("cannot allocate {count} KV pages in one backing chunk within the pool budget")
  is raised *inside* `allocate`, so the caller above converts it too. It is named at
  the resource level, not per consumer.
- `hipengine/server/api.py:5347`: the startup `except MemoryError` handler logs and
  **re-raises**, so an admission refusal raised during resident-session preparation
  keeps its type and its message; nothing converts it to `internal_error`.

## Next

- Consequence for the acceptance: "a named refusal with a 503-class error" is only
  accurate for the *startup* path. The established convention for a per-request
  memory overload in this repository is 429 `engine_busy` with `Retry-After` and a
  named `overload_source`. The 503 mapping added for `MemoryAdmissionRefused` is
  therefore the answer for a refusal that nothing else converts -- which today means
  startup -- and it does not compete with the pool path, because that path converts
  first (`MemoryAdmissionRefused` subclasses `MemoryError`, so the existing
  `except MemoryError` catches it and answers 429 exactly as before).
- Remaining work for the task is unchanged in substance but narrower in shape: the
  consumers other than the device KV pool (draft/provider KV, INT8 MTP verifier
  scratch, captured graphs, retained prefix ownership) are not priced through the
  pool's own `budget_bytes` / `accounted_bytes` accounting, and the pool's growth
  clamp is the only place their bytes would be seen today. Pricing them means
  giving the pool accounting their byte counts, not adding a parallel budget.
