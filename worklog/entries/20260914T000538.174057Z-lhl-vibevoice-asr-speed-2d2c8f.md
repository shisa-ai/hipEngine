# VibeVoice ASR speed campaign: E2E at 1.03x torch

## Summary

Speed campaign for the torch-free VibeVoice-ASR path: 13.72 s -> 4.55 s
end to end on the 11 s JFK clip, now within 3% of the torch GPU lane
(4.43 s), with decode faster per token than torch. Follow-up to
`20260913T231428.406858Z-lhl-vibevoice-asr-e2e-7bec14.md`.

## Changes

- Batched prompt prefill: new `vv_rope_positions_f32` and
  `vv_prefill_attention_f32` kernels (causal, dense KV, shared-score
  window) + `prefill_rows` in the Qwen2 runtime; `greedy_generate`
  prefills the whole prompt in one pass (9.41 s -> ~0.7 s).
- Front-end: persistent scratch arena with ping-pong buffers (replaces
  ~300 malloc/free per forward; exact-capacity reset, no mid-pass
  growth), warp-per-row RMSNorm, Abramowitz-Stegun fast-erf GELU
  (1.5e-7 error, far below bf16), WMMA bulk GEMM for tile-aligned
  FFN/connector matmuls, im2col+WMMA for the five large strided convs
  (weights stream once instead of once per 4-row tile).
- Benchmark harness `scripts/vibevoice_asr_bench.py` (same-host lanes,
  identical preprocessing; torch lane must use eager attention).

## Validation

- gfx1151, 11 s real speech, best of 3: hipEngine 4.549 s
  (front-end 0.348, prompt+decode 4.200, 49 tokens) vs torch 4.425 s;
  decode 66.0 ms/token measured (forward_layers) vs torch ~81 ms/token.
  Front-end 0.92 -> 0.35 s over the campaign. GPU suites: 10/10 pass
  (front-end 7/7 incl. torch-GPU bf16 fixture parity; Qwen2 runner 3/3
  greedy chain equal to torch). Transcript content identical to torch
  (End timestamp 11.0 vs 11.07 - benign bf16 divergence).
- Negative result retained as knowledge: WMMA GEMV variants on the
  rows=1 decode path measured ~86% slower (bulk-tile kernels); the
  scalar dense GEMV family stays. Arena growth mid-pass was the root
  cause of two memory faults (dangling views) - fixed by exact-capacity
  resets (32 ping-pong/im2col units).
