# the lane mapping and the combine are both correct so the contamination is in the GEMV rows

## Summary

`20260928T055550` named the per-lane selected GEMV as the buggy route and
described the mechanism as rows contaminating each other. This unit reads the
three kernels that carry that mapping and clears two of them, narrowing the
defect to the projection's own per-row output.

## Cleared: the lane-to-row map

`gemma4_moe_lane_to_row_kernel` writes

```cpp
lane_to_row[sorted_lanes[row]] = static_cast<int32_t>(row);
```

so `lane_to_row[lane] = compact_row` -- lane-indexed, mapping to the compact
position. That is exactly the direction `gemma4_moe_weighted_accumulate_kernel`
consumes it in, `row = lane_to_row[lane]`.

## Cleared: the combine

The combine kernel reads `expert_out[row * hidden + col]` and
`sorted_weights[row]` with that same `row`. Both are correct:

- `expert_out` is written in compact order, so a compact row index is the right
  index for it.
- `sorted_weights` is written by the group-scatter as
  `sorted_weights[out_idx] = routing_weights[lane]` where `out_idx` is the
  compact position, so it is **compact-indexed**, not lane-indexed. Indexing it
  by `row` is therefore right, and the same `row` serving both reads is not a
  mismatch.

The kernel's own comment records that an earlier version gave each compact row
its own block and raced on the token row, and that owning a whole token per
block removed the race. The current form accumulates each column in a register
per token, so there is no read-modify-write on the output and no cross-lane
sharing there either.

## What this leaves

The routing, the lane map and the combine are all correct, and the divergence
still survives with a **single active expert** and identical inputs
(`20260928T055550`). With one active expert, one group, and a correct mapping,
the only thing that changes between `lanes=2` and `lanes=4` is **how many
compact rows the projection produces and in what order**. So the per-row output
of the projection depends on the number of compact rows -- the defect is in the
GEMV family's row handling, not in anything that consumes it.

That also fits the earlier observations better than a lane-mapping error would:
the difference is a *constant* for every row count at or above 2, and it appears
under two disjoint routings and a single-expert routing alike.

## Validation

- `gemma4_moe.hip` read at the lane-to-row kernel, the accumulate kernel, and
  the host wrapper's launch geometry (`dim3(tokens)` blocks, `top_k` slots per
  token).
- `group_scatter.hip` read at all four `sorted_weights[out_idx] =
  routing_weights[lane]` sites, which is what establishes the compact indexing.
- The conclusion is a narrowing by elimination over kernels that were read, not
  an inference from the observed magnitudes.
