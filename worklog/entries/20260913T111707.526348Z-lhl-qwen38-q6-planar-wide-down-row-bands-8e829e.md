# gfx1151 planar Q6 wide-down prefill row bands

## Summary

The gfx1151 planar-Q6 prefill policy sent the wide down shape
`(K, N) = (17408, 5120)` to the 32-row `shared4` owner (2 waves x 1 row tile,
64 threads) from row 256 upward. That band came from a rows 256/384/480/536
screen; the owner was never measured at prefill row counts. A rows 256-4096
screen of the whole registered shared-weight ladder now shows that owner is
1.4-1.7x off inside the band and 2.4x off above it, and every sibling is
BF16-bit exact to the plain parent, so the fix is a pure scheduling change.

Promoted on this host (same GGUF, production profile, one sequential session,
prompt lengths 512/1024/4096):

| prompt | prefill tok/s before | after | delta |
| ---: | ---: | ---: | ---: |
| 512 | 405.03 | **434.42** | +7.26% |
| 1024 | 395.98 | **414.63** | +4.71% |
| 4096 | 373.25 | **401.04** | +7.45% |

Decode is untouched by construction (the planar Q6 decode GEMV route is a
different selector) and measured flat: 12.226 -> 12.227 (512), 12.014 ->
12.009 (1024), 12.158 -> 12.117 (4096); the 4096 samples drift monotonically
down within the run (12.130/12.117/12.090), which is host drift, not the
selector.

## Changes

- `hipengine/kernels/hip_gfx1151/__init__.py`: for `(17_408, 5_120)` only,
  rows 288-1024 now select `shared4r4` (4 waves x 4 row tiles x 32 columns)
  and rows >= 1025 select `shared4_gfx1100` (4 waves x 4 row tiles x 48
  columns). The `shared4r6` band keeps its `(5_120, 1_024)` shape, and
  `shared4r9` at row 536, the `shared3r1`/`shared4r4`/`shared4r3` exact-row
  rules, the low-VGPR bands, and the shared4-from-256 rule for the other five
  shapes are unchanged.
- `scripts/qwen38_q6_planar_prefill_large_row_screen.py`: real-tensor screen
  of the nine registered owners at rows 256-4096 with bit-equality and
  max-absolute-deviation checks against the plain parent.
- `tests/test_unit_gfx1151_backend.py`: routing expectations updated, plus
  coverage for the new rows >= 1025 band.

## Validation

Screen (`scripts/qwen38_q6_planar_prefill_large_row_screen.py`, gfx1151,
`blk.0.ffn_down.weight` and `blk.3.attn_v.weight`, burst 8, median of 3
repetitions, every owner `bit_equal=True` with `max_abs = 0.0` at all 12
screened rows):

| rows | shared4 (previous) ms | selected now | ms | speedup |
| ---: | ---: | --- | ---: | ---: |
| 256 | 5.501 | shared4r4 | 1.927 | 2.85x |
| 512 | 10.983 | shared4r4 | 4.104 | 2.68x |
| 1024 | 21.925 | shared4r4 | 8.812 | 2.49x |
| 2048 | 43.498 | shared4_gfx1100 | 17.717 | 2.46x |
| 4096 | 86.898 | shared4_gfx1100 | 36.438 | 2.39x |

Both row counts that the prefill actually issues for this shape are covered:
1024 (the four GDN-layer prompt chunks) and 4096 (the single full-attention
layer pass). `rocprofv3 --kernel-trace` on the previous policy shows exactly
those two call sites: 96 calls at 12.09 ms (rows 1024) and 8 calls at 86.8 ms
(rows 4096), 16.7% of the 4K prefill's kernel time.

End-to-end A/B, identical command on this host, production profile
(`HIPENGINE_GGUF_FP16_RECURRENT_STATE=0`, `HIPENGINE_GGUF_VERIFY_CAPTURE_PREFILL_GDN=1`,
`HIPENGINE_GGUF_VERIFY_PRODUCTION_Q4_ROWTILE=1`, `GPU_MAX_HW_QUEUES=2`,
`HIPENGINE_HIP_ARCH=gfx1151`):

```
PYTHONPATH=. .venv/bin/python scripts/qwen38_gfx1151_readme_sweep.py \
  --prompt-lengths 512 1024 4096 --decode-tokens 16 --warmups 1 --repetitions 3 \
  --output <arm>.json
```

Before = commit `b98417620` clean tree; after = the same tree with this change
applied (provenance `dirty=true`, base commit `b98417620`). Prefill stdev is
0.05-0.15% of the median in both arms, so the deltas are far outside the run
noise. The harness graph/eager gate passed on all 18 checks with
`ids_exact=true`, `final_logits_exact=true`, and `state_exact=true`.
