# Task 42: a stripped environment export is now a loud failure, not a silent default

## Summary

A launcher can clear or filter the server environment and strip a tuning
variable without failing. The server keeps its default, and the run measures
the default while the report claims the raised value. The task-39 shape sweep
hit this exactly: its wrapper ran `exec env -i` and forwarded two hard-coded
variables, so `HIPENGINE_MTP2_MAX_CONTEXT_TOKENS=8192` never reached the
server. The "forced window" arm reproduced the default to the digit (11.40
tok/s both arms), one step from publishing "raising the window changes
nothing" as a finding about the model.

The server now reports what it resolved, and a preflight turns that report into
an assertion. A stripped or mistyped knob fails loudly instead of quietly
producing a number for the wrong configuration.

Note the repo was never the source of the hazard: no tracked script uses
`env -i`. The wrapper that stripped the export was a session artifact under
`/tmp`. The durable fix is therefore observability plus an assertion, not a
change to a launcher, so the next harness that builds a clean environment
cannot repeat it silently.

## Changes

- `hipengine/server/api.py`
  - `_mtp2_context_window_resolution()` reports `env`, `exported`, `resolved`,
    `qualified_default`, and `error` for the MTP context window. It returns an
    error string instead of raising, so a diagnostic payload cannot become a
    new crash path with a different failure order than the adapter's own call
    sites.
  - `_mtp2_context_window_log_fields()` renders the same resolution as the
    `env:`/`resolved:` pair already used for `candidate_budget`.
  - The startup `EFFECTIVE_MTP:` line gained
    `mtp2_context_window=env:... resolved:...` in both the pre-resolution
    (pending) and resolved branches, so the window is visible at launch even
    before the engine prepares its generator.
  - `_speculative_mtp_capability()` gained a `context_window` block, making the
    resolved value machine-readable.
  - `/v1/hipengine/capabilities` gained a top-level `effective_env` map holding
    every `HIPENGINE_*` variable the server resolved.
  - `_effective_hipengine_env()` redacts credentials by **exact name**
    (`HIPENGINE_API_KEY`, `HIPENGINE_KEY`) rather than by substring. A
    substring rule on `KEY`/`TOKEN` would hide the tuning knobs this report
    exists to expose: `HIPENGINE_MTP2_MAX_CONTEXT_TOKENS`,
    `HIPENGINE_MAX_CONTEXT_TOKENS`, `HIPENGINE_GGUF_INT8_KV_KEY_ONLY`,
    `HIPENGINE_FULL_QKV_SPLIT_KEY_FUSED`. A test pins that distinction.
- `scripts/bench_env_preflight.py` (new) - asserts that a running server
  resolved the requested knobs. Importable (`env_preflight_failures`,
  `assert_env_effective`) and usable as a CLI:

  ```bash
  python3 scripts/bench_env_preflight.py --url http://127.0.0.1:8097 \
      HIPENGINE_MTP2_MAX_CONTEXT_TOKENS=8192
  ```

  Deliberate choices, each one a silent-success path this closes:
  - A missing or unreadable `effective_env` block is a **failure**, not a pass,
    so a check that cannot see its evidence never reports success.
  - A redacted value is a failure to verify, never a pass.
  - `--unset NAME` catches a stale export from an earlier launch in the same
    shell.
  - `find_context_window()` searches the payload for the block instead of
    hard-coding its nesting, because a hard-coded path fails open the day the
    payload is reorganized.
  - When the window is requested, the resolved value is cross-checked against
    the export, not just the echo: an export can be present while the adapter
    still resolves the default.
- `benchmarks/HARNESSES.md` - new section documenting the failure mode, the
  forward-the-whole-namespace launcher pattern, and the preflight.
- `tests/test_unit_bench_env_preflight.py` (new, 30 tests) - covers the server
  report (prefix filter, ordering, exact-name redaction, default/exported/
  invalid resolution, log rendering) and the preflight (stripped export,
  mistyped name, mismatched value, missing report, redacted value, stale
  export, resolved-window divergence, path-agnostic discovery, CLI exit codes).
- `tests/test_integration_server_api.py` - the two capabilities tests assert
  exact dict equality on the MTP block, so both gained the `context_window`
  expectation. Both now pin the environment with
  `monkeypatch.delenv("HIPENGINE_MTP2_MAX_CONTEXT_TOKENS")`, because the window
  is an environment resolution and a value exported in a developer's shell
  would otherwise change the expectation.

## Validation

- `uv run pytest tests/test_unit_bench_env_preflight.py -q` - 30 passed.
- `uv run pytest tests/test_integration_server_api.py -k "capabilit or mtp" -q`
  - exit 0 after the two expectation updates. Before the update these were the
  only two failures in the selection, and both diffs were exactly the new
  `context_window` key.
- Manual check of the resolution against a real environment under `uv run`:
  `HIPENGINE_API_KEY` reports `<redacted>` while
  `HIPENGINE_GGUF_INT8_KV_KEY_ONLY` and `HIPENGINE_MTP2_MAX_CONTEXT_TOKENS`
  stay readable, and `exported: 8192` resolves to `resolved: 8192`.
- Manual check of the preflight against the recorded footgun shape: with
  `effective_env` holding only `HIPENGINE_HIP_ARCH` and `context_window`
  resolving 1023, requesting 8192 fails with both "not present in the server
  environment" and "resolved to 1023, not 8192".
- `uv run pytest -q` (reviewed unit tier) - exit 0, no failures. This run
  collected before a pure reordering of the two new helper definitions inside
  `hipengine/server/api.py`. The reordering is not observable to tests (no test
  asserts module source order or line numbers), and the post-move state was
  re-validated by the focused server-API selection (exit 0) plus a direct smoke
  check of all three helpers: `unset -> ('unset', '1023')`,
  `8192 -> ('8192', '8192')`, and an invalid export rendering
  `invalid(HIPENGINE_MTP2_MAX_CONTEXT_TOKENS must be an integer number of
  tokens)` rather than raising.
- `uv run --with ruff ruff check --select E4,E7,E9,F` on the new script, the new
  test file, and `hipengine/server/api.py` - clean. The one `F841` in `api.py`
  (`yellow` unused) is present in the committed baseline as well, so it is not
  from this change.

## Next

- The task-39 sweep wrapper under `/tmp` was not touched while `bg-238` was
  running, because bash reads a running script incrementally and an edit could
  corrupt that run. That run's forced-window server did report
  `window=8192`, so the earlier wrapper correction holds. The wrapper still
  forwards a hard-coded variable list, so the next knob added to it can be
  stripped the same way. Replace it with the forward-the-whole-namespace
  pattern from `benchmarks/HARNESSES.md`, or run
  `scripts/bench_env_preflight.py` before each arm.
- Wire the preflight into the shape-sweep launcher so every arm asserts its
  window before measuring, rather than relying on a human to notice identical
  numbers. A no-op arm reproduced the default to the digit (11.40 vs 11.40);
  an assertion is what turns that into a failure.
