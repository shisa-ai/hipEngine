# Flash-Next shared decode batch by default with automatic MTP

## Summary

`hipengine serve --model <Flash-Next shards>` served concurrent requests one
c1 runner per request, two at a time, each stepping on its own. The shared AR
batch existed but was opt-in, capped at four slots and 2,048 positions, and
reserved a full-context K/V window per slot on top of a full-context c1 runner
per request. MTP was opt-in only. This unit makes the batch the serving
default, sizes it from memory, and selects MTP automatically where it is the
faster route.

## Changes

- Batch runner pool (`hipengine/runtime/qwen4_exp_batch_runner.py`,
  `qwen4_exp_batch_state.py`, `qwen4_exp_batch_qsa_index.py`): the K/V and
  raw index-key slabs can be one block pool shared by every slot
  (`pool_blocks=N` or `"auto"`, sized from free memory after every other
  allocation, keeping 3 GiB in reserve). `admit(slot, positions=...)` takes
  that extent's blocks, publishes them to every QSA layer's page table and
  index member map, and holds them until release. Slot zeroing coalesces
  contiguous blocks (the static layout's ~24K memsets per admit at 262K become
  a few dozen). Step and import bounds follow the slot's own blocks.
- Serving (`hipengine/generation/qwen4_exp_gguf.py`,
  `qwen4_exp_ar_batch.py`): request capacity (default 8, at most 64, the
  indexed decode kernels' row bound) is separate from two c1 staging runners.
  A plain AR row prefills on a staging runner, imports into its batch slot, and
  returns the runner. `plan_admission` admits in arrival order while a staging
  runner, a slot, and the extent's blocks are free. A request longer than a
  batch slot (65,536 positions) or the whole pool, and every MTP row, decodes
  on its staging runner. Memory admission plans the staging runners only.
  `HIPENGINE_QWEN4_EXP_AR_BATCH=0` is now the rollback; the width/context
  ceiling and `HIPENGINE_QWEN4_EXP_AR_BATCH_SLOTS` are gone.
- Automatic MTP (`hipengine/models/qwen4_exp.py`,
  `Qwen4ExpGGUFTextGenerator.resolve_speculative_mtp_serving_plan`): the plugin
  declares single-row BF16 MTP, automatic-eligible for greedy and
  processed-argmax requests and explicit-only for sampled ones. The request's
  intent travels as `speculative_mtp_automatic` (`SamplingParams`,
  `GenerationRequest`, set from the server's route decision). An automatic
  request registered while others are registered decodes plainly; an
  automatic MTP row is demoted to the batch when another request registers
  (one c1 step feeds its already-published root token, then its state is
  imported); a request the MTP route refuses (a resident session) decodes
  plainly. Explicit requests keep MTP and its errors.
- Engine (`hipengine/generation/engine_loop.py`): optional runner hook
  `speculative_live_candidate_count`. Without it, rows that stopped
  speculating were partitioned one per work item and the batch stepped at
  width 1 under load.
- Server capabilities report the new envelope (`rollback_env`, `max_rows`,
  `request_capacity`, `staging_runners`, pool blocks); `docs/API.md` and
  `docs/REFACTOR.md` describe the path and its remaining gaps.

## Validation

Host zbook (gfx1151), unsloth `UD-Q4_K_XL`, production profile, MTP head
discovered (`Qwen3.8-Flash-Next-MTP-Q8_0`).

- Default `hipengine serve --model .../UD-Q4_K_XL` (no other flags): ready in
  26 s at 262,144 context; 8 batch slots of 65,536 positions, pool of 713
  blocks (182,528 positions), 2 staging runners, 2.25 GiB free after every
  startup stage.
- Chat, 128 tokens each, `ignore_eos`, wall time including prefill:
  1 request 30.55 tok/s (automatic MTP); 2 concurrent 27.83 aggregate; 4
  concurrent 40.13; 8 concurrent 48.06 (steps at width 8 for 120 of 127
  ticks). Before this unit the default server measured about 19 tok/s
  aggregate at every width.
- `scripts/qwen4exp_http_grid.py`: 50 of 50 probes 200; all 24 MTP probes
  executed MTP, the probe without an MTP field took automatic MTP, the
  four-request AR group finished in 7.30 s.
- `scripts/qwen4exp_http_soak.py --rounds 3`: 35 checks, 0 failures (after
  fixing the resident-session refusal found by the first run, 32/35).
- `scripts/qwen4exp_ar_batch_http_check.py --with-mtp`: 71 of 71 (the C1 phase
  now opts out of MTP and the C4 phase follows the server's capacity).
- Pooled vs static batch runner: logits bit-identical on the synthetic GPU
  fixture; pool exhaustion refuses admission by name without mutation.
- Unit tier: 15,391 passed and the 139 failures/errors were fakes building a
  real batch over a stand-in resident; those c1-path files now pin the
  rollback lever (303 passed). Batch/serving unit and GPU files pass.
