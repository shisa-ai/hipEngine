# Pin the n>1 live-many gate that decides multi-choice speculation

## Summary

Readiness-checklist item: multiple choices, tool/structured responses, and
unsupported sampling either work through existing contracts or select a named
supported fallback.

`_chat_live_many_streaming_allowed` (`hipengine/server/api.py:12563`) is the
gate that decides whether an `n>1` chat request is expanded onto the live-many
path -- the path that can run the speculative route -- or resolved through a
single-choice route. It had **no direct coverage**; the only tests touching
`live_many`/`stream_many` are integration and live files.

The gate is a pure predicate over the request, so its whole contract is
CPU-testable, which matters while the live-server half of the checklist is
blocked on GTT pressure.

### What a `False` means, and why it is not a silent downgrade

Every branch is a **route decision, not a refusal**. `False` sends the request
down a route the server supports and reports in the response's route decision,
so it is the "named supported fallback" arm of the acceptance. The
explicit-refusal arm -- a named capability error -- lives in
`_speculative_mtp_route_for_request` (`:14290`), which raises
`OpenAIHTTPError(400, code="unsupported_parameter")` when `speculative_mtp` is
disabled for the server and `OpenAIHTTPError(501,
error_type="unsupported_feature")` when the engine does not support it and the
client asked explicitly. An automatic request in the same condition returns
`_SPECULATIVE_MTP_DEFAULT_ROUTE` instead. That is the required split, and it is
implemented.

## Changes

- `tests/test_unit_server_live_many_gate.py` (new), 22 cases:
  - both sides of the width threshold (`n=1` excluded, `n=2` admitted) plus
    `n=7`, an unrelated width, so the gate is shown to test the constraint
    rather than a particular value;
  - each exclusion axis: `tools`, tools with `tool_choice`, `logprobs`,
    `top_logprobs`, `response_format` `json_object` and `json_schema`,
    `guided_json`, `guided_regex`, `guided_choice`, a stop string, a stop
    list, and a continuation;
  - falsy-but-present optional fields must **not** exclude (`tools: []`,
    `tools: None`, `logprobs: False`, `stop: []`, `stop: None`,
    `continuation_id: None`), because treating a client's explicitly-defaulted
    field as a constraint would drop multi-choice speculative serving for
    requests that carry no constraint at all;
  - exclusions apply at the unrelated width too, guarding against an
    implementation that special-cases one width.

### One case was wrong on first write, and the correction is a finding

The first version asserted that `tool_choice` alone excludes the request. It
does not: the gate tests `not request.tools`, and `tool_choice` only constrains
which of `tools` may be called, so on its own it carries no constraint. The
case moved to the falsy group with that rationale, and a `tools` +
`tool_choice` case was added to the exclusion group. Worth keeping because it
is the kind of asymmetry a later reader would otherwise "fix" in the wrong
direction.
