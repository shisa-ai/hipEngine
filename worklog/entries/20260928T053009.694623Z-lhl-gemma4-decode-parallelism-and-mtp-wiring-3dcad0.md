# decode is parallelism-starved at one row and the mtp that fixes it is unreachable

## Summary

Decode is 24.85 tok/s. The recorded baseline is 16.09 and the campaign target is
80.20, so 3.23x remains -- and the loop's metric is a prefill ratio, so none of
the 95 iterations so far have covered it. A census of a one-token step says the
problem is not what it looked like:

| bucket | ms | share |
| --- | --- | --- |
| `gemma4_project_experts_selected` | 16.70 | 36.8% |
| `launch_gguf_linear` (206 calls) | 14.12 | 31.6% |
| rmsnorm (150 calls) | 2.09 | 4.6% |
| router_topk | 1.17 | 2.6% |
| `gemma4_attention_prefill_bf16` | 0.35 | **0.8%** |
| kernels measured | 40.6 | **90.7%** |
| host and unmeasured | 4.2 | **9.3%** |

Dispatch overhead is 9.3 percent, not the dominant cost, so the
`ROOFLINE.md` §5.3 framing does not apply here. Attention is 0.8 percent and
irrelevant at one token. Decode is the same two buckets as prefill -- experts and
dense linears -- which is why the prefill work has been moving decode too.

## The real limit: one row is not enough parallelism

Per-token cost collapses as rows are added:

| rows | wall | ms/token | `launch_gguf_linear` | ms/call |
| --- | --- | --- | --- | --- |
| 1 | 45 ms | **45.0** | 14.12 ms | 0.069 |
| 4 | 98 ms | **24.5** | 24.45 ms | 0.119 |
| 16 | 95 ms | **5.9** | 32.28 ms | 0.157 |

`launch_gguf_linear` goes from 14.12 ms at one row to 32.28 ms at sixteen -- 7x
better per row. The experts behave the same way. These are GEMVs that read each
weight exactly once, so they should stream at this part's bandwidth, and instead
they achieve 42 GB/s (dense) and 80 GB/s (experts) against a ~256 GB/s ceiling.

It is not dequant-ALU-bound: 42 GB/s over Q4_K's 0.5625 bytes per parameter is
75 G parameters/s, and even at four ALU ops per weight that is 300 Gops against a
~30 Tops peak. The kernels are waiting on memory they never issue enough
requests to fill. The decision tree's branch for this is "undersubscribed:
split-K / change grid shape", and the cheapest source of extra rows is not a
kernel change at all.

## MTP is implemented and unreachable

`hipengine/runtime/gemma4_assistant.py` has `Gemma4MtpDrafter` with
`draft(token, *, hidden_row)` returning the draft token list, the assistant's
`forward`, and the `prime(backbone_hidden)` handoff. `scripts/gemma4_mtp_acceptance.py`
measures 0.78 accepted drafts per slot. It works.

Its only callers are that script and `tests/test_gpu_gemma4_assistant_forward.py`.
Nothing in `hipengine/generation/gemma4_gguf.py` calls it, and that module
declares:

```python
supports_speculative_mtp = False
```

`docs/reference/GEMMA4-ASSISTANT-MTP.md` already names this as the work item:
*"`hipengine/generation/gemma4_gguf.py` declares `supports_speculative_mtp =
False`, and that declaration is what the work has to make true, not a gate that
blocks the work."*

This is the "works in the harness is not works" defect exactly, and it is two
objective items at once: "make sure our MTP is working as well" is not satisfied
by a route reachable only from a benchmark script, and the draft/verify loop is
also the fix for the parallelism starvation above, because verifying k drafts is
a k+1-row forward.

## Plan

In `gemma4_gguf.py`'s decode loop:

1. After each accepted step, read the backbone hidden state via
   `runner.hidden_state(row)` and call `drafter.draft(token, hidden_row=...)`.
2. Forward `[token] + drafts` as one call. This is the multi-row forward the
   runner already supports; it is where the 7x per-row gain comes from.
3. Greedy acceptance: accept the longest matching prefix, plus the one bonus
   token the target's own logits give.
4. Rewind the KV position to the accepted length.
5. Flip `supports_speculative_mtp = True`.

The decode loop must stay correct when the drafter is absent or the artifact has
no MTP head, so the declaration is a capability, not a precondition: an artifact
without an assistant head decodes exactly as it does now.

## Expected win

0.78 accepted drafts per slot with a 4-token draft is about 1.78 tokens per
target step. The verify forward costs the same as a 2-to-4-row step rather than
four one-row steps, which the table above prices at roughly a quarter of the
per-token cost. A 1.5 to 1.8x decode improvement is the conservative read, which
is most of the objective's "2X on decode".

## Validation

- Census with `scripts/gemma4_prefill_kernel_census.py --prompt 1 --repeats 3
  --warmup 2`, and at `--prompt 4` and `--prompt 16` for the row scaling, on the
  8060S (gfx1151). The script event-times every launch, so the measured/unmeasured
  split is its own accounting, not an estimate.
- The 4-row and 16-row walls are noisy (98 ms against 95 ms); the ms/token column
  and the per-call column are the load-bearing numbers, and both are monotone.
- The MTP acceptance figure is the committed measurement from `9931a77a`, not
  re-measured here.
- The claim that the drafter is unreachable is a repository-wide grep for
  `Gemma4MtpDrafter` and `gemma4_mtp`, not an inference.

## Next

Implement the five steps above, then re-run the decode bench and the acceptance
script. This is the first unit in the campaign that targets decode rather than
prefill, and it should move `decode_tps_512p128o` from 24.85 rather than the
prefill ratio the loop has been tracking.
