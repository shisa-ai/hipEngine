# The q5_k iu8 route is a capability miss: 704 is not a multiple of 128

## Summary

Found the cause of the launch failure from the previous entry, and it is a
capability miss in the kernel rather than a wiring bug. The flag is gone and the
route now declines on its own precondition.

**The cause.** `gguf_q5_k_selected_dual_wmma_iu8_risk_prefill_kernel` rejects
`out_features_a % 128 != 0` with `hipErrorInvalidValue` before any work runs, and
the iu8-WMMA kernel tiles `out_features` in 128-column units. Gemma 4 26B-A4B's
fused `ffn_gate_up_exps` is `(2816, 1408, 128)` in GGUF order, which reversed is
`[128 experts, 1408 out, 2816 in]`, so each half is **704** - and `704 % 128 = 64`.
The route cannot tile this geometry at all. Every other guard passes:
`in_features` 2816 is a multiple of 256, the grid is well inside limits, the
shared arrays total about 16 KiB, and the ctypes argument order is correct.

**The fix is a precondition, not a flag.** The previous entry gated the route off
because it failed at launch, which was right at the time - the cause was unknown
and a changed-arithmetic path must not run when it cannot be shown correct. Now
that the cause is a geometry the kernel does not support, a flag is the wrong
instrument: the dispatch should ask the kernel's own capability question and
decline. `_gemma4_project_experts_gate_up_wmma_iu8` returns `False` when
`intermediate % 128`, so the strict grouped owner runs, exactly as the Q4_K route
declines when its quant key does not match. The flag, its `docs/REFACTOR.md`
entry, and its `docs/ENVS.md` row are all removed.

**The route is not dead code.** It stays wired and enabled for any artifact whose
expert intermediate is a multiple of 128, which is a kernel capability rather
than an artifact identity. This model's 704 is what disqualifies it here.

That closes the line of investigation. Layer 29's 110.89 ms cannot be recovered
through this route at this geometry; it would need a kernel variant that tiles
`out_features` in 64-column units.

## Changes

- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_experts.py`: the `intermediate %
  128` precondition in the new route; the flag function and its dispatch check
  removed.
- `docs/REFACTOR.md` and `docs/ENVS.md`: the flag's entries removed, since the
  flag no longer exists.

## Validation

- Default path unchanged: `scripts/gemma4_campaign_bench.py --prompt 512
  --output 128 --samples 3` gives 264 tok/s prefill, decode 20.99,
  `path parity=True`, with no launch failure - the route declines and the strict
  owner runs.
- `tests/test_unit_gemma4_expert_route.py`: exit 0.
- All four documentation gates pass, including env-var coverage now that the
  undocumented flag is gone.
- **The route still does not run for this model**, and that is the finding rather
  than a defect to fix here.
