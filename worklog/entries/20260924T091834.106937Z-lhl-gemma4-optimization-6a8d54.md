# Gemma 4 G1 profiling attribution: prefill-family decode costs, attention dominance at long context

## Summary

- G1 profiling ran on two primary shapes with `rocprofv3 --kernel-trace`,
  A/B pairs diffed per kernel name (A = prompt+output 1 = load/prefill;
  B = prompt+output 17/16 = A + decode steps; attribution = (B-A)/steps).
  Short: 128p, traces 2641 vs 38641 dispatches. Long: 4096p, 18121 vs
  56521. Raw dumps stayed in `/tmp` (never committed per AGENTS).
- **Profile recipe fix (this is why earlier attempts hung):** the profiled
  first forward spawned `<compiler> --version` via
  `compiler_version_text` (`hipengine/core/build.py:417`) as a cache-key step,
  and that child inherits rocprofv3 instrumentation and never returns —
  py-spy showed the client idle in `subprocess.communicate` at 82% CPU.
  Fix, matching docs/OPTIMIZATION.md §7: precompute `hipcc --version` to a
  file outside the profiler and run with
  `HIPENGINE_COMPILER_VERSION_FILE=<file>` + `HIPENGINE_REQUIRE_CACHED_BUILD=1`.
  After that both shapes ran rc=0. Also learned: a hung profiled client
  ignores TERM and keeps its VRAM; kill -9 it before the next run or the
  next load OOMs (that happened once and is recorded here).
- **Decode attribution, short shape (128p/16o, wall 34.75 ms/step profiled;
  device diff 41.32 ms/step):** `gemma4_attention_prefill_kernel`
  9.97 ms/step (24%, 60 layers), `gguf_q4_k_selected_prefill_out_kernel`
  9.43 (23%, 58/step), `gguf_k_pack8_prefill_out_kernel` 6.12+1.91 (19%,
  410/step), `q5_1_selected_gemv` 5.15 (12%), rmsnorm family ~3.0,
  `copyBuffer` 1.37, MoE routing/grouping ~2.0. Zero negative-diff kernels.
- **Decode attribution, long shape (4096p/17o, wall 101.8 ms/step = 9.8
  tok/s):** `gemma4_attention_prefill_kernel` **150.86 ms/step = 79.2%**
  (60 x 2.51 ms) vs 9.97 at KV~129; q4_k 13.04, q5_1 gemv 8.87, pack8
  6.12 (identical to short shape — linear stays flat as predicted),
  rmsnorm ~1.8, copyBuffer 1.4.
- **Prefill attribution, long shape (wall 37.98 s = 108 tok/s profiled):**
  q4_k selected 31.12 s device (41.7%), q5_1 gemv 19.09 s (25.6%),
  attention 17.55 s (23.5%), q8_0 lm-head exact_prefill_tiled 4.69 s
  (6.3%). Linear projections dominate prefill; attention does not.
- **Audit conclusion (hypothesis partially refuted):** decode is NOT
  misrouted to multi-row prefill launches. Grid evidence: attention launches
  (4096,1,1) in decode vs (524288,1,1) in prefill; q4_k launches
  (180224,8,1) vs (180224,1024,1) — rows-aware grids, and
  `gemma4_attention.py`'s docstring says KV-cache mode is the decode step by
  design. What remains: (a) q4_k has **no registered
  `pack8_gemv_decode_*` family** (registrations exist only for gguf_q5_k,
  gguf_q8_0 and mixed), so `_gemv_decode_dispatch`'s q4_k branch fails
  `is_registered` and falls back silently as documented — registering a q4_k
  decode owner is the concrete G3 candidate; (b) attention at 2.51 ms/layer
  with KV 4096 is orders of magnitude above the ~GB-scale read at 960 GB/s —
  the single biggest win and an open mechanism question (capacity scan vs
  uncoalesced per-key access); (c) pack8's 410 launches/step is a
  launch-count target (grouped experts).
- **Measurement caveats (recorded, not hidden):** device sums exceed wall
  (41.32 vs 34.75; 190.4 vs 101.8) — per-dispatch trace inflation and/or
  stream overlap; profiled wall is only ~12% above unprofiled, so kernel
  *shares* are usable and absolute device milliseconds are not. Transfer
  attribution is still missing: kernel-trace reports `memory_copy=0` (needs
  a `--hip-api-trace` run) — open G1 sub-item.
- Milestone-1 completeness: added the missing **memory metric** to the
  harness (RED first): `memory_row()` emits `artifact.memory` with
  total/used-bytes at `before_load`, `after_load`, `after_runs` and a peak.
  Real check: 0.04 → 17.89 → 21.53 GiB used of 23.98 GiB.
- Campaign-target context unchanged: baseline 16.09 decode tok/s at 1024/128
  vs target 80.20 (0.70 x Qwen 114.57); llama.cpp same artifact 68.92.
