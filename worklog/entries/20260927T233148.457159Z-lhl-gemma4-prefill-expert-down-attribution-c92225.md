# the Q5_1 expert down projection is 43 percent of prefill with no MMQ route

## Summary

The routed experts are 43.4% of gfx1151 prefill and had no measured mechanism.
Timing each real expert launch with HIP events gives one, and it names a kernel
that already exists in this tree and already runs for another model.

**The expert down projection runs at 8.6 GB/s where the gate/up projection on the
same layer runs at 67 GB/s** — 11.8x per FLOP, 7.8x per byte. The difference is
the quantization route, not the shape:

| route | quant | n | per launch | rate |
| --- | --- | ---: | ---: | ---: |
| gate_up MMQ | Q4_K | 120 | 4.240 ms | 7.66 TFLOP/s, 67 GB/s |
| down (`rows` ⊇ grouped) | Q5_1 | 124 | 24.935 ms | 0.65 TFLOP/s, 8.6 GB/s |

`gemma4_project_experts_gate_up_mmq` returns `False` for any `quant_key` other
than `gguf_q4_k` and `gguf_q5_k`, so **Q5_1 has no MMQ route in gemma4's expert
dispatch** and the down projection falls to the fp32 grouped family.

**This is not an untuned kernel.** The winning variant is
`selected_grouped_prefill_staged_out4_bf16_bf16_out` and its own docstring
records it as the measured optimum of a small sweep, 1.91x over the incumbent at
the Gemma 4 down projection. The route lacks an MMQ path; the kernel is already
the best of its family.

**It is also not bandwidth-bound.** The staged kernel reads each weight exactly
once — it stages `d`, `m` and `qh` per (output column, k-chunk) into shared
memory and the grid is `(out_features/4, num_experts)` = 90112 blocks. 174.4 MB
per launch at 20.97 ms is 8.6 GB/s, 3.4% of the 256 GB/s this host reaches on a
pack8 Q8_0 GEMV.

## The named path

`gguf_q5_1_mmq_ds4_selected_prefill_bf16_bf16_out` exists, is registered under
`KernelKey("hip_gfx1100", "moe_linear", "gguf_q5_1",
"q5_1_mmq_ds4_selected_prefill_bf16_bf16_out")`, and
`hipengine/runtime/qwen4_exp_runner.py` already runs it for Qwen4-Exp's
`expert_down`. The activation pack it needs is `gguf_q8_1_mmq_ds4_pack_bf16` —
**the same DS4 Q8_1 pack the gemma4 Q4_K gate_up route already calls.**

It is unreachable from gemma4 because `_GROUPED_PREFILL_VARIANTS` does not
contain it and the MMQ entry point takes `x_ds4` rather than raw bf16, so it
cannot be added to that tuple. Reaching it needs an explicit route in
`gemma4_experts.py`.

**The scratch is already big enough.** `Gemma4ExpertScratch` sizes `mmq_workspace`
at `lanes * (hidden_size // 128) * 144 * _MMQ_ACTIVATION_PASSES` = 12,976,128
bytes. The down projection needs `lanes * ceil(intermediate/128) * 144` =
3,538,944. No new buffer is required.

**The blocker, and why it is real.** The Q5_1 MMQ requires
`in_features % 128 == 0`. This artifact's down width is **704**, and
`704 % 128 = 64`. The kernel computes `ds4_blocks = in_features / 128` (integer,
so 5) and each `kb` consumes 4 Q5_1 blocks = 128 weight elements, so 5 x 128 =
640 and **it would silently drop the last 64 elements.** The guard prevents
exactly that.

The fix is bounded: loop `ds4_blocks` over `ceil(in_features/128)` and, when
`(kb+1)*128 > in_features`, read only the Q5_1 blocks that exist and zero the
rest instead of reading 48 bytes past the row end; the activation pack writes a
half-filled trailing DS4 block the same way. Materializing a 768-wide padded copy
of `ffn_down_exps` would also work with no kernel change, at about 174 MB of
extra device memory.

## Validation

Every number is from this session on this host:

```
env -u HIP_VISIBLE_DEVICES ROCR_VISIBLE_DEVICES=0 PYTHONPATH=. \
  python3 scripts/gemma4_prefill_route_ablation.py --prompt 2048 --repeats 2
# baseline prefill 7.191 s, 284.8 tok/s
# no_experts saves 3.087 s (43.4%)
```

The per-launch times are HIP events around each real
`gemma4_project_experts_*` call during a 2048-token `Gemma4Runner.forward`. The
weight shapes and quant keys were read from the loaded artifact's
`Gemma4GGUFWeightSpec`, not from documentation: `ffn_gate_up_exps` is
`(128, 1408, 2816)` Q4_K and `ffn_down_exps` is `(128, 2816, 704)` Q5_1.

**No correctness gate applies: no code changed.** The MMQ route the next unit
would wire changes arithmetic — it quantizes activations to DS4 Q8_1 — so that
unit needs the `docs/EXECUTION-PROFILES.md` gate and the
`docs/OPTIMIZATION.md` correctness gates. It cannot use the bit-exact argument
the attention change used.

## Expected effect, with its basis

If the down projection reaches the Q4_K MMQ's rate, 3.1 s becomes about 0.4 s:
**about 2.7 s of the 7.191 s prefill, roughly 284.8 -> 450 tok/s.** llama.cpp
pp512 on this host is 1012.98 tok/s, so that closes about 40% of the remaining
gap on its own.

**This is an estimate, not a measured claim.** The 7.66 TFLOP/s figure is the
Q4_K route at its own shape, and the Q5_1 route's wider weight rows give it a
different reuse pattern. The Q5_1 MMQ's rate at this shape has not been measured.

## Next

Extend the Q5_1 MMQ kernel and its DS4 activation pack to a partial trailing
group, then wire gemma4's down projection to it. That is the largest single lever
left in gfx1151 prefill.

The dense Q8_0 share of prefill remains **unmeasured, not zero**: the
`no_dense_q8` and `no_all_gemv` arms both report about -1%, which is impossible
because skipping every GEMV cannot save less than skipping the experts alone at
43.4%.
