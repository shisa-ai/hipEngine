# Evidence audit: the retained UD speed claims rest on speed_claim_eligible=false artifacts

## Summary

A publication-readiness review found that the retained UD decode/MTP parity
numbers are carried by artifacts whose own provenance says
`speed_claim_eligible: false`, while the docs describe the same rows as
retained evidence. This entry records the audit, the exact scope of the
problem, and the remedy.

The audit mapped every speed claim in `benchmarks/README.md` and the recent
`benchmarks/CHANGELOG.md` to its backing artifact and checked four fields:
`invalidation.invalid`, `timing_evidence_valid`, per-arm
`provenance.dirty`, and per-arm `provenance.speed_claim_eligible`.

### What the gates actually say

The two gates are independent, and the docs conflated them:

- `timing_evidence_valid` is the **control/timing** gate. It is true for the
  retained artifact.
- `speed_claim_eligible` is the **provenance** gate. It is false whenever the
  measuring worktree was dirty, because a rate measured from uncommitted
  source cannot be attributed to a commit.

So an artifact can pass every timing and control gate and still be
inadmissible as a speed claim. That is exactly the state the reviewer
described, and it is correct behaviour, not a bug in the gate.

### Two further provenance gaps

- `2026-09-12-ud-gfx1100-mtp-automatic-admission.json` backs the README's
  admission grant (2.4126x / 2.3517x) and carries **no** `dirty`,
  `speed_claim_eligible`, or `timing_evidence_valid` field at all, so its
  eligibility is not machine-checkable.
- `2026-09-13-ud-gfx1100-norm-fixed5120-row-slab.json` and
  `2026-09-13-ud-gfx1100-iq-dense-strict-row-slab-cover.json` are
  `status: retained` with per-arm rates (`true_ar_tok_s`, `mtp_b3_tok_s`) but
  **no per-arm provenance block**.
- The four-arm decode A/B (UD 29.98 vs plain 35.37 -> 0.848x; UD 29.49 vs
  plain 36.66 -> 0.804x) is recorded only in
  `benchmarks/results/final-decode-campaign-2026-09-11/README.md`, a markdown
  rollup with no provenance-carrying JSON, so its dirty/eligibility state
  cannot be checked at all.

### Why the K_S arms read `speed_claim_eligible: false` with a clean tree

In `paired-ud-plain-mtp-c1-natural25-b3-graph-xtx.json` the `ud-q4-k-s` arm
has `dirty: false` and `speed_claim_eligible: false` with
`suite_status: correctness_failed` — the recorded `general_ja_plan` exactness
divergence. `docs/EXECUTION-PROFILES.md` section 6 lists generated-ID equality
as `recorded_not_binding` for the production profile, while the artifact's own
eligibility gate treats `correctness_failed` as disqualifying. Those two
policies disagree. This entry records the disagreement rather than resolving
it; it needs an owner decision, because it decides whether the K_S row is
publishable at all.

## Outcome of the re-measurement

`scripts/ud_mtp_paired.py --runs 2 --device-index 1 --expect-device "7900 XTX"`
was run at commit `92c7e3dc45aba24e46d6e1aab8a22df032dda629` with a clean
tracked and untracked worktree:

| arm | true AR tok/s | MTP B3 tok/s | MTP/AR | dirty | speed_claim_eligible | suite_status |
| --- | ---: | ---: | ---: | --- | --- | --- |
| `ud-q4-k-m` | 32.922 | **50.231** | 1.5258 | false | **true** | `complete_exact` |
| `ud-q4-k-s` | 32.311 | 49.356 | 1.5275 | false | false | `correctness_failed` |
| `plain-q4-k-m` | 38.373 | 65.347 | 1.7029 | false | **true** | `complete_exact` |
| `plain-q4-k-s` | 41.135 | 70.092 | 1.7040 | false | false | `correctness_failed` |

Derived parity: `Q4_K_M` **0.858x AR / 0.769x MTP**; `Q4_K_S` **0.785x /
0.704x**. All four arms are `binding_passed` with `timing_evidence_valid`, and
the U6 gate passes with `open_items: []`.

Three results follow.

1. **The clean run confirms the plan doc and contradicts the README.** The plan
doc's `50.131` and the new `50.231` agree to 0.2%; the README's `49.409` was
stale. The README was citing a superseded artifact, and the two documents
disagreed about what the retained result even was.
2. **The `dirty: true` flag was removable, not fundamental.** The first re-run
still read `dirty: true` with `untracked_count: 1`: the untracked file was this
very audit entry. Parking it outside the repository made the second run read
`untracked_count: 0`, `dirty: false`, `speed_claim_eligible: true`. So the
original `dirty: true` on the retained artifacts is consistent with the normal
measure-then-commit order, and the eligibility gate is doing its job.
3. **The `Q4_K_S` row cannot be made eligible by re-measuring.** Both
`Q4_K_S` arms, UD and plain, are `correctness_failed` on the same 2/20
`general_ja_plan` rows with a clean tree. The conflict noted above is therefore
real and blocking for that row, not an artifact of provenance.
