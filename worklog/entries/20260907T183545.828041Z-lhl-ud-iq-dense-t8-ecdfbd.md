# IQ dense strict kernel: T=8 column tile + per-block header preload

## Summary

The GEMV-leaf survey (previous entry) showed the raw IQ/Q3 rows=1 family at
23-38 GB/s while Q5_K/Q6_K reach 124-145 GB/s on identical geometry, and that
this family dominates both published UD files. This unit restructures
`gguf_iq_dense_strict_kernel` and recovers a large fraction of that gap while
keeping the strict reduction contract bit-identical. Production decode on the
K_M public path went from 3.85 to 5.52 tok/s (gross, zbook).

## Changes

`hipengine/kernels/hip_gfx1100/quant/gguf_iq_dense.hip`:

1. **T=8 column tile.** Each 128-thread block now owns 8 consecutive output
   columns (`dim3((N+T-1)/T, rows)`), amortizing the x-row load that the old
   one-column-per-block layout re-read once per output column. Measured T
   sweep: 2/4/8/16 all ran; T=8 was the sweet spot (T=4 and T=2 lose to x
   re-reads, T=16 mostly loses to serialization of the 16 payload streams).
2. **Cooperative per-quant-block header preload.** Phase A hoists each
   column's `(d * scale)` header products into shared memory (at most
   T*16 slots, one per 128 threads), phase B decodes only the payload byte(s)
   per element. This is the same discipline the Q6_K pack8 kernel already
   uses. Per-element global loads drop from ~5 scattered bytes to the payload
   byte(s) plus one warp-uniform shared read.
3. **RB=4 quant blocks per barrier round** with double-buffered shared arrays
   (`s_d[RB][T*16]` etc.): two barriers per 4 quant blocks instead of per
   block. RB=8 measured worse than RB=4 (shared/L1 pressure), RB=4 retained.
4. `__launch_bounds__(128, 16)`: no measured effect (VGPR=48, LDS=640B per
   block never limited occupancy) but documents the intended envelope.

IQ4_NL (Q=1, 32-element blocks) keeps the plain per-element decode inside the
same tile; its tensors are small (embedding-class) and it is not a decode
bottleneck.

## Validation

- RED-first: the restructure initially failed the bit-exact gate three times
  (phase-A out-of-bounds reads on partial tiles; `j`/`g` index confusion;
  nibble variants swapped for IQ2_XS/IQ2_S; Q3_K payload indexing must be
  block-local). Each was fixed against the synthetic decoder test that
  exposed it; final state is exact parity.
- `tests/test_gguf_ud_dense.py`: 84/84 - bit-exact vs the 128-strided
  accumulator reference, both leaf and runtime callers.
- Oracle and surface suites: `test_gguf_iq_dequant.py`,
  `test_gguf_iq_dequant_oracle.py`, `test_gguf_ud_km.py`, `test_gguf_ud_ks.py`,
  `test_gguf_ud_codecs.py`, `test_gguf_ud_admission.py`, `test_gguf_iq_gemv.py`
  (837 total) plus the iq2_xs gemv/mmq/selected-prefill suites (339) and
  `test_gguf_e2e_acceptance.py` (6) - all green.
- Perf (gross, zbook, sustained-load clock variability applies):
  leaf bandwidth 36.5 -> 83.8 GB/s (IQ4_XS), 27.1 -> 60.4 (IQ3_S),
  28.3 -> 70.4 (IQ3_XXS), 28.6 -> 56.6 (IQ2_S), 22.8 -> 41.8 (IQ2_XS),
  31.3 -> 74.2 (Q3_K). Public-path K_M decode 3.85 -> 5.52 tok/s, prefill
  6.0 -> 9.2 tok/s (121-token prompt, 64 tokens). K_S decode 5.80 tok/s.
  Artifact: `benchmarks/results/2026-09-08-zbook-ud-iq-dense-t8-header-preload.json`.
- rocprofv3 kernel census on the public path confirms the new
  `gguf_iq_dense_strict_kernel<*,*,8>` is the top production kernel (7488
  calls in a 4-generation profile), i.e. the optimized route is the one
  serving production decode and prefill.

## Measurement artifacts to distrust

The GEMV-leaf survey's Q4_K rows (33-34 GB/s) were a microbench artifact:
the sweep resolved a different (slower) Q4_K variant than production because
of kernel-registration order in the sweep process. Standalone Q4_K
`launch_gguf_linear` measures 120-137 GB/s and the production kernel census
shows Q4_K served by `gguf_q4_k_pack8_prefill_out` at ~120 GB/s equivalent.
Q4_K was never actually 4-5x slow in production. The survey artifact's JSON
records this correction.

## Next

  dependent table lookups. Headroom vs Q5/Q6 still ~2-3x for the small-bit
  families; next levers would be payload vectorization (u32 loads covering
  nibble pairs) and removing `iq_signs` via bit-scan instructions.
- lm_head Q6_K gemv at N=vocab measures ~65 GB/s (5.6 ms/call, ~2% of step
  time) - separate future target.
