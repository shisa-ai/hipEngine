# the capacity gate is a pure win batch-composition invariance and 9.7 percent more decode

## Summary

Two arms of `scripts/gemma4_campaign_bench.py` against the real 17 GB
`gemma-4-26B-A4B-it-UD-Q4_K_XL.gguf`, both at `--prompt 512 --output 128
--samples 3`:

| arm | route | prefill tok/s | decode tok/s |
| --- | --- | --- | --- |
| 1 | MMQ (post-fix default) | 584, 578, 580 | **27.3144** |
| 2 | uniform grouped | — | 24.8987 |

MMQ beats grouped by **2.4157 tok/s, 9.7%**. Arm 1's three decode samples span
27.24 to 27.41, a within-arm spread of **0.6%**, so the difference is **sixteen
times the spread** and is a real effect rather than noise.

## What this settles

**The capacity-based gate from `20260928T062754` stays.** MMQ for decode is a
9.7% win, so the fallback to uniform grouped is not needed and would cost
decode. The caveat that entry recorded -- that a large-capacity runner's
single-token decodes now run MMQ and that throughput was unmeasured -- is
**closed in the favourable direction**.

**The old baseline is now explained.** Arm 2's 24.8987 matches the 24.85 figure
this branch had been measuring against to within 0.2%. The pre-fix gate
(`lanes = rows * top_k` against `num_experts`) took the **grouped** route for
decode and MMQ for prefill, so that baseline was a **mixed** configuration, and
both uniform configurations were unmeasured until now.

**The batch-composition-invariance fix cost nothing and gained about 9.7%
decode**, because the mixed configuration it replaced was running the slower
route for the decode half. The contract fix and the throughput win are the same
change.

**Prefill is unchanged at 584 tok/s**, so the prefill gap to the 1013 reference
(1.73x off) is untouched by all of this.

## Environment note

`scripts/gemma4_campaign_bench.py` guards the visible device against
`DEFAULT_EXPECT_GPU`, which names the W7900 campaign host. On the 8060S the run
refuses until `--expect-gpu 8060S` is passed. The refusal exits 0 from the shell
pipeline's point of view -- the error comes from the per-arm Python and the
pipeline's status comes from `tail` -- so an arm that measured nothing can read
as a successful arm. Worth knowing before trusting a green background task here.
