# delete the gemma4 expert pack8 layout, the settlement is complete

## Summary

**The expert pack8 layout is gone.** `docs/REFACTOR.md`'s entry for it was settled
on 2026-09-28 -- the packed layout is never ahead -- and its own second bullet
named the deletion as the thing that unblocks. That deletion is now done, so the
ledger entry is resolved rather than open.

This is the deliverable `20260928T101120` identified, and it is a code change
rather than another attribution unit.

## What was removed

From `hipengine/loading/gemma4_gguf_device.py`, which drops 486 to 270 lines:

- `pack8_layout_enabled()` and the `HIPENGINE_GEMMA4_EXPERT_PACK8_LAYOUT` flag
- `LAYOUT_Q4_K_PACK8` and `_PACK8_ALLOCATION_NAMES`
- `_pack8_shapes()`, `_pack8_nbytes()`, `pack8_arrays()`, `_materialize_pack8()`
- the planning branch that gave a rank-3 `Q4_K` expert tensor the packed layout
- the pack8 branch in `resident_bytes()`
- `_product()`, which only `_pack8_nbytes` used, and `import os`, which only the
  flag read

From `hipengine/kernels/hip_gfx1100/gemma4/gemma4_experts.py`: the
`pack8_selected` rung of the expert route ladder, `gemma4_project_experts_pack8`,
and its `_PACK8_LAYER` / `_PACK8_VARIANT` constants.

Also: the `gemma4_project_experts_pack8` leaf in
`scripts/gemma4_prefill_kernel_census.py`, the env-var row in `docs/ENVS.md`, and
the six tests in `tests/test_unit_gemma4_gguf_device.py` that existed to exercise
or pin the layout.

## What deliberately remains, because it is a different thing

**`_SELECTED_PACK8_VARIANT` and the `pack8_selected` GEMV kernels were left in
place.** The shared name is a trap I checked before cutting: that family is the
eight-output-columns-per-block form of the per-lane selected GEMV over the **raw**
blocks, preferred where registered by `gemma4_project_experts_selected` -- a live
route -- and pinned bit-exact against its single-output owner by
`tests/test_unit_gemma4_expert_route.py::test_pack8_selected_is_bit_exact_against_the_single_output_owner`,
which still passes. It shares the name and nothing else. The dense `require_pack8`
GEMV path in `hipengine/kernels/hip_gfx1100/quant/gguf_k_gemv.py` is likewise
unrelated, as is the qwen35/laguna `LAYOUT_Q4_K_PACK8`, which is defined
independently in `hipengine/loading/laguna_gguf_materialize.py` with the same
string value.

**`hipengine/loading/__init__.py` needed no change.** It re-exports a
`LAYOUT_Q4_K_PACK8` and the grep flagged it, but the file contains no `gemma4`
reference at all -- those exports are qwen35's.

## What it buys

A flag, a 19.2 GB raw/packed duplication path, and 116.6 s of load-time repacking
off the path of anyone who had set the variable. The load path itself is
unchanged for everyone else, since the flag was off by default.

**The pinning test is gone with the flag, and that is the correct end state rather
than a coverage loss.** It existed to stop a silent flip back to a 2.75x decode
regression; there is no longer a default that can flip.
