# Muse Glimmer DFlash speculative decode: draft oracle, GPU drafter, exact cycle

## Summary

P3 DFlash implemented: dual-mode draft model (target-feature KV injection +
non-causal masked-block token mode), GPU drafter composed from registered
kernels, and a target-corrected greedy draft/verify/commit provider with
contiguous-KV truncate rollback. Capability-gated (architecture + structural
checks), auto-discovered sidecar for ship-on; no identity gating.

## Changes

- `scripts/muse_glimmer_dflash_oracle.cpp`: llama.cpp API oracle — target
  prefill with `llama_set_embeddings_layer_inp` extraction at [2,14,26,38,50],
  feature injection, `llama_set_causal_attn(ctx_dft,false)` noise block, draft
  logits dump. (The non-causal call is essential: the first tool revision
  missed it and the mask rows diverged — anchor row matched, the classic

  embedding norm on the draft input.
- `hipengine/runtime/muse_glimmer.py`: `prefill_with_taps`, `decode_with_taps`,
  `verify_with_taps` (all-row logits), `truncate`; layer-input taps captured
  BF16->F32 in tap order.
- `hipengine/runtime/muse_glimmer_dflash.py`: resident drafter — raw-layout

- Generator: attach/supports/capabilities/generate_speculative_detailed/

## Debugging findings

- Draft semantics: CPU reference vs llama.cpp oracle — 16/16 block argmax,
  cosine 0.9998 (residual = oracle's RDNA3 MMQ int8 activations, the
  documented changed-arithmetic pattern; the f32 env cannot reach MMQ).
- GPU drafter vs oracle: 16/16 argmax, cosine >= 0.999 gate green (after
  fixing the fc activation dtype: F32 features must not be read as BF16).
- Exactness suite: the first run caught a real cycle bug — on partial
  acceptance, verify row j processed the *rejected* draft token, so its KV
  and logits belonged to the wrong token. Fix: truncate to the accepted
  prefix and process the corrected token fresh (one extra target decode per
  partial cycle, the same reprocess llama.cpp does in its next batch). The
  all-accepted path was already correct (every verify row saw an accepted
  prefix; the bonus token is processed fresh).
- Second exactness failure (general_en_explain, index 27): multi-row verify
  projections dispatch to different kernels than single-row decode, so the
  verify-written K/V differ by bf16 rounding and flip near-tie argmaxes
  (measured: post-truncate decode logits shift up to 0.05 vs AR; decode-with-
  taps vs decode-step is bit-identical, isolating the row-count dispatch).
  Fix: verify runs the single-row decode path per token (bit-identical KV to
  AR). The batched-invariant block verify (row-independent GEMV verify +
  decode-equivalent attention) is the recorded task #7 performance work —
  without it a block verify costs k forwards and cannot beat AR.
