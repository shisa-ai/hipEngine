# Natural ShareGPT MTP route comparison: the staged route is inert below the graph cap and 1.65x the row-wise route above it

## Summary

Task #9 asked for the staged linear-attention route to be re-reviewed against the
shipping row-wise route on a realistic load, with each guard classified instead of
left implicit. The answer on natural (unpadded) ShareGPT prompts, one server
process per route, every load carrying an explicit no-MTP autoregressive control
beside the speculative arm (`--route-mix off,auto`):

| lane (matched prompts, c=1 unless noted) | AR | row-wise route | staged route |
| --- | ---: | ---: | ---: |
| natural short (median 36-token prompts) | 12.02 | 23.62 (**1.96x**) | 23.54 (**1.96x**) |
| natural short, c=4 staggered | 4.62 | 3.91 (0.85x) | 3.93 (0.85x) |
| natural long (608-1,929 tokens) | 8.75 | 9.33 (**1.07x**) | 15.39 (**1.76x**) |

The two routes are identical below the 1,023-token graph cap because the cached
native target graph replays the whole target step there and the dense
linear-attention chain never runs. Above the cap the graph refuses with
`target_graph_context_bucket_miss` and the eager chain serves the cycle, which is
where the promotion pays: **1.65x the row-wise route on the same prompts and
tokens** (1.81x excluding prefill), same acceptance (0.688), same cycle count (695).

Guards, each classified rather than assumed:

- **Speculation beats autoregressive decoding at concurrency 4: not satisfied.**
  Matched c=4 short lanes measure 0.85x on both routes (identical because both are
  graph-served); aggregate throughput 13.9 against 16.4 tok/s.
- **The speculative stream reproduces the autoregressive stream token for token: a
  transition requirement, met by the registered strict control and knowingly relaxed
  by the default verify path.** `HIPENGINE_GGUF_MTP_VERIFY_MODE=serial_exact` is
  identical to the AR arm on **9/9** natural prompts; the default `native` mode is
  identical on **6/9** short and **8/9** natural long (eager) prompts. The
  arrival-order control (two rows of the same prompt, same arm, one process) is
  **9/9 identical in all three lanes**, so the difference is the verify arithmetic
  and not submission order. Token exactness costs 2.9x throughput: 8.07 against
  23.55 tok/s for `native`, below the 11.54 tok/s AR control. Every divergence is a
  single token whose two continuations are semantically equivalent.
- **Every cycle below the split threshold is graph-served: a physical limit of the
  retained short bucket plus a schedule requirement.** Gate cycle ends 1,016-1,032
  submit the graph (`target_native_graph_submitted=true`) with `split_k_calls=0`
  against a required 4, inside the production numerical envelope (KL 5.2e-05 to
  3.5e-04, top-1 agreement 1.0) while failing byte-exactness.
- **Absolute task quality: not established, route-neutral.** The task packet
  records `output_ids_exact=true` and `gpu_accept_match_cpu=true` for every task
  while `task_score_passed=false` with `selected_choice=null`: the scored output
  equals the teacher's and the packet's answer extraction found no choice letter.

## Validation

- Correctness: the gate arms in the packet ran green on this commit
  (`--cycle-ends 3530 --candidate-budgets 3 --disable-target-graph`, 5/5 direct
  cases, warm and under the profiler) with `staged_chain_calls` 48 and
  `row_wise_attn_calls` 0 per case, the row-wise control at 192 row-wise calls,
  and `qwen35_paged_full_attn_decode_split_k_gate_bf16_spans` observed at 64 calls
  against a required 14.
- Kernel trace: `rocprofv3 --kernel-trace --output-format csv` over the same gate
  command after an unprofiled warm build, `HIPENGINE_REQUIRE_CACHED_BUILD=1` with
  the compiler version pinned; 46,222 launches, 157.2 s device time, with the
  per-cycle families named in the artifact.
- Performance: three measurement phases, each on the physical host
  `gfx1151`/`55ea6c50...` (Ryzen AI MAX+ 395, Radeon 8060S), Qwen3.8-27B
  `Q4_K_M`, bf16 KV, candidate budget 3, temperature 0, prefix cache off,
  `HIPENGINE_MTP2_OUTPUT_SPANS=1`. Phase 1: 24-prompt loads at c=1 and c=4 on both
  routes. Phase 2: matched lanes (`--prompt-repeats 2` with an odd prompt count)
  plus a natural-long lane with the adapter window raised to 8,192. Phase 3: three
  `--prompt-repeats 3` lanes separating arrival order from verify mode and from the
  graph (`native` short, `serial_exact` short, `native` long-eager).
- Harness traps found and worked around, both recorded in the artifact: the
  readiness probe must be `/ready` (503 until the engine holds a model), and
  `--prompt-repeats 2` with an **even** `--num-prompts` gives each prompt the same
  arm in both repeats, so `arm_identity` compares zero prompts; the matched lanes
  use an odd count.
