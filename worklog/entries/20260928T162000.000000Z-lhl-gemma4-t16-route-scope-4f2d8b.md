# the t16 route is a weight layout, not a kernel: promoting it is a repack unit

## Summary

`20260928T160000` scoped the promotion of the registered t16 gate/up route as "wire the
t16 route for the production shape". Reading the wrapper shows that framing was too
optimistic, and the reason is in the wrapper's own docstring.

**`gguf_q4_k_t16_selected_dual_q8_1_ds4_mmq32_fused_prefill_compact32_bf16_bf16_out`
delegates to the production kernel.** Its body calls
`gguf_q4_k_selected_dual_q8_1_ds4_mmq32_prefill_compact32_bf16_bf16_out` with the same
pointers and the same argument list. The docstring says what actually differs:

> Launch MMQ32 against resident T16 weights in a fused gate | up row block. Both changes
> at once: the weights are **16-wide output tiles rather than raw GGUF blocks**, and the
> two weight pointers address the gate and up slices of one per-expert row block, so the
> tile run covers the fused width and the up half's tiles start after the gate half's.

**The kernel is shared; the difference is the weight layout the caller prepared.** The
13 percent the harness measured is the value of that layout, not of a different kernel,
which is consistent with it: the prototype's `t16` mode differs from its plain mode in
the same way.

**So the promotion is a repack unit, not a symbol swap.** The expert weights must be
repacked from raw GGUF Q4_K blocks into 16-wide output tiles before the route can run,
which means a repack step, a loader path for the repacked artifact, and the wiring that
selects it -- and the repack has to be validated against the strict owner exactly as a
new kernel would be, because the arithmetic it feeds is the same one that already
carries the route's activation-quantization error bound.

## T16 already exists in this tree, in the decode path

`hipengine/core/specdec2_scope.py` carries the layout as a request-local scope:

```python
_q4_t16_physical_extra_rowtiles: ContextVar[bool] = ContextVar(
    "q4_t16_physical_extra_rowtiles", default=False)

@contextlib.contextmanager
def q4_t16_physical_extra_rowtiles_session(enabled: bool) -> Iterator[None]:
    """Select production-qualified extra Q4 rowtiles for one physical target."""
```

with `q5_t16_physical_rowtile`, `q6_t16_physical_rowtile` and
`q6_t16_physical_mixed_rowtiles` alongside it. **"Production-qualified" is the
implementation's own word for this layout**, so the repack machinery is not
hypothetical -- it exists and is exercised. It is scoped to the speculative-decode
target rather than the prefill, which is the gap the promotion would have to close.

## What this means for the candidate

The 13 percent design margin measured in `20260928T160000` stands, and so does the
observation that the dp4a MMQ32 family is where it lives. **What changes is the size of
the unit**: repack plus loader plus wiring plus parity plus an end-to-end measurement is
a session-scale change, not the one-line import swap the previous entry implied. The
expected end-to-end value is unchanged at about **20 ms of a 687.7 ms prefill, 3.0
percent**, if the design margin transfers to the production geometry -- and the
production geometry is not the fixture the margin was measured on.

## Next

- **The repack unit, if it is taken, should start by finding where the decode path
  builds its T16 row tiles.** `q4_t16_physical_extra_rowtiles_session` is the consumer;
  its producer is the repack the prefill route needs, and reusing it is the difference
  between a loader change and a new subsystem.
- **Re-measure the design margin on the production geometry before doing the repack.**
  The harness fixture is 5504 wide against the gate/up projection's 1408 and cannot be
  reduced (`--out-features-b 0` is rejected). A repack is a large unit to start on a
  number measured at the wrong width.
- **The rest of the excluded set stands**: `ROWS_PER_PASS`, the readback drain, the down
  projection's ceiling, the WMMA direction, and the shared-cause instruction-mix
  hypothesis are all measured and closed.
