# Small-row prefill extent is live tokens; the 256-row lead is dead

## Summary

Settled the lead from `20260830T165104…` from source, without a GPU run. The prefill
launch extent is **live
token count**, not the 256-row scratch capacity the probe reported, so "we compute 256
rows for 45" is dead.
Whatever the small-row prefill deficit is, it is inside the kernel and its schedule, not
a mis-sized extent.

## Changes

- Decision only; no code change. Closes an open item recorded one entry ago.

## Evidence (read, not inferred)

- `launch_gguf_linear_pair` takes an explicit `rows: int` parameter
  (`hipengine/runtime/gguf_linear.py:3644-3650`), as do the `_silu` and `_concat` variants.
- Prefill-side callers pass live counts: `rows = len(self.token_ids)`
  (`hipengine/runtime/qwen35_gguf_runner.py:719`) and `rows = int(self.row_end) -
  int(self.row_start)` (`:1013`).
  Decode call sites pass `rows=1` literally.
- Therefore `prefill_scratch_rows_planned = 256` in the probe is an allocated capacity,
  which costs memory, not
  compute.

## What the same file says about the region

- `hipengine/runtime/gguf_linear.py` already carries measured route decisions for exactly
  this row regime:
  a rows<=8 small-B rowtile/GEMV domain, `rows<=32` keeping the unfused chain because the
  fused owner measured
  8.2% slower in 16/32-row groups, and recorded prefill deltas at rows 16/24/32/45/96/192
  (+1.7% to +2.1%) with
  identical generated ids. So the route space around 45 rows has been swept; the remaining
  ~250 ms fixed cost at
  ~45 rows lives below the dispatch layer.

## Consequence for #12

- Scope is now only the kernel and its launch schedule: grid/occupancy and fixed setup for
  row counts below tile
  height at Q4_K prefill shapes, with strict `kernels/cpu_reference/` parity and a
  `rocprofv3 --kernel-trace`
  entry. Route choice, extent, and the all-GEMV alternative are all measured out.
