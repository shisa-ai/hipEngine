# 24 GB XTX dense-27B MTP startup OOM

## Summary

A user reported Qwen3.8-27B Q4_K_M (embedded MTP head) dying with HIP OOM in
eager warmup on an RX 7900 XTX (24 GB), at every `--max-context-tokens` from
4K to 32K and with either KV storage. Reproduced on our XTX with both PyPI
0.7.1 and v0.8.0 using `/models/gguf/Qwen3.8-27B-Q4_K_M.gguf`.

Root cause of the startup OOM: the failing allocation is not target prefill.
It is the NextN draft provider's batch session (`Qwen35GGUFNextNExecutor`),
built lazily by the first MTP request (the `WARMUP_SPECULATIVE_MTP` smoke).
The draft runs on adapted one-layer weights whose geometry misses the gfx1100
H5120 row-cap policy, so `_prefill_scratch_rows` picks the natural 4,096-row
chunk and `__post_init__` eagerly allocates a ~3.2 GiB
`_GGUFFullAttentionPrefillScratch` (about 0.8 MiB per row). Those rows also
floor the draft's packed-verify scratch via `_packed_verify_union_geometry`.
The draft session never runs chunked prefill (it steps 2-8 hidden rows, and
the MoE-only bulk prime grows the packed workspace to the prompt length on its
own), so the 4,096 rows were pure overhead.

The warmup treats the failure as non-fatal, prints `hipEngine ready`, but the
engine service is already closed: every later request returns 503
`engine_unavailable`.

## Changes

- `hipengine/runtime/qwen35_gguf_nextn.py`: the draft batch session passes
  `prefill_chunk_size=_NEXTN_BATCH_PREFILL_SCRATCH_ROWS` (128). Draft bulk
  scratch measured 0.13 GiB instead of the 4,096-row allocation that failed.
- `tests/test_unit_qwen35_gguf_nextn_batch_session_scratch.py`: RED/GREEN pin
  that the executor sizes its batch session with that ceiling.

## Validation

- RED: the new test failed with `KeyError: 'prefill_chunk_size'` before the
  change; GREEN after.
- `uv run pytest -k "nextn or mtp or capacity"`: 3602 passed, 2 skipped.
- RX 7900 XTX (GPU 1), `hipengine serve --max-context-tokens 4096 --kv-storage
  int8_per_token_head`: MTP warmup passes; plain-default (auto MTP) and
  explicit `speculative_mtp: true` requests return correct text on route
  `speculative_mtp` (acceptance 0.76 on a 16-token prompt).
- W7900 (GPU 0), default settings: auto context 61,440; short and 3,013-token
  `speculative_mtp` requests succeed on route `speculative_mtp`.
- XTX, same 4K INT8 config with `--speculative-mtp-serving off`: a 3,013-token
  prompt serves (unaffected by this change; the reporter's "off also fails"
  did not reproduce on v0.8.0).

## Next

- Still failing on XTX with MTP on: a 3,013-token `speculative_mtp` prompt at
  4K INT8 OOMs in `_int8_prefill_oracle_cache_for_layer` (72 MiB request, 0
  free). `_int8_prefill_oracle_capacity_positions` sizes each layer's BF16
  oracle pair to every physical page of the shared KV pool (36,864 positions on
  a 4,096-token server), about 2.3 GiB across 16 layers, whereas the estimator
  prices the transient at 64 KiB x context. Either address the oracle by the
  request's logical span or price the pool-sized oracle in
  `qwen35_gguf_resident_breakdown`.
- The auto-context estimate never prices the MTP draft provider (~525 MiB
  hot-vocab head plus ~260 MiB layer weights plus scratch, ~1.8 GiB total
  measured on XTX), which is built after sizing.
- `bytes_per_token` in the `KVCache:` log is the marginal footprint, including
  `private_workspace_bytes` priced for `workspace_lease_slots` (4 under auto
  concurrency): 404,064 B/token BF16 at 32K versus 64 KiB of real KV.
- The pinned-context warning says "the selected context ... is the largest that
  fits" even when the estimate says it does not fit (32K BF16:
  `allocatable_context_tokens=1792`).
- A non-fatal startup warmup failure that closes the engine service should
  fail startup (or report not-ready) instead of printing `hipEngine ready`.
- `HIPENGINE_MAX_PREFILL_CHUNK_TOKENS` does not bound these session scratch
  rows; the reporter tried 2048 and saw no change.
