# The sampled MTP route commits its coupled accept on device and beats its AR control

## Summary

The sampled (temperature > 0) MTP route now decides its coupled acceptance from
the verifier's own device logits and commits it on device, so a sampled row
keeps the N2 target graph instead of paying one full-vocabulary logits row per
verified prefix on the host. On the rejected artifact's own protocol the arm
goes from **0.47x to 1.90x** of its in-load true-AR control.

The production cap4 c1 evidence row advertises the sampled mode, so a
temperature request at that key takes this route by default. The guard that
pinned the route closed is inverted rather than deleted: it now requires the
sampled mode to appear on exactly the row whose artifact measured the win.

## Result


Same host, `Qwen3.8-27B-Q4_K_M.gguf`, `hip_gfx1151` (zbook, Ryzen AI MAX+ PRO
395 / Radeon 8060S), production profile, 8192-token context, bf16 KV, one server
process, in-load control assigned per request:

```
scripts/sharegpt_mtp_routing_pass.py --num-prompts 4 --min-prompt-len 64 \
  --max-prompt-len 900 --max-total-len 2048 --output-len 128 --record-ids \
  --seed 4242 --temperature 0.7 --route-mix off,off,on,on
```

| arm | decode tok/s | median ITL | median TTFT | MTP output tokens |
| --- | ---: | ---: | ---: | ---: |
| sampled MTP (`on`) | **26.05** | **36.4 ms** | 4073 ms | 253 / 256 |
| in-load AR control (`off`) | 13.73 | 132.1 ms | 1713 ms | 0 |

**1.897x decode, 3.63x median ITL.** The same process's greedy arm (2 prompts,
`--temperature 0.0 --route-mix on --output-len 32`) holds 10.30 tok/s with 100%
request coverage and 96.9% MTP output share.

The pre-fix tree measured **6.42-6.54 tok/s against 13.67-13.73 (0.475x)** on
this protocol, in three separate runs, reproducing the rejected artifact. The
gain is therefore the device accept and not a change in draft quality:
acceptance is unchanged (253 of 256 output tokens from speculative cycles, 89
accepted over 38 cycles on the sampled arm in the pre-fix runs), and the graph
path is only reachable when the device plan exists, because `allow_graph` is
gated on it.

## Changes

Four repairs, all retained, three of them in this session's own wiring:

1. **The plan rides the request state.** `_DeviceSampledAcceptPlan` was created
   as a `propose_batch` local and read in `execute_target_frontier`
   (`NameError`), and the N2 capture read a `sampled_library` bound only inside
   one branch (`UnboundLocalError`). The engine loop *contains* these failures,
   and a contained failure drops the request with `disable=True`, so every later
   cycle planned `no_provider` — for **every** row, greedy included — with one
   `[cycle-failure]` line as the only trace. Fixed in `da6c124d0`, with
   `test_sampled_accept_plan_rides_the_request_state_between_phases` pinning the
   seam (RED at `3db16a0d2`).
2. **The capture binds its handles.** `sampled_library` is initialized with the
   other kernel handles and the argmax accept kernel is resolved for both
   topologies: the sampled variant replaces its launch, not its registration.
3. **The adapter reads the planner's mode.** `_sampled_route_request` and
   `_device_sampled_accept_plan` read the row's *raw* request through
   `speculative_sampling_mode(params)`, which answers `processed` for a
   temperature request that carries EOS (the server relaxes thinking fields for
   the MTP path), while the planner reading the scheduler's resolved sampler
   block answers `sampled`. `capability()` now records the planner's mode per
   request and both adapter-side probes reuse it.
4. **The sampled variant is warmed outside the capacity-1 warmup.** Its only
   capture site was inside `if self.owner.capacity == 1:` in
   `observe_prefill_result`, and the serving configuration that admits the
   route runs at resident capacity 4, so the variant was never captured and
   every cycle declined the device plan for a missing graph. The warm is now
   unconditional on capacity, gated on a prefill-time candidate predicate
   (host sampler, temperature > 0, qualified route) because the planner has not
   published a mode for the row yet at prefill. The prefill-time identity
   (`state`, `row`, `target`, `token_id`, `budget`) is resolved once above both
   blocks.

## Scope and what is not covered

- One load point per arm (2 requests each), one seed, c=1,
  `realized_group_rows=1`, `resident_capacity=4`, candidate budget 3, bf16 KV,
  uniform layout, production profile. Not a repeated-run campaign; the
  pre-fix counterfactual is three runs of the same protocol on the same host.
- **c >= 2 is not covered.** Those lanes still inherit the one-row policy cell
  (the 242 `no_provider` events in the rejected artifact), so a wider admitted
  cell or an explicit serial-rows decision is still required there.
- The sampled arm's TTFT is 2.4x the control's (4073 ms against 1713 ms) because
  the sampled row's prefill is not the packed path. That is now the dominant
  cost at these prompt lengths and is the next lever, not the cycle cost.
- The measurement ran with `HIPENGINE_DEBUG_SAMPLED_ROUTE=1` (stderr only); no
  trace-off point was measured.
