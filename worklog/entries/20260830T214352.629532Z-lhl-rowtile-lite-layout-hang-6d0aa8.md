# feeding the lite tile layout to dense_rowtile hangs the device

## Summary

Task #12 was diagnosable but not closable. `dense_rowtile` takes only `(x, tiles, out)`, so its ~1e7 ULP
divergence cannot come from missing metadata arguments, and the wrapper calls itself the "compact-T16
row-reuse owner", which points at the 2304-byte `tile16_lite` layout rather than the 2368-byte full layout
the sweep feeds it. I wired a lite payload into the sweep and the arm **hung the GPU instead of producing
output**. The attempt is reverted and uncommitted. Recorded as a hazard: those leaves must not be handed an
unvalidated layout without a watchdog, because the failure mode is a kernel that never completes.

## Changes

- None retained. `scripts/gguf_t16_prefill_row_sweep.py` is restored to `2e31d9099`. The lite wiring was
  unvalidated and could wedge the device for anyone who ran it, so it is neither committed nor left behind a
  default-off flag.

## Validation

- `--rows 2,4,6,8` on `(17408,5120)` with a lite payload produced **zero output for 900 s** (`rc=124`). It
  blocked before the first row's result line, so inside that row's arm loop, not during payload build.
- After the process was killed, `rocm-smi --showuse` reported the device usable and a fresh
  `get_hip_runtime().device_synchronize()` returned in **0.27 s**: the wedge cleared with the dead process
  instead of persisting in the driver.
- `tests/test_gguf_q4_k_t16_dense.py -k physical_r6` normally finishes in seconds, showed the same stall
  while the hung kernel was alive, and then **passed in seconds** once it was gone. That pairs the two
  observations: the stall belonged to the hung kernel, not to the environment.
- Repacker cost is not the explanation. On a 256-column probe `repack_gguf_q4_k_tile16` took 0.02 s and
  `repack_gguf_q4_k_tile16_lite` took 0.01 s.

## Next

- #12 still needs the correct tiles payload for `dense_rowtile` / `dense_rowtile_col4`. The safe route is to
  copy the exact call site from the production sidecar path, which already runs these leaves at rows 2-8,
  instead of reconstructing a layout from docstrings. Guessing wrong here costs a device wedge, not a bad
  number.
- Scope check that survives the failure: those leaves are contract-capped at rows 2..8 by
  `_check_dense_q4_t16_rowtile_shape`, so a valid result still cannot move prefill (rows 33-192) and cannot
  close #11. #11 stays a genuine new-kernel task - the down projection's ~107-column-block grid against 512
  compute units needs split-K or column resplit with a `kernels/cpu_reference` RED gate.
