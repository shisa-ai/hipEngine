# decode runs at 36 percent of dram peak so the 2x target needs 53 and the expert arm is provably broken

## Summary

The traffic census counts bytes per decode step directly, which turns the route ablation's
milliseconds into bandwidth and settles two open questions at once. It also produces a
number that cannot be true.

`scripts/gemma4_decode_traffic_census.py --prompt 8 --output 16`:

```
TOTAL                                    3255.7 MB/step
launches per step:                        762.7
expert-mmq gate_up gguf_q4_k   30.93 launches   795.4 MB
expert-mmq down    gguf_q5_1   30.93 launches   529.4 MB
```

## The bandwidth picture

Against the ~256 GB/s DRAM peak of this part, with the ablation's 35.53 ms step:

| | MB/step | measured | GB/s | % of peak |
|---|---|---|---|---|
| **total** | 3255.7 | 35.53 ms | **91.6** | **35.8%** |
| dense Q8 | 1930.9 | 15.23 ms | 126.8 | 49.5% |
| **experts** | 1324.8 | 0.54 ms | **2453.3** | **958%** |

**The decode step runs at 35.8% of DRAM peak.** The bandwidth floor for these bytes is

```
3255.7 MB / 256 GB/s = 12.72 ms/token = 78.6 tok/s
```

against today's **28.1 tok/s**. So the step is **2.8x off its own bandwidth floor**.

## What the objective's target actually requires

**41.9 tok/s = 23.85 ms/token.** At that step time the same 3255.7 MB/step needs
**136.5 GB/s, which is 53.3% of DRAM peak.**

That is the whole decode target stated as one efficiency number: **get the step from
35.8% to 53.3% of DRAM peak.** The dense Q8 path already runs at **49.5%**, so the
efficiency being asked for is one this engine has already demonstrated on part of the
step. This is a reachable target and it is not a bytes problem -- the bytes are what they
are.

## The number that cannot be true

**The expert arm's 0.54 ms implies 2453 GB/s, or 958% of DRAM peak.** No kernel can move
1324.8 MB in 0.54 ms on this part. Combined with `20260928T072625`'s finding that the arm
is only 0.65 sigma from zero, the conclusion is no longer "under-resolved":

**The `no_experts` arm does not skip the expert work.** The census proves the launches
happen and the bytes are real; the ablation proves the arm's savings are impossible for
those bytes. The arm's `spy_selected` hook does not intercept the route that actually
runs, which is the same shape as the `no_all_gemv` anomaly in `20260928T072536` -- the
expert path is reached through an entry point neither hook covers.

**Consequence: the expert path has no valid measurement in the ablation table.** It
moves **40.7% of all bytes in the step** and its cost is unknown.

## What the residual says

The arms overlap -- skipping a route removes dependent work, so individual savings are
not additive -- so the residual is only suggestive. Still: the accounted arms sum to
about 30.98 ms against a 35.53 ms step, leaving ~4.55 ms unattributed, which is the right
order for an unmeasured expert path. That residual in turn implies ~291 GB/s, still above
peak, so the residual arithmetic does not close either. It is recorded as a bound on the
direction, not as a measurement.

only its byte totals are read, not its timing.
