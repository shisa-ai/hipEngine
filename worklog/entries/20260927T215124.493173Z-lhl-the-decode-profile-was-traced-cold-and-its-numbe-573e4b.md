# The decode profile was traced cold and its numbers do not survive
## Summary
The previous entry recorded a decode profile and ranked its kernels. That ranking
is **not sound** and is withdrawn here. The profiled run was a cold run, and
`rocprofv3 --kernel-trace` serializes dispatches, so neither the absolute times
nor the balance between kernels is representative.
This entry supersedes the quantitative content of
`worklog/entries/20260927T214634.034019Z-lhl-the-gfx1151-decode-profile-puts-half-its-time-in-fa3133.md`
and
`benchmarks/results/2026-09-28-gemma4-gfx1151-decode-profile.json`. The artifact
now carries a `correction` block naming what is wrong; the earlier entry is left
in place because committed entries are immutable.
## The contradiction that exposed it
| reading | profiled run | clean run |
| --- | --- | --- |
| prefill | 33.45 s | 1.52 s |
| decode | 4.31 tok/s | 20.03 tok/s |
| per forward | 2.53 s | 0.135 s |
The profiled run's own JSON reports `prefill_s = 33.45`, which is the JIT
compilation of a cold start rather than prefill work, and `decode_tps = 4.31`.
The trace spans 40.499 s across 16 forwards. The clean run is about **19x**
faster per forward.
The arithmetic then contradicts itself directly. The decode window holds
**2.766 s of kernel time over 15 decode forwards, 184 ms per token**, while the
clean run measures **49.9 ms per token of wall time**. A single-stream trace
cannot contain more kernel time than wall time.
## Why the earlier overlap explanation was wrong
The previous entry noticed the 3.5x discrepancy and attributed it to decode
issuing work on more than one stream. Checking that directly:
- `Stream_Id` is **0** for every dispatch in the decode window.
- The critical-path union equals the naive duration sum **exactly**, 2.766 s both
  ways, which is what a single stream must give.
So there is no overlap to explain the discrepancy. The kernel durations
themselves are inflated by tracing. The earlier entry reached the wrong
conclusion from the right observation, and the fix is not a better denominator —
it is a different measurement method.
## What survives, and what does not
**Survives:** the kernel list shows which kernels the decode path issues,
including that grouped prefill-shaped kernels with very large grids are among
them. That is a lead worth testing.
**Does not survive:** every millisecond figure, every percentage share, and the
bandwidth reading derived from them (45 GB/s of 256 GB/s). The 49.6 percent MoE
share is withdrawn.
## What replaces it
An overhead-free A/B. `scripts/gemma4_campaign_bench.py` reports `decode_tps`
directly, so timing a decode with the grouped expert route disabled against the
same decode with it enabled gives a clean attribution with no profiling
serialization. If a trace is genuinely needed, warm up first, profile only a
warmed region, and prefer counter-only collection over `--kernel-trace`.
