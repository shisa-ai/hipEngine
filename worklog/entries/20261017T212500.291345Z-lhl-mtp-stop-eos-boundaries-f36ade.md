# Honor stop and EOS boundaries during Flash-Next MTP verification

## Summary

The Flash-Next provider now shares AR's terminal-boundary policy for stop IDs,
multi-token stop sequences, minimum-token limits and request-specific EOS.
Every root, serial verifier row, batched verifier row and scheduler K0 step
checks the boundary before consuming another target distribution. Only the
consumed prefix advances target/draft state and the request sampler.

This is a lower-layer control implementation unit. HTTP capability/admission
is deliberately unchanged until the processor/grammar integration is tested;
PS6/task 19 remains open. No performance claim or GPU arithmetic change.

## Changes

- Replace duplicated EOS-only stopping in `qwen4_exp_mtp.py` with the existing
  `_token_finish` helper. Preserve the full finish record, including matched
  stop sequence, resolved EOS and output bound, while naming the MTP sampler.
- Remove these controls from the provider's unimplemented-control rejection.
  Keep grammar, forced/structured/thinking controls and resident-session guards
  until their ownership integration is complete. No new flag or fallback path.
- Retain raw provider committed IDs/logprobs (including terminal tokens) for
  ownership/accounting. Existing resident collection removes only the terminal
  stop/EOS bytes and corresponding visible logprobs; generated IDs remain exact.
- Migrate obsolete rejection tests to still-unimplemented forced/structured
  controls rather than retain stale assertions against the supported controls.
