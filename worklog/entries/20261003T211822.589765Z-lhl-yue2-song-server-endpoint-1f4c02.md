# Serve song generation at POST /v1/audio/songs

## Summary

The server routes on the surface a model declares. A model that declares `song`
serves `POST /v1/audio/songs`, returns `audio/wav` or a JSON provenance document,
and refuses the text endpoints with a named capability miss; a text model does the
reverse. Before this, a served YuE2 model had no reachable endpoint at all.

## Changes

- `hipengine/server/api.py` — `POST /v1/audio/songs` over `LLM.generate_song()`
  through the thread pool. `wav` returns the audio with generation identity headers
  (`X-Hipengine-Request-Id`/`-Frames`/`-Duration-Seconds`/`-Latent-Identity`/
  `-Audio-Identity`/`-Generation-Seconds`); `json` returns the same audio as base64
  plus the plan, semantic token count, truncation flags, checkpoint identities, and
  timing. `_SongRequestCancellation` polls `Request.is_disconnected()` and feeds the
  pipeline's cooperative `cancelled` hook, so a disconnected client stops the song
  between stages rather than after it finishes. A busy pipeline is a retryable 429
  `engine_busy` with `Retry-After`; a cancelled request is 499 `cancelled`.
- Startup — `_resolved_generation_surfaces()` reads the declaration from the loaded
  engine, and `_startup_generation_surfaces()` resolves it from model metadata on
  the lazy path, so routing is decided before the first request. A model with no
  text surface builds its pipeline during startup instead of running the text
  warmup, chat smoke, and KV-pool preparation it has no use for; `/ready` returning
  200 then means the advertised request is servable. Startup logs
  `SURFACES: model=… surfaces=…` and `LOAD_TIMING: … song_session_s=…`.
- Routing guards — `_require_text_surface()` refuses `/v1/completions` and
  `/v1/chat/completions` on a model that does not generate text, naming the surface
  it does generate and the endpoint to use. The guard is a routing decision: a text
  model's request handling is unchanged.
- Capability reporting — `song_generation` in
  `/v1/hipengine/capabilities` and in the `/v1/models` metadata, with the resolved
  checkpoints (`decoder_source: hugging_face_cache` when no `--vae-model` was given),
  and `surfaces` plus per-route booleans in the compact capability summary.
- `hipengine/server/__main__.py` — `--vae-model` (env `HIPENGINE_YUE2_VAE_DIR`),
  forwarded through `ServerConfig.vae_model` to `LLM(vae_model=…)`.
- Docs — `docs/API.md` gains the endpoint row and a "Song generation" section
  (fields, headers, busy/cancel behaviour); `docs/ENVS.md` documents
  `HIPENGINE_YUE2_VAE_DIR`; `docs/MODELS.md`, `README.md`, and the YuE2 model card
  now name the library and HTTP entry points instead of the session-only path.

## Validation

- `tests/test_unit_server_songs.py` (new, 24 tests) drives the app with a fake
  engine: the WAV body and headers, the JSON form, surface routing in both
  directions, field validation with its parameter name, the 429/499/500 mappings,
  and the advertised capability.
- `uv run pytest tests/test_unit_server_songs.py tests/test_unit_util_wav.py -q` →
  exit 0.
- Live, on this host (gfx1151), through the surface a user reaches — `hipengine
  serve --model m-a-p/YuE2-3B` with no `--vae-model`, so the decoder came from the
  HF cache:
  - startup: `surfaces=song`, pipeline built in 6.7 s, `/ready` 200, capabilities
    report both resolved checkpoints;
  - `POST /v1/audio/songs` with a real lyric (`cot="off"`, `steps=4`, short lyric) →
    200 `audio/wav`, 30,612,268 bytes, 3986 frames, 159.44 s of 48 kHz stereo, 409 s
    wall clock;
  - a concurrent second request → 429 `engine_busy` with `Retry-After`;
  - killing the client → 499 `cancelled` in the log within seconds, GPU back to 0%
    busy, and the next request accepted rather than refused as busy;
  - `/v1/chat/completions` on that server → 501 `unsupported_feature` naming the
    song surface and the endpoint to use.
- `python3 scripts/docs/check_all.py` → all 4 gates pass.

## Next

- The song route is outside the batched text path by design: one request at a time.
  Concurrent songs would need a pipeline pool, not a queue.
- `Retry-After` on a busy song is the server-wide `queue_retry_after_seconds`
  (1 s), which is a poor hint for a multi-minute pipeline. Changing it is a
  server-wide policy decision, not this unit's.
- No gfx1100 run: the endpoint is backend-agnostic, but the registered `hip_gfx1100`
  factory is still unexercised.
