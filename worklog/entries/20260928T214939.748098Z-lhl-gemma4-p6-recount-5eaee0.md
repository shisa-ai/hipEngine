# P6's launch count is right, its landing point is not

## Summary

Iteration 19 said to recount P6's launch figures before anyone writes code,
because the row's 412 → ~180 had never been checked against the tree. It is
now checked. The starting figure is correct; the destination is not.

## The recount

From `/tmp/gemma4-prefill-census-dual.json` (Gemma 4, W7900, 1024 tokens):

| family | calls | total_ms | mean_us |
| --- | ---: | ---: | ---: |
| `layer_total` | 60 | 2224.23 | 37070.6 |
| `attention_prefill` | 60 | 965.03 | 16083.9 |
| `dense:gguf_q8_0` | **410** | **615.91** | **1502.2** |
| `moe_wmma_dual:gguf_q4_k` | 58 | 304.52 | 5250.3 |

- **410 dense calls, not 412** — the row is accurate to two launches.
- **60 layers**, so **6.83 dense projections per layer**, i.e. the expected
  seven: `attn_q`, `attn_k`, `attn_v`, `attn_output`, `ffn_gate`, `ffn_up`,
  `ffn_down` (420 minus ten, the odd layer doing something slightly
  different).

## Where the arithmetic disagrees with the row

The two fusions this row describes save:

| fusion | before → after | saved per layer |
| --- | --- | ---: |
| q/k/v into one | 3 → 1 | 2 |
| dense gate/up into one | 2 → 1 | 1 |
| | | **3** |

3 per layer × 60 layers = **180 launches saved**, which lands at
**410 − 180 = 230**, not the row's ~180.

Reaching ~180 would need a third fusion, and neither remaining projection can
provide one:

- `ffn_down` takes a different input dimension (the MLP intermediate, not
  hidden), so it cannot share a weight or a launch with gate/up.
- `attn_output` reads the attention result rather than the layer input, so it
  is not in the same GEMM as q/k/v.

**The likely origin of the error:** 180 is exactly the number of launches the
fusions *save*. The row appears to have recorded the saving as the
destination.

## What the saving actually is

Fusing does not reduce work — every product still gets computed, and the
grouped GEMM runs the same FLOPs the three separate ones did. What it removes
is per-launch overhead and what it adds is fuller tiles on the narrower
projections. At `mean_us = 1502` per dense call these are not launch-bound
kernels, so the honest ceiling is the row's 5–15 ms, unchanged; only the
destination count moves.
