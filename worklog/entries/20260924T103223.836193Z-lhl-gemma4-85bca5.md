# Gemma 4 G3 decode-kernel benchmark evidence row

## Summary

Published the post-kernel measurement as benchmark evidence. The four-row
matrix was re-measured on the same day, host, GPU, artifact and frozen prompt
ids as the baseline and shipped as
`benchmarks/results/2026-09-24-gemma4-26b-a4b-decode-kernel.json`
(`performance_claim=true`, paired against the baseline artifact in
`measurements.baseline_reference`).

Measured (RX 7900 XTX, `--output 128 --samples 3`, medians of three, all rows
`public_path_parity=true`):

| prompt | decode tok/s (baseline) | delta | prefill tok/s |
| --- | --- | --- | --- |
| 128 | 33.96 (32.25) | +5.3% | 139.7 |
| 512 | 26.56 (22.02) | +20.6% | 134.7 |
| 1024 | 20.42 (16.09) | +26.9% | 127.8 |
| 4096 | 11.71 (10.14) | +15.5% | 108.1 |

First-token at 1024 is 8.01 s and public wall 14.25 s (baseline 8.00 /
15.88-15.92). Prefill is unchanged within noise, as expected for a decode-only
kernel change. Decode gain scales with live keys — attention's share of the
step — which is the shape story the profiling attribution predicted.

Two scope decisions, both recorded in the artifact rather than left implicit:

- **Boundary rows were not re-measured.** The decode kernel is bit-exact and
  routes on no new condition, so boundary correctness (token counts, context
  limits) carries from the baseline artifact; all four new rows keep exact
  public-path parity. Boundary *rates* are re-established in the campaign's
  integrated-confirmation phase. They were never headline numbers.
- **llama.cpp comparator rows were re-used, not re-run.** Same GPU, same GGUF,
  and the 1024-prompt id sha256 is byte-identical between artifacts
  (`9730ebf8...`), so the comparator remains a same-workload basis; only the
  hipEngine side moved.
