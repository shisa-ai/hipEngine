# DMS determinism compares unwritten slot bytes; Maple rmsnorm failure unlocalized

## Summary

The interrupted `final-all-suite` run recorded exactly ten failures: two
`test_gpu_hip_runtime.py` fake-runtime nodes (already repaired by
`bba6b52fa`), six MTP nodes (already explained as order-dependent VRAM
exhaustion by `483251fca`), and the two nodes this unit owns:

- `tests/test_gpu_kvcache_dms_device_hip.py::test_device_determinism_across_backends`
- `tests/test_gpu_maple_attention_kernels.py::test_maple_standard_rmsnorm_is_bf16_bit_exact`

The DMS failure is localized and repaired. The test compared the entire
per-layer K slot plane (`view.k_bits`) across two backend instances. The
planes are allocated lazily by `DMSDevicePayloadStore._ensure_layer` with an
uninitialized `hipMalloc`, and the pack kernel writes only live rows
`[base_offset, base_offset + live_count)`. The full-plane comparison therefore
compares unwritten allocation bytes, which no contract defines. In a long
process the two `hipMalloc` results carry different garbage and the assertion
fails while the live payload and attention are bit-identical.

The Maple failure is not localized. The rmsnorm node is deterministic for its
fixed seed 33 and did not reproduce under any bounded order, allocation, or
memory-pressure permutation tried here. A separate, real fragility was found:
the node's CPU oracle uses numpy pairwise summation while the kernel uses a
256-thread partial sum plus tree reduction, so the two disagree by one BF16
ulp for some inputs. That fragility does not explain the observed failure,
because seed 33 is stable across rebuilds and flag ablations, and is recorded
rather than "fixed".

## Changes

- `tests/test_gpu_kvcache_dms_device_hip.py`: added `_live_k_payload`, which
  returns the written K rows per head for one layer, and changed
  `test_device_determinism_across_backends` to compare that live payload
  exactly instead of the whole slot plane. Exact `np.testing.assert_array_equal`
  equality on live payload and on `compact_decode_attention` output is
  preserved; no tolerance was relaxed and no workload was skipped.
- Added `worklog/entries/` decision entry (this file). No production or kernel
  code changed. No change to `dms_device.py`, `dms.py`, or any Maple source:
  the DMS readback API returning the raw plane is correct, and the Maple kernel
  is deterministic.

## Next

- Maple `test_maple_standard_rmsnorm_is_bf16_bit_exact` remains an
  unlocalized intermittent failure. It is not reproducible in isolation or in
  any bounded order/allocation/global-state/memory-pressure permutation tried
  here, and the only failure signature observed in `final-all-suite.log` has no
  traceback because the run was interrupted. Re-examine if it recurs with a
  captured traceback; the next diagnostic step is a bounded prefix replay on a
  single GPU with `--tb=long` and a junitxml, which this unit's scope excludes.
- The rmsnorm oracle uses a different summation order than the kernel. Any
  change that makes that gate robust while preserving exact equality needs a
  reduction-order-matching oracle; a numpy emulation of the kernel's order did
  not reproduce the kernel's own seed-33 result, so that path was not taken.
