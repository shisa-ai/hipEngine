# Execute the MLP shard slice on two GPUs and validate it against an independent oracle

## Summary

TP2-A is done: `scripts/tp2_mlp_slice_e2e.py` materializes each rank's shard
payloads from the incumbent planner, uploads them to that rank's own device
(device 0 and device 1), runs the unfused chain the route resolves to today -
gate GEMV, up GEMV, `silu_mul_separate_out_bf16`, down GEMV - synchronizes, and
copies every intermediate back. On device 0 it also runs the TP1 teacher: the
fused `dense_dual_local32_bf16_bf16_out` pair+SiLU at its admitted shape plus the
full down GEMV. Both ranks' partials and their f32 sum are compared against an
independent host oracle computed from the dequantized GGUF weights.

## Changes

- `scripts/tp2_mlp_slice_e2e.py`: the executor. Host side: float64 truth chain
  (`down(silu(gate @ x) * (up @ x))`), a per-rank **contract emulation** that
  rounds each intermediate to bf16 exactly where the device chain writes bf16,
  and the f32 partial sum. Device side: per-rank `_ShardWeight` stand-ins
  carrying the planned `layout`/`quant_key` from the incumbent materialization
  plan (never a table here), current-device scoping around every allocation,
  copy and launch (a launch outside its rank's device scope fails with HIP
  status 400), one stream per rank, and the TP1 teacher through the resident
  weights.
- `tests/test_unit_scripts_tp2_mlp_slice_e2e.py`: host-only oracle tests (SiLU
  stability, bf16 round-to-nearest-even, the split contract reproducing the
  truth through the split, partial widths, uneven-FFN refusal, the relative
  error floor) plus the two-GPU end-to-end test, skip-guarded on two HIP
  devices and the artifact.

## Validation

```
uv run python3 scripts/tp2_mlp_slice_e2e.py --model /models/gguf/Qwen3.8-27B-Q4_K_M.gguf \
  --layer 0 --json benchmarks/results/2026-09-15-w7900-tp2-mlp-slice-e2e.json
uv run pytest tests/test_unit_scripts_tp2_mlp_slice_e2e.py
```

7 tests pass including the end-to-end run (5.6 s). Measured on this host, two
AMD Radeon Pro W7900 (gfx1100), Q4_K_M artifact, layer 0, seed 20260915:

| comparison | max abs | mean rel | max rel |
| --- | ---: | ---: | ---: |
| TP2 sum vs f64 truth | 2.1e-05 | 2.2e-03 | 1.2e-02 |
| TP2 sum vs bf16 contract sum | 7.6e-06 | 2.4e-05 | 7.6e-03 |
| TP2 sum vs TP1 teacher | 9.8e-04 | 1.3e-03 | 7.6e-03 |
| TP1 teacher vs f64 truth | 1.0e-03 | 2.3e-03 | 1.2e-02 |

Reading: the summed TP2 output sits inside the bf16 quantization envelope, and
it is as close to the truth as the unsharded TP1 teacher is - the slice loses
nothing numerically. The device partials land on the bf16 contract emulation
with max abs 7.6e-06, which is accumulation-order noise, so the *contract* the
device implements is exactly the one the oracle describes. Rank partials are
full-width (5120), so the reduction is a plain f32 sum over ranks.

This is a correctly executing, validated two-GPU TP=2 MLP slice. It is not yet a
measured speedup: no timing, and the exchange is still a host f32 sum rather
than the native transport.
