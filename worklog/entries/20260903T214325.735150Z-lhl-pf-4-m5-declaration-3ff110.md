## Mechanism mapping

Halo-box M5 (`binbcast.cu`):
- `weighted_expert_sum_rows_f32<10, 2560>`: one thread per (token, channel);
  serial i=0..9 `product = experts[t,i,c] * weights[t,i]` (mul rounded, then
  add — volatile product), F32 experts in, F32 out; staging pool + D2D copy.
- `shared_mul_add_f32` (mul+add+residual): **inactive** on the binding graph
  (HB-2 census).

hipEngine incumbent (`qwen4_exp_runner.py` grouped path, rows>1):
1. `weighted_lanes_sum_out_bf16_f32w` — one thread per (token, channel);
   serial k=0..9 `acc = fmaf(float(values[row*features+col]), weights[row],
   acc)` over the row's 10 lanes; **BF16 out**.
2. `shared_gate_combine_batch_out_bf16` —
   `out = float(routed) + sigmoid(gate_logit[t]) * float(shared)`; BF16 out.

Verdict on the "port": the incumbent already implements the M5 mechanism
shape (same thread mapping, same serial 10-step order) with three strict
advantages: fmaf single-rounding, direct store (no staging pool + D2D copy),
and **half the expert-output read traffic** (BF16 vs F32 experts). The M5
F32-in/F32-out boundary is additionally blocked cross-engine per HB-3 ("M5
lacks a common F32/BF16 boundary"). An M5-style candidate that changed fmaf →
mul+add would be a T1/T2 rounding change for zero mechanistic gain. **No M5
port candidate exists. Close the "port M5" sub-item as blocked/no-delta with
this entry as the record.**

M8 "fold where boundaries match": the active M8 symbols are internal graph
selections blocked per HB-2/HB-3; the quantize piece belongs to PF-1. Nothing
admissible folds from M8 into this lever.

## The admissible lever-2 candidate (T0)

Fuse steps 1+2 into one kernel:
`weighted_lanes_sum_shared_gate_combine_batch_out_bf16_f32w`
(new body in `fused/paro_combine.hip` + wrapper + registry; nothing existing
fits — `weighted_lanes_sum_shared_add_out_bf16_f32w` is registered but lacks
the gate and is unwired in any runner).

- **Arithmetic class: T0** — the fused kernel preserves the unfused rounding
  boundary exactly: `selected = bf16(acc)` (same fmaf accumulation order k=0..9),
  then `out = bf16(float(selected) + sigmoid(gate_logit[t]) * float(shared))`,
  identical to the unfused chain's memory round-trip of `routed` (BF16 write +
  read is exact). Same reductions, same order, same intermediates.
- **Strict fallback (named):** the existing unfused chain
  (`weighted_lanes_sum_out_bf16_f32w` + `shared_gate_combine_batch_out_bf16`)
  stays production and untouched.
- **Savings:** one launch + the routed BF16 round-trip
  (write 2·T·2560 + read 2·T·2560 bytes) per MoE layer per forward.
- **RED plan:** tests asserting the fused output is bit-identical to the
  unfused chain (fixture: production-faithful routed lanes, sorted weights,
  lane_to_row map, shared rows, per-token gate logits; shapes rows 1/16/64/512,
  hidden 2560, top_k 10), ImportError-first on the unmodified path, plus
  `rocprofv3 --kernel-trace` smoke and a kernel-level chain A/B at the gate
  shapes before any promotion; whole-model counterbalanced A/B only if the
  kernel-level A/B wins.
