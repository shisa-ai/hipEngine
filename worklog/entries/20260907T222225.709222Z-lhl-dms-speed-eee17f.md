# DMS INT8 beats dense too: wave-grouped GQA producer

## Summary

Continuation of the DMS speed campaign on W7900 GPU0 (loop
dms-int8-speed/run-20260907-220254, preceded by the BF16 loop). The INT8
codec's decode went 91.79 -> 38.03 ms/step at 16K context; the final
three-arm A/B (fresh process per arm, same manifest prompt slice):

| Arm | Prefill | Decode (median) |
| --- | --- | --- |
| dense BF16 | 631.7 tok/s | 45.55 ms/step |
| DMS BF16 | 626.5 tok/s | 37.92 ms/step (-16.7% vs dense) |
| DMS INT8 | 622.5 tok/s | 38.29 ms/step (-15.9% vs dense) |

Both DMS codecs now beat the dense route while keeping the capacity
advantage. Two INT8 changes:

- a524f307e: `dms_int8_append_kernel` rewritten from a serial per-token loop
  (two `__syncthreads` per live token, ~24k barriers per call at live 12K)
  to the BF16 family's chunked two-pass keep-scan (91.79 -> 61.30).
- d1737d8dc: `dms_int8_attn_split_wave_kernel` - the wave6 treatment ported
  to INT8. The old grid was one block per q-head (re-reading K/V 6x across
  the GQA group); the wave kernel runs one block per (kv-head, split) with
  shared-Q staging, 4-wide int8 loads and per-token scale dequant in
  registers, warp-shuffle reductions, same partials ABI (bf16 reducer
  unchanged), geometry-gated dispatch. Kernel 0.723 -> 0.077 ms at live
  8192 (9.4x); full model 61.30 -> 38.03.

Correctness: greedy tokens identical to the pre-campaign INT8 baseline at
every kept iteration (bitwise same eviction decisions and outputs); finite
logits; int8 device payload tests 5/5 (CPU-codec equality, overflow
tripwire). An intermediate bug in the append port (owning-thread copy loop
starting at `d = tid`, skipping elements) was caught by the CPU-codec test
before any measurement was recorded.
