# Narrow compact no-evict G0 mismatch to decode numerical parity

## Summary

The G0 failure is narrowed to decode-path numerical parity, not demonstrated
loss of the current token. The exact offending operation is not established;
no runtime or kernel repair is justified by the available evidence alone.

The pilot on zbook, hip_gfx1151, Qwen3.8-27B Q4_K_M, BF16 KV, four
1,024-token validation prompts and two dense-teacher-forced decode steps used
model SHA-256 `7e78da5d7e3ae28d178121f58646953305f3e5bd3cb46f4a75584e8b6c6fe169`.
Its provenance records commit `ad1e5ca9c84e3abc2abeb5092825a81bf6eed978` plus
scoped dirty changes. This is historical quality evidence, not a fresh run or
performance claim. The 11/12 agreement includes four prefill rows and eight
decode rows (not twelve decode rows plus four prefill rows).

## Changes

- Worklog only. No regression test or speculative repair; G0 and campaign
  thresholds unchanged. All pre-existing IQ and audit edits left untouched.
- Inspected the runtime decode callsite, compact device metadata and split
  producer/reducer. The runtime appends K/V before attention on the same stream.
  Append stores the supplied absolute position and publishes `keepers + 1` to
  the persistent device live-count buffer consumed by attention. Host metadata
  is finalized afterward and checked against device counts.
- For no-evict, positions should be 0..1024 at decode step 0 and 0..1025 at
  step 1. Dense publishes context = position + 1 as well. Every pilot digest
  reports actual compression 1.0, live/logical rows 65,664 = 16 * 4 * 1,026,
  and max live count 1,026. This rules against missing retained rows; aggregate
  digests are not direct proof of every device position or payload byte.
- `DMSDevicePayloadStore.attention_layer_device` uses split attention at
  capacity 1,026 (>256): five splits, with one/two live rows in the last split
  at steps 0/1. The kernel computes `count = min(256, live - begin)` clipped
  at zero, so the appended current token is inside the attended range.
- Dense is **also split** under the live default threshold of 1,024, correcting
  an initial verbal hypothesis of an unsplit dense route. Runtime selection
  chooses generic paged split/gate at this shape/context; the grouped 24Q/4KV
  dense policy starts at 4,096. Compact selects the group-6 wave producer when
  its architecture compile define is enabled (gfx1151), otherwise the generic
  grouped producer. Pilot JSON does not record compiled symbols or environment
  overrides, so this is source-derived selection, not a measured kernel trace.
- Compact wave scoring sums dimensions in four-component lane groups and
  shuffle reductions, followed by per-split exponentials, unnormalized P@V,
  and a separate global rescale/divide. These arithmetic trees are not an
  exact-parity contract with the generic dense path. Small attention differences
  can propagate through BF16 gates and subsequent layers; causality for the
  observed logit error still requires matched-input attention measurements.
- An additional inspection candidate is the compact reducer's shared-memory
  reuse: `global_m = reduction[0]` is followed by writes of `local_l` to the
  same array without a read-completion barrier. This warrants a focused
  synchronization check, but is not a proven explanation of the deterministic
  pilot and was not changed. Repeatability alone cannot exclude a race.
