# both attention paths are starved of blocks so the cheaper dot is the wrong lever

## Summary

The key-parallel flash port attacks the dot product, and the dot product is not
the bottleneck. **The port should be dropped**, and the previous entry's proposed
microbenchmark would have measured the wrong quantity.

Two pieces of evidence already in the tree say so, and neither is new work -- I
found them by reading the kernel and the probe that already exist.

## Evidence 1: the prefill kernel says its cost is invariant to the dot

`gemma4_attention.hip`'s warp-per-key path carries this comment in the source:

> Doing that per key costs eight `__syncthreads` rounds per key, which is the whole
> cost of this kernel (**measured 147 GFLOP/s and ~5.3 us per key at 512 tokens,
> invariant to the work inside the key iteration**).

"Invariant to the work inside the key iteration" is the decisive phrase. The
warp-per-key path is *already implemented and selected* for `head_dim` 256 and
512 at `blockDim.x == 256`. It already removed the block-tree barriers, and the
resulting kernel does not care how expensive the per-key dot is. Making the dot
cheaper cannot help a kernel whose time is independent of the dot.

My previous entry (`20260928T064926`) counted **issue slots** -- a throughput model
-- and concluded the port was 0.81x to 1.30x. That model does not describe this
kernel. The port may well be *faster per key* in isolation and still move nothing
end to end.

## Evidence 2: the decode path is parallelism-starved, and the probe says so

`scripts/gemma4_attention_scale_probe.py` documents its own measurement:

> a single-request decode step launches **16 blocks of 512 threads on a 96-CU GPU**
> ... At 16 blocks the kernel is moving 16 MB per launch in 280 us, about **57 GB/s
> of a ~960 GB/s peak**.

and `us/head` falls **6.9x** from 16 to 64 blocks. That is a 6.9x available
speedup, and the probe names the fix: "split-K over the key range, **which keeps
total traffic constant** instead of growing it the way this probe does".

So both attention paths are limited by **how many blocks are in flight**, not by
arithmetic. A cheaper dot leaves the block count where it is.

## The discrepancy worth checking next

`decode_slices` in `gemma4_attention.py` returns 1 below 1024 keys and 4 at or
above it for `head_dim <= 256`, and its docstring says the split "partitions
output dimensions, **not keys**, and preserves ascending-key accumulation. The
exact value above one no longer controls its grid."

That is not the shape the scale probe recommended. Splitting **output dimensions**
keeps the grid at `tokens * num_heads` -- the same 16 blocks -- and so does not add
the parallelism the probe identified as the limiter; splitting **keys** is what
adds blocks while holding traffic constant. The docstring may be describing a
superseded design, and the split path is only reached at `keys >= 1024`, so the
single-request decode geometry the probe measured may not take it at all.

**This is a discrepancy between two documents in the tree, not a measured defect.**
Resolving it needs one measurement: run the decode kernel at the probe's geometry
with `decode_selection()` read back, and check whether the launched grid grows with
`slices`. If it does not, the split is not the fix the probe asked for and the
block-count lever is still open.

## Changes

No code. The entry records two findings from existing sources and one discrepancy,
and withdraws the previous entry's proposed next step.

## Validation

No code and no benchmark, so no test result applies. Evidence 1 is a measured claim
quoted from `hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention.hip`; evidence 2
is a measured claim quoted from `scripts/gemma4_attention_scale_probe.py`'s module
docstring, dated 2026-09-25 on gfx1100. Neither measurement is mine and neither is
re-run here; both are cited with their source so they can be checked.

## Next

1. **Drop the key-parallel port.** Its premise is that the dot is the bottleneck,
   and both attention paths measure as block-starved instead.
2. Resolve the split discrepancy above: read `decode_selection()` back at the
   probe's geometry and check whether the grid grows with `slices`.
3. If the grid does not grow, the lever is a genuine key-range split, which the
   probe already predicts is worth up to 6.9x on the decode attention share.
4. The three port constraints remain recorded and remain true
   (`20260928T091438`, `20260928T094719`, `20260928T100244`); they are simply not
   on the critical path any more.
