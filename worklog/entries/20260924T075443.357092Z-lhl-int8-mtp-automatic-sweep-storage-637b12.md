# The automatic c2 sweep runs the default storage, not INT8

## Summary

The readiness row "Automatic intent at physical c2 on INT8 KV" named
`scripts/gguf_mtp_c1c8_server_bench.py --mtp-request-mode automatic` as its
verification and attributed the withholding to an INT8 static width bound. The
width half was real and is fixed (`7c3914162`), but the command does not reach
INT8, so it cannot clear the row and its cause attribution was wrong.

What the live route decision actually says at a realized width of 2, read from
the response's own `generation_shape.route_decision` on a server built exactly
the way that script builds one:

```
requested_route: speculative_mtp_auto
selected_route:  default
reason:          automatic_mtp_scope_not_promoted
realized_group_rows: 2
static_intent_allowed: false
policy_cell:     qwen38-q4km-gfx1151-production-bf16-c2-k3-d24
static_eligibility.reason:      diagnostic_production_c2_after_ar_rebase
static_eligibility.automatic_eligible: false
```

The gate is a retained **BF16** evidence row that is explicit-only by promotion
decision, not an INT8 static bound. That is consistent with the row's own
quoted numbers: the explicit arm's c2 rate (25.75 tok/s against AR 10.79) is the
same cell, admitted because an explicit request may use an explicit-only row.

Why the command cannot reach INT8: the script constructs `LLM` and
`ServerConfig` without a KV storage selector, and `git log -S kv_storage --
scripts/gguf_mtp_c1c8_server_bench.py` is empty -- it has never contained one.
`ServerConfig.kv_storage` defaults to `"auto"`, and `/ready` reports
`effective_kv_storage: bf16` for that construction. Passing
`kv_storage="int8_per_token_head"` to both objects still reported `bf16`, so the
INT8 cell for this artifact is reached through the CLI route the other INT8
gates use (`hipengine serve --kv-storage int8_per_token_head`), which is what
they assert against `/ready`.

Consequence worth stating plainly: every artifact that script has produced
under an `int8kv` name is a BF16 run. The artifacts are not edited here; the
readiness row now says so where it cited one.

## Changes

- `docs/reference/INT8-MTP-SERVER-READINESS.md`: the row stays open with the

  the automatic sweep run, renamed to say which storage it used. Commit
  `86de3308`, clean tree, 325 s, `status: failed`,
  `failure_reasons: ["w2: route expectation engaged=0/10 mtp_expected=True"]`,
  c1 and c4 engaged 10/10 with `ar_mtp_equal: true`.

## Validation

- The decision above was read live, not inferred: `/tmp/probe_live_route.py`
  (scratch) rebuilds the bench's own construction and prints the full
  `generation_shape.route_decision` the response carries, which the bench's
  `_response_mtp` reduces to a route string and a nine-key summary. Two
  concurrent requests through one shared `TestClient` produce the width-2 group;
  a per-thread client does not batch at all, which is why the first version of
  the probe showed singletons.
- Offline, the same plan payload admits: feeding the model plugin's own rows=2
  automatic plan to `_serving_plan_route_decision(requested_route=AUTO,
  group_rows=2)` returns `route=speculative_mtp`. So the withholding is in the
  plan the live path resolves (BF16 evidence), not in the api layer's handling
  of an INT8 plan.
- `tests/test_unit_int8_mtp_serving.py` -- 36 passed, pinning the widened INT8
  width bound that `7c3914162` introduced.
- The sweep itself now completes: the pool-close fix in `86de33082` is what let
  it write an artifact at all. Before that fix the same command ran every cell
  and then failed shutdown with
  `RuntimeError: cannot close global device KV pool with private workspace`.
