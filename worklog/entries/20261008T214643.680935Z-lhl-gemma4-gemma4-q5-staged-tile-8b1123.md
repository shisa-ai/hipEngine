# Retract the instrument-sensitivity thesis: the 1000x shift was my Q5_1 prefill overrun

## Summary

`ff7569f41` ("perf: widen Gemma Q5 staged prefill tile") changed a template
instantiation from `<4, 4, 256>` to `<4, 8, 256>` while the launcher's
`out_tile` stayed `constexpr 4` -- and `out_tile` is what sizes both the staged
shared bytes (`staged_bytes = out_tile * ((in_features + 255) / 256) * 8 * 12`)
and the grid (`(out_features + out_tile - 1) / out_tile`). The kernel therefore
staged eight columns of weights into a four-column buffer and wrote eight output
columns per block while the grid covered half of them, so the Q5_1 expert down
projection overran shared memory and returned wrong prefill values. The registry
key said `..._prefill_staged_out4_bf16_bf16_out` the whole time. Fixed in
`ebe2cc48b`, which sizes the template from the launcher's own `out_tile`.

**This retracts my instrument-sensitivity thesis.** The following committed
claims were measured on that defective tree and are withdrawn:

The measured mechanism in the retracted entry -- a ~7e-7 f32 difference against a
3.9e-3 bf16 ULP, giving 1-ULP flips -- is a real, still-measured phenomenon of
reassociating kernels. It was simply not what moved these numbers: the
divergence was 5e-3 with *zero* arithmetic change in the decode route, because
the prefill was corrupt.

**What survives, because it is kernel-level and never touched the model:**

- The flash decode kernel is bit-identical between `abf639894` and HEAD across
  24/24 cases, with f32 agreement 4.7e-7 .. 9.1e-7 (`01855f231`,
  `benchmarks/results/2026-10-08-gemma4-flash-kernel-deviation.json`). Those runs
  drive the raw ABI on synthetic buffers, so the prefill defect cannot enter them.
- The f32 battery bound tightened from 1e-4 to 1e-5 with measured margins, the
  flat-in-slice-count finding, and the corrected flip rate (`4433e0c3a`).
- The decode ABI and admission findings (`a931c6a07`): decode takes `keep_mask`,
  `flash_admits` is shape-only.
- The V-pipeline lookahead defect I introduced in `37ba3b3da` and fixed in
  `b9e0f3f0d`, and its provenance correction (`9e58e6bbb`).

## How the escape happened

Four failures, in the order they mattered:

1. **I asserted the sizing was fine instead of computing it.** The unit's entry
   said "the existing dynamic shared-memory allocation already covered the
   eight-column tile". `staged_bytes` is a literal function of `out_tile`; one
   line of arithmetic refutes it. A template argument that the launcher sizes
   against is a contract, and I changed one side of it.
2. **I validated a prefill kernel with a decode measurement.** The recorded
   evidence was a 64K *decode* tok/s delta (+0.2%), which is noise for a prefill
   kernel. The smoke that did exercise prefill checked "path parity" and finite
   output -- that the intended route ran, not that its values were right.
3. **Six red unit tests were dismissed as "pre-existing, unowned".** They were in
   the default tier, named the exact kernel family I had just changed
   (`test_unit_gemma4_expert_route.py` Q5_1 grouped prefill), and compared that
   kernel's arithmetic against a dequantized reference.
4. **The pre-existence check ran the wrong way.** I recorded that the failures
   "reproduce unchanged at `308c4c38c`" -- a *descendant* of the defect, so the
   check could only ever confirm it. The parent is `5e0a50b8c`, and the bisect
   confirms it reads mean KL 1.82e-4 / 0 flips against the 2026-09-30 reference
   where `ff7569f41` reads 1.72e-1 / 29 flips.

`docs/TESTING.md` now carries the rule that failure 4 needed: reproduce a
suspected pre-existing failure at an ancestor, never a descendant, and treat a
failure naming the family you touched as a finding about your change.
