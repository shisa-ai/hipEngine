# Qwen4Exp AR batch width4 focused task review: code/migration pass, two cases inconclusive at 1024

## Summary

Ran a focused, longer free-output review of the four deterministic width-4
batch-vs-strict divergences from the passed 450-row numerical gate. The review
used the original fixture-order groups and companions, two runs per route, and a
bounded progression of 256, 512, 768, and 1024 tokens. The 1024-token outputs
are the reviewed evidence.

The batch route has **no semantic failure** in these four cases. The code and
Japanese migration cases are EOS-complete on both routes and pass. The English
memory-bandwidth explanation and the Japanese speculative-decoding explanation
cover every required checklist item on both routes, but both routes exhausted
the 1024-token budget before EOS, so their completion is **inconclusive** under
the stated rule rather than an automatic pass or fail. The calibrated numerical
gate remains `requires_task_review`; admission remains `eligible=true,
admitted=false`. No promotion or default claim is made.

Case verdicts at 1024:

- **`code_topological_sort`: pass (both routes).** Strict EOS 766, batch EOS
  781. Both emitted a single fenced Python code block with `topo_sort(nodes,
  edges)`, a cycle `ValueError`, and DAG/cycle tests. The generated code was
  extracted and executed in a 10-second isolated subprocess with a temporary
  cwd, no network setup, and CPU/address-space limits. Strict: direct rc 0,
  pytest rc 0, 4 tests passed. Batch: direct rc 0, pytest rc 0, 5 tests passed.
  The code text differs (strict uses `deque` and unknown-node validation; batch
  uses `defaultdict` and a local import), but both satisfy the contract.
- **`heldout_general_ja_migration`: pass (both routes).** Strict EOS 769, batch
  EOS 609. Both are Japanese plans covering the async job design, compatibility
  (old endpoint retained, versioned new endpoint, polling/webhook, schema/SDK,
  idempotency), monitoring (queue depth, latency, failure rate, alerts,
  tracing/logging), and explicit rollback conditions and procedure. Strict is
  more detailed; batch is more concise.
- **`general_en_explain`: inconclusive, both truncated.** Both cover the
  memory-bandwidth thesis, autoregressive decode/KV-cache mechanism, a concrete
  7B/RTX-4090 example, and throughput-change examples (quantization,
  batching/arithmetic intensity, FlashAttention/PagedAttention). Both exhausted
  1024 tokens without EOS inside the final PagedAttention example. All required
  content is present; completion is not certified. This is not a semantic
  failure.
- **`heldout_general_ja_speculative`: inconclusive, both truncated.** Both cover
  acceptance rate, verification cost, and memory usage (draft-model memory,
  KV-cache management/rollback, bandwidth, batch-size limits), and tie them to
  when draft+verify exceeds sequential decode. Both exhausted 1024 tokens
  without EOS inside the conclusion. All required sections are present;
  completion is not certified. This is not a semantic failure.
