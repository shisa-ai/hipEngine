# Implement cap4 realized-singleton automatic MTP

## Summary

Implemented the active prerequisite for the separately designed dynamic
admission campaign: the normal four-slot Qwen3.8 Q4_K_M strict owner can now
run automatic MTP only while its realized due group is a singleton. A second
live speculative child makes adapter capability disappear before proposal, so
both rows execute transitional K0/AR with exact provider catch-up. When one row
retires or cancels, the survivor can resume C1 MTP at the next transaction
boundary.

The implementation is intentionally narrower than physical C2. It adds one
fingerprinted resident-capacity-4/realized-C1 automatic evidence row and a
`singleton_only` request intent propagated through existing API, Generation-2,
and GGUF plugin boundaries. Explicit physical C2/C4 diagnostics are unchanged.

## Changes

- Added a generic automatic singleton-only sampling/request control bit from
  server realized-route selection through `SamplingParams`, `GenerationRequest`,
  `ResidentEngineLoop`, and the registered GGUF adapter.
- Added private one-slot NextN provider/verifier activation for an automatic
  singleton under a wider resident owner.
- Bound the transactional journal to `target.scratch` slot views instead of
  owner-wide state buffers; no state arithmetic changed.
- Made singleton-only capability and claims fail closed whenever a peer enters
  the due work item. Existing K0 catch-up keeps provider state synchronized and
  permits survivor re-entry after the group shrinks.
- Added RED/GREEN capability, routing-tag, private-provider, neighbor-K0, and
  wide-owner slot-journal tests. PARO accepts and ignores the generic control so
  its capacity-1 route is unchanged.
- Added provisional compact artifact
  `benchmarks/results/2026-08-27-gfx1151-qwen38-realized-singleton-auto.json`;
  final retained publication waits for a clean-source rerun of this commit.
