# Wire the device sampled accept into the N2 target graph

## Summary

A sampled MTP row can now keep the target graph: the N2 accept/commit graph has a
captured sampled variant that decides the drafted chain with the coupled
acceptance from the resident verifier's own device logits, and the caller stages
the row's temperature and the draws from the row's sampler stream per replay.
The serving arm could not be evaluated this unit because MTP does not attach a
provider in this tree for the ShareGPT protocol at all, greedy included; that is
a separate defect recorded below, and the sampled-mode evidence guard stays
closed.

## Changes

- `hipengine/kernels/hip_gfx1100/speculative/sampled_accept.hip` — the chain
  kernel now consumes a caller-supplied draw block (`rows + 1` uniforms per
  request, walk order: one per acceptance test, then one for the residual or
  bonus sample) instead of generating its own counter-based uniforms. That is
  what keeps the row's stream aligned with the autoregressive route: the draws
  are the row's own, not a second stream.
- `hipengine/runtime/gguf_native_spec_cycle.py` — `sampled_accept` capture
  variant: graph-owned `sampled_temperatures` (rows) and `sampled_draws`
  (rows + 1) tensors, a row-stats launch plus the sampled chain launch in place
  of the argmax accept kernel, and the flag in the configuration key,
  `compatible_with`, and `launch_ineligibility_reason` so the two variants
  cannot be confused. `launch(..., sampled_accept_state=(temperature, draws))`
  stages the per-replay values.
- `hipengine/runtime/qwen35_gguf_runner.py` — `sampled_accept` through
  `capture_native_spec_target_graph`, `prepare_native_spec_target_graph` (its
  own `_native_spec_b<n>_target_graph_n2_sampled` cache slot), and
  `verify_target_from_device_proposal`.
- `hipengine/runtime/qwen35_gguf_mtp.py` — `prepare(..., sampled_accept=...)`
  passes the state to the device-proposal route.
- `hipengine/generation/qwen35_gguf_mtp2.py` — `_DeviceSampledAcceptPlan` stages
  `rows + 1` draws from the row's host sampler stream after snapshotting the RNG
  state, and `settle(accepted)` rewinds and re-advances by exactly the draws the
  device consumed. `_device_sampled_accept_plan` admits the device path only for
  a host-sampled row whose parameters need no logits processors, whose prompt
  constraints are inactive, and whose sampled graph is already warmed; the
  warmup captures that graph after the first token. A sampled row whose plan
  exists takes the device proposal again, passes `sampled_accept`, and skips the
  host `_sampled_accept_summary` recomputation.
- `tests/test_gpu_sampled_accept_chain.py` — the three decision/law tests now
  feed explicit draw blocks to both the device walk and the host oracle.

## Blocked: the serving arm could not be measured

The ShareGPT protocol from the rejected artifact
(`benchmarks/results/2026-09-18-gfx1151-qwen38-mtp-sampled-acceptance-serving-rejected.json`)
was re-run against this tree with the same server command line, the same
harness flags (`--num-prompts 4 --min-prompt-len 64 --max-prompt-len 900
--max-total-len 2048 --output-len 128 --record-ids --seed 4242 --temperature 0.7
--route-mix off,off,on,on`), and the temporary qualification switch (the cap4 c1
evidence row's `sampling_modes` gaining `"sampled"`, reverted in this unit as the
artifact documents).

Result: **no MTP at all.** `mtp_requests=0`, `mtp_output_share=0.0%`,
`speculation coverage: never_entered=4`, and
`refusal cost: events=254 by_reason={"no_provider": 254}` over 256
autoregressive tokens. A control run of the same harness at `--temperature 0.0`
(greedy, which does not touch any sampled-route code) fails identically:
`non-MTP reasons: {"no_provider": 1}`, `never_entered=1`, 62 no_provider events
over 64 AR tokens.

Two facts bound the diagnosis:

- a greedy row's path through this unit's diff is a no-op: the sampled plan is
  consulted only when the sampled route is selected, the warmup's sampled
  capture only for a sampled row, and every graph change is inert while
  `sampled_accept` is false;
- the qualification switch only flips the capability's
  `supported_sampling_modes` (`("greedy", "sampled") if
  sampled_route_qualified else ("greedy",)`), so it cannot affect greedy
  admission.

So MTP currently fails to attach a provider for this protocol independently of
sampling mode and independently of this unit. The earlier in-session MTP runs
that did engage used the `mtp-bench` / prompt-suite harnesses rather than
`sharegpt_mtp_routing_pass.py`, so either the tree regressed in the intervening
commits or this harness's admission path differs; that has to be settled before
the sampled arm can be compared with an in-load AR control.

No evidence row was written, and
`tests/test_unit_speculative_sampling_modes.py::test_no_shipped_evidence_row_advertises_the_sampled_mode`
is still green (verified in the 62-test run above).
