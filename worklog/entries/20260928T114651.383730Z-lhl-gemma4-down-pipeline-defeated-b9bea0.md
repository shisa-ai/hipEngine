# the compiler rewrites a software-pipelined row loop back into load-wait-use, and total issue is 41 percent occupied

## Summary

The previous entry ended with a specific, falsifiable plan: give the row loop two
activation register sets so iteration `r+1`'s scalar load issues before iteration
`r`'s dp4a consume the first set. It was written, twice, and both times the
compiler rewrote it back into `load -> s_waitcnt lgkmcnt(0) -> use`.

| arm | ms/call (three runs) | median |
| --- | --- | ---: |
| baseline | 2.479 / 2.525 / 2.484 | 2.484 |
| pipeline, load-next-then-consume | 2.813 / 2.701 / 2.575 | 2.701 |
| pipeline, consume-then-load-next | 2.755 / 2.571 / 2.543 | 2.571 |

Both are slower, and the disassembly says why. In the second version -- the
ordering that should work, because the load is issued *after* every consumer so
the next iteration's wait has nothing new to cover -- the loop is 84
instructions with the load at offset 43 and the wait at 49:

```
  43  s_load_b256 s[60:67], s[40:41], 0x20
  44  s_load_b64  s[40:41], s[40:41], 0x0
  49  s_waitcnt lgkmcnt(0)
  50  v_dot4_i32_iu8 v63, v35, s60, 0 neg_lo:[1,1,0]
  ...
  75  v_dot4_i32_iu8 v63, v61, s67, v63 neg_lo:[1,1,0]
```

The dp4a at 50-75 consume `s60` through `s67` -- the registers written at 43-44.
The compiler coalesced the loop-carried `xa = na` copy into a single register
set and sank the load to sit immediately before its use, which is precisely the
schedule the change was meant to avoid. It is optimizing register pressure, and
it wins: the pipeline is not reachable by reordering source statements.

**Why the wait cannot be worked around from source.** The promotion to scalar
loads is the right encoding (see the previous entry), but it puts the result in
a fixed set of SGPRs, and the wait the compiler emits is `lgkmcnt(0)` -- wait for
*every* outstanding scalar load. A prefetch issued before the wait is therefore
waited on by it, and the prefetch's whole latency lands back on the critical
path. Making this work needs a counted wait (`lgkmcnt(1)`), which the source
cannot express.

**A better accounting of what the kernel is doing.** The previous entry compared
the measured `SQ_INSTS_VALU` against the VALU issue peak and got 17.7 percent.
That understates the kernel, because VALU is only part of what it issues. The
row loop body is 59 instructions and 16 of them are `v_dot4`, so 221.4 M measured
VALU corresponds to roughly:

```
row loop, 59 instructions x 22 blocks x 128 threads x 32 rows x 22 subs / 32
                                                      = 467.9 M wave-instr/call
at 464 G wave-instr/s                                  =   1.008 ms
measured                                               =   2.484 ms
issue occupancy                                        =    40.6 %
VALU share of the row loop's instructions              =    47.3 %
```

**So the kernel is at 41 percent of issue peak, not 18 percent** -- the gap is
stall cycles, not an unused pipeline. That also reconciles the dp4a probe: it
removed 28.7 percent of VALU but only 13.6 percent of total instructions, and
bought 2.3 percent, a sensitivity of about 0.17x. Instruction count is a real
lever, but a weak one, and it is not the exposed resource.

## Next

The load-latency lever is closed at the source level, so the remaining routes to
it are structural rather than schedulers:

1. **More warps per SIMD.** The stall is only visible because 5 blocks per CU
   leaves 5 warps per SIMD with nothing to cover a scalar-load wait, and the
   block's warps all read the same uniform address so they stall together. The
   kernel is register-limited to 5 blocks at 96 VGPRs, and `acc[ROWS_PER_PASS]`
   is 32 of them. This is the one lever that attacks the stall without needing
   the compiler to cooperate -- but `ROWS_PER_PASS` 16 was already measured
   slower in production, so the experiment has to separate occupancy from the
   doubled weight fetch it also causes.
2. **Give the activation a residency the weight stream cannot evict.** The
   activation is 3.5 MB and the weight stream is 190 MB per call; if the scalar
   load is missing L1 rather than hitting it, the latency being hidden is L2's,
   not L1's, and the fix is a cache hint or a smaller working set rather than a
   schedule.
