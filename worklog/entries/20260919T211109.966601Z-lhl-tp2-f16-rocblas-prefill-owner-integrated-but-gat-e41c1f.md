# tp2 f16 rocblas prefill owner integrated but gate-blocked

## Summary

The source-F16 rocBLAS prefill owner is now integrated into the TP2 route with
rank-owned scratch and handles, and it is **kept default-off because it fails the
production numerical gate.** It is a real **+3.97%** on the 512-token prefill
(490.0 -> 471.3 ms, four paired same-session deltas all the same sign), but it
moves the heldout prompt the wrong way: mean_kl 0.06998 -> 0.09288, max_kl
3.7705 -> 4.2241, top-1 0.9375 -> 0.921875. Both arms fail the gate, so this is
not a regression against a passing baseline - it is a candidate that does not
repair one, and promoting it on speed alone would be exactly the premature
"bottleneck solved" this campaign keeps having to retract.

## Changes

- `hipengine/runtime/qwen35_gguf_runner.py`
  - `build_t16_f16_rocblas_prefill_owner(runner, scratch, ...)` - the owner
    construction extracted to module level so a TP2 rank can build an owner over
    its own planes and its own rocBLAS handle without standing up a resident
    session per rank. Returns `(owner, library, rocblas)` so handles are cacheable.
  - `allocate_t16_f16_rocblas_prefill_planes(runner, *, rows)` - allocates only
    `q6_f16_x`/`q6_f16_weight`/`q6_f16_out`. **48 MiB/rank** at rows=512 against
    **461 MiB/rank** for a whole resident session (118 MiB of it scratch).
  - `_q6_f16_rocblas_prefill_context` delegates to the builder and accepts a
    `scratch=` override.
- `hipengine/distributed/tp2_generate.py`
  - per-rank planes, library, handle and readiness state; the owner context is
    entered inside the per-device loop around that rank's attention work;
    released in `close()`.
  - `use_t16_f16_rocblas_prefill` defaults **False**, with the gate numbers in
    the comment.
- `scripts/tp2_bulk_prefill_diagnostic.py` - `--t16-f16-rocblas-prefill` and
  `--pad-prompt-tokens`.
- `tests/test_unit_tp2_t16_f16_rocblas_prefill_owner.py` (new).

## Two silent bugs found while integrating

1. **Planes cached on device alone.** The owner's admission filter compares
   against `planes.rows`, so caching without a row check makes the first pass's
   row count permanent: a session warmed at 64 rows keeps the exact T16 owner for
   every later 512-row pass. Nothing raises; the optimization just stops
   happening. Fixed by re-allocating (and releasing the superseded planes) when
   `rows` grows.
2. **The gate never ran the owner.** The suite's prompts are 52-64 tokens and the
   policy's smallest admitted row count is **512**, so the flag-on and flag-off
   runs returned **bit-identical logits** (`logits_sha256` matched exactly). That
   was briefly read as "the owner is numerically safe"; it meant "the owner did
   not run". `--pad-prompt-tokens` exists so the gate can reach an admitted row
   count.

## Validation

Perf, one session, A/B/B/A counterbalanced, both arms warmed, `logits_rows=1`,
512 tokens, W7900 + RX 7900 XTX:

| arm | samples (ms) | median |
| --- | --- | --- |
| owner off | 489.6, 490.1, 490.0, 490.9 | 490.0 |
| owner on | 471.1, 469.1, 471.5, 472.4 | 471.3 |

`+3.97%` throughput; paired deltas +3.92/+4.48/+3.91/+3.90.

Gate, `--pad-prompt-tokens 512 --max-sequence-length 640`:

| metric | off | on |
| --- | ---: | ---: |
| translate mean_kl | 0.03659 | 0.03331 |
| translate max_kl | 2.0210 | 1.7743 |
| translate top-1 | 0.96875 | 0.96875 |
| heldout mean_kl | 0.06998 | **0.09288** |
| heldout max_kl | 3.7705 | **4.2241** |
| heldout top-1 | 0.9375 | **0.921875** |
| heldout flipped rows | 8 | 10 |
| `all_passed` | false | false |

- `pytest tests/test_unit_tp2_t16_f16_rocblas_prefill_owner.py` -> **5 passed**.
- Default-path check: a session built without the flag reports
  `use_t16_f16_rocblas_prefill == False`.
- Owner admission by row count (fresh planes each time): 52/64/200 -> falls back;
  512/1024 -> owner built.

## Blocker

The owner needs the route's **numerical** blocker to clear first, then must
re-pass against whatever fixes it. It is not blocked on more speed work. Both
gate arms fail, so the route itself is the open problem: at 512 rows the exact
T16 baseline already shows mean_kl 0.03659 and max_kl 2.021 on the translate
prompt, far outside the envelope.

## Next

- Localize the 512-row route failure. The owner is a useful instrument here: it
  is a second, independent arithmetic path whose logits differ, so a
  layer-by-layer capture with and without it separates "wrong arithmetic" from
  "wrong state".
- Do not add the +3.97% to any plan total; it is not landable as-is.
