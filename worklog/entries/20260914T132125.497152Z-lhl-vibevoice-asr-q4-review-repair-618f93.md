# VibeVoice Q4 review repair: WER unit corrected (1.978% not 0.020%); ownership, isolation, memory and manifest fixed

## Summary

An external review of the VibeVoice-ASR Q4_K_M workstream found nine defects.
All nine are confirmed by direct inspection or recomputation and all nine are
now fixed, with regression tests. The most consequential is an evidence error:
`_wer` returns jiwer's **fraction** in [0, 1], but every print site and every
artifact field formatted it with a `%` sign, understating all reported WER by
100x. Corrected values on the frozen 50-clip / 23-speaker subset:

| Lane | Reported before | Correct |
| --- | ---: | ---: |
| hipEngine bf16 | 0.020% | **1.978%** |
| hipEngine Q4_K_M | 0.020% | **1.978%** |
| torch GPU bf16 | 0.046% | **4.586%** |

The Q4-equals-bf16 result and the hip-better-than-torch ordering are unchanged;
only the scale was wrong. The Q4 acceptance bound was also stated as "+0.2
absolute" while quoting fractions, which made it trivially true; it is
restated as +0.2 percentage points absolute (observed delta 0.000).

The WER rows were never rolled into `benchmarks/README.md` or
`benchmarks/CHANGELOG.md`, so the correction is confined to the three committed
artifacts under `benchmarks/results/` (rewritten in place with
`*_wer_fraction` + `*_wer_pct` and a `corrections` note) and to the worklog
entries that quote "0.02%"/"0.05%" — those entries are immutable, so this entry
is their correction record:

- `20260914T110013.315941Z-…-q4-runner-24536e.md` (line 59)

## Changes

Evidence and harness integrity:

- `scripts/vibevoice_asr_wer.py`: `_wer` documents that it returns a fraction;
  new `_wer_pct` is the only percentage form; prints and artifact fields use it.
  `parse_transcript` replaces the silent `except: pass` fallback — malformed
  structured output is reported as `no_json`/`bad_json` and `_transcription_only`
  raises on it by default, so a schema failure can no longer be scored as an
  ordinary word error. `--systems` is now `choices=["torch", "hip"]`; previously
  `bench_torch_gpu if system == "torch" else bench_hipengine` silently ran the
  bf16 hip lane under any other label.
- `scripts/vibevoice_asr_wer_q4.py`: percentage unit fixed, malformed
  transcripts reported, and the artifact now records the GGUF sha256 plus the
  per-clip request hashes it verified.
- `scripts/vibevoice_asr_to_gguf.py`: `iter_tensors` converted bf16 **bit
  patterns** with `astype(np.float16)`, reinterpreting the integer as a value
  (0x3F80 -> 16256.0) instead of converting the number; every `--dtype f16`
  export was garbage. It now converts numerically and yields the target
  encoding, and the writer no longer re-converts. The shipped Q4 path used
  `--dtype bf16`, so no retained artifact is affected.
- `scripts/vibevoice_asr_gguf_merge.py`: new `validate_inputs` rejects
  architecture mismatch, overlapping tensor names, non-BF16 encoder tensors, and
  an incomplete backbone (missing globals or any per-layer GEMM), and prints
  input sha256 prefixes. Previously a dropped tensor produced a silently
  incomplete model.

Runtime correctness:

- `hipengine/kernels/hip_gfx1100/vibevoice/q4.py`: the module-global
  `_F32_SCRATCH` (keyed only by output width) is gone. The emulated dual
  gate/up GEMV now takes caller-owned `scratch=(gate, up)` and falls back to
  per-call buffers; a process-global cache let interleaved requests on separate
  runners overwrite each other's intermediates and was never released.
- `hipengine/runtime/vibevoice_qwen2_q4.py` + `hipengine/loading/vibevoice_asr_gguf.py`:
  ownership is now exact. `Qwen2Q4Weights` owns its device buffers and has an
  idempotent `close()` (which also drops the `GGUF_WEIGHT_TYPES` entries);
  runtimes borrow them instead of `keep()`ing them into their own free lists.
  Previously two runtimes over one weights object double-freed the same
  pointers — the second `close()` raised `HIP error 1: invalid argument`.
- `hipengine/loading/vibevoice_asr_gguf.py`: `malloc(host_f32.nbytes * 2)`
  allocated 8 bytes per element for bf16 buffers that need 2, wasting ~6.5 GB on
  the embedding and lm_head. Now `host.size * 2`. Measured loader footprint
  12.6 GB -> **6.103 GB** (339 buffers), with embed and lm_head exactly
  `vocab_size * hidden_size * 2`.
- `hipengine/runtime/vibevoice_qwen2.py`: `quant='bf16'` was hardcoded in the
  shared prefill path, so the Q4 runtime emitted a manifest claiming bf16. It
  now records `quant_name` (`bf16` on the base class, `q4_k_m` on the Q4
  subclass).

## Validation

- `tests/test_unit_vibevoice_q4_evidence.py` (new, CPU-only, 14 tests): fraction
  vs percentage units, transcript parse statuses, strict-mode rejection, unknown
  `--systems` rejection, bf16->f16 numeric conversion (including the pinned
  0x3F80 -> 16256.0 defect), `iter_tensors` target encodings, and five merge
  rejection paths. All pass.
- `tests/test_gpu_vibevoice_qwen2_q4_runner.py` (7 tests, was 3): the original
  logits/greedy-chain/routing gates still pass after the refactor (greedy chain
  still 16/16 vs the torch fixture), plus new ownership (two runtimes over one
  weights handle both close cleanly; weights remain open), per-runner scratch
  identity, `quant_name`/manifest `q4_k_m`, and bf16-exact loader buffer sizes.
- Direct measurement on gfx1151: loader 6.103 GB / 339 buffers; embed and lm_head
  1.090 GB each (ratio 1.00x vs bf16 requirement); scratch pointers distinct
  across runners and registered in the runner's own free list; `weights.close()`
  idempotent and `GGUF_WEIGHT_TYPES` empty afterwards.

## Next

- `scripts/vibevoice_asr_wer_full.py` (new, untracked-to-be-committed) is the
  persistent multi-lane driver that answers the statistical-power objection to
  the 50-clip gate: one processor pass plus one model load per lane instead of
  the bench's per-clip subprocess reload. 50 clips is ~1.5k words, i.e. 0-1
  errors at these WERs; the full test-clean set is 2620 utterances (~52k words).
  Not yet run at scale — the Q4 lane's incremental prefill (11 s/request) and
  the torch/bf16 lanes' per-clip reload are the cost to remove first.
- Q4 speed remains open and unchanged: naive per-column GEMV is 114 ms/token.
  Measured this session on real blocks: pack8 GEMV is 5.7x per GEMV and works at
  rows=146 (gate 28.6 ms, q 2.2 ms), i.e. ~2.6 s per 146-row prefill versus
  11 s incremental — one integration fixes both decode and prefill. The naive
  batched Q4 prefill kernels are not the answer (gate 164 ms, down 158 ms at 146
  rows, ~15 s/request, worse than incremental).
- The matched-protocol speed comparison vs torch is still not run; no speed
  claim is made.
