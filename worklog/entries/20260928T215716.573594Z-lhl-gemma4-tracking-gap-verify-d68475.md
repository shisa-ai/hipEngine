# Verifying iteration 21's "untracked bet": half right, and narrower than claimed

## Summary

Iteration 21 reported that the tiled sliding kernel P1 calls "the live bet
for the gap" is referenced by the punchlist but has no row of its own. That
is worth checking before writing a new row, because writing one would
duplicate an item if the bet already exists under another name. It does.

**The tiled kernel is P2, verbatim.** `a4c7cdfc8`'s entry Next reads:

> A tiled `head_dim`-512 kernel for the 5 global layers (41.3 ms per
> prefill); AOTriton's vendored images do not cover 512.

and P2's row title is *"Tiled flash attention at head_dim 512 for the 5
global layers."* Same item, same framing, already tracked, already carrying
llama.cpp's `flash_attn_tile<512,512,4,8>` as option (a). Iteration 21's
finding, taken as "the tiled kernel is tracked nowhere", is **wrong** — and
acting on it would have put a duplicate row on a list whose credibility
depends on each row being one item.

I also suspected P1 had misattributed the reference, since `a4c7cdfc8`'s
commit message is about sliding-layer plumbing rather than a tiled kernel.
That suspicion was also wrong. The commit's *entry* (not its message) has
the Next, and its second bullet is precisely P1's gap:

> Prompts past the 1024-token window width keep the exact kernel on later
> blocks (1228.9 tok/s at 2048 tokens); the same tiled kernel removes that.

So one kernel serves two rows, and P1's pointer is accurate — it just
resolves only through `git show a4c7cdfc8`.

## What is genuinely missing

Three smaller things, all now fixed:

1. **P1's exit pointed off-list.** "…the tiled-kernel alternative remains
   the live bet" sent the reader to a commit hash with no row to land on.
   P1 now says the bet resolves to **P2's option (a)**.
2. **P2 did not know it was also P1's exit.** Its payoff was recorded as
   five global layers only. P2 now states that the same port removes
   P1's past-window sliding fallback, so the work is worth twice what its
   row claimed — and P1's blocked plumbing route is not the only way that
   gap closes.
3. **The number was nowhere.** `1228.9 tok/s at 2048 tokens`, the measured
   cost of the past-window fallback, appeared **zero times** in the
   punchlist (`grep -c 1228.9` → 0). A row that argues about closing a gap
   should carry what the gap costs.

## Why this correction matters more than the gap would have

Iteration 21's report was a *tracking* claim, and a false tracking claim
costs more than a false performance claim on this list: it invites a
duplicate row, which then has to be reconciled later by someone who does
not know why there are two. The verification cost one `grep`; the
duplication would have cost a reader's trust in the whole table. Checking
the finding was the right move precisely because the previous iteration had
sounded confident.
