# Build the Qwen4Exp GDN DPP library for the running GPU

## Summary

A GPU-visible `--suite all` on the W7900 + RX 7900 XTX host segfaulted at
about 20% in
`tests/test_gpu_qwen4exp_ar_batch_decode.py::test_serving_generator_decodes_two_rows_in_one_batch_step`,
also at the `v0.8.1` tag. `build_qwen4_exp_gdn_dpp()` forced
`target_arch="gfx1151"`, so the `qwen4_exp_gdn_multi` library held only a
gfx1151 code object. The gfx1100 batch decode route loads it for
`qwen4_exp_gdn_decode_rowsplit_indexed_f32`, and HIP dereferenced NULL in
`hipLaunchKernel` instead of returning an error (gdb native backtrace; the
cached manifest showed `--offload-arch=gfx1151`). Flash-Next does not fit on
gfx1100 (about 82.5 GB of device weights), so this was a kernel-correctness
and suite-blocking defect, not a serving outage.

## Changes

- The DPP builder no longer sets `target_arch`; it follows
  `HIPENGINE_HIP_ARCH` or the local device like every other HIP family. The
  source already guards the DPP reduction with `__gfx1151__`; gfx1100
  compiles the shuffle fallback, which keeps the same XOR pairing order.
  gfx1151 builds still target gfx1151.
- `tests/test_unit_qwen4exp_gdn_dpp_variant.py` pinned the forced target; it
  now asserts both DPP builders leave the target to the device (RED before,
  GREEN after).
- Once the crash was gone, `tests/test_gpu_qwen4exp_mixed_gdn.py::test_physical_permutation_does_not_change_row_results`
  ran for the first time on gfx1100 and failed by 1-2 ULP. The kernel was not
  at fault: the test's CPU input projection used one BLAS matmul over all
  rows, and numpy gave different bits for 2 of 6 rows of `attn_qkv` and
  `attn_gate` once permuted. The test now projects one row at a time.
- `docs/LESSONS-LEARNED.md` build-cache section: a library without a code
  object for the running GPU can segfault on launch; check the manifest.

## Validation

- W7900 and RX 7900 XTX each: the DPP-using GPU files
  (`ar_batch_decode`, `gdn_indexed_decode`, `gdn_dpp`, `gdn_rowsplit_prefill`)
  49 passed, 10 skipped (DPP parity is gfx1151-only); `mixed_gdn` 9 passed.
- The GPU-visible `--suite all` now runs past the old crash. It stopped at
  about 34% after 52 minutes with SIGABRT while 100+ leaked
  `engine_service` worker threads were alive; the aborting test
  (`test_live_evie_gpu_runtime.py` by collection count) passes alone. Before
  that point other GPU files fail independently of this change: HIP out of
  memory in Gemma 4 and VibeVoice setup, VibeVoice models absent from the
  local Hugging Face cache, and Gemma 4 graph/WMMA/expert, M4/M5 GGUF MTP and
  Maple RMSNorm failures.
