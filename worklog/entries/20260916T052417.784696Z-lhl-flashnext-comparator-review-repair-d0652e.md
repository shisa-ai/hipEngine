# Flash-Next comparator review repair: corrected PR63 gain, withdrawn attention claim, delimited per-component attribution

## Summary

A five-finding review of the halo-box PR #63 comparison (commit `269b37267`) was
correct on all five points. Repairing it changed the headline from **+13.9% to
+39.9%**, withdrew an attention-regression claim, and produced the first
per-component prefill attribution whose windows hold exactly one prefill.

The headline number was wrong for two independent reasons, and the smaller error
was the profiler. Both arms were originally measured with `--profile`, and the
rate was read from the server's own `prompt_ms`. Reading the server's timer does
not remove profiler overhead, and there was no reason to believe the overhead was
equal between two builds. It turns out to be small — 0.2-0.5% across the ten
cases where a profiled and an unprofiled capture of the same build agree — but
"small" is not "established equal", so profiled captures are now excluded from
rate rows by declaration rather than by convention.

The larger error was contamination of the baseline row. An earlier full-suite
capture of `69946438a` at bf16 put `mixed_ja_en-p1024` at 351.8 and
`mixed_ja_en-p4096` at 363.6 tok/s. The same build now reads 610.0 and 677.2.
Those three cases are measured last in every run, and in that run they were
73-86% low, which dragged the run's weighted rate from 654.4 down to 511.5, a
21.8% depression. Whatever happened is not a property of the engine: it does not
reproduce, and the same binary is flat across categories when it is not
happening. The earlier comparison used that row as its baseline.

The original candidate number was also a single measured repetition, and it read
about 24% high (4873.5 ms against 3926 ms now).

The attention-regression claim is withdrawn. Delimited to single prefills,
`qsa_attention` is 156.6 -> 155.7 ms, and the dominant kernel
`flash_attn_ext_f16<256, 256, 16, 4, false, false, false>` agrees on duration
(273.1 -> 270.2 ms over two prefills), dispatch count (48), grid
`(24576, 8, 1)` and workgroup `(32, 8, 1)`. The earlier +101.2% came from a
window that did not hold the same amount of work in each arm. This is the reason
per-component numbers from undelimited traces should not be reported at all, and
it is now enforced: `qwen4exp_delimited_prefill_attribution.py` refuses to
attribute a request it cannot match to a burst, and
`qwen4exp_prefill_component_gap.py` refuses to compare two artifacts that did not
match every measured request.

## Changes

### Harness: `scripts/qwen4exp_llamacpp_prefill_comparator.py`

- `--inter-request-gap-ms` (default 0). Back-to-back requests produce one
  continuous run of dispatches, so a trace cannot be split per request and a
  burst covers the warmup and the measured prefill together. That is the direct
  cause of the ~1.7 kernel-sum-over-measured-prompt ratio. A 2000 ms gap puts
  each request in its own burst.
- `--trace-root` is no longer required. It was required unconditionally, which
  made a plain rate measurement look like it needed the profiler; an unprofiled
  run now gets a fresh temporary directory.

### New: `scripts/qwen4exp_delimited_prefill_attribution.py`

Matches each measured request to the burst whose kernel sum is a plausible
fraction of that request's `prompt_ms`, then reports per-family and per-kernel
milliseconds for the matched bursts only. A burst holding two prefills reads near
2.0 and is rejected. Buckets come from `qwen4exp_comparator_role_map.py` so both
engines classify a kernel the same way.

### New: `scripts/qwen4exp_prefill_component_gap.py`

Side-by-side per-family comparison of two attribution artifacts. Asserts that
both matched every measured request before producing a table.

### New: `benchmarks/results/2026-09-15-flashnext-engine-comparison/comparison.py`

Written earlier but never wired in. Enforces the canonical case set, per-case
prompt token hash match against a shared reference, exact repetition count,
positive finite `prompt_ms`, and rate-eligible measurement class; reports
unmeasured stalls as `unknown` while preserving every sample. `assemble.py` now
loads every engine through it and computes one estimator for all rows.

### `scripts/llamacpp_pair_token_compare.py`

The checker could pass vacuously: a missing token array became `[]`, two empty
arrays compared "identical", a short sequence was compared over its own length,
and it exited 0 on divergence. The decision logic is now a pure `compare_arms`
function that raises rather than returning a verdict it cannot support, and it
exits non-zero on divergence.

### `benchmarks/results/2026-09-15-flashnext-engine-comparison/assemble.py`

`_rate_row` deleted. It was the equal-weight mean of per-case medians while
hipEngine's row was total tokens over total prefill time — two different
quantities whose ratio was not a speedup.
