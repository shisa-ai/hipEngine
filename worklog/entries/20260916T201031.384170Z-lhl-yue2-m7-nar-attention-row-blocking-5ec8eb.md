# YuE2 M7 NAR attention bandwidth and row blocking

## Summary

M7 profiling found the NAR attention kernel was reading the whole K/V cache once
per (query row, query head) pair. On the smallest production case that is 27.9 GB
of traffic per call, and the kernel was the single largest consumer of GPU time in
the e2e path. Blocking four query rows per block, so one loaded K or V element
serves four rows, cuts the replay from 78.0 s to 51.6 s (**1.51x**) with the
output bit-identical to the parent kernel.

The first attempt at row blocking was *slower* (93.1 s) because the dot product
still loaded K once per row; only the loop order (dimension outside, row inside)
turned the blocking into reuse. That mistake is worth recording: the blocking
itself is not the win, the reuse is.

## Changes

- `hipengine/kernels/hip_gfx1100/yue2/nar.hip`: `YUE2_NAR_ROWS_PER_BLOCK 4`.
  Grid becomes `(num_q_heads, ceil(rows / 4))`; shared memory holds
  `2 * blockDim * 4` floats. Two reductions: each lane computes its own key's
  `expf` once instead of once per lane (blockDim x fewer transcendentals), and the
  K/V elements a lane loads are reused by all four rows. Per-row arithmetic is
  untouched -- same serial dot product, same tile walk, same accumulation order.
- `scripts/yue2_nar_attention_golden.py` + `tests/fixtures/yue2/operators/nar_attention_parent.npz`:
  the parent kernel's exact output bits on a multi-tile GQA shape (198 keys over
  tiles of 128, so the tail tile is partial), recorded before the rewrite.
- `tests/test_unit_yue2_nar_kernels.py`: bit-parity test against those bits. It
  fails on a perturbed reduction (verified: using the running max instead of the
  tile max reports a nan diff), so it is a real gate rather than a tautology.
- `scripts/yue2_oracle.py`: schema and relation checks for the new fixture,
  including that it still spans a partial tail tile.
- `scripts/yue2_e2e_gate.py`: per-case `nar_seconds` / `vae_seconds`.

## Validation

- Bit-parity test passes; all 10 NAR kernel tests pass. The test is a real gate:
  perturbing the reduction to use the running max instead of the tile max makes it
  fail with a nan diff.
- All three M4 production parity gates re-run and reproduce their pre-change
  numbers to the last recorded digit: chunk0 latents rel L2 0.01225 / cosine
  0.999926 / 16.2% BF16-exact, multi-chunk 0.01071 / 0.999944 / 16.9%, restricted
  visibility 0.00885 / 0.999962 / 21.5%. The kernel change is numerically inert.
- `rocprofv3 --kernel-trace` on the cached-only smoke (34 rows, 579 keys,
  gfx1151, parent and final traced in the same session):
  `yue2_nar_attention_kernel` average **1208.26 us -> 724.99 us** (1.67x) across
  140 dispatches, VGPR 24 -> 32, no scratch. The M4 entry recorded 1028.59 us for
  the parent in an earlier session; profiled durations move between sessions, which
  is why the artifact pairs runs traced together.
- Replay of `mandarin-off-s1234` (1297 frames, 2 ODE steps, NAR+VAE):
  **78.0 s -> 76.5 s** for the shared-weight change alone and **51.6 s** with row
  blocking (1.51x); a later repeat measured 54.5 s, so treat the ratio as ~1.5x.
  The split is 31.98 s of solve and 22.47 s of decode, which makes the VAE conv1d
  the second largest consumer and corrects the earlier assumption that the decode
  was a rounding error.
- Same case at the product's 32 steps: 465.9 s, frames 1297/1297 and samples
  2490176/2490176 unchanged.
- Matched same-host comparison against the pinned upstream's own recorded run of
  the same case (zbook / gfx1151): NAR 443.4 s against 27.32 s, decoder 22.47 s
  against 69.09 s, AR 19.35 tok/s against 31.97 tok/s. The NAR solver is the
  largest gap and the decoder is a win.

## Next

- M7 continues with the VAE `yue2_vae_conv1d_f32_kernel` (76 dispatches /
  16.25 s of the profiled replay, 213.9 ms each) as the next isolated candidate.
- Unexplored NAR candidates, in profile order: 8 rows per block (K/V traffic
  halves again at 8x the reduction work), and a tree reduction for the tile
  maximum (`fmax` is exact, so it stays bit-exact) to shorten the 128-step serial
  walk each lane still performs per tile.
- The tile-max serial walk and the per-lane `expf` were the two costs the profile
  could not attribute cleanly: removing the exponentials moved the smoke by 1.12x
  but the replay by only 1.02x, so the kernel is not transcendental-bound at the
  production row count. Splitting those two effects properly needs a
  counter-based profile rather than a kernel trace.
- M8: gfx1100 remains unverified -- no such hardware was available for any YuE2
  gate.
