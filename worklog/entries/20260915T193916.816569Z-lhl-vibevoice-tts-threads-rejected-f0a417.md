# VibeVoice-TTS: chain_exact is not a sufficient gate -- a threads=64 GEMV regresses audio with an identical token chain

## Summary

`dense_dual_gemv_out_bf16` -- the LM decode's gate+up projection -- is 3.8x faster
at `threads=64` than at the `threads=256` default the decode path uses
(74.8 us vs 283.0 us at rows=1, K=1536, N=8960). Applying it took the LM stage
from 1.450 s to 1.266 s and pooled RTF from 1.201 to 1.174, **with
`chain_exact: true`**. The ten-seed generated-audio suite then returned **57/60
against the baseline's 58/60**, introducing a new failure that the baseline does
not have. The change is reverted.

## The regression

| arm | failures |
| --- | --- |
| baseline (BM=128, threads=256) | 2 |
| BM=64 low-row tile (kept) | 2 |
| dual GEMV threads=64 (rejected) | **3** |

The new failure is `single-numbers` on seed 20260917 at **WER 0.1667**, failing
`intelligible`. It does not appear in either accepted arm.

## Why this matters more than the change itself

The thread count changes the reduction width, and therefore the summation order:
**5 of 17920** dual-GEMV outputs move by about one ulp. That is the same class of
perturbation as the rejected semantic GEMV, and it produces the same outcome.

The important part is what did **not** catch it:

- **`chain_exact` was true.** The generated token chain was identical to the
  oracle across the whole request. The LM's argmax never flipped.
- The full correctness suite was green: **126 passed, 11 skipped**.
- `negative_conditions_match` was true.

So an identical token chain does not imply identical audio. The LM's *hidden
state* -- not just its sampled tokens -- conditions the diffusion head, and a
one-ulp change there is enough to move the generated waveform. **`chain_exact` is
a necessary check, not a sufficient one**, and this path must be gated on the
generated-audio quality suite alone.

## Measurements

Isolated, rows=1 (LM geometry H=1536, F=8960):

| call | threads=64 | threads=128 | threads=256 |
| --- | ---: | ---: | ---: |
| gate+up (dual) | **74.8 us** | 117.6 us | 283.0 us |
| down (single) | 56.9 us | **44.0 us** | 45.2 us |
| qkv (single) | **13.2 us** | 21.7 us | 33.2 us |
| o_proj (single) | **9.0 us** | 14.6 us | 22.2 us |

Bandwidth at (1, 1536, 8960) for the dual: **585.8 GB/s at 64 threads, 457.3 at
128, 207.3 at 256.** End-to-end with only the gate+up call site changed:
`lm_total_seconds` 1.450 -> 1.266, `pooled_rtf` 1.201 -> 1.174.

Note the qkv and o_proj rows are `dense_gemv_out_bf16`, not the
`dense_gemv_bf16_f32_out` / `dense_gemv_f32_bf16w_f32_out` kernels the decode
path actually calls for those projections, so those two rows are indicative only.

## Changes

Nothing is retained; the change is reverted.


- `hipengine/runtime/vibevoice_qwen2.py`: the `threads=64` argument on the
  gate+up call is removed.
- `benchmarks/results/2026-09-15-gfx1151-vibevoice-tts-session-real-request.json`:
  restored to the accepted revision's numbers.

## Validation

- `uv run python scripts/vibevoice_tts_session_bench.py` with `threads=64` -> `chain_exact: true`, pooled RTF 1.174.
- `uv run --with jiwer --with transformers python scripts/vibevoice_tts_quality_suite.py --phase all --seeds 20260915,...,20260924` -> **57/60**, new failure `single-numbers` seed 20260917 (WER 0.1667).
- `uv run pytest tests/ -k vibevoice` -> 126 passed, 11 skipped (green, and it does not see the defect).

## Next

The opportunity is real but needs a mechanism that does not move the arithmetic.
The same reasoning that produced the accepted BM=64 tile applies: a change that
preserves the summation order is safe by construction, and one that does not must
clear the quality suite. A `threads=64` variant that keeps the 256-wide reduction
tree would be worth trying; a bare thread-count change is not.
