# Forced tokens and force-sequence completion through speculative MTP

## Summary

Task 8, first half. A request with a pending forced token is served by the
sampled MTP route, and the tokens it publishes are the tokens the autoregressive
route publishes for the same request: the queue head at the position the queue
governs, in order, consumed exactly once.

A forced token is a caller-level override, not a sampling-law field: the
autoregressive route emits the queue head instead of drawing from the row
(`select_token` in `hipengine/generation/sampling.py`). A cycle publishes several
tokens at once, so the override has to reach the accept walk. It does so as the
law of the row that predicts that position -- a point mass on the forced token --
which the coupled accept already handles exactly: a draft that agrees is
accepted, and one that does not is corrected to the forced token. That is the
same mechanism the finish rule uses, and it needs no new accept-walk code.

The live queue is a different matter. It may only be consumed for the tokens a
cycle actually published, so the overrides are resolved per row from cloned
states (never the live one), and the live state is popped at commit time by the
count of published tokens that carried an override.

## Changes

- `hipengine/generation/sampling.py`: `processed_distribution` takes
  `forced_token_id` and returns a point mass on it, keeping `select_token`'s two
  checks (outside the vocabulary, or rejected by the request's own tokenizer
  constraint, is an error rather than a silently published token). The override
  is opt-in, so the helper still reports the row's own sampling law when the
  caller resolves no override.
- `hipengine/generation/mtp_sampled_accept.py`: one row walk
  (`_row_prefix_walk`) now backs both `row_prefix_states` and the new
  `row_forced_token_ids`. Each row's state is the state `_process_row` would see
  at that point of an autoregressive decode -- its own override still at the head
  of the queue -- while a child's state has its parent's override already
  consumed, which is what makes a chain drain the queue in order instead of
  seeing the same head at every row. `sampled_accept_summary` passes each row's
  override into the distribution. `published_forced_count` returns how many of a
  cycle's published tokens carried an override (a stop inside the chain must not
  consume the overrides behind it), and `observe_published_tokens` mirrors one
  autoregressive step per published token into the live state: prepare, consume
  the override when this token was one, then observe. It refuses a mismatch
  between the consumed override and the published token, which is the invariant
  that keeps the live queue and the published output in step.
- `hipengine/generation/qwen35_gguf_mtp2.py`: `_sampled_accept_summary` returns
  the row walk's overrides as a third element; the commit computes the published
  forced count and hands it to `observe_published_tokens`. The native-sampler
  branch raises rather than sampling if a forced token ever reaches it, because
  the device sampler draws each row on its own stream and returns no host row.
- `hipengine/generation/sampling.py`: `forced_tokens_pending`,
  `post_thinking_forced_tokens_pending`, and
  `force_sequence_completion_token_sequences` moved from
  `SAMPLED_MTP_UNSERVABLE_BLOCKERS` to `SAMPLED_MTP_SERVABLE_BLOCKERS`. They are
  one queue: the post-thinking queue becomes pending when a row's observed token
  ends the thinking phase, and a partially matched force-sequence queues its
  remainder inside `observe`, which the row walk already runs per row. The
  post-thinking queue can only be non-empty alongside a thinking budget, so in
  practice that field is still refused by `thinking_budget`; the docstring says
  so rather than claiming a reachability it does not have.
- `docs/reference/SAMPLING.md`: the paragraph that listed the sampled route's
  blockers as "fields that require AR fallback today" now separates the greedy
  route's list from what the sampled route serves, and names the three fields
  that still keep a request autoregressive.
- `docs/REFACTOR.md`: a new entry for the forced-token requests that skip the
  captured-graph sampled accept, with its removal condition.
- `scripts/mtp_forced_token_gate.py`: the live gate. Both arms run the same four
  requests through `hipengine.LLM` -- the route is the only difference -- and the
  autoregressive arm is the reference. It pins the resident context (see below)
  and refuses to start without headroom.
- `tests/test_unit_sampling_distribution.py`,
  `tests/test_unit_mtp_sampled_accept.py`,
  `tests/test_unit_speculative_sampling_modes.py`,
  `tests/test_unit_mtp_native_sampling.py`,
  `tests/test_unit_mtp_forced_token_gate.py`: the point mass and its two
  refusals, the queue drain across rows, the correction and full-accept cases,
  the published-count and publish-time pop, the servable/unservable partition,
  the adapter's host path, and the gate's own checks driven against a fake that
  violates exactly one thing.

## What is still refused, and why

Two families remain on the autoregressive path, with the cause and the clearing
command recorded next to the list in
`hipengine/generation/sampling.py`:

- `json_object_close_forcing` and `tool_call_constraint` are tokenizer-keyed:
  they advance a text DFA in `observe_selected_token_text` and mask the row's
  support from it. The row walk observes token ids, not text, so inside one cycle
  the later rows would be processed against a DFA state that has not seen the
  earlier rows' tokens -- the mask would be wrong for exactly the rows a cycle
  publishes together. Clearing command: observe each row's decoded text in the
  row walk (the tokenizer and the per-row remaining-token budget are already
  available at the call site), then gate against the autoregressive route for a
  tool-call and a json_object request.
- `thinking_budget` is a policy refusal, not a structural one: the host thinking
  state is per-row sampler state this route already walks, but it is unreachable
  because the server relaxes the budget under its default `hint` policy before
  the blocker check and refuses the request under `hard`, serving plain AR.
  Clearing command: measure a thinking request through this route on both
  policies, then move the field to servable.

Neither is a silent downgrade: an explicit request runs or returns the named
sampling-capability error, which is the existing behavior.

The sampled case is the documented exception: the accept walk draws one uniform
per verified row where the autoregressive route draws one per step, so the two
arms publish different draws from the same law. Its forced prefix is identical on
both arms, and the induced-law gate is what measures the law itself.

The unforced request run after every forced case published the same 16 ids as the
unforced seed request on both arms, so no queue state survived a request.

## Two things this unit got wrong first

- The first live run of the gate caught an `UnboundLocalError` in the host
  sampled-accept path: a function-local import of the row walk inside the native
  branch bound the name for the whole function, so the host path read an unbound
  local. The engine contained it by falling back to autoregressive decoding for
  that request and recording `precommit_failure_ar_fallback` in its own
  diagnostics, which is what the gate's route check read. Fixed, and pinned by
  `test_host_sampled_accept_resolves_forced_overrides_without_consuming_them`
  (verified by re-introducing the import and watching the test reproduce the
  exact error).
- The first version of the gate loaded the model with a pinned 4096-token context
  but never called `prepare`, so GGUF auto-sizing selected the model's own
  183808-token context -- about 49 GiB of BF16 KV -- on top of two resident
  17 GiB servers. That exhausted the machine's 125 GiB of RAM and the kernel OOM
  killer reaped the two servers and several user session services. The gate now
  calls `prepare` with the pinned context, sets `HIPENGINE_GGUF_AUTO_CONTEXT=0`
  so the pin is honored exactly, and refuses to start below 40 GiB of available
  RAM, checked per arm.
