# qwen4exp shared target pass mixed layout

## Summary

Added the immutable host layout for one shared Qwen4Exp target pass containing
autoregressive rows and prepared speculative chains: request groups, physical
rows, a validated generic verifier row contract, and per-request commit
destinations for accepted-prefix counts. This is a layout prerequisite only. The
batch runtime still admits one row per unique slot and has no shared execution,
so nothing new runs on a device.

## Changes

- `hipengine/runtime/qwen4_exp_mixed_layout.py` (new, torch-free host module).
  - `Qwen4ExpMixedRequest`: request id, physical slot, that slot's owner token,
    the append position of the root row, the already-decided root token, and the
    prepared candidates at depths `1..N`. Empty candidates is an AR peer;
    `autoregressive(...)` names that case.
  - `Qwen4ExpMixedRow`: physical row, semantic row, request, slot, owner token,
    depth, position, token. `context` is derived (`position + 1`) for a future
    executor and is not a kernel ABI.
  - Owner token `0` is refused at both request and row construction. The batch
    owner zeroes every slot (`_owners = [0] * slots`) and `admit()` increments
    `_next_owner` before returning it, so a live admission is `1..N` and `0`
    means unowned. A request or row carrying `0` would name the slot without
    owning it.
  - `Qwen4ExpMixedLayout`: stores rows in physical order and derives a
    `TargetVerifyBatch` from them in `__post_init__`, so a layout is either a
    generic verifier row contract or it does not exist.
    `require_verifier_compatible()` re-derives and compares that batch.
  - `compile_mixed_layout(requests, *, physical_row_order=None)` builds the rows;
    `physical_row_order[p]` is the semantic row at physical row `p`, so a
    permutation never rewrites a row's request, depth, position or token.
  - `commit_destinations(accepted_counts, *, transaction_id, next_tokens)`
    returns a validated `TargetCommitPlan` naming each request's commit row,
    token and position. Accepted count `k` means `k + 1` consumed input rows
    (root plus `k` candidates), and the destination is the **last** of them: the
    final state checkpoint the commit keeps (GDN, conv, PLE, attention,
    position), not the first row and not one row per consumed row.
  - `mixed_request_from_proposal(...)` adapts a prepared `Qwen4ExpMTPProposal`
    by reading `start_position`/`root_token`/`candidates`. `runtime` does not
    import `generation`; the adapter reads the three fields instead of the type.
- `tests/test_unit_qwen4exp_mixed_layout.py` (new, 47 tests).

Reused rather than duplicated: `TargetVerifyBatch` owns the row contract
(tokens, positions, `row_to_request`, `parent_rows`, `root_rows`,
`candidate_rows`, `draft_depths`, `active_mask`) and `TargetCommitPlan` owns the
commit-destination shape, so this module adds the qwen4_exp binding (slot, owner
token, physical permutation) and no second scheduler vocabulary.

Row semantics: depth `d` appends at `start_position + d`, matching
`Qwen4ExpMTPProposal.start_position` and
`verify_target_block_state_rows`' `start = int(self.position)`; a root row's
token is already decided but its target row is appended by this pass. Validation
runs before any row set exists: duplicate request ids, slots and owner tokens,
`physical_row` not equal to its position, a row naming a request outside the
pass, a request whose prepared row count or depth set does not match, a position
or token that disagrees with `(start_position, depth)`, and a `semantic_row` set
that is not the contiguous request-major chain order.

Where AR rows differ from chain rows, documented in the module and pinned by
tests:

- An AR peer contributes exactly one root row: `draft_depth == 0`, absent from
  `candidate_rows`, `candidate_counts` entry `0`. A generic verifier that assumes
  every request has a candidate row cannot consume one.
- A pass with no candidate rows has no generic work projection:
  `TargetVerifyBatch.to_work_item()` raises, and the layout still describes the
  pass.
- An AR peer must pass accepted count `0` and therefore advances exactly once;
  a non-zero count is refused. Its single consumed row is both the first and the
  final checkpoint of that one-row prefix.

A parent row must precede its child physically, because `TargetVerifyBatch`
resolves chain parents by row index. An interleaving permutation is accepted; a
permutation that puts a candidate before the row it extends is refused here
rather than failing later.

## Next

- M2: the shared target pass itself. It needs the batch owner's row plan relaxed
  (repeated slots, rows > slots, per-row positions) plus row-major GDN/conv/PLE
  state before a layout can be executed.
- Per-request commit and cancellation inside a shared pass remains M3 work; this
  layout names destinations but has no notion of peers finishing early.
