# RT-1 promoted: the serving prefill chunk cap is not the fairness bound

## Summary

RT-1's measured 256 -> 1024 prefill win is promoted to the serving default
(`DEFAULT_MAX_PREFILL_CHUNK_TOKENS` 256 -> 1024) because its recorded blocker is
falsified by the code it was about.

The blocker, as the ledger recorded it, was that `max_prefill_chunk_tokens`
"is a C4 scheduler knob bounding per-tick prefill work so decode is not
starved ... Raising it 4x makes each prefill tick up to 4x longer". That
premise is wrong. `_run_token_budget_round` bounds per-tick prefill work with
`round_prefill_token_budget` and only splits that already-bounded budget into
chunks:

```python
prefill_budget = self.round_prefill_token_budget          # 1024
while prefill_budget > 0 and self.scheduler.has_prefill_work():
    chunk_size = min(self.prefill_chunk_size, prefill_budget)
```

So the per-tick fairness bound is the **round budget** (1024), and the chunk cap
can only subdivide it. At 256 against a 1024 round budget the engine processed
1024 budgeted tokens as **4 x 256**; at 1024 it processes the same 1024 tokens
as **1 x 1024**. Per-tick work is identical. A cap below the round budget cannot
make the engine fairer - it can only multiply per-chunk overhead, which is the
whole of the measured win.

Corroborating: `ResidentEngineLoop.__init__`'s own `prefill_chunk_size` default
was **already 1024**; only `EngineLoopConfig.max_prefill_chunk_tokens` was
pulling it down to 256. The two knobs were simply inconsistent, and this
promotion aligns them.

## Changes

- `hipengine/generation/engine_loop.py`: `DEFAULT_MAX_PREFILL_CHUNK_TOKENS`
  256 -> 1024, with a comment recording the mechanism, the measured range, and
  the scope limits (prefill-only harness; not a decode-latency claim).
- `tests/test_unit_engine_loop_prefill_chunk.py` (new): pins the relationship
  rather than a bare number - the chunk cap must equal the round budget, the
  per-round token count is unchanged by the cap, and the cap strictly reduces
  fragmentation. A future change to either knob must keep them consistent.
- `tests/test_integration_generation_batch_scheduler.py`:
  `test_engine_loop_cli_env_defaults_match_docs` now asserts the config default
  against `DEFAULT_MAX_PREFILL_CHUNK_TOKENS` (plus the cap == budget invariant)
  instead of the literal 256, so it cannot drift from the constant again.

## Next

- **This is a prefill-only measurement and the note says so.** It is not a
  decode-latency-under-concurrency claim. The specific protection the old
  default was thought to provide - a shorter prefill tick - is provided by
  `round_prefill_token_budget`, which is unchanged, so no c2/c8 claim is needed
  to justify the flip; but a c2/c8 prefill-interleaving measurement on the
  serving path would still be worth having.
- **A serving-path A/B was attempted and could not run here, on either
  backend.** `gguf_live_server_bench.py` requires `--model` to be a single file
  (`model.is_file()`), so the 4-shard Qwen3.8-Flash-Next directory cannot be
  loaded, and its own `--prefill-chunk-size` default (256) means it cannot
  exercise the engine's serving default without an explicit override anyway. It
  was tried with the harness's default single-file model (Qwen3.6-35B-A3B
  UD-Q4_K_M): on `hip_gfx1100` it died with `HIP error 98: invalid device
  function` even without the cached-build gate, and on `hip_gfx1151` (the
  backend `QWEN4_EXP_BACKEND` actually names) it timed out waiting for the
  engine service. **No serving-path timing was obtained, and none is claimed.**
  The promotion does not depend on it: the property that made the flip safe -
  per-tick prefill work is bounded by the round budget, not the cap - is a
  code-level invariant pinned by the new tests, and the speedup is the
  recorded prefill-harness measurement above.
- `RT-3`'s shape policy is unnecessary for this change (established separately:
  short requests are unaffected by owner size, and a two-owner policy measured
  1.06% *slower* at 0.017x the within-arm spread). What remains for a larger
  chunk is the memory-admission question, not a policy.
- `docs/REFACTOR.md` should be re-read for the c2 qualification requirement that
  named this flip; the round-budget argument addresses the fairness half of it.
