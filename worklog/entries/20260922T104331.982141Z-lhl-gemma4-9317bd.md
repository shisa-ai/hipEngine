# Gemma 4 GGUF tokenizer reconstructed from metadata

## Summary

Adds `Gemma4GGUFTokenizer`, the first hipEngine tokenizer that is not a GPT-2
byte-BPE model, and gates it against the `tokenizer.json` that shipped with the
same artifact.

The recipe differs from the existing `qwen35`/`laguna` family in three ways:

- The normalizer replaces every space with U+2581 and the merges run on raw
  UTF-8. There is no GPT-2 byte<->unicode map in the pipeline, so `é` is one
  merge-able string rather than `Ã©`.
- The vocabulary carries the 256 `<0xXX>` byte tokens (GGUF type `UNUSED`) and
  the model runs with `byte_fallback` enabled.
- Control and user-defined tokens are matched literally from the GGUF token
  types, which is exactly how llama.cpp overlays its own attribute table.

`tokenizer.ggml.model` is `gemma4`, which carries its own pre-tokenizer and no
`tokenizer.ggml.pre` key, so the recipe is selected on the model name alone.

### Two deliberate deviations from a literal reading of the GGUF

1. **`<eos>` is written with type `NORMAL`.** It is an added token in the
   reference `tokenizer.json`, and llama.cpp overrides it to control for
   `gemma4` while logging that the model file is a bug. Both are matched here:
   the configured special ids and the gemma4 end-of-generation token strings are
   registered as special added tokens even when the GGUF type disagrees. Without
   this, a literal `<eos>` in text byte-splits into `<`, `eos`, `>`.
2. **`<|tool_response>` stays non-special.** The converter promotes it (and the
   other six chat-visible tokens) to `USER_DEFINED` so the chat parser can read
   them, so it is matched literally but still renders in decoded text under
   `skip_special=True`. Only `CONTROL` tokens are dropped there.

`eog_token_ids` follows llama.cpp's gemma4 end-of-generation set — `<turn|>`
(the configured `eos_token_id`), `<eos>`, and `<|tool_response>` — rather than
the single id in `tokenizer.ggml.eos_token_id`.

### The newline split is measured, not assumed

llama.cpp splits on newlines before merging because its BPE merge lookup asserts
that no token spans one. The reference pre-tokenizer has no such split. Three
candidate recipes (normalizer only, newline split, `Split(" ")` as written in
`tokenizer.json`) were compared against the reference tokenizer on the corpus
below; all three agree with it on every text, so the llama.cpp split is used and
costs nothing.

## Changes

- `hipengine/tokenization/gguf.py`: `gemma4` branch in `_build_hf_encoder`
  (full-vocabulary BPE with byte fallback, U+2581 normalizer, newline-split
  pre-tokenizer, replace/byte-fallback/fuse decoder), an `extra_special_ids`
  hook on the base tokenizer, and `Gemma4GGUFTokenizer` with its own
  `decode`, `eog_token_ids`, and `stop_token_ids`.
- `hipengine/tokenization/__init__.py`: export `Gemma4GGUFTokenizer`.
- `tests/_gemma4_gguf_fixture.py`: a hand-built 294-token SPM vocabulary with
  real merges, all 256 byte tokens, and the `<eos>`-is-NORMAL quirk, plus
  `tokenizer_fixture_metadata`.
- `tests/test_unit_gemma4_gguf_tokenizer.py` (new): 22 unit tests.
- `tests/test_live_gemma4_gguf_tokenizer.py` (new): 5 live tests.

## Validation

```bash
uv run pytest tests/test_unit_gemma4_gguf_tokenizer.py \
              tests/test_unit_gemma4_gguf_loader.py -q
# 43 passed

uv run pytest tests/test_live_gemma4_gguf_tokenizer.py --suite live -q
# 5 passed
```

The live test builds the tokenizer from
`gemma-4-26B-A4B-it-UD-Q4_K_XL.gguf` (262,144 tokens, 514,906 merges) and
compares its ids against `hf-ref/tokenizer.json` for a deterministic corpus of
source text, Unicode, whitespace, and control-token cases. **All 990 texts agree
exactly**, and all round-trip through the GGUF decoder. The corpus includes the
two cases that a hand-written fixture list missed: a literal `<eos>` and a
literal `<turn|>` inside prose.

The unit tier pins the recipe mechanics on the hand-built vocabulary, where the
expected ids are stated symbolically, so a change in merge priority, the
normalizer, or the added-token overlay fails without needing the 17 GB artifact.
