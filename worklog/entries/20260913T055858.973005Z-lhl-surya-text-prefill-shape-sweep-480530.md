# Text-prefill shape sweep: the shared envelope re-chooses the text tile

## Summary

`plan_score_tiles` is one planner for both score matrices
(`test_prefill_and_vision_share_one_planner`), and the shape envelope added for
the vision tower (`max(SHAPE_TILE_ROWS=128, ceil(rows / SHAPE_TILE_DIVISOR=32))`
rows, rounded down to `SHAPE_TILE_MULTIPLE=32`) is applied to the text prefill
too. That envelope is calibrated on the 256/1024/4096/6400/34320-patch vision
grids; on the text path it re-chooses the tile the byte budget already picked —
512 rows instead of 1024 at 16384 tokens, 256 instead of 1955 at 8580 — and the
recorded evidence only compared each choice with *dense*, never across query
blocks. The code comment and `docs/REFACTOR.md` carried the 16384-token case as
an unmeasured 2.4% miss.

**Measured: the cap silently regresses the text prefill by 3.0% at 16384 tokens
and 2.1% at 8580, and the text curve is monotone in tile count in both passes.**
The widest tile the 512 MiB budget admits is the text optimum at both lengths,
and it is at or below the dense time, so on the text path the envelope is pure
loss — it buys 268 MB of a 6.4 GB peak for the 3.0%, and a user who needs that
memory sets a smaller budget, which derives a smaller tile anyway. The text path
needs a text-aware rule (task #86), not a looser vision constant.

passes (the second in reverse order). `pooled` is the mean of all 4 timed
prefills; `p1`/`p2` are the per-pass means. Resident 3086.4 MB. `tiles` is

What the numbers say:

1. **The cap costs 3.0% / 2.1%.** At 16384 tokens the production 512 rows are
   17.436 s against the 512 MiB budget's own 1024 rows at 16.927 s (17.436 /
   16.927 = 1.0301); at 8580 tokens 7.692 s against 1955 rows at 7.535 s
   (1.0208). Against the best shape the sweep found (2048 rows, outside the
   budget at 1073.7 MB and 562.3 MB) the gaps are 3.7% and 2.4%, and against
   dense 2.7% and 1.0%.
2. **The curve is monotone in tile count, in both passes.** 16384 tokens:
   128/64/32/16/9/8 tiles = 17.799/17.611/17.397/16.927/16.853/16.808 s;
   8580: 68/34/34/17/9/5/5 tiles = 7.718/7.659/7.596/7.560/7.535/7.513 s. Every
   halving of the tile count is faster, and no shape in the middle beats the
   widest measured one — the ordering is identical in pass 1 and pass 2, which
   is what makes the drift check meaningful rather than decorative.
3. **The arithmetic is shape-invariant, so this is not extra FLOPs.**
   `_attention_packed` passes `m=tokens` to the QK^T batched SGEMM for every
   tile and sums `bq` to `tokens`, so `sum_t 2*nq*tokens*bq*hd` is the dense
   FLOPs for any plan; the AV GEMM is likewise `m=hd, n=bq, k=tokens`. What
   changes is the number of GEMM calls and the number of times the full key
   range is re-read (`tiles * tokens * hd * 4` per head per operand). The
   existing phase profile (`2026-09-12-gfx1151-surya-phase-attributed-profile.json`)
   puts 66.2% of prefill kernel time in `gemm_library`, 30.7% in shape-invariant
   GDN recurrence, 1.3% in the conv, and 0.3% in softmax, so the shape-sensitive
   term lives in the batched score GEMMs. Launch count is not the mechanism:
   128 tiles add ~480 launches over 8, which at microseconds each is ~1% of the
   1.0 s gap.
4. **Memory is not what the cap is buying.** The cap halves the 16384-token tile
   (536.9 -> 268.4 MB) and cuts the 8580-token tile 7.6x (536.8 -> 70.3 MB), but
   the peaks it moves are 6656.8 -> 6388.4 MB (4.0%) and 5212.2 -> 4745.8 MB
   (8.9%) because 180.8 KiB/token of non-attention scratch dominates. The
   budget's own plan is *inside* the 512 MiB budget at both lengths, so the cap
   is a second, unrequested constraint.
5. **The recorded baseline reproduces.** The task's `16.638 -> 16.774 s` is the
   pre-envelope artifact (`2026-09-12-gfx1151-surya-text-prefill-tiling.json`,
   commit `7ec024e8f`): dense 14709.2 MB / 16.638 s and the 512 MiB budget's own
   1024-row plan 6656.2 MB / 16.774 s. This sweep measures those two at
   14709.9 MB / 16.72 s and 6656.8 MB / 16.79 s — peaks to 0.7 MB, times to
   0.5%. The envelope-era artifact
   (`2026-09-13-gfx1151-surya-text-prefill-tiling.json`) re-measured the same
   two paths at 512 rows (6388.4 MB / 17.170 s) and 256 rows (4745.8 MB /
   7.543 s); this sweep reproduces those peaks exactly (6388.4, 4745.8) and
   those times to 0.6% (17.21, 7.59 s), as it does that artifact's 128 MiB row
   at block 256 (6254.2 MB / 17.398 -> 17.44 s) and both dense rows (7031.2 MB
   / 7.495 -> 7.49 s). Every one of the seven shared points lands within 0.6%
   and within 0.7 MB, so the 16.638 -> 16.774 s comparison is the same protocol
   on the same host and this sweep extends it rather than replacing it.
6. **Drift was caught and is not shape.** Only the two dense rows exceeded the
   pass tolerance (7.49 vs 7.75 s, 16.72 vs 17.25 s: 3.3% / 3.1%); the other 14
   rows agreed within 3%. The ratios vary monotonically with position in the
   run, i.e. a global scale of ~1-3% rather than a per-shape effect, which is
   why the ranking uses the pooled mean and the reverse pass exists.

## Changes

- `scripts/surya_attention_memory.py`: `--text-blocks` (a named query block
  solves the byte budget backwards as `nq * tokens * block * 4`, lifts
  `SHAPE_TILE_ROWS` / `SHAPE_TILE_DIVISOR` / `SHAPE_TILE_MULTIPLE`, and
  `SystemExit`s if the planner does not return exactly the requested width) and
  `--passes 2` (the second pass runs the plan list in reverse and records
  `pass_ratio` per row). Byte-budget rows keep the envelope, because they are
  the production plan. Rows now carry `requested_block`, `envelope_lifted`,
  `effective_budget_bytes`, `prefill_seconds_pass2`, `prefill_seconds_pooled`,
  `prefill_runs_pooled`, `pass_ratio`, `vs_dense`, `vs_best_shape`, and each
  result carries `best_shape_by_tokens`; the payload records the production
  envelope it read at import. Mirrors `surya_vision_tiling_cost.py --blocks` /
  `--passes`, which is the sibling sweep this one was missing.
- `tests/test_surya_bench_harness.py`: a GPU-free test pins that the lift
  reaches the planner (1955 rows stays 1955, the 16384-token 1024-row width is
  reachable) and that it is restored afterwards, so a silently broken lift
  cannot make every sweep row the production shape wearing a different label.
- `benchmarks/results/2026-09-13-gfx1151-surya-text-prefill-shape-sweep.json`.
- `benchmarks/CHANGELOG.md`, `benchmarks/README.md` (a 3-line protocol note;
  the scoreboard is at 498/500 lines, so it must replace rather than grow),
  `docs/MODEL-SURYA.md`, `docs/REFACTOR.md` (the envelope entry now lists the
  text path as its third measured disagreement and names the fix), and the
  `SHAPE_TILE_ROWS` comment in `hipengine/runtime/surya.py` (the unmeasured
  2.4% is replaced by the measured 3.0% / 2.1% and the monotone curve).
