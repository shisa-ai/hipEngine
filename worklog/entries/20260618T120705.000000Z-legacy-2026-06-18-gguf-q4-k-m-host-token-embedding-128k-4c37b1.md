# 2026-06-18 — GGUF Q4_K_M host-token-embedding 128K capacity diagnostic

## Summary

- Historical pre-Worklog2 journal entry, ported verbatim from `WORKLOG-LEGACY.md` (source lines 95881-95889).
- First appended to the journal in commit `f3624ec9` (subject: fix: add GGUF host embedding capacity diagnostic).

## Changes


- Audited Q4_K_M decode-repack resident weights on GPU1: the only remaining `raw_gguf` device allocation is `root.token_embedding` (`gguf_q8_0`, 540,344,320 bytes / `0.503 GiB`). All selected MoE Q4/Q5/Q6, lm-head Q6, and dense Q8_0 layer weights are already resident T16/pack8/dense layouts, so there is no larger raw+packed duplicate to drop without changing runtime behavior.
- Added guarded diagnostic env `HIPENGINE_GGUF_HOST_TOKEN_EMBEDDING=1`: it frees the device Q8_0 token-embedding allocation after load, keeps a GGUF host memmap, dequantizes exact Q8_0 rows to BF16 on host, copies BF16 embeddings into the normal device hidden buffer, and marks GGUF decode graph replay unavailable because the graph consumes generated token IDs on device. Default path is unchanged when the env is unset.
- Focused CPU tests: `python3 -m pytest tests/test_qwen35_gguf_host_token_embedding.py tests/test_gguf_embedding_dispatch.py -q` -> `4 passed`; `python3 -m pytest tests/test_qwen35_gguf_host_token_embedding.py tests/test_gguf_embedding_dispatch.py tests/test_qwen35_gguf_compact_moe_gemv_routing.py -q` -> `11 passed`; `python3 -m py_compile hipengine/runtime/qwen35_gguf_runner.py scripts/qwen35_gguf_bench.py scripts/qwen35_readme_sweep.py tests/test_qwen35_gguf_host_token_embedding.py` -> passed. A broader unrelated `tests/test_qwen35_gguf_compact_moe_wmma_routing.py` probe still fails on a stale `_COMPACT_MOE_Q4_DUAL_DS4_KEYS` test symbol (not touched by this change).
- GPU1 default-path 512/128+4K/128 non-regression check (env unset, 1 warmup + 3 measured, TheRock ROCm 7.13, cached builds): `512/128` median `2316.723` prefill / `124.168` decode tok/s, stable IDs `[318]*3`, `22.487 GiB`; `4K/128` median `2619.224` / `113.972`, stable IDs `[220]*3`, `22.487 GiB`. This keeps the default memory/ID path intact; decode deltas are within normal short-gate run noise versus the 2026-06-18 baseline (`125.218` / `114.129`). Raw JSON: `/tmp/hipengine-default-after-host-embedding-512-4k-3run.json`.
- GPU1 host-token diagnostic `128K/128` (env set, graph replay auto-disabled by host embedding, 0 warmup + 1 measured): `761.864` prefill / `11.141` decode tok/s, final ID `[17]`, finite final logits, `23.399849 GiB` tracked peak and `23.913330 GiB` sampled HIP used. Weight residency drops to `20.511 GiB` and removes `raw_gguf`; decode scratch is `2.638 GiB` (`2.505 GiB` full-attention KV), session buffers `0.251 GiB`. Raw JSON: `/tmp/hipengine-host-embedding-128k-128.json`; compact artifact: `benchmarks/results/2026-06-18-gpu1-gguf-q4km-host-token-embedding-128k-diagnostic.json`.
- Decision: diagnostic retained / blocked, not promoted. It proves llama.cpp-like 24GB `128K/128` capacity is within reach by removing ~0.5 GiB of weight residency, but the price is unacceptable decode throughput because graph replay cannot use host-provided dynamic token embeddings. Next plausible retained path is GGUF INT8/full-attention KV or another device-side embedding/cache strategy that preserves graph-class decode.
