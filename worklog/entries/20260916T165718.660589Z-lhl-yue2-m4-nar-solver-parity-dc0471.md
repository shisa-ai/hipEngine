# YuE2 M4 NAR solver parity and fixture re-record

## Summary

The M4 NAR device runtime reproduces the pinned upstream flow-matching solver on
the recorded fixture: every teacher-forced velocity agrees to 1.2-1.9% relative
L2 with 0.9998+ cosine, and the native 4-step midpoint solve lands on the
reference's own latents at 1.2% relative L2, 0.999926 cosine, `max_abs` 0.078 on
a reference norm of 72.74. Two real defects were found and fixed on the way: a
sign error in the solver's state update, and a recorder bug that had produced an
internally inconsistent fixture.

## Findings

- **Solver sign error.** `nar_state_update_bf16` already computes
  `state - bf16(v * scale)`; `solve` was passing negative step sizes
  (`-h/2`, `-h`), which made the integrator *add* the velocity instead of
  subtracting it. The velocity function itself was never wrong -- teacher-forced
  evaluation at the recorded states matched the reference at every step, which is
  exactly what localized the defect to the update path. The scales are now the
  positive `h/2` and `h`.
- **The old `chunk0.npz` was internally inconsistent.** Its recorded velocities
  beyond step 0 were not reproducible from its own recorded states by either the
  native runtime or a freshly loaded pinned upstream `CachedNAR` (upstream re-run
  38.12 / 39.07 / 44.54 vs fixture 46.81 / 45.25 / 46.70; step 0 exact). The
  recorder's loop was correct as written, so the cause is environmental, not
  logical, and the fix is a guard rather than a rewrite: `cmd_nar` now replays
  every recorded velocity at its own recorded state and timestep before writing
  and fails the recording on any mismatch. The re-record reports
  `replay_step{0..3}_max_abs = 0.0`, and a fresh upstream run now reproduces the
  new fixture at every step with `maxdiff 0.000000`.
- **`cmd_nar` imported `yue2` before installing its path**, so the recorder could
  only ever run with the reference package already on `sys.path`. Fixed by moving
  `_install_path()` above the lazy import. The oracle also needs `tiktoken`
  (already listed among the tooling modules it records versions for).
- **A gate that never advanced its own state.** The first version of
  `scripts/yue2_nar_gate.py` compared `state_bits()` against each recorded state
  without ever writing one, so every "velocity" row after step 0 was really
  `velocity(noise, raw_i)`. It now teacher-forces each recorded state explicitly
  and separately solves end to end, which is what separates a velocity defect
  from a trajectory defect.

## Changes

- `hipengine/runtime/yue2_nar.py`: positive solver scales; new public
  `load_state(state)` that stages FP32 `[frames, 64]` values into the padded
  device state (with shape/finiteness validation), used by `condition` and by the
  gate's teacher forcing.
- `scripts/yue2_nar_gate.py`: teacher-forced per-step attribution plus an
  end-to-end `solve` comparison; pass requires both the solved latents and the
  worst teacher-forced velocity to stay inside the relative-L2 bound.
- `scripts/yue2_oracle.py`: path install before the lazy reference import;
  records `steps` and `nar_cond_end`; `--nar-cond-end`; replay self-check.
- `scripts/yue2_nar_rocprof_smoke.py`: cached-only `rocprofv3 --kernel-trace`
  child for the NAR kernels (builds `yue2_nar`, `vibevoice_encoder`,
  `paro_silu`, `dense_gemv` and `cast` with `require_cached=True`).
- `tests/fixtures/yue2/nar/chunk0.npz` + `manifest.json`: re-recorded with the
  self-checking recorder; the manifest now carries `steps`, `nar_cond_end` and
  the four replay residuals.
