# the mtp serving pattern is a provider the generator delegates to and gemma 4 needs four steps

## Summary

`20260928T073254` established that `LLM.generate_speculative_mtp_detailed()` raises for the
Gemma 4 generator because `supports_speculative_mtp` is `False`. This reads the working
implementation in `qwen4_exp_gguf.py` and turns "wiring not started" into a concrete plan
with the pattern to mirror.

## The pattern

The MTP serving route is a **provider the generator delegates to**, not logic inside the
generator.

`hipengine/generation/engine_loop.py:565`:

```python
def supports_speculative_mtp(self) -> bool:
    supports = getattr(self._inner, "supports_speculative_mtp", None)
```

so the outer loop asks the inner generator, and the inner generator's answer is a property
over an attached provider. From `hipengine/generation/qwen4_exp_gguf.py`:

```python
@property
def supports_speculative(self) -> bool:
    return self._speculative_provider is not None

@property
def supports_speculative_mtp(self) -> bool:
    return self.supports_speculative

def attach_speculative_provider(self, provider: Any) -> None:
    self._require_open()
    if self._speculative_provider is not None:
        raise RuntimeError("Qwen4Exp generator already has a speculative provider")
    self._speculative_provider = provider

def generate_speculative_detailed(self, request):
    if self._speculative_provider is None:
        raise NotImplementedError("Qwen4Exp speculative provider is not attached")
    return list(self._speculative_provider.generate_detailed(request))

def generate_speculative_mtp_detailed(self, request):
    return self.generate_speculative_detailed(request)
```

**The generator is thin. All the work is in the provider.**

## What Gemma 4 needs, in four steps

1. **Add the provider plumbing to the Gemma 4 generator** (`SubmitPollTextGenerator`,
   `hipengine/generation/engine_loop.py`): `_speculative_provider`,
   `supports_speculative`, `supports_speculative_mtp`, `attach_speculative_provider`,
   `generate_speculative_detailed`, `generate_speculative_mtp_detailed`. This is a
   mechanical mirror of the Qwen4Exp code above.
2. **Write a Gemma 4 MTP provider.** This is the real work: it implements the
   draft -> verify -> commit loop behind `generate_detailed(request)`. **The pieces
   already exist** -- `Gemma4MtpDrafter` and `Gemma4Runner` in
   `hipengine/runtime/gemma4_assistant.py` and `hipengine/runtime/gemma4.py`, driven
   together today by `scripts/gemma4_mtp_acceptance.py`, and `hipengine/speculative/`
   supplies `DraftBatch`, `TargetVerifyBatch` and `TargetCommitPlan`.
3. **Attach the provider** where the engine builds the generator, so the route is reachable
   from `hipengine.LLM` rather than only from a harness.
4. **Verify through `LLM.generate_speculative_mtp_detailed()`** on the real artifact, with
   a generated-token-count assertion, and compare against `LLM.generate()` for the speedup
   that `20260928T073254` could not measure.

## Sizing

Step 1 is small and mechanical. **Step 2 is the work**, and it is the step that turns the
measured 0.796 acceptance into a decode speedup or shows it does not. Steps 3 and 4 are
small once 2 exists.

The important consequence for the objective: **the hard component -- a drafter that beats
llama.cpp at three of four positions -- is already built and measured.** What is missing is
the loop that consumes it, not the drafter.
