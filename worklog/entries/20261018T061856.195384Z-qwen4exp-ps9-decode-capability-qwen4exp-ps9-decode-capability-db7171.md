# Publish the decode route and AR batch envelope in capabilities from the shared probe

## Summary

The capabilities manifest did not mention the decode route at all. A client
could only discover the opt-in Flash-Next AR batch path, its width bound, or its
position bound by calling `/v1/hipengine/decode` after a request had already
selected a path, or by reading source. That is the PS9 gap where an advertised
capability does not match execution.

Both surfaces now call one probe, so they cannot disagree, and capabilities
publishes the build's qualification envelope before the first request. A
provider whose telemetry carries no batch key reports `ar_batch: null` instead
of inheriting the Flash-Next envelope, and an unusable
`HIPENGINE_QWEN4_EXP_AR_BATCH_SLOTS` value is reported rather than turned into a
manifest failure. The request path still refuses to serve with that value.

No runtime, default, dispatch, capacity, or MTP route changed. No performance
claim is made.

## Changes

- `hipengine/server/api.py`: extracted `_probe_decode_telemetry(engine)` from
  the `/v1/hipengine/decode` handler, so the endpoint and the manifest share one
  implementation and one failure taxonomy. Added `_decode_capability_summary`
  and wired it into the capabilities payload as a top-level `decode` key beside
  `admission` and `parallelism`.
- `tests/test_unit_server_decode_capabilities.py`: new unit file, 16 cases over
  the shared probe and the summary. Covers a missing hook, the generator hop and
  a direct engine hook, non-mapping payloads, a raising hook whose message must
  not leak, the uninitialized envelope, the switch and a valid width, three
  invalid width values, live state pass-through, a provider without the batch
  key, an unavailable probe, and that the summary goes through the shared probe.
- `tests/test_integration_server_api.py`: extended the existing decode-telemetry
  test to assert the manifest reports the same path and the same live batch
  snapshot as the endpoint, that the qualified bounds are published, and that an
  engine without the hook advertises no path.
- `docs/API.md`: the capabilities row mentions the decode route, and the decode
  telemetry section documents the manifest mirror and its field meanings.
- `docs/QWEN4EXP-PRODUCTION-SERVING.md`: PS9 records this unit as done and names
  what remains open.

## Validation

```bash
uv run pytest -q tests/test_unit_server_decode_capabilities.py
# 16 passed

uv run pytest -q tests/test_unit_server_*.py tests/test_integration_server_api.py \
  tests/test_integration_server_speculative_provider.py
# 736 passed, exit 0
```

The second bundle is the narrow server-surface gate: the refactor touches the
decode endpoint that every `/v1/hipengine/decode` consumer uses, so the whole
unit-server and server-integration files were run rather than only the new test.

No GPU was used. The tests drive fake engines; the live Flash-Next server was
not started for this unit, so the manifest has not been read from a real
Qwen4Exp process yet. The next live HTTP run reads it.
