# P6's premise checks out, and the dense projections are separable by construction

## Summary

`docs/campaigns/GEMMA4-26B-A4B-PUNCHLIST.md` P6 proposes concatenating
q/k/v and the shared-MLP gate/up into one weight each at load, cutting 412
dense launches per 1024-token prefill toward ~180 for an estimated 5–15 ms.
Iteration 18 flagged its row-count premise as unverified. It is verified, and
the answer is better than the row assumed.

## Finding: the concatenation has no shape obstacle

The concern was grouped-query attention: if k and v have fewer heads than q,
the matrices have different output dimensions and a flat merge would not
apply. It does not need to. A fused QKV projection stacks the three weights
along the **output** axis — `X @ [Wq; Wk; Wv]` — so the output dimensions
simply add. Equal row counts are never a precondition, and a ragged KV head
count changes the fused width, not whether it can be fused.

Concretely, `hipengine/models/gemma4.py` declares all three separately
(`attn_q.weight`, `attn_k.weight`, `attn_v.weight`, lines 32–34) plus
separate `ffn_gate.weight` / `ffn_up.weight` (lines 40–41), so the artifact
really does carry them split and the concatenation would be a load-time
materialization — which is what the row's "must be a replacement layout, not
an added copy" constraint is for.

## Finding: the codebase already fuses both shapes elsewhere

- **Experts are already fused.** `blk.{layer}.ffn_gate_up_exps.weight`
  (line 49) is a single gate/up tensor for the MoE experts, while the dense
  MLP's `ffn_gate` and `ffn_up` are still two. P6 is bringing the dense path
  to a layout the same file already uses one line further down.
- **A fused QKV weight is already on the tuning record.**
  `hipengine/kernels/hip_gfx1100/__init__.py` line 352 carries
  `attn_qkv (10240, 5120) 84.5 -> 57.8 us` — a 5120-hidden layer whose Q, K
  and V outputs total 10240, i.e. exactly the ragged-GQA concatenation above.
  The kernel path for that shape exists and has been measured.

### A correction to my own first read

I initially cited `_linear_qkv_width` in `hipengine/loading/qwen35_gguf.py`
(line 1424) as a general fused-QKV precedent. **It is not.** The definition
is `2 * config.ssm_group_count * config.ssm_state_size +
config.ssm_inner_size`, and it appears alongside `ssm_conv1d` — it computes
the *linear-attention (SSM)* input width for Qwen3.5's hybrid layers, not an
attention QKV. The real precedents are the two listed above. Recorded here so
the next reader does not repeat the same over-read.

## What P6 would need

1. Load-time materialization of the fused tensors for Gemma 4 — allocate the
   combined buffer, copy, and drop the originals so memory is transiently
   higher but flat afterwards.
2. The dense MLP already has a fused counterpart in-tree, so its half is the
   more routine change.
3. Attention's projection call sites must consume one output and slice it,
   rather than calling three kernels.
4. A check that the launch-count saving is real. 412 → ~180 is the row's
   figure and has not been recounted against the current tree.

None of this touches arithmetic: stacking weights along the output axis
computes the identical products, so no numerical gate is required — only the
memory constraint (iteration 89's load-time repack warning) and the sanity
bar.
