# Reproducible IKV-C2 packed-ownership trace generator

## Summary

The IKV-C2 primitive gate requires `rocprofv3 --kernel-trace` evidence that the
row-batched INT8 split-K producer and its strided gated reducer each launch once
for all rows while the c1 leaf launches once per row. That is the evidence which
shows the packed consumer is genuinely row-batched rather than a loop of c1
launches, and it was the only IKV-C2 gate artifact without a committed
generator: `benchmarks/results/2026-09-11-w7900-ikv-c2-batch-decode-ownership-trace.json`
had been assembled by an ad-hoc parser that no longer existed.

That mattered beyond reproducibility. The artifact had frozen the *pre*-promotion
capability snapshot (`admitted_max_direct_rows` 1, capability `3a105595…`) while
sitting in the evidence set for a promotion to physical c4, so a reader
cross-checking the trace against the capability would find a contradiction. A
hand-edit would have fixed the number once and let it drift again.

`scripts/qwen38_int8_batch_decode_ownership_trace.py` now produces the artifact,
and it resolves the capability snapshot live from the model registry, so the
field cannot go stale again. All measured numbers are unchanged.

## Changes

- `scripts/qwen38_int8_batch_decode_ownership_trace.py` (new). Runs
  `rocprofv3 --kernel-trace --output-format csv` over the `c4-ragged` case of
  `tests/test_qwen38_int8_batch_attention_gpu.py`, reduces the CSV to the
  compact artifact, and supports `--trace-dir` for parse-only regeneration with
  no GPU run.
  - Profiling protocol per `docs/KERNELS.md`: the JIT cache is warmed by an
    unprofiled gate run and the profiled run sets
    `HIPENGINE_REQUIRE_CACHED_BUILD=1`, so an accidental `hipcc` spawn inside the
    profiler fails instead of corrupting the trace.
  - Classification maps kernel names to `batch_producer` / `batch_reducer` /
    `c1_producer` / `c1_reducer`, with the batch patterns matched first.
  - `summarize_ownership` *refuses* rather than certifies: a batch producer or
    reducer that did not launch exactly once, a c1 leaf that did not launch once
    per row, a missing packed path, or a c1-only width all raise.
  - `capability_snapshot` resolves the live INT8-KV capability via
    `Qwen35GGUFModel().resolve_kv_capability(...)`, so the artifact records the
    currently admitted width.
  - `--trace-command` records the command that produced an existing trace, so a
    parse-only regeneration keeps its provenance; the artifact separates
    `command` (how the trace was taken) from `reduction` (how it was reduced).
- `tests/test_qwen38_int8_batch_decode_ownership_trace.py` (new, 21 tests).
  Covers classification (including that the batch producer is not misread as the
  c1 leaf), CSV reduction and its error paths, the summary arithmetic pinned to
  the retained measured durations, every refusal case, and two drift guards: the
  generator's `GATE_CASES` table must match the primitive gate's `parametrize`
  table, and the committed artifact must re-derive to its own stored blocks.
- `benchmarks/results/2026-09-11-w7900-ikv-c2-batch-decode-ownership-trace.json`
  regenerated from the retained trace in `/tmp` (parse-only, no GPU run). The
  capability block moves to the promoted snapshot
  (`admitted_max_direct_rows` 4, capability `4b0e936f…`), matching the cwidth
  promotion artifact. `vgpr_count` becomes a typed integer instead of a raw CSV
  string; the trace `command` is preserved verbatim and a new `reduction` field
  records that this regeneration parsed an existing trace. Every other field is
  byte-identical, including all launch durations.
- `benchmarks/HARNESSES.md` gains the generator's catalog row.
- `benchmarks/CHANGELOG.md` gains a dated line recording that no metric changed.

## Validation

CPU-only; no GPU run was needed because the retained rocprofv3 CSV was still on
disk and the generator can parse it directly.

- `uv run pytest tests/test_qwen38_int8_batch_decode_ownership_trace.py -q` ->
  21 passed.
- Fidelity against the existing artifact, parse-only: the derived `ownership`
  and `kernel_time_ns` blocks are *equal* to the committed ones
  (batch 75,562 ns over 2 launches vs c1 leaf 245,921 ns over 8, ratio 3.255;
  producer grid `[1024, 5, 4]`, reducer grid `[6144, 4, 1]`), as are `schema`,
  `kind`, `performance_claim`, `host`, and `workload`. The only launch-field
  difference is `vgpr_count` `"64"` -> `64`.
- Mutation RED: disabling the "batch producer and reducer launch exactly once"
  guard made `test_summary_rejects_a_per_row_batch_path` fail with `DID NOT
  RAISE ValueError`. Source restored and re-green.
- CLI error paths exercised without a GPU: a missing trace directory, a c1 case
  against a 4-row trace (`only meaningful above c1`), and an unknown `--case`.
- Related suites (packed-owner chunk flush, INT8 KV capability, INT8 transition
  gate, packed verify layout, server cwidth probe, GGUF sampling): all passed,
  1 skipped.
- `uv run pytest --collect-only` -> 13,283 tests collected (up 21), no
  collection errors.
- `python3 scripts/sync_benchmark_readme.py --check` -> synchronized.

## Next

- The trace is still c4-ragged only. A c8 case would need a `GATE_CASES` entry
  and a re-run; nothing in the gate requires it, since the width-4 geometry
  already demonstrates the single-launch-per-group property.
- Unchanged IKV-C2 limitations: packed decode graphs and the MTP spec target
  graph require BF16 KV, and batched prefill stays IKV-C3-blocked.
