# P5 is refuted, which closes the whole MMQ-tile group (P4 + P5)

## Summary

P5 ("single-plane int8 MMQ for the dense Q8_0 projections") is **closed as
refuted**, and with P4 already closed this run the punchlist's MMQ-tile group
— `docs/campaigns/GEMMA4-26B-A4B-OPTIMIZATION.md` line 491 calls them
"P4-P5 (MMQ tiles)" — is now entirely dead.

The refutation is stronger than the dead-ends table implies, because it is not
about guard planes at all. P5's row argued it was "structurally different"
from the refuted three-plane `d4x3` chain, and that is true — and irrelevant.
**Iteration 150 refuted the single-plane path itself by making it run.**

## What iteration 150 actually did

The dense int8 MMQ route had been configured for Gemma4 but **never launched
a kernel**. Iteration 148 ruled out policy and tensor types; iteration 150
found the exact mechanism:

- `_wmma_prefill_dispatch` (line 3410) rewrites a raw Q8_0 dispatch to
  `abi="wmma_raw"` / `variant="wmma_prefill_bf16_bf16_out"`
- `_q8_mmq_prefill_dispatch` (line 3471, runs **second**) matches on
  `abi == "raw"` and `variant == "prefill_bf16_bf16_out"` — both miss
- All 680 admitted dispatches were rejected **on a key mismatch, not on
  policy**

Moving the MMQ dispatch ahead of the WMMA rewrite made it fire. And firing it
was:

| | tok/s |
| --- | --- |
| before the reorder | 1373 / 1367 / 1367 |
| after the reorder | **1054 / 1056 / 1053** |

**29% slower** — while the gate passed and `kl_max` *improved* (0.000893
against 0.001341 for the WMMA route). The int8 kernel is correct, arguably
more accurate, and simply loses to bf16 WMMA on Gemma4's dense projection
shapes. Iteration 155 independently prices the penalty at **+0.25 s per
prefill**.

Iteration 150's own conclusion: *"the only thing wrong with the dead path was
that it looked dead"*, and the dispatch ordering that keeps it unreachable is
**load-bearing** — nothing in the code said so, and only making it fire and
measuring revealed it.

## The estimate class, not just the route

P5's comparator cell read **"115.6 ms against 59.0 ms (2.0x)"**, and that is
the specific reasoning iteration 150 killed: the figure came from comparing an
MMQ TFLOP/s against a bf16 WMMA rate. The measurement does not support it for
these shapes, and iteration 150 says in terms that **"that estimate should not
be reused."**

This matters beyond one row. P4's opening inference this same run made the
equivalent mistake — it read distance from peak as evidence the reachable gap
was shaped like the lever in hand — and P4 was closed on the same day for the
same reason. Two rows, two independent restatements of one rule: **a TFLOP/s
or TOPS comparison against a peak is a prompt to investigate, never a
justification to build.**

## What remains open in this family

**P6 — concatenate q/k/v, and the shared-MLP gate/up, into one weight each at
load** (est. 5–15 ms, unmeasured; 412 dense launches per 1024-prefill).

P6 is *not* another MMQ tile. It changes weight layout and launch count, not
the compute path, so none of iterations 89, 150 or 155 bear on it. The row
already carries the right constraint — "this must be a replacement layout,
not an added copy" — and iteration 89's warning about load-time repack cost
is the thing to watch.

Its feasibility is unverified. Step one for whoever takes it is to confirm
q, k and v share row counts in this artifact (if the model uses grouped-query
attention with fewer KV heads, they do not, and the concatenation needs a
different shape than the row assumes).
