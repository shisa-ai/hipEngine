# UD prefill is 12x slower than plain Q4_K_S on the same model: it never reaches the WMMA GEMM prefill family

## Summary

Prompted by the question "is our prefill really at 13 tok/s, isn't Q4_K_M/S at
like 500?". It is really 13, and the comparison is the right one to make. On
the **same model, same GPU, same harness, same 512-token shape**:

| File | Prefill | Decode | GPU time for one 512-token prefill |
| --- | ---: | ---: | ---: |
| `Qwen3.8-27B-Q4_K_S.gguf` (plain) | 160.5 tok/s | 12.56 tok/s | 3,320 ms |
| `Qwen3.8-27B-UD-Q4_K_M.gguf` | 13.77 tok/s | 4.22 tok/s | 37,299 ms |

**11.2x more GPU time**, matching the 12x wall-clock gap, so this is device
work and not host overhead. This reframes the raw-IQ optimization campaign:
every win in it so far is a win inside the slow regime.

## Evidence that this is not a harness artifact

- Decode on the plain file measures 12.56 tok/s against the published
  scoreboard row of 13.1 for the same model/quant/GPU, so the harness agrees
  with published protocol on decode.
- The row-slab A/B reports exactly 1.00x on the plain file, which is correct:
  that file has no raw IQ tensors for the row tile to affect.
- Both arms were measured in the same process against one resident model.

## Changes

No code change. This entry records a measurement and the queue
reprioritization that follows from it.

## Mechanism

rocprofv3 kernel census, 512-token prefill, matched shape.

Plain `Q4_K_S` reaches the GEMM family:

| Calls | ms | Share | Kernel |
| ---: | ---: | ---: | --- |
| 12 | 1703.3 | 51.3% | `qk_t16_selected_direct_gemv_kernel<*,5,...>` |
| 212 | 687.2 | 20.7% | `gguf_q4_t16_dense_wmma_prefill_shared_b_bf16_kernel` |
| 64 | 599.3 | 18.1% | `gguf_q4_t16_dense_dual_wmma_prefill_silu_bf16_kernel` |
| 192 | 50.2 | 1.5% | rocBLAS Tensile `Cijk_...MT128x128x32_MI16x16x16x1` |

UD `Q4_K_M` is entirely on GEMV-shaped kernels:

| Calls | ms | Share | Kernel |
| ---: | ---: | ---: | --- |
| 131 | 15641.5 | 41.9% | `gguf_k_prefill_out_rowbatch_kernel<*,*,5,32>` (Q5_K) |
| 117 | 9250.0 | 24.8% | `gguf_iq_dense_strict_kernel<0,true,8,8>` (IQ4_XS) |
| 93 | 7547.4 | 20.2% | `gguf_q4_k_pack8_prefill_out_kernel` |
| 5 | 1731.4 | 4.6% | `gguf_q4_k_pack8_dual_prefill_out_kernel` |

The decisive detail is the third row: **even the Q4_K tensors inside the UD
file miss the WMMA prefill kernels** and land on `pack8_prefill_out`. So this
is not "IQ kernels are slow". It is a layout/route property of the UD path as
a whole: the WMMA prefill family requires the T16 repacked layouts
(`LAYOUT_GGUF_Q4_K_T16` and siblings), and UD tensors are resident as
`LAYOUT_RAW_GGUF` or pack8.

A GEMV-shaped prefill re-reads the weight matrix once per row block; a GEMM
reads it once. The row tile landed earlier today cut the number of passes by
8x, which is why it bought 1.79x. Routing UD prefill onto the GEMM family
changes the exponent, not the constant.

## Also recorded: the plain path is itself below its published row

The same harness measures the plain file at 160.5 tok/s prefill where the
scoreboard publishes 396.1 for that model/quant/GPU. Decode agrees, prefill
does not, so there is a second and separate route/protocol gap on the
`Qwen35GGUFResidentSession.prefill(use_bulk=True)` path — most likely
`use_wmma_prefill`, which is opt-in (`HIPENGINE_GGUF_WMMA_PREFILL`,
`PrefillConfig.use_wmma_prefill`). **The 160.5 figure is therefore a floor on
the plain path, and the true UD headroom is larger than 12x.** No claim is
made here about which protocol the published row used; that has to be
reconstructed before either number is quoted as a comparison.

## Validation

Both arms measured in one process against one resident model, alternating,
best-of-2 rounds after a warm round each. Kernel censuses taken with
rocprofv3 `--kernel-trace` on prebuilt `.so` files with
`HIPENGINE_REQUIRE_CACHED_BUILD=1` and an explicit compiler-version file, at a
matched 512-token prompt for both files. The harness is cross-checked against
the published scoreboard on decode for the plain file (12.56 measured vs 13.1
published).

## Decision

The raw-IQ decode queue (B4 payload dword loads, further LDS work) is
**deprioritized** below the prefill route question. The remaining decode items
are worth at most tens of percent inside a regime that is an order of
magnitude off the sibling path.

New top of queue, in order:

1. **Reconstruct the published 396.1 tok/s protocol** for plain
   `Qwen3.8-27B-Q4_K_S` and re-measure the UD file under it. Both numbers above
   may move; the ratio is what matters and it should be re-established under
   the published protocol before any of this is quoted.
2. **Determine why UD Q4_K tensors do not reach `gguf_q4_t16_dense_wmma_prefill_*`.**
   This is a materialization/layout question (T16 vs raw/pack8) in
   `qwen35_gguf_materialize.py` and `qwen35_gguf_consumer_surface.py`, not a
   kernel question. It is also the cheapest of the three, because those
   kernels already exist and are qualified.
3. **A5, dense entry point over the existing IQ integer-MMQ prefill kernels**
   (`gguf_iq_source_mmq_prefill.hip`, `gguf_iq2_xs_mmq_prefill.hip`), which
   exist and are correctness-tested in selected/MoE shape only. This is the
   IQ-side equivalent of item 2.

## Next

Items 1-3 under **Decision** above, in that order, on the desktop gfx1151.

## Caveats

zbook is power- and thermal-limited. The 11.2x GPU-time ratio comes from
kernel traces rather than wall clock, so it is robust to clock variation, but
the absolute rates are provisional and all three items above should be
re-measured on the desktop gfx1151.
