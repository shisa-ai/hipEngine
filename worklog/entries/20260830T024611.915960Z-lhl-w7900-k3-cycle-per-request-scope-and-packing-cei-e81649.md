# W7900 Qwen3.8: K3 cycles are per-request in source, bounding wave-packing headroom at about 1.49x by C8

## Summary

The K3 cycle is built **per request** in source, so wave packing is a real and
specific gap. But its ceiling is modest: a perfectly wave-packed cycle is worth
about **1.49x** at C8 (47.1 vs the measured 31.6 tok/s), while the peer row is
94.7 -- so acceptance, not packing, is the dominant half of the MTP table.

## Changes

- Scoping only; no code changed.

## Validation

Call site: `hipengine/generation/qwen35_gguf.py:4044` binds
`session.run_native_spec_mtp_cycle` and invokes it with a single
`root_token=prev_token`, `root_position=seq_position`, `remaining_decode` and
per-request draft KV state -- one cycle per lane, inside the per-request
generation routine. Consistent with that, the spec target-graph cache is
per-session (`hipengine/runtime/gguf_native_spec_cycle.py:464`
`_native_target_graph_cache(session)`, keyed `(rows, bool, context_bucket)`), and
the graph names seen in route telemetry are budget-scoped
(`_native_spec_b1/b2/b3_target_graph`, `gguf_native_spec_cycle.py:1479-1484`), not
wave-scoped.

Why that costs time: decode-side GEMMs at these sizes are weight-streaming-bound,
so a 4-row verify costs roughly what a 32-row verify costs. Eight lanes each paying
their own draft-pass chain plus their own small verify is therefore close to pure
waste; the measured cycle cost ratio 2.95 (C1) to 5.95 (C8) AR steps says substantial
sharing already happens somewhere (packed decode steps and graph replays are both
non-zero in the C8 telemetry), but the cycle is still priced at ~6 steps.

Ceiling estimate, stated as an estimate: if the wave paid four passes total
(three draft rounds + one 32-row verify), C8 cycle wall would be 4 x 82.2 / 8 =
411 ms of wave work, i.e. 8 x 1.933 wave tokens per 329 ms = **47.1 tok/s** against
the measured **31.6**, a **1.49x** headroom. The same model run at C1 predicts
*slower* than measured (0.74x), so the four-pass model is crude and only useful
directionally at C8 -- it is not a prediction of the implementation's result. The
comparison that matters: peers reach 94.7 at C8, roughly 3x our measured row, which
no packing of the current cycle can close while our cycle yields 1.93 tokens.

Priority read across the open tasks: the prefill submodule is 0.37x of peers by C8
and is worth an estimated 2441 -> ~855 ms of C8 admission, so it is a larger and
better-bounded prize than K3 packing; acceptance work remains the only route to the
peer K3 rates.

Method notes (process defects I hit and fixed, so the next session does not repeat
them): the runner's completion marker is `arm packet done rc=0` in the **wrapper**
log -- `CHAIN_EXIT` never appears in the arm log, and grepping for it there produced
one false completion claim. And `pgrep -f "scripts/gguf_..."` matches the waiting
wrapper's own command line, which deadlocked two queued runs until they were killed;
use the bracket form `pgrep -f "[g]guf_..."` or verify idleness and chain in one job.
