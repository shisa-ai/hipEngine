# the tiled prefill variant is 2.4x faster at long context and slower at 2048 tokens exactly as the corrected analysis predicted

## Summary

The tiled production variant is **correct and measured**. It is **2.4-2.5x faster than the
strict kernel at 8192 and 15872 keys**, and **slightly slower at 2048 keys**. That split is
exactly what `20260928T073811` and `20260928T074535` predicted once the LDS-traffic claim was
withdrawn, and it means the artifact's 2048-token measurement point is not the case this change
helps.

## Correctness

Against the strict kernel, same inputs, bf16:

| shape | bit-exact | maxrel |
|---|---|---|
| dense 256d keys=1024 tokens=8 | 100.0% | 0 |
| dense 256d keys=2048 tokens=64 | 100.0% | 1.51e-03 |
| dense 512d keys=1024 tokens=8 | 100.0% | 0 |
| odd keys=1000 | 100.0% | 0 |
| swa window=1024 keys=2048 tokens=64 | 100.0% | 0 |

**5 of 5 pass.** The `keys=2048` row is the only one with two tiles and therefore the only one
where the rescale runs; it is still 100% bit-exact at bf16 width, with a maxrel of 1.5e-03 --
last-bit territory, and a mean relative error of 6e-09.

**The harness guard is the fix from `20260928T074535`:** the sticky HIP error is cleared between
launches and the test **asserts the reference kernel's output is nonzero before comparing**.
Without that it reported four failing shapes as bit-exact.

## The measurement

`device_synchronize()` around each launch -- the first run without it reported 43 TFLOP/s,
which is launch time, not execution time.

| case | strict ms | tiled ms | speedup |
|---|---|---|---|
| swa 256d keys=2048 tok=2048 | 56.70 | 62.22 | **0.91x** |
| dense 256d keys=2048 tok=2048 | 116.30 | 118.39 | **0.98x** |
| dense 512d keys=2048 tok=2048 | 229.87 | 216.83 | 1.06x |
| **swa 256d keys=8192 tok=8192** | 1340.96 | 546.20 | **2.46x** |
| **swa 256d keys=15872 tok=15872** | 4046.79 | 1688.89 | **2.40x** |

## What the numbers say

**The 2048-key row is a single tile, so there is no occupancy benefit and the tiling only adds
barriers -- and it shows: 0.91x, a 9% regression.** That is the artifact's own measurement
point, and **this change does not help it.** The correction in `20260928T074535` predicted
exactly this, and `20260928T073811` had already established that 2048 keys gets six blocks per
CU, so there was no occupancy to recover there.

**At 8192 keys and above the strict kernel collapses.** Its own scaling shows it: **71x more time
for 7.75x more keys** (56.70 ms at 2048 to 4046.79 ms at 15872). The tiled kernel's scaling is
**27x for the same 7.75x** -- still superlinear, but the collapse is gone. **That is the
footprint effect: the strict kernel's 34 KiB at 8192 keys and 64 KiB at 15872 keys allow one
block per CU; the tiled kernel's 7 KiB allows six at any context.**

**So the variant's benefit is real, large, and confined to long context.** It is not a fix for
the artifact's headline number.

## Scope of the claim

- **Attention-isolated, single-launch, gfx1151, synthetic inputs.** Not end-to-end prefill, and
  not a llama.cpp comparison at long context.
- **The tiled variant reassociates**, so it is a production candidate: the strict kernel is
  unchanged and keeps the bit-exact gate.
- **No end-to-end prefill number is claimed**, and the artifact's 2048-token figure is unchanged
  by this work.

## Changes

`hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention.hip`: adds
`gemma4_attention_prefill_tiled_kernel<scalar_t, kTile, kDPerThread>` (`kTile = 1024`),
`launch_gemma4_attention_prefill_tiled`, and the two `extern "C"` entry points
`hipengine_gemma4_attention_prefill_tiled_bf16` / `_f32`. **The `extern "C"` wrappers are what
instantiate the templates**; without them a build passes without compiling the new code.
The strict kernel and its launcher are untouched.

**Phase 3 is split** -- 3a computes weights strided over the tile and writes them back over their
logits, keeping `running_sum` a per-thread *partial* so the final block sum is correct; 3b has
**every thread visit every key**, because the output element a thread owns needs the weight of
every key rather than the strided subset it computed. Merging the two was the defect in
`20260928T074435`.

## Validation

Build via `build_gemma4_attention(load=True)`: OK, both symbols present, only pre-existing
warnings. Correctness: 5 of 5 shapes pass with the reference-nonzero guard. Timing:
`device_synchronize()` per iteration, median of 2-5 iterations, on gfx1151.
