# MTP finish rule: stop ids, sequences and the EOS floor through the cycle commit

## Summary

Task 6. The sampled MTP route serves the four finish-rule request fields
(`min_tokens`, `eos_token_id`, `stop_token_ids`, `stop_token_sequences`) instead
of refusing them, and this unit is the live measurement that says so.

The rule itself landed earlier, on 2026-09-21 in `e3a553f9a`: the cycle commit
applies the autoregressive finish rule to the whole verified chain through
`limit_chain_accept_finish`/`chain_finish_index`
(`hipengine/speculative/streaming.py`), selecting the terminal prefix, and the
four fields moved back into `SAMPLED_MTP_SERVABLE_BLOCKERS`. What did not land
was the evidence. The readiness checklist still read "Explicit text-stop MTP
currently returns a 501 sampling-capability error", and `docs/REFACTOR.md` still
listed the blockers as open pending "a finish-rule gate, not just the
induced-law gate". Both statements were stale against the code, and the live
half had never been run: the same GTT resource conflict that blocked the sampled
acceptance blocked this one.

This unit lands the gate those documents asked for, measures both KV cells with
it, and closes both statements.

## Changes

- New `scripts/mtp_finish_rule_gate.py`. It takes a seeded free trajectory from
  the running server, then places a stop at each *distinct* token of that
  trajectory and requires both the speculative and the autoregressive arm to
  publish exactly that prefix, to report `finish_reason=stop` and
  `finish_details.reason=stop`, and to publish nothing after the stop. It
  repeats that for a multi-token stop sequence, checks that `eos_token_id` fires
  `eos` at or above `min_tokens` and withholds the token below the floor, and
  checks that a request which stops early leaves a concurrent neighbour's
  published ids unchanged. It is storage-neutral and takes `--expect-storage`
  so a run pins the cell it measured; it refuses a server running the rejected
  capability under the KV diagnostic override unless
  `--allow-kv-diagnostic-override` records that explicitly.
- New `tests/test_unit_mtp_finish_rule_gate.py`, 19 cases. Each check is driven
  against a fake server that violates exactly one thing -- a stop that
  overshoots its chain, a stop that publishes the whole chain, arms that
  disagree about the prefix, a token published off the trajectory, a finish
  reason that is not the stop, an EOS that fires for another rule, an EOS token
  emitted below the floor, an EOS floor that stops anyway, a neighbour whose
  cursor moves, a trajectory too short to sweep -- and the harness confirms each
  named check actually fires.
- `docs/reference/INT8-MTP-SERVER-READINESS.md`: the "stopping inside an
  accepted draft chain" checklist item is closed, the open-items sentence no
  longer lists INT8 text-stop MTP, and the gate command and description are
  added.
- `docs/REFACTOR.md`: the sampled-route finish-rule blocker paragraph is marked
  resolved, with the gate and evidence named.
- `docs/reference/SAMPLING.md`: the sampled-MTP section said "token-stop
  constraints ... fall back to ordinary decoding"; they are served by the commit
  now, so the sentence names the finish rule instead.
- Artifacts:
  `benchmarks/results/2026-09-22-gfx1151-qwen38-int8-mtp-finish-rule.json` and
  `benchmarks/results/2026-09-22-gfx1151-qwen38-bf16-mtp-finish-rule.json`.

## Validation

Both cells, through `/v1/completions`, on a 40-token seeded free trajectory:

| Check | INT8 (`int8_per_token_head`) | BF16 |
| --- | --- | --- |
| Distinct stop positions swept | 12 | 12 |
| Rows that ran real draft cycles | 11 | 11 |
| Stops that matched at their build position | 11 | 11 |
| Multi-token stop sequences | 6 | 6 |
| EOS-floor rows (at/above, below) | 2 | 2 |
| Neighbour ids unchanged under concurrency | yes | yes |

Every row published a prefix of the trajectory ending at or before the stop,
with `finish_reason=stop` and `finish_details.reason=stop`, on both arms. The
one row that did not speculate is the `' twenty'` stop, which matches the first
generated token (it is a prefix of `' twenty-one'`), so no chain can exist; the
gate records that exemption per row rather than skipping the row, and still
requires the finish and parity checks there.

The EOS floor is a paired A/B on the same seed and EOS token: at or above the
floor the request finishes at the EOS token with `finish_details.reason=eos`
(14 published tokens, matching the free prefix); below it the route withholds
that token, emits a different tokenization of the same text, and continues past
the position (35 published tokens, with the withheld token absent before the
floor).

Repeatability: a second full run of the gate on the same server produced the
same free trajectory, the same per-stop published and cycle counts, the same
EOS-floor rows, and the same neighbour ids. Cross-cell: the free trajectory and
every stopped prefix were identical on INT8 and BF16; cycle counts differed in
one row (7 vs 8) while the published ids did not, so published output is the
reproducible quantity across cells, not cycle timing.

Unit tier: `tests/test_unit_mtp_finish_rule_gate.py` 19 passed. Documentation
gates: `python3 scripts/docs/check_all.py` all 4 passed.

Two limits stated rather than implied. The INT8 cell ran under the documented
diagnostic override, because the artifact's compact INT8 quality record is
rejected; the gate refuses an override server unless the flag is passed, and the
artifact records `diagnostic_override: true` rather than presenting the run as
qualified. And this is a correctness gate: it makes no speed claim, which is
task 20's to make.
