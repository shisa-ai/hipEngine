# the row-invariance regression test lands as two passes and two xfails pinning the two defects

## Summary

`tests/test_gpu_gemma4_expert_row_invariance.py` is new. It asserts the property
every existing test checks *around* rather than *for*: a token's expert output is
a function of that token, not of the other rows that share its block.

The coverage gap was real and specific. `tests/test_unit_gemma4_expert_route.py`
checks the preference order, the threshold
(`test_prefill_route_switches_at_one_lane_per_expert`) and which route runs at
`compact_rows=256`, `127` and below the crossover.
`tests/test_gpu_gemma4_expert_route_true_geometry.py` checks the MMQ tile walk at
the true projection geometry under two activation profiles. **None of them
compares the output across row counts.** Every test asks which route ran; none
asks whether the routes agree.

```
tests/test_gpu_gemma4_expert_row_invariance.py ..xx   [2 passed, 2 xfailed]
```

## What each case establishes

| case | result | meaning |
| --- | --- | --- |
| whole forward, MMQ route on | **xfail** | row 0 moves by 8192.0 when a row is appended |
| whole forward, MMQ route off | **xfail** | row 0 still moves, by 6144.0 -- the down defect |
| gate/up stage, MMQ off, two experts | **pass** | the gate/up stage *is* row-count invariant |
| gate/up stage, MMQ off, one expert | **pass** | same, single expert |

The two passes are what localize the gate/up defect to the **MMQ route**: with
that route off, the stage is invariant for both a one-expert and a two-expert
routing. The two xfails are the caller-visible failure and the second defect,
kept separate because they have different causes and different fixes.

## A test bug worth recording

The first version of the two-expert case was marked `xfail` and reported
`FAILED`, which read as a third defect. It was the test: `_gate_up_row_zero`
sliced `[:fused]` from a `(rows * 2, fused)` array, which takes *rows* rather
than elements, so the comparison was against a 2-D array and the `.view`
raised. With the slice flattened the case **XPASSes** under `strict=True`,
which is how the mistake surfaced -- `strict=True` turns an unexpectedly passing
test into a failure, and that is the reason to keep it on.

The corrected reading is in the table above. No third defect exists.

## Changes

- `tests/test_gpu_gemma4_expert_row_invariance.py` (new): a module-scoped
  fixture loading the fixture model, a `_forward_row_zero` helper and a
  `_gate_up_row_zero` helper that reads the real intermediate out of the
  layer's expert scratch, four cases, and an explicit HIP-availability guard
  (`ctypes.CDLL("libamdhip64.so")` + `pytest.skip`) so a no-ROCm runner skips
  rather than fails.

## Validation

- `uv run pytest tests/test_gpu_gemma4_expert_row_invariance.py -v` on the
  8060S (gfx1151): **2 passed, 2 xfailed**, exit 0.
- `--runxfail` on the same file shows the two xfails fail on the *invariant*
  (`AssertionError: row 0 moved by 8192.0000 when a row was appended` and `by
  6144.0000 with the MMQ route disabled`), not on an incidental error. That
  check is the reason the file was not committed on its first run, when all
  three cases failed with a `TypeError` from passing a buffer where a pointer
  was expected.
- `grep -c HIPENGINE_GAMMA4` is 0, confirming no misspelled environment name
  survives in the file.

## Next
