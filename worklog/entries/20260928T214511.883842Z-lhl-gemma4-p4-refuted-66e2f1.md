# P4 is refuted, and the inference that opened it was wrong

## Summary

P4 ("larger int8 MMQ tiles for the Q4_K gate_up") is **closed as refuted**,
and this entry corrects the reasoning in
`worklog/entries/20260928T214210.602945Z-lhl-gemma4-p15-p4-premise-855519.md`,
which is superseded by this one.

That entry measured the roofline correctly and then drew the wrong
conclusion from it. Both halves need stating separately, because the
measurement survives and the inference does not.

## What holds

Iteration 16's numbers are sound and stay on the record:

- `moe.gate_up` = 1.884 TFLOP in 114.1 ms = **16.51 TFLOP/s**, 22% of
  `docs/ROOFLINE.md`'s 75.3 TOPS measured INT8 WMMA
- weights stream at 73.5 GB/s = **9% of the 864 GB/s memory peak**
- arithmetic intensity **224.6 FLOP/byte against a 70.9 ridge point**

So gate_up is genuinely **compute-bound and nowhere near either peak**. It is
not bandwidth-bound, and iteration 126's bandwidth conclusion does not apply
to it. That much is unchanged.

## What does not

The entry then argued: not bandwidth-bound, far from compute peak, and a
2.40 time ratio against a 2.00 MAC ratio — **therefore the tile shape is
what's wrong, so build P4's bigger tiles.**

Reading the campaign record before writing any code showed that exact
inference had already been tested, four times:

| iteration | lever | result |
| --- | --- | --- |
| 101 | wider out-block at two accumulator footprints | **both regressions** |
| 102 | wider expert grid (uncapped `grid.y`) | neutral, no effect |
| 104 | input re-read fix (`COLS=4`, halves 8.1 GB to 4.05 GB) | **~4%, reverted** |
| 126 | rows-per-expert reuse | refuted |

The campaign's own summary of all four: *"Nothing that changes how the work
is **shaped** moves these kernels, and nothing that changes how much traffic
they move does either. Both sit at 2-4 TFLOPS against a device with ~61 TFLOPS
of fp32 and ~123 of WMMA fp16. The remaining explanation is the inner loop's
instruction mix and latency structure."*

**The error was treating distance from peak as evidence that the reachable
part of the gap is shaped like the lever I was holding.** Far from peak is a
necessary condition for a win, never a sufficient one — iteration 101 sits at
the same distance from peak and *regressed* when its shape was widened. The
2.40-vs-2.00 time ratio I offered as corroboration is consistent with a tile
defect but does not distinguish it from the latency/issue-bound structure
that iterations 101/102/104 actually found; I read a compatible signal as a
discriminating one.

**P4's `I = 64` candidate is literally iteration 101's wider out-block** at a
different label. That was the pre-stated stopping condition for this
iteration — "if J=64/I=64 is what those iterations already tried, close this
immediately" — and it fired on the first read.

## What is actually open on this kernel

Two things, both recorded in the campaign and neither needing a new
measurement:

1. **The WMMA compute path, measured at ~12%** (iteration 102: 598.36 →
   667.65 tok/s, 1.116x). It is held off the default path by the arithmetic
   gate and has an open lead decision about whether an absolute `kl_max` bar
   applies to a reordering-class change. Iteration 102 also flagged that its
   own figure is one run each against 8–9% environmental drift, so it needs
   repeats before being relied on.
2. **The inner loop's instruction mix and latency structure** — the
   campaign's stated explanation for why four shape/traffic levers all
   failed. Nobody has looked here yet.

The 2.7x figure the record carries for WMMA is stale; iteration 102 measured
1.12x and said so.
