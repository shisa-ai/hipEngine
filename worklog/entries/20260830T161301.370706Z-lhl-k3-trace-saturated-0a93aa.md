# K3 C8 trace: kernel time is 9.3x wall, consistent with a saturated device

## Summary

First `rocprofv3 --kernel-trace` of the GGUF K3 cycle at C8. It did not produce a clean
device-share number,
but it produced something more useful: total traced kernel time is **9.3x the measured
wall time**, which is
only consistent with lane-level device concurrency, i.e. a busy GPU. That argues against
a host-side stall
being the K3 C5-C8 problem, and against any cheap local fix.

## Changes

- No code change. The single-width MTP control script attempted for this was incomplete
  (`KeyError: 'ar'`:
  the harness cell reads `measured["ar"]["generated_ids"]` unconditionally, so patching
  `ARMS` alone is not
  enough) and was **deleted rather than left broken**. The working route was to trace the
  normal harness.

## Measured

`/tmp/he-mtp/tr8/mtp8_kernel_trace.csv` from `rocprofv3 -f csv --kernel-trace` around
`scripts/gguf_mtp_c1c8_server_bench.py --widths 8 --candidate-budget 3 --max-tokens 24`
(clean tracked source
at `e22031ad4`, cache prebuilt + `HIPENGINE_REQUIRE_CACHED_BUILD=1` per `docs/KERNELS.md`):

- 812,614 kernel rows, 3 duplicates, **56,282 ms** total traced kernel time.
- Same packet cell: AR arm wall 2,391 ms, MTP arm wall 3,658 ms, so 6,049 ms of measured wall.
- Ratio 9.3x. Top kernels by total time are decode/prefill GEMMs (`q4_k_t16_dense_r*`
  13,188 ms over 171,872
  launches; `q6_k_t16_qmicro_*` 11,455 ms over 47,580), not accept-window kernels.

## Reading, and its limits

- A sum of kernel durations can exceed wall only through concurrency. At width 8 with per-
  lane dispatch, ~8x is
  the expected order, and 9.3x is that order. The plain alternative reading - "the GPU is
  oversubscribed, this
  is a bug" - would be wrong: it is what speculative width looks like in a trace.
- What this does **not** establish: per-arm attribution. Both arms issue the same GEMM
  families, so kernel names
  cannot split the 56 s into AR and MTP, and without that split there is no defensible
  device-share percentage
  for the MTP cycle. The AR artifact carried `launches_total` plus named-kernel breakdowns
  precisely because
  this split needs to be done properly; that work is still open.
- Therefore #17's "is the accept window waiting on a busy device or an idle one" question
  is still not answered
  directly. What changed is the prior: 9.3x concurrency plus AR's measured 95% device share makes an
  idle-GPU-stall explanation unlikely, so effort should go to pipelining/capture rather
  than more host-side
  micro-tuning.
