# Size Gemma 4 prefill scratch by block, not context, so the default context loads

## Summary

The generator's default context is 8192, and it did not load. `Gemma4Runner`
sized every layer's prefill scratch from `max_block`, which defaulted to
`capacity`, so the scratch was a function of the context rather than of the
widest block actually forwarded. On the real 26B UD-Q4_K_XL artifact that is
52.68 GB of scratch at 8192 against 17.00 GB of resident blocks and 1.85 GB of
KV -- 71.5 GB in total, on a 48 GB device.

`forward` now chunks a prompt wider than `max_block` into consecutive blocks,
and `max_block` defaults to `DEFAULT_PREFILL_BLOCK = 512` instead of the
capacity. Chunking is exact: `_keep_mask` is built from absolute positions, and
a one-token-at-a-time path is already bit-identical to a dense prefill
(`test_incremental_decode_matches_a_dense_prefill`), which is the same
computation as a two-block split.

Measured on the real artifact at the default context: **23.21 GB peak VRAM**,
down from the 71.5 GB the same configuration needs when scratch is sized from
the context. That is a measured peak from `rocm-smi` sampled every 3 s during
the run, not an estimate.

512 rather than 1024 because the scratch difference is 3.29 GB against 6.58 GB,
and 3.29 GB is what keeps the default context inside a 24 GB card's budget; the
smaller block costs prefill speed on long prompts, which is the right trade for
a default that has to load before it can be tuned.

## Changes

- `hipengine/runtime/gemma4.py`: `DEFAULT_PREFILL_BLOCK = 512`; `max_block`
  defaults to `min(capacity, DEFAULT_PREFILL_BLOCK)`; `forward` validates the
  whole request and then forwards it as consecutive blocks through the new
  `_forward_block`, which carries the old body and keeps the
  `rows > max_block` guard.
- `tests/test_unit_gemma4_runner.py`:
  `test_a_prompt_wider_than_max_block_is_chunked_exactly` forwards a 12-token
  prompt through a `max_block=4` runner and compares against a single wide
  block, also asserting the position advanced by the full prompt.
- `scripts/gemma4_real_generate.py`: `--context` now defaults to the
  generator's own, `--long-probe-words` adds a probe long enough to cross a
  block boundary, and the run prints the runner's `max_block`.

RED was observed before the fix: the new test raised
`ValueError: 12 tokens exceeds max_block 4`.

## Next

`max_block` is not reachable from `LLM`; a caller with spare memory cannot trade
memory for prefill speed without constructing the runner directly. That is a
tuning knob rather than a missing capability, so it stays unplumbed until a
measurement shows the block size costs something worth recovering. The 24 GB
card is now inside the budget on paper (23.21 GB measured peak) but has not been
run.
