# Attention head shards materialize, and the local head indices are identity

## Summary

Step 1 of the head-sharding unit the 2026-09-23 attribution sized at 11.7%:
`hipengine/distributed/shard_weights.py` now materializes a second shard family,
attention, through the same payload path the dense MLP uses. Nothing on the
device path changed; this unit is host-side payload materialization plus the
tests that pin its geometry.

The load-bearing result is a correctness one. A sharded route only works if a
rank's materialized rows match the local head indices its kernels will use. They
do, with no remap table:

- **Full attention is a contiguous prefix.** `attn_q` rank 0 is source rows
  `[0, 6144)` (q-heads 0..11, one segment), rank 1 is `[6144, 12288)`;
  `attn_k`/`attn_v` rank 0 are `[0, 512)` (kv-heads 0..1), rank 1 `[512, 1024)`.
  So local head `j` is global head `rank * local_heads + j`, and the grouped-query
  ratio is preserved (`24/4 == 12/2`), so local q head `j` pairs with local kv
  head `j // 6` exactly as it does globally.
- **GDN value heads are tile-major**, `(0..7, 16..23, 32..39)` for rank 0, which
  is llama.cpp's `k_head = v_head % k_heads` order. That is precisely what makes
  the runner's identity local indexing correct: local value head `j` pairs with
  local key head `j % 8`, and
  `v_heads_for()[j] % 16 == k_heads_for()[j % 8]` holds for every `j` on both
  ranks. `GDNHeadMap`'s own docstring states this convention, and the test asserts
  the equation rather than trusting it.

So the plan in the previous checkpoint holds unchanged: substitute the uploaded
`ShardWeight`s plus a halved config (head_count 24 -> 12, head_count_kv 4 -> 2,
ssm_group_count 16 -> 8, ssm_inner_size 6144 -> 3072, ssm_time_step_rank
48 -> 24) into each rank's runner, and the existing attention helpers compute
sharded attention with no new kernel and no head remap.

## Changes

`hipengine/distributed/shard_weights.py`:

- Added `ShardFamily`, `MLP_FAMILY` and `ATTENTION_FAMILY`, plus
  `FULL_ATTENTION_SLOTS` (`attn_q`/`attn_k`/`attn_v`/`attn_output`) and
  `LINEAR_ATTENTION_SLOTS` (`attn_qkv`/`attn_gate`/`ssm_alpha`/`ssm_beta`/
  `ssm_conv1d`/`ssm_a`/`ssm_dt_bias`/`ssm_out`).
- Generalized the resolver to `resolve_shard_context(..., family=...)` and the
  materializer to `materialize_shards(..., family=...)`, with
  `resolve_mlp_shard_context` / `materialize_mlp_shards` /
  `upload_mlp_shard_weights` kept as thin MLP wrappers so the shipped route and
  `scripts/tp2_*.py` are untouched, and `resolve_attention_shard_context` /
  `materialize_attention_shards` / `upload_shard_weights` added.
- Layer roles are now the family's **slot names**, resolved through
  `model_map.layer(id).tensors`, instead of a name reconstructed by string
  surgery on the GGUF tensor name. That is required, not cosmetic:
  `blk.0.ssm_dt.bias` is the slot `ssm_dt_bias`, and the old derivation produced
  `ssm_dt.bias`, which is not a planner slot.
- `_rank_payload` gained `allow_raw`, off for the MLP family (whose refusal of
  raw layouts is a deliberate guard) and on for attention, where five GDN slots
  are `dense_f32` and the rank payload is the slice's bytes verbatim.
- `_t16_repack_for_layout` gained `gguf_q5_k_t16_v1` (`ssm_out` resolves to it;
  `repack_gguf_q5_k_tile16` already existed) and now returns `None` for the
  materializer's own `LAYOUT_RAW_GGUF` / `LAYOUT_DENSE_F32` / `LAYOUT_DENSE_BF16`
  constants rather than only for strings starting with `raw`. A t16-family layout
  with no recorded repack is still a named refusal.

`docs/REFACTOR.md`: the `Mlp*` type names now carry attention payloads too; the
entry records the rename and wrapper-removal condition.
