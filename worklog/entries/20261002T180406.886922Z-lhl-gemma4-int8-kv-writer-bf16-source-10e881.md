# BF16-source per-token/head INT8 paged KV writer

## Summary

Added the first bounded Gemma D12 prerequisite: a generic BF16-source
per-token/head INT8 paged-KV writer. Gemma produces BF16 K/V rows, so the
existing FP32-source INT8 writer could not consume them. The new sibling
decodes BF16 input to FP32 and then applies the identical codec: scale
`max(abs(row))/127` in FP32, quantize round-to-nearest-even with the unrounded
scale, clamp to `[-127, 127]`, store the rounded fp16/fp32 scale, and emit a
zero scale/payload for all-zero rows.

This is a native hipEngine sibling, not an upstream port. The INT8
per-token/head writer is already hipEngine-native (`paged_kv_write.hip` header
notes "INT8 per-token/head writer is hipEngine-native"); the BF16-source
variant is a typed extension of that native kernel. `check_lineage.py` reports
the parent `csrc/amd/qwen35_expert.hip` as DRIFT, but this writer's INT8 codec
has no parent counterpart to copy.

## Grouped-granularity repair (reviewer finding)

Independent review found a high-severity fallthrough. `plan_paged_kv_write`
consults the granularity table first, then falls through to the storage table.
The initial BF16 entries were keyed in the storage table as
`(INT8_PER_TOKEN_HEAD, kind, BF16)`, so a BF16 source with granularity
`block16` or `hadamard_group32` resolved to the per-token/head BF16 writer
even though the shared validator accepts grouped scale shapes — a wrong-format
write. Reproduction before the repair:

```
block16            bf16 decode -> per_token_head_bf16_spans   (wrong)
block16            bf16 prompt -> per_token_head_bf16_prompt_spans (wrong)
block16            bf16 batch  -> per_token_head_bf16_batch_spans  (wrong)
hadamard_group32   bf16 decode -> per_token_head_bf16_spans   (wrong)
...
```

Repair, scope-limited to the new BF16 routes:

- Moved only the three BF16 entries out of `_PAGED_KV_WRITE_ROUTES` into
  `_PAGED_KV_WRITE_GRANULARITY_ROUTES`, keyed `("per_token_head", kind, BF16)`.
  A grouped granularity now finds no granularity route and no storage-table
  BF16 fallback, so the planner raises `no paged KV write route`.
- `_int8_bf16src_symbol` now raises a named capability miss when scale metadata
  is missing or `granularity != "per_token_head"`, before any build/launch.
  This is defense in depth for direct wrapper callers that bypass the planner.
- Existing FP32 behavior is unchanged, including the pre-existing `block16`
  FP32 fallthrough to `per_token_head_spans`; after the repair every FP32 row
  resolves exactly as before.
