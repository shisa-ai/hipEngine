# a global layer's window is the whole context, and saying so buys 1.9 percent at 512 and 0.6 percent at 2048

## Summary

The previous unit trimmed prefill attention's trailing masked run by spending the
promise `window > 0` already makes: a sliding-causal mask is zero above a row's
own position as well as below its window. That left the five global layers
untouched, because `attention.sliding_window is None` makes the runtime pass
`window = 0`, which is the documented "caller makes no such promise" case.

**Their mask is causal all the same.** `_keep_mask` builds `keep =
key_positions <= queries` and ANDs a window in only when one exists, so a global
layer's mask is exactly the sliding-causal mask with an unbounded window. The
call site can say so:

```python
key_begin = _sliding_read_range(attention, start, rows)
...
window=start + rows - key_begin
if attention.sliding_window is None
else int(attention.sliding_window),
```

`start + rows - key_begin` is the `keys` the kernel is handed two lines later, so
this describes the mask that was built rather than promising anything new, and
`first_kept = row_offset + token - window + 1` is `token - rows + 1`, which clamps
to 0 as before. The assistant head gets the same treatment with `int(view.live)`.

## Result

Census at both lengths, both arms in one session, the runtime files the only
difference between them:

| | baseline (trim only) | with global window | delta |
| --- | ---: | ---: | ---: |
| 512 attention | 144.46 ms | **132.07 ms** | **-8.6%** |
| 512 prefill | 729.1 tok/s | **742.9 tok/s** | **+1.9%** |
| 2048 attention | 1897.39 ms | **1860.76 ms** | **-1.9%** |
| 2048 prefill | 504.9 tok/s | **507.9 tok/s** | **+0.6%** |

## The negative is the useful part

The global layers walk the same 20 percent waste the sliding ones did -- 50, 25,
16.6 and 12.5 percent across the four blocks of a 2048 prefill, weighted to 20 --
so by the sliding layers' own result (-25.7 percent at 2048 for a 24 percent walk
reduction) this should have been worth roughly 130 ms. It is worth 37 ms.

**Their cost is not proportional to the walk.** The shapes differ in a way that
explains it: the sliding layers are 16 query heads over 8 KV heads, so two query
heads share a KV row, while the global layers are 16 over 2, so eight do. Each K
and V row is therefore read four times as often per key on the global layers, and
their time tracks bytes rather than iterations. A walk trim removes iterations.

That is the same reading the earlier per-layer work reached from the other
direction -- the global layers were 3.3x slower per layer doing identical FLOP --
and it says their lever is **query tiling**, which cuts K/V re-reads, not another
walk bound. At 2048 they are 655 ms of the 1813 ms attention bench, and after
this unit they are the larger half.

## Changes

- `hipengine/runtime/gemma4.py` -- hoist `key_begin` and pass the block's full
  key count as a global layer's window.
- `hipengine/runtime/gemma4_assistant.py` -- the same for a non-sliding block's
  single query, using `int(view.live)`.

No kernel change; the kernel's contract is unchanged and this is the caller
telling it the truth about the mask it built.

## Next

**Query tiling for the global layers.** They are now the larger half of prefill
attention at 2048 and their cost tracks K/V bytes, which tiling divides by the
tile width. The tile has to carry its own row offsets into the causal and sliding
bounds, and the per-row max means the softmax bookkeeping is per tile row rather
than per block -- that is the work, and it is a kernel change rather than a call
site one.
