# Use bound KV scratch for singleton NextN slots

## Summary

P8 localized physical C2's acceptance collapse and 12 out-of-vocabulary
`INT_MAX` proposal cycles to the singleton ragged-tail path on nonzero provider
slots. Scheduler binding replaces each resident session's KV planes/block table
with its global-pool allocation. `_run_step_batch_device_top1()` correctly uses
those bound sessions, but singleton `_run_block()` rebuilt a view from the
executor's original parent scratch. This combined the bound nonzero page table
with the wrong cache owner. Slot 0 accidentally worked; slot 1 produced a
non-finite attention context from otherwise finite target hidden, fused hidden,
Q/K/V, and pre/post-write live K/V.

A diagnostic address-equivalent rebase (first physical page pointer plus
zero-based table) removed every slot-1 NaN/`INT_MAX`; the prior nbytes/slot
attempt was invalid for global-pool backing and is not evidence. The canonical
fix is to use the session scratch already bound by `bind_device_kv_allocation()`.

## Changes

- `Qwen35GGUFNextNExecutor._run_block()` now uses
  `self._batch_sessions[slot].scratch` and fails visibly if it is unavailable.
- Add a RED/GREEN unit proving singleton slot 1 sends the session-bound scratch
  to the model block and never calls the stale parent `for_slot()` owner.
- No math, kernel, target, accept, policy, or batch proposal route changed.
