# Prepare the resident Inkling block traversal

## Summary

The residual kernels now match the geometry prefill actually uses, and the projection owner can run its attention half and its expert chain inside a caller-owned arena. Nothing selects the device traversal yet; the hidden state still crosses the host twice per visit. This entry records the geometry that decides the design so the traversal itself is mechanical.

## Changes

- `residual_read` is batched over block rows and query-major: `values` is block-major, one output row per (query, block row), and one query's rows are contiguous. The earlier shape was a single shared value stack, which no prefill path uses.
- `project_attention_resident` accepts `plan.device` (arena cursor, input pointers, result pointer): it runs the same kernel sequence inside caller memory and leaves the branch output on the device. The kernel sequence moved into `_attention_kernels` and is shared by both modes.
- `project_experts_mixed_rows(..., device=(hidden, result))` takes routed rows that are already resident and leaves the mixed, convolved projection at `result`. It refuses the call unless the shared-tile route launch is what the geometry would pick, so it cannot silently read a stale repeat buffer.
- Add `attention_resident_extent`, `copy_device`, `project_from_device`, `upload`, `residual_kernel` and `supports_resident_block` on the projection owner.
- The residual launchers are resolved at construction and gated on registration, like the controller and prepare kernels.

## Validation

- `tests/test_gpu_inkling2_residual.py` now covers the real geometry: `(rows, blocks, queries, width)` of `(1, 18, 1, 2304)`, `(64, 18, 3, 2304)`, `(64, 18, 4, 2304)`, `(3, 2, 3, 2304)` and `(2, 9, 1, 384)`, all against `_mix_residual_rows`. Nine GPU cases pass on W7900.
- The projections refactor is behavior-preserving: the resident-attention harness at 64 and 151 tokens gives worst KL from `strict` `1.26e-4`, worst KL from the host control `6.2e-5`, 8 of 8 top agreement and bit-identical repeats, the same numbers as before the refactor. A 128-token prefill still routes all 192 expert inputs through the shared tile launch.

## Geometry this settled

- `ffn_res_query.weight` is one row per layer, and `attn_res_query.weight` is `(3, hidden)` for global layers and flattened to `(hidden,)` for local ones. So the residual read is `rows` independent softmaxes over each row's own residual values, with 1, 3 or 4 queries, never one shared value stack.
- The residual stack is per row: each entry is `(rows, hidden)`, so the device stack is block-major, `capacity * rows * hidden`.
- Prefill uses the shared-tile expert launch (no repeated activation upload) at 64 rows, so a resident expert input only has to be copied, not re-staged.

## Plan for the traversal

One arena per 64-token block, in this order: `h`, branch output, `m`, `normalized`, read output (4 query-major slots), message output, query rows, three stack regions (working, previous, prelude snapshot), the saved `h` copies for the prelude and the previous partial, one controller region, and the attention scratch from `attention_resident_extent`. Per visit: write `_rms(h)` into the working stack at `count`, read the attention inputs, run the attention half with `plan.device`, either bump `count` (residual-block boundary) or `row_add` the branch into `h`, read the mlp inputs from the same stack, normalize, project the router from the resident rows, run the expert chain with `device=`, then `row_add` the result. The prelude rotation is the only subtle part: the first core-start visit snapshots `h` and the stack, and each later core-start visit makes the abandoned stack `previous`, copies the snapshot into the other rotating region, and restores `h` from its saved copy. At the end, download `h` and the stack so `_output_hidden` and the tap capture keep their current meaning.
