# Decode gap narrowed: norm + combine-scan + adaptive splits; mtpbench AR/DFlash lead

## Summary

Task #27 (Gate A decode). Traced both engines' decode steps: hipEngine's
GEMVs are at the DRAM roof like llama.cpp's; the gap was in the small
kernels and launch gaps, not the weight reads. Three changes landed:

1. **Combine live-scan** — skip the -INF block suffix using the device live
   key end (zero-based unwindowed ranges only). Bit-exact: 160/160
   dual-library fixtures.
2. **Norm kernel** — 256 -> 1024 threads + warp-shuffle block reduction
   (2 syncs instead of 16-20 LDS rounds). The 13 us single-block norm was
   latency-bound; now ~2-3 us. Production reassociation (f32 reduction order
   changes; bf16 outputs bit-identical on 56K fixture elements).
3. **Adaptive split blocks** — sticky per-session
   `n_blocks = clamp(ceil(capture_len/64), 16, 64)`, shared by the decode
   graph, verify graphs, and eager fallback (row bit-identity requires the
   same config on both sides). Crossing 2048 keys re-captures both graph
   families together. A 512-key range on 64 blocks costs ~24 us vs ~17 us on
   16 (empty blocks still launch; the combine still scans).

A tried-and-reverted variant: n_blocks=1 for short ranges regressed 512/1024
badly (one wave serializes all splits); the min-16 adaptive config keeps
parallelism and is ID-equal to forced 64-block.

Results (vs llama.cpp HEAD 3b4d6ab3f, same host/day):
- llama-bench shapes (128-token window): 512 12.639->12.835 (parity, lc
  12.844); 1024 12.624->12.710 (lc 12.822); 4096 12.521->12.623 (lc 12.748).
  The 4096 shape crosses the threshold inside the window; the one-time
  ~150 ms re-capture amortizes to ~1.2 ms/step there (production amortizes
  over the full output).
- **mtpbench 512 outputs: AR 12.865 vs lc 12.83, DFlash 27.54 vs lc 27.20 —
  hipEngine leads both**, exactness 10/10.
