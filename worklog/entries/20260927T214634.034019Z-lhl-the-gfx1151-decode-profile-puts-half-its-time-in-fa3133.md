# The gfx1151 decode profile puts half its time in the MoE expert path at 18 percent bandwidth
## Summary
With prefill landed at 1.52 s (338 tok/s) against llama.cpp's 1012.98, the
remaining gap is 3.00x. Decode is the larger relative gap at 20.03 against 41.92
tok/s, 2.09x, and it is the target the objective names explicitly, so this
iteration profiled it rather than starting another prefill change.
The headline reading is a bandwidth one. Decode runs at 49.9 ms per token and a
4B-active MoE at Q4_K moves roughly 2.25 GB per token, so decode achieves about
**45 GB/s of the 256 GB/s peak, 18 percent**. llama.cpp reaches about 94 GB/s,
37 percent, on the same host and the same artifact. The ceiling for this shape
is near 100 tok/s, so 41.92 is reachable and the gap is memory-level parallelism,
not raw bandwidth.

## The lead
The single largest decode consumer is a **grouped prefill kernel**, launched with
grid 90112 x 128 and workgroup 128 — 11.5 million workgroups for a batch-1
decode in which at most eight experts are active. Two more grouped kernels are
launched the same way. A grouped prefill grid is sized for a block of rows times
every expert, so at batch 1 most of those workgroups have nothing to do and
return early. Early-return workgroups are cheap individually, but 11.5 million
of them per layer is a plausible mechanism for 18 percent bandwidth utilisation.
The runtime already has a decode-shaped selected GEMV for the same quant
(`q5_1_selected_gemv_bf16_bf16`, 9.2 percent), so the question is whether the
grouped route should be reached at all at batch 1, or whether the two serve
different tensors (gate/up against down).
## What this entry does not claim
It establishes where the time goes and how far decode is from bandwidth. It does
**not** establish that the grouped route is redundant, that it is required, or
that replacing it would be faster. No correctness or timing experiment was run
against that question, and the next iteration should run one rather than assume.
One measurement caveat is recorded rather than smoothed over: summing kernel
durations gives 172.86 ms per token against a measured 49.9 ms per token, so
decode issues work on more than one stream and the sums overcount by about 3.5x.
The per-kernel ranking is still meaningful because each row is that kernel's own
time, but a critical-path union is the right denominator and was not computed.
