# the prefill kernel runs at 1.6 percent of compute peak and is 16.6x off its own gfx1100 record with only 2.4x explained by cu count

## Summary

I have been quoting the prefill gap as "584 vs 1013 tok/s, 1.74x short" for many entries.
That is an end-to-end figure. The primary artifact for the kernel itself says something much
sharper, and I had never read it.

## The artifact

`benchmarks/results/2026-09-28-gemma4-gfx1151-prefill-attention-isolated.json`:

```json
"model_30_layer_total_ms": 2207.2,
"in_situ_route_ablation_ms": 2295,
"gfx1100_campaign_record_ms": 133.02,
"ratio_vs_gfx1100": 16.59,
"hw_ratio_note": "gfx1100 96 CU / ~960 GB/s vs gfx1151 ~40 CU / ~256 GB/s -> 2.4x CU, 3.75x BW"
```

Per case, at 2048 tokens:

| case | ms/launch | GFLOP/s | layers |
|---|---|---|---|
| swa 256d 16q/8kv window=1024 | 62.23 | 414.2 | 25 |
| swa 256d window=0 | 77.48 | 443.7 | -- |
| full 512d 16q/2kv window=0 | 130.27 | 527.8 | 5 |

## What the numbers say

**Achieved throughput is 414-528 GFLOP/s.** For this part -- ~40 CU, 128 FMA per CU per
clock, ~2.6 GHz -- FP32 peak is about **26.6 TFLOP/s**. So the kernel runs at
**1.56-1.98% of compute peak.**

**The same kernel on gfx1100 takes 133.02 ms against 2207.2 ms here: 16.59x.** The artifact's
own hardware note gives 2.4x for the CU count and 3.75x for bandwidth, so:

- unexplained by CU count: **6.9x**
- unexplained by bandwidth: **4.4x**

**Most of the gap is not the hardware.** A port that scaled with the CU count would be 2.4x
off, not 16.6x.

## This corroborates a separate measurement

`81e8c24eb` recorded that the prefill kernel "runs at 4 percent of issue capacity with bytes
free so it is latency bound". That is an independent instrument -- issue occupancy rather
than achieved FLOPs -- and it points the same way. **1.6% of compute peak and 4% of issue
capacity are two views of a latency-bound kernel, not a throughput-bound one.**

## Why this matters for the fix

The diagnosis in `20260928T073550` and `20260928T073623` is that the kernel visits every key
**three times**, with an LDS round trip each time: compute the logit, exponentiate it and
write it back, then read the weight to accumulate. **That chain is a latency chain, and it is
the mechanism by which a kernel ends up at 1.6% of peak while bandwidth sits idle.**

So the three numbers agree: 1.6% of compute peak, 4% of issue capacity, and a three-pass LDS
dependency per key. **The tiled `logits_s` fix addresses the measured cause, not a guessed
one.**

## A correction to how I have been stating the target

**"1.74x short of llama.cpp" understates the kernel's problem.** It is an end-to-end number
that includes parts of the pipeline the kernel does not own. **The kernel itself is 16.59x
off its own record on the sibling part, with 4.4-6.9x unexplained by hardware, at 1.6% of
compute peak.** Both statements are true and the second is the one that says how much room
there is.
