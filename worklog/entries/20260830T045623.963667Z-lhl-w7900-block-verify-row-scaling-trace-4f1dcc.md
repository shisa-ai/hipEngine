# W7900: block-verify cost is a route-switch cliff, not per-row scaling

## Summary

Task #10 finally has trace data. Five `rocprofv3` arms at block rows 1/2/4/8/16, same model, same
flags, three steps each. Verify cost does not scale per row: at rows=1 the route is the decode GEMV
family at 30.5 ms/step, at rows=2 it switches to `gguf_q4_t16_dense_wmma_prefill_shared_b_bf16` and
kernel time jumps **7.2x** to ~218 ms, then stays flat - 218.4 / 220.3 / 225.3 / 251.4 ms for rows
2/4/8/16, i.e. +15% for 8x the rows. Marginal cost above two rows is about 2.2 ms/row and ms/row
falls 109.2 -> 15.7. The cost is a ~215 ms fixed price for entering the prefill-shaped WMMA route,
which is the same object as task #12 small-row prefill (~252-271 ms fitted fixed cost), not a
speculative-decoding penalty.

## Changes

Artifact `2026-08-30-w7900-q4km-block-verify-row-scaling-trace.json`, plus docs trap 7 (`6f18b8592`)
for the two instrument facts that had blocked this sweep for four dead arms: on a `q5_k_t16_v1`
repack the verify path defaults to F32 activations and both dense-Q8 escapes require
`gguf_q8_0_t16_v1`, so `block-verify` only runs with
`HIPENGINE_GGUF_VERIFY_CAPTURE_PREFILL_GDN=1`, and the wrapper flag that looks like it enables the
route (`--verify-dense-q8-dp4a-f32`) is inert because no `hipengine/` code reads that argument.

## Validation

`summary` from each arm (kernel time and host wall per step, 1073 kernel calls/step at rows>=2):

| rows | kernel ms/step | host ms/step | kernel share | ms/row | dominant kernel |
| --- | --- | --- | --- | --- | --- |
| 1 | 30.51 | 38.43 | 0.794 | 30.5 | `q4_k_t16_dense_dual_local32_silu_gemv` (32.9%) |
| 2 | 218.42 | 226.64 | 0.964 | 109.2 | `gguf_q4_t16_dense_wmma_prefill_shared_b_bf16` (65.7%) |
| 4 | 220.27 | 228.64 | 0.963 | 55.1 | same (65.5%) |
| 8 | 225.32 | 233.90 | 0.963 | 28.2 | same (64.3%) |
| 16 | 251.43 | 260.28 | 0.966 | 15.7 | same (57.7%) |

Applying the decision rule in `20260830T030945...-50b888`: share is 0.963-0.966 above one row with a
host residual of 8.1-8.9 ms/step, so the verify cycle is **kernel-bound**. Extending graph capture to
verify cycles is worth at most a few percent of the window; the lever is the prefill-route cost. This
is consistent with `20260830T030216...-37f4a1`, which killed the per-row 3.21x premise from walls, and
now replaces that inference with traces.

## Next

- The traced configuration is **not** the shipped default: the GDN capture env is required because
  nothing else can run block-verify on a Q4 repack. Absolute milliseconds here must not be quoted as
  production verify cost. Two follow-ups if production verify cost is ever needed: make a bf16
  activation route the default for block-verify on q5 repacks, or register the missing
  `(gguf_q5_k_t16_v1, f32, bf16)` linear - the latter changes arithmetic class and needs the profile
  gate, the former is a routing decision.
- Repeatability is unmeasured in this artifact: one arm per row count, three steps, ~2.3 min each.
  The cliff (7.2x) and the flatness (+15% for 8x rows) are both far outside plausible single-arm
  noise, but the 2.2 ms/row marginal figure is not yet repeated.
- Since rows>=2 inherits the prefill fixed cost, MTP row cost should be attacked by fixing small-row
  prefill (#12), not by making the verifier leaner per row. That is the actionable consequence of
  this whole thread for the MTP scoreboard.
