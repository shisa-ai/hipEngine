# Filter source-F16 pair policy by actual request rows

## Summary

Fixed the bounded source-F16 owner context to select ordered pair-only metadata
from the actual bulk request length rather than the allocation capacity. A
M517 request in a 1024-row arena had selected the M1024-M2047 interval, causing
the newly admitted Q4/Q4 pair to fail closed and execute only its QKV singleton.

## Changes

- Added an optional `request_rows` argument to the private source-F16 owner
  context and passed `len(token_ids)` from both synchronous and asynchronous
  public bulk-prefill entry points.
- Retained scratch-capacity filtering as the compatibility default for internal
  test/diagnostic callers, while rejecting non-positive or out-of-capacity
  request rows.
- Expanded owner-context tests to separate scratch capacity from request length
  at M517/M1024/M2048/M4096 and prove exact fail-closed intervals.

## Validation

- The complete quality harness first caught only **120** added pair-producer
  launches instead of the required **192** on a 517-row prompt. Per-shape
  ownership showed the missing 72 gate launches and isolated the capacity/row
  mismatch.
- After the fix, the same production prompt records exactly **192/192** added
  Q4/Q4 producer launches, **33/33 top-1**, max KL **0.001333**, finite output,
  and byte-exact candidate repeat.
- Full affected kernel/registry/dispatch/scratch/runner bundle: **150 passed,
  13 availability-guarded skips**. Ruff and diff hygiene pass.
