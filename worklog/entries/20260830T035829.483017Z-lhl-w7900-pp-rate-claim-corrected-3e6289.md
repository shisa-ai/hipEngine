# W7900 Qwen3.8: no evidence pp matches peers; small-row prefill is the residual

## Summary

I told the user the residual AR loss was "no longer GEMM-bound, since single-prompt pp already
matches llama.cpp at 959-999 tok/s", and wrote the same into the task ledger. No measurement
says that. 959-999 does not exist in any artifact, log, or entry; grepping the tree for it
finds only unrelated 1-August Laguna files. The committed parity entry gives **883.8 tok/s at
512 tokens for hipEngine alone**, explicitly marked *cross-engine unmeasured*, and at the
~45-token shape that actually dominates admission we are **1.52x slower**, not equal. The
residual is therefore a prefill-rate deficit at small row counts, which is a different unit of
work than the graph-capture / launch-bound direction I had pointed at.

## Changes

Ledger and task direction only; no code, no benchmark row changed.

## Validation

Source of truth is `worklog/entries/20260829T215206.066388Z-...-1921c9.md`, still current for
these numbers:

| shape | hipEngine | comparator | verdict |
| --- | --- | --- | --- |
| ~45 tokens | 159.7 tok/s (0.2818 s) | ~243 tok/s implied by 223.4 ms admission minus a 38.3 ms first step | **1.52x slower** |
| 512 tokens | 883.8 tok/s (0.5793 s) | retained packet does not cover it | internal only |

Internally, device time is **6.32 ms/token at 45 tokens vs 1.29 ms/token at 512** (5.5x), so
the deficit is small-row inefficiency inside prefill, not per-lane session setup as I guessed.

Cross-checks that hold: today's C1 prefill row is 148.891 tok/s against the entry's 159.7 at the
same shape (08-29 vs 08-30 sessions), and 148.891 vs llama.cpp current 200.946 is 0.74x = a
1.35x deficit, bracketing the entry's 1.52x. So both the direction and the order of magnitude
survive; what dies is the "we already match on pp" inference.

That entry also carries an instrument warning worth repeating, because it is how a plausible
wrong pp rate gets produced: `scripts/qwen35_gguf_bench.py` leaves `use_wmma_prefill` unset, so
its default route reports 45-token prefill at 98.3 tok/s against the shipping route's 159.7
(+62.4%), and 869.0 vs 883.8 at 512. Rates from that harness's default route are not engine
rates.
