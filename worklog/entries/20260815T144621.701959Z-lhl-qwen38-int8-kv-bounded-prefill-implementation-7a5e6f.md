# Implement bounded exact INT8 prefill ownership

## Summary

Wired the geometry/policy lifetime planner into GGUF resident allocation. Memory-
positive explicit INT8 layouts now allocate full-prompt hidden ownership, run
the existing exact layer-outer prefill schedule, and reuse one BF16 K/V oracle
pair across attention layers. BF16, short mirrored INT8, and memory-negative
hybrid layouts preserve their old allocation/scheduling route. A focused real
Qwen3.8 screen reproduces the prior candidate logits exactly and lowers 32K-
capacity tracked prefill peak by `1.613554 GiB` with matched performance bands.

## Changes

- Resolve and publish `int8_prefill_lifetime` in resident prefill diagnostics.
  The choice uses geometry, storage policy, mirror presence, dense hidden-alias
  policy, and exact byte terms; there is no model-name or backend branch.
- Allocate token/hidden capacity from the selected plan. The existing
  `alloc_capacity < rows` scheduler therefore selects layer-outer execution only
  when full ownership is present.
- Key selected INT8 oracle caches to one shared pair; retain per-layer keys for
  chunk-outer plans. A fail-closed guard forbids shared ownership if a future
  allocation drift re-enters chunk-outer execution.
- Refactored the hidden buffer count into one helper so planning and allocation
  cannot disagree. Added session-plan/shared/local ownership tests.
- Repaired two existing hidden-seed forwarding mocks to cover the already-
  required Q6 prefill context; the original broad focused bundle established all
  other nodes passing, and only those repaired nodes were rerun.

## Validation

- RED: the new integration test failed collection before the session planner
  existed. GREEN: INT8 policy + prefill-liveness bundle passes 58 tests.
- The broader changed-path bundle completed with all other tests passing and two
  unrelated hidden-seed mock failures; the two repaired nodes then pass, as does
  the complete changed INT8 policy file (28 tests). Per focused-repair policy the
  broad bundle was not repeated.
- Real `mixed_v1` 512/8 with 32K capacity passes at mean/max KL
  `0.00025920/0.00111877`, 100% top-1, zero BF16 mirror, all 16 attention layers
  INT8, and the exact same candidate-logit SHA-256 as the pre-change screen:
  `448a6b018a7f7efd3649e8340c1c8c6abade3f1fde6bbba64218f7f08606fdc3`.
- Preliminary dirty-tree 4K/128, one warmup + three measured persistent-session
  runs, old -> bounded: prefill `978.573 -> 980.367 tok/s` (`+0.183%`), eager
  decode `34.108 -> 34.022` (`-0.252%`, overlapping sample bands), tracked peak
  `18.943464 -> 17.329910 GiB` (`-1.613554 GiB`), current ownership
  `16.927839 -> 17.203934 GiB` (`+0.276094 GiB`), finite logits, and identical
  `[9707,9707,9707]` final IDs. The peak delta exactly matches modeled hidden,
  token, and shared-oracle bytes.
- Correction to the prior design entry: expanding the INT64 prefill-token owner
  changes its 33,024-position prediction from `1.613770` to `1.613554 GiB`,
  matching measurement exactly. At 64K the 24-GiB low-memory policy uses 1,024-
  row chunks, below the proven 4,096-row in-place threshold, so the safe plan
  owns two hidden planes and predicts `2.519051 GiB` lower peak versus current
  per-layer oracles—not the earlier one-plane `3.134766 GiB` estimate.
