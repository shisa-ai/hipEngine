# The local32 column-loop full unroll is a measured regression, not an MLP win

## Summary

`gguf_iq4_xs_local32_gemv_kernel` is the single largest item in the UD verifier
(12.24 ms/step, 26.0% of UD-Q4_K_M) and it runs at 46-58% of the 960 GB/s DRAM
roofline. It is memory-latency-bound at fixed occupancy. The obvious next lever
is more loads in flight, and the kernel's own source looked like it was
blocking that. It was not. The change measured **worse on every shape**, twice,
and was reverted.

## The hypothesis

The unrolled eight-column loop carried a per-column bounds check:

```cuda
#pragma unroll
for (int t = 0; t < COLS; ++t) {
    if (n0 + t >= N) break;      // <-- here
    const uint8_t* b = w + (n0 + t) * col_bytes + blk * 136;
```

with the mirroring `if (n0 + t < N)` around the store.

**Both are dead code.** The launch contract enforces `N % 8 == 0`
(`launch_local32_rows` raises, and the C entry `hipengine_gguf_iq4_xs_local32_gemv`
returns `hipErrorInvalidValue`) and the grid is `N / 8`, so `n0 + t <= N - 1`
for every `t < 8`. The branches can never be taken.

The hypothesis was that they are nevertheless expensive: with `t` unrolled they
become eight N-dependent branches, so the compiler cannot prove them false and
cannot hoist the eight columns' 136-byte records. Removing them should leave
all eight records in flight and lift memory-level parallelism.

## The measurement

`scripts/gguf_iq_local32_rows_headroom.py` on the four real IQ4_XS tensors from
`Qwen3.8-27B-UD-Q4_K_M.gguf`, interleaved min-of-N, five rounds, `--reps 3`,
physical GPU1 (RX 7900 XTX, gfx1100). Two independent runs of the change and one
run after reverting:

| Tensor (rows 4) | baseline sibling | unroll run 1 | unroll run 2 | reverted |
| --- | ---: | ---: | ---: | ---: |
| `blk.0.ffn_down` | 0.1190 | 0.1250 | 0.1238 | 0.1214 |
| `blk.0.ffn_gate` | 0.1038 | 0.1321 | 0.1242 | 0.1095 |
| `blk.11.attn_q` | 0.0791 | 0.0866 | 0.0870 | 0.0829 |
| `blk.36.attn_qkv` | 0.0682 | 0.0838 | 0.0751 | 0.0714 |

The rows == 1 owner regressed too, and by more: `ffn_gate` 0.1011 -> 0.1115 /
0.1100, `attn_qkv` 0.0465 -> 0.0581 / 0.0581.

Against the revert, that is **+5.0% / +26.9% / +10.1% / +23.5%** on the sibling
at rows 4 and **+20.6% / +8.8% / +14.0% / +25.0%** on the rows == 1 owner. The
two unroll runs agree with each other, and the revert run agrees with the
baseline run, so this is a real regression rather than spread. The sibling's
`bit-ex` column stayed `True` throughout, so nothing about the arithmetic
changed.

## Why it is a regression

The branches are load-bearing. They end each column's live range before the
next column's header, scale and two payload words are loaded, which is what
keeps the register file from holding all eight columns at once. Forcing the
full unroll trades that for register pressure rather than for more loads in
flight. The owner already sits at 192 VGPRs at rows 1, and the ROWS > 1 sibling
uses a one-resident-block launch bound to spend registers on the row
accumulators.

This is the third instruction-level rejection on this family, after the Q5_K
rowtile column width and the activation load vectorization. The pattern is
consistent: the compiler is already scheduling this loop well, and source-level
restructuring that assumes otherwise loses.

## What this rules out, and what is left

It rules out the cheap route to memory-level parallelism. The remaining levers
for this owner are the ones that change the geometry rather than the schedule:

- **explicit prefetch** of the next `blk` iteration's column records, which
  needs a hardware-counter unit to confirm the stalls are DRAM latency rather
  than L2 or LDS;
- **a wider row/wave split**, which changes the accumulation order and therefore
  owes a new bit-exactness contract plus the full production profile gate.

Neither is a bounded change, and neither should be attempted without the
counter unit.

## Changes

None retained. The kernel edit was reverted after measurement.

## Validation

- `scripts/gguf_iq_local32_rows_headroom.py` baseline / unroll x2 / revert on
  the four real IQ4_XS tensors; artifact at
  `benchmarks/results/2026-09-13-ud-gfx1100-local32-column-unroll-rejected.json`.
- `bit-ex` (sibling vs rows == 1 owner, per row) stayed `True` in every arm,
  so the candidate was arithmetically safe and was rejected purely on speed.
- `git checkout -- hipengine/kernels/hip_gfx1100/quant/gguf_iq_dense.hip`
  restored the retained kernel; the revert run reproduces the baseline.
