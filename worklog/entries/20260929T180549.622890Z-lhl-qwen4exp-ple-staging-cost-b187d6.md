# PL-2 cost-gated out: the PLE staging/H2D copy is 0.029% of the request

## Summary

**PL-2 is rejected by its own cost gate.** The entire addressable cost - H2D copy
plus staging memcpy - is **~2.65 ms per complete request** against a **9,055.58 ms**
production `code-p512` wall: **0.029%**. The gate says "if material, test one
bounded double-buffer path". It is not material, so no path was built.

I also found and fixed a real telemetry gap that would have misled this very gate.

## Measurements

Two independent measurements, neither requiring the model.

`scripts/qwen4exp_ple_h2d_cost.py` - the pinned H2D at the real staging shapes
(median of 15, 3 warmups, device-synchronized):

| copy | bytes | median | effective |
|---|---:|---:|---:|
| prefill (512 x 2560 fp32) | 5.00 MiB | **67.60 us** | 77.6 GB/s |
| decode (1 x 2560 fp32) | 10.00 KiB | **16.97 us** | 0.6 GB/s (latency-bound) |
| **per request** (128 + 1) | **6.25 MiB** | **2.240 ms** | |

Fresh in-engine attribution, current code, `--ple-telemetry --case-id code-p512`:
gather+dequantize **0.974 s**, staging copy 0.409 ms, H2D (decode only) 11.444 ms.

## Why it is not worth overlapping

**1. The payload is tiny and mostly latency-bound.** 6.25 MiB per request. Only
the prefill copy is bandwidth-shaped (5 MiB at 77.6 GB/s); the 128 decode copies
are 10 KiB each at 0.6 GB/s - per-call latency, 16.97 us apiece, which is
**0.027% of a 61.75 ms decode step**.

**2. The dominant PLE term is not a copy.** Gather/dequantize is 0.974 s, ~370x
the whole copy cost, and it is CPU work against the mmap'd PLE table. Async H2D
staging does not touch it. The 2026-09-02 telemetry artifact reached the same
ranking independently, which is a useful cross-check from different code.

**3. Perfect overlap recovers 0.029%.** 2.65 ms of 9,055.58 ms.

## The telemetry gap

The engine's **prefill** PLE copy never called `record_h2d`, so PLE telemetry
counted only the 128 decode copies and **understated the per-request H2D payload
4x**. I verified the fix rather than assuming it:

| | h2d_bytes | |
|---|---:|---|
| before | 1,310,720 | 1.25 MiB (decode only) |
| after | **6,553,600** | **6.25 MiB** |

6,553,600 = 5,242,880 (prefill) + 1,310,720 (decode), matching the independently
measured shapes exactly. This matters beyond this unit: without it the next person
cost-gating PLE I/O reads a 4x-low number and could wrongly conclude the copy is
free. The added `record_h2d` is guarded exactly like the decode path's, so it is a
no-op with telemetry disabled and production is unaffected.

## Measurement honesty

**The instrumented walls are noisy and I did not build on them.**
`gather_dequant_wall_ns` moved 0.974 s -> 1.635 s between two identical telemetry
runs, and `h2d_wall_ns` moved 11.444 -> 11.988 ms for an added 67.60 us copy. The
existing artifact already says its telemetry-enabled wall is excluded from
performance evidence, and this confirms why. The **bytes** are deterministic and
are the reliable evidence; every timing in the verdict table above comes from the
standalone uninstrumented measurement, not from the counters.

**Not a speed claim.** `performance_claim: false`. This measures the existing
synchronous copy and rejects a candidate - it does not measure an alternative.
One workload shape, one host; the boundary excludes gather/dequantize, which is
where the real PLE cost is.
