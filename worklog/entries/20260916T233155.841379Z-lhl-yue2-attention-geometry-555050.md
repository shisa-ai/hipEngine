# YuE2 NAR attention: latency-bound geometry, not instruction count

## Summary

The tensor-core NAR attention is now **2.13 ms** per call at the production shape,
from 3.85 ms — a 1.84x gain that puts it **faster than the pinned upstream's own
attention kernel (2.31 ms)** and takes the product's 32-step solve of
`mandarin-off-s1234` to **26.07 s against the reference's 27.32 s**. The solver was
16.2x behind that reference before this work; it is now 1.05x ahead.

The finding that produced it was an instruction count, not a timing: the kernel was
**latency-bound, not issue- or WMMA-bound**, and the fix was block geometry.

## Changes

- `hipengine/kernels/hip_gfx1100/yue2/nar_wmma.hip`: `WAVES` 4 -> 12,
  `K_BATCH` 64 -> 32, and the shared arrays marked 16-byte aligned. No fragment

- `benchmarks/results/yue2_m7_attention_wmma_geometry_20260917.json` (new): the

- `benchmarks/results/yue2_reference_comparison_geometry_20260917.json` (new): the
  twelve-case comparison at the new geometry.
- `benchmarks/README.md`, `benchmarks/CHANGELOG.md`, `docs/KERNELS.md`: retained rows
  and the geometry finding.

## How the diagnosis went

The kernel measured 7.5 TFLOP/s, 15% of the device's fp16 peak, while the
reference's kernel reached 12.4 TFLOP/s. Three plausible causes were tested in
order:

1. **Fragment assembly.** The source reads each WMMA fragment element by element
   (16 shared loads per fragment). Rewriting it as one `half16_t` vector load
   produced a **byte-identical ISA** — 2 902 instructions, 456 16-bit moves, 64
   WMMA, unchanged — so the compiler had already vectorized it. No-op, reverted.
2. **Occupancy hints.** `__launch_bounds__(THREADS, 3)` and `(THREADS, 4)` measured
   within noise of `(THREADS, 2)` (3.93 / 3.69 / 3.85 ms). Shared memory (34 816 B
   at the time) already limited the block count to one per CU, so the hint could not
   change residency. No-op.
3. **The arithmetic.** A static ISA count of the built object plus the wave count
   from `rocprofv3`: 2 902 instructions per key batch, 1 312 waves over 40 CUs x
   4 SIMD, 11.2M cycles for the call. That is ~11 cycles per instruction issued —
   the kernel is stalling, not issuing. At 128 threads per block and 248 VGPRs it
   ran two waves per SIMD.

That pointed at geometry rather than instruction count, and the sweep agreed: the
block width is the lever.

## The change

`WAVES` 4 -> 12 (128 -> 384 threads), `ROWS_PER_BLOCK` 32 -> 96, `K_BATCH` 64 -> 32.
Shared memory goes to 60 928 B (`shared_query` 192x136 + `shared_tile` 32x136), still
one block per CU, so the gain is three waves per SIMD instead of two and shorter
per-batch dependency chains. The lane-to-column mapping is untouched — 16 columns per
wave means 8 query rows x 2 query heads — which is why a larger block was a small
change rather than a rewrite of the fragment code.

Sweep (median ms/call, production shape):

| Geometry | ms/call |
| --- | ---: |
| WAVES=4, K_BATCH=64, blocks=2 (previous) | 3.85 |
| WAVES=8, K_BATCH=32, blocks=2 | 2.46 |
| WAVES=8, K_BATCH=64, blocks=2 | 2.42 |
| WAVES=10, K_BATCH=32, blocks=2 | 2.21 |
| **WAVES=12, K_BATCH=32, blocks=2 (retained)** | **2.07** |
| WAVES=12, K_BATCH=16, blocks=2 | 2.15 |
| WAVES=13, K_BATCH=16, blocks=2 | 2.45 |
| WAVES=4, K_BATCH=64, blocks=4 | 3.69 |

`WAVES=12` with `K_BATCH=64` exceeds the 65 536-byte shared-memory limit (69 632),
so this is the corner of the feasible region. `K_BATCH` 32 against 64 at
`WAVES=8` is identical within noise (2.59/2.60, 2.70/2.68, 2.82/2.81 over three
paired rounds), so it was chosen to fit the wider block rather than on a timing
difference. Register use falls from 248 to 224 VGPRs.

## Validation

- `python3 scripts/yue2_attention_bench.py --kernel {scalar,wmma} --repeat 15`,
  alternating in one session: scalar 18.97 / 20.56 ms, tensor core **2.13 / 2.17 ms**
  (minima 2.07), i.e. 9.3x the scalar kernel and 1.08x the reference's 2.31 ms.
- `rocprofv3 --kernel-trace`: `yue2_nar_attention_wmma_kernel`, 21 calls at
  2.533 ms, VGPR 224, LDS 60 928.
- `python3 scripts/yue2_nar_gate.py --fixture artifacts/yue2/oracle/{nar,nar-condend,nar-multichunk}`:
  all three pass. chunk0 latents rel L2 0.01099 / cosine 0.999941 (0.01042 before),
  restricted visibility 0.00894 / 0.999961 (0.00938 before), multi-chunk
  0.01090 / 0.999943 (0.01054 before), against a 0.05 / 0.999 gate. The batch size
  changed from 64 keys to 32, so the online-softmax batching changed by design; this
  stays a production-profile variant with `nar_attention_f32` as the registered
  strict fallback behind `HIPENGINE_YUE2_NAR_ATTENTION=scalar`.
- 23/23 in `tests/test_unit_yue2_nar_kernels.py` (seven WMMA shapes against the
  independent FP64 reference, plus the geometry guard) and 48/48 across the NAR
  runtime, operator and fixture modules.
- Twelve-case replay: **12/12** with every case reproducing its exact frame and
  sample counts, 458.7 s against 464.6 s at the previous geometry.
- 32-step product solve of `mandarin-off-s1234`: **26.07 s** (was 32.22 s), full
  replay 46.16 s (was 60.28 s), determinism bit-identical, frames 1297/1297 and
  samples 2490176/2490176 exact.
- Across all twelve cases the solver's per-ODE-step ratio to the reference falls
  from 5.79x (scalar attention) to **3.78x**.

## Next

The projections are now the dominant item by a wide margin: 14.7 s of a 26.07 s
solve, 229 ms per evaluation, at 16.0 TFLOP/s against 19.4 TFLOP/s for the same
shapes launched back to back by hipBLASLt. Closing that in-place gap is worth about
3.9 s; going past ~20 TFLOP/s needs a hand-written GEMM, because a 4 096³ square
GEMM also measures 21 TFLOP/s on this device against a ~51 TFLOP/s fp16 peak. The
attention now has to beat the reference rather than catch it.
