# gemma4 decode is ~28.0 tok/s, and the A/B that was supposed to attribute it proved nothing

## Summary

**Decode, which the objective wants 2x on and which had no current number, is ~28.0 tok/s** at
prompt=512/output=128/samples=3.

The most recent recorded row at the **identical protocol**
(`2026-09-28-gemma4-gfx1151-decode-route-uniform-grouped.json`, same 512/128/3) is **24.90**. So
decode is up about 12.5 percent since then -- **but I cannot attribute that to any particular
change, and the A/B I ran to find out was invalid.**

| --- | --- | --- |
| hipEngine, now (n=3) | **27.73, 28.04, 28.14** | measured here |

**The objective's "2x on our decode" reads as 2x the current rate, i.e. about 56 tok/s, which is
roughly llama.cpp's number.** The gap is about 2.0x.

Prefill in the same runs: 0.5868, 0.5897, 0.5899 s -- consistent with the 0.5911 from
`20260929T193000`, and comfortably better than the 0.6525 that preceded the T16 layout change.

## The invalid A/B, and why it is worth writing down

`20260929T193000` swapped the dense leaves onto the T16 layout, which also moved decode from the
raw GEMV family to `t16_gemv_decode_*`. That is a plausible decode win, so I ran an A/B: stash the
change, measure decode, restore.

**The stash was a no-op.** The output ended with `No stash entries found` -- `4e6fdb5e0` had
already **committed** those edits, so `git stash push -- <files>` had nothing to stash and both
arms ran identical code. The "before" arm reported 27.68/28.04/28.10, statistically the same as
the "after" arm's 27.73/28.04/28.14, and I nearly recorded "the layout change is decode-neutral"
as a measured result.

**The failure mode is specific and repeatable:** `git stash` tests the *working tree*, so it can
only A/B **uncommitted** changes. After a commit, the same command silently becomes a no-op rather
than an error. The correct form is `git checkout <commit> -- <files>`, and the guard is to assert
the tree actually changed -- `git stash list` non-empty, or a diff against the saved copy -- before
trusting the result.

**A second-order lesson:** the first A/B in this session (`20260929T193000`, against
`test_unit_gemma4_gpu_kernels.py`) *was* valid, because that change was still uncommitted. The
same technique is not reusable after the commit lands, and nothing warns you.
