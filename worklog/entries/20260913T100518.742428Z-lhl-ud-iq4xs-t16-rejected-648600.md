# The IQ4_XS T16 layout does not pay: the owner is not load-bound

## Summary

The `IQ4_XS repack into a tile layout` item in `docs/UD-GFX1151-OPTIMIZE.md`
rested on one inference: `gguf_iq4_xs_local32_gemv` runs at 396-461 GB/s while
the t16 rowtile owner reaches 704 GB/s on the same `(5120, 17408)` shape, and
IQ4_XS has no tile layout, so the gap was read as structural to the two owner
families. The previous unit built the byte-neutral `GGUF_IQ4_XS_T16_*` layout.
This unit built the owner and measured it. **The item is rejected: the tile
layout buys nothing on this owner.**

The T16 owner keeps the local32 accumulation order exactly -- same per-(row,
column) k ownership, same FMA order, same wave32 shuffle tree, same
cross-wave serial sum -- so it is bit-identical to the shipped owner, and that
is confirmed on every case measured. It halves the payload loads and the
payload bytes per block, and the result is a small loss on most shapes.

That independently confirms the earlier finding that this owner is
latency-bound at low occupancy and not load-bound, and it removes the
premise the item was built on.

## Changes

`docs/UD-GFX1151-OPTIMIZE.md`: the item is marked rejected with the measured
ratios. `docs/REFACTOR.md`: a new entry for the now-unused layout primitive
with its removal trigger.

No kernel change was retained. The scratch owner was added to a scratch copy
of `hipengine/kernels/hip_gfx1100/quant/gguf_iq_dense.hip` and the file was
restored byte-for-byte afterwards (`git status -sb` clean, verified).

## Validation

Harness `/tmp/phase8/t16bench.py` loads six real IQ4_XS tensors out of
`/models/gguf/Qwen3.8-27B-UD-Q4_K_M.gguf`, repacks each with
`repack_gguf_iq4_xs_tile16`, and times the T16 owner against
`launch_local32` / `launch_local32_rows` on the same random activation, best
of 4 x 30 launches after 3 warmups, with `waves = _local32_waves(K, N)` for
both arms so the cross-wave order matches. The output is compared bit-for-bit
for every case.

The single-wave geometry, which is what makes the Q5_K t16 rowtile fast (no
barriers, no shared-memory cross-wave exchange, whole-K per wave), was also
timed on the same owner and is worse on nine of twelve cases (0.62x to
1.13x). The IQ4_XS per-element decode is a dependent LDS codebook lookup
(`s_cb[nibble]`) rather than arithmetic, so removing the barriers does not
recover the difference.

The `exact=True` column is the load-bearing evidence for the layout itself:
it shows the tile is a true permutation, since the same arithmetic on
repacked bytes reproduces the raw owner's output bit for bit at two row
slabs on six shapes.

## Next

Do not re-open the IQ4_XS tile repack without a change to the decode itself.
The measured constraints on this owner are now: `COLS` 8, the `WAVES`
heuristic, the `ROWS > 1` launch-bounds floor, a 29% throughput fall from
rows=1 to rows=4 at a fixed byte count, and a payload-load count that can be
halved with no benefit. The remaining UD-versus-plain gap is the IQ family's
425-441 GB/s against the K family's 600-978 GB/s, and the strict
Q3_K/IQ3_S owner's 131 GB/s, all of which are now blocked on a
counter-level diagnosis that this host cannot provide.
