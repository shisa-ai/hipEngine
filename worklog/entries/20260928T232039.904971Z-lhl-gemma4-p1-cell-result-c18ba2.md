# P1's last untested cell was run, and it does not flip

## Summary

The one combination of launch mode and window style that neither P1's sweep
nor the parity test had ever executed — **integer window bounds under
`CompactVarlen`** — is now run. It behaves exactly as the non-varlen case
did: **top-left**. P1's blocker is structural rather than a consequence of
the launch mode, so the row closes, and P2's option (a) becomes the sole
route for both the past-window sliding fallback and the five global layers.

## The run

`scripts/gemma4_p1_window_alignment_probe.py` at the discriminating shape
`rows=512 keys=1536 window=128` (suffix block starting at 1024), scoring the
flash output against six candidates rather than against an expected answer:

| candidate | maxabs | meanabs | match |
| --- | ---: | ---: | :---: |
| baseline (both sentinels) vs causal | 0.007812 | 0.000083 | ✅ |
| integer-window vs causal | 2.640625 | 0.289426 | |
| integer-window vs bottom-right window | 2.726562 | 0.352266 | |
| integer-window vs block-local causal | 2.585938 | 0.138928 | |
| **integer-window vs top-left window** | **0.007812** | **0.000091** | ✅ |
| integer-window vs left-edge-only control | 2.640625 | 0.286896 | |

Two controls matter as much as the match:

- The **baseline** matches plain causal at the BF16 noise floor, which
  validates the harness at this shape before anything is concluded from it.
- The **left-edge-only control** shares P1's reading of the window's left
  edge but omits the block-local right bound, and it *misses*. That isolates
  the right bound: the window cuts a suffix block at block-local `i` instead
  of `start + i`, which is precisely P1's original diagnosis.

## Why this is conclusive rather than merely consistent

Every one of P1's four recorded figures reproduces **to four decimals**:

| | this run | P1's sweep |
| --- | --- | --- |
| vs plain causal | 2.640625 / 0.289426 | 2.6406 / 0.28943 |
| vs bottom-right | 2.726562 / 0.352266 | 2.7266 / 0.35227 |
| vs block-local causal | 2.585938 / 0.138928 | 2.5859 / 0.13893 |
| matching candidate | 0.007812 / 0.000091 | top-left 0.0078 / 0.00009 |

Identical output in a launch mode nobody had exercised before means varlen is
**not** the missing ingredient. The hypothesis that the sentinels needed
`cu_seqlens` to carry a bound — the reason this cell was worth building a
gate for — is answered: supplying a real integer bound under varlen changes
nothing about *where* the bound is applied.

## The chain that produced it

The cell could not be run at all three iterations ago: `window_left` /
`window_right` appeared in zero `.py` files. It took three steps to make it
executable, and two of those steps were corrections:

1. **X4** (`faea18409`, `85cb520dd`) — established that no release ships a
   runtime that would clear the old gate, so waiting was never a plan.
2. **P1's gate rewritten** (`72fdff05b`, `68e49c4ad`) — the varlen hypothesis
   was sound in sourcing and wrong in novelty: the configuration is
   production, already pinned to causal by the parity test. Caught by reading
   the shim before spending a GPU pass.
3. **Parameterization** (`3d084638d`) — made the remaining cell reachable,
   with defaults equal to the previous hardcoded bytes so the default path
   did not move.
