# qweight_high is not required for q4_k, so the repack output satisfies the kernel

## Summary

The `qweight_high` question is resolved, and for q4_k it is **not an obstacle** -
so the last open risk in the plan is closed.

The kernel guards on `qtype`:

```c
if constexpr (qtype == 4 || qtype == 5) {
  if (mins == nullptr) return static_cast<int>(hipErrorInvalidValue);
}
if constexpr (qtype == 5 || qtype == 6) {
  if (qweight_high == nullptr) return static_cast<int>(hipErrorInvalidValue);
}
```

So `qweight_high` is required **only** for q5_k (read as `uint8`) and q6_k (read as
`uint16`), where it carries the extra bits those formats have. For `qtype == 4` the
read path uses only `pw` from `qweight_low` plus the scale and min - which is
exactly what `repack_gguf_q4_k_pack8` produces: an int32 `qweight` plus fp32
`scales` and `mins`.

**So the q4_k pack8 expert kernel is satisfied by the existing repack output, with
`qweight_high` passed as null.**

The same guard block confirms two launch preconditions worth noting for the wiring:

- `out_features % PACK8 == 0` - and 1408 % 8 == 0, the same arithmetic that made the
  fused tensor pack8-compatible in the first place.
- `threads` must be 32, 64 or 128.

Both are satisfied by Gemma 4's geometry and the existing launch conventions, but
they are now written down rather than assumed.

## Validation

- Read from the kernel's own guard block and its per-`qtype` read path, which is
  the authoritative statement of what each format requires.
- The `1408 % 8 == 0` arithmetic is the same check performed independently in the
  earlier compatibility entry.
- **Not verified:** numerical correctness of the pack8 route against the current
  route on Gemma 4's geometry. That is the implementation unit's correctness gate
  and cannot be settled by reading.
