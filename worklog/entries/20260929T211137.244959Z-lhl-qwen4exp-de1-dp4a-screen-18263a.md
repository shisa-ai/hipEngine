# DE-1 candidate measured: the decode Q8_1-DP4A linear is 2.0x faster than the exact variant production runs

## Summary

First **measured** candidate in this campaign rather than an analysis of existing evidence. At the
real decode gate+up shape, the Q8_1-DP4A `logical128/t64` variant is **~2.0x faster** than the exact
variant production runs today, **after** being charged for its activation quantization.

## Changes

- **New `scripts/qwen4exp_de1_decode_gemv_screen.py`** - head-to-head kernel screen.
- **New artifact** `benchmarks/results/2026-09-29-qwen4exp-de1-decode-gemv-screen/`
  (`README.md`, `screen.json`).
- **New gate candidate `decode_dp4a_linear`** in `scripts/qwen4exp_layer2_profile_gate.py`.
- **Gate run launched** (background, `bg-75`) to test production admissibility.
- No default changed. **This unit ran on the GPU.**

## Result

Shape: **one token, 10 selected experts of 512, 2560 -> 640** (the real `ffn_gate_exps` /
`ffn_up_exps` geometry), 18,432,000 bytes per dispatch. 5 warmups, 30 reps, min, sync both sides.
Host **gfx1151**, machine_id `55ea6c509d0b49eea8de7094a1023668` - the same host as every artifact
in this campaign.

## Why this candidate

Ledger section 7I records `DP4A safe-43 decode (Q4_DP4A64)` as *"withdrawn - Part of the failed
composition"* with **no reopen condition at all**. Three checks say that verdict does not survive:

1. **Its own acceptance passed.** `_DECODE_EVIDENCE` =
   `2026-08-29-gfx1151-qwen38-flash-next-production-dp4a-safe43-decode.json`,
   `status: accepted_explicit_production_profile`, **mean KL 2.72e-4, max KL 5.77e-3**.
2. **The recovery's triggering candidate did not touch it.** `production_q8_fallback` declares
   *"other production paths unchanged"* and failed on **task quality** (a fabricated Llama-2 GQA
   claim), not on this route.
3. **The only measurement of the flag's own cost was in a phase where it is inert.**
   `2026-09-16-disabled-family-recoverable-time` measured **prefill** (23.648 s fallback median),
   where a decode-only selector cannot act: `Q4_DP4A64` shows +0.066 s = 1.003x with
   **"Same logits: yes"**.

And the ledger itself records what disabling it cost: *"The September 14 recovery then disabled
`Q4_DP4A64` and the other decode selectors (**TG 18.1 -> 11.4 at 4K** ...)"* - a 37% decode
regression, from which QSA ordered decode was later restored but this route was not.

## Mechanism confirmed

`hipengine/generation/qwen4_exp_profiles.py` sets `HIPENGINE_QWEN4_EXP_Q4_DP4A64 = "1" if production`
and then, for `gguf_ud_q4_k_xl`, zeroes **every** flag in `PRODUCTION_ARITHMETIC_RECOVERY_FLAGS` -
which includes `Q4_DP4A64` - before restoring `PRODUCTION_Q8_QSA_RESTORED_FLAGS`, a **different**
set that does not contain it. Measured on the real bound profile:
`HIPENGINE_QWEN4_EXP_Q4_DP4A64 = '0'` while `PRODUCTION_Q4_DP4A_DECODE_LAYERS` still holds the full
**43 layers** `[0,2,5,6,8,9,10,11,13..47]`. So it was zeroed by a blanket sweep and never restored.

The runner's own selector (`qwen4_exp_runner.py:4975`) requires `rows == 1`, a shared gate/up quant
key, the flag truthy, the layer in `_LAYERS`, and the kernel registered. The candidate supplies the
one missing condition.

## Gate run

`scripts/qwen4exp_layer2_profile_gate.py --candidate decode_dp4a_linear`, launched as background
`bg-75`. The candidate's `environment` is applied **post-binder** (the gate builds the generator,
records `bound_environment`, then calls `os.environ.update(candidate_spec.environment)`), which is
the correct ordering for a recovery-zeroed flag.

**Result pending.** No promotion is claimed and no default changed.

## Projection, explicitly not a measurement

`DE-1`'s owner is 14.013 ms/step of a 54.218 ms/step decode kernel sum. At 2.0x that is ~7.0
ms/step, a **~7.0 ms/step saving = ~12.9%** of the decode kernel sum. This is arithmetic on a
kernel-level ratio, not an end-to-end measurement.

## Limits

- **Kernel-level screen only.** No profile gate result yet, no end-to-end decode run.
- **One shape.** This model is dynamically quantized; other layers may differ.
- **Synthetic weights**, not the model's own tensors.
- **One host** (gfx1151).
- The screen's exact-arm figure (~76-77 GB/s) is a min-of-30 micro-benchmark; the trace-derived
  figure for the same kernel is 63.43 GB/s from a profiled capture. They agree in magnitude and
  neither is a serving-path number.

## Validation

- **Ran on the GPU**, not derived: `scripts/qwen4exp_de1_decode_gemv_screen.py` executes both
  kernels and times them, so the 2.0x is a direct measurement.
- **Two independent runs** of the same protocol (2.073x, 1.983x) bound the run-to-run variance at
  ~5% and rule out a single lucky sample.
- **The exact arm is asserted bit-equal to the unfused reference** (`exact_bitexact_vs_unfused =
  True`), which validates the fixture and the comparison rather than assuming it.
- **The DP4A arm is charged for quantization** rather than measured matvec-only, per the row's own
  action requirement; the 12.0% share is reported separately so the charge is auditable.
- **Host identity checked, not assumed**: `machine_id = 55ea6c509d0b49eea8de7094a1023668`, matching
  every artifact in this campaign.
- **The bound profile was read directly** rather than inferred from source: constructing the real
  production generator prints `HIPENGINE_QWEN4_EXP_Q4_DP4A64 = '0'` alongside the full 43-layer
  `PRODUCTION_Q4_DP4A_DECODE_LAYERS`.
- **The candidate was exercised through the gate's own CLI** (`--help` lists `decode_dp4a_linear`)
  and the script parses clean.
- `scripts/sync_benchmark_readme.py --check`: synchronized.
