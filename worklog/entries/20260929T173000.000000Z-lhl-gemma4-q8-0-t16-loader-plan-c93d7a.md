# the Q8_0 T16 loader change: exact edit sites, verified

## Summary

Reconnaissance for the loader change that `20260929T163000` measured as a 1.4-1.8x lever on the
dense term. **No code was changed.** What follows is the mechanism, traced end to end, so the
implementation is mechanical rather than exploratory.

## The mechanism, traced

**1. The dispatch resolves on `quant_key`.** `gemma4_project` dispatches on storage form --
`isinstance(weight, int)` means a bf16 pointer, anything else is a GGUF device weight and goes to
`launch_gguf_linear`. That function reads `weight.spec.quant_key`, so setting the T16 key is what
selects the T16 registry entry. This is why a tiles allocation alone would not work: the raw key
has no bf16 WMMA prefill (`20260929T153000`).

**2. The pointer is chosen by ABI, not by layout.** The two call sites that matter:

```python
allocation_name = {"t16": "tiles"}.get(dispatch.abi)
...
allocation = weight.allocation(allocation_name)
```

and the ABI comes from the quant key:

```python
if abi == "t16" and quant == "gguf_q8_0_t16_v1":
```

**So the whole contract is: declare a `"tiles"` allocation, set `quant_key="gguf_q8_0_t16_v1"`,
and the dispatch reads `weight.allocation("tiles")` on its own.** No dispatch change is needed.

## The three edit sites

**`hipengine/loading/gemma4_gguf_device.py`, `_plan_one`** -- add a branch beside the existing Q4_K
one, which is the working precedent:

```python
if quant_key == "gguf_q4_k" and len(source.shape) == 3 and source.shape[1] % 32 == 0:
    allocation_names = ("raw", "t16_gate", "t16_up")     # existing
```

The Q8_0 case is rank-2 and needs one `"tiles"` allocation:

```python
if quant_key == "gguf_q8_0" and len(source.shape) == 2 and slot_path.startswith("layers."):
    return Gemma4GGUFWeightSpec(
        slot_path=slot_path, source=source,
        quant_key="gguf_q8_0_t16_v1",
        layout=LAYOUT_RAW_GGUF,
        allocation_names=("tiles",),
    )
```

`layout=LAYOUT_RAW_GGUF` is correct and not a shortcut: the tiles are uint8 blocks, so the existing
`storage_dtype == "uint8_blocks"` check passes and no new layout constant is needed.

**`hipengine/loading/gemma4_gguf_device.py`, the materializer** -- the existing repack loop assumes
`t16_gate` / `t16_up` and calls `derived_half_shape`, which raises for a rank-2 spec. It needs a
branch for `"tiles"` on a Q8_0 spec calling `repack_gguf_q8_0_tile16(raw)`, whose `.tiles` is
already the right dtype and shape (`e4583bb8c`).

**`hipengine/loading/gemma4_gguf_device.py`, the materializer** -- **`allocations["raw"]` is set
unconditionally today.** With `allocation_names=("tiles",)` the raw blocks would still be uploaded
and retained, doubling resident memory for these leaves (about 1.6 GB). Make the raw upload
conditional on `"raw" in spec.allocation_names`. **This is the one change that touches shared
code**, so it is the one to review hardest: the Q4_K expert path passes `("raw", "t16_gate",
"t16_up")` and must keep uploading raw.

## Why not keep both allocations

Keeping `("raw", "tiles")` would avoid touching the shared path, but it doubles the Q8_0 leaves'
resident memory for no benefit -- nothing reads the raw blocks once the T16 route is selected. The
repack itself costs exactly 1.0x, so a tiles-only spec is memory-neutral against today.

## What still needs gating

- **The decode path reads these same weights.** The T16 layout has its own GEMV decode kernels, so
  decode is not left without a route, but it is a different kernel and needs its own correctness
  and speed check. This is the main risk in the change.
- **Bit-losslessness is established** (`e4583bb8c`) but only for the repack, not for the end-to-end
  model output. The arithmetic gate is a teacher-forced comparison against the current build.
- **The expected win is -55 to -75 ms (-8 to -11 percent)**, and it is an expectation from an
  isolated microbench, not a measurement.
