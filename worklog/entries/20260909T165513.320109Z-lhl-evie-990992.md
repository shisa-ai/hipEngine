# EVIE INT8/FP8 quant evaluation: not applicable

## Summary

Evaluated INT8/FP8 weight quant for the encoder and rejected it on two
independent grounds: (1) no library support on this stack (rocBLAS
gemm_ex NOT_SUPPORTED for all int8/fp8 combos; hipBLASLt gfx1151 has no
int8/fp8 matmul algorithms — FP8 layouts accepted, zero heuristic
results), and (2) the runtime is launch-bound: all GEMM work is 18.6 ms
of a 231 ms page, so even a perfect 2x quant speedup gains <4% end to
end and cannot close the torch-bf16 gap.

## Changes

- `docs/MODEL-EVIE.md`: new "INT8/FP8 quantization evaluation" section
  with the evidence and the retrieval-first accuracy-gate design
  (embedding cosine, MaxSim delta, ranking preservation via top-1
  agreement / recall@k / Kendall tau) recorded for any future quant
  path.

## Validation

- rocBLAS int8 probe: gemm_ex status 11 for T,N / N,T / N,N / T,T at
  (9216, 151, 2560) with i8 A/B, i32 compute.
- hipBLASLt probes (AMD enums, harness sanity-checked against the working
  f16 problem): int8 compute descriptors rejected (INVALID_VALUE); i8
  operands with 32F compute rejected; FP8 E4M3/E5M2 datatypes accepted
  with zero algorithms on gfx1151.
- Page instrumentation (fixture doc page, fp16 mode): total 231.1 ms,
  dense `_gemm` incl. casts 16.3 ms, batched attention f16 GEMMs
  2.3 ms, other (launches, elementwise, GDN recurrence, host dispatch)
  212.5 ms.
- Note: earlier per-piece timings (e.g. "MLP 1.75 ms x 32 = 56 ms") were
  inflated by buffer-accumulation in the reps loops; the in-pipeline
  measurement above is authoritative.

## Next

The perf frontier is launch/dispatch overhead, not arithmetic: fusions,
fewer Python-level dispatches, and the remaining f16-stream tasks
(#16, #17).
