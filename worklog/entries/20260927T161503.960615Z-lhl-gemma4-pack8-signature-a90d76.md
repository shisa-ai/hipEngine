# The pack8 expert kernel needs six weight pointers, and a dual variant covers the fused gate/up

## Summary

The last unknown before implementation is answered, and the route change is well
defined rather than a redesign.

`hipengine_gguf_q4_k_expert_pack8_selected_bf16_bf16_out` takes:

```
x, selected, qweight_low, qweight_high, scales, mins, out,
x_rows, rows, num_experts, in_features, out_features, threads, stream
```

So it needs **six** weight and scale pointers where the current `selected_gemv`
route passes **one** `qweight`: `qweight_low` is `int32_t`, `qweight_high` is
`void*`, and `scales`/`mins` are `float` - matching the pack8 layout's fp32
`scales` and `mins`.

There is also a **dual** variant,
`gguf_q4_k_expert_pack8_dual_selected_bf16_bf16_out`, with an explicit
15-argument Python signature covering `qweight`/`scales`/`mins` for **both**
halves plus two output pointers. That is exactly Gemma 4's fused gate/up case in a
**single launch**, which is the shape the current route already uses.

So the route change is: thread the packed weight's arrays through the MoE route
and swap the registry lookup. Not a signature redesign.

**The one detail left for implementation:** `repack_gguf_q4_k_pack8` returns a
single int32 `qweight` array, while the kernel takes a `qweight_low`/`qweight_high`
pair. The kernel may expect the layout split, or `qweight_high` may be a
different structure entirely - that needs to be read from the kernel body before
the wiring is written, not assumed.
