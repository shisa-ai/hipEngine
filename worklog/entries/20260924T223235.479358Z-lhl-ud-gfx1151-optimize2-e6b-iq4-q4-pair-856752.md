# UD gfx1151 optimize2 E6b: (IQ4_XS gate, Q4_K up) mixed pair lands — bit-exact, 1.04×, −13.56 launches/tok conserved

## Summary

Iteration 12 landed E6 step 2a: the UD artifact's largest single mixed-quant
gate/up family — ordered (IQ4_XS gate, Q4_K up), **7 layers** — now runs a
fused pair + SiLU owner instead of two singles plus the elementwise kernel.

**What the census re-derived first** (fresh GGUFReader per-block recount over
both artifacts): UD = 65 gate/up blocks, 37 same-quant, **exactly 28 mixed
(22 IQ4-involved across 7 ordered combos, 6 K-quant across 3)** — matches
E4c's sizing to the digit. Plain = 65×(Q4_K, Q4_K) same-quant; its mixed
owners (`q6_q4_t16_mixed_grid_pair` 23.25/tok, narrow pairs 7.75×2) serve
other tensor classes, so plain's precedent proves two-quant pair owners are
buildable and registered, not that any UD combo is already covered. None of
UD's 10 ordered combos has an owner; the largest single combo is (23, 12) ×7.

**The lever (one family):** new fused owner
`hipengine/kernels/hip_gfx1100/fused/gguf_iq4_q4_pair.{hip,py}` +
registration (`linear_pair_silu`, `gguf_iq4_xs+gguf_q4_k_t16_v1`,
`iq4_q4_pair_silu_bf16_bf16_out`, reached via the `fused` package import the
gfx1151 alias mirror already loads) + one route block in
`launch_gguf_linear_pair_silu`. Exactness design:

- Side A = the local32 dual's split-K decode verbatim, wave count from the
  shared `_local32_waves` rule (imported, not copied), so its association
  matches the session local32 single's.
- Side B = the dense Q4T16 single's **full single-wave chain recomputed in
  every wave with only wave 0's partial published** — the single always
  accumulates all superblocks in one wave, so publishing wave 0 keeps side B
  bit-identical for any wave count instead of re-associating K across waves.
- Both accumulators bf16-round exactly where `silu_mul_separate_out` reads
  the buffers, then that kernel's SiLU arithmetic verbatim.

**Gates, all green:**

- RED→GREEN unit route test (fires for the ordered combo at rows==1;
  reversed order and rows≠1 decline — each is its own future unit).
- GPU exactness test (HIP-guarded): pair == `iq4 single + q4 single +
  silu_mul` bit-for-bit at K=5120.
- Production-shape screen `(5120, 17408)` rows=1: **bit-exact AND 1.04×**
  (504.2 vs 523.3 µs/layer, allocate-once, warm 10 + 50 measured) — ships,
  unlike E6a's rejected 0.93× dual.
- Conservation census through the `LLM.generate()` graph path (e4b → e6b
  baseline): pair fires **6.78/tok**, IQ4 singles −6.79, Q4 singles −6.78,
  silu −6.78 → **807.97 → 794.41 launches/tok (−13.56; the four deltas sum
  to −13.57 — exact conservation, zero collateral drift)**, decode
  pure_us −54.6 µs/tok (84828.8 → 84774.2).

**The probe caught what the harness could not.** The first census run
crashed with `KeyError: 'tiles'`: side A (IQ4 local32) reads the **`raw`**
allocation — the local32 column bytes live there, as the IQ4 same-quant
dual passes them — while the unit fake exposes all five allocations, so the
route test passed with a pointer the production weight does not have. Fixed
to `raw` (side A) / `tiles` (side B) with the reason in-line; test
expectation corrected to the production-true `(x, raw, tiles, out, ...)`.
This is the "works in the harness is not works" gate earning its keep, and
the route now carries the comment that documents the asymmetry.

Note on the direct→tile8 split seen between the E4 and E4b census snapshots
(84.28/42.62 → 10.66/116.25, perfectly conserved): it predates this change —
`e4b-census-ud.json` already carries the post-E4b numbers at 807.97 total.
The E6b conservation is therefore computed against **e4b**, the last pre-E6b
census, where only the four family symbols move.
