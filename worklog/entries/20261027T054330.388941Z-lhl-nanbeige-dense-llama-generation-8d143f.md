# Bring dense Llama generation across the public surface

## Summary

The dense Llama-family path already admitted checkpoints, materialized FP8/BF16
weights, and ran a capture-capable prompt pass, but nothing reached it: the
loader and runner were imported only by tests, and there was no decode path or
generation registration. This unit adds a KV cache, a one-token decode step, a
tokenizer adapter, and a registered generator, so `hipengine.LLM.generate()`
serves the checkpoint it was written for — `primitive-ai/Nanbeige4.3-33B-FP8`
(`LlamaForCausalLM`, head_dim 128, GQA 56/8, `rope_theta` 120e6,
compressed-tensors FP8 per-output-channel, `lm_head` unquantized).

## Changes

- `hipengine/runtime/llama_dense.py` (new): `LlamaKVCache` (one contiguous BF16
  `[max_context, kv_width]` buffer per layer plus a device context-length
  scalar) and `LlamaDenseRunner`, which adds `decode_step()` to the existing
  prefill runner. Decode uses the tree's dense GQA decode attention
  (`qwen35_full_attn_decode_context_bf16`): FP32 query and output against the
  BF16 cache, so Q is widened with `bf16_to_f32` and the attention output is
  narrowed with `f32_to_bf16` before `o_proj`.
- `hipengine/runtime/llama_prefill.py`: `prefill()` takes an optional
  `kv_cache` sink and writes each layer's roped K/V through it. The sink is a
  structural `write()` call, so this module still owns no cache layout. Logits
  and captured taps are unchanged.
- `hipengine/tokenization/llama_dense.py` (new): `tokenizer.json` adapter that
  validates vocabulary width and chat-token ids against the checkpoint, and
  renders the checkpoint's own ChatML prompt (system turn, assistant prefix,
  ` thinking` per the template's default). A non-ChatML template is refused by
  name instead of being rendered with markers its tokenizer may not carry.
- `hipengine/generation/llama_dense.py` (new): `LlamaDenseGenerator`, registered
  for `(llama_dense, hip_gfx1100|hip_gfx1151, bf16)`. Prompt pass, then one
  `decode_step` per token; token selection is the shared
  `sampling.select_token`, so temperature/top-k/top-p/min-p, logit bias, and the
  history penalties behave as they do everywhere else.
- `hipengine/generation/__init__.py`: import the new module from
  `register_builtin_generators`.
- `tests/_llama_tiny.py`: the fixture now writes a word-level `tokenizer.json`
  (markers isolated, every decoder row decodable), declares eos/bos, retains
  per-layer K/V in the reference trace, and adds
  `tiny_llama_reference_decode()` — a KV-cache greedy reference with the same
  per-op BF16 rounding as the prefill reference.
- `tests/test_gpu_llama_dense_decode.py` (new), `tests/test_unit_llama_dense_generation.py`
  (new).
- `docs/REFACTOR.md`: entry for the missing `head_dim` 128 flash owner and the
  64 KiB LDS decode ceiling. The prefill attention module already claimed this
  follow-up was recorded there; it now is.

## Decisions

- **Decode attention is the dense context kernel, not the paged path.** The
  dense kernel needs no block table and indexes the cache by absolute position,
  which is the whole cache contract here. The cost is its LDS score row: the
  servable context is `MAX_DENSE_DECODE_CONTEXT` = 16128 tokens, so the default
  is 8192 and a longer request is refused by name rather than silently clamped.
  The paged route lifts the ceiling and is the removal condition in
  `docs/REFACTOR.md`.
- **The generator owns a per-request cache, not a resident session.** It declares
  `supports_resident_session_kv = False` and one resident request. `LLM` drives
  it through the existing submit/poll bridge, which invokes one inner generation
  call per request, so no scheduler work was needed. A wider batch is refused
  with a named error.
- **Sampling is the shared host sampler, not a private one.** A second
  implementation would drift from the documented processing order. What this
  path cannot serve (grammar, tool-call constraints, forced-token queues,
  multi-token stop sequences, logprobs, thinking budgets, speculative MTP,
  non-BF16 KV) is refused in `_validate_request` and listed in the error.
- **The context default is the checkpoint's, capped by the kernel's.** An
  explicit `context_length` above either bound is an error; only the default
  clamps.

## Validation

- `uv run pytest` over the five dense-Llama files: **56 passed** (21 new unit
  cases, 4 new GPU cases, 31 pre-existing).
- GPU decode assertions: the prompt pass leaves the reference's roped K and
  projected V in the cache **bit-identical**; five decode-step logits track the
  KV-cache reference within `1e-2` of peak with matching argmax; greedy tokens
  from the runner equal the reference's; and `LLM.generate()` on the fixture
  emits the reference's greedy tokens with `LlamaDenseGenerator` behind the
  bridge, `quant=bf16`, and `backend` resolved to a registered key.
- Real checkpoint, Radeon 8060S (gfx1151), 125 GB unified memory:
  `LLM(Nanbeige4.3-33B-FP8, max_sequence_length=8192)` resolved to
  `backend=hip_gfx1151`, `quant=bf16`, `LlamaDenseGenerator`,
  `context_length=8192`. Weight load **114.4 s** for 34 GB of FP8 shards
  materialized to ~66 GB of resident BF16. A 25-token chat prompt generated 48
  greedy tokens in **15.47 s = 3.10 tok/s**, which is 66 GB / 0.322 s ≈ 205 GB/s
  of weight traffic — memory-bandwidth bound, not launch bound. Output was
  coherent continuation, and a second request on the same process reset the
  cache and generated normally.
- `python3 scripts/docs/check_all.py`: all 4 gates passed.

## Next

- The dense decode attention ceiling and the missing flash prefill owner are one
  follow-up, tracked in `docs/REFACTOR.md`.
- Throughput is roofline-bound on BF16-resident weights. Keeping the checkpoint's
  FP8 storage resident would cut weight traffic roughly in half and needs an
  FP8 GEMV/GEMM owner plus its numerical gate; that is a new kernel family, not a
  change to this path.
