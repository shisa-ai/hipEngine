# Native-cycle attribution diagnostic and identity-free sampled qualification

## Summary

The reported CPU failures were artifacts of the stashed working tree, not
defects; both pass on the restored sources. Three real changes landed instead.

First, `sampled_route_qualified_for` no longer falls back to identity-keyed
evidence rows. It answers from the plugin's implementation declaration alone, so
an artifact no measurement describes still runs when the kernels cover it.

Second, the native-state diagnostic was rebuilt around the lane the two recorded
divergences actually ran on. A lone speculative request keeps its per-request
`Qwen35GGUFTransactionalVerifier` at any `--max-active-requests`; that verifier
launches `Qwen35GGUFResidentSession.verify_target_block_native_cycle` with
`device_accept_commit=True`, so the N2 native target graph decides acceptance,
copies the selected Conv/GDN state row and hidden tap into the resident
destinations, and advances the cursor on device. `verify_target_blocks_batch`
runs only for a packed request group. A one-request packed target also exists,
behind the backend's `GGUF_SPECDEC2_MTP2_PHYSICAL_C1` capability (declared by
gfx1100, not by gfx1151) plus an explicit `packed_c1_target` evidence row. The
diagnostic resolves and records the lane, reproduces the singleton native cycle,
and refuses the packed lane instead of relabelling it.

Third, the verdict model separates four contracts. `strict_state_copy` is the
byte comparison of the committed destination against the captured verifier row
the accept selected. `ownership` is the row index, committed token, commit
position, resulting cursor, and visible tokens against the accept that selected
them. `repeatability` compares repeated native runs at the same prefix.
`numerical_drift` measures the native rows and committed state against AR and is
never gating. A top-1 or generated-ID difference alone is a diagnostic signal,
not a correctness failure.

## The commit-provenance check

The native graph's accept kernel writes `accept_buffers.commit_rows`, and
`linear_commit_kernel` copies that row from the captured
`_verify_linear_state_row_pair` buffers into `scratch.layer_conv_states` /
`scratch.layer_recurrent_states`; `hidden_commit_kernel` copies the same row of
the captured hidden taps into `scratch.hidden_seed_fp32`. After the launch the
diagnostic reads:

- `commit_row`, `commit_token`, `commit_position`, `end_position`,
  `accepted_draft_tokens`, `full_accept`, `next_token`, `input_token_ids`, and
  `token_ids` from `Qwen35GGUFNativeAcceptCommitResult`;
- `session.position` as the resulting cursor;
- the captured source row at `commit_row` and the resident destination per
  linear layer, plus row 0 when it is not the selected row;
- `result.hidden_seeds[commit_row]` and `scratch.hidden_seed_fp32`.

It then proves `commit_row == accepted`, `commit_token ==
input_token_ids[commit_row]`, `commit_position == start + commit_row`,
`end_position == commit_position + 1`, `session.position == end_position`,
`token_ids == drafts[:accepted] + [target_top1[commit_row]]`, and byte equality
of every committed destination against its selected source row. The hidden-tap
comparison also covers artifacts with no linear-attention layers. Nothing in
this check compares native state against AR state.

## The verdict model

Verdicts, in precedence order:

- `inconclusive_serial_control_mismatch` when the serial-exact control disagrees
  with AR state at the same cursor, so the comparison basis is broken.
- `repeatability_mismatch` when `--repeat` produced differing row top-1, logit
  bytes, commit metadata, or committed state; decisive for determinism and it
  blocks attributing the other readings.
- `commit_ownership_defect` when `strict_state_copy` or `ownership` is broken;
  decisive, and proven from the commit provenance rather than inferred.
- `inconclusive_ownership_unverified` when the commit provenance was not
  captured.
- `numerical_drift_measured` when ownership and the copy are exact and the
  repeats agree, but the native rows or committed state differ from AR. The
  block carries `gating: false`, the per-row top-1 mismatch list, shared
  `compare_logits` KL/delta metrics, the fingerprint mismatch list, and an
  elementwise per-layer state delta against AR. This replaces the earlier
  `row_arithmetic_drift` verdict, which wrongly treated a top-1 difference as
  decisive.
- `no_divergence_at_this_cycle` when the rows and committed state are
  bit-identical to AR.

## Record input

The diagnostic reads either record shape: a row-level `ids` list
(`/tmp/mtp-repair/moe-hostproposal-native.json`) or the OpenAI response field
`response.hipengine.token_accounting.choice_generated_token_ids`
(`/tmp/mtp-repair/qwen38-q4ks-http-matrix.json`). Without `--record-row` it takes
the first row that did not use MTP. The rendered prompt is checked against the
row's `usage.prompt_tokens` (512 for the MoE record, 22 for the Qwen3.8 record),
so a wrong template or reasoning mode fails before any GPU work. Measured on the
real records: `--prompt-reasoning none` renders exactly 512 and 22 tokens, while
`off` renders 516 and 26 and `open` renders 514 and 24, so `none` is the default.
The record's `thinking_policy` is a sampler-level MTP policy, not a prompt
setting; the earlier draft mapped it to `build_chat_prompt(reasoning="hint")`,
which that function rejects, and built the tokenizer as
`Qwen35GGUFTokenizer(path)`, which is missing required arguments.

Known capture limits, reported rather than worked around:

- The packed capacity>1 lane is not reproduced. Production's packed host path
  builds `TargetVerifyBuffers` from `_accept_target_batch_on_device`, and its
  device path uses `_commit_deferred_packed_verify_states_batch_device`; the
  earlier draft approximated it with a host accept count, which cannot prove the
  accept that selected the row. It was also not the lane of either recorded
  divergence, and the recorded backend (gfx1151) does not declare
  `GGUF_SPECDEC2_MTP2_PHYSICAL_C1`, so a lone request cannot reach the packed
  one-row target there.
- The HTTP records carry no per-cycle provider drafts, so the diagnostic uses
  the record's AR trajectory as candidates. The root row is the production row;
  deeper rows can differ from the production proposal.
- If the native graph is unavailable for the session, or the logits or captured
  state rows are missing, the diagnostic exits with the reason instead of
  substituting the eager fallback or inferring ownership from AR equality.
