# Gemma 4 P9: the parallel compaction path was already written and never called

## Summary

Iteration 12 found that `moe.route_glue` is 71% one kernel,
`qwen35_moe_group_compact_active`, at 153.1 us per launch. Reading it
explained the cost immediately: it launches **one workgroup of 256 threads**,
assigns each thread one expert, and has every thread **serially scan all
`total_lanes` twice** — once to count, once to scatter. That is
`num_experts x total_lanes` comparisons executed across two waves.

The same file already contains the fix. `qwen35_moe_group_compact_active_parallel`
(added upstream as "stable expert-major compaction without the serial 256 x
total_lanes scan") is exported from `hipengine.kernels.hip_gfx1100.moe`, its
Python wrapper takes `parallel: bool = False`, and **no production caller
passed it.** The only call site, `gemma4_experts.py`, was taking the default.

The change is one keyword: `parallel=True` at that call.

## Measurement

A/B over both variants on identical inputs, GPU 1, with **every output buffer
sentinel-filled (`-12345`) before each launch** — the coverage assertion the
iteration-11 bug made mandatory. All six outputs (`sorted_lanes`,
`sorted_experts`, `sorted_weights`, `expert_start`, `active_experts`,
`active_count`) were compared, not just the obvious ones:

| lanes | serial | parallel | speedup | all 6 outputs identical |
| ---: | ---: | ---: | ---: | :---: |
| 64 | 0.080 ms | 0.064 ms | 1.24x | yes |
| 128 | 0.076 ms | 0.057 ms | 1.33x | yes |
| 512 | 0.152 ms | 0.060 ms | 2.54x | yes |
| 1024 | 0.241 ms | 0.061 ms | 3.92x | yes |
| 4096 | 0.840 ms | 0.078 ms | 10.78x | yes |
| 32768 | 5.147 ms | 0.156 ms | 33.06x | yes |
| 65536 | 7.485 ms | 0.215 ms | 34.83x | yes |

The parallel path is faster at every size and **never slower**, so there is no
cross-over to model and no threshold to pick. Sentinel counts were zero for
`s_lanes`, `s_exps`, `s_wts`, `e_start` and `act_ct` at every size; `active`
correctly shows unwritten slots at small lane counts because it is a
variable-length list of only the nonempty experts, in both variants equally.

Production's serial time of 153.1 us per launch sits between the rows above,
so the real `total_lanes` is close to 512 — where the speedup is 2.54x.

| decode @1024 | 43.80 tok/s | 43.57 tok/s | -0.53% |
| decode @4096 | 40.17 tok/s | 39.95 tok/s | -0.55% |

`moe.router_gemm` moved 5.2 -> 5.3 and 20.5 -> 20.6, i.e. unchanged within
noise, so **the census delta landed only in the family that owns the change**.

**The decode cost is understood and is not the kernel.** The parallel launcher
performs three launches internally (count, prefix, scatter), while the call
site still runs its own `group_count` and `group_prefix_active` immediately
before — five launches where the serial path took three. Two extra launches
per MoE block over the decode step's layers accounts for roughly 0.5%, and it
matches the observed -0.53%. The redundancy is removable: `counts` has no
consumer after the prefix call, and the A/B showed the parallel path writes
`expert_start`, `active_experts` and `active_count` identically on its own.
That is the next change, not a reason to hold this one.
