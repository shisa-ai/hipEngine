# P8 remainder: full prefill blocks project through F32 rocBLAS SGEMM

## Summary

P8's remaining ask said "router logits through WMMA or hipBLASLt, blocked
on a dtype: `qwen35_router_logits_bf16_f32w` takes F32 weights, so the
named route means downcasting router_proj". The screen found the
unnamed route that needs no downcast: keep the F32 weights, upcast the
BF16 prescaled row bit-exactly, and project through the bound rocBLAS
`sgemm_rowmajor_nt` -- same inputs as the tile route, different
accumulation order. It wins from ~896 rows up (1.18x at the 1024-row
production block, 2.48-3.07x at 4096 on W7900/XTX), and the row's named
F16-downcast route loses to it on both counts: slower at 4096 (0.3030
vs 0.2444 ms on XTX) and ~100x less accurate (maxabs 5.0e-03 vs
4.7e-05 against float64). The tier is `tokens >= 1024`
(= DEFAULT_PREFILL_BLOCK); narrower blocks keep the token tile, which
still wins beneath ~830 rows, and decode stays on the fused launch.

## Changes

- - `gemma4_router.py`: `_ROUTER_SGEMM_MIN_TOKENS = 1024` selects a third
  projection tier inside `gemma4_router_topk_bf16` -- `bf16_to_f32` of
  the prescaled row into a new lazy `prescaled_f32` scratch buffer
  (counted in `_sizes()` so the whole-table upper bound stays honest;
  never allocated by a decode-only runner) plus
  `rocblas.sgemm_rowmajor_nt` over the unchanged F32 `proj_ptr`.
  Selection is by row count only, the same shape of dispatch as the
  token-tile tier; no flag. Module/chain docstrings updated (and the
  stale `threads=256` corrected to the actual 128).
- Tests: `tests/test_gpu_gemma4_router_variant_selection.py` gains the
  RED-first `test_router_chain_routes_full_prefill_blocks_through_sgemma`
  -- a counting `get_rocblas` wrapper proves the chain really calls
  SGEMM at 1024 rows (RED: AttributeError on the missing symbol), two
  runs must be bit-identical, and the selection invariant is the file's
  existing one: the new route's top-8 sets may not disagree with the
  float64 anchor more often than the tile route's. Measured at
  1024x2816->128: chain vs tile 0/1024 rows differ, chain vs float64
  0/1024, tile vs float64 0/1024 (the anchor must be the SAME
  prescaled row both routes consume -- a first draft anchored on raw
  hidden made both arms mismatch 1024/1024 and proved nothing).
- Screens/harness: `scratch/p8_router_sgemm_screen.py` (full ladder
  1..4096 rows, dynamic gpu label, numpy-float64 and finite guards
  before timing), `scratch/p8_gate_chain.sh` + the three wrappers
  (baseline arm = the selection constant raised at runtime so the
  capture runs the pre-change tile route on the same tree; route
  counter for the 4.4 check), `scratch/p8_maxblock_probe.py` (fit
  flip check).

## Validation

- - Screen, both cards, artifacts `2026-09-30-gemma4-p8-router-gemm-screen.json`
  (W7900) and `-xtx.json`: A/B/C/D at every ladder point; crossover
  between 768 and 896 rows on both; B wins 1024 (0.1632 -> 0.1379
  W7900, 0.1835 -> 0.1379 XTX) and 4096 (0.6603 -> 0.2659, 0.7363 ->
  0.2443); C (F16 downcast) never wins.
- Teacher-forced gate, campaign recipe, baseline captured with the tier
  pinned off on the same tree: `--prompt 2048 --prefill 1024` PASS
  (kl_max 0.0141 vs 0.05, mean 2.23e-05 vs 1e-3, p99 1.93e-4, top-1
  1.0, 0 flips; artifact `...-p8-router-sgemm-gate.json`), and the
  wider `--prompt 5120 --prefill 4096` PASS (kl_max 0.0166, mean
  2.90e-05, top-1 1.0, 0 flips; artifact `...-gate-4096.json`). Both
  provenance: W7900, `max_block 1024` -- the tier was exercised, not
  vacuously compared. (V1's recorded 4096 failure, kl_max 0.224
  bisectioned to the tt16 commit, compares against a pre-tt16
  baseline; this gate compares the tile arm at HEAD against the
  sgemm arm at HEAD and passes.)
- Reachability (4.4): the fit only keeps 1024-row blocks where memory
  allows. On the idle 48 GB W7900 it does, and the instrumented
  campaign bench records `P8_ROUTE_SGEMM_CALLS=150` with
  `path parity=True`. On the occupied 24 GB XTX (8.7 GB held by other
  jobs) the fit takes 512 at every context from 2048 to 8192; there
  the tier correctly stays silent -- at 512 rows the tile is faster
  (0.0671 vs 0.1265), so firing would have been the regression.
- Same-binary bench A/B on the W7900 (artifacts
  `...-p8-router-sgemm-head.json` / `...-p8-router-tile-base.json`,
  prompt 1024 / output 128 / 3 samples): prefill 0.38 s (2685-2692
  tok/s) with the tier against 0.39 s (2637-2651) on the tile arm;
  decode 71.3 vs 70.9 tok/s (the tier never runs at tokens==1, so
  this is noise).
- Fit flip: `p8_maxblock_probe.py with_f32|without_f32 --context
  8192` on the XTX reads `max_block 512` BOTH ways -- the new
  `prescaled_f32` table entry (11.5 MB at block 1024) did not push
  any fit decision across a boundary.
- Loops metric: d8 probe `per_decode_step.hip_host_ms` 4.5958 vs
  iteration 150's 4.6024 -- not worse (decode routes through the
  fused tokens==1 launch, untouched).
- Tests: RED battery 3/3; router/decode-graph/contracts bundle green
  except two documented pre-existing (weighted-accumulate bitwise,
  order-dependent incremental-decode which passes 4/4 isolated);
  default tier 8 failures, all in the documented set (runner x6,
  weighted-accumulate, specdec2 bridge) -- zero new.
