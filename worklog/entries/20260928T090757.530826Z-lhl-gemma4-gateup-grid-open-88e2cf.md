# the gate up caller passes the per expert width so grid x should be 44 and the trace says 5632

## Summary

`20260928T090630` left one contradiction: the trace's
`grid = (5632, 8, 1)` for the MoE gate/up MMQ requires
`out_features_total = 180,224`, while the caller appeared to pass one expert's
width. **This unit traced the value end to end and it is the per-expert 704.
The contradiction stands, and it is now bounded rather than vague.**

The chain, each link read:

| where | value |
| --- | --- |
| `gemma4_layer.py:195` | `Gemma4ExpertScratch(intermediate=self.expert_intermediate, ...)` |
| `gemma4_layer.py:177` | `expert_intermediate: int` |
| `runtime/gemma4.py:577` | `expert_intermediate=config.moe_intermediate_size` |
| `loading/gemma4_gguf_materialize.py:89` | `moe_intermediate_size=config.expert_feed_forward_length` |
| `loading/gemma4_gguf_materialize.py:231` | `fused_width = 2 * config.expert_feed_forward_length` |
| gemma4 26B-A4B | `expert_feed_forward_length = 704`, `num_experts = 128` |

So `intermediate = 704`, `out_features_a = out_features_b = 704`,
`out_features_total = 1408`, and **`grid.x` is 44** -- confirmed independently
by the per-expert stride: `expert_stride_rows = out_features_a +
out_features_b = 1408` matches the tensor's `(num_experts, 2 * 704, 2816)`
shape, which is what `fused_width` names.

The Python wrapper at `gguf_q4_k_q8_1_selected_prefill.py:1760` and the
`extern "C"` shim at `.hip:6870` both pass `out_features_a`/`out_features_b`
straight through, and `launch_selected_dual_q8_1_ds4_mmq32_compact32` computes
`grid.x = out_features_total / 32` at `:4990` and launches that grid at `:4998`.
There is exactly one call site (`gemma4_experts.py:1201`).

**The trace says 5632, which is `44 x 128 = grid.x x num_experts`.**

## What is ruled out

* **A stale .so.** `9eb796652` -- "the mmq gate reads the runner's declared
  width" -- is the only commit touching this area, it is timestamped
  06:28 UTC, and the trace's schema creation is 08:46 UTC. It changed the
  route gate (`lanes` to `route_width`) and **not** the arguments.
* **An argument-order mismatch.** The Python signature and the C++ shim agree
  field for field.
* **A second call site.** There is one.
* **`grid_size_x` meaning something else.** `workgroup_size_x = 128` is the
  block and `grid_size_y` tracks `mmq_total_rows/32` correctly (8 during decode,
  155-205 during prefill), so the x column is the x dimension.

## What is not ruled out

1. **The .so loaded at trace time was built from a revision where the grid
   included `num_experts`.** The build cache is content-hashed, so the artifact
   that ran is identifiable in principle, but I did not identify it.
2. **The trace is not from this call site.** The mangled name matches
   `..._mmq32_fused_prefill_compact32_kernelILi1EE`, and gemma4-only kernels
   (`gemma4_rmsnorm_kernel`, `gemma4_attention_decode_class`,
   `gemma4_moe_lane_to_row`) appear throughout the same region, so this is
   unlikely but not excluded.

**I tried to settle it empirically with a fresh `rocprofv3 --kernel-trace` run
and rocprofv3 wrote no output** -- the target directory stayed empty and no
`*_kernel_trace.csv` appeared anywhere, so the run produced nothing to read.
That is a tooling failure, not evidence either way, and it is the reason this
stays open.

## Why it is worth closing

If `grid.x` really is 5632, then **45,056 blocks are launched for 352 blocks of
work** -- the 44 that matter per row tile, against 5588 per row tile that take
the `global_col_base >= out_features_total` early-out. The gate/up is 24.5
percent of decode and streams 17.8 MB per layer in about 244 us, and
`20260928T090630` established it is not arithmetic-bound. **A 128x block
over-launch is a candidate explanation and a cheap fix**, so the fact is worth
one more attempt rather than a shrug.

If it is 44, then the early-out reasoning in `20260928T084954` was right for
the wrong reason and the grid is already minimal -- in which case the 73 GB/s
comes from the K-loop's serial tile loads and barrier on only 352 blocks, which
is a different fix again.
