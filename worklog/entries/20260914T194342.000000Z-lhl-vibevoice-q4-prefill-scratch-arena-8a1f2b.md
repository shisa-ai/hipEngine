# Prefill scratch: per-runner arena instead of ~20 malloc/free pairs per call (3.2-4.1%)

## Summary

Both prefill routes allocated roughly 20 scratch buffers with individual
`malloc` calls per call and freed them in a `finally` block — 22 device
allocations of 36.6 MB for an 89-row prompt, costing a directly measured
4.22 ms of a 220.2 ms prefill (1.92%).

They now take aligned views from a per-runner `DeviceMemoryArena` that is
rewound on reuse and replaced only when a larger row count needs more room.
`positions`/`counts` come from the same arena instead of being uploaded
separately. Measured in-process with a rotating A/B that reproduces the old
behaviour through a shim:

| lane | ms | trials |
| --- | ---: | --- |
| per-call malloc/free | 223.8 | 224.0, 224.0, 226.0, 220.9, 223.9, 221.5, 222.6, 223.7 |
| reused arena | 216.8 | 215.6, 215.2, 217.0, 217.1, 220.0, 220.4, 216.7, 215.0 |

**+7.0 ms (+3.22%)**, with bit-identical output (same `hidden_rows` SHA-256,
logits SHA-256, logits sum and argmax). A repeated prefill now performs **zero**
device allocations.

## Changes

- `hipengine/runtime/vibevoice_qwen2.py`: add `_PrefillScratchArena`; the base
  `_prefill_batched` route takes its scratch and its `positions`/`counts` from
  it, and the `try/finally` free loop is gone. The arena is created in
  `__init__` and released in `close()`.
- `hipengine/runtime/vibevoice_qwen2_q4.py`: same arena for the Q4 runner.
- `hipengine/kernels/hip_gfx1100/vibevoice/q4.py`: `q4_prefill` takes its 22
  scratch views from `runner._prefill_scratch`; `malloc`/`free`/`_upload`
  imports for this function are gone.
- `tests/test_gpu_vibevoice_qwen2_q4_runner.py`: reuse regression test.
- `benchmarks/results/2026-09-14-gfx1151-vibevoice-q4-prefill-scratch-arena.json`
  and a `benchmarks/CHANGELOG.md` line.

## Validation

- `test_prefill_scratch_is_reused_across_calls` patches `HipRuntime.malloc`, the
  single choke point every allocation path goes through, and requires a second
  same-size prefill to allocate nothing. RED on the parent revision with 22
  device allocations, GREEN after with 0. An earlier version of this test
  patched `DeviceMemoryArena.create` and was vacuous on the parent revision,
  because the old code allocated directly rather than through the arena.
- 75 passed, 1 xfailed across the Q4 and bf16 runner suites, the Q4 evidence
  suite, the front-end contract suite and the encoder kernel suite.
- Output is bit-identical before/after: same `hidden_rows` SHA-256, logits
  SHA-256, logits sum and argmax.
- Free path: the arena is released only through the base `close()` (which Q4
  runners reach via `super().close()`), and the arena views are never freed
  individually — one free path, so the double-free trap from
  `20260914T191520` cannot recur here.

### A probe bug worth recording

The first output-hash probe re-uploaded nothing between prefills, so each pass
consumed the previous pass's output as input — `prefill_rows` overwrites its
input buffer. The hash therefore depended on the iteration count, which is why
two runs of the same revision disagreed after the trial count changed. The
probe now restores the input buffer before every pass; the hashes above come
from the corrected probe. This is the same buffer-reuse trap already recorded in
`20260914T180119`, and it is easy to hit again from a throwaway timing script.
