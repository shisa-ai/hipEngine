# gemma4 gfx1151: the decode and prefill walks are both issue-bound, and the prefill moves 25x fewer bytes per instruction

## Summary

The two shapes of the full-layer kernel, same counters, same 65,536-key band, one
full layer:

| shape | duration ms | SQ busy | VALU | LDS | instr / SQ-cycle | **DRAM bytes per instruction** |
| --- | --- | --- | --- | --- | --- | --- |
| decode, 1 token | 1.40 | 99.5% | 1,144,904 | 577,666 | 0.45 | **156** |
| prefill, 256 tokens | 75.53 | 100.0% | 64,861,800 | 46,935,839 | 0.60 | **6.3** |

**Both are ~100% SQ-busy, so neither is waiting on memory.** The difference is
what they get per issued instruction, and it is a factor of 25.

That reframes the prefill finding. It is not a kernel that is badly *scheduled*
against DRAM; it is a kernel that amortizes DRAM across rows so effectively that
DRAM stops being the limit, and then does not convert the saved time into
throughput. The prefill's instruction count per token is 4x *lower* than the
decode's (437k against 1.72M) and its LDS count per token is 3x lower, so it is
already the more instruction-efficient of the two per unit of query work. It
simply moves so few bytes per instruction that 111.8M instructions buy only 708 MB.

## What this means for the fix

The direction is **fewer instructions per byte moved**, not a different memory
access pattern. Concretely, the prefill's 46.9M LDS instructions are 42% of its
count and are the staging loop re-loading the K and V tile for each of the 16-row
block's K-batches, so widening the K-batch (K_BATCH 16 -> 32) or widening the
query tile would cut instructions per staged byte. The source records why neither
is free: K_BATCH 32 does not fit in the 64 KB workgroup allocation alongside the
Q tile, and a 16-row by 8-head query tile is 130 KB. Those are the real
constraints, and they are shared-memory constraints, not bandwidth ones.

## The model gap worth naming

`docs/ROOFLINE.md`'s decision tree is built around DRAM and tensor limits. This
kernel sits at 4% of DRAM and ~1% of the tensor rate and is 100% issue-busy, which
is a third regime the tree does not currently branch on. Every "percent of
roofline" figure in this campaign has been a DRAM figure, and for the prefill that
was never the binding limit -- which is why the byte model's 97x error went
unnoticed for as long as it did.

## Next

- **Widen K_BATCH or the query tile, whichever the shared-memory budget allows.**
  That is the named, measured lever: it cuts LDS instructions per staged byte,
  and LDS is 42% of the instruction count. The 64 KB workgroup allocation is the
  constraint to work against.
- Attribute the 111.8M instructions concretely -- build a variant with the
  softmax chain stubbed and one with the staging loop stubbed, and read the
  counter difference. That turns the three named suspects into one.
- The sliding prefill kernel shares the tile structure; it should be measured the
  same way before the prefill path is touched.
