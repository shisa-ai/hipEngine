# The pack8 expert route measured 2.75x slower, so it is off by default with the cause recorded

## Summary

**The pack8 expert route is a measured loss, and the default is reverted.**

| arm | decode tok/s |
| --- | --- |
| baseline, no pack8 code | 21.03 |
| pack8 layout on | **7.64** |
| pack8 layout off, the new default | **20.9966** |

Same box, same command (`--prompt 512 --output 128 --samples 3`, 8060S), same
artifact. Prefill is unchanged at 265-266 tok/s throughout.

**The route was confirmed to be taken**, so this is the kernel and not a wiring
miss: `gemma4_moe_expert_route_counts` reported `pack8_selected: 928` with
`selected_gemv: 960`, the latter serving the tensors that have no packed layout.

**The mechanism is a representation trade that loses here.** The packed form
replaces the raw Q4_K block metadata with precomputed fp32 scale and min terms,
which is 1.33x the raw bytes. This projection is bandwidth-bound rather than
metadata-bound -- the earlier profile put it at 15% of achievable bandwidth, which
is exactly what made it look like a target -- so decoding less metadata means
reading more bytes. And the kernel is shaped for prefill
(`gguf_expert_pack8_selected_prefill_kernel`), while the ladder reaches it exactly
where rows are fewest: `grouped_prefill` takes every block with at least one row
per expert, so a packed weight is only selected below that threshold, which is the
decode case. The layout is reached where it is slowest.

**Correctness was never in question and is not the reason.** The same-weight
parity gate passes, and the raw route is separately pinned against the CPU
reference. Every correctness test passes with the layout on and off -- which is
precisely why the default now has its own test, since a silent flip back would
reintroduce a 2.75x regression with nothing else noticing.

**The flag is a legitimate default-off.** The product defaults permit default-off
for an observed failure with a named cause, and this is one: the number is recorded
where the flag is defined, in `docs/ENVS.md`, and in `docs/REFACTOR.md`, together
with what would clear it.

## Changes

- `hipengine/loading/gemma4_gguf_device.py`: `pack8_layout_enabled`, the `_plan_one`
  branch gated on it, and the measured cause written where the flag is defined.
- `tests/test_unit_gemma4_gguf_device.py`: the pack8 tests set the flag explicitly,
  and a new `test_the_pack8_layout_is_off_by_default` pins the default.
- `docs/ENVS.md`: the flag row with the measurement and the clearing condition.
- `docs/REFACTOR.md`: the flag, the unreached code, and the duplication it enables.
- `benchmarks/results/2026-09-27-gemma4-gfx1151-pack8-expert-route-measured.json`:
  the rejected candidate with all three arms.

## Validation

- The three-arm measurement above, re-run after the revert to confirm the baseline
  is restored rather than assumed.
- 63 passed across `tests/test_unit_gemma4_gguf_device.py` and
  `tests/test_unit_gemma4_expert_route.py`.
- `python3 scripts/docs/check_all.py`: all 4 gates pass, including env-var coverage
  for the new flag.
- **Pre-existing, reported not fixed:**
  `test_unit_gemma4_runner.py::test_incremental_decode_matches_a_dense_prefill`
  fails with the identical 4.417 max abs diff with these files stashed, so it is not
  a regression from this work.
- **Not measured:** the row count at which the packed layout would win. That is the
  one regime the ladder does not already give to `grouped_prefill` -- a large-batch
  decode where rows exceed the expert count -- and it is the named clearing
  condition.

## Next

- Either measure the packed layout above the expert count, or delete the unreached
  code. Keeping it is defensible only while that measurement is outstanding.
- The decode target is still 2X against a 21.0 tok/s baseline. This unit removed a
  candidate rather than moving the metric. The largest remaining decode line is
  still the MoE projection, and the bandwidth arithmetic says the headroom is real
  but is not reachable by changing the weight representation alone.
