# Surya phase-attributed profile: decode is 16.4-17.2 ms/token, not 26.7

## Summary

The 2026-09-11 Surya profile divided each phase's **whole-process** kernel total
by that phase's call count. `rocprofv3` aggregates a process, and a decode trace
must run the vision tower and a prefill to seed the KV state, so those setup
kernels were billed to decode. On the full page the setup is 1934 ms of kernel
time, 56% of the reported 26.737 ms/token.

Re-measured with kernels attributed to driver-recorded phase ranges, decode is
**16.376 ms/token** at a 106-token context and **17.204 ms/token** at 1066, so
context length costs **1.05x per token, not 1.58x**. The 2342 MB of fp32 text
weights stream at **136-143 GB/s** aggregate (155-163 GB/s inside the GEMMs),
and transfers inside the decode range are **0.007 ms/token (0.04%)** rather than
the 0.29 ms/token the whole-process total implied.

The two facts that drive the next optimization survive the correction: decode is
weight-bandwidth-bound, and 492 dispatches per token — 187 of them single-row
SGEMV at 75.21 us — are the largest structural cost on top of the streaming.
What does not survive is the context-length story: attention and softmax growth
with context was an artifact of the setup attribution, not a measured trend.

## Changes

`scripts/surya_gpu_rocprof_driver.py` records a host-side `CLOCK_MONOTONIC`
range around each phase and reports `ranges: [{name, calls, start_ns, end_ns}]`
alongside `calls_executed`. `calls` is the count **inside** the range, which is
not `calls_executed`: vision and prefill do one warmup outside their range, and
decode's step count is only known once the loop ends. That per-range count is
the divisor, so per-call cost is exact for every phase rather than only for
decode.

The clock choice is load-bearing and was not the first attempt. ROCTx is the
obvious mechanism: `libroctx64` loads, `roctxRangePushA` returns 0, and
`rocprofv3 --marker-trace` records nothing for it in this environment. The
kernel trace timestamps, however, are `CLOCK_MONOTONIC` nanoseconds — verified
by comparing a trace's first `Start_Timestamp` against
`time.clock_gettime_ns(CLOCK_MONOTONIC)` — so host-side boundaries taken around
a device synchronize slice the trace exactly, with no extra dependency.

`scripts/surya_profile_report.py` gains `_attribute`, which buckets kernels and
transfers into the range containing their `Start_Timestamp` and returns rows in
no range as `outside` rather than dropping or reassigning them, and
`_attribute_phases`, which makes the phase range the headline and retains the
unattributed trace as `whole_process`. Ranges are matched by the driver's own
`--phase`, not the `--trace` label, because one suite traces the same phase
twice (small and full pages). Without ranges the summary is labelled
`whole_process` instead of being presented as a phase cost.

`_context_span` promotes the decode context to a first-class artifact field
(`context: {context_start, context_end, mean_context, pos_start, pos_end,
 decode_steps}`, `null` for phases with no KV state) and the report prints it,
so a per-token cost cannot be read as measured at one endpoint context it never
saw. Ranges are also compacted in the artifact — the ranked kernel table is kept
only on the headline — because repeating a 20-row table of 500-character kernel
names per range tripled the file for no added information.

## Validation

Artifact: `benchmarks/results/2026-09-12-gfx1151-surya-phase-attributed-profile.json`.
The superseded artifact gains `superseded_by` and `superseded_reason` naming the
decode rows as wrong and the 1.58x reading as withdrawn.

Host: AMD Ryzen AI Max+ Pro 395, Radeon 8060S (gfx1151), HIP 7.15.26333. JIT
libraries were prebuilt outside the profiler and every profiled process ran
cache-only (`HIPENGINE_REQUIRE_CACHED_BUILD=1` with a precomputed compiler
version file), so no hipcc time is in any trace.

```
hipcc --version > /tmp/hipengine-hipcc-version.txt
for spec in ...; do HIPENGINE_HIP_ARCH=gfx1151 python3 \
    scripts/surya_gpu_rocprof_driver.py --phase $p --repeat $r --page $page; done
rocprofv3 --kernel-trace --memory-copy-trace --output-format csv -d <dir> -- \
  env HIPENGINE_HIP_ARCH=gfx1151 \
      HIPENGINE_COMPILER_VERSION_FILE=/tmp/hipengine-hipcc-version.txt \
      HIPENGINE_REQUIRE_CACHED_BUILD=1 \
  sh -c 'python3 scripts/surya_gpu_rocprof_driver.py --phase decode --repeat 200 \
         --page tests/fixtures/surya/page_small.png > <dir>/driver.json'
python3 scripts/surya_profile_report.py --trace decode-small=<dir> ... \
  --out benchmarks/results/2026-09-12-gfx1151-surya-phase-attributed-profile.json
```

| phase | 2026-09-11 ms/call | re-attributed ms/call | setup kernel time |
| --- | --- | --- | --- |
| vision 256 patches | 27.097 | 27.231 | (warmup outside range) |
| vision 4096 patches | 1019.203 | 1028.947 | (warmup outside range) |
| prefill 106 tokens | 95.599 | 95.485 | (warmup outside range) |
| prefill 1066 tokens | 793.623 | 792.118 | (warmup outside range) |
| decode @106 ctx | 16.967 | **16.376** | 132.854 ms |
| decode @1066 ctx | 26.737 | **17.204** | 1934.125 ms |
| request, 64 steps | 1161.256 | 1162.608 | 0.480 ms outside |

Derived for decode-small: 492.0 dispatches/token, 87.6% projection GEMMs,
2342 MB / 16.376 ms = 143.0 GB/s aggregate and 163.2 GB/s inside the GEMMs. For
decode-full: 88.0%, 136.1 GB/s and 154.7 GB/s. The context ratio is
17.204 / 16.376 = 1.0506x.

A quoted context is the start of its 200-step run, not a fixed length. The
driver now reports both, because mRoPE positions are not KV lengths: the
small-page run spans context 106-305 (mRoPE positions 50-249) and the full-page
run spans 1066-1265 (positions 74-273). The ratio therefore compares runs whose
mean contexts are about 206 and 1166, which is a 5.7x span rather than 10x, and
is the honest basis for calling decode flat in context at this range.

Cross-check against the superseded run, which is the reason to trust the
correction rather than suspect a workload change: the whole-request phase
reproduces its 1.452 s wall as 1.455 s (0.25%) and its first eight greedy ids
(1038, 1957, 1038, 1038, 1049, 1981, 1108, 1097) exactly. The vision and
prefill rows move by under 1% because for them the only change is excluding one
warmup call from the divisor (20 calls in range versus 21 executed).

Tests: `tests/test_surya_profile_report.py` (44 tests). New coverage: range
bucketing including the inclusive-start / exclusive-end boundary, untimestamped
rows staying outside every range, a setup kernel larger than the whole decode
being excluded from the phase cost, the per-range call count winning over
`calls_executed`, a range with no call count falling back to `calls_executed`,
a trace with no ranges being labelled `whole_process`, transfer attribution,
context-span extraction including the mean and the absent case, and
committed-artifact assertions that every phase headline equals its range, that
decode-full's setup exceeds half its decode total, and that both decode phases
carry a context span whose mRoPE end is below its KV end. The artifact
classification test now reads the current artifact.

Not a performance change: no kernel, dispatch, or default path was touched.
