# The Q8 dense-wide route is already live: prefill is ~256 tok/s, the published 185 tok/s row predates it by two days, and MoE is now the largest prefill cost

## Summary

I went looking for the next dense-projection win and found that the published
baseline describes a tree that no longer exists. **Three corrections, all
measured, and together they redirect where the remaining prefill time is.**

**1. The 6.74x wide-row route is already the production default and is running.**
`benchmarks/README.md` said of `dense_wide256_f32_f32_out`: *"It is registered but
not a default ... no production gate has been run."* That is false as of
2026-09-17. The certified plan for `gguf_ud_q4_k_xl` binds
`HIPENGINE_QWEN4_EXP_Q8_DENSE_WIDE=1` with
`HIPENGINE_QWEN4_EXP_Q8_DENSE_WIDE_LAYERS` at 16-47
(`hipengine/generation/qwen4_exp_profiles.py:52,794-802`), and it clears
`HIPENGINE_QWEN4_EXP_Q8_WMMA_LAYERS` because the two families selectable for the
same layers is the contention the 2026-09-17 route fix had to resolve.

**Measured, not read off the config.** A launch census over one real
`code-p4096` prefill at the production profile, 1595 launches total:

| kernel | launches | layers |
| --- | ---: | --- |
| `hipengine_gguf_q8_0_dense_wide256_f16in_f32_f32_out` | **1056** | 32 (16-47) |
| `hipengine_gguf_q8_0_gemv_coltile8_rowbatch4_wave_scale_pipelined_dpp_f32_f32_out` | **536** | 16 (0-15) |
| `hipengine_gguf_q8_0_pack8_gemv_f32_f32_out` | 3 | |

1056 = 32 layers x 33 and 536 = 16 layers x 33.5, so the wide kernel replaces the
coltile chain on exactly the certified two thirds and the exact chain keeps the
rest. **This also confirms the DPP leaf promoted in `20261003T220950` is on the
production path for layers 0-15** - the census names it, not the pipeline parent.

**2. The published 185.2 / 190.6 / 183.6 prefill row predates the route.** That row
is at `ddfc2a746` (2026-09-15), and `git show ddfc2a746:hipengine/generation/
qwen4_exp_profiles.py | grep -c PRODUCTION_Q8_DENSE_WIDE_PREFILL_LAYERS` returns
**0** - the constant does not exist at that commit. The route was certified two
days later, so the published row prices the exact chain on all 48 layers. The same
probe measured this prefill's wall at **15.986 s = 256.2 tok/s** for `code-p4096`
(single un-warmed call, so an upper bound on the wall and not a protocol-matched
rate).

**3. The cost model closes, which is what makes the reattribution safe.** On the
2026-09-16 per-role capture (22046 ms, `linear:` 10553 ms on the exact chain at all
48 layers), replacing two thirds of the dense projections at the measured 6.74x
predicts 3518 + 1045 = 4563 ms of `linear:` and a 16056 ms prefill. **Measured
15.986 s.** A 0.4% closure on an independent run means the old capture's *shape* is
still usable even though its *dense-projection rows* are now stale:

| family | 2026-09-16 capture | current, dense corrected | share now |
| --- | ---: | ---: | ---: |
| `moe` (gate+up 2710, down 1588, repair 1370, routing 931) | 6499 | **6499** | **40.6%** |
| `linear` | 10553 | 4563 | 28.5% |
| `gr_read` (pure gather) | 2539 | 2539 | 15.9% |
| `qsa_prefill` | 1421 | 1421 | 8.9% |
| `gdn` | 824 | 824 | 5.2% |
| boundary + ple | 110 | 110 | 0.7% |
| **total** | 22046 | **15956** | |

**The consequence is a ranking inversion.** The dense projections were the largest
prefill cost and are now second; **the routed MoE block is the largest single
prefill cost at ~40.6%**, and within it the `_risk_` repair pass alone is 1370 ms,
8.6% of the whole prefill, spent repairing a non-exact kernel. The dense-projection
lever is also not exhausted: layers 0-15 are still on the exact chain because the
f16 route "fails the calibrated envelope at 0-47 and passes at 16-47", so the
remaining question there is the numerics at 0-15, not the kernel.

**A second structural defect, already in the capture and now worth more:** the same
README records that `gr_read:hc_attn_down` and `gr_read:hc_ffn_down` are non-matmul
time, that the same tensor is read twice, and that **the gather costs 1271 + 1268 =
2539 ms against 549 + 549 = 1098 ms for the matmuls that consume it** - a gather
costing 2.3x the projection it feeds, 15.9% of the prefill.

## A harness hazard found while doing this

`wmma_prefill_dispatch_recorder` records into a `ContextVar`. My first probe drove
the prefill through `EngineService.generate_detailed`, which dispatches on worker
threads, so the recorder returned an **empty selector list** - not a "declined"
record, nothing at all - while the launch census showed the wide kernel running
1056 times. **A route-engagement gate that measures through `LLM.generate()` /
`EngineService` will silently report zero selectors and cannot distinguish that from
a route that did not fire.** The existing
`scripts/execution_profile_q8_wmma_prefill_layers_gate.py` is not affected because
it calls `runner.prefill(...)` directly on its own thread. The probe now reports the
launch census as the primary evidence and treats the selector summary as
corroboration only, and it writes its report immediately after the prefill so that a
teardown or summary failure cannot discard a completed run - four attempts were lost
to exactly that.
