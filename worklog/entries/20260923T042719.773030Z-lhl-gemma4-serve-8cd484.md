# Gemma 4 real-artifact serving: context limit dropped, chat prompt doubled BOS

## Summary

`LLM.generate()` now serves the real 17 GB UD-Q4_K_XL artifact on gfx1100 and
agrees with llama.cpp's greedy output on an identical prompt. Two defects in the
serving path surfaced only because the real artifact was finally available, and
both are fixed here.

The first was that `LLM(max_sequence_length=N)` was silently ignored for Gemma 4.
`LLM._factory_capacity_kwargs` forwards a configured limit only to a factory that
declares the parameter, and `make_gemma4_generator_gfx1100` declared neither
`max_sequence_length` nor `resident_capacity`, so the limit was dropped and the
generator kept its own 8192 default. That default is not launchable: the runner
sizes per-layer prefill scratch from the context, and at 8192 the artifact needs
17.00 GB of resident blocks + 52.68 GB of scratch + 1.85 GB of KV = 71.5 GB,
against a 48 GB W7900. Before the fix there was no route by which a user could
lower it.

The second was a doubled BOS. The artifact's chat template emits
`{{ bos_token }}` itself, and `tokenize_chat` encoded the rendered string with
`add_special_tokens=True`, inserting a second `<bos>`: 24 prompt tokens where
llama.cpp and HuggingFace produce 23. Both references tokenize a rendered chat
prompt without adding special tokens (llama.cpp
`tools/completion/completion.cpp:920` passes `add_special=false`; HF
`apply_chat_template(tokenize=True)` does the same).

## Changes

- `hipengine/generation/gemma4_gguf.py`: `make_gemma4_generator_gfx1100` takes
  `max_sequence_length` and passes it as the runner context;
  `Gemma4GGUFGenerator.tokenize_chat` encodes the rendered template with
  `add_special_tokens=False`.
- `tests/test_unit_gemma4_generate.py`: three tests. The factory forwards the
  limit (device-free); `LLM(max_sequence_length=1024)` reaches the built runner;
  chat tokenization produces exactly one BOS. All three were RED first -- the
  limit test observed `context_length=8192` for a requested 1024, and the BOS
  test observed `(2, 2, ...)`.
- `scripts/gemma4_real_generate.py`: the real-artifact end-to-end run through
  `hipengine.LLM`, on the llama.cpp-rendered 23-token prompt, comparing sampled
  ids against llama.cpp's.

## Validation

Real artifact, GPU 0 (W7900, 48 GB), `--context 2048 --max-tokens 12`, exit 0:

```
generator=Gemma4GGUFGenerator backend=hip_gfx1100 quant=gguf_q4_k_m context=2048
[thinking-on] prompt ids match llama.cpp: True (23 tokens)
[thinking-on] ids:  (100, 45518, 107, 236829, 139, 6804, 236787, 22168, 29104, 236761, 107, 140)
  text: '<|channel>thought\n*   Task: Say hello.\n    '
[thinking-on] first tokens match llama.cpp: True
[thinking-on-factual] ids:  (100, 45518, 107, 818, 2430, 563, 10980, 573, 506, 5279, 529, 7001)
  text: '<|channel>thought\nThe user is asking for the capital of France'
```

Token 100 is `<|channel>` and 45518 is `thought`; llama.cpp prints
`<|channel>thought` as its first greedy output on this sequence, and the
tokenizer has no single token for that string. Decode reached 20.7 tok/s on the
second request. `dmesg` `sq_intr` count was 394 before and 394 after: no new
faults. Full gemma4 tier: 166 passed, 0 failed, exit 0.

The `enable_thinking=True` path is what makes the prompt 23 tokens; the earlier
CPU probe that ran without it was measuring a different, reasoning-disabled
prompt.

## Next

The generator's 8192 default still cannot load on a 48 GB device, because
scratch is sized from the context rather than from the block being forwarded.
Now that the limit is plumbed, a caller can work around it, but the default
should work: chunk prefill inside `Gemma4Runner.forward` at a bounded block
(e.g. 1024, matching the engine loop's `prefill_chunk_size`) so scratch becomes
a block resource rather than a context resource. Chunk invariance is already
established -- `test_incremental_decode_matches_a_dense_prefill` shows a
one-token-at-a-time path is bit-identical to a dense prefill, and `_keep_mask`
is absolute-position based. That change needs a long-prompt real-artifact run to
exercise a block larger than the current 23-token prompt.
