# AR has only ~5% host slack, so its C6-C8 deficit is kernel-side

## Summary

Existing kernel-trace evidence shows AR's per-step wall time is ~95% traced kernel time.
AR therefore has
almost no host-side slack to recover, which puts the AR C6-C8 deficit in the same
kernel-side family as the
small-row prefill deficit (#12) rather than in host scheduling.

## Changes

- Decision about where to spend remaining effort; no code change.
- Reads an existing artifact; nothing re-measured here.

## Evidence

`benchmarks/results/2026-08-30-w7900-q4km-ar-rows-scaling-kernel-trace.json` (gfx1100,
Q4_K_M, production
profile, `rocprofv3 --kernel-trace` around `scripts/gguf_c1c8_ar_only_control.py`):

| rows | wall per step (ms) | traced kernel per step (ms) | device share |
| --- | ---: | ---: | ---: |
| C1 | 46.6 | 44.2 | 94.8% |
| C2 | 65.3 | 59.9 | 91.7% |

- Wall growth ratio C1->C2 is 1.40 against a kernel-time ratio of 1.355, so the width
  scaling itself is
  mostly kernel growth, not accumulating host work.
- Consequence for the decomposition numbers: AR decode-step cost (~34 ms at C1 in
  `20260830T143753…`) is almost entirely device time, so its w^0.36 scaling is a device-
  shape property.

## Inference, labelled

The artifact measures rows 1 and 2. Extending "AR is device-bound" to C6-C8 is an
inference from two widths and
a matched growth ratio; it is not measured there. If a future trace shows the device
share falling with width,
this decision needs revisiting.

## Consequences

- #12 stays the right target for the AR widths we lose (42.5-44.3 vs peer 45.5-58.7 tok/s
  at C6-C8): reduce
  kernel work per step at these row counts, do not look for host-side savings in the AR path.
- #17's analogous device-busy fraction for the K3 cycle is still unmeasured, and the
  harness for it does not
  exist: `scripts/mtp_verifier_rocprof.py` has zero GGUF references (safetensors path
  only) and there is no
  single-width MTP control script equivalent to `gguf_c1c8_ar_only_control.py`. Building
  that control script is
  the prerequisite for deciding between pipelining and capture for the MTP cycle.
- `rocm-smi --showuse` is a duty-cycle metric: a low reading proves idle time, a high
  reading proves nothing,
  so it is not a substitute for the trace.
