# UD MTP width scope: c1 is reachable, c2/c4/c8 need a UD serving-evidence row

## Summary

U6 item 6 names "c2/c4/c8 serving" as unmeasured. This entry records what
actually gates it, because the gate is structural rather than a missing run.

**c1 is reachable.** `scripts/gguf_mtp_c1c8_server_bench.py` on
`Qwen3.8-27B-UD-Q4_K_M.gguf` with `--widths 1` engages MTP on all ten canonical
prompts (`engaged: true`, `mtp_self_exact`, `ar_mtp_equal`), with MTP scope
granted in process. The server's resident capacity defaults to the maximum
measured width, so `--widths 1` gives capacity 1.

**c2/c4/c8 is refused before the run.** The same bench at
`--resident-capacity 8` refuses every cell, including width 1, with a recorded
reason:

```
[mtp2-decline] c1 singleton shape refused: existing_state=True,
automatic_singleton=False, physical_singleton=False, slot_count=8, capacity=8
```

That comes from `Qwen35GGUFMTP2Adapter.capability` in
`hipengine/generation/qwen35_gguf_mtp2.py`. Its condition is:

```
(existing is not None and existing.verifier is None and not physical_singleton)
or (not automatic_singleton and not physical_singleton
    and (slot_count > 1 or capacity > 1))
```

So the explicit C1 MTP route is admitted **only at resident capacity 1**. Above
that, MTP needs `physical_singleton`, which is

```
eligibility is not None and eligibility.eligible
and eligibility.max_realized_group_rows > 1
```

and `eligibility` is the serving plan's static eligibility, which only exists
for an artifact that has a `SpeculativeMTPServingEvidence` row failing solely
on `physical_group_not_qualified` (`hipengine/speculative/serving.py`). Those
rows live in `hipengine/models/qwen35.py`, and they cover exactly one weight
quant:

```
weight_quant values: ['gguf_q4_k_m']
realized_group_rows values: ['1', '2', '8']
resident_capacity values: ['1', '2', '4', '8']
```

There is **no UD serving-evidence row**. So UD MTP above capacity 1 is refused
by a table that the U6 pin is itself supposed to populate.

**This is not a deadlock, but it is an ordering constraint.** The
serving-evidence row is the *output* of qualification, and the qualification
measurements themselves do not need it: `scripts/ud_mtp_paired.py` and
`scripts/ud_mtp_ar_verify_numerics_gate.py` drive the resident session directly
and already grant MTP scope in process. The unblock path is therefore:

1. grant UD MTP *serving evidence* in process for a candidate run, the same
   candidate-mode pattern `ud_mtp_paired.mtp_scope_granted` already uses for
   scope, and record the artifact as diagnostic;
2. measure c2/c4/c8 on the server route that way;
3. write the real `SpeculativeMTPServingEvidence` rows for the UD artifacts
   citing those artifacts.

Step 3 is a product-admission change and is not done here.

**A second, independent bound: MTP serving stops at 1023 context.** The same
adapter caps streaming activation at

```
max_context = min(1023, *(target.target_layout.max_sequence_length ...))
```

with the comment that longer requests stay K0 until an exact shifted-page eager
target owner is qualified independently of graph capture. So a measured
verifier context beyond 1023 does not widen the *served* MTP envelope. The
declared `context_max` has to respect that cap, which is why the 4096 verifier
point is evidence about the verifier rather than about serving.

**Item 6's mechanical gate is the context, not the widths.** In
`Qwen35GGUFUDMTPCertification.blocked_items` the item is appended when
`context_max is None or not widths`. Both records already declare
`widths=(1,)`, which is non-empty, so what keeps item 6 open is
`context_max is None`. Declaring a narrower width envelope is the designed
mechanism: `widths` is a per-record field, not a constant.

## Changes

None. This entry records the mechanism; the run it describes is a smoke test,
not a retained measurement.

## Validation

- `gguf_mtp_c1c8_server_bench.py --model Qwen3.8-27B-UD-Q4_K_M.gguf --quant
  gguf_ud_q4_k_m --widths 1 --max-tokens 24 --candidate-budget 3`: ten
  canonical prompts, MTP engaged 10/10, `ar_self_exact`, `mtp_self_exact` and
  `ar_mtp_equal` all true, status `complete`.
- Same command with `--resident-capacity 8`: engaged 0/10, status `failed`,
  reason `w1: route expectation engaged=0/10 mtp_expected=True`, and
  `decision_reason` `backend_k0_fallback` on the row. With
  `HIPENGINE_MTP2_TRACE_DECLINE=1` the refusal above is printed verbatim.
- `python3 -c` scan of `hipengine/models/qwen35.py` for the evidence tables'
  axis values, as quoted above.
- The bench rates are a different protocol from the paired one (server path
  `gguf_packed_ar_server_decode` at ~14 tok/s AR, not the resident
  graph-replay leaf at ~32), so nothing here is a rate claim.
