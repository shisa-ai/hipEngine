# the token side tile was never swept because an unmeasured register assumption said it would not fit

## Summary

`2cf3a0a5f` swept the Q8_0 WMMA prefill tile space and moved the default to
`(64, 32)`, +9.9% prefill. That sweep's tile set was `tile_m in {16,32,64} x
tile_n in {16,32}` -- **it never tried `tile_n = 64`**, and the heuristic's own
docstring justified the omission with "32 is the largest value whose
accumulator and activation registers fit."

That was an assumption, not a measurement. **`(32, 64)` needs 143 VGPRs against
`(64, 32)`'s 127, and it is the fastest tile on three of gemma4's four dense
prefill shapes.** The dense family drops 4.121 -> 3.639 ms and prefill goes
0.773 -> 0.749 s.

**The reason the assumption survived is that the two directions are not
register-symmetric, so reasoning by analogy from the one that was measured
gives the wrong answer.** `my_out[TM]` is only an index array; `my_token[TN]`
and the activation gather are per-TN. So widening the token tile costs more
registers than widening the output tile at the same accumulator count -- which
is exactly why it was assumed unaffordable, and the real cost is 16 registers.

## The sweep

`rows=512`, bf16 in, bf16 out, best of 8, ms. All six tiles `maxdiff
0.000e+00` against the `(64,32)` reference on every shape.

## A defect this exposed in my own first attempt

My first pass added the tiles to `_ALLOWED_TILES` and to both launchers'
dispatch chains, then measured. Both new tiles failed with
`HIP error 1: invalid argument` and I read that as a resource rejection --
143 VGPRs against the `__launch_bounds__(32, 8)` budget.

It was not. **The C++ launchers carry their own argument guard that I had not
touched**, and it hard-coded the old tile set:

```cuda
(tile_n != 16 && tile_n != 32)) {
  return static_cast<int>(hipErrorInvalidValue);
}
```

The launcher rejected the tile before it ever reached the launch, and the
error code was the launcher's own return value rather than anything the
runtime reported. **The tell was available immediately and I read past it: a
resource rejection would have been a compile-time spill or a runtime launch
failure with a different code, and `hipErrorInvalidValue` is the code this
function returns for a rejected argument.** The dispatch chain, the Python
allow-list, and the guard are three separate places encoding the same tile
set; extending two of three produced a failure that looked like a hardware
limit.

## Why the change is free of arithmetic risk

A tile change reorders no arithmetic. It changes which output elements a block
owns, and every output's K-loop still accumulates in the same order over the
same values. That is why all six tiles are bit-identical here, and it is the
same property `2cf3a0a5f` relied on. No execution-profile gate applies.

## A larger finding on the qwen35moe shapes, which the profile pins separately

The `qwen4_exp_profiles.py` experiment profile pins this same flag pair at
``(64, 32)`` for the qwen35moe route (``:570``/``:571``). Those shapes were not
in the sweep above, so they were measured too -- same harness, same tile set,
``rows=512``, best of 8, all ``maxdiff 0.000e+00``:

| shape | out/rows | (64,32) | (32,64) | winner |
| --- | --- | --- | --- | --- |
| swa k/v 2816x2048 | 4.00 | **0.377** | 0.435 | (64,32) by 15% |
| qwen35moe ssm down 4096x2048 | 4.00 | **0.789** | 0.958 | (64,32) by 21% |
| global q_proj 2816x8192 | 16.0 | 2.603 | **1.799** | (32,64) by 45% |
| qwen35moe qkv 2048x8192 | 16.0 | 2.357 | **1.486** | (32,64) by 59% |
| **total** | | 6.126 | **4.678** | **(32,64) by 31%** |

**So the pinned value is stale for the same reason the gemma4 default was: it
was chosen from the sweep that never tried ``tile_n = 64``.**

Across all eight measured shapes the winner separates cleanly at
``out_features / rows = 5``: four below it (4.00, 4.00, 4.13, 4.00) all prefer
``(64, 32)`` and four above it (5.50, 5.50, 8.00, 16.0) all prefer
``(32, 64)``. **That is a tight bracket, [4.13, 5.50], but it is not yet a
rule.** Every one of the eight was measured at ``rows = 512``, so
``out/rows`` and plain ``out`` are indistinguishable in this data -- the
crossover could sit at ``out = 2560`` regardless of ``rows``. Separating them
needs the same shapes at ``rows`` 256 and 1024, which is the next unit rather
than something to assert now.

The mechanism is a trade of two byte streams with equal totals: weight bytes
are ``grid.y x out_features x K`` and activation bytes are
``grid.x x rows x K``. Both tiles have the same area, so the total is
identical and only the mix changes -- ``(32, 64)`` halves the weight reads and
doubles the activation reads. That favours the wider token tile when the
weight matrix is the larger one, which is the ``out > rows`` regime.

**The profile pin is left as it is.** Changing another route's production
tuning value is a change this unit cannot evidence end-to-end, and the
qwen35moe route was not loaded here. The microbench is strong and the exact
command to reproduce it is in the next section.

## Changes

* `hipengine/kernels/hip_gfx1100/quant/gguf_q8_0_prefill.hip` -- `(16,64)` and
  `(32,64)` instantiations in the single and dual launchers; both launchers'
  argument guards extended to accept `tile_n == 64`.
* `hipengine/kernels/hip_gfx1100/quant/gguf_q8_0_prefill.py` --
  `_ALLOWED_TILES` gains the two tiles; `_default_tiles` returns `(32, 64)` at
  `rows >= 64`, `(32, 32)` at `rows >= 32`, `(32, 16)` below, with `tile_m`
  falling back to 16 under `out_features 32`. The docstring records the sweep,
  the VGPR table, and the correction to the previous assumption.
* `tests/test_gpu_gguf_q8_0_wmma_prefill.py` -- the pinning test asserted the
  old `(64, 32)` default and the old `tile_n in {16, 32}` bound. It now asserts
  the measured rule and records why the previous comment was an assumption.
