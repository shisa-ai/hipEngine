# The gfx1151 llama.cpp baseline, and the prefill gap is length-dependent

## Summary

The objective's third item, "get llama.cpp baseline numbers", had no valid row on
this host. The campaign's reference is **68.92 tok/s decode on gfx1100 (W7900)**;
this worktree runs gfx1151, and `docs/OPTIMIZATION.md` §2 makes the two
independent lanes whose absolute rates may not be compared unless one declared
same-host protocol measured both. Measuring llama.cpp here supplies the missing
reference and turns the objective's two targets into numbers.

Same artifact, same host (AMD Radeon 8060S, gfx1151), llama.cpp build
`17252c769` through `llama-bench -ngl 99`:

| shape | llama.cpp | hipEngine | gap |
| --- | --- | --- | --- |
| pp512 | 1012.98 ± 31.24 | 271 | 3.74x |
| pp1024 | 1057.48 ± 0.91 | 251 | 4.21x |
| pp2048 | 1067.14 ± 4.05 | 220 | 4.85x |
| pp4096 | 1039.85 ± 52.38 | not measured | - |
| tg128 | 41.92 ± 0.11 | 20.03 | 2.09x |

Two readings matter more than the ratios:

- **The decode target is exactly the llama.cpp rate.** The objective asks for 2X
  on decode and the same-host reference is 2.09x. It is not a number to invent;
  it is "match the reference implementation".
- **Prefill is 3.7x to 4.9x, not the 30x the objective describes.** The campaign's
  grouped expert routes took 512/128 prefill from 11.617 to 4.200 s on gfx1100
  (2.77x) before this measurement, so the 30x framing predates that work.

## The structural finding

**llama.cpp's prefill is flat in prompt length; this engine's falls.**

| prompt | llama.cpp | hipEngine |
| --- | --- | --- |
| 512 | 1012.98 | 271 |
| 1024 | 1057.48 | 251 |
| 2048 | 1067.14 | 220 |

A weight-bandwidth-bound prefill should be flat or improve slightly with length,
which is what the reference does across a 512-to-4096 range. This engine loses
19 percent between 512 and 2048. The gap therefore widens exactly where the
objective's long-prompt cases live, and any candidate that only improves the
weight-bound routes will not close it.

This is stated as an observation, not an attribution. The campaign's iteration-49
`rocprofv3` profile on gfx1100 puts 81 percent of a 512-token prefill in three
weight-bound routes and 10.6 percent in attention; attention is the only O(n²)
term in that list, which makes it the first candidate, but that profile is a
gfx1100 lane and no equivalent attribution has been run on gfx1151.

## Changes

- `benchmarks/results/2026-09-28-gemma4-gfx1151-llamacpp-baseline.json`: the
  reference row, the engine row, the gap, and the length-dependence finding. It
  promotes nothing and changes no default.

## Validation

Both sides are same-host, same-artifact, same-shape measurements taken in this
session. llama.cpp is three repeats per point with `llama-bench`'s own spread
(0.11 to 52.38 tok/s across the points, largest at pp4096). The engine is three
samples per point through `scripts/gemma4_campaign_bench.py` with under 1 percent
spread at every point and `path parity true` in every run.

No kernel changed, so no correctness gate applies. The row is a reference
baseline and asserts no hipEngine improvement over a prior hipEngine row.

## Next

The prefill item needs an attribution on gfx1151 before a candidate is chosen,
because the length dependence says the gfx1100 profile's shape does not transfer.
A `rocprofv3` kernel trace at 512 and at 2048 on this host would separate the
flat part of the cost from the growing part, which is the one measurement that
decides whether attention or a weight-bound route is the right target.

The decode item needs the opposite: the same-host gap is a clean 2.09x and the
campaign has already identified a MoE roofline gap on gfx1100, so the question
there is whether that attribution holds on gfx1151.
