# Size the deferred MTP startup check at ~28 GiB free VRAM

## Summary

The on-device follow-up to `20260920T205110.389553Z` cannot run yet, and the
free-memory figure in that entry is wrong in a way that matters. A 15.33 GiB
GGUF does not need ~16 GiB of free VRAM; it needs **~28 GiB**, because the
device also holds the KV pool, its metadata, and the runtime workspace. The
machine currently has 15.91 GiB free - the concurrent `continue-gothrough`
loop's server holds ~104 GiB - so no configuration of this model fits. The
check is blocked on that server stopping; the code change it verifies is
already committed and covered by the server test suite.

## Measured requirement

From a successful 8192-context bf16 run of the 15.93 GiB Q4_K_M
(`/tmp/t43/server-a-mtp-w8192.log`):

```
INFO:     KVCache: storage=bf16 scale=fp32 slots=1 max_context_tokens=8192
          ... requested_kv=0.50 GiB metadata=0.66 GiB total=2.73 GiB
INFO:     STARTUP_MEMORY: final_stage=guard final_free=92.06 GiB
          final_used=27.94 GiB peak_stage=after_raw_warmup peak_used=27.94 GiB
          min_free_stage=after_raw_warmup min_free=92.06 GiB total=120.00 GiB
```

A 16384-context run of the same model reports `final_used=29.98 GiB`
(`/tmp/t44/server.log`). Weights alone reach 15.80 GiB of the 15.93 GiB file, so
the ~12 GiB above the file size is KV plus workspace, not optional overhead. The
minimum free VRAM for the check is therefore ~28 GiB, and a 20 GiB gate would
still only buy a minute-long load that dies in `prepare` with "automatic GGUF
resident context sizing found no allocatable context tokens" - which is exactly
how the first attempt failed (`/tmp/mtp-logs-check/eager.log`, port 8113).

## Changes

- No repository code. `/tmp/mtp-logs-check/run.sh` (the deferred-check probe) was
  hardened: a preflight gate that refuses below 30 GiB free VRAM with a reason,
  fail-fast on `startup failed` or process death instead of polling `/ready` for
  eight minutes, a `trap` that always kills the launched server, and a
  `status.txt` the caller can read without pipe buffering.
- The first attempt leaked its own server on port 8113: the timeout path exited
  without killing the pid. That server is stopped and both ports are free.

## Validation

- `MIN_FREE_GIB=999 bash /tmp/mtp-logs-check/run.sh` and the default gate both
  exit 2 at preflight with nothing launched; `ss` confirms ports 8113/8114 free.
- Current device state: `hipMemGetInfo` free=15.91 GiB of 120.00 GiB; host RAM
  112 GiB of 125 GiB used; the only `hipengine.server` process is the loop's
  (pid 1879881, started 05:34 local), and `.multiloop` reports the loop's
  iteration 15 as running.
