# Japanese flips the first token by prefill shape: the chunked production schedule is the outlier

## Summary

Running the gate for `general_ja` with the mismatch lists recorded turns the
dense27B divergence from a 1-vs-1 into a **2-vs-1 against the chunked
production schedule**: on this prompt the whole-prompt one-shot prefill and the
prefix-then-decode route agree with each other and disagree with the 256-row
chunked route, which is the schedule the engine serves. That is a stronger
result than "the gate compares schedules that cannot agree": for Japanese the
schedule shape decides the first token, and the product's own shape is the
minority side.

## Changes

- None. One gate run for `general_ja` with the artifact's recorded command
  (`--source-lifecycle completed`, `greedy_fast`) and `--json`.

## Validation

`/tmp/t30-ja/code.json`, status failed, `passed: false`. First-token votes:

| route | prefix prefill shape | first token |
| --- | --- | --- |
| candidate (prefix reuse) | 256-row chunks | **271** |
| `scheduler_chunk_diagnostic` (production schedule) | 256-row chunks | **271** |
| `one_shot_bulk_diagnostic` | one 1,224-row call | **96026** |
| `initial_state` / serial reference | one 1,024-row call + 200 single-row steps | **96026** |

State fingerprints are the same shape as `code`'s: 126 mismatches against the
one-shot reference (47 conv + 47 recurrent + 16 kv.key + 16 kv.value) and 128
against the serial one (48 + 48 + 16 + 16), with no `position` mismatch in
either. So the bit difference is universal in both categories and it is only
Japanese where it moves the decision -- but note which side of the split the
agreement falls on: the two single-call prefix prefills agree, and the chunked
one is alone. For `code` all four routes agree on the first token (248046) and
only the state bytes differ, which is the harmless end of the same phenomenon.

The product's route is the outlier here, so this cannot be closed as "the gate
is over-strict" alone. Two readings remain, and they need one more measurement
to separate:

- the 256-row chunked prefill has a real arithmetic defect for this shape
  (cross-chunk state handoff), or
- it is a legitimate rounding side and this prompt sits on a knife edge, in
  which case any chunk width would flip it too.

## Next

Serve the same prompt at several prefill chunk widths and compare the generated
ids. `HIPENGINE_MAX_PREFILL_CHUNK_TOKENS` (`hipengine/generation/engine_loop.py`,
default 256) is the knob, greedy sampling keeps the comparison exact, and the
served harness already in use (`scripts/sharegpt_mtp_routing_pass.py` with a
fixed prompt and `--speculative-mtp off`) reports `output_sha256` per row:

- if the output is stable at every width except 256, the production chunk width
  is implicated and the chunked path's cross-chunk handoff is the thing to
  inspect;
- if the output flips at every width, the prompt is knife-edge and the
  calibrated envelope has to be defined against a schedule-invariant reference
  rather than against any single schedule.

Only then: the gate's `passed` expression (make the production comparison
binding, keep the others as diagnostics with KL/top-1 recorded) and the
calibrated mean/tail/top-1 and task gates.
