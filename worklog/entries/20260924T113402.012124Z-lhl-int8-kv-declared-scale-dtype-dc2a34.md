# INT8 KV binds the declared scale dtype, not the fp16 request default

## Summary

An INT8 KV request carried the fp16 scale-dtype default into its capability key.
Every INT8 declaration is keyed fp32, so no declaration matched, the contract
resolved as `unsupported` with `max_direct_rows: 0`, and the shared direct INT8
decode leaf could not resolve at a group width above one. That is what closed
the automatic-INT8-MTP c2/c4 cell, and it is why the refusal named a contract
miss rather than the quality verdict the artifact actually carries.

The request default is the only source of the mismatch: `ServerConfig` and the
generation request params both default `kv_scale_dtype` to fp16, and
`_gguf_int8_effective_scale_dtype` raises it to fp32 only when a BF16
full-attention mirror is present at long context. Mirror-free INT8 -- the
configuration the unverified diagnostic override reaches -- stays on fp16.

## Changes

`hipengine/generation/qwen35_gguf.py`:

- `declared_int8_scale_dtype` returns the scale dtype the declarations name for
  a request's other axes when the requested dtype is not among them, and `None`
  when the request is already declared, no declaration covers the other axes, or
  none names a dtype.
- `_resolve_request_kv_policy` binds that dtype on the resolved policy before
  resolving the capability, so the capability, the prepared policy, and the
  session allocation agree on one contract, and appends the substitution to the
  resolution reason rather than applying it silently.

`tests/test_unit_qwen38_int8_kv_capability.py`:

- `test_int8_request_binds_the_declared_scale_dtype_not_the_fp16_default` pins
  fp16 to fp32 on both backends, leaves a request already on fp32 alone, and
  leaves a granularity no declaration covers (`hadamard_group32`) unsubstituted.
