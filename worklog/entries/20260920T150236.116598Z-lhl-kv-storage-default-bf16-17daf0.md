# Default server KV storage to bf16

## Summary

The server shipped `--kv-storage` defaulting to `int8_per_token_head`, which
silently disabled the speculative (MTP) route on every default-configured
server. All 15 retained `SpeculativeMTPServingEvidence` rows in
`hipengine/models/qwen35.py` carry `kv_storage="bf16"`, and the speculative path
has no int8 KV storage view at all (`_KV_POLICY = "paged_bf16_kv_live_spans"` in
`hipengine/speculative/paro_mtp_profiles.py`, hardcoded as `kv_backend_key` in
`hipengine/generation/qwen35_paro_mtp2.py`). The admission check at
`hipengine/speculative/serving.py:526` therefore fired
`kv_storage_not_qualified` on every request and MTP fell back to AR
unconditionally — not occasionally, but structurally, for any server left on
the default.

int8 KV is a compression tradeoff, not a precision improvement: it stores
roughly half the per-token KV bytes at lower KV precision. Presenting it as the
default made the accurate storage look like the fallback, and the help text
reinforced that by describing BF16 as what an artifact "fails closed" to.

## Changes

- `hipengine/server/__main__.py`: `--kv-storage` default is now `bf16`
  (`HIPENGINE_KV_STORAGE` still overrides). Rewrote the help text to name BF16 as
  the higher-precision baseline and the only storage with retained MTP evidence,
  and to describe `int8_per_token_head` as an explicit compressed opt-in.
- `docs/API.md`: documented default updated, and the 176,128-token resident
  context figure is now attributed to the int8 policy it was measured on rather
  than to the default. Removed the stale "pass `--kv-storage bf16` to force the
  previous behavior" line, which no longer means anything now that BF16 is the
  default.

## Validation

- `build_parser().parse_args(["--model", ...]).kv_storage` returns `'bf16'` with
  `HIPENGINE_KV_STORAGE` unset, and `'int8_per_token_head'` when the env var is
  set — so the override path still works.
- `uv run pytest` over the eight test files referencing `kv_storage`
  (`test_integration_gguf_context_ceiling_probe.py`,
  `test_integration_gguf_production_load_gate.py`,
  `test_integration_qwen38_packed_c1_teacher_repeat.py`,
  `test_live_qwen4exp_context_capacity.py`,
  `test_unit_concurrency2_production_load.py`,
  `test_unit_concurrency2_token_budget.py`, `test_unit_dispatch_batch.py`,
  `test_unit_generation_qwen35_paro.py`): 205 passed, exit 0, zero FAILED/ERROR.

Not yet validated: no end-to-end server run has been made against the new
default, so the claim "MTP now engages by default" rests on the admission logic
and evidence-row keys rather than an observed MTP cycle. A live server smoke on
the new default is owed.

## Next

- Run a live server on the new default and confirm the MTP route is admitted
  (no `kv_storage_not_qualified` in `/ready`) and that prefix caching remains off.
- **Prefix caching does not come along with this change.** Its blocker was
  measured on BF16 KV — `benchmarks/results/2026-09-20-w7900-gfx1100-prefix-gate-bf16.json`,
  six active-source scopes failing scheduler state-byte comparison and
  heldout-code exceeding production mean/p99/max KL of
  0.00678/0.12955/0.67657. BF16 is the configuration that failed, so
  `--prefix-cache off` stays the HTTP default.
- `kv_storage_not_qualified` names the wrong cause. It reads as "not yet
  measured" when the actual condition is that the speculative path has no int8
  KV storage view. A reader chasing MTP-on-int8 will look for a missing
  measurement instead of an unimplemented storage view. Naming the real cause in
  the reason string is a separate follow-up.
- The capacity cost of this default is unmeasured. int8 stored about half the
  per-token KV bytes, so BF16 holds proportionally less resident context at the
  same KV memory budget; the exact bf16 figure at the 48 GiB W7900 budget has
  not been re-measured.
