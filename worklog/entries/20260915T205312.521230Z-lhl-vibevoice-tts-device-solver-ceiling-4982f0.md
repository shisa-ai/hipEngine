# Measured ceiling for the device-side solver: 1.2358x on the diffusion frame, +5.56% of warm

## Summary

`20260915T205238.929028Z` narrowed the diffusion stage's remaining opportunity to one
thing: the per-step `eps` readback, which forces the host to block for the full
remaining device time and leaves the GPU idle while the numpy solver runs. Before
writing a HIP kernel for it, I measured the **ceiling** of that route directly, by
keeping all 42 head kernels and removing *only* the per-step D2H.

**Ceiling: 1.2358x on the diffusion frame -- 8.902 ms/frame, +222.6 ms per request,
+5.56% of the 4.005 s warm synthesis.** Larger than the ~4.1% I estimated in
`20260915T205121.492340Z`, because the saving includes the host numpy solver time and
not just the copy stall. Projected RTF: **1.201 -> ~1.134**.

No code retained; the measurement is the deliverable. The scope of the implementation
that would capture it is recorded below.

## Changes

None. Working tree clean.

## Validation

### Method

In-process A/B, two runs per arm, best-of-7, with `copy_device_to_host` monkeypatched
to a no-op for the "removed" arm. All 42 kernels still run; only the readback is
dropped, so the *output is garbage* -- this measures the timing ceiling, not a working
path:

```
with per-step D2H readback : 46.649 / 47.133 ms/frame -> best 46.649
D2H removed (ceiling)      : 38.009 / 37.747 ms/frame -> best 37.747
=> 1.2358x, saving 8.902 ms/frame
   25 frames: +222.6 ms of 4005 ms warm = +5.56%
```

The two arms are well separated (46.6/47.1 vs 38.0/37.7), unlike the neutral
condition-upload A/B in `20260915T205238.929028Z` (45.7-47.4 vs 45.8-46.3), so this
result is outside the noise band and is trustworthy.

### Caveat on the ceiling

8.902 ms/frame is an upper bound that assumes a device solver costs nothing. A real one
adds a kernel, but the tensors are tiny (2 x 64 = 128 fp32 values), so the added
device time should be a few microseconds against the ~8.9 ms recovered. Expect to land
close to the ceiling, not merely near it.

### Scope of the implementation

`sample_speech_tokens` (lines ~277-296) currently does five pieces of per-step host
work around `forward()`:

1. `combined = np.concatenate([half, half])` -- broadcast the first latent row
2. `raw_eps = self.forward(...)` -- 42 kernels **+ the D2H**
3. `np.split(raw_eps, 2)` -- split cond/uncond
4. the CFG combine, which is **bf16-grid rounding**, not plain fp32:
   `uncond + bf16_round(cfg_scale * (cond - uncond))`, then `bf16_round` of the sum
5. `sched.step(eps, t, speech)` -- the DPM-Solver++ order-2 midpoint update

To remove the readback, 1/3/4/5 must move onto the device, and `forward()` must return a
device pointer instead of a host array.

Two things that will decide whether this is bit-exact or merely quality-equivalent, and
which must be settled before the kernel is written:

- **`bf16_round` in the CFG combine is a real rounding step.** The device kernel has to
  reproduce round-to-nearest-even onto the bf16 grid at exactly those two points, or the
  arithmetic diverges from the reference.
- **`DPMSolverMultistepScheduler.step` is sequential fp32 accumulation**, the same
  property that made `_alpha_bar_tables` (see `20260915T203624.733692Z`) impossible to
  vectorise. Porting it means replicating the accumulation order, not just the formula.

If the port cannot be made bit-exact, it must be evaluated under the production-profile
gates in `docs/EXECUTION-PROFILES.md` before promotion -- a changed summation order here
is the same class of risk as the `threads=64` LM GEMV that
`quality-threads64-rejected.json` recorded as a 1.23x win with a quality cost.
