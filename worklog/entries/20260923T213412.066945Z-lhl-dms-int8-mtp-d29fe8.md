# Bind per-head variable DMS spans for multi-row verify attention

## Summary

Task 9, unit 1 of 4: the compact DMS device store can now bind a
``per_head_variable`` span set for several rows at once.

The gap was not in the kernel. ``dms_compact_attn_decode_splitk_int8`` already
reads ``base_offsets``/``live_counts`` as ``[rows, kv_heads]`` and indexes the
``[slots]`` float32 scale planes per slot; task 9's earlier pass gated that with
five GPU cases. The gap was in the store the AR route drives: every entry point
was one row. ``attention_layer_device`` hardcoded ``rows=1``, the split workspace
was allocated as ``q_heads * num_splits * dim``, and the only extent planes were
one ``[kv_heads]`` pair per layer. A verifier attending N rows of one request
therefore had no way to bind its span set, and the workspace could not have held
it if it had: at ``rows=3`` with three splits the kernel writes three times past
the one-row allocation.

The AR route keeps its own path unchanged. ``_ensure_split_workspace`` now takes
a row count and grows the allocation, never shrinks it, so a one-row call after a
verify chain keeps the wider buffer and the pointers a binding returned stay
valid. Growth is still a lifecycle boundary: the old partials are synchronised
and freed rather than left referenced by an in-flight launch.

## Changes

- ``hipengine/kvcache/dms_device.py``: ``_ensure_row_planes`` allocates the
  ``[rows, kv_heads]`` int32 extent planes on first bind, bounded by the store's
  existing ``max_pack_rows`` row bound. ``bind_row_spans`` validates and publishes
  them and returns the device pointers. ``attention_rows_device`` launches the
  split-K leaf for ``rows > 1`` from bound or caller-supplied planes, sizing the
  workspace for the row axis. ``attention_rows`` is the host-bound form, staging
  ``[rows, q_heads, dim]`` Q and output. ``split_workspace_bytes`` exposes the
  allocation for the gate.
- Both codecs route multi-row through their split-K leaf: it is the leaf whose
  per-row indexing and partial-output ABI cover more than one row, and the BF16
  producer already launches ``rows * (grouped ? kv_heads : q_heads) * num_splits``
  blocks.
- ``tests/test_gpu_dms_int8_device_payloads.py``: one new GPU case.

## Validation

- RED first: the new case failed with ``AttributeError: 'DMSDevicePayloadStore'
  object has no attribute 'attention_rows'`` after building its DMS state, so the
  fixture itself is proven to construct variable per-head extents (asserted
  ``live0[0] == tokens`` and ``0 < live0[1] < tokens``) and appends that extend
  both heads by exactly one.
- GREEN: the case passes. It builds a 520-token request where head 0 never evicts
  and head 1 evicts every other token outside the recency window, appends three
  draft tokens, and binds ``row_live = live0 + r + 1`` over three rows, which is
  the verify chain's own prefix law. Splits is 3, so the case exercises the
  split-K path, and the workspace assertion ``split_workspace_bytes >=
  rows * q_heads * splits * dim * 4`` is exactly what the previous one-row sizing
  could not satisfy.
- Oracle: the AR route's own attention, the same kernel called once per row with
  that row's own ``[kv_heads]`` counts and its own one-row workspace. Agreement
  within 3e-5, plus an explicit check that the rows are not all the same answer,
  which a binding that ignored the row axis would produce.
- The device entry point is covered separately with raw device pointers, no host
  staging, and eight repeats pin determinism bit-for-bit.
- ``test_gpu_kvcache_dms_device_hip.py`` + ``test_gpu_dms_int8_backend_integration.py``:
  15 passed, so the AR path the store already served is unchanged.
  ``test_gpu_dms_compact_attn_decode_int8_hip.py``: 5 passed.

## Findings

- ``test_int8_pack_append_attention_and_restore[8193-256-4-24]`` fails, and it is
  pre-existing and unrelated to this change: it fails inside ``append_layer``'s
  retention expectation before any attention call, in a path this change does not
  touch, and it is nondeterministic (1, 1 and 3 mismatched positions across three
  runs, 5 in another). The kernel retains a token at a position the test's
  expected compaction order does not. That is a repeatability defect in the
  append compaction, which the verify chain will depend on, and it is filed as
  its own task rather than fixed here.
- The store's ``max_pack_rows`` doubles as the multi-row bound. It is already the
  bound the store uses for its other row-shaped workspace, so no new parameter
  was needed.
