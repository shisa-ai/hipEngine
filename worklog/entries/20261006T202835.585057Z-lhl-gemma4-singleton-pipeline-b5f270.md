# Pipeline the Gemma 4 singleton PV key walk

## Summary

Deep decode was the singleton P*V stage. The decode kernel census at 131072
depth (restored-state profile, 127 decode steps, kernel trace + PMC) puts
`gemma4_attention_staged_pv_singleton_kernel` at 8.21s of 12.3s of kernel time
-- 67%, 2.155ms per launch -- with everything else an order of magnitude
smaller (score 10.4%, MoE gemv 8.9%, dense 3.6%). The singleton's counters
said latency exposure, not bandwidth or LDS: SQ_WAIT_ANY 5.7 per cycle,
SQ_WAIT_INST_LDS 0.001, ALUStalledByLDS ~0, and the walk's V traffic at
131072 is ~1.4 GB per step, only ~5% of this part's DRAM rate. The kernel
walked one key at a time: load V, FMA into the accumulator, repeat 131072
times, with a single dependent chain per thread and only ~34-75 one-wave CTAs
in flight to hide the load latency.

This unit unrolls the singleton's key loop by eight: eight V loads are in
flight per thread while the per-(row, dimension) accumulation stays exactly
one ascending-key FMA chain -- keys in ascending order within the window,
zero weights skipped per key, tile remainder on the original single-key walk.
The strict bitwise contract is untouched (102 GPU parity tests), and the
restored-state decode at 131072 reproduces the mint-time fresh decode's 128
greedy token IDs exactly.

Measured with the restored 131072 state (the cross-process KV harness this
campaign landed for exactly this loop): decode 9.43 -> 9.92 tok/s at
unroll 4, then **12.35 tok/s at unroll 8 (+31%)**. That is **1.07x llama.cpp's
11.52** at this depth, from 0.82x -- the deep-decode gap flips to a lead at
131072. The 256Ki depth remains to be measured once its 55 GiB state fits
the disk.
