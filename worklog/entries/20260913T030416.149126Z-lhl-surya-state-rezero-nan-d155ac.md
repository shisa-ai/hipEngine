# Surya full-suite NaN: state re-zero was scale-by-zero, which cannot clear a recycled NaN

## Summary

The Surya GPU family failed only inside a full-suite pytest run: 23 of the base
commit's 81 failures were Surya (8 in `tests/test_surya_gpu.py`, 15 in
`tests/test_surya_transcription.py`), the same tests passed in isolation (56
passed as their own bundle), and the signature was degenerate device state --
`generated_token_ids=(0, 0, 0, ...)`, `text=''`,
`finish_details.reason='length'`, and KL `nan` against the torch fp32 oracle.
Token 0 repeated is a *consequence*, not a second symptom: `np.argmax` over an
all-NaN logit vector returns index 0.

**Root cause: the conv and GDN recurrent states were "re-zeroed" before every
prefill with a scale-by-zero kernel (`x * 0.0`), which is a no-op for a NaN.**
`NaN * 0 == NaN` in IEEE-754, so any NaN left in recycled device memory survived
the re-zero, and the first GDN layer propagated it into every logit. In a fresh
process the same buffers happen to come back zeroed -- `hipMalloc` returns
zeroed pages for a fresh allocation, and the states are 96 KiB and 1 MiB -- so
every isolated run passed. After a long suite had churned device memory, the
allocation landed on pages holding another test's NaN/Inf, and the text decoder
returned all-NaN logits.

That single defect explains the whole attribution table:

* only the text path failed. The vision tower has no recurrent state and the
  vision-only tests (`test_gpu_vision_*`, `test_gpu_full_page_vision_*`,
  `test_gpu_tiled_vision_*`) all passed in the failing run, while every test
  that runs the text decoder failed, including the text-only one.
* `test_gpu_generator_checks_capacity_before_vision` failed on `assert
  out.text` -- a 4-token generation whose text was empty -- not on its capacity
  assertion, so it is the same defect and not a second mechanism.
* `test_gpu_generator_multi_prompt_isolation` passed in the same run because it
  only requires self-consistency, and a uniformly NaN model is consistent.
* `test_gpu_repeated_request_isolation` is the second test in its file, so the
  poison is not a "many Surya tests in" effect; it is whatever the *preceding*
  files left in device memory.

The same idiom existed in three more places in the Evie runner, whose kernels
the Surya text decoder reuses (`_zero_conv_state`, the segment conv-state slab,
and the GDN state slab). Evie's GPU tests pass in the full suite only because
they run in the first 9% of it, before anything has left a NaN behind; the
defect reproduces there too under the same poison probe. All five sites now use
`hipMemset`, and there is no `_F(0.0)` in-place scale left in `hipengine/runtime`.

## Changes

- `hipengine/runtime/surya.py`: the conv-state and GDN-state re-zero in
  `_gdn_layer_prefill` is `self.runtime.memset(ptr, 0, nbytes)` instead of
  `hipengine_evie_scale_f32(ptr, ptr, 0.0, n)`. Comments record why the
  scale-by-zero was wrong; the `_check(err, ...)` calls go away with the kernel
  launch.
- `hipengine/runtime/evie.py`: the same replacement at the three zeroing sites
  (`_zero_conv_state`, `seg.conv_state_slab`, `state_slab`), which are the same
  defect with the same failure mode.
- `tests/test_surya_gpu.py::test_gpu_state_rezero_clears_recycled_nan` (new,
  RED first): prefill, overwrite every conv/GDN state buffer with `0xFF` (a
  quiet NaN in fp32), prefill again, require finite and bit-identical logits.
  Fails before the fix with `65425 of 65425 logits are not finite`.
- `tests/test_evie_gpu_runtime.py::test_state_rezero_clears_recycled_nan` (new,
  RED first): the same probe on `encode_document`, requiring the 151x128 doc
  embeddings to be finite and identical. Fails before the fix with all 19328
  values NaN.
- `tests/test_surya_kv_spans.py`: the destination zero-fill seed is hoisted
  into a named local so it outlives the unpinned H2D copy (see the full-suite
  result below). Its order dependence is a separate tracked unit, but the
  failure blocked this unit's acceptance criterion and the mechanism is the
  host-side half of the same gotcha, so it is fixed here.
- `docs/KERNELS.md`: a "Device-memory hygiene" section -- recycled blocks below
  ~4 MiB keep their previous contents while fresh allocations are zeroed, so
  re-zero state with a memset, treat any read-before-write as a latent bug, and
  keep the source of an unpinned H2D copy alive until the copy lands.

## Validation

The mechanism was established before the fix by poisoning buffers in a single
process, which reproduces the full-suite signature deterministically:

| probe | before fix | after fix |
| --- | --- | --- |
| poison all 36 conv/GDN state buffers (20.7 MB) with 0xFF, re-prefill | 65425/65425 logits NaN, argmax 0, text `''` | bit-identical to the unpoisoned prefill |
| poison all 81 per-call buffers (scratch + split-K partials + KV planes + states, 79.3 MB) | -- | bit-identical (logits `array_equal`, max\|d\| 0) |
| poison nothing (control) | identical | identical |
| poison the Evie zero-state buffers, re-`encode_document` | 19328/19328 NaN | bit-identical |

The 81-buffer probe matters as much as the 36-buffer one: it shows the Surya
text path is now invariant to *any* NaN in recycled device memory, not just to
the state buffers that happened to be the culprit. The KV planes are included
in it, so the prefill also provably reads no unwritten KV slot.

The second and third rows also ruled out the alternatives that were tried first:
poisoning only `_scratch` (28 buffers), only the split-K partials, or only the
KV planes each left the logits bit-identical, so the defect was localized to the
state group before any code was changed. A direct probe of the zeroing op
showed it left all 24704 floats NaN and nonzero (`err=0`), which is what
identified `x * 0.0` rather than a missing call.

## Full-suite result

**Surya failures: 23 -> 1** on the first run at the fix
(`59 failed, 12411 passed, 172 skipped, 4 xfailed, 6 warnings in 3081.64 s`
against the pre-fix 81/82 failed). The 23 failures in `tests/test_surya_gpu.py`
and `tests/test_surya_transcription.py` are gone; both files pass inside the
suite, as does `tests/test_surya_transcription.py` on its own (25 passed).

The single remaining Surya failure was
`tests/test_surya_kv_spans.py::test_scatter_f32_spans_honors_page_table_and_eviction`,
which had passed in the pre-fix run and which is the separate order-dependence
tracked as its own task. It turned out to be the *host-side* half of the same
gotcha family, and it was fixed here because it blocked the acceptance
criterion:

- Deterministic 2-test reproduction: `test_gpu_text_only_matches_oracle`
  followed by the scatter test fails in 10 s, and the scatter test alone passes
  in 0.4 s. So it is host-heap state left by a preceding Surya test, not device
  state and not the scatter kernel.
- The failure was 4 mismatching elements of 1048576, all in slots the scatter
  never writes, with values like `4.58e-41` -- a denormal, i.e. recycled host
  heap bytes read as floats. The cause is the line
  `copy_host_to_device(dst_buf, host_array_ptr(np.zeros_like(expected)), ...)`:
  a same-statement temporary as the source of an unpinned H2D copy, which on
  this stack the DMA reads after the call returns. It is the same defect the
  Surya runner's `_upload` docstring already documents for its own copies.
- Fix: hoist the zero-fill into a named local so it stays alive across the
  `device_synchronize()` that already followed the copy batch. The 2-test
  reproduction then passes (2 passed in 10.5 s) and the file pair passes in the
  alphabetical order that used to fail (`51 passed in 115.6 s`).

The confirmation full-suite run at the final tree is recorded below; the
mechanism is fixed deterministically either way, so the suite's result is
confirmation rather than the primary evidence.

## Next

  closed. Worth remembering for the other suites: a
  `host_array_ptr(<temporary>)` source is the same class as a device
  read-before-write, and only shows up when the host heap happens to be dirty at
  that moment.

  `hipengine/runtime/` and to the Surya/Evie test files. Any other runtime that
