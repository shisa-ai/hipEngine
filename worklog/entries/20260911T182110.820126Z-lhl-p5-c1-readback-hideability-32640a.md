# C1 decode readback is not hideable: the step is launch-bound, not readback-bound

## Summary

The P5 C1 decode attribution named a 16.2 ms/step synchronous D2H readback at
`_read_sample` as 44% of the step wall and flagged deferring it as the obvious
follow-up. **That hypothesis is wrong**, and establishing why is the useful result:
the readback is not recoverable time, and the real bottleneck is elsewhere.

Two measurements decide it.

First, a child-only run (no profiler) splits each measured step wall into the
blocking readback and host time outside it, attributing copies by wrapping
`runtime.memcpy` and snapshotting per-call-site totals around each step:

| Phase | Median | Share of wall |
| --- | --- | --- |
| Step wall | 35.079 ms | 100% |
| Blocking readback (`_read_sample`) | 20.186 ms | 57.5% |
| Host work outside the readback | 14.951 ms | 42.6% |

Second, the phase split alone cannot say whether the blocked time is wasted, so it
is paired with the committed trace's GPU-idle split, which bounds it: at most
**5.178 ms/step** of *all* HIP API time occurs while the GPU is idle, and the
readback is one HIP API call. So **at least 11.118 ms/step of the readback
overlaps GPU-busy time**. The host is blocked waiting on GPU work that must happen
anyway.

The dependency is strict, which closes the question. The sampled token index is
read back to the host, which then builds the next step's input embedding
(`_copy_token_embeddings_to_device`, 62 calls, 31.4 us median). The host cannot
enqueue the next step without it, so there is no token-independent work to move in
front of the block. Deferring the readback cannot recover the time.

## The actionable finding

The redirect matters more than the negative result. The GPU is idle
**19.257 ms/step (52.6% of the window)** while the host enqueues **~793 kernel
launches/step** and spends 14.951 ms/step outside the readback. The step is
**launch/feed-bound**, not readback-bound.

The lever is therefore reducing or amortizing launch count. Graph capture already
exists on the c8 packed route (`graph_capture_seconds` 0.186, one synchronized
replay per logical transition) while the C1 route is eager, which makes it the
most likely large win. That is now task #24, with a measurement step first: split
the 14.951 ms of host time into launch overhead versus Python bookkeeping before
implementing anything.

`split_step_phases` rejects a readback longer than its own step. Without that, a
mis-attributed copy would produce negative host time, which reads as an
improvement rather than an error — the same class of failure as the earlier
negative-residual bug in this script.

## Validation

- `uv run pytest tests/test_gguf_c1_decode_attribution.py -q` — 33 passed.
- Child-only run, W7900 / gfx1100, cache-only (`HIPENGINE_REQUIRE_CACHED_BUILD=1`,
  pinned compiler version), 62 measured steps at 2048 prompt rows, Qwen3.8-27B
  `Q4_K_M`, INT8 KV. Values above.

Honest limits, recorded in the artifact:

- The phase split is child-only and not itself profiled, so the GPU-busy claim
  rests on the committed trace's `api_while_gpu_idle_ns`, which bounds all HIP API
  time rather than the readback alone.
- The two runs differ: 35.079 vs 36.605 ms wall and 20.186 vs 16.296 ms readback.
  The overlap conclusion holds in both; the absolute split is not identical.
- The 14.951 ms/step of host time is not yet decomposed into launch overhead versus
  Python bookkeeping.
- No optimization was attempted. This is a negative result about the readback
  hypothesis, not a measurement of any launch-reduction alternative.
- `performance_claim` is false and no scoreboard row changed.
