# The TP2 prefill gap is a missing dispatch context, not a rendezvous

## Summary

A review of the previous entry found four things wrong with it and one thing
missing. All five were acted on. The headline outcome is that the reason the TP2
prefill is 30% behind llama.cpp's tensor split is now identified and measured:
**the TP2 bulk prefill omits five calibrated dispatch contexts that the
single-card bulk prefill installs**, and without them the largest GEMMs on the
attention path resolve to a *decode-shaped GEMV kernel* during prefill.

Entering the one context that matters takes the product-path prefill from
**494.1 ms to 477.6 ms (+3.45%)**, confirmed across four independent interleaved
A/B/A runs. It is not integrated yet; the reasons are concrete and recorded.

## What the review got right, and what it changed

**The attribution mixed repetitions.** `tp2_prefill_phase_attribution.py` took
`min(walls)` for the wall but selected phase spans from the *worst* repetition,
so the percentages and the unaccounted remainder described an execution that
never happened. Fixed: every repetition is now a paired record, the headline is
the minimum-wall repetition read together with **its own** spans, and the JSON
keeps the full paired list.

**The "MLP arithmetic is exhausted" conclusion was unsupported.** It is
retracted in `docs/REFACTOR.md`, in the capability comment, and here. It was
inferred from stream-event spans that cannot carry it: the spans include enqueue
bubbles, the hooks bracket *both* ranks' sequential host submissions, and the
"full-row head" control that appeared to confirm it changed the workload rather
than only the synchronization. Nothing measured shows a 30 ms chain reduction
becoming 30 ms of extra exchange wait, so the ~30 ms saving is unestablished too.
The isolated kernel speedup is real; what the pipeline does with it is not known.

**The correctness status was contradictory.** `benchmarks/README.md` claimed a
passing production gate while the diagnostic reported `all_passed: false`. These
are different gates and the public summary now says so: the arm-vs-control gate
compares the bulk prefill candidate against its own serial control *within* the
TP2 route and passes; the cross-route check against a single-card reference does
not, and that is the unresolved blocker.

**The decisive experiments were not reproducible.** The untracked dispatch probe
is replaced by a committed, phase-filtered census, and the capability A/B now has
a committed driver.

**The stale shard-width table.** `test_gfx1151_backend_admits_dense_q5_t16_ssm_out_and_08b_roles`
was missing the four uneven-split widths (7_168 / 10_240 / 7_680 / 9_728) that
the campaign had already measured and admitted. Repaired as an exact equality
with the measurements named, not by loosening the assertion. **57 pass.**

## The attribution, repaired

The host timeline was added alongside the device timeline, and it changes the
picture. Host spans sum to **71.76 ms** against a **489.56 ms** device span, so
the prefill is **device-bound** and the host has roughly 7x headroom. That bounds
the enqueue-bubble concern the review raised: it cannot be the whole story.
Instrumentation overhead is −0.54%, within noise, so the recorded wall is usable.

Per layer, from one repetition read whole:

| | rank 0 (W7900) | rank 1 (RX 7900 XTX) |
| --- | ---: | ---: |
| attention | 3.659 ms | 3.248 ms |
| MLP chain | 2.961 ms | 2.621 ms |
| MLP exchange | **0.926 ms** (sd 0.005) | 1.694 ms |

Rank 0's exchange is *constant* to within 5 microseconds, which makes it pure
work: it never waits. Rank 1's is that same work plus a wait. The model
`rank1_exchange = (rank0 attention+chain − rank1 attention+chain) + rank0
exchange work` predicts **1.677 ms against 1.694 measured** — a 1% match. Every
layer synchronises at its MLP exchange, rank 0 is the critical path, and rank 1
idles ~0.75 ms/layer.

That gives one cheap, testable lever: rebalancing the MLP shard to 0.463/0.537
would equalise `attention + chain` and is worth ~24 ms/prefill (~4.9%) **on that
model**. The model assumes chain cost scales with shard width, which is untested;
it should be measured before being relied on.

## Two negative results that redirect the work

**The exchange is at its floor.** Measured PCIe ceiling on this host is
**~14 GB/s per direction** for a 5.24 MB transfer (both devices). The exchange's
two such transfers cost ~0.75 ms of a 0.926 ms span, so it is at **~81% of the
hardware floor**. Direct peer access is unavailable — `hipDeviceCanAccessPeer`
returns 0 in both directions between the W7900 and the RX 7900 XTX — so host
staging is required and the traffic cannot be halved. The spin-add kernel is
fully scalar (2-byte loads from host-mapped memory), which looked like a large
win until the floor was measured: at most ~2% remains. **Not the lever.**

**The fusion's null result is still unexplained.** Retained because it is exact
and strictly less work (384 → 128 launches per prefill), but the mechanism is
recorded as unknown rather than guessed.

## The finding

The single-card bulk prefill wraps its pass in six dispatch contexts. The TP2
rank-local bulk prefill installs one:

```python
# TP1 (qwen35_gguf_runner.py, run_bulk)          # TP2 (_bulk_attention_layer)
resident_prefill_dispatch_session(...)            resident_prefill_dispatch_session(...)
_prefill_f16_staging_context()
_q6_integer_mmq_context()
_iq_dense_mmq_context()
_q8_mmq_prefill_context()
_q6_f16_rocblas_prefill_context(request_rows=...)
```

Without them, the largest GEMMs on the attention path run a decode kernel during
prefill:

| tensor | quant | shape | GFLOP/layer | TP2 prefill variant |
| --- | --- | --- | ---: | --- |
| `attn_qkv` | `gguf_q6_k_t16_qmicro_planar_v1` | (5120, 10240) | 53.7 | `t16_gemv_decode` |
| `ssm_out` | `gguf_q5_k_t16_v1` | (6144, 5120) | 32.2 | `t16_gemv_decode` |
| `attn_v` (16 layers) | `gguf_q6_k_t16_qmicro_planar_v1` | (5120, 1024) | — | `t16_gemv_decode` |
| `attn_gate`, `attn_q`, `attn_k` | `gguf_q4_k_t16_v1` | — | — | `t16_wmma_prefill` |

This is why attention runs at **31.2 TFLOPS** (GDN) and **34.6** (full attention)
while the sharded MLP chain reaches **46.2 TFLOPS/rank** on the same device.

The route is available, not merely registrable: the model geometry is admitted by
`GGUF_DENSE_T16_F16_ROCBLAS_PREFILL_POLICIES`, and every shape above is admitted
at exactly rows=512 by the per-quant policy tables.

**Measured, interleaved, one session, medians of 3:**

| arm | median | effect |
| --- | ---: | ---: |
| none (control) | 494.1 ms | — |
| all five contexts | 476.7 ms | **+3.65%** |
| `_q6_f16_rocblas_prefill_context` alone | 477.6 ms | **+3.45%** |
| `_q6_integer_mmq_context` alone | 496.8 ms | none |

Four separate A/B/A runs agreed (+3.63/+3.71, +3.67/+3.73, and the interleaved
run), with control drift of −0.31% and −0.26%. The win is entirely the f16-rocBLAS
route.

**What is deliberately not claimed:** the per-tensor variant diff under the
context was not captured cleanly — the cache-clearing in that capture was invalid
and reported 56 tensors for the baseline against 280 for the arm — so the routing
change rests on the timing A/B plus the admitted-policy lookup, not on a variant
census. One earlier single-context probe also produced a null result that the
interleaved run then resolved in favour of the effect; the interleaved ordering
is the one being reported.

## Why it is not integrated

Not a one-line change, and the failure modes are recorded so the next attempt
does not rediscover them:

- The contexts are methods on `Qwen35GGUFResidentSession`, not on the runner the
  TP2 session holds.
- They carry **per-rank scratch** (the f16 weight plane, `q6_f16_x`,
  `q6_f16_out`), so each must be entered **inside** the per-device loop around
  that rank's own work. Entering one rank's context around both ranks' work makes
  rank 1 read rank 0's f16 planes and faults the GPU: `Memory access fault by GPU
  node-2 ... Page not present or supervisor privilege`.
- A `Qwen35GGUFResidentSession(shared_runner=runner)` per rank works and reuses
  the uploaded weights (confirmed: `runner shared = True`), but allocates its own
  bulk-prefill workspace on top of the TP2 session's.
- The route changes attention arithmetic from int8 WMMA to source-F16 rocBLAS, so
  it needs the applicable production-profile gate and a registered strict
  fallback, not just the timing A/B.
