# D7 GEGLU clause: down-prologue fold built bit-exact, rejected by the screen

## Summary

- Measurement first (exact, from the d3 census trace + model config): the two
  decode GeGLU launches are **dense** (grid = rows 1 x I 2112, stream 0) and
  **routed** (lanes 8 x I 704, stream 1), each ~2.0 µs, n=2160 each — 60
  launches = **0.120 ms/token**, exactly the row's estimate, measured under
  queue depth (census durations), so 0.12 is the true ceiling.
- Built the **down-prologue fold**: a fused t64 selected GEMV variant that
  consumes `gate_up_out` directly and computes
  `bf16(gelu_tanh(bf16 gate) * bf16 up)` inside its input load — the exact
  store/load rounding of the `gemma4_gelu_tanh_mul_bf16` chain (identical
  helpers and constants verified across both .hip files). RED first:
  `test_q5_1_selected_geglu_down_matches_the_chain_bitwise` asserts the fused
  output **bitwise equals** the gelu-then-down chain at rows 1 and 8, with
  poison sentinels (fused-stride overrun) and an input-immutability check; a
  numpy formula oracle pins the chain at ~1 bf16 ulp (device `tanhf` vs numpy
  may sit one ulp apart before the round — bitness is claimed only
  device-vs-device, correctly).
- Caller wiring followed the D5 pattern: `_SELECTED_GEGLU_VARIANT`
  registration (capability, not a name check; `linear`/`gguf_q5_1` only, the
  unfused chain stays the strict fallback), `gemma4_experts_geglu_fold_ready`
  decides before the gelu stage, and the fused branch heads the down ladder so
  no other branch can double-launch.
- **Screen verdict: reject.** `scripts/gemma4_geglu_down_fold_screen.py`,
  production geometry (in 704, out 2816, E 128), agreement-first, absolute
  1.0 µs gate: chain 12.201 -> fold **13.764** µs/call at rows=1 and 55.532
  -> fold **90.784** at rows=8 (the production decode shape, lanes 8),
  bit_equal true both. The structure is the cause and it is general: a GEMV
  re-reads its input once per (row, out) block, so applying the activation in
  the down GEMV evaluates gelu `out_features` times more often than the
  chain's single pass — 2x input traffic plus `tanhf` per re-read. Wiring the
  fold at production decode would have cost ~35 µs x 30 layers = ~1 ms/token.
  The screen is why this never reached a census.
- Code reverted to HEAD (kernel, launcher, wrapper, registration, caller,
  test — all four files were modified only by this unit and restored with
  `git checkout --`). Kept: the screen script and its artifact as the
  measurement of record.
- The row's other structural reading survives: the correct fold is the
  **paired gate_up epilogue** — a block owning gate column c and up column
  c+I computes both dots over one K read, so the activation runs once per
  (row, c) and the gelu launch disappears with gate_up_out never written.
  Ceiling **0.060 ms/token routed + 0.060 dense = the row's 0.12**; open, and
  now known to require a gate_up-owner restructure (the D1 t16 crown jewel)
  rather than a down-input change. Not built this iteration: the prologue
  screen says the prize is 0.06 ms routed (0.4% busy) against a core rewrite
  of the family's fastest kernel — D8's launch/host items and the remaining
  route_glue members are larger.
