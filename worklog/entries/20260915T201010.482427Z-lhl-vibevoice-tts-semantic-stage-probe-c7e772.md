# Semantic frontend is O(n), GPU-resident, and not sync-copy bound; 29.8 ms/frame is unexplained by the two obvious suspects

## Summary

The semantic frontend is the third-largest session stage (0.794 s of 4.230 s warm
synthesis, 19%) and had not been investigated. Three hypotheses were tested and all
three are dead: it is genuinely incremental (O(n), not O(n^2)); it is genuinely
GPU-resident (HIP kernels, not a CPU fallback); and its two synchronous D2D memcpys
cost only 0.43 ms/frame (1.01x). The measured 29.78 ms/frame is roughly 100x the
stage's arithmetic and is not explained by any of them. No code change.

## Changes

No code change. One immutable worklog entry.

### Measured

Host `zbook` (gfx1151, AMD RYZEN AI MAX+ PRO 395 / Radeon 8060S). Semantic spec:
`hidden_size=128, depths=(3,3,3,3,3,3,8), ratios=(2,2,4,5,5,8), num_filters=32,
kernel_size=7, ffn_expansion=4`. Total downsampling is
`2*2*4*5*5*8 = 3200`, which is exactly the 3200-sample streaming chunk, so each
frame emits exactly one latent frame.

```
semantic encode_chunk_streaming : 29.78 ms/frame  (27 frames = 0.80 s)
_scratch.reset(21.7 MB)         :  0.00 ms/call   (counter only, no allocation)
async D2D vs sync D2D           : 29.78 vs 30.20 ms/frame  -> 1.01x, 0.43 ms/frame
```

### Hypothesis 1 (dead): O(n^2) re-encoding of accumulated audio

`encode_chunk_streaming` takes one 3200-sample chunk plus a caller-owned `state`
dict carrying the convolution tails, matching the fork's `use_cache=True` encode.
It does not re-encode the accumulated waveform. O(n).

### Hypothesis 2 (dead): CPU fallback

The frontend resolves `get_hip_runtime()` and dispatches real HIP kernels
(`vv_im2col_bf16`, `frontend_gemm`, `vv_add_bias_bf16`, `vv_conv_gemm_bf16`, ...).
It is a GPU implementation.

### Hypothesis 3 (dead): synchronous memcpy stalls

`runtime.memcpy` calls `hipMemcpy` (the blocking variant); `memcpy_async` exists and
is unused in this file. The two sync D2D copies sit in the streaming im2col path and
run at most once per stage, so ~12 stalls per frame. Replacing only the D2D copies
with `memcpy_async(..., stream=0)` -- ordering-preserving, since the kernels also use
stream 0, and leaving other copies synchronous so the D2H readback stays correct --
moved 30.20 -> 29.78 ms/frame. **1.01x. Not the bottleneck.**

## Validation

- `encode_chunk_streaming` timed in isolation over 27 frames with a single
  `device_synchronize()` around the whole loop (not per call), so the measurement
  does not repeat the pipeline-serialization error retracted in
  20260915T200702.494130Z.
- The async-D2D variant was compared against the unpatched runtime in the same
  process, with the patch reverted after each arm.
- Arithmetic check: stage 0 is 3 conv layers at length 3200, 32 filters,
  kernel_size 7, i.e. ~23M MACs per layer, ~69M MACs for the stage -- sub-0.1 ms of
  GPU work. The observed 29.78 ms is ~100x that, so the cost is overhead-bound, not
  arithmetic-bound.

## Next

- The remaining suspects for the 29.78 ms are launch count across 26 layers (each
  layer runs conv + norm + FFN + residual) and poor occupancy on the very short
downsampled stages (stages 5 and 6 run at 8 and 1 rows). Both need a kernel-count
  and per-kernel-duration profile (`rocprofv3`) to separate; a chunk-size scaling
  test (feed 32000 samples = 10 latent frames) would distinguish fixed per-frame
  overhead from per-sample cost.
- Diffusion (32%, 1.373 s) remains the largest single stage and iteration 29 already
  placed it at 45% of its weight-traffic floor.
