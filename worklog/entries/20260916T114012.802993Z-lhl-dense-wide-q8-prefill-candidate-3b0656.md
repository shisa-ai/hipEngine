# Port the comparator's wide-row Q8_0 prefill into hipEngine

## Summary

The replay harness measured hipEngine at 11.70x the pinned comparator on Q8_0
`attn_qkv`. This unit closes most of that gap with a new registered kernel and
identifies the remainder with a measured mechanism rather than a hypothesis.

On the same replay packet, the new `dense_wide256_f32_f32_out` runs **2.570 ms**
(two 50-repetition runs: 2.573 and 2.566) against the production dispatch's
**19.663 ms** — **7.65x**. It is 1.72x the comparator's complete-operation time
(1.492 ms) and 1.92x its kernel-only time (1.339 ms).

The remaining gap is **entirely the activation path**, and that is measured, not
inferred. A timing-only probe of the same kernel reading a pre-converted f16
activation instead of f32-plus-conversion runs at **1.303 ms** — faster than the
comparator's 1.339 ms kernel. The kernel body already matches; the input
representation is what does not.

Radeon 8060S / `gfx1151`, one packet, same process, 30-50 repetitions per
variant:

| Engine | Kernel | ms | TFLOP/s | max\|d\| vs f64 |
| --- | --- | ---: | ---: | ---: |
| hipEngine production | `coltile8_rowbatch4_f32_f32_out` | 19.663 | 2.73 | 2.06e-06 |
| hipEngine production (wave-scale) | `coltile8_rowbatch4_wave_scale_f32_f32_out` | 17.319 | 3.10 | 2.06e-06 |
| hipEngine best in-tree | `wmma_prefill_f32_f32_out@tile16x32` | 4.401 | 12.20 | 2.83e-03 |
| **new candidate** | `q8_0_dense_wide_kernel<128,256,64,64>` | **2.570** | **20.89** | 2.83e-03 |
| comparator | `mmb_dense_kernel<128,256,64,64,1>` | 1.339 | — | — |
| candidate, pre-converted f16 activation (probe) | same kernel | **1.303** | — | — |

## Changes

### What was built

`hipengine/kernels/hip_gfx1100/quant/gguf_q8_0_dense_wide.{hip,py}`, ported from
`ggml/src/ggml-cuda/mmb.cu` `mmb_dense_kernel<128, 256, 64, 64, 1>` at
`c4aa302294fcd5121af2039fd4d3dee0d472ec03`.

The kernel covers 128 output columns x 256 rows per 256-thread block, staging a
dequantized weight tile and a converted activation tile in 55,296 bytes of LDS.
Each weight byte is read from global memory once per 256 rows instead of once per
4-32, which takes the projection's derived weight traffic from 7.13 GB to
0.111 GB. The K loop is double-buffered through registers: the next K-tile loads
from global while the current one is consumed from LDS.

Deliberate differences from the source, all recorded in the `.hip` header:

- The activation arrives as f32 and is converted during LDS staging, so the
  variant keeps an f32 ABI with no hidden scratch state. This is the one
  difference that costs real time, quantified below.
- Operands are f16 rather than bf16. RDNA3 runs both at the same WMMA rate, so
  this is better precision at no cost, and it matches the in-tree f16 WMMA
  lineage in `gguf_q8_0_prefill.hip`.
- The epilogue bounces each 16x16 result through a per-wave LDS region with a
  wave barrier, not the source's block-wide barrier pair per output tile.
- Tail handling is a template parameter, so the exactly-divisible case has no
  per-fragment predication. This was worth 13% on its own (2.911 -> 2.536 ms),
  after an 11% gain from removing a K-tile staging spill (2.911 -> 2.599 ms on
  the layout that was then fastest).

Registered as a tile family — `dense_wide256`, `dense_wide64x256`,
`dense_wide128x128`, `dense_wide64x128` — because the layout choice is a
measured crossover, not a constant. `dense_wide256` (the comparator's own
tiling) wins on this shape.

### The mechanism

Kernel-level `rocprofv3 --kernel-trace`, both engines in one process, 83
launches each, identical geometry:

| Kernel | avg | VGPR | LDS | Scratch | grid | block |
| --- | ---: | ---: | ---: | ---: | --- | ---: |
| `q8_0_dense_wide_kernel<128,256,64,64>` | 2580.1 us | 256 | 55296 | 0 | 80x4 | 256 |
| `mmb_dense_kernel<128,256,64,64,1>` | 1339.0 us | 256 | 55296 | 0 | 80x4 | 256 |

Resource usage is now identical. The difference is what each kernel reads:
hipEngine re-reads a 10.5 MB f32 activation once per column block (80 times,
838 MB) and converts it in-kernel; the comparator reads a pre-converted bf16
activation (419 MB) that ggml produced in one 68 us pass.

The probe isolates this exactly. Same kernel, same weights, same launch, with
only the activation load changed from two `float4` plus eight `f32->f16`
conversions to a single `half8_t` load:

- f32 activation, in-kernel convert: **2.541 ms**
- pre-converted f16 activation: **1.303 ms**
- comparator kernel: **1.339 ms**

The probe reads f32 bytes as f16, so its values are garbage and it is a timing
instrument only. It was built outside the tree and is not registered.

### Two intermediate findings worth keeping

- **The production dispatch is not the fastest registered Q8_0 prefill.** A
  sweep of all 25 registered `f32_f32_out` variants with a measurement on this
  packet found `wmma_prefill_f32_f32_out@tile16x32` at 4.401 ms, 4.5x faster
  than the production key. It was not selected because its numerics are 1000x
  worse (2.83e-03 against the exact reference, versus 2.06e-06), which is a
  decision for the production gate, not a dispatch bug. This is recorded rather
  than acted on.
- **The candidate introduces no new numerical class.** That 2.83e-03 is exactly
  the error the already-registered `wmma_prefill_f32_f32_out` family reports, and
  the elementwise matrix confirms it is the same arithmetic rather than a
  coincidence: the candidate is **bit-identical** to `wmma_prefill` at 16x32,
  16x16, 32x16 and 64x32 — 0 of 10,485,760 elements differ — while the two
  negative controls (the strict f32 coltile family and the int8 WMMA family)
  differ on 99.99% of elements. The f16 prefill arithmetic question therefore
  predates this unit; it is not created by it.
- **`iu8_wmma_prefill_f32_f32_out` already had the right instruction family.**
  It uses int8 WMMA on raw Q8_0 codes with a 3-plane activation and is 2.76x
  faster than production (7.129 ms) with better numerics than f16
  (5.30e-06 vs f64). It stops at 16 rows per block, which is why it does not
  reach the comparator. A future direction that keeps exact weights and needs no
  dequant at all.

## Validation

The kernel's arithmetic is f16 operands with f32 accumulation, so bit parity
with the strict f32 coltile family is not its contract. `docs/EXECUTION-PROFILES.md`
is the binding contract and is **not** satisfied by this unit — no model-level
KL, top-1, determinism or task gate has been run.

What is established:

- The output tracks an f16-simulated reference (both operands rounded to f16,
  product accumulated in float64) to **max|d| 1.111e-04** on the replay packet.
  That is accumulation-order error for K=2560; a structural bug would miss by
  the f16 rounding scale (2.8e-03) instead.
- Against the exact float64 reference the maximum relative error is **2.08e-04**
  (2.834e-03 absolute). The strict coltile family is 1.5e-07 relative. This is a
  real precision reduction of roughly three orders of magnitude and is the
  reason the candidate is not a default.
- `tests/test_gpu_gguf_q8_0_dense_wide.py`: 20 tests, all passing. Registry
  binding for the family, build plan, the `in_features % 64` contract, both
  oracles across shapes with and without tails in rows and output columns, and
  gfx1151 alias reachability.
- **Bit-identical to the registered f16 WMMA family across tilings.**
  `verify_tiling_invariance.py` compares whole output matrices elementwise: the
  candidate matches `wmma_prefill_f32_f32_out` exactly at four different tilings
  (0 of 10,485,760 elements differ) while both negative controls differ on
  99.99% of elements. Recorded in `tiling-invariance.json`.
- The binary targets **gfx1151** natively (verified from the ELF), so the
  measurement is not gfx1100 code running in a compatibility mode.

### Reachability

The production runtime requests `backend="hip_gfx1151"`, and the alias pass in
`hipengine/kernels/hip_gfx1151/__init__.py` mirrors every gfx1100 key except
explicit exclusions. The new module was added to `_GFX1100_MODULES` so the
family is reachable under that key; without it the candidate could never be
dispatched regardless of its speed. A test asserts this rather than trusting it.

## Next

- **No model-level gate.** The reviewer's plan calls for enabling only
  `attn_qkv` in a diagnostic run and measuring strict-teacher numerics. That has
  not been run, and it decides whether f16 prefill arithmetic is admissible at
  all. Nothing here should be promoted before it.
- **No end-to-end A/B.** The 7.65x is one leaf on one packet, not a model rate.
- **The activation path is not fixed.** Reaching the comparator needs the
  activation converted once instead of 80 times, which means a pre-converted
  input variant plus a conversion kernel, and a dispatch change to run the
  conversion first — the pattern `gguf_q8_0_mmq_prefill` already uses with its
  caller-supplied `x_d4_ptr`. That is a separate unit and touches the dispatch
  path.
- **One geometry, one layer, one chunk, one host.** Not extended to `ssm_out`,
  `attn_gate`, or the Q5_1 expert-down shapes yet.
