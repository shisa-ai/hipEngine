# Fix Gemma campaign context propagation through the public constructor

## Summary

The five-length comparison exposed a harness bug: `_resolve_generator`
assigned `context_length` on `SubmitPollTextGenerator`, which forwards reads
but not writes. The inner Gemma generator therefore built an 8192-capacity
runner even when the harness reported a larger requested context.

The harness now passes `max_sequence_length` to `hipengine.LLM` before
resolving the generator. No production arithmetic or runtime default changes.
The initial 8448/16640 allocation probes are invalid for their requested
capacities; their recorded `runner_capacity` is 8192. Preserve the original
files outside Git, mark them invalid in the comparison artifact, and use the
corrected probes. The initial 8192 probe and 512/1024/4096 timing rows have
matching requested and actual capacities and remain usable.

## Changes

- `scripts/gemma4_campaign_bench.py`: use the public constructor's capacity
  argument instead of shadowing the forwarding wrapper.
- `tests/test_unit_gemma4_campaign_bench.py`: a forwarding-wrapper regression
  at capacities 8192, 8448 and 16640 checks constructor arguments and agreement
  between requested, reported and actual capacity.
- The temporary Gemma allocation probe asserts actual capacity before calling
  a short prefill; it is not a production path or a feature gate.
