# PF-1d forensics: stale-dispatch replay isolated, harness fixed

## Summary

Localized the first-run state-determinism defect that blocked PF-1d and
matched the P3 rejection signature: **the first decode-bearing request after
switching the MMQ policy replays the previous chain's dispatch once.**

## Evidence (zbook/gfx1151, code-p512 then code-p1024, 24-step forced
trajectories, sha256 prefixes of full logit trajectories)

- code-p512: strict / x2 x3 / x3 x3 — all internally deterministic.
- code-p1024: strict deterministic; x2 x3 deterministic;
  **x3 repeat 0 = `397ca16541bef732` (the x2 trajectory hash); repeats 1-2 =
  `84001d802601b514` (the true x3 hash).**
- Prefill-only probe (no decode steps): x3-after-x2 equals direct x3 exactly
  (`c7d2f63176f6e26d`) — the replay trigger requires an intervening
  decode-bearing request under the previous policy.

## Interpretation

A one-shot cached dispatch/plan (rebuilt or invalidated after one replay)
serves the first request after a policy flip. Production never flips the MMQ
policy within a session, so the defect is **harness/experiment-scoped** and
does not impugn the incumbent's production determinism. It fully explains the
P3 rejection's "repeat 1 differs from repeats 2-3" signature class.

- `scripts/execution_profile_q8_mmq_plane_gate.py`: `_warm_policy()` — one
  discarded 32-token warmup request after every policy flip (strict,
  candidate, context), with the forensics note in its docstring; route block
  records `warmup_request_after_policy_flip: true`. Harness-only; no
  production code touched.
