# HC-3: the GR gate store is dead but removing it costs 2%

## Summary

Ledger HC-3 recorded an "unconsumed 168 MB/layer GR gate write" as an
arithmetic-free optimization: "No arithmetic risk -> Remove or fuse the write".
Both halves were checked, and the item is now **closed as a negative result**.

The consumer census confirms the first half: no production caller reads the gate
field. But the write is **not** free money - a strict variant that suppresses it
produces a bit-identical `mixed` and measures **2% slower** (6.6551 ms against
6.5198 ms at rows=1024, K=320, N=10240), with sample sets that do not overlap.

The deliverable is the negative result. HC-3 must not be re-attempted on the
theory that a dead write is free.

## Next

**Bounded caveat, stated so it is not over-read:** the variant was implemented as
an `if (WRITE_GATE)` branch on a template parameter inside the existing epilogue.
A separately written kernel body with no branch at all might schedule
differently and show the small win the traffic arithmetic predicts. That is
unmeasured. What is measured and retainable is the negative result for this
implementation, which is enough to stop HC-3 as written.

Explanation offered, and clearly marked as inference rather than measurement:
the kernel is weight-traffic-bound, so the 42 MB store is ~1.2% of the 3.565 GB
weight read and the store likely acts as a latency sink keeping the memory
pipeline busy while the next residency's weight loads are in flight. It was not
profiled.

1. **HC-7 census** - HC-3 named one dead write and it turned out to cost

3. **HC-1 production gate** - the staged-f32 mechanism measured 2.388x with
