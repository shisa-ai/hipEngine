# Ship M7's product rule: an explicit speculative_mtp request runs or fails naming the capability

## Summary

Punchlist M7's row opens with `speculative_mtp: true` on `LLM.generate()` and
`hipengine serve`, and states the rule "an explicit request either runs or
fails naming the missing capability". The `serve` half already exists in the
tree; the `generate()` half did not exist at all -- `SamplingParams` carried no
such field, so `SamplingParams(speculative_mtp=True)` did not even construct.
The flag now exists, `generate()` honours it, and an unsupported model fails
with `NotImplementedError: speculative MTP generation is not supported by this
generator` instead of quietly returning plain autoregressive text.

## Changes

- `hipengine/llm.py` -- `SamplingParams.speculative_mtp: bool = False`, and a
  route at the top of `generate_detailed` that delegates to the existing
  `generate_speculative_mtp_detailed` when the flag is set.
- `tests/test_unit_llm_generate_mtp_flag.py` -- 6 unit tests.
- `tests/test_live_gemma4_generate_mtp_flag.py` -- 1 live test on the real
  artifact behind a HIP + artifact guard.

## Validation

- `pytest tests/test_unit_llm_generate_mtp_flag.py -q` -- **6 passed**: the
  flag routes to the MTP path (and the AR path is asserted not to run), the
  list-shaped `generate()` honours it too, an unsupported generator and a
  support-declaring generator with no callable both raise naming the
  capability, the default path is never diverted, and the field's default is
  `False`.
- `pytest tests/test_live_gemma4_generate_mtp_flag.py tests/test_unit_llm_mtp_eligibility.py -q`
  -- **5 passed** (5.86 s live). The live test asserts the refusal on the real
  17 GB artifact *and* that the same prompt without the flag still generates,
  so the failure is attributable to the request rather than to a broken model.
- `pytest tests/ -k "llm or generation" -q` -- **255 passed, 0 failed, 0
  skipped, exit 0**. `generate_detailed` is the core entry for every existing
  caller, so the regression bundle covers the path the route sits on top of.
- `python3 audit/audit.py check` -- no row names `llm.py`,
  `generate_mtp_flag`, or `speculative_mtp`; `open flag` is 0 and
  `open ungoverned-flag-branch` is the same 8 pre-existing env-var rows
  (`hipengine/core/build.py:225` first). No new debt.

## Decisions

- **Default `False`, asserted by test.** The flag is opt-in, so no existing
  caller's arithmetic can move; a test pins the default rather than assuming
  it.
- **No silent fallback, by construction.** The route returns before the
  autoregressive path is even built, so there is no branch that could quietly
  downgrade. That is the row's rule expressed in control flow rather than in
  documentation.
- **What I verified about `serve` vs what I did not.** Measured by reading:
  `api.py:2013` declares the request field `speculative_mtp: bool | dict | None`,
  `:1532` advertises `"request_field": "speculative_mtp"` in the capability
  block, `:276-278` define the serving routes, and `:12506` reaches the
  engine's `generate_speculative_mtp_detailed`. **Not measured:** what the
  server actually does with `speculative_mtp: true` on a gemma 4 request at
  runtime. That remains open and is not claimed here.
