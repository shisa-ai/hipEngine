# Q5 pair decode verified and extended: T16 dual SiLU GEMV, bit-exact

## Summary

UD impact-list task 5. Verified the dense pair decode policy for the UD
files' Q5 roles on gfx1100 and extended it. The verification finding is
structural: the registered Q5 pair decode (`linear_pair` / `gguf_q5_k` /
`pack8_gemv_decode_*`) requires a raw-abi dispatch, but the UD artifacts
materialize Q5 T16-only (allocations = tiles, no raw sidecar), so the pair
can never fire - a decode-step census confirmed every Q5 tensor runs as a
`t16_gemv_decode` single (131 on K_M, 80 on K_S) and every Q5 pair attempt
declines. The task premise's "~74 single pack8_decode launches / 165us pair
sighting" describes the pre-item-2 raw-materialized config, which the T16
compaction superseded. Extension: a bit-exact Q5 T16 dense dual SiLU GEMV
modeled on the resident direct-GEMV decode owner, wired through the
`GGUF_DENSE_PAIR_SILU_DECODE_POLICIES` table for the UD identities. The
measurable effect is small (the pairable share is only 9+6 gate/up pairs,
~0.5% of decode); the dominant Q5 decode finding is recorded for follow-up.

## Measurements

|---|---:|---:|---:|---:|

| attn k/v (1024x5120) | 37.2 us | 11 | 0.41 | 99 |
| **total** | | **131** | **15.82** | |

15.82 ms/token is ~32% of the 49.9 ms decode step; the achieved bandwidth
(220-380 GB/s on a ~2.5 TB/s part) is the real Q5 decode problem. The tile8
sibling is only ~5% better (15.07 ms). A raw pack8 sidecar would need +4.8
GB VRAM and only matches T16 bytes; the pair sighting's 165 us/pair implies
~750 GB/s for the pack8 pair - a local32-class T16 GEMV rewrite (like the
still-gated IQ4_XS local32 candidate, 2.5-2.9x) is the proportionate lever.

Dual leaf (XTX, blk.25 gate/up, rows=1):

| arm | time |
|---|---:|
| 2x single GEMV + silu_mul_separate | 256.0 us |
| Q5 T16 dual fused-SiLU | **222.0 us (0.87x)** |

Bit-exact: zero bf16 mismatches vs the unfused chain on the real pair (and
on synthetic tiles in the committed test).

Decode-step census after the wiring: K_M 131 -> 113 Q5 singles with 9
`pair_silu` fusions (True); K_S 80 -> 68 with 6 fusions. Mixed-quant pairs
and every other role decline unchanged.

E2E (XTX, published protocol 512/128): decode 20.05 -> 20.01 (K_M) and
18.16 -> 18.22 (K_S) - within the ~1% run noise, as expected from the
0.3 ms/token saving; prefill unchanged (591.0 -> 592.0 / 525.0 -> 529.7).

## Changes

- `gguf_t16_selected_gemv.hip`: `q5_k_t16_dense_dual_silu_gemv_kernel`
  (mirrors the resident direct-GEMV decode owner's 128-thread block, strided
  K ownership, weight expression, wave32 tree and serial wave-0..3
  reduction; both accumulators fed by one activation load; gate/up
  independently rounded to BF16 before the fused SiLU product) + launch +
  export.
- `gguf_t16_selected_gemv.py`: wrapper + registration
  (`linear_pair_silu` / `gguf_q5_k_t16_v1` /
  `q5_dense_dual_silu_gemv_decode_bf16_bf16_out`).
- `gguf_linear.py`: the rows==1 Q5 T16 decode branch in
  `launch_gguf_linear_pair_silu` (fires only when both sides dispatch to
  the `t16_gemv_decode` owner; mixed-quant pairs decline).
- `hip_gfx1100/__init__.py`: `GGUF_DENSE_PAIR_SILU_DECODE_POLICIES` entries
  for the UD K_M/K_S identities (3-tuple keys with the preset) at
  (1, 5120, 17408).
- `tests/test_gguf_q5_k_t16_dense.py`: the bit-exact decode-dual test
  (synthetic tiles vs single x2 + silu_mul_separate).
