# Project the TP2 bulk head for the last prompt row only

## Summary

Profiling the bulk prefill found that **46% of its kernel time was one kernel**:
`q6_k_t16_qmicro_planar_gemv_bf16_kernel<float>`, 2 calls per prefill at a p50 of
385 ms each - the sharded head projection, run as a *decode* GEMV over all 512
prompt rows.

The cause is a mismatch with the rest of the engine. Picking the next token
needs the **last** prompt row's logits and nothing else, and that is what both
other routes compute:

- the single-card route computes output_norm for every row but then calls
  `_sample_from_hidden(last_hidden_ptr)` at **rows=1**;
- this session's own token-serial route projects the head at **rows=1** per
  position (`_forward_token`).

The bulk path was the only route projecting all 512 rows, so it paid 512x the
head arithmetic on a 5120x248320 matrix and read 512 rows back over PCIe
(508 MB per rank) for logits nothing read.

`bulk_prefill` now takes `logits_rows`, and `generate` passes 1. The default is
still all-rows because the teacher-forced diagnostic needs every position.

## Result

| 512-token prompt, 128 decode, c=1, same bench and protocol | Prefill tok/s | Decode tok/s |
| --- | ---: | ---: |
| token-serial | 39.3 | 38.35 |
| bulk, all-rows head (before) | 459.7 | 38.94 |
| **bulk, last-row head** | **922.1** | 38.79 |

Runs: `[922.8, 922.1, 923.9, 922.0, 910.0, 909.0]` - stable, and **2.0x** the
previous bulk number on an identical protocol. Against the external references
at the same shape: single-card resident bulk prefill 875.8 (we now lead it by
1.05x), llama.cpp TP=1 941.8 (0.98x), llama.cpp TP=2 tensor split 1474.6 (0.63x,
down from 3.21x behind).

## Correctness: the change is numerically free

`scripts/tp2_prefill_kernel_inventory.py`-adjacent measurement, warm session,
same prompt: the last row of the all-rows projection and the single row of the
last-row projection are **bit-identical** - KL 0.000e+00, max_abs 0.000e+00,
same argmax (261), `array_equal` true. The GEMV computes each output row
independently and resolves the same variant either way.

That is what makes this safe to land without re-running the production gate: the
gate path (`teacher_forced_logits` -> all rows, `offset_rows = 0`) is unchanged,
and the product path now produces *the same logits* as the gate path for the row
it reads, so the decode trajectory that follows is identical too.

## Changes

- `hipengine/distributed/tp2_generate.py` - `_finish_bulk_prefill(rows, *,
  project_rows=None)` offsets both the final RMSNorm and the head projection to
  the trailing `project_rows` rows and reads back only those; `bulk_prefill(...,
  logits_rows=None)`; `generate` passes `logits_rows=1`. `logits_rows` is
  validated before any allocation so a bad argument is a plain `ValueError`
  rather than a launch failure that poisons the session.
- `scripts/tp2_prefill_kernel_inventory.py` - new ranked bulk-prefill kernel
  inventory, per rank, modelled on `tp2_decode_kernel_inventory.py` and reusing
  its probe, agent-to-rank mapping, region-window and rollup helpers.
- `tests/test_unit_distributed_tp2_generate.py` - the product-path test now
  injects a single readback row (a 4-row readback no longer fits the request),
  plus tests pinning `logits_rows` semantics, its range validation, and that
  `teacher_forced_logits` still gets every row.
