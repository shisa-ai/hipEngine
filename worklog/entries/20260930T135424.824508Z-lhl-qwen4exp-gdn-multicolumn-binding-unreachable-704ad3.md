# GD-4 multi-column GDN prefill: the promoted binding was unreachable

## Summary

The GD-4 promotion (`f1fdb54d0`) renamed the production tile16 binding from the DPP
route to the multi-column route, on the stated basis that "the env binding is the
live path". It was not live. `HIPENGINE_QWEN4_EXP_GDN_TILE16_VARIANT` is read only
inside the runner's `if colwarps_prefill:` block, and the condition that bound it
was `production and quant == "gguf_ud_q4_k_xl"` - but the UD quant is the
arithmetic-recovery profile, and `GDN_COLWARPS_PREFILL` is itself one of
`PRODUCTION_ARITHMETIC_RECOVERY_FLAGS`, so the UD binder sets that flag to `"0"`
and closes the very gate the variant feeds. The variant was therefore named
exactly where it could never dispatch, and cleared exactly where the gate is open
(`gguf_q4_k_m`). The promoted route ran zero times in every production profile.

The condition predates the promotion: it was inherited from the DPP binding, so
the DPP route was equally unreachable, and the "live path" claim in `f1fdb54d0`
was wrong for both.

## Changes

- `hipengine/generation/qwen4_exp_profiles.py`: the tile16 binding now tracks the
  gate it feeds - `quant != "gguf_ud_q4_k_xl"` instead of `==`. UD recovery keeps
  `""` (its gate is closed and its exact owners are the intended arithmetic);
  `gguf_q4_k_m` production now names `qwen4exp_gdn_tiled16_multi_prefill`.
- `tests/test_unit_qwen4exp_arithmetic_recovery.py`,
  `tests/test_unit_qwen4exp_ple_mapping_policy.py`: both pinned the old
  unreachable contract. Rewritten to pin the corrected one - UD binds `""` with
  `COLWARPS_PREFILL == "0"`, q4_k_m binds the multi-column route with
  `COLWARPS_PREFILL == "1"`.
- `scripts/qwen4exp_gdn_multicolumn_route_probe.py` (new): wraps the registered
  tile16 callables and the selection predicate, then runs a real prefill, so
  engagement is observed rather than inferred.
- `scripts/qwen4exp_layer2_profile_gate.py`: `CandidateSpec` gains a `quant` field
  (`_make_generator` previously hardcoded `QWEN4_EXP_QUANTS[1]`, so the gate could
  only ever run the UD profile and could not observe the binding on the profile
  that keeps the gate open). Adds candidate `production_gdn_multi_q4km`, which has
  an empty environment override and `count_registered_dispatch=True`: it can only
  pass if the q4_k_m production binder by itself dispatches the multi-column
  owner, and it records the dispatch count so the result cannot be vacuous.

## Validation

Engagement, measured by `scripts/qwen4exp_gdn_multicolumn_route_probe.py` on
gfx1151 at rows=512, `Hk16/Hv48/Dk=Dv=128`, production profile:

- before the fix: predicate reached 15/15 returning True, env var read inside the
  predicate was `''`, multi-column dispatches **0**, other tiled dispatches 0.
- after the fix: env var read inside the predicate is
  `qwen4exp_gdn_tiled16_multi_prefill`, predicate 15/15 True, multi-column
  dispatches **30**, other tiled dispatches 0.

Unit gates: `tests/test_unit_qwen4exp_arithmetic_recovery.py`,
`tests/test_unit_qwen4exp_ple_mapping_policy.py`, and the broader
`-k "qwen4exp or arithmetic_recovery or execution_profile"` selection all pass
(exit 0).

The pre-existing numerical evidence for the route remains
`benchmarks/results/2026-09-15-journey-gdn-multi-restoration/artifact.json`
(candidate env carries `GDN_COLWARPS_PREFILL: "1"` and the multi-column variant;
`measurement_valid: true`, `numerical_passed: true`, KL mean 1.07e-4, top-1
0.9983, per-category top-1 >= 0.9846, `prefill_last` KL ~1e-9). That artifact
validates the route on a UD profile with the column-warp suffix explicitly
restored, which is the configuration the route needs; it does not by itself cover
the q4_k_m production profile this fix now enables, so
`production_gdn_multi_q4km` is the gate that does.
