# Extend the Gemma 4 punchlist: verification gaps, cross-cutting candidates, missing dead ends

## Summary

Added three sections to `docs/campaigns/GEMMA4-26B-A4B-PUNCHLIST.md` at the
user's request. Nothing was removed and no existing row was rewritten; the
candidate tables P1-P13, D1-D12 and M1-M7 are untouched.

**The one finding that matters: the numerical gate stops exactly where the
window starts.** Every recorded gate run in the campaign uses `--prefill 1024`
(13 occurrences) or `--prefill 0` (3), and the sliding window is 1024 tokens, so
masking begins at position 1024 and a 1024-token prefill covers positions 0-1023
only. **No gate run has ever exercised the prefill attention path that P1
replaces** -- and P1 is the largest estimated win on the board (~1300 ms at
4096). The gate's `--prefill` pushes ids through the cache in a single forward,
so it cannot be extended past the window by raising `--prompt` alone.

Related and unresolved: sliding attention is 29.9 ms at 1024 tokens and
**1478.7 ms at 4096** -- 49x for 4x the tokens. A correctly windowed kernel is
bounded at 1024 keys per query and should scale about 4x (~120 ms); unwindowed
O(n^2) work would give 16x. The 49x is consistent with an unwindowed fallback on
top of a slower kernel. If the fallback does not mask, P1's win is larger than
estimated **and today's 4096-token prefill output is wrong**. That check has not
been run.

## Changes

- New **Verification prerequisites** section (V1-V4): extend the gate past the
  window; build an independent oracle for the windowed path (the gate compares
  two hipEngine arms, so it cannot catch a mask both share); establish whether
  the fallback masks at all; re-run the decode gate at 4096 context.
- New **Not yet in this scoreboard** subsection: 8192 context, time to first
  token, a prefill floor column, a prefill launch census, sampler cost, and the
  `hipengine serve` path.
- New **Cross-cutting** candidate table (X1-X6): f16 KV storage, XTX headroom as
  a tracked constraint, lm_head byte reduction, the vendored AOTriton release,
  prefill graph capture, and an explicit batching-is-out-of-scope note.
- **Measured dead ends** expanded from 7 to 13 rows. The six added were all
  already refuted and recorded elsewhere, just not on this page.

## Validation

- `python3 scripts/docs/check_all.py`: only the pre-existing
  `2026-09-21-zbook-fast-cpu-gpu-sampling.json` worktree-path drift fails.
- All ten markdown tables checked for uniform column counts.
- The gate-coverage claim is from a count over `GEMMA4-26B-A4B-OPTIMIZATION.md`
  (`--prefill 1024` x13, `--prefill 0` x3) plus reading `capture_chain` in
  `scripts/gemma4_teacher_forced_gate.py`, which confirms `--prefill` is one
  forward. The 49x scaling is the punchlist's own published numbers, not
  re-measured.
- The six new dead-ends rows cite artifacts under `benchmarks/results/` and
  worklog entries; their `kl_max` and throughput values were read from those
  files, not re-run.
