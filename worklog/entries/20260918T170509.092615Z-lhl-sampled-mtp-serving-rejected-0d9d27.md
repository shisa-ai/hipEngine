# sampled MTP acceptance is a measured serving loss: the route stays closed

## Summary

The sampled (`min(1, p/q)` plus residual resample) MTP route now runs end to end
in serving, and it is a measured loss: with the evidence-row switch in place a
temperature-0.7 request reaches a provider and commits sampled acceptances, and
on a matched ShareGPT load it decodes **0.47x of its in-load true-AR control at
c=1** while **99%** of its output tokens come from speculative cycles. The limit
is not acceptance but the cycle's own cost: **5.3x** the identical draft chain's
greedy cycle, because the native target graph commits the argmax accept on device
and a sampled row therefore runs the eager verifier and computes the accept
decision on the host from full-vocabulary logits. The switch is reverted; the
route stays closed and every temperature request keeps running autoregressive.

## Validation

Serving, zbook / Radeon 8060S (gfx1151), Qwen3.8-27B Q4_K_M, bf16 KV,
production profile, commit `cd8a5b29b` plus the row switch, one server process,
`HIPENGINE_MTP2_OUTPUT_SPANS=1`, `scripts/sharegpt_mtp_routing_pass.py
--num-prompts 4 --min-prompt-len 64 --max-prompt-len 900 --max-total-len 2048
--output-len 128 --record-ids --seed 4242 --route-mix off,off,on,on`:

| point | AR control | sampled MTP | ratio |
| --- | ---: | ---: | ---: |
| c=1, t=0.7 | 13.56 tok/s, TTFT 1,735 ms | 6.37 tok/s, TTFT 5,628 ms | 0.47x |
| c=2, t=0.7 | 9.50 tok/s, TTFT 3,497 ms | 7.07 tok/s, TTFT 6,961 ms | 0.74x |
| c=1, t=0.0 (greedy control) | 20.58 tok/s | 34.07 tok/s | 1.66x |

- c=1 t=0.7 sampled rows: 127 and 126 of 128 tokens from speculation (coverage
  99.2% / 98.4%), 89 and 87 accepted drafts over 38 and 39 cycles -- the same
  counts the greedy control accepted on the same prompts.
- Cost: 3.37 emitted tokens per cycle at 528.5 ms/cycle against 98.9 ms/cycle for
  the identical draft chain at t=0, i.e. 7.2 autoregressive steps of work per
  cycle. The t=0 point on the same load is +66%, so neither the harness nor the
  host explains the sampled arm.
- c=2 is not a sampled-MTP rate: 242 `no_provider` events against 244
  autoregressive tokens, because the admitted policy cell is the one-row `C1/K3`
  cell and the due group is width 2.
- Correctness basis: the exact induced-law gate from the earlier unit (824/824
  comparisons, max total variation 4.5e-16, 144/144 law agreements, Monte-Carlo
  arm clean). Cross-arm token identity is deliberately **not** used as an oracle
  here: the sampled walk consumes the row's sampler stream differently from the
  autoregressive path (acceptance draws plus a possible residual resample against
  one draw per token), so equal ids are not expected even though the induced law
  is equal.
- Narrow unit bundle: `tests/test_unit_qwen35_gguf_mtp2_seam.py`,
  `tests/test_unit_qwen35_gguf_mtp_session.py`,
  `tests/test_unit_speculative_sampling_modes.py`,
  `tests/test_unit_mtp_sampled_accept.py`,
  `tests/test_unit_qwen35_gguf_mtp2_c1_physical.py` - 241 passed, no failures
  (`timeout 1800 uv run pytest <those five files> -q`).

## Next

- The lever is a **device-side sampled accept**: compute the coupled acceptance
  from device logits and commit on device like the argmax path, which is what
  removes `allow_graph=False` and the host full-vocabulary work. The arithmetic
  gate already fixes the target law and does not need redoing.
- At c>=2 the sampled route also inherits the one-row policy cell, so any future
  arm needs either a wider admitted cell or an explicit decision about serial
  one-row sampled cycles.
