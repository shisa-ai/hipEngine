# M2h pinned accept staging measured null

## Summary

The M2 investigation identified the accept-interval wall as the dominant
non-target cost at every width (marker decomposition: at production bound 4
the first accept upload of each subgroup stalls a median 210.9 ms while the
16-row target kernels total ~42 ms; at bound 8 the single upload stalls a
median 758.6 ms). `faulthandler` stack dumps during the stall showed the
engine thread inside a synchronous `hipMemcpy` in `_upload_accept_array`
with no other Python thread in a HIP call, and the m2f probe showed a 4-byte
copy from a second thread stalling up to 1.04 s process-wide. The initial
hypothesis was HIP-runtime pageable-copy serialization, so the seven per-cycle
accept uploads were re-issued through one persistent `hipHostRegister`-pinned
64 KiB staging arena (synchronous, same stream ordering, bit-identical data).

**The hypothesis is dead.** Same-session full C1-C8 pair on the W7900-class
gfx1151 host: control (production bound 4, pinned) moved every width inside
+-1.8% of the M0 re-freeze, indistinguishable from the AR arms' own drift
(C1 +0.1%, C8 +0.1%); treatment (bound 8, pinned) reproduced the M1 wide
regression unchanged (C5 +12.1% but C6/C7 -18.6/-24.7%). A stream-ordered
copy from pinned memory waits on the same queued work as the pageable copy,
so the upload "stall" is the accept path *waiting for previously queued GPU
work* (target pass plus whatever else the server has enqueued, e.g. chunked
prompt prefill), not a pageable-copy pathology. The change was reverted
(`git restore` of the adapter and its test; seam suite green at 57 nodes);
the width-1 validator change from the same working pass was retained as
`aeb391dbb` (M3 groundwork, separate unit).

## Consequences for M2

- Host copy morphology is closed as an explanation. The M2 lever must remove
  the *wait itself*: either shrink/overlap the queued work inside the accept
  window (prefill interleave, target-pass structure, wide-owner recovery), or
  stop paying a full device drain per subgroup in the accept interval.
- The bound-4 decomposition bounds the prize: per C8 cycle (931.3 ms wall)
  marked host spans account 501 ms (2 x proposal 35.4 + 2 x enqueue-drain
  211.2 + commit/readback ~8 ms) and ~430 ms is outside the marked phases
  (target launch, replay/prefill, provider). A kernel-family trace of the
  current head at C8 bound 4 (m2i, warm + profiled, `HIPENGINE_COMPILER_VERSION_FILE`
  pinned) is the designated next evidence: it names which GPU families own
  the 211 ms drain window (target kernels vs chunked prefill vs proposal
  residue) and whether gaps show GPU idle.
