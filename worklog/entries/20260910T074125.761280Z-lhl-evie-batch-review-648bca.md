# EVIE batching: proceed with isolated attention and stronger RED gates

## Summary

Proceed with query batching, after amending
[the proposed handoff](20260910T072310.038380Z-lhl-evie-fddba8.md).
The isolation surfaces identified there are relevant, and the segmented
cluster8 recurrence exists with the stated metadata. The design and RED
strategy need the corrections below before execution.

1. **Batch dense projections but retain separate attention blocks.** A
   dense score matrix over B concatenated length-L sequences costs B^2 L^2
   entries per head; independent blocks cost B L^2. At B=8 the proposed
   masking route computes/stores eight times the needed attention scores,
   and the value GEMM also computes through the masked blocks. A mask kernel
   makes finite-input attention mathematically isolated, not computationally
   efficient. Prefer batch/head planes with strided-batched GEMMs for uniform
   lengths, pointer-array batching or length buckets for ragged inputs, or a
   segmented attention kernel. Reuse existing attention layouts/256-byte
   base-alignment rules. A dense masked route can be a bounded short-query
   correctness baseline, but should not determine the document architecture.

2. **Repeated identical queries do not prove isolation.** With identical
   Q/K/V and repeated position IDs, allowing attention over B copies multiplies
   both the softmax numerator and denominator by B, leaving its mathematical
   output unchanged. It can pass a duplicate-query comparison with a completely
   missing attention mask. Test distinct queries first; hold A fixed while
   replacing B with a very different same-length C, and assert A is unchanged
   under the same batch shape/schedule. Include batch permutation, unrelated
   neighbor lengths, left/right padding, short segments of lengths 1/2/3/4/5,
   slot reuse, repeated calls and explicit empty-input behavior. Use a conv
   boundary impulse to detect leakage into the first three rows of the next
   segment. Compare intermediate conv/recurrence/attention outputs to separate
   CPU calls, not only final embeddings.

3. **Do not implement conv isolation as a boundary state reset.** The existing
   `linear_attn/conv.hip:199` prefill kernel computes token outputs in parallel
   and reads previous tokens directly from `hidden_states`. For kernel size 4,
   every tap at the first three tokens of a new segment needs a segment-start
   check. A reset at token==segment_start does not prevent those reads, and a
   shared mutable reset can introduce races. For stateless EVIE encode, use
   zero for a tap whose source precedes the segment start; otherwise read the
   same segment's input. If preserving final conv state, use separate state
   owners and a separate/race-free update. Retain the strict tap accumulation
   order. An initial per-segment call to the existing kernel with isolated
   state is a valid slower baseline while testing batched projections.

4. **Choose the arithmetic contract before implementation.** The handoff's
   "bit-for-bit or <=1e-6" mixes two different contracts. Larger GEMM shapes
   may choose different reduction schedules even in FP32. Exact segment/state
   ownership and same-shape neighbor isolation are mandatory. Cross-width byte
   equality additionally requires a compatible arithmetic schedule. If that
   fails only numerically, retain the sequential strict route and qualify an
   explicit batched numerical variant through predeclared retrieval gates;
   do not loosen thresholds after inspecting results. FP16 single-fixture
   bounds are not full profile certification. Retain determinism, finite
   intermediates, real retrieval/heldout gates for production qualification,
   and registered strict fallbacks.

5. **Keep metadata and document ownership explicit.** Existing segmented GDN
   takes int32 cu_seqlens and int64 state_indices; allocate/reset separate
   state slots and preserve the unscaled normalized Q expected by cluster8.
   Decide packed valid tokens versus padded batch representation rather than
   vaguely combining the two. Build positions independently per sequence and
   split outputs by validated offsets. For document batching, image-token
   lookup must select each request's visual-feature slice; per-token embedding
   arithmetic alone does not establish correct image ownership. A 64-token
   scratch capacity bucket is not a logical sequence or segment length.

6. **Do not promise the projected page speedup.** A torch batch-size ablation
   is useful motivation, but its gain is not transferable to hipEngine's
   kernels. If vision stays sequential, only the text portion can benefit.
   With unchanged fraction f and text speedup s, page speedup is bounded by
   1/(f+(1-f)/s), ignoring new packing costs. Measure vision/text/recurrence
   separately and report query-only results before forecasting document gains.
   The newer HIP-event sums also do not alone establish a hard 9% graph
   ceiling: an event interval may include idle gaps between host submissions,
   and instrumentation can perturb many short launches. A device/API trace and
   uninstrumented wall comparison are needed before declaring batching the
   only remaining lever or all remaining time useful GPU computation.
