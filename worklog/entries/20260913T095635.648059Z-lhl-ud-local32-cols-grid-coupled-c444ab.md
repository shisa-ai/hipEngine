# The local32 column count is optimal at 8 and was not coupled to its grid divisor

## Summary

`gguf_iq4_xs_local32_gemv` is the largest single family in UD-Q4_K_M: 117
tensors, 4760.0 MB, 11.373 ms/step (31.3% of UD kernel time) at 425-441 GB/s
against the t16 rowtile owners' 600-704 GB/s. This unit swept the one
remaining bit-identical geometry knob on that owner, `COLS`, and found the
shipped value already optimal. **No tuning change was retained.** The
sweep also exposed a latent trap in the source, which is what this unit
commits.

The four local32 owners (`gguf_iq4_xs_local32_gemv_kernel`,
`gguf_iq4_xs_local32_dual_silu_kernel`, `gguf_iq4_nl_local32_gemv_kernel`,
`gguf_iq_split_local32_gemv_kernel`) each index output columns from
`blockIdx.x * COLS`, but their seven launchers computed `grid = N / 8` as a
literal. `COLS` and the grid divisor are the same quantity, so editing `COLS`
alone makes the launcher cover only `N / 8 * COLS` columns and silently
computes a fraction of the output -- which reads as a large speedup.

The first sweep hit exactly that: `COLS = 2` "measured" 4.803 ms/step and
991 GB/s, a 2.25x win. Comparing the actual output against the shipped
`COLS = 8` output caught it as a mismatch. The commit replaces the literal 8
in both places with `GGUF_IQ_LOCAL32_COLS` so the two cannot drift.

## Changes

`hipengine/kernels/hip_gfx1100/quant/gguf_iq_dense.hip`:

- New file-scope `#define GGUF_IQ_LOCAL32_COLS 8` with a comment recording the
  sweep and the failure mode.
- Four `constexpr int COLS = 8;` -> `constexpr int COLS = GGUF_IQ_LOCAL32_COLS;`.
- Seven `const dim3 grid(unsigned(N / 8));` ->
  `const dim3 grid(unsigned((N + GGUF_IQ_LOCAL32_COLS - 1) / GGUF_IQ_LOCAL32_COLS));`.

Behaviour-preserving at `GGUF_IQ_LOCAL32_COLS 8`: the same output dump
(`/tmp/phase8/dump-cols8.bin` vs `/tmp/phase8/dump-cols8b.bin`, byte-identical
`cmp`) and the same timing (11.198 vs 11.220 ms full pass, 10.800 vs 10.796 ms
per-tensor).

## Validation

Per-tensor measurement over all 117 IQ4_XS tensors at rows=3, each launch
synchronised, best of 3 after 2 warmups, on the W7900 (gfx1100):

| COLS | ms | GB/s | vs COLS=8 | output |
| --- | --- | --- | --- | --- |
| 2 | 11.297 | 421.4 | 0.955x | bit-identical |
| 4 | 10.768 | 442.1 | 1.003x | bit-identical |
| 8 (shipped) | 10.796 | 440.9 | 1.000x | -- |
| 16 | 31.890 | 149.3 | 0.339x | bit-identical |

Full pass over the same 117 tensors, rows=3: 11.220 ms / 424.2 GB/s, which
reproduces the 2026-09-13 verifier census figure of 11.373 ms/step and
therefore validates the harness. `COLS` only changes which output columns
share a block -- the per-(row, column) k ownership, FMA order, shuffle tree
and cross-wave serial sum are untouched -- so every value is bit-identical,
which the dumps confirm.

Harnesses: `/tmp/phase8/iqxsfull.py` (full-pass and per-tensor timing),
`/tmp/phase8/iqxsdump.py` (output dump for the bit-identity check).

Tests: `pytest tests/test_gguf_iq_local32_decode.py
tests/test_gguf_iq_local32_rows.py tests/test_gguf_iq_dense_tables_closed_form.py -q`

## Next

`COLS` is closed; do not re-sweep it, and if it is ever changed, change
`GGUF_IQ_LOCAL32_COLS` and nothing else. The IQ4_XS gap to the t16 rowtile
owners is structural (raw layout, no tile), so the remaining lever is the
T16 repack item in `docs/UD-GFX1151-OPTIMIZE.md`: a new `GGUF_IQ4_XS_T16_*`
layout plus CPU packer and inverse, then a new owner. Also note that
`rocprofv3 --pmc` is unusable on this host (`--list-avail` enumerates no
PMCs and a `--pmc` run hangs), so the Q5_K residual gap stays blocked on
hardware counters as its plan item says.
