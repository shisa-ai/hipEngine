# Q4 decode: caller-owned o_proj scratch removes 28 malloc/free pairs per token (9.7% median, bit-identical)

## Summary

`q4_dense_gemv_f32_bf16w_f32_out` (the `o_proj` decode GEMV) already accepted an
`x_bf16_scratch` buffer, but its only caller in `forward_layers` never supplied
one, so the wrapper fell through to `malloc(7168)` + `free` once per layer. That
is 28 malloc/free pairs on every decoded token. The Q4 runner now allocates one
7168-byte bf16 scratch at construction and passes it.

The arithmetic is unchanged: the same `f32_to_bf16` narrowing and the same pack8
GEMV run on the same values. The two lanes produce a bit-identical logits
checksum (relative difference `0.000e+00`) and the same 40-token chain.

Measured in-process A/B over four runs (alternating lane order, same loop and
fixture): median **9.66%** faster decode (3.8-5.5 ms/token), and the Q4 lane
becomes far more stable (48.1-49.1 ms/token vs 51.9-55.1 ms/token).

## Changes

- `hipengine/runtime/vibevoice_qwen2.py`: add `self._o_proj_x_bf16 = None` to the
  base runner, and pass `x_bf16_scratch` in `forward_layers` only when the runner
  owns one.
- `hipengine/runtime/vibevoice_qwen2_q4.py`: allocate the scratch once via
  `keep(_alloc(heads * head_dim * 2))`.
- `scripts/vibevoice_asr_q4_decode_scratch_bench.py`: new rotating three-lane A/B
  bench (Q4 per-layer malloc, Q4 persistent scratch, dense bf16) that asserts the
  Q4 lanes stay bit-identical.
- `benchmarks/results/2026-09-14-gfx1151-vibevoice-q4-decode-scratch.json`,
  `benchmarks/README.md`, `benchmarks/CHANGELOG.md`.

## Validation

- `tests/test_gpu_vibevoice_qwen2_q4_runner.py`: 13 passed, 1 xfailed (unchanged).
- `tests/test_gpu_vibevoice_qwen2_runner.py`: 8 passed. The dense implementation
  of `dense_gemv_f32_bf16w_f32_out` takes keyword-only arguments with no
  `**kwargs`, so the kwarg is passed conditionally; the bf16 lane passes nothing
  new and is unaffected.
- Bit-identical logits checksum and identical token chain between the two Q4
  lanes in every run.

### Two traps worth recording

1. `close()` has **two independent free paths**: the attribute-name tuple and
   `self._buffers`. A buffer must be released through exactly one. The first
   version of this change both `keep()`ed the scratch (appending it to
   `self._buffers`) and added it to the attribute tuple, which double-freed it
   and raised `HIP error 1` in
   `test_weights_own_buffers_and_runners_borrow`. `_dual_scratch` avoids this by
   being in `self._buffers` only. That existing test is the regression guard.
2. Do not compare this session's absolute rates to the recorded 48.1 ms/token in
   `2026-09-14-gfx1151-vibevoice-q4-pack8-decode.json`. That run had the same
   per-layer malloc, but its dense bf16 lane measured 72.2 ms/token against 74.75
   here, so the host was in a different power/thermal state. The retainable claim
   is the in-process A/B delta and the matched same-process ratio (Q4 1.55x the
   dense bf16 lane this session, vs 1.39x for the same Q4 lane with per-layer
   malloc), not an old-to-new absolute rate.
