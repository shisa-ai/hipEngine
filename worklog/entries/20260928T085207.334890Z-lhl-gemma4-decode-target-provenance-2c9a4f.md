# the 2x decode target is parity with the same-host reference not beating it

## Summary

`20260928T070233` concludes that "the objective's 2X on decode ... target is
roughly 49.7 tok/s, which is *above* the same-host llama.cpp reference by about
19%. So reaching the objective's decode bar on this host means beating llama.cpp,
not merely matching it." **That is wrong**, and the record already says so.

`20260928T025924`, written while the decode item was live, states it directly:

> The 2x decode item is untouched this unit: the engine is at 20.97 tok/s at 512
> against llama.cpp's 41.92, so the objective's 2x decode target is parity with
> the same-host reference.

The arithmetic agrees. The baseline contemporaneous with the objective was
**20.97**, not 24.85, and 2 x 20.97 = **41.94**, which is llama.cpp's 41.92 to
within 0.05%. The 24.85 figure I used is the branch's *pre-fix mixed
configuration* baseline measured much later, after the route work had already
moved the number -- so doubling it answers a different question.

The difference matters because the two framings imply different work. "Parity
with llama.cpp" is a reachable target by matching an external engine on the same
silicon. "Beat llama.cpp by 19%" is not the same claim and would justify a
different, more aggressive line of attack. The correct statement is that the
objective's decode bar and the same-host reference are the same number, and the
gap to it is 1.53x (27.31 against 41.92).

The distance figure in `20260928T070233` survives -- 1.53x is right -- and so
does its central point that the 80.20 campaign target is gfx1100 arithmetic while
41.92 is this host's comparator. What does not survive is the derived claim about
what the bar requires.
