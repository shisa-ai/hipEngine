# Chunk 4096 at native context leaves 84-168 MB scratch margin: blanket promotion blocked

## Summary

RT-1 and RT-3 measured the 4096-row prefill workspace at **+4.96 GB** and framed it
as "paid by the prompt that receives the win", with short requests "byte-for-byte
identical in time and memory". **Both framings are harness artifacts.**

`Qwen4ExpPrefillWorkspace.allocate_inputs` sizes the prefill input buffers as
`rows = min(prefill_chunk_size, max_sequence_length)`, and that
`max_sequence_length` is the **runner's** — set from the model's native context in
`__init__`, where the base workspace is allocated, before any request-level
context applies. `qwen4exp_profile_gap.py` set
`max_sequence_length = max(768, prompt_tokens + 1)`, tying context to prompt
length. That is why RT-3's table showed p512 resolving to 768 rows at *both* chunk
sizes and concluded the workspace "is already shape-aware".

**It is context-aware, not prompt-aware.** In the serving path the context is the
model's native 262144, so `rows = min(chunk, 262144) = chunk` for every session,
and the larger chunk is paid at session construction by **every** session.

Measured with `scripts/qwen4exp_chunk_memory_probe.py` (Tier-1 allocation probe, no
full prefill), native context 262144, one process per arm:

| config | chunk 1024 peak | chunk 4096 peak | delta | scratch margin @4096 | device scratch margin @4096 |
|---|---:|---:|---:|---:|---:|
| c1 | 93.03 GB | 98.73 GB | **+5.71 GB (+6.13%)** | **168 MB** | **84 MB** |
| c2 | 103.53 GB | 114.94 GB | **+11.41 GB (+11.02%)** | **252 MB** | **168 MB** |

Chunk 1024 leaves 2.39 GB (c1) and 4.78 GB (c2) of device scratch margin. **At
chunk 4096 the allowance is consumed to within 84 MB and 168 MB** — no headroom for
another owner, a third session, or any future workspace.

**A blanket production chunk-4096 is therefore not promotable**, and this is the
concrete measured blocker AGENTS.md requires rather than a hypothesis.

## Validation

`scripts/qwen4exp_chunk_memory_probe.py`, production profile, cached build with
`HIPENGINE_REQUIRE_CACHED_BUILD=1`, clean tracked revision (the probe refuses a
dirty one), `--capacity` 1 and 2, `--chunk-size` the only difference within each
pair, ~52 s per arm, one repetition each. The delta is **entirely scratch**:
`explicit_components_bytes` moves only 99,739,496,800 -> 99,802,411,360 at c2,
while the scratch allowance grows 8.59 -> 15.39 GB and observed device scratch
grows 3.81 -> 15.22 GB.

Independent corroboration from the fairness packet, where `LLM.prepare()` was
passed `max_sequence_length=4097` and the session still reported **262144**:
`prefill_token_ids` is `rows * 8`, and it read 8,192 B at chunk 1024 and 32,768 B
at chunk 4096 — a direct read of rows 1024 -> 4096 at native context, independent
of the prompt.

## Next

- **The crossover is not established.** Only native 262144 was measured. A capacity
  guard needs the context below which chunk 4096 is admissible, and this packet
  shows the guard has only 84-168 MB to work with at native context — so it must
  actually check rather than assume.
- Tier-1 only: allocation validity and tracked peak, no full-prefill completion
  claim at depth.
- **This does not retract the speed win.** The generator chunk 4096 delivers
  -5.74% / -5.80% prefill wall through the engine loop at 183x separation with no
  peer-fairness cost and a halved peer worst-gap
  (`worklog/entries/20261003T190751.024622Z`, `...20261003T191902.865457Z`). Both
  results stand: the win is real, the blanket default is blocked on measured
  admission headroom.
