# R0523: c4 race attributed to graph-replay GDN recurrent-state corruption

## Summary

R0523's intermittent c4 packed-decode race is **attributed to GDN recurrent-state
corruption during packed-decode graph replay**, not the down-residual arithmetic
(already falsified in
[`20261111T004304.713417Z`](20261111T004304.713417Z-lhl-r0523-q4-attribution-falsified-993a7a.md)).
Per-step, per-row hashing of the packed GDN recurrent state on the **real server
c4 route** shows a row's recurrent digest diverging from the reference multiset as
early as **decode step 4**, then propagating through every later step (the state is
cumulative). The previously observed step-73 token flip (6866→3154) is downstream
amplification of much earlier state damage.

**Update (clean untraced reproduction):** the per-step device→host hashing is a
strong observer effect. With conv+recurrent hashing enabled (every step, and every
2nd step), 15- and 20-rep c4 bursts were **byte-clean** in all measured reps — the
added synchronization suppressed the race. Running the R0523 clearing command
**without** the trace env (`HIPENGINE_R0523_STATE_TRACE` unset), 60 reps, reproduced
it cleanly: **6/60 c4 measured reps diverge, every one at request_index=1, decode
position 73, token 6866→3154** (context 512+73=585); the separate c1 oracle and the
live-admission rep are clean. The fixed row/position/token signature matches the
original R0387 report. The earlier "step 4" onset came from a perturbed rec-only
trace and is provisional; the robust facts are (a) the race is real and reproducible
untraced, and (b) it always surfaces at decode pos 73 for this prompt.

## Validation

W7900 GPU0 (gfx1100), hermetic TheRock env, dense Qwen3.8-27B-Q4_K_M, BF16 KV,
greedy, strict, native packed route; prompt_length 512, decode 128, c4.

- Trace lines land in the server log
  `/tmp/hipengine-gfx1151-f1-server/hipengine-c4.server.log` (the bench spawns the
  server as a subprocess; env is inherited via `os.environ.copy()`).
- The scheduler **permutes physical slot assignment across repeats** (the same 4
  step-1 digests appear in different row order), so per-row comparison is invalid;
  the parser compares the **sorted multiset** of row digests per step.
- 23 repeats parsed: first divergence **step 4, rep 8** (digest `4ff64458baa043b3`
  → `35add7ca235b3abc`); divergence-onset steps across repeats {4, 20, 25, 58, 99,
  103, 118}. Once a row corrupts, its digest stays divergent for all later steps.
- Caveat: the per-step device→host hashing adds synchronization (observer effect),
  which can shift the observed onset; the attribution (recurrent state corrupts in
  replay) is robust to that, the exact onset step is not.
