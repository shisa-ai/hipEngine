# MTP/AR attribution proved against committed output spans, and refusal events separated from tokens

## Summary

`reconciled` was arithmetic consistency wearing an attribution label:
`ar_output_tokens` is defined as `completion_tokens - mtp_output_tokens`, so a
response reporting five completion tokens, three speculative ones and
ninety-nine in-cycle autoregressive ones satisfied it. It now fails, and the
split is checked against committed work instead of against the subtraction.

Two independent sources of evidence, in increasing strength:

1. **Always reported.** The committed cycle records bound the speculative
   output: each committed speculative cycle emits one verified token plus its
   accepted drafts, so `mtp_output_tokens` may not exceed
   `accepted_draft_tokens + (cycles - depth-0 cycles)`. The response publishes
   that bound (`mtp_output_tokens_explained_by_cycles`,
   `unexplained_mtp_output_tokens`, `speculative_cycles`), requires committed
   cycles for any speculative output, requires
   `ar_output_tokens_in_cycles <= ar_output_tokens`, and names every failed check
   in `reconciled_reasons` instead of returning a bare boolean.
2. **With `HIPENGINE_MTP2_OUTPUT_SPANS=1`.** The backend records one committed
   output span per speculative cycle and per autoregressive step — execution
   mode, planner reason, emitted-token position, token count — and the response
   publishes `span_accounting`: the spans must be contiguous, every speculative
   token must be inside a span, the spanned autoregressive tokens must be exactly
   the in-plan ones, and the unspanned remainder must equal
   `ar_output_tokens - ar_output_tokens_in_cycles`.

## What the real run showed, including a correction to my own check

First c=1 ShareGPT run with spans on: **19 of 24 rows reconciled**, five failing
`spans_do_not_reach_the_completion_count`. That was a defect in the check, not in
the engine. A request legitimately emits autoregressive tokens outside the plan —
the prompt-prefill root token before it, and the final token when the decode that
produces it retires the row — and the accounting helper deliberately records no
span for a step whose row is already released. The five rows had
`completion=128, mtp=126, ar=2, in_cycles=1, spans tiling 1..127`, i.e. exactly
one trailing unspanned autoregressive token.

So the check was replaced by the identity that is actually true and still
discriminating: `unspanned_tokens == ar_output_tokens - ar_output_tokens_in_cycles`,
plus "all speculative tokens are spanned". Under it, the same protocol proves
**24 of 24**.

Second c=1 ShareGPT run (same protocol, spans on):

| Quantity | Value |
| --- | ---: |
| Requests / failures | 24 / 0 |
| MTP output share | 99.06% |
| Decode rate | 20.05 tok/s |
| Committed spans | 1,046 |
| Spanned tokens | 3,067 (3,043 MTP + 24 AR) |
| Unspanned tokens | 5 |
| Completion tokens | 3,072 |
| Unexplained MTP tokens | 0 |
| Requests with a complete proof | 24 of 24 |
| Driver exceptions | 0 |

The identity holds exactly: `3,067 + 5 = 3,072` and `5 = 29 - 24`. Every one of
the 3,043 speculative tokens is inside a span, so nothing speculative hides in
the unspanned remainder.

## Refusal events are not token counts

`fallback_reason_counts` merged step events, failure events and the admission
refusal into one map and was carried in the harness row next to token counts,
where the real numbers invite exactly the wrong reading: this run reports
**24 `no_provider` events and 29 autoregressive tokens** (24 emitted by the
depth-zero `no_provider` cycle that opens each request, 5 by the retiring
decode). The field is now `fallback_event_counts` (with `fallback_event_total`),
the harness row carries `fallback_event_counts` / `fallback_event_total`
separately from `ar_output_tokens` / `mtp_output_tokens`, and per-reason *token*
attribution is reported only from spans as
`span_accounting.ar_tokens_by_reason`. `docs/API.md` states the unit in both
places.

## Changes

- `hipengine/speculative/accounting.py`
  - `OUTPUT_SPANS_ENV` / `output_span_recording_enabled()` and `_record_span`,
    called from `record_speculative_outputs` (mode `mtp` for a speculative
    cycle, `ar` for a depth-zero cycle) and `record_autoregressive_step`. Off by
    default; the accounting block gains `output_spans` only when it is on.
  - `span_accounting(...)` validates a span list against the reported split and
    returns the tiling result, the unspanned counts, and the failed reasons. It
    is shared by the server and the gate so the proof has one definition.
- `hipengine/generation/qwen35_gguf.py`: `_GGUFResidentLoopRow` declares
  `mtp2_output_spans`. The row is a slots dataclass, so the shared helper could
  not attach the field at runtime; the diagnostic switch raised
  `AttributeError` inside the driver thread and **closed the engine service**
  (every concurrent request answered 500). `_record_span` now also treats an
  `AttributeError` as "no proof recorded" rather than propagating, because an
  operator-set diagnostic must never be able to take down generation.
- `hipengine/server/api.py`: `_mtp_output_reconciliation` (the committed-cycle
  bounds and the reason list), the span proof when spans were reported, and the
  `fallback_event_counts` / `fallback_event_total` rename.
- `scripts/gguf_mtp_api_gate.py`: requires the committed cycle counts, a
  non-empty `reconciled_reasons`-free reconciliation, `unexplained == 0`, and a
  passing span proof when one is present.
- `scripts/sharegpt_mtp_routing_pass.py`: carries the new fields, reports
  `reconciled_requests` / `unreconciled_requests` / `span_proof_requests` /
  `span_proof_failures` / `fallback_event_total`, and tells the operator to set
  the switch when no span proof was recorded.
- `docs/API.md`, `docs/QWEN38-GFX1151-MTP-SERVING-IMPROVEMENTS.md`,
  `benchmarks/README.md`, `benchmarks/CHANGELOG.md`, and the artifact
  `benchmarks/results/2026-09-17-gfx1151-qwen38-mtp-attribution-span-proof.json`.

## Notes

- The span switch is diagnostic, not a production default: the list grows with
  the cycle count (1,046 spans for 3,072 tokens here) and the aggregate proof is
  already reported without it.
- The five unspanned trailing tokens are the honest answer to "did every emitted
  token come from a committed cycle": no, five came from the decode that retires
  the request, and the response now says so instead of leaving the remainder
  implicit in a subtraction.
- `docs/REFACTOR.md` has no new entry: nothing here is a temporary flag or a
  fallback to remove. The diagnostic switch is documented in `docs/API.md`.
