# The IQ4_XS local32 owner degrades with the row slab at a fixed byte count

## Summary

`gguf_iq4_xs_local32_gemv` is the largest family in UD-Q4_K_M (117 tensors,
4760.0 MB, 11.373 ms/step = 31.3% of UD kernel time). It runs at 425-441 GB/s
against the t16 rowtile owners' 600-704 GB/s. With `COLS` and the `WAVES`
heuristic already measured-optimal (the 2026-09-09 wave sweep plus this
session's `COLS` sweep), the only remaining bit-identical knob was the
`ROWS > 1` launch-bounds floor.

**That knob is neutral, so nothing was retained.** The unit's value is the
diagnosis it produced: the owner's achieved bandwidth falls monotonically with
the row slab at a *fixed byte count*, which is a design constraint on any
replacement owner.

## Changes

None retained. The scratch edit was a one-line change of the IQ4_XS
`gguf_iq4_xs_local32_gemv_kernel` launch bounds from
`ROWS > 1 ? 1 : (16 / WAVES > 0 ? 16 / WAVES : 1)` to
`ROWS > 1 ? <N> : ...` for N in {2, 4, 8}. The file was restored byte-for-byte
afterwards (`git status -sb` clean, verified).

## Validation

Per-tensor timing over all 117 IQ4_XS tensors, each launch synchronised, best
of 3 after 2 warmups, W7900 (gfx1100), `/tmp/phase8/iqxsfull.py`:

**Launch-bounds floor at rows=3** (baseline min-blocks 1 = 10.796 ms /
440.9 GB/s):

| min blocks | ms | GB/s |
| --- | --- | --- |
| 2 | 10.869 | 437.9 |
| 4 | 10.803 | 440.6 |
| 8 | 10.828 | 439.6 |

All inside run-to-run spread, so the compiler either does not comply or
occupancy is not what the floor controls.

**Row-slab gradient at a fixed byte count** (one pass over the same 4760.0 MB,
so the byte count per measurement is identical):

| rows | ms | GB/s |
| --- | --- | --- |
| 1 | 8.453 | 563.1 |
| 2 | 9.861 | 482.7 |
| 3 | 10.796 | 440.9 |
| 4 | 11.923 | 399.2 |

This is the informative result. The row slab does not change the bytes read
(the weight is decoded once and reused across the rows), so a bandwidth-bound
owner would be flat. It is not: throughput falls 29% from rows=1 to rows=4.
Per element the owner does `1 BFE + 1 ds_read + 1 mul + ROWS FMA`, so the
operation count per byte rises with the slab, and the live state
(`acc[ROWS][8] + xv[ROWS][8]`) rises with it too. A replacement owner should
therefore minimise live per-row state and keep the per-element operation count
independent of the row slab.

The two limits that are *not* binding were checked arithmetically against the
measured time and the gfx1100 machine model: the L1 wave-request rate is about
1.5% of the ~960e9/s a 96-CU part can issue, and the payload fetch is 1.25x
the payload (bytes 8..135 of each 136-byte block spans 5 sectors per u32
wave-request). Neither can explain 44% of roofline, so the residual is latency
at low occupancy.

## Next

The IQ4_XS gap is structural. The remaining lever is the T16 repack item in
`docs/UD-GFX1151-OPTIMIZE.md`: a `GGUF_IQ4_XS_T16_*` layout plus CPU packer
and inverse, then a new owner. Note that the T16 layout is a bit-lossless
*permutation* of the same bytes, so an owner reading it can keep the local32
accumulation order if that is wanted -- the existing t16 rowtile owners are
not bit-identical to the rows==1 decode owners, but that is a property of
their lane-to-k mapping, not of the layout.

`rocprofv3 --pmc` is unusable on this host (`--list-avail` enumerates no PMCs
and a `--pmc` run hangs), so no counter-level confirmation of the latency
diagnosis is available.
