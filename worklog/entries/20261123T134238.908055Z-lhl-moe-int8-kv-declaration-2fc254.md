# Declare INT8 KV contracts for the Qwen3.5/3.6 MoE GGUF plugin

## Summary

Explicit `kv_storage="int8_per_token_head"` on Qwen3.6-35B-A3B was refused with
"no registered kernel implements this backend/target/quant/KV/scale contract".
That was a missing declaration, not a missing kernel: `Qwen35MoeGGUFModel`
declared no KV contracts, while the MoE stack runs the same resident-runner
full-attention layers as the dense plugin. The INT8 split-K decode/batch shape
checks admit `(16, 2)` alongside `(24, 4)` at D256, the sequential direct INT8
prefill is geometry-general (the runner already picks it for any geometry but
24/4/256), and the append/prompt writers are head-count generic. The MoE plugin
now declares the dense plugin's INT8 contracts (uniform per-token-head FP32,
c4 batch leaf; tail-four Hadamard group32 FP16, one row per step).

## Changes

- `hipengine/models/qwen35.py`: `Qwen35MoeGGUFModel.kv_capability_declarations`
  = `_QWEN38_GGUF_KV_CAPABILITY_DECLARATIONS`.
- `tests/test_unit_qwen38_int8_kv_capability.py`: both layouts resolve to
  `admit` for the MoE plugin on gfx1100 and gfx1151 (RED without the change:
  2 failed).

## Validation

- KV/MoE unit files (35 files): 835 passed.
- Public `hipengine.LLM`, W7900, Qwen3.6-35B-A3B-UD-Q4_K_M, INT8:
  - R0207 probe (initial pages 2, `max_active_requests=2`, radix): all 7 steps ran
    (short, long, prefix reuse of 5 pages, two-request batch with growth 16->144,
    stream cancel, refill, short). Tracked bytes returned to 0 at close. Five of
    the seven outputs are byte-identical to the BF16 run; the two long
    single-prompt outputs differ.
  - Route check (32 greedy tokens): provenance `runtime_action=admit`,
    `effective_kv_storage=int8_per_token_head`, `status=unmeasured`,
    `max_packed_rows=4`; direct INT8 prefill (sequential) 60 launches, INT8
    split-K decode 980. The answers match BF16; the long prompt emits
    `<|endoftext|>` at the same point in both and differs only after it
    (`ignore_eos=True`).
  - `max_active_requests=4`: duplicate prompts in the batch produce identical
    rows; row 0 diverges from the c2 run only after EOS (char 142 vs EOS at 81).
- `kv_storage="tail4_hadamard_group32"`: admitted (`max_packed_rows=1`);
  Hadamard-group32 INT8 prefill 24 launches and decode 256. Short and both
  batch rows are byte-identical to BF16; the long row differs only after EOS
  (char 142).
- No quality measurement is claimed; the contract is unmeasured, not qualified.
