# the MMQ route is row-count invariant at the true geometry so production prefill is unaffected

## Summary

`20260928T060351` left one question open that decided the fix's scope: is the
MMQ gate/up route's row-count dependence a toy-shape artifact, or does it survive
at the real 2816/704/128-expert projection? Two cases added to
`tests/test_gpu_gemma4_expert_route_true_geometry.py` answer it.

```
tests/test_gpu_gemma4_expert_route_true_geometry.py ..   [2 passed]
```

**Both properties hold at the true geometry.**

| case | result |
| --- | --- |
| same live rows, scratch widened 1x to 8x | **bit-identical** |
| compact row 0, 128 live rows against 129 | **bit-identical** |

So the divergence the fixture shows does **not** reproduce where the model
actually runs.

## What this settles

**Production prefill is unaffected.** The MMQ route's row-count dependence is a
property of the fixture's geometry, not of the route at the shape it is used at.
The route therefore stays on by default, and no default change is warranted --
which matters, because it is the measured faster path and a change made on a toy
measurement would have traded real throughput for a defect that is not there.

**The fix is narrow.** What needs repairing is the route at the fixture's
degenerate shape, which is the shape the rest of the expert coverage runs at and
the shape the row-invariance test uses. A route that is wrong at a shape its own
coverage uses is still worth fixing, but it is a test-and-coverage defect rather
than a production one.

**A second property is confirmed intact.** The scratch's documented contract --
*"a capacity, not an identity: the caller sizes it for the widest block it will
run and then runs narrower blocks through it"* -- holds at the true geometry. The
existing envelope cases only ever ran with `capacity_factor=1`, i.e. capacity
equal to live width, so a route that read its capacity instead of its live width
would have passed all of them. The new case runs the same live rows through a
scratch eight times wider and requires bit equality. It passes, so that
mechanism is ruled out as well as the row-count one.

## Why the degenerate shape is where it shows

At the fixture's geometry the route runs at its most degenerate point in two
dimensions at once: `in_features=256` is exactly **one** Q4_K block per row
(the real row is 11 blocks at 2816), and `intermediate=64` gives a fused
gate/up width of exactly 128, i.e. **one** 128-wide column tile with no partial
block (the real 1408 is 11 tiles). The true-geometry test's own docstring names
this failure mode: *"a stride, a block count or a column tile derived from a
shape that the toy makes trivial."*

## Changes

- `tests/test_gpu_gemma4_expert_route_true_geometry.py`: two cases appended,
  `test_mmq_route_does_not_read_its_scratch_capacity` and
  `test_mmq_route_row_zero_is_invariant_under_an_appended_row`, with the
  reasoning for both in a comment above them. The second asserts that the
  activation helper still makes row 0 identical across row counts before relying
  on it, so the case fails loudly rather than passing vacuously if that helper
  changes.

## Validation

- `uv run pytest tests/test_gpu_gemma4_expert_route_true_geometry.py -k
  "capacity or appended"` on the 8060S (gfx1151): **2 passed**, exit 0.
- Both cases compare the route's own output at two widths, so no external
  reference is involved and the comparison is bit equality rather than an
  envelope.
- The capacity case uses `capacity_factor=1` against `=8` on the *same* live
  row count, which is the only way to separate capacity from live width.
