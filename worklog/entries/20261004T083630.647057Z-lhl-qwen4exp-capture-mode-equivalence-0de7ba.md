# The production capture kwargs are equivalent to the runner defaults; the loop split is not an attribution

## Summary

Two measurement-validity results, no engine change, no retained row moved.

**The canonical bench already measures the production configuration.**
`qwen4exp_canonical_ar_bench.py` calls `runner.step(current)` with the runner
defaults (`capture_logits=True`, `capture_target_hidden=True`,
`token_id_resident=False`), while the production generator passes
`_qwen4_exp_compact_step_kwargs()` for an uncontrolled greedy request
(`capture_logits=False`, `capture_target_hidden=False`,
`token_id_resident=True`). `capture_logits=True` copies the full vocabulary to
the host and takes a host `argmax`, and it forces a `device_synchronize()`
inside every decode step, so if it mattered every retained decode row would be a
pessimistic measurement of a configuration no serving client runs. A new
`--capture-mode {full,compact}` flag measures both:

| mode | p512 decode tok/s | p4096 decode tok/s | p512 prefill tok/s | p4096 prefill tok/s |
| --- | ---: | ---: | ---: | ---: |
| `full` | 20.738 | 17.220 | 264.717 | 268.668 |
| `compact` | 20.755 | 17.173 | 264.797 | 271.105 |
| delta | +0.08% | -0.27% | +0.03% | +0.91% |

All four deltas are at or inside the run-to-run spread. **The retained decode
and prefill rows already describe the production path and need no
re-baselining.** This closes the "is the headline decode number a harness
artifact" worry raised by the capture-config difference.

**The host/device loop split is a loop split, not an attribution.**
`runner.step()` ends with a blocking device-to-host copy of the argmax result
(`_finish_lm_head` -> `copy_device_to_host`), so the "host enqueue" window
contains the device wait and the trailing drain is zero by construction.
`decode_device_drain_ms_per_step` is 0.000 in all four rows above, in **both**
capture modes, including `compact` where no explicit per-step synchronize
exists at all. A zero drain therefore does not mean the step is host-bound.

**This withdraws the reading in `20261004T073816`** that a zero
`device_drain_ms` proves the GPU "completed all 128 queued steps before the host
finished enqueuing them". That entry's measurement stands; its interpretation
does not. The same defect applies to
`scripts/qwen4exp_decode_host_bound_probe.py`, whose `host_bound: true` verdict
and 79.1 / 80.1 / 107.4 ms-per-step "host enqueue" figures are per-step *wall*
with the blocking readback inside them, not host cost. See
`20261004T084500` (companion) for the counter-rotated measurement that replaces
them.

## Changes

- `scripts/qwen4exp_canonical_ar_bench.py`: new `--capture-mode {full,compact}`
  on the `hipengine` subcommand. `compact` imports the generator's own
  `_qwen4_exp_compact_prefill_kwargs` / `_qwen4_exp_compact_step_kwargs` rather
  than restating them, so the bench measures exactly what the generator passes.
  The chosen mode and kwargs are recorded in the artifact protocol block.
  `_hipengine_case_sample` gains `prefill_kwargs` / `step_kwargs`.
- `scripts/qwen4exp_canonical_ar_bench.py`: `_hipengine_case_sample` also splits
  the prefill and decode loops at their trailing synchronize and reports
  `{prefill,decode}_{host_enqueue,device_drain}_ms`, with the `_sample_group_summary`
  rollup. The code comment states explicitly that the split cannot attribute the
  two windows while `step()` blocks internally.
- `tests/test_unit_qwen4exp_canonical_ar_bench.py`: `--capture-mode` default and
  parsing, `_capture_kwargs` equivalence with the generator helpers, and the
  split rollup (present only for rows that carry it, so llama.cpp rows and older
  artifacts are unaffected).
- Artifact and protocol note:
  `benchmarks/results/2026-10-04-qwen4exp-decode-capture-mode/`.

## Validation

Hardware: AMD Radeon 8060S / `gfx1151` (Strix Halo Framework host), ROCm
7.15.26333, `HIPENGINE_HIP_ARCH=gfx1151`. Model: Qwen3.8-Flash-Next
`unsloth-...-UD-Q4_K_XL`, production profile, BF16 KV, greedy AR, chunk 1024,
warm PLE, one case per process, one warmup and one measured repetition.

- Command: `uv run python scripts/qwen4exp_canonical_ar_bench.py hipengine
  --model-root <UD-Q4_K_XL> --case-id <case> --prefill-chunk-size 1024
  --execution-profile production --capture-mode <full|compact> --ple-cache-mode
  warm --ple-telemetry --warmups 1 --repetitions 1 --compiler-version-file
  /tmp/hipengine-hipcc-version.txt --require-cached-build --output <out>.json`.
- `uv run pytest tests/test_unit_qwen4exp_canonical_ar_bench.py -q`: **15
  passed** (3 new).
- Cross-check: the `full` legs reproduce the retained rows (20.738 vs 21.01 at
  p512, 17.220 vs 17.40 at p4096, both inside the documented thermal spread), so
  the new instrumentation did not perturb the protocol.
