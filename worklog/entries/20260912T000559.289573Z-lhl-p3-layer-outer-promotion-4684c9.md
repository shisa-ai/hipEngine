# Layer-outer packed prefill promoted to the default

## Summary

`HIPENGINE_GGUF_PACKED_LAYER_OUTER` was default OFF pending the P3 packet gates.
Those gates closed during this session (`dfd31004d`, `a340d93c1`, `7c56b13af`),
so the promotion was re-decided on measured evidence and the flag is now default
ON. `=0` is the explicit rollback to the corrected chunk-outer executor.

Two things change with the default, and both were measured:

1. The packed AR prefill executes layer-outer, sharing one BF16 oracle pair per
   session instead of one per INT8-retained full-attention layer.
2. The resumable (bounded-yield) service prefill becomes reachable for leased
   server requests (`hipengine/generation/qwen35_gguf.py` reads the same flag).

## Measured

Same host (W7900 GPU0, gfx1100, 27B `Q4_K_M`, INT8 KV, `GPU_MAX_HW_QUEUES=1`),
`scripts/gguf_prefill_route_ab.py`, flag off vs on, 8 decode tokens,
`--assert-entry-agreement`:

| Prompt rows | chunk-outer tok/s | layer-outer tok/s | ratio | tracked peak delta | IDs | layer-outer `executor_mode` |
| ---: | ---: | ---: | ---: | ---: | --- | --- |
| 1,024 | 761.49 | 750.17 | 1.0151 | 0.000 GiB | identical | `None` (single chunk) |
| 2,048 | 743.17 | 740.60 | 1.0035 | **-0.438 GiB** | identical | `layer_outer_packed` |
| 4,096 | 724.83 | 724.86 | 1.0000 | **-0.438 GiB** | identical | `layer_outer_packed` |
| 8,192 | 684.78 | 689.19 | 0.9936 | **-0.438 GiB** | identical | `layer_outer_packed` |

The 1,024-row pair is the useful control: the layer-outer executor does not
engage at a single chunk, so both flag settings ran identical code and their
1.5% spread **is** the protocol's noise floor. At every length where the
executor actually differs the ratio is 1.0035/1.0000/0.9936, i.e. inside that
floor, so this is wall parity and not a speed claim in either direction. The
0.438 GiB peak reduction is consistent across all three multi-chunk lengths and
zero at the single-chunk length, which is what the shared-oracle mechanism
predicts.

Server route, `scripts/gguf_server_cwidth_probe.py --widths 1 --prompt-rows 2048
--max-tokens 64 --no-serial-control`, flag off vs on:

| | off | on |
| --- | --- | --- |
| `fallback_reasons_delta` | `incremental_prefill_unsupported` 1.0, `int8_direct_full_prompt_prefill` 1.0 | `{}` (zero fallbacks) |
| `prefill_executor_modes_delta` | `{"None": 0.0}` | `{"layer_outer_packed": 1.0}` |
| prompt / completion tokens | 2,048 / 64 | 2,048 / 64 |
| wall | 4.952 s | 5.018 s |
| throughput | 426.515 tok/s | 420.902 tok/s (-1.32%) |

The executor mode is now a *measured* field rather than an inference: the probe
previously recorded only route and fallback counters, so a run could have claimed
the layer-outer route without showing it. `prefill_executor_modes_delta` reads
`hipengine_resident_prefill_executor_mode_total`, which the server already
exported.

## Why promotion rather than another gate

Exactness is established by the P6f `layer_boundary_state` gate: the committed
per-layer direct INT8 K/V, its scales, and the linear conv/recurrent state
fingerprint identically to the one-shot reference at a full and a ragged shape,
under both the single-plane hidden alias and its two-plane control. The wall A/B
adds identical generated IDs at 1,024/2,048/4,096/8,192 rows. The improvement is
a memory reduction with wall parity, which is non-regressive, so the repo rule
(keep and promote measured, exact, non-regressive improvements unless a concrete
blocker exists) applies. No blocker remains: the gates are closed, the server
route engages cleanly with zero fallbacks, and the rollback is registered.

## Honest limits

- One run per A/B point and one per server arm. The noise floor is *estimated*
  from the single identical-code pair (1,024 rows, 1.5%), not from repeats, so
  "parity within noise" means "inside a single observed spread of the same code",
  not a confidence interval. The 8,192-row point being 0.6% faster is not claimed
  as a win for the same reason.
- The 1.5% floor is measured at 1,024 rows only; the spread at 8,192 rows is not
  separately established.
- The A/B compares prefill tok/s with 8 decode tokens, and the server check is
  width 1 at 2,048 rows only. No concurrent or long-context server load was
  re-measured with the new default, and the resumable path's scheduler interaction
  under load was not re-measured here (the P6e/P6f proofs cover its correctness and
  bounded decode gap).
- `tracked_peak_gib` is the runtime's own tracked peak, not a device-wide VRAM
  measurement.
- The oracle saving is 0.438 GiB on this model and geometry; other geometries
  with a different layer count or KV width were not measured.
