# Why dense_wide256 never executes: the WMMA route owns the same layer scope

## Summary

`dense_wide256_f32_f32_out` never runs because the f16 WMMA dense Q8_0 prefill
route claims the identical layer scope earlier in the same dispatch chain and
changes the dispatch ABI on its way through.

In `launch_gguf_linear` the chain order is positional:

- `hipengine/runtime/gguf_linear.py:3582` — `_wmma_prefill_dispatch`
- `hipengine/runtime/gguf_linear.py:3686` — `_q8_dense_wide_dispatch`

When the WMMA route fires it returns `GGUFLinearDispatch(..., "wmma_raw")`
(`gguf_linear.py:8117-8128`): variant `wmma_prefill_f32_f32_out` and **abi
`wmma_raw`, not `raw`**. The wide selector's first condition is
`dispatch.abi != "raw"` (`gguf_linear.py:2925`), so it returns the parent
immediately — before the `HIPENGINE_DW_DEBUG` probe, before `is_registered`,
and before the "not registered" `RuntimeWarning`. That is precisely the
observed symptom: the route is silent and the warning never fires.

The collision was introduced by this entry's own `base_commit`. `04f1dde42`
bound the production default `HIPENGINE_QWEN4_EXP_Q8_WMMA_LAYERS` to
`PRODUCTION_Q8_WMMA_PREFILL_LAYERS = tuple(range(16, 48))`
(`hipengine/generation/qwen4_exp_profiles.py:731`), which the runner converts
into `wmma_prefill_session(True)` plus a `gguf_q8_0`-and-layer weight filter
(`hipengine/runtime/qwen4_exp_runner.py:7569-7592`). That is the **same 16-47
scope** the wide route was being gated at.

The result is zero overlap, so the kernel can never be reached:

| Layers | Owner | Why the wide route loses |
| --- | --- | --- |
| 0-15 | exact coltile chain | excluded by the wide route's own `_LAYERS` scope |
| 16-47 | `wmma_prefill_f32_f32_out` | WMMA runs first and sets abi `wmma_raw` |

The selector logic, the layer-scope parser, and kernel registration are **not**
the defect. Registration is downstream of the gate that rejects, which is why
registering the tile family changed nothing.

## Validation

Verified by executing the real dispatch chain in-process against a stub weight,
with `hipengine.runtime.gguf_linear.resolve` replaced by a sentinel raise and
every `_*_dispatch` helper wrapped in a tracer. CPU only: no GPU allocation, no
HIP runtime, no kernel launch. Sessions were armed exactly as
`_prefill_chunked_impl` arms them (`raw_k_prefill_rowbatch_session(32)`,
`raw_k_prefill_variant_session("coltile8_wave_scale")`, `wmma_prefill_session`,
`wmma_prefill_weight_filter_session`), shape `rows=512, K=2560, N=6144`,
backend `hip_gfx1151`.

```
WMMA 16-47 + dense_wide 16-47, layer 20
  _wmma_prefill_dispatch: raw/prefill_f32_f32_out -> wmma_raw/wmma_prefill_f32_f32_out
  FINAL -> gguf_q8_0 / wmma_prefill_f32_f32_out          # wide route silent

WMMA off + dense_wide 16-47, layer 20
  _raw_k_prefill_rowbatch_dispatch: -> raw/coltile8_rowbatch4_f32_f32_out
  _raw_k_wave_scale_dispatch:       -> raw/coltile8_rowbatch4_wave_scale_f32_f32_out
  _q8_dense_wide_dispatch:          -> raw/dense_wide256_f32_f32_out
  FINAL -> gguf_q8_0 / dense_wide256_f32_f32_out         # selector is correct

WMMA 16-47 or WMMA off, dense_wide 16-47, layer 4
  FINAL -> gguf_q8_0 / coltile8_rowbatch4_wave_scale_f32_f32_out
```

The middle arm is the positive control: with the WMMA selector cleared, the wide
route is selected on an unmodified tree. No performance claim is made here; this
is a routing result only.

## Two evidence problems found alongside the root cause

**1. The launch census cannot see either route.**
`launch_census.record_launch` is called only from
`hipengine/kernels/hip_gfx1100/quant/gguf_k_gemv.py`, the single quant module
that imports `launch_census`. `wmma_prefill_*` is exported from
`gguf_q8_0_prefill.py` and `dense_wide256_*` from `gguf_q8_0_dense_wide.py`;
neither is instrumented. So `04f1dde42`'s recorded follow-up — "2144 coltile
launches and zero `wmma_prefill`" — cannot distinguish *did not run* from *not
counted*, and the same instrument would fail to confirm a wide-route launch.
Any future attribution for these two families needs `rocprofv3 --kernel-trace`,
not the linear census.

**2. Every census artifact reports only layers 0-15.**
Across `dw-census.json`, `dw-census2.json`, `default-census.json` and
`dw-census3.json` the census holds 137 distinct roles, all
`linear:layers.{0..15}.*` plus three `linear:root.*`, with no `<unattributed>`
row and a uniform x16 multiplier (8 prefill chunks x 2 repetitions). A GGUF
header scan of the model shows ggml type 8 (Q8_0) `hc_attn_down`,
`hc_ffn_down`, `hc_attn_up`, `hc_ffn_up` and `ffn_{gate,up,down}_shexp` present
at layers **0-47**, and `plan_qwen4_exp_residency` assigns layout purely from
the tensor via `_qwen4_exp_runtime_layout`, with no layer-index dependence. So
layers 16-47 should carry the same raw Q8_0 projections and do not appear.
Unresolved. Until it is explained, no census-derived statement about layers
16-47 should be relied on — including any claim that the wide route did or did
not run there.
