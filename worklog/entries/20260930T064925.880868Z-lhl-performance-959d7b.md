# D2 sliding-layer flash-decoding (split-K) for Gemma decode

## Summary

Punchlist row D2 (sliding-layer flash-decoding), profiled then designed.
Profile-first, XTX lane, `rocprofv3 --kernel-trace` via
`scripts/gemma4_family_census.py drive --prompt 1024 --decode 64` (warm,
`HIPENGINE_REQUIRE_CACHED_BUILD=1`): decode busy **14.175 ms/tok**, of which

| kernel | ms/tok | calls/step |
| --- | --- | --- |
| `gguf_k_pack8_prefill_out` (dense) | 3.827 | 126 |
| `gemma4_attention_decode_dimension` (phase 2, V-sum) | 2.909 | 30 |
| `gemma4_attention_decode_class` (phase 1, softmax) | 1.501 | 30 |
| `q5_1_selected_gemv` (MoE down) | 1.495 | 29 |
| `qk_t16_selected_direct_gemv` (MoE gate_up) | 1.048 | 29 |

`attn.sliding` (two-phase pair on the 25 hd256 layers) = **3.658 ms/tok =
25.8% of decode busy**, the largest open family; `attn.global` = 0.751.
Artifact geometry: 30 layers, q=16; sliding kv=8 hd256 window 1024 (25),
global kv=2 hd512 (5). Sliding's GQA ratio is exactly the row's
"2 query heads packed per KV head".

Cause of the phase-2 cost, from the source: `gemma4_decode_split_launch`
grids phase 2 at `head_grid * ceil(head_dim/32)` blocks of 32 threads —
one output dimension per thread walking all keys in a dependent chain —
128 wave32 blocks against 96 CUs x 4 SIMDs, ~33% wave occupancy, while
phase 1 sits at 16 head blocks. Both passes re-read KV the other pass
already touched, through a 65 KB+ workspace round trip.

## Design (frozen before implementation)

Two new kernels in `gemma4_attention.hip`, production-reassociating:

1. `gemma4_attention_decode_flash_kernel<scalar_t>` — grid
   `tokens x num_kv_heads x S`, 128 threads. Each block owns one KV head's
   q-pair (kQPerKV = num_heads/num_kv_heads = 2 on sliding) and a contiguous
   key slice. Phase A: class-style warp-tree QK dots (kOwn=8, kHalves=1,
   `gemma4_warp_tree`), K loaded once per key and dotted against both q rows,
   slice logits to LDS, per-row slice max. Phase B: `expf(logit - m_slice)`
   (per row), slice denominator, and per-lane V accumulation — lane owns
   dims `2*lane, 2*lane+1` for *both* rows, one `gemma4_load_v<2>` pair per
   key applied to both accumulators, prefetch pipeline depth 2. Writes
   partials `(m, l, o[2][head_dim])` per (head, slice).
2. `gemma4_attention_decode_flash_combine_kernel<scalar_t>` — grid
   `tokens x num_heads`, 128 threads, 2 dims/lane. Sequential flash merge
   in ascending slice order: `alpha = expf(M - M_new)`,
   `beta = expf(m_s - M_new)`, dead slices (`l_s == 0`) skipped before any
   exponent, `L == 0` prefix adopted directly; `out = O / L`, and NaN when
   `L == 0` to propagate the incumbent's all-masked-row NaN semantics
   (`test_all_masked_row_matches`).

Workspace `(tokens * num_heads * S * (2 + head_dim)) * 4` bytes behind a new
`hipengine_gemma4_decode_flash_workspace_bytes` symbol; Python allocates
`max(split, flash)` so the split fallback is always sized.

Dispatch: negative `split_slices` is the flash request (Python passes `-S`).
The host wrapper flashes only when `head_dim == 256`, workspace non-null and
`S >= 2`, else falls through to the incumbent split/class/block chain — the
strict, bit-exact-to-block path that doubles as flash's unfused fallback.
Slice formula lives in Python as the single source of truth:
`S = clamp(ceil(keys/32), 4, 64)` (keys >= 1024 is the only admitted range,
so S is 32 at 1024, 64 at 4096+; LDS logits bound 34 KB at context cap).
Admission is capability-only: `head_dim == 256`, `tokens == 1`,
`num_heads % num_kv_heads == 0 and ratio == 2`, workspace fits. No identity
keys. `decode_selection` gains `3 = flash`.

Why not make it bit-exact: the per-slice max changes exp arguments, so
weights differ by an exact rescale factor applied at combine — reassociation
only, which `docs/EXECUTION-PROFILES.md` allows on the production route and
the D2 row explicitly sanctions. Contract: agreement to float precision vs
the single kernel in the unit battery, production KL/top-1 bars at
`scripts/gemma4_teacher_forced_gate.py gate`.

## Changes

- `gemma4_attention.hip`: `gemma4_attention_decode_flash_kernel` (grid
  `tokens*num_kv*slices`, 128 threads), `..._flash_combine_kernel` (grid
  `tokens*num_heads`), the extern-C wrapper `gemma4_decode_flash_launch`
  (shape gate, shared sizing, two launches), `..._flash_workspace_bytes`,
  and the `launch_gemma4_attention_decode` negative-slices request routing
  `split_slices < 0` into the flash arm with the incumbent chain as the
  strict fallthrough.
- `gemma4_attention.py`: `flash_slices` / `flash_admits` /
  `flash_workspace_bytes` (Python is the slice-formula source of truth),
  `decode_selection` docs for `3 = flash`, and `_launch_prefill` requests
  `-flash_slices(keys)` when `slices > 1` and the shape admits.
- `gemma4_decode_graph.py`: bucket scratch pre-touch sizes
  `max(split, flash)` workspace when the launched route may be flash.
- `tests/test_gpu_gemma4_flash_decode.py` (32 tests): capability surface,
  flash selection for the admitted geometry, float-precision agreement vs
  the single kernel across f32/bf16 x keep/holes/window/none masks x
  keys 1024/2055/4096, all-masked NaN parity, poisoned-workspace immunity,
  non-admitted geometries keeping incumbent routing, and the production
  wrapper (`gemma4_attention_prefill_f32`, the registered entry) selecting
  flash after a real launch.
- `scripts/gemma4_teacher_forced_gate.py`: route observation counts
  flash (selection 3) into the split family, so the gate accepts the
  shipped route it is judging.

Design correction against the frozen plan: phase B does **not** publish
per-lane accumulators through a cross-warp staging array. Two defects
killed that shape, both found by golden-reference localization:

1. `gemma4_warp_tree` folds the eight per-lane partials into element 0 on
   lane 0 only (the class kernel's own contract); every lane storing
   `reduced` raced partial reductions into the same shared address.
2. With `d0 = tid*2` and warps splitting keys, warp w's threads own dims
   `[w*32*2, ...)`, so no dim range is covered by more than one warp -- no
   cross-warp sum can reassemble a dimension, and the natural
   `warp*128+tid` slot index double-counts the warp.

The shipped phase B instead uses `gemma4_decode_pass3`'s partition: every
thread owns dims `(2*tid, 2*tid+1)` and walks the whole slice itself, so
each accumulator is complete as written -- no staging, no cross-warp sum.
A weight pass overwrites the LDS logits in place with
`exp(logit - row_max)` (zero for masked keys), so each (q, key)
exponent is computed once per block instead of once per dimension.
Shared shrank to `kQ*warps + kQ*head_dim + kQ*slice_max` floats (584 at
the 1024 threshold).
