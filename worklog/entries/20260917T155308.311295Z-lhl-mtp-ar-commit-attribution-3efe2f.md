# Count autoregressive output at the decode that emits it

## Summary

Autoregressive output of a speculative request is now attributed by the decode
that emits the token, not by the plan that selected autoregressive decoding. The
review of the output-accounting unit found that a plan can be prepared more than
once for the same row: a mixed group whose speculative subset is retried prepares
the same request twice, so one emitted token could be counted twice. Counting at
preparation also attributed a token to a plan whose decode never emitted it - on
the real server the final autoregressive step of the 945-token arm was counted by
its plan while its token was emitted by the request finalization path.

The plan's reason now travels with the row to the emission: the resident loop
records it when an AR-only plan is prepared, the decode that emits the token
reports it back through `note_speculative_ar_commit`, and the adapter records one
step per emitted token. A pending reason that no decode consumes is dropped when
the request is reclaimed, so it cannot attribute a later token.

On the real `gfx1151` server the emitted sequence is unchanged - same 77 MTP /
51 autoregressive split of 128 tokens, same `first_fallback_position 78`, same
690 characters, same 128 exact token IDs - and the plan-attributed count moves
from 51 to 50: the one step whose plan never emitted is now the post-plan
remainder of `ar_output_tokens` instead of a plan-attributed step. The reason
histogram still sums exactly to `ar_output_tokens_in_cycles`, so every
plan-attributed step still names the reason that selected it.

## Changes

- `hipengine/generation/engine_loop.py`: `_pending_ar_reasons` carries each
  AR-only plan's per-row reason to the decode; `_attribute_autoregressive_commits`
  calls the runner's commit hook once per emitted token and pops the reason, so a
  second preparation for the same row replaces the entry instead of adding a
  second attribution; `_reclaim_runner_state` drops a pending reason that no
  decode consumed.
- `hipengine/generation/qwen35_gguf_mtp2.py`: `prepare_k0` no longer records an
  autoregressive step (it still performs the transitional K0 catch-up);
  `note_speculative_ar_commit` records one step with the plan reason and the
  output index the token just occupied. The hook does not require live
  speculative intent, because the token that reaches `max_new_tokens` retires the
  request inside the decode; it requires a row that still owns a lease and a
  slot, and it skips a request id the owner does not know.
- `hipengine/generation/qwen35_gguf.py`, `hipengine/generation/qwen35_paro.py`:
  the runner forwards `note_speculative_ar_commit` to its resolved adapter. The
  loop observes the runner, so the adapter method alone was unreachable - the
  first live run after the change reported zero plan-attributed steps, which is
  what caught it.
- `scripts/gguf_mtp_api_gate.py`: a `used: true` row now also fails when
  `ar_output_tokens_in_cycles` exceeds `ar_output_tokens` or is missing. A double
  count inflates the plan-attributed count above the autoregressive output, so
  this is the mechanical gate for the defect class rather than for one instance
  of it.
- Tests: `tests/test_unit_qwen35_gguf_mtp2_seam.py` (preparation alone
  attributes nothing; the decode attributes one step; the step survives the
  decode that retires the request; a released or unknown row is skipped),
  `tests/test_unit_specdec2_engine_loop.py` (a retried plan replaces its pending
  reason and one emitted token is attributed once; commits never exceed emitting
  decodes; reclaim drops an unconsumed reason; the runner-forwarding tests live
  in the seam file), `tests/test_unit_gguf_mtp_api_gate.py` (the new gate).

The AR-reference arm of the previous unit is unaffected: a request without
speculative intent still publishes no accounting block at all.

Real server, `gfx1151`, `Qwen3.8-27B-Q4_K_M` (17,106,775,008 B),
`--max-context-tokens 16384 --kv-storage bf16`, **no speculative flags** (automatic
MTP resolving to depth 3), greedy 128 outputs, `enable_thinking=false`. Same-host
A/B, one server per code state, the same 945-token prompt, exact command
`/tmp/accounting_probe.py <url> qwen3.8-27b-q4km <out> <label> 1024 false`:

| Code state | MTP / AR | In-cycles | Fallback reasons | First fallback | Chars |
| --- | --- | ---: | --- | ---: | ---: |
| HEAD `0a184f55d` (count at plan) | 77 / 51 | 51 | `no_provider 1`, `context_bucket_miss 49`, `output_room_miss 1` | 78 | 690 |
| this unit (count at emission) | 77 / 51 | 50 | `no_provider 1`, `context_bucket_miss 49` | 78 | 690 |

Both runs emitted 128 exact token IDs, committed 23 cycles (66 drafts, 54
accepted, depth histogram `{1: 1, 2: 1, 3: 21}`) and reported
`reconciled: true`; the plan-attributed count equals the fallback reason count in
both. The one-token difference is the final autoregressive step: the old code
counted it when its plan was prepared, the new code counts the token where it was
emitted - by the request finalization path, after the plan - and reports it in
the `ar_output_tokens` remainder.

Five arms on the final code, all with `passed: true` under the corrected
contract (`mtp + ar == completion`, `ar_in_cycles <= ar`, reason counts sum to
`ar_in_cycles`, exact IDs match the completion count), artifact
`benchmarks/results/2026-09-17-gfx1151-qwen38-mtp-ar-commit-attribution.json`:

| Arm | Shape | MTP / AR | In-cycles | First fallback | Cycles / accepted |
| --- | --- | --- | ---: | ---: | --- |
| A blocking | 945 prompt, 128 out | 77 / 51 | 50 | 78 | 23 / 54 |
| B streaming | same request | 77 / 51 | 50 | 78 | 23 / 54 |
| C blocking | 3,530 prompt, 128 out (refused) | 0 / 128 | 127 | 0 | 0 / 0 |
| D concurrent long | 945 prompt, 128 out | 77 / 51 | 50 | 78 | 23 / 54 |
| D concurrent short | 140 prompt, 128 out | 126 / 2 | 1 | null | 64 / 62 |

Arm D is the mixed-group case the review described: both requests are decoded in
one group, the long one falls back mid-generation while the short one keeps
speculating, and each request's counts reconcile independently. Before the
change, a plan prepared for the same row twice could add a second attribution to
that row; the concurrent arm now reports `ar_output_tokens_in_cycles` at or below
its autoregressive output for both requests.

Diagnosis method: temporary `HIPENGINE_MTP2_TRACE_ACCOUNTING` prints at plan
preparation, at attribution, at the adapter commit, and at reclaim (removed
before this commit). They showed the final arm's last AR-only plan attributed one
step at preparation while the decode that followed emitted the previous tick's
token, and that the runner - not the adapter - is what the loop observes.
