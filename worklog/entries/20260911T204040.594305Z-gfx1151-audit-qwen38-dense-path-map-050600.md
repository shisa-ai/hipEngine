# Qwen3.8-27B dense code path map: plugin, runtime, quant owners, dispatch, backend admission

## Summary

End-to-end map of the Qwen3.8-27B dense GGUF path, plus a resolved answer to the
"which parts are gfx1100-only" question. The headline result is negative and
useful: **the 80 hardcoded `KernelKey("hip_gfx1100", ...)` module constants in
`qwen35_gguf_runner.py` are not gfx1100 pins.** They are nominal source markers
whose `backend` field is deliberately discarded at resolution, and that is now
verified both statically and at runtime rather than inferred from reading.

The one genuine backend pin on a Qwen3.8 path is PARO's
`_PAGED_KV_REGISTRY_BACKEND` (already recorded in `docs/REFACTOR.md`). There is
also a mirror-image gap worth naming: the Qwen3.8 execution-profile plans are
registered for **gfx1151 only**.

## Changes

- `docs/KERNELS.md`: new "Qwen3.8-27B dense GGUF route map" subsection under the
  GGUF/Qwen/Laguna path, giving the plugin → factory → materialize → dispatch →
  registry chain and the default route in one place.
- No source change. This is a review unit; every claim below is a read or a
  runtime resolution check against commit `dbcf80b47`.

## Validation

Static: all 47 module-level `KernelKey("hip_gfx1100", ...)` constants plus 10
container dicts in `qwen35_gguf_runner.py` were extracted by name, and every
usage line of every name was checked for a `.backend` read. Result: **0 usages
read `.backend` off a hardcoded constant.** Every consumer substitutes the
active backend, for example:

```python
def _resolve(key: KernelKey):
    return resolve(backend=backend, layer=key.layer, quant=key.quant,
                   variant=key.variant, missing="none")
```

Runtime, on the gfx1151 host, resolving the dense GDN keys that appear in the
hardcoded list:

| layer / quant / variant | `hip_gfx1100` resolves to | `hip_gfx1151` resolves to |
| --- | --- | --- |
| `gdn_recurrent_rmsnorm_gate / gguf_qwen35 / bf16_indexed_singleton` | `qwen35_gdn_recurrent_rmsnorm_gate_indexed_lowp_bf16` | `qwen35_gdn_recurrent_rmsnorm_gate_indexed_shared_statecache24_lowp_bf16` |
| `... / bf16_indexed_singleton_fp16state` | `..._lowp_bf16_fp16state` | `..._shared_statecache24_lowp_bf16_fp16state` |

The two backends return different bodies, so the hardcoded literal is provably
not selecting the gfx1100 kernel on gfx1151.

Hardcoded-constant breakdown by layer (80 total): `gdn_prefill_recurrent` 29,
`moe_linear` 27, `linear_attn_prefill_prepare` 5, `gdn_recurrent_rmsnorm_gate` 4,
`gdn_chain_recurrent_rmsnorm_gate` 2, and 13 singletons. Dense-path share is 46
(all quant `gguf_qwen35`); the rest is the MoE path.

Graph-replay claim re-verified (this was asserted in the previous unit's
artifact, so it was checked rather than trusted): the measured gfx1151 runs
record `requested_graph_replay_decode: True`, `effective_graph_replay_decode:
True`, `decode_graph_disabled_reason: None`, and
`decode_graph_transport_provenance = {transport: hipgraph, backend:
hip_gfx1151, gfx_arch: gfx1151, replayed_steps: 128}`. The discarded warmup run
records `False` for the same fields, which is the documented eager warmup.

## The map

**1. Model plugin.** `hipengine/models/qwen35.py` → `Qwen35GGUFModel`,
registered as `QWEN35_GGUF`. `name = "qwen3_5_gguf"`,
`architectures = ("qwen35",)`, `default_quant = "gguf_q4_k_m"`,
`default_backend = "auto"`. There is no separate Qwen3.8 plugin: `qwen35` is the
shared dense architecture string for Qwen3.5/3.6/3.8, and Qwen3.8-27B is served
through this plugin. Siblings are `Qwen35MoeGGUFModel` (`qwen35moe`,
Qwen3.6-35B-A3B) and `Qwen35ParoMoeModel` (PARO W4A16). The plugin owns
artifact-scoped capability evidence: `kv_capability_evidence` (INT8 K/V) and
`speculative_mtp_serving_evidence` (MTP), read through `resolve_kv_capability`
and `resolve_speculative_mtp_serving_plan`.

**2. Backend admission.** `hipengine/kernels/backends.py`.
`HIP_BACKEND_TARGET_ARCH = {hip_gfx1100: gfx1100, hip_gfx1151: gfx1151}`.
`select_backend` precedence is explicit argument → `HIPENGINE_BACKEND` → detected
arch via `amdgpu-arch` / `rocm_agent_enumerator` → `cpu_reference` fallback with
a warning. `configure_hip_process_environment` applies backend-local HIP defaults
before `libamdhip64` loads: gfx1100 gets `HSA_SCRATCH_SINGLE_LIMIT=8388608`,
gfx1151 gets `GPU_MAX_HW_QUEUES=2`; explicit user values are never overwritten.
Per-backend knobs are read with `backend_package_capability(backend, NAME,
default)`, which imports `hipengine.kernels.<backend>` and reads a module-level
constant — no dispatch branches.

**3. Generator factory.** `hipengine/generation/registry.py`, key
`(model, backend, quant, mode="greedy_one_token")`, exact match, raises
`MissingGeneratorError` otherwise. `qwen35_gguf.py` builds
`_GGUF_GENERATOR_FACTORIES_BY_BACKEND` with an entry for **both** backends plus
`_GGUF_GENERATOR_FACTORY_OVERRIDES` for `(backend, quant)`, and registers them for
`qwen3_5_gguf` and `qwen3_5_moe_gguf` across six quants. This layer is symmetric
and is not a gfx1100-only surface.

**4. Execution profile (optional).** `LLM.execution_profile` defaults to `None`,
and `_resolve_execution_profile` returns `None` in that case, so **the default
route is the unprofiled legacy path** with no variant manifest and no profile
binder env. When a profile is requested, `resolve_runtime_profile` keys on
`RuntimeProfileKey(model, backend, quant, profile)` and raises
`MissingRuntimeProfilePlanError` if no plan is registered. Registered plans:
`qwen36_dense_gguf_gfx1100`, `qwen36_moe_gguf_gfx1100`, `qwen36_gguf_gfx1151`,
`qwen38_gguf_gfx1151`, `qwen4_exp_gfx1151`.

**5. Weight materialization and quant owners.**
`hipengine/loading/qwen35_gguf_materialize.py`. `HIPENGINE_GGUF_DECODE_REPACK`
defaults to `"1"`, and `use_decode_repack = requested and not
contract_q3_f32_linear`, so raw-IQ models (IQ2_XS/IQ3_XXS/IQ4_XS) skip the T16
repack and keep compressed rank-3 layouts. For Q4_K_M the decode layout is
`LAYOUT_GGUF_Q4_K_T16 = "gguf_q4_k_t16_v1"`, which is also the registry quant
string. So the three quant identities on this path are: file quant
`gguf_q4_k_m`, decode layout/registry quant `gguf_q4_k_t16_v1` for the dense
linears, and `gguf_qwen35` for the GDN / linear-attention / state families.

**6. Dense linear dispatch.** `hipengine/runtime/gguf_linear.py`,
`resolve_gguf_linear_dispatch(weight, activation_dtype, output_dtype, backend,
rows)`. The table key is `(weight.spec.layout, activation_dtype, output_dtype)`
and yields a template dispatch; `quant` is taken from the weight itself when the
template says `"<from-weight>"`. On T16 layouts with `rows > 1` the variant is
forced to `t16_wmma_prefill_bf16_bf16_out`; otherwise `_variant_for_rows(...)`
picks the row width. The emitted `KernelKey` uses `_weight_backend(weight,
backend=backend)` — the **resolved** backend. Results are memoized in
`_DISPATCH_RESOLVE_CACHE` keyed with the registry generation.

**7. Kernel resolution.** `hipengine/kernels/registry.py`, `resolve(backend,
layer, quant, variant, missing)`. Fallback order is exact key → same without
variant → `fp16` quant on the same backend → `cpu_reference`. There is
deliberately **no cross-HIP-backend fallback**, which is why
`hipengine/kernels/hip_gfx1151/__init__.py` must alias the gfx1100 key space
explicitly (1307 shared, 105 gfx1100-only, 241 declared exclusions, 18 body
overrides).

**8. Default route.** Prefill is bulk WMMA
(`use_bulk_prefill`, `bulk_prefill_attention_mode=bulk`, `use_wmma_prefill`
defaulted True by `_resident_session_wmma_prefill_default()`). Decode passes
`use_gemv_decode=True` literally at both shipping call sites and is **eager by
default**: `HIPENGINE_GGUF_DECODE_GRAPH` exists, but the resident GGUF path is
eager because the retired decode-graph path corrupted recurrent state on
relaunch. Explicitly requesting graph replay does engage it and does pass the
correctness gates (verified above). Measured 512/128 on gfx1151 at this commit:
380.366 tok/s prefill, 12.213 tok/s AR decode.

## Findings

1. **Not a pin (verified):** the 80 `KernelKey("hip_gfx1100", ...)` constants in
   `qwen35_gguf_runner.py`. Their `backend` field is ignored at every use site and
   the active backend is substituted. Recorded because the literal reads like a
   pin and will keep attracting false alarms.
2. **A real pin (already tracked):** `qwen35_paro.py:213`
   `_PAGED_KV_REGISTRY_BACKEND = "hip_gfx1100"`, used at lines 2122, 2259, 3778,
   and 4212. Unlike finding 1, this value *is* the resolution backend, so on
   gfx1151 PARO cannot reach the gfx1151 override for
   `paged_attn_decode / w4_paro / bf16_context_batch_c1_exact_spans`. See the
   `docs/REFACTOR.md` entry.
3. **Mirror-image gap:** `qwen38_gguf_profiles.py` pins
   `QWEN38_GGUF_BACKEND = "hip_gfx1151"`, so the Qwen3.8 strict/production
   variant plans exist only for gfx1151. Because the profile key is
   `(model="qwen3_5_gguf", backend, quant)`, a profile request for a Qwen3.8-27B
   file on gfx1100 resolves to the **Qwen3.6** dense gfx1100 plan — the key
   cannot distinguish Qwen3.6-27B from Qwen3.8-27B. This is fail-safe (the plan
   is real and gate-backed, and the default route needs no plan at all), but it
   means "Qwen3.8-27B under an explicit profile on gfx1100" is not a supported,
   evidenced configuration.
4. **Benign fallback:** `qwen35_gguf.py:1136` defaults `target_arch` to
   `hip_gfx1100` only for `__new__`-bypass test fixtures; every real generator
   stores a concrete backend in `__post_init__` via `resolve_backend`.
