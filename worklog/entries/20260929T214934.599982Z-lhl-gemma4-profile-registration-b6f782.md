# Register gemma4 strict and production profile plans; the default flips with byte-identical generation

## Summary

Piece (A) of the gate build lands: `hipengine/generation/gemma4_profiles.py`
registers both `RuntimeProfilePlan`s for `(gemma4_gguf, hip_gfx1100,
gguf_q4_k_m)` -- the quant `llm.resolved_quant` supplies on the shipped
artifact, confirmed again by the probe below -- and
`generation/__init__.py` calls the idempotent registrar alongside the qwen
ones. An omitted profile therefore resolves to `production` for gemma4
instead of the migration path, and an A/B proves the flip moves **zero
arithmetic**: the same prompt produces the same 24 greedy token IDs and the
same text with registration as without it.

Two rules discovered while building it shaped the plan content: a production
selection's `strict_fallback_variant` must name the *strict plan's* variant
for that scope (the §7.1 rollback key, which `resolve_runtime_profile`
enforces), and production's scopes must be a subset of strict's. Both pushed
the design toward exactly what the curation entry asked for: the measured
`auto` rows as production, the measured `grouped` rows as strict, and scopes
where strict cannot run what it would declare omitted rather than mislabelled.

### What building it corrected

- **The attribution entry's "three grouped owners" for `down_q8_0` were three
  failed probe attempts, not three owners.** The resolve spy recorded every
  *request*, and `gemma4_project_experts_grouped` walks
  fold128 -> amortized -> rowbatch8 catching `MissingKernelError` on each. For
  q8_0 none registers (`gemma4_experts.py` says outright "Not every quant
  registers one"), so the projection falls through to the selected owner under
  the **`linear`** layer key -- which is the `linear/moe_selected_q8_0` row,
  3 calls, exactly as observed. Under production that same projection runs
  `grouped_wmma` under **`moe_linear`**. One logical scope therefore spans two
  registry layers depending on profile, which the `(layer, scope)` axis cannot
  express, so `moe_linear/down_q8_0` is absent from both plans and the reason
  is recorded (revised B3). Its production variant is genuinely registered and
  genuinely runs; omitting it keeps every declared row true rather than
  declaring a strict variant that does not exist.
- **`resolve_runtime_profile` validates more than existence.** It first
  enforces that production's rollback key equals strict's variant per scope
  (`ValueError`, caught by the end-to-end probe before the registry check),
  then checks every selected and fallback key against the kernel registry after
  trying `load_backend_kernel_package`. The production fallbacks now name the
  grouped exact owners, matching how the qwen plans are written.
