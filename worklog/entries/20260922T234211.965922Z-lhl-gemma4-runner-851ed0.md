# Gemma 4 runner: config from GGUF metadata, forward parity, bit-exact decode

## Summary

`hipengine/runtime/gemma4.py` runs the Gemma 4 decoder forward pass over a
resident GGUF artifact and returns logits. It is validated against the CPU
reference on the quantized fixture, and incremental decode is **bit-identical**
to a dense prefill of the same sequence.

This is the unit that turns the validated kernels into a model. Every stage
resolves through the four-axis registry, so there is no branch on a quant or
backend name anywhere in the runner.

## The config comes from the artifact, not from a side file

`load_gemma4_device_weights(reader)` needs no HF `config.json`. A user who has a
`.gguf` file has a `.gguf` file; requiring a second file beside it would be a
second thing to get wrong, and every field the forward pass reads is in the GGUF
metadata — including the per-layer attention geometry and both RoPE contracts
(`full_rope` and `swa_rope`).

Two facts the metadata cannot state are read from the tensor list rather than
assumed:

- **Tied lm head.** GGUF omits `output.weight` when the head is tied, so its
  absence *is* the tie.
- **`k_eq_v`.** A layer with no `attn_v.weight` takes the raw K projection as V.
  On the fixture the global layer is `k_eq_v=True` and the sliding layer is not,
  so both branches are exercised.

`hf_config=` remains as an override for a conversion the GGUF metadata cannot
describe. It is no longer the only way in.

## Where softcapping belongs

The reference applies `tanh(logits / cap) * cap` immediately after the lm_head
and returns the capped logits; so does the streaming reference. The runner
initially applied it in the sampler instead, on the theory that it belonged to
the sampling step.

That was wrong, and the parity test caught it: every reference logit came back as
exactly ±30 while the runner returned raw values in the thousands. Capping is
part of the model's output distribution — a caller computing logprobs or running
their own sampler must see the distribution the model defines — so it is applied
in `forward()`.

`forward(..., apply_softcap=False)` exposes the raw projection. This exists
because the fixture's random weights produce logits far beyond the cap, so with
capping on both sides every value saturates to ±30 and a parity comparison would
be comparing saturated constants. Disabling it on both sides makes the
comparison sharp. A separate test asserts the cap is applied and matches, and
asserts the fixture's raw logits exceed the cap so that test cannot pass
vacuously.

## Measured parity

Runner against `gemma4_text_forward`, uncapped on both sides, last row:

| case | max abs diff | scale | relative | argmax |
| --- | --- | --- | --- | --- |
| prefill, 4 tokens | 57.62 | 1861 | 3.096% | agrees |
| sliding, 24 tokens (window 16) | 5.442 | 2277 | 0.239% | agrees |
| decode 1-at-a-time vs dense prefill | **0** | 835.3 | **0.000%** | agrees |

The decode row is the one worth naming: the KV cache path is **bit-identical** to
the dense path, not merely close. Both sides run the same kernels over the same
tiles, so an exact match is the expected result, and any non-zero difference
would mean the cache append offset, the mask width, or the block size had drifted.

The reference state dict is built from the artifact's tensors **dequantized**,
which is exactly what the device path reads. That makes the comparison isolate
arithmetic precision rather than also measuring quantization.

## Tests

`tests/test_unit_gemma4_runner.py`, 9 tests:

- config derivation from metadata, including `k_eq_v` and partial RoPE
  (16 of 64 pairs rotate on the global layer)
- the two layer types get different rope tables — asserted to differ in head
  width, angle count, and base, so a runner that built one table for the model
  could not pass
- prefill parity, decode-vs-dense, sliding window with a prompt longer than the
  window, softcap applied and matching, reset determinism, and two input guards

`test_reset_rewinds_the_cache` requires **exact** equality rather than
`allclose`, because the same inputs on the same code path should reproduce
bit-for-bit; any difference means stale cache state leaked across the reset.
