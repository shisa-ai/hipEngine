# R3: lm_head/embed_tokens int8 assessment (non-starter on Q4_K_S)

## Summary

Assessed whether int8 lm_head / embed_tokens transfers to hipEngine's Qwen3.8
Q4_K_S GGUF path. The external repo's "lm_head int8 / embed int8" was a
bf16 -> int8 halving on two untied ~2.5 GB bf16 matrices. Our GGUF already
stores lm_head (`output.weight`) as **Q6_K** (6.5625 bits, 1.043 GB) and embed
(`token_embd.weight`) as **Q4_K** (4.5 bits, 0.715 GB), both already *below*
int8 (8 bits, 1.271 GB) in precision AND size. Converting to int8 would be a
byte *increase* (lm_head +22%, embed +78%), so the premise does not transfer.
The registered `w8a16_lm_head_argmax_rows_bf16` kernel exists but is wired only
for the PARO runner, not the GGUF Qwen3.8 decode path (which uses
`launch_gguf_linear` on the Q6_K `lm_head` root). lm_head is a measurable
decode cost (4.63 ms/token, ~5.9% of decode wall), so the relevant question is
not int8 but whether lm_head could go *lower* than Q6_K (e.g. Q4_K) — a
separate top-1-drift-risky experiment, not a dtype transfer.

## Changes

- Confirmed GGUF tensor dtypes for Qwen3.8-27B Q4_K_S
  (`/models/gguf/Qwen3.8-27B-Q4_K_S.gguf`): `output.weight` = Q6_K,
  `token_embd.weight` = Q4_K, `output_norm.weight` = F32; file type
  MOSTLY_Q4_K_S (14).
- Byte math at 248320 x 5120: bf16 2.543 GB, int8 1.271 GB, Q6_K 1.043 GB,
  Q5_K 0.874 GB, Q4_K 0.715 GB.
- Traced the GGUF decode path: lm_head runs through `launch_gguf_linear` on
  `weights.root("lm_head")` (Q6_K), not the w8a16 kernel. The
  `w8a16_lm_head_argmax_rows_bf16` symbol is imported/launched only in
  `hipengine/runtime/qwen35_paro_runner.py`.
- Measured lm_head decode cost from the retained post-qmicro rocprof trace
  (`/tmp/qwen38-task22-post-qmicro-production-profile-c318/production-p4096-ar16_kernel_trace.csv`):
  16 dispatches of `q6_k_t16_qmicro_planar_gemv_bf16_kernel<float>` (FP32
  output) = 4629.1 us mean/token; 74.1 ms total across the AR16 window, ~5.9%
  of decode kernel wall. Embed is a gather, not a GEMM, and is already Q4_K.

## Validation

- GGUF dtype reads and the byte math are deterministic from the actual model
  file (GGUFReader) and fixed tensor shape 248320 x 5120.
- lm_head cost is from the committed production AR16 rocprof kernel trace
  (same source used for the retained post-qmicro decode profile). 16 FP32-out
  q6 planar GEMV dispatches correspond to the 16 AR decode steps.
- Kernel-source wiring cross-checked by grep across `hipengine/` for the
  w8a16 lm_head symbol (PARO-only).

## Result / decision

- lm_head / embed_tokens int8 does **not** transfer to the Q4_K_S GGUF path:
  both matrices are already below int8 size, so int8 would *increase* decode
  bytes. No action.
- The only direction that could cut lm_head's ~5.9% decode cost is a *lower*
  weight quant (Q4_K, ~0.72 GB) on the logit-defining head, which is a
  top-1-drift-risky experiment with its own strict gate — not part of this
  int8 premise. Deferred.
- If the W4A16 / bf16-head representation were ever used (PARO), the existing
  w8a16 lm_head kernel would be the relevant path, but that is not the Q4_K_S
  campaign's representation.
