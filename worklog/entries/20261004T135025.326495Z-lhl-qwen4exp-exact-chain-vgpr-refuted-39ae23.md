# The exact coltile leaf's 12-VGPR gap is not the pointer array - DP-8's occupancy route is closed by measurement

## Summary

**Tested the hypothesis from `20261004T134932.403319Z` - that the exact coltile
leaf's 8 wave-uniform row pointers, worth 16 VGPR, are the 12 VGPR that separate
it from the 32-wave ceiling. It is REFUTED. The production leaf's VGPR does not
move, and `DP-8`'s occupancy route is closed by measurement.**

## The experiment

Replaced the stored `weight_rows[COL_TILE]` array in the pipelined leaf with a
scalar base plus uniform offsets - `wrow_base + col * row_bytes` - which computes
identical addresses from terms that are all wave-uniform. Arithmetic, accumulator
order and reduction untouched. Then recompiled and re-read the same register
census.

| leaf | VGPR | static instructions | waves/CU |
| --- | ---: | ---: | ---: |
| **production leaf (pipelined, DPP)** | **76 -> 76** | **309 -> 318** | 25 -> 25 |
| production leaf, DPP off | 76 -> 76 | 378 -> 385 | 25 -> 25 |
| pipelined, unscaled (no wave-scale) | 83 -> 83 | 382 -> 384 | 23 -> 23 |
| sibling 4x8 pipelined | 88 -> **74** | 434 -> **404** | 23 -> **25** |

**The production leaf is unchanged in VGPR and 9 static instructions worse.** The
compiler was already keeping that pointer state out of vector registers, so the
array was never the constraint.

**The change was reverted.** It buys the production leaf nothing, costs it 9
instructions, and the only leaf it helps is the 4x8 sibling, which is not the
production tile.

## What this closes, and what it leaves

**`DP-8`'s occupancy question is now answered negatively.** The ledger had
corrected this leaf from "occupancy at the register-only maximum" to "merely
unmeasured", and the correction was right to insist on a measurement. The
measurement says: **the 12 VGPR are not recoverable from the pointer array**, so
they are the arithmetic's own state - 32 accumulators plus 24 floats of staged
operand (two pipelined stages of `COL_TILE + ROW_BATCH`). Those are irreducible
without changing the tile, which `DP-8` records as already swept, or the
pipelining, which is worth 6.84%.

**So the exact chain stays where `DP-8` left it: a load-latency problem.** Its own
diagnosis was that the chain runs at 2650 GFLOP/s, 16.1% of an instruction-mix
ceiling a probe sustains at 16467 GFLOP/s, and that this motivates a
latency/scheduling hypothesis rather than a demonstrated gain. The hardware-counter
capture - wait cycles, VMEM latency - remains the unstarted half of that row, and
it is now the only route left to the 6x.

## A secondary result worth keeping

**The pointer-array form does help the 4x8 sibling: 88 -> 74 VGPR, 434 -> 404
instructions, 23 -> 25 waves.** That tile is registered
(`hipengine_gguf_q8_0_gemv_coltile4_rowbatch8_pipelined_f32_f32_out`) but is not
the production leaf, so it is recorded rather than promoted. **If that tile is
ever preferred for some shape, the pointer-array form should be applied to it
first** - it is a free 2 waves and 30 instructions there.

**Note the direction of this result against the earlier reasoning:** I argued from
the budget decomposition that 8 pointers at 2 VGPR each were 16 of the 76 and
therefore the reducible part. The arithmetic was right and the inference was
wrong, because the compiler had already done the promotion the change was trying
to force. **A register budget that adds up is not evidence about where the
compiler put things.**

  `..._pipelined_kernelIffLi8ELi8ELi4ELb1ELb0ELb1`, encoding
  `qtype=8, COL_TILE=8, ROW_BATCH=4, WAVE_SCALE=true, ROW_FIRST=false,
  DPP_REDUCTION=true`.
- `git status --porcelain hipengine/` is clean after the revert and
  `weight_rows[COL_TILE]` is present in the file again.
- **No timing was run and no speed claim is made.** The change was rejected on the
  register census alone, before any GPU measurement, because a change that does
  not move the constraint cannot move the performance.

## Next

**The occupancy route is closed; the hardware-counter capture is the remaining
route.** `DP-8`'s first bounded experiment named it: capture wait cycles, VMEM
latency and occupancy for the layers 0-12 coltile launches, then decide whether the
6x is reachable at all. Until that capture exists, the exact chain should be
treated as optimised to the extent the register file allows, and the campaign's
prefill levers are the ones already recorded as blocked by the numerical envelope.
