# llama.cpp stages K in 256-element chunks and hipEngine's MMQ32 stages 32

## Summary

The prefill gap is **1.36x against llama.cpp** -- 746.6 tok/s against 1012.98 -- not the 30x
the objective's premise states, and `20260928T135000` already established it is a compute
efficiency gap rather than a bandwidth one. This unit reads llama.cpp's MMQ configuration
for the same architecture and quant and finds the difference in the kernel structure.

**llama.cpp's RDNA3.5 Q4_K configuration, from `ggml/src/ggml-cuda/mmq-config-rdna3-5.cuh`
in `~/llama.cpp/llama.cpp-hip`:**

```
ggml_cuda_mmq_config(type, nthreads, occupancy, I, J, sram_layout, K_vram, stream_k, fallback)

CASE(Q4_K, 128, 2,  64,  16, LAYOUT_Q8_1, MMQ_ITER_K=256, false, true);
CASE(Q4_K, 128, 2,  64,  32, LAYOUT_Q8_1, MMQ_ITER_K=256, false, true);
CASE(Q4_K, 256, 2, 128,  64, LAYOUT_Q8_1, MMQ_ITER_K=256, false, true);
CASE(Q4_K, 256, 2, 128, 128, LAYOUT_Q8_1, MMQ_ITER_K=256, false, true);
CASE(Q4_K, 256, 2, 128,  48..112, LAYOUT_Q8_1, MMQ_ITER_K=256, false, false);
```

**hipEngine's fused gate/up MMQ32 kernel, from
`hipengine/kernels/hip_gfx1100/quant/gguf_q4_k_q8_1_selected_prefill.hip`:**

```cpp
__launch_bounds__(128, 2)
__global__ void gguf_q4_k_selected_dual_q8_1_ds4_mmq32_fused_prefill_compact32_kernel(...) {
  __shared__ q4_k_mmq32_cache weight_tile[32];
  __shared__ q8_1_mmq32_cache activation_tile[32];
```

## The comparison

| | llama.cpp RDNA3.5 Q4_K | hipEngine MMQ32 |
| --- | --- | --- |
| threads per block | 128 or 256 | **128** |
| occupancy target | **2** | **2** |
| tile `I` (weight rows) | 64 to 128 | **32** |
| tile `J` (tokens) | 16 to 128 | **32** |
| **K staged per pass** | **256** | **32** |

**Thread count and occupancy are already identical.** That independently confirms the
`__launch_bounds__` experiment in `20260928T200000` -- llama.cpp targets two blocks per CU
and beats hipEngine, and hipEngine's own kernel already asks for two. **Occupancy is not the
difference and was never going to be.**

**The difference is the tile and the K staging, and the K staging is eight times smaller.**
A 32-element K chunk means the weight tile is re-staged from L2 eight times as often for the
same arithmetic. That is a mechanism for the L2 fetch amplification `20260928T135000`
recorded -- 66.6 GB of fetches against a 13.2 GB weight set, 3.8x and 7.4x -- and for
llama.cpp doing "the same arithmetic 1.36x faster" while moving *more* DRAM bytes (28.1 GB/s
against 24.5).

**The kernel's own name says 32.** `mmq32` is the tile, and the existing variants in the
tree -- `t16` and the WMMA routes -- are variations on the output-tile width, not on the K
staging.

## What this is and is not

**This is a source-level structural comparison, not a measurement.** The claim it supports
is that hipEngine's K staging is 8x smaller than llama.cpp's for the same quant on the same
architecture. **It is not a measurement that a 256-element K staging would be faster**, and
the 1.36x is not proven to be this.

**It is, however, the first concrete difference found between two implementations doing the
same arithmetic on the same hardware**, after the route, tile, occupancy, bandwidth, launch,
gap and packing dimensions were all closed by measurement.

## Next

- **Test the K staging.** The experiment is a variant of the MMQ32 kernel that stages 64 or
  128 K elements per pass instead of 32, on the same tile and the same arithmetic, measured
  on the existing expert microbenchmark. If the rate moves toward llama.cpp's, the 1.36x has
  a mechanism and a lever; if it does not, the structural difference is real but not the
  cause and the next place to look is the `I`/`J` tile.
- **Do not re-derive that the gap is 1.36x.** `20260928T133000` audited the objective and
  recorded the llama.cpp reference (`scripts/gemma4_llamacpp_reference_bench.py`, pp512
  1012.98, decode 41.92); the objective's "30X" is stale and the audit's own table already
  says so.
- **The objective's decode item is at parity, not 2x short.** The audit records the 2x target
  as 41.92 tok/s -- parity with the same-host llama.cpp reference -- and decode at 28.06.
