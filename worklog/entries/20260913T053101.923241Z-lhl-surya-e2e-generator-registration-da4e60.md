# run_surya_ocr must register its own generator; the e2e test must not borrow another test's import

## Summary

`tests/test_surya_e2e.py::test_end_to_end_greedy_matches_torch_reference` failed
in isolation and passed in the full suite. The task framed it as a test-isolation
bug ("a test must not depend on another test's import to register the generator
it needs"), and that is the symptom. **The defect is in the library**: the
generator registration is an import-time side effect of
`hipengine.generation.surya`, `hipengine.LLM` performs it
(`LLM._get_text_generator` calls `register_builtin_generators()`), and
`run_surya_ocr` -- a documented public entry point that resolves the *same*
registry key -- did not. So the public API worked only when something else in
the process had imported the generation package first, which in a test session
means another test module's import.

Mechanism, in one line each:

* in isolation, `pytest tests/test_surya_e2e.py` collects only this file, nothing
  imports `hipengine.generation.surya`, `_FACTORIES` is empty, and
  `resolve_text_generator(model="surya_ocr2", backend="cpu_reference",
  quant="fp32")` raises
  `MissingGeneratorError: ... known: <none>` in 0.44 s;
* in the full suite, `tests/test_surya_server_multimodal.py` imports
  `from hipengine.generation.surya import SuryaOCRGenerator` at module level.
  Pytest imports every test module before running any test, so that registration
  is already present when the e2e test runs.

The same class of hidden dependency existed in a second file that the task did
not mention: `tests/test_surya_public_api.py`'s two `run_surya_ocr` tests never
register the generator themselves. That file happened to be green standalone
because `test_plugin_and_generator_registered` -- its *first* test -- calls
`register_builtin_generators()` explicitly, so selecting the `run_surya_ocr`
tests alone in a fresh process used to raise `MissingGeneratorError` (the
registry starts empty; measured). They pass now because the library registers.
The library fix covers both files and any future caller; a test-side workaround
would have had to be repeated at every call site.

## The `clear_generation_registry_for_tests` question

The task asked whether registry clearing is what makes the dependency
order-sensitive. **It is not**: `clear_generation_registry_for_tests()` has no
callers anywhere in the tree (only its definition, the `__init__` re-export, and
the `__all__` entry). The order sensitivity is entirely the collection-time
import above.

It is, however, a trap if it is ever used, and that is worth recording because
it is the same class of bug: the built-in registrations are *module-scope calls*,
so once the modules are in `sys.modules` a later
`register_builtin_generators()` cannot replay them -- and `_BUILTINS_REGISTERED`
stays `True`, so it does not even try. A test that calls the clear would
permanently empty the registry for the rest of the process. Its docstring now
says so, and names the two working options (re-register explicitly, or
snapshot/restore `_FACTORIES` the way `tests/conftest.py` already does for the
kernel registry). Making the builtins replayable is a separate refactor: it
means giving each generation module a callable `register_*()` instead of a
module-scope `register_text_generator(...)`, which is what the runtime-profile
registries in `register_builtin_generators()` already do.

## Changes

- `hipengine/loading/surya.py`: `run_surya_ocr` calls
  `register_builtin_generators()` before resolving, mirroring
  `LLM._get_text_generator`. The import stays inside the function because
  `hipengine.generation.surya` imports this module. Docstring updated.
- `tests/test_surya_e2e.py`: new module-scoped `registered_generators` fixture
  (used by the end-to-end test) that registers the builtins explicitly, so the
  file no longer depends on another module's import even if the library path
  regresses; new
  `test_run_surya_ocr_registers_its_generator_from_a_fresh_process` pins the
  library behavior in a subprocess, where no other test has run.
- `hipengine/generation/registry.py`: `clear_generation_registry_for_tests`
  docstring documents the trap above (no behavior change).
- `docs/MODEL-SURYA.md`: the serving-path section now states that
  `run_surya_ocr` registers the builtins itself and works from a fresh process.

## Validation

- RED, before the fix: `pytest tests/test_surya_e2e.py::test_end_to_end_greedy_matches_torch_reference`
  fails in 0.44 s with
  `MissingGeneratorError: no generation implementation for (surya_ocr2, cpu_reference, fp32, greedy_one_token); known: <none>`.
- Fresh-process registry state before any call (so the new regression test is
  not vacuous): `registered_text_generators()` prints `()`.
- GREEN after the fix, fresh process: `run_surya_ocr(Path('/nonexistent-surya-model'),
  'page.png', max_new_tokens=1)` gets past resolution and fails later with
  `FileNotFoundError`, i.e. the registry lookup succeeded.
- `pytest tests/test_surya_e2e.py::test_run_surya_ocr_registers_its_generator_from_a_fresh_process`:
  1 passed in 1.38 s (a fresh interpreter that imports only the loading module
  and then sees `('surya_ocr2', 'cpu_reference', 'fp32', 'greedy_one_token')`
  in `registered_text_generators()`).
- Isolated acceptance, `python3 -m pytest tests/test_surya_e2e.py`: **11 passed in
  29.8 s**, zero skipped, so the end-to-end test itself ran rather than skipping
  on a missing model.
- Blast radius of the library change: `tests/test_llm_generate.py` (exercises
  `register_builtin_generators` directly), `tests/test_surya_public_api.py`, and
  `tests/test_surya_server_multimodal.py` (the module-level import that used to
  provide the registration for everyone else) -- 43 passed in 142.0 s as one
  bundle.
- The second file's hidden dependency, pinned directly:
  `pytest tests/test_surya_public_api.py -k run_surya_ocr` (both entry-point
  tests, nothing else in the process, so nothing registers on their behalf) --
  **2 passed, 3 deselected in 27.3 s**. Before this change that selection raised
  `MissingGeneratorError` in a fresh process, since the registry starts empty
  and neither test registers.
