# Pin the error retryability taxonomy and verify the HTTP responsiveness items

## Summary

Readiness item: GPU waits must leave the HTTP event loop responsive, and
busy/rejected/unavailable errors must retain correct status and retryability.

**Most of the acceptance was already covered, and two of its four conditions
are now verified rather than merely covered.** Recorded first because it is the
honest headline:

| condition | state |
| --- | --- |
| concurrent `/health` returns while engine work waits | **verified** |
| engine-closed returns the typed 503 | **verified** |
| over-capacity returns correct status + `Retry-After` | covered at the wire; decision layer newly pinned |
| unsupported explicit request is a non-retryable 501 | covered at the wire; decision layer newly pinned |

The two verified conditions run without a GPU:

```
pytest "tests/test_integration_server_api.py::test_busy_snapshot_does_not_block_other_http_requests"
  -> 12 passed in 0.90s
pytest "tests/test_integration_server_api.py::test_completion_tokenize_timeout_is_engine_unavailable"
  -> 2 passed in 0.86s
```

The responsiveness case drives a fake engine whose `live_loop_snapshot` blocks
on a threading event, then asserts `/health` and `/v1/models` answer while the
snapshot is still pending, that the release was not set, and that the request
was not served on the snapshot's thread. It covers `n=2` with `live_many=True`,
which is the multi-choice path adjacent to MTP. The mechanism is
`readiness_payload`'s `await asyncio.to_thread(_live_loop_snapshot, engine)`
(`hipengine/server/api.py:6914`), which keeps the blocking engine read off the
event loop.

## Changes

- `tests/test_unit_server_error_retryability.py` (new), 22 cases, pinning the
  decision layer that the integration tests only sample:

  - the three acceptance conditions against `_ERROR_TAXONOMY`: engine-closed
    503 retryable, over-capacity 429 retryable, unsupported-feature 501 not
    retryable;
  - `_generation_admission_http_error`: status 429, code `engine_busy`,
    `error_type="rate_limit_error"`, the `Retry-After` header, and the routing
    metadata it adds (`reason`, `overload_source`, the admission dict) --
    including that it preserves caller-supplied routing fields and builds the
    dict when absent;
  - **`Retry-After` clamping**, which no existing test covered: the existing
    cases assert exact values for positive inputs only. Zero and negative must
    floor at one second, because a zero delay tells a client to retry
    immediately and it would be rejected again;
  - the `_error_extension` contract for unknown codes: an unrecognised code is
    reported with its status but carries **no** `retryable` field, which a
    client must not read as permission to retry, and which is how "known
    non-retryable" differs from "unknown";
  - alias resolution keeps `legacy_code`, and omits it when already canonical;
  - taxonomy integrity: every alias targets a real code, every entry carries
    the four fields the response builder reads with a 4xx/5xx status, every
    `emitted` code resolves to a retry verdict, and the advertised manifest
    round-trips both the table and the aliases;
  - the retryability split asserted as a whole, so a future edit that flips a
    code's verdict fails rather than silently changing what clients are told.
