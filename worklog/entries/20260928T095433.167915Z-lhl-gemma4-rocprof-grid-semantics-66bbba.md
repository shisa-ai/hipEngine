# rocprofv3 grid_size_x is work items not workgroups so every trace grid this session was off by blockdim

## Summary

The factor-of-128 contradiction is closed, and the cause is a misreading of the
profiler's own column.

**`rocprofv3`'s `grid_size_x` is the number of work-items (threads) in x, not the
number of workgroups.** Every grid I read from a trace this session was therefore
off by `blockDim.x`, and two units were sized from those readings.

## The verification

Checked against a launch whose dimensions are known independently from its source,
not inferred. `gemma4_attention_prefill_kernel` is launched at
`gemma4_attention.hip:572` as:

```cuda
hipLaunchKernelGGL(
    gemma4_attention_prefill_kernel<scalar_t>,
    dim3(static_cast<unsigned int>(tokens * num_heads)),
    dim3(static_cast<unsigned int>(threads)),   // 256
    ...);
```

At the bench's 512-token, 16-head shape that is exactly **8192 workgroups in x,
1 in y and z**. The trace for that same run reports:

```
reported grid_size = (2097152, 1, 1)  blk = (256)   x60 dispatches
workgroups in x = 2097152 / 256 = 8192
```

**8192 matches the launcher exactly.** So the column is work-items, and the relation
is `grid_size_x = grid.x * blockDim.x` (and `grid_size_y = grid.y * blockDim.y`, which
is why the y column looked correct -- `blockDim.y` is 1 in every kernel here).

## What it reconciles

The MoE gate/up reports `grid=5632x8` with `blk=128`:

```
5632 / 128 = 44 workgroups in x   x   8 in y   =   352 blocks
```

which is **exactly** the `grid.x = (704 + 704) / 32 = 44` that the launcher computes
from the `intermediate = 704` measured at the call site in `20260928T095245`. The
trace and the caller agree; there was never a contradiction, only a column I had
read as workgroups.

The same correction applies across that decode table:

| kernel | reported | blk | actual workgroups |
| --- | --- | ---: | --- |
| MoE gate/up | 5632 x 8 | 128 | **44 x 8 = 352** |
| MoE down | 2816 x 128 | 128 | 22 x 128 = 2816 |
| dense GEMV | 45056 x 1 | 128 | 352 x 1 |
| q8_0 dense | 90112 x 2 | 128 | 704 x 2 |
| attention prefill | 2097152 x 1 | 256 | 8192 x 1 |

**The `%` and `ms` columns are unaffected** -- durations and dispatch counts are not
grid-derived -- so the decode attribution's shares (MoE gate/up 28.1 percent, q8_0
20.9, dense GEMV 12.8, MoE down 11.5) stand. Only the grid readings were wrong.

## Why this was worth a unit

I sized two units from trace grids. The first (`20260928T095039`) concluded the
gate/up runs 45,056 blocks and is per-block-setup dominated; that was wrong, and it
took a live interception of the call site plus this check to find it. The second
(`20260928T095245`) reached the right answer but for the wrong reason -- it treated
the trace as untrustworthy rather than as misread.

**A trace column is a reading of an instrument, and I had not verified what the
instrument reports.** The verification cost one query against a kernel whose launch
dimensions were already known.
