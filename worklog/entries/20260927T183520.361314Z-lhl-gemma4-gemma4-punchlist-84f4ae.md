# Gemma 4 family scoreboard and punchlist

## Summary

Profiled hipEngine and llama.cpp `a97cce8` on the same artifact
(`gemma-4-26B-A4B-it-UD-Q4_K_XL.gguf`), GPU (RX 7900 XTX, host `epyc`), BF16 KV
and shapes (1024 and 4096 tokens), bucketed every kernel into functional
families, and wrote `docs/campaigns/GEMMA4-26B-A4B-PUNCHLIST.md`: a family
scoreboard plus a prefill / decode / MTP punchlist with trace-derived gain
estimates.

Headline, unprofiled, XTX: prefill 1977 / 1060 tok/s against llama.cpp's
4969 / 4505 (1024 / 4096 tokens); decode 43.15 / 39.79 against 84.45 / 81.67
(1024 / 4096 context). llama.cpp with the Gemma 4 MTP assistant at draft 3:
164.59 tok/s (1.90x) on the XTX, 139.26 (1.86x) on the W7900.

Findings that set the order:

- Decode gap (11.65 ms busy per token at 1024) is MoE gate_up +4.70 ms (the
  decode owner runs about 91 GB/s), sliding attention +3.93, MoE down +1.55 and
  routing +1.08. hipEngine's dense Q8_0 decode already beats llama.cpp's.
- Decode MoE now costs 8.25 ms per token through a `*_selected_prefill_out`
  owner, against iteration 40's 6.2 ms through `selected_gemv_bf16_bf16_out`:
  a possible regression, recorded as the first check under D1.
- Prefill at 4096 is 56% attention: sliding blocks past the 1024-token window
  fall back to the exact class kernel (1478.7 ms). The vendored AOTriton
  0.11.2b ships `WindowedAttention` images and takes integer window bounds, so
  candidate P1 is a wrapper and admission change.
- Layer 29 (Q5_K / Q8_0 experts) is 13.8% of a 1024-token prefill.
- The prefill lm_head runs once per 512-token block although only the final
  block's last row is used.

## Validation

- Traces: hipEngine through `gemma4_family_census.py drive` (the same code as the
  scratch driver used here) under `rocprofv3 --kernel-trace` with the
  compiler-version pair, at `--prompt 1024` and `--prompt 4096`,
  `--decode 64`, on both GPUs. llama.cpp through `llama-bench -p P -n 0 -r 2
  --no-warmup` and `-p 0 -n 64 -d P -r 1 --no-warmup`, same flags as the
  scoreboard. The rollup's launch counts match the model: 29 gate_up, 29 down,
  50 sliding, 10 global attention launches per llama.cpp forward.
- Unprofiled rates: `scripts/gemma4_campaign_bench.py --prompt {1024,4096}
  --output 128 --samples 3 --warmup 1 --expect-gpu "RX 7900 XTX"` (decode stdev
  0.45 / 0.52); `llama-bench -r 3` at BF16 and f16 KV.
- MTP: `llama-server --spec-type draft-mtp -md MTP/mtp-gemma-4-26B-A4B-it-Q8_0.gguf
  --spec-draft-n-max {1,2,3,4,6}`, greedy, 5 chat prompts x 256 tokens after one
  warm-up request, on each GPU.
- A deadlock on the first trace attempt came from omitting
  `HIPENGINE_COMPILER_VERSION_FILE` / `HIPENGINE_REQUIRE_CACHED_BUILD`. That is
  the known G1 recipe issue, and the census docstring carries the recipe.
- Caveat recorded in the doc: llama.cpp's second HIP stream makes rocprofv3
  timestamps interleave across queues, so its families come from count-based
  subtraction, not timestamp splits. Its BF16-KV decode trace at 4096 context
  overstates the KV conversion kernel, which overlaps other work (unprofiled
  step 12.24 ms against 16.86 ms profiled busy).
