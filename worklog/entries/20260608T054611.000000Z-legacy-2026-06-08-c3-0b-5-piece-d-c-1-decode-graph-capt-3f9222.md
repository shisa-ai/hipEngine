## Changes

- Added `Qwen35ParoResidentSession.capture_batch_decode_graph` + `Qwen35ParoBatchDecodeGraph`: captures one `_step_batch_from_device_tokens(advance_positions=True)` into a HIP graph and replays it once per generated token. The captured step reads input tokens from `batch_lm_out_index`, runs the c-aware layers, writes the next-token argmax back to `batch_lm_out_index`, and advances the device decode counters — so replay walks the decode forward with no host involvement on the compute path. Full-attention span capacity (`max_live_count`/`max_context_len`) is baked for the last replay step while device `live_counts` (position/context buffers) start at the captured position and advance each replay; the batch attention kernel loops over the device `live_counts` and treats `max_context_len` only as a skip-guard (verified `qwen35_paged_full_attn_decode_context_tensor_batch_kernel`), and full attention uses the session-wide `max_splits`, so no per-step split recompute is needed.
- **Capture-safety fix (required):** the full-attention block table was cached under a *single* `(rows, slots)` key, but the row-chunked full-attention path (c4 rowchunk layers) calls `_batch_full_spans` with several `(chunk_rows, chunk_slots)` per step, so the single-key cache thrashed — re-issuing a host→device copy every call. That is wasteful eagerly and **fatal under HIP graph capture** (HIP error 906: host→device copy on a capturing stream). Replaced it with a per-`(rows, slots)` dict of persistent block-table buffers; once the eager warmup touches every chunk key, capture performs no malloc/copy. This was the second per-step alloc removed after C3.0b-1's segment metadata.
- **Validation gate** (`scripts/qwen35_batch_decode_graph_smoke.py`, new): PARO linear-attention layers carry recurrent state that advances every decode step, so the eager reference and the capture/replay each run from their own fresh session (prefill+warmup is deterministic → identical post-warmup state). Replayed token stream is **byte-identical to the eager device-resident reference at c2, c4, c8** (`first_mismatch: null`, launches == decode), prompt 128 / warmup 4 / decode 16–32, L40, `HIP_VISIBLE_DEVICES=1`. Independently, the eager-default and device-resident `native_batch_vs_independent_c1` retained-bench equality stayed green (0 mismatches, c4/c8) after the block-table dict-cache change — so eager decode is unregressed.
- **Throughput (preliminary, single-run, near-noise):** back-to-back replay vs eager device-resident loop (decode 32): c2 127.1→128.9 (+1.5%), c4 176.1→179.6 (+2.0%), c8 229.9→228.8 (−0.5%). Small/neutral — the eager device-resident path is already host-lean after C3.0a + C3.0b-1, so graph replay only removes the residual host-side per-dispatch launch latency, not the per-dispatch **device** overhead the regime is bound by (consistent with the documented c=1 finding). A firm throughput claim needs multi-rep medians via a retained-bench replay path; correctness is the solid deliverable here. No new kernel added (replay uses existing kernels), so no rocprof kernel gate applies.
