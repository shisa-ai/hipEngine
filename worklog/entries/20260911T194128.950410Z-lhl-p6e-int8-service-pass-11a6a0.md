# P6's service half passes on the resumable INT8 route; executor_mode does not identify that route

## Summary

Two results, one positive and one a correction to this audit's own earlier
conclusion.

**1. P6's service half now passes on the deliverable route.** The harness set no KV
field, so `ServerConfig.kv_storage` defaulted to `"auto"`, which
`resolve_kv_policy` resolves to BF16. With BF16 KV the session's
`kv_attention_source` is `bf16`, so the gate at `qwen35_gguf.py:8084` never enters
the `int8_direct` branch and the resumable executor is never attempted. Setting
`kv_storage="int8_per_token_head"` with `kv_scale_dtype="fp32"` makes the route
engage and **all eight gates pass**, including `resumable_path_engaged`.

**2. `executor_mode` does not identify the resumable route.** The earlier entry
concluded that `executor_modes: {"None": 2.0}` meant the chunk-outer executor ran.
That is wrong and is withdrawn. The field is set only by
`_prefill_batch_native_layer_outer` (`qwen35_gguf_runner.py:23122`), the
**non-resumable** layer-outer entry; the resumable entry
`prefill_batch_native_layer_outer_resumable` (`qwen35_gguf_runner.py:22502`) never
sets it. So `None` is the expected value on both the chunk-outer path and the
resumable path, and the field the code comment describes as distinguishing
layer-outer from chunk-outer does not cover the entry P6 actually uses.

## Changes

The harness now configures INT8 KV in all three places that matter:

- `LLM(model, ..., kv_storage=..., kv_scale_dtype=..., kv_scale_granularity=...)`
- the harness's own `llm.prepare(..., sampling_params=SamplingParams(kv_storage=...))`
  — this runs **first**, so leaving it at `auto` would resolve to BF16 regardless
  of the server config
- `ServerConfig(..., kv_storage=..., kv_scale_dtype=..., kv_scale_granularity=...)`

with `--kv-storage` (default `int8_per_token_head`), `--kv-scale-dtype` (default
`fp32`) and `--kv-scale-granularity` (default `per_token_head`), and the requested
values recorded in the artifact.

## Concurrency check

A sibling agent reported using GPU 0 during 16:15–17:25 UTC and asked whether that
invalidates these results. It does not, on three grounds.

- **No overlap with the runs that matter.** Local time is UTC+9, so the runs above
  are 19:31:03 and 19:35:57 UTC, about two hours after that window closed. Of this
  audit's artifacts only `/tmp/p6e-proof.json` (17:25:19) falls inside it, and its
  results were superseded several times before this unit.
- **The findings are state and configuration claims, not timing claims.** Whether a
  route engages, what `kv_attention_source` is, and whether the oracle owner is
  allocated are not affected by device contention. Contention cannot make a BF16
  layout into an INT8 one.
- **The timing gates have wide margins and reproduce tightly.** Contention would
  inflate both sides of `bounded_decode_gap`, which compares the refill against the
  reference within the same run.

The earlier entry that recorded "P6e's service half passes" with 825.8 ms
acknowledgement and a 39.566/42.430 ms gap pair was measured in the possibly
overlapping window. Those numbers are superseded by the two runs above, which are
tighter and cleaner, and no current claim rests on them.

## Honest limits

- `performance_claim` is false: this is a qualification result, not a throughput
  claim, and no scoreboard row changes.
- The engagement gate keys on the oracle-owner peak, which is specific to the
  layer-outer shared-oracle mechanism. It is strong evidence for this route but
  would not generalise to a resumable path that allocated no such owner.
- `executor_modes` remains exported and is still correct for the non-resumable
  layer-outer entry, but it should not be used as an engagement indicator.
- The runs cover one layer budget (4) and one cancellation delay (600 ms), so the
  reviewer's requested coverage is not yet met.
- Blocking and slow-consumer survivors are checked for exact text equality with the
  reference, which is a strong equality gate but does not probe longer outputs.
