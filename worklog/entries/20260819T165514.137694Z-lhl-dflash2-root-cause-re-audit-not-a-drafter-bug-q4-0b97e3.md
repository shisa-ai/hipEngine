# DFlash2 root-cause re-audit: not a drafter bug; Q4 lane erases acceptance, verify O(N^2) + draft cost block MTP

## Summary

Re-audit of why DFlash2 (reference: "faster than MTP", blog acceptance 4.80 vs
MTP 4.28 at block 8 on the BF16 target, 2.7-3.4x AR on SGLang) measured slower
than our MTP B3 (23.85 tok/s = 1.78x AR) on the Qwen3.8-27B Q4_K_M gfx1151
lane. **Conclusion: the drafter is NOT broken** — the blocker is the lane +
hardware economics, plus two real (now-fixed/identified) implementation cost
inefficiencies.

### Evidence the drafter is not broken

- Batch chain verify and sequential per-token verify produce **identical**
  acceptance (3.64 == 3.64) and identical recall (r1 0.763, r16 0.947, unary
  0.711) on `code_merge_intervals` — the earlier "tap drift" does NOT degrade
  acceptance; the bulk-verify tap capture is faithful.
- recall@1 (0.763 avg incl. decay) and recall@16 (0.947 avg) are inside the
  reference blog's per-position range (r1 0.729-0.854, r16 0.878-0.995) — the
  drafter's per-position quality matches the reference.
- AR-exact on every run (all outputs are greedy target predictions).

### The real blockers (lane + economics, not implementation)

1. **Q4_K_M target erases DFlash2's acceptance advantage.** The reference's
   4.80 > 4.28 is the BF16 target at T>0. On our Q4_K_M greedy lane: DFlash2
   3.49 (B7) / 2.80 (B3) vs MTP 3.85 (B3). DFlash2 feeds on the target's
   hidden states (5-tap projection), so target quantization degrades it
   disproportionately; MTP only consumes token embeddings. This is a lane
   property, not a code bug (the reference itself says "for quantized targets
   use block_size <= 5").
2. **Verify is the dominant shared cost, and grows O(N^2) in block rows.** 4-row
   verify ~166ms (same as MTP B3's ~160ms); 8-row verify ~620ms (3.6x for 2x
   rows — causal block attention is O(N^2), 36 vs 10 pairs). So the only
   economic operating point is B3, where DFlash2's acceptance (2.80) is below
   MTP's (3.85) AND its draft is 13-30x MTP's.
3. **DFlash2's 5-layer drafter + selector is ~13x the draft compute of MTP's
   head** (74ms forward + select vs ~5ms), and its acceptance does not exceed
   MTP's on this lane to amortize it.

Airtight arithmetic: even with a **free** drafter, DFlash2 at B3 =
2.80/0.166 = 16.9 tok/s = 1.26x AR < MTP B3's 1.78x AR (acceptance 2.80 <
3.85). No implementation fix on this Q4/8060S lane reaches MTP B3.

### Implementation cost inefficiencies (fixable)

- **FIXED**: the cycle called `drafter.last_logits_argmax()` — a full
  (rows x 248320) device->host logit copy — for the "unary" diagnostic. The
  top-1 of the already-on-device top-16 is the global argmax, so the copy is
  redundant; replaced with `cands[:, 0]` in both native cycles (identical
  unary values, AR-exact preserved).
- **IDENTIFIED**: the remaining ~70ms select is dominated by a full-logit GEMM
  (7x5120 x 248320) reading the 2.54 GiB dequantized BF16 output head every
  cycle. A Q6-quantized top-K GEMV (verifier's `_verify_lm_head_q6_top1_dp4a`
  computes top-1 only, not top-16) would cut it ~3x. Worth doing as a cost
  reduction even though it does not cross the MTP line.
- **IDENTIFIED**: the rowtile-8 verify (620->310ms) was reverted as
  AR-divergent; root-causing it halves the 8-row verify.

## Changes

- `scripts/dflash2_gguf_cycle.py`: replaced the full-vocab host-copy argmax
  (`last_logits_argmax`) with the on-device top-16 rank-0 (`cands[:, 0]`) in
  both the batch and sequential native cycles.

## Validation

- Batch vs sequential on `code_merge_intervals`: mean_acceptance 3.64 both,
  recall@1 0.763 / r16 0.947 / unary 0.711 both — identical (no tap drift
  effect on acceptance).
- After the unary fix: fox prompt unary-argmax 0.513 unchanged, AR-exact
  40/40, acceptance 1.82 unchanged.
- Reference cross-check (blog): Qwen3.8-27B acceptance 4.80 (BF16, T>0,
  block 8); our Q4 greedy 3.49; MTP B3 3.85 measured here.

## Next

- Decide whether to invest in the Q6 top-K select GEMV (~3x select speedup,
  B3 -> ~0.8x AR) and the rowtile-8 verify root-cause (halves 8-row verify) —
  both real cost reductions but neither reaches MTP B3 on the Q4/8060S lane.
- The only path to DFlash2 > MTP on this hardware is a BF16 (non-Q4) target,
  which is out of the closed Q4 lane's scope.
