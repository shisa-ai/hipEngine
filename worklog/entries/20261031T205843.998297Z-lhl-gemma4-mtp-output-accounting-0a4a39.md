# Gemma 4 MTP publishes shared output accounting

## Summary

`hipengine/generation/gemma4_mtp.py` now publishes the shared per-request
MTP-versus-AR block as `diagnostics.specdec2_mtp2`, built by
`hipengine/speculative/accounting.py`. Before this, a served Gemma response
could report `proposed_draft_tokens` and `accepted_draft_tokens` but could not
answer which emitted tokens came from committed speculative cycles and which
from an autoregressive step. Several providers already answered that through
the shared block; mixed serving was still being migrated in another worker
while this unit ran, so this is one provider migration, not the last one.

Every legacy diagnostic is preserved with the same values and the same
meaning, generated tokens are unchanged, and no shared helper, server, Qwen
provider, doc, kernel or other worker's file was edited.

## Changes

- `hipengine/generation/gemma4_mtp.py`
  - Added `_Gemma4MTPOutputAccounting`, a request-local carrier created once per
    `generation_steps` frame. It declares the fields the shared helper writes
    (`mtp2_cycles`, candidate/accepted lists, `mtp2_mtp_output_tokens`,
    `mtp2_ar_step_output_tokens`, `mtp2_first_fallback_position`,
    `mtp2_ar_step_reasons`, `mtp2_output_spans`, and the three cycle phase
    sums). Request ownership stays with the frame; the provider keeps no new
    cross-request state, and `last_cycles` stays the legacy last-request record.
  - Both budget keys carry the frame's resolved budget: `mtp2_requested_budget`
    and `mtp2_candidate_budget`. `speculative_output_accounting` reads the
    latter unconditionally, so a carrier that set only the former published
    `candidate_budget: 0` beside a positive request -- "asked for six, ran at
    zero". The legacy `candidate_budget` diagnostic stays the provider's
    configured default, which a per-request override makes disagree; the block
    reports the frame's numbers and the regression pins both sides of that.
  - One `record_speculative_outputs` call per committed cycle, with the
    published prefix length as `visible_count` and the pre-append index as
    `output_position`. Rejected proposals, drafts the accept walk observed
    before settling, and a stop-truncated tail are never counted; the prefill
    root token stays out of the block because it precedes the plan and the
    response layer already derives it as `completion_tokens -
    mtp_output_tokens`.
  - `record()` now returns the host-wall delta it already accumulated, so the
    same measurement points feed the legacy `phase_census` and the block's
    `cycle_timing_ms` (proposal, target, accept). Only a committed cycle adds
    to those sums, so a proposal that never reached a commit publishes no phase
    time. The legacy census values are unchanged.
  - `_cycle_output` hoists its diagnostics dict to a variable and adds the block
    beside the route fields. The legacy dict body is unchanged.
  - The carrier exists only when the request's resolved budget is positive. A
    zero budget is how `Gemma4ResidentModelRunner` serves a plain row on this
    provider, and `hipengine/generation/gemma4_resident.py` strips only
    `_MTP_ONLY_DIAGNOSTICS` from such a row, which does not include
    `specdec2_mtp2`. Guarding on the budget is what keeps a plain Gemma
    response free of a speculative block without touching that shared file.
  - `plan_group_rows`, `plan_ar_only`, `plan_reason`, `provider_readiness` and
    `provider_state_present` stay unset. This route has no group planner and no
    prompt-activation decision, so the block reports them absent rather than
    inventing a decision the provider does not make.
- `tests/test_unit_gemma4_mtp_output_accounting.py` (new, 47 cases): the schema
  and legacy-field preservation, accepted/corrected/rejected cycle attribution,
  the zero-draft tail as in-plan autoregressive output, `max_tokens == 1`
  intent without a cycle, the budget-0 plain-row contract, a multi-token stop
  and an EOS that truncate a group mid-walk, a budget/horizon sweep asserting
  `mtp + in_cycle_ar + prefill_root == emitted` and
  `mtp == accepted + cycles - depth0` (the identity the server's
  `_mtp_output_reconciliation` checks), diagnostic span tiling through
  `span_accounting`, phase sums equal to the legacy census, request-local
  isolation across two requests on one provider, the declared-field contract,
  the per-request budget versus the provider's legacy budget, a deadline before
  any work, and cancellation between cycles.

Findings recorded, not changed:

- The route's zero-budget frames already record zero-draft cycles in the legacy
  `cycles` diagnostic; the resident runner strips that list for plain rows.
- `mtp_output_tokens` is bounded by `accepted + speculative_cycles` by
  construction, because each committed speculative cycle emits its accepted
  drafts plus exactly one target-verified token.
