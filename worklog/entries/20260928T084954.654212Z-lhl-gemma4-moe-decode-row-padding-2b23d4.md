# the decode moe pads one real row per expert to a 32 row mmq tile and the trace grid proves it

## Summary

`20260928T084824` named the MoE gate_up as the one decode path not near the
memory ceiling -- 0.534 GB per token at 75 GB/s where the dense GEMV beside it
runs at 199. This unit finds the mechanism and it is the row tile.

**The gate_up MMQ rounds every active expert's compact rows up to a 32-row
tile. During a 1-token decode each active expert has exactly one real row, so
the kernel computes 32 rows per expert where 1 is real.** The trace's grid
proves it: `grid=(5632, 8, 1)` on a 1-token decode, where `grid.y` is
`mmq_total_rows / 32` and 8 is `8 active experts x 32 padded rows / 32`.

That is a 32x arithmetic overrun on 24.5 percent of decode. **The fix is a
smaller MMQ row tile, which is bit-identical** -- the row tile changes which
rows a block owns, not the order any output's K-loop accumulates -- so it does
not touch the batch-composition-invariance contract that keeps decode on the
prefill route, and it does not need an execution-profile gate.

**The payoff is bounded and smaller than the 32x suggests.** The same kernel
reaches 103 GB/s in prefill, where the tiles are full, so the reachable decode
rate is somewhere between its current 70 GB/s and that 103. That is 7.09 ms per
token falling to between 2.7 and 4.9, or 7 to 15 percent of decode.

## What the grid shows

From `rocpd_kernel_dispatch`'s `grid_size_*` and `workgroup_size_x`, decode
region:

| kernel | grid | block | n |
| --- | --- | --- | --- |
| `..._mmq32_fused_prefill_compact32` | **(5632, 8, 1)** | 128 | 1015 |
| `q5_1_mmq_ds4_selected_prefill` | (2816, 128, 1) | 128 | 1102 |
| `gemma4_attention_decode_class<1,2>` | (8192, 1, 1) | 512 | 875 |

The launcher sets `row_tiles = mmq_total_rows / 32` and `grid.y = row_tiles`
(`gguf_q4_k_q8_1_selected_prefill.hip:4992`). `qwen35_moe_mmq32_tile_map`'s own
docstring is "Map compact expert starts to **32-row MMQ tile starts**". With 8
active experts at one row each the compact starts are `[0,1,...,8]` and the
tile starts are `[0,32,64,...,224]`, so `mmq_total_rows` is 256 and `grid.y` is
8. The trace agrees.

**The down projection is worse in a different way**: `grid.y = 128` on a
1-token decode, which is the full expert count, because
`laguna_moe.py:2644` sizes it as `_mmq32_static_upper_rows(lanes, expert_count)`
-- the runner's declared capacity rather than the call's live rows. The 120
empty experts' tiles early-out on `expert_id < 0`, so they are cheap, but the
launch covers 4096 rows for 8 real ones.

## The arithmetic

Per layer, gate+up, from the artifact's own metadata (128 experts, ffn 704,
hidden 2816, q4_k at 144 bytes per 256 weights):

| | padded rows | padded FLOP | weight bytes | measured | rate |
| --- | --- | --- | --- | --- | --- |
| decode, 1 token | 8 x 32 = 256 | 2.03 GFLOP | 17.8 MB | 253 µs | 70 GB/s |
| prefill, 512 tokens | 128 x 32 = 4096 | 32.5 GFLOP | 285.5 MB | 2.76 ms | 103 GB/s |

Decode's padded arithmetic is 32x its live arithmetic (8 experts x 1 row x
2 x 704 x 2816 x 2 = 63.4 MFLOP), and it is 8 times smaller in absolute terms
than prefill's while taking only 11 times less time. **So the kernel is
arithmetic-bound in both cases, and the padded rows are what it is doing.**

**A 1-row tile would not change the weight traffic at all.** Each expert's
weight matrix is read once per (tile_col, expert) either way, because the row
tile partitions rows within an expert, not experts across tiles. Only the
arithmetic drops. So the floor is set by bytes: 17.8 MB per layer at the dense
path's 199 GB/s is 89 µs, or 2.7 ms per token, against 7.09 measured.

## Why this is safe to change

The batch-composition contract in `gemma4_moe_prefill_route_enabled` is about
*which arithmetic* runs -- int8-dp4a against fp32 -- and it is why decode takes
the prefill route at all. A row-tile change stays inside the same arithmetic:
the MMQ accumulates over K in the same order for every output element, and the
row tile only decides which output elements a block owns. The kernel already
computes `valid_rows` and guards the tail, so a narrower tile is the existing
tail path with a different constant.

That is the same class of change as `2cf3a0a5f`, where six tiles of the dense
Q8_0 kernel were measured bit-identical. **It should be measured the same way
before it is claimed.**
