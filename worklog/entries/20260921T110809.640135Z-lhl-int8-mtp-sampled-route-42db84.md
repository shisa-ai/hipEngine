# INT8 KV declares the sampled MTP route its accept path already implements

## Summary

`temperature`, penalty, `logit_bias`, and `suppress_token_ids` requests now
speculate on INT8 KV instead of dropping to AR. The three INT8 declarations list
`sampling_modes=("greedy_fast", "sampled")`, and no other production code changed.

## What actually refused the route

The runtime gate was never the blocker, and this is the finding that resolves the
tension in task 4's warning. `Qwen35GGUFMTP2Adapter._sampled_route_qualified`
matches on **backend, target architecture, weight quant, and artifact size — and
never on KV storage**, exactly as its docstring says. So it already treated BF16
and INT8 alike: for the gfx1151 Q4_K_M artifact it returned true for both.

That left the declaration as the single refusing gate:
`hipengine/speculative/serving.py:592`, reached because the INT8 declaration
inherited `("greedy_fast",)` from `hipengine/speculative/serving.py:566`.

Task 4's warning — "do not widen `sampling_modes`" — was right about the
*declaration* asymmetry and wrong about the consequence. Declaring `sampled` for
INT8 does not widen the **effective** scope, because the runtime gate still
requires an evidence row matching this backend, architecture, weight quant, and
artifact size, and that check is storage-blind. The declaration states what the
kernels execute; the evidence row states what was measured. Both layers now agree
about INT8.

Measured through the real plugin on the gfx1151 artifact:

| storage | mode | rows | before | after |
| --- | --- | --- | --- | --- |
| `int8_per_token_head` | `sampled` | 1 | `mtp_sampling_unsupported` | `implemented_gguf_dense_int8_native_chain` |
| `int8_per_token_head` | `sampled` | 2 | `mtp_sampling_unsupported` | `implemented_gguf_dense_int8_gfx1151_group_native_chain` |
| `int8_per_token_head` | `processed_argmax` | 1, 2 | refused | **still refused** |
| `bf16` | `sampled` | 1-4 | admitted (evidence) | unchanged |
| `bf16` | `processed_argmax` | 1, 2 | refused | **still refused** |

`processed_argmax` is the finish-rule and metadata set (`min_tokens`,
`eos_token_id`, stop ids, stop sequences, `logprobs`). It does not reach the
sampled route at all and stays refused on **both** storages. That is task 6, not a
storage question, and it is now pinned by test.

## Why the declaration is the truthful statement

The induced-law exactness contract is unaffected by this change: the accept still
samples from the target's own law after applying the request's sampler pipeline to
each verified row, and it is storage-agnostic by construction —
`sampled_accept_summary` consumes the verifier's row logits and the request's
sampler state, and never reads KV.

The route's one remaining gap is its own finish rule: the cycle commit ends a row
only when its last visible token is the row's EOS, and a stochastic accept has no
`greedy_chain_eos_limit` bound, so a stop token or EOS can land mid-cycle. That is
contained per request by the servable-blocker set rather than fixed, and it is not
INT8-specific — it is why every declaration was greedy-only. The device-side accept
that the declaration comment named as the second precondition landed 2026-09-19
(`_device_sampled_accept_plan`, for native-sampler rows with no processors,
`top_k == 0`, and no constraints), so the comment now names one open gap instead
of two.
