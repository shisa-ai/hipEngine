# Gemma 4 gate/up MMQ spike: int8 dp4a dual selected prefill is 5.6x the fp32 grouped route

## Summary

The in-tree int8-dp4a MMQ grouped route works at Gemma 4's expert geometry and is
**5.6x** the fp32 route it would replace, with quantization error inside the envelope
this kernel family already asserts in its own test.

Scratch harness `/tmp/i7_mmq_spike.py`, geometry (in 2816, out 704 + 704, 128 experts,
4096 compact rows = 512 tokens x top-8), synthetic Q4_K weights:

| route | time |
| --- | ---: |
| raw fp32 grouped, two launches (what ships) | 37.04 ms |
| MMQ dual: activation pack + 32-row tile map + one dual launch | **6.60 ms** |

Numerics against the raw route on the same inputs: max |diff| 48 on outputs whose mean
magnitude is 611.6, i.e. **normalised max 2.1e-2 and mean 1.1e-3**. The Q5_1 MMQ
selected-prefill test asserts exactly this envelope against its strict owner
(`abs_mmq.max() < 2e-2`, `abs_mmq.mean() < 2e-3`), so this is the established
production-variant contract for the family, not a new tolerance.

## What the harness had to get right

Three things cost time and are worth recording, because none is documented:

1. **Weights are per-expert.** The raw grouped kernel indexes
   `qweight + (expert * out_features + out) * row_bytes`, so the buffer must hold all
   `num_experts` matrices. A single expert's matrix faults on the device.
2. **The activation pack is the single-plane `gguf_q8_1_mmq_ds4_pack_bf16`**, not the
   `d4x3` three-plane variant - the MMQ32 dual reads the one-plane layout and its
   workspace is `compact_capacity * (hidden // 128) * 144` bytes. Using the three-plane
   pack against that workspace size overruns it.
3. **Random bf16 activations are not usable for numerics.** 15-bit random patterns
   include the exponent-all-ones encodings, so NaN propagates through every dot product
   and the whole comparison is NaN. Generate finite bf16 (shift a random f32) instead.

Also confirmed: the tile map readback is needed and sane - `mmq_total_rows` came back
5856 = 32 x 183 tiles for 4096 compact rows over 128 experts, with
`expert_start_mmq32 = [0, 32, 64, ...]` and `tile_expert = [0, 1, 2, ...]`. So the
launcher does not need a host-side bound; read the 8-byte total after the tile map, as
the existing Qwen4 route does.

## Production recipe (next unit)

`gemma4_experts_forward_bf16` already fuses gate and up into one call
(`gate_up_proj` is `(num_experts, 2 * intermediate, hidden)`, one launch with
`out_features = 2 * intermediate`), and the dual MMQ writes gate in the first half and
up in the second half of each row - **the same layout**, so `gemma4_gelu_tanh_mul_bf16`
consumes it unchanged.

The one gap: the dual MMQ computes its expert base as
`qweight + expert_id * local_out_features * weight_row_bytes` for each of `a` and `b`,
which assumes two separate per-expert matrices. Gemma 4 holds the fused buffer, whose
expert stride is `2 * intermediate` rows. The smallest change is a launcher variant
taking an explicit `expert_row_stride` (equal to `local_out_features` today, equal to
`2 * intermediate` for the fused layout) - a few lines in
`gguf_q4_k_q8_1_selected_prefill.hip` plus its wrapper, no model or loader change.

Remaining production work: add the five scratch buffers (workspace, identity,
`expert_start_mmq32`, `tile_expert`, total) to `Gemma4ExpertScratch`, run
pack -> tile map -> readback -> dual launch in place of the current fused projection,
and keep the raw route as the fallback for geometries that do not qualify. Expected
effect on the campaign metric: Q4_K gate/up is ~29 x 37 ms = 1.07 s of the 4.23 s
512/128 prefill, so replacing it with ~29 x 6.6 ms saves ~0.87 s, about **1.26x**.

The Q5_1 down projection (30.1% of prefill) is **not** covered: its MMQ kernel requires
`ffn % 128 == 0` and Gemma 4's 704 fails, so it stays on the fp32 route, which is
already at its instruction limit.
