# 2026-06-07 — concurrency C3.0c output-tiled GEMV: transposed layout + decode-path integration

## Summary

- Historical pre-Worklog2 journal entry, ported verbatim from `WORKLOG-LEGACY.md` (source lines 76706-76713).
- First appended to the journal in commit `672a7427` (subject: feat: wire transposed output-tiled GEMV into c>1 decode projections (C3.0c)).

## Changes

- Extended the C3.0c output-tiled kernel to the **transposed** qweight layout (`launch_pack8_output_tiled<scalar_t, true>` + extern "C" `hipengine_gemv_awq_pack8_output_tiled_transposed_bf16/fp16` + Python wrappers). Bit-exact gate `tests/test_paro_awq_output_tiled_gemv.py` now covers both layouts: **96/96 PASS** (strided + transposed × rows {2,4,8} × 4 shapes × threads {64,128} × {bf16,fp16}), byte-identical to `gemv_awq_pack8_strided` / `gemv_awq_pack8_transposed`.
- Critical integration finding (via a call-count probe wrapping every projection wrapper in `qwen35_paro`, c2 128-ctx native decode): the c>1 decode projections run on the **TRANSPOSED** layout (`.qweight_pack8_decode`), not the strided `.qweight` layout. Per-step projection-kernel calls: `gemv_awq_dual_pack8_transposed_fp16` 2200, `gemv_awq_pack8_transposed_fp16` 1800, `gemv_paro_marlin_k_fma_fp16` 1600, `gemv_awq_selected_dual_pack8_transposed_fp16` 1200, `gemv_awq_selected_pack8_transposed_fp16` 1200, fusedw4_prefill 270/240. The strided single GEMV (`project_pack8`'s `.qweight` branch, my first integration target) is **not** on the decode hot path — so the original non-transposed wiring was inert for decode.
- Wired the transposed output-tiled single GEMV into the real c>1 decode hot sites (`hipengine/runtime/qwen35_paro.py`): full-attn QKV + Z projection (`force_gemv` path) and shared-expert down projection (`use_batch_gemv` path), gated `tokens in {2,4,8}` (frozenset, env kill-switch `HIPENGINE_DISABLE_PACK8_OUTPUT_TILED`). After wiring, the c2 probe shows `gemv_awq_pack8_output_tiled_transposed_fp16` = 1000 calls/step and the per-row `gemv_awq_pack8_transposed_fp16` drops 1800→800 — the kernel is genuinely exercised on the decode path.
- Correctness e2e: native batch decode (128-ctx, c4, 24 decode tokens), output-tiled ON vs `HIPENGINE_DISABLE_PACK8_OUTPUT_TILED=1` OFF → **all 4 rows byte-identical** generated tokens (guaranteed by the 96/96 bit-exact kernel gate; verified end-to-end now that the kernel is actually on-path). `test_dense_gemv_plan` + `test_paro_awq_gemv_plan` green (dispatch unaffected).
- Throughput: NOT claimed. A crude process-wall A/B (decode 200, 3 reps each) was uninformative — model-load/build-check/system noise dominates (ON 61/104/100 s, OFF 92/90/119 s). A valid c>1 decode throughput needs the proper isolated-decode protocol, and c>1 remains correctness-blocked for retained claims regardless. The wired single-transposed projection is a small decode slice (~5.3 ms/step profiled of ~88 ms); the **dual** transposed projection (2200 calls/step, ~9.1 ms) is the larger lever and needs a NEW output-tiled DUAL pack8 kernel — queued as the next C3.0c packet.
- Scope note: kernel work is now done in-repo/this tree (fork boundary changed); AGENTS.md's kernel-R&D-in-parent rule intentionally left unedited to avoid fork merge conflicts.
