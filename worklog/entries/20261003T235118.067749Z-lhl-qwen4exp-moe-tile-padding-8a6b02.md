# MoE prefill pays 1.60x in per-expert tile padding at the production chunk

Status: decision

## Summary

The routed-MoE gate/up prefill kernel launches over a **padded** row space in which
every expert that owns at least one row is rounded up to a full 16-row WMMA tile.
At the production prefill chunk (1024 tokens, top-10 over 512 experts) that is
**16384 padded rows for 10240 real rows - 1.60x the necessary work**. This is now
the largest single quantified structural cost in the prefill window that is not a
kernel-instruction question, and it is recorded as the next design target rather
than as a tuning knob.

No kernel was written, no default changed, nothing promoted.

## Changes

### Mechanism, with locations

1. `hipengine/kernels/hip_gfx1100/moe/group_scatter.hip:350` - the tile map rounds
   each expert up:

   ```
   padded = ((count + tile_rows - 1) / tile_rows) * tile_rows;
   ```

   `qwen35_moe_wmma_tile_map` passes `tile_rows = 16` (`group_scatter.hip:971`).

2. `hipengine/runtime/qwen4_exp_runner.py:4122` - the production prefill path calls
   `qwen35_moe_wmma_tile_map` and reads back `wmma_total_rows` (the padded total),
   not the compact row count.

3. `hipengine/kernels/hip_gfx1100/quant/gguf_q4_k_selected_prefill.hip:924` - the
   launched grid covers the padded space:

   ```
   const int64_t row_tiles = wmma_total_rows / 16;
   ```

   `_check_common` enforces `wmma_total_rows % 16 == 0`, so the padding is not
   merely bookkeeping - it is the grid.

### Measured arithmetic

Uniform top-10 over 512 experts, `padded = 512 * ceil((tokens*10/512)/16) * 16`:

| tokens | real rows | padded rows | waste | work ratio |
| ---: | ---: | ---: | ---: | ---: |
| 256 | 2560 | 8192 | 220.0% | **3.20x** |
| 512 | 5120 | 8192 | 60.0% | **1.60x** |
| **1024 (production chunk)** | **10240** | **16384** | **60.0%** | **1.60x** |
| 2048 | 20480 | 24576 | 20.0% | 1.20x |
| 4096 | 40960 | 40960 | 0.0% | 1.00x |

The same arithmetic reproduces independently through the harness's own map builder
(`scripts/qwen4exp_moe_main_kernel_cost.py::_maps`): balanced 10240 -> 13696 padded,
balanced 1024 -> 8192 padded, balanced 4096 -> 8192 padded. (The harness's `balanced`
synthesizer spreads rows more thinly across experts than uniform top-10 does, so it
pads *more* at a given row count; the mechanism and the direction are identical.)

Waste disappears only at 4096 tokens, where each expert owns 80 rows and every tile
is full. **The production chunk size is 1024, which sits on the worst plateau.**

### Consequence for the recorded efficiency

The per-role artifact computes `gflop` from the **real** row count (10240), while the
kernel executes the **padded** row count (16384). The reported
`moe:layers.*.expert_gate` figure of 2328 GFLOP/s (6308.23 GFLOP / 2710 ms) therefore
understates the kernel's actual work by 1.60x: it is really moving **~3724 GFLOP/s**.
The kernel is closer to its roofline than the artifact implies, and the headroom that
padding removal would recover is real work that is currently being thrown away, not
inefficiency inside the kernel.

This does not change the conclusion that the kernel is far from the WMMA peak, but it
does change where the next unit should look.

### Why the obvious variants do not fix it

- **`j32` (TILE_ROWS=32)** - `selected_dual_wmma_iu8_risk_j32_prefill_bf16_bf16_out`
  is registered with a signature identical to production, but **no runtime selector
  reaches it**. It is a dead variant. It also makes padding *worse*, not better:
  at 10240 balanced rows the harness map builds 16384 padded rows at tile 32 against
  13696 at tile 16, because a taller tile raises the rounding floor for every expert.
  Taller tiles are the wrong direction under per-expert alignment.
- **The exact grouped fallback**
  (`selected_dual_grouped_rowbatch8_out4_expertgrid64_bf16_bf16_out`) processes the
  compact rows without tile padding, so it does 1.60x *less* work at this shape - and
  still loses by +19.6% to +394.9% (median +157.8%, already recorded). Its per-row
  efficiency is low enough that removing padding cannot pay for it.
- **The F16 operand route (MX-1)** is closed on both halves of its acceptance target;
  the most recent measurement puts it 2.4x *slower* than the iu8-risk owner in 8 of 8
  cases (median +138.5%). The iu8 three-plane scheme is what makes this route fast,
  not what makes it slow.

So the fix is neither a taller tile, nor the exact grouped path, nor an operand-class
change. It has to be a row space that packs tail rows from multiple experts into
shared tiles - which needs a kernel that can switch weight pointers mid-tile, or a
second tail path whose per-row cost is under 1/4 of the WMMA path's.

### Harness change (no promotion)

`scripts/qwen4exp_moe_owner_ab.py` gained a per-owner tile height
(`owner_tile_rows`) plus per-height device maps, so the two iu8-risk template heights
can be timed without either one being charged the other's padding. The added `j32`
arm is retained as a capability, not as a candidate: the padding arithmetic above
predicts it loses, and the prediction is analytic rather than measured.
