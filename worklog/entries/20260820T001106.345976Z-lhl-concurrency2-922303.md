# Extend packed-decode rowtile to rows 5/6/7 (fix c5/c6/c7 wmma collapse)

## Summary
Continuous batching needs arbitrary c=N, not just {1,2,4,8}. Measuring the
arbitrary-width curve (c3-c7) on Qwen3.8-27B-Q4_K_M showed a **collapse**:
c3 scaled fine (rowtile ROW_TILE=3) but **c5/c6/c7 fell back to the scalar
wmma GEMM** (25/29/33 tok/s, 30-40 ms/row) because the t16 dense rowtile only
covered rows {2,3,4,8}. A batch of 5 was *slower per token than a batch of 4*.
This entry extends the t16 dense rowtile (FFN gate/up dual SiLU + down GEMV)
to rows 5/6/7 so every width 2-8 uses the weight-amortized owner.

## Changes
- `gguf_t16_selected_gemv.hip`: `launch_q4_dense_rowtile` (down GEMV) rows cap
  4->7 + CASE(5/6/7); `launch_q4_dense_dual_rowtile_silu` (gate/up) CASE(5/6/7).
  The kernel template is generic over ROW_TILE (`float acc[ROW_TILE][cols]`,
  loops `row < ROW_TILE`), so the new instantiations are exact (no reassociation).
- `gguf_t16_selected_gemv.py`: `_check_dense_q4_t16_rowtile_shape` 2..4/8 -> 2..8.
- `qwen35_gguf_runner.py`: `native_batch_decode_session(2<=rows<=8)`.
- `gguf_linear.py`: sidecar-decode dispatch gate 2..8; `_q4_t16_sidecar_decode_variants`
  and `_q4_t16_dense_native_dispatch` 2..4 -> 2..7 (col4 variant kept rows<=4);
  gate/up `_q4_t16_dual_rowtile_silu_dispatch` sole_t16 rows==8 -> 2..8.
- `scripts/gguf_packed_ar_bench.py`: added c3/c5/c6/c7 configs (arbitrary-width coverage).

Conservative: c8's **down** stays on wmma (only gate/up uses ROW_TILE=8) so the
committed c8 behavior is byte-identical; the changes only ADD rows 5/6/7.

## Validation
Qwen3.8-27B-Q4_K_M, gfx1100 (W7900), `scripts/gguf_packed_ar_bench.py
--prompt-length 128 --decode-steps 8 --warmup-runs 1 --measured-runs 2`:

| cfg  | step_ms | agg tok/s | per-row ms | before tok/s | passed | repeatable |
|------|---------|-----------|-----------|--------------|--------|-----------|
| c4   | 42.5    | 95.05     | 10.6      | 94.5 (unch)  | True   | True      |
| c5   | 74.2    | 67.79     | 14.8      | 25.3 (2.7x)  | True   | True      |
| c6   | 80.6    | 75.04     | 13.4      | 29.2 (2.6x)  | True   | True      |
| c7   | 108.9   | 64.30     | 15.6      | 32.6 (2.0x)  | True   | True      |
| c8   | 116.8   | 68.61     | 14.6      | 68.6 (unch)  | True   | True      |

All prefix-exact (batch-composition invariant). c4/c8 unchanged (no regression);
c5/c6/c7 join the ~13-16 ms/row compute-bound curve. Minor non-monotonicity
(c6 13.4 < c5 14.8 < c7 15.6) is a register/tiling artifact, not a collapse.

## Next
General c=N beyond 8 (c10/c20/c26/c32) is out of scope here: the packed-decode
graph is capped at 8 rows/group, so c>8 needs multi-group scheduling (e.g.
c16=2x8, c26=8+8+8+2) + a decision on serial vs parallel group execution and
whether the FFN re-reads weights per group. See the vLLM/SGLang GEMM M-tiling
comparison in the CONCURRENCY2 follow-up.
