# The repair rate is 0.7119%: quantified corroboration for EG-3, not a reopening

## Summary

EG-3 concluded from indirect evidence that the sparse exact repair is *"limited by the
latency of its dependent memory chain"*. This packet supplies the **direct number EG-3
inferred**, and **corroborates EG-3 without reopening it.**

| quantity | value |
|---|---:|
| calls | 94 |
| outputs | 4,928,307,200 |
| risky outputs | 35,083,610 |
| **aggregate repair rate** | **0.7119%** |
| max per-call rate | 0.7797% |
| over-capacity calls | **0** |

Derived: 373,230 risky per call, 1,440 B re-read per repair, **50.5 GB** moved at an
**effective 40.9 GB/s**, 35.2 ns per repair.

## Why this confirms EG-3's mechanism

**40.9 GB/s is far below this part's memory peak**, and EG-3 already measured that moving
3.3x fewer bytes made the kernel **slower**. Together those rule out a bandwidth limit and
confirm the latency-bound dependent chain: the repair is slow because each slot's work is
a serial chain, not because it moves too many bytes.

## The prize, quantified

| route | fast | repair | ideal at fast efficiency | disproportion | saving |
|---|---:|---:|---:|---:|---:|
| q4_k (**measured**) | 2,713.953 | 573.211 | 19.32 | **29.7x** | **553.9 ms = 2.44%** |
| q5_1 (rate *unmeasured*) | 1,482.958 | 661.210 | 10.6 | - | 650.7 ms = 2.87% |
| **combined ceiling** | | | | | **1,204.5 ms = 5.31%** |

The repair does **0.71% of the work in 22.7% of the MoE GEMM time**.

**Scope discipline**: the rate is measured for the **q4_k route only**. The census's
1,234.4 ms covers q4_k *and* q5_1. The q5_1 row is an inference, and the 5.31% is a
ceiling assuming both routes match. **The defensible claim is the 2.44% q4_k row.**

## Why I did not reopen EG-3

EG-3 closed the whole "reduce per-slot scalar work" class *by measurement*, with reopen
condition "a measured mechanism (registers, instruction count, occupancy)" - all three
falsified there. **This packet adds no new mechanism.** It measures incidence and
effective bandwidth, both of which agree with EG-3's conclusion.

I want to be explicit that I considered and rejected a reopening: my first reading of
40.9 GB/s was "the access pattern is the problem, bucket the risk indices by expert for
coalescing". That is close to what EG-3 already tested - the bitmap variant hoists the
per-slot search and moves 3.3x fewer bytes - and it was **22% slower**. A latency-bound
dependent chain is not fixed by improving coalescing. Recording this so the idea is not
re-derived.
