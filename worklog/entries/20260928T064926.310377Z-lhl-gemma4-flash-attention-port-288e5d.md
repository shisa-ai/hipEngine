# the key-parallel port is issue-bound on LDS and loses without float4 vectorization

## Summary

Counting the pinned tree's instructions says the key-parallel flash port is worth
**1.3x at best and is a loss at worst**, not the ~2x its framing implied. The
whole outcome hinges on whether the compiler emits vectorized LDS for the q and k
reads, which is a microbenchmark question, not a kernel-writing question.

This was worth doing before writing 300 lines of HIP. It is arithmetic on the tree
that `20260928T100244` pinned, not a measurement, and it is presented as such.

## The count

`gemma4_warp_key_logit` gives one warp **one key**. Per lane: 8 leaf multiplies
(contraction off), 7 intra-lane adds, 5 shuffles, 5 adds, 1 broadcast -- **26
issues per key per warp**, of which 8 are the q/k loads.

Key-parallel gives lane `k` key `k`, and that lane must reproduce the entire tree
alone, because the tree is a fixed 31-pair shape over lane-partials: 32 partials x
8 leaves = 256 multiplies, then 32 x 7 + 31 = 255 adds. **511 issues for 32 keys =
16 issues per key per warp.** So in issue terms alone the port is 26/16 = **1.63x**.

That 1.63x is not the number that matters, because it omits the loads. Lane `k`
needs all `head_dim` q values and all `head_dim` k values, and **neither fits in
registers**: 256 floats for q alone against a 255-register cap. Both come from LDS,
and they are re-read for every key the lane handles -- 512 LDS accesses per key per
lane, against gemma4's 16.

| variant | issues/key/warp | vs gemma4's 26 |
|---|---|---|
| gemma4 (warp-per-key) | 26 | -- |
| key-parallel, scalar LDS | 16 + 16 = **32** | **0.81x -- a loss** |
| key-parallel, float4 LDS | 16 + 4 = **20** | **1.30x** |

So the port is a **regression** if the q/k reads compile to scalar LDS and a
**1.3x** dot-level win if they compile to float4. On the decode census's 19.1%
attention share (38.0% at 2048 keys) that is somewhere between a small loss and
about 6% end-to-end -- against an objective that needs 1.53x overall.

## Changes

No code. The entry is the arithmetic and the decision it forces.

## What this changes

The next step is not to write the kernel. It is a microbenchmark that times the
same dot two ways at this geometry and reads the generated ISA for the LDS width.
If the loads do not vectorize, the port should be dropped in favour of something
that attacks the other 81% of the step; if they do, the 1.3x is real but is a
6%-end-to-end contributor rather than a 2x one.

## Caveats, stated plainly

- These are **issue counts**, not measurements. No cycle, no stall, no occupancy,
  and no latency is modelled. The shuffle chain in gemma4 has real latency on the
  critical path, which would move the comparison toward the port; the LDS bank
  conflicts in the port would move it away.
- The 26 and 511 both assume the compiler does not hoist or CSE anything across
  keys. Hoisting q out of the key loop is exactly what registers cannot do here.
- gemma4's own LDS traffic is 16 accesses per lane per key, and its 26 issues
  already include 8 of them, so the two sides are not counted identically at the
  boundary. The table above counts issue slots for both and bandwidth only for the
  port, which is the conservative direction.

## Validation

No code and no benchmark, so no test result applies. The arithmetic is a count
over the tree that `20260928T100244` pinned and `20260928T064822` confirmed against
the kernel; it is reproducible from the two issue counts in the table. It is
explicitly **not** a performance measurement and no claim in this entry should be
read as one.
