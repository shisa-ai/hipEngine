Observed launch geometry (why the gap exists):

- `q8_0_raw_mmq128_q8_1_d4_kernel`: workgroup 32×8 (256 threads); grid =
  (out_features, 32) with out_features ∈ {96,128,160,640,2560,3072}; i.e.
  **one block per output column** × 128-token tiles — no cross-column weight
  reuse; Q8_0 weights are re-read per column.
- `gguf_k_prefill_out_coltile_rowbatch_kernel`: workgroup 128; grids
  40960×128 / 98304×128; COL_TILE=8, ROW_BATCH=4 (2560-col projections,
  512-token chunks).
- `gguf_k_selected_prefill_out_kernel<quant8>`: workgroup 128; grid
  327680×5120; block-per-output-row GEMV-class schedule at prefill shapes.

Halo-box reference geometry (`a7ad7b7f` `mmq-config-rdna3-5.cuh`, Q8_0,
`CASE(type, nthreads, occupancy, I, J, layout, K_vram, stream_k, fallback)`):
J≤48 → 128 threads, occupancy 2, I=64; J=64–112 → 256 threads, I=128;
J=128 → 256 threads, I=64; SRAM layout Q8_0, K_vram = MMQ_ITER_K. The
mechanism is **I=64/128 output rows staged in SRAM per block** versus our
single-column blocks — that is the port target for PF-1c/PF-1d.
