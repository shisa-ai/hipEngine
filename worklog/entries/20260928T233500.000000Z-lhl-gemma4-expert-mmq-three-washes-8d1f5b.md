# three levers on the down projection, all washes, and a 23.6x discrepancy that was my own arithmetic

## Summary

`20260928T231000` named the pre-aligned nibble layout as the next lever on the Q5_1 down
projection. **Reading the kernel first showed the lever does not apply**, and two further
experiments also came back flat. This entry records the three washes so they are not repeated,
corrects an arithmetic error of my own, and points at the one open question the authoritative
decomposition already names.

## The pre-aligned layout does not apply to this kernel

The Q4_K MMQ32 inner loop unpacks every weight qword before each dp4a, and the pre-aligned
layouts remove that. **The Q5_1 kernel already hoists the equivalent work out of the row loop**,
and says so in a comment at the unpack site:

> "The weight side of the dot product is the same for every row in the pass and every plane,
> so it is unpacked once here instead of per row."

So the shift-and-and that the layout port would remove is already amortized across all rows in
the pass. **Checking cost one command and saved a kernel port.** The Q5_1 case is harder than
Q4_K's anyway: it needs the four-bit nibbles *and* a fifth-bit expansion (`expand_hi_bits`)
recombined, which is more work than a nibble split and correspondingly more valuable to hoist --
which is exactly what the kernel already does.

## Two row-loop unrolls, both flat

The remaining obvious suspect was the row loop, which is not unrolled because `rcount` is
dynamic, and which carries two eight-deep serial `dot4_u8_s8` chains per row:

| row loop | GMAC/s | median |
| --- | ---: | ---: |
| not unrolled (HEAD) | 2946 / 3043 | 2.756 ms |
| `#pragma unroll 2` | 3022 | 2.687 ms |
| `#pragma unroll 4` | 2913 | 2.788 ms |

**The unroll-2 result is inside the run-to-run spread**: the same HEAD configuration measured
2946 in one run and 3043 in another, so 3022 is not a change. Unroll 4 is worse. **The kernel
is not limited by the serial chains either.** Both edits are reverted and the tree is at HEAD.

## A 23.6x discrepancy that was mine

Comparing the census's routed-expert term (320.25 ms) against the two leaves' arithmetic, I
computed 13.58 ms and a 23.6x gap. **That was an arithmetic error, not a finding.** The
decomposition's own validation line states the correct form:

```
gate_up 29 layers x 4096 rows x 2 x 2816 x 704 = 470 G over 0.156537 s = 3.00 TMAC/s
down    29 layers x 4096 rows x 2816 x 704     = 243 G over 0.103881 s = 2.34 TMAC/s
```

**4096 rows is per layer, and there are 29 layers**, and the fused gate/up is `2 x 2816 x 704`
per row rather than `2816 x 2816`. I had used 4096 rows as the whole-model total and the wrong
inner dimension. The census and the microbenches agree; there was nothing to reconcile. It is
recorded because I was one sentence from writing it up as a 24x finding.

## The authoritative picture, and the one open question

`20260928T144500` decomposes the expert block in place and is the ground truth:

| part | ms | % of step |
| --- | ---: | ---: |
| **q4k gate_up MMQ kernel** | **156.537** | 22.76% |
| **q5_1 down MMQ (dp4a)** | **103.881** | 15.11% |
| activation pack (gate_up) | 9.314 | 1.35% |
| q5_k gate_up WMMA (layer 29) | 10.271 | 1.49% |
| q5_k exact repair (layer 29) | 3.551 | 0.52% |
| activation pack (down) | 2.590 | 0.38% |
| device->host readback | 1.240 | 0.18% |
| tile map (gate_up) | 0.356 | 0.05% |
| **sum of parts** | **287.740** | **41.84%** |
| prefill wall | 687.724 | |

**The two MMQ kernels are 260.4 of the 287.7 ms; everything else in the block is 27.3 ms
between them.** So the expert MMQ is the right target, and matching llama.cpp's 1.36x there is
worth about 94 ms of the 122.8 ms gap.

**Both kernels read their weights at 49 GB/s and run at 2.3 to 3.0 TMAC/s** -- 19 percent of DRAM
peak and 8 to 10 percent of what an int8 dp4a path on 40 CUs implies. Neither axis is near a
ceiling, so the kernels are **latency-bound**, and the entry draws the inference that matters:

> The two 49 GB/s figures agreeing to 0.4 percent across two different quantizations and two
> different kernels is itself information: it says the rate is set by something shared -- the
> pass structure, the activation load path, or the launch geometry -- rather than by either
> kernel's arithmetic.

**The one open question it names is a row tile above 32 with the accumulator pressure that
implies.** `20260928T231000` measured the weight traffic side of that: four times the traffic
costs 3 percent, so the traffic is free and accumulator pressure is the only real cost. That is
the lever, and it is untested.

## One number that does not match

The down projection runs at **2.34 TMAC/s in situ against 2.95 in its own microbench**, a 21
percent gap. The microbench uses a uniform 32 rows per expert; the prefill's router does not.
That gap is unexamined and it is larger than any of the three effects tested here.
