# The decode host floor is 20 percent, so the step is not launch bound

## Summary
A decode step moves 3219.6 MB in 825.6 launches and takes 40.2 ms. That traffic
is 12.6 ms at 256 GB/s, so most of the step is not device bandwidth, and the
census has kept pointing at the launch count as the structural candidate.
Measuring the host floor settles it: **8.11 ms/token with no launches issued**,
a 123.3 tok/s ceiling.

**The step is not launch-bound.** 8.11 of 40.2 ms is 20 percent, so removing
every launch buys at most 1.26x and still leaves 8.11 ms.

## The arithmetic that decides the plan
| | ms/token | tok/s |
| --- | --- | --- |
| host floor, no launches | 8.11 | 123.3 |
| device traffic at 256 GB/s | 12.6 | -- |
| host + ideal device | 20.7 | 48.3 |
| actual | 40.2 | 24.89 |

Host plus device traffic at **peak** is 20.7 ms, or 48.3 tok/s, which is above
llama.cpp's 41.92. Parity is reachable, but only with kernels near peak
bandwidth: the host floor alone leaves less headroom than the gap, so there is no
version of this that wins on launch count.

Actual minus the host floor is 32.1 ms for 12.6 ms of traffic, so the device side
runs at about **39 percent of peak**.

## Consequence for the decode objective
The lever is kernel efficiency and multi-token steps, not fewer launches. **MTP
is the larger lever**: it produces more than one token per forward pass, so it
amortises the 8.11 ms host floor and the device-side inefficiency at once, where
a kernel-efficiency campaign has to reach near peak to close 1.68x. That is why
the next decode unit is MTP rather than a launch-count reduction or another
decoder swap -- the previous iteration already showed the dense Q8_0 decoder's
choice is neutral.

## Caveats
- The host floor and device work are measured separately and need not be
  additive: with real launches the host runs ahead while the GPU works, so 20.7
  ms is a pessimistic bound rather than a target.
- The host floor is a property of this launch structure and this host path, not
  a hardware limit.
