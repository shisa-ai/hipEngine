# Attribute the c=1 MTP cycle: the target verify window is 98% of a cycle and host phases are 2%

## Summary

Task #31, steps 1-2. The per-cycle phase timings were already measured per row
and thrown away before reaching a client: `_execution_metadata` publishes them
into `_recent_completed_routes`, which `observability_snapshot()` returns and the
server's readiness/Prometheus consumers discard, while the client-facing
`specdec2_mtp2` block carried only counts. They are now published on the served
path (accounting block, `speculative_mtp.cycle_timing_ms`, routing-pass row), so
the split below needed no profiler run and no route-equivalence argument.

Measurement (dense 27B Q4_K_M, gfx1151, production profile, cache off, c=1,
candidate budget 3, 4 ShareGPT conversations x 4 turns, 16/16 rows engaged,
`benchmarks/results/2026-09-20-gfx1151-q4km-mtp2-cycle-phase-split-c1.json`):

| phase window | ms/cycle | share |
| --- | --- | --- |
| `target` (verify pass) | **110.67** | **98.13%** |
| `provider_update` | 1.24 | 1.10% |
| `proposal` (draft) | 0.88 | 0.78% |
| `accept`, `accept_enqueue`, `accept_tail`, `accept_upload`, `selected_commit`, `target_readback`, `candidate_readback` | 0.00 each | 0.00% |
| **sum** | **112.78** | |

Independently observed decode wall per cycle (`itl_median_ms` x in-cycle tokens /
cycles): median **110.76 ms** (min 107.86, max 113.79). Phase sum / observed wall
= **1.018**, so the instrumented phases account for the whole cycle rather than a
fraction of it. Median 36.05 ms/token ITL, 2.09 accepted drafts/cycle.

## What this settles, and what it does not

- The withdrawn hypothesis ("the MTP gap is mostly Python host cost") is now
  measured at c=1 and is **false as stated for the host phases that are
  instrumented**: proposal + provider update + the whole accept chain total
  ~2.1 ms of a ~111 ms cycle (~1.9%). #25's priming/activation rewrite operates
  entirely inside that 2 ms, so it cannot move c=1 throughput.
- The dominant component is the **target verify window**. That window is host
  wall around the verify pass, so it contains the device work of verifying
  1+K = 4 rows plus whatever synchronization sits inside it. It is *not*
  device-busy time, and this measurement does not split it. The accept-side
  readback windows (`target_readback`, `candidate_readback`) are 0.00 on this
  route, so no readback cost is separated out here either.
- The magnitude is consistent with a weight-streaming-bound verify: ~111 ms for
  4 rows against an AR step of ~83 ms at c=1 is ~1.33x an AR step for ~3.1
  tokens/cycle. That is a roofline-shaped statement, not a kernel measurement.
- Therefore the remaining question in #31 step 3 is exactly one thing: inside
  the target window, how much is device-busy versus synchronization/idle. That
  needs markers or a profiler run against *this* route, and it is the only
  remaining gate before any optimization target is named.
