# VibeVoice-TTS: fused DPM-Solver++ step kernel (bit-exact)

## Summary

A new device kernel `vv_diff_dpm_step_bf16` performs one DPMSolver++
order-1/order-2 midpoint update on-device in the fork's eager rounding order.
It is bit-identical to the numpy CPU solver over the full 20-step schedule
(60/60 steps across 3 seeds, comparing both the returned sample and the
per-step `x0`), is registered in the four-axis registry, and carries a RED
test.

It is **not yet wired into the runtime**, and this entry makes no performance
claim. `sample_speech_tokens` still runs the solver on the host.

## Changes

- `hipengine/kernels/hip_gfx1100/vibevoice/diffusion.hip` — the kernel and its
  `extern "C"` launch wrapper.
- `hipengine/kernels/hip_gfx1100/vibevoice/diffusion.py` — the ctypes host
  wrapper `vv_diff_dpm_step_bf16`, `_ARGTYPES_DPM_STEP`, and a new `_I32`
  (`ctypes.c_int32`) alias.
- `hipengine/kernels/cpu_reference/vibevoice_tts_diffusion.py` — a new
  read-only `DPMSolverMultistepScheduler.step_scalars()` exposing the per-step
  bf16-rounded scalars without advancing scheduler state, plus a module-level
  `_scalar()` helper.
- `hipengine/kernels/vibevoice.py` — `vv_diff_dpm_step_bf16` added to
  `PRIMITIVES`; registration is automatic from that tuple.
- `tests/test_live_vibevoice_tts_diffusion_gpu.py` — new RED test
  `test_gpu_dpm_step_kernel_matches_cpu_solver`, plus the kernel added to the
  registry-resolution test.

`step_scalars()` exists because the kernel needs the per-step scalars on the
host (0-dim FP32 values derived from `sigmas`), while
`_first_order`/`_second_order` compute them inline while consuming
`model_outputs`. It reproduces the same values without touching `_step_index`,
`lower_order_nums`, or `model_outputs`, so the device path and the numpy
oracle share one source of truth. Instrumented comparison at order 2 confirms
`scale`, `coef_b`, `half_coef_b`, and `inv_r0_b` are identical to what the
reference uses internally.

Two bring-up bugs were found by comparing the kernel against a strictly-FP32
numpy emulation of the same expression tree, not by inspection:

1. **`mode` vs `order` semantics.** The kernel branch was `if (mode != 0)`,
   but the wrapper passes the scheduler's `order` (1 or 2) directly, so
   `order == 1` took the *second-order* path. The branch is now `if (order > 1)`.
2. **`int` vs `int64_t` argument width.** `mode` was declared `_I`
   (`ctypes.c_int64`) while the kernel declares `int mode`; the 8-byte value
   spilled into the adjacent `stream` argument slot. Now `_I32`.

## Validation

The kernel is bit-identical to `DPMSolverMultistepScheduler.step` over the full
20-step schedule, comparing the returned sample and the intermediate `x0` at
every step: 3 seeds x 20 steps = 60 steps, **0 mismatches**.

The committed RED test asserts per-step `x0` equality, per-step sample
equality, and that the schedule exercised both solver orders (`{1, 2}`), so the
second-order path cannot silently go untested.

```bash
uv run pytest tests/test_live_vibevoice_tts_diffusion_gpu.py \
  -k "dpm_step or registry" -p no:cacheprovider -q
```

Result: `2 passed`.

## Next

Wiring the kernel onto the default path is a separate, larger unit and is
unmeasured.

`VibevoiceTTSDiffusionHeadGPU.forward()` takes host `x_bf16_u16` and uploads
it with `copy_host_array_to_device`. Fusing only the solver step while leaving
`forward` host-facing would remove the host arithmetic but reintroduce a D2H
of the post-step latent every step, so the win would be small. The useful
change is to give the head a device-input/device-output entry point and run
the CFG combine (`vv_diff_cfg_combine_bf16`, already registered and bit-exact)
plus the solver step entirely on device, leaving one D2H per frame.

1. Add a device-input/device-output head entry point.
2. Rewrite the `sample_speech_tokens` loop to keep `speech`, `eps`, and
   `x0_prev` device-resident.
3. Re-run the full-parity GPU tests and the RTF harness, and only then record
   a performance claim against the RTF 1.228 baseline.

No default path changed, so no benchmark rollup update is required for this
entry. `docs/REFACTOR.md` does not need an entry yet: this is an unused
primitive with a RED test, not a default-off flag or fallback chain. If the
wiring above is not done, it should be revisited there.
