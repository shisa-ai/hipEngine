## Why this clears neither gate

**P2 option (b) — head_dim-512 image.** The 0.14 performance tables that show
`d_head = 512` are for **gfx950 and gfx1201**, not gfx1100. The bundle for
gfx110x exists; whether it contains an hdim-512 `attn_fwd` image is exactly
what the vendored inventory lacked and what release notes do not say.
Confirmed by listing the bundle, not by reading about it.

**P1 — window alignment.** No release note read here claims any change to
how integer window bounds are aligned. P1's blocker was established by
measurement — four candidate masks discriminated at
`rows=512 keys=1536 window=128`, with `top_left_window` matching at maxabs
0.0078 and the alternatives missing — and a release note cannot overturn a
measurement. P1's own clearing command is the test: install a runtime whose
windowed images take absolute or bottom-right bounds, **re-run that same
comparison to confirm the alignment flipped**, then restore the plumbing.
Nothing found here says that test would now pass.

## The upgrade is not free

The 0.14 notes state API stability plainly: *VarlenBits supersedes
VarlenType*, and ABI compatibility is only promised **from 0.13b onward** —
"applications targeting 0.13b can upgrade to 0.14b as a drop-in." hipEngine
sits at 0.11.2b, which is outside that promise, so 0.11 → 0.14 crosses at
least one API break and is not the drop-in a 0.13 → 0.14 reading would
suggest. That belongs in the estimate for whoever takes the upgrade.
