# The active decode traffic is 3.50 GB per token, and decode runs at 31 percent of peak
## Summary
Every bandwidth reading I have recorded this session rested on an **assumed**
2.25 GB of active weights per token. That assumption was wrong. Measuring the
traffic from the artifact's own tensor offsets gives **3.50 GB per token**, which
changes the conclusion about how far decode is from peak.
## How the number is obtained
The 658 tensors are sized from their **data-offset deltas** rather than from a
quant-size table. That matters: the first attempt used a hand-written table and
produced a 26.19 GB total against a 17.01 GB file, which is how the error was
caught. Summing offset deltas reproduces the file size exactly, so the sizing is
anchored to something checkable.
| quantity | value |
| --- | --- |
| file size | 17.01 GB |
| expert (rank-3) tensors | 14.42 GB across 60 tensors |
| **active per token** | **3.50 GB** |
The 60 rank-3 expert tensors are scaled by
`expert_used_count / expert_count = 8 / 128`; everything else counts in full.
Metadata read from the artifact confirms those values: `gemma4.block_count = 30`,
`gemma4.expert_count = 128`, `gemma4.expert_used_count = 8`,
`gemma4.expert_feed_forward_length = 704`, `gemma4.feed_forward_length = 2112`.
## The corrected readings
| | tok/s | ms/token | GB/s | share of 256 GB/s |
| --- | --- | --- | --- | --- |
| hipEngine, short context | 22.38 | 44.68 | **78.2** | **31%** |
| hipEngine, 512 context | 20.03 | 49.93 | **70.0** | **27%** |
| llama.cpp, same host and artifact | 41.92 | 23.85 | **146.5** | **57%** |
## What this corrects
Two committed figures are withdrawn:
- The withdrawn decode profile's **18 percent** of peak.
- The decode context-scaling entry's **20 percent**, in a block that called
  itself "arithmetic on two measured numbers". The *inputs* were not both
  measured: 2.25 GB was derived from a guessed bits-per-parameter figure.
Both were built on the same wrong 2.25 GB input and were wrong by 1.55x.
The artifact now carries a `CORRECTED` block with the corrected values and the
basis, so the wrong figure is not left standing in the record.
## Why the corrected reading matters more, not less
The headroom is **1.87x, not 5x**. That is a better-grounded target than the one
I had, for a concrete reason: **146 GB/s is not a theoretical ceiling, it is what
llama.cpp already achieves on this host and this artifact.** So the decode target
is "stream the same bytes at 57 percent of peak instead of 31", which is a
statement about kernel efficiency rather than about an unreachable roofline.
It also removes a hypothesis. At 31 percent of peak there is no case that decode
is reading redundant data; the traffic is within 1.0x of the minimum the model
requires. The gap is how efficiently those bytes are streamed, not how many.

## Validation
- The sizing is anchored: summing offset deltas over all 658 tensors gives
  17.01 GB, equal to `os.path.getsize` on the artifact. The first attempt's
  26.19 GB against the same file is what exposed the bad table.
- The expert scaling uses `expert_used_count` and `expert_count` read from the
  artifact's own metadata, not assumed.
- The tok/s and ms/token columns are the previously measured, warm, untraced
  figures; only the byte input changed.
- No production code changed, so no correctness gate applies. No new performance
  claim is made: this corrects a derived quantity and the claims resting on it.
