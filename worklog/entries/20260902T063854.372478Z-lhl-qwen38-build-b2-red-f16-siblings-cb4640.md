## Mechanism correction (design recon)

The Z1 "F16 activation-B" label came from Laurent's Vulkan pipeline where
activations enter F32 and F16 staging halves bytes. hipEngine activations
are already BF16 (16-bit), so an FP16 encoding alone is byte-neutral. The
concrete in-tree mechanism: load_compact_row_half16<half_t> in
gguf_k_t16_selected_prefill.hip takes one vectorized 32-byte load while the
BF16 path converts per element per use for WMMA operands. An F16-staged
activation operand (cast once, vector-loaded per tile) removes those
converts. All dense kernels template on scalar_t already (verified at
gguf_k_t16_selected_prefill.hip:1739/1850), so each sibling is a new
instantiation plus Python wrapper, not a kernel rewrite. The selected
dual-wmma family already ships fp16_in wrappers (compact path), proving the
plumbing; the dense sole-T16 owners are bf16-only today — exactly the
blocker artifact's claim.
