# Refill physical MTP provider groups

## Summary

Fix staggered physical SPECDEC2 arrival so a newly ready request refills an
existing compatible max-capacity NextN provider group. Previously the adapter
looked only at groups already named by the current physical plan. If requests
became decode-ready on separate ticks, each opened a separate provider; their
first joint frontier then rejected `physical NextN proposal requires one
provider group` and recovered to AR before target work.

A diagnostic W7900 C2/K1 run now reaches physical proposal, R4 target, GPU
accept/selected commit/provider repair exactly with zero hot allocation. It is
not an economics win or capability promotion: D8 staged wall is `1.716 s`
versus `0.864 s` true AR, and only one of eight proposed drafts is accepted.
Both gfx1100 physical capability constants remain false.

## Changes

- RED-test sequential physical admission with one existing max-capacity provider
  group and one newly ready request.
- Reuse any compatible provider group with sufficient executor capacity before
  opening a new batch group in `_ensure_request_states()`.
- Preserve existing same-plan group validation, explicit refill-capacity error,
  singleton C1 open, and new-group fallback.
