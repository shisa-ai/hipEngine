# Take key-sliced flash decode from 256 keys in the gfx1100 production plan

## Summary

W7900 decode was slower at 512 prompt tokens than at 256 or 1024 (76.4, 70.4
and 76.6 tok/s through the campaign bench). A depth sweep in one process shows
why: below 1024 keys a decode step runs the single class attention kernel,
which walks its keys serially per head, so the median step grows from 12.06 ms
at 64 prompt tokens to 15.64 ms at 960; at 1024 keys the split policy hands the
step to the key-sliced flash kernel and it drops to 12.90 ms.

The gfx1100 production plan already selects the `gemma4_flash` decode variant
for the long global row. That preference now also takes a one-token step on
either packing from `FLASH_DECODE_PREFERRED_MIN_KEYS` = 256 keys (the two
routes cross near 192; flash is ahead from 256). Strict, and any plan without
the flash decode variant, keep the single kernel below 1024 keys. The gfx1151
plan declares no decode scope, so nothing changes there.

Public path, W7900, production, BF16 KV, 128 outputs, one warmup and five
samples, `scripts/gemma4_campaign_bench.py`, before against after in the same
session: decode 72.62 -> 76.85 tok/s at 384 prompt tokens (1.058x), 70.50 ->
76.51 at 512 (1.085x), 66.12 -> 75.93 at 768 (1.148x), generated ids equal and
`public_path_parity` true. 1024 and 8192 are outside the changed band and read
76.36 and 69.52 (three samples, no before arm in this run).

Section 2.11 packet on the W7900, 18 cases and 1,134 teacher-forced rows at
prompt depths 257-897 (keys 257-961), strict arm with the entry held above
1024: median row KL 7.7e-7 (bar 1e-3), p90 1.9e-3 (2e-2), flip-damage 0.35%
(3%), top-1 99.12% (96%); every category inside its bars; repeats, isolation
and task checks pass on all 18.

## Next

- Unresolved: between 2% and 20% of decode steps, varying run to run, take
  about 3.4 ms longer than the rest (near 16 ms against 12.6). Timing every HIP
  API call inside a step shows the final blocking copy waits the same 1.3-1.4 ms
  in fast and slow steps, so the extra time is on the host side of the step,
  in kernel launches or Python. Disabling or freezing Python garbage
  collection, `ROC_ACTIVE_WAIT_TIMEOUT` at 1,000 and 20,000, and pinning the
  process to one core or four each left it in place. `HSA_ENABLE_INTERRUPT=0`
  makes most steps slow. A GPU monitor was polling the device throughout and
  was not stopped; that is untested.
- The same timing shows the host spends about 11.4 ms of a 12.8 ms step
  launching roughly 500 kernels, with the device finishing 1.4 ms behind it.
  Replaying the step from a captured graph measured no gain here, so host and
  device are close to balanced and either alone will not move decode much.
