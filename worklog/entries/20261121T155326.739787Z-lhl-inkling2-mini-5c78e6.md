# Audit Loom Inkling prefill and matched benchmark target

## Summary

The published Loom Inkling program batches the stateful GPU work that hipEngine still submits per token. Start with causal short convolution and KV/attention; measure dense and routed-expert weight reuse after those paths are batched.

## Changes

- No runtime changes. Audited [Loom package `277f099b`](https://huggingface.co/loom-fun/unsloth-Inkling-2-Mini-loom/tree/277f099b5003b725e099d48caa1a2c0db1f9b650), whose source weights are Unsloth `UD-Q4_K_XL` at `ea0c79b2ecd73669e774c8519b79bfabfddbc027`.
- [`program/llm.loom`](https://huggingface.co/loom-fun/unsloth-Inkling-2-Mini-loom/blob/277f099b5003b725e099d48caa1a2c0db1f9b650/program/llm.loom#L45896) launches block convolution against the previous history and commits the new history separately. The local attention path stages current KV separately from the rolling cache, runs tiled causal attention, then commits the ring. That order prevents a prompt block from overwriting older KV still needed by its early rows. hipEngine already separates state by loop visit and keeps provisional DSpark rollback; preserve both when batching.
- The program also fuses RMS normalization with row preparation, tiles the loop controllers and expert router across rows, and uses matrix instructions for prefill projections. These are candidates for hipEngine, not drop-in replacements: packed weight formats, activation arithmetic, and the device memory layouts differ. The existing HIP expert path already batches launches, not necessarily weight reads across rows. Its output convolution already consumes the device result before readback; retain that ownership when batching.
