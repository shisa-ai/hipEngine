# fused gate/up silu shard route promoted to tp2 default

## Summary

Packet 3's MLP shard chain now resolves its gate/up route through the same
shape-qualified fused decode policy the TP1 runner uses - never a hardcoded
variant name. The qwen35/`MOSTLY_Q4_K_M` policy row carries the shard shape
(1, 5120, 8704) under the gate the full-width shape used: the kernel's own
pure shape contract already admitted it (`dense_t16_pair_decode_shape_error`
-> null), and the slice probe measured the fused candidate bit-identical to
the unfused chain on both ranks of the hardware pair with faster device
chains (246.9 vs 307.2 us; the one-block walls were 335.6 vs 401.6 us).

Full-model result: decode p50 53.12 -> 50.65 ms/token at the matched
composition, production gates identical to every prior retained run to all
recorded digits (teacher-forced mean KL 6.425e-04, max KL 5.246e-03, top-1
100% vs both controls; both TP1 controls bit-identical; TP2 repeat
bit-exact). Exchange protocol unchanged (compiled driver, 9,216 reductions).

Also recorded as an analysis decision, not a probe unit: sharding
attention/GDN weights (Packet 3 step 2) is a no-go for the single-token
eager schedule. Each block's output projection (attn_output, ssm_out) is a
row-cut reduction point, so full attention+GDN sharding adds 64 in-schedule
exchange waits per token (at the measured 156-169 us p50, about +10 ms)
against at most ~4-5 ms of W7900 weight-read savings (~24% of 16.5 GiB
replicated bytes halved). Revisit only when the schedule amortizes
collectives - the batched/graphed TP2 schedule, which is also the dominant
wall's recorded lever: the compiled-exchange e2e stage attribution shows
~36.5 ms/token of host time submitting the two ranks' attention/GDN launches
against ~20 ms of device weight reads, so the host enqueue path, not device
work, is the critical path.
