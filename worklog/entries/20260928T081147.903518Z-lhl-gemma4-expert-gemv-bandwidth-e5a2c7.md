# the decode expert route runs an MMQ32 prefill kernel and the pack8 decode route is never selected

## Summary

Following `22d80e1c7`, which found the isolated expert GEMV at 17-21% of peak, I
traced which kernel the decode default actually issues and found two things worth
measuring.

**The decode default runs a prefill kernel.** `gemma4_project_experts_gate_up_mmq`
for `gguf_q4_k` dispatches to
`gguf_q4_k_selected_dual_q8_1_ds4_mmq32_fused_prefill_compact32_bf16_bf16_out`,
whose name is explicit about being the MMQ32 prefill path. Around that call it
also packs the activations (`gguf_q8_1_mmq_ds4_pack_bf16`) and performs a
`copy_device_to_host`. A device-to-host read in the decode path is a
synchronisation point, and the route still won its A/B by 9.7%
(`ba97b2cd6`), which says the alternative it beat was worse rather than that this
is good.

**A third decode route is never reached.** `gemma4_project_experts_rows`, the
route dispatcher, documents a preference order in which `pack8_selected` (route
2) ranks *above* `selected_gemv` (route 3), and both are "the same launch shape
over the same arithmetic, differing only in which representation of the weight
they read". Route 2 is "reached only for a weight the planner gave the packed
arrays", and `hipengine/runtime/gemma4.py` contains **no reference to the packed
layout at all**. So on the real path route 2 cannot be taken and the packed
representation is never built.

That matters because `22d80e1c7` measured the two representations on identical
shapes at identical thread counts and the packed one is **1.25x faster** -- 54.0
GB/s against 43.4 GB/s on Q4_K gate/up. The dispatcher already prefers it. It is
not being offered the choice.

This is a **candidate, not a defect**. The MMQ route is the measured winner of the
one A/B that exists (`ba97b2cd6`: 27.3144 against 24.8987 for uniform grouped),
and nothing here shows `pack8_selected` beating it -- `pack8_selected` has never
been run as a decode route at all. The claim is narrower: there is a
dispatcher-preferred decode route that the runtime never selects, and its kernel
is 1.25x faster than the sibling kernel the non-MMQ route used.

## Changes

None. No source file changed. This entry records a dispatch trace and connects it

## Validation

Read from `hipengine/kernels/hip_gfx1100/gemma4/gemma4_experts.py`:

- `gemma4_project_experts_gate_up_mmq`, the `gguf_q4_k` branch, imports
  `gguf_q4_k_selected_dual_q8_1_ds4_mmq32_fused_prefill_compact32_bf16_bf16_out as
  mmq_gate_up` and `gguf_q8_1_mmq_ds4_pack_bf16 as pack_activations`, and the
  surrounding body takes `copy_device_to_host` from `hipengine.core.memory`.
- `gemma4_project_experts_rows`' docstring lists the preference order and states
  route 2 "is reached only for a weight the planner gave the packed arrays", with
  routes 2 and 3 differing "only in which representation of the weight they read".
- `grep -n "packed\|pack8" hipengine/runtime/gemma4.py` returns nothing, so no
  code on the runtime path requests the packed layout.

The 1.25x is from `22d80e1c7`'s probe run, `selected` 43.4 GB/s against
`selected_pack8` 54.0 GB/s at `--rows 8`, `in=2816`, `out=1408`, 128 experts, the
same shapes and thread count for both.

Not verified here: whether the packed layout can be built for this artifact's
expert weights, what it costs to build, or what `pack8_selected` achieves as a
full decode route. None of those are established by this entry.
