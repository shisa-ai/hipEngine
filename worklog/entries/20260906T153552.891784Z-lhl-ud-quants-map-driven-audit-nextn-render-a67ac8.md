# ud-quants-map-driven-audit nextn text rendering repair

## Summary

Resolved the consolidated U0b review finding P2 against
`scripts/gguf_quant_route_audit.py` (follow-up to
`worklog/entries/20260906T133705.818212Z-lhl-ud-quants-map-driven-audit-39649e.md`).
The default CLI text printed a single unscoped `validation=` word — actually the
AR map's verdict — plus per-slot `nextn ... rejected=0` counts, so an
independent NextN map validation failure or construction error was invisible in
the default text even though the JSON captured it. A reader could take
`validation=passed` + `rejected=0` as the draft being admitted. The repair is
print-only: JSON schema and all computed sections are unchanged.

## Changes

- `scripts/gguf_quant_route_audit.py`:
  - Extracted the tensor-map text summary into
    `_print_tensor_map_summary(tensor_map)` and rescoped the verdicts: the main
    line now prints `ar_validation=passed|FAILED (diagnostic)` (was the
    ambiguous `validation=`), and a dedicated NextN line reports the NextN
    map's own state — `nextn map: validation=passed|FAILED (diagnostic)
    block_id=... own_slots=.../... fallback_slots=...` when built,
    `nextn map: NOT BUILT (diagnostic only; nextn routes withheld): <error>`
    when construction raised, and `nextn map: not applicable (no AR-excluded
    trailing MTP block in this file)` when the file has no NextN block by
    design (no invented failure).
  - NextN validation details are printed when present: `nextn missing:`,
    `nextn unexpected:`, `nextn dtype:`, `nextn shape:` preview lines (first 4
    items + `(+N more)`), covering the missing/type/shape/unexpected error
    classes of the finding.
  - NextN route scope lines are labeled
    `[map validation FAILED; diagnostic only]` whenever the NextN map's
    validation failed (`nextn.diagnostic`), so zero per-slot planner refusals
    (`rejected=0`) can no longer read as map admission or consumer
    qualification. When construction failed there are no nextn route lines at
    all; the AR verdict, alias lines, and full AR route table are preserved in
    every NextN failure mode.
- `tests/test_scripts_gguf_quant_route_audit.py`: added a byte-level all-F32
  qwen35 CLI fixture helper (`_qwen35_byte_file`, reusing `_QWEN35_METADATA`,
  `_ar_layer_tensors`, `_nextn_block_tensors`, `_t`, `_header`, `_kv`,
  `_aligned`; F32 because real quant block layouts cannot exist at hidden=8,
  and the AR map validates structurally so AR validation still passes while
  NextN dtype expectations surface diagnostically) plus four tests driven
  through actual `main`/capsys or the extracted helper: missing required NextN
  tensor (CLI), NextN map-construction failure (CLI, monkeypatched
  `build_qwen35_gguf_nextn_tensor_map` — the established error-branch pattern
  of `test_planner_qualification_error_is_reported_not_raised`), absent NextN
  block (CLI), and the fully valid NextN state (helper-level with the real
  `_mapped(_fixture_tensors())` section).

## Limitations

- The valid-NextN state is covered at helper level rather than through a
  byte-level CLI file: a CLI file whose NextN map validates clean would need
  real quant block layouts (Q4_K/Q6_K need 256-element inner dims), i.e. a
  hidden=256 fixture — deliberately out of scope for this print-only repair.
- The construction-failure CLI case is driven by monkeypatching the NextN map
  builder (deterministic, matches the file's existing error-branch test
  pattern); the only real-data construction-failure path found (native-XL
  quant variant over a MoE architecture) would require a full MoE fixture and
  is not exercised here.
- The `nextn dtype:` detail line prints tensor-level strings from the NextN
  validation as-is; line length is unbounded for many errors beyond the 4-item
  preview (preview truncation bounds it in practice).
