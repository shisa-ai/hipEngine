# Repair concurrent MTP prompt activation, and classify every routing setting

## Summary

Two separate blockers sat behind the c>=4 failures reported in
[`20260917T162126.651176Z`](20260917T162126.651176Z-lhl-sharegpt-mtp-routing-pass-8d7978.md).
Only one of them was a bug.

**The bug, now fixed: a chunked prefill held the MTP prompt activation across
ticks, and a second request's activation raised inside the driver thread.**
`Qwen35GGUFMTP2Adapter.begin_prompt_streaming` allowed one prompt activation at a
time because the activation primes shared provider state, and it released that
claim only at the request's final prefill chunk. `max_prefill_chunk_tokens` is
256, so every prompt longer than that kept the claim open across ticks - which
made the "already reserved" assertion reachable by ordinary concurrency rather
than a programming error. The raise escaped `_prefill_native_chunk`, killed the
driver thread, and `_fail_all` closed the service; every later request was told
to lower `--max-context-tokens` for a state bug.

The guard now refuses only the rows that are not already streaming, records
`prompt_activation_in_flight` on them, zeroes their candidate budget (a request
whose first chunk missed the sink cannot prime a provider later in its prompt),
and keeps the engine alive. Rows that already hold a sink are carried through the
same call, so a mixed batch can no longer strand an open activation.

Measured on the same protocol as the failing pass (`gfx1151`,
Qwen3.8-27B-Q4_K_M, ShareGPT loader, 128-output override, default
configuration):

| arm | before | after |
| --- | --- | --- |
| harness c=4 | 4 completed, 20 failed | **24 completed, 0 failed** |
| `vllm bench serve` c=4 | 8 / 16, 8.70 output tok/s | **24 / 0, 28.39 output tok/s** |
| `vllm bench serve` c=8 | 11 / 21, 8.71 output tok/s | **32 / 0, 27.23 output tok/s** |
| driver tracebacks | one per server lifetime | **0** |
| four concurrent ~330-token prompts | service closed | 4 of 4 completed, 0 tracebacks |

**The capability gap, now classified: MTP does not run for most concurrent
requests, for two recorded reasons.** The serving evidence row for this cell is
`cap4-realized-c1-b3`, which matches only `realized_group_rows == 1`; a request
admitted while it is alone is later batched into a wider decode group and
silently realizes `effective_route="default"`. And a group that mixes rows with
and without a draft provider fails closed before provider mutation. Neither is
fatal, both are visible per request, and both are recorded in
[`docs/REFACTOR.md`](../docs/REFACTOR.md). 5 of the 24 c=4 requests did run MTP
(three covered 127 of 128 tokens at depth 3), so the path is reachable under
concurrency but not reliable.

## Settings classification (one request per setting, live server)

The task asked which settings silently keep real requests off the MTP path. Each
row below is one request against a default-configuration server with the same
prompt and 64-token budget, reading `generation_shape.route` /
`route_decision` and `speculative_mtp.effective_route` / `used`.

**Not blockers (verified):** thinking enabled or disabled (24 of 24 ShareGPT
requests streamed a thinking block and all ran MTP); `stream=true`; explicit
`temperature=0.0`; `top_p` at 0.9 or 1e-8; `top_k=50`; `seed=42`;
`repetition_penalty=1.0`; `presence_penalty=0.0`; output room down to 2 tokens;
auto candidate budget (depth 3, honoured per request); prompt length to 841
tokens (the 1,023-token window never bound).

**Capability gaps (recorded, not fixed):**

| Setting | Route effect | Why it is a real gap |
| --- | --- | --- |
| `temperature > 0` | `sampling_mode_not_qualified`, 7.9 s against 2.9 s with MTP | the verifier accepts a draft when it matches the target's greedy token, which is not the sampling distribution; correct speculation needs a rejection test |
| `logprobs` / `top_logprobs` | same refusal, 6.7 s against 2.9 s | selection is unchanged under greedy, but the verified positions must expose the top-k logits the response contract promises |
| `logit_bias`, non-identity penalties | same refusal, 5.5 s against 2.9 s | processors change the selected token, so the verifier would have to apply them at each verified position |
| `ignore_eos=true` | same refusal, 5.5 s against 2.9 s | cycle termination and stop semantics are not wired for a request that must not stop on EOS |
| multi-token stop sequences | same refusal, 5.5 s against 2.9 s | a cycle can cross a stop sequence inside the cycle, so the commit path would have to trim to the boundary |

`temperature > 0` is the largest of these in practice, because it is what real
clients send most often.

**Not a bug after all:** `min_tokens` alone is rejected with `min_tokens requires
eos_token_id`, which is a coherent validation chain (`eos_token_id` is itself
incompatible), not a silent downgrade. And the response contract already
distinguishes selected from realized routing - a refused or downgraded request
reports `effective_route="default"` with `used=false` and a specific
`fallback_reason` next to `selected_route="speculative_mtp"`. The first pass read
as a route that lied only because the recorder did not capture `effective_route`.

**Documentation inconsistency:** `stop_token_ids` is listed in
`SPECULATIVE_MTP_INCOMPATIBLE_CONDITIONS` but the API rejects the parameter
outright with HTTP 400 `unsupported_parameter`, so that condition is unreachable
through the OpenAI surface.

## Changes

- `hipengine/generation/qwen35_gguf_mtp2.py`: `begin_prompt_streaming` splits the
  requested ids into rows that already hold a sink and rows that do not, applies
  every admission check to the new rows only, and turns the activation conflict
  into a reported refusal. The claim id, prompt-row units, provider capacity and
  group key now describe the rows actually being activated.
- `tests/test_unit_qwen35_gguf_mtp2_seam.py`:
  `test_mtp2_prompt_activation_in_flight_refuses_only_new_rows` covers the
  refusal, the untouched open activation, the mixed call, provider reuse after
  release, and re-activation after the claim is freed.
- `docs/REFACTOR.md`: the conservative refusal, what would replace it, and the
  exactness gate that replacement needs (generated-token equality plus
  non-collapsed acceptance, because a corrupted draft provider lowers acceptance
  rather than changing accepted tokens); plus the wider-realized-width evidence
  gap.
- `benchmarks/results/2026-09-17-gfx1151-qwen38-sharegpt-mtp-routing.json`: the
  before/after arms and the settings classification above.

## Next

- Wider realized widths need their own measured serving-evidence rows before MTP
  can be admitted at c>1, and mixed K/K0 groups need a declared partition instead
  of failing closed. Both are in `docs/REFACTOR.md`.
- Non-greedy sampling is the largest lost opportunity on the routing side and is
  a math unit (speculative sampling), not a settings fix.
- The recorder should capture `effective_route`, `selected_route` and the
  in-stream error body so the next pass reports the realized route directly.
