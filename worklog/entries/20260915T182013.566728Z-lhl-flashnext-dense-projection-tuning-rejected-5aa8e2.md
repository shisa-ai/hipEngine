# Flash-Next per-operation prefill cost; dense projection tuning rejected

## Summary

Every operation in the 4096-token `code-p4096` prefill now has a measured cost
and a real shape, and the first experiment on the largest identified projection
came back negative: **the dense projection cannot be made substantially faster by
tuning.** The tile-shape design space is exhausted and the kernel's own
instruction mix caps it at 22.1% of FP32 peak, against 8.9% measured.

Corrected two numbers that were being used as fact. The FP32 peak for
percent-of-peak was **14.8 TFLOP/s**, which is neither this machine's FP32 rate
nor its BF16 matrix-core rate; the measured hardware is gfx1151 (Radeon 8060S,
Strix Halo APU, 40 CUs at 2.9 GHz) whose FP32 peak is **29696 GFLOP/s**. That
halves every previously published percentage. Separately, the production
`attn_qkv` instantiation was misidentified from its kernel name alone.

## Findings

**Cost by operation, 22046 ms total.** matmul 14368 ms (65.2%), non-matmul
6308 ms (28.6%), risk/repair 1370 ms (6.2%). By family: `linear` 10553 ms
(47.9%), `moe` 6599 ms (29.9%), `gr_read` 2539 ms (11.5%), `qsa_prefill`
1421 ms (6.4%), `gdn` 824 ms (3.7%).

The MoE block decomposes into gate+up 2710 ms, down 1588 ms, repair 1370 ms
(20.8% of the block) and routing/scatter/reduction 931 ms. Repair is not a small
share of this block.

**Every dense projection runs through one kernel family.** `linear:` roles are
10553 ms, of which 10070 ms is
`gguf_k_prefill_out_coltile_rowbatch_kernel`. That family runs at 2650 GFLOP/s =
8.9% of the 29696 GFLOP/s FP32 peak.

**The tuning path is exhausted.** Sweeping all seven registered coltile/rowbatch
instantiations on identical operands across five real GDN layers (0, 9, 22, 34,
46) and row counts 1/8/64/512/1024, with weights rotating per layer: production
is already the fastest, the next best is 12–14% slower. The kernel has 0 spill
bytes and sits at the register-only occupancy maximum (≤16 waves/SIMD at 72
VGPR), so neither spills nor occupancy is the limit.

**The limit is the instruction mix.** The inner loop is 145 instructions per
k-iteration, of which 40 are FMA-class (27.6%). The 105 non-FMA instructions are
32 dequantization, 26 address arithmetic, 15 `s_waitcnt`, 7 `s_delay_alu` and
the rest control flow. That fixes the design's ceiling at 6554 GFLOP/s = 22.1%
of peak. Measured is 8.9%, i.e. **40% of the design's own ceiling**; the missing
60% is memory-latency stall. About 2.5x is recoverable within the design by
hiding stalls; the remaining ~4.5x needs the 72.4% of non-multiplying issue slots
reduced, which tiling cannot do.

**Correction: the production instantiation is the wave-scale one.** `WAVE_SCALE`
is a template parameter, so both instantiations share the kernel name
`gguf_k_prefill_out_coltile_rowbatch_kernel`. The trace's template argument list
is `float, float, 8, 8, 4, true`. Reading the base name and assuming otherwise
made the first sweep report a 12% "win" that was really the shipped
configuration beating a superseded one. `wave_scale` replaces the per-lane
`k / 32` with `__builtin_amdgcn_readfirstlane`, making the block pointer and the
FP16 scale load wave-uniform; the loop drops from 171 to 145 instructions and the
output is bit-identical (`max_abs_diff = 0.0` on every layer and row count).

## Validation

- Role-marked capture: 100% attribution, 9652 kernels, 22368.1 ms of a
  22932.5 ms window, 0 ms unattributed.
- Identical-operand sweep: 175 (layer, rows, variant) rows, all bit-identical to
  production, spread ≤0.3% across five layers at 1024 rows.
- Standalone `attn_qkv` at 1024 rows measures 17.32 ms against 17.95 ms
  in-model (2585.0 ms / 144 launches), so the isolated harness is representative.
- Instruction mix read from `hipcc -save-temps=obj` device assembly for the
  production instantiation; VGPR/SGPR/LDS/spill from the same object via
  `scripts/gguf_prefill_kernel_resources.py`.
- `scripts/sync_benchmark_readme.py --check` passes.

Diagnostic only. **No performance claim is retained** and no hipEngine rate
changed.
