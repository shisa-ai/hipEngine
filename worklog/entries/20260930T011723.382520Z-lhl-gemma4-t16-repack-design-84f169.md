# D1 repack design: t16 gate_up wiring map and open questions

## Summary

Recon for the loader-side t16 repack unit (D1's work item after iteration 136's
screen). **The t16 family was built for this: almost the entire production
route already resolves for quant key `gguf_q4_k_t16_v1`, and the gaps are two
registration aliases plus loader work.** No new kernels.

### Registry probe results (run live, `_ensure_linear_kernel_registered` + `is_registered`)

For `gguf_q4_k_t16_v1`:

| key the gemma chain probes | registered? |
|---|---|
| `linear \| selected_gemv_bf16_bf16_out` (decode + strict-selected fallback) | **NO** — gap 1 |
| `moe_linear \| selected_gemv_bf16_bf16_out` | NO (profile declaration needs it, see below) |
| `moe_linear \| selected_t16_gemv_decode_bf16_bf16_out` | YES (the screen's 4.9x kernel) |
| `moe_linear \| selected_dual_q8_1_ds4_mmq32_prefill_compact32_bf16_bf16_out` (auto/production prefill) | **YES** |
| `moe_linear \| selected_dual_wmma_prefill_compact_bf16_bf16_out` (gemma's WMMA probe spelling) | YES (qwen alias precedent) |
| `moe_linear \| selected_dual_wmma_prefill_compact32_*` | YES |
| `moe_linear \| selected_dual_grouped_*` (strict exact route) | NO — strict falls through to selected (correct, slower) |

### ABI checks (all pass)

- Decode: t16 wrapper `(x_ptr, selected_ptr, tiles_ptr, out_ptr, x_rows, rows,
  num_experts, in, out, *, stream, ...)` matches gemma's call at
  `gemma4_experts.py:1411` **including `stream=`**, and raw/t16 signatures are
  identical — so registering the t16 fn under the *same variant name*
  `selected_gemv_bf16_bf16_out` (quant key carries the layout) is the honest
  fix, exactly the alias pattern qwen documents ("so dispatch can route on
  `quant_key` alone").
- Prefill auto route: `gemma4_project_experts_mmq_dual` resolves its leaf via
  `_mmq32_leaf_owner` = `(moe_linear, weight.spec.quant_key, _MMQ32)` → t16
  registered, and `gguf_q4_k_t16_..._mmq32_compact32` (q8_1 prefill file:1918)
  forwards to the shared leaf with `_SYMBOL_T16_DS4_MMQ32_BF16` (a
  tiles-reading symbol) and the same positional args + `expert_stride_rows`.
  **Zero gemma prefill changes needed.**
- Fused `gate | up` offsets survive the layout: tiles per expert =
  88 out_tiles x 11 blocks x 2368 B = 2,292,224 B; half = tile 44 = row 704
  exactly (Q4_K rows are whole 256-blocks, 704 % 16 == 0).

### Remaining work items (design)

1. **Gap 1 — decode alias registration.** Register
   `gguf_q4_k_t16_selected_gemv_bf16_bf16_out` under
   `(linear, gguf_q4_k_t16_v1, selected_gemv_bf16_bf16_out)` (the key gemma's
   decode *and* the strict-mode chain fallback resolve). Without it the strict
   arm's grouped probes miss and the chain falls through to
   `gemma4_project_experts_by_offset`, which reads expert strides from the
   tiles allocation as if raw — silent corruption. Also register under
   `moe_linear` if profile rows declare it there (open question 2).
2. **Loader.** `_plan_one` returns a t16 spec (layout
   `LAYOUT_GGUF_Q4_K_T16`, quant_key `gguf_q4_k_t16_v1`,
   `allocation_names=("tiles",)`) for stacked rank-3 **Q4_K gate_up**
   (`ffn_gate_up_exps`) only; device materialize gains the t16 branch (repack
   via `repack_gguf_q4_k_tile16`, tiles nbytes plan, upload, free raw);
   `expert_stride_bytes` must become allocation-based (today it uses
   `spec.source.nbytes // experts` = raw bytes, which is **not** the tile
   stride — 2,230,592 vs 2,292,224 for the real shape, and half_bytes would
   land off a tile boundary); the 9 `weight.allocation("raw")` sites in
   `gemma4_experts.py` switch to the spec's primary allocation name (down stays
   `raw`, gate_up becomes `tiles`).
3. **Profiles.** `gemma4_profiles.py` pins `registry_quant=_Q4_K` on scopes
   `moe_decode_q4_k` (linear) and `gate_up_q4_k` (moe_linear). After the
   conversion the runtime resolves `gguf_q4_k_t16_v1`, so the plan rows must
   follow: both strict and production plans (the quant-change rule at
   `execution_profiles.py:428` forbids production differing from strict), the
   production row keeps `_MMQ32` as selected (registered under t16), and the
   strict row's selected for the t16 scope must be a registered exact owner —
   `selected_gemv_bf16_bf16_out` (gap 1's alias), because `_GROUPED_DUAL` has
   no t16 owner.
4. **Loud-failure guard.** `gemma4_project_experts_by_offset` /
   `launch_gguf_linear_raw_ptr` should raise on a non-raw resident layout
   instead of misreading, so a future probe miss fails loudly.
5. **RED/GREEN tests** (write first): planner unit (gate_up Q4_K → t16 spec,
   everything else raw); tiles round-trip on the real shape
   (2816 x 1408 x 128); dispatch-identity (every probe the chain can issue for
   a t16 gate_up resolves to a tiles-reading owner, including the strict-mode
   miss path); profile resolution still passes `_verify_registered_variants`;
   GPU: same-weights t16-vs-raw forward must be bit-identical (repack is
   lossless and mmq32 arithmetic is unchanged), then the campaign p4096 gate
   must reproduce `0.48681258576151065` (or the delta explained).
6. **Validation.** Peak memory (X2 row: XTX already 91.6% — tiles are +2.76%
   over raw per converted tensor), load-time repack cost (29 tensors, streamed
   per tensor), family census / rocprof showing `*_t16_*` kernels live in
   `LLM.generate()`, decode + prefill 1024 re-measure.

### Deliberately out of scope

- **Q5_1 down** — no t16 family, in_features 704 fails the guard (see
  `...-d3-t16-eligibility-...` entry).
- **Layer-29 Q5_K gate_up** — `gguf_q5_k_t16_v1` decode is registered under
  `moe_linear` only while gemma probes `linear`; needs the same alias decision,
  worth ~1 layer. Follow-up, not this unit.
- Dense Q4_K (attn etc.) — no measured need, bigger blast radius.

### Open questions for the implementation iteration

1. Does any test compare plan rows against *actual* dispatch identity
   (`b1b033dc3`'s dispatch-identity test)? That decides whether profile edits
   are mandatory or merely truthful. Run `test_unit_gemma4_profiles.py` after
   the conversion and see.
2. Does `_verify_registered_variants` run against the *converted* quant for
   every profile mode (it keys rows, not weights)? If rows keep raw quant it
   still passes (raw keys exist) — the edit then only matters for honesty +
   identity tests; if the binder is weight-driven it must change. Determine by
   reading `resolve_runtime_profile` callers.
3. `gguf_selected_contract.py` output-owner checks — confirm they don't pin
   layout/quant for `ffn_gate_up`.
4. Whether the strict arm's grouped→selected fall-through changes strict-mode
   *timing* materially in gate runs (correctness unaffected: both exact).
