# The MMQ gate/up error was measured against a zero buffer

## Summary

Every gate/up error number recorded for the Gemma 4 MMQ prefill route is an
artifact of the harness that produced it. The fp32-arm wrapper captured the
shared `gate_up_out` buffer *before* calling the route, while the MMQ-arm wrapper
captured it *after*, so the fp32 reference was never captured at all. At 64 ids
the "reference" was a zero buffer and the reported error was the MMQ arm's own
output magnitude; at 96 ids it was the previous 64-id run's output.

This voids the conclusions in
`benchmarks/results/2026-09-28-gemma4-mmq-divergence-distribution-dump.json`
that were derived from those numbers — specifically that the route's entire error
is the DS4 activation quantization budget, that the error is length-independent,
and the task-15/task-18 reasoning built on them. It does **not** touch the KL-by-
length probe, which compares whole forwards and never used this harness.

The corrected error is **0.655 percent relative at one activation plane and
0.606 percent at three**. Three planes buy 1.08x, not the three orders of
magnitude predicted from the pack arithmetic, because the activation term they
remove is only about 41 percent of the error.

## Validation

Harness diagnosis verified, not inferred, by reproducing the old wrapper pattern
with both captures instrumented (`/tmp/mmq_oldcheck.py`):

- ids=64: fp32 capture `mean|a|=0.0, max|a|=0.0, nonzero=0`; MMQ capture
  `mean|b|=0.822610, max|b|=38.7500`; reported "error" `mean=0.822610,
  max=38.7500`. The error is the output magnitude.
- ids=96: fp32 capture `nonzero=720896` = `512 x 1408`, the previous 64-id run's
  output; reported "error" `mean=0.990430`.

Corrected measurement with both arms capturing after their call
(`/tmp/mmq_realerr.py`):

| ids | fp32 `mean|out|` | 1 plane | 3 planes |
| --- | --- | --- | --- |
| 64 | 0.8225 | 0.005386 (0.655%) | 0.004987 (0.606%) |
| 96 | 0.7729 | 0.005144 (0.666%) | 0.004724 (0.611%) |

Error decomposition at 64 ids: `0.004987^2 + 0.002205^2 = 2.9732e-05`, root
`5.453e-03` against a measured `5.386e-03`, 1.2 percent agreement. The three-plane
arm isolates the non-activation term at 0.00499; the 0.002205 the planes remove is
the activation term.

Isolation tests that the source reading had already got wrong once each way:

- Pack, standalone against numpy (`/tmp/mmq_packtest.py`): one plane reconstructs
  at 7.64e-03 relative, three planes at 4.08e-06 — **1873x**, matching the 1630x
  predicted from the pack arithmetic. Plane scale medians 5.28e-3, 2.04e-5,
  5.96e-8. The error feedback works.
- Leaf (`/tmp/mmq_zero.py`): three-plane leaf with planes 1 and 2 zeroed is
  **bit-identical** to the one-plane leaf (0 of 720896 differ), and differs from
  the intact three-plane run in 435886 of 720896. The multi-pass path is live, the
  plane stride is right, and the extra planes are consumed.
- In-kernel printf in the body's pass loop: pass 0 contributes ~0.05-0.16 per k32,
  pass 1 ~2e-4, pass 2 ~1e-6. Reverted.

The earlier claim that the two leaves were bit-identical was a scratch-script bug:
it bound the three-plane symbol to a name and then called the one-plane symbol
twice. That measurement, which is what `f8608d07f` recorded as an unresolved
contradiction against the source, was not a measurement.

`tests/test_unit_gemma4_expert_route.py` was not run: no production code changed.
