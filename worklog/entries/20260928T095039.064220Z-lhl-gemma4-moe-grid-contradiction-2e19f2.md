# the decode moe gate up grid is 128x the expert width and the caller cannot be passing the width it reads

## Summary

I set out to size the decode MoE gate/up's per-block cost, having closed its route
alternatives last unit. I have the measured grid. **I cannot reconcile it with what
the caller passes, and the discrepancy is a factor of exactly 128 -- the expert
count.** Recording it rather than picking the branch that fits.

## Why that does not reconcile

`launch_selected_dual_q8_1_ds4_mmq32_compact32` (the only definition of that name,
line 4949) builds the grid as:

```cuda
const int64_t out_features_total = out_features_a + out_features_b;
const int64_t row_tiles = mmq_total_rows / 32;
const dim3 grid(out_features_total / 32, row_tiles);
```

`5632 = out_features_total / 32` forces **`out_features_a + out_features_b =
180,224`**, and `180,224 = 128 x 1408`, i.e. **every expert's fused width summed.**

But the caller cannot be passing that. `_gemma4_project_experts_gate_up_mmq`
(`gemma4_experts.py:1204`) does:

```python
weight_ptr = weight.allocation("raw").buffer.ptr
row_bytes = (in_features // 256) * 144
mmq_gate_up(
    ...,
    weight_ptr,
    weight_ptr + intermediate * row_bytes,   # qweight_b
    out_ptr,
    compact_rows, in_features,
    intermediate, intermediate,              # out_features_a, out_features_b
    num_experts, total_rows, ...,
)
```

`qweight_b` is `weight_ptr + intermediate * row_bytes`, and that has to be the
**up-half base**. Under the fused `(num_experts, 2*intermediate, hidden)` layout the
up half starts `intermediate` rows in, so **`intermediate` must be 704** -- the
per-expert half width, which `runtime/gemma4.py:297` confirms
(`moe_intermediate_size = gguf.expert_feed_forward_length`). At 704 the grid would
be `44 x 8`, not `5632 x 8`.

Both cannot hold, and the factor between them is exactly `num_experts = 128`.

**This is the same contradiction `20260928T090630` recorded**, now sharpened: it is
not a question about the scratch sizing or the trace's provenance, it is a factor of
128 between the grid the trace shows and the grid the arguments imply.

## Why it matters

The kernel's own expert addressing uses that same sum:

```cuda
const int64_t expert_stride_rows = FUSED_EXPERT_LAYOUT
    ? (out_features_a + out_features_b) : local_out_features;
const int64_t expert_bytes = expert_stride_rows * weight_row_bytes;
const uint8_t* __restrict__ expert_base = qweight + expert_id * expert_bytes;
```

**If `out_features_a + out_features_b` is 180,224 then `expert_bytes` is 128x the
true per-expert stride of 1408 rows, and every expert but the first reads past its
own block.** The output is correct in practice, so this is more likely a misreading
on my part than a live bug -- but I cannot currently say which, and the difference
decides whether the fix is a grid change or a stride change.

It also decides the size of the per-block problem I was sizing. If grid.x is 44, the
gate/up runs **352 blocks** per dispatch and each block has real work to amortize its
setup over. If grid.x is 5632, it runs **45,056** and 99 percent of them do nothing
but read a weight tile. Those two worlds want opposite fixes.

## The decisive next step, and it is one step

**Print the arguments the launcher actually receives.** Not the arguments the call
site appears to pass -- the values at the launch. Either:

1. `mmq_gate_up`'s Python wrapper reorders or scales its positional arguments before
   the FFI call (the wrapper is `_make_...`-generated; I did not read it), or
2. the grid is built from a different quantity than the kernel's
   `out_features_total`, or
3. the trace's grid belongs to a different dispatch than the one I matched by name
   and count.

A one-line printf in the launcher, or reading `mmq_gate_up`'s generated signature,
separates these. **I ran out of context before doing it, and guessing here would
have produced a confident wrong answer about the largest single line in decode.**
