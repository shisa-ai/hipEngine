# the MMQ_K experiment is a subsystem change, and its contained form is one new struct plus one kernel

## Summary

`20260928T204000` scoped "a variant of the MMQ32 kernel staging 64 K elements per pass" as a
bounded experiment. Reading the kernel to make the edit shows it is not:

- **`MMQ_K` is a per-kernel `constexpr`** -- three kernels in the file declare their own
  (lines 1099, 3319, 4088), so the constant itself is local and cheap to change.
- **But the 32-element K span is encoded in a shared struct.** `q4_k_mmq32_cache` is
  `{ uint32_t qs[4]; uint16_t dm[2]; }` -- 4 words of nibbles and one scale/min pair, which
  *is* 32 K elements -- and `q8_1_mmq32_cache` is `{ int32_t qs[8]; uint16_t ds[2]; }`, the
  same span on the activation side. **Those structs are referenced nine times in a file
  containing twenty-one `__global__` kernels.**

**So raising `MMQ_K` widens a type that every MMQ32 kernel in the file shares.** The edit is
not local, and a half-applied version would leave kernels with a struct whose layout no
longer matches the staging they were written for -- a silent-wrong-answer failure mode, not
a compile error, because the indexing is arithmetic rather than typed.

## The contained form

**A parallel struct plus one kernel**, not a change to the existing ones:

- `q4_k_mmq64_cache { uint32_t qs[8]; uint16_t dm[4]; }` -- 40 bytes, two subblocks
- `q8_1_mmq64_cache { int32_t qs[16]; uint16_t ds[4]; }` -- 72 bytes
- one new `__global__` kernel taking them, with `MMQ_K = 64`, the inner qword loop unrolled
  16 times instead of 8, and **two** `(dscale, dmin)` pairs applied per accumulation instead
  of one

That is roughly fifty lines and one new kernel. **It is a real unit, not an end-of-budget
edit**, and starting the wider version instead would touch three kernels' staging code and
nine struct references to answer a question about one of them.

**Shared memory is not a constraint on it.** The current tiles are `32 x 20 = 640` and
`32 x 36 = 1152` bytes; the doubled forms are 1280 and 2304, for 3584 bytes total against
the 64 KB an RDNA3 CU provides.

## Why this is recorded rather than attempted

**The session has already produced this exact shape of finding once**, when the T16 promotion
turned out to be a repack rather than an import swap (`20260928T160000`). **Beginning a
change that spans a shared type at the end of a budget is how a branch gets a half-finished
kernel**, and the failure mode here is arithmetic indexing rather than a type error, so it
would not be caught by the compiler.

**The K staging remains the best-founded candidate for the 1.36x**, and this entry narrows it
rather than closing it: the constant is local, the struct is not, and the contained experiment
is one new struct and one new kernel.

## What would make it cheaper

**If the question is only "does the loop count matter", it does not need a new kernel.** The
existing kernel's iteration count is `in_features / MMQ_K`, and the microbenchmark already
takes `--in-features`. A sweep across K values that are all multiples of 32 would show
whether the per-element rate degrades as the iteration count grows -- but it cannot, because
the iteration count is proportional to K, so the per-element overhead is constant by
construction. **That is why the experiment needs the variant and why the variant needs the
struct.**
