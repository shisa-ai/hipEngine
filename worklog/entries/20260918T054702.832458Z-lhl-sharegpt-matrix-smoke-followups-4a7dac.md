# Matrix smoke: provider-refused case is blocked by the autoregressive prefill limit, and a long prompt can fail after streaming

## Summary

The real-workload harness's new matrix features were smoked end-to-end on the
head tree (4 prompts, c=2, `--cases short,beyond`, `--prompt-repeats 2`,
`--route-mix off,auto`, `--record-ids`). Every new report block emitted
(`by_route_arm`, `by_case`, `by_repeat`, `arm_identity`, `QUALITY`), the
provider-window refusal appeared as `target_context_k0`, and the prefix split
reported `prefix miss` beside `prefix hit-1`. The smoke also exposed two engine
issues outside the harness unit, which is why this entry is `blocked` rather than
a clean checkpoint.

## Changes

- `scripts/sharegpt_mtp_routing_pass.py`: the `beyond` case's help and the module
  docstring now state that a `beyond` prompt only measures the provider-window
  refusal on a server whose autoregressive prefill accepts a context of 1,024 or
  more, because the head tree's packed paged AR prefill rejects it.

## Validation

- `uv run pytest tests/test_unit_sharegpt_mtp_routing_recorder.py` -> 24 passed.
- Smoke artifact `/tmp/mtp-matrix-smoke/matrix-smoke.json` and console report;
  server log `/tmp/mtp-matrix-smoke/server.log`.

Two engine findings, both on the head tree with
`--max-context-tokens 8192 --kv-storage bf16 --execution-profile production`:

1. A 1,241-token prompt is rejected with HTTP 400 `unsupported_parameter`
   ("packed paged AR prefill currently requires context < 1024"). The provider
   window refuses such a prompt for MTP (`target_context_k0`, which is the
   intended refusal), but the autoregressive fallback cannot serve it either, so
   the request fails. This blocks the provider-refused-but-AR-served arm of the
   validation matrix: the band where the provider refuses and AR still serves is
   roughly 1,022-1,023 prompt tokens.
2. That 400 arrived after 139 s of streamed output with 1,253 thinking
   characters already delivered, and two other long-prompt requests returned
   HTTP 500 with no body at all. A rejection that arrives after a response has
   been streaming for minutes is worse than an early refusal: the client cannot
   distinguish it from a truncation, and the harness records it as a failure row
   with `events=737`.

## Next

- Give findings 1 and 2 their own unit: either make the packed paged AR prefill
  accept the context the provider refuses, or refuse such a request at admission
  before any prompt work, and always before the response has streamed.
- Until then, the coupling arm's provider-refused side stays observed (the c=4
  contention case, 456 non-speculative tokens attributed to `no_provider`)
  rather than constructed, and the harness documents that.
