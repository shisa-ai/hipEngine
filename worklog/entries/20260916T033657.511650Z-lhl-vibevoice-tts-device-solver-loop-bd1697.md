# VibeVoice-TTS: device-resident DPMSolver loop (CFG D2H removed)

## Summary

`sample_speech_tokens` now keeps the latent, the CFG-combined eps and the
previous x0 on device for the whole 20-step schedule. The per-step eps D2H is
gone; the only device-to-host traffic is the final readback, plus the per-step
snapshots when `collect` is requested. Same-session interleaved A/B on the
pinned gfx1151 request: the diffusion stage drops **14.9%** (1.521 -> 1.295 s)
and warm synthesis **3.5%** (8.515 -> 8.216 s), with the generated chain
bit-identical.

The 5.56% figure carried into the task was an estimate from the earlier
round-trip ceiling; the measured session-level effect is **~3.5%**, and that
number is load-contaminated (see Validation). The diffusion-stage delta is the
trustworthy one.

## Changes

- `hipengine/runtime/vibevoice_tts_diffusion.py`
  - `forward` split into a thin host wrapper plus `forward_into`, which runs the
    head with `x_rows` already resident and leaves the raw eps in the device
    buffer with no readback. `read_eps`/`_read_device` do the explicit reads.
  - `sample_speech_tokens` rewritten around the device loop: `speech` and
    `x0_prev` ping-pong between two buffers each (the step kernel declares
    `sample`/`sample_out` and `x0_prev`/`x0_out` `__restrict__`, so input and
    output must not alias), `x_rows` is filled by two D2D copies of latent row 0
    (the fork drives both CFG branches from the first row), and the head's own
    eps buffer is deliberately left untouched so the final raw eps is still
    available for the return value.
  - Module docstring updated: it still claimed the solver ran on the host.
- `hipengine/kernels/cpu_reference/vibevoice_tts_diffusion.py`
  - `step_scalars()` (added in the previous unit) plus a new `advance_step()`
    that performs the state advance, which `step()` now calls, so the device
    loop and the oracle share one advance rule.
- `hipengine/kernels/hip_gfx1100/vibevoice/diffusion.hip`
  - **`vv_diff_cfg_combine_kernel` rounding fixed.** It rounded the `(c - u)`
    difference to bf16 before scaling, giving `r(u + r(cfg * r(c - u)))` --
    three roundings. The sampling oracle is
    `bf16_round(u + bf16_round(cfg * (c - u)))`, two roundings, with the
    difference in fp32. The kernel now matches the oracle.
- `tests/test_live_vibevoice_tts_diffusion_gpu.py`
  - New `test_gpu_cfg_combine_matches_sampling_oracle`, which pins the kernel
    against the oracle formula directly and asserts its inputs actually
    distinguish the two- and three-rounding forms.

## Validation

**The CFG kernel bug was invisible until now.** `vv_diff_cfg_combine_bf16` was
registered in `PRIMITIVES` but had **no caller anywhere in the tree**, so its
rounding chain was never checked against the sampling path. It surfaced only
because the device loop started using it: the first device run diverged from the
host path at step 0 (max |diff| 0.055 on eps_cfg). After the fix, the device
loop is bit-identical to the host loop at every step.

Intermediate-state comparison against the CPU reference, whole 20-step schedule
on the pinned single-speaker request, device loop vs host loop:

| state | mismatched steps | max abs diff |
| --- | ---: | ---: |
| `eps` (raw head output) | 0/20 | 0.0 |
| `eps_cfg` (CFG-combined) | 0/20 | 0.0 |
| `speech` (post-step latent) | 0/20 | 0.0 |

Final `speech` and final raw `eps` also compare equal. Command:
`uv run python -m pytest tests/test_live_vibevoice_tts_diffusion_gpu.py
tests/test_unit_vibevoice_tts_diffusion.py -p no:cacheprovider -q` -> 15 passed.
`chain_exact` was `True` in all four A/B session runs.

Same-session interleaved A/B (arm order device, host, device, host, one process,
one machine state) on the pinned single-speaker request, gfx1151 / Radeon 8060S:

| arm | pooled RTF | warm (s) | diffusion (s) |
| --- | ---: | ---: | ---: |
| device | 2.494 / 2.436 | 8.312 / 8.119 | 1.298 / 1.292 |
| host | 2.550 / 2.559 | 8.500 / 8.530 | 1.496 / 1.546 |

Device means 2.465 / 8.216 / 1.295 against host means 2.5545 / 8.515 / 1.521:
diffusion **-14.9% (1.174x)**, warm **-3.5%**, pooled RTF **-3.5%**.

Isolated diffusion-call A/B (8 reps, same process, median): 57.06 -> 49.26 ms,
**1.1584x**, outputs identical -- consistent with the in-session stage delta.

**Host-load caveat.** These runs were taken at load average 13.3, so the
absolute RTF ~2.5 is roughly 2x the recorded 1.201 and is **not** comparable to
it. Only the same-session device/host deltas above are valid evidence. No
cross-session absolute rate is claimed. The diffusion-stage share of warm is
17.9% in the host arm, so a 14.9% stage win predicts ~2.7% overall; the measured
3.5% is within noise of that under this load, and the honest range is **~2.7-3.5%**.

**Task-quality gate.** The 10-seed generated-audio suite (seeds 20260915..20260924,
matching the recorded run) returns **58/60 request-runs passing** with failures
`two-long` at seed 20260918 and `two-2turn` at seed 20260919 -- **identical** to
the recorded suite: same per-request pass counts (10/10/10/9/10/9), same per-seed
failure sets, same `stable` flags. Command: `uv run --with jiwer --with
transformers python scripts/vibevoice_tts_quality_suite.py --seeds
20260915,...,20260924`. So the device path changes neither the token chain, nor
the per-step latents, nor the unassisted audio quality. Artifact:
`benchmarks/results/2026-09-16-gfx1151-vibevoice-tts-device-solver-loop.json`.
