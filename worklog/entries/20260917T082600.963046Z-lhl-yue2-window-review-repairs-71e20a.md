# YuE2 window review repairs: domain-keyed cache, full domain validation, non-finite guard, interleaved timing

## Summary

An external review of the phase-windowed output head
(`worklog/entries/20260917T061846.471372Z-lhl-yue2-ar-head-window-1c7649.md`) reported two
code defects and four evidence problems. Both defects are real; three of the four evidence
problems are real and one is not reproducible. This entry records the repairs, the
re-measurement, and the one review item I could not confirm.

## Changes

### Defect 1: the window cache was keyed on "filled", not on the domain

`Yue2ArRuntime.logits` checked `if not self._logits_window_filled` before refilling, and
the domain comparison lived inside `_fill_window_rows`. A caller that asked for a second
domain without moving a hidden row (i.e. without `forward_layers`, which is what
invalidates the cache in the session loop) therefore got the *first* domain's rows back:
the guard was false, the refill never ran, and the domain check inside it was never
reached. `generate_tokens` calls `runtime.reset()` first, so the session loop never hit
this, but `logits()` is public and the reviewer reproduced it directly. The previous unit's
test reset the cache before switching domains, which is exactly the step that hides the
bug.

Fix: the domain is now part of the cache key and is validated on every call, before the
`_logits_window_filled` test. `tests/test_unit_yue2_ar_paired_head.py::
test_switching_domain_without_a_step_reprojects` reproduces the reviewer's case — project
`(100, 108)`, then ask for `(200, 204)` with no reset — and asserts a second head call, the
shifted weight pointer, finite rows in the new window, `-inf` back over the old one, and
that a repeat of the *same* domain is still a cache hit.

### Defect 2: a negative lower bound reached the kernel

Validation checked `width <= 0` and `high > vocab_size` but not `low >= 0`, so
`domain=(-1, 4)` computed a weight pointer *ahead* of its allocation and dispatched a
kernel read from it; the host scatter would have failed afterwards, too late to matter.
`_validate_domain` now checks the whole range before any dispatch: the pair unpacks, both
bounds are integers (`bool` rejected, matching the module's other validators),
`0 <= low < high <= vocab_size`. `_fill_window_rows` validates again so the pointer
arithmetic is guarded at its own entry point, and
`test_invalid_domains_are_rejected_before_dispatch` asserts no head call happens for
`(-1, 4)`, `(0, 0)`, `(8, 4)`, `(0, vocab+1)`, `(2.5, 4)`, `(0, "4")`, `"nope"`, `(0,)`
and `(0, 1, 2)`. `None` stays valid: it means the full projection.

### Defect 3 (found while repairing): a NaN inside the allowed domain was silently masked

The first cut folded *every* non-finite value in the score row to `-inf` before the mask.
That is right for the `-inf` a windowed row carries outside its window, and wrong for a NaN
or `+inf` *inside* the allowed set, where it means the head or the CFG combination produced
a broken row and masking it would hide the failure. `distribution` (and the legacy `off`
variant) now build the allowed set first, raise `FloatingPointError` naming the first
selectable non-finite token if any exists, and fold only the rows the phase cannot select.
This is the guard the reviewer asked for. Covered by
`tests/test_unit_yue2_protocol.py::test_distribution_rejects_non_finite_inside_the_allowed_domain`,
including the detail that `MUSIC_END` sits *below* `CODEC_OFFSET` and so is selectable
during `semantic`, and that `abc`'s masked holes are still just masked.

The guard runs in the sampling path, so the session gate was re-run to confirm it does not
fire on real rows: **PASS**, with the same agreement values as before the guard (abc forced
0.991 / 0.997, semantic forced 0.982 / 0.971 / 0.967).

## Measurements

### Evidence repair: the RNG claim proved nothing

The artifact compared `timing["random"]`, which is `{algorithm, seed}` — identical for any
two runs of the same request, so it added no information beyond "both used seed 1234". The
reviewer is right. `YuE2Random.state_digest()` now hashes the live PCG64 state, so it
depends on how many draws were consumed, and the session timing record carries it as
`random_state_digest`. Equal digests mean every subsequent draw agrees, which is the claim
that was being made. `test_random_state_digest_tracks_the_stream_position` covers the
three cases: equal seeds agree, unequal consumption differs, equal consumption agrees
again (and then produces equal draws).

### Evidence repair: the timing was best-of-N and single-run

The head figure was best-of-ten per arm in two blocks and the production figure was one
48-token run per arm. `scripts/yue2_ar_head_window_validation.py` (protocol v2) now
interleaves both arms inside one repetition, flips the order every repetition, drops
best-of entirely, and reports median/min/max/p25/p75 plus the median and range of the
*paired* ratio. The production loop gets a discarded warmup per arm and 5 measured
repetitions per arm, alternating order, and reports the paired per-token saving.

Two independent runs, `mandarin-off-s1234`, temperature 1.0:

| Measurement | Run 1 | Run 2 |
| --- | --- | --- |
| `semantic` head, full → windowed | 3.821 → 0.847 ms | 3.837 → 0.818 ms |
| `semantic` paired ratio | 4.53x (4.08-5.80) | **4.68x (4.41-5.01)** |
| `abc` head, full → windowed | 4.187 → 3.483 ms | 4.128 → 3.444 ms |
| `abc` paired ratio | 1.20x (1.13-1.33) | 1.20x (1.18-1.39) |
| loop windowed, ms/token | 56.86 (56.23-56.94) | 56.83 (55.45-56.92) |
| loop full control, ms/token | 61.09 (60.17-61.39) | 61.37 (60.78-61.57) |
| paired saving, ms/token | 4.23 (3.94-5.16) | 4.71 (4.45-5.34) |

The retained figures are the run-2 medians: **3.84 → 0.82 ms (4.68x)** for the semantic
head, 4.13 → 3.44 ms (1.20x) for `abc`, and **61.4 → 56.8 ms/token (4.7 ms/token, 1.08x)**
for the loop. Two corrections against the previous unit's report: the semantic speedup is
4.68x, not 4.82x — best-of-ten inflated it — and `abc` gains 1.20x, not 1.05x, which the
best-of-ten block understated. Both arms are stable: every one of the 10 loop runs has
windowed faster than full, by 3.94-5.34 ms/token.

The loop comparison is the only place the two arms differ in *what the head computes*, and
both arms produced identical tokens and an identical PCG64 digest
(`48fbdbe8717bdbfb`) in all ten runs.

### Evidence repair: the replay gate does not validate the window

The README line "the AR replay gate above still scores full-vocabulary rows and is
unchanged" was doing double duty as evidence for the window unit. It is not: the replay
matrix drives the unwindowed route, so it validates the *fallback* and the paired head.
Windowed execution is covered by parts A, B and D of the head-window validation and by the
session gate. The validation artifact now records that split explicitly under
`parts.coverage`, and the README and changelog no longer cite the replay gate as window
evidence.

### Not reproduced: the KL exponent

The review item "the KL number in the report dropped its exponent; the artifact says
0.0011578938, not 1.1578938" does not match the published text. `benchmarks/README.md`
says `1.1579e-3`, the worklog entry says `0.0011578938168649458`, and the replay artifacts
record `aggregate.pooled_mean_kl = 0.0011578938168649458`; those are the same number, and
no published sentence writes `1.1578938`. No correction was needed. The substantive half of
that item — that the replay gate validates the fallback rather than the window — is real
and is fixed above.

## Validation

### Regression found by the wider unit run

`python3 -m pytest tests/ -k yue2` also caught a regression the previous unit left behind:
`tests/test_unit_yue2_session.py`'s `FakeRuntime.logits` did not accept the `domain`
keyword that `generate_tokens` started passing, so four session tests errored. The previous
unit had run only the paired-head and protocol files. The fake now honors `domain` by
returning a full row with `-inf` outside it, which is the real runtime's contract, so the
session tests exercise the windowed row too. 257 yue2 tests pass.

## Next

The reviewer's ordering is: these repairs, then two-row transformer execution, then a
window-relative sampler. The window-relative sampler is the requested next unit, so it goes
next; the design constraints the reviewer named are all real, and a first pass over the
sampler code confirms they are the whole risk surface:

- `window_penalty` calls `np.bincount(recent, minlength=scores.shape[-1])` and raises on a
  history token above that bound, so a window-relative row needs the history mapped into
  window coordinates with out-of-window ids dropped. That is the identity: those rows are
  `-inf` and stay `-inf` under `x * alpha` for any `alpha > 0`.
- top-k masks by *value* (`scores < threshold`), not by index, so it is tie-safe under a
  window shift. top-p sorts with `kind="stable"`, so ties keep ascending token order in
  both layouts and the trailing `-inf` tail contributes nothing to `cumulative`.
- `sample_categorical` is the one place that is not obviously identical: with a flat
  `-inf` tail, a draw equal to the exact total would `searchsorted` into the tail, and the
  tail is shorter in a windowed row. `uniform()` is in `[0, 1)`, so the draw is strictly
  below the total and the tail is unreachable except through an fp64 rounding of
  `uniform() * total` onto `total`; that is a pre-existing latent defect in the full row
  (it would return a masked token), and the windowed unit should fix it in both paths
  rather than paper over it.
- `combine_cfg` and `softmax_f32` are two more full-row passes over 184 704 elements that
  could shrink by the same 5.6x under the same identity argument.
