# Correct the engine-command-timeout error report in ENVS.md

## Summary

`docs/ENVS.md`'s entry for `HIPENGINE_ENGINE_COMMAND_TIMEOUT_SECONDS` stated that
an exhausted command budget "raises an error ... which the server reports as
HTTP 503 `engine_unavailable` (retryable), the same shape it uses for a closed
engine service." That is true for commands that serve a request, and **false for
the readiness and metrics diagnostics**, which read the engine through
`_live_loop_snapshot` / `_engine_service_health`
(`hipengine/server/api.py:9795`, `:9808`). Both swallow every exception and
return `None`, so a timeout there costs the payload its live snapshot fields and
nothing else.

Verified by `tests/test_unit_server_ready_degradation.py`, added in
`75fa742d1`: with an engine whose every readiness read raises
`EngineCommandTimeout`, `/ready` answers 200 with `ready: true` and no
`engine_unavailable`. A mutation check removing the swallow fails that case
while `/health` still passes, because `/health` never reads the engine.

The entry now states which commands get the 503 and which degrade.

## Decision: do not add a separate readiness budget

The same investigation established that `/ready`'s worst-case latency is the
command budget -- `DEFAULT_COMMAND_TIMEOUT_SECONDS = 300.0`. A readiness probe
therefore has a five-minute ceiling by default.

**Decision: correct the documentation rather than add a second budget.** The
reasons, so the call can be revisited deliberately:

- The default is a reasoned choice, not an oversight. The same ENVS.md entry
  explains it: a command queues behind "a context prepare that grows the KV pool
  and captures graphs, or one prefill tick of a large prompt. Both legitimately
  exceed half a minute, so the default is generous and this value is not a bound
  on engine work."
- The knob already exists and is configurable, so an operator who needs a tight
  probe can lower it today. That is the clearing command.
- The bound costs **diagnostics, not correctness**. `/ready`'s verdict comes
  from `readiness.ready`, its own startup state; the live snapshot is
  accompanying detail. A slow probe therefore degrades the payload and never
  withholds a correct readiness answer.
- A per-call readiness budget would be a **new mechanism** in a shared
  component. `_wait_response` deliberately reads one budget
  (`engine_service.py:964`), and splitting it is a design decision about the
  service's contract, not a defect repair.
- `asyncio.wait_for` at the endpoint is not an alternative: the documented
  behaviour is that "a timed-out command is abandoned by its caller but still
  runs on the driver thread", so abandoning it earlier would leave the worker
  thread blocked and, under repeated polling, exhaust the default executor.

**Recommendation for the lead, not implemented:** if a probe needs a tighter
ceiling than the liveness budget allows, the clean lever is an optional
per-call budget on the diagnostics control path only, leaving request-serving
commands on the shared budget. It is a small change to `_control` and
`_wait_response` plus a config field, and it should carry its own tests. Left
undone deliberately rather than assumed.

## Changes

- `docs/ENVS.md`: the `HIPENGINE_ENGINE_COMMAND_TIMEOUT_SECONDS` entry now
  distinguishes request-serving commands (503 `engine_unavailable`) from the
  readiness/metrics diagnostics (timeout swallowed, live snapshot omitted,
  endpoint still answers), and notes that `/health` never reads the engine.
