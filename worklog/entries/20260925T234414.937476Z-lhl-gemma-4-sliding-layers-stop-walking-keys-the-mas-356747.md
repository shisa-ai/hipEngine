# Gemma 4 sliding layers stop walking keys the mask already zeroed (+1.2% metric, +34.9% at 4096p)

## Summary

A decode step on a sliding layer now hands the attention kernel only the keys
its window can keep. The mask zeroed every out-of-window key already, but it is
full width, so the kernel walked the whole live context - at context 4096, 3073
of 4224 keys per layer whose weight is exactly zero, on 25 of Gemma 4's 30
layers. The walk is what costs, not the work inside it. **1024p 45.3015 ->
45.8427 tok/s (+1.2%) and 4096p 31.7066 -> 42.7662 (+34.9%)**, with the 128p and
512p rows flat and inert by construction.

The change is bit-exact rather than close, so it owed no execution-profile gate
and moved no token. It also exposed a second defect that made the first
measurement a 5.5% *regression*, which is the more useful half of the unit.

## Changes

- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_layer.py`: `gemma4_layer_forward_bf16`
  gained `key_begin`. It moves the key pointer, the value pointer and the
  keep-mask pointer forward together by `key_begin` (key/value by
  `key_begin * num_kv_heads * head_dim` BF16 elements, the mask by `key_begin`
  uint8 columns) and passes `keys - key_begin`. The kernel is untouched: no new
  ABI, no kernel-side change.
- `hipengine/runtime/gemma4.py`: `_sliding_read_range(attention, start, rows)`
  returns `max(0, live - window)` for a sliding layer and a one-row block, and 0
  otherwise. It rejects a non-positive window rather than silently masking
  everything.
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention.py`: `decode_slices`
  takes `head_dim`. Narrow heads (256) take 4 slices as soon as the 1024-key
  entry threshold is reached; the 512-wide `attention_k_eq_v` layers keep the
  previous doubling rule unchanged. A dead loop after the function's `return`,
  left by the earlier policy edit, is removed.
- `tests/test_unit_gemma4_sliding_read_range.py` (new, 8 tests) pins the range
  against the mask itself - the first key the range keeps is the first key the
  mask keeps - across window and context combinations, not only at thresholds.
- `tests/test_unit_gemma4_attention_routing.py` and
  `tests/test_gpu_gemma4_attention_decode_parity.py` updated for the new
  signature, with the narrow-head rule pinned at values unrelated to its
  thresholds.
- `benchmarks/results/2026-09-26-gemma4-26b-a4b-sliding-read-range-accepted.json`,
  `benchmarks/CHANGELOG.md`, `benchmarks/README.md`: the campaign's rollup for
  this acceptance, plus the two acceptances since 2026-09-24 (the key-class
  decode kernel and the two-phase split) that had evidence rows but no rollup
  line or scoreboard update.

## Validation

- **Bit-exactness.** Masked keys contribute `exp(-inf) = 0` to both the
  denominator and the weighted sum, the row maximum is unchanged because the
  dropped entries were `-inf`, and removing zero-valued terms does not reorder
  the survivors. The 128-token generation is byte-identical to an incumbent arm
  of the same code path measured minutes earlier in the same session (128/128
  ids), and `public_path_parity` is true on all four rows.
- **Intended path, on the public surface.** Spying on both selection functions
  during a real 1024-token `LLM.generate()`: 525 sliding-layer calls skipped keys
  (`key_begin` 1..7, growing with context) and selected
  `head_dim=256 keys=1024 slices=4`; the 5 full layers stayed at 0; prefill
  blocks (rows=512) never skipped, which is the one-row restriction holding.
- **Guard.** `pytest tests/test_unit_gemma4_*.py tests/test_gpu_gemma4_*.py -q`
  exits 0 on GPU1 with the loop's configured command.
- **Rows.** 128p 51.9240 -> 51.7789, 512p 48.0158 -> 47.9667 (both flat and
  untouched - with fewer live keys than the window, `key_begin` is 0 and the
  layer passes byte-identical pointer and key arguments), 1024p +1.2%, 4096p
  +34.9%. The incumbent arm measured 45.2913 against the loop's recorded 45.3015
  (0.02% apart), which validates the pairing.
- **No gate owed.** No arithmetic changed. The slice counts the metric row uses
  are the ones the split's production-profile gate covered, and the shortened
  range only drops zero-valued terms, so the gated numerics are unchanged.

## Next

- The first measurement of this change was a **5.5% regression** (45.2913 ->
  42.8098) and the cause was the slice policy, not the read range: handing
  sliding layers exactly 1024 keys dropped them from 4 slices to 2, worth 1.3 ms
  per step, because the policy kept more than 512 keys per slice - a floor that
  is wrong for a 256-wide head. Both halves are now in the unit. The lesson worth
  carrying: a change that shortens the work can silently move a *different*
  decision that keys off the work's size, and the regression check is what
  catches it rather than the speedup check.
- The wide geometry's slice rule is still the unmodified doubling rule. It was
  measured to lose 3.5% at 1024 keys (5 of 30 layers, ~0.2% end-to-end) and that
  case does not occur on any campaign row, so it stays as measured rather than
  guessed at.
- Next in the campaign's measured order: the ~5 ms/token host gap that iteration
  25 left after removing 6.4 ms of per-launch build cost, then the MoE and dense
  decode GEMVs (6.2 + 3.9 ms of the step). The read range's gradient also makes
  long-context rows the best value per unit of work: the same technique applies
  to any policy whose live span is narrower than the mask's width.
