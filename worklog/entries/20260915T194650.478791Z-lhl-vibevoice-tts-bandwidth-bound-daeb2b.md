# VibeVoice-TTS is memory-bandwidth bound: the diffusion head streams 123 GB of weights per request

## Summary

The remaining stage costs are explained by weight streaming, not by kernel
scheduling. The diffusion head holds **246.5 MB** of weights and is invoked **once
per generated frame**, running the 20-step DDPM solver each time. That is
**123.3 GB of weight traffic per request** (246.5 MB x 20 steps x 25 frames),
which is a **0.616 s floor at the ~209 GB/s this host actually sustains**. The
stage measures **1.298 s**, so it runs at about **45% of the achievable bandwidth**.

This reframes the objective's speed question. The model is not short of compute or
of a better launch configuration; it is streaming weights and the remaining gap is
kernel arithmetic that this model's audio quality is hypersensitive to.

## The measurement

Practical bandwidth on this host, 256 MB buffers:

| operation | rate |
| --- | ---: |
| device-to-device copy | **209 GB/s** (read+write) |
| memset | **221 GB/s** (write) |

Diffusion weights, from `s.diffusion._linears`:

| | MB |
| --- | ---: |
| 4 layers x (adaLN, gate, up, down) | 226.6 |
| cond_proj, final_adaLN, final_linear, noisy_proj, t_mlp_0, t_mlp_2 | 20.1 |
| **total** | **246.5** |

Per solver pass the head runs at **rows=2** -- the CFG positive and negative
branches are already batched, so the weights are read once for both. The traffic
is therefore 246.5 MB per step, 4.93 GB per frame, 123.3 GB per request.

## Why the traffic is not reducible

- **Frames cannot be batched.** `vibevoice_tts_session.py` calls
  `diffusion.sample_speech_tokens` once per generated frame, and each frame's
  `condition` is the LM hidden state for that frame, which depends on the previous
  frame's semantic feedback. The frames are sequentially dependent, so the 25x
  traffic reduction that batching would give is unavailable.
- **The weights do not fit in cache.** 246.5 MB against a far smaller L2, and the
  same weights are re-read on all 20 steps of every frame.
- **The CFG branches are already shared**, so there is no second factor of two
  hiding in the batch dimension.

## Where this leaves the remaining headroom

Every measured gap in this model has the same shape: a kernel running at 45-68% of
the ~209 GB/s this host sustains, where closing the gap means changing the
summation order and this model's generated audio is hypersensitive to that. The
recorded evidence:

- `dense_dual_gemv_out_bf16` at 138.1 GB/s (66% of peak) at its default, 169.5
  GB/s (81%) at `threads=64` -- rejected, because the thread count moves the
  reduction width and the ten-seed quality suite drops 58/60 -> 57/60.
- Shared-memory staging to reach the same place bit-exactly: **bit-exact and
  0.99x**, because the kernel is latency-bound rather than load-width-limited.
- The accepted semantic win (BM=64 WMMA tile, 1.108 s -> 0.781 s) worked precisely
  because it changed the *column tile* and not the accumulation order.

So the honest position is that hipEngine is at **1.201 pooled RTF against torch's
1.336** on the frozen request -- faster, but 1.11x rather than the 2-10x the
objective's framing anticipates -- and the reason is a bandwidth-bound workload
whose remaining headroom sits behind an arithmetic change that this model's audio
quality rejects. That is a property of the model on this hardware, not a missing
optimisation that has simply not been found yet.

## Next

If more speed is wanted, the candidates in order of expected value are: (1) a
work-partitioning change to the GEMV family that keeps the 256-wide tree pairing,
which is the only route to the 45-68% bandwidth gaps that is safe by construction;
(2) the LM stage at 1.450 s, which has not had the weight-traffic analysis the
diffusion just got; (3) reducing the diffusion step count or the head's precision,
both of which are quality candidates rather than kernel work and would need the
generated-audio suite to justify.
