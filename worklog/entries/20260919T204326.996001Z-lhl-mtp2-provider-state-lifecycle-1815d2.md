# A refused group retains its provider state; the c=4 lane is group composition, not a release

## Summary

Task #26. Its two open questions were unanswerable from the published facts,
because `provider_readiness` reports `declined` whether or not the row still
holds provider state -- and the lifecycle answers are opposite. A row refused by
its realized width keeps the provider it can use again when its group narrows; a
row whose state is gone cannot speculate until something primes it again.

`provider_state_present` is now published beside readiness (accounting block,
`speculative_mtp.execution`, routing-pass row), and the live c=4 run answers both
questions:

| | value |
| --- | --- |
| rows | 8 (2 conversations x 4 turns, cache on, c=4) |
| declined by width | 8/8 (`plan_group_rows=4`, `plan_ar_only=true`) |
| `provider_state_present=true` while refused | **5/8** |
| `provider_state_present=false` | 3/8 -- all `prefix_reuse_k0` cache hits, which never prime |
| cycles | **0** |
| failed requests | 0 (49.6 s wall) |

So:

- **(c) A declined group does not release its rows' provider state.** It retains
  it, and retention is the correct behavior rather than a leak: the group
  narrows when co-decoding rows finish, and a narrowed group is admitted -- which
  is exactly the singleton-group row that speculated once in the earlier c=4
  artifact. The state is dead weight only while the group stays too wide, and it
  is needed again the moment it does not.
- **(a) The one-cycle row is group composition, not a lost provider.** The
  mechanism is now measured: a row's provider is primed once and stays attached
  while later cycles are refused by the realized width. A row admitted as a
  singleton and then refused inside a wider group keeps everything it needs to
  speculate again.
- **(b) No row lost state after priming in this load.** The "provider state
  released immediately after activation" case is not reproduced here, so the
  earlier release hypothesis is unsupported by this evidence rather than refuted
  in general. If it ever happens, `provider_state_present=false` next to a
  `ready`/`prompt_buffered` history is what it will look like.

The c=4 lane remains entirely autoregressive on this route (0 cycles in 8 rows),
which is a static-eligibility fact about the width-4 cell, not a provider
lifecycle fact. #25's premise and #31's attribution already point the same way:
there is nothing to win by recovering these rows until the cell itself is
qualified.

## A real defect this unit found in itself

The first live run failed every request with HTTP 500:
`'_GGUFResidentLoopRow' object has no attribute 'mtp2_provider_state_present'`.
The row is a slots dataclass, so `setattr` from the accounting layer raises
inside the engine loop instead of reporting the fact. The field is now declared
there, and `test_resident_loop_row_declares_the_diagnostic_span_field` lists
every attribute the accounting layer writes -- the previous version listed only
eight of them, which is why an undeclared field could ship. Unit tests using
`SimpleNamespace` rows cannot catch this class of bug; only the declared-field
list or a live run can.
