# The repair-free candidate engaged all along — the gate's counter was blind to a direct dispatch call

## Summary

The first layer2 gate run of `repair_free_gate_up` returned
**`candidate_dispatch_calls: 0`** and **`measurement_valid: false`**, which reads as
"the route never ran" and would have been recorded as evidence against the candidate.

**It was an instrument artifact.** The route engaged on every call.

The gate's counter (`scripts/qwen4exp_candidate_dispatch.py`) works by replacing the
**registry** entry with a counting wrapper. The plain iu8 gate/up owner is not invoked
through a registry resolve — the runner calls it as a **direct module attribute**
(`qwen4_exp_runner.py:4397`, `gguf_q4_k_selected_dual_wmma_iu8_prefill_bf16_bf16_out(...)`).
So the wrapper was installed in a place the runner never looks, and the count stayed
zero however often the route ran. `measurement_valid` then correctly refused the run,
because the gate requires `counter["calls"] > 0` — **the harness was right to refuse;
the declaration was wrong.**

This is the **same defect class** as commit `84290f3dd` ("the DP-8 prefill A/B harness
could not see its own route"), and the gate already has the remedy: a
`direct_dispatch_target` spec that patches the module attribute the runner actually
calls, with `direct_dispatch_reference` verifying the alias matches the declared
implementation.

## The fix

Added to the `repair_free_gate_up` candidate:

```python
direct_dispatch_target=("hipengine.runtime.qwen4_exp_runner",
                        "gguf_q4_k_selected_dual_wmma_iu8_prefill_bf16_bf16_out"),
direct_dispatch_reference=(
    "hipengine.kernels.hip_gfx1100.quant.gguf_q4_k_selected_prefill",
    "gguf_q4_k_selected_dual_wmma_iu8_prefill_bf16_bf16_out"),
dispatch_shape_positions=(7, 8, 9, 10),
```

`dispatch_shape_positions` records `(compact_rows, in_features, out_features_a,
out_features_b)` so the run carries the shapes it dispatched, not just a count.

## Validation

An independent engagement probe (`/tmp/repair_free_engagement_probe.py`, diagnostic,
writes nothing) built the production generator, applied the candidate's three overrides
**post-construction exactly as the gate does**, and counted the three route families.
It was run twice: once with a hand-rolled patch of the runner's module attributes, and
once with **the gate's own `count_candidate_dispatch` and the gate's own declared
spec**, so the second run validates the declaration rather than a bespoke patch.

| counter | calls |
| --- | ---: |
| plain iu8 gate/up (the candidate) | **4** |
| iu8-risk gate/up (the repair route) | **0** |
| sparse exact repair | **0** |

Recorded shape: `[50, 2560, 640, 640]` — `compact_rows=50`, `in_features=2560`,
`out_features_a=out_features_b=640`, i.e. exactly the Qwen4-Exp gate/up projection.
**`ENGAGED: True`.** The override moves the route off the repair and onto the plain
owner as intended, on a short prefill, with no repair pass.

The environment at construction is also recorded by the probe and matters for reading
the first run's `bound_environment`: `PRODUCTION_MOE_PREFILL=0` and
`Q4_K_MMQ_PREFILL=0`, so neither of the branches that precede `exact_grouped_q4_gate`
was active, and `production_grouped_moe` is layer-scoped rather than a blanket
pre-emption.
