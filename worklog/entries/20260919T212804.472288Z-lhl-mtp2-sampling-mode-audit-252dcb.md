# Sampling-mode audit: one stale contract left, in the direct-generator entry

## Summary

Task #23 asked for an audit rather than a rebuild: find tests or harness code
that still assume the pre-gate speculative sampling-mode contract, then either
close the task or name one specific remaining gap. The audit finds the served
route clean, one test-level artifact of the old framing (fixed here), and **one
real remaining gap**, named below with its two sites.

## What the served route does now

`speculative_serving_sampling_mode` (`hipengine/generation/sampling.py:895`)
answers with the three-value vocabulary the evidence rows are keyed on:
`greedy_fast` when `speculative_mtp_sampling_blockers` is empty, `sampled` when
the request actually samples and `sampled_speculative_mtp_blockers` is empty,
and `processed_argmax` otherwise. The adapter gates the sampled mode on
`_sampled_route_qualified()` (backend, target arch, quant, artifact size), the
planner propagates the resolved mode, and the API accepts
`speculative_mtp: {enabled, provider, candidate_budget}`. Nothing in the tests,
the harnesses, or the docs still asserts that a temperature request is refused
by MTP as a rule: the 2026-09-19 sampled-accept work moved that claim to a
measured 1.90x at c=1, and `benchmarks/CHANGELOG.md` states the current behavior.

Two tests do pin the *greedy* half, correctly:
`test_servable_requests_map_to_the_sampled_mode` and
`test_unservable_requests_keep_the_autoregressive_route` assert
`speculative_serving_sampling_mode` per request class, which is the current
contract rather than the old one.

## The stale test name, fixed

`tests/test_unit_sampling.py::test_speculative_mtp_sampling_allows_only_greedy_fast_policy`
was named for the pre-gate policy while its body tests
`speculative_mtp_sampling_blockers` / `supports_speculative_mtp_sampling` --
the greedy route's predicate, which is still exactly "greedy fast only". The
name invited the reading that the file states the whole policy, so it is now
`test_greedy_speculative_route_predicate_allows_only_greedy_fast_requests` with
a docstring naming the sampled predicate as the other half and
`speculative_serving_sampling_mode` as the decision between them. No assertion
changed.

## The remaining gap, named

The direct-generator MTP entry still declares the pre-gate contract:

- `hipengine/generation/qwen35_gguf.py::_generate_speculative_mtp_detailed`
  (reached from the entry above it at line 3681) raises
  `NotImplementedError("GGUF speculative MTP currently supports only
  greedy-fast sampling")` for any non-`GREEDY_FAST` sampler plan.
- The transactional verify work that path drives,
  `hipengine/generation/batch_scheduler.py::next_speculative_verify_work`,
  builds every work item with `target_sampling_policy="raw_target_top1"` and
  `compatible_sampling_modes=SPECULATIVE_TARGET_COMPATIBLE_SAMPLING_MODES`
  (`("greedy_fast",)`, line 43), and raises
  `ValueError("speculative verification requires greedy-fast sampling; ...
  incompatible fields: temperature")` for a sampled request. Its integration test
  (`test_resident_batch_scheduler_rejects_speculative_verify_for_processed_sampling`)
  pins that refusal.

Both statements are accurate for *that* implementation -- its verifier commits a
raw target top-1, so it genuinely cannot serve a sampled accept -- which is why
this is recorded rather than relaxed: widening the constants without a sampled
accept would let a sampled request run the greedy verifier and silently change
its sampling law. The repair is to stop having two sampling contracts, by
routing a sampled request to the MTP2 adapter that already owns the sampled
accept. That is a rebuild of the direct-generator entry, not an audit, and the
task says so.

Reachability: the server's sampled requests reach the adapter route and are
measured there, so the gap is confined to direct-generator callers
(`scripts/specdec2_c1_gate.py`, `scripts/specdec2_perf_bridge.py`, and any
direct `generate` caller with MTP enabled and a temperature).
