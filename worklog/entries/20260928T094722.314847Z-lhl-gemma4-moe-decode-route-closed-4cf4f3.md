# both decode moe route alternatives to the fused mmq measure slower so the route is correctly chosen

## Summary

The decode MoE gate/up runs the fused int8-dp4a MMQ at **73 GB/s** while the dense
GEMV reaches **199 GB/s** on the same hardware. That gap is 24.5 percent of decode
and it looked like a routing mistake.

**It is not.** Both alternative routes exist, both are reachable, and both measure
**slower**. The route is correctly chosen, and this closes the largest remaining
decode lead.

## The gate/up route, and its two alternatives

`gemma4_experts.py:486` selects the fused MMQ when all three hold:

```python
route_width = scratch.tokens          # the runner's declared width, not this call's lanes
if not (gemma4_moe_gate_up_mmq_enabled()
        and gemma4_moe_prefill_route_enabled(lanes=route_width, num_experts=num_experts)
        and gemma4_project_experts_gate_up_mmq(...)):
    _record_moe_route(gemma4_project_experts_rows(...))   # the ladder
else:
    _record_moe_route("gate_up_mmq32")
```

`HIPENGINE_GEMMA4_MOE_GATE_UP_MMQ` is the rollback lever, so the alternative is one
env var away. Measured on `--prompt 512 --output 128 --samples 3`:

| route | prefill tok/s | decode tok/s |
| --- | ---: | ---: |
| fused MMQ (default) | **693** | **28.06** |
| fp32 grouped / selected ladder | 320 | 24.66 |

**Disabling the MMQ route costs 2.2x on prefill and 1.14x on decode.** Both halves
move the same way, so this is not a prefill-for-decode trade.

**Which route actually ran, from the engine's own counters** rather than from a
kernel name or from the env var that was set:

```
HIPENGINE_GEMMA4_MOE_GATE_UP_MMQ unset:
  down_mmq32     360
  gate_up_mmq32  360

HIPENGINE_GEMMA4_MOE_GATE_UP_MMQ=0:
  down_mmq32       360
  grouped_prefill   58
  grouped_row4      12
  selected_gemv    290
```

## The pack8 route is wired, reachable, and already measured

`gemma4_project_experts_pack8` sits **third in the ladder, ahead of
`selected_gemv`**, and the q4_k/q5_k/q6_k kernels it resolves are registered under
`("hip_gfx1100", "moe_linear", <quant>, "expert_pack8_selected_bf16_bf16_out")`.
`_PACK8_LAYER` and `_PACK8_VARIANT` both match those registrations.

**It never fires, and that is deliberate.** It returns `False` at
`has_allocation("qweight")` because the planner does not give a Q4_K expert tensor
the packed layout by default:

```python
def pack8_layout_enabled() -> bool:
    """Whether the planner gives a Q4_K expert tensor the pack8 layout.

    **Default off, with a measured cause.** On 2026-09-27 this box measured decode
    at 21.03 tok/s before the layout and 7.64 tok/s after it ... with
    `pack8_selected` confirmed as the route that ran (928 calls).
```

**2.75x slower, plus 19.2 GB.** The recorded reason is a representation trade that
loses here: the packed form replaces raw Q4_K block metadata with precomputed fp32
scale and min terms, which is **1.33x the raw bytes**, and this projection is
bandwidth-bound rather than metadata-bound, so decoding less metadata means reading
more bytes.

So the flag's default is a named concrete cause with a measurement behind it, not a
"not yet qualified" hold, and its clearing condition is already written down: a
row count where `rows` exceeds the expert count, most plausibly a large-batch
decode.

## What this means for the 73 GB/s

The gate/up is slow **relative to the dense path**, but it is the fastest of the
three routes that exist for it. The dense path's 199 GB/s is not a reachable target
for this projection by changing route -- the dense path is a pack8 GEMV over a
different weight form, and forcing the MoE onto the packed form costs 2.75x.

The remaining explanation is structural and was already recorded in
`20260928T090630`: the MMQ block skips 31 of 32 rows' arithmetic (it is not an
arithmetic overrun) but still pays the weight tile load, the activation tile load,
and the `__syncthreads()` once per K-block. At a 1-token decode the grid is
`(5632, 8)` = 45,056 blocks of 128 threads, so 5.77M threads move 17.8 MB of
weights -- about **3 bytes per thread**. The kernel is dominated by per-block setup
and the weight stream is incidental.

**That is the thing to attack, and it is a kernel change, not a routing change.**

## Next

1. **The MoE block's per-block cost is the target**, not its route: 45,056 blocks
   moving 3 bytes per thread. A narrower column tile or a split-K changes how much
   work each block does for the same weight stream.
2. **The pack8 layout's clearing condition is untested**: a batch decode where
   `rows` exceeds the expert count. That does not move the objective's
   single-stream decode metric, so it is not the next unit, but it is a real
   experiment with a documented hypothesis.
