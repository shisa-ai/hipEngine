# Full-suite attribution: 81 failures pre-exist at the base commit, zero regressions from the Surya serving work

## Summary

The milestone full-suite run came back with **82 failures**, so it was attributed
against the pre-change commit instead of assumed. `d5a220a6f` in a separate
worktree (`git worktree add /tmp/hipengine-base d5a220a6f`) fails **81** tests in
the same run. The difference is exactly one case, and it is a case this work
*added*:

```
base: 81 failed / 23 Surya      head: 82 failed / 24 Surya
comm -13 base-failed head-failed:
  FAILED tests/test_surya_transcription.py::test_transcription_meets_ground_truth[a4]
comm -23 base-failed head-failed: (empty)
```

So there are **no regressions**, and `[a4]` inherits the pre-existing
full-suite condition described below rather than introducing one. Every Surya
test passes in isolation: `tests/test_surya_gpu.py tests/test_surya_transcription.py`
is **56 passed**, and the focused bundles for this work are green (84, 19, 16).

## What is pre-existing

**The Surya GPU family fails only inside a full-suite run.** 23 of the base's 81
failures are Surya (8 in `test_surya_gpu.py`, 15 in `test_surya_transcription.py`),
and the same set fails at head. The signature is a degenerate device state, not a
Python-logic error:

```
generated_token_ids=(0, 0, 0, 0, 0, ...)   # pad token repeated
text=''                                     # finish_details.reason='length'
text-only prefill KL vs torch oracle = nan
```

Token 0 for every step and `nan` in the logits means the runner is reading
garbage, and it happens only after the suite has run many other GPU tests. The
same tests pass in isolation, so this is a suite-order or device/JIT-state
interaction, not a property of the Surya kernels. `docs/KERNELS.md` already
documents a JIT-cache class of failure; this is not that symptom (garbage rather
than a hang) but the same family of "global state across a long run".

A second, independent pre-existing order dependence was found while looking:
`tests/test_surya_e2e.py::test_end_to_end_greedy_matches_torch_reference` **fails
in isolation** with

```
MissingGeneratorError: no generation implementation for
(surya_ocr2, cpu_reference, fp32, greedy_one_token); known: <none>
```

and **passes in the full suite**, because the registry it needs is populated by
another test's import. The two directions of order dependence coexist in the same
family.

**54 non-Surya failures are also pre-existing** and unrelated to this work:
`test_grammar_masks.py` (8, `ModuleNotFoundError: No module named 'llguidance'`,
an optional extra), the `test_laguna_h*` source-policy gates (13), the
`test_generation_batch_scheduler.py` retained-command device-env gates (13),
`test_micro_hip_dispatch_floor.py` (8), `test_agentic_harness_traces.py` (2),
`test_qwen4exp_pf1_dense_parity.py`, `test_qwen4exp_q8_0_grouped_wmma_down.py`,
`test_smoke_add_plan.py`, `test_scripts_check_published_command_drift.py`.

**One pre-existing repo-state gate is red on its own terms.**
`tests/test_benchmark_readme_sync.py::test_benchmark_readme_is_a_compact_current_scoreboard`
asserts `len(scoreboard.splitlines()) < 500` and `benchmarks/README.md` is
**1861** lines at the base commit (`assert 1861 < 500`). It was already failing
before this work, so the required Surya rollup did not break it — and the rollup
was rewrapped to be net **-4 lines** rather than growing an over-budget file. The
500-line budget and the file's actual size have diverged by 3.7x, which is a
question for the file's owners rather than something to resolve by deleting
other units' retained rows.
