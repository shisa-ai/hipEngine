# Task 46: PM4 vs hipgraph at packed widths - audit finding retracted, limit now cites measured evidence

## Summary

Task 45's guard audit flagged `GGUF_DECODE_GRAPH_SUBMISSION_POLICIES` in
`hipengine/kernels/hip_gfx1100/__init__.py` as an unjustified "until measured"
restriction, because the dense 27B entry lists only `{1: 128}` and
`_resolve_gguf_decode_graph_submission_transport` falls back to `hipgraph` when
`thresholds.get(physical_rows)` is `None`. **That finding was wrong, and the
prior evidence refutes it.** The restriction has a measured basis; the comment's
wording was the actual defect.

The requested PM4-vs-hipgraph measurement **could not be run**: this host is
`gfx1151` (Radeon 8060S), `scripts/pm4_packed_graph_bench.py` accepts only
`--backend hip_gfx1100`, PM4 is gfx1100-only (`docs/PM4.md`: "Implement gfx1100
first; do not infer gfx1151 or gfx12 safety from gfx1100"), and there are zero
gfx1151 PM4 artifacts under `benchmarks/results/`. The one reachable SSH host
(`stg04`) carries only an integrated Barcelo APU. No gfx1100 device is reachable
from here, so no substitute measurement was attempted and none is claimed.

## Evidence that retracts the finding

`benchmarks/results/2026-08-08-gfx1100-pm4-packed-c2-c4-c8-blocked.json`
(`status: measured_blocked`, W7900, `hip_gfx1100`, bf16 KV, counterbalanced,
5 paired rounds, one loaded model, 8-session pool):

| width | hipgraph tok/s | PM4 tok/s | replay wall delta | paired PM4 wins |
| --- | --- | --- | --- | --- |
| c2 | 136.27 | 121.08 | +12.55% | 0/5 |
| c4 | 197.51 | 180.88 | +9.20% | 0/5 |
| c8 | 257.22 | 243.38 | +5.69% | 0/5 |
| c1 (reference) | 10.726 ms/tok | 9.964 ms/tok | **-7.10%** | **5/5** |

PM4 capture is also 3.3x more expensive at c2 (75.50 ms vs 22.82 ms). The
artifact's own conclusion is the decision the table encodes: "keep HIP graph for
packed c2/c4/c8; canonical explicit PM4 remains eligible only for the separately
proven c1 whole-step graph until packed replay is optimized."

Its notes identify the mechanism: "The near-constant 1.77-1.86 ms PM4 replay
penalty across c2/c4/c8 points to packed-tape submission/dependency overhead
rather than model arithmetic scaling." That is a submission-layer property, so
it does not vary with model geometry. Correctness was exact throughout
(`paired_performance_trajectories_exact`, `natural_suite_trajectories_exact`,
400/800 layer comparisons at c2/c4), so this is purely a performance block.

So the pattern is c1 wins / c>1 loses, and the dense table's single c1 row is the
correct reading of it - the same shape as the MoE row, not a missing
measurement.

## Residual gap, stated honestly

The artifact measured the **MoE** geometry (`Qwen3.6-35B-A3B-UD-Q4_K_M`), not the
dense 27B. Dense packed c2/c4/c8 specifically has still never been measured. The
mechanism above argues it will lose the same way, but that is inference from the
identified cause, not a measurement, and this entry does not claim otherwise. If
gfx1100 access returns, that one run would close the gap.
