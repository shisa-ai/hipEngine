# Correction: session configuration contract and the withdrawn product-path readings

## Summary

A review of `e42be2d1c` found four defects in the product-path timing unit: the harness's
semantic cap never reached generation, the published whole-path ratio was a frame
normalisation presented as a measurement, the bandwidth analysis counted the
checkpoint's acoustic weights as AR traffic, and the "batching is the only route"
conclusion assumed two rows share a weight read that the current GEMV cannot share.
All four are confirmed in the code and corrected here. The original measurements are
kept as recorded; the readings derived from them are withdrawn and restated.

## Changes

- `hipengine/runtime/yue2_session.py`: `Yue2Session` resolved the ABC and semantic
  sampling for its *recorded* config (`effective_config`) but passed the caller's
  `abc_sampling` / `semantic_sampling` straight through to the AR session, so a
  request with no override generated with the inner `Yue2ArSession`'s
  `GenerationConfig` while the result recorded the session's own. Both paths now go
  through one resolver, `_phase_sampling`, in `plan`, `generate_semantic`,
  `_generate_locked` and `effective_config`, so the recorded settings and the executed
  settings cannot diverge. An explicit override still wins.
- `tests/test_unit_yue2_product.py`: `FakeArSession` now applies the budget it is
  given the way the real loop does, records both phases' sampling, and three tests pin
  the contract: the session's config caps generation, an explicit override beats it,
  and the staged API resolves the same way. Reverting the runtime change fails two of
  them, so the test is red on the defect rather than merely present.
- `scripts/yue2_case_timing.py`: records both sides' frames, samples and durations;
  reports per-unit stage rows plus the raw elapsed ratio and the real-time-factor ratio
  separately; refuses to report if the semantic cap did not reach generation; fixes the
  host's GPU identity parse (`rocminfo` labels the line `Name:`, which the first
  version missed).
- `benchmarks/results/yue2_product_case_timing_20260917.json`: measurements unchanged,
  with `known_issues` recording the withdrawn readings and `superseded_by` pointing at
  the fixed-token comparison that will replace them.
- `benchmarks/README.md`, `benchmarks/CHANGELOG.md`, `docs/MODEL-YUE2.md`: corrected
  interpretation (below).

## Withdrawn readings

- **154.1 s whole path at 1.12x slower** was our 172.45 s linearly normalised to the
  reference's 1 297 frames. It is an estimate, and frame-normalising attention-heavy
  work is not valid. The measured pair is 172.45 s against 137.80 s, i.e. 1.25x raw
  elapsed for different outputs (our run produced 1 451 tokens / 58.04 s of audio, the
  reference's recorded run 1 297 / 51.88 s), or 1.12x by real-time factor. Neither is
  a like-for-like whole-path ratio; the per-unit rows are.
- **13 GB per token of AR weight traffic** counted the whole 7.26 GB checkpoint. The
  checkpoint also carries the acoustic weights; the AR stage's own per-step read is
  ~3.575 GB per branch, measured from the checkpoint's tensor byte offsets: 28 layers
  of q/k/v/o/gate/up/down at 100.7 MB each (2.819 GB) plus the 756.5 MB output head.
  Two serial branch forwards therefore read ~7.15 GB per token, not 13 GB, which is
  87 GB/s at our 82.1 ms against the reference's 114 GB/s at 31.3 ms.
- **"415 GB/s required, so batching is the only route"** followed from the wrong
  traffic figure, and even at the correct one both implementations sit far below this
  host's ~256 GB/s LPDDR5X peak, so the AR stage is not at a bandwidth ceiling.
  Batching is a candidate to measure, not a proven route. Two further facts point the
  same way: this host's single-row decode GEMVs are documented at 20-28% of peak
  (`scripts/gguf_q8_0_dense_bw_microbench.py`), and the current GEMV launches
  `dim3(out_features, rows)` with the row on `blockIdx.y`
  (`kernels/hip_gfx1100/linear/dense_gemv.hip:1183`), so a two-row call re-reads the
  weights rather than sharing them; explicit reuse needs a kernel that loops over rows
  inside a block.

## Kept findings

- The per-unit stage comparison stands, because both sides' units are matched work:
  AR 82.1 ms per token against 31.3, solver 21.2 ms per frame against 21.1 (matched),
  decoder 15.5 ms per frame against 53.3 (3.44x faster). The AR stage is 69% of our
  elapsed time and is the entire remaining gap.
- The reference really does batch its CFG branches:
  `~/yue2-shootout/shared/upstream/yue2/sampling.py` builds
  `GraphAR(model, [prefix, negative], ...)` and calls `graph.step()` once per token
  (its eager path makes two model calls), while our loop calls
  `forward_layers(position, branch=0)` then `branch=1` and each call runs one row.
  That is a real 2x difference in weight passes per token, and it is what the two-row
  work has to be measured against.
- Our first reading of the token-count mismatch (1 451 against 1 297) was a symptom of
  the configuration defect, not a sampling difference: the cap was 1 298 and it did not
  reach generation.
