# Close R0510 startup probe under physical memory pressure

## Summary

R0510 asked that bounded-context startup probes and the public concurrent requests
that follow succeed under physically constrained memory, not just under a
configured budget, and that a failed probe release all of its resources. Both
hold on gfx1151, so the entry closes. `_startup_probe_width_reduction` and the
OOM retry-at-width-1 path stay as capability guards.

## Changes

- Removed R0510 from `docs/REFACTOR.md`. No code change.

## Validation

All runs: Radeon 8060S (128 GiB unified), Qwen3.8-27B-UD-Q4_K_M, `hipengine serve
--max-context-tokens 1024 --max-active-requests 4 --speculative-mtp-serving opt_in`.
A separate hog process pinned device memory first, leaving N GiB free.

- N = 26, 23, 22: the startup scratch probe passed at width 4 (packed MTP verify
  widths [2, 4]), and four concurrent completions (two `speculative_mtp: true`)
  all returned 200 with the requested routes.
- N = 21: resident prepare fit; the width-4 probe hit HIP OOM, the server retried at
  width 1, which also OOMed in prefill, and startup failed loudly with the HIP error
  named.
- N = 20: resident preparation failed loudly (`cannot allocate 16 KV pages within the
  pool budget`) before any probe ran.
- Release after a failed probe, in one process (`LLM(max_active_requests=4)`
  prepared, then a hog leaving 3 / 1.5 / 0.75 GiB): `prepare_request_scratch` at
  width 4 raised HIP OOM with zero change in tracked allocated bytes and allocation
  count. A width-1 probe then succeeded with zero residual delta. The only free-memory
  delta was 11.5 MiB on the first failure, which is not hipEngine-tracked memory
  (library/module residency) and did not recur.
- Not exercised: client cancellation during a startup probe.
