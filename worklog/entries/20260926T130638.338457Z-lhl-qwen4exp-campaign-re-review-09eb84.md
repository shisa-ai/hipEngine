# Qwen4Exp campaign re-review: the wide-F16 hoist is inert, the chunk lever is about 1.3 s, and the priority order changes

## Summary

An external review of the campaign was checked against the tree, the retained
packets and the primary upstream sources. Its family table, baseline, kernel
counts, gate numbers and qualification-scope concern all reproduce. Three
recorded conclusions do not, and the engineering priority order in
`docs/QWEN4EXP-STATUS.md` section 5 predates the last five entries.

**Correction 1 - the wide-F16 activation hoist is inert on this lane, not
merely unverified.** `wide_f16_activation_session` has exactly one production
binder, `hipengine/runtime/qwen35_gguf_runner.py:19338-19344` (the
qwen35/qwen36 resident runner). `hipengine/runtime/qwen4_exp_runner.py`, which
runs Qwen3.8-Flash-Next, contains no reference to the workspace API at all,
although it calls `launch_gguf_linear` 21 times, so the launch-time hook is on
the path and declines. The gate is `_wide_f16_activation_stage_ptr`
(`hipengine/runtime/gguf_linear.py:508-515`): it needs a bound owner of at
least `2 x rows x in_features` bytes, and returns zero without one, so every
wide launch keeps the f32-input owner. The census in
`20260921T153632.874575Z-lhl-qwen4exp-wide-f16-activation-hoist-e358ce` (792
`dense_wide256_f32_f32_out`, zero siblings) therefore has two independent
causes: the registry-population bug that unit fixed, and the absent binder.
Fixing only the first cannot change the census. The 553.9 ms is unrealized, and
the work item is binding and sizing a bounded owner in the qwen4exp prefill
path, not integrating the composite, which exists and is tested (12 unit + 7
GPU tests).

**Correction 2 - the chunk lever is about 1.3 s, not 1.7-1.9 s.**
`20260921T155134.440179Z-lhl-qwen4exp-prefill-chunk-lever-4b792a` projects the
MoE half by scaling the engine's measured four-launch per-layer times
(4 x 14.4 = 57.7 ms gate/up, 4 x 8.6 = 34.4 ms down) by the tile ratio
2801/4480 = 0.6252, giving 36.1 and 21.6 ms. Those two candidate numbers are
not measured anywhere. `benchmarks/results/2026-09-22-moe-main-kernel-cost/`
measures the one-launch case directly at 45.39 ms gate/up and 27.31 ms down
(40960 rows, 2801 tiles), which is 72.7 ms per layer against the projected
57.7 ms. The packet's own numbers on both arms give 94.88 -> 72.7 ms per
layer, 22.2 ms x 48 = **1.07 s**; pairing the engine's measured baseline with
the packet's measured candidate gives (58.0 + 34.4) - 72.7 = 19.7 ms per
layer = **0.95 s**. The scaling fails because the engine's four-launch
baseline already runs at 142 GB/s while the sweep's 40960-row launch reaches
114-126 GB/s, so the candidate point does not inherit the baseline's per-tile
rate. Time is proportional to tiles within one routing sweep (857/1024/640/640
tiles -> 14.80/17.26/11.05/10.85 ms) but not across the two measurement bases.
With the dense half at 325 ms, measured directly in
`benchmarks/results/2026-09-22-dense-chunk-rows/`, the lever is about **1.3 s**.

**Correction 3 - the chunk engine A/B the entry lists as not run was run on
2026-09-15, and it did move the MoE chunk.** The matched-throughput arm is
`scripts/qwen4exp_prefill_restore_ab.py --candidate production_baseline
--candidate-chunk-size 4096`. `Qwen4ExpGGUFResidentModelRunner` has a single
`prefill_chunk_size` driving the top-level row loop
(`hipengine/runtime/qwen4_exp_runner.py:7595`), and the depth gate records
`strict code-p4096 [1024,1024,1024,1024]` against `candidate code-p4096
[4096]`, so one 4096-row chunk means one MoE launch per layer at 40960 routes
rather than four at 10240. Measured: 4K PP 183.116 -> 190.333 tok/s (+3.94%,
0.88 s of 22.37 s), 780/780 exact logits, with the canonical numerical,
boundary/reuse, active-task and two-runner lifecycle gates all passing
(`benchmarks/results/2026-09-15-chunk4096-accounting/`). What is missing is a
re-measurement on today's composition, not a first measurement: that A/B ran at
183.1 tok/s 4K prefill on the same host (`machine_id
55ea6c509d0b49eea8de7094a1023668`) and the same 12-case fixture as the
`42ce71156` baseline's 241.9 tok/s, so the composition moved 32% underneath it.

**Blocker cleared.** The idle `hipengine serve` (pid 4175913, 98.6 GB GTT) in
`/home/lhl/hipEngine-main` that four entries recorded as blocking engine work
is terminated; GTT is about 18 MB with 113 GB available.

## Revised priority order

| Priority | Work | Why it moved | Gate |
| --- | --- | --- | --- |
| 1 | Bind and size the wide-F16 activation owner in the qwen4exp prefill path, then census and A/B | The composite is built and tested; only the binder is missing. 553.9 ms is currently 0 ms realized | Bit-identical to the f32-input owner, already proven by the existing GPU test |
| 2 | Re-measure chunk 2048/4096 on today's composition, then wire the lane-scoped default | The 2026-09-15 A/B is real but 32% stale; the lever is ~1.3 s not 1.7-1.9 s | 780-row exact numerics and a capacity probe at the new chunk |
| 3 | MoE route-tile successor: attack the per-lane risk state, not the tile height | The j32 rejection and the R9V comparison below | Bit-identical outputs and identical risk queues / main+repair chain |
| 4 | QSA K/V LDS staging with row tiling | 1.25 s recoverable, bit-exact per row | Row-exact comparison, no numerical gate |
| 5 | GR: screen with the prefill-boundary KL probe, land the unconsumed gate-write removal first | Drift localized to the Q8_0 projection boundary; three levers carry no arithmetic risk | Probe below about 5e-9 before any 780-row run |
| 6 | Dense early layers: arithmetic-preserving tiling | 12-47 and 8-47 fail, so widening the F16 scope is not available | Per-category and tail gates, not aggregate only |
| 7 | Qualification debt: full-stack strict teacher and a coverage-aware claim | See Limitations | - |

Two couplings matter. Dense and MoE savings are independent kernels and do add;
the hoist and the chunk lever do **not**, because both reduce f32-activation
staging traffic in the same K loop. And at chunk 2048 or larger the hoist
cannot fire at all while the owner is sized for 1024 rows, so priority 1 must
be sized for the intended chunk.

## Upstream evidence

Checked 2026-09-26. `pwilkin/llama.cpp` `strix-halo` is frozen at 2026-09-16
with no perf work after the journey page; R9V v0.4.4 (2026-09-25) is CED and
vision VRAM sharing only; the Husky page is unchanged.

- **Wilkin's finished-stack disable-one ablation table** is the most useful new
  artifact. It prices each mechanism on one fixed binary for this model:
  maskless KQ path 1.48x, lazy direct PLE reader 2.75x, sparse attention kernel
  1.71x, bf16 WMMA dequant GEMM 1.42x, fused HC gate GEMM + mix 1.19x, bf16 HC
  streams 1.08x, depthwise conv1d 1.08x, and flat for fused HC combine + norm,
  sparse attention entirely, and the WMMA indexer. Two arms map onto our
  remaining owners and independently corroborate the GR priority; the bf16
  WMMA dequant GEMM is already our promoted dense route. The maskless KQ path
  has no analogue here: our QSA uses a sentinel (`-3.4e38f`, `// masked`) and
  ballot/prefix masks in registers rather than a materialized dense mask
  (`hipengine/kernels/hip_gfx1100/attention/qwen4_exp_qsa_flash.hip:163`,
  `qwen4_exp_qsa.hip:1131-1233`). The PLE reader is a demand-paging mechanism
  our warm `Qwen4ExpPLEStagingRing` does not have.
- **Two independent negative results against a megakernel.** Wilkin measures
  the entire sparse path as break-even (0.98x at depth 0, 1.00x at 140k)
  against a dense head-256 flash kernel and notes dense is the numerically
  exact computation. Husky built a whole-MLP persistent dispatch with a grid
  barrier and reports identical output and no speedup, with the mechanism that
  back-to-back dispatches in one encoder already have almost no gap, so a
  megakernel only pays where it can overlap the next stage's weight loads with
  the current stage's tail. That matches our 0.46 s out-of-kernel budget.
- **The R9V MoE comparison changes priority 3.** Their 32-route-group kernel
  costs them nothing because they carry no repair contract, while our j32
  attempt spilled 492 B/thread. Our at-risk flags are already in LDS
  (`__shared__ int lds_row_atrisk[TILE_ROWS]`,
  `hipengine/kernels/hip_gfx1100/quant/qwen4_exp_q5_1.hip:1069`), so the
  register cost is the per-lane fp32 accumulation across the widened route
  tile, not the flags. A successor must shrink that state or share the weight
  read without widening the route tile. Their kernel is otherwise the same
  class we already ship: our production gate/up is
  `gguf_q4_k_selected_dual_wmma_iu8_risk_prefill_bf16_bf16_out` with iu8 WMMA
  and per-32 scales (`qwen4_exp_q5_1.hip:1266`,
  `gguf_q4_k_selected_prefill.hip:1726,2080`, no arch guard, running on
  gfx1151). Their 2.4-3.9x is measured against their own GEMV kernel and their
  parity evidence is against their own activation-quantized parent, so neither
  the ratio nor the certification transfers.
- **Chunk corroboration with a caution.** R9V independently settled on
  4096-token chunks with a 32-route group, but the mechanism is PCIe streaming
  amortization for host-resident experts, which we do not have. They report
  saturation above 4096 tokens and a decode regression at 4096 chunks (75.1 to
  70.7 tok/s) because the larger activation memory forced a different expert
  placement. Direction corroborates; magnitude and mechanism do not.
- **Correctness lead.** pwilkin fixed two QSA bugs on this model path in
  September: block metadata sized from the KV view while blocks are keyed by
  position, which trips `cell position runs past the cell window` once a cache
  carries positions ahead of its cells (after an M-RoPE image), and `-1`
  selection sentinels leaking into the masked attention path, which only the
  maskless kernel understands, faulting in `set_rows` after an image or with
  several sequences. We use sentinel masks and ship multimodal support, so both
  deserve a targeted check. This is a correctness risk, not a perf lead.

## Limitations

- Correction 1 is source inspection at `9a1e94400`. The decisive check is the
  already scripted census re-run; no engine run was performed here.
- Correction 2 replaces one model with another model, not with a measurement of
  today's composition. The 0.88 s engine A/B and the 1.3 s projection still
  disagree, and only a re-measurement settles it. The 2801-tile candidate is
  also the packet's `balanced` routing while the 1120-tile baseline is the
  engine's real routing; routing moves the tile count up to 60% at fixed rows
  (857/1024/640/640), so the real-routing count at 40960 routes is unmeasured.
  Bounding it from the engine's 512-expert histogram shape puts it near
  2.7k-2.8k, so this is second-order, but it should be captured rather than
  assumed.
- The qualification-scope concern in the external review reproduces exactly
  (`scripts/execution_profile_q8_wmma_prefill_layers_gate.py:426` sets
  `profile_qualification_claim = quality_passed and deterministic` with no
  coverage term, and `:481/:482/:497/:498` expose `--case-id`, `--limit`,
  `--decode-steps` defaulting to 24 and `--repeat-runs`), but the promoted
  artifact is full coverage: 12 cases, 128 decode steps, 3 repeats, 1548 rows,
  mean KL 3.7955e-4, p95 1.762e-3, p99 5.424e-3, max 1.5304e-2, top-1
  1538/1548, zero rows over the 2e-2 review boundary
  (`benchmarks/results/2026-09-17-q8-dense-wide-16-47-gate/`). The teacher is
  the production profile with the route's selectors cleared, which section 4
  already discloses. The residue is mechanical: add a coverage field and make
  the claim coverage-aware. Note also that the gate script's
  `--prefill-chunk-size` defaults to 1024, so a chunk promotion needs the gate
  re-run at the new chunk.
- Not checked: llama.cpp upstream master for qwen4exp perf work (only the
  `strix-halo` branch was read), and no new GPU measurement of any kind was
  taken for this entry.
