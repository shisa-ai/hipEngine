# GD-4 duplicates an already-rejected in-tree candidate (GPF-8)

## Summary

`GD-4` is the ledger's largest remaining performance lever — ~5.5% of prefill — and its
row reads as an untried idea: *"Screen state drift over 4K prompts and chunk/tail
boundaries before a full production gate."*

**The mechanism was already built, validated, and rejected in this tree as `GPF-8`**,
recorded in `docs/GGUF-PREFILL-OPTIMIZATION.md` and
`benchmarks/results/2026-07-15-gfx1100-gguf-gdn-chunkwise-wy8-rejected.json`.
**The ledger does not mention it anywhere — `grep -c GPF-8 docs/QWEN4EXP-OPTIMIZATION-LEDGER.md`
returns 0.** So the row overstates how unexplored the idea is.

`GPF-8` was an *eight-token FP32 chunkwise/triangular-WY GDN prefill* (`chain_wy8`,
default `chain_lds32_direct`) — the same reformulation `GD-4` proposes.

## What GPF-8 establishes in favour of GD-4

**The mechanism works.** `GD-3` confirmed by hardware counter that the production
recurrence kernel is bound by register-file capacity (`VGPR_Count` 256, the hardware
maximum, ~12.5% occupancy). GPF-8's chunkwise kernel compiled at **48 VGPR, 28672 B LDS,
0 scratch per thread**, workgroup 256 — a **5.3x reduction in register pressure**. So the
premise that the chunkwise form escapes the register bound is validated in-tree rather
than hypothesised.

It also passed its resource and family gates: 34 CPU oracle tests, 33 focused GPU tests,
one-token byte-exact both plain and segmented, and the synthetic 30-layer 512-token GDN
family at **47.491 ms against a predeclared 66.0 ms ceiling**.

## What GPF-8 establishes against GD-4 — the part that matters

**GPF-8 was byte-exact at one token**, so its kernel was correct, and at full chunks its
primitive stayed inside the frozen tolerance (atol 5e-4, rtol 5e-3). **The model-level
gate still failed:**

| gate | result | limit |
| --- | ---: | ---: |
| KL | **0.056522** | 0.05 |
| top-1 | **445/450 = 98.889%** | 99% |
| free-running exact trajectories | **5 of 18** | all |

So the chunkwise reassociation **alone, at FP32, with no fp16 anywhere**, was enough to
fail the model gate while every primitive-level check passed.

**That is the same failure mode as `MX-1`**, which sits 8.0-9.5x below the BF16 floor
already in the path and still failed the 18-row `prefill_last` scope.

**`GD-4` adds fp16 operands on top of that reassociation.** The state-drift screen
measured fp16 operands plus fp16 intra-chunk accumulation at **1.106e-07 NMSE** against
pure-f32 reassociation's **1.9e-13** — six orders worse. So GD-4's numerical risk is
strictly greater than a candidate already known to fail.

## The speed evidence is weaker than it looks

GPF-8's speed rejection was against an **external** floor — 2003.399 tok/s at 512 against
the 2412.320 llama.cpp HIP floor, **16.951% below** (4K passed at +1.116%) — not against
its own serial baseline. **The artifact does not record the baseline family time**, so it
neither confirms nor refutes that the chunkwise kernel beat the serial route on the GDN
stage. It cannot be cited either way.

## Scope difference that must not be hand-waved

GPF-8 was **Qwen3.6-35B-A3B `gguf_q4_k_m`** on the `qwen35_gdn_prefill_*` family. GD-4 is
**Qwen3.8-Flash-Next** `qwen4_exp_gdn_prefill_f32_kernel<true, true>` at a different shape
(Hk16/Hv48/Dk=Dv=128, 3x kv-repeat). **The mechanism transfers; the numbers do not.**

## Consequence: the first experiment is re-scoped

Building the fused fp16 WMMA scan first would be the expensive way to learn what a
decision experiment can settle.

**The cheap decisive step** is to port the *existing* CPU oracle's chunkwise/WY arithmetic
into a plain, unfused **FP32** GPU kernel for the qwen4exp shape, and run the production
envelope on **that** before writing any WMMA:

- If a correct FP32 chunkwise kernel fails the envelope here as it did at GPF-8, **the fp16
  fused build is dead** and the ~5.5% is not recoverable by this route.
- If it passes, the fp16 WMMA build is justified with the numerical question already
  answered.

The oracle half of the RED test already exists:
`hipengine.kernels.cpu_reference.gdn_prefill_chunkwise_wy_segments`, validated against an
independent token-serial f64 definition at chunk sizes 1/2/3/8/16 plus a 17-token tail
(`tests/test_unit_gdn_chunkwise_wy_cpu.py`, `tests/fixtures/gdn_chunkwise_wy_tiny.json`).
**No GPU implementation of it exists** — the name appears only in `cpu_reference/ops.py`.

## Scope and limits

- **GPF-8's KL failure is not proven to transfer.** Different model, different quant,
  different kernel family, different shape, and a different numerical contract era (the
  contract changed prospectively on 2026-07-15, the same day as this artifact). What
  transfers is the *failure mode*, not the number.
- **The attribution is clean but narrow:** byte-exact at one token and inside frozen
  tolerance at full chunks, yet KL 0.056522. That says the reassociation was sufficient to
  fail; it does not say the failure would reproduce at a different shape.
- GPF-8 bundled the chunkwise recurrence with a *direct-conv Q/K/V* input path. The
  one-token byte-exactness argues the input path was not the cause, but the artifact does
  not separate the two by measurement.
- No kernel was written and no performance claim is made. This entry changes a plan, not a
  default.
