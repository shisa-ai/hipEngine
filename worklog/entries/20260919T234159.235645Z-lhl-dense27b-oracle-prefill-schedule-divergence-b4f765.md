# The dense27B oracle divergence is between prefill schedules, not in prefix reuse

## Summary

Reading the merge-qualification artifact against the gate's own comparison
sites localizes the dense27B oracle divergence to the **prefill schedule**, not
to prefix reuse: the candidate reproduces the 256-chunked private oracle
exactly in every category, while the two other references -- the one-shot
prefix prefill and the per-token serial suffix -- disagree with it (and with
each other) in every category. Task #30 asked which route produces the
divergence; the answer from this artifact is that the prefix-reuse route does
not, and the gate is currently gating on agreement between three prefill
schedules that are not arithmetically identical.

## Changes

- None. This entry is a reading of the committed qualification artifact plus
  the gate's own comparison sites; no production or test code changed.

## Evidence

`scripts/gguf_prefix_reuse_gate.py` builds three reference states from the same
private session and compares each against the candidate:

- `semantic_boundary_mismatches` (line 642): candidate boundary vs
  `oracle_session.prefill(prefix)` -- a **one-shot** prefix prefill.
- `scheduler_state_mismatches`: candidate initial vs the oracle after the
  **256-row chunked** prefill, reported as `private_batched_recompute`.
- `initial_state_mismatches` (line 680): candidate initial vs the oracle after
  `prefill(prefix)` plus one `step()` per suffix token -- the **serial suffix**.

From `benchmarks/results/2026-09-20-gfx1151-prefix-mtp-merge-qualification.json`,
per category:

| category | private_batched_recompute (chunked) | semantic_boundary (one-shot) | initial_state (serial) | initial_output | kl_mean | trajectory |
| --- | --- | --- | --- | --- | --- | --- |
| code | pass, 0 mismatches | **False** | **False** | True | 3.9e-05 | exact |
| general_en | pass, 0 mismatches | **False** | **False** | True | 7.2e-03 | exact |
| general_ja | pass, 0 mismatches | **False** | **False** | **False** | 6.8e-01 | **not exact** |
| mixed_ja_en | pass, 0 mismatches | **False** | **False** | True | 3.4e-03 | exact |

The candidate matches the chunked oracle exactly in all four categories -- zero
boundary and final state mismatches, `output_exact=true` in three -- and fails
only the comparisons whose reference is a *different* schedule. So the failure
is not "the candidate drifts from the reference"; it is "the schedules do not
agree with each other", and the candidate is on the chunked side.

The magnitude spread is consistent with a query-window/batch-shape arithmetic
difference in the batched prefill rather than with a prefix-reuse defect: `code`
keeps byte-identical state comparisons failing while its logits agree to 4e-05
and its trajectory is exact, i.e. a state difference too small to move the
argmax, and Japanese is the category where it moves two of four teacher-forced
predictions (`[271, 271, ...]` against `[96026, 98222, ...]`). This is the same
family as the pinned bound in `docs/BENCHMARKS`-referenced
`test_split_prefill_divergence_boundaries_are_unchanged` and the 2026-09-19
entry recording that the vendored AOTriton prefill is query-window dependent
above 2,048 tokens -- here at a 1,224-token context with 256-row chunks against
a 1,224-row one-shot call.

## Next

1. Dump the mismatching state component for `code`, the smallest-KL category:
   `_compare_states` already returns per-component entries and the gate stores
   only `not mismatches` for these two comparisons, so the one-line change is to
   record the summary the way `private_batched_recompute` does. If the
   component is the paged KV (or the Conv/GDN state) rather than a metadata
   field, the schedule-arithmetic reading is confirmed; if it is an unwritten
   tail or a metadata field, the comparison itself is over-strict and the gate
   should compare the declared contract instead of raw buffers.
2. Then decide the gate's reference: the production contract is
   independent-c1 state/KV, and the candidate already satisfies it against the
   schedule the engine actually uses (256-row chunks). A one-shot and a
   per-token reference cannot both be exact against a chunked route unless the
   prefill is schedule-invariant, which it is not by construction today.
3. Only after that: the calibrated mean/tail/top-1 and task gates, and the
   full mtp-bench category suite plus heldouts for any performance claim.
