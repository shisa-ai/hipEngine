# INT8 KV C1 decode graph is exact but the 19.2 ms/step gap does not recover

## Summary

Task `#24` set out to reduce the GPU-idle share of the C1 decode step, with the
recommended lever being graph capture. The first substantive finding is that the
C1 decode graph was never missing: it is implemented, live on BF16 KV, and gated
off for INT8 by KV *storage* checks. The second is that enabling it on the IKV-C2
production layout is numerically exact but performance-neutral, so the
19.218 ms/step interior-gap ceiling from the previous unit was not recoverable.

### The path-fidelity gap in the earlier measurement chain

The previous three units (`#23` and the two gap units) measured
`Qwen35GGUFResidentSession.step()` driven directly in a Python loop
(`scripts/gguf_c1_decode_attribution.py`, the child at line 202). That is not the
path the server takes. The server goes through the resident loop
(`hipengine/generation/qwen35_gguf.py`), whose C1 entry point
`_step_native_c1_graph` already captures and replays a whole-step graph, and whose
manifest distinguishes `native_c1_graph` from `native_c1_eager`. The attribution
artifact hardcoded `"execution_mode": "eager (no graph capture)"` at line 1163
rather than reading that manifest, so its eager label was an assumption. The
launch-count and gap numbers remain valid *for the eager step they measured*, but
they were never a statement about a route without a graph option.

### The actual blocker, and it was two gates

1. `Qwen35GGUFResidentSession._resolve_decode_graph_min_replay_steps` returned
   `None` whenever `kv_storage_dtype != DType.BF16`, so the resident loop saw
   `minimum is None` and never attempted capture for any INT8 storage.
2. `gguf_decode_graph._decode_graph_kv_layout_admitted` admits INT8 only for
   `tail4_hadamard_group32` with `hadamard_group32` scales. The IKV-C2 production
   layout (`int8_per_token_head`, `uniform`, `per_token_head` FP32 scales) was
   never admitted.

Gate 1 was introduced in `24ae7f4d1` ("perf: enable state-bound GGUF graph on
gfx1151") whose own message says "keep eager for unmeasured backends, shapes, and
sampling routes" — a conservative scope restriction, not a measured
capture-safety limit. That is why the right move was to measure rather than
record an inference. Note also that gate 1 rejects the `tail4_hadamard_group32`
layout that gate 2 explicitly admits, so that admitted INT8 layout has been
unreachable from the resident loop.

### The measurement

New default-off `HIPENGINE_GGUF_INT8_KV_DECODE_GRAPH` admits the INT8 layout in
both places, keeping the eager step as the registered fallback. The harness
`scripts/gguf_true_ar_category_bench.py` gained `--kv-policy bf16|int8_per_token_head`
(it previously could only measure BF16, so the campaign's production KV layout
was unbaselineable) and now records `generated_sha256` over the whole generated
sequence plus the full `generated_token_ids` list.

W7900 (gfx1100), Qwen3.8-27B `Q4_K_M`, INT8 KV, full 10-prompt mtp-bench
category suite (code 4, general_en 2, general_ja 2, mixed_ja_en 2), 128 decode
tokens, `HIP_VISIBLE_DEVICES=0`, both runs on this host:

| | eager (flag off) | graph replay (flag on) |
| --- | --- | --- |
| `graph_replay_decode` | 0/10 | 10/10 |
| generated tokens vs eager | — | **10/10 identical**, all 129 tokens, sha256 |
| finite final logits | 10/10 | 10/10 |
| decode total | 43,297 ms | 43,067 ms |
| weighted decode rate | 29.563 tok/s | 29.721 tok/s |
| delta | — | **-0.53%** (capture included) |
| delta excluding capture | — | **-2.48%** |
| capture cost | — | 844 ms total (1.96%); 181.5 ms first, 70-82 ms after |
| per-prompt delta | — | mean -0.53%, median -0.74%, 9/10 faster, worst +1.48% |

Step wall is ~33.8 ms/token in both arms. The previous unit's ceiling was
19.218 ms/step of interior gap; essentially none of it converted to wall. The
most consistent explanation is that the "GPU idle" share was already overlapped
with GPU execution rather than host-starved, so removing the per-launch host work
does not shorten the step, and the graph's own launch/instantiate cost plus the
per-token readback bound what is left. That is a refutation of the lever
hypothesis as measured, not a failed implementation.

### Consequence for the default

The flag stays off, and the blocker is specific rather than vague:
`_resolve_decode_graph_min_replay_steps` returns the backend default floor (24 on
gfx1100) while `packed_decode_graph_min_replay_steps` applies the model/width
policy floor (128 for dense H5120 `Q4_K_M` at one row). Capture costs ~70-82 ms,
so a 24-step generation pays roughly 9% and would regress. The scalar C1 path
therefore needs the same policy floor the packed path uses before the flag can be
considered for promotion.

## Honest limits

- One run per arm. The -0.53% / -2.48% deltas are single-run and small; the
  per-prompt sign (9/10) is suggestive but the effect is not separated from
  run-to-run noise here, which is itself part of why the flag stays off.
- 128 decode tokens only, one prompt length class, one width (C1). Capture
  amortization at other horizons is inferred from the measured ~70-82 ms cost,
  not measured.
- The graph was captured per prompt, so the reported rate pays capture 10 times;
  a production session that captures once and generates far longer would see a
  smaller capture share, but that was not measured.
- The explanation for why the interior gap did not convert (host work already
  overlapped, graph overhead plus readback dominating) is inferred from the flat
  step wall. No new trace was taken to attribute the post-change step.
- This unit measured the direct-session AR path with `session.reset()` between
  prompts, not a live server request. The resident-loop eligibility code is the
  same one the server consults, but the server route was not re-run.
