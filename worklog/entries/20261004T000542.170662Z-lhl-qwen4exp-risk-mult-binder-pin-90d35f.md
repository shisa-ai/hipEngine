# The production profile pins the iu8 risk multiplier to 4.0, so the 4.0->1.0 A/B never ran

## Summary

Every "the risk multiplier is flat" reading taken on the production or canonical path
was measuring **nothing**. `hipengine/generation/qwen4_exp_profiles.py:852` binds
`HIPENGINE_QWEN4_EXP_Q4_IU8_RISK_MULT = "4.0"` as part of the production profile, and
`_apply_profile_env` (same file, line 638) writes it with an unconditional
`os.environ[key] = value`. A shell assignment is therefore discarded by the binder.

The proof is in the runs' own recorded route environment: two prefill runs launched
with `HIPENGINE_QWEN4_EXP_Q4_IU8_RISK_MULT=4.0` and `=1.0` in the environment both
report

```
bound_route_env HIPENGINE_QWEN4_EXP_Q4_IU8_RISK_MULT = 4.0
```

and both report an identical repair queue of **70,167,220 slots over 1504 calls**
(repair rate 0.8057%, `over_capacity_calls` 0). The multiplier never changed, which is
why the repair time, the risk-owner time, and the window total were all flat.

**There is no flat-time anomaly to explain.** The chain of reasoning built on that
flatness - including the fixed-grid mechanism and its 3394 ms prize - has no premise.

## Changes

No code change, no default change, nothing promoted. This entry records a measurement
defect and the experiment that has to be re-run.

## Validation

### The pin

```python
# qwen4_exp_profiles.py:852
"HIPENGINE_QWEN4_EXP_Q4_IU8_RISK_MULT": "4.0",
```

```python
# qwen4_exp_profiles.py:638
def _apply_profile_env(values: dict[str, str]) -> None:
    for key, value in values.items():
        previous = os.environ.get(key)
        ...
        os.environ[key] = value          # unconditional
        _binder_written[key] = value
```

The binder does record the discard in `_last_prebinder_conflicts` and
`_report_prebinder_conflicts()` warns about it, but the default
`PREBINDER_CONFLICT_ENV` is `warn`, so a discarded override is a warning in a log, not
a failure. The run proceeds and reports the profile's value.

### The evidence

| run | multiplier in the shell | `bound_route_env` | repair slots | calls | repair rate |
| --- | --- | --- | ---: | ---: | ---: |
| `risk-4.0` | `4.0` | `4.0` | 70167220 | 1504 | 0.0080574 |
| `risk-1.0` | `1.0` | **`4.0`** | 70167220 | 1504 | 0.0080574 |

Identical to the last digit. The second arm did not run at 1.0.

### What this explains

- The kernel trace's flat repair (4808.702 vs 4844.580 ms), flat risk owner
  (21188.779 vs 21181.150 ms), and flat window (65.068 vs 65.358 s): **both trace arms
  were the same configuration.**
- The earlier canonical-protocol reading of "flat" while an isolating harness read
  -2.11%: the canonical protocol could not move the multiplier, so flat was the only
  possible result. The isolating harness sets the variable directly (the pattern is
  visible at `scripts/qwen4exp_layer2_profile_gate.py:134`, which passes
  `environment={"HIPENGINE_QWEN4_EXP_Q4_IU8_RISK_MULT": "1.0"}` to a subprocess), which
  is why it could see an effect at all.

### What this does not change

- The **measured-and-gated** multiplier result stands: tightening to 1.0 cuts the
  repaired share of rows **0.7119% -> 0.2092%** (3.40x fewer) and passes the numerical
  gate with 3.3-6.4x margin, including 274x better than a previously rejected
  candidate on the exact scope that rejected it. That was measured by a harness that
  actually applies the value.
- The production default is **4.0**, and the profile comment says so deliberately.
  The 1.0 result was never promoted into the profile - the binding is still 4.0.

### The unsupported claim this exposes

The profile's own comment records the conclusion that "the real lever is the pass's
launch geometry, not its threshold". That conclusion rested on the production A/B
reading flat - which it did only because the multiplier was pinned. **The launch-
geometry claim is now unsupported**, and with it the withdrawn fixed-grid mechanism.

## Next

`scripts/qwen4exp_profile_gap.py --override KEY=VALUE` applies overrides *after* the
binder, which is the only way to run the 1.0 arm on the production path. That A/B is
running now at both multipliers with `--risk-diagnostics`, and each run records its
effective route environment, so the arm is provable rather than assumed.

Two outcomes, both actionable:

1. **The repair time falls ~3.40x with the queue.** Then the threshold is a real lever
   on the production path, worth roughly the repair's share of the window at 4.0
   (4808.702 ms, 7.39%) scaled by the reduction - and the promotion to 1.0 should be
   made in the profile rather than left pinned.
2. **The repair time stays flat with a queue that genuinely changed.** Then the flatness
   is real, and the per-launch fixed cost becomes the target - with the earlier grid
   analysis retracted, so that work starts from scratch.

Do not cite the 3394 ms launch-geometry prize or the fixed-grid mechanism.
