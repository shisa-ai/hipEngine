# Gemma 4 P9c: route_glue after the compaction fix, and why weighted_accumulate stops here

**fell from 97.215 ms to 34.443 ms** across the same trace shape (rocprofv3
`--kernel-trace` over `gemma4_family_census.py drive --prompt 1024
--prefill-repeats 2 --decode 1`, through `cached_build_env`), which

## Scoping weighted_accumulate — stopping rather than forcing

Guard (d) from the iteration hypothesis says to close if the kernel is
already the fastest available for its shape. It is close enough that a
rewrite does not pay:

**Standalone, GPU 1, 50 warmups then 300 timed**, tokens varying, hidden
2816, top_k 8:

| tokens | ms | expert_out bytes read | achieved |
| ---: | ---: | ---: | ---: |
| 512 | 0.0589 | 23.1 MB | 0.39 TB/s |
| 1024 | 0.0746 | 46.1 MB | 0.62 TB/s |
| 4096 | 0.3469 | 184.5 MB | 0.53 TB/s |

From `docs/ROOFLINE.md`: VRAM is 864 GB/s theoretical peak, L3 (Infinity
Cache, 96 MB) is 2.30 TB/s, L2 is 2.88 TB/s over 6 MB. At tokens 512 and
1024 the working set fits in L3, so the traffic is L3-served and 0.39–0.62
TB/s is **17–27% of the L3 ceiling** — there is apparent headroom.

**But the kernel is not bandwidth-bound, it is latency-bound**, and that
distinction is what closes it. Arithmetic: ~384 x 2816 x 8 = 8.65 MFMA in
40.9 us is about 211 GFLOP/s, roughly **0.4% of W7900's FP32 peak**. The
bytes do not saturate anything either. What the kernel actually lacks is
memory-level parallelism — each thread walks `col` with an eight-deep
dependent chain of gathers, so outstanding requests per wave stay low and
the ceiling is latency x in-flight, not bandwidth.

Fixing that means remapping the block so a thread owns a contiguous run of
columns and can issue wide vector loads per gathered row (hidden 2816 with
256 threads currently gives each thread strided, non-contiguous columns),
plus splitting the grid across columns as well as tokens. That is a
redesign, not a parameter change, and it needs its own correctness and gate
cycle.

**The arithmetic does not justify it.** Weighted_accumulate is 3.7 ms of a
451 ms device-busy prefill, about **0.8%**. A genuinely good rewrite might
halve it — 1.85 ms, **0.4% of prefill**. The change this session already
shipped (iteration 13) moved busy by 18 ms and prefill by 3.7%. Forcing a
kernel redesign for a return an order of magnitude smaller is exactly what
"measure before you tune, and do not force a fusion that cannot pay" rules
out.
