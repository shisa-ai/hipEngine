# The Q5_K gate/up WMMA prefill pair is a loss at verifier rows

## Summary

UD MTP B3 rises **43.919 -> 45.973 tok/s (K_M, +4.7%)** and **45.077 -> 46.990
(K_S, +4.2%)** at flat AR, taking MTP/AR to **1.4396x** and **1.4985x**. The
lever is a one-line row gate on the fused Q5_K gate/up pair. It also corrects a
2026-09-12 plan entry that closed the same question the wrong way.

## How the census found it

Three instruction-level rejections on the local32 IQ family (activation
vectorization, Q5_K rowtile column width, column-loop full unroll) mean the
plan's own rule applies, so this iteration started with a re-audit rather than
another tweak. `scripts/gguf_mtp_verifier_rocprof.py --mode block-verify
--block-rows 3 --block-verify-mode native --native-spec-target-cycle` on
`Qwen3.8-27B-UD-Q4_K_M` against the plain `Q4_K_M` control at the same shape:

| kernel | UD calls/step | UD us/call | UD ms/step | plain ms/step |
| --- | ---: | ---: | ---: | ---: |
| `gguf_iq4_xs_local32_gemv` | 117.0 | 96.7 | 11.314 | - |
| `q5_k_t16_dense_rowtile_gemv` | 108.0 | 84.3 | 9.100 | 2.801 |
| `gguf_q5_k_t16_dense_dual_wmma_prefill_silu_bf16` | 9.0 | 635.4 | 5.719 | - |
| `gguf_iq_dense_strict` | 11.0 | 387.7 | 4.265 | - |

Totals: UD host 50.66 ms / kernel 45.54 ms / 967 calls per step against plain
33.69 / 29.33 / 806.

The pair at **635 us/call** stood out. The model has 131 Q5_K tensors (4834 MB),
12 `ffn_gate` + 16 `ffn_up` at 61.3 MB each. Nine gate/up pairs took the WMMA
pair owner: 9 x 122.6 MB = 1103 MB in 5.719 ms = **193 GB/s**. The same model,
the same step, ran its other 108 Q5_K tensors through the t16 rowtile owner at
410 GB/s. Per tensor the pair was 317 us against 145 us for two singles.

The cause is in the variant table. Every entry is a WMMA *prefill* owner whose
block owns a fixed row tile:

```
(257, base)     tile 256 rows
(129, row128)   tile 128
(65,  row64)    tile  64
(33,  row48)    tile  48
(2,   row32)    tile  32   <-- the only entry reachable below 33 rows
```

At the native verifier envelope (2-8 rows) the row32 entry runs a 32-row WMMA
tile to produce 3. The trace confirms it: every one of the 144 pair calls had
`gridY == 1`, i.e. at most one 32-row tile, so this owner had no caller above 32
rows in the profiled workload at all.

## The change

`_q5_t16_dense_pair_silu_variant` now returns `None` below one full row tile
(`_Q5_T16_DENSE_DUAL_SILU_MIN_TILE_ROWS = 32`). The two singles then take their
normal verifier-row owner, `q5_k_t16_dense_rowtile_gemv`, which is already what
every other Q5_K tensor on this model uses at these rows. The five variants and
the pair path stay registered so a rows >= 32 caller can still take them; see
`docs/REFACTOR.md` for the removal trigger.

## The 2026-09-12 close of this item was wrong

The plan recorded: "the Q5_K gate/up dual runs the WMMA prefill owner at
verifier rows and the whole pair costs 6.38 ms/step against the plain Q4_K dual
rowtile's 8.85, so UD's arm is already the cheaper one measured."

That compares UD's nine-call per-step total against the plain control's
64-call per-step total. Those are different amounts of work on different
tensors, so the comparison cannot decide which owner is better for the same
pair. The per-tensor A/B (317 vs 145 us, same model, same step, same rows) says
the opposite, and the paired protocol now agrees. The plan entry is corrected in
place with the measurement, and the wrong comparison is named so it is not
reused.
