# Staged dense linear-attention verifier rows promoted to the gfx1151 Q4_K_M default

## Summary

The 2026-09-12 rejection of the batched (staged) dense linear-attention verifier
chain was bit-exactness only: one BF16 ULP at layer 46, `max_abs` 0.015625 on
the retained B3 fixture, against scalar AR. Bit-exactness is not the promotion
bar. Re-measured on the current dense path under the eager verifier, the staged
chain is byte-exact against the serial-exact teacher at every straddle band
(1,020-1,028, 3,528-3,532 and 8,192), the matched row-wise control is exact as
well, the committed long-context task packet binds task/AR-id/eager-ownership
equality at a 4,096-token context, and at a 3,055-token prompt the staged route
turns a 0.713x loss into a 1.630x win. It is now the backend default on gfx1151
for a loader-qualified plain `MOSTLY_Q4_K_M` artifact
(`GGUF_STAGED_LINEAR_ROWS_LONG_DEFAULT_FILE_TYPES`), with the row-wise c1 route
retained as the registered strict fallback.

## Changes

- `hipengine/kernels/hip_gfx1151/__init__.py`: new capability
  `GGUF_STAGED_LINEAR_ROWS_LONG_DEFAULT_FILE_TYPES = frozenset({"mostly_q4_k_m"})`
  replacing the boolean `GGUF_STAGED_LINEAR_ROWS_LONG` (which no longer exists,
  so an unlisted backend cannot inherit an unnamed default). gfx1100 declares
  nothing and keeps the row-wise route.
- `hipengine/runtime/qwen35_gguf_runner.py`: `_gguf_staged_linear_rows_long_enabled`
  now takes `file_type_name` and `artifact_preset_key`. An explicit env value
  still wins in either direction; otherwise the stamp-membership default applies
  only when `artifact_preset_key is None`, i.e. only to an artifact the loader
  resolved as a plain control. A preset-bound (UD) or unknown-manifest artifact
  and an unlisted stamp keep the row-wise c1 strict route. The call site passes
  the runner weights' `file_type_name` and `artifact_preset_key`.
- `hipengine/runtime/qwen35_gguf_mtp.py`: `Qwen35GGUFMTPDecodeSession` gained
  `allow_graph: bool = True` and forwards it to `verifier.prepare`. It previously
  always allowed the cached native target graph, so a packet that binds eager
  cycle ownership could only pass if the graph happened to be ineligible at its
  context (the graph context limit is 65,544 on gfx1151).
- `scripts/gguf_mtp_long_context_gate.py`: `--disable-target-graph` forces the
  eager verifier for the whole packet; the per-case records carry
  `all_cycles_eager`, `native_graph_submitted` and the route counters.
- `scripts/gguf_mtp_server_pair_bench.py`: the suite mode added with the route
  probe (`--prompts-file`, `--pad-to-tokens`) could not report a served row's
  route reliably, because the accounting arrives split across stream chunks and
  the route fields live under different keys on the streaming and non-streaming
  channels. `_merge_extension` now merges nested extensions instead of replacing
  them, `route_summary` reads both channels and the `draft_cycles` alias, and
  `_flat_generated_ids` normalizes the per-choice id list so a single-choice
  response compares as one sequence.
- `scripts/gguf_mtp_pair_rollup.py`: each row now records the route the request
  actually took (`mtp_used`, `speculative_cycles`, `mtp_coverage`, candidate
  budget, verifier route) so an MTP arm cannot be scored without its route.
- Tests: `tests/test_live_gguf_native_spec_cycle.py` (capability admission, plain
  vs preset identity, unlisted stamp, gfx1100) and
  `tests/test_unit_gguf_mtp_long_context_task_gate.py` (`--disable-target-graph`
  reaches the packet, the session stores and forwards `allow_graph`).
- Docs: `docs/ENVS.md` row rewritten as a rollback seam; `docs/REFACTOR.md`
  entries for the row-wise long-context branch and the staged-linear admission
  updated with the resolved state and a removal trigger;
  `benchmarks/README.md` new "Long-context speculation" section; artifact
  `benchmarks/results/2026-09-19-gfx1151-qwen38-staged-linear-rows-long-verifier-route.json`.

## Validation

Host: zbook, AMD Radeon 890M (`gfx1151`), ROCm from the therock env; model
Qwen3.8-27B `Q4_K_M` GGUF at `/home/lhl/models/gguf/Qwen3.8-27B-Q4_K_M.gguf`,
BF16 KV. Every command below ran in the therock environment described in the
artifact's `sources` block.

Correctness (eager route, `scripts/gguf_mtp_long_context_gate.py
--disable-target-graph`, `HIPENGINE_GGUF_STAGED_LINEAR_ROWS_LONG=1`):

- 1,020-1,028 straddle band: **19/19 exact** against the serial-exact teacher,
  `staged_chain_calls` 48 and `row_wise_attn_calls` 0 per case.
- 3,528-3,532: **13/13 exact**, same counters.
- 8,192: **3/3 exact**, same counters.
- Row-wise control at 3,528-3,532 with an explicit `=0`: **13/13 exact** with
  `row_wise_attn_calls` 192 and `staged_chain_calls` 0.
- Graph-eligible packet (no `--disable-target-graph`): the 9 eager cases (graph
  bucket miss at ends 1,024/1,026) are exact on the staged route and the 5 eager
  cases are exact on the row-wise route.
- Committed RF1 task packet at a 4,096-token context on the eager route:
  **6/6 `binding_passed`** - `output_ids_exact`, `gpu_accept_match_cpu`,
  `all_cycles_eager` and `split_k_observed` true on every task. The absolute task
  score is 0/6 (`absolute_task_quality_passed: false`) because the 8-token budget
  is consumed by the model's thinking block; that is an RF6 quality input, and
  the retained 2026-08-22 packet recorded the same failure mode on the older
  model. It is not a binding failure.

Serving A/B, one server process per arm, both arms against that process, the
true no-MTP arm selected by the request's own `speculative_mtp` field,
`--speculative-candidate-budget 3`, `--max-context-tokens 8192`,
`HIPENGINE_MTP2_MAX_CONTEXT_TOKENS=8192`:

| prompt tokens | true AR | MTP staged | MTP row-wise |
| ---: | ---: | ---: | ---: |
| 672 | 11.99 | 24.22 (2.016x) | 24.22 (2.019x) |
| 877 | 11.93 | 16.33 (1.366x) | 16.33 (1.369x) |
| 3,055 | 11.21 | 18.25 (1.630x) | 8.00 (0.713x) |

The 3,055-token cell is 2.282x apart with identical 32-token generated ids in
both arms; the AR control rates of the two server processes agree within 0.14%.
The two short shapes sit below the split threshold, where both route settings
run the same arithmetic - they are the control that the arms differ only in
route.

Category suite and heldouts at the promoted shape (`--prompts-file` +
`--pad-to-tokens`): the full mtp-bench suite is **10/10** exact on generated ids
against its own AR arm at **1.42x-2.55x (median 1.864x)** and the category
heldouts are **8/8** exact at **1.35x-2.21x (median 1.828x)**, with 98.4-99.2% of
output tokens from speculative cycles. Both suites at ~850 tokens (below the
threshold) are also 18/18 exact.

Route control at ~850 tokens: the staged and row-wise arms produce
**byte-identical output on 10/10 prompts** (both the 600-character streaming
sample and the 32-token identity probe) at rates within 3%. This is what makes
the two MTP-versus-AR text divergences at that shape attributable to sampling
below the route: they appear identically under both route settings.
