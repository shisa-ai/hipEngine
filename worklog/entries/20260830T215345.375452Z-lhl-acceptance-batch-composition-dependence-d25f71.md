# acceptance shifts with width on an identical prompt suite

## Summary

Task #16 asked whether the K3 acceptance drop with width is real or a prompt-mix
artifact. The prompt suite is loaded once, before the width loop, and reused at every
width. So the prompts are held constant, and acceptance still moves by 39 percent on
the first draft position. That makes it a batch-composition dependence.

## Changes

- None. Read-only.

## Validation

- `scripts/gguf_mtp_c1c8_server_bench.py:653` loads
  `load_prompt_suite(Path(args.prompts).resolve())` once, in the same scope that later
  drives the width loop at :735-751. There is no per-width prompt selection, so every
  width replays the same suite.
- Recorded protocol is identical across widths: candidate_budget 3, max_tokens 24,
  mtp_request_mode explicit, resident_capacity 8, correctness_contract ar_exact,
  10 cells per width with 10/10 passing and 10/10 MTP engagement.
- Against that constant input, first-position acceptance moves 0.9296 at width 1 to
  0.5710 from width 3 onward, and mean acceptance moves 0.789 to 0.467.

Acceptance is a request-local quantity. If verify and draft arithmetic were
batch-composition invariant, replaying the same prompts at a different concurrency
could not change it. This repo treats batch-composition invariance as a normative gate
rather than a preference, so this outranks K3 kernel work: either the gate has a hole on
the MTP path, or some legitimate width-dependent effect is masquerading as acceptance
drift.

Candidate mundane explanations to eliminate first, in order: scheduling order changing
which tokens reach a draft position before a wave boundary; different truncation when a
request spans waves; and warmup ordering, since the harness warms two arms per width.
None of those is expected to move a 39 percent first-position shift, but they are
cheaper to rule out than a kernel audit.

## Next

1. Write the invariance test: same suite, same seed, width 1 versus width 3, comparing
   accepted tokens positionally per request. A RED fixture is the cheapest way to
   localize this, and it is the form this repo requires before touching kernels.
2. If accepted sequences diverge, compare against the CPU reference per request to
   decide whether it is arithmetic coupling or state leakage.
3. Keep #11 separated from this. Kernel throughput work cannot fix acceptance.
