# Add the decode budget and missed reference-engine strategies to the Inkling GGUF plan

## Summary

Loom's ordinary decode on Strix Halo is already close to the weight-streaming floor. Both Inkling GGUF files read about 4 GB of weights per decode token. At the ~221 GB/s local read reference that is an 18 ms floor; Loom's measured 39–43 tok/s (23–26 ms) streams at roughly 155–175 GB/s. Its generated single-token branch issues about 26 kernels per sliding-window visit, the same order as hipEngine's ~1,230 dispatches per row. The gap is per-dispatch cost, host waits and kernel bandwidth, not kernel count. A match leaves only about 3–5 ms per token for everything except weight streaming, so whole-token submission and near-bandwidth matrix–vector kernels are prerequisites, and fusion is sized by the measured cost per dependent node.

The [GGUF implementation plan](../../docs/campaigns/INKLING2-MINI-GGUF-EXECUTION.md) now carries this budget and the strategies the first source pass missed. It also records the [matched 48-visit dump](20261124T143027.342689Z-lhl-inkling2-mini-5d86dc.md) that closed the boundary-comparison artifact on one prompt.

## Changes

- New "Decode budget" section: per-token weight bytes for both files, the Strix and W7900 floors, Loom's launch count and what differs, the overhead budget for a match, and byte arithmetic for four rows and depth-one verification. All figures are computed, not measured.
- Step 0: model-free measurement of µs per dependent node (Python, HIP graph, `aql`/`pm4` transports, `HIP_FORCE_DEV_KERNARG`, one synchronize under default and spin scheduling) and per-kernel GB/s at real decode shapes.
- Step 2: rocBLAS FP32 projections for every non-Q8_0 dense tensor (router, loop controllers and the other F32/BF16 matrices), the largest device bucket in the four-row trace; the host-built `heads × extent` relative bias uploaded every decode visit; and device token selection, using head-fused argmax partials for greedy rows and the existing native sampler where it admits the request.
- Step 3: rows per expert scale as T/16, so a matrix kernel must be tested together with the wider block. Adds Loom's RDNA3 recipe (integer dot below 64 tokens per step, FP16 WMMA on expert-sorted 64-row tiles from 64). Records that the grouped-Q8 rejection measured KL against `fast`, not against `strict`.
- Step 4 is now "capture the whole token, then fuse to the measured budget". It names the in-tree whole-step graph owners, the AQL/PM4 transports and the C function-table dispatcher, and lists source-attributed fusion candidates, including the load-time convolution-residual fold as an arithmetic candidate.
- Step 6: share dense, controller and head reads across rows before grouping experts. Step 7: a dedicated verifier window path, plus break-even acceptance from the measured window cost.
- Source table: Loom's integer-dot/WMMA split, head partials and device sampler; Gufo's default graph replay; the Vulkan fork's per-token time split and convolution-residual fold.

## Validation

- Per-token weight bytes. Mainline `UD-Q4_K_M` on `epyc`, header only through `scan_gguf`, with the visit plan of layers 0–5 once, 6–17 three times and 18–23 once. The output was experts 1.784, dense 1.444, loop controllers 0.227, head 0.492, total 3.947 GB:

  ```bash
  PYTHONPATH=. .venv/bin/python - "$MODEL" <<'PY'
  import sys
  from hipengine.loading.gguf import scan_gguf
  t = {x.name: x for x in scan_gguf(sys.argv[1]).tensors}
  plan = [*range(6), *range(6, 18), *range(6, 18), *range(6, 18), *range(18, 24)]
  def layer(L): return [(n, x) for n, x in t.items() if n.startswith(f'blk.{L}.')]
  experts = sum(x.nbytes * 8 / 128 for L in plan for n, x in layer(L) if '_exps' in n)
  dense = sum(x.nbytes for L in plan for n, x in layer(L) if '_exps' not in n and 'loop_' not in n)
  loop = sum(2 * x.nbytes for n, x in t.items() if n.startswith('blk.') and 'loop_' in n)
  head = t['output.weight'].nbytes
  print(experts / 1e9, dense / 1e9, loop / 1e9, head / 1e9)
  PY
  ```
