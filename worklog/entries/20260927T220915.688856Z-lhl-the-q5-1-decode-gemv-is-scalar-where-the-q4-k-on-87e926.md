# The Q5_1 decode GEMV is scalar where the Q4_K one is vectorized
## Summary
With the decode target now grounded — stream 3.50 GB per token at 57 percent of
peak instead of 31, where 57 percent is what llama.cpp already reaches — the
question is what limits the streaming. Reading the two decode GEMVs that cover
the expert traffic turns up a concrete structural difference between them.
## The difference
**Q5_1** (`hipengine/kernels/hip_gfx1100/quant/qwen4_exp_q5_1.hip:1169`,
`q5_1_selected_gemv_bf16_bf16_kernel`) walks the contraction **one element per
thread per iteration**:
```cpp
for (int64_t column = threadIdx.x; column < in_features; column += blockDim.x)
```
No `#pragma unroll` appears on it either.
**Q4_K** (`hipengine/kernels/hip_gfx1100/quant/gguf_q4_k_gemv.hip:1602` and again
at `:2159`) walks it **eight elements per thread per iteration**:
```cpp
const int64_t vec_stride = static_cast<int64_t>(blockDim.x) * 8;
const int64_t main_end = (in_features / vec_stride) * vec_stride;
```
The pack8 Q8_0 GEMV uses the same `block_dim * 8` shape.
So two kernels covering comparable shares of the same expert traffic use
different memory access shapes, and the scalar one is on the Q5_1 side. Q5_1 is
29 of the artifact's 658 tensors and the Q4_K family is another 29, so this is
not a corner of the model.
There are also specialised variants beside the base kernel —
`q5_1_selected_gemv_logical256_t64_bf16_bf16_kernel` and
`q5_1_selected_gemv_logical256_t128_bf16_bf16_kernel` — which may be the
optimised forms of the same operation.
## What this does not establish
**Which variant actually runs in decode.** The only trace that showed
`q5_1_selected_gemv_bf16_bf16_kernel` is the one withdrawn for being cold and
traced, so its kernel list is not evidence about the warmed decode path. The
`logical256` variants could be the ones selected, in which case the scalar base
kernel is dead code rather than a bottleneck.
It also does not establish that a scalar access shape is *the* cause of 31 percent
of peak. It is a plausible mechanism — one element per thread per iteration means
one outstanding load per thread and high per-element overhead, which is the
classic shape for reaching a fraction of bandwidth — but plausible is not
measured, and no timing was taken.
