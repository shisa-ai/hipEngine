# Q4_K_M scratch-row clamp decided: not needed on gfx1151

## Summary

Closes section K's carried-forward "Q4_K_M scratch-row clamp" item, which the
audit called the one correctness question on its list. **Decision: no clamp is
needed on gfx1151, and the `MOSTLY_Q4_K_M` key is not added.**

The gfx1100 cap is a *memory* policy, and the overrun it is associated with was
caused by the cap shrinking the allocation, not by the cap's absence:

- `38e5b85ce` (2026-09-07) added
  `GGUF_DENSE_PREFILL_SCRATCH_ROW_CAP_POLICIES` for the dense H5120
  `MOSTLY_Q4_K_M` geometry to stop session scratch being sized by the declared
  context below 4,096 rows (~1 MiB per declared token against a 64 KiB/token KV
  payload). Its evidence is memory: BF16 3,840 request peak 21.820 → 19.375 GiB,
  declared-context boundary 3,840 → 40,960 tokens, capped and uncapped runs
  token-identical.
- `2082f1353` (2026-09-09) then had to teach chunk resolution to honor the cap:
  the cap pinned the allocation at 1,024 rows while the auto policy resolved a
  4,096-row query chunk, so `for_chunk` wrote 4,096 metadata rows into a
  1,024-row positions buffer. That failure mode needs a cap that makes the
  allocation smaller than the natural chunk.

The invariant that matters is `chunk_rows <= allocated_rows`. Without a cap the
allocation is `max(selector_linear(capacity), selector_full(capacity))`, every
selector is monotone in tokens and bounded by capacity, so a request with
`rows <= capacity` cannot select more than the allocation. The outer chunk loop
additionally takes `min(_prefill_scratch_rows(rows), bulk_scratch.rows)`, and
`_chunk_ranges` only ever shortens the final chunk, which covers tails and
packed multi-request rows.

    at capacities 1,024/4,096/8,192/32,768 with tails of 0/1/3 rows and 1/2-row

## Limitation recorded in the audit

This is a proof of the selection invariant plus the policy history, not a GPU
run of the boundary matrix. The device-side metadata writes are bounded by the
same `rows` value the invariant bounds and the 2026-09-09 crash was a selection
mismatch rather than a device-side accounting error, so the static argument
covers the known failure mode — but a confirming gfx1151 run at 1K/4K/8K with
tails and packed requests is the measurement that would close it empirically.

Separately: without the cap, gfx1151 scratch still tracks the declared context
below 4,096. That is a capacity/boundary question for the gfx1151 lane (section
J's capacity items, backlog C2/C3/C5), not a correctness one, and it is
recorded as such rather than folded into this decision.
