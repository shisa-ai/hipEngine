# MTP IU4 review 2 marginal value and R13 routing

## Summary

Second review pass over `MTP-IU4.md` after the R6-R12 implementation work
(`734946037`..`bcf9ac1a2`). The implementation lane delivered: R6 raised M128
executed arithmetic 12.54 -> 64.39 TOPS (5.13x), R7 screened prefill gate/up at
2.668x-3.105x, and R8 measured a **complete-model 1.476x p512 prefill**
(384.70 -> 567.92 tok/s) before failing its quality gate.

**Corrections accepted from the implementation lane.** Three findings from the
first review were wrong and their corrections stand: (a) the 21.723-ms
"non-kernel gap" subtracted R1's *profiled* 89.348-ms kernel sum from an
*unprofiled* 111.071-ms wall and is an inference, not a measured bucket; (b) the
"~8.6 ms residual" is directly measured at 3.954 ms; (c) `output.weight` is
about 1.043 GB, not the estimated 638 MB, so the Q6 root runs at roughly 219
GB/s and is already at the practical roof rather than 62% of it. No further
correction needed; R9 item 3 correctly deprioritizes the Q6 root as a result.

Three gaps remain in the current framing.

**Gap 1 - the tiny-M DOT8 win is 81% a control defect (decisive).** R1 measures
the same 6.417-GB gate/up sweep twice: 30.162 ms @ 212.76 GB/s at B1/M2 and
35.576 ms @ 180.4 GB/s at B3/M4. Identical bytes, 17% worse bandwidth. So the
exact M4 schedule fix already targeted by R9 item 2 saves **5.414 ms (4.87% of a
111.071-ms B3 cycle)** at zero bytes and zero quality risk, while the DOT8
sidecar at the measured 1.230x saves **6.652 ms (5.99%)**. The sidecar's
**marginal** value is therefore **1.238 ms = 1.11% of a B3 cycle** for +5.33 GiB
and a full T3 campaign. The "~6%" figure quoted in the implementation summary
overstates the representation's standalone case by roughly 5x. This also
explains the M-shape of the reported results without reference to M at all: at
M2 the owner is already at 212.8 GB/s and the sidecar loses (0.952x); at M4 the
owner is 17% down and the sidecar wins (1.230x). **The sidecar's speedup is a
function of the control's inefficiency.** Ordering matters: running any tiny-M
representation screen before R9 item 2 credits the representation with the
schedule's deficit.

**Gap 2 - "M16+" is the wrong scope for R10.** Against §3's own weight-only
table at one sweep and 221 GB/s, M16 has a **14.14 TOPS memory roof** versus a
28.25 TOPS DOT4 roof: memory binds and both arithmetic lanes sit 2-8x above it.
The IU4 arithmetic lane cannot contribute below roughly **M32** (DOT4
crossover), and the full 2x not until **M~124**. Because the chunked owner
rereads weights across chunks, effective OI is lower and memory binds harder
still. Scoping R10 at M16 points it at a shape whose answer is predetermined.
Implied concurrency: a B3 verifier reaches M32 near c8 and M64+ near c16+.

**Gap 3 - R8's quality failure is non-uniform and was never localized.** The
canonical category packet is 100% top-1 with p95/p99/max KL
0.004255/0.015595/0.015673 and fails on **mean KL 0.001124 against a 0.001 gate
-- a 12.4% overage with passing tails**. The varied p512 trajectory fails much
harder (88.89% top-1, max KL 0.08754). The **5.6x max-KL spread** between the
two packets indicates concentrated, not diffuse, error. Diffuse quantization
noise does not produce that spread. No per-layer sensitivity measurement exists,
so the standard mitigations were never available to the decision.

## Changes

Documentation only. No code, kernel, measurement, or artifact changed.

- `MTP-IU4.md`
  - New Verdict subsection **"Marginal value of tiny-M U4/S4"**: the
    exact-fix-versus-sidecar table, the 81.4% figure, the 1.11% marginal result,
    and the observation that the sidecar's speedup tracks control inefficiency
    rather than M.
  - **R9 item 2** promoted to "highest-value exact item; must run before any
    tiny-M representation screen", with the marginal-value rationale and a
    requirement to record VGPR/occupancy/effective GB/s per M so the deficit's
    mechanism is named rather than inferred.
  - **R10** rescoped from M16+ to **M32/64/128**, with the binding-constraint
    table, the implied c8/c16+ concurrency, and an instruction to establish the
    physical-M histogram first so R10 can close negative without kernel work.
  - New **R13 - layer-selective routing to recover the R8 prefill gate**:
    per-layer sensitivity sweep, top-k exact retention (k=8 retains ~1.40x of
    the measured 1.476x), role-selective precision with `down` kept exact.
    Requires no new weights and no change to the immutable PFS. Carries an
    explicit anti-gaming constraint (calibration split, heldout confirmation)
    and an explicit accept criterion that passing canonical but not varied p512
    is not a pass.
  - New **Priority note**: ceiling comparison across R9/R10/R12/R13, arguing
    R13 is worth roughly an order of magnitude more than R9 and is closer to
    landing, with workload mix named as the one input that reorders it.
  - "Explicitly not scheduled" tiny-M entry updated with the marginal-value
    kill and the R9-item-2 sequencing precondition.
