# batched reused-suffix prefill: remove the <1024 paged gate, wire the extend route

## Summary

Implements the audit decision
(`worklog/entries/20260918T142514.675878Z-pi-prefix-cache-batched-suffix-audit-73980d.md`).
The reused-suffix serial loop (~34 ms/token, ~1,679 dispatches/token) existed
because one policy gate — `_validate_packed_ar_prefill_context` — refused the
packed paged prefill route at `max_live_count >= 1024`. The machinery the
batched "extend" needs (non-zero slot starts, per-slot GDN state seeding,
prefix-KV import, commit-back through the session block table) was already in
the packed AR route; the gate is removed and both reused-suffix branches now
prefill batched. Shared-prefix admission no longer requires a contiguous
suffix run, so `shared_admission_noncontiguous` cannot fire — hits at any
context length now reach the route that makes them cheaper than a miss.

## Resolution: the batched extend is correct; the gate was the wrong oracle

`initial_state_exact` compares GDN bytes against a reference that consumes the
suffix through serial `session.step` calls. Only a serial candidate can match
it. Measured on the Qwen3.5-0.8B fixture:

- restore + serial suffix versus a full private prefill + serial suffix:
  **bit-identical, 36/36 buffers** - the restore path itself is exact.
- restore + batched suffix versus that same serial reference: ~5e-3 relative
  L2 on conv and recurrent state.
- **Control at `start_position == 0` (no reuse at all): ~5e-3 relative L2,
  the same magnitude.** Batched-versus-serial GDN arithmetic differs by this
  much for every prompt the engine prefills. Requiring a reused suffix to be
  serial-bit-exact imposes a standard the default prefill path does not meet.

The contract prefix caching actually owes its users is HIT == MISS: enabling
the cache must not change the answer. Measured on Qwen3.6-35B-A3B UD-Q4_K_M,
gfx1151, real tokenized prompts from all four mtp-bench categories, both arms
teacher-forced along one common trajectory (letting each arm follow its own
greedy path makes a single differing token cascade and overstates KL by orders
of magnitude - an earlier draft of this measurement made that mistake):

- **24 of 36 category x shape configurations are bit-identical** (KL exactly
  0, top-1 100%, same first token): every shape with suffix >= 2 and total
  context <= 2048, across `code`, `general_en`, `general_ja`, `mixed_ja_en`.
- Two families diverge, identically in all four categories:
  `suffix == 1`, and `total > 2048`.

**Both divergence families reproduce identically on clean HEAD (d01ec1b51).**
Re-running the same split-versus-single-call probe in a HEAD worktree gives the
same numbers to three significant figures (kl_max 3.656e-04 at 256+1;
2.512e-04 / 1.969e-04 / 2.495e-04 / 2.614e-04 above 2048). They are
pre-existing properties of chunked prefill - a one-row prefill selects
`rows == 1` decode-shaped kernels, and splitting a >2048 context anywhere
diverges from one call - and the probe that exposes them uses no pool sharing,
no snapshot restore, and no prefix-cache machinery at all. The batched suffix
extend inherits them; it does not introduce them.

Against a true serial reference at total 2052 the single call is the closer of
the two (kl_mean 2.37e-2 versus 1.59e-1, top-1 100% versus 91.7%), so the
>2048 split path is a genuine pre-existing accuracy gap worth its own unit. It
is tracked in `docs/REFACTOR.md`, not here.

Two leads were checked and rejected: the packed AR prefill does seed GDN state
from the session (`_sync_packed_decode_initial_state`, `copy_linear_state`
defaults true) and that state is demonstrably consumed (zeroing it changes
35/36 buffers and the sampled token); and
`HIPENGINE_GGUF_GDN_PREFILL_MODE=exact` changes nothing on this path
(identical KL to five significant figures).

## Superseded blocker note

`initial_state_exact` is a strict byte-equality oracle over the GDN boundary
state, and the batched extend fails it while matching every output the gate
checks. Per the `AGENTS.md` rule that there is no exactness contract, that is
**not** an automatic rejection — but it is also not something to land on the
default path on output equality alone, for one specific reason: the divergent
boundary state is exactly what `_capture_prefix_snapshot` persists and what a
later turn restores. The deviation is not a one-shot reassociation that washes
out inside a request; it seeds every subsequent reuse of that prefix. The
live fixture test asserts token-ids, KL and 8-step continuations, so it cannot
see this — it was never designed to compare state bytes.

Before promotion this needs the production-profile treatment in
`docs/EXECUTION-PROFILES.md` (calibrated mean/p95/p99/max KL, top-1 by
category, determinism, isolation, task gates) run against the multi-turn
reuse shapes where the snapshot is re-restored, not a single-turn gate. A
prior artifact
(`benchmarks/results/2026-07-21-gfx1100-gguf-processed-argmax-p2048-active-prefix-correctness.json`)
recorded `initial_state_exact: true`, so the strict check is known-holdable
and the serial route still holds it today.

Worth ruling out first, cheaply: the route forces
`HIPENGINE_GGUF_VERIFY_CAPTURE_PREFILL_GDN=1` around every
`prefill_batch_native` call. If the captured-vs-computed boundary state
differs in that mode, this is a capture-path defect rather than batched-scan
reassociation, and the fix is local.
