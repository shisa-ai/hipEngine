# the default context 8192 is under the ceiling but max_sequence_length is unclamped above it

## Summary

The chain ends here, and the answer is that the cap is **live for any user who asks
for a longer context**, while the default sits safely under it.

`hipengine/generation/gemma4_gguf.py`:

```python
_GEMMA4_DEFAULT_CONTEXT = 8_192

context_length = _GEMMA4_DEFAULT_CONTEXT
if max_sequence_length is not None:
    context_length = int(max_sequence_length)
...
runner = Gemma4Runner(weights=weights, capacity=self.context_length)
```

`max_sequence_length` is documented in that same function as *"the public `LLM`
context limit"*. It is passed through **unclamped** into `context_length`, which
becomes `capacity`, which `__post_init__` validates against the attention kernel's
LDS budget.

So:

| request | outcome |
|---|---|
| default (no `max_sequence_length`) | 8,192 -- **under the ceiling, constructs** |
| `max_sequence_length=16384` | **over 15,616 -- raises at construction** |
| `max_sequence_length=32768` or 131072 | **raises at construction** |

## What is correct

The failure is **loud and named**: a `NotImplementedError` stating the geometry and
the byte count, raised before any allocation. Nothing truncates the context, nothing
silently serves a shorter window, and no request is quietly downgraded. That is
exactly the behaviour this repository requires of a capability miss, and it is why
this is a limit rather than a defect.

## Why it still matters

The default being 8,192 is why the objective's runs worked -- 584 tok/s prefill and
27.31 tok/s decode both came from contexts under the ceiling. So nothing currently in
use is broken.

But the ceiling is a **shared-memory budget in one attention kernel**, not a property
of the model. Gemma 4 26B is a long-context model; a user who asks for 32k gets a
refusal that names a byte count rather than a model limitation. The limit is real and
correctly reported, and it exists for a reason that the token-tiled online-softmax
rewrite removes.
