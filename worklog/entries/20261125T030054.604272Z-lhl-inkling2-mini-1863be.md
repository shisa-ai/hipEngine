# Project wide Inkling prompt blocks through grouped WMMA experts

## Summary

In `fast` a prompt block of 192 or more token rows projects its experts with a grouped WMMA kernel
instead of the FP32 four-route tiles. Narrower blocks and tails keep the tiles, which stay the
strict control. This changes arithmetic (FP16 activations in two parts, another order of FP32
accumulation), so it is a production arithmetic candidate behind the profile gate.

- **The kernel.** The block's routes are grouped by expert. One wave32 computes 32 output columns by
  64 grouped rows of one expert: each NVFP4 sub-block (16 values and one E4M3 scale) is dequantized
  to FP16 in registers, an activation enters as an FP16 high part plus an FP16 residual that the
  same weights multiply, accumulation is FP32, and the expert's outer scale is applied on store.
  Gate/up reads each token row once per route; the activation runs on the grouped rows; down writes
  route-ordered rows for the existing ordered mix. The host still selects routes and builds the
  schedule once per visit.
- **The FP32 route had little left.** The same tile arithmetic with 16 routes per wave instead of
  four is bitwise equal to the shipped tile and at most 1.3 times faster at 256 rows
  ([entry](20261125T012524.445129Z-lhl-inkling2-mini-b7405e.md)).

128 outputs, five repetitions, `fast` with 256-row blocks, W7900, mainline `UD-Q4_K_M`):

| --- | ---: | ---: | ---: | ---: |
| 47 | 0.208 s | 0.208 s | 1.00 times | 18.12 tok/s |

- The 128 greedy output tokens are the tile row's at all three depths.
- Against the 64-row `fast` row before the width change the first token now comes 1.53 times sooner
  after 575 and 2,057 prompt tokens.
- Peak GPU memory for 2,057 prompt tokens and 32 outputs is 16.14 GiB at both widths.

**Numerics at prompt ends against strict**, session-only sweep from 128- to 512-row blocks:

| Activations | Largest KL | Strict's top-1 |
| --- | ---: | --- |
| Two parts | 3.7e-6 | holds at every point |
| One FP16 value | 8.1e-5 | holds at every point |

One FP16 value is about 20 times less accurate for about 1.4 times the kernel speed, so two parts
are the default; the one-value kernel is registered as `selected_wmma_f16_f32_out` for a gated trial.

## Changes

- `hipengine/kernels/hip_gfx1100/quant/gguf_nvfp4_selected_wmma.hip` and `.py` (new): the grouped
  kernel in two variants and `fp16_parts`, the split of FP32 rows into FP16 parts.
- `hipengine/loading/inkling2_gguf_device.py`: blocks of 192 or more rows take the grouped path in
  `project_experts_mixed_rows`, from the host or from resident rows; one arena holds the FP16 parts
  and the grouped intermediates.
- `hipengine/generation/inkling2_gguf.py`: the two selections of the `fast` plan with their tile
  fallbacks.
- `tests/test_gpu_inkling2_selected_wmma.py`, `tests/test_gpu_inkling2_wmma_block.py` (new) and
  `tests/test_unit_inkling2_gguf_runtime.py`.
- `docs/KERNELS.md`: the source row. `audit/triage/kernel.jsonl`: the two new kernel rows triaged.

## Validation

- Kernel: six cases against a dequantized NumPy reference in float64 (both parts, compact and
  route-ordered stores, shared and per-route inputs, 128 and 2,304 inputs), untouched output rows,
  the FP16 split against the host's, and refused geometry. Error is within 1e-4 of the row's
  bound; measured at 1.7e-6 to 3.6e-6 of it.
- Block: 192, 200 and 257 rows through `project_experts_mixed` against the strict owner in both
  layouts, checking that the grouped kernels ran and that one upload and one download carried the
  block; 200 rows left resident through `device=`.
