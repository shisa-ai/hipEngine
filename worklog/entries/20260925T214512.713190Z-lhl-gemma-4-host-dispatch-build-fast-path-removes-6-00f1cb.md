# Gemma 4 host dispatch: build fast path removes 6.4 ms/token of per-launch key derivation (+7.2% short-prompt decode)

## Summary

Iteration 25 of the Gemma 4 26B-A4B campaign. Iteration 24's launch
census (21,813 launches for 1024p+32o, ~14 tiny elementwise launches per layer
per step) attributed iteration 19's 8.0 ms/token host gap to launch count.
Decomposing the per-launch host cost showed the gap was not in the HIP call at
all: a bare ctypes call with prebuilt args costs 1.84 us and the
`signed_kernel_fn` lookup 0.53 us, but the launcher wrapper cost **11.81 us**.
The extra ~9.5 us was `build_hip` re-deriving its cache key on every launch,
because the kernel launchers resolve their library per call (they pass no
`library=`): `build_gemma4_norm(load=True)` alone measured 7.97 us, of which
`_resolve_compiler_version` was 2.05, the target-arch read 0.85, cache-root
resolution 0.48, path normalisation ~2.2, and the rest call glue.
`os.environ.get` costs 0.463 us per read on POSIX because the mapping fsencodes
the key on every access, so the 8-12 environment reads in that derivation were
the largest single term.

A fast path in front of the loaded-library cache takes the wrapper to **5.27 us**
(2.2x less host cost per launch) and removes **6.4 ms of host time per decode
step** (989 build calls per step x 6.5 us). The campaign metric moved +0.8% at
1024p, +1.7% at 512p, **+7.2% at 128p** and stayed flat at 4096p - the gradient
expected when host dispatch is hidden behind GPU execution at long prompts and
exposed at short ones. That closes iteration 19's host-gap hypothesis as a
critical-path item at the primary row: removing 6.4 ms/token of host work moved
1024p by +0.8%, so the remaining step time there is GPU work.

## Changes

- `hipengine/core/build.py`: `_FAST_PATH_CACHE` in front of
  `_LOADED_LIB_CACHE`, keyed on the raw request (family, profile, output_name,
  `os.fspath(sources)`, cache_root, compiler, compiler_version, target_arch,
  `os.fspath(include_dirs)`, extra_flags) plus `_build_env_signature(compiler)`.
  `os.fspath` rather than `str(Path(...))` because the latter re-parses the path
  (~2 us) and was the second largest term removed.
- `_BUILD_ENV_KEYS` lists every knob the key derivation or the flag builders
  read (both arch vars, cache root, require_cached, both device-lib-path vars,
  `HIPENGINE_PREFILL_MCUMODE`, `HIPENGINE_DISABLE_UNROLL600`); the four
  version-override variables are covered via `_environment_version_identity`, so
  a mid-process environment change still selects a fresh resolution - the
  contract `_LOADED_LIB_CACHE` already had.
- `_env_get` / `_build_env_signature` read the bytes-keyed dict behind
  `os.environ` (`_ENVIRON_DATA`, shared with `os.environb`) with precomputed byte
  keys, falling back to the public mapping when CPython does not expose it or a
  caller has swapped `os.environ`. Both paths observe in-place mutations, so the
  response to environment changes is unchanged. `_version_env_keys_bytes` caches
  the four per-compiler version keys instead of rebuilding them with f-strings
  per launch.
- `tests/test_unit_build.py`: five tests, including the RED-first derivation-count
  test and a source-scan oracle that fails if a new `HIPENGINE_*` read appears in
  the module without being listed in `_BUILD_ENV_KEYS`.
- No flag, no env var, no fallback chain: the fast path is unconditional and the
  public-mapping read is a portability guard, not a configuration switch.
- Evidence row
  `benchmarks/results/2026-09-25-gemma4-26b-a4b-host-dispatch-fastpath-accepted.json`.

## Validation

- RED-first: `test_build_hip_per_launch_load_does_not_rederive_its_key`
  counts `_resolve_compiler_version` calls across six identical per-launch loads:
  6 before the change, 1 after.
- 148 passed on the gemma4 bundle (unit contracts, attention routing and
  geometry, campaign bench unit, GPU decode parity, GPU attention geometry, GPU
  weight geometry).
- 130 passed across every other `build_hip` consumer
  (`test_unit_cuda_sm120a_backend`, `test_unit_gfx1151_backend`,
  `test_unit_qwen38_int8_batch_decode_ownership_trace`,
  `test_integration_mtp_bench_tool`), including the tests that change
  `HIPENGINE_HIP_ARCH`, `HIP_DEVICE_LIB_PATH` and `HIPENGINE_BUILD_CACHE_ROOT`
  mid-process.
- Real path: 31,647 `build_hip` entries across a 1024p+32o generate, 31,647 fast
  hits, 0 slow-path derivations, 989 build calls per decode step.
- Campaign rows (`scripts/gemma4_campaign_bench.py --prompt P --output 128
  --samples 3`, label `host-dispatch-fastpath`), `public_path_parity=true` on
  every row: 1024p 43.6297 -> 43.9827 (+0.8%), 512p 47.32 -> 48.1231 (+1.7%),
  128p 48.4910 -> 51.9685 (+7.2%), 4096p 28.49 -> 28.5889 (flat). Prefill
  unchanged on every row (129/135/139/108 tok/s); public wall 10.88/6.43/3.36/42.34
  s, improved or held against 10.58/6.56/3.58/42.42 s. Campaign baseline 16.0931
  -> 43.9827, +173%.
- Host-side microbenchmark: launcher wrapper 11.81 -> 5.27 us per launch, with
  the bare ctypes call at 1.84 us and `signed_kernel_fn` at 0.53 us as the
  remaining floor.
