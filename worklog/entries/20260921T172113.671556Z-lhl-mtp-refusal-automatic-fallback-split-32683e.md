# Pin the explicit-MTP refusal and automatic-MTP fallback split

## Summary

Second slice of the same readiness item as the live-many gate. The checklist
requires that an explicit request either runs or raises a **named** capability
error, that an automatic request may take a supported fallback, and that an
explicit request is never silently downgraded.

`_speculative_mtp_route_for_request` (`hipengine/server/api.py:14290`) decides
that split. Its route-selection branches were already covered by
`test_unit_speculative_sampling_modes.py`; its two **refusal** branches were
not:

- server `speculative_mtp_serving="off"` + explicit request ->
  `OpenAIHTTPError(400, code="unsupported_parameter", param="speculative_mtp")`
- engine that cannot run MTP + explicit request ->
  `OpenAIHTTPError(501, error_type="unsupported_feature",
  code="unsupported_feature", param="speculative_mtp")`

In both conditions an automatic request returns `_SPECULATIVE_MTP_DEFAULT_ROUTE`
(the autoregressive route) instead. The function is pure over
`(config, request, engine, sampling)`, so the whole split is CPU-testable.

## Changes

- `tests/test_unit_server_mtp_refusal.py` (new), 8 cases, reusing the
  `_server_config` / `_serving_request` / `_serving_engine` / `_params`
  helpers from `test_unit_speculative_sampling_modes.py`:
  - explicit + `off` raises the 400 with the parameter named;
  - explicit + incapable engine raises the 501 with the capability named;
  - automatic falls back to AR without raising in three configurations
    (`off`, `auto` with an incapable engine, and `enabled` with an incapable
    engine), which is the permitted fallback arm;
  - `speculative_mtp: false` returns AR even in a configuration that would
    refuse an explicit `true`, because a client that declined MTP asked for
    nothing that must be refused;
  - a dedicated case asserting the refusal conditions **raise** rather than
    returning the AR route, which is the property the checklist names.
