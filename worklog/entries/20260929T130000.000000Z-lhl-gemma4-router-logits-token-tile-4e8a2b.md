# the router logits run 1.257x on the declared token-tiled schedule, bit-exact

## Summary

`20260929T123000` found four admitted gfx1151 MoE modes that the gemma4 path never consults.
This wires one of them, and records what the other three actually need -- which is not what that
entry assumed.

## The one that applies

`LAGUNA_ROUTER_LOGITS_MODE = "token_tile_8"` on gfx1151, with the admission *"Exact eight-token
router tiling preserves every token/expert's K traversal and reduction tree while reusing each
F32 weight row twice as long."*

The two kernels differ only in their grid:

```cpp
// qwen35_router_logits_bf16_f32w          dim3(num_rows, tokens)
// qwen35_router_logits_bf16_f32w_token_tile_8
//                                         dim3(num_rows, (tokens + 8 - 1) / 8)
```

One block per (expert-row, **token**) versus per (expert-row, **eight tokens**) -- so a weight row
is read once per eight tokens instead of once per token.

## Bit-exactness, and where it stops

`scripts/gemma4_router_tile_equivalence.py` runs the schedules on identical inputs and compares
logits. **This matters more here than for the compactor: the logits feed top-k selection, so a
changed logit can change which experts a token routes to.**

| schedule | vs untiled |
| --- | --- |
| `token_tile_8` | **IDENTICAL** at tokens 1/512/777/4096 and at 512x1024 rows=64 |
| `token_tile_16` | **NOT identical** -- 7.153e-07 max absolute delta, so it reassociates |

**Exactness is per schedule and is not uniform across the family**, which is why each is recorded
in the source rather than asserted for the group. `token_tile_16` runs when asked for by name and
no backend declares it as a default; `token_tile_4` is the baseline and has no tiled kernel, so
the untiled launch is what it denotes. An unknown mode is rejected by the resolver rather than
silently falling back.

## Measured

**Kernel isolation**, same session, same inputs, 20 iterations after 3 warmups, HIP event pair:

```
tokens=512 hidden=2816 rows=128:
  untiled        0.4743 ms
  token_tile_8   0.3773 ms   1.257x
```

**-0.097 ms per call over 30 layers is -2.9 ms per prefill.**

**In place** (`scripts/gemma4_expert_mmq_wrapper_split.py`), confirming the intended kernel is
the one that runs: `router logits (tile8)` 30 calls, 11.910 ms total, 0.3970 ms/call, 1.81
percent of the step -- and **zero calls for the untiled variant**.

**End to end**, 512-token prefill, median of 7 same-session runs: **0.6540 -> 0.6525 s**. That is
-1.5 ms against a -2.9 ms kernel-isolation figure, both inside this host's ~1.5 percent noise
floor (`20260929T100000`). **The claim this entry makes is the 1.257x kernel figure; the
end-to-end number is consistent with it and does not independently resolve it.**
`public_generated_equals_expected` was `True` in all seven runs.

## What the other three modes actually need

`20260929T123000` listed four modes; checking them before wiring found three do not apply to this
model as-is, and that is worth recording so the next session does not rediscover it:

- **`LAGUNA_SELECTED_DOWN_MODE`** names `mmq64x64_d4_f32_**q6**_wavecols...`. **There is no
  `wavecols`/`rawprefetch`/`doublebuf` variant anywhere in the Q5_1 down kernel**, and gemma4's
  down projection is Q5_1. The mode is Q6-only.
- **`LAGUNA_SELECTED_GATE_UP_MODE`**'s variants do exist for Q4_K, but they are **MMQ32**
  improvements, and gemma4's gate/up already takes the T16 WMMA route, measured 1.264x faster
  than MMQ32 (`20260929T080000`). It would have to beat T16, not MMQ32.
- **`LAGUNA_FUSED_SELECTED_SILU_PACK`** is gated on both of the above being in specific sets, so
  it cannot be turned on independently of them.

**So the mode set is mostly Laguna-quant-specific.** The router mode was the one that transfers,
because `qwen35_router_logits_bf16_f32w` is quant-independent -- it takes BF16 hidden and F32
weights.

## Changes

- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_router.py`: resolve
  `resolve_laguna_router_logits_mode(backend)` and dispatch through an explicit mode-to-kernel
  map. No backend branch, no new flag; the registered capability is the lever.
- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_layer.py`: `_layer_backend()` takes the backend
  from whichever projection carries resident quantized weights, since `router_proj` is always a
  raw f32 pointer. Falls back to the kernel tree's own backend for bf16 artifacts, which is what
  `gguf_embedding` does.
- `scripts/gemma4_router_tile_equivalence.py`: the oracle and the timing harness.
- `scripts/gemma4_expert_mmq_wrapper_split.py`: patches the router kernels so the running
  schedule is visible.
