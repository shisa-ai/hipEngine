# Make GPU tool provenance survive the ROCm 10.1.0 rocm-smi removal

## Summary

`scripts/gemma4_scoreboard_snapshot.py` captured `rocm-smi` output through
`_run`, which raises on a non-zero exit and does not catch `OSError`. ROCm 10.1.0
no longer ships `rocm-smi`, so provenance capture would abort outright on a clean
10.1.0 prefix.

On this host the failure is masked instead of visible: a system ROCm 7.2.3 install
still provides `/opt/rocm/bin/rocm-smi`, which stays on the default `PATH`. The
snapshot therefore "succeeds" while recording tool identity that has nothing to
do with the active stack, with no way to tell from the artifact.

Both failure modes are the same defect: provenance recorded an optional tool as if
it were authoritative. The fix captures each tool best-effort and records the
resolved path and availability, so an absent tool leaves an empty list and a stale
binary is visible rather than silently trusted.

## Changes

- `scripts/gemma4_scoreboard_snapshot.py`: added `_tool_capture`, which resolves
  the tool with `shutil.which`, returns empty output with `available: false` when
  it is missing, fails, or cannot be executed, and records the resolved path.
  `provenance()` now uses it for `rocm-smi` and adds `amd-smi static -a` capture.
  New keys: `rocm_smi_available`, `rocm_smi_path`, `amd_smi`,
  `amd_smi_available`, `amd_smi_path`. The existing `rocm_smi` key keeps its
  line-list shape, so no consumer breaks.
- `tests/test_unit_gemma4_scoreboard_snapshot.py`: added coverage for a missing
  `rocm-smi`, a stale out-of-prefix binary, and a present-but-failing tool.
- `docs/reference/THEROCK.md`: the "Known Issues On ROCm 10.1.0" call-site table
  no longer lists this script as a hard failure; it now describes the
  availability/path recording.

## Validation

- `pytest tests/test_integration_micro_collect_env.py tests/test_unit_gemma4_scoreboard_snapshot.py`
  — 6 passed.
- Live check on this host through the ROCm 10.1.0 prefix confirms the fix records

```text
rocm_smi_path:  /opt/rocm/bin/rocm-smi                        (stale system 7.2.3)
amd_smi_path:   .../therock/lib/python3.12/site-packages/_rocm_sdk_devel/bin/amd-smi
hipcc_version_first_line: HIP version: 7.16.26385-0000000
```

- `python3 scripts/docs/check_all.py` — all 4 gates pass.

The other `rocm-smi` call sites were checked and already degrade safely:
`benchmarks/micro/collect_env.py` and `scripts/gguf_c1_decode_attribution.py`
guard with `shutil.which`, and `scripts/gguf_pack8_dual_wmma_row_microbench.py`
catches `OSError`. Only this script hard-failed.

  `rocm-smi --showmeminfo vram --showuse --showtemp` record in
  `commands.environment` and validates for `GPU`/`VRAM` markers, so a new c>N/A4
  diagnostic artifact cannot be produced from a clean ROCm 10.1.0 prefix. That

  extending an artifact schema changes what past artifacts mean.
