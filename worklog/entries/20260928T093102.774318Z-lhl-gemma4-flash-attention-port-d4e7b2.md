# the exact reduction order a key-parallel port has to reproduce

## Summary

`20260928T091438` named bit-identity against `gemma4_plain` as the hard part of the
flash port without saying what it requires. This records the actual order, read
from `gemma4_warp_key_logit`, because it is the specification any port must meet
and it is more delicate than "five shuffles".

One block per `(token, head)`, 256 threads, 8 warps each owning a key. Per key,
lane `l` holds logical dimensions `l + 32k`:

```
#pragma clang fp contract(off)          // NOT decoration; see below
for (k = 0; k < 8; ++k)
    p[k] = q_s[l + 32k] * k_row[l + 32k]      // plain multiply, not an fma
if (kLeaves == 16)                            // head_dim 512 only
    for (k = 0; k < 8; ++k)
        p[k] = fmaf(q_s[l + 32(k+8)], k_row[l + 32(k+8)], p[k])
for (k = 0; k < 4; ++k) p[k] += p[k + 4]      // intra-lane
for (k = 0; k < 2; ++k) p[k] += p[k + 2]      // intra-lane
p[0] += p[1]                                   // intra-lane
for (off = 16; off > 0; off >>= 1)
    p[0] += __shfl_down(p[0], off)             // 5 warp stages
return __shfl_sync(0xffffffff, p[0], 0)        // broadcast lane 0
```

Three properties a port has to carry, each of which changes the last mantissa
bits if it is dropped:

1. **Contraction is off for the leaves.** The file states the reason: "Letting the
   compiler fuse a leaf into a tree add rounds once instead of twice and the
   logits stop being bit-identical." So a port that writes `dot += q[d]*k[d]` and
   lets the compiler contract produces a *different* number, not a
   faster-or-equal one.
2. **The 512-wide leaf is an fmaf into the 256-wide result.** The leaves reproduce
   the block and decode kernels' per-thread accumulation
   `dot = 0; for (d = tid; d < head_dim; d += threads) dot += q[d] * k[d]` with
   contraction left on. At head_dim 512 with 256 threads that is two leaves per
   thread and the second is a fused multiply-add into the first; at 256 it is one
   leaf and `fma(a, b, 0)` is exact, so a single rounded multiply is already what
   the block kernel computes. The two widths therefore need *different* code, not
   the same code with a different bound.
3. **The tree shape is fixed.** Intra-lane `k+4`, `k+2`, `k+1`, then lanes
   `+16, +8, +4, +2, +1`. The file's contract is that "every pair added is the pair
   `gemma4_attn_block_sum` adds, in the same descending order".

## What this means for a key-parallel port

The QSA layout gives lane `k` key `k`, which removes the per-key shuffle tree --
that is the whole prize. But the shuffle stages combine *lanes*, and in a
key-parallel layout each lane holds a *different key*, so lane `k` cannot read
another lane's partial for the same key. To stay bit-identical it must therefore
compute the **entire tree for its own key alone**: all 32 lane-partials `s(l)`,
each a 3-stage tree over 8 dimensions, then the 5-stage combine over `l`, in that
order, serially.

That is the same 256 multiplies gemma4 performs per key -- it spreads them over 32
lanes at 8 each and pays the tree, while the port does them in one lane and pays
nothing. The instruction win is real but it is an *issue-efficiency* win (roughly
30 instructions per 8 MACs down to about 2 per MAC), not a reduction in multiply
count, and it comes with 512 LDS reads per key per lane for `q_s` and `k_tile`
where gemma4 reads 8 of each.

This entry does not claim the port wins. It records the specification, which is
the part that is expensive to rediscover and cheap to get wrong.
