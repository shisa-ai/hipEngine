# the decode executor declares the ffn branches parallel and issues both on one stream

## Summary

`20260928T074136` raised a candidate and left it unverified: the layer plan declares two
parallel feed-forward branches as a flat sequence, but `layer_sequence` has no consumer in
`hipengine/`, so whether the runtime overlaps them was unknown. **It does not. The executor
says the branches are parallel and then issues both on the same stream.**

## The executor

`hipengine/kernels/hip_gfx1100/gemma4/gemma4_layer.py` (621 lines). Its docstring states the
structure at line 11:

```
# parallel; they are not stacked.
dense = rmsnorm(down(gelu(gate(x)) * up(x)), post_feedforward_layernorm_1)
experts = rmsnorm(moe(rmsnorm(residual, pre_feedforward_layernorm_2)), ...)
out = (residual + rmsnorm(dense + experts, post_feedforward_layernorm)) * layer_scalar
```

**And the code carries the same claim at line 504:**

```python
# --- dense branch (parallel with the MoE branch) ------------------------
```

**Then it issues the dense branch (504-553) and the MoE branch (570-594) in order, and every
launch in both takes the same `stream`.** The join is `gemma4_branch_add_bf16(buf("dense"),
buf("experts"), ...)` at line 608.

## Why that is serial by construction

**A HIP stream executes one kernel at a time.** Two branches issued on one stream cannot
overlap regardless of whether they depend on each other. **So the comment is accurate about
the data dependency and inaccurate about the execution** -- and the same is true of the
model-level docstring, which says the branches "are siblings rather than alternatives" while
the executor runs them one after the other.

**This upgrades the previous entry's candidate from unverified to verified.** The declaration
is a DAG; the execution is a sequence; the gap is a stream.

## The fix, and why it should pay on decode specifically

**Issue the MoE branch on a second stream and join before `branch_add`.** The join needs an
event recorded on the second stream and waited on the first.

**The case for it is specific to decode.** At batch 1 the GPU is massively underutilized, so
two concurrent kernels can occupy SMs that one leaves idle. That is precisely the regime where
stream overlap converts unused hardware into wall time. At prefill batch sizes the same change
would mostly contend for resources.

**Expected effect: the feed-forward half's wall time moves toward `max(dense, moe)` instead of
`dense + moe`.** The feed-forward half is roughly 10 of the layer's 18 ops, and the decode
step is dominated by per-link latency (`20260928T073101`), so removing links is the right
kind of change rather than merely a plausible one.

## What I have not measured

**The two branches are not equal in cost.** The dense branch is a gate/up/down GEMV chain; the
MoE branch is a router plus expert GEMVs. **If one dominates, the saving is bounded by the
smaller one**, and the measurement to take first is each branch's wall time at the production
decode shape. That number decides whether this is worth doing before any code is written.
