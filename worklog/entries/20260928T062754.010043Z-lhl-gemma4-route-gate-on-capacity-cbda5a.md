# the mmq gate reads the runner's declared width so a token's output no longer depends on its batch

## Summary

The two MMQ gates in `gemma4_experts_forward_bf16` read `scratch.tokens` -- the
width the **runner** was built for -- instead of `lanes` -- the width of the
**call** in flight.

`test_incremental_decode_matches_a_dense_prefill` now passes **without any env
override**, and the affected suites are **exit 0 with zero failures**.

## Why this was a contract violation, not a tuning question

`AGENTS.md` names batch-composition invariance as a distinct contract:

> Control/ownership, deterministic repeatability, arithmetic equality, and
> batch-composition invariance remain distinct contracts -- do not collapse
> them.

`gemma4_moe_prefill_route_enabled` chose between the int8-dp4a MMQ route and the
fp32 grouped family using `lanes = rows * top_k`. Those are different arithmetic,
so the *performance* choice silently became an *arithmetic* choice, and a
token's logits depended on how many tokens shared its call. It was worse than a
single-step rounding difference: **each decode step writes KV that later steps
read, so the difference compounds through the cache.**

Measured, before this change:

| comparison | divergence |
| --- | --- |
| 5-token prefill against 5 single-token decodes | **14.26%** (max abs 4.279 on scale 30) |
| same, with both MMQ routes forced off | **passes** |

The second row is what identified the cause.

## The fix

`scratch` is a capacity, not an identity -- the forward's own comment says the
caller "sizes it for the widest block it will run and then runs narrower blocks
through it". So the gate reads that capacity:

```python
route_width = scratch.tokens
```

A runner built for 512 tokens now takes the same route for its 512-wide prefill
and its 1-token decodes. The route is a property of the **runner**, not the
**call**.

**This is better than gating everything to one family**, which was the
alternative: it keeps the measured MMQ prefill win (1.27x on the 512/128
prefill) for large-capacity runners, and it keeps the cheaper per-lane GEMV grid
for small decode-only runners.

The grouped family's own internal dispatcher (`gemma4_project_experts_rows`,
which passes `compact_rows`) is deliberately **unchanged**. That crossover picks
between `selected_gemv` and `grouped_prefill`, both fp32 grouped variants, and
they were measured to agree exactly at the true shape -- so it is not an
arithmetic choice and does not need the same treatment.

## Caveat: one number is still unmeasured

A large-capacity runner's single-token decodes now run **MMQ**, whose decode
throughput is not measured. That is the number that would decide between this
fix and uniform-grouped. It is measurable by benchmarking decode on a
large-capacity runner. If it regresses materially, the fallback is to gate both
families off and pay the measured prefill cost -- the contract is not optional,
but which uniform route satisfies it is.

The change is reversible either way: both routes keep their env levers
(`HIPENGINE_GEMMA4_MOE_GATE_UP_MMQ`, `HIPENGINE_GEMMA4_MOE_DOWN_MMQ`).

## Changes

- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_experts.py`: `route_width =
  scratch.tokens` added above the gate/up gate, and both MMQ gates pass it.
- The gate's docstring now states that `lanes` is the width the runner was built
  for, why selecting by live row count is wrong, and that a caller with no
  declared width (the grouped family's own dispatcher) may still pass its live
  row count.
