# Keep Gemma 4 strict blocks off the pack8 wide-thread lever after the main merge

## Summary

The origin/main merge (`5decbf124`) combined the branch's default-on pack8
GEMV narrow-projection block-size lever (`HIPENGINE_GGUF_PACK8_GEMV_WIDE`,
one-row launches only) with main's Gemma 4 runner, whose contract is that an
N-row block equals N one-row forwards bit for bit. The lever reassociated only
the one-row side, so `tests/test_gpu_gemma4_packed_batch_forward.py`
(10/16) and `tests/test_gpu_gemma4_runner_verify_rows.py` (3/17) failed at the
merge while passing on main.

These edits were already in the shared worktree, uncommitted and unattributed;
the lead asked for them to be verified and committed as part of the merge.

## Changes

- `gguf_linear.py`: `pack8_gemv_exact_threads_session()` scope;
  `_pack8_gemv_decode_threads` keeps the parent block size inside it.
- `gemma4.py`: enter the scope around the block forward and packed prefill.
- `docs/REFACTOR.md`: record the scope and its removal condition under the
  existing `HIPENGINE_GGUF_PACK8_GEMV_WIDE` entry.
- Test repairs for failures main already carried on this host:
  `test_gpu_gemma4_moe_empty_lane_guard.py` passed `memcpy` arguments in
  (src, dst) order; `test_gpu_hip_runtime.py`'s fake library lacked the
  `hipEventQuery` entry point main's runtime binds.
