# P6e survivor equality now covers 192 characters, four times the previous span

## Summary

The survivors were already compared byte-identically against the reference, so this
item looked already satisfied. It was not quite: at `--decode-tokens 24` the
reference was only **48 characters**, which is a weak equality check. A yield that
dropped, duplicated, or reordered a token late in a short sequence could still match.
Raising `--decode-tokens` to 96 lengthens the reference and every survivor to
**192 characters** and makes the assertion cover four times as many tokens.

`--decode-tokens` sets `max_tokens` for every arm, so this is one flag rather than
new harness code. No gate logic changed.

## Changes

- Retained proof re-run at `--decode-tokens 96` instead of 24, lengthening the
  reference and all five survivors from 48 to 192 characters.
- `docs/SERVER-DIRECT-PARITY-ROADMAP.md`: the coverage table's survivor row now
  records the 192-character span and the single shared hash instead of only
  "byte-identical".

No harness or gate logic changed; the only difference is the decode length passed on
the command line.

## Honest limits

- A longer survivor strengthens the equality check but does not make it exhaustive: a
  divergence beyond 192 characters is still unobserved.
- The reference itself is a greedy 192-character generation, so this compares the
  yield's output against the same engine's output, not against an independent oracle.
  It detects a yield that corrupts state, not a model that is wrong.
- Decode length is now four times the earlier runs, so the wall time per run grew
  accordingly. No gate threshold was changed to accommodate that.
- I initially misread the artifact while checking this: the per-request records carry
  `chars` and `text_sha256`, not `text`, so my first reading printed zero-length text
  for fields that were in fact 192 characters. The conclusion above is from the
  `chars` and hash fields.
