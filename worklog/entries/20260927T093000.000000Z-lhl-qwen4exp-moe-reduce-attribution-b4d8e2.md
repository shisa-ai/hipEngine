# moe_reduce is 81% maps; the router is reduction-bound, not traffic-bound

## Summary

Sprint R asked to attribute maps, scatter/gather and reductions before fusing, to
avoid counting the same saving twice, and to report complete-operation cost rather
than the standalone bucket.

**moe_reduce is 81% maps.** From the shipped-default role trace (halved from 2
repetitions): router logits 617.73 ms (78.7%), weighted_lanes_sum 67.66 (8.6%),
group_scatter_gather 52.06 (6.6%), silu_mul_dual 29.22 (3.7%), router_select 18.25
(2.3%) = 784.93 ms against the taxonomy's 758.4. By class: **maps 635.98 (81.0%),
reduction 67.66 (8.6%), scatter/gather 52.06 (6.6%), activation 29.22 (3.7%)**.
**The reduction is not the target** - fusing it caps at 8.6% of the bucket.

**The router's limiter is the reduction structure, not traffic.** Screened at the
real shape (1024 x 2560 x 512); the faithful T=4 copy is **bit-identical** to the
shipped library, so the screen is attributable:

| variant | ms | vs shipped |
| --- | ---: | ---: |
| shipped | 3.0126 | 1.000 |
| faithful T=4 copy | 3.0877 | 0.976 (diff 0.0) |
| T=8 / T=16 / T=32 | 2.7062 / 2.9069 / 4.0032 | 1.11 / 1.04 / 0.75 |
| 2D tile 16x16 (10x less traffic) | 11.7314 | **0.257** |
| **warp-per-token (shuffle reduction)** | **1.4834** | **2.031** |

Tile width is flat. Traffic is refuted: the shipped kernel sustains **2222 GB/s**
of L2-resident re-reads (6.71 GB in 3.01 ms), and a 2D tile with 10x less traffic
is **3.9x slower** because it adds an LDS round-trip per operand element. The
lever is the **8-barrier 256-thread LDS tree reduction**, which warp-per-token
replaces with a 5-step shuffle for **2.03x**. **Prize 313.6 ms.**

The warp variant is **not bit-exact** (max abs diff 4.9e-7) - the reduction order
changes - so it needs the production profile gate and a registered strict
fallback, not a parity argument.

**Activation packing is not ours to collect.** The taxonomy's `quantize_pack` is a
comparator-side family: hipEngine **0.0**, halobox-base 284.8, halobox-pr63 0.0.
Our bucket is 0.0 because the conversion is **inside** the matmul kernels. Our
complete explicit conversion is `f32_to_bf16_kernel` 11.16 + `bf16_to_f32_kernel`
5.06 = **16.22 ms**. Quoting 284.8 as recoverable would double-count with
`dense_projection`. It is not clean on the comparator side either: PR #63 moved
`dense_projection` only 162.4 ms and `expert_gate_up` only 57.6 while
`expert_down` fell 737.0, so the bucket's disappearance and the matmul speedup
are entangled.

## Double-counting guard

Each saving is reported once, in the family that owns it. The moe_reduce classes
sum to 100% with no overlap; the comparator's bucket elimination is not claimed
here; the iu8 repair passes are not counted here because they are folded into
`expert_gate_up` and `expert_down`.
