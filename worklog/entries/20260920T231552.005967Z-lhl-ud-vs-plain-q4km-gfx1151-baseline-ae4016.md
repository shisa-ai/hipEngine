# Qwen3.8-27B UD-Q4_K_M vs plain Q4_K_M same-session baseline on gfx1151

## Summary

No current Qwen3.8-27B UD row existed for this host. Both arms ran back to back in
one thermal window under one `/tmp/ud-baseline/run_pair.sh` invocation, so the
comparison is same-conditions rather than cross-date. The UD file is **32-33%
slower on decode and 38-43% slower on prefill** at every measured shape, while
using 0.82 GiB less tracked peak:

**These are zbook rates.** The task's stated baseline (404.5 / 12.15) is the
desktop `gfx1151` host, which is a different physical machine from this laptop
(`zbook`); see the first item below.

| Shape | Plain prefill | UD prefill | Δ | Plain decode | UD decode | Δ |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 512/128 | 311.955 | 194.684 | -37.59% | 11.6348 | 7.8765 | -32.30% |
| 1024/128 | 310.728 | 179.983 | -42.08% | 11.3765 | 7.7184 | -32.15% |
| 4096/128 | 297.077 | 167.971 | -43.46% | 11.5605 | 7.7285 | -33.15% |

Two things came out of the run and neither is a throughput claim.

**The published plain row is a different physical host, so it is not a baseline
here.** The same-session plain arm
measures 311.955 / 11.6348 at 512/128 against the published `benchmarks/README.md`
row of 404.474 / 12.150 from commit `3e2431130`. That row carries
`host_name: gfx1151` and `machine_id 55ea6c509d0b49eea8de7094a1023668`; both arms
here ran on `zbook` (`87c566d30a5645cf8d12ed7ef6b6e1e8`). Per
`docs/OPTIMIZATION.md` §2 those are independent lanes, so the 22.9% is a host
difference and not a regression. It is also already recorded:
`docs/campaigns/UD-OPTIMIZED-ROUTE-PLAN.md` item 0 gives zbook's plain prefill
floor as 294.8 tok/s against the desktop's 396.1, and
`2026-09-08-zbook-ud-prefill-route-gap.json` describes zbook as a "laptop;
power- and thermal-limited" host. This session's 311.955 sits just above the
recorded floor, which is the expected direction. Everything else was identical
across the two runs: protocol, execution profile, manifest SHA, all ten variant
selections, model fingerprint, HIP version, clang commit, and every `HIPENGINE_*`
variable except the two compiler-version-file pins. I first wrote this up as an
unexplained regression before checking the host identity, and the task's own
stated baseline (404.5) is the desktop row, so the absolute rates here must not
be read against it.

**The UD file keeps no tuned decode layouts.** The route audit shows plain
routing 288 Q4_K tensors to `gguf_q4_k_t16_v1`, 48 Q5_K to `gguf_q5_k_t16_v1`,
and 65 Q6_K to the planar/T16 variants, while UD routes everything except 103
Q4_K tensors to the generic `raw-gguf-kernel` path. The mechanism is a real call
chain, not an inference from the route table: the loader calls
`preflight_qwen35_gguf_artifact()` without `repack_veto`
(`qwen35_gguf_materialize.py:885`), the admission layer then pre-applies the
model-wide raw-IQ veto
(`qwen35_gguf_admission.py:2393-2400`), and `decode_repack` is already `False`
by the time the planner's per-tensor branch runs
(`qwen35_gguf_materialize.py:444-452`, `:1298`). So
`HIPENGINE_UD_REPACK_ELIGIBILITY`'s documented default `per-tensor` - which
`qwen35_gguf_policy.py:94-104` describes as keeping T16/x8/planar layouts for a
dense model's Q4/Q5/Q6/Q8 tensors - does not reach the production AR path.
Running the audit under both env values produces byte-identical route tables.

I corrected two claims mid-run. First, the route audit prints
`nextn map: validation=FAILED` for UD, and I first read that as a defective draft
block. It is not: the audit calls `build_qwen35_gguf_nextn_tensor_map(info,
strict=False)` without the artifact pin, so it validates the UD draft block
against the plain expectation. With the preset's own pin the strict build passes,
and the UD file resolves preset `gguf_ud_q4_k_m` with scopes `("ar", "mtp")`.
Second, I first wrote the published-row comparison up as an unexplained 22.9%
regression with the toolchain install root as the leading hypothesis; it is a
cross-host comparison, which `docs/OPTIMIZATION.md` §2 forbids, and the host
identity check settled it.

## Validation

- Both arms ran the harness's own gate: 18 category/heldout prompts each, with
  generated ids, final full logits, and state fingerprint matching between the
  eager trajectory and the captured graph. Both arms passed 18/18, and the
  harness refuses to emit timings otherwise.
- Host was clean: zero GPU processes during the run, `power_dpm_force_performance_level=auto`,
  governor `performance`, tuned `accelerator-performance`, load average 0.91.
- Every per-shape CV is at or below 0.72% (worst: UD prefill at 1024, 0.721%);
  decode CVs are at or below 0.67%.
- Harness defaults verified against the published command: `--prompt-lengths
  512 1024 4096`, `--decode-tokens 128`, `--max-sequence-length 8192`,
  `--warmups 1`, `--repetitions 3`, and the script is byte-identical across
  `3e2431130..HEAD`.
- Route diagnostic: `scripts/gguf_quant_route_audit.py` on both files, plus an
  env A/B (`HIPENGINE_UD_REPACK_ELIGIBILITY=per-tensor` vs `model-wide`) showing
  identical route tables.
- Draft-block correction verified by direct execution: preset resolution,
  `resolve_qwen35_gguf_nextn_draft_qtypes`, and a strict build with the pin.

## Next

- **The repack question is the actionable one and it is unmeasured.** Granting
  per-tensor eligibility to this artifact would put its Q4/Q5/Q6/Q8 tensors on
  the tuned layouts, which is the difference between this file and the plain
  file's routing. Whether that recovers any of the 32-43% gap is unknown: it
  needs a layout change, the execution-profile correctness gate for the affected
  variants, and a measurement. Nothing in this unit did any of that, and the
  measurement is not a prerequisite for trying it.
- **Whether pre-applying the model-wide veto for a dense UD file is intended is
  not stated in the code.** The comment at `qwen35_gguf_materialize.py:439-445`
  justifies the model-wide behaviour for raw-IQ rank-3 expert models ("one
  compatible resident plan instead of mixing compressed rank-3 layouts with
  Q4-oriented T16 residents"); the policy docstring says the opposite for dense
  models. Recorded as an open question rather than a defect, because the two
  statements may both be deliberate for different model classes.
- **The published-row question is closed, not open.** It was a cross-host
  comparison. The desktop `gfx1151` lane has its own published plain row and this
  unit did not measure that host.
- **UD MTP on gfx1151 is unmeasured.** The preset carries the MTP scope and its
  pinned draft map passes the strict build, but the minted U6 certificate
  declares `backend=hip_gfx1100`, `context_max=1023`, `widths=c1` and its
  evidence artifacts are gfx1100 runs, while `resolve_qwen35_gguf_artifact_preset`
  grants the scope on any backend. No UD MTP arm was run here, so no UD
  speculative rate, exactness result, or speedup is claimed.
