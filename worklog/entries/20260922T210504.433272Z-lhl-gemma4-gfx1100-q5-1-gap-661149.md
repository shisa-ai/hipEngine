# Q5_1 has no raw GPU linear path; a resolved dispatch key is not a GPU kernel

## Summary

**Q5_1 has no raw GPU linear path.** `resolve_gguf_linear_dispatch` returns a key
for it, and the registry resolves that key to
`hipengine.kernels.cpu_reference.ops.linear` — a NumPy function.

Q5_1 is `ffn_down_exps` on every expert: **29% of the model's parameters** and
5.52 GB of the 17.00 GB artifact. The Gemma 4 GPU path cannot run without it.

This also **corrects a claim in
`20260922T124343.841312Z-lhl-gemma4-gfx1100-quant-weights-6d6544.md`.** That entry
reported "all four quant types resolve on the raw layout" and concluded the
artifact was "fully servable without a repack step". The check behind that
conclusion resolved dispatch *keys*, which proves a key exists and not that a GPU
kernel backs it. It was too weak to support the conclusion drawn from it.

## The measurement

Resolving each raw type and inspecting what the registry actually returns:

| quant | rows | resolved to | GPU? |
| --- | --- | --- | --- |
| `gguf_q4_k` | 1 | `gguf_q4_k_gemv.gguf_q4_k_gemv_bf16_bf16_out` | yes |
| `gguf_q4_k` | 3 | `gguf_q4_k_gemv.wrapper` | yes |
| `gguf_q5_k` | 1 | `gguf_k_gemv.wrapper` | yes |
| `gguf_q5_k` | 3 | `gguf_k_gemv.wrapper` | yes |
| `gguf_q8_0` | 1 | `gguf_k_gemv.wrapper` | yes |
| `gguf_q8_0` | 3 | `gguf_k_gemv.wrapper` | yes |
| **`gguf_q5_1`** | **1** | **`cpu_reference.ops.linear`** | **no** |
| **`gguf_q5_1`** | **3** | **`cpu_reference.ops.linear`** | **no** |

The failure is loud rather than silent: `launch_gguf_linear_raw_ptr` passes
`stream=...`, which `cpu_reference.ops.linear` rejects with
`TypeError: linear() got an unexpected keyword argument 'stream'`. That is how it
was found — a real-artifact Q5_1 expert projection raised rather than returning
wrong numbers. Had the CPU reference happened to accept the extra keyword, it
would have been handed raw device pointers and produced garbage.

## What is not the answer

`kernels/hip_gfx1100/quant/gguf_q5_1_mmq_selected_prefill.py` registers
`gguf_q5_1_mmq_ds4_selected_prefill_bf16_bf16_out`, which is a real GPU kernel
over Q5_1 with an expert-selected interface. It is **not** a drop-in here:

- its activation contract is `x_ds4_ptr`, an x quantized to a ds4 plane format,
  not the plain bf16 activation the Gemma 4 expert loop produces;
- it consumes compact expert-sorted rows via `expert_start_ptr` rather than a
  per-expert offset into a stacked weight;
- it defaults to `planes=3`, implying a resident layout the raw path does not
  have.

`can_resolve(backend="hip_gfx1100", layer="moe_linear", quant="gguf_q5_1",
variant="q5_1_mmq_ds4_selected_prefill_bf16_bf16_out")` returns **False** as
written, so it is not reachable through the plain dispatch either.

## What does work

The expert conversion itself is correct, and Q4_K proves it on the real artifact.
`layers.0.ffn_gate_up_exps`, Q4_K, `(128, 1408, 2816)`, three rows:

| expert | bf16 vs NumPy | quantized vs NumPy | quantized vs bf16 |
| --- | --- | --- | --- |
| 0 | 0.301% | **0.291%** | 0.301% |
| 127 | 0.325% | **0.325%** | 0.286% |

Expert 127 is the last one, so the per-expert byte stride
(`nbytes // num_experts`, taken from the tensor's byte count rather than
recomputed from the element shape, because a quantized row is a whole number of
256-element blocks) is right at both ends of the range.

`gemma4_project_expert` dispatches on the weight's storage form the same way
`gemma4_project` does, offsetting a bf16 pointer by `out * in * 2` and a GGUF
weight by its expert stride.

- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_types.py` (new): `Gemma4Projection`.
  It moved out of `gemma4_layer.py` because the layer imports from the expert

## Validation

- `pytest tests/test_unit_gemma4_gpu_kernels.py` — 50 passed.
- Real-artifact Q4_K expert projections at both ends of the expert range —
  ~0.3%, at the rounding floor (table above).
- `ruff check` clean.

Q5_1, Q5_K and Q8_0 expert projections are **not** validated. Q5_K and Q8_0
resolve to GPU kernels and are expected to work; Q5_1 has nothing to call.

## The clearing command

This is a gate nothing can currently clear, which makes it a bug in the gate
rather than a valid restriction. Two routes, either of which clears it:

1. **Add a raw Q5_1 linear kernel** (GEMV and prefill) to
   `kernels/hip_gfx1100/quant/`, registered under
   `linear/gguf_q5_1/{gemv,prefill}_bf16_bf16_out`. This is the direct fix and
   matches the shape of the existing `gguf_q4_k_gemv` and `gguf_k_gemv` modules.
2. **Repack Q5_1 into the ds4 plane layout** the existing
   `q5_1_mmq_ds4_selected_prefill` kernel consumes, and route the experts through
   the selected-dispatch path. More work, but it reuses a kernel that already
   exists and is the shape the MoE loop actually wants.

Route 1 is smaller and keeps the raw-residency model intact. Route 2 is the
better end state.
