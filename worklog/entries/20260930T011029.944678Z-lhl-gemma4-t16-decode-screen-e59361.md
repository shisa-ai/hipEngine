# t16 decode GEMV screen: 5x at gate_up decode shape

## Summary

Iteration 38's scoped D1 precondition is answered, decisively and in favour of
the repack: the t16 repacked-layout decode GEMV runs the real Gemma 4 MoE
gate_up decode geometry (in 2816, out 1408, 128 resident Q4_K experts, top_k
rows 8, 17.8 MB of selected weight bytes) at **523.7-546.4 GB/s against the
production raw-layout selected GEMV's 107.3-107.8 GB/s — 4.86-5.09x — with
bitwise-identical outputs in every run** (kl 0.0, max_abs 0.0). Four runs on
the XTX at git `1be26e1d6`; artifact
`benchmarks/results/2026-09-30-gemma4-t16-decode-gemv-screen.json`.

The production arm cross-validates the recorded evidence: 107.3-107.8 GB/s
against the ~104-107 GB/s iterations 31/32 measured for both launch
structures (per-expert vs selected — the row's open hypothesis from iteration
31 is therefore answered too: the structures do not differ materially; the
layout does).

## Changes

- `scripts/gguf_q4_k_t16_decode_screen.py` — same-process, same-bytes A/B of
  `gguf_q4_k_selected_gemv_bf16_bf16_out` (production) vs

  the screen result and the corrected work item.

## Validation

- 4 runs, XTX (`ROCR_VISIBLE_DEVICES=1`): production 0.1655-0.1663 ms
  (107.3-107.8 GB/s, 0.2% range); t16 0.0327-0.0341 ms (523.7-546.4 GB/s,
  2.2% range); agreement bitwise-identical each run. The screen's internal
  gate (arms must agree) passed every time; run 1 paid the JIT build of
  `gguf_t16_selected_gemv.so`, later runs cache-hit.
- Geometry holds without substitution: t16 validation needs out % 16 == 0
  (1408) and in % 256 == 0 (2816); bytes_per_row 1584 matches the D1 trace
  shape.
- Loop iteration 92 recorded as a log (metric redefinition: t16 GB/s vs the
  frozen-packet KL baseline; all four verification checks passed, so
  keep/revert does not apply — see the iteration note).
