# TP2 per-layer attribution: the unexplained milliseconds are uniform shard-route efficiency, not layer type or gaps

## Summary

Localized the **4.53 ms/token** that the previous unit's traffic accounting left
unexplained. The answer is uniform: the shard route achieves ~88-89% of the
*resident* route's per-byte bandwidth on the same rank, evenly across all 64
layers and both layer types, with no rank or layer structure. That is a
registry/kernel-efficiency target at the shard shapes, and it closes off the two
competing explanations (a slow layer family, or device-side gaps around the
exchange).

`scripts/tp2_stage_device_attribution.py` now records per-`(layer, rank)`
HIP-event pairs in addition to the four coarse spans, and takes the reduction
owner as an argument, so the aggregate `layers` span splits by layer index and
by layer type on both transports. Sixteen hand-driven steps on the default
device-side reduction:

| quantity | rank 0 (W7900) | rank 1 (RX 7900 XTX) |
| --- | ---: | ---: |
| per-layer median | 0.350 ms | 0.349 ms |
| per-layer min / max | 0.327 / 0.386 | 0.307 / 0.386 |
| full-attention blocks (n=16) | 0.345 ms | 0.357 ms |
| GDN/linear-attention blocks (n=48) | 0.350 ms | 0.348 ms |
| per-layer rank skew | median 0.008 ms, max 0.056 ms | |
| achieved, 162.3 MB/rank/layer | 464 GB/s | 466 GB/s |
| same rank's measured resident bandwidth | 529.3 GB/s | 637.7 GB/s |

**Hypothesis falsified.** I expected a bimodal per-layer distribution with the
GDN blocks (or the full-attention blocks) carrying the deficit. Instead the two
families are within 1.4% of each other, the ordering flips between ranks, the
per-layer spread is 18% with no layer-index pattern, and rank skew is 0.008 ms
median. The per-layer floor from the traffic accounting is **306.7 us** (162.3
MB/rank at the slow rank's measured 529.3 GB/s); the measured median is 350 us.
That is **3.09 ms/token** of the 24.155 ms wall, and it is a *uniform* 12%
per-byte shortfall on both ranks: the host-reduction control isolates rank 1
(which does not wait on its peer in host mode) at 287 us / **566 GB/s**, 89% of
its own 637.7 GB/s.

The same two runs decompose the transport, which is the measured basis for the
device-side default rather than an assumption:

| term | ms/token |
| --- | ---: |
| host reduction exposed between layers (rank 0) | 3.178 |
| inter-layer gap with the device reduction | 0.307 |
| in-graph exchange cost on rank 0's device timeline | 0.492 |

So the device reduction removes **2.87 ms** of exposed host time from the layer
loop and pays **0.49 ms** inside the graphs — consistent with the recorded
promotion (27.44 -> 24.87 ms/token when it became the graphed default).

## Validation

- **Both arms, 16 steps each, same session builder and same host:**
  ```
  HIP_VISIBLE_DEVICES=0,1 HIP_PATH=/opt/rocm PYTHONPATH=/home/lhl/hipEngine-main \
    python3 scripts/tp2_stage_device_attribution.py \
    /models/gguf/Qwen3.8-27B-Q4_K_M.gguf 16 {device,host} --json /tmp/tp2_attr_<mode>.json
  ```
  Device: wall 25.758 ms/step, layers 23.030/22.976, tail 1.226/1.285, metadata
  1.069/1.008. Host: wall 28.955, layers 25.410/25.417, per-layer device sums
  22.232 (rank 0) / 18.477 (rank 1). The diagnostic drives the layer loop by
  hand and records 128 extra events per step, so its wall is not the production
  wall; the per-layer spans are the comparable quantity and they reproduced
  across two independent runs (22.932/22.897 then 22.723/22.701).
- **Sanity of the split:** in host mode the per-layer spans sum to 22.232 ms
  while the aggregate `layers` span is 25.410 ms — the 3.178 ms difference is
  the host reduction, which by construction runs between the per-layer spans
  rather than inside them. In device mode the same difference is 0.307 ms. That
  internal consistency is what makes the transport decomposition usable.
- **No production code changed**, so no strict/profile numerical gate applies.
  The session still asserts greedy tokens against a plain production
  `generate` run over the same continuation (the script's existing check).
- **Interpretation limit:** these are HIP stream-event spans, so each includes
  device-side waits (notably the in-graph exchange spin-sum) and is an upper
  bound on true kernel execution; layer spans on the two ranks overlap by
  construction. The 12% shortfall is a comparison against the *resident route's
  measured* bandwidth on the same rank, not against the hardware peak (the
  resident route itself achieves 61-66% of peak).
