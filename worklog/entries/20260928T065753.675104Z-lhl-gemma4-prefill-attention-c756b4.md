# resident logits in LDS are the latency chain and online softmax is what unblocks the tile

## Summary

The prefill kernel's LDS layout **is** the latency chain that `20260928T065707`
identified, and it also caps how far the fix from `20260928T065619` can go. Both
limits come from one design decision, and one change lifts both.

`gemma4_attention_shared_bytes` states it in its own docstring: *"This
implementation stores one logit per live key in LDS."* The requirement is
`(head_dim + keys + threads) * 4` bytes. A key visit therefore writes its logit to
LDS, and passes 2 and 3 read it back and write the weight -- **three LDS round trips
per visit**, at ~20-30 cycles of latency each, on top of the 26-issue reduction.
With the kernel at 4% of issue capacity and bytes free, that round-trip chain is what
the time is going to.

## The two limits

**Token tiling is capped at `TQ` around 4.** Under the resident-logit design a block
holding `TQ` query rows needs `TQ x keys` logits resident:

| `TQ` | LDS for `head_dim=512`, `keys=2048` | |
|---|---|---|
| 2 | 24.0 KiB | fits |
| 4 | 48.0 KiB | fits |
| 8 | 96.0 KiB | **over the 64 KiB budget** |

So the lever from `20260928T065619` -- amortize a fixed per-visit cost over several
query rows -- runs out at `TQ` ~4 under this layout, which is a 4x ceiling on the
visit reduction before anything else is considered.

**The kernel already refuses long contexts.** At `head_dim=256` the requirement
reaches 64.5 KiB, **100.8% of the budget, at `keys` ~16000**. The docstring's own
conclusion is that *"larger contexts need a tiled attention implementation, not a
larger prefill scratch block."* The design has a hard context ceiling of about 16k
keys and no amount of scratch grows it.

## What lifts both

An **online-softmax (flash-style) kernel keeps no logits resident** -- only the query
rows and a running `(max, sum, accumulator)` per row. LDS then holds the q rows and
nothing that scales with `keys`:

| `TQ` | LDS, online softmax, `head_dim=512` |
|---|---|
| 4 | 8.0 KiB |
| 8 | 16.0 KiB |
| 16 | 32.0 KiB |

`TQ=16` fits in half the budget. So online softmax does three things at once: removes
the three LDS round trips per visit that are the latency chain, removes the `TQ ~ 4`
ceiling on amortizing visits, and removes the ~16k-key context ceiling.

**This is one change, not three**, and it is the change the kernel's own docstring
already points at.

## What this does not say

- It does not say how much of the 4% is the LDS round trips specifically. The
  26-issue reduction plus 3 round trips is an accounting of the chain's *contents*,
  not a measurement of which stage dominates. A profile is still the right first step
  and I have not run one.
- It does not size the win. Removing the chain entirely would not take the kernel to
  100% of issue capacity; it would take it to whatever the next limit is.
- `TQ` and the LDS figures above assume one block per query-row tile. Whether
  `head_dim=512` tiles the same way is open -- that geometry already needed a tiling
  decision for a different reason (`20260928T091438`, the 100.4 KiB port budget).

## Changes

No code. The entry is arithmetic over `gemma4_attention_shared_bytes`'s own formula,
which is the kernel's own statement of its requirement.

## Validation

```
# from gemma4_attention.py
required = (head_dim + keys + threads) * 4      # threads = min(256, ...)
if required > 64 * 1024: raise NotImplementedError(...)
```

The formula and the 64 KiB ceiling are read from the source, not assumed. The `TQ`
figures multiply that formula by the row count and add `TQ * head_dim * 4` for the q
rows. The ~16k-key ceiling is the `keys` at which the formula reaches 64 KiB for
`head_dim=256`, which is where the source itself raises.
