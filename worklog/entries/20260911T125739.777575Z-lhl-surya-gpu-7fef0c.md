# Surya GPU vision tower, public generator, and request contracts

## Summary

Land the Surya OCR GPU public path on gfx1151: the HIP vision tower runs on
device, a registered `(surya_ocr2, hip_gfx1151, fp32)` generator drives the
full pipeline, both generators share an explicit greedy-only request contract,
and the GPU runner no longer leaks tracked device allocations across
`close()`. A follow-up review found four concrete defects in the prior
bring-up; this unit fixes all four and records the architectural drift that
remains.

## Changes

- `hipengine/runtime/surya.py`
  - `vision_forward` completed (patch embed, learned position add, 12
    bidirectional-attention blocks, merger) and wired to the text decoder via
    the existing `visual_features` injection path.
  - **Memory-ownership fix:** the constructor re-initialised
    `_head_bias_bufs` *after* `_alloc_state()` and the staging `_permanent()`
    calls had appended to it, so `close()` freed nothing of the 54 persistent
    per-layer state/staging buffers. Removed the clobber. The cached
    `_ptr_array_bufs` (batched-GEMM pointer arrays, created lazily in
    `_dev_ptr_array`) were never freed; they are now constructed in
    `__init__` and released in `close()`.
  - Removed the temporary `vision_stage_hook` debug scaffolding.
- `hipengine/generation/surya_gpu.py` (new): `SuryaOCRGeneratorGPU` +
  `make_surya_generator_gpu`, registered under
  `(surya_ocr2, hip_gfx1151, fp32)`.
- `hipengine/generation/surya_contract.py` (new): shared greedy-only request
  contract. Supported controls are `max_tokens`, `ignore_eos`, `eos_token_id`,
  `stop_token_ids`, `deadline_at`, `cancellation_token`; every other
  sampling/constraint control must be at its neutral default or the request
  raises `SuryaRequestError`. Also owns `check_prompt_capacity` and the shared
  `greedy_decode_tokens` loop.
- `hipengine/generation/surya.py`: rewritten onto the shared contract;
  `generate_multimodal_detailed` now returns `generated_token_ids` and
  `finish_details`. Previously the docstring claimed sampling "raises" while
  the code silently ignored every sampling field.
- `hipengine/generation/__init__.py`: import the new generator module during
  lazy builtin registration.
- `tests/test_surya_gpu.py` (new): GPU vision vs CPU reference, GPU vision vs
  the `vision_merged` torch oracle, full GPU pipeline greedy-ID parity, the
  registered generator path (including capacity and unsupported-control
  rejection), and a repeated create/use/close allocation-leak guard.
- `tests/test_surya_generation_contract.py` (new): 24 pure unit tests over the
  contract (defaults accepted, unsupported controls rejected, capacity,
  EOS/stop/length finish reasons, no trailing decode, deadline).
- `scripts/surya_perf_compare.py`: one measurement protocol for every lane.
- `docs/MODEL-SURYA.md`, `docs/KERNELS.md`, `docs/REFACTOR.md`: status,
  catalog, and drift ledger.

## Validation

- `HIPENGINE_HIP_ARCH=gfx1151 python3 -m pytest tests/test_surya_gpu.py -q`
  → 5 passed.
- `python3 -m pytest tests/test_surya_generation_contract.py -q` → 24 passed.
- Surya bundle (`model_contract`, `oracle_fixtures`, `text_decoder`, `vision`,
  `e2e`, `public_api`, `gpu`, `generation_contract`) → all green, repeated.
- Leak guard is a genuine regression test: reintroducing the
  `_head_bias_bufs` clobber makes it fail, and restoring the fix makes it pass.
  Instrumented counts: 527 tracked allocations / 2.73 GB alive after
  construction, 0 after `close()`.
- Full GPU pipeline (GPU vision features → GPU prefill → GPU decode) reproduces
  the torch fp32 oracle greedy IDs exactly, 64/64 tokens
  (`tests/test_surya_gpu.py::test_gpu_end_to_end_ocr_matches_oracle`).
- GPU vision vs `vision_merged`: within the CPU-reference noise band.
- Observed once: a `test_gpu_end_to_end_ocr_matches_oracle` failure in the run
  immediately following an aborted bug-injection test process. Seven
  consecutive clean file/bundle runs afterwards (4 + 3) passed; not reproduced.

## Benchmark

`HIPENGINE_HIP_ARCH=gfx1151 python3 scripts/surya_perf_compare.py --runs 3`
on the Ryzen AI Max+ Pro 395 (Radeon 8060S, gfx1151), `page_small.png` /
"Transcribe this page." / 64 new tokens, fp32 everywhere. Every lane now times
the same region (preprocessing + vision + prefill + decode); `init_s` is
checkpoint load plus runner construction, excluded from `e2e`.

| Lane | init_s | e2e_s | vision+prefill_s | decode_s | decode tok/s | correctness |
| --- | --- | --- | --- | --- | --- | --- |
| hipengine_gpu | 0.431 | 2.051 | 0.152 | 1.947 | 32.9 | PASS |
| torch_cuda (same iGPU) | 6.461 | 2.577 | 1.612 | 0.925 | 69.2 | PASS |
| hipengine_cpu | 0.580 | 20.450 | 2.840 | 18.826 | 3.4 | PASS |
| torch_cpu | 6.365 | 149.935 | 17.979 | 131.676 | 0.5 | PASS |

The previous rollup compared different work (hipEngine e2e excluded
preprocessing and CPU vision but included runner construction; the torch arm
included vision with a loaded model; the hipEngine "prefill" stage omitted
vision). Corrected numbers: hipEngine 2.051 s vs torch 2.577 s end-to-end,
vision+prefill 10.6x faster, decode 2.1x slower. `init_s` uses a warm JIT
cache. Artifact: `benchmarks/results/2026-09-11-gfx1151-surya-lane-compare.json`.
