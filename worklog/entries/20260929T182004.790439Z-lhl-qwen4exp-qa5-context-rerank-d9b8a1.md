# QA-5 closed: the named kernel does not run, and the running one is at 100% occupancy

## Summary

QA-5 says: *"Full-attention context kernel, further - 25% occupancy, LDS-limited in the
launch carrying 81% of its time; two bit-exact levers already taken."* Its stated next
step is **"Re-read its share in X-3 before another lever."** I did that re-read. The
answer is **no**, and the premise is stale on both counts.

## 1. The named kernel does not appear in the current default capture

X-3's attribution (`role-analysis.json`, window 22,698.6 ms, 9,652 kernel rows) contains
**zero** entries for `qwen35_paged_full_attn_prefill_gqa_gate_fp16_kernel`. Its occupancy
is real and I reproduced it from the register census: **VGPR=256, 1,934 instructions, 8
waves/CU = 25.0%**. But it is not running at `code-p4096`.

## 2. The kernel that does carry the time runs at 100% occupancy

The entire full-attention family in that capture is **one kernel**:

| kernel | ms | share of window | rows |
|---|---:|---:|---:|
| `qwen35_paged_full_attn_decode_context_tensor_batch_kernel` | 801.566 | **3.531%** | 36 |

Measured: **VGPR=18, SGPR=53, 554 instructions, 32 waves/CU = 100.0%**. There is no
occupancy headroom in the kernel that is actually executing.

## 3. Where the LDS limit *would* bind

The launch computes `shared = (max_context_len + threads + head_dim) * 4` with
`threads = 32` if `max_context_len <= 1024` else `64`, and `head_dim = 256` (read from the
model's `attention_key_length` via the GGUF config, not assumed). Against 64 KiB LDS per
CU and the measured 256-VGPR register limit:

| context | threads | LDS bytes | blocks/CU | waves/CU | occupancy | binding |
|---:|---:|---:|---:|---:|---:|---|
| 512 | 32 | 3,200 | 20 | 8 | 25.0% | registers |
| 1024 | 32 | 5,248 | 12 | 8 | 25.0% | registers |
| 2048 | 64 | 9,472 | 6 | 8 | 25.0% | registers |
| 4096 | 64 | 17,664 | 3 | 6 | **18.8%** | **LDS** |
| 8192 | 64 | 34,048 | 1 | 2 | **6.2%** | **LDS** |
| 16064+ | 64 | >65,536 | - | - | - | global score scratch |

**The binding resource changes with context length.** "25% occupancy, LDS-limited"
conflates two regimes: below the crossover registers bind (25%), above it LDS does. A
single figure is correct for neither regime above 2048.

## 4. The 64 KiB overflow is already guarded - I nearly reported a bug

`paged_attn_decode.hip:3796`:

```cpp
use_global_scores = global_score_workspace or (max_context_len + threads + head_dim) * 4 > 65536
```

Exactly the derived threshold (switching at context 16,064 for this shape), matching
`docs/KERNELS.md`'s documented global-score-scratch fallback. **I first read the >64 KiB
row as a possible launch failure** and would have reported a non-existent bug. Checking
the guard in the source first is what caught it. This is the third self-caught error this
session, after the unequal-work DE-3 sweep and the silently-rejected `__launch_bounds__`
flag in QA-2.

## Verdict

**Another occupancy/LDS lever on this kernel is not justified.** Share 3.531%; the named
kernel does not run; the running kernel is at 100% occupancy. QA-5 closed as a stale
premise.
