# TP2 uneven split fails the production numerical gate on a single tail row

## Summary

The uneven TP2 split is implemented and reaches the production gate harness, but
this gate run does **not** certify it. The verdict is blocked, and the blocking
failure is in the *control* arms, not in the uneven-split arm.

What the run did establish, from
`benchmarks/results/2026-09-18-w7900-tp2-uneven-split-optimal-gate-blocked.json`
(18 canonical + heldout prompts, 831 teacher-forced positions, 3 arms, one
revision, wall 665 s):

- The uneven split resolves end to end on real weights: fractions
  `[0.417145, 0.582855]`, leaves `ffn_gate`/`ffn_up`/`ffn_down`, alignment 256,
  shard widths **7168 (rank 0, W7900)** and **10240 (rank 1, RX 7900 XTX)**, and
  **both ranks resolve the fused `dense_dual_local32_bf16_bf16_out` variant**.
  This is the outcome the pair-route allowlist work (`c09827fa5`) was for: an
  uneven boundary no longer falls back to the unfused three-launch chain.
- Decode determinism holds at the new split: 3 sweeps, `per_row_match: true`,
  no mismatched sweeps, and `nonfinite_rows: []`.

What blocked it: `all_gates_passed: false` with every recorded failure on the
`tp1-d0` and `tp1-d1` control arms — `max_kl 0.0699463 > 0.05` for global,
canonical, and the `code` category (and `code/canonical`) on both. The same
value appears on both single-GPU controls, and the TP2 arm has no scored
comparison entry in the artifact, so the uneven-split arm's numerical verdict is
unknown rather than failed.

The breach is therefore the already-documented post-horizon tail, not a new
numerical defect: `docs/EXECUTION-PROFILES.md` 6.5 declares the Qwen3.8-27B
`Q4_K_M` sustained comparison horizon at **D=42** (`60af7efea`), while this run
scored every position in each prompt (~46 per prompt over 831 rows). The
`code`-category tail row that breaches is the same row the horizon work
attributed to a low-probability, flat reference row.

Provenance caveat: the artifact records `source_revision c09827fa5` with
`source_dirty: true`, i.e. the run used that revision plus uncommitted harness
changes (the horizon plumbing that landed later as `3d8fa0698`). A certifying
re-run must come from a clean revision.
