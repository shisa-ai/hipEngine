# Qwen4Exp AR decode batch behind a default-off qualification switch

## Summary

Plain autoregressive decode in the resident serving runner can now advance every
row of one decode work item with a single N-row `Qwen4ExpGGUFBatchRunner` step,
selected by `HIPENGINE_QWEN4_EXP_AR_BATCH=1`. The switch is default-off: with it
unset, `decode_batch` still loops the per-request c1 runners exactly as before.
Each request is prefilled by c1 (chunked, unchanged), imported once into a pinned
physical batch slot at the end of its prefill, and from then on steps only
through the shared call.

This is wiring plus control-contract evidence. It is not a production
promotion: the production numerical gate, live HTTP qualification, and the MTP
route decision are all still open (see "Not established here").

## Changes

- `hipengine/generation/qwen4_exp_ar_batch.py` (new): `Qwen4ExpARBatchOwner`
  owns the lazily built batch runner and the request -> `(slot, owner token)`
  map; `Qwen4ExpARBatchStepError`; `ar_batch_enabled` /
  `ar_batch_state_slots` env resolution; `make_qwen4_exp_ar_batch_runner`
  builds the real runner over the generator's shared residency.
- `hipengine/generation/qwen4_exp_gguf.py`:
  - `_prepare_ar_batch()` pins the decode mode at the first `prepare()` (a
    serving runner never mixes c1 and batch steps), builds the owner, and fails
    closed when the generator has no model-owned residency.
  - `reserve_admission()` pins a slot after the c1 reset and MTP reservation;
    `_release_runner()` releases it, so rollback, reclaim, discard, and close all
    clean up through one path.
  - `plan_admission()` admits at most as many AR rows as the batch holds, so a
    narrower `HIPENGINE_QWEN4_EXP_AR_BATCH_SLOTS` leaves surplus requests
    pending instead of raising inside a tick.
  - `_prefill_row()` imports the completed c1 prefill exactly once
    (`_import_ar_batch`); `decode_batch()` samples every AR row, then makes one
    `_step_ar_batch()` call and publishes in work-item order.
  - `compact_batch()` keeps the pinned physical slots and refuses an MTP row
    that somehow holds one; `decode_telemetry()` reports the selected path,
    width histogram, imports, releases, and failure state through the existing
    `prepare_request_scratch` dict under `decode`.
- `docs/REFACTOR.md`: the batch-runner entry now records the switch, the exact
  promotion blockers, and the remaining duplication/consolidation debt.
- Tests: `tests/_qwen4exp_ar_batch_fixtures.py` (fake c1/batch/MTP owners),
  `tests/test_unit_qwen4exp_ar_batch_decode.py` (29 CPU tests),
  `tests/test_gpu_qwen4exp_ar_batch_decode.py` (3 synthetic-model GPU tests).

Review repairs in the owner, all CPU-testable through the fake runner:

- `close()` keeps the runner reference and the leases until the free actually
  succeeds, records the failure, and leaves the owner in a `closing` state that
  refuses `ensure`/`reserve`/`step`/`import` until a retry finishes. The real
  batch runner frees in reverse and pops each slab only after its free returns,
  so a retry frees each remaining slab exactly once. `release()` during a
  pending close drops the lease without calling into the half-closed runner.
- Row handles are parsed with `operator.index` and an explicit bool rejection
  before anything mutates, so `3.7`, `True`, `"5"`, or `None` cannot become a
  token, request id, slot, or position by truncation.
- A step result is validated before any output is attributed: returned slot
  order must equal the requested order, the token count must match the row
  count, tokens must be non-negative integers, and a row set that needs the full
  readback must return a finite `(rows, vocab)` logits array. A malformed result
  after a successful `batch.step` is unrecoverable (state advanced, output
  unattributable), so it fails the rows exactly like a failed call.
- Import is tracked per lease: a second import for the same request raises
  instead of overwriting the slot's live history, and a step refuses a lease
  that was never imported.

### Contracts the code now enforces

- One N-row call per decode tick: rows are sampled first and stepped together;
  no c1 `step` runs for a row that owns a batch slot.
- Physical slot identity is pinned at admission and never derived from
  scheduler slot indices; `compact_batch` moves no state, so a scheduler
  compaction cannot re-bind a row to another request's state.
- The c1 prefill is imported once, at the final position of a multi-chunk
  prefill, and never on a partial chunk. A repeated import is refused rather
  than resetting the slot, and a step requires an imported lease.
- Cancellation between sampling and the shared step publishes nothing and
  leaves the slot for reclaim to release; a slot reused by a later request gets
  a fresh owner token, and the stale token is refused by the runner.
- A failed or malformed step poisons its rows: the owner releases every
  participating slot, records the failure, raises `Qwen4ExpARBatchStepError` out
  of the tick, and refuses new reservations and new steps. A row that lost its
  slot raises instead of silently continuing on c1, and a poisoned row set is
  never re-stepped or re-attributed.
- Teardown is retryable: a partial free leaves the runner reachable and the
  owner refuses new work until `close()` succeeds, instead of dropping the
  handle that a retry needs.
- MTP rows never take a batch slot and never join a batch step; they keep the
  existing request-owned c1 runner plus draft at width 1. Speculative candidates
  are never registered as requests.

RED sensitivity was checked by re-introducing each defect and confirming the
suite fails: (1) routing AR rows back to the per-row c1 step fails 8 tests;
(2) skipping the slot release on reclaim/discard fails 4; (3) importing on every
prefill chunk instead of at completion fails the chunked-prefill test. For the
review repairs: (4) restoring the old close order (clear the handle and set
`closed` before the free) fails the close-retry test; (5) `int(token)` instead
of the strict parse fails all five non-integer cases; (6) attributing the raw
result with no validation fails the `no_logits` and `nan_logits` cases (the
truncated-token and short-logits cases are still converted into failed rows by
the surrounding handler, which is the intended behavior); (7) removing the
import-once flag fails the repeated-import and unimported-step tests.

The GPU test builds two real c1 prefills over the committed batch-runner
fixture, then drives the generator through `SubmitPollTextGenerator`. It
observes `decode_path = qwen4exp_full_model_ar_batch`, `imports = 2`,
`step_widths = {"2": 2}`, `releases = 2`, both c1 runner positions still equal
to their prompt lengths (no c1 decode step), and per-row forced-token chains
`(5,5,5)` / `(17,17,17)` from per-request `logit_bias`, which a swapped result
row could not produce. A second test confirms the uncontrolled argmax path
follows the independent c1 greedy chain; that fixture's chain reaches a fixed
point after one token, so it establishes path agreement, not row distinctness.

No performance claim: no timing was measured, and `benchmarks/` is unchanged.

## Not established here

- **Production numerical gate.** Not run. The batch path is not bit-identical to
  c1 by construction (mixed dense/sparse QSA rows, N-row GEMM variants), so
  promotion needs the calibrated mean/p95/p99/max KL, top-1 by category,
  determinism, isolation, BF16-relative, and task gates on the full
  `mtpbench-code-general-ja` suite plus category holdouts. The earlier
  real-checkpoint evidence in this tree is diagnostic only (short c1 drift,
  sparse-threshold correctness run), not an admission result.
- **Live serving qualification.** No HTTP/streaming/disconnect run at width 2,
  no long-context run. Contexts above `dense_equivalent_limit` (2051 positions
  at block budget 512) exercise the batch's per-row index selection, which the
  5-12 token prompts here never reach.
- **MTP.** Unchanged and unqualified for batching: MTP stays at width 1 on c1.
  A mixed AR/MTP workload runs two KV layouts and cannot share a step, so the
  PS8 claim in `docs/QWEN4EXP-PRODUCTION-SERVING.md` stays open.
- **Memory.** The batch path retains the c1 state pool *and* the batch slabs at
  the same time: every request keeps its c1 runner (prefill, MTP, rollback) while
  the batch holds `state_slots` full contexts with their own KV, GDN
  recurrent/conv, PLE history, index slabs, and N-row scratch. The default width
  equals the serving capacity, so a capacity probe must budget both pools
  together; the combined cost on the production checkpoint is unmeasured here
  and this unit makes no memory-efficiency claim.
- **Failure semantics under load.** A poisoned step raises through the tick and
  disables the path for that serving runner. That is deliberate fail-closed
  behavior; no restart/recovery policy has been exercised.
