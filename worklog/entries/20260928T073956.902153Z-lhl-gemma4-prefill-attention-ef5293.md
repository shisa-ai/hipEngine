# the prefill symbol is bit exactly gated against decode inside the decode named test file so the wmma path is not free

## Summary

**`20260928T073919` is wrong on its central claim.** It asserted "there is no prefill output
gate" and "the current prefill kernel's numerical behaviour is not pinned against anything".
Both are false, and the correction **reverses the port decision that entry made**.

## The gate

`tests/test_gpu_gemma4_attention_decode_parity.py` -- despite its name -- **does gate the
prefill symbol**:

- **`test_decode_symbol_bit_matches_prefill_symbol`** (line 173) launches
  `_SYMBOL_PREFILL_F32` / `_SYMBOL_PREFILL_BF16` and compares the result to the decode symbol
  **bitwise**;
- further prefill-symbol tests at lines 225-260, launching with `_ARGTYPES_PREFILL`.

The helper's own comment states the contract:

> Prefill's tail is (window, row_offset) instead of decode's (split_workspace,
> split_slices). window 0 makes first_kept 0, so the prefill symbol visits every key exactly
> as decode's keep_mask does -- which is the parity these tests assert.

## How the previous entry got it wrong

It ran `ls tests/ | grep -i "gemma4.*attention"`, saw that the only file with "parity" in its
name said **decode**, and concluded no prefill gate existed. **The gate is inside the file
whose name says decode.** A filename is not a coverage map.

**This is the same failure mode as `20260928T073848`** -- concluding from a name or a listing
rather than opening the artifact. That one cost five iterations of re-deriving an existing
algorithm; this one would have cost a port that silently breaks a green test.

## What the gate pins, and what it does not

| path | pinned? |
|---|---|
| prefill symbol at `window = 0` (dense causal) | **yes, bit-exactly, against decode** |
| prefill symbol at `window > 0` (sliding, `first_kept`) | **no** -- every comparison runs at `window = 0` |

So the sliding-window path has no numerical gate at all, and the dense path has a
bit-exactness gate.

## The decision this reverses

`20260928T073848` and `20260928T073919` concluded **"the WMMA path is available"** because no
prefill gate existed to break. **A gate exists, and it is bit-exact.**

**A WMMA-based port fails `test_decode_symbol_bit_matches_prefill_symbol`**, because a
different reduction order is exactly what bit-exactness against decode forbids. **WMMA is not
freely available.** The options are:

1. **Tile the buffer and keep the key-visit order and the reduction tree.** The logits are
   already unchanged by tiling; if the tiled kernel also accumulates in the same key order,
   **the bit-exact gate keeps passing** and the port is purely a shared-memory change.
   **This is the conservative and correct choice.**
2. **Take WMMA and deliberately relax the gate to a tolerance.** That is a real decision with
   a real cost -- it trades a bit-exact contract for speed on a path that currently has one.
   It is not something to slip in as part of a performance port.

**Recommendation: option 1.** It gets the tiling, which is the measured fix
(`20260928T073550`), without spending a contract that took a dedicated test to establish.

## A gap this does expose

**The sliding-window path is ungated.** That is a real finding and it stands independently of
the port: `first_kept` and the windowed walk have no numerical reference. Since the artifact's
sliding-layer case is 25 of the 30 layers, that is most of the kernel's work with no gate.
