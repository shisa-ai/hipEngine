# Curate gemma4's strict vs production variant sets per scope, with named blockers

## Summary

Step 1 of the gate build (task #44, piece A): decide what `strict` and
`production` actually *are* for every registry-resolved gemma4 scope, by
measurement rather than assertion. The route pin `HIPENGINE_GEMMA4_MOE_PREFILL`
(`gemma4_experts.py::_prefill_mode`) selects among
`{auto, wmma, wmma_plain, mmq, grouped, selected}`; its docstring declares
`auto` the production route (MMQ gate_up + WMMA down, logits gate 37x inside
the calibrated envelope) and `grouped`/`selected` the exact arms. The trace
confirms the docstring: under `grouped` the production MMQ variant disappears
entirely and the grouped exact owners take its place. That gives the MoE
scopes a measured strict arm. Three blockers then fell out, and per the prior
entry's rule they are recorded rather than defaulted.

## Validation

### Method

Wrap `hipengine.kernels.registry.resolve` in a counting spy, load the shipped
artifact **once**, switch `HIPENGINE_GEMMA4_MOE_PREFILL` between arms (the
pin is read per call, so one load serves all three), and difference arms that
differ by **exactly one decode step**: `max_tokens=2` vs `max_tokens=3` on the
same prompt, giving `D = B - A` and `P = A - D` with no division. Keys whose
counts did not difference linearly are marked non-linear instead of forced
into numbers. Prompt: `"The quick brown fox jumps over the lazy dog. " x 256`,
about 3072 tokens -- inferred from `wmma_prefill` resolving 375 times against
the prior entry's 125 at a 1024-token prompt, exactly 3x.

### Findings

1. **The knob is real.** mmq32 vanishing under `grouped` is the observable
   proof that the exact MoE arm is reachable today with no code change:
   `HIPENGINE_GEMMA4_MOE_PREFILL=grouped`.
2. **`selected` mode is not a candidate strict pin.** In that arm the MoE
   gate_up/down resolves under `linear` instead of `moe_linear`
   (`linear|gguf_q4_k|selected_gemv` jumps from 0 prefill to 87), the key set
   shrinks to 8, and two arms stopped differing linearly. It routes through a
   different attribution path and would need its own study.
3. **One `(layer, quant)` pair can resolve several variants in one run**
   (q4_k MoE: 232 mmq32 + 29 rowbatch8). `VariantSelection` keys on
   `(layer, scope)` and allows one variant each, so the scope axis must carry
   the projection role (gate_up / down / shared), not just phase+quant. That
   needs call-site attribution, which the next probe takes from the spy's
   stack.

### Blockers, named rather than defaulted

- **B1 -- dense prefill strict arm is unreachable.** The exact owner for dense
  Q8_0 prefill is `prefill_bf16_bf16_out`, documented in
  `runtime/gemma4.py:584` ("what a shape runs when WMMA prefill is off"), but
  `kernels/hip_gfx1100/gemma4/gemma4_layer.py:171` passes
  `use_wmma_prefill=True` as an **explicit kwarg**, and
  `gguf_linear._resolve_use_wmma_prefill` gives kwarg precedence over session
  and env. The comment there records the reason: the fallback schedule costs
  3.16x on the (512, 2816, 2112) q/k/v shape, and ENVS.md names the env var as
  only the low-level session default. Clearing command: that call site must
  take the profile's policy (a binder-set session/kwarg value) before a
  strict capture can run the dense arm.
- **B2 -- dense decode has no pin.** `pack8_gemv_bf16_bf16_out` (125/step) and
  the `selected_gemv` decode rows resolve the same in both arms; the registry
  holds plainer families (`gemv_bf16_bf16_out`, `prefill_bf16_bf16_out` for
  q8_0) but nothing routes gemma4 to them. Named as a scope where strict is
  unestablished, not as production==strict.
- **B3 -- MoE q8_0's strict arm splits across three owners** (3 calls each).
  Which projection each belongs to is unattributed, so it cannot yet be one
  `VariantSelection`.
- **B4 -- lm_head f32 counts are data-dependent.** `pack8_gemv_bf16_f32_out`
  did not difference linearly (a=2,b=1 in one arm), so it carries no phase
  label; its role (greedy f32 output) is known from the prior entry.
