# DMS C>1 unblocked: per-step decode-owner routing; C2/C4@16K and C8@4K pass

## Summary

Implemented per-step DMS decode-owner routing on the shared runner (RED-first
via the committed repro probe, then unit-locked, then integration-proven).
C2 and C4 at 16,384 tokens/session and C8 at 4,096 tokens/session now pass
fully interleaved on the XTX with per-session extent ledgers consistent and
zero teardown residue. C8 at 8,192/16,384 tokens/session OOMs at
compact-backend pack-time allocation — the same dense-owner + payload
coexistence memory boundary as the C1 ladder, not a routing blocker.

## Changes

- `hipengine/runtime/qwen35_gguf_runner.py`: added
  `Qwen35GGUFResidentSession._refresh_dms_decode_owner_marker()` and call it
  at the top of `step()` and `step_async_top1()`. A DMS session claims the
  shared runner's `_dms_decode_owner` marker for its own step; a session
  without a DMS backend clears a foreign marker so dense decode never
  inherits DMS routing. The prefill-finalize set remains for backward
  compatibility and is overwritten by whichever session steps next.
- `tests/test_qwen38_dms_decode_owner_routing.py`: six unit cases locking
  the marker semantics (claim, clear-on-dense, no-op cases, missing runner
  tolerance) without requiring the model.
- `scripts/qwen38_dms_concurrency_probe.py` (committed last unit) served as
  the RED integration repro and is now the GREEN integration gate.
- `benchmarks/results/2026-09-07-rx7900xtx-dms-concurrency-ladder.json`:
  compact rollup (passes, failures with stage/classification, fix evidence).
- Campaign doc Packet 4 C2/C4/C8 item updated from structurally-blocked to
  measured with the fix evidence.

  session raises "DMS direct append device/host live-count mismatch"
  (`hipengine/kvcache/dms.py:1695`); 0 decode rows survive.
- GREEN (post-fix): C2@16,384 (8/8 decode rows), C4@16,384 (16/16), and
  C8@4,096 (32/32) pass; every session's DMS snapshot consistent
