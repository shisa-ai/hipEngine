# D7 weighted accumulate: column-tiling the decode launch (bit-exact grid redistribution)

## Summary

- Punchlist D7's weighted-accumulate clause, delivered by a **grid
  redistribution instead of the row's literal epilogue fold**, chosen on the
  measurement: the decode launch of `gemma4_moe_weighted_accumulate_bf16` is
  one block per token, and at `tokens == 1` that single 256-thread block ran
  **17.8 µs/launch** (n=2160 = 30 layers x 72 decode steps in the d6 trace)
  against a ~2 µs floor for the neighbouring single-block kernels (lane_to_row
  1.9, gather 2.5, gelu 2.0) — 8 lanes x 2816 columns of dependent loads with
  one block nowhere to hide, so 30 layers cost 0.53 ms/token. Latency-bound,
  not work-bound.
- The row's literal fix — fold the accumulate into the down GEMV's epilogue —
  was **not** taken: the down decode owner's grid is per-(lane, output
  element), so the top-8 lanes would write one token row from eight different
  blocks. That needs atomics, and non-deterministic add order is an arithmetic
  change behind the campaign gate. The column tiling gets ~80% of the row's
  prize bit-exactly; the GEGLU clause remains open.
- Mechanism: `blockIdx.y` now tiles the column dimension
  (`col_base = blockIdx.y * blockDim.x`, stride `blockDim.x * gridDim.y`).
  Each column's slot loop still runs entirely inside one thread in lane order,
  so the sum per (token, col) is unchanged; at `gridDim.y == 1` the index
  arithmetic reduces to the previous form instruction for instruction. The
  wrapper takes `col_tiles: int = 0` (0 = auto = ceil(hidden/threads)), a
  scheduling parameter documented as such — not a flag, no REFACTOR entry.
