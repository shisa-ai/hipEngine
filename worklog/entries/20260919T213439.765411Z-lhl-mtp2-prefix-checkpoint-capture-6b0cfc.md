# Capture the prefix checkpoint at the walk's block-aligned boundary

## Summary

Task #21 unit 1b, second half: the capture. The priming walk in
`_catch_up_provider` (`hipengine/generation/qwen35_gguf_mtp2.py`) now takes one
snapshot per prompt, on the iteration whose `run_step` brings the cursor to the
block-aligned boundary, and stores it in the checkpoint store from `55d731fe6`.

Two design details are worth naming, because both are easy to get wrong in a way
that looks like it works:

- **The boundary hidden row is `rows[boundary - 1]`, not `rows[boundary]`.** The
  walk consumes token `p` with hidden `p-1`, so `rows[p-1]` is the row that
  produces token `p`. For a prefix of length `P` the next token sits at position
  `P`, so the row a restore must hand the first draft step is `rows[P-1]` -- the
  row for the token *after* the prefix. The capture stages it into the step
  buffer and `snapshot_prefix_state` takes its own copy, so the next iteration's
  overwrite of that buffer is harmless.
- **The boundary is `floor(prompt_len / block_size) * block_size`.** The cache
  only matches whole blocks, so a checkpoint taken at the prompt's end would
  never be looked up.

Both the block size and the block ids belong to the runner (the radix cache owns
the former and the row's allocation the latter), so the adapter takes them
through two attributes rather than reaching for them: `prefix_checkpoint_capacity`
and `prefix_checkpoint_block_size` (0 disables capture) and a
`prefix_checkpoint_key` callable returning the row's current block ids. **Capture
is off by default** -- zero capacity -- so nothing changes until the runner wires
it, which is the next unit.

A capture that cannot be taken is skipped rather than raised: no store, no key,
no block ids, an executor without `snapshot_prefix_state`, or a snapshot that
refuses all leave the row decoding exactly as it does today. The checkpoint is
an optimization, and a request must not fail because its prefix could not be
cached.

## Validation

The new tests use the file's existing executor-double style and pin the parts
that are silent when wrong:

- **the capture point**: a shared log records steps and snapshots, and the test
  asserts `step 7, snapshot 8, step 8, step 9` -- the snapshot lands after the
  step that brings the cursor to 8 and before the remaining prompt steps, which
  is what makes the recurrent state current at exactly `prefix_len`;
- **the boundary row**: the staged copies are read back through `ctypes` and the
  capture's own copy (index 8 of 12: ten walk steps, the capture, the final
  root-buffer copy) equals `float_array_to_bf16_bits(rows[7])`;
- **the stored key**: the blob is retrievable as `prompt_ids[:8]` with block ids
  `(11, 12)` and a later lookup with moved block ids misses, so the store's
  validation is exercised through the capture path rather than only in the
  store's own tests;
- **the off switches**: zero capacity stores nothing and builds no store, a zero
  block size takes no snapshot, a key provider returning `None` skips, a
  snapshot that raises is contained and stores nothing, and an executor with no
  `release_prefix_state` gets no store at all rather than one that would leak.

Guards: the seam file plus both checkpoint files, the accounting file, and the
shadow-lifecycle file -> 175 passed.

## What this does not do

The runner still does not set the three attributes, so capture never fires in
production yet. That is the next unit: `_refresh_prefix_cache(row)`
(`hipengine/generation/qwen35_gguf.py:7026`) runs right after admission with the
row's allocation in hand, which is where the block ids and the cache's block
size are both available.
