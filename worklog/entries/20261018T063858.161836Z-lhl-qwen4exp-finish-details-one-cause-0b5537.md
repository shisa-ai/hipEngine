# qwen4exp finish details name one cause

## Summary

A request `stop` string trimmed on the server produced `finish_details` with
`reason: "stop"` beside the backend's `eos_token_id`. The model had generated
the stop text and then EOS, so the backend finish was `eos`; the server trimmed
the text and rewrote only `reason`, leaving a payload that named two different
causes. The matched stop string was also never reported, so a client could not
tell which of several stops fired.

Observed on the resident qwen4exp server (Qwen3.8-Flash-Next UD-Q4_K_XL,
gfx1151, production profile, `stop: ["STOPHERE"]`):

```
{"reason": "stop", "eos_token_id": 248046, "sampler_mode": "processed_argmax",
 "cache_action": "append_none"}
```

`_apply_stop` now returns the matched string, and `_finish_details_payload`
drops the backend's `eos_token_id`, `length_limit`, and `stop_sequence` when a
server stop supplies the reason, then records `matched_stop`. All five call
sites (completions and chat, streaming and blocking) pass it through.

## Changes

- `hipengine/server/api.py`: `_apply_stop` returns `(text, reason, matched)`;
  `_finish_details_payload` / `_chat_finish_details_payload` accept
  `matched_stop` and remove the contradictory backend cause fields.
- `docs/API.md`: `finish_details` documents `matched_stop` and the one-cause
  rule.
- `tests/test_integration_server_api.py`: the stop expectation asserts
  `matched_stop` and the absence of the backend cause.
- `scripts/qwen4exp_finish_route_audit.py`: live finish/route audit. Length,
  EOS, stop, and sampled-MTP cases; each finish claim is checked against the
  payload that produced it.

speculation is implemented on this route, so the response reports
`used: true`, names `qwen4_exp_mtp`, and its draft/accepted counts equal the sum
over the reported cycles. An earlier draft of the audit asserted a named
fallback here and was wrong about the route.
