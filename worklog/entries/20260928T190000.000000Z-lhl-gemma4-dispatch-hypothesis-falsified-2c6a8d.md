# the host-dispatch hypothesis is falsified: the wrapper costs 18 microseconds, not 176

## Summary

`20260928T184000` found the dense term's in-situ time to be its isolated kernel time plus
about 0.176 ms per launch of gap, and argued the gap was too large for kernel-launch
overhead and therefore host-side Python and ctypes dispatch. **That is wrong, and this unit
measures it directly rather than inferring it from a share.**

A back-to-back launch loop with no intervening synchronize costs **0.0177 to 0.0203 ms per
launch** -- 18 to 20 microseconds -- against GPU times of 0.49 to 1.51 ms for the same
kernels. **The host is 28 to 77 times faster than the GPU work it queues.**

```
shape          host dispatch   gpu         host/gpu
4096 -> 2816   0.0203 ms       1.5071 ms   0.013
2816 -> 4096   0.0185 ms       1.0519 ms   0.018
2816 -> 2112   0.0177 ms       0.4935 ms   0.036
```

**The prefill is not dispatch-bound at the wrapper level**, and the 0.176 ms gap is not
Python or ctypes cost.

## What this does and does not refute

**Refuted: the wrapper is the bottleneck.** 20 microseconds per launch across 206 dense
launches is 4.1 ms, about an eighth of the 36.2 ms gap. Even if every launch were pure
wrapper overhead with the GPU idle, the wrapper cannot account for the gap.

**Not refuted: that the gap exists, or that it is host-side.** The measurement bounds the
*launch call* and nothing else. The engine's per-launch path is more than a launch call --
argument construction, registry dispatch, and whatever else runs between two kernels in
`gemma4_layer_forward_bf16`. **A host-side cost of 0.176 ms per layer step that is not the
ctypes call remains possible**, and the two candidates that fit that size are a host
round-trip (a readback or synchronize) and Python-side per-layer work.

**Also not tested: the device side.** Kernel-to-kernel transition latency, cache flush
between kernels, and event-record overhead all sit inside the in-situ per-call time and
none is bounded by this measurement.

## Why this is worth recording rather than quietly dropping

The previous entry's argument was an inference from a size -- "0.176 ms is too large for
launch overhead, therefore it is host dispatch" -- and it reached a mechanism the
measurement did not support. The direct measurement cost ten lines and reverses it.

**It also removes the scaling prediction that was queued as the next test.** That prediction
(the gap's share should grow with prompt length) was a consequence of a per-launch cost; with
the wrapper bounded at 20 microseconds it no longer follows from anything established.

## Next

- **Get a timeline instead of a budget.** Every number in this line of work is a sum over
  intervals; a profiler trace of one 512-token prefill step would show the 36.2 ms as
  concrete gaps with names attached -- which kernel precedes each gap, whether the gap is
  host-side or device-side, and whether it clusters at a particular layer. That is the
  measurement that ends the guessing, and `scripts/gemma4_expert_mmq_wrapper_split.py` and
  the `*_rocprof.py` probes are the existing precedents for doing it.
- **Do not add more budget arithmetic.** Two entries have now been spent decomposing a sum
  whose terms are being read from overlapping event intervals. The gap needs a timeline.
- **The orientation effect remains the only kernel-level rate gap in the dense term**
  (worth about 22 ms) and it is unaffected by this.
