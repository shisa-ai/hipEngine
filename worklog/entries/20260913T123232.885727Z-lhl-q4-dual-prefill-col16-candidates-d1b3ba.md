# gfx1151 Q4 dual-SiLU prefill: col16 tile candidates + parity gate

## Summary

The dominant gfx1151 prefill kernel
(`gguf_q4_t16_dense_dual_wmma_prefill_silu_bf16_kernel<false,false,4,4>`, 33-36.5%
of prefill kernel time) can now express a 16-column output block. Two candidate
arms are registered under the existing four-axis key and are bit-identical to
the 32-column parent at every row count:

| Variant (`linear_pair_silu`/`gguf_q4_k_t16_v1`) | Instantiation | VGPR | LDS | grid x (5,120 -> 17,408) |
| --- | --- | --- | --- | --- |
| `dense_dual_wmma_prefill_bf16_bf16_out` (owner) | `<false,false,4,4,2>` | 248 | 32 KiB | 544 |
| `dense_dual_wmma_prefill_col16_row256_bf16_bf16_out` | `<false,false,4,4,1>` | 224 | 16 KiB | 1,088 |
| `dense_dual_wmma_prefill_col16_row512_bf16_bf16_out` | `<false,false,8,4,1>` | 248 | 32 KiB | 1,088 |

Neither arm is selected by dispatch or any engine path; the parent stays the
strict owner and the registered fallback. Selection is a later decision and
requires a same-protocol prefill gate, so this unit retains **no performance
claim** and moves no published number.

The screen's occupancy arm (16 columns x 256 rows with `__launch_bounds__(128,4)`)
was implemented, measured, and removed in the same unit: on this toolchain the
launch-bounds min-blocks floor does not constrain register allocation, so the
arm was a renamed duplicate of `col16_row256`. Evidence and the named
alternative mechanism are in `docs/REFACTOR.md`.

## Changes

- `hipengine/kernels/hip_gfx1100/quant/gguf_k_t16_selected_prefill.hip`:
  `out_tiles_per_block` template parameter on the dual SiLU kernel and its
  launcher (default 2, so every existing instantiation keeps its exact template
  arguments), the launcher's column divisibility check now derives from that
  parameter, the row-tiles-per-wave `static_assert` bound moved 4 -> 8, and two
  new `extern "C"` exports. The K16 WMMA association, the BF16 gate/up rounding
  boundary, and the block/grid arithmetic are unchanged, which is why the arms
  are exact.
- `hipengine/kernels/hip_gfx1100/quant/gguf_k_t16_selected_prefill.py`: the
  shared dual launcher helper takes `column_tiles` (default 2) so the 16-column
  arms validate a 16-column contract instead of a 32-column one; two symbol
  constants, two wrappers, two registry entries, two `__all__` entries.
  Registration is the only reachability path: no dispatch, policy, or engine
  branch names these variants, and the gfx1151 backend picks them up through the
  existing shared-body alias in `hipengine/kernels/hip_gfx1151/__init__.py`.
- `tests/test_unit_gguf_q4_t16_dual_prefill_col16.py` (new, unit tier, CPU only):
  resolves both arms on `hip_gfx1100`, resolves their `hip_gfx1151` aliases,
  asserts the strict parent owner stays registered and distinct, pins both
  exported C symbol names through a recording ctypes stand-in, and pins the
  column contract (16 accepted for the arms, 32 still required by the parent).
- `tests/test_gpu_gguf_q4_k_t16_dense.py`: a new strict gate
  (`test_q4_t16_dense_dual_col16_wmma_silu_matches_parent_and_cpu_reference`,
  10 cases) and four new cases in the existing production-shape gate
  (`..._matches_unfused_chain_at_production_shape`, now 13 cases).
- `scripts/qwen38_packet4_q4_dual_silu_row_leaf.py`: the two arms joined the
  candidate list, with the per-arm reporting loop derived from the candidate
  dict instead of a repeated literal list.
- `docs/REFACTOR.md`: retirement condition for the arms and the measured
  launch-bounds finding.

## Validation

RED first: both new test groups failed before the kernel/registry change
(`is_registered` false for all three arms; `getattr(t16_prefill, ...)` returned
`None`), and pass after it.

Strict gate (GPU, gfx1151, ROCm `therock`, `hipcc` 23.0.0git):

```bash
.venv/bin/python -m pytest \
  "tests/test_gpu_gguf_q4_k_t16_dense.py::test_q4_t16_dense_dual_col16_wmma_silu_matches_parent_and_cpu_reference" \
  "tests/test_gpu_gguf_q4_k_t16_dense.py::test_q4_t16_dense_dual_wmma_silu_matches_unfused_chain_at_production_shape" -q
# 23 passed
```

The 10-case test asserts, per arm and per row count (7/16/33/256/512):
bit-exact equality with the parent owner, bit-exact equality with the unfused
chain (two `shared_b` owners plus `silu_mul_separate_out_bf16`, which re-applies
the fused kernel's exact BF16 boundary), and `rtol=0.012, atol=0.5` against
`kernels/cpu_reference.ops.gguf_quant_gemv` on both projections. The 13-case
production-shape test asserts bit-exact equality with the unfused chain at
5,120 -> 17,408 for rows 45/96/192/256/511/512/1,024.

The CPU floor is asserted on the two BF16-rounded projections and not on their
product, deliberately. On the synthetic Q4_K fixture the up-projection cancels
O(1) summands down to ~1e-2, so a ~1e-3 fragment-rounding error is a large
*relative* error in `silu(gate) * up` even when both inputs are correct:
measured at 256 rows, parent parity was exact while 7 of 8,192 product cells
exceeded `rtol=0.012` (worst cell: expected -0.566, actual -0.914, gate 74.0,
up -7.7e-3). Asserting a product tolerance there would gate the fixture's
conditioning, not the kernel.

Kernel trace (new kernel, gfx1151, `rocprofv3` 1.3.5, prebuilt `.so` with
`HIPENGINE_REQUIRE_CACHED_BUILD=1`, real `blk.0.ffn_gate/up` tiles from
`Qwen3.8-27B-Q4_K_M.gguf`):

```bash
hipcc --version > /tmp/hipengine-hipcc-version.txt
rocprofv3 --kernel-trace --output-format csv -d /tmp/q4-col16-trace2 -- \
  env HIPENGINE_REQUIRE_CACHED_BUILD=1 \
      HIPENGINE_COMPILER_VERSION_FILE=/tmp/hipengine-hipcc-version.txt PYTHONPATH=. \
  .venv/bin/python scripts/qwen38_packet4_q4_dual_silu_row_leaf.py \
    --model /models/gguf/Qwen3.8-27B-Q4_K_M.gguf --rows 512 1024 \
    --burst 2 --repetitions 1 --warmups 1 --output /tmp/q4-col16-trace2/rows.json
```

Both arms appear under their expected mangled names with zero scratch and the
expected grids (`col16_row256`: VGPR 224, LDS 16,384, grid 1,088 x 2 at 512 rows;
`col16_row512`: VGPR 248, LDS 32,768, grid 1,088 x 1 at 512 rows, x 2 at 1,024),
and both report `bit_equal: true` against the parent at both row counts on real
tensors. Durations in that trace are single-shot and profiler-wrapped, so they
are recorded as smoke evidence only, not as a benchmark.

Launch-bounds occupancy probe (the reason the third arm was removed):

```bash
python3 scripts/gguf_prefill_kernel_resources.py \
  --source hipengine/kernels/hip_gfx1100/quant/gguf_k_t16_selected_prefill.hip \
  --arch gfx1151 --waves-per-workgroup 4 --filter dense_dual_wmma_prefill
# <false,false,4,4,1,1> vgpr=219 lds=16384 ; <false,false,4,4,1,4> vgpr=219 lds=16384
```

A patched copy with a literal `__launch_bounds__(128, 4)` also reports
`vgpr=219`, and the profiler agrees (224 VGPR, scratch 0, both spellings), so
the floor cannot create the 4-workgroups-per-CU occupancy the screen's second
candidate assumed. Resident workgroups stay VGPR-bound at 2 per CU for both the
parent and the 16-column tile.

The same resource probe on `--arch gfx1100` compiles both arms and reports the
same shape (`col16_row256`: vgpr=219, lds=16384; `col16_row512`: vgpr=241,
lds=32768), so the new instantiations are not gfx1151-only.

Narrow regression bundle (CPU, unit tier): the new unit file plus
