# Measure a dependent reduction chain and withdraw the collective-cost estimate

## Summary

Repairs review finding R3 (P1). The previous chain ladder put every reduction
inside one native group and re-read unchanged send buffers, so its marginal
latency (28-35 us) measured the cost of adding an op to an open group, not the
cost of a dependent reduction. Multiplying it by 128 row-parallel projections
produced the published 3.66-4.48 ms per-token collective estimate, which is not
a model-step cost.

The new protocol measures a real chain: each reduction runs in its own native
group, and a stream-ordered device copy consumes the previous reduction result
and produces the next input, so the final value depends on every step. The value
is checked against exact arithmetic, which turns the measurement into a
dependency test.

The result changes the decision input by an order of magnitude, and the batched
structure the old ladder measured is shown on hardware to be unable to carry a
dependency at all.

## Protocol

- `_measure_dependent_chain()` in `scripts/tp_collective_bench.py`, enabled by
  `--dependent-depths` (default `1,4,16,32,64,128`).
- Per step: one `group_start`/`group_end` boundary around one all-reduce per
  rank, preceded by a `memcpy_async` (device-to-device) that reads the previous
  result and writes this step's input on the same stream.
- Both group modes are measured. `per_step` is the correct structure;
  `per_chain` reproduces the batched structure of the old ladder and is kept as
  the contrast case.
- Verification: every rank starts at 1.0, so a dependent chain of depth ``d``
  over two ranks ends at ``2^d`` (infinity once the dtype saturates) while a
  chain that ignores its predecessor ends at 2.0. The chain is re-seeded outside
  the timed region each iteration, so the expected value does not depend on the
  iteration count.

## Measured on two GPUs (W7900 + XTX, gfx1100, host-staged collectives)

Exact command:

```bash
uv run python scripts/tp_collective_bench.py --mode collective --devices 0,1 \
  --rows 1,2 --prefill-rows 128 --dtypes fp32,bf16 --ops all_reduce \
  --iterations 30 --warmup 10 --chain-depth 1,16,32 --enqueue single \
  --dependent-depths 1,4,16,32,64,128 \
  --json benchmarks/results/2026-09-14-w7900-tp2-dependent-reduction-chain.json
```

## The batched structure cannot carry a dependency

`per_chain` fails the value check at every depth: at depth 128 the final value is
exactly **2**, the single-step value, meaning no consumer copy ever read a
reduction result. RCCL defers its collectives until `group_end`, so every copy
enqueued between `group_start` and `group_end` runs before every collective in
that group. A dependent layer chain therefore needs one group per layer boundary;
it is not a tuning choice.

This is also why the old ladder could not measure a per-layer cost: its numbers
are reproducible (36 us/step here versus 28-35 us before) but they describe a
structure in which the dependency the model needs is absent.

## Consequence for the per-token estimate

At the decode shape (rows 1, 20 KB fp32 per rank), one dependent reduction costs
**177.8 us**, so 128 row-parallel reductions per token cost **22.8 ms** of
collective time. The published estimate was 3.66-4.48 ms. The single-GPU token
time used in that comparison was 33.5-35.8 ms, so on the eager path TP2 does not
break even: the corrected collective cost alone is 64% of a single-GPU token.

Two limits on this conclusion, both recorded rather than resolved here:

- The consumer is a device copy, which models the dependency a real layer
  boundary creates but not the layer's compute. A real step also has that
  compute on the stream, which changes overlap but not the group count.
- The remaining candidate is a captured HIP graph containing the per-boundary
  groups, where replay replaces 128 host-side group transitions. That path needs
  its own measurement and its own graph-composition qualification; the earlier
  49-node claim came from the aggregated protocol and is not evidence about it.
