# Diagnose fresh-owner dense MTP acceptance variation

## Summary

Investigate the fresh-owner acceptance variation observed during snapshot-copy
validation without conflating unchanged final output IDs with control equality.

## Changes

- Replaced per-owner timed tuning with the first executable hipBLASLt heuristic
  candidate. Candidate launch failures advance in fixed order; no executable
  candidate raises a named error. Existing session/stream ownership is unchanged.
- Added CPU RED/GREEN tests for timing-independent selection and ordered
  rejection fallback, plus a public fresh-owner regression.

  cycle/accepted-token outcomes, plus one within-owner 20/43 result.
- Current-source public reproduction runs six fresh owners, each with the same
  warmup and three heldout_general_ja_speculative repeats. Snapshot copying is
  unchanged. Command: `bash /tmp/hipengine-repair-run.sh /tmp/mtp-repeatability-traces.py`.

- Current-source reproduction completed: six fresh owners, three repeats each,
  all 19 cycles / 44 accepted tokens. Every prepared proposal/target trace,
  acceptance summary and generated ID sequence matches across all runs.
  Tracked allocations return to zero after every owner closes.
