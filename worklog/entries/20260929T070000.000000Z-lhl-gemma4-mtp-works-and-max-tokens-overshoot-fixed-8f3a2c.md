# Gemma 4 MTP works: 2.10x decode at budget 6, bit-identical, and the route was overshooting max_tokens

## Summary

**The objective's MTP item is answered: it works, and it is worth 2.10x.**

```
plain generate()                 :  28.91 tok/s  (2.21s)
generate_speculative_mtp_detailed:  60.74 tok/s  (1.05s)
speedup                          :  2.101x
outputs identical                :  True
```

Budget sweep at 64 tokens, both routes warmed before either is timed:

| 2 | 28.40 | 45.94 | 1.618x | yes |

## `gemma4_mtp_e2e_speedup.py` cannot report MTP working

That script calls `hipengine.LLM(model=...)` with no `speculative_provider` and no
`draft_model`. `llm.py:1353` only enters the provider-resolution block `if
self.speculative_provider is not None`, so the script's `supports_speculative_mtp: False` and
`generate_speculative_mtp_detailed: NOT SUPPORTED` describe **the script's own arguments, not
the feature**. Its `--help` offers no way to supply either. MTP is registered
(`speculative/registry.py:311`) and wired (`gemma4_gguf.py:317 attach_speculative_provider`),
and the assistant sidecar `mtp-gemma-4-26B-A4B-it-Q8_0.gguf` is present beside the artifact.

`scripts/gemma4_mtp_probe.py` is added: it supplies the provider and the sidecar, **warms both
routes before timing either** (the first `generate()` on a fresh process pays the JIT, and
timing a cold plain call against a warm speculative one reports the JIT rather than the
speedup -- 3.52 against 45.94 tok/s, a spurious 9.4x), and checks that the speculative output
equals plain greedy.

## The route overshot `max_tokens`

At budgets 3 and 4 the speculative output was **not** identical to plain. The tokens were
right -- the spec text was an exact prefix-extension of plain's, every shared character equal
(192 against 197 chars) -- but the route emitted more tokens than the request allowed.

The cause is in `gemma4_mtp.py`. A cycle commits `accepted + 1` tokens: the accepted drafts
plus the row at `accepted`, which is always kept. The old line capped only the *drafts*:

```python
budget = min(self.candidate_budget, request.max_tokens - len(generated))
```

so with one token left the cycle drafted one, the verify read two rows, and the commit landed
one past `max_tokens`. It shows only when 64 is not a multiple of the realised cycle length,
which is why budgets 2, 6 and 8 happened to agree and 3 and 4 did not.

**Fixed** by leaving a row of headroom so the commit is bounded by construction:

```python
remaining = request.max_tokens - len(generated)
budget = min(self.candidate_budget, remaining - 1)
drafter.max_drafts = budget if budget > 0 else 1
drafts = drafter.draft(token, hidden_row=seed_row) if budget > 0 else []
if not drafts and budget > 0:
    break
```

`remaining == 1` now takes a zero-draft cycle, which is a plain single-token verify: the row
count is `len(drafts) + 1 == 1`, `accepted` stays 0, and the commit is exactly one token.
`max_drafts` is never assigned the zero `__post_init__` rejects. Qwen's route
(`qwen4_exp_mtp.py:226`) already stops exactly at `max_tokens` by checking after each
single-token step; this brings the batched-verify route to the same contract.

**All three budgets that disagreed now agree**, with the speedup unchanged (1.788x, 1.890x,
2.101x against 1.792x, 1.871x, 2.121x).

## Changes

- `hipengine/generation/gemma4_mtp.py` -- bound the draft budget at `remaining - 1` so a cycle's
  `accepted + 1` commit cannot pass `max_tokens`, and route the `remaining == 1` tail through a
  zero-draft cycle instead of letting the `not drafts` guard break out of the loop.
- `scripts/gemma4_mtp_probe.py` -- new. Supplies the provider and the assistant sidecar, warms
  both routes before timing either, and checks the speculative output against plain greedy.

The two unit suites pass. `test_gpu_gemma4_assistant_forward.py` has **two failures that are
pre-existing and unrelated**: `test_the_draft_chain_reproduces_llamacpps_candidates` and
`test_the_adapter_cycle_agrees_with_a_token_by_token_decode`. Both were reproduced with this
change stashed, and both are tie-order differences against llama.cpp -- the same candidate set
in a different order (`[139, 623, 3729]` against `[139, 3729, 623]`), and a bonus token of 580
against 1131. They concern `Gemma4SpeculativeCycle`, not the `Gemma4MTPCycle` this unit
touches.
