# Correct the dense-wide baseline to the production dispatch

## Summary

The dense-wide candidate's baseline was mislabeled in the entry it shipped with
([20260916T114012](./20260916T114012.802993Z-lhl-dense-wide-q8-prefill-candidate-3b0656.md)).
That entry calls `coltile8_rowbatch4_f32_f32_out` at 19.663 ms "the production
dispatch". It is the **strict** dispatch. Production replaces it with
`coltile8_rowbatch4_wave_scale_f32_f32_out` at **17.319 ms** for this shape, so
the candidate's gain over the path the model actually runs is **6.74x**, not
7.65x. The 7.65x number is correct as a statement about the strict dispatch.

The kernel, its tests, its registration and every measured number are unchanged.
Only the profile label and the ratio derived from it were wrong.

## Changes

- `benchmarks/results/2026-09-16-dense-wide-q8-prefill-candidate/README.md`:
  table rows are now labeled by dispatch profile, the headline ratio is 6.74x
  with 7.65x stated against strict, and the profile mapping is explained.
- `assemble.py` reads the three capture manifests and emits
  `dispatch_by_profile` plus a `captures` block into `artifact.json`, so which
  number is a baseline for which profile is machine-readable rather than prose.
- `benchmarks/README.md`, `benchmarks/CHANGELOG.md`, `docs/KERNELS.md`: same
  correction in the rollup row and the catalog row.

All three captures carry identical weight, activation and output hashes
(prefixes shown; full values in `artifact.json`), so the two dispatches were
timed on the same bytes and produced the same output. The production timing
itself comes from two independent measurements: the registered-variant sweep
(17.319 ms, 30 repetitions) and the earlier three-round counterbalanced A/B
(17.346 ms, 10 repetitions per round).

`assemble.py` re-run clean; the artifact carries the mapping.
