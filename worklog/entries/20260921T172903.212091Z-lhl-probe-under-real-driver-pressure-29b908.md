# Probe responsiveness with a real EngineService holding its driver thread

## Summary

Final slice of the readiness item, closing the gap left by the existing
responsiveness test.

That test
(`test_integration_server_api.py::test_busy_snapshot_does_not_block_other_http_requests`)
injects a fake engine whose `live_loop_snapshot` blocks on a worker thread. It
proves the event loop stays free -- which holds -- but it bypasses the engine
service entirely: no driver thread, no command budget. It therefore cannot show
what bounds `/ready`, nor how the endpoints behave once a budget expires.

This module drives the **real** `EngineService` with a driver whose control
method holds the driver thread, and puts it behind the real ASGI app. That
reproduces the shape of the MTP pressure case -- long-running engine work
occupying the sole driver thread while probes are polled -- without a GPU.

## What it establishes

- **`/health` answers while the driver is held**, and its latency does not
  approach the command budget. It is a static dict and never reads the engine.
- **`/ready` is bounded by the command budget and then degrades.** With a driver
  that never releases, the probe returns 200 with `ready: true` and no
  `engine_unavailable`, after roughly the budget. It gives up rather than
  hanging, and the readiness verdict is unaffected because it comes from
  `readiness.ready`, the server's own startup state.
- **`engine_service_health` never queues on the driver.** `EngineService.health`
  reads `_unhealthy`/`_closed` directly (`engine_service.py:292`), so the
  service-health half of the payload is answered without touching the driver
  thread. Only the snapshot read is exposed to the pressure. That is why the
  pressure case costs `/ready` its diagnostics rather than its verdict.

## Changes

- `tests/test_unit_server_mtp_pressure_probe.py` (new), 3 cases, over a real
  `EngineService(driver, command_timeout_seconds=0.6)`:
  - `/health` returns while `/ready` is provably still pending on the driver
    (the test waits for the driver to signal it received the command, and
    asserts `/ready` has not completed, before timing `/health`);
  - `/ready` returns within the budget plus slack when the driver never
    releases, with `ready: true` and no error code;
  - `engine_service_health` answers promptly while the driver is held by
    another thread.

  The driver's hold is an event rather than a sleep, and the fixture releases it
  before `close()`, because `close` enqueues its own command and waits on the
  same budget.

## Next

- The live measurement remains outstanding: whether a real MTP cycle holds the
  driver thread long enough for the budget to matter. The mechanism is now
  exercised end to end against the real service, so the remaining unknown is
  the duration of real MTP work, not the behaviour under it. That needs a
  server (PID 4175913 holds ~96 GiB of GTT).
- The recommendation from `8dfb8ddb0` stands and is untouched by this unit: if a
  probe needs a ceiling tighter than the liveness budget, add an optional
  per-call budget on the diagnostics control path only. This module would cover
  the change.
