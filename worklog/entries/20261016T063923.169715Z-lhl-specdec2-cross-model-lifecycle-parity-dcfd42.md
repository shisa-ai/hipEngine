# Add cross-model lifecycle-parity contract tests

## Summary

Extended `tests/test_unit_specdec2_cross_model_contracts.py` from 16 to 37 collected tests with five cross-model lifecycle-parity functions, closing the gaps the task-#18 test review identified: per-model seam suites each test lifecycle events against their own fixture only, so nothing asserted the same event behaves consistently across the dense/MoE/PARO owner shapes.

## Changes

- `test_a_failed_stage_keeps_a_sibling_stream_and_a_retry_healthy` (9 cases, shape x stage): a failure injected at prepare/propose/execute leaves the sibling stream's staged state intact, releases the failing cycle's claim reservation exactly once, and leaves the owner reusable for a retry under a fresh operation id.
- `test_cancellation_resolves_at_the_target_boundary_without_publishing_the_cancelled_row` (3 cases): a cancellation consulted through the loop's callable publishes nothing for the cancelled row; survivors commit exactly themselves, and an uncontested follow-up cycle publishes every row.
- `test_every_refusal_records_a_named_reason_and_admission_records_none` (5 cases): every refused semantics query records a stable non-empty reason - repeated, not suppressed - while an admitted query records none, so a silent downgrade cannot hide behind a bare `None`.
- `test_a_frontier_without_a_kv_binding_still_names_its_kv_keys`: pins today's production frontier shape (`kv_binding=None` plus the loose KV string keys, since no adapter populates a binding yet) and proves a half-populated binding that disagrees with the frontier's own keys is refused by name.
- `test_staged_state_is_per_cycle_not_per_request_lifetime` (3 cases): the same request id runs consecutive cycles with per-cycle staged state; an interleaved unrelated request sees neither.
- Owner-double extensions: `release_speculative_claims` now records releases, and `execute_target_frontier` consults the `cancelled_request_ids` callable and excludes cancelled rows from its committed result.
- No production code changed.

No-RED rationale: these are additive contract pins over existing behavior of unchanged production records (`TargetFrontier`, `SpeculativeCapability`, the seam protocol) and the fixture doubles; there is no new production behavior to drive red first. Each pin documents a contract the per-model suites assume per-fixture.
