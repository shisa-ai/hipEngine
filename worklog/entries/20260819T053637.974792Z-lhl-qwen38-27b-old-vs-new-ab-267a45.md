# Qwen3.8-27B old-vs-new (G1 vs C2) same-protocol A/B: parity, no scaling, C2 packed invariance break

## Findings

### F1 — Neither design scales this model (pre-existing, not a C2 effect)

Packed c2/c4 decode costs ~5x the c1 per-step time in BOTH trees:
ITL p50 = 36ms (c1) vs 184ms (c2) vs 198ms (c4), so aggregate tok/s DROPS
c1→c2 (23.2→10.1) and only partially recovers at c4 (17.6). The pre-C2
tree shows the identical collapse (same route counters: 889
`native_packed_decode_steps`, same ITL to the millisecond). This is a
model-specific property — Qwen3.8-27B is dense and weight-bandwidth-bound,
and the gfx1100 packed decode kernel (the "qmicro planar rowtile" family)
does not reuse weight bandwidth across the batch for this shape. The 35B-A3B
MoE (the C2-6 retained model) has no such collapse: its packed path scaled
1.68x at c8. Physical c8 is unavailable in both designs (old registry cap 4;
new rowtile [2,4]).

### F2 — C2 packed path breaks batch-composition invariance for this model (regression)

The pre-C2 tree is byte-exact vs the c1 oracle at c2/c4 (6/6, 12/12). The
current C2 tree is NOT: prompt row 2 (sha256 21bb8bca19ecba9c…) matches the
c1 oracle through decode token 73, then emits 6866 where the oracle emits
3154 (deterministic across all c2 and c4 runs). Only the prompt row that
generates varied tokens before converging to the 9707 repeat diverges; the
all-9707 rows stay exact. Batch-composition invariance is a first-class gate
(EXECUTION-PROFILES), so the current C2 packed route for this model fails
its strict-parity contract even though its speed is unchanged.

Candidate root causes (to bisect, not yet confirmed): the C2 packed-KV /
workspace changes — af5d00098 (GlobalDeviceKVPool workspace leases for
execution state) and 29a786afc (page-aware packed KV copies via
packed-state page table) — which touch exactly the packed decode data path.
