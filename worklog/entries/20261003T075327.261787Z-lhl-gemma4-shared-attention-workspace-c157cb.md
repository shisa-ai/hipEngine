# Share one Gemma attention workspace across runner layers

## Summary

`Gemma4Runner.__post_init__` now gives every layer the same
`Gemma4AttentionScratch` instead of one owner per layer. The workspace is
transient -- a layer's launch chain finishes with it before the next layer
starts -- and the block submits all layers serially on the default stream, so
one allocation serves them all. Per-layer owners retained one growth chain per
layer, which is what made the runner's transient attention memory scale with the
layer count on a deep prefill. Kernels, scratch semantics, and the
`Gemma4LayerScratch` default (a standalone layer still owns its own scratch) are
unchanged.

## Changes

- `hipengine/runtime/gemma4.py`: construct one `Gemma4AttentionScratch` in
  `__post_init__` and pass it as `attention=` to every `Gemma4LayerScratch`.
  Cleanup is unchanged: each layer scratch still closes the owner it was handed
  and `Gemma4AttentionScratch.close` is idempotent, so the shared workspace is
  synchronized and freed exactly once on both the normal and constructor-failure
  paths. Different streams still get separate buffers, because the scratch keys
  its allocations by stream.
- `tests/test_unit_gemma4_runner_lifecycle.py`: six CPU tests with a fake
  attention runtime and the existing fake allocator.
- `scripts/gemma4_workspace_ownership_probe.py`: reproducible instrumented
  public-generation owner control using a native campaign packet's exact input
  IDs and output count, with two CPU protocol/cleanup checks.
