# The WMMA dense prefill is 19 percent faster and wrong at short rows

## Summary

I found a real 19 percent prefill win, measured it, gated it, and then **reverted
it**, because the same route that passes the numerical gate over 1023 paired rows
diverges from the exact tiled route by up to 10.9 KL at short prompt lengths and
has no row guard.

The Gemma 4 dense prefill is 29.7 percent of a 512-token prefill and runs
`gguf_q8_0_exact_prefill_tiled_out`, an FMA-tiled kernel whose own source comment
records that its cost is "a block's weight bytes are re-read once per row tile"
and whose accumulator cap (`COL_TILE * ROW_TILE <= 64`) means the tiled family is
already explored to its limit. The tree also ships a WMMA matrix-core dense
prefill. `hipengine/generation/gemma4_gguf.py` contains **no wmma reference at
all**, so the Gemma 4 path never opts into it, while the Qwen resident path ships
`use_wmma_prefill=True` by default.

Turning it on for a 512-token prefill:

| | prefill | decode |
| --- | --- | --- |
| route off | 1.88 s (273.6 tok/s) | 21.02 tok/s |
| route on | 1.52 s (338.0 tok/s) | 20.98 tok/s |

**+19 percent prefill**, decode unchanged. `rocprofv3` confirms the intended
route ran and replaced the tiled kernel: 746.0 ms becomes 234.3 + 111.0 ms, a
2.16x kernel win, and the per-forward union falls 2510.5 to 2027.3 ms.

The campaign's numerical gate passes at 1023 paired rows: mean KL 4.9e-05, p95
1.5e-05, p99 2.1e-04, max 0.0365 against limits of 1e-3 / 5e-3 / 2e-2 / 5e-2,
and **zero top-1 flips**.

## Why I reverted it anyway

The gate exercises 1024-row prefill plus 1023 decode rows. It says nothing about
short prompts, so I measured those directly, comparing the real artifact's
last-row logits with the route on and off as `KL(off || on)`:

| rows | KL | top-1 same |
| --- | --- | --- |
| 2 | 0.187 | yes |
| 4 | 0.658 | no |
| 8 | 0.093 | yes |
| 16 | 0.898 | yes |
| 32 | 3.456 | no |
| 64 | **10.880** | no |

The gate's `kl_max` limit is 0.05. At 64 rows the WMMA arm assigns probability
**0.000000** to the tiled arm's top-1 token. A reassociation difference cannot
drive a token's probability to zero, so this is not the arithmetic difference the
gate was written to bound.

The harness is not the explanation: the off arm run twice produces bit-identical
logits and KL 0.000e+00 at rows 4, 16 and 64.

The divergence is worst at 64 rows and clean at 1024, so the route is sound at
large row counts and broken at small ones. **I did not locate the boundary and I
did not isolate the cause**, which is exactly why I did not add a row floor: a
threshold picked from an unexplained boundary would hide the defect rather than
fix it, and it would make short prompts silently take a different route for
reasons no one could state.

## A pre-existing defect it exposes

With the route forced on, `test_unit_gemma4_runner.py::test_runner_prefill_matches_the_reference`
fails with `gemma4 MMQ gate/up tile row count 0 is outside capacity 224`. I
reproduced it on the **unmodified** tree with only `HIPENGINE_GGUF_WMMA_PREFILL=1`
set, so it is not caused by the landing attempt.

`qwen35_moe_wmma_tile_map_kernel` computes `total` as
`prefix[num_experts - 1]`, the inclusive sum of every expert's padded count, so
`total == 0` means the router's compacted expert starts were all zero. A
different arithmetic path changing the router's output on a degenerate synthetic
fixture is expected; the defect is that `gemma4_project_experts_gate_up_mmq`
**raises** instead of returning `False`, even though its own docstring says it
returns `False` when the weight or geometry does not qualify and the caller falls
back to the fp32 grouped route. It is unreachable on the real artifact, where
top-8 over 128 experts always selects eight.

## Changes

None landed. `hipengine/runtime/gemma4.py`, `hipengine/runtime/gguf_linear.py`,
`tests/test_unit_gemma4_runner.py` and `tests/test_unit_gguf_linear_dispatch.py`
were edited for the landing attempt and reverted to `7f937b948`. The default
prefill route is confirmed back at 1.88 s (272 tok/s) for 512 tokens.

The win remains reachable without any code change:
`HIPENGINE_GGUF_WMMA_PREFILL=1`.

## Validation

- The 19 percent and the 2.16x kernel split are measured, not inferred: the
  campaign bench at 512p/128o with 3 samples and a warmup, and a `rocprofv3`
  kernel trace unioned per forward.
- The gate result is the campaign's own evaluator against a frozen baseline whose
  sha256 is recorded in the artifact.
- The divergence table is a direct logit comparison with a bit-identical
  self-check on the same harness.
- The exposed fixture defect was reproduced on the unmodified tree, which is what
  separates it from the landing attempt.
- No production code changed, so no promotion gate applies.

## Next

  `use_wmma` session would separate the dense route from every other dispatch
  decision `HIPENGINE_GGUF_WMMA_PREFILL` touches. That the env var flips more
  than one route is the leading reason the cause is still ambiguous.
- Locate the row boundary between 64 and 1024 and explain it before any default-on
  landing. The candidates are a k-tile tail in the WMMA kernel (`in_features`
  2816 against the `K_TILES_PER_BLOCK` walk) or a small-row dispatch difference.
- Fix `gemma4_project_experts_gate_up_mmq` to fall back on a zero-row tile map.
