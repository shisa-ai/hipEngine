# R0200: row64 down owner engages in the strict profile, not production

## Summary

Resolve R0200's engagement question: identify and trace the specific public
context that selects the `GGUF_Q4_T16_PHYSICAL_SHARED_B_ROW64` down owner
(shape `(17408,5120)`, rows 33-192).

**Decision: the row64 down owner is a strict-profile owner.** It engages under
`execution_profile="strict"` (BF16 prefill, F16-staging off). The production
default does NOT select it: production enables prefill F16-staging
(`prefill_f16_staging_for` returns true only for `production` without strict
fallback), which swaps the BF16 C1-rowtile dispatcher for the FP16-in sibling
`t16_wmma_prefill_fp16_in_bf16_out` — a single `_launch_dense_t16` launch with no
row64 branch. This is why the 2026-11-08 engagement note saw the down owner
"not engage" in ordinary production prefill. The earlier "used the shared-B
parent" reading was imprecise: production uses the FP16-in sibling, not the
shared-B parent.

## Validation

All runs: W7900 GPU0 (gfx1100), hermetic TheRock env, model
`/models/gguf/Qwen3.8-27B-Q4_K_M.gguf`, public `LLM.generate_detailed` with
token-ID prompts (exact prefill rows), greedy, C1.

Model geometry (GGUF metadata scan): `ffn_down` is Q6_K (33 layers) + Q4_K
(32 layers), shape (in=17408, out=5120); `ffn_gate`/`ffn_up` Q4_K. The row64
owner applies to the 32 Q4_K down layers (`gguf_q4_k_t16_v1`).

Route attribution (registry.resolve audit, production): resolves
`t16_wmma_prefill_fp16_in_bf16_out` x112 vs the BF16 dispatcher
`t16_wmma_prefill_bf16_bf16_out` x5 — production runs the FP16-in sibling, which
has no row64 branch.

Strict-profile row-band trace (F16-staging off, fp16_resolves=0):
- rows 32 -> `shared_b_bf16_bf16_out` (256-row parent, below band).
- rows 33/64/128/192 -> `shared_b_row64_bf16_bf16_out`, 32 calls each (the 32
  Q4_K down layers).
- rows 193 -> `shared_b_w64_bf16_bf16_out` (above band).
Boundaries flip correctly at 32->33 and 192->193; the registered 256-row
shared-B parent is preserved outside the band.

Parity + teardown (strict, rows=64, max_tokens=8):
- Forced the row64 slot to call the 256-row shared-B parent (32 calls at row 64);
  greedy output is bit-identical to the normal row64 run (`parity_match=True`).
  Ownership change, not an arithmetic change.
- `memory_stats()` after `llm.close()`: current_allocated_bytes=0,
  active_allocations=0 (clean teardown).

Tracing note (for future route work): the kernel module self-registers at import
(`gguf_k_t16_selected_prefill.py` bottom), so a monkeypatch must be followed by
`register_gguf_k_t16_selected_prefill_kernels(replace=True)` to reach the
registry; the `wmma_prefill_dispatch_recorder` ContextVar does not cross the
engine driver thread, so a registry.resolve wrapper is the reliable public-route
audit.
