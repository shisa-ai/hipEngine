# qwen4exp batch head graph capture

## Summary

Captured the Qwen4Exp batch runner's final output head — the `root.head_hc_*` GR
read plus the tied `root.lm_head` projection — with the existing `MoeGraphCache`,
so a steady-state step launches one graph instead of two eager GGUF kernels at
the end of `_execute_step`. Arithmetic, metadata, readback, buffer lifetime and
the graph/eager fallback are unchanged. This is an H2 host-overhead increment
only; the parent owns the GPU measurement.

## Changes

`hipengine/runtime/qwen4_exp_batch_runner.py`:

- `_execute_step` now wraps the head's two launches in one `head_unit(stream)`
  closure and runs it through the module's existing `_run_segment` helper, with
  the cache key `("head", rows, residual_ptr)`.
- `_run_segment` gained an optional `key` argument for a unit that is not a
  layer; it still defaults to the layer convention `(graph_key, name)`, and the
  `graph is None` branch still runs the unit eagerly on the caller's stream.
- Comment and `graph_stats` docstring updated: the cache now holds layer segments
  and the output head, and the key shapes are named.

Why the key is what it is:

- **Row width** fixes the launch geometry of both the GR read and the lm_head
  projection, so a captured graph cannot serve a different row count.
- **Residual pointer identity**: a captured graph bakes in the pointer values it
  read, and the head's input is the final residual handed over by the last layer.
  Keying on the pointer means a different input buffer captures its own graph
  rather than replaying one that would read the wrong rows. Contents are *not* in
  the key, which is correct: a replay reads the buffer's current contents at the
  baked pointer, so a normal step at the same width and pointer replays.
- The head is stateless — it writes only its own session-resident scratch and
  `logits`, and keeps nothing across steps — so it is graph-safe under the same
  argument as the layer segments.
- No `inject` guard is needed, and this is the one place the head differs from a
  layer segment. `_layer_graph` refuses to capture a layer whose GR read has no
  inject weight, because that read memsets inject logits on the null stream and a
  capture would not record it. The head passes `inject_weight=None` too, but
  `run_qwen4_exp_gr_read` now zero-fills that buffer with `memset_async` on the
  stream it is handed, so under capture the fill is recorded; the eager path
  (`stream == 0`) keeps the legacy synchronous `memset`, unchanged. This is the
  same stream-aware fill the P8 root/head probe needed to clear HIP 906
  (`worklog/entries/20260831T225648.666763Z-lhl-qwen4exp-p8-root-head-graph-boundary-22d88e.md`).
  Whether `_layer_graph`'s guard is still needed is a separate question and was
  left alone.
- Both launches now receive `stream=` (0 on the eager path, the capture stream
  during capture, the caller's stream on replay), matching the layer segments.
  Previously they relied on the default stream; the eager path is unchanged.

Preserved deliberately:

- **Readback outside capture.** The `capture_logits` D2H copy and the
  `argmax_f32_rows_i32` plus ids D2H stay after the head unit, so no host copy
  enters a capture and no sync is added to a replay.
- **Buffer lifetime.** `close()` already destroys the cache before the scratch it
  references; the head graph now depends on that ordering too, and a test pins it.
- **Fallback semantics.** With `graph_segments` off the head is eager exactly as
  before; a refused or failed capture marks `("head", rows, residual_ptr)`
  eager-only and later steps at that width and pointer stay eager.
- **Torch-free, no new flag, no new metadata field.** No new import, environment
  variable, result field or stats key.

Cost to be aware of: a new key pays two logits-sized D2H snapshots (the eager
reference and the parity replay) plus one eager run of the unit. At width 8 and a
151936-token vocabulary that is about 4.9 MB per snapshot, once per key, never in
steady state.
