# QA-10 closed: the D256 sparse-attention owner has no K-tile or occupancy lever

## Summary

`QA-10` was parked "historically blocked, not tested" with the action *"After `X-3`, inspect the
actual owner for an equivalent configurable K tile/occupancy lever; if present, screen a bounded
pair at real 24/2/256 geometry and tails."*

**`X-3` is CAPTURED at `2789c19d6`, so the dependency was satisfied - and the row's own close
condition applies: there is no applicable lever on either axis it names.**

## Changes

**Ledger `QA-10` closed.** No code, kernel, dispatch or default changed.

**K tile: does not exist.** The owner's decomposition is `grid = (query_heads, rows)`,
`block = (head_dim, 1, 1)`, and the inner loop consumes `head_dim` in a **single block-wide tree
reduction per selected position** - there is no K tiling to configure. `grep -niE
'nbatch|k_tile|ktile|k_batch|TILE_K'` over the whole `.hip` source returns **nothing**, so the
external reference's `nbatch_K` concept has no analogue here. The row's caution not to copy that
constant is not merely prudent; there is no corresponding site to copy it into.

**Occupancy: already maximal.** Static census with `scripts/qwen4exp_repair_register_census.py
--source hipengine/kernels/hip_gfx1100/attention/qwen4_exp_qsa.hip --threads-per-block 256`:

| kernel | VGPR | SGPR | static ins | waves/CU | occupancy |
|---|---:|---:|---:|---:|---:|
| `qsa_sparse_attention_paged_bf16_rows_f32_kernel` (**prefill owner**) | **16** | 49 | 280 | **32** | **100.0%** |
| `qsa_sparse_attention_paged_bf16_f32_kernel` (**decode owner**) | **18** | 50 | 275 | **32** | **100.0%** |

32 waves/CU is the gfx11 ceiling (65536 VGPR/CU, 8-VGPR granules, 8 waves/SIMD across 4 SIMDs).
VGPR 16-18 is far below any granule threshold, so there is no register pressure to relieve and
`__launch_bounds__` cannot raise a kernel already at the ceiling.

**The census discriminates**, which is what makes the 100% credible rather than a default: three
siblings in the same file land at **87.5%** (`h256_wave_rows<true,4>`, VGPR 66), **65.6%**
(`ordered_values_v2`, VGPR 95) and **56.2%** (`h256_wave_rows<true,8>`, VGPR 108). The measurement
responds to register pressure; it is not returning a constant.

**Consequence:** no bounded pair can be constructed, because there is no knob to vary. A "screen"
of two configurations would be a screen of one configuration against itself.

## What this does NOT close, stated so it is not overread

The kernel's real inefficiency is visible in the same loop and is **not** a tiling or occupancy
problem: a full block-wide tree reduction with `2 * log2(blockDim.x)` `__syncthreads()` calls
**per selected position**. That is an issue-limited structure, and it is `QA-2`'s subject ("the
kernel is issue-limited, not traffic-limited").

**The row routes it away itself**: *"A changed reduction belongs under §3.1."* Nothing here measures
or proposes a reduction change, and this closure does not pre-empt `QA-2`.

Also untouched: whether a different *decomposition* - e.g. splitting head_dim across warps rather
than one block-wide reduction - would help. That is a changed reduction, i.e. `QA-2`/§3.1, not a
configuration lever.

## Limits

Static census only - **no GPU execution, no timing, no performance claim**. One arch (`gfx1151`),
one compile-flag set, one `--threads-per-block` value (256, matching the D256 geometry). Register
counts come from the assembler's `next_free_vgpr`/`next_free_sgpr` directives and occupancy is the
gfx11 model's arithmetic on those counts, not a measured occupancy counter. The K-tile conclusion
is a source property of this tree at `7ebd2f68b` and would need re-reading if the loop structure
changes.
