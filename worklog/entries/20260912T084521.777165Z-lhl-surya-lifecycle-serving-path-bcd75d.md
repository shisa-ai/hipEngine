# Surya lifecycle: stage-boundary cancellation, failure recovery, and the serving path

## Summary

Three lifecycle gaps closed, and the KVLiveSpans migration the cleanup ledger
records is now characterized as a device-side blocker with a work breakdown
rather than a vague deferral.

**Cancellation and deadlines are now observed at stage boundaries.** The only
check was per generated token inside `greedy_decode_tokens`, so an already
cancelled or already expired request still paid for preprocessing, the whole
vision tower, and the text prefill before it noticed. Both generators now check
at the top of `_generate_ocr` (before preprocessing), immediately before the
vision tower, and at the top of `_decode_greedy` (before the prefill).

**Failure recovery is exact, and now gated.** An abandoned request leaves the
runner holding a partially written KV cache and advanced conv/GDN state, and
because the abandoned request is the longer one it leaves more written KV slots
than the next request will attend over. `prefill` zeroes the conv and GDN state
and rewrites KV from slot 0, and decode attends only over `_seq_len + 1` slots,
so the follow-up request is bit-identical to the same request on a runner that
never saw the abandoned one.

**One implementation per backend on the public path.** `run_surya_ocr` carried
its own copy of preprocess -> vision -> prefill -> greedy loop, defaulted to the
ad-hoc `"Transcribe this page."` prompt, and had no stop-token, capacity, or
cancellation handling. It now defaults to `FULL_PAGE_HTML_PROMPT` and delegates
to the registered `(surya_ocr2, cpu_reference, fp32)` generator, so the public
entry point and `LLM(...)` share one implementation.

## Results

Stage-boundary checks, measured by the RED tests (a recording stub runner over
the real `_generate_ocr` / `_decode_greedy` code paths):

| request state | stages run before the fix | after |
| --- | --- | --- |
| already cancelled | preprocess, render_prompt, check_vision_capacity, vision_forward, prefill | none |
| already expired | preprocess, render_prompt, check_vision_capacity, vision_forward, prefill | none |
| cancelled during preprocessing | preprocess, render_prompt, check_vision_capacity, vision_forward, prefill | preprocess |
| cancelled during vision | preprocess, render_prompt, check_vision_capacity, vision_forward, prefill | preprocess, vision_forward |

Recovery, gfx1151, `page_table.png` as the reference and `page_dense.png`
abandoned at decode step 8: the follow-up `page_table.png` run reproduces the
reference ids exactly, and an over-capacity rejection followed by another
`page_table.png` run also reproduces them.

## KVLiveSpans assessment

`KVLiveSpans` is a frozen dataclass over hipEngine `Tensor` descriptors and
`Tensor.from_handle` wraps a raw device pointer, so the host half is small: one
`KVLiveSpans` per request from the runner's existing plane pointers plus two
int32 `base_offsets`/`live_counts` device arrays. The kernel half has no
drop-in, verified by inspection:

- Every spans-aware attention or KV-write kernel in `hip_gfx1100` stores BF16
  (`laguna_kv_attention.hip`, `paged_attn_decode.hip`, `paged_kv_write.hip`) or
  int8 with per-token-head scales (`..._int8_scale_f32_spans`). Surya stores
  fp32 KV.
- The only plain dense-context decode kernel
  (`hipengine_qwen35_full_attn_decode_context_bf16`) is BF16-only, takes a
  device `context_len` scalar rather than the spans ABI, and reserves
  `(max_context_len + 256) * 4` bytes of LDS — 66560 bytes at Surya's 16384
  default context, above the 64 KiB per-workgroup limit on gfx11.

Closing the gap therefore means a new fp32-KV spans-aware decode-attention
kernel for head_dim 256 with GQA repeat 4, plus a spans-aware
`surya_scatter_kv_f32`. That kernel would also replace three rocBLAS batched
GEMMs and three elementwise kernels per full-attention layer over a materialized
`(heads, total)` score row, so it is a decode-cost win as well as an ABI fix —
which is why it belongs in its own unit with a strict RED gate against the
current path, a numerical gate, and launch/cycle evidence. Triggers recorded in
`docs/REFACTOR.md`.
