# the GPU prefers the tree over a plain sum but the softmax cannot pin it bit-exactly

## Summary

The logit-tree oracle now runs against the real kernel, and the result is a
partial confirmation with a stated limit.

`tests/test_unit_gemma4_attention_logit_tree.py` **7 passed**, including a
HIP-guarded test that runs `gemma4_attention_prefill_f32` on one query row and two
keys with a one-hot `V`, so the kernel's output at dimension `j` *is* key `j`'s
softmax weight. Twelve random pairs distinguished the tree from a plain
dimension-order sum; the kernel matched the **tree on 7 and the plain sum on 1**.

That ratio is the finding. If my reading of the tree were wrong, neither order
would be favoured and the two counts would be comparable; instead the tree is
seven times as likely to reproduce the kernel. So the tree is the kernel's order.

**The comparison cannot be bit-exact, and the reason is worth recording.** The
kernel's logits are never exposed -- they exist only inside the kernel -- so they
are observable only through `expf` and a divide. NumPy's `np.exp` on float32 is
not `expf` and does not round identically, so a *correct* tree still mismatches on
some pairs. The residual 5 of 12 are that, not a wrong order.

Pinning the tree bit-exactly therefore needs a comparison in the logit domain,
which means either exposing the logits from the kernel or comparing a new kernel
against `gemma4_plain` end to end at exact equality. The latter is the port's
acceptance test and is the shape the geometry suite already uses.

## Changes

- `tests/test_unit_gemma4_attention_logit_tree.py`: adds `_gpu_softmax_pair`,
  `_softmax_pair` and `test_the_gpu_logits_use_the_tree_not_a_plain_sum`, HIP
  guarded via `ctypes.CDLL("libamdhip64.so")` availability so a no-ROCm
  runner skips it rather than failing. The assertion is a comparison of the two
  match counts, not a tolerance, and it fails if either the tree is not the closer
  order or its match count is below half the discriminating pairs.

## Validation

```
uv run pytest tests/test_unit_gemma4_attention_logit_tree.py -v
# 7 passed in 0.45s
```

Twelve discriminating pairs on seed 2024, `head_dim` 256, `tokens=1`, `keys=2`,
`num_heads=1`, `num_kv_heads=1`, `scale=1.0`, `window=0`. Tree 7, plain 1. The
test asserts `tree_matches > plain_matches` and `tree_matches >= discriminating // 2`,
so it cannot pass by the two orders being indistinguishable, and it fails loudly if
a future change makes the tree stop being the closer order.

The bit-exact pins in this file are unaffected and still pass: they compare the
oracle against itself on fixed inputs and never involve the kernel.
