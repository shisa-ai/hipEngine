# Repair mapped embedding borrow for dense NextN

## Summary

Repaired dense NextN fallback borrowing after the XTX sole-resident mapped Q4
token table exposed a stale raw-owner assumption. The first llama-compatible
MTP admission attempt completed target AR but failed before B1 because the
provider borrowed the target plan's allocation-empty placeholder rather than
its effective mapped weight. The repair borrows the mapped device-visible view
and never rehydrates or duplicates the 715,161,600-byte embedding.

## Changes

- Added one runtime helper that borrows the effective target token embedding via
  `ensure_device_token_embedding()` plus the target-owned lm-head.
- Routed both dense category and focused GGUF MTP harnesses through the helper;
  updated the existing GPU transaction setup to exercise the same contract.
- Added a RED/GREEN unit regression proving the mapped owner is selected instead
  of the allocation-empty target placeholder.

## Validation

- RED: focused one-prompt XTX B1-B3 admission reached AR at 20.948993 tok/s,
  then failed in NextN `launch_gguf_embedding()` with `KeyError: 'raw'`; sampled
  peak delta was 16.448 GiB and process teardown returned to baseline.
- RED unit test initially failed collection because the effective-borrow helper
  did not exist.
- GREEN CPU: `uv run pytest -q tests/test_qwen36_dense_gguf_suite.py
  tests/test_qwen35_gguf_nextn_materialize.py` -> 9 passed; the changed GPU E2E
  file collects all seven tests, and compileall/diff checks pass.
- GREEN XTX: same cache-only llama-compatible one-prompt protocol is exact for
  AR/B1/B2/B3. Transition rates are 20.175/46.609/50.272/65.493 tok/s, all MTP
  outputs match true AR, B1/B2/B3 accept 12/16/17 draft tokens, peak delta is
  17.183 GiB, and teardown returns to 0.062 GiB. This one-prompt row is an
  admission diagnostic, not a retainable performance claim.
