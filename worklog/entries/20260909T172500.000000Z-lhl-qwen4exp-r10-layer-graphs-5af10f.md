# R10: decode layer-graph expansion - measured negative, kept default-off

## Summary

Implemented the R6-selected decode graph expansion (#20): the three
stateless GDN layer segments around the stateful conv/recurrent mixer
(attention GR read; gr_write + FFN GR read; MoE epilogue) are now
graph-capturable per layer through the existing MoeGraphCache machinery
(extended with multi-region output validation). Gated by
HIPENGINE_QWEN4_EXP_LAYER_GRAPHS, default off.

Measured results at code-p4096, production routes:

- Capture/replay integrity: 108 captured units (3 segments x 36 GDN
  layers), 756 replays, **0 rejects** (every self-validation parity
  check passed); full state gate (logits, 4 decode steps, recurrent
  state, full KV) bit-identical with graphs on vs off; canonical E2E
  output digests identical.
- **Performance: negative in both measurement contexts.** Raw runner
  step wall: 49.8 -> 50.5 ms/step (warm, +0.6 ms). Serving path
  (canonical AR bench, code-p4096): TG 18.65/18.67 -> 18.58/18.62
  tok/s (-0.5%); PP unchanged within noise (268.2 -> 267.1).

## Interpretation

The R6 estimate ("3-5 ms/token recoverable by graph-capturing the ~1700
individually-launched non-MoE kernels") is refuted: those launches'
host time is already overlapped with device execution. The decode step
is device-bound in the runner loop (step wall ~50.0 ms vs 49.3 ms
device); the serving-path host bucket (~3.6 ms/token above the runner
loop) lives in the generation wrapper (logits D2H, sampling, request
bookkeeping), which layer graphs cannot touch. Graph-node dispatch
overhead makes segment graphs a small net loss.

Consequence for the queue: decode TG progress requires device-side
kernel efficiency (#22, MoE expert GEMV pair, ~9 ms/token potential) or
serving-wrapper host work; launch restructuring is a dead end on this
device/runtime.

- hipengine/runtime/moe_graph.py: run()/capture accept out_regions for
