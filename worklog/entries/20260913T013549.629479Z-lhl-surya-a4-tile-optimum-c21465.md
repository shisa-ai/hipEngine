# Surya A4 page-scale tile optimum

## Summary

The 34320-patch A4 page is the one grid that can only run tiled (a dense score
matrix is 56.5 GB), so it is the grid that tests the shape rule rather than the
byte budget. Swept across 15 query blocks with the byte-budget row included for
the first time, the landscape is:

- **The time optimum is interior, at 4096 rows / 6435.0 MiB / 9 tiles =
  40076.23 ms**, and it is a plateau rather than a point: 2048-8192 rows
  (3217.5-12870.0 MiB) all measure 40076-40618 ms, flat within 1.4%. The
  512 MiB default (320 rows, 502.7 MiB) is **7.4% above it** on the product of
  two same-run ratios, at 1/12.8th of the scratch. Past 4096 rows the curve
  turns back up: 8192 rows is 0.93% *slower* in the same run, so the win from
  fewer tiles saturates around 9 tiles and the wide-tile cost takes over.
- **The knee is at ~320-512 rows / ~500-800 MiB.** The marginal return is
  5.60 ms/MiB (256 -> 320), then 1.43 (320 -> 1024), 0.68 (1024 -> 2048), 0.16
  (2048 -> 3072), and negative past 4096. The 512 MiB default budget therefore
  sits just past the knee: it buys 6.8 of the available 7.4 percentage points
  for 1/12.8th of the memory the optimum wants.
- **The envelope is not the binding constraint here, by design.** The cap is
  `max(128, 34320/32) = 1073` rows, far above the 325 the budget derives, so the
  budget still chooses the shape. The measured budget row confirms it: the
  production plan picks 320 rows at 502.7 MiB and runs 43301.54 ms, 0.04% off
  the explicit 320-row row (43318.30 ms) in the same artifact.
- **The wavefront rounding reproduces.** Every non-multiple of 32 in the
  comparable 256-512 width band is slower than every multiple in the second run
  too (means 46953 vs 43951 ms, a 6.8% gap; the two retained sweeps together
  give 47183 vs 44003 ms, 7.2%). Rounding the budget's 325 rows down to
  320 is worth **47836.19 -> 43318.30 ms (1.104x)** and shrinks the tile
  510.6 -> 502.7 MiB.

Two corrections to the recorded evidence came out of the sweep. The A4 rows in
the shape-envelope entry were single-pass with `--reps 2`; they are now two-pass
and the production row is measured directly rather than inferred from the
planner plus a `--blocks` row. And the entry's "raising
`max_vision_scratch_bytes` above ~6 GB fails with `hipErrorInvalidConfiguration`"
does not reproduce: 4096 rows (6435.0 MiB) and 8192 rows (12870.0 MiB) both ran
cleanly, twice each, in four separate processes.

## Changes

- `scripts/surya_vision_tiling_cost.py` — new `--budgets` selector (MiB values,
  or `dense`) for the byte-budget plans, defaulting to the full set. A grid that
  cannot run densely must not include `dense`, and a budget far below the grid
  makes its row very slow, so both ends needed to be selectable: the A4 sweep
  wants the 512 MiB production row, and running the fixed set would have added a
  ~13-minute 8 MiB row (5 rows across 6864 tiles) and an impossible dense row.
- `benchmarks/results/2026-09-13-gfx1151-surya-vision-tiling-a4-v2.json` — the
  12-plan two-pass landscape (11 explicit shapes plus the 512 MiB budget row).
- `benchmarks/results/2026-09-13-gfx1151-surya-vision-tiling-a4-curve.json` —
  same-run 320/1024/2048/3072 ms against MiB, the time/memory curve the knee and
  the plateau come from.
- `benchmarks/results/2026-09-13-gfx1151-surya-vision-tiling-a4-plateau.json` —
  same-run 2048/2560/3072 rows, the intermediate point that showed the apparent
  2.6% step from 2048 to 2560 in the cross-run numbers was drift.
- `benchmarks/results/2026-09-13-gfx1151-surya-vision-tiling-a4-ceiling.json` —
  same-run 4096/8192 rows, which locates the optimum's far side and refutes the
  ~6 GB launch-failure note.
- `hipengine/runtime/surya.py`, `benchmarks/README.md`,
  `benchmarks/CHANGELOG.md`, `docs/REFACTOR.md` — the A4 numbers move to the
  two-pass artifact, the plateau and knee are recorded, and the launch-failure
  claim is replaced by what the probes measured.

`pass check: 12/12 rows within max(10%, 2 ms)`. Every `pass_ratio` is <= 1.000
(pass 2 faster by 0-2.3%), which is a systematic warm-up or clock effect rather
than the disturbance the check exists to catch — a reversed pass cannot land on
the same shape twice, but it also cannot cancel a drift that favors whichever
pass runs later in the process.

Run C, `--blocks 2048,2560,3072 --reps 2`, the plateau between B's last two
points: 40552.16 / 40470.99 / 40374.40 ms, a 0.44% spread over 3217.5-4826.2
MiB. It is why the plateau is stated as 2048-8192 rows rather than 2048-3072:
the cross-run numbers (A's 41374.20 against C's 40552.16 at 2048 rows) made it
look like a 2.6% step, and the same-run check says 0.44%. Run D,
`--blocks 4096,8192 --reps 2`: 40076.23 ms at 6435.0 MiB against
40448.65 ms at 12870.0 MiB, so the far side of the optimum is a 0.93% turn-up.
Runs A, C and D each contain a shape that appears in another run, which is how
the cross-run drift was measured: 2048 rows is 41374.20 (A), 40552.16 (C) and
40617.58 (B), a 2.0% spread, and 3072 rows is 40362.12 (B), 40374.40 (C) and
40279.84 (a `--reps 1` probe), a 0.23% spread. The default shape is the
steadiest: 320 rows is 43288.39 (B), 43301.54 (A, budget row) and 43318.30 (A,
`--blocks`), 0.07% apart across two processes and a day. So the ordering and the
>=3% effects are the reliable signal; absolute values carry up to 2% between
runs, which is why the headline "7.4% above the optimum" is the product of two
same-run ratios (`43288.39 -> 40362.12` in B, `40076.23/40362.12` across B and
D) rather than a difference of numbers from different runs.

The shape-envelope entry's A4 table additionally lists 384/448/480 rows at
43663-44116 ms and 272/304/400 rows at 45050-45505 ms from that earlier
cliff-mapping sweep, whose artifact was not retained. The tightest
extreme-vs-extreme margin anywhere in the A4 evidence is that sweep's 1.1% (400
rows against 352 rows), and that 1.1% is the honest limit of the claim and the
reason the rounding is documented as a tie-break rather than a guarantee; the
code comment and `benchmarks/README.md` cite the artifact-backed 7.2% for the
means and keep the 1.1% as the caveat. The rounding's own benefit is stable
across both sweeps: 325 -> 320 rows is 48496.26 -> 43862.87 ms (1.106x) in the
first and 47836.19 -> 43318.30 ms (1.104x) in the second.

## Next

- A dense A4 baseline is no longer obviously impossible: the GTT aperture on
  this host is 124 GiB and 120 GB was free at probe time, so 56.5 GB of score
  matrix is inside the device's reach even though 6.4-12.6 GiB tiles run
  comfortably. That would turn the A4 evidence from shape-to-shape into
  shape-to-dense, but it is a ~10-15 minute forward and a 56.5 GB allocation on
  a shared host, so it should be a deliberate decision rather than a side effect
  of a shape sweep. Untested here on purpose.
- The 4096-row optimum is a measured optimum for *this* page on *this* device,
  not a rule: `rows / 8` would be 4290 rows at A4 and would be a bad cap
  everywhere else (the envelope exists because 1024-patch grids want 128-256
  rows). It is evidence for where the A4 budget could go, not a change to the
  planner.
- The 2% cross-run drift on 2048 rows is unexplained and larger than on any
  other shape measured three times; if a future claim needs 2048-row numbers to
  1%, it should measure them in the same run as its baseline.
