# Request-owned sparse QSA index state and batched block selection

## Summary

Adds the N-request form of the sparse QSA index path so the committed dense
batch mixer can be extended past its equivalence bound. No runner, server,
default, kernel, or registry change; the c1 owners are untouched and remain the
fallback.

The audit question this unit answers: **is `query_count = N` on the existing
score kernel independent-request scoring?** It is not. `qwen4_exp_qsa_score_f32`
(`kernels/hip_gfx1100/attention/qwen4_exp_qsa.hip:2363`) computes
`scores[q * blocks + b] = dot(queries[q], pooled_keys[b])` — one `pooled_keys`
array shared by every query. `qwen4_exp_qsa_score_rows_f32` (`:2762`) adds a row
dimension but keeps that single `pooled_keys` and interprets rows as *consecutive
positions of one request* (`first_position + r`, shared block count). Neither can
score two requests with different key histories. Passing `query_count=N` there
would score N queries against one request's keys, which is the mistake this unit
avoids.

What the committed ABI *does* already support row-batched is selection:
`hipengine_qwen4_exp_qsa_topk_expand_rows_f32_i64` (`:2444`) takes per-row query
positions, a per-row score stride, a per-row output slice, and writes a per-row
count, and its kernel body is the same one the single-query `topk_expand` uses.
So the honest split of this unit is:

| stage | dispatches per step (N rows) | batched? |
| --- | --- | --- |
| append raw index key | `N` | no — `scatter_index_key_device_position_f32` takes one page table and one position scalar |
| pool newly complete blocks | `<= N` | no — `pool_norm_rope_f32` writes one contiguous output range from one member map |
| score blocks | `N` | no — every score ABI shares one `pooled_keys` |
| select blocks + tail | **1** | **yes** — `topk_expand_rows_f32_i64` |

3N + 1 dispatches instead of 4N. The per-slot stages are serial kernel dispatch
and are labelled that way; nothing here claims physical batching of the index
path. Section "Missing ABI" states exactly what real batching would need.

## Changes

- `hipengine/runtime/qwen4_exp_batch_qsa_index.py` (new, 947 lines):
  - `Qwen4ExpBatchQsaIndexState.allocate(attention_state, index_heads, index_dim,
    compression_ratio, block_budget, runtime=None)` reuses
    `Qwen4ExpBatchAttentionState` for the cache mappings: slot `s` owns physical
    blocks `[s*bpr, (s+1)*bpr)`, so the raw-key slab is indexed by *global*
    physical position — exactly the value the scatter kernel computes — and the
    member maps of two slots cannot alias. Allocated per slot:
    `[complete_blocks][index_dim]` pooled keys, one `ratio`-wide member map, one
    block-start vector, a `(cursor, pooled_count)` pair, and a reset generation.
    Shared and row-indexed: `scores[rows][complete_blocks]`, `positions[rows]`,
    `selected_positions[rows][budget*ratio+ratio-1]`, `selected_counts[rows]`.
    Geometry whose byte products or int32 member indices cannot be addressed is
    rejected before a runtime is resolved or a byte is allocated, and
    `complete_blocks >= block_budget` is required because the selection kernel
    needs `score_stride >= budget`.
  - `prepare(slot_ids)` publishes the row-to-slot map and uploads one int64 query
    position per row (`cursor - 1`). A slot with no appended key is admitted so
    its *first* append has a row; `select_active` refuses it until a key exists.
    Row order is the caller's, every slot appears at most once, and a copy
    failure clears the active set instead of publishing half a row table.
  - `append_active(raw_keys_ptr)` scatters one key per active row through *that
    row's* page table at *that row's* device position, so a key lands at exactly
    the logical position the row's KV write used. It validates
    `cursor == attention.position_host[row]` first, which is what makes "append
    the index key in the same step as the KV write" a checked contract rather
    than a convention. One dispatch per row.
  - `select_active(prepared_queries_ptr, key_norm_weight_ptr, rotary_dim, theta,
    eps)` pools only newly completed blocks per slot, scores row `r` against
    slot `slot_ids[r]`'s pooled keys, then selects every row in one dispatch.
    Returns `(counts, positions)` host copies plus row-addressed device
    accessors (`selected_positions_row_ptr`, `selected_counts_row_ptr`) for the
    sparse attention consumer.
  - `partition_rows()` splits the active set into dense (within the budget, i.e.
    inside `dense_equivalent_limit`) and sparse row groups, because a row inside
    the bound has no defined sparse selection and the c1 owner rejects it too.
    Mixing both groups in one call is refused with the offending row named.
  - **Rollback is a bounded transaction, not a snapshot.** `begin_rollback()`
    issues one single-use `Qwen4ExpBatchQsaIndexRollback` per owner;
    `rollback(token)` applies and consumes it; `discard_rollback()` abandons it.
    Only counters are captured, as immutable tuples, so a token cannot be mutated
    into false provenance after issue. Counters suffice because every read is
    bounded by them: a speculated append writes raw position `cursor` and a
    speculated pool writes pooled block `pooled_count`, both strictly beyond the
    token, and both are rewritten by the next append at that position. The
    interface is intentionally narrower than a snapshot and enforces it:
    - owner identity is a monotonic per-owner id (not `id()`), so a token cannot
      be accepted by a later owner that reuses a freed address;
    - each slot carries a reset generation, advanced by `reset_slot`, so a token
      captured before a slot was released for a new request is refused — applying
      it would re-expose the previous request's counters to the new one;
    - a token that would move any slot forward past the current cursor is
      refused, because a rewind may only go backwards;
    - a token is accepted only while it *is* the pending token, so it can never
      be applied twice — a rewind followed by an overwrite of the rewound
      positions cannot be re-advanced by replaying an old token;
    - a second `begin_rollback` while a token is pending is refused, so there is
      exactly one live transaction;
    - every rejection happens before any assignment, so a refused rollback
      leaves the counters, the generations, the pending token, and the active row
      set untouched.
    `rollback` also clears the active row set, because published query positions
    may no longer be valid after a rewind.
  - Lifecycle follows the sibling batch owners: `closing` before the first free,
    `_require_open` also poisons the owner when the mirrored attention state is
    closing, `close` drops the pending token, and `close` pops only after each
    free returns so a partial failure retries without a double free.
- `tests/test_unit_qwen4exp_batch_qsa_index.py` (new, 22 tests): the four
  primitives are monkeypatched recorders, and the batch attention owner is real
  (fake runtime) because the ownership contract is defined in terms of its page
  tables. Asserts the member map is the slot's own global physical positions and
  is disjoint across slots; the exact dispatch sequence (pool per slot with work,
  `N` scores, 1 selection) with per-row pointer arithmetic proving row `r` reads
  slot `slot_ids[r]`'s pooled base and writes its own score slice; the selection
  dispatch's `rows`, `score_stride`, `output_stride`, ratio, and budget;
  incremental pooling; row permutations swapping per-row bases; 15 no-dispatch
  rejection cases including a dense row; re-derivation of the published metadata;
  and the rollback contract: immutable single-use token, second live token
  refused, consumed token refused after a rewind plus overwrite, foreign-owner
  token refused, pre-reset token refused with the reset slots named, forward
  movement refused, discard, and a table of invalid tokens each asserted to leave
  every counter and the pending token unchanged.
- `tests/test_gpu_qwen4exp_batch_qsa_index.py` (new, 9 tests / 14 items): four
  slots, 16 positions, block size 8, ratio 2, budget 2, two index heads of four
  dimensions, distinct per-slot key streams, and one independent
  `Qwen4ExpQSAIndexDeviceState` per slot as the strict comparison basis.

- **Exact against the c1 owner.** Pooled keys are bit-identical and the selected
  position sequence is identical, in every case. That is the expected result:
  append, pool, and score are the same primitives with the same per-slot
  arguments, and selection is the same kernel body with a row dimension. The
  asserted gate is exact equality, not a tolerance.
- **The CPU oracle is a second, independent check.** Pooled keys agree to
  3.6e-07 (float32 reduction order in the RMS sum only) and the selected position
  *set* is identical, so the slot addressing is verified arithmetically and not
  only by canaries.
- **Compression boundaries** are covered on both sides: lengths 6/8 end on a
  block edge (`tail = 0`, count `= budget*ratio`) while 7/9 leave a one-token
  tail (`count = budget*ratio + 1`), and the tail tokens are asserted to be
  `arange(blocks*ratio, length)` exactly as the c1 owner produces them.
- **Sparse budget overflow**: 8 and 6 complete blocks against a budget of 2
  return 4 and 5 positions, so the selection is genuinely sparse rather than a
  dense pass with a large budget.
- **Deterministic ties**: with all-zero raw keys, blocks pool/normalize/rotate to
  zero and every eligible score is exactly `0.0`; the selection takes the two
  lowest block indices (positions `[0,1,2,3]`) and the c1 owner and the oracle
  agree. One row in that fixture also had a higher-scoring fifth block, and the
  tie among the zero-score blocks still resolved to the lowest indices.
- **Untouched slots** keep every byte of their raw and pooled slabs and their
  cursors across a selection on other slots.
- **Row permutations** (`[2,0]` then `[0,2]`) move the per-row result with the
  slot, matching each slot's independent owner in both orders.
- **Slot reuse**: after `reset_slot`, a new history on the same slot matches a
  freshly allocated independent owner that only ever saw the new history, so no
  stale key survives the reuse.
- **Rollback is exact and bounded**: a speculative key that completes a block is
  visible in the pooled slab, `rollback` rewinds the counters, and the real
  continuation then matches both the never-speculated twin slot and the
  independent owner, with block 3 holding the real key's pooled value. Three
  further GPU tests show the token is refused, with the raw slab, cursors, and
  pooled counts byte-identical afterwards, when (a) it was already consumed and
  the rewound position was overwritten, (b) the slot was reset and reused for a
  new history — after which the slot still selects exactly like a fresh owner,
  and (c) it is presented to a different owner.

Two hazards were found and fixed while adding the enforcement, both of which the
looser first draft would have shipped: a token's numpy counter arrays were
mutable after issue, so a caller could rewrite its provenance; and the rollback
assigned the cursor slice before validating the pooled slice, so a malformed
token would have been "rejected" after half the rewind was already applied. The
token now carries immutable tuples, and validation completes before any
assignment.

Scores beyond a row's complete-block count are never written and never read (the
kernel bounds both by `blocks = (cursor+1)/ratio`). The slab is left
uninitialised, as the c1 owner leaves its `scores` buffer, so a row reading a
block it did not score shows up as garbage rather than as a plausible zero.

## Missing ABI

Real physical batching of the index path needs three primitives that do not
exist. These are the boundaries, stated as the ABI they would need; nothing in
this unit assumes them, and the per-slot dispatch above is what runs today.

1. `int hipengine_qwen4_exp_qsa_scatter_index_keys_rows_f32(
     const void* source, void* destination, const void* block_tables,
     const void* positions, int64_t rows, int64_t block_table_stride,
     int64_t block_size, int64_t index_dim, hipStream_t stream)`
   — row `r` reads `block_tables[r * block_table_stride ...]` and
   `positions[r]`; today the wrapper takes one table and one position scalar, so
   the append is `N` launches.
2. `int hipengine_qwen4_exp_qsa_pool_norm_rope_rows_f32(
     const void* raw_keys, const void* member_indices, const void* block_starts,
     const void* weight, void* output, const void* output_offsets,
     int64_t blocks, int64_t ratio, int64_t index_dim, int64_t rotary_dim,
     float theta, float eps, hipStream_t stream)`
   — a per-block output offset so several slots' newly complete blocks land in
   their own pooled slabs in one launch; today the output range is contiguous
   from one base, so the pool is one launch per slot with work.
3. `int hipengine_qwen4_exp_qsa_score_rows_indexed_f32(
     const void* queries, const void* pooled_keys, void* scores,
     const void* block_counts, int64_t rows, int64_t pooled_stride,
     int64_t score_stride, int64_t heads, int64_t index_dim,
     hipStream_t stream)`
   — row `r` scores `block_counts[r]` keys starting at
   `pooled_keys[r * pooled_stride]` into `scores[r * score_stride]`. This is the
   essential one: `score_f32` and `score_rows_f32` both share one `pooled_keys`
   across their queries, so no combination of their arguments yields
   independent-request scoring.

With all three, the step becomes 3 launches regardless of `N`. None of the three
is required for correctness today; they are required to stop calling 3N
dispatches "batched".

Integration interface the runner would need (not implemented here, and no claim
that it works):

- One `Qwen4ExpBatchQsaIndexState` per QSA layer, alongside the existing batch
  attention owner for that layer, with the same slot space.
- Per step: `attention.prepare(slot_ids, positions)` as today, then
  `index.prepare(slot_ids)`, `index.append_active(raw_index_keys_ptr)` in the
  same step as the KV write, and `index.select_active(...)` for the rows
  `partition_rows()` reports as sparse. The dense group stays on
  `run_qwen4_exp_batch_dense_qsa_token_mixer` with its `dense_equivalent_limit`.
- The prepared index queries (`[rows, index_heads, index_dim]`, normalized and
  rotated) are the caller's, exactly as in the c1 owner; this module does not
  project them. The buffer must hold `rows` query rows; a shorter buffer is read
  out of bounds, as it would be by the c1 owner.
- Compaction must call `reset_slot` (which advances the slot generation and
  therefore invalidates any pending rollback token) for every slot that changes
  owner; the counters plus the generations are the whole ownership record.
- A speculative step must bracket `begin_rollback` / `rollback`, and a step that
  is committed must `discard_rollback` (or simply never capture again). A
  rewind-then-overwrite sequence cannot reuse its old token by construction.
- Prefill chunks stay on the c1 owner: a chunk's rows are one request's
  consecutive positions, not independent requests, and the batch owner appends
  exactly one key per active row.

Not validated, and not claimed:

- **MTP / speculative decoding.** The rollback transaction exists because a
  speculative step needs it, and the GPU tests show an append-only rollback is
  exact. That is not an MTP integration: a verify step needs several rows per
  request sharing one position space, per-candidate index keys, and a selection
  per candidate, none of which this module expresses, and a token cannot span a
  slot reset. `qwen4_exp_mtp.py` keeps its own `Qwen4ExpQSAIndexDeviceState`.
- **Production numerics.** Evidence is fixture weights on one QSA index layer.
  The calibrated profile gates in `docs/EXECUTION-PROFILES.md` (mean/p95/p99/max
  KL, top-1 by category, isolation, BF16-relative, task) are unrun on a real
  checkpoint.
- **Speed.** No timing was taken, and with 3N + 1 dispatches there is no reason to
  expect a step-level win over N independent c1 owners. The selection launch is
  the only genuinely shared work, and it is one 1024-thread block per row.
- **Capacity.** Per-slot slabs are explicit and additive, matching the batch
  attention owner's disjoint-block model; nothing here shares or compacts slots.
- **Arbitrary snapshots.** Not supported by design. Only one live single-use
  token exists per owner, it cannot cross a slot reset, and it cannot be replayed.
