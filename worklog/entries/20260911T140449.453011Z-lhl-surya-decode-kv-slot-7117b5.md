# Surya GPU decode_step KV off-by-one: stale slot corrupted requests after a longer one

## Summary

`SuryaGpuRunner.decode_step` advanced `self._seq_len` **before** running the
decode stack. `_seq_len` is the next free KV slot: `_attn_layer_decode` reads
`pos = self._seq_len`, scatters the new token into that slot, and attends over
`pos + 1` positions. Incrementing first made the scatter land one slot too high
and made attention read the skipped slot, which this request never wrote.

On a fresh runner the skipped slot holds zeros, so the spurious attention term
has `V = 0` and only inflates the softmax denominator by `exp(-max)` — usually
small enough to leave the argmax alone. After any longer request on the same
runner the slot holds that request's real K/V, and the corruption becomes
visible. Concretely, on one runner:

```
fresh, text-only          : [1247, 1186, 1248, 126, 1979, 97, ...]   correct
after a full-page request : [1247, 1186, 1248,  67, 1979, 63, ...]   wrong
text-only again           : [1247, 1186, 1248,  67, 1979, 63, ...]   stays wrong
```

Moving the increment after `_decode_stack` fixes it; the two sequences then
agree token for token.

This was found by adding text-only coverage, not by a failing existing test:
every GPU test drives the multimodal path, and `test_gpu_repeated_request_isolation`
only checks multimodal -> multimodal.

## Changes

- `hipengine/runtime/surya.py`: in `decode_step`, run `_decode_stack` first and
  advance `_seq_len` afterwards, with a comment naming the hazard. No other
  change; `_seq_len` has exactly two readers (`_attn_layer_decode` and this
  method) and prefill already leaves it at the next free slot.
- `tests/test_surya_gpu.py`: `test_gpu_text_only_matches_oracle` (new) gates the
  text-only path against the torch fp32 oracle's `logits_first` (KL < 1e-4 plus
  argmax) and against the NumPy CPU reference's greedy continuation, then
  performs a full-page multimodal request followed by a second text-only request
  and requires that one to match the CPU reference too.

## Validation

- Reproduction on one runner, `HIPENGINE_HIP_ARCH=gfx1151`, text-only prompt
  (40 tokens) with the 1024x1024 page as the preceding multimodal request:
  pre-fix `A != B` (B and C both `[..., 67, ...]`); post-fix `A == B`.
- RED/GREEN on the new test with the fix reverted and restored:
  - reverted: `AssertionError: text-only decode is not isolated from a preceding
    multimodal request: [1247, 1186, 1248, 67, ...] vs [1247, 1186, 1248, 126, ...]`
    (first divergence at index 3)
  - restored: passes.
- The regression block deliberately uses `page_full.png`, not `page_small.png`.
  With page_small as the preceding request the stale slot's contents are close
  enough to the correct value that the buggy build still passes — the test would
  have been a false negative.
- Text-only prefill vs the torch oracle `logits_first`: CPU KL 9.552e-08
  (max|d| 2.646e-05), GPU KL 9.554e-08 (max|d| 3.839e-05), argmax agreement on
  both.
- `HIPENGINE_HIP_ARCH=gfx1151 python3 -m pytest` on the eight Surya modules
  (model contract, oracle fixtures, text decoder, vision, e2e, public API,
  generation contract, GPU) → 91 passed.
- The multimodal paths still match the torch oracle exactly after the fix:
  `test_gpu_end_to_end_ocr_matches_oracle` (page_small, 64 tokens) and
  `test_gpu_full_page_layout_matches_oracle` (1024x1024, 78 tokens) both pass,
  so the changed KV indexing did not move the reference results.

## Next

- No timing was measured for the fix. It moves one integer increment across a
  call and does not change launch counts, so no measurable effect is expected,
  but that is an argument, not a measurement.
- The pre-fix code was subtly wrong even on a fresh runner (an extra
  `exp(-max)` term in the decode softmax denominator). Any earlier Surya GPU
  quality or speed number that depended on decode-step logits carries that
  offset; the greedy-ID gates above show it did not change the reference
  sequences on the tested pages.
- `scripts/surya_perf_compare.py` calls `runner.decode_step` directly and its
  stored lane comparisons predate this fix; re-run it before quoting those
  numbers again.
