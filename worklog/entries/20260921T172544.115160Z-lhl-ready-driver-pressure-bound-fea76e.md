# Bound /ready under driver pressure and pin its degradation

## Summary

Follow-up to the previous unit on the same readiness item, pursuing the
residual risk recorded there: the MTP-specific pressure case, where engine work
holds the GPU while `/ready` is polled.

**Finding: the two readiness endpoints have very different bounds, and only one
of them is tight.**

- `/health` (`hipengine/server/api.py:7012`) returns a static dict and never
  touches the engine. It is responsive by construction. **Verified** here.
- `/ready` calls `readiness_payload`, which reads the engine through
  `asyncio.to_thread`. The event loop therefore stays responsive, but the
  **request itself** waits for that read.

The read is not a plain getter. It goes

```
_live_loop_snapshot -> llm.live_loop_snapshot -> EngineService.live_loop_snapshot
  -> _control("live_loop_snapshot")
```

and `_control` (`engine_service.py:793`) **enqueues a command onto the sole
driver thread** and waits. `EngineService`'s own docstring states the design:
"A control command waits behind whatever the single driver thread is already
doing, so this budget guards liveness rather than bounding engine work."

So **`/ready`'s worst-case latency is `_command_timeout_seconds`, whose default
is `DEFAULT_COMMAND_TIMEOUT_SECONDS = 300.0` -- five minutes.** No orchestrator
or load balancer treats a five-minute probe response as healthy.

### Why the existing responsiveness test does not cover this

`test_integration_server_api.py::test_busy_snapshot_does_not_block_other_http_requests`
uses a fake engine whose `live_loop_snapshot` blocks on a threading event the
test releases. That fake is called directly on a worker thread: there is no
driver thread and no command budget in the path, so the test proves the **event
loop** stays responsive -- which it does -- and says nothing about how long
`/ready` itself can take. The bound comes from a layer the fake bypasses.

### A timeout degrades `/ready`; it does not make it a 503

`_live_loop_snapshot` and `_engine_service_health` both swallow every exception
and return `None`. So a command timeout on a busy driver costs the readiness
payload its live diagnostics and nothing else. That is the right behaviour: an
orchestrator polling during a long generation must not see the instance flap out
of rotation for a transient busy period, and a genuine service fault is reported
through the service-health path rather than through a timed-out probe. **Verified**
here, including a mutation check.

## Changes

- `tests/test_unit_server_ready_driver_bound.py` (new), 4 cases. Builds a real
  `EngineService` over a fake driver whose control method holds the driver
  thread on an event:
  - the readiness read times out at the budget, and the timeout names the
    budget (`budget_s=0.4`);
  - the same call returns normally when the driver answers in budget;
  - the bound follows the configured budget, so it is a number rather than an
    assumption;
  - `DEFAULT_COMMAND_TIMEOUT_SECONDS == 300.0`, asserted so a change to a
    probe's worst-case latency cannot land silently.

  The driver's hold is an event rather than a bare sleep: `close()` enqueues its
  own command and waits on the same budget, so a driver still sleeping would
  time the shutdown out.

- `tests/test_unit_server_ready_degradation.py` (new), 3 cases. Drives the real
  ASGI app with an engine whose every readiness read raises
  `EngineCommandTimeout`:
  - `/ready` still answers 200 with `ready: true` and no `engine_unavailable`,
    so the timeout degrades rather than 503s;
  - `/health` answers 200 and never calls the engine at all.

## Validation

- `pytest tests/test_unit_server_ready_driver_bound.py
  tests/test_unit_server_ready_degradation.py
  tests/test_unit_server_error_retryability.py
  tests/test_unit_generation_execution_failure_containment.py` -> 49 passed.
- Mutation check on the degradation contract: removing the exception swallow
  from `_live_loop_snapshot` fails only the `/ready` case, while `/health`
  still passes because it never reads the engine. Source restored immediately;
  `git diff` clean afterwards.
- No RED phase: no defect was found. The bound and the degradation are both
  deliberate, and both were undocumented by tests.

## Next

- **The bound itself is the open question, and it is a design question, not a
  test gap.** `/ready` blocking up to five minutes on a busy driver thread is
  deliberate per the `_control` docstring, and it is survivable because the
  timeout degrades rather than 503s. But the v0.6.0 claim that HTTP handling
  "stays responsive while engine work waits on the GPU" holds for the event loop
  and for `/health`, and does not hold for `/ready`'s own latency. If a probe
  needs a tight bound, the lever is a smaller command budget for the readiness
  read specifically, not a change to the shared liveness budget -- worth a
  decision rather than an assumption.
- Not measured live: whether an actual MTP cycle can hold the driver thread long
  enough to matter. The mechanism is shared, so the fake-driver result is strong
  evidence for the shape of the bound, but the live duration is unmeasured, and
  that needs a server (PID 4175913 holds ~96 GiB of GTT).
