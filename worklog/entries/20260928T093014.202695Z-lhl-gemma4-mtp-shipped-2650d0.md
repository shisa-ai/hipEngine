# mtp is reachable from the public llm api at 1.66x and the route is an attribute that only exists when a provider is attached

## Summary

**MTP is shipped.** `LLM.generate_speculative_mtp_detailed()` reaches the Gemma 4
provider, and it is **1.66x** end to end.

```
AR          : 3.38s  28.4 tok/s
speculative : 2.04s  47.1 tok/s
speedup     : 1.66x
```

That closes the gap `20260928T092503` left open, and it does it with a mechanism
that keeps the reviewed invariant intact rather than by editing the test.

## The route, read rather than guessed

`LLM.generate()` is plain autoregressive **by design**. The speculative route is
a separate public method, and reading it found the actual branch:

```python
supports = getattr(generator, "supports_speculative_mtp", None)
if supports is not None and not bool(supports):
    raise NotImplementedError(...)
detailed = getattr(generator, "generate_speculative_mtp_detailed", None)
if not callable(detailed):
    raise NotImplementedError(...)
```

and the wrapper it consults, `SubmitPollTextGenerator.supports_speculative_mtp`,
ends with:

```python
return bool(supports) and callable(getattr(self._inner, "generate_speculative_mtp_detailed", None))
```

**`bool(supports)` is the whole problem.** With no declaration on the inner
generator, `supports` is `None` and that line is `False` however callable the
method is. So the inner **must** declare the attribute truthy for the legacy
route to be selected.

But a declaration is what `tests/test_unit_gemma4_speculative_wiring.py` pins
against, and **the test is right**: the wrapper's first line returns `False`
outright when the attribute is present and falsy, so a declaration that reads
`False` while no provider is attached would make the runner's staged hooks
unreachable. My earlier attempt was exactly that -- a property returning
`self._speculative_provider is not None` -- and it was wrong for a reason I did
not see at the time.

## The mechanism

An attribute that **does not exist** unless a provider is attached:

```python
def __getattr__(self, name: str) -> Any:
    if name == "supports_speculative_mtp":
        if self.__dict__.get("_speculative_provider") is not None:
            return True
    raise AttributeError(name)
```

Verified both ways:

| state | `getattr(g, "supports_speculative_mtp", "<absent>")` | route |
| --- | --- | --- |
| no provider | `'<absent>'` | falls through to the staged check, unchanged |
| provider attached | `True` | legacy route selected |

`vars(Gemma4GGUFGenerator)` still has no `supports_speculative_mtp`, so the pin
holds and **the staged route is exactly as reachable as it was before this
generator grew a provider.** `__getattr__` uses `self.__dict__.get` rather than
`getattr` to avoid recursing through itself.

## What I got wrong last unit, and the pattern

I tested `llm.generate()` -- which never routes speculatively by design -- saw no
telemetry, concluded the property "bought nothing", and reverted a change that
was pointing at the right mechanism. **The lesson is not "the property was
right"; it was wrong.** It is that *a failed test only refutes the hypothesis it
actually exercised*, and I had picked the wrong entry point, so the failure said
nothing about the property. Reading the route first would have shown both the
correct entry point and the correct mechanism in one pass, which is what the
previous entry said to do and what this one did.

## Also settled

* **Bit-exactness.** The verify reads the backbone's own logits at each position,
  so the cycle reproduces plain greedy exactly (measured in
  `20260928T092027`). It can land enabled on the default path with no
  arithmetic-change gate; only the route needed work, and that is now done.
* **The quant key.** `QUANT_AGNOSTIC = "*"` in `speculative/registry.py`, with a
  fallback after an exact-key miss, so the provider does not carry a written list
  of known-good quantizations. The first registration attempt proved the list was
  unworkable on its first run: the resolved quant is `gguf_q4_k_m`, which is not
  in `registered_quants()` at all.
* **The staged-route invariant.** `uv run pytest tests/ -k speculative` is
  **315 passed, 5 skipped, 0 failed**, including the pinning test.

## Next

1. **`llm.generate()` still does not use MTP, and that is now a product question
   rather than a plumbing one.** The speculative route is opt-in through its own
   method, which is how the engine is shaped. Whether plain `generate` should
   auto-select it is a default, and the arithmetic is bit-exact, so nothing
   technical blocks it.
2. **A cheaper verify row is what stands between 1.66x and 3.2x.** The MoE's
   expert traffic is linear in rows, so the gate/up and down projections are the
   lever -- they are 32 percent of decode and run at 75 and 47 GB/s against a
   regime the dense path shows supports 199.
