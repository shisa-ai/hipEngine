# PN4 checkpoint: host-side dispatch analysis; host-vs-GPU bound unresolved

## Summary

Measured the host-side dispatch cost of the Qwen3.6-35B eager decode on the
live ZBook session (gfx1151) to decide whether P3-LAQ1-B (Q8 dual GEMV kernel
optimization) or a host-path mechanism is the right next step.

Per-call host dispatch medians during decode: `launch_gguf_linear` 48.1 us,
`launch_gguf_linear_pair` 55.4 us, `launch_gguf_linear_triple` 70.5 us,
`qwen35_gdn_recurrent_rmsnorm_gate_lowp` 38.7 us, conv 34.6 us, attn_norm
20.7 us. Pure HIP enqueue (pre-resolved, pre-bound ctypes) is ~6 us, so ~40-45
us/call is Python dispatch machinery.

Key correction from the earlier "dispatch-bound" hypothesis: the
`_DISPATCH_RESOLVE_CACHE` actually hits 97% (9 misses / 282 gets per step); an
earlier 80%-miss reading conflated `resolve_gguf_linear_dispatch` calls made by
the pair resolver. Re-resolution is NOT the cost; the per-call overhead is the
cache-key construction + `_LAUNCH_ABI` resolution + allocation lookups.

Host step time ~31 ms/token (device sync after enqueue ~0.04 ms); production
p512/d128 wall ~46 ms/token. rocm-smi reports 0% GPU use on this APU (metric
unavailable), and stage markers are host-side timestamps whose "GPU-exclusive"
walls overlap in GPU time, so the earlier "150 us/layer gdn_attention_core
idle" is not necessarily GPU idle.

**Verdict: host-vs-GPU bound is UNRESOLVED.** The qkv_gate stage itself is
kernel-bound (Q8 dual 67.7 us vs 72 us wall). The decisive experiment is a
complete-wall A/B with a host-speedup (launch-plan memoization) or a
GPU-reduction: if the wall drops, host-bound (memoization is the biggest win);
if flat, GPU-bound (P3-LAQ1-B Q8 kernel is the target). Do not invest in a
large gguf_linear.py refactor before this A/B.
