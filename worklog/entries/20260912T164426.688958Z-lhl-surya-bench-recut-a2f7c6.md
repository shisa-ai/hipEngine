# Surya bench pages re-cut onto fitting canvases; the _fit variant family is gone

## Summary

Four of the seven Surya bench pages drew text past their own canvas, so the text
the suite claimed to measure was not the text in the image: `ja` body lines were
576-663 px wide on a 512 px page (480 px usable), `mixed` Latin lines 503/506 px
against 480, `scan` ~531 px against 476, and `page_long` drew six 224 px blocks
from y=168 so blocks 5 and 6 fell off a 1024 px canvas. Scoring against the
intended text read correct model output as error, which is how the recorded
`line.` -> `literature` "hallucination" arose — the model was completing a
clipped word.

`scripts/surya_bench_pages.py` now draws every text page through
`_draw_text_fit`, which raises instead of clipping, and the four pages are
re-cut onto canvases that hold them (1024x1024 for `ja`/`mixed`/`scan`,
1024x1600 for `long`). `FIT_PAGES`, `write_fit_pages`, `acceptance_page` and the
`--fit` flag are gone; `page_filename` returns `page_<name>.png` for every page,
so the transcription acceptance suite and the benchmark suite read the same
bytes and there is no longer a page that only one of them sees.

The re-cut bytes are exactly the former `page_<name>_fit.png` bytes — sha256
verified for all four — which is why the captured full-page-protocol oracle
needed only its `page` field renamed and none of its ids re-captured.
`oracle_bench.json` (the ad-hoc-prompt fixture) was re-captured with torch fp32
over all seven pages, because the images the ad-hoc prompt sees did change.

The vision grids grew with the canvas (`ja`/`mixed`/`scan` 32x32 -> 64x64,
`long` 64x64 -> 100x64), so the re-cut suite's absolute rates are not comparable
with the superseded 2026-09-11 baseline; the retained comparison is against the
torch fp32 lane measured in the same session.

## Validation

Re-run on the Ryzen AI Max+ Pro 395 (Radeon 8060S, gfx1151), fp32, one process
per lane:

```
HIPENGINE_HIP_ARCH=gfx1151 python3 scripts/surya_perf_compare.py --split all --runs 3 --lanes hipengine_gpu --out /tmp/surya_lane_hip.json
HIPENGINE_HIP_ARCH=gfx1151 python3 scripts/surya_perf_compare.py --split all --runs 3 --lanes torch_cuda --out /tmp/surya_lane_torch.json
python3 scripts/surya_perf_compare.py --merge /tmp/surya_lane_hip.json /tmp/surya_lane_torch.json --out benchmarks/results/2026-09-13-gfx1151-surya-suite-recut.json
```

All 24 rows PASS with empty `gate_failures`. Decode 54.6-57.0 tok/s vs
24.6-28.1, median 2.19x (2.03x-2.23x on every page); end-to-end 0.20-8.85 s vs
0.29-14.38 s. `ja` 2.71 -> 5.75 s, `long` 5.67 -> 8.85 s and `mixed` 5.13 ->
6.76 s versus the clipped pages, because their vision grids are 4x bigger;
decode is unchanged at ~55 tok/s.

Two findings the re-run produced, both recorded rather than hidden:

1. **The scan page cannot carry an exact-id gate under the ad-hoc prompt.** On
   the re-cut page both lanes free-run into the same rigid 10-box layout
   template — identical labels, identical `count`, fixed line pitch — and only
   the bbox digits differ. Neither lane's digits read the page: the lines are
   drawn 470-554 of 1000 wide, torch reports 474-566, hipEngine a flat 564. The
   case now declares `parity="structure"`, gating box count, label sequence,
   reading order and per-box `count`, and reports the drift as `bbox_max_delta`
   (90 of 1000). This is not a HIP defect and not a regression: it reproduces at
   the pre-KV-spans commit `b1e241d57` with the same first divergence (id 7 of
   158, same lengths), and under the checkpoint's real prompt on the same image
   both lanes read the page and agree within 2 of 1000 with identical labels and
   text. The other eleven cases keep the exact-id gate.

2. **Both lanes in one process corrupt the tail of the hipEngine lane on this
   suite (task #80).** The same 12 cases with `--lanes hipengine_gpu` alone pass
   every gate; with `--lanes hipengine_gpu,torch_cuda` the last three hipEngine
   rows (`full`, `columns`, `list`) come back degenerate from the first
   generated token. Every stage time is unchanged — `full` e2e 3.663 s against
   3.344 s in isolation, and only because it ran 96 tokens instead of 78;
   `init_s` identical to 0.04 s — so the device was healthy and fast and the
   logits were wrong. `--merge` exists so the retained comparison does not ride
   on that state. Narrowing the trigger: `long,full,columns,list` combined
   reproduces clean, so it needs a longer preceding prefix; a combined run is
   reproducible with the single command in `docs/MODEL-SURYA.md`.
