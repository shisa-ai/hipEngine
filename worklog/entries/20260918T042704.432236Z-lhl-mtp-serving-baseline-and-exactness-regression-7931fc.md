# Shipping MTP is slower than AR on natural ShareGPT serving, and its greedy output diverges from AR at 16+ tokens

## Summary

A matched serving baseline on the shipping configuration (gfx1151, Qwen3.8-27B
`Q4_K_M`, production profile, BF16 KV, natural-length ShareGPT requests, greedy)
finds **no MTP speedup**: the automatic route is 11-20% *slower* than true AR on
completed-request throughput and inter-token latency at c=1, c=2 and c=4, and it
adds 1.5-1.8x TTFT. The same configuration's greedy output **diverges from AR
after 5-7 tokens** and the MTP arm's text is incoherent where AR's is correct
("What is 17 times 3?" -> AR "17 x 3 = 51"; MTP "about 4 being multiplied by some
other number of their data"). The project's own MTP API semantics gate fails on
this tree for both lifecycles, but its 8-token exactness cases pass, so it does
not reach the divergence. A worktree bisect isolates the divergence to one
commit: `f607e3184` (`085bdd86b~1`) is exact at every budget, `085bdd86b` is not,
and the deferral fix in `253beefe3` is bisected out.

BF16 KV, `--speculative-mtp-serving auto --speculative-candidate-budget 3`,
greedy, thinking enabled, 32-128 output tokens, natural ShareGPT prompt lengths.

The control lane's per-arm numbers, head against the exact tree:

| --- | ---: | ---: | ---: |

Two AR runs and two MTP runs are each bit-identical (`32/32` shared tokens), so
this is a systematic path difference, not nondeterminism. The regression is
exactly `085bdd86b perf: stage long-context verifier rows on per-row exact
attention leaves`: `f607e3184` (`085bdd86b~1`) is exact at 8/16/32 and the next
commit is not, in the same worktree with the same server flags. That commit
replaced the dense staged-verifier gate
`not _use_gguf_full_attention_split_decode(attention_context_limit)` with
`_staged_full_attention_rows_ready(...)`. For a short prompt under
`--max-context-tokens 8192` the old condition declined the staged route (8192 is
above the 1024 split threshold) and the new one accepts it, so short-context
dense verifier rows moved from the row-wise strict route to the staged batched
route that the same commit's own comment records as diverging from scalar AR in
BF16. The commit's retained benchmark is a long-context verifier chain, so its
own evidence could not see the short-context change.

Gate: `scripts/gguf_mtp_api_gate.py --model .../Qwen3.8-27B-Q4_K_M.gguf`
returns `passed=False` for both the eager and lazy-restart lifecycles at
`253beefe3`, with `completion_single` and `chat_single` reporting
`ids_exact: true` at 8 tokens.

Control: the same six natural ShareGPT prompts, same server flags, same harness,
on the last tree where the control prompt was exact (`f607e3184`) decode **2194
tokens in 93.0 s (23.60 tok/s)** against true AR's **186.1 s (11.79 tok/s)**. At
the head the same automatic arm needs **234.2 s (9.37 tok/s)** and true AR is
unchanged (186.7 s, 11.75 tok/s). The speculative win on this workload is 2.00x,
and the head's -20% is the regression, not a property of speculative decoding.

That control tree is **not exact in general**, which the harness's per-run
identity comparison found: sequential, c=1, no repeats and no prefix reuse, its
two arms are byte-identical on **5 of 7 natural prompts** and diverge at token
**47** and token **155** on the other two, while the head diverges on 5 of 6
prompts after 5-7 tokens. The trees differ in degree, not in kind. The early
universal divergence is what makes the head's text incoherent; the late
prompt-dependent one is the shape the production numerical envelope exists to
bound, and it needs the calibrated KL/top-1 evaluation before either tree's MTP
output is called exact.

## Next

- Fix the verifier route in `085bdd86b`: restore the row-wise strict route for
dense verifier rows below the split threshold, or prove the staged route exact
there, and re-run this ladder on the fix.
- Re-measure the matched c=1/c=4 baseline on the repaired tree. The control
confirms the same defect causes the low acceptance (0.10-0.24) and the slowdown:
a verifier that does not reproduce the target's own path also rejects the draft's
proposals.
- Classify the control tree's residual divergence (2 of 7 prompts at tokens 47 and
  155, sequential, no prefix reuse) against the production numerical envelope: KL
  and top-1 by category against the strict teacher, not byte identity. Until then
  the 2.00x control rate is a rate, not an exactness claim.
- Extend the API semantics gate past 8 tokens (16/32) so a divergence inside the
  first verify cycles cannot pass again.
- Until the verifier is exact, do not promote any MTP serving default: the
  automatic route is slower *and* changes generated content on ordinary prompts.
- Re-run the matched baseline after the fix; the acceptance/quality gates in
  `docs/EXECUTION-PROFILES.md` need a serving-traffic task gate, not only the
  mtp-bench prompt classes.
