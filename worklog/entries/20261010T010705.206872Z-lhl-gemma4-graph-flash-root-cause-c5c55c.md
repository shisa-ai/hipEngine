# Flash decode is frozen-extent-unsafe; split and class replay bit-exact

## Summary

Iteration 3 of the decode run chased extending the whole-step decode graph past
the 1024-key split-route guard. Root cause of the guard's measured ~10-26
percent replay divergence is now precisely localized; no code change landed
(this entry is the handoff for the implementation unit).

## Root cause

- The flash-decoding phase kernel partitions the key range as
  `j_begin = keys*slice/slices` with `slices = flash_slices(keys)` — both
  functions of the LIVE key count on the launched path. A graph capture bakes
  the bucket-frozen extent instead, so the captured partitioning differs from
  what the launched path would use at each replay position. The attention is
  mathematically equal (masked lanes contribute zero) but NOT bit-equal:
  different partial sums round differently, and the ~1e-7 divergence
  amplifies through the remaining layers into the observed 5-26 percent
  logit deltas. Evidence: layer probe at a 1023-token prompt (`/tmp/layer_probe.py`,
  width-1 capture so frozen geometry is nearly live) — layers 0-5 attention
  outputs bit-equal, layer 6 (first sliding layer after the first global
  layer) is the first diverging output with a bit-equal query input; the
  divergence then propagates to every later layer.
- The split (two-phase dimension partition) and class/global-logits routes are
  partition-order-invariant under frozen supersets and replay bit-exact
  (route-forced A/B at a 1023-token prompt, 16 steps: worst rel 0.0 for both,
  vs 2.63e-01 for flash).
- The flash kernels themselves ARE graph-safe: isolated capture+replay of both
  geometries (hd256 ratio 2, hd512 ratio 8), including two sequential
  launches sharing one workspace, is bit-identical (`/tmp/flash_iso2.py`).
  It is the frozen-extent dependence, not the graph mechanics.
- Probe notes: `_Bucket.for_position` binds `BUCKET_WIDTH` at def time, so a
  module-attribute monkeypatch does not change bucketing; and any D2D save
  memcpy inside capture that is not a KV append trips `_identify_appends`.

## Measurements (zbook / Radeon 8060S, gfx1151)

Prize for extending capture coverage (wall A/B, guard bypassed, 64-token
decode, launched arm vs graph arm):

| prompt tokens | launched | graph | gain |
| ---: | ---: | ---: | ---: |
| 1024 | 33.12 | 34.66 | +4.7% |
| 2048 | 33.74 | 37.73 | +11.8% |
| 4096 | 34.10 | 36.41 | +6.8% |
| 8192 | 36.15 | 35.88 | -0.8% (device-bound) |

Route speed, launched, flash vs split (forced via `flash_admits=False`):

| prompt tokens | flash | split | split vs flash |
| ---: | ---: | ---: | ---: |
| 1024 | 33.18 | 34.41 | +3.7% |
| 2048 | 32.87 | 33.91 | +3.1% |
| 4096 | 34.05 | 30.91 | -9.2% |

So split is both the graph-safe AND the faster route at 1024-2048.

## Next unit (design)

1. **Route crossover**: decode attention routes to the split below the
   measured crossover (~2560-3072 keys; pin by measurement) and flash above.
   Sliding layers sit at exactly 1024 keys past the window start, so they take
   split permanently. This is an arithmetic change on the selected decode
   path: run the full `docs/EXECUTION-PROFILES.md` section 2.11 packet
   (strict-chain KL + top-1 flips + batch invariance) before default
   selection.
2. **Guard extension**: `_SPLIT_ROUTE_MIN_KEYS` becomes the crossover; buckets
   below it capture (split replays bit-exact), buckets above keep the launched
   fallback. Graph-vs-launched stays bit-identical because both arms route the
   same per depth.
3. Expected row gains: 1024 and 2048 decode gain the split route (+3%) AND the
   graph replay (+8-12%); 4096+ unchanged this unit.
4. The device-resolved flash fix (kernel reads live keys/delta from a staged
   device slot, derives `flash_slices(live)` per block so replay partitions
   exactly as launched) stays the clearing route for 4096+ capture — recorded
   in `docs/REFACTOR.md`.
