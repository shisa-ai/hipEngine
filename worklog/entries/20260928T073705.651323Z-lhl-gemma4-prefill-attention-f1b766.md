# the 15872 ceiling is confirmed end to end on the real launch path and the error message names the tiled fix

## Summary

`20260928T073623` derived the 15872 context ceiling from the launcher's shared-memory
arithmetic and cross-checked it against an earlier independent derivation. Both were
arithmetic. This exercises the real launch path at a length above the ceiling and confirms
it there.

## The end-to-end confirmation

```
scripts/gemma4_attention_prefill_bench.py --tokens 16000

NotImplementedError: Gemma 4 gfx1100 attention requires 66048 bytes of shared memory
for head_dim=256, keys=16000; this kernel supports at most 65536 bytes and needs tiled
attention for this context
```

The arithmetic matches the derivation exactly:

```
(head_dim + keys + threads) * 4 = (256 + 16000 + 256) * 4 = 66048
ceiling: (512 + keys) * 4 <= 65536  ->  keys <= 15872
```

**The ceiling is enforced on the path a caller actually takes**, not only in a helper the
launch path might bypass.

## The error message already names the fix

> ... and needs **tiled attention** for this context

The module's own docstring says the same: *"This implementation stores one logit per live
key in LDS. Larger contexts need a tiled attention implementation, not a larger prefill
scratch block."*

**So the intended fix is already known to the codebase, and `20260928T073623`'s plan -- size
`logits_s` by tile instead of by `keys` -- is the fix the code says it needs.** That is an
independent confirmation of the plan from the code's own stated intent, which is a stronger
signal than the plan looking reasonable to me.

## The boundary was already tested

`tests/test_unit_gemma4_attention_context_ceiling.py` computes the ceiling **by bisection**
rather than hard-coding it, then asserts the arithmetic on both sides:

```python
ceiling = _largest_accepted_capacity(head_dim)
assert (head_dim + ceiling + threads) * 4 <= 64 * 1024
assert (head_dim + ceiling + 1 + threads) * 4 > 64 * 1024
```

and pins both sides for both head widths: **15872 / 15873 at `head_dim=256`** and
**15616 / 15617 at `head_dim=512`**. The 512 case is the 15616 figure found separately
earlier, so all three appearances of these numbers now agree.

**What this iteration adds is that the guard the test pins is the guard the launch path
hits** -- the test asserts through the Python entry point, and the bench confirms that is
the same check a real call runs into.
