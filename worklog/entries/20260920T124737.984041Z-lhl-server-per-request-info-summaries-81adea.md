# server per-request info summaries

## Summary

`hipengine serve --info` (or `HIPENGINE_INFO=1`) now logs one `REQUEST_INFO` line
per completed generation request, reporting tokens in/out, prefill time and rate,
server-observed time to first token and decode rate, wall time, the request's
persistent KV allocation, and the shared KV pool state. Before this, the server
only logged request-level failures (`REQUEST_FAILED`); per-request token counts
and phase rates existed only inside opt-in response metadata
(`stream_options.include_hipengine`) or in the aggregate `/metrics` counters.

## Changes

- `hipengine/server/api.py`: added `ServerConfig.info`, `_log_request_info`,
  `_info_number`, `_telemetry_kv_request_bytes`, `_stream_timing_enabled`,
  `_generation_output_timing`, `_generation_output_kv_request_bytes`, and
  `_stream_timing_summary`. Summary logging is wired to the four existing
  `record_success` sites: blocking `generate()`, `stream_completion_one`,
  `stream_chat_completion_many`, and `stream_chat_completion`.
- `hipengine/server/api.py`: `_StreamTimingTracker` is now created when either the
  client asked for stream metadata or `--info` is on, and `_attach_stream_hipengine`
  feeds that tracker even when the `hipengine` metadata block itself stays opt-in.
  This keeps `--info` free of client cooperation: a plain
  `stream_options: {"include_usage": true}` request still reports ttft and decode
  rate. The default path (no flag, no metadata request) is unchanged.
- `hipengine/server/__main__.py`: `--info/--no-info` flag (env `HIPENGINE_INFO`),
  passed through to `ServerConfig`.
- `docs/API.md` and `docs/ENVS.md`: documented the flag, the line format, and the
  fact that `kv_request_alloc_mib` is a reservation, not the bytes a prompt touched.
- `tests/test_integration_server_api.py`:
  `test_info_mode_logs_one_request_summary_per_completed_request` asserts exactly
  one summary line per completed request, that its token counts match the response
  `usage`, and that no line is emitted with the flag off. The existing
  CLI/env-defaults test now also covers `--info` / `HIPENGINE_INFO`.

Field semantics worth keeping straight:

- Blocking requests have no first-token timestamp, so their `decode_ms` is derived
  from engine phase accounting (`request_total_ms - prefill_ms`). Streamed requests
  use the server's observed first-token time. Both were measured on the same
  workload below and agree within 0.2%.
- `kv_request_alloc_mib` comes from the request's KV layout
  `persistent_total_bytes` (`hipengine/runtime/qwen35_gguf_runner.py`), i.e. the
  space reserved for the request's own context (`request_pages * 256` tokens), not
  the bytes its prompt touched. An 8k-token prompt reserving a 262k-token context
  reports 2,560 MiB.
- Phases the backend does not report are omitted rather than logged as zero.

```
timeout 600 python3 -m pytest tests/test_integration_server_api.py \
  -k "info_mode or metrics_prefix_cache" -q

```

RED note: the new test could not be written RED-first, because the flag, the
config field, and the call sites all had to exist before the test could construct
`ServerConfig(info=True)`; on the pre-change tree
(`git show HEAD:hipengine/server/api.py | grep -c "info: bool"` → 0) the test fails
at construction with `TypeError: unexpected keyword argument 'info'`. The negative
half of the test does fail against an implementation that logs unconditionally.

Live, single host, AMD Radeon Pro W7900-class gfx1151 host serving
`Qwen3.8-27B-Q4_K_M.gguf` (`kv_storage=int8_per_token_head`), server started as:

```
hipengine serve --model /models/gguf/Qwen3.8-27B-Q4_K_M.gguf \
  --served-model-name qwen3.8-27b --host 127.0.0.1 --port 8000 --info --metrics prometheus
```

Same prompt, same `max_tokens=64`, `enable_thinking=false`, streaming request sent
*without* `include_hipengine`. Two independent runs of the pair:

The blocking row's derived decode rate (10.06 and 10.02 tok/s) matches the
streaming row's observed rate (10.04 and 9.95 tok/s) for the same 51 tokens,
which is the cross-check that the derived blocking formula is sound. Stream
`usage` reported `prompt_tokens=49 completion_tokens=51` in both cases, and the
SSE body contained no `hipengine` key, confirming the summary needs no client
metadata request.

## Next

- `--info` reports the request's own KV reservation and the pool total; it does not
  split live-versus-reserved pool bytes. If that distinction matters for capacity
  questions, the pool payload already carries the page counters to derive it.
- Prefix-cache hit accounting (`cached_tokens`) is not in the summary line; a
  radix-cache deployment would want that added next to `tokens_in`.
