# Review capacity-preserving DMS speed recovery

## Summary

The requested push completed first: `origin/main` advanced from `c8bbf0484` to `8a6f4662927e0c98b8e1b5ec06c000a06d00f283`. Review and an unchanged-runtime attribution request identify capacity-preserving opportunities: eliminate repeated whole-store speculative snapshots for decode, then eliminate the second full trunk execution for exact-budget prefill. This needs layer-local collector finalization and removal of the current capture/pack mutual exclusion, not altered prompt attention, packing arithmetic or retention. At `hipengine/generation/qwen35_gguf.py:2380-2406`, capacity is approximately `F + max(B+C, L*C+S)`, not `F+B+L*C`: B is bulk/hidden/oracle storage, C one compact layer, L the layer count, S decode split scratch, and F other live allocations. The earlier full-depth failure was exactly that overlap. The measured 16K staging/restore time is too small to prioritize over trunk replay. Later asynchronous staging may overlap subsequent trunk work only if the previous compact destination is retired before allocating the next one.
- Kernel follow-ups: replace append's first prefix-rank scan with integer counting and bypass the second scan when nothing expires (`dms_compact_int8.hip:96-209`); reuse split exponential factors without changing reduction order (`dms_compact.hip:953-1011`). - Grouped multi-row compact attention is future work, not the current bottleneck: `hipengine/generation/qwen35_gguf_mtp2.py:300-301` selects serial target verification for DMS, so current calls use the grouped singleton producer. Extending grouped reuse across rows requires native transactional integration as well as the primitive. Changing reduction order requires the production numerical gate.
