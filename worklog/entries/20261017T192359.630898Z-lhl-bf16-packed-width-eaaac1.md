# Restore the declared BF16 packed decode width

## Summary

A BF16 KV resident session reported `packed_decode_max_rows = 1`, so every AR
decode group wider than one row took the serial c1 path with
`fallback_reason: packed_decode_width_unqualified`. `8a5ff70d6` (2026-09-22,
"cap the packed decode width on a hybrid INT8 layer layout") moved the
assignment out of the INT8 route-resolution branch to after the layer layout is
known, which made it run for BF16 sessions too. For BF16 the retained INT8 leaf
is never bound, so the new helper returned its INT8 no-leaf refusal width and
capped the packed AR decode of every BF16 server at one row.

The cap belongs to the INT8 stack only: only a direct INT8 layout can mix the
retained INT8 leaf and the standard batch leaf in one packed batch. A BF16 stack
takes the standard leaf on every full-attention layer, so one packed batch
describes the whole group. The policy now takes the session's KV storage dtype
and returns the declared standard width for any non-INT8 stack. Both INT8 caps
are unchanged: no retained leaf, and a hybrid INT8/BF16 layer layout, still
return one row, and a uniform INT8 layout still returns the declared direct
width.

Recorded evidence of the regression, from this repository's own artifacts:
`benchmarks/results/2026-09-24-gfx1151-qwen38-default-kv-mtp-vs-ar-c1c4-automatic.json`
reports `fallback_reasons: {"packed_decode_width_unqualified": 92}`,
`serial_decode_fallback_steps: 92`, `native_packed_decode_steps: 0`, and
`physical_width_decode_steps: {"1": 255, "2": 0, ...}` with a
`kv_attention_source: "bf16"` execution manifest at `physical_execution_width: 1`.
The uniform INT8 run from the same day
(`...int8kv-declared-fp32-mtp-vs-ar-c1c4-automatic.json`) has no such fallback.

## Changes

- `hipengine/runtime/qwen35_gguf_runner.py`
  - Added `_GGUF_STANDARD_PACKED_DECODE_ROWS = 8`, the declared standard width
    (the widest advertised shared-slot AR physical width). The session dataclass
    field default and the constructor initializer now use it instead of a
    separate literal `8`.
  - `_gguf_packed_decode_max_rows` takes `kv_storage_dtype` and returns the
    standard width for any storage dtype other than `int8_per_token_head`. The
    INT8 branch is untouched: no callable retained leaf returns 1, any
    BF16-mirror full-attention layer returns 1, otherwise the declared
    `direct_rows`.
  - The constructor passes `kv_storage_dtype=self.kv_storage_dtype` and the
    call-site comment now states that a BF16 stack keeps the declared standard
    width. No math, kernel, dispatch, flag, or admission change.
- `tests/test_unit_gguf_packed_decode_width.py` (new): the BF16 standard-width
  case through the constructor's real policy inputs, a BF16 case that hands the
  policy INT8-only inputs, and the three preserved INT8 caps.
- `tests/test_unit_qwen35_gguf_int8_kv_policy.py`: the four existing width tests
  gained the explicit `kv_storage_dtype=DType.INT8_PER_TOKEN_HEAD` keyword.
  Assertions are unchanged.
- `tests/test_live_generation_qwen35_gguf_sampling.py`: added
  `test_gguf_resident_bf16_c4_uses_the_declared_standard_packed_width`, which
  derives the session width from the real policy and asserts a c4 BF16 group
  takes `_step_native_chunk` at `physical_rows=4` with no serial fallback.
