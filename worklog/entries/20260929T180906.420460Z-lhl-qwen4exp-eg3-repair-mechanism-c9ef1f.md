# EG-3 mechanism measured: registers, occupancy and instruction count all falsified

## Summary

**EG-3 stays closed, now with the mechanism measured instead of hypothesized.**
The row was parked until "a measured mechanism (registers, instruction count,
occupancy) reopens it". Measured: **all three are falsified.**

The decisive evidence is not a new experiment - it is the already-measured
row-bitmap variant, which turns out to be a complete natural experiment.

## The census

New `scripts/qwen4exp_repair_register_census.py` builds the kernel family with
`--save-temps` and reads `.amdhsa_next_free_vgpr` / `next_free_sgpr` plus the
device disassembly. Occupancy uses the gfx11 register file (65536 VGPR/CU,
granule 8, 32 waves/CU ceiling):

| kernel | VGPR | SGPR | static ins | waves/CU | occupancy |
|---|---:|---:|---:|---:|---:|
| `grouped_pair2` (the body the repair reproduces) | 87 | 94 | 459 | 23 | 71.9% |
| **`sparse_exact_repair` (current)** | 57 | 63 | 336 | 32 | **100.0%** |
| `row_bitmap_repair` (the rejected alternative) | 49 | 43 | **238** | 32 | **100.0%** |

## Why all three mechanisms are falsified

**Registers.** 57 VGPRs. Both 57 and the bitmap's 49 land in the same 64-VGPR
granule, giving 32 waves/CU = **100% occupancy, the architectural ceiling**.
`__launch_bounds__(128, 2)` asks for only 25%. The repair already has *more*
occupancy than the kernel it duplicates (71.9%). No register-driven gain exists.

**Occupancy.** At the ceiling. Unimprovable by any means.

**Instruction count.** The natural experiment. The bitmap variant has **29% fewer
static instructions (238 vs 336) at the same 100% occupancy** and moves **3.3x
fewer bytes** - and it measured **22% slower** (3.5054 vs 2.8685 ms). Fewer
instructions at equal occupancy produced a slower kernel.

## It also kills the candidate I was about to build

I measured the repair's instruction profile and found 29% scalar ALU, dominated by
a **per-slot 64-bit division** plus a **per-slot binary search over expert starts**.
I built a synthetic probe (`prologue_probe.hip`, kept for reproducibility): the
per-slot prologue is **136 instructions**, and a bit-exact magic-reciprocal
division plus a cached expert search is **70** - a 48.5% prologue reduction with
`s_delay_alu` stalls falling 16 -> 4.

Then I read the bitmap kernel's source and found it *already implements that
exact optimization*. Its own comment:

```
// One expert lookup per row instead of one per element.
```

One expert lookup per row, fewer bytes, fewer instructions, same occupancy - and
22% slower. So the whole "reduce per-slot scalar work" class is closed **by
measurement, not argument**, and I did not build the candidate.

I recorded the 136 -> 70 number in the packet **explicitly labelled as not a
projected win**, so the next person does not re-derive it and mistake it for one.

## The actual mechanism

The bitmap's per-row decomposition stages a whole activation row through shared
memory behind a barrier (`x_s[i] = ...` then `__syncthreads()`), adding a
serialization point per row. The repair is limited by the **latency of its
dependent memory chain**. That is consistent with every prior observation in the
row: grid size has no effect (17920 -> 262144 blocks: 3.05 -> 3.18 ms), 3.3x fewer
bytes is slower, and L2-residency gains only 13.8%.

## Validation

- Census reproduced the kernel family's register counts and instruction counts
  from two independent artifacts of the same compile (the `.s` directives and the
  device-object disassembly), and they agree.
- Occupancy arithmetic cross-checked against the whole family: 87 VGPR -> 23
  waves/CU (71.9%), 128 VGPR -> 16 waves (50%), 216 VGPR -> 9 waves - the model is
  consistent across a 4x register range, not fitted to one kernel.
- Ledger IDs unchanged (70).
- Honest scope: the census is **static** (register limit only, no LDS/scratch), one
  profile, one arch. The 22% bitmap figure is the existing `20260917` packet, not
  re-measured here; this packet adds the register/instruction context that
  explains it.
