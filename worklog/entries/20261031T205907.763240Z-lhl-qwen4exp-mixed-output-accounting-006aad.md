# qwen4_exp mixed serving rows publish shared output accounting

## Summary

`Qwen4ExpServingMixed` now records each mixed MTP row's committed output through
the shared speculative accounting helper and publishes the block as
`telemetry.diagnostics.specdec2_mtp2` from `_mixed_telemetry`. That is the
telemetry `reclaim` publishes for a mixed row, so a shared-target MTP response
reports the same MTP-versus-AR split as the resident routes and the
request-owned Qwen4Exp provider route.

Ordinary batch peers that share the same target pass publish no split at all:
they carry no speculative intent, and `speculative_output_accounting` returns
`None` for them because the module never sets their requested budget.

All legacy provider counters in `_mixed_telemetry` (`cycle_count`,
`cycles_count`, `candidate_budget`, `proposed_draft_tokens`,
`accepted_draft_tokens`, `physical_*`) are unchanged and still published beside
the new block. The block is authoritative: it describes the tokens the response
actually delivers, so a cancelled request whose output `reclaim` rewrote to the
scheduler-committed prefix never falls back to the legacy cycle counters, which
would attribute tokens the caller never received.

## Changes

`hipengine/generation/qwen4_exp_serving_mixed.py`

- `_mixed_output_accounting(row)` (module level, not a method: the existing
  regression tests call `_mixed_telemetry` unbound with a dummy `self`):
  - returns `None` for a row without `mtp_budget`. That is the depth
    `register_speculative_request` stored, already clamped to the provider's
    budget, and the generic provider route rejects a request that asked for a
    different depth, so requested and effective depth are the same number.
  - replays the row's committed cycles onto a scratch record and cuts them at
    `len(row.generated_ids)`, then returns `speculative_output_accounting` of
    that record. The cut is a prefix: committed cycles are contiguous and in
    order, so the delivered ones are a prefix of the ledger and at most one is
    partial. A partial cycle keeps `min(accepted, delivered)` accepted drafts
    and reports the depth it selected; the token after the accepted drafts is
    the target's own correction or bonus, so the drafts inside the prefix are
    exactly `min(accepted, delivered)`. Spans are recorded during the replay, so
    a span that straddles the trim is cut and a later one is dropped, and the
    K0 reason counts only cover delivered K0 cycles.
  - a row that counted cycles without a commit ledger publishes no block. No
    production route records speculative accounting on a serving row except
    this module (the request-owned `qwen4_exp_mtp` provider keeps its own
    `SimpleNamespace` record and publishes its own block), so the shape is
    unreachable; it is handled by deferring to the legacy counters rather than
    publishing a zero-cycle block that would claim the delivered output was
    entirely autoregressive.
- `_execute_mixed_cycle` appends one `_MixedCommit(position, tokens, accepted,
  depth, reason)` per committed mixed row, in the post-commit loop where the
  tokens are appended: `position` is the pre-append `len(generated_ids)`,
  `tokens` is the accepted drafts plus the target's own correction or bonus
  token (already cut at the stop and horizon checks inside
  `consume_proposal_rows`), `depth` is `len(proposal.candidates)` (the selected
  depth, not the consumed prefix), and `accepted` is `acceptance.accepted`.
  Recording the cycle instead of attributing it immediately is what makes the
  delivered prefix computable: `reclaim` runs after the pass.
- `_mixed_commits(row)` owns the ledger. It is created on first use as a row
  attribute rather than a declared field, because the serving row's dataclass
  lives in `qwen4_exp_gguf` and nothing outside this module reads it. The
  helper's own counters cannot serve as the ledger: they aggregate a row that
  can later be trimmed, and the recorded spans are a diagnostic switch.
- `plan_reason` comes from `plan.reasons` when the plan is a real
  `SpecRequestPlan`. The plan `_mixed_k0_decode` fabricates has no reasons, and
  its decision is exactly "decode these rows autoregressively", so
  `SpecPlanReason.POLICY_SELECTED_AR` is recorded for it. A K0 pass is a
  depth-zero cycle: its token is `ar_output_tokens_in_cycles`, not MTP output.
- `_mixed_telemetry` builds its diagnostics dict first and adds `specdec2_mtp2`
  only when the helper returns a block, mirroring
  `qwen35_gguf._request_diagnostics`.

Untested here: no GPU and no loaded model, so the device pass
(`Qwen4ExpMixedTargetPass.verify/commit`, the batch runner's slot cursors) ran
only through the CPU fakes, and the trim is applied the way `reclaim` applies it
(`generated_ids[:] = committed_prefix`) rather than by cancelling a live
request.

One boundary is outside this module. A trimmed row's *stream* keeps the chunk
it already sent: `_published_token` builds the terminal chunk from the row's
state at publication time, before any later cancel/reclaim trims the output, so
a client that received a finished chunk and then saw a trimmed reclaimed output
would see the two disagree. Streaming cannot retract a chunk, and the blocking
reclaimed output is authoritative. The mixed row's terminal chunk now carries
`_mixed_telemetry` (repaired in `20834a542`, "fix: preserve mixed telemetry on
terminal single-token streams", using the same `mixed_mtp or mixed_widths`
selection `reclaim` uses), so it publishes the split as it stood when the row
finished.
