# Unit 1 of the prefix checkpoint: a portable provider blob with a pinned layout

## Summary

Task #21, first implementation unit. The design entry (aa79f0b4e) established
that a prefix-cache hit needs a snapshot of the provider's own state that
outlives the request, and that the provider's KV is private -- so the checkpoint
is a second copy of the prefix's KV. This unit implements that snapshot and
restore on the executor, with the layout pinned by tests.

`Qwen35GGUFNextNPrefixCheckpoint` is deliberately a distinct type from
`Qwen35GGUFNextNRequestCheckpoint`: the request-local one is bound to a provider
slot and carries no KV, which is exactly why it cannot serve a prefix hit, and
keeping them distinct is what stops the slot-bound one being stored in a prefix
table. The blob carries `prefix_len`, `hidden_size`, per-layer
`key_buffers`/`value_buffers` (truncated to the prefix, `None` for layers without
full attention), `state_backups` (the mutable Conv/GDN content in the same
layer-major order `capture_request_checkpoint` uses), `boundary_hidden`, and the
cursor.

Three executor methods:

- `snapshot_prefix_state(request_id, *, prefix_len, boundary_hidden=None)`.
  Requires the cursor to be exactly at `prefix_len`, because the recurrent state
  is *current* state rather than history: a snapshot taken later would describe a
  later position. This is what makes the priming walk the capture point -- the
  walk visits every position in order, so the caller snapshots on the iteration
  that brings the cursor to the block-aligned boundary.
- `restore_prefix_state(checkpoint, request_id)`. Crosses requests on purpose:
  the blob is content, not slot ownership, so it lands in whatever slot the new
  request owns, with the destination's own live state buffers receiving the
  backups by position. The target-side half (publishing the boundary hidden row
  as the row that produced the last prefix token) stays with the caller, because
  that is target state.
- `release_prefix_state(checkpoint)`. Idempotent, and frees the KV copies, the
  state backups, and the hidden row.

## Validation

`tests/test_unit_mtp_nextn_prefix_checkpoint.py` pins the parts that are cheap to
get wrong and expensive to debug live:

- the KV copy is `prefix_len` rows at the slot stride of the packed cache
  (`slot_nbytes = nbytes / physical_slots`, `row_nbytes = slot_nbytes /
  max_positions`) -- not the whole provider window;
- the copy set is per *cache*, not per layer: four state backups, one key, one
  value, one hidden row, for a two-layer scratch whose second layer has no full
  attention (an allocation per layer would pass a looser assertion and leak);
- a restore into a *different* request slot writes the destination's live states
  and the destination slot's KV slice, and moves the cursor to the boundary;
- the snapshot refuses a cursor that is not at the boundary, a non-positive
  prefix, a prefix beyond the provider window, and an inactive request; a restore
  refuses a released blob, a state-layout mismatch, and a destination window too
  small;
- release frees every allocation exactly once and is idempotent.

It deliberately does not test numerics: the real round trip (snapshot, advance
the provider, restore, and check the next proposal against an unbroken run) needs
real weights and belongs with the integration unit.

Guards: the MTP/speculative unit tier, the shadow-lifecycle test, and the server
API integration file all pass (exit 0).

## What this unit does not do, and why

The blob has no caller yet. Capturing at the boundary needs two things this unit
deliberately left alone:

1. **The storage home**, which the design entry left open with a recommendation
   (a side table keyed by radix node block ids, evicted with the node). Capturing
   without it would leak one blob per completed prompt.
2. **The block size at the capture site.** The radix match is block-aligned, so
   the boundary is `floor(prompt_len / block_size) * block_size`; the adapter
   does not know the block size, the runner does.
