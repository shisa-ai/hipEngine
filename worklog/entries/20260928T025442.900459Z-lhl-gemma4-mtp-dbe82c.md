# the gemma4 MTP head is verified bit-exact against llama.cpp

## Summary

The Gemma 4 assistant (MTP) head forward now reproduces llama.cpp's own draft
candidates exactly, for four chained draft steps, including the reported
probabilities. Getting there required discarding two wrong models of the head,
both of which had been written into the test as the oracle.

**The input pairing is lagged.** `common/speculative.cpp` documents `pending_h`
as the "pair (h_p, x_{p+1}) at MTP pos p+1" and `verify_h`'s row 0 as "the
sampled token". Step 0 is therefore fed the token the target *just sampled*
together with the hidden row that *produced* it, not the hidden row of the token
itself. Every earlier reading here paired them by row, which is off by one
position.

**The query position is `dp.n_past`, constant across the round.** llama.cpp
takes its `is_mem_shared` branch for Gemma 4 assistants (with a link to the
Hugging Face doc) and adds every draft token at the same `dp.n_past`, one past
the last row the target wrote. The Hugging Face doc's "the position_ids value
are constant" is that branch, not a statement about the whole decode.

**`nextn_proj_post` does not reconstruct the target's hidden state.** The
previous oracle asserted `cos(h_next, backbone_postnorm_at_next_position) > 0.5`.
That cosine is -0.02 for a verified-correct forward, while the backbone's own
hidden rows sit at +0.41 from each other; the projected state is a recurrence
input, not a prediction of the target's activations. Three independent
implementations agree on the value -- this forward, a NumPy reading of
llama.cpp's graph, and transformers' own `Gemma4AssistantForCausalLM` over the
same GGUF -- so the assertion, not the forward, was wrong.

## Changes

- `hipengine/runtime/gemma4_assistant.py`: the head owns its recurrent state.
  `prime(backbone_hidden)` applies the target's final norm to seed it; each
  `forward(token_id, position=..., shared_kv=...)` consumes it and replaces it
  with the head's own projected state. One buffer serves as both input and
  output, which is safe because the input half is copied to host for the
  pre-projection concat before any layer runs and the output is written after
  the last one. `core/memory.py` has no device-to-device copy, so this also
  removes a per-step round trip.
- `tests/test_gpu_gemma4_assistant_forward.py`: the cosine oracle is replaced by
  two tests. The first is functional and self-contained -- the head's first draft
  must be the token the target itself goes on to produce. The second chains four
  steps and asserts the head's top three candidates at each step against the list
  llama.cpp prints under `--verbose` for the same prompt:
  `[45518, 3305, 44027]`, `[108, 107, 236768]`, `[236829, 236775, 818]`,
  `[139, 3729, 623]`.
- `tests/test_unit_gemma4_assistant_geometry.py`: `rotated_pairs` ->
  `rope_angles`, the name `Gemma4RopeConfig` actually uses.

## Validation

- `uv run pytest tests/test_gpu_gemma4_assistant_forward.py -q` -- 2 passed.
- `uv run pytest tests/test_unit_gemma4_assistant_geometry.py
  tests/test_unit_gemma4_assistant_device.py
  tests/test_unit_gemma4_assistant_gguf.py
  tests/test_unit_gemma4_assistant_kv_binding.py -q` -- 25 passed.
- The A/B against llama.cpp is exact, not approximate. With the chat-templated
  prompt (66 tokens, matching `prompt_n` in the server timings), llama.cpp's
  `--verbose` run printed

      pos 0:  45518 (   1.000) 'thought'    3305 (0.000) ' thought'   44027 (0.000) ' thoughtful'
      pos 1:    108 (   0.998) '\n'          107 (0.002) '\n'        236768 (0.000) ')'
      pos 2: 236829 (   1.000) '*'         236775 (0.000) '"'          818 (0.000) 'The'
      pos 3:    139 (   1.000) '   '         3729 (0.000) ' ...'        623 (0.000) ' "'

  and the head returns the same three tokens in the same order with the same
  probabilities at every step. llama.cpp's own acceptance on that call --
  `accepted 1/4 draft tokens` -- follows from the chain: it drafts 108 where the
  target sampled 107.
- Head quality, for calibration: with `--temp 0 --top-k 1` llama.cpp's MTP gets
  `#acc rate/pos = (1.000, 0.750, 0.500, 0.500)`, `#mean acc len = 3.75`. With
  its default sampler (`temp 1.0, top_k 64, top_p 0.95`) it gets
  `(0.652, 0.391, 0.348, 0.304)` over 90 drafts. Those are the numbers an
  integrated draft loop should reproduce.
- The head does not agree with its own backbone on every prompt. On the short
  synthetic prompt the test used to carry it drafts 5279 where the backbone
  drafts 236772; the reference implementation drafts 5279 there too, so that is
  head quality, not a wiring defect. The first test runs on the templated prompt
  and says so.

## Next

- The head is not wired into the engine: `hipengine/generation/gemma4_gguf.py`
  still declares `supports_speculative_mtp = False`, and nothing outside the test
  constructs `Gemma4AssistantHead`. The draft loop and the verify/accept step are
  the remaining work, and `(0.652, 0.391, 0.348, 0.304)` is the acceptance to
  measure against.
- llama.cpp needs `--verbose` for its draft-candidate lines (`SPC_DBG`); the
  default verbosity hides them, which is why the first MTP run here only showed
  the `statistics` line.
