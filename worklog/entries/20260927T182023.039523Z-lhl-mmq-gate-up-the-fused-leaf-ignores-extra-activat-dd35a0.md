# MMQ gate/up: the fused leaf ignores extra activation planes

## Summary

Switched the Gemma 4 gate/up MMQ route to three-plane (d4x3) activation packing,
found the change had no effect, localised why, and reverted the route to one plane
so no cost regression lands. The kernel-level enabler is kept and the blocker is
recorded in code.


`benchmarks/results/2026-09-28-gemma4-mmq-divergence-distribution-dump.json`
records that the route's gate/up error is exactly the one-plane DS4 activation
quantization budget: running the fp32 arm on activations that had only been
quantized to DS4 and back reproduces the MMQ arm's error to four significant
figures, at a ratio of 1.00x at both 64 and 96 ids. The leaf is correct.

The same route is measured and promoted for Qwen35, and `qwen4_exp_profiles.py`
names `d4x3` variants throughout, while `gemma4_experts.py` sized `mmq_workspace`
as `lanes * (hidden_size // 128) * 144` - one 144-byte DS4 block per 128 input
elements per row, commented as "the size the single-plane pack kernel writes".
Reproducing the pack's multi-pass arithmetic on the real captured Gemma 4
activations gave 0.71687% relative error at one plane, 0.00279% at two and
0.00044% at three, so three planes should cut the gate/up error about 1630x.


With the pack writing three populated planes, the workspace sized for three, the
launcher forwarding `ACTIVATION_PASSES = 3` and the route confirmed by
instrumentation to call the new `ds4x3` symbol, the gate/up error is **still
bit-identical**: mean absolute 0.8225 at 64 ids against 0.8225 for the one-plane
quantization arm, ratio 1.00x. The leaf body still reads one activation plane at
this layout and geometry.

Raising `_MMQ_ACTIVATION_PASSES` without fixing that would pay three times the
activation bytes and three times the pack work for zero accuracy, so the route is
left at one plane and the reason is recorded on the constant itself.

## Changes

- `gguf_q4_k_q8_1_selected_prefill.hip`: the fused leaf kernel
  `gguf_q4_k_selected_dual_q8_1_ds4_mmq32_fused_prefill_compact32_kernel` was a
  non-templated kernel that hardcoded `ACTIVATION_PASSES = 1` when calling its
  body, and the launcher's `FUSED_EXPERT_LAYOUT` branch launched it without
  template arguments. Both are fixed: the kernel is templated on the pass count
  and the launcher forwards it. The existing one-pass instantiation is unchanged.
- `gguf_q4_k_q8_1_selected_prefill.hip` / `.py`: added
  `hipengine_gguf_q4_k_selected_dual_q8_1_ds4x3_fused_mmq32_prefill_compact32_bf16_bf16_out`
  (`Q4_K_LAYOUT_RAW, 3, false, true`) and its Python wrapper.
- `gemma4_experts.py`: added `_MMQ_ACTIVATION_PASSES` as the single source of
  truth for the plane count, used by the workspace sizing.

## Validation

- `tests/test_unit_gemma4_expert_route.py`: 48 passed, exit 0.
- Clean JIT rebuild of `gguf_q4_k_q8_1_selected_prefill` from a removed cache,
  which is how the new symbol was confirmed present.
- Two measurement harnesses: `/tmp/mmq_quant.py` (both arms on the same layer,
  input and output buffer) and `/tmp/mmq_planes.py` (reads the packed workspace
  back and counts non-zero quants per plane).


The first two measurement runs after the edits reported the old numbers because
they used a stale `.so`; the build cache key did not change until the `.hip` edit
that mattered. A clean rebuild from a removed cache directory is what made the
result trustworthy. Anyone chasing a "the kernel change did nothing" result here
should force the rebuild before believing it.

## Next

Find where the body's activation read is pinned to one plane for the
`Q4_K_LAYOUT_RAW` plus fused geometry, then raise `_MMQ_ACTIVATION_PASSES` to 3
and re-measure. The acceptance is the measured gate/up error falling by roughly
three orders of magnitude; if it does not, the diagnosis is wrong rather than the
measurement. Then measure the cost against the recorded 1.265x prefill win
(4.177/4.201/4.223 s -> 3.294/3.319/3.327 s on the 512/128 row) before any
promotion claim, and run `scripts/gemma4_mmq_prefill_length_probe.py`, reporting
the full per-length table rather than the exit code.

The route stays gated off. Nothing was promoted.
