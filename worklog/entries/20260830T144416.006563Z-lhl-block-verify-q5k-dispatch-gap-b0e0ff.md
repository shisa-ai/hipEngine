# block-verify route dies on an unsupported q5_k t16 linear dispatch

## Summary

With the correct model path (20260830T144044…), `--mode block-verify` on the campaign model reaches
model load and warm-build, then dies in linear-layer dispatch:

```
ValueError: unsupported GGUF linear dispatch: layout='gguf_q5_k_t16_v1'
  hipengine/runtime/gguf_linear.py:2515 launch_gguf_…
  hipengine/runtime/gguf_linear.py:2181 resolve_gguf_…
```

Two things follow. First, **the sentinel never appeared on the campaign model** - no
`token_id 2147483647` anywhere in the run - so the open question in 20260830T143145… is
still open and
must not be described as reproduced. Second, the verifier-block route is blocked by a
dispatch gap, not
by ROCTX (fixed) or by the model path (fixed).

## Changes

- No code change. Command, verbatim: `scripts/gguf_mtp_verifier_rocprof.py --model
  /models/gguf/Qwen3.8-27B-Q4_K_M.gguf --mode block-verify --block-rows 8 --steps 24 --prompt-ids
  13781,41099,12597,703,2099`, exit 1, log `/tmp/he-parity/blockrows-8-realpath.log`.

## Finding

- The route progressed past load, past the warm-build pass, and into a profiled child before
  failing,
  so ROCTX discovery and the model path are both confirmed working: the failure is downstream.
- A `gguf_q5_k` layout on a Q4_K_M subject is not explained here. Two candidates, both
  unverified: (a)
a non-attention tensor group in this GGUF - drafter/nextn head or output head - really is
    Q5_K and the
  bulk block-verify path resolves it through a variant the registry lacks; (b) the 5-token prompt I
passed (my choice, for validity reasons) steers variant selection into a `t16` tile path
    that no other
  route exercises. Ruled out: the sentinel, the model path, ROCTX discovery.
- Why this matters for #17 specifically: the block-rows-at-fixed-width sweep was the planned
  discriminator between per-row verifier cost and per-lane serialization. That route is unavailable
until the dispatch resolves, so the accept-phase evidence has to come from server
    telemetry instead
  (bg-81, which reports `specdec2_mtp2_*` per row and already showed the accept phase dominating).

## Validation

- Exit code 1 recorded in the log (`python_exit=1`); traceback lines quoted verbatim above.
- Absence of the sentinel checked by grepping the same log, not by assuming it would not recur.
