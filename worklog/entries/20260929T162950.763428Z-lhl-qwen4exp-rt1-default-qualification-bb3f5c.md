# Qualification: RT-1's 4.94% compares 1024->4096, not the server's default

## Summary

A qualification to the RT-1 measurement I recorded earlier this session, found by
checking the call site rather than trusting the word "default".

**The -4.94% compares 1024 -> 4096, which is the benchmark protocol's value, not
the server's.** The serving path's default is **256**.

## The defaults are not one number

| site | value | governs |
|---|---:|---|
| `EngineLoopConfig.max_prefill_chunk_tokens` (`DEFAULT_MAX_PREFILL_CHUNK_TOKENS`) | **256** | the serving/CLI path |
| `EngineLoop.__init__(prefill_chunk_size=...)` | 1024 | only the no-config fallback |
| `EngineLoop` CLI default | 256 | `HIPENGINE_MAX_PREFILL_CHUNK_TOKENS` |
| `qwen4exp_profile_gap.py` own default | 512 | the harness |
| what this packet passed | 1024 | the recorded attribution command |

Line 313's `prefill_chunk_size: int = 1024` is a *fallback*: line 1907 sets
`self.prefill_chunk_size = int(resolved_config.max_prefill_chunk_tokens)`, so a
supplied config overrides it with 256 by default. The CLI help agrees
("default: 256").

## Consequence

The serving-relevant comparison is **256 -> 4096** - 16x the chunk, not 4x - and
it is **unmeasured**. So:

- The -4.94% is a valid result for **1024 -> 4096 under this harness protocol**.
- It is **not** evidence for the size of the production change.
- Nothing in this packet should be cited as "the server would be 4.94% faster".

The X-6 gate result is unaffected in kind: route arithmetic and drift are
invariant to the chunk size over the range tested, and that conclusion does not
depend on which default is in play. **The speedup figure does.**

## Why this is worth a separate entry

I wrote "today's default" repeatedly while measuring, because 1024 is what the
protocol uses and what the recorded command passed. That phrasing quietly
promoted a benchmark parameter into a product default, and it survived several
commits. It is the same defect shape as the rest of this session - a label read
as covering something it does not - and the fix is not a caveat buried in a
README but a correction to the claim.

I found it by checking where the default is actually set, which is what I should
have done before writing "default" the first time. Third mechanism/default claim
of mine this session that did not survive checking.
