# Remove the staged PV singleton unroll rollback lever

## Summary

R0047 is resolved: `HIPENGINE_GEMMA4_PV_UNROLL` and its per-launch
`getenv`/`atoi` reader are gone, and the staged singleton P*V decode walk
launches at a fixed 32-key in-flight V window. Width 32 was already the deployed
default, so this is a host-launch deletion with no numerical change.

Both halves of the removal condition were re-verified at HEAD, independently of
the sweep plan:

- The restored-state 262015 record is in the repository:
  `benchmarks/results/2026-10-09-gemma4-gfx1151-256ki-paired.json`. Its
  `execution_profile` names "PV singleton width 32", `decode_tps` is 10.2094
  against llama.cpp's 7.2105 (1.4159x) at the same depth, and
  `restored_ids_equal_mint_ids` is true over 128 generated tokens.
- The paired width ladder is the table in the immutable entry
  `worklog/entries/20261009T054652.959669Z-lhl-gemma4-pv-unroll32-77ada1.md`:
  interleaved 8/16/32 on both head geometries, u32/u8 = 0.742 sliding at 262144
  keys, 0.645/0.667/0.664 global at 65536/131072/262144, arms bit-identical at
  every point. **Soft spot, confirmed rather than inherited:** the leaf A/B JSON
  behind that table lived only at
  `/tmp/multiloop-beat-llamacpp/pv_unroll_leaf_ab.json`, and that path no longer
  exists on this host, so it cannot be filed under `benchmarks/results/` after
  the fact. The worklog table is the record, as the plan allowed.
- One release cycle without a rollback: the lever is present in `v0.8.0`
  (2026-10-20), `v0.8.1`, `v0.8.2`, and `v0.8.3` (2026-10-24) -- four tagged
  releases, checked by grepping the file at each tag (`v0.7.1` predates the
  file: `gemma4_attention_staged.hip` does not exist in that tag). No test,
  script, profile, or worklog sets the variable, and no artifact records a
  rollback.

The lever had no strict-arm role to lose: all three widths were bit-identical,
so it never isolated a numerical candidate the way R0046's lever did. What it
did cost was a `getenv` + `atoi` on every singleton decode launch, on the
latency-bound path it was introduced to tune.

## Changes

- `hipengine/kernels/hip_gfx1100/gemma4/gemma4_attention_staged.hip`: deleted
  the `getenv`/`atoi` block, the `unroll == 16` / `unroll == 32` branches, and
  the 8- and 16-wide instantiations in
  `launch_gemma4_attention_staged_pv_singleton_rows`; the launcher now returns
  one `launch_singleton_pv<scalar_t, kResidentRows, kExactRows, 32>` call. The
  `kPvUnrollV` template parameter, the singleton kernel body, the grid, the
  shared footprint, the row-group/slice decomposition, and the launcher's
  callers are untouched. The comment above the launch states the fixed width and
  its measured basis instead of naming a lever.
- `docs/ENVS.md`: deleted the lever's row.
- `docs/REFACTOR.md`: rewrote the section as an R0047 removal record -- the
  surviving constant, the unchanged arithmetic and strict fallback, the endpoint
  artifact and the worklog ladder, the four releases, and the /tmp loss of the
  raw ladder JSON.
- `tests/test_unit_gemma4_attention_staged.py`: added
  `test_the_singleton_launcher_instantiates_one_width_and_reads_no_environment`,
  which reads the `.hip` source and pins three things: no `getenv`/`atoi` and no
  `PV_UNROLL` name in the translation unit, exactly one
  `launch_singleton_pv<...>` instantiation and it is width 32, and the
  `kPvUnroll`/`kPvUnrollV` template parameters still forming the kernel
  contract. Without it, re-adding a per-launch selector would be silent: the
  width is not observable from Python.

Not changed: the singleton kernel body, `launch_gemma4_attention_staged_pv_rows`
(the 256-thread decomposition), `gemma4_attention_prefill_bf16` as the strict
fallback and registered plain variant, every other Gemma 4 lever
(`HIPENGINE_GEMMA4_ROUTER_SGEMM` stays, per R0048's restated role), and the
historical artifacts, changelog, and closed campaign docs that mention the
width-32 profile.
